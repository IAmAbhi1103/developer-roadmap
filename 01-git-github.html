Daily basics

Git is the tool that records every change you make to your code, so you can see what changed, who changed it, why, and go back to any earlier point. Every software team in the world uses it — in a Java full-stack job you will run Git commands many times a day, and almost every interview asks about it.

This module covers the local side of Git: everything that happens on your own computer. You will install Git, create repositories, make commits, read history, keep junk files out and undo mistakes safely. Sharing code through GitHub comes next in Module 2, working in branches with a team in Module 3, and the professional-level tools (rebase, reset, reflog, recovery) in Module 4. Git is also the entry point to the delivery pipeline you will meet in DevOps · Module 4.

After this module you will be able to:

  • explain what version control is, and how Git stores your work as snapshots linked by commit hashes;
  • install Git on Windows, set your identity, and understand the three configuration levels and line-ending settings;
  • start or copy a repository with git init and git clone;
  • move changes through the three areas — working folder, staging area and repository — with git add and git commit;
  • read what changed with git status, git diff, git log and git show;
  • write small commits with clear messages, like a professional;
  • write a correct .gitignore and never commit secrets;
  • undo mistakes without losing work, using git restore, git restore --staged and git commit --amend.

What version control is and why every team uses it

Version control records every change to your files as a numbered history, so you can compare, undo and merge work from many people — and Git is the tool almost every team uses for it.

Imagine you are building a Spring Boot project. On Monday it works. On Tuesday you change the payment code and now nothing works. Without version control you would try to remember what you changed, or you would keep folders such as project_final, project_final_v2 and project_final_REAL. Now add four teammates who all edit the same files. That is chaos.

A version control system (VCS) solves this. It keeps a complete history of your project: every change, who made it, when, and a message saying why. A repository (or repo) is the project folder plus this history. Each saved point in the history is called a commit.

What version control gives you

History
Every change is recorded with the author, date and message. You can answer "who changed this line, and why?" months later.
Undo
You can return one file, or the whole project, to any earlier commit. Experiments become safe.
Parallel work
Several people (or you, on several features) work at the same time in separate branches and combine the results later. You will learn this in Module 3.
Collaboration
The system merges edits from different people. When two people change the same lines, it tells you instead of silently overwriting one of them.
Backup and sharing
When you copy the repository to a server such as GitHub, the code and its history are safe even if your laptop is lost.
Traceability
Teams link every change to a ticket, a code review and a build. When production breaks, you can find the exact commit that caused it.

Three generations of version control

  1. Manual copies — folders and zip files. No history, no merging, easy to lose work.
  2. Centralized systems (CVS, Subversion/SVN, Perforce) — one server holds the full history; developers keep only a working copy. You need the server for almost every action.
  3. Distributed systems (Git, Mercurial) — every developer has a full copy of the repository, including the entire history. A server such as GitHub is just one more copy that everyone agrees to share.

A short history of Git

Linus Torvalds, the creator of Linux, wrote Git in 2005. The Linux kernel team had lost access to the tool they were using and needed a replacement that was fast, safe with thousands of contributors, and fully distributed. Git was built around those goals. Today Git is the default choice for new projects. GitHub, GitLab and Bitbucket are websites built on top of Git — you will see exactly how they differ in Git vs GitHub.

What a developer's day looks like with Git

In Module 1 you learn the steps Edit and test and Commit on your own machine. The other steps build on top of them.

Why Git won

  • Speed. Most commands only touch your local disk, so they finish in milliseconds.
  • Cheap branches. A branch is just a small pointer (see How Git stores your work), so making one per feature costs nothing.
  • Integrity. Every object is identified by a hash of its content. Silent corruption or tampering is detected.
  • Ecosystem. IntelliJ IDEA, VS Code, GitHub, GitLab, CI servers, code review tools and deployment pipelines all speak Git.

What Git is not

  • Not a backup of everything. Git only protects what you commit. Untracked and ignored files (.env, build output) are not in the history. A repository that exists only on your laptop is not backed up either.
  • Not made for big binary files. Videos, large datasets and compiled .jar files make the repository slow and large. Teams keep them in artifact repositories or object storage instead.
  • Does not track empty folders. Git tracks files, not directories. To keep an empty folder, put a placeholder file such as .gitkeep inside it.
  • Not a deployment tool. It stores source code. Build and deployment pipelines read from it.

Mistake: using file names as version control

Copies named _final, _v2 and _old tell you nothing about what changed or why, and nothing merges them for you.

Wrong: history hidden in file names

OrderService.java
OrderService_old.java
OrderService_v2_FINAL.java
OrderService_v2_FINAL_fixed.java

Right: one file, history in Git

$ git log --oneline -- OrderService.java
8d41b7e Fix rounding error in order total
3f2a9c1 Add GST calculation to order total
a17c0de Create OrderService

Real projects

In a company, nothing reaches production without Git. A ticket in Jira gets a branch, the branch becomes a pull request, a reviewer approves it, an automated pipeline builds and tests it, and a deployment is tied to a specific commit or tag. When something breaks in production, the team looks at the history to find which commit introduced the bug and either fixes it or reverts that commit. Knowing Git well is part of being employable, not an optional extra.

Interview: "What is version control? What does 'distributed' mean?"

  • Version control records changes to files over time so you can see history, restore old versions and let many people work together.
  • Distributed means every developer's clone holds the full repository, including the whole history — not only a working copy.
  • Consequence: commits, logs, diffs and branches work offline and are fast; the server is a shared copy, not the only copy.
  • Contrast with SVN: one central server, history only there, most commands need the network.
  • Add that Git and GitHub are different things — Git is the tool, GitHub is a hosting service.

Install Git and set up your identity

Install Git for Windows, check it with git --version, then tell Git your name and email once with git config --global — every commit you make carries them.

Check first whether Git is already installed. Open a terminal and run:

$ git --version
git version 2.47.1.windows.1

If you see a version number, Git is installed (your number will differ). If you see 'git' is not recognized (Windows) or command not found (macOS/Linux), install it.

Installing on Windows

The standard way is Git for Windows. Download the installer from git-scm.com/downloads, or install it from a terminal with the Windows package manager:

$ winget install --id Git.Git -e --source winget

Git for Windows installs three things you will use:

  • Git itself — the git command, which also works from Command Prompt, PowerShell and the terminals inside IntelliJ IDEA and VS Code.
  • Git Bash — a terminal that understands Unix-style commands (ls, cat, grep, rm). Most tutorials and Linux servers use these commands, so learning them here pays off later. Paths look different: C:\Users\asha becomes /c/Users/asha.
  • Git Credential Manager — remembers your GitHub login so you do not type it on every push (see HTTPS, tokens and Git Credential Manager).

First-time setup: your name and email

Every commit records who made it. Git does not ask you — you tell it once:

$ git config --global user.name "Asha Rao"
$ git config --global user.email "asha@example.com"
$ git config user.name
Asha Rao

Use the same email that is verified on your GitHub account. GitHub uses the commit email to link commits to your profile and to count them in your contribution graph. If you prefer not to expose your personal email in public commits, GitHub gives you a private noreply address (see Creating your GitHub account).

Tip: use different emails automatically with includeIf

If you keep work projects in one folder, add this to ~/.gitconfig and put the work email in ~/.gitconfig-work. Every repository under ~/work/ then uses the work identity without any per-repo command.

[includeIf "gitdir:~/work/"]
    path = ~/.gitconfig-work

Recommended settings for a new machine

$ git config --global init.defaultBranch main
$ git config --global core.editor "code --wait"
$ git config --global alias.st "status -s"
$ git config --global alias.lg "log --oneline --graph --all --decorate"
  • init.defaultBranch main — new repositories start on main instead of the older default master. Without it, a plain git init may create master, and then your local name will not match the main branch that GitHub creates.
  • core.editor "code --wait" — opens VS Code for commit messages. --wait makes Git wait until you close the file.
  • alias.* — shortcuts. After this, git st runs git status -s and git lg prints the compact history graph.

The result is a plain text file you can read and edit:

[user]
	name = Asha Rao
	email = asha@example.com
[init]
	defaultBranch = main
[core]
	editor = code --wait
[alias]
	st = status -s
	lg = log --oneline --graph --all --decorate

Tip: if you land in Vim, here is the way out

If you run git commit without -m and no editor is configured, Git opens Vim. Press i to start typing, then Esc, then type :wq and press Enter to save and quit. To abandon the commit, press Esc and type :q!. An empty message cancels the commit with Aborting commit due to empty commit message.

Line endings: why they matter on Windows

Windows ends each text line with two characters, CRLF (\r\n). Linux and macOS use one, LF (\n). If a Windows developer and a Linux developer commit the same file without a policy, one of two bad things happens: every line of the file shows as changed in diffs, or a shell script saved with CRLF fails on a Linux server with an error such as /bin/bash^M: bad interpreter.

The setting core.autocrlf tells Git to convert line endings for you:

ValueOn commitOn checkoutUse on
trueCRLF → LFLF → CRLFWindows (the installer default)
inputCRLF → LFNo changemacOS and Linux
falseNo changeNo changeWhen a .gitattributes file controls everything

With true the repository always stores LF, while your Windows editor sees CRLF. You may see this harmless warning when you add a file:

warning: in the working copy of 'Hello.java', LF will be replaced by CRLF the next time Git touches it

A personal setting is not enough for a team, because each developer can configure it differently. The reliable fix is a .gitattributes file committed to the repository, which applies to everybody:

# Let Git decide text files and normalise them to LF inside the repository
* text=auto

# Scripts must always be LF, even on Windows
*.sh   text eol=lf
mvnw   text eol=lf

# Windows batch files must be CRLF
*.bat  text eol=crlf
*.cmd  text eol=crlf

# Never touch binary files
*.png  binary
*.jpg  binary
*.jar  binary

If you add .gitattributes to an existing project, run git add --renormalize . once so the files already in the repository are normalised too.

Rule: configure identity before the first commit

Set user.name and user.email before your first commit. A commit that already exists keeps its author for good unless you rewrite it (see Undo safely for the last commit, and Module 4 for older ones).

Conventions

  • Use your real name and a stable email — it is shown to your whole team in every commit.
  • Keep --global for personal preferences and local config for project-specific values.
  • Keep init.defaultBranch as main and commit a .gitattributes file for line endings in team projects.
  • Never put passwords or tokens in .gitconfig files; use the credential helper.

Edge cases

  • Values with spaces need quotes: git config --global user.name Asha Rao fails with error: wrong number of arguments; write "Asha Rao".
  • Running git config user.name "X" outside a repository fails with fatal: not in a git directory because local is the default level. Add --global.
  • Config keys are case-insensitive for the section and variable name, which is why --list prints init.defaultbranch in lower case.
  • A repository can override your global identity. If commits show the wrong email, run git config --show-origin user.email in that repository to see which file wins.

Interview: "How do you configure Git? What are the config levels?"

  • Three levels — system, global, local — stored in the Git install folder, ~/.gitconfig and .git/config. Local overrides global overrides system.
  • First setup is user.name and user.email; they go into every commit.
  • Inspect with git config --list --show-origin.
  • Explain CRLF vs LF and core.autocrlf, and say that a team should enforce it with .gitattributes.

How Git stores your work: snapshots, hashes and HEAD

Git saves each commit as a full snapshot of your project, names it with a SHA hash, links it to its parent commit, and uses tiny pointers — HEAD and branch names — to remember where you are.

You can use Git for months by memorising commands. You will use it well only when you know what the commands do inside. The good news: the core idea is small. Git is a simple key-value store — you give it content, it gives back a name (a hash) — and four kinds of objects built on top of that.

Snapshots, not differences

Older systems such as SVN store a file as a list of changes: "version 1, then these lines added, then these lines removed". Git thinks differently. Each time you commit, Git records a snapshot of every tracked file as it looks at that moment. If a file did not change, Git does not copy it again — the new snapshot simply points to the same stored content as before. So snapshots are cheap, and going to any commit is fast, because Git does not have to replay a chain of changes.

When you run git diff or git show, Git computes the difference between two snapshots on the fly. The difference is not what is stored.

The four object types

Everything inside the hidden .git/objects folder is one of four kinds of objects:

blob
The content of one file — only the content, not the file name. Two files with identical content share one blob.
tree
A folder. It lists names and, for each name, the hash of a blob (a file) or another tree (a sub-folder).
commit
A snapshot label. It points to one top-level tree, to its parent commit(s), and stores the author, date and message.
tag
A fixed, named pointer to a commit, optionally with its own message (used for releases; see Module 4).

SHA hashes: the name of every object

Git names an object by running its content through a hash function. The result is a 40-character hexadecimal string, called the SHA (or commit hash), for example 3f2a9c1e8b7d4a5c6f0e1d2b3a4c5d6e7f8a9b0c. (Git has been moving from SHA-1 to SHA-256, which gives 64 characters; today's repositories are still SHA-1 by default, and everything you learn here works the same.)

  • Same content gives the same hash; any change gives a completely different hash. This is how Git detects corruption and how it knows two files are identical without comparing them.
  • A commit's hash is computed from its tree, its parent hash, author, date and message. So a commit's hash includes its parent's hash: changing an old commit changes every commit after it. This chain makes history tamper-evident.
  • You rarely type all 40 characters. The first 7 are normally enough: git show 3f2a9c1. Git accepts any prefix that is unique in the repository (at least 4 characters).

Parent links make a history

Each commit stores the hash of the commit that came before it (its parent). A merge commit has two parents. Following parent links backwards from the newest commit gives you the whole history, and that is exactly what git log prints.

Branches and HEAD are just pointers

A branch is a file that holds one commit hash. That is all. The branch main is the file .git/refs/heads/main containing the hash of its latest commit. When you commit, Git creates the new commit and moves the branch pointer forward to it. Creating a branch means writing a new 41-byte file, which is why branches are instant and free.

HEAD is a special pointer that means "where I am now". Usually it points to a branch name, not to a commit directly:

$ cat .git/HEAD
ref: refs/heads/main
$ cat .git/refs/heads/main
3f2a9c1e8b7d4a5c6f0e1d2b3a4c5d6e7f8a9b0c

The next commit becomes the child of whatever HEAD points to, and the branch HEAD points to moves forward with it. When HEAD points straight at a commit instead of a branch, you are in detached HEAD state — you will meet that in Module 3.

Naming commits relative to HEAD

ExpressionMeaning
HEADThe commit you are on (the latest commit of the current branch)
HEAD~1 or HEAD~ or HEAD^The first parent of HEAD — one commit back
HEAD~3Three commits back, always following first parents
HEAD^2The second parent of HEAD (only exists for a merge commit)
main~2Two commits before the tip of main

~ means "go back N generations"; ^ means "choose which parent". For an ordinary commit with one parent, HEAD~1 and HEAD^ are the same.

Where everything lives: the .git folder

A repository is just your project folder plus one hidden folder, .git. Delete .git and the history is gone, but your files stay. Copy .git elsewhere and you have the whole repository.

.git/
├── HEAD            which branch (or commit) you are on
├── config          local configuration
├── index           the staging area (binary file)
├── objects/        all blobs, trees, commits, tags
├── refs/
│   ├── heads/      one file per local branch
│   ├── remotes/    remote-tracking branches (Module 2)
│   └── tags/       tags
└── logs/           the reflog (Module 4)

Rule: never edit or delete files inside .git by hand

Use Git commands. Hand-editing .git is the fastest way to corrupt a repository. Also never run git init inside a folder that already sits inside another repository, or you create a nested repository.

Edge cases

  • Git stores each distinct content once, so a copied file costs almost nothing. It stores the content, not the file name — names live in trees.
  • Moving a file does not "record a move". Git simply sees one path disappear and another with identical content appear, and detects the rename when you ask (git log --follow, git diff -M).
  • Unreachable objects (for example commits left behind after a mistake) are not deleted immediately. Git keeps them for a while and cleans up later with garbage collection. This is what makes recovery possible (Module 4).
  • Git packs old objects together and stores them as compressed deltas inside pack files to save disk space. That is an internal storage optimisation. Conceptually, every commit is still a full snapshot.

Interview: "Does Git store diffs or snapshots? What is HEAD?"

  • Snapshots: each commit points to a tree describing the whole project; unchanged files reuse the same blob.
  • Objects are blob, tree, commit and tag, each named by a SHA hash of its content; the commit hash includes the parent hash, so history is tamper-evident.
  • A branch is a movable pointer to a commit; HEAD is a pointer to the current branch (or commit).
  • That is why branching is cheap and why committing just moves a pointer forward.

The three areas and the four file states

Changes travel from your working folder, to the staging area with git add, to the repository with git commit — and every file is always untracked, unmodified, modified or staged.

Beginners expect one step: change a file, save it to history. Git uses two steps, and that is what makes it powerful. The extra step lets you choose exactly which changes go into the next commit.

The three local areas

Working folder (working tree)
The real files on your disk, the ones you open in IntelliJ. You edit them freely.
Staging area (index)
A preparation zone, stored in .git/index. It holds the snapshot of what will go into the next commit. Think of it as the box you pack before you seal and ship it.
Repository (the .git folder)
The permanent history of commits. A commit is stored here only when you run git commit.

An everyday comparison: a Swiggy order. Choosing dishes is editing the working folder. Putting them in the cart is git add — you can still remove items. Paying is git commit — now it is recorded.

Why a staging area exists

Suppose you fixed a bug in PaymentService.java and, in the same hour, started a new feature in OrderController.java. You want two separate commits, each with a clear message. With a staging area you stage and commit the bug fix first, then the feature. Without it, Git could only commit "everything that changed". Even inside one file you can stage only some changes (git add -p, see git add variants).

The four file states

Every file in your folder is in exactly one of these states:

StateMeaningHow it gets here
UntrackedGit has never seen this file; it is not in any commit or in the staging areaYou create a new file
Unmodified (committed)The file matches the last commitAfter git commit, or right after a clone

Tracked means "Git knows this file": it is in the last commit or in the staging area. Everything else is untracked (or ignored, see .gitignore).

The same file can be in two places at once

This surprises everybody once. If you stage a file and then edit it again, the staged version and the working version differ. git status lists the file twice:

$ git add README.md
$ echo "Runs on port 8080" >> README.md
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	modified:   README.md

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md

A commit now saves only the staged version. The last line you typed stays modified in the working folder until you git add it again.

Mistake: thinking git add is only for new files

Beginners edit a tracked file, run git commit -m "fix" and see no changes added to commit. Every change — new, edited or deleted — must be staged first. (The shortcut git commit -a stages modified and deleted tracked files for you, but never new ones.)

Edge cases

  • An empty folder never shows up as untracked — Git tracks files only.
  • If you change a file's permissions (executable bit), Git sees a change even if the content is the same.
  • A file that is listed in .gitignore but was already committed is still tracked, so it still shows up as modified (see .gitignore).

Interview: "Explain the working directory, staging area and repository."

  • Working directory: real files you edit. Staging area (index): the snapshot being prepared for the next commit. Repository: committed history in .git.
  • Commands: git add moves changes working → staging; git commit moves staging → repository.
  • Reason for staging: build commits deliberately, even from part of a file with git add -p.
  • Name the four file states: untracked, unmodified, modified, staged.

Start a repository: git init and git clone

Use git init to turn a folder you already have into a repository, and git clone <url> to copy an existing repository with its full history.

Every Git journey starts one of two ways. Either you have a project and want Git to track it (git init), or somebody already has a repository and you want a copy (git clone).

git init: create a new repository

$ mkdir java-practice
$ cd java-practice
$ git init

$ git status

No commits yet

If you started a project with Spring Initializr or an IDE and now want Git, run git init in the project root — the folder that holds pom.xml — and create your .gitignore before the first git add ..

Mistake: git init in the wrong folder

Running git init in your home folder (C:\Users\asha) makes your whole user profile a repository, and git status then lists thousands of files. Always cd into the project folder first. If it happened, delete the stray .git folder in the wrong place.

Exceptions and errors

Interview: "Difference between git init and git clone?"

  • init makes an empty repository from a local folder; clone copies an existing repository including full history and sets up origin.
  • Mention what a clone creates: a working copy, remote-tracking branches and a tracking local branch.
  • Add that a clone is a real, complete backup — you can clone from a clone.

Useful variations of git commit:

  • git commit (no -m) opens your editor so you can write a longer message.
  • git commit -a -m "msg" (or -am) first stages every modified or deleted tracked file. It skips new files. Convenient, but it skips your chance to review what goes in.
  • git commit -m "Summary" -m "Body paragraph" gives a subject and a body without opening an editor.
  • git commit --amend fixes the last commit (Undo safely).
  • git commit --allow-empty -m "Trigger CI" makes a commit with no changes; teams use it to re-run a pipeline.

What "nothing to commit" tells you

On branch main
Changes not staged for commit:
	modified:   README.md

no changes added to commit (use "git add" and/or "git commit -a")

You edited the file but never staged it. Run git add README.md, then commit. If the output instead says nothing to commit, working tree clean, everything is already committed.

A habit that saves you: look before you commit

  1. git status — which files changed? Any surprise files (build output, .env)?
  2. git diff — read your own unstaged changes line by line. You will catch leftover System.out.println calls and debug code.
  3. git add only the files (or parts) that belong to this one change.
  4. git diff --staged — read exactly what will be committed.
  5. git commit -m "..." with a clear message.

Using the IDE

IntelliJ IDEA and VS Code both have a Commit window with checkboxes, diffs and a message box. They run the same Git commands underneath. Use them if you like, but learn the command line first: it works the same everywhere (servers, CI, pair sessions) and it teaches you what the IDE buttons do.

Convention: commit often, review always

  • Commit when one logical thing works — a method added and tested, a bug fixed. Do not wait until the end of the day.
  • Run git status often. It costs nothing and prevents most mistakes.
  • Never commit code that does not compile. Run the build or the tests first.

Mistake: git commit -m with unquoted words, or the wrong quotes

The message must be one quoted argument. In Windows cmd, use double quotes; single quotes are not treated as quotes there.

Wrong: words split into many arguments

error: pathspec 'null' did not match any file(s) known to git

Right: one quoted message

$ git commit -m "Fix null pointer in invoice"
[main 2c8a1be] Fix null pointer in invoice
 1 file changed, 3 insertions(+), 1 deletion(-)

Edge cases

  • In a brand-new repository git log fails with fatal: your current branch 'main' does not have any commits yet. Make a commit first.
  • If a file was deleted in the folder, the deletion is also a change that needs staging: git add file (or git rm file) stages it.
  • A commit never contains unstaged changes. After committing, any edits made after git add are still in your folder as modifications.
  • A pre-commit hook (a script a team installs) can reject a commit, for example when a formatter or a secret scanner fails. Read its message and fix the cause; do not bypass it with --no-verify unless the team agrees.

Interview: "Walk me through your daily Git workflow."

  • Pull the latest code, create a branch, edit, then loop: status, diff, add, commit.
  • Push the branch and open a pull request (Modules 2 and 3).
  • Say that you review your own diff before every commit and keep commits small.

Renaming and moving: git mv

$ git mv InvoiceSvc.java InvoiceService.java
$ git status -s
R  InvoiceSvc.java -> InvoiceService.java

git mv old new is the same as three steps: rename in the folder, git rm old, git add new. Convention: rename in its own commit

Commit a pure rename (or move) separately from edits to the same file. If you rename and rewrite half the file in one commit, Git may not recognise the rename, and git log --follow and git blame lose the trail. IntelliJ's refactor-rename does the file rename and the code updates together — still, keep the commit focused.

Edge cases

  • Case-only renames on Windows. Windows treats Invoice.java and invoice.java as the same name, and Git may not notice the change. Use git mv invoice.java Invoice.java so Git records it. A mismatch between the class name and the file name also breaks the build on Linux servers, so this matters.
  • Empty directories cannot be added. Put a .gitkeep file inside (the name is a convention; Git gives it no special meaning).
  • git add on an ignored file fails with The following paths are ignored by one of your .gitignore files; add -f to force it (rarely a good idea).
  • On Windows, git add . may print LF will be replaced by CRLF warnings; they are harmless (line endings).

Interview: "Difference between git add . , git add -A and git add -u?"

  • -u stages modified and deleted tracked files only — no new files.
  • -A stages new, modified and deleted files in the whole repository; . does the same for the current directory and below.
  • Also mention git add -p for committing part of a file, and that you review with git diff --staged.

Good commits: small changes and clear messages

Make each commit one logical change, and write a message with a short imperative summary (about 50 characters or less), a blank line, and a body that explains why.

A commit is a message to your team and to yourself in six months. When production fails at night, someone will read your commit list to decide what to revert. A history of fix, changes and asdf is useless. A clean history is a feature of your project.

One commit, one logical change

Ask: "can I describe this commit in one short sentence without using 'and'?" If not, split it.

  • Atomic. A commit does one thing: add a validation, fix a bug, rename a class, upgrade a dependency.
  • Complete. The project builds and the tests pass at every commit. Then git bisect (see Module 4) and reverts work reliably.
  • Reviewable. Reviewers can understand a small diff in minutes. A 2,000-line commit gets a quick "looks good" and hides bugs.
  • Separate concerns. Do not mix formatting changes, refactoring and new behaviour. Mix them and the real change disappears in noise.

Anatomy of a good message

Add retry to payment gateway client

The gateway returns HTTP 503 during its nightly maintenance window.
Retry up to three times with exponential backoff instead of failing
the order immediately. Orders failed 2-3 times every night before.

Refs: BILL-142
  1. Subject line: a summary of about 50 characters, up to 72 at most. Many tools (GitHub lists, git log --oneline) cut longer ones.
  2. Blank line after the subject. Git and tools use it to separate the subject from the body.
  3. Body (optional for tiny changes): explain what and why, not how — the diff already shows how. Wrap lines at about 72 characters.
  4. Footer (optional): ticket numbers (Refs: BILL-142), Closes #57 (GitHub closes the issue when the commit reaches the default branch), breaking-change notes.

Imperative mood

Write the subject as a command, as if finishing the sentence "If applied, this commit will ...". That matches the messages Git itself writes (Merge branch ..., Revert "...").

Conventional Commits

Many teams add a short type prefix so tools can generate changelogs and decide version numbers. This style is called Conventional Commits:

feat: add UPI payment option to checkout

The usual types are feat, fix, docs, style, refactor, test and chore; a ! or a BREAKING CHANGE: footer marks a breaking change. Use it only if your team does — consistency inside one repository matters more than the style you pick.

Writing a long message

For a message with a body, run git commit without -m so your editor opens. Lines starting with # are comments and are ignored. You can also pass two -m options: the first becomes the subject, the second the body.

$ git commit -m "Add retry to payment gateway client" \
             -m "Gateway returns 503 during nightly maintenance. Retry 3 times."

Rule: never commit secrets or generated files

Before every commit confirm that passwords, tokens, .env files, build output (target/) and IDE folders are not staged. Removing a secret in a later commit does not remove it from history (see .gitignore).

Conventions and habits

  • Commit work-in-progress freely on your own branch, then tidy it before sharing (interactive rebase, Module 4).
  • Mention the ticket id if your team uses Jira or GitHub issues.
  • Do not write the "how" in the message ("changed line 40 to use a for loop"); explain the reason ("loop avoids a second query").
  • A commit that only fixes a typo from the previous commit is a candidate for git commit --amend if you have not pushed yet.
  • Do not commit commented-out code or TODO debug prints. Version control remembers old code for you.

Mistake: one giant commit at the end of the day

"Add whole checkout feature" with 60 changed files cannot be reviewed, cannot be reverted partly, and breaks git bisect. Commit as each piece works: model, repository, service, controller, tests.

Edge cases

  • An empty message aborts the commit: Aborting commit due to empty commit message.
  • In -m "...", special characters such as ! or $ can be expanded by some shells. Use single quotes in Git Bash when your message contains them.
  • Authors and committers can differ: after a rebase or a cherry-pick, the author stays the original person while the committer is you.

Interview: "What makes a good commit message?"

  • Short imperative summary (about 50 characters), blank line, body explaining why and not how, ticket reference.
  • One logical change per commit; builds and tests pass at every commit.
  • Why it matters: code review, git blame, bisect, reverts and changelogs all depend on it.

Useful options

$ git diff --stat              # summary: files and +/- counts
$ git diff --name-only         # just the file names
$ git diff --name-status       # file names with A / M / D letters
$ git diff src/main/java       # limit to a path

$ git diff main...feature      # changes on feature since it left main

The two-dot form A..B compares the tips of A and B directly (same as git diff A B). The three-dot form A...B compares B with the point where it split from A — that is "what did this branch add", which is what a pull request shows.

The classic surprise: git diff shows nothing

You edit a file, run git add, then git diff. The output is empty. That is not a bug: the change is now in the staging area, so the working folder and the staging area are equal. Run git diff --staged to see it.

$ git add InvoiceService.java
$ git diff
$ git diff --staged
diff --git a/InvoiceService.java b/InvoiceService.java

Diff tools and the IDE

The terminal diff is enough for small changes. For big ones, IntelliJ IDEA's side-by-side diff (Ctrl+D in the Commit window) and VS Code's Source Control view are easier to read. git difftool opens an external tool you configure.

Mistake: committing without reading the diff

Always run git diff --staged before git commit. This is where you spot a stray System.out.println, a hard-coded password, a wrong file, or a huge accidental reformat.

Edge cases

  • git diff does not show untracked files. Stage them with git add -N file (intent-to-add) or just use git status.
  • Binary files print Binary files a/logo.png and b/logo.png differ — no line diff.
  • With CRLF conversion active, a file may show every line as changed. See line endings in Install Git.
  • If the text \ No newline at end of file appears, the last line lacked a final newline; adding one counts as a change.
  • Long output opens in a pager; press q to leave. Use git --no-pager diff to print it all at once.

Reading the header lines closely

The line index 3a4b5c6..8d9e0f1 100644 holds two abbreviated blob hashes (the old and the new content of the file, as Git stores them) and the file mode. 100644 means a normal file; 100755 means an executable one. If you only change the mode (for example with chmod +x), the diff shows old mode 100644 and new mode 100755 and no text hunks. A new file shows new file mode 100644 with --- /dev/null, a deleted file shows deleted file mode with +++ /dev/null, and a renamed file shows rename from and rename to lines.

A diff can contain many hunks, one for every changed area. Each hunk has its own @@ header. Git adds three unchanged context lines around every change by default, so you can find the place in the file. Change this with -U<n>: git diff -U0 shows only changed lines, git diff -U10 shows ten lines of context. If two changes are close together, Git merges them into one hunk.

The three areas, step by step

The best way to understand the diff forms is to watch all three areas move during one edit. Here a developer changes one line of a file called application.properties.

$ echo "server.port=9090" >> src/main/resources/application.properties
$ git diff --stat
 src/main/resources/application.properties | 1 +
 1 file changed, 1 insertion(+)
$ git add src/main/resources/application.properties
$ git diff --stat                  # empty: working folder == staging area
$ git diff --staged --stat
 src/main/resources/application.properties | 1 +
 1 file changed, 1 insertion(+)
$ git commit -m "Run the service on port 9090"
$ git diff HEAD                    # empty: nothing differs from the last commit
$ git diff HEAD~1 HEAD --name-status
M       src/main/resources/application.properties

After git add the change moved from "unstaged" to "staged", so the first diff went empty and the second filled up. After the commit, both are empty because all three areas hold the same content. git diff HEAD~1 HEAD then shows the commit you just made. This is also what git show prints (plus the commit message).

If you stage only part of a file (git add -p), the same file appears in both git diff (the part you left out) and git diff --staged (the part you picked). git diff HEAD shows the sum of the two.

diff, show, log -p and status

These commands are often mixed up. git status lists which files differ. git diff shows what lines differ, between areas that are not committed yet. git show <commit> shows one finished commit with its diff. git log -p shows the diff of every commit in the history. Use status first, diff second, and show or log -p when you look at the past.

Wrong: commit straight after add

Right: read what is staged first

Rule: know which two areas a diff compares

Plain git diff never shows staged changes, and --staged never shows unstaged ones. When a diff looks wrong or empty, first ask "which two areas am I comparing?" before you suspect Git.

Convention: a review loop before every commit

Professionals follow the loop git status → git diff → git add → git diff --staged → git commit. Small, focused diffs also make better commits: if the staged diff mixes two unrelated changes, unstage one part and commit them separately.

More edge cases

  • A diff between branches with the two-dot form can look "reversed" for what you expected; use the three-dot form to see only what the feature branch added.
  • Very large or generated files (lock files, minified bundles) make diffs unreadable. Limit the diff to your source paths.
  • Renames are detected by similarity, not recorded; a renamed file that was also heavily edited may show as a delete plus an add.

Interview: "Difference between git diff and git diff --staged?"

  • Plain git diff: working folder vs staging area (unstaged changes). --staged: staging area vs HEAD (what the next commit contains).
  • Add git diff HEAD for both together, and git diff A..B for two commits or branches.
  • Explain why a diff can be empty right after git add.

20-second answer: "Git has three areas: the working folder, the staging area and the last commit. Plain git diff compares working folder with staging, so it shows unstaged edits. git diff --staged compares staging with the last commit, so it shows exactly what my next commit will contain. git diff HEAD shows both together. After git add, plain diff goes empty, which is normal."

Keep junk and secrets out: .gitignore

A .gitignore file lists patterns of files Git must never track — build output, IDE folders and secrets — and it only works for files that are not already tracked.

Your project folder holds more than source code. Maven writes target/, IntelliJ writes .idea/, Node writes node_modules/, and you have a .env with passwords. None of that belongs in history: it is generated, personal to your machine, huge, or secret. Without .gitignore they all appear in git status and one careless git add . commits them.

How it works

Create a text file named .gitignore in the project root and commit it, so the whole team shares the rules. Each line is a pattern. Lines starting with # are comments; empty lines are ignored. Git applies the patterns to untracked files: matching files no longer show in git status and are skipped by git add ..

# Build output
target/

# IDE
.idea/

# Secrets
.env

Why a few files are un-ignored

The Maven and Gradle wrapper jars must be committed so everyone can run ./mvnw or ./gradlew without installing the tool; that is why they have ! lines after *.jar. .env.example is a template with fake values that tells teammates which variables to set — committing it is good practice.

Which files can have rules?

  1. .gitignore in the project — shared with the team (the usual place). Folders can have their own .gitignore that applies below them.
  2. .git/info/exclude — same syntax, but private to your clone and not committed. Good for personal scratch files in one project.

A good split: the project .gitignore holds things every contributor generates (target/, node_modules/, secrets); your global file holds your personal editor choices.

Why is Git still tracking my ignored file?

.gitignore only affects untracked files. If a file was committed before you ignored it, Git keeps tracking it and keeps showing changes. You must tell Git to forget it — but keep it on disk — with git rm --cached:

$ echo ".env" >> .gitignore
$ git rm --cached .env
rm '.env'
$ git rm -r --cached .idea/
$ git add .gitignore
$ git commit -m "Stop tracking .env and .idea"
$ git status -s
$ git check-ignore -v .env
.gitignore:12:.env	.env

git check-ignore -v <path> explains which rule (file, line and pattern) ignores a path — the best debugging tool when a file is ignored and you do not know why. If it prints nothing, no rule matches. To list ignored files, use git status --ignored.

To untrack every file whose rule you added later, the full reset is: git rm -r --cached ., then git add ., then commit. Review git status carefully before committing.

If a secret was already committed

Rule: never commit secrets, and treat a leaked one as compromised

Passwords, API keys, database URLs with credentials, private keys and tokens must never be in a repository. If one was committed — even if you deleted it in the next commit — it is still in history, and anyone who cloned it, or any bot scanning GitHub, can read it. First rotate the secret (change the password, revoke the key). Then optionally remove it from history with a history-rewriting tool (Module 4). Rotation matters more than cleanup.

The professional pattern: read secrets from environment variables or a secrets manager. In Spring Boot, write spring.datasource.password=${DB_PASSWORD} in application.yml and set DB_PASSWORD outside Git.

Common mistakes

  • Adding a file to .gitignore after committing it and expecting it to vanish.
  • Writing target vs target/ vs /target without knowing the difference (see the pattern table).
  • Trailing spaces in a pattern line: they are part of the pattern, so it no longer matches (unless escaped).
  • Ignoring *.jar and breaking the Maven wrapper for teammates.
  • Naming the file .gitignore.txt — Windows Notepad may add .txt. The name must be exactly .gitignore.

Edge cases

  • Ignored files are not deleted by Git; they simply stay out of status and staging.
  • Force-add an ignored file with git add -f; after that it is tracked and ignore rules no longer apply to it.
  • git clean -fdX deletes all ignored files (for example target/); git clean -n first shows what would be removed. Be careful: ignored files cannot be recovered from Git.
  • On case-insensitive file systems (Windows, macOS), pattern matching depends on core.ignorecase.

Interview: "I added a file to .gitignore but Git still shows it. Why?"

  • The file is already tracked; .gitignore only affects untracked files.
  • Fix: git rm --cached <file>, commit. The file stays on disk but leaves the repository going forward.
  • Debug with git check-ignore -v. If it was a secret, rotate it — history still contains it.

Undo safely: restore, restore --staged and commit --amend

Discard working changes with git restore file, unstage with git restore --staged file, and fix the last commit with git commit --amend — all before you push.

Everybody makes mistakes: you edit the wrong file, stage too much, or misspell a commit message. Git makes most mistakes fixable, but the right command depends on where the mistake is: working folder, staging area, or the last commit. This article covers the safe commands. Dangerous ones (reset --hard, force push, rebase) are in Module 4.

The undo matrix

1. Discard changes in the working folder

$ git status -s
 M src/main/java/InvoiceService.java
$ git restore src/main/java/InvoiceService.java
$ git status -s
$

git restore <file> copies the version from the staging area (or from the last commit, if nothing is staged) back into the working folder. Your edits are gone — Git never saw them, so Git cannot bring them back. Check with git diff first when unsure. Restore a whole folder with git restore src/; restore everything with git restore ..

Mistake: restoring work you wanted to keep

Uncommitted changes that were never staged or committed are the one thing Git cannot recover. If you are not sure, git stash (Module 3) or make a temporary commit first.

2. Unstage a file

$ git add .
$ git status -s
M  pom.xml
A  scratch.txt
$ git restore --staged scratch.txt
$ git status -s
M  pom.xml
?? scratch.txt

--staged makes the command act on the staging area instead of the working folder: it resets the staged version to match the last commit, and your edits stay in the folder. It is the exact opposite of git add. To change both areas at once, use git restore --staged --worktree <file>. In a repository with no commits yet, git restore --staged fails; use git rm --cached <file> there.

3. Fix the last commit: git commit --amend

--amend replaces the latest commit with a new one. Use it for a typo in the message, or a file you forgot.

$ git commit -m "Add invoce total"
[main 2c8a1be] Add invoce total
$ git commit --amend -m "Add invoice total"
[main 9f1d3a7] Add invoice total
 Date: Mon Nov 9 19:05:44 2026 +0530
$ git commit -m "Add Coupon entity and repository"
$ git add src/main/java/CouponRepository.java
$ git commit --amend --no-edit
[main 4e6b8c2] Add Coupon entity and repository
 2 files changed, 41 insertions(+)

Notice the hash changed from 2c8a1be to 9f1d3a7. The old commit was not edited — Git made a new commit with a new hash (a commit's hash includes its message and content, see How Git stores your work) and moved the branch to it. --no-edit keeps the old message. Running git commit --amend with nothing staged and no -m opens the editor to change just the message.

Why amend is fine before push and dangerous after

Rule: amend only commits you have not pushed

Amend rewrites history: the old commit is replaced by a different one. If the old commit is only on your computer, nobody else is affected. If you already pushed it, teammates may have built work on the old hash. Your next push is rejected as a non-fast-forward; forcing it over their work creates duplicate commits and conflicts for everyone. For pushed commits use git revert, or, on your own feature branch only, a force push with care (Module 4, and Push rejected).

The older commands: checkout -- file

Before Git 2.23 (2019) the same jobs were done by git checkout, which also switches branches — one command with two very different meanings. Git added git restore and git switch to split them. You will still see the old forms in tutorials and old scripts:

Getting an old version of a file

$ git log --oneline -- src/main/java/InvoiceService.java
8d41b7e Fix rounding error in order total
3f2a9c1 Add GST calculation to order total
$ git restore --source=3f2a9c1 src/main/java/InvoiceService.java

The old version arrives as an ordinary modification. Review it with git diff, then stage and commit — or restore it again.

Edge cases and errors

  • error: pathspec 'x' did not match any file(s) known to git — the path is wrong or the file is untracked. git restore cannot touch untracked files; delete them by hand or with git clean.
  • If you deleted a tracked file in your folder, git restore <file> brings it back from the staging area or last commit.
  • git restore --staged on a file staged for deletion makes it unstaged-deleted; run git restore on it again to bring the file back.
  • Amending during a merge or a rebase has special rules; finish the operation first.
  • git clean -f deletes untracked files for good. Always preview with git clean -n; add -d for folders.

Tip: when something looks very wrong, stop and check

Run git status and git log --oneline -5. Git almost never loses committed work. Even after a wrong amend, the previous commit still exists for a while and the reflog can find it (Module 4). Panic and random commands cause more damage than the first mistake.

Interview: "How do you undo changes in Git?"

  • Say where the change is: working folder → git restore file; staged → git restore --staged file; last commit → git commit --amend.
  • Warn that discarding unstaged edits is permanent, and that amend rewrites history, so it is only for unpushed commits.
  • For pushed commits, use git revert, which adds a new commit instead of rewriting history.
  • Mention that git restore/git switch replaced the overloaded git checkout in Git 2.23.

Interview questions — Daily Git basics

What is Git, and how is it different from GitHub?

Git is a distributed version control system that runs on your computer and records the history of your files. GitHub is a website that hosts Git repositories and adds pull requests, issues, code review and automation. You can use Git without GitHub (local use, GitLab, Bitbucket, your own server), but not GitHub without Git.

What does "distributed" mean in a version control system?

Every clone holds the full repository, including the whole history. You can commit, view logs, diff and branch offline. A central server such as GitHub is a convenient shared copy, not the only copy. In a centralized system (SVN) the history lives only on the server.

Explain the working directory, staging area and repository.

The working directory holds the files you edit. The staging area (index) holds the snapshot being prepared for the next commit. The repository (.git) holds the committed history. git add moves changes from the first to the second; git commit moves them from the second to the third. The staging area lets you build clean, focused commits, even from part of a file with git add -p.

Does Git store snapshots or differences?

Snapshots. Each commit points to a tree that describes the whole project at that moment; unchanged files point to the same stored blob, so nothing is duplicated. Differences are calculated when you run git diff. Internally Git compresses objects into pack files with deltas for disk space, but that is only storage optimisation.

What is a commit hash, and why does it change when you amend a commit?

A SHA hash computed from the commit's content: its tree, parent hash(es), author, date and message. Because the hash depends on all of these, changing anything — even the message — produces a new hash. That makes a commit and its history tamper-evident, and it is why amend and rebase "rewrite history": they create new commits.

What are HEAD, HEAD~1 and HEAD^?

HEAD points to the current commit, usually through the current branch name. HEAD~1 and HEAD^ both mean its first parent, one commit back. HEAD~3 goes three commits back; HEAD^2 selects the second parent of a merge commit.

What is the difference between git add ., git add -A and git add -u?

git add -u stages modifications and deletions of already tracked files only. git add -A also stages new files, across the whole repository. git add . does the same as -A for the current directory and everything below it. Before committing, review with git status and git diff --staged.

I edited a file, ran git add, and now git diff shows nothing. Why?

git diff compares the working folder with the staging area. After git add both are equal, so there is no difference. Use git diff --staged to see what is staged for the next commit, or git diff HEAD to see all changes since the last commit.

How do you write a good commit message?

A subject of about 50 characters in the imperative mood ("Fix null pointer in cart"), a blank line, then a body that explains why the change was made, plus a ticket reference if the team uses one. Keep each commit to one logical change that builds and passes tests.

I added .env to .gitignore but git status still shows it as modified. What is wrong?

The file was committed earlier, so it is tracked, and .gitignore only affects untracked files. Run git rm --cached .env and commit; the file stays on your disk but leaves the repository. Because it is still in old commits, rotate any secret it contained.

How do you undo each of these: unstaged edits, a staged file, the last commit message?

Unstaged edits: git restore <file> (permanent). Staged file: git restore --staged <file> (edits stay). Last commit message or a forgotten file: git commit --amend, only if the commit is not pushed. For a pushed commit use git revert.

What does git commit -am "msg" do, and what does it miss?

It stages every modified and deleted tracked file and commits in one step. It does not include new untracked files. It also skips the chance to review what is staged, so check with git status and git diff first.

What are the Git config levels, and which one wins?

System (all users on the machine), global (~/.gitconfig, your user) and local (.git/config, one repository). The most specific wins: local over global over system. git config --list --show-origin shows the value and the file each setting comes from.

Why does Git not track an empty folder, and how do you keep one?

Git stores file content in trees; a tree needs at least one file to have an entry. To keep an empty directory, put a placeholder file in it, conventionally named .gitkeep.

Practice — Daily Git basics

  1. Set up (easy). Install Git, set user.name, user.email and init.defaultBranch main, and run git config --list --show-origin. Done when you can point to the file each of your three settings comes from.
  2. First repository (easy). Create a folder java-practice, run git init, add a README.md and Hello.java, and make your first commit. Done when git log --oneline shows one commit and git status says the working tree is clean.
  3. Five small commits (easy). Make five small, separate changes to the project (for example a new class, a bug fix, a README line, a rename with git mv, a new test) with a clear imperative message each. Done when git log --oneline --graph reads like a story and every message is under 50 characters.
  4. Watch the states (easy). Create a file, then run git status -s after each step: create, git add, edit again, git commit. Write down the code you saw each time (??, A_, AM). Done when you can predict each code before running the command.
  5. Partial staging (medium). Change two unrelated places in one file. Use git add -p to commit them separately. Done when git log -p -n 2 shows one change per commit.

What a remote is

A remote is a short name (an alias) for the URL of another copy of your repository. It is not a special kind of repository — it is just a bookmark stored in your local config. The remote copy is usually a bare repository on a server: history only, no working folder, because nobody edits files there.

Conventional remote names

origin
The default name for the repository you cloned from, or the one you publish to. git clone creates it automatically. The name has no magic meaning; it is only a convention.
upstream
By convention, the original project when you work from your own fork. Your fork is origin, the project you forked from is upstream (see Fork vs clone).

A repository can have many remotes: for example origin (your fork), upstream (the main project) and staging (a deployment target). Remotes only matter when you run fetch, pull or push; every other command works on local data.

The three things a remote gives you

  • Backup. If your laptop dies, the code is safe on GitHub.
  • Sharing. Teammates clone it, and you exchange commits through it.
  • Integration. Pull requests, code review, issues, and CI/CD pipelines are triggered by pushes to the remote.

Edge cases

  • A remote is not live. Git does not watch it. Nothing leaves or enters your repository until you run push, fetch or pull.
  • A remote can be a local path (../backup.git) or a network share. GitHub is simply the most common choice.
  • GitHub can go down, and an owner can delete a repository. A remote is not your only backup unless you also keep clones.

Interview: "What is the difference between Git and GitHub?"

  • Git is the distributed version control tool; GitHub is a cloud service that hosts Git repositories and adds collaboration features such as pull requests, issues and Actions.
  • GitLab and Bitbucket are alternatives; the Git commands are the same.
  • A remote is a named URL (usually origin) for a hosted copy of your repo.

Creating your GitHub account

Sign up at github.com with a username you can show on a CV, turn on two-factor authentication, and make your commit email match an email verified on your account.

Your GitHub profile is public by default and recruiters look at it. A few decisions at the start save trouble later.

  1. Go to github.com, choose Sign up, and verify your email.
  2. Pick a professional username (for example asha-rao, not cool_killer_99). It appears in every repository URL and is awkward to change later because links break.
  3. Fill in your name, a short bio and a photo. A complete profile looks trustworthy.
  4. Turn on two-factor authentication (2FA) in Settings → Password and authentication. Use an authenticator app or a passkey. GitHub requires 2FA for contributors, and a hijacked account with code access is serious.
  5. Add your Git email (next section) and then set up login from your computer: SSH key or HTTPS with a token.

Email and the noreply address

GitHub attaches a commit to your profile by matching the commit's email with an email on your account. If they do not match, the commit shows a grey avatar and does not count in your contribution graph. Add your email in Settings → Emails and verify it.

Commits are public. To avoid exposing your personal address, turn on Keep my email addresses private and use the private address GitHub shows you, which has the form ID+username@users.noreply.github.com. Set it in Git:

$ git config --global user.email "12345678+asha-rao@users.noreply.github.com"

(Use the exact address from your own settings page; the numbers above are an example.) Also tick Block command line pushes that expose my email if you want GitHub to refuse commits that use your private address by mistake.

Make your profile work as a portfolio

  • Pin your best 4–6 repositories, each with a good README.
  • Create a profile README: a repository with the same name as your username and a README.md in it. GitHub shows that file at the top of your profile. Put a short intro, your tech stack and links.
  • Commit regularly. The green contribution graph is not the goal, but steady, real work shows.
  • Never leave secrets, college assignment dumps or half-broken projects as your pinned work.

Rule: never share your password or token

Do not paste tokens into chats, screenshots, code or commit messages. GitHub scans public repositories for leaked tokens and revokes them, but treat any leaked token as compromised and revoke it yourself in Settings.

Edge cases

  • GitHub stopped accepting account passwords for Git operations over HTTPS in 2021. You need a token, Git Credential Manager (browser login) or an SSH key.
  • Commits made before you added the email to your account are not re-linked automatically, but adding the email afterwards does link them.
  • Students can get extra features through the GitHub Education programme; check the current offer on docs.github.com.

Log in with an SSH key

Create an ed25519 key pair with ssh-keygen, upload the public key to GitHub, and use git@github.com:user/repo.git URLs — no password or token for every push.

SSH uses a pair of keys: a private key that never leaves your computer and a public key that you give to GitHub. When you push, GitHub sends a challenge that only the owner of the private key can answer. Nothing secret travels over the network.

Step 1: check for an existing key

Step 2: generate an ed25519 key

$ ssh-keygen -t ed25519 -C "asha@example.com"
Generating public/private ed25519 key pair.
Enter file in which to save the key (/c/Users/asha/.ssh/id_ed25519):

Enter same passphrase again:
Your identification has been saved in /c/Users/asha/.ssh/id_ed25519

  • -t ed25519 chooses the key type. Ed25519 is modern, short and secure; it is the recommended type for GitHub.
  • -C adds a comment (usually your email) so you can recognise the key later. It has no security meaning.
  • Press Enter to accept the default location. Set a passphrase — it encrypts the private key file, so a stolen laptop does not give away your access.

Step 3: let the ssh-agent remember the passphrase

The ssh-agent is a background program that holds your unlocked key, so you type the passphrase once per session. In Git Bash:

$ eval "$(ssh-agent -s)"
Agent pid 2481
$ ssh-add ~/.ssh/id_ed25519
Enter passphrase for /c/Users/asha/.ssh/id_ed25519:
Identity added: /c/Users/asha/.ssh/id_ed25519 (asha@example.com)

On Windows you can instead use the built-in OpenSSH agent service (start it from an administrator PowerShell with Get-Service ssh-agent | Set-Service -StartupType Manual and Start-Service ssh-agent), then run ssh-add in a normal terminal. Either way is fine.

Step 4: add the public key to GitHub

$ cat ~/.ssh/id_ed25519.pub
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIExampleOnlyNotARealKeyxxxxxxxxxxxxxxxxxxx asha@example.com

Copy the whole line. In GitHub open Settings → SSH and GPG keys → New SSH key, give it a title such as "Asha laptop", choose type Authentication Key and paste the line.

Rule: share only the .pub file

The file ending in .pub is public and safe to share. The file without an extension (id_ed25519) is your private key. Never upload, email or commit it. If it leaks, delete the key from GitHub and generate a new one.

Step 5: test the connection

$ ssh -T git@github.com
The authenticity of host 'github.com (140.82.112.4)' can't be established.
ED25519 key fingerprint is SHA256:...
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
Hi asha-rao! You've successfully authenticated, but GitHub does not provide shell access.

The first time, SSH asks whether to trust GitHub. Compare the fingerprint with the one published in GitHub's documentation (docs.github.com, "GitHub's SSH key fingerprints"), then answer yes. The final line means success — "no shell access" is expected, because GitHub only serves Git. Now use the SSH URL when you clone or add a remote:

$ git clone git@github.com:asha-rao/billing-service.git

If a repository already uses an HTTPS URL, switch it with git remote set-url origin git@github.com:asha-rao/billing-service.git (see Managing remotes).

Create one key per account and describe them in ~/.ssh/config. Then use the host alias in the remote URL (git@github-work:company/repo.git).

Errors you will meet

  • Permission denied (publickey). — GitHub does not know any key your computer offered. Check that you uploaded the .pub file to the right account, that the key is loaded (ssh-add -l), and run ssh -vT git@github.com to see which keys are tried.
  • Could not resolve hostname github.com — no internet or DNS problem.
  • Connection timed out on port 22 — a firewall blocks SSH. GitHub supports SSH on port 443 with host ssh.github.com; set it in ~/.ssh/config.
  • WARNING: UNPROTECTED PRIVATE KEY FILE! — on Linux and macOS the key file must be readable only by you (chmod 600).
  • Host key verification failed — the saved fingerprint does not match; make sure you are on a trusted network before you accept a changed one.

Conventions

  • One key per device, so you can revoke a lost laptop without affecting the others.
  • Use ed25519 with a passphrase. Avoid old DSA keys and short RSA keys.
  • Remove keys from GitHub when you stop using a device.

HTTPS login: tokens and Git Credential Manager

With HTTPS you log in through Git Credential Manager (a browser sign-in) or a personal access token used as the password; prefer a fine-grained token with only the permissions you need.

GitHub no longer accepts your account password for Git over HTTPS. You prove who you are in one of two ways.

Option 1: Git Credential Manager (easiest)

Git Credential Manager (GCM) installs with Git for Windows. When you first clone, push or pull over HTTPS, it opens a browser window where you sign in to GitHub (with your 2FA). It then stores a token in the Windows Credential Manager and reuses it, so you are not asked again.

$ git push -u origin main
# a browser window opens: "Sign in to GitHub" -> Authorize
Enumerating objects: 12, done.
To https://github.com/asha-rao/billing-service.git
 * [new branch]      main -> main

Check the helper with git config --global credential.helper; on Windows it prints manager. If a wrong or old login is stuck, remove it in the Windows search bar under Credential Manager → Windows Credentials → git:https://github.com, and Git will ask again.

Option 2: Personal access token (PAT)

A personal access token is a long random string that acts as a password for one purpose. GitHub offers two kinds:

PointFine-grained tokenClassic token
Scope of accessChosen repositories onlyAll repositories you can access
PermissionsDetailed (for example "Contents: read and write")Broad scopes such as repo

RecommendationPreferredUse only where fine-grained tokens are not supported
  1. In GitHub open Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
  2. Give it a name, a short expiry (for example 30–90 days) and select only the repository it needs.
  3. Under repository permissions give Contents read and write (enough for push and pull).
  4. Copy the token once — GitHub will never show it again.
  5. Use it as the password when Git asks. The username is your GitHub username.
$ git push

The credential helper then stores the token so you paste it only once. Tokens are also what scripts and CI servers use, usually from an encrypted secret and never from the repository.

Mistake: putting the token inside the remote URL

You will see tutorials that use https://TOKEN@github.com/user/repo.git. It saves the token in plain text in .git/config and in your shell history. Use the credential helper instead.

Errors you will meet

  • remote: Invalid username or token. Password authentication is not supported for Git operations. — you typed your account password. Use a token or the browser login.
  • fatal: Authentication failed — expired, revoked or under-privileged token; stale credentials in the credential manager. Remove the stored credential and try again.
  • remote: Permission to user/repo.git denied to other-user — you are logged in as a different account than the repository owner; clear the cached login.
  • remote: Repository not found — often a private repository and a token that cannot see it, or a typo in the URL.

Tip: the GitHub CLI

The optional gh tool (cli.github.com) lets you run gh auth login once, and then create repositories and pull requests from the terminal. It is handy but not needed for this module.

Interview: "HTTPS or SSH for GitHub? How do you authenticate?"

  • Both work. SSH uses a key pair and needs no prompts after setup; HTTPS uses a token or Git Credential Manager.
  • Passwords are not accepted any more; tokens should be fine-grained, short-lived and least-privilege.
  • Never commit keys or tokens; the private key stays on your machine.

The fetch = line says: copy each branch refs/heads/X from the server to refs/remotes/origin/X locally. The [branch "main"] section is the tracking information described below.

Remote-tracking branches: origin/main

When you fetch, Git does not touch your own branches. It stores what it learned about the server in remote-tracking branches named <remote>/<branch>, for example origin/main. Think of origin/main as a bookmark: "the last time I talked to GitHub, its main was here". You cannot commit on it directly; only fetch, pull and push move it.

A key point: origin/main can be out of date. If a teammate pushed an hour ago and you have not fetched, your origin/main still shows the old position.

Publishing: git push -u origin main

$ git push -u origin main
Enumerating objects: 15, done.
Counting objects: 100% (15/15), done.
Writing objects: 100% (15/15), 2.31 KiB | 2.31 MiB/s, done.
To github.com:asha-rao/billing-service.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

The syntax is git push <remote> <branch>. The -u (short for --set-upstream) does two things: pushes, and records that local main tracks origin/main. After that, plain git push, git pull and git status know which remote branch you mean. You need -u only the first time for each branch.

The upstream branch of a local branch is the remote branch it is paired with. Tracking gives you:

  • git push and git pull without arguments;
  • the friendly summary in git status: Your branch is ahead of 'origin/main' by 2 commits.

Useful push options

  • git push — push the current branch to its upstream.
  • git push origin feature/coupon — push a named branch (and add -u the first time).
  • git push --tags — push tags (releases), see Module 4.
  • git push origin --delete feature/coupon — delete a branch on the server.
  • git config --global push.autoSetupRemote true — a convenience setting: the first git push of a new branch automatically sets its upstream, so you can skip -u.

Mistake: git remote add origin when origin already exists

You get error: remote origin already exists. Either change the URL with git remote set-url origin <url> or pick another name. This often happens after git clone, which already created origin.

Errors and edge cases

  • fatal: The current branch feature has no upstream branch. — you never set tracking. Run the command Git prints: git push --set-upstream origin feature.
  • fatal: 'origin' does not appear to be a git repository — no remote called origin; check git remote -v.
  • error: src refspec main does not match any — your local branch is called master or you have no commits yet. Check with git branch.
  • Remote-tracking branches for branches deleted on the server stay in your clone until you run git fetch --prune (or git remote prune origin).
  • You can give push and fetch different URLs (git remote set-url --push); this is rare.

Interview: "What does git push -u origin main do? What is origin/main?"

  • It pushes local main to the remote origin and sets origin/main as its upstream, so later git push/git pull need no arguments.
  • origin/main is a remote-tracking branch: a read-only local bookmark of the server's main as of the last fetch.
  • git branch -vv shows each branch's upstream and ahead/behind counts.

git fetch vs git pull

Fetch downloads new commits from the remote and only updates origin/main — it is always safe; pull is fetch plus a merge (or rebase) into your current branch, which changes your files.

Fetch never alters your working folder, so it cannot lose or conflict with anything. Fetch from all remotes with git fetch --all; add --prune to remove tracking branches deleted on the server.

pull: fetch and integrate

$ git pull
Updating 7d3e4f2..a9b8c7d
Fast-forward
 README.md                 | 2 +-
 src/main/java/Health.java | 9 +++++++++
 2 files changed, 10 insertions(+), 1 deletion(-)

git pull = git fetch + git merge origin/main (into the current branch). Cases:

  • Fast-forward: you have no new local commits, so Git just moves your branch pointer forward. No merge commit.
  • True merge: both sides have new commits, so Git creates a merge commit with two parents. If both changed the same lines, you get a conflict to resolve (Module 3).

Pull with rebase

git pull --rebase = fetch, then replay your local commits on top of the fetched ones. The history stays a straight line, with no extra merge commit for every sync.

Rebase creates new commits (D', E') with new hashes, so it is safe only for commits you have not shared. Details in Module 4. Choose a default once:

$ git config --global pull.rebase false    # merge (plain default behaviour)
$ git config --global pull.rebase true     # rebase
$ git config --global pull.ff only         # refuse to create a merge commit; fail instead

If you set none of these and the histories have diverged, current versions of Git stop and tell you to choose how to reconcile (fatal: Need to specify how to reconcile divergent branches.). That message is your cue to set pull.rebase or to run git pull --rebase or git pull --no-rebase once. Many teams recommend pull.rebase true on feature branches, or pull.ff only as the safest habit (fetch, then merge deliberately). Follow what your team does.

Habits that avoid trouble

  • Before you start work each day: git switch main then git pull.
  • Commit or stash your changes before pulling. Pulling with a dirty working folder can fail or mix changes.
  • When unsure what a pull will do, run git fetch first and look with git log main..origin/main.
  • Pull before you push, every time.

Errors and edge cases

  • error: Your local changes to the following files would be overwritten by merge — commit or stash first.
  • fatal: refusing to merge unrelated histories — the two repositories started separately (a common result of adding a README on GitHub and also running git init locally). If you are sure, add --allow-unrelated-histories.
  • There is no tracking information for the current branch. — set it: git branch --set-upstream-to=origin/main.
  • A merge conflict during pull leaves the repository in a merging state; resolve it or abort with git merge --abort (or git rebase --abort).

Interview: "Difference between git fetch and git pull?"

  • Fetch only downloads and updates remote-tracking branches; it never changes your branch or files, so it is always safe.
  • Pull = fetch + merge into the current branch (or fetch + rebase with --rebase); it can cause conflicts.
  • Good answer adds: fetch then review, set pull.rebase, and fast-forward vs merge commit.

Push rejected: non-fast-forward errors

Git rejects a push when the remote branch has commits you do not have; the fix is to pull (merge or rebase) first and then push — never a blind force push.

You will see this error within your first week:

To github.com:asha-rao/billing-service.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:asha-rao/billing-service.git'
hint: Updates were rejected because the remote contains work that you do
hint: do not have locally. This is usually caused by another repository
hint: pushing to the same ref. You may want to first integrate the remote
hint: changes (e.g., 'git pull ...') before pushing again.

Variants of the same problem say (non-fast-forward) — "the tip of your current branch is behind its remote counterpart".

Why it happens

A push can only fast-forward the remote branch: the new tip must contain the old tip as an ancestor. If a teammate pushed first, the remote has commit X that your history lacks. Accepting your push would drop X from the branch. Git refuses to lose their work.

The right fix

  1. git pull --rebase (or git pull). Git brings in X and puts your Y on top of it (or merges).
  2. Resolve conflicts if there are any, test the build.
  3. git push — now it is a fast-forward and succeeds.
$ git pull --rebase
Successfully rebased and updated refs/heads/main.
$ git log --oneline -3
5e6f7a8 Add coupon validation          <- your commit, now on top
a9b8c7d Add health endpoint            <- teammate's commit
7d3e4f2 Describe the service in README
$ git push
   a9b8c7d..5e6f7a8  main -> main

Do not force push to "make the error go away"

Wrong: overwrites your teammate's commit

$ git push --force
# remote main now has only YOUR history.
# X is gone from GitHub; the teammate's next push breaks.

Right: integrate first

$ git pull --rebase
$ git push

A force push (git push --force or -f) makes the remote branch point exactly where yours does, discarding whatever was there. There are real reasons for it — you amended or rebased your own feature branch that nobody else uses — and then you use the safer form:

$ git push --force-with-lease

--force-with-lease forces only if the remote branch is still where you last saw it (your origin/feature). If someone pushed in the meantime, it refuses. Details and team rules are in Module 4.

Rule: no force pushes to shared branches

Never force push main or any branch others work on. Most teams protect main with branch protection rules on GitHub, which block force pushes and direct pushes entirely (Module 3).

Mistake: pulling after committing in panic with uncommitted work

If your working folder has uncommitted edits to a file that the pull also changes, Git refuses to continue. Commit your work (or git stash) before git pull.

What Git checks, exactly

When you run git push, Git asks the server what commit the remote main points to. It then checks whether that commit is an ancestor of the commit you are sending. If yes, the update only moves the branch pointer forward along a straight line: a fast-forward. If no, the two histories have diverged and the server refuses, because moving the pointer would make the teammate's commit unreachable. The message says fetch first when your Git does not even have that commit yet, and non-fast-forward when it already knows the commit (for example after a git fetch) but it is not in your history.

Diagnose before you fix

Do not guess. Fetch the remote state (this changes nothing in your files) and look at both sides.

$ git fetch
$ git status
On branch main
Your branch and 'origin/main' have diverged,
and have 1 and 1 different commits each, respectively.
  (use "git pull" if you want to integrate the remote branch with yours)
$ git log --oneline --graph --all
* 5e6f7a8 (HEAD -> main) Add coupon validation
| * a9b8c7d (origin/main) Add health endpoint
|/
* 7d3e4f2 Describe the service in README
$ git log --oneline HEAD..origin/main     # commits you are missing
a9b8c7d Add health endpoint

The graph shows the fork at 7d3e4f2. Your commit and the teammate's commit both sit on top of it. To push, one line of history must contain both.

Three ways to integrate

OptionWhat happensResult
git pull --rebaseYour commits are replayed on top of the remote tipStraight history; your commit gets a new hash
git pull (merge)Git creates a merge commit that joins both linesBoth lines stay visible; extra merge commit
git push --forceRemote is overwritten with your historyTeammate's commit is lost from the remote

With --rebase Git temporarily sets your commit aside, moves to the new remote tip, and applies your commit again. The content is the same but it is a new commit (Y becomes Y'), because its parent changed. This is safe here because you had not pushed Y yet. If your change touches the same lines as the teammate's, Git stops with a conflict. You edit the file, run git add, and then git rebase --continue. To give up and return to the state before the pull, run git rebase --abort.

You can make rebase the default with git config --global pull.rebase true, or make pulls refuse anything but a fast-forward with git pull --ff-only. Many teams choose the first for feature branches; follow your team's rule. Merge versus rebase is explained in depth in Module 4.

A legitimate force push: your own rewritten branch

Suppose you pushed feature/coupons, then ran git commit --amend or git rebase main on it. The local commits now have new hashes, so the push is rejected as non-fast-forward. Nobody else uses the branch, so overwriting the remote is correct. Use the lease form.

$ git push --force-with-lease
 + 4c1d2e3...9b8a7f6 feature/coupons -> feature/coupons (forced update)

# if a teammate had pushed to the branch meanwhile:
 ! [rejected]        feature/coupons -> feature/coupons (stale info)

The lease compares the remote tip with your remembered origin/feature/coupons. A mismatch means someone added work you have not seen, and the push is refused. One caution: if a tool such as your IDE runs git fetch in the background, your remembered value updates without you reading the new commits, and the lease then passes. Fetch and look at the log yourself before forcing.

If a wrong force push already happened

The overwritten commits are not deleted at once. Your teammate still has them in their local repository and in git reflog. They can find the lost hash there and push it back with git push origin <hash>:main after the branch protection is lifted, or recreate a branch from it. Tell the team immediately instead of hoping nobody notices.

Wrong: ignore the hint and retry

$ git push
 ! [rejected] main -> main (fetch first)
$ git push origin main
 ! [rejected] main -> main (fetch first)
# same error: spelling it out changes nothing

Right: integrate, then push

$ git pull --rebase
$ ./mvnw test
$ git push

Rule: never rewrite history that others already pulled

Rebase, amend and force push are for commits only you have. Once a teammate has based work on a commit, changing it forces them to repair their branch.

Convention: pull often, push small

Run git pull --rebase before you start work and before you push. Short-lived branches and small pull requests make rejections rare and conflicts small.

Edge cases

  • Pulling with a rebase while you have uncommitted edits can fail with "cannot pull with rebase: You have unstaged changes". Commit or git stash first (and git stash pop afterwards).
  • A rejection on a branch with no remote counterpart yet is not this error; a brand new branch is pushed with git push -u origin <branch>.
  • Rejected pushes can repeat: someone may push again while you resolve a conflict. Pull again, then push quickly.

Interview: "Your push was rejected. What do you do?"

  • Explain the reason: the remote has commits I do not have, and a non-fast-forward push would discard them.
  • Fix: git pull --rebase (or merge), resolve conflicts, run tests, push.
  • Mention that force push is only for your own branches after a rewrite and then --force-with-lease, never on shared branches.

20-second answer: "The remote has a commit I do not have, so my push is not a fast-forward and Git refuses to drop their work. I run git fetch to look, then git pull --rebase, fix conflicts, run the tests and push. I only force push my own rewritten branch, and then with --force-with-lease, never to shared branches like main."

Fork vs clone, and contributing to open source

Clone copies a repository to your computer; fork copies it to your own GitHub account first, so you can propose changes to a project you cannot push to by opening a pull request.

Rule of thumb: if you can push to the repository (your own, or your company's), just clone it and work in branches. If you cannot (someone else's open-source project), fork it first.

The open-source contribution flow

  1. Fork. Click Fork on the project's GitHub page. You now own asha-rao/project.
  2. Clone your fork (not the original): 
    $ git clone git@github.com:asha-rao/project.git
$ cd project
  3. Add the original as upstream. 
    $ git remote add upstream https://github.com/original-owner/project.git
$ git remote -v
origin    git@github.com:asha-rao/project.git (fetch)
origin    git@github.com:asha-rao/project.git (push)
upstream  https://github.com/original-owner/project.git (fetch)
upstream  https://github.com/original-owner/project.git (push)
  4. Read the rules. Open CONTRIBUTING.md and the issue list. Look for issues labelled good first issue. Comment on the issue before you start a large piece of work.
  5. Create a branch for the change: git switch -c fix-readme-typo (branches are covered in Module 3).
  6. Edit, test and commit with a clear message that follows the project's style.
  7. Push to your fork: git push -u origin fix-readme-typo.
  8. Open a pull request. GitHub shows a banner "Compare & pull request". Write what you changed and why, and link the issue (Fixes #123).
  9. Respond to review. Push more commits to the same branch; the pull request updates by itself. Be polite and patient.

Keep your fork up to date

The original project keeps moving, but your fork does not follow automatically. Sync it before starting new work.

$ git switch main
$ git fetch upstream
$ git merge upstream/main          # or: git rebase upstream/main
$ git push origin main

Or use the web way: on your fork's page click Sync fork → Update branch, then git pull locally. Keep your fork's main identical to upstream and do your own work on branches, so the sync never conflicts.

Tip: fast-forward only

Use git merge --ff-only upstream/main for the sync. It fails if your main has stray commits, which is a useful warning that you committed on the wrong branch.

Your first open-source contribution

Start with documentation: fix a typo, clarify an unclear paragraph, correct a broken link. These changes are small, easy to review and welcome, and they teach you the whole fork-to-pull-request flow without risk. Search GitHub for the label good first issue or documentation. Then move to tests, small bug fixes and finally features.

Conventions

  • Never commit directly on your fork's main; work on a branch per change.
  • One pull request = one change. Keep it small.
  • Follow the project's code style, commit message rules, and licence/CLA requirements.
  • Naming: origin = your fork, upstream = the original.

Edge cases

  • If you have write access to a repository (a teammate in your company), you do not need a fork; branches in the same repository are simpler. Some companies still use forks for strict permission control.
  • Private repositories can be forked only if the owner's settings and plan allow it.
  • Forking a repository you already forked does not create a second copy; GitHub takes you to your existing fork.
  • Deleting the fork does not harm the original. Deleting the original does not delete forks of public repositories.
  • Pull request commits stay in the pull request even if you later delete the branch locally.

Interview: "Fork vs clone? How do you contribute to open source?"

  • Clone = Git copy to your machine. Fork = GitHub copy under your account, needed when you cannot push to the original.
  • Flow: fork, clone your fork, add upstream, branch, commit, push to your fork, open a pull request.
  • Keep in sync with git fetch upstream and merge or rebase, or GitHub's Sync fork button.

Interview questions — GitHub and remotes

What is the difference between Git and GitHub?

Git is the open-source distributed version control tool that runs locally. GitHub is a hosting service for Git repositories that adds pull requests, issues, code review, Actions and more. GitLab and Bitbucket are similar services; the Git commands are the same on all of them.

What is a remote? What are origin and upstream?

A remote is a named URL pointing to another copy of the repository. origin is the conventional name of the repository you cloned from or push to. upstream is the conventional name for the original project when origin is your fork. Both names are only conventions.

HTTPS or SSH for GitHub — how do you choose, and how do you set up SSH?

Both are secure. HTTPS is easiest (browser login via Git Credential Manager or a token); SSH needs no prompts after setup. For SSH: ssh-keygen -t ed25519 -C "email", add the public key (.pub) in GitHub Settings, test with ssh -T git@github.com, and use git@github.com:user/repo.git URLs. The private key never leaves your machine.

Can you push to GitHub with your account password?

No. GitHub does not accept account passwords for Git operations. Use an SSH key, Git Credential Manager (browser sign-in), or a personal access token. Prefer fine-grained tokens with limited repository access and an expiry date.

What does git push -u origin main do?

It pushes local main to the remote origin and sets origin/main as the upstream (tracking) branch of main. After that, git push and git pull work without arguments and git status shows ahead/behind counts.

What is origin/main, and how is it different from main?

main is your own branch, which you move by committing. origin/main is a remote-tracking branch: a read-only bookmark for where main was on the server at your last fetch or push. It can be stale until you fetch.

What is the difference between git fetch and git pull?

Fetch downloads new commits and updates remote-tracking branches such as origin/main; it never changes your branch or working files, so it is always safe. Pull is fetch followed by a merge (or a rebase with --rebase) into your current branch, so it can create a merge commit or conflicts.

Your git push is rejected with "fetch first" or "non-fast-forward". Why, and what do you do?

The remote branch has commits that you do not have; pushing would overwrite them. Run git pull --rebase (or git pull), fix any conflicts, run the tests, and push again. Do not force push to get past the error.

When is a force push acceptable, and what is --force-with-lease?

Only on a branch that nobody else uses, after you rewrote history with amend or rebase. --force-with-lease forces the push only if the remote branch is still where you last saw it, so you do not overwrite a teammate's new commits. Never force push shared branches such as main.

What is the difference between a fork and a clone?

A clone is a Git copy on your computer. A fork is a GitHub copy under your own account, linked to the original so you can open pull requests. If you can push to the repository, clone it. If not (open source), fork it, clone your fork, and add the original as upstream.

Walk through contributing to an open-source project.

Fork, clone your fork, add upstream, read CONTRIBUTING.md, create a branch, make a small change, commit with a clear message, push to your fork (origin), then open a pull request that links the issue. Respond to review by pushing more commits to the same branch.

How do you keep a fork in sync with the original project?

Add the original as upstream, then git fetch upstream, merge or rebase upstream/main into your local main, and push to origin. Alternatively click Sync fork on GitHub and pull. Keep your own work on branches so the sync is a clean fast-forward.

You created a GitHub repo with a README and now cannot push your local project. What happened?

The two repositories have unrelated histories: GitHub already holds a first commit that your local repository does not have. Pull with --allow-unrelated-histories once, then push; or create the GitHub repository empty next time.

What belongs in a good README?

A one-line description, a screenshot or sample output, the tech stack, features, how to run it with exact commands, configuration or environment variables (without real secrets), API documentation, how to run tests, a live link, and the licence.

What a branch really is: a pointer, plus HEAD

A branch is a small movable label that points to one commit; HEAD points to the branch you are on, and every new commit moves that branch forward.

Every commit stores a snapshot of your project and the id of its parent commit (the commit it was built on). Follow the parent ids backwards and you get the history: a chain of commits. A branch is not a copy of that chain. It is only a name that points to one commit — normally the newest commit of one line of work.

This one idea explains almost everything else in this module: why creating a branch is instant, why deleting a branch does not delete commits, and why git commit "moves" a branch.

A branch is a file that holds one commit id

Look inside the hidden .git folder of any repository:

$ cat .git/refs/heads/main
9d4e7f0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e
$ cat .git/HEAD
ref: refs/heads/main

The file name is the branch name. The content is a commit id — a 40-character hash in a normal repository. That is all a branch is. A name with a slash, such as feature/login, is simply a file login inside a folder feature. (Git may later pack many of these small files into one file, .git/packed-refs; the idea does not change.)

Git never copies your project to make a branch. It writes one tiny file, so you can create a branch in a few milliseconds and throw it away just as fast. That is why Git users make branches freely — one per task.

HEAD: where you are now

HEAD is the second pointer. It tells Git where you are. Normally it does not point at a commit directly. It points at a branch name (ref: refs/heads/main above), and that branch points at a commit. Two consequences follow:

  • The commit that HEAD resolves to is the parent of your next commit.
  • The branch that HEAD points to is the branch that moves forward when you commit.

How commits move a branch

When you run git commit, Git does three things:

  1. It creates a new commit whose parent is the commit HEAD currently resolves to.
  2. It moves the current branch (the one HEAD points to) to the new commit.
  3. HEAD itself does not change — it still points to the branch name. Every other branch stays exactly where it was.

You can see the labels with git log --decorate. The words in brackets are the pointers:

$ git switch -c feature/login
Switched to a new branch 'feature/login'
$ git log --oneline --decorate -3
3f2a1bc (HEAD -> feature/login, origin/main, origin/HEAD, main) Add order summary page
8c1d2e4 Add order entity
1a2b3c4 Initial commit

$ git commit -am "Add login endpoint"
[feature/login 9d4e7f0] Add login endpoint
 1 file changed, 24 insertions(+)
$ git log --oneline --decorate -2
9d4e7f0 (HEAD -> feature/login) Add login endpoint
3f2a1bc (origin/main, origin/HEAD, main) Add order summary page

HEAD -> feature/login means "HEAD points to the branch feature/login". origin/main is a remote-tracking branch: your own bookmark of where main was on GitHub the last time you fetched (see Module 2). Notice that main did not move when you committed on feature/login.

Two lines of work

Now suppose a teammate adds commit M3 to main while you add F1 and F2 on your branch. The two branches have diverged: both have commits the other does not. Joining them again is what merge does (next articles).

What switching branches does to your folder

git switch main does two things: it moves HEAD to main, and it rewrites the tracked files in your working folder so they match the commit main points to. Files that Git does not track (untracked or ignored) are left alone.

What about changes you have not committed? Git carries them to the other branch if that is safe — that is, if the files you changed are identical in both commits. If the switch would overwrite your edits, Git stops and protects them:

$ git switch other
error: Your local changes to the following files would be overwritten by checkout:
	App.java
Please commit your changes or stash them before you switch branches.
Aborting

Your options are to commit the work, to park it with git stash (Module 4), or to discard it with git restore.

  • In a brand-new repository HEAD points to main, but the branch does not exist until the first commit (an unborn branch). git branch prints nothing until then.
  • Deleting a branch deletes only the label. The commits stay in the repository until garbage collection removes the ones nothing points to (see the reflog).

Wrong: start coding without looking

Tip: always see your branch

Interview: "What is a branch in Git? What is HEAD?"

  • A branch is a lightweight, movable pointer to a commit. It is stored as a tiny file containing a commit id, so creating one is instant and costs almost nothing.
  • When you commit, Git creates a commit whose parent is the current commit and moves the current branch to it.
  • HEAD is a pointer to "where you are". Normally it points to a branch, which points to a commit. It can also point directly at a commit — a detached HEAD (next article).
  • Deleting a branch removes the label, not the commits; unreferenced commits are cleaned up later by garbage collection.
  • Mention that a branch is not a copy of files and not a folder — that is the misconception interviewers look for.

Detached HEAD: what it is and how to get out safely

HEAD is "detached" when it points straight at a commit instead of a branch; commits you make there belong to no branch and can be lost unless you create a branch for them.

Normally HEAD points to a branch, and the branch points to a commit. In a detached HEAD state, HEAD skips the branch and points directly at one commit. Git has no label that moves when you commit, so a new commit has nothing keeping it alive.

It is not an error

"Detached HEAD" sounds scary, but it is a normal and useful state. It is how you look at old code, test an old release or let a tool such as git bisect visit old commits. It only becomes a problem if you commit there and then walk away.

Why it can lose work

Suppose you make a commit while detached:

$ git commit -am "Try a different discount rule"
[detached HEAD 5a6b7c8] Try a different discount rule
 1 file changed, 3 insertions(+), 1 deletion(-)

The new commit 5a6b7c8 has 3f2a1bc as its parent, but no branch points to it. The moment you switch away, nothing in the branch list leads to that commit any more. Git warns you:

$ git switch main
Warning: you are leaving 1 commit behind, not connected to
any of your branches:

  5a6b7c8 Try a different discount rule

If you want to keep it by creating a new branch, this may be a good time
to do so with:

Switched to branch 'main'

The commit is not deleted at once — it stays in the reflog for at least 30 days by default — but you will lose track of it, and garbage collection will remove it eventually. Read that warning; it contains the commit id you need.

The rescue in full:

$ git switch -c experiment/discount-rule

Now HEAD points to a branch again, and the commit is safe. Merge the branch into main (next article) or delete it when you are done.

Rule: before you commit, make sure HEAD is attached

If git status says HEAD detached at … and you want to keep your work, create a branch before you commit, or at least before you switch away: git switch -c new-branch-name.

Edge cases

  • During a rebase, HEAD is detached on purpose while Git replays your commits one by one. When the rebase finishes, Git attaches HEAD to your branch again. Do not "fix" it.
  • git checkout origin/main detaches HEAD. If you want to work on main, use git switch main (the local branch).
  • git switch v1.2.0 without --detach fails: fatal: a branch is expected, got tag 'v1.2.0'. The same happens for a commit id (got commit '…') and for origin/main (got remote branch 'origin/main'). The error includes a hint to use --detach.
  • On CI servers HEAD is usually detached, so git branch --show-current prints an empty line. Scripts that need the branch name read it from the CI environment variables instead.
  • A submodule is normally checked out in detached HEAD at the commit the parent repository records.

Mistake: checking out a tag or a remote branch and starting to work

Wrong: commits end up on no branch

$ git checkout v1.2.0
$ # ...edit files...
$ git commit -am "Fix rounding bug"
$ git switch main    # the fix is now "left behind"

Right: start a branch from the tag first

$ git switch -c hotfix/1.2.1 v1.2.0
$ # ...edit files...
$ git commit -am "Fix rounding bug"
$ git push -u origin hotfix/1.2.1

Tip: lost a commit? Think reflog

If you left a detached HEAD without keeping the id, run git reflog. Every place HEAD has been is listed there, including your detached commits. Find the line with your commit message and run git branch rescue-branch <id>.

Interview: "What is a detached HEAD, and how do you recover from it?"

  • Normally HEAD points to a branch. In a detached HEAD it points directly at a commit — after checking out a commit id, a tag or a remote-tracking branch.
  • Looking around is safe. Commits made there are not on any branch, so switching away leaves them unreachable and they will eventually be garbage-collected.
  • Recovery: git switch -c new-branch while still detached; or git branch new-branch <id> afterwards, finding the id in Git's warning or in git reflog.
  • To leave without keeping anything: git switch main or git switch -.
  • Add that rebase and bisect detach HEAD temporarily by design.

checkout vs switch and restore

Older tutorials use git checkout for everything. It does too many unrelated jobs: switching branches, creating branches, detaching HEAD and throwing away file changes. One short command could therefore destroy work by accident — git checkout -- . discards every edit in the folder without asking. Git 2.23 (2019) split the job in two clearer commands: git switch for branches and git restore for files. git checkout still works, and you will see it everywhere, so know both.

GoalOld wayNew way
Switch to a branchgit checkout maingit switch main
Create and switchgit checkout -b feature/xgit switch -c feature/x
Detach HEAD at a commitgit checkout 3f2a1bcgit switch --detach 3f2a1bc
Discard edits in a filegit checkout -- App.javagit restore App.java
Unstage a filegit reset HEAD App.javagit restore --staged App.java
Get a file from another commitgit checkout 3f2a1bc -- App.javagit restore --source=3f2a1bc App.java

git switch only changes branches, and it refuses to move to a commit id or tag unless you add --detach. git restore only touches files and never moves HEAD. If a file and a branch have the same name, git checkout name has to guess; the new commands never have to.

Mistake: git restore and git branch -D cannot be undone casually

git restore App.java throws away your uncommitted edits in that file for good — they were never saved in Git, so there is nothing to recover. Run git diff App.java first if you are not sure. Likewise, check git branch --no-merged main before using -D.

Conventions

  • One branch per task, created from an up-to-date main: git switch main, git pull, git switch -c feature/….
  • Delete a branch as soon as its pull request is merged. Stale branches make the list useless.
  • Use -d by default and -D only after you have checked.
  • Push with git push -u origin branch-name the first time, so later git pull and git push need no arguments.
  • Set the default name for new repositories once: git config --global init.defaultBranch main.

Interview: "git branch -d vs -D?", "How do you delete a remote branch?", "checkout vs switch?"

  • -d deletes only if the branch is fully merged; -D forces it and can lose unmerged commits.
  • Remote branch: git push origin --delete branch; then git fetch --prune to clear stale remote-tracking branches.
  • git switch changes branches; git restore changes files. git checkout did both (and more), which made it error-prone. They arrived in Git 2.23.
  • Create and switch in one step with git switch -c; git switch - returns to the previous branch.

Branch naming conventions

Name a branch with a type prefix, an optional ticket id and a short lowercase description — feature/CRM-142-login-endpoint — so anyone can tell what it is for without opening it.

Git lets you call a branch almost anything. Teams do not, because a branch name is read many more times than it is typed: in the branch list, in the pull-request title bar, in CI logs and in Jira. A good name answers three questions at a glance: what kind of work is it, which ticket is it, and what does it do?

The common pattern

Most teams use <type>/<ticket>-<short-description>:

feature/CRM-142-login-endpoint

What Git itself allows

Git's own rules (they come from git check-ref-format) are looser than team rules, but you must know the hard limits. A branch name cannot:

  • contain spaces, ~, ^, :, ?, *, [, a backslash, .. or @{;
  • start with - (Git would read it as an option) or end with /, . or .lock;
  • contain two slashes in a row, or a part that starts with a dot;
  • be called HEAD or just @.

You can test a name before you use it: git check-ref-format --branch "feature/my branch" fails because of the space.

Exception: a branch and a "folder" of branches cannot share a name

Because feature/login is stored as a file inside a folder called feature, you cannot have a branch named feature and another named feature/login at the same time. Git stops you:

$ git switch -c feature/login
fatal: cannot lock ref 'refs/heads/feature/login': 'refs/heads/feature' exists;
cannot create 'refs/heads/feature/login'

The fix is to rename or delete the plain feature branch. This is one more reason to always use a type prefix and never a bare word like feature or bugfix as a branch name.

Conventions

  • Agree on the prefixes once, write them in CONTRIBUTING.md or the team wiki, and use only those.
  • Keep the prefix list in line with your commit types (feature ↔ feat, bugfix ↔ fix); see Conventional Commits.
  • Never reuse the name of a merged branch for new work. Create a new one from a fresh main.
  • Bots create their own branches (for example dependabot/maven/…); do not fight them.
  • In GitHub Actions you can filter by pattern: on: push: branches: ['feature/**'] runs a workflow only for feature branches.

Mistake: names that differ only in case, or that only mean something to you

Feature/Login and feature/login are two different branches in Git, but on Windows and macOS they can collide in the local file system and confuse every tool. And a name such as my-work forces each reviewer to open the branch to learn what it is. Use lowercase and be specific.

Interview: "How do you name your branches?"

  • A type prefix (feature/, bugfix/, hotfix/, release/), the ticket id, then a short lowercase, hyphen-separated description: feature/CRM-142-login-endpoint.
  • Reasons: readable branch lists, filters in CI, automatic linking to Jira or GitHub Issues, and an obvious branch purpose for reviewers.
  • Mention the technical limits: no spaces, no ~ ^ : ? * [, and a branch named feature blocks feature/login.
  • Say the team's convention matters more than which convention: consistency is the point.

Merging: fast-forward, three-way merge and merge commits

git merge brings the commits of another branch into the branch you are on — by just moving the pointer forward (fast-forward) when history is a straight line, or by creating a new merge commit with two parents when both branches have moved on.

Branches let you work apart. A merge is how the work comes back together. You stand on the branch that should receive the changes and name the branch to bring in:

git switch main              # the branch that receives the work
git merge feature/login      # the branch that is brought in

Direction matters: the branch you are on changes; the branch you name does not. What Git does next depends on how the two branches look.

Fast-forward merge

If main has no new commits since you created your branch, the history is a straight line: everything on main is already part of your branch. Git has nothing to combine. It simply moves the main label forward to the tip of your branch. This is a fast-forward, and it creates no new commit.

$ git switch main
Switched to branch 'main'
$ git merge feature/login
Updating 3f2a1bc..9d4e7f0
Fast-forward
 AuthController.java | 24 ++++++++++++++++++++++++
 1 file changed, 24 insertions(+)
 create mode 100644 AuthController.java

The line Updating 3f2a1bc..9d4e7f0 shows the label moving from the old commit to the new one, and Fast-forward confirms nothing else was needed.

Three-way merge and the merge commit

Now suppose a teammate added commit M3 to main while you worked on feature/login. The branches have diverged, so moving a label is not enough: Git must combine the two lines. It builds a new commit that has two parents — a merge commit.

The method is called a three-way merge because Git compares three snapshots:

  1. Git finds the merge base — the newest commit both branches share (M2 here). You can see it with git merge-base main feature/login.
  2. It compares the merge base with the tip of your branch ("ours") and with the tip of the other branch ("theirs").
  3. For every part of every file: if only one side changed it, Git takes that change. If both sides made the same change, Git takes it once. If both changed the same lines in different ways, Git stops with a conflict.
  4. Git saves the combined result as a new commit whose first parent is your branch's tip and whose second parent is the tip you merged.
$ git merge feature/search
Merge made by the 'ort' strategy.
 Search.java | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 Search.java
$ git log --oneline --graph
*   0448514 Merge branch 'feature/search'
|\
| * 94b84dd Add search
* | 39d975f Add pay
|/
* 1eb5322 Add login endpoint
$ git log -1 --format=%p
39d975f 94b84dd

The graph shows the two lines meeting. %p prints the parent ids: the first is where main was, the second is the branch that was merged. (ort is the name of Git's default merge strategy since Git 2.34; older versions print recursive. You never need to choose one.) An editor opens for the merge message; the default, Merge branch 'feature/search', is fine. On GitHub the default is Merge pull request #12 from acme/feature/search.

--ff-only is the safe way to bring in someone else's work when you do not expect your own commits to be mixed in. If a fast-forward is not possible, Git refuses instead of creating a surprise merge commit:

$ git merge --ff-only feature/search

git pull --ff-only does the same for pulling. Many people set it as the default with git config --global pull.ff only.

--squash stages the combined changes but stops before committing, and it records no link to the merged branch:

$ git merge --squash feature/search

$ git commit -m "feat: add product search"

Because Git never saw a real merge, git branch -d feature/search will say the branch is not merged. GitHub's "Squash and merge" button works the same way (merge options).

Merging main into your branch

You can also merge in the other direction to keep your feature branch up to date. This brings the latest main into your branch; main itself does not change:

git switch feature/login
git merge main                # or: git merge origin/main after a git fetch

The default message is Merge branch 'main' into feature/login (Git adds "into …" for any branch other than main). It works, but too many of these commits make a branch noisy; Module 4 shows the alternative, rebase. GitHub's Update branch button on a pull request does this same merge.

Rule: merge from the receiving branch, with a clean working folder

  • Switch to the branch that should receive the changes first, then run git merge <other>.
  • Commit or stash your own edits before merging. With uncommitted changes in the way, Git may refuse: error: Your local changes to the following files would be overwritten by merge.
  • Update the receiving branch (git pull) before you merge into it.
  • Run the build and tests after every merge — even a merge without conflicts.

Edge cases

  • Already up to date. — the other branch is already part of your branch; nothing happens. You see this if you run git merge while standing on the wrong branch.
  • fatal: refusing to merge unrelated histories — the two branches share no common commit. It happens when you git init locally and also create the repository on GitHub with a README, then pull. Only if you are sure, add --allow-unrelated-histories.
  • A merge without any Git conflict can still break the code (a semantic conflict): one person renames getTotal(), another adds a new call to getTotal() in a different file. Git sees no clash, but the build fails. Only compiling and testing finds this.
  • If you save an empty message in the merge message editor, Git does not create the merge commit. The merge stays unfinished until you run git commit again or git merge --abort.
  • To test a merge without committing, use git merge --no-commit --no-ff x, look around, then run git merge --abort.

Mistake: merging into a stale local main

Wrong: local main is behind origin/main

$ git switch main
$ git merge feature/login
$ git push
 ! [rejected]  main -> main (fetch first)

Right: update first, then merge, then push

$ git switch main
$ git pull --ff-only
$ git merge --no-ff feature/login
$ git push

Tip: preview before you merge

git log main..feature/login --oneline lists the commits you are about to bring in, and git diff main...feature/login --stat shows which files they touch. git log --merges lists only merge commits; git log --no-merges hides them.

Real projects: GitHub does the merging

On a team, main is usually protected, so you do not run git merge feature/x on main yourself. You press the merge button on a pull request and GitHub performs the merge on its server. You still use git merge main on your own branch to catch up, and git pull is really git fetch followed by git merge.

Interview: "Fast-forward vs three-way merge? What is a merge commit?"

  • Fast-forward: the target branch has no new commits, so Git just moves its pointer to the other branch's tip. No new commit; history stays linear.
  • Three-way merge: both branches have new commits. Git compares the merge base, ours and theirs, combines the changes and creates a merge commit with two parents.
  • --no-ff forces a merge commit to keep the feature visible in history and easy to revert as a unit; --ff-only refuses anything that is not a fast-forward.
  • The merge base is the nearest common ancestor; if both sides edit the same lines differently, you get a conflict.
  • Add that git pull = fetch + merge, and that squash merges do not record a merge relationship.

Merge conflicts: why they happen and how to resolve one by hand

A conflict happens when two branches changed the same lines (or one deleted what the other edited); Git marks the clash inside the file, you choose the final text, then git add the file and commit.

Git merges line by line. When two branches changed different parts of a file, Git combines them without asking. When both changed the same lines in different ways, Git cannot know which version is right — a human has to decide. That stop is a merge conflict. It is not an error and nothing is broken; Git is asking for help.

When conflicts happen

SituationHow Git reports it
Both branches edited the same lines of a fileboth modified
One branch edited a file, the other deleted itdeleted by us / deleted by them
Both branches created a file with the same path but different contentboth added
A binary file (image, JAR) changed on both sidesboth modified — Git cannot merge bytes, you pick one version

Different lines in the same file are not a conflict. Two people editing the top and the bottom of PriceCalculator.java merge cleanly.

A conflict, step by step

Start with this method on main:

public class PriceCalculator {
    public static final int GST_PERCENT = 18;

    public long total(long amount) {
        return amount + amount * GST_PERCENT / 100;
    }
}

Ravi changes the same return line on main to round the result. Asha, on feature/discount, adds a discount and rewrites the same line. She also adds a DISCOUNT_PERCENT constant near the top — a change in a different place. Both changes are now committed. Someone merges the feature branch into main (locally here, to keep the example simple):

$ git switch main

$ git merge feature/discount

CONFLICT (content): Merge conflict in src/main/java/com/acme/crm/PriceCalculator.java
Automatic merge failed; fix conflicts and then commit the result.

Read the three lines: Git merged what it could (Auto-merging), found a clash (CONFLICT (content)) and stopped halfway (Automatic merge failed). The merge is now in progress. git status tells you what to do:

  (use "git merge --abort" to abort the merge)

	both modified:   src/main/java/com/acme/crm/PriceCalculator.java

        return Math.round(discounted * (1 + GST_PERCENT / 100.0));
    }
}

  1. Find the files. git status lists them under Unmerged paths.
  2. Edit each file. Decide the final code and delete all three marker lines (<<<<<<<, =======, >>>>>>>).

  4. Mark it resolved. git add src/main/java/com/acme/crm/PriceCalculator.java. For a conflict, git add means "I have resolved this file".
  5. Check. git status now says All conflicts fixed but you are still merging.
  6. Finish the merge. git commit — Git has already prepared the message Merge branch 'feature/discount'. Save and close the editor, or run git commit --no-edit.
  7. Verify and share. git log --oneline --graph, then git push.

During a conflict, git diff shows a combined diff with two columns of + and - signs — one column compares the file with your side, the other with the incoming side. For a small Config.txt in which both branches changed the line price = 100, it looks like this:

$ git diff
diff --cc Config.txt
index 62b723e,66f6ddf..0000000
--- a/Config.txt

@@@ -1,3 -1,3 +1,7 @@@

The first column compares the working file with your side, the second with the incoming side. A + in a column means "this line is new compared with that side". So +price = 120 (plus in the second column) exists on your side only, + price = 90 (plus in the first column) exists on the incoming side only, and ++ means the line is new compared with both — here, the markers themselves. Once you resolve the file, the diff for it becomes empty.

A one-file shortcut: if you decide the entire file from one side is right, git restore --theirs file followed by git add file resolves it at once. Use it for binary files and for files you know you want completely from one side. For code, read both sides first.

Git can show you the original code too, which often makes a conflict easier to understand. Set git config --global merge.conflictStyle zdiff3 (Git 2.35 and later; diff3 on older versions). Each conflict then gets a third section, starting with |||||||, with the version from the common ancestor.

Changing your mind: git merge --abort

If the conflict is bigger than you expected, or you merged the wrong branch, stop:

$ git merge --abort
$ git status -sb
## main

The command is silent. Your working folder and your branch are back exactly as they were before git merge. It works best when you started the merge with a clean working folder; with uncommitted changes, Git may not be able to restore them. That is one more reason to commit or stash before you merge.

Delete conflicts and binary files

When one branch edits a file that the other deleted, git status shows deleted by us or deleted by them. Decide which is right:

git status                      # deleted by them: LegacyReport.java
git add LegacyReport.java       # keep the file (with the edits)
# or
git rm LegacyReport.java        # accept the deletion

For a binary file such as a logo or a JAR, you cannot merge the bytes. Pick a side with git restore --ours logo.png or --theirs, then git add logo.png.

Rules for resolving

  • Remove all three markers from every conflicted file. Search for <<<<<<< before you commit: git grep -n "<<<<<<<".
  • A conflicted file stays "unmerged" until you run git add on it; the merge cannot finish before that.
  • Build and run the tests before committing the merge.
  • Resolve conflicts on the branch that receives the merge result. If you are updating your feature branch from main, resolve on the feature branch, never on main.
  • If you do not understand the other side's change, ask the person who wrote it. Do not guess.

Edge cases

  • Whole-file conflicts usually mean line endings or formatting changed (CRLF vs LF, or a tool re-indented the file). Fix the cause (a shared formatter, .gitattributes) instead of resolving hundreds of lines by hand.
  • In a git pull, "ours" is your local branch and "theirs" is the remote's. In a rebase it is the other way round — see rebase workflow.
  • git merge -X theirs resolves only the clashing lines automatically in favour of the other branch. It is quick but silent; it can throw away your work without telling you. Avoid it unless you understand the result.
  • A conflict can appear in a file you never touched, if a teammate's merged branch changed the same lines you changed. Always read the whole conflict.
  • Already committed a wrong resolution and not pushed? git reset --hard ORIG_HEAD undoes the merge (see reset). If you pushed, use revert.

Mistake: committing with the markers still in the file

The file still contains <<<<<<< and =======. Java will not compile (javac reports errors such as illegal start of expression), and a broken application.properties may fail only at startup. Another common mistake is choosing "accept mine" for every conflict, which silently deletes a teammate's work.

Wrong: markers left behind

        return Math.round(amount * 1.18);
=======

>>>>>>> feature/discount

Right: one final version, no markers

        return Math.round(amount * 1.18);

Interview: "What is a merge conflict and how do you resolve it?"

  • A conflict occurs when two branches change the same lines (or one deletes a file the other edits) and Git cannot choose automatically.
  • Git stops the merge, marks the file with <<<<<<<, ======= and >>>>>>>, and lists it as unmerged in git status.
  • Resolve: edit the file to the correct final code and remove the markers, build and test, git add the file, then git commit. Use git merge --abort to cancel.
  • Explain ours (the branch you are on) vs theirs (the branch being merged).
  • Finish with prevention: small PRs, merge or rebase from main often, a shared formatter, and talking to teammates about shared files.

How to avoid conflicts

You cannot avoid all conflicts, but good habits make most of them disappear:

  1. Keep branches small and short-lived. A branch that lives for two days sees few changes on main. A branch that lives for three weeks sees many.
  2. Update from main often. Merge or rebase origin/main into your branch at least once a day, so you solve small conflicts early instead of one huge one at the end.
  3. Make small pull requests. A pull request that touches ten lines can conflict in at most ten lines.
  4. Do not reformat unrelated code in a feature branch. A formatting change touches every line and conflicts with everyone. Do formatting in its own pull request.
  5. Use one shared formatter that runs the same way for everyone and in CI: Spotless or google-java-format for Java, Prettier for JavaScript and TypeScript, and an .editorconfig file for indentation. Add a .gitattributes file (* text=auto) so Windows and Linux machines agree on line endings (Module 4).
  6. Split big classes. Small classes with one job are rarely edited by two people at once.
  7. Talk. "I am refactoring OrderService today" saves hours.
  8. Do not hand-edit generated files (for example OpenAPI clients). Regenerate them after merging.

Conflict hot spots in Java and full-stack projects

  • pom.xml or build.gradle: two people add a dependency at the end of the same list. Usually you keep both entries.
  • application.properties / application.yml: both add settings in the same place. Keep both; check for duplicate keys.
  • package-lock.json: do not merge it by hand. Accept one side (or merge package.json first), then run npm install to regenerate the lock file.
  • Database migrations: two developers both create V12__add_orders.sql. Git sees two different files, so there is no Git conflict — but Flyway fails at startup with an error about more than one migration with the same version. Rename one to the next free number before merging.

Semantic conflicts: green merge, red build

Sometimes there is no Git conflict, yet the merged code is broken: one branch renames a method, the other adds a call to the old name. This is why you build and test after every merge, and why GitHub Actions workflows triggered by pull_request test the result of merging your branch into the base branch, not just your branch alone.

Tip: git rerere

If you resolve the same conflict repeatedly (long-running branches, repeated rebases), turn on rerere ("reuse recorded resolution") with git config --global rerere.enabled true. Git then remembers how you resolved a conflict and applies the same fix automatically next time.

Conventions

  • Resolve conflicts on your feature branch before the pull request is merged — never leave them to the reviewer.
  • After resolving, push and let CI run again; a resolution is new code and needs the same checks.
  • Mention in the merge commit or PR comment when you resolved something non-obvious.
  • Agree as a team on one formatter and one line-ending policy, and enforce both in CI.

Interview: "How do you avoid merge conflicts?"

  • Short-lived branches, small pull requests and frequent updates from main.
  • A shared formatter and consistent line endings, so formatting never causes conflicts.
  • Communication about files that several people touch, and splitting large classes.
  • When one happens: read both sides, resolve in the feature branch, compile, run tests, then push.
  • Mention semantic conflicts: even a clean merge needs a build and tests.

Pull requests: open, review and merge

A pull request (PR) is a GitHub page where you ask to merge one branch into another, so teammates can read the change, discuss it and run automated checks before it reaches main.

You have a branch with commits. You want them in main. You could merge it yourself, but on a team nobody wants unreviewed code in main. A pull request is the polite, tracked way: you propose the change, others review it, and when it is approved and the tests pass, it is merged.

Pull requests are a GitHub feature, not a Git feature

Git itself only has branches and merges. Pull requests belong to the hosting service. GitLab calls the same thing a merge request; Bitbucket and Azure DevOps also call them pull requests. The commands you run (git push, git merge) are Git; the page with reviews, comments and the merge button is GitHub.

Why teams use them

  • Review: a second pair of eyes finds bugs, design problems and security holes before production does.
  • Automated checks: CI builds the code and runs the tests on every pull request (DevOps · Module 4).
  • Knowledge sharing: reviewers learn the code; authors learn the team's standards.
  • History and discussion: the PR page keeps the "why" — questions, decisions, links to the issue — long after the branch is deleted.
  • Protection for main: with branch protection, changes can only enter through a reviewed, passing PR (Module 4).

Opening a pull request

  1. Push your branch: git push -u origin feature/12-login-endpoint. GitHub prints a link in the terminal and shows a yellow Compare & pull request banner on the repository page.
  2. Click the banner (or Pull requests → New pull request). Check the two branch selectors: base is where the change should go (usually main), compare is your branch.
  3. Write a clear title and a description (next article shows how). Add Closes #12 to link the issue.
  4. On the right, pick reviewers, labels and, if your team uses them, assignees, a milestone and a project.
  5. Click Create pull request — or the arrow next to it for Create draft pull request.
  6. Watch the Checks: CI starts automatically. A green tick is good, a red cross means read the log and fix it.

A draft pull request says "this is not ready for a final review yet". Use it to share work early and get feedback on the direction, or to see whether CI passes. Updating a pull request

A pull request is not a snapshot; it follows the branch. To address feedback, you simply commit on the same branch and push. GitHub adds the new commits to the PR, re-runs CI and shows what changed:

git switch feature/12-login-endpoint
# ...fix the code...
git add -p
git commit -m "fix(auth): return 401 for a wrong password"
git push

You do not open a new PR, and you do not need -u again. When you have fixed everything, reply to the comments and click the re-request review icon next to the reviewer's name.

Merging and after

When the PR is approved and green, a person with write access clicks the merge button. GitHub offers three ways to merge (see merge options), and a Delete branch button appears afterwards. If you delete a branch by mistake, the PR page offers Restore branch. Finally, update your own machine: git switch main, git pull, then delete the local branch.

Same repository or a fork?

Inside a company you normally push branches to the same repository and open the PR from there. In open source, you do not have write access, so you fork the repository (your own copy on GitHub), push a branch to the fork and open a PR from the fork to the original repository (the upstream). Forks and remotes are explained in Module 2; the review and merge steps are identical.

Rules of a healthy pull request process

  • No direct pushes to main. All changes arrive through a PR.
  • One purpose per PR. Keep it small enough for a reviewer to understand in one sitting.
  • CI must pass before merging. Never merge on red.
  • At least one approval from someone other than the author.
  • All review conversations are resolved (or answered) before merging.

Conventions

  • Write the title like a commit subject: present tense, specific (Add login endpoint, or feat(auth): add login endpoint if your team uses Conventional Commits).
  • Open a draft early when you want feedback on direction.
  • Link the issue with Closes #12; add screenshots for UI changes.
  • Review other people's PRs promptly — teams usually aim for the same working day.
  • Delete the branch after merging.

Common mistakes

  • Wrong base branch — for example opening against release when you meant main. Check the base selector before clicking create.
  • Unrelated commits in the PR — you branched from an old branch, not from main. Check the Commits tab; it should list only your commits.
  • Giant PRs with hundreds of changed files that nobody can review properly.
  • No description — reviewers have to guess what and why.
  • Pushing new commits after approval and merging without telling anyone.
  • Committing secrets (.env, keys) into a PR — once it is on GitHub, treat the secret as leaked (playbook).

Real projects

On a typical team the PR link goes into the team chat, CI runs automatically, a bot adds labels, CODEOWNERS requests the right reviewers, and the board moves the ticket to In review. The author usually merges after approval — or turns on auto-merge, which merges the PR by itself once the required checks pass and approvals are in.

Interview: "What is a pull request? How is it different from git merge?"

  • A PR is a GitHub feature: a request to merge a branch into another, with a page for review, discussion and automated checks. Git itself has no pull requests.
  • The merge is still a Git merge; the PR adds review, approvals, CI and an audit trail before it happens.
  • Flow: push the branch, open the PR (base = main, compare = your branch), reviewers comment, you push more commits to the same branch, approval and green checks, merge, delete the branch.
  • Pushing more commits to the branch updates the same PR automatically.
  • Mention draft PRs, linking issues with Closes #12, and required reviews and status checks from branch protection.

Writing a good PR and reviewing code

A good pull request is small, explains what and why in its description, and passes CI; a good review reads the code for correctness, design and tests, comments politely, and ends with Approve or Request changes.

The previous article showed the mechanics of a pull request. This one is about the human part, which decides how fast your code gets merged. Teams remember developers who write clear PRs and give useful reviews.

Writing a good PR

Think of your reviewer as a busy colleague who has never seen your branch. In two minutes they should understand what changed, why, how to check it and what to look at carefully.

  • Keep it small. Aim for a change a reviewer can read in 15–20 minutes. Large reviews get skimmed, and skimmed reviews miss bugs. If a feature is big, split it: first the database migration, then the service, then the controller, then the UI.
  • One purpose. Do not mix a bug fix, a refactor and a new feature. Put formatting-only changes in their own PR.
  • Title: a specific one-liner in the same style as a commit subject: Add login endpoint, not Changes or Fix stuff.
  • Description: use a template (below). Add screenshots or a short screen recording for UI changes, and example requests and responses for API changes.
  • Review your own PR first. Open the Files changed tab and read your diff as if it were someone else's. You will find forgotten System.out.println calls, commented-out code and stray files.
  • Make CI green before you ask for a review. Reviewers should not be the first to find a failing test.

Reviewing someone else's code

Open the Files changed tab. Read the description first, then the tests (they show the intent), then the production code. Check these things, roughly in this order:

  1. Does it solve the problem? Compare the code with the linked issue. Are edge cases handled: null, empty list, duplicate request, a user without permission?
  2. Correctness and bugs. Off-by-one errors, wrong HTTP status, missing transaction, race conditions, resources that are not closed, NullPointerException risks.
  3. Security. No secrets in the code; input validated; authorisation checked; no SQL built by string concatenation; no sensitive data in logs.
  4. Design. Is the logic in the right layer (controller, service, repository)? Does it follow the patterns already used in the project? Is it simpler than it could be?
  5. Tests. Is the new behaviour tested, including the failure cases? Do the tests really assert something?
  6. Readability. Clear names, short methods, comments that explain why, not what.
  7. Performance and data. N+1 queries, missing indexes for new queries, loading a whole table into memory, a database migration that locks a big table.
  8. Leftovers. Debug prints, commented-out code, unrelated files, TODOs without a ticket.

Automate what a machine can check (formatting, unused imports, static analysis, tests) so that humans spend their time on logic and design.

Comment etiquette

  • Review the code, not the person. Write "This method can return null" and not "You forgot null checks".
  • Ask questions before you accuse: "What happens if the list is empty?"
  • Explain why and, if you can, suggest a fix.

After new commits, approvals can become stale

Branch protection has a setting called Dismiss stale pull request approvals when new commits are pushed. When it is on, a new push removes earlier approvals and you need a fresh review. Another setting, Require approval of the most recent reviewable push, makes sure someone other than the pusher looks at the final code.

Rules

  • Nobody merges unreviewed code into main, and you cannot approve your own PR.
  • Every blocking comment is fixed or answered before merge.
  • The PR description says what, why and how it was tested.

Common mistakes

  • Approving with "LGTM" (looks good to me) without reading the diff.
  • Reviewing style by hand that a formatter should handle.
  • Sending a 2,000-line PR and asking for a "quick look".
  • Taking comments personally, or replying defensively. A comment is about the code.
  • Pushing a big new change after the approval, with no new review.

Real projects

Most teams have a review checklist, a rule such as "two approvals for payment code", and a CODEOWNERS file that asks the owners of a folder automatically (Module 4). Seniors often write a comment as a question to help juniors learn instead of just correcting them. Reviewing is also the fastest way for you to learn a codebase: review small PRs from day one.

Interview: "How do you do a code review? What do you look for?"

  • Start with the description and linked issue; read tests, then code.
  • Check correctness and edge cases, security, design fit, tests, readability and performance.
  • Leave specific, polite, actionable comments, use suggestions for small fixes, and separate blocking from optional.
  • End with Approve or Request changes; follow up on re-review.
  • Add that you want CI and linters to catch style so people focus on logic.

GitHub merge options: merge commit, squash and rebase

When a PR is ready, GitHub can merge it in three ways: a merge commit (keeps everything, adds a join commit), squash and merge (all commits become one), or rebase and merge (commits replayed on top with new ids, no merge commit).

The green button at the bottom of a pull request has a small arrow with three choices. A repository admin can switch each choice on or off in Settings → General → Pull Requests, so you may see only one or two. The choice decides what main's history looks like for years, so teams pick it deliberately.

Take a PR branch with three commits: "Add entity", "Fix typo" and "Add endpoint". Here is what each option does to main.

1. Create a merge commit

This is the same as git merge --no-ff: all three commits are kept, plus one merge commit with two parents. The message is Merge pull request #12 from acme/feature/12-login-endpoint.

2. Squash and merge

All commits of the PR are combined into one new commit on main. The branch's own commits do not reach main. By default the commit subject is the PR title followed by the PR number, for example Add login endpoint (#12), and the body lists the individual commit messages (you can edit both before merging).

3. Rebase and merge

GitHub replays each commit of the PR on top of the latest main, one by one. The result is a straight line and no merge commit. The commits are re-created with new ids (the code is the same, but the hashes change, and the committer becomes you), which is the same thing git rebase does locally. Because this needs a clean replay, the option is not available when the PR has conflicts; you must rebase locally first.

What teams choose

  • Squash and merge is the most common choice in product teams. main gets one commit per PR, which matches one ticket, and the PR title becomes the commit message — so it must be good (and fits Conventional Commits, see next articles). Reverting a feature is one git revert. The cost: you lose the fine-grained commits and git bisect can only point at the whole PR.
  • Merge commit is preferred when the history of how a feature was built matters, and by teams that use Git Flow. It is the safest option because it rewrites nothing.
  • Rebase and merge suits teams that make each commit small, buildable and well-named, and want a linear log with full detail. It fails more often because it needs a conflict-free replay.

Many repositories also require a linear history in branch protection, which allows only squash or rebase merges.

Mistake: building on a branch that was squash-merged

After a squash merge, your old feature branch still contains the original commits, while main has a different single commit with the same changes. If you keep working on that old branch (or branch a second feature off it) and merge again, Git sees the old commits as new and you get strange conflicts. After a squash or rebase merge, delete the branch and start the next one from the updated main.

Edge cases

  • Squash merges credit one author. GitHub adds Co-authored-by: lines for other commit authors.
  • After a squash or rebase merge, local git branch -d feature/x prints error: the branch 'feature/x' is not fully merged. The work is merged, Git just cannot see it. Check on GitHub, then use git branch -D feature/x.
  • GitHub can auto-delete head branches after merge (a repository setting) and can enable auto-merge on a PR.

Conventions

  • Follow the team's setting; do not mix styles in one repository.
  • With squash, edit the final message so it describes the change, not "Address review comments".
  • Turn on auto-delete of merged branches to avoid hundreds of stale branches.

Interview: "Squash vs merge commit vs rebase on GitHub?"

  • Merge commit: keeps all commits plus a two-parent merge commit; full history, branchy graph.
  • Squash: one commit per PR, linear, hides messy commits, easy to revert; loses detail.
  • Rebase and merge: replays commits with new ids, linear, no merge commit; needs no conflicts.
  • Name your team's choice and the reason; mention that squash needs -D to delete the local branch.

Writing good commit messages

A good commit message has a short subject in the imperative mood ("Add login endpoint"), a blank line, and an optional body that explains why; each commit contains one logical change.

The commit log is the diary of your project. Six months later, nobody remembers why a line was changed, but git log and git blame do. A message like fix or changes wastes that. A good message lets a teammate, or you, understand a change without opening the diff.

Anatomy

Add login endpoint

Users could not sign in because no endpoint existed. Add POST /api/auth/login,
which checks the BCrypt hash and returns a JWT valid for one hour.

Wrong passwords and unknown emails both return 401 so that the response does
not reveal which emails are registered.

Closes #12
  • Subject line — one line, up to about 50 characters (72 is the hard limit tools like git log --oneline and GitHub start to cut), no full stop at the end, first letter capital.
  • Blank line — required. Git uses it to separate subject from body.
  • Body (optional) — wrapped at about 72 characters. Explain what and, more importantly, why. The diff already shows how.
  • Footer (optional) — issue references (Closes #12), Co-authored-by:, BREAKING CHANGE:.

Imperative mood and "present tense"

Write the subject as a command, as if finishing the sentence "If applied, this commit will…": Add, Fix, Remove, Rename, Update. This is also the style Git itself uses for its own messages (Merge branch…, Revert "…"). People often call it "present tense"; the important part is to use Add, not Added or Adds.

An atomic commit contains exactly one logical change and leaves the project in a working state (it builds and tests pass). Do not mix a bug fix, a rename and a new feature. Benefits: easy review, easy git revert of just one thing, easy git cherry-pick, and git bisect can find the exact bad change.

What to write in the body

  • The reason: the bug you saw, the requirement, the decision.
  • What you tried and rejected, if a future reader might wonder.
  • Side effects and anything surprising ("this changes the default timeout from 30s to 10s").
  • Links to issues, not long discussions — the discussion lives in the issue.

For a one-line message, git commit -m "Add login endpoint" is fine. For a body, run git commit without -m and write in the editor, or pass -m twice: the first is the subject, the second becomes the body.

git commit -m "Fix total for empty cart" \
  -m "calculateTotal() threw ArithmeticException. Return 0 for an empty cart."

Rules

  • Subject in the imperative, no full stop, about 50 characters.
  • Blank line between subject and body.
  • One logical change per commit, and each commit builds.
  • Never put secrets or personal data in a message — it stays in history.

Common mistakes

  • Vague subjects: update, fix issues, final, final2.
  • Describing the file, not the change: Changes in UserService.java.
  • "Fix review comments" commits stay in history if you do not squash — fix them up first (interactive rebase).
  • Giant "end of day" commits with fifty files.
  • Writing the message in Hinglish or in slang in a shared project — use clear English.

Tips

  • Save work-in-progress as small local commits freely, then clean them up before opening the PR.
  • git commit --amend fixes the last message if you have not pushed yet.
  • git config --global commit.verbose true shows the diff inside the editor while you write.
  • A PR template and a commit template (git config commit.template) remind the team of the format.

Interview: "What makes a good commit message?"

  • Short imperative subject (about 50 characters), blank line, body explaining why.
  • One logical change per commit, so it can be reviewed, reverted and bisected on its own.
  • References the issue; may follow Conventional Commits.
  • Mention that the diff shows what changed; the message tells why.

Not every company uses Conventional Commits; many just use ticket ids such as CRM-142: Add login endpoint. Follow what the project already does. If there is no rule, Conventional Commits is a safe, widely understood choice.

Interview: "What are Conventional Commits?"

  • A format type(scope): description with types such as feat, fix, docs, refactor, test and chore.

Branching strategies: GitHub flow, Git Flow and trunk-based development

A branching strategy is the team's agreement on which branches exist and how work moves between them; GitHub flow (main plus short feature branches) fits most web teams, Git Flow suits versioned releases, and trunk-based development suits very fast, heavily automated teams.

Git allows any branch layout. Without an agreement, every developer invents their own and merges become painful. A branching strategy (also called a workflow) is a short set of rules: which long-lived branches exist, how feature branches are named and merged, and how releases and hotfixes are made. Pick the simplest strategy that fits how you release.

GitHub flow

The simplest, and the one in the roadmap. There is one long-lived branch, main, and it is always deployable.

  1. Create a branch from main with a descriptive name.
  2. Commit and push regularly.
  3. Open a pull request (a draft early if you want feedback).
  4. Review, discuss, and let CI run.
  5. Merge into main after approval.
  6. Deploy (often automatically); delete the branch.

Git Flow

Git Flow was described by Vincent Driessen in 2010 for software shipped in numbered versions. It uses two long-lived branches and three kinds of short-lived branches:

  • main — only released code; every commit is tagged with a version (v1.2.0).
  • develop — the integration branch where finished features collect.
  • feature/* — branch from develop, merge back into develop.
  • release/* — branch from develop when a version is ready to stabilise; only bug fixes go in. Then merge into main (tag it) and back into develop.
  • hotfix/* — branch from main to fix a live bug quickly; merge into both main and develop.

Trunk-based development

In trunk-based development everyone integrates into one branch (the "trunk", usually main) at least once a day. Branches, if used at all, live for hours, not days. Unfinished features are hidden behind feature flags — an on/off setting in code or configuration — so incomplete work can be merged but stays invisible to users. It depends on strong automated tests and fast CI, because every merge must be safe to release.

Release branches in other strategies

Even GitHub-flow teams sometimes need a long-lived release/1.4 branch to patch an old version that customers still run. You then fix on main first and cherry-pick the fix to the release branch. Some teams also keep environment branches (staging, production); they are easy to understand but cause drift, so modern teams prefer deploying the same commit through environments.

Conventions

  • Start with GitHub flow. Add more structure only when you really ship numbered versions or support several at once.
  • Keep branches short-lived whatever the strategy. Long branches are the main source of painful merges.
  • Protect main (and develop) with required reviews and checks.
  • Write the rules down in CONTRIBUTING.md so new joiners need not guess.

Exception: Git Flow is no longer the default advice

The author of Git Flow himself added a note to his article saying it suits software with explicit versions, and that teams doing continuous delivery should use a simpler flow. If your web application is deployed many times a week, Git Flow adds ceremony with little benefit.

Real projects

Service companies with client-specific releases often use Git Flow or a variant. Startups and product companies running a web backend mostly use GitHub flow with squash merges, sometimes moving towards trunk-based development with feature flags. Always follow the repository's existing flow; ask in the first week.

Interview: "Which branching strategy do you prefer and why?"

  • Describe GitHub flow, Git Flow and trunk-based in one line each.
  • Say it depends on the release model: continuous delivery favours GitHub flow or trunk-based; versioned products favour Git Flow.
  • Stress short-lived branches, small PRs, protected main and CI.
  • Mention feature flags as the way to merge unfinished work safely.

Interview questions — Branches and teamwork

What is a branch in Git?

A branch is a lightweight, movable pointer to a commit — a small file holding a commit id. Creating a branch copies no files, so it is instant. When you commit on a branch, the pointer moves forward to the new commit. HEAD points to the branch you are currently on.

What is HEAD? What is a detached HEAD?

HEAD is a pointer to where you are now: normally it points to a branch, which points to a commit. In a detached HEAD, it points straight to a commit (for example after git checkout a1b2c3d or checking out a tag). Commits you make there belong to no branch and can be lost. To keep them, run git switch -c new-branch. To leave without keeping anything, run git switch main.

What is the difference between a fast-forward merge and a three-way merge?

If the target branch has no new commits, Git only moves its pointer forward: a fast-forward, with no new commit. If both branches have new commits, Git compares the merge base and the two tips, combines the changes and creates a merge commit with two parents. --no-ff forces a merge commit; --ff-only refuses anything else.

How do you resolve a merge conflict?

Run git status to list the unmerged files. Open each, find the markers <<<<<<<, =======, >>>>>>>, write the correct final code and delete the markers. Build and test, run git add on the file, then git commit to finish. To cancel, use git merge --abort. Always read both sides, and ask the author if you are unsure.

What do "ours" and "theirs" mean in a conflict?

In a merge, ours is the branch you are on (HEAD) and theirs is the branch you are merging in. In a rebase they are reversed: ours is the branch you are rebasing onto, and theirs is your own commit being replayed. This surprises people, so check the labels in the markers.

How can you reduce merge conflicts?

Keep branches short-lived and PRs small, update your branch from main often, use a shared formatter and line-ending policy, avoid reformatting unrelated code, and talk to teammates about shared files. Build and test after each merge because semantic conflicts do not show up as Git conflicts.

What is a pull request, and how is it different from git merge?

A pull request is a GitHub feature: a request to merge one branch into another, with a page for review, comments, CI checks and approvals. Git has no pull requests. The final merge is still a Git merge, but the PR adds review and an audit trail before it. Pushing more commits to the branch updates the PR automatically.

Explain merge commit, squash and merge, and rebase and merge on GitHub.

Merge commit keeps all branch commits and adds a two-parent merge commit. Squash combines the whole PR into a single new commit on main. Rebase and merge replays each commit on top of main with new ids and no merge commit. Squash and rebase give a linear history; squash also hides messy commits and makes reverting a feature easy.

Why does git branch -d refuse to delete a branch after a squash merge?

-d only deletes a branch whose commits are reachable from the current branch. A squash merge creates a different commit, so the original commits are not reachable from main, and Git says the branch is not fully merged. After confirming on GitHub that the PR is merged, use git branch -D.

What makes a good commit message? What are Conventional Commits?

A short imperative subject (about 50 characters), a blank line, and a body that explains why. One logical change per commit. Conventional Commits adds a structure, type(scope): description, with types such as feat, fix, docs, refactor, test and chore, and ! for breaking changes. Tools use it to bump versions and write changelogs.

Compare GitHub flow, Git Flow and trunk-based development.

GitHub flow: only main plus short feature branches via PRs, deploy from main. Git Flow: main and develop plus feature, release and hotfix branches, built for versioned releases. Trunk-based: everyone merges into one trunk at least daily, with feature flags and strong CI. Choose by release model; keep branches short.

How do you delete a branch locally and on the remote?

Locally: git branch -d name (safe) or -D (force). Remotely: git push origin --delete name. Other people's remote-tracking copies disappear when they run git fetch --prune.

What does this print? You are on main and run git merge feature/x twice in a row.

The first run merges (fast-forward or a merge commit). The second prints Already up to date. because every commit of feature/x is now part of main, so there is nothing to do.

You merged the wrong branch and have conflicts you do not understand. What do you do?

If the merge is still in progress, run git merge --abort; it restores the state before the merge. Then merge the correct branch. If you already committed the merge but did not push, git reset --hard ORIG_HEAD or git reset --hard HEAD~1 undoes it. If you pushed, use git revert -m 1 <merge-commit>.

git rebase: replaying commits on a new base

git rebase main takes the commits of your branch and replays them on top of the latest main, giving a straight-line history; it creates new commits, so never rebase commits that other people already have.

You branched from main a few days ago. Since then main moved on. You want your branch to include those new commits. In Module 3 you did git merge main, which adds a merge commit. Rebase is the other way: it changes the base your branch grows from, so it looks as if you had started your work from the newest main.

How rebase works

Before rebase, the branches have diverged:

You run git switch feature and then git rebase main. Git does the following:

  1. Finds the commits that are on your branch but not on main: F1 and F2.
  2. Saves each of them as a patch (the change it made).
  3. Moves your branch to the tip of main (M4).
  4. Applies the patches one by one on top, creating new commits F1' and F2'.
$ git switch feature/discount
$ git rebase main
Successfully rebased and updated refs/heads/feature/discount.
$ git log --oneline --graph
* 5d1e7c2 Add discount tests
* b83fa90 Add discount before GST
* 7e3c1d4 Update tax rate (this is main's latest commit)
* 1a9b2f6 Add PriceCalculator

The history is a straight line. The content is the same as a merge would give, but the commits F1' and F2' have different ids from F1 and F2, because a commit id depends on its parent. That single fact explains the golden rule below.

Neither is "right". Use merge when history truth and safety matter or when the branch is shared. Use rebase to update your own private branch before the pull request, so the PR looks tidy and the final merge can be fast-forward or squash.

The golden rule

Rule: never rebase commits that other people already have

Rebase makes new commits and abandons the old ones. If a teammate has already based work on your old commits (they pulled your branch, or you pushed it and they built on it), their history now contains commits that no longer exist in yours. When they pull, Git sees two versions of the same work and creates duplicates and confusing conflicts. Rebase only commits that exist only on your machine, or on a branch only you use — even if you pushed it as a PR branch.

Never rebase main, develop or any shared branch.

The rebase workflow, including conflicts

git fetch origin                     # get the latest main from GitHub
git switch feature/discount
git rebase origin/main               # replay your commits on the new main
# ...tests...
git push --force-with-lease          # needed if the branch was pushed before

$ git rebase origin/main

  1. Open the conflicted file, fix the markers (same as in merge conflicts).
  2. git add <file> — do not run git commit.
  3. git rebase --continue — Git commits the fixed patch and replays the next one. More conflicts may come; repeat.
  4. Changed your mind? git rebase --abort returns you to exactly where you started.
  5. If a commit becomes empty or unwanted: git rebase --skip drops it.

Exception: ours and theirs swap in a rebase

While a rebase is replaying your commits onto main, Git is standing on main. So ours (the HEAD side of the markers) is the branch you are rebasing onto (main), and theirs is your commit being replayed. This is the opposite of a merge. git status says rebase in progress, and the IDE shows the "Continue Rebase" action.

git pull --rebase

A normal git pull is fetch plus merge, and when your local branch has commits that the remote lacks, it creates a merge commit just for "syncing". git pull --rebase is fetch plus rebase: your unpushed commits are replayed on top of what you fetched.

git pull --rebase
git config --global pull.rebase true     # make it the default
git config --global rebase.autoStash true  # stash and unstash dirty files automatically

This is safe because the commits being rebased are your own unpushed ones.

Pushing after a rebase: --force-with-lease

If you already pushed the branch, a rebase changes its commits, and a normal git push is rejected as non-fast-forward because the remote has the old versions. You must force the push, and you should do it in the safe way:

CommandBehaviour
git push --forceOverwrites the remote branch no matter what. If a teammate pushed a commit there meanwhile, it is destroyed without a warning.
git push --force-with-leaseOverwrites only if the remote branch is still at the commit you last fetched. If someone else pushed, Git refuses and tells you. Safe default.
 
$ git push
 ! [rejected]        feature/discount -> feature/discount (non-fast-forward)
$ git push --force-with-lease
+ 9d4e7f0...5d1e7c2 feature/discount -> feature/discount (forced update)

The line starts with + to mark a forced update. Many teams forbid force pushes on main and allow them on personal feature branches. Note: --force-with-lease is protected only by what you have fetched; running git fetch just before can quietly defeat the check, so do not fetch and push blindly in a script.

Other useful forms

  • git rebase --onto main old-base feature — move only the commits after old-base onto main. Used when you branched a feature off another feature branch whose PR was squash-merged.
  • git rebase -i — interactive: edit the commit list (next article).
  • git rebase --abort / --continue / --skip — the three exits.
  • git rebase --rebase-merges — keep merge commits instead of flattening them (rare).

Mistake: rebasing a shared branch

Wrong: rebase main, or a branch teammates use

git switch main
git rebase feature/x
git push --force

Right: rebase your private branch onto main

git switch feature/x
git rebase origin/main
git push --force-with-lease

Tip: you can always get back

Before a risky rebase, mark the spot: git branch backup-before-rebase. After the rebase the backup branch still points to the old commits. If the result is bad, git reset --hard backup-before-rebase. Or use the reflog, which remembers ORIG_HEAD as well.

Real projects

Teams that squash-merge PRs rarely need to rebase for history reasons. They still use git pull --rebase every day and rebase a feature branch before review if the team likes a linear PR. Some teams ban rebase after the PR is opened, because it hides what changed since review.

Interview: "Merge vs rebase?"

  • Merge joins two lines with a merge commit and keeps history as it happened; rebase replays your commits on a new base, giving linear history with new commit ids.
  • Rebase rewrites history, so never rebase shared commits; use it on your own feature branch.
  • After rebasing a pushed branch, use --force-with-lease, not --force.
  • Conflicts in rebase are resolved per commit with --continue; --abort cancels.
  • Mention git pull --rebase and that ours/theirs are swapped.

Interactive rebase: tidy your commits before review

git rebase -i HEAD~4 opens a list of your last four commits so you can reword, squash, fixup, drop, reorder or edit them before you share the branch.

While you work, your commits look like a diary: "wip", "fix typo", "oops", "address comments". Nobody wants these in main. Interactive rebase lets you rewrite the last few commits — combine them, rename them, remove them, change their order — and so turn the diary into a clean story. Do it before you open the PR, or before you merge, only on commits that nobody else has built on.

Starting

Say these are your last four commits:

$ git log --oneline -4
e41f09a wip
9c2d7b1 fix typo
3b8a6e0 Add AuthService
17d5c42 Add LoginRequest record

Start the rebase for the last four commits. HEAD~4 means "four commits before HEAD" and is the commit just before the ones you want to edit:

git rebase -i HEAD~4
git rebase -i main            # or: every commit of the branch since it left main

Git opens your editor with a todo list. Note the order: oldest commit first, the reverse of git log.

pick 17d5c42 Add LoginRequest record
pick 3b8a6e0 Add AuthService
pick 9c2d7b1 fix typo
pick e41f09a wip

# Commands:
# p, pick   = use commit
# r, reword = use commit, but edit the commit message
# e, edit   = use commit, but stop for amending
# s, squash = use commit, but meld into previous commit
# f, fixup  = like "squash", but discard this commit's log message
# d, drop   = remove commit
# x, exec   = run command (the rest of the line) using shell

You change the word at the start of a line, save and close the editor, and Git replays the commits following your instructions.

The commands

CommandWhat it doesTypical use
pickKeep the commit as it isDefault
rewordKeep the changes, stop to let you edit the messageFix a poor message
editStop after applying the commit so you can change files or split itSplit a big commit, or fix something in an old commit
squashMerge into the commit above; combine the messagesJoin "fix typo" into the commit it fixes
fixupLike squash, but throw away this commit's messageJoin a tiny fix without a message to edit
dropDelete the commit completely (or delete the line)Remove debug or wip commits
execRun a shell command after a commit, such as exec ./mvnw testCheck that every commit still builds

Changing the order of the lines changes the order of the commits. A commit can only be squashed into the one above it in the list.

Example: squash and reword

Goal: one commit for "Add AuthService" that includes the typo fix, no "wip", and a better first message. Edit the todo list like this:

reword 17d5c42 Add LoginRequest record
pick 3b8a6e0 Add AuthService
fixup 9c2d7b1 fix typo
drop e41f09a wip

Save and close. Git stops for the reword and opens the message editor; you change it to feat(auth): add LoginRequest record, save, and the rebase finishes:

[detached HEAD 6a1f3de] feat(auth): add LoginRequest record
 Date: Mon Nov 9 11:02:44 2026 +0530
 1 file changed, 6 insertions(+)
Successfully rebased and updated refs/heads/feature/12-login-endpoint.
$ git log --oneline -2
a94c0e8 Add AuthService
6a1f3de feat(auth): add LoginRequest record

Two commits remain instead of four, and the commit ids changed. If you pushed the branch before, finish with git push --force-with-lease.

Using edit to split a commit

Mark a commit edit. The rebase stops right after applying it. Then:

git reset HEAD~1              # undo the commit, keep the changes in the working folder
git add -p                    # stage the first part
git commit -m "refactor: extract JwtService"
git add .                     # stage the rest
git commit -m "feat: add login endpoint"
git rebase --continue

Fixup commits and --autosquash

While you work you often notice a mistake in an earlier commit. Instead of a vague "fix" commit, mark it as a fix for that commit:

git commit --fixup 3b8a6e0                 # message becomes: fixup! Add AuthService
git rebase -i --autosquash main            # fixup lines are moved and marked for you
git config --global rebase.autoSquash true # always do this

With --autosquash Git moves each fixup! commit directly under its target and sets it to fixup. You only check the list and save. This is the cleanest way to respond to review comments if your team is fine with rewriting the PR branch. (git commit --squash <commit> does the same but keeps the message for editing.)

When it goes wrong

  • git rebase --abort — cancels and returns to the state before you started.
  • git rebase --edit-todo — change the todo list during a stopped rebase.
  • Deleting all lines in the todo file (empty file) aborts the rebase.
  • Finished already but unhappy? git reflog shows where the branch was before, and git reset --hard HEAD@{1} style recovery brings it back (reflog).

Rules

  • Only rewrite commits that are not shared with others.
  • After an interactive rebase on a pushed branch, push with --force-with-lease.
  • Squashing across a merge commit does not work well: interactive rebase flattens merges unless you use --rebase-merges. Rebase branches that contain only normal commits.

Edge cases

  • If you drop a commit that later commits depend on, you will get conflicts when replaying them.
  • The first line cannot be squash or fixup (nothing above it): Git reports cannot 'squash' without a previous commit.
  • Wrongly set editor? Use git config --global core.editor "code --wait" for VS Code.

Conventions

  • Tidy before opening a PR, not after the first review.
  • Commits that remain should each build and have a clear message.
  • If your team squash-merges, tidying individual commits is optional; the PR title matters more.

Interview: "How do you squash commits?"

  • git rebase -i HEAD~N (or -i main), change pick to squash/fixup on the later commits, save, edit the final message.
  • Alternative: git reset --soft HEAD~N then one new commit.
  • On GitHub, "Squash and merge" does it at merge time.
  • Warn that it rewrites history: use only on unshared commits; push with --force-with-lease.

git stash: park unfinished work

git stash saves your uncommitted changes on a shelf and gives you a clean working folder, so you can switch branches and come back later with git stash pop.

You are in the middle of a feature when your lead says "urgent bug on main, please fix now". Your files are half-edited, not ready for a commit. You cannot switch branches easily with dirty files. Stash solves this: it takes your uncommitted changes (to tracked files), stores them in a stack, and restores the folder to the last commit.

The basic flow

$ git status -s
 M src/main/java/com/acme/crm/OrderService.java
$ git stash push -m "wip: order cancel logic"
Saved working directory and index state On feature/cancel: wip: order cancel logic
$ git status -s
$ git switch main
$ git switch -c hotfix/null-cart
# ...fix the bug, commit, push, open PR...
$ git switch feature/cancel
$ git stash pop
On branch feature/cancel
Changes not staged for commit:
	modified:   src/main/java/com/acme/crm/OrderService.java
Dropped refs/stash@{0} (3f9d2a1c...)

Plain git stash works too, but git stash push -m "text" gives the entry a name. Without a message you get something like WIP on feature/cancel: 4b7e1a2 Add cancel endpoint, which is hard to tell apart later.

Untracked files need -u

By default stash ignores files that Git does not know yet. If your work includes a brand-new file, a plain stash leaves it in the folder:

$ git stash push -m "wip"
$ git status -s
?? CancelOrderRequest.java        # still here: untracked files are not stashed
$ git stash push -u -m "wip with new files"

apply vs pop

pop = apply + drop. Prefer apply when you are not sure the result will be clean: you keep the entry until you are happy, then git stash drop. If pop hits a conflict, Git does not drop the entry (so your work is still safe); resolve the conflict, then drop it yourself. You can also apply a stash on a different branch from the one it came from.

Stash into a new branch

If popping gives conflicts because the branch moved on, or you realise the work deserves its own branch:

git stash branch feature/cancel-v2 stash@{0}

A good habit: for anything that will wait overnight, make a commit wip: cancel order on your feature branch. Later, git reset HEAD~1 or an interactive rebase removes it again.

Rules

  • Always give a stash a message with -m.
  • Stash does not include untracked files unless you use -u.
  • Stashes are local; they are not pushed and they are not tied to the branch (you can apply them anywhere).

Edge cases

  • No local changes to save — nothing to stash (or only untracked files without -u).
  • git stash pop with conflicts prints CONFLICT and keeps the stash; resolve, git add and git stash drop.
  • git stash clear and git stash drop are hard to undo, but the commit objects remain for a while; git fsck --unreachable --no-reflogs can find them. Do not rely on it.

Common mistakes

  • Forgetting stashes for weeks; git stash list grows and nobody remembers what they hold.
  • Stashing without -u and wondering why the new file is still there (or lost on a branch switch).
  • Using git stash pop on the wrong branch and creating a mess.

Interview: "What is git stash and when do you use it?"

  • It saves uncommitted changes to a stack and cleans the working folder, so you can switch tasks.
  • pop restores and removes; apply restores and keeps; -u includes untracked files.
  • Use it for short interruptions; use a WIP commit or a branch for longer work.

git cherry-pick: copy one commit to another branch

git cherry-pick <commit> applies the change made by one commit onto your current branch as a new commit, without merging the rest of the branch it came from.

Merge brings all commits of a branch. Sometimes you want only one. A typical case: a bug was fixed on main, and the same fix must also go into the old release/1.4 branch that customers still run. You do not want to merge all of main into the release branch. Cherry-pick picks that one commit, like picking one cherry from a tree.

How it works

Git looks at the change the chosen commit made (the difference between the commit and its parent), applies that difference on your current branch, and creates a new commit with the same message and author but a different id and parent.

$ git log --oneline main -3
e8a4c10 Update Swagger docs
b21f7d9 Fix NullPointerException for empty cart
5d02aa3 Add order history page
$ git switch release/1.4
Switched to branch 'release/1.4'
$ git cherry-pick b21f7d9
[release/1.4 7c93e5f] Fix NullPointerException for empty cart
 Date: Fri Nov 6 16:20:11 2026 +0530
 1 file changed, 3 insertions(+), 1 deletion(-)

The new commit is 7c93e5f; the original on main is still b21f7d9. Git treats them as two unrelated commits, which has a consequence: when you later merge the two branches, Git handles the duplicate change fine in most cases (same change on both sides), but a long-term cherry-pick habit can confuse history.

git cherry-pick A..BCopy the commits after A up to and including B (A itself is excluded)
git cherry-pick A^..BCopy A through B (A included)

Conflicts

If the target branch differs from where the commit was made, the change may not apply cleanly:

hint: run "git cherry-pick --abort".

Resolve the markers as in a merge, git add the file and run git cherry-pick --continue. To give up, git cherry-pick --abort.

Typical uses

  • Hotfix to a release branch: fix on main first, then cherry-pick (with -x) to each supported release branch. Fixing on main first makes sure the fix is not lost in the next version.
  • Rescue a commit from the wrong branch: you committed on main but meant a feature branch: switch to the right branch, cherry-pick the commit, then remove it from main (playbook).
  • Take one useful commit from an abandoned branch or a teammate's PR.
  • Backport a security patch to an older version.

Rules

  • The picked commit gets a new id. The same fix now exists twice, in two branches.
  • Pick commits in the same order they were made when you pick more than one, or you risk conflicts.
  • Have a clean working folder before you start.

Mistake: using cherry-pick instead of merge

If you keep cherry-picking commit after commit between two long-lived branches, you create duplicates and conflicts later when they are finally merged. Cherry-pick is for single, exceptional commits. If you need most of a branch, merge or rebase it. Also, a commit that depends on earlier commits (a method added two commits before) will not compile when picked alone.

Tip: preview with git cherry

git cherry -v release/1.4 main lists commits in main that are not yet applied to release/1.4, comparing by content. A - at the start means an equivalent commit is already there; a + means it is missing.

Interview: "What is cherry-pick and when would you use it?"

  • It copies a single commit onto the current branch as a new commit (new id).
  • Use it for hotfix backports, rescuing a commit from the wrong branch or taking one commit from another branch.
  • Mention -x, ranges and resolving conflicts with --continue; warn about duplicates.

git reset: move the branch and choose what to keep (soft, mixed, hard)

git reset <commit> moves the current branch to another commit; --soft keeps your changes staged, --mixed (default) keeps them unstaged, and --hard throws them away — which makes --hard the risky one.

You committed something wrong. Maybe the message was bad, maybe the code was half-finished, maybe it should never have been committed. If the commit is still only on your machine, git reset can undo it. To understand the three modes you need to remember the three places Git keeps your files (from Module 1):

HEAD (the last commit)
The snapshot of the commit your branch points to.
Index (staging area)
What the next commit will contain; filled by git add.
Working folder
The real files you edit.

What each mode changes

All modes first move the branch (and HEAD) to the target commit. They differ in what else they reset to match:

ModeYour changes end up…Use it to
--softStaged, ready to commit againRedo the last commit(s): change the message, or squash several commits into one
--mixed (default)In the working folder, unstagedUn-commit and re-stage differently; split a commit; unstage files
--hardDeletedThrow away commits and local edits; match a known good state

Examples

Start with three commits on a feature branch:

$ git log --oneline
c3d4e5f Add cancel endpoint
b2c3d4e Add OrderService.cancel
a1b2c3d Add Order entity
git reset --soft HEAD~1
git status -s          # the changes of c3d4e5f are staged
git commit -m "feat(order): add cancel endpoint"   # commit again with a better message
git reset HEAD~1       # same as: git reset --mixed HEAD~1
git status -s          # files show as modified, not staged
git add -p             # stage them in smaller pieces and make two commits
git reset --hard HEAD~1
git log --oneline      # c3d4e5f is gone from the branch (still in the reflog)

Useful variants

CommandMeaning
git reset HEAD~1Branch back one commit; keep changes unstaged
git reset --soft HEAD~3Branch back three commits; keep all their changes staged — then one commit squashes them
git reset --hard origin/mainMake your branch exactly like the remote; local commits and edits are lost
git reset --hard ORIG_HEADUndo the last merge or pull (ORIG_HEAD remembers where HEAD was before a risky command)
git reset file (= git reset HEAD file)Unstage a file; the file is untouched. Modern form: git restore --staged file
git restore fileDiscard working-folder edits of one file. This is permanent; there is no undo

Do not confuse git reset file (unstage one file; path given, branch does not move) with git reset commit (moves the branch).

Why reset --hard is risky

  • It deletes uncommitted edits in the working folder. These were never in a commit, so nothing can bring them back — not the reflog, nothing.
  • It silently drops commits from the branch. The commits can usually be recovered through the reflog for some weeks, but only if you know to look.
  • On a shared branch it rewrites history. If you push it (which needs a force push), you remove teammates' work or cause diverged histories.

Mistake: hard reset with unsaved edits

Run git status and git diff before every reset --hard. If there is anything you might want, commit it to a temporary branch or git stash it first. For uncommitted work, git stash is the safety net; for committed work, the reflog is.

Rules

  • Reset only commits you have not pushed (or on a private branch).
  • For a commit that is already shared, use git revert, which adds a new commit instead of rewriting history.
  • Check with git status and git log --oneline before and after.

Edge cases

  • During a merge with conflicts, git reset --merge aborts safely (like git merge --abort); git reset --hard also works but is blunter.
  • If you reset a branch and your teammates already pulled the old commits, their next pull will try to merge them back. Coordinate, or use revert.
  • git reset --keep is a safer cousin of --hard: it refuses if it would overwrite local edits.

Interview: "Explain git reset soft, mixed and hard"

  • All three move the branch to the target commit. Soft keeps changes staged; mixed (default) unstages them but keeps files; hard resets index and files too.
  • Hard deletes uncommitted work; risky on shared history.
  • Reset rewrites history (local); revert adds a new commit (safe for shared branches).

git revert: undo a commit safely, and revert vs reset

git revert <commit> creates a new commit that does the opposite of an earlier one, undoing its effect without rewriting history — the right tool for commits that are already pushed.

Suppose commit b21f7d9 broke production and it is already on main, which everyone has pulled. You cannot reset (that would rewrite shared history). Instead you add a new commit that cancels the old one:

$ git revert b21f7d9
[main 4e6a91c] Revert "Add discount to every order"
 1 file changed, 2 insertions(+), 5 deletions(-)
$ git push
$ git log --oneline -3
4e6a91c Revert "Add discount to every order"
b21f7d9 Add discount to every order
5d02aa3 Add order history page

The history now shows both the mistake and its undo. Nothing was rewritten, so everyone can simply pull. The default message is Revert "<original subject>"; add the reason in the body ("rolled back, causes double discount in checkout").

Common forms

CommandMeaning
git revert HEADUndo the latest commit
git revert a1b2c3dUndo one specific commit, wherever it is in history
git revert HEAD~3..HEADUndo the last three commits, one revert commit each (newest first)
git revert -n a1b2c3dApply the reversal but do not commit (--no-commit); combine several reverts into one commit
git revert -m 1 <merge-commit>Undo a merge commit, keeping parent 1 (the mainline) as the base
git revert --continue / --abortAfter a conflict

If the reversal clashes with later changes, Git reports a conflict. Resolve it as always, git add, then git revert --continue.

Reverting a merge commit

A merge commit has two parents, so Git does not know which side you want to keep. You must say: -m 1 means "the first parent is the mainline", i.e. undo the changes the merged branch brought in:

$ git revert -m 1 0448514
[main 91d3c2e] Revert "Merge pull request #14 from acme/feature/wishlist"
$ git revert 0448514
error: commit 0448514 is a merge but no -m option was given.

Exception: reverting a merge, then merging the branch again

After you revert a merge, Git thinks the branch's commits are already merged, so merging the same branch again (after fixing it) brings in nothing. The fix: revert the revert commit first (which re-applies the changes), then add your new fixes. This surprises many people. With squash merges the problem does not exist, because each PR is just a normal commit and a plain git revert works.

Rule: pushed means revert

If a commit has reached a shared branch such as main, use git revert. Use reset and amend only while the commits are yours alone.

Conventions

  • Say why in the revert commit body, and link the issue or incident.
  • On GitHub, the Revert button on a merged PR opens a new PR that reverts it — the usual way on protected branches.
  • After reverting urgently, fix the problem on a branch and re-apply the work through a new PR.

Interview: "git reset vs git revert? How do you undo a pushed commit?"

  • Reset moves the branch pointer and rewrites history; revert adds an inverse commit and keeps history.
  • For a pushed commit use git revert <sha> and push normally; for a merge commit use -m 1.
  • Use reset only on local unpushed work; if you must reset a shared branch, a force push is needed and the team must be told — avoid it.

git reflog: recover "lost" commits

The reflog is Git's private diary of where HEAD and each branch pointed over time, so after a bad reset, rebase or branch delete you can find the old commit id and get your work back.

When Git "loses" a commit, it usually did not delete anything. It only moved a branch label away from it. The commit object is still stored. You just need its id. The reflog (reference log) records every move of HEAD and of your branches on your machine: commits, checkouts, resets, rebases, merges, pulls.

Reading the reflog

$ git reflog
3f9d2a1 (HEAD -> main) HEAD@{0}: reset: moving to HEAD~2
b21f7d9 HEAD@{1}: commit: Add cancel endpoint
7c93e5f HEAD@{2}: commit: Add OrderService.cancel
5d02aa3 HEAD@{3}: checkout: moving from feature/cancel to main
e8a4c10 HEAD@{4}: commit: Update Swagger docs

Each line shows the commit id, a position name HEAD@{n} (0 = now, bigger = older), and what happened. Here, at HEAD@{0} someone ran git reset HEAD~2, and the two commits they dropped are still listed as HEAD@{1} and HEAD@{2}.

You can use these names anywhere a commit is expected: git show HEAD@{1}, git diff HEAD@{2} HEAD. Time-based names work too: main@{yesterday} or HEAD@{2.hours.ago}. git reflog show feature/cancel shows the log of one branch.

Recover after a hard reset

You ran git reset --hard HEAD~2 and now realise the two commits were needed. Find the commit you were on before, then move back to it:

$ git reflog
3f9d2a1 HEAD@{0}: reset: moving to HEAD~2
b21f7d9 HEAD@{1}: commit: Add cancel endpoint
$ git reset --hard b21f7d9        # or: git reset --hard HEAD@{1}
HEAD is now at b21f7d9 Add cancel endpoint
$ git log --oneline -2
b21f7d9 Add cancel endpoint
7c93e5f Add OrderService.cancel

If you are nervous about moving your current branch, make a new branch at the old commit instead: git branch rescue b21f7d9. This is the safest way, since it changes nothing else.

Recover a deleted branch

This is the roadmap exercise. You deleted a branch that had commits not yet merged:

$ git branch -D feature/search
Deleted branch feature/search (was 9e12b7c).

Git even prints the commit id: 9e12b7c. If you missed it, find it in the reflog (look for the last checkout: moving from feature/search or the last commit on it):

$ git reflog
a77c01d HEAD@{0}: checkout: moving from feature/search to main
9e12b7c HEAD@{1}: commit: Add search filter
$ git switch -c feature/search 9e12b7c
Switched to a new branch 'feature/search'

The branch is back with all its commits.

Undo a rebase, amend or merge

  • Before a rebase or merge Git saves the old tip as ORIG_HEAD, so right afterwards git reset --hard ORIG_HEAD undoes it.
  • Later, find the line before the rebase in the reflog (the entry just before rebase (start)) and reset to it.
  • For a bad git commit --amend, the old commit is the previous reflog entry.

How long entries live

Reflog entries expire. By default (the settings gc.reflogExpire and gc.reflogExpireUnreachable) entries that are still reachable stay for 90 days, and entries for commits that are no longer reachable from any branch stay for 30 days. After that, Git's cleanup (git gc, which runs automatically now and then) may delete the unreachable commits for good. So: recover soon, within a few weeks.

What the reflog cannot do

  • It is local. It is not pushed, and a fresh clone has an empty reflog. If a colleague deleted a branch on their machine, the reflog on your machine will not help.
  • It only tracks committed (or stashed) work. Uncommitted edits lost by git reset --hard or git checkout -- file are gone; nothing records them. (A file you had at least staged with git add may still be recoverable with git fsck --lost-found, but do not count on that.)
  • A deleted remote branch can be restored on GitHub (the PR page has Restore branch), or by pushing a local copy again.

Rules

  • Commit before you experiment; the reflog only protects commits.
  • When something goes wrong, stop and run git reflog before you try more commands.
  • Recover onto a new branch first (git branch rescue <sha>) and inspect it before moving anything else.

Tip: find an old commit by message

git reflog | grep -i "search filter" finds the entry quickly. git log -g shows the reflog in the long git log format, which is better when you need the message and the date.

Interview: "I deleted a branch / did a hard reset. Can you recover?"

  • Yes, if the work was committed: run git reflog, find the commit id, and create a branch there (git switch -c name <sha>) or git reset --hard <sha>.
  • The reflog is local and entries expire (about 30 days for unreachable commits, 90 for reachable).
  • Uncommitted changes cannot be recovered.

Tags and releases with semantic versions

A tag is a permanent name for one commit, used to mark releases such as v1.2.0; use annotated tags (git tag -a), push them explicitly, and number them with SemVer (MAJOR.MINOR.PATCH).

A branch moves forward with every commit. A tag does not: it is a fixed label stuck to one commit. When you release version 1.2.0 of your CRM, you tag the exact commit that was built and deployed. Months later you can still check out v1.2.0, compare it with v1.3.0 or rebuild the old version for a customer.

Semantic versioning (SemVer)

Semantic Versioning gives the numbers a meaning. A version is MAJOR.MINOR.PATCH:

PartIncrease it when…Example
MAJORYou make an incompatible (breaking) change to the public API1.4.2 → 2.0.0
MINORYou add functionality in a backward-compatible way1.4.2 → 1.5.0
PATCHYou make backward-compatible bug fixes only1.4.2 → 1.4.3
  • When you raise MAJOR, MINOR and PATCH reset to 0; when you raise MINOR, PATCH resets to 0.
  • Pre-release versions add a hyphen: 2.0.0-alpha.1, 2.0.0-beta.2, 2.0.0-rc.1. They rank below the final 2.0.0.
  • Build metadata adds a plus sign and does not affect ordering: 1.2.0+build.45.
  • Versions 0.y.z mean "initial development": anything may change. Version 1.0.0 declares the public API stable.
  • Versions are compared as numbers: 1.10.0 is newer than 1.9.0.

The Git tag usually adds a v in front: tag v1.2.0 for version 1.2.0. Match it with the version in your pom.xml (Maven uses 1.2.0-SNAPSHOT for work in progress and 1.2.0 for a release) or build.gradle.

GitHub Releases

A GitHub Release is a page built on a tag: a title, release notes and downloadable files (a JAR, a ZIP, checksums). Create it under Releases → Draft a new release: choose or create the tag, press Generate release notes (GitHub lists merged PRs and contributors since the last release), edit, tick pre-release if needed, attach files and publish. With the optional GitHub CLI: gh release create v1.2.0 --generate-notes.

Good release notes group changes (Features, Fixes, Breaking changes) and say what users must do to upgrade. With Conventional Commits and labelled PRs this is mostly automatic. A GitHub Actions workflow can run when a tag is pushed, build the JAR or Docker image and publish it (DevOps · Module 4).

Rules

  • Tag releases with annotated tags and v-prefixed SemVer names.
  • Tags are not pushed automatically; push them.
  • Never move or reuse a published tag. If 1.2.0 has a bug, release 1.2.1.

Edge cases

  • Moving a tag (git tag -f) is possible but others who already fetched the old one will not get the new one. Treat tags as immutable.
  • A tag and a branch can share a name, which confuses commands (warning: refname 'v1' is ambiguous). Keep the names different.
  • Squash-merged PRs make tagging easy: tag the merge commit on main.

Mistake: tagging but forgetting to push

You create v1.2.0, the CI or the release page does not see it, because the tag exists only on your laptop. Run git push origin v1.2.0 and check on GitHub under Tags.

More professional tools: bisect, blame, clean, log -S, worktree, hooks and more

These smaller tools solve real problems: bisect finds the commit that broke something, blame and log -S find who changed what and when, clean removes untracked files, and hooks, LFS, .gitattributes and signed commits keep a team's repository healthy.

git bisect: find the commit that introduced a bug

A test passed last month and fails today. Between then and now there are 200 commits. Bisect does a binary search: you mark one commit good and one bad, Git checks out the middle commit, you test it, and in about eight steps (200 commits need log₂(200) ≈ 8) it finds the first bad commit.

$ git bisect start
$ git bisect bad                    # the current commit is broken
$ git bisect good v1.1.0            # this tag was fine
Bisecting: 99 revisions left to test after this (roughly 7 steps)
[4b7e1a2...] Add order filters
$ ./mvnw -q test                    # test this commit
$ git bisect good                   # or: git bisect bad
Bisecting: 49 revisions left to test after this (roughly 6 steps)
...
9c2d7b1e... is the first bad commit
commit 9c2d7b1e...
    Refactor tax calculation
$ git bisect reset                  # return to where you started

To automate it, give Git a command that exits with 0 for good and non-zero for bad: git bisect run ./mvnw -q test. Small, atomic commits make bisect very effective (one reason not to squash everything on your own branch before merge).

git clean: remove untracked files

git clean deletes files that Git does not track (build output, leftover files). Deleted files do not go to a recycle bin, so always preview first:

$ git clean -nd                     # include untracked directories
$ git clean -fd                     # really delete untracked files and directories

git worktree (brief)

A worktree checks out a second branch in a second folder from the same repository, so you can fix a hotfix without stashing or switching:

git worktree add ../crm-hotfix hotfix/null-cart   # new folder with that branch
git worktree list
git worktree remove ../crm-hotfix                 # when done

A branch can be checked out in only one worktree at a time.

.gitattributes (brief)

This file in the repository root tells Git how to treat files. The most common use is making line endings consistent between Windows (CRLF) and Linux/macOS (LF):

# normalise text files; checkout converts to the platform's line ending
* text=auto
# shell scripts must always keep LF, or they fail on Linux
*.sh text eol=lf
# treat these as binary: no diff, no line-ending change
*.png binary
*.jar binary

Git LFS (brief)

Git stores every version of every file forever, so big binary files (videos, design files, datasets) make a repository huge. Git LFS (Large File Storage) is an extension that stores such files on a separate server and keeps only small pointer files in Git. It is installed separately (git lfs install once), then you choose patterns: git lfs track "*.psd", which writes a rule into .gitattributes. Commit that file and the large files behave normally. GitHub limits the size of normal files and LFS storage has quotas; do not put build output or dependencies in Git at all.

Git hooks and pre-commit checks (brief)

A hook is a script that Git runs at a certain moment. Hooks live in .git/hooks/ and are named after the event: pre-commit (before a commit is created), commit-msg (check the message), pre-push (before pushing). If the script exits with a non-zero status, Git stops the operation.

#!/bin/sh
# Block the commit if the code is not formatted
./mvnw -q spotless:check || {
    echo "Run ./mvnw spotless:apply and commit again"
    exit 1
}

The .git folder is not shared when others clone the repository, so hooks are not shared either. Teams share hooks in a tracked folder and run git config core.hooksPath .githooks, or use tools: Husky (JavaScript projects), the pre-commit framework, or Lefthook. You can skip hooks once with git commit --no-verify, so CI must run the same checks too — hooks are a convenience, CI is the guarantee.

Signed commits (brief)

Anyone can set user.name and user.email to any value, so commit authorship can be faked. Signing a commit proves it came from the holder of a key. GitHub then shows a green Verified badge. Many organisations require it.

git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true      # sign every commit
git commit -S -m "feat: add login endpoint"  # or sign one commit
git log --show-signature -1

You also add the same public key to GitHub as a signing key (a separate setting from your login key). GPG keys work too, and Git supports signing with SSH keys from version 2.34.

Rules

  • Run git clean -n before git clean -f. Deleted untracked files cannot be recovered.
  • Hooks are local. Repeat every important check in CI.
  • Do not commit large binaries or secrets; use LFS or an artifact store, and use environment variables or a secret manager for secrets.

Tip: aliases for your favourite commands

For example git config --global alias.lg "log --oneline --graph --decorate --all" makes git lg a short command for a nice graph.

Interview: "How would you find which commit introduced a bug?"

  • Use git bisect: mark a known bad and a known good commit, test the commits Git offers (or automate with bisect run), and it finds the first bad commit by binary search in O(log n) steps.
  • Then git show the commit, and use git blame or git log -S to understand the context.

Disaster recovery playbook: fixing common Git mistakes

Most Git mistakes can be fixed: stop, run git status and git reflog, then pick the right recovery from the table — and if you pushed a secret, rotate the secret first.

Everyone makes these mistakes. The difference between a junior and a senior is not that the senior never makes them, but that the senior stays calm and knows the way out. First, the general procedure:

  1. Stop. Do not run more commands in panic; each can make recovery harder.
  2. Look. git status, git log --oneline --graph --all -10 and git reflog.
  3. Make a safety branch if you have commits worth keeping: git branch rescue.
  4. Check whether it is pushed. Local-only mistakes can be rewritten. Pushed ones need revert (or a coordinated force push).
  5. Fix with the smallest tool (table below), then verify.

Committed to the wrong branch

You are on main and made two commits that belong on a new feature branch. Nothing is pushed yet.

Order matters: create the branch first, then reset. Check git status is clean before the hard reset. Alternatively, switch to the right branch and cherry-pick the commits, then reset main.

You pushed a secret

A database password or API key is now on GitHub. The order of actions is important:

  1. Rotate the secret immediately. Revoke the old key or change the password at the provider (cloud console, payment gateway, database). Assume it was copied: bots scan public GitHub within minutes, and even private repositories have many readers. This step is the real fix.
  2. Check the provider's logs for misuse during the exposure.
  3. Remove the secret from the code and use an environment variable or a secret manager; add the file (.env) to .gitignore.
  4. Optionally clean the history so the old value does not stay visible. Use git filter-repo (a separate tool, the replacement for the old git filter-branch) or BFG Repo-Cleaner, then force push, and ask everyone to re-clone. Forks, clones, PR refs and caches may still hold the old data, so this does not make the secret safe — which is why step 1 comes first.
  5. Turn on GitHub secret scanning and push protection to block such pushes in the future.

Mistake: deleting the file and thinking the secret is gone

A new commit that removes the secret does not remove it from history: anyone can open the old commit. Only rotating the secret makes it harmless.

Bad commit or merge already on main

Tell the team in the chat. After the incident is over, fix the root problem on a branch and send it through a new PR. If you really must force-push a shared branch, agree with the team first, use --force-with-lease, and tell everyone to git fetch and reset their local copy.

Rules

  • Before anything destructive, check git status and make a rescue branch.
  • Shared history is never rewritten without agreement; use revert.
  • A leaked secret is always rotated, whatever you do to the history.

Prevention

  • Protect main so nobody can push or force-push to it.
  • Keep .gitignore current (.env, target/, node_modules/, IDE folders).
  • Use git add -p and look at git diff --staged before every commit.
  • Use secret scanning and a pre-commit secret check.

Interview: "You pushed a password to GitHub. What do you do?"

  • Rotate or revoke the credential immediately; check logs for abuse.
  • Remove it from the code, move to environment variables or a secret manager.
  • Optionally rewrite history with git filter-repo or BFG and force push, knowing it is only cosmetic because the secret may already be copied.
  • Enable secret scanning and push protection; tell the security team if your company requires it.

Branch protection, rulesets and CODEOWNERS

Branch protection (or the newer rulesets) forces every change to main to go through a pull request with required reviews and passing checks, and blocks force pushes and deletion; CODEOWNERS asks the right people to review automatically.

Rules written in a wiki are easy to forget. Rules enforced by GitHub cannot be forgotten. A repository admin sets them in Settings → Branches (a branch protection rule) or Settings → Rules → Rulesets. Rulesets are the newer system: they can target many branches by pattern, can be shared across a whole organisation, can be switched to an "evaluate" mode first, and several can apply at once.   • Required checks must have exactly the names of the CI jobs; a check that never runs will block merging forever.

  • Protect with a small set of strict rules, and keep the review requirements reasonable so that PRs do not wait for days.
  • Keep CODEOWNERS short and use teams, not individuals, so holidays do not block merges.

Interview: "How do you protect the main branch?"

GitHub Actions and Dependabot at a glance

GitHub Actions runs your build and tests automatically on GitHub when you push or open a PR, from a YAML file in .github/workflows/; Dependabot opens PRs that update your dependencies.

GitHub Actions is GitHub's built-in automation (CI/CD: continuous integration and delivery). A workflow is a YAML file in .github/workflows/. It says when to run (the trigger, such as push or pull_request) and what jobs and steps to run on a fresh virtual machine (a runner). The results appear as checks on the PR, and branch protection can require them. The full topic, including Docker and deployment, is in DevOps · Module 4. Here is a first workflow for a Maven project:

name: CI

on:
  pull_request:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 21
          cache: maven
      - name: Build and test
        run: ./mvnw -B verify
  • on — the triggers: every PR, and every push to main.
  • runs-on — the kind of machine (a GitHub-hosted Linux runner).
  • uses: actions/checkout@v4 — downloads your code; setup-java installs JDK 21 and caches Maven downloads.
  • run — a shell command; if it fails, the job and the PR check turn red.

Commit this file on a branch and open a PR: the Checks tab shows the build running. Name the job (build) in your branch protection as a required check.

Mistake: putting secrets in the workflow file

Use Settings → Secrets and variables → Actions and read them as ${{ secrets.NAME }}. Never write tokens or passwords in YAML. Also remember that workflows from forked PRs do not get your secrets by default.

Dependabot (brief)

Dependabot checks your dependencies (Maven, Gradle, npm, Docker, even the Actions you use) and opens a PR when a newer version or a security fix exists. Turn on Dependabot alerts and security updates in repository settings, and add a config file for regular version updates:

version: 2
updates:
  - package-ecosystem: maven
    directory: "/"
    schedule:
      interval: weekly
  - package-ecosystem: github-actions
    directory: "/"
    schedule:
      interval: weekly

Each update is a normal PR: CI runs on it, and you review and merge. Do not auto-merge major upgrades without tests.

Real projects

A typical setup: CI on every PR (build, tests, lint), required by branch protection; a release workflow on tags that builds a JAR or Docker image; Dependabot for weekly updates; CODEOWNERS for sensitive folders. Together they let a team merge quickly and safely many times a day.

Interview: "What is GitHub Actions? How does CI fit with PRs?"

  • It runs workflows defined in YAML on events like pull_request; each run reports a check on the PR.
  • Branch protection requires the checks to pass before merge, so broken code cannot reach main.
  • Dependabot automates dependency update PRs.

Interview questions — Professional Git

What is the difference between merge and rebase?

Merge combines two branches by creating a merge commit with two parents and keeps history as it happened. Rebase takes your commits and replays them on top of another branch, creating new commits (new ids) and a linear history. Rebase rewrites history, so never rebase commits that others already have; use it on your own feature branch. After rebasing a pushed branch use git push --force-with-lease.

What is the difference between git fetch and git pull?

git fetch downloads new commits and updates remote-tracking branches such as origin/main, but does not touch your branches or files. git pull is fetch followed by a merge into your current branch (or a rebase with --rebase). Fetch first when you want to look before you integrate (git log HEAD..origin/main).

Reset vs revert: when do you use which?

git reset moves the branch pointer back and so rewrites history; use it for local, unpushed commits. git revert adds a new commit that undoes an earlier one and keeps history; use it for commits that are already pushed or merged into a shared branch.

Explain reset --soft, --mixed and --hard.

All three move the branch to the target commit. --soft leaves the index and files unchanged, so the undone changes are staged. --mixed (default) resets the index, so the changes remain in files, unstaged. --hard resets index and files, so the changes are discarded. Uncommitted edits lost by --hard cannot be recovered.

How do you undo a commit that you already pushed?

Use git revert <sha> and push the new commit; for a merge commit use git revert -m 1 <sha>. This keeps history intact. Resetting and force-pushing is possible on a private branch but dangerous on a shared one.

What is HEAD, and what is a detached HEAD?

HEAD points to the commit you are working on, normally through the current branch. A detached HEAD points directly to a commit, for example after checking out a tag or a commit id. New commits there are not on any branch and can be lost; create a branch with git switch -c name to keep them.

What does git stash do, and what is the difference between apply and pop?

It saves uncommitted changes in a stack and restores a clean working folder. apply brings the changes back and keeps the stash entry; pop brings them back and deletes the entry. Use -u to include untracked files and -m to name the entry.

What does git cherry-pick do?

It applies the change of a single commit onto the current branch as a new commit with a new id. Typical use: copy a hotfix from main to a release branch. Conflicts are resolved like in a merge and finished with git cherry-pick --continue.

I deleted a branch with unmerged commits. How do I get it back?

Run git reflog, find the last commit of the branch (Git also prints it when you delete: was 9e12b7c), and recreate it with git switch -c name 9e12b7c. This works for committed work on your machine for roughly 30 days or more, until garbage collection removes unreachable commits.

What is the difference between --force and --force-with-lease?

--force overwrites the remote branch unconditionally. --force-with-lease overwrites only if the remote is still at the commit you last saw, so it refuses when a teammate has pushed in the meantime and protects their work.

How do you squash the last four commits?

Run git rebase -i HEAD~4, keep pick on the first line and change the others to squash or fixup, then edit the combined message. Or run git reset --soft HEAD~4 and make one new commit. This rewrites history: do it only on unshared commits and push with --force-with-lease.

What is the difference between a lightweight and an annotated tag, and what is SemVer?

A lightweight tag is just a name for a commit. An annotated tag is a full object with tagger, date and message and is the right choice for releases. SemVer numbers versions MAJOR.MINOR.PATCH: major for breaking changes, minor for compatible features, patch for bug fixes. Tags are pushed explicitly (git push origin v1.2.0).

A bug appeared sometime in the last 200 commits. How do you find the cause?

Use git bisect: start it, mark the current commit bad and an old one good, then test each commit Git checks out and answer good or bad (or automate with git bisect run). It performs a binary search and names the first bad commit in about eight steps.

You pushed an API key to GitHub. What do you do?

Revoke and replace the key first; assume it is already copied. Check the provider's logs. Remove it from the code and use environment variables or a secret manager. Rewriting history with git filter-repo or BFG is optional and does not make the old key safe. Enable secret scanning and push protection.

How do you protect the main branch?

Use branch protection or rulesets: require a pull request, required approvals, passing status checks (CI), resolved conversations, optionally CODEOWNERS review, linear history and signed commits; block force pushes and deletion. This makes the team workflow automatic.

Cheat sheet — Professional Git

  • git rebase main replay your branch commits on top of main (new ids, linear history)
  • Golden rule never rebase or reset commits other people already have
  • --continue / --skip / --abort the three exits of a rebase or cherry-pick that stopped
  • git pull --rebase fetch and rebase your local commits instead of making a merge commit
  • git push --force-with-lease safe force push after a rebase; never plain --force
  • git rebase -i HEAD~4 edit the last four commits: pick, reword, edit, squash, fixup, drop
  • git commit --fixup sha then git rebase -i --autosquash main to fold a fix into an older commit
  • git stash push -m "msg" -u shelve changes, including untracked files
  • git stash list / pop / apply / drop see, restore and remove, restore and keep, delete entries
  • git cherry-pick sha copy one commit to the current branch; -x notes the source
  • git reset --soft HEAD~1 undo commit, keep changes staged
  • git reset HEAD~1 undo commit, keep changes unstaged (mixed)
  • git reset --hard sha move branch and discard all changes; risky
  • git revert sha new commit that undoes an old one; safe for pushed history
  • git revert -m 1 merge undo a merge commit, keeping the mainline
  • git commit --amend replace the last commit (unpushed only)
  • git reflog diary of where HEAD was; find lost commits and use git switch -c name sha
  • ORIG_HEAD remembers HEAD before a merge, rebase or reset: git reset --hard ORIG_HEAD
  • git tag -a v1.2.0 -m "msg" annotated release tag; git push origin v1.2.0 to publish
  • SemVer MAJOR.MINOR.PATCH; breaking / feature / fix; pre-release -rc.1
  • git bisect start / good / bad / run / reset binary-search for the bad commit
  • git blame -L a,b file; git log -S"text" who changed a line; when text appeared or vanished
  • git clean -n then -fd preview, then delete untracked files
  • Secret pushed rotate first, clean history later (and optionally)
  • main protection PR required, approvals, status checks, no force push; CODEOWNERS for reviewers

Practice — Professional Git

  1. Rebase vs merge. Create a repository with two commits on main. Branch feature/a with two commits, then add a commit on main. Update feature/a once with git merge main (reset it afterwards with git reset --hard ORIG_HEAD) and once with git rebase main. Compare git log --oneline --graph --all. Done when you can explain why the commit ids changed after the rebase.
  2. Rebase conflict. Make main and your branch change the same line, then rebase. Resolve the conflict, git add, git rebase --continue. Repeat and finish with git rebase --abort. Done when you can say which side "ours" is.
  3. Tidy with interactive rebase. Make four commits: "add feature", "typo", "wip", "add tests". Use git rebase -i HEAD~4 to fixup the typo, drop wip and reword the others. Done when git log --oneline shows two clean commits.
  4. Stash. Edit a tracked file and create a new file. Run git stash push -m "wip", notice the new file stays, then use -u. Switch to another branch, switch back, git stash pop. Done when both changes return and git stash list is empty.
  5. Cherry-pick a hotfix. Create release/1.0 from an early commit. Fix a bug on main and cherry-pick that commit with -x to the release branch. Done when the release branch has the fix, and the message contains (cherry picked from commit ...).
  6. Roadmap exercise: undo a mistake three ways. Commit a mistake (for example a wrong file) three times, each in a fresh copy of the repository. Undo it with git commit --amend, with git revert, and with git reset --soft HEAD~1. Done when you can say which of the three is allowed after a push and why.
  7. Roadmap exercise: recover a deleted branch. Create a branch with two commits, switch away and delete it with git branch -D. Bring it back using git reflog and git switch -c. Then do a git reset --hard HEAD~2 on main and recover that too. Done when both branches have their commits back.
  8. Tag a release. Create the annotated tag v1.0.0, push it, then create a GitHub Release with generated notes. Add a fix, tag v1.0.1. Done when the Releases page lists both and git describe works.
  9. Find a bug with bisect. Create 10 commits where commit 6 introduces a failing check (a script that exits 1). Use git bisect run ./check.sh to find it. Done when Git names the sixth commit as the first bad one.
  10. Protect main and add CI. In your own repository add .github/workflows/ci.yml through a PR, add a CODEOWNERS file, then create a branch protection rule requiring a PR and the CI check. Try to push to main directly and read the error. Finish the Main and Remote sections of Learn Git Branching (learngitbranching.js.org) if you have not yet. Done when the direct push is rejected and a PR with a red check cannot be merged.

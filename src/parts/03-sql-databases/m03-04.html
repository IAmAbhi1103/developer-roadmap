Classic query: second and Nth highest salary

"Find the second highest salary" is the most asked SQL interview question. Know three answers: a subquery with MAX, LIMIT … OFFSET on distinct values, and DENSE_RANK, then turn the last into an Nth-highest function.

The question and its traps

Distinct salaries in the sample data, highest first: 300000, 220000, 160000, 150000, 120000, 110000, 90000, 75000, 65000, 55000. Three people share 150000, which is why the question says "highest salary", not "second row". Clarify in the interview: do ties count once (the usual meaning)? What should be returned if there is no second salary (NULL, not an error)?

How each approach works

Knowing the mechanics lets you explain the answer, not just recite it.

  • MAX approach. The inner query finds the top value (300000). The outer query throws that value away with salary < 300000 and takes the maximum of what is left (220000). It is two passes over the table, or two index lookups when salary is indexed.
  • OFFSET approach. SELECT DISTINCT salary makes a list of unique values, ORDER BY … DESC sorts it, OFFSET 1 skips the top value and LIMIT 1 keeps the next one. Think "sort the distinct values, skip N-1".
  • DENSE_RANK approach. The window function numbers the rows by salary, giving tied rows the same number and never leaving gaps (1, 2, 3, 4, 4, 4, 5 …). Then a plain WHERE rnk = N picks the group. The CTE is needed because a window function cannot be used directly in WHERE (it runs after it; see Logical order of a query).

The rank each tool gives to the sample salaries shows why the choice matters:

SalaryROW_NUMBERRANKDENSE_RANK

The fifth highest salary is 120000. Only DENSE_RANK = 5 finds it. RANK = 5 returns no row at all (the ranks jump from 4 to 7), and ROW_NUMBER = 5 returns one of the three 150000 earners, chosen arbitrarily. Details of the three functions are in ranking functions.

Approach 1: subquery with MAX

SELECT MAX(salary) AS second_highest
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
 second_highest
----------------
      220000.00
(1 row)

Works everywhere, returns NULL if no second value exists (MAX of nothing), and is easy to explain. It does not generalise to the Nth value without nesting more.

Approach 2: LIMIT with OFFSET on distinct values

SELECT (SELECT DISTINCT salary
        FROM employees
        ORDER BY salary DESC
        LIMIT 1 OFFSET 1) AS second_highest;

Same output. The outer SELECT ( … ) is the trick that turns "no row" into NULL; without it the query returns an empty result. Forgetting DISTINCT is the classic bug: the rows 150000, 150000, 150000 count as three positions, so the fifth "row" is 150000 while the fifth highest salary is 120000. Standard SQL spelling: OFFSET 1 ROWS FETCH FIRST 1 ROW ONLY.

Approach 3: DENSE_RANK

WITH ranked AS (
    SELECT first_name, salary,
           DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
    FROM employees
)
SELECT first_name, salary
FROM ranked
WHERE rnk = 2;
 first_name |  salary
------------+-----------
 Vikram     | 220000.00
(1 row)

This version returns the people and returns all of them when several share the Nth salary: change to rnk = 4 and you get Ananya, Priya and Rahul (150000). It is the answer to give when the interviewer asks "who earns the Nth highest?".

Nth highest salary per department

The usual follow-up. Add PARTITION BY dept_id so the numbering restarts in every department:

WITH ranked AS (
    SELECT dept_id, first_name, salary,
           DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk
    FROM employees
)
SELECT dept_id, first_name, salary
FROM ranked
WHERE rnk = 2
ORDER BY dept_id, first_name;
 dept_id | first_name |  salary
---------+------------+-----------
       1 | Priya      | 150000.00
       1 | Rahul      | 150000.00
       2 | Ananya     | 150000.00
       3 | Farhan     |  65000.00
(4 rows)

Engineering has salaries 220000, 150000, 150000, 110000 and 90000, so both 150000 earners are second. Meera is alone in her group (no department), so there is no second salary and she does not appear. A department with one distinct salary simply has no row in the result; if the question wants one row per department with NULL for "none", join the result back to departments with a LEFT JOIN.

Nth highest as a function

CREATE OR REPLACE FUNCTION nth_highest_salary(n INT)
RETURNS NUMERIC
LANGUAGE sql STABLE
AS $$
    SELECT (SELECT DISTINCT salary
            FROM employees
            ORDER BY salary DESC
            LIMIT 1 OFFSET n - 1);
$$;

SELECT nth_highest_salary(3) AS third, nth_highest_salary(20) AS twentieth;
   third   | twentieth
-----------+-----------
 160000.00 |    (null)
(1 row)

MySQL does not accept an expression after LIMIT or OFFSET inside a function, so the usual form first computes the offset in a variable:

CREATE FUNCTION getNthHighestSalary(N INT) RETURNS DECIMAL(10,2)
DETERMINISTIC
BEGIN
    SET N = N - 1;
    RETURN (SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET N);
END;

A fourth, window-free way that works on any version is the counting definition: a salary is the Nth highest if exactly N-1 distinct salaries are above it.

SELECT DISTINCT e1.salary
FROM employees e1
WHERE (SELECT COUNT(DISTINCT e2.salary) FROM employees e2 WHERE e2.salary > e1.salary) = 2;
-- 160000.00  (the third highest)

It is a correlated subquery, so it is slow on big tables; mention it as the "no window functions" answer.

Edge cases: NULLs, one value, empty table

  • NULL salaries. The sample column is NOT NULL, but in other tables it may not be. PostgreSQL sorts NULL first in DESC order, so ORDER BY salary DESC LIMIT 1 OFFSET 1 can return NULL as the "highest". Add WHERE salary IS NOT NULL (or NULLS LAST). MySQL sorts NULL last in DESC, so the same query behaves differently there. MAX ignores NULL, so approach 1 is safe.
  • Only one distinct salary. All employees earn the same: there is no second value. Approach 1 returns NULL, approach 2 (wrapped) returns NULL, approach 3 returns no rows.
  • Empty table. MAX of nothing is NULL, so approach 1 returns NULL as well.
  • N larger than the number of values. nth_highest_salary(20) returns NULL as shown. A negative N makes OFFSET fail with a "OFFSET must not be negative" error.

Rule: say what "Nth highest" means before you write SQL

Two readings exist. Nth highest value: ties count once (what this article solves). Nth row in the sorted list: ties take several places. The first is the standard interview meaning. Return the salary for a "value" question and the employees for a "who" question. State your choice in one sentence.

Convention: pick by what you need back

Need only the number, once, on any database: the MAX subquery or the wrapped OFFSET. Need the people, ties, or a per-group answer: DENSE_RANK. Need it in a reusable function or API: the wrapped OFFSET inside a function, as above. In an application, prefer one query with DENSE_RANK over loading all salaries into Java and sorting them.

Mistake: ORDER BY salary DESC LIMIT 1 OFFSET 1 without DISTINCT

Without DISTINCT it counts rows, not values: the 4th, 5th and 6th rows all hold 150000, so "fifth highest" comes out wrong, and it also gives the wrong second value whenever two people share the top salary. Rank values, not rows.

Mistake: RANK() for the Nth highest value

Wrong: no row for N = 5

SELECT salary FROM (
    SELECT salary, RANK() OVER (ORDER BY salary DESC) AS rnk
    FROM employees) t
WHERE rnk = 5;        -- 0 rows: ranks go 4, 4, 4, 7

Right: DENSE_RANK has no gaps

SELECT DISTINCT salary FROM (
    SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
    FROM employees) t
WHERE rnk = 5;        -- 120000.00

Interview angle

Give approach 1 first (always works), then the DENSE_RANK version for Nth and ties. Say what you return when there is no such salary. Variants: "Nth highest per department" (add PARTITION BY dept_id), "second highest without LIMIT or window functions" (approach 1).

Expect these follow-ups: "what if two people share the top salary?", "what if there is no second salary?", "do it for every department", and "how would you make it fast on 50 million rows?" (an index on salary lets the database walk the index from the top and stop; the counting subquery cannot use it well).

Classic query: find and delete duplicates

Find duplicates with GROUP BY … HAVING COUNT(*) > 1, see the extra rows with a window ROW_NUMBER, delete all but one copy with a self-join or window delete, and then add a UNIQUE constraint so it cannot happen again.

Duplicates enter a table in a few predictable ways: a form submitted twice, a retry after a timeout (the first request had actually succeeded), a CSV imported twice, or a missing UNIQUE constraint in the first place. The fix always has two parts: clean the existing rows, then close the door so it cannot happen again. First decide what "duplicate" means: the same email, or the same name and date of birth? That decision is the list of columns you group by.

A table with duplicates

The sample employees.email is unique, so create a scratch table that lacks the constraint, like a badly imported sign-up list:

CREATE TEMP TABLE signups (
    id    INT PRIMARY KEY,
    email VARCHAR(100) NOT NULL
);
INSERT INTO signups VALUES
    (1, 'a@x.com'), (2, 'b@x.com'), (3, 'a@x.com'),
    (4, 'c@x.com'), (5, 'b@x.com'), (6, 'a@x.com');

Finding duplicates

SELECT email, COUNT(*) AS copies
FROM signups
GROUP BY email
HAVING COUNT(*) > 1
ORDER BY email;
  email  | copies
---------+--------
 a@x.com |      3
 b@x.com |      2
(2 rows)

To see the rows themselves, with their ids, number the copies of each email. Row number 1 is the original, higher numbers are the extras:

SELECT id, email,
       ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS copy_no
FROM signups
ORDER BY email, id;
 id |  email  | copy_no
----+---------+---------
  1 | a@x.com |       1
  3 | a@x.com |       2
  6 | a@x.com |       3
  2 | b@x.com |       1
  5 | b@x.com |       2
  4 | c@x.com |       1
(6 rows)

Another way is a self join: FROM signups a JOIN signups b ON a.email = b.email AND a.id < b.id returns each duplicate pair once. For several columns together (name and date of birth), group by all of them.

How GROUP BY … HAVING finds them. The database puts rows with the same email into one group, counts each group, and HAVING keeps only the groups with a count above 1. Each returned row stands for several table rows. That is why this query tells you which values repeat but not which ids; use the window query or a join when you need the ids.

Duplicates over several columns, and near-duplicates

Group by every column that together defines a duplicate. Another scratch table, where the same person is entered twice in different cities:

CREATE TEMP TABLE contacts (id INT PRIMARY KEY, name VARCHAR(30), city VARCHAR(30));
INSERT INTO contacts VALUES
    (1,'Asha','Pune'), (2,'Asha','Pune'), (3,'Asha','Delhi'),
    (4,'Bilal','Delhi'), (5,'Bilal','Delhi');

SELECT name, city, COUNT(*) AS copies
FROM contacts
GROUP BY name, city
HAVING COUNT(*) > 1
ORDER BY name;
 name  | city  | copies
-------+-------+--------
 Asha  | Pune  |      2
 Bilal | Delhi |      2
(2 rows)

Asha in Delhi is a different group, so she is not reported. Real data is messier: 'A@x.com', 'a@x.com' and 'a@x.com ' (trailing space) are the same address to a human but three values to GROUP BY. Normalise inside the query: GROUP BY LOWER(TRIM(email)). Clean the data on the way in, too.

Deleting duplicates, keeping one row

Keep the row with the lowest id. Three ways; each deletes ids 3, 5 and 6 and leaves 1, 2 and 4. Try them inside BEGIN … ROLLBACK.

DELETE FROM signups AS s
USING signups AS keep
WHERE s.email = keep.email
  AND s.id > keep.id;
DELETE FROM signups
WHERE id NOT IN (SELECT MIN(id) FROM signups GROUP BY email);
DELETE FROM signups
WHERE id IN (
    SELECT id
    FROM (SELECT id,
                 ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn
          FROM signups) AS t
    WHERE rn > 1
);
 id |  email
----+---------
  1 | a@x.com
  2 | b@x.com
  4 | c@x.com
(3 rows)

Approach 2 is safe here because MIN(id) is never NULL; with a nullable column NOT IN is the trap from Join traps. In MySQL you cannot select from the table you delete from in a subquery (ERROR 1093), so use a join delete: DELETE s FROM signups s JOIN signups k ON s.email = k.email AND s.id > k.id;. If the table has no id column, PostgreSQL offers the hidden physical row id ctid to tell identical rows apart (DELETE FROM t WHERE ctid NOT IN (SELECT MIN(ctid) FROM t GROUP BY …)).

Another option for a huge table is to build a clean copy and swap: CREATE TABLE signups_clean AS SELECT DISTINCT ON (email) * FROM signups ORDER BY email, id;.

Before deleting, look at what would go. DELETE … RETURNING in PostgreSQL shows the rows it removed, which is handy for an audit log or a quick check inside a transaction:

BEGIN;
DELETE FROM signups s
USING signups keep
WHERE s.email = keep.email AND s.id > keep.id
RETURNING s.id, s.email;      -- 3 a@x.com, 5 b@x.com, 6 a@x.com
ROLLBACK;                     -- change to COMMIT when the list is right

Keeping the newest instead. Change the tie-breaker. With the window version, number the copies from the other end (ORDER BY id DESC) and still delete rn > 1; with MIN(id) use MAX(id). "Keep the most complete row" needs a rule such as "the row with the fewest NULLs", usually a window ORDER BY on a computed score.

Which method to choose

MethodStrengthWeakness
Self-join deleteShort; easy to reason aboutDifferent syntax in MySQL and PostgreSQL; slow without an index on the key column
NOT IN (SELECT MIN(id) …)ReadableNULL trap; MySQL error 1093
ROW_NUMBER then delete rn > 1Very flexible keep rule; the SELECT doubles as a previewNeeds MySQL 8 or PostgreSQL

With no unique column, rank the physical rows instead. This works in PostgreSQL for completely identical rows (ORDER BY ctid inside the window picks a stable survivor):

DELETE FROM signups
WHERE ctid IN (
    SELECT ctid
    FROM (SELECT ctid,
                 ROW_NUMBER() OVER (PARTITION BY email ORDER BY ctid) AS rn
          FROM signups) AS t
    WHERE rn > 1
);

The shorter MIN(ctid) form shown above needs a recent PostgreSQL (the MIN aggregate for ctid arrived in version 14); the window form works on older ones too. On a very large table, delete in batches (for example 10,000 ids at a time) so locks and the transaction stay short. PostgreSQL leaves the removed rows as dead space until VACUUM reclaims it.

Preventing duplicates

ALTER TABLE signups ADD CONSTRAINT uq_signups_email UNIQUE (email);
-- case-insensitive version:  CREATE UNIQUE INDEX uq_signups_email_lower ON signups (LOWER(email));

You can only add the constraint after the duplicates are gone, otherwise it fails with ERROR: could not create unique index "uq_signups_email" and DETAIL: Key (email)=(a@x.com) is duplicated..

If the duplicates come from a data load, let the database skip them: PostgreSQL INSERT … ON CONFLICT (email) DO NOTHING, MySQL INSERT IGNORE or ON DUPLICATE KEY UPDATE (see INSERT and upserts). In application code, catch the constraint violation (in Spring this surfaces as DataIntegrityViolationException) instead of "check then insert", which two parallel requests can both pass.

Rule: decide which copy survives, then test with SELECT first

"Keep the oldest", "keep the newest", "keep the most complete" are different queries. Run the SELECT of the rows to be removed (rn > 1), check the count, then delete inside a transaction.

Edge cases: NULLs and the unique constraint

  • GROUP BY puts all NULLs into one group, so rows with a NULL email show up as a "duplicate group". But a plain a.email = b.email self-join never matches NULL to NULL. Pick one on purpose; to match NULLs write a.email IS NOT DISTINCT FROM b.email (PostgreSQL) or a.email <=> b.email (MySQL).
  • A UNIQUE constraint does not stop repeated NULLs in PostgreSQL or MySQL. If "no two empty emails" must hold, make the column NOT NULL.
  • If the unique key is case-insensitive (usernames), enforce it with UNIQUE (LOWER(email)) as an index, not just a constraint on the raw column. MySQL's default collation is already case-insensitive, so there 'A@x.com' and 'a@x.com' clash without extra work.
  • Foreign keys that point at the removed rows block the delete (or cascade). Re-point the children to the surviving id first.

Mistake: deleting every row that has a duplicate

Wrong: removes the originals too

DELETE FROM signups
WHERE email IN (SELECT email FROM signups
                GROUP BY email HAVING COUNT(*) > 1);
-- deletes ids 1, 2, 3, 5, 6: only id 4 survives

Right: spare one row per group

DELETE FROM signups
WHERE id NOT IN (SELECT MIN(id) FROM signups GROUP BY email);
-- deletes ids 3, 5, 6

The finder query returns values; deleting by value removes every copy. Always keep one id.

Convention: verify after the cleanup

Re-run the finder query; it must return 0 rows. Compare the row count before and after (6 − 3 = 3 here). Only then add the constraint, in the same migration if possible. In real projects this goes into a Flyway or Liquibase script, run on a copy of production data first.

Mistake: SELECT DISTINCT is not a cleanup

SELECT DISTINCT hides duplicates in one query but leaves them in the table. The data problem stays, and every other query has to remember to hide them.

Interview angle

Two parts: "find duplicate emails" (GROUP BY … HAVING) and "delete duplicates keeping one" (self join or ROW_NUMBER). The follow-up is "how do you prevent them?" (unique constraint) and "what if there is no primary key?" (ctid, or create a new table with DISTINCT).

A strong answer also names the trade-offs: the self join needs an index to be fast, NOT IN has the NULL trap, ROW_NUMBER lets you choose which copy to keep, and you always preview with a SELECT and run the delete in a transaction. Another variant: "find the second occurrence only" (rn = 2).

Classic queries: higher than manager, top N per group, nothing to match

Employees earning more than their manager (a self join), the top 3 salaries per department (DENSE_RANK), and departments or customers with nothing attached (anti-joins) are the next three interview staples.

Employees who earn more than their manager

Join the table to itself: e is the employee, m is the manager, and compare their salaries.

SELECT e.first_name AS employee, e.salary,
       m.first_name AS manager,  m.salary AS manager_salary
FROM employees AS e
JOIN employees AS m ON m.emp_id = e.manager_id
WHERE e.salary > m.salary;
 employee |  salary   | manager | manager_salary
----------+-----------+---------+----------------
 Karan    | 160000.00 | Ananya  |      150000.00
(1 row)

Rahul earns exactly what his manager Priya earns, so he does not qualify (strict >). An inner join is right here: the CEO has no manager and cannot earn more than one. Approach 2 is a correlated subquery:

SELECT first_name, salary
FROM employees AS e
WHERE salary > (SELECT m.salary FROM employees AS m WHERE m.emp_id = e.manager_id);

Same result (Karan). It is fine because each employee has at most one manager, so the subquery returns at most one value.

How the self join works. The same table is used twice under two aliases, so each row of e is paired with exactly one row of m: the one whose emp_id equals its manager_id. After the join the database has one wide row per employee that has a manager; WHERE then compares the two salaries. A few of the 11 pairs:

Earning more than the department average

A close cousin: compare each row with an aggregate of its own group. The window version computes the average once per department and keeps it next to every row:

SELECT first_name, dept_id, salary
FROM (SELECT first_name, dept_id, salary,
             AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg
      FROM employees) AS t
WHERE salary > dept_avg
ORDER BY dept_id, salary DESC, first_name;
 first_name | dept_id |  salary
------------+---------+-----------
 Vikram     |       1 | 220000.00
 Priya      |       1 | 150000.00
 Rahul      |       1 | 150000.00
 Karan      |       2 | 160000.00
 Ananya     |       2 | 150000.00
 Sunita     |       3 | 120000.00
(6 rows)

The averages are 144,000 for Engineering, about 128,333 for Sales and 80,000 for HR. Meera forms a group of one, and nobody is above their own average there. The older form is a correlated subquery, WHERE salary > (SELECT AVG(salary) FROM employees x WHERE x.dept_id = e.dept_id); it gives the same rows but recomputes the average per row unless the optimizer rewrites it. Note that in the subquery version x.dept_id = e.dept_id is never true for NULL, so Meera would be dropped (her salary is compared with NULL).

Top 3 salaries in each department

Covered in ranking functions; here is the answer to give in an interview (department names included):

WITH ranked AS (
    SELECT e.dept_id, e.first_name, e.salary,
           DENSE_RANK() OVER (PARTITION BY e.dept_id ORDER BY e.salary DESC) AS pos
    FROM employees AS e
)
SELECT d.name AS department, r.first_name, r.salary
FROM ranked AS r
JOIN departments AS d ON d.dept_id = r.dept_id
WHERE r.pos <= 3
ORDER BY d.name, r.pos, r.first_name;

The inner join drops Meera (no department). Approach 2 is the correlated count of distinct higher salaries (< 3) and approach 3 the LATERAL join with LIMIT 3, both shown in the ranking article. Say clearly whether ties may return more than 3 rows.

Ties decide which function to use. Engineering has two people at 150000, so "top 2" is not clear-cut:

Choose ROW_NUMBER (with ORDER BY salary DESC, emp_id) when you need exactly N rows per group, and DENSE_RANK when "top N salaries" means N distinct values. For the special case "the single highest earner per department" PostgreSQL has a short form:

SELECT DISTINCT ON (dept_id) dept_id, first_name, salary
FROM employees
ORDER BY dept_id, salary DESC;
 dept_id | first_name |  salary
---------+------------+-----------
       1 | Vikram     | 220000.00
       2 | Karan      | 160000.00
       3 | Sunita     | 120000.00
  (null) | Meera      | 300000.00
(4 rows)

Here Meera appears, because DISTINCT ON treats NULL as its own group; the join-based answer above drops her. Decide whether people without a department belong in the report. MySQL has no DISTINCT ON; use ROW_NUMBER() … = 1.

Departments with no employees

LEFT JOIN employees e ON e.dept_id = d.dept_id
WHERE e.emp_id IS NULL;

-- 2. NOT EXISTS
SELECT d.name FROM departments d
WHERE NOT EXISTS (SELECT 1 FROM employees e WHERE e.dept_id = d.dept_id);

-- 3. NOT IN  (broken here)
SELECT d.name FROM departments d
WHERE d.dept_id NOT IN (SELECT dept_id FROM employees);

Customers who never ordered

The same pattern on the shop tables; the answer is Sara Khan and Tanvi Desai. All three forms are in Join traps. Related variants to practise: products never sold (Desk Lamp), customers with only cancelled orders (none: Kabir has a delivered one), and departments without an active project (Sales).

Choosing an anti-join form

FormNULL-safeNotes
NOT EXISTSyesClearest intent; PostgreSQL plans it as an anti-join. Default choice.
LEFT JOIN … WHERE x IS NULLyesSame plan; test a column that is never NULL in the right table (its key)
NOT IN (subquery)noOne NULL in the subquery makes it return nothing; often slower
EXCEPTyesCompares whole rows, removes duplicates; gives ids only

Rule: in an anti-join, a condition on the missing side goes in ON

When the question adds a condition ("no employee earning above 130,000"), that condition describes which right-side rows count as a match. Put it in the ON clause (or inside the NOT EXISTS). In WHERE it removes the NULL row you are looking for.

Mistake: filtering the right table in WHERE

Wrong: always returns 0 rows

SELECT d.name
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.dept_id
WHERE e.emp_id IS NULL AND e.salary > 130000;

Right: HR and Marketing

SELECT d.name
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.dept_id
                     AND e.salary > 130000
WHERE e.emp_id IS NULL
ORDER BY d.name;

In the wrong version, a row cannot have emp_id IS NULL and a salary above 130,000 at the same time. HR's best salary is 120,000, and Marketing has nobody, so the right query lists both. More on this in Join traps.

Edge cases

  • Empty result is valid. "Employees earning more than the manager" returns one row here, but on a table where nobody does, zero rows is the correct answer, not an error. Say so.
  • Strict vs non-strict. > excludes Rahul (equal to his manager); >= would include him. Ask which one is meant.
  • Missing manager. The CEO has a NULL manager_id, so the join finds no partner and drops her. If a manager row could be missing (deleted), the join also drops that employee.
  • Employees with no department vanish from any inner join to departments; use LEFT JOIN if they must appear.

Tip: state your assumptions out loud

Before writing, say: "Ties count as the same salary", "the CEO has no manager so an inner join is fine", "I return NULL when no row exists". Interviewers grade the reasoning at least as much as the SQL.

Interview angle

For each of these, be ready to give two solutions and say which you prefer: self join vs correlated subquery, DENSE_RANK vs LATERAL, NOT EXISTS vs LEFT JOIN … IS NULL. The NOT IN NULL trap is the usual follow-up.

Also practise the neighbours: "employees earning more than the department average", "highest paid per department", "customers with no orders in the last 30 days", and "managers with no reports" (a self-join anti-join on manager_id).

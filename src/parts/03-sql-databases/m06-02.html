MongoDB basics: documents, collections and queries

MongoDB stores JSON-like documents (BSON) in collections without a fixed schema; you query them with filter documents, update them with operators like $set and $inc, and analyse them with the aggregation pipeline.

The document model

A relational row is flat: columns of simple values. A MongoDB document is a nested structure of fields, arrays and sub-documents, stored as BSON (binary JSON, which adds types such as dates, 64-bit integers, decimals and ObjectId). A collection groups documents, roughly like a table, and a database groups collections. Documents in one collection need not have the same fields.

_id is the primary key. If you do not supply one, the server generates an ObjectId: a 12-byte value that includes a timestamp, so ids are roughly time-ordered and unique across servers. A single document can be up to 16 MB.

Read: find, filters, projection, sort, limit

db.restaurants.find({ city: "Pune" })                        // all Pune restaurants

db.restaurants.find(
  { city: "Pune", rating: { $gt: 4.0 } },                    // filter
  { name: 1, rating: 1, _id: 0 }                             // projection: which fields to return
).sort({ rating: -1 }).limit(5)                              // sort descending, top 5

db.restaurants.findOne({ name: "Dosa Point" })
db.restaurants.countDocuments({ isOpen: true })
[ { name: 'Dosa Point', rating: 4.6 }, { name: 'Spice Hub', rating: 4.3 } ]

The first argument is the filter document; { city: "Pune" } means equality, like WHERE city = 'Pune'. Several fields in one filter are combined with AND. The second argument is the projection (1 include, 0 exclude).

Update and delete

db.restaurants.updateOne(
  { name: "Spice Hub" },                                      // which document
  {
    $set:  { isOpen: false },                                 // set or add a field
    $inc:  { reviewCount: 1 },                                // add to a number (creates it at 0 first)
    $push: { cuisines: "Biryani" }                            // append to an array
  }
)
db.restaurants.updateMany({ city: "Pune" }, { $set: { zone: "West" } })
db.restaurants.updateOne({ name: "New Place" }, { $set: { city: "Pune" } }, { upsert: true })

db.restaurants.deleteOne({ name: "Biryani House" })
db.restaurants.deleteMany({ isOpen: false })

Always use update operators. Passing a plain document (updateOne(filter, {isOpen: false})) is rejected by updateOne (only replaceOne replaces whole documents). Single-document operations are atomic, including updates of nested fields and arrays inside that document.

Indexes

db.restaurants.createIndex({ city: 1, rating: -1 })            // compound index, same prefix rule as SQL
db.restaurants.createIndex({ name: 1 }, { unique: true })
db.restaurants.find({ city: "Pune" }).sort({ rating: -1 }).explain("executionStats")
// winningPlan: IXSCAN (index scan) good;  COLLSCAN (collection scan) = full scan, bad on big collections

MongoDB uses B-tree indexes with the same ideas as Module 5: compound indexes follow the leftmost-prefix rule; indexes speed reads and cost writes. Without an index, a query scans the whole collection.

Aggregation pipeline basics

The aggregation pipeline passes documents through stages, each transforming the stream: the MongoDB equivalent of WHERE, GROUP BY, ORDER BY and joins.

db.restaurants.aggregate([
  { $match:   { isOpen: true } },                                     // WHERE
  { $group:   { _id: "$city",                                         // GROUP BY city
                avgRating: { $avg: "$rating" },
                count:     { $sum: 1 } } },
  { $sort:    { avgRating: -1 } },                                    // ORDER BY
  { $project: { _id: 0, city: "$_id", avgRating: 1, count: 1 } }      // choose and rename fields
])
[ { avgRating: 4.45, count: 2, city: 'Pune' } ]
db.orders.aggregate([
  { $match: { status: "DELIVERED" } },
  { $lookup: { from: "restaurants",            // other collection
               localField: "restaurantId",     // field in orders
               foreignField: "_id",            // field in restaurants
               as: "restaurant" } },           // result array
  { $unwind: "$restaurant" }
])

Put $match and $sort early so they can use indexes and shrink the stream. $lookup works but is not a replacement for relational joins; if you use it all the time, the data may belong in a relational database.

Embedding vs referencing

The central design decision. Embed related data inside the document, or reference it by storing the other document's _id (like a foreign key, without enforcement).

Embed whenReference when
Data is read together (menu with restaurant)Data is used on its own, from many places
One-to-few; the child list is small and boundedOne-to-many with unbounded growth (orders of a user)
The child belongs to one parent and dies with itMany-to-many, or shared between parents
You want atomic updates of parent and child togetherThe child changes often, or the document would approach 16 MB

Rule of thumb: model the data the way the application reads it. A restaurant page needs the menu: embed it. A user's order history grows forever: store orders in their own collection with userId. Duplicating a little data (restaurant name inside an order, like the snapshot columns in Module 4) is normal in document design.

When MongoDB fits, and when not

Good fit

  • Content, catalogues and profiles with varying fields
  • Data read and written as whole documents
  • Rapidly evolving schemas in early products
  • Horizontal scaling through sharding for large volumes

Poor fit

  • Many relationships and frequent joins
  • Multi-record transactions as the main workload (money, inventory)
  • Ad-hoc reporting across entities
  • Teams that need schema enforcement everywhere (possible with JSON Schema validation, but optional)

Spring Boot supports it with Spring Data MongoDB (MongoRepository, @Document). MongoDB does support multi-document ACID transactions on replica sets, but if you need them everywhere, a relational database is simpler. Official docs: mongodb.com/docs.

Mistake: unbounded arrays inside a document

Pushing every order into user.orders makes the document grow without limit, slows each update and eventually hits 16 MB. Embed only bounded data.

Edge cases

  • No foreign keys: nothing stops a reference to a deleted document. Your code must clean up.
  • Types are per value: rating: "4.3" (string) and rating: 4.3 (number) are different, and a filter on one will not match the other.
  • A compound index must match the query's leading fields, as in SQL.

Interview angle

  • Document vs row? Nested, schema-flexible BSON versus flat, fixed-column rows.
  • Embed or reference? Embed for bounded data read together; reference for unbounded or shared data.
  • How do you do a join? $lookup in an aggregation, or better, model so you do not need one.
  • When not MongoDB? Heavy relationships, multi-record transactions and strict consistency as the main need.

CAP theorem, PACELC and eventual consistency

When the network splits a distributed database into parts that cannot talk to each other (a partition), it must choose between answering with possibly stale data (availability) or refusing to answer until it can be sure (consistency); you cannot have both during a partition.

The three properties

Consistency (C)
Every read sees the latest write, or an error. All clients see the same data at the same time, as if there were a single copy. (This is not the ACID "consistency" about constraints.)
Availability (A)
Every request to a node that is working gets a non-error response, even if it might not be the newest data.
Partition tolerance (P)
The system keeps working when the network drops or delays messages between nodes.

Why you must choose

Imagine a balance stored on two servers, in Mumbai and Delhi, each with a copy. The link between them breaks (a partition). A client changes the balance in Mumbai. Now a client reads from Delhi.

  • Choose consistency (CP): Delhi refuses to answer (an error or a timeout) because it cannot be sure its value is current. The system is consistent but not available at Delhi.
  • Choose availability (AP): Delhi answers with its old value 100. The system is available but returns stale data, and the two copies must be reconciled when the network heals.

You cannot answer correctly and always answer. That is the CAP theorem: in the presence of a partition, you pick C or A. Partitions are not optional in a real network (cables fail, packets are lost, nodes pause), so "P" is a fact of life, and the actual decision is CP or AP. When there is no partition, a system can be both consistent and available. A single-node database has no partition to worry about.

CP and AP systems

CP: consistency firstAP: availability first
During a partitionMinority side stops serving (or reads and writes fail)Every side keeps serving; copies diverge
Typical examplesZooKeeper, etcd, HBase, MongoDB with majority settings, relational databases with synchronous replicationCassandra, DynamoDB (default reads), CouchDB, DNS

Most modern products are tunable: Cassandra and DynamoDB let you ask for stronger consistency per query (at a cost in latency), and MongoDB lets you choose write and read concerns. Treat the CP/AP labels as defaults and tendencies, not as fixed properties.

Eventual consistency

Eventual consistency means: if no new writes arrive, all copies eventually become the same. In between, reads may return older values. A like count that shows 1,204 on one phone and 1,206 on another for a few seconds is fine. A bank balance that shows two different values is not. AP systems use eventual consistency, and need a rule for conflicts: last write wins (by timestamp), version vectors, or application-level merging. Read-your-writes problems (you post a comment and do not see it) are the usual user-visible symptom.

PACELC in one paragraph

CAP only talks about the rare case of a partition. PACELC extends it: if there is a Partition, choose A or C; Else (normal operation), choose between Latency and Consistency. Keeping replicas strictly in sync costs round trips, so even when everything works, a system that waits for all copies is slower than one that answers from the nearest copy. So a database is described by two choices, for example PA/EL (available during partitions and low latency otherwise, Cassandra's default style) or PC/EC (consistent always, paying latency, as in many strongly consistent stores). PACELC is a better way to talk about real trade-offs, but CAP is what interviewers ask first.

Rule: CAP applies to distributed systems during a partition

A single PostgreSQL server is not "CA"; it is simply not distributed. Don't say "pick any two of three": P is not optional, so the choice is C or A when a partition happens.

Mistake: calling a database "CP" or "AP" without context

Behaviour depends on configuration (replication factor, read and write consistency, quorum). Say "by default, and with these settings" in an interview.

Interview angle

  • Explain CAP simply. In a network partition a distributed system must choose between consistency (refuse or error) and availability (answer, possibly stale).
  • Give a CP and an AP example, and when you would use each. CP for money and coordination (etcd, relational with sync replication); AP for carts, feeds and likes (Cassandra, DynamoDB).
  • What is eventual consistency? Copies converge when writes stop; reads can be stale meanwhile.
  • PACELC? Else, when no partition, trade latency against consistency.

Replication, partitioning and sharding

Replication copies the same data to several servers for availability and read capacity; partitioning splits a big table into pieces, and sharding spreads those pieces across servers to scale writes and storage, with the shard key as the critical design choice.

Replication: primary and replicas

In primary-replica replication (older name: master-slave) one server, the primary, accepts all writes. It sends its changes (the write-ahead log in PostgreSQL, the binary log in MySQL) to one or more replicas, which apply them and serve reads.

Why replicate:

  • High availability: if the primary dies, promote a replica (failover).
  • Read scaling: reporting and read-heavy traffic go to replicas.
  • Backups and analytics on a replica without disturbing production.
  • Geography: a replica near the users.

Replication does not scale writes (one primary) and is not a backup (a bad DELETE replicates too).

Synchronous vs asynchronous

Replication lag and read-your-writes

With asynchronous replication a replica is always a little behind: replication lag, usually milliseconds but seconds or more under load. A user updates their profile (write to primary), the page reloads and reads from a replica that has not received the change yet, and shows the old data. This breaks read-your-writes consistency. Fixes:

  • Read from the primary for a short time after a write by that user (for example 5 seconds), or for the critical pages (checkout, order confirmation).
  • Route reads that must be fresh to the primary and tolerant reads (browse, search) to replicas.
  • Wait until the replica reaches the write's log position (supported by some systems).

In Spring Boot you typically configure two data sources and a routing rule, or let a proxy/managed service (such as an RDS or Cloud SQL reader endpoint) split the traffic. @Transactional(readOnly = true) is the natural hook for choosing a replica.

Failover

If the primary fails, a replica is promoted to be the new primary and clients are pointed to it. Tools such as Patroni (PostgreSQL) or managed cloud databases automate this. Risks: the promoted replica may be missing the last few async commits; and split brain, when the old primary comes back and still thinks it is the leader, so two servers accept writes. Good setups use a fencing/consensus mechanism to ensure only one primary.

Partitioning: splitting one big table

Partitioning divides a large table into smaller pieces on the same server, while queries still treat it as one table. Vertical partitioning splits columns (rarely used big columns into a side table, as in one-to-one splits). Horizontal partitioning splits rows by a rule. PostgreSQL has built-in declarative partitioning with three methods:

CREATE TABLE orders (
    id          BIGINT GENERATED ALWAYS AS IDENTITY,
    user_id     BIGINT NOT NULL,
    status      TEXT NOT NULL,
    placed_at   TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (id, placed_at)               -- the key must include the partition column
) PARTITION BY RANGE (placed_at);

CREATE TABLE orders_2026_10 PARTITION OF orders
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE orders_2026_11 PARTITION OF orders
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

-- Only the November partition is scanned (partition pruning)
EXPLAIN SELECT * FROM orders WHERE placed_at >= '2026-11-05' AND placed_at < '2026-11-10';

-- Removing a month of old data is instant, no huge DELETE
DROP TABLE orders_2026_10;
CREATE TABLE restaurants_by_region (id BIGINT, name TEXT, region TEXT NOT NULL)
    PARTITION BY LIST (region);
CREATE TABLE restaurants_west  PARTITION OF restaurants_by_region FOR VALUES IN ('Pune', 'Mumbai');
CREATE TABLE restaurants_north PARTITION OF restaurants_by_region FOR VALUES IN ('Delhi', 'Noida');

CREATE TABLE sessions (id BIGINT, user_id BIGINT NOT NULL) PARTITION BY HASH (user_id);
CREATE TABLE sessions_p0 PARTITION OF sessions FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE sessions_p1 PARTITION OF sessions FOR VALUES WITH (MODULUS 4, REMAINDER 1);
-- ... p2 and p3
MethodRuleUse
RANGEValue rangesDates: fast pruning and cheap removal of old data
LISTExplicit valuesRegion, tenant, country
HASHHash of a column modulo NEven spread when there is no natural range

Partitioning helps maintenance (drop old data, vacuum smaller pieces) and queries that filter on the partition key. It does not help queries that don't, and it adds management work. Don't partition a table until it is large (tens or hundreds of millions of rows).

Sharding: splitting across servers

Sharding is horizontal partitioning where the pieces (shards) live on different servers. When one machine can no longer handle the write load or the data volume, sharding spreads both. Each row belongs to exactly one shard, chosen by the shard key.

StrategyHowProsCons
RangeKey ranges map to shardsRange queries stay on few shards Hot spots: new ids or recent dates all hit the last shard
Hashhash(key) mod N picks the shardEven spread Range queries touch all shards; changing N moves most data
Directory / lookupA table maps key to shardFlexible placement The directory is a bottleneck and extra hop

Consistent hashing reduces data movement when you add or remove a shard: only a small part of the keys move instead of almost all. It is covered in System Design · Module 5.

Choosing a shard key
  • High cardinality with many distinct values, so data spreads out.
  • Even access: avoid a key where one value gets most of the traffic (a celebrity user, country = 'IN', or placed_at with range sharding). That shard becomes a hot spot.
  • Matches the main query: if most queries include user_id, shard by it so each query hits one shard.
  • Stable: changing a row's key means moving it between servers.
What gets harder
  • Cross-shard queries: a report over all users must ask every shard and merge the results (scatter-gather).
  • Joins and transactions across shards: expensive or unavailable; you need distributed transactions or sagas, or you design so related rows share a shard key (all of a user's orders on the user's shard).
  • Resharding: adding shards and moving data while the system runs.
  • Unique ids: sequences are per server, so use UUIDs or snowflake-style ids.
  • Operations: backups, schema changes and monitoring multiply.

Some databases shard for you (MongoDB sharded clusters, Cassandra, DynamoDB, Citus for PostgreSQL, Vitess for MySQL); with plain PostgreSQL or MySQL you build routing in the application.

Scale in order

  1. Fix queries and add indexes (Module 5).
  2. Add caching (caching patterns).
  3. Scale the server up (more CPU, RAM, faster disks).
  4. Add read replicas.
  5. Partition huge tables.
  6. Shard, as the last resort.

Rule: a replica is not a backup

Replication copies mistakes instantly. Keep real backups with point-in-time recovery and test the restore.

Mistake: sharding too early

Many systems that think they need sharding actually need an index, a cache or a replica. Sharding makes every later feature (joins, reports, transactions) harder. One well-tuned PostgreSQL server handles a very large workload.

Edge cases

  • A unique constraint in a PostgreSQL partitioned table must include the partition key, so a global unique email across partitions needs a different mechanism.
  • Replicas can apply changes in order but still lag behind each other, so two replicas may disagree briefly.
  • Long-running queries on a replica can be cancelled by replication conflicts (PostgreSQL "canceling statement due to conflict with recovery").

Interview angle

  • Replication vs sharding? Replication copies the same data (availability, read scale); sharding splits different data across servers (write and storage scale).
  • Sync vs async replication? Sync waits for a replica (no loss, slower); async does not (fast, may lose the last commits, lag).
  • How do you choose a shard key? High cardinality, even load, matches the main query, rarely changes.
  • Range vs hash sharding? Range keeps range queries local but creates hot spots; hash spreads evenly but scatters ranges.
  • Partitioning vs sharding? Same server versus many servers.

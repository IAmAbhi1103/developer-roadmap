One-to-many and one-to-one relationships in SQL

In a one-to-many relationship the foreign key goes on the "many" side; a one-to-one relationship is the same foreign key plus a UNIQUE constraint (or a shared primary key).

One-to-many: the foreign key lives on the many side

One customer places many orders, and each order belongs to one customer. The child row (the order) holds one value, so it can hold one foreign key column. The parent (the customer) could not hold "many" values in one column without breaking first normal form. That is why the foreign key goes on the "many" side.

CREATE TABLE customers (
    id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  TEXT NOT NULL,
    email TEXT NOT NULL UNIQUE
);

CREATE TABLE orders (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    placed_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    total_paise BIGINT NOT NULL CHECK (total_paise >= 0),
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers (id)
);

-- PostgreSQL does not index foreign key columns for you
CREATE INDEX idx_orders_customer_id ON orders (customer_id);

INSERT INTO customers (name, email) VALUES
    ('Asha', 'asha@example.com'),
    ('Bilal', 'bilal@example.com');
INSERT INTO orders (customer_id, total_paise) VALUES (1, 25000), (1, 18000), (2, 9900);

SELECT c.name, o.id AS order_id, o.total_paise
FROM customers c
JOIN orders o ON o.customer_id = c.id
ORDER BY o.id;
 name  | order_id | total_paise
-------+----------+-------------
 Asha  |        1 |       25000
 Asha  |        2 |       18000
 Bilal |        3 |        9900
(3 rows)

The foreign key now protects the data from both directions:

-- A child with no parent
INSERT INTO orders (customer_id, total_paise) VALUES (99, 25000);
-- ERROR:  insert or update on table "orders" violates foreign key constraint "fk_orders_customer"
-- DETAIL:  Key (customer_id)=(99) is not present in table "customers".

-- A parent that still has children
DELETE FROM customers WHERE id = 1;
-- ERROR:  update or delete on table "customers" violates foreign key constraint
--         "fk_orders_customer" on table "orders"
-- DETAIL:  Key (id)=(1) is still referenced from table "orders".

Mandatory or optional

Whether a child must have a parent is decided by NOT NULL on the foreign key column. orders.customer_id is NOT NULL: an order always has a customer, so the relationship is "exactly one" on that end. employees.manager_id or orders.coupon_id would be nullable: "zero or one". A NULL foreign key is never checked, because "no parent" is a valid state.

What happens on delete: ON DELETE actions

The foreign key also says what to do when the parent row is deleted or its key is updated.

ActionWhen the parent is deletedTypical use
NO ACTION (default)Error if children exist, checked at the end of the statementSafe default
RESTRICTError at once; cannot be deferred"Never delete a customer who has orders"
CASCADEDelete the children tooWeak entities: order lines, link rows
SET NULLSet the child's foreign key to NULLOptional links: coupon, manager
SET DEFAULTSet the foreign key to its default valueRare
 
-- Lines die with their order
CONSTRAINT fk_order_items_order FOREIGN KEY (order_id)
    REFERENCES orders (id) ON DELETE CASCADE

-- An order keeps existing if its coupon is removed
CONSTRAINT fk_orders_coupon FOREIGN KEY (coupon_id)
    REFERENCES coupons (id) ON DELETE SET NULL

-- Customers with orders can never be deleted by accident
CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id)
    REFERENCES customers (id) ON DELETE RESTRICT

One-to-one

In a one-to-one relationship each row on one side matches at most one row on the other. A real example: every users row may have one user_profiles row. Before you create a second table, ask whether you need one. If every user always has exactly one profile and the columns are small, plain columns on users are simpler and faster (no join). Split into two tables for a reason:

  • Rarely used or large columns (a long bio, a document) that you do not want on every row you read.
  • An optional group of attributes that most rows do not have (a restaurant's bank details, a seller's GST data).
  • Security: credentials or personal documents in a table with stricter permissions.
  • A subtype: columns that exist only for one kind of row.
Way 1: foreign key plus UNIQUE

The dependent table has its own key and a foreign key that is also unique. The UNIQUE is what turns "one-to-many" into "one-to-one": without it, one user could get many profile rows.

CREATE TABLE user_profiles (
    id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id    BIGINT NOT NULL,
    bio        TEXT,
    avatar_url TEXT,
    CONSTRAINT uq_user_profiles_user_id UNIQUE (user_id),
    CONSTRAINT fk_user_profiles_user FOREIGN KEY (user_id)
        REFERENCES users (id) ON DELETE CASCADE
);

INSERT INTO user_profiles (user_id, bio) VALUES (1, 'Java developer');
INSERT INTO user_profiles (user_id, bio) VALUES (1, 'A second profile');
-- ERROR:  duplicate key value violates unique constraint "uq_user_profiles_user_id"
-- DETAIL:  Key (user_id)=(1) already exists.
Way 2: shared primary key

The child's primary key is the foreign key. No extra id and no extra unique constraint are needed, because a primary key is already unique. JPA supports this with @OneToOne and @MapsId (see Spring Boot · Module 3).

CREATE TABLE user_profiles (
    user_id    BIGINT PRIMARY KEY,
    bio        TEXT,
    avatar_url TEXT,
    CONSTRAINT fk_user_profiles_user FOREIGN KEY (user_id)
        REFERENCES users (id) ON DELETE CASCADE
);
Which side holds the foreign key?

Put it on the side that depends on the other, usually the optional one: the profile points to the user, not the other way round. That gives "a user has zero or one profile; a profile belongs to exactly one user". If both sides must always exist ("every user has a profile and every profile has a user"), two foreign keys cannot be created in one step without deferred constraints, which is a good sign to merge the two tables into one.

Self-reference: a table related to itself

A foreign key may point to its own table. employees.manager_id refers to employees.id: one manager has many reports, and the top person has NULL. This is how trees and org charts are stored; see Hierarchies.

Rule: the foreign key and the key it points to must have the same type

A BIGINT id needs a BIGINT foreign key column. MySQL's InnoDB refuses mismatched types or signedness. PostgreSQL accepts some compatible pairs, but always declare them identical. Also, a foreign key must point to a primary key or a unique column.

Convention: name and index every foreign key

Name the column after the parent: customer_id references customers.id. Name the constraint fk_<child>_<parent>, as in fk_orders_customer, so error messages are readable. Create an index on every foreign key column (idx_orders_customer_id). MySQL's InnoDB creates one for you if none exists; PostgreSQL does not. Without it, "orders of this customer" and every parent delete scan the whole child table (see Module 5).

Mistake: the foreign key on the wrong side, or a missing UNIQUE

Wrong: the "one" side points to the many

-- a customer can only ever have one order!
CREATE TABLE customers (
    id       BIGINT PRIMARY KEY,
    order_id BIGINT REFERENCES orders (id)
);

Right: the "many" side points to the one

CREATE TABLE orders (
    id          BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers (id)
);

For one-to-one, the other classic slip is forgetting UNIQUE on the foreign key. The model then silently allows many rows per parent, and the JPA @OneToOne breaks later with "more than one row with the given identifier".

Edge cases

  • ON DELETE SET NULL on a NOT NULL column is a contradiction; the delete fails with a not-null violation. Make the column nullable or choose another action.
  • Two tables that reference each other (a cycle) cannot both have NOT NULL foreign keys, because neither row can be inserted first. Make one nullable, or use a DEFERRABLE INITIALLY DEFERRED constraint so the check runs at COMMIT.
  • CASCADE can ripple through many tables and lock or delete a huge number of rows in one statement. Use it for true parts of a parent (order lines), not for independent data.
  • "One-to-one" often becomes "one-to-many" later (one address becomes many). Think before adding UNIQUE, because removing it is an easy migration but fixing code that assumed one is not.

Interview angle

  • How do you implement one-to-many? A foreign key column in the "many" table that references the parent's primary key, indexed.
  • How do you enforce one-to-one? A foreign key with a UNIQUE constraint, or make the foreign key the child's primary key.
  • CASCADE vs RESTRICT vs SET NULL: delete children, block the delete, or keep the child with no parent.
  • Does PostgreSQL index a foreign key automatically? No. MySQL InnoDB does.

Many-to-many relationships and join tables

A many-to-many relationship needs a third table, the join (junction) table, with one foreign key to each side; its primary key is either the pair of foreign keys or a surrogate id plus a unique constraint on the pair.

Why two tables are not enough

A student takes many courses, and a course has many students. A foreign key in students can point to only one course; a foreign key in courses can point to only one student. Neither side can hold "many". The fix is a third table where each row says "this student takes this course".

The join table

CREATE TABLE students (
    id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL
);
CREATE TABLE courses (
    id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title TEXT NOT NULL
);

CREATE TABLE enrollments (
    student_id  BIGINT NOT NULL,
    course_id   BIGINT NOT NULL,
    enrolled_on DATE   NOT NULL DEFAULT CURRENT_DATE,
    grade       TEXT,
    PRIMARY KEY (student_id, course_id),
    CONSTRAINT fk_enrollments_student FOREIGN KEY (student_id)
        REFERENCES students (id) ON DELETE CASCADE,
    CONSTRAINT fk_enrollments_course FOREIGN KEY (course_id)
        REFERENCES courses (id) ON DELETE CASCADE
);

-- The primary key index serves "courses of a student" (leftmost column).
-- "Students of a course" needs its own index on the second column.
CREATE INDEX idx_enrollments_course_id ON enrollments (course_id);

INSERT INTO students (name) VALUES ('Asha'), ('Bilal');
INSERT INTO courses (title) VALUES ('Databases'), ('Java'), ('Spring Boot');
INSERT INTO enrollments (student_id, course_id, grade) VALUES
    (1, 1, 'A'), (1, 2, 'B'), (2, 1, 'B'), (2, 3, 'A');

The primary key (student_id, course_id) does two jobs: it makes each row unique and it forbids enrolling the same student in the same course twice. Both columns are part of the key, so both are NOT NULL automatically.

-- Courses of Asha
SELECT c.title, e.grade
FROM enrollments e
JOIN courses c  ON c.id = e.course_id
JOIN students s ON s.id = e.student_id
WHERE s.name = 'Asha';

-- Students per course, including courses nobody took
SELECT c.title, COUNT(e.student_id) AS students
FROM courses c
LEFT JOIN enrollments e ON e.course_id = c.id
GROUP BY c.title
ORDER BY c.title;
   title   | grade
-----------+-------
 Databases | A
 Java      | B
(2 rows)

    title    | students
-------------+----------
 Databases   |        2
 Java        |        1
 Spring Boot |        1
(3 rows)

Use the composite key for a pure link that can exist only once (product to category, user to role). Use a surrogate key when the same pair can legitimately appear again, or when the link row is itself referenced by other tables.

Extra columns: the association entity

The join table may carry facts about the relationship itself: enrolled_on and grade above, or quantity and unit_price on order_items. When a join table has its own columns and its own life, it is a real entity. Give it a business name (enrollments, order_items, loans) rather than student_courses. This matters in JPA: @ManyToMany works only for a pure link with two columns. As soon as the link has extra columns, map the join table as an entity with two @ManyToOne associations (see Spring Boot · Module 3).

Many-to-many to itself

A user follows many users and is followed by many. Both columns point to the same table:

CREATE TABLE follows (
    follower_id BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    followed_id BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    followed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (follower_id, followed_id),
    CHECK (follower_id <> followed_id)   -- nobody follows themselves
);
CREATE INDEX idx_follows_followed_id ON follows (followed_id);

Here the order of the pair matters (A follows B is not B follows A). For a symmetric relationship such as friendship, store each pair once with CHECK (user_a_id < user_b_id), so (3, 7) is allowed and (7, 3) is not.

Rule: a join table must forbid duplicate pairs

Always make the pair unique, by a composite primary key or a UNIQUE constraint, and make both foreign keys NOT NULL. Otherwise "enrolled twice" becomes a data bug that shows up as double counts in reports.

Convention: name it after the business fact, then index the second column

Prefer a noun the business uses (enrollments, order_items, memberships). For a plain link use both table names, such as book_authors or user_roles. A composite primary key indexes the pair in order, so add an index that starts with the second column (idx_enrollments_course_id) when you also look up from that side.

Mistake: a list of ids in one column

Wrong: comma-separated ids

CREATE TABLE students (
    id         BIGINT PRIMARY KEY,
    name       TEXT,
    course_ids TEXT   -- '1,2,5'
);
-- no foreign keys, no joins, LIKE '%2%' also matches 12 and 22

Right: one row per link

CREATE TABLE enrollments (
    student_id BIGINT REFERENCES students (id),
    course_id  BIGINT REFERENCES courses (id),
    PRIMARY KEY (student_id, course_id)
);

An array or JSONB column of ids has the same problem: the database cannot check that the ids exist, and cannot cascade deletes.

Edge cases

  • COUNT with LEFT JOIN: COUNT(*) counts the one row produced for a course with no students; COUNT(e.student_id) counts only real rows and returns 0.
  • Three-way links: a fact that relates three things (doctor, patient, clinic) is one join table with three foreign keys and a key over all three.
  • ON DELETE CASCADE on both sides is normal for a pure link: deleting a student removes only their link rows, never the courses.

In real projects

You will see this pattern everywhere: user_roles and role_permissions (security), product_categories and product_tags (a Flipkart-style catalogue), order_items (the link between orders and products, with quantity and the price at that time). Spring Data JPA models the first two with @ManyToMany and the last with an entity.

Interview angle

  • How do you model many-to-many in a relational database? A join table with a foreign key to each side; its primary key is the pair, or a surrogate id with a unique pair.
  • Where do attributes of the relationship go? Into the join table (quantity on order_items).
  • Why not store a list of ids in a column? It breaks first normal form, loses foreign key checks and cascades, and makes joins and searches slow or impossible.
  • Composite key or surrogate key for the join table? Composite for a pure unique link; surrogate when pairs can repeat or the row is referenced elsewhere.

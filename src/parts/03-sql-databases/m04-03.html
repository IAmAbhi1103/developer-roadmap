Keys: super, candidate, primary, alternate, unique, foreign, composite

A key is a column (or set of columns) that identifies rows: of all the keys that could be the identifier (candidate keys), you pick one as the primary key; the rest are alternate keys, and a foreign key points at another table's key.

Why there are so many names

Interviewers love this topic because the words overlap. They all answer one question: "which columns identify a row?" Start from one idea: a super key is any set of columns whose values are unique across the table. Everything else is a refinement of it. Take this table of employees:

CREATE TABLE employees (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email         TEXT NOT NULL UNIQUE,
    pan           CHAR(10) UNIQUE,            -- government tax id, optional
    name          TEXT NOT NULL,
    department_id BIGINT REFERENCES departments (id)
);
 id |      email       |    pan     | name  | department_id
----+------------------+------------+-------+---------------
  1 | asha@corp.in     | ABCDE1234F | Asha  |             10
  2 | bilal@corp.in    | PQRST5678K | Bilal |             10
  3 | chitra@corp.in   |            | Chitra|             20
KeyMeaningIn employees
Super keyAny set of columns that is unique per row. It may carry useless extra columns.{id}, {id, name}, {email, name}, {pan} …
Candidate keyA minimal super key: remove any column and it is no longer unique.{id}, {email}, {pan}
Primary keyThe one candidate key you choose as the official identifier. Unique and NOT NULL; one per table.id
Alternate keyA candidate key that was not chosen as the primary key.email, pan
Unique keyHow you implement an alternate key: a UNIQUE constraint. A table can have many; columns may allow NULL. UNIQUE (email), UNIQUE (pan)

Composite keyA key made of two or more columns. It can be primary, unique or foreign.PRIMARY KEY (order_id, menu_item_id) on a join table

Super key and candidate key are theory words; you never write them in SQL. You write PRIMARY KEY, UNIQUE and FOREIGN KEY. The theory tells you how to choose: list every candidate key first, then pick the primary key from them.

Primary key rules

  • It is unique and never NULL. The database builds a unique index for it.
  • A table has at most one primary key (which may be composite).
  • It should be stable: if a value can change (an email), every foreign key pointing at it must change too. ON UPDATE CASCADE hides the cost but not the risk.
  • It should be small, because every foreign key and every index entry repeats it.

Composite keys

A composite key is right when no single column identifies a row but a combination does, for example (order_id, menu_item_id) on order_items: one line per item per order. The column order matters for the index that backs it: this key serves lookups by order_id alone, but not by menu_item_id alone (see the leftmost-prefix rule in Module 5). Composite keys get awkward when other tables must reference the row: each of them repeats every column. That is a reason to prefer a single-column surrogate key for rows that other tables point at.

Rule: every table gets a primary key

A table without one allows duplicate rows that cannot be told apart, cannot be updated safely and cannot be referenced by a foreign key. JPA also requires an @Id. If you cannot find a natural identifier, add a surrogate one (next article).

Edge cases

  • MySQL's InnoDB stores the table inside the primary key index (a clustered index), so a large primary key such as a random UUID makes every secondary index bigger and inserts scatter across pages.
  • A foreign key may point to a UNIQUE column, not only to a primary key, but pointing at the primary key is clearer.
  • A composite foreign key must match the whole composite key, column for column. With MATCH SIMPLE (the default) a row with any NULL in it skips the check.
  • A unique constraint on a nullable column does not stop duplicate "missing" values. To allow only one row per non-null value, that is already what you get; to treat NULL as a value, use a partial or expression index.

Interview angle

  • Candidate key vs primary key? Candidate keys are all the minimal unique identifiers; the primary key is the one you chose. The others are alternate keys, enforced with UNIQUE.
  • Super key vs candidate key? A super key can have extra columns; a candidate key cannot lose any column and stay unique.
  • Can a table have two primary keys? No. It can have one composite primary key and many unique keys.
  • Can a primary key be a foreign key? Yes, in a shared-primary-key one-to-one, and in join tables whose composite key consists of two foreign keys.

Surrogate vs natural keys, and BIGINT vs UUID

A natural key is a real-world value (email, PAN, ISBN) used as the identifier; a surrogate key is a meaningless id generated by the database, and for most application tables a surrogate BIGINT identity primary key plus UNIQUE constraints on the natural keys is the safest choice.

The two kinds

A natural key comes from the business: an email, a mobile number, an IFSC code, an ISBN, a vehicle registration number. A surrogate key is invented by you: id = 42 tells you nothing about the row. The debate is old, but the practical answer is settled in most teams: use a surrogate primary key, and still declare the natural keys UNIQUE so the business rule is enforced.

Natural keySurrogate key
MeaningHas business meaningNone; just an identity
StabilityCan change: people change email and mobile; "permanent" ids get reissued or correctedNever changes
SizeOften long text; repeated in every foreign key and index8 bytes (BIGINT) or 16 (UUID)

Good fitTiny stable reference data: country code IN, currency INRAlmost every application entity

The classic failure of natural keys: a company uses email as the primary key, then a user asks to change it. Every orders, addresses and payments row that references it must change in the same transaction, and every other system that stored the old value breaks. With a surrogate key, you update one cell.

CREATE TABLE users (
    id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- surrogate
    email      TEXT NOT NULL,
    mobile     TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_users_email  UNIQUE (email),                    -- natural key
    CONSTRAINT uq_users_mobile UNIQUE (mobile)
);

Small code tables are the exception where a natural key is fine and even nicer, because the key is readable and stable:

CREATE TABLE currencies (
    code CHAR(3) PRIMARY KEY,          -- 'INR', 'USD'
    name TEXT NOT NULL
);
-- payments.currency CHAR(3) REFERENCES currencies (code)

Auto-generated numeric ids

In PostgreSQL write BIGINT GENERATED ALWAYS AS IDENTITY (standard SQL, PostgreSQL 10+). The older BIGSERIAL still works but is not standard. In MySQL write BIGINT AUTO_INCREMENT. GENERATED ALWAYS refuses a manual value unless you say OVERRIDING SYSTEM VALUE; GENERATED BY DEFAULT allows one. Use BIGINT, not INT: a 32-bit integer ends at about 2.1 billion, and a busy table plus gaps from rolled-back inserts can reach that sooner than you think. Changing the type on a 500-million-row table later is a long migration.

Identity values have gaps. A rolled-back transaction still consumed its numbers; sequences never reuse them. Never use the id as a "count of rows" or expect it to be gapless. If the business needs gapless numbers (invoice numbers for GST), generate them in a controlled, separate step.

BIGINT identity vs UUID

A UUID is a 128-bit identifier shown as 36 characters, such as 018f3c2e-7a41-7b3d-9c10-2f5d8a6b1e90. It can be created anywhere, without asking the database.

  • v4 is 122 random bits. Collisions are practically impossible. But values arrive in random order.
  • v7 starts with a 48-bit millisecond timestamp, then random bits. Newer values sort after older ones, so it keeps most of the uniqueness benefit and is friendly to indexes.
-- v4: built in since PostgreSQL 13
CREATE TABLE sessions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id BIGINT NOT NULL
);

-- v7: PostgreSQL 18 adds uuidv7(); on older versions generate it in the application

A reasonable default: BIGINT identity for the primary key, and when you must expose an id in a URL, add a separate random public_id UUID UNIQUE column, so the internal key stays small and fast. Choose UUIDs as primary keys when ids are created outside the database (offline apps, many services, data merged from several sources). Prefer v7 over v4 for a primary key. In MySQL InnoDB, a random v4 primary key is the worst case, because the table itself is ordered by it.

Convention: surrogate primary key, natural keys as UNIQUE

Name it id, type BIGINT, generated by the database. Every real-world identifier (email, SKU, GSTIN) becomes a UNIQUE constraint with a name such as uq_users_email. Expose a public_id if the id must be unguessable.

Mistake: using a "stable" real-world value as the primary key

Phone numbers get recycled, emails change, PAN or Aadhaar numbers must not be copied into every table (and may be restricted by law), names are not unique. If you choose a natural key, ask: can it change, can it be missing or wrong at insert time, is it private, is it short?

In real projects

Spring Data JPA entities usually have @Id @GeneratedValue(strategy = GenerationType.IDENTITY) Long id. If you use UUIDs, assign them in the application (or with a v7 generator) so the entity has its id before it is saved; see Spring Boot · Module 3.

Interview angle

  • Surrogate or natural key? Surrogate primary key for stability and size; natural keys stay UNIQUE. Natural keys are fine for tiny stable lookup tables.
  • Why not UUID everywhere? 16 bytes in every index and foreign key, hard to read, and v4 inserts fragment indexes. v7 reduces the last problem.
  • Why BIGINT over INT? 2.1 billion is reachable, and gaps use up numbers.

Functional dependencies and anomalies

A functional dependency "A → B" means that if you know A you know exactly one B; a table that mixes several such facts about different things repeats data and suffers insert, update and delete anomalies, which normalization removes.

Functional dependencies in simple words

Think of a functional dependency (FD) as "A decides B". Write it A → B. If two rows have the same A, they must have the same B. Examples from a food app:

  • restaurant_id → restaurant_name, city: knowing the restaurant tells you its name and city.
  • order_id → customer_id, order_date: one order has one customer and one date.
  • (order_id, menu_item_id) → quantity: the quantity needs both parts of the key.
  • menu_item_id → name is true; name → menu_item_id is not (two restaurants can both sell "Veg Biryani").

FDs come from the business rules, not from the data you happen to see. A sample may look like "city decides pincode" by luck. Always ask the business: "can one X ever have two Ys?" The left side of an FD that decides every other column is a key. Normalization is the process of making sure every FD in a table is justified by a key.

Kinds of dependencies

Four kinds of FD are worth naming, because the normal forms in Normalization are defined in terms of them. Take a table whose key is the pair (order_id, item):

KindExampleMeaningProblem it causes
Trivial(order_id, item) → order_idThe right side is part of the left sideNone; always true
Full(order_id, item) → qtyNeeds the whole keyNone; this is what a good non-key column looks like
Partialorder_id → customerOnly part of the key decides it Repeats on every item line; breaks 2NF
Transitiveorder_id → customer → cust_cityA non-key column decides another non-key columnRepeats the city for every order; breaks 3NF

From a few FDs you can derive others with three rules called Armstrong's axioms: reflexivity (a set determines its own subsets), augmentation (if A → B then A, C → B, C) and transitivity (if A → B and B → C then A → C). Transitivity is the one that creates "hidden" chains like order_id → customer → cust_city.

Finding the key: attribute closure

The closure of a set of columns is everything they decide, directly or through chains. A set whose closure is all columns is a key (a minimal one is a candidate key; see Keys). Take the FDs of the order sheet below (customer names are assumed unique to keep the sketch short):

  • order_id → customer, restaurant
  • customer → cust_city and restaurant → rest_city
  • (restaurant, item) → price
  • (order_id, item) → qty
  1. Start with {order_id, item}.
  2. The first FD adds customer and restaurant.
  3. The second adds cust_city and rest_city.
  4. Now restaurant and item are both known, so price joins in.
  5. The last FD adds qty. All eight columns are reached: (order_id, item) is a key.

Start with {order_id} alone and you stop after customer, restaurant and the two cities: no item, qty or price. So order_id is only part of the key, and the columns it decides are the partial dependencies.

Testing a suspected FD against data

Data can disprove an FD, never prove it. To test "customer decides cust_city", look for a customer that has two cities:

SELECT customer
FROM order_sheet
GROUP BY customer
HAVING COUNT(DISTINCT cust_city) > 1;

On the sheet below the query returns no rows, so no counter-example exists yet. That is not proof; it only means the data does not contradict the rule. After the half-finished update shown later it returns Asha: the FD is now violated by the data, which is exactly an update anomaly.

An unnormalized table and its anomalies

A beginner stores everything about an order in one wide table:

 order_id | customer | cust_city | restaurant | rest_city | item         | qty | price
----------+----------+-----------+------------+-----------+--------------+-----+------
      101 | Asha     | Pune      | Spice Hub  | Pune      | Paneer Tikka |   2 |  220
      101 | Asha     | Pune      | Spice Hub  | Pune      | Butter Naan  |   4 |   40
      102 | Bilal    | Delhi     | Dosa Point | Delhi     | Masala Dosa  |   1 |  120
      103 | Asha     | Pune      | Dosa Point | Delhi     | Masala Dosa  |   2 |  120

Customer facts repeat on every line, restaurant facts repeat on every line, and the item price repeats on every order. Three problems follow.

Update anomaly

Asha moves to Mumbai. You must change every one of her rows (101, 101, 103). Miss one and the table says she lives in two cities. The same happens when Dosa Point changes its name.

UPDATE order_sheet SET cust_city = 'Mumbai'
WHERE order_id = 101;            -- forgot order 103!
SELECT DISTINCT customer, cust_city FROM order_sheet WHERE customer = 'Asha';
 customer | cust_city
----------+-----------
 Asha     | Mumbai
 Asha     | Pune
(2 rows)
Insert anomaly

A new restaurant signs up but has no orders yet. There is no row to put it in, unless you invent a fake order with NULL in the order columns. Facts about one thing cannot exist without facts about another.

-- order_sheet has PRIMARY KEY (order_id, item)
INSERT INTO order_sheet (restaurant, rest_city) VALUES ('Tandoor Town', 'Pune');
-- ERROR:  null value in column "order_id" of relation "order_sheet" violates not-null constraint
Delete anomaly

Asha cancels order 101 and you delete both of its rows. Spice Hub appears in no other order, so the only rows that said "Spice Hub exists in Pune and sells Paneer Tikka at 220 and Butter Naan at 40" are gone too. Deleting one order destroyed a restaurant and its menu. (Deleting order 102 would be harmless here, because Dosa Point also appears in order 103: whether you lose the fact depends on luck, which is the problem.)

DELETE FROM order_sheet WHERE order_id = 101;
SELECT * FROM order_sheet WHERE restaurant = 'Spice Hub';   -- 0 rows: Spice Hub is gone
AnomalyWhat goes wrongRoot cause
UpdateOne fact stored many times; some copies change, some do notRedundancy
InsertCannot record a fact until an unrelated fact existsTwo subjects in one table
DeleteRemoving one fact removes anotherTwo subjects in one table

All three disappear when each table describes one thing and every non-key column depends on the key of that thing. The next article does this step by step.

What the fixed design looks like

Each FD gets a home. The determinant becomes the key of a table that holds exactly what it decides:

CREATE TABLE customers   (customer_id INT PRIMARY KEY,
                          name VARCHAR(50) NOT NULL, city VARCHAR(50) NOT NULL);
CREATE TABLE restaurants (restaurant_id INT PRIMARY KEY,
                          name VARCHAR(50) NOT NULL, city VARCHAR(50) NOT NULL);
CREATE TABLE menu_items  (menu_item_id INT PRIMARY KEY,
                          restaurant_id INT NOT NULL REFERENCES restaurants,
                          name VARCHAR(50) NOT NULL, price NUMERIC(8,2) NOT NULL);
CREATE TABLE orders      (order_id INT PRIMARY KEY,
                          customer_id INT NOT NULL REFERENCES customers,
                          restaurant_id INT NOT NULL REFERENCES restaurants);
CREATE TABLE order_lines (order_id INT REFERENCES orders,
                          menu_item_id INT REFERENCES menu_items,
                          qty INT NOT NULL CHECK (qty > 0),
                          PRIMARY KEY (order_id, menu_item_id));

Now each anomaly is gone:

UPDATE customers SET city = 'Mumbai' WHERE customer_id = 1;         -- Asha moves: one row
INSERT INTO restaurants VALUES (4, 'Tandoor Town', 'Pune');          -- no order needed
DELETE FROM orders WHERE order_id = 101;  -- (after deleting its lines) restaurant stays

Fully worked, with all the steps from 1NF to 3NF, in Normalization and the food-delivery design. A price copied into the order line at purchase time (as order_items.unit_price in the sample database) is not a violation: it records a different fact, "the price on that day", which must not change when the menu price does.

Rule: an FD is a statement about every possible row, not only today's rows

"city decides pincode" may be true in your ten sample rows and false in real life (one city has many pincodes). Decide FDs from the business rules and confirm them with the people who own the data. Use SQL only to hunt for counter-examples.

Mistake: using a name as the determinant

"customer decides cust_city" fails the day two customers are both called Asha. Names, emails typed by hand and phone numbers are poor determinants; a surrogate id is a safe one.

Wrong: changes every Asha

UPDATE order_sheet SET cust_city = 'Mumbai'
WHERE customer = 'Asha';

Right: the id points to one person

UPDATE customers SET city = 'Mumbai'
WHERE customer_id = 1;

Edge cases: when redundancy is acceptable

  • Read-only copies. Reporting tables and data warehouses repeat values on purpose to avoid joins. There, nobody updates a single row; the table is rebuilt from the source of truth. See Denormalization.
  • Snapshots. A price or address stored on an order as it was at that moment is history, not redundancy.
  • NULL and FDs. If restaurant → rest_city and some restaurants have no city yet, a NULL city is a "not known" value, not a second city. Keep key columns NOT NULL so FDs stay reliable.

Tip: a quick smell test

If you see the same value typed again and again down a column (a city, a product name, a category), ask "which fact does this repeat, and which key decides it?" Then move it to its own table. If a column needs "N/A" or NULL for most rows because the row is about something else, you have mixed subjects.

Interview angle

  • What is a functional dependency? A → B: each value of A is linked to exactly one value of B. A key is an A that decides every column.
  • Name the three anomalies with an example. Update: change in many places. Insert: cannot add a restaurant without an order. Delete: deleting the last order erases the restaurant.
  • Why do anomalies happen? Redundancy from storing several subjects in one table.
  • Partial vs transitive dependency? Partial: a non-key column depends on only part of a composite key (breaks 2NF). Transitive: a non-key column depends on another non-key column (breaks 3NF).
  • Is every FD a key? No. A key is a left side whose closure is every column. customer → cust_city is an FD but customer is not a key of the order sheet.
  • How do you show an FD does not hold? Find two rows with the same left side and different right sides (a GROUP BY … HAVING COUNT(DISTINCT …) > 1 query).

Normalization: 1NF, 2NF, 3NF, BCNF (and 4NF)

Normalization splits a table until every non-key column depends on "the key, the whole key, and nothing but the key": 1NF removes repeating groups, 2NF removes partial dependencies, 3NF removes transitive dependencies, and BCNF closes the last gaps.

The idea

Each normal form is a stricter test. A table in 3NF is also in 2NF and 1NF. The memory line "the key (1NF), the whole key (2NF), and nothing but the key (3NF), so help me Codd" sums it up. We will use one running example, the order sheet from the previous article, and fix it step by step.

0NF: not even first normal form

Here the sheet keeps all items of an order in one row and stores several phone numbers in one cell:

 order_id | customer | phones            | restaurant | items
----------+----------+-------------------+------------+--------------------------------
      101 | Asha     | 98100, 98200      | Spice Hub  | Paneer Tikka x2, Butter Naan x4
      102 | Bilal    | 98300             | Dosa Point | Masala Dosa x1

1NF: atomic values, no repeating groups

Rule: every cell holds one value, there are no repeating groups or arrays of values, and rows are identified by a key. Give each item its own row and keep one phone per row. The key becomes (order_id, item).

 order_id | item         | qty | price | customer | cust_city | restaurant | rest_city
----------+--------------+-----+-------+----------+-----------+------------+----------
      101 | Paneer Tikka |   2 |   220 | Asha     | Pune      | Spice Hub  | Pune
      101 | Butter Naan  |   4 |    40 | Asha     | Pune      | Spice Hub  | Pune
      102 | Masala Dosa  |   1 |   120 | Bilal    | Delhi     | Dosa Point | Delhi

Phones move to their own table customer_phones (customer, phone). The wide table is now in 1NF, but still has the anomalies from before. Look at the dependencies:

  • (order_id, item) → qty: needs the whole key. Good.
  • order_id → customer, cust_city, restaurant, rest_city: needs only part of the key.
  • item → price: needs only the other part of the key.

2NF: no partial dependency on a composite key

Rule: in 1NF, and every non-key column depends on the whole key, not on part of it. This only matters when the key is composite. Split by the part of the key that decides the column:

orders(order_id PK, customer, cust_city, restaurant, rest_city)
   101 | Asha  | Pune  | Spice Hub  | Pune
   102 | Bilal | Delhi | Dosa Point | Delhi

menu_items(item PK, price)
   Paneer Tikka | 220
   Butter Naan  |  40
   Masala Dosa  | 120

order_lines(order_id PK/FK, item PK/FK, qty)
   101 | Paneer Tikka | 2
   101 | Butter Naan  | 4
   102 | Masala Dosa  | 1

Item price is now stored once. (Later we will bring the price at order time back on purpose; see Denormalization.)

One problem is left in orders: cust_city is not decided by order_id directly, but by customer, who is decided by order_id. If Asha places ten orders, her city repeats ten times.

3NF: no transitive dependency

Rule: in 2NF, and no non-key column depends on another non-key column. A transitive dependency is a chain order_id → customer → cust_city: the city depends on the key only through the customer. Move each chain to its own table:

customers(customer_id PK, name, city)
restaurants(restaurant_id PK, name, city)
menu_items(menu_item_id PK, restaurant_id FK, name, price)
orders(order_id PK, customer_id FK, restaurant_id FK, ordered_at)
order_lines(order_id PK/FK, menu_item_id PK/FK, qty)
customer_phones(customer_id FK, phone, PK(customer_id, phone))

Every table is about one thing. Changing Asha's city is one update, a restaurant can exist with no orders, and deleting an order never deletes a customer. Most business databases stop at 3NF, and it is the level interviews expect for a design question. Here it is as SQL:

CREATE TABLE customers   (customer_id   BIGINT PRIMARY KEY, name TEXT NOT NULL, city TEXT NOT NULL);
CREATE TABLE restaurants (restaurant_id BIGINT PRIMARY KEY, name TEXT NOT NULL, city TEXT NOT NULL);
CREATE TABLE menu_items (
    menu_item_id  BIGINT PRIMARY KEY,
    restaurant_id BIGINT NOT NULL REFERENCES restaurants (restaurant_id),
    name          TEXT NOT NULL,
    price         NUMERIC(8,2) NOT NULL
);
CREATE TABLE orders (
    order_id      BIGINT PRIMARY KEY,
    customer_id   BIGINT NOT NULL REFERENCES customers (customer_id),
    restaurant_id BIGINT NOT NULL REFERENCES restaurants (restaurant_id),
    ordered_at    TIMESTAMPTZ NOT NULL
);
CREATE TABLE order_lines (
    order_id     BIGINT REFERENCES orders (order_id),
    menu_item_id BIGINT REFERENCES menu_items (menu_item_id),
    qty          INT NOT NULL CHECK (qty > 0),
    PRIMARY KEY (order_id, menu_item_id)
);

BCNF: every determinant is a key

Boyce-Codd normal form is a slightly stricter 3NF. Rule: for every functional dependency X → Y in the table, X must be a super key. 3NF allows one loophole: a non-key column may determine part of a candidate key. BCNF closes it. The loophole appears rarely and only with overlapping candidate keys. Example: riders work in zones, each dispatcher handles exactly one zone, and a rider in a zone is looked after by one dispatcher.

 rider_id | zone       | dispatcher
----------+------------+-----------
        7 | Kothrud    | Meena
        7 | Hinjewadi  | Sunil
        8 | Kothrud    | Meena
        9 | Hinjewadi  | Sunil

The dependencies are (rider_id, zone) → dispatcher and dispatcher → zone. The candidate keys are (rider_id, zone) and (rider_id, dispatcher). Now dispatcher → zone has a determinant (dispatcher) that is not a key, so BCNF fails, although 3NF passes (zone is part of a candidate key). The symptom is redundancy: "Meena handles Kothrud" is repeated, and renaming her means several updates. Decompose:

CREATE TABLE dispatchers (
    dispatcher TEXT PRIMARY KEY,
    zone       TEXT NOT NULL
);
CREATE TABLE rider_dispatchers (
    rider_id   BIGINT NOT NULL,
    dispatcher TEXT   NOT NULL REFERENCES dispatchers (dispatcher),
    PRIMARY KEY (rider_id, dispatcher)
);

The price: the original rule "a rider has one dispatcher per zone" is no longer a single constraint, so you must enforce it another way (a trigger, or application logic). This is the known trade-off: BCNF can lose dependency preservation, while 3NF decomposition never does. In practice, aim for BCNF and accept 3NF when BCNF would make a rule hard to enforce.

4NF and beyond, in one paragraph

Fourth normal form removes multi-valued dependencies. If a restaurant has several cuisines and several delivery areas, and the two lists are independent, storing them in one table (restaurant_id, cuisine, area) forces every combination: 3 cuisines and 4 areas make 12 rows, and adding a cuisine means adding 4 rows. Split into restaurant_cuisines and restaurant_areas, two independent many-to-many tables. 5NF handles rarer join dependencies and is seldom needed. If you model each many-to-many relationship as its own join table, you get 4NF for free.

Summary

FormFixesTest question
1NFRepeating groups, multi-valued cellsIs every cell a single value and every row uniquely identified?
2NFPartial dependency on part of a composite keyDoes each non-key column need the whole key?
3NFTransitive dependency via a non-key columnDoes any non-key column decide another non-key column?
BCNFA non-key determinant, with overlapping keysIs every determinant a super key?
4NFIndependent multi-valued facts in one tableAre two unrelated lists crossed together?

Rule: normalize from the dependencies, not from guesses

List the functional dependencies first, find the keys, then check each form. A table with a single-column key is automatically in 2NF (no partial dependency is possible). 3NF is the practical target for transactional (OLTP) databases.

Edge cases

  • Is a TEXT[] or JSONB column a 1NF violation? Strictly, yes when you query inside it as a list of facts. Use it for opaque data you only store and return, not for things you join or count.
  • Splitting an address into street, city, pincode is "atomic enough" if you filter by city. Atomic depends on how you use the value, not on the type.
  • pincode → city is a real transitive dependency; many teams keep both columns on the address because the data is entered together and rarely changes. That is a conscious denormalization.

Mistake: normalizing past usefulness

Splitting gender, title and country into lookup tables for a 10-row demo gives joins and no benefit. Normalize facts that change or repeat in volume (customer, product, price). A CHECK constraint is enough for a tiny, fixed list.

Interview angle

  • Explain 1NF, 2NF, 3NF with an example. Use the order sheet: items to rows (1NF), item price out of the order line (2NF), customer city out of the order (3NF).
  • 3NF vs BCNF? BCNF needs every determinant to be a super key; 3NF lets a non-key column decide part of a key. BCNF may lose a dependency.
  • Is a higher normal form always better? No. It reduces anomalies but adds joins; see Denormalization.
  • What is a partial dependency? A transitive dependency? A column depending on part of a composite key; a column depending on the key through another non-key column.

Denormalization: when and how

Denormalization means deliberately storing redundant data to avoid joins or to freeze a historical value; do it only for a measured need, and keep the copies consistent in a planned way.

Normalize first, then break the rule on purpose

A normalized schema is the correct starting point: it protects the data. Denormalization is a conscious trade: faster or simpler reads in exchange for harder writes and a risk of inconsistency. "My join looks complicated" is not a reason. A proper index and a good query fix most slow joins. Denormalize when you have a measured problem or a real business rule.

Keeping redundant data consistent

A copy is a promise to keep two places equal. Choose one mechanism and make it the only way to write:

  1. Same transaction. Update the source and the copy in one transaction in the service layer. Simple, but every writer must remember.
  2. Trigger. The database updates the counter on every insert into the child table. It cannot be bypassed, but it hides logic and slows writes.
  3. Materialized view. CREATE MATERIALIZED VIEW daily_sales AS … stores the result of a query; REFRESH MATERIALIZED VIEW rebuilds it (on a schedule). Good for reports.
  4. Periodic job. A nightly job recomputes counters from the source of truth. It also repairs any drift.
  5. Events. Publish "restaurant renamed" and let other services update their copies; consistency is eventual (see Module 6).
BEGIN;
INSERT INTO reviews (restaurant_id, user_id, stars) VALUES (3, 1, 5);
UPDATE restaurants
SET rating_count = rating_count + 1,
    rating_sum   = rating_sum + 5          -- average = rating_sum / rating_count
WHERE id = 3;
COMMIT;

Store the sum and the count, not the average: the average cannot be updated correctly from itself, but a sum and a count can.

Pros

  • Fewer joins; faster reads
  • Historical correctness (snapshots)
  • Simple queries for reports

Cons

  • Redundant storage
  • Every write must update the copies
  • Copies can drift and need repair jobs
  • More code to remember and test

Rule: one source of truth for every fact

For each denormalized value, decide which column is the truth and how the copy is refreshed. Write it in a comment on the column or in the team's design notes. A copy with no refresh plan is a bug waiting to happen.

Mistake: denormalizing before measuring

Copying customer_name onto every order "to avoid a join" gives you update anomalies from the previous article, on purpose. First check the plan with EXPLAIN ANALYZE (see Module 5) and add an index. Only denormalize if the cost is still too high.

In real projects

Transactional databases (OLTP) stay close to 3NF with a few snapshots and counters. Analytics databases (OLAP, data warehouses) often use wide, denormalized "star schemas" on purpose. Document stores such as MongoDB embed related data by design (see MongoDB).

Interview angle

  • When would you denormalize? Measured read-performance problems, derived counters and reports, and history snapshots such as price on an order line.
  • What are the risks? Inconsistent copies, slower writes, extra code.
  • Why store unit_price on order_items if it is on menu_items? Because the menu price changes and the order must keep the price actually charged.

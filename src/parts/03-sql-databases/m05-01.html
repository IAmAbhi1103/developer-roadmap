How data is stored, and why a full scan is slow

A database stores rows in fixed-size pages (blocks) on disk; without an index it must read every page of a table (a sequential scan), so cost grows with table size.

Pages, not rows

Disks and memory do not read single rows. The database divides each table file into pages (also called blocks): 8 KB in PostgreSQL, 16 KB in MySQL InnoDB. A page holds many rows. To read one row the database loads the whole page into its memory cache (the buffer pool, called shared_buffers in PostgreSQL). Reading from memory takes microseconds; reading from disk takes far longer, even on SSD. Most database tuning is about touching fewer pages.

Heap tables and clustered tables

  • PostgreSQL uses a heap: rows sit in the table file in roughly the order they were written, with no sorting. Every index is separate and points to a row by its physical address, the tuple id (page number and slot).
  • MySQL InnoDB uses a clustered index: the table is the primary key B-tree, and rows are stored in primary key order. Secondary indexes store the primary key value, so a lookup through a secondary index does a second search in the primary key tree.

This is why a large random primary key (UUID v4) hurts InnoDB more: every insert lands in a random place in the table itself. In PostgreSQL the effect is smaller, because only the index suffers.

The full table scan

To answer WHERE customer_id = 42 with no index, the database has no choice: read every page of the table, test each row, and keep the matches. This is a sequential scan (Seq Scan in PostgreSQL, "ALL" in MySQL). If the table has 1 million rows in 10,000 pages, all 10,000 pages are read to return maybe 10 rows. Doubling the table doubles the work: the cost is O(n).

A sequential scan is not always bad. For a tiny table, or a query that needs a large part of the table (say 30% of rows), reading everything in order is the cheapest plan, because sequential reads are fast and an index adds extra lookups. The goal is to avoid scans that read a lot to return a little.

Selectivity and cardinality

Cardinality is the number of distinct values in a column. Selectivity is the fraction of rows a condition keeps. WHERE email = 'x' keeps one row in a million: very selective, perfect for an index. WHERE is_active = true keeps 95% of rows: not selective, and an index does not help. A column like status with 5 values has low cardinality; email has high cardinality. Rule of thumb: an index pays off when a query reads a small fraction of the table (a few percent or less). The planner decides using the statistics it collects, see EXPLAIN.

The buffer cache hides the first lesson

A table that fits in memory scans quickly, which is why a slow query can look fine on your laptop with 10,000 rows and collapse on production with 50 million. Always test with realistic row counts; the experiment in the EXPLAIN article shows how.

Interview angle

  • What is a page/block? The fixed-size unit (8 KB in PostgreSQL, 16 KB in InnoDB) the database reads and caches; many rows per page.
  • Heap vs clustered table? PostgreSQL keeps unsorted rows and separate indexes; InnoDB stores rows inside the primary key B-tree.
  • Why is a full scan slow? It reads every page, O(n) in table size.

Indexes and B-trees

An index is a separate sorted structure (usually a B-tree) that lets the database find rows in O(log n) steps instead of scanning the table; it speeds up reads but costs space and slows every insert, update and delete.

The idea: a book's index

To find "Normalization" in a thick book you do not read every page; you look it up in the index at the back, which is sorted and points to page numbers. A database index works the same way: a sorted copy of one or more columns, with a pointer to the row. Because it is sorted, the database can binary-search it.

CREATE INDEX idx_orders_user_id ON orders (user_id);

SELECT id, total_paise FROM orders WHERE user_id = 42;   -- can now use the index

DROP INDEX idx_orders_user_id;

How a B-tree looks

The default index type everywhere is the B-tree (in practice a B+ tree). It is a balanced tree of pages: a root page, some internal pages, and leaf pages at the bottom. Each internal entry holds a key and a pointer to a child page that covers the range below it. The leaf pages hold every key in sorted order, plus the pointer to the table row, and are linked to their neighbours.

Looking up key 57: read the root (57 is between 40 and 80, go to the middle child), read that page (57 is between 50 and 65, go to its middle child), read the leaf, find 57 and its row pointer, then read the table page. That is three index pages and one table page, not 10,000.

Why lookups are O(log n)

A page holds hundreds of keys, so the tree is very wide and very shallow. With about 300 keys per page, 2 levels address 90,000 rows, 3 levels 27 million, and 4 levels 8 billion. A lookup in a table of tens of millions of rows touches about 3 or 4 pages. The top levels stay in memory, so usually only the leaf and the table page come from disk. Inserts keep the tree balanced by splitting a full page into two.

What a B-tree is good at

  • Equality: WHERE id = 5.
  • Ranges: WHERE placed_at >= '2026-11-01' AND placed_at < '2026-12-01'. Find the start in the tree, then walk the linked leaves in order. A hash index cannot do this.
  • Sorting: ORDER BY placed_at LIMIT 10 reads the first 10 leaf entries, no sort needed.
  • Prefix match: LIKE 'Pan%' is a range in disguise (with the right collation or operator class, see When an index is not used).
  • MIN/MAX: the first or last leaf entry.

What an index costs

An index is not free. Each one is another structure on disk and in memory, and the database must keep it in step with the table.

OperationEffect of each extra index
SELECT with a matching conditionMuch faster
INSERTOne more entry to add, with possible page splits
UPDATE of an indexed columnThe entry must move; in PostgreSQL this can also block cheap in-place "HOT" updates
DELETEOne more entry to mark dead and clean later
Disk and memoryOften 10–30% of the table size per index, competing for cache
PlannerMore plans to consider (a small cost)

So how many indexes is too many? There is no number. Add an index for a query you have proven slow and that runs often; drop indexes that are never used. A read-heavy reporting table can carry many; a write-heavy table (event log, payment attempts) should have few. Find unused ones with PostgreSQL's statistics view:

SELECT relname AS table_name, indexrelname AS index_name, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY relname;

Do not drop primary key or unique indexes that show zero scans: they enforce rules, not just speed.

Indexes on foreign keys

PostgreSQL does not index a foreign key column automatically. Without an index on orders.user_id, the query "orders of user 42" scans the table, and so does every DELETE on users, which must check that no order still points at that user. Index every foreign key you join on or delete through. MySQL InnoDB creates the index for you.

Rule: primary key and UNIQUE create an index; nothing else does

Declaring PRIMARY KEY or UNIQUE builds a unique B-tree index automatically. A plain foreign key, a CHECK or a column you often filter on gets none; you add it with CREATE INDEX.

Convention: add indexes in migrations, named and reviewed

Name them idx_<table>_<columns>. On a busy production PostgreSQL table, use CREATE INDEX CONCURRENTLY: it builds without blocking writes (it takes longer and cannot run inside a transaction block).

Mistake: "index every column"

It slows writes, wastes memory and the planner often ignores indexes on low-selectivity columns anyway. Start from your slow queries, not from the column list.

Interview angle

  • What is an index and how does it work? A sorted B-tree of column values with row pointers; lookups take O(log n) page reads; leaves are linked for range scans.
  • When does an index slow things down? Writes (every index is updated), disk/cache use, and low-selectivity columns where it is not used.
  • B-tree vs hash? Hash does equality only; a B-tree also handles ranges, sorting and prefixes.
  • Does a primary key have an index? Yes, a unique one, created automatically.

Unique, partial, expression and covering indexes

Beyond a plain index you can enforce uniqueness, index only some rows (partial), index a computed value (expression), or store extra columns in the index so the table is never touched (covering with INCLUDE, enabling index-only scans).

A plain B-tree index (see Indexes and B-trees) covers every row and every value of one or more columns exactly as stored. The four variants below change one of those three words: which rows (partial), what value (expression), what else is stored (covering) or what the index promises (unique). They all use the same B-tree underneath, so the reading rules from composite indexes still apply. Examples use the food-app tables users and orders from this module.

Unique index

CREATE UNIQUE INDEX is what a UNIQUE constraint uses underneath. It speeds lookups and rejects duplicates.

CREATE UNIQUE INDEX uq_users_email_lower ON users (lower(email));

INSERT INTO users (email, mobile, name) VALUES ('Asha@Example.com', '+919800000001', 'Asha');
INSERT INTO users (email, mobile, name) VALUES ('asha@example.com', '+919800000002', 'A2');
-- ERROR:  duplicate key value violates unique constraint "uq_users_email_lower"
-- DETAIL:  Key (lower(email))=(asha@example.com) already exists.

How uniqueness is enforced. On every insert or update the database searches the B-tree for the new key. If it already exists, the statement fails; if another transaction is inserting the same key at that moment, this one waits until the other commits or rolls back, then decides. That is why a unique index is the only reliable duplicate guard: a "check, then insert" in application code lets two parallel requests both pass the check. In Spring this failure arrives as DataIntegrityViolationException.

A UNIQUE constraint and a unique index do the same job. The constraint is the declaration ("this must be unique"); the index is the machinery. Use a plain unique index only when you need something a constraint cannot express: a WHERE condition (partial) or an expression. A unique index may span columns, as in UNIQUE (restaurant_id, name): the pair must be unique, not each column.

NULLs in a unique index

PostgreSQL and MySQL both allow many rows with NULL in a unique column, because NULL is never equal to NULL. PostgreSQL 15 added UNIQUE NULLS NOT DISTINCT for the case where at most one NULL is allowed. On older versions, make the column NOT NULL or build the unique index on an expression such as COALESCE(col, '').

Partial index

A partial index covers only rows that match a WHERE condition. It is smaller, cheaper to maintain, and exactly right when queries always target a small subset.

-- Only active orders: the kitchen screen reads these all day
CREATE INDEX idx_orders_active ON orders (restaurant_id)
    WHERE status NOT IN ('DELIVERED', 'CANCELLED');

-- Unique only among live rows (soft delete)
CREATE UNIQUE INDEX uq_users_email_live ON users (email) WHERE deleted_at IS NULL;

The planner uses a partial index only when the query's WHERE clause implies the index condition. MySQL does not support partial indexes.

Typical uses of a partial index:

SituationIndexWhy it helps
Soft delete with a unique ruleUNIQUE (email) WHERE deleted_at IS NULL A deleted user's email can be registered again
Queue of "pending" rows(created_at) WHERE status = 'PENDING' Millions of finished rows are not in the index at all
Rare flag(user_id) WHERE is_featuredTiny index for 1% of rows
Mostly-NULL column(coupon_code) WHERE coupon_code IS NOT NULL NULL rows add nothing and are skipped

The planner may use a partial index only when it can prove that the query's condition implies the index condition. Repeat the same condition in the query to be safe:

SELECT order_id
FROM orders
WHERE status NOT IN ('DELIVERED', 'CANCELLED')   -- same condition as the index
  AND restaurant_id = 7;

A condition that depends on a bind parameter (status = $1) may not let the planner prove the match for a cached generic plan, so check with EXPLAIN from the real application, not only from psql (EXPLAIN). When a row's update changes whether it matches, the database adds or removes its entry in the index; this is cheap.

Expression (functional) index

If a query wraps a column in a function, a normal index on the column cannot help. Index the expression:

-- Slow: the function hides the column from a plain index on email
SELECT * FROM users WHERE lower(email) = 'asha@example.com';

CREATE INDEX idx_users_email_lower ON users (lower(email));
-- Now the same query can use the index. The expression must match exactly.

-- Dates: orders placed on a given day
CREATE INDEX idx_orders_placed_date ON orders ((placed_at::date));

MySQL 8.0.13 and later supports functional key parts in the same way, written with extra parentheses.

The database computes the expression when the row is written and stores the result in the index. At query time it computes the expression on your constant and searches the index. If your query writes the expression differently, there is no match and the index is ignored. Functions used in an expression index must be IMMUTABLE (same input, same output, always). lower(email) qualifies; now() or a function that depends on the session time zone does not.

MySQL differences. From 8.0.13 MySQL accepts functional key parts, with an extra pair of parentheses: CREATE INDEX idx_email_lower ON users ((LOWER(email)));. MySQL's default collations are case-insensitive, so a plain index on email already serves email = 'Asha@Example.com' there, and the lower() trick is less common. Before 8.0.13 the workaround was a generated column plus an index on it, which also works in PostgreSQL (12+) as GENERATED ALWAYS AS (…) STORED.

Covering index and index-only scan

Normally the index finds the row pointer, then the database fetches the table page for the other columns (a heap fetch). If the index itself contains every column the query needs, the table visit is skipped. This is a covering index, and PostgreSQL shows it as Index Only Scan. INCLUDE (PostgreSQL 11+) adds payload columns that are stored in the index but not used for searching or ordering.

CREATE INDEX idx_orders_user_cover
    ON orders (user_id, placed_at DESC) INCLUDE (status, total_paise);

-- All columns are in the index: Index Only Scan
SELECT placed_at, status, total_paise
FROM orders
WHERE user_id = 42
ORDER BY placed_at DESC
LIMIT 10;

PostgreSQL keeps old row versions (MVCC, see Isolation levels), so an index-only scan must check the table's visibility map to know that a row is visible to everyone. That map is kept current by VACUUM; on a heavily updated table the scan may still visit the heap often. MySQL InnoDB gets the same effect when a secondary index includes all needed columns, because every secondary index already carries the primary key.

The plan shows whether it worked. The line to look for is Index Only Scan and, below it, Heap Fetches: 0 (or a small number):

Limit
  ->  Index Only Scan using idx_orders_user_cover on orders
        Index Cond: (user_id = 42)
        Heap Fetches: 0

Notice the split inside idx_orders_user_cover: user_id and placed_at are the key, used for searching and sorting; status and total_paise are payload that rides along in the leaf pages. If the query filters or sorts on status, put it in the key, not in INCLUDE. An INCLUDE column also takes no part in uniqueness: CREATE UNIQUE INDEX … (user_id) INCLUDE (status) still guarantees only that user_id is unique.

MySQL. There is no INCLUDE. You get a covering index by adding the extra columns to the end of the key itself, which makes the key larger. EXPLAIN then shows Using index in the Extra column. The primary key columns are always part of every InnoDB secondary index, so selecting the id is free.

Every index adds work to each INSERT, UPDATE and DELETE and takes disk and memory. Add an index for a measured slow query (EXPLAIN), not "just in case". A covering index that exists for one query is easy to forget; name it for its purpose.

Rule: the query must match the index definition

Partial: the query's WHERE must imply the index WHERE. Expression: the query must use the same expression. Covering: every column the query reads or sorts by must be in the key or in INCLUDE, and SELECT * almost never qualifies. If the shape does not match, the index is silently ignored; see When an index is not used.

Convention: name, create concurrently, verify

  • Name them by role: uq_users_email_live, idx_orders_active, idx_orders_user_cover.
  • On a live PostgreSQL table use CREATE INDEX CONCURRENTLY: it does not block writes, but cannot run inside a transaction block, and a failed run leaves an INVALID index that you must drop. MySQL builds most secondary indexes online with InnoDB; check the LOCK clause when in doubt.
  • After creating one, run EXPLAIN to confirm it is used, and drop it if it is not.

Mistake: a plain unique index on a soft-deleted table

Wrong: blocks re-registration

CREATE UNIQUE INDEX uq_users_email ON users (email);
-- a user with deleted_at set still owns the address forever

Right: unique among live rows

CREATE UNIQUE INDEX uq_users_email_live
    ON users (email) WHERE deleted_at IS NULL;

A similar slip: index email, then query WHERE lower(email) = …. The plain index cannot be used; create the expression index or store the email already lower-cased.

Edge cases

  • An expression index works only if the query uses the same expression: lower(email) is not LOWER(TRIM(email)).
  • Wide INCLUDE lists make the index big and slow to write. Include only what the hot query needs.
  • Index-only scans do not help on tables that change constantly and are rarely vacuumed.
  • A unique index treats NULLs as distinct in PostgreSQL, so many rows can have a NULL value.

Interview angle

What is a covering index? An index that holds every column a query needs, so the database answers from the index alone (index-only scan) without reading the table. What is a partial index? An index over only the rows matching a condition: smaller and cheaper, for queries that always filter on that condition.

Follow-ups: "why was my index-only scan still reading the table?" (the visibility map is stale; VACUUM it), "how do you enforce unique emails ignoring case?" (unique index on lower(email)), "why not index every column?" (write cost and memory) and "how do you add an index to a busy table?" (CREATE INDEX CONCURRENTLY).

Composite indexes and the leftmost-prefix rule

A composite index on (a, b, c) is sorted by a, then b within a, then c within b, so it can serve queries that use a leftmost prefix of its columns (a; a, b; a, b, c) but not queries that skip the first column.

Why column order matters

Think of a phone book sorted by last name, then first name. You can find "Sharma" quickly. You can find "Sharma, Asha" quickly. But you cannot find everyone called "Asha" quickly, because Ashas are spread across the whole book. A composite B-tree index is that phone book. The first column is the primary sort; each following column sorts inside it.

CREATE INDEX idx_orders_user_status_placed
    ON orders (user_id, status, placed_at);

Which queries can use (a, b, c)?

With a = user_id, b = status, c = placed_at:

Query conditionUses the index?Why
a = ?YesLeftmost prefix
a = ? AND b = ?YesPrefix of two
a = ? AND b = ? AND c = ?Yes, fullyAll three
a = ? AND c = ?Partly: seeks on a, then filters c insideb is skipped, so c cannot narrow the seek
b = ?Poorly (full index scan at best)Does not start with a
b = ? AND c = ?PoorlyDoes not start with a
c = ?PoorlyDoes not start with a
a = ? AND b > ? AND c = ?Seeks on a, b range; c only filtersAfter a range column, later columns cannot narrow the seek

This is the leftmost-prefix rule. (PostgreSQL 18 added a "skip scan" that can sometimes use the index without the first column, but do not design around it; write the index so the first column is in the query.) MySQL follows the same prefix rule.

How to choose the column order

  1. Equality columns first. Columns tested with = narrow the search to one spot in the tree.
  2. Range column last. A range (>, <, BETWEEN) or sort column goes after the equality columns, because the index can walk a range only along its last used column.
  3. Among equalities, put the most selective, or the most commonly used alone, first. A column that appears alone in other queries is a good first column, so one index serves several queries.
  4. Check the sort. If the query has ORDER BY, make the index order match so no separate sort step is needed.
-- Query: a user's delivered orders in the last 30 days, newest first
SELECT id, total_paise, placed_at
FROM orders
WHERE user_id = 42 AND status = 'DELIVERED' AND placed_at >= now() - INTERVAL '30 days'
ORDER BY placed_at DESC;

-- Best index: equalities (user_id, status), then the range/sort column
CREATE INDEX idx_orders_user_status_placed ON orders (user_id, status, placed_at);
-- A B-tree can be scanned backwards, so ASC also serves ORDER BY ... DESC.

With one index on (user_id) and another on (status), PostgreSQL can combine them (a bitmap AND) but a single composite index is faster and cheaper. Also notice: an index on (a, b) makes a separate index on (a) redundant. Drop the single-column one.

Sort order and ORDER BY

The index can return rows already sorted, which turns ORDER BY ... LIMIT 10 into reading 10 index entries. For mixed directions (ORDER BY user_id ASC, placed_at DESC) declare the same directions in the index: (user_id ASC, placed_at DESC). For a single direction, a backwards scan covers the opposite order.

Index with a join

For a join, the column used to match rows on the inner side needs an index. In the food-delivery schema the join order_items.order_id = orders.id uses the composite primary key (order_id, menu_item_id) of order_items, whose leftmost column is order_id, so no extra index is required. The reverse lookup ("all orders containing this item") filters on the second column and needs idx_order_items_menu_item_id.

Rule: the first column decides whether the index can be used

Put in the first position a column that appears in the WHERE clause of the queries you want to speed up. An index starting with a column your query never filters on is nearly useless to it.

Mistake: guessing the order from the table definition

Wrong: range column first

CREATE INDEX idx_o ON orders (placed_at, user_id);
-- WHERE user_id = 42 AND placed_at >= ...: seeks on placed_at,
-- then must test user_id on every entry in the range

Right: equality first

CREATE INDEX idx_o ON orders (user_id, placed_at);
-- seeks straight to user 42, then walks the date range

Tip: one index for several queries

List your top five queries on a table and look for columns they share as the first filter. One composite index with that column first often replaces three single-column ones.

Interview angle

  • Explain the leftmost-prefix rule. An index on (a, b, c) is sorted by a then b then c, so it helps queries filtering on a, on a and b, or on a, b and c, but not on b or c alone.
  • How do you order columns? Equality columns first, then the range or sort column last.
  • Is an index on (a, b) enough for queries on a? Yes; the extra index on (a) is redundant.

When an index is not used (and how to fix it)

An index is ignored when the query hides the column behind a function or cast, uses a leading wildcard, has low selectivity, queries a tiny table, uses OR across columns, or breaks the column order; check the plan with EXPLAIN and rewrite the query or the index.

The usual suspects

"I created an index but the query is still slow" almost always matches one of these cases. Each shows the wrong query, why, and the fix.

CauseExampleFix

Arithmetic on the columnWHERE total_paise + 100 > 5000 Move math to the constant: total_paise > 4900
Leading wildcardWHERE name LIKE '%tikka'Trigram index (pg_trgm) or full-text search
Implicit type castWHERE mobile = 9810000001 (text column, number) Use the right type: '+919810000001'

Example 1: function on the column

CREATE INDEX idx_users_email ON users (email);

EXPLAIN SELECT * FROM users WHERE lower(email) = 'asha@example.com';
-- Seq Scan on users  (Filter: (lower(email) = 'asha@example.com'::text))

-- Fix: index the expression the query uses
CREATE INDEX idx_users_email_lower ON users (lower(email));
EXPLAIN SELECT * FROM users WHERE lower(email) = 'asha@example.com';
-- Index Scan using idx_users_email_lower on users

Example 2: leading wildcard

A B-tree is sorted from the first character. LIKE 'Pan%' is a range from "Pan" to "Pao", so it can use the index (in PostgreSQL the index needs the text_pattern_ops operator class unless the database uses the C collation). LIKE '%tikka' could match anywhere, so every entry must be tested.

CREATE INDEX idx_menu_items_name_prefix ON menu_items (name text_pattern_ops);
SELECT * FROM menu_items WHERE name LIKE 'Pan%';        -- can use the index

CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_menu_items_name_trgm ON menu_items USING gin (name gin_trgm_ops);
SELECT * FROM menu_items WHERE name LIKE '%tikka%';     -- can use the trigram index

Example 3: implicit cast

-- mobile is TEXT with an index
SELECT * FROM users WHERE mobile = 9810000001;
-- ERROR:  operator does not exist: text = integer   (PostgreSQL refuses)
-- MySQL would silently convert every row's text to a number and ignore the index.

PostgreSQL is strict, but ORMs and JDBC can still send a parameter with the wrong type (a bigint parameter against a numeric column, or a varchar against a text/char mismatch in older drivers), which turns the index off. Keep Java types and column types aligned.

Example 4: low selectivity

-- 95% of restaurants are open
EXPLAIN SELECT * FROM restaurants WHERE is_open = true;
-- Seq Scan on restaurants  (Filter: is_open)
-- Reading 95% of the table through an index is slower than just scanning it.

The planner is not broken; it compared costs and chose the cheaper plan. Don't force an index in this case.

How to diagnose

  1. Run EXPLAIN (ANALYZE, BUFFERS) your_query and read the scan node.
  2. If it says Seq Scan on a big table, check which of the causes above applies.
  3. Check estimated vs actual rows. A big difference means stale statistics: run ANALYZE table_name.
  4. Fix the query or the index, then run EXPLAIN again and compare.

Edge cases

  • Sometimes the index is ignored because the planner is right. Test with SET enable_seqscan = off; in a session to see what the index plan would cost, but never leave that setting in production.
  • After a bulk load or a large delete, the planner may use old statistics. ANALYZE fixes it; autovacuum does this in the background but not instantly.
  • A query that returns a large fraction of rows can legitimately do a Seq Scan even with a good index.

Mistake: adding an index without looking at the plan

Adding an index and assuming it works is the most common tuning error. Always run EXPLAIN before and after.

Interview angle

Aggregate functions: COUNT, SUM, AVG, MIN, MAX

An aggregate function reads many rows and returns one value. The five basic ones are COUNT, SUM, AVG, MIN and MAX, and all of them except COUNT(*) silently ignore NULL.

What they do

FunctionReturnsWorks onOn an empty set
COUNT(*)number of rowsrows0
COUNT(col)number of rows where col is not NULLany type0
SUM(col)totalnumbersNULL
AVG(col)mean of the non-NULL valuesnumbersNULL
MIN(col), MAX(col)smallest / largestnumbers, text, datesNULL

Without GROUP BY, an aggregate collapses the whole table (or the rows that pass WHERE) into a single row.

SELECT COUNT(*)                 AS employees,
       SUM(salary)              AS payroll,
       ROUND(AVG(salary), 2)    AS avg_salary,
       MIN(salary)              AS lowest,
       MAX(salary)              AS highest,
       MIN(hire_date)           AS first_hire
FROM employees;
 employees |  payroll   | avg_salary | lowest  | highest   | first_hire
-----------+------------+------------+---------+-----------+------------
        12 | 1645000.00 |  137083.33 | 55000.00 | 300000.00 | 2015-04-01
(1 row)

You cannot mix an aggregate with a plain column in the same SELECT unless you group: SELECT first_name, MAX(salary) FROM employees fails with ERROR: column "employees.first_name" must appear in the GROUP BY clause or be used in an aggregate function. The database cannot know which name to show next to the maximum. (Finding the person with the maximum is a different query, see Nth highest salary.)

COUNT(*) vs COUNT(col) vs COUNT(DISTINCT col)

This is the most asked aggregate question. COUNT(*) counts rows. COUNT(col) counts rows where the column has a value. COUNT(DISTINCT col) counts different non-NULL values. They only differ when there are NULLs or repeats.

SELECT COUNT(*)                AS all_rows,
       COUNT(dept_id)          AS with_dept,
       COUNT(DISTINCT dept_id) AS distinct_depts
FROM employees;

SELECT COUNT(*) AS customers, COUNT(phone) AS with_phone FROM customers;
 all_rows | with_dept | distinct_depts
----------+-----------+----------------
       12 |        11 |              3
(1 row)

 customers | with_phone
-----------+------------
         7 |          4
(1 row)

Meera has no department, so COUNT(dept_id) is 11. Five employees share department 1, six share 2 and 3, but only three different ids exist. COUNT(1) and COUNT(*) are the same thing and equally fast; write COUNT(*).

NULLs are ignored

Aggregates skip NULL values. That is usually what you want, but it changes averages:

SELECT ROUND(AVG(x), 2)              AS avg_ignoring_null,
       ROUND(AVG(COALESCE(x, 0)), 2) AS avg_null_as_zero,
       SUM(x)              AS total,
       COUNT(x)            AS counted
FROM (VALUES (10), (20), (NULL)) AS t(x);
 avg_ignoring_null | avg_null_as_zero | total | counted
-------------------+------------------+-------+---------
             15.00 |            10.00 |    30 |       2
(1 row)

Decide what a missing value means. A missing rating should not count as zero stars; a missing sale probably does count as zero sales. Also remember: SUM of an empty set is NULL, not 0, while COUNT of an empty set is 0.

SELECT SUM(salary) AS total, COALESCE(SUM(salary), 0) AS safe_total, COUNT(*) AS n
FROM employees WHERE dept_id = 99;
  total   | safe_total | n
----------+------------+---
 (null)   |          0 | 0
(1 row)

AVG, integers and ROUND

AVG of an integer column returns NUMERIC in PostgreSQL (and a decimal in MySQL), so it does not truncate. The trap is doing the division yourself with two integers:

SELECT SUM(hours_per_week)                       AS total_hours,
       SUM(hours_per_week) / COUNT(*)            AS wrong_int_division,
       ROUND(AVG(hours_per_week), 2)             AS avg_hours,
       ROUND(SUM(hours_per_week)::NUMERIC / COUNT(*), 2) AS avg_by_hand
FROM employee_projects;
 total_hours | wrong_int_division | avg_hours | avg_by_hand
-------------+--------------------+-----------+-------------
         260 |                 23 |     23.64 |       23.64
(1 row)

ROUND(x, 2) rounds to two decimals; ROUND(x) to a whole number; a negative second argument rounds to tens or hundreds. In PostgreSQL ROUND(value, digits) needs a NUMERIC (cast a DOUBLE PRECISION first: ROUND(x::NUMERIC, 2)). Casting is covered in Type casting.

Aggregating expressions, and listing values

The argument can be any expression. Revenue is quantity times price per line:

SELECT SUM(quantity * unit_price) AS revenue_all_orders FROM order_items;
SELECT STRING_AGG(first_name, ', ' ORDER BY first_name) AS engineers
FROM employees WHERE dept_id = 1;
 revenue_all_orders
--------------------
           21924.00
(1 row)

                engineers
-----------------------------------------
 Arjun, Divya, Priya, Rahul, Vikram
(1 row)

STRING_AGG (PostgreSQL) glues values into one text; MySQL calls it GROUP_CONCAT(first_name ORDER BY first_name SEPARATOR ', '). Other useful PostgreSQL aggregates: BOOL_AND, BOOL_OR, ARRAY_AGG, JSONB_AGG. COUNT(DISTINCT x), SUM(DISTINCT x) work too, but SUM(DISTINCT salary) adds each different salary only once, which is rarely what you mean.

Rule: no aggregates in WHERE

WHERE salary > AVG(salary) fails with ERROR: aggregate functions are not allowed in WHERE. WHERE runs before any group exists. Use a subquery (salary > (SELECT AVG(salary) FROM employees)) or HAVING.

Mistake: COUNT(col) when you meant COUNT(*)

"How many customers do we have?" with COUNT(phone) answers 4, not 7. Count a column only when you want to skip its NULLs; otherwise use COUNT(*).

Edge cases

  • With no GROUP BY, an aggregate query always returns exactly one row, even over zero input rows. With GROUP BY and no input rows, you get zero rows.
  • SUM of an INT column returns BIGINT in PostgreSQL, and SUM of BIGINT returns NUMERIC, so overflow is rare. MIN and MAX work on text (alphabetical) and dates.
  • Nesting aggregates, MAX(AVG(x)), is an error. Aggregate in a subquery, then aggregate again.

Interview angle

"Difference between COUNT(*), COUNT(col) and COUNT(DISTINCT col)?" and "what do aggregates do with NULL?" are near-certain. A strong answer also mentions that SUM of nothing is NULL (use COALESCE) and that AVG(COALESCE(x,0)) differs from AVG(x).

GROUP BY and HAVING

GROUP BY splits rows into groups and runs the aggregates once per group; HAVING then filters the groups. WHERE filters rows before grouping, HAVING filters groups after.

How GROUP BY works

Think of it as sorting the rows into piles by the grouping columns, then collapsing each pile into one row. Every other column in the SELECT must either be in the GROUP BY or be inside an aggregate.

SELECT dept_id,
       COUNT(*)              AS headcount,
       ROUND(AVG(salary), 2) AS avg_salary
FROM employees
GROUP BY dept_id
ORDER BY dept_id;
 dept_id | headcount | avg_salary
---------+-----------+------------
       1 |         5 |  144000.00
       2 |         3 |  128333.33
       3 |         3 |   80000.00
  (null) |         1 |  300000.00
(4 rows)

NULL is treated as one group: all NULLs go together, although NULL is never equal to NULL in a comparison. To show the department name instead of the id you need a join (Joins); you then group by the id and the name, or only by the id (see the next section).

The GROUP BY rules

  • Every selected column that is not inside an aggregate must appear in GROUP BY. Otherwise PostgreSQL says column "e.first_name" must appear in the GROUP BY clause or be used in an aggregate function.
  • Exception: if you group by a table's primary key, PostgreSQL lets you select the other columns of that table, because they are determined by the key. GROUP BY d.dept_id allows d.name.
  • MySQL enforces the same rule through the ONLY_FULL_GROUP_BY mode, on by default since MySQL 5.7.5 (ERROR 1055). Older setups with the mode off return an arbitrary value from the group, a silent bug. Keep the mode on.
  • You can group by an expression or several columns. Write the expression or use the alias (PostgreSQL and MySQL both allow an alias in GROUP BY, standard SQL does not).
  • The order of the output rows is not guaranteed. Add ORDER BY.

Grouping by several columns and by expressions

Each distinct combination becomes one group. Orders per customer and status:

SELECT customer_id, status, COUNT(*) AS orders
FROM orders
GROUP BY customer_id, status
ORDER BY customer_id, status;
 customer_id |  status   | orders
-------------+-----------+--------
           1 | DELIVERED |      2
           1 | SHIPPED   |      1
           2 | DELIVERED |      1
           2 | PLACED    |      1
           3 | CANCELLED |      1
           3 | DELIVERED |      1
           4 | DELIVERED |      1
           5 | PLACED    |      1
           5 | SHIPPED   |      1
(9 rows)

Grouping by an expression: how many people were hired per year, keeping only years with more than one hire (that is HAVING, next).

SELECT EXTRACT(YEAR FROM hire_date) AS hire_year, COUNT(*) AS hires
FROM employees
GROUP BY EXTRACT(YEAR FROM hire_date)
HAVING COUNT(*) > 1
ORDER BY hire_year;

(2 rows)

HAVING: filtering groups

HAVING is WHERE for groups. Its condition can use aggregates, which WHERE cannot. Departments with an average salary above 100,000:

SELECT dept_id, ROUND(AVG(salary), 2) AS avg_salary
FROM employees
GROUP BY dept_id
HAVING AVG(salary) > 100000
ORDER BY dept_id;
 dept_id | avg_salary
---------+------------
       1 |  144000.00
       2 |  128333.33
  (null) |  300000.00
(3 rows)

PostgreSQL does not allow the alias in HAVING (HAVING avg_salary > … fails); repeat the expression. MySQL allows the alias.

WHERE vs HAVING

WHEREHAVING

Use both together. Question: which departments have at least two people earning 100,000 or more? The salary test is a row condition (WHERE); the "at least two" is a group condition (HAVING).

SELECT dept_id, COUNT(*) AS high_earners
FROM employees
WHERE salary >= 100000           -- row filter: runs first
GROUP BY dept_id
HAVING COUNT(*) >= 2             -- group filter: runs after grouping
ORDER BY dept_id;
 dept_id | high_earners
---------+--------------
       1 |            4
       2 |            2
(2 rows)

Step by step: WHERE drops Divya, Neha, Farhan and Isha (under 100,000); the rest are grouped into dept 1 (4 rows), dept 2 (2), dept 3 (Sunita, 1) and NULL (Meera, 1); HAVING keeps groups with two or more. Put a row condition in HAVING and it still works (HAVING dept_id = 1), but it is slower and confusing. Filter rows in WHERE.

Another everyday pattern: orders with a total above 4,000, from order_items:

SELECT order_id, SUM(quantity * unit_price) AS order_total
FROM order_items
GROUP BY order_id
HAVING SUM(quantity * unit_price) > 4000
ORDER BY order_id;
 order_id | order_total
----------+-------------
        2 |     4097.00
        7 |     4298.00
(2 rows)

Rule: SELECT may only contain grouped columns and aggregates

Think "one output row per group". Anything else has several possible values per group and the database refuses to guess.

Mistake: aggregates in WHERE

Wrong: aggregate in WHERE

SELECT dept_id FROM employees
WHERE COUNT(*) > 2 GROUP BY dept_id;
-- ERROR:  aggregate functions are not allowed in WHERE

Right: aggregate in HAVING

SELECT dept_id FROM employees
GROUP BY dept_id HAVING COUNT(*) > 2;

Edge cases

  • HAVING without GROUP BY treats the whole result as one group: SELECT COUNT(*) FROM employees HAVING COUNT(*) > 100 returns zero rows.
  • Departments with no employees (Marketing) do not appear in a GROUP BY on employees; they have no rows. To list them with a count of 0 you need a LEFT JOIN, see Join traps.
  • Join first, then group: if the join multiplies rows, the counts and sums multiply too.

Interview angle

"What is the difference between WHERE and HAVING?" Answer with the logical order: WHERE filters rows before grouping and cannot use aggregates; HAVING filters groups after aggregation. Then give one query using both. Often followed by "find departments with more than N employees" or "duplicates" (GROUP BY … HAVING COUNT(*) > 1, see Duplicates).

Conditional aggregation, FILTER and ROLLUP

Put a CASE (or PostgreSQL's FILTER) inside an aggregate to count or sum only some rows, and you can build several measures, or a pivot table, in a single pass. ROLLUP adds subtotal and grand-total rows.

Why it is useful

A report often needs several counts side by side: total orders, delivered orders, cancelled orders. Running one query per number is slow and clumsy. Conditional aggregation computes them all in one scan. The idea: the aggregate only sees the rows (or values) that your condition lets through.

SELECT COUNT(*)                                          AS all_orders,
       COUNT(*) FILTER (WHERE status = 'DELIVERED')      AS delivered,
       SUM(CASE WHEN status = 'CANCELLED' THEN 1 ELSE 0 END) AS cancelled,
       COUNT(CASE WHEN status IN ('PLACED', 'SHIPPED') THEN 1 END) AS open_orders
FROM orders;
 all_orders | delivered | cancelled | open_orders
------------+-----------+-----------+-------------
         10 |         5 |         1 |           4
(1 row)

Three equivalent spellings appear here:

  • COUNT(*) FILTER (WHERE …) is the standard, readable form. PostgreSQL has it; MySQL does not.
  • SUM(CASE WHEN cond THEN 1 ELSE 0 END) works everywhere. This is the portable version.
  • COUNT(CASE WHEN cond THEN 1 END) relies on COUNT ignoring NULL: the CASE returns NULL when the condition is false (no ELSE), and NULL is not counted. Beginners write COUNT(CASE … ELSE 0 END) and wonder why every row is counted: 0 is not NULL.

How it works, step by step

  1. The database reads each row once (after WHERE has removed rows, and with GROUP BY it decides which group the row belongs to).
  2. For every aggregate in the SELECT list it checks that aggregate's own condition: the FILTER predicate, or the value of the CASE expression.
  3. If the row passes, its value goes into that aggregate's running state (a counter, a sum). If not, that one aggregate skips the row. The other aggregates still see it.
  4. When the group ends, each aggregate returns its result. One scan gives many answers.

What an aggregate returns when no row passes its condition depends on the aggregate, and this causes most surprises:

SpellingPostgreSQLMySQLIf no row matches
COUNT(*) FILTER (WHERE c)yesno0
SUM(x) FILTER (WHERE c)yesnoNULL
SUM(CASE WHEN c THEN 1 ELSE 0 END)yesyes0
COUNT(CASE WHEN c THEN 1 END)yesyes0
SUM(CASE WHEN c THEN x END)yesyesNULL
AVG(CASE WHEN c THEN x END)yesyesNULL

A percentage is the classic use: divide a conditional count by the total count. Write 100.0, not 100, so the division is not an integer division.

SELECT ROUND(100.0 * COUNT(*) FILTER (WHERE status = 'DELIVERED') / COUNT(*), 1)
           AS delivered_pct
FROM orders;
 delivered_pct
---------------
          50.0
(1 row)

Per group

Combined with GROUP BY it answers "for each department, how many high earners?" without hiding departments that have none:

SELECT dept_id,
       COUNT(*)                                          AS headcount,
       SUM(CASE WHEN salary >= 150000 THEN 1 ELSE 0 END)   AS earn_150k_plus,
       ROUND(AVG(salary) FILTER (WHERE salary >= 100000), 0) AS avg_of_high
FROM employees
GROUP BY dept_id
ORDER BY dept_id;
 dept_id | headcount | earn_150k_plus | avg_of_high
---------+-----------+----------------+-------------
       1 |         5 |              3 |      157500
       2 |         3 |              2 |      155000
       3 |         3 |              0 |      120000
  (null) |         1 |              1 |      300000
(4 rows)

Department 1 high earners (at least 100,000): 220000, 150000, 150000, 110000, average 157,500. Department 3 has one (Sunita, 120,000), so the average is 120,000.

Pivoting rows into columns

A pivot turns values of a column into column headings. SQL has no simple pivot command in PostgreSQL or MySQL, so you write one conditional aggregate per output column. Revenue per product category by order status, a small report:

SELECT p.category,
       SUM(oi.quantity * oi.unit_price) FILTER (WHERE o.status = 'DELIVERED') AS delivered,
       SUM(oi.quantity * oi.unit_price) FILTER (WHERE o.status = 'SHIPPED')   AS shipped,
       SUM(oi.quantity * oi.unit_price) FILTER (WHERE o.status = 'PLACED')    AS placed
FROM order_items oi
JOIN orders   o ON o.order_id   = oi.order_id
JOIN products p ON p.product_id = oi.product_id
GROUP BY p.category
ORDER BY p.category;
  category   | delivered | shipped | placed
-------------+-----------+---------+---------
 Electronics |   6793.00 | 5494.00 | 1098.00
 Home        |    450.00 |  (null) |  900.00
 Stationery  |   2910.00 |  (null) |  780.00
(3 rows)

(Joins are explained in the next articles; read this one again afterwards.) The cancelled order 4 is left out of all three columns on purpose. Wrap a column in COALESCE(…, 0) to show 0 instead of NULL. The same pivot idea shows up again in Pivot and median.

Subtotals with ROLLUP

GROUP BY ROLLUP (category) adds an extra row with the grand total. With two columns it also adds a subtotal per first column. The added rows show NULL in the rolled-up columns.

SELECT category,
       COUNT(*)   AS products,
       SUM(stock) AS units_in_stock
FROM products
GROUP BY ROLLUP (category)
ORDER BY category;
  category   | products | units_in_stock
-------------+----------+----------------
 Electronics |        3 |            465
 Home        |        2 |             60
 Stationery  |        2 |           1300
 (null)      |        7 |           1825
(4 rows)

MySQL spells it GROUP BY category WITH ROLLUP. The last row is the grand total. If a real group can also be NULL, you cannot tell it from the total row; the function GROUPING(category) returns 1 on the added rows (PostgreSQL and MySQL 8). Related: CUBE (all combinations) and GROUPING SETS (the exact set of groupings you list), both PostgreSQL.

Filtering groups by a conditional measure

A conditional aggregate can sit in HAVING too. "Customers who have at least one delivered order and at least one order still open" needs two conditions on the same group, which a plain WHERE cannot express:

SELECT customer_id,
       COUNT(*) FILTER (WHERE status = 'DELIVERED')            AS delivered,
       COUNT(*) FILTER (WHERE status IN ('PLACED', 'SHIPPED')) AS open_orders
FROM orders
GROUP BY customer_id
HAVING COUNT(*) FILTER (WHERE status = 'DELIVERED') >= 1
   AND COUNT(*) FILTER (WHERE status IN ('PLACED', 'SHIPPED')) >= 1
ORDER BY customer_id;
 customer_id | delivered | open_orders
-------------+-----------+-------------
           1 |         2 |           1
           2 |         1 |           1
(2 rows)

Customer 3 has a delivered order but only a cancelled one besides it, and customer 5 has open orders but nothing delivered, so both are left out.

ROLLUP with two columns

With ROLLUP (a, b) you get the detail rows (a, b), a subtotal for each a, and one grand total. The order of the columns matters: the grouping is rolled up from right to left. Units sold per product, with a subtotal per category:

SELECT p.category, p.name,
       COALESCE(SUM(oi.quantity), 0) AS units
FROM products p
LEFT JOIN order_items oi ON oi.product_id = p.product_id
GROUP BY ROLLUP (p.category, p.name)
ORDER BY p.category NULLS LAST, p.name NULLS LAST;
  category   |         name         | units
-------------+----------------------+-------
 Electronics | Mechanical Keyboard  |     3
 Electronics | USB-C Cable          |     8
 Electronics | Wireless Mouse       |     5
 Electronics | (null)               |    16
 Home        | Desk Lamp            |     0
 Home        | Water Bottle         |     3
 Home        | (null)               |     3
 Stationery  | Gel Pen Pack         |    17
 Stationery  | Notebook A5          |    18
 Stationery  | (null)               |    35
 (null)      | (null)               |    54
(11 rows)

The LEFT JOIN keeps Desk Lamp, which was never sold. A (null) in name marks a subtotal row, and NULL in both columns marks the grand total. To print readable labels, test with GROUPING, not with IS NULL:

Wrong: a real NULL looks like a total

SELECT COALESCE(category, 'TOTAL') AS category,
       COUNT(*) AS products
FROM products
GROUP BY ROLLUP (category);

Right: GROUPING() is 1 only on added rows

SELECT CASE WHEN GROUPING(category) = 1 THEN 'TOTAL'
            ELSE category END AS category,
       COUNT(*) AS products
FROM products
GROUP BY ROLLUP (category);

The wrong version works on the sample data, because no category is NULL. It breaks the day a product with a NULL category is added: that group would also be labelled TOTAL.

ROLLUP is shorthand for a particular list of GROUPING SETS, and the database still reads the table only once. The alternative, a UNION ALL of one GROUP BY per level, reads it once per level and is much longer. In MySQL, write GROUP BY p.category, p.name WITH ROLLUP.

Convention: prefer FILTER, fall back to CASE

In PostgreSQL code FILTER (WHERE …) reads best. In code that must also run on MySQL (or that a JPA native query shares between databases) use SUM(CASE WHEN …).

Rule: the condition belongs inside the aggregate, not in WHERE

Use WHERE for conditions that apply to every measure in the query. Use FILTER or CASE for conditions that apply to one measure. Mix them freely: first WHERE shrinks the rows, then each aggregate filters further.

Edge cases

  • Empty group, empty result. SUM(…) FILTER and SUM(CASE … END) give NULL when nothing matches. Wrap them in COALESCE(…, 0) for reports, or use ELSE 0 if zero is the right answer.
  • NULLs in the tested column. A condition like status = 'DELIVERED' is unknown (not true) for a NULL status, so the row is simply not counted. It is not counted as "not delivered" either; that is why the sums of all buckets may be lower than COUNT(*).
  • Ties and overlaps. Buckets such as salary >= 100000 and salary >= 150000 overlap, so a row counts in both. Make ranges exclusive when the columns must add up to the total.
  • MySQL shortcut. MySQL treats a comparison as 0 or 1, so SUM(status = 'CANCELLED') works there. PostgreSQL rejects it (a boolean cannot be summed); write the CASE or FILTER form instead.

Mistake: ELSE 0 inside AVG (and COUNT)

A zero is a value, so it takes part in the average. Average salary of people earning at least 100,000:

Wrong: the 4 low earners drag it down

SELECT AVG(CASE WHEN salary >= 100000 THEN salary ELSE 0 END)
FROM employees;          -- 113333.33  (1,360,000 / 12)

Right: skipped rows give NULL

SELECT AVG(CASE WHEN salary >= 100000 THEN salary END)
FROM employees;          -- 170000.00  (1,360,000 / 8)
-- PostgreSQL: AVG(salary) FILTER (WHERE salary >= 100000)

The same trap makes COUNT(CASE … ELSE 0 END) count every row. Use ELSE 0 only with SUM.

In real projects

Dashboards and admin screens ("orders today: placed, shipped, delivered, cancelled") usually run one conditional-aggregate query instead of four counts, which saves round trips and gives a consistent snapshot. In a Spring Data repository this is typically a native query returning a projection interface.

Mistake: using WHERE when you need several measures

If you put WHERE status = 'DELIVERED' on the query, the other columns (cancelled, open) become zero. A WHERE limits all measures; a FILTER limits one.

Interview angle

"Show orders per status as columns" or "count male and female employees in one row per department" are pivot questions: answer with SUM(CASE WHEN … THEN 1 ELSE 0 END) per output column plus GROUP BY. Mention FILTER as the PostgreSQL form.

Likely follow-ups: "what does SUM return when no row matches?" (NULL, so use COALESCE), "why does COUNT(CASE … ELSE 0 END) count everything?" (0 is not NULL), and "how do you add a total row?" (ROLLUP, with GROUPING() to label it).

Logical order of a query

You write SELECT first, but the database evaluates a query in a different order: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, then LIMIT. That order explains almost every "why can't I use this here?" error.

The order

  1. FROM / JOIN: find the tables and combine them into one big set of rows.
  2. WHERE: throw away rows that do not match. No groups and no select aliases exist yet.
  3. GROUP BY: collapse the remaining rows into groups.
  4. HAVING: throw away groups. Aggregates are available now.
  5. SELECT: compute the output columns, expressions and aliases. Window functions (Module 3) are computed here too.
  6. DISTINCT: remove duplicate output rows.
  7. ORDER BY: sort the result. The select aliases exist now.
  8. LIMIT / OFFSET (FETCH FIRST): cut the sorted result.

This is the logical order, the meaning of the query. The optimizer is free to reorder the real work (it uses an index, filters early, joins in a smarter order) as long as the answer is the same.

What the order explains

SELECT   dept_id,                              -- 5. compute columns
         ROUND(AVG(salary), 0) AS avg_sal      --    alias avg_sal is born here
FROM     employees                             -- 1. read table
WHERE    hire_date >= '2018-01-01'             -- 2. keep rows hired from 2018
GROUP BY dept_id                               -- 3. one group per department
HAVING   COUNT(*) >= 2                         -- 4. keep groups with 2+ rows
ORDER BY avg_sal DESC                          -- 7. alias is allowed here
LIMIT    2;                                    -- 8. top two groups
 dept_id | avg_sal
---------+---------
       1 |  125000
       2 |  117500
(2 rows)

Check by hand. WHERE keeps nine people hired from 2018 (Meera, Vikram and Ananya drop out). GROUP BY makes three groups: department 1 (Priya, Rahul, Arjun, Divya, average 125,000), department 2 (Karan, Neha, average 117,500) and department 3 (Sunita, Farhan, Isha, average 80,000). HAVING keeps all three (each has two or more rows), ORDER BY sorts them by the alias and LIMIT 2 cuts off department 3.

QuestionAnswer from the order
Why can't I use a SELECT alias in WHERE? WHERE (step 2) runs before SELECT (step 5) creates the alias. Repeat the expression, or use a subquery/CTE.
Why can I use it in ORDER BY?ORDER BY (step 7) runs after SELECT.
Why can HAVING use COUNT(*) but WHERE cannot? Groups exist only after step 3.
Why does LIMIT need ORDER BY to be meaningful? It cuts the result at step 8, after sorting. Without a sort, "the first rows" is arbitrary.
Why can't I filter on a window function in WHERE? Windows are computed in step 5, after WHERE. Wrap the query in a subquery or CTE and filter outside.
Why can a LEFT JOIN's ON and WHERE give different results?ON is part of step 1 (builds the rows, keeps unmatched left rows); WHERE (step 2) then deletes rows, including those NULL-extended ones.

Where PostgreSQL and MySQL are more relaxed

Both databases accept a select alias in GROUP BY, and MySQL also in HAVING. This is a convenience, not standard SQL, and it does not extend to WHERE. Do not rely on it if the query must be portable.

Rule: a clause can only use what earlier steps produced

If an error says a column, alias or aggregate "does not exist" or "is not allowed", find the step where the thing is created and the step where you used it. Fix the order: repeat the expression, move it into a subquery, or move the condition to the right clause.

Tip: build queries in this order too

Write FROM and JOIN first, then WHERE, then GROUP BY, then the select list. Check the rows after each step. Many people start from the select list and end up confused.

Interview angle

"In which order does SQL execute a query?" Name all eight steps and explain the alias rule. It is also the clean way to answer "WHERE vs HAVING". The optional follow-up is that the optimizer may physically reorder work but must keep the logical result.

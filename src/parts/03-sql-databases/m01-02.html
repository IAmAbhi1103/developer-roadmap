The sample database: a company and a shop

Every example in Modules 1–3 runs on one small database: a company (departments, employees, projects) and an online shop (customers, products, orders). Run the script on this page once in learn_sql and you can paste every query in these notes and get the same results.

Learning SQL on made-up tables that change in every chapter wastes time. Here you create the tables once and keep them for the whole course. The data is tiny on purpose (a dozen employees, ten orders), so you can check every result in your head. It also contains a few deliberate "traps" (an employee with no manager, a department with no staff, a customer who never ordered) because real data is never tidy, and the classic interview questions are all about these edge cases.

Step 1: the company tables

Do not worry if some syntax is new. Each part (data types, PRIMARY KEY, FOREIGN KEY, CHECK, DEFAULT) is explained later in this module; for now just run it. Connect to learn_sql as app_user (see Install PostgreSQL or MySQL), save all five blocks below in order as sample_schema.sql, and run the file.

-- Start clean (children first) so the script can be re-run at any time.
-- WARNING: this drops tables with these names. Use a practice database only.
DROP TABLE IF EXISTS order_items, orders, products, customers,
                     employee_projects, projects, employees, departments CASCADE;

CREATE TABLE departments (
    dept_id   INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name      VARCHAR(50) NOT NULL UNIQUE,
    location  VARCHAR(50) NOT NULL
);

CREATE TABLE employees (
    emp_id      INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    first_name  VARCHAR(50)    NOT NULL,
    last_name   VARCHAR(50)    NOT NULL,
    email       VARCHAR(100)   NOT NULL UNIQUE,
    dept_id     INT,
    manager_id  INT,
    salary      NUMERIC(10, 2) NOT NULL CHECK (salary > 0),
    hire_date   DATE           NOT NULL DEFAULT CURRENT_DATE,
    CONSTRAINT fk_employees_dept
        FOREIGN KEY (dept_id) REFERENCES departments (dept_id)
        ON DELETE SET NULL,
    CONSTRAINT fk_employees_manager
        FOREIGN KEY (manager_id) REFERENCES employees (emp_id)
        ON DELETE SET NULL
);

CREATE TABLE projects (
    project_id  INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name        VARCHAR(100)   NOT NULL,
    dept_id     INT            NOT NULL,
    start_date  DATE           NOT NULL,
    end_date    DATE,
    budget      NUMERIC(12, 2) NOT NULL CHECK (budget >= 0),
    CONSTRAINT fk_projects_dept
        FOREIGN KEY (dept_id) REFERENCES departments (dept_id),
    CONSTRAINT ck_projects_dates
        CHECK (end_date IS NULL OR end_date >= start_date)
);

CREATE TABLE employee_projects (
    emp_id          INT         NOT NULL,
    project_id      INT         NOT NULL,
    role            VARCHAR(30) NOT NULL,
    hours_per_week  SMALLINT    NOT NULL CHECK (hours_per_week BETWEEN 1 AND 60),
    PRIMARY KEY (emp_id, project_id),
    CONSTRAINT fk_ep_employee
        FOREIGN KEY (emp_id) REFERENCES employees (emp_id) ON DELETE CASCADE,
    CONSTRAINT fk_ep_project
        FOREIGN KEY (project_id) REFERENCES projects (project_id) ON DELETE CASCADE
);

Step 2: the shop tables

CREATE TABLE customers (
    customer_id  INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name         VARCHAR(100) NOT NULL,
    email        VARCHAR(100) NOT NULL UNIQUE,
    city         VARCHAR(50)  NOT NULL,
    phone        VARCHAR(15),
    joined_on    DATE         NOT NULL DEFAULT CURRENT_DATE
);

CREATE TABLE products (
    product_id  INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name        VARCHAR(100)   NOT NULL,
    category    VARCHAR(30)    NOT NULL,
    price       NUMERIC(10, 2) NOT NULL CHECK (price >= 0),
    stock       INT            NOT NULL DEFAULT 0 CHECK (stock >= 0)
);

CREATE TABLE orders (
    order_id     INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id  INT         NOT NULL,
    order_date   DATE        NOT NULL DEFAULT CURRENT_DATE,
    status       VARCHAR(20) NOT NULL DEFAULT 'PLACED'
                 CHECK (status IN ('PLACED', 'SHIPPED', 'DELIVERED', 'CANCELLED')),
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers (customer_id)
);

CREATE TABLE order_items (
    order_id    INT            NOT NULL,
    product_id  INT            NOT NULL,
    quantity    INT            NOT NULL CHECK (quantity > 0),
    unit_price  NUMERIC(10, 2) NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, product_id),
    CONSTRAINT fk_items_order
        FOREIGN KEY (order_id) REFERENCES orders (order_id) ON DELETE CASCADE,
    CONSTRAINT fk_items_product
        FOREIGN KEY (product_id) REFERENCES products (product_id) ON DELETE RESTRICT
);

Step 4: move the id counters

-- We inserted ids by hand, so move each counter to the largest id in its table
SELECT setval(pg_get_serial_sequence('departments', 'dept_id'), 4),
       setval(pg_get_serial_sequence('employees', 'emp_id'), 12),
       setval(pg_get_serial_sequence('projects', 'project_id'), 5),
       setval(pg_get_serial_sequence('customers', 'customer_id'), 7),
       setval(pg_get_serial_sequence('products', 'product_id'), 7),
       setval(pg_get_serial_sequence('orders', 'order_id'), 10);

Why? An identity column hands out ids from its own counter, which starts at 1. When you insert ids yourself the counter does not move, so the first insert without an id would try to use 1 again and fail with ERROR: duplicate key value violates unique constraint "departments_pkey". Loading seed data with explicit ids and then fixing the counter is exactly what pg_dump writes into backups. MySQL's AUTO_INCREMENT moves its counter by itself.

How results are shown in these notes

Results are printed the way psql prints them: a header, a dashed line, the rows, then the row count. Numbers are right-aligned and text is left-aligned. Run this once per psql session so that NULL is visible instead of an empty cell:

\pset null '(null)'

Almost every example has an ORDER BY, so your rows come back in the same order as shown. Without it the order is not guaranteed (see ORDER BY, LIMIT and pagination). A GUI such as DBeaver shows the same data in a grid.

The deliberate quirks

These facts come back again and again in later examples and interview questions:

  • Meera Iyer (the CEO) has dept_id = NULL and manager_id = NULL. She is the only employee without a department, and the root of the management tree.
  • Marketing has no employees, and the Brand Campaign project has nobody assigned.
  • Ananya, Priya and Rahul all earn 150000. Ties matter for ranking and "Nth highest" questions.
  • Karan (160000) earns more than his manager Ananya (150000); Rahul earns exactly the same as his manager Priya.
  • Customers Sara and Tanvi never ordered, the Desk Lamp was never sold, order 4 is cancelled, and three customers have no phone number.

Using MySQL instead

The script is written for PostgreSQL. Three things change for MySQL 8:

  • Replace INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY with INT AUTO_INCREMENT PRIMARY KEY, and delete the setval block.
  • Write date defaults with parentheses: DEFAULT (CURRENT_DATE).
  • Use MySQL 8.0.16 or newer, the first version that enforces CHECK constraints.

Foreign keys are written as separate CONSTRAINT … FOREIGN KEY clauses on purpose. MySQL silently ignores a foreign key written inline, as in dept_id INT REFERENCES departments (dept_id), while the table-level form works in both databases. (MySQL also accepts the word CASCADE in DROP TABLE and ignores it; the order of the table names already puts children first.)

Tip: reset whenever you break something

Practise UPDATE and DELETE freely. When the data no longer matches the outputs in these notes, run sample_schema.sql again: it drops and rebuilds all eight tables in a second.

Mistake: running the script in the wrong database

The script drops tables called employees, orders and so on. Run it only in your practice database. Check with \conninfo first, and never run it against a database that holds real data.

Note: why so little data?

Tiny tables hide performance problems. Slow queries, indexes and EXPLAIN only become interesting with thousands or millions of rows. When you need those, generate them with generate_series (see Recursive CTEs and generating series).

SQL style: formatting, naming, quoting and comments

SQL ignores layout and keyword case, so style is a team agreement: uppercase keywords, lowercase snake_case names, one clause per line, one naming rule for tables, and no quoted identifiers. Consistent style makes queries easy to read in code review and easy to compare in a diff.

Why bother?

The database does not care how a query looks. People do. A 40-line query pasted as one line is unreadable, and a team where every developer names tables differently wastes time guessing. The rules below are the common defaults in Java teams. If your company has its own guide, follow that one instead; the point is to be consistent.

Layout

  • Keywords in UPPERCASE (SELECT, FROM, WHERE, ORDER BY) and names in lowercase. Keywords then stand out from table and column names.
  • One clause per line, starting at the left edge. A long column list gets one column per line.
  • Put AND and OR at the start of the continuation line, indented, so you can comment out one condition without touching the others.
  • Write joins explicitly with JOIN … ON …, one join per line.
  • Use short table aliases (e for employees) and qualify every column with the alias as soon as a query has two tables.
  • End every statement with a semicolon.

Wrong: legal, but hard to read and review

select e.first_name,d.name,e.salary from employees e join departments d
on e.dept_id=d.dept_id where e.salary>100000 and d.location='Bengaluru' order by e.salary desc;

Right: same query, laid out for people

SELECT e.first_name,
       d.name AS department,
       e.salary
FROM employees AS e
JOIN departments AS d ON d.dept_id = e.dept_id
WHERE e.salary > 100000
  AND d.location = 'Bengaluru'
ORDER BY e.salary DESC;

Avoid reserved words as names (order, user, group, table, desc, end, check), spaces, CamelCase, and abbreviations nobody can decode. This is why the shop table is called orders and not order. Spring Boot and Hibernate map a Java field firstName to the column first_name by default, so snake_case in the database costs you nothing in Java.

Quoting identifiers

PostgreSQL converts unquoted names to lowercase, so FirstName, FIRSTNAME and firstname are the same column. Double quotes switch that off: "FirstName" is a different, case-sensitive name, and from then on you must type the quotes every time. Quotes are also the only way to use a reserved word or a name with a space. MySQL uses backticks for the same job: `order`. The simple rule: do not create anything that needs quotes.

Wrong: quoted CamelCase name

CREATE TABLE "Employee" (emp_id INT PRIMARY KEY);
SELECT * FROM Employee;
-- ERROR:  relation "employee" does not exist

Right: plain lowercase name

CREATE TABLE employee (emp_id INT PRIMARY KEY);
SELECT * FROM employee;
SELECT * FROM Employee;   -- also works: folded to lowercase

The same problem hits reserved words: SELECT * FROM order; fails with ERROR: syntax error at or near "order", because ORDER starts an ORDER BY clause. It works only as "order".

Comments

-- A line comment: everything to the end of the line is ignored
SELECT first_name,        -- trailing comment
       salary /* inline block comment */
FROM employees
/* A block comment can
   span several lines. */
WHERE dept_id = 3;

MySQL also accepts # for a line comment, and requires a space after --. PostgreSQL allows block comments to nest; MySQL does not. To store documentation inside the database use COMMENT ON TABLE employees IS 'Staff of the company'; in PostgreSQL (psql's \d+ shows it) or the COMMENT '…' clause of CREATE TABLE in MySQL.

Tools that enforce style

Do not argue about spaces in code review; let a tool decide. pgAdmin, DBeaver and IntelliJ can all reformat a selected query. SQLFluff is a linter and formatter you can run in a CI pipeline, and pgFormatter is a formatter for PostgreSQL.

Convention: write SQL like code

SQL files that live in your repository (migrations, reports, seed data) go through the same review as Java. Teams that use Flyway or Liquibase keep every schema change as a versioned SQL file, so naming and layout rules are checked in pull requests.

Mistake: positional and clever shortcuts

ORDER BY 3 and GROUP BY 1, 2 are legal, but nobody can tell which column is meant, and the query silently changes meaning when someone edits the select list. Write the column name or the alias.

Tip: comment the why, not the what

-- keep cancelled orders: finance reports include them helps the next reader. -- select the name above SELECT name does not.

Interview angle

Style is rarely asked directly, but it shows in every whiteboard query. Interviewers notice uppercase keywords, aliases, one clause per line, and explicit joins. If asked about naming, say you pick one convention per project, avoid reserved words and quoted identifiers, and name constraints explicitly so error messages are readable.

SELECT, FROM and WHERE: reading data

SELECT chooses the columns, FROM names the table, and WHERE keeps only the rows that match a condition. A query only reads: it never changes the table.

The shape of a query

The smallest useful query has two parts, and a third part that is optional:

SELECT first_name, last_name, salary   -- which columns to show
FROM employees                          -- which table to read
WHERE dept_id = 3;                      -- which rows to keep (optional)
 first_name | last_name |  salary
------------+-----------+-----------
 Sunita     | Patel     | 120000.00
 Farhan     | Shaikh    |  65000.00
 Isha       | Banerjee  |  55000.00
(3 rows)

Conceptually the database works in this order: take the table in FROM, keep the rows that pass WHERE, then pick the columns in SELECT. You write SELECT first, but it is processed after the filter. That is why a column alias created in SELECT cannot be used in WHERE (see Logical order of a query). Without WHERE you get every row. The columns come out in the order you list them, not the order in the table.

Choosing columns, and why to avoid SELECT *

SELECT * means "all columns". It is handy in a terminal when you explore a table:

SELECT * FROM departments ORDER BY dept_id;
 dept_id |    name     | location
---------+-------------+-----------
       1 | Engineering | Bengaluru
       2 | Sales       | Mumbai
       3 | HR          | Pune
       4 | Marketing   | Delhi
(4 rows)

In application code and in views, list the columns you need. The star causes real problems:

  • It moves data you do not use. A table with a large TEXT or JSON column sends that data over the network for every row, even if you only show a name.
  • It breaks when the table changes. Someone adds, drops or reorders a column, and code that reads results by position (rs.getString(3) in JDBC) quietly gets the wrong value.
  • It blocks index-only scans. If an index already contains the columns you need, the database can skip the table. With * it cannot (see Module 5).
  • It collides in joins. Joining two tables with SELECT * returns dept_id and name twice, and a program reading "name" gets one of them.

SELECT * is fine in COUNT(*), in EXISTS (SELECT * FROM …), and for quick exploration. JPA and Hibernate always generate an explicit column list.

Three rules cover most of the confusion:

  • Text and dates go in single quotes, numbers do not. Write dates in the ISO form 'YYYY-MM-DD'; it is unambiguous and sorts correctly.
  • Text comparison is case-sensitive in PostgreSQL: 'engineering' does not equal 'Engineering'. MySQL's default collation ignores case, so the same query finds the row there. See LIKE, ILIKE and case sensitivity.

Column aliases with AS

An alias gives a column or expression a new name in the result. The name is what JDBC's getString("full_name") and Spring Data projections read. Write AS even though it is optional (the next section shows why).

SELECT first_name || ' ' || last_name AS full_name,
       salary * 12                    AS annual_salary
FROM employees
WHERE dept_id = 3
ORDER BY emp_id;
   full_name   | annual_salary
---------------+---------------
 Sunita Patel  |    1440000.00
 Farhan Shaikh |     780000.00
 Isha Banerjee |     660000.00
(3 rows)

To get spaces or capital letters in an alias, quote it: AS "Annual Salary" in PostgreSQL (backticks in MySQL). Avoid that for anything a program reads. An alias can be used in ORDER BY, but not in WHERE, because WHERE runs before SELECT creates it:

SELECT salary * 12 AS annual_salary FROM employees WHERE annual_salary > 1000000;
-- ERROR:  column "annual_salary" does not exist

-- Repeat the expression instead
SELECT salary * 12 AS annual_salary FROM employees WHERE salary * 12 > 1000000;

Expressions and calculations

In SELECT and WHERE you can use arithmetic (+ - * / %), functions (ROUND, UPPER) and literal values. In PostgreSQL and MySQL a SELECT needs no FROM, which makes the database a calculator (Oracle needs FROM DUAL).

SELECT 2 + 3 AS total, 7 / 2 AS int_div, 7 / 2.0 AS dec_div, 7 % 3 AS remainder;
 total | int_div |      dec_div       | remainder
-------+---------+--------------------+-----------
     5 |       3 | 3.5000000000000000 |         1
(1 row)

Look at 7 / 2: when both sides are integers, PostgreSQL does integer division and truncates to 3. Make one side a decimal (7 / 2.0) to get 3.5. MySQL behaves differently: 7 / 2 returns 3.5000, and 7 DIV 2 is the integer division. A real example with prices, rounded to two decimals:

SELECT name, price, ROUND(price * 0.18, 2) AS gst
FROM products
WHERE product_id <= 3
ORDER BY product_id;

FROM employees
WHERE dept_id = 3;

The wrong query runs without an error and returns one column, named last_name, that holds first names (Sunita, Farhan, Isha). This is why you write AS for every alias: then a missing comma is a syntax error instead of a silent bug.

Errors you will see

  • ERROR: column "salry" does not exist: a typo in a column name. PostgreSQL often adds a hint such as Perhaps you meant to reference the column "employees.salary".
  • ERROR: relation "employee" does not exist: wrong table name, or you are connected to the wrong database or schema.
  • ERROR: syntax error at or near "FROM": very often a trailing comma, as in SELECT first_name, FROM employees.

Edge cases that are fine: a SELECT without WHERE returns every row, and the same column may appear twice in the select list.

Convention

List columns explicitly, give every computed column an AS alias, and always qualify columns with a table alias once a query has more than one table. Always write ORDER BY when the order of rows matters.

Interview angle

  • Why avoid SELECT *? Extra data over the network, breaks position-based code when the schema changes, blocks index-only scans, duplicate column names in joins.
  • Can you use a select alias in WHERE? No: WHERE is evaluated before SELECT. You can use it in ORDER BY.
  • What does SELECT 7 / 2 return? 3 in PostgreSQL (integer division), 3.5000 in MySQL.

Data types: numbers, text and booleans

Every column has a type that decides what it can store, how much space it takes and how it behaves. Use integers for counts and ids, NUMERIC for money, VARCHAR or TEXT for text, and never use REAL or DOUBLE for rupees.

Why the type matters

A data type is a rule attached to a column. The database rejects values that do not fit ('abc' in an integer column), stores each value in the right number of bytes, and knows how to compare and calculate with it. A wrong type causes bugs that are hard to see later: a phone number stored as an integer loses its leading zero, a price stored as a float is off by a paisa, and an INT id column overflows when the table grows. Choose the type once, carefully, because changing it later on a big table is slow and risky.

Integers

TypeSizeRangeUse for
SMALLINT2 bytes−32,768 to 32,767small counters, hours per week
INT / INTEGER4 bytesabout ±2.1 billionmost ids and counts
BIGINT8 bytesabout ±9.2 × 1018ids of big tables, UPI transaction numbers, paise totals

MySQL has the same three plus TINYINT (1 byte) and MEDIUMINT, and allows UNSIGNED (so INT UNSIGNED reaches about 4.29 billion). PostgreSQL has no unsigned types; use a CHECK (x >= 0) instead. In Java: SMALLINT maps to short, INT to int, BIGINT to long. If a value does not fit you get ERROR: integer out of range (PostgreSQL) or ERROR 1264 ... Out of range value (MySQL in strict mode).

Exact decimals: NUMERIC and DECIMAL

NUMERIC(p, s) stores a decimal number exactly. p is the precision (total digits) and s is the scale (digits after the point). NUMERIC(10, 2) holds up to 8 digits before the point and 2 after: 99999999.99. DECIMAL is a synonym in both databases. Use it for money, tax rates and anything that must add up to the last paisa.

SELECT 123.456::NUMERIC(10, 2) AS rounded;        -- 123.46 (rounded, no error)
SELECT 123456789.5::NUMERIC(10, 2) AS too_big;
-- ERROR:  numeric field overflow
-- DETAIL:  A field with precision 10, scale 2 must round to an absolute value
--          less than 10^8.

Approximate decimals: REAL and DOUBLE PRECISION

REAL (4 bytes, about 6 digits) and DOUBLE PRECISION (8 bytes, about 15 digits; DOUBLE in MySQL) are binary floating-point types, the same as Java's float and double. They are fast, but they cannot store 0.1 exactly, just as 1/3 cannot be written exactly in decimal. Good for sensor readings and statistics. Wrong for money.

SELECT 0.1::DOUBLE PRECISION + 0.2::DOUBLE PRECISION = 0.3::DOUBLE PRECISION AS float_sum,
       0.1::NUMERIC + 0.2::NUMERIC = 0.3::NUMERIC                          AS numeric_sum;
 float_sum | numeric_sum
-----------+-------------
 f         | t
(1 row)

A float sum of many small amounts drifts; an invoice total that is one paisa off fails an audit. In Java the pair is BigDecimal for NUMERIC, never double. Another option is to store whole paise in a BIGINT (price_paise = 79900), which many payment systems do.

Text: CHAR, VARCHAR and TEXT

TypeMeaningNotes
CHAR(n)Exactly n characters, padded with spaces Only for truly fixed codes (country code 'IN'). Padding surprises people.
VARCHAR(n)Up to n characters Rejects longer values. Good when a real limit exists (email 100, PIN code 6).
TEXTAny length PostgreSQL: same speed as VARCHAR. MySQL: separate family (TEXT 64 KB, MEDIUMTEXT 16 MB, LONGTEXT 4 GB).

In PostgreSQL there is no performance gain from VARCHAR(50) over TEXT; the length is only a validation rule. Use VARCHAR(n) when the limit is a business rule, and TEXT for free text such as descriptions and comments. In MySQL VARCHAR is stored inside the row and can be indexed fully, while TEXT columns need a prefix length in an index, so prefer VARCHAR for searchable columns. Also in MySQL the limit counts characters, but the whole row cannot exceed 65,535 bytes.

INSERT INTO departments (name, location) VALUES ('Research', 'A very long city name ...
    repeated until it passes fifty characters in total length ok');
-- ERROR:  value too long for type character varying(50)

MySQL in strict mode (the default since 5.7) gives ERROR 1406 (22001): Data too long for column 'location' at row 1. With strict mode off, MySQL silently cuts the value, which hides bugs. Check SELECT @@sql_mode; contains STRICT_TRANS_TABLES.

Boolean

PostgreSQL has a real BOOLEAN type with values TRUE, FALSE and NULL. It also accepts 't', 'yes', '1' and similar text. MySQL's BOOLEAN is only another name for TINYINT(1), so TRUE is stored as 1 and the column accepts 2 or 7 as well. Write WHERE is_active or WHERE NOT is_active in PostgreSQL. Add NOT NULL DEFAULT FALSE to avoid a third, meaningless state.

Rule: money is NUMERIC (or whole paise), never FLOAT

Use NUMERIC(p, s) with the scale your currency needs (2 for rupees) and map it to BigDecimal. Choose the precision for the largest value you can imagine, not the smallest.

Mistake: storing phone numbers, PIN codes and Aadhaar numbers as integers

You never do arithmetic on them, and integers drop leading zeros (0123 becomes 123) and break on +91. Store identifiers as VARCHAR, and add a CHECK for the format if you want. That is why customers.phone is VARCHAR(15).

Edge cases: silent changes and implicit casts

  • NUMERIC rounds extra decimals silently; only extra digits before the point raise an error.
  • Comparing text with a number (WHERE phone = 9876500001) makes PostgreSQL fail with operator does not exist: character varying = integer, while MySQL converts silently and may also stop using the index. Pass the right type from JDBC.
  • CHAR(5) pads 'ab' to 'ab '. PostgreSQL ignores the padding when comparing; avoid CHAR and the question never arises.

Interview angle

"Which type for money?" gets the answer NUMERIC/DECIMAL with a reason: floats cannot represent 0.1 exactly. Also expect "VARCHAR vs TEXT" (same speed in PostgreSQL, the length is a rule) and "INT vs BIGINT for ids" (an INT runs out at 2.1 billion rows, which a busy event table reaches in a few years).

Data types: dates, UUID, JSON, identity columns and ENUM

Store moments as TIMESTAMPTZ (PostgreSQL), days as DATE, structured extras as JSONB, and generate ids with GENERATED ... AS IDENTITY (MySQL: AUTO_INCREMENT). Prefer a CHECK or lookup table over ENUM.

Date and time types

DATEa calendar day2026-04-10
TIMEa time of day14:30:00
TIMESTAMPday + time, no time zone2026-04-10 14:30:00
TIMESTAMPTZan exact moment in time (PostgreSQL)2026-04-10 14:30:00+05:30
INTERVALa length of time (PostgreSQL)3 days 02:00:00

The difference between TIMESTAMP and TIMESTAMPTZ trips up many developers. TIMESTAMPTZ ("timestamp with time zone") does not store a zone. It converts every input to UTC for storage, and converts back to the session's TimeZone setting when it prints. So the same row shows 09:00 in London and 14:30 in Mumbai, and it is still the same instant. TIMESTAMP stores the digits you gave it and knows nothing about zones, so it is only right for things like "the shop opens at 10:00 local time".

CREATE TEMP TABLE t (at TIMESTAMPTZ);
INSERT INTO t VALUES ('2026-04-10 14:30:00+05:30');

SET TimeZone = 'Asia/Kolkata';
SELECT at FROM t;
SET TimeZone = 'UTC';
SELECT at FROM t;
           at
------------------------

           at
------------------------
 2026-04-10 09:00:00+00

MySQL has DATETIME (no conversion, years 1000–9999) and TIMESTAMP (converted to UTC for storage, range 1970 to 2038-01-19, so avoid it for far-future dates). Many Spring Boot teams run the database in UTC and map to Instant or OffsetDateTime; for DATE use LocalDate. Time-zone handling in queries is in Date ranges and time zones.

UUID

A UUID is a 128-bit identifier such as 3f2b8c1e-5a7d-4c9e-9b21-0d4e6f7a8b90. It can be created by any application server without asking the database, which is useful when ids are generated before the insert or across several services, and it does not reveal how many rows exist. PostgreSQL has a native UUID type (16 bytes) and the built-in gen_random_uuid() (PostgreSQL 13 and later). Random UUIDs make index inserts scatter across the whole B-tree, so for very write-heavy tables prefer time-ordered UUIDs (UUIDv7; PostgreSQL 18 added a uuidv7() function). MySQL has UUID() and stores it best as BINARY(16) via UUID_TO_BIN(). A BIGINT identity is smaller and faster; choose UUID for a reason, not by habit.

CREATE TABLE sessions (
    session_id  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    customer_id INT  NOT NULL REFERENCES customers (customer_id)
);

JSON and JSONB

PostgreSQL can keep a JSON document in a column. JSON stores the text exactly as given. JSONB parses it into a binary form: slightly slower to write, faster to query, it removes duplicate keys and does not keep key order or spaces, and it supports indexes (GIN). Use JSONB unless you must keep the original text. MySQL's single JSON type is stored in binary too.

CREATE TEMP TABLE events (id INT, payload JSONB);
INSERT INTO events VALUES (1, '{"type": "login", "device": {"os": "Android"}}');

SELECT payload -> 'device'            AS device_json,   -- returns JSON
       payload ->> 'type'            AS type_text,     -- returns text
       payload -> 'device' ->> 'os'  AS os
FROM events
WHERE payload @> '{"type": "login"}';  -- containment, can use a GIN index
     device_json     | type_text |   os
---------------------+-----------+---------
 {"os": "Android"}   | login     | Android
(1 row)

MySQL uses the same -> and ->> operators on a path: payload->>'$.type'. JSON is good for data that really has no fixed shape (audit payloads, third-party webhooks, optional settings). If you filter or join on a field all the time, make it a normal column. More in Module 6.

ENUM, briefly

An ENUM is a column that accepts only a fixed list of words. PostgreSQL defines it as a separate type, MySQL writes it inline:

-- PostgreSQL
CREATE TYPE order_status AS ENUM ('PLACED', 'SHIPPED', 'DELIVERED', 'CANCELLED');
-- MySQL
CREATE TABLE orders_demo (status ENUM('PLACED', 'SHIPPED', 'DELIVERED', 'CANCELLED'));

Adding a value later is easy in PostgreSQL (ALTER TYPE ... ADD VALUE), but removing or renaming one is painful, and in MySQL changing the list rewrites the table. Our sample schema uses VARCHAR(20) with a CHECK (status IN (...)) instead: easy to change, easy to map to a Java enum with @Enumerated(EnumType.STRING). If the list has attributes or changes often, use a small lookup table with a foreign key.

Rule: store moments in UTC-aware columns

In PostgreSQL use TIMESTAMPTZ for "when did it happen" (created_at, paid_at). Use DATE for a day with no time (hire_date). Never store a moment as text.

Mistake: using TIMESTAMP for events and getting shifted times

A server in Mumbai writes 14:30 into a plain TIMESTAMP; a reporting job in UTC reads it as 14:30 UTC, five and a half hours off. With TIMESTAMPTZ both sides agree on the instant.

Edge cases

  • Invalid dates fail: '2026-02-30' raises ERROR: date/time field value out of range.
  • MySQL (non-strict) can store 0000-00-00; modern strict mode refuses it.
  • A JSON text that is not valid JSON fails with ERROR: invalid input syntax for type json.
  • Identity counters never go back after ROLLBACK or DELETE.

Interview angle

Common questions: TIMESTAMP vs TIMESTAMPTZ (the second normalises to UTC), JSON vs JSONB (binary, indexable), UUID vs auto-increment (UUID: generated anywhere, no guessable order, bigger, scattered index writes; identity: small and ordered), and SERIAL vs IDENTITY (identity is the standard, newer form).

CREATE TABLE, ALTER TABLE and DROP TABLE

CREATE TABLE defines a table with its columns, types and constraints, ALTER TABLE changes it afterwards, and DROP TABLE removes it with all its data. Real projects keep every such change in versioned migration files instead of typing it by hand.

CREATE TABLE

A table definition is a list of columns, each with a name, a type and optional rules, followed by optional table-level constraints. This is a small, complete example you can run next to the sample database:

CREATE TABLE IF NOT EXISTS leave_requests (
    request_id  INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    emp_id      INT          NOT NULL REFERENCES employees (emp_id),
    start_date  DATE         NOT NULL,
    end_date    DATE         NOT NULL,
    reason      TEXT,
    status      VARCHAR(10)  NOT NULL DEFAULT 'PENDING',
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT ck_leave_dates  CHECK (end_date >= start_date),
    CONSTRAINT ck_leave_status CHECK (status IN ('PENDING', 'APPROVED', 'REJECTED'))
);

IF NOT EXISTS makes the statement do nothing (with a notice) when the table is already there, so a script can be re-run. Without it you get ERROR: relation "leave_requests" already exists. Two more ways to create a table:

-- same columns, no data (PostgreSQL: add INCLUDING ALL to copy constraints and indexes)
CREATE TABLE employees_backup (LIKE employees INCLUDING ALL);

-- table made from a query: columns and data, but no constraints
CREATE TABLE high_earners AS
SELECT emp_id, first_name, salary FROM employees WHERE salary >= 150000;

A temporary table (CREATE TEMP TABLE) lives only for your session and is handy for experiments, as in the examples above. Tables can also live in a schema, a named folder inside the database: hr.employees. The default schema in PostgreSQL is public (see Module 4).

Several actions can go in one statement separated by commas, and PostgreSQL runs them together. If the new type cannot be converted automatically, PostgreSQL asks you to say how: ALTER COLUMN age TYPE INT USING age::INT.

What goes wrong on a table that already has rows

ALTER TABLE employees ADD COLUMN grade VARCHAR(2) NOT NULL;
-- ERROR:  column "grade" of relation "employees" contains null values

ALTER TABLE employees ADD COLUMN grade VARCHAR(2) NOT NULL DEFAULT 'L1';   -- works

Existing rows need a value for the new column. Give a default, or add the column as nullable, fill it with an UPDATE, then add SET NOT NULL. The same applies when you add a constraint: ADD CONSTRAINT ... CHECK (salary > 100000) fails with check constraint "..." of relation "employees" is violated by some row if any row breaks it. Fix the data first.

Cost and locks on production tables

Most ALTER TABLE forms take a strong lock, so other queries wait. Adding a column with a constant default is instant in PostgreSQL 11 and later, but changing a column type usually rewrites the whole table while holding the lock. Adding a foreign key or CHECK scans the table. For big tables, PostgreSQL lets you add a constraint as NOT VALID (new rows are checked, old rows are not) and later run ALTER TABLE ... VALIDATE CONSTRAINT name, which checks without blocking writes. Teams run schema changes through Flyway or Liquibase migrations, in a quiet period, after testing on a copy of production data (see Spring Boot · Module 3).

DROP TABLE

DROP TABLE IF EXISTS leave_requests;
DROP TABLE departments;
-- ERROR:  cannot drop table departments because other objects depend on it
-- DETAIL:  constraint fk_employees_dept on table employees depends on table departments
-- HINT:  Use DROP ... CASCADE to drop the dependent objects too.

DROP TABLE departments CASCADE;   -- removes the foreign keys that point at it (and views)

DROP TABLE deletes the structure and all data at once and cannot be undone except by a rollback or a backup. CASCADE does not delete the child table, only the constraints and views that depend on it; RESTRICT (the default) refuses. DROP TABLE a, b, c drops several. See Safe changes, TRUNCATE and DROP for the difference from DELETE and TRUNCATE.

Another difference: PostgreSQL has transactional DDL, so you can wrap ALTER and DROP in BEGIN ... ROLLBACK and test them safely. MySQL commits implicitly before and after every DDL statement, so there is nothing to roll back.

Rule: every table gets a primary key, and every constraint a name

A table without a primary key has no way to identify one row, and JPA refuses it. Name constraints yourself (fk_leave_approver), because only a named constraint can be dropped by a readable command, and its name appears in the error message.

Convention: add columns, do not edit history

Never edit an old migration after it ran anywhere. Add a new migration. Prefer additive, backwards compatible changes (new nullable column) first, deploy the code, and only then drop what is unused.

Mistake: DROP in the wrong database

Check \conninfo before a destructive script. The editor tab for staging and production look the same. Many teams give developers no DROP permission on production at all.

Exceptions and errors

  • ERROR: relation "x" already exists on repeated CREATE; use IF NOT EXISTS.
  • ERROR: column "x" of relation "t" already exists on a repeated ADD COLUMN (PostgreSQL also has ADD COLUMN IF NOT EXISTS).
  • ERROR: cannot alter type of a column used by a view or rule: drop and recreate the view.
  • Dropping a column used by a foreign key in another table fails until you use CASCADE.

Interview angle

Expect to write a CREATE TABLE with a primary key, foreign key and a check on the board, and to answer "how do you add a NOT NULL column to a table with a million rows?" (nullable or default first, backfill in batches, then SET NOT NULL, in a migration tool).

Constraints in depth: PRIMARY KEY, UNIQUE, NOT NULL, CHECK and DEFAULT

A constraint is a rule the database enforces on every write, so bad data cannot get in whatever the application does. Each constraint has its own error message, and naming constraints makes those messages readable.

Why the database must enforce rules

Validation in Java (@NotNull, @Size) is good for friendly messages, but it can be bypassed: a second service, a data-fix script, a bug, or two requests racing each other. A constraint inside the database cannot be bypassed. It is also checked atomically, which is the only reliable way to guarantee "no two users with the same email" under concurrency. Use both layers.

Column constraint vs table constraint

A column constraint is written on the column line and concerns that column. A table constraint is written after the columns and can involve several columns. Anything with two or more columns must be a table constraint.

CREATE TABLE enrollments_demo (
    student_id  INT          NOT NULL,                          -- column constraint
    course_id   INT          NOT NULL,
    grade       CHAR(1)      CHECK (grade IN ('A','B','C','D','F')),  -- column check
    credits     SMALLINT     NOT NULL DEFAULT 3,
    CONSTRAINT pk_enrollments_demo PRIMARY KEY (student_id, course_id),   -- table, composite
    CONSTRAINT uq_demo_pair        UNIQUE (course_id, student_id, grade)  -- table
);

If you do not name a constraint, PostgreSQL invents a name (employees_email_key, employees_pkey, employees_salary_check, orders_customer_id_fkey). The generated names are predictable, but your own (uq_employees_email) are clearer and let a Java exception handler recognise the constraint by name.

PRIMARY KEY

A primary key marks the column (or columns) that identify a row. It is UNIQUE plus NOT NULL, a table can have only one, and the database builds a unique index for it. A composite primary key uses two or more columns: employee_projects uses (emp_id, project_id), so one employee can be on many projects and each pair appears once. Choosing keys (natural vs surrogate) is in Module 4.

INSERT INTO departments (dept_id, name, location) VALUES (1, 'Legal', 'Chennai');
-- ERROR:  duplicate key value violates unique constraint "departments_pkey"
-- DETAIL:  Key (dept_id)=(1) already exists.

INSERT INTO employee_projects (emp_id, project_id, role, hours_per_week)
VALUES (5, 1, 'Lead', 30);
-- ERROR:  duplicate key value violates unique constraint "employee_projects_pkey"
-- DETAIL:  Key (emp_id, project_id)=(5, 1) already exists.

MySQL: ERROR 1062 (23000): Duplicate entry '1' for key 'departments.PRIMARY'.

UNIQUE

UNIQUE allows no repeats but, unlike a primary key, allows NULL, and since NULL is never equal to NULL, many NULLs are allowed in a unique column (PostgreSQL 15 added UNIQUE NULLS NOT DISTINCT to change this; MySQL also allows multiple NULLs). A table can have many unique constraints, and they can cover several columns together: UNIQUE (dept_id, name) means a name is unique inside a department.

INSERT INTO employees (first_name, last_name, email, salary)
VALUES ('Meera', 'Iyer 2', 'meera.iyer@example.com', 90000);
-- ERROR:  duplicate key value violates unique constraint "employees_email_key"
-- DETAIL:  Key (email)=(meera.iyer@example.com) already exists.

MySQL: ERROR 1062 (23000): Duplicate entry 'meera.iyer@example.com' for key 'employees.email'. Case matters: Meera.Iyer@example.com is a different value in PostgreSQL but a duplicate in MySQL (case-insensitive collation). To make emails case-insensitive in PostgreSQL use a unique index on lower(email) (indexes are in Module 5).

NOT NULL

The simplest and most valuable constraint. Columns are nullable by default, so you must say NOT NULL every time a value is required. Decide per column: is "unknown" a valid state? A hire date, yes it must exist; a project end_date, no, it can be open.

INSERT INTO employees (first_name, email, salary) VALUES ('Zoya', 'z@example.com', 50000);
-- ERROR:  null value in column "last_name" of relation "employees" violates not-null constraint
-- DETAIL:  Failing row contains (13, Zoya, null, z@example.com, null, null, 50000.00, ...).

MySQL: ERROR 1364 (HY000): Field 'last_name' doesn't have a default value when the column is omitted, or ERROR 1048 (23000): Column 'last_name' cannot be null when NULL is given.

CHECK

CHECK tests a condition on the row's own columns. The row is accepted when the condition is TRUE or unknown (NULL). This surprises people: CHECK (salary > 0) lets a NULL salary through, so pair it with NOT NULL when the value is mandatory. A check cannot contain a subquery or look at other rows; use a unique index, foreign key or trigger for that.

INSERT INTO employees (first_name, last_name, email, salary)
VALUES ('Zoya', 'Khan', 'zoya.khan@example.com', -5);
-- ERROR:  new row for relation "employees" violates check constraint "employees_salary_check"
-- DETAIL:  Failing row contains (13, Zoya, Khan, zoya.khan@example.com, null, null, -5.00, ...).

UPDATE projects SET end_date = '2023-01-01' WHERE project_id = 1;
-- ERROR:  new row for relation "projects" violates check constraint "ck_projects_dates"

MySQL 8.0.16+: ERROR 3819 (HY000): Check constraint 'employees_chk_1' is violated. Older MySQL accepted the syntax and ignored it, so confirm the version.

DEFAULT

DEFAULT is not a rule but a fallback: when an INSERT leaves the column out (or says the word DEFAULT), the database uses the default. It can be a constant or an expression such as now() or CURRENT_DATE. It is used only when the column is missing. Explicitly inserting NULL does not trigger the default; it stores NULL, or fails if the column is NOT NULL.

INSERT INTO orders (customer_id) VALUES (6);               -- status = 'PLACED', today's date
INSERT INTO orders (customer_id, status) VALUES (6, NULL);
-- ERROR:  null value in column "status" of relation "orders" violates not-null constraint

Adding and removing constraints later

ALTER TABLE employees ADD CONSTRAINT uq_employees_email UNIQUE (email);
ALTER TABLE employees ADD CONSTRAINT ck_employees_salary CHECK (salary > 0);
ALTER TABLE employees ALTER COLUMN last_name SET NOT NULL;
ALTER TABLE employees ALTER COLUMN hire_date SET DEFAULT CURRENT_DATE;
ALTER TABLE employees DROP CONSTRAINT ck_employees_salary;

Rule: constraints see rows, not statements' intent

They run on every INSERT and UPDATE. A constraint that fails aborts the whole statement (all rows of a multi-row insert) and, inside a transaction, marks the transaction as failed in PostgreSQL: you must ROLLBACK before running anything else.

Convention: be strict by default

Start every column as NOT NULL and relax it only when "no value" is a real state. Add CHECK for ranges, small value lists and date order. Put the real rules in the database and translate its errors (SQLState 23505 unique, 23503 foreign key, 23502 not null, 23514 check) into clean API messages in Spring.

Mistake: checking "does it exist" in Java, then inserting

Wrong: race condition

if (!repo.existsByEmail(email)) {   // two requests can both pass here
    repo.save(new Employee(email));
}

Right: UNIQUE plus handling the error

try {
    repo.save(new Employee(email));          // UNIQUE decides
} catch (DataIntegrityViolationException e) {
    throw new EmailAlreadyUsedException(email);
}

Edge cases

  • Several NULLs in a UNIQUE column are fine; several empty strings are not. Do not store '' where you mean NULL.
  • CHECK passes on NULL. CHECK (end_date >= start_date) passes when end_date is NULL, which is what ck_projects_dates relies on.
  • MySQL's CHECK before 8.0.16 was parsed and ignored.

Interview angle

Likely: "primary key vs unique key" (one per table, never NULL vs many, NULLs allowed), "can a unique column hold several NULLs?" (yes), "does CHECK reject NULL?" (no), and "how do you stop duplicate emails under concurrent requests?" (a unique constraint, not an application check).

Foreign keys and referential actions

A foreign key forces a column to hold only values that exist in another table's key, which keeps relationships valid. ON DELETE and ON UPDATE decide what happens to the child rows when the parent changes: refuse, delete, or set NULL.

What a foreign key guarantees

In employees, dept_id must be a real departments.dept_id or NULL. The table that holds the foreign key is the child; the table it points to is the parent. The database then blocks two things: inserting (or updating to) a child row whose parent does not exist, and deleting (or changing the key of) a parent that still has children, unless an action says otherwise. This is referential integrity. The foreign key must point to a column that is a primary key or has a unique constraint.

-- inline form (PostgreSQL; MySQL IGNORES this form)
dept_id INT REFERENCES departments (dept_id)

-- table form (works everywhere, can be named)
CONSTRAINT fk_employees_dept FOREIGN KEY (dept_id) REFERENCES departments (dept_id)
    ON DELETE SET NULL ON UPDATE CASCADE

Errors when the rule is broken

INSERT INTO employees (first_name, last_name, email, dept_id, salary)
VALUES ('Zoya', 'Khan', 'zoya.khan@example.com', 99, 50000);
-- ERROR:  insert or update on table "employees" violates foreign key constraint "fk_employees_dept"
-- DETAIL:  Key (dept_id)=(99) is not present in table "departments".

DELETE FROM departments WHERE dept_id = 1;
-- ERROR:  update or delete on table "departments" violates foreign key constraint
--         "fk_projects_dept" on table "projects"
-- DETAIL:  Key (dept_id)=(1) is still referenced from table "projects".

MySQL words: ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (...) and ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (...). A NULL foreign key is always allowed, as the CEO's dept_id shows; add NOT NULL when the relationship is mandatory (projects.dept_id).

ON DELETE and ON UPDATE actions

ActionWhen the parent row is deleted or its key changesUse when
NO ACTION (default)Error. Checked at the end of the statement; in PostgreSQL the check can be deferred to commit time.Safe default
RESTRICTError immediately, never deferrable. In MySQL (InnoDB) it behaves the same as NO ACTION.You want an unmistakable block (products that were sold)
CASCADEThe child rows are deleted (or their key is updated to the new value) Children have no meaning without the parent (order lines, project assignments)
SET NULLThe child's column becomes NULL (column must be nullable) The link is optional (employee's department)
SET DEFAULTThe child's column becomes its default value Rare. PostgreSQL only; InnoDB rejects it.

The sample schema uses all the common ones. Watch each in a transaction and roll back afterwards, so the data stays unchanged:

BEGIN;

-- SET NULL: HR (3) has employees 4, 11, 12, but also projects. Remove the project first.
DELETE FROM projects WHERE dept_id = 3;
DELETE FROM departments WHERE dept_id = 3;
SELECT emp_id, first_name, dept_id FROM employees WHERE emp_id IN (4, 11, 12) ORDER BY emp_id;

-- CASCADE: deleting order 1 deletes its two lines in order_items
DELETE FROM orders WHERE order_id = 1;
SELECT COUNT(*) AS lines_of_order_1 FROM order_items WHERE order_id = 1;

-- RESTRICT: product 1 was sold, so it cannot be deleted
DELETE FROM products WHERE product_id = 1;   -- ERROR (inside a transaction: now aborted)

ROLLBACK;

ON UPDATE works the same way for changes to the parent key, but keys rarely change, so the default NO ACTION is almost always right. You do not need it with surrogate ids.

Choosing the action

Foreign keys need indexes on the child side

PostgreSQL indexes the parent key (it is a primary key) but does not create an index on the foreign-key column of the child. Deleting a department then has to scan all of employees to look for children, and joins on that column are slow. Add one yourself: CREATE INDEX idx_employees_dept_id ON employees (dept_id);. MySQL InnoDB creates it automatically if none exists. See Module 5.

Special cases

  • Self-reference: employees.manager_id points to employees.emp_id. The top of the tree has NULL. Inserting a row that refers to a row inserted later fails in MySQL (row-by-row check) unless you insert in the right order.
  • Composite foreign keys: a key with two columns references a composite key and is declared with both columns in the same constraint.
  • Deferrable constraints (PostgreSQL): DEFERRABLE INITIALLY DEFERRED delays the check until COMMIT, useful for loading circular references.
  • Many-to-many uses a junction table with two foreign keys and a composite primary key, like employee_projects and order_items (designed in Module 4).

Rule: always declare foreign keys

"We check it in the application" is how orphan rows (orders for deleted customers) are born. Declare the foreign key, make the child column NOT NULL when the link is mandatory, and index it.

Mistake: CASCADE everywhere

ON DELETE CASCADE on orders.customer_id would delete a customer's whole order history, and the invoices, with one careless DELETE. Cascade only for true parts-of-a-whole. Many systems never delete at all and use a deleted_at or is_active column (soft delete).

Edge cases

  • SET NULL on a NOT NULL column fails at definition time in MySQL, and at delete time in PostgreSQL.
  • Cascades chain: deleting a customer can delete orders, which delete order items.
  • MySQL ignores inline REFERENCES, so always use the table-level form for portability.
  • A database dump may need constraints disabled to load tables in any order; in PostgreSQL pg_dump orders them correctly.

Interview angle

Typical questions: "what happens when you delete a parent row that has children?" (error by default; cascade or set null if declared), "RESTRICT vs NO ACTION" (when the check runs; same in MySQL), "does PostgreSQL index a foreign key column?" (no, create the index), and the JPA link: @OneToMany(cascade = REMOVE) is Hibernate deleting children, while ON DELETE CASCADE is the database doing it.

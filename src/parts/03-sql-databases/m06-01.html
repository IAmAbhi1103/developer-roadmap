Relational databases are the right default, but they are not the only tool. Some jobs, such as caching a product page for 60 seconds, counting page views at 50,000 per second, storing flexible documents, or searching text, fit other kinds of stores better. This module is a tour of the "beyond relational" world: what the main NoSQL families are, how Redis and MongoDB work, what the CAP theorem really says, how databases copy and split data across servers, and how you change a schema safely over time with Flyway or Liquibase.

You do not need to master every tool. The goal is to choose well, speak about the trade-offs in an interview, and use Redis and MongoDB at a working level. Redis caching connects to Spring's cache abstraction in Spring Boot · Module 6; replication and sharding return as system design topics in System Design · Module 5; and migrations are part of every Spring Boot project with a database (Spring Boot · Module 3). It builds on the relational basics of Modules 1–3, the design rules of Module 4 and the transaction ideas of Module 5.

SQL vs NoSQL, and when to use each

NoSQL is a family of non-relational stores (key-value, document, wide-column, graph, search) that trade some relational features, such as joins and strict schemas, for scale, flexibility or speed; start with a relational database and add a NoSQL store when a specific need justifies it.

What "NoSQL" means

NoSQL ("not only SQL") is a loose label for databases that do not use the relational model of tables, rows and joins. They appeared because some workloads (web-scale traffic, huge write volumes, flexible data, caching) were awkward or expensive to run on one relational server. Different NoSQL databases have little in common except that they are not relational, so always ask "which family?"

ACID vs BASE

Relational databases promise ACID (Module 5). Many distributed NoSQL systems relax it to BASE: Basically Available (the system keeps answering even when parts fail), Soft state (data may change without input while copies converge) and Eventually consistent (if writes stop, all copies become equal after some time). BASE is a description of the trade-off, not a standard. Note that several NoSQL stores now offer transactions (MongoDB multi-document transactions, DynamoDB transactions), and PostgreSQL scales further than most people expect, so the line is blurrier than the slogans.

Practical rules:

  • Money, orders, inventory, anything with relationships and correctness rules: relational.
  • Cache, sessions, rate limiting, leaderboards: Redis next to your main database.
  • Documents read and written as a whole, with changing fields: a document store (or PostgreSQL JSONB, which is often enough).
  • Massive append-only writes with a known access pattern: wide-column.
  • Search with ranking and typo tolerance: a search engine, fed from the main database.
  • Deep relationship queries (friends of friends): a graph database.

Polyglot persistence

Polyglot persistence means using several databases in one system, each for what it does best. A food-delivery platform might keep orders and payments in PostgreSQL (the source of truth), cache menus and sessions in Redis, search restaurants in Elasticsearch, and store the rider location stream in a wide-column store. The price is real: more systems to run, monitor, back up and keep consistent. A copy in another store is a derived copy; the relational database stays the source of truth, and the copies are rebuilt from it (via events or change data capture). Add each new store only when a measured need appears.

Convention: default to PostgreSQL, justify every addition

A single PostgreSQL gives you transactions, joins, JSONB, full-text search and decent queue support. Many products never need anything else. Add Redis when caching or counters demand it, and others only with a clear reason.

Mistake: choosing NoSQL "because it scales" or "to avoid schema design"

A schema-less store moves the schema into your code and your data, where it is harder to check. Teams that start with a document database and later need joins and transactions face a painful migration. Choose by access patterns and consistency needs, not fashion.

Interview angle

  • SQL vs NoSQL? Relational: structured, relationships, ACID, flexible queries. NoSQL: specific models (key-value, document, wide-column, graph, search) for scale, flexibility or speed on known access patterns, often with weaker consistency.
  • ACID vs BASE? Strict transactional guarantees versus availability and eventual convergence.
  • Which database for X? Name the family and justify with the access pattern and the consistency need; mention that the relational database stays the source of truth.
  • What is polyglot persistence? Several stores, each for its strength, with one source of truth.

Redis: an in-memory data structure store

Redis keeps data in memory and offers rich types (strings, lists, hashes, sets, sorted sets) with sub-millisecond commands, key expiry and optional persistence; it is mostly used as a cache, session store, rate limiter or leaderboard next to the main database.

What Redis is

Redis (Remote Dictionary Server) is a key-value store where values are data structures. All data lives in RAM, so reads and writes take well under a millisecond, and a single server can handle hundreds of thousands of operations per second. Keys are strings; values can be several types, each with its own commands.

  • Mostly single-threaded command execution. One thread runs commands one at a time, so every command is atomic and there are no locks or race conditions inside a command. Recent versions use extra threads for network I/O, but commands still execute serially. The consequence: one slow command (such as KEYS * on millions of keys) blocks everyone.
  • Memory is the limit. Data must fit in RAM (or you set a limit and an eviction policy).
  • Persistence is optional (below).

(integer) 1
127.0.0.1:6379> SET lock:order:7 "worker-1" EX 30 NX     # NX: only set if the key does not exist

127.0.0.1:6379> INCR page:views                          # atomic counter
(integer) 1
127.0.0.1:6379> INCR page:views
(integer) 2
127.0.0.1:6379> DEL greeting
(integer) 1

A key with no expiry lives forever. TTL returns remaining seconds, -1 if there is no expiry and -2 if the key does not exist. SET key value EX 60 NX is one atomic command: create only if absent, with an expiry. It is the basis of simple locks and of "do this only once" checks.

Use both for important data, or neither for a pure cache (a cache can always be rebuilt from the database). Redis is not a replacement for your primary database for data you cannot lose.

Memory limit and eviction

Set maxmemory and an maxmemory-policy in redis.conf (or with CONFIG SET). When memory is full, Redis evicts keys by the policy:

PolicyEvicts
noeviction (default)Nothing; writes fail with an out-of-memory error
allkeys-lruLeast recently used key among all keys (a good cache default)
allkeys-lfuLeast frequently used among all keys
volatile-lru, volatile-lfuSame, but only keys that have a TTL
volatile-ttlKeys with the shortest time to live
allkeys-random, volatile-randomRandom keys

Use cases

  • Cache: store query results or rendered pages with a TTL (next article).
  • Sessions: a login session as a hash or string with a TTL, shared by all app servers.
  • Rate limiting: INCR rate:user:42:minute, set EXPIRE 60 on first use, block when the count passes the limit.
  • Leaderboards: sorted sets give rank and top-N in logarithmic time.
  • Queues and streams: lists or Streams for simple work queues (for serious messaging use Kafka or RabbitMQ).
  • Distributed locks: SET lock:x token NX PX 30000 and release only if the token still matches (a small Lua script). Use with caution: a lock with a timeout can expire while the holder is still working, and a failover can lose the lock. Use libraries such as Redisson rather than hand-rolling, and never rely on it alone for money.

From Java

@Service
public class MenuCache {
    private final StringRedisTemplate redis;

    public MenuCache(StringRedisTemplate redis) { this.redis = redis; }

    public void put(long restaurantId, String json) {
        redis.opsForValue().set("menu:" + restaurantId, json, Duration.ofMinutes(5));
    }
    public String get(long restaurantId) {
        return redis.opsForValue().get("menu:" + restaurantId);   // null if missing or expired
    }
}

Setup and the @Cacheable abstraction are in Spring Boot · Module 6. Official docs: redis.io/docs.

Rule: every cache key gets a TTL, and keys have a naming scheme

Use type:id:field style names (menu:12, session:abc) and always set an expiry for cached data, so stale or forgotten keys clean themselves up.

Mistake: KEYS * in production, and unbounded keys

KEYS * scans every key and blocks the single thread. Use SCAN (cursor-based, incremental). Also avoid huge values and giant lists/sets (millions of members in one key): one slow operation delays every client.

Edge cases

  • Setting a key again with SET removes its previous TTL unless you pass KEEPTTL.
  • Expiry is lazy plus periodic sampling, so an expired key can occupy memory for a short time.
  • Redis transactions (MULTI/EXEC) run commands together without interleaving, but have no rollback of commands that fail at run time. They are not SQL transactions.

Interview angle

  • Why is Redis fast? In-memory data, simple data structures, mostly single-threaded execution with no lock overhead, efficient protocol.
  • RDB vs AOF? Snapshots (fast restart, may lose minutes) versus a write log (less loss, larger and slower to replay).
  • When is Redis the wrong choice? As the only copy of important data, or for complex queries and joins.
  • Which type for a leaderboard? A sorted set (ZADD, ZREVRANGE).

Caching patterns: cache-aside, read-through, write-through, write-behind

A cache keeps recent results in fast storage in front of the database; cache-aside (the app checks the cache, then the database, then fills the cache) is the most common pattern, and the hard parts are invalidation and stampedes.

Why cache

The database is the slow, shared, expensive part of the request path. A menu that changes once a day but is read 10,000 times an hour should not hit PostgreSQL 10,000 times. A cache answers repeats from memory: faster responses and less load on the database. The price is the possibility of stale data: the cache and the database can disagree for a while.

Cache-aside (lazy loading)

The application owns the logic. It is the default pattern with Redis and Spring's @Cacheable.

public Menu getMenu(long restaurantId) {
    String key = "menu:" + restaurantId;
    String cached = redis.opsForValue().get(key);
    if (cached != null) {
        return json.fromJson(cached, Menu.class);                 // hit
    }
    Menu menu = menuRepository.loadMenu(restaurantId);            // miss: read the database
    redis.opsForValue().set(key, json.toJson(menu), Duration.ofMinutes(5));
    return menu;
}

public void updatePrice(long itemId, long restaurantId, long newPaise) {
    menuRepository.updatePrice(itemId, newPaise);                 // write the database first
    redis.delete("menu:" + restaurantId);                         // then invalidate the cache
}

Pros: only requested data is cached; a cache outage only slows things down. Cons: the first request after a miss is slow, and there is a window where cache and database differ.

Read-through

The application talks only to the cache. On a miss, the cache layer itself loads the data from the database and stores it. The logic moves out of your code into a cache library or provider (for example a loading cache with a loader function). From the caller's view it is the same as cache-aside, with less boilerplate.

Write-through

Every write goes to the cache, and the cache writes to the database synchronously before returning.

Cache and database stay consistent and reads are always fresh. Writes are slower (two writes), and you cache data that may never be read.

Write-behind (write-back)

Writes go to the cache and return immediately; the cache saves them to the database later, in batches.

Very fast writes and fewer database writes (good for counters like "views"), but if the cache fails before flushing, data is lost. Not for payments or orders.

Cache invalidation

"There are only two hard things in computer science: cache invalidation and naming things." Your options:

  • TTL: let entries expire after N seconds. Simple; accept staleness up to N.
  • Explicit delete on write: delete (or update) the key when the data changes, as in the code above. Delete rather than update the cached value; it avoids two writers racing to set different values.
  • Versioned keys: include a version in the key (menu:12:v7) so old entries simply stop being used.
  • Combine TTL and delete: delete for freshness, TTL as a safety net against missed deletes.

A subtle race: reader A misses and loads old data; writer updates the database and deletes the key; reader A then writes the old data into the cache. A short TTL limits the damage.

Cache stampede (thundering herd)

When a popular key expires, hundreds of requests miss at once and all hit the database to rebuild it, which can overload it. Defences:

  • Single-flight / lock: only the first request rebuilds; others wait briefly or serve the old value.
  • TTL jitter: add a random few seconds to TTLs so many keys do not expire together.
  • Refresh ahead: refresh popular keys in the background before they expire.
  • Cache negative results too (a short TTL for "not found") so missing ids don't hammer the database.

Rule: the database is the source of truth; the cache must be rebuildable

You should be able to flush the entire cache and lose nothing but speed. If you cannot, the data does not belong only in a cache.

Mistake: caching everything, and caching without measuring

Cache data that is read often, changes rarely and is costly to compute. Caching per-user or rapidly changing data gives a low hit ratio and more staleness bugs than speed. Track the hit ratio; if it is low, the cache is not helping.

In real projects

Most Spring Boot services use cache-aside through @Cacheable and @CacheEvict with a Redis cache manager, for reference data (menus, configuration, product details), sessions and rate limits. Hot paths such as login, checkout and payments stay on the database.

Interview angle

  • Explain cache-aside. Check the cache; on a miss read the database and fill the cache; on a write update the database and delete the key.
  • Write-through vs write-behind? Synchronous write to both (consistent, slower) versus cache first and database later (fast, risk of loss).
  • How do you invalidate? TTL plus delete on write; versioned keys.
  • What is a cache stampede and how do you stop it? Many misses at once on an expired hot key; use a lock/single-flight, TTL jitter or background refresh.

Subqueries: scalar, IN, derived tables and ANY/ALL

A subquery is a SELECT inside another statement, in parentheses. It can return one value (scalar), a list (for IN) or a whole table (a derived table in FROM). Use it when one query needs the answer of another.

Why and where

"Employees who earn more than the company average" needs two steps: compute the average, then compare. With a subquery you write both in one statement and the database runs the inner part first (or rewrites it into a join). A subquery can sit in three places:

PositionMust returnExample use
WHERE / HAVINGone value, or one column for INcompare with an average
FROMany table (needs an alias)aggregate, then join the result
SELECT listexactly one valuea per-row lookup or count

Scalar subquery

A scalar subquery returns one row with one column, and can be used wherever a single value fits.

SELECT first_name, salary
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees)
ORDER BY salary DESC, emp_id;
 first_name |  salary
------------+-----------
 Meera      | 300000.00
 Vikram     | 220000.00
 Karan      | 160000.00
 Ananya     | 150000.00
 Priya      | 150000.00
 Rahul      | 150000.00
(6 rows)

The inner query does not depend on the outer one, so it runs once. If it returns two or more rows where one value is expected, the statement fails:

SELECT first_name FROM employees
WHERE salary = (SELECT salary FROM employees WHERE dept_id = 1);
-- ERROR:  more than one row returned by a subquery used as an expression

MySQL says ERROR 1242 (21000): Subquery returns more than 1 row. Fix by using an aggregate (MAX(salary)), IN, or LIMIT 1 with an ORDER BY when you truly want one row. If the subquery returns no row, the scalar value is NULL, and the comparison matches nothing. If it returns two columns you get ERROR: subquery has too many columns.

Subquery with IN

IN (subquery) tests whether a value appears in the single column the subquery returns. Products that were sold at least once:

SELECT product_id, name
FROM products
WHERE product_id IN (SELECT product_id FROM order_items)
ORDER BY product_id;
 product_id |        name
------------+---------------------
          1 | Wireless Mouse
          2 | Mechanical Keyboard
          3 | USB-C Cable
          4 | Notebook A5
          5 | Gel Pen Pack
          6 | Water Bottle
(6 rows)

The Desk Lamp (id 7) was never sold. The inner query returns product ids with duplicates, which does not matter: IN only asks "is it there?" and never multiplies the outer rows (unlike a join). The negated form NOT IN has the NULL trap described in Join traps.

Derived tables: a subquery in FROM

A subquery in FROM acts as a temporary table for this one statement. It must have an alias (required by MySQL, and by PostgreSQL before version 16). It is the usual way to aggregate first and then join or filter on the result. Employees paid above their own department's average:

SELECT e.first_name, e.salary, d.avg_salary
FROM employees AS e
JOIN (SELECT dept_id, ROUND(AVG(salary), 2) AS avg_salary
      FROM employees
      GROUP BY dept_id) AS d ON d.dept_id = e.dept_id
WHERE e.salary > d.avg_salary
ORDER BY e.emp_id;
 first_name |  salary   | avg_salary
------------+-----------+------------
 Vikram     | 220000.00 |  144000.00
 Ananya     | 150000.00 |  128333.33
 Sunita     | 120000.00 |   80000.00
 Priya      | 150000.00 |  144000.00
 Rahul      | 150000.00 |  144000.00
 Karan      | 160000.00 |  128333.33
(6 rows)

Meera is missing: her dept_id is NULL, so she matches no group. This is also where the logical order bites: you cannot compare a salary with AVG(salary) in the same query level, because the aggregate does not exist at WHERE time, but you can compare with a column of a derived table that was already computed. Nested derived tables get hard to read; CTEs are the cleaner way to write them.

Subquery in the SELECT list

A scalar subquery in the select list computes one extra value per row, for example the share of the company payroll:

SELECT first_name,
       salary,
       ROUND(100 * salary / (SELECT SUM(salary) FROM employees), 1) AS pct_of_payroll
FROM employees
WHERE dept_id = 3
ORDER BY emp_id;
 first_name |  salary   | pct_of_payroll
------------+-----------+----------------
 Sunita     | 120000.00 |            7.3
 Farhan     |  65000.00 |            4.0
 Isha       |  55000.00 |            3.3
(3 rows)

(Window functions do this more elegantly: percent of total.)

ANY and ALL

ANY (same as SOME) is true if the comparison holds for at least one value of the subquery; ALL if it holds for every value. = ANY (…) is the same as IN. Employees who earn more than everyone in Sales:

SELECT first_name, salary
FROM employees
WHERE salary > ALL (SELECT salary FROM employees WHERE dept_id = 2)
ORDER BY salary DESC;
 first_name |  salary
------------+-----------
 Meera      | 300000.00
 Vikram     | 220000.00
(2 rows)

salary > ALL (…) equals salary > (SELECT MAX(…)); the second form is easier to read, so ALL and ANY are rare in practice. Beware: if the subquery returns an empty set, ALL is true for every row and ANY is false. A NULL inside the list makes ALL unknown.

Subquery, join or CTE?

The optimizer often rewrites a subquery into a join, so do not choose for speed alone. Choose for readability: a scalar comparison is clearest as a subquery, a lookup of columns is clearest as a join, and a multi-step calculation is clearest as a CTE.

Rule: know how many rows and columns a subquery returns

After =, >, <: one row, one column. After IN: one column, any number of rows. In FROM: anything, with an alias. In SELECT: one row, one column.

Mistake: using = where IN is needed

Wrong: breaks as soon as 2 rows come back

WHERE dept_id = (SELECT dept_id FROM departments WHERE location = 'Pune')

Right: IN accepts any number of rows

WHERE dept_id IN (SELECT dept_id FROM departments WHERE location = 'Pune')

The wrong version works today because only one department is in Pune, and fails the day a second one opens. Code that works only by luck is a bug waiting.

Edge cases

  • MySQL (before 8.0.14 in many cases) could not use LIMIT inside an IN subquery (This version of MySQL doesn't yet support 'LIMIT & IN/ALL/ANY/SOME subquery'); wrap it in a derived table.
  • MySQL does not let you UPDATE or DELETE a table while selecting from the same table in a subquery (ERROR 1093); wrap the subquery in a derived table or use a join.
  • The subquery's columns are limited to its own FROM unless it is correlated (next article).

Interview angle

Likely questions: "employees earning more than the average", "what error does a scalar subquery with two rows give", "does a derived table need an alias" and "subquery vs join, which is faster" (usually the same plan; measure with EXPLAIN).

Correlated subqueries and EXISTS

A correlated subquery uses a column of the outer query, so conceptually it runs once per outer row. EXISTS is the most useful correlated test: it asks "does at least one row match?" and stops at the first.

How a correlated subquery runs

In the earlier subqueries, the inner query stood alone. A correlated one refers to the outer row:

SELECT e.first_name, e.salary
FROM employees AS e
WHERE e.salary > (SELECT AVG(x.salary)
                  FROM employees AS x
                  WHERE x.dept_id = e.dept_id)      -- refers to the outer row e
ORDER BY e.emp_id;
 first_name |  salary
------------+-----------
 Vikram     | 220000.00
 Ananya     | 150000.00
 Sunita     | 120000.00
 Priya      | 150000.00
 Rahul      | 150000.00
 Karan      | 160000.00
(6 rows)
  1. Take the first outer row (Meera, dept_id = NULL).
  2. Run the inner query with e.dept_id filled in from that row. Here nothing matches (NULL equals nothing), so AVG is NULL, the comparison is unknown, and Meera is dropped.
  3. Take the next outer row (Vikram, dept 1), average department 1 again (144000), compare, keep.
  4. Repeat for every row.

This "once per row" picture is the meaning. The optimizer often turns it into a join or computes each department average once. But sometimes it cannot, and a correlated subquery on a big table is then slow: 1 million outer rows means 1 million inner runs. The same result via a derived table (previous article) computes the averages once.

Correlated subquery in the SELECT list

SELECT d.name,
       (SELECT COUNT(*) FROM employees e WHERE e.dept_id = d.dept_id) AS headcount
FROM departments AS d
ORDER BY d.dept_id;
    name     | headcount
-------------+-----------
 Engineering |         5
 Sales       |         3
 HR          |         3
 Marketing   |         0
(4 rows)

Marketing shows 0 because a scalar COUNT over no rows is 0. This reads simply, but for big tables prefer LEFT JOIN … GROUP BY.

EXISTS

EXISTS (subquery) is true when the subquery returns at least one row, and false when it returns none. What the subquery selects does not matter (convention: SELECT 1), the database only checks whether a row exists and stops at the first match.

SELECT c.customer_id, c.name
FROM customers AS c
WHERE EXISTS (SELECT 1
              FROM orders AS o
              WHERE o.customer_id = c.customer_id)
ORDER BY c.customer_id;
 customer_id |     name
-------------+--------------
           1 | Aarav Shah
           2 | Diya Kapoor
           3 | Kabir Singh
           4 | Ishita Joshi
           5 | Rohan Das
(5 rows)

NOT EXISTS gives the opposite (customers 6 and 7), and is the safest anti-join (Join traps). Because it is a yes/no test, EXISTS never multiplies rows and is NULL-safe: it only looks at whether a row came back.

IN vs EXISTS vs JOIN

The same question, "customers with orders", written three ways:

-- IN
SELECT name FROM customers WHERE customer_id IN (SELECT customer_id FROM orders);
-- EXISTS
SELECT name FROM customers c WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
-- JOIN (needs DISTINCT, otherwise one row per order)
SELECT DISTINCT c.name FROM customers c JOIN orders o ON o.customer_id = c.customer_id;
INEXISTSJOIN
Rows returned5 customers5 customers10 rows (one per order) unless DISTINCT

On performance: modern PostgreSQL and MySQL 8 turn IN and EXISTS into a semi join and usually pick the same plan, so the old advice "EXISTS is always faster" is outdated. What does matter is an index on the inner table's join column (orders.customer_id). Verify with EXPLAIN (Module 5).

More EXISTS patterns

SELECT first_name FROM employees e
WHERE EXISTS (SELECT 1 FROM employee_projects ep WHERE ep.emp_id = e.emp_id);

SELECT d.name FROM departments d
WHERE EXISTS (SELECT 1 FROM projects p
              WHERE p.dept_id = d.dept_id AND p.end_date IS NULL);

The first returns 9 people (Sunita, Ananya, Priya, Rahul, Arjun, Divya, Karan, Neha, Farhan). The second returns Engineering, HR and Marketing; the Sales project has ended. Also useful: "WHERE NOT EXISTS (…) for the opposite", and the "relational division" question "customers who bought all products of a category", written as a double NOT EXISTS.

Rule: qualify every column inside a correlated subquery

Inside (SELECT … FROM employees x WHERE x.dept_id = e.dept_id) use different aliases for the outer and inner copies. If you leave a name unqualified, SQL resolves it to the innermost table first and the "correlation" quietly becomes x.dept_id = x.dept_id, which is always true.

Mistake: a correlated subquery in SELECT on a large table

A per-row subquery over a million-row table without an index on the inner join column is a slow query. Rewrite it as a join with GROUP BY, or a window function. If you see N+1 queries from the application, that is the same idea at another level: Hibernate's lazy loading runs one query per parent.

Edge cases

  • EXISTS is true even if the subquery's selected value is NULL; only the existence of a row counts. SELECT NULL, SELECT 1 and SELECT * behave alike.
  • A correlated subquery can reference only the enclosing query levels, not sibling tables in the outer FROM (use LATERAL in PostgreSQL for that).

Interview angle

"What is a correlated subquery?" (depends on the outer row, conceptually runs per row.) "IN vs EXISTS?" (same result for positive tests, EXISTS is NULL-safe when negated; planners treat both as semi joins.) "Customers without orders", "departments with no employees" and "employees who earn more than their department average" are the usual tasks.

UNION, UNION ALL, INTERSECT and EXCEPT

Set operators stack the results of two queries on top of each other. UNION removes duplicates, UNION ALL keeps them and is faster, INTERSECT keeps rows found in both, and EXCEPT keeps rows found only in the first.

Joins go sideways, set operations go down

A join adds columns from another table. A set operation adds rows from another query. Both queries must produce the same number of columns, with compatible types in the same order. The column names of the result come from the first query.

SELECT location AS city FROM departments
UNION
SELECT city FROM customers
ORDER BY city;
   city
-----------
 Ahmedabad
 Bengaluru
 Delhi
 Kolkata
 Mumbai
 Pune
(6 rows)

UNION vs UNION ALL

The departments give 4 cities and the customers give 7 (Mumbai twice), so there are 11 rows in total. UNION sorts or hashes the result to remove duplicates and returns 6 distinct cities. UNION ALL simply appends and returns all 11:

SELECT COUNT(*) FROM (
    SELECT location AS city FROM departments
    UNION ALL
    SELECT city FROM customers
) AS all_cities;
 count
-------
    11
(1 row)

Default to UNION ALL when you know the inputs are disjoint (this month's orders plus last month's) and use UNION only when you really need de-duplication. Note that UNION compares whole rows, so it also merges two different people who happen to have the same selected values.

A practical UNION ALL

A single contact list of HR employees and Mumbai customers, with a label for the source:

SELECT first_name || ' ' || last_name AS name, email, 'employee' AS kind
FROM employees WHERE dept_id = 3
UNION ALL
SELECT name, email, 'customer'
FROM customers WHERE city = 'Mumbai'
ORDER BY kind, name;
      name       |           email            |   kind
-----------------+----------------------------+----------
 Aarav Shah      | aarav.shah@example.com     | customer
 Sara Khan       | sara.khan@example.com      | customer
 Farhan Shaikh   | farhan.shaikh@example.com  | employee
 Isha Banerjee   | isha.banerjee@example.com  | employee
 Sunita Patel    | sunita.patel@example.com   | employee
(5 rows)

ORDER BY goes once, at the very end, and applies to the combined result; it can only use the column names (or positions) of the output. To sort or limit one part, wrap it in parentheses or a subquery.

INTERSECT

ORDER BY 1;

INTERSECT is "in A and in B"; EXCEPT is "in A but not in B" (Oracle calls it MINUS). Order matters for EXCEPT: A except B differs from B except A. Both remove duplicates; PostgreSQL also has INTERSECT ALL and EXCEPT ALL. Unlike NOT IN, EXCEPT treats NULLs as equal, so it is safe with NULLs. The same results can be written with IN, NOT EXISTS or joins; set operators read more like the question. Precedence: INTERSECT binds tighter than UNION and EXCEPT; use parentheses.

MySQL support

UNION and UNION ALL work everywhere. MySQL added INTERSECT and EXCEPT only in version 8.0.31; before that you must write them with joins or NOT EXISTS.

Rule: same column count, compatible types, same order

SELECT dept_id FROM departments UNION SELECT name, city FROM customers;
ERROR:  each UNION query must have the same number of columns

SELECT dept_id FROM departments UNION SELECT name FROM customers;
ERROR:  UNION types integer and character varying cannot be matched

Cast when needed: SELECT dept_id::TEXT …. Columns are matched by position, not name, so a swapped order silently mixes the data.

Mistake: UNION where UNION ALL is meant

Using UNION by habit costs a sort of the whole result and can quietly drop legitimate duplicate rows (two orders of the same amount on the same day). Write UNION ALL unless you want de-duplication.

Edge cases

  • NULLs count as equal for removing duplicates in UNION, INTERSECT and EXCEPT (different from =).
  • You cannot use ORDER BY on a column that is not in the output of a set operation.
  • A literal such as NULL in the first query takes its type from the other query in PostgreSQL; add a cast if you get a type error.

Interview angle

"UNION vs UNION ALL" (duplicates, speed), "UNION vs JOIN" (rows vs columns), "how do you find rows in table A that are not in table B" (EXCEPT, NOT EXISTS, LEFT JOIN … IS NULL), and "what rules must the two queries follow" (column count, types, position).

CASE WHEN: conditional logic in SQL

CASE is SQL's if/else: it returns the value of the first branch whose condition is true. It works in SELECT, WHERE, ORDER BY, GROUP BY, inside aggregates and in UPDATE.

CASE is an expression, not a statement

Beginners from Java expect CASE to be like an if statement that runs code. It is not. It is an expression: it produces one value, like a + b does. That is why you can put it anywhere a value is allowed: a SELECT column, a WHERE condition, an argument of SUM, a sort key, the right side of SET. In Java terms it is closer to the ternary operator cond ? x : y (or a switch expression) than to an if block.

  1. The database takes the first WHEN and evaluates its condition for the current row.
  2. If the condition is true, it returns the matching THEN value and stops. Later branches are not looked at.
  3. If it is false or unknown (NULL), it moves to the next WHEN.
  4. If every branch fails, it returns the ELSE value, or NULL when there is no ELSE.

Searched CASE and simple CASE

The searched form tests any condition in each branch; the simple form compares one expression with several values (like Java's switch).

SELECT first_name, salary,
       CASE
           WHEN salary >= 200000 THEN 'Senior'
           WHEN salary >= 100000 THEN 'Mid'
           ELSE 'Junior'
       END AS band
FROM employees
WHERE emp_id <= 5
ORDER BY emp_id;
 first_name |  salary   |  band
------------+-----------+--------
 Meera      | 300000.00 | Senior
 Vikram     | 220000.00 | Senior
 Ananya     | 150000.00 | Mid
 Sunita     | 120000.00 | Mid
 Priya      | 150000.00 | Mid
(5 rows)
SELECT order_id,
       CASE status
           WHEN 'PLACED'    THEN 'We received your order'
           WHEN 'SHIPPED'   THEN 'On the way'
           WHEN 'DELIVERED' THEN 'Delivered'
           ELSE 'Cancelled'
       END AS message
FROM orders;

Rules of evaluation: branches are tested top to bottom and the first true one wins, so order the conditions from most to least specific (Meera is 300000, which matches both the first and second condition; she gets 'Senior'). If nothing matches and there is no ELSE, the result is NULL. All THEN/ELSE values must have compatible types; mixing a number and text fails with ERROR: CASE types integer and text cannot be matched. In a simple CASE, the comparison is =, so WHEN NULL never matches; use a searched CASE WHEN x IS NULL.

CASE in GROUP BY and aggregates

To count people per band, compute the band in a derived table (or repeat the expression in GROUP BY):

SELECT band, COUNT(*) AS people
FROM (SELECT CASE WHEN salary >= 200000 THEN 'Senior'
                  WHEN salary >= 100000 THEN 'Mid'
                  ELSE 'Junior' END AS band
      FROM employees) AS t
GROUP BY band
ORDER BY band;
  band  | people
--------+--------
 Junior |      4
 Mid    |      6
 Senior |      2
(3 rows)

Inside an aggregate, CASE decides which rows count: SUM(CASE WHEN status = 'CANCELLED' THEN 1 ELSE 0 END). This is conditional aggregation, covered in its own article.

Several bands as columns

Put one CASE inside each aggregate and you get a ready cross-tab: employees per department, split by salary band. Each row counts in exactly one band because the ranges do not overlap.

SELECT dept_id,
       SUM(CASE WHEN salary >= 200000 THEN 1 ELSE 0 END)                       AS senior,
       SUM(CASE WHEN salary >= 100000 AND salary < 200000 THEN 1 ELSE 0 END) AS mid,
       SUM(CASE WHEN salary < 100000 THEN 1 ELSE 0 END)                       AS junior
FROM employees
GROUP BY dept_id
ORDER BY dept_id;
 dept_id | senior | mid | junior
---------+--------+-----+--------
       1 |      1 |   3 |      1
       2 |      0 |   2 |      1
       3 |      0 |   1 |      2
  (null) |      1 |   0 |      0
(4 rows)

The column totals (2, 6, 4) match the band counts above. More about this pattern, including FILTER, is in Conditional aggregation.

Handling NULL with CASE

A searched CASE can test IS NULL, which is how you turn "missing" into a label. Grouping by that label needs the expression repeated, or the output position (PostgreSQL and MySQL both accept GROUP BY 1; the logical order that allows aliases is in Logical order of a query):

SELECT CASE WHEN phone IS NULL THEN 'missing' ELSE 'present' END AS phone_status,
       COUNT(*) AS customers
FROM customers
GROUP BY 1
ORDER BY 1;
 phone_status | customers
--------------+-----------
 missing      |         3
 present      |         4
(2 rows)

CASE in ORDER BY

Alphabetical order is rarely the business order. CASE lets you define your own:

SELECT order_id, status
FROM orders
ORDER BY CASE status
             WHEN 'PLACED'    THEN 1
             WHEN 'SHIPPED'   THEN 2
             WHEN 'DELIVERED' THEN 3
             ELSE 4

CASE in UPDATE

One statement can apply different changes to different rows, and it is atomic:

BEGIN;
UPDATE employees
SET salary = salary * CASE WHEN salary < 100000 THEN 1.10
                           WHEN salary < 200000 THEN 1.05
                           ELSE 1.00 END;
ROLLBACK;   -- practice only

MySQL vs PostgreSQL: UPDATE with several columns

PostgreSQL evaluates every right-hand side with the old row values, so SET a = b, b = a really swaps the two columns. MySQL applies assignments left to right and later ones see the new values, so the same statement leaves both columns equal to the old b. When you need a swap on MySQL, put the logic in one CASE on a single column or use a temporary value.

Interviewers sometimes ask for IF or DECODE. Name them, then say you prefer CASE because it is standard SQL and portable. A Spring Boot app that may change databases should keep to the standard forms.

Rule: every branch must produce the same kind of value

The database picks one result type for the whole CASE. THEN 1 … ELSE 'none' fails in PostgreSQL with ERROR: CASE types integer and text cannot be matched. Cast one side (CAST(n AS TEXT)) or return the same type everywhere. Mixing 1 and 1.5 is fine; the result becomes numeric.

CASE and indexes

A CASE around a column in WHERE or ORDER BY hides the column from a normal index, so large tables may be scanned and sorted fully. Prefer plain conditions in WHERE: (:status IS NULL OR status = :status) instead of a CASE that returns true or false. For a business sort order on a big table, store the rank in a column (or a small lookup table with a sort_order) and sort by that.

Mistake: comparing with NULL inside CASE

Wrong: never true

SELECT name,
       CASE phone WHEN NULL THEN 'missing' ELSE 'present' END AS s
FROM customers;      -- Diya shows 'present'

Right: IS NULL in a searched CASE

SELECT name,
       CASE WHEN phone IS NULL THEN 'missing' ELSE 'present' END AS s
FROM customers;

The simple form turns into phone = NULL, which is unknown, so the branch is skipped. Other slips in the same family: forgetting END (a syntax error near the next keyword) and writing ELSE before the last WHEN.

Convention: always write ELSE, and format one branch per line

An explicit ELSE makes the "nothing matched" case a decision rather than an accident. Keep CASE for simple mappings; if you have twenty branches, the mapping belongs in a lookup table you can join to.

Mistake: overlapping branches in the wrong order

Wrong: everyone is 'Junior'

CASE WHEN salary >= 0      THEN 'Junior'
     WHEN salary >= 100000 THEN 'Mid' END

Right: most specific first

CASE WHEN salary >= 100000 THEN 'Mid'
     ELSE 'Junior' END

Edge cases

  • A false condition and an unknown (NULL) condition both skip the branch.
  • Branches are evaluated lazily, so a division inside a skipped branch normally does not run. Do not rely on it: the optimizer may fold constants early.
  • The result type is the common type of all branches; NULL alone does not set a type.

Interview angle

Typical tasks: "grade students by marks", "count pass and fail in one query", "pivot rows to columns", "swap values with one UPDATE" (SET gender = CASE gender WHEN 'M' THEN 'F' ELSE 'M' END). Know that CASE returns NULL when nothing matches.

A strong answer also says: the first true branch wins, so branch order matters; all branches share one type; a simple CASE cannot test NULL; and CASE inside SUM is how you pivot. If asked to "avoid division by zero", show NULLIF(b, 0) as the short form of the CASE.

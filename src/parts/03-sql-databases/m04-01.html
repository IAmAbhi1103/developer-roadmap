Database design is the work you do before you write CREATE TABLE: deciding which tables exist, which columns they have, how they connect and which rules the database must enforce. It matters more than any query trick. A slow query can be rewritten in an afternoon, but a wrong table layout leaks into every query, every JPA entity, every API response and every row already stored, and it gets more expensive to fix each month.

This module teaches design as a process: collect requirements, find the entities, draw an ER diagram, turn relationships into foreign keys and join tables, choose keys, normalize to remove redundancy, and pick sensible names and data types. It ends with a complete worked design of a food-delivery app (users, restaurants, menu items, orders, order items, payments) with DDL and the queries it must support. It builds on the tables and constraints from Module 1 and prepares the ground for indexes and transactions in Module 5. The tables you design here become JPA entities in Spring Boot · Module 3. PostgreSQL syntax is the default; MySQL differences are noted where they matter.

  • Turn a written requirement into entities, attributes and relationships, and draw them as an ER diagram.
  • Implement one-to-one, one-to-many and many-to-many relationships in SQL, including join tables.
  • Explain every kind of key and choose between surrogate and natural keys, and between BIGINT and UUID.
  • Spot update, insert and delete anomalies, normalize a table step by step to 3NF and BCNF, and decide when to denormalize on purpose.
  • Apply practical patterns: audit columns, soft delete, status columns, money, UTC timestamps, JSONB, trees and multi-tenancy.
  • Name tables and constraints consistently, pick the right data type for each column, and design a complete schema for a real app.

The database design process: from requirements to tables

Good design is a repeatable process: write down the requirements, find the entities, give them attributes, connect them with relationships, choose keys, normalize, add constraints and indexes, and finally check that your important queries are easy to write.

Why design before you create tables

Adding a column later takes a minute. Undoing a wrong shape takes months. Suppose the first version stores an order as one row with a text column items holding 'biryani,coke'. Every report, every discount rule and every "how many biryanis did we sell" question now needs string parsing, and a year of data has to be converted by a migration that someone must write carefully. A short design session at the start removes this whole class of pain.

Design happens at three levels. The conceptual level is the ER diagram: entities and relationships, no data types. The logical level is the set of tables, columns, keys and normal forms, still independent of one product. The physical level adds data types, indexes, partitioning and engine-specific choices. This module walks through all three in order.

The eight steps

  1. Requirements. Find out what the system must remember and which questions it must answer. Write them as plain sentences.
  2. Entities. The nouns: the things you keep data about (customer, order, restaurant).
  3. Attributes. The facts about each entity (name, email, price).
  4. Relationships. The verbs between entities, with cardinality (how many on each side) and optionality (is the link compulsory?).
  5. Keys. Choose a primary key for every table, mark the natural unique identifiers, and place the foreign keys.
  6. Normalize. Remove redundancy with the normal forms so each fact is stored once (later in this module).
  7. Constraints and indexes. Add NOT NULL, UNIQUE, CHECK and foreign keys so bad data cannot get in, then indexes for foreign keys and the main queries.
  8. Review the queries. Write the ten most important queries. If one needs an awkward chain of joins, or the design cannot answer it, go back and fix the model.

A small example: a library

Start from the requirements, written the way a client would say them:

1. The library has members. Each member has a name, an email and a join date.
2. The library has books. Each book has a title, an ISBN and one or more authors.
3. The library owns several physical copies of a book. Each copy has a shelf code.
4. A member can borrow a copy. We must remember the borrow, due and return dates.
5. A member may hold at most 5 books at a time.
6. We must list overdue loans and every book a member has ever borrowed.

Finding entities, attributes and relationships

Nouns become entities or attributes. To decide which, ask: does this thing have facts of its own, or can many other things share it? If yes, it is an entity with its own table. "Author" has a name, a country and many books, so it is an entity. "Email" is just a fact about a member, so it is a column. The tricky case is the address. If a user has exactly one address and you never treat it separately, columns on users are fine. If a user can have several addresses, or an order must remember the address it was sent to, make addresses a table.

Verbs become relationships. Ask the cardinality question in both directions. "Can one member borrow many copies? Can one copy be borrowed by many members?" Over time both answers are yes, which is many-to-many. A relationship that carries its own data (borrow date, due date) becomes a table of its own: that is the loan entity. Ask the optionality question too: must every copy belong to a book? Yes. Must every member have a loan? No.

Rules become constraints or code. "Due date is not before borrow date" is a CHECK. "A member may hold at most 5 books" cannot be written as a simple constraint, because it depends on other rows; it lives in the service layer (often with a lock, see Locking) or in a trigger.

Convention: design on paper, review in a pull request

Draw the ER diagram first (a whiteboard photo or a Mermaid block in the repository README) and let a teammate review it before anyone writes a migration. It is far cheaper to move a box on a diagram than to move a column in production.

Mistake: designing from the screen or from the Java classes

A screen shows a mix of facts from several entities, and a class often mirrors one JSON response. If the tables copy them, you get repeated columns and duplicated data.

Wrong: a fixed number of repeated columns

CREATE TABLE students (
    id       BIGINT PRIMARY KEY,
    name     TEXT,
    course1  TEXT,
    course2  TEXT,
    course3  TEXT   -- what about the fourth course?
);

Right: one row per fact in a link table

CREATE TABLE enrollments (
    student_id BIGINT REFERENCES students (id),
    course_id  BIGINT REFERENCES courses (id),
    PRIMARY KEY (student_id, course_id)
);

Tip: write the queries before the DDL

List the five to ten most important questions in plain words ("all orders of a customer, newest first", "revenue per restaurant per day"). A good design answers each with a simple join and an index. If a question needs five joins or string parsing, the model is wrong, and finding that out on paper costs nothing.

Edge case: when to bend the process

A throw-away prototype can start with fewer tables, but never without primary keys. Reporting and analytics databases are often shaped differently on purpose (wide, denormalized tables), see Denormalization. And not every rule belongs in the database: validation that needs an external service, such as checking a GSTIN against a government API, stays in the application.

Interview angle

"Design the database for a food-delivery / hotel-booking / library app" is a very common round. A strong answer follows the steps out loud: clarify the requirements, list entities, state each relationship with its cardinality, draw the ER diagram, choose keys, normalize to 3NF, add constraints, mention indexes for the key queries, and name one trade-off (for example a deliberate denormalization such as storing the price on the order line).

ER diagrams: entities, attributes and relationships

An ER (entity-relationship) diagram is a picture of the things you store (entities), the facts about them (attributes) and how they connect (relationships), including how many on each side (cardinality) and whether the link is compulsory (optionality).

The three building blocks

Entity
A thing you store data about that can be told apart from other things: a customer, an order, a restaurant. An entity type becomes a table; each single customer is a row. Textbooks call the table an "entity set" and the row an "entity".
Attribute
A fact about an entity: name, email, price. It becomes a column.
Relationship
An association between entities: a customer places orders; an order contains menu items. It becomes a foreign key or a join table. A relationship can have attributes too, such as quantity on the link between an order and a menu item.

Kinds of attributes

Textbooks classify attributes, and the classes tell you how to store them.

Age is the classic derived attribute. If you store age it is wrong the day after the birthday, so store date_of_birth and calculate. Storing a derived value is sometimes right, for speed or as a history snapshot, but then it is a deliberate denormalization, not an accident.

Cardinality and optionality

Cardinality is the maximum number of related rows on each side: one-to-one (1:1), one-to-many (1:N) or many-to-many (M:N). Optionality (also called participation) is the minimum: must a related row exist (1) or may it be absent (0)? Put together, each end of a relationship is one of four things: exactly one, zero or one, one or many, zero or many. Say them as sentences:

  • A restaurant has zero or many menu items. A menu item belongs to exactly one restaurant.
  • A user has zero or one profile. A profile belongs to exactly one user.
  • An order contains one or many items. An item line belongs to exactly one order.

The database enforces the "exactly one" side easily: a foreign key column that is NOT NULL. It cannot enforce "one or many" on the other side with a plain foreign key, because the order row has to exist before its first item row does. "An order must have at least one item" is checked in the service layer, or with a deferred constraint trigger.

The symbol next to an entity tells how many of that entity relate to one row of the other. In the diagram below, customers ||--o{ orders reads "one customer places zero or many orders", and read backwards "each order belongs to exactly one customer".

A solid line (--) marks an identifying relationship, where the child cannot exist without the parent. A dotted line (..) marks a non-identifying one. In an entity box, PK, FK and UK mark primary, foreign and unique key columns; write the type as a single word (varchar, not varchar(100)).

Weak entities

A weak entity has no key of its own. It is identified only through an owner (a strong entity), and it disappears when the owner does. An order line is the standard case: "line 2" means nothing without saying which order. Its key combines the owner's key with a partial key: PRIMARY KEY (order_id, line_no), and its foreign key to the owner is usually ON DELETE CASCADE. In practice many teams give weak entities a surrogate id as well (JPA is easier with a single-column key), but the dependency is still visible in the NOT NULL foreign key.

Rule: every line has a verb and two cardinality ends

A relationship line with no label, or with one end missing its symbol, is ambiguous. Label each line with a verb ("places", "contains") and give both ends a cardinality and an optionality.

Convention: keep diagrams readable

Name entities exactly like the tables will be named. On a big diagram list only the key columns and the columns that matter for understanding. Draw the full column list in the DDL, not in the picture. Split a large system into several diagrams, one per area (orders, payments, catalogue).

Mistake: reading the foot on the wrong end

  • The crow's foot sits at the "many" end: next to orders, not next to customers. Beginners often draw it on the wrong side and then put the foreign key in the wrong table.
  • Drawing a many-to-many line between two tables in the physical model. Databases have no such thing; the join table must be a box on the diagram.
  • Turning "an employee has several phone numbers" into phone1, phone2 columns. That is a multi-valued attribute: use a table.

Edge cases: recursive, three-way and subtype relationships

  • Recursive: an entity related to itself, such as an employee who manages other employees. One table with manager_id pointing to employees.id (see Hierarchies).
  • Ternary: a fact that links three entities at once, such as a doctor treating a patient at a clinic. Use one join table with three foreign keys.
  • Subtype (specialization): a payment that is either a card payment or a UPI payment. Model it with one table plus a type column, or a parent table with one child table per subtype.

Tip: tools that draw ER diagrams for you

pgAdmin 4 has an ERD tool, DBeaver can generate a diagram from an existing schema (very useful when you inherit an unknown database), and MySQL Workbench has EER diagrams. For documentation inside a repository, a Mermaid erDiagram block is version-controlled text.

Interview angle

  • Entity, attribute, relationship: table, column, foreign key or join table.
  • Cardinality vs optionality: cardinality is the maximum (one or many), optionality is the minimum (zero or one).
  • What is a weak entity? One that has no key of its own and depends on an owner entity, like an order line; its key includes the owner's key.
  • Derived attribute: calculated from others (age from date of birth); normally not stored.
  • How do you map a multi-valued attribute? A separate table with a foreign key back to the entity.

Views, updatable views and materialized views

A view is a saved query with a name that you use like a table. It stores no data, so it is always current. A materialized view (PostgreSQL) does store the result and must be refreshed. Views hide complexity and sensitive columns.

What and why

Some queries are used again and again: the join of orders, items and products, or the department summary every dashboard needs. Instead of pasting that SQL into ten places, save it once as a view. Callers write SELECT * FROM department_summary and the database substitutes the saved query. Reasons to use views:

  • Reuse: one definition of a business rule ("what counts as revenue").
  • Simplicity: hide joins and calculations from report writers and from the application.
  • Security: expose some columns or rows and not others.
  • Stable interface: change the tables underneath and keep the view's shape.

Creating a view

CREATE OR REPLACE VIEW department_summary AS
SELECT d.dept_id,
       d.name,
       COUNT(e.emp_id)              AS headcount,
       COALESCE(SUM(e.salary), 0)   AS payroll
FROM departments AS d
LEFT JOIN employees AS e ON e.dept_id = d.dept_id
GROUP BY d.dept_id, d.name;

SELECT * FROM department_summary ORDER BY dept_id;
 dept_id |    name     | headcount |  payroll
---------+-------------+-----------+-----------
       1 | Engineering |         5 | 720000.00
       2 | Sales       |         3 | 385000.00
       3 | HR          |         3 | 240000.00
       4 | Marketing   |         0 |         0
(4 rows)

The view stores only the SELECT. When you query it, the database expands the definition into your query and optimizes the whole thing together, so a filter you add on the view can still use the base tables' indexes. Querying a view is exactly as fast as running its query. Remove it with DROP VIEW department_summary. CREATE OR REPLACE VIEW can change the query, but in PostgreSQL it can only add columns at the end; renaming, removing or retyping columns needs DROP and CREATE. Avoid SELECT * inside a view: the column list is fixed when the view is created, and later table changes do not flow in.

Views for security

Give a role access to the view, not the table. The payroll team sees salaries, everybody else gets the directory without them:

CREATE VIEW employee_directory AS
SELECT emp_id, first_name, last_name, email, dept_id     -- no salary, no manager
FROM employees;

REVOKE ALL ON employees FROM reporting_role;
GRANT SELECT ON employee_directory TO reporting_role;

A PostgreSQL view runs with the privileges of its owner by default, which is what makes this work. Since PostgreSQL 15 you can create it WITH (security_invoker = true) to check the caller's rights instead. Row-level restrictions are also possible with a WHERE in the view, or with row level security policies (Module 5).

Updatable views

A simple view (one table, no GROUP BY, DISTINCT, aggregates, window functions or set operations) is automatically updatable in PostgreSQL (since 9.3) and MySQL: INSERT, UPDATE and DELETE on the view change the base table. A view with a join, an aggregate or DISTINCT is read-only unless you add INSTEAD OF triggers.

CREATE VIEW engineering_staff AS
SELECT emp_id, first_name, last_name, email, dept_id, salary
FROM employees
WHERE dept_id = 1
WITH CHECK OPTION;

UPDATE engineering_staff SET salary = 95000 WHERE emp_id = 8;     -- fine: Divya stays visible
UPDATE engineering_staff SET dept_id = 2 WHERE emp_id = 8;
-- ERROR:  new row violates check option for view "engineering_staff"

WITH CHECK OPTION forbids changes through the view that would make the row disappear from the view (moving Divya to Sales). Without it, the update would succeed and she would vanish from engineering_staff.

Materialized views

A materialized view runs the query once and stores the result like a table. Reads are fast (and the result can be indexed), but the data is only as fresh as the last refresh. Perfect for expensive aggregations: a dashboard that reads yesterday's totals.

CREATE MATERIALIZED VIEW monthly_revenue AS
SELECT DATE_TRUNC('month', o.order_date)::DATE AS month,
       SUM(oi.quantity * oi.unit_price)         AS revenue
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.order_id
WHERE o.status <> 'CANCELLED'
GROUP BY DATE_TRUNC('month', o.order_date);

CREATE UNIQUE INDEX uq_monthly_revenue_month ON monthly_revenue (month);

SELECT * FROM monthly_revenue ORDER BY month;

REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_revenue;   -- rebuild without blocking readers
   month    | revenue
------------+---------
 2026-01-01 | 5256.00
 2026-02-01 | 2797.00
 2026-03-01 | 7594.00
 2026-04-01 | 2778.00
(4 rows)

REFRESH MATERIALIZED VIEW recomputes everything and locks readers while it works. CONCURRENTLY keeps the old data readable, but needs a unique index on the view. Schedule refreshes with pg_cron, an operating-system cron job, or a Spring @Scheduled task. MySQL has no materialized views: build a summary table and refresh it with a scheduled job or event.

Views and Spring

From Java a view looks like a table. You can map a read-only JPA entity to a view (@Entity @Immutable on a class with @Table(name = "department_summary")), or select from it with a native query or a Spring Data projection. Flyway or Liquibase migrations create the view like any other object, in the right order after its tables.

Rule: a view depends on its tables

You cannot drop or retype a column used by a view (ERROR: cannot drop column salary of table employees because other objects depend on it). Drop the view first, or drop with CASCADE and recreate it. Keep view definitions in version-controlled migrations.

Mistake: building views on views on views

Each layer hides the real cost, and the optimizer may not flatten them well. Nested views are hard to debug and easy to slow down. Prefer a few well-named views over a tower of them.

Edge cases

  • An ORDER BY inside a view definition is not a promise about the order of the final result; sort in the outer query.
  • A materialized view is not updated by changes to its base tables, not even in the same transaction.
  • Views cannot take parameters. For that use a function that returns a table (Functions, procedures and triggers).
  • MySQL view algorithms: MERGE (inlined) or TEMPTABLE (materialized temporarily, slower); MySQL picks by itself.

Interview angle

"What is a view? Does it store data?" (no, a stored query), "view vs materialized view" (freshness vs speed), "can you update through a view" (simple views yes, with WITH CHECK OPTION to protect the filter), "why use views" (reuse, security, abstraction).

Functions, stored procedures and triggers

A function is reusable code stored in the database that returns a value, a procedure is called with CALL and can control transactions, and a trigger runs code automatically when rows change. They are powerful, and many teams use them sparingly.

Why code lives in the database at all

SQL alone has no variables, loops or if-statements. Databases add a procedural language to the server: PL/pgSQL in PostgreSQL, a SQL/PSM dialect in MySQL. Code stored there runs next to the data, so it avoids network round trips, can be shared by every application that connects, and can enforce rules nobody can bypass. The price is discussed at the end of this article.

Functions

A function takes arguments and returns a value (or a table). Simple ones can be written in plain SQL:

CREATE OR REPLACE FUNCTION dept_headcount(p_dept INT)
RETURNS INT
LANGUAGE sql STABLE
AS $$
    SELECT COUNT(*)::INT FROM employees WHERE dept_id = p_dept;
$$;

SELECT dept_headcount(1) AS engineering, dept_headcount(4) AS marketing;
 engineering | marketing
-------------+-----------
           5 |         0
(1 row)

The body sits between $$ … $$ (dollar quoting, so you need no escaping for single quotes). STABLE tells the planner that the function does not change data and gives the same answer inside one statement; the options are IMMUTABLE (same inputs always give the same output, can be used in an index), STABLE and VOLATILE (the default; may change anything). A function can also return a table, which acts like a parameterised view: RETURNS TABLE (name TEXT, salary NUMERIC) AS $$ SELECT … $$, called with SELECT * FROM top_earners(3).

With PL/pgSQL you get variables, conditions and loops, and errors:

CREATE OR REPLACE FUNCTION salary_grade(p_salary NUMERIC)
RETURNS TEXT
LANGUAGE plpgsql IMMUTABLE
AS $$
BEGIN
    IF p_salary IS NULL THEN
        RETURN NULL;
    ELSIF p_salary >= 200000 THEN
        RETURN 'Senior';
    ELSIF p_salary >= 100000 THEN
        RETURN 'Mid';
    END IF;
    RETURN 'Junior';
END;
$$;

SELECT first_name, salary_grade(salary) AS grade FROM employees WHERE emp_id IN (1, 8);
 first_name | grade
------------+--------
 Meera      | Senior
 Divya      | Junior
(2 rows)

Stored procedures

A procedure (CREATE PROCEDURE, PostgreSQL 11 and later; MySQL has them too) is invoked with CALL, does not return a value in a SELECT, and, unlike a function, can COMMIT or ROLLBACK inside it. It fits batch work and multi-step operations.

CREATE OR REPLACE PROCEDURE raise_salary(p_emp INT, p_percent NUMERIC)
LANGUAGE plpgsql
AS $$
BEGIN
    IF p_percent <= 0 OR p_percent > 50 THEN
        RAISE EXCEPTION 'Percent must be between 0 and 50, got %', p_percent;
    END IF;

    UPDATE employees
    SET salary = ROUND(salary * (1 + p_percent / 100), 2)
    WHERE emp_id = p_emp;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Employee % does not exist', p_emp;
    END IF;
END;
$$;

CALL raise_salary(8, 10);      -- Divya: 90000 becomes 99000
CALL raise_salary(99, 10);     -- ERROR:  Employee 99 does not exist

Spring calls them with JdbcTemplate / SimpleJdbcCall, or in JPA with @Procedure and @NamedStoredProcedureQuery. In MySQL the syntax needs a changed statement delimiter, because the body contains semicolons:

DELIMITER $$
CREATE PROCEDURE raise_salary(IN p_emp INT, IN p_percent DECIMAL(5,2))
BEGIN
    UPDATE employees SET salary = ROUND(salary * (1 + p_percent / 100), 2) WHERE emp_id = p_emp;
END$$
DELIMITER ;
CALL raise_salary(8, 10);

Triggers

A trigger runs a function automatically BEFORE or AFTER an INSERT, UPDATE or DELETE, once FOR EACH ROW (or once per statement). Inside, NEW is the new row and OLD the old one. In PostgreSQL a trigger is two objects: a trigger function that RETURNS TRIGGER, and the CREATE TRIGGER that attaches it.

Example 1: keep an updated_at column current.

ALTER TABLE products ADD COLUMN updated_at TIMESTAMPTZ NOT NULL DEFAULT now();

CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.updated_at := now();      -- change the row before it is written
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_products_updated_at
BEFORE UPDATE ON products
FOR EACH ROW
EXECUTE FUNCTION set_updated_at();

Now every UPDATE products … refreshes updated_at even if the application forgot. (EXECUTE FUNCTION is PostgreSQL 11+ syntax; older versions say EXECUTE PROCEDURE.) MySQL does this without a trigger: updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP.

Example 2: an audit log of salary changes.

CREATE TABLE salary_audit (
    audit_id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    emp_id      INT           NOT NULL,
    old_salary  NUMERIC(10,2) NOT NULL,
    new_salary  NUMERIC(10,2) NOT NULL,
    changed_at  TIMESTAMPTZ   NOT NULL DEFAULT now(),
    changed_by  TEXT          NOT NULL DEFAULT current_user
);

CREATE OR REPLACE FUNCTION log_salary_change()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO salary_audit (emp_id, old_salary, new_salary)
    VALUES (OLD.emp_id, OLD.salary, NEW.salary);
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_employees_salary_audit
AFTER UPDATE OF salary ON employees
FOR EACH ROW
WHEN (OLD.salary IS DISTINCT FROM NEW.salary)
EXECUTE FUNCTION log_salary_change();

UPDATE employees SET salary = 95000 WHERE emp_id = 8;
SELECT audit_id, emp_id, old_salary, new_salary, changed_by FROM salary_audit;
 audit_id | emp_id | old_salary | new_salary | changed_by
----------+--------+------------+------------+------------
        1 |      8 |   90000.00 |   95000.00 | app_user
(1 row)

The trigger fires only when the salary column changes and the value really differs (the WHEN clause), and writes to the audit table in the same transaction: if the update rolls back, so does the audit row. That is why audit logs are the best use of triggers: nobody can forget them, whatever application or script changes the data.

Pros and cons

Pros

  • Runs next to the data: fewer round trips for bulk work.
  • One implementation shared by every application and script.
  • Cannot be bypassed; ideal for audit trails and integrity rules.
  • Permissions can allow a procedure without allowing direct table access.

Cons

  • Hidden behaviour: an UPDATE that "also does something else" surprises developers.
  • Harder to test, debug, version and review than Java; weaker tooling.
  • Ties you to one database's dialect; scaling logic means scaling the database, the hardest tier to scale.
  • Deployment is split: the code and its database objects must be released together.

In real projects: why many teams keep business logic in the application

A Spring Boot team usually keeps business rules in Java services, where they are unit-tested, versioned with the code and portable. They use the database for what it is best at: constraints, indexes, transactions, sometimes audit triggers and the updated_at trigger, and stored procedures for heavy batch jobs or legacy systems (banks and ERPs often have thousands). In Spring, @CreatedDate and @LastModifiedDate (Spring Data auditing) or Hibernate's @UpdateTimestamp replace the updated_at trigger when only the application writes to the table. Triggers are the right tool when other writers exist.

Rule: triggers must be fast, small and idempotent-safe

A trigger runs inside the triggering statement's transaction, for every affected row. A slow trigger slows every write; a trigger that updates the same table can fire itself again (recursion). Keep them short, and document each one where developers will find it.

Mistake: business workflow in triggers

"When an order is inserted, a trigger reduces stock, sends an email row, updates the customer's total…" becomes a chain no one can follow, and a bulk load of 100,000 orders runs 100,000 extra statements. Put workflows in a service and use triggers only for simple, local rules.

Edge cases

  • Row triggers do not fire for TRUNCATE; statement-level truncate triggers do.
  • A BEFORE trigger returning NULL silently cancels the operation for that row. RAISE EXCEPTION cancels the whole statement.
  • Bulk loads such as COPY still fire triggers (unless disabled with ALTER TABLE … DISABLE TRIGGER).
  • In MySQL, triggers are not fired by cascading foreign-key actions.

Interview angle

"Function vs procedure" (function returns a value and is used inside queries; procedure is called with CALL and can manage transactions), "what is a trigger and when would you use one" (audit, timestamps), and the architecture question "would you put business logic in stored procedures?" A balanced answer lists the pros and cons above and says you prefer the application layer for business rules.

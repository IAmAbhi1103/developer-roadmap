Isolation levels and concurrency problems

The isolation level decides how much one transaction sees of others running at the same time: higher levels prevent more anomalies (dirty, non-repeatable and phantom reads, lost update, write skew) at the price of more blocking or more retries; PostgreSQL defaults to Read Committed and MySQL InnoDB to Repeatable Read.

The problem: transactions run at the same time

Real databases serve hundreds of transactions at once. If each one saw every change of every other one instantly, results would be unpredictable. If each one waited for the others to finish (strict serial order), the database would be safe but slow. Isolation levels are the dial between the two. The anomalies below are what can go wrong at lower settings.

MVCC in simple words

MVCC (multi-version concurrency control) is how PostgreSQL and InnoDB achieve isolation without making readers wait for writers. An UPDATE does not overwrite a row; it writes a new version and keeps the old one. Each transaction (or each statement) works with a snapshot: the set of versions that were committed when the snapshot was taken. Readers read old versions while a writer prepares new ones, so "readers never block writers and writers never block readers". Writers still block each other on the same row. Old versions are cleaned later (VACUUM in PostgreSQL, purge in InnoDB).

The anomalies

Dirty read
Reading data another transaction has changed but not yet committed. If it rolls back, you read data that never existed.
Non-repeatable read
Reading the same row twice in one transaction and getting different values, because another transaction committed a change in between.
Phantom read
Running the same query twice and getting different rows (new or missing), because another transaction committed an insert or delete that matches your condition.
Lost update
Two transactions read a value, both compute a new one, and the second write overwrites the first, so one update is lost.
Write skew
Two transactions read overlapping data, each makes a decision, and each writes different rows; together they break a rule that each alone respected.

Levels versus anomalies

The SQL standard defines four levels. The table shows what can happen at each, in PostgreSQL's actual behaviour (the standard is weaker in places, and MySQL differs slightly).

Setting the level

-- PostgreSQL: for one transaction
BEGIN ISOLATION LEVEL REPEATABLE READ;
-- or, as the first statement inside it:
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

SHOW transaction_isolation;               -- PostgreSQL: current level
SELECT @@transaction_isolation;           -- MySQL

-- MySQL, for the next transaction only
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
@Transactional(isolation = Isolation.REPEATABLE_READ)
public void closeDayReport() { /* ... */ }

Demo 1: dirty read (and why you never see it in PostgreSQL)

Starting state: Asha's balance is 50000.

Session A                                 Session B
------------------------------------      ------------------------------------
BEGIN;
UPDATE accounts SET balance_paise = 0
  WHERE id = 1;                           -- not committed
                                          BEGIN ISOLATION LEVEL READ UNCOMMITTED;
                                          SELECT balance_paise FROM accounts
                                            WHERE id = 1;     --> 0  (dirty!)
ROLLBACK;                                 -- the 0 never existed
                                          -- PostgreSQL would show 50000 here

Demo 2: non-repeatable read at Read Committed

In Read Committed each statement gets a fresh snapshot, so it sees everything committed before it started.

Session A                                 Session B
------------------------------------      ------------------------------------
BEGIN;  -- READ COMMITTED
SELECT balance_paise FROM accounts
  WHERE id = 1;                --> 50000
                                          BEGIN;
                                          UPDATE accounts SET balance_paise = 30000
                                            WHERE id = 1;
                                          COMMIT;
SELECT balance_paise FROM accounts
  WHERE id = 1;                --> 30000   (same query, different answer)
COMMIT;

At Repeatable Read the second select in session A would still return 50000, because the snapshot is taken once, at the first statement of the transaction.

Demo 3: phantom read

Session A                                 Session B
------------------------------------      ------------------------------------
BEGIN;  -- READ COMMITTED
SELECT count(*) FROM orders
  WHERE restaurant_id = 1
    AND status = 'PLACED';     --> 3
                                          INSERT INTO orders (...)  -- restaurant 1, PLACED
                                          COMMIT;
SELECT count(*) FROM orders
  WHERE restaurant_id = 1
    AND status = 'PLACED';     --> 4   (a phantom row)
COMMIT;

Non-repeatable reads are about changes to a row you already saw; phantoms are about new or removed rows that match your condition.

Demo 4: lost update

Two customers buy the last two units of an item. The application reads the stock, subtracts in Java and writes the result back:

Session A                                 Session B
------------------------------------      ------------------------------------
BEGIN;                                    BEGIN;
SELECT stock FROM items WHERE id = 7;     SELECT stock FROM items WHERE id = 7;
  --> 10                                     --> 10
-- app computes 10 - 2 = 8                -- app computes 10 - 3 = 7
UPDATE items SET stock = 8
  WHERE id = 7;
COMMIT;
                                          UPDATE items SET stock = 7
                                            WHERE id = 7;     -- overwrites A!
                                          COMMIT;
-- final stock = 7, but 5 units were sold: should be 5

Fixes, from simplest: (1) let the database do the arithmetic, which takes a row lock for the update: UPDATE items SET stock = stock - 2 WHERE id = 7 AND stock >= 2; and check the row count; (2) lock the row when you read it: SELECT ... FOR UPDATE (see Locking); (3) add a version column and detect the conflict (optimistic locking); (4) use Repeatable Read, where PostgreSQL makes the second writer fail with "could not serialize access due to concurrent update" and you retry.

Demo 5: write skew

Rule: at least one rider must stay on shift. Two riders go off shift at the same moment:

Session A (rider 1 leaves)                Session B (rider 2 leaves)
------------------------------------      ------------------------------------
BEGIN ISOLATION LEVEL REPEATABLE READ;    BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM riders
  WHERE on_shift;              --> 2       SELECT count(*) FROM riders
                                            WHERE on_shift;       --> 2
-- 2 >= 2, safe to leave                   -- 2 >= 2, safe to leave
UPDATE riders SET on_shift = false
  WHERE id = 1;
                                          UPDATE riders SET on_shift = false
                                            WHERE id = 2;   -- different row: no conflict
COMMIT;                                   COMMIT;
-- nobody is on shift: the rule is broken

Each transaction was correct alone. They wrote different rows, so row-level conflict detection never fired. Only Serializable (in PostgreSQL, serializable snapshot isolation) notices the dependency and aborts one transaction with an error. You can also lock the rows you read (SELECT ... FOR UPDATE on all on-shift riders) or enforce the rule with a constraint or a single row that all transactions must update.

Serialization failures and retry

At Repeatable Read and Serializable, PostgreSQL may abort a transaction rather than allow an anomaly. The error has SQLSTATE 40001 (serialization_failure); a detected deadlock gives 40P01. These are not bugs: the transaction did nothing wrong and should simply be run again.

for (int attempt = 1; attempt <= 3; attempt++) {
    try {
        transferService.transfer(fromId, toId, amountPaise);   // @Transactional inside
        break;
    } catch (CannotSerializeTransactionException | DeadlockLoserDataAccessException e) {
        if (attempt == 3) throw e;
        Thread.sleep(20L * attempt);                           // small back-off
    }
}

Spring translates these SQL states into CannotSerializeTransactionException and DeadlockLoserDataAccessException. Retry the whole transaction (outside the @Transactional method), never a single statement. Spring Retry's @Retryable does this declaratively.

MySQL InnoDB differences

  • Default is Repeatable Read: plain SELECTs read a snapshot fixed at the first read.
  • Locking reads and writes (SELECT ... FOR UPDATE, UPDATE) read the latest committed data, not the snapshot, and use next-key locks (row plus gap locks) to block phantoms. A transaction can therefore see rows its own snapshot select did not show.
  • InnoDB Repeatable Read does not abort lost updates; the second writer waits for the lock and then writes. Atomic updates (SET stock = stock - 2) or FOR UPDATE remain the right tools.
  • Serializable turns plain selects into shared locking reads, so transactions block rather than abort.

Which level should you use?

LevelUse when
Read CommittedThe default for most OLTP code: each statement sees fresh data and transactions rarely abort. Combine with atomic updates or row locks for read-then-write logic.
Repeatable ReadReports and multi-statement reads that must see a consistent picture (monthly statement totals); be ready for serialization errors on writes.
SerializableRules spanning several rows that you cannot lock or constrain easily; accept retries.
Read UncommittedAlmost never.

Rule: a higher level is not a substitute for correct write logic

Read-modify-write in application code is a lost-update bug at Read Committed. Use an atomic UPDATE ... SET x = x - n, a lock, or a version check, and know what your level really guarantees.

Edge cases

  • The standard allows phantoms at Repeatable Read; PostgreSQL and InnoDB (plain reads) do not show them. Interview answers should name the standard first and mention the difference.
  • In PostgreSQL the snapshot of a Repeatable Read transaction starts at its first query, not at BEGIN.
  • Sequences and now() are not affected by isolation: now() is the transaction start time, so it stays fixed inside the transaction.

Interview angle

  • Name the isolation levels and the anomalies each prevents. Use the table: RU allows all, RC stops dirty reads, RR stops non-repeatable reads, Serializable stops phantoms and write skew.
  • Default levels? PostgreSQL Read Committed; MySQL InnoDB Repeatable Read.
  • Dirty vs non-repeatable vs phantom? Uncommitted data; a changed row; changed set of rows.
  • What is MVCC? Keeping several versions of a row, so readers use a snapshot and do not block writers.
  • You get "could not serialize access". What do you do? Retry the whole transaction.

Locking: row locks, FOR UPDATE, SKIP LOCKED and deadlocks

Databases lock rows (and sometimes tables) so concurrent writers do not collide; SELECT ... FOR UPDATE locks the rows you read, NOWAIT and SKIP LOCKED control what happens when they are busy, and two transactions waiting for each other cause a deadlock that the database breaks by aborting one.

Row locks and table locks

MVCC lets readers proceed, but two transactions that change the same row must take turns. The first UPDATE or DELETE takes an exclusive row lock; a second one on the same row waits until the first commits or rolls back. Plain SELECT takes no row lock.

LockTaken byBlocks
Exclusive row lockUPDATE, DELETE, SELECT ... FOR UPDATE Other writers and lockers of that row; not plain reads
Shared row lockSELECT ... FOR SHAREWriters of that row; other shared lockers are fine
Table lock (various modes)LOCK TABLE, most ALTER TABLE, CREATE INDEX (not concurrently), TRUNCATEDepends on the mode; the strongest blocks all reads and writes

Row locks are held until the end of the transaction. That is why long transactions are dangerous: the longer you hold locks, the longer others wait. Table-level locks from schema changes are the most disruptive (an ALTER TABLE waiting behind a long query makes every new query queue behind it). Set a lock_timeout for migrations.

SELECT ... FOR UPDATE: lock what you read

This is the pessimistic fix for read-then-write logic. Read the row and lock it in one statement; nobody else can change it until you commit.

BEGIN;
SELECT stock FROM items WHERE id = 7 FOR UPDATE;     -- locks the row; others wait here
-- application checks stock >= 2 and computes the new value
UPDATE items SET stock = stock - 2 WHERE id = 7;
COMMIT;                                              -- lock released
Session A                                 Session B
------------------------------------      ------------------------------------
BEGIN;                                    BEGIN;
SELECT stock FROM items WHERE id = 7
  FOR UPDATE;            --> 10
                                          SELECT stock FROM items WHERE id = 7
                                            FOR UPDATE;      -- waits...
UPDATE items SET stock = 8 WHERE id = 7;
COMMIT;                                   --> 8   (B continues with the new value)
                                          UPDATE items SET stock = 5 WHERE id = 7;
                                          COMMIT;

If the check and update can be one statement, prefer it: UPDATE items SET stock = stock - 2 WHERE id = 7 AND stock >= 2 is atomic, needs no explicit lock, and returns 0 rows when stock is short.

FOR SHARE, NOWAIT, SKIP LOCKED

ClauseBehaviour
FOR UPDATEExclusive lock on the selected rows; waits if busy
FOR SHAREShared lock: the row cannot change while you hold it (for example the parent row while you insert children)
... NOWAITFail immediately with an error if any row is locked, instead of waiting
... SKIP LOCKEDSilently skip rows that are locked and return the rest

SKIP LOCKED is the building block of a database job queue: many workers each claim a different job without waiting for each other.

BEGIN;

SELECT id, payload
FROM jobs
WHERE status = 'PENDING'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;          -- a row another worker holds is skipped, not waited for

-- ... process the job, then:
UPDATE jobs SET status = 'DONE' WHERE id = 101;
COMMIT;

If a worker crashes, its transaction rolls back and the job returns to PENDING by itself. FOR UPDATE NOWAIT suits "if this seat is being booked right now, tell the user to try another". Both clauses exist in PostgreSQL (SKIP LOCKED since 9.5) and MySQL 8.0+.

Deadlocks

A deadlock happens when two transactions each hold a lock the other needs. Neither can continue, ever.

Session A (1 -> 2)                         Session B (2 -> 1)
------------------------------------      ------------------------------------
BEGIN;                                    BEGIN;
UPDATE accounts SET balance_paise =
  balance_paise - 100 WHERE id = 1;       -- A holds row 1
                                          UPDATE accounts SET balance_paise =
                                            balance_paise - 50 WHERE id = 2;  -- B holds row 2
UPDATE accounts SET balance_paise =
  balance_paise + 100 WHERE id = 2;       -- A waits for B
                                          UPDATE accounts SET balance_paise =
                                            balance_paise + 50 WHERE id = 1;  -- B waits for A
-- ERROR:  deadlock detected               (one session is chosen as the victim and rolled back)
-- DETAIL:  Process 1201 waits for ShareLock on transaction 5532; blocked by process 1244.
--          Process 1244 waits for ShareLock on transaction 5531; blocked by process 1201.
-- HINT:  See server log for query details.

The database finds the cycle (PostgreSQL checks after deadlock_timeout, 1 second by default; InnoDB detects it at once), aborts one transaction with an error (SQLSTATE 40P01 in PostgreSQL, error 1213 in MySQL), and the other proceeds. Your code must retry the aborted transaction.

How to prevent deadlocks:

  • Lock in a consistent order. Always update the lower account id first, whatever the transfer direction. This removes the cycle.
  • Keep transactions short and touch as few rows as possible.
  • Lock all needed rows up front: SELECT ... WHERE id IN (1, 2) ORDER BY id FOR UPDATE.
  • Index foreign keys: a missing index can make a delete lock many rows.
  • Retry on deadlock errors.
BEGIN;
SELECT id FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;   -- always ascending
UPDATE accounts SET balance_paise = balance_paise - 100 WHERE id = 1;
UPDATE accounts SET balance_paise = balance_paise + 100 WHERE id = 2;
COMMIT;

Lock waits and timeouts

A transaction that waits for a lock waits forever by default in PostgreSQL. Set limits so a stuck session does not freeze the application:

SET lock_timeout = '3s';                       -- PostgreSQL: error if a lock wait exceeds 3 s
SET statement_timeout = '30s';
SET idle_in_transaction_session_timeout = '60s';

-- Who is blocking whom? (PostgreSQL)
SELECT pid, pg_blocking_pids(pid) AS blocked_by, state, query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

MySQL has innodb_lock_wait_timeout (50 seconds by default), after which the waiting statement fails with error 1205 "Lock wait timeout exceeded".

Rule: take locks in a fixed order and release them fast

Commit or roll back quickly. Never keep a transaction open while waiting for a user, an HTTP call or a message queue.

Mistake: FOR UPDATE on a wide range

SELECT * FROM orders WHERE status = 'PLACED' FOR UPDATE locks every placed order for as long as the transaction lives. Lock the few rows you need, with LIMIT or by id.

Edge cases

  • In PostgreSQL, inserting a row with a foreign key takes a shared lock on the referenced parent row, so many child inserts and a parent update can conflict.
  • In MySQL InnoDB, a locking read on a range also locks the gaps between index records, which can block inserts you did not expect. Use an exact unique key lookup when possible.
  • A locking read without a useful index may lock (or scan and lock) more rows than you expect; check the plan with EXPLAIN.

Interview angle

  • What does SELECT ... FOR UPDATE do? Locks the selected rows until commit so no one else can update them; the pessimistic fix for read-then-write.
  • What is SKIP LOCKED for? Work queues: workers take unlocked jobs without waiting.
  • What is a deadlock and how do you avoid it? A cycle of waits; the database aborts one victim. Consistent lock order, short transactions, retry.
  • How do you find what is blocking? pg_stat_activity and pg_blocking_pids (PostgreSQL), SHOW ENGINE INNODB STATUS (MySQL).

Optimistic vs pessimistic locking

Pessimistic locking locks the row before you change it and makes others wait; optimistic locking lets everyone proceed, stores a version number in the row, and rejects an update whose version has changed, so you retry or tell the user.

Two philosophies

  • Pessimistic: "Conflicts are likely, so prevent them." Lock the row first (SELECT ... FOR UPDATE). Others wait. Safe, simple to reason about, but holds locks and can deadlock.
  • Optimistic: "Conflicts are rare, so detect them." Read without locking, and at update time check that nobody changed the row since you read it. No locks are held while the user thinks.

Optimistic locking with a version column

Add an integer version column. Every update includes the version it read in the WHERE clause and increments it. If another transaction changed the row meanwhile, the version no longer matches, zero rows are updated, and you know there was a conflict.

ALTER TABLE items ADD COLUMN version INT NOT NULL DEFAULT 0;

-- Read (no lock)
SELECT id, stock, version FROM items WHERE id = 7;      --> stock 10, version 3

-- Update only if still version 3
UPDATE items
SET stock = 8, version = version + 1
WHERE id = 7 AND version = 3;
-- UPDATE 1  -> success.   UPDATE 0 -> someone else changed it: reload and retry or report
User A                                    User B
------------------------------------      ------------------------------------
reads stock 10, version 3                 reads stock 10, version 3
UPDATE ... SET stock = 8, version = 4
  WHERE id = 7 AND version = 3;  --> 1 row
                                          UPDATE ... SET stock = 7, version = 4
                                            WHERE id = 7 AND version = 3;  --> 0 rows
                                          -- conflict detected: reload (stock 8) and retry

This catches the lost update without any lock held across the user's think time (a form open for two minutes), which is why it is the standard for web apps and REST APIs. A timestamp column works too, but an integer version has no clock-precision problems.

JPA: @Version

JPA does this for you. Add @Version to an entity; Hibernate adds the version check to every UPDATE and increments it.

@Entity
public class Item {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private int stock;

    @Version
    private int version;          // managed by JPA: never set it yourself
}
// SQL issued: update item set stock=?, version=? where id=? and version=?
// If 0 rows are updated: OptimisticLockException
// (Spring translates it to ObjectOptimisticLockingFailureException)

In a REST API this maps well to HTTP: return the version (or an ETag) with the resource, and reject an update with 412 Precondition Failed or 409 Conflict when it is stale. See Spring Boot · Module 3 for entities and the repository layer.

Pessimistic locking in JPA

public interface ItemRepository extends JpaRepository<Item, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)                 // SELECT ... FOR UPDATE
    @Query("select i from Item i where i.id = :id")
    Optional<Item> findByIdForUpdate(@Param("id") Long id);
}

@Transactional
public void reserve(Long itemId, int qty) {
    Item item = repo.findByIdForUpdate(itemId).orElseThrow();   // row locked until commit
    if (item.getStock() < qty) throw new IllegalStateException("Out of stock");
    item.setStock(item.getStock() - qty);
}

Often the best "lock" is a constraint: a UNIQUE (show_id, seat_no) makes the database reject the second booking with no application locking at all. Catch the unique violation and say "seat taken".

Convention: add @Version to entities that users edit

It costs one column and protects against silent lost updates. Handle ObjectOptimisticLockingFailureException by returning HTTP 409 or retrying a small, safe operation.

Edge cases

  • Bulk JPQL/SQL updates bypass @Version unless you increment the version yourself.
  • Retrying an optimistic failure must reload the entity first; re-sending the same stale object fails again.
  • A pessimistic lock without a timeout can hang a request; set a lock timeout hint (jakarta.persistence.lock.timeout) or use NOWAIT.

Interview angle

  • Optimistic vs pessimistic? Detect conflicts with a version vs prevent them with a lock; choose by how often conflicts happen and how long the user holds data.
  • How does @Version work? Hibernate adds AND version = ? to the update, increments it, and throws OptimisticLockException if no row matched.
  • How do you prevent overselling the last item? Atomic conditional UPDATE, FOR UPDATE, or a version check with retry.

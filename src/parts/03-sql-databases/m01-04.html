Filters: AND, OR, NOT, IN and BETWEEN

Combine conditions with AND, OR and NOT, remembering that AND binds tighter than OR, so use parentheses. IN replaces a chain of ORs, and BETWEEN is inclusive at both ends, which is a trap for timestamps.

AND, OR and NOT

WHERE accepts any condition that is TRUE, FALSE or UNKNOWN (see NULL and three-valued logic). You build bigger conditions from smaller ones:

  • a AND b: both must be true.
  • a OR b: at least one must be true.
  • NOT a: reverses a condition (NOT (dept_id = 1)).

Precedence: AND before OR

Like multiplication before addition in maths, SQL evaluates NOT first, then AND, then OR. Comparison operators (=, >, IN, BETWEEN, LIKE) bind tighter than all three. The famous bug: you want employees of Engineering or Sales who earn more than 100000.

Wrong: read as dept 1, OR (dept 2 AND salary > 100000)

SELECT first_name, dept_id, salary
FROM employees
WHERE dept_id = 1 OR dept_id = 2 AND salary > 100000
ORDER BY emp_id;

Right: parentheses say what you mean

SELECT first_name, dept_id, salary
FROM employees
WHERE (dept_id = 1 OR dept_id = 2)
  AND salary > 100000
ORDER BY emp_id;

Whenever a WHERE mixes AND and OR, add parentheses even if you are sure about the precedence. The next reader will not be. To rewrite a negated condition use De Morgan's laws: NOT (a AND b) is NOT a OR NOT b, and NOT (a OR b) is NOT a AND NOT b.

IN: a list of allowed values

x IN (1, 3) is the same as x = 1 OR x = 3, shorter and harder to get wrong. NOT IN is the opposite.

SELECT first_name, dept_id FROM employees WHERE dept_id IN (1, 3) ORDER BY emp_id;

SELECT first_name, dept_id FROM employees WHERE dept_id NOT IN (1, 3) ORDER BY emp_id;

To include her write WHERE dept_id NOT IN (1, 3) OR dept_id IS NULL. IN also takes a subquery: dept_id IN (SELECT dept_id FROM departments WHERE location = 'Pune') (see Subqueries).

BETWEEN: an inclusive range

x BETWEEN a AND b means x >= a AND x <= b. Both ends are included. It works for numbers, dates and text.

SELECT first_name, salary
FROM employees
WHERE salary BETWEEN 90000 AND 150000
ORDER BY salary DESC, emp_id;

SELECT order_id, order_date
FROM orders
WHERE order_date BETWEEN '2026-03-01' AND '2026-03-31'
ORDER BY order_id;

Divya (exactly 90000) and the three employees at exactly 150000 are in the result, because the ends are included. Three more details:

  • Put the smaller value first. BETWEEN 150000 AND 90000 returns no rows, with no error. PostgreSQL has BETWEEN SYMMETRIC, which swaps the bounds for you.
  • NOT BETWEEN a AND b means x < a OR x > b.
  • NULL is never between anything, so NULL rows are dropped (as with every comparison).

The BETWEEN trap with timestamps

The order query above is safe because order_date is a DATE. If the column is a TIMESTAMP, the literal '2026-03-31' means 2026-03-31 00:00:00, so everything that happened later on March 31 is outside the range:

SELECT TIMESTAMP '2026-03-31 15:30:00'
       BETWEEN DATE '2026-03-01' AND DATE '2026-03-31' AS in_march;
 in_march
----------
 f
(1 row)

For dates with a time part, use a half-open range: >= '2026-03-01' AND < '2026-04-01'. It also keeps working when someone changes the column from DATE to TIMESTAMP. See Date ranges and time zones.

Putting it together

A realistic filter: staff of Engineering or Sales, paid between 100000 and 160000, who joined in 2020 or later.

SELECT first_name, dept_id, salary, hire_date
FROM employees
WHERE dept_id IN (1, 2)
  AND salary BETWEEN 100000 AND 160000
  AND hire_date >= '2020-01-01'
ORDER BY emp_id;
 first_name | dept_id |  salary   | hire_date
------------+---------+-----------+------------
 Rahul      |       1 | 150000.00 | 2020-03-02
 Arjun      |       1 | 110000.00 | 2022-08-16
 Karan      |       2 | 160000.00 | 2021-05-24
(3 rows)

Priya is out (hired 2019), Vikram earns too much, Ananya was hired in 2017, and Divya and Neha earn too little. Each condition is on its own line, so you can comment one out to see its effect.

Rule: NOT, then AND, then OR

If a condition mixes AND and OR, use parentheses. The precedence is the same in PostgreSQL and MySQL, but nobody should have to remember it.

Mistake: OR with a bare value

Wrong: the second operand is a number, not a condition

SELECT * FROM employees WHERE dept_id = 1 OR 2;
-- PostgreSQL: ERROR:  argument of OR must be type boolean, not type integer
-- MySQL: runs, treats 2 as TRUE, and returns every row

Right: repeat the column, or use IN

SELECT * FROM employees WHERE dept_id = 1 OR dept_id = 2;
SELECT * FROM employees WHERE dept_id IN (1, 2);

Another beginner error is salary > 100000 AND < 200000: each condition needs its own column, salary > 100000 AND salary < 200000, or use BETWEEN when both ends are inclusive.

Edge cases

  • Combining NULL checks with other filters needs parentheses too: WHERE dept_id = 1 OR dept_id IS NULL returns the five Engineering employees and the CEO.
  • An empty list is a syntax error: IN () fails. When a Java program builds the list, handle the empty case before sending the query.
  • Very long IN lists are slow to plan and a statement can carry only a limited number of bind parameters. Put big lists in a temporary table or a subquery. In PostgreSQL you can also pass a single array parameter: WHERE id = ANY (?).

Tip: one condition per line

Start each continuation line with AND or OR. When a result looks wrong, comment out conditions one at a time and watch the row count change.

Interview angle

  • Which is evaluated first, AND or OR? AND. Show the a OR b AND c example and fix it with parentheses.
  • Is BETWEEN inclusive? Yes, both ends. Mention the timestamp trap and the half-open range fix.
  • IN versus several ORs? Same result, IN is shorter. The difference appears with NOT IN and NULL.

Pattern matching: LIKE, ILIKE and case sensitivity

LIKE matches text against a pattern where % means "any characters" and _ means "exactly one character". It is case-sensitive in PostgreSQL (use ILIKE for case-insensitive) and case-insensitive by default in MySQL.

Case sensitivity

This is where PostgreSQL and MySQL differ, and it surprises people who move between them.

QuestionPostgreSQLMySQL
'abc' = 'ABC'falsetrue (default collation utf8mb4_0900_ai_ci: case- and accent-insensitive)
first_name LIKE 'a%' finds Ananya?NoYes
Case-insensitive searchILIKE, or LOWER(col) LIKE LOWER(x) plain LIKE

SELECT first_name FROM employees WHERE first_name LIKE 'a%';    -- 0 rows
SELECT first_name FROM employees WHERE first_name ILIKE 'a%';   -- Ananya, Arjun

SELECT name FROM products WHERE name ILIKE '%mouse%';           -- Wireless Mouse

ILIKE is a PostgreSQL extension, not standard SQL. The portable way is LOWER(first_name) LIKE 'a%', which works everywhere. Another PostgreSQL option is the citext extension, a text type that compares case-insensitively; people use it for email columns.

Escaping % and _ with ESCAPE

What if you need to find a real underscore or percent sign? The underscore in 'SAVE_10' is a wildcard, so the pattern also matches SAVEX10 and SAVE-10. Put an escape character before the wildcard and tell SQL which character it is with ESCAPE:

SELECT code
FROM (VALUES ('SAVE_10'), ('SAVEX10'), ('SAVE-10')) AS t(code)
WHERE code LIKE 'SAVE_10';                    -- _ is a wildcard: all 3 match

SELECT code
FROM (VALUES ('SAVE_10'), ('SAVEX10'), ('SAVE-10')) AS t(code)
WHERE code LIKE 'SAVE!_10' ESCAPE '!';        -- !_ means a literal underscore

The default escape character is a backslash in both databases, but backslashes are also special in some string literals (MySQL treats \ as an escape inside every string). Choosing your own character with ESCAPE avoids that confusion.

Regular expressions

When LIKE is too weak, PostgreSQL has POSIX regular expressions and MySQL has REGEXP.

TaskPostgreSQLMySQL

Regular expressions are slower than LIKE and cannot use a normal index. Use them for validation-style checks and occasional searches, not for hot queries.

LIKE and indexes

A search for names that start with a prefix (LIKE 'Ana%') can use an index in principle. A search with a leading wildcard (LIKE '%nya' or '%cable%') cannot use a normal B-tree index, so the database reads the whole table. In PostgreSQL a plain index also helps prefix searches only if the database uses the C collation or you create the index with text_pattern_ops. For "contains" searches on large tables, use a trigram index (pg_trgm extension) or full-text search; indexes are covered in Module 5.

Searching from Java

Never glue the user's text into the SQL string. Pass the whole pattern as a parameter:

String sql = "SELECT name, price FROM products WHERE name ILIKE ?";
try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setString(1, "%" + term + "%");      // the % signs are part of the parameter
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            System.out.println(rs.getString("name"));
        }
    }
}

The parameter stops SQL injection (see Core Java · Module 8), but a % or _ typed by the user still acts as a wildcard; escape them if that matters. Spring Data JPA derives the query for you from method names such as findByNameContainingIgnoreCase.

Rule: the pattern must match the whole value

LIKE is not a "contains" search by itself. name LIKE 'Cable' matches only the exact text Cable. Add % where text may appear before or after.

Mistake: expecting MySQL behaviour in PostgreSQL

A search for WHERE email = 'Priya.Menon@Example.com' finds the row in MySQL and returns nothing in PostgreSQL, because the stored value is lowercase. Normalise on input (store emails in lowercase) or compare with LOWER(email) = LOWER(?). A unique index on LOWER(email) then stops duplicates that differ only by case.

Edge cases

  • LIKE '%' matches every non-NULL value; a NULL value never matches any pattern.
  • Wrapping the column in a function (LOWER(name) LIKE …) stops a normal index on name from being used. Create an index on the expression, or use ILIKE with a trigram index.
  • MySQL's default collation also ignores accents (a equals á); PostgreSQL does not unless you use the unaccent extension.

Interview angle

  • What do % and _ mean? Any number of characters, and exactly one character.
  • How do you search without caring about case in PostgreSQL? ILIKE, or compare LOWER() on both sides.
  • Why can LIKE '%abc' be slow? A leading wildcard cannot use a B-tree index, so the table is scanned.
  • How do you match a literal %? Use ESCAPE and put the escape character before it.

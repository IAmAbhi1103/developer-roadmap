ORDER BY, LIMIT, OFFSET and pagination

ORDER BY is the only way to get rows in a guaranteed order. LIMIT and OFFSET (or the standard FETCH FIRST) cut the result down to one page, and a page is only stable when the sort includes a unique tie-breaker column.

Sorting with ORDER BY

A table is a set of rows with no order. If you do not write ORDER BY, the database returns rows in whatever order is cheapest at that moment, and that order can change after an update, a new index or a different query plan. ORDER BY goes at the end of the query (before LIMIT) and sorts ascending (ASC, the default) or descending (DESC). With several columns, the database sorts by the first one and uses the next only to break ties. Each column has its own direction:

SELECT dept_id, first_name, salary
FROM employees
ORDER BY dept_id, salary DESC;
 dept_id | first_name |  salary
---------+------------+-----------
       1 | Vikram     | 220000.00
       1 | Priya      | 150000.00
       1 | Rahul      | 150000.00
       1 | Arjun      | 110000.00
       1 | Divya      |  90000.00
       2 | Karan      | 160000.00
       2 | Ananya     | 150000.00
       2 | Neha       |  75000.00
       3 | Sunita     | 120000.00
       3 | Farhan     |  65000.00
       3 | Isha       |  55000.00
  (null) | Meera      | 300000.00
(12 rows)

You can sort by a column that is not in the select list, by an expression (ORDER BY salary * 12), or by an alias from the select list (ORDER BY annual_salary). Text sorts by the database's collation, which decides whether 'apple' comes before 'Banana'; to ignore case, sort by LOWER(name). To sort in a custom order (for example PLACED, SHIPPED, DELIVERED) use a CASE expression, see CASE expressions.

Where do NULLs go?

PostgreSQL treats NULL as larger than every value. So ASC puts NULLs last and DESC puts them first (the output above shows the CEO's NULL department at the end). You can say what you want with NULLS FIRST or NULLS LAST:

SELECT name, phone FROM customers ORDER BY phone;               -- NULLs last
SELECT name, phone FROM customers ORDER BY phone NULLS FIRST;
     name     |   phone
--------------+------------
 Aarav Shah   | 9876500001
 Kabir Singh  | 9876500003
 Ishita Joshi | 9876500004
 Sara Khan    | 9876500006
 Diya Kapoor  | (null)
 Rohan Das    | (null)
 Tanvi Desai  | (null)
(7 rows)

     name     |   phone
--------------+------------
 Diya Kapoor  | (null)
 Rohan Das    | (null)
 Tanvi Desai  | (null)
 Aarav Shah   | 9876500001
 Kabir Singh  | 9876500003
 Ishita Joshi | 9876500004
 Sara Khan    | 9876500006
(7 rows)

MySQL does the opposite: it treats NULL as the smallest value, so ASC puts NULLs first, and it has no NULLS FIRST/LAST syntax. The usual workaround sorts on phone IS NULL first (which is 0 for real values and 1 for NULL): ORDER BY phone IS NULL, phone puts NULLs last.

LIMIT, OFFSET and FETCH FIRST

LIMIT n returns at most n rows. Together with ORDER BY it answers "top N" questions. OFFSET m skips the first m rows.

SELECT first_name, salary
FROM employees
ORDER BY salary DESC
LIMIT 3;
 first_name |  salary
------------+-----------
 Meera      | 300000.00
 Vikram     | 220000.00
 Karan      | 160000.00
(3 rows)

The SQL standard spells the same thing FETCH FIRST n ROWS ONLY. PostgreSQL supports both, MySQL only LIMIT. The standard form can also keep ties (PostgreSQL 13 and later). Three employees share the salary 150000, so asking for the top 5 with ties returns 6 rows:

SELECT first_name, salary
FROM employees
ORDER BY salary DESC
FETCH FIRST 5 ROWS WITH TIES;
 first_name |  salary
------------+-----------
 Meera      | 300000.00
 Vikram     | 220000.00
 Karan      | 160000.00
 Ananya     | 150000.00
 Priya      | 150000.00
 Rahul      | 150000.00
(6 rows)
NeedPostgreSQLMySQLOther databases
First 10 rowsLIMIT 10 or FETCH FIRST 10 ROWS ONLY LIMIT 10SQL Server TOP 10; Oracle 12c+ FETCH FIRST
Skip 20, take 10LIMIT 10 OFFSET 20 LIMIT 10 OFFSET 20 or LIMIT 20, 10 SQL Server OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY

Careful with the MySQL short form: LIMIT 20, 10 means offset 20, count 10 (the offset comes first). Prefer LIMIT 10 OFFSET 20, which reads the same in both databases.

Pagination

A web page that shows 4 employees at a time asks for page 1, 2, 3 and so on. The formula is OFFSET = (page - 1) * page_size. Spring Data's PageRequest.of(page, size) counts pages from 0, so for it the offset is page * size. Page 2 of size 4:

SELECT emp_id, first_name
FROM employees
ORDER BY emp_id
LIMIT 4 OFFSET 4;
 emp_id | first_name
--------+------------
      5 | Priya
      6 | Rahul
      7 | Arjun
      8 | Divya
(4 rows)

The page controls usually also need the total number of rows, which takes a second query, SELECT COUNT(*) FROM employees. Spring Data's Page type runs both for you.

Paging only works when the sort is deterministic. If you sort by salary, three employees tie at 150000, and the database may return those three in a different order for page 1 than for page 2. A row can then appear on both pages, or on neither. The fix is a tie-breaker: add a unique column last, as in ORDER BY salary DESC, emp_id.

Why large OFFSETs are slow, and keyset pagination

OFFSET 100000 does not jump to row 100,001. The database reads and throws away the first 100,000 rows, so later pages get slower and slower. Keyset pagination (also called the seek method) remembers the last key of the previous page and asks for the rows after it. An index on the key makes every page equally fast:

SELECT emp_id, first_name
FROM employees
WHERE emp_id > 8          -- last emp_id seen on the previous page
ORDER BY emp_id
LIMIT 4;
 emp_id | first_name
--------+------------
      9 | Karan
     10 | Neha
     11 | Farhan
     12 | Isha
(4 rows)

The trade-off: you can go to the next or previous page, but not jump to "page 57", and the sort key must be unique (or you must compare two columns together). Infinite-scroll feeds and APIs with large tables use it; admin screens with page numbers usually use OFFSET.

Rule: LIMIT and OFFSET need ORDER BY

Without ORDER BY, "the first 3 rows" means any 3 rows. Always sort first, and make the sort unique when you page through results.

Mistake: LIMIT without ORDER BY

Wrong: "top 3 salaries" returns any 3 rows

SELECT first_name, salary FROM employees LIMIT 3;

Right: sort, then cut

SELECT first_name, salary
FROM employees
ORDER BY salary DESC, emp_id
LIMIT 3;

Edge cases and errors

  • LIMIT 0 returns no rows but still returns the column names, which is handy for checking a query's shape. An OFFSET larger than the row count returns an empty result, not an error.
  • Negative values fail: ERROR: LIMIT must not be negative. In PostgreSQL, LIMIT ALL and LIMIT NULL mean "no limit"; MySQL does not accept them.
  • With SELECT DISTINCT, the ORDER BY columns must appear in the select list (see DISTINCT and DISTINCT ON).
  • Ordering by position (ORDER BY 2) is legal but fragile; use the name or alias.

In real projects

Every list endpoint in a REST API should be paginated; an unbounded SELECT on a growing table is a production incident waiting to happen. Spring Data JPA turns a Pageable into exactly the ORDER BY … LIMIT … OFFSET … you see here (see Spring Boot · Module 3).

Interview angle

  • Is the order of rows guaranteed without ORDER BY? No. Not even "by primary key".
  • How do you implement pagination? ORDER BY a unique key, LIMIT size OFFSET (page - 1) * size; mention that big offsets are slow and keyset pagination (WHERE id > last_id) fixes that.
  • Where do NULLs sort? PostgreSQL: as the largest value (last in ASC); MySQL: as the smallest. NULLS FIRST/LAST is PostgreSQL only.

DISTINCT and DISTINCT ON

DISTINCT removes duplicate rows from a result. It compares the whole row, not one column. DISTINCT ON (PostgreSQL only) keeps one row per group, chosen by ORDER BY.

Removing duplicates

Many rows share the same value in some columns: several customers live in Mumbai, many employees work in the same department. SELECT DISTINCT returns each different row once:

SELECT DISTINCT city
FROM customers
ORDER BY city;
   city
-----------
 Ahmedabad
 Bengaluru
 Delhi
 Kolkata
 Mumbai
 Pune
(6 rows)

Internally the database sorts or hashes the result to find duplicates, so DISTINCT costs time on big results. Use it when duplicates are expected and unwanted, not as a reflex.

DISTINCT works on the whole row

With several columns, two rows are duplicates only if all selected columns are equal. Customer 1 has one DELIVERED and one SHIPPED order, so both pairs stay:

SELECT DISTINCT customer_id, status
FROM orders
ORDER BY customer_id, status;
 customer_id |  status
-------------+-----------
           1 | DELIVERED
           1 | SHIPPED
           2 | DELIVERED
           2 | PLACED
           3 | CANCELLED
           3 | DELIVERED
           4 | DELIVERED
           5 | PLACED
           5 | SHIPPED
(9 rows)

DISTINCT is not a function. SELECT DISTINCT(city), name FROM customers does not mean "distinct city"; the parentheses are just grouping, and the whole row (city, name) is compared. To count distinct values use COUNT(DISTINCT city) (see Aggregate functions).

NULL in DISTINCT

Two NULLs are not equal in a comparison, but DISTINCT treats them as the same value, so all NULLs collapse into one row. The CEO has no department, so a list of departments that appear among employees contains a NULL:

SELECT DISTINCT dept_id FROM employees ORDER BY dept_id;
 dept_id
---------
       1
       2
       3
  (null)
(4 rows)

DISTINCT ON: one row per group (PostgreSQL)

A very common task: "for each department, the highest paid employee" or "for each customer, the latest order". PostgreSQL has a shortcut: DISTINCT ON (columns) keeps only the first row of each group, and "first" is decided by ORDER BY.

SELECT DISTINCT ON (customer_id)
       customer_id, order_id, order_date
FROM orders
ORDER BY customer_id, order_date DESC;
 customer_id | order_id | order_date
-------------+----------+------------
           1 |        7 | 2026-03-21
           2 |        9 | 2026-04-03
           3 |        6 | 2026-03-08
           4 |        5 | 2026-02-27
           5 |       10 | 2026-04-10
(5 rows)

Read it as: sort by customer, newest order first; then keep the first row for each customer. Another example, the best-paid person in each department (the NULL department forms its own group):

SELECT DISTINCT ON (dept_id)
       dept_id, first_name, salary
FROM employees
ORDER BY dept_id, salary DESC;
 dept_id | first_name |  salary
---------+------------+-----------
       1 | Vikram     | 220000.00
       2 | Karan      | 160000.00
       3 | Sunita     | 120000.00
  (null) | Meera      | 300000.00
(4 rows)

DISTINCT ON is not standard SQL and MySQL does not have it. The portable way is a window function, ROW_NUMBER() OVER (PARTITION BY … ORDER BY …), covered in Ranking functions. It also handles "top 3 per group", which DISTINCT ON cannot.

DISTINCT versus GROUP BY

SELECT DISTINCT city FROM customers and SELECT city FROM customers GROUP BY city return the same rows. Use DISTINCT when you only want unique values, and GROUP BY when you also compute something per group, such as a count (see GROUP BY).

Rule: ORDER BY must start with the DISTINCT ON columns

The ORDER BY list has to begin with the same expressions as DISTINCT ON. Otherwise PostgreSQL stops with ERROR: SELECT DISTINCT ON expressions must match initial ORDER BY expressions. And without any ORDER BY the surviving row of each group is arbitrary.

Mistake: DISTINCT as a bandage for a join bug

A query returns the same employee three times, and someone adds DISTINCT to "fix" it. The real problem is usually a join that multiplies rows (for example joining employees to employee_projects and showing only employee columns). DISTINCT hides the symptom, costs time, and can still hide real duplicates you wanted to see. Find out why rows multiply (see join cardinality).

Edge cases

  • SELECT DISTINCT first_name FROM employees ORDER BY emp_id fails in PostgreSQL: ERROR: for SELECT DISTINCT, ORDER BY expressions must appear in select list. After removing duplicates there is no single emp_id per row to sort by.
  • DISTINCT applies to the whole select list, so adding one more column (such as emp_id) can make every row unique and "stop working".

Interview angle

  • Does DISTINCT apply to one column or all? All selected columns together.
  • How are NULLs treated? As equal to each other: they collapse into one row.
  • How do you get the latest row per group? DISTINCT ON in PostgreSQL, or ROW_NUMBER() in any database.

NULL and three-valued logic

NULL means "unknown or missing", not zero and not an empty string. Any comparison with NULL gives UNKNOWN, WHERE keeps only rows that are TRUE, so = NULL never matches: use IS NULL, COALESCE and IS DISTINCT FROM instead.

What NULL is

NULL marks a value that is missing or unknown. Meera, the CEO, has manager_id = NULL: she has no manager. Three customers have phone = NULL: we do not know their number. NULL is not 0 (a salary of zero is a known value), and it is not '' (an empty string is a known, empty text). Because "unknown" can be anything, SQL cannot say whether NULL equals something. This leads to three-valued logic: a condition is TRUE, FALSE or UNKNOWN.

The key rule for queries: WHERE keeps a row only when the condition is TRUE. FALSE and UNKNOWN rows are both dropped. So a row whose condition is UNKNOWN silently disappears.

IS NULL and IS NOT NULL

SELECT first_name, dept_id FROM employees WHERE dept_id = NULL;

SELECT first_name, dept_id, manager_id FROM employees WHERE dept_id IS NULL;
 first_name | dept_id
------------+---------
(0 rows)

 first_name | dept_id | manager_id
------------+---------+------------
 Meera      | (null)  | (null)
(1 row)

The first query is valid SQL and returns nothing, with no error. That is what makes it dangerous.

The silent loss with <>

The same effect hides rows in "not equal" filters. Five employees work in Engineering (dept 1), so you expect seven others. dept_id <> 1 is UNKNOWN for the CEO, so she is dropped:

SELECT first_name FROM employees WHERE dept_id <> 1 ORDER BY emp_id;            -- 6 rows
SELECT first_name FROM employees WHERE dept_id IS DISTINCT FROM 1 ORDER BY emp_id; -- 7 rows
 first_name
------------
 Ananya
 Sunita
 Karan
 Neha
 Farhan
 Isha
(6 rows)

 first_name
------------
 Meera
 Ananya
 Sunita
 Karan
 Neha
 Farhan
 Isha
(7 rows)

a IS DISTINCT FROM b is a NULL-safe "not equal": it is TRUE when the values differ, treats two NULLs as equal, and never returns UNKNOWN. a IS NOT DISTINCT FROM b is the NULL-safe "equal". MySQL's NULL-safe equals operator is <=>.

COALESCE and NULLIF

COALESCE(a, b, c, …) returns the first argument that is not NULL. It replaces NULL with a default for display or calculation. It works in every database; MySQL also has IFNULL(a, b) and Oracle has NVL.

SELECT name, COALESCE(phone, 'no phone') AS phone
FROM customers
ORDER BY customer_id;
     name     |   phone
--------------+------------
 Aarav Shah   | 9876500001
 Diya Kapoor  | no phone
 Kabir Singh  | 9876500003
 Ishita Joshi | 9876500004
 Rohan Das    | no phone
 Sara Khan    | 9876500006
 Tanvi Desai  | no phone
(7 rows)

NULLIF(a, b) does the reverse: it returns NULL when a equals b, otherwise a. Its classic use is avoiding division by zero, because dividing by NULL gives NULL instead of an error:

SELECT 100 / 0;                -- ERROR:  division by zero
SELECT 100 / NULLIF(0, 0);     -- NULL (shown as an empty or (null) cell)

In a real query it looks like total / NULLIF(order_count, 0). Another use is turning empty strings from a form into NULL: NULLIF(TRIM(phone), '').

NULL in arithmetic, text and aggregates

  • Arithmetic and text: any operation with NULL gives NULL. salary + NULL is NULL, and so is 'Mr ' || NULL in PostgreSQL. Wrap nullable parts in COALESCE.
  • Aggregates skip NULLs (except COUNT(*)). The CEO has no department and no manager:
SELECT COUNT(*) AS total, COUNT(dept_id) AS with_dept, COUNT(manager_id) AS with_manager
FROM employees;
 total | with_dept | with_manager
-------+-----------+--------------
    12 |        11 |           11
(1 row)

AVG, SUM, MIN and MAX also ignore NULLs; more in Aggregate functions.

NULL in IN and NOT IN: the classic trap

x IN (1, 2, NULL) is TRUE when x is 1 or 2, and otherwise UNKNOWN (not FALSE), because x = NULL is unknown. The danger is NOT IN: it is a chain of <> tests joined by AND, and one UNKNOWN makes the whole chain never TRUE.

SELECT 2 IN (1, 2, NULL) AS a, 3 IN (1, 2, NULL) AS b, 3 NOT IN (1, 2, NULL) AS c;
 a |   b    |   c
---+--------+--------
 t | (null) | (null)
(1 row)

This bites in real queries. "Which departments have no employees?" The subquery below returns the dept_id of every employee, including the CEO's NULL:

SELECT name
FROM departments
WHERE dept_id NOT IN (SELECT dept_id FROM employees);
 name
------
(0 rows)

Marketing has no employees, but for it the test is 4 NOT IN (1, 2, 3, NULL), which is UNKNOWN. Two fixes: filter the NULLs out of the subquery, or (better) use NOT EXISTS, which does not have this problem (see EXISTS and anti-joins).

SELECT name
FROM departments
WHERE dept_id NOT IN (SELECT dept_id FROM employees WHERE dept_id IS NOT NULL);
   name
-----------
 Marketing
(1 row)

NULL in constraints, sorting and grouping

  • UNIQUE allows many NULLs in PostgreSQL and MySQL, because NULLs are not equal to each other. (PostgreSQL 15 adds UNIQUE NULLS NOT DISTINCT if you want only one.)
  • CHECK passes when the condition is TRUE or UNKNOWN. Only FALSE rejects the row. CHECK (price > 0) does not stop a NULL price; add NOT NULL.
  • Primary keys are never NULL. Foreign keys may be NULL, which means "no related row".
  • ORDER BY, DISTINCT, GROUP BY, UNION treat all NULLs as one group, even though NULL = NULL is unknown.

NULL in Java

JDBC can lose the difference between NULL and zero. rs.getInt("manager_id") returns 0 for a NULL, and employee 0 does not exist. Use rs.getObject("manager_id", Integer.class) (returns null) or call rs.wasNull() right after getInt. In JPA, map nullable columns to wrapper types (Integer, Long), not int or long.

Rule: test NULL only with IS NULL, IS NOT NULL or IS DISTINCT FROM

= NULL and <> NULL never return TRUE. Remember also that a comparison such as <> 1 drops NULL rows.

Mistake: = NULL and NOT IN with a nullable subquery

Wrong: always zero rows

SELECT * FROM customers WHERE phone = NULL;
SELECT * FROM departments
WHERE dept_id NOT IN (SELECT dept_id FROM employees);

Right

SELECT * FROM customers WHERE phone IS NULL;
SELECT * FROM departments d
WHERE NOT EXISTS (SELECT 1 FROM employees e WHERE e.dept_id = d.dept_id);

Convention: fewer NULLs, on purpose

Make a column NOT NULL unless "unknown" is a real state of the data. Use a DEFAULT for the rest (stock INT NOT NULL DEFAULT 0). Do not store an empty string to mean "none", and do not store 0 or 'N/A' to mean "unknown": they poison averages and comparisons. (Oracle treats '' as NULL; PostgreSQL and MySQL do not.)

Interview angle

  • Why does WHERE col = NULL return nothing? The comparison is UNKNOWN, and WHERE keeps only TRUE rows. Use IS NULL.
  • What is the difference between COUNT(*) and COUNT(col)? COUNT(*) counts rows; COUNT(col) counts rows where col is not NULL.
  • What does NOT IN return if the list contains a NULL? No rows. Explain the AND chain of <> and prefer NOT EXISTS.
  • NULL vs empty string vs 0? Three different things: unknown, known-empty, known-zero.

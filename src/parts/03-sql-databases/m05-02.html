EXPLAIN and EXPLAIN ANALYZE: reading query plans

EXPLAIN shows the plan the database chose and its cost estimate; EXPLAIN ANALYZE runs the query and adds real times and row counts, so you can see where time goes and whether an index is used.

What the planner does

SQL says what you want, not how to get it. The query planner (optimizer) considers several ways (scan with or without an index, join order, join method), estimates the cost of each using table statistics, and executes the cheapest. EXPLAIN prints the chosen plan as a tree of nodes. You read it from the innermost, most indented node outward; data flows up.

EXPLAIN SELECT ...;                      -- plan and estimates only; the query is NOT run
EXPLAIN ANALYZE SELECT ...;              -- runs the query; adds actual times and rows
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;   -- also shows pages read from cache and disk

Mistake: EXPLAIN ANALYZE on INSERT, UPDATE or DELETE

EXPLAIN ANALYZE really executes the statement. To look at a write safely, wrap it: BEGIN; EXPLAIN ANALYZE DELETE ...; ROLLBACK;

The scripted experiment: 1 million rows

The best way to learn indexes is to feel the difference. Run this in psql on a test database. It uses generate_series to create a million rows without any outside file.

Reading the plan: the numbers

cost=0.42..48.90
Two numbers: the estimated cost to return the first row, then to return all rows. The unit is arbitrary (relative page-read costs). Only compare costs within the same database.
rows=10
The planner's estimate of rows this node returns.
width=34
Estimated average row size in bytes.
actual time=0.03..0.05
Real milliseconds to the first row and to the last row (only with ANALYZE). It is per loop.
rows=11 (in the actual part)
The rows really returned. Compare with the estimate: a big gap (10 vs 100,000) means the statistics are stale or the planner misjudges the data.
loops=N
How many times the node ran. For a node on the inner side of a nested loop the total time is actual time × loops.
Buffers: shared hit=14 read=3
hit pages came from memory, read pages from disk (or the OS cache). Lower is better.
Rows Removed by Filter
Rows read and then thrown away. A large number means the database read a lot to keep a little: look for a missing index.

Statistics and ANALYZE

The planner's choices are only as good as its statistics: row counts, distinct values and the most common values per column. ANALYZE table_name refreshes them; the autovacuum process runs it automatically after enough changes. Run it by hand after a bulk load. If estimated and actual rows differ by 10× or more, run ANALYZE first. If they still differ, look for correlated columns or skewed data.

MySQL EXPLAIN in brief

MySQL prints a table of rows instead of a tree. EXPLAIN ANALYZE exists too (MySQL 8.0.18+) and prints a tree similar to PostgreSQL's. The columns of the classic table:

ColumnWhat to look at
typeAccess method, best to worst: const, eq_ref, ref, range, index, ALL (full scan, bad)
possible_keys / keyIndexes that could be used / the one chosen (NULL means none)
rowsEstimated rows examined
ExtraUsing index (covering), Using filesort and Using temporary (extra work to avoid)

A tuning routine

  1. Find the slow query (application logs, pg_stat_statements, slow query log).
  2. Run EXPLAIN (ANALYZE, BUFFERS) on production-like data.
  3. Find the node with the biggest actual time × loops, and big Rows Removed by Filter.
  4. Compare estimated and actual rows; run ANALYZE if they are far apart.
  5. Change one thing: add or reorder an index, rewrite the condition, select fewer columns.
  6. Run EXPLAIN ANALYZE again and compare. Keep the change only if it helps.

Rule: judge by actual time and buffers, not by cost alone

Cost is an estimate in made-up units. The truth is actual time and Buffers from EXPLAIN (ANALYZE, BUFFERS), run twice (the first run may be cold).

Edge cases

  • With loops=1000, a node showing actual time=0.05 costs 50 ms in total.
  • On a small test table the planner picks a Seq Scan even with a perfect index. Test with realistic volumes.
  • EXPLAIN on a parameterized query inside a prepared statement can differ from the literal version: PostgreSQL may use a generic plan after several executions.

Interview angle

  • EXPLAIN vs EXPLAIN ANALYZE? The first shows the estimated plan; the second runs the query and shows real times and row counts.
  • What do you look for? Seq Scan on big tables, big gaps between estimated and actual rows, rows removed by filter, sorts spilling to disk, nested loops with high loop counts.
  • Nested loop vs hash join vs merge join? Per-row indexed lookups (small outer); hash table of one side (large unsorted); merge of two sorted sides.
  • A query got slow after a bulk import. Why? Stale statistics; run ANALYZE.

Transactions and ACID

A transaction groups several statements into one all-or-nothing unit; ACID (Atomicity, Consistency, Isolation, Durability) names the four guarantees the database gives, shown best by a bank transfer.

Why transactions exist

Moving ₹500 from Asha's account to Bilal's takes two updates: subtract from one, add to the other. If the server crashes between them, ₹500 vanishes. If two transfers touch the same account at once, one update can overwrite the other. A transaction wraps the statements so they succeed together or not at all, and are protected from other users while they run.

CREATE TABLE accounts (
    id            BIGINT PRIMARY KEY,
    owner         TEXT   NOT NULL,
    balance_paise BIGINT NOT NULL CHECK (balance_paise >= 0)
);
INSERT INTO accounts VALUES (1, 'Asha', 100000), (2, 'Bilal', 50000);

BEGIN;                                                           -- start the transaction
UPDATE accounts SET balance_paise = balance_paise - 50000 WHERE id = 1;
UPDATE accounts SET balance_paise = balance_paise + 50000 WHERE id = 2;
COMMIT;                                                          -- make both changes permanent

SELECT * FROM accounts ORDER BY id;
 id | owner | balance_paise
----+-------+---------------
  1 | Asha  |         50000
  2 | Bilal |        100000

BEGIN;
UPDATE accounts SET balance_paise = balance_paise - 80000 WHERE id = 1;   -- Asha has 50000 only
-- ERROR:  new row for relation "accounts" violates check constraint "accounts_balance_paise_check"
ROLLBACK;     -- PostgreSQL: after an error the transaction is "aborted"; only ROLLBACK works

SELECT balance_paise FROM accounts WHERE id = 1;     -- still 50000
BEGIN;
INSERT INTO orders (user_id, restaurant_id, delivery_address, total_paise)
VALUES (1, 1, 'MG Road', 60000);
SAVEPOINT before_coupon;
UPDATE coupons SET used_count = used_count + 1 WHERE code = 'BAD';   -- fails or is not wanted
ROLLBACK TO SAVEPOINT before_coupon;      -- order insert is kept
COMMIT;

Autocommit

Outside BEGIN, every single statement is its own transaction that commits at once: autocommit. That is the default in psql and in the PostgreSQL JDBC driver's server behaviour. JDBC starts with connection.setAutoCommit(true); to run several statements together you call setAutoCommit(false), then commit() or rollback(). Spring does this for you: a method annotated with @Transactional gets one connection, turns off autocommit, commits on normal return and rolls back on a runtime exception (see Spring Boot · Module 3). In MySQL the same: autocommit is on by default; DDL statements such as CREATE TABLE cause an implicit commit, but PostgreSQL can roll DDL back.

ACID, letter by letter

LetterPromiseBank-transfer exampleHow the database does it
AtomicityAll statements apply, or noneDebit and credit both happen, or neither Undo information / old row versions; rollback discards changes
ConsistencyData moves from one valid state to another; rules always hold Balance never negative; foreign keys valid; total money unchanged Constraints (CHECK, FOREIGN KEY, UNIQUE) abort violating transactions; the application defines the business rules
IsolationConcurrent transactions do not see each other's half-done work A second transfer cannot read Asha's balance between the debit and the credit MVCC (versions) and locks; see isolation levels
DurabilityAfter COMMIT, data survives a crash After "transfer successful" the money stays moved even if the server loses power Write-ahead log (WAL, redo log), flushed to disk at commit

Durability in more detail: the database first appends a description of the change to a write-ahead log and forces it to disk (fsync) before telling you "committed". Data pages in memory are written to the table files later, in the background. After a crash, the database replays the log to restore every committed change and discards the uncommitted ones. Appending to a log is fast sequential I/O, which is why commits are cheap. (PostgreSQL's setting synchronous_commit = off trades a tiny window of lost commits for speed; do not use it for payments.) InnoDB calls its log the redo log and also keeps an undo log to roll back and to serve old versions.

Consistency has two meanings. In ACID it means "no rule is broken at commit". This is different from "consistency" in the CAP theorem (all nodes agree) in Module 6.

What a transaction does not do

  • It does not make a long operation safe if it contains a call to a payment gateway or an email: those side effects cannot be rolled back. Keep transactions short and do external calls outside them, or use patterns such as an outbox table.
  • It does not stop all concurrency bugs by itself: the isolation level decides what you can see (next article), and read-then-write logic needs locks (see Locking).

Rule: one transaction per business operation, kept short

Group the statements that must succeed together (transfer, place an order and its lines). Commit as soon as possible. A transaction left open holds locks and blocks cleanup (VACUUM); an "idle in transaction" connection is a classic production problem.

Mistake: catching the exception and carrying on in the same transaction

In PostgreSQL, after any error the whole transaction is aborted: every later statement fails with "current transaction is aborted, commands ignored until end of transaction block". Roll back, or use a savepoint around the risky statement. In Spring, swallowing a RuntimeException inside a @Transactional method means the transaction still commits whatever was done before.

Edge cases

  • MySQL's MyISAM engine has no transactions; use InnoDB (the default since MySQL 5.5).
  • COMMIT can itself fail (deferred constraints, serialization failure at the Serializable level). Handle the error and retry.
  • Sequences and identity values are not rolled back: a rolled-back insert leaves a gap in ids.

Interview angle

  • Explain ACID with an example. Bank transfer: atomic (both updates or none), consistent (balance never negative, total unchanged), isolated (no one sees the money in flight), durable (survives a crash thanks to the WAL).
  • How is durability implemented? Write-ahead log flushed at commit; replayed after a crash.
  • Autocommit? Each statement is its own transaction unless you start one explicitly.
  • ACID consistency vs CAP consistency? Rules hold after commit, versus all nodes see the same data.

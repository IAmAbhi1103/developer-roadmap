INSERT: adding rows, RETURNING and upserts

INSERT INTO table (columns) VALUES (…) adds rows; list the columns every time, add many rows in one statement, copy rows with INSERT … SELECT, and use ON CONFLICT (MySQL: ON DUPLICATE KEY UPDATE) to insert-or-update in one atomic step.

Note: examples that change data

The statements in this article and the next two change rows. Each example is wrapped in BEGIN; … ROLLBACK;, so the sample database is exactly the same afterwards (the next article explains why this is also the safest habit in real work). The outputs below leave out the BEGIN and ROLLBACK lines that psql prints. In MySQL write START TRANSACTION; instead of BEGIN;.

One row, and RETURNING

BEGIN;
INSERT INTO departments (name, location)
VALUES ('Finance', 'Delhi')
RETURNING dept_id, name;
ROLLBACK;
 dept_id |  name
---------+---------
       5 | Finance
(1 row)

INSERT 0 1

The line INSERT 0 1 is the command tag: the statement inserted 1 row (the 0 is a historical object id and is always 0 today). We did not give a dept_id; the identity column generated it. RETURNING (PostgreSQL) sends back any columns of the new row, including generated ones, so you do not need a second SELECT. It also works with UPDATE and DELETE. MySQL has no RETURNING; you call SELECT LAST_INSERT_ID() instead.

From Java, ask JDBC for the generated key. The PostgreSQL driver does this with RETURNING behind the scenes:

String sql = "INSERT INTO departments (name, location) VALUES (?, ?)";
try (PreparedStatement ps = connection.prepareStatement(sql, new String[] {"dept_id"})) {
    ps.setString(1, "Finance");
    ps.setString(2, "Delhi");
    ps.executeUpdate();
    try (ResultSet keys = ps.getGeneratedKeys()) {
        if (keys.next()) {
            System.out.println("New id: " + keys.getInt(1));
        }
    }
}

Always list the columns

The column list says which value goes where. Columns you leave out get their DEFAULT, or NULL if there is none. If a left-out column is NOT NULL and has no default, the insert fails.

BEGIN;
INSERT INTO customers (name, email, city)
VALUES ('Meghna Rao', 'meghna.rao@example.com', 'Chennai')
RETURNING *;
ROLLBACK;
 customer_id |    name    |         email          |  city   | phone  |  joined_on
-------------+------------+------------------------+---------+--------+------------
           8 | Meghna Rao | meghna.rao@example.com | Chennai | (null) | 2026-10-21
(1 row)

INSERT 0 1

The new customer got the next id, a NULL phone (no default) and today's date (the default expression CURRENT_DATE). You can also write the keyword DEFAULT in the value list (VALUES (DEFAULT, 'Meghna', …)), or insert a row made only of defaults with INSERT INTO t DEFAULT VALUES.

Wrong: no column list, values map to table order

INSERT INTO departments VALUES ('Finance', 'Delhi');
-- ERROR:  invalid input syntax for type integer: "Finance"

Right: name the columns

INSERT INTO departments (name, location) VALUES ('Finance', 'Delhi');

Without a column list the values must match all columns in table order. It breaks (or worse, silently stores data in the wrong columns) the day someone adds a column.

Many rows in one statement

List several rows after VALUES, separated by commas. The statement is atomic: either every row is inserted or none is. It is also much faster than separate inserts, because there is one round trip and one parse.

BEGIN;
INSERT INTO products (name, category, price, stock)
VALUES ('Phone Stand', 'Electronics', 349.00, 80),
       ('Pencil Box',  'Stationery',   60.00, 200)
RETURNING product_id, name;
ROLLBACK;
 product_id |    name
------------+-------------
          8 | Phone Stand
          9 | Pencil Box
(2 rows)

INSERT 0 2

From Java, use JDBC batching (addBatch() and executeBatch()) for thousands of rows. Note that Hibernate cannot batch inserts for entities whose id is generated by an IDENTITY column, because it needs the id right after every insert (see Spring Boot · Module 3).

INSERT … SELECT: copy rows from a query

Instead of VALUES, feed the insert with a SELECT. This copies, archives or transforms data entirely inside the database. The column types and the column count of the SELECT must match the insert's column list.

BEGIN;
CREATE TABLE clearance (
    product_id INT PRIMARY KEY,
    name       VARCHAR(100),
    sale_price NUMERIC(10, 2)
);
INSERT INTO clearance (product_id, name, sale_price)
SELECT product_id, name, ROUND(price * 0.8, 2)
FROM products
WHERE category = 'Stationery';
SELECT * FROM clearance ORDER BY product_id;
ROLLBACK;
INSERT 0 2

 product_id |     name     | sale_price
------------+--------------+------------
          4 | Notebook A5  |      96.00
          5 | Gel Pen Pack |      72.00
(2 rows)

To create the table and fill it in one step, use CREATE TABLE clearance AS SELECT …. That form copies the data and column types but no constraints, so add the primary key afterwards.

Upsert: insert, or update if it already exists

Sometimes you do not know whether a row exists: importing a customer list, handling a message that may arrive twice, counting page views. Checking with a SELECT first and then inserting is a race condition: two sessions can both see "not found" and both insert. An upsert does it in one atomic statement. The email column of customers is unique, so it can decide what "already exists" means:

BEGIN;
INSERT INTO customers (name, email, city)
VALUES ('Aarav Shah', 'aarav.shah@example.com', 'Navi Mumbai')
ON CONFLICT (email) DO UPDATE SET city = EXCLUDED.city
RETURNING customer_id, name, city;
ROLLBACK;
 customer_id |    name    |    city
-------------+------------+-------------
           1 | Aarav Shah | Navi Mumbai
(1 row)

INSERT 0 1

EXCLUDED is a pseudo-table that holds the row you tried to insert. ON CONFLICT (email) names the unique column (or constraint) that detects the conflict. Use DO NOTHING to skip a duplicate silently (the command tag becomes INSERT 0 0). MySQL spells it differently, and reacts to a conflict on any unique key:

INSERT INTO customers (name, email, city)
VALUES ('Aarav Shah', 'aarav.shah@example.com', 'Navi Mumbai') AS new
ON DUPLICATE KEY UPDATE city = new.city;

MySQL also has REPLACE INTO, which deletes the old row and inserts a new one. That fires ON DELETE actions and can change ids, so prefer ON DUPLICATE KEY UPDATE.

Rule: one statement, one outcome

A single INSERT is all-or-nothing. If row 99 of 100 violates a constraint, no row is inserted. A multi-row insert inside a transaction is safe to retry.

Edge cases

  • Ids have gaps. A sequence never goes back, even when the transaction rolls back or an upsert turns into an update. After running the examples above, the next real department gets id 6 or higher, not 5. Never rely on ids being continuous.
  • With GENERATED ALWAYS AS IDENTITY you cannot supply an id: ERROR: cannot insert a non-DEFAULT value into column "id". (Our sample tables use BY DEFAULT, which allows it.)
  • In one upsert statement, two input rows must not hit the same existing row: ERROR: ON CONFLICT DO UPDATE command cannot affect row a second time.

In real projects

Upserts make jobs and message consumers idempotent: processing the same event twice leaves the same result. Counters use ON CONFLICT (page) DO UPDATE SET hits = page_hits.hits + 1. Data imports use INSERT … SELECT from a staging table, usually in a migration script.

Interview angle

  • How do you insert if absent, update if present? ON CONFLICT … DO UPDATE (PostgreSQL), ON DUPLICATE KEY UPDATE (MySQL), or MERGE. Explain why "SELECT then INSERT" is a race condition.
  • How do you get the generated id? RETURNING, LAST_INSERT_ID(), or JDBC getGeneratedKeys().
  • Why list the column names? The statement keeps working when the table gets new columns.

UPDATE and DELETE

UPDATE … SET … WHERE changes existing rows and DELETE FROM … WHERE removes them. The WHERE clause decides which rows are touched; without it, every row is. Check the row count in the command tag after every change.

UPDATE

The syntax is UPDATE table SET column = expression [, column = expression …] WHERE condition. The expression can use the row's current values, so you can calculate the new value from the old one. Here is a 10 percent raise for the Sales department (inside a transaction that is rolled back, as in the previous article):

BEGIN;
UPDATE employees
SET salary = salary * 1.10
WHERE dept_id = 2
RETURNING emp_id, first_name, salary;
ROLLBACK;
 emp_id | first_name |  salary
--------+------------+-----------
      3 | Ananya     | 165000.00
      9 | Karan      | 176000.00
     10 | Neha       |  82500.00
(3 rows)

UPDATE 3

UPDATE 3 tells you three rows changed. If you expected three, good. If it says 12, you forgot the WHERE. An UPDATE that matches no row is not an error; it prints UPDATE 0.

  • Several columns: SET salary = 90000, dept_id = 2.
  • NULL and defaults: SET phone = NULL and SET stock = DEFAULT.
  • All right-hand sides use the old row. SET a = b, b = a swaps the two values; the second assignment does not see the first.
  • A subquery can supply a value: SET salary = (SELECT MAX(salary) FROM employees WHERE dept_id = 2) as long as it returns one row and one column.

UPDATE using another table

Often the rows to change are chosen by looking at another table: "give a 5 percent raise to everyone who works on the Payments Platform project (id 1)". The portable way is a subquery:

UPDATE employees
SET salary = salary * 1.05
WHERE emp_id IN (SELECT emp_id FROM employee_projects WHERE project_id = 1);

This changes three rows: Priya becomes 157500.00, Rahul 157500.00 and Arjun 115500.00. PostgreSQL also has UPDATE … FROM, MySQL has UPDATE … JOIN:

UPDATE employees AS e
SET salary = e.salary * 1.05
FROM employee_projects AS ep
WHERE ep.emp_id = e.emp_id
  AND ep.project_id = 1;
UPDATE employees AS e
JOIN employee_projects AS ep ON ep.emp_id = e.emp_id
SET e.salary = e.salary * 1.05
WHERE ep.project_id = 1;

Edge case: one target row, many matching rows

If the join finds several source rows for one employee (for example an employee on projects 1 and 2 when you remove the project_id filter), PostgreSQL applies only one of them, chosen arbitrarily, and the employee is updated once, not twice. A subquery with IN never has this surprise.

DELETE

DELETE FROM table WHERE condition removes the matching rows. Rows that reference the deleted row through a foreign key are handled by the foreign key's ON DELETE rule (see Foreign key actions). In the sample database, items of an order are deleted together with the order:

BEGIN;
DELETE FROM orders WHERE status = 'CANCELLED' RETURNING order_id, customer_id;
SELECT COUNT(*) AS items_left FROM order_items;
ROLLBACK;
 order_id | customer_id
----------+-------------
        4 |           3
(1 row)

DELETE 1

 items_left
------------
         18
(1 row)

Order 4 had one item, so order_items went from 19 rows to 18 without you deleting anything there: fk_items_order is declared with ON DELETE CASCADE. The opposite case is a customer who has orders, where the default rule refuses the delete:

ERROR:  update or delete on table "customers" violates foreign key constraint
        "fk_orders_customer" on table "orders"
DETAIL:  Key (customer_id)=(1) is still referenced from table "orders".

Deleting rows by looking at another table works like UPDATE: use a subquery (WHERE order_id IN (SELECT …)), PostgreSQL's DELETE … USING, or MySQL's DELETE t FROM t JOIN ….

Check how many rows changed

Every UPDATE and DELETE reports a count (UPDATE 3, DELETE 1). Compare it with what you expected before you commit. In Java, executeUpdate() returns the same number, and code can use it: an UPDATE … WHERE id = ? AND version = ? that returns 0 means somebody else changed the row first (this is how optimistic locking works).

Soft delete: mark instead of remove

Many applications never run DELETE on business data. They add a column such as deleted_at TIMESTAMPTZ and set it, so the row can be restored and the history is kept:

ALTER TABLE customers ADD COLUMN deleted_at TIMESTAMPTZ;

UPDATE customers SET deleted_at = NOW() WHERE customer_id = 6;

SELECT * FROM customers WHERE deleted_at IS NULL;   -- every query must remember this

The costs: every query must filter deleted_at IS NULL (views or Hibernate's soft-delete support can hide that), unique constraints get awkward (a deleted email blocks a new signup unless you use a partial unique index such as CREATE UNIQUE INDEX … ON customers (email) WHERE deleted_at IS NULL), and personal data must still be erased when privacy rules require it.

Rule: every UPDATE and DELETE needs a WHERE you have checked

Write the WHERE first, run it as a SELECT, and only then turn it into an UPDATE or DELETE (see Changing data safely).

Mistake: a forgotten or wrong WHERE

Wrong: everyone gets the raise

UPDATE employees SET salary = salary * 1.10;      -- UPDATE 12

Right: only Sales

UPDATE employees SET salary = salary * 1.10 WHERE dept_id = 2;   -- UPDATE 3

The command tag is your alarm bell: 12 instead of 3. A similar bug is WHERE dept_id = 2 OR salary > 100000 written when you meant AND; it matches far more rows than you think.

Errors and limits

  • An update can violate a constraint: SET salary = -5 fails with new row for relation "employees" violates check constraint "employees_salary_check".
  • A subquery in SET that returns two rows fails: ERROR: more than one row returned by a subquery used as an expression.
  • MySQL allows UPDATE … LIMIT n and DELETE … LIMIT n; PostgreSQL does not. To limit a delete in PostgreSQL use WHERE ctid IN (SELECT ctid … LIMIT n) or a key subquery.

Interview angle

  • What happens if you forget WHERE in an UPDATE? Every row changes. Describe the safe workflow: SELECT first, transaction, check the count, then commit.
  • Hard delete vs soft delete? Hard delete removes the row for good; soft delete sets a flag or timestamp, keeps history, but every query must filter it.
  • How do you update one table using another? A subquery, UPDATE … FROM (PostgreSQL) or UPDATE … JOIN (MySQL).

Changing data safely: transactions, TRUNCATE and DROP

Databases do not ask "are you sure?". Look first with a SELECT, change inside a transaction, check the row count, then COMMIT or ROLLBACK. Know the difference between DELETE (some rows), TRUNCATE (all rows, fast) and DROP TABLE (the table itself).

The risk

Most tools run in autocommit mode: every statement is committed the moment it succeeds. An UPDATE employees SET dept_id = 1 without WHERE moves all twelve employees to Engineering, and there is no undo button. Your only way back is a backup. People lose real data this way, so experienced developers follow a routine.

The safe workflow

  1. Look first. Write the WHERE clause as a SELECT and check the rows and the count.
  2. Open a transaction with BEGIN;.
  3. Run the change with exactly the same WHERE. Read the command tag.
  4. Verify with another SELECT.
  5. COMMIT; if everything is as expected, ROLLBACK; if not.
learn_sql=> SELECT emp_id, first_name, salary FROM employees WHERE dept_id = 3 ORDER BY emp_id;
 emp_id | first_name |  salary
--------+------------+-----------
      4 | Sunita     | 120000.00
     11 | Farhan     |  65000.00
     12 | Isha       |  55000.00
(3 rows)

learn_sql=> BEGIN;
BEGIN
learn_sql=*> UPDATE employees SET salary = salary * 1.10 WHERE dept_id = 3;
UPDATE 3
learn_sql=*> SELECT emp_id, first_name, salary FROM employees WHERE dept_id = 3 ORDER BY emp_id;
 emp_id | first_name |  salary
--------+------------+-----------
      4 | Sunita     | 132000.00
     11 | Farhan     |  71500.00
     12 | Isha       |  60500.00
(3 rows)

learn_sql=*> ROLLBACK;
ROLLBACK

The * in the prompt (learn_sql=*>) means "a transaction is open". The count UPDATE 3 matched the three rows seen in step 1, so this is a plan you could have committed. After ROLLBACK the salaries are back to the old values. If a statement fails inside a transaction, PostgreSQL marks the whole transaction as failed (prompt learn_sql=!>) and answers every later command with ERROR: current transaction is aborted, commands ignored until end of transaction block; the only way out is ROLLBACK.

Transactions in short

CommandMeaning
BEGIN (or START TRANSACTION)Start a group of statements that succeed or fail together
COMMITMake all changes permanent and visible to others
ROLLBACKUndo every change since BEGIN
SAVEPOINT name / ROLLBACK TO nameUndo only part of a transaction

PostgreSQL can roll back CREATE TABLE, ALTER TABLE and DROP TABLE too. MySQL cannot: DDL statements commit the open transaction automatically, so there is no undo for them. Transactions, ACID and isolation levels are explained in Module 5; in Spring Boot you get them with @Transactional.

Where autocommit hides

  • psql: autocommit is on. \set AUTOCOMMIT off makes it open a transaction for you (then you must COMMIT).
  • DBeaver and MySQL Workbench: an auto-commit toggle sits in the toolbar. Switch to manual commit when you work on important data.
  • JDBC: connection.setAutoCommit(false) starts a transaction; the default is true.
  • MySQL safe mode: start the client with mysql --safe-updates (Workbench has a "Safe Updates" option). UPDATE and DELETE without a key condition in WHERE or a LIMIT are then rejected. PostgreSQL has no built-in equivalent.

DELETE vs TRUNCATE vs DROP

Three ways to get rid of data, and one of the most common interview questions:

DELETETRUNCATEDROP TABLE
RemovesThe rows you choose, or allAll rowsThe whole table: rows, columns, indexes, constraints
WHEREYesNoNo
GroupDMLDDLDDL

Roll backYesPostgreSQL yes, MySQL noPostgreSQL yes, MySQL no

DELETE FROM clearance;                                  -- all rows, row by row, can use WHERE
TRUNCATE TABLE clearance;                               -- all rows, fast, no WHERE
TRUNCATE TABLE orders, order_items RESTART IDENTITY;    -- PostgreSQL: several tables, reset ids
TRUNCATE TABLE orders CASCADE;                          -- PostgreSQL: also empties tables that reference it!
DROP TABLE clearance;                                   -- error if it does not exist
DROP TABLE IF EXISTS clearance;                         -- no error if it does not exist

Why is DELETE slow on a big table? It removes row by row, writes each change to the log, fires triggers, and in PostgreSQL leaves dead row versions behind for VACUUM to clean. TRUNCATE throws away the table's files in one step. The price is a strong lock (it waits for, and blocks, every other query on that table) and the missing WHERE. TRUNCATE on a table that other tables reference fails in both databases (ERROR: cannot truncate a table referenced in a foreign key constraint); PostgreSQL's CASCADE option "fixes" it by truncating the child tables too, which is rarely what you want.

Keep a way back

  • Before a risky change on real data, copy the table: CREATE TABLE employees_backup AS SELECT * FROM employees; (drop it later).
  • Real systems rely on full backups (pg_dump, mysqldump) and point-in-time recovery, and on least privilege: analysts get read-only accounts.
  • Schema and data changes in production go through reviewed migration scripts (Flyway or Liquibase), not through someone's SQL window.

Rule: read the row count before you commit

The count in UPDATE n or DELETE n must match what the preview SELECT showed. If it does not, ROLLBACK.

Mistake: DROP or TRUNCATE on the wrong database

The window title says production, you thought it said learn_sql. Check \conninfo before destructive commands, colour production connections red in DBeaver or pgAdmin, and never keep production credentials in a tool you use for practice.

Tip: type the WHERE before the verb

Write … WHERE emp_id = 7 first, then move the cursor to the start and type DELETE FROM employees. If you press Enter by accident halfway, there is no incomplete destructive statement.

Interview angle

  • DELETE vs TRUNCATE vs DROP: some or all rows with WHERE and logging, versus all rows quickly without WHERE, versus the table itself. Add the rollback difference between PostgreSQL and MySQL, and that TRUNCATE is DDL.
  • How do you protect against a bad update? Preview with SELECT, use a transaction, check the count, keep backups, use least-privilege accounts.
  • Can DDL be rolled back? In PostgreSQL yes; in MySQL no, it commits implicitly.

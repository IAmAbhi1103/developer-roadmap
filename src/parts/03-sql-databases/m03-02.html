Window functions: OVER, PARTITION BY and ORDER BY

A window function calculates something across a set of related rows (the "window") but, unlike GROUP BY, keeps every row. OVER (PARTITION BY … ORDER BY …) defines the window: partition = which rows belong together, order = their sequence.

The problem GROUP BY cannot solve

You want each employee's salary next to the average salary of their department, to see who is above or below. GROUP BY dept_id returns one row per department and loses the employees. A subquery or a join back to a grouped result works, but is clumsy. A window function does it directly:

SELECT first_name,
       salary,
       ROUND(AVG(salary) OVER w, 2)          AS dept_avg,
       ROUND(salary - AVG(salary) OVER w, 2) AS diff
FROM employees
WHERE dept_id = 1
WINDOW w AS (PARTITION BY dept_id)
ORDER BY emp_id;
 first_name |  salary   | dept_avg  |   diff
------------+-----------+-----------+-----------
 Vikram     | 220000.00 | 144000.00 |  76000.00
 Priya      | 150000.00 | 144000.00 |   6000.00
 Rahul      | 150000.00 | 144000.00 |   6000.00
 Arjun      | 110000.00 | 144000.00 | -34000.00
 Divya      |  90000.00 | 144000.00 | -54000.00
(5 rows)

All five employees are still there, and every row has the average of its own department. The WINDOW w AS (…) clause names a window so you do not repeat it.

Syntax

function_name(arguments) OVER (
    PARTITION BY column1, column2      -- optional: split rows into independent groups
    ORDER BY column3 [DESC]            -- optional: order within each partition
    frame_clause                       -- optional: which rows around the current row (next article)
)
  • OVER () with nothing inside: the window is the whole result set. SUM(salary) OVER () is the grand total on every row.
  • PARTITION BY: like GROUP BY but without collapsing rows. The function restarts for every partition. Omit it and there is one partition.
  • ORDER BY inside OVER: required by ranking and navigation functions (ROW_NUMBER, LAG); for aggregates it makes the result cumulative (running total) instead of the same value on every row. It is independent from the final ORDER BY of the query.

You can combine them: grouping runs first, then windows run over the grouped rows (RANK() OVER (ORDER BY SUM(salary) DESC) is legal in a GROUP BY query).

Where windows run, and why you cannot filter on them

From the logical order: windows are computed in the SELECT step, after WHERE, GROUP BY and HAVING. Two consequences:

  • A window only sees rows that survived WHERE. Filtering first changes the result: the average over "dept 1 only" differs from the average over everyone.
  • You cannot use a window function in WHERE, since it does not exist yet: ERROR: window functions are not allowed in WHERE. To filter on a rank or running total, compute it in a subquery or CTE and filter outside.

Wrong: filter on the window in WHERE

SELECT first_name, salary
FROM employees
WHERE ROW_NUMBER() OVER (ORDER BY salary DESC) <= 3;
-- ERROR:  window functions are not allowed in WHERE

Right: compute in a CTE, filter outside

WITH ranked AS (
    SELECT first_name, salary,
           ROW_NUMBER() OVER (ORDER BY salary DESC, emp_id) AS rn
    FROM employees
)
SELECT first_name, salary FROM ranked WHERE rn <= 3;

Databases like Snowflake and BigQuery have a QUALIFY clause for this; PostgreSQL and MySQL do not, so the CTE pattern above is the one to memorise.

Rule: windows need PostgreSQL 8.4+ or MySQL 8.0+

MySQL 5.7 has no window functions at all, so interview answers for MySQL 5.7 use variables or correlated subqueries. Every maintained MySQL (8.x) supports everything in this module.

Mistake: forgetting that ORDER BY inside OVER changes an aggregate

SUM(salary) OVER (PARTITION BY dept_id) gives the department total on every row. SUM(salary) OVER (PARTITION BY dept_id ORDER BY hire_date) gives a running total. Adding an ORDER BY is a change of meaning, not a cosmetic choice.

Edge cases

  • NULL partition keys form one partition (Meera, with dept_id = NULL, is a partition of one).
  • Window functions cannot be nested inside each other or inside aggregates of the same level; wrap one in a subquery.
  • Query-level ORDER BY sorts the final output only; the window ORDER BY decides the calculation.

Interview angle

"What is a window function and how does it differ from GROUP BY?" Rows are kept; the function looks at a window defined by PARTITION BY/ORDER BY. "Why can't you use it in WHERE?" Logical order. Then expect ranking and top N per group.

ROW_NUMBER, RANK, DENSE_RANK and NTILE

All four number rows in an ordered window. They differ only in how they treat ties: ROW_NUMBER never repeats, RANK repeats and skips, DENSE_RANK repeats and does not skip, and NTILE(n) splits rows into n equal buckets.

The four on the same data

Ananya, Priya and Rahul all earn 150,000, so the sample data is ideal for seeing ties.

SELECT first_name, salary,
       ROW_NUMBER() OVER w AS row_num,
       RANK()       OVER w AS rnk,
       DENSE_RANK() OVER w AS dense_rnk,
       NTILE(4)     OVER w AS quartile
FROM employees
WINDOW w AS (ORDER BY salary DESC)
ORDER BY salary DESC, emp_id;

Ranking functions take no argument (except NTILE) and require an ORDER BY in the window. With ties, ROW_NUMBER is not deterministic: the database may number Ananya, Priya and Rahul in any order, and a different one on the next run. Add a unique tie-breaker (ORDER BY salary DESC, emp_id) to make it repeatable. Also available: PERCENT_RANK() (relative rank from 0 to 1) and CUME_DIST() (share of rows at or below).

Ranking inside groups

PARTITION BY restarts the numbering for every group. Rank within each department:

SELECT dept_id, first_name, salary,
       DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS pos
FROM employees
WHERE dept_id = 1
ORDER BY salary DESC, emp_id;
 dept_id | first_name |  salary   | pos
---------+------------+-----------+-----

       1 | Priya      | 150000.00 |   2
       1 | Rahul      | 150000.00 |   2
       1 | Arjun      | 110000.00 |   3
       1 | Divya      |  90000.00 |   4
(5 rows)

Top N per group

The most common use. Wrap the ranking in a CTE and filter on it. "Top 3 salaries in each department":

WITH ranked AS (
    SELECT dept_id, first_name, salary,
           DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS pos
    FROM employees
    WHERE dept_id IS NOT NULL
)
SELECT dept_id, first_name, salary, pos
FROM ranked
WHERE pos <= 3
ORDER BY dept_id, pos, first_name;
 dept_id | first_name |  salary   | pos
---------+------------+-----------+-----
       1 | Vikram     | 220000.00 |   1
       1 | Priya      | 150000.00 |   2
       1 | Rahul      | 150000.00 |   2
       1 | Arjun      | 110000.00 |   3
       2 | Karan      | 160000.00 |   1
       2 | Ananya     | 150000.00 |   2
       2 | Neha       |  75000.00 |   3
       3 | Sunita     | 120000.00 |   1
       3 | Farhan     |  65000.00 |   2
       3 | Isha       |  55000.00 |   3
(10 rows)

Department 1 returns four rows because two people share second place, so the top 3 salaries are 220000, 150000 and 110000. Which function you pick answers a different question:

QuestionUseDept 1 returns
The 3 highest salary valuesDENSE_RANK() <= 3Vikram, Priya, Rahul, Arjun (4 rows)
Everyone in the first 3 places (gaps after ties)RANK() <= 3Vikram, Priya, Rahul (3 rows)
Exactly 3 employeesROW_NUMBER() <= 3Vikram, Priya, Rahul (3 rows; tie broken by emp_id)

In an interview, ask which one the interviewer means; that question alone shows maturity. Two other ways to write top N per group, both without a window function:

-- Correlated subquery: fewer than 3 distinct higher salaries in the same department
SELECT e.dept_id, e.first_name, e.salary
FROM employees e
WHERE e.dept_id IS NOT NULL
  AND (SELECT COUNT(DISTINCT x.salary)
       FROM employees x
       WHERE x.dept_id = e.dept_id AND x.salary > e.salary) < 3;

-- LATERAL join (PostgreSQL): the top 3 rows of each department
SELECT d.name, t.first_name, t.salary
FROM departments d
CROSS JOIN LATERAL (SELECT first_name, salary FROM employees e
                    WHERE e.dept_id = d.dept_id
                    ORDER BY salary DESC LIMIT 3) AS t;

The first has the same meaning as DENSE_RANK and works on MySQL 5.7; the second returns exactly 3 rows per department and is fast with an index on (dept_id, salary DESC).

Other uses

  • The latest row per group: ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date DESC) = 1 gives each customer's most recent order. PostgreSQL's DISTINCT ON (customer_id) is a shortcut (DISTINCT).
  • De-duplication: number the copies of each duplicate and delete those above 1 (Duplicates).
  • Buckets: NTILE(4) labels each employee's pay quartile; NTILE(100) approximates percentiles. With 12 rows and 4 buckets each gets 3; with 10 rows and 4 buckets the sizes are 3, 3, 2, 2 (the extra rows go to the first buckets).
  • Pagination with a numbered list (rarely better than LIMIT).

Rule: pick the function from the tie behaviour you need

Same rank for equal values and no gaps: DENSE_RANK. Same rank but gaps: RANK. Always unique: ROW_NUMBER, with a deterministic tie-breaker in ORDER BY.

Mistake: ROW_NUMBER for "Nth highest salary"

If three people share the second salary, ROW_NUMBER() = 2 returns just one of them and may skip the real second value entirely (the second row can hold the same salary as the first). For "Nth highest value" use DENSE_RANK.

Edge cases

  • NULLs in the ordering column sort last in ASC and first in DESC in PostgreSQL (MySQL: smallest). Use NULLS LAST or filter them out.
  • NTILE(5) on 3 rows gives buckets 1, 2, 3 and leaves 4 and 5 empty.
  • Rank values are BIGINT; comparing with an integer literal is fine.

Interview angle

"Difference between RANK, DENSE_RANK and ROW_NUMBER" with the 150000-tie example is the single most common window-function question. Then "top 3 salaries in each department" and "latest order per customer". Mention the CTE needed to filter on the rank.

Frames, running totals, LAG/LEAD and FIRST/LAST_VALUE

A frame narrows the window around the current row (ROWS BETWEEN 2 PRECEDING AND CURRENT ROW). Frames power running totals and moving averages. LAG/LEAD read the previous or next row, and LAST_VALUE needs a full frame to behave as expected.

What a frame is

Inside a partition, the frame is the set of rows the function actually reads for the current row. Syntax: ROWS | RANGE | GROUPS BETWEEN start AND end, where the boundaries are UNBOUNDED PRECEDING, n PRECEDING, CURRENT ROW, n FOLLOWING and UNBOUNDED FOLLOWING.

Defaults matter. With no ORDER BY in the window, the frame is the whole partition. With an ORDER BY and no explicit frame, it is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW: from the first row up to the current row and all its peers (rows with the same sort value). That default causes the next two surprises.

ROWS vs RANGE

ROWS counts physical rows. RANGE works on values and includes every peer of the current row. The difference only shows when the sort column has ties. Department 1, running total by salary:

SELECT first_name, salary,
       SUM(salary) OVER (ORDER BY salary DESC)                                  AS default_range,
       SUM(salary) OVER (ORDER BY salary DESC, emp_id
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)      AS rows_frame
FROM employees
WHERE dept_id = 1
ORDER BY salary DESC, emp_id;
 first_name |  salary   | default_range | rows_frame
------------+-----------+---------------+------------
 Vikram     | 220000.00 |     220000.00 |  220000.00
 Priya      | 150000.00 |     520000.00 |  370000.00
 Rahul      | 150000.00 |     520000.00 |  520000.00
 Arjun      | 110000.00 |     630000.00 |  630000.00
 Divya      |  90000.00 |     720000.00 |  720000.00
(5 rows)

With the default RANGE, Priya and Rahul are peers (same salary), so both include both of them: 520000 each. ROWS with a unique ordering gives the true row-by-row running total. Rule of thumb: for running totals, write ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW and order by a unique key. PostgreSQL also has GROUPS mode (counts groups of peers). MySQL supports ROWS and RANGE.

Running totals and moving averages

Employees in hire order: the cumulative payroll and a 3-row moving average.

SELECT first_name, hire_date, salary,
       SUM(salary) OVER (ORDER BY hire_date, emp_id
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
       ROUND(AVG(salary) OVER (ORDER BY hire_date, emp_id
                         ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2)      AS moving_avg_3
FROM employees
ORDER BY hire_date, emp_id;

Percent of total

A window aggregate without ORDER BY reads the whole partition, so each row can be divided by its group's total:

SELECT first_name, salary,
       ROUND(100 * salary / SUM(salary) OVER (PARTITION BY dept_id), 1) AS pct_of_dept
FROM employees
WHERE dept_id = 3
ORDER BY salary DESC;
 first_name |  salary   | pct_of_dept
------------+-----------+-------------
 Sunita     | 120000.00 |        50.0
 Farhan     |  65000.00 |        27.1
 Isha       |  55000.00 |        22.9
(3 rows)

LAG and LEAD

LAG(expr, offset, default) returns the value from offset rows before the current row (default offset 1); LEAD looks after. When no such row exists you get NULL, or the default you provide. They ignore frames and need an ORDER BY.

SELECT first_name, hire_date,
       LAG(first_name)             OVER w AS hired_before,
       LEAD(first_name, 1, 'nobody') OVER w AS hired_after
FROM employees
WHERE emp_id <= 5
WINDOW w AS (ORDER BY hire_date)
ORDER BY hire_date;
 first_name | hire_date  | hired_before | hired_after
------------+------------+--------------+-------------
 Meera      | 2015-04-01 | (null)       | Vikram
 Vikram     | 2016-07-15 | Meera        | Ananya
 Ananya     | 2017-02-20 | Vikram       | Sunita
 Sunita     | 2018-06-11 | Ananya       | Priya
 Priya      | 2019-01-07 | Sunita       | nobody
(5 rows)

Typical uses: the change from the previous month (revenue - LAG(revenue) OVER (ORDER BY month), see month-over-month growth), days since the previous login, and comparing a row with the next event. Note the WHERE ran first: the window only saw five employees.

FIRST_VALUE, LAST_VALUE and NTH_VALUE

FIRST_VALUE(expr) returns the value from the first row of the frame, LAST_VALUE from the last row, NTH_VALUE(expr, n) from the n-th. Here is the famous gotcha, in HR (the highest salary first):

SELECT first_name, salary,
       FIRST_VALUE(first_name) OVER (ORDER BY salary DESC) AS top_earner,
       LAST_VALUE(first_name)  OVER (ORDER BY salary DESC) AS last_wrong,
       LAST_VALUE(first_name)  OVER (ORDER BY salary DESC
            ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS lowest_paid
FROM employees
WHERE dept_id = 3
ORDER BY salary DESC;
 first_name |  salary   | top_earner | last_wrong | lowest_paid
------------+-----------+------------+------------+-------------
 Sunita     | 120000.00 | Sunita     | Sunita     | Isha
 Farhan     |  65000.00 | Sunita     | Farhan     | Isha
 Isha       |  55000.00 | Sunita     | Isha       | Isha
(3 rows)

The default frame ends at the current row, so "the last row of the frame" is simply the current row (last_wrong). To see the real last row, extend the frame to UNBOUNDED FOLLOWING. FIRST_VALUE works with the default frame because the frame always starts at the first row. Alternatively, flip the ordering and use FIRST_VALUE.

Rule: spell out the frame when it matters

Running totals: ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW with a unique order key. LAST_VALUE and NTH_VALUE: … AND UNBOUNDED FOLLOWING. Relying on the default hides the peer behaviour from the next reader.

Mistake: a running total ordered by a non-unique column

Ordering a running total by order_date when several orders share a date gives the same total for all of them (the default RANGE frame, peers included) or a random split inside the day with ROWS. Add a tie-breaker such as the id.

Edge cases

  • ROWS frames with n PRECEDING near the start just use fewer rows; no error, no padding.
  • RANGE with an offset (RANGE BETWEEN 7 PRECEDING AND CURRENT ROW) needs one numeric or date ordering column and means "values within 7 of the current value".
  • LAG/LEAD with PARTITION BY do not cross partitions; the first row of each partition gets NULL.
  • Window frames need an ORDER BY for ROWS to be meaningful.

Interview angle

Likely: "running total per customer", "month-over-month change", "7-day moving average", "difference between ROWS and RANGE", and "why does LAST_VALUE return the current row?" The last two are the questions that separate memorised answers from understanding.

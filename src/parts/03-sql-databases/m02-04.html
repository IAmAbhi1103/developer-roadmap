String functions

SQL has a standard toolbox for text: join (||, CONCAT), measure (LENGTH), change case, trim, cut (SUBSTRING, LEFT, RIGHT), search (POSITION), replace and pad. Names differ a little between PostgreSQL and MySQL, so know both.

Why use them in SQL?

Cleaning and shaping text inside the query is faster than pulling every row into Java: build a display name, split an email into user and domain, mask a phone number, find the rows with a certain pattern, format an invoice number with leading zeros. Remember that a function around a column in WHERE (WHERE LOWER(email) = '…') stops a normal index on that column from being used; create an expression index (CREATE INDEX … ON employees (LOWER(email))) or store the data in the form you search for.

SQL strings are 1-based: the first character is position 1, not 0 as in Java. A position of 0 from POSITION means "not found".

A frequent real task is turning "first and last name" columns into a display name. Use CONCAT_WS(' ', first_name, last_name) when parts may be NULL: || returns NULL if any piece is NULL, and CONCAT_WS skips NULL pieces.

Searching text

LIKE and ILIKE (Module 1) cover simple patterns. For more, PostgreSQL has regular expressions with ~ (case-sensitive) and ~* (case-insensitive):

SELECT first_name, email
FROM employees
WHERE email ~ '^[a-k]'          -- starts with a letter from a to k
ORDER BY emp_id;
 first_name |           email
------------+----------------------------
 Ananya     | ananya.rao@example.com
 Arjun      | arjun.reddy@example.com
 Divya      | divya.krishnan@example.com
 Karan      | karan.malhotra@example.com
 Farhan     | farhan.shaikh@example.com
 Isha       | isha.banerjee@example.com
(6 rows)

Regular expressions are powerful but cannot use a normal index. For serious text search (words, ranking, stemming) PostgreSQL has full-text search (to_tsvector), and large systems use Elasticsearch or similar.

Rule: NULL in, NULL out

Almost every string function returns NULL when an argument is NULL: UPPER(NULL), NULL || 'x', LENGTH(NULL). Wrap possibly-missing values in COALESCE(col, '') or use CONCAT_WS.

Mistake: LENGTH in MySQL on non-English text

LENGTH('नमस्ते') in MySQL returns the number of bytes (18 in UTF-8), not characters (6). Use CHAR_LENGTH. PostgreSQL's LENGTH counts characters.

Tip: store clean, display late

Trim and lowercase data when it enters (emails), and format for display in the application or in the query. Data that is stored dirty needs TRIM(LOWER(…)) in every query, and defeats indexes.

Edge cases

  • SUBSTRING(s FROM 0 FOR 3) returns only 2 characters in PostgreSQL, since position 0 is "before the string". Start at 1.
  • SPLIT_PART(s, '@', 5) past the last part returns an empty string, not NULL (PostgreSQL). A position of 0 raises ERROR: field position must not be zero.
  • CHAR(n) values are space padded, which makes length and comparison results surprising; another reason to avoid CHAR.

Interview angle

Typical: "get the domain from an email" (SPLIT_PART or SUBSTRING after POSITION), "pad ids with zeros" (LPAD), "first letter capital" (INITCAP or UPPER(LEFT(…)) || LOWER(SUBSTRING(…))), "count a character in a string" (LENGTH(s) - LENGTH(REPLACE(s, 'a', ''))).

Date and time functions

Get the current time with NOW() and CURRENT_DATE, pull parts out with EXTRACT, round down with DATE_TRUNC, do arithmetic with INTERVAL, and measure gaps with AGE or by subtracting dates. MySQL uses DATE_FORMAT, DATEDIFF and DATE_ADD instead.

EXTRACT and DATE_TRUNC

EXTRACT(field FROM value) pulls out one part as a number. DATE_TRUNC('unit', value) cuts a timestamp down to the start of the year, month, week or day, which is the key to grouping by period. The examples use Priya's hire date, 2019-01-07, a Monday.

SELECT hire_date,
       EXTRACT(YEAR  FROM hire_date)           AS yr,
       EXTRACT(MONTH FROM hire_date)           AS mon,
       EXTRACT(DOW   FROM hire_date)           AS dow,          -- 0 = Sunday
       DATE_TRUNC('month', hire_date)::DATE    AS month_start,
       TO_CHAR(hire_date, 'Dy DD Mon YYYY')    AS pretty
FROM employees
WHERE emp_id = 5;
 hire_date  |  yr  | mon | dow | month_start |     pretty
------------+------+-----+-----+-------------+-----------------
 2019-01-07 | 2019 |   1 |   1 | 2019-01-01  | Mon 07 Jan 2019
(1 row)

Other EXTRACT fields: DAY, QUARTER, WEEK, DOY (day of year), HOUR, EPOCH (seconds since 1970). MySQL has YEAR(d), MONTH(d), DAYOFWEEK(d) (1 = Sunday) and also accepts EXTRACT. It has no DATE_TRUNC; use DATE_FORMAT(d, '%Y-%m-01') or LAST_DAY().

Grouping by month is a very common report:

SELECT TO_CHAR(DATE_TRUNC('month', order_date), 'YYYY-MM') AS month,
       COUNT(*)                                             AS orders
FROM orders
GROUP BY DATE_TRUNC('month', order_date)
ORDER BY DATE_TRUNC('month', order_date);

(4 rows)

MySQL: DATE_FORMAT(order_date, '%Y-%m') in both the select list and GROUP BY.

Rule: keep dates as dates

Store dates in DATE or TIMESTAMPTZ columns, never in text. Compare dates with dates, and format only at the edge, for display. Use ISO 'YYYY-MM-DD' literals in SQL.

Mistake: DATE_TRUNC returns timestamptz, not date

DATE_TRUNC('month', hire_date) on a DATE returns a timestamp with time zone, so the printed value changes with the session's time zone. Cast back with ::DATE when you want a day, as in the examples above.

Edge cases

  • Invalid dates raise ERROR: date/time field value out of range: "2026-02-30". A bad text input raises invalid input syntax for type date.
  • February 29: + INTERVAL '1 year' from 2024-02-29 gives 2025-02-28.
  • "Week" numbering is a trap: EXTRACT(WEEK …) is the ISO week (Monday start; the first days of January may belong to week 52 or 53 of the previous year).

Interview angle

Expect "orders per month", "employees hired in the last year", "age from date of birth", "customers who joined in the last 30 days", and "find the day of week with most orders". Group with DATE_TRUNC/DATE_FORMAT, filter with ranges (next article).

Filtering date ranges and time zones

Filter dates with a half-open range, >= start AND < next_start, never with BETWEEN on timestamps. Store moments as TIMESTAMPTZ, convert to a local zone with AT TIME ZONE only when you display or bucket by local day.

The half-open range

Hard question: "all orders in March 2026". For a DATE column BETWEEN '2026-03-01' AND '2026-03-31' works. For a TIMESTAMP it silently loses data, because the end point '2026-03-31' means 2026-03-31 00:00:00:

SELECT TIMESTAMP '2026-03-31 15:00:00' BETWEEN '2026-03-01' AND '2026-03-31' AS between_says,
       TIMESTAMP '2026-03-31 15:00:00' >= '2026-03-01'
       AND TIMESTAMP '2026-03-31 15:00:00' <  '2026-04-01'                  AS half_open_says;
 between_says | half_open_says
--------------+----------------
 f            | t
(1 row)

The half-open form includes the start and excludes the next period's start. It works for dates, timestamps and any precision, and the end of one range is exactly the start of the next, so ranges never overlap or leave gaps.

-- a fixed month
SELECT order_id, order_date
FROM orders
WHERE order_date >= DATE '2026-03-01' AND order_date < DATE '2026-04-01'
ORDER BY order_id;

-- the last 30 days
SELECT COUNT(*) FROM orders WHERE order_date >= CURRENT_DATE - 30;

-- the current month, whatever today is
SELECT COUNT(*) FROM orders
WHERE order_date >= DATE_TRUNC('month', CURRENT_DATE)
  AND order_date <  DATE_TRUNC('month', CURRENT_DATE) + INTERVAL '1 month';
 order_id | order_date
----------+------------
        6 | 2026-03-08
        7 | 2026-03-21
        8 | 2026-03-30
(3 rows)

Keep the column bare so indexes work

A condition that wraps the column in a function cannot use a normal index on that column. The database must compute the function for every row. Rewrite it as a range on the bare column:

Wrong: function on the column (index not used)

WHERE EXTRACT(YEAR FROM order_date) = 2026
  AND EXTRACT(MONTH FROM order_date) = 3

Right: range on the bare column

WHERE order_date >= DATE '2026-03-01'
  AND order_date <  DATE '2026-04-01'

A condition written so that an index can be used is called sargable (search-argument able). Same idea as WHERE LOWER(email) = … in the string article.

Time zones

Chapter one rule: store the instant, not the local clock. In PostgreSQL that means TIMESTAMPTZ (data types). It is saved as UTC; each session shows it in its TimeZone setting. AT TIME ZONE converts between the two kinds of timestamp, and its direction trips people up:

  • timestamptz AT TIME ZONE 'zone' returns a plain timestamp: the wall-clock time in that zone.
  • timestamp AT TIME ZONE 'zone' returns a timestamptz: it says "this wall-clock reading was taken in that zone".
SET TIME ZONE 'UTC';
SELECT TIMESTAMPTZ '2026-04-10 09:00:00+00' AT TIME ZONE 'Asia/Kolkata' AS ist_clock,
       TIMESTAMP   '2026-04-10 14:30:00'    AT TIME ZONE 'Asia/Kolkata' AS instant;
      ist_clock      |        instant
---------------------+------------------------
 2026-04-10 14:30:00 | 2026-04-10 09:00:00+00
(1 row)

Typical use: counting orders per local day. A purchase at 23:30 IST on 9 April is 18:00 UTC on 9 April, but 00:10 IST on 10 April is 18:40 UTC on 9 April, so grouping on the UTC date puts it on the wrong day for an Indian shop. Group on the local date:

SELECT (created_at AT TIME ZONE 'Asia/Kolkata')::DATE AS local_day, COUNT(*) AS orders
FROM web_orders                        -- a hypothetical table with created_at TIMESTAMPTZ
GROUP BY (created_at AT TIME ZONE 'Asia/Kolkata')::DATE
ORDER BY local_day;

India has no daylight saving time (always +05:30), but many countries do, and across a DST change a "day" has 23 or 25 hours. Use the zone name ('Asia/Kolkata', 'America/New_York'), not a fixed offset such as '+05:30', so the database knows the rules. List names with SELECT name FROM pg_timezone_names.

MySQL: TIMESTAMP converts to UTC on storage according to the session time_zone variable; DATETIME does not. CONVERT_TZ(ts, 'UTC', 'Asia/Kolkata') converts, but named zones work only after the time-zone tables have been loaded into MySQL. A frequent production fix is running all servers, JVMs and databases in UTC.

In Java use Instant or OffsetDateTime for TIMESTAMPTZ, and LocalDate for DATE. Never store java.util.Date without knowing the JVM's time zone.

Rule: ranges are closed at the start and open at the end

col >= start AND col < end_exclusive. For "the whole of 30 April" the end is 1 May. Compute it with + INTERVAL '1 day' instead of writing 23:59:59, which loses fractions of a second.

Mistake: comparing a timestamp column with a date literal

WHERE created_at = '2026-04-10' matches only rows at exactly midnight. To match a day use created_at >= '2026-04-10' AND created_at < '2026-04-11', or created_at::DATE = '2026-04-10' for small tables only.

Edge cases

  • A date literal compared with a TIMESTAMPTZ is read in the session time zone, so the same query can return different rows for two sessions in different zones.
  • BETWEEN with a reversed range (BETWEEN 10 AND 5) returns nothing; use BETWEEN SYMMETRIC in PostgreSQL if order is unknown.
  • The OVERLAPS operator checks whether two periods overlap: (s1, e1) OVERLAPS (s2, e2).

Interview angle

"Why not BETWEEN for timestamps?" is a favourite. Give the half-open answer and add that it keeps indexes usable. "How do you handle time zones?" Store UTC with TIMESTAMPTZ, convert at the edges, run servers in UTC, use named zones.

Type casting

A cast converts a value from one type to another: CAST(x AS INTEGER), or the PostgreSQL shorthand x::INTEGER. Do it explicitly, and expect an error when the text cannot be converted.

Why you need it

Types decide behaviour. Integer division truncates, text sorts alphabetically ('10' before '9'), dates compare as dates and JDBC parameters arrive with a type. Casting is how you say what you mean: divide as decimals, compare a number stored as text, turn a timestamp into a day, or build a string from an id. SQL also converts some types automatically (implicit casts); the explicit form is safer.

The two syntaxes

SELECT CAST('42' AS INTEGER) + 1       AS a,    -- standard SQL, works in every database
       '42'::INTEGER + 1               AS b,    -- PostgreSQL shorthand
       7::NUMERIC / 2                  AS c,    -- decimal division
       CAST(150000.60 AS INTEGER)      AS d,    -- numeric to integer rounds
       TRUNC(150000.60)                AS e,    -- cuts off the decimals
       '2026-04-10'::DATE + 1          AS f,
       NOW()::DATE                     AS g,    -- timestamp to date
       emp_id::TEXT || '-' || last_name AS h
FROM employees WHERE emp_id = 5;
  a | b  |          c          |   d    |   e    |     f      |     g      |    h
----+----+---------------------+--------+--------+------------+------------+----------
 43 | 43 |  3.5000000000000000 | 150001 | 150000 | 2026-04-11 | 2026-04-10 | 5-Menon
(1 row)

(Column g shows the day you run it.) Note the rounding: casting a decimal to an integer rounds in PostgreSQL (150000.60 becomes 150001), unlike Java's (int) cast, which truncates.

Errors and implicit casts

SELECT 'abc'::INTEGER;
-- ERROR:  invalid input syntax for type integer: "abc"

SELECT '2026-13-45'::DATE;
-- ERROR:  date/time field value out of range: "2026-13-45"

SELECT first_name + 1 FROM employees;
-- ERROR:  operator does not exist: character varying + integer

SELECT '10' + 5;        -- 15: a bare quoted literal is "unknown" and adopts the number type

PostgreSQL is strict: a text column is not converted silently. MySQL is lax: it converts silently, and SELECT 'abc' + 5 returns 5 with a warning, because 'abc' becomes 0. The same laxness makes WHERE phone = 9876500001 compare numbers (and scan the whole table, ignoring the index on phone). Be explicit.

A related pitfall is casting inside a join or WHERE: ON o.customer_id::TEXT = c.ref works, but it blocks index use. Better to fix the column types.

Safe conversion of dirty data

PostgreSQL has no built-in "try cast" before version 16 (PostgreSQL 16 added pg_input_is_valid for this check). The classic approach is a regular expression guard:

SELECT CASE WHEN raw ~ '^[0-9]+$' THEN raw::INT END AS safe_value
FROM (VALUES ('12'), ('abc'), ('7')) AS t(raw);
 safe_value
------------
         12
     (null)
          7
(3 rows)

Rule: cast one side to match the other, and cast the value, not the indexed column

Write WHERE phone = '9876500001' (text to text) rather than casting phone::BIGINT. Cast the literal or parameter so the indexed column stays untouched.

Mistake: integer division in percentages

Wrong: always 0 or 1

SELECT delivered / total * 100;      -- 5 / 10 = 0

Right: cast first, or multiply first

SELECT 100.0 * delivered / total;    -- 50.0
SELECT delivered::NUMERIC / total * 100;

Edge cases

  • Casting to VARCHAR(5) silently truncates in an explicit cast, but raises "value too long" on an INSERT.
  • NULL casts to any type and stays NULL.
  • ' 42 '::INT works (PostgreSQL trims spaces around numbers); '4 2'::INT does not.

Interview angle

"What does SELECT 5/2 return?" (2 in PostgreSQL, 2.5000 in MySQL), "how do you get decimals?" (cast one operand), "explicit vs implicit casting" and "how do you convert text to a date".

Basic and intermediate SQL answer "what is in the table" and "how do I combine tables". Advanced SQL answers the harder questions: "rank employees inside each department", "what was the change from last month", "walk the whole management chain", "who logged in five days in a row". The tools are common table expressions (WITH), window functions (OVER), views, and the ability to put logic into the database with functions, procedures and triggers. These are also the topics that separate a strong SQL interview answer from an average one.

Common table expressions (WITH)

A CTE is a named, temporary result defined with WITH name AS (…) at the top of a statement. It lets you write a complex query as a sequence of small, readable steps instead of nested subqueries.

What and why

Nested subqueries read inside-out, and when the same subquery is needed twice you have to copy it. A CTE gives the step a name, defined once, read top to bottom. It exists only for the statement that follows; nothing is saved in the database. Both PostgreSQL and MySQL (8.0 and later) support it.

WITH step_one AS (
    SELECT ...
),
step_two AS (                 -- a later CTE can use an earlier one
    SELECT ... FROM step_one ...
)
SELECT ...
FROM step_two
JOIN step_one ON ...;         -- the main query can use all of them

Example: a multi-step report

Goal: for each customer, the number of orders and the total spent, ignoring cancelled orders. Step one computes the total of each order, step two summarises per customer, and the main query adds the name.

WITH order_totals AS (
    SELECT o.order_id, o.customer_id,
           SUM(oi.quantity * oi.unit_price) AS total
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.order_id
    WHERE o.status <> 'CANCELLED'
    GROUP BY o.order_id, o.customer_id
),
customer_totals AS (
    SELECT customer_id, COUNT(*) AS orders, SUM(total) AS spent
    FROM order_totals
    GROUP BY customer_id
)
SELECT c.name, ct.orders, ct.spent
FROM customer_totals AS ct
JOIN customers AS c ON c.customer_id = ct.customer_id
ORDER BY ct.spent DESC;
     name     | orders |  spent
--------------+--------+---------
 Aarav Shah   |      3 | 6206.00
 Diya Kapoor  |      2 | 5597.00
 Rohan Das    |      2 | 2474.00
 Kabir Singh  |      1 | 2100.00
 Ishita Joshi |      1 | 2048.00
(5 rows)

Sara and Tanvi are absent because they have no orders and the report starts from customer_totals. Kabir has one order because his other order (4) was cancelled.

Using a CTE twice

The big win over a subquery: a CTE can be referenced several times. "Customers who spent more than the average customer":

WITH spend AS (
    SELECT o.customer_id, SUM(oi.quantity * oi.unit_price) AS spent
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    WHERE o.status <> 'CANCELLED'
    GROUP BY o.customer_id
)
SELECT c.name, s.spent
FROM spend AS s
JOIN customers AS c ON c.customer_id = s.customer_id
WHERE s.spent > (SELECT AVG(spent) FROM spend)      -- second use of the same CTE
ORDER BY s.spent DESC;
    name     |  spent
-------------+---------
 Aarav Shah  | 6206.00
 Diya Kapoor | 5597.00
(2 rows)

(6206 + 5597 + 2474 + 2100 + 2048 = 18425, divided by 5 customers = 3685.)

Performance: in PostgreSQL 12 and later, a non-recursive CTE that is referenced once and has no side effects is inlined like a subquery, so the optimizer treats it the same. A CTE referenced more than once is computed once and reused (materialized). You can force the behaviour: WITH x AS MATERIALIZED (…) or AS NOT MATERIALIZED (…). Before PostgreSQL 12 every CTE was an "optimization fence", always computed first, which made some old advice ("CTEs are slow") true then. Today a CTE is mostly a readability tool, not a performance trick. MySQL 8 behaves similarly (it merges simple CTEs, or materializes them).

Data-modifying CTEs (PostgreSQL)

A CTE can contain INSERT, UPDATE or DELETE with RETURNING, and the main statement can use what came back. This moves rows between tables in one atomic statement:

WITH removed AS (
    DELETE FROM orders
    WHERE status = 'CANCELLED' AND order_date < DATE '2026-03-01'
    RETURNING *
)
INSERT INTO orders_archive
SELECT * FROM removed;

(Run it only on a copy: order 4 is cancelled and older than March, but it has order lines that this delete would also cascade. A real archive job would copy the lines first.) MySQL does not allow data-modifying CTEs.

Convention: name steps for what they hold

Use names like order_totals and active_customers, not t1 and x. One logical step per CTE, ordered from raw data to final shape, and let the last SELECT stay short. Teams often format the WITH block at the left edge so reviews read like a recipe.

Mistake: expecting a CTE to behave like a table or a temp table

A CTE is visible only inside its statement, has no index, and (unless materialized) is not computed once and cached for the next statement. If you run five queries on the same expensive intermediate result, create a temporary table or a materialized view instead (Views).

Rules and edge cases

  • CTE names must be unique in the WITH list. A later CTE can read an earlier one, but not the other way round: ERROR: relation "customer_totals" does not exist.
  • A CTE shadows a real table with the same name for that statement.
  • Column names can be listed after the name: WITH t(day, total) AS (…).
  • A CTE can be used in INSERT … WITH …, UPDATE and DELETE in PostgreSQL and MySQL 8 (WITH before the statement).

Interview angle

"What is a CTE and when would you use one?" Readability, reuse inside one statement, recursion. Know the difference from a view (stored vs temporary) and a temp table (data stored, indexable). Many "top N per group" and "Nth highest" answers use a CTE with a window function.

Recursive CTEs and generating series

A recursive CTE starts with an anchor query and repeatedly joins its own previous result until nothing new appears. It is how SQL walks trees and graphs (org charts, category trees) and generates sequences of numbers or dates.

The structure

A recursive CTE has two parts joined by UNION ALL:

  1. Anchor member: a normal query that returns the starting rows (the root of the tree).
  2. Recursive member: a query that refers to the CTE's own name. It runs on the rows produced by the previous round and returns the next level.
  3. Termination: the loop stops when a round returns zero rows. All rounds are then combined into the final result.
WITH RECURSIVE name (columns) AS (
    SELECT ...                       -- anchor: runs once
    UNION ALL
    SELECT ... FROM name ... WHERE ...   -- recursive: runs again and again
)
SELECT * FROM name;

MySQL 8 also needs the word RECURSIVE. (SQL Server and Oracle do not use the keyword.)

Counting from 1 to 5

WITH RECURSIVE counter (n) AS (
    SELECT 1                         -- anchor
    UNION ALL
    SELECT n + 1 FROM counter WHERE n < 5   -- recursive; stops when n reaches 5
)
SELECT n FROM counter;
 n
---
 1
 2
 3
 4
 5
(5 rows)

Round 0 returns 1. Round 1 reads the 1 and returns 2. This repeats until n < 5 fails, the round returns nothing, and the loop ends.

The org chart

The classic use. Start with the employee that has no manager, then repeatedly add the people whose manager_id equals an emp_id found in the previous round. Track the level and the path as you go:

WITH RECURSIVE org AS (
    SELECT emp_id, first_name, 1 AS level, first_name::TEXT AS path
    FROM employees
    WHERE manager_id IS NULL                      -- anchor: the CEO
    UNION ALL
    SELECT e.emp_id, e.first_name, o.level + 1, o.path || ' > ' || e.first_name
    FROM employees AS e
    JOIN org AS o ON e.manager_id = o.emp_id      -- recursive: direct reports of the previous level
)
SELECT level, path
FROM org
ORDER BY path;
 level |              path
-------+--------------------------------
     1 | Meera
     2 | Meera > Ananya
     3 | Meera > Ananya > Karan
     3 | Meera > Ananya > Neha
     2 | Meera > Sunita
     3 | Meera > Sunita > Farhan
     3 | Meera > Sunita > Isha
     2 | Meera > Vikram
     3 | Meera > Vikram > Priya
     4 | Meera > Vikram > Priya > Arjun
     4 | Meera > Vikram > Priya > Divya
     4 | Meera > Vikram > Priya > Rahul
(12 rows)

The path column gives you a handy sort that keeps each branch together. In MySQL, cast the path to a long enough type (CAST(first_name AS CHAR(200))), because the column width is fixed by the anchor row.

All subordinates of one manager

Change only the anchor to start from any node. Everyone under Vikram, directly or not:

WITH RECURSIVE team AS (
    SELECT emp_id, first_name FROM employees WHERE emp_id = 2      -- Vikram
    UNION ALL
    SELECT e.emp_id, e.first_name
    FROM employees e
    JOIN team t ON e.manager_id = t.emp_id
)
SELECT first_name FROM team WHERE emp_id <> 2 ORDER BY emp_id;

Going up works the same way with the join reversed. The chain of command above Divya (id 8) joins e.emp_id = c.manager_id. A category tree (categories(id, name, parent_id)) is the same pattern: breadcrumbs "Electronics > Computers > Laptops", or all sub-categories of a category for a product filter. Comment threads and bill-of-materials tables are further examples.

Generating series

Reports often need a row for every day, even days with no data. A recursive CTE can create the days, and in PostgreSQL the built-in generate_series is shorter:

SELECT d::DATE AS day, COUNT(o.order_id) AS orders
FROM generate_series(DATE '2026-04-01', DATE '2026-04-10', INTERVAL '1 day') AS d
LEFT JOIN orders AS o ON o.order_date = d::DATE
GROUP BY d
ORDER BY d;
    day     | orders
------------+--------
 2026-04-01 |      0
 2026-04-02 |      0
 2026-04-03 |      1
 2026-04-04 |      0
 2026-04-05 |      0
 2026-04-06 |      0
 2026-04-07 |      0
 2026-04-08 |      0
 2026-04-09 |      0
 2026-04-10 |      1
(10 rows)

Without the generated calendar, the days with no orders would simply be missing. MySQL has no generate_series; use a recursive CTE that adds one day (d + INTERVAL 1 DAY). Also handy: generate_series(1, 100000) to create a large test table for practising indexes and EXPLAIN:

CREATE TABLE big_numbers AS
SELECT n, md5(n::TEXT) AS hash FROM generate_series(1, 100000) AS n;

Protecting against endless loops

If the data contains a cycle (A manages B, B manages A), the recursion never finishes. Defences:

  • Carry a depth counter and stop: … WHERE o.level < 20.
  • Track visited ids in an array and refuse repeats: WHERE e.emp_id <> ALL (o.visited).
  • PostgreSQL 14 and later has a CYCLE clause that detects and marks cycles for you.
  • MySQL stops with an error after cte_max_recursion_depth rounds (default 1000).
  • Prevent bad data: a CHECK (manager_id <> emp_id) stops the simplest cycle.

Rule: anchor, UNION ALL, and a way out

The recursive member must reference the CTE exactly once and must eventually return no rows. Use UNION ALL (plain UNION removes duplicates each round and is slower, but also prevents some cycles). The column types come from the anchor, so cast the anchor to a type wide enough for later rounds (first_name::TEXT).

Mistake: no termination condition

Wrong: never stops

WITH RECURSIVE c(n) AS (
    SELECT 1 UNION ALL SELECT n + 1 FROM c
)
SELECT * FROM c;

Right: bounded

WITH RECURSIVE c(n) AS (
    SELECT 1 UNION ALL SELECT n + 1 FROM c WHERE n < 100
)
SELECT * FROM c;

The wrong query runs until memory or time runs out (add LIMIT while testing, which stops a PostgreSQL recursive CTE early).

Edge cases

  • A tree with several roots (or none) works: the anchor returns all roots; if no row has a NULL parent, you get nothing.
  • Rows are not guaranteed to come out level by level unless you order them. Always add ORDER BY.
  • For huge or very deep graphs, a dedicated graph database, or a materialized path column, may be a better design (Module 4).

Interview angle

"How do you query a hierarchy in SQL?" Describe the anchor and recursive member and the stop condition, then write the org-chart query. Follow-ups: "how do you detect cycles", "print the level/indentation" and "generate dates between two days". A self join only goes one level; a recursive CTE goes all the way down.

Worked design: a food-delivery app

Follow the design process end to end for a Swiggy-style app: requirements, entities, ER diagram, full PostgreSQL DDL in 3NF with constraints and indexes, then the queries the app must run.

1. Requirements

Write the requirements as plain sentences first. Every noun is a candidate entity, every verb a candidate relationship (see the design process).

  • A user signs up with an email and a mobile number and can save several addresses.
  • A restaurant has a name, a city and an open/closed flag, and sells many menu items, each with a price and an availability flag.
  • A user places an order with exactly one restaurant. It has many order items, each with a quantity. The price and name at the time of ordering must be kept, and the delivery address must be remembered even if the saved address changes later.
  • An order moves through PLACED, ACCEPTED, PREPARING, OUT_FOR_DELIVERY, DELIVERED or CANCELLED.
  • An order is paid with one or more payments: a failed UPI attempt can be retried by card. Each payment has a method, an amount and a status.

2. Entities, relationships and the ER diagram

Reading it: a user has zero or many addresses and orders; an order has exactly one user and one restaurant, at least one order item (||--|{), and zero or many payments (zero while unpaid, several if the first attempt fails). order_items is the join table between orders and menu items with extra columns, so it is a real entity.

3. Design decisions

  • Keys: surrogate BIGINT identity everywhere; email and mobile are UNIQUE. order_items uses the composite key (order_id, menu_item_id): one line per item, and the quantity says how many.
  • Money: integer paise (_paise suffix) with CHECKs.
  • 3NF check: user data lives only in users, restaurant data only in restaurants, and so on; no non-key column depends on another non-key column. Restaurant name on an order is reached by a join, not copied.
  • Deliberate denormalization: order_items.item_name and unit_price_paise (price at order time), the delivery address text on orders, and orders.total_paise (sum of lines, written in the same transaction). Each has a reason; see Denormalization.
  • Delete rules: lines die with their order (CASCADE); users, restaurants and menu items that have orders cannot be deleted (RESTRICT); a deleted saved address does not affect old orders.
  • Status: text with CHECK for orders and payments.

4. The DDL

CREATE TABLE users (
    id         BIGINT GENERATED ALWAYS AS IDENTITY,
    email      TEXT NOT NULL,
    mobile     TEXT NOT NULL,
    name       TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT pk_users PRIMARY KEY (id),
    CONSTRAINT uq_users_email  UNIQUE (email),
    CONSTRAINT uq_users_mobile UNIQUE (mobile),
    CONSTRAINT ck_users_mobile CHECK (mobile ~ '^\+[0-9]{8,15}$')
);

CREATE TABLE addresses (
    id      BIGINT GENERATED ALWAYS AS IDENTITY,
    user_id BIGINT NOT NULL,
    label   TEXT,                            -- 'Home', 'Office'
    line1   TEXT NOT NULL,
    city    TEXT NOT NULL,
    pincode CHAR(6) NOT NULL,
    CONSTRAINT pk_addresses PRIMARY KEY (id),
    CONSTRAINT fk_addresses_user FOREIGN KEY (user_id)
        REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT ck_addresses_pincode CHECK (pincode ~ '^[0-9]{6}$')
);
CREATE INDEX idx_addresses_user_id ON addresses (user_id);

CREATE TABLE restaurants (
    id         BIGINT GENERATED ALWAYS AS IDENTITY,
    name       TEXT NOT NULL,
    city       TEXT NOT NULL,
    is_open    BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT pk_restaurants PRIMARY KEY (id)
);
CREATE INDEX idx_restaurants_city ON restaurants (city);

CREATE TABLE menu_items (
    id            BIGINT GENERATED ALWAYS AS IDENTITY,
    restaurant_id BIGINT NOT NULL,
    name          TEXT NOT NULL,
    price_paise   BIGINT NOT NULL,
    is_available  BOOLEAN NOT NULL DEFAULT true,
    CONSTRAINT pk_menu_items PRIMARY KEY (id),
    CONSTRAINT fk_menu_items_restaurant FOREIGN KEY (restaurant_id)
        REFERENCES restaurants (id) ON DELETE RESTRICT,
    CONSTRAINT uq_menu_items_restaurant_name UNIQUE (restaurant_id, name),
    CONSTRAINT ck_menu_items_price CHECK (price_paise >= 0)
);

The unique pair (restaurant_id, name) also serves as the index for "items of a restaurant", so no separate index on restaurant_id is needed.

CREATE TABLE orders (
    id               BIGINT GENERATED ALWAYS AS IDENTITY,
    user_id          BIGINT NOT NULL,
    restaurant_id    BIGINT NOT NULL,
    status           TEXT NOT NULL DEFAULT 'PLACED',
    delivery_address TEXT NOT NULL,          -- snapshot of the address text
    total_paise      BIGINT NOT NULL,        -- sum of lines, set when the order is placed
    placed_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT pk_orders PRIMARY KEY (id),
    CONSTRAINT fk_orders_user FOREIGN KEY (user_id)
        REFERENCES users (id) ON DELETE RESTRICT,
    CONSTRAINT fk_orders_restaurant FOREIGN KEY (restaurant_id)
        REFERENCES restaurants (id) ON DELETE RESTRICT,
    CONSTRAINT ck_orders_status CHECK (status IN ('PLACED','ACCEPTED','PREPARING',
        'OUT_FOR_DELIVERY','DELIVERED','CANCELLED')),
    CONSTRAINT ck_orders_total CHECK (total_paise >= 0)
);
CREATE INDEX idx_orders_user_placed ON orders (user_id, placed_at DESC);
CREATE INDEX idx_orders_restaurant_placed ON orders (restaurant_id, placed_at);
CREATE INDEX idx_orders_active ON orders (status)
    WHERE status NOT IN ('DELIVERED','CANCELLED');           -- partial index

CREATE TABLE order_items (
    order_id         BIGINT NOT NULL,
    menu_item_id     BIGINT NOT NULL,
    item_name        TEXT   NOT NULL,        -- snapshot
    unit_price_paise BIGINT NOT NULL,        -- snapshot
    quantity         INT    NOT NULL,
    CONSTRAINT pk_order_items PRIMARY KEY (order_id, menu_item_id),
    CONSTRAINT fk_order_items_order FOREIGN KEY (order_id)
        REFERENCES orders (id) ON DELETE CASCADE,
    CONSTRAINT fk_order_items_menu_item FOREIGN KEY (menu_item_id)
        REFERENCES menu_items (id) ON DELETE RESTRICT,
    CONSTRAINT ck_order_items_qty CHECK (quantity > 0),
    CONSTRAINT ck_order_items_price CHECK (unit_price_paise >= 0)
);
CREATE INDEX idx_order_items_menu_item_id ON order_items (menu_item_id);

CREATE TABLE payments (
    id           BIGINT GENERATED ALWAYS AS IDENTITY,
    order_id     BIGINT NOT NULL,
    method       TEXT   NOT NULL,
    amount_paise BIGINT NOT NULL,
    status       TEXT   NOT NULL DEFAULT 'PENDING',
    gateway_ref  TEXT,                       -- id from the payment gateway
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT pk_payments PRIMARY KEY (id),
    CONSTRAINT fk_payments_order FOREIGN KEY (order_id)
        REFERENCES orders (id) ON DELETE RESTRICT,
    CONSTRAINT uq_payments_gateway_ref UNIQUE (gateway_ref),
    CONSTRAINT ck_payments_method CHECK (method IN ('UPI','CARD','NETBANKING','COD')),
    CONSTRAINT ck_payments_status CHECK (status IN ('PENDING','SUCCESS','FAILED','REFUNDED')),
    CONSTRAINT ck_payments_amount CHECK (amount_paise > 0)
);
CREATE INDEX idx_payments_order_id ON payments (order_id);

Why payments is separate from orders: an order can have several attempts, and payment facts (gateway id, status, refund) change independently of the order. The gateway reference is UNIQUE, which makes a repeated callback (webhook) from the gateway harmless: the second insert fails instead of charging twice.

6. The key queries

The last design step is to run the queries the app needs and check each is simple and can use an index. If a query is awkward, the model may be wrong.

Show a restaurant's menu
SELECT id, name, price_paise / 100.0 AS price_rupees
FROM menu_items
WHERE restaurant_id = 1 AND is_available
ORDER BY name;
 id |     name     | price_rupees
----+--------------+--------------
  2 | Butter Naan  |        40.00
  1 | Paneer Tikka |       220.00
(2 rows)
Place an order, in one transaction
BEGIN;

WITH new_order AS (
    INSERT INTO orders (user_id, restaurant_id, delivery_address, total_paise)
    VALUES (1, 1, '12 MG Road, Pune 411001', 2 * 22000 + 4 * 4000)
    RETURNING id
)
INSERT INTO order_items (order_id, menu_item_id, item_name, unit_price_paise, quantity)
SELECT new_order.id, m.id, m.name, m.price_paise, v.qty
FROM new_order
JOIN (VALUES (1, 2), (2, 4)) AS v(menu_item_id, qty) ON TRUE
JOIN menu_items m ON m.id = v.menu_item_id AND m.restaurant_id = 1 AND m.is_available;

INSERT INTO payments (order_id, method, amount_paise, status, gateway_ref)
VALUES (currval(pg_get_serial_sequence('orders', 'id')), 'UPI', 60000, 'SUCCESS', 'pay_001');

COMMIT;

The service computes the total from the same prices it reads, in one transaction, so the order, its lines and the payment appear together or not at all (transactions are explained in Module 5). In Spring this is a @Transactional method. A real service would read the prices first and compute the total from the rows it inserted; the literal total here only keeps the example short.

A user's order history, newest first
SELECT o.id, r.name AS restaurant, o.status, o.total_paise, o.placed_at
FROM orders o
JOIN restaurants r ON r.id = o.restaurant_id
WHERE o.user_id = 1
ORDER BY o.placed_at DESC
LIMIT 20;
Reports: revenue per restaurant per day, best-selling items
SELECT r.name, o.placed_at::date AS day, COUNT(*) AS orders, SUM(o.total_paise) / 100.0 AS revenue
FROM orders o
JOIN restaurants r ON r.id = o.restaurant_id
WHERE o.status = 'DELIVERED' AND o.placed_at >= now() - INTERVAL '30 days'
GROUP BY r.name, o.placed_at::date
ORDER BY day DESC, revenue DESC;

SELECT oi.item_name, SUM(oi.quantity) AS sold
FROM order_items oi
JOIN orders o ON o.id = oi.order_id
WHERE o.restaurant_id = 1 AND o.status = 'DELIVERED'
GROUP BY oi.item_name
ORDER BY sold DESC
LIMIT 5;
Orders still unpaid, and the live kitchen queue
-- Orders with no successful payment
SELECT o.id, o.total_paise
FROM orders o
WHERE o.status <> 'CANCELLED'
  AND NOT EXISTS (SELECT 1 FROM payments p
                  WHERE p.order_id = o.id AND p.status = 'SUCCESS');

-- Live orders (served by the partial index idx_orders_active)
SELECT id, status FROM orders
WHERE status NOT IN ('DELIVERED','CANCELLED') ORDER BY id;

7. Review checklist

  1. Every table has a primary key and every relationship a named foreign key.
  2. Every foreign key column is indexed (the composite keys cover their first column).
  3. Every column is NOT NULL unless "unknown" is real.
  4. Every rule that data must follow has a CHECK, UNIQUE or foreign key.
  5. Each key query was written and its plan looked at with EXPLAIN (see Module 5).
  6. Denormalized columns have a documented source of truth.

What this design leaves out on purpose

  • Riders and delivery tracking, coupons, taxes and delivery fees, reviews and ratings, menu categories and restaurant opening hours. Each is a new table or two (for example coupons and order_coupons).
  • A status history table (order_status_history) for audit and for the "where is my order" timeline.
  • Soft delete for menu items: here is_available = false does the job, and old orders keep their snapshot.

Mistake: no snapshot of price or address

Joining an old order to the current menu price rewrites history: a ₹220 order becomes ₹250 the day the restaurant changes the menu. Copy what must not change into the order.

Interview angle

"Design the database for a food-delivery app" is a classic. A strong answer: list entities from the requirements, draw the ER diagram, name each relationship's cardinality, implement the many-to-many through order_items with price snapshot, put money in paise, add status CHECKs and foreign key indexes, normalize to 3NF, justify each denormalization, and finish by writing the key queries.

Interview questions — Database design

What are the steps of a database design process?

Collect requirements; find entities (nouns) and attributes; define relationships and their cardinality; draw the ER diagram; choose primary and foreign keys; normalize (usually to 3NF); add constraints and indexes; finally write the key queries and check they are simple and fast. If a needed query is awkward, go back and adjust the model.

How do you implement one-to-one, one-to-many and many-to-many in SQL?

One-to-many: a foreign key on the "many" table. One-to-one: a foreign key with a UNIQUE constraint, or a shared primary key. Many-to-many: a join table with a foreign key to each side, and a composite primary key (or a surrogate key plus a unique pair). Attributes of the relationship, such as quantity, live in the join table.

Candidate key vs primary key vs alternate key vs super key?

A super key is any column set that is unique. A candidate key is a minimal super key. The primary key is the candidate key you choose; the other candidate keys are alternate keys, implemented with UNIQUE. Example: in employees, id, email and pan are candidate keys, id is the primary key, and {id, name} is a super key but not a candidate key.

Surrogate or natural primary key? Why?

Prefer a surrogate key (a generated BIGINT): it never changes, is small, and does not leak personal data into child tables. Keep natural keys (email, SKU) as UNIQUE constraints. Natural keys are fine for tiny stable code tables such as currency INR. The risk with natural keys is that "stable" values change, forcing updates in every referencing table.

BIGINT identity or UUID for a primary key?

BIGINT is 8 bytes, readable, and inserts append at the end of the index. UUIDs are 16 bytes but can be created anywhere and are hard to guess. Random v4 UUIDs scatter inserts and bloat indexes; time-ordered v7 UUIDs fix most of that. A common compromise is a BIGINT primary key plus a public_id UUID for URLs.

What are update, insert and delete anomalies?

They are problems of a table that mixes subjects. Update: the same fact is stored in many rows and some copies change. Insert: you cannot record a restaurant until it has an order. Delete: deleting the last order deletes the only record of the restaurant. Normalization removes them by giving each fact one home.

Explain 1NF, 2NF and 3NF with an example.

1NF: atomic cells, no repeating groups (one row per ordered item). 2NF: no column depends on only part of a composite key (item price moves out of order_lines into menu_items). 3NF: no non-key column depends on another non-key column (customer city moves from orders to customers). Summary phrase: the key, the whole key, and nothing but the key.

What is the difference between 3NF and BCNF?

BCNF requires that for every dependency X → Y, X is a super key. 3NF also accepts it when Y is part of a candidate key. The difference shows only with overlapping composite candidate keys, for example dispatcher → zone in (rider_id, zone, dispatcher). BCNF can lose the ability to enforce a dependency with a plain constraint; 3NF decomposition never does.

When would you denormalize, and how do you keep the data correct?

For measured read problems (reports, counters like average rating) and for history snapshots such as the unit price on an order line. Keep one source of truth and refresh the copy in the same transaction, with a trigger, a materialized view, or a periodic recompute job. Store the sum and count, not the average.

How do you store money and why not FLOAT?

Use NUMERIC(p,s) or integer paise in a BIGINT. Floating point cannot represent values like 0.1 exactly, so sums drift (0.1 + 0.2 gives 0.30000000000000004). Name the unit in the column (amount_paise) and add a currency column if needed.

TIMESTAMP vs TIMESTAMPTZ?

In PostgreSQL, TIMESTAMPTZ stores an exact instant (converted to UTC) and shows it in the session time zone. TIMESTAMP keeps a wall-clock reading with no zone, which is ambiguous across servers and daylight changes. Use TIMESTAMPTZ for events and convert to local time in the UI.

What are the problems with soft delete?

Every query must filter deleted_at IS NULL (use a view or framework support); unique constraints clash with deleted rows (use a partial unique index); cascades do not fire; tables grow; and privacy deletion requests need real removal or anonymising.

Why are polymorphic associations discouraged?

A (target_type, target_id) pair cannot be a foreign key, so the database cannot prevent orphans or cascade deletes. Use one nullable foreign key per target with a CHECK that exactly one is set, or separate tables.

Why does a phone number not belong in an INT column?

It is an identifier, not a quantity: you never add phone numbers, and leading zeros, + and country codes get lost. Store it as text in E.164 form, with a CHECK on the pattern.

Design the tables for a food-delivery app.

Entities: users, addresses, restaurants, menu_items, orders, order_items, payments. Users to orders and restaurants to menu items are one-to-many; orders to menu items is many-to-many through order_items, which carries quantity and the price at order time. Orders to payments is one-to-many (retries). Use surrogate BIGINT keys, paise for money, CHECKs for status, and index every foreign key.

Cheat sheet — Database design

  • Process requirements → entities → attributes → relationships → keys → normalize → constraints and indexes → review queries
  • One-to-many foreign key on the many side; NOT NULL if the parent is mandatory
  • One-to-one foreign key + UNIQUE, or shared primary key
  • Many-to-many join table; composite PK, or surrogate id + UNIQUE (a_id, b_id)
  • Super key any unique column set; candidate key minimal one; primary key the chosen one; alternate key the others
  • Surrogate key generated id (default choice); natural key real-world value, keep as UNIQUE
  • IDs BIGINT GENERATED ALWAYS AS IDENTITY; UUID v7 over v4; public_id for URLs
  • FD A → B means each A has exactly one B; keys decide all columns
  • Anomalies update (many copies), insert (no row for a new fact), delete (lose another fact)
  • 1NF atomic cells, no repeating groups
  • 2NF no dependency on part of a composite key
  • 3NF no transitive dependency; the practical target for OLTP
  • BCNF every determinant is a super key; may lose dependency preservation
  • 4NF split independent multi-valued facts into separate tables
  • Denormalize only after measuring, or for snapshots and counters; keep one source of truth
  • Audit columns created_at, updated_at (NOT NULL, DEFAULT now()), created_by
  • Soft delete deleted_at + partial unique index + view; purge old rows
  • Status text + CHECK, or a lookup table; avoid numeric codes and risky ENUMs
  • Money NUMERIC or paise BIGINT; never FLOAT
  • Time TIMESTAMPTZ in UTC; DATE for dates only
  • JSONB for variable, rarely joined data; GIN index; promote hot keys to columns
  • Trees parent_id + recursive CTE; polymorphic (type,id) is a trap
  • Names snake_case, id, customer_id, fk_orders_customer, uq_users_email, idx_orders_customer_id, is_active
  • Types phone and pincode as text; files as URL or key in the database

Practice — Database design

  1. Draw it. From the sentence "a library lends books to members; a book can have many authors; a loan has a due date" list entities, attributes and cardinalities, and draw the Mermaid erDiagram. Done when every relationship has the right crow's foot symbols and the many-to-many has a join table.
  2. Implement the relationships. Write CREATE TABLE for the library with named constraints: one-to-many (member to loans), many-to-many (books to authors) and a one-to-one (member to library card with UNIQUE). Insert rows and prove that duplicates and orphans are rejected.
  3. Find the keys. For employees(id, email, pan, name) list all super keys of size one and two, the candidate keys, the primary key and the alternate keys. Done when you can explain each choice.
  4. Normalize. Take the wide table order_sheet from the anomalies article, create it with data, demonstrate one update, one insert and one delete anomaly, then normalize step by step to 3NF and show the tables after each step.
  5. BCNF. Create rider_zones, show the redundancy, decompose it into two tables and note which rule can no longer be a single constraint.
  6. Patterns. Add audit columns with an updated_at trigger to a table, then add soft delete with a partial unique index on email. Show that a deleted user's email can be reused.
  7. Roadmap exercise: food delivery. Without looking at the worked design, design tables for users, restaurants, menu items, orders, order items and payments, normalized to 3NF, with an ER diagram. Compare with the article and list the differences. Done when every foreign key is indexed and the price snapshot is explained.
  8. Key queries. Load seed data and write the queries: menu, place order (transaction), order history, revenue per restaurant per day, best sellers, unpaid orders. Done when all six run and you can state which index each uses.
  9. Choose types. Review a table you wrote earlier and fix every wrong type (phone as number, money as float, timestamp without zone). Explain each fix in one sentence.
  10. Review a schema. Take a classmate's or an online sample schema and write a review: missing keys, missing indexes, wrong types, naming problems, normalization problems.

Schema migrations with Flyway and Liquibase

A migration tool keeps the database schema in versioned, reviewed files that run in order and are recorded in a history table; Flyway uses plain SQL files like V1__create_users.sql, Liquibase uses changelogs, and an applied migration must never be edited.

Why migrations

The code lives in Git; the database should too. Without migrations, developers run ad-hoc ALTER TABLE statements by hand, staging and production drift apart, nobody knows which version a database is at, and a new teammate cannot build a working database. A schema migration is a small, ordered, versioned script that moves the schema from one version to the next. The tool:

  • keeps a history table of which migrations ran,
  • runs the missing ones, in order, when the application starts or in the pipeline,
  • checks that already-applied scripts were not changed, and
  • makes every environment (laptop, CI, staging, production) reach the same schema.

Do not use Hibernate's spring.jpa.hibernate.ddl-auto=update for this. It guesses changes, never drops, has no history and no review. In production use validate (or none) and let the migration tool own the schema.

Flyway

Flyway is the simplest tool: migrations are plain SQL files named by a convention. In Spring Boot they live in src/main/resources/db/migration.

src/main/resources/db/migration/
  V1__create_users.sql
  V2__create_restaurants_and_menu_items.sql
  V3__add_orders.sql
  V4__add_users_mobile_index.sql
  R__refresh_reporting_views.sql
V<version>__<description>.sql
A versioned migration: capital V, a version number, two underscores, a description with underscores. Runs exactly once, in version order.
R__<description>.sql
A repeatable migration: no version. It runs again whenever its content (checksum) changes, after all versioned ones. Use it for views, functions and procedures that you recreate.
flyway_schema_history
The table Flyway creates to record every applied migration.
CREATE TABLE users (
    id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email      TEXT NOT NULL,
    name       TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_users_email UNIQUE (email)
);
ALTER TABLE users ADD COLUMN mobile TEXT;
CREATE UNIQUE INDEX uq_users_mobile ON users (mobile);
CREATE OR REPLACE VIEW v_daily_sales AS
SELECT placed_at::date AS day, count(*) AS orders, sum(total_paise) AS revenue_paise
FROM orders
GROUP BY placed_at::date;

The history table after a run:

 installed_rank | version |          description          | success
----------------+---------+-------------------------------+---------
              1 | 1       | create users                  | t
              2 | 2       | create restaurants and menu   | t
              3 | 3       | add orders                    | t
              4 | 4       | add users mobile index        | t
              5 |         | refresh reporting views       | t

The table also stores a checksum of each script. On the next start Flyway recomputes the checksums of already-applied files. If one differs (someone edited a past migration), it stops with an error such as "Migration checksum mismatch for migration version 2", because that database no longer matches what the file says. That is the reason for the iron rule below.

Flyway in Spring Boot

<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<!-- Flyway 10 and later: add the module for your database -->
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
spring:
  flyway:
    enabled: true                         # default when flyway-core is on the classpath
    locations: classpath:db/migration     # default
    baseline-on-migrate: false            # set true only to adopt an existing database
  jpa:
    hibernate:
      ddl-auto: validate                  # Hibernate checks entities against the schema, never changes it

With flyway-core on the classpath, Spring Boot runs pending migrations at start-up, before JPA uses the schema. The version of the Flyway artifacts is managed by Spring Boot's dependency management. See Spring Boot · Module 3 for the data-access setup.

The Flyway command-line tool has the same main commands: migrate (apply pending), info (status of each migration), validate (check checksums), baseline (mark an existing database as a given version, so only later migrations run), repair (fix the history table), and clean (drops everything; never in production, disable it).

Liquibase

Liquibase describes changes in a changelog made of changesets. The file can be XML, YAML, JSON or SQL, and Liquibase can generate SQL for the target database, which helps when you support several databases. Each changeset is identified by id + author + file path, and recorded in the DATABASECHANGELOG table (with a checksum; a lock table DATABASECHANGELOGLOCK prevents two runs at once).

databaseChangeLog:
  - changeSet:
      id: 1-create-users
      author: asha
      changes:
        - createTable:
            tableName: users
            columns:
              - column:
                  name: id
                  type: BIGINT
                  autoIncrement: true
                  constraints: { primaryKey: true, nullable: false }
              - column:
                  name: email
                  type: VARCHAR(255)
                  constraints: { nullable: false, unique: true }
  - changeSet:
      id: 2-add-users-mobile
      author: asha
      changes:
        - addColumn:
            tableName: users
            columns:
              - column: { name: mobile, type: VARCHAR(20) }
      rollback:
        - dropColumn: { tableName: users, columnName: mobile }

Spring Boot looks for classpath:/db/changelog/db.changelog-master.yaml by default when liquibase-core is on the classpath (change it with spring.liquibase.change-log).

Either is fine. Most Spring Boot teams on PostgreSQL pick Flyway for its simplicity. Official docs: Flyway documentation and Liquibase documentation.

The iron rule: never edit an applied migration

Once a migration has run anywhere beyond your own laptop (shared dev, CI, staging, production), it is history. Editing it breaks the checksum and leaves different databases with different schemas. To change something, add a new migration: V5__fix_users_mobile_length.sql. If you made a mistake before pushing, you may delete and redo it locally.

Safe migration practices

On a running system, old and new versions of your application run together for a moment during a deploy, and a long lock on a hot table can take the site down. Follow these habits:

  • Make changes backward compatible. The old code must keep working against the new schema.
  • Add, don't change in place. Adding a nullable column or a new table is safe; renaming or dropping a column the old code uses is not.
  • Watch locks. Many ALTER TABLE forms take a strong lock. Use short lock_timeout; create indexes with CREATE INDEX CONCURRENTLY in PostgreSQL (it cannot run in a transaction, so configure that migration to run outside one).
  • Backfill in batches (thousands of rows per transaction), not one giant UPDATE that locks the table and bloats the log.
  • Test migrations against a copy of production-size data and a real PostgreSQL (Testcontainers), not only H2.
  • Keep each migration small and reviewed like code. Take a backup before risky ones.

Expand, migrate, contract

To change something incompatible, such as renaming users.full_name to name, split it across several releases:

  1. Expand. Add the new column (nullable). Old code is unaffected. 
    ALTER TABLE users ADD COLUMN name TEXT;
  2. Migrate. Deploy code that writes both columns and still reads the old one. Copy existing data in batches, then deploy code that reads the new column. 
    UPDATE users SET name = full_name
WHERE id IN (SELECT id FROM users WHERE name IS NULL LIMIT 10000);
  3. Contract. When no running code uses the old column, drop it in a later release. 
    ALTER TABLE users ALTER COLUMN name SET NOT NULL;
ALTER TABLE users DROP COLUMN full_name;

Each step can be deployed and rolled back independently, with zero downtime. The same pattern covers changing a type, splitting a table or adding a NOT NULL column.

Rule: migrations are append-only and run in the same order everywhere

Never edit or delete an applied migration; never reuse a version number. If two branches create V7, renumber one before merging (Flyway can also be set to allow out-of-order versions, but avoid relying on it).

Mistake: ddl-auto=update in production, and edited migrations

"It worked on my machine" because Hibernate quietly changed a table. Move all schema changes to migrations and use ddl-auto=validate. When a checksum error appears after someone edited an old file, revert the edit and add a new migration; use repair only when you understand why.

Edge cases

  • Adopting Flyway on an existing database: set a baseline (baseline-on-migrate: true or flyway baseline) so existing objects are treated as the starting version.
  • On MySQL, DDL statements commit implicitly, so a failing multi-statement migration can be left half applied. PostgreSQL can roll DDL back with the transaction, which is a real advantage.
  • Seed data for tests belongs in test-only locations (db/testdata), not in the production migration path.

Interview angle

  • Why use Flyway or Liquibase? Versioned, reviewed, repeatable schema changes that reach every environment in order, with a history and checksums.
  • Can you edit an applied migration? No: the checksum fails and environments diverge; add a new one.
  • Versioned vs repeatable migrations? Versioned run once in order; repeatable run again whenever their content changes (views, functions).
  • How do you rename a column without downtime? Expand, migrate, contract over several releases.

Interview questions — Beyond relational

When would you choose NoSQL over a relational database?

When a specific need beats relational strengths: key lookups at huge speed (Redis), flexible nested documents (MongoDB), massive write volumes with a known access pattern (Cassandra), graph traversals (Neo4j) or text search (Elasticsearch). For money, orders and data with relationships and transactions, stay relational. Often the answer is both: relational as the source of truth plus a NoSQL store for one job (polyglot persistence).

What is the difference between ACID and BASE?

ACID: atomic, consistent, isolated, durable transactions. BASE: basically available, soft state, eventually consistent: a looser model for distributed systems that favours availability and scale. BASE systems accept stale reads and conflicting copies that converge later.

Why is Redis so fast, and what is it used for?

Data is held in memory in efficient structures, and commands run on a mostly single-threaded loop with no lock overhead. Typical uses: cache, sessions, rate limiting, leaderboards (sorted sets), counters, simple queues and short-lived locks.

RDB vs AOF persistence in Redis?

RDB writes periodic snapshots: compact and fast to restore, but changes since the last snapshot are lost on a crash. AOF logs every write command: far less data loss (about one second with everysec) but larger and slower to replay. Use both for important data, none for a pure cache.

Explain cache-aside, and how you keep the cache fresh.

The app reads the cache; on a miss it reads the database and stores the result with a TTL. On a write it updates the database and deletes the cache key. TTL is the safety net for missed invalidations. Watch for the stale window and for stampedes on expiry of hot keys (lock, TTL jitter, background refresh).

What is a cache stampede?

A popular key expires and many requests miss at once, all rebuilding it from the database and overloading it. Prevent it with a single-flight lock so one request rebuilds, random TTL jitter, refreshing before expiry, and caching "not found" results briefly.

Embed or reference in MongoDB?

Embed when the data is read together, small and bounded, and owned by the parent (a restaurant's menu). Reference when the data grows without bound, is shared, or is used on its own (a user's orders). Model for how the application reads the data.

Write a MongoDB query for open restaurants in Pune with rating above 4, best first.
db.restaurants.find(
  { city: "Pune", isOpen: true, rating: { $gt: 4 } },
  { name: 1, rating: 1, _id: 0 }
).sort({ rating: -1 })

A compound index on { city: 1, rating: -1 } would support it.

Explain the CAP theorem.

A distributed data store can provide at most two of consistency (every read sees the latest write), availability (every request to a live node gets an answer) and partition tolerance (it keeps working when the network splits). Because partitions happen, the real choice during one is C or A: refuse requests to stay correct (CP), or answer possibly stale data (AP). Without a partition you can have both.

How is consistency in CAP different from consistency in ACID?

In ACID it means a transaction keeps the data valid (constraints and business rules hold). In CAP it means all replicas return the same, up-to-date value. They are different guarantees about different things.

What is eventual consistency and what is PACELC?

Eventual consistency: replicas converge when writes stop, but reads can be stale meanwhile. PACELC extends CAP: if there is a partition choose availability or consistency; else, in normal operation, choose between latency and consistency, because keeping replicas in step costs time.

Replication vs sharding vs partitioning?

Replication copies the same data to more servers for availability and read capacity. Partitioning splits one table into pieces (PostgreSQL range, list or hash partitions) on one server. Sharding puts pieces on different servers to scale writes and storage, using a shard key. Replication does not scale writes; sharding makes joins and transactions across shards hard.

What is replication lag and how do you handle read-your-writes?

With asynchronous replication a replica trails the primary by some time, so a read right after a write may return old data. Read from the primary for a short period after the user's write or on critical pages, and send only staleness-tolerant reads to replicas.

Why do teams use Flyway or Liquibase, and what is the golden rule?

They keep schema changes in versioned files applied in order and tracked in a history table, so every environment has the same schema and changes are reviewed. The rule: never edit a migration that has been applied; add a new one. Release breaking changes as expand, migrate, contract.

Cheat sheet — Beyond relational

  • NoSQL families key-value (Redis, DynamoDB), document (MongoDB), wide-column (Cassandra), graph (Neo4j), search (Elasticsearch)
  • ACID vs BASE strict transactions vs basically available, soft state, eventually consistent
  • Default choice PostgreSQL as source of truth; add a specialised store only for a measured need (polyglot persistence)
  • Redis in-memory, mostly single-threaded, atomic commands; types String, List, Hash, Set, Sorted Set (+ Streams, HyperLogLog, Bitmaps)
  • Redis expiry SET k v EX 60 NX, EXPIRE, TTL (-1 no expiry, -2 missing)
  • Redis persistence RDB snapshots (fast restart, may lose minutes) vs AOF log (less loss, bigger)
  • Eviction maxmemory + allkeys-lru for caches; default noeviction
  • Redis uses cache, sessions, rate limit (INCR + EXPIRE), leaderboard (ZADD), queue, lock (with care)
  • Never KEYS * in production; use SCAN
  • Cache-aside read cache, miss → DB → fill; write DB → delete key
  • Read-through / write-through / write-behind cache loads / writes both sync / writes cache first, DB later (loss risk)
  • Invalidation TTL + delete on write; stampede: lock, jitter, refresh ahead
  • MongoDB database → collection → document (BSON), _id primary key (ObjectId), 16 MB document limit
  • Mongo CRUD insertOne/insertMany, find(filter, projection).sort().limit(), updateOne(filter, {$set,$inc,$push}), deleteOne
  • Mongo operators $gt $gte $lt $in $and $or $exists; dot notation for nested fields
  • Aggregation $match → $group → $sort → $project, $lookup for joins
  • Embed vs reference embed bounded data read together; reference unbounded or shared data
  • CAP during a partition choose C (CP, refuse) or A (AP, maybe stale); P is not optional
  • PACELC partition: A or C; else: latency or consistency
  • ACID C vs CAP C valid data vs same data on all replicas
  • Replication primary writes, replicas read; async = lag and possible loss, sync = safe but slower; not a backup
  • Partitioning PostgreSQL PARTITION BY RANGE | LIST | HASH; pruning; drop old partitions fast
  • Sharding pieces on different servers by shard key; avoid hot spots; cross-shard joins and transactions are hard
  • Flyway V1__name.sql versioned, R__name.sql repeatable, flyway_schema_history, checksums; ddl-auto=validate
  • Migration safety never edit applied migrations; backward compatible; expand → migrate → contract; CREATE INDEX CONCURRENTLY; batch backfills

Practice — Beyond relational

  1. Choose the store. For a food-delivery platform, decide the best store for: orders and payments, restaurant menus shown on a hot page, login sessions, "top 10 riders today", restaurant search with typo tolerance, and rider GPS pings. Write one sentence of reasoning each and name the source of truth.
  2. Redis hands-on. Run Redis in Docker and open redis-cli. Practise one command group for each type: a string with EX, a list queue, a hash cart, a set of likes and a sorted-set leaderboard. Check TTL counts down and the key disappears.
  3. Rate limiter. With INCR and EXPIRE, implement "5 requests per minute per user" in redis-cli, then in a small Spring Boot service using StringRedisTemplate. Done when the sixth request in a minute is rejected and the counter resets by itself.
  4. Cache-aside. Add a Redis cache in front of "get menu by restaurant" in a Spring Boot app (manual code, then @Cacheable). Measure response time with and without the cache, invalidate on update, and log the hit ratio.
  5. Stampede test. Expire a hot key and fire 100 parallel requests. Count database calls, then add a lock or TTL jitter and compare.
  6. MongoDB hands-on. Run MongoDB in Docker and use mongosh: insert 10 restaurants with nested menus, query by city and rating with projection and sort, update with $set/$inc/$push, create a compound index and compare explain("executionStats") before and after.
  7. Aggregation. Write a pipeline that returns the average rating and count of open restaurants per city, sorted best first; then a $lookup from orders to restaurants.
  8. Design decision. Model "users and their orders" in MongoDB twice: with orders embedded and with orders referenced. List when each breaks (document growth, queries by order) and which you would pick.
  9. CAP discussion. For a shopping cart, a bank balance and a "likes" counter, say whether you would choose CP or AP, what a user sees during a partition, and how conflicts are resolved.
  10. Migrations. Add Flyway to a Spring Boot project. Write V1 (users), V2 (orders) and a repeatable view. Set ddl-auto=validate. Then edit V1 on purpose and observe the checksum error; revert it and add V3 instead. Finally, rename a column using expand, migrate, contract in three migrations.

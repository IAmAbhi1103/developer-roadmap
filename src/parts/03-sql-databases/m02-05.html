Interview questions — Intermediate SQL

What is the difference between WHERE and HAVING?

WHERE filters individual rows before grouping and cannot use aggregate functions. HAVING filters groups after GROUP BY and can use aggregates. Example: keep salaries of at least 100000 with WHERE, then keep departments with two or more such people with HAVING COUNT(*) >= 2. Put every condition that does not need an aggregate in WHERE; it is cheaper.

COUNT(*), COUNT(column) and COUNT(DISTINCT column): what is the difference?

COUNT(*) counts rows. COUNT(col) counts rows where col is not NULL. COUNT(DISTINCT col) counts different non-NULL values. In the sample data, COUNT(*) on employees is 12, COUNT(dept_id) is 11 and COUNT(DISTINCT dept_id) is 3.

In which order does SQL evaluate a query?

FROM and JOIN, WHERE, GROUP BY, HAVING, SELECT (expressions, aliases, window functions), DISTINCT, ORDER BY, LIMIT/OFFSET. This is why a select alias cannot be used in WHERE but can be used in ORDER BY, and why HAVING can use aggregates and WHERE cannot.

Explain INNER, LEFT, RIGHT and FULL joins with the employees and departments tables.

Inner returns only employees whose department exists: 11 rows (Meera has no department, Marketing has no employees). Left keeps all employees: 12 rows, Meera with a NULL department. Right keeps all departments: 12 rows, Marketing with a NULL employee. Full keeps both: 13 rows. MySQL has no full join; emulate it with a union of a left and a right join.

Why does a WHERE condition on the right table turn a LEFT JOIN into an INNER JOIN?

The left join first adds unmatched left rows with NULLs in the right table's columns. A later WHERE o.status = 'DELIVERED' is false (unknown) for those NULLs, so the rows are removed again. Put conditions about the optional table in the ON clause, or use WHERE … OR o.id IS NULL when that is what you mean.

How do you find customers who have never placed an order? Give two or three ways.

(1) LEFT JOIN orders … WHERE o.order_id IS NULL. (2) WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id), the safest. (3) WHERE customer_id NOT IN (SELECT customer_id FROM orders), which fails (returns no rows) if the subquery produces a NULL. The answer is Sara Khan and Tanvi Desai.

What happens with NOT IN when the subquery contains a NULL?

It returns no rows. x NOT IN (1, NULL) becomes x <> 1 AND x <> NULL; the second test is unknown, so the whole is never true. Use NOT EXISTS or add WHERE col IS NOT NULL to the subquery.

What is a self join? Show how to list each employee with the manager's name.

A table joined to itself using two aliases. SELECT e.first_name, m.first_name AS manager FROM employees e LEFT JOIN employees m ON m.emp_id = e.manager_id. It must be a left join, otherwise the CEO (no manager) disappears. A self join follows one level only; use a recursive CTE for the whole hierarchy.

What is a correlated subquery, and how is it different from a normal one?

A normal subquery is independent and runs once. A correlated subquery refers to a column of the outer query, so it conceptually runs once per outer row, for example "salary greater than the average salary of the same department". The optimizer may rewrite it into a join; where it cannot, it is slow on big tables, and an aggregate in a derived table or a window function is the faster rewrite.

IN vs EXISTS vs JOIN: which should you use?

For "does a matching row exist", IN and EXISTS give the same result and modern optimizers use the same semi-join plan. EXISTS is clearer for correlated tests and NULL-safe when negated. A JOIN is for when you need columns of the other table, but it multiplies rows when there are several matches (needs DISTINCT or aggregation).

UNION vs UNION ALL?

Both stack two result sets with the same number of compatible columns. UNION removes duplicate rows (an extra sort or hash step); UNION ALL keeps everything and is faster. Use UNION ALL unless you need distinct rows. Joins add columns; unions add rows.

Why must every non-aggregated column in the SELECT list appear in GROUP BY?

The output has one row per group, so each column needs one value per group. A column that is neither grouped nor aggregated has several values, and the database refuses to pick one (PostgreSQL error: "must appear in the GROUP BY clause or be used in an aggregate function"; MySQL with ONLY_FULL_GROUP_BY on, error 1055). Exception: columns functionally dependent on a grouped primary key are allowed in PostgreSQL.

How do you select all orders placed in March 2026 from a timestamp column?

Use a half-open range: WHERE created_at >= '2026-03-01' AND created_at < '2026-04-01'. BETWEEN '2026-03-01' AND '2026-03-31' would stop at midnight at the start of 31 March and lose that day. The range form keeps ranges adjacent and lets an index on the bare column work, unlike EXTRACT(MONTH FROM created_at) = 3.

What does SELECT 7 / 2 return, and how do you get 3.5?

In PostgreSQL both operands are integers, so it is integer division and the answer is 3. Make one side decimal: 7 / 2.0, 7::NUMERIC / 2 or CAST(7 AS NUMERIC) / 2. MySQL returns 3.5000 for / and has DIV for integer division. It matters for percentages: delivered / total * 100 is 0 until you cast.

A join made my SUM too large. Why, and how do you fix it?

A one-to-many join repeats the "one" side once per matching row, so its values are summed several times (employee salaries joined to a table with several project rows per employee). Fix: aggregate before the join in a subquery or CTE, or use EXISTS/IN if you only need to test existence. Check by comparing COUNT(*) with the distinct count of the key.

Cheat sheet — Intermediate SQL

  • Aggregates COUNT, SUM, AVG, MIN, MAX ignore NULL; COUNT(*) counts rows; SUM of nothing is NULL.
  • Count variants COUNT(*) all rows, COUNT(col) non-NULL, COUNT(DISTINCT col) different values.
  • GROUP BY every non-aggregated select column must be grouped; NULLs form one group; add ORDER BY.
  • HAVING filters groups and may use aggregates; WHERE filters rows first and may not.
  • Conditional aggregate SUM(CASE WHEN c THEN 1 ELSE 0 END), or COUNT(*) FILTER (WHERE c) in PostgreSQL.
  • ROLLUP GROUP BY ROLLUP (a) adds subtotal and grand-total rows (MySQL WITH ROLLUP).
  • Logical order FROM, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT.
  • Alias rule select alias is visible in ORDER BY, not in WHERE.
  • INNER JOIN matches only. LEFT all left rows. RIGHT all right rows. FULL both (no FULL in MySQL).
  • LEFT JOIN trap right-table filters go in ON; count COUNT(right.id), not COUNT(*).
  • Anti-join LEFT JOIN … WHERE r.id IS NULL or NOT EXISTS; avoid NOT IN with NULLs.
  • Self join same table, two aliases (e, m); use LEFT so the root stays.
  • CROSS JOIN every pair, |A| × |B| rows; a missing ON does this by accident.
  • USING / NATURAL USING (col) is fine; avoid NATURAL JOIN.
  • Fan-out one-to-many joins repeat the "one" side; aggregate before joining.
  • Subquery shapes scalar (one value), IN (one column), derived table (needs alias), EXISTS (yes/no).
  • Correlated uses an outer column; conceptually runs per outer row.
  • Set operators UNION distinct, UNION ALL keep all, INTERSECT, EXCEPT; same column count and types.
  • CASE first true branch wins; no match and no ELSE gives NULL; works in ORDER BY and aggregates.
  • NULL helpers COALESCE(a, b), NULLIF(a, b); 10 / NULLIF(x, 0) avoids division by zero.
  • Strings ||/CONCAT, LENGTH, UPPER, TRIM, SUBSTRING, POSITION, SPLIT_PART, LPAD; 1-based positions.
  • Dates NOW(), CURRENT_DATE, EXTRACT, DATE_TRUNC, AGE, d + INTERVAL '1 month'; MySQL DATE_FORMAT, DATEDIFF, DATE_ADD.
  • Date ranges col >= start AND col < next_start; never BETWEEN on timestamps; keep the column bare.
  • Time zones store TIMESTAMPTZ; AT TIME ZONE 'Asia/Kolkata' for local days; run servers in UTC.
  • Casting CAST(x AS INT) or x::INT; 7/2 is 3 in PostgreSQL, so cast one side to NUMERIC.

Use the sample database. Write each query first, then check the row count given.

  1. Aggregates. One query that returns the number of employees, the payroll, the highest and lowest salary, and the number of employees with a department. Done when it shows 12, 1645000, 300000, 55000 and 11.
  2. GROUP BY and HAVING. For each department id: headcount, average salary (rounded to 2 decimals) and highest salary; keep only departments with an average above 100000. Then show departments with at least two employees hired after 2020. Explain which parts belong in WHERE and which in HAVING.
  3. Every join type. Join employees and departments with inner, left, right and full joins and record the row counts (11, 12, 12, 13). Then list departments with their employee count, including Marketing with 0, and explain why COUNT(*) would be wrong.
  4. Customer report. For each customer: number of orders and total spent on delivered orders, showing 0 for customers with nothing. Use LEFT JOIN with the status filter in ON. Done when Sara and Tanvi show 0 and Aarav shows 2 delivered orders worth 1908.
  5. Self join. List employees with their manager's name, and a second query with the number of direct reports per manager (Meera 3, Priya 3, Ananya 2, Sunita 2, Vikram 1).
  6. Subqueries. Find employees paid above their department's average in three ways: a correlated subquery, a derived table join, and (after Module 3) a window function. All must return 6 rows. Add the employees who earn more than the company average, and compare.
  7. Anti-joins. Customers who never ordered, products never sold, departments with no employees and employees who are not managers (7 rows). Write each with NOT EXISTS, then show what NOT IN does for the last one.
  8. Sets and CASE. Build one list of all email addresses (employees and customers) with a column saying where each came from; then label each product 'Cheap' under 300, 'Normal' under 1000 and 'Premium' otherwise, and count products per label. Sort orders as PLACED, SHIPPED, DELIVERED, CANCELLED.

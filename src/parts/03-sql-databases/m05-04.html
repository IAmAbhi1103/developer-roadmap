Connection pooling and HikariCP

Opening a database connection is slow and each one costs memory on the server, so applications keep a small pool of open connections and lend them out; Spring Boot uses HikariCP, and a small pool is usually faster than a large one.

Why connections are expensive

Opening a connection to PostgreSQL involves a TCP handshake, usually TLS, authentication, and the server starting a process (PostgreSQL) or thread (MySQL) with its own memory. That can take several milliseconds to tens of milliseconds, more than a typical indexed query. If every web request opened and closed a connection, the database would spend more time connecting than working. And the server can only hold so many: PostgreSQL's max_connections is 100 by default, and each connection uses memory.

How a pool works

  1. At start-up the pool opens a few connections.
  2. A request calls dataSource.getConnection(). If an idle connection exists, it is handed out at once.
  3. If none is idle and the pool is below its maximum, a new connection is opened.
  4. If the pool is at its maximum, the caller waits, up to connectionTimeout, then fails with an exception.
  5. When the code calls connection.close(), the pooled wrapper returns the connection to the pool for reuse; the real connection stays open.

The connection is only busy while a transaction or statement uses it. In Spring a @Transactional method holds one connection for its whole duration, so long transactions mean long borrow times.

HikariCP in Spring Boot

HikariCP is the default pool in Spring Boot (since 2.0): fast, small and well tested. If spring-boot-starter-data-jpa or -jdbc is on the classpath, you already have it. Configure it in application.yml under spring.datasource.hikari:

spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/fooddb
    username: app
    password: ${DB_PASSWORD}
    hikari:
      pool-name: food-pool
      maximum-pool-size: 10        # max connections (default 10)
      minimum-idle: 10             # idle connections kept ready (default = maximum)
      connection-timeout: 30000    # ms to wait for a free connection (default 30 s)
      idle-timeout: 600000         # ms before an extra idle connection is closed (default 10 min)
      max-lifetime: 1800000        # ms before any connection is retired (default 30 min)
      leak-detection-threshold: 20000   # log a warning if borrowed longer than 20 s (default off)
PropertyMeaningSensible value
maximumPoolSizeMost connections the pool will hold, in use plus idle Start at 10; see sizing below
minimumIdleIdle connections to keep ready. HikariCP advises leaving it unset so the pool has a fixed sizeSame as maximum for steady traffic
connectionTimeoutHow long a caller waits for a connection before an exception 2–5 s in an API, so requests fail fast instead of piling up
idleTimeoutIdle time after which extra connections (above minimumIdle) are closed; only matters if minimumIdle is lower than maximumDefault 10 min
maxLifetimeA connection is retired after this age (replaced when idle) A few minutes less than any database or firewall timeout; default 30 min
leakDetectionThresholdLogs a stack trace if a connection stays out too long Enable in dev and staging to catch unclosed connections

maxLifetime exists because a firewall, a load balancer or the database may silently drop connections that live too long. HikariCP retires its own connections just before that, so your code never receives a dead one. Set it shorter than the database's or network's own limit.

Pool sizing: smaller than you think

It is tempting to think "more connections, more speed." The opposite is often true. A database has a limited number of CPU cores and disk operations; beyond that, extra concurrent queries just compete, causing context switching and lock contention. HikariCP's own guidance gives a starting formula for a pool: connections = (core_count × 2) + effective_spindle_count, and notes that a pool around 10 can serve thousands of front-end users. A good rule: start with 10, measure, and raise it only if requests wait for connections while the database is not yet busy.

  • Across instances: total connections = pool size × number of app instances. Ten instances with a pool of 20 need 200 connections: more than the default PostgreSQL max_connections of 100. Keep the sum well under the database limit, leaving room for admin tools, migrations and monitoring.
  • Many instances or serverless: put an external pooler such as PgBouncer in front of PostgreSQL.
  • Keep transactions short. A pool of 10 serves far more users if each borrows a connection for 5 ms than for 500 ms.
  • Do not hold a connection while calling a slow API. A @Transactional method that makes an HTTP call keeps its connection idle but locked.

Pool exhaustion: the symptoms

All connections are in use and new requests wait. After connectionTimeout they fail:

java.sql.SQLTransientConnectionException: food-pool - Connection is not available,
request timed out after 30000ms (total=10, active=10, idle=0, waiting=17)

What you see: requests suddenly slow and then fail with timeouts, CPU low on the app server, many threads parked in HikariPool.getConnection in a thread dump, and waiting greater than 0. Typical causes:

  • A slow query or lock wait that keeps connections busy (the pool is a victim, not the cause).
  • Long transactions, or external calls inside a transaction.
  • A connection leak: code that borrows a connection and never closes it (plain JDBC without try-with-resources).
  • A pool too small for the traffic, or too many instances for the database limit.
  • Open-session-in-view (spring.jpa.open-in-view, on by default in Spring Boot) holding the connection until the HTTP response is written. Many teams turn it off.
try (Connection con = dataSource.getConnection();
     PreparedStatement ps = con.prepareStatement("SELECT name FROM users WHERE id = ?")) {
    ps.setLong(1, 42L);
    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) System.out.println(rs.getString("name"));
    }
}   // close() is called automatically: the connection goes back to the pool

Monitor the pool with Actuator and Micrometer metrics (hikaricp.connections.active, hikaricp.connections.pending, hikaricp.connections.timeout) and alert when pending is above zero for a while. See Spring Boot · Module 6.

Rule: total pool size across all instances must stay below the database's max_connections

Do the multiplication before deploying: instances × maximum-pool-size, plus scheduled jobs, plus admin connections.

Mistake: fixing timeouts by raising the pool size

If connections are exhausted because queries are slow or locked, a bigger pool adds more load to an already struggling database. Find the slow query first (EXPLAIN ANALYZE, slow query log).

Edge cases

  • A pool can hold a connection that the database already closed (restart, failover). HikariCP validates connections on borrow and retires old ones, so you normally only see a few failed requests, then recovery.
  • With Java 21 virtual threads you can have thousands of threads, but the pool is still the limit: a thousand virtual threads still share the same 10 connections.
  • Session state (SET ..., temporary tables, advisory locks) lives on the connection and leaks to the next borrower. Reset it or avoid it.

Interview angle

  • Why use a connection pool? Connections are expensive to open; a pool reuses them and caps load on the database.
  • What is the default pool in Spring Boot and its default size? HikariCP, 10 connections.
  • How big should the pool be? Smaller than you think; start around 10, measure, and keep instances × pool size under max_connections.
  • "Connection is not available, request timed out" - what do you check? Slow queries, long transactions, leaks, pool size versus load, and the thread dump.

The N+1 query problem

N+1 means running one query for N parent rows and then one more query for each parent to load its children (N+1 queries in total); detect it in the SQL log and fix it with a JOIN, an IN-list batch, or JPA fetch joins and entity graphs.

What it is, in SQL terms

You want each restaurant with its menu items. The slow way:

SELECT id, name FROM restaurants WHERE city = 'Pune';           -- 1 query, returns 50 rows

SELECT * FROM menu_items WHERE restaurant_id = 1;               -- then 1 query per restaurant
SELECT * FROM menu_items WHERE restaurant_id = 2;
SELECT * FROM menu_items WHERE restaurant_id = 3;
-- ... 50 times: 51 queries in total

Each query is fast, but 51 round trips to the database add up (network latency plus parsing plus scheduling, per query). With 1,000 restaurants it becomes 1,001 queries for one page. The cost grows with the data, which is why the bug stays hidden in development with 5 rows and appears in production.

How ORMs cause it

With JPA, relationships are loaded lazily by default: restaurant.getMenuItems() looks like a simple getter but runs a query the first time it is called. A loop hides this:

@Entity
public class Restaurant {
    @Id private Long id;
    private String name;
    @OneToMany(mappedBy = "restaurant")           // LAZY by default
    private List<MenuItem> menuItems = new ArrayList<>();
    // getters
}

// Service
List<Restaurant> list = restaurantRepository.findByCity("Pune");     // query 1
for (Restaurant r : list) {
    System.out.println(r.getName() + ": " + r.getMenuItems().size());  // query 2..N+1
}
select r.id, r.name, r.city from restaurants r where r.city=?
select m.id, m.name, m.restaurant_id from menu_items m where m.restaurant_id=?
select m.id, m.name, m.restaurant_id from menu_items m where m.restaurant_id=?
select m.id, m.name, m.restaurant_id from menu_items m where m.restaurant_id=?
... (one more for each restaurant)

It also happens with @ManyToOne set to EAGER (the JPA default for that mapping): loading 100 orders then loads each order's user separately, and when a serializer (Jackson) walks an entity graph and triggers lazy loads. The fix is never "make everything EAGER": that loads too much everywhere.

How to detect it

  • Read the SQL log for the request. Many near-identical queries differing only in an id mean N+1. Enable spring.jpa.show-sql=true or, better, logging.level.org.hibernate.SQL=DEBUG (and bind parameters with org.hibernate.orm.jdbc.bind=TRACE in Hibernate 6).
  • Count queries per request. Hibernate statistics (spring.jpa.properties.hibernate.generate_statistics=true) report the statement count; libraries like datasource-proxy can assert it in tests.
  • Database side: in PostgreSQL pg_stat_statements shows one statement called thousands of times; a slow endpoint with fast individual queries is the typical sign.
  • Tests: write an integration test that asserts "this endpoint runs at most 3 queries".

The fixes

1. A JOIN (one query)

Let the database join the two tables and return everything at once:

SELECT r.id, r.name, m.id AS item_id, m.name AS item_name, m.price_paise
FROM restaurants r
LEFT JOIN menu_items m ON m.restaurant_id = r.id
WHERE r.city = 'Pune'
ORDER BY r.id, m.id;

The result repeats each restaurant's columns on every item row; the app groups them. For a parent with many children and wide columns, this duplication costs bandwidth, which leads to the next option.

2. IN-list batching (two queries)
SELECT id, name FROM restaurants WHERE city = 'Pune';                    -- 50 rows
SELECT * FROM menu_items WHERE restaurant_id IN (1, 2, 3, /* ... */ 50);  -- all children at once

No duplicated parent columns, and the number of queries is constant (2) instead of N+1. Hibernate does this when you set a batch size.

3. JPA: fetch join, entity graph, batch size
public interface RestaurantRepository extends JpaRepository<Restaurant, Long> {

    // (a) JPQL fetch join: one query with a JOIN
    @Query("select distinct r from Restaurant r left join fetch r.menuItems where r.city = :city")
    List<Restaurant> findWithMenuByCity(@Param("city") String city);

    // (b) Entity graph: same idea without writing JPQL
    @EntityGraph(attributePaths = "menuItems")
    List<Restaurant> findByCity(String city);
}
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 50     # lazy collections load 50 parents per IN query

With default_batch_fetch_size the loop above issues ... where restaurant_id in (?, ?, ...) once per 50 restaurants instead of once per restaurant. It is a cheap global safety net that makes N+1 into N/50 + 1. Per association, @BatchSize(size = 50) does the same.

4. Select only what you need (DTO projection)
public record RestaurantItemCount(Long id, String name, long items) {}

@Query("""
    select new com.example.food.RestaurantItemCount(r.id, r.name, count(m))
    from Restaurant r left join r.menuItems m
    where r.city = :city
    group by r.id, r.name
    """)
List<RestaurantItemCount> countItemsByCity(@Param("city") String city);

If a screen needs only counts or a few columns, a projection with GROUP BY is one cheap query and avoids loading entities at all. JPA details are in Spring Boot · Module 3.

Choosing a fix

SituationFix
Need parents with their children on one screenFetch join or @EntityGraph
Several collections on one entityBatch size or separate queries (fetching two lists in one query gives MultipleBagFetchException or a huge row product)
Pagination of parents with childrenPage the parent ids first, then load children with an IN query (a fetch join with Pageable pages in memory and Hibernate warns)
Only counts or a few columnsDTO projection with GROUP BY
Many places, no time to auditdefault_batch_fetch_size as a safety net

Rule: know how many queries a request runs

A page that depends on a list should run a small, fixed number of queries, not a number that grows with the data. Check the SQL log for every new list endpoint.

Mistake: switching everything to EAGER

Wrong: eager everywhere

@OneToMany(mappedBy = "restaurant", fetch = FetchType.EAGER)
private List<MenuItem> menuItems;
// every query for a Restaurant now loads items, even when not needed;
// N+1 can still happen through derived queries

Right: lazy by default, fetch on demand

@OneToMany(mappedBy = "restaurant")           // lazy
private List<MenuItem> menuItems;
// use @EntityGraph or JOIN FETCH in the specific query that needs them

Edge cases

  • LazyInitializationException is the cousin: touching a lazy collection after the transaction or session has closed. Fix by fetching in the query, not by opening the session longer.
  • A fetch join with distinct may still return duplicate parents with older Hibernate versions unless distinct is set; Hibernate 6 de-duplicates entity results automatically.
  • N+1 is not only an ORM problem: a hand-written JDBC loop that queries inside a for loop has the same issue.

Interview angle

  • What is the N+1 problem? One query for N parents plus one per parent for children: N+1 round trips.
  • How do you find it? SQL logging, Hibernate statistics, query-count assertions in tests, pg_stat_statements.
  • How do you fix it? JOIN FETCH or @EntityGraph, batch fetching with an IN list, or a DTO projection; not blanket EAGER.
  • Why does it not show in development? Small data; the number of queries grows with the data size.

Interview questions — How databases work inside

What is an index and how does a B-tree index speed up a query?

An index is a separate sorted structure (usually a B+ tree) of column values with pointers to rows. The tree is wide and shallow, so finding a key reads only 3 or 4 pages: O(log n) instead of reading the whole table. Leaf pages are linked in order, so range scans and sorted output are cheap too.

When does an index hurt?

Every insert, update of an indexed column and delete must also update each index, so writes get slower and storage and cache use grow. On low-selectivity columns or small tables, the planner ignores the index anyway. Keep indexes for queries you have measured, and drop unused ones.

Explain the leftmost-prefix rule.

An index on (a, b, c) is sorted by a, then b, then c. It can serve queries filtering on a; a and b; or a, b and c. It cannot efficiently serve b or c alone, because the entries for one b value are scattered through the index. Put equality columns first and the range or sort column last.

Name reasons why an index may not be used.

A function or arithmetic on the column (lower(email)), a leading wildcard (LIKE '%x'), an implicit cast, low selectivity, a tiny table, OR across columns, wrong column order, and stale statistics. Check with EXPLAIN; fix with an expression index, a trigram index, correct types, a reordered index, or ANALYZE.

What is a covering index?

An index that contains every column the query needs, so the database answers from the index alone without reading the table (an Index Only Scan). In PostgreSQL you add extra columns with INCLUDE.

What is the difference between EXPLAIN and EXPLAIN ANALYZE?

EXPLAIN shows the planned steps and estimated costs without running the query. EXPLAIN ANALYZE runs it and adds actual time, actual rows and loops per node; with BUFFERS it adds page counts. Compare estimated and actual rows to spot stale statistics, and look for Seq Scans that discard many rows.

Explain ACID with an example.

Bank transfer of ₹500: Atomicity - the debit and credit both happen or neither. Consistency - the rules (balance not negative, total unchanged) hold after the transaction. Isolation - other transactions do not see the half-finished state. Durability - once committed, the change survives a crash because the write-ahead log was flushed to disk.

What are dirty, non-repeatable and phantom reads?

Dirty read: reading another transaction's uncommitted change. Non-repeatable read: the same row gives a different value on the second read because another transaction committed a change. Phantom read: the same query returns a different set of rows because another transaction committed an insert or delete.

List the isolation levels and the defaults of PostgreSQL and MySQL.

Read Uncommitted, Read Committed, Repeatable Read, Serializable. PostgreSQL defaults to Read Committed (and treats Read Uncommitted as Read Committed); MySQL InnoDB defaults to Repeatable Read. Higher levels prevent more anomalies but cause more blocking or more serialization failures that must be retried.

What is MVCC?

Multi-version concurrency control: updates create new row versions and keep the old ones, so each transaction reads from a snapshot. Readers do not block writers and writers do not block readers; old versions are removed later (VACUUM in PostgreSQL).

What is a deadlock and how do you prevent it?

Two transactions each hold a lock the other needs. The database detects the cycle and aborts one with an error. Prevent it by taking locks in a consistent order (lowest id first), keeping transactions short, locking all needed rows up front, and retrying the aborted transaction.

Optimistic vs pessimistic locking: which and when?

Pessimistic locks the row first (SELECT ... FOR UPDATE) and makes others wait; use it when conflicts are likely and transactions are short (seat booking, wallet). Optimistic reads freely and checks a version column at update time (@Version in JPA), failing on conflict; use it when conflicts are rare or the user holds the data for a while (editing forms).

Two users buy the last item at the same time. How do you stop overselling?

Make the check and update atomic: UPDATE items SET stock = stock - 1 WHERE id = ? AND stock >= 1 and check that one row was updated. Alternatives: SELECT ... FOR UPDATE first, or a version check with retry. Don't read the stock, subtract in Java and write it back at Read Committed: that is a lost update.

Why use a connection pool, and how do you size it?

Opening connections is slow and the server can hold only a limited number. A pool (HikariCP, default 10) reuses open connections. Keep it small (around 10 to start), because more concurrent queries than the database can run just compete; make sure instances × pool size stays below max_connections. Pool exhaustion shows up as "Connection is not available, request timed out".

What is the N+1 problem and how do you fix it?

One query loads N parent rows and then N more queries load each parent's children, usually from lazy loading inside a loop. Detect it in the SQL log. Fix it with a JOIN FETCH or @EntityGraph, batch loading (default_batch_fetch_size), or a DTO projection, not by making everything EAGER.

Cheat sheet — How databases work inside

  • Page 8 KB (PostgreSQL) / 16 KB (InnoDB) unit of I/O; PostgreSQL heap vs InnoDB clustered table
  • Seq Scan reads all pages, O(n); fine for tiny tables or large fractions
  • B-tree balanced, wide, shallow; lookup O(log n); equality, range, ORDER BY, prefix LIKE
  • Other index types hash (equality), GIN (JSONB, arrays, full-text), GiST, BRIN (huge ordered tables)
  • Index cost slower writes, more disk and cache; drop unused ones (pg_stat_user_indexes)
  • FK indexes PostgreSQL does not create them; InnoDB does
  • Variants unique, partial (WHERE), expression (lower(col)), covering (INCLUDE)
  • Composite (a,b,c) serves a; a,b; a,b,c. Equality first, range last, match ORDER BY
  • Index ignored function or cast on column, LIKE '%x', low selectivity, tiny table, OR, wrong order, stale stats
  • EXPLAIN estimate only; EXPLAIN (ANALYZE, BUFFERS) runs it, shows actual time, rows, loops, pages
  • Plan nodes Seq Scan, Index (Only) Scan, Bitmap Scan, Nested Loop, Hash Join, Merge Join, Sort
  • Estimated vs actual rows far apart means run ANALYZE
  • Transaction BEGIN / COMMIT / ROLLBACK / SAVEPOINT; autocommit = one statement per transaction
  • ACID atomic (all or none), consistent (rules hold), isolated (no half-done reads), durable (WAL flushed at commit)
  • Anomalies dirty read, non-repeatable read, phantom read, lost update, write skew
  • Levels RU, RC (PostgreSQL default), RR (MySQL default), Serializable; RR/Serializable may need retry on SQLSTATE 40001
  • MVCC row versions + snapshots; readers do not block writers
  • Row locks FOR UPDATE, FOR SHARE, NOWAIT, SKIP LOCKED (job queues)
  • Deadlock cycle of waits; lock in consistent order, keep short, retry (40P01)
  • Atomic update SET stock = stock - n WHERE stock >= n beats read-modify-write
  • Optimistic version column / @Version; pessimistic FOR UPDATE / PESSIMISTIC_WRITE
  • HikariCP maximum-pool-size 10, connection-timeout 30 s, max-lifetime 30 min; small pools win
  • Pool math instances × pool size < max_connections (100 default in PostgreSQL)
  • N+1 1 query for parents + N for children; fix with fetch join, @EntityGraph, batch size, projection

Practice — How databases work inside

  1. Roadmap exercise: the index experiment. Build the 1-million-row orders_big table with generate_series from the EXPLAIN article. Time WHERE customer_id = 4242, save the EXPLAIN (ANALYZE, BUFFERS) output, add the index, run ANALYZE, and compare execution time and buffers. Done when you can explain every line of both plans.
  2. Break the index. On the same table try a function on the column, a leading wildcard, and a low-selectivity filter (status). For each, show the plan and apply the fix (expression index, trigram index, partial index) and show the new plan.
  3. Composite index lab. Create an index on (customer_id, status, placed_at). Write six queries that filter on different combinations (a; a,b; b; a,c; ...) and record which ones use the index and how. Reorder the columns and repeat.
  4. Covering index. Make a query return customer_id, placed_at, amount_paise for one customer as an Index Only Scan with INCLUDE. Run VACUUM and check that heap fetches go to zero.
  5. Roadmap exercise: bank transfer. Create accounts, then simulate a transfer with BEGIN, two updates and COMMIT. Repeat with a ROLLBACK and with a failing CHECK. Add a SAVEPOINT to retry one step. Done when balances are always correct.
  6. Roadmap exercise: isolation in action. Open two psql sessions. Reproduce a non-repeatable read at Read Committed, then show it disappears at Repeatable Read. Reproduce the lost update on items.stock, then fix it three ways (atomic update, FOR UPDATE, version column). Try the write-skew rider example at Repeatable Read and at Serializable.
  7. Deadlock. Cause the opposite-order transfer deadlock between two sessions, read the error, then fix it with ordered locking.
  8. Job queue. Create a jobs table with 20 rows. In two sessions run the FOR UPDATE SKIP LOCKED claim query and show each session gets a different job.
  9. Optimistic locking in Spring. Add @Version to an entity, update the same row from two threads or two requests, and show ObjectOptimisticLockingFailureException. Return HTTP 409.
  10. N+1 hunt. In a Spring Boot app with Restaurant and MenuItem, load 50 restaurants and print item counts. Count the queries in the log, then fix it with @EntityGraph and again with default_batch_fetch_size. Write a test that asserts the query count. Also set maximum-pool-size to 2 and run a load of 20 parallel requests to watch the pool time out.

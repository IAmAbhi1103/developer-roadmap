Audit columns and soft delete

Audit columns (created_at, updated_at, created_by) record who changed a row and when; soft delete marks a row as deleted with deleted_at instead of removing it, which brings extra work for uniqueness, queries and privacy.

Audit columns

Almost every business table carries the same small set of columns. They answer support questions ("when did this order change?"), help debugging, and feed incremental data loads.

CREATE TABLE restaurants (
    id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name       TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_by BIGINT REFERENCES users (id),
    updated_by BIGINT REFERENCES users (id)
);

CREATE FUNCTION set_updated_at() RETURNS trigger AS $$
BEGIN
    NEW.updated_at := now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_restaurants_updated_at
BEFORE UPDATE ON restaurants
FOR EACH ROW EXECUTE FUNCTION set_updated_at();

MySQL can do the same in the column itself: updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP. PostgreSQL has no such clause, so use a trigger or set the value in the application. In Spring Data JPA, the annotations @CreatedDate, @LastModifiedDate, @CreatedBy and @LastModifiedBy fill these columns for you when auditing is enabled (Spring Boot · Module 3).

  • created_at never changes after insert. Give it DEFAULT now() and NOT NULL.
  • updated_at changes on each update. Keep it NOT NULL too, starting equal to created_at, so you never have to handle NULL.
  • created_by / updated_by point to the user (or a service account). Many teams skip them on small tables.

Audit columns say when and who, but not what changed. For a full history (compliance, payments), add a separate *_history table filled by a trigger or by the application, or use change data capture. A column updated_at is not a history.

Soft delete

A hard delete runs DELETE and the row is gone. A soft delete keeps the row and marks it:

ALTER TABLE menu_items ADD COLUMN deleted_at TIMESTAMPTZ;   -- NULL means "alive"

-- "Delete"
UPDATE menu_items SET deleted_at = now() WHERE id = 5 AND deleted_at IS NULL;

-- Every normal read must filter
SELECT id, name FROM menu_items WHERE restaurant_id = 3 AND deleted_at IS NULL;

-- Restore
UPDATE menu_items SET deleted_at = NULL WHERE id = 5;

Use deleted_at rather than a boolean is_deleted: it also tells you when. A timestamp is just as easy to filter, and it can be used to purge old rows later.

Soft delete is useful when history must survive (an order that references a deleted menu item), when users may undo, or when you must keep records for legal reasons. But it has real costs:

PitfallWhat happensFix
Forgotten filterOne query without deleted_at IS NULL shows deleted data A view, or Hibernate's @SQLRestriction / @SoftDelete (Hibernate 6.4+)
Unique constraintsA deleted user keeps the email, so a new sign-up with it fails Partial unique index, below
Foreign keysChild rows still point at a "deleted" parentDecide what a deleted parent means for its children
GrowthTables grow forever; indexes carry dead rowsArchive or purge old rows
Privacy law"Delete my data" requests need real removal or anonymisingAnonymise personal columns, or hard-delete after a period
 
CREATE UNIQUE INDEX uq_users_email_live
    ON users (email)
    WHERE deleted_at IS NULL;

-- A view so that application code cannot forget the filter
CREATE VIEW live_menu_items AS
SELECT * FROM menu_items WHERE deleted_at IS NULL;

MySQL has no partial indexes; a common workaround is a unique index on (email, deleted_at), which works only if deleted_at is never NULL for live rows. Some teams store a sentinel date instead. That is one reason to avoid soft delete on tables where hard delete is acceptable.

Convention: soft delete only where you need it

Use it for business records you may need to show or restore (users, products, orders). Do not use it for link rows, sessions or temporary data; delete those for real. Keep the filter in one place (a view or a framework setting).

Mistake: "delete" that cascades into soft-deleted data

A soft delete runs UPDATE, so ON DELETE CASCADE never fires. If a restaurant is soft-deleted, its menu items are still "alive" unless you update them too or filter through the parent. Decide the rule and test it.

Interview angle

  • Soft vs hard delete? Soft keeps the row with a marker (history, undo), but needs filters, partial unique indexes and a purge plan. Hard removes it.
  • Why deleted_at not is_deleted? It records when, and works as the purge-date input.

Status columns, money, timestamps and JSONB

Model a status as a text column with a CHECK (or a lookup table when it needs data), money as NUMERIC or integer paise, time as UTC TIMESTAMPTZ, and use JSONB only for flexible data you do not join on.

Status: text + CHECK, lookup table, or ENUM

An order moves through PLACED, ACCEPTED, PREPARING, OUT_FOR_DELIVERY, DELIVERED or CANCELLED. Three ways to store it:

Text + CHECKLookup table + FKDatabase ENUM
Add a valueAlter the constraintINSERT a rowALTER TYPE … ADD VALUE
Remove or rename a valueAlter the constraint, update rowsUpdate rows and FKHard (PostgreSQL cannot drop a value)
Extra data per status (label, sort order, is_final)NoYesNo
Readable in queriesYesYes with a join, or text keyYes
Works the same in MySQLYes (8.0.16+ enforces CHECK)YesMySQL has its own ENUM syntax
 
-- 1. Text with CHECK: simple, my default for small fixed lists
status TEXT NOT NULL DEFAULT 'PLACED'
    CONSTRAINT ck_orders_status CHECK (status IN
        ('PLACED','ACCEPTED','PREPARING','OUT_FOR_DELIVERY','DELIVERED','CANCELLED'))

-- 2. Lookup table: when statuses carry data or are edited by admins
CREATE TABLE order_statuses (
    code     TEXT PRIMARY KEY,           -- natural key is fine here
    label    TEXT NOT NULL,
    is_final BOOLEAN NOT NULL DEFAULT false
);
status TEXT NOT NULL DEFAULT 'PLACED' REFERENCES order_statuses (code)

-- 3. PostgreSQL ENUM type
CREATE TYPE order_status AS ENUM ('PLACED','ACCEPTED','DELIVERED','CANCELLED');
status order_status NOT NULL DEFAULT 'PLACED'

Rule of thumb: text with CHECK for short fixed lists, a lookup table when the list changes at runtime or has attributes, and avoid ENUM when values may be renamed or removed. Do not store status as a bare number (status = 3): nobody remembers what 3 means. In JPA, use @Enumerated(EnumType.STRING), never ORDINAL, because reordering the Java enum would silently change the meaning of stored data. The legal transitions (PLACED → ACCEPTED, but never DELIVERED → PLACED) are business rules; enforce them in the service, or with a trigger if many writers exist.

Money

Never store money in FLOAT or DOUBLE. Binary floating point cannot represent 0.1 exactly, and errors add up.

SELECT 0.1::double precision + 0.2::double precision AS float_sum,
       0.1::numeric + 0.2::numeric AS numeric_sum;
      float_sum      | numeric_sum
---------------------+-------------
 0.30000000000000004 |         0.3

Two good options:

  • NUMERIC(12,2) (also DECIMAL): exact decimals; 12 digits in total, 2 after the point. Readable, and correct. In Java it maps to BigDecimal.
  • Integer minor units: store paise as BIGINT (₹250.50 is 25050). Fast, exact, no rounding surprises, and it maps to a Java long. Payment gateways like Razorpay also speak in paise. The column name should say so: amount_paise.

Add a CHECK (amount_paise >= 0) where negatives make no sense, and a currency column (CHAR(3), ISO code) when more than one currency is possible. Decide the rounding rule for tax and discounts once, and apply it in one place.

Timestamps: store UTC with TIMESTAMPTZ

In PostgreSQL TIMESTAMPTZ (timestamp with time zone) stores one exact instant, internally in UTC, and shows it in the session's time zone. TIMESTAMP (without time zone) stores a calendar-and-clock reading with no zone, which is ambiguous the moment two servers or two users are in different zones, or when clocks change.

SET TIME ZONE 'Asia/Kolkata';
SELECT TIMESTAMPTZ '2026-11-10 09:00:00+00' AS tz_value;
SET TIME ZONE 'UTC';
SELECT TIMESTAMPTZ '2026-11-10 09:00:00+00' AS tz_value;
        tz_value
------------------------
 2026-11-10 14:30:00+05:30

        tz_value
------------------------
 2026-11-10 09:00:00+00

Same instant, shown in two zones. Use TIMESTAMPTZ for "when did it happen" (created_at, paid_at). Use DATE for a calendar date with no time (date of birth) and TIME sparingly (opening hours). In MySQL, TIMESTAMP is converted to UTC and back, while DATETIME stores the literal value; set the connection and server time zone explicitly. In Java use Instant or OffsetDateTime, and convert to the user's zone only when displaying.

JSONB: flexible data inside a relational table

PostgreSQL's JSONB stores JSON in a binary form that can be indexed and queried. It is useful for data whose shape varies or that you only read as a whole.

CREATE TABLE menu_items (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        TEXT NOT NULL,
    price_paise BIGINT NOT NULL,
    attributes  JSONB NOT NULL DEFAULT '{}'
);
INSERT INTO menu_items (name, price_paise, attributes) VALUES
    ('Paneer Tikka', 22000, '{"spice": "medium", "allergens": ["milk"], "vegetarian": true}');

SELECT name FROM menu_items WHERE attributes @> '{"vegetarian": true}';   -- containment
SELECT name, attributes ->> 'spice' AS spice FROM menu_items;           -- text value

CREATE INDEX idx_menu_items_attributes ON menu_items USING gin (attributes);

Good uses

  • Optional, varying attributes (product specs per category)
  • Raw third-party payloads (a payment gateway response) kept for debugging
  • User preferences and settings

Bad uses

  • Data you join, filter, sort or aggregate on all the time: make real columns
  • Anything needing foreign keys or constraints
  • "I did not want to design the schema"

A good compromise: real columns for the stable core (name, price) and one JSONB column for the long tail. If a JSON key becomes important to queries, promote it to a column. In MySQL the type is JSON, with different functions.

Rule: never use floating point for money, never TIMESTAMP without zone for events

Money is NUMERIC or integer minor units. Events are TIMESTAMPTZ in UTC. Show local time only in the UI.

Mistake: storing status as a free-text string with no constraint

Without a CHECK or lookup, 'Delivered', 'DELIVERED' and 'delivred' all get in, and reports silently miss rows. Constrain it.

Interview angle

  • How do you store money? NUMERIC(p,s) or integer paise; never float; keep currency in a column.
  • TIMESTAMP vs TIMESTAMPTZ? TZ stores an exact instant (UTC internally); plain TIMESTAMP has no zone and is ambiguous.
  • When use JSONB? Flexible, rarely joined data; index with GIN; not for core relational facts.

Hierarchies, polymorphic associations and multi-tenancy

Store a tree with a self-referencing parent_id (adjacency list) and read it with a recursive query; avoid polymorphic (type, id) foreign keys by using one real foreign key per target; and for multi-tenancy put a tenant_id on every table.

Hierarchical data: the adjacency list

Categories, org charts, comment threads and folders are trees. The simplest model is a row that points at its parent:

CREATE TABLE menu_categories (
    id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name      TEXT NOT NULL,
    parent_id BIGINT REFERENCES menu_categories (id),   -- NULL for the root
    CHECK (parent_id <> id)
);
CREATE INDEX idx_menu_categories_parent_id ON menu_categories (parent_id);

INSERT INTO menu_categories (name, parent_id) VALUES
    ('Food', NULL), ('Starters', 1), ('Mains', 1), ('Veg Starters', 2);

-- All descendants of "Food" with their depth
WITH RECURSIVE tree AS (
    SELECT id, name, parent_id, 0 AS depth FROM menu_categories WHERE id = 1
    UNION ALL
    SELECT c.id, c.name, c.parent_id, t.depth + 1
    FROM menu_categories c
    JOIN tree t ON c.parent_id = t.id
)
SELECT repeat('  ', depth) || name AS category, depth FROM tree ORDER BY depth, id;
   category    | depth
---------------+-------
 Food          |     0
   Starters    |     1
   Mains       |     1
     Veg Starters |     2
(4 rows)

Recursive CTEs are covered in Module 3. The adjacency list is simple to insert and move (change one parent_id) and enforces the parent with a foreign key. Reading a whole subtree needs a recursive query, which is fine for modest trees. Alternatives exist for read-heavy trees:

ModelIdeaTrade-off
Adjacency listparent_idSimple writes; subtree needs recursion
Materialized pathStore '/1/2/4/' (or PostgreSQL ltree) Fast subtree with LIKE; moving a node rewrites many paths
Closure tableA table of every (ancestor, descendant, depth) pairFast reads of any relation; more rows and more write work
Nested setsLeft/right numbers per nodeFast subtree reads; very costly inserts

Start with an adjacency list. Move to another model only if recursion measurably hurts. Guard against cycles (A is parent of B and B of A): the recursive query would loop forever, so add a depth limit (WHERE t.depth < 20) or validate in the service.

Polymorphic associations: avoid them

A polymorphic association is one reference that can point to several tables, for example a comment that belongs to either a restaurant or a menu item:

Wrong: type + id, no foreign key possible

CREATE TABLE reviews (
    id          BIGINT PRIMARY KEY,
    target_type TEXT NOT NULL,   -- 'restaurant' or 'menu_item'
    target_id   BIGINT NOT NULL, -- which table? the database cannot check
    stars       INT NOT NULL
);

Right: one nullable FK per target + CHECK

CREATE TABLE reviews (
    id            BIGINT PRIMARY KEY,
    restaurant_id BIGINT REFERENCES restaurants (id),
    menu_item_id  BIGINT REFERENCES menu_items (id),
    stars         INT NOT NULL,
    CHECK (num_nonnulls(restaurant_id, menu_item_id) = 1)  -- exactly one
);

The first design cannot have a real foreign key, so orphan rows appear when targets are deleted, and no cascade works. The second keeps integrity at the cost of one column per target. Other fixes: separate tables (restaurant_reviews, menu_item_reviews), or a common parent table that both targets share a key with. Frameworks such as Rails use type + id (and JPA's @Any exists), but integrity then lives in application code only.

Multi-tenancy in brief

A multi-tenant system serves many customers (tenants), such as many restaurant chains using one SaaS billing product. Three layouts, from cheapest to most isolated:

ModelHowGood forCost
Shared tablestenant_id column on every tableMany small tenants A missing filter leaks data; noisy neighbours
Schema per tenantOne PostgreSQL schema eachDozens to hundreds of tenants Migrations run per schema
Database per tenantSeparate databaseFew large or regulated tenants Most operational work: backups, migrations, connections
 
CREATE TABLE invoices (
    tenant_id  BIGINT NOT NULL REFERENCES tenants (id),
    id         BIGINT GENERATED ALWAYS AS IDENTITY,
    number     TEXT NOT NULL,
    PRIMARY KEY (tenant_id, id),
    CONSTRAINT uq_invoices_number UNIQUE (tenant_id, number)   -- unique per tenant
);
CREATE INDEX idx_invoices_tenant ON invoices (tenant_id, id);

ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;               -- PostgreSQL
CREATE POLICY tenant_isolation ON invoices
    USING (tenant_id = current_setting('app.tenant_id')::bigint);

Put tenant_id first in indexes and unique constraints, and in every query. PostgreSQL row level security makes the database enforce the filter even if a query forgets it.

Convention: prefer real foreign keys over clever generic ones

A foreign key is the cheapest, strongest check you have. Give up generality before giving up a foreign key.

Edge cases

  • A recursive CTE on a cyclic graph never ends on UNION ALL; use UNION or a depth limit.
  • With shared tables, a global UNIQUE (email) is usually wrong: two tenants may both have admin@shop.com.

Interview angle

  • How do you store a category tree? parent_id self-reference, read with a recursive CTE; mention closure table or ltree for heavy reads.
  • Why avoid polymorphic associations? No foreign key, so no integrity or cascade.
  • Multi-tenancy options? Shared table + tenant_id, schema per tenant, database per tenant; pick by tenant count and isolation needs.

Naming conventions

Pick one simple, predictable style (lowercase snake_case, id primary keys, customer_id foreign keys, prefixed constraint and index names), write it down, and apply it everywhere.

Why it matters

Names are the user interface of a schema. A predictable name lets a new developer guess a column, and it makes error messages self-explaining ("violates foreign key constraint fk_orders_customer"). The exact style matters less than being consistent. Module 1 already covered SQL style in SQL style; this is the design side.

    order_id     BIGINT NOT NULL,
    amount_paise BIGINT NOT NULL,
    is_refunded  BOOLEAN NOT NULL DEFAULT false,
    paid_at      TIMESTAMPTZ,
    CONSTRAINT pk_payments PRIMARY KEY (id),
    CONSTRAINT fk_payments_order FOREIGN KEY (order_id) REFERENCES orders (id),
    CONSTRAINT ck_payments_amount CHECK (amount_paise > 0)
);
CREATE INDEX idx_payments_order_id ON payments (order_id);

INSERT INTO payments (order_id, amount_paise) VALUES (1, -5);
-- ERROR:  new row for relation "payments" violates check constraint "ck_payments_amount"

Names to avoid

  • Reserved or risky words: user, order, group, table, desc, end, references. In PostgreSQL user is reserved and needs quotes, which is why you see users and orders (plural) in most schemas. Check the database's keyword list when in doubt.
  • Quoted mixed-case names ("OrderItems"): PostgreSQL folds unquoted names to lowercase, so you would have to quote them forever.
  • Vague names: data, value, type, flag, temp. Say what it is: delivery_instructions.
  • Type or table prefixes: tbl_orders, order_order_date. The type is visible in the schema.
  • Abbreviations nobody knows: cust_nm. Disk is cheap; clarity is not.

Mapping to Java

Spring Boot's default naming strategy maps createdAt in an entity to the column created_at and OrderItem to order_item, so snake_case columns work without extra configuration. If your table is order_items, add @Table(name = "order_items").

Rule: PostgreSQL limits identifiers to 63 bytes

Longer names are cut silently, which can make two long index names collide. Keep index and constraint names short but meaningful. MySQL's limit is 64 characters.

Convention: write the naming rules down

One short page in the repository ("tables plural, ids id, FKs x_id") ends arguments and keeps migrations consistent when ten people add tables.

Interview angle

Interviewers look for consistency and reasons: plural vs singular is a choice; avoiding reserved words, naming FKs after the parent, and naming constraints so errors are readable are the points that show experience.

Choosing data types

Pick the smallest type that is correct for the data and its future: BIGINT ids, NUMERIC or paise for money, TEXT for names and phone numbers, TIMESTAMPTZ for instants, BOOLEAN for flags, and a URL (not the file) for files.

Why not store files in the database?

A 2 MB photo inside a row inflates the table, slows backups and replication, and fills the buffer cache with bytes you rarely query. The database is good at structured data; object storage (S3, Azure Blob) is good at files and serves them cheaply through a CDN. Store the object key or URL, plus metadata (content type, size, checksum), and keep the file elsewhere. A tiny icon (a few KB) in a column is acceptable.

Size and range thinking

  • SMALLINT holds up to 32,767; INT up to about 2.1 billion; BIGINT up to about 9.2 quintillion.
  • Every byte is repeated in each row, each index entry and each foreign key. Shave bytes on huge tables (use SMALLINT for a status code on a billion-row log), not on small ones.
  • Enforce what the type cannot: CHECK (quantity > 0), CHECK (stars BETWEEN 1 AND 5), NOT NULL.

NULL or a default?

Make a column NOT NULL unless "unknown or not applicable" is a real state. A nullable column forces three-valued logic into every query (x = NULL is never true; see NULL logic). Use NULL for "we do not know" (a delivery time not yet set), and a real default for "zero by default" (rating_count INT NOT NULL DEFAULT 0).

Mistake: a phone number or pincode as a number

Wrong

phone   BIGINT,   -- 0 and + lost; 91 prefix ambiguous
pincode INT       -- 011001 becomes 11001

Right

phone   TEXT CHECK (phone ~ '^\+[0-9]{8,15}$'),
pincode CHAR(6) CHECK (pincode ~ '^[0-9]{6}$')

PostgreSQL vs MySQL

MySQL needs a length for VARCHAR(n) and has TINYINT, DATETIME and ENUM; PostgreSQL has real BOOLEAN, TIMESTAMPTZ, UUID, JSONB, arrays and range types. Regex CHECK as shown uses PostgreSQL's ~; MySQL uses REGEXP.

Interview angle

  • Which type for a phone number? Text, in E.164 form; it is an identifier.
  • Where do you keep images? In object storage; the table keeps the URL or key.
  • VARCHAR(255) or TEXT? In PostgreSQL they perform the same; use a length only for a real rule.

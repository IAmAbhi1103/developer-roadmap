What dynamic programming is (and how to spot a DP problem)

Dynamic programming (DP) solves a problem by splitting it into smaller subproblems that repeat, solving each subproblem only once, storing its answer, and building the final answer from the stored answers.

Many interview problems have a simple recursive solution that is far too slow. The recursion keeps solving the same smaller problem again and again. Dynamic programming fixes this with one idea: remember what you already computed. That single change often turns an exponential solution (that would run for hours) into a polynomial one (that runs in milliseconds).

The name is historical. Richard Bellman chose it in the 1950s, and "programming" here means planning with a table, not writing code. A useful way to think about DP is smart brute force: you still consider every choice, but you never solve the same subproblem twice.

The two properties every DP problem has

Overlapping subproblems
The same smaller problem appears many times inside the recursion. Computing fib(5) asks for fib(3) twice and fib(2) three times. If every subproblem were new (the two halves in merge sort never repeat), storing answers would not help — that is plain divide and conquer.
Optimal substructure
The best answer to the big problem is built from the best answers to its subproblems. The cheapest way to reach step 10 is the cheaper of "cheapest way to step 9, then one step" and "cheapest way to step 8, then two steps". A classic counter-example is the longest simple path in a graph: the longest path A→C through B is not always "longest A→B" plus "longest B→C", because those two paths may share vertices.

Words you will see in every DP article

State
The small set of values that describes one subproblem, for example "the first i houses" or "amount a with the first k coins". You store one answer per state.
Transition (recurrence)
The formula that computes a state from smaller states, for example dp[i] = max(dp[i-1], dp[i-2] + nums[i]).
Base case
The smallest states whose answer you know directly, for example dp[0] = 0.
Memoization (top-down)
Keep the recursive solution and add a cache (the memo). Before computing a state, check the memo; after computing it, store it.
Tabulation (bottom-up)
Fill an array (the DP table) with loops, from the base cases up to the final answer, so every value you read is already computed.

How to recognise a DP problem

Look for these signals. Two or three of them together almost always mean DP.

  • The question asks for one number that summarises many possibilities: a minimum or maximum (cost, profit, length), the number of ways, or a yes/no "is it possible".
  • The solution is a sequence of choices: take or skip this item, which coin to use next, where to cut, one step or two steps.
  • Brute force is exponential: trying every subset (2n) or every path.
  • After a choice, the rest of the problem is described by a few numbers: an index, a remaining amount, the previous element. Those numbers are your state.
  • Typical words: "subsequence", "partition", "number of ways", "minimum cost to reach", "longest", "can you reach / form", "at most k transactions".
  • Typical constraints: n up to a few thousand (an O(n²) table is fine), an amount or capacity up to about 104, two strings up to about 1,000 characters each.

It is probably not DP when you must list every solution (all permutations — the output itself is exponential, so use backtracking), when a simple local rule is provably optimal (greedy), or when subproblems never repeat (divide and conquer).

How to think: the path from brute force to DP

  1. Write the brute-force recursion. Give the function one clear meaning, for example minCoins(amount) = fewest coins that make amount.
  2. Look at its parameters. The parameters that change between calls are the state.
  3. Ask: can the same parameters appear twice? Draw a small recursion tree. If yes, you have overlapping subproblems.
  4. Add a memo keyed by the state. You now have a correct top-down DP.
  5. If needed, turn it into a bottom-up table, then shrink the table to a few variables or one row.

Tip: memoized recursion is already a full DP answer

In most interviews a clean memoized solution with the right complexity is accepted. Convert to bottom-up when the interviewer asks for less space, or when the recursion would be too deep (thousands of levels or more).

Mistake: drawing a table before you can say what a cell means

DP is not "make a 2D array and hope". If you cannot finish the sentence "dp[i][j] is the …", stop and define the state first. Every later step — transition, base case, order — depends on that sentence.

Real-world DP

Diff tools compare files by finding a longest common subsequence of lines. Spell checkers and "did you mean" search use edit distance. Sequence alignment in bioinformatics (Needleman–Wunsch), the Viterbi algorithm in speech recognition, the Bellman–Ford shortest-path algorithm and TeX's paragraph line-breaking are all dynamic programming.

Interview angle: "What is DP and how is it different from recursion or greedy?"

  • DP = recursion over subproblems + storing each answer, so each subproblem is solved once.
  • It needs overlapping subproblems and optimal substructure; name both and give a one-line example.
  • Divide and conquer has no overlap; greedy commits to one local choice; DP compares all choices but reuses answers.
  • Complexity of a DP = number of states × work per state.

From recursion to DP in four steps: Fibonacci and climbing stairs

You reach almost every DP solution through the same four steps — plain recursion, memoization (top-down), tabulation (bottom-up) and space optimisation — and the recurrence itself never changes; only the way you store answers does.

The best way to learn DP is to walk one problem through all four steps and watch the complexity fall at each step. Fibonacci is the standard first example because the recurrence is given to you. Climbing Stairs (LeetCode 70) is the same recurrence in disguise, and it shows how you discover a recurrence yourself.

The problem: Fibonacci numbers

The Fibonacci numbers are defined as F(0) = 0, F(1) = 1 and F(n) = F(n-1) + F(n-2): 0, 1, 1, 2, 3, 5, 8, 13, 21, … (LeetCode 509, "Fibonacci Number").

Step 1 — plain recursion

static long fib(int n) {
    if (n <= 1) return n;                  // base cases: fib(0) = 0, fib(1) = 1
    return fib(n - 1) + fib(n - 2);        // the recurrence
}

This is correct and very slow. Each call makes two more calls, so the call tree roughly doubles at every level. The starred calls below are repeated work.

Time: O(2n) (a tighter bound is about 1.618n). fib(40) makes 331,160,281 calls. Space: O(n) for the call stack, because the deepest chain of calls is n long.

Step 2 — memoization (top-down)

Keep the recursion, add a cache. Before you compute fib(n), look in the memo. After you compute it, store it.

import java.util.Arrays;

public class FibMemo {
    static long[] memo;

    static long fib(int n) {
        if (n <= 1) return n;
        if (memo[n] != -1) return memo[n];      // solved before: reuse
        memo[n] = fib(n - 1) + fib(n - 2);      // solve once, store
        return memo[n];
    }

    public static void main(String[] args) {
        int n = 50;
        memo = new long[n + 1];
        Arrays.fill(memo, -1);                  // -1 means "not computed yet"
        System.out.println(fib(n));
    }
}

Each value from 2 to n is now computed exactly once; every other call returns from the memo in O(1). Time: O(n). Space: O(n) for the memo plus O(n) for the call stack.

Step 3 — tabulation (bottom-up)

Notice that the recursion finishes the small values first. So compute them first, in a loop, and you need no recursion at all.

static long fib(int n) {
    if (n <= 1) return n;
    long[] dp = new long[n + 1];            // dp[i] = F(i)
    dp[0] = 0;
    dp[1] = 1;
    for (int i = 2; i <= n; i++) {
        dp[i] = dp[i - 1] + dp[i - 2];      // both values are already filled
    }
    return dp[n];
}

Time: O(n). Space: O(n) for the table, and no stack — so no StackOverflowError for large n.

Step 4 — space optimisation

dp[i] only reads the two previous values. Keep two variables instead of the whole array.

static long fib(int n) {
    if (n <= 1) return n;
    long prev2 = 0, prev1 = 1;              // F(i-2) and F(i-1)
    for (int i = 2; i <= n; i++) {
        long cur = prev1 + prev2;
        prev2 = prev1;                      // slide the window forward
        prev1 = cur;
    }
    return prev1;
}

The same journey on Climbing Stairs (LeetCode 70)

Problem: a staircase has n steps. Each move climbs 1 or 2 steps. In how many distinct ways can you reach the top? For n = 3 the answer is 3: 1+1+1, 1+2, 2+1.

Nobody gives you the recurrence here, so find it with the framework:

  • State: ways(i) = number of ways to stand on step i.
  • Transition: look at the last move. You arrived at step i either with a 1-step from i-1 or a 2-step from i-2. These two groups never overlap, so ways(i) = ways(i-1) + ways(i-2).
  • Base cases: ways(0) = 1 (one way to be at the start: do nothing) and ways(1) = 1.
  • Answer: ways(n). It equals F(n+1) — Fibonacci again.
public class ClimbingStairs {

    // Step 1: plain recursion — O(2^n) time
    static int waysRec(int i) {
        if (i <= 1) return 1;
        return waysRec(i - 1) + waysRec(i - 2);
    }

    // Step 2: memoization — O(n) time, O(n) space.
    // Here every answer is at least 1, so 0 can safely mean "unknown".
    static int waysMemo(int i, int[] memo) {
        if (i <= 1) return 1;
        if (memo[i] != 0) return memo[i];
        memo[i] = waysMemo(i - 1, memo) + waysMemo(i - 2, memo);
        return memo[i];
    }

    // Step 3: tabulation — O(n) time, O(n) space
    static int waysTable(int n) {
        if (n <= 1) return 1;
        int[] dp = new int[n + 1];           // dp[i] = ways to reach step i
        dp[0] = 1;
        dp[1] = 1;
        for (int i = 2; i <= n; i++) dp[i] = dp[i - 1] + dp[i - 2];
        return dp[n];
    }

    // Step 4: O(1) space — the version to submit
    static int climbStairs(int n) {
        int prev2 = 1, prev1 = 1;            // ways(i-2), ways(i-1)
        for (int i = 2; i <= n; i++) {
            int cur = prev1 + prev2;
            prev2 = prev1;
            prev1 = cur;
        }
        return prev1;
    }

    public static void main(String[] args) {
        System.out.println(waysRec(5));
        System.out.println(waysMemo(5, new int[6]));
        System.out.println(waysTable(5));
        System.out.println(climbStairs(45)); // the largest n LeetCode tests
    }
}

Generalisation: if the allowed moves are any steps from a set such as {1, 3, 5}, the transition becomes "sum of ways(i - s) for every allowed step s ≤ i". That is exactly the "count ordered ways to make an amount" pattern you will meet again in coin change.

Rule: check the memo before recursing, store the answer before returning

Both halves matter. Without the check you recompute; without the store the memo stays empty and you are back to O(2n).

Mistake: computing the value but never saving it

Wrong: the memo is read but never written

if (memo[n] != -1) return memo[n];
return fib(n - 1) + fib(n - 2);   // still O(2^n)

Right: store, then return

if (memo[n] != -1) return memo[n];
memo[n] = fib(n - 1) + fib(n - 2);
return memo[n];

Edge cases: n = 0 and overflow

  • An array of size n + 1 with dp[1] = 1 crashes with ArrayIndexOutOfBoundsException when n = 0. Return early for tiny n.
  • F(46) = 1,836,311,903 is the largest Fibonacci number that fits in an int. With int, F(47) silently wraps around and prints -1323752223. With long, the limit is F(92). Beyond that use BigInteger, or the modulo the problem asks for.

Note: Fibonacci in O(log n)

Fibonacci can be computed in O(log n) with fast matrix exponentiation. It is a nice maths trick, but DP interviews care about the four-step journey above, not about this formula.

Interview angle: "Can you do better?"

Interviewers often start with Climbing Stairs or Fibonacci and keep asking "can you do better?". Walk the four steps out loud and state the time and space of each: O(2n) → O(n) time with O(n) space → O(n) time with O(1) space. Mention that the memoized version still uses O(n) stack.

The DP framework: state, transition, base cases, order, answer

Solve any DP problem by answering five questions: what one cell means (state), how it is computed from smaller cells (transition), which cells you know directly (base cases), in which order to fill the cells (iteration order), and which cell holds the final answer.

Every DP solution in this module follows the same five questions. Answer them in a comment before you write code, and the code almost writes itself. Interviewers grade this explanation as much as the code.

The five questions

  1. State. Finish the sentence "dp[i] is the …". Include every value that changes between subproblems: an index, a remaining capacity, the previous choice, a flag such as "holding a stock".
  2. Transition. Ask "what was the last decision?" and express the state through smaller states: dp[i] = min / max / sum over choices of (…).
  3. Base cases. The smallest states with a known answer, plus the value you use for impossible states (infinity for a minimum, minus infinity or 0 for a maximum, 0 for a count, false for a yes/no).
  4. Iteration order. Every state you read must already be computed. Small indices first if dp[i] reads dp[i-1]; large first if it reads dp[i+1].
  5. Answer. Which cell or cells hold the result: dp[n], the maximum over all dp[i], or dp[0][n-1].
  6. (Optional) Space. If a row only reads the previous row, keep one or two rows instead of the full table.

Worked example: Perfect Squares (LeetCode 279)

Problem: given n, return the fewest perfect squares (1, 4, 9, 16, …) that add up to n. For n = 12 the answer is 3 (4 + 4 + 4); for n = 13 it is 2 (4 + 9). Greedy fails here: for 12 it takes 9 first and ends with 9 + 1 + 1 + 1 = four squares.

  1. State: dp[i] = the fewest squares that sum to i.
  2. Transition: the last square used is some j*j ≤ i, so dp[i] = min over j of dp[i - j*j] + 1.
  3. Base case: dp[0] = 0 (zero squares make 0).
  4. Order: i from 1 to n, because i - j*j is always smaller than i.
  5. Answer: dp[n].
import java.util.Arrays;

public class PerfectSquares {
    public static int numSquares(int n) {
        int[] dp = new int[n + 1];                  // dp[i] = fewest squares summing to i
        Arrays.fill(dp, Integer.MAX_VALUE);
        dp[0] = 0;                                  // base case
        for (int i = 1; i <= n; i++) {              // order: small sums first
            for (int j = 1; j * j <= i; j++) {      // choice: the last square j*j
                dp[i] = Math.min(dp[i], dp[i - j * j] + 1);
            }
        }
        return dp[n];                               // the answer
    }

    public static void main(String[] args) {
        System.out.println(numSquares(12));         // 3
        System.out.println(numSquares(13));         // 2
    }
}

The expression dp[i - j * j] + 1 never overflows: because 1 is a square, every smaller value was already set to a real count before it is read.

Complexity: n states × about √n choices each = O(n√n) time, O(n) space.

Choosing the state

Ask: "what do I need to know about the decisions so far to make the remaining decisions?" Only that goes into the state. The number of dimensions equals the number of parameters that change in your recursive brute force.

Choosing the iteration order

Draw an arrow from each cell to the cells it reads. Fill the table so that every arrow points to a cell that is already filled.

  • dp[i] reads dp[i-1], dp[i-2] → loop i upwards.
  • dp[i] reads dp[i+1] (a "suffix" formulation, as in Triangle or Dungeon Game) → loop i downwards.
  • dp[i][j] reads the cells above, left and above-left → rows top to bottom, columns left to right.
  • dp[l][r] reads shorter ranges → loop by range length, or l downwards and r upwards.
  • 1D knapsack → capacity downwards for 0/1 items, upwards for unlimited items (explained in 0/1 knapsack).

static final int UNKNOWN = -1;
static int[] memo;                        // memo[i] = answer for state i

static int solve(int i) {
    if (i == 0) return 0;                 // 1. base cases first
    if (memo[i] != UNKNOWN) return memo[i];
    int best = Integer.MAX_VALUE;         // identity: MAX for min, MIN for max, 0 for counts
    // 2. for each choice c that is valid at state i:
    //        best = Math.min(best, cost(c) + solve(smallerState(i, c)));
    memo[i] = best;                       // 3. store before returning
    return best;
}

The complexity of any DP

Time = number of states × work per state. Space = number of states you store (less after optimisation). Fibonacci: n × O(1). Perfect Squares: n × O(√n). LCS of two strings: (m·n) × O(1). LIS the simple way: n × O(n) = O(n²). Burst Balloons: n² states × O(n) choices = O(n³). Say this formula out loud in interviews — it shows you understand where the cost comes from.

Convention: name the table and document its meaning

Use dp for tables and memo for caches, and put the one-line meaning right above the declaration: // dp[i] = fewest coins to make amount i. For "first i elements" states, size the array n + 1 so dp[0] can stand for the empty prefix — this removes most boundary checks.

Mistake: a state that forgets something important

If two different situations share the same state but need different answers, the state is missing information. In House Robber II (houses in a circle), "best for the first i houses" is not enough, because robbing the last house is only allowed if the first one was skipped. Fix it by adding the missing fact to the state, or by splitting the problem into cases.

Tip: write the recurrence as a comment first

One comment line such as // dp[i] = max(dp[i-1], dp[i-2] + nums[i-1]) gives the interviewer something to agree with before you code, and catches mistakes early.

Interview angle: explain the five answers

A strong DP answer sounds like: "Let dp[i] be …. The last decision is …, so dp[i] = …. The base case is …. I fill i from small to large because …. The answer is dp[n]. There are n states with O(k) work each, so O(n·k) time and O(n) space, which I can reduce to O(1) because each state reads only the previous two."

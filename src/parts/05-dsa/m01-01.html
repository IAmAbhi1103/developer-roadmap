This module is Stage 1 of the DSA roadmap: the foundations. Plan about three months and about 90 problems. You learn how to measure code with Big-O, how to use Java's collections for problem solving, and the first family of techniques that every later topic builds on: basic maths, arrays, strings, hashing, sorting, binary search, recursion and bit manipulation.

All code is in Java. These ideas are not only for interviews. In a real Spring Boot service you count things with a HashMap, sort with a Comparator, binary search a sorted list, and spot the accidental O(n²) loop that makes an API slow. How to approach any DSA problem

Read carefully, let the constraints tell you the target complexity, solve small examples by hand, write the brute force first, then remove the repeated work to find the pattern — and only then code and test the edge cases.

Most wrong answers do not come from a missing trick. They come from rushing: you misread the question, pick an algorithm that is too slow for the input size, or forget the empty array. A fixed routine fixes this. It also makes you calm in interviews, because you always know the next step.

The method below is the one the roadmap asks you to follow for every problem in this module. Use it even for easy problems, so it becomes a habit before the hard ones arrive.

The eight steps

  1. Read the problem twice and restate it. Say it in one sentence in your own words. Write down the input, the output, and what makes an answer valid. In an interview, ask clarifying questions: can the array be empty? Can values be negative? Are there duplicates? Is the input sorted? Do they want indices or values? What if there are many answers?
  2. Read the constraints and set a target complexity. If n ≤ 10^5, an O(n²) solution (1010 steps) will time out, so you need O(n log n) or O(n). The value limits also tell you whether int is enough or you need long. See From constraints to target complexity.
  3. Work examples by hand. Solve the given examples on paper, then invent two or three small ones of your own, including an edge case. If you cannot solve it by hand, you cannot code it.
  4. Write down the brute force. The simplest correct idea, usually "try everything". State its complexity. It is a safe baseline, it often passes small constraints, and it shows you where the wasted work is.
  5. Find the pattern. Ask: what work does the brute force repeat? Which data structure or idea removes it? A HashMap removes repeated searching, a prefix sum removes repeated adding, sorting enables binary search and two pointers. Use the clue table below.
  6. Plan, then code. Write the steps as comments first. Then write clean code with clear names (left, right, windowSum, not a1, t). Small helper methods are fine.
  7. Dry run and test edge cases. Trace your code on one example, line by line, tracking the variables. Then run through the edge-case checklist.
  8. State the complexity and trade-offs. Give time and extra space. Mention what you would change if memory were tight or the input were sorted.

A worked example: Two Sum

Problem: given an array nums and a target, return the indices of two different elements whose sum is target. Exactly one answer exists.

  • Restate: find i != j with nums[i] + nums[j] == target; return [i, j].
  • Constraints: n up to 104. O(n²) is about 108 simple steps — borderline. The follow-up asks for better than O(n²).
  • Brute force: check every pair, O(n²) time, O(1) space.
  • Repeated work: for each nums[i] the inner loop searches the array for target - nums[i]. Searching is the waste. A HashMap of "value → index seen so far" answers "have I seen target - nums[i]?" in O(1) on average.
  • Result: one pass, O(n) time, O(n) space. Full solution and dry run in The two-sum idea.

The edge-case checklist

  • Empty input, one element, two elements.
  • All elements equal; all distinct.
  • Already sorted and reverse sorted input.
  • Zero, negative numbers, the minimum and maximum values (Integer.MIN_VALUE).
  • Overflow: can a sum or product exceed about 2.1 × 109? Then use long.
  • Strings: empty string, spaces, upper and lower case, digits and punctuation.
  • The first and last index — most off-by-one bugs live at the ends.
  • The largest input allowed by the constraints (time limit and recursion depth).

Test like a professional: a stress test

When you are not sure your fast solution is right, write a slow solution that is obviously correct and compare the two on thousands of small random inputs. This is called stress testing. It finds bugs that your hand-made examples miss.

import java.util.Arrays;
import java.util.Random;

public class StressTest {
    // Slow but obviously correct: try every subarray, O(n^2)
    static int brute(int[] a) {
        int best = Integer.MIN_VALUE;
        for (int i = 0; i < a.length; i++) {
            int sum = 0;
            for (int j = i; j < a.length; j++) {
                sum += a[j];
                best = Math.max(best, sum);
            }
        }
        return best;
    }

    // The fast solution we want to trust: Kadane's algorithm, O(n)
    static int fast(int[] a) {
        int best = a[0], cur = a[0];
        for (int i = 1; i < a.length; i++) {
            cur = Math.max(a[i], cur + a[i]);
            best = Math.max(best, cur);
        }
        return best;
    }

    public static void main(String[] args) {
        Random rnd = new Random(42);               // fixed seed = repeatable runs
        for (int test = 0; test < 10_000; test++) {
            int n = 1 + rnd.nextInt(8);            // small sizes expose bugs fastest
            int[] a = new int[n];
            for (int i = 0; i < n; i++) a[i] = rnd.nextInt(21) - 10;   // -10..10
            if (brute(a) != fast(a)) {
                System.out.println("Mismatch for " + Arrays.toString(a));
                return;
            }
        }
        System.out.println("All 10000 random tests passed");
    }
}

Mistake: coding before you know the complexity

You write 40 lines, submit, and get "Time Limit Exceeded". Ten seconds with the constraints would have told you O(n²) cannot pass. Always fix the target complexity in step 2, before you write any code.

Mistake: memorising solutions instead of patterns

If you remember "Two Sum uses a HashMap" but not why (it removes a repeated search), you cannot solve the next problem that needs the same idea in a new form. In your log, always write the pattern and the key trick, not just the problem name.

Tip: say the brute force even when you know the optimal answer

One sentence is enough: "Brute force is checking all pairs, O(n²); we can do O(n) with a HashMap." It proves you understand the problem and gives the interviewer a reason to trust your optimisation.

Interview angle: how you are graded

Interviewers score more than the final code. A strong performance shows, in order:

  • Clarifying questions about input size, edge cases and output format.
  • A brute force with its complexity, then a clear reason for the better approach.
  • Thinking aloud while coding, so the interviewer can follow and help.
  • A dry run on an example and a check of edge cases before saying "done".
  • The final time and space complexity, stated without being asked.

Big-O, Omega and Theta: what complexity measures

Complexity describes how an algorithm's running time or memory grows as the input size n grows, ignoring constant factors — so you can compare algorithms before you run them.

What and why

A stopwatch is a poor way to compare algorithms. The time depends on the machine, the JVM warming up, and the exact input. Time complexity instead counts the number of basic steps an algorithm performs as a function of the input size n. Space complexity does the same for extra memory.

The real question complexity answers is: if the input becomes 10 times bigger, how much slower does my code get? Linear search over 1,000 items needs up to 1,000 comparisons; over 1,000,000 items, up to 1,000,000. Binary search needs about 10 and about 20. That difference — not the exact milliseconds — decides whether your code survives production data or a judge's time limit.

A basic step is anything that takes constant time: an arithmetic operation, a comparison, an array access, an assignment. You do not count every step exactly. You find the step that runs most often and count how many times it runs.

O, Ω and Θ — the three bounds

Big-O — upper bound
f(n) = O(g(n)) if there are constants c > 0 and n0 such that f(n) ≤ c · g(n) for every n ≥ n0. Read it as "f grows no faster than g".
Big-Omega (Ω) — lower bound
f(n) = Ω(g(n)) if f(n) ≥ c · g(n) for every n ≥ n0. "f grows at least as fast as g".
Big-Theta (Θ) — tight bound
f(n) = Θ(g(n)) if it is both O(g(n)) and Ω(g(n)). "f grows exactly like g, up to constants".

Example: an algorithm does f(n) = 3n² + 5n + 2 steps. For every n ≥ 6, 3n² + 5n + 2 ≤ 4n², so f(n) = O(n²) with c = 4. It is also at least 3n², so it is Ω(n²), and therefore Θ(n²). It is also technically O(n³) — true, but a useless, loose bound.

Note: "Big-O" in everyday speech means the tight bound

Engineers and interviewers say "merge sort is O(n log n)" when they mean Θ(n log n). That is normal and fine. Just know the formal difference in case you are asked, and never answer "bubble sort is O(n³)" — true but misleading.

Best, average and worst case — a different question

O, Ω and Θ describe how a function grows. Best, average and worst case describe which inputs you are talking about. They are two separate axes. Linear search finds the target at index 0 in the best case (1 step), at the end or not at all in the worst case (n steps), and in the middle on average (about n/2 steps, still Θ(n)).

Rules for simplifying

  1. Drop constants. O(2n) = O(n), O(n/2) = O(n), O(500) = O(1). Constants depend on the machine; growth does not.
  2. Drop lower-order terms. O(n² + n) = O(n²); O(n + log n) = O(n). For large n the biggest term dominates.
  3. Sequential steps add. A loop over n, then another loop over n: O(n + n) = O(n).
  4. Nested steps multiply. For each of n items, do n work: O(n · n) = O(n²).
  5. Different inputs get different letters. With two arrays of sizes a and b, one pass over each is O(a + b), and comparing every pair is O(a · b). Calling either of them "O(n)" or "O(n²)" is wrong.
  6. The base of a logarithm does not matter. log2 n and log10 n differ only by a constant factor (log2 n ≈ 3.32 · log10 n), so we just write O(log n).
  7. For if/else, take the costlier branch when you want the worst case.
public class SimplifyRules {
    // Rule 3: two sequential loops add up: n + n = 2n, so O(n)
    static int maxMinusMin(int[] a) {
        int max = Integer.MIN_VALUE;
        for (int x : a) max = Math.max(max, x);   // n steps
        int min = Integer.MAX_VALUE;
        for (int x : a) min = Math.min(min, x);   // n more steps
        return max - min;
    }

    // Rules 4 and 5: nested loops over two different inputs multiply: O(a * b)
    static int countEqualPairs(int[] a, int[] b) {
        int count = 0;
        for (int x : a) {             // a.length times
            for (int y : b) {         //   b.length times each
                if (x == y) count++;
            }
        }
        return count;
    }

    public static void main(String[] args) {
        System.out.println(maxMinusMin(new int[]{4, 9, 1, 7}));
        System.out.println(countEqualPairs(new int[]{1, 2, 2}, new int[]{2, 2, 3}));
    }
}

Why constants still matter in practice

Big-O hides constants, but your program still pays them. For small inputs an O(n²) algorithm with tiny steps can beat an O(n log n) one with heavy steps. That is why library sorts switch to insertion sort for very small ranges. In Java, counting lowercase letters with an int[26] is much faster than a HashMap<Character, Integer>, although both are O(n): the map hashes, boxes each char into an object and follows references. Use Big-O to choose the right class of algorithm, then use common sense about constants.

Rule: complexity is about growth, not exact time

Always express complexity in terms of the input sizes (n, m, the length of a string, the number of edges). A statement like "it takes 3 seconds" is a measurement, not a complexity.

Mistake: one letter for two inputs

Merging two sorted arrays of lengths m and n is O(m + n). If you say "O(n)", the interviewer will ask "n of which array?". If one array can be much larger than the other, the difference matters — for example, O(m log n) for binary searching each of m items in an array of n.

Mistake: leaving constants in the final answer

"O(2n + 5)" is not wrong, but it shows you do not know the convention. Simplify to O(n). Keep the constant only when you are comparing two algorithms of the same class in detail.

Interview angle: "What is the difference between O, Ω and Θ?"

  • O is an upper bound, Ω a lower bound, Θ a tight bound (both at once).
  • They are separate from best/average/worst case: quick sort's worst case is Θ(n²) and its average case is Θ(n log n).
  • In practice "Big-O" is used for the tight bound of the worst case.
  • Follow-up "Is O(n) always faster than O(n²)?" — No. For small n the constants can win; Big-O only promises that the O(n) algorithm wins for large enough n.

Analysing loops and hidden costs

To find the complexity of iterative code, count how many times the innermost statement runs: single loops are O(n), nested loops multiply, loops that halve or double are O(log n), and every library call inside a loop brings its own cost.

The method

  1. For each loop, find the range of the loop variable and how it changes (adds, multiplies, halves).
  2. Count the iterations as a formula in n. For dependent loops (the inner range depends on the outer variable), write the sum.
  3. Multiply for nesting, add for loops that run one after another.
  4. Add the cost of each method call inside the loop body — list.contains is not O(1).
  5. Simplify: drop constants and lower-order terms.

The loop patterns you must recognise

// 1. Simple loop: n iterations -> O(n)
for (int i = 0; i < n; i++) { work(); }

// 2. Step of 2 (or any constant): n/2 iterations -> still O(n)
for (int i = 0; i < n; i += 2) { work(); }

// 3. Two nested loops over n: n * n -> O(n^2)
for (int i = 0; i < n; i++)
    for (int j = 0; j < n; j++) { work(); }

// 4. Dependent nested loops (all pairs i < j):
//    (n-1) + (n-2) + ... + 0 = n(n-1)/2 -> O(n^2)
for (int i = 0; i < n; i++)
    for (int j = i + 1; j < n; j++) { work(); }

// 5. Halving: i = n, n/2, n/4, ..., 1 -> about log2(n) + 1 iterations -> O(log n)
for (int i = n; i > 0; i /= 2) { work(); }

// 6. Doubling: i = 1, 2, 4, ... < n -> about log2(n) iterations -> O(log n)
for (int i = 1; i < n; i *= 2) { work(); }

// 7. Linear outer, logarithmic inner -> O(n log n)
for (int i = 0; i < n; i++)
    for (int j = 1; j < n; j *= 2) { work(); }

// 8. Square-root loop: i goes up to sqrt(n) -> O(sqrt n)
for (int i = 1; (long) i * i <= n; i++) { work(); }

// 9. Harmonic: n/1 + n/2 + n/3 + ... + n/n = about n ln n -> O(n log n)
for (int i = 1; i <= n; i++)
    for (int j = i; j <= n; j += i) { work(); }

// 10. Geometric: 1 + 2 + 4 + ... < 2n -> O(n), NOT O(n log n)
for (int i = 1; i < n; i *= 2)
    for (int j = 0; j < i; j++) { work(); }

// 11. Inner loop with a constant bound (e.g. 26 letters): 26n -> O(n)
for (int i = 0; i < n; i++)
    for (int c = 0; c < 26; c++) { work(); }

Do not just trust the formulas — count. This program counts the iterations of several patterns for n = 1,000,000:

public class CountSteps {
    public static void main(String[] args) {
        int n = 1_000_000;
        long single = 0, halving = 0, root = 0, harmonic = 0, geometric = 0;
        for (int i = 0; i < n; i++) single++;
        for (int i = n; i > 0; i /= 2) halving++;
        for (int i = 1; (long) i * i <= n; i++) root++;
        for (int i = 1; i <= n; i++) {
            for (int j = i; j <= n; j += i) harmonic++;
        }
        for (int i = 1; i < n; i *= 2) {
            for (int j = 0; j < i; j++) geometric++;
        }
        int m = 1_000;
        long pairs = 0;
        for (int i = 0; i < m; i++) {
            for (int j = i + 1; j < m; j++) pairs++;
        }
        System.out.println("single loop    : " + single);
        System.out.println("halving loop   : " + halving);
        System.out.println("i * i <= n     : " + root);
        System.out.println("harmonic loops : " + harmonic);
        System.out.println("geometric loops: " + geometric);
        System.out.println("pairs (m=1000) : " + pairs);
    }

The "while inside for" trap — amortized O(n)

Nested-looking code is not always O(n²). What matters is the total number of times the inner statement runs over the whole program. In the code below, j is never reset. It only moves forward, at most n times in total, so the whole thing is O(n). This "each pointer moves at most n times" argument is the heart of two pointers and sliding window (Module 2).

// Counts, for each a[i], how many elements of the sorted array b are smaller.
// Both arrays sorted ascending. Looks nested, but j only moves forward: O(n + m).
static int[] countSmaller(int[] a, int[] b) {
    int[] result = new int[a.length];
    int j = 0;
    for (int i = 0; i < a.length; i++) {
        while (j < b.length && b[j] < a[i]) j++;   // total j++ over the whole run <= m
        result[i] = j;
    }
    return result;
}

A worked example

static long mystery(int[] a) {
    int n = a.length;
    Arrays.sort(a);                           // O(n log n)
    long total = 0;
    for (int i = 0; i < n; i++) {             // n times
        for (int j = 1; j < n; j *= 2) {      //   about log n times each
            total += a[i] % j;
        }
    }
    for (int i = 0; i < n; i++) total += a[i];   // n more steps
    return total;    // O(n log n) + O(n log n) + O(n) = O(n log n)
}

Three parts run one after another, so their costs add. The sort is O(n log n), the nested loop is n · log n, the last loop is n. The biggest term wins: O(n log n) time, and O(1) extra space apart from what the sort uses internally.

Wrong: O(n²) because contains() scans the list

static boolean hasDuplicate(int[] nums) {
    List<Integer> seen = new ArrayList<>();
    for (int x : nums) {
        if (seen.contains(x)) return true;  // O(n) each time
        seen.add(x);
    }
    return false;
}

Right: O(n) with a HashSet

static boolean hasDuplicate(int[] nums) {
    Set<Integer> seen = new HashSet<>();
    for (int x : nums) {
        if (!seen.add(x)) return true;      // O(1) average
    }
    return false;
}

Self-check

for (i = 0; i < n; i++) for (j = 0; j < i * i; j++) work(); — what is the complexity?

The inner loop runs i² times, so the total is 0² + 1² + … + (n−1)², which is about n³/3. The answer is O(n³).

while (n > 1) n = n / 3; — what is the complexity?

n is divided by 3 each time, so the loop runs about log3 n times: O(log n). The base does not matter.

for (i = 2; i < n; i = i * i) work(); — what is the complexity?

i takes the values 2, 4, 16, 256, 65536, … that is 22k. The loop stops when 22k ≥ n, so k ≈ log2 log2 n. The answer is O(log log n) — very slow-growing.

One loop over an array of size n, then a nested loop over a matrix of r rows and c columns. Complexity?

Sequential parts add: O(n + r · c). Keep both terms because they are different inputs and either one can be larger.

Mistake: "two loops means O(n²)"

Two loops one after the other are O(n). A loop nested inside another with a constant bound (26 letters, 4 directions in a grid) is O(n). A while loop whose pointer never resets is O(n) in total. Always count the total work, do not just count the loop keywords.

Tip: write the count first, simplify second

For a dependent loop, first write the exact sum, for example "(n − 1) + (n − 2) + … + 1", then use the table of known sums. Interviewers like to see this step; it shows you are not guessing.

Interview angle: "What is the complexity of this code?"

Expect a snippet with a twist: a halving inner loop, a dependent inner bound, a geometric loop, or a hidden contains/substring. Walk through it aloud: name each loop's iteration count, say whether they add or multiply, include library costs, then simplify. Finish with the space complexity too.

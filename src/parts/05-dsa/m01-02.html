Analysing recursion: recurrences, recursion trees, Master theorem

Write the running time of a recursive function as a recurrence — the work done in one call plus the cost of its recursive calls — then solve it with a recursion tree or, for divide-and-conquer, with the Master theorem.

From code to a recurrence

A recurrence describes the cost T(n) of a problem of size n in terms of the cost of smaller problems. Read it straight off the code:

  • How many recursive calls does one call make? (1 call, 2 calls, n calls…)
  • How big is each smaller problem? (n − 1, n/2, …)
  • How much work does one call do outside the recursive calls? (O(1) for a comparison, O(n) for a merge.)
public class Recurrences {
    // One call on n-1, constant extra work: T(n) = T(n-1) + O(1)  ->  O(n)
    static long factorial(int n) {
        if (n <= 1) return 1;
        return n * factorial(n - 1);
    }

    // One call on half the range: T(n) = T(n/2) + O(1)  ->  O(log n)
    static int search(int[] a, int lo, int hi, int target) {
        if (lo > hi) return -1;
        int mid = lo + (hi - lo) / 2;
        if (a[mid] == target) return mid;
        return a[mid] < target ? search(a, mid + 1, hi, target)
                               : search(a, lo, mid - 1, target);
    }

    // One call on n-1, but O(n) work per call: T(n) = T(n-1) + O(n)  ->  O(n^2)
    static void selectionSortRec(int[] a, int start) {
        if (start >= a.length - 1) return;
        int minIdx = start;
        for (int i = start + 1; i < a.length; i++) {
            if (a[i] < a[minIdx]) minIdx = i;
        }
        int tmp = a[start]; a[start] = a[minIdx]; a[minIdx] = tmp;
        selectionSortRec(a, start + 1);
    }

    // Two calls on n-1 and n-2: T(n) = T(n-1) + T(n-2) + O(1)  ->  O(1.618^n), "O(2^n)"
    static long fib(int n) {
        if (n < 2) return n;
        return fib(n - 1) + fib(n - 2);
    }

    public static void main(String[] args) {
        int[] a = {5, 1, 4, 2, 3};
        selectionSortRec(a, 0);
        System.out.println(factorial(10) + " " + search(a, 0, a.length - 1, 4) + " " + fib(15));
    }
}

Method 1: expand the recurrence

For "subtract" recurrences, unroll a few levels and spot the sum:

  • T(n) = T(n−1) + c → c + c + … (n times) = O(n).
  • T(n) = T(n−1) + n → n + (n−1) + … + 1 = n(n+1)/2 = O(n²).
  • T(n) = 2T(n−1) + c → c(1 + 2 + 4 + … + 2n−1) = c(2n − 1) = O(2n). Tower of Hanoi has exactly this recurrence and needs 2n − 1 moves.
  • T(n) = T(n/2) + c → c added once per halving, log2 n times = O(log n).

Method 2: the recursion tree

Draw each call as a node, with its own (non-recursive) work written inside. Add the work level by level, then add the levels. For merge sort, every level does n work in total and there are about log2 n + 1 levels:

The same picture solves other recurrences quickly:

  • T(n) = 2T(n/2) + c: level work is c, 2c, 4c, … up to n·c at the leaves. It is a geometric series dominated by the last level: O(n). (Example: finding the max of an array by splitting it in halves.)
  • T(n) = T(n/2) + n: level work is n, n/2, n/4, …, which adds to less than 2n: O(n). (Example: quickselect when the pivot is always the median.)

For branching recursion such as Fibonacci, the tree shows both the cost and the waste:

Each call branches into two, and the depth is n, so the tree has at most 2n nodes. The exact number of calls is 2·F(n+1) − 1, which grows like 1.618n (the golden ratio). Count them yourself:

public class FibCalls {
    static long calls = 0;

    static long fib(int n) {
        calls++;
        if (n < 2) return n;
        return fib(n - 1) + fib(n - 2);
    }

    public static void main(String[] args) {
        for (int n : new int[]{10, 20, 30, 40}) {
            calls = 0;
            long value = fib(n);
            System.out.println("fib(" + n + ") = " + value + ", calls = " + calls);
        }
    }
}

Every +10 in n multiplies the work by about 123 (1.61810). Storing each answer the first time you compute it (memoization) turns this into O(n) — that is dynamic programming, covered in Module 3.

A quick rule for branching recursion

If each call makes b recursive calls and the depth is d, the tree has about bd nodes. Total time ≈ number of nodes × work per node:

  • Subsets (pick / not pick each of n items): 2 branches, depth n → 2n leaves; copying each subset costs O(n) → O(n · 2n).
  • Permutations: n choices, then n−1, then n−2… → n! leaves → O(n · n!) with copying.

Method 3: the Master theorem

The Master theorem solves divide-and-conquer recurrences of the form T(n) = a·T(n/b) + f(n), where a ≥ 1 subproblems each have size n/b (b > 1) and f(n) is the work to split and combine. Compare f(n) with n^(log_b a), which is the total work at the leaves:

  1. Leaves dominate. If f(n) grows polynomially slower than nlogb a, then T(n) = Θ(nlogb a).
  2. Balanced. If f(n) = Θ(nlogb a), every level does the same work, so T(n) = Θ(nlogb a · log n).
  3. Root dominates. If f(n) grows polynomially faster than nlogb a (and a·f(n/b) ≤ c·f(n) for some c < 1 — true for normal polynomials), then T(n) = Θ(f(n)).

When the Master theorem does not apply

  • Subtract-type recurrences such as T(n) = T(n−1) + n or T(n) = 2T(n−1) + 1 — the problem shrinks by subtraction, not division. Expand them instead.
  • Unequal splits such as T(n) = T(n/3) + T(2n/3) + n — use the recursion tree (every level does at most n work and there are O(log n) levels, so O(n log n)).
  • Gaps between the cases such as T(n) = 2T(n/2) + n log n — f(n) is bigger than n but not polynomially bigger. The basic theorem is silent; the extended form gives Θ(n log² n).

Space of recursion

Recursion uses memory for the call stack: maximum depth × memory per frame. Factorial is O(n) deep, recursive binary search O(log n), merge sort O(log n) for the stack (plus O(n) for its temporary array). See Space complexity and amortized cost.

Wrong: two identical calls make it O(n)

// T(n) = 2T(n/2) + O(1)  ->  O(n)
static long power(long x, int n) {
    if (n == 0) return 1;
    if (n % 2 == 0) {
        return power(x, n / 2) * power(x, n / 2);
    }
    return x * power(x, n - 1);
}

Right: compute once, reuse — O(log n)

// T(n) = T(n/2) + O(1)  ->  O(log n)
static long power(long x, int n) {
    if (n == 0) return 1;
    long half = power(x, n / 2);
    if (n % 2 == 0) return half * half;
    return half * half * x;
}

Mistake: counting only one branch

"fib calls itself with n−1, so it is O(n)" ignores the second call. Count all recursive calls in the body, and check whether the calls repeat work. Draw two or three levels of the tree when unsure.

Tip: the leaf count of a balanced split

For a recurrence T(n) = a·T(n/b) + …, the tree has logb n levels and alogb n = nlogb a leaves. That single fact is the whole idea behind the Master theorem: compare the leaf work with the root work.

Interview angle: "Why is merge sort O(n log n)?" and "Why is naive Fibonacci exponential?"

  • Merge sort: the array halves at each level, so there are about log n levels; each level merges a total of n elements; n × log n.
  • Fibonacci: each call makes two calls, so the call tree grows like 1.618n; the same subproblems are solved again and again; memoization or a bottom-up loop makes it O(n).
  • Always add the space: merge sort uses O(n) extra memory; naive Fibonacci uses O(n) stack depth.

Space complexity, the call stack and amortized cost

Space complexity counts the extra memory an algorithm needs as n grows, including the recursion call stack; amortized cost is the average cost per operation over any long sequence of operations, which is why ArrayList.add is O(1) even though it sometimes copies the whole array.

Total space vs auxiliary space

Auxiliary space is the extra memory your algorithm allocates beyond the input. Total space includes the input itself. When an interviewer asks "what is the space complexity?", they almost always mean auxiliary space. The memory for the returned answer is usually not counted either — but say so explicitly ("O(1) extra space, not counting the output array").

Things that use space:

  • New arrays and collections: an int[n], a HashMap with up to n entries, a StringBuilder of length n.
  • Copies made by library calls: toCharArray(), substring(), clone(), Arrays.copyOf, new ArrayList<>(list).
  • The call stack: every active recursive call keeps a stack frame with its parameters and local variables until it returns.

Examples

public class SpaceExamples {
    // O(1) extra space: a fixed number of variables, whatever n is
    static long sum(int[] a) {
        long s = 0;
        for (int x : a) s += x;
        return s;
    }

    // O(n) extra space: a new array of size n
    static int[] reversedCopy(int[] a) {
        int[] r = new int[a.length];
        for (int i = 0; i < a.length; i++) r[i] = a[a.length - 1 - i];
        return r;
    }

    // O(1) extra space: reverse in place with two indices
    static void reverseInPlace(int[] a) {
        for (int i = 0, j = a.length - 1; i < j; i++, j--) {
            int t = a[i]; a[i] = a[j]; a[j] = t;
        }
    }

    // O(n) extra space hidden in the call stack: n frames are alive at the deepest point
    static long sumRec(int[] a, int i) {
        if (i == a.length) return 0;
        return a[i] + sumRec(a, i + 1);
    }

    public static void main(String[] args) {
        int[] a = {3, 5, 2};
        reverseInPlace(a);
        System.out.println(sum(a) + " " + sumRec(a, 0) + " "
                + java.util.Arrays.toString(reversedCopy(a)));
    }
}

Memory in real numbers

An int is 4 bytes and a long is 8, so new int[1_000_000] is about 4 MB and new long[1_000_000] about 8 MB. A typical judge allows 256 MB, so int[10^7] (40 MB) is fine but int[10^4][10^4] (108 ints, 400 MB) is not. Collections cost much more per element than primitive arrays: an ArrayList<Integer> stores a reference to a separate Integer object for every value — on a typical 64-bit JVM roughly 16 bytes per object plus 4–8 bytes per reference. Prefer int[] when the size is known.

The time–space trade-off

Many optimisations buy time with memory: Two Sum goes from O(n²) time / O(1) space to O(n) / O(n) with a HashMap; prefix sums answer range sums in O(1) after O(n) extra memory; memoization stores answers to avoid recomputing. Know both sides and say which one you chose and why.

Amortized analysis: why ArrayList.add is O(1)

An ArrayList stores elements in an internal array. When the array is full, add allocates a bigger array (about 1.5 times the old capacity: old + (old >> 1)) and copies every element. That one call is O(n). But resizes happen rarely: capacities go 10, 15, 22, 33, 49, 73, 109, … The copies form a geometric series, so the total copying for n adds is only a small constant times n. Spread over n operations, each add costs O(1) — this is the amortized cost.

public class GrowthSimulation {
    public static void main(String[] args) {
        int n = 1_000_000;
        long capacity = 10, copies = 0;
        int resizes = 0;
        for (long size = 0; size < n; size++) {
            if (size == capacity) {            // array is full
                copies += size;                // copy every element into the new array
                capacity = capacity + (capacity >> 1);   // grow by 50%
                resizes++;
            }
        }
        System.out.println("adds           = " + n);
        System.out.println("resizes        = " + resizes);
        System.out.println("element copies = " + copies);
        System.out.printf("copies per add = %.2f%n", (double) copies / n);
    }
}
adds           = 1000000
resizes        = 29
element copies = 2430972
copies per add = 2.43

A million adds cause only 29 resizes and about 2.4 copies per add on average — a constant, so O(1) amortized. With growth factor 1.5 the copies are bounded by n · (1 + 2/3 + 4/9 + …) = 3n.

Amortized is not the same as average case

Average case averages over random inputs and can be unlucky. Amortized is a guarantee: for any sequence of n operations, the total cost is at most n × (amortized cost). Other amortized-O(1) operations: StringBuilder.append, ArrayDeque push and offer, HashMap.put (it rehashes everything when the size passes capacity × 0.75), and pointers that only move forward.

Tip: pre-size when you know the final size

new ArrayList<>(n) and new StringBuilder(n) skip the resizes completely. For a HashMap that will hold n entries, the capacity must be about n / 0.75 to avoid rehashing.

Java 19+: HashMap.newHashMap(n)

Since Java 19, HashMap.newHashMap(int numMappings) and HashSet.newHashSet(int) create a map or set sized for that many entries, doing the load-factor maths for you. On Java 17 use new HashMap<>((int) (n / 0.75f) + 1).

Mistake: forgetting the call stack

"My recursive solution uses no extra space" is wrong if the recursion goes n levels deep — that is O(n) space, and for n around 105 it can even crash with StackOverflowError. Always state the recursion depth as part of the space complexity.

Interview angle: "Is ArrayList.add O(1)?"

  • Appending at the end is O(1) amortized; a single add that triggers a resize is O(n).
  • The array grows by about 50%, so resizes are rare and total copying is O(n) for n adds.
  • add(index, x) in the middle is O(n) because it shifts elements — always.
  • Related: "space of recursive binary search?" — O(log n) for the stack; the iterative version is O(1).

From constraints to target complexity

A judge runs roughly 10^7 to 10^8 simple operations per second, so the input limits tell you which complexity will pass: n ≤ 20 allows 2^n, n ≤ 5,000 allows n², and n up to 10^6 needs n log n or n.

The rule of thumb

Most judges give 1–2 seconds per test. Java, once the JIT compiler has warmed up, handles somewhere around 107–108 simple operations (additions, comparisons, array accesses) per second. So plug the maximum constraint into your complexity: if the result is up to about 108, it will probably pass; if it is 1010, it will not. Treat this as an estimate — heavy objects, HashMap boxing and cache misses make the real constant larger.

Constraints tell you more than speed

  • Overflow: the maximum possible sum is n × max|value|. With n = 105 and values up to 109, the sum can reach 1014, far above Integer.MAX_VALUE (about 2.1 × 109) — use long. Products of two values up to 109 need long too.
  • Data structure choice: values in [0, 10^6] fit an array index, so a count array beats a HashMap. Values up to 109 or negative values need a HashMap (or sorting).
  • Recursion depth: recursion 105 levels deep may overflow the default stack. Prefer iteration, or see Recursion vs iteration.
  • Multiple test cases: on Codeforces-style judges, a line like "the sum of n over all test cases does not exceed 2 · 105" means your complexity is judged on the total n, so O(n log n) per test is fine — but resetting a 106-sized array for each of 104 tests is not.
  • Memory: a 256 MB limit allows about 6 × 107 ints in total.

Rule: always plug the maximum constraint into your complexity

Before coding, compute the worst-case operation count with the largest n (and the largest values). If it is clearly above 108, you need a better algorithm, not micro-optimisations.

Tip: constraints are the biggest hint in the problem

Setters choose limits so that the intended solution passes and slower ones fail. "n ≤ 20" is practically a sign saying "use bitmasks or subsets". "n ≤ 105, values ≤ 109" says "sort or hash, and use long for sums". A huge n like 1018 says "a formula or a logarithmic algorithm".

Mistake: ignoring the value constraints

Your algorithm is O(n) and correct on the samples, but fails on hidden tests because int sum overflowed at 1014. Read the value ranges as carefully as the size ranges.

Interview angle: constraints are often not given

In an interview, ask: "How large can n get? Can values be negative or very large? Does it fit in memory?" Then say your target out loud: "With n up to a million, I'm aiming for O(n log n) or better." It shows you think like an engineer who designs for real data sizes — the same skill you use when an endpoint must handle a million rows.

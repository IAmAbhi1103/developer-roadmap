Greedy: the greedy-choice property and when it fails

A greedy algorithm repeatedly takes the choice that looks best right now and never reconsiders it; it is correct only when the problem has the greedy-choice property, which you justify with an exchange argument, and it is wrong for problems like coin change with coins {1, 3, 4}.

Backtracking tries every choice. A greedy algorithm tries only one: the choice that looks best at this moment, by a fixed rule. It commits to that choice and never looks back. When it works, greedy is wonderful: usually a sort followed by one pass, O(n log n) time and O(1) extra space. The whole difficulty is knowing when it works. A greedy rule that looks natural is often wrong, so in an interview you must be able to defend the rule.

Two properties that make greedy correct

Greedy-choice property
There is an optimal solution that contains your greedy first choice. In other words, making the locally best choice never rules out a globally best answer.
Optimal substructure
After you make that choice, what is left is a smaller problem of the same kind, and an optimal solution to it combined with your choice is optimal for the whole problem. (Dynamic programming needs this property too.)

The exchange argument, in simple words

The exchange argument is the standard way to prove a greedy rule. Take any optimal solution that does not use your greedy choice. Show that you can swap one of its choices for the greedy choice without making the solution worse. So there is an optimal solution that uses the greedy choice. Repeat for the smaller problem that remains, and by induction the greedy algorithm builds an optimal solution.

Example — activity selection. You have meetings with start and end times and one room; you want the maximum number of non-overlapping meetings. Greedy rule: always pick the meeting that ends first. Proof sketch: take any optimal schedule and look at its first meeting X. Let G be the meeting that ends earliest overall, so G ends no later than X. Replace X with G. G ends no later than X ended, so G cannot clash with the second meeting of the schedule. The schedule has the same number of meetings, so it is still optimal — and now it starts with G. Repeat for the rest of the day.

When greedy fails

The classic counter-example is coin change (minimum number of coins for an amount). With Indian coins {1, 2, 5, 10, 20, 50, 100, 200, 500}, "take the biggest coin that fits" happens to be optimal. With coins {1, 3, 4} and amount 6 it is not:

MethodCoins usedCount
Greedy (largest first)4 + 1 + 13
Optimal3 + 32

The greedy choice "take 4" looks best now but locks you out of 3 + 3. The exchange argument breaks here: you cannot swap a 4 for something without changing the total. For arbitrary coins you need dynamic programming (minimum coins for each amount). Other well-known failures: 0/1 knapsack (you cannot split an item; fractional knapsack is greedy-solvable), shortest path with negative edges, and longest path problems.

import java.util.Arrays;

public class GreedyCoinsFail {
    static int greedy(int[] coins, int amount) {       // coins sorted ascending
        int count = 0;
        for (int i = coins.length - 1; i >= 0; i--) {
            count += amount / coins[i];
            amount %= coins[i];
        }
        return amount == 0 ? count : -1;
    }

    static int dp(int[] coins, int amount) {           // correct for any coins
        int[] best = new int[amount + 1];
        Arrays.fill(best, Integer.MAX_VALUE);
        best[0] = 0;
        for (int a = 1; a <= amount; a++) {
            for (int c : coins) {
                if (c <= a && best[a - c] != Integer.MAX_VALUE) {
                    best[a] = Math.min(best[a], best[a - c] + 1);
                }
            }
        }
        return best[amount] == Integer.MAX_VALUE ? -1 : best[amount];
    }

    public static void main(String[] args) {
        int[] coins = {1, 3, 4};
        System.out.println("greedy: " + greedy(coins, 6));   // 3 (4 + 1 + 1)
        System.out.println("dp:     " + dp(coins, 6));       // 2 (3 + 3)
    }
}
greedy: 3
dp:     2

How to recognise a greedy problem

  • The goal is a maximum or minimum count/cost, and a sorted order seems to matter (by end time, by ratio, by size).
  • Intervals, scheduling, "minimum number of …", "can you reach …", "assign … to …".
  • The constraints are large (n up to 105 or 106), so backtracking is impossible and an O(n log n) or O(n) solution is expected.
  • You can find a quick argument ("if I did anything else I could swap it for this") — and you cannot find a small counter-example.

A template: sort, then sweep

Most greedy solutions look like this. The sort key is the whole idea of the algorithm.

Arrays.sort(items, comparatorThatEncodesTheGreedyRule);  // O(n log n)
State state = initialState();
for (Item item : items) {                                  // one pass, O(n)
    if (canTake(state, item)) {
        take(state, item);                                 // commit; never undone
    }
}
return answerFrom(state);

How to think

  1. Guess a rule: sort by end, by ratio, by deadline, by start. Try two or three.
  2. Try to break each guess with a tiny example (3–4 items). One counter-example kills the rule.
  3. If a rule survives, explain it with an exchange argument in one or two sentences.
  4. If every rule fails and the choices overlap in sub-answers, switch to dynamic programming.
  5. Write the code, then test ties and the smallest inputs (one item, equal values).

Two easy examples

Assign Cookies (LeetCode 455)

Child i is content with a cookie of size at least g[i]; cookie j has size s[j]; each child gets at most one cookie. Maximise content children. Rule: give each cookie, smallest first, to the least greedy child it can satisfy. Why: a small cookie that fits a child is no use to a hungrier one, and giving a big cookie to a small child wastes it (exchange argument).

import java.util.Arrays;

public class AssignCookies {
    public static int findContentChildren(int[] g, int[] s) {
        Arrays.sort(g);
        Arrays.sort(s);
        int child = 0;                                   // least greedy unsatisfied child
        for (int cookie = 0; cookie < s.length && child < g.length; cookie++) {
            if (s[cookie] >= g[child]) child++;          // this cookie satisfies the child
        }
        return child;
    }

    public static void main(String[] args) {
        System.out.println(findContentChildren(new int[]{1, 2, 3}, new int[]{1, 1})); // 1
        System.out.println(findContentChildren(new int[]{1, 2}, new int[]{1, 2, 3})); // 2
    }
}

Complexity: O(n log n + m log m) for the sorts, one linear pass, O(1) extra space (ignoring the sort).

Fractional Knapsack

Items have a value and a weight; the bag holds capacity W; you may take fractions of an item. Maximise total value. Rule: sort by value per kg, highest first; take whole items while they fit, then a fraction of the next one. The exchange argument is easy: if a lower-ratio item is in the bag while a higher-ratio item is not full, swapping some weight to the better item increases the value. If items cannot be split (0/1 knapsack), the same rule fails and you need DP.

import java.util.Arrays;

public class FractionalKnapsack {
    // items[i] = {value, weight}
    public static double maxValue(int[][] items, int capacity) {
        Arrays.sort(items, (a, b) ->
            Double.compare((double) b[0] / b[1], (double) a[0] / a[1]));  // best ratio first
        double total = 0;
        int room = capacity;
        for (int[] it : items) {
            if (room == 0) break;
            int take = Math.min(it[1], room);            // whole item, or what still fits
            total += (double) it[0] * take / it[1];
            room -= take;
        }
        return total;
    }

    public static void main(String[] args) {
        int[][] items = {{60, 10}, {100, 20}, {120, 30}};
        System.out.println(maxValue(items, 50));          // 240.0
    }
}

Ratios are 6, 5 and 4. Take all of items 1 and 2 (weight 30, value 160); 20 kg remain, so take 20/30 of item 3 (value 80); total 240. Complexity: O(n log n) time, O(1) extra space.

Huffman coding (idea only)

Huffman coding compresses text by giving frequent characters short bit codes and rare characters long ones, with no code being the prefix of another. The greedy rule: repeatedly take the two least frequent nodes, merge them into a parent whose frequency is their sum, and put it back. A PriorityQueue makes each step O(log n), so building the code tree costs O(n log n). The merged tree gives each character a code by reading left = 0, right = 1 from the root. The same "merge the two smallest" loop solves Minimum cost to connect sticks:

PriorityQueue<Integer> pq = new PriorityQueue<>();
for (int s : sticks) pq.add(s);
int cost = 0;
while (pq.size() > 1) {
    int sum = pq.poll() + pq.poll();   // always merge the two cheapest
    cost += sum;
    pq.add(sum);
}
return cost;                           // O(n log n)

Mistake: trusting a rule that passes the sample

A greedy rule that matches the examples in the problem statement can still be wrong. Always test it on a small tricky case you invent, or run a brute force on random tiny inputs. For "activity selection", sorting by start time or by duration both pass many samples and both are wrong.

Mistake: comparator subtraction can overflow

Wrong: a[1] - b[1] overflows for large values

Arrays.sort(intervals, (a, b) -> a[1] - b[1]);

Right: Integer.compare is always safe

Arrays.sort(intervals, (a, b) -> Integer.compare(a[1], b[1]));

Exceptions: when a sort key needs a tie-breaker

If two items tie on the main key, the order between them may matter. Example: sorting meetings by end time, ties are harmless; but sorting people for "Queue Reconstruction by Height" needs height descending and then position ascending. When the result depends on ties, state the second key out loud.

Interview angle

"Why is greedy correct here?" is the real question. A strong answer: state the rule, give a two-sentence exchange argument, name a case where the obvious rule fails (coin change with {1, 3, 4}), and give the complexity (dominated by the sort). If you cannot prove it, say what you tested. Then mention that the dynamic-programming alternative exists and costs more.

Greedy on intervals: activity selection, arrows, partitions, platforms

Interval problems are usually greedy with a sort: sort by end time to keep the most intervals, sweep once, and compare each start with the end you currently hold; partition labels and minimum platforms use the same sort-and-sweep idea.

You met the interval basics (merge, insert, meeting rooms) in Module 2. This article covers the greedy interval family. The central rule is: sort by end time. The interval that ends first leaves the most room for the rest, which is exactly the exchange argument from the previous article.

Problem 1 — Activity selection / Non-overlapping Intervals (LeetCode 435)

Activity selection: given activities with start and end times, choose the maximum number that do not overlap. Non-overlapping Intervals asks the mirror question: the minimum number of intervals to remove so that the rest do not overlap. The answer is n − (maximum kept). Intervals that only touch ([1,2] and [2,3]) do not overlap.

import java.util.Arrays;

public class NonOverlappingIntervals {
    public static int eraseOverlapIntervals(int[][] intervals) {
        if (intervals.length == 0) return 0;
        Arrays.sort(intervals, (a, b) -> Integer.compare(a[1], b[1]));  // by END time
        int kept = 1;
        int lastEnd = intervals[0][1];                // end of the last interval we kept
        for (int i = 1; i < intervals.length; i++) {
            if (intervals[i][0] >= lastEnd) {         // starts after (or when) the last ended
                kept++;
                lastEnd = intervals[i][1];
            }                                         // else: overlaps, drop it (it ends later)
        }
        return intervals.length - kept;
    }

    public static void main(String[] args) {
        int[][] a = {{1, 2}, {2, 3}, {3, 4}, {1, 3}};
        System.out.println(eraseOverlapIntervals(a)); // 1
    }
}

Dry run for [[1,2],[2,3],[3,4],[1,3]]: sorted by end → [1,2], [2,3], [1,3], [3,4] (ties in any order). Keep [1,2] (lastEnd 2). [2,3] starts at 2 ≥ 2 → keep, lastEnd 3. [1,3] starts at 1 < 3 → drop. [3,4] starts at 3 ≥ 3 → keep. Kept 3, removed 1.

Why sort by end and not start? With [1,100], [2,3], [4,5], sorting by start picks the long interval first and keeps 1; sorting by end keeps 2. Complexity: O(n log n) time (sort), O(1) extra space (O(log n) for the sort).

Problem 2 — Minimum Number of Arrows to Burst Balloons (LeetCode 452)

Each balloon is a horizontal segment [xStart, xEnd]. An arrow shot straight up at x bursts every balloon with xStart ≤ x ≤ xEnd. Find the fewest arrows. This is the same problem in disguise: find the minimum number of points that stab all intervals. Sort by end; shoot at the end of the first balloon; every balloon whose start is ≤ that x is also burst; the first balloon that starts after x needs a new arrow.

import java.util.Arrays;

public class MinArrows {
    public static int findMinArrowShots(int[][] points) {
        if (points.length == 0) return 0;
        Arrays.sort(points, (a, b) -> Integer.compare(a[1], b[1]));   // by END
        int arrows = 1;
        int arrowX = points[0][1];                   // shoot at the first balloon's end
        for (int i = 1; i < points.length; i++) {
            if (points[i][0] > arrowX) {             // this balloon starts after the arrow
                arrows++;
                arrowX = points[i][1];
            }                                        // else: already burst by the current arrow
        }
        return arrows;
    }

    public static void main(String[] args) {
        int[][] p = {{10, 16}, {2, 8}, {1, 6}, {7, 12}};
        System.out.println(findMinArrowShots(p));    // 2
    }
}

Sorted by end: [1,6], [2,8], [7,12], [10,16]. Arrow at 6 bursts the first two; [7,12] starts at 7 > 6, so a second arrow at 12 bursts the last two. Answer 2. Note the comparison is >, not >=: balloons that touch at one point are burst by the same arrow. In Problem 1 the comparison is >=, because touching intervals do not overlap. This one-character difference is the classic trap. Complexity: O(n log n) time, O(1) extra space.

Problem 3 — Partition Labels (LeetCode 763)

Cut a string into as many parts as possible so that each letter appears in at most one part. Return the part sizes. For "ababcbacadefegdehijhklij" the answer is [9, 7, 8].

Idea. Record the last index of every letter. Sweep from left to right while keeping end, the farthest last-occurrence of any letter seen in the current part. When the index i reaches end, no letter of this part appears later, so cut here. Each part is as short as possible, so the number of parts is the maximum.

import java.util.ArrayList;
import java.util.List;

public class PartitionLabels {
    public static List<Integer> partitionLabels(String s) {
        int[] last = new int[26];
        for (int i = 0; i < s.length(); i++) last[s.charAt(i) - 'a'] = i;

        List<Integer> sizes = new ArrayList<>();
        int partStart = 0, end = 0;
        for (int i = 0; i < s.length(); i++) {
            end = Math.max(end, last[s.charAt(i) - 'a']);   // extend to cover this letter
            if (i == end) {                                  // everything seen ends here
                sizes.add(end - partStart + 1);
                partStart = i + 1;
            }
        }
        return sizes;
    }

    public static void main(String[] args) {
        System.out.println(partitionLabels("ababcbacadefegdehijhklij"));
    }
}
[9, 7, 8]

The first part: a last appears at 8, so end is at least 8; b at 5, c at 7. At i = 8 the part closes with size 9. Complexity: O(n) time, O(1) space (26 letters).

Problem 4 — Minimum Platforms (classic, GeeksforGeeks style)

Given arrival and departure times of trains at a station, find the minimum number of platforms so that no train waits. (Same as Meeting Rooms II.) Sort arrivals and departures separately, then sweep both lists like a merge: each arrival before the next departure needs one more platform; each departure frees one. The answer is the maximum number of platforms in use at any moment.

import java.util.Arrays;

public class MinPlatforms {
    public static int minPlatforms(int[] arr, int[] dep) {
        int[] a = arr.clone(), d = dep.clone();
        Arrays.sort(a);
        Arrays.sort(d);
        int i = 0, j = 0, inUse = 0, best = 0;
        while (i < a.length) {
            if (a[i] <= d[j]) {          // next event is an arrival (a train at the same time
                inUse++;                 // as a departure still needs its own platform)
                best = Math.max(best, inUse);
                i++;
            } else {                     // next event is a departure
                inUse--;
                j++;
            }
        }
        return best;
    }

    public static void main(String[] args) {
        int[] arr = {900, 940, 950, 1100, 1500, 1800};
        int[] dep = {910, 1200, 1120, 1130, 1900, 2000};
        System.out.println(minPlatforms(arr, dep));   // 3
    }
}

Between 11:00 and 11:20 the trains arriving at 9:40, 9:50 and 11:00 are all still present (their departures are at 12:00, 11:20 and 11:30), so three platforms are needed. Complexity: O(n log n) time, O(1) extra space apart from the clones. A PriorityQueue of departure times gives the same bound.

Mistake: mixing up > and >= between similar problems

Decide first whether touching at a single point counts as overlap. Meeting rooms and intervals ("[1,2] and [2,3] do not clash") use >= to keep; arrows ("balloons touching at x = 6 are burst together") use > to start a new group. Write the sentence in a comment before the comparison.

Edge cases

  • Empty input: return 0 before touching intervals[0], or you get ArrayIndexOutOfBoundsException.
  • Identical intervals count as overlapping (each is kept at most once).
  • Values near Integer.MIN_VALUE or MAX_VALUE: never subtract in the comparator; use Integer.compare.

Real-project usage

Booking systems (IRCTC, hotel or hospital slots), calendar apps and job schedulers use exactly these sweeps: "how many rooms/platforms/servers are busy at once?" and "which requests can run on one machine?". The cluster-wide version uses a priority queue of end times.

Interview angle

Say "sort by end time" and immediately explain why with a tiny counter-example. Know that Non-overlapping Intervals, Minimum Arrows and Activity Selection are the same idea (answers: n − kept, number of groups, kept). Complexity is O(n log n) from the sort; the sweep is O(n).

Jump Game, Gas Station and Candy

Some greedy problems need no sort at all: track the farthest index you can reach (Jump Game I and II), reset the starting point whenever the tank goes negative (Gas Station), and fix constraints with two passes (Candy).

These problems are solved with a single pass and a few variables. They look like dynamic programming at first, and a quick brute force (try all jump sizes) is exponential, but a running "best so far" value is enough. The skill is to define that value correctly.

Problem 1 — Jump Game (LeetCode 55)

You stand at index 0. nums[i] is the maximum jump length from index i. Can you reach the last index? For [2, 3, 1, 1, 4] yes; for [3, 2, 1, 0, 4] no, because every path ends at index 3 whose value is 0.

Idea. Keep farthest, the largest index reachable using the cells seen so far. At each index i, if i > farthest, index i cannot be reached at all, so the answer is false. Otherwise update farthest = max(farthest, i + nums[i]). Everything up to farthest is reachable because you can always make a shorter jump.

public class JumpGame {
    public static boolean canJump(int[] nums) {
        int farthest = 0;                              // largest reachable index so far
        for (int i = 0; i < nums.length; i++) {
            if (i > farthest) return false;            // a gap we can never cross
            farthest = Math.max(farthest, i + nums[i]);
            if (farthest >= nums.length - 1) return true;   // early exit
        }
        return true;
    }

    public static void main(String[] args) {
        System.out.println(canJump(new int[]{2, 3, 1, 1, 4}));   // true
        System.out.println(canJump(new int[]{3, 2, 1, 0, 4}));   // false
    }
}

Dry run on [3, 2, 1, 0, 4]: i=0 → farthest 3; i=1 → 3; i=2 → 3; i=3 → 3 (value 0 adds nothing); i=4 → 4 > 3 → false. Complexity: O(n) time, O(1) space.

Problem 2 — Jump Game II (LeetCode 45)

Now the last index is guaranteed reachable; find the minimum number of jumps. For [2, 3, 1, 1, 4] the answer is 2 (0 → 1 → 4).

Idea — implicit BFS. Think of levels. Level k is the set of indices reachable with exactly k jumps. curEnd is the right edge of the current level; farthest is the farthest index reachable from anything in the current level (the edge of the next level). When the scan reaches curEnd, you must make one more jump to continue, so increment jumps and move curEnd = farthest. This is breadth-first search on an array, without a queue.

public class JumpGameII {
    public static int jump(int[] nums) {
        int jumps = 0;
        int curEnd = 0;          // right edge of the current level (reachable with 'jumps' jumps)
        int farthest = 0;        // right edge of the next level
        for (int i = 0; i < nums.length - 1; i++) {     // do not process the last index
            farthest = Math.max(farthest, i + nums[i]);
            if (i == curEnd) {                           // must jump to go further
                jumps++;
                curEnd = farthest;
            }
        }
        return jumps;
    }

    public static void main(String[] args) {
        System.out.println(jump(new int[]{2, 3, 1, 1, 4}));   // 2
        System.out.println(jump(new int[]{2, 3, 0, 1, 4}));   // 2
    }
}

Dry run on [2, 3, 1, 1, 4]: i=0 → farthest 2, i == curEnd (0) → jumps 1, curEnd 2. i=1 → farthest 4. i=2 → farthest 4, i == curEnd → jumps 2, curEnd 4. The loop ends at i=3. Answer 2. Complexity: O(n) time, O(1) space. The loop stops at n − 2 on purpose: if it processed the last index it could count one extra jump when curEnd equals n − 1. For n == 1 the loop does not run and the answer is 0.

Problem 3 — Gas Station (LeetCode 134)

There are n stations on a circle. gas[i] is the fuel you get at station i; cost[i] is the fuel needed to drive to station i + 1. Starting with an empty tank, return the index from which you can complete the full circle clockwise, or −1 if impossible. The answer is unique if it exists.

Idea. Two facts. (1) If the total gas is less than the total cost, no start works. (2) Otherwise a start exists. Scan once with a running tank. If the tank becomes negative at station i, then no station between the current start and i can be the start either (each of them reached i with a non-negative tank in a feasible run, which is no better than starting at it with zero), so set the start to i + 1 and reset the tank. The candidate left at the end is the answer.

public class GasStation {
    public static int canCompleteCircuit(int[] gas, int[] cost) {
        int total = 0;        // total surplus over the whole circle
        int tank = 0;         // surplus since the current candidate start
        int start = 0;
        for (int i = 0; i < gas.length; i++) {
            int diff = gas[i] - cost[i];
            total += diff;
            tank += diff;
            if (tank < 0) {            // cannot get from 'start' to i + 1
                start = i + 1;         // the next station is the new candidate
                tank = 0;
            }
        }
        return total >= 0 ? start : -1;
    }

    public static void main(String[] args) {
        int[] gas = {1, 2, 3, 4, 5};
        int[] cost = {3, 4, 5, 1, 2};
        System.out.println(canCompleteCircuit(gas, cost));   // 3
    }
}

Dry run: differences are [-2, -2, -2, 3, 3]. i=0: tank −2 < 0 → start 1. i=1: −2 → start 2. i=2: −2 → start 3. i=3: tank 3. i=4: tank 6. Total is 0 ≥ 0, so the answer is 3. Complexity: O(n) time, O(1) space. The brute force that tries each start is O(n²).

Problem 4 — Candy (LeetCode 135), briefly

Children stand in a line with ratings. Each child gets at least one candy, and a child with a higher rating than a neighbour must get more candy than that neighbour. Find the minimum total candy.

Idea. Two simple passes, each fixing one side. Left to right: if rating[i] > rating[i - 1], then candy[i] = candy[i - 1] + 1. Right to left: if rating[i] > rating[i + 1], then candy[i] = max(candy[i], candy[i + 1] + 1). The max keeps the left-side promise. Sum the array.

import java.util.Arrays;

public class Candy {
    public static int candy(int[] ratings) {
        int n = ratings.length;
        int[] c = new int[n];
        Arrays.fill(c, 1);                                   // everyone gets at least one
        for (int i = 1; i < n; i++) {                        // satisfy the left neighbour
            if (ratings[i] > ratings[i - 1]) c[i] = c[i - 1] + 1;
        }
        for (int i = n - 2; i >= 0; i--) {                   // satisfy the right neighbour
            if (ratings[i] > ratings[i + 1]) c[i] = Math.max(c[i], c[i + 1] + 1);
        }
        int total = 0;
        for (int x : c) total += x;
        return total;
    }

    public static void main(String[] args) {
        System.out.println(candy(new int[]{1, 0, 2}));   // 5  (2 + 1 + 2)
        System.out.println(candy(new int[]{1, 2, 2}));   // 4  (1 + 2 + 1)
    }
}

Complexity: O(n) time, O(n) space (an O(1)-space slope-counting version exists but is rarely required). The pattern "one pass per constraint direction" also solves Trapping Rain Water with prefix maxima and Product of Array Except Self.

Mistake: Gas Station forgetting the total check

Without total >= 0 the loop returns some index even when the circuit is impossible (for example gas = [2], cost = [3] returns 1, outside the array). The reset trick finds the only possible start; the total test confirms that it works.

Edge cases

  • Jump Game with [0] → true (you are already at the last index); with [0, 1] → false.
  • Jump Game II with a single element → 0 jumps.
  • Gas Station with one station: valid iff gas[0] >= cost[0].
  • Candy with equal ratings: neighbours with equal ratings have no constraint, so each may get 1.

Tip: greedy or DP for Jump Game?

The DP version ("canReach[i] is true if some earlier reachable j can jump to i") is O(n²) and hits time limits at n = 104. The greedy version works because reachability is a prefix: if index i is reachable, all smaller indices are too. When you can state such a structural fact, greedy follows.

Interview angle

Interviewers like Gas Station because the brute force is easy and the O(n) idea needs a proof. Say it in two sentences: "if the total is non-negative a solution exists; if I run out of gas at i starting from s, every station in between would run out too, so the new start is i + 1." For Jump Game II, say "it is BFS where each level is a range, so no queue is needed". Both show you can see the structure rather than memorise code.

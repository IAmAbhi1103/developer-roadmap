Interview technique: the first five minutes and the whole 45

A coding interview scores how you think as much as what you write: clarify, give the brute force, improve it, code cleanly, test with examples, and state the complexity, speaking throughout.

Many people who can solve a problem alone fail the interview because they go silent, jump into code, or never test. The interviewer cannot read your mind; they grade what they can hear and see. A fixed routine removes the panic, because you always know the next step.

The 45-minute shape

MinutesPhaseWhat you do
0-5UnderstandRepeat the problem, ask questions, work one example
5-12PlanBrute force, its complexity, then the better idea and why
12-30CodeWrite clean code, narrating the key lines
30-40TestDry run the example, then edge cases; fix bugs calmly
40-45Wrap upState time and space complexity; discuss improvements and questions

A script for the first five minutes

  1. Restate in your own words: "So we get an array of integers and must return the length of the longest strictly increasing subsequence. Right?"
  2. Ask clarifying questions (see below).
  3. Work a small example by hand and say what you see. This often reveals the pattern.
  4. Say the constraint-driven target: "With n up to 105 I need about O(n log n)."
  5. Offer the brute force first: "The simple approach checks all pairs in O(n²). It is correct but too slow. Let me find a better way."

Clarifying questions worth asking

  • Input size and value ranges (overflow? negatives? zero?).
  • Can the input be empty or null? Duplicates? Is it sorted?
  • What should I return for no answer: -1, empty list, exception?
  • Can I modify the input? Is extra memory allowed?
  • For strings: only lowercase letters, or Unicode? Case sensitive?
  • For graphs: directed or not, weighted, connected, can there be cycles or self-loops?

Brute force first, then optimise

Always state the brute force, even when you see the optimal solution at once. It proves you understand the problem, gives a fallback if you get stuck, and lets you point to the exact waste you remove ("this inner loop recomputes the same sum, so a prefix sum removes it"). Moving from O(n²) to O(n) through a named idea (hash map, two pointers, sort, heap) is the story interviewers want to hear.

Writing clean code without an IDE

  • Use descriptive names (left, right, minCost), not a, b, x1.
  • Write the function signature first, then the edge-case guard (if (nums == null || nums.length == 0) return 0;), then the main loop.
  • Split out a helper for a repeated step (isValid, expand) instead of one long method.
  • Keep to one style; do not rush with unreadable one-liners.
  • You cannot compile, so slow down on generics, imports and semicolons; say "I will import java.util" and move on.

Test like a reviewer

When the code is written, do not say "done". Walk through it with the example from the start, line by line, with real values in a small table of variables. Then run the edge cases: empty input, one element, all equal, duplicates, negatives, the maximum size, and a case where the answer does not exist. Finding your own bug is a strong positive; hiding it is not.

nums = [2, 3, 1, 1, 4]   (Jump Game)
i=0  reach=0 -> reach = max(0, 0+2) = 2
i=1  reach=2 -> reach = max(2, 1+3) = 4
i=2  reach=4 -> reach = max(4, 2+1) = 4
...  reach >= last index (4)  =>  true

State the complexity clearly

End with: "Time O(n log n) because of the sort, space O(n) for the map." Name what n is when there are two inputs (m and n). Mention recursion stack space. If you can improve it, say how, even if you do not code it.

Handling hints

A hint is not a failure; interviewers give hints to see how you react. Listen, restate it ("so you suggest I think about sorting first"), and use it. Do not argue, and do not ignore it. Candidates who take a hint well and finish often score better than candidates who needed none but explained nothing.

When you are stuck

  1. Say so calmly: "I am thinking about whether this is a window or a DP problem."
  2. Return to a small example and solve it by hand; write the steps you take.
  3. Walk the clue table in your head: sorted? contiguous? all solutions? dependencies?
  4. Simplify: solve a smaller version (no duplicates, no negatives, k = 1).
  5. Fall back to the brute force and code it. A correct slow solution beats a half-written fast one.
  6. Ask for a hint after a few minutes of real effort, not after thirty seconds.

Behaviours that cost offers

  • Coding in silence for fifteen minutes.
  • Starting to code before agreeing on the approach.
  • Saying "it works" without a test.
  • Defensiveness when the interviewer points out a bug.

Practise out loud

Solve one problem a week while recording yourself or talking to a friend. The first recordings sound awkward; after six weeks the routine becomes automatic. Pair mock interviews on free platforms or with college friends are even better.

Online assessments and the Java gotchas that cost marks

An online assessment (OA) is a timed, silent test with hidden test cases: scan all questions first, secure the easy marks, watch the time, and avoid the Java traps (overflow, Integer comparison, concurrent modification, string concatenation in loops).

An OA is the first filter at most companies: a timed test on a platform (HackerRank, CodeSignal, HackerEarth and similar) with two to four coding problems, sometimes plus MCQs. No one watches you think, so only passing test cases counts. Time management is a skill by itself.

OA strategy

  1. Read all problems first (2 to 4 minutes). Rank them by how sure you are.
  2. Take the easiest first and finish it fully; points are usually per test case, so partial credit exists but a full solve is worth more per minute.
  3. Set a time box for each problem (for example, in a 60-minute test with two problems, plan about 20 minutes for the easy one and 35 for the hard one, and keep 5 as a buffer).
  4. Write the brute force when stuck. It often passes the small tests, which gives partial marks. Then try to optimise if time remains.
  5. Read the input format exactly: how many lines, spaces or newlines, what to print. Many wrong answers are format mistakes.
  6. Test with the sample, then your own edge cases before the last submit. Remember that hidden tests include the maximum size.
  7. Keep ten minutes at the end to re-read, not to start something new.

Fast input and output in Java

On platforms that read from standard input, Scanner is slow for 105 numbers or more. Use BufferedReader and StringTokenizer, and StringBuilder or PrintWriter for output.

import java.io.*;
import java.util.*;

public class Main {
    public static void main(String[] args) throws IOException {
        BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
        int n = Integer.parseInt(br.readLine().trim());
        StringTokenizer st = new StringTokenizer(br.readLine());
        int[] a = new int[n];
        for (int i = 0; i < n; i++) a[i] = Integer.parseInt(st.nextToken());
        long sum = 0;
        for (int x : a) sum += x;              // long accumulator: the sum may exceed int
        StringBuilder out = new StringBuilder();
        out.append(sum).append('\n');
        System.out.print(out);                 // one print call, not one per line
    }
}

Java gotchas in interviews and OAs

1. Integer overflow

int holds up to 2,147,483,647. Sums, products and mid-point calculations can overflow silently. Use long for sums and products, and lo + (hi - lo) / 2 for the midpoint. Use Math.addExact or Math.multiplyExact if you want an ArithmeticException instead of a silent wrap. Also remember Math.abs(Integer.MIN_VALUE) is still negative.

int a = 2_000_000_000;
long wrong = a + a;                            // int + int overflows BEFORE widening: -294967296
long right = (long) a + a;                     // cast first: 4000000000
int big = Integer.MAX_VALUE;
// big + 1 == Integer.MIN_VALUE   (no exception)
2. == on Integer (and other wrappers)

Java caches Integer objects for values from -128 to 127, so == works for small values and fails for larger ones. This bites when you compare map values or list elements.

Wrong: compares references

List<Integer> list = List.of(1000, 1000);
if (list.get(0) == list.get(1)) { /* false! */ }

Right: compares values

if (list.get(0).equals(list.get(1))) { /* true */ }
// or unbox: (int) list.get(0) == (int) list.get(1)

Likewise compare Strings with equals, never ==.

3. Modifying a collection while iterating

Removing from an ArrayList or HashMap inside a for-each loop throws ConcurrentModificationException (fail-fast iterators). Use an Iterator with it.remove(), removeIf, iterate over a copy, or collect items to remove and remove them after the loop.

List<Integer> nums = new ArrayList<>(List.of(1, 2, 3, 4, 5, 6));
nums.removeIf(x -> x % 2 == 0);                // safe: [1, 3, 5]
// for (int x : nums) if (x % 2 == 0) nums.remove((Integer) x);
// ...the for-each version above throws ConcurrentModificationException

Also remember list.remove(int index) versus list.remove(Object o): for a List<Integer>, list.remove(3) removes the element at index 3, not the value 3. Use list.remove(Integer.valueOf(3)) for the value.

4. String concatenation in loops

Strings are immutable, so s += c in a loop copies the string every time: O(n²) for n characters. Use StringBuilder (append, reverse, insert, setCharAt) and call toString() once.

5. Other traps
  • Arrays.sort on int[] with a comparator does not compile: use Integer[], or sort a list. For int[][] use Arrays.sort(a, (x, y) -> Integer.compare(x[0], y[0])), not subtraction (x[0] - y[0] can overflow).
  • Arrays.asList(int[]) gives a list with one element (the array). Use boxed types or streams.
  • PriorityQueue is a min-heap; for a max-heap pass Collections.reverseOrder(). Its iterator order is not sorted order.
  • Integer division and modulo: -7 / 2 == -3 and -7 % 2 == -1 in Java. Use Math.floorMod for a non-negative remainder.
  • char arithmetic: 'a' + 1 is an int; cast to (char) when appending.
  • Shallow copies: new ArrayList<>(path) when saving a backtracking path; adding path itself stores a reference that keeps changing.
  • Default values: new int[n] is all zeros; new boolean[n] all false; new Integer[n] all null (unboxing a null throws NullPointerException).
  • Deep recursion (about 104 to 105 frames) risks StackOverflowError; use an explicit stack.

Partial credit and plagiarism rules

Most platforms score by test cases, so a correct brute force still earns points. Many also run plagiarism and tab-switch checks; solve on your own and follow the stated rules.

Interview angle

These gotchas appear as short "what does this print" questions and as silent bugs in your solution. Mention overflow and null/empty input when you list edge cases.

Company-tagged preparation: service companies and product companies

Use company tags to find the style and difficulty of questions, not to memorise a list; service companies lean on arrays, strings and basics, product companies on mediums across all patterns plus design.

LeetCode lets you filter problems by company tag (some filters need a paid plan), and many candidates post their interview experiences in discussion forums and on sites like GeeksforGeeks. These are useful for knowing what kind of problems to expect. They are not a guarantee.

How to use company tags responsibly

  1. Cover the patterns first. Company lists are only worth doing once your pattern base is solid, which is the point of this stage.
  2. Pick two to five target companies and look at their tagged problems, sorted by frequency, from the last six to twelve months.
  3. Solve for the pattern. A tag helps you see which patterns repeat; the exact problem will often be a variation. Write the pattern in your log.
  4. Read recent discussion posts for the round structure (how many rounds, OA first or not, whether system design appears) rather than for "leaked" questions.
  5. Treat everything as unverified. Tags and posts can be old, wrong or one person's single experience. Never rely on a fixed question bank, and never present memorised answers as your own thinking; interviewers change problems and probe follow-ups.
  6. Be honest. If you have seen a problem before, tell the interviewer.

A study plan for the target list

  • Service-focused: solve all easy and basic medium problems for arrays, strings, hashing and sorting; polish one project; practise aptitude and SQL; learn to explain your Java basics.
  • Product-focused: after the pattern base, do 40 to 60 company-tagged mediums, 5 to 10 hards, timed mocks, and begin system design (see System Design).
  • For all: a one-minute self-introduction, two or three project stories you can tell clearly, and a few questions to ask the interviewer.

Common mistakes

  • Starting company lists in month 4 with weak basics; you memorise solutions and cannot adapt.
  • Believing a poster's claim that "this will definitely be asked".
  • Ignoring the non-DSA parts: core Java, SQL, Spring Boot and projects are asked at nearly every Indian full-stack interview.

For a Java full-stack role

Expect a mixed loop: one or two DSA rounds at easy-medium level, then Java/Spring/SQL questions, then a project discussion. DSA is the gate; the other topics on these pages (Collections, SQL, Spring) decide the offer.

Contests: weekly LeetCode, Codeforces and CodeChef

Contests train speed and calm under a clock; do the weekly LeetCode contest, upsolve every unsolved problem afterwards, and treat the rating as a side effect, not the goal.

Why do contests

  • They simulate the pressure of an OA: a timer, no hints, hidden tests, a penalty for wrong submissions.
  • They give you problems you have not seen, which tests real pattern recognition instead of memory.
  • They force fast, correct implementation, which makes your templates automatic.
  • Regular practice shows weak patterns clearly: the problem you could not solve is the next topic to study.

LeetCode weekly and biweekly contests

LeetCode runs a weekly contest (usually on Sunday morning in India) and a biweekly contest on Saturday nights, each with four problems and about 90 minutes. Check the exact timing on the site. Problems go from easy to hard. As a rough target: solve the first two reliably, then the third, and read the fourth for an idea. Reaching problem 3 regularly is a strong sign for interviews at good product companies.

A contest-day routine

  1. Before: be at the desk 10 minutes early, with an editor ready, water, and a plain sheet of paper. Do not warm up with a new topic.
  2. Read all four problems quickly, then start with the easiest. Do not stay on a hard one while an easy one waits.
  3. For each problem: think for 3 to 5 minutes, write the idea in a comment, code it, test the sample, and submit. A wrong answer costs a time penalty, so test small edge cases first.
  4. If stuck for 15 minutes, move on and return later.
  5. After: note which problems you solved, how long each took and which topic blocked you.

Upsolving: where the learning happens

Upsolving means solving the problems you could not finish during the contest, afterwards. This is worth more than the contest itself.

  1. Spend 30 to 60 minutes trying again without the editorial.
  2. Read the editorial or a top solution and understand the idea, not just the code.
  3. Re-implement it from scratch the next day, and add it to your log with the pattern and the "key idea" line.
  4. Add the topic to your weak-pattern list and practise three or four similar problems.

Rating is not the goal

The rating is noisy: it goes up and down with the difficulty of one set of problems, your sleep and luck. Companies do not hire by LeetCode rating. Judge progress by the number of problems you can solve cleanly in the time, and by problems you could not solve three months ago and can now. Do not skip a contest because you fear a rating drop; the practice is the point. Never use unfair means (shared solutions, bots); platforms ban accounts, and it defeats the training.

Time budget

A contest plus its upsolve takes about 3 hours per week. If your time is limited, do one contest every week and skip the biweekly one.

Common mistakes

  • Checking the rank list during the contest instead of solving.
  • Never upsolving: the contest then becomes entertainment, not practice.
  • Submitting without testing and collecting penalties.

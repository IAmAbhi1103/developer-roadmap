Interview questions — Polish: patterns, technique and range queries

How do you decide which pattern to use on a new problem?

I look at three things: the input (sorted array, string, tree, graph, intervals), what is asked (min/max, count, yes/no, all solutions, an order) and the constraints on n. Sorted input suggests binary search or two pointers; a contiguous subarray suggests a sliding window or prefix sums; "all combinations" suggests backtracking; an optimum over choices with repeated subproblems suggests DP; dependencies suggest topological sort; weighted shortest path suggests Dijkstra. I say the clue aloud, then confirm with a small example.

What do you do in the first five minutes of a coding interview?

Restate the problem, ask clarifying questions (size, duplicates, empty input, what to return when no answer exists), work a small example by hand, state the target complexity from the constraints, and describe the brute force with its complexity. Only then I move to the better idea, and I agree on it with the interviewer before writing code.

Why state the brute force when you already see the optimal solution?

It shows that you understand the problem, gives a correct fallback, and lets you explain the optimisation as a clear step ("this repeated sum becomes a prefix sum"). It also gives the interviewer a chance to guide you. Skipping it makes a good solution look like a memorised one.

How does spaced repetition work for DSA practice?

Every problem that needed a hint or help goes in a log with a "next review" date. I re-solve it from a blank editor, timed, after 3 days, then 2 weeks, then 1 month. A clean solve moves it to the next gap; a failure resets it. Problems I solved quickly alone need no review. The log also shows which patterns are weak, and those decide what new problems I pick.

Write the lower-bound binary search. What is its loop invariant?

The answer (first index with a[i] >= target) always lies in [lo, hi] where hi starts at n.

int lo = 0, hi = a.length;
while (lo < hi) {
    int mid = lo + (hi - lo) / 2;
    if (a[mid] < target) lo = mid + 1; else hi = mid;
}
return lo;

The midpoint is computed as lo + (hi - lo) / 2 to avoid overflow.

What is the difference between BFS and Dijkstra, and when does BFS give shortest paths?

BFS finds shortest paths when every edge has the same cost, because it explores nodes in order of the number of edges. Dijkstra handles different non-negative weights using a priority queue of the best known distances. With negative edges Dijkstra fails and you need Bellman-Ford. Complexities: BFS O(V + E), Dijkstra O((V + E) log V).

Give three Java gotchas that commonly cause wrong answers in interviews.

(1) Integer overflow: int + int wraps silently, so use long or cast before the operation. (2) == on Integer objects compares references and works only for the cached range -128 to 127; use equals. (3) Removing from a collection inside a for-each loop throws ConcurrentModificationException; use an iterator or removeIf. Also: s += c in a loop is O(n²); use StringBuilder.

What does this print? Integer a = 1000, b = 1000; System.out.println(a == b);

It prints false. Autoboxing uses Integer.valueOf, which caches only -128 to 127, so 1000 creates two separate objects and == compares their references. With 1 instead of 1000 it would print true. Use a.equals(b).

How would you handle being stuck during an interview?

Say what I am thinking, go back to a small example and solve it by hand, walk through the patterns (sorted? contiguous? all solutions? dependencies?), try a simpler version of the problem, and if time is passing, code the brute force so that I have a correct answer. I ask for a hint after real effort, and I use the hint openly.

How do you manage time in an online assessment?

Read all questions first and start with the one I am most sure about. Give each question a time box. When stuck, submit a brute force for partial test cases, then return. Check the input and output format carefully, test the sample and a few edge cases before submitting, and keep a few minutes at the end for re-reading. I use fast input (BufferedReader) when n is large.

How should you use company-tagged questions?

After the patterns are solid, to learn the typical difficulty and style for the companies I target, and to see which patterns repeat. I do not treat them as a guaranteed question list: tags can be old, and interviewers change problems and ask follow-ups. I solve for the pattern, log it, and read recent posts mostly for the round structure.

What problem does a segment tree solve, and what are its complexities?

It supports range queries (sum, min, max, gcd) together with point updates on an array. Build is O(n); each query and update is O(log n); memory is O(n) (about 4n entries in the recursive layout). A node stores the combined answer for its range; a query uses nodes fully inside the range and splits at partial overlaps. With lazy propagation it also supports range updates in O(log n).

How does a Fenwick tree work, and why does i & -i matter?

It is a 1-indexed array where tree[i] holds the sum of the block ending at i whose length is the lowest set bit of i. That bit is i & -i. Prefix sum: add tree[i] and subtract the lowest bit until 0. Update: add the delta and add the lowest bit until past n. Both are O(log n) with very little code.

When would you choose prefix sums, a Fenwick tree or a segment tree?

Prefix sums when the array never changes (O(1) query, O(n) build). A Fenwick tree for sums or counts with point updates (O(log n) both, tiny code). A segment tree when you need min or max, or range updates with lazy propagation, or a custom combine function. For most interviews prefix sums or a Fenwick tree are enough.

What do you say at the end of a solution?

I dry run the code on the example, check the edge cases (empty, single element, duplicates, negatives, the largest input), and then state time and space complexity with names for each variable, including recursion stack space. If there is a better trade-off (more memory for less time, or the reverse), I mention it.

Cheat sheet — Polish: patterns, technique and range queries

  • Log row problem, date, pattern, result, minutes, one-line key idea, next review date.
  • Spaced repetition re-solve needed-help problems at 3 days, 2 weeks, 1 month; blank editor, timed, out loud.
  • Checklists NeetCode 150 / Striver sheet are maps for gaps, not goals; tick only what you can redo cold.
  • Constraints to complexity n ≤ 20 exponential; ≤ 500 O(n³); ≤ 5,000 O(n²); ≤ 105 O(n log n); ≤ 106 O(n); 109 O(log n).
  • Sorted + search / pair binary search, two pointers.
  • Contiguous + condition sliding window (positive) or prefix sum + HashMap (negatives).
  • All solutions backtracking; best or count with repeats DP; local choice safe greedy.
  • Graph shortest path unweighted BFS; weighted Dijkstra; negative edges Bellman-Ford.
  • Order with dependencies topological sort; cycle means count < n.
  • Connectivity over time union-find; prefix queries trie; top K heap of size K; next greater monotonic stack.
  • Binary search mid = lo + (hi - lo) / 2; lower bound uses lo < hi, hi = n, hi = mid.
  • Merge sort stable, O(n log n), O(n) extra; quick sort average O(n log n), random pivot; quickselect average O(n).
  • BFS mark visited when you enqueue; Dijkstra skip stale queue entries; DSU path compression + union by size.
  • Interview flow clarify, example, brute force, optimise, code, test, complexity.
  • When stuck small example, simpler version, pattern table, brute force; ask for a hint after real effort.
  • OA read all problems, easiest first, time-box, brute force for partial marks, check I/O format, fast input.
  • Java traps int overflow, Integer ==, ConcurrentModificationException, remove(int) vs remove(Object), string += in loops, subtraction in comparators.
  • Company prep patterns first; tags show style and difficulty, not a guaranteed list; be honest about problems seen before.
  • Contests read all problems, easiest first; upsolve every unsolved problem; rating is noise.
  • Segment tree build O(n), query/update O(log n), array size 4n; identity: 0 for sum, Long.MAX_VALUE for min.
  • Lazy propagation pending range updates stored on nodes; pushed down only when needed.
  • Fenwick tree 1-indexed; query i -= i & -i; update i += i & -i; range = prefix(r) − prefix(l−1).
  • Choose static array: prefix sums; sum with updates: Fenwick; min/max or range update: segment tree.

Practice — Polish: patterns, technique and range queries

Months 10 to 12 target: re-solve all your "needed help" problems, fill the gaps found by NeetCode 150 or the Striver sheet, solve company-tagged problems for your targets, and do the weekly contests, with at least 15 new problems and about 300 problems in the log by the end.

  1. Set up the log. Create the spreadsheet or file with the columns from the revision system, add every problem you remember with its result, and schedule the first reviews. Done when every "needed help" problem has a review date.
  2. Re-solve the help list. Work through all problems marked "needed help", from a blank editor, 30 to 40 minutes each, out loud. Done when you re-solve most cleanly; send the rest back to the 3-day step.
  3. Templates from memory. On paper, then in an editor, write binary search, lower bound, merge sort, partition, BFS, DFS, Dijkstra, union-find, topological sort and coin change, as in the templates. Done when all ten take under 30 minutes in total and pass small tests.
  4. Pattern sorting drill. Take 30 problem titles from the NeetCode 150 list, cover the solutions, and write the pattern and first idea for each in under two minutes. Check against the clue table. Done when you name the pattern correctly for about 25 of them.
  5. Timed mocks. Once a week solve two mediums in 70 minutes while speaking aloud, using the first-five-minutes script. Ask a friend to listen, or record yourself. Done when you finish most mediums in 30 to 40 minutes and state time and space complexity every time.
  6. OA simulation. Do three full practice assessments (three problems in 90 minutes) on a coding platform's practice mode, including fast input and the input format. Done when you submit correct solutions to at least two of three in time.
  7. Company-tagged set. For two to five target companies, solve 15 or more recent tagged problems you have not done, and log the pattern of each. Done when you can say which patterns repeat for each company.
  8. Contest cycle. Take part in four weekly LeetCode contests and upsolve every unsolved problem within two days. Done when you reach the third problem in at least one contest and have new rows in the log for each upsolve.
  9. Range-query structures (optional). Implement a segment tree and a Fenwick tree from scratch; solve Range Sum Query - Mutable with both, then Count of Smaller Numbers After Self with the Fenwick tree. Done when both pass and you can explain i & -i and the three segment-tree cases.
  10. The "done when" check. You are ready when you can spot the pattern of a new medium problem in 5 to 10 minutes, solve most mediums in 30 to 40 minutes while explaining out loud, state time and space complexity every time, have about 300 problems in the log, and write binary search, merge sort, BFS, DFS, Dijkstra, union-find and a basic DP from memory.

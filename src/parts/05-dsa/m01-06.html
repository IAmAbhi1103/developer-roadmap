Sorting: bubble, selection and insertion sort

The three simple sorts are O(n²), easy to write and good for learning the ideas of swaps, invariants and stability; only insertion sort has a real use in practice, for small or nearly sorted data.

Why learn sorting at all?

In real code you call Arrays.sort. In interviews, you are asked to implement a sort, to explain properties (stable? in place? worst case?), or to use sorting as a tool: "sort first, then two pointers", "sort intervals by start". Sorting changes an O(n²) search into O(n log n) + O(n) in dozens of problems. Know these terms:

In place
Uses O(1) extra memory (apart from the call stack in some cases).
Stable
Equal elements keep their original relative order. If records (Rahul, 90) and (Priya, 90) are sorted by marks, a stable sort leaves Rahul before Priya if he came first.
Comparison sort
Decides order only by comparing two elements. No comparison sort can beat O(n log n) in the worst case.
Adaptive
Runs faster on nearly sorted input.

Bubble sort

Repeatedly walk through the array, swapping adjacent pairs that are out of order. After pass k, the k largest elements have "bubbled" to the end. If a whole pass makes no swap, the array is sorted and you can stop early.

import java.util.*;

public class BubbleSort {
    static void bubbleSort(int[] a) {
        int n = a.length;
        for (int pass = 0; pass < n - 1; pass++) {
            boolean swapped = false;
            for (int i = 0; i < n - 1 - pass; i++) {      // last 'pass' elements are final
                if (a[i] > a[i + 1]) {
                    int t = a[i]; a[i] = a[i + 1]; a[i + 1] = t;
                    swapped = true;
                }
            }
            if (!swapped) break;                           // already sorted: O(n) best case
        }
    }

    public static void main(String[] args) {
        int[] a = {5, 1, 4, 2, 8};
        bubbleSort(a);
        System.out.println(Arrays.toString(a));
    }
}
[1, 2, 4, 5, 8]

Dry run: [5,1,4,2,8] → pass 1: [1,4,2,5,8] → pass 2: [1,2,4,5,8] → pass 3: no swap, stop. Time: best O(n) (with the flag), average and worst O(n²). Space O(1). Stable (it swaps only when strictly greater).

Selection sort

Find the minimum of the unsorted part and swap it to the front of that part. The sorted prefix grows by one each round.

import java.util.*;

public class SelectionSort {
    static void selectionSort(int[] a) {
        for (int i = 0; i < a.length - 1; i++) {
            int min = i;
            for (int j = i + 1; j < a.length; j++) {
                if (a[j] < a[min]) min = j;
            }
            int t = a[i]; a[i] = a[min]; a[min] = t;       // at most one swap per round
        }
    }

    public static void main(String[] args) {
        int[] a = {64, 25, 12, 22, 11};
        selectionSort(a);
        System.out.println(Arrays.toString(a));
    }
}
[11, 12, 22, 25, 64]

Time O(n²) in every case (it always scans the rest), space O(1), only O(n) swaps — useful when writes are expensive. Not stable: swapping the minimum to the front can jump over an equal element.

Insertion sort

Like sorting playing cards in your hand: take the next element and slide it left into its correct place among the already sorted prefix.

import java.util.*;

public class InsertionSort {
    static void insertionSort(int[] a) {
        for (int i = 1; i < a.length; i++) {
            int key = a[i];
            int j = i - 1;
            while (j >= 0 && a[j] > key) {      // shift bigger elements right
                a[j + 1] = a[j];
                j--;
            }
            a[j + 1] = key;
        }
    }

    public static void main(String[] args) {
        int[] a = {12, 11, 13, 5, 6};
        insertionSort(a);
        System.out.println(Arrays.toString(a));
    }
}
[5, 6, 11, 12, 13]

Dry run: [12,11,13,5,6] → insert 11: [11,12,13,5,6] → 13 stays → insert 5: [5,11,12,13,6] → insert 6: [5,6,11,12,13]. Time: best O(n) (already sorted), average and worst O(n²); space O(1); stable (it stops at an equal element); adaptive.

Where insertion sort is actually used

For tiny arrays (roughly under a few dozen elements) its low overhead beats O(n log n) algorithms. Real library sorts such as TimSort and dual-pivot quicksort switch to insertion sort for small ranges or runs. It is also the right choice when data is "almost sorted" — each element is only a few places from its final position.

"Which sort for nearly sorted data?" Insertion sort: O(n + number of inversions). "Which makes the fewest writes?" Selection sort. "Is bubble sort ever used?" Practically no, but the early-exit flag question is a favourite. The follow-up is always: "now do it in O(n log n)" — merge sort or quick sort, next.

Merge sort and counting inversions

Merge sort splits the array in half, sorts each half recursively, then merges the two sorted halves in linear time: O(n log n) always, stable, but it needs O(n) extra space.

The idea: divide, conquer, combine

Sorting two halves is easier than sorting the whole, and merging two already sorted lists is easy: repeatedly take the smaller of the two front elements. The recursion bottoms out at arrays of size 1, which are sorted by definition.

Code

import java.util.*;

public class MergeSort {
    static void mergeSort(int[] a) {
        if (a.length < 2) return;
        int[] tmp = new int[a.length];               // allocate the buffer once
        sort(a, tmp, 0, a.length - 1);
    }

    private static void sort(int[] a, int[] tmp, int lo, int hi) {
        if (lo >= hi) return;                        // base case: 0 or 1 element
        int mid = lo + (hi - lo) / 2;
        sort(a, tmp, lo, mid);
        sort(a, tmp, mid + 1, hi);
        merge(a, tmp, lo, mid, hi);
    }

    private static void merge(int[] a, int[] tmp, int lo, int mid, int hi) {
        int i = lo, j = mid + 1, k = lo;
        while (i <= mid && j <= hi) {
            if (a[i] <= a[j]) tmp[k++] = a[i++];     // <= keeps equal elements in order: stable
            else tmp[k++] = a[j++];
        }
        while (i <= mid) tmp[k++] = a[i++];
        while (j <= hi) tmp[k++] = a[j++];
        for (k = lo; k <= hi; k++) a[k] = tmp[k];    // copy back
    }

    public static void main(String[] args) {
        int[] a = {38, 27, 43, 3, 9, 82, 10};
        mergeSort(a);
        System.out.println(Arrays.toString(a));
    }
}
[3, 9, 10, 27, 38, 43, 82]

Complexity. Recurrence T(n) = 2T(n/2) + O(n). By the recursion tree there are log2 n levels with n work each → O(n log n) in best, average and worst cases (see analysing recursion). Space: O(n) for the buffer plus O(log n) for the call stack. Stable if the merge takes from the left half on ties (<=). Not in place (for arrays).

Dry run of one merge: left [3, 27, 38, 43], right [9, 10, 82]. Compare 3 vs 9 → 3; 27 vs 9 → 9; 27 vs 10 → 10; 27 vs 82 → 27; 38 vs 82 → 38; 43 vs 82 → 43; right leftover 82. Result [3, 9, 10, 27, 38, 43, 82].

Mistakes in merge sort

Allocating a new array in every recursive call (correct but slow and memory hungry); using < instead of <= in the merge and losing stability; forgetting to copy the buffer back; computing (lo + hi) / 2 (can overflow for huge indices); and using lo == hi as the base case when lo > hi can happen for empty ranges — lo >= hi covers both.

Application: counting inversions

An inversion is a pair i < j with a[i] > a[j]; it measures how unsorted an array is. Brute force over all pairs is O(n²). Merge sort counts them for free: during a merge, when you take an element from the right half, it is smaller than every element still waiting in the left half — that is mid - i + 1 inversions at once.

public class Inversions {
    static long countInversions(int[] a) {
        return sort(a.clone(), new int[a.length], 0, a.length - 1);
    }

    private static long sort(int[] a, int[] tmp, int lo, int hi) {
        if (lo >= hi) return 0;
        int mid = lo + (hi - lo) / 2;
        long count = sort(a, tmp, lo, mid) + sort(a, tmp, mid + 1, hi);
        int i = lo, j = mid + 1, k = lo;
        while (i <= mid && j <= hi) {
            if (a[i] <= a[j]) tmp[k++] = a[i++];
            else {
                tmp[k++] = a[j++];
                count += mid - i + 1;               // a[i..mid] are all greater than a[j]
            }
        }
        while (i <= mid) tmp[k++] = a[i++];
        while (j <= hi) tmp[k++] = a[j++];
        for (k = lo; k <= hi; k++) a[k] = tmp[k];
        return count;
    }

    public static void main(String[] args) {
        System.out.println(countInversions(new int[]{2, 4, 1, 3, 5}));
        System.out.println(countInversions(new int[]{5, 4, 3, 2, 1}));
    }
}

For [2,4,1,3,5] the inversions are (2,1), (4,1), (4,3) = 3. The worst case (reverse sorted, n = 5) has n(n−1)/2 = 10. Return long: for n = 105 there can be 5 × 109 inversions. The same merge-and-count idea solves Count of Smaller Numbers After Self and Reverse Pairs.

Why choose merge sort?

Strengths

  • Guaranteed O(n log n); no bad inputs.
  • Stable.
  • Works well on linked lists (O(1) extra space, no random access needed) and for external sorting of data larger than memory.
  • Parallelises naturally.

Weaknesses

  • O(n) extra space on arrays.
  • Slower constants than quick sort on arrays (copying).

Java connection

Arrays.sort(Object[]), Collections.sort and List.sort use TimSort, a hybrid of merge sort and insertion sort that detects existing sorted runs — stable and O(n) on already sorted data.

Why it is correct and why it is n log n

Correctness comes from one invariant: before each merge, both halves are sorted. Merging keeps the smallest unused element of each half in front, so the output is built in sorted order, one smallest element at a time. By induction on size, every call returns a sorted range. For speed, count the work per level. At the top, one merge touches n elements. At the next level, two merges touch n/2 each, again n in total. Every level costs n, and halving n down to 1 takes log2 n levels. For n = 8 that is 3 levels, so about 8 × 3 = 24 element moves, not 8 × 8 = 64. For n = 1,000,000 the gap is about 20 million versus 1012.

Bottom-up merge sort (no recursion)

You can skip recursion: merge runs of width 1, then 2, 4, 8 and so on until one run covers the array. It has no call stack, so there is no StackOverflowError risk, and it is how many library sorts are built. Add it to the same MergeSort class, reusing merge.

static void bottomUp(int[] a) {
    int n = a.length;
    int[] tmp = new int[n];
    for (int width = 1; width < n; width *= 2) {
        for (int lo = 0; lo < n - width; lo += 2 * width) {
            int mid = lo + width - 1;                      // end of the left run
            int hi = Math.min(lo + 2 * width - 1, n - 1);  // last run may be shorter
            merge(a, tmp, lo, mid, hi);
        }
    }
}

The guard lo < n - width means a right run exists; if it does not, the left run is already sorted and is left alone.

Sort a linked list in O(n log n)

Merge sort is the natural sort for linked lists. Finding the middle needs the slow and fast pointers from fast and slow pointers; merging relinks nodes and needs no extra array, so the extra space is only the recursion stack, O(log n).

// fragment: class ListNode { int val; ListNode next; ListNode(int v) { val = v; } }
static ListNode sortList(ListNode head) {
    if (head == null || head.next == null) return head;
    ListNode slow = head, fast = head.next;    // fast starts one step ahead: left half not longer
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
    }
    ListNode right = slow.next;
    slow.next = null;                          // cut the list into two
    return mergeLists(sortList(head), sortList(right));
}

static ListNode mergeLists(ListNode a, ListNode b) {
    ListNode dummy = new ListNode(0), tail = dummy;
    while (a != null && b != null) {
        if (a.val <= b.val) { tail.next = a; a = a.next; }   // <= keeps it stable
        else { tail.next = b; b = b.next; }
        tail = tail.next;
    }
    tail.next = (a != null) ? a : b;           // attach the leftover run
    return dummy.next;
}

Dry run: counting inversions step by step

Take [2, 4, 1, 3, 5]. The split is [2,4,1] and [3,5]; [2,4,1] splits into [2,4] and [1].

  • Merge [2,4] with [1]: 1 < 2, so 1 is taken from the right while both 2 and 4 wait on the left. That is mid - i + 1 = 2 inversions, (2,1) and (4,1). Result [1,2,4].
  • Merge [3] and [5] (from [3,5]): no right element is smaller. Zero inversions.
  • Merge [1,2,4] with [3,5]: 1 and 2 come from the left; then 3 < 4, so 3 is taken from the right while 4 waits. One inversion, (4,3). Then 4 and 5 are copied.

The total is 2 + 0 + 1 = 3, matching the program output.

Another problem: Reverse Pairs

Count pairs i < j with nums[i] > 2 * nums[j]. It is inversions with a doubled right side, so you cannot count during the merge itself. Instead, count before merging, while both halves are sorted: for each left element, a moving pointer j finds how many right elements are less than half of it. Because the left side is sorted, j only moves forward, so the counting step is O(n) per level.

// call between the two recursive sorts and merge(...)
private static long countPairs(int[] a, int lo, int mid, int hi) {
    long count = 0;
    int j = mid + 1;
    for (int i = lo; i <= mid; i++) {
        while (j <= hi && (long) a[i] > 2L * a[j]) j++;   // long: 2 * a[j] can overflow int
        count += j - (mid + 1);                           // right elements smaller than a[i] / 2
    }
    return count;
}

Count of Smaller Numbers After Self uses the same merge-and-count idea but must carry each element's original index through the sort. The pattern to remember: a pair-counting question over i < j with a comparison between values is often merge sort in disguise.

Edge cases

  • Empty or one-element array: the base case lo >= hi returns at once. For the inversion counter, a.length == 0 calls sort(..., 0, -1), which returns 0.
  • Duplicates and inversions: equal elements are not inversions. The merge takes from the left on ties (<=), so the count is not touched. Using < would wrongly count equal pairs.
  • Already sorted or reverse sorted input: same O(n log n); merge sort has no bad case. Only the inversion count changes (0 or n(n−1)/2).
  • Overflow: the inversion count needs long; (lo + hi) / 2 can overflow for indices near 231.

Mistake: counting with the wrong tie rule

Wrong: strict compare on the left side

if (a[i] < a[j]) tmp[k++] = a[i++];     // ties go right
else { tmp[k++] = a[j++]; count += mid - i + 1; }
// [2, 2] reports 1 inversion

Right: ties go to the left, no count

if (a[i] <= a[j]) tmp[k++] = a[i++];
else { tmp[k++] = a[j++]; count += mid - i + 1; }
// [2, 2] reports 0 inversions

Interview angle

Write it, state T(n) = 2T(n/2) + n → O(n log n), O(n) space, stable. Common follow-ups: "sort a linked list in O(n log n)" (find the middle with slow/fast pointers, merge), "count inversions", "merge k sorted lists" (heap, Module 2), and "why does Java use a merge-based sort for objects?" — because stability matters for objects.

Quick sort, partitioning and quickselect

Quick sort picks a pivot, partitions the array so smaller elements come before it and larger ones after, then recurses on both sides: O(n log n) on average, O(n²) in the worst case, in place and not stable.

The idea

Merge sort does the hard work when combining; quick sort does it when splitting. After one partition step the pivot is at its final sorted position, so the two sides can be sorted independently, with nothing to combine afterwards.

Lomuto partition (simple)

Pivot = last element. Keep an index i marking the end of the "smaller than pivot" zone; scan j from left to right and swap smaller elements into that zone. Finally swap the pivot into place.

import java.util.*;

public class QuickSort {
    private static final Random RNG = new Random();

    static void quickSort(int[] a) {
        sort(a, 0, a.length - 1);
    }

    private static void sort(int[] a, int lo, int hi) {
        if (lo >= hi) return;
        int p = partition(a, lo, hi);
        sort(a, lo, p - 1);
        sort(a, p + 1, hi);
    }

    // Lomuto partition with a random pivot; returns the pivot's final index
    private static int partition(int[] a, int lo, int hi) {
        swap(a, lo + RNG.nextInt(hi - lo + 1), hi);      // random pivot moved to the end
        int pivot = a[hi];
        int i = lo - 1;
        for (int j = lo; j < hi; j++) {
            if (a[j] < pivot) swap(a, ++i, j);
        }
        swap(a, i + 1, hi);
        return i + 1;
    }

    private static void swap(int[] a, int i, int j) {
        int t = a[i]; a[i] = a[j]; a[j] = t;
    }

    public static void main(String[] args) {
        int[] a = {7, 2, 9, 4, 3, 8, 1};
        quickSort(a);
        System.out.println(Arrays.toString(a));
    }
}
[1, 2, 3, 4, 7, 8, 9]

Hoare partition (fewer swaps)

Two pointers start at the ends and move toward each other; swap when the left one holds a value ≥ pivot and the right one holds a value ≤ pivot. It does about three times fewer swaps than Lomuto on average, but returns a split point, not the pivot's final index, so the recursion is on [lo, p] and [p+1, hi].

import java.util.*;

public class HoareSort {
    static void sort(int[] a, int lo, int hi) {
        if (lo >= hi) return;
        int p = partition(a, lo, hi);
        sort(a, lo, p);                  // note: p, not p - 1
        sort(a, p + 1, hi);
    }

    static int partition(int[] a, int lo, int hi) {
        int pivot = a[lo + (hi - lo) / 2];
        int i = lo - 1, j = hi + 1;
        while (true) {
            do { i++; } while (a[i] < pivot);
            do { j--; } while (a[j] > pivot);
            if (i >= j) return j;
            int t = a[i]; a[i] = a[j]; a[j] = t;
        }
    }

    public static void main(String[] args) {
        int[] a = {5, 3, 8, 1, 9, 2, 5};
        sort(a, 0, a.length - 1);
        System.out.println(Arrays.toString(a));
    }
}
[1, 2, 3, 5, 5, 8, 9]

Edge case: Hoare is fragile — memorise the exact form

Small changes (using hi as pivot, recursing on p - 1, changing do/while to while) cause infinite recursion or missed elements. In an interview, Lomuto is safer unless asked for Hoare.

Complexity: why average O(n log n) and worst O(n²)

  • Good split (pivot near the middle): T(n) = 2T(n/2) + n → O(n log n). Even a 10/90 split every time gives O(n log n), because depth is log10/9 n.
  • Worst split (pivot is the smallest or largest each time): T(n) = T(n−1) + n → O(n²). It happens with a first/last-element pivot on an already sorted array, or many duplicates with a naive partition. The recursion depth also becomes n, which can cause StackOverflowError.
  • Fixes: pick a random pivot (expected O(n log n) for any input), median of three, recurse into the smaller side first, and use three-way partitioning when there are many equal keys.
  • Space: O(log n) average for the call stack; O(n) worst case. Time is typically faster than merge sort in practice thanks to cache-friendly in-place scans.

Quickselect: the k-th element in O(n) average

You do not need a full sort to find the k-th smallest element. After partitioning, the pivot is at its final index p: if p equals the target index you are done, otherwise recurse into only one side. T(n) = T(n/2) + n averages to O(n); the worst case is O(n²) (use a random pivot).

import java.util.*;

public class QuickSelect {
    private static final Random RNG = new Random();

    // Kth Largest Element in an Array (215)
    static int findKthLargest(int[] nums, int k) {
        int target = nums.length - k;            // index in ascending order
        int lo = 0, hi = nums.length - 1;
        while (lo <= hi) {
            int p = partition(nums, lo, hi);
            if (p == target) return nums[p];
            if (p < target) lo = p + 1;
            else hi = p - 1;
        }
        throw new IllegalArgumentException("k out of range");
    }

    private static int partition(int[] a, int lo, int hi) {
        int r = lo + RNG.nextInt(hi - lo + 1);
        int t = a[r]; a[r] = a[hi]; a[hi] = t;
        int pivot = a[hi], i = lo - 1;
        for (int j = lo; j < hi; j++) {
            if (a[j] < pivot) { i++; t = a[i]; a[i] = a[j]; a[j] = t; }
        }
        t = a[i + 1]; a[i + 1] = a[hi]; a[hi] = t;
        return i + 1;
    }

    public static void main(String[] args) {
        System.out.println(findKthLargest(new int[]{3, 2, 1, 5, 6, 4}, 2));
    }
}
5

A min-heap of size k gives O(n log k) and is safer (no bad worst case); quickselect is O(n) expected. Quickselect modifies the input array.

Counting sort (brief)

If values are integers in a small range 0..k, you do not need comparisons: count each value, then write them out in order. Time O(n + k), space O(k). It is stable in its prefix-sum form and powers radix sort. Sort Colors is counting sort with k = 3.

import java.util.*;

public class CountingSort {
    static void countingSort(int[] a, int maxValue) {
        int[] count = new int[maxValue + 1];
        for (int x : a) count[x]++;
        int idx = 0;
        for (int v = 0; v <= maxValue; v++) {
            while (count[v]-- > 0) a[idx++] = v;
        }
    }

    public static void main(String[] args) {
        int[] a = {4, 2, 2, 8, 3, 3, 1};
        countingSort(a, 8);
        System.out.println(Arrays.toString(a));
    }
}
[1, 2, 2, 3, 3, 4, 8]

Three-way partitioning for many duplicates

With Lomuto and a strict <, an array where every element is equal puts the whole array on one side every time: the pivot lands at the first index, the split is 0 and n−1, and the time becomes O(n²). The fix is the Dutch national flag partition (the same idea as Sort Colors): split into three zones — less than, equal to, and greater than the pivot — and recurse only on the first and last zone. The middle zone is already in its final place.

// add to the QuickSort class (uses RNG and swap from above)
private static void sort3(int[] a, int lo, int hi) {
    if (lo >= hi) return;
    int pivot = a[lo + RNG.nextInt(hi - lo + 1)];
    int lt = lo, i = lo, gt = hi;
    // invariant: a[lo..lt-1] < pivot, a[lt..i-1] == pivot, a[gt+1..hi] > pivot
    while (i <= gt) {
        if (a[i] < pivot) swap(a, lt++, i++);
        else if (a[i] > pivot) swap(a, i, gt--);      // do not advance i: new value unseen
        else i++;
    }
    sort3(a, lo, lt - 1);
    sort3(a, gt + 1, hi);
}

On an array of all equal values this finishes in one pass: every element goes to the middle zone. With few distinct keys the time approaches O(n).

Keeping the stack small

Recursion depth is log n only on balanced splits. A bad split gives depth n and can throw StackOverflowError for large inputs. A cheap guarantee: recurse into the smaller side and loop on the larger side. Each recursive call then handles at most half the range, so the depth is at most log2 n even in the worst case (the time can still be O(n²) without a good pivot).

private static void sort(int[] a, int lo, int hi) {
    while (lo < hi) {
        int p = partition(a, lo, hi);
        if (p - lo < hi - p) {            // left side is smaller: recurse on it
            sort(a, lo, p - 1);
            lo = p + 1;                   // then loop on the right side
        } else {
            sort(a, p + 1, hi);
            hi = p - 1;
        }
    }
}

Dry run of quickselect

Find the 2nd largest in [3, 2, 1, 5, 6, 4]. The target index in ascending order is n − k = 4. Suppose the random pivot happens to be the last element, 4. Lomuto scans: 3, 2 and 1 are smaller and move to the front; 5 and 6 stay. The pivot swaps into index 3, giving [3, 2, 1, 4, 6, 5], so p = 3. Since 3 < 4, the answer is on the right: lo = 4. The range [6, 5] has pivot 5; 6 is not smaller, so the pivot swaps to index 4: [..., 5, 6], p = 4 = target. The answer is 5. Only part of the array was ever touched, which is why the average cost is n + n/2 + n/4 + ... = O(n).

Use the heap when data arrives one by one or the array must stay unchanged (see heap problems). Use quickselect when you hold the whole array and want the best average time.

What Java uses

Arrays.sort(int[]) and the other primitive overloads use a dual-pivot quicksort. Stability does not matter for primitives, because equal ints are indistinguishable. Object arrays use TimSort, which is stable (see comparators and stability).

Edge cases

  • Sorted or reverse-sorted input with a first/last pivot: O(n²) and recursion depth n. A random or median-of-three pivot avoids it.
  • All equal elements: O(n²) with Lomuto and strict comparison; fixed by three-way partition.
  • Empty array: hi = -1, so lo >= hi returns immediately. But RNG.nextInt(hi - lo + 1) would throw IllegalArgumentException if called with a bound of 0 or less, so the base case must run first.
  • k out of range in quickselect: k < 1 or k > n never meets the target index; the loop ends and the code throws an exception. Validate k up front.

Mistake: a fixed pivot on sorted input

Wrong: always the first element

int pivot = a[lo];                       // sorted input: splits 0 and n-1

Right: a random element

int r = lo + RNG.nextInt(hi - lo + 1);
swap(a, r, hi);                          // then partition with a[hi] as pivot

Interview angle

"Worst case of quick sort?" O(n²) when pivots are always extreme (sorted input with first/last pivot). "How do you avoid it?" Random pivot or median-of-three. "Is quick sort stable?" No — partition swaps jump over equal elements. "Why does Java use quicksort for int[] but a merge sort for objects?" Primitives have no identity, so stability is irrelevant and in-place speed wins; objects need stability.

Comparators, stability and choosing a sort

Java sorts objects with a Comparator that returns negative, zero or positive; build them with Comparator.comparing and thenComparing, never by subtraction, and choose your algorithm from the comparison table.

How a comparator works

A Comparator<T> has one method, int compare(T a, T b). Return a negative number if a should come before b, zero if they are equal for sorting, and a positive number if a comes after b. It must be consistent: if compare(a,b) < 0 then compare(b,a) > 0, and it must be transitive. A broken comparator can make TimSort throw IllegalArgumentException: Comparison method violates its general contract!

import java.util.*;

public class Comparators {
    record Employee(String name, String dept, int salary) {}

    public static void main(String[] args) {
        // 1. Strings: by length, then alphabetically
        String[] words = {"banana", "fig", "apple", "kiwi", "date"};
        Arrays.sort(words, (a, b) -> a.length() != b.length()
            ? Integer.compare(a.length(), b.length())
            : a.compareTo(b));
        System.out.println(Arrays.toString(words));

        // 2. Integer[] descending
        Integer[] nums = {3, 9, 1, 7};
        Arrays.sort(nums, Comparator.reverseOrder());
        System.out.println(Arrays.toString(nums));

        // 3. Intervals by start, then by end
        int[][] iv = {{3, 5}, {1, 9}, {1, 4}, {2, 3}};
        Arrays.sort(iv, (a, b) -> a[0] != b[0] ? Integer.compare(a[0], b[0])
                                              : Integer.compare(a[1], b[1]));
        System.out.println(Arrays.deepToString(iv));

        // 4. Objects: dept ascending, salary descending, name as tie-breaker
        List<Employee> staff = new ArrayList<>(List.of(
            new Employee("Asha", "IT", 90), new Employee("Ravi", "HR", 70),
            new Employee("Neha", "IT", 120), new Employee("Kabir", "HR", 70)));
        staff.sort(Comparator.comparing(Employee::dept)
            .thenComparing(Employee::salary, Comparator.reverseOrder())
            .thenComparing(Employee::name));
        staff.forEach(e -> System.out.println(e.dept() + " " + e.salary() + " " + e.name()));

        // 5. Largest number: order strings so that a+b beats b+a
        String[] digits = {"3", "30", "34", "5", "9"};
        Arrays.sort(digits, (a, b) -> (b + a).compareTo(a + b));
        System.out.println(String.join("", digits));
    }
}

Example 5 is Largest Number (179): two numbers are ordered by which concatenation is bigger, not by their own value. Custom orders like this are the core of many "sort then greedy" problems.

Mistake: comparing by subtraction

(a, b) -> a - b overflows for large or negative values (Integer.MIN_VALUE - 1 becomes a large positive number) and gives a wrong or contract-violating order. Use Integer.compare(a, b). Also never write a comparator that returns only 1 or 0 (never negative); it breaks the contract.

Edge case: primitives have no comparator

Arrays.sort(int[], comparator) does not exist. To sort int[] descending, use Integer[] (boxing cost), sort ascending and reverse, or sort a stream: Arrays.stream(a).boxed().sorted(Comparator.reverseOrder()). For int[][] a comparator works because each row is an object.

Stability explained

A sort is stable when equal keys keep their input order. This makes multi-key sorting easy: sort by the secondary key first, then by the primary key with a stable sort. Java's object sorts are stable (TimSort), so the following example keeps names alphabetical inside each marks group:

import java.util.*;

public class Stability {
    record Student(String name, int marks) {}

    public static void main(String[] args) {
        List<Student> list = new ArrayList<>(List.of(
            new Student("Anil", 80), new Student("Bela", 90),
            new Student("Chitra", 80), new Student("Deep", 90)));
        list.sort(Comparator.comparingInt(Student::marks));   // stable
        list.forEach(s -> System.out.print(s.name() + " "));
    }
}
Anil Chitra Bela Deep

Anil still precedes Chitra, and Bela precedes Deep, because they were in that order before sorting.

Sorting as a tool: classic problems

Merge Intervals (56)
Sort by start; walk through, extending the current interval while the next start is ≤ current end. O(n log n).
Meeting Rooms (252 / 253)
Sort by start and check overlaps; for the minimum number of rooms sort starts and ends separately, or use a heap (Module 2).

import java.util.*;

public class MergeIntervals {
    static int[][] merge(int[][] intervals) {
        Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));
        List<int[]> out = new ArrayList<>();
        for (int[] cur : intervals) {
            if (out.isEmpty() || out.get(out.size() - 1)[1] < cur[0]) {
                out.add(cur);                                  // no overlap: new interval
            } else {
                int[] last = out.get(out.size() - 1);
                last[1] = Math.max(last[1], cur[1]);           // overlap: extend
            }
        }
        return out.toArray(new int[0][]);
    }

    public static void main(String[] args) {
        int[][] r = merge(new int[][]{{1, 3}, {8, 10}, {2, 6}, {15, 18}});
        System.out.println(Arrays.deepToString(r));
    }
}

Interview angle

Typical questions: "sort strings by length then alphabetically" (write the comparator on a whiteboard), "what is a stable sort and when does it matter" (multi-key sorting), "which sort would you use for 10 million integers / for objects / for nearly sorted data / for numbers 0..100". Strong answers pick by property: counting for small ranges, TimSort for objects, insertion for tiny or nearly sorted, quick sort (Arrays.sort) for primitives.

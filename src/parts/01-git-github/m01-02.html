How Git stores your work: snapshots, hashes and HEAD

Git saves each commit as a full snapshot of your project, names it with a SHA hash, links it to its parent commit, and uses tiny pointers — HEAD and branch names — to remember where you are.

You can use Git for months by memorising commands. You will use it well only when you know what the commands do inside. The good news: the core idea is small. Git is a simple key-value store — you give it content, it gives back a name (a hash) — and four kinds of objects built on top of that.

Snapshots, not differences

Older systems such as SVN store a file as a list of changes: "version 1, then these lines added, then these lines removed". Git thinks differently. Each time you commit, Git records a snapshot of every tracked file as it looks at that moment. If a file did not change, Git does not copy it again — the new snapshot simply points to the same stored content as before. So snapshots are cheap, and going to any commit is fast, because Git does not have to replay a chain of changes.

When you run git diff or git show, Git computes the difference between two snapshots on the fly. The difference is not what is stored.

The four object types

Everything inside the hidden .git/objects folder is one of four kinds of objects:

blob
The content of one file — only the content, not the file name. Two files with identical content share one blob.
tree
A folder. It lists names and, for each name, the hash of a blob (a file) or another tree (a sub-folder).
commit
A snapshot label. It points to one top-level tree, to its parent commit(s), and stores the author, date and message.
tag
A fixed, named pointer to a commit, optionally with its own message (used for releases; see Module 4).

SHA hashes: the name of every object

Git names an object by running its content through a hash function. The result is a 40-character hexadecimal string, called the SHA (or commit hash), for example 3f2a9c1e8b7d4a5c6f0e1d2b3a4c5d6e7f8a9b0c. (Git has been moving from SHA-1 to SHA-256, which gives 64 characters; today's repositories are still SHA-1 by default, and everything you learn here works the same.)

  • Same content gives the same hash; any change gives a completely different hash. This is how Git detects corruption and how it knows two files are identical without comparing them.
  • A commit's hash is computed from its tree, its parent hash, author, date and message. So a commit's hash includes its parent's hash: changing an old commit changes every commit after it. This chain makes history tamper-evident.
  • You rarely type all 40 characters. The first 7 are normally enough: git show 3f2a9c1. Git accepts any prefix that is unique in the repository (at least 4 characters).

Parent links make a history

Each commit stores the hash of the commit that came before it (its parent). A merge commit has two parents. Following parent links backwards from the newest commit gives you the whole history, and that is exactly what git log prints.

Branches and HEAD are just pointers

A branch is a file that holds one commit hash. That is all. The branch main is the file .git/refs/heads/main containing the hash of its latest commit. When you commit, Git creates the new commit and moves the branch pointer forward to it. Creating a branch means writing a new 41-byte file, which is why branches are instant and free.

HEAD is a special pointer that means "where I am now". Usually it points to a branch name, not to a commit directly:

$ cat .git/HEAD
ref: refs/heads/main
$ cat .git/refs/heads/main
3f2a9c1e8b7d4a5c6f0e1d2b3a4c5d6e7f8a9b0c

The next commit becomes the child of whatever HEAD points to, and the branch HEAD points to moves forward with it. When HEAD points straight at a commit instead of a branch, you are in detached HEAD state — you will meet that in Module 3.

Naming commits relative to HEAD

ExpressionMeaning
HEADThe commit you are on (the latest commit of the current branch)
HEAD~1 or HEAD~ or HEAD^The first parent of HEAD — one commit back
HEAD~3Three commits back, always following first parents
HEAD^2The second parent of HEAD (only exists for a merge commit)
main~2Two commits before the tip of main

~ means "go back N generations"; ^ means "choose which parent". For an ordinary commit with one parent, HEAD~1 and HEAD^ are the same.

Where everything lives: the .git folder

A repository is just your project folder plus one hidden folder, .git. Delete .git and the history is gone, but your files stay. Copy .git elsewhere and you have the whole repository.

.git/
├── HEAD            which branch (or commit) you are on
├── config          local configuration
├── index           the staging area (binary file)
├── objects/        all blobs, trees, commits, tags
├── refs/
│   ├── heads/      one file per local branch
│   ├── remotes/    remote-tracking branches (Module 2)
│   └── tags/       tags
└── logs/           the reflog (Module 4)

Rule: never edit or delete files inside .git by hand

Use Git commands. Hand-editing .git is the fastest way to corrupt a repository. Also never run git init inside a folder that already sits inside another repository, or you create a nested repository.

Edge cases

  • Git stores each distinct content once, so a copied file costs almost nothing. It stores the content, not the file name — names live in trees.
  • Moving a file does not "record a move". Git simply sees one path disappear and another with identical content appear, and detects the rename when you ask (git log --follow, git diff -M).
  • Unreachable objects (for example commits left behind after a mistake) are not deleted immediately. Git keeps them for a while and cleans up later with garbage collection. This is what makes recovery possible (Module 4).
  • Git packs old objects together and stores them as compressed deltas inside pack files to save disk space. That is an internal storage optimisation. Conceptually, every commit is still a full snapshot.

Interview: "Does Git store diffs or snapshots? What is HEAD?"

  • Snapshots: each commit points to a tree describing the whole project; unchanged files reuse the same blob.
  • Objects are blob, tree, commit and tag, each named by a SHA hash of its content; the commit hash includes the parent hash, so history is tamper-evident.
  • A branch is a movable pointer to a commit; HEAD is a pointer to the current branch (or commit).
  • That is why branching is cheap and why committing just moves a pointer forward.

The three areas and the four file states

Changes travel from your working folder, to the staging area with git add, to the repository with git commit — and every file is always untracked, unmodified, modified or staged.

Beginners expect one step: change a file, save it to history. Git uses two steps, and that is what makes it powerful. The extra step lets you choose exactly which changes go into the next commit.

The three local areas

Working folder (working tree)
The real files on your disk, the ones you open in IntelliJ. You edit them freely.
Staging area (index)
A preparation zone, stored in .git/index. It holds the snapshot of what will go into the next commit. Think of it as the box you pack before you seal and ship it.
Repository (the .git folder)
The permanent history of commits. A commit is stored here only when you run git commit.

An everyday comparison: a Swiggy order. Choosing dishes is editing the working folder. Putting them in the cart is git add — you can still remove items. Paying is git commit — now it is recorded.

Why a staging area exists

Suppose you fixed a bug in PaymentService.java and, in the same hour, started a new feature in OrderController.java. You want two separate commits, each with a clear message. With a staging area you stage and commit the bug fix first, then the feature. Without it, Git could only commit "everything that changed". Even inside one file you can stage only some changes (git add -p, see git add variants).

The four file states

Every file in your folder is in exactly one of these states:

StateMeaningHow it gets here
UntrackedGit has never seen this file; it is not in any commit or in the staging areaYou create a new file
Unmodified (committed)The file matches the last commitAfter git commit, or right after a clone
ModifiedA tracked file changed but the change is not stagedYou edit and save a tracked file
StagedThe change is queued for the next commitgit add file

Tracked means "Git knows this file": it is in the last commit or in the staging area. Everything else is untracked (or ignored, see .gitignore).

Watching the states change

The command git status tells you the state of every file. Follow one file through its whole life:

Notice that git status itself tells you the next command to use. Read its hints.

The same file can be in two places at once

This surprises everybody once. If you stage a file and then edit it again, the staged version and the working version differ. git status lists the file twice:

$ git add README.md
$ echo "Runs on port 8080" >> README.md
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	modified:   README.md

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md

A commit now saves only the staged version. The last line you typed stays modified in the working folder until you git add it again.

Short status: git status -s

The short form prints one line per file with two status columns. The left column is the staging area compared to the last commit; the right column is the working folder compared to the staging area.

In the table, _ stands for a blank space; the real output has a space there. Quick rule: a letter in the left column means "ready to commit"; a letter in the right column means "not staged yet".

Tip: git status -sb

Add -b to also print the branch and its relation to the remote, for example ## main...origin/main [ahead 2].

Mistake: thinking git add is only for new files

Beginners edit a tracked file, run git commit -m "fix" and see no changes added to commit. Every change — new, edited or deleted — must be staged first. (The shortcut git commit -a stages modified and deleted tracked files for you, but never new ones.)

Edge cases

  • An empty folder never shows up as untracked — Git tracks files only.
  • If you change a file's permissions (executable bit), Git sees a change even if the content is the same.
  • A file that is listed in .gitignore but was already committed is still tracked, so it still shows up as modified (see .gitignore).

Interview: "Explain the working directory, staging area and repository."

  • Working directory: real files you edit. Staging area (index): the snapshot being prepared for the next commit. Repository: committed history in .git.
  • Commands: git add moves changes working → staging; git commit moves staging → repository.
  • Reason for staging: build commits deliberately, even from part of a file with git add -p.
  • Name the four file states: untracked, unmodified, modified, staged.

Start a repository: git init and git clone

Use git init to turn a folder you already have into a repository, and git clone <url> to copy an existing repository with its full history.

Every Git journey starts one of two ways. Either you have a project and want Git to track it (git init), or somebody already has a repository and you want a copy (git clone).

git init: create a new repository

$ mkdir java-practice
$ cd java-practice
$ git init
Initialized empty Git repository in C:/Users/asha/java-practice/.git/
$ git status
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)

git init creates the hidden .git folder and nothing else. It does not add or commit your files — you do that next. You can also give the folder name directly (git init java-practice), and choose the first branch name with git init -b main (or set init.defaultBranch once, see Install Git).

If you started a project with Spring Initializr or an IDE and now want Git, run git init in the project root — the folder that holds pom.xml — and create your .gitignore before the first git add ..

git clone: copy an existing repository

A clone gives you the complete repository: all files, all branches' history, plus a link back to where it came from. Git also checks out the default branch so you can start working.

$ git clone https://github.com/spring-projects/spring-petclinic.git
Cloning into 'spring-petclinic'...
remote: Enumerating objects: 9850, done.
remote: Total 9850 (delta 0), reused 0 (delta 0), pack-reused 9850
Receiving objects: 100% (9850/9850), 7.89 MiB | 6.12 MiB/s, done.
Resolving deltas: 100% (4021/4021), done.
$ cd spring-petclinic
$ git log --oneline -n 3

(The object counts and sizes above are only an illustration; yours will differ.) The clone is placed in a new folder named after the repository. To choose another folder name, add it at the end: git clone <url> my-folder.

What git clone does, step by step:

  1. Creates the folder and runs git init inside it.
  2. Adds a remote called origin that points to the URL you gave.
  3. Downloads all objects (the full history).
  4. Creates remote-tracking branches such as origin/main (Module 2).
  5. Creates a local branch for the remote's default branch, sets it to track origin/main, and checks it out.
$ git remote -v
origin  https://github.com/spring-projects/spring-petclinic.git (fetch)
origin  https://github.com/spring-projects/spring-petclinic.git (push)

Mistake: git init in the wrong folder

Running git init in your home folder (C:\Users\asha) makes your whole user profile a repository, and git status then lists thousands of files. Always cd into the project folder first. If it happened, delete the stray .git folder in the wrong place.

Exceptions and errors

  • fatal: not a git repository (or any of the parent directories): .git — you ran a Git command outside a repository. Check where you are with pwd.
  • fatal: destination path 'repo' already exists and is not an empty directory — the folder you are cloning into is not empty. Choose another name.
  • Reinitialized existing Git repository — running git init again is harmless; it does not erase anything.
  • fatal: repository '...' not found or Authentication failed — wrong URL, a private repository, or missing login (credentials).
  • Do not clone a repository inside another repository folder. Keep each project in its own folder, for example C:\dev\, and avoid cloning into OneDrive-synced folders, which can interfere with the many small files in .git.

Interview: "Difference between git init and git clone?"

  • init makes an empty repository from a local folder; clone copies an existing repository including full history and sets up origin.
  • Mention what a clone creates: a working copy, remote-tracking branches and a tracking local branch.
  • Add that a clone is a real, complete backup — you can clone from a clone.

Markdown and a clear README

A README.md is the front page of your repository, written in Markdown; it must say what the project does, how to run it, and how to use it — in the first minute a reader spends.

GitHub shows the file README.md under the file list of every repository. A recruiter or teammate decides in seconds whether your project is worth a look. A project with no README looks abandoned, however good the code is.

Markdown in ten minutes

Markdown is a plain-text format with simple symbols for headings, lists and links. GitHub, GitLab, Stack Overflow and many tools render it. Files end in .md.

You wantYou type
Headings# Title, ## Section, ### Sub-section
Bold, italic**bold**, *italic*
Inline codeA word wrapped in single backticks
Bulleted list- item (indent two or four spaces for a nested list)
Numbered list1. step
Task list- [ ] todo and - [x] done
Link[text](https://example.com)
Image![alt text](docs/screenshot.png)
Quote> quoted text
Horizontal line---
TableRows of | a | b | with a |---|---| line under the header

A code block starts and ends with three backticks; write the language after the opening fence for colour highlighting. Here is how a Markdown snippet looks in the source:

# Billing Service

A **Spring Boot** REST API that creates invoices.

## Features
- [x] Create and fetch invoices
- [ ] Send invoice by email

## Run it
```bash
./mvnw spring-boot:run
```

| Endpoint | Method | Purpose |
|----------|--------|---------|
| /api/invoices | POST | Create an invoice |
| /api/invoices/{id} | GET | Fetch one invoice |

> Note: needs Java 21 and PostgreSQL 16.
  • Leave a blank line between paragraphs, before and after lists, and around code fences.
  • Use relative paths for files inside the repository (docs/screenshot.png) so links work on every branch and fork.
  • To show a literal backtick or special character, escape with a backslash: \*.
  • GitHub also supports Mermaid diagrams in fenced blocks marked mermaid, emoji codes, and automatic links for issue numbers (#12) and @username mentions.

Badges

A badge is a small image link, typically showing build status or licence. GitHub Actions can give you a build badge from the workflow page; services like shields.io generate others. Keep to two or three useful ones.

![Build](https://github.com/asha-rao/billing-service/actions/workflows/ci.yml/badge.svg)

What a good README contains

  1. Title and one-line description — what is this and who is it for?
  2. Screenshot or demo GIF — for a UI project, this sells the project instantly. For an API, show a sample request and response.
  3. Tech stack — Java 21, Spring Boot, PostgreSQL, React, Docker.
  4. Features — a short list.
  5. Architecture — a small diagram or a few lines about layers.
  6. Getting started — prerequisites and exact commands to run it. Test them on a clean clone.
  7. Configuration / environment variables — a table of names, purpose and example values (never real secrets).
  8. API documentation — endpoints or a link to Swagger UI.
  9. Tests — how to run them.
  10. Live demo link and licence.

Swagger UI note

The Swagger UI path and dependency depend on the library you use (for example springdoc-openapi) and its version. Write the path that works for your project, and see Spring Boot · Module 2 for REST API documentation.

Profile README

Create a public repository whose name is exactly your username (for example asha-rao/asha-rao) and add a README.md. GitHub displays it at the top of your profile. Keep it short: who you are, what you are learning, your stack, links to two or three pinned projects, and how to reach you. No walls of badges.

Conventions

  • The file is named README.md in the repository root (GitHub also shows one inside .github/ or docs/, root wins).
  • Write for a stranger who has never seen the project. Give exact commands, not "run the app".
  • Keep it current: a README that describes last year's setup is worse than none.
  • Put long guides in a docs/ folder and link them.
  • Use relative links for images and files inside the repository.

Common mistakes

  • Only the project name and nothing else.
  • Commands that only work on your laptop (C:\Users\asha\... paths).
  • Putting real passwords, tokens or private URLs in the README or in the example config.
  • Screenshots saved as huge files, or images that live outside the repository and break later.
  • Skipping a blank line before a list or a table, so it renders as plain text.

Fork vs clone, and contributing to open source

Clone copies a repository to your computer; fork copies it to your own GitHub account first, so you can propose changes to a project you cannot push to by opening a pull request.

Two different things

PointCloneFork
What it isA Git operation: copy a repository to your diskA GitHub feature: copy a repository to your GitHub account
Where the copy livesYour computerYour GitHub account (a new remote repository)
Link to originalorigin points to the originalGitHub remembers the parent, shows "forked from", and can open pull requests to it
Can you push?Only if you have write access to the originalAlways, to your own fork
Use forYour own repository or your team's repositoryContributing to a project you do not own

They are often combined: you fork on GitHub, then clone your fork to your laptop.

Rule of thumb: if you can push to the repository (your own, or your company's), just clone it and work in branches. If you cannot (someone else's open-source project), fork it first.

The open-source contribution flow

  1. Fork. Click Fork on the project's GitHub page. You now own asha-rao/project.
  2. Clone your fork (not the original): 
    $ git clone git@github.com:asha-rao/project.git
$ cd project
  3. Add the original as upstream. 
    $ git remote add upstream https://github.com/original-owner/project.git
$ git remote -v
origin    git@github.com:asha-rao/project.git (fetch)
origin    git@github.com:asha-rao/project.git (push)
upstream  https://github.com/original-owner/project.git (fetch)
upstream  https://github.com/original-owner/project.git (push)
  4. Read the rules. Open CONTRIBUTING.md and the issue list. Look for issues labelled good first issue. Comment on the issue before you start a large piece of work.
  5. Create a branch for the change: git switch -c fix-readme-typo (branches are covered in Module 3).
  6. Edit, test and commit with a clear message that follows the project's style.
  7. Push to your fork: git push -u origin fix-readme-typo.
  8. Open a pull request. GitHub shows a banner "Compare & pull request". Write what you changed and why, and link the issue (Fixes #123).
  9. Respond to review. Push more commits to the same branch; the pull request updates by itself. Be polite and patient.

Keep your fork up to date

The original project keeps moving, but your fork does not follow automatically. Sync it before starting new work.

$ git switch main
$ git fetch upstream
$ git merge upstream/main          # or: git rebase upstream/main
$ git push origin main

Or use the web way: on your fork's page click Sync fork → Update branch, then git pull locally. Keep your fork's main identical to upstream and do your own work on branches, so the sync never conflicts.

Tip: fast-forward only

Use git merge --ff-only upstream/main for the sync. It fails if your main has stray commits, which is a useful warning that you committed on the wrong branch.

Your first open-source contribution

Start with documentation: fix a typo, clarify an unclear paragraph, correct a broken link. These changes are small, easy to review and welcome, and they teach you the whole fork-to-pull-request flow without risk. Search GitHub for the label good first issue or documentation. Then move to tests, small bug fixes and finally features.

Conventions

  • Never commit directly on your fork's main; work on a branch per change.
  • One pull request = one change. Keep it small.
  • Follow the project's code style, commit message rules, and licence/CLA requirements.
  • Naming: origin = your fork, upstream = the original.

Edge cases

  • If you have write access to a repository (a teammate in your company), you do not need a fork; branches in the same repository are simpler. Some companies still use forks for strict permission control.
  • Private repositories can be forked only if the owner's settings and plan allow it.
  • Forking a repository you already forked does not create a second copy; GitHub takes you to your existing fork.
  • Deleting the fork does not harm the original. Deleting the original does not delete forks of public repositories.
  • Pull request commits stay in the pull request even if you later delete the branch locally.

Interview: "Fork vs clone? How do you contribute to open source?"

  • Clone = Git copy to your machine. Fork = GitHub copy under your account, needed when you cannot push to the original.
  • Flow: fork, clone your fork, add upstream, branch, commit, push to your fork, open a pull request.
  • Keep in sync with git fetch upstream and merge or rebase, or GitHub's Sync fork button.

Clone options and private repositories

Use git clone --depth 1 for a fast, small copy, -b branch to start on a specific branch, and make sure your login can see a private repository before you clone it.

The options

CommandEffect
git clone <url>Full copy; checks out the default branch
git clone <url> folder-nameClone into a folder with another name
git clone -b develop <url>Check out the develop branch after cloning (all branches are still downloaded)
git clone --single-branch -b develop <url>Download only that branch's history
git clone --depth 1 <url>Shallow clone: only the latest commit, no older history
git clone --branch v1.2.0 --depth 1 <url>A tag or branch, shallow
git clone --recurse-submodules <url>Also fetch submodules (repositories nested inside)
 
$ git clone --depth 1 https://github.com/spring-projects/spring-boot.git
$ cd spring-boot
$ git log --oneline
b3c4d5e (grafted, HEAD -> main, origin/main) Latest commit message

Use a shallow clone when you only need the current code: a quick look at a project, a CI build, a Docker image build. A full clone is better for real development, because git log, blame and bisect need history. You can fetch the missing history later with git fetch --unshallow. A related option, --filter=blob:none, makes a "partial clone" that downloads file contents on demand; it is useful for very large repositories.

Cloning a private repository

  • You must have access: be the owner, a collaborator, or a member of the organisation with read permission. Otherwise GitHub answers Repository not found (it hides private repositories from people without access).
  • HTTPS: Git Credential Manager opens the browser login the first time, or you give a token that includes access to that repository (HTTPS login). Organisations that use SAML single sign-on require you to authorise the token or key for that organisation in GitHub settings.
  • SSH: your key must be added to your GitHub account (SSH key); then clone with git@github.com:org/repo.git.
  • Deploy keys are SSH keys attached to one repository (read-only by default) — used by servers that need to pull code, not by people.
$ git clone git@github.com:acme-corp/payments-service.git
Cloning into 'payments-service'...
remote: Enumerating objects: 4120, done.
Receiving objects: 100% (4120/4120), 3.02 MiB | 5.10 MiB/s, done.

Errors and edge cases

  • fatal: Authentication failed or Permission denied (publickey) — see the login articles. Confirm with ssh -T git@github.com.
  • A shallow clone limits commands: you cannot see old history, and pushing is possible but merging with deep history can be awkward until you --unshallow.
  • Very long paths can fail to check out on Windows. If you see "Filename too long", enable git config --global core.longpaths true and clone to a short folder such as C:\dev.
  • Cloning into an OneDrive-synced folder can slow Git and sometimes corrupt files; use a local folder outside synced paths.

Visibility, LICENSE and the .github folder

A repository is public or private; a public project needs a LICENSE file so others know what they may do with it; and a .github folder holds templates and workflows that GitHub reads automatically.

Public or private

PointPublicPrivate
Who can read itAnyone on the internetOnly people you invite
Good forPortfolio, open source, learning projectsCompany code, unfinished work, anything with business data
Searchable by botsYes, quicklyNo

Change it later in Settings → General → Danger Zone → Change visibility. Making a private repository public exposes the whole history, including old secrets and deleted files. Check history before you flip the switch. Your own learning projects should be public and clean; company code stays private.

Licences

Code with no licence is, legally, all rights reserved: others can read it on GitHub but may not copy, change or reuse it. Add a licence file named LICENSE to say what is allowed. GitHub can add one when you create the repository (Choose a license). Common choices:

LicenceWhat it allowsCondition
MITUse, copy, modify, sell — almost anythingKeep the copyright and licence text
Apache 2.0Like MIT, plus an explicit patent grantKeep notices; state changes
GPL 3.0Use and modifyDerived work you distribute must also be GPL (a "copyleft" licence)
BSD 2/3-clauseSimilar to MITKeep the notice

For a personal portfolio project, MIT is the usual simple choice. For code you reuse, check its licence first: you must follow it. This is general information, not legal advice; for company code the legal team decides.

The .github folder

GitHub looks for special files inside a folder named .github at the repository root.

.github/
├── workflows/
│   └── ci.yml                    GitHub Actions pipelines (see DevOps)
├── PULL_REQUEST_TEMPLATE.md      pre-filled text for every new pull request
├── ISSUE_TEMPLATE/
│   └── bug_report.md             templates for new issues
├── CODEOWNERS                    who must review which files
└── dependabot.yml                automatic dependency update pull requests
  • Workflows run automatically on pushes and pull requests: build, test, deploy. Learn them in DevOps · Module 4.
  • Pull request template reminds contributors to describe changes and tick a checklist; pull requests themselves are in Module 3.
  • CODEOWNERS assigns reviewers automatically; combined with branch protection it enforces review rules (Module 4).
  • Other community files that GitHub recognises: CONTRIBUTING.md (how to contribute), CODE_OF_CONDUCT.md, SECURITY.md (how to report vulnerabilities).

Other settings worth knowing

  • Collaborators (Settings → Collaborators) — give a teammate read, write or admin access.
  • Default branch — the branch GitHub shows and uses for new pull requests (normally main).
  • Branch protection rules — block direct pushes and require reviews; see Module 3.
  • Secret scanning and push protection — GitHub can warn or block when a commit contains a recognisable token.
  • Releases and tags — mark versions such as v1.0.0 (Module 4).

Edge cases

  • Deleting a repository on GitHub is permanent after you confirm; GitHub may let you restore it for a short time, but do not rely on it. Keep a clone.
  • Renaming a repository redirects old URLs for a while, but update your remotes with git remote set-url.
  • A repository's visibility does not change who can see your commits' email address: avoid personal emails (noreply address).

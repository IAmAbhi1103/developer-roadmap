Undo safely: restore, restore --staged and commit --amend

Discard working changes with git restore file, unstage with git restore --staged file, and fix the last commit with git commit --amend — all before you push.

Everybody makes mistakes: you edit the wrong file, stage too much, or misspell a commit message. Git makes most mistakes fixable, but the right command depends on where the mistake is: working folder, staging area, or the last commit. This article covers the safe commands. Dangerous ones (reset --hard, force push, rebase) are in Module 4.

1. Discard changes in the working folder

$ git status -s
 M src/main/java/InvoiceService.java
$ git restore src/main/java/InvoiceService.java
$ git status -s
$

git restore <file> copies the version from the staging area (or from the last commit, if nothing is staged) back into the working folder. Your edits are gone — Git never saw them, so Git cannot bring them back. Check with git diff first when unsure. Restore a whole folder with git restore src/; restore everything with git restore ..

Mistake: restoring work you wanted to keep

Uncommitted changes that were never staged or committed are the one thing Git cannot recover. If you are not sure, git stash (Module 3) or make a temporary commit first.

2. Unstage a file

$ git add .
$ git status -s
M  pom.xml
A  scratch.txt
$ git restore --staged scratch.txt
$ git status -s
M  pom.xml
?? scratch.txt

--staged makes the command act on the staging area instead of the working folder: it resets the staged version to match the last commit, and your edits stay in the folder. It is the exact opposite of git add. To change both areas at once, use git restore --staged --worktree <file>. In a repository with no commits yet, git restore --staged fails; use git rm --cached <file> there.

3. Fix the last commit: git commit --amend

--amend replaces the latest commit with a new one. Use it for a typo in the message, or a file you forgot.

$ git commit -m "Add invoce total"
[main 2c8a1be] Add invoce total
$ git commit --amend -m "Add invoice total"
[main 9f1d3a7] Add invoice total
 Date: Mon Nov 9 19:05:44 2026 +0530
$ git commit -m "Add Coupon entity and repository"
$ git add src/main/java/CouponRepository.java
$ git commit --amend --no-edit
[main 4e6b8c2] Add Coupon entity and repository
 2 files changed, 41 insertions(+)

Notice the hash changed from 2c8a1be to 9f1d3a7. The old commit was not edited — Git made a new commit with a new hash (a commit's hash includes its message and content, see How Git stores your work) and moved the branch to it. --no-edit keeps the old message. Running git commit --amend with nothing staged and no -m opens the editor to change just the message.

Why amend is fine before push and dangerous after

Rule: amend only commits you have not pushed

Amend rewrites history: the old commit is replaced by a different one. If the old commit is only on your computer, nobody else is affected. If you already pushed it, teammates may have built work on the old hash. Your next push is rejected as a non-fast-forward; forcing it over their work creates duplicate commits and conflicts for everyone. For pushed commits use git revert, or, on your own feature branch only, a force push with care (Module 4, and Push rejected).

The older commands: checkout -- file

Before Git 2.23 (2019) the same jobs were done by git checkout, which also switches branches — one command with two very different meanings. Git added git restore and git switch to split them. You will still see the old forms in tutorials and old scripts:

Old formModern formJob
git checkout -- filegit restore fileDiscard working changes
git reset HEAD filegit restore --staged fileUnstage
git checkout <commit> -- filegit restore --source=<commit> fileFile from another commit
git checkout maingit switch mainChange branch (Module 3)

Getting an old version of a file

$ git log --oneline -- src/main/java/InvoiceService.java
8d41b7e Fix rounding error in order total
3f2a9c1 Add GST calculation to order total
$ git restore --source=3f2a9c1 src/main/java/InvoiceService.java
$ git status -s
 M src/main/java/InvoiceService.java

The old version arrives as an ordinary modification. Review it with git diff, then stage and commit — or restore it again.

Edge cases and errors

  • error: pathspec 'x' did not match any file(s) known to git — the path is wrong or the file is untracked. git restore cannot touch untracked files; delete them by hand or with git clean.
  • If you deleted a tracked file in your folder, git restore <file> brings it back from the staging area or last commit.
  • git restore --staged on a file staged for deletion makes it unstaged-deleted; run git restore on it again to bring the file back.
  • Amending during a merge or a rebase has special rules; finish the operation first.
  • git clean -f deletes untracked files for good. Always preview with git clean -n; add -d for folders.

Tip: when something looks very wrong, stop and check

Run git status and git log --oneline -5. Git almost never loses committed work. Even after a wrong amend, the previous commit still exists for a while and the reflog can find it (Module 4). Panic and random commands cause more damage than the first mistake.

Interview: "How do you undo changes in Git?"

  • Say where the change is: working folder → git restore file; staged → git restore --staged file; last commit → git commit --amend.
  • Warn that discarding unstaged edits is permanent, and that amend rewrites history, so it is only for unpushed commits.
  • For pushed commits, use git revert, which adds a new commit instead of rewriting history.
  • Mention that git restore/git switch replaced the overloaded git checkout in Git 2.23.

Interview questions — Daily Git basics

What is Git, and how is it different from GitHub?

Git is a distributed version control system that runs on your computer and records the history of your files. GitHub is a website that hosts Git repositories and adds pull requests, issues, code review and automation. You can use Git without GitHub (local use, GitLab, Bitbucket, your own server), but not GitHub without Git.

What does "distributed" mean in a version control system?

Every clone holds the full repository, including the whole history. You can commit, view logs, diff and branch offline. A central server such as GitHub is a convenient shared copy, not the only copy. In a centralized system (SVN) the history lives only on the server.

Explain the working directory, staging area and repository.

The working directory holds the files you edit. The staging area (index) holds the snapshot being prepared for the next commit. The repository (.git) holds the committed history. git add moves changes from the first to the second; git commit moves them from the second to the third. The staging area lets you build clean, focused commits, even from part of a file with git add -p.

Does Git store snapshots or differences?

Snapshots. Each commit points to a tree that describes the whole project at that moment; unchanged files point to the same stored blob, so nothing is duplicated. Differences are calculated when you run git diff. Internally Git compresses objects into pack files with deltas for disk space, but that is only storage optimisation.

What is a commit hash, and why does it change when you amend a commit?

A SHA hash computed from the commit's content: its tree, parent hash(es), author, date and message. Because the hash depends on all of these, changing anything — even the message — produces a new hash. That makes a commit and its history tamper-evident, and it is why amend and rebase "rewrite history": they create new commits.

What are HEAD, HEAD~1 and HEAD^?

HEAD points to the current commit, usually through the current branch name. HEAD~1 and HEAD^ both mean its first parent, one commit back. HEAD~3 goes three commits back; HEAD^2 selects the second parent of a merge commit.

What is the difference between git add ., git add -A and git add -u?

git add -u stages modifications and deletions of already tracked files only. git add -A also stages new files, across the whole repository. git add . does the same as -A for the current directory and everything below it. Before committing, review with git status and git diff --staged.

I edited a file, ran git add, and now git diff shows nothing. Why?

git diff compares the working folder with the staging area. After git add both are equal, so there is no difference. Use git diff --staged to see what is staged for the next commit, or git diff HEAD to see all changes since the last commit.

How do you write a good commit message?

A subject of about 50 characters in the imperative mood ("Fix null pointer in cart"), a blank line, then a body that explains why the change was made, plus a ticket reference if the team uses one. Keep each commit to one logical change that builds and passes tests.

I added .env to .gitignore but git status still shows it as modified. What is wrong?

The file was committed earlier, so it is tracked, and .gitignore only affects untracked files. Run git rm --cached .env and commit; the file stays on your disk but leaves the repository. Because it is still in old commits, rotate any secret it contained.

How do you undo each of these: unstaged edits, a staged file, the last commit message?

Unstaged edits: git restore <file> (permanent). Staged file: git restore --staged <file> (edits stay). Last commit message or a forgotten file: git commit --amend, only if the commit is not pushed. For a pushed commit use git revert.

What does git commit -am "msg" do, and what does it miss?

It stages every modified and deleted tracked file and commits in one step. It does not include new untracked files. It also skips the chance to review what is staged, so check with git status and git diff first.

What are the Git config levels, and which one wins?

System (all users on the machine), global (~/.gitconfig, your user) and local (.git/config, one repository). The most specific wins: local over global over system. git config --list --show-origin shows the value and the file each setting comes from.

Why does Git not track an empty folder, and how do you keep one?

Git stores file content in trees; a tree needs at least one file to have an entry. To keep an empty directory, put a placeholder file in it, conventionally named .gitkeep.

Cheat sheet — Daily Git basics

  • git --version check the installed Git version
  • git config --global user.name "Name" and user.email "mail" set your identity once
  • git config --list --show-origin show every setting and the file it comes from
  • git config --global init.defaultBranch main new repos start on main
  • git init make the current folder a repository; git clone <url> copy a repository with history
  • Three areas working folder → (git add) → staging area → (git commit) → repository
  • File states untracked, unmodified, modified, staged
  • git status / git status -s what is changed, staged or untracked (?? new, M_ staged, _M not staged)
  • git add file, git add ., git add -A, git add -u, git add -p stage whole files, everything, tracked only, or chosen hunks
  • git commit -m "msg" save the staged snapshot; -am also stages tracked changes first
  • git log --oneline --graph --all compact history of all branches
  • git log -p / --stat / -n 5 / --author / --since / --grep / -S"text" show patches, file stats, limit, or filter history
  • git show <commit> one commit with its diff; git show <commit>:path a file as it was then
  • git diff unstaged changes; git diff --staged what the next commit will contain; git diff HEAD both
  • HEAD~1 / HEAD^ the parent of HEAD; HEAD~3 three commits back
  • git rm file delete and stage; git rm --cached file stop tracking, keep on disk; git mv old new rename
  • .gitignore patterns: *.log, target/ (dir at any depth), /target (root only), **/logs, !keep.txt (negation)
  • git check-ignore -v path tells which rule ignores a path
  • Already tracked file in .gitignore? git rm --cached file then commit
  • git restore file discard working changes (permanent); git restore --staged file unstage
  • git commit --amend fix the last commit (message or forgotten file); only before push
  • git checkout -- file is the old form of git restore file
  • Commit message imperative subject ≤ 50 chars, blank line, body explains why
  • Never commit secrets, .env, build output (target/), IDE folders; rotate any secret that leaked

Practice — Daily Git basics

  1. Set up (easy). Install Git, set user.name, user.email and init.defaultBranch main, and run git config --list --show-origin. Done when you can point to the file each of your three settings comes from.
  2. First repository (easy). Create a folder java-practice, run git init, add a README.md and Hello.java, and make your first commit. Done when git log --oneline shows one commit and git status says the working tree is clean.
  3. Five small commits (easy). Make five small, separate changes to the project (for example a new class, a bug fix, a README line, a rename with git mv, a new test) with a clear imperative message each. Done when git log --oneline --graph reads like a story and every message is under 50 characters.
  4. Watch the states (easy). Create a file, then run git status -s after each step: create, git add, edit again, git commit. Write down the code you saw each time (??, A_, AM). Done when you can predict each code before running the command.
  5. Partial staging (medium). Change two unrelated places in one file. Use git add -p to commit them separately. Done when git log -p -n 2 shows one change per commit.
  6. Java .gitignore (medium). Add a .gitignore for Java/Maven/IntelliJ (use the template in this module). Create a target/ folder and a .env file. Done when git status shows neither, and git check-ignore -v .env prints your rule.
  7. Untrack a mistake (medium). Commit a file secrets.txt on purpose, then add it to .gitignore and stop tracking it without deleting it. Done when the file is still on disk, is not in git ls-files, and git status is clean. Note why the old commit still contains it.
  8. Undo drill (medium). (a) Edit a file and discard the change with git restore. (b) Stage a file and unstage it with git restore --staged. (c) Make a commit with a typo in the message and fix it with --amend. (d) Forget a file, then add it to the last commit with --amend --no-edit. Done when each case ends with a clean git status and a changed hash after (c) and (d).
  9. History detective (hard). Clone any open-source Java repository. Find the commit that introduced a given string with git log -S, show that commit with git show, list the five most recent commits by one author, and view a file as it was ten commits ago. Done when you can explain each commit you found.
  10. Line endings (hard). Add a .gitattributes with * text=auto and *.sh text eol=lf. Create a run.sh, commit it, and verify with git ls-files --eol that it is stored as LF. Done when you can explain why the setting belongs in the repository and not only in core.autocrlf.

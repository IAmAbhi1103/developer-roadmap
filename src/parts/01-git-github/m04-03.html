Tags and releases with semantic versions

A tag is a permanent name for one commit, used to mark releases such as v1.2.0; use annotated tags (git tag -a), push them explicitly, and number them with SemVer (MAJOR.MINOR.PATCH).

A branch moves forward with every commit. A tag does not: it is a fixed label stuck to one commit. When you release version 1.2.0 of your CRM, you tag the exact commit that was built and deployed. Months later you can still check out v1.2.0, compare it with v1.3.0 or rebuild the old version for a customer.

Semantic versioning (SemVer)

Semantic Versioning gives the numbers a meaning. A version is MAJOR.MINOR.PATCH:

PartIncrease it when…Example
MAJORYou make an incompatible (breaking) change to the public API1.4.2 → 2.0.0
MINORYou add functionality in a backward-compatible way1.4.2 → 1.5.0
PATCHYou make backward-compatible bug fixes only1.4.2 → 1.4.3
  • When you raise MAJOR, MINOR and PATCH reset to 0; when you raise MINOR, PATCH resets to 0.
  • Pre-release versions add a hyphen: 2.0.0-alpha.1, 2.0.0-beta.2, 2.0.0-rc.1. They rank below the final 2.0.0.
  • Build metadata adds a plus sign and does not affect ordering: 1.2.0+build.45.
  • Versions 0.y.z mean "initial development": anything may change. Version 1.0.0 declares the public API stable.
  • Versions are compared as numbers: 1.10.0 is newer than 1.9.0.

The Git tag usually adds a v in front: tag v1.2.0 for version 1.2.0. Match it with the version in your pom.xml (Maven uses 1.2.0-SNAPSHOT for work in progress and 1.2.0 for a release) or build.gradle.

GitHub Releases

A GitHub Release is a page built on a tag: a title, release notes and downloadable files (a JAR, a ZIP, checksums). Create it under Releases → Draft a new release: choose or create the tag, press Generate release notes (GitHub lists merged PRs and contributors since the last release), edit, tick pre-release if needed, attach files and publish. With the optional GitHub CLI: gh release create v1.2.0 --generate-notes.

Good release notes group changes (Features, Fixes, Breaking changes) and say what users must do to upgrade. With Conventional Commits and labelled PRs this is mostly automatic. A GitHub Actions workflow can run when a tag is pushed, build the JAR or Docker image and publish it (DevOps · Module 4).

Rules

  • Tag releases with annotated tags and v-prefixed SemVer names.
  • Tags are not pushed automatically; push them.
  • Never move or reuse a published tag. If 1.2.0 has a bug, release 1.2.1.

Edge cases

  • Moving a tag (git tag -f) is possible but others who already fetched the old one will not get the new one. Treat tags as immutable.
  • A tag and a branch can share a name, which confuses commands (warning: refname 'v1' is ambiguous). Keep the names different.
  • Squash-merged PRs make tagging easy: tag the merge commit on main.

Mistake: tagging but forgetting to push

You create v1.2.0, the CI or the release page does not see it, because the tag exists only on your laptop. Run git push origin v1.2.0 and check on GitHub under Tags.

Interview: "What is a Git tag? What is semantic versioning?"

  • A tag is a fixed name for a commit, used for releases; branches move, tags do not. Annotated tags carry author, date and message.
  • Tags must be pushed explicitly.
  • SemVer: MAJOR for breaking changes, MINOR for new compatible features, PATCH for bug fixes; pre-release suffixes like -rc.1.

More professional tools: bisect, blame, clean, log -S, worktree, hooks and more

These smaller tools solve real problems: bisect finds the commit that broke something, blame and log -S find who changed what and when, clean removes untracked files, and hooks, LFS, .gitattributes and signed commits keep a team's repository healthy.

git bisect: find the commit that introduced a bug

A test passed last month and fails today. Between then and now there are 200 commits. Bisect does a binary search: you mark one commit good and one bad, Git checks out the middle commit, you test it, and in about eight steps (200 commits need log₂(200) ≈ 8) it finds the first bad commit.

$ git bisect start
$ git bisect bad                    # the current commit is broken
$ git bisect good v1.1.0            # this tag was fine
Bisecting: 99 revisions left to test after this (roughly 7 steps)
[4b7e1a2...] Add order filters
$ ./mvnw -q test                    # test this commit
$ git bisect good                   # or: git bisect bad
Bisecting: 49 revisions left to test after this (roughly 6 steps)
...
9c2d7b1e... is the first bad commit
commit 9c2d7b1e...
    Refactor tax calculation
$ git bisect reset                  # return to where you started

To automate it, give Git a command that exits with 0 for good and non-zero for bad: git bisect run ./mvnw -q test. Small, atomic commits make bisect very effective (one reason not to squash everything on your own branch before merge).

git blame and git log -S: who changed this and when

$ git blame -L 10,14 src/main/java/com/acme/crm/PriceCalculator.java
9c2d7b1e (Asha Rao 2026-10-02 10) public long total(long amount) {
9c2d7b1e (Asha Rao 2026-10-02 11)     long discounted = amount - amount * DISCOUNT_PERCENT / 100;
3b8a6e00 (Ravi K.   2026-09-11 12)     return Math.round(discounted * (1 + GST_PERCENT / 100.0));
$ git show 9c2d7b1e                 # see the whole commit, with its message

blame shows, for each line, the last commit that changed it. It is a tool for finding context ("why was this written?"), not for blaming people. Useful options: -L start,end for a range, -w to ignore whitespace changes. If a huge formatting commit hides the real author, list it in a file and use git blame --ignore-revs-file .git-blame-ignore-revs (GitHub also reads a file with that name).

To find when a piece of text was added or removed, use the pickaxe search:

git log -S"GST_PERCENT" --oneline          # commits that added or removed this exact string
git log -G"discount.*PERCENT" --oneline    # commits whose diff matches a regex
git log -p -- src/main/java/com/acme/crm/PriceCalculator.java   # history of one file with diffs
git log --follow -- src/main/java/com/acme/crm/Tax.java         # follow renames
git log --author="Asha" --since="2 weeks ago" --oneline

git clean: remove untracked files

git clean deletes files that Git does not track (build output, leftover files). Deleted files do not go to a recycle bin, so always preview first:

$ git clean -n                      # dry run: only shows what would be removed
Would remove notes.txt
$ git clean -nd                     # include untracked directories
$ git clean -fd                     # really delete untracked files and directories
$ git clean -fdx                    # also delete ignored files (target/, .env!) - dangerous
Removing notes.txt

-x deletes ignored files too, including a local .env or IDE settings you wanted. A safer way to clean a Maven project is ./mvnw clean.

git worktree (brief)

A worktree checks out a second branch in a second folder from the same repository, so you can fix a hotfix without stashing or switching:

git worktree add ../crm-hotfix hotfix/null-cart   # new folder with that branch
git worktree list
git worktree remove ../crm-hotfix                 # when done

A branch can be checked out in only one worktree at a time.

.gitattributes (brief)

This file in the repository root tells Git how to treat files. The most common use is making line endings consistent between Windows (CRLF) and Linux/macOS (LF):

# normalise text files; checkout converts to the platform's line ending
* text=auto
# shell scripts must always keep LF, or they fail on Linux
*.sh text eol=lf
# treat these as binary: no diff, no line-ending change
*.png binary
*.jar binary

Git LFS (brief)

Git stores every version of every file forever, so big binary files (videos, design files, datasets) make a repository huge. Git LFS (Large File Storage) is an extension that stores such files on a separate server and keeps only small pointer files in Git. It is installed separately (git lfs install once), then you choose patterns: git lfs track "*.psd", which writes a rule into .gitattributes. Commit that file and the large files behave normally. GitHub limits the size of normal files and LFS storage has quotas; do not put build output or dependencies in Git at all.

Git hooks and pre-commit checks (brief)

A hook is a script that Git runs at a certain moment. Hooks live in .git/hooks/ and are named after the event: pre-commit (before a commit is created), commit-msg (check the message), pre-push (before pushing). If the script exits with a non-zero status, Git stops the operation.

#!/bin/sh
# Block the commit if the code is not formatted
./mvnw -q spotless:check || {
    echo "Run ./mvnw spotless:apply and commit again"
    exit 1
}

The .git folder is not shared when others clone the repository, so hooks are not shared either. Teams share hooks in a tracked folder and run git config core.hooksPath .githooks, or use tools: Husky (JavaScript projects), the pre-commit framework, or Lefthook. You can skip hooks once with git commit --no-verify, so CI must run the same checks too — hooks are a convenience, CI is the guarantee.

Signed commits (brief)

Anyone can set user.name and user.email to any value, so commit authorship can be faked. Signing a commit proves it came from the holder of a key. GitHub then shows a green Verified badge. Many organisations require it.

git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true      # sign every commit
git commit -S -m "feat: add login endpoint"  # or sign one commit
git log --show-signature -1

You also add the same public key to GitHub as a signing key (a separate setting from your login key). GPG keys work too, and Git supports signing with SSH keys from version 2.34.

Rules

  • Run git clean -n before git clean -f. Deleted untracked files cannot be recovered.
  • Hooks are local. Repeat every important check in CI.
  • Do not commit large binaries or secrets; use LFS or an artifact store, and use environment variables or a secret manager for secrets.

Tip: aliases for your favourite commands

For example git config --global alias.lg "log --oneline --graph --decorate --all" makes git lg a short command for a nice graph.

Interview: "How would you find which commit introduced a bug?"

  • Use git bisect: mark a known bad and a known good commit, test the commits Git offers (or automate with bisect run), and it finds the first bad commit by binary search in O(log n) steps.
  • Then git show the commit, and use git blame or git log -S to understand the context.

Disaster recovery playbook: fixing common Git mistakes

Most Git mistakes can be fixed: stop, run git status and git reflog, then pick the right recovery from the table — and if you pushed a secret, rotate the secret first.

Everyone makes these mistakes. The difference between a junior and a senior is not that the senior never makes them, but that the senior stays calm and knows the way out. First, the general procedure:

  1. Stop. Do not run more commands in panic; each can make recovery harder.
  2. Look. git status, git log --oneline --graph --all -10 and git reflog.
  3. Make a safety branch if you have commits worth keeping: git branch rescue.
  4. Check whether it is pushed. Local-only mistakes can be rewritten. Pushed ones need revert (or a coordinated force push).
  5. Fix with the smallest tool (table below), then verify.

Committed to the wrong branch

You are on main and made two commits that belong on a new feature branch. Nothing is pushed yet.

$ git branch --show-current
main
$ git branch feature/cancel            # new branch right here, with your two commits
$ git reset --hard origin/main         # move main back to the remote's state
HEAD is now at e8a4c10 Update Swagger docs
$ git switch feature/cancel            # your commits are safe here
$ git log --oneline -3

Order matters: create the branch first, then reset. Check git status is clean before the hard reset. Alternatively, switch to the right branch and cherry-pick the commits, then reset main.

You pushed a secret

A database password or API key is now on GitHub. The order of actions is important:

  1. Rotate the secret immediately. Revoke the old key or change the password at the provider (cloud console, payment gateway, database). Assume it was copied: bots scan public GitHub within minutes, and even private repositories have many readers. This step is the real fix.
  2. Check the provider's logs for misuse during the exposure.
  3. Remove the secret from the code and use an environment variable or a secret manager; add the file (.env) to .gitignore.
  4. Optionally clean the history so the old value does not stay visible. Use git filter-repo (a separate tool, the replacement for the old git filter-branch) or BFG Repo-Cleaner, then force push, and ask everyone to re-clone. Forks, clones, PR refs and caches may still hold the old data, so this does not make the secret safe — which is why step 1 comes first.
  5. Turn on GitHub secret scanning and push protection to block such pushes in the future.

Mistake: deleting the file and thinking the secret is gone

A new commit that removes the secret does not remove it from history: anyone can open the old commit. Only rotating the secret makes it harmless.

Bad commit or merge already on main

git switch main
git pull --ff-only
git revert b21f7d9                  # a normal commit
git revert -m 1 0448514             # a merge commit
git push                            # or open a PR if main is protected

Tell the team in the chat. After the incident is over, fix the root problem on a branch and send it through a new PR. If you really must force-push a shared branch, agree with the team first, use --force-with-lease, and tell everyone to git fetch and reset their local copy.

Rules

  • Before anything destructive, check git status and make a rescue branch.
  • Shared history is never rewritten without agreement; use revert.
  • A leaked secret is always rotated, whatever you do to the history.

Prevention

  • Protect main so nobody can push or force-push to it.
  • Keep .gitignore current (.env, target/, node_modules/, IDE folders).
  • Use git add -p and look at git diff --staged before every commit.
  • Use secret scanning and a pre-commit secret check.

Interview: "You pushed a password to GitHub. What do you do?"

  • Rotate or revoke the credential immediately; check logs for abuse.
  • Remove it from the code, move to environment variables or a secret manager.
  • Optionally rewrite history with git filter-repo or BFG and force push, knowing it is only cosmetic because the secret may already be copied.
  • Enable secret scanning and push protection; tell the security team if your company requires it.

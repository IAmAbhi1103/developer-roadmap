In Module 1 and Module 2 you worked alone: commit on one line of history, push to GitHub. Real teams cannot work like that. Five people change the same project at the same time, and nobody wants a half-finished login page to break the code that is already live. The answer is branches — separate lines of work that you create cheaply, share through pull requests and bring back together with a merge.

This is the part of Git that every job uses every day. Almost every company on GitHub runs some version of the flow in the last article of this module — issue, branch, commits, pull request, review, merge — and interviewers ask about branches, HEAD, merge conflicts and pull requests in nearly every Java full-stack interview. Module 4 adds the professional tools (rebase, stash, cherry-pick, reset, reflog) for the days when something goes wrong. The CI pipelines in DevOps · Module 4 run on exactly the branches and pull requests you learn here.

After this module you will be able to:

  • explain what a branch and HEAD really are, and get out of a detached HEAD without losing work;
  • create, switch, rename and delete branches (local and remote) with git switch and git branch, using names a team will accept;
  • merge branches and say in advance whether Git will fast-forward or create a merge commit;
  • read conflict markers and resolve a merge conflict in the terminal, in VS Code and in IntelliJ;
  • open, review and merge pull requests, and choose between merge commit, squash and rebase;
  • write commit messages — including Conventional Commits — that a teammate can actually use;
  • compare GitHub flow, Git Flow and trunk-based development, and follow one feature from issue to merged pull request.

What a branch really is: a pointer, plus HEAD

A branch is a small movable label that points to one commit; HEAD points to the branch you are on, and every new commit moves that branch forward.

Every commit stores a snapshot of your project and the id of its parent commit (the commit it was built on). Follow the parent ids backwards and you get the history: a chain of commits. A branch is not a copy of that chain. It is only a name that points to one commit — normally the newest commit of one line of work.

This one idea explains almost everything else in this module: why creating a branch is instant, why deleting a branch does not delete commits, and why git commit "moves" a branch.

A branch is a file that holds one commit id

Look inside the hidden .git folder of any repository:

$ cat .git/refs/heads/main
9d4e7f0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e
$ cat .git/HEAD
ref: refs/heads/main

The file name is the branch name. The content is a commit id — a 40-character hash in a normal repository. That is all a branch is. A name with a slash, such as feature/login, is simply a file login inside a folder feature. (Git may later pack many of these small files into one file, .git/packed-refs; the idea does not change.)

Git never copies your project to make a branch. It writes one tiny file, so you can create a branch in a few milliseconds and throw it away just as fast. That is why Git users make branches freely — one per task.

HEAD: where you are now

HEAD is the second pointer. It tells Git where you are. Normally it does not point at a commit directly. It points at a branch name (ref: refs/heads/main above), and that branch points at a commit. Two consequences follow:

  • The commit that HEAD resolves to is the parent of your next commit.
  • The branch that HEAD points to is the branch that moves forward when you commit.

How commits move a branch

When you run git commit, Git does three things:

  1. It creates a new commit whose parent is the commit HEAD currently resolves to.
  2. It moves the current branch (the one HEAD points to) to the new commit.
  3. HEAD itself does not change — it still points to the branch name. Every other branch stays exactly where it was.

You can see the labels with git log --decorate. The words in brackets are the pointers:

$ git switch -c feature/login
Switched to a new branch 'feature/login'
$ git log --oneline --decorate -3
3f2a1bc (HEAD -> feature/login, origin/main, origin/HEAD, main) Add order summary page
8c1d2e4 Add order entity
1a2b3c4 Initial commit

$ git commit -am "Add login endpoint"
[feature/login 9d4e7f0] Add login endpoint
 1 file changed, 24 insertions(+)
$ git log --oneline --decorate -2
9d4e7f0 (HEAD -> feature/login) Add login endpoint
3f2a1bc (origin/main, origin/HEAD, main) Add order summary page

HEAD -> feature/login means "HEAD points to the branch feature/login". origin/main is a remote-tracking branch: your own bookmark of where main was on GitHub the last time you fetched (see Module 2). Notice that main did not move when you committed on feature/login.

Two lines of work

Now suppose a teammate adds commit M3 to main while you add F1 and F2 on your branch. The two branches have diverged: both have commits the other does not. Joining them again is what merge does (next articles).

What switching branches does to your folder

git switch main does two things: it moves HEAD to main, and it rewrites the tracked files in your working folder so they match the commit main points to. Files that Git does not track (untracked or ignored) are left alone.

What about changes you have not committed? Git carries them to the other branch if that is safe — that is, if the files you changed are identical in both commits. If the switch would overwrite your edits, Git stops and protects them:

$ git switch other
error: Your local changes to the following files would be overwritten by checkout:
	App.java
Please commit your changes or stash them before you switch branches.
Aborting

Your options are to commit the work, to park it with git stash (Module 4), or to discard it with git restore.

Rule: a new commit only moves the branch that HEAD points to

All other branches stay where they are. If you commit while on main, main moves — even if you meant to be on a feature branch. Always check where you are before you commit: git branch --show-current or git status.

Edge cases

  • In a brand-new repository HEAD points to main, but the branch does not exist until the first commit (an unborn branch). git branch prints nothing until then.
  • Deleting a branch deletes only the label. The commits stay in the repository until garbage collection removes the ones nothing points to (see the reflog).
  • Two or more branches can point at the same commit — as main and feature/login do in step 2 of the picture.
  • Creating a branch with a name that exists fails: fatal: a branch named 'feature/login' already exists.
  • Branch names are case-sensitive in Git, but Windows and macOS file systems are not. Avoid two names that differ only by case.

Mistake: committing on main because you forgot to branch

Check first, then branch, then work. If you did commit on main by accident, do not panic — see the disaster recovery playbook.

Wrong: start coding without looking

$ git status -sb
## main...origin/main
$ git commit -am "Add login endpoint"
# the commit landed on main

Right: look, create the branch, then commit

$ git branch --show-current
main
$ git switch -c feature/login
Switched to a new branch 'feature/login'
$ git commit -am "Add login endpoint"

Tip: always see your branch

Git Bash shows the branch in the prompt, for example (feature/login). IntelliJ shows it in the bottom-right widget and VS Code in the bottom-left status bar. If your tool does not show it, run git status before every commit.

Interview: "What is a branch in Git? What is HEAD?"

  • A branch is a lightweight, movable pointer to a commit. It is stored as a tiny file containing a commit id, so creating one is instant and costs almost nothing.
  • When you commit, Git creates a commit whose parent is the current commit and moves the current branch to it.
  • HEAD is a pointer to "where you are". Normally it points to a branch, which points to a commit. It can also point directly at a commit — a detached HEAD (next article).
  • Deleting a branch removes the label, not the commits; unreferenced commits are cleaned up later by garbage collection.
  • Mention that a branch is not a copy of files and not a folder — that is the misconception interviewers look for.

Detached HEAD: what it is and how to get out safely

HEAD is "detached" when it points straight at a commit instead of a branch; commits you make there belong to no branch and can be lost unless you create a branch for them.

Normally HEAD points to a branch, and the branch points to a commit. In a detached HEAD state, HEAD skips the branch and points directly at one commit. Git has no label that moves when you commit, so a new commit has nothing keeping it alive.

It is not an error

"Detached HEAD" sounds scary, but it is a normal and useful state. It is how you look at old code, test an old release or let a tool such as git bisect visit old commits. It only becomes a problem if you commit there and then walk away.

How you get into a detached HEAD

What you didWhy HEAD is detached
git checkout 3f2a1bc (a commit id)A commit is not a branch name
git checkout v1.2.0 (a tag)Tags never move, so Git will not attach HEAD to one
git checkout origin/mainA remote-tracking branch is read-only for you; the local branch is main
git switch --detach HEAD~2You asked for it explicitly
During git rebase or git bisectGit visits commits one by one on your behalf
On a CI serverCI usually checks out one exact commit, not a branch

Git tells you what happened. This is the message from git checkout with a commit id:

$ git checkout 3f2a1bc
Note: switching to '3f2a1bc'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.

If you want to create a new branch to retain commits you create, you may
do so (now or later) by using -c with the switch command. Example:

  git switch -c <new-branch-name>

Or undo this operation with:

  git switch -

Turn off this advice by setting config variable advice.detachedHead to false

HEAD is now at 3f2a1bc Add order summary page
$ git status
HEAD detached at 3f2a1bc
nothing to commit, working tree clean

Other signs: the shell prompt shows (HEAD detached at 3f2a1bc), git branch lists * (HEAD detached at 3f2a1bc), and VS Code or IntelliJ show a commit id where the branch name should be. git switch --detach is silent — Git assumes you know what you are doing.

Why it can lose work

Suppose you make a commit while detached:

$ git commit -am "Try a different discount rule"
[detached HEAD 5a6b7c8] Try a different discount rule
 1 file changed, 3 insertions(+), 1 deletion(-)

The new commit 5a6b7c8 has 3f2a1bc as its parent, but no branch points to it. The moment you switch away, nothing in the branch list leads to that commit any more. Git warns you:

$ git switch main
Warning: you are leaving 1 commit behind, not connected to
any of your branches:

  5a6b7c8 Try a different discount rule

If you want to keep it by creating a new branch, this may be a good time
to do so with:

 git branch <new-branch-name> 5a6b7c8

Switched to branch 'main'

The commit is not deleted at once — it stays in the reflog for at least 30 days by default — but you will lose track of it, and garbage collection will remove it eventually. Read that warning; it contains the commit id you need.

How to get out safely

SituationWhat to do
You were only looking aroundgit switch - (back to the previous branch) or git switch main
You made commits and want to keep them — still detachedgit switch -c rescue-branch — creates a branch at the current commit and attaches HEAD to it
You made commits and already switched awaygit branch rescue-branch 5a6b7c8 using the id from the warning; if you lost the id, find it with git reflog
You made commits and do not want themSwitch to a branch and ignore the warning; the commits become unreachable
You want a hotfix on top of an old releasegit switch -c hotfix/1.2.1 v1.2.0 — start a real branch from the tag

The rescue in full:

$ git switch -c experiment/discount-rule
Switched to a new branch 'experiment/discount-rule'
$ git log --oneline --decorate -2
5a6b7c8 (HEAD -> experiment/discount-rule) Try a different discount rule
3f2a1bc Add order summary page

Now HEAD points to a branch again, and the commit is safe. Merge the branch into main (next article) or delete it when you are done.

Rule: before you commit, make sure HEAD is attached

If git status says HEAD detached at … and you want to keep your work, create a branch before you commit, or at least before you switch away: git switch -c new-branch-name.

Edge cases

  • During a rebase, HEAD is detached on purpose while Git replays your commits one by one. When the rebase finishes, Git attaches HEAD to your branch again. Do not "fix" it.
  • git checkout origin/main detaches HEAD. If you want to work on main, use git switch main (the local branch).
  • git switch v1.2.0 without --detach fails: fatal: a branch is expected, got tag 'v1.2.0'. The same happens for a commit id (got commit '…') and for origin/main (got remote branch 'origin/main'). The error includes a hint to use --detach.
  • On CI servers HEAD is usually detached, so git branch --show-current prints an empty line. Scripts that need the branch name read it from the CI environment variables instead.
  • A submodule is normally checked out in detached HEAD at the commit the parent repository records.

Mistake: checking out a tag or a remote branch and starting to work

Wrong: commits end up on no branch

$ git checkout v1.2.0
$ # ...edit files...
$ git commit -am "Fix rounding bug"
$ git switch main    # the fix is now "left behind"

Right: start a branch from the tag first

$ git switch -c hotfix/1.2.1 v1.2.0
$ # ...edit files...
$ git commit -am "Fix rounding bug"
$ git push -u origin hotfix/1.2.1

Tip: lost a commit? Think reflog

If you left a detached HEAD without keeping the id, run git reflog. Every place HEAD has been is listed there, including your detached commits. Find the line with your commit message and run git branch rescue-branch <id>.

Interview: "What is a detached HEAD, and how do you recover from it?"

  • Normally HEAD points to a branch. In a detached HEAD it points directly at a commit — after checking out a commit id, a tag or a remote-tracking branch.
  • Looking around is safe. Commits made there are not on any branch, so switching away leaves them unreachable and they will eventually be garbage-collected.
  • Recovery: git switch -c new-branch while still detached; or git branch new-branch <id> afterwards, finding the id in Git's warning or in git reflog.
  • To leave without keeping anything: git switch main or git switch -.
  • Add that rebase and bisect detach HEAD temporarily by design.

Branch commands: list, create, switch, rename and delete

git branch manages branch names and git switch moves between them: create with switch -c, delete merged branches with -d, force with -D, and remove a remote branch with git push origin --delete.

Because a branch is only a pointer (see the first article), every branch command is quick. This article is the reference you will come back to. The roadmap commands are git switch -c feature/login, git branch and git switch main; around them are the options you need on the job.

Create a branch

# Create AND switch (what you want 95% of the time)
git switch -c feature/login

# Create from a specific starting point (a branch, a tag or a commit id)
git switch -c hotfix/1.2.1 v1.2.0
git switch -c feature/cart origin/main

# Create only; stay where you are
git branch feature/login
git branch rescue-branch 5a6b7c8

Without a starting point, the new branch starts at the commit you are on. git branch feature/login does not switch to it — a very common surprise. If you create a branch from origin/main, Git sets origin/main as its upstream. The first git push -u origin feature/cart corrects that, so the branch tracks its own remote twin.

Switch between branches

$ git switch main
Switched to branch 'main'
Your branch is up to date with 'origin/main'.
$ git switch -
Switched to branch 'feature/login'
$ git switch feature/search
branch 'feature/search' set up to track 'origin/feature/search'.
Switched to a new branch 'feature/search'
  • git switch - jumps back to the previous branch — handy for toggling between two tasks.
  • git switch feature/search, when no local branch has that name but exactly one remote has it, creates a local branch that tracks the remote one. This is how you start working on a branch a teammate pushed.
  • git switch --detach <commit> detaches HEAD on purpose (detached HEAD).
  • git switch -C name creates the branch or resets an existing one to the start point. Use it carefully: it moves a branch you may care about.

Rename a branch

git branch -m feature/login feature/login-endpoint   # old name, new name
git branch -m feature/login-endpoint                 # rename the branch you are on

Renaming changes only your local branch. If it is already pushed, publish the new name and delete the old one, then tell teammates:

git push -u origin feature/login-endpoint
git push origin --delete feature/login

-M forces the rename even if the new name already exists (it overwrites that branch). Do not use it unless you are sure. On GitHub you can also rename a branch in the browser; GitHub then retargets open pull requests and redirects the old links.

Exception: -d refuses after a squash merge, even though the work is merged

When GitHub squashes a pull request into one new commit, the original commits of your branch never become part of main. Git cannot see that the work is merged, so git branch -d says "not fully merged". If the pull request really shows Merged, -D is correct here. Check the PR first. Details in merge options.

You cannot delete the branch you are standing on; switch to another branch first. Git also refuses to delete a branch that is checked out in another worktree.

Delete a remote branch and clean up

$ git push origin --delete feature/login
To github.com:acme/crm.git
 - [deleted]         feature/login
$ git fetch --prune
From github.com:acme/crm
 - [deleted]         (none)     -> origin/feature/login
$ git branch -vv
  feature/login  9d4e7f0 [origin/feature/login: gone] Add login endpoint
  • git push origin --delete name removes the branch on GitHub. The old short form is git push origin :name.
  • Other people's copies of origin/feature/login stay until they run git fetch --prune (or git remote prune origin). Set git config --global fetch.prune true to prune on every fetch.
  • A local branch whose upstream was deleted shows : gone] in git branch -vv. That is your list of leftovers to delete locally.
  • On GitHub, Settings → General → Pull Requests → Automatically delete head branches removes the branch right after its pull request is merged.

checkout vs switch and restore

Older tutorials use git checkout for everything. It does too many unrelated jobs: switching branches, creating branches, detaching HEAD and throwing away file changes. One short command could therefore destroy work by accident — git checkout -- . discards every edit in the folder without asking. Git 2.23 (2019) split the job in two clearer commands: git switch for branches and git restore for files. git checkout still works, and you will see it everywhere, so know both.

GoalOld wayNew way
Switch to a branchgit checkout maingit switch main
Create and switchgit checkout -b feature/xgit switch -c feature/x
Detach HEAD at a commitgit checkout 3f2a1bcgit switch --detach 3f2a1bc
Discard edits in a filegit checkout -- App.javagit restore App.java
Unstage a filegit reset HEAD App.javagit restore --staged App.java
Get a file from another commitgit checkout 3f2a1bc -- App.javagit restore --source=3f2a1bc App.java

git switch only changes branches, and it refuses to move to a commit id or tag unless you add --detach. git restore only touches files and never moves HEAD. If a file and a branch have the same name, git checkout name has to guess; the new commands never have to.

Mistake: git restore and git branch -D cannot be undone casually

git restore App.java throws away your uncommitted edits in that file for good — they were never saved in Git, so there is nothing to recover. Run git diff App.java first if you are not sure. Likewise, check git branch --no-merged main before using -D.

Conventions

  • One branch per task, created from an up-to-date main: git switch main, git pull, git switch -c feature/….
  • Delete a branch as soon as its pull request is merged. Stale branches make the list useless.
  • Use -d by default and -D only after you have checked.
  • Push with git push -u origin branch-name the first time, so later git pull and git push need no arguments.
  • Set the default name for new repositories once: git config --global init.defaultBranch main.

Interview: "git branch -d vs -D?", "How do you delete a remote branch?", "checkout vs switch?"

  • -d deletes only if the branch is fully merged; -D forces it and can lose unmerged commits.
  • Remote branch: git push origin --delete branch; then git fetch --prune to clear stale remote-tracking branches.
  • git switch changes branches; git restore changes files. git checkout did both (and more), which made it error-prone. They arrived in Git 2.23.
  • Create and switch in one step with git switch -c; git switch - returns to the previous branch.

Branch naming conventions

Name a branch with a type prefix, an optional ticket id and a short lowercase description — feature/CRM-142-login-endpoint — so anyone can tell what it is for without opening it.

Git lets you call a branch almost anything. Teams do not, because a branch name is read many more times than it is typed: in the branch list, in the pull-request title bar, in CI logs and in Jira. A good name answers three questions at a glance: what kind of work is it, which ticket is it, and what does it do?

The common pattern

Most teams use <type>/<ticket>-<short-description>:

feature/CRM-142-login-endpoint
bugfix/CRM-188-empty-cart-npe
hotfix/CRM-201-payment-timeout
release/1.4.0
chore/upgrade-spring-boot
docs/api-readme

hotfix/An urgent fix for productionhotfix/CRM-201-payment-timeout

The prefix tells reviewers what to expect, lets CI treat branch types differently (for example, run a workflow only for feature/** and release/** branches), and groups branches in tools that fold names at the slash. The ticket id (CRM-142) links the branch to your tracker: the Jira–GitHub integration, for example, connects branches and pull requests automatically when the issue key appears in the name. On teams that track work in GitHub Issues, the issue number plays the same role: feature/12-login-endpoint.

Style rules

  • Lowercase for the description, with hyphens between words. The ticket key keeps its normal capitals (CRM-142).
  • Short but meaningful — about three to five words. feature/CRM-142-login-endpoint, not feature/CRM-142-add-the-new-login-endpoint-for-customers-using-jwt.
  • No spaces and no odd characters. Use hyphens, never underscores mixed with hyphens.
  • Describe the change, not the person: asha-branch says nothing. (A few teams prefix a username on purpose; follow your team's rule.)
  • One purpose per branch. If the name needs "and", it is probably two branches.
Weak nameProblemBetter
test, new, tempSays nothing; will be forgottenspike/redis-cache

What Git itself allows

Git's own rules (they come from git check-ref-format) are looser than team rules, but you must know the hard limits. A branch name cannot:

  • contain spaces, ~, ^, :, ?, *, [, a backslash, .. or @{;
  • start with - (Git would read it as an option) or end with /, . or .lock;
  • contain two slashes in a row, or a part that starts with a dot;
  • be called HEAD or just @.

You can test a name before you use it: git check-ref-format --branch "feature/my branch" fails because of the space.

Exception: a branch and a "folder" of branches cannot share a name

Because feature/login is stored as a file inside a folder called feature, you cannot have a branch named feature and another named feature/login at the same time. Git stops you:

$ git switch -c feature/login
fatal: cannot lock ref 'refs/heads/feature/login': 'refs/heads/feature' exists;
cannot create 'refs/heads/feature/login'

The fix is to rename or delete the plain feature branch. This is one more reason to always use a type prefix and never a bare word like feature or bugfix as a branch name.

Conventions

  • Agree on the prefixes once, write them in CONTRIBUTING.md or the team wiki, and use only those.
  • Keep the prefix list in line with your commit types (feature ↔ feat, bugfix ↔ fix); see Conventional Commits.
  • Never reuse the name of a merged branch for new work. Create a new one from a fresh main.
  • Bots create their own branches (for example dependabot/maven/…); do not fight them.
  • In GitHub Actions you can filter by pattern: on: push: branches: ['feature/**'] runs a workflow only for feature branches.

Mistake: names that differ only in case, or that only mean something to you

Feature/Login and feature/login are two different branches in Git, but on Windows and macOS they can collide in the local file system and confuse every tool. And a name such as my-work forces each reviewer to open the branch to learn what it is. Use lowercase and be specific.

Interview: "How do you name your branches?"

  • A type prefix (feature/, bugfix/, hotfix/, release/), the ticket id, then a short lowercase, hyphen-separated description: feature/CRM-142-login-endpoint.
  • Reasons: readable branch lists, filters in CI, automatic linking to Jira or GitHub Issues, and an obvious branch purpose for reviewers.
  • Mention the technical limits: no spaces, no ~ ^ : ? * [, and a branch named feature blocks feature/login.
  • Say the team's convention matters more than which convention: consistency is the point.

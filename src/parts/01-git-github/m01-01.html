Git is the tool that records every change you make to your code, so you can see what changed, who changed it, why, and go back to any earlier point. Every software team in the world uses it — in a Java full-stack job you will run Git commands many times a day, and almost every interview asks about it.

This module covers the local side of Git: everything that happens on your own computer. You will install Git, create repositories, make commits, read history, keep junk files out and undo mistakes safely. Sharing code through GitHub comes next in Module 2, working in branches with a team in Module 3, and the professional-level tools (rebase, reset, reflog, recovery) in Module 4. Git is also the entry point to the delivery pipeline you will meet in DevOps · Module 4.

After this module you will be able to:

  • install Git on Windows, set your identity, and understand the three configuration levels and line-ending settings;
  • start or copy a repository with git init and git clone;
  • move changes through the three areas — working folder, staging area and repository — with git add and git commit;

  • write a correct .gitignore and never commit secrets;
  • undo mistakes without losing work, using git restore, git restore --staged and git commit --amend.

What version control is and why every team uses it

Version control records every change to your files as a numbered history, so you can compare, undo and merge work from many people — and Git is the tool almost every team uses for it.

Imagine you are building a Spring Boot project. On Monday it works. On Tuesday you change the payment code and now nothing works. Without version control you would try to remember what you changed, or you would keep folders such as project_final, project_final_v2 and project_final_REAL. Now add four teammates who all edit the same files. That is chaos.

A version control system (VCS) solves this. It keeps a complete history of your project: every change, who made it, when, and a message saying why. A repository (or repo) is the project folder plus this history. Each saved point in the history is called a commit.

What version control gives you

History
Every change is recorded with the author, date and message. You can answer "who changed this line, and why?" months later.
Undo
You can return one file, or the whole project, to any earlier commit. Experiments become safe.
Parallel work
Several people (or you, on several features) work at the same time in separate branches and combine the results later. You will learn this in Module 3.
Collaboration
The system merges edits from different people. When two people change the same lines, it tells you instead of silently overwriting one of them.
Backup and sharing
When you copy the repository to a server such as GitHub, the code and its history are safe even if your laptop is lost.
Traceability
Teams link every change to a ticket, a code review and a build. When production breaks, you can find the exact commit that caused it.

Three generations of version control

  1. Manual copies — folders and zip files. No history, no merging, easy to lose work.
  2. Centralized systems (CVS, Subversion/SVN, Perforce) — one server holds the full history; developers keep only a working copy. You need the server for almost every action.
  3. Distributed systems (Git, Mercurial) — every developer has a full copy of the repository, including the entire history. A server such as GitHub is just one more copy that everyone agrees to share.
PointCentralized (SVN)Distributed (Git)
Where history livesOn the central serverIn every clone
Work offlineVery limited — commits go to the serverFully — commit, view history, compare, all offline
Commit speedNetwork round tripInstant (local disk)
BranchingHeavier, used carefullyCheap and fast — branch for every task

A short history of Git

Linus Torvalds, the creator of Linux, wrote Git in 2005. The Linux kernel team had lost access to the tool they were using and needed a replacement that was fast, safe with thousands of contributors, and fully distributed. Git was built around those goals. Today Git is the default choice for new projects. GitHub, GitLab and Bitbucket are websites built on top of Git — you will see exactly how they differ in Git vs GitHub.

What a developer's day looks like with Git

In Module 1 you learn the steps Edit and test and Commit on your own machine. The other steps build on top of them.

Why Git won

  • Speed. Most commands only touch your local disk, so they finish in milliseconds.
  • Cheap branches. A branch is just a small pointer (see How Git stores your work), so making one per feature costs nothing.
  • Integrity. Every object is identified by a hash of its content. Silent corruption or tampering is detected.
  • Ecosystem. IntelliJ IDEA, VS Code, GitHub, GitLab, CI servers, code review tools and deployment pipelines all speak Git.

What Git is not

  • Not a backup of everything. Git only protects what you commit. Untracked and ignored files (.env, build output) are not in the history. A repository that exists only on your laptop is not backed up either.
  • Not made for big binary files. Videos, large datasets and compiled .jar files make the repository slow and large. Teams keep them in artifact repositories or object storage instead.
  • Does not track empty folders. Git tracks files, not directories. To keep an empty folder, put a placeholder file such as .gitkeep inside it.
  • Not a deployment tool. It stores source code. Build and deployment pipelines read from it.

Mistake: using file names as version control

Copies named _final, _v2 and _old tell you nothing about what changed or why, and nothing merges them for you.

Wrong: history hidden in file names

OrderService.java
OrderService_old.java
OrderService_v2_FINAL.java
OrderService_v2_FINAL_fixed.java

Right: one file, history in Git

$ git log --oneline -- OrderService.java
8d41b7e Fix rounding error in order total
3f2a9c1 Add GST calculation to order total
a17c0de Create OrderService

Real projects

In a company, nothing reaches production without Git. A ticket in Jira gets a branch, the branch becomes a pull request, a reviewer approves it, an automated pipeline builds and tests it, and a deployment is tied to a specific commit or tag. When something breaks in production, the team looks at the history to find which commit introduced the bug and either fixes it or reverts that commit. Knowing Git well is part of being employable, not an optional extra.

Interview: "What is version control? What does 'distributed' mean?"

  • Version control records changes to files over time so you can see history, restore old versions and let many people work together.
  • Distributed means every developer's clone holds the full repository, including the whole history — not only a working copy.
  • Consequence: commits, logs, diffs and branches work offline and are fast; the server is a shared copy, not the only copy.
  • Contrast with SVN: one central server, history only there, most commands need the network.
  • Add that Git and GitHub are different things — Git is the tool, GitHub is a hosting service.

Install Git and set up your identity

Install Git for Windows, check it with git --version, then tell Git your name and email once with git config --global — every commit you make carries them.

Check first whether Git is already installed. Open a terminal and run:

$ git --version
git version 2.47.1.windows.1

If you see a version number, Git is installed (your number will differ). If you see 'git' is not recognized (Windows) or command not found (macOS/Linux), install it.

Installing on Windows

The standard way is Git for Windows. Download the installer from git-scm.com/downloads, or install it from a terminal with the Windows package manager:

$ winget install --id Git.Git -e --source winget

Git for Windows installs three things you will use:

  • Git itself — the git command, which also works from Command Prompt, PowerShell and the terminals inside IntelliJ IDEA and VS Code.
  • Git Bash — a terminal that understands Unix-style commands (ls, cat, grep, rm). Most tutorials and Linux servers use these commands, so learning them here pays off later. Paths look different: C:\Users\asha becomes /c/Users/asha.
  • Git Credential Manager — remembers your GitHub login so you do not type it on every push (see HTTPS, tokens and Git Credential Manager).

On other systems: macOS — brew install git (or run git and accept the Xcode command-line tools prompt); Debian and Ubuntu — sudo apt install git.

First-time setup: your name and email

Every commit records who made it. Git does not ask you — you tell it once:

$ git config --global user.name "Asha Rao"
$ git config --global user.email "asha@example.com"
$ git config user.name
Asha Rao

Use the same email that is verified on your GitHub account. GitHub uses the commit email to link commits to your profile and to count them in your contribution graph. If you prefer not to expose your personal email in public commits, GitHub gives you a private noreply address (see Creating your GitHub account).

Mistake: committing without an identity

If you skip the setup, your first commit stops with an error. Run the two git config commands shown in the message and commit again.

Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"

to set your account's default identity.
Omit --global to set the identity only in this repository.

The three configuration levels

Git reads settings from three files. A more specific level overrides a less specific one: local beats global beats system.

LevelFlagApplies toFile
System--systemEvery user on this computeretc/gitconfig inside the Git install folder
Global--globalAll repositories of your user~/.gitconfig — on Windows C:\Users\asha\.gitconfig
Local--local (the default inside a repo)Only this repository.git/config

Without a flag, git config key value writes to the local level and only works inside a repository. Use local when one project needs a different value — for example your company email in work repositories and your personal email everywhere else:

$ cd ~/work/billing-service
$ git config user.email "asha.rao@company.com"      # local: only this repo
$ git config --show-origin user.email
file:.git/config	asha.rao@company.com

To see every setting and the file it comes from:

$ git config --list --show-origin
file:C:/Program Files/Git/etc/gitconfig	core.autocrlf=true
file:C:/Program Files/Git/etc/gitconfig	credential.helper=manager
file:C:/Users/asha/.gitconfig	user.name=Asha Rao
file:C:/Users/asha/.gitconfig	user.email=asha@example.com
file:C:/Users/asha/.gitconfig	init.defaultbranch=main
file:.git/config	core.repositoryformatversion=0

Use git config --list --show-scope to print system, global or local in front of each line instead of a path. To open a config file in your editor, run git config --global --edit. To remove a setting, run git config --global --unset user.name.

Tip: use different emails automatically with includeIf

If you keep work projects in one folder, add this to ~/.gitconfig and put the work email in ~/.gitconfig-work. Every repository under ~/work/ then uses the work identity without any per-repo command.

[includeIf "gitdir:~/work/"]
    path = ~/.gitconfig-work

Recommended settings for a new machine

$ git config --global init.defaultBranch main
$ git config --global core.editor "code --wait"
$ git config --global alias.st "status -s"
$ git config --global alias.lg "log --oneline --graph --all --decorate"
  • init.defaultBranch main — new repositories start on main instead of the older default master. Without it, a plain git init may create master, and then your local name will not match the main branch that GitHub creates.
  • core.editor "code --wait" — opens VS Code for commit messages. --wait makes Git wait until you close the file.
  • alias.* — shortcuts. After this, git st runs git status -s and git lg prints the compact history graph.

The result is a plain text file you can read and edit:

[user]
	name = Asha Rao
	email = asha@example.com
[init]
	defaultBranch = main
[core]
	editor = code --wait
[alias]
	st = status -s
	lg = log --oneline --graph --all --decorate

Tip: if you land in Vim, here is the way out

If you run git commit without -m and no editor is configured, Git opens Vim. Press i to start typing, then Esc, then type :wq and press Enter to save and quit. To abandon the commit, press Esc and type :q!. An empty message cancels the commit with Aborting commit due to empty commit message.

Line endings: why they matter on Windows

Windows ends each text line with two characters, CRLF (\r\n). Linux and macOS use one, LF (\n). If a Windows developer and a Linux developer commit the same file without a policy, one of two bad things happens: every line of the file shows as changed in diffs, or a shell script saved with CRLF fails on a Linux server with an error such as /bin/bash^M: bad interpreter.

The setting core.autocrlf tells Git to convert line endings for you:

ValueOn commitOn checkoutUse on
trueCRLF → LFLF → CRLFWindows (the installer default)
inputCRLF → LFNo changemacOS and Linux
falseNo changeNo changeWhen a .gitattributes file controls everything

With true the repository always stores LF, while your Windows editor sees CRLF. You may see this harmless warning when you add a file:

warning: in the working copy of 'Hello.java', LF will be replaced by CRLF the next time Git touches it

A personal setting is not enough for a team, because each developer can configure it differently. The reliable fix is a .gitattributes file committed to the repository, which applies to everybody:

# Let Git decide text files and normalise them to LF inside the repository
* text=auto

# Scripts must always be LF, even on Windows
*.sh   text eol=lf
mvnw   text eol=lf

# Windows batch files must be CRLF
*.bat  text eol=crlf
*.cmd  text eol=crlf

# Never touch binary files
*.png  binary
*.jpg  binary
*.jar  binary

If you add .gitattributes to an existing project, run git add --renormalize . once so the files already in the repository are normalised too.

Rule: configure identity before the first commit

Set user.name and user.email before your first commit. A commit that already exists keeps its author for good unless you rewrite it (see Undo safely for the last commit, and Module 4 for older ones).

Conventions

  • Use your real name and a stable email — it is shown to your whole team in every commit.
  • Keep --global for personal preferences and local config for project-specific values.
  • Keep init.defaultBranch as main and commit a .gitattributes file for line endings in team projects.
  • Never put passwords or tokens in .gitconfig files; use the credential helper.

Edge cases

  • Values with spaces need quotes: git config --global user.name Asha Rao fails with error: wrong number of arguments; write "Asha Rao".
  • Running git config user.name "X" outside a repository fails with fatal: not in a git directory because local is the default level. Add --global.
  • Config keys are case-insensitive for the section and variable name, which is why --list prints init.defaultbranch in lower case.
  • A repository can override your global identity. If commits show the wrong email, run git config --show-origin user.email in that repository to see which file wins.

Interview: "How do you configure Git? What are the config levels?"

  • Three levels — system, global, local — stored in the Git install folder, ~/.gitconfig and .git/config. Local overrides global overrides system.
  • First setup is user.name and user.email; they go into every commit.
  • Inspect with git config --list --show-origin.
  • Explain CRLF vs LF and core.autocrlf, and say that a team should enforce it with .gitattributes.

GitHub Issues and Projects boards

Issues track bugs, tasks and ideas (with templates, labels, assignees and milestones), and Projects boards turn those issues and PRs into a visible workflow such as Todo, In progress and Done.

Git stores code history; the team still needs a place to say what to build and who is doing it. On GitHub that place is Issues. Many small teams use Issues and Projects instead of a separate tool like Jira; bigger companies often use Jira and link its ticket ids in branch names and commits.

Issues

An issue has a title, a Markdown description, a number (#12), and a conversation. The right sidebar holds the organising fields:

FieldPurposeExample
AssigneesWho is working on it@asha
LabelsCategory and priority tagsbug, enhancement, good first issue, priority-high
MilestoneGroups issues for a release or sprint, with a progress barv1.3.0
ProjectsAdds the issue to a boardCRM Sprint 14
DevelopmentLinked branches and PRsPR #13 closes this issue

In any issue, PR or commit message, #12 becomes a link, and @name notifies a person. In a PR description Closes #12 closes the issue on merge. You can also create a branch directly from an issue (the Development section), which names it for you.

Issue templates

Templates make people include the details you need. Put Markdown files (or YAML forms) in .github/ISSUE_TEMPLATE/; GitHub then shows a chooser when someone clicks New issue.

---
name: Bug report
about: Something does not work as expected
labels: bug
---

## What happened
## Steps to reproduce
1.
2.
## Expected result
## Actual result
## Environment
Java version, browser, OS, app version

A good bug report has exact steps, the expected and the actual result, and the log or screenshot. A good feature request explains the user problem first and the solution second. Acceptance criteria ("done when …") make a task testable.

Projects boards

A GitHub Project is a flexible planning view over issues and PRs from one or more repositories. You can show the same items as a Board (Kanban columns), a Table (spreadsheet with custom fields like Priority, Estimate and Sprint) or a Roadmap (timeline). A typical board:

Built-in automation can do the moves for you: when an issue is opened it goes to Todo; when a PR is opened it moves to In review; when it is merged or the issue is closed it moves to Done.

Conventions

  • One issue = one deliverable. Split big issues into small ones, and track the parent with a task list (- [ ] #14).
  • Use a small, consistent label set; avoid dozens of labels nobody remembers.
  • Put the issue number in the branch name and Closes #n in the PR.
  • Do not use issues for secrets or security vulnerabilities; use a private security advisory.

Real projects

In a company the ticket usually comes from Jira, Azure Boards or similar: branch feature/CRM-142-login, commit CRM-142: add login endpoint. The tool links the branch and PR to the ticket automatically, so the workflow in Module 3 stays the same. In open source, Issues are the main way to discuss and plan, and labels such as good first issue help new contributors.

Interview: "How do you track work on GitHub?"

  • Issues with templates, labels, assignee, milestone; a Projects board for the workflow.
  • Link PRs with Closes #n so tickets close and boards update automatically.

Branch protection, rulesets and CODEOWNERS

Branch protection (or the newer rulesets) forces every change to main to go through a pull request with required reviews and passing checks, and blocks force pushes and deletion; CODEOWNERS asks the right people to review automatically.

Rules written in a wiki are easy to forget. Rules enforced by GitHub cannot be forgotten. A repository admin sets them in Settings → Branches (a branch protection rule) or Settings → Rules → Rulesets. Rulesets are the newer system: they can target many branches by pattern, can be shared across a whole organisation, can be switched to an "evaluate" mode first, and several can apply at once. Both offer similar options.

Important options

OptionWhat it enforces
Require a pull request before mergingNo direct push to main; changes arrive through a PR
Required approvals (1, 2, …)The number of approving reviews before the merge button works
Dismiss stale approvals on new commitsNew pushes cancel earlier approvals
Require review from Code OwnersThe owners listed in CODEOWNERS must approve changes to their files
Require status checks to passNamed CI checks (build, test, lint) must be green; optionally the branch must be up to date with main
Require conversation resolutionAll review threads must be resolved
Require signed commitsOnly verified signatures are accepted
Require linear historyNo merge commits; only squash or rebase merges
Block force pushesNobody can rewrite main's history
Restrict deletionsThe branch cannot be deleted
Include administrators / no bypassRules apply to admins too

With these set, an attempt to push straight to main fails:

$ git push origin main
remote: error: GH006: Protected branch update failed for refs/heads/main.
remote: error: Changes must be made through a pull request.
To github.com:acme/crm.git
 ! [remote rejected] main -> main (protected branch hook declined)

The fix is the normal workflow: push a feature branch and open a PR. A common setting for a small team: PR required, 1 approval, status checks build and test required, branch up to date, force pushes and deletions blocked.

CODEOWNERS

A CODEOWNERS file maps paths to people or teams. When a PR touches a path, the owners are requested as reviewers automatically, and with Require review from Code Owners their approval is mandatory. The file lives in .github/CODEOWNERS, in the root, or in docs/.

# Default owner for everything
*                         @acme/backend-team

# Frontend code
/frontend/                @acme/frontend-team

# Payments and security need extra care
/src/main/java/com/acme/crm/payment/   @asha @acme/security
/src/main/resources/db/migration/      @acme/dba

# CI configuration
/.github/workflows/       @acme/devops

Patterns work like .gitignore; if several lines match a file, the last matching line wins. Owners need write access to the repository.

Rules

  • Protect main (and release branches) on every serious project.
  • Required checks must have exactly the names of the CI jobs; a check that never runs will block merging forever.
  • Rules apply to everyone, including admins, otherwise they get skipped "just this once".

Edge cases

  • The author cannot approve their own PR; with one required approval you need a second person. Single-developer projects often set approvals to 0 and keep the status checks.
  • On the free plan, branch protection works on public repositories; some features on private repositories need a paid plan.
  • Protection stops pushes, but local tools can still create the commits; the error appears only when you push.

Conventions

  • Protect with a small set of strict rules, and keep the review requirements reasonable so that PRs do not wait for days.
  • Keep CODEOWNERS short and use teams, not individuals, so holidays do not block merges.

Interview: "How do you protect the main branch?"

  • Branch protection or a ruleset: PR required, review approvals, required status checks, block force pushes and deletions, optionally CODEOWNERS review and signed commits.
  • Explain that it enforces process automatically for everyone.

GitHub Actions and Dependabot at a glance

GitHub Actions runs your build and tests automatically on GitHub when you push or open a PR, from a YAML file in .github/workflows/; Dependabot opens PRs that update your dependencies.

GitHub Actions is GitHub's built-in automation (CI/CD: continuous integration and delivery). A workflow is a YAML file in .github/workflows/. It says when to run (the trigger, such as push or pull_request) and what jobs and steps to run on a fresh virtual machine (a runner). The results appear as checks on the PR, and branch protection can require them. The full topic, including Docker and deployment, is in DevOps · Module 4. Here is a first workflow for a Maven project:

name: CI

on:
  pull_request:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 21
          cache: maven
      - name: Build and test
        run: ./mvnw -B verify
  • on — the triggers: every PR, and every push to main.
  • runs-on — the kind of machine (a GitHub-hosted Linux runner).
  • uses: actions/checkout@v4 — downloads your code; setup-java installs JDK 21 and caches Maven downloads.
  • run — a shell command; if it fails, the job and the PR check turn red.

Commit this file on a branch and open a PR: the Checks tab shows the build running. Name the job (build) in your branch protection as a required check.

Mistake: putting secrets in the workflow file

Use Settings → Secrets and variables → Actions and read them as ${{ secrets.NAME }}. Never write tokens or passwords in YAML. Also remember that workflows from forked PRs do not get your secrets by default.

Dependabot (brief)

Dependabot checks your dependencies (Maven, Gradle, npm, Docker, even the Actions you use) and opens a PR when a newer version or a security fix exists. Turn on Dependabot alerts and security updates in repository settings, and add a config file for regular version updates:

version: 2
updates:
  - package-ecosystem: maven
    directory: "/"
    schedule:
      interval: weekly
  - package-ecosystem: github-actions
    directory: "/"
    schedule:
      interval: weekly

Each update is a normal PR: CI runs on it, and you review and merge. Do not auto-merge major upgrades without tests.

Real projects

A typical setup: CI on every PR (build, tests, lint), required by branch protection; a release workflow on tags that builds a JAR or Docker image; Dependabot for weekly updates; CODEOWNERS for sensitive folders. Together they let a team merge quickly and safely many times a day.

Interview: "What is GitHub Actions? How does CI fit with PRs?"

  • It runs workflows defined in YAML on events like pull_request; each run reports a check on the PR.
  • Branch protection requires the checks to pass before merge, so broken code cannot reach main.
  • Dependabot automates dependency update PRs.

Interview questions — Professional Git

What is the difference between merge and rebase?

Merge combines two branches by creating a merge commit with two parents and keeps history as it happened. Rebase takes your commits and replays them on top of another branch, creating new commits (new ids) and a linear history. Rebase rewrites history, so never rebase commits that others already have; use it on your own feature branch. After rebasing a pushed branch use git push --force-with-lease.

What is the difference between git fetch and git pull?

git fetch downloads new commits and updates remote-tracking branches such as origin/main, but does not touch your branches or files. git pull is fetch followed by a merge into your current branch (or a rebase with --rebase). Fetch first when you want to look before you integrate (git log HEAD..origin/main).

Reset vs revert: when do you use which?

git reset moves the branch pointer back and so rewrites history; use it for local, unpushed commits. git revert adds a new commit that undoes an earlier one and keeps history; use it for commits that are already pushed or merged into a shared branch.

Explain reset --soft, --mixed and --hard.

All three move the branch to the target commit. --soft leaves the index and files unchanged, so the undone changes are staged. --mixed (default) resets the index, so the changes remain in files, unstaged. --hard resets index and files, so the changes are discarded. Uncommitted edits lost by --hard cannot be recovered.

How do you undo a commit that you already pushed?

Use git revert <sha> and push the new commit; for a merge commit use git revert -m 1 <sha>. This keeps history intact. Resetting and force-pushing is possible on a private branch but dangerous on a shared one.

What is HEAD, and what is a detached HEAD?

HEAD points to the commit you are working on, normally through the current branch. A detached HEAD points directly to a commit, for example after checking out a tag or a commit id. New commits there are not on any branch and can be lost; create a branch with git switch -c name to keep them.

What does git stash do, and what is the difference between apply and pop?

It saves uncommitted changes in a stack and restores a clean working folder. apply brings the changes back and keeps the stash entry; pop brings them back and deletes the entry. Use -u to include untracked files and -m to name the entry.

What does git cherry-pick do?

It applies the change of a single commit onto the current branch as a new commit with a new id. Typical use: copy a hotfix from main to a release branch. Conflicts are resolved like in a merge and finished with git cherry-pick --continue.

I deleted a branch with unmerged commits. How do I get it back?

Run git reflog, find the last commit of the branch (Git also prints it when you delete: was 9e12b7c), and recreate it with git switch -c name 9e12b7c. This works for committed work on your machine for roughly 30 days or more, until garbage collection removes unreachable commits.

What is the difference between --force and --force-with-lease?

--force overwrites the remote branch unconditionally. --force-with-lease overwrites only if the remote is still at the commit you last saw, so it refuses when a teammate has pushed in the meantime and protects their work.

How do you squash the last four commits?

Run git rebase -i HEAD~4, keep pick on the first line and change the others to squash or fixup, then edit the combined message. Or run git reset --soft HEAD~4 and make one new commit. This rewrites history: do it only on unshared commits and push with --force-with-lease.

What is the difference between a lightweight and an annotated tag, and what is SemVer?

A lightweight tag is just a name for a commit. An annotated tag is a full object with tagger, date and message and is the right choice for releases. SemVer numbers versions MAJOR.MINOR.PATCH: major for breaking changes, minor for compatible features, patch for bug fixes. Tags are pushed explicitly (git push origin v1.2.0).

A bug appeared sometime in the last 200 commits. How do you find the cause?

Use git bisect: start it, mark the current commit bad and an old one good, then test each commit Git checks out and answer good or bad (or automate with git bisect run). It performs a binary search and names the first bad commit in about eight steps.

You pushed an API key to GitHub. What do you do?

Revoke and replace the key first; assume it is already copied. Check the provider's logs. Remove it from the code and use environment variables or a secret manager. Rewriting history with git filter-repo or BFG is optional and does not make the old key safe. Enable secret scanning and push protection.

How do you protect the main branch?

Use branch protection or rulesets: require a pull request, required approvals, passing status checks (CI), resolved conversations, optionally CODEOWNERS review, linear history and signed commits; block force pushes and deletion. This makes the team workflow automatic.

Cheat sheet — Professional Git

  • git rebase main replay your branch commits on top of main (new ids, linear history)
  • Golden rule never rebase or reset commits other people already have
  • --continue / --skip / --abort the three exits of a rebase or cherry-pick that stopped
  • git pull --rebase fetch and rebase your local commits instead of making a merge commit
  • git push --force-with-lease safe force push after a rebase; never plain --force
  • git rebase -i HEAD~4 edit the last four commits: pick, reword, edit, squash, fixup, drop
  • git commit --fixup sha then git rebase -i --autosquash main to fold a fix into an older commit
  • git stash push -m "msg" -u shelve changes, including untracked files
  • git stash list / pop / apply / drop see, restore and remove, restore and keep, delete entries
  • git cherry-pick sha copy one commit to the current branch; -x notes the source
  • git reset --soft HEAD~1 undo commit, keep changes staged
  • git reset HEAD~1 undo commit, keep changes unstaged (mixed)
  • git reset --hard sha move branch and discard all changes; risky
  • git revert sha new commit that undoes an old one; safe for pushed history
  • git revert -m 1 merge undo a merge commit, keeping the mainline
  • git commit --amend replace the last commit (unpushed only)
  • git reflog diary of where HEAD was; find lost commits and use git switch -c name sha
  • ORIG_HEAD remembers HEAD before a merge, rebase or reset: git reset --hard ORIG_HEAD
  • git tag -a v1.2.0 -m "msg" annotated release tag; git push origin v1.2.0 to publish
  • SemVer MAJOR.MINOR.PATCH; breaking / feature / fix; pre-release -rc.1
  • git bisect start / good / bad / run / reset binary-search for the bad commit
  • git blame -L a,b file; git log -S"text" who changed a line; when text appeared or vanished
  • git clean -n then -fd preview, then delete untracked files
  • Secret pushed rotate first, clean history later (and optionally)
  • main protection PR required, approvals, status checks, no force push; CODEOWNERS for reviewers

Practice — Professional Git

  1. Rebase vs merge. Create a repository with two commits on main. Branch feature/a with two commits, then add a commit on main. Update feature/a once with git merge main (reset it afterwards with git reset --hard ORIG_HEAD) and once with git rebase main. Compare git log --oneline --graph --all. Done when you can explain why the commit ids changed after the rebase.
  2. Rebase conflict. Make main and your branch change the same line, then rebase. Resolve the conflict, git add, git rebase --continue. Repeat and finish with git rebase --abort. Done when you can say which side "ours" is.
  3. Tidy with interactive rebase. Make four commits: "add feature", "typo", "wip", "add tests". Use git rebase -i HEAD~4 to fixup the typo, drop wip and reword the others. Done when git log --oneline shows two clean commits.
  4. Stash. Edit a tracked file and create a new file. Run git stash push -m "wip", notice the new file stays, then use -u. Switch to another branch, switch back, git stash pop. Done when both changes return and git stash list is empty.
  5. Cherry-pick a hotfix. Create release/1.0 from an early commit. Fix a bug on main and cherry-pick that commit with -x to the release branch. Done when the release branch has the fix, and the message contains (cherry picked from commit ...).
  6. Roadmap exercise: undo a mistake three ways. Commit a mistake (for example a wrong file) three times, each in a fresh copy of the repository. Undo it with git commit --amend, with git revert, and with git reset --soft HEAD~1. Done when you can say which of the three is allowed after a push and why.
  7. Roadmap exercise: recover a deleted branch. Create a branch with two commits, switch away and delete it with git branch -D. Bring it back using git reflog and git switch -c. Then do a git reset --hard HEAD~2 on main and recover that too. Done when both branches have their commits back.
  8. Tag a release. Create the annotated tag v1.0.0, push it, then create a GitHub Release with generated notes. Add a fix, tag v1.0.1. Done when the Releases page lists both and git describe works.
  9. Find a bug with bisect. Create 10 commits where commit 6 introduces a failing check (a script that exits 1). Use git bisect run ./check.sh to find it. Done when Git names the sixth commit as the first bad one.
  10. Protect main and add CI. In your own repository add .github/workflows/ci.yml through a PR, add a CODEOWNERS file, then create a branch protection rule requiring a PR and the CI check. Try to push to main directly and read the error. Finish the Main and Remote sections of Learn Git Branching (learngitbranching.js.org) if you have not yet. Done when the direct push is rejected and a PR with a red check cannot be merged.

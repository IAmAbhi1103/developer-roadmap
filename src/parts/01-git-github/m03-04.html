Branching strategies: GitHub flow, Git Flow and trunk-based development

A branching strategy is the team's agreement on which branches exist and how work moves between them; GitHub flow (main plus short feature branches) fits most web teams, Git Flow suits versioned releases, and trunk-based development suits very fast, heavily automated teams.

Git allows any branch layout. Without an agreement, every developer invents their own and merges become painful. A branching strategy (also called a workflow) is a short set of rules: which long-lived branches exist, how feature branches are named and merged, and how releases and hotfixes are made. Pick the simplest strategy that fits how you release.

GitHub flow

The simplest, and the one in the roadmap. There is one long-lived branch, main, and it is always deployable.

  1. Create a branch from main with a descriptive name.
  2. Commit and push regularly.
  3. Open a pull request (a draft early if you want feedback).
  4. Review, discuss, and let CI run.
  5. Merge into main after approval.
  6. Deploy (often automatically); delete the branch.

Git Flow

Git Flow was described by Vincent Driessen in 2010 for software shipped in numbered versions. It uses two long-lived branches and three kinds of short-lived branches:

  • main — only released code; every commit is tagged with a version (v1.2.0).
  • develop — the integration branch where finished features collect.
  • feature/* — branch from develop, merge back into develop.
  • release/* — branch from develop when a version is ready to stabilise; only bug fixes go in. Then merge into main (tag it) and back into develop.
  • hotfix/* — branch from main to fix a live bug quickly; merge into both main and develop.

Trunk-based development

In trunk-based development everyone integrates into one branch (the "trunk", usually main) at least once a day. Branches, if used at all, live for hours, not days. Unfinished features are hidden behind feature flags — an on/off setting in code or configuration — so incomplete work can be merged but stays invisible to users. It depends on strong automated tests and fast CI, because every merge must be safe to release.

Release branches in other strategies

Even GitHub-flow teams sometimes need a long-lived release/1.4 branch to patch an old version that customers still run. You then fix on main first and cherry-pick the fix to the release branch. Some teams also keep environment branches (staging, production); they are easy to understand but cause drift, so modern teams prefer deploying the same commit through environments.

Conventions

  • Start with GitHub flow. Add more structure only when you really ship numbered versions or support several at once.
  • Keep branches short-lived whatever the strategy. Long branches are the main source of painful merges.
  • Protect main (and develop) with required reviews and checks.
  • Write the rules down in CONTRIBUTING.md so new joiners need not guess.

Exception: Git Flow is no longer the default advice

The author of Git Flow himself added a note to his article saying it suits software with explicit versions, and that teams doing continuous delivery should use a simpler flow. If your web application is deployed many times a week, Git Flow adds ceremony with little benefit.

Real projects

Service companies with client-specific releases often use Git Flow or a variant. Startups and product companies running a web backend mostly use GitHub flow with squash merges, sometimes moving towards trunk-based development with feature flags. Always follow the repository's existing flow; ask in the first week.

Interview: "Which branching strategy do you prefer and why?"

  • Describe GitHub flow, Git Flow and trunk-based in one line each.
  • Say it depends on the release model: continuous delivery favours GitHub flow or trunk-based; versioned products favour Git Flow.
  • Stress short-lived branches, small PRs, protected main and CI.
  • Mention feature flags as the way to merge unfinished work safely.

A complete team workflow: from issue to merged feature

The daily loop on a team is: pick an issue, update main, create a branch, commit small, push, open a PR, handle review, merge, delete the branch, and pull main again.

This article walks through one feature from start to end, using all the commands from Modules 1–3. The project is a CRM at the made-up company Acme (github.com/acme/crm). The task is issue #12 "Add login endpoint". The team uses GitHub flow, a protected main and squash merges.

Step 1: Understand the issue and sync

Read the issue, ask questions if the acceptance criteria are unclear, and assign it to yourself. Then make sure your local main matches the remote:

$ git switch main
Switched to branch 'main'
$ git pull --ff-only
Updating 3f2a1bc..8a1c9de
Fast-forward
 README.md | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

Step 2: Create a branch

$ git switch -c feature/12-login-endpoint
Switched to a new branch 'feature/12-login-endpoint'

The name carries the type and the issue number (naming). If the ticket system uses ids like CRM-12, use feature/CRM-12-login-endpoint.

Step 3: Work in small commits

Write code, run the tests, and commit after each logical step. Each commit builds on its own.

$ git add src/main/java/com/acme/crm/auth/LoginRequest.java
$ git commit -m "feat(auth): add LoginRequest and LoginResponse records"
[feature/12-login-endpoint 4b7e1a2] feat(auth): add LoginRequest and LoginResponse records
 2 files changed, 12 insertions(+)

$ git add -p
$ git commit -m "feat(auth): add AuthService with BCrypt password check"

$ git add .
$ git commit -m "feat(auth): add POST /api/auth/login endpoint"

$ git add src/test
$ git commit -m "test(auth): cover valid login, wrong password, unknown user"

Before each git add, run git status and git diff to see exactly what goes in. Never use git add . blindly; it can add .env files or build output.

Step 4: Stay up to date

If the work takes more than a day, bring in the newest main so you meet conflicts early:

$ git fetch origin
$ git merge origin/main
Already up to date.

Some teams prefer git rebase origin/main here (see rebase). Use whichever your team uses, and only rebase while the branch is still private.

Step 5: Check and push

$ ./mvnw test
[INFO] Tests run: 14, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
$ git log --oneline origin/main..HEAD
d2f93c1 test(auth): cover valid login, wrong password, unknown user
91ab0e4 feat(auth): add POST /api/auth/login endpoint
7c4d812 feat(auth): add AuthService with BCrypt password check
4b7e1a2 feat(auth): add LoginRequest and LoginResponse records
$ git push -u origin feature/12-login-endpoint

git log origin/main..HEAD lists exactly the commits your PR will contain. If you see something unexpected, fix it now.

Step 6: Open the pull request

Open the PR on GitHub: base main, compare feature/12-login-endpoint. Title: feat(auth): add login endpoint. Fill the template, add Closes #12, ask for reviewers. Read your own diff once. Wait for CI to turn green. Move the ticket to In review.

Step 7: Handle review

Ravi comments: "Both wrong password and unknown user should give the same message." You agree, change the code and push:

$ git switch feature/12-login-endpoint
$ git add -p
$ git commit -m "fix(auth): use one error message for wrong password and unknown user"
$ git push

The new commit appears in the PR and CI runs again. Reply to Ravi's comment, resolve the thread and re-request review. Ravi approves.

Step 8: Merge

CI is green, one approval is in, no conflicts. Click Squash and merge. Check the final message: feat(auth): add login endpoint (#13) (the PR number, here 13, differs from the issue number). GitHub closes issue #12 because of Closes #12. Click Delete branch (or let GitHub do it).

Step 9: Clean up locally

$ git switch main
$ git pull --ff-only
Updating 8a1c9de..e5f6a77
Fast-forward
 ...
$ git branch -d feature/12-login-endpoint
error: the branch 'feature/12-login-endpoint' is not fully merged
$ git branch -D feature/12-login-endpoint
Deleted branch feature/12-login-endpoint (was d2f93c1).
$ git fetch --prune
$ git branch -vv

The -d failure is normal after a squash merge, because your four commits are not in main — only the squashed one is. You checked on GitHub that the PR is merged, so -D is safe. git fetch --prune removes remote-tracking branches that no longer exist on GitHub.

Step 10: Next task

Start again from step 1 with a fresh branch from the updated main. Never start a new feature on top of the old merged branch.

Common mistakes in the daily loop

  • Starting a branch from an out-of-date main, or from another unfinished feature branch.
  • Working directly on main by accident. Check git branch --show-current (or the prompt) before you commit.
  • Forgetting to push before the end of the day: your work exists only on one laptop.
  • Leaving a branch open for two weeks without updating it.
  • Committing to main locally by mistake — see the recovery playbook.

Tips

  • Set git config --global pull.ff only and git config --global fetch.prune true to make the loop safer and tidier.
  • Show the branch in your shell prompt or use the IDE status bar.
  • Commit often locally; tidy later with interactive rebase before review.

Interview: "Walk me through your Git workflow on a feature."

  • Pull the latest main, create a feature branch named after the ticket, commit small meaningful changes.
  • Push, open a PR linked to the issue, wait for CI, address review by pushing more commits.
  • Merge via the team's method (squash is common), delete the branch, pull main.
  • Mention staying up to date with main and never pushing directly to a protected main.

Interview questions — Branches and teamwork

What is a branch in Git?

A branch is a lightweight, movable pointer to a commit — a small file holding a commit id. Creating a branch copies no files, so it is instant. When you commit on a branch, the pointer moves forward to the new commit. HEAD points to the branch you are currently on.

What is HEAD? What is a detached HEAD?

HEAD is a pointer to where you are now: normally it points to a branch, which points to a commit. In a detached HEAD, it points straight to a commit (for example after git checkout a1b2c3d or checking out a tag). Commits you make there belong to no branch and can be lost. To keep them, run git switch -c new-branch. To leave without keeping anything, run git switch main.

What is the difference between a fast-forward merge and a three-way merge?

If the target branch has no new commits, Git only moves its pointer forward: a fast-forward, with no new commit. If both branches have new commits, Git compares the merge base and the two tips, combines the changes and creates a merge commit with two parents. --no-ff forces a merge commit; --ff-only refuses anything else.

How do you resolve a merge conflict?

Run git status to list the unmerged files. Open each, find the markers <<<<<<<, =======, >>>>>>>, write the correct final code and delete the markers. Build and test, run git add on the file, then git commit to finish. To cancel, use git merge --abort. Always read both sides, and ask the author if you are unsure.

What do "ours" and "theirs" mean in a conflict?

In a merge, ours is the branch you are on (HEAD) and theirs is the branch you are merging in. In a rebase they are reversed: ours is the branch you are rebasing onto, and theirs is your own commit being replayed. This surprises people, so check the labels in the markers.

How can you reduce merge conflicts?

Keep branches short-lived and PRs small, update your branch from main often, use a shared formatter and line-ending policy, avoid reformatting unrelated code, and talk to teammates about shared files. Build and test after each merge because semantic conflicts do not show up as Git conflicts.

What is a pull request, and how is it different from git merge?

A pull request is a GitHub feature: a request to merge one branch into another, with a page for review, comments, CI checks and approvals. Git has no pull requests. The final merge is still a Git merge, but the PR adds review and an audit trail before it. Pushing more commits to the branch updates the PR automatically.

Explain merge commit, squash and merge, and rebase and merge on GitHub.

Merge commit keeps all branch commits and adds a two-parent merge commit. Squash combines the whole PR into a single new commit on main. Rebase and merge replays each commit on top of main with new ids and no merge commit. Squash and rebase give a linear history; squash also hides messy commits and makes reverting a feature easy.

Why does git branch -d refuse to delete a branch after a squash merge?

-d only deletes a branch whose commits are reachable from the current branch. A squash merge creates a different commit, so the original commits are not reachable from main, and Git says the branch is not fully merged. After confirming on GitHub that the PR is merged, use git branch -D.

What makes a good commit message? What are Conventional Commits?

A short imperative subject (about 50 characters), a blank line, and a body that explains why. One logical change per commit. Conventional Commits adds a structure, type(scope): description, with types such as feat, fix, docs, refactor, test and chore, and ! for breaking changes. Tools use it to bump versions and write changelogs.

Compare GitHub flow, Git Flow and trunk-based development.

GitHub flow: only main plus short feature branches via PRs, deploy from main. Git Flow: main and develop plus feature, release and hotfix branches, built for versioned releases. Trunk-based: everyone merges into one trunk at least daily, with feature flags and strong CI. Choose by release model; keep branches short.

How do you delete a branch locally and on the remote?

Locally: git branch -d name (safe) or -D (force). Remotely: git push origin --delete name. Other people's remote-tracking copies disappear when they run git fetch --prune.

What does this print? You are on main and run git merge feature/x twice in a row.

The first run merges (fast-forward or a merge commit). The second prints Already up to date. because every commit of feature/x is now part of main, so there is nothing to do.

You merged the wrong branch and have conflicts you do not understand. What do you do?

If the merge is still in progress, run git merge --abort; it restores the state before the merge. Then merge the correct branch. If you already committed the merge but did not push, git reset --hard ORIG_HEAD or git reset --hard HEAD~1 undoes it. If you pushed, use git revert -m 1 <merge-commit>.

Cheat sheet — Branches and teamwork

  • git branch list local branches; -a all, -r remote, -vv with upstream
  • git switch -c name create a branch and move to it; git switch - goes back to the previous branch
  • git switch name move to an existing branch (old form: git checkout name)
  • git branch -m new rename the current branch
  • git branch -d / -D delete a merged branch / force-delete
  • git push origin --delete name delete a branch on the remote
  • git fetch --prune drop remote-tracking branches deleted on the remote
  • HEAD points to the current branch, which points to a commit; detached HEAD points to a commit directly
  • Branch names feature/, bugfix/, hotfix/, release/ plus ticket id, lowercase, hyphens
  • git merge name bring a branch into the current one; fast-forward when possible
  • --no-ff / --ff-only / --squash force a merge commit / refuse non-fast-forward / stage all changes without a merge link
  • git merge --abort cancel a merge that stopped on conflicts
  • Conflict markers <<<<<<< ours, =======, >>>>>>> theirs; remove all, then git add and git commit
  • git restore --ours/--theirs file take one side of a conflicted file
  • git log main..feature commits in feature that are not in main
  • gh pr create open a PR from the terminal (optional GitHub CLI)
  • Closes #12 in a PR description closes the issue when merged into the default branch
  • Review options Comment, Approve, Request changes; suggestions can be committed in one click
  • Merge options merge commit (keeps all), squash (one commit), rebase (linear, new ids)
  • Commit subject imperative, about 50 characters, no full stop, blank line before the body
  • Conventional Commits feat(scope): text; fix = patch, feat = minor, ! = major
  • GitHub flow main always deployable, short branches, PR, merge, deploy
  • Git Flow main + develop + feature/release/hotfix branches, for versioned releases
  • Trunk-based merge to one trunk daily, feature flags, strong CI
  • Daily loop pull main, branch, commit small, push, PR, review, merge, delete branch, pull main

Practice — Branches and teamwork

  1. Branch basics. In a new repository make two commits on main. Create feature/calculator with git switch -c, add a Calculator.java with an add method and commit. Switch back to main and check that the file is gone, then return. Done when git branch -vv shows both branches and git log --oneline --graph --all shows the feature commit ahead of main.
  2. Fast-forward and no-ff. Merge feature/calculator into main with a plain merge. Then create feature/subtract, commit, and merge it with --no-ff. Done when the log shows a straight line for the first merge and a merge commit with two parents for the second.
  3. Roadmap exercise: pull request. Push feature/calculator to your own GitHub repository, open a pull request into main with a proper description and Closes #1 (create issue #1 first), merge it with Squash and merge and delete the branch. Done when the issue closes by itself and you have synced your local main with git pull and deleted the local branch.
  4. Roadmap exercise: a conflict on purpose. Create a file Config.txt with price = 100. On one branch change that line to price = 120, on another to price = 90, commit both. Merge one into the other, read the markers, resolve by hand, run git add and commit. Done when the file has no markers and the log shows the merge commit. Repeat once and use git merge --abort.
  5. Detached HEAD rescue. Run git switch --detach HEAD~1, make a commit, then switch back to main and read Git's warning. Recover the commit by creating a branch with the hash. Done when git branch lists your rescue branch with the commit.
  6. Review a PR. Ask a friend (or use a second account) to open a PR in your repository. Leave one inline comment with a suggestion, one question, and request changes. Let them fix and push; then approve. Done when the PR shows Changes requested followed by Approved.
  7. Conventional Commits. Rewrite these into Conventional Commits and good subjects: "fixed login bug", "added new page", "updated readme", "removed old API, now clients must use v2". Done when the last one uses ! and a BREAKING CHANGE: footer.
  8. Compare merge options. Make three small commits on a branch. Merge three copies of it (create copies with git branch copy1 and so on) using a merge commit, git merge --squash and a rebase (git rebase main then fast-forward). Compare git log --oneline --graph for each. Done when you can explain the three shapes.
  9. Full team workflow. With a friend, create an issue, branch, push, PR, review, squash-merge and clean up, following the walkthrough exactly. Done when both machines show an updated main and no stale branches (git fetch --prune).
  10. Learn Git Branching. Finish the Main and Remote sections of Learn Git Branching (learngitbranching.js.org). Done when all levels in those sections show as solved.

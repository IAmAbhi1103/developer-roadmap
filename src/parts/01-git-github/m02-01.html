In Module 1 everything stayed on your own computer. A remote is another copy of your repository on a server. GitHub is the most popular place to host that copy. With a remote you get a backup, a way to share code with a team, and the base for pull requests, code review and automated builds.

This module connects your local repository to GitHub: creating an account and logging in safely (SSH key or token), adding a remote, pushing, fetching and pulling, understanding why a push is rejected, writing a README, and contributing to someone else's project through a fork. Git vs GitHub, and what a remote is

Git is the version control tool on your computer; GitHub, GitLab and Bitbucket are websites that host Git repositories; a remote is a named link from your repository to one of those hosted copies.

Beginners often say "Git" when they mean "GitHub". They are different things, and interviewers like to check that you know it.

What a remote is

A remote is a short name (an alias) for the URL of another copy of your repository. It is not a special kind of repository — it is just a bookmark stored in your local config. The remote copy is usually a bare repository on a server: history only, no working folder, because nobody edits files there.

Conventional remote names

origin
The default name for the repository you cloned from, or the one you publish to. git clone creates it automatically. The name has no magic meaning; it is only a convention.
upstream
By convention, the original project when you work from your own fork. Your fork is origin, the project you forked from is upstream (see Fork vs clone).

A repository can have many remotes: for example origin (your fork), upstream (the main project) and staging (a deployment target). Remotes only matter when you run fetch, pull or push; every other command works on local data.

The three things a remote gives you

  • Backup. If your laptop dies, the code is safe on GitHub.
  • Sharing. Teammates clone it, and you exchange commits through it.
  • Integration. Pull requests, code review, issues, and CI/CD pipelines are triggered by pushes to the remote.

Edge cases

  • A remote is not live. Git does not watch it. Nothing leaves or enters your repository until you run push, fetch or pull.
  • A remote can be a local path (../backup.git) or a network share. GitHub is simply the most common choice.
  • GitHub can go down, and an owner can delete a repository. A remote is not your only backup unless you also keep clones.

Interview: "What is the difference between Git and GitHub?"

  • Git is the distributed version control tool; GitHub is a cloud service that hosts Git repositories and adds collaboration features such as pull requests, issues and Actions.
  • GitLab and Bitbucket are alternatives; the Git commands are the same.
  • A remote is a named URL (usually origin) for a hosted copy of your repo.

Creating your GitHub account

Sign up at github.com with a username you can show on a CV, turn on two-factor authentication, and make your commit email match an email verified on your account.

Your GitHub profile is public by default and recruiters look at it. A few decisions at the start save trouble later.

  1. Go to github.com, choose Sign up, and verify your email.
  2. Pick a professional username (for example asha-rao, not cool_killer_99). It appears in every repository URL and is awkward to change later because links break.
  3. Fill in your name, a short bio and a photo. A complete profile looks trustworthy.
  4. Turn on two-factor authentication (2FA) in Settings → Password and authentication. Use an authenticator app or a passkey. GitHub requires 2FA for contributors, and a hijacked account with code access is serious.
  5. Add your Git email (next section) and then set up login from your computer: SSH key or HTTPS with a token.

Email and the noreply address

GitHub attaches a commit to your profile by matching the commit's email with an email on your account. If they do not match, the commit shows a grey avatar and does not count in your contribution graph. Add your email in Settings → Emails and verify it.

Commits are public. To avoid exposing your personal address, turn on Keep my email addresses private and use the private address GitHub shows you, which has the form ID+username@users.noreply.github.com. Set it in Git:

$ git config --global user.email "12345678+asha-rao@users.noreply.github.com"

(Use the exact address from your own settings page; the numbers above are an example.) Also tick Block command line pushes that expose my email if you want GitHub to refuse commits that use your private address by mistake.

Make your profile work as a portfolio

  • Pin your best 4–6 repositories, each with a good README.
  • Create a profile README: a repository with the same name as your username and a README.md in it. GitHub shows that file at the top of your profile. Put a short intro, your tech stack and links.
  • Commit regularly. The green contribution graph is not the goal, but steady, real work shows.
  • Never leave secrets, college assignment dumps or half-broken projects as your pinned work.

Rule: never share your password or token

Do not paste tokens into chats, screenshots, code or commit messages. GitHub scans public repositories for leaked tokens and revokes them, but treat any leaked token as compromised and revoke it yourself in Settings.

Edge cases

  • GitHub stopped accepting account passwords for Git operations over HTTPS in 2021. You need a token, Git Credential Manager (browser login) or an SSH key.
  • Commits made before you added the email to your account are not re-linked automatically, but adding the email afterwards does link them.
  • Students can get extra features through the GitHub Education programme; check the current offer on docs.github.com.

Log in with an SSH key

Create an ed25519 key pair with ssh-keygen, upload the public key to GitHub, and use git@github.com:user/repo.git URLs — no password or token for every push.

SSH uses a pair of keys: a private key that never leaves your computer and a public key that you give to GitHub. When you push, GitHub sends a challenge that only the owner of the private key can answer. Nothing secret travels over the network.

Both are secure. Pick one and stay with it. Many developers use SSH on their laptop; HTTPS with the credential manager is just as fine.

Step 1: check for an existing key

$ ls ~/.ssh
id_ed25519  id_ed25519.pub  known_hosts

If id_ed25519 and id_ed25519.pub exist, you already have a key and can skip to step 3. In Git Bash ~ is your user folder, C:\Users\asha.

Step 2: generate an ed25519 key

$ ssh-keygen -t ed25519 -C "asha@example.com"
Generating public/private ed25519 key pair.
Enter file in which to save the key (/c/Users/asha/.ssh/id_ed25519):
Enter passphrase (empty for no passphrase):
Enter same passphrase again:
Your identification has been saved in /c/Users/asha/.ssh/id_ed25519
Your public key has been saved in /c/Users/asha/.ssh/id_ed25519.pub
  • -t ed25519 chooses the key type. Ed25519 is modern, short and secure; it is the recommended type for GitHub.
  • -C adds a comment (usually your email) so you can recognise the key later. It has no security meaning.
  • Press Enter to accept the default location. Set a passphrase — it encrypts the private key file, so a stolen laptop does not give away your access.

Step 3: let the ssh-agent remember the passphrase

The ssh-agent is a background program that holds your unlocked key, so you type the passphrase once per session. In Git Bash:

$ eval "$(ssh-agent -s)"
Agent pid 2481
$ ssh-add ~/.ssh/id_ed25519
Enter passphrase for /c/Users/asha/.ssh/id_ed25519:
Identity added: /c/Users/asha/.ssh/id_ed25519 (asha@example.com)

On Windows you can instead use the built-in OpenSSH agent service (start it from an administrator PowerShell with Get-Service ssh-agent | Set-Service -StartupType Manual and Start-Service ssh-agent), then run ssh-add in a normal terminal. Either way is fine.

Step 4: add the public key to GitHub

$ cat ~/.ssh/id_ed25519.pub
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIExampleOnlyNotARealKeyxxxxxxxxxxxxxxxxxxx asha@example.com

Copy the whole line. In GitHub open Settings → SSH and GPG keys → New SSH key, give it a title such as "Asha laptop", choose type Authentication Key and paste the line.

Rule: share only the .pub file

The file ending in .pub is public and safe to share. The file without an extension (id_ed25519) is your private key. Never upload, email or commit it. If it leaks, delete the key from GitHub and generate a new one.

Step 5: test the connection

$ ssh -T git@github.com
The authenticity of host 'github.com (140.82.112.4)' can't be established.
ED25519 key fingerprint is SHA256:...
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
Hi asha-rao! You've successfully authenticated, but GitHub does not provide shell access.

The first time, SSH asks whether to trust GitHub. Compare the fingerprint with the one published in GitHub's documentation (docs.github.com, "GitHub's SSH key fingerprints"), then answer yes. The final line means success — "no shell access" is expected, because GitHub only serves Git. Now use the SSH URL when you clone or add a remote:

$ git clone git@github.com:asha-rao/billing-service.git

If a repository already uses an HTTPS URL, switch it with git remote set-url origin git@github.com:asha-rao/billing-service.git (see Managing remotes).

Several GitHub accounts (work and personal)

Create one key per account and describe them in ~/.ssh/config. Then use the host alias in the remote URL (git@github-work:company/repo.git).

Host github-personal
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes

Host github-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_work
    IdentitiesOnly yes

Errors you will meet

  • Permission denied (publickey). — GitHub does not know any key your computer offered. Check that you uploaded the .pub file to the right account, that the key is loaded (ssh-add -l), and run ssh -vT git@github.com to see which keys are tried.
  • Could not resolve hostname github.com — no internet or DNS problem.
  • Connection timed out on port 22 — a firewall blocks SSH. GitHub supports SSH on port 443 with host ssh.github.com; set it in ~/.ssh/config.
  • WARNING: UNPROTECTED PRIVATE KEY FILE! — on Linux and macOS the key file must be readable only by you (chmod 600).
  • Host key verification failed — the saved fingerprint does not match; make sure you are on a trusted network before you accept a changed one.

Conventions

  • One key per device, so you can revoke a lost laptop without affecting the others.
  • Use ed25519 with a passphrase. Avoid old DSA keys and short RSA keys.
  • Remove keys from GitHub when you stop using a device.

HTTPS login: tokens and Git Credential Manager

With HTTPS you log in through Git Credential Manager (a browser sign-in) or a personal access token used as the password; prefer a fine-grained token with only the permissions you need.

GitHub no longer accepts your account password for Git over HTTPS. You prove who you are in one of two ways.

Option 1: Git Credential Manager (easiest)

Git Credential Manager (GCM) installs with Git for Windows. When you first clone, push or pull over HTTPS, it opens a browser window where you sign in to GitHub (with your 2FA). It then stores a token in the Windows Credential Manager and reuses it, so you are not asked again.

$ git push -u origin main
# a browser window opens: "Sign in to GitHub" -> Authorize
Enumerating objects: 12, done.
To https://github.com/asha-rao/billing-service.git
 * [new branch]      main -> main

Check the helper with git config --global credential.helper; on Windows it prints manager. If a wrong or old login is stuck, remove it in the Windows search bar under Credential Manager → Windows Credentials → git:https://github.com, and Git will ask again.

Option 2: Personal access token (PAT)

A personal access token is a long random string that acts as a password for one purpose. GitHub offers two kinds:

PointFine-grained tokenClassic token
Scope of accessChosen repositories onlyAll repositories you can access
PermissionsDetailed (for example "Contents: read and write")Broad scopes such as repo
ExpiryRequiredOptional
RecommendationPreferredUse only where fine-grained tokens are not supported
  1. In GitHub open Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
  2. Give it a name, a short expiry (for example 30–90 days) and select only the repository it needs.
  3. Under repository permissions give Contents read and write (enough for push and pull).
  4. Copy the token once — GitHub will never show it again.
  5. Use it as the password when Git asks. The username is your GitHub username.
$ git push
Username for 'https://github.com': asha-rao
Password for 'https://asha-rao@github.com': <paste the token here>

The credential helper then stores the token so you paste it only once. Tokens are also what scripts and CI servers use, usually from an encrypted secret and never from the repository.

Mistake: putting the token inside the remote URL

You will see tutorials that use https://TOKEN@github.com/user/repo.git. It saves the token in plain text in .git/config and in your shell history. Use the credential helper instead.

Errors you will meet

  • remote: Invalid username or token. Password authentication is not supported for Git operations. — you typed your account password. Use a token or the browser login.
  • fatal: Authentication failed — expired, revoked or under-privileged token; stale credentials in the credential manager. Remove the stored credential and try again.
  • remote: Permission to user/repo.git denied to other-user — you are logged in as a different account than the repository owner; clear the cached login.
  • remote: Repository not found — often a private repository and a token that cannot see it, or a typo in the URL.

Tip: the GitHub CLI

The optional gh tool (cli.github.com) lets you run gh auth login once, and then create repositories and pull requests from the terminal. It is handy but not needed for this module.

Interview: "HTTPS or SSH for GitHub? How do you authenticate?"

  • Both work. SSH uses a key pair and needs no prompts after setup; HTTPS uses a token or Git Credential Manager.
  • Passwords are not accepted any more; tokens should be fine-grained, short-lived and least-privilege.
  • Never commit keys or tokens; the private key stays on your machine.

Interview questions — GitHub and remotes

What is the difference between Git and GitHub?

Git is the open-source distributed version control tool that runs locally. GitHub is a hosting service for Git repositories that adds pull requests, issues, code review, Actions and more. GitLab and Bitbucket are similar services; the Git commands are the same on all of them.

What is a remote? What are origin and upstream?

A remote is a named URL pointing to another copy of the repository. origin is the conventional name of the repository you cloned from or push to. upstream is the conventional name for the original project when origin is your fork. Both names are only conventions.

HTTPS or SSH for GitHub — how do you choose, and how do you set up SSH?

Both are secure. HTTPS is easiest (browser login via Git Credential Manager or a token); SSH needs no prompts after setup. For SSH: ssh-keygen -t ed25519 -C "email", add the public key (.pub) in GitHub Settings, test with ssh -T git@github.com, and use git@github.com:user/repo.git URLs. The private key never leaves your machine.

Can you push to GitHub with your account password?

No. GitHub does not accept account passwords for Git operations. Use an SSH key, Git Credential Manager (browser sign-in), or a personal access token. Prefer fine-grained tokens with limited repository access and an expiry date.

What does git push -u origin main do?

It pushes local main to the remote origin and sets origin/main as the upstream (tracking) branch of main. After that, git push and git pull work without arguments and git status shows ahead/behind counts.

What is origin/main, and how is it different from main?

main is your own branch, which you move by committing. origin/main is a remote-tracking branch: a read-only bookmark for where main was on the server at your last fetch or push. It can be stale until you fetch.

What is the difference between git fetch and git pull?

Fetch downloads new commits and updates remote-tracking branches such as origin/main; it never changes your branch or working files, so it is always safe. Pull is fetch followed by a merge (or a rebase with --rebase) into your current branch, so it can create a merge commit or conflicts.

Your git push is rejected with "fetch first" or "non-fast-forward". Why, and what do you do?

The remote branch has commits that you do not have; pushing would overwrite them. Run git pull --rebase (or git pull), fix any conflicts, run the tests, and push again. Do not force push to get past the error.

When is a force push acceptable, and what is --force-with-lease?

Only on a branch that nobody else uses, after you rewrote history with amend or rebase. --force-with-lease forces the push only if the remote branch is still where you last saw it, so you do not overwrite a teammate's new commits. Never force push shared branches such as main.

What is the difference between a fork and a clone?

A clone is a Git copy on your computer. A fork is a GitHub copy under your own account, linked to the original so you can open pull requests. If you can push to the repository, clone it. If not (open source), fork it, clone your fork, and add the original as upstream.

Walk through contributing to an open-source project.

Fork, clone your fork, add upstream, read CONTRIBUTING.md, create a branch, make a small change, commit with a clear message, push to your fork (origin), then open a pull request that links the issue. Respond to review by pushing more commits to the same branch.

How do you keep a fork in sync with the original project?

Add the original as upstream, then git fetch upstream, merge or rebase upstream/main into your local main, and push to origin. Alternatively click Sync fork on GitHub and pull. Keep your own work on branches so the sync is a clean fast-forward.

You created a GitHub repo with a README and now cannot push your local project. What happened?

The two repositories have unrelated histories: GitHub already holds a first commit that your local repository does not have. Pull with --allow-unrelated-histories once, then push; or create the GitHub repository empty next time.

What belongs in a good README?

A one-line description, a screenshot or sample output, the tech stack, features, how to run it with exact commands, configuration or environment variables (without real secrets), API documentation, how to run tests, a live link, and the licence.

Cheat sheet — GitHub and remotes

  • Git vs GitHub Git is the local tool; GitHub hosts repositories and adds pull requests, issues, Actions
  • remote a named URL for another copy of the repo; origin is yours, upstream is the original project
  • ssh-keygen -t ed25519 -C "email" create an SSH key pair; share only the .pub file
  • ssh -T git@github.com test SSH login ("successfully authenticated")
  • HTTPS login Git Credential Manager (browser) or a fine-grained personal access token; passwords are not accepted
  • git remote -v list remotes; add, rename, remove, set-url manage them
  • git remote add origin <url> link a local repo to GitHub
  • git push -u origin main push and set the upstream so later git push/git pull need no arguments
  • origin/main read-only bookmark of the server's main as of the last fetch or push
  • git branch -vv shows each branch's upstream and ahead/behind
  • git fetch download only, always safe; git fetch --prune also drops deleted remote branches
  • git pull = fetch + merge; git pull --rebase = fetch + rebase; set pull.rebase once
  • git log main..origin/main commits you would receive from a pull
  • Push rejected (fetch first / non-fast-forward) remote has commits you lack: pull --rebase, test, push
  • git push --force-with-lease the only acceptable force push, and only on your own branch
  • Publish a project create an empty GitHub repo, git remote add origin, git push -u origin main
  • refusing to merge unrelated histories use --allow-unrelated-histories once, or start from an empty repo
  • README.md description, screenshot, stack, run steps, env vars, API docs, tests, licence
  • Markdown # headings, - lists, [text](url) links, ![alt](img) images, triple backticks with language for code, | tables
  • Fork your GitHub copy of someone else's repo; clone your Git copy on disk
  • Open-source flow fork → clone → add upstream → branch → commit → push to fork → pull request
  • Sync a fork git fetch upstream, merge or rebase upstream/main, push; or "Sync fork" button
  • git clone --depth 1 shallow clone, latest commit only; -b name picks the branch
  • LICENSE no licence means all rights reserved; MIT is the usual simple choice for personal projects
  • .github/ workflows, PR and issue templates, CODEOWNERS, dependabot.yml

Practice — GitHub and remotes

  1. Account and 2FA (easy). Create (or review) your GitHub account with a professional username, enable two-factor authentication and set a noreply or verified email in Git. Done when a test commit shows your avatar on GitHub.
  2. SSH key (easy). Generate an ed25519 key with a passphrase, add the public key to GitHub and run ssh -T git@github.com. Done when it prints your username in the success message.
  3. Publish java-practice (easy). Create a repository java-practice on GitHub (empty). In your local project add a Java .gitignore, commit, then git remote add origin and git push -u origin main. Done when the files appear on GitHub, target/ and .idea/ do not, and git status says your branch is up to date with origin/main.
  4. Read the story (easy). Make five small commits with clear messages and push them. Done when git log --oneline --graph reads like a story and the GitHub commits page shows the same five messages.
  5. Fetch vs pull (medium). Clone your repository a second time into another folder. Commit and push a change from the first copy. In the second copy run git fetch, inspect with git log main..origin/main and git diff main origin/main, and then git pull. Done when you can explain which of your branches each command moved.
  6. Cause and fix a rejected push (medium). With the two copies, commit in both without pulling and push from the second one. Read the error, fix it with git pull --rebase, and push. Done when both copies show the same history and nobody's commit was lost.
  7. Write a README (medium). Add a README.md to a Spring Boot project using the template in this module: description, stack, run steps, environment variables, API table. Done when a friend can run the project from a fresh clone using only the README.
  8. Profile README (medium). Create the repository named after your username, add a short profile README and pin two projects. Done when it shows at the top of your profile.
  9. Fork and sync (hard). Fork any public Java repository, clone your fork, add upstream, and sync using both the command line and the Sync fork button. Done when git remote -v shows both remotes and your main matches upstream.
  10. Your first pull request (hard). Fork a beginner-friendly open-source repository, fix a typo or unclear sentence in its docs on a new branch, push it to your fork and open a real pull request that follows the project's CONTRIBUTING.md. Done when the pull request is open with a clear title and description.

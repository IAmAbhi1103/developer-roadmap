Writing a good PR and reviewing code

A good pull request is small, explains what and why in its description, and passes CI; a good review reads the code for correctness, design and tests, comments politely, and ends with Approve or Request changes.

The previous article showed the mechanics of a pull request. This one is about the human part, which decides how fast your code gets merged. Teams remember developers who write clear PRs and give useful reviews.

Writing a good PR

Think of your reviewer as a busy colleague who has never seen your branch. In two minutes they should understand what changed, why, how to check it and what to look at carefully.

  • Keep it small. Aim for a change a reviewer can read in 15–20 minutes. Large reviews get skimmed, and skimmed reviews miss bugs. If a feature is big, split it: first the database migration, then the service, then the controller, then the UI.
  • One purpose. Do not mix a bug fix, a refactor and a new feature. Put formatting-only changes in their own PR.
  • Title: a specific one-liner in the same style as a commit subject: Add login endpoint, not Changes or Fix stuff.
  • Description: use a template (below). Add screenshots or a short screen recording for UI changes, and example requests and responses for API changes.
  • Review your own PR first. Open the Files changed tab and read your diff as if it were someone else's. You will find forgotten System.out.println calls, commented-out code and stray files.
  • Make CI green before you ask for a review. Reviewers should not be the first to find a failing test.

Teams put a PR template in the repository, in .github/pull_request_template.md. GitHub fills the description box with it for every new PR:

Reviewing someone else's code

Open the Files changed tab. Read the description first, then the tests (they show the intent), then the production code. Check these things, roughly in this order:

  1. Does it solve the problem? Compare the code with the linked issue. Are edge cases handled: null, empty list, duplicate request, a user without permission?
  2. Correctness and bugs. Off-by-one errors, wrong HTTP status, missing transaction, race conditions, resources that are not closed, NullPointerException risks.
  3. Security. No secrets in the code; input validated; authorisation checked; no SQL built by string concatenation; no sensitive data in logs.
  4. Design. Is the logic in the right layer (controller, service, repository)? Does it follow the patterns already used in the project? Is it simpler than it could be?
  5. Tests. Is the new behaviour tested, including the failure cases? Do the tests really assert something?
  6. Readability. Clear names, short methods, comments that explain why, not what.
  7. Performance and data. N+1 queries, missing indexes for new queries, loading a whole table into memory, a database migration that locks a big table.
  8. Leftovers. Debug prints, commented-out code, unrelated files, TODOs without a ticket.

Automate what a machine can check (formatting, unused imports, static analysis, tests) so that humans spend their time on logic and design.

How to comment

Hover over a line in Files changed and click the blue + to comment on that line. Drag across several lines to comment on a range. Two kinds of review comments exist:

  • Single comment — posted immediately and visible at once.
  • Start a review — comments are collected as pending. You send them together in one go, which means one notification for the author instead of twenty.

A suggestion lets you propose the exact replacement text. Click the suggestion icon in the comment box, or write a fenced block that starts with ```suggestion. The author can click Commit suggestion and GitHub makes the commit on the PR branch. It is perfect for typos and one-line fixes.

Comment etiquette

  • Review the code, not the person. Write "This method can return null" and not "You forgot null checks".
  • Ask questions before you accuse: "What happens if the list is empty?"
  • Explain why and, if you can, suggest a fix.
  • Mark small taste points as optional with a prefix such as nit:. Many teams also label comments blocking or question.
  • Praise good work too: "Nice test, this covers the tricky case."
  • Do not leave a review waiting for days. Aim for the same working day.
  • If a discussion goes back and forth more than twice, talk face to face or on a call, then write the outcome in the PR.

Responding to review as the author

  1. Read all comments before you start fixing anything.
  2. Fix what you agree with, commit and push to the same branch. The PR updates by itself. Use Commit suggestion for tiny fixes.
  3. Reply to each comment: "Done" or a short explanation. If you disagree, say why politely and offer a trade-off; if the reviewer still insists, follow the team lead.
  4. Click Resolve conversation only on threads that are really settled (many teams let the reviewer resolve).
  5. Click the re-request review icon next to the reviewer's name so they are notified.
  6. Do not squash or force-push in the middle of a review unless the team agrees — it makes it hard for the reviewer to see what changed since their last look.

After new commits, approvals can become stale

Branch protection has a setting called Dismiss stale pull request approvals when new commits are pushed. When it is on, a new push removes earlier approvals and you need a fresh review. Another setting, Require approval of the most recent reviewable push, makes sure someone other than the pusher looks at the final code.

Rules

  • Nobody merges unreviewed code into main, and you cannot approve your own PR.
  • Every blocking comment is fixed or answered before merge.
  • The PR description says what, why and how it was tested.

Common mistakes

  • Approving with "LGTM" (looks good to me) without reading the diff.
  • Reviewing style by hand that a formatter should handle.
  • Sending a 2,000-line PR and asking for a "quick look".
  • Taking comments personally, or replying defensively. A comment is about the code.
  • Pushing a big new change after the approval, with no new review.

Real projects

Most teams have a review checklist, a rule such as "two approvals for payment code", and a CODEOWNERS file that asks the owners of a folder automatically (Module 4). Seniors often write a comment as a question to help juniors learn instead of just correcting them. Reviewing is also the fastest way for you to learn a codebase: review small PRs from day one.

Interview: "How do you do a code review? What do you look for?"

  • Start with the description and linked issue; read tests, then code.
  • Check correctness and edge cases, security, design fit, tests, readability and performance.
  • Leave specific, polite, actionable comments, use suggestions for small fixes, and separate blocking from optional.
  • End with Approve or Request changes; follow up on re-review.
  • Add that you want CI and linters to catch style so people focus on logic.

GitHub merge options: merge commit, squash and rebase

When a PR is ready, GitHub can merge it in three ways: a merge commit (keeps everything, adds a join commit), squash and merge (all commits become one), or rebase and merge (commits replayed on top with new ids, no merge commit).

The green button at the bottom of a pull request has a small arrow with three choices. A repository admin can switch each choice on or off in Settings → General → Pull Requests, so you may see only one or two. The choice decides what main's history looks like for years, so teams pick it deliberately.

Take a PR branch with three commits: "Add entity", "Fix typo" and "Add endpoint". Here is what each option does to main.

1. Create a merge commit

This is the same as git merge --no-ff: all three commits are kept, plus one merge commit with two parents. The message is Merge pull request #12 from acme/feature/12-login-endpoint.

2. Squash and merge

All commits of the PR are combined into one new commit on main. The branch's own commits do not reach main. By default the commit subject is the PR title followed by the PR number, for example Add login endpoint (#12), and the body lists the individual commit messages (you can edit both before merging).

3. Rebase and merge

GitHub replays each commit of the PR on top of the latest main, one by one. The result is a straight line and no merge commit. The commits are re-created with new ids (the code is the same, but the hashes change, and the committer becomes you), which is the same thing git rebase does locally. Because this needs a clean replay, the option is not available when the PR has conflicts; you must rebase locally first.

What teams choose

  • Squash and merge is the most common choice in product teams. main gets one commit per PR, which matches one ticket, and the PR title becomes the commit message — so it must be good (and fits Conventional Commits, see next articles). Reverting a feature is one git revert. The cost: you lose the fine-grained commits and git bisect can only point at the whole PR.
  • Merge commit is preferred when the history of how a feature was built matters, and by teams that use Git Flow. It is the safest option because it rewrites nothing.
  • Rebase and merge suits teams that make each commit small, buildable and well-named, and want a linear log with full detail. It fails more often because it needs a conflict-free replay.

Many repositories also require a linear history in branch protection, which allows only squash or rebase merges.

Mistake: building on a branch that was squash-merged

After a squash merge, your old feature branch still contains the original commits, while main has a different single commit with the same changes. If you keep working on that old branch (or branch a second feature off it) and merge again, Git sees the old commits as new and you get strange conflicts. After a squash or rebase merge, delete the branch and start the next one from the updated main.

Edge cases

  • Squash merges credit one author. GitHub adds Co-authored-by: lines for other commit authors.
  • After a squash or rebase merge, local git branch -d feature/x prints error: the branch 'feature/x' is not fully merged. The work is merged, Git just cannot see it. Check on GitHub, then use git branch -D feature/x.
  • GitHub can auto-delete head branches after merge (a repository setting) and can enable auto-merge on a PR.

Conventions

  • Follow the team's setting; do not mix styles in one repository.
  • With squash, edit the final message so it describes the change, not "Address review comments".
  • Turn on auto-delete of merged branches to avoid hundreds of stale branches.

Interview: "Squash vs merge commit vs rebase on GitHub?"

  • Merge commit: keeps all commits plus a two-parent merge commit; full history, branchy graph.
  • Squash: one commit per PR, linear, hides messy commits, easy to revert; loses detail.
  • Rebase and merge: replays commits with new ids, linear, no merge commit; needs no conflicts.
  • Name your team's choice and the reason; mention that squash needs -D to delete the local branch.

Writing good commit messages

A good commit message has a short subject in the imperative mood ("Add login endpoint"), a blank line, and an optional body that explains why; each commit contains one logical change.

The commit log is the diary of your project. Six months later, nobody remembers why a line was changed, but git log and git blame do. A message like fix or changes wastes that. A good message lets a teammate, or you, understand a change without opening the diff.

Anatomy

Add login endpoint

Users could not sign in because no endpoint existed. Add POST /api/auth/login,
which checks the BCrypt hash and returns a JWT valid for one hour.

Wrong passwords and unknown emails both return 401 so that the response does
not reveal which emails are registered.

Closes #12
  • Subject line — one line, up to about 50 characters (72 is the hard limit tools like git log --oneline and GitHub start to cut), no full stop at the end, first letter capital.
  • Blank line — required. Git uses it to separate subject from body.
  • Body (optional) — wrapped at about 72 characters. Explain what and, more importantly, why. The diff already shows how.
  • Footer (optional) — issue references (Closes #12), Co-authored-by:, BREAKING CHANGE:.

Imperative mood and "present tense"

Write the subject as a command, as if finishing the sentence "If applied, this commit will…": Add, Fix, Remove, Rename, Update. This is also the style Git itself uses for its own messages (Merge branch…, Revert "…"). People often call it "present tense"; the important part is to use Add, not Added or Adds.

Bad

fix
changes
Fixed bug.
Added some stuff and also refactored the OrderService and updated pom.
wip
asdf

Good

Add login endpoint
Fix NullPointerException when cart is empty
Remove unused Razorpay client
Rename OrderDto to OrderResponse
Upgrade Spring Boot to 3.5.7

One change per commit

An atomic commit contains exactly one logical change and leaves the project in a working state (it builds and tests pass). Do not mix a bug fix, a rename and a new feature. Benefits: easy review, easy git revert of just one thing, easy git cherry-pick, and git bisect can find the exact bad change.

If you edited many things, split them while staging. git add -p asks hunk by hunk what to include:

$ git add -p
@@ -12,6 +12,9 @@ public class OrderService {
+    public void cancel(long orderId) {
Stage this hunk [y,n,q,a,d,s,e,?]? y

Keys: y stage, n skip, s split the hunk into smaller ones, e edit by hand, q quit.

What to write in the body

  • The reason: the bug you saw, the requirement, the decision.
  • What you tried and rejected, if a future reader might wonder.
  • Side effects and anything surprising ("this changes the default timeout from 30s to 10s").
  • Links to issues, not long discussions — the discussion lives in the issue.

For a one-line message, git commit -m "Add login endpoint" is fine. For a body, run git commit without -m and write in the editor, or pass -m twice: the first is the subject, the second becomes the body.

git commit -m "Fix total for empty cart" \
  -m "calculateTotal() threw ArithmeticException. Return 0 for an empty cart."

Rules

  • Subject in the imperative, no full stop, about 50 characters.
  • Blank line between subject and body.
  • One logical change per commit, and each commit builds.
  • Never put secrets or personal data in a message — it stays in history.

Common mistakes

  • Vague subjects: update, fix issues, final, final2.
  • Describing the file, not the change: Changes in UserService.java.
  • "Fix review comments" commits stay in history if you do not squash — fix them up first (interactive rebase).
  • Giant "end of day" commits with fifty files.
  • Writing the message in Hinglish or in slang in a shared project — use clear English.

Tips

  • Save work-in-progress as small local commits freely, then clean them up before opening the PR.
  • git commit --amend fixes the last message if you have not pushed yet.
  • git config --global commit.verbose true shows the diff inside the editor while you write.
  • A PR template and a commit template (git config commit.template) remind the team of the format.

Interview: "What makes a good commit message?"

  • Short imperative subject (about 50 characters), blank line, body explaining why.
  • One logical change per commit, so it can be reviewed, reverted and bisected on its own.
  • References the issue; may follow Conventional Commits.
  • Mention that the diff shows what changed; the message tells why.

Conventional Commits

Conventional Commits is a simple format for commit subjects — type(scope): description, like feat(auth): add login endpoint — that tools can read to build changelogs and decide the next version number.

A plain good message is for humans. Conventional Commits adds a small, strict structure on top so that machines can also read it. Many teams use it together with automatic release tools. The format is:

type(scope): short description

optional body

optional footer(s)
  • type — what kind of change it is (table below).
  • scope (optional) — the part of the system, in brackets: auth, cart, api, ui.
  • description — short, imperative, lower case, no full stop.
  • ! — a mark before the colon that says "breaking change".

Types

TypeUse forExample
featA new feature for the userfeat(cart): add coupon support
fixA bug fixfix(order): handle empty cart
docsDocumentation onlydocs: explain local setup
styleFormatting, no code meaning changestyle: apply google-java-format
refactorCode restructure, no behaviour changerefactor(auth): extract JwtService
perfPerformance improvementperf(search): add index on email
testAdd or fix teststest(auth): cover wrong password
buildBuild system or dependenciesbuild: upgrade Spring Boot
ciCI configurationci: cache Maven repository
choreOther maintenancechore: update .gitignore
revertReverts an earlier commitrevert: feat(cart): add coupon support

The specification itself only requires feat and fix; the other types come from common conventions (such as the Angular project's) and teams may add their own.

Breaking changes

A breaking change forces users of your API to change their code. Mark it with ! after the type or scope, or with a footer that starts with BREAKING CHANGE::

feat(api)!: rename /orders to /v2/orders

BREAKING CHANGE: clients must call /v2/orders. The old path returns 404.

Link with semantic versioning

CommitVersion bumpExample
fixPATCH1.4.2 → 1.4.3
featMINOR1.4.3 → 1.5.0
Any type with ! or BREAKING CHANGEMAJOR1.5.0 → 2.0.0

Release tools such as release-please or semantic-release read the log since the last release, choose the next version from these rules and write the changelog. (Details of versions are in Tags and releases.) You do not need these tools to use the format; it is useful just for clear history.

Using it in a team

  • With squash and merge, only the PR title becomes the commit. Some teams add a check that rejects PR titles that do not follow the format.
  • A commit-msg Git hook (for example with commitlint) can check each message on your machine (hooks).
  • Pick scopes from a short list the team agrees on; do not invent a new scope for every commit.

Rules

  • A type is required; a colon and a space follow the type or scope.
  • Breaking changes use ! or a BREAKING CHANGE: footer.
  • Use feat only for user-visible features and fix only for bugs. Do not call a refactor a fix.

Common mistakes

  • Using feat for everything, which makes MINOR bumps meaningless.
  • Hiding a breaking change inside a normal fix.
  • Mixing several types in one commit — split it.
  • Long, vague scopes such as (backend-service-changes).

Real projects

Not every company uses Conventional Commits; many just use ticket ids such as CRM-142: Add login endpoint. Follow what the project already does. If there is no rule, Conventional Commits is a safe, widely understood choice.

Interview: "What are Conventional Commits?"

  • A format type(scope): description with types such as feat, fix, docs, refactor, test and chore.
  • ! or a BREAKING CHANGE: footer marks incompatible changes.
  • It maps to SemVer: fix = patch, feat = minor, breaking = major, and drives automatic changelogs and releases.

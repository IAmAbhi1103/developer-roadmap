Managing remotes and tracking branches

Use git remote add origin <url> to link a repository to GitHub, git push -u origin main to publish and set tracking, and origin/main to mean "my last known copy of the remote's main".

The remote commands

CommandPurpose
git remote -vList remotes with their fetch and push URLs
git remote add <name> <url>Add a remote
git remote rename old newRename a remote
git remote remove <name>Delete the link (not the remote repository)
git remote set-url <name> <url>Change a remote's URL (for example HTTPS to SSH)
git remote show originDetailed report: branches, tracking, what push and pull would do
git remote prune originDelete stale remote-tracking branches that no longer exist on the server
 
$ git remote add origin git@github.com:asha-rao/billing-service.git
$ git remote -v
origin  git@github.com:asha-rao/billing-service.git (fetch)
origin  git@github.com:asha-rao/billing-service.git (push)
$ git remote set-url origin https://github.com/asha-rao/billing-service.git
$ git remote rename origin github
$ git remote remove github

The remotes are stored in .git/config:

[remote "origin"]
	url = git@github.com:asha-rao/billing-service.git
	fetch = +refs/heads/*:refs/remotes/origin/*
[branch "main"]
	remote = origin
	merge = refs/heads/main

The fetch = line says: copy each branch refs/heads/X from the server to refs/remotes/origin/X locally. The [branch "main"] section is the tracking information described below.

Remote-tracking branches: origin/main

When you fetch, Git does not touch your own branches. It stores what it learned about the server in remote-tracking branches named <remote>/<branch>, for example origin/main. Think of origin/main as a bookmark: "the last time I talked to GitHub, its main was here". You cannot commit on it directly; only fetch, pull and push move it.

A key point: origin/main can be out of date. If a teammate pushed an hour ago and you have not fetched, your origin/main still shows the old position.

Publishing: git push -u origin main

$ git push -u origin main
Enumerating objects: 15, done.
Counting objects: 100% (15/15), done.
Writing objects: 100% (15/15), 2.31 KiB | 2.31 MiB/s, done.
To github.com:asha-rao/billing-service.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

The syntax is git push <remote> <branch>. The -u (short for --set-upstream) does two things: pushes, and records that local main tracks origin/main. After that, plain git push, git pull and git status know which remote branch you mean. You need -u only the first time for each branch.

Upstream (tracking) branches

The upstream branch of a local branch is the remote branch it is paired with. Tracking gives you:

  • git push and git pull without arguments;
  • the friendly summary in git status: Your branch is ahead of 'origin/main' by 2 commits.
$ git branch -vv
  feature/coupon 3b4c5d6 Add Coupon entity
* main           7d3e4f2 [origin/main: ahead 1] Describe the service in README
$ git status
On branch main
Your branch is ahead of 'origin/main' by 1 commit.
  (use "git push" to publish your local commits)
Status lineMeaningNext step
Your branch is up to date with 'origin/main'Same commit as your last known server stateNothing
Your branch is ahead of 'origin/main' by N commitsYou have commits not pushed yetgit push
Your branch is behind 'origin/main' by N commitsThe server has commits you do not havegit pull
Your branch and 'origin/main' have divergedBoth sides have new commitsPull (merge or rebase), then push

These messages compare with your last fetch. Run git fetch first for the real picture. To set or change tracking later: git branch -u origin/main (or --set-upstream-to=origin/main).

Useful push options

  • git push — push the current branch to its upstream.
  • git push origin feature/coupon — push a named branch (and add -u the first time).
  • git push --tags — push tags (releases), see Module 4.
  • git push origin --delete feature/coupon — delete a branch on the server.
  • git config --global push.autoSetupRemote true — a convenience setting: the first git push of a new branch automatically sets its upstream, so you can skip -u.

Mistake: git remote add origin when origin already exists

You get error: remote origin already exists. Either change the URL with git remote set-url origin <url> or pick another name. This often happens after git clone, which already created origin.

Errors and edge cases

  • fatal: The current branch feature has no upstream branch. — you never set tracking. Run the command Git prints: git push --set-upstream origin feature.
  • fatal: 'origin' does not appear to be a git repository — no remote called origin; check git remote -v.
  • error: src refspec main does not match any — your local branch is called master or you have no commits yet. Check with git branch.
  • Remote-tracking branches for branches deleted on the server stay in your clone until you run git fetch --prune (or git remote prune origin).
  • You can give push and fetch different URLs (git remote set-url --push); this is rare.

Interview: "What does git push -u origin main do? What is origin/main?"

  • It pushes local main to the remote origin and sets origin/main as its upstream, so later git push/git pull need no arguments.
  • origin/main is a remote-tracking branch: a read-only local bookmark of the server's main as of the last fetch.
  • git branch -vv shows each branch's upstream and ahead/behind counts.

git fetch vs git pull

Fetch downloads new commits from the remote and only updates origin/main — it is always safe; pull is fetch plus a merge (or rebase) into your current branch, which changes your files.

Both commands bring in other people's work, but they do different amounts of it.

Pointgit fetchgit pull
Downloads new commitsYesYes
Updates origin/mainYesYes

fetch: look before you merge

$ git fetch origin
remote: Enumerating objects: 7, done.
From github.com:asha-rao/billing-service
   7d3e4f2..a9b8c7d  main       -> origin/main
$ git status
Your branch is behind 'origin/main' by 2 commits, and can be fast-forwarded.
$ git log --oneline main..origin/main
a9b8c7d Add health endpoint
c1d2e3f Fix typo in README
$ git diff main origin/main --stat

The notation main..origin/main means "commits in origin/main that are not in main" — exactly what you would receive. Then integrate when ready with git merge origin/main (or git rebase origin/main). Fetch never alters your working folder, so it cannot lose or conflict with anything. Fetch from all remotes with git fetch --all; add --prune to remove tracking branches deleted on the server.

pull: fetch and integrate

$ git pull
Updating 7d3e4f2..a9b8c7d
Fast-forward
 README.md                 | 2 +-
 src/main/java/Health.java | 9 +++++++++
 2 files changed, 10 insertions(+), 1 deletion(-)

git pull = git fetch + git merge origin/main (into the current branch). Cases:

  • Fast-forward: you have no new local commits, so Git just moves your branch pointer forward. No merge commit.
  • True merge: both sides have new commits, so Git creates a merge commit with two parents. If both changed the same lines, you get a conflict to resolve (Module 3).

Pull with rebase

git pull --rebase = fetch, then replay your local commits on top of the fetched ones. The history stays a straight line, with no extra merge commit for every sync.

Rebase creates new commits (D', E') with new hashes, so it is safe only for commits you have not shared. Details in Module 4. Choose a default once:

$ git config --global pull.rebase false    # merge (plain default behaviour)
$ git config --global pull.rebase true     # rebase
$ git config --global pull.ff only         # refuse to create a merge commit; fail instead

If you set none of these and the histories have diverged, current versions of Git stop and tell you to choose how to reconcile (fatal: Need to specify how to reconcile divergent branches.). That message is your cue to set pull.rebase or to run git pull --rebase or git pull --no-rebase once. Many teams recommend pull.rebase true on feature branches, or pull.ff only as the safest habit (fetch, then merge deliberately). Follow what your team does.

Habits that avoid trouble

  • Before you start work each day: git switch main then git pull.
  • Commit or stash your changes before pulling. Pulling with a dirty working folder can fail or mix changes.
  • When unsure what a pull will do, run git fetch first and look with git log main..origin/main.
  • Pull before you push, every time.

Errors and edge cases

  • error: Your local changes to the following files would be overwritten by merge — commit or stash first.
  • fatal: refusing to merge unrelated histories — the two repositories started separately (a common result of adding a README on GitHub and also running git init locally). If you are sure, add --allow-unrelated-histories.
  • There is no tracking information for the current branch. — set it: git branch --set-upstream-to=origin/main.
  • A merge conflict during pull leaves the repository in a merging state; resolve it or abort with git merge --abort (or git rebase --abort).

Interview: "Difference between git fetch and git pull?"

  • Fetch only downloads and updates remote-tracking branches; it never changes your branch or files, so it is always safe.
  • Pull = fetch + merge into the current branch (or fetch + rebase with --rebase); it can cause conflicts.
  • Good answer adds: fetch then review, set pull.rebase, and fast-forward vs merge commit.

Push rejected: non-fast-forward errors

Git rejects a push when the remote branch has commits you do not have; the fix is to pull (merge or rebase) first and then push — never a blind force push.

You will see this error within your first week:

To github.com:asha-rao/billing-service.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:asha-rao/billing-service.git'
hint: Updates were rejected because the remote contains work that you do
hint: do not have locally. This is usually caused by another repository
hint: pushing to the same ref. You may want to first integrate the remote
hint: changes (e.g., 'git pull ...') before pushing again.

Variants of the same problem say (non-fast-forward) — "the tip of your current branch is behind its remote counterpart".

Why it happens

A push can only fast-forward the remote branch: the new tip must contain the old tip as an ancestor. If a teammate pushed first, the remote has commit X that your history lacks. Accepting your push would drop X from the branch. Git refuses to lose their work.

The right fix

  1. git pull --rebase (or git pull). Git brings in X and puts your Y on top of it (or merges).
  2. Resolve conflicts if there are any, test the build.
  3. git push — now it is a fast-forward and succeeds.
$ git pull --rebase
Successfully rebased and updated refs/heads/main.
$ git log --oneline -3
5e6f7a8 Add coupon validation          <- your commit, now on top
a9b8c7d Add health endpoint            <- teammate's commit
7d3e4f2 Describe the service in README
$ git push
   a9b8c7d..5e6f7a8  main -> main

Do not force push to "make the error go away"

Wrong: overwrites your teammate's commit

$ git push --force
# remote main now has only YOUR history.
# X is gone from GitHub; the teammate's next push breaks.

Right: integrate first

$ git pull --rebase
$ git push

A force push (git push --force or -f) makes the remote branch point exactly where yours does, discarding whatever was there. There are real reasons for it — you amended or rebased your own feature branch that nobody else uses — and then you use the safer form:

$ git push --force-with-lease

--force-with-lease forces only if the remote branch is still where you last saw it (your origin/feature). If someone pushed in the meantime, it refuses. Details and team rules are in Module 4.

Rule: no force pushes to shared branches

Never force push main or any branch others work on. Most teams protect main with branch protection rules on GitHub, which block force pushes and direct pushes entirely (Module 3).

Mistake: pulling after committing in panic with uncommitted work

If your working folder has uncommitted edits to a file that the pull also changes, Git refuses to continue. Commit your work (or git stash) before git pull.

What Git checks, exactly

When you run git push, Git asks the server what commit the remote main points to. It then checks whether that commit is an ancestor of the commit you are sending. If yes, the update only moves the branch pointer forward along a straight line: a fast-forward. If no, the two histories have diverged and the server refuses, because moving the pointer would make the teammate's commit unreachable. The message says fetch first when your Git does not even have that commit yet, and non-fast-forward when it already knows the commit (for example after a git fetch) but it is not in your history.

Diagnose before you fix

Do not guess. Fetch the remote state (this changes nothing in your files) and look at both sides.

$ git fetch
$ git status
On branch main
Your branch and 'origin/main' have diverged,
and have 1 and 1 different commits each, respectively.
  (use "git pull" if you want to integrate the remote branch with yours)
$ git log --oneline --graph --all
* 5e6f7a8 (HEAD -> main) Add coupon validation
| * a9b8c7d (origin/main) Add health endpoint
|/
* 7d3e4f2 Describe the service in README
$ git log --oneline HEAD..origin/main     # commits you are missing
a9b8c7d Add health endpoint

The graph shows the fork at 7d3e4f2. Your commit and the teammate's commit both sit on top of it. To push, one line of history must contain both.

Three ways to integrate

OptionWhat happensResult
git pull --rebaseYour commits are replayed on top of the remote tipStraight history; your commit gets a new hash
git pull (merge)Git creates a merge commit that joins both linesBoth lines stay visible; extra merge commit
git push --forceRemote is overwritten with your historyTeammate's commit is lost from the remote

With --rebase Git temporarily sets your commit aside, moves to the new remote tip, and applies your commit again. The content is the same but it is a new commit (Y becomes Y'), because its parent changed. This is safe here because you had not pushed Y yet. If your change touches the same lines as the teammate's, Git stops with a conflict. You edit the file, run git add, and then git rebase --continue. To give up and return to the state before the pull, run git rebase --abort.

You can make rebase the default with git config --global pull.rebase true, or make pulls refuse anything but a fast-forward with git pull --ff-only. Many teams choose the first for feature branches; follow your team's rule. Merge versus rebase is explained in depth in Module 4.

A legitimate force push: your own rewritten branch

Suppose you pushed feature/coupons, then ran git commit --amend or git rebase main on it. The local commits now have new hashes, so the push is rejected as non-fast-forward. Nobody else uses the branch, so overwriting the remote is correct. Use the lease form.

$ git push --force-with-lease
 + 4c1d2e3...9b8a7f6 feature/coupons -> feature/coupons (forced update)

# if a teammate had pushed to the branch meanwhile:
 ! [rejected]        feature/coupons -> feature/coupons (stale info)

The lease compares the remote tip with your remembered origin/feature/coupons. A mismatch means someone added work you have not seen, and the push is refused. One caution: if a tool such as your IDE runs git fetch in the background, your remembered value updates without you reading the new commits, and the lease then passes. Fetch and look at the log yourself before forcing.

If a wrong force push already happened

The overwritten commits are not deleted at once. Your teammate still has them in their local repository and in git reflog. They can find the lost hash there and push it back with git push origin <hash>:main after the branch protection is lifted, or recreate a branch from it. Tell the team immediately instead of hoping nobody notices.

Wrong: ignore the hint and retry

$ git push
 ! [rejected] main -> main (fetch first)
$ git push origin main
 ! [rejected] main -> main (fetch first)
# same error: spelling it out changes nothing

Right: integrate, then push

$ git pull --rebase
$ ./mvnw test
$ git push

Rule: never rewrite history that others already pulled

Rebase, amend and force push are for commits only you have. Once a teammate has based work on a commit, changing it forces them to repair their branch.

Convention: pull often, push small

Run git pull --rebase before you start work and before you push. Short-lived branches and small pull requests make rejections rare and conflicts small.

Edge cases

  • Pulling with a rebase while you have uncommitted edits can fail with "cannot pull with rebase: You have unstaged changes". Commit or git stash first (and git stash pop afterwards).
  • A rejection on a branch with no remote counterpart yet is not this error; a brand new branch is pushed with git push -u origin <branch>.
  • Rejected pushes can repeat: someone may push again while you resolve a conflict. Pull again, then push quickly.

Interview: "Your push was rejected. What do you do?"

  • Explain the reason: the remote has commits I do not have, and a non-fast-forward push would discard them.
  • Fix: git pull --rebase (or merge), resolve conflicts, run tests, push.
  • Mention that force push is only for your own branches after a rewrite and then --force-with-lease, never on shared branches.

20-second answer: "The remote has a commit I do not have, so my push is not a fast-forward and Git refuses to drop their work. I run git fetch to look, then git pull --rebase, fix conflicts, run the tests and push. I only force push my own rewritten branch, and then with --force-with-lease, never to shared branches like main."

Publish an existing local project to GitHub

Create an empty repository on GitHub, then in your project run git remote add origin and git push -u origin main.

This is the most common first remote task: you have a project on your laptop and want it on GitHub. Two situations exist, and the difference matters.

Case 1: your local project already has commits

  1. Create the repository on GitHub. Click New repository, enter a name such as java-practice, choose Public or Private, and do not tick Add a README, .gitignore or license. A completely empty repository avoids the "unrelated histories" problem.
  2. Prepare locally. Make sure the branch is called main and your .gitignore is committed.
  3. Add the remote and push. GitHub shows these commands on the empty repository page.
$ cd java-practice
$ git branch -M main
$ git remote add origin git@github.com:asha-rao/java-practice.git
$ git push -u origin main
Enumerating objects: 9, done.
Writing objects: 100% (9/9), 1.64 KiB | 1.64 MiB/s, done.
To github.com:asha-rao/java-practice.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

git branch -M main renames the current branch to main (forcing, even if the name exists). Use the HTTPS URL if you chose HTTPS login. Refresh the GitHub page and your files and full history are there.

Case 2: a project with no Git yet

$ cd billing-service
$ git init -b main
$ printf "target/\n.idea/\n.env\n" > .gitignore
$ git add .
$ git status -s                          # check: no target/, no .env
$ git commit -m "Initial commit: Spring Boot billing service"
$ git remote add origin git@github.com:asha-rao/billing-service.git
$ git push -u origin main

Create .gitignore before the first git add .. Once target/ or a secret is in the first commit, removing it needs extra steps (.gitignore).

Case 3: you created the repository with a README first

If you let GitHub create a README, the remote already has a commit your local repository lacks. The first push is then rejected, and a plain pull fails with refusing to merge unrelated histories. Two ways out:

$ git pull origin main --allow-unrelated-histories
$ git push -u origin main

or start cleaner: clone the GitHub repository first, copy your files into the clone, then add and commit. Both work; the empty-repository approach in Case 1 is simpler.

Create the repository from the terminal (optional)

With the GitHub CLI installed and logged in (gh auth login), one command does the web steps:

$ gh repo create java-practice --private --source=. --remote=origin --push

Check that it worked

$ git remote -v
$ git status
On branch main
Your branch is up to date with 'origin/main'.
nothing to commit, working tree clean
$ git branch -vv

Mistake: publishing secrets or large files

Before the first push read git status and git ls-files. A public repository is copied and scanned by bots within minutes. Check for .env, passwords in application.yml, target/, and big data files.

Errors and edge cases

  • error: src refspec main does not match any — no commit exists yet, or your branch is called master; use git branch -M main.
  • fatal: remote origin already exists — use git remote set-url origin <url>.
  • remote: Repository not found — typo in owner/name, or the repository is private and you are logged in to another account.
  • A repository named differently on GitHub than your folder is fine; the folder name never matters to Git.

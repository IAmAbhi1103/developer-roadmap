Caching: layers, patterns, eviction and invalidation

A cache keeps copies of expensive-to-get data in a faster place; you choose where to cache (browser, CDN, proxy, app, Redis), a read/write pattern (cache-aside, read-through, write-through, write-behind, write-around), an eviction policy (LRU, LFU, TTL) and an invalidation strategy, accepting some staleness in return for speed and lower load.

What problem it solves

Reading from memory is about 1,000 times faster than from SSD and far faster than a cross-network database query (latency numbers). Most workloads read a small hot set of data again and again (the same products, the same profiles). A cache stores that hot data in fast storage so most reads skip the slow source. Benefits: lower latency, higher throughput, fewer database queries (and a smaller database bill). The price: stale data, extra moving parts, and the famous hard problem of knowing when to invalidate.

For Spring's @Cacheable and Redis integration see Spring Boot · Module 6, and for Redis itself SQL · Module 6. This article is the system-design view.

A common combo is a tiny local cache (Caffeine) in front of Redis: a "two-level" cache. It is fastest but doubles the staleness problem, so keep local TTLs very short (seconds).

The caching patterns

PatternRead pathWrite pathConsistencyMain risk
Cache-asideApp checks cache, on a miss loads from DB and fills the cacheApp writes to DB, then deletes (or updates) the cache keyEventual; stale until TTL or deleteRaces between a delete and a concurrent read-fill
Read-throughCache itself loads from DB on a missSame as cache-asideEventualNeeds a cache layer with loader support
Write-throughReads hit a warm cacheWrite goes to cache and DB together, returns after bothStrong between cache and DBSlower writes; caches data never read
Write-behind (write-back)Reads hit the cacheWrite to cache, DB updated later in batchesDB lags behindData loss if the cache dies before flushing
Write-aroundMisses go to DB then cacheWrites go to DB only, bypass cacheCache stale until TTLFirst read after write is slow
  • Cache-aside is the default for web apps: simple, resilient (if the cache dies, the app still works from the database), and caches only what is requested. Spring's @Cacheable implements it.
  • Read-through is the same idea with the loading logic inside the cache library or service (Caffeine LoadingCache, many managed caches).
  • Write-through keeps the cache always fresh for written data; good for read-heavy data that is updated rarely and must not be stale (profile settings). Write latency is the cost.
  • Write-behind gives very fast writes and batching (counters, analytics), but you can lose acknowledged writes. Use it only where loss is tolerable or the cache is durable.
  • Write-around avoids filling the cache with data that is written once and rarely read (logs, uploads).
import java.time.Duration;
import java.util.Optional;
import org.springframework.data.redis.core.StringRedisTemplate;
import com.fasterxml.jackson.databind.ObjectMapper;

public class ProductService {
    private final StringRedisTemplate redis;
    private final ProductRepository repo;
    private final ObjectMapper json = new ObjectMapper();

    public ProductService(StringRedisTemplate redis, ProductRepository repo) {
        this.redis = redis;
        this.repo = repo;
    }

    public Optional<Product> find(long id) throws Exception {
        String key = "product:" + id;
        String cached = redis.opsForValue().get(key);
        if (cached != null) {                                   // hit
            return Optional.of(json.readValue(cached, Product.class));
        }
        Optional<Product> fromDb = repo.findById(id);           // miss
        if (fromDb.isPresent()) {
            redis.opsForValue().set(key, json.writeValueAsString(fromDb.get()),
                                    Duration.ofMinutes(5));
        }
        return fromDb;
    }

    public void update(Product p) {
        repo.save(p);                                           // 1. write the source of truth
        redis.delete("product:" + p.id());                      // 2. then invalidate the cache
    }
}

Note the order in update: write the database first, then delete the cache entry. Deleting first lets a concurrent reader refill the cache with the old value before your write lands. Even in the right order a tiny race window remains; a TTL bounds the damage.

Eviction policies

Memory is limited, so when the cache is full it must evict something.

PolicyEvictsGood forWeakness
LRU (least recently used)The entry untouched the longestGeneral use; recent items are likely reusedOne big scan can flush the hot set
LFU (least frequently used)The entry used the fewest timesStable popularity (top products)Old popular items linger; needs counters
FIFOThe oldest insertedSimpleIgnores usage entirely
TTL (time to live)Entries after a fixed lifetimeBounding stalenessNot an eviction by memory pressure by itself
RandomA random entryCheap, surprisingly decentUnpredictable

Redis configures this with maxmemory and maxmemory-policy (for example allkeys-lru, allkeys-lfu, volatile-ttl; Redis uses sampled approximations rather than an exact LRU). Caffeine uses a modern frequency-aware policy (W-TinyLFU).

LRU is a classic interview coding task. A hash map plus a doubly linked list gives O(1) get and put. In Java, LinkedHashMap in access order does it in a few lines:

import java.util.LinkedHashMap;
import java.util.Map;

public class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    public LruCache(int capacity) {
        super(16, 0.75f, true);              // true = access order (LRU)
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;            // evict the least recently used
    }

    public static void main(String[] args) {
        LruCache<String, Integer> c = new LruCache<>(2);
        c.put("a", 1); c.put("b", 2);
        c.get("a");                          // a is now most recent
        c.put("c", 3);                       // evicts b
        System.out.println(c.keySet());
    }
}
[a, c]

This class is not thread-safe; production code uses Caffeine or Redis.

Invalidation strategies

  • TTL only: accept staleness up to N seconds. Simple and robust; always set one, even when you also invalidate explicitly, as a safety net.
  • Explicit invalidation on write: delete the key (or tag) after updating the database. Fresh, but every writer must know every cached view of the data.
  • Event-driven invalidation: publish a "product changed" event (Kafka, Redis pub/sub, or CDC from the database log); consumers evict. Decouples writers from caches.
  • Versioned keys: include a version in the key (product:42:v7); a new version makes the old entry unreachable, and eviction cleans it up.
  • Write-through or refresh-ahead: update or reload the entry instead of deleting it.

"There are only two hard things in computer science"

Cache invalidation is on the famous list because the cache and the source can disagree in many ways: races, failed deletes, multiple writers, derived data. The robust answer is: short TTL for safety, delete on write for freshness, and a design where occasional staleness is acceptable.

What to cache, and what not to

Cache this

  • Read-heavy, rarely changing data: catalogues, configuration, reference data.
  • Expensive results: aggregates, rendered fragments, results of slow joins.
  • Hot objects: popular profiles, trending lists, session data.
  • Data where slight staleness is fine.

Avoid or be careful

  • Frequently changing data with strict freshness needs (account balance, stock count at checkout).
  • Write-heavy data that is rarely re-read.
  • Per-user private data in a shared cache without the user id in the key.
  • Huge objects, or anything that is cheaper to compute than to fetch.

Interview angle

  • "I use cache-aside with Redis, a TTL of a few minutes, and delete the key after writing the database."
  • Be ready to compare write-through (fresh, slower writes) with write-behind (fast, can lose data).
  • For eviction, say LRU by default; LFU when popularity is stable; mention O(1) with a hash map and a doubly linked list.

Classic cache problems: stampede, penetration, avalanche, hot keys

Caches fail in a few well-known ways: stale data, a stampede when a hot key expires, penetration by requests for keys that do not exist, an avalanche when many keys expire together, and hot keys that overload one node; each has a standard fix, and the hit ratio tells you if the cache works.

1. Stale data

The cache holds an old value after the source changed. Causes: a TTL that is too long, a missed invalidation, a race between a read-fill and a write. Fixes: delete on write after the database commit, a short TTL as a safety net, versioned keys, and event-based invalidation. Decide per data type how much staleness the business accepts: a product description may be 10 minutes old, a stock count at checkout may not.

2. Cache stampede (thundering herd)

A very popular key expires. In the same instant, thousands of requests miss, and all of them run the same expensive database query to rebuild it. The database spikes or collapses.

Fixes:

  • Locking (mutex per key): only the first requester rebuilds; the others wait or get the old value. Distributed version: SET lock:key token NX PX 5000 in Redis; always set an expiry on the lock and release it only if you still own it.
  • Request coalescing (single flight): inside one instance, concurrent requests for the same key share one in-flight load. In Java use a ConcurrentHashMap of CompletableFuture, or Caffeine's LoadingCache, which already does this.
  • Early (probabilistic) refresh: refresh a key shortly before it expires, in the background, or let the cache serve slightly stale data while one request refreshes (stale-while-revalidate).
  • Never-expire hot keys and refresh them with a scheduled job.
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ConcurrentHashMap;
import java.util.function.Supplier;

public class SingleFlight<V> {
    private final ConcurrentHashMap<String, CompletableFuture<V>> inFlight =
        new ConcurrentHashMap<>();

    public V load(String key, Supplier<V> loader) {
        CompletableFuture<V> mine = new CompletableFuture<>();
        CompletableFuture<V> existing = inFlight.putIfAbsent(key, mine);
        if (existing != null) {
            return existing.join();               // someone else is loading: wait for them
        }
        try {
            V value = loader.get();               // only one thread runs the expensive load
            mine.complete(value);
            return value;
        } catch (RuntimeException e) {
            mine.completeExceptionally(e);
            throw e;
        } finally {
            inFlight.remove(key);
        }
    }
}

3. Cache penetration

Requests ask for keys that do not exist (a random product id, or an attacker's flood). The cache never has them, so every request goes through to the database, and the cache gives no protection.

  • Cache the empty result (a "null" marker) with a short TTL, such as 30–60 seconds.
  • Bloom filter in front: a compact probabilistic set of all valid ids. If the filter says "definitely not present", reject at once. It can have false positives (rare, a harmless extra DB check) but never false negatives. Libraries: Guava BloomFilter; Redis has Bloom filter support through its modules. You must add new ids to the filter when records are created.
  • Validate input (id ranges, formats) and apply rate limiting per client.

4. Cache avalanche

Many keys expire at the same moment (you loaded them together with the same TTL), or the whole cache restarts empty. Suddenly the database gets the load of everything. Fixes:

  • TTL jitter: add a random amount, for example 5 minutes plus a random 0–60 seconds.
  • Warm the cache before taking traffic after a restart.
  • High availability for the cache (Redis replicas or cluster) so one failure does not empty it.
  • Protect the database: rate limiting, circuit breaker, request queues, and degraded responses if the cache is down.
import java.time.Duration;
import java.util.concurrent.ThreadLocalRandom;

static Duration ttlWithJitter(Duration base, Duration maxJitter) {
    long extra = ThreadLocalRandom.current().nextLong(maxJitter.toSeconds() + 1);
    return base.plusSeconds(extra);       // 5 min + 0..60 s
}

5. Hot keys

One key gets a huge share of traffic (a celebrity's profile, a flash-sale product). In a sharded cache that key lives on one node, which becomes the bottleneck even though the cluster is idle. Fixes: a short local (in-process) cache in front of Redis for those keys; replicate the hot key under several names (product:42#1 … #8) and read a random one; detect hot keys by monitoring and promote them automatically.

Measuring: the hit ratio

Hit ratio = hits ÷ (hits + misses). A healthy read cache is often above 90%, but the right target depends on the workload. A cache with a 60% hit ratio and an expensive miss path may not be worth its complexity. In Redis, INFO stats reports keyspace_hits and keyspace_misses. Also watch evictions (a high count means the cache is too small), memory use, latency, and the miss-path latency. Spring Boot Actuator and Micrometer expose cache metrics (Spring Boot · Module 6).

The value of a hit ratio is easy to compute: if a hit costs 1 ms and a miss costs 51 ms (1 ms cache check plus 50 ms database), a 90% ratio gives an average of 0.9 × 1 + 0.1 × 51 = 6 ms; at 99% it is 1.5 ms. Small ratio gains matter a lot when misses are expensive.

Common mistakes

  • Caching without a TTL: stale entries live forever after one missed invalidation.
  • One shared TTL for everything loaded together (avalanche).
  • Not caching "not found", so misses are never absorbed.
  • Storing mutable objects shared across threads in a local cache, then changing them.
  • Treating the cache as the source of truth. It can disappear at any time; the app must work without it, only slower.

Interview angle

  • Name all three: stampede (hot key expires; fix with locking or early refresh), penetration (non-existent keys; fix with null caching and Bloom filters), avalanche (mass expiry; fix with TTL jitter).
  • Explain the cache-aside write order: database first, then delete the key.
  • Close with the metric: "I would track the hit ratio, evictions and miss latency."

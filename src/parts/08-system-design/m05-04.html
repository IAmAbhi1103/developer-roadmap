The database scaling ladder

Scale a database in order of cost and risk: tune queries and indexes, scale up the machine, add caching, add read replicas, partition big tables, and only then shard; denormalization and federation are side tools along the way.

Why a ladder

The database is usually the first real bottleneck, because it holds shared state and cannot simply be cloned like a stateless app server. Each step up the ladder buys more capacity but costs more complexity. A strong answer climbs one rung at a time and says what number forces the next rung. Jumping straight to sharding for 500 requests per second is a classic over-engineering mistake.

Rung by rung

  1. Query and index tuning. Find slow queries (EXPLAIN, slow-query log), add the right indexes, remove N+1 queries, fix missing pagination, use connection pooling (HikariCP) and proper pool sizes. One missing index can cost 100x. This is free capacity and always comes first (SQL · Module 5).
  2. Scale up (vertical). More CPU, RAM and faster NVMe disks. RAM matters most: if the working set (the hot data and indexes) fits in memory, reads are fast. Needs no code change, but has a ceiling and a single point of failure.
  3. Caching. Move repeated reads to Redis or a local cache (Caching). Often removes 80–95% of read load for read-heavy products. Does nothing for writes.
  4. Read replicas. Copy the data to followers and send reads to them (Replication). Scales reads almost linearly; writes still go to one primary; adds replication lag.
  5. Partitioning. Split one huge table into smaller pieces inside the same database (by date or id range). Queries touching one partition scan far less data, old partitions can be dropped or archived cheaply. Still one server.
  6. Sharding. Split data across several independent database servers so writes and storage scale out (Sharding). The biggest step: queries, transactions and operations all become harder.

The word "partition" is also used loosely for "a shard" (Kafka partitions, DynamoDB partitions), so ask which one is meant.

Side tools

  • Denormalization: store redundant data to avoid joins (copy the user's name into each comment row, keep a precomputed like_count). Reads get faster; writes get more complex and the copies can drift apart, so update them from one place or an event.
  • Federation (functional partitioning): split the database by feature, not by row: a users database, an orders database, a products database. Each is smaller and can be scaled and tuned separately. The price is that joins across them move into application code, and it fits naturally with microservices owning their data.
  • CQRS-style read models: write to the main store, project data into a separate store optimised for reading (a search index, a denormalised table).
  • Archival: move old rows to cheap storage; smaller hot tables are faster.
  • Choose a different database when the access pattern fits one better (SQL vs NoSQL).

Worked reasoning

Suppose the estimate says 7,000 peak requests per second, 90% reads (the estimation example). Reads would be 6,300 per second. With a 90% cache hit ratio only about 630 reads per second reach the database. A single primary with a couple of replicas handles that and the 700 writes per second easily. So the design needs cache plus replicas, not sharding, today. Sharding enters only when the dataset grows beyond one server's disk (the estimate showed about 36 TB of metadata in five years) or writes exceed what one primary can do (many thousands per second).

Common mistake: sharding to fix a slow query

If one query is slow, spreading the table across servers will not fix a missing index; it will only make the problem 10 times larger and harder to debug. Measure first, then pick the rung that addresses the measured limit: CPU, memory, disk IO, connections, or storage size.

Interview angle

  • "I would start with indexes and query tuning, then a cache and read replicas. Sharding is the last resort because it breaks joins and transactions."
  • Say which limit you are hitting: read throughput (cache and replicas), write throughput or storage size (sharding).

Replication: leader–follower, multi-leader, leaderless

Replication keeps copies of the data on several nodes for availability and read scale; the usual setup is one leader with followers, synchronous replication is safer but slower than asynchronous, and asynchronous replication causes lag, which you handle with read-your-writes tricks.

Why replicate

Three reasons: availability (if the primary dies, a copy can take over), read scalability (many followers serve reads), and latency (a copy near the users). Replication does not scale writes (every copy must apply every write) and it does not replace backups (a bad DELETE replicates too). For SQL basics see SQL · Module 6.

Leader–follower (primary–replica)

One node, the leader, accepts writes and records them in a log (the WAL in PostgreSQL, the binlog in MySQL). Followers stream and replay the log. Reads can go to any follower. It is simple, has no write conflicts (one writer), and is the default in PostgreSQL, MySQL and most managed databases (RDS, Cloud SQL). If the leader fails, a follower is promoted (failover).

Fully synchronous replication to all followers is rarely used because one slow node blocks writes. Most systems use async, or semi-sync with one synchronous follower so a committed write exists on at least two machines. This is the PACELC latency vs consistency choice in action (CAP and PACELC).

Replication lag and its anomalies

With async replication a follower may be milliseconds to seconds (sometimes minutes under load) behind. Readers see odd things:

  • Read-your-writes violation: you post a comment, the page reloads from a follower and your comment is missing.
  • Non-monotonic reads: one read hits a fresh follower, the next hits a stale one and data seems to go back in time.
  • Causality violation: a reply is visible but the question is not yet.

Mitigations: read from the leader for the user's own data or for a few seconds after a write; route critical reads (balances, checkout) to the leader; track the log position of the user's last write and read only from a follower that has reached it; pin a user to one follower (monotonic reads); monitor lag and take a lagging follower out of rotation. In Spring, a routing DataSource chooses leader or follower by whether a transaction is read-only (@Transactional(readOnly = true)).

import org.springframework.jdbc.datasource.lookup.AbstractRoutingDataSource;
import org.springframework.transaction.support.TransactionSynchronizationManager;

public class ReadWriteRoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly()
            ? "replica" : "primary";      // keys registered as target data sources
    }
}

Wrap the target sources in a LazyConnectionDataSourceProxy so the routing decision is made after the transaction's read-only flag is set; this is a common gotcha.

Failover details

Promoting a follower means: detect the failure (heartbeats and timeouts), choose the most up-to-date follower, reconfigure the others and the clients, and fence the old leader. Risks: with async replication the promoted follower may lack the last few writes (lost or conflicting writes), the old leader may return and believe it is still leader (split-brain), and a too-short timeout causes needless failovers during a load spike. Tools: Patroni (PostgreSQL), MySQL group replication or orchestrators, managed Multi-AZ setups.

Multi-leader replication

Several nodes accept writes, usually one leader per data centre, and replicate to each other. Benefits: low write latency in each region, and each region keeps working if the link between them fails. Cost: write conflicts (two users edit the same row in different regions). You need conflict resolution: last-write-wins, per-field merge, application-level merge, or CRDTs. It also has tricky corner cases with auto-incrementing keys, triggers and constraints. Use it only for real multi-region writes, or offline-capable clients (a calendar app syncing a phone), and prefer to avoid it otherwise.

Leaderless replication

No leader: the client (or a coordinator node) sends each write to several replicas and reads from several, using quorums (N, R, W). Used by Cassandra, Riak and DynamoDB-style stores. Strengths: no failover event, writes continue as long as a quorum is reachable, good for multi-region and high availability. Costs: weaker consistency, conflict handling (vector clocks or last-write-wins), read repair and anti-entropy to heal replicas, and no multi-row transactions in general.

Common mistakes

  • Sending a "read after write" to a follower and showing the user stale data.
  • Treating replicas as backups; deletions and corruption replicate too. Keep point-in-time backups.
  • Ignoring lag until a follower is minutes behind; alert on it.
  • Promoting an out-of-date follower without checking, and losing committed writes.

Interview angle

  • "One leader takes writes, followers serve reads asynchronously. Replication lag means I read my own writes from the leader."
  • Explain sync vs async as a durability vs latency trade-off, and semi-sync as the compromise.
  • Say that replication scales reads and availability, not writes; for writes you shard.

Sharding: strategies, shard keys, hot spots and resharding

Sharding splits one logical database into independent shards on different servers so writes and storage scale out; the shard key decides how well it works, and the costs are cross-shard queries, cross-shard transactions, hot spots and painful resharding.

The idea

When one primary cannot hold the data or handle the writes, you split the rows by a rule. Each shard is a complete database (usually with its own replicas) holding a subset of the rows. A router (in the application, a library, or a proxy such as Vitess or a MongoDB mongos) maps each request to the right shard.

Sharding strategies

StrategyRuleStrengthsWeaknesses

Choosing the shard key

This is the most important decision, and it is hard to change later. A good shard key:

  • Has high cardinality (many distinct values): user_id is good, country or status is bad.
  • Spreads load evenly: no single value attracts most of the traffic.
  • Matches the main access pattern, so common queries touch one shard: shard orders by customer_id if you mostly fetch "my orders".
  • Is stable: a key that changes means moving the row between shards.
  • Avoids monotonic values in range sharding (timestamps, auto-increment ids send all new writes to the newest shard).

Hot spots

A hot shard gets disproportionate load: a celebrity account, one giant tenant, today's date when sharding by date, or a flash-sale product. Fixes: hash-based keys; add a random suffix or salt to spread one hot key (and merge on read); give the heavy tenant a dedicated shard (directory-based); cache the hot data; split the hot shard further.

Resharding

Data grows, so shards fill up and you must add more. With hash mod N, going from 3 shards to 4 moves about 75% of keys, a huge migration. Better approaches:

  • Many logical shards on few servers: create, say, 256 logical shards up front and map them to 4 servers. To grow, move whole logical shards to new servers; the key-to-shard mapping never changes. This is the most common pragmatic design.
  • Consistent hashing moves only about 1/N of the keys when a node joins (next article).
  • Directory-based mapping lets you move one range or tenant at a time.
  • Do the move online: copy data in the background, keep it in sync (dual writes or change-data capture), verify, switch traffic, delete the old copy.

What sharding breaks

  • Cross-shard queries: "all orders over ₹10,000 today" must go to every shard and be merged (scatter–gather): slow and fragile. Mitigate with a secondary index or search store, or by designing queries around the shard key.
  • Joins: across shards they happen in application code, or are avoided by denormalizing, or by co-locating related data (shard orders and order items by the same customer id).
  • Transactions: an ACID transaction across shards needs two-phase commit (slow and blocking) or a saga with compensating actions (Module 6). Prefer designs where one business operation touches one shard.
  • Unique ids: auto-increment ids collide across shards. Use UUIDs, a Snowflake-style id (timestamp + machine id + sequence), or an id service.
  • Operations: schema migrations, backups, monitoring and rebalancing now multiply by the number of shards.

Tools that provide sharding: Vitess (MySQL), Citus (PostgreSQL), MongoDB's built-in sharding, Cassandra and DynamoDB (shard by design with a partition key), CockroachDB and Spanner (distributed SQL that shards automatically and keeps transactions).

public class ShardRouter {
    private final int logicalShards = 256;              // fixed, never changes
    private final java.util.List<String> shardUrls;     // logical shard -> server

    public ShardRouter(java.util.List<String> shardUrls) {
        this.shardUrls = shardUrls;                     // size = 256, many point to one server
    }

    public String urlFor(long userId) {
        int logical = (int) Math.floorMod(Long.hashCode(userId), logicalShards);
        return shardUrls.get(logical);                  // moving a logical shard = edit the list
    }
}

Common mistakes

  • Sharding by a low-cardinality key such as country, status or boolean.
  • Starting with hash mod N and no plan for adding nodes.
  • Designing queries that always need all shards.
  • Sharding early, before replicas, caching and indexing are used up.

Interview angle

  • "I would shard by user id with a hash, using many logical shards so I can rebalance by moving whole shards. Single-user queries touch one shard."
  • Always name the cost: cross-shard joins, transactions and resharding. Offer co-location or sagas.
  • Say what you would watch: shard size, per-shard QPS, and skew.

Consistent hashing and virtual nodes

Consistent hashing places nodes and keys on a ring so that adding or removing a node moves only about 1/N of the keys instead of nearly all of them; virtual nodes give each server many points on the ring for an even spread.

The problem with hash mod N

To pick a cache server for a key, the obvious rule is server = hash(key) mod N. It works until N changes. With 3 servers going to 4, a key stays only if hash mod 3 == hash mod 4, which is true for about 25% of keys. The other 75% now map to a different server: cache misses everywhere (a stampede on the database), or in a sharded database, a huge data migration. Servers join and leave constantly (autoscaling, failures), so we need a rule that moves few keys.

The ring

Map the hash space (for example 0 to 232 − 1) onto a circle. Hash each server to a position on the ring. To find the server for a key, hash the key to a position and walk clockwise to the first server you meet.

  • Remove a server: only its keys move, all to the next server clockwise. Everyone else is untouched.
  • Add a server: it takes over only the keys between itself and the previous server.
  • On average only K/N keys move (K keys, N servers), instead of almost all.

The unevenness problem and virtual nodes

With only a few servers placed by hash, the arcs between them differ in size, so one server may own 50% of the ring while another owns 10%. When a server fails, all its load falls on a single neighbour, which may then fail too.

The fix is virtual nodes (vnodes): each physical server gets many positions on the ring (100–200 is typical), by hashing "serverA#0", "serverA#1", and so on. The arcs average out, so each server owns roughly 1/N of the ring. When a server leaves, its many small arcs go to many different neighbours, spreading the extra load evenly. A bigger machine can simply be given more vnodes (weighting). The cost is a larger ring to store and search, and more metadata to keep in sync.

A Java sketch with TreeMap

A TreeMap keeps keys sorted, and ceilingEntry finds the first position at or after a hash in O(log n). If there is none, wrap around to the first entry.

import java.nio.ByteBuffer;
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.util.Map;
import java.util.TreeMap;

public class ConsistentHashRing {
    private final TreeMap<Long, String> ring = new TreeMap<>();
    private final int vnodes;

    public ConsistentHashRing(int vnodes) {
        this.vnodes = vnodes;
    }

    public void addNode(String node) {
        for (int i = 0; i < vnodes; i++) {
            ring.put(hash(node + "#" + i), node);        // many points per server
        }
    }

    public void removeNode(String node) {
        for (int i = 0; i < vnodes; i++) {
            ring.remove(hash(node + "#" + i));
        }
    }

    public String nodeFor(String key) {
        if (ring.isEmpty()) {
            throw new IllegalStateException("no nodes");
        }
        Map.Entry<Long, String> e = ring.ceilingEntry(hash(key));   // next clockwise
        if (e == null) {
            e = ring.firstEntry();                                   // wrap around
        }
        return e.getValue();
    }

    private static long hash(String s) {
        try {
            byte[] d = MessageDigest.getInstance("MD5")
                .digest(s.getBytes(StandardCharsets.UTF_8));
            return ByteBuffer.wrap(d).getLong();           // first 8 bytes as a long
        } catch (java.security.NoSuchAlgorithmException ex) {
            throw new IllegalStateException(ex);
        }
    }
}

Usage: create new ConsistentHashRing(150), call addNode("cache-1") for each server, and route with nodeFor("user:42"). If you add cache-4 later and compare the routing for a large set of keys, only about a quarter of them change, whereas with mod N about three quarters would. (MD5 is used here only as a well-spread hash, not for security; the sketch is not thread-safe and ignores replication.)

For replication on the ring, store each key on the next R distinct physical servers clockwise (the preference list in Dynamo-style systems).

Where it is used

  • Distributed caches (client libraries for Memcached use it; Redis Cluster uses a related fixed scheme of 16,384 hash slots, which also moves only slots when nodes change).
  • Databases: Cassandra and DynamoDB-style stores partition data on a ring with vnodes.
  • Load balancing with affinity: send the same key (user, URL) to the same backend so local caches stay warm.
  • CDNs and object stores to decide which node stores which object.

Edge cases

  • A single very hot key still lands on one server; consistent hashing balances keys, not traffic.
  • Hash collisions between nodes are rare but must be handled (add a salt).
  • After adding a node, the new node's cache is cold; the keys it takes over miss once.

Interview angle

  • "With mod N, adding a server remaps most keys. With consistent hashing only about 1/N move."
  • "Virtual nodes smooth the distribution and spread a failed node's load across many peers."
  • Be ready to code the TreeMap version: ceilingEntry with wrap-around.

UML class diagrams: boxes, relationships and how they map to Java

A UML class diagram shows classes (name, attributes, methods) and the relationships between them (association, aggregation, composition, inheritance, realization, dependency) so that you can discuss a design before and after you code it.

UML (Unified Modeling Language) is a standard way of drawing software designs. You do not need all of it. In interviews and design discussions you mostly need two diagrams: the class diagram (the static structure: what exists and how it is connected) and the sequence diagram (the dynamic behaviour: who calls whom, in what order; see next article). In low-level design interviews (Module 3) a class diagram is usually the first thing you draw. Here we write diagrams in Mermaid text, which becomes a picture.

The class box

A class is a box with three compartments: the name, the attributes (fields) and the operations (methods). A visibility symbol precedes each member.

SymbolMeaningJava
+publicpublic
-privateprivate
#protectedprotected
~package-privateno modifier
 
public class BankAccount {
    private String accountNumber;
    private long balanceInPaise;
    protected AccountStatus status;

    public void deposit(long amount) { /* ... */ }
    public void withdraw(long amount) { /* ... */ }
    public long getBalance() { return balanceInPaise; }
    List<String> auditTrail() { /* ... */ return List.of(); }
}

In Mermaid, static members are marked with a $ suffix and abstract with *, but you rarely need them. Special kinds of types are shown with an annotation line such as <<interface>>, <<abstract>> or <<enumeration>>.

Each relationship as Java code

The diagram arrow tells you what to look for in the code:

// Inheritance:   Animal <|-- Dog
abstract class Animal { abstract void makeSound(); }
class Dog extends Animal { void makeSound() { System.out.println("Woof"); } }

// Realization:   Pet <|.. Dog   (a class can do both)
interface Pet { void play(); }
class Puppy extends Animal implements Pet {
    void makeSound() { }
    public void play() { }
}

// Association:   Customer --> Order     (a field holds a reference)
class Customer {
    private final List<Order> orders = new ArrayList<>();     // 1 to many
}

// Aggregation:   Department o-- Employee   (parts are passed in; they can outlive it)
class Department {
    private final List<Employee> staff = new ArrayList<>();
    void add(Employee e) { staff.add(e); }
}

// Composition:   House *-- Room   (the whole creates and owns its parts)
class House {
    private final List<Room> rooms = new ArrayList<>();
    House() { rooms.add(new Room("Hall")); }
}

// Dependency:    OrderService ..> Mailer   (no field; used inside a method only)
class OrderService {
    void confirm(Order order, Mailer mailer) {       // Mailer arrives as a parameter
        mailer.send(order.customerEmail(), "Confirmed");
    }
}

Aggregation versus composition is the classic confusion: in code both are fields, so the difference is in lifetime and ownership (see Core Java · Module 2). Many professional diagrams use only plain association and composition. If you are unsure, an association arrow is rarely wrong.

Multiplicity and labels

Multiplicity says how many instances take part: 1 exactly one, 0..1 optional, * many, 1..* at least one. Put it in quotes beside each end, and add a label for the role.

Read it aloud: "A customer places zero or more orders. An order contains one or more items, and the items belong to that order alone (composition). Each item refers to one product. An order may have one payment." Mapping to Java: Customer has List<Order>; Order has List<OrderItem> created inside it; OrderItem has a Product field; Order has an optional Payment field.

How to draw a class diagram in an interview

  1. List the nouns in the requirement: these are candidate classes.
  2. List the verbs: these become methods, placed on the class that owns the data.
  3. Add relationships and multiplicity; use composition when the part cannot exist alone.
  4. Extract interfaces where behaviour varies (payment methods, pricing rules), and mark them <<interface>>.
  5. Show only what helps: skip getters and setters, trivial fields and every utility class.

Edge cases and conventions

  • Mermaid generics use tildes: List~Order~, not angle brackets. In this site's source you must also write < as &lt; in the arrows.
  • Arrow direction in association shows navigability: Order --> Customer means Order holds the reference. A plain line -- means no direction is stated.
  • The JPA @OneToMany and @ManyToOne pair is a bidirectional association drawn with two arrows or one plain line.
  • Dependency (..>) is weaker than association: no field, only a temporary use.

Mistakes to avoid

  • Using inheritance arrows for "has-a" ideas; confusing the filled diamond (composition) with the hollow one (aggregation).
  • Drawing every getter, every DTO and every utility. A diagram that shows everything shows nothing.
  • Pointing the realization arrow from the interface to the class. It points to the interface.

Interview: UML class diagram

  • Explain the difference between association, aggregation and composition using ownership and lifetime.
  • Explain inheritance versus realization: solid versus dashed line, both with a hollow triangle at the parent.
  • In LLD rounds, draw the classes with key methods and multiplicities, then say which design principle each interface supports.

UML sequence diagrams: lifelines, messages and alt/loop blocks

A sequence diagram shows objects as vertical lifelines and the messages between them as horizontal arrows in time order, so you can explain one scenario (such as placing an order or logging in) step by step.

A class diagram shows what exists; a sequence diagram shows what happens during one use case. Time runs from top to bottom. It is the best tool to explain request flows, to check that a design has the right collaborators, and to spot a class that does too much or too little.

The parts of a sequence diagram

Participant / lifeline
A box at the top (an object, service or actor such as the user) with a dashed vertical line below it that represents its life during the scenario. In Mermaid: participant or actor.
Synchronous message
A call where the caller waits for the answer: a solid line with a filled arrowhead (A->>B: message), like an ordinary Java method call.
Return message
The reply, drawn as a dashed line (B-->>A: result).
Asynchronous message
A call where the sender does not wait (a message put on a queue, @Async, an event). Drawn with an open arrowhead: A-)B: message in Mermaid.
Activation bar
A thin box on a lifeline showing when the object is busy. Mermaid uses activate/deactivate or the shortcut +/- on arrows.
Fragment (alt, opt, loop)
A labelled box around messages: alt (if / else), opt (if with no else), loop (repeat), par (parallel).

Example 1: place an order

What this diagram teaches you about the design:

  • OrderService is the coordinator; it talks to inventory, payment and repository. If this list grows past four or five collaborators, think about a Facade or events.
  • The confirmation email is asynchronous: failure to send it must not roll back the order.
  • The "declined" branch shows compensation (release the reserved stock). Missing branches in a diagram are missing code in the program.

The matching Java skeleton:

public OrderConfirmation placeOrder(Cart cart) {
    for (CartItem item : cart.items()) {
        inventory.reserve(item.sku(), item.qty());               // loop
    }
    PaymentResult result = payments.charge(cart.totalInPaise());
    if (result.approved()) {                                     // alt
        Order order = repository.save(Order.from(cart, result.receipt()));
        events.publish(new OrderPlaced(order.id()));             // async
        return OrderConfirmation.of(order);
    }
    inventory.release(cart.items());                             // else: compensate
    throw new PaymentFailedException(result.reason());
}

Tips for good sequence diagrams

  • One diagram per scenario. Draw the happy path first, then add the failure branches.
  • Show five to seven participants at most; group the rest ("Database", "Payment provider").
  • Name messages after methods or HTTP calls so the code is easy to match.
  • Use the diagram to find design problems: a lifeline that talks to everyone is a god object; a lifeline with no messages is unnecessary.

Edge cases

  • Do not draw getters, logging and framework internals; show business collaborations.
  • In a microservices flow, show the network hop and timeouts: a synchronous call across services is a failure point (see distributed system patterns).

Interview: sequence diagrams

  • Class diagram vs sequence diagram? Static structure versus dynamic interaction over time.
  • Synchronous vs asynchronous message? The caller waits for the reply, or does not.
  • Be ready to sketch "place an order" or "login" on a whiteboard: actors, services, alt for success and failure.

Interview questions — Design principles

What do cohesion and coupling mean, and what should you aim for?

Cohesion is how strongly the members of one module belong together; coupling is how much one module depends on others. Aim for high cohesion and low coupling: each class has one focused job, and classes talk through small interfaces. This makes change cheap, because a change touches few places.

Explain each letter of SOLID in one line.

S: a class has one reason to change. O: add behaviour by adding new code, not by editing old code. L: a subtype can replace its parent without breaking callers. I: prefer small, role-specific interfaces to fat ones. D: depend on abstractions, not on concrete details; high-level code owns the abstraction.

Does SRP mean a class should have only one method?

No. SRP is about reasons to change (or actors), not about method count. A class with fifteen methods that all serve one concern is fine. A class with three methods that mix SQL, pricing and email is not. Ask: "who would ask me to change this class?" If the answer is several different groups, split it.

How do you apply OCP to a growing switch statement?

Introduce an interface (for example DiscountPolicy), write one class per branch, and let the caller loop over or look up the right implementation. A new case becomes a new class. In Spring you can inject List<DiscountPolicy> or Map<String, DiscountPolicy> so new @Component classes are found automatically. This is the Strategy pattern.

Why is a Square not a valid subclass of a mutable Rectangle?

A Rectangle promises that setting the width leaves the height unchanged. Square breaks this by changing both. Code like r.setWidth(5); r.setHeight(4); expects area 20, but a Square gives 16. The child cannot be substituted for the parent, which violates LSP. Fix: use immutable types or a shared Shape interface, not inheritance between them.

Which SOLID principle does a method that throws UnsupportedOperationException usually break?

LSP, because callers of the parent type expect the method to work. The root cause is often ISP: the interface is too fat, so some implementers cannot honour all of it. Split the interface into smaller roles so that each class implements only what it supports.

What is the difference between DIP, DI and IoC?

DIP is a design principle: high-level code depends on an abstraction, not on a low-level detail. DI is a technique: objects receive their collaborators from outside (usually via the constructor) instead of creating them. IoC is the wider idea that a framework or container controls object creation and flow, calling your code. Spring's container is an IoC container that performs DI, and DI makes DIP practical. You can inject a concrete class and still violate DIP.

Why is constructor injection preferred over field injection?

Dependencies are explicit and cannot be forgotten, fields can be final, the object is never half-built, and you can create it in a plain unit test with new without Spring. Field injection hides dependencies and needs reflection or a container to set them.

Is DRY the same as "never write similar code twice"?

No. DRY is about duplicated knowledge, such as one business rule in three places. Two blocks that look alike but change for different reasons should stay separate; merging them couples unrelated things, which is worse than the duplication. Use the rule of three: abstract when the third copy appears and the common shape is clear.

How do KISS and YAGNI stop over-engineering?

KISS prefers the simplest design that solves the problem. YAGNI says do not build features or flexibility "just in case", because the guess about the future is usually wrong and unused code still costs. Keep the code loosely coupled and well tested so that real changes are cheap, and add the abstraction when a second or third real case shows up.

Why favour composition over inheritance?

Inheritance couples a child to the parent's implementation (fragile base class), is fixed at compile time and allows one parent. Composition holds collaborators behind interfaces, so you can swap them at run time and test with fakes. It also avoids class explosion: channels × priorities needs N × M subclasses by inheritance but only N + M classes with composition.

What is the Law of Demeter? Give an example violation.

A method should talk only to itself, its parameters, its fields and objects it creates. order.getCustomer().getAddress().getCity() makes the caller depend on three classes' structure. Fix: order.isShippedTo("Mumbai"), so only Order and Customer know the details. Fluent builders and streams are not violations because each call is on the same type.

Name five code smells and the refactoring for each.

Long method → Extract Method. Large class → Extract Class. Primitive obsession → value objects (Email, Money). Feature envy → Move Method. Switch on type → replace conditional with polymorphism. Others: data clumps → parameter object; shotgun surgery → gather the scattered concern into one class.

Why should you avoid boolean flag parameters?

The call send(user, text, true) does not say what true means, and a flag shows the method does two things. Split it into two well-named methods or pass an enum such as Priority.URGENT.

Aggregation versus composition: how do they differ in a class diagram and in code?

Both mean "whole has parts". In aggregation (hollow diamond) the parts exist independently and are passed in, like employees in a department. In composition (filled diamond) the whole creates and owns the parts and they die with it, like rooms in a house. In Java both are fields; the difference is who creates the parts and who controls their lifetime.

Cheat sheet — Design principles

  • Good design low cost of change: high cohesion, low coupling.
  • Cohesion things inside a module belong together; describe the class without "and".
  • Coupling how much modules know about each other; depend on interfaces, not classes.
  • Encapsulation hide data, expose behaviour; every public getter is a small leak.
  • Program to an interface declare List, not ArrayList; depend on roles.
  • SRP one reason to change (one actor); not "one method".
  • OCP extend by adding classes, not editing; replace growing switch with an interface (Strategy).
  • LSP a subtype must work wherever the parent works; no stronger preconditions, no weaker postconditions, no surprise exceptions.
  • ISP many small role interfaces beat one fat interface; no empty or throwing stubs.
  • DIP high-level code owns the abstraction; low-level details implement it.
  • DIP vs DI vs IoC principle vs technique (inject through constructor) vs container controls flow.
  • DRY one authoritative place for each piece of knowledge, not each line of text.
  • Rule of three copy twice, abstract on the third.
  • KISS simplest thing that works; YAGNI do not build it until needed.
  • Law of Demeter no a.getB().getC().doIt() chains (builders are fine).
  • Tell, Don't Ask account.withdraw(x), not read-decide-set from outside.
  • Separation of concerns controller → service → repository; cross-cutting through aspects.
  • Composition over inheritance N + M classes beat N × M; inherit only for true is-a.
  • Clean code intent-revealing names, short methods, ≤3 parameters, no flags, guard clauses, named constants, comments say why.
  • Code smells long method, large class, primitive obsession, feature envy, shotgun surgery, switch on type, duplication, data clumps.
  • Refactor safely tests first, tiny steps, run tests after each, commit often.
  • UML class + - # ~ visibility; inheritance <|--; realization <|..; association -->; aggregation o--; composition *--; dependency ..>.
  • Multiplicity 1, 0..1, *, 1..* in quotes at each end.
  • UML sequence lifelines, ->> sync, -->> return, -) async, alt/opt/loop blocks.

Practice — Design principles

  1. Spot the responsibilities (easy). Take a UserService that registers a user, hashes the password, saves to the database, sends a welcome email and writes an audit log. List its reasons to change. Done when you have a list of at least four concerns and a name for each class you would extract.
  2. Apply SRP (easy/medium). Refactor the class from exercise 1 into a coordinator plus collaborators (PasswordHasher, UserRepository, WelcomeMailer, AuditLog). Done when UserService.register is under ten lines and you can unit-test it with fakes and no database.
  3. Replace a switch with Strategy (medium). Write a ShippingCostCalculator with a switch on STANDARD, EXPRESS, SAME_DAY. Refactor to a ShippingPolicy interface with one class per mode. Done when adding INTERNATIONAL needs no edit to the calculator; then inject List<ShippingPolicy> with Spring.
  4. Fix an LSP violation (medium). Given abstract class Account { withdraw(); } with a FixedDepositAccount that throws UnsupportedOperationException in withdraw, redesign the hierarchy with Account, Withdrawable and Depositable interfaces. Done when no method throws UnsupportedOperationException and callers cannot pass an FD to withdrawAll.
  5. Segregate an interface (medium). Split a 6-method ProductRepository into reader, writer and search interfaces. Make a catalog page depend only on the reader. Done when a test for the catalog fakes one method, not six.
  6. Invert a dependency (medium). Take a class that calls new SmtpMailer() and new MySqlDao() inside its methods. Introduce interfaces, constructor injection and a Spring @Service. Done when you can swap both in a plain JUnit test and the service never imports a JDBC or SMTP class.
  7. Composition over inheritance (medium/hard). Model a coffee shop with EspressoWithMilk, EspressoWithSoy, LatteWithSugar and so on as subclasses. Replace it with a Drink composed of a base, a milk and toppings. Done when you can create ten combinations with six classes in total.
  8. Clean-code makeover (medium). Take any 60-line method from your own project. Apply: rename, extract three methods, replace magic numbers with constants or an enum, remove a boolean flag, add guard clauses. Done when each method does one thing and tests still pass.
  9. Find the smells (medium). Review a pull request or an open-source class and write down five smells from the table, each with the line numbers and the refactoring you would apply.
  10. Diagrams (hard). For a "library management" system, draw (a) a class diagram with at least six classes, using composition, an interface and multiplicity, and (b) a sequence diagram for "borrow a book" with an alt block for "book unavailable". Done when every arrow can be mapped to a field, parameter or method call in Java.

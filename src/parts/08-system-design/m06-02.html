Delivery semantics: at-most-once, at-least-once, effectively once

A message system can promise at-most-once (may lose), at-least-once (may duplicate) or exactly-once; true exactly-once delivery over an unreliable network is not achievable, so you combine at-least-once delivery with idempotent consumers to get "effectively once" processing.

The core problem

A producer sends a message and waits for an acknowledgement (ack). Three things can go wrong: the message is lost on the way, the consumer crashes before finishing, or the ack is lost after the work was done. In the last case the sender cannot tell "never arrived" from "arrived but the ack vanished". It must choose: send again (risking a duplicate) or do not send again (risking a loss). That choice is the whole topic.

The three guarantees

GuaranteeHow it worksFailure outcomeTypical use
At-most-onceSend once, never retry. Consumer acks before processingMessage can be lost, never duplicatedMetrics, logs, location pings where a gap is fine
At-least-onceRetry until acked. Consumer acks after processingMessage can be processed twice, never lostDefault for orders, payments, notifications
Exactly-onceEach message has exactly one effectNo loss, no duplicate effectMoney movement, inventory

The order of ack and processing decides the guarantee

  • Ack first, then process (at-most-once): if the consumer crashes after the ack, the message is gone.
  • Process first, then ack (at-least-once): if the consumer crashes after processing but before the ack, the broker redelivers and the work runs again.

Kafka makes this concrete: a consumer commits its offset (its position in the log). Commit before processing gives at-most-once; commit after processing gives at-least-once. RabbitMQ and SQS use acknowledgements and visibility timeouts in the same way.

Is exactly-once real?

Over an unreliable network, delivering a message exactly once is impossible in the general case (a version of the "two generals" problem). What systems can offer is exactly-once processing effect, which is the combination:

at-least-once delivery + deduplication / idempotency = effectively once

Kafka provides features for this inside its own world: an idempotent producer (the broker drops duplicate sends from the same producer session) and transactions that write results and commit offsets atomically in a read-process-write pipeline between Kafka topics. Those guarantees stop at Kafka's boundary. The moment a consumer writes to a database, sends an email or calls a payment API, you need your own idempotency.

Making a consumer effectively once

  1. Give every message a stable unique id created by the producer (a UUID or a business id such as orderId + eventType). Never create it in the consumer.
  2. In one database transaction, insert the id into a processed_message table and apply the business change.
  3. A duplicate violates the unique constraint; catch it, skip the work, and ack the message.
  4. Ack only after the transaction commits.
  5. Expire old ids after a safe window (longer than the broker's maximum redelivery time).

The SQL version is in the Idempotency article. Other options: an upsert by natural key, or optimistic locking with a version number.

Deduplication windows and ordering

A dedupe store cannot grow forever, so it keeps ids for a window (a day, a week). A duplicate that arrives after the window gets through, so choose the window longer than the longest possible redelivery. Also remember ordering: retries and parallel consumers can reorder messages. Kafka orders only inside a partition, so choose the partition key (for example orderId) so that all events of one order go to one partition. Consumers that need order should process one partition sequentially, and should still guard against stale updates with a version or timestamp check.

Poison messages and dead-letter queues

A message that always fails (bad JSON, a bug) will be retried forever under at-least-once and can block the queue. After N attempts, move it to a dead-letter queue (DLQ), alert, and inspect it later. Fix the bug, then replay from the DLQ; idempotent consumers make replay safe.

Exception: at-most-once is sometimes the right answer

For a driver's GPS ping every 4 seconds, losing one ping is harmless and the next one replaces it. Retrying would only add load and delay. Fire-and-forget is correct there.

Common mistakes

  • Believing a broker flag called "exactly-once" protects your database and email side effects.
  • Non-idempotent consumers on an at-least-once queue (double refund, double email).
  • Auto-committing offsets before the work finishes.
  • Generating the dedupe id from a timestamp or random value inside the consumer.

Interview angle

  • State the three guarantees and what breaks in each.
  • Say: "Exactly-once delivery is not possible over a network; I use at-least-once plus an idempotent consumer to get exactly-once effects."
  • Mention ack-after-processing, the processed-message table, DLQ and partition keys for ordering.

Distributed transactions: why not 2PC, and the saga pattern

Two-phase commit gives atomic commits across databases but blocks and depends on a coordinator, so microservices use sagas instead: a chain of local transactions where each step has a compensating action that undoes it if a later step fails.

The problem

In a monolith, "place order" is one @Transactional method: insert the order, take payment, reduce stock; if anything fails, the database rolls everything back. With database-per-service (see Monolith vs microservices) those three writes live in three databases owned by three services. There is no single transaction around them. What if payment succeeds and then inventory says "out of stock"? You must undo the payment.

Two-phase commit (2PC)

2PC uses a coordinator and works in two phases.

In phase 1 each participant does the work, writes it to its log, locks the rows and votes yes or no. In phase 2, if all voted yes the coordinator orders commit; if any voted no (or timed out) it orders abort.

Why it is avoided in microservices:

  • Blocking. After voting yes, a participant must wait for the decision and keeps its locks. If the coordinator crashes now, participants are stuck "in doubt" until it returns, and other transactions queue behind those locks.
  • Coordinator is a single point of failure and a latency cost (extra round trips, forced disk writes at each step).
  • Availability drops. All participants must be up and fast for any commit to succeed, which is a CP choice in CAP terms.
  • Not every system supports it. Most message brokers, SaaS APIs (a payment gateway) and many NoSQL stores cannot join an XA transaction.

2PC (XA transactions) still exists inside some databases and in tightly controlled setups, and distributed SQL databases use consensus-based commits internally. But for service-to-service business workflows, the standard answer is the saga.

The saga idea

A saga is a sequence of local transactions, one per service. Each step commits on its own and then triggers the next. If a step fails, the saga runs compensating transactions for the steps that already committed, in reverse order. A compensation is a new business action that semantically undoes the earlier one: "refund the payment", "release the reserved stock", "cancel the order". It is not a database rollback; the first change was already visible.

StepLocal transactionCompensation if a later step fails
1 OrdersCreate order as PENDINGMark order CANCELLED
2 PaymentAuthorise or capture ₹1,200Refund or void the authorisation
3 InventoryReserve 2 unitsRelease the 2 units
4 ShippingCreate shipmentCancel the shipment

Happy path and failure path (orchestrated)

Choreographed saga

Without a central orchestrator, services react to each other's events. On failure, the failing service publishes a failure event and earlier services listen and compensate.

Design rules for sagas

  • Every step and every compensation must be idempotent and retryable: messages repeat (Delivery semantics).
  • Compensations must always be able to succeed. "Refund" can be retried until it works; design so that it cannot be refused.
  • Persist the saga state (which step, what status) so a restarted orchestrator continues where it stopped. A status column on the order plus a saga log table is the minimum.
  • Order steps to put the hard-to-undo ones last. Reserve stock and authorise payment first; do irreversible things (ship, send final email) at the end. Prefer a pending or reserved state that can be released over a final state that must be reversed.
  • Handle timeouts: a step that never answers needs a deadline, then a retry or a compensation.
  • Publish step results reliably with the outbox pattern.

Eventual consistency in practice

Sagas have no isolation: between steps, other requests can see the half-finished state (an order PENDING, stock reserved but payment not yet confirmed). This is eventual consistency. You manage it in the design: show states such as "processing" to the user, use semantic locks (the reserved flag stops another request taking the same stock), and make reads tolerate pending data. Typical user-facing flow: return 202 Accepted with an order id, let the client poll or receive a push when the order is CONFIRMED or CANCELLED.

public enum OrderStatus {
    PENDING,            // saga started
    PAYMENT_CAPTURED,   // step 2 done
    STOCK_RESERVED,     // step 3 done
    CONFIRMED,          // all steps done
    CANCELLING,         // compensating
    CANCELLED           // compensation finished
}

Exception: when to still use a local transaction

If two pieces of data always change together, they probably belong in the same service and database. Needing sagas everywhere is a sign that service boundaries are drawn wrong.

Common mistakes

  • Compensations that are not idempotent (double refund).
  • No saga state, so a crash leaves orders stuck in PENDING forever. Run a sweeper job for stuck sagas.
  • Treating compensation as a database rollback. Customers may already have seen an email or a notification; the compensation may need to send an apology too.
  • Hand-building a big orchestrator when a workflow engine would do.

Transactional outbox and change data capture

Saving to the database and publishing to a broker are two writes that cannot be one transaction; the outbox pattern writes the event into an outbox table in the same database transaction as the business change, and a relay (a poller or change data capture) publishes it afterwards.

The dual-write problem

The order service must save the order and publish OrderPlaced. As code it looks innocent:

@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);                 // 1. database write
    broker.publish(new OrderPlaced(order.id())); // 2. broker write
}

The two writes are not atomic. If the app crashes between 1 and 2, the order exists but no event is sent: payment and shipping never start. If you publish first and the commit then fails, you announced an order that does not exist. Even publishing inside the transaction does not help; the broker is not part of the database transaction, and the commit can still fail after the publish. This is the dual-write problem.

The outbox solution

Write the event to an outbox table in the same local transaction as the business data. A single database commit makes both durable, or neither. A separate process then reads new outbox rows and publishes them to the broker.

CREATE TABLE outbox (
    id            BIGSERIAL PRIMARY KEY,
    event_id      UUID         NOT NULL UNIQUE,      -- consumers use this to dedupe
    aggregate_id  VARCHAR(64)  NOT NULL,             -- e.g. the order id, used as message key
    event_type    VARCHAR(64)  NOT NULL,             -- e.g. OrderPlaced
    payload       JSONB        NOT NULL,
    created_at    TIMESTAMP    NOT NULL DEFAULT now(),
    published_at  TIMESTAMP                          -- null until sent
);
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);
    outboxRepository.save(new OutboxEvent(
        UUID.randomUUID(), order.id().toString(), "OrderPlaced", toJson(order)));
    // one commit: either both rows exist or neither does
}

Two ways to relay

1. Polling publisher. A scheduled job selects unpublished rows, sends them, then marks them published. Simple, no extra infrastructure. Downsides: polling delay and load on the database. With several relay instances, claim rows safely using SELECT ... FOR UPDATE SKIP LOCKED in PostgreSQL.

@Scheduled(fixedDelay = 500)
@Transactional
public void publishPending() {
    List<OutboxEvent> batch = outboxRepository.lockNextBatch(100);   // FOR UPDATE SKIP LOCKED
    for (OutboxEvent e : batch) {
        broker.send(e.aggregateId(), e.eventType(), e.payload());   // key = aggregate id
        e.markPublished();
    }
}

If the app crashes after sending but before marking, the event is sent again after restart. That is fine: delivery is at-least-once and consumers dedupe by event_id (Delivery semantics).

2. Change data capture (CDC). Every database writes all changes to its transaction log (PostgreSQL's WAL, MySQL's binlog). A CDC tool reads that log and turns each committed row change into an event, with no polling queries. Debezium is the best-known open-source CDC tool; it runs on Kafka Connect and can read the outbox table and publish each new row to a Kafka topic. Benefits: low delay, low load on the database, order preserved as in the log. Costs: another system to run, and the log retention and connector offsets to monitor.

AspectPolling publisherCDC (Debezium)
SetupA scheduled jobKafka Connect plus connector
LatencyPoll interval (hundreds of ms)Very low
Database loadRepeated queriesReads the log, light
OrderingBy id or time, needs careFollows commit order
Best forSmall and medium systemsHigh volume, many consumers

Other uses of CDC

CDC is useful beyond outbox: keep a search index (Elasticsearch) in sync with the database, invalidate caches when rows change, feed a data warehouse, or replicate to another store without changing the application code. It turns "the database changed" into a stream everyone can use (Module 5 has the cache and search building blocks).

Housekeeping

  • Delete or archive published outbox rows regularly, or the table grows without limit.
  • Use the aggregate id as the message key so events of one order stay in order inside a Kafka partition.
  • Version your event payloads; consumers upgrade at different times.
  • Monitor the oldest unpublished row: it shows relay lag.

Rule: never publish to the broker directly from inside the business transaction

Write to the outbox; let the relay publish. Consumers must still be idempotent, because the outbox gives at-least-once delivery, not exactly-once.

In real projects

This pattern sits under almost every saga and every "publish event after save" feature. The Spring and Kafka side is in Spring Boot · Module 7. Related idea for the receiving side: the inbox (processed-message) table.

Resilience: timeouts, circuit breakers, bulkheads and load shedding

A failure in one dependency must not become a failure of everything: set timeouts on every call, stop calling a broken service with a circuit breaker, isolate resources with bulkheads, serve a fallback when possible, and shed excess load before you fall over.

A cascading failure story

The checkout service calls the recommendation service to show "you may also like". One evening the recommendation database slows down: responses now take 30 seconds instead of 50 ms. Checkout has no timeout, so each request waits. Checkout has 200 worker threads; at 100 requests per second, all 200 are stuck within about two seconds. Checkout now cannot serve any request, even ones that never need recommendations. The API gateway sees checkout timing out, retries, and doubles the traffic. The front-end calls other services that also call checkout; they exhaust their threads too. A slow non-critical feature has brought down the shop. This is a cascading failure. The tools below each cut one link in that chain.

1. Timeouts everywhere

Every remote call needs a timeout. Waiting forever is the most common root cause of cascades. Know the two kinds:

  • Connect timeout: how long to wait to establish the connection. Keep it short (often a few hundred milliseconds to one second), because a healthy server accepts connections fast.
  • Read (response) timeout: how long to wait for data after the request is sent. Base it on the callee's real latency: for example the 99th percentile plus a margin (if p99 is 200 ms, use around 500 ms to 1 s), not 60 seconds.

Also set a timeout on database calls, connection-pool borrow time, and queue waits. Pass a deadline down the chain: if the user's request has 2 s in total and 1.5 s is gone, the next service should not start work that needs 1 s.

import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.URI;
import java.time.Duration;

HttpClient client = HttpClient.newBuilder()
    .connectTimeout(Duration.ofMillis(500))          // connect timeout
    .build();

HttpRequest req = HttpRequest.newBuilder(URI.create("http://recs/v1/for/42"))
    .timeout(Duration.ofSeconds(1))                  // request (response) timeout
    .GET()
    .build();

2. Circuit breaker

Like an electrical fuse. If a dependency keeps failing, stop calling it for a while: fail immediately (fast), give it time to recover, and test it carefully before going back. This saves your threads and avoids hammering a sick service.

  • Closed: calls pass; the breaker counts failures and slow calls in a sliding window (for example the last 100 calls).
  • Open: when the failure rate crosses a threshold (say 50%), calls fail instantly without touching the dependency, for a wait period (say 30 s).
  • Half-open: after the wait, a few trial calls go through. If they succeed, close; if they fail, open again.

Treat slow calls as failures too, because slowness is what drains threads. The Resilience4j configuration and annotations are in Spring Boot · Module 7.

3. Bulkheads

On a ship, watertight compartments stop a leak from sinking the whole vessel. A bulkhead limits the resources one dependency or one customer can use, so a failure stays inside its compartment.

  • Separate thread pools or concurrency limits per dependency: at most 20 concurrent calls to recommendations, 50 to payments. When recommendations hang, only those 20 slots are stuck; the other 180 workers keep serving checkout.
  • Separate connection pools per downstream or per workload.
  • Separate deployments for critical and non-critical traffic, or per-tenant quotas, so one noisy client cannot starve the rest.

4. Fallbacks and graceful degradation

When a call fails or the breaker is open, return something useful instead of an error: a cached response, a default value, a simplified result, or skip the feature. The checkout page without recommendations still sells things. Graceful degradation means the product loses features one by one, not all at once. Decide in advance which features are critical (payment) and which are optional (recommendations, reviews, "recently viewed"), and wrap the optional ones in timeout plus fallback.

List<Product> recs;
try {
    recs = recsClient.forUser(userId);          // has timeout and circuit breaker
} catch (Exception e) {
    recs = popularProductsCache.top(10);        // fallback: generic popular items
}

5. Load shedding and rate limiting

Every server has a limit. Past it, accepting more work makes everything slower, and latency explodes until requests time out; goodput (useful work done) collapses. Load shedding means deliberately rejecting some requests early, with a quick 503 or 429, so the rest succeed. Choose what to drop: low-priority traffic first (analytics, background refresh), then by client, and protect critical paths like payment. Techniques: a limit on in-flight requests, a bounded queue (reject when full instead of queueing without bound), and watching latency or CPU to start shedding. It pairs with rate limiting at the edge, which caps each client's rate before it reaches the system (Module 5 covers algorithms; the distributed rate limiter design builds one).

  • A bounded queue gives back-pressure: producers learn to slow down.
  • Return Retry-After so clients back off (Retries).
  • Reject early: the cheapest request is the one you refuse before doing work.

Putting the tools together

ToolProtects againstCost
TimeoutWaiting forever on a hung callSome calls cut off that would have finished

A sensible order for one outbound call is: bulkhead limit, circuit breaker, then a time-limited call, with retry only for safe, transient failures, and a fallback at the end. Finally, test it: kill a dependency in staging (chaos testing) and check that the system degrades as planned.

Common mistakes

  • Default timeouts that are infinite or minutes long.
  • Circuit breaker around an operation that is not safe to skip (it hides real errors without a plan).
  • A shared thread pool for all dependencies, so no bulkhead exists.
  • Fallbacks that call another fragile service.
  • Retries inside the breaker multiplying load on the failing dependency.

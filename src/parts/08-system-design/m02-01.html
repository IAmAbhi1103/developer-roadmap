A design pattern is a named, proven solution to a problem that keeps appearing in object-oriented design. "Use a Strategy here" lets a whole team understand a design in four words. Patterns also explain the frameworks you use every day: Spring is full of singletons, factories, proxies, templates and observers, and the JDK uses them too (Comparator, InputStream wrappers, Runnable).

This module teaches 13 patterns in detail, in three groups (creational, structural, behavioural), and then shows where Spring uses them. Each pattern follows the same shape: intent, the problem, structure, complete Java code on a realistic example, JDK and Spring usage, pros and cons, and when not to use it. It builds on Module 1: nearly every pattern is a way to apply SOLID, especially the Open/Closed and Dependency Inversion principles. What design patterns are, how to learn them and the danger of over-engineering

A design pattern is a reusable, named solution to a common design problem; the Gang of Four book groups 23 of them into creational, structural and behavioural patterns, and the right way to learn them is to start from the problem, not from the pattern.

In 1994 four authors (Erich Gamma, Richard Helm, Ralph Johnson and John Vlissides, called the Gang of Four or GoF) published Design Patterns: Elements of Reusable Object-Oriented Software. It describes 23 patterns they had seen in good code. A pattern is not a library you import or code you copy. It is a description of a problem, a solution structure and the trade-offs, which you adapt to your case. The value is in three things: a ready solution, a shared vocabulary ("wrap it in a Decorator"), and a reminder of the costs.

The three categories

CategoryConcernPatterns in these notes
CreationalHow objects are createdSingleton, Factory (Simple, Method, Abstract), Builder; also Prototype
StructuralHow classes and objects are combined into larger structuresAdapter, Decorator, Facade, Proxy; also Composite, Flyweight
BehaviouralHow objects communicate and share responsibilityStrategy, Observer, Command, State, Chain of Responsibility, Template Method; also Iterator, Mediator, Memento, Visitor

How to read each pattern

  1. Intent: one line saying what the pattern is for.
  2. The problem: the pain, as a short story. If you do not feel the pain, you do not need the pattern.
  3. Structure: the classes and their relationships (a UML class diagram, see UML class diagrams).
  4. Code: a complete, realistic Java version.
  5. Where you have seen it: JDK and Spring examples.
  6. Pros, cons, and when not to use it.

How to learn patterns well

  • Problem first. Ask "what changes here, and what hurts?" and then "which pattern solves that?". Memorising names without problems gives you a hammer looking for nails.
  • Find them in code you know. new BufferedReader(new FileReader(...)) is Decorator. Collections.sort(list, comparator) is Strategy. Once you see them, they stay in memory.
  • Write each one once on a small example and then refactor a messy class into it.
  • Learn the trade-offs. Every pattern adds classes and indirection. A pattern is a purchase; know the price.

Patterns and the principles

Patterns are not new ideas on top of SOLID. They are SOLID applied to recurring situations: Strategy, State, Decorator and Template Method apply the Open/Closed Principle; Factory, Adapter and Facade apply Dependency Inversion; Strategy and Decorator use composition over inheritance.

The danger: over-engineering

Beginners who just learned patterns put them everywhere: a SingletonFactoryBuilder to create a class used once. This hurts: more classes, more files, harder reading, and flexibility nobody asked for (YAGNI). A language also reduces the need for some patterns. With lambdas and records, Java removes much of the ceremony: a Strategy can be a lambda, a Command can be a Runnable, a Builder is often not needed for a small record.

When to introduce a pattern

  • You have a real problem you can name (a growing switch, an unreadable 8-argument constructor, a third-party API you cannot change).
  • The simple solution has already hurt once or twice.
  • You can say in one sentence what the pattern buys you.

If not, write the simple code first. Refactor to a pattern when the need appears.

Anti-patterns to know

  • God object: one class that knows and does everything.
  • Spaghetti code: tangled control flow with no structure.
  • Golden hammer: using the one pattern you know for every problem.
  • Singleton abuse: global state in disguise (see Singleton).
  • Premature abstraction: an interface with one implementation and no plan for a second.

Interview: design patterns in general

  • What is a design pattern? A general, reusable solution to a commonly occurring design problem, with a name, structure and trade-offs. Not code to copy.
  • Name the three categories with two examples each. Creational: Singleton, Builder. Structural: Adapter, Proxy. Behavioural: Strategy, Observer.
  • Which patterns have you used? Pick three from your projects: Strategy for payment methods, Builder for request objects, Observer through Spring events. Explain the problem each solved.

Singleton: thread-safe implementations, breaking it, and Spring's singleton scope

Singleton guarantees that a class has exactly one instance and gives global access to it; in Java you write it with an eager field, a holder class or an enum, and you must understand how threads, reflection, serialization and cloning can break it.

Intent: ensure that a class has only one instance and provide a global point of access to it.

The problem

Some things must exist once in a process: an application configuration, a connection pool, a logger registry, a cache, a hardware device handle. If two ConnectionPool objects each opened 50 connections, the database would run out. You need a way to stop others from calling new. The answer is a private constructor plus a static method that returns the single instance.

1. Eager initialisation

Create the instance when the class loads. It is simple and thread-safe, because the JVM guarantees that class initialisation runs once and is visible to all threads.

public final class AppConfig {
    private static final AppConfig INSTANCE = new AppConfig();   // created at class load

    private final java.util.Properties props = new java.util.Properties();

    private AppConfig() {                  // nobody else can call new
        props.setProperty("currency", "INR");
    }

    public static AppConfig getInstance() { return INSTANCE; }

    public String get(String key) { return props.getProperty(key); }
}

Downside: the object is built even if it is never used, which matters when it is expensive. Also, an exception in the constructor happens at class-load time (ExceptionInInitializerError).

2. Lazy initialisation with synchronized

Create the instance on the first call. The naive version is not thread-safe: two threads may both see null and both create an object. Making the method synchronized fixes it:

public final class LazySingleton {
    private static LazySingleton instance;

    private LazySingleton() { }

    public static synchronized LazySingleton getInstance() {    // safe, but slow
        if (instance == null) {
            instance = new LazySingleton();
        }
        return instance;
    }
}

Correct, but every call takes the lock, even long after the instance exists. That cost is small today but visible on a very hot path.

3. Double-checked locking with volatile

Check once without a lock (fast path); only if it is null, lock and check again.

public final class DclSingleton {
    private static volatile DclSingleton instance;     // volatile is REQUIRED

    private DclSingleton() { }

    public static DclSingleton getInstance() {
        DclSingleton local = instance;                 // 1st check, no lock
        if (local == null) {
            synchronized (DclSingleton.class) {
                local = instance;                      // 2nd check, with lock
                if (local == null) {
                    instance = local = new DclSingleton();
                }
            }
        }
        return local;
    }
}

Why volatile? The statement instance = new DclSingleton() is really three steps: (1) allocate memory, (2) run the constructor to set the fields, (3) write the reference into instance. The compiler and CPU may reorder 2 and 3. Then a second thread, doing the unlocked first check, can see a non-null instance that points to an object whose constructor has not finished, and use a half-built object. volatile forbids that reordering and guarantees that a thread seeing the reference also sees the finished fields (the Java memory model, Core Java · Module 6). Without volatile DCL is broken. Copying into a local variable avoids a second volatile read on the fast path.

4. The holder idiom (Bill Pugh)

Put the instance in a private static nested class. The JVM loads the nested class only when getInstance() first touches it, and class initialisation is thread-safe. You get laziness and thread safety with no locks and no volatile. This is the usual recommendation for a lazy singleton.

public final class ConnectionPool {
    private ConnectionPool() { /* open connections */ }

    private static class Holder {                       // loaded on first use
        private static final ConnectionPool INSTANCE = new ConnectionPool();
    }

    public static ConnectionPool getInstance() {
        return Holder.INSTANCE;
    }
}

5. The enum singleton

Joshua Bloch (Effective Java) calls a single-element enum the best way to write a singleton. The JVM guarantees one instance per constant, thread-safe creation, and protection against reflection and serialization attacks.

public enum IdGenerator {
    INSTANCE;

    private final java.util.concurrent.atomic.AtomicLong next =
            new java.util.concurrent.atomic.AtomicLong(1000);

    public long nextId() { return next.getAndIncrement(); }
}

// usage
long id = IdGenerator.INSTANCE.nextId();

Limits: an enum cannot extend another class (it can implement interfaces), and it is eager, in the sense of being created when the enum class loads.

Breaking a singleton, and the fixes

Reflection. setAccessible(true) on the private constructor lets any code create a second instance.

import java.lang.reflect.Constructor;

Constructor<AppConfig> c = AppConfig.class.getDeclaredConstructor();
c.setAccessible(true);
AppConfig second = c.newInstance();
System.out.println(second == AppConfig.getInstance());     // false: two instances!

Fix: throw from the constructor if an instance exists (if (INSTANCE != null) throw new IllegalStateException();), or use an enum. Reflection cannot instantiate enums: newInstance throws IllegalArgumentException("Cannot reflectively create enum objects"). Note that with Java modules and a security manager, access can also be restricted.

Serialization. If the singleton implements Serializable, each deserialization builds a new object. Fix: add readResolve() that returns the real instance, and mark fields transient or avoid serializing. Enums handle this automatically.

public final class Session implements java.io.Serializable {
    private static final Session INSTANCE = new Session();
    private Session() { }
    public static Session getInstance() { return INSTANCE; }

    private Object readResolve() {              // called after deserialization
        return INSTANCE;                        // discard the new copy
    }
}

Cloning. If the class (or a parent) implements Cloneable, clone() makes a second copy. Fix: do not implement Cloneable, or override clone() to throw CloneNotSupportedException or return the instance.

Multiple class loaders. A singleton is one per class loader, not per JVM. In application servers, two web apps (or a hot-reload tool) can each load their own copy. And in a cluster, every JVM has its own singleton, so it cannot guard a database-wide or cluster-wide resource.

Spring's singleton scope versus the GoF Singleton

By default, a Spring bean has singleton scope: the container creates one instance of the bean per container (per bean definition) and returns it every time. It sounds like Singleton, but the mechanism is different:

QuestionGoF SingletonSpring singleton bean
Who enforces "one"?The class itself (private constructor)The container
Scope of "one"Per class loaderPer container and bean definition (you can define two beans of one class)
Can you call new?NoYes (plain Java classes; Spring just does not)
How do users get it?getInstance() (global access)Dependency injection
TestingHard to replaceEasy: inject a fake
 
@Service                                  // singleton scope by default
class PricingService {
    private final TaxPolicy taxPolicy;
    PricingService(TaxPolicy taxPolicy) { this.taxPolicy = taxPolicy; }
}

@Service
@Scope("prototype")                       // a new instance every time it is requested
class ShoppingCart { }

Because a singleton bean is shared by all request threads, it must be stateless or thread-safe. Do not keep per-user data in fields of a @Service. This is the most common bug caused by the singleton scope. Prefer Spring beans over hand-written GoF singletons in application code. More on scopes: Spring fundamentals.

Singletons in the JDK

  • Runtime.getRuntime() returns the one runtime of the JVM.
  • Collections.emptyList() returns one shared immutable instance, and every enum constant is a singleton by definition.

Pros

  • One shared instance for a truly unique resource.
  • Lazy creation saves memory when the object is costly.
  • Controlled access to the instance.

Cons

  • It is global state: any code can touch it, which hides dependencies.
  • Hard to unit-test and to replace with a fake.
  • Violates SRP (it controls its own lifecycle and does its job).
  • Needs care with threads, serialization, reflection and class loaders.

When NOT to use a Singleton

  • When you only need "one in practice". Let the DI container manage one instance and inject it. That gives you the single instance without the global access.
  • For objects that carry per-user or per-request state.
  • When tests need to reset or replace the object. Static state leaks between tests.
  • In a cluster, when you need "one across all servers". You need a distributed lock or a database, not a singleton.

Common mistakes

  • Double-checked locking without volatile.
  • A lazy "check then create" without any synchronisation.
  • A singleton that is mutable and shared (a mutable HashMap field), updated from many threads.
  • A Spring @Component that also has a getInstance() method. Pick one mechanism.

Interview: Singleton

  • How do you write a thread-safe Singleton? Name three ways: holder idiom, enum, DCL with volatile. Say you prefer the holder or the enum.
  • Why volatile in double-checked locking? It stops the reordering of "assign reference" before "run constructor", so no thread sees a half-built object.
  • How can a singleton be broken? Reflection, serialization, cloning, multiple class loaders. Fixes: throw in the constructor, readResolve, do not implement Cloneable, or use an enum.
  • Spring singleton vs GoF Singleton? One per container and bean definition, enforced by the container, injected; GoF is one per class loader, enforced by the class itself.
  • Why is Singleton called an anti-pattern? Hidden global state and poor testability.

The Factory family: static factory, Simple Factory, Factory Method and Abstract Factory

Factories move object creation out of the code that uses the object, so callers depend on an interface and not on a concrete class; the family has four members that differ in how much they let you vary: static factory methods, Simple Factory, Factory Method and Abstract Factory.

Intent: create objects without exposing the creation logic, so that the caller works with an abstraction.

The problem

A notification feature starts simple. The code that sends a message also decides which class to build:

public void notifyUser(String channel, String to, String text) {
    Notifier notifier;
    if (channel.equals("EMAIL")) {
        notifier = new EmailNotifier(smtpHost);
    } else if (channel.equals("SMS")) {
        notifier = new SmsNotifier(apiKey);
    } else if (channel.equals("PUSH")) {
        notifier = new PushNotifier(fcmToken);
    } else {
        throw new IllegalArgumentException(channel);
    }
    notifier.send(to, text);
}

Every caller that needs a notifier repeats this if chain. Adding WhatsApp edits many methods. The calling code knows concrete classes and their constructor arguments. Moving the creation into one place fixes it.

Level 0: static factory methods

A static factory method is a static method that returns an instance. It is not a GoF pattern, but it is the most used form in Java (Effective Java, Item 1). Advantages over constructors: it has a name (Money.ofRupees(5)), it need not create a new object each call (caching, as in Integer.valueOf), it can return a subtype, and it can hide the implementation class (List.of returns a private JDK class).

Level 1: Simple Factory

A Simple Factory is one class (often with a static method) that holds the if/switch and returns the right product. It is not a GoF pattern, but it is the first step and enough for many programs.

public interface Notifier {
    void send(String to, String text);
}

class EmailNotifier implements Notifier {
    public void send(String to, String text) { System.out.println("EMAIL " + to + ": " + text); }
}
class SmsNotifier implements Notifier {
    public void send(String to, String text) { System.out.println("SMS " + to + ": " + text); }
}
class PushNotifier implements Notifier {
    public void send(String to, String text) { System.out.println("PUSH " + to + ": " + text); }
}

enum Channel { EMAIL, SMS, PUSH }

public final class NotifierFactory {
    private NotifierFactory() { }

    public static Notifier create(Channel channel) {
        return switch (channel) {                       // exhaustive for an enum
            case EMAIL -> new EmailNotifier();
            case SMS   -> new SmsNotifier();
            case PUSH  -> new PushNotifier();
        };
    }
}

// caller depends on Notifier and Channel only
NotifierFactory.create(Channel.SMS).send("98100", "OTP 4521");
SMS 98100: OTP 4521

The factory itself still has a switch, so adding a channel edits the factory (an OCP violation, but only in one place). To avoid it, register creators in a map or let Spring collect the implementations (see Spring below).

Level 2: Factory Method (GoF)

Factory Method: a base class defines an algorithm and declares an abstract method that creates the product; subclasses decide which concrete product to create. The creator uses the product only through the interface.

import java.util.List;

interface Exporter {
    String export(List<String> rows);
}
class CsvExporter implements Exporter {
    public String export(List<String> rows) { return String.join("\n", rows); }
}
class JsonExporter implements Exporter {
    public String export(List<String> rows) {
        return rows.stream().map(r -> "\"" + r + "\"")
                   .collect(java.util.stream.Collectors.joining(",", "[", "]"));
    }
}

abstract class ReportJob {
    public final void run(List<String> rows) {
        Exporter exporter = createExporter();               // the factory method
        System.out.println(exporter.export(rows));
    }
    protected abstract Exporter createExporter();          // subclasses decide
}

class CsvReportJob extends ReportJob {
    protected Exporter createExporter() { return new CsvExporter(); }
}
class JsonReportJob extends ReportJob {
    protected Exporter createExporter() { return new JsonExporter(); }
}

public class FactoryMethodDemo {
    public static void main(String[] args) {
        new CsvReportJob().run(List.of("a", "b"));
        new JsonReportJob().run(List.of("a", "b"));
    }
}
a
b
["a","b"]

Factory Method is the Template Method pattern (Template Method) applied to creation. Use it when a class cannot know in advance which objects it must create, and subclasses (or a framework user) should decide.

Level 3: Abstract Factory (GoF)

Abstract Factory creates a family of related products that must be used together, without naming their concrete classes. Think of a checkout that needs a tax calculator and an invoice formatter that match the country: Indian GST with a GSTIN invoice, or US sales tax with a different invoice. Mixing an Indian calculator with a US formatter would be a bug; the factory makes sure the family stays consistent.

interface TaxCalculator { long taxOn(long amountInPaise); }
interface InvoiceFormatter { String format(long totalInPaise); }

interface RegionFactory {                       // the abstract factory
    TaxCalculator taxCalculator();
    InvoiceFormatter invoiceFormatter();
}

class IndiaFactory implements RegionFactory {
    public TaxCalculator taxCalculator() { return amount -> amount * 18 / 100; }   // GST
    public InvoiceFormatter invoiceFormatter() {
        return total -> "Tax Invoice: Rs " + total / 100.0;
    }
}
class UsFactory implements RegionFactory {
    public TaxCalculator taxCalculator() { return amount -> amount * 7 / 100; }    // sales tax
    public InvoiceFormatter invoiceFormatter() {
        return total -> "Invoice: $" + total / 100.0;
    }
}

class Checkout {
    private final RegionFactory region;
    Checkout(RegionFactory region) { this.region = region; }

    String bill(long amount) {
        long total = amount + region.taxCalculator().taxOn(amount);
        return region.invoiceFormatter().format(total);
    }
}

// new Checkout(new IndiaFactory()).bill(100000)  -> "Tax Invoice: Rs 1180.0"
// new Checkout(new UsFactory()).bill(100000)     -> "Invoice: $1070.0"

Both interfaces here have one method, so lambdas implement them. Adding a new region is a new factory class; adding a new product (say, a ShippingRule) means changing the factory interface and all factories, which is the main weakness.

In the JDK and Spring

  • Static factory methods: Integer.valueOf, List.of, LocalDate.of, Optional.of, Executors.newFixedThreadPool.
  • Factory Method: Collection.iterator() (each collection returns its own iterator type) and Iterable.iterator().
  • Abstract Factory: javax.xml.parsers.DocumentBuilderFactory, java.sql.Connection (creates Statements that match the driver).
  • Spring: the BeanFactory/ApplicationContext is a giant factory; a FactoryBean<T> lets a bean produce another object; @Bean methods are factory methods. Injecting Map<String, Notifier> or List<Notifier> replaces a hand-written factory switch:
@Component("EMAIL") class EmailNotifier implements Notifier { /* ... */ }
@Component("SMS")   class SmsNotifier   implements Notifier { /* ... */ }

@Service
class NotificationService {
    private final Map<String, Notifier> notifiers;      // key = bean name

    NotificationService(Map<String, Notifier> notifiers) { this.notifiers = notifiers; }

    void send(String channel, String to, String text) {
        Notifier n = notifiers.get(channel);
        if (n == null) throw new IllegalArgumentException("Unknown channel " + channel);
        n.send(to, text);                                   // new channel = new @Component
    }
}

Pros

  • Callers depend on interfaces, not on concrete classes (DIP).
  • Creation logic lives in one place; construction details can change freely.
  • New products are added with little or no change to callers (OCP).
  • Abstract Factory keeps related products consistent.

Cons

  • More classes and indirection.
  • Factory Method needs a subclass per product.
  • Abstract Factory is hard to extend with a new product kind.

When NOT to use a factory

  • When there is only one implementation and no plan for another: just call the constructor.
  • When a DI container already chooses the implementation. Do not write a factory for what @Bean, profiles or @ConditionalOnProperty can do.
  • Do not build an Abstract Factory unless products truly must match as a family.

Interview: factories

  • Factory Method vs Abstract Factory? Factory Method: one product, subclass decides, uses inheritance. Abstract Factory: a family of products, object composition. Abstract Factory is often implemented with several factory methods.
  • Why prefer a static factory to a constructor? Names, caching, subtype return, hiding the class (Effective Java Item 1).
  • How would you remove the switch from a factory in Spring? Inject a Map<String, Interface>.

High-level design (HLD) is the view from far above the code. In the earlier modules you designed classes and objects (low-level design). Here you design a whole system: which services exist, where the data lives, how requests travel, and what happens when a machine, a network link or a whole data centre fails. This module gives you the vocabulary and the arithmetic that every later design is built from.

You already build Spring Boot services. HLD asks the next question: what if one million people call your service at the same time, and one of the three servers behind it dies in the middle? The answers use a small set of ideas: estimate the load, scale out, stay available, and choose how consistent your data must be. Module 5 then gives you the building blocks (load balancers, caches, queues, shards) that put these ideas into practice.

  • Walk through one request from the browser to the database and back, naming every hop.
  • Choose between REST, gRPC, WebSockets, SSE, long polling and webhooks for a given feature.
  • Explain latency, throughput and percentiles, and say why an average hides the pain.
  • Do a back-of-the-envelope estimate of requests per second, storage and bandwidth.
  • Explain stateless services and where session state goes when you scale out.
  • Calculate availability for components in series and in parallel, and read a nines table.
  • Explain CAP with a partition scenario, PACELC, quorums and consistency models, and pick the right consistency for each feature.

What system design interviews test, and the path of one request

A system design interview tests whether you can turn vague requirements into a sensible architecture, justify trade-offs with numbers, and follow one request through every layer: client, DNS, CDN, load balancer, app servers, cache, database, queue and workers.

What the interviewer is really checking

There is no single correct answer. The interviewer watches how you think. A good candidate clarifies the problem first, states assumptions, sketches a simple design, estimates the load, and then improves the design where the numbers say it will hurt. Weak candidates jump to "Kafka and microservices" in the first minute without knowing how many users there are.

The signals they look for are the same in nearly every interview:

  • Requirements: you separate functional requirements (what the system does: "shorten a URL", "post a photo") from non-functional requirements (how well it does it: latency, availability, consistency, durability, scale).
  • Estimation: you size the problem before choosing tools.
  • Trade-offs: every choice costs something. You say what you gain and what you pay. "I use a cache here; the price is stale data for up to 60 seconds, which is fine for a product page."
  • Depth on demand: when asked "how does that work inside?", you can go one level down (how replication works, what a partition key is).
  • Failure thinking: you ask "what if this node dies?" before the interviewer does.

A repeatable framework for any design question

  1. Clarify the scope and the users. Ask: who uses it, how many, read-heavy or write-heavy, which features are in scope.
  2. List requirements: functional first, then non-functional with numbers (for example "99.9% available, p99 read latency under 200 ms").
  3. Estimate requests per second, storage and bandwidth (the estimation article).
  4. Draw the API and the data model (a few endpoints, a few tables).
  5. Draw the high-level design: client, load balancer, services, database.
  6. Deep dive into one or two hard parts (the hot path, the bottleneck).
  7. Handle failures and scale: replication, caching, sharding, monitoring.

The path of one request

Take a user opening a shopping page on Flipkart-style site. Here is the journey a typical large web system makes. Not every system has every box, and a small one has only a few of them. The skill is knowing when each box earns its place.

  1. Client. The browser or mobile app builds an HTTPS request. It may first check its own cache (the browser cache) and skip the network.
  2. DNS. The client turns shop.example.com into an IP address. The answer is often cached and may point to the nearest region (DNS).
  3. CDN. Static files (images, JavaScript, CSS) come from an edge server near the user. A hit ends the journey here (CDN).
  4. Load balancer. Dynamic requests (API calls) arrive at one public address. The load balancer picks a healthy app server and often terminates TLS (Load balancers).
  5. App server. Your Spring Boot instance authenticates the request and runs the business logic. It should hold no user state, so any instance can serve any request.
  6. Cache. Before touching the database, the app asks Redis. A hit returns in about a millisecond (Caching).
  7. Database. On a miss, the app queries the database, usually a read replica for reads and the primary for writes (Replication).
  8. Queue and workers. Slow or non-urgent work (send email, resize image, update the search index) is put on a queue and the response returns at once. Workers consume the queue later (Queues).

Tip: start with the simplest design that meets the numbers

Begin with one app server and one database on the whiteboard. Add a box only when a number or a failure case demands it: "At 5,000 reads per second one database will struggle, so I add a cache." This shows judgement, not buzzwords.

Interview angle: what to say in the first five minutes

  • "Let me clarify scope and non-functional requirements before I draw anything."
  • "Let me estimate the scale so I know which parts need to be distributed."
  • "I will start simple and then evolve the design where the numbers hurt."
  • Always state assumptions aloud; the interviewer can correct them cheaply.

Common mistake: designing for Google scale on day one

A system with 10,000 users does not need sharding, Kafka and five microservices. Over-engineering costs money and makes failures harder to find. Say what the design looks like now and how it grows at 10x and 100x. That is exactly what a senior engineer does at work.

Words you will hear in every design talk

Scalability
The ability to handle more load by adding resources, without a redesign.
Availability
The fraction of time the system answers correctly (see Availability).
Consistency
Whether all readers see the same, latest data (see CAP).
Durability
Once the system says "saved", the data survives crashes.
Bottleneck
The one part that limits the whole system's speed. Find it, fix it, find the next one.

Client–server and communication styles: REST, gRPC, WebSockets and more

Use REST over HTTP+JSON as the default for public APIs, gRPC for fast internal service-to-service calls, WebSockets for two-way real-time traffic, SSE for server-to-browser streams, long polling as a fallback, and webhooks to let another system call you when something happens.

Client–server in one paragraph

In the client–server model a client starts a conversation and a server answers. The browser asks, your Spring Boot app replies. The client opens a connection (TCP, usually with TLS on top), sends a request, and waits for a response. HTTP is the request–response protocol of the web. Every style below is a different way to use this connection. The key questions are: who starts the message, how long the connection stays open, and how the data is encoded (text like JSON, or binary like Protocol Buffers).

REST over HTTP and JSON

REST models your system as resources (/orders/42) and uses HTTP verbs (GET, POST, PUT, PATCH, DELETE) and status codes. Bodies are usually JSON. It is stateless: each request carries everything the server needs.

  • Strengths: universal (every language, browser and tool understands it), easy to debug with curl, easy to cache (GET responses, CDN, ETag), mature tooling (Spring MVC, OpenAPI).
  • Costs: JSON is text, so payloads are larger and parsing is slower than binary. You may need several round trips to build one screen (over-fetching or under-fetching). There is no built-in streaming or schema enforcement.
  • Use it for: public APIs, browser-to-backend calls, CRUD-style services.

For the design details of REST (status codes, idempotency, versioning, pagination), see Spring Boot · Module 2.

gRPC

gRPC is a remote procedure call framework from Google. You describe your service in a .proto file; tools generate client and server code in many languages. Messages are encoded with Protocol Buffers (a compact binary format), and calls travel over HTTP/2, which multiplexes many calls on one connection.

syntax = "proto3";

service OrderService {
  rpc GetOrder (OrderRequest) returns (OrderReply);            // unary
  rpc WatchOrders (OrderRequest) returns (stream OrderReply);  // server streaming
  rpc Upload (stream Chunk) returns (UploadSummary);           // client streaming
  rpc Chat (stream Msg) returns (stream Msg);                  // bidirectional
}

message OrderRequest { int64 id = 1; }
message OrderReply   { int64 id = 1; string status = 2; }
  • Strengths: small and fast messages, strict typed contract, generated code, four call types including streaming, deadlines and cancellation built in.
  • Costs: not human-readable on the wire, browsers cannot call it directly (they need gRPC-Web and a proxy), harder to debug, and load balancers must understand HTTP/2.
  • Use it for: internal service-to-service calls in a microservice system where latency and bandwidth matter.

WebSockets

A WebSocket starts as an HTTP request that is "upgraded" to a long-lived, full-duplex TCP connection: either side can send a message at any time without a new request. Messages are small frames with very little overhead.

  • Strengths: real-time two-way traffic with low latency: chat, multiplayer games, live collaboration, trading screens.
  • Costs: the server must hold one open connection per user. That is memory and file descriptors, so a node serves tens of thousands, not millions. The connection is stateful, which makes load balancing, deploys and reconnects harder. You must write your own heartbeat, reconnect and message-ordering logic. Proxies and firewalls sometimes interfere.
  • Use it for: chat, live notifications with replies, collaborative editing.

Server-Sent Events, long polling and short polling

  • Short polling: the client asks "anything new?" every few seconds. Simple, but wasteful: most answers are empty, and updates are delayed up to one interval.
  • Long polling: the client asks, and the server holds the request open until it has data (or a timeout), then replies; the client immediately asks again. Works everywhere over plain HTTP, with less waste than short polling, but each message costs a full request cycle.
  • Server-Sent Events (SSE): one HTTP response that stays open and the server pushes text events through it. One direction only (server to client), built-in auto-reconnect in browsers, plain HTTP. Ideal for live scores, progress bars and notifications.

GraphQL (brief) and webhooks

GraphQL exposes a single endpoint where the client sends a query that names exactly the fields it wants. This removes over-fetching and lets a mobile screen get everything in one round trip. The costs: caching is harder (every query is a POST with a different body), a naive resolver design causes the N+1 query problem, and expensive queries must be limited. It fits client-driven apps with many different screens.

A webhook reverses the direction: you give another system a URL, and it sends an HTTP POST to you when something happens (Razorpay telling you a payment succeeded, GitHub telling you about a push). You avoid polling, but you must handle retries, duplicates (make the handler idempotent), verify a signature so nobody can fake events, and respond fast (accept, then process asynchronously).

Rule: every network call can fail, so set timeouts and make writes idempotent

A call may time out after the server already did the work. The client then retries and the work runs twice. Give writes an idempotency key (for example a payment request id) so the retry is safe. Never call another service without a timeout.

Real projects usually mix styles

A typical product uses REST between the mobile app and the API gateway, gRPC or REST between internal services, a WebSocket or SSE channel for live notifications, Kafka for events between services, and webhooks from the payment provider. You pick per interaction, not once for the whole system.

Interview angle

  • "Chat needs both sides to push, so I use WebSockets. Notifications are one-way, so SSE is lighter. For service-to-service I use gRPC for speed, and REST at the edge for compatibility."
  • Mention the cost of WebSockets: sticky connections and one socket per user, so the gateway layer for sockets is scaled and deployed separately.
  • Say that you pick the simplest style that meets the latency need; polling every 30 seconds is fine for a dashboard.

Latency, throughput and percentiles

Latency is how long one request takes, throughput is how many requests finish per second; measure latency with percentiles (p50, p95, p99), not averages, and remember the rough cost of memory, disk and network operations.

Two different questions

Latency is the time for one request, from sending to getting the answer, in milliseconds. Throughput is how much work the system finishes per unit of time: requests per second (RPS or QPS), messages per second, or megabytes per second.

Analogy: a motorway. Latency is how long one car takes from Mumbai to Pune. Throughput is how many cars reach Pune per hour. Adding lanes raises throughput but does not make any single car faster. A faster speed limit lowers latency. The two are linked but not the same: a system can have high throughput and poor latency (a batch job that handles millions of rows but each takes minutes), or low latency and low throughput (a fast server that handles only one request at a time).

Why averages lie: percentiles

Suppose 99 requests take 100 ms and one takes 10 seconds. The average is about 199 ms and looks healthy, but one in every hundred users waited ten seconds. Latency has a long tail, so we use percentiles:

  • p50 (median): half of the requests are faster than this. The "typical" user.
  • p95: 95% are faster; 1 in 20 is slower.
  • p99: 1 in 100 is slower. Heavy users see it often.
  • p99.9: the extreme tail, often GC pauses, cold caches or retries.

The tail matters more than it looks. A page that makes 20 backend calls is slow if any call is slow. If each call has a 1% chance of being slow, the page is slow with probability 1 − 0.9920 ≈ 18%. This is called tail latency amplification. That is why SLOs are written as "p99 under 300 ms", never "average under 100 ms".

Little's law

Little's law links three numbers in any stable system:

L = λ × W

L = average number of requests inside the system at once
λ = arrival rate (requests per second)
W = average time each request spends in the system (seconds)

Example: your service gets 2,000 requests per second and each takes 50 ms (0.05 s). Then L = 2,000 × 0.05 = 100 requests in flight at once. If a Tomcat instance has 200 worker threads, one instance handles it with room to spare. If a database call slows down to 500 ms, L becomes 1,000, the threads run out, requests queue, and latency climbs further. This is how a slow dependency takes down a healthy service. It also shows how to size connection pools and thread pools: concurrency needed = rate × time.

What happens near saturation

A server at 50% load answers quickly. As utilisation approaches 100%, queues build and latency rises sharply, not smoothly. Plan to run services at 60–70% of peak capacity, keep the rest as headroom for spikes and failures, and use load shedding (reject some requests early with 503 or 429) rather than letting every request time out.

Common mistake: reporting the average and the maximum only

The average hides the tail; the maximum is one unlucky request. Report p50, p95 and p99, and measure at the client or load balancer so queueing time is included. Also avoid averaging percentiles across servers; merge the raw histograms instead.

Tip: ways to cut latency, in the order you try them

  1. Do less: remove unneeded calls and use indexes.
  2. Do it nearby: CDN for static content, regional deployments, a cache close to the app.
  3. Do it in parallel: call independent services at the same time, not one after the other.
  4. Do it later: return now and finish slow work through a queue.

Interview angle

  • "I would track p99 latency, because averages hide the slow tail that real users feel."
  • Quote ratios, not exact figures: memory is about 1,000x faster than SSD, and a cross-region call is about 1,000x slower than a local memory read.
  • Use Little's law to justify thread-pool or connection-pool sizes.

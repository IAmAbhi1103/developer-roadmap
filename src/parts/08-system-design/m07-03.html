Design a notification system (push, SMS, email, in-app)

A notification system accepts "tell user X about Y" requests from many services and delivers them over several channels; the design is a validation layer, per-channel queues with priorities, workers that call external providers with retries and rate limits, and idempotency so nobody gets the same message twice.

1. Requirements

Functional:

  • Other services (orders, payments, marketing) send notifications through an API or by publishing events.
  • Channels: mobile push (FCM for Android, APNs for iOS), SMS, email and in-app (a bell icon list).
  • Templates with variables ("Your order {{orderId}} is out for delivery").
  • User preferences: opt in or out per channel and per category; quiet hours (do not disturb).
  • Scheduled and bulk (campaign) notifications.
  • Delivery status tracking (queued, sent, delivered, failed, opened) where the provider reports it.

Non-functional: high availability and no loss for important messages (OTP, payment alerts); at-least-once delivery with deduplication so users are not spammed; priority (an OTP must not wait behind a marketing blast); soft real-time (OTP within seconds, marketing within minutes); scalable for burst traffic; respect provider rate limits. Out of scope: building the SMS carrier network, the content of marketing campaigns.

2. Capacity estimates (assumptions)

  • 10 million users, on average 5 notifications per user per day → 50 million per day → 50,000,000 ÷ 86,400 ≈ 580 per second on average.
  • Burst: a marketing campaign pushes to all 10 million users within 10 minutes (600 seconds) → 10,000,000 ÷ 600 ≈ 16,700 per second. The system must be sized for this, not for the average.
  • Channel mix (assumed): 70% push, 20% email, 5% SMS, 5% in-app only. SMS is 2.5 million per day and costs real money per message, so SMS is the channel to protect with limits.
  • Storage: a log row of about 300 bytes per notification → 50M × 300 B = 15 GB per day. Keep 90 days for support: 90 × 15 GB = 1.35 TB. Older data goes to cheap storage or is deleted.
  • Queue sizing: at the 16,700/s burst with 1 KB messages, throughput is about 17 MB/s, which one small Kafka cluster handles. Workers: if one worker can make 200 provider calls per second, the burst needs about 85 workers, which autoscaling can add.

3. API design

POST /api/v1/notifications
Idempotency-Key: 5d1c0d6e-...
{"userId": 9912,
 "type": "ORDER_SHIPPED",              // maps to a template + category
 "channels": ["PUSH", "EMAIL"],        // optional: otherwise from preferences
 "priority": "HIGH",
 "data": {"orderId": "OD-7731", "eta": "Tomorrow"},
 "sendAt": "2026-11-12T09:00:00+05:30"}   // optional

202 Accepted
{"notificationId": "n_01JC3...", "status": "QUEUED"}

GET  /api/v1/users/9912/notifications?cursor=...&limit=20   (in-app list)
POST /api/v1/notifications/n_01JC3.../read
PUT  /api/v1/users/9912/preferences
     {"email": {"marketing": false}, "quietHours": {"from": "22:00", "to": "07:00"}}

The API answers 202 Accepted because delivery is asynchronous. The caller needs the idempotency key so a retried request does not create a second notification (Idempotency).

4. Data model

CREATE TABLE notification (
    id            VARCHAR(30) PRIMARY KEY,
    user_id       BIGINT       NOT NULL,
    type          VARCHAR(40)  NOT NULL,
    channel       VARCHAR(10)  NOT NULL,        -- PUSH, SMS, EMAIL, INAPP
    status        VARCHAR(12)  NOT NULL,        -- QUEUED, SENT, DELIVERED, FAILED
    payload       JSONB        NOT NULL,
    attempts      INT          NOT NULL DEFAULT 0,
    created_at    TIMESTAMP    NOT NULL,
    updated_at    TIMESTAMP    NOT NULL
);
CREATE INDEX idx_notif_user ON notification (user_id, created_at DESC);

CREATE TABLE user_preference (
    user_id BIGINT, channel VARCHAR(10), category VARCHAR(20), enabled BOOLEAN,
    PRIMARY KEY (user_id, channel, category)
);
CREATE TABLE device_token (
    user_id BIGINT, token VARCHAR(300), platform VARCHAR(10), updated_at TIMESTAMP,
    PRIMARY KEY (user_id, token)
);

Preferences, templates and device tokens are small, relational and read-heavy: PostgreSQL or MySQL with a Redis cache in front. The notification log is write-heavy and time-ordered, queried by user and time: a wide-column store (Cassandra) or a partitioned SQL table works. Use SQL first and say when you would move.

5. High-level architecture

Why one queue per channel? Each provider has different speed, cost, failure modes and rate limits. If the email provider is slow, the backlog must not delay push or SMS. This is the bulkhead idea from Resilience. Within a channel, use separate queues (or topics) per priority: OTP and payment alerts on a high-priority queue with dedicated workers, marketing on a low-priority queue that may take hours.

Steps inside the validation stage: authenticate the caller → check the idempotency key → load the user's preferences and quiet hours → pick channels → render the template (language, variables) → write a row as QUEUED → publish to the channel queue. Use the outbox pattern (Outbox) so the row and the queue message cannot disagree.

6. Deep dive A: reliable delivery, retries and duplicates

  • At-least-once. A worker takes a message, calls the provider, and acks the queue only after the call succeeds. If it crashes before acking, the message is redelivered. So duplicates are possible (Delivery semantics).
  • Deduplication. Each notification has an id. Before sending, the worker sets SET sent:<id>:<channel> 1 NX EX 86400 in Redis (or a conditional update in the DB, status QUEUED → SENT). If it already exists, skip. Pass the same id as the provider's idempotency or collapse key when they support one (FCM has a collapse key so repeated messages replace each other). The remaining window (crash after the provider accepted but before recording) gives a rare duplicate; accept it and say so.
  • Retries. Transient provider errors (timeouts, 5xx, 429) are retried with exponential backoff and jitter (Retries), using delayed retry queues (retry after 10 s, 1 min, 10 min) instead of sleeping in the worker. After N attempts, move to a dead-letter queue and mark FAILED. Permanent errors (invalid or unregistered device token, unsubscribed number) are never retried; delete the bad token.
  • Failover between providers. Keep two SMS or email providers; a circuit breaker switches to the second when the first fails.
  • Ordering is not guaranteed and rarely needed across notifications; for status updates on one order, include a version or timestamp so a late "packed" does not overwrite "shipped".

7. Deep dive B: priority, rate limits and bursts

  • Priority: separate queues and consumer groups. Do not use one queue with a priority field on Kafka; consumers read in offset order. RabbitMQ and SQS-style systems have their own priority options, but separate queues are simpler and predictable.
  • Provider limits: providers throttle you. A token-bucket limiter per provider and per sender (Rate limiter) in the workers keeps you under the limit; when the bucket is empty, leave the message in the queue.
  • Per-user limits: cap marketing to, say, 3 per day per user, and collapse bursts ("5 people liked your post" instead of 5 pushes). This protects users from spam, which is also a non-functional requirement.
  • Bulk campaigns: a campaign job reads the audience in pages, creates notifications in batches and feeds the low-priority queue at a controlled rate, never all 10 million at once. Spread sends over time zones.
  • Scheduling: store sendAt and let a scheduler (a DB poller with an index, or delayed messages) enqueue when due. Respect quiet hours by shifting non-urgent messages to the next allowed time.

8. Deep dive C: channel details and tracking

  • Push: the app registers a device token with the backend; the worker sends the token and payload to FCM or APNs. Tokens expire or change; handle "unregistered" replies by deleting the token. Push is best-effort: if the phone is offline, the provider holds the message for a limited time.
  • SMS: costly and regulated (in India, sender id and template registration rules apply for transactional and promotional SMS). Use for OTP and critical alerts; prefer push or email for marketing. Watch for fraud: an attacker triggers OTP SMS to premium numbers (pumping), so rate limit OTP per number and per IP.
  • Email: use a provider (SES, SendGrid and similar); handle bounces and spam complaints via webhooks and stop mailing bad addresses; include an unsubscribe link; set up SPF, DKIM and DMARC so mail is not marked as spam.
  • In-app: write to the notification table and push over the user's open WebSocket if any (see Chat); the bell icon reads the list with cursor pagination and an unread count kept in Redis.
  • Tracking: providers send delivery and open events through webhooks. A callback service updates the status. Treat webhooks as at-least-once too: updates must be idempotent and monotonic (SENT → DELIVERED → OPENED, never backwards).

9. Bottlenecks, scaling and monitoring

  • Scale workers per queue by queue depth (autoscaling on lag). The database write of status rows can become the bottleneck; batch updates and partition by time.
  • Cache preferences and templates in Redis with short TTLs; invalidate on change.
  • Queue brokers are replicated across zones; the API is stateless.
  • Metrics: queue lag per channel, send success rate, provider latency, DLQ size, delivered-to-sent ratio, cost per channel. Alert on lag for high-priority queues and on a sudden drop in the success rate.
  • Security: validate the caller's identity and allowed types so one service cannot message all users; never put secrets or full card numbers in payloads; mask OTPs in logs.

Follow-up questions

  • How do you guarantee an OTP is delivered within 10 seconds? (Dedicated high-priority queue and workers, multiple SMS providers with failover, alert on latency.)
  • What if a user has 3 devices? (One token row per device; send to all active ones, or only the most recent.)
  • How do you support user timezones and localisation? (Store locale and zone; render templates per locale.)
  • How would you avoid sending a "your order was delivered" push twice after a retry? (Idempotency key plus dedupe set, monotonic status.)
  • How do you test without messaging real users? (A sandbox provider and a dry-run mode.)

Interview angle

  • Say early: "async, one queue per channel and priority, at-least-once with dedupe".
  • Size for the campaign burst (16,700 per second), not the average (580).
  • Show you know channel details: device tokens, SMS cost and abuse, email bounces.

Design a chat app (like WhatsApp)

A chat app keeps a WebSocket open from each online user to a gateway, routes each message to the recipient's gateway through a session registry, stores messages durably so offline users catch up when they return, and tracks sent, delivered and read states with acknowledgements.

1. Requirements

Functional:

  • One-to-one chat and small group chat (up to a few hundred members).
  • Send and receive text messages in real time; media as links to files (images, video, documents).
  • Message states: sent, delivered, read (the ticks).
  • Online / last-seen status.
  • Messages sent to offline users are delivered when they reconnect, and as push notifications.
  • Chat history synced on a new device (within limits).

Non-functional: low latency (well under a second when both are online), no message loss (durability), per-conversation ordering, high availability, millions of concurrent connections, and security (TLS everywhere; end-to-end encryption is a deep topic, mention it). Out of scope: voice and video calls, stories, payments inside chat.

2. Capacity estimates (assumptions)

  • 50 million daily active users, 40 messages sent per user per day → 2 billion messages per day → 2,000,000,000 ÷ 86,400 ≈ 23,000 per second on average; peak 3× ≈ 70,000 per second.
  • Message size ~100 bytes of text plus ~100 bytes of metadata = 200 B. Per day: 2 × 109 × 200 B = 400 GB; per year ≈ 146 TB; with 3× replication ≈ 440 TB. Media (images, videos) is far bigger and goes to object storage and a CDN, not to the message store.
  • Concurrent connections: if 40% of daily users are online at once → 20 million WebSocket connections. A tuned gateway server can hold on the order of 100,000 idle connections (approximate; depends on memory and kernel tuning) → 20,000,000 ÷ 100,000 = 200 gateway servers, plus headroom.
  • Presence heartbeats: every 30 seconds per connection → 20M ÷ 30 ≈ 670,000 tiny messages per second, handled inside the gateways in memory; only status changes go to shared storage.
  • Bandwidth: 70,000 messages/s × 200 B = 14 MB/s of message payload. Small; connection count and fan-out dominate, not bytes.

3. API design

Chat uses a persistent WebSocket for real-time events, and normal REST for everything else (login, history, media upload). HTTP polling would waste requests, and long polling holds a request open and re-establishes it per message; WebSockets give a two-way channel with little overhead per message.

// client -> server
{"type": "send", "clientMsgId": "c-7f31", "chatId": "ch_88",
 "text": "Reached office", "ts": 1762853392000}

// server -> sender (ack: stored)
{"type": "ack", "clientMsgId": "c-7f31", "msgId": "m_5501772", "seq": 412}

// server -> recipient
{"type": "message", "msgId": "m_5501772", "chatId": "ch_88", "from": 9912,
 "seq": 412, "text": "Reached office", "ts": 1762853392100}

// recipient -> server
{"type": "delivered", "msgId": "m_5501772"}
{"type": "read", "chatId": "ch_88", "upToSeq": 412}
GET  /api/v1/chats/ch_88/messages?afterSeq=400&limit=50
POST /api/v1/media           (returns an upload URL; message then carries the media id)
GET  /api/v1/users/9912/presence

The clientMsgId is an idempotency key generated by the client: if the app resends after a lost ack, the server recognises the duplicate (Idempotency).

4. Data model

Access patterns: "append a message to a conversation" and "read the latest N messages of a conversation, or all after sequence S". Writes are huge and append-only, with reads by chat id in order. That fits a wide-column / partitioned store (Cassandra, HBase, DynamoDB) with the chat as the partition key and the sequence as the sort key. A single SQL database would need sharding by chat id early.

messages
  partition key : chat_id
  clustering key: seq (ascending)
  columns       : msg_id, sender_id, text, media_id, created_at

user_inbox  (for offline delivery)
  partition key : user_id
  clustering key: msg_id
  columns       : chat_id, seq

chats       : chat_id, type (DIRECT, GROUP), member_ids, created_at
users       : user_id, phone, name, avatar_url, last_seen
receipts    : (chat_id, user_id) -> last_delivered_seq, last_read_seq

Receipts use watermarks (the last sequence delivered or read per user per chat), not one row per message, which keeps group receipts cheap: "read up to 412" marks everything before it.

5. High-level architecture

Send flow:

  1. The sender's app sends the frame over its WebSocket to gateway 1.
  2. Gateway 1 forwards it to the message service, which assigns the next seq for that chat and writes the message to the store. Now it is durable.
  3. The message service replies with an ack (the first tick: "sent").
  4. It looks up each recipient in the session registry (user_id → gateway id, kept in Redis, with a TTL refreshed by heartbeats).
  5. If the recipient is online on gateway 2, the service forwards the message to gateway 2, which pushes it down the socket. The recipient app sends delivered (second tick).
  6. If the recipient is offline, the message stays in their inbox and a push notification is sent through FCM or APNs. On reconnect, the app asks for everything after its last seq.

6. Deep dive A: gateways, routing and scale of connections

  • Stateful connections. A WebSocket is tied to one gateway, so load balancing happens only at connect time (L4 load balancer or a connection router). After that, messages for a user must be sent to their gateway. The session registry gives that mapping. Alternative: publish to a pub/sub channel per user or per gateway and let gateways subscribe (Redis pub/sub, Kafka); simpler but chattier.
  • Gateway failure. Clients reconnect automatically with exponential backoff and jitter (so 100,000 clients lost together do not reconnect at the same millisecond) and then sync from their last seq. No message is lost because messages are stored before being routed.
  • Deploys. Draining a gateway means asking clients to reconnect elsewhere gradually.
  • Group chat. The message service stores one copy under the chat id, then fans out to each member's gateway. For groups up to a few hundred this is cheap. Very large groups or channels need a different design (clients pull, or fan-out through a queue).

7. Deep dive B: ordering, IDs and delivery guarantees

  • Ordering. Global ordering is impossible and unnecessary; users only need order inside a conversation. The message service owns a per-chat counter: all writes for one chat are handled by the same shard or partition (shard key = chat id), so it can assign increasing seq numbers. Clients sort by seq, not by device clock time. Timestamps from phones are wrong too often.
  • IDs. msgId should be unique and time-sortable (Snowflake, see Unique IDs); seq gives dense ordering per chat for gap detection: if the client sees 410, 411, 413 it knows 412 is missing and requests it.
  • Delivery semantics. Client to server and server to client are both at-least-once, with dedupe by clientMsgId and msgId so the user sees each message exactly once (Delivery semantics). The client resends until it gets an ack.
  • Receipts. Delivered and read events travel the reverse path and update the watermark; the sender's app is told by the same routing. Batch read receipts ("read up to seq 412") to avoid sending one event per message. Users can disable read receipts for privacy.
  • Multiple devices. Each device is a separate connection and has its own last-synced seq; the inbox model delivers to all of them.

8. Deep dive C: presence and offline handling

  • Online status. The gateway marks a user online in Redis when the socket opens (SET presence:<id> online EX 60) and refreshes it on each heartbeat. If heartbeats stop (network drop), the key expires and the user becomes offline with last_seen = last heartbeat. This TTL approach copes with crashes where no "disconnect" event arrives (Heartbeats).
  • Who sees presence? Pushing every status change to every contact is a fan-out problem (a user with 500 contacts flickering online/offline). Fetch presence on demand when a chat is opened, and subscribe only for the chats currently on screen. Add a small delay before announcing "offline" so brief network blips do not flicker.
  • Offline users. Messages remain in the inbox until acked as delivered. Push notifications carry no or minimal content (privacy) and wake the app. Limit retention for undelivered messages (for example 30 days) to bound storage.
  • Media. The client uploads the file to object storage (pre-signed URL), gets a media id, and sends a normal message carrying that id and a thumbnail; receivers download via CDN (Module 5).
  • End-to-end encryption (brief): keys live on devices, the server stores and routes ciphertext it cannot read. This makes server-side search, spam filtering and multi-device sync harder, and needs a key exchange protocol (the Signal protocol is the best-known design). Mention it as a design choice with trade-offs.

9. Bottlenecks, scaling and failure

  • Gateways scale by adding servers; the limit is connections per machine. Message store scales by partitioning on chat id. Hot chats (huge groups) may need special handling.
  • Redis session registry: replicate it; if lost, gateways re-register connected users within a heartbeat or two. Rebuildable state is a good property.
  • Overload: rate limit senders to stop spam (Rate limiter), bound per-connection send buffers, drop slow consumers.
  • Monitoring: connected users, message latency end to end, undelivered backlog, reconnect rate, push failure rate.

Follow-up questions

  • How do you support "typing…" indicators? (Ephemeral events through the gateways only; never stored; throttled.)
  • How does search in chat history work? (Local on device for E2E; otherwise an index per user.)
  • How would you design channels with a million members? (Pull-based, fan-out on read, cached latest pages; see News feed.)
  • What if two devices send at the same moment? (Server assigns seq; both messages appear in seq order.)
  • How do you migrate off a failing gateway without dropping messages? (Store-then-route, client resync by seq.)

Interview angle

  • The central trick: store first, then route; then offline and reconnect come almost for free.
  • Do the connection maths: 20 million connections ÷ 100,000 per gateway = 200 servers.
  • Ordering is per conversation (a server-assigned seq), not global and not by phone clocks.

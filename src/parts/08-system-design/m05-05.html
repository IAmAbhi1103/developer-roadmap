SQL vs NoSQL and the NoSQL families

Choose SQL when you need relations, transactions and flexible queries (the default), and a NoSQL family when one access pattern or scale dominates: key-value for lookups and caches, document for flexible records, wide-column for massive writes, graph for relationships, plus time-series and search stores for special data.

What changes between the two

Relational (SQL) databases store rows in tables with a fixed schema, relate tables with keys, query them with SQL (joins, aggregates), and give ACID transactions. NoSQL ("not only SQL") is a family of databases that give up some of that (a fixed schema, joins, or multi-row transactions) in exchange for something else: easier horizontal scaling, flexible data shape, or speed for one access pattern. Do not choose by fashion; choose by access pattern, consistency need and scale. Fundamentals are in SQL · Module 6; this is the design view.

Convention: start with PostgreSQL

A well-run relational database handles far more than most products ever need, supports JSON columns for flexible fields, and keeps your options open. Add specialised stores when a measured need appears (cache, search, analytics), and keep the relational database as the source of truth. This is called polyglot persistence: each data type in the store that fits it.

How each one is used in a design

  • Key-value: Redis for the session store and cache; DynamoDB for a serverless primary store with single-digit-millisecond lookups at any scale when you know the key. Model the partition key with care.
  • Document: a product with different attributes per category (a phone has a screen size, a shirt has a fabric) fits a document better than a table with 80 nullable columns. Store data that is read together, together (embedding). Cost: duplicated data and no strong join story.
  • Wide-column: Cassandra models one table per query: for "latest 50 messages in chat X" use partition key chat_id and clustering key sent_at DESC. Writes are fast because they are append-style (LSM trees), and data spreads across a ring automatically (consistent hashing). You pay with limited query flexibility and eventual consistency.
  • Graph: "friends of friends who like X" is a few hops in a graph database but a painful self-join in SQL. Choose it when relationship traversal is the core feature.

Consistency, joins and the "NoSQL means no schema" myth

Many NoSQL systems favour availability and partition tolerance and offer tunable or eventual consistency (CAP), but this varies: MongoDB can be strongly consistent on a single primary, and DynamoDB offers strongly consistent reads when asked. "Schemaless" really means the schema lives in your application code, which then has to handle old and new document shapes. Joins are not available or are costly, so you denormalize and model data around the queries, not around the entities.

Common mistakes

  • Picking MongoDB because "it scales" when the data is relational and the load is small.
  • Using a document store for financial data that needs multi-row transactions.
  • Modelling a wide-column table like a SQL table and then needing ad-hoc queries.
  • Treating Elasticsearch or Redis as the only copy of important data.

Interview angle

  • "I choose by access pattern: orders and payments in PostgreSQL for transactions, sessions in Redis, product search in Elasticsearch, activity feed in Cassandra."
  • Do not say "NoSQL is faster" or "SQL does not scale"; say what each gives up.
  • For a chat or feed system, justify wide-column by write rate and the query pattern.

Message queues and streams: Kafka, RabbitMQ, SQS and async processing

A queue or log sits between a producer and consumers so work happens asynchronously: it decouples services, absorbs spikes and enables retries; Kafka is a partitioned replayable log for high-throughput streams, RabbitMQ is a flexible broker with exchanges and acks, SQS is a managed queue, and consumers must be idempotent because delivery is at least once.

The problem: synchronous chains are fragile

If placing an order synchronously calls payment, inventory, email, invoice PDF and analytics, the user waits for all of them, and one slow or failing service breaks the order. With a message queue the order service saves the order, puts an "OrderPlaced" message on a queue and replies at once. Other services consume the message in their own time.

Benefits of asynchronous processing:

  • Decoupling: producer and consumer can be deployed, scaled and fail separately; you can add a new consumer without touching the producer.
  • Buffering spikes (load leveling): a flash sale produces 50,000 orders per second for a minute; the queue stores them and workers drain at their own steady rate.
  • Retries and resilience: if the email provider is down, the message waits and is retried.
  • Faster responses: slow work moves out of the request path.
  • Scaling workers independently by queue length.

Costs: eventual consistency (the invoice appears a few seconds later), harder debugging and tracing, duplicate and out-of-order messages, and one more system to run.

Kafka: a distributed log

Kafka stores messages in a durable, append-only log. A topic is split into partitions; each partition is an ordered sequence, and each message has an offset (its position). Consumers do not delete messages; they track their offset. Messages stay until the retention time or size is reached, so consumers can replay history.

  • Ordering is guaranteed only within a partition. Messages with the same key (for example orderId) hash to the same partition, so one order's events stay in order.
  • Consumer groups: consumers in one group split the partitions between them (scale out up to the number of partitions); a different group gets its own full copy of the stream. This gives both work-queue and pub/sub in one model.
  • Replication: each partition is copied to several brokers; a leader serves reads and writes. Producers choose the acknowledgement level (acks=all for durability).
  • Throughput is very high, as it uses sequential disk writes and batching; it fits event streaming, log and metric pipelines, CDC, event sourcing.
  • Costs: more operational weight (cluster management; modern versions use KRaft instead of ZooKeeper), partition count is hard to change later, no per-message priority, and consumer rebalancing pauses.

RabbitMQ: a smart broker

RabbitMQ implements AMQP. Producers publish to an exchange, which routes messages to queues by bindings and a routing rule (direct: exact key; topic: patterns like order.*; fanout: all queues; headers). Consumers read from a queue and acknowledge (ack) each message after processing; unacknowledged messages are redelivered. Once acked, the message is gone. It supports per-message TTL, priorities, dead-letter exchanges and flexible routing, and it is excellent for task queues with complex routing and moderate volume. It is not built for replay or for the throughput of Kafka. See Spring Boot · Module 7 for Spring AMQP and Spring Kafka.

Amazon SQS (and SNS)

SQS is a fully managed queue: no servers to run, scales automatically, pay per request. A consumer receives a message, which becomes invisible for the visibility timeout; if the consumer deletes it in time the work is done, otherwise it reappears and is retried. Standard queues give at-least-once delivery with best-effort ordering and very high throughput; FIFO queues give ordering per message group and de-duplication, with lower throughput limits. Built-in dead-letter queues and retention up to 14 days. For pub/sub, SNS fans a message out to many SQS queues. Cost: vendor lock-in, no replay once deleted, polling latency.

Reliability: delivery semantics and idempotent consumers

  • At-most-once: the message may be lost, never duplicated (ack before processing).
  • At-least-once: never lost, but duplicates happen (ack after processing; a crash between processing and ack causes redelivery). This is the usual default.
  • Exactly-once: hard in general. Kafka offers idempotent producers and transactions inside Kafka; end to end across a database you get effectively once by combining at-least-once delivery with an idempotent consumer.

An idempotent consumer produces the same result if it sees a message twice. Common ways: record processed message ids in a table with a unique constraint; use natural idempotency (an upsert keyed by order id instead of an insert); version numbers. See the saga and outbox patterns in Module 6.

@KafkaListener(topics = "orders", groupId = "invoice-service")
@Transactional
public void onOrderPlaced(OrderPlaced event) {
    // processed_events has a UNIQUE constraint on event_id
    boolean firstTime = processedEvents.insertIfAbsent(event.eventId());
    if (!firstTime) {
        return;                              // duplicate delivery: do nothing
    }
    invoiceService.createInvoice(event.orderId());   // same transaction as the insert
}

Backpressure, retries and dead-letter queues

  • Backpressure: if producers outrun consumers, the queue grows without bound. Watch queue depth and consumer lag, scale consumers, limit producers (rate limits, bounded queues), or shed low-priority work. A queue hides overload; it does not remove it.
  • Retries: retry transient errors with exponential backoff and jitter; cap the number of attempts.
  • Dead-letter queue (DLQ): after N failed attempts a message moves to a DLQ so it does not block the others (a poison message otherwise retries forever). Alert on DLQ size, inspect, fix, and replay.
  • Ordering vs parallelism: strict ordering limits parallel consumption; order only what needs it, by key.

Typical event-driven uses

  • Send email or SMS after sign-up or order, with retries.
  • Generate thumbnails and video transcodes after an upload event.
  • Update the search index when a product changes (Search).
  • Keep caches and read models fresh; fan out a post to followers' feeds.
  • Collect logs, clickstream and metrics into analytics.

Common mistakes

  • Assuming exactly-once delivery and writing consumers that break on duplicates.
  • Publishing to the queue and writing to the database as two separate steps; one can fail (use the outbox pattern).
  • No DLQ, so one bad message blocks a partition or loops forever.
  • Putting large payloads in messages; send an id or an S3 link instead.

Interview angle

  • "I decouple the slow parts with a queue: the API returns 202 Accepted, workers do the rest, and consumers are idempotent because delivery is at least once."
  • Choose Kafka for high-volume streams, replay and multiple independent consumers; RabbitMQ for task routing; SQS when on AWS and you want zero operations.
  • Explain partitions: ordering per key, parallelism across partitions, consumers up to the number of partitions.

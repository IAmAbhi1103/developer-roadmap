Object storage (S3) for files, presigned URLs and multipart uploads

Store files (images, videos, documents) in object storage such as S3, which is cheap, extremely durable and scales without limit, and keep only the metadata and the object key in your database; let clients upload and download directly with presigned URLs, and put a CDN in front.

Why not store files in the database or on the app server

Large binary files in a relational database bloat it, slow backups and replication, and waste expensive storage. Files on an app server's disk break statelessness (the next instance cannot see them) and die with the machine. Object storage is built for exactly this: a flat store of immutable blobs addressed by key over HTTP. Examples: Amazon S3, Google Cloud Storage, Azure Blob Storage, and self-hosted MinIO.

S3 concepts

Bucket
A top-level container with a globally unique name; holds objects. Settings such as access policy, versioning and lifecycle rules apply per bucket.
Object
The file's bytes plus metadata. An object is written or replaced as a whole; you cannot edit part of it in place.
Key
The object's name inside the bucket, for example users/42/avatar/2026-11.jpg. The namespace is flat; the slashes only look like folders (a "prefix").
Metadata
System metadata (size, content type, ETag, last-modified) and your own key-value tags.
Storage class
Hot (frequent access), infrequent access, and archive tiers with lower price and slower or paid retrieval. Lifecycle rules move or delete objects by age automatically.
Versioning
Keeps old versions of an object, so an overwrite or delete can be undone.
  • Durability: S3 advertises eleven nines (99.999999999%) of durability for standard storage, achieved by storing data redundantly across multiple facilities. That is about durability (not losing objects), not availability (always reachable), which is lower.
  • Consistency: S3 now gives strong read-after-write consistency for object writes, overwrites and deletes, so a read after a successful PUT sees the new data.
  • Limits: a single object can be up to 5 TB; one PUT request up to 5 GB; larger uploads use multipart.
  • Not a file system: no append, no rename (it is copy and delete), no locking, and each request has network latency of tens of milliseconds. Do not use it for databases or for tiny frequent random writes.

The standard pattern: blob in S3, metadata in the database

The database row holds the object_key, owner, content type, size and status, and the bytes live in S3. Queries, permissions and joins stay in SQL, and storage scales separately.

Presigned URLs

A presigned URL is a normal S3 URL with a signature and expiry in its query string, created by your server with its credentials. Whoever holds it can perform that one operation (upload this key, or download this object) until it expires, with no AWS credentials of their own. Benefits: the file bytes skip your servers (saving bandwidth, CPU and memory), the bucket can stay private, and access is time-limited.

import java.time.Duration;
import software.amazon.awssdk.services.s3.model.PutObjectRequest;
import software.amazon.awssdk.services.s3.presigner.S3Presigner;
import software.amazon.awssdk.services.s3.presigner.model.PutObjectPresignRequest;

public class PresignService {
    private final S3Presigner presigner;                    // built once, reused

    public PresignService(S3Presigner presigner) {
        this.presigner = presigner;
    }

    public String uploadUrl(String bucket, String key, String contentType) {
        PutObjectRequest put = PutObjectRequest.builder()
            .bucket(bucket).key(key).contentType(contentType).build();
        PutObjectPresignRequest req = PutObjectPresignRequest.builder()
            .signatureDuration(Duration.ofMinutes(10))      // short-lived
            .putObjectRequest(put).build();
        return presigner.presignPutObject(req).url().toString();
    }
}

Generate keys on the server (for example a UUID under the user's prefix) so clients cannot overwrite other people's files, check the file type and size limits, and verify the upload before marking it complete. Downloads work the same way with a presigned GET for private files.

Multipart upload

For large files (videos, backups) S3 supports multipart upload: start an upload, send the file as numbered parts (5 MB to 5 GB each, up to 10,000 parts) in parallel, then complete the upload and S3 assembles them. Benefits: parallel speed, resume by re-sending only failed parts (important on mobile networks), and uploads beyond 5 GB. AWS recommends it for objects above about 100 MB. Add a lifecycle rule to abort unfinished uploads, or the abandoned parts keep costing money.

CDN in front, and other practices

  • Serve public media through a CDN (CDN) with the bucket private and the CDN allowed to read it. This cuts latency and S3 request cost.
  • Use fingerprinted or unique keys so objects never change and caches stay valid.
  • Make thumbnails asynchronously: an upload event goes to a queue (Queues), a worker resizes and writes several sizes.
  • Encrypt at rest and in transit; block public access by default; apply least-privilege roles.
  • Spread keys with varied prefixes only if you hit request-rate limits; S3 scales per prefix automatically in most cases.
  • Be aware of costs: storage per GB-month, requests, and especially data transfer out.

Common mistakes

  • Making a bucket public to "make it work" and leaking private files.
  • Proxying every upload through the API server, so it becomes the bandwidth bottleneck.
  • Long-lived presigned URLs that get shared.
  • Forgetting to delete the S3 object when the database row is deleted (orphans cost money).

Interview angle

  • "Files go to S3, metadata to PostgreSQL. The client uploads with a presigned URL, so our servers never touch the bytes, and a CDN serves downloads."
  • For large videos mention multipart upload and resumable uploads.
  • Quote durability vs availability correctly: eleven nines is about not losing data.

Search engines: the inverted index and Elasticsearch

A search engine answers "which documents contain these words, ranked by relevance" using an inverted index; Elasticsearch and OpenSearch scale it with shards and replicas, but they are a secondary index, not your source of truth, so keep them in sync with the database through events or change data capture.

The problem

SQL LIKE '%phone%' scans every row, cannot use an index for a leading wildcard, ignores spelling mistakes and word forms, and cannot rank results. Users expect Google-style search: typo tolerance, relevance order, filters, highlights, autocomplete. A search engine is built for this.

The inverted index in simple words

A normal index maps a document to its words. An inverted index flips it: for each word, it lists the documents that contain it (like the index at the back of a textbook).

Doc 1: "red running shoes"
Doc 2: "blue running jacket"
Doc 3: "red jacket"

Term      → documents
red       → 1, 3
running   → 1, 2
shoes     → 1
blue      → 2
jacket    → 2, 3

Query "red jacket": red → {1,3}, jacket → {2,3}; intersect → {3}; OR → {1,2,3} ranked

Before indexing, text goes through an analyzer: split into tokens, lowercase, remove stop words ("the", "is"), and apply stemming (running to run) so related forms match. The same analysis is applied to the query. Results are ranked by a relevance score, classically TF-IDF and in modern engines BM25: a term that is frequent in this document but rare across all documents scores higher.

Elasticsearch and OpenSearch

  • Elasticsearch (built on Apache Lucene) and its fork OpenSearch store JSON documents in an index, split into shards spread across nodes, each with replicas for availability and read throughput. They expose a REST API with a rich query language.
  • Use cases: product and site search, autocomplete and "did you mean", log and event analytics (the ELK stack), filtering and faceting (price, brand), geo search.
  • Near-real-time: new documents become searchable after a short refresh interval (about a second by default), not instantly.
  • Number of primary shards is fixed when you create the index; plan it, or reindex later.

Rule: treat the search index as derived data

It is optimised for reading, offers weaker transactional guarantees, and can be rebuilt. Keep the source of truth in the database, and be able to reindex everything from it. Never store the only copy of important data in Elasticsearch.

Trade-offs and failure modes

  • Index lag: a just-added product may not appear for a second or more.
  • Memory and disk hungry; wrong mappings or too many shards hurt performance; deep pagination (page 10,000) is expensive.
  • Cluster operations: split-brain risk if misconfigured, shard rebalancing, and version upgrades.
  • Relevance tuning is real work: analyzers, synonyms, boosting.
  • For small datasets, PostgreSQL full-text search (tsvector) may be enough, with no new system.

Interview questions — Building blocks

Walk through what happens when a user types a URL, from a system design view.

DNS resolves the name (cached; possibly geo-routed to the nearest region). Static assets come from a CDN edge. API requests reach a load balancer that terminates TLS and picks a healthy app server. The app checks Redis, and on a miss queries a database (reads from a replica). Slow work is put on a queue for workers. Each hop adds latency and a failure mode, which is why each has caching, redundancy or timeouts.

What is the difference between an L4 and an L7 load balancer?

L4 balances TCP/UDP connections using only IP and port: very fast, protocol-agnostic, few features. L7 understands HTTP, so it can route by path, host or header, terminate TLS, set sticky cookies and retry. Use L4 for raw speed and non-HTTP traffic, L7 when you need content-based routing. Many systems use both.

Which load-balancing algorithm would you use and why?

Round robin for identical servers and similar requests; weighted when machine sizes differ; least connections when request durations vary a lot, since it adapts to load; consistent hashing when the same key should reach the same server (local caches, sharded caches). Combine with active health checks so dead servers leave the pool.

How would you rate limit an API? Compare token bucket and sliding window.

Token bucket refills tokens at a steady rate and allows bursts up to the capacity; it needs only two values per client. Fixed windows are simple but allow double bursts at the boundary. A sliding window log is exact but stores every timestamp; the sliding window counter approximates it with two counters. Distribute state in Redis with atomic operations (INCR with EXPIRE, or a Lua script). Return 429 with Retry-After.

Explain cache-aside, write-through and write-behind.

Cache-aside: the app reads the cache, loads from the database on a miss and fills the cache; on writes it updates the database then deletes the key. Write-through: every write goes to cache and database together, so the cache is fresh but writes are slower. Write-behind: write to the cache and flush to the database later, which is fast but risks losing data if the cache fails.

What is a cache stampede and how do you prevent it?

A hot key expires and many requests rebuild it at once, overloading the database. Prevent it with a per-key lock or request coalescing so only one request loads, refreshing the entry before it expires (or serving stale while refreshing), and jittered TTLs. Never-expiring hot keys refreshed by a background job also work.

How do you handle cache penetration and cache avalanche?

Penetration is repeated requests for keys that do not exist, so every one hits the database. Cache the empty result for a short time, put a Bloom filter of valid keys in front, and validate input. Avalanche is many keys expiring together or the cache dying: add random jitter to TTLs, warm the cache, run it in a highly available setup and protect the database with limits.

What is the order of database scaling steps?

Tune queries and indexes, scale up the machine, add a cache, add read replicas, partition large tables, and finally shard. Each step adds complexity, so you move down only when a measured limit (read load, write load, storage) forces it. Replicas and caches scale reads; only sharding scales writes and total storage beyond one machine.

What problems does replication lag cause and how do you handle them?

With async followers a read may miss a recent write (read-your-writes violation), or go back in time across two followers (non-monotonic reads). Handle it by reading your own data from the leader for a short time after a write, sending critical reads to the leader, tracking the last write position, and pinning a user to one follower. Monitor lag and remove lagging followers.

How do you choose a shard key, and what are the downsides of sharding?

Pick a high-cardinality, evenly distributed, stable key that matches the main query pattern, like user id, so most queries touch one shard. Avoid monotonic keys with range sharding because they create a hot shard. Downsides: cross-shard joins and transactions, scatter-gather queries, hot spots, uniqueness of ids, and complex resharding. Many logical shards mapped to a few servers make rebalancing easier.

Explain consistent hashing and why virtual nodes are used.

Servers and keys are hashed onto a ring; a key belongs to the next server clockwise. When a server joins or leaves only about 1/N of the keys move, compared with most keys for hash mod N. With few servers the arcs are uneven, so each server is placed at many virtual points, which evens out the load and spreads a failed node's keys across many neighbours. In Java a TreeMap with ceilingEntry and wrap-around implements the lookup.

When would you pick NoSQL over SQL?

When the access pattern is simple and known and scale is huge (key-value or wide-column), when data is flexible and nested (document), or when relationship traversal is central (graph). I still default to a relational database for business data that needs transactions and ad-hoc queries, and add specialised stores next to it (polyglot persistence). I would not claim NoSQL is simply faster.

Kafka vs RabbitMQ vs SQS: how do you choose?

Kafka is a replayable partitioned log with very high throughput, ordering per partition and consumer groups; choose it for event streaming and many independent consumers. RabbitMQ is a broker with flexible routing, acks and priorities; choose it for task queues and complex routing. SQS is a managed queue with no operations on AWS and simple semantics. Delivery is typically at least once, so consumers must be idempotent.

How would you design file upload for a photo app?

The client asks the API for an upload permission; the API validates and returns a short-lived presigned PUT URL for a server-generated key. The client uploads directly to S3 (multipart for large files) and then confirms. The API stores metadata in the database. An S3 event goes to a queue and workers scan and create thumbnails. A CDN serves downloads from the private bucket.

How do you keep a search index in sync with your database?

Avoid dual writes because they are not atomic. Use the outbox pattern (write the change and an event in one transaction, publish it, let an indexer update Elasticsearch) or change data capture from the database log. The index is derived data and eventually consistent, and you must be able to reindex everything from the database into a new index and swap an alias.

Cheat sheet — Building blocks

  • DNS name to IP, cached by TTL; geo and latency routing; failover is minutes, not seconds.
  • CDN edge caches near users; use fingerprinted URLs with long max-age, purge only in emergencies.
  • Cache-Control max-age, s-maxage, private, no-store, immutable, stale-while-revalidate, ETag.
  • L4 vs L7 L4 sees IP and port (fast); L7 sees HTTP (routing, TLS, cookies).
  • LB algorithms round robin, weighted, least connections, IP hash, consistent hashing.
  • Health checks active probes plus passive error watching; readiness vs liveness; connection draining.
  • LB availability run two across zones or a managed balancer; avoid sticky sessions.
  • API gateway routing, auth, rate limits, aggregation, protocol translation; BFF per client type.
  • Rate limit algorithms token bucket (bursts), leaky bucket (smooth), fixed window (boundary burst), sliding log (exact), sliding counter (cheap approximation).
  • Rate limit response 429, Retry-After, X-RateLimit headers; atomic Redis INCR+EXPIRE or Lua; decide fail open or closed.
  • Cache layers browser, CDN, proxy, local, Redis, database buffer cache.
  • Cache patterns cache-aside (default), read-through, write-through, write-behind, write-around.
  • Eviction LRU default, LFU for stable popularity; always set a TTL.
  • Cache problems stampede (lock, coalesce, early refresh), penetration (null cache, Bloom), avalanche (TTL jitter), hot key (local copy, replicate).
  • Hit ratio hits / (hits + misses); average latency = hit% × hit time + miss% × miss time.
  • DB ladder indexes, scale up, cache, replicas, partitioning, sharding.
  • Replication leader-follower is default; async is fast but lags; multi-leader needs conflict handling; leaderless uses quorums.
  • Replication lag fix read own writes from the leader; pin users; monitor lag.
  • Sharding range, hash, directory, geo; key needs high cardinality and even load; use many logical shards.
  • Sharding costs cross-shard joins, transactions, scatter-gather, resharding, unique ids.
  • Consistent hashing ring plus virtual nodes; adding a node moves about 1/N of keys; TreeMap ceilingEntry with wrap-around.
  • NoSQL types key-value (Redis, DynamoDB), document (MongoDB), wide-column (Cassandra), graph (Neo4j), plus time-series and search.
  • Queues decouple, buffer, retry; point-to-point vs pub/sub; at-least-once so make consumers idempotent; use a DLQ.
  • Kafka vs RabbitMQ vs SQS replayable log with partitions; smart routing broker; managed simple queue.
  • Object storage blob in S3, metadata in the DB, presigned URLs, multipart for big files, CDN in front.
  • Search inverted index, analyzers, BM25; Elasticsearch is derived data synced by outbox or CDC.

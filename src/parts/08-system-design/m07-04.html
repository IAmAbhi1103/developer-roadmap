Design a news feed (like Instagram)

A news feed shows each user the recent posts of the people they follow; the core decision is fan-out on write (push each new post into followers' precomputed feeds, fast reads) versus fan-out on read (assemble the feed at request time), and real systems use a hybrid so celebrity accounts do not cause millions of writes.

1. Requirements

Functional:

  • Users create posts (text, photos, videos).
  • Users follow and unfollow other users.
  • A user opens the app and sees a feed of recent posts from the accounts they follow, newest or best first, loaded page by page (infinite scroll).
  • Likes and comments exist, but the design focus is the feed itself.

Non-functional: feed load in under about 300 ms (reads must be fast), high availability, a new post appears in followers' feeds within a few seconds (eventual consistency is fine; a delay of seconds is not noticed), scalability to hundreds of millions of users, and tolerance for accounts with tens of millions of followers. Strong consistency is not required: seeing a post a little late is acceptable. Out of scope: the ranking model itself (mention the inputs), ads, stories.

2. Capacity estimates (assumptions)

  • 100 million daily active users; each opens the feed 10 times a day → 1 billion feed reads per day → 1,000,000,000 ÷ 86,400 ≈ 11,600 per second; peak 3× ≈ 35,000 per second.
  • 10 million new posts per day → 10,000,000 ÷ 86,400 ≈ 116 posts per second.
  • Reads outnumber writes: 11,600 ÷ 116 = 100:1. This strongly favours doing work at write time.
  • Average user follows 200 accounts. Fan-out on write: 10M posts × 200 followers = 2 billion feed insertions per day ≈ 23,000 per second. That is a lot but each is a tiny write (an id into a list), and it runs asynchronously.
  • A celebrity with 50 million followers: one post would need 50,000,000 insertions. At 23,000 per second of system capacity that single post would take about 36 minutes of the total fan-out budget. This is why a pure push model fails for celebrities.
  • Feed cache: keep the latest 500 post ids per active user. Each id 8 bytes → 500 × 8 = 4 KB per user → 100,000,000 × 4 KB = 400 GB (before Redis overhead, which might double it). A sharded Redis cluster of a few nodes with 128 GB each can hold it.
  • Post storage: 10M posts × ~1 KB metadata = 10 GB per day (3.65 TB per year). Media: if 30% of posts carry a 500 KB photo → 3M × 500 KB = 1.5 TB per day in object storage behind a CDN.

Pagination: use a cursor (the id or time of the last item seen), not page=5 or OFFSET. With offset, new posts push items down and the user sees duplicates or skips; deep offsets are also slow (SQL · Module 5 explains why). Cursor pagination asks for "20 items older than this id", which is stable and uses an index.

4. Data model

users        user_id, name, follower_count, is_celebrity
follows      (follower_id, followee_id)   index both ways
posts        post_id (Snowflake, time-sortable), author_id, text, media_ids, created_at
feed:{user}  Redis sorted set: member = post_id, score = post_id or time
             (latest ~500 entries)
likes        (post_id, user_id) + counter cache
media        media_id -> object-storage path
  • Posts are written once and read by id, plus "latest posts of author X": a wide-column store or sharded SQL keyed by author_id works, with time-sortable post ids (Unique IDs) so newest-first ordering needs no extra column.
  • Follows is a graph edge list; it needs both "who does X follow" and "who follows X". Store two tables or two indexes. Shard by user id.
  • The precomputed feed is a Redis sorted set per user holding only post ids, not full posts (small, and edits or deletes affect one copy). Hydrate ids into full posts by fetching from a post cache.
  • Counters (likes) are updated asynchronously and cached; approximate counts are acceptable.

5. High-level architecture

Write path: the post service stores the post, then publishes a "post created" event (via an outbox, Outbox). Fan-out workers read the author's follower list in pages and add the post id to each follower's feed sorted set, trimming to 500. Read path: the feed service reads the top 20 ids after the cursor from the user's sorted set, fetches post bodies from the post cache (batch get), fetches author data, and returns the page; images load from the CDN.

6. Deep dive A: fan-out on write vs on read vs hybrid

AspectFan-out on write (push)Fan-out on read (pull)

Read costVery low: read one listHigh: read posts of ~200 followees, merge, sort

Hybrid (the usual answer). Use push for normal users and pull for celebrities:

  • If the author has fewer than a threshold of followers (say 100,000, tuned from data), fan out on write.
  • If the author is above the threshold, do not fan out. Store the post only.
  • At read time, the feed service takes the user's precomputed feed (normal accounts) and merges in recent posts from the few celebrities the user follows, fetched from a per-celebrity "recent posts" cache. A user follows few celebrities, so this extra read is small and the celebrity's list is shared by all their followers, so it caches very well.
  • Skip fan-out for inactive users (not opened the app in 30 days). Rebuild their feed on return with the pull method.
public List<PostView> getFeed(long userId, String cursor, int limit) {
    List<Long> ids = new ArrayList<>(feedCache.range(userId, cursor, limit));  // pushed posts

    for (long celeb : graph.celebritiesFollowedBy(userId)) {                  // few of them
        ids.addAll(celebRecent.range(celeb, cursor, limit));                  // pulled posts
    }
    ids.sort(Comparator.reverseOrder());          // newest first (time-sortable ids)
    List<Long> page = ids.stream().distinct().limit(limit).toList();
    return postHydrator.load(page);                // batch get from post cache
}

7. Deep dive B: ranking, caching and consistency

  • Chronological vs ranked. A chronological feed is the sorted set as it is. A ranked feed takes candidate posts (say 500 ids), scores each with features (author affinity, recency, past engagement, post type), and returns the top ones. Scoring is a separate service; keep the interface simple: ids in, ordered ids out. In the interview, mention it and keep the focus on retrieval.
  • Hot posts and cache. A viral post is read by millions, so cache the post object with a short TTL, and use a local cache for the hottest ids to avoid a hot key on one Redis shard (Module 5). Media is served from the CDN with long cache lifetimes.
  • Deletes and edits. Because feeds hold ids only, a deleted post disappears when hydration returns "not found" or "deleted"; the feed service filters those out. No need to remove it from 200 feeds immediately.
  • Unfollow and block. Filter at read time by the current follow set (cheap), and lazily clean the stored feed.
  • New follow. Backfill: add the followee's last few posts into the follower's feed.
  • Consistency. The feed is eventually consistent: after posting, the author should see their own post immediately (read-your-writes), so the client inserts it locally or the feed service merges the author's own latest posts. Followers see it within seconds.

8. Deep dive C: the fan-out pipeline at scale

  • Fan-out is a queue-driven job. Split one author's follower list into pages of, say, 1,000 followers; each page is a separate task so many workers share one big fan-out and a failed page can be retried alone.
  • Writes to Redis are idempotent (ZADD of the same member is harmless), so at-least-once processing is fine (Delivery semantics).
  • Use priority: a post by a user with 100 followers should not wait behind a 5-million follower fan-out. Separate queues by author size.
  • Fan-out lag is the key metric: time from post creation to last insertion. Alert when it exceeds a few seconds for normal accounts.
  • Redis memory is the cost driver: trimming to 500 entries and limiting to active users keeps it bounded. If the cache is lost, rebuild feeds lazily by pull.

9. Bottlenecks and scaling

  • Feed cache shards by user id; add nodes with consistent hashing (Module 5).
  • Graph service reads of follower lists are heavy: cache them and page them.
  • Post store shards by author or post id; read replicas for hydration misses.
  • Media is offloaded to object storage and CDN; image resizing happens asynchronously at upload, producing several sizes.
  • Monitoring: feed p99 latency, cache hit ratio for feeds and posts, fan-out lag, queue depth, empty-feed rate (a sign of cache loss).

Follow-up questions

  • Where exactly is the threshold between push and pull, and how do you pick it? (Measure follower distribution and fan-out cost; start near 105 and tune.)
  • How do you show "new posts available" without reloading? (Poll a lightweight count endpoint or use a WebSocket event.)
  • How would you add comments and like counts without hot-row contention? (Sharded counters, async aggregation.)
  • How do you avoid showing the same post twice across pages? (Stable cursor by post id, dedupe in the merge.)
  • How do you handle a user following 5,000 accounts? (Cap, or lean on pull with caching.)

Interview angle

  • Lead with the read:write ratio (100:1) to justify precomputing feeds.
  • Explain the celebrity problem with a number (50 million inserts per post), then the hybrid fix.
  • Store ids, not posts, in the feed; use cursor pagination.

Design a food delivery app (like Swiggy)

A food delivery platform connects customers, restaurants and delivery partners; the design is a restaurant discovery and menu service, an order service driven by a state machine and payment saga, a location service tracking partners, and a matching service that assigns the best nearby partner with a timeout and fallback.

1. Requirements

Functional:

  • Customer: search and browse restaurants near me, view menus, add to cart, pay, place an order, track it live, rate it.
  • Restaurant: receive orders, accept or reject, update menu and availability, mark order ready.
  • Delivery partner: go online/offline, receive an assignment, accept or reject, pick up, deliver, share live location.
  • Platform: estimate delivery time, handle cancellations, refunds and payouts.

Non-functional: an order must never be lost or charged twice (consistency for orders and payments); browsing can be eventually consistent and must be fast; high availability, especially at lunch and dinner peaks; location updates in near real time; assignment decisions within a few seconds. Out of scope: routing algorithm internals, pricing and surge models, ads.

2. Capacity estimates (assumptions)

  • 5 million orders per day nationwide. Average: 5,000,000 ÷ 86,400 ≈ 58 per second. Orders cluster in lunch and dinner: assume 60% of orders fall in 4 hours (14,400 seconds) → 3,000,000 ÷ 14,400 ≈ 210 orders per second at peak. Use 250 with headroom.
  • Browsing: each order comes from about 20 sessions that search and browse, with several requests each → peak read traffic on the order of 20 × 210 = 4,200 sessions/s, say 20,000 read requests per second. Heavily cached.
  • Delivery partners: 100,000 online at peak. Location update every 5 seconds → 100,000 ÷ 5 = 20,000 location writes per second. Each update ~50 bytes (partner id, lat, lng, time) → 1 MB/s. Only the latest position matters for matching, so this is an overwrite workload, not an append workload.
  • Order storage: 5M orders/day × 2 KB (order, items, history) = 10 GB per day → 3.65 TB per year. Manageable in sharded SQL.
  • Menu catalogue: 300,000 restaurants × 100 items × 1 KB = 30 GB. It fits in memory caches easily.

4. Data model

  • Orders, payments, users, partners: relational (PostgreSQL / MySQL) because an order involves several related rows and needs transactions and constraints. Shard by city or by customer id when needed.
  • Restaurants and menus: read-heavy, rarely changed, read as a document. Store in the database, index into a search engine (Elasticsearch/OpenSearch) for text and filter queries (cuisine, rating, veg only), with a geo filter for distance.
  • Live partner locations: an in-memory geo store (Redis GEO or a geohash/H3 grid), with the latest location only. History can be sampled into a log store for analytics and disputes.

5. High-level architecture

6. Deep dive A: the order lifecycle as a state machine

  • One service owns the state (order service). Others send events; the order service validates that a transition is legal (for example, you cannot go from DELIVERED to PREPARING) with an optimistic-lock update: UPDATE orders SET status = 'ACCEPTED' WHERE order_id = ? AND status = 'PAID'. Zero rows updated means a stale or duplicate event; ignore it.
  • The flow is a saga (Saga): reserve/authorise payment → ask the restaurant to accept → find a partner. Compensation: if the restaurant rejects or does not respond within, say, 3 minutes (a timer in a scheduler or a delayed message), refund and cancel. If no partner can be found, retry matching with a wider radius, then cancel and refund.
  • Reliable events via the outbox pattern (Outbox); every consumer is idempotent.
  • Keep the status history table for support and for showing the customer a timeline.

7. Deep dive B: location tracking and nearby search

  • Ingestion. 20,000 updates per second go to a location service that overwrites each partner's latest position in an in-memory geo store. Use a lightweight protocol (HTTP/2 or MQTT; a WebSocket works too). Batch and reduce the rate when the partner is idle or stationary. Update the geo index only when the cell changes or every N seconds.
  • Nearby query. Redis GEO stores points in a sorted set using a geohash score and supports a radius query around a point (GEOSEARCH in current Redis versions). Alternative: bucket space into geohash or H3 cells and keep a set of partners per cell; to find partners within 3 km, query the cell and its neighbours. The deep treatment of geohash and quadtrees is in Ride sharing.
  • Live tracking for the customer. While the order is PICKED_UP, the customer app polls GET /orders/{id} every few seconds or holds a Server-Sent Events / WebSocket stream. The tracking service reads the partner's latest location and an ETA. Polling every 5 seconds from 500,000 simultaneous deliveries is 100,000 requests per second, so a push channel and a small cache are cheaper.
  • ETA = restaurant preparation time + partner travel time to restaurant + travel time to the customer. Use a maps/routing service with live traffic; add a learned correction from past orders. State this as an estimate with error bars.

8. Deep dive C: partner matching

When an order becomes ACCEPTED, start matching so that a partner arrives as food becomes ready (not too early; waiting partners waste capacity).

  1. Candidates: query the geo index for available partners within a radius of the restaurant (start with 2–3 km).
  2. Filter: online, not already carrying too many orders, right vehicle type, not recently rejected this order.
  3. Score: distance or ETA to the restaurant, current load, rating, acceptance rate, and whether the delivery direction fits an order they already carry (batching).
  4. Offer: send the best candidate an assignment with a timeout (10–15 seconds). Create the assignment in the database with state OFFERED. If accepted, atomically update partner_id where it is still null (a conditional update prevents two partners getting one order). If rejected or timed out, offer to the next candidate.
  5. Fallback: if nobody accepts after K attempts, widen the radius, add an incentive, or alert operations.

Avoid assigning the same partner to two orders at once by marking the partner as reserved during an offer; use a short lease with a TTL, not a lock that can get stuck (Coordination). Global optimisation (batching many orders and many partners and solving an assignment problem every few seconds) beats greedy one-by-one matching but is more complex; mention it as an improvement.

9. Bottlenecks, scaling and failure

  • Peaks: lunch and dinner. Pre-scale before the peak, cache restaurant lists per area, and shed non-essential features (recommendations) first (Resilience).
  • Sharding: by city for orders, restaurants and partners; each city is nearly independent, which also limits the blast radius of a failure.
  • Search: read replicas of the search index; update it asynchronously when menus change.
  • Payments: use the idempotent flow in Payments; never store card data yourself.
  • Failure cases: restaurant tablet offline (fallback: call, auto-cancel after timeout); partner phone loses network (last known position, reassign after a timeout); duplicate events (idempotent handlers).
  • Monitoring: order success rate, time to restaurant accept, time to assign a partner, delivery time vs ETA, location staleness, cancellation reasons.

Follow-up questions

  • How do you handle a restaurant going out of stock after an order? (Item-level substitution/refund flow; short menu cache TTL; push availability changes.)
  • How do you show "restaurants open now within 5 km, sorted by rating"? (Search index with geo-distance filter and sort, ranked results, cached per area.)
  • How do you prevent a partner's duplicate location updates from corrupting state? (Last-write-wins by timestamp; discard older updates.)
  • What happens if the order service restarts mid-saga? (State is in the database; resume from the last persisted status; timers are persisted.)
  • How would you support batching two orders for one partner? (Matching scores route overlap and time windows.)

Interview angle

  • Draw the order state machine; interviewers like it because it exposes failure paths.
  • Separate consistency needs: orders and payments strong, browsing and tracking eventual.
  • Explain matching as candidates → filter → score → offer with timeout → fallback.

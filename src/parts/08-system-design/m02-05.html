Where Spring uses design patterns

Spring is built from patterns: singleton beans, factories (the container), proxies for @Transactional, template classes like JdbcTemplate, observer-style application events, the DispatcherServlet front controller, HandlerAdapter, filter chains and strategy-based resolvers.

When you can name the pattern behind a Spring feature, the feature stops being magic, and you can predict its limits (such as the self-invocation trap). The table below is the quick map. Each row names the pattern, the Spring feature, and what the pattern explains.

Four examples in detail

1. Singleton beans

The container creates each singleton bean once and hands out the same instance. It is a different mechanism from the GoF class (see Singleton), but the same warning applies: shared state is shared by every thread.

2. Proxies for @Transactional

The proxy opens a transaction, calls your method and commits or rolls back (see the sequence diagram in Proxy). Because it is a proxy, three rules follow: the call must come through the proxy (no self-invocation), the method must be public in the usual setup, and the class must not be final. When something "mysteriously" does not run in a transaction, check these first.

3. JdbcTemplate

It is both a Template Method (the fixed skeleton of acquire connection, prepare, execute, map, release) and a Facade over JDBC. Your RowMapper lambda is the variable step. It also translates checked SQLException into the unchecked DataAccessException hierarchy.

4. Application events

One bean publishes a plain object, and other beans react. The order service does not know who listens. Add @Async for non-blocking listeners and @TransactionalEventListener for commit-aware ones (see Observer).

How a request flows: several patterns together

Version note

These patterns are stable across Spring Boot 3.x and 4.x. Details that moved: the servlet API package is jakarta.servlet since Boot 3, and RestTemplate is in maintenance mode in favour of RestClient (Spring Framework 6.1+), which uses the Builder pattern. The Template and Strategy ideas are the same in both.

Interview: patterns in Spring

  • Which design patterns does Spring use? Name at least five with the feature: Singleton (bean scope), Factory (ApplicationContext), Proxy (@Transactional), Template (JdbcTemplate), Observer (events), Front Controller (DispatcherServlet), Chain (filters), Strategy (resolvers).
  • How does Spring implement AOP? With proxies (JDK dynamic or CGLIB), created by a BeanPostProcessor.
  • Is the DispatcherServlet a pattern? Yes, Front Controller: a single entry point that delegates.

Other patterns in brief: Prototype, Composite, Flyweight, Iterator, Mediator, Memento, Visitor

Seven more GoF patterns are worth knowing by name and one-line idea: Prototype (copy an existing object), Composite (tree of parts treated like one), Flyweight (share small immutable objects), Iterator (traverse without exposing structure), Mediator (central coordinator), Memento (save and restore state) and Visitor (add operations to a class hierarchy from outside).

You will rarely write these from scratch, but interviewers ask about them, and you use several every day without knowing it. Learn the idea and one Java example for each.

Prototype (creational)
Create new objects by copying an existing one instead of building from scratch. Useful when construction is expensive or when you need many variations of a configured template (a default invoice, a game enemy). In Java: clone(), copy constructors or a copy()/toBuilder() method. See shallow vs deep copy in Core Java. Spring: @Scope("prototype") makes the container return a fresh instance for each request (it is "prototype scope", not exactly the GoF copy).
Composite (structural)
Compose objects into a tree, and treat single objects and groups through the same interface. A file system (file and folder both have size()), a menu with sub-menus, a UI component tree, an organisation chart, a product bundle containing products. A call on the root goes recursively to all children. 
interface FileNode { long size(); }
record FileLeaf(String name, long bytes) implements FileNode {
    public long size() { return bytes; }
}
record Folder(String name, java.util.List<FileNode> children) implements FileNode {
    public long size() { return children.stream().mapToLong(FileNode::size).sum(); }
}
JDK: Swing/AWT Container holds Components; Map.putAll style bulk operations on collections of collections. Spring Security has composite delegating classes.
Flyweight (structural)
Share many small, identical, immutable objects to save memory, by separating the shared intrinsic state from the per-use extrinsic state. In Java: the Integer cache (Integer.valueOf(100) returns a cached object for -128 to 127), the String pool, Boolean.TRUE, enum constants. Use it when you have millions of similar objects (characters in a text editor, tiles in a game map).
Iterator (behavioural)
Give sequential access to the elements of a collection without exposing its structure. Java built it in: Iterable and Iterator (hasNext, next, remove) power the enhanced for loop. To make your class loopable, implement Iterable<T>. Iterators of ArrayList are fail-fast: structural modification during iteration throws ConcurrentModificationException. See Collections.
Mediator (behavioural)
Replace many-to-many direct links between objects with one coordinator, so objects talk only to the mediator. Examples: a chat room (users send to the room, which relays), an air-traffic controller, a UI form where the dialog enables the Submit button when fields are valid. Java: java.util.Timer coordinates tasks; ExecutorService sits between submitters and threads; Spring's DispatcherServlet mediates between handlers and views; message brokers do the same between services. Risk: the mediator becomes a god object.
Memento (behavioural)
Capture and store an object's internal state in an opaque snapshot so it can be restored later, without breaking encapsulation. Used for undo, checkpoints and "save game". The object (originator) creates the memento; a caretaker keeps a stack of them; only the originator can read the contents. Java: serialization snapshots, record copies of immutable state. It complements Command undo: Command reverses an operation, Memento restores a saved state.
Visitor (behavioural)
Add new operations to a class hierarchy without changing the classes, by moving each operation into a visitor with one visit method per type. The elements have a single accept(visitor) method (double dispatch). Good when the types are stable but operations change often (a compiler walking a syntax tree, tax rules over different item types). Bad when new types appear often, because every visitor must change. JDK: java.nio.file.FileVisitor with Files.walkFileTree. In modern Java (17+), sealed interfaces plus a pattern-matching switch give a lighter alternative.

Quick example: Iterator for a custom class

import java.util.Iterator;
import java.util.List;

public class Playlist implements Iterable<String> {
    private final List<String> songs;
    public Playlist(List<String> songs) { this.songs = List.copyOf(songs); }

    @Override
    public Iterator<String> iterator() {
        return new Iterator<>() {
            private int index = 0;
            public boolean hasNext() { return index < songs.size(); }
            public String next() { return songs.get(index++); }
        };
    }
}

// for (String s : new Playlist(List.of("A", "B"))) System.out.println(s);

Other patterns you may hear of

Interpreter (evaluate a small language), Bridge (separate abstraction from implementation so both vary: the notification-channel example in composition over inheritance is a Bridge in spirit), and Null Object (an object that does nothing, instead of null: Collections.emptyList(), a NoOpNotifier). Beyond GoF: Repository, Dependency Injection, Specification, Circuit Breaker and Saga appear in architecture (Module 6).

A 4-question test before you add a pattern

  1. What exact pain am I feeling in the code today?
  2. Is there a simpler fix (a method, a parameter, a lambda, a record)?
  3. Will a teammate understand it faster with the pattern than without it?
  4. Can I give it a name that the team already knows?

Tip: patterns in interviews

For a low-level design question (Module 3) you will usually need Strategy (pricing, payment, parking fees), State (vending machine, order, elevator), Observer (notifications), Factory (creating vehicles or notifiers), Singleton (a manager or logger) and Builder (complex requests). Name the pattern aloud and say which pain it removes.

Interview questions — Design patterns

What is a design pattern, and what are the three categories?

A design pattern is a named, reusable solution to a common design problem, with structure and trade-offs; it is a description, not code to copy. The Gang of Four grouped 23 patterns into creational (how objects are created: Singleton, Factory, Builder), structural (how objects are composed: Adapter, Decorator, Facade, Proxy) and behavioural (how objects interact: Strategy, Observer, Command, State, Chain of Responsibility, Template Method).

How do you write a thread-safe Singleton? Why does double-checked locking need volatile?

Best choices: the holder idiom (a private static nested class holding the instance) or a single-element enum. Double-checked locking also works if the field is volatile. Without it, the assignment instance = new X() can be reordered, so another thread might see a non-null reference to an object whose constructor has not finished. volatile forbids that reordering and gives safe publication.

How can a Singleton be broken, and how do you prevent each way?

Reflection (setAccessible(true) on the constructor): throw from the constructor if an instance exists, or use an enum. Serialization (each deserialization creates a new object): add readResolve() returning the instance. Cloning: do not implement Cloneable, or throw from clone(). Multiple class loaders also create one instance per loader. An enum singleton resists the first three.

What is the difference between a Spring singleton bean and the GoF Singleton?

A GoF Singleton is enforced by the class itself (private constructor) and is one per class loader, accessed globally with getInstance(). A Spring singleton is enforced by the container: one instance per bean definition per container, injected where needed, and the class itself can still be instantiated with new. Spring singletons are shared across threads, so they must be stateless or thread-safe.

Factory Method versus Abstract Factory?

Factory Method defines one creation method that subclasses override to decide the product (inheritance). Abstract Factory is an interface with several creation methods that produce a family of related products, such as TaxCalculator and InvoiceFormatter for one country, and you swap the whole factory. A Simple Factory is neither: one class with a switch that returns the right product.

When would you use Builder, and how does it compare with a telescoping constructor?

Use Builder when a class has many parameters, several optional, and you want immutability and readable code. Telescoping constructors (many overloads) are unreadable and easy to call with swapped arguments; setters leave a half-built, mutable object. A builder collects values by name, validates in build() and returns an immutable object. Examples: HttpRequest.newBuilder(), Lombok @Builder.

Adapter vs Decorator vs Proxy vs Facade?

Adapter changes an interface so incompatible classes work together. Decorator keeps the interface and adds behaviour, stackable at run time. Proxy keeps the interface and controls access (lazy loading, security, caching, transactions). Facade gives a new, simpler interface over many classes. Examples: InputStreamReader; BufferedReader; the Spring @Transactional proxy; SLF4J or an OrderFacade.

How does @Transactional work, and why does a call from another method of the same class not start a transaction?

Spring wraps the bean in a proxy (JDK dynamic proxy for interfaces, or a CGLIB subclass; Boot uses CGLIB by default). The proxy begins the transaction, calls your method, and commits or rolls back (rollback on runtime exceptions by default). A call using this inside the class goes directly to the target object and skips the proxy, so no transaction logic runs. Fix by moving the method to another bean, or by using AspectJ weaving.

How would you replace a long if/else on payment type with a pattern?

Use Strategy: define a PaymentStrategy interface and one class per method. In Spring, make each a @Component and inject a List or Map of them into the service, which picks by key. Adding a method means adding a class. If the choice depends on the order's lifecycle (not the client's pick), use State instead.

Strategy vs State?

The structure is the same: a context delegates to an interface. In Strategy, the client chooses an algorithm, and strategies are independent of each other. In State, the object changes its own state object as events happen, and the states usually know the transitions. Use State for order life cycles and vending machines; use Strategy for pricing and payment rules.

Explain Observer and its Spring implementation. What is the catch?

A subject notifies registered listeners about changes without knowing them. In Spring, publish an event with ApplicationEventPublisher and handle it with @EventListener. Catches: listeners run synchronously on the publisher's thread by default (and inside its transaction), so a slow or failing listener affects the publisher; use @Async or @TransactionalEventListener(AFTER_COMMIT). Also beware of forgotten listeners that leak memory. For cross-service events you need a message broker.

What is the Command pattern used for, and which Java type is a command?

Command turns a request into an object with execute() (and undo()). It lets you queue, schedule, log, retry or undo operations and decouples the sender from the receiver. Runnable and Callable are commands, and ExecutorService is the invoker. A text editor's undo stack of command objects is the standard example.

Where does Chain of Responsibility appear in Spring and servlets?

Servlet filters: each Filter receives a FilterChain and calls chain.doFilter to continue or returns to stop. Spring Security is a SecurityFilterChain of ordered filters (CORS, CSRF, authentication, authorization). HandlerInterceptors in Spring MVC are similar. A handler that does not call the next one ends the chain, for example to return 401.

What is Template Method, and how is it different from Strategy?

Template Method defines the fixed order of steps in a final method of a base class; subclasses implement some steps (abstract methods or hooks). Examples: AbstractList, HttpServlet.service, JdbcTemplate with callbacks. It varies steps by inheritance, decided at compile time. Strategy varies a whole algorithm by composition, decided at run time. Prefer Strategy when you need flexibility or want to avoid inheritance.

Which patterns would you name when designing a notification system?

Strategy or Factory for channels (email, SMS, push), Observer or events to trigger notifications from business actions, Decorator for retry, logging or rate limiting around a channel, Template Method for shared message-building steps, Builder for the message object, and Chain of Responsibility for fallback channels. Mention that you would start simple and add patterns only as the need appears.

Cheat sheet — Design patterns

  • Pattern named, reusable solution to a recurring design problem; learn the problem first.
  • Categories creational (creation), structural (composition), behavioural (interaction).
  • Singleton one instance; holder idiom or enum; DCL needs volatile; break by reflection, serialization, clone; prefer a Spring bean.
  • Spring singleton one per container per bean definition; must be stateless or thread-safe.
  • Static factory of, valueOf, from, getInstance, create, copyOf; named, can cache, can return subtypes.
  • Simple Factory one switch that returns products; not GoF.
  • Factory Method subclass decides which product; Abstract Factory family of related products.
  • Builder step-by-step construction, validate in build(), immutable result; Lombok @Builder; skip for 2-3 fields.
  • Adapter converts an interface (third-party SDK to your interface); object adapter over class adapter.
  • Decorator same interface, adds behaviour, stackable; BufferedReader; order matters.
  • Facade one simple API over a subsystem; SLF4J, JdbcTemplate, OrderFacade; keep it thin.
  • Proxy same interface, controls access: virtual, protection, remote, caching.
  • Spring AOP JDK proxy (interfaces) or CGLIB (subclass; Boot default); self-invocation bypasses the proxy.
  • Strategy interchangeable algorithms; replaces switch; Comparator; inject Map/List of beans.
  • Observer subject notifies listeners; Spring @EventListener; sync by default; Observable is deprecated.
  • Command request as object; undo/redo, queues; Runnable, Callable.
  • State one class per state, object swaps its state; order life cycle, vending machine.
  • State vs Strategy object changes state itself vs client picks algorithm.
  • Chain of Responsibility ordered handlers that may stop the request; servlet filters, Spring Security chain.
  • Template Method final skeleton plus abstract steps and hooks; AbstractList; Hollywood principle.
  • Template callbacks JdbcTemplate, TransactionTemplate: skeleton in the template, your lambda varies the step.
  • Adapter / Decorator / Proxy / Facade converts / enhances / controls / simplifies.
  • Others Prototype (copy), Composite (tree), Flyweight (share), Iterator, Mediator, Memento (snapshot), Visitor.
  • Do not over-engineer no pattern without a pain; lambdas and records replace much ceremony.

Practice — Design patterns

  1. Singleton five ways (easy). Write an AppConfig singleton using eager init, synchronized, double-checked locking, the holder idiom and an enum. Write a test with 100 threads calling getInstance() and assert that all references are the same. Done when all five variants pass.
  2. Break and fix a singleton (medium). Break your class-based singleton with reflection, serialization and clone, then fix each. Done when the enum version cannot be broken by the same code and the others fail loudly or return the original.
  3. Replace a switch with Strategy (easy/medium). Take a PriceCalculator with a switch on REGULAR, PREMIUM, STUDENT. Refactor it into a PricingStrategy interface, then with Spring inject a Map<String, PricingStrategy>. Done when a new customer type is a new class only.
  4. Factory and Builder (medium). Build a NotifierFactory that returns email, SMS or push senders, and a NotificationRequest with a builder (required: recipient, message; optional: subject, priority, scheduled time). Done when invalid requests fail in build().
  5. Add logging with a Decorator (medium). Take a UserRepository interface and add LoggingUserRepository (log each call and its time) and CachingUserRepository as decorators. Done when you can stack them in either order and explain the difference in the log.
  6. Adapter for a payment SDK (medium). Define PaymentGateway, then adapt two fake vendor SDKs with different method names, units and error codes. Done when the checkout code compiles without importing either vendor class.
  7. Observer with Spring events (medium). Publish an OrderPlacedEvent; write three listeners (email, loyalty, analytics). Make one listener @Async and one @TransactionalEventListener(AFTER_COMMIT). Done when a rolled-back order sends no email.
  8. State machine (medium/hard). Implement an order (NEW → PAID → SHIPPED → DELIVERED, cancel from NEW or PAID) with the State pattern and write a test for every illegal transition. Then redo it as an enum with abstract methods and compare the code size.
  9. Chain and Template Method (medium/hard). Build an order-validation chain (five checks, ordered cheap-first) and a servlet-style filter chain that logs timing. Then write a ReportExporter template with CSV and HTML subclasses. Done when adding a check or a format needs no change to existing classes.
  10. Proxy and the self-invocation trap (hard). Write a JDK dynamic proxy that logs the duration of any interface method. Then, in a Spring Boot app, reproduce a @Transactional(REQUIRES_NEW) method called from the same class, show in the logs that no new transaction starts, and fix it by moving the method to another bean. Done when you can explain the fix with a sequence diagram.

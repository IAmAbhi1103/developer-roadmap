State: behaviour that changes with the object's state

State moves the state-dependent behaviour of an object into separate state classes, so the object delegates to its current state and changes state by swapping that object, which replaces large if/else blocks on a status field.

Intent: allow an object to alter its behaviour when its internal state changes; the object will appear to change its class.

The problem

An e-commerce order moves through states: NEW → PAID → SHIPPED → DELIVERED, and it can be cancelled in some states but not others. The first version uses an enum and checks it in every method:

class Order {
    private OrderStatus status = OrderStatus.NEW;

    void pay() {
        if (status == OrderStatus.NEW) status = OrderStatus.PAID;
        else throw new IllegalStateException("Cannot pay in " + status);
    }
    void ship() {
        if (status == OrderStatus.PAID) status = OrderStatus.SHIPPED;
        else throw new IllegalStateException("Cannot ship in " + status);
    }
    void cancel() {
        if (status == OrderStatus.NEW || status == OrderStatus.PAID) status = OrderStatus.CANCELLED;
        else throw new IllegalStateException("Cannot cancel in " + status);
    }
    // deliver(), refund(), ... each with its own chain of ifs
}

With 5 states and 6 actions you have up to 30 combinations spread across many if blocks. A new state touches every method. The rules of the state machine are hidden in conditions.

Structure and implementation

interface OrderState {
    default void pay(Order o)    { throw new IllegalStateException("Cannot pay in " + name()); }
    default void ship(Order o)   { throw new IllegalStateException("Cannot ship in " + name()); }
    default void cancel(Order o) { throw new IllegalStateException("Cannot cancel in " + name()); }
    String name();
}

class NewState implements OrderState {
    public void pay(Order o)    { o.setState(new PaidState()); }
    public void cancel(Order o) { o.setState(new CancelledState()); }
    public String name() { return "NEW"; }
}
class PaidState implements OrderState {
    public void ship(Order o)   { o.setState(new ShippedState()); }
    public void cancel(Order o) { o.setState(new CancelledState()); }     // refund here
    public String name() { return "PAID"; }
}
class ShippedState implements OrderState {
    public String name() { return "SHIPPED"; }          // pay/ship/cancel not allowed
}
class CancelledState implements OrderState {
    public String name() { return "CANCELLED"; }
}

class Order {
    private OrderState state = new NewState();           // initial state

    void pay()    { state.pay(this); }                   // delegate
    void ship()   { state.ship(this); }
    void cancel() { state.cancel(this); }
    void setState(OrderState s) { this.state = s; }
    String status() { return state.name(); }
}

public class StateDemo {
    public static void main(String[] args) {
        Order order = new Order();
        order.pay();
        order.ship();
        System.out.println(order.status());      // SHIPPED
        order.cancel();                          // throws IllegalStateException
    }
}

Each state class contains only the rules for that state, in one place. Illegal actions fall back to the default method that throws. A new state (for example RETURNED) is a new class and changes only the states that can lead to it. The transitions are visible and testable.

Variations: states can be stateless singletons (shared instances or enum constants) to avoid creating objects; an enum with abstract methods per constant is a compact Java form of State when the states carry no data; and for big workflows the Spring State Machine project or a workflow engine provides a ready framework.

State in the JDK and Spring

  • Thread.State is an enum of states, but the thread's behaviour is inside the JVM, not State classes.
  • Spring State Machine (a separate project) and workflow engines such as Camunda implement the idea at framework level.
  • JDBC Connection (open, in transaction, closed), TCP sockets and media players are classic state-driven objects.
  • The Java 17+ sealed interface with records and a pattern-matching switch is a modern, compact alternative for immutable state: each state is a record, and a pure function next(state, event) returns the new state.

Pros

  • Removes big status conditionals; one class per state (SRP, OCP).
  • Transitions are explicit and easy to test.
  • Illegal operations are handled in one default place.

Cons

  • Many small classes, even for a simple life cycle.
  • Transition rules are spread across state classes; the whole picture needs a diagram.
  • States need access to the context, adding coupling between them.

When NOT to use State

  • When there are two or three states with a few simple rules: an enum and a switch are clearer.
  • When the status is just data stored in a database and no behaviour changes with it.
  • When the workflow is long, configurable, or owned by the business: use a workflow engine.

In real projects

Order, payment, ticket, loan and shipment life cycles are all state machines. Whichever way you code them, also enforce the rule in the database (a status column with allowed values) and protect transitions from concurrent updates (optimistic locking with @Version), or two requests can move the same order in conflicting ways.

Interview: State

  • What problem does State solve? Large if/else or switch blocks on a status field, repeated in every method.
  • State vs Strategy? Same shape. State changes itself over time and knows transitions; Strategy is chosen by the client and is independent.
  • How would you model a vending machine or an order life cycle? State pattern or a state machine; draw the state diagram first.

Chain of Responsibility: pass a request along a chain of handlers

Chain of Responsibility links handlers in a sequence; each one either handles the request, changes it, or passes it to the next, so the sender does not know which handler will act; servlet filters and the Spring Security filter chain work this way.

Intent: avoid coupling the sender of a request to its receiver by giving more than one object a chance to handle the request.

The problem

Before an order is accepted, it must pass several checks: the cart is not empty, the customer is not blocked, stock is available, the payment limit is not exceeded, and the pincode is serviceable. Putting everything in one method gives a long list of ifs that you cannot reorder, reuse or test one by one. Some checks apply only to some orders, and new checks arrive often. A chain turns each check into a handler with one job.

Implementation: a validation pipeline

import java.util.List;

record OrderRequest(String customerId, List<String> skus, long totalPaise,
                    boolean customerBlocked) { }

class ValidationException extends RuntimeException {
    ValidationException(String message) { super(message); }
}

abstract class OrderCheck {
    private OrderCheck next;

    OrderCheck linkWith(OrderCheck next) {            // returns next, so links can be chained
        this.next = next;
        return next;
    }

    final void check(OrderRequest request) {
        doCheck(request);                              // may throw to stop the chain
        if (next != null) next.check(request);         // otherwise pass it on
    }

    protected abstract void doCheck(OrderRequest request);
}

class NonEmptyCartCheck extends OrderCheck {
    protected void doCheck(OrderRequest r) {
        if (r.skus().isEmpty()) throw new ValidationException("Cart is empty");
    }
}
class CustomerActiveCheck extends OrderCheck {
    protected void doCheck(OrderRequest r) {
        if (r.customerBlocked()) throw new ValidationException("Customer is blocked");
    }
}
class PaymentLimitCheck extends OrderCheck {
    private static final long LIMIT_PAISE = 10_000_000;       // Rs 1,00,000
    protected void doCheck(OrderRequest r) {
        if (r.totalPaise() > LIMIT_PAISE) throw new ValidationException("Above payment limit");
    }
}

public class ChainDemo {
    public static void main(String[] args) {
        OrderCheck chain = new NonEmptyCartCheck();
        chain.linkWith(new CustomerActiveCheck()).linkWith(new PaymentLimitCheck());

        chain.check(new OrderRequest("C1", List.of("SKU-1"), 50000, false));   // passes
        System.out.println("First order OK");
        try {
            chain.check(new OrderRequest("C2", List.of("SKU-2"), 20_000_000, false));
        } catch (ValidationException e) {
            System.out.println("Rejected: " + e.getMessage());
        }
    }
}

Order matters: put cheap checks first and expensive ones (database, remote calls) last. This example is a validation chain, where every handler runs unless one fails. There are two styles of chain:

  • First-handler-wins (classic GoF): the request is passed on until one handler handles it and stops. Examples: exception handling (the first matching catch), a support escalation (agent, then manager, then director), approval by amount.
  • Pipeline (everyone participates): each handler does its part and passes on, possibly modifying the request or the response. Examples: servlet filters, middleware, validation.

A list-based version

The linked-node chain is the textbook form. In day-to-day Java, a List of handlers is often simpler, and Spring will inject it for you in @Order:

public interface OrderValidator {
    void validate(OrderRequest request);                  // throws ValidationException
}

@Service
class OrderValidationService {
    private final List<OrderValidator> validators;        // every @Component, in @Order

    OrderValidationService(List<OrderValidator> validators) { this.validators = validators; }

    void validate(OrderRequest request) {
        validators.forEach(v -> v.validate(request));
    }
}

Chain of Responsibility in the JDK and Spring

  • Servlet filters: Filter.doFilter(request, response, chain); each filter calls chain.doFilter(...) to continue, or returns without calling it to stop the request (for example, when authentication fails).
  • Spring Security: a SecurityFilterChain is an ordered chain of filters (CORS, CSRF, authentication, authorization, ...); the request passes through each, and any filter can reject it. FilterChainProxy holds the chains. See Security.
  • Spring MVC: HandlerInterceptors run in order before and after a controller.
  • Java: a series of catch blocks; java.util.logging handlers and parent loggers; class loader delegation to the parent class loader first.
  • Middleware in Express, ASP.NET and API gateways follow the same structure.
@Component
public class RequestTimingFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain)
            throws ServletException, IOException {
        long start = System.nanoTime();
        try {
            chain.doFilter(request, response);            // pass to the next handler
        } finally {
            long ms = (System.nanoTime() - start) / 1_000_000;
            log.info("{} {} took {} ms", request.getMethod(), request.getRequestURI(), ms);
        }
    }
}

(Imports and a log field omitted; jakarta.servlet packages in Boot 3.x and 4.x.)

Pros

  • Decouples sender from receivers; the sender needs one entry point.
  • Each handler has one job; add, remove or reorder handlers freely (SRP, OCP).
  • Easy to test each handler alone.

Cons

  • No guarantee that a request is handled (first-wins chains may fall off the end).
  • Hard to debug: the flow is spread across many classes.
  • A mis-ordered chain gives wrong behaviour; a handler that forgets to call next silently cuts the chain.
  • Long chains add per-request cost.

When NOT to use Chain of Responsibility

  • When there are only two or three fixed checks: sequential statements are clearer.
  • When you need a known, unique receiver: call it directly.
  • When all checks must be reported together (show all validation errors): run a list of validators and collect results, not a chain that stops at the first failure.

Interview: Chain of Responsibility

  • What is it, and where is it in Spring? A chain of handlers where each may handle or forward; servlet filters and the Spring Security filter chain.
  • What happens if a filter does not call chain.doFilter? The request stops there; the target servlet or controller is never reached (used on purpose to reject).
  • Chain vs Decorator? Both wrap/forward to a next object. A decorator always delegates and adds behaviour; a chain handler may stop the flow.

Template Method: a fixed skeleton with steps that subclasses fill in

Template Method defines the steps of an algorithm in a base class method and lets subclasses supply some of the steps, so the order is fixed and shared while the details vary; Spring's JdbcTemplate applies the same idea with callbacks.

Intent: define the skeleton of an algorithm in an operation, deferring some steps to subclasses, so subclasses can redefine certain steps without changing the algorithm's structure.

The problem

You export reports as CSV, Excel and PDF. Every export does the same things in the same order: fetch the data, filter it, build the header, write each row, write the footer, close the output. Only the format-specific steps differ. If each exporter is written separately, the common steps are copy-pasted and a fix in one is missed in the others (a DRY failure). Template Method keeps the order in one place.

Implementation

import java.util.List;

record Row(String name, long amountPaise) { }

abstract class ReportExporter {

    public final String export(List<Row> rows) {         // the template method: final!
        StringBuilder out = new StringBuilder();
        out.append(header()).append('\n');
        int count = 0;
        for (Row row : selectRows(rows)) {                 // step with a default
            out.append(formatRow(row)).append('\n');
            count++;
        }
        out.append(footer(count));
        return out.toString();
    }

    protected abstract String header();                    // must be provided
    protected abstract String formatRow(Row row);          // must be provided

    protected List<Row> selectRows(List<Row> rows) {      // hook: optional override
        return rows;
    }
    protected String footer(int count) {                   // hook with a default
        return "Total rows: " + count;
    }
}

class CsvExporter extends ReportExporter {
    protected String header() { return "name,amount"; }
    protected String formatRow(Row r) { return r.name() + "," + r.amountPaise() / 100.0; }
}

class PositiveOnlyHtmlExporter extends ReportExporter {
    protected String header() { return "<tr><th>Name</th><th>Amount</th></tr>"; }
    protected String formatRow(Row r) {
        return "<tr><td>" + r.name() + "</td><td>" + r.amountPaise() / 100.0 + "</td></tr>";
    }
    @Override protected List<Row> selectRows(List<Row> rows) {          // override a hook
        return rows.stream().filter(r -> r.amountPaise() > 0).toList();
    }
}

public class TemplateMethodDemo {
    public static void main(String[] args) {
        List<Row> rows = List.of(new Row("Asha", 150000), new Row("Ravi", -5000));
        System.out.println(new CsvExporter().export(rows));
        System.out.println(new PositiveOnlyHtmlExporter().export(rows));
    }
}

Three kinds of steps appear in a template: abstract steps that every subclass must implement, hooks with a default that a subclass may override, and fixed steps in the base class. Declare the template method final so that subclasses cannot change the order. This is the Hollywood principle: "don't call us, we'll call you". The base class calls the subclass, not the other way round.

Callback style: Spring's templates

Inheritance is not the only way. Spring's JdbcTemplate, TransactionTemplate, RestTemplate and JmsTemplate use the same idea with callbacks (lambdas or small objects) instead of subclasses: the template owns the boring, error-prone skeleton (open connection, create statement, handle exceptions, close resources) and your callback supplies the variable part.

// The template does: get connection, prepare statement, run it, loop the result set,
// translate SQLException, close everything. You provide only the row mapping:
List<Employee> list = jdbcTemplate.query(
        "SELECT id, name, salary FROM employees WHERE dept_id = ?",
        (rs, rowNum) -> new Employee(rs.getLong("id"), rs.getString("name"),
                                     rs.getLong("salary")),     // RowMapper callback
        10);

// TransactionTemplate: begin, run your code, commit or roll back
Long id = transactionTemplate.execute(status -> {
    repository.save(order);
    return order.id();
});

The callback version is a Strategy-like design (composition), but the structure "fixed skeleton plus a variable step" is Template Method. Compare: inheritance-based Template Method uses extends; callback-based uses a lambda passed in.

Template Method in the JDK and frameworks

  • AbstractList, AbstractMap, AbstractSet: you implement get(int) and size() (for an AbstractList) and the class gives you iterator(), indexOf, equals, hashCode and more, written in terms of those steps. This is a very common interview example.
  • InputStream.read(byte[]) is built on the single abstract read(); Reader and Writer likewise.
  • HttpServlet.service() inspects the HTTP method and calls doGet, doPost, etc., which you override.
  • AbstractApplicationContext.refresh() in Spring is a famous template method; JdbcTemplate, JmsTemplate, OncePerRequestFilter.doFilter (calls your doFilterInternal) and AbstractController do the same.
  • JUnit's @BeforeEach / test / @AfterEach life cycle is a template method run by the framework.

Pros

  • Removes duplicated skeleton code (DRY).
  • The framework controls the order; subclasses cannot break it.
  • Easy way to offer extension points (hooks).

Cons

  • Uses inheritance: subclasses are tied to the base class (fragile base class; Liskov must hold).
  • The more steps and hooks, the harder to know what to override.
  • One parent only; you cannot combine two templates.
  • Hard to read: the control flow jumps between base and subclass.

When NOT to use Template Method

  • When the variation can be a Strategy passed in (composition): it is more flexible and avoids inheritance. Many modern designs replace Template Method with Strategy or callbacks.
  • When there is only one implementation.
  • When the subclass would need to change the order of steps. The skeleton is then not really fixed.

Common mistakes

  • Forgetting final on the template method, so a subclass overrides the whole algorithm.
  • Calling an overridable method from a base-class constructor: the subclass method runs before the subclass fields are initialised.
  • Too many abstract methods: the subclass becomes a form to fill in. Prefer a few steps plus hooks with defaults.

Interview: Template Method

  • What is it? A base class fixes the algorithm's steps; subclasses override some steps. Example: report exporter, AbstractList.
  • Template Method vs Strategy? Template Method varies steps through inheritance (compile time); Strategy varies the whole algorithm through composition (run time).
  • Which Spring classes use it? JdbcTemplate, TransactionTemplate, AbstractApplicationContext.refresh.
  • What is the Hollywood principle? "Don't call us, we'll call you": the framework calls your code.

Adapter vs Decorator vs Proxy vs Facade

All four wrap other objects, but they differ in intent: Adapter changes an interface, Decorator adds behaviour, Proxy controls access, and Facade simplifies a whole subsystem.

These four structural patterns look alike in a class diagram: one class holds a reference to another and forwards calls. Interviewers ask for the difference because the structure is the same and only the intent separates them. The fastest way to decide is to ask what the wrapper does to the interface and to the behaviour.

How to choose

  1. Do you need to call a class whose interface does not match what your code expects, and you cannot change it? Adapter.
  2. Do you want to add a feature (logging, caching, compression) to a class while keeping its interface, in combinations that the caller picks? Decorator.
  3. Do you want to control whether, when or how the real object is reached (lazy, permission, remote, transaction), without the caller knowing? Proxy.
  4. Do you have many classes and want one easy entry point for a common job? Facade.

The same problem, four ways

Imagine a payment library:

  • Adapter: the vendor's method is makePayment(card, rupees, currency); you wrap it as pay(PaymentRequest).
  • Decorator: a LoggingGateway and a RetryingGateway that implement PaymentGateway and wrap another gateway, stacked as you like.
  • Proxy: a FraudCheckingGatewayProxy that decides whether the call goes through at all, or a Spring proxy that opens a transaction around it.
  • Facade: a CheckoutFacade.checkout(cart) that calls inventory, payment and shipping.

Blurry borders

  • Decorator and Proxy have the same structure. A decorator is usually built by the client to add a feature; a proxy is often hidden from the client, and it often creates or finds the real object itself.
  • A caching wrapper can be called either a caching proxy or a caching decorator. Name it after the dominant reason: "adds a feature" or "controls access".
  • A Spring AOP proxy that adds behaviour around a call is a proxy in mechanism and a decorator in effect.
  • An adapter that also wraps several objects starts to look like a facade. Keep adapters one-to-one.

Interview: the four-way question

  • Answer in one line each: Adapter converts, Decorator enhances, Proxy controls, Facade simplifies.
  • Give one JDK or Spring example each: InputStreamReader, BufferedReader, @Transactional proxy, SLF4J or JdbcTemplate.
  • Add that Decorator and Proxy have the same structure and differ in intent.

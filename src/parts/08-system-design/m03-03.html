Design a library management system

Separate the idea of a book (title, author) from a physical copy that can be loaned; model members, loans with due dates and a fine Strategy, and make check-out of one copy atomic.

Requirements and assumptions

Functional:

  • The library holds books; each book can have several physical copies, each with a barcode.
  • Members search books by title or author, borrow a copy and return it.
  • A member may hold at most 5 loans; a loan lasts 14 days.
  • Late returns cost a fine per overdue day.

Non-functional: two members cannot borrow the same copy; fine rules must be easy to change.

Assumptions: one library branch, in-memory, reservations and notifications are extensions, librarians are not modelled as separate roles in the core code.

Entities and relationships

The key insight: Book and BookCopy are two classes. "Clean Code" is a book (one title, one ISBN); the three shelf copies are BookCopy objects. Status belongs to the copy, not the book.

Key design decisions

  • Book vs copy split avoids a "copies available" integer that must be kept in sync with who holds what.
  • Loan as an entity (not just a field) gives you due date, history and the fine calculation a home. Many-to-many "member borrows book" almost always needs a link class with its own data.
  • Strategy for fines (Module 2): per-day today, capped or category-based tomorrow.
  • Search sits behind a method on Library; if asked for many criteria, extract a SearchCriteria interface or use predicates.
  • A Clock is injected so due dates are testable.

Core code: model

import java.time.LocalDate;
import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.Set;

enum CopyStatus { AVAILABLE, LOANED }

record Book(String isbn, String title, String author) { }

class BookCopy {
    private final String barcode;
    private final Book book;
    private CopyStatus status = CopyStatus.AVAILABLE;

    BookCopy(String barcode, Book book) {
        this.barcode = barcode;
        this.book = book;
    }

    String barcode() { return barcode; }
    Book book() { return book; }

    synchronized boolean tryCheckout() {            // check and set in one step
        if (status != CopyStatus.AVAILABLE) return false;
        status = CopyStatus.LOANED;
        return true;
    }

    synchronized void release() { status = CopyStatus.AVAILABLE; }
}

class Member {
    static final int MAX_LOANS = 5;
    private final String id, name;
    private final Set<String> borrowed = new HashSet<>();

    Member(String id, String name) {
        this.id = id;
        this.name = name;
    }

    String id() { return id; }

    synchronized boolean tryAddLoan(String barcode) {
        if (borrowed.size() >= MAX_LOANS) return false;
        return borrowed.add(barcode);
    }

    synchronized void removeLoan(String barcode) { borrowed.remove(barcode); }
}

record Loan(BookCopy copy, Member member, LocalDate issued, LocalDate due) { }

interface FineStrategy {
    long fine(long overdueDays);                    // paise
}

class PerDayFine implements FineStrategy {
    public long fine(long overdueDays) { return Math.max(0, overdueDays) * 200; }
}

Core code: the library service

import java.time.Clock;
import java.time.LocalDate;
import java.time.temporal.ChronoUnit;
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

class Library {
    private static final int LOAN_DAYS = 14;

    private final Map<String, Book> books = new ConcurrentHashMap<>();
    private final Map<String, List<BookCopy>> copies = new ConcurrentHashMap<>();
    private final Map<String, Member> members = new ConcurrentHashMap<>();
    private final Map<String, Loan> loansByBarcode = new ConcurrentHashMap<>();
    private final FineStrategy fines;
    private final Clock clock;

    Library(FineStrategy fines, Clock clock) {
        this.fines = fines;
        this.clock = clock;
    }

    void addMember(Member m) { members.put(m.id(), m); }

    void addBook(Book b, int copyCount) {
        books.put(b.isbn(), b);
        List<BookCopy> list = copies.computeIfAbsent(b.isbn(), k -> new ArrayList<>());
        synchronized (list) {
            for (int i = 0; i < copyCount; i++) {
                list.add(new BookCopy(b.isbn() + "-" + (list.size() + 1), b));
            }
        }
    }

    List<Book> search(String text) {
        String q = text.toLowerCase();
        return books.values().stream()
                .filter(b -> b.title().toLowerCase().contains(q)
                          || b.author().toLowerCase().contains(q))
                .toList();
    }

    Loan checkout(String memberId, String isbn) {
        Member m = members.get(memberId);
        List<BookCopy> list = copies.get(isbn);
        if (m == null || list == null) throw new IllegalArgumentException("Unknown member or book");

        for (BookCopy c : List.copyOf(list)) {
            if (!c.tryCheckout()) continue;               // someone else holds this copy
            if (!m.tryAddLoan(c.barcode())) {              // limit reached: undo
                c.release();
                throw new IllegalStateException("Loan limit reached");
            }
            LocalDate today = LocalDate.now(clock);
            Loan loan = new Loan(c, m, today, today.plusDays(LOAN_DAYS));
            loansByBarcode.put(c.barcode(), loan);
            return loan;
        }
        throw new IllegalStateException("No copy available");
    }

    long returnCopy(String barcode) {
        Loan loan = loansByBarcode.remove(barcode);
        if (loan == null) throw new IllegalArgumentException("Copy is not on loan");
        long overdue = ChronoUnit.DAYS.between(loan.due(), LocalDate.now(clock));
        loan.member().removeLoan(barcode);
        loan.copy().release();
        return fines.fine(overdue);
    }
}
import java.time.Clock;

public class LibraryDemo {
    public static void main(String[] args) {
        Library lib = new Library(new PerDayFine(), Clock.systemDefaultZone());
        lib.addMember(new Member("M1", "Asha"));
        lib.addBook(new Book("978-0132350884", "Clean Code", "Robert C. Martin"), 2);

        Loan loan = lib.checkout("M1", "978-0132350884");
        System.out.println("Due: " + loan.due().isAfter(loan.issued()));
        System.out.println("Fine: " + lib.returnCopy(loan.copy().barcode()));
        System.out.println(lib.search("clean").size());
    }
}

Concurrency

  • BookCopy.tryCheckout is synchronized on the copy: two members racing for the last copy cannot both win.
  • The member's limit is checked inside the member's own lock; if the limit fails we undo the copy checkout. That is a compensating step, simpler than holding two locks.
  • loansByBarcode.remove is atomic, so a double return does not double-charge a fine.

Mistake: a counter on Book

Keeping availableCopies++/-- on Book tempts you into an unsynchronized read-modify-write and loses updates under load. Derive availability from the copies themselves.

Edge cases

  • Same member borrows two copies of the same title: policy question; add a check on the member's loans by ISBN if not allowed.
  • Return of a copy that is not on loan, or an unknown barcode: clean error.
  • Overdue by zero or negative days (early return): Math.max(0, ...) gives no fine.
  • Member with unpaid fines: block new loans (add a check in checkout).
  • Lost copy: a third status LOST and a replacement-cost fee.

Extensions interviewers ask

  • Reservations: a queue of waiting members per ISBN; on return, notify the first one (Observer, Module 2) and hold the copy for 2 days.
  • Different member types (student 3 loans, staff 10): a MembershipPolicy Strategy holding the limit and loan days.
  • Renewals: extend due once if nobody reserved the book; make Loan hold a mutable due date or create a new Loan.
  • Multiple branches: add Branch; copies belong to a branch.
  • Search by many fields: an index map (author to books) or a database full-text index.

What the interviewer is testing

Library management is a favourite "warm-up" LLD problem because it looks easy and hides several design questions. The interviewer wants to see whether you (1) separate the idea of a book from a physical copy, (2) model the link between member and copy as its own thing with dates (a loan), (3) keep rules such as fines and limits out of the entities so they can change, and (4) notice that two members can race for the last copy. Candidates who put an int availableCopies on Book and a borrow() method on Member usually get stuck on all four. The general routine is in The LLD method; here it is applied with the talking points.

Extension in code: membership types and reservations

import java.util.Deque;
import java.util.Map;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentLinkedDeque;

// Strategy: limits and days depend on the membership type
enum Membership {
    STUDENT(3, 14), STAFF(10, 30);

    private final int maxLoans;
    private final int loanDays;
    Membership(int maxLoans, int loanDays) {
        this.maxLoans = maxLoans;
        this.loanDays = loanDays;
    }
    int maxLoans() { return maxLoans; }
    int loanDays() { return loanDays; }
}

// Reservation queue: first come, first served, per ISBN
class ReservationQueue {
    private final Map<String, Deque<String>> waiting = new ConcurrentHashMap<>();

    void reserve(String isbn, String memberId) {
        waiting.computeIfAbsent(isbn, k -> new ConcurrentLinkedDeque<>())
               .addLast(memberId);
    }

    Optional<String> nextFor(String isbn) {
        Deque<String> q = waiting.get(isbn);
        return q == null ? Optional.empty() : Optional.ofNullable(q.pollFirst());
    }
}

// Observer: told when a copy comes back, so it can notify the next member
interface ReturnListener {
    void onCopyReturned(String isbn, String nextMemberId);
}

In returnCopy you would call reservations.nextFor(isbn) and, if a member id is present, notify the listener and keep the copy in a RESERVED state until a deadline. Replacing the fixed MAX_LOANS and LOAN_DAYS constants with a field of type Membership on Member touches only those two places; Library asks the member for its limits.

Concurrency: from JVM locks to database constraints

  • In memory: the check-and-set on BookCopy is atomic because both steps are inside one synchronized method. Never hold two locks at once (copy and member) unless you always take them in the same order, or you invite a deadlock.
  • In a database: the same rule becomes a constraint. In PostgreSQL, a partial unique index guarantees that a copy has at most one open loan, even with many application servers:
CREATE TABLE loan (
    id          BIGSERIAL PRIMARY KEY,
    copy_id     BIGINT NOT NULL REFERENCES book_copy(id),
    member_id   BIGINT NOT NULL REFERENCES member(id),
    issued_on   DATE   NOT NULL,
    due_on      DATE   NOT NULL,
    returned_on DATE
);

-- at most one active loan per copy: the second insert fails
CREATE UNIQUE INDEX one_active_loan_per_copy
    ON loan (copy_id) WHERE returned_on IS NULL;

The application catches the unique-violation error, treats it as "someone else took this copy" and tries the next copy. This is the same idea as in Concurrency in LLD: make the database the final referee.

Wrong: availability as a counter

class Book {
    int available = 3;
    boolean borrow() {
        if (available > 0) { available--; return true; }   // race
        return false;
    }
}

Right: state lives on each copy

for (BookCopy c : copies) {
    if (c.tryCheckout()) {          // atomic check-and-set on one copy
        return new Loan(c, member, today, today.plusDays(14));

}

Rules

  • A Book is a title; a BookCopy is a physical item with its own barcode and status.
  • Limits, loan days and fines are policies, not constants buried in the entities.
  • Check-and-update of a copy's status must be one atomic step.

Conventions

  • Give Loan the dates and let it answer "is it overdue on this day?" rather than computing in the service.
  • Inject a Clock; in tests use Clock.fixed(...) to test fines without waiting.
  • Keep search in its own method or class (CatalogSearch) so you can later swap the in-memory filter for a database query.

Edge cases and exceptions

  • Returning a copy twice: loansByBarcode.remove returns null the second time, so you throw IllegalArgumentException and charge no second fine.
  • Crash between "copy marked loaned" and "loan saved": in a database use one transaction; in memory the compensating release() covers the limit failure but not a JVM crash, which is why real systems persist.
  • A member returns a book after the library's closing time: the policy (count that day or not) is a requirement; ask the interviewer.

How to present this in 45 minutes

  1. 5 min: ask about member types, limits, fines, reservations, branches.
  2. 7 min: diagram; stress Book vs BookCopy and Loan as a link entity.
  3. 20 min: code BookCopy, Loan, Library.checkout/returnCopy.
  4. 8 min: concurrency on the last copy, edge cases, then reservations with Observer.

Interview: sentences that score points

  • "I separate Book from BookCopy so availability is derived, not a counter I must keep in sync."
  • "Loan is an association class: it carries the due date, so fines and history have a home."
  • "Fines are a Strategy; membership limits are another small policy. Neither is hard-coded."
  • "Two members racing for the last copy are handled by an atomic check-and-set on the copy; in a database I would add a unique partial index."
  • "For reservations I would add a queue per ISBN and an Observer to notify the next member."

Design a vending machine with the State pattern

A vending machine behaves differently depending on whether it is idle, holds money or is out of service, so give each situation its own State class and let the machine delegate every action to its current state instead of using nested if statements.

Requirements and assumptions

  • The machine sells products identified by a code (A1, B2) with a price and a stock count.
  • Flow: insert money, choose a product, receive the product and change.
  • The user may cancel before choosing and gets a refund.
  • Reject: choosing without money, not enough money, sold-out product, unknown code.
  • An admin can refill stock (separate API, not covered by user states).
  • Assumptions: money is accepted as a total amount in paise (no coin hardware), change is always available, one user at a time, the machine object is shared by the keypad, so its methods are synchronized.

The state machine first

Draw this before the class diagram: states are the nodes, user actions are the arrows. Each state decides what every action means. In Idle, "select product" is an error; in HasMoney, "select product" tries to sell.

Key design decisions

  • State pattern (Module 2): the alternative is a switch (state) inside every method. Adding an OutOfServiceState then means editing every switch; with State it is one new class.
  • Default methods throw IllegalStateException, so each concrete state overrides only what is valid for it.
  • The machine owns data (balance, inventory); states own transitions. States are stateless, so they could be shared, but creating them keeps the code simple.
  • Inventory is a separate class (single responsibility): stock changes do not touch the state logic.

Core code: inventory and state interface

import java.util.HashMap;
import java.util.Map;

record Product(String code, String name, long pricePaise) { }

record Dispense(Product product, long changePaise) { }

class Inventory {
    private final Map<String, Product> products = new HashMap<>();
    private final Map<String, Integer> stock = new HashMap<>();

    void add(Product p, int quantity) {
        products.put(p.code(), p);
        stock.merge(p.code(), quantity, Integer::sum);
    }

    Product find(String code) {
        Product p = products.get(code);
        if (p == null) throw new IllegalArgumentException("Unknown product " + code);
        return p;
    }

    boolean inStock(String code) { return stock.getOrDefault(code, 0) > 0; }

    void take(String code) { stock.merge(code, -1, Integer::sum); }
}

interface VendingState {
    default void insertMoney(VendingMachine m, long paise) {
        throw new IllegalStateException("Cannot insert money now");
    }
    default Dispense select(VendingMachine m, String code) {
        throw new IllegalStateException("Cannot select now");
    }
    default long cancel(VendingMachine m) {
        throw new IllegalStateException("Nothing to cancel");
    }
}

Core code: the two states and the machine

class IdleState implements VendingState {
    @Override
    public void insertMoney(VendingMachine m, long paise) {
        if (paise <= 0) throw new IllegalArgumentException("Amount must be positive");
        m.addBalance(paise);
        m.setState(new HasMoneyState());
    }
    // select and cancel inherit the default: they throw
}

class HasMoneyState implements VendingState {
    @Override
    public void insertMoney(VendingMachine m, long paise) {
        if (paise <= 0) throw new IllegalArgumentException("Amount must be positive");
        m.addBalance(paise);
    }

    @Override
    public Dispense select(VendingMachine m, String code) {
        Product p = m.inventory().find(code);
        if (!m.inventory().inStock(code)) {
            throw new IllegalStateException("Sold out: " + p.name());
        }
        if (m.balance() < p.pricePaise()) {
            throw new IllegalStateException(
                "Insert " + (p.pricePaise() - m.balance()) + " more paise");
        }
        m.inventory().take(code);
        long change = m.balance() - p.pricePaise();
        m.clearBalance();
        m.setState(new IdleState());
        return new Dispense(p, change);
    }

    @Override
    public long cancel(VendingMachine m) {
        long refund = m.balance();
        m.clearBalance();
        m.setState(new IdleState());
        return refund;
    }
}

class VendingMachine {
    private VendingState state = new IdleState();
    private final Inventory inventory;
    private long balance;

    VendingMachine(Inventory inventory) { this.inventory = inventory; }

    synchronized void insertMoney(long paise) { state.insertMoney(this, paise); }
    synchronized Dispense select(String code) { return state.select(this, code); }
    synchronized long cancel() { return state.cancel(this); }

    // used by states
    Inventory inventory() { return inventory; }
    long balance() { return balance; }
    void addBalance(long p) { balance += p; }
    void clearBalance() { balance = 0; }
    void setState(VendingState s) { state = s; }
}

public class VendingDemo {
    public static void main(String[] args) {
        Inventory inv = new Inventory();
        inv.add(new Product("A1", "Cola", 4_000), 2);
        VendingMachine vm = new VendingMachine(inv);

        vm.insertMoney(5_000);
        Dispense d = vm.select("A1");
        System.out.println(d.product().name() + ", change " + d.changePaise());
        try {
            vm.select("A1");                      // back to Idle: not allowed
        } catch (IllegalStateException e) {
            System.out.println("Error: " + e.getMessage());
        }
    }
}

Concurrency

The public methods of VendingMachine are synchronized, which makes each action (check state, change balance, move state) atomic. A physical machine has one keypad, so this is enough. For a networked fleet, each machine is still one object per JVM; the server-side stock count becomes a database row updated with UPDATE ... SET stock = stock - 1 WHERE stock > 0.

Edge cases

  • Money inserted, product sold out: stay in HasMoney so the user can pick another item or cancel.
  • Exact payment: change is 0.
  • Unknown code: IllegalArgumentException before touching stock.
  • Machine cannot make change: add a coin float to the machine and check it before selling (a real constraint; ask about it).
  • Power loss mid-transaction: persist balance, or refund on restart.

Where State differs from Strategy

Both swap an object behind an interface. In Strategy the client chooses the algorithm and it rarely changes during use. In State the object changes itself from one state to the next as events happen, so states know about each other.

Extensions interviewers ask

  • Out-of-service state: add OutOfServiceState where everything throws except cancel; the machine enters it when a sensor fails. No existing state changes.
  • Dispensing as its own state when the motor takes seconds: Idle, HasMoney, Dispensing, then Idle.
  • Coin and note handling: a CoinChanger class with denominations and a greedy change algorithm.
  • Several payment methods: a PaymentMethod Strategy (cash, UPI QR).
  • Sales report and low-stock alerts: an Observer on Inventory.

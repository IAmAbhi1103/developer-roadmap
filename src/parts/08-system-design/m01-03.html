Law of Demeter, Tell Don't Ask and separation of concerns

Talk only to your direct collaborators (Law of Demeter), tell objects what to do instead of pulling their data out and deciding for them (Tell, Don't Ask), and keep different concerns such as web, business and data in different layers (separation of concerns).

These three ideas all reduce coupling. They say the same thing in different words: do not let one class know the inner structure of another.

Law of Demeter ("don't talk to strangers")

The Law of Demeter (LoD), also called the principle of least knowledge, says a method should call methods only on:

  • its own object (this),
  • its parameters,
  • objects it creates, and
  • its direct fields (its friends).

It should not reach through one object to get another and call that one. The warning sign is a chain of getters, sometimes called a train wreck:

Wrong: knows the whole chain

// OrderPrinter knows Order has a Customer, which has an Address, which has a City
String city = order.getCustomer().getAddress().getCity();
if (city.equals("Mumbai")) {
    surcharge = 50;
}

Right: ask your friend

// Order hides how the city is found
if (order.isShippedTo("Mumbai")) {
    surcharge = 50;
}

// in Order
boolean isShippedTo(String city) {
    return customer.livesIn(city);       // Customer hides Address
}

With the first version, a change in how Customer stores an address (say, a list of addresses with a default one) breaks every caller that walked the chain. With the second, only Customer.livesIn changes.

When chains are fine

  • Fluent APIs and builders return the same object: sb.append("a").append("b"), stream.filter(...).map(...), HttpRequest.newBuilder().uri(...).build(). These are not Demeter violations, because every call is on the same kind of object.
  • Plain data structures (records, DTOs, JSON trees) are meant to be navigated: response.user().name().
  • Do not add dozens of one-line wrapper methods mechanically (getCustomerAddressCity()). Ask what the caller really wants to know (isShippedTo), and name that.

Tell, Don't Ask

"Ask" style code pulls data out of an object, makes a decision outside, and pushes the result back. "Tell" style code sends a command and lets the object, which owns the data, decide. The first scatters business rules across callers; the second keeps each rule next to its data. This is encapsulation applied to behaviour.

// ASK: the caller owns the rule, and every caller must repeat it
if (account.getBalance() >= amount && account.getStatus() == Status.ACTIVE) {
    account.setBalance(account.getBalance() - amount);
} else {
    throw new IllegalStateException("Cannot withdraw");
}

// TELL: the account owns the rule
account.withdraw(amount);

// in Account
void withdraw(long amount) {
    if (status != Status.ACTIVE) throw new IllegalStateException("Account not active");
    if (amount > balance) throw new IllegalStateException("Insufficient funds");
    balance -= amount;
}

Notice the symptoms of "ask": many getters and setters, and "service" classes full of ifs that inspect entities. Such an entity with no behaviour is sometimes called an anemic domain model. It is not always wrong (simple CRUD apps live with it), but when rules become complex, move them into the objects that own the data.

Edge cases

  • Queries are fine: order.total() asks for a value. The problem is asking for data in order to decide something the object could decide.
  • Strict Tell, Don't Ask can push presentation logic into entities. Keep formatting and UI decisions out of domain classes.
  • JPA entities and DTOs need getters for frameworks; the principle still applies to the methods you add by hand.

Separation of concerns (SoC)

A concern is a distinct job: showing data, applying business rules, storing data, logging, security. Separation of concerns means each concern lives in its own part of the system with a clear boundary. It is SRP at the scale of layers and modules.

The rules of layering: a controller never builds SQL; a repository never decides discounts; a service never touches HttpServletRequest. Cross-cutting concerns (logging, transactions, security, caching) are separated through aspects and filters, not repeated in each method. In Spring that is what @Transactional and Spring Security do for you, using proxies.

@RestController
class OrderController {
    private final OrderService service;
    OrderController(OrderService service) { this.service = service; }

    @PostMapping("/orders")
    ResponseEntity<OrderResponse> place(@RequestBody @Valid PlaceOrderRequest req) {
        Order order = service.place(req.toCommand());      // no business rules here
        return ResponseEntity.status(201).body(OrderResponse.from(order));
    }
}

Mistakes to avoid

  • Business rules inside controllers or in JavaScript only, because "it was quick".
  • Returning JPA entities from controllers, so the database shape leaks into the public API.
  • Putting @Transactional or SQL in controllers.
  • Splitting into so many layers that a simple field copies through six classes (accidental complexity; KISS).

Interview: coupling principles

  • Law of Demeter? A method should talk only to itself, its parameters, its fields and objects it creates. Avoid a.getB().getC().doIt(). Mention fluent builders as an allowed exception.
  • Tell, Don't Ask? Put the rule in the object that owns the data: account.withdraw(x) rather than reading the balance and setting it from outside.
  • Separation of concerns? Controller, service and repository layers, each with one job; cross-cutting concerns handled by aspects.

Composition over inheritance: from inheritance explosion to Strategy

Use inheritance for a few real is-a relations; for behaviour that varies along several independent directions, hold the behaviours as fields (composition) and combine them at run time, which avoids a class explosion.

The basics are in Core Java · Module 2: has-a versus is-a, the fragile base class, aggregation and composition. This article is the design view: how a hierarchy grows out of control, and the standard refactoring that fixes it.

The problem: inheritance explosion

You are building a notification system. First it sends email. Then SMS. Then someone asks for urgent messages, which must be sent immediately and logged. A natural first design extends the class for every combination:

There are two independent axes: the channel (email, SMS, push) and the priority (normal, urgent, scheduled). With 3 channels and 3 priorities, inheritance needs 9 classes, and each new channel adds 3 more. The urgent logic is copied in every urgent class. This is the class explosion. Worse, the behaviour is fixed at compile time: a message cannot be switched from normal to urgent while running.

The refactoring: extract each axis and compose

  1. Find each direction of variation: channel and delivery policy.
  2. Make an interface for each one.
  3. Give the main class one field per interface, set in the constructor.
  4. Delete the subclasses; combine by passing different parts.
interface Channel {
    void deliver(String to, String message);
}

class EmailChannel implements Channel {
    public void deliver(String to, String message) {
        System.out.println("EMAIL to " + to + ": " + message);
    }
}
class SmsChannel implements Channel {
    public void deliver(String to, String message) {
        System.out.println("SMS to " + to + ": " + message);
    }
}

interface DeliveryPolicy {
    void send(Runnable deliverAction);
}

class Immediate implements DeliveryPolicy {
    public void send(Runnable deliverAction) { deliverAction.run(); }
}
class Delayed implements DeliveryPolicy {
    private final long millis;
    Delayed(long millis) { this.millis = millis; }
    public void send(Runnable deliverAction) {
        java.util.concurrent.CompletableFuture
            .runAsync(deliverAction, java.util.concurrent.CompletableFuture
                .delayedExecutor(millis, java.util.concurrent.TimeUnit.MILLISECONDS));
    }
}

class Notification {
    private final Channel channel;                // composed behaviour 1
    private final DeliveryPolicy policy;          // composed behaviour 2

    Notification(Channel channel, DeliveryPolicy policy) {
        this.channel = channel;
        this.policy = policy;
    }

    void send(String to, String message) {
        policy.send(() -> channel.deliver(to, message));
    }
}

public class NotificationDemo {
    public static void main(String[] args) {
        new Notification(new EmailChannel(), new Immediate()).send("asha@x.com", "Hi");
        new Notification(new SmsChannel(), new Immediate()).send("98100", "OTP 4521");
    }
}
EMAIL to asha@x.com: Hi
SMS to 98100: OTP 4521

Now there is one Notification class, two small channel classes and two small policy classes: 3 + 3 = 6 classes instead of 9, and adding a push channel is one class, not three. Any combination is possible, and you can change either part at run time. This is the Strategy pattern, and also the shape behind Spring dependency injection.

When to choose which

Use inheritance whenUse composition when
There is a true is-a that passes the Liskov testBehaviour varies along more than one axis
The parent is designed for extension (Template Method)You want to change behaviour at run time
You want to share a stable skeleton of an algorithmYou want to test with fake parts
The hierarchy is shallow (2 levels)You want to reuse code from a class that is not a real parent

Rule of thumb

Use interfaces to say what a thing can do, composition to get the code that does it, and inheritance only for a small, stable skeleton. If you cannot say "a B is always usable as an A", do not write B extends A.

Mistakes to avoid

  • Extending a utility class to get its methods (class OrderService extends BaseService with 40 helper methods). Inject helpers instead.
  • "Base" classes that grow into a god-class every subclass depends on.
  • Composition with no interface: holding a concrete PdfWriter field. You get has-a but not swappability.

Why inheritance is risky: the fragile base class

Explosion is only one problem. The deeper one is that a subclass depends on how its parent works inside, not just on what it promises. When the parent changes an internal detail, the child breaks even though no public signature changed. This is the fragile base class problem. The classic case is a set that counts how many elements were ever added:

Wrong: inherits and depends on internals

import java.util.Collection;
import java.util.HashSet;

class CountingSet<E> extends HashSet<E> {
    private int added = 0;
    @Override public boolean add(E e) { added++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) {
        added += c.size();
        return super.addAll(c);     // calls add() for each item inside!
    }
    int added() { return added; }
}
// addAll(List.of("a","b","c")) -> added() == 6, not 3

Right: wraps and delegates

import java.util.Collection;
import java.util.HashSet;
import java.util.Set;

class CountingSet<E> {
    private final Set<E> inner = new HashSet<>();
    private int added = 0;
    boolean add(E e) { added++; return inner.add(e); }
    boolean addAll(Collection<? extends E> c) {
        added += c.size();
        boolean changed = false;
        for (E e : c) changed |= inner.add(e);
        return changed;             // we control exactly what happens
    }
    int added() { return added; }
}

The inherited addAll calls add for every element, so the count doubles. If the JDK ever changed that internal call, the child would break again in the other direction. With composition you depend only on the public contract of Set. For a version that is also a Set, use a Decorator that implements the interface and forwards calls.

The idea in one picture

A second example: order pricing

An e-commerce team writes FestivalOrder extends Order to apply a festival discount, then PrimeFestivalOrder extends FestivalOrder for members, then a GstExemptPrimeFestivalOrder. Each rule multiplies the tree. With composition, an Order holds a PricingRule and a TaxRule, and you assemble the combination per request:

interface PricingRule { long apply(long subtotalPaise); }
interface TaxRule     { long taxOn(long amountPaise); }

class Order {
    private final long subtotal;
    private final PricingRule pricing;
    private final TaxRule tax;

    Order(long subtotal, PricingRule pricing, TaxRule tax) {
        this.subtotal = subtotal;
        this.pricing = pricing;
        this.tax = tax;
    }
    long payable() {
        long net = pricing.apply(subtotal);
        return net + tax.taxOn(net);
    }
}

class Demo {
    public static void main(String[] args) {
        PricingRule festival = s -> s - s / 10;          // 10% off
        PricingRule member   = s -> festival.apply(s) - 5_000;
        TaxRule gst18        = a -> a * 18 / 100;
        System.out.println(new Order(100_000, festival, gst18).payable());
        System.out.println(new Order(100_000, member, gst18).payable());
    }
}

Rules are plain lambdas here, which is the lightest form of composition: behaviour passed as a value.

Composition, delegation and default methods

  • Composition: the object holds other objects and uses them. The parts' lifetime usually belongs to the whole (see the UML note in UML class diagrams).
  • Delegation: the object forwards a call to the held part. This is the mechanism of composition.
  • Interface default methods give shared code without a parent class, but they cannot hold state. They help for small helpers, not for the main logic.
  • Sealed hierarchies (Java 17+) keep inheritance safe by listing the allowed subclasses. Use them for closed sets of variants such as payment results.

In the JDK and Spring

  • Stack extends Vector is a well-known JDK mistake: a stack exposes add(int, E) and get(i). ArrayDeque is the modern choice and does not inherit them.
  • Collections.synchronizedList and the Java I/O wrappers (BufferedReader around a Reader) compose instead of subclassing.
  • Thread versus Runnable: pass a Runnable to a thread instead of extending Thread.
  • Spring: JdbcTemplate and RestTemplate take callbacks and converters; constructor injection of collaborators is composition. Spring Data repositories are interfaces, not base classes you extend with logic.

Comparison

InheritanceComposition
Relationshipis-ahas-a / uses

Rules

  • Never inherit only to reuse code. Inherit only when the Liskov test passes and the parent was designed for extension.
  • If you do design a class for extension, document which methods call which (self-use), or make the class final.
  • Each composed part should be an interface, so it can be replaced.

Conventions

  • Default to final classes; open them to extension on purpose.
  • Pass parts through the constructor and keep them private final.
  • Name the parts by role (Channel, PricingRule), not by kind of class.

When NOT to prefer composition

  • Frameworks that expect you to extend a base class: HttpServlet, OncePerRequestFilter, Exception. Extend them, but keep the subclass thin and move logic into injected collaborators.
  • A real is-a with a stable parent: ArrayList is a List; a Circle is a Shape.
  • Forwarding every method of a wide interface by hand is noise. Use a small IDE-generated delegate, or reconsider (ISP, I: Interface Segregation).

Interview: composition over inheritance

  • Give the reason: inheritance couples the child to the parent's implementation and is fixed at compile time; composition couples to an interface and can change at run time.
  • Use the notification example: channel × priority makes N × M subclasses; composition gives N + M classes.
  • Say which pattern it leads to: Strategy (also Decorator and State).
  • Concede that inheritance is still right for real is-a and designed-for-extension classes.

Interview: follow-ups on composition

  • What is the fragile base class problem? A child that relies on the parent's internal calls breaks when the parent changes. Use the HashSet.addAll counting example.
  • Composition vs aggregation? Both are has-a. In composition the part cannot live without the whole; in aggregation it can.
  • Does "prefer composition" mean never inherit? No. It is a default, not a ban.
  • Which patterns follow from it? Strategy, Decorator, State, Adapter, and dependency injection.

Clean code: naming, small methods, no magic numbers and more

Clean code reads like clear prose: names say what things are, each function does one thing, there are no unexplained numbers, errors are handled separately from the main flow, and comments explain why, not what.

You write code once, and read it many times: when you fix a bug, add a feature, or review a pull request. Clean code (the title of Robert C. Martin's book) optimises for the reader. Each rule below comes with a before and after.

1. Meaningful names

A name should answer what it is, why it exists and how it is used, so that no comment is needed. Use nouns for classes and variables, verbs for methods, and the vocabulary of the business (the domain).

Wrong

int d;                       // elapsed time in days
List<int[]> list1 = getThem();
void proc(Order o, boolean f) { }
class DataManager { }

Right

int elapsedDays;
List<Cell> flaggedCells = findFlaggedCells();
void cancel(Order order, boolean refundIssued) { }
class InvoiceGenerator { }
  • Classes: nouns (OrderValidator); methods: verbs (calculateTotal); booleans: questions (isPaid, hasStock).
  • Avoid noise words (Data, Info, Manager, Util) and encodings (strName, IOrderService is debated; follow your team).
  • Use one word per concept: do not mix fetch, get and retrieve for the same idea.
  • Use searchable names. A name like MAX_RETRIES is easy to find; 3 is not.
  • Length matches scope: i in a three-line loop is fine; a field used across a class needs a full name.

2. Small functions that do one thing

A function should do one thing, at one level of abstraction, and be short enough to see on one screen (many teams aim for under 20 lines). If you can extract a piece with a name that is not just a restatement of the code, extract it.

Wrong: one long method mixing levels

void checkout(Cart cart) {
    for (Item i : cart.items()) {
        if (i.qty() <= 0) throw new IllegalArgumentException();
    }
    long total = 0;
    for (Item i : cart.items()) total += i.price() * i.qty();
    if (total > 100000) total -= total / 10;
    System.out.println("Charging " + total);
}

Right: reads like an outline

void checkout(Cart cart) {
    validate(cart);
    long total = applyBulkDiscount(sum(cart));
    charge(total);
}

3. Few parameters; parameter objects

Zero to two parameters are easy; three is the practical limit; more is a smell. Group related values into an object (parameter object), usually a record:

Wrong: long list, order easy to mix up

createUser("Asha", "Rao", "asha@x.com", "98100", "Pune", "411001", true);

Right: named, grouped, extendable

record Address(String city, String pincode) { }
record NewUser(String firstName, String lastName, String email,
               String phone, Address address, boolean newsletter) { }

createUser(new NewUser("Asha", "Rao", "asha@x.com", "98100",
                       new Address("Pune", "411001"), true));

For many optional values, use a Builder.

4. No boolean flag arguments

A boolean parameter means the method does two things. The call site render(true) says nothing. Split into two methods, or pass an enum.

Wrong

sendMessage(user, text, true);      // true = what?

Right

sendUrgentMessage(user, text);
sendNormalMessage(user, text);
// or: sendMessage(user, text, Priority.URGENT);

5. Guard clauses and early return

Handle the invalid cases first and return or throw. The main path then stays at the left margin without deep nesting (the "arrow anti-pattern").

Wrong: nested

double payment(Employee e) {
    double result;
    if (!e.isDead()) {
        if (!e.isRetired()) {
            result = e.salary();
        } else {
            result = e.pension();
        }
    } else {
        result = 0;
    }
    return result;
}

Right: guard clauses

double payment(Employee e) {
    if (e.isDead()) return 0;
    if (e.isRetired()) return e.pension();
    return e.salary();
}

6. Constants and enums, not magic numbers or strings

A magic number is a literal whose meaning is not obvious. Replace it with a named constant; replace sets of related strings with an enum, so the compiler checks them.

Wrong

if (user.getStatus().equals("A")) { ... }
if (retries > 3) { ... }
long fee = amount * 18 / 100 + 25;

Right

enum AccountStatus { ACTIVE, BLOCKED, CLOSED }
private static final int MAX_RETRIES = 3;
private static final int GST_PERCENT = 18;
private static final long FLAT_FEE_PAISE = 25;

if (user.status() == AccountStatus.ACTIVE) { ... }
if (retries > MAX_RETRIES) { ... }
long fee = amount * GST_PERCENT / 100 + FLAT_FEE_PAISE;

Values like 0, 1 and -1 in obvious contexts (i + 1, list.size() == 0) do not need names. Configuration that differs per environment (URLs, timeouts) belongs in application.yml, not in constants.

7. Comments explain why, not what

If a comment restates the code, delete it or rename the code. Use comments for intent, warnings, a business rule, or the reason for a surprising choice. Javadoc is for public APIs.

// Bad: says what the code already says
i++;   // increment i

// Better: explains a decision the code cannot
// Banks settle on working days only, so a weekend due date moves to Monday (RBI rule).
LocalDate due = nextWorkingDay(requested);

Do not leave commented-out code; version control remembers it (see Git basics). A TODO needs an owner or a ticket number.

8. Error handling as a separate concern

Main logic should not be buried under try/catch blocks and error-code checks. Use exceptions, not magic return values like -1 or null. Keep error mapping in one place (in Spring, @RestControllerAdvice).

// Bad: error codes mixed with the flow
int code = service.transfer(from, to, amount);
if (code == -1) { ... } else if (code == -2) { ... }

// Good: the happy path is clean, the failure is an exception
service.transfer(from, to, amount);      // throws InsufficientFundsException

@RestControllerAdvice
class ApiExceptionHandler {
    @ExceptionHandler(InsufficientFundsException.class)
    ResponseEntity<ErrorBody> onInsufficient(InsufficientFundsException e) {
        return ResponseEntity.status(409).body(new ErrorBody(e.getMessage()));
    }
}
  • Do not catch Exception and ignore it. At least log it, or let it propagate.
  • Return empty collections, not null; use Optional for "maybe a value" return types.
  • Throw specific exceptions with a message that says what failed and with which ID.

9. Small classes and consistent formatting

Keep classes small and focused (SRP). Order members the same way in every file (constants, fields, constructors, public methods, private methods). Use one formatter for the whole team (Google Java Style, Spotless or the IDE formatter in CI) so that diffs show real changes, not whitespace arguments. Keep lines to about 100 to 120 characters.

Checklist before you open a pull request

  • Could a new teammate understand each method name without reading the body?
  • Is any method longer than a screen, or doing "X and Y"?
  • Any literal number or string that has a meaning? Name it.
  • Any boolean parameter, more than three parameters, or deep nesting?
  • Is there dead code, a commented-out block, or a comment that repeats the code?

Cautions

  • Rules are guidelines. A 40-line method that reads as one clear story can beat ten tiny methods that make you jump around.
  • Do not extract a method for every line; extract when the new name adds meaning.
  • Refactor under test. Change structure, not behaviour, and run the tests after each step.

Interview: clean code

  • What is clean code? Code that is easy to read, change and test: good names, small focused functions, no duplication, no magic values.
  • How do you handle a 300-line method? Write tests first, then extract methods with intent-revealing names (Extract Method), group data into objects, and replace conditionals with polymorphism.
  • Why avoid boolean arguments? Call sites are unreadable and the method does two things.

Code smells and the refactoring that fixes each

A code smell is a surface sign that the design has a problem; learn the common smells (long method, large class, primitive obsession, feature envy, shotgun surgery, switch on type, duplicated code, data clumps) and the standard refactoring for each.

A code smell is a pattern in code that is not a bug but hints at a deeper design weakness. The term comes from Kent Beck and Martin Fowler's book Refactoring. A refactoring is a small change that improves structure without changing behaviour. The rule: smell, then test, then refactor in small steps, then test again.

Example 1: primitive obsession → value object

Primitive obsession means using String, int and long for domain ideas. A String can hold anything, so every method that receives an email must check it again, or forget to.

// Smell: any string is accepted; amount might be rupees or paise?
void register(String email, String phone, long amount) { /* ... */ }
register("98100", "asha@x.com", 5);        // arguments swapped: compiles fine!

// Refactored: the type carries the rule
record Email(String value) {
    Email {                                          // compact constructor validates once
        if (value == null || !value.matches("[^@\\s]+@[^@\\s]+\\.[^@\\s]+")) {
            throw new IllegalArgumentException("Invalid email: " + value);
        }
    }
}
record Money(long paise) {
    Money {
        if (paise < 0) throw new IllegalArgumentException("Negative money");
    }
    Money plus(Money other) { return new Money(paise + other.paise); }
}
void register(Email email, Phone phone, Money deposit) { /* ... */ }

Swapping arguments is now a compile error, and validation lives in one place. (Phone would be another record.)

Example 2: feature envy → Move Method

// Smell: InvoicePrinter is more interested in Order's data than its own
class InvoicePrinter {
    long total(Order order) {
        long sum = 0;
        for (OrderItem i : order.items()) sum += i.unitPaise() * i.qty();
        return sum;
    }
}

// Fix: the method moves to the class that owns the data
record Order(String id, List<OrderItem> items) {
    long total() {
        return items.stream().mapToLong(i -> i.unitPaise() * i.qty()).sum();
    }
}

Example 3: switch on type → polymorphism

This one is covered in OCP. A quick cousin: if (employee.type == MANAGER) ... else if (type == ENGINEER) ... repeated in pay(), bonus() and title(). Replace the type code with an interface or an abstract class Employee with one subclass per type, or a Strategy/State object when the type changes at run time.

Example 4: data clumps → Extract Class

// Smell: street, city, state, pincode travel together in many signatures
void ship(String street, String city, String state, String pincode) { }
boolean deliverable(String street, String city, String state, String pincode) { }

// Fix
record Address(String street, String city, String state, String pincode) {
    boolean isMetro() { return List.of("Mumbai", "Delhi", "Chennai", "Kolkata").contains(city); }
}
void ship(Address to) { }
boolean deliverable(Address to) { }

Once the clump becomes a class, behaviour like isMetro() finds a natural home.

Shotgun surgery versus divergent change

They are opposites, and interviewers like to ask. Divergent change: one class changes for many reasons (too much in one place; split it). Shotgun surgery: one reason for change touches many classes (one concern scattered; gather it). Both come from wrong boundaries.

Safe refactoring workflow

  1. Make sure tests cover the code. If none, write characterization tests that record current behaviour.
  2. Change one small thing (rename, extract, move).
  3. Run the tests. If red, undo and try a smaller step.
  4. Commit often, so each step can be reverted alone.

Tip: let the IDE do it

IntelliJ IDEA and Eclipse have automated, behaviour-preserving Extract Method, Extract Class, Move, Rename, Introduce Parameter Object and Inline. Static analysis tools such as SonarQube report long methods and duplication. Use them as hints, not as judges.

Interview: code smells

  • What is a code smell? A sign of a design problem, not a bug. Name three and the fix for each: long method (Extract Method), switch on type (polymorphism), data clumps (parameter object).
  • What is refactoring? Improving structure without changing behaviour, in small, tested steps.
  • Feature envy? A method uses another object's data more than its own; move it there.

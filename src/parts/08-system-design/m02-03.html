Proxy: control access with a stand-in, and how Spring AOP uses it

A proxy is a stand-in object with the same interface as the real one that controls access to it (lazy loading, security, caching, logging, transactions); Spring creates proxies, either JDK dynamic or CGLIB, to implement @Transactional, @Cacheable and @Async.

Intent: provide a surrogate or placeholder for another object to control access to it.

The problem

Sometimes you cannot or should not let clients touch the real object directly. It may be expensive to create (a large report or image), it may need an access check (only admins can delete), it may live on another machine, or you want to add cross-cutting work (a transaction, a log line) without touching its code. The proxy looks exactly like the real object to the client, but it stands in front and decides when and whether to forward the call.

A hand-written protection proxy

enum Role { VIEWER, ADMIN }
record User(String name, Role role) { }

interface DocumentService {
    String read(String id);
    void delete(String id);
}

class RealDocumentService implements DocumentService {
    public String read(String id) { return "Contents of " + id; }
    public void delete(String id) { System.out.println("Deleted " + id); }
}

class SecureDocumentProxy implements DocumentService {
    private final DocumentService target;
    private final User current;

    SecureDocumentProxy(DocumentService target, User current) {
        this.target = target;
        this.current = current;
    }

    public String read(String id) {
        return target.read(id);                          // anyone may read
    }

    public void delete(String id) {
        if (current.role() != Role.ADMIN) {              // access control lives here
            throw new SecurityException(current.name() + " may not delete");
        }
        target.delete(id);
    }
}

public class ProxyDemo {
    public static void main(String[] args) {
        DocumentService real = new RealDocumentService();
        DocumentService asViewer = new SecureDocumentProxy(real, new User("Ravi", Role.VIEWER));
        System.out.println(asViewer.read("D1"));
        asViewer.delete("D1");                           // throws SecurityException
    }
}

A virtual (lazy) proxy

interface Report { String content(); }

class HeavyReport implements Report {
    HeavyReport() { System.out.println("Loading 200 MB report..."); }
    public String content() { return "big report"; }
}

class LazyReport implements Report {
    private Report real;                                  // not created yet
    public String content() {
        if (real == null) real = new HeavyReport();       // created on first use
        return real.content();
    }
}

(Not thread-safe as written; add synchronized or a holder if several threads can call content().)

The JDK dynamic proxy

Writing one proxy class per interface is tedious. The JDK can create a proxy at run time for any interface, using java.lang.reflect.Proxy and an InvocationHandler that receives every call.

import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Proxy;

interface Greeter { String greet(String name); }

public class DynamicProxyDemo {
    public static void main(String[] args) {
        Greeter real = name -> "Hello, " + name;

        InvocationHandler handler = (proxy, method, methodArgs) -> {
            System.out.println("before " + method.getName());
            Object result = method.invoke(real, methodArgs);     // call the real object
            System.out.println("after " + method.getName());
            return result;
        };

        Greeter proxy = (Greeter) Proxy.newProxyInstance(
                Greeter.class.getClassLoader(),
                new Class<?>[] { Greeter.class },
                handler);

        System.out.println(proxy.greet("Asha"));
    }
}

after greet

One handler can add logging, timing or transactions to any interface. This is the core idea behind Spring AOP.

How Spring AOP uses proxies

When you annotate a bean with @Transactional, @Cacheable, @Async or @PreAuthorize, Spring does not change your class. After creating the bean, a BeanPostProcessor wraps it in a proxy and puts the proxy in the container. Everyone who injects your bean gets the proxy. When a method is called, the proxy runs the extra work (begin transaction, check cache, run on another thread), calls your real method, and then finishes (commit or rollback).

Spring has two ways to build the proxy:

JDK dynamic proxyCGLIB proxy
HowImplements the target's interfacesGenerates a subclass of the target class at run time
NeedsThe bean implements at least one interfaceA non-final class; methods must be non-final and non-private to be intercepted
Inject asThe interface type onlyThe class type or an interface
Default in Spring BootNoYes: Boot sets spring.aop.proxy-target-class=true, so class-based (CGLIB) proxies are used even when interfaces exist

Spring Framework itself uses JDK proxies when the bean has interfaces and CGLIB otherwise, unless you set proxyTargetClass. In modern Boot applications, you can assume CGLIB. A related detail: a @Transactional class declared final cannot be subclassed, so proxying fails or the annotation is silently useless in some setups (Kotlin classes are final by default, which is why the Spring Kotlin plugin opens them).

The self-invocation pitfall

The proxy only sees calls that come through it. When a method calls another method of the same class using this, the call goes straight to the real object and skips the proxy, so the advice does not run.

@Service
public class InvoiceService {

    public void process(Long id) {
        // ... some work
        archive(id);                 // same as this.archive(id): NO proxy, NO transaction!
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void archive(Long id) {
        // expected: a new transaction. Actual (when called from process): none or the caller's.
    }
}

The same problem hits @Cacheable, @Async and @Retryable. The fixes, best first:

  1. Move the method to another bean (ArchiveService) and inject it. The call then goes through its proxy. This is usually also a better design.
  2. Inject the bean into itself (self-injection, often with @Lazy) and call through it. Works but looks odd.
  3. Use AspectJ weaving (compile-time or load-time), which changes the bytecode instead of using proxies, so self-calls work.
  4. Expose the proxy with @EnableAspectJAutoProxy(exposeProxy = true) and call ((InvoiceService) AopContext.currentProxy()).archive(id). Works but couples your code to Spring AOP.

Related traps: the annotation on a private method is not applied by proxy-based AOP; @Transactional on public methods is the safe habit across Spring versions; and only a RuntimeException or Error triggers rollback by default (checked exceptions need rollbackFor). Full coverage is in the Spring notes (Data access).

Proxies in the JDK, Hibernate and elsewhere

  • java.lang.reflect.Proxy; Collections.unmodifiableList is also proxy-like.
  • Hibernate returns a proxy for getReference and for LAZY associations. Touching it outside the session throws LazyInitializationException.
  • Mockito creates proxy objects (mocks) at run time, as do Feign and Spring Data repositories (an interface you write becomes a proxy with a generated implementation).
  • Remote proxies: gRPC and Feign client stubs hide network calls behind a Java interface.

Pros

  • Adds access control, laziness, caching or transactions without changing the real class.
  • Client code is unchanged because the interface is the same (OCP).
  • One handler can serve many classes (dynamic proxy / AOP).

Cons

  • Magic: behaviour that is invisible in the code, hard to debug (the self-invocation trap).
  • Extra indirection and a small cost per call; stack traces are longer.
  • equals, getClass() and instanceof may behave unexpectedly with proxies.
  • CGLIB needs non-final classes and methods; JDK proxies need interfaces.

When NOT to use a hand-written Proxy

  • When the same concern applies to many classes: use AOP or an annotation, not one proxy class per service.
  • When simple code at the call site does the job (one if for a permission check).
  • When the "proxy" changes the interface or adds new behaviour the client must know about. That is a Decorator or an Adapter (see the comparison).

Interview: Proxy and Spring AOP

  • How does @Transactional work? A proxy wraps the bean; it begins a transaction, calls the target, then commits, or rolls back on a runtime exception.
  • JDK proxy vs CGLIB? Interface-based vs subclass-based; Boot defaults to CGLIB.
  • Why does @Transactional not work when one method calls another in the same class? The call bypasses the proxy. Fix by moving the method to another bean.
  • Proxy vs Decorator? Same structure. Proxy controls access to the object (often creating or locating it itself); Decorator adds behaviour the client composes.
  • Name the types of proxy. Virtual, protection, remote, caching.

Strategy: interchangeable algorithms behind an interface

Strategy puts each algorithm in its own class behind a common interface, so the code that needs the algorithm (the context) can pick or swap it at run time, replacing long if/else or switch chains.

Intent: define a family of algorithms, encapsulate each one, and make them interchangeable.

The problem

A checkout supports UPI, credit card, net banking and cash on delivery. A first draft puts everything into one method:

public Receipt pay(String method, long paise) {
    if (method.equals("UPI")) {
        // validate VPA, call UPI API, handle callbacks ...
    } else if (method.equals("CARD")) {
        // 3-D Secure, card network fees, ...
    } else if (method.equals("NETBANKING")) {
        // redirect to bank ...
    } else if (method.equals("COD")) {
        // add handling fee ...
    }
    throw new IllegalArgumentException(method);
}

Each branch is a different algorithm that changes for different reasons. The method grows with every new option, branches cannot be tested alone, and the same if chain is probably repeated for refunds and reports. This is the Open/Closed violation from Module 1. Strategy is the fix.

Implementation

import java.util.EnumMap;
import java.util.Map;

enum PaymentMethod { UPI, CARD, COD }
record Receipt(String mode, long chargedPaise) { }

interface PaymentStrategy {                              // the strategy
    Receipt pay(long amountInPaise);
}

class UpiPayment implements PaymentStrategy {
    public Receipt pay(long amount) { return new Receipt("UPI", amount); }
}
class CardPayment implements PaymentStrategy {
    public Receipt pay(long amount) {
        long fee = amount * 2 / 100;                      // 2% card fee
        return new Receipt("CARD", amount + fee);
    }
}
class CodPayment implements PaymentStrategy {
    public Receipt pay(long amount) { return new Receipt("COD", amount + 4000); }   // Rs 40
}

class CheckoutService {                                   // the context
    private final Map<PaymentMethod, PaymentStrategy> strategies =
            new EnumMap<>(PaymentMethod.class);

    CheckoutService() {
        strategies.put(PaymentMethod.UPI, new UpiPayment());
        strategies.put(PaymentMethod.CARD, new CardPayment());
        strategies.put(PaymentMethod.COD, new CodPayment());
    }

    Receipt checkout(PaymentMethod method, long amountInPaise) {
        PaymentStrategy strategy = strategies.get(method);       // choose at run time
        if (strategy == null) throw new IllegalArgumentException("Unsupported " + method);
        return strategy.pay(amountInPaise);                      // no if/else chain
    }
}

public class PaymentStrategyDemo {
    public static void main(String[] args) {
        CheckoutService checkout = new CheckoutService();
        System.out.println(checkout.checkout(PaymentMethod.UPI, 100000));
        System.out.println(checkout.checkout(PaymentMethod.CARD, 100000));
        System.out.println(checkout.checkout(PaymentMethod.COD, 100000));
    }
}
Receipt[mode=UPI, chargedPaise=100000]
Receipt[mode=CARD, chargedPaise=102000]
Receipt[mode=COD, chargedPaise=104000]

To add net banking, write one new class and register it. checkout() does not change. Each strategy is tested alone.

Strategy as a lambda

If the interface has one method, a strategy can be a lambda or a method reference, which removes the class ceremony:

interface DiscountRule { long apply(long amountInPaise); }

DiscountRule none    = amount -> amount;
DiscountRule tenOff  = amount -> amount * 90 / 100;
DiscountRule flat200 = amount -> Math.max(0, amount - 20000);

long total = priceWith(tenOff, 150000);        // passes behaviour as a value

static long priceWith(DiscountRule rule, long amount) { return rule.apply(amount); }

Strategy in the JDK

  • Comparator is the best-known strategy: list.sort(Comparator.comparing(Employee::salary)) passes a sorting algorithm to the List (the context). So are the comparators in TreeMap and PriorityQueue.
  • ThreadPoolExecutor takes a RejectedExecutionHandler (what to do when the queue is full) and a ThreadFactory.
  • LayoutManager in Swing/AWT; java.util.zip.Deflater compression levels; Collections.shuffle(list, random) with a pluggable Random.

Strategy in Spring

Spring makes Strategy nearly free. Declare each strategy as a bean and inject all of them. You can inject a Map<String, PaymentStrategy> (key = bean name) or a List<PaymentStrategy> and let each strategy say what it supports:

public interface PaymentStrategy {
    PaymentMethod method();                   // which key this strategy serves
    Receipt pay(long amountInPaise);
}

@Component class UpiPayment implements PaymentStrategy {
    public PaymentMethod method() { return PaymentMethod.UPI; }
    public Receipt pay(long amount) { return new Receipt("UPI", amount); }
}
@Component class CardPayment implements PaymentStrategy { /* ... */ }

@Service
public class CheckoutService {
    private final Map<PaymentMethod, PaymentStrategy> byMethod;

    public CheckoutService(List<PaymentStrategy> strategies) {      // all beans injected
        this.byMethod = strategies.stream()
                .collect(Collectors.toMap(PaymentStrategy::method, s -> s));
    }

    public Receipt checkout(PaymentMethod method, long amount) {
        return byMethod.get(method).pay(amount);
    }
}

A new payment method is a new @Component and nothing else. Spring's own strategies include HandlerMethodArgumentResolver, ViewResolver, HttpMessageConverter, PasswordEncoder and ResourceLoader. Strategies chosen by configuration also appear as @ConditionalOnProperty or profile-specific beans.

Pros

  • Removes long conditionals; follows OCP.
  • Each algorithm is isolated, easy to test and reuse.
  • Behaviour can be changed at run time (by user choice or configuration).
  • Composition instead of inheritance.

Cons

  • More classes (reduced by lambdas).
  • The client must know the strategies to choose one (or you need a selection mechanism).
  • For two simple, stable branches, it is overkill.

When NOT to use Strategy, and the State comparison

  • When there are two branches that will never grow: an if is clearer.
  • When the "algorithms" differ in only one number: use a parameter.
  • Strategy vs State: the shape (a context holding an interface reference) is identical. In Strategy, the client usually picks the strategy and it rarely changes; strategies do not know each other. In State, the object switches its own state as events occur, and states often know the next state.

Why the pattern exists

An if / else if chain on a type code ("UPI", "CARD") looks harmless at first. Then it grows: every new payment method edits the same method, every change risks the others, the method becomes hundreds of lines, and unit tests need to set up all branches. This breaks the Open/Closed Principle and the Single Responsibility Principle. Strategy fixes it by turning each branch into a class that implements one interface. The context (the checkout) no longer decides how; it only asks the chosen strategy to do it. Selecting which strategy to use becomes a separate, small decision.

The parts and the flow

A second example: retry back-off

A client calls a flaky payment API and waits between attempts. Different callers want different waiting rules: a fixed pause for a batch job, exponential growth for user requests. The waiting rule is a strategy; the retry loop is the context.

import java.time.Duration;
import java.util.concurrent.Callable;

interface BackoffPolicy {
    Duration delayBefore(int attempt);              // attempt starts at 1
}

class FixedBackoff implements BackoffPolicy {
    private final Duration pause;
    FixedBackoff(Duration pause) { this.pause = pause; }
    public Duration delayBefore(int attempt) { return pause; }
}

class ExponentialBackoff implements BackoffPolicy {
    private final Duration base;
    private final Duration cap;
    ExponentialBackoff(Duration base, Duration cap) { this.base = base; this.cap = cap; }
    public Duration delayBefore(int attempt) {
        long millis = base.toMillis() * (1L << Math.min(attempt - 1, 20));
        return Duration.ofMillis(Math.min(millis, cap.toMillis()));
    }
}

class Retrier {                                      // the context
    private final int maxAttempts;
    private final BackoffPolicy backoff;
    Retrier(int maxAttempts, BackoffPolicy backoff) {
        this.maxAttempts = maxAttempts;
        this.backoff = backoff;
    }
    <T> T call(Callable<T> task) throws Exception {
        for (int attempt = 1; ; attempt++) {
            try { return task.call(); }
            catch (Exception e) {
                if (attempt >= maxAttempts) throw e;
                Thread.sleep(backoff.delayBefore(attempt).toMillis());
            }
        }
    }
}

With new ExponentialBackoff(Duration.ofMillis(100), Duration.ofSeconds(2)) the waits are 100, 200, 400, 800 ms and so on, capped at 2 seconds. Adding "exponential with jitter" is one new class; Retrier is not edited. (Libraries such as Resilience4j and Spring Retry ship ready-made policies, so write your own only to learn or for tiny needs.)

Choosing the strategy

  • By configuration: a property such as payment.default=UPI picks the bean at start-up.
  • By request data: a registry Map<PaymentMethod, PaymentStrategy> and a lookup, as in the implementation above. This is the usual choice for a web app.
  • By rules: each strategy has a supports(request) method and the context picks the first that matches (a small chain; see Chain of Responsibility).

Do not put the switch back into the client. One lookup in one place is fine; the same switch in ten places is the original problem again.

Strategy vs the things it is confused with

PatternWho changes the behaviour?Key idea
StrategyThe client or configuration, from outsideInterchangeable algorithms; usually independent of each other
StateThe object itself, as its state changesStates know about each other and trigger transitions
Template MethodSubclasses fill steps of a fixed skeletonInheritance instead of composition
CommandThe invoker runs a request objectOne request, maybe queued or undone

Strategy and Template Method solve the same problem in two ways. Prefer Strategy when the variation is a whole algorithm or must change at run time (composition over inheritance). Choose Template Method when the order of steps is fixed and only some steps vary.

An enum with behaviour: the lightweight form

If the set of strategies is closed and small, an enum can carry the behaviour and avoids the extra interface and registry:

enum ShippingRate {
    STANDARD { long fee(long paise) { return paise > 49_900 ? 0 : 4_900; } },
    EXPRESS  { long fee(long paise) { return 9_900; } };

    abstract long fee(long orderPaise);
}
// ShippingRate.EXPRESS.fee(20_000) -> 9900

The trade-off: the list is fixed in one file, so you lose the open-for-extension benefit and cannot add a strategy from another module.

Wrong: the switch lives in the context

long fee(String courier, long paise) {
    switch (courier) {
        case "FAST":  return paise / 10;
        case "CHEAP": return 4_900;
        default: throw new IllegalArgumentException();
    }
}

Right: the context asks a strategy

long fee(CourierRates rates, long paise) {
    return rates.feeFor(paise);        // CourierRates is the strategy
}

Rules

  • All strategies share one interface and are interchangeable without the context knowing which one it has (LSP).
  • The context depends on the interface only, never on a concrete strategy class.
  • Pass the data a strategy needs as parameters. Do not let it reach into the context's private state.

Conventions

  • Make strategies stateless and reuse one instance; stateless objects are safe to share between threads.
  • Name them after the policy: ExponentialBackoff, PercentOff. In Spring, one @Component per strategy and inject the whole collection.
  • Provide a sensible default (a "no-op" or standard strategy) so the context never holds null.

Edge cases

  • Unknown key: a registry lookup that returns null leads to NullPointerException. Fail early with a clear IllegalArgumentException naming the key.
  • Strategies that need different inputs: the interface becomes a bag of parameters. Wrap them in a request record, or the abstraction is wrong.
  • Stateful strategies (a counter, a cache) are not safe to share. Create one per context or make them thread-safe.

Interview: Strategy

  • Which pattern replaces a big if/else or switch on type? Strategy (or State if the type changes over time).
  • JDK example? Comparator passed to Collections.sort or list.sort.
  • How do you implement it in Spring? Beans implementing one interface, injected as a Map or List.
  • Strategy vs Template Method? Strategy changes the whole algorithm by composition (swap an object); Template Method fixes the skeleton and lets subclasses fill in steps by inheritance.

Interview: harder Strategy questions

  • How does Strategy remove if/else? Each branch becomes a class behind an interface; a registry picks the class; adding a branch needs no edit to the context.
  • Strategy vs State? Same shape. State changes itself as the object moves between states; a strategy is chosen from outside and does not trigger transitions.
  • Where in the JDK? Comparator, RejectedExecutionHandler.
  • When is it overkill? Two branches that will never grow. A lambda or a simple if is enough.

Observer: publish changes to many listeners

Observer lets one object (the subject) notify any number of registered listeners when something happens, without the subject knowing who they are; in Spring you do this with ApplicationEventPublisher and @EventListener.

Intent: define a one-to-many dependency so that when one object changes state, all its dependents are notified and updated automatically.

The problem

When an order is placed, the system must send an email, reduce stock, award loyalty points and tell the analytics team. If OrderService.place() calls all four directly, it is coupled to every one of them: it needs four dependencies, a failure in analytics can break the order, and each new reaction means editing OrderService (against OCP and SRP). With Observer, OrderService only announces "order placed", and interested parties subscribe.

Implementation

import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;

enum OrderStatus { PLACED, PAID, SHIPPED, DELIVERED }
record OrderEvent(String orderId, OrderStatus status) { }

interface OrderListener {
    void onEvent(OrderEvent event);
}

class OrderEventPublisher {                               // the subject
    private final List<OrderListener> listeners = new CopyOnWriteArrayList<>();

    void subscribe(OrderListener l)   { listeners.add(l); }
    void unsubscribe(OrderListener l) { listeners.remove(l); }

    void publish(OrderEvent event) {
        for (OrderListener l : listeners) {
            try {
                l.onEvent(event);
            } catch (RuntimeException e) {                // one bad listener must not stop others
                System.err.println("Listener failed: " + e.getMessage());
            }
        }
    }
}

class EmailListener implements OrderListener {
    public void onEvent(OrderEvent e) {
        System.out.println("Email: order " + e.orderId() + " is " + e.status());
    }
}
class LoyaltyListener implements OrderListener {
    public void onEvent(OrderEvent e) {
        if (e.status() == OrderStatus.DELIVERED) {
            System.out.println("Loyalty: award points for " + e.orderId());
        }
    }
}

public class ObserverDemo {
    public static void main(String[] args) {
        OrderEventPublisher publisher = new OrderEventPublisher();
        publisher.subscribe(new EmailListener());
        publisher.subscribe(new LoyaltyListener());
        publisher.subscribe(e -> System.out.println("Audit: " + e));       // a lambda listener

        publisher.publish(new OrderEvent("O-1", OrderStatus.SHIPPED));
        publisher.publish(new OrderEvent("O-1", OrderStatus.DELIVERED));
    }
}
Email: order O-1 is SHIPPED
Audit: OrderEvent[orderId=O-1, status=SHIPPED]
Email: order O-1 is DELIVERED
Loyalty: award points for O-1
Audit: OrderEvent[orderId=O-1, status=DELIVERED]

CopyOnWriteArrayList lets listeners subscribe or unsubscribe while a publish is looping, without ConcurrentModificationException. Two choices every observer design must make: push (send the data in the event, as here) or pull (send a reference and let listeners ask), and synchronous (the publisher waits for all listeners, as here) or asynchronous (listeners run on other threads or through a queue).

Observer in the JDK

  • java.util.Observable and Observer are deprecated since Java 9. They were not type-safe and not thread-safe. Do not use them in new code.
  • java.beans.PropertyChangeListener and PropertyChangeSupport are still available for bound properties.
  • Event listeners in GUI toolkits (ActionListener, JavaFX properties); ServletContextListener and HttpSessionListener in servlets.
  • java.util.concurrent.Flow (Java 9+) defines Publisher/Subscriber interfaces for reactive streams with back-pressure.

Observer in Spring: application events

Spring has Observer built in. The container is the event bus: you publish an event object with ApplicationEventPublisher, and any bean method annotated @EventListener whose parameter type matches receives it. Since Spring 4.2 an event can be any object, so a record works.

public record OrderPlacedEvent(String orderId, String customerEmail) { }

@Service
public class OrderService {
    private final OrderRepository repository;
    private final ApplicationEventPublisher events;

    public OrderService(OrderRepository repository, ApplicationEventPublisher events) {
        this.repository = repository;
        this.events = events;
    }

    @Transactional
    public void place(Order order) {
        repository.save(order);
        events.publishEvent(new OrderPlacedEvent(order.id(), order.email()));
    }                                         // OrderService knows no listeners
}

@Component
class EmailSender {
    @EventListener
    void on(OrderPlacedEvent e) {
        // send the confirmation mail
    }
}

@Component
class LoyaltyService {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    void on(OrderPlacedEvent e) {
        // runs only if the order transaction committed
    }
}
  • By default, @EventListener methods run synchronously on the publisher's thread, inside its transaction. A slow or failing listener affects the publisher. Add @Async (with @EnableAsync) to run it on another thread.
  • @TransactionalEventListener ties a listener to the transaction phase. AFTER_COMMIT avoids sending an email for an order that later rolls back.
  • Spring also publishes its own events: ContextRefreshedEvent, ApplicationReadyEvent and others, which you can listen to.

For events that must cross process boundaries (microservices), in-memory observers are not enough; you need a message broker. That is the publish/subscribe pattern covered in Module 6 and in the messaging section of the Spring notes.

Pros

  • Loose coupling: the subject does not know its observers (OCP, DIP).
  • Add or remove reactions at run time or by adding a new class.
  • Natural fit for events and notifications.

Cons

  • Hidden control flow: hard to see who reacts to an event.
  • Order of notification is usually undefined (Spring: use @Order).
  • Memory leaks ("lapsed listener"): a forgotten subscription keeps an object alive.
  • Synchronous listeners can slow or break the publisher; exceptions need handling.
  • Event storms or cycles (a listener publishes an event that triggers itself).

When NOT to use Observer

  • When the caller needs a result from the other party: use a normal method call.
  • When the reaction must be part of the same atomic operation (debit and credit in one transaction). Hiding it behind events makes the flow unclear and the guarantee unclear.
  • When there is exactly one fixed collaborator and it will not change.

Interview: Observer

  • Explain Observer with an example. Order placed event with email, loyalty and stock listeners; the order service knows none of them.
  • How is it done in Spring? ApplicationEventPublisher.publishEvent and @EventListener; @TransactionalEventListener(AFTER_COMMIT) for transaction-safe reactions; @Async for non-blocking.
  • Is java.util.Observable recommended? No, deprecated since Java 9.
  • Observer vs pub/sub? Observer: in-process, direct references. Pub/sub: a broker decouples publishers and subscribers in space and time.

Command: turn a request into an object (undo, queues, Runnable)

Command wraps a request (an action and its data) in an object, so you can queue it, log it, schedule it, pass it around or undo it; in Java, Runnable and Callable are the everyday commands.

Intent: encapsulate a request as an object, letting you parameterise clients with different requests, queue or log requests, and support undoable operations.

The problem

A text editor has buttons, menu items and keyboard shortcuts that all perform actions: type text, delete, bold. You want undo and redo, and a macro recorder. If the button code calls document.insert(...) directly, nothing remembers what was done or how to reverse it. If each action is an object with execute() and undo(), the editor can keep a history stack. The same idea gives you job queues: store commands now, run them later on a worker thread.

Command
The interface with execute() (and undo() if needed).
Concrete command
Holds the receiver and the data needed, and calls the receiver in execute().
Receiver
The object that really does the work (Document).
Invoker
Triggers commands and keeps history (Editor, a button, a scheduler). It does not know what the command does.

Implementation: undo and redo

import java.util.ArrayDeque;
import java.util.Deque;

class Document {                                          // receiver
    private final StringBuilder text = new StringBuilder();
    void insert(int pos, String s) { text.insert(pos, s); }
    void remove(int pos, int len)  { text.delete(pos, pos + len); }
    int length() { return text.length(); }
    @Override public String toString() { return text.toString(); }
}

interface Command {
    void execute();
    void undo();
}

class InsertCommand implements Command {
    private final Document doc;
    private final int pos;
    private final String text;

    InsertCommand(Document doc, int pos, String text) {
        this.doc = doc; this.pos = pos; this.text = text;
    }
    public void execute() { doc.insert(pos, text); }
    public void undo()    { doc.remove(pos, text.length()); }     // exact reverse
}

class DeleteCommand implements Command {
    private final Document doc;
    private final int pos;
    private final int len;
    private String removed = "";                          // saved so undo can restore it

    DeleteCommand(Document doc, int pos, int len) {
        this.doc = doc; this.pos = pos; this.len = len;
    }
    public void execute() {
        removed = doc.toString().substring(pos, pos + len);
        doc.remove(pos, len);
    }
    public void undo() { doc.insert(pos, removed); }
}

class Editor {                                            // invoker with history
    private final Deque<Command> undoStack = new ArrayDeque<>();
    private final Deque<Command> redoStack = new ArrayDeque<>();

    void run(Command c) {
        c.execute();
        undoStack.push(c);
        redoStack.clear();                                // a new action ends the redo history
    }
    void undo() {
        if (undoStack.isEmpty()) return;
        Command c = undoStack.pop();
        c.undo();
        redoStack.push(c);
    }
    void redo() {
        if (redoStack.isEmpty()) return;
        Command c = redoStack.pop();
        c.execute();
        undoStack.push(c);
    }
}

public class CommandDemo {
    public static void main(String[] args) {
        Document doc = new Document();
        Editor editor = new Editor();
        editor.run(new InsertCommand(doc, 0, "Hello World"));
        editor.run(new DeleteCommand(doc, 5, 6));
        System.out.println(doc);          // Hello
        editor.undo();
        System.out.println(doc);          // Hello World
        editor.undo();
        System.out.println("[" + doc + "]");   // []
        editor.redo();
        System.out.println(doc);          // Hello World
    }
}

Command as a job queue

Because a command is just an object, you can put it in a queue and run it later, on another thread, or after a failure (retry). This is the idea behind background jobs, task schedulers and even database write-ahead logs.

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

ExecutorService workers = Executors.newFixedThreadPool(4);

Runnable sendInvoice = () -> mailer.send("asha@example.com", "Invoice #42");   // a command
Runnable resizeImage = () -> imageService.resize("photo.jpg", 200, 200);

workers.submit(sendInvoice);          // invoker: the executor runs commands off-thread
workers.submit(resizeImage);
workers.shutdown();

(mailer and imageService stand for your own objects.) In Java, a Runnable is a command with no result and no undo, and a Callable<V> is a command that returns a value. Lambdas make small commands almost free.

Command in the JDK and Spring

  • Runnable, Callable, ExecutorService.submit, Timer/TimerTask, ScheduledExecutorService.
  • Swing Action and ActionListener.
  • Spring: @Async methods and @Scheduled tasks are commands run by an executor; Spring Batch steps; TransactionCallback.
  • Architecture level: a command message in messaging and CQRS ("PlaceOrder") is the same idea sent over a queue (Module 6).
  • A single-method functional interface used with a lambda is also a command. The "macro" variant, MacroCommand, holds a list of commands and runs them in order (a Composite of commands).

Pros

  • Decouples who triggers an action from who performs it.
  • Enables undo/redo, queuing, scheduling, logging, retry and macros.
  • New commands are added without changing the invoker (OCP).

Cons

  • One class per action, so a lot of small classes (lambdas help).
  • Undo is hard when actions have side effects that cannot be reversed (sent emails, payments).
  • Undo needs saved state (the removed text), which costs memory.

When NOT to use Command

  • When you only call a method and need no queue, history or undo: a direct call is simpler.
  • For irreversible side effects, "undo" should be a compensating action (a refund), designed on purpose, not pretended (see the saga pattern in Module 6).

Why the pattern exists

A normal method call is instant and invisible: the caller says "do it now" and the moment it returns, nothing remains of the request. That is fine until you need to do something with the request itself: remember it for undo, run it later, run it on another thread, retry it after a failure, write it to a log, or send it over the network. For all of these, the request must be a thing you can hold, so you turn it into an object. The three roles are always the same: an invoker decides when, a command carries what, and a receiver does the real work.

The flow with undo

A second example: commands as data

In a backend, a command is often a small immutable record that describes an intention, plus a handler that executes it. This lets you validate, log and queue commands in one place, which is the idea behind command buses and CQRS ("command" side).

import java.util.HashMap;
import java.util.Map;
import java.util.function.Consumer;

sealed interface OrderCommand permits PlaceOrder, CancelOrder { }
record PlaceOrder(String orderId, long paise) implements OrderCommand { }
record CancelOrder(String orderId, String reason) implements OrderCommand { }

class CommandBus {
    private final Map<Class<?>, Consumer<Object>> handlers = new HashMap<>();

    <C extends OrderCommand> void register(Class<C> type, Consumer<C> handler) {
        handlers.put(type, c -> handler.accept(type.cast(c)));
    }

    void send(OrderCommand command) {
        System.out.println("LOG " + command);                   // one place to log
        Consumer<Object> h = handlers.get(command.getClass());
        if (h == null) throw new IllegalArgumentException("No handler for " + command);
        h.accept(command);
    }
}

public class BusDemo {
    public static void main(String[] args) {
        CommandBus bus = new CommandBus();
        bus.register(PlaceOrder.class, c -> System.out.println("placed " + c.orderId()));
        bus.register(CancelOrder.class, c -> System.out.println("cancelled " + c.orderId()));
        bus.send(new PlaceOrder("O-7", 129900));
        bus.send(new CancelOrder("O-7", "changed mind"));
    }
}

Because a command here is plain data, you can also store it in a database table or send it through Kafka or RabbitMQ and execute it on another machine. That is a command message. The difference from an event: a command says "please do this" and is addressed to one handler; an event says "this happened" and has any number of listeners (Observer).

Macro commands and composite undo

import java.util.ArrayDeque;
import java.util.Deque;
import java.util.List;

class MacroCommand implements Command {                 // Command from the editor example
    private final List<Command> steps;
    MacroCommand(List<Command> steps) { this.steps = List.copyOf(steps); }
    public void execute() { steps.forEach(Command::execute); }
    public void undo() {
        Deque<Command> reversed = new ArrayDeque<>();
        steps.forEach(reversed::push);                  // last executed is undone first
        reversed.forEach(Command::undo);
    }
}

Undo must run in the reverse order of execute, or the positions stored in the commands will point to the wrong places. If step 3 of 5 fails during execute, a robust macro undoes steps 1 and 2 before rethrowing.

Two ways to implement undo

ApproachHowGood for
Inverse operationThe command knows the opposite action (insert undoes delete)Small, reversible changes; cheap memory
Snapshot (Memento)Save the previous state before executing, restore on undoComplex edits; costs more memory
CompensationA new action that cancels the effect (a refund)External side effects that cannot be reversed

Command compared with its neighbours

  • Strategy: a reusable algorithm the context calls again and again. A command is one specific request with its own data, run once (or redone).
  • Callable / Runnable: a command with no undo. Use a plain functional interface when you need only "run this later".
  • Memento: stores state for restore. Commands often use a memento for undo.
  • Chain of Responsibility: passes a request along handlers until one handles it. A command bus has exactly one handler per command type.

Wrong: undo does not mirror execute

public void execute() { doc.insert(pos, text); }
public void undo()    { doc.remove(0, text.length()); }   // wrong position

Right: undo uses the same saved data

public void execute() { doc.insert(pos, text); }
public void undo()    { doc.remove(pos, text.length()); }

Rules

  • A command must carry everything it needs (the receiver and the arguments) so that it can run later, away from the code that created it.
  • If you offer undo, every command in the history must support it, and the history must be cleared of redo entries when a new command runs (as the Editor above does).
  • Make the data in a command immutable. If a captured object changes before the command runs, you execute a different request than the one the user made.

Conventions

  • Name commands as imperative verbs: PlaceOrder, CancelOrder. Events use the past tense: OrderPlaced.
  • Use a lambda or Runnable for tiny fire-and-forget actions, and a class or record when you need history, logging or serialisation.
  • Give queued commands an id so that a retry can be made idempotent (processing the same id twice has the same effect as once).

Edge cases

  • Unbounded history: an undo stack can grow without limit. Cap its size and drop the oldest entry.
  • Lambdas and checked exceptions: Runnable.run() cannot throw a checked exception; use Callable, or catch and wrap.
  • Captured variables: a lambda can only capture local variables that are effectively final, which pushes you towards immutable command data.
  • Executor failures: an exception thrown from a task submitted with submit is stored in the returned Future; if you never call get(), you never see it.

Interview: Command

  • When do you use Command? When you need to queue, schedule, log or undo operations, or decouple the sender from the receiver. Give the editor undo example.
  • Which Java interface is a command? Runnable (and Callable).
  • Command vs Strategy? Both wrap behaviour in an object. A command represents one request (with its data, executed at a given time, maybe undone); a strategy represents an interchangeable algorithm that a context uses repeatedly.

Interview: harder Command questions

  • Name the four roles. Command, concrete command, receiver, invoker (and the client that creates commands).
  • How does undo work? Each command stores what it needs to reverse itself; the invoker keeps a stack. Redo is a second stack.
  • Command vs event? Command: an instruction to one handler. Event: a fact for many listeners.
  • Where in Spring or the JDK? Runnable and ExecutorService, @Async, @Scheduled, job queues.

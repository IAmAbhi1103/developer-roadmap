Design a rate limiter (token bucket)

A rate limiter decides per client whether a request is allowed; the token bucket gives each client a bucket that refills at a steady rate and spends one token per request, which allows short bursts while enforcing a long-run average, and it needs a lock per bucket to be thread safe.

Requirements and assumptions

  • allow(key) returns true if the client (user id, API key or IP) may proceed, false if it must be rejected (an API would answer HTTP 429 Too Many Requests).
  • Limit example: 100 requests per minute per user, with bursts up to 20.
  • Constant-time check; thousands of threads; many keys.
  • Algorithms must be swappable: token bucket, fixed window, sliding window.
  • Assumptions: single JVM first (distributed version at the end), limits are the same for all keys (per-key rules are an extension), time comes from an injectable clock.

The algorithms compared

How the token bucket works

The bucket holds up to capacity tokens and refills at refillPerSecond. You do not need a timer thread. On each call compute how many tokens have accrued since the last call: elapsed × rate, add them, cap at capacity, then try to take one. This is lazy refill.

Key design decisions

  • Interface RateLimiter (Strategy, Module 2): callers (a servlet filter or Spring interceptor) never know which algorithm runs.
  • One TokenBucket per key held in a ConcurrentHashMap with computeIfAbsent, which creates the bucket atomically.
  • Lock per bucket, not a global lock: different users never wait for each other.
  • Monotonic clock: use System.nanoTime() (via a supplier) for elapsed time. Wall-clock time can jump backwards.
  • Doubles for tokens allow fractional refill (0.5 token after half a second at 1 per second).

Core code

import java.util.function.LongSupplier;

interface RateLimiter {
    boolean allow(String key);
}

class TokenBucket {
    private final long capacity;
    private final double refillPerNano;
    private final LongSupplier nanoClock;
    private double tokens;
    private long lastRefill;

    TokenBucket(long capacity, double refillPerSecond, LongSupplier nanoClock) {
        this.capacity = capacity;
        this.refillPerNano = refillPerSecond / 1_000_000_000.0;
        this.nanoClock = nanoClock;
        this.tokens = capacity;                         // start full
        this.lastRefill = nanoClock.getAsLong();
    }

    synchronized boolean tryConsume() {
        refill();
        if (tokens >= 1) {
            tokens -= 1;
            return true;
        }
        return false;
    }

    private void refill() {
        long now = nanoClock.getAsLong();
        double added = (now - lastRefill) * refillPerNano;
        tokens = Math.min(capacity, tokens + added);    // never exceed capacity
        lastRefill = now;
    }
}
import java.util.ArrayDeque;
import java.util.Deque;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.function.LongSupplier;

class TokenBucketLimiter implements RateLimiter {
    private final Map<String, TokenBucket> buckets = new ConcurrentHashMap<>();
    private final long capacity;
    private final double refillPerSecond;
    private final LongSupplier clock;

    TokenBucketLimiter(long capacity, double refillPerSecond, LongSupplier clock) {
        this.capacity = capacity;
        this.refillPerSecond = refillPerSecond;
        this.clock = clock;
    }

    public boolean allow(String key) {
        return buckets
                .computeIfAbsent(key, k -> new TokenBucket(capacity, refillPerSecond, clock))
                .tryConsume();
    }
}

/** Alternative: exact sliding window using a log of timestamps. */
class SlidingWindowLogLimiter implements RateLimiter {
    private final Map<String, Deque<Long>> logs = new ConcurrentHashMap<>();
    private final int limit;
    private final long windowNanos;
    private final LongSupplier clock;

    SlidingWindowLogLimiter(int limit, long windowMillis, LongSupplier clock) {
        this.limit = limit;
        this.windowNanos = windowMillis * 1_000_000L;
        this.clock = clock;
    }

    public boolean allow(String key) {
        Deque<Long> log = logs.computeIfAbsent(key, k -> new ArrayDeque<>());
        synchronized (log) {
            long now = clock.getAsLong();
            while (!log.isEmpty() && now - log.peekFirst() >= windowNanos) {
                log.pollFirst();                         // drop requests outside the window
            }
            if (log.size() >= limit) return false;
            log.addLast(now);
            return true;
        }
    }
}

        AtomicLong now = new AtomicLong();               // fake clock in nanoseconds

Concurrency

  • Refill and consume must be one step: tryConsume is synchronized, so two threads cannot both spend the last token.
  • computeIfAbsent on ConcurrentHashMap creates exactly one bucket per key even under races.
  • Lock-free option: keep (tokens, lastRefill) in an immutable object inside an AtomicReference and loop with compareAndSet. Good to mention, rarely required.

Fixed window boundary problem

With a limit of 100 per minute, a client can send 100 requests at 10:00:59 and 100 more at 10:01:00: 200 requests in two seconds, all allowed. Sliding windows and token buckets avoid this.

Edge cases

  • Long idle period: tokens are capped at capacity, so an idle client does not bank unlimited credit.
  • Clock going backwards: nanoTime does not; with wall-clock time guard against negative elapsed values.
  • Memory: millions of keys create millions of buckets. Evict idle ones (a bucket full for a while can be dropped and recreated full) with a scheduled cleanup or a bounded cache (like the LRU cache).
  • Cost-based requests: tryConsume(n) for expensive calls.
  • What to return: the HTTP layer sends 429 and a Retry-After header; the limiter can expose "seconds until next token".

Distributed rate limiting

Several app servers need one shared count, usually in Redis. A check-then-update must be atomic, so people use a Lua script (Redis runs a script without interleaving other commands) or simple INCR plus EXPIRE for a fixed window. Trade-offs: an extra network hop per request, the limiter itself can become a bottleneck or point of failure (decide: fail open or fail closed), and strict global accuracy costs latency. Many teams accept small errors by letting each node keep a local bucket and sync periodically, or put the limit in an API gateway. This leads into the HLD module.

Extensions interviewers ask

  • Different limits per user tier or per endpoint: a rule lookup (key, route) -> config; build the bucket from the rule.
  • Multiple limits together (10 per second and 1000 per hour): a composite limiter that must satisfy all.
  • Metrics: count rejected requests per key.
  • Queue instead of reject: leaky bucket with a bounded queue.
  • Dynamic config reload: volatile reference to the rule table.

How to present this in 45 minutes

  1. 5 min: key, limit, burst, single node or distributed, reject or queue.
  2. 5 min: compare the five algorithms in one table; pick token bucket and say why.
  3. 20 min: code TokenBucket with lazy refill, the limiter map, the demo with a fake clock.
  4. 10 min: thread safety, memory cleanup of idle keys.
  5. 5 min: distributed version with Redis and Lua, fail-open or fail-closed.

Design a food delivery order flow (Observer for status updates)

An order moves through a fixed set of statuses (placed, accepted, preparing, ready, picked up, delivered or cancelled); validate each transition with a table, and notify the customer, restaurant, delivery dispatcher and analytics through the Observer pattern so the order class does not know who is listening.

Requirements and assumptions

  • A customer places an order from one restaurant with items and quantities.
  • Status flow: PLACED, ACCEPTED, PREPARING, READY, PICKED_UP, DELIVERED. Cancellation is allowed before PICKED_UP.
  • Different parties react to each change: the customer gets a notification, the restaurant sees new orders, a delivery partner is assigned when food is READY, analytics records everything.
  • Invalid transitions (DELIVERED to PREPARING) are rejected.
  • Assumptions: money in paise; payment, maps and routing are out of scope; notifications are printed to the console; observers run synchronously in the core code (asynchronous delivery is discussed below).

Entities

Key design decisions

  • Observer (Module 2): when the status changes, the order loops over its observers. Adding SMS, email, a loyalty-points service or analytics means a new observer class and one subscribe call; Order never changes (open/closed, Module 1).
  • Transition table inside the enum instead of if chains: the legal moves are data, easy to read and test. If each status also had different behaviour, you would use the State pattern as in the vending machine. Here statuses carry no behaviour, only rules, so an enum plus table is lighter.
  • Notify outside the lock and isolate observers: one failing observer must not stop the others or roll back the order.
  • Snapshot of observers (CopyOnWriteArrayList) so subscribing during a notification does not throw ConcurrentModificationException.
  • Delivery partner assignment is a Strategy (nearest, least busy) used inside DeliveryDispatcher.

Core code: status rules and the order

import java.util.EnumMap;
import java.util.EnumSet;
import java.util.List;
import java.util.Map;
import java.util.Set;
import java.util.concurrent.CopyOnWriteArrayList;

enum OrderStatus {
    PLACED, ACCEPTED, PREPARING, READY, PICKED_UP, DELIVERED, CANCELLED;

    private static final Map<OrderStatus, Set<OrderStatus>> NEXT = new EnumMap<>(OrderStatus.class);
    static {
        NEXT.put(PLACED, EnumSet.of(ACCEPTED, CANCELLED));
        NEXT.put(ACCEPTED, EnumSet.of(PREPARING, CANCELLED));
        NEXT.put(PREPARING, EnumSet.of(READY, CANCELLED));
        NEXT.put(READY, EnumSet.of(PICKED_UP, CANCELLED));
        NEXT.put(PICKED_UP, EnumSet.of(DELIVERED));
        NEXT.put(DELIVERED, EnumSet.noneOf(OrderStatus.class));
        NEXT.put(CANCELLED, EnumSet.noneOf(OrderStatus.class));
    }

    boolean canMoveTo(OrderStatus target) { return NEXT.get(this).contains(target); }
}

record OrderItem(String name, int quantity, long pricePaise) { }

interface OrderObserver {
    void onStatusChanged(Order order, OrderStatus from, OrderStatus to);
}

class Order {
    private final String id, customerId, restaurantId;
    private final List<OrderItem> items;
    private OrderStatus status = OrderStatus.PLACED;
    private final List<OrderObserver> observers = new CopyOnWriteArrayList<>();

    Order(String id, String customerId, String restaurantId, List<OrderItem> items) {
        if (items.isEmpty()) throw new IllegalArgumentException("Order has no items");
        this.id = id;
        this.customerId = customerId;
        this.restaurantId = restaurantId;
        this.items = List.copyOf(items);
    }

    String id() { return id; }
    String customerId() { return customerId; }
    String restaurantId() { return restaurantId; }
    synchronized OrderStatus status() { return status; }

    long total() {
        return items.stream().mapToLong(i -> i.pricePaise() * i.quantity()).sum();
    }

    void subscribe(OrderObserver o) { observers.add(o); }

    void moveTo(OrderStatus next) {
        OrderStatus old;
        synchronized (this) {                                  // validate and change atomically
            if (!status.canMoveTo(next)) {
                throw new IllegalStateException("Illegal move " + status + " -> " + next);
            }
            old = status;
            status = next;
        }
        for (OrderObserver o : observers) {                    // notify outside the lock
            try {
                o.onStatusChanged(this, old, next);
            } catch (RuntimeException e) {
                System.err.println("Observer failed: " + e.getMessage());   // isolate failures
            }
        }
    }
}

class CustomerNotifier implements OrderObserver {
    public void onStatusChanged(Order o, OrderStatus from, OrderStatus to) {
        System.out.println("Customer " + o.customerId() + ": order " + o.id() + " is " + to);
    }
}

class RestaurantNotifier implements OrderObserver {
    public void onStatusChanged(Order o, OrderStatus from, OrderStatus to) {
        if (to == OrderStatus.PLACED || to == OrderStatus.CANCELLED) {
            System.out.println("Restaurant " + o.restaurantId() + ": order " + o.id() + " " + to);
        }
    }
}

class DeliveryDispatcher implements OrderObserver {
    public void onStatusChanged(Order o, OrderStatus from, OrderStatus to) {
        if (to == OrderStatus.READY) {
            System.out.println("Dispatcher: finding a delivery partner for " + o.id());
        }
    }
}

Concurrency

  • The restaurant presses "accepted" while the customer presses "cancel" at the same instant. Both call moveTo. The synchronized block validates and changes the status as one step, so one wins and the other gets IllegalStateException (or a valid transition from the new state). Nobody sees a half-updated order.
  • With a database: UPDATE orders SET status = 'ACCEPTED' WHERE id = ? AND status = 'PLACED' and check that one row changed. That is the same compare-and-set idea (Concurrency in LLD).
  • Notifying outside the lock means two quick updates might notify out of order. If order matters to observers, include a sequence number or deliver through a single-threaded queue per order.

Edge cases

  • Illegal transition or a repeated one: rejected with a clear message.
  • Cancel after pickup: not allowed by the table; real systems add a "refund request" flow instead.
  • An observer throws (SMS provider down): logged, others still run; consider retries.
  • Restaurant never accepts: a timeout job moves PLACED to CANCELLED after N minutes.
  • Observers that are slow: do not call a slow network API inside the loop; hand the event to a queue.
  • Memory: unsubscribe observers of finished orders, or let the order go out of scope.

Extensions interviewers ask

  • Asynchronous notifications: publish an event to an executor or a message broker (Kafka, RabbitMQ). Observers become consumers. This is the same Observer idea scaled across services (Spring Boot · Module 7).
  • Delivery partner assignment: a Strategy (nearest, least loaded, rating), plus a partner state (available, busy).
  • Order undo or edit: allow item edits only in PLACED.
  • Payment: add PAYMENT_PENDING before PLACED, and a refund observer on CANCELLED.
  • Different order types (pickup, dine-in): different transition tables chosen by a factory.
  • Live tracking: a location stream from the partner app, separate from status.

Interview questions — LLD interview problems

How do you start an LLD interview question?

I do not start with code. First I ask clarifying questions about users, main use cases, variations, limits and whether thread safety or persistence is needed. I write the agreed scope and my assumptions down. Next I list entities and the public methods, draw a class diagram, and only then write code, model first and main flow second. I keep talking so the interviewer can follow my reasoning.

How do you find the classes in a problem?

I underline nouns in the requirements, keep those that have their own data and behaviour or identity, and turn plain attributes into fields. Fixed sets of values become enums. Verbs become methods on the class that owns the data needed. I look for things that vary (pricing, split rules, selection rules) and put them behind an interface. I also ask what changes together and what changes separately, which shows where one class should become two (for example Book and BookCopy, Seat and ShowSeat).

When do you use a design pattern in an LLD answer, and when not?

Only when I can name the variation or the problem it solves: Strategy for pricing or split rules, State for a machine whose behaviour depends on its mode, Observer when many parties react to one change, Factory when object creation depends on a type. Using a pattern with nothing varying (Singleton for everything, a Factory for one class) is a negative sign. I say "no pattern needed here" when that is true, as in tic-tac-toe.

Explain the double-booking problem and how you prevent it.

It is a check-then-act race: two requests both see a seat as free and both book it. The fix is to make the check and the write one atomic step. In memory I use a lock around the critical section (one lock per show so multi-seat booking is all-or-nothing). In a real system with several servers the database decides: a unique constraint on (show, seat), a conditional update such as WHERE status = 'AVAILABLE', SELECT ... FOR UPDATE for high contention, or an optimistic version column. For checkout I add a HELD state with expiry.

Why not keep a database transaction open while the user pays?

Payment takes seconds or minutes. An open transaction holds locks and a connection, so other users queue up and the pool runs dry. Instead I use a short transaction to mark the seats HELD with an expiry time, release the lock, take the payment, then another short transaction to confirm. If the user leaves, the hold expires.

Why is a per-show lock a good choice for BookMyShow?

A booking changes several seats at once, and it must succeed for all or none. One lock per show makes that trivial and avoids deadlocks that per-seat locks cause when two users lock seats in opposite order. Different shows use different locks, so they do not slow each other. The lock is held only while flipping seat states, never during payment. If one show becomes extremely hot, I would go to per-seat locks in sorted order or to database-level conditional updates.

Implement an LRU cache with O(1) operations. Which structures and why?

A HashMap from key to node gives O(1) lookup. A doubly linked list ordered by recency gives O(1) move-to-front and O(1) removal of the tail, because a node knows its neighbours. get moves the node to the front; put inserts at the front and, if over capacity, removes the tail node and its map entry (the node stores its key for that). Sentinel head and tail nodes avoid null checks. In Java, LinkedHashMap with accessOrder = true and removeEldestEntry does the same.

Is a ConcurrentHashMap enough to make an LRU cache thread safe?

No. Each map operation is safe, but the cache must update the map and the recency list together, and even get writes (it reorders). Those compound steps need one lock, so the simple answer is synchronized methods. For more throughput: segment the cache into several independent LRUs by key hash, or use a library such as Caffeine that buffers recency updates.

Compare the token bucket and the fixed window rate limiter.

A fixed window counts requests per time slot and resets at the boundary. It is simple but allows up to double the limit across a boundary (100 at 10:00:59 and 100 at 10:01:00). A token bucket refills continuously, allows a bounded burst equal to capacity, and enforces the average rate over time, with O(1) time and memory per key. Refill is computed lazily from timestamps, no timer thread. Both need atomic updates per key.

How do you make a rate limiter work across many servers?

Keep the counters or buckets in a shared store such as Redis and make each check atomic, for example with a Lua script, because separate GET and SET calls would race. Costs: an extra network call per request and a new failure point, so decide whether the limiter fails open or closed. Alternatives are enforcing at the API gateway or using local buckets with periodic sync when small inaccuracy is acceptable.

How does the State pattern help the vending machine, compared with a switch statement?

With a switch, every method (insert, select, cancel) contains a branch per state, so adding OutOfService means editing all of them and it is easy to miss one. With State, each state class implements what each action means in that state, and the machine delegates. A new state is a new class. Invalid actions fall back to default methods that throw. The cost is more classes, which is worth it when states and actions both multiply.

How do you schedule an elevator? Explain the idea behind your algorithm.

Each elevator keeps its direction and two sorted sets of stops, one above and one below. It moves toward the next stop in its direction, serves everything on the way, and reverses when no stops remain in that direction (LOOK, a variant of SCAN from disk scheduling). This avoids zig-zagging and starvation. A dispatcher Strategy assigns a hall call to the best elevator, for example the idle one or the one moving toward the caller that is nearest. Each elevator's state changes under its own lock.

How does Splitwise simplify debts?

Compute each person's net balance (owed to them minus what they owe); the sum is zero. Put creditors and debtors into two priority queues. Repeatedly take the largest debtor and the largest creditor, transfer the smaller of the two amounts, and push back whatever remains. Each transfer clears at least one person, so there are at most N-1 transfers. The true minimum number of transfers is NP-hard in general, so the greedy method is the practical answer.

Why store money as a long of paise and not a double?

Binary floating point cannot represent values like 0.1 exactly, so sums drift and equality checks fail. A long of the smallest unit (paise) is exact and fast. When dividing, decide where the leftover paise go (for example the first participants get one extra), so the parts always add up to the total. BigDecimal is the alternative when you need fractional units or currencies with different scales.

The interviewer says "make it thread safe" at the end. What do you do?

I name the shared mutable state and the compound operations on it (check-then-act, read-modify-write). For each I choose the smallest tool: an atomic or putIfAbsent for a single value, a lock per object (per show, per bucket, per account) for multi-step updates, never a global lock if objects are independent. I keep slow work (payment, network) outside the lock, lock in a fixed order if two locks are needed, and mention the database constraint as the real guard for multiple servers.

Practice — LLD interview problems

  1. Warm-up: shopping cart. Rebuild the cart from the LLD method article from memory, then add a coupon-code rule and a combined rule. Done when adding a rule needs no change to Cart and you have a test for each rule.
  2. Race it. Write the broken Seat.book from the concurrency article, run it with 200 threads on one seat in a loop and count winners. Then fix it with synchronized and with putIfAbsent. Done when the count is always exactly 1.
  3. Parking lot. Implement it with the Strategy for pricing. Add EV spots and a "nearest free spot" allocation policy. Done when a unit test with a fake Clock checks the fee for 59 minutes, 61 minutes and 5 hours.
  4. Tic-tac-toe, then Snake and Ladder. Code both with an injected dice. Add undo to tic-tac-toe using a stack of moves. Done when a scripted game ends in a win, a draw and an invalid move.
  5. Library and vending machine. Code the library with reservations (a waiting queue notified on return) and the vending machine with an OutOfServiceState. Done when every invalid action throws a clear exception.
  6. Elevator. Run three elevators with random requests from several threads and a scheduler calling stepAll() every 100 ms. Print the stops. Done when no request waits longer than two full sweeps.
  7. LRU cache. Write the hand-made version, the LinkedHashMap version, then add a TTL. Done when the same test suite passes on both and a 16-thread stress test never throws.
  8. Splitwise. Add all three split types, history and simplify. Done when the sum of all net balances is zero in every test and a group of 5 people with 8 expenses needs at most 4 transfers.
  9. BookMyShow in 60 minutes. Set a timer and code the hold, pay, confirm flow. Then write the SQL conditional update and unique constraint for the same flow. Done when 100 threads fighting for 10 seats produce exactly 10 bookings and no seat is booked twice.
  10. Rate limiter and food delivery. Build the token bucket with a fake clock and a sliding window alternative, then the order flow with an asynchronous observer using an executor. Done when both pass tests, including a failing observer that does not stop the others.

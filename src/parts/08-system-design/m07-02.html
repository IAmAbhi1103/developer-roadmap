Design Pastebin (text sharing with expiry)

Pastebin stores blocks of text under a short link; because pastes can be large and are rarely changed, keep small metadata in a database and the text itself in object storage behind a CDN, generate keys like a URL shortener, and expire pastes with a TTL plus a background cleaner.

1. Requirements

Functional:

  • A user (logged in or anonymous) pastes text and gets a unique link.
  • Anyone with the link can read the paste. Options: public, unlisted or private.
  • Optional expiry (10 minutes, 1 day, 1 month, never), optional syntax highlighting language, optional custom alias.
  • Pastes are immutable once created (editing creates a new paste); users can delete their own.

Non-functional: high availability for reads, low read latency (a few hundred milliseconds), durability (a paste must not be lost before it expires), a size limit (say 10 MB), unguessable links for unlisted pastes, and abuse control (spam, malware, illegal content). Strong consistency for the "create then open" flow is nice: the creator opens the link immediately, so reads right after writes must work. Out of scope: collaborative editing, full-text search across all pastes.

2. Capacity estimates (assumptions)

  • Writes: 1 million new pastes per day → 1,000,000 ÷ 86,400 ≈ 12 per second; peak about 3× = 36 per second.
  • Reads: 5 reads per paste → 5 million reads per day → 5,000,000 ÷ 86,400 ≈ 58 per second; peak ~175 per second. Many pastes are read once or twice, a few go viral.
  • Average paste size 10 KB. Daily text = 1,000,000 × 10 KB = 10 GB. Per year = 10 GB × 365 ≈ 3.65 TB. Over 5 years ≈ 18 TB, before compression (text often compresses 3–5×) and before expiry removes many pastes.
  • Metadata: about 200 B per paste (key, owner, size, times, storage path) → 1M × 200 B = 200 MB per day, about 73 GB per year. Small enough for one database with replicas.
  • Read bandwidth: 58/s × 10 KB ≈ 580 KB/s average. Trivial. Even the 10 MB worst case at a few requests per second is manageable via a CDN.
  • Keys: 1M per day × 365 × 5 ≈ 1.8 billion keys. Base62 with 8 characters (628 ≈ 2.18 × 1014) leaves a huge margin and makes random guessing impractical.

Conclusion: request rates are low; the interesting problems are storing large blobs cheaply, expiry, and unguessable keys.

3. API design

201 Created
{"key": "k3Fq9XaB", "url": "https://paste.example/k3Fq9XaB",

{"key": "k3Fq9XaB", "language": "java", "createdAt": "...",

For large pastes, a good variant is to return metadata only and let the client fetch the raw text from a CDN URL (/raw/k3Fq9XaB), so big payloads never pass through the app servers.

4. Data model

Split metadata from content. Metadata is small, structured and queried by key or by user; content is a large blob read as a whole.

CREATE TABLE paste (
    paste_key    VARCHAR(12)  PRIMARY KEY,
    owner_id     BIGINT,                          -- null for anonymous
    visibility   VARCHAR(10)  NOT NULL,           -- PUBLIC, UNLISTED, PRIVATE
    language     VARCHAR(20),
    size_bytes   INT          NOT NULL,
    blob_path    VARCHAR(200) NOT NULL,           -- e.g. pastes/2026/11/11/k3Fq9XaB
    created_at   TIMESTAMP    NOT NULL DEFAULT now(),
    expires_at   TIMESTAMP
);
CREATE INDEX idx_paste_owner   ON paste (owner_id, created_at DESC);
CREATE INDEX idx_paste_expires ON paste (expires_at);

The content lives in object storage (S3, GCS, Azure Blob, MinIO; see Module 5). Why not keep 10 KB–10 MB text in the database? Large rows bloat the buffer cache and backups, slow replication, and cost far more per GB than object storage, which is cheap, durable (designed for many nines of durability) and scales to petabytes. Tiny pastes (under a few KB) could be stored inline in the row as an optimisation; do not start there.

Database choice: a relational database is fine for this volume (73 GB per year of metadata). A key-value store also works since the main lookup is by key. Choose what the team knows; mention the alternative.

5. High-level architecture

Write path: validate size and rate → get a unique key → upload the text to object storage at blob_path → insert the metadata row → return the link. Do the blob upload first; if the insert fails you have an orphan blob (cleaned up by a periodic scan), which is better than a metadata row pointing to a missing blob. Read path: check cache → on a miss read the metadata row, check expires_at and visibility → fetch the blob → fill the cache → return.

6. Deep dive A: key generation

The same options as the URL shortener apply: counter + base62, random pre-generated keys, or hashing. For Pastebin, unguessable keys matter more because "unlisted" means "anyone with the link", so a sequential key would let people walk through all pastes. Use a random 8-character base62 key from a key service, or encode a random 48-bit number (8 base62 characters). On insert, rely on the primary key: if a random key already exists (very unlikely), generate another and retry. For private pastes, also check ownership on read; the key alone is not authorisation.

7. Deep dive B: object storage and the read path

  • Immutability helps. A paste never changes, so it can be cached for a long time. The CDN and the browser can cache /raw/<key> with a long Cache-Control max-age, which removes most read load. When a paste is deleted or expires, purge it from the CDN (or accept bounded staleness for public pastes).
  • Signed URLs. For private pastes the app can hand out a short-lived signed URL to the object store, so the bytes flow storage → client directly. This keeps big traffic off the app servers and still enforces authorisation.
  • Compression. Compress text (gzip) before storing, typically cutting size 3–5×; the 18 TB five-year figure becomes roughly 4–6 TB.
  • Hot pastes. A viral paste is served by the CDN; the origin sees only misses. Cache metadata for hot keys in Redis with a TTL, using the patterns in Module 5.
  • Large uploads. For the 10 MB limit, either accept through the API with a body size cap or issue a pre-signed upload URL so the client uploads straight to storage, then calls the API to commit.

8. Deep dive C: expiry

Expired pastes must stop being served immediately, and their storage must eventually be reclaimed. Separate these two goals.

ApproachHowTrade-off
Lazy expiryOn every read, compare expires_at with now; if past, return 404 (and optionally delete)Always correct for reads; storage is not freed for pastes nobody reads
Background cleanerA scheduled job selects rows with expires_at < now() in batches, deletes the blob and then the rowFrees storage; needs the index on expires_at and batching to avoid load spikes
Native TTLUse a store with TTL (Redis, DynamoDB TTL, object-store lifecycle rules)No custom code; deletion time is approximate (often within hours or days)
Time-bucketed partitionsPartition metadata (and blob prefixes) by expiry date and drop whole partitionsVery cheap deletion; more design effort

A solid answer combines lazy expiry for correctness with a background cleaner (or lifecycle rule) for storage. Delete the row first and the blob second, or mark first and sweep later, so a failure leaves an orphan blob rather than a dangling pointer. Cache entries get a TTL no longer than the paste's remaining life.

@Scheduled(fixedDelay = 60_000)
public void cleanExpired() {
    List<PasteMeta> batch = repo.findExpired(Instant.now(), 500);   // uses idx_paste_expires
    for (PasteMeta p : batch) {
        blobStore.delete(p.blobPath());      // idempotent: deleting a missing blob is fine
        repo.deleteByKey(p.key());
        cache.evict(p.key());
    }
}

9. Bottlenecks, scaling and abuse

  • Scaling is easy here. Stateless API servers behind a load balancer; metadata DB with read replicas; blobs in object storage that scales by itself. If metadata outgrows one DB, shard by paste_key.
  • Availability: cached and CDN content survive a database blip; run across zones.
  • Abuse: rate limit anonymous creation per IP; reject over-size content; scan for malware, credentials leaks and illegal material; provide a report button and takedown flow; add X-Content-Type-Options and serve raw text as text/plain so a paste cannot run as a web page (stored XSS).
  • Privacy: never put private paste content in logs; encrypt blobs at rest.
  • Monitoring: cache hit ratio, p99 latency, storage growth, orphan count, cleaner lag.

Follow-up questions

  • How would you add search over paste content? (A search index, fed by CDC or a queue; public pastes only.)
  • How do you stop the same spam paste being posted millions of times? (Content hash dedupe and rate limits.)
  • What if the object store is down? (Serve from cache/CDN; fail creates with a clear error or queue them.)
  • How would you support editing or versions? (New immutable version with a parent id.)
  • How do you make "burn after reading" pastes work? (Atomic delete on first read, with a conditional update to avoid two readers.)

Interview angle

  • The key insight to say early: "metadata in a database, content in object storage".
  • Treat expiry as two problems: correctness on read, reclamation in the background.
  • Mention immutability, CDN caching and unguessable keys.

Design a distributed rate limiter (with Redis)

A distributed rate limiter decides, in about a millisecond, whether a client may make a request now; the usual design keeps per-client counters or token buckets in Redis, updates them atomically with a Lua script, and decides what to do when Redis itself is slow or down.

1. Requirements

Functional:

  • Limit requests per client (user id, API key or IP) per rule, such as 100 requests per minute, or 10 per second on login.
  • Different limits per endpoint and per plan (free vs paid).
  • Reject excess requests with 429 Too Many Requests and tell the client when to retry.
  • Rules can be changed without redeploying.

Non-functional: very low added latency (a few milliseconds at most, since it sits on every request), accurate enough across many servers (not 10× over the limit), highly available (it must not become the outage), and scalable to the whole API's traffic. Decide the failure policy: when the limiter is down, do we fail open (allow traffic) or fail closed (block)? For most APIs fail open; for expensive or security-critical endpoints (login, SMS) fail closed or fall back to local limits. Out of scope: DDoS protection at network level (a CDN/WAF job).

2. Capacity estimates (assumptions)

  • Total API traffic: 50,000 requests per second at peak. Every request needs one limiter check → 50,000 checks per second.
  • One Redis node handles very roughly on the order of 100,000 simple operations per second (an approximation that depends on hardware and commands). A Lua script costs more than one GET, so budget a node for perhaps 30,000–50,000 checks per second. We need a cluster of 3–5 shards with headroom, sharded by client key.
  • Memory: 10 million active clients, each with a token bucket of about 100 bytes (key + two fields + overhead) → 10,000,000 × 100 B = 1 GB. Memory is not the problem; operations per second are.
  • Latency: a Redis round trip inside a data centre is roughly 0.5–1 ms. With a budget of 5 ms this is fine; with 100 rules per request it would not be (so check only the few rules that apply).

3. Choosing the algorithm

The algorithms are explained in Module 5 and as a single-machine class in Module 3. Here is the comparison that matters for the distributed design.

AlgorithmState per clientAccuracyNotes
Fixed window counter1 counter + window startAllows up to 2× the limit around a window boundarySimplest, cheapest (INCR + EXPIRE)
Sliding window logTimestamp of every requestExactMemory heavy (limit × clients)
Sliding window counterTwo counters (current and previous window)Close approximationGood balance; small state
Token bucketToken count + last refill timeAllows controlled burstsMost popular; two fields per client
Leaky bucketQueue or level + timeSmooth constant output rateGood when the backend needs a steady rate

The boundary problem: with a limit of 100 per minute and a fixed window, a client can send 100 requests at 12:00:59 and 100 more at 12:01:00, which is 200 in two seconds. The sliding window counter estimates the current rate as current + previous × overlap. For example, 30 seconds into a window, with 40 requests in the previous window and 30 in the current one, the estimate is 30 + 40 × 0.5 = 50.

This design uses the token bucket: a bucket of capacity C refills at R tokens per second; each request takes one token; an empty bucket means reject. It allows short bursts up to C and a long-run rate of R.

4. API design

The limiter is usually a library or sidecar inside the API gateway, with an optional internal service for rule lookup. Internal API:

POST /internal/v1/ratelimit/check
{"clientId": "key_8a1f", "rule": "orders-create", "cost": 1}

200 OK
{"allowed": true, "remaining": 87, "limit": 100, "resetMs": 8200}

200 OK
{"allowed": false, "remaining": 0, "retryAfterMs": 1300}

The public API then answers rejected calls like this:

HTTP/1.1 429 Too Many Requests
Retry-After: 2
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1762853400

The X-RateLimit-* headers are a widely used convention (not one single official standard); Retry-After is a standard HTTP header.

5. Data model

Two kinds of data. Rules (config): (rule, plan, limit, window or refill), stored in a small database or config service and cached in each limiter instance, refreshed every few seconds. Counters (hot state): a Redis hash per client and rule.

ratelimit:{key_8a1f}:orders-create   (hash)
    tokens = 87.0
    ts     = 1762853392100        (last refill time, ms)
  expire after about 2 x the time to refill a full bucket

6. High-level architecture

7. Deep dive A: atomic checks in Redis

The naive approach is GET then SET from the app. Two gateways do it at the same time, both see 1 token left, and both allow: a race condition. The state change must be atomic. For a fixed window, INCR is atomic by itself. For a token bucket you need several steps (read, refill, subtract, write), so run them as one Lua script; Redis executes a script without interleaving other commands.

local key      = KEYS[1]
local capacity = tonumber(ARGV[1])   -- max tokens
local refill   = tonumber(ARGV[2])   -- tokens added per second
local now      = tonumber(ARGV[3])   -- current time in ms
local cost     = tonumber(ARGV[4])   -- tokens needed for this request

local data   = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(data[1])
local ts     = tonumber(data[2])
if tokens == nil then
  tokens = capacity
  ts = now
end

tokens = math.min(capacity, tokens + math.max(0, now - ts) * refill / 1000)
local allowed = 0
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
end

redis.call('HSET', key, 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', key, math.ceil(capacity / refill * 2000))
return {allowed, math.floor(tokens)}
import java.util.List;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;

public class RedisRateLimiter {
    private final StringRedisTemplate redis;
    private final DefaultRedisScript<List> script;

    public RedisRateLimiter(StringRedisTemplate redis, String luaSource) {
        this.redis = redis;
        this.script = new DefaultRedisScript<>(luaSource, List.class);
    }

    public boolean allow(String clientId, String rule, int capacity, double refillPerSec) {
        String key = "ratelimit:{" + clientId + "}:" + rule;     // {..} = hash tag
        List<?> r = redis.execute(script, List.of(key),
            String.valueOf(capacity), String.valueOf(refillPerSec),
            String.valueOf(System.currentTimeMillis()), "1");
        return r != null && ((Long) r.get(0)) == 1L;
    }
}

Notes: in Redis Cluster all keys touched by one script must live in the same slot; the {clientId} hash tag guarantees that. Passing time from the gateway means clock differences between gateways add small errors; if that matters, read the time inside the script with redis.call('TIME'). Keep scripts short, since they block the Redis thread while running.

8. Deep dive B: accuracy, latency and failure

  • Centralised vs local limits. Calling Redis on every request adds about a millisecond and makes Redis a dependency. A hybrid cuts both: each gateway keeps a local counter and syncs with Redis every 100 ms or after N requests (batching), or gets a slice of the quota ("you may admit 20 of this client's 100 per minute locally"). It is slightly less exact (a client might exceed by a small percentage) but much cheaper. Say which error you accept.
  • Sharding. Shard Redis by client key with consistent hashing (Module 5); one hot client stays on one shard, so for extreme keys use a local limiter or split the key into sub-buckets.
  • Failure policy. If a Redis call times out (use a very short timeout, 5–20 ms), fail open with a local in-memory limiter as a safety net, and raise an alert. For login or SMS, fail closed. A circuit breaker (Resilience) stops the gateway from waiting on a dead Redis.
  • Replication. Redis replication is asynchronous, so after a failover the counters can roll back a little and clients get a brief extra allowance. For a limiter that is acceptable.
  • Multi-region. Strict global limits need cross-region calls (slow). Usually each region enforces its own share of the limit (for example 50% each) or syncs asynchronously.

9. Deep dive C: where to put it and how to identify clients

  • Placement: at the edge or API gateway (best: reject before doing any work), as a middleware in each service, or both (coarse at the edge, fine-grained per service). Client-side limiting alone is not enough since clients can be hostile.
  • Identity: API key or user id once authenticated; IP address for anonymous traffic (but many users share one IP behind NAT, so be generous), and a combination for login attempts (per username plus per IP).
  • Cost-based limits: let an expensive call take 5 tokens instead of 1.
  • Response: return 429 with Retry-After; well-behaved clients back off with jitter (Retries). Log rejections to spot abusive clients and tune rules.

Bottlenecks and scaling

Add Redis shards as checks per second grow; reduce checks with local batching; keep rules in memory; monitor Redis CPU, command latency and the rejection rate. At 10× traffic (500,000 checks per second) the central-Redis-per-request design needs 10–15 shards, so moving to local batching or quota slices becomes worthwhile.

Follow-up questions

  • How do you stop one tenant using the whole shared quota? (Per-tenant limits plus a global limit.)
  • How would you rate limit by "requests in flight" instead of rate? (A semaphore-style counter that is decremented on completion; needs expiry for crashed requests.)
  • Fixed window vs sliding window: which and why? (Sliding window counter for accuracy at low cost; token bucket for bursts.)
  • How do you test the limiter? (Load test with many parallel clients; assert total allowed ≤ limit plus tolerance.)

  • State your failure policy (fail open or closed) and justify it per endpoint.
  • Mention the boundary problem of fixed windows and why token bucket or sliding window is better.

Low-level design (LLD) interviews ask you to turn a vague real-world idea ("design a parking lot") into classes, relationships and working Java code in about an hour. There is no single right answer. The interviewer watches how you ask questions, pick entities, apply the design principles and patterns where they help, handle two users clicking at the same time, and explain your choices.

This module first teaches how these interviews are scored and a repeatable method for them. It then covers the one topic that separates average from strong answers: concurrency, especially double booking. After that come ten classic problems, each with requirements, a class diagram, core code, edge cases and the follow-up questions interviewers love. Every problem reuses the same few ideas, so the tenth feels much easier than the first.

How LLD interviews work and how they are scored

An LLD round is a 45–60 minute conversation where you gather requirements, model entities, draw a class diagram and write core code; interviewers score communication and design judgement at least as much as the final code.

What the round looks like

You get one sentence: "Design a parking lot" or "Design BookMyShow". The interviewer is deliberately vague. A whiteboard, a shared document or an IDE is open. You are expected to talk the whole time. At product companies and startups the round often ends with runnable code and a small main that proves it works. At service companies the round may stop at the class diagram and a few key methods. Either way the same skills are checked.

This is different from a high-level design (HLD) round. HLD is about servers, databases, caches and scale across machines. LLD is about classes, interfaces and methods inside one service. The LLD interviewer cares whether your code is easy to extend, test and read.

A 45–60 minute plan

  1. Clarify (5–8 min). Ask questions, write the agreed requirements as bullets, mark what is out of scope.
  2. Entities and public API (5 min). List nouns, then the 3–5 methods the outside world calls, such as park(vehicle) and unpark(ticket).
  3. Class diagram (8–10 min). Boxes, relationships, enums, where patterns plug in.
  4. Core code (20–25 min). Write the model, then the main flow. Skip getters and trivial classes; say "assume getters".
  5. Edge cases and concurrency (5 min). Walk the failure paths; name the shared state and how you protect it.
  6. Extensions (5 min). Answer "what if we add X". A good design absorbs it with one new class.

Clarifying questions that work for almost any problem

  • Who are the users or actors (customer, admin, system)? Which of them do we support first?
  • What are the three or four main use cases? What is explicitly out of scope (payments, UI, notifications)?
  • What are the variations (vehicle types, payment modes, split types)? Will new ones be added later?
  • What are the limits and sizes (capacity, number of floors, users)? This decides data structures.
  • Is it a single process or several servers? Do we need thread safety? Do we need persistence?
  • What happens on failure (lot full, item out of stock, payment declined)? Exception, error code or retry?
  • Do we need history, audit or reports?

Common mistakes that cost the offer

  • Jumping to code with no requirements or diagram. You will rewrite it half-way.
  • God classes: one ParkingLot that parks, prices, prints tickets and talks to the database. See SRP.
  • Overusing patterns: a Factory for a class with one constructor, or Singleton for everything. Use a pattern when you can name the variation it protects.
  • Ignoring concurrency in booking, inventory or counter problems.
  • Using strings and ints where an enum or a small class is clearer.
  • Silent coding: 15 minutes without a word. The interviewer cannot score what they cannot hear.
  • Gold-plating: designing a payment gateway when the question was a vending machine.

If the interviewer interrupts with a hint

Take it. Say "good point, that changes X" and adjust. Interviewers give hints when they want to see how you collaborate. Arguing, or ignoring the hint, scores worse than a flawed first design.

The LLD method: requirements to code, with a worked example

Follow five steps every time: requirements, entities, class diagram, core code, edge cases; here the method is applied to a small shopping cart with discounts.

The five steps

  1. Requirements. Split into functional (what the system does) and non-functional (thread safety, extensibility, performance). Write assumptions down.
  2. Entities. Underline the nouns in the requirements: they are candidate classes. Verbs become methods. Things with a fixed set of values become enums. Things that vary by behaviour become interfaces.
  3. Class diagram. Decide relationships: has-a (composition/aggregation), is-a (inheritance, used sparingly), uses (dependency). See Module 1 on UML.
  4. Core code. Model classes first (immutable where possible), then the one service class that runs the main use case. Depend on interfaces, inject them through the constructor.
  5. Edge cases. Null and empty input, limits, duplicates, failure paths, concurrent callers.

Noun-verb trick

Not every noun is a class. "Customer name" is a field of Customer, not a class. Make a class only if it has its own data and behaviour, or its own identity and lifecycle. Not every verb is a method on the first noun you thought of: ask "who has the data needed to do this?" and put the method there.

Worked example: shopping cart with discounts

1. Requirements (and assumptions)
  • A customer adds items with quantity to a cart and sees the total.
  • Discounts: a percentage off the whole cart, and "flat amount off if total is above a threshold". More rules will come later.
  • Assumptions: single currency, money kept in paise (long) to avoid floating point errors, one discount at a time, single user per cart (no concurrency).
2. Entities

Nouns: cart, item, product, discount. Items have a price and quantity. Discount rules vary, so DiscountRule is an interface (the Strategy pattern). Cart is the class that owns items and applies a rule.

3. Core code
import java.util.ArrayList;
import java.util.List;

record Product(String name, long pricePaise) { }

record CartItem(Product product, int quantity) {
    CartItem {
        if (quantity <= 0) throw new IllegalArgumentException("quantity must be positive");
    }
    long lineTotal() { return product.pricePaise() * quantity; }
}

interface DiscountRule {
    long discount(long subtotalPaise);          // how much to subtract
}

class PercentOff implements DiscountRule {
    private final int percent;
    PercentOff(int percent) { this.percent = percent; }
    public long discount(long subtotal) { return subtotal * percent / 100; }
}

class FlatOffAboveThreshold implements DiscountRule {
    private final long threshold, flat;
    FlatOffAboveThreshold(long threshold, long flat) {
        this.threshold = threshold;
        this.flat = flat;
    }
    public long discount(long subtotal) { return subtotal >= threshold ? flat : 0; }
}
class Cart {
    private final List<CartItem> items = new ArrayList<>();

    void add(Product product, int quantity) {
        items.add(new CartItem(product, quantity));
    }

    long subtotal() {
        return items.stream().mapToLong(CartItem::lineTotal).sum();
    }

    long total(DiscountRule rule) {
        long sub = subtotal();
        long off = Math.min(rule.discount(sub), sub);   // never go below zero
        return sub - off;
    }
}

public class CartDemo {
    public static void main(String[] args) {
        Cart cart = new Cart();
        cart.add(new Product("Keyboard", 150_000), 1);
        cart.add(new Product("Mouse", 50_000), 2);
        System.out.println(cart.total(new PercentOff(10)));
        System.out.println(cart.total(new FlatOffAboveThreshold(200_000, 30_000)));
    }
}

4. Edge cases and extensions
  • Quantity zero or negative: rejected in the record's compact constructor.
  • A discount larger than the subtotal: capped with Math.min.
  • Empty cart: subtotal 0, total 0, no exception.
  • "Add coupon codes": a new DiscountRule class. Cart does not change (open/closed principle).
  • "Combine two discounts": a CompositeRule that holds a list of rules (the Composite idea from Module 2).

Rule: keep money in integers

Store paise or cents in a long, or use BigDecimal. double cannot represent 0.1 exactly, so totals drift by a paisa and tests fail in surprising ways.

Convention: depend on interfaces, build in main

Pass collaborators (rules, repositories, clocks) into constructors. In an interview this single habit shows dependency inversion, makes the code testable, and costs nothing.

Why you need a method

Most candidates fail an LLD round not because they do not know patterns, but because they start typing classes in the first minute. Halfway through they discover a requirement they never asked about, the design has no room for it, and the clock is running. A fixed method makes your thinking visible, keeps you from forgetting steps under stress, and gives the interviewer easy places to steer you. How the round is scored is explained in How LLD interviews work; this article is the step-by-step routine you follow inside that round.

The interview flow with a time budget

Step 1 in detail: clarifying questions and what to say

Never accept the one-line problem as the full problem. Ask short, specific questions, and say your assumption aloud so that the interviewer can correct you. A good set:

  • Scope: "Which features are in scope for today? I will cover X and Y, and leave Z as an extension. Is that fine?"
  • Actors: "Who uses it: only customers, or admins too?"
  • Rules: "Is there a limit, a time window, a priority order?" (for example, how many items, how long a loan lasts).
  • Scale and concurrency: "Is it one process or many? Can two users act on the same item at the same time?"
  • Persistence and interface: "Can I keep data in memory and skip the UI and database for now?"
  • Extensibility: "Which part do you expect to change most? Pricing rules? Payment types?" This tells you where to put an interface.

A sentence to say: "I will state my assumptions, then list entities, then draw the classes, then code the main flow. Stop me if you want a different order." It shows structure and invites guidance.

Steps 2 and 3 in detail: from nouns to a diagram

Write the requirement sentences on the board, underline nouns and circle verbs, then fill a small table. This is easy to explain aloud and hard to get wrong.

A noun with data and behaviourClassCart, CartItem

Say why each relationship is what it is: "A cart owns its items, so composition. A cart only uses a discount rule for one call, so a dependency." Pick a pattern only when a requirement points at it: "rules will change" suggests Strategy; "status changes the behaviour" suggests State; "notify several parties" suggests Observer. See the selection cheat sheet.

Step 4 in detail: how to write the code

  1. Start with enums and records (they are fast and show good habits).
  2. Write the interfaces next, then one or two implementations, not all.
  3. Write the service class with the main use case; inject collaborators through the constructor.
  4. Add a short main that proves it works, with the expected output.
  5. Say "I will skip getters and the remaining implementations; the pattern is the same." Interviewers prefer a clean core to a long dump.

Step 5 in detail: edge cases, concurrency and extensions

Leave the last minutes for this; it is where senior candidates stand out. Walk through three lists out loud:

  • Bad input: null, empty, zero or negative values, unknown ids, duplicates.
  • Concurrency: "Two users could check out the last item. The check and the update must be one atomic step. I would use synchronized on the item, or a database constraint if the data is persistent." The full toolbox is in Concurrency in LLD.
  • Extensions: name two changes and show where they go. "A coupon code is a new DiscountRule. A new payment method is a new class. Neither edits Cart."

Applying the method to a different problem

"Design a notification service that sends email and SMS, and lets users choose channels." Nouns: user, notification, channel, preference. Channel varies, so it is an interface (Channel with EmailChannel and SmsChannel). Preferences are data held by the user. A NotificationService.notify(user, message) loops over the user's channels. Edge cases: a user with no channel, a failing channel (should the others still send?), retry, rate limit. Extension: push notification is one new class. The same five steps, five minutes of thinking, and the code writes itself.

Wrong: jump into code and a pattern

// minute 1: "I will use a Factory and a Singleton"
class NotificationFactory { /* ... */ }
class NotificationManager { static NotificationManager instance; }

Right: requirements decide the design

// minute 12: channels vary, so one small interface
interface Channel { void send(String to, String text); }
class NotificationService {
    private final java.util.List<Channel> channels;
    NotificationService(java.util.List<Channel> channels) { this.channels = channels; }
}

Rules

  • Do not code before you have stated requirements and assumptions.
  • Every class must justify itself: data plus behaviour, or identity and lifecycle.
  • Money in integer units or BigDecimal; time through an injected Clock so tests can control it.

Conventions

  • Keep one use case end to end instead of five half-written ones.
  • Keep the model free of I/O (no printing, no database calls inside entities).
  • Return results or throw clear exceptions; avoid returning null for failure.

Edge cases about the method itself

  • If the interviewer says "just the class diagram", spend the saved time on relationships, multiplicity and extension points.
  • If the problem is a known one (parking lot, elevator), do not recite a memorised answer. Still ask your questions; the assumptions differ between interviewers.
  • If you get stuck, say what you would try next. Silence costs more than a wrong first guess.

Interview: using the method as an answer

  • "How do you approach an LLD problem?" Requirements and assumptions, entities from nouns, relationships and a class diagram, the core flow in code, then edge cases, concurrency and extensions. Mention that you ask questions first.
  • "What do you do when requirements are vague?" Ask, state a default, and record it so you can change it later.
  • "How do you decide on an interface?" Where the requirement says behaviour varies or will change.
  • "What would you improve with more time?" Persistence, validation, tests, events and metrics.

Concurrency in LLD: preventing double booking

Double booking is a check-then-act race: two requests both see a seat free, then both book it; fix it by making the check and the write one atomic step using a lock, a database constraint, a row lock or a version column, and use holds with expiry for seats that are chosen but not yet paid.

The race condition

Booking code often reads: "if seat is free, mark it booked". The two steps (check, then act) are separate. If two threads interleave between them, both pass the check.

class Seat {
    private String bookedBy;                        // null means free

    boolean book(String user) {
        if (bookedBy == null) {                    // check
            // another thread can run here
            bookedBy = user;                       // act
            return true;
        }
        return false;
    }
}

The cure is always the same idea: make check and act atomic, so nobody can slip in between. How you do that depends on where the truth lives: in memory of one JVM, or in a database shared by many servers.

Solution 1: in-memory locks (single JVM)

See Core Java · Module 6 for the basics of synchronized, ReentrantLock and the memory model.

import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentMap;
import java.util.concurrent.locks.ReentrantLock;

class SafeSeat {
    private String bookedBy;

    synchronized boolean book(String user) {       // lock on this seat object
        if (bookedBy != null) return false;
        bookedBy = user;
        return true;
    }

    synchronized boolean isFreeUnsafe() { return bookedBy == null; }
}

class SeatMap {
    // Lock-free style: putIfAbsent is atomic for ConcurrentHashMap
    private final ConcurrentMap<String, String> owner = new ConcurrentHashMap<>();

    boolean book(String seatId, String user) {
        return owner.putIfAbsent(seatId, user) == null;   // null means we won
    }
}

class MultiSeatBooking {
    private final ReentrantLock lock = new ReentrantLock();   // one lock per show

    boolean bookAll(java.util.List<SafeSeat> seats, String user) {
        lock.lock();
        try {
            // check all first, then book all; needs to be one critical section
            for (SafeSeat s : seats) if (!s.isFreeUnsafe()) return false;
            seats.forEach(s -> s.book(user));
            return true;
        } finally {
            lock.unlock();                          // always unlock in finally
        }
    }
}

Look at the shape of the last class: when a booking touches several seats, one lock per seat is risky (deadlock if two users lock seats in opposite order). Two safe options: one lock per show (simple, less parallelism), or per-seat locks always taken in sorted seat-id order.

Why per-seat locks can deadlock

User A locks seat 5 then waits for seat 6. User B locks seat 6 then waits for seat 5. Neither moves. Fix: sort the seat ids and always lock in that order, or use tryLock with a timeout and roll back.

In-memory locks stop at the JVM boundary

If you run two copies of your Spring Boot app behind a load balancer, synchronized in copy 1 knows nothing about copy 2. For a real booking system the database must be the referee.

Solution 2: database constraints

Make the invalid state impossible to store. A unique constraint on (show_id, seat_id) in a bookings table lets exactly one insert win; the loser gets a constraint violation, which you turn into "seat already taken".

CREATE TABLE booking (
    id        BIGSERIAL PRIMARY KEY,
    show_id   BIGINT NOT NULL,
    seat_id   BIGINT NOT NULL,
    user_id   BIGINT NOT NULL,
    created   TIMESTAMP NOT NULL DEFAULT now(),
    CONSTRAINT uq_show_seat UNIQUE (show_id, seat_id)
);

-- Second insert for the same show and seat fails with a unique violation
INSERT INTO booking (show_id, seat_id, user_id) VALUES (10, 12, 1);
INSERT INTO booking (show_id, seat_id, user_id) VALUES (10, 12, 2);  -- error

This is the strongest and simplest guard. In Spring you catch DataIntegrityViolationException and return a clean "seat taken" message. It works across any number of servers.

Solution 3: pessimistic lock with SELECT ... FOR UPDATE

Lock the rows you are about to change so others wait. Inside a transaction:

BEGIN;
SELECT status FROM show_seat
 WHERE show_id = 10 AND seat_id IN (12, 13)
 ORDER BY seat_id            -- same order for everyone avoids deadlocks
 FOR UPDATE;                  -- other transactions block here until we commit
-- application checks every status = 'AVAILABLE'
UPDATE show_seat SET status = 'BOOKED', user_id = 1
 WHERE show_id = 10 AND seat_id IN (12, 13);
COMMIT;

Use it when conflicts are common (a hot show) and you want a guaranteed result without retries. The cost: waiting transactions hold connections. Keep the transaction short, never wait for the user inside it. Details are in SQL · Module 5.

Solution 4: optimistic locking with a version column

Do not lock. Read the row with its version; update only if the version is unchanged; if no row was updated, someone else won, so retry or fail.

-- read: status = 'AVAILABLE', version = 7
UPDATE show_seat
   SET status = 'BOOKED', user_id = 1, version = version + 1
 WHERE show_id = 10 AND seat_id = 12
   AND status = 'AVAILABLE' AND version = 7;
-- rows affected = 1 -> we won;  rows affected = 0 -> someone else changed it

In JPA you add a @Version field and Hibernate does this for you, throwing OptimisticLockException on conflict. Optimistic locking is best when conflicts are rare.

Solution 5: temporary holds with expiry

Real users pick seats, then spend two minutes typing card details. You cannot keep a database lock for that long. Instead, introduce a middle state: AVAILABLE → HELD → BOOKED. A hold records held_by and hold_expires_at. Payment success turns it to BOOKED; timeout or failure turns it back.

-- try to hold: succeeds if free, or if an old hold has expired
UPDATE show_seat
   SET status = 'HELD', held_by = 1, hold_expires_at = now() + interval '5 minutes'
 WHERE show_id = 10 AND seat_id = 12
   AND (status = 'AVAILABLE'
        OR (status = 'HELD' AND hold_expires_at < now()));
-- rows affected = 1 -> hold granted

A background job (or lazy check on read, as above) releases expired holds. The single conditional UPDATE is atomic, so two users cannot both get the hold.

Solution 6: distributed locks (Redis), with caveats

A distributed lock is a lock shared by many servers, often kept in Redis with SET key value NX PX 30000 (set only if absent, auto-expire in 30 seconds). Only the holder who set the key may delete it, so the value is a unique token and the release checks it.

Caveats of distributed locks

  • The lock expires on a timer. If the holder pauses (long GC, slow network) past the expiry, a second holder enters while the first still thinks it holds the lock.
  • A fencing token (a number that grows with each lock grant, checked by the database on write) protects against that stale holder.
  • A Redis failover can lose the key, so two clients may hold the lock. Multi-node schemes such as Redlock are debated for safety-critical use.
  • It adds a moving part. If a database constraint can do the job, prefer the constraint.

How to answer "how do you avoid double booking?"

  1. Name the race: check-then-act on shared state.
  2. In the code you write: lock the critical section (per show or sorted per-seat locks).
  3. In production: a unique constraint as the final guard, a conditional update or row lock for the claim, a hold state with expiry for checkout.
  4. Mention what you would not do: keep a DB transaction open while the user pays.

Common mistakes

  • Locking a new object each call (synchronized (new Object())): nobody else shares it, so it protects nothing.
  • Using a ConcurrentHashMap but still doing if (!map.containsKey(k)) map.put(k, v). That is check-then-act again; use putIfAbsent or compute.
  • Forgetting to release the hold or lock on the failure path.

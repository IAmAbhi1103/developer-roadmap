A high-level design (HLD) interview gives you one vague sentence, such as "Design a URL shortener", and 45 minutes. Nobody expects a perfect answer. They want to see how you think: do you ask questions, do the arithmetic, pick sensible components, explain trade-offs and notice what can fail? This module gives you a repeatable method and ten fully worked problems, so that you have both the process and the building blocks ready.

Every problem uses tools from earlier modules. Estimation and trade-offs come from Module 4, the components (cache, queue, sharding, CDN, object storage) from Module 5, and idempotency, sagas, outbox and IDs from Module 6. Where a problem needs a pattern, it links back instead of re-explaining. The low-level class-design cousins of some of these problems are in Module 3.

All numbers in the capacity estimates are assumptions made for practice. They are round and approximate on purpose; in an interview you state your assumptions aloud and the interviewer adjusts them. They are not statistics about any real company.

After this module you will be able to:

  • Run a 45-minute HLD interview with a clear time plan and know how you will be scored.
  • Turn a vague prompt into requirements, estimates, APIs, a data model and a diagram.
  • Design the ten classic systems: URL shortener, Pastebin, rate limiter, notification system, chat, news feed, food delivery, ride sharing, video streaming and payments.
  • Discuss two to four deep dives per problem with options and trade-offs.
  • Answer "what if traffic grows 10 times?" and other follow-ups calmly.

The HLD interview method: a script, a checklist and a rubric

Spend 45 minutes in six phases (requirements, estimates, high-level design, data model, deep dive, trade-offs), say your reasoning out loud, drive the conversation yourself, and always cover numbers, bottlenecks and failure.

What an HLD interview tests

There is no single right answer. The interviewer checks whether you can: handle ambiguity by asking questions, size a system with simple arithmetic, assemble known building blocks into a coherent whole, justify choices by trade-offs, go deep on one or two hard parts, and communicate clearly. Seniority shows in depth and judgement, not in the number of boxes on the board.

Total: 40–50 minutes. For a 60-minute slot, give the deep dive more time. Wear a watch; the most common time mistake is spending 20 minutes on requirements and drawing, then rushing the part that scores most.

The script: what to say in each phase

Phase 1: requirements (5 min)

Say: "Before I design anything, I want to clarify scope. I will ask a few questions, then write down what is in and out." Then ask from this checklist, choosing the questions that matter:

  • Users and use cases: who uses it, and what are the two or three core actions?
  • Scale: how many users or requests per day? Read-heavy or write-heavy?
  • Features: what is in scope for 45 minutes, and what is a later extension?
  • Consistency and freshness: must users always see the latest data, or is a few seconds of delay fine?
  • Availability and latency: any target, such as 99.9% uptime or under 200 ms?
  • Durability: can we ever lose data? (A chat message: no. A view counter: maybe.)
  • Geography: one region or global? Mobile, web, or both?
  • Constraints: abuse and security, privacy, compliance, retention time.

Write two lists: functional (what the system does) and non-functional (how well: scale, latency, availability, consistency, durability). End with "Out of scope: ...". Confirm: "Does this match what you have in mind?"

Phase 2: estimates (5 min)

Say: "I will do rough numbers to see which parts are hard. All approximate." Convert users to requests per second: daily requests ÷ 86,400 ≈ per second, and round 86,400 to about 100,000 when you are in a hurry. Peak is typically 2–3 times the average. Then storage (items × size × retention) and bandwidth (QPS × size). Use powers of ten and write the units. See Module 4 for the cheat numbers. State what the numbers imply: "4,000 reads per second is easy for one cache node, so the real problem is storage over 5 years" is the kind of conclusion that earns credit.

Phase 3: high-level design (10–15 min)

Say: "First the API, then a simple end-to-end design, then I will improve it." Define the 3–5 endpoints with request and response shapes. Draw the minimum working path: client → load balancer → app servers → database. Walk one write and one read through it. Then add components only when a requirement or number demands them: cache for read-heavy load, queue for slow or bursty work, CDN for static content, search index for text search. Name each addition and why.

Phase 4: data model (5 min)

List the main entities, their key fields, primary keys and the main access patterns ("lookup by short code", "latest posts of user X"). Choose SQL or NoSQL based on those patterns, scale and consistency needs, and say why. Mention indexes and the shard key if you will shard.

Phase 5: deep dive (10–15 min)

Say: "The hardest part here is X. Let me go deeper." Often the interviewer picks. Present options, compare them in a table or sentences, choose one, and state the cost of the choice. Two good deep dives beat five shallow ones.

Phase 6: trade-offs and wrap-up (5 min)

Cover: single points of failure and what happens when each box dies; bottlenecks; how it scales 10×; data loss and duplicates; monitoring and alerting; security and abuse; cost. Finish with a 20-second summary of the design and what you would build next.

How to drive the conversation

  • Narrate: "I am choosing X over Y because...". Silence worries interviewers.
  • Propose a plan at the start ("I will cover requirements, numbers, design, data, then a deep dive") and tick it off.
  • Check in at phase ends: "Shall I go deeper here, or move on?" Follow the interviewer's hints; a question usually points at what they want to see.
  • When you do not know, reason aloud from principles. Do not bluff about product internals.
  • Use the board: one diagram, labelled arrows, numbers beside components.
  • Say the trade-off every time you pick: "Fan-out on write makes reads fast but writes expensive."

Common mistakes

What loses points

  • No requirements: designing the wrong system.
  • No numbers: you cannot justify sharding or caching without them.
  • Over-engineering: Kafka, Kubernetes, microservices and a service mesh for 40 requests per second. Start simple, scale when numbers demand it.
  • Name-dropping: saying "Cassandra" without saying why.
  • Ignoring failure: never saying what happens when a node, a network link or a dependency fails.
  • Single point of failure left on the diagram.
  • Not listening: ignoring a hint to move to the part the interviewer cares about.
  • Defensive tone: treat challenges as new requirements, not attacks.

"What if traffic grows 10×?"

Answer with a method, not panic. First re-do the numbers: which resource hits its limit first? Then walk the path from the user inwards:

  1. Edge: CDN and caching for anything static or cacheable.
  2. App tier: stateless servers behind a load balancer scale horizontally; add instances and autoscaling.
  3. Cache: raise the hit ratio, add nodes, protect against hot keys.
  4. Database reads: add read replicas; accept replication lag where allowed.
  5. Database writes and storage: shard by a good key, or move the hot table to a store built for writes.
  6. Async the slow stuff: move non-urgent work to queues; add back-pressure.
  7. Protect the system: rate limits, load shedding, graceful degradation.

Then say what would break next at 100×. That shows you know scaling is a sequence of bottlenecks.

1. Requirements  functional | non-functional | out of scope

Interview angle

  • Open with the plan and the clarifying questions. That alone separates you from most candidates.
  • Always give at least one number, one trade-off and one failure scenario per component you add.
  • Practise out loud with a timer. Saying it is a different skill from knowing it.

Design a URL shortener (like bit.ly)

A URL shortener maps a short code to a long URL; it is read-heavy, so the design is a key-value lookup with a cache in front, a collision-free way to create 7-character codes (counter plus base62, hash, or pre-generated keys), and a choice between 301 and 302 redirects that trades speed for analytics.

1. Requirements

Functional:

  • Given a long URL, create a short URL (for example https://sho.rt/aZ3k9Q1).
  • Opening the short URL redirects to the original URL.
  • Optional: custom alias, expiry time, click analytics, user accounts.

Non-functional: very low redirect latency (under about 50 ms server time), high availability (a dead short link breaks every page it was posted on), short codes that are hard to guess or enumerate, durable links (never lose a mapping), and eventual consistency is fine for analytics but not for the mapping itself. Out of scope: link-preview pages, malware scanning (mention it).

2. Capacity estimates (assumptions)

  • New URLs: 100 million per month. A month is about 30 × 86,400 = 2,592,000 seconds. Writes ≈ 100,000,000 ÷ 2,592,000 ≈ 39 per second, call it 40. Peak at 3× ≈ 120 per second.
  • Read:write ratio 100:1. Reads ≈ 40 × 100 = 4,000 per second on average, about 12,000 per second at peak.
  • Retention 5 years: 100M × 12 × 5 = 6 billion URLs.
  • Row size: code 7 B + long URL ~200 B + timestamps and user ~50 B, say 500 B with index overhead. Storage = 6 × 109 × 500 B = 3 × 1012 B = 3 TB. One modern database cluster handles that; sharding is for write throughput and availability more than raw size.
  • Code length: base62 has 62 characters (a–z, A–Z, 0–9). 626 ≈ 56.8 billion and 627 ≈ 3.52 trillion. For 6 billion URLs, 6 characters would fit, but 7 gives about 590 times headroom. Use 7.
  • Cache: 4,000 reads/s × 86,400 ≈ 345 million reads/day. If the hottest 20% of URLs get most traffic, caching 20% of one day's distinct URLs ≈ 0.2 × 345M × 500 B ≈ 35 GB. That fits a small Redis cluster.
  • Bandwidth: 4,000 × 500 B = 2 MB/s of response data. Tiny.

Conclusion: this is not a big-data problem. The interesting parts are generating unique codes, caching, and keeping redirects fast and available.

Creation should accept an Idempotency-Key header so a retry does not create two codes (Idempotency). Unknown or expired codes return 404 (or 410 Gone for expired).

4. Data model

CREATE TABLE url_mapping (
    short_code  VARCHAR(10)   PRIMARY KEY,
    long_url    VARCHAR(2048) NOT NULL,
    user_id     BIGINT,
    created_at  TIMESTAMP     NOT NULL DEFAULT now(),
    expires_at  TIMESTAMP
);
CREATE INDEX idx_mapping_user ON url_mapping (user_id);

The main access pattern is a single-key lookup by short_code, with no joins and no transactions across rows. That fits a key-value or wide-column store (DynamoDB, Cassandra) very well, and also a sharded SQL database. PostgreSQL or MySQL is fine up to this scale with replicas; choose NoSQL if you expect much higher write rates or want built-in horizontal scaling. The shard key is short_code (even spread because codes are random-looking). Analytics are stored separately (see below).

5. High-level architecture

The read path (99% of traffic) and the write path have very different load, so deploy them as separate services or at least separate scaling groups. Redirect servers are stateless; any instance can serve any code.

6. Deep dive A: generating the short code

OptionHow it worksProsCons
Counter + base62Get next unique number, encode in base62No collisions, shortest codesCounter is a dependency; codes are guessable and sequential
Hash of the URLMD5 or SHA-256, take first 7 base62 charactersNo coordination; same URL gives same codeCollisions to handle; two users cannot have separate codes for one URL
Pre-generated keys (KGS)A key service creates random unused codes in advance; app takes oneFast, no collision check at request time, unguessableOne more service; must avoid giving a key twice

Counter + base62. Take a number such as 125 and convert it to base 62: repeatedly divide by 62 and map remainders to characters. A 64-bit counter from a ticket server with ranges or a Snowflake generator (Unique IDs) removes the single-database bottleneck: each app server leases a range of, say, 1,000 numbers and encodes them locally. To stop people enumerating links (aZ3k9Q1, aZ3k9Q2), apply a reversible shuffle to the number first, or use a random permutation.

public final class Base62 {
    private static final String ALPHABET =
        "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

    public static String encode(long n) {
        if (n == 0) return "0";
        StringBuilder sb = new StringBuilder();
        while (n > 0) {
            sb.append(ALPHABET.charAt((int) (n % 62)));
            n /= 62;
        }
        return sb.reverse().toString();
    }

    public static void main(String[] args) {
        System.out.println(encode(125));            // 125 = 2*62 + 1
        System.out.println(encode(3_521_614_606_207L)); // 62^7 - 1, the largest 7-char value
    }
}

Hash + collision handling. Compute base62(md5(longUrl)) and keep 7 characters. Seven characters is about 42 bits of the hash, so with billions of URLs collisions do happen (birthday effect). On insert, if the code exists with a different long URL, append a counter or salt to the input and hash again. This makes the write path a read-then-write loop; rely on the primary key constraint to catch the race between two writers.

Pre-generated keys. A separate key generation service fills a table of unused 7-char random codes. App servers take a batch of keys (for example 1,000) and mark them used atomically. Keys given to a server that crashes are simply lost, which is fine with 3.5 trillion possible codes. Pick this when unguessability matters.

7. Deep dive B: redirects, 301 vs 302 and analytics

StatusMeaningEffect
301 Moved PermanentlyCache this redirectBrowsers and proxies remember it; later clicks may never reach you, so no analytics and the link cannot be changed
302 Found (or 307)Temporary redirectEvery click hits your server: you can count it, change the target or expire the link; slightly more load

If you need analytics, expiry or editing, use 302 and accept the extra load (the numbers above are small). If you only want minimal cost and fixed links, 301. The click must not slow the redirect: the redirect service sends the user to the target first and writes a small event (code, time, country, user agent) to a queue; consumers aggregate into an analytics store (ClickHouse or similar, or counters in a time-series table). Losing a few click events is acceptable (at-most-once is fine, see Delivery semantics).

8. Deep dive C: caching hot links

Link popularity is highly skewed: a few viral links get most clicks. Use cache-aside in Redis: look up code; on a miss read the database and store with a TTL of hours; an LRU or LFU policy handles memory (Module 5). With a 90%+ hit ratio the database sees under 400 reads per second at the 4,000/s average. Add a tiny in-process cache for the top few thousand codes to protect Redis from hot keys. Cache "not found" for a short time so scanners guessing random codes do not reach the database (penetration), and a Bloom filter of all existing codes can reject most guesses outright. Expired links: store expires_at in the cache value and check it on every read; the database cleans up with a background job.

9. Bottlenecks and scaling

  • Database: add read replicas first; shard by short_code when storage or writes outgrow one cluster. Use consistent hashing so adding shards moves little data.
  • Availability: multiple app instances across zones; Redis with replicas; database with replicas and automatic failover. Serve cached redirects even if the database is briefly down.
  • Multi-region: replicate the mapping to each region and route users to the nearest one with DNS (Module 5). Writes can go to a home region.
  • Abuse: rate limit creation per user and IP; scan target URLs for malware and phishing; block known bad domains.
  • Monitoring: redirect p99 latency, cache hit ratio, error rate, counter or key pool remaining, queue lag.

Follow-up questions

  • Same long URL submitted twice: return the same code or a new one? (Per-user dedupe by hashing userId + url.)
  • How do you delete expired links at scale? (TTL in a key-value store, or a nightly batch by partition.)
  • How do you stop one user's custom alias clashing with generated codes? (Reserve a different namespace or length.)
  • What if the counter service dies? (Servers hold leased ranges; run two counter nodes with odd and even steps.)
  • How would you count unique visitors? (Approximate with HyperLogLog.)

Interview angle

  • Do the 627 arithmetic out loud; it shows you size the code length from the numbers.
  • Compare the three code-generation options in a sentence each and pick one with a reason.
  • Know 301 vs 302 and its analytics consequence.

API gateway and BFF

An API gateway is the single front door for clients of a microservice system: it routes requests and handles the cross-cutting work (authentication, rate limiting, TLS, logging, aggregation, protocol translation) so each service does not repeat it; a BFF is a gateway tailored to one kind of client.

The problem

With ten microservices, a mobile app would need ten addresses, ten authentication checks, and ten round trips to draw one screen. Every service would also re-implement rate limits, logging and CORS. An API gateway is a server that sits between clients and your services and presents one uniform entry point. A gateway differs from a plain load balancer: the load balancer spreads traffic over identical servers; the gateway understands your APIs and decides which service gets each call.

Common products: Spring Cloud Gateway (a natural fit for a Java team), Kong, NGINX, Envoy-based gateways, AWS API Gateway, Azure API Management. See Spring Boot · Module 7 for Spring Cloud Gateway.

Backend for Frontend (BFF)

One generic gateway tends to grow a lot of client-specific code. A Backend for Frontend gives each client type its own thin gateway service: a mobile BFF that returns compact payloads for slow networks, a web BFF that returns what the React app needs, a partner BFF with a stable versioned API. The BFF belongs to the front-end team, aggregates calls, and shapes responses, while the core services stay generic. The cost is more services to run and some duplicated code.

Trade-offs and failure modes

  • Single point of failure and bottleneck: run many gateway instances behind a load balancer; keep the gateway stateless and fast.
  • Extra hop: adds a few milliseconds. Keep logic in the gateway thin.
  • The "god gateway": if business logic creeps in, the gateway becomes a monolith that every team must change. Keep it to cross-cutting work and routing.
  • Gateway security is not enough: services should still verify identity (zero trust) in case something bypasses the gateway.

What a request goes through

Seeing the order of work makes the gateway concrete. A call to GET /orders/42 from a mobile app passes through a chain of steps. Each step can reject the request early, which is why the cheap checks (TLS, rate limit, token) come before the expensive one (calling a service).

Two details matter. First, the gateway must remove any identity header sent by the client (such as X-User-Id) before it adds its own, or a user could pretend to be someone else. Second, it must add a correlation id (for example X-Request-Id) so one request can be followed through every service log.

Gateway vs load balancer vs reverse proxy vs service mesh

These four are often mixed up, and interviewers like the question. They overlap in technology (Envoy and NGINX appear in several roles) but differ in purpose.

ComponentSitsMain jobUnderstands your API?
Load balancerIn front of copies of one serviceSpread traffic, health checksNo (L4) or a little (L7)
Reverse proxyIn front of serversForward requests, TLS, caching, compressionOnly paths and headers
API gatewayAt the edge, for external clientsRouting between services, auth, quotas, aggregationYes: routes, plans, API keys
Service meshBeside every service (sidecar), for internal callsmTLS, retries, timeouts, telemetry between servicesTraffic level, not business meaning

A short way to remember: the gateway handles north-south traffic (clients to your system); a service mesh handles east-west traffic (service to service). Most systems use a load balancer in front of the gateway instances, a gateway at the edge, and optionally a mesh inside. See DNS and CDN for what sits even further out.

A configuration example: Spring Cloud Gateway

For a Java team, Spring Cloud Gateway is the natural pick: it is a Spring Boot application, so routes, filters and security use the tools you already know. A route has an id, a target uri, predicates (when the route matches) and filters (what to change on the way). The setup, the starter and the filter catalogue are covered in Spring Boot · Module 7.

spring:
  cloud:
    gateway:
      routes:
        - id: orders
          uri: http://order-service:8080
          predicates:
            - Path=/api/orders/**
          filters:
            - StripPrefix=1          # /api/orders/42 becomes /orders/42
        - id: catalog
          uri: http://catalog-service:8080
          predicates:
            - Path=/api/products/**
          filters:
            - StripPrefix=1

Property names changed in newer Spring Cloud releases

Newer Spring Cloud Gateway releases split the project into a WebFlux server and a WebMVC server, and the route properties moved under a longer prefix (for example spring.cloud.gateway.server.webflux.routes). The same route can also be written in Java with RouteLocatorBuilder. Check the reference of the version in your project before copying YAML.

BFF in practice: one call, three services

A mobile home screen needs the user's name, the open orders and a few recommendations. Without a BFF, the phone makes three calls over a slow network. A BFF makes the three calls on the fast data-centre network, in parallel, and returns one small JSON:

import org.springframework.web.reactive.function.client.WebClient;
import reactor.core.publisher.Mono;

record Home(String userName, String openOrders, String picks) { }

class HomeBff {
    private final WebClient users;
    private final WebClient orders;
    private final WebClient recs;

    HomeBff(WebClient users, WebClient orders, WebClient recs) {
        this.users = users;
        this.orders = orders;
        this.recs = recs;
    }

    Mono<Home> home(String userId) {
        Mono<String> u = users.get().uri("/users/{id}", userId)
                .retrieve().bodyToMono(String.class);
        Mono<String> o = orders.get().uri("/orders?user={id}&status=open", userId)
                .retrieve().bodyToMono(String.class);
        Mono<String> r = recs.get().uri("/picks/{id}", userId)
                .retrieve().bodyToMono(String.class)
                .onErrorReturn("[]");                 // recommendations are optional
        return Mono.zip(u, o, r, Home::new);           // three calls run in parallel
    }
}

Note the last design choice: recommendations are optional, so if that service fails the screen still loads with an empty list. Decide for each downstream call whether it is required or optional; that is graceful degradation. (The code assumes Spring WebFlux is on the classpath.)

More failure modes and how to handle them

  • Slow service drags the gateway down: without timeouts, threads or connections pile up on the slow backend and the gateway stops answering everyone. Set a timeout per route and a limit on concurrent calls.
  • Retry storms: if the gateway retries failed calls and every instance does the same, a struggling service receives double or triple the load. Retry only safe (idempotent) requests, a small number of times, with back-off.
  • Circuit breaker: after repeated failures, stop calling the service for a while and return a fallback or a fast 503.
  • Bad config deploy: a wrong route takes the whole site down. Keep route config in version control, roll out gradually and keep the last good version.
  • Large uploads and long connections: proxying big files or WebSockets through the gateway consumes its memory and connections. Use presigned URLs to object storage for uploads (see Object storage).

Pros

  • One public address and one place for TLS, auth, quotas and logs.
  • Clients are shielded from internal service moves and splits.
  • Aggregation cuts mobile round trips.

Cons

  • One more hop and one more component to run, scale and secure.
  • A shared gateway team can become a bottleneck for releases.
  • Risk of business logic creeping in.

Rules

  • Keep the gateway stateless so any instance can handle any request, and run at least two instances.
  • Strip client-supplied identity headers; add trusted ones after authentication.
  • Every route needs a timeout. No exceptions.

Conventions

  • Version the public API in the path (/v1/orders) and route versions to different services if needed.
  • Return consistent error bodies and use 429 for rate limits and 503 for an unavailable backend.
  • Log request id, route, status and latency; alert on latency percentiles and 5xx rate (Latency, throughput and percentiles).

When NOT to use a gateway (or a BFF)

  • A monolith or two services: a reverse proxy and a load balancer are enough.
  • One client type with similar needs: a shared gateway is enough; a BFF per client is extra cost.
  • Service-to-service calls inside the cluster should not detour through the public gateway; use direct calls, or a mesh.

Interview angle

  • "Clients talk only to the gateway; it authenticates, rate limits and routes. Services behind it stay private."
  • Contrast it with a load balancer in one line: the balancer spreads load over copies of one service, the gateway routes between different services and applies policies.
  • Mention BFF when a mobile and a web client have very different needs.

Interview: follow-ups on the gateway

  • Gateway vs load balancer? The balancer picks among identical servers; the gateway chooses between different services and applies API policies.
  • Gateway vs service mesh? Gateway: edge, north-south. Mesh: inside, east-west.
  • Is the gateway a single point of failure? Not if you run several stateless instances behind a load balancer and across zones.
  • When BFF? When clients (mobile, web, partners) need different payloads and release at different speeds.
  • Where does authorisation happen? Coarse checks (token valid, scope) at the gateway; fine-grained business rules in the service.

Rate limiting: algorithms, Redis and responses

Rate limiting caps how many requests a client may make in a time window to protect the system from abuse and overload; the main algorithms are token bucket, leaky bucket, fixed window, sliding window log and sliding window counter, and a distributed limiter keeps its counters in Redis with atomic operations.

Why limit, and who to limit

A rate limiter rejects or delays requests above an allowed rate. It protects against accidental overload (a client bug in a retry loop), abuse and scraping, brute-force logins, and noisy neighbours in a shared system. It also enforces paid plans (100 calls per minute on the free tier) and keeps costs predictable. You choose the key to limit by: user id, API key, IP address, tenant, or an endpoint (login is limited more strictly than reads).

Where to rate limit

  • CDN / edge / WAF: blocks floods early and cheaply, mostly by IP.
  • API gateway or load balancer: the usual place; one policy for all services, before expensive work happens.
  • In the service: fine-grained limits that need business knowledge (per-tenant quotas, expensive endpoints), using a library such as Bucket4j or Resilience4j.
  • Client side: well-behaved clients also limit themselves, but never trust that.

The five algorithms

1. Token bucket

A bucket holds up to capacity tokens. Tokens are added at a fixed refill rate. Each request takes one token; with none left, the request is rejected. Because the bucket can fill while a client is idle, short bursts are allowed (up to the capacity) but the long-term average stays at the refill rate. Memory is tiny: two numbers per key (tokens and last refill time). This is the most widely used algorithm (used by API gateways and cloud providers). A Java implementation is in Module 3.

2. Leaky bucket

Requests enter a queue of fixed size (the bucket) and leave at a constant rate (the leak). If the queue is full, new requests are dropped. The output is perfectly smooth, which is good when the downstream system needs steady traffic (a payment partner that accepts exactly 50 per second). Cost: bursts are queued and delayed rather than served at once, and old requests may wait behind new ones.

3. Fixed window counter

Count requests per fixed time slot (for example per minute). If the count exceeds the limit, reject until the next slot. Very simple and cheap (one counter per key per window). The flaw is the boundary burst: with a limit of 100 per minute, a client can send 100 at 12:00:59 and another 100 at 12:01:00, so 200 requests in two seconds.

4. Sliding window log

Keep a timestamp of every request in the last window (a sorted set). On each request remove old timestamps, count the rest, allow if under the limit. This is exact, with no boundary burst. Cost: memory proportional to the limit per key (storing 10,000 timestamps for a 10,000-per-hour key), so it suits low limits.

5. Sliding window counter

A cheap approximation of the log. Keep counters for the current and previous fixed windows, and weight the previous one by how much of it still overlaps the sliding window:

estimate = current_count + previous_count × (1 − elapsed_fraction_of_current_window)

Limit 100 per minute. Previous minute: 80. Now 15 s into this minute: 30 so far.
estimate = 30 + 80 × (1 − 15/60) = 30 + 60 = 90  → allow (under 100)

Memory is two counters per key, and the smoothing is good enough in practice (the error is small when traffic is fairly even). It is a popular balanced choice.

A distributed implementation with Redis

With many gateway instances, counters cannot live in each instance's memory (a client could get N times the limit). Keep them in Redis, shared by all instances. The operations must be atomic or two requests can both read "99" and both be allowed.

Fixed window with INCR and EXPIRE
import java.time.Duration;
import org.springframework.data.redis.core.StringRedisTemplate;

public class FixedWindowLimiter {
    private final StringRedisTemplate redis;
    private final int limit;
    private final Duration window;

    public FixedWindowLimiter(StringRedisTemplate redis, int limit, Duration window) {
        this.redis = redis;
        this.limit = limit;
        this.window = window;
    }

    public boolean allow(String clientId) {
        long slot = System.currentTimeMillis() / window.toMillis();
        String key = "rl:" + clientId + ":" + slot;
        Long count = redis.opsForValue().increment(key);   // atomic INCR
        if (count != null && count == 1) {
            redis.expire(key, window);                     // first hit sets the TTL
        }
        return count != null && count <= limit;
    }
}

Watch the gap between INCR and EXPIRE: if the process dies in between, the key never expires. Including the window slot in the key makes stale keys harmless, and a Lua script removes the gap entirely.

Token bucket as a Lua script

Redis runs a Lua script atomically, so read-modify-write is safe. This script keeps tokens and the last refill time in a hash. (Check your Redis version's rules for using time inside scripts; passing now from the caller is the simplest portable way, at the price of clock differences between app servers.)

-- KEYS[1] = bucket key
-- ARGV[1] = capacity, ARGV[2] = refill tokens per second, ARGV[3] = now in ms
local data = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local tokens = tonumber(data[1])
local ts = tonumber(data[2])
if tokens == nil then
  tokens = capacity
  ts = now
end
tokens = math.min(capacity, tokens + (now - ts) / 1000 * rate)
local allowed = 0
if tokens >= 1 then
  tokens = tokens - 1
  allowed = 1
end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) * 2)
return allowed

From Java, run it with Spring Data Redis's DefaultRedisScript and redis.execute(script, keys, args...). Sliding window log in Redis uses a sorted set: ZREMRANGEBYSCORE (drop old), ZCARD (count), ZADD (record), wrapped in a script or a transaction.

What to return to the client

HTTP/1.1 429 Too Many Requests
Retry-After: 12
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1731312000
Content-Type: application/json

{"error":"rate_limit_exceeded","message":"Try again in 12 seconds"}
  • Use status 429 Too Many Requests, not 403 or 500.
  • Retry-After tells well-behaved clients how many seconds to wait.
  • The X-RateLimit-* headers (a widespread convention; an IETF draft standardises similar RateLimit-* names) let clients slow down before they are rejected.
  • Clients should respond with exponential backoff with jitter.

Design decisions and failure modes

  • Fail open or closed? If Redis is down, should the limiter let all traffic through (risking overload) or block all (risking an outage)? Most systems fail open for ordinary APIs and fail closed for security-critical ones such as login. Keep a small local fallback limiter.
  • Race conditions: use atomic commands or Lua, never read-then-write from the app.
  • Latency: a Redis round trip per request adds about a millisecond; limit locally in batches or use sticky routing if that matters.
  • Hot keys and sharding: one very popular client key sits on one Redis node; shard keys by client id.
  • Rule hierarchy: per-IP, per-user and global limits together; return the strictest.
  • Distinguish rate limiting from load shedding: limits are per client; load shedding drops requests when the whole system is overloaded.

Common mistake: limiting by IP only

Many users share one IP behind a company or mobile carrier NAT, and attackers rotate IPs. Limit by authenticated identity when you can, and use IP limits as a coarse outer layer.

Interview angle

  • "I use a token bucket in the gateway: it allows short bursts and enforces a steady average, and it needs only two values per client in Redis."
  • Explain why fixed windows allow double bursts at the boundary, and how the sliding window counter fixes it cheaply.
  • Return 429 with Retry-After; decide fail-open vs fail-closed out loud.

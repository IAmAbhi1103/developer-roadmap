DNS in system design

DNS translates names to IP addresses through a cached hierarchy of resolvers; in system design you use it to point users to the nearest or a healthy region (GeoDNS, latency-based routing, failover), and you pick a TTL that balances speed against how fast you can change the answer.

What problem it solves

Humans use names (api.shop.example) and machines use IP addresses. The Domain Name System (DNS) is the distributed phone book that maps one to the other. It is the very first step of almost every request, and it is also a design tool: because you control the answer, you can decide which IP a user receives.

How resolution works

  1. The browser checks its own cache and the operating system cache (and the hosts file).
  2. If missing, it asks a recursive resolver, usually run by the ISP or a public service. The resolver does the legwork.
  3. The resolver asks a root server, then the TLD server (for .com, .in), then the domain's authoritative server, which holds the real records.
  4. The answer comes back with a TTL (time to live): how many seconds every cache may reuse it. Each cache along the way stores it.

Because of caching, most lookups never reach your authoritative server, so DNS is fast and cheap, and also slow to change.

TTL: the main trade-off

Before a migration, lower the TTL a day ahead so the cutover takes minutes. Even then, some resolvers and clients ignore TTL and keep old answers longer, so never rely on DNS for instant failover.

DNS as a traffic-steering tool

  • Round-robin DNS: several A records for one name; resolvers rotate them. Crude load spreading with no health awareness.
  • Weighted routing: send 10% of users to the new version (a canary) and 90% to the old.
  • GeoDNS / geolocation routing: answer depends on where the resolver is: Indian users get the Mumbai IP, European users the Frankfurt IP. Good for data-residency rules.
  • Latency-based routing: the provider answers with the region that measured lowest latency to the user.
  • DNS failover: the DNS service runs health checks against each endpoint and stops returning an unhealthy one. Combined with a short TTL this gives regional failover in a minute or two.
  • Anycast: many servers around the world announce the same IP and the network routes each user to the nearest. Used by public DNS and CDNs.

Managed services such as Amazon Route 53 and Cloudflare provide these policies. In the multi-region design from earlier, DNS is the first and coarsest load balancer: it picks the region, then a regional load balancer picks the server.

Failure modes and costs

  • DNS is a SPOF unless you use multiple name servers, ideally from more than one provider. A DNS outage makes a healthy site unreachable.
  • Stale caches keep sending users to a dead IP until TTL expires.
  • JVM caching: Java can cache DNS lookups for a long time in some configurations (see the networkaddress.cache.ttl security property). A service that calls a hostname whose IP changes (a load balancer or a managed database endpoint) can keep using an old IP, so set a modest TTL for long-running JVMs.
  • Cache poisoning and spoofing are attacks on resolvers; DNSSEC adds signatures.

Interview angle

  • "DNS is the first hop. I use latency-based or geo routing to send users to the nearest region and health checks for failover, with a short TTL on those records."
  • State the limit: DNS failover is minutes, not seconds, because clients cache; use a load balancer or anycast for fast failover inside a region.

CDN: content delivery networks

A CDN keeps copies of your content on edge servers close to users so most requests never reach your origin; it cuts latency, bandwidth cost and origin load, and you control it with cache-control headers and versioned URLs.

The problem

Physics sets a floor for latency: a round trip from Bengaluru to a US server is around 200 ms, and a web page needs many round trips. Serving the same 2 MB image from your origin to a million users also burns your bandwidth and CPU. A Content Delivery Network (CDN) is a global fleet of edge servers (points of presence, PoPs) that cache your files near users. Examples: Cloudflare, Amazon CloudFront, Akamai, Fastly.

How it works

DNS or anycast sends the user to a nearby edge. On a hit the edge answers at once. On a miss it fetches from the origin, stores the response according to the cache headers, and returns it. Many CDNs add a shield (a middle cache tier) so that a miss in many edges becomes one request to the origin.

What to put on a CDN: static vs dynamic

Static content (images, CSS, JavaScript bundles, fonts, videos, downloads) is the classic fit: identical for everyone, rarely changing. Dynamic content (a user's cart, a personalised feed) usually cannot be cached shared across users. Modern CDNs still help with dynamic traffic: they keep connections to the origin warm, terminate TLS near the user, compress, can cache API responses that are the same for everybody (a product catalogue for 30 seconds) and can run small code at the edge. Never cache per-user responses under a shared key.

@GetMapping("/products/{id}")
public ResponseEntity<Product> get(@PathVariable long id) {
    Product p = service.find(id);
    return ResponseEntity.ok()
        .cacheControl(CacheControl.maxAge(Duration.ofMinutes(5)).cachePublic())
        .eTag("v" + p.version())
        .body(p);
}

Invalidation: how to change what is cached

  1. Versioned (fingerprinted) URLs: name files by content, app.3f9c2a.js. A new build means a new URL, so the old cache entry is simply never asked for again. Cache these for a year with immutable. This is the best strategy for static assets (Vite and webpack do it by default).
  2. Short TTL for things that change but can be a little stale (a home page for 60 s).
  3. Explicit purge or invalidation: call the CDN API to remove a path. It works but is slower, may cost money per request, and propagates in seconds to minutes. Keep it for emergencies (a wrong price, a legal takedown).
  4. Never cache the HTML shell for long; it points to the fingerprinted files.

Benefits, costs, failure modes

Pros

  • Much lower latency for far-away users.
  • Offloads most bandwidth and requests from the origin.
  • Absorbs traffic spikes and some DDoS attacks.
  • Gives TLS and compression close to the user.

Cons

  • Stale content if headers are wrong; invalidation is slow.
  • Cost per GB and per request; some CDNs charge for purges.
  • Cache-key mistakes can leak private data between users.
  • An extra dependency: a CDN outage can take down the whole site's assets.

Common mistake: caching a response that varies per user

If an API returns data tied to a cookie or Authorization header and the CDN caches it as public, the next user gets someone else's data. Mark such responses private or no-store, and keep cookies out of the cache key for static paths.

Real projects

A typical setup: the React build from Vite goes to S3, CloudFront sits in front, assets are fingerprinted with a one-year cache, index.html has a short TTL, user uploads are served from the same CDN through object-storage URLs (Object storage), and the API is not cached at the edge except for a few public endpoints.

Interview angle

  • "Static assets and media go through a CDN with long-lived, fingerprinted URLs, so deploys do not need purges."
  • Name the trade-off: stale content and invalidation delay in return for latency and offload.
  • For video streaming, say that the CDN carries almost all bytes; the origin only serves misses.

Load balancers: L4 vs L7, algorithms and health checks

A load balancer spreads incoming traffic over several healthy servers behind one address; L4 balancers route by IP and port (fast, simple), L7 balancers read HTTP (smart routing, TLS, headers), and you choose an algorithm and health checks to avoid sending traffic to a sick or overloaded node.

What problem it solves

One server has a limit and is a single point of failure. A load balancer (LB) gives clients one stable address and distributes requests over a pool of servers. It makes horizontal scaling work (Scaling), removes dead servers from rotation, and lets you deploy without downtime by draining one server at a time. For the Nginx basics see DevOps · Module 2.

L4 vs L7

The layers refer to the OSI model. An L4 (transport-layer) balancer sees only IP addresses and TCP/UDP ports; it forwards connections without understanding the content. An L7 (application-layer) balancer terminates the connection, reads the HTTP request (path, host, headers, cookies) and makes a routing decision per request.

Common pattern: an L4 balancer or anycast at the very front for raw speed and DDoS absorption, then L7 balancers that route by path to different services.

Health checks

The balancer must know who is alive.

  • Active checks: the balancer probes each server every few seconds (a TCP connect or an HTTP GET to /actuator/health). After N failures the server is removed; after M successes it returns.
  • Passive checks: the balancer watches real traffic; too many errors or timeouts from a server mark it down. No extra probe traffic, but real users hit the failure first.

Design the health endpoint carefully. A liveness check says the process runs. A readiness check says it can take traffic (database connected, warmed up). Do not make the check depend on every downstream service: if the shared database slows down and every health check fails, the balancer pulls all servers out and you cause a total outage. Also use connection draining (finish in-flight requests before removing a server) and slow start for new servers.

upstream api_servers {
    least_conn;
    server 10.0.1.11:8080 weight=2 max_fails=3 fail_timeout=30s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=30s;
    server 10.0.1.13:8080 backup;
}

server {
    listen 443 ssl;
    server_name api.shop.example;
    # ssl_certificate and key directives here: TLS ends at the balancer

    location /api/ {
        proxy_pass http://api_servers;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_next_upstream error timeout http_502 http_503;
    }
}

Sticky sessions, TLS termination and routing

  • Sticky sessions (session affinity) pin a client to one server using a cookie or IP hash. Downsides: uneven load, lost sessions when the server dies, harder deploys. Prefer stateless apps with a shared session store.
  • TLS termination: the balancer holds the certificate, decrypts, and talks plain HTTP (or re-encrypts) to backends. This centralises certificates and saves CPU on app servers. Inside a trusted network plain HTTP is common; stricter setups re-encrypt (end-to-end TLS) or use mutual TLS.
  • Path and host routing: /api/* to the API pool, /ws/* to the WebSocket pool, admin.shop.example to a locked-down pool. Also blue-green and canary rollouts by weights.
  • Client IP: behind an L7 balancer the app sees the balancer's IP; read X-Forwarded-For (and configure Spring Boot's forwarded-headers support).

Making the load balancer itself highly available

A single balancer is a new single point of failure. Options: run two in active-passive with a floating virtual IP that moves on failure (keepalived and VRRP for self-managed), or active-active behind DNS or anycast. Cloud load balancers (ALB, NLB, Google Cloud Load Balancing) are already distributed across zones and managed for you. In Kubernetes the Service, Ingress and the cloud load balancer play these roles (DevOps · Module 5). There is also client-side load balancing (the client library such as Spring Cloud LoadBalancer picks an instance from a service registry) and a service mesh sidecar, both common between internal services.

Failure modes

  • All servers fail health checks together (a bad check) and traffic goes nowhere.
  • Retry storms: the balancer retries failed requests on other servers and doubles the load on an already struggling pool. Limit retries and use backoff.
  • Uneven load from sticky sessions or from a few very heavy clients.
  • Thundering herd on a recovering server; slow start helps.
  • Idle timeouts: the balancer closes long-lived connections (WebSockets, long polls) unless timeouts are raised and heartbeats sent.

Interview angle

  • "An L7 balancer routes by path and terminates TLS; an L4 balancer is faster and good for raw TCP. I use least connections when request durations vary, and active health checks on a readiness endpoint."
  • "The balancer is redundant: two across zones, or a managed cloud balancer."
  • Mention connection draining for zero-downtime deployments, and that sticky sessions are a smell rather than a design.

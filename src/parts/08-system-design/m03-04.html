Design an elevator system

Each elevator keeps its own direction and sorted sets of stops and serves them with a LOOK-style sweep (go one way serving stops, then reverse); a controller assigns each new request to the best elevator through a swappable selection Strategy.

Requirements and assumptions

Functional:

  • A building has N floors and M elevators.
  • Hall call: a person on a floor presses UP or DOWN; the system sends one elevator.
  • Cabin request: a person inside presses a destination floor.
  • Each elevator moves one floor at a time, stops at requested floors and idles when nothing is pending.

Non-functional: requests arrive from many threads at once; the selection rule must be replaceable; no starvation of far floors.

Assumptions: no weight limit, no door timing (doors open instantly), no emergency mode, time is simulated by calling step(), and a hall call is served as "go to that floor" (direction-aware pickup is an extension).

The scheduling idea

A naive elevator serves requests in arrival order (FCFS) and zig-zags. Disk schedulers solved the same problem with SCAN: keep going in one direction serving every request on the way, then reverse. LOOK is SCAN that reverses at the last pending request instead of the building's end. It is simple and avoids starvation.

Entities

  • Direction (enum UP, DOWN, IDLE).
  • Elevator: id, current floor, direction, two TreeSets of stops (up and down). Owns its movement.
  • ElevatorSelector (interface): picks the elevator for a hall call. A Strategy.
  • ElevatorController: receives requests, asks the selector, forwards. Facade.

Key design decisions

  • Two sorted sets per elevator: TreeSet gives ordered stops and O(log n) add and remove. Going up, the next stop is simply the next floor reached; going down likewise.
  • Strategy for dispatch (Module 2): nearest idle, nearest moving toward the caller, least loaded, zoned. Swap without touching the controller.
  • State per elevator: the direction enum is the minimum. If doors, maintenance and overload matter, turn it into the State pattern (same idea as the vending machine).
  • Simulated time: step() moves one floor. A real scheduler thread calls stepAll() every second. Tests call it directly, no sleeping.

Core code: the elevator

import java.util.TreeSet;

enum Direction { UP, DOWN, IDLE }

class Elevator {
    private final int id;
    private int floor = 0;
    private Direction direction = Direction.IDLE;
    private final TreeSet<Integer> upStops = new TreeSet<>();
    private final TreeSet<Integer> downStops = new TreeSet<>();

    Elevator(int id) { this.id = id; }

    synchronized int floor() { return floor; }
    synchronized Direction direction() { return direction; }
    int id() { return id; }

    synchronized void addStop(int target) {
        if (target == floor) { arrive(); return; }          // already here
        if (target > floor) upStops.add(target); else downStops.add(target);
        if (direction == Direction.IDLE) {
            direction = (target > floor) ? Direction.UP : Direction.DOWN;
        }
    }

    /** Move one floor in the current direction (one tick of time). */
    synchronized void step() {
        switch (direction) {
            case UP -> {
                floor++;
                if (upStops.remove(floor)) arrive();
                if (upStops.isEmpty()) {
                    direction = downStops.isEmpty() ? Direction.IDLE : Direction.DOWN;
                }
            }
            case DOWN -> {
                floor--;
                if (downStops.remove(floor)) arrive();
                if (downStops.isEmpty()) {
                    direction = upStops.isEmpty() ? Direction.IDLE : Direction.UP;
                }
            }
            case IDLE -> { }
        }
    }

    private void arrive() {
        System.out.println("Elevator " + id + " stops at " + floor);
    }
}

Core code: selector and controller

import java.util.Comparator;
import java.util.List;

interface ElevatorSelector {
    Elevator select(List<Elevator> all, int floor);
}

class NearestSelector implements ElevatorSelector {
    private static final int AWAY_PENALTY = 100;

    public Elevator select(List<Elevator> all, int floor) {
        return all.stream()
                .min(Comparator.comparingInt((Elevator e) -> cost(e, floor)))
                .orElseThrow();
    }

    private int cost(Elevator e, int floor) {
        int distance = Math.abs(e.floor() - floor);
        Direction d = e.direction();
        boolean toward = (d == Direction.UP && floor >= e.floor())
                      || (d == Direction.DOWN && floor <= e.floor());
        return (d == Direction.IDLE || toward) ? distance : distance + AWAY_PENALTY;
    }
}

class ElevatorController {
    private final List<Elevator> elevators;
    private final ElevatorSelector selector;
    private final int floors;

    ElevatorController(List<Elevator> elevators, ElevatorSelector selector, int floors) {
        this.elevators = List.copyOf(elevators);
        this.selector = selector;
        this.floors = floors;
    }

    void requestElevator(int floor, Direction wanted) {
        checkFloor(floor);
        selector.select(elevators, floor).addStop(floor);   // hall call
    }

    void selectFloor(int elevatorId, int floor) {
        checkFloor(floor);
        elevators.get(elevatorId).addStop(floor);          // cabin request
    }

    void stepAll() { elevators.forEach(Elevator::step); }

    private void checkFloor(int floor) {
        if (floor < 0 || floor >= floors) {
            throw new IllegalArgumentException("No such floor: " + floor);
        }
    }
}

public class ElevatorDemo {
    public static void main(String[] args) {
        var ctl = new ElevatorController(
                List.of(new Elevator(0), new Elevator(1)), new NearestSelector(), 10);
        ctl.requestElevator(5, Direction.UP);     // elevator 0 is chosen (tie, first wins)
        ctl.selectFloor(0, 8);
        for (int i = 0; i < 8; i++) ctl.stepAll();
    }
}

Concurrency

  • All mutable state of an elevator is touched only inside synchronized methods, so a cabin press and the scheduler tick cannot corrupt the sets.
  • The selector reads floor and direction from several elevators without a global lock. The picture may be slightly stale, which is acceptable for a heuristic: the worst case is a slightly worse choice, never a wrong state.
  • One scheduler thread (ScheduledExecutorService) drives stepAll(); request threads only add stops.

Edge case: never hold two elevator locks together

The controller never locks two elevators at once, so there is no deadlock. If a feature needs to move a stop from one elevator to another, lock in id order.

Edge cases

  • Request for the current floor: open the door, no movement.
  • Duplicate requests for the same floor: sets ignore duplicates.
  • Invalid floor: rejected by the controller.
  • Request behind the current direction: parked in the other set; served after the sweep, so a far floor waits at most one sweep (no starvation).
  • Hall call direction: a person going DOWN at floor 6 should only be picked by an elevator that will continue down. The simple version ignores the direction; the direction-aware version keeps hall calls separate from cabin stops.

Extensions interviewers ask

  • Multiple elevators: already modelled; discuss other selectors (zones, least busy).
  • Peak-hour logic (morning rush to floor 0): a selector that parks idle elevators on the ground floor.
  • Weight and capacity: a load field; skip hall calls if full.
  • Express and VIP elevators: a flag per elevator and a filtering selector.
  • Maintenance mode: a State that rejects new stops and finishes current ones.
  • Display panel: an Observer on elevator movement.

  2. 5 min: explain SCAN/LOOK in two sentences with the floor drawing.
  3. 8 min: diagram: controller, elevator, selector Strategy.
  4. 20 min: code Elevator.addStop/step, then selector and controller.

Design an LRU cache (HashMap + doubly linked list)

An LRU cache evicts the least recently used entry when full; combine a HashMap for O(1) lookup with a doubly linked list that keeps entries in recency order, so both get and put run in O(1).

Requirements and assumptions

  • get(key) returns the value or null, and marks the entry most recently used.
  • put(key, value) inserts or updates, marks it most recently used, and if the size exceeds capacity removes the least recently used entry.
  • Both operations O(1) average time.
  • Generic in key and value; capacity fixed at construction (must be positive).
  • Then: thread safety.

Why two structures

Structure aloneLookupMove to frontEvict oldest
HashMapO(1)no orderno order
Doubly linked listO(n)O(1) if you hold the nodeO(1) at the tail
Both togetherO(1)O(1)O(1)

The map gives you the node for a key in O(1). Because the list is doubly linked, you can unlink that node without scanning (you know its prev and next). The head side holds the most recently used; the tail side holds the eviction candidate.

Key design decisions

  • Sentinel head and tail nodes mean insert and remove never check for null neighbours.
  • The node stores its key so eviction can remove the entry from the map: you find the tail node, then need its key to call map.remove.
  • Private helper methods unlink(node) and addFirst(node); get and put compose them.
  • A generic class, and no pattern needed. An eviction policy Strategy (LRU, LFU, FIFO) is the extension that earns one (Module 2).

Core code

import java.util.HashMap;
import java.util.Map;

public class LRUCache<K, V> {
    private static final class Node<K, V> {
        final K key;
        V value;
        Node<K, V> prev, next;
        Node(K key, V value) {
            this.key = key;
            this.value = value;
        }
    }

    private final int capacity;
    private final Map<K, Node<K, V>> map = new HashMap<>();
    private final Node<K, V> head = new Node<>(null, null);   // most recent side
    private final Node<K, V> tail = new Node<>(null, null);   // least recent side

    public LRUCache(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("capacity must be > 0");
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public synchronized V get(K key) {
        Node<K, V> n = map.get(key);
        if (n == null) return null;
        unlink(n);
        addFirst(n);                       // now most recently used
        return n.value;
    }

    public synchronized void put(K key, V value) {
        Node<K, V> n = map.get(key);
        if (n != null) {                   // update existing
            n.value = value;
            unlink(n);
            addFirst(n);
            return;
        }
        if (map.size() == capacity) {      // evict least recently used
            Node<K, V> lru = tail.prev;
            unlink(lru);
            map.remove(lru.key);
        }
        n = new Node<>(key, value);
        map.put(key, n);
        addFirst(n);
    }

    public synchronized int size() { return map.size(); }

    private void unlink(Node<K, V> n) {
        n.prev.next = n.next;
        n.next.prev = n.prev;
    }

    private void addFirst(Node<K, V> n) {
        n.next = head.next;
        n.prev = head;
        head.next.prev = n;
        head.next = n;
    }
}
public class LRUDemo {
    public static void main(String[] args) {
        LRUCache<String, Integer> cache = new LRUCache<>(2);
        cache.put("a", 1);
        cache.put("b", 2);
        System.out.println(cache.get("a"));   // a becomes most recent
        cache.put("c", 3);                    // evicts b
        System.out.println(cache.get("b"));
        System.out.println(cache.get("c"));
    }
}

The LinkedHashMap shortcut

Java already has this structure. A LinkedHashMap built with accessOrder = true moves an entry to the end on every access, and removeEldestEntry lets you evict automatically.

import java.util.LinkedHashMap;
import java.util.Map;

class LruMap<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LruMap(int capacity) {
        super(16, 0.75f, true);                  // true = access order
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;                // called after each put
    }
}

Which should you write in the interview?

Say the shortcut first ("in production I would use LinkedHashMap with access order, or Caffeine"), then offer to build it by hand, which is what the question usually wants. Writing only the shortcut can look like dodging the data structure.

Thread safety

The simplest correct version is what the code above does: synchronized on every method. Note that even get must be synchronized, because it writes (it reorders the list). A ConcurrentHashMap alone does not help, since map and list must change together as one step.

  • One lock: simple, correct, becomes a bottleneck under heavy reads.
  • Read-write lock: does not help, because every read is a write.
  • Segmented (striped) caches: N independent LRU caches chosen by hash(key) % N; each has its own lock, so threads rarely collide. Eviction becomes approximate per segment.
  • Library route: Caffeine records accesses in buffers and applies reordering lazily, so reads barely block. In a Spring app you would use it through the cache abstraction rather than writing your own.

Edge cases

  • Capacity 1: every new key evicts the previous one. The code handles it because eviction happens before the insert.
  • Updating an existing key never evicts anything.
  • Null keys: HashMap allows them but the sentinel nodes also hold null keys; reject null keys explicitly if you want a clean contract.
  • get of a stored null value is indistinguishable from a miss; use Optional or disallow null values.

Extensions interviewers ask

  • TTL (expiry): store expiresAt in the node; check it in get and treat expired as a miss; optionally a cleaner thread.
  • LFU instead of LRU: map from frequency to a linked list of keys, plus a minFrequency counter, for O(1).
  • Pluggable eviction: an EvictionPolicy interface with onAccess and evict (Strategy).
  • Write-through or load on miss: a loader function passed to the constructor, used by get.
  • Distributed cache: consistent hashing across nodes (HLD topic, later modules).

How to present this in 45 minutes

  1. 3 min: clarify get/put semantics, capacity, generics, thread safety.
  2. 5 min: explain why a map alone or a list alone fails; draw map plus list.
  3. 20 min: write Node, unlink, addFirst, then get and put.
  4. 10 min: run the example, mention the LinkedHashMap version.
  5. 7 min: thread safety options and TTL or LFU follow-ups.

Strong vs eventual consistency, consistency models and quorums

Strong (linearizable) consistency makes a distributed store look like one copy, eventual consistency lets replicas catch up later, and in between sit useful guarantees such as read-your-writes, monotonic reads and causal consistency; quorums (R + W > N) let you tune the trade-off per request.

Why replicas disagree

To survive failures and serve more reads, data is copied to several nodes. A write reaches the copies at slightly different times: network delay, a slow node, an asynchronous replication stream. In the gap, two readers can ask two nodes and get two different answers. A consistency model is the promise a system makes about which answers are allowed. Stronger promises are easier for application programmers but cost latency and availability.

The models, strongest to weakest

ModelPromise (one line)Example
Strong / linearizableEvery read returns the latest completed write; the system behaves like a single copy with one global orderBank balance, seat lock, etcd, Spanner
SequentialAll clients see the operations in the same order, though not necessarily real-time orderSome coordination services
CausalIf B happened because of A (a reply to a comment), everyone sees A before B; unrelated writes may appear in any orderComment threads, chat replies
Read-your-writesAfter you write, your own later reads see that writeEdit profile, then refresh and see the change
Monotonic readsOnce you have seen a value, you never see an older one later (time does not go backwards)Scrolling a feed without items vanishing
EventualIf writes stop, all replicas converge to the same value eventually; no promise whenDNS, like counts, Cassandra at low consistency levels

Strong consistency is the simplest to reason about, but it needs coordination (a leader or consensus such as Raft or Paxos) on every write and often on reads, so it costs latency, and during a partition the minority side cannot proceed. Eventual consistency is fast and always available, but the application must tolerate stale reads and conflicting writes.

A stale read, step by step

Ways to give users read-your-writes without making everything strongly consistent:

  • Read from the primary for a short window (for example 5 seconds) after the user writes.
  • Route a user's reads to the primary for data they own, and to replicas for other people's data.
  • Remember the log position or version of the user's last write and read only from a replica that has caught up to it.
  • Sticky routing of a user to one replica also gives monotonic reads.

Quorums: N, R and W in simple words

In leaderless stores such as Cassandra, DynamoDB-style systems and Riak, data is stored on N replicas. A write is reported successful when W replicas have acknowledged it. A read asks R replicas and returns the newest version among them.

If R + W > N, every read set overlaps every write set in at least one replica,
so a read always includes at least one node that has the latest write.

N = 3 (three copies)
W = 2, R = 2  → R + W = 4 > 3  → reads see the latest write (strong-ish)
W = 1, R = 1  → R + W = 2 ≤ 3  → fast, but reads may be stale (eventual)
W = 3, R = 1  → R + W = 4 > 3  → fast reads, slow writes, writes fail if any node is down
W = 1, R = 3  → R + W = 4 > 3  → fast writes, slow reads

A quorum is not a full guarantee of linearizability: sloppy quorums, concurrent writes, clock skew and nodes that join or leave can still produce surprises. Systems add read repair (fix stale replicas when a read notices a difference), hinted handoff (hold a write for a down node) and anti-entropy (background sync) to converge.

Common settings are N = 3 with quorum reads and writes (R = W = 2). That tolerates one failed replica and still reads fresh data. In Cassandra you choose per query: ONE, QUORUM, ALL, or a local variant per data centre.

Conflict resolution when writes diverge

  • Last write wins (LWW): keep the highest timestamp. Simple, but clocks drift and silently drops a concurrent update.
  • Version vectors: detect that two writes were concurrent and keep both versions for the application to merge (the Dynamo shopping-cart approach).
  • CRDTs: data types designed so concurrent updates merge automatically (counters, sets). Good for likes and collaborative editing.

Choosing consistency per feature

FeatureMinimum consistencyWhy
Payment, wallet debitStrong (single leader, transaction)Double spend is unacceptable

Comment threadCausalA reply must not appear before its parent

Search results, recommendationsEventualIndex updates seconds later are fine

The expensive part of a system (payments) can be strongly consistent in a small, well-protected database, while the high-volume parts (feed, counters) are eventually consistent. Mixing models in one product is normal.

Exception: eventual consistency is not "no consistency"

Eventual consistency promises convergence once writes stop. Production systems usually converge in milliseconds to seconds. The danger is not that data is wrong forever, but that the application logic (for example "check balance, then debit") assumes freshness it does not have.

Common mistake: reading the balance from a replica before debiting

A check-then-act sequence on stale data lets two requests both pass the check. Do the check and the update on the primary in one transaction, or use a conditional update such as UPDATE ... SET balance = balance - 800 WHERE id = ? AND balance >= 800.

Interview angle

  • "With N = 3, W = 2 and R = 2 the read and write sets overlap, so reads see the latest write while tolerating one node down."
  • Name the model you need instead of just saying "eventual": read-your-writes for profile edits, causal for comments.
  • Explain how you would fix a stale read after a write (read from primary briefly, or track the replica position).

Interview questions — HLD fundamentals

What do system design interviews test, and how do you structure your answer?

They test whether you can handle an open problem: clarify requirements, estimate scale, propose a simple design, find the bottleneck, and justify trade-offs. A structure that works: clarify scope, list functional and non-functional requirements, estimate load, define the API and data model, draw the high-level design, deep-dive into the hard part, then cover failures and scaling.

When would you choose gRPC over REST?

For internal service-to-service calls where latency, payload size and a strict contract matter. gRPC uses HTTP/2 and Protocol Buffers, giving smaller binary messages, multiplexing, generated clients and streaming. REST is better at the public edge: browsers call it natively, it is easy to debug and cache, and any partner can use it.

WebSockets, SSE or long polling for live notifications?

If only the server pushes (notifications, scores), SSE is the lightest: plain HTTP with auto-reconnect. If both sides send frequently (chat, games, collaboration), use WebSockets, and accept the cost of one open connection per user. Long polling is a fallback when proxies block the others. For infrequent updates, plain polling every 30 seconds may be enough.

What is the difference between latency and throughput?

Latency is the time one request takes; throughput is how many requests complete per second. A motorway analogy: latency is one car's journey time, throughput is cars per hour. More servers raise throughput but do not make one request faster. Caching and nearby servers cut latency. Batching raises throughput but can raise per-item latency.

Why use p99 instead of the average latency?

Latency distributions have a long tail. An average of 200 ms can hide 1% of requests taking ten seconds. Those users are real, and a page with many backend calls hits the slow tail often: with 20 calls and a 1% slow chance each, about 18% of page loads are slow. SLOs are therefore stated as percentiles, for example "p99 under 300 ms".

Estimate the requests per second for 10 million daily users making 20 requests each.

10 million × 20 = 200 million requests per day. Divide by about 86,400 seconds: roughly 2,300 requests per second on average. With a peak factor of 3, plan for about 7,000 RPS. At about 700 RPS per instance that is 10 instances at peak, and about 20 with headroom and zone redundancy.

What is Little's law and how do you use it?

L = λ × W: requests in flight equals arrival rate times time in system. At 2,000 RPS with 50 ms per request, 100 requests are in flight. It sizes thread and connection pools, and shows why a slow dependency is dangerous: if a call goes from 50 ms to 500 ms, concurrency needed grows tenfold, pools run out and the service stalls.

Vertical vs horizontal scaling: which first, and why?

Vertical is simplest (a bigger machine, no code changes) so it is a good first step, especially for databases. But it has a ceiling, costs rise steeply and it is a single point of failure. Horizontal scaling adds machines behind a load balancer and has no hard ceiling, but needs stateless services and shared or partitioned data. Typically you scale the stateless app tier out and the database up first, then add replicas and shards.

What makes a service stateless, and where do sessions go?

A stateless service keeps no per-client data in its own memory or disk between requests, so any instance can handle any request. Sessions move to Redis (shared store, instant revocation) or to a signed JWT (no lookup, but harder to revoke). Sticky sessions work but cause uneven load and lose sessions when an instance dies. Files go to object storage, scheduled jobs use a lock.

What does 99.9% availability mean in downtime?

(1 − 0.999) × one year = about 8.77 hours per year, or about 43 minutes per month. 99.99% is about 52 minutes a year, and 99.999% about 5 minutes a year. Each extra nine costs far more and usually requires automatic failover because humans cannot respond in minutes.

Three components each have 99.9% availability. What is the total in series and what if two are in parallel?

In series you multiply: 0.9993 ≈ 0.997, so 99.7% (about 26 hours of downtime a year). Two in parallel: 1 − (0.001 × 0.001) = 99.9999%, assuming failures are independent. In practice shared racks, zones, deploys and bugs break that assumption, so redundancy must be spread across failure domains.

Explain the CAP theorem with an example. Why is "CA" not a real choice?

When a network partition separates replicas, a system must choose: refuse some requests to stay consistent (CP) or answer with possibly stale data to stay available (AP). Example: Mumbai and Chennai lose their link; Mumbai accepts a withdrawal; Chennai cannot know. Partitions cannot be prevented in a real network, so P is forced, and the only choice is C or A during the partition. "CA" only describes a system that is not distributed.

What does PACELC add to CAP?

If there is a Partition choose Availability or Consistency; Else, in normal operation, choose Latency or Consistency. It captures the daily cost of strong consistency: waiting for replicas to acknowledge. Cassandra defaults to PA/EL (fast and available), while a single-primary database with synchronous replication is PC/EC.

What is a quorum and when does R + W > N matter?

With N replicas, a write waits for W acknowledgements and a read queries R replicas. If R + W > N the read and write sets must share at least one replica, so a read includes a node with the latest write. N = 3, R = W = 2 is the common setting: one node can be down and reads stay fresh. Lower R and W give speed and availability but allow stale reads.

How would you pick consistency for payments vs likes?

Payments use strong consistency: one leader, transactions, conditional updates; an error is better than a double spend. Likes use eventual consistency: availability and latency matter more, and small count errors do not matter. Profile edits need read-your-writes. Consistency is chosen per feature, not once per product.

Cheat sheet — HLD fundamentals

  • Interview flow clarify, requirements, estimate, API and data, high-level design, deep dive, failures.
  • Request path client, DNS, CDN, load balancer, app servers, cache, database, queue, workers.
  • REST default for public APIs, JSON, easy caching, no streaming.
  • gRPC HTTP/2 plus Protobuf, fast internal calls, streaming, not browser-native.
  • WebSocket full duplex, one open connection per user, stateful.
  • SSE server-to-client push over HTTP with auto-reconnect.
  • Polling short polling wastes requests; long polling holds the request open.
  • Webhook the other system calls you; verify signature, be idempotent, reply fast.
  • Latency vs throughput time per request vs requests per second.
  • Percentiles use p50, p95, p99; averages hide the tail.
  • Latency ladder RAM about 100 ns, SSD about 100 µs, same-DC hop about 0.5 ms, cross-continent about 100 ms.
  • Little's law L = λ × W (in flight = rate × time).
  • Time constants a day is about 105 s; 1 million per day is about 12 per second.
  • Estimation average RPS = per day / 86,400; peak = 2–5x average; storage = items × size × days × replicas.
  • Scale up vs out up is simple but capped; out needs stateless services and a load balancer.
  • Stateless no per-client memory or disk; sessions in Redis or JWT, files in S3.
  • Nines 99.9% about 8.77 h/year; 99.99% about 52.6 min/year; 99.999% about 5.26 min/year.
  • Series multiply availabilities (worse); parallel 1 − product of failure chances (better).
  • SLI / SLO / SLA measurement, internal target, customer contract; the gap is the error budget.
  • SPOF any single component whose failure stops the system; remove with redundancy.
  • Failover active-passive (standby, slower) vs active-active (all serve, more complex); beware split-brain.
  • CAP during a partition choose consistency (CP) or availability (AP); "CA" is not a distributed option.
  • PACELC partition: A or C; else: latency or consistency.
  • Quorum R + W > N makes read and write sets overlap; N = 3, R = W = 2 is typical.
  • Models strong, causal, read-your-writes, monotonic reads, eventual; choose per feature.

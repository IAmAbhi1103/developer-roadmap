Design principles are the habits that keep code easy to change. A program that works today but breaks in three places whenever a requirement moves is a badly designed program, even if every test passes. This module gives you the vocabulary (cohesion, coupling, SOLID, DRY, KISS, YAGNI) and the practical skills (clean code, spotting code smells, drawing UML) that every design discussion and every code review uses.

It builds on Core Java · Module 2 (OOP), which explains how classes, interfaces and polymorphism work. Here the question changes from "how does it work?" to "how should I arrange it so it survives change?". The next module, Design patterns, shows ready-made solutions that apply these principles, and LLD interview problems asks you to use both.

  • Judge a design with two ideas: high cohesion and low coupling.
  • Explain each SOLID principle in 30 seconds and show a violating and a fixed version in Java.
  • Tell DRY from accidental duplication, and use KISS and YAGNI to stop over-engineering.
  • Refactor messy code using clean-code rules and name the code smell you are fixing.
  • Draw class diagrams and sequence diagrams and map each arrow to Java code.

What good design means: cohesion, coupling and designing for change

Good design means code that is cheap to change: each class does one focused job (high cohesion), classes know as little as possible about each other (low coupling), and details are hidden behind interfaces (encapsulation).

Nobody can predict every future requirement. Tomorrow the business adds a new payment method, a new tax rule, or moves from MySQL to PostgreSQL. A design is good when such a change touches few places and breaks nothing else. A design is bad when one small change forces edits in ten files. Almost every principle in this module is a way to measure or improve this one property: cost of change.

Cohesion: things that belong together

Cohesion measures how strongly the parts inside one module (a method, a class, a package) belong together. In a highly cohesive class, every field and method serves one clear purpose. You can describe the class in one sentence without using "and".

Low cohesion: a grab-bag

public class Utils {
    public static String formatRupees(long paise) { /* ... */ return ""; }
    public static boolean isValidPan(String pan) { /* ... */ return true; }
    public static void sendSms(String phone, String text) { /* ... */ }
    public static byte[] zip(byte[] data) { /* ... */ return data; }
}

High cohesion: one purpose each

public final class MoneyFormatter {
    public String rupees(long paise) { /* ... */ return ""; }
}
public final class PanValidator {
    public boolean isValid(String pan) { /* ... */ return true; }
}
public interface SmsGateway {
    void send(String phone, String text);
}

Names like Utils, Helper, Manager and Common are warning signs: they attract unrelated code because nobody knows where else it should go. Cohesion also applies to methods: a method validateAndSaveAndEmail() has three purposes.

Coupling: how much one part knows about another

Coupling measures how much one module depends on another. When class A is tightly coupled to class B, a change in B forces a change in A, and you cannot test or reuse A without B. Some coupling is unavoidable (parts must talk), so the goal is loose coupling: depend on a small, stable contract rather than on details.

Kind of couplingWhat A depends onExample
Tight (bad)The concrete classnew MySqlOrderRepository() inside a service
Tight (bad)Another class's internalsorder.getCustomer().getAddress().getCity()
Tight (bad)Shared mutable stateA public static Map that many classes edit

Loose (good)A message or eventPublishing OrderPlaced instead of calling five services

Here is a tightly coupled class and a loosely coupled one:

// Tight: the service creates its own dependency, so you cannot swap or fake it
class ReportService {
    private final PdfWriter writer = new PdfWriter();       // hard-wired
    void publish(String text) { writer.write(text); }
}

// Loose: the service only knows the small interface it needs
interface DocumentWriter {
    void write(String text);
}

class LooseReportService {
    private final DocumentWriter writer;                    // any implementation
    LooseReportService(DocumentWriter writer) { this.writer = writer; }
    void publish(String text) { writer.write(text); }
}

class PdfWriter implements DocumentWriter {
    public void write(String text) { System.out.println("PDF: " + text); }
}

The goal: high cohesion, low coupling

These two travel together. When each class has one focused job, it needs fewer collaborators and talks to them through small interfaces. When responsibilities are mixed, classes reach into each other and coupling rises. If you remember only one sentence from this module, remember this one.

Encapsulation: the root of good design

Encapsulation means hiding data and implementation behind a small public interface (see Core Java). From a design view, it is what makes low coupling possible. If other classes cannot see your fields, they cannot depend on them, so you are free to change them later.

// Exposed: every caller can break the rule and depends on the representation
class WalletBad {
    public long balance;
}
// caller: wallet.balance -= 500;   // overdraft possible, rules scattered in callers

// Encapsulated: the rule lives in one place, the field can change type later
class Wallet {
    private long balanceInPaise;

    void debit(long paise) {
        if (paise <= 0) throw new IllegalArgumentException("Amount must be positive");
        if (paise > balanceInPaise) throw new IllegalStateException("Insufficient funds");
        balanceInPaise -= paise;
    }
    long balance() { return balanceInPaise; }
}

Rule of thumb: expose behaviour (debit), not data (setBalance). Every public getter and setter is a small leak of your design.

Program to an interface, not an implementation

Declare variables, parameters and return types with the most general type that gives you the methods you need. Write List<Order> orders = new ArrayList<>();, not ArrayList<Order> orders = .... Write a method that accepts Collection<Order> when it only loops. On the larger scale, a service depends on a PaymentGateway interface, and the Razorpay or Stripe class is a detail chosen at the edge of the program. The caller then survives any change of implementation, because it never named one.

Designing for change

  1. Find what varies. Payment methods, tax rules, notification channels, report formats: these change often. Business names and core flows change rarely.
  2. Hide what varies behind an interface. Callers depend on the interface and never know which version runs.
  3. Keep the stable part stable. The flow "validate, price, pay, notify" should not be edited when a new payment method arrives.
  4. Do not predict, prepare. You cannot guess every change. Keep code simple and decoupled, then refactor when a real change arrives (see YAGNI).

A quick test for any design: "If requirement X changes, how many files do I edit?" If the answer is one or two, the design is doing its job.

Coupling cannot be zero

  • A system with no coupling does nothing. The aim is to couple to stable abstractions, such as List, PaymentGateway, or a domain event, and not to volatile details.
  • Too many tiny classes can raise coupling too, because readers must hop between files. Balance both goals.
  • Coupling across a network (microservices) is costlier than inside a JVM; see distributed system patterns.

Mistakes to avoid

  • Calling a class "cohesive" because it is in one file. Cohesion is about purpose, not location.
  • Making every field public "for convenience" and every class depend on new ConcreteClass().
  • Creating an interface for every class by habit. Add an interface when there are, or will really be, several implementations or when you need a seam for tests.

Interview: good design

  • What is cohesion and coupling? Cohesion: how well the inside of a module belongs together. Coupling: how much modules depend on each other. Aim for high cohesion and low coupling.
  • How do you reduce coupling? Depend on interfaces, inject dependencies, hide data, communicate with events, and follow the Law of Demeter.
  • How does encapsulation help design? It lets you change internals without touching callers.

The OOP pillars revisited with design in mind

Encapsulation hides change, abstraction names what matters, inheritance reuses a true is-a contract, and polymorphism lets you replace if/else on type with objects that each know their own behaviour: together they are the tools every design principle uses.

Core Java explains how the four pillars work: Core Java · Module 2 has the syntax, rules and examples. This article asks a different question: what does each pillar buy you in a design? Think of them as tools, and of the principles in this module as the instructions for using them.

PillarDesign question it answersPrinciple that depends on it
EncapsulationHow do I stop callers depending on my internals?Low coupling, Tell, Don't Ask
AbstractionWhat is the smallest contract callers need?ISP, DIP
InheritanceWhich types are truly substitutable?LSP, composition over inheritance
PolymorphismHow do I add behaviour without editing old code?OCP, Strategy

Encapsulation: hide what may change

Every private field is a decision you may change later without telling anyone. Design for it: make fields private, make objects immutable when possible (records, final fields), return unmodifiable views or copies of collections, and put the rules next to the data they protect. An Order should expose addItem() and cancel(), not getItems().add(...) and setStatus(...).

Abstraction: name the idea, hide the how

An abstraction is a promise: "give me an Order and I will return a Receipt". The caller does not care about databases or HTTP. A good abstraction is small (few methods), stable (does not change when internals change) and honest (it does not leak details such as SQLException in a method that has nothing to do with SQL). In Java you express abstractions with interfaces and abstract classes; Core Java compares the two.

Inheritance: use sparingly, and only for real is-a

Inheritance is the strongest coupling Java offers. A child sees and depends on its parent's behaviour. Use it when the child truly is a parent in every situation the parent is used (the Liskov test, see LSP) and when the parent was designed to be extended. For code reuse alone, prefer composition.

Polymorphism: replace conditionals with objects

Polymorphism is the engine of design for change. Instead of one method with an if or switch on a type code, you define an interface and let each type implement its own behaviour. Adding a new type then means adding a class, not editing a switch in five places.

// Before: every new shape means editing this method (and every other switch like it)
static double area(String type, double a, double b) {
    switch (type) {
        case "CIRCLE":    return Math.PI * a * a;
        case "RECTANGLE": return a * b;
        default: throw new IllegalArgumentException(type);
    }
}

// After: each shape knows its own area; adding Triangle edits nothing existing
interface Shape { double area(); }
record Circle(double r) implements Shape {
    public double area() { return Math.PI * r * r; }
}
record Rectangle(double w, double h) implements Shape {
    public double area() { return w * h; }
}

Java 21 adds sealed interfaces with pattern-matching switch as a second tool: when the set of types is closed and fixed, a sealed hierarchy with an exhaustive switch is also good design, because the compiler tells you every place to update when you add a type. Choose polymorphic methods when new types are likely; choose sealed types plus switch when new operations are likely.

Design habits from the pillars

  • Private fields, behaviour-rich classes, few setters.
  • Small interfaces named after the role (PaymentGateway), not the technology (RazorpayService).
  • Default to final classes; open a class for extension on purpose.
  • Any switch or instanceof chain on a type is a hint to ask whether polymorphism fits (see code smells).

Interview: OOP pillars from a design view

  • Do not recite definitions only. Say what each pillar protects: encapsulation protects against change in data, abstraction against change in implementation, polymorphism against change in behaviour.
  • Mention that inheritance is the one to be careful with, and say why (fragile base class; see composition over inheritance).

S: Single Responsibility Principle

A class should have only one reason to change: it should serve one actor or one concern, so that a change in business rules, storage or notifications touches only the class that owns that concern.

SOLID is a set of five principles popularised by Robert C. Martin ("Uncle Bob"): Single responsibility, Open/closed, Liskov substitution, Interface segregation, Dependency inversion. They are guidelines, not laws, but they appear in almost every design interview and code review. We take them one at a time, each with a violating version and a fix.

The Single Responsibility Principle (SRP) says: a class should have one, and only one, reason to change. Martin later restated it as: a module should answer to one actor, meaning one group of people who ask for changes. If the finance team and the marketing team both ask for changes to the same class, that class has two responsibilities, and their edits will collide.

The violation: a class that does everything

Look at a typical first draft of order placement. It validates, calculates the price, writes to the database and sends an email, all in one place.

import java.sql.*;
import java.util.List;

record OrderItem(String sku, long unitPaise, int qty) { }
record Order(String id, String customerEmail, List<OrderItem> items) { }

public class OrderService {
    public void placeOrder(Order order) throws SQLException {
        // 1. validation rules (changes when the business rules change)
        if (order.items().isEmpty()) {
            throw new IllegalArgumentException("Order has no items");
        }
        if (!order.customerEmail().contains("@")) {
            throw new IllegalArgumentException("Bad email");
        }
        // 2. pricing (changes when the finance team changes discounts or GST)
        long total = 0;
        for (OrderItem i : order.items()) total += i.unitPaise() * i.qty();
        if (total > 500_000) total = total * 95 / 100;
        // 3. persistence (changes when the database or schema changes)
        try (Connection c = DriverManager.getConnection("jdbc:postgresql://db/shop");
             PreparedStatement ps = c.prepareStatement(
                 "INSERT INTO orders(id, email, total) VALUES (?, ?, ?)")) {
            ps.setString(1, order.id());
            ps.setString(2, order.customerEmail());
            ps.setLong(3, total);
            ps.executeUpdate();
        }
        // 4. notification (changes when marketing wants SMS or a new template)
        System.out.println("Mail to " + order.customerEmail() + ": order " + order.id());
    }
}

There are four reasons to change this class: validation rules, pricing, the database, and the message. Each belongs to a different person or team. The problems are practical:

  • Merge conflicts and regressions. A discount change can accidentally break the SQL.
  • Hard to test. To test the discount you need a live database.
  • No reuse. The pricing logic cannot be used by the "show cart" page.
  • Hard to read. Four concerns are mixed in one method.

The refactoring: one class per reason to change

import java.util.List;

class OrderValidator {
    void validate(Order order) {
        if (order.items().isEmpty()) {
            throw new IllegalArgumentException("Order has no items");
        }
        if (!order.customerEmail().contains("@")) {
            throw new IllegalArgumentException("Bad email");
        }
    }
}

class PriceCalculator {
    long totalInPaise(List<OrderItem> items) {
        long total = 0;
        for (OrderItem i : items) total += i.unitPaise() * i.qty();
        return total > 500_000 ? total * 95 / 100 : total;
    }
}

interface OrderRepository {
    void save(Order order, long totalInPaise);
}

interface OrderNotifier {
    void orderPlaced(Order order);
}

public class OrderService {
    private final OrderValidator validator;
    private final PriceCalculator pricing;
    private final OrderRepository repository;
    private final OrderNotifier notifier;

    public OrderService(OrderValidator validator, PriceCalculator pricing,
                        OrderRepository repository, OrderNotifier notifier) {
        this.validator = validator;
        this.pricing = pricing;
        this.repository = repository;
        this.notifier = notifier;
    }

    public void placeOrder(Order order) {                 // the workflow, nothing else
        validator.validate(order);
        long total = pricing.totalInPaise(order.items());
        repository.save(order, total);
        notifier.orderPlaced(order);
    }
}

OrderService now has one job: coordinate the steps. Its reason to change is "the order workflow changes". The JDBC code lives in a JdbcOrderRepository, the email in an EmailOrderNotifier. You can test PriceCalculator with plain JUnit and no mocks, and replace the notifier with a fake in a test of the service.

How Spring helps

In Spring Boot, the layered structure is SRP at work: @RestController handles HTTP, @Service holds business rules, @Repository talks to the database. Spring's dependency injection then wires the small classes together, so splitting a class into four costs you almost nothing: you declare the collaborators as constructor parameters and the container supplies them.

Common misunderstandings

  • "One class = one method." Wrong. A class may have many methods if they all serve the same responsibility. BigDecimal has dozens of methods and one purpose: decimal arithmetic.
  • "Split everything." Splitting too far creates dozens of tiny classes that each do nothing and are hard to follow. Split along reasons to change, not along lines of code.
  • It is about change, not size. A 400-line class with one reason to change can be fine; a 60-line class that mixes SQL and email is not.
  • Entities and DTOs: a JPA entity that is also the JSON response and also the form object has three reasons to change. Use separate DTOs at the API boundary.

Tip: how to find responsibilities

Describe the class in one sentence. If you need "and" or "or", split it. Ask: "Who would ask me to change this?" If the answer lists several roles (finance, ops, security), you have several responsibilities. Another signal: the class imports packages from unrelated areas (java.sql and javax.mail in one file).

Interview: explain SRP in 30 seconds

"SRP says a class should have only one reason to change. If validation, pricing, database access and email are in one class, any of four teams can break it. I split them so that each class serves one concern, and a coordinator class calls them. It makes code easier to test and to change. It does not mean one method per class; it is about reasons to change." Follow-up: "How do you know when to split?" Answer: when you see unrelated imports, a hard-to-name class, or tests that need heavy setup.

O: Open/Closed Principle

Software entities should be open for extension but closed for modification: you add new behaviour by writing new classes that plug into an existing abstraction, without editing the tested code that already works.

Every time you edit a working class, you risk breaking it. The Open/Closed Principle (OCP), from Bertrand Meyer and popularised by Uncle Bob, says design the code so that new behaviour arrives as new code, not as edits to old code. "Open for extension" means you can add behaviour. "Closed for modification" means the existing, tested source stays untouched.

It is not magic. It works only along the lines of change you anticipated (or have already seen once). You build the abstraction around something that varies, such as a discount rule, and then new variations are new classes.

The violation: a switch that grows forever

enum CustomerType { REGULAR, PREMIUM, STUDENT }

public class DiscountCalculator {
    public long discountInPaise(CustomerType type, long amountInPaise) {
        switch (type) {
            case REGULAR:
                return 0;
            case PREMIUM:
                return amountInPaise * 10 / 100;
            case STUDENT:
                return amountInPaise * 5 / 100;
            default:
                throw new IllegalArgumentException("Unknown type " + type);
        }
    }
}

Marketing now wants a FESTIVE discount, then EMPLOYEE, then FIRST_ORDER. Each one means editing this method, recompiling and retesting every existing branch, and probably editing similar switch blocks elsewhere (the invoice printer, the report). This is a sign that OCP is violated: every new variant edits old code.

The fix: an abstraction and one class per rule

public interface DiscountPolicy {
    boolean appliesTo(CustomerType type);
    long discountInPaise(long amountInPaise);
}

class RegularDiscount implements DiscountPolicy {
    public boolean appliesTo(CustomerType type) { return type == CustomerType.REGULAR; }
    public long discountInPaise(long amount) { return 0; }
}

class PremiumDiscount implements DiscountPolicy {
    public boolean appliesTo(CustomerType type) { return type == CustomerType.PREMIUM; }
    public long discountInPaise(long amount) { return amount * 10 / 100; }
}

class StudentDiscount implements DiscountPolicy {
    public boolean appliesTo(CustomerType type) { return type == CustomerType.STUDENT; }
    public long discountInPaise(long amount) { return amount * 5 / 100; }
}

public class DiscountCalculator {
    private final java.util.List<DiscountPolicy> policies;

    public DiscountCalculator(java.util.List<DiscountPolicy> policies) {
        this.policies = policies;
    }

    public long discountInPaise(CustomerType type, long amountInPaise) {
        return policies.stream()
                .filter(p -> p.appliesTo(type))
                .findFirst()
                .orElseThrow(() -> new IllegalArgumentException("No policy for " + type))
                .discountInPaise(amountInPaise);
    }
}

To add a festive discount you write FestiveDiscount implements DiscountPolicy and add it to the list. DiscountCalculator is closed: it never changes. The set of rules is open: it grows by adding classes. This is the Strategy pattern (Strategy).

How Spring makes OCP easy

Spring can inject all beans of an interface as a List, or as a Map keyed by bean name. You write a new @Component and the calculator finds it, with no registration code:

import org.springframework.stereotype.Component;
import org.springframework.stereotype.Service;
import java.util.List;

@Component
class FestiveDiscount implements DiscountPolicy {          // new class only
    public boolean appliesTo(CustomerType type) { return type == CustomerType.FESTIVE; }
    public long discountInPaise(long amount) { return amount * 15 / 100; }
}

@Service
class DiscountService {
    private final List<DiscountPolicy> policies;           // Spring injects every bean

    DiscountService(List<DiscountPolicy> policies) { this.policies = policies; }
    // same logic as above
}

(The example assumes CustomerType has a FESTIVE constant, added as part of the new feature; adding an enum constant is not editing the calculator.)

Other ways to get OCP

  • Inheritance and the Template Method: a base class fixes the algorithm; subclasses fill in steps (Template Method).
  • Decorator: wrap an object to add behaviour without changing it (Decorator).
  • Plugins and ServiceLoader: new JARs on the classpath add implementations of an interface.
  • Lambdas: pass a Predicate or Comparator instead of hard-coding a rule.

Common misunderstandings and limits

  • You cannot close code against every change. Pick the likely axis of change. If you guess wrong, the abstraction does not help, so wait for the second or third variant before building it (see YAGNI).
  • "Never modify a class" is not the rule. Fixing a bug in PremiumDiscount is a normal edit. The rule is about adding features.
  • A switch over a closed, stable set (days of the week) is fine. The smell is a switch that you keep editing and that is copied in several places.
  • A good test: does adding a feature require editing existing if/else or switch blocks? If yes, OCP is violated.

Mistake: building the framework first

Writing a PolicyFactoryProvider with a plugin system for a rule that has one variant is over-engineering. Write the simple if first. When the second variant arrives, refactor to an interface. When the third arrives, you will thank yourself.

Interview: explain OCP in 30 seconds

"OCP says classes should be open for extension and closed for modification. If I have a switch on customer type for discounts, every new type edits that method. I introduce a DiscountPolicy interface, one class per rule, and the calculator loops over the policies. A new rule is a new class; old code stays untouched. In Spring I inject List<DiscountPolicy> so a new @Component is picked up automatically." Common follow-up: "Is it always possible?" Answer: only along anticipated axes of change; do not abstract early.

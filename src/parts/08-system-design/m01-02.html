L: Liskov Substitution Principle

If S is a subtype of T, you must be able to use an S anywhere a T is expected without breaking the program: a subclass may do more than its parent promises, but never less, and it must not surprise callers.

Barbara Liskov's principle protects the main promise of inheritance and interfaces: code written against the parent type keeps working with every child. If a method takes a Shape, it must work for every Shape you ever create. When a subclass breaks this promise, callers start writing if (x instanceof Special) checks, and polymorphism is lost.

"Is-a" in English is not enough. A square is a rectangle in geometry, but a Square class is not a valid subtype of a mutable Rectangle class. The test is behavioural: can the child stand in for the parent in all the parent's contracts?

The classic violation: Rectangle and Square

class Rectangle {
    protected int width;
    protected int height;

    void setWidth(int w)  { this.width = w; }
    void setHeight(int h) { this.height = h; }
    int area() { return width * height; }
}

class Square extends Rectangle {              // "a square is a rectangle"
    @Override void setWidth(int w)  { this.width = w; this.height = w; }
    @Override void setHeight(int h) { this.width = h; this.height = h; }
}

public class LspDemo {
    static void resize(Rectangle r) {
        r.setWidth(5);
        r.setHeight(4);
        System.out.println(r.area() + " (expected 20)");
    }
    public static void main(String[] args) {
        resize(new Rectangle());
        resize(new Square());
    }
}
20 (expected 20)
16 (expected 20)

The method resize is correct for a Rectangle. With a Square it gives a wrong answer, because Square changed the meaning of setWidth (it also changes the height). The subtype broke the parent's implied contract: "setting the width does not change the height".

Fix: do not model it as inheritance of a mutable class. Make both implement a common read-only abstraction, or make them immutable so the problem disappears.

interface Shape { int area(); }

record Rectangle(int width, int height) implements Shape {
    public int area() { return width * height; }
}

record Square(int side) implements Shape {
    public int area() { return side * side; }
}

Violation 2: the unsupported method

A very common LSP break is a subclass that throws UnsupportedOperationException (or does nothing) for a method it inherited.

// Violating
abstract class Bird {
    abstract void eat();
    abstract void fly();
}
class Sparrow extends Bird {
    void eat() { /* ... */ }
    void fly() { /* ... */ }
}
class Penguin extends Bird {
    void eat() { /* ... */ }
    void fly() { throw new UnsupportedOperationException("Penguins cannot fly"); }
}

static void migrate(java.util.List<Bird> birds) {
    for (Bird b : birds) b.fly();           // crashes when a Penguin is in the list
}

The callers of Bird believe every bird flies. The fix is to split the hierarchy so that the contract matches reality:

interface Bird { void eat(); }
interface Flyer { void fly(); }

class Sparrow implements Bird, Flyer {
    public void eat() { /* ... */ }
    public void fly() { /* ... */ }
}
class Penguin implements Bird {
    public void eat() { /* ... */ }
}

static void migrate(java.util.List<? extends Flyer> flyers) {
    for (Flyer f : flyers) f.fly();         // only things that can fly are accepted
}

Now a Penguin cannot even be passed to migrate: the compiler enforces the contract.

The rules behind LSP

The contract of a method has a before part (preconditions), an after part (postconditions), and rules that always hold (invariants). A valid subtype follows these:

RuleMeaningViolation example
Preconditions: do not strengthenChild accepts at least what the parent acceptsParent takes any amount; child rejects amounts above 10,000
Postconditions: do not weakenChild promises at least what the parent promisesParent never returns null; child returns null
Invariants: keep themRules that always hold, still holdParent keeps balance at 0 or more; child allows negative
Exceptions: no new surprisesChild throws only what the parent's contract allowsChild throws UnsupportedOperationException from an inherited method
History: no new mutationChild must not change what the parent treats as fixedAn immutable parent whose child adds setters

Java helps with some of this: an overriding method cannot throw broader checked exceptions, cannot reduce visibility, and may only narrow the return type (covariance). It cannot enforce the rest. Contracts live in Javadoc, in tests, and in your head.

A realistic example: payment methods

interface PaymentMethod {
    /** Charges the amount. Never returns null; throws PaymentFailedException if declined. */
    Receipt charge(long amountInPaise);
}

class UpiPayment implements PaymentMethod { /* ... */
    public Receipt charge(long amountInPaise) { return new Receipt("UPI", amountInPaise); }
}

// Violating child: returns null for small amounts and refuses large ones silently
class WalletPayment implements PaymentMethod {
    public Receipt charge(long amountInPaise) {
        if (amountInPaise < 100) return null;            // postcondition weakened
        if (amountInPaise > 1_000_000) return null;      // surprise
        return new Receipt("WALLET", amountInPaise);
    }
}
record Receipt(String mode, long paise) { }
class PaymentFailedException extends RuntimeException { }

The checkout code written for PaymentMethod calls receipt.mode() and gets a NullPointerException. The honest fix: WalletPayment throws PaymentFailedException, exactly as the contract says.

Misunderstandings and JDK examples

  • LSP is about behaviour, not syntax. A class can compile as a subtype and still violate LSP.
  • The JDK itself bends LSP: List.of(...), Arrays.asList(...) and Collections.unmodifiableList(...) implement List but throw UnsupportedOperationException on some mutators. It is documented as an "optional operation", and it is a known trade-off. In your own code, avoid it; split read-only and mutable interfaces instead.
  • A subclass that overrides a method with an empty body ("do nothing") is often a violation too: callers expect the effect.
  • Frequent instanceof checks in client code ("if it is a Penguin, skip") are the symptom.

Tip: test the contract once, run it for every subtype

Write an abstract JUnit test class for the interface (PaymentMethodContractTest) with an abstract create() method, and extend it once per implementation. Any subclass that breaks the contract fails the same tests.

Interview: explain LSP in 30 seconds

"LSP says a subtype must be usable wherever its parent type is, without the caller noticing. The standard example: a Square extending a mutable Rectangle breaks code that sets width and height separately. Another sign is a child that throws UnsupportedOperationException. A subclass must not require more, promise less, or throw surprises. The fix is usually to change the hierarchy: smaller interfaces, immutable types, or composition."

I: Interface Segregation Principle

Clients should not be forced to depend on methods they do not use: prefer several small, role-specific interfaces over one fat interface.

An interface is a contract the implementer must fulfil and the client sees. When one interface has twenty methods, every implementer must write all twenty (many as empty stubs), and every client sees methods it should never call. A change to a method that a client never uses can still force that client to recompile and retest. The Interface Segregation Principle (ISP) says: split the interface by client role.

The violation: a fat interface

interface MultiFunctionDevice {
    void print(Document d);
    void scan(Document d);
    void fax(Document d);
    void staple(Document d);
}

class OfficePrinterPro implements MultiFunctionDevice {      // can do all
    public void print(Document d)  { /* ... */ }
    public void scan(Document d)   { /* ... */ }
    public void fax(Document d)    { /* ... */ }
    public void staple(Document d) { /* ... */ }
}

class BasicPrinter implements MultiFunctionDevice {          // can only print
    public void print(Document d)  { /* ... */ }
    public void scan(Document d)   { throw new UnsupportedOperationException(); }
    public void fax(Document d)    { throw new UnsupportedOperationException(); }
    public void staple(Document d) { throw new UnsupportedOperationException(); }
}
class Document { }

Three methods in BasicPrinter lie. That also breaks LSP: callers of MultiFunctionDevice cannot trust scan. A fat interface is usually the cause of an LSP violation.

The refactoring: role interfaces

interface Printer  { void print(Document d); }
interface Scanner  { void scan(Document d); }
interface Fax      { void fax(Document d); }

class BasicPrinter implements Printer {
    public void print(Document d) { /* ... */ }
}

class OfficePrinterPro implements Printer, Scanner, Fax {
    public void print(Document d) { /* ... */ }
    public void scan(Document d)  { /* ... */ }
    public void fax(Document d)   { /* ... */ }
}

class ReportJob {
    private final Printer printer;                 // needs only printing
    ReportJob(Printer printer) { this.printer = printer; }
    void run(Document d) { printer.print(d); }
}

ReportJob asks only for a Printer. It works with both devices, and a change in Fax cannot affect it. Java lets a class implement many interfaces, so splitting costs nothing for implementers who do everything.

A backend example: the repository

Suppose you start with this interface:

// Fat: login code, admin code and report code all see everything
interface UserStore {
    User findById(long id);
    User findByEmail(String email);
    void save(User user);
    void delete(long id);
    List<User> searchAll(String text);
    void exportToCsv(Path file);
}

// Segregated by client role
interface UserReader { User findById(long id); User findByEmail(String email); }
interface UserWriter { void save(User user); void delete(long id); }
interface UserSearch { List<User> searchAll(String text); }
interface UserExporter { void exportToCsv(Path file); }

The login service gets only a UserReader. If someone injects a mock in a test, there is one method to fake, not six. The read-only report job cannot call delete by accident, because the type does not allow it. That is also a security benefit.

(Assumed types for the fragment: User, java.util.List, java.nio.file.Path.)

ISP in the JDK and Spring

  • Java Collections: Iterable, Collection, List, RandomAccess are layers. A method that only loops should take Iterable or Collection, not ArrayList.
  • Functional interfaces: Runnable, Supplier, Comparator each have one method: the smallest possible role interface.
  • Spring Data: Repository, CrudRepository and PagingAndSortingRepository are separate layers, so you extend only what you need. A custom repository can extend plain Repository and declare just the two query methods the service needs.
  • Servlet and Spring listeners: callbacks like ApplicationListener have a single method.

Limits and misunderstandings

  • ISP does not mean "one method per interface" for everything. Group methods that always change together and are used together.
  • Too many micro-interfaces make code hard to navigate. Split when two kinds of clients use different subsets.
  • It applies to classes too: a class with a wide public API forces clients to know too much. Expose a narrow API.
  • Java 8 default methods can hide a fat interface: adding a new default method to a widely used interface is easier than splitting it, but the interface is still fat.

Mistake: empty or throwing implementations

If you write throw new UnsupportedOperationException() or an empty body to satisfy an interface, stop. Either the interface is too big (ISP) or the subtype is wrong (LSP). Fix the interface.

Why the principle exists

Robert C. Martin formulated ISP while helping a company with a printer system in which one big Job class served every kind of client: print jobs, staple jobs and fax jobs all used the same class. Any change to the stapling code forced a rebuild and redeploy of the code that only printed. The cost was not the bad design itself; it was the ripple. A client that depends on a method it never calls still depends on the interface as a whole, so every change to the interface reaches it.

You feel the same pain today: a unit test must fake six methods when the class under test uses one, a new method on a shared interface breaks twelve implementers, and a junior developer calls delete() on a repository handed to a read-only report. ISP asks you to design the interface from the client's point of view: "what does this caller need?", not "what can this implementation do?".

A second example: payments

A payment service starts with one interface. Checkout needs charge, the support team needs refund, and a nightly job needs settle. Putting them in one PaymentOps interface looks tidy, until you add a cash-on-delivery provider that cannot do online refunds and has no settlement. Now it must throw from two methods.

interface Charger  { String charge(String orderId, long paise); }
interface Refunder { void refund(String paymentId, long paise); }
interface Settler  { void settle(java.time.LocalDate day); }

// An online provider plays all three roles
class CardProvider implements Charger, Refunder, Settler {
    public String charge(String orderId, long paise) { return "PAY-" + orderId; }
    public void refund(String paymentId, long paise) { /* call the bank */ }
    public void settle(java.time.LocalDate day)      { /* send the batch file */ }
}

// Cash on delivery only plays one role: no fake methods
class CashOnDelivery implements Charger {
    public String charge(String orderId, long paise) { return "COD-" + orderId; }
}

class CheckoutService {
    private final Charger charger;                    // sees one method only
    CheckoutService(Charger charger) { this.charger = charger; }
    String pay(String orderId, long paise) { return charger.charge(orderId, paise); }
}

Wiring is easy: one CardProvider object is passed to the checkout as a Charger, to the support tool as a Refunder and to the job as a Settler. The object is the same; the view of it is narrow. A test for CheckoutService can even use a lambda: new CheckoutService((id, p) -> "FAKE"), because a single-method interface is a functional interface.

ISP in the JDK, honestly

The JDK is not perfect. Collection.add is an "optional operation": List.of(...) and Collections.unmodifiableList return lists whose add throws UnsupportedOperationException. That is a fat interface leaking into an LSP problem, and the JDK accepted it for convenience in 1998. Functional interfaces such as Supplier and Comparator show the opposite style: one method, one role. Use these examples to show you can see the trade-off, not only the textbook case.

ISP, SRP and LSP: how they differ

PrincipleLooks atQuestion it asks
SRPA classDoes it have more than one reason to change?
ISPAn interface, from each client's sideDoes any client depend on methods it does not use?
LSPA subtypeCan it replace its parent without surprises?
DIPThe direction of a dependencyDoes high-level code own the abstraction?

A fat interface is often an SRP problem in disguise: an interface that mixes reading, writing and exporting has several reasons to change. Splitting by client role usually fixes both at once.

Wrong: the client takes the fat type

class ReportJob {
    private final UserStore store;          // can also delete and export
    ReportJob(UserStore store) { this.store = store; }
    long countActive() {
        return store.searchAll("").size();
    }
}

Right: the client asks for its role

class ReportJob {
    private final UserSearch search;        // exactly what it uses
    ReportJob(UserSearch search) { this.search = search; }
    long countActive() {
        return search.searchAll("").size();
    }
}

Rules for applying ISP

  • Design the interface for the caller. Write the client first, see which calls it makes, and shape the interface to match.
  • Declare parameters, fields and constructor arguments with the narrowest type that works.
  • If an implementation must throw UnsupportedOperationException or leave a body empty, the interface is wrong.

Conventions

  • Name role interfaces after what the client wants: Charger, UserReader, Notifier. Avoid IManager and Handler2.
  • Keep one fat implementation class if it is natural; the segregation is in the interfaces, not necessarily in the classes.
  • Put an interface in the package of the client that uses it (the DIP habit), not next to the implementation.

When NOT to split

  • Methods that every client uses together, such as open, read and close of one resource, belong in one interface.
  • A small public library interface with one implementer and one client gains nothing from three tiny interfaces. Split when a second kind of client or a second implementation appears.
  • Splitting a published interface breaks every user of it. For a public API, add a new narrower interface and let the old one extend it.

Interview: explain ISP in 30 seconds

"No client should depend on methods it does not use. A fat MultiFunctionDevice forces a basic printer to implement scan and fax as empty methods. I split it into Printer, Scanner and Fax, and each class implements only the roles it has. The benefits: fewer fake methods, easier mocking, smaller change impact. In Spring Data, the layered repository interfaces follow the same idea."

Interview: follow-up questions on ISP

  • ISP vs SRP? SRP is about reasons to change of a class. ISP is about what each client is forced to see of an interface. They often fix the same code.
  • How do you spot a violation? Empty or throwing methods, mocks with many unused stubs, and clients that import an interface for one call.
  • Does ISP mean one method per interface? No. Group methods by client role.
  • Show a real example. The payment roles above, or Spring Data's layered repositories.

D: Dependency Inversion Principle (and DI, and IoC)

High-level business code should not depend on low-level details such as a database or an email library; both should depend on an abstraction that the high-level code owns, and the concrete detail is supplied from outside.

In a normal top-down program, the high-level class (OrderService, the business rules) calls the low-level class (MySqlOrderRepository, SmtpMailer). The source code of the high level then mentions the low level, so a change of database edits the business code. The Dependency Inversion Principle (DIP) reverses the arrow of the source dependency:

  1. High-level modules should not depend on low-level modules. Both should depend on abstractions.
  2. Abstractions should not depend on details. Details should depend on abstractions.

"Inversion" means that the low-level class now implements an interface which the high-level module defines. The arrow that used to point from business to database now points from database to business.

The violation

public class OrderService {
    private final MySqlOrderRepository repository = new MySqlOrderRepository();   // concrete
    private final SmtpMailer mailer = new SmtpMailer("smtp.example.com");          // concrete

    public void place(Order order) {
        repository.insert(order);
        mailer.send(order.customerEmail(), "Order placed");
    }
}

Problems: you cannot unit-test place without MySQL and an SMTP server; moving to PostgreSQL or SES means editing the service; the service decides how its collaborators are built.

The refactoring: abstraction + constructor injection

// The high-level module owns these abstractions
public interface OrderRepository {
    void save(Order order);
}
public interface Mailer {
    void send(String to, String message);
}

public class OrderService {
    private final OrderRepository repository;
    private final Mailer mailer;

    public OrderService(OrderRepository repository, Mailer mailer) {   // injected
        this.repository = repository;
        this.mailer = mailer;
    }

    public void place(Order order) {
        repository.save(order);
        mailer.send(order.customerEmail(), "Order placed: " + order.id());
    }
}

// Low-level details implement the abstractions
class JdbcOrderRepository implements OrderRepository {
    public void save(Order order) { /* JDBC code */ }
}
class SmtpMailer implements Mailer {
    public void send(String to, String message) { /* SMTP code */ }
}

Now a unit test needs no infrastructure:

class FakeRepository implements OrderRepository {
    final java.util.List<Order> saved = new java.util.ArrayList<>();
    public void save(Order order) { saved.add(order); }
}

@Test
void savesAndNotifies() {
    var repo = new FakeRepository();
    var sent = new java.util.ArrayList<String>();
    var service = new OrderService(repo, (to, msg) -> sent.add(to));   // lambda as Mailer

    service.place(new Order("O1", "asha@example.com", java.util.List.of()));

    assertEquals(1, repo.saved.size());
    assertEquals(java.util.List.of("asha@example.com"), sent);
}

(JUnit 5 imports omitted. Mailer has one method, so a lambda can implement it.)

DIP vs DI vs IoC

These three terms are confused in every interview. They are related but different.

TermWhat it isLevel
DIP Dependency Inversion PrincipleA design rule: depend on abstractions, owned by the high-level codePrinciple (the "why")
IoC Inversion of ControlA broad idea: a framework or container calls your code, and controls creation and flow, instead of your code controlling everythingArchitecture style
DI Dependency InjectionA technique: an object receives its collaborators from outside (constructor, setter, field) instead of creating themTechnique (the "how")

DI is one way to achieve IoC. DIP is the design goal that DI makes easy. You can follow DIP without a framework (pass objects in main), and you can use a Spring container and still violate DIP by injecting concrete classes everywhere.

How Spring helps

The Spring container is an IoC container: you declare components, and Spring creates them and injects the dependencies. Constructor injection is the recommended style because it makes dependencies visible and fields final:

@Repository
class JdbcOrderRepository implements OrderRepository {
    private final JdbcTemplate jdbc;
    JdbcOrderRepository(JdbcTemplate jdbc) { this.jdbc = jdbc; }
    public void save(Order order) {
        jdbc.update("INSERT INTO orders(id, email) VALUES (?, ?)",
                    order.id(), order.customerEmail());
    }
}

@Service
class OrderService {
    private final OrderRepository repository;      // the interface, not the JDBC class
    private final Mailer mailer;

    OrderService(OrderRepository repository, Mailer mailer) {   // one constructor: no @Autowired
        this.repository = repository;
        this.mailer = mailer;
    }
}

With one implementation per interface, Spring picks it automatically. With two, use @Primary or @Qualifier. Switching from JDBC to JPA is a new @Repository class, with no change to OrderService. More on wiring in the Spring notes (Spring fundamentals).

Misunderstandings

  • "DIP = using @Autowired." No. Injecting JdbcOrderRepository (a concrete class) into the service is DI without DIP.
  • "Every class needs an interface." No. Value objects, records, DTOs and simple stable utilities (String, List) do not need one. Add an abstraction at boundaries: database, network, clock, file system, email, payment gateways.
  • The interface must be shaped by what the business needs (save(Order)), not copied from the library API (executeUpdate(String sql)). Otherwise the abstraction leaks details.
  • Injecting the clock (java.time.Clock) is a small DIP win: tests can fix the time.

Mistakes to avoid

  • Calling new on a collaborator inside a service, or using a static singleton (Mailer.getInstance()) that cannot be replaced.
  • Field injection (@Autowired private Foo foo;), which hides dependencies and blocks final fields and plain-Java tests.
  • Circular dependencies (A needs B needs A): the abstractions are split wrongly; extract a third class.

Interview: explain DIP in 30 seconds

"High-level policy should not depend on low-level detail; both depend on an abstraction. My OrderService depends on an OrderRepository interface that it owns; JdbcOrderRepository implements it. So I can swap the database or test with a fake. DI is the technique that supplies the implementation through the constructor, and IoC is the idea that the container, not my code, builds and wires the objects." Be ready to separate the three terms.

DRY, KISS and YAGNI

DRY says every piece of knowledge should live in one place; KISS says choose the simplest design that works; YAGNI says do not build features or flexibility until you actually need them. They pull against over-engineering and against copy-paste.

SOLID tells you how to structure code. Three shorter slogans tell you when to stop. They sound obvious, but a surprising amount of real damage comes from ignoring them or from applying them blindly.

DRY: Don't Repeat Yourself

The principle comes from The Pragmatic Programmer: every piece of knowledge must have a single, unambiguous, authoritative representation in the system. The key word is knowledge, not text. If the GST rate is 18% and you write 0.18 in the cart, the invoice and the report, then one business fact lives in three places. When the rate changes, you will miss one, and the invoice will disagree with the cart.

Wrong: the same rule copied

// CartService
long tax = amount * 18 / 100;
// InvoiceService
long gst = amount * 18 / 100;
// ReportService
long taxPart = amount * 18 / 100;

Right: one authoritative place

public final class TaxPolicy {
    private static final int GST_PERCENT = 18;
    public long gstOn(long amountInPaise) {
        return amountInPaise * GST_PERCENT / 100;
    }
}
// every service calls taxPolicy.gstOn(amount)

DRY also covers: constants and enums (not repeated strings), shared validation rules, database schema versus entity classes (generate one from the other or keep them in sync with tests), documentation that restates code, and build configuration.

DRY is about knowledge, not identical-looking code

Two code blocks may look the same today but represent different knowledge. Merging them couples two unrelated things. Example: a shipping-address validator and a billing-address validator are both "check pincode has six digits". If the rule for billing later allows foreign postal codes while shipping stays Indian only, the shared function now needs flags and conditions. That is accidental duplication, and removing it was the mistake.

SituationSame knowledge?Action
GST rate used in three servicesYes, one business ruleExtract to one place
Two DTO classes with the same three fieldsNo, different API contracts that may divergeKeep separate
Same 6-line loop in two methods, same reason to changeYesExtract a method
Two validators that look alike but belong to different featuresProbably notWait; see the rule of three

The rule of three

Copy once: fine. Copy a second time: you have three copies, so now refactor. Duplicating twice shows you the real shape of what is common and what differs; abstracting after the first copy is a guess. Martin Fowler describes it as: "the first time you do something, you just do it; the second time you wince but do it anyway; the third time you refactor". Duplication is cheaper than the wrong abstraction.

KISS: Keep It Simple, Stupid

Among designs that work, prefer the simplest one. Simple means few moving parts, easy to read, easy to debug, and easy for a new teammate to follow, not "fewest lines". A clever one-liner with nested ternaries and streams is not simple.

Wrong: clever

return users.stream()
    .collect(Collectors.groupingBy(u -> u.age() > 17 ? u.city() != null
        ? u.city() : "NA" : "MINOR", Collectors.counting()))
    .entrySet().stream().max(Map.Entry.comparingByValue())
    .map(Map.Entry::getKey).orElse(null);

Right: boring and clear

Map<String, Long> countByCity = new HashMap<>();
for (User u : users) {
    if (u.age() < 18) continue;
    String city = u.city() == null ? "NA" : u.city();
    countByCity.merge(city, 1L, Long::sum);
}
return mostFrequent(countByCity);      // a small named method

KISS in design: a method call before a message queue, a monolith before microservices, a HashMap before a distributed cache, an if before a rules engine. Add complexity only when a measured problem demands it.

YAGNI: You Aren't Gonna Need It

From Extreme Programming: do not add functionality until it is necessary. Developers love building "just in case" features: a plugin system, a generic base class, ten configuration flags, support for MongoDB "in case we change". Unused code still costs: it must be written, tested, read, and kept compatible, and your guess about the future is usually wrong.

// Over-engineered for a service with one payment gateway
interface PaymentGatewayFactoryProvider { PaymentGatewayFactory get(String region); }
interface PaymentGatewayFactory { PaymentGateway create(Map<String, Object> config); }
// ... 6 more types, an XML config loader, a registry

// What the team needed on day one
class RazorpayClient {
    Receipt charge(long paise, String token) { /* call the API */ return null; }
}
// Add an interface when the second gateway is really planned (then it is easy)

YAGNI is not "never plan". It means: do not implement speculative features. Good habits (small classes, tests, loose coupling) keep change cheap, so you do not need to predict it.

The tension between them

DRY pushes you to abstract; KISS and YAGNI push you to wait. A balanced working rule: write the simple version first; duplicate once if unsure; abstract when the third case appears and the shared knowledge is clear; delete code that is not used.

Other short principles

Separation of concerns
Keep different jobs in different places (UI, business rules, data access). See next article.
Law of Demeter
Talk only to your direct friends. See the next article.
Principle of least astonishment
A method should do what its name says and nothing surprising. getUser() that creates a user breaks it.
Fail fast
Check inputs early and throw a clear exception, instead of letting bad data travel deep.
Boy Scout rule
Leave the code a little cleaner than you found it.
Premature optimisation
Do not optimise without measuring; Knuth: "premature optimization is the root of all evil" (in the 97% of cases where it does not matter).

Mistakes to avoid

  • Merging two similar-looking methods with a boolean flag parameter to "stay DRY"; the result is harder to read than the duplicates (see clean code).
  • Building a generic framework "for the next project" inside the current one.
  • Using KISS as an excuse for one 600-line method.

  • What is DRY? One authoritative place for each piece of knowledge; example the GST rate. Add: it is about knowledge, not identical lines.
  • When does DRY go wrong? When you merge code that looks similar but changes for different reasons; mention the rule of three.
  • YAGNI vs designing for change? I keep the code loosely coupled so change is cheap, but I do not build the features until they are needed.

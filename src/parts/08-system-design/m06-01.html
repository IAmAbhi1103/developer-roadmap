Once an application runs on more than one machine, new problems appear that a single Spring Boot process never had: a call can time out and you do not know if it worked, a message can arrive twice, two databases cannot commit together, and one slow service can drag down ten others. This module teaches the standard patterns that handle those problems. It builds on the building blocks in Module 5 (queues, caches, replication) and the trade-offs in Module 4 (CAP, consistency), and it is the toolbox you reach for in every design in Module 7.

The Spring-side code for these ideas (Resilience4j, Kafka, RabbitMQ, the outbox with Spring Data) lives in Spring Boot · Module 7. Here you learn the concepts, the failure stories and the interview answers.

Monolith, modular monolith and microservices

A monolith is one deployable unit, microservices are many small independently deployed services that each own their data, and a modular monolith sits between them; choose microservices for team and scaling reasons, not because they sound modern.

The three shapes

A monolith is one codebase built and deployed as one unit. All features (users, orders, payments) run in the same process and usually share one database. Calls between features are plain method calls. A microservices architecture splits the system into many small services. Each runs in its own process, is deployed on its own, and owns its own data. Calls between them go over the network (HTTP, gRPC or messages). A modular monolith is one deployable unit whose insides are split into strict modules with clear public interfaces and no reaching into another module's tables.

Comparison

DeploymentOne unitOne unitMany units, independent

TransactionsOne ACID transactionOne ACID transactionSagas, eventual consistency

Why start with a monolith

A network call is slower than a method call by a factor of roughly 10,000 or more (approximate: a method call takes nanoseconds, a call inside one data centre takes about half a millisecond to a few milliseconds). A network call can also fail, time out or return late, while a method call cannot. Each microservice adds a pipeline, monitoring, a deployment, versioned contracts and a data copy problem. Small teams pay all of this cost and get little in return. The common advice is: start with a well-structured (modular) monolith, and split out a service when a clear pain appears.

Good reasons to split a service:

  • Independent scaling: video encoding needs many CPUs, the user profile does not.
  • Team autonomy: 50+ engineers stepping on each other in one codebase and one release train.
  • Different technology or reliability needs: a payment service with stricter security, or a machine-learning service in Python.
  • Fault isolation: a bug in the recommendation code must not take down checkout.

Bad reasons: "Netflix does it", "it is modern", "we want to put it on the CV".

Service boundaries: bounded contexts

The hardest part is deciding where to cut. The best guide is the idea of a bounded context from domain-driven design. In simple words: a part of the business where words have one clear meaning and one team owns the rules. "Product" means different things to different teams. To the catalogue team it is a title, images and a description. To the inventory team it is a SKU and a stock count. To billing it is a price and a tax code. Each context keeps its own model of "product" instead of one giant shared class.

  • Cut along business capabilities (Orders, Payments, Inventory, Shipping), not technical layers (a "database service", a "validation service").
  • A good service has high cohesion (things that change together live together) and low coupling (it rarely needs another service to finish its work).
  • If two services must always be deployed together, or one cannot do anything without calling the other on every request, the boundary is probably wrong. You built a distributed monolith: all the pain of microservices with none of the benefits.

Database per service and its consequences

Each microservice should own its data and expose it only through its API or events. If two services share tables, a schema change in one breaks the other, and you are back to a monolith. The consequences are real:

  • No cross-service joins. To show "my orders with product names" you call the product service, or keep a small copy of the product name inside the order (a deliberate duplicate), or build a read model fed by events.
  • No cross-service ACID transaction. Placing an order that touches orders, payment and inventory needs a saga, not @Transactional.
  • Eventual consistency. Copies of data lag behind; the user may see old data for a moment.
  • Polyglot persistence becomes possible: Postgres for orders, Redis for sessions, Elasticsearch for search.

Exception: sometimes share a database early

Many real migrations first split the code into services while they still read the same database, then separate the schemas step by step. It is a temporary compromise, fine if you know it is temporary and each table has exactly one writing service.

Moving from monolith to services: the strangler fig

Do not rewrite everything. Put a gateway in front, build one new service for one capability, route that capability's traffic to it, and delete the old code. Repeat. Over months the monolith shrinks. This is called the strangler fig pattern. See Module 5 for the gateway.

Common mistakes

  • Splitting too early: ten services for a team of four.
  • Splitting by technical layer, so every feature touches every service.
  • Shared database tables between services.
  • Long synchronous call chains (A calls B calls C calls D): availability multiplies down. Four services at 99.9% each give about 99.6% together (0.9994 ≈ 0.996).
  • No tracing or central logging, so nobody can follow a request.

In real projects

In Spring Boot, a modular monolith is separate packages or Maven modules with a small public API each; tools such as Spring Modulith check that modules do not reach into each other. When a module is split out, the in-process interface becomes a REST client or a message. The Spring side of services, discovery and messaging is in Spring Boot · Module 7.

Interview angle

  • "Monolith vs microservices?" Never answer "microservices are better". Say: monolith first, split for independent scaling, team size or fault isolation, and name the cost (network failures, distributed data, operations).
  • Define a bounded context in one sentence and give the "product means different things" example.
  • Name the distributed monolith as the anti-pattern.

Sync vs async communication, and event-driven architecture

Synchronous calls (REST, gRPC) are simple and give an immediate answer but couple availability and latency; asynchronous messaging decouples services in time and absorbs spikes at the cost of eventual consistency and harder debugging.

Synchronous communication

The caller sends a request and waits for the response. Examples: REST over HTTP, gRPC. It fits when the caller needs the answer to continue: "is this coupon valid?", "what is the price?". It is easy to understand and debug, and errors come back directly.

The problem is temporal coupling: both services must be up at the same moment. If the payment service is down, checkout is down. If it is slow, checkout is slow, and your threads pile up waiting. Latency adds up along the chain, and availability multiplies down (see the previous article).

Asynchronous communication

The sender puts a message on a broker (Kafka, RabbitMQ, SQS, see the queues article in Module 5) and moves on. A consumer processes it later. Two shapes exist:

  • Command / task message: "send this email", "charge this card". One consumer group does the work.
  • Event: "OrderPlaced happened". The producer does not know or care who listens; many consumers may react.

Comparison table

AspectSynchronous (REST, gRPC)Asynchronous (queue, events)

Rule of thumb: use sync for reads and for steps where the user must see the result now; use async for everything that can happen "soon" (emails, analytics, search indexing, inventory updates, shipping). A mixed design is normal: the user-facing call is sync and fast, and it triggers async work behind it.

Event-driven architecture

In an event-driven architecture, services announce facts that already happened (OrderPlaced, PaymentCaptured) and other services react. Benefits: loose coupling (add a new consumer without touching the producer), natural audit trail, easy fan-out, and buffering. Costs: you cannot read the flow from one place, ordering and duplicates need care, and the system is eventually consistent.

  • Event notification: a small event ("order 42 changed"); consumers call back for details.
  • Event-carried state transfer: the event holds the data consumers need, so they can keep their own copy and never call back. Good for read models.
  • Event sourcing (advanced, brief): the stored truth is the sequence of events; current state is computed from them. Powerful but a big commitment; do not offer it casually.

Choreography vs orchestration

When one business process crosses several services, who decides what happens next?

Choreography: there is no boss. Each service listens for events and reacts, and may emit its own event. Like dancers who know their steps.

Orchestration: one component (the orchestrator, often inside the order service or a workflow engine) tells each service what to do and tracks the state of the whole process.

AspectChoreographyOrchestration
ControlSpread across servicesOne place
CouplingLoose; services know events onlyOrchestrator knows every participant
VisibilityHard: the flow is implicitEasy: one place shows the state
Adding a stepAdd a listenerChange the orchestrator
RiskHidden cycles, "who handles failure?"Orchestrator becomes a bottleneck or god service
FitsSimple flows, 2–4 stepsComplex flows with branching and compensation

Many teams start with choreography and move to orchestration when the process grows to five or more steps with failure paths. Workflow engines (Temporal, Camunda, AWS Step Functions) provide orchestration as a product; they store the state and retry for you.

Rule: async consumers must assume duplicates and reordering

Brokers usually deliver at least once. Every consumer must be idempotent (see Idempotency and Delivery semantics), and must not assume events from different keys arrive in global order.

Common mistakes

  • Making everything async: simple reads become a maze of events and polling.
  • Fake async: sending a message and then blocking until a reply, which keeps all the coupling.
  • Publishing events with no schema versioning, so a field rename breaks every consumer.
  • Dual write: saving to the database and publishing to the broker as two separate steps (fixed by the outbox pattern).

Interview angle

  • Give the rule: sync when the caller needs the answer now, async for side effects and spikes.
  • Define choreography and orchestration with the order example; say you would pick orchestration once failure paths grow.
  • Mention the cost: eventual consistency, duplicates, tracing.

Idempotency and idempotency keys

An operation is idempotent if doing it many times has the same effect as doing it once; because networks force clients to retry, you make non-idempotent operations (like "charge ₹500") idempotent with a client-generated idempotency key and a dedupe table.

Why this matters: the timeout problem

A client calls POST /payments. The server charges the card, but the response is lost, or the client times out before it arrives. The client now knows nothing: did the charge happen? If it retries and the server charges again, the customer pays twice. If it does not retry and the charge never happened, the order is lost. The network gives you no way to tell the two cases apart. The fix is to make the retry safe.

Idempotent means: applying the operation once or ten times leaves the system in the same state (and returns the same result).

Naturally idempotent operations

OperationIdempotent?Why
GET /orders/42YesReads change nothing
PUT /users/7 with a full bodyYesSets the same final state
DELETE /orders/42Yes (state)Gone after the first call; the second returns 404 or 204
SET balance = 500YesAbsolute value
balance = balance + 500NoEach call adds again
POST /paymentsNoEach call creates a new payment
"Send email"NoEach call sends another email

HTTP defines GET, PUT, DELETE, HEAD and OPTIONS as idempotent and POST as not. That is the contract; your code must honour it. The tricks: prefer "set to X" over "add X"; use natural unique constraints (one row per (order_id, step)); and for POST, use an idempotency key.

The idempotency key pattern

The client generates a unique key (a UUID) once per logical action and sends it in a header on every attempt of that action. The server stores the key with the result. If the same key arrives again, the server returns the stored result instead of doing the work again.

POST /v1/payments HTTP/1.1
Host: api.example.com
Idempotency-Key: 7c9e6679-7425-40de-944b-e07fc1f90ae7
Content-Type: application/json

{"orderId": 42, "amountPaise": 50000, "currency": "INR"}

The dedupe table

CREATE TABLE idempotency_key (
    key            VARCHAR(64) PRIMARY KEY,   -- unique per client and action
    client_id      BIGINT       NOT NULL,
    request_hash   CHAR(64)     NOT NULL,     -- SHA-256 of the request body
    status         VARCHAR(16)  NOT NULL,     -- IN_PROGRESS, DONE
    response_code  INT,
    response_body  TEXT,
    created_at     TIMESTAMP    NOT NULL DEFAULT now()
);
-- delete rows older than 24 hours with a scheduled job

The primary key does the heavy lifting: two concurrent requests with the same key cannot both insert. The handler in Java, simplified:

@PostMapping("/v1/payments")
public ResponseEntity<PaymentResponse> pay(
        @RequestHeader("Idempotency-Key") String key,
        @RequestBody PaymentRequest req) {

    String hash = Sha256.of(req.toString());
    try {
        keys.insertInProgress(key, req.clientId(), hash);       // PK insert
    } catch (DuplicateKeyException dup) {
        IdempotencyRecord rec = keys.find(key);
        if (!rec.requestHash().equals(hash)) {
            return ResponseEntity.status(422).build();          // same key, different body
        }
        if (rec.status().equals("IN_PROGRESS")) {
            return ResponseEntity.status(409).build();          // first attempt still running
        }
        return ResponseEntity.status(rec.responseCode()).body(rec.responseAs(PaymentResponse.class));
    }
    PaymentResponse result = paymentService.charge(req);         // do the real work
    keys.complete(key, 201, result);                             // store the response
    return ResponseEntity.status(201).body(result);
}

In a real service, the business write and the "complete" update should be in one database transaction whenever the work is in the same database. If the work is an external call (a card network), pass the same key on to that provider too, so the whole chain is protected.

Rules for keys

  • The client creates the key, once per intention, and reuses it on every retry. A new key per retry defeats the purpose.
  • Scope the key to the client (or user) so two clients cannot collide.
  • Store a hash of the request. Same key with a different body is a client bug: return an error (HTTP 422 is commonly used), do not silently replay.
  • Handle the IN_PROGRESS state: return 409 or make the second request wait.
  • Keep keys long enough to cover the client's retry window (24 hours is a common choice), then delete them.
  • Return the same response (status and body) for a replay.

Idempotent consumers

The same idea protects message consumers. Each message has a unique id. Before processing, the consumer inserts the id into a processed_message table in the same transaction as its business change. A duplicate hits the unique constraint and is skipped. Alternatives: make the business operation naturally idempotent (upsert by key), or use a version check ("apply only if version is 6, set to 7").

BEGIN;
INSERT INTO processed_message (message_id) VALUES ('evt-9f31');   -- fails on duplicate
UPDATE account SET balance_paise = balance_paise + 50000 WHERE id = 7;
COMMIT;

Common mistakes

  • Generating a new key on each retry.
  • Checking for the key with SELECT and then inserting: two parallel requests both see "not found". Use the unique constraint as the lock.
  • Saving the key after the work. A crash between the two loses the protection.
  • Keeping keys forever (table grows) or for too short a time (late retry double-charges).

Interview angle

  • Open with the "response lost" story, then define idempotency.
  • Describe the header, the dedupe table with a primary key, the stored response and the request hash. Mention the in-progress state.
  • Say that payment providers expose exactly this idea (an Idempotency-Key style header) and that consumers use a processed-message table.

Retries: backoff, jitter, retry storms and budgets

Retry only safe, transient failures, wait longer after each attempt (exponential backoff), add randomness (jitter) so clients do not retry in sync, cap the attempts, and limit total retries with a budget, or your retries will become the outage.

Why retry, and when

Many failures are transient: a dropped packet, a brief overload, a leader election, a deployment restarting a pod. A retry a moment later usually works. But a retry is also extra load, and it can repeat a side effect. So ask two questions first:

  1. Is the failure retryable? Timeouts, connection resets, HTTP 502/503/504 and 429 (after the wait the server asks for) are. A 400, 401, 403 or 404 will fail the same way again; do not retry.
  2. Is the operation safe to repeat? Reads and idempotent writes: yes. A plain POST without an idempotency key: no (see Idempotency).

Exponential backoff

Retrying immediately in a tight loop hammers a service that is already struggling. Exponential backoff doubles the wait after each failure: wait = base × 2attempt, up to a maximum cap. With a base of 100 ms and a cap of 10 s:

AttemptPure exponential waitWith cap 10 s
1100 ms100 ms
2200 ms200 ms
3400 ms400 ms
4800 ms800 ms
51.6 s1.6 s
812.8 s10 s

Jitter: why randomness is essential

Suppose 10,000 clients lose their connection at the same instant (a server restarted). With plain backoff they all retry at 100 ms, then all at 200 ms, then all at 400 ms. The server sees waves of 10,000 requests, each wave knocking it down again. This is a thundering herd. Jitter adds randomness so retries spread out over time.

  • Full jitter: sleep a random time between 0 and the backoff value. Spreads load best and is a widely recommended default.
  • Equal jitter: half the backoff fixed plus a random half.
  • Decorrelated jitter: next sleep is random between the base and 3 × the previous sleep.
import java.util.concurrent.Callable;
import java.util.concurrent.ThreadLocalRandom;

public final class Retry {
    public static <T> T withBackoff(Callable<T> call, int maxAttempts) throws Exception {
        long baseMs = 100, capMs = 10_000;
        for (int attempt = 1; ; attempt++) {
            try {
                return call.call();
            } catch (Exception e) {
                if (attempt == maxAttempts || !isRetryable(e)) {
                    throw e;                                  // give up: bubble up
                }
                long backoff = Math.min(capMs, baseMs * (1L << attempt));
                long sleep = ThreadLocalRandom.current().nextLong(backoff + 1);   // full jitter
                Thread.sleep(sleep);
            }
        }
    }

    private static boolean isRetryable(Exception e) {
        return e instanceof java.net.SocketTimeoutException
            || e instanceof java.net.ConnectException;
    }
}

Retry storms and multiplication

Retries multiply across layers. Imagine three layers, A calls B calls C, each allowing 3 attempts. If C is down, each request to A causes up to 3 calls to B, and each of those causes 3 calls to C: 3 × 3 = 9 calls to the already-failing C. With four layers it is 27. A small slowdown turns into a retry storm that makes recovery impossible, because the failing service keeps getting more load than normal.

Defences:

  • Retry at one layer only (usually the edge or the layer closest to the failure) and pass errors up without retrying in the middle layers.
  • Retry budget: allow retries only as a small fraction of normal traffic, for example "retries may be at most 10% of requests in the last minute". When the budget is spent, fail fast. At 1,000 requests per second, that is at most about 100 retries per second, never 3,000.
  • Circuit breaker: stop calling a dependency that is clearly down (see Resilience).
  • Deadlines: pass a total time limit down the chain; do not start a retry if the caller has already given up.
  • Respect Retry-After headers and 429 responses from the server.

Rule: a retry needs a limit, a delay, randomness and a safe operation

Max attempts, backoff with a cap, jitter, and idempotency. Remove any one of the four and you have a risk.

In real projects

You rarely hand-write the loop. Spring offers retry support and Resilience4j has Retry with exponential backoff configuration; see Spring Boot · Module 7. For messaging, the broker or a retry topic does it, with a dead-letter queue for messages that still fail after N attempts so that a poison message does not block the queue forever.

Common mistakes

  • Retrying non-idempotent POSTs, causing duplicate orders or charges.
  • Retrying 4xx errors that can never succeed.
  • Fixed delay with no jitter, which synchronises the clients.
  • Retries at every layer of a call chain.
  • No timeout on the call, so the first attempt hangs and the retry logic never runs.

Interview angle

  • "How do you retry safely?" Idempotency, exponential backoff with a cap, jitter, a max attempt count, a retry budget, a circuit breaker.
  • Explain the multiplication: 3 layers × 3 attempts = 27 calls from one user request in the worst case.
  • Mention dead-letter queues for async work.

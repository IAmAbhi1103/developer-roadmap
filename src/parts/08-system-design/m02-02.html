Builder: telescoping constructors, immutable objects and Lombok

Builder constructs a complex object step by step with named, readable calls and produces a finished (usually immutable) object, which avoids constructors with many parameters.

Intent: separate the construction of a complex object from its representation, so that you can build it step by step and get a valid, usually immutable, result.

The problem: telescoping constructors

An email message has two required values (recipient, subject) and many optional ones (cc, bcc, body, reply-to, attachments, priority). With constructors you end up with a "telescope":

public class EmailMessage {
    public EmailMessage(String to, String subject) { /* ... */ }
    public EmailMessage(String to, String subject, String body) { /* ... */ }
    public EmailMessage(String to, String subject, String body, String cc) { /* ... */ }
    public EmailMessage(String to, String subject, String body, String cc, String bcc,
                        String replyTo, boolean highPriority) { /* ... */ }
}

// What does this call mean? Which string is cc, which is bcc?
new EmailMessage("a@x.com", "Hi", "Body", null, "boss@x.com", null, true);

Problems: you cannot tell what each argument means, swapping two strings compiles fine, you pass null for the optional ones, and you need a constructor for every combination. The other common escape, a no-argument constructor plus setters (the JavaBeans style), leaves the object half-built and mutable between calls, so it cannot be immutable or thread-safe.

Structure

A hand-written builder for an immutable class

The product has a private constructor and only final fields. The nested Builder takes the required values in its constructor, offers one method per optional value (each returns this, so you can chain), and checks the rules in build().

import java.util.ArrayList;
import java.util.List;

public final class EmailMessage {
    private final String to;
    private final String subject;
    private final String body;
    private final List<String> cc;
    private final boolean highPriority;

    private EmailMessage(Builder b) {
        this.to = b.to;
        this.subject = b.subject;
        this.body = b.body;
        this.cc = List.copyOf(b.cc);                   // immutable copy
        this.highPriority = b.highPriority;
    }

    public static Builder builder(String to, String subject) {   // required values
        return new Builder(to, subject);
    }

    public String to() { return to; }
    public String subject() { return subject; }
    public String body() { return body; }
    public List<String> cc() { return cc; }
    public boolean highPriority() { return highPriority; }

    @Override public String toString() {
        return "EmailMessage{to=" + to + ", subject=" + subject + ", cc=" + cc
             + ", highPriority=" + highPriority + "}";
    }

    public static final class Builder {
        private final String to;                       // required
        private final String subject;                  // required
        private String body = "";                      // optional, with a default
        private final List<String> cc = new ArrayList<>();
        private boolean highPriority;

        private Builder(String to, String subject) {
            this.to = to;
            this.subject = subject;
        }

        public Builder body(String body) { this.body = body; return this; }
        public Builder cc(String address) { this.cc.add(address); return this; }
        public Builder highPriority() { this.highPriority = true; return this; }

        public EmailMessage build() {
            if (to == null || !to.contains("@")) {
                throw new IllegalStateException("A valid recipient is required");
            }
            if (subject == null || subject.isBlank()) {
                throw new IllegalStateException("Subject is required");
            }
            return new EmailMessage(this);              // validated, then frozen
        }
    }

    public static void main(String[] args) {
        EmailMessage m = EmailMessage.builder("asha@example.com", "Your invoice")
                .body("Please find it attached.")
                .cc("accounts@example.com")
                .highPriority()
                .build();
        System.out.println(m);
    }
}
EmailMessage{to=asha@example.com, subject=Your invoice, cc=[accounts@example.com], highPriority=true}

Each call reads like a sentence. Required values cannot be forgotten because they are in the factory method. The finished object is immutable and always valid, because validation runs once in build().

Lombok @Builder

Lombok (a code-generation library, annotation processor) writes the builder for you. You add it as a dependency and your IDE needs the plugin.

import lombok.Builder;
import lombok.Singular;
import lombok.Value;

@Value                     // all fields private final, getters, equals/hashCode/toString
@Builder(toBuilder = true) // generates CustomerBuilder, plus customer.toBuilder()
public class Customer {
    String name;
    String email;
    @Builder.Default String country = "IN";
    @Singular java.util.List<String> phones;     // generates phone("..") and phones(..)
}

// Customer c = Customer.builder().name("Asha").email("a@x.com").phone("98100").build();
// Customer moved = c.toBuilder().country("US").build();     // copy with one change

Lombok's builder does not make required fields mandatory: a forgotten field is just null, unless you add checks (for example @NonNull on a field, which generates a null check in the constructor). Hand-written builders force required values in the entry point.

Builders with records

A record with two or three components needs no builder; call the constructor. With many optional components, a record can still have a hand-written builder, or you can use "wither" methods that return a changed copy: p.withCity("Pune"). Libraries such as RecordBuilder and the IDE can generate builders for records.

Builders in the JDK and Spring

  • StringBuilder builds a string by appending; strictly a builder in the everyday sense, though without a separate product type.
  • HttpClient.newBuilder() and HttpRequest.newBuilder() (Java 11+) are textbook builders:
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.time.Duration;

HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(5))
        .followRedirects(HttpClient.Redirect.NORMAL)
        .build();

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/orders/42"))
        .header("Accept", "application/json")
        .GET()
        .build();
  • Others: Stream.builder(), Locale.Builder, ProcessBuilder, java.util.stream.Collectors (not a builder), and in Spring UriComponentsBuilder, RestClient.builder(), WebClient.builder(), SpringApplicationBuilder and User.withUsername(...) in Spring Security.

Director (the classic GoF variant)

The GoF description adds a Director class that knows a recipe (the order of build steps), such as "build a standard welcome mail". In practice a static helper does that: EmailTemplates.welcome(user) returns a pre-configured builder. You do not need a separate Director class in everyday Java.

Pros

  • Readable call sites with named values.
  • Immutable objects without a huge constructor.
  • Validation in one place before the object exists.
  • Same builder can make different representations or presets.

Cons

  • More code (a second class), unless Lombok generates it.
  • Fields are duplicated in the builder and the product.
  • A builder can be used incorrectly: not calling a required method is only caught at run time (unless required values are in the entry point).

When NOT to use a Builder

  • For a class with two or three fields: a constructor, static factory or record is simpler (KISS).
  • When all fields are required and there are few of them.
  • Builders and JPA entities mix badly: entities need a no-argument constructor and frameworks set fields by reflection. Use builders for DTOs, commands and value objects.

Common mistakes

  • Reusing one builder after build() without copying its lists, so two products share a mutable list. Copy collections in the constructor (List.copyOf).
  • Putting validation in the builder methods only. Validate in build(), where all fields are known.
  • Building the object without the invariants (a "builder" that just calls setters on a mutable object).

Interview: Builder

  • What problem does Builder solve? Telescoping constructors and half-built mutable objects. You get readable, step-by-step construction and an immutable, valid result.
  • Builder vs Factory? Factory chooses which class to create in one call; Builder assembles one complex object over many calls.
  • Where have you seen Builder? StringBuilder, HttpRequest.newBuilder(), Lombok @Builder, UriComponentsBuilder.

Adapter: making incompatible interfaces work together

Adapter wraps an existing class with an incompatible interface and translates calls, so your code can use it through the interface it expects, without changing either side.

Intent: convert the interface of a class into another interface that clients expect, so classes with incompatible interfaces can work together.

The problem

Your shop code talks to a PaymentGateway interface that you designed. Now the business signs a contract with a provider whose SDK is a jar you cannot change. Its method names, parameter types and result codes are all different: it takes rupees as a double, a card number as a String, and returns an int status code. If you call the SDK directly from the order code, the vendor's API spreads across your system, and changing the vendor later hurts. Like a travel plug adapter, you wrap the foreign socket in a shape your plug fits.

Implementation

// --- Target: what our application expects ---
record PaymentRequest(String cardToken, long amountInPaise, String orderId) { }
record PaymentResult(boolean success, String reference, String message) { }

interface PaymentGateway {
    PaymentResult pay(PaymentRequest request);
}

// --- Adaptee: the third-party SDK, which we cannot change ---
class FastPaySdk {
    // returns 0 on success, 101 = declined, 500 = server error
    public int makePayment(String card, double rupees, String currency) {
        return rupees < 50_000 ? 0 : 101;
    }
    public String lastTransactionId() { return "FP-" + System.nanoTime(); }
}

// --- Adapter: translates our interface to the SDK ---
class FastPayAdapter implements PaymentGateway {
    private final FastPaySdk sdk;

    FastPayAdapter(FastPaySdk sdk) { this.sdk = sdk; }

    @Override
    public PaymentResult pay(PaymentRequest request) {
        double rupees = request.amountInPaise() / 100.0;                  // paise to rupees
        int code = sdk.makePayment(request.cardToken(), rupees, "INR");   // call the SDK
        return switch (code) {                                            // map the result
            case 0   -> new PaymentResult(true, sdk.lastTransactionId(), "Approved");
            case 101 -> new PaymentResult(false, null, "Declined by bank");
            default  -> new PaymentResult(false, null, "Gateway error " + code);
        };
    }
}

// --- Client: knows only the target interface ---
class CheckoutService {
    private final PaymentGateway gateway;
    CheckoutService(PaymentGateway gateway) { this.gateway = gateway; }

    String checkout(String orderId, long paise, String token) {
        PaymentResult r = gateway.pay(new PaymentRequest(token, paise, orderId));
        return r.success() ? "Paid, ref " + r.reference() : "Failed: " + r.message();
    }
}

public class AdapterDemo {
    public static void main(String[] args) {
        CheckoutService service = new CheckoutService(new FastPayAdapter(new FastPaySdk()));
        System.out.println(service.checkout("O-1", 129900, "tok_abc"));
        System.out.println(service.checkout("O-2", 9_000_000, "tok_abc"));
    }
}
Paid, ref FP-123456789
Failed: Declined by bank

The vendor's names, the double rupees and the integer codes stay inside FastPayAdapter. Switching to another provider is a new adapter class (say RazorpayAdapter) with no change to CheckoutService. In tests, use a fake PaymentGateway.

Object adapter vs class adapter

The version above is an object adapter: it holds the adaptee in a field (composition). A class adapter would inherit from the adaptee and implement the target interface at the same time. Java has single class inheritance, so class adapters are rare and need the target to be an interface. Prefer the object adapter: it works with any subclass of the adaptee and keeps the coupling loose (composition over inheritance).

Anti-corruption layer

In larger systems, an adapter that shields your domain from a foreign model (a legacy system, a partner API, another microservice) is called an anti-corruption layer. It translates not just method names but concepts and error handling, so the foreign model does not leak into yours.

Adapters in the JDK and Spring

  • Arrays.asList(array) adapts an array to the List interface (writes go through to the array).
  • InputStreamReader adapts a byte InputStream to a character Reader; OutputStreamWriter does the reverse.
  • Collections.enumeration(c) and Enumeration.asIterator() convert between old and new iteration styles.
  • Executors.callable(runnable) adapts a Runnable to a Callable.
  • Spring MVC: HandlerAdapter lets DispatcherServlet call any kind of handler (annotated controllers, HttpRequestHandlers, functional endpoints) in the same way. Spring has adapters such as MessageListenerAdapter in its messaging modules too.
  • Spring Data repositories and HttpMessageConverters also translate between your types and external representations.

Pros

  • Reuses existing code without changing it.
  • Keeps vendor-specific code in one class (SRP).
  • Easy to replace a vendor or fake it in tests (DIP, OCP).

Cons

  • An extra class and one more call per operation.
  • When the two interfaces are very different, the adapter becomes complicated.
  • Some features of the adaptee may not map to the target interface.

When NOT to use an Adapter

  • When you control both sides: change the interface instead of wrapping it.
  • When a method reference or lambda is enough, for example turning a Function into a Comparator with Comparator.comparing.
  • Do not let the adapter grow business logic. It only translates.

Why the pattern exists

Software rarely starts from a blank page. You integrate a payment SDK, a legacy billing module, a partner's SOAP service or an open-source library, and none of them was written against your interfaces. You cannot edit them (they are a jar, or owned by another team), and you do not want to edit your own clients either (they are many and stable). The only place left for the translation code is a new class in the middle. That class is the Adapter. It exists so that foreign ideas stop at the boundary: your domain keeps its own language, and the translation is written once and tested once.

The call flow

A second example: file storage

Your app stores invoices through a FileStore interface. In development you use the local disk; a legacy partner system only offers a client that works with (host, path, byte[]) and throws its own checked exception. Two adapters make both look the same.

import java.io.IOException;
import java.io.UncheckedIOException;
import java.nio.file.Files;
import java.nio.file.Path;

interface FileStore {
    void save(String name, byte[] content);
    byte[] load(String name);
}

// Adapter 1: java.nio.file.Files already does the job, we only change the shape
class LocalDiskStore implements FileStore {
    private final Path root;
    LocalDiskStore(Path root) { this.root = root; }
    public void save(String name, byte[] content) {
        try { Files.write(root.resolve(name), content); }
        catch (IOException e) { throw new UncheckedIOException(e); }
    }
    public byte[] load(String name) {
        try { return Files.readAllBytes(root.resolve(name)); }
        catch (IOException e) { throw new UncheckedIOException(e); }
    }
}

// The adaptee: a legacy client we cannot change (fragment, class assumed)
class LegacyArchiveClient {
    void put(String host, String path, byte[] data) throws ArchiveException { /* ... */ }
    byte[] get(String host, String path) throws ArchiveException { return new byte[0]; }
}
class ArchiveException extends Exception { }

// Adapter 2: translates names and exceptions
class ArchiveStore implements FileStore {
    private final LegacyArchiveClient client;
    private final String host;
    ArchiveStore(LegacyArchiveClient client, String host) {
        this.client = client;
        this.host = host;
    }
    public void save(String name, byte[] content) {
        try { client.put(host, "/invoices/" + name, content); }
        catch (ArchiveException e) { throw new IllegalStateException("Archive save failed", e); }
    }
    public byte[] load(String name) {
        try { return client.get(host, "/invoices/" + name); }
        catch (ArchiveException e) { throw new IllegalStateException("Archive load failed", e); }
    }
}

Note the two jobs an adapter really has: shape translation (names, units, argument order) and error translation (a vendor's checked exception becomes your own exception, so no vendor type leaks to callers).

Adapter in one line: lambdas and method references

When the target is a functional interface, a lambda is an adapter written inline. Comparator.comparing(Employee::name) adapts a "key extractor" to the comparison role, and executor.submit(() -> legacy.run()) adapts a call to Runnable. Write a full class only when the translation has state, several methods, or needs its own tests.

Adapter or something else?

PatternInterface changes?Purpose
AdapterYes: A to BMake an existing class fit the interface you need
DecoratorNo, sameAdd behaviour
FacadeYes: many classes to one simple APIHide a subsystem
ProxyNo, sameControl access (lazy, remote, security)

A quick test: "I have class X and need it to look like interface Y" is Adapter. "I want X plus logging" is Decorator. "I want one simple call over five classes" is Facade. The full table is in Adapter vs Decorator vs Proxy vs Facade.

Wrong: vendor types leak through

class FastPayAdapter implements PaymentGateway {
    // returns the SDK's int code to the caller
    public int pay(PaymentRequest r) throws FastPayException {
        return sdk.makePayment(r.cardToken(),
                               r.amountInPaise() / 100.0, "INR");
    }
}

Right: only domain types cross the boundary

class FastPayAdapter implements PaymentGateway {
    public PaymentResult pay(PaymentRequest r) {
        try {
            int code = sdk.makePayment(r.cardToken(),
                                       r.amountInPaise() / 100.0, "INR");
            return map(code);                   // own result type
        } catch (RuntimeException e) {
            return new PaymentResult(false, null, "Gateway unavailable");
        }
    }
}

Rules

  • The adapter implements the interface the client owns. The target interface should not mention vendor concepts.
  • Convert units, ids and error types inside the adapter. Document the mapping (for example, which vendor code means "declined").
  • One adapter per adaptee. If you need two vendors, write two adapters and pick one by configuration.

Conventions

  • Name it after the adaptee: FastPayAdapter, ArchiveStore. Keep adapters in an infrastructure or adapter package, away from the domain (this is the "ports and adapters" style, also called hexagonal architecture).
  • Test the adapter with a fake adaptee, and test the client with a fake target.

Edge cases

  • Lossy mapping: a double rupee amount can lose precision (0.1 + 0.2). Compute from integer paise as late as possible, or use BigDecimal.
  • Unmappable features: if the target has refund and the adaptee cannot, do not throw silently; split the interface (ISP) so the adapter implements only what it can.
  • Timeouts and retries belong to the adapter or a decorator around it, not to the business code.
  • Two-way adapter: one class implementing both interfaces so two systems can call each other. It is rare; avoid it unless needed.

Interview: Adapter

  • What is Adapter? A wrapper that converts one interface to another so that incompatible classes can work together. Give the payment SDK example.
  • Name JDK examples. InputStreamReader, Arrays.asList.
  • Adapter vs Decorator? Adapter changes the interface; Decorator keeps the same interface and adds behaviour. See the comparison table.

Interview: harder Adapter questions

  • Where would you use it in a real project? Wrapping each payment, SMS or email vendor behind your own interface, and as the anti-corruption layer towards legacy systems.
  • Class adapter vs object adapter in Java? Object adapter (composition); Java has single inheritance, so a class adapter is limited.
  • Is Spring's HandlerAdapter really an Adapter? Yes: DispatcherServlet works with the HandlerAdapter interface, and one implementation exists per handler type.
  • How does it support OCP? A new vendor is a new adapter; the client is not edited.

Decorator: adding behaviour by wrapping

Decorator wraps an object that has the same interface and adds behaviour before or after delegating to it, so you can stack features (caching, logging, retries) at run time without subclassing.

Intent: attach additional responsibilities to an object dynamically, as a flexible alternative to subclassing.

The problem

A PriceService loads product prices from a database. You need logging, then caching, then retry on failure, and sometimes you want only some of these. If you use inheritance (CachedLoggingPriceService, LoggingRetryingPriceService, ...) the classes multiply, as in the inheritance explosion. A decorator is a class that implements the same interface, holds another object of that interface, and adds one concern. You stack them like layers.

Implementation

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

interface PriceService {
    long priceOf(String sku);
}

class DbPriceService implements PriceService {            // the real component
    public long priceOf(String sku) {
        System.out.println("  DB query for " + sku);
        return 49900;
    }
}

abstract class PriceServiceDecorator implements PriceService {
    protected final PriceService delegate;
    protected PriceServiceDecorator(PriceService delegate) { this.delegate = delegate; }
}

class LoggingPriceService extends PriceServiceDecorator {
    LoggingPriceService(PriceService delegate) { super(delegate); }

    public long priceOf(String sku) {
        long start = System.nanoTime();
        long price = delegate.priceOf(sku);                       // call the wrapped object
        System.out.println("priceOf(" + sku + ") = " + price + " in "
                + (System.nanoTime() - start) / 1000 + " us");
        return price;
    }
}

class CachingPriceService extends PriceServiceDecorator {
    private final Map<String, Long> cache = new ConcurrentHashMap<>();
    CachingPriceService(PriceService delegate) { super(delegate); }

    public long priceOf(String sku) {
        return cache.computeIfAbsent(sku, delegate::priceOf);     // only calls on a miss
    }
}

public class DecoratorDemo {
    public static void main(String[] args) {
        PriceService service =
            new LoggingPriceService(new CachingPriceService(new DbPriceService()));
        service.priceOf("SKU-1");
        service.priceOf("SKU-1");
    }
}
  DB query for SKU-1
priceOf(SKU-1) = 49900 in 812 us
priceOf(SKU-1) = 49900 in 15 us

The second call did not hit the database, and the logging decorator on the outside saw both calls. The order of wrapping matters: logging outside caching logs every call; caching outside logging would log only the cache misses. The client holds a PriceService and cannot tell how many layers there are.

Note: computeIfAbsent on ConcurrentHashMap must not modify the map from inside the mapping function. A single database call is fine.

Decorator in Java I/O

The classic JDK example is the I/O stream family. InputStream is the component interface; FileInputStream is the concrete component; BufferedInputStream, GZIPInputStream and DataInputStream are decorators.

import java.io.*;
import java.util.zip.GZIPInputStream;

try (BufferedReader reader = new BufferedReader(          // adds line reading + buffering
        new InputStreamReader(                            // adapter: bytes to chars
            new GZIPInputStream(                          // adds decompression
                new FileInputStream("orders.csv.gz")),    // the real source
            java.nio.charset.StandardCharsets.UTF_8))) {
    String line;
    while ((line = reader.readLine()) != null) {
        System.out.println(line);
    }
}

Each layer adds one feature and delegates the rest. You can see both Decorator (buffer, gzip) and Adapter (InputStreamReader) in this one line.

Other uses

  • JDK: Collections.unmodifiableList, Collections.synchronizedMap and Collections.checkedList wrap a collection and add a behaviour (read-only, locking, type checks) behind the same interface.
  • Servlets: HttpServletRequestWrapper and HttpServletResponseWrapper let a filter alter a request; Spring has ContentCachingRequestWrapper.
  • Spring WebFlux: ServerHttpRequestDecorator.
  • Annotation-driven decoration: @Cacheable, @Transactional, @Retryable add behaviour around a bean through proxies (the mechanism is the Proxy pattern, the effect is Decorator-like).
  • In Spring you can declare a decorator as a bean: mark the real one @Primary or inject it by qualifier into the wrapper.

Pros

  • Adds behaviour without changing the original class (OCP).
  • Combine features in any order at run time; no class explosion.
  • Each decorator has one concern (SRP).

Cons

  • Many small objects; stack traces become deep and harder to read.
  • The order of decorators matters and is easy to get wrong.
  • You cannot tell from the interface which decorators are inside, and removing one from the middle is awkward.
  • A wide interface forces each decorator to forward every method.

When NOT to use a Decorator

  • When the concern is cross-cutting for many classes (logging, security, transactions). Use AOP: one aspect instead of a decorator per class.
  • When the interface is huge (20 methods). Forwarding every method is painful.
  • When code depends on the concrete type (instanceof or casts); wrapping breaks it.
  • For a single fixed variation, a plain subclass or a parameter is simpler.

Why the pattern exists

Subclassing adds behaviour at compile time and for all instances of the subclass. Real systems need the opposite: this one call should be logged, that one retried, and in tests neither. If every combination needs a class, you get the explosion described in Composition over inheritance. The Decorator answers with a simple trick: the wrapper has the same type as the thing it wraps, so a client cannot tell the difference, and wrappers can be stacked like layers of clothing. The same idea is behind @Transactional and @Cacheable in Spring.

How a call travels through the stack

A second example: payments, and why order matters

interface Gateway { String charge(String orderId, long paise); }

class RealGateway implements Gateway {            // fails twice, then works
    private int calls = 0;
    public String charge(String orderId, long paise) {
        if (++calls < 3) throw new IllegalStateException("timeout");
        return "PAY-" + orderId;
    }
}

class Retrying implements Gateway {
    private final Gateway next;
    private final int max;
    Retrying(Gateway next, int max) { this.next = next; this.max = max; }
    public String charge(String orderId, long paise) {
        for (int attempt = 1; ; attempt++) {
            try { return next.charge(orderId, paise); }
            catch (IllegalStateException e) { if (attempt >= max) throw e; }
        }
    }
}

class Auditing implements Gateway {
    private final Gateway next;
    Auditing(Gateway next) { this.next = next; }
    public String charge(String orderId, long paise) {
        System.out.println("charge " + orderId + " " + paise);
        String ref = next.charge(orderId, paise);
        System.out.println("ok " + ref);
        return ref;
    }
}

public class DecoratorOrderDemo {
    public static void main(String[] args) {
        System.out.println("-- retry outside audit");
        new Retrying(new Auditing(new RealGateway()), 3).charge("O-1", 1000);
        System.out.println("-- audit outside retry");
        new Auditing(new Retrying(new RealGateway(), 3)).charge("O-1", 1000);
    }
}
-- retry outside audit
charge O-1 1000
charge O-1 1000
charge O-1 1000
ok PAY-O-1
-- audit outside retry
charge O-1 1000
ok PAY-O-1

Same decorators, different order, different behaviour: the first stack logs every attempt, the second logs the business call once. Always decide the order on purpose and write it down where the stack is assembled (a configuration class or factory method). A real payment retry also needs an idempotency key so a retry cannot charge twice; see Command and the queue articles for that idea.

A reusable base class

When the interface has several methods, put the forwarding in an abstract decorator once, and let each concrete decorator override only the method it changes. The existing PriceServiceDecorator above is this pattern. Most IDEs can also generate the forwarding methods ("delegate methods") so you do not type them by hand.

Decorator, inheritance, proxy and AOP

ApproachChosen whenWeak point
SubclassOne fixed extensionExplosion; fixed at compile time
DecoratorOptional, stackable features for one interfaceOrder sensitivity; forwarding code
ProxyControlling access to the same object (lazy load, remote, security)Same shape, different intent
AOP (@Aspect)One concern across many beansMagic; harder to debug

Decorator and Proxy have the same structure. The difference is intent: a decorator adds a responsibility chosen by the client; a proxy controls access and usually creates or locates the real object itself. See the structural comparison.

Wrong: the decorator forgets to delegate one method

class Auditing implements Gateway {
    public String charge(String id, long paise) {
        return log(next.charge(id, paise));
    }
    public void refund(String ref) {
        // forgot: next.refund(ref) -- refund silently does nothing
    }
}

Right: every method forwards

class Auditing implements Gateway {
    public String charge(String id, long paise) {
        return log(next.charge(id, paise));
    }
    public void refund(String ref) {
        log("refund " + ref);
        next.refund(ref);
    }
}

Rules

  • A decorator implements the same interface as the wrapped object and holds one reference to it.
  • Forward every method; add behaviour only where intended. Do not change the meaning of the contract (LSP).
  • A decorator must be usable wherever the plain object is, and must not need to know what is inside.

Conventions

  • Name by the feature: Retrying, Caching, Auditing (or a suffix such as CachingPriceService).
  • Assemble the stack in one place and keep the order visible. In Spring, use a @Configuration class with explicit @Bean methods.
  • Keep each decorator small and independently tested with a fake inner object.

Edge cases

  • Identity: decorated == original is false, and instanceof checks on the concrete type fail. Program to the interface.
  • Exceptions: a decorator that catches and swallows exceptions (a retry that returns null at the end) hides failures. Rethrow the last one.
  • State: a caching decorator shared by threads needs a thread-safe store, as the ConcurrentHashMap note above says.
  • Streams: closing the outermost wrapper closes the inner ones (BufferedReader.close()), so close only the outer.

Interview: Decorator

  • What is Decorator? A wrapper with the same interface that adds behaviour and delegates to the wrapped object.
  • JDK example? new BufferedReader(new FileReader(...)); each layer adds a feature.
  • Decorator vs inheritance? Decorator adds features at run time and in any combination; inheritance fixes them at compile time and multiplies classes.
  • Decorator vs Proxy? Similar structure; Decorator adds responsibilities chosen by the client, Proxy controls access to the object. See the comparison.

Interview: harder Decorator questions

  • Decorator vs inheritance? Decorator adds behaviour per object at run time and can be stacked; inheritance is static and per class.
  • Decorator vs Proxy? Same structure; decorator adds responsibility, proxy controls access.
  • Does order matter? Yes. Show the retry and audit example.
  • Where in Spring? Request wrappers in servlet filters, and annotation behaviour (@Cacheable, @Transactional) which Spring implements with proxies.

Facade: one simple door to a complex subsystem

Facade provides one simple, high-level interface to a group of classes, so clients make one call instead of coordinating five collaborators and learning how they fit together.

Intent: provide a unified, simpler interface to a set of interfaces in a subsystem.

The problem

Placing an order in an e-commerce app needs five collaborators in the right order: check stock, reserve stock, charge the payment, create the shipment, send the confirmation. If the web controller, the mobile API, the admin tool and the batch job each coordinate these steps themselves, the sequence (and its failure handling) is copied four times and any change touches four places. A facade holds that coordination once.

Implementation

import java.util.List;

record Line(String sku, int qty) { }
record PlaceOrderCommand(String customerEmail, List<Line> lines, String cardToken) { }
record OrderConfirmation(String orderId, String trackingNumber) { }

// --- subsystem classes (each has its own API) ---
class InventoryService {
    boolean reserve(List<Line> lines) { /* ... */ return true; }
    void release(List<Line> lines)    { /* ... */ }
}
class PaymentService {
    long priceOf(List<Line> lines)         { return 129900; }
    String charge(String token, long paise) { return "PAY-1001"; }
}
class ShippingService {
    String createShipment(String email, List<Line> lines) { return "TRK-77"; }
}
class NotificationService {
    void orderConfirmed(String email, String orderId) { /* ... */ }
}

// --- the facade: ONE method for the whole use case ---
public class OrderFacade {
    private final InventoryService inventory;
    private final PaymentService payments;
    private final ShippingService shipping;
    private final NotificationService notifications;

    public OrderFacade(InventoryService inventory, PaymentService payments,
                       ShippingService shipping, NotificationService notifications) {
        this.inventory = inventory;
        this.payments = payments;
        this.shipping = shipping;
        this.notifications = notifications;
    }

    public OrderConfirmation placeOrder(PlaceOrderCommand cmd) {
        if (!inventory.reserve(cmd.lines())) {
            throw new IllegalStateException("Out of stock");
        }
        try {
            long total = payments.priceOf(cmd.lines());
            String paymentId = payments.charge(cmd.cardToken(), total);
            String tracking = shipping.createShipment(cmd.customerEmail(), cmd.lines());
            notifications.orderConfirmed(cmd.customerEmail(), paymentId);
            return new OrderConfirmation(paymentId, tracking);
        } catch (RuntimeException e) {
            inventory.release(cmd.lines());                  // compensate on failure
            throw e;
        }
    }
}

A controller now writes orderFacade.placeOrder(cmd) and nothing else. Notice that a facade does not forbid direct access: advanced code may still use the subsystem classes. It just offers a convenient default path. In Spring this class is a normal @Service (often called an application service or use-case service).

Facades in the JDK and Spring

  • SLF4J is literally the "Simple Logging Facade for Java": one API (LoggerFactory.getLogger(...)) in front of Logback, Log4j 2 or java.util.logging.
  • JdbcTemplate hides the connection, statement, result set and exception handling of raw JDBC behind calls such as query and update (it is also a Template Method, see below).
  • EntityManager / JpaRepository fronts a large persistence subsystem.
  • JDK: java.net.URL.openStream() hides socket and protocol handling; Files.readAllLines(path) hides stream creation and closing; HttpClient hides low-level networking.
  • Spring Boot's SpringApplication.run(...) is a facade over context creation, auto-configuration and server start.
// With raw JDBC: connection, statement, result set, try/catch/finally for 15 lines
// With the facade:
List<String> names = jdbcTemplate.query(
        "SELECT name FROM employees WHERE dept_id = ?",
        (rs, rowNum) -> rs.getString("name"),
        10);

Pros

  • Simple API for the common use case; clients learn one class.
  • Reduces coupling: clients do not know the subsystem classes.
  • One place for the orchestration and its failure handling.

Cons

  • The facade can grow into a god object that knows too much (keep it thin; one facade per use-case area).
  • It adds a layer; for a two-class subsystem it is noise.
  • Hides capabilities. Clients needing the fine detail must bypass it.

When NOT to use a Facade

  • When the subsystem is already simple, or when the facade would only forward one call to one class.
  • When the "facade" starts holding business rules and state. Then it is a service with too many responsibilities; split it (SRP).
  • In distributed systems, a facade over many remote services needs timeouts and failure policy; see the API gateway and orchestration patterns in Module 6.

Why the pattern exists

As a system grows, a use case such as "register a user" or "place an order" needs several collaborators in a fixed order. Without a facade, every caller (REST controller, mobile API, batch job, test) repeats that sequence. The sequences drift apart, one caller forgets the step that sends the email, and a change to the order of steps means editing five places. A Facade moves the sequence into one class and gives callers one meaningful method. It also reduces coupling: callers know one class, not five, so the subsystem can change behind the facade.

Where a facade sits

A second example: user onboarding

Registering a user creates the account, opens a wallet and sends a welcome email. The facade owns the sequence and the transaction boundary; each service stays focused on its own area.

record SignUp(String name, String email) { }
record Onboarded(long userId, long walletId) { }

interface UserService   { long create(String name, String email); }
interface WalletService { long open(long userId); }
interface MailService   { void sendWelcome(String email); }

class OnboardingFacade {
    private final UserService users;
    private final WalletService wallets;
    private final MailService mail;

    OnboardingFacade(UserService users, WalletService wallets, MailService mail) {
        this.users = users;
        this.wallets = wallets;
        this.mail = mail;
    }

    Onboarded register(SignUp request) {
        long userId = users.create(request.name(), request.email());
        long walletId = wallets.open(userId);
        try {
            mail.sendWelcome(request.email());        // nice to have: do not fail signup
        } catch (RuntimeException e) {
            System.out.println("Welcome mail failed, will retry later");
        }
        return new Onboarded(userId, walletId);
    }
}

In a Spring Boot app you would annotate the facade method with @Transactional so the user and the wallet are saved together or not at all. The mail call is deliberately outside the "must succeed" path: the facade is the place where such policy decisions live. For a mail that must not be lost, publish an event and let a listener send it (see Observer).

Facade, service layer and application service

In a typical Spring app the class you call a "service" often is a facade over repositories and other services. Names vary between teams (OrderFacade, OrderApplicationService, OrderService). What matters is the role: a thin coordinating layer with no business rules of its own. Business rules (price calculation, eligibility) stay in domain objects or domain services, which the facade calls.

PatternGoalNumber of classes behind it
FacadeSimplify use of a subsystemMany
AdapterConvert one interface to anotherUsually one
DecoratorAdd behaviour, same interfaceOne (wrapped)
MediatorLet peers talk through a hub; peers know the hubMany, which also call back

The one-way knowledge is the key difference from a Mediator: subsystem classes do not know the facade exists, while Mediator colleagues talk to the mediator. Compare all structural patterns in the comparison article.

Wrong: business rules inside the facade

Onboarded register(SignUp r) {
    if (r.email().endsWith("@gmail.com")
            && r.name().length() > 3) {   // rules leak in
        // ... 40 lines of eligibility and pricing logic
    }
    long id = users.create(r.name(), r.email());
    return new Onboarded(id, wallets.open(id));
}

Right: facade coordinates, domain decides

Onboarded register(SignUp r) {
    eligibility.check(r);                  // rule lives in its own class
    long id = users.create(r.name(), r.email());
    return new Onboarded(id, wallets.open(id));
}

Rules

  • A facade coordinates; it does not hold business rules. If an if expresses a business decision, it belongs in a domain class.
  • The facade's methods use the client's vocabulary (register, placeOrder), not the subsystem's (createRow).
  • Subsystem classes must not depend on the facade, or you create a cycle.

Conventions

  • One facade per use-case area (orders, onboarding, reporting), not one giant SystemFacade.
  • Accept and return simple request/response objects (records), not subsystem entities.
  • Put the transaction boundary and the failure policy in the facade, and document it.

Edge cases

  • Partial failure: if the wallet step fails after the user was created and there is no shared transaction (two microservices), you need a compensating action or a saga (Module 6).
  • Bypass: a facade should not forbid direct use of the subsystem. If a rare caller needs fine control, let it use the services.
  • Testing: unit test the facade with mocked services to check the order and the failure path; test each service separately.
  • Facade over a remote system: each call is a network call; add timeouts and keep the facade stateless.

Interview: Facade

  • What is Facade? A single simple interface in front of a complicated subsystem. Example: OrderFacade.placeOrder.
  • Facade vs Adapter? Facade simplifies many classes into a new, easier interface; Adapter converts one interface into the one a client already expects. See the comparison.
  • Name a Facade in Java. SLF4J, JdbcTemplate.

Interview: harder Facade questions

  • Facade vs Adapter? A facade simplifies many classes and defines a new interface; an adapter makes an existing class match an interface that already exists.
  • Is a Spring @Service a facade? Often yes, when it coordinates repositories and other services. It stops being one when it is full of business rules.
  • How do you stop a facade becoming a god class? Split by use-case area and push rules into domain classes.
  • Give a JDK or library example. SLF4J, JdbcTemplate, Files.readAllLines.

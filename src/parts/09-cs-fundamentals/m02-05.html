What happens when you type a URL and press Enter: the full walkthrough

The browser parses the URL, resolves the domain through DNS, opens a TCP connection and a TLS session, sends an HTTP request that passes a CDN or load balancer to your Spring Boot app and its database, receives the response, then parses and renders it, fetching more assets and API data as it goes.

Why interviewers love this question

One question touches DNS, TCP, TLS, HTTP, load balancing, your backend framework, the database and browser rendering. It shows how deep your understanding goes and which part you know best. The trick is a clear order, then depth where you are strong. Use the 14 steps below as your skeleton. The case: you type https://shop.example.com/products for a React front end backed by a Spring Boot API.

Step 1: URL parsing, HSTS and the shortcut checks

The browser first decides whether you typed a URL or a search term. If it is a URL it splits it into scheme (https), host, port (443 by default), path and query. If you typed just shop.example.com, the browser consults its HSTS list: if the site asked to be HTTPS-only (or is preloaded in the browser), the browser silently upgrades http:// to https:// and skips the insecure first request. It also checks for a cached copy of the resource (HTTP cache) and for a service worker that may answer directly. A fresh cached copy ends the story here.

Step 2: DNS resolution

The browser needs the IP of shop.example.com. It looks in, in order: its own DNS cache, the OS cache and hosts file, the home router's cache, and then asks the recursive resolver of your ISP or a public one (see DNS). On a miss the resolver walks root → TLD (.com) → authoritative server and gets back an A (or AAAA) record. It caches it by TTL. For a big site the answer is the address of a CDN edge or load balancer near you, not of one application server. Typical cost: from nothing (cached) to a few tens of milliseconds.

Step 3: TCP connection

With the IP, the browser asks the OS for a socket to port 443. The OS picks an ephemeral source port and runs the three-way handshake (SYN, SYN-ACK, ACK). The path crosses your NIC, Wi-Fi or Ethernet, the router (which NATs your private address), then ISP and internet routers; at each hop the MAC addresses are rewritten and the TTL decreases. ARP is used to find the gateway's MAC on your LAN. This step costs one round trip. If the browser already has an open connection to this host (HTTP/2 or keep-alive), it skips steps 3 and 4. With HTTP/3 the transport and TLS steps merge on top of UDP and QUIC.

Step 4: TLS handshake

Inside that TCP connection the browser sends a ClientHello (with SNI and key share). The server answers with its choice, its certificate chain and a proof of key ownership. The browser verifies the chain against its trusted CAs and the hostname, then both sides derive the same symmetric keys (TLS 1.3, one extra RTT). From this point everything is encrypted, and ALPN has also agreed which HTTP version to use (HTTP/2 typically).

Step 5: The HTTP request

The browser sends something like GET /products HTTP/2 with the Host, Accept, Accept-Encoding: gzip, br, User-Agent and any matching Cookie headers. If the site is a single-page app, this first request returns a small HTML shell; the data comes later via API calls.

Step 6: CDN, reverse proxy and load balancer

The request reaches the server's front door. A CDN (content delivery network) edge near you may answer static files from its cache immediately. Otherwise a reverse proxy such as Nginx or a cloud load balancer terminates TLS (decrypts), may apply a WAF (web application firewall) and rate limits, chooses a healthy instance (round robin, least connections) and forwards the request over the private network, often as plain HTTP/1.1, adding headers such as X-Forwarded-For so the app knows the client's real IP. See System Design · Module 5 for load balancing and CDNs, and DevOps · Module 2 for Nginx.

Step 7: Inside the Spring Boot application

The embedded Tomcat accepts the connection on a thread (or, with virtual threads, a cheap one). The request passes the servlet filter chain (character encoding, CORS, Spring Security: authenticate the cookie or JWT, authorise the user, logging filters). Then the DispatcherServlet maps GET /products to a @RestController method through handler mapping; argument resolvers bind path variables, query parameters and the request body (JSON → Java object via Jackson). The controller calls a @Service that holds the business logic and (with @Transactional) starts a transaction. The service calls a Repository. Details: Spring Boot · Module 2.

Step 8: The database (and cache)

The service may first check a cache such as Redis. On a miss, the repository borrows a connection from the pool (HikariCP), and Hibernate sends SQL such as SELECT ... FROM product WHERE active = true over a TCP connection to the database (PostgreSQL port 5432). The database parses and plans the query, uses an index, reads pages from its buffer cache or disk and returns rows. The connection returns to the pool, the transaction commits or rolls back, and the rows are mapped to entities, then to DTOs. See SQL · Module 5.

Step 9: The response travels back

Jackson serialises the DTOs to JSON, the controller returns 200 OK with headers such as Content-Type: application/json, Cache-Control and perhaps Content-Encoding: gzip. The response goes back through the filters, Tomcat, the load balancer (which re-encrypts it if needed and may add headers), possibly through the CDN (which may cache it), over TCP segments split to the MSS, and each segment is acknowledged. Your browser's TLS layer decrypts it and hands the bytes to the HTTP layer.

Step 10: Browser parsing and rendering

The browser's rendering engine turns bytes into pixels (see Frontend · Module 1):

  1. Parse the HTML into the DOM tree. The parser stops at plain <script> tags unless they use defer or async.
  2. Parse CSS into the CSSOM. CSS blocks rendering until loaded.
  3. Combine DOM and CSSOM into the render tree (only visible elements with their computed styles).
  4. Layout (reflow): compute each box's size and position.
  5. Paint the pixels, then composite layers on the GPU.

Step 11: More requests

While parsing, the browser finds links to CSS, JavaScript bundles, fonts and images. Each is another request, usually reusing the open HTTP/2 connection (multiplexing) and often served from the CDN or the browser cache. When the React bundle runs, it calls your API with fetch('/api/products'), repeating steps 5 to 9 for JSON, then updates the DOM and the browser repaints. Cookies, a CORS preflight (OPTIONS) for cross-origin calls and authentication headers can add requests. Finally the connection is kept alive or closed by the idle timeout (the FIN exchange).

Tip: know where time goes

Roughly: DNS (0 to tens of ms), TCP (1 RTT), TLS 1.3 (1 RTT), server time (your code and database), transfer time (size ÷ throughput), browser parse and render. Every layer has a caching escape hatch: DNS cache, HTTP cache, CDN, Redis, DB buffer cache. Mention caching at each step.

What changes in other cases

  • Cached or HSTS: steps are skipped; a fresh cache entry means no request at all, and a stale one triggers a conditional request that returns 304.
  • Redirects: http → https (301) or example.com → www costs a full extra round trip.
  • Proxy or VPN: the browser connects to the proxy first; HTTPS goes through an HTTP CONNECT tunnel.
  • Failure points: DNS fail (UnknownHostException), TCP refused or timeout, TLS certificate error, 4xx/5xx from the app, slow query (504 from the proxy).

The 3–4 minute spoken answer, and follow-up questions

A strong answer follows the request in order, spends a sentence or two per stage, names the key protocol at each, and signals depth you can expand on; practise it aloud until it runs for three to four minutes.

How to structure it

  1. Open with a one-line map: "I'll go from the browser, through the network, to the server and back."
  2. Cover all stages in order. Do not dive into one stage before finishing the skeleton.
  3. Add one specific detail per stage that proves you understand (TTL, SYN, SNI, filter chain, connection pool, render tree).
  4. Close with the caching and optimisation points, and offer to go deeper on any part.

Speaking pace is about 130 words a minute, so 3–4 minutes is 400–500 words. The model answer below is about that length. Adapt the backend part to your own project.

Model answer

"Let me walk through it from the keyboard to the screen. First the browser parses the URL into scheme, host, port and path. If the site is on the HSTS list, it upgrades to HTTPS straight away. It also checks its HTTP cache, and if there is a fresh copy, it may not go to the network at all.

Next it needs an IP address, so it does a DNS lookup. It checks the browser cache, the OS cache and the hosts file, then asks the recursive resolver. If the resolver has no cached answer, it asks a root server, which points to the .com TLD server, which points to the authoritative server for the domain. That returns an A record with a TTL, and every layer caches it.

With the IP, the browser opens a TCP connection to port 443: the three-way handshake of SYN, SYN-ACK and ACK, which costs one round trip. Then the TLS handshake. In TLS 1.3 the client sends its supported ciphers and a key share, the server replies with its key share and certificate, the browser validates the certificate chain against trusted CAs and checks the hostname, and both sides derive the same symmetric key. From then on, everything is encrypted, and the HTTP version is negotiated, usually HTTP/2.

Now the browser sends the HTTP request, for example GET /products with headers and cookies. It usually reaches a CDN or a load balancer first. The CDN can serve static content from its cache. For dynamic requests, the load balancer terminates TLS, picks a healthy instance and forwards the request to my Spring Boot application.

In the application, the request passes through the servlet filters, which handle things like CORS and Spring Security authentication. Then the DispatcherServlet routes it to the right controller method, which binds the parameters and calls the service layer. The service holds the business logic, may check a Redis cache and, if needed, calls the repository. Through the connection pool, Hibernate sends a SQL query to the database. The database uses an index, finds the rows and returns them. The service maps them to DTOs and the controller returns them as JSON with a 200 status.

The response travels back the same way: through the load balancer, maybe cached by the CDN, split into TCP segments and decrypted by the browser. Then the browser renders: it parses HTML into the DOM, CSS into the CSSOM, merges them into a render tree, calculates layout and paints pixels. While doing so it discovers CSS, JavaScript, fonts and images and fetches them, mostly in parallel over one HTTP/2 connection. If it is a React app, the JavaScript then calls my API for data and re-renders. Caching happens at nearly every step, from DNS to the CDN to the browser cache, which is what makes the web fast."

Follow-up questions and short answers

What if the DNS server is down or slow?
The OS tries the next configured resolver. Public resolvers are replicated; cached answers still work until the TTL ends. The user sees a "site can't be reached" or UnknownHostException in Java.
Where is TLS terminated, and why?
Usually at the load balancer or reverse proxy, so certificates are managed in one place and the app is not burdened by crypto. For zero trust setups it is re-encrypted to the app.
How does HTTP/2 change this?
One connection for all resources, multiplexed, with header compression. No need to open six connections, so fewer handshakes.
What if it is HTTP and not HTTPS?
No TLS step; data is readable and modifiable on the way. Browsers mark it "Not secure".
How would you make the page faster?
Fewer round trips: keep-alive/HTTP/2/HTTP/3, CDN, DNS prefetch, compression, caching headers, smaller JS bundles, database indexes and a Redis cache.
How does the server know which of many sites you want?
The Host header (and SNI at the TLS layer).
What if the server is in another country?
Higher RTT multiplies every handshake round trip; that is why CDNs and regional deployments matter.
What happens to session state with many servers?
Use a shared session store such as Redis or stateless tokens; sticky sessions are a fallback.
What does ARP do in this flow?
It resolves your gateway's MAC address on the local network so the first frame can leave your LAN.
Where does NAT happen?
At your home router (and maybe your ISP) rewriting the private source IP and port.
What is the difference between the browser cache and the CDN?
The browser cache is private to one user's device; the CDN cache is shared by many users and sits near them.
What happens on a POST form submit instead of a GET?
The body carries the data; the server responds with 201 or a redirect (the Post/Redirect/Get pattern to avoid resubmission on refresh).

Mistakes to avoid

  • Starting with "the browser sends an HTTP request" and skipping DNS, TCP and TLS.
  • Memorising a script: interviewers interrupt. Remember the order, not the sentences.
  • Spending three minutes on one stage and rushing the rest. Skeleton first, depth when asked.
  • Saying TCP "sends the website". TCP only moves bytes; HTTP gives them meaning.

Tip: tune it to the role

For a backend role, linger on filters, the controller-service-repository path, connection pooling and caching. For frontend, on parsing and the render tree. For a DevOps or system design round, on DNS, load balancer, CDN and TLS termination. A one-sentence "I can go deeper into any part" invites the follow-up you prepared for.

Network security basics: firewalls, proxies, VPNs and common attacks

Firewalls filter traffic by rules, proxies stand in for clients or servers, VPNs tunnel traffic privately across the internet, and the classic attacks (DDoS, MITM, DNS and ARP spoofing, SYN flood) are defended by filtering, rate limiting, encryption and certificates.

Security goals

Security is usually described by the CIA triad: confidentiality (only the right people read the data), integrity (data is not altered) and availability (the service stays up). Attacks target one of the three. Good design is defence in depth: many layers, so one failure is not fatal.

Firewalls

A firewall allows or blocks traffic using rules, normally "default deny": only what is explicitly allowed gets through.

  • Packet-filtering (layer 3/4): rules on source/destination IP, port and protocol. Example: allow TCP 443 from anywhere, TCP 22 only from the office IP, block the rest.
  • Stateful: remembers connections, so replies to allowed outbound requests are let back in automatically. Most firewalls today.
  • Application-layer / WAF (layer 7): understands HTTP and blocks SQL injection or XSS patterns. A "next-generation firewall" adds deep packet inspection and intrusion prevention.

Firewalls can run on a host (iptables/nftables, Windows Firewall), at the network edge, or in the cloud (security groups and network ACLs; see DevOps · Module 2). A DMZ is a separate network zone for public-facing servers, so a breach there does not give direct access to the internal network.

Proxies

TypeSits in front ofPurpose
Forward proxyClientsClients go through it to reach the internet: filtering, caching, hiding client IPs, corporate policy.
Reverse proxyServersClients talk to it, not the servers: load balancing, TLS termination, caching, protection (Nginx, HAProxy, cloud load balancers).

Remember: a forward proxy hides the client, a reverse proxy hides the server.

VPN

A VPN (Virtual Private Network) creates an encrypted tunnel between your device and a VPN gateway. Your traffic is encapsulated inside the tunnel packets, so the local network or ISP cannot read it, and the destination sees the gateway's IP. Uses: remote employees reaching the office network (remote-access VPN), joining two office networks (site-to-site), or privacy on public Wi-Fi. Common protocols include IPsec, OpenVPN and WireGuard. A VPN moves trust to the VPN provider; it does not make you anonymous or fix an insecure site.

How HTTPS and certificates defend

TLS makes sniffing useless (encryption), makes tampering detectable (integrity) and blocks impersonation (the certificate must match the domain and chain to a trusted CA). If an attacker poisons DNS or ARP and steers you to their machine, they cannot present a valid certificate for bank.example, so the browser warns. This is why you should never click through a certificate warning. HSTS stops downgrade attacks, and certificate pinning or mTLS tighten trust further for apps and services.

Practical checklist for a developer

  • Expose only needed ports; default-deny firewall rules; databases never public.
  • Use HTTPS everywhere, redirect HTTP, enable HSTS.
  • Secrets in environment or a vault, not in code or URLs.
  • Rate-limit login and public APIs; put a WAF/CDN in front.
  • Keep software patched; use SSH keys, not passwords; disable Telnet and plain FTP.

Limits of these defences

  • Firewalls cannot stop an attack that arrives on an allowed port (a bad request to port 443) without a WAF or app-level checks.
  • DDoS defence needs capacity upstream; a single server cannot absorb a large flood.
  • SYN cookies lose some TCP options; they are used only under attack.

Interview: "What is a firewall / VPN / proxy / DDoS?"

  • One-sentence definitions, then the layer or direction (forward vs reverse proxy).
  • For each attack, say what is exploited (ARP trust, DNS trust, handshake state) and the fix.
  • Tie it together: HTTPS plus validated certificates defeats most MITM attempts.

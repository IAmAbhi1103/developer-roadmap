Inheritance types, the diamond problem and uses of super

Java allows single, multilevel and hierarchical inheritance with classes, and gets multiple and hybrid inheritance only through interfaces, which avoids the diamond problem for state.

Types of inheritance

HierarchicalB and C both extend ACar and Bike extend Vehicle Yes

class Animal { void eat() { System.out.println("eats"); } }
class Dog extends Animal { void bark() { System.out.println("barks"); } }   // single
class Puppy extends Dog { void weep() { System.out.println("weeps"); } }   // multilevel
class Cat extends Animal { void meow() { System.out.println("meows"); } }  // hierarchical

A Puppy object can call eat(), bark() and weep(). Every Java class, directly or indirectly, extends java.lang.Object, which is why every object has toString(), equals(), hashCode() and so on.

Multiple inheritance through interfaces

A Java class can extend only one class but can implement any number of interfaces, and an interface can extend several interfaces:

interface Flyable { void fly(); }
interface Swimmable { void swim(); }

class Duck implements Flyable, Swimmable {       // multiple inheritance of TYPE
    public void fly()  { System.out.println("Duck flies"); }
    public void swim() { System.out.println("Duck swims"); }
}

A Duck is-a Flyable and is-a Swimmable. Interfaces have no instance state, so there is no conflict about whose fields to inherit.

The diamond problem

Suppose A has a method show() that both B and C override differently. Which version should D inherit? In C++ (which allows multiple class inheritance) D may get two copies of A's data and an ambiguous show(). This is the diamond problem.

How Java avoids it: a class can extend only one class, so D cannot extend both B and C. That also removes the question of duplicated state. Reasons given: simpler language and predictable behaviour.

The diamond with default methods (Java 8+)

Since Java 8, interfaces can have default methods, so conflicts can happen again. The rules:

  1. A method inherited from a class always wins over an interface method.
  2. If one interface extends another, the more specific (sub-interface) default wins.
  3. Otherwise there is a conflict: the compiler reports an error and the class must override the method. It can pick one with Interface.super.method().
interface Walker  { default String move() { return "walk"; } }
interface Swimmer { default String move() { return "swim"; } }

class Duck implements Walker, Swimmer {
    @Override
    public String move() {                      // required: otherwise compile error
        return Walker.super.move() + " and " + Swimmer.super.move();
    }
}

public class Test {
    public static void main(String[] args) {
        System.out.println(new Duck().move());
    }
}
walk and swim

Uses of super

  • super(...) — call a parent constructor (must be first in the constructor).
  • super.method() — call the parent's version of an overridden method, often to extend it rather than replace it.
  • super.field — read the parent's field that a same-named child field hides.
class Account {
    protected double balance = 100;
    void describe() { System.out.println("Account balance " + balance); }
}

class SavingsAccount extends Account {
    protected double balance = 5;               // hides the parent's field
    @Override
    void describe() {
        super.describe();                        // parent behaviour first
        System.out.println("Savings extra " + this.balance + " / parent " + super.balance);
    }
}

new SavingsAccount().describe() prints Account balance 100.0 and then Savings extra 5.0 / parent 100.0.

Constructor order in an inheritance chain

class A { A() { System.out.println("A"); } }
class B extends A { B() { System.out.println("B"); } }
class C extends B { C() { System.out.println("C"); } }
// new C() prints: A, B, C   (parent constructors run first)

The first line of every constructor is an implicit or explicit call to a parent constructor, so the chain always starts at Object and runs down to the class you instantiated.

Inheritance rules in Java

  • One extends only; many implements.
  • Private members and constructors are not inherited (private fields exist in the object but are not accessible in the child).
  • A final class cannot be extended; a final method cannot be overridden.
  • Static methods are "inherited" for calling but are hidden, not overridden.
  • Cyclic inheritance (A extends B, B extends A) is a compile error.

Use inheritance only for a true is-a

Test: "is every B really an A in all situations?" A Stack that extends Vector (as the JDK's old java.util.Stack does) exposes methods like insertElementAt that break stack discipline. When in doubt use composition (see the relationships article).

Interview angle

"Why does Java not support multiple inheritance?" — To avoid the diamond problem and complexity; interfaces give multiple inheritance of type. Follow-up: "But default methods?" — conflicts must be resolved explicitly with X.super.m(). Also: "constructor execution order", "can we inherit private members?"

Polymorphism: overloading, overriding and binding

Overloading (same name, different parameters) is resolved by the compiler; overriding (same signature in a subclass) is resolved at runtime from the actual object, which is static versus dynamic binding.

Compile-time vs runtime polymorphism

MechanismMethod overloadingMethod overriding
Decided byCompiler, from the declared types of the arguments JVM, from the actual class of the object
Also calledStatic or early bindingDynamic or late binding, dynamic method dispatch

Operator overloading: Java does not let you define your own. The only built-in case is +, which adds numbers and concatenates strings. (C++ and Kotlin allow it.) Java designers left it out to keep code predictable.

Method overloading

Overloading means several methods in the same class (or between a class and its subclass) with the same name but different parameter lists. A method's signature is its name plus the parameter types in order.

class Calculator {
    int add(int a, int b)          { return a + b; }
    double add(double a, double b) { return a + b; }
    int add(int a, int b, int c)   { return a + b + c; }
}

Method overriding

Overriding means a subclass provides its own implementation of a method already defined in its superclass (or interface), with the same signature. Always write @Override; the compiler then checks that you really override.

class Notification {
    String channel() { return "generic"; }
}
class SmsNotification extends Notification {
    @Override
    String channel() { return "SMS"; }
}
// Notification n = new SmsNotification();  n.channel() returns "SMS"

Mistake: changing only the return type

int  find(String s) { return 0; }
long find(String s) { return 0; }     // compile error: same signature

The return type is not part of the signature, so this is neither overloading nor a valid override.

Static vs dynamic binding

Binding is linking a method call to the method body that will run.

  • Static (early) binding: the compiler decides. It applies to private, static and final methods, constructors, and overload selection.
  • Dynamic (late) binding: the JVM decides at runtime from the object's real class. It applies to all other instance methods; in Java every non-static, non-private, non-final method is virtual by default.

Fields are never polymorphic: a field access is resolved by the reference type.

Upcasting and downcasting

Shape s = new Circle(2);           // upcast: always safe, implicit
Circle c = (Circle) s;             // downcast: explicit, checked at runtime
if (s instanceof Circle circle) {  // pattern matching (Java 16+): test and cast
    System.out.println(circle.area());
}
Rectangle r = (Rectangle) s;       // compiles, throws ClassCastException at runtime

Through a parent reference you can call only what the parent type declares (the compiler checks that), but the child's overriding version runs.

Output-prediction questions

1. Fields, instance methods and static methods through a parent reference

class Parent {
    String name = "Parent";
    void show() { System.out.println("Parent.show"); }
    static void greet() { System.out.println("Parent.greet"); }
}
class Child extends Parent {
    String name = "Child";
    @Override void show() { System.out.println("Child.show"); }
    static void greet() { System.out.println("Child.greet"); }

// in main:
Parent p = new Child();
System.out.println(p.name);
p.show();
p.greet();
System.out.println(((Child) p).name);
Parent
Child.show

The field and the static method follow the reference type (Parent); only the instance method is dynamic.

2. Which overload runs for f(5)?

static void f(long x)    { System.out.println("long"); }
static void f(Integer x) { System.out.println("Integer"); }
static void f(Object x)  { System.out.println("Object"); }
static void f(int... x)  { System.out.println("varargs"); }
// f(5) prints: long

Java tries three phases in order: (1) widening only, no boxing, no varargs — f(long) fits, so it wins. Delete that overload and phase 2 (boxing) picks f(Integer), the most specific of Integer and Object. Varargs is the last resort.

3. null argument and reference type

static void g(Object o) { System.out.println("Object"); }
static void g(String s) { System.out.println("String"); }

g(null);                 // String: the most specific applicable overload
Object o = "hello";
g(o);                    // Object: chosen by the declared type, not the runtime type

With g(String) and g(StringBuilder) instead, g(null) is a compile error: ambiguous.

4. An overridden method called from a parent constructor

class Base {
    Base() { init(); }
    void init() { System.out.println("Base.init"); }
}
class Derived extends Base {
    int x = 5;
    @Override void init() { System.out.println("Derived.init x=" + x); }
}
// new Derived() prints: Derived.init x=0

The parent constructor runs first and calls the child's init() (dynamic binding), but the child's field initialiser x = 5 has not run yet, so x is still 0. Never call overridable methods from a constructor.

5. Overloading with an upcast argument

class Animal { }
class Dog extends Animal { }
static void speak(Animal a) { System.out.println("animal"); }
static void speak(Dog d)    { System.out.println("dog"); }

Animal a = new Dog();
speak(a);                // animal  (compile-time type is Animal)
speak(new Dog());        // dog

Edge cases

  • A subclass can hide a static method by declaring one with the same signature; this is hiding, not overriding.
  • You can overload main, but the JVM calls only public static void main(String[]).
  • Overriding with a covariant return: parent returns Number, child returns Integer — valid.
  • An overriding method cannot throw a broader checked exception than the parent declares; a parent method that declares none cannot be overridden with a checked exception.

Abstract class vs interface (Java 8 and later)

An abstract class is a partly built base class that can hold state and constructors and is extended once; an interface is a contract of capabilities that a class can implement many times and (since Java 8) can carry default, static and private methods but no instance state.

Abstract class

An abstract class is declared with abstract; it cannot be instantiated, and may contain abstract methods (no body) and ordinary methods, fields and constructors. A subclass must implement all inherited abstract methods or be abstract itself.

abstract class Bird {
    protected final String name;                 // state
    Bird(String name) { this.name = name; }      // constructor

    abstract String sound();                     // must be implemented
    void eat() { System.out.println(name + " eats"); }   // shared code
}

Interface

An interface defines a contract: what a class can do. Classes implement it. Members are implicitly public; methods are abstract unless marked default, static or private; fields are implicitly public static final (constants).

interface Flyable {
    int MAX_ALTITUDE = 1000;               // public static final constant

    void fly();                            // abstract (implicitly public)

    default void land() {                  // Java 8: default method with a body
        System.out.println("Landing safely");
        log("land");
    }

    static Flyable noOp() {                // Java 8: static method
        return () -> { };
    }

    private void log(String action) {      // Java 9: private helper
        System.out.println("log: " + action);
    }
}

The noOp() body is valid because an interface with exactly one abstract method can be written as a lambda (a functional interface; add @FunctionalInterface to have the compiler enforce it).

What changed in Java 8 and 9

  • Java 8: default methods. Added so existing interfaces can gain methods without breaking every implementing class — this is how List.sort, Iterable.forEach and Collection.stream were added.
  • Java 8: static methods in interfaces (utility methods tied to the interface, called as Flyable.noOp(); not inherited by implementing classes).
  • Java 9: private methods (instance and static) to share code between default methods without exposing it.

Because of these, the old statement "an interface cannot have method bodies" is outdated, and "interface = 100% abstraction" is true only for the pre-Java-8 view.

When to use which

Choose an abstract class when

  • Related classes share state (fields) and code
  • You need constructors or non-public members
  • You want a template: fixed steps, with some steps left to subclasses (the Template Method pattern)

Choose an interface when

  • You define a capability that unrelated classes can share (Comparable, Runnable, Flyable)
  • A class needs several roles at once
  • You want loose coupling and easy testing: code to the interface

Common modern design: an interface for the contract, plus an optional abstract class that gives a skeleton implementation (like List and AbstractList in the JDK). Prefer interfaces by default; reach for an abstract class when you need shared state.

Both together

class Sparrow extends Bird implements Flyable {
    Sparrow() { super("Sparrow"); }                 // abstract class constructor runs
    @Override String sound() { return "chirp"; }
    @Override public void fly() { System.out.println(name + " flies"); }
}

Frequent questions

Can an abstract class have a constructor?
Yes. It cannot be called with new directly, but a subclass constructor calls it with super(...), so the abstract class can initialise its own fields (as Bird sets name). The object that gets created is the subclass object.
Can an abstract class have no abstract methods?
Yes. It then just prevents instantiation (a "base class only") — for example HttpServlet in Java EE.
Can an interface have state?
Only constants: fields are always public static final. There are no instance fields, so no per-object state.
Can an abstract class be final? A method abstract and private/static/final?
No to all: these contradict the purpose, because abstract means "must be extended or overridden".
Can an interface have a main method?
Yes, since static methods are allowed; it runs like any class's main.
Can a default method override equals or hashCode?
No; the compiler forbids default methods for the methods of Object.
What is a marker interface?
An interface with no methods (Serializable) that tags a class; covered in the extra concepts article.

Sealed types (Java 17+)

A sealed interface or class restricts which classes may implement or extend it, with permits. It is useful when you want a closed set of subtypes, for example with pattern matching in switch.

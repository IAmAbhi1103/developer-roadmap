HTTP: requests, responses, methods, status codes and headers

HTTP is a stateless, text-based request/response protocol on top of TCP: the client sends a method, a URL, headers and an optional body, and the server answers with a status code, headers and an optional body.

What HTTP is

HTTP (HyperText Transfer Protocol) is the application-layer protocol of the web and of almost every REST API. It is client–server (the client always starts), request–response (one request gets one response) and stateless: the server keeps no memory of earlier requests, so each request must carry everything needed to process it (cookies and tokens fill this gap, see the next article). It normally runs on TCP port 80, or 443 with TLS. For API design with Spring Boot see Spring Boot · Module 2; here we cover the protocol itself.

URL anatomy

A URL like https://shop.example.com:8443/orders/42?status=open#items has a scheme (https), host (shop.example.com), optional port (8443; default 443 for https, 80 for http), path (/orders/42), query string (status=open) and fragment (items, used only by the browser and never sent to the server).

Request format

POST /orders HTTP/1.1
Host: shop.example.com
User-Agent: Mozilla/5.0
Accept: application/json
Content-Type: application/json
Content-Length: 37
Authorization: Bearer eyJhbGciOi...
Cookie: JSESSIONID=ABC123

{"productId": 7, "quantity": 2}

A request has: (1) the request line (method, path, version); (2) headers, one Name: value per line; (3) a blank line; (4) an optional body. The Host header is mandatory in HTTP/1.1; it lets one server and IP host many websites (virtual hosting).

Response format

HTTP/1.1 201 Created
Content-Type: application/json
Content-Length: 41
Location: /orders/1001
Set-Cookie: JSESSIONID=ABC123; HttpOnly; Secure
Cache-Control: no-store

{"id": 1001, "status": "CREATED"}

A response has a status line (version, status code, reason phrase), headers, a blank line and an optional body.

A method is "safe" if it does not change server state, and "idempotent" if doing it many times has the same effect as once.

Persistent connections (keep-alive)

HTTP/1.0 opened a new TCP connection for every request: handshake cost each time (and with HTTPS, a TLS handshake too). HTTP/1.1 connections are persistent by default: after a response the connection stays open for the next request, until either side sends Connection: close or an idle timeout expires. This saves round trips and avoids repeating TCP slow start. Pipelining (sending several requests without waiting) was defined in 1.1 but is rarely used because responses must still come back in order.

Idempotence and retries

Because the network can fail after a request is sent but before the reply arrives, a client does not know whether the server acted. It is safe to retry GET, PUT and DELETE. A POST retry can create a duplicate order, so payment APIs use an idempotency key header that makes the server ignore repeats.

Mistake: using GET to change data

Browsers, crawlers and proxies treat GET as safe: they prefetch, cache and retry it. A GET /deleteUser?id=5 link can be triggered by a crawler or a cached prefetch. Use POST, PUT or DELETE for changes. Also never put passwords or tokens in the URL: it is logged and shown in history.

Edge cases

  • HTTP does allow a body on GET and DELETE, but many servers and proxies ignore it. Avoid it.
  • A 302 redirect after POST usually makes the browser re-request with GET. Use 307 or 308 to keep the method.
  • Statelessness is about the protocol: servers can still keep state (sessions, caches) if the client identifies itself each time.

Interview: "What is HTTP? What does stateless mean?"

  • Application-layer, request-response, text-based, on TCP; default ports 80 and 443.
  • Stateless: no memory between requests; state goes in cookies, tokens or the database.
  • Know the status classes, 401 vs 403, GET vs POST, and idempotent methods.

Cookies and sessions

Cookies let a stateless protocol remember users: the server sets a small named value in the browser, the browser sends it back on every request, and a session stores the user's real data on the server under that cookie's ID.

The problem and the idea

HTTP forgets you after every response. But a shopping cart or a login must survive across requests. The fix is a cookie: a small piece of data that the server asks the browser to store. The browser then attaches it automatically to later requests to the same site.

Cookie attributes

Set-Cookie: JSESSIONID=abc123; Path=/; Max-Age=1800; HttpOnly; Secure; SameSite=Lax

Expires / Max-AgeWhen the cookie dies. Without one it is a session cookie, deleted when the browser closes.
Domain, PathWhich hosts and URL paths receive the cookie.

HttpOnlyJavaScript cannot read it (document.cookie): blunts XSS theft.
SameSiteStrict never sent on cross-site requests, Lax sent only on top-level navigations (the browser default), None always (needs Secure). Defends against CSRF.

Browsers limit cookies to about 4 KB each and a few dozen per site, and send them on every request to that site (including images), so keep them small.

Cookies vs sessions

A session is usually implemented with a cookie: the cookie holds the session ID and the server holds the data. In Java servlet containers this ID is JSESSIONID. When you run several app instances behind a load balancer, the session must be reachable from all of them: use sticky sessions (the load balancer pins a user to one instance) or, better, a shared store such as Redis (Spring Session) or a stateless token (JWT), covered in Spring Boot · Module 4.

Other client storage

localStorage and sessionStorage hold larger data (about 5 MB) in the browser but are not sent automatically with requests and are readable by any script on the page, so do not keep secrets there. See Frontend · Module 4.

Rule: session cookies should be HttpOnly, Secure and SameSite

A cookie that identifies a logged-in user is a key to the account. Set HttpOnly (no script access), Secure (HTTPS only) and SameSite=Lax or Strict. Spring Security and Tomcat support these settings.

Edge cases

  • Session fixation: if the session ID does not change at login, an attacker who planted a known ID gets the logged-in session. Always issue a new ID on login (Spring Security does).
  • Third-party cookies (set by another domain's content on the page) are being restricted by browsers because they enable cross-site tracking.
  • Cookies are tied to the host: example.com cookies are not sent to other.com.

What it looks like on the wire

Cookies are ordinary HTTP headers (see HTTP basics). The server sends one Set-Cookie header per cookie. The browser answers with a single Cookie header that joins all matching cookies with semicolons. The browser sends only the name and value back; the attributes (Path, Secure and so on) stay in the browser and are never repeated.

HTTP/1.1 200 OK
Set-Cookie: JSESSIONID=abc123; Path=/; HttpOnly; Secure; SameSite=Lax
Set-Cookie: theme=dark; Path=/; Max-Age=31536000

GET /cart HTTP/1.1
Host: shop.example.com
Cookie: JSESSIONID=abc123; theme=dark

Attributes in more detail

  • Domain. If you leave it out, the cookie is host-only: it goes to the exact host that set it. If you set Domain=example.com, it also goes to every subdomain such as api.example.com. Fewer hosts is safer.
  • Path. The cookie is sent when the request path starts with this value. Path=/ means the whole site. Path is a convenience, not a security boundary.
  • Max-Age and Expires. Max-Age is in seconds from now; Expires is a date. If both appear, Max-Age wins. To delete a cookie, the server sends the same name with Max-Age=0. A cookie with neither is a session cookie and disappears when the browser closes (browsers that restore tabs may keep it longer).
  • SameSite and "site". A site is the registrable domain, such as example.com, so app.example.com and api.example.com are the same site, while example.com and other.com are not. Lax still sends the cookie when a user clicks a link to your site from another site, but not on cross-site POST forms or background requests, which stops most CSRF attacks.
  • Name prefixes. A cookie named __Host- something is accepted only if it has Secure, Path=/ and no Domain. This protects it from being overwritten by a sibling subdomain.

How sessions work on the server

A session is a server-side map (attribute name to value) that belongs to one browser. The server creates it when needed, generates a long random ID, and sends that ID in a cookie. The ID must be unguessable, because anyone who holds it acts as that user. In Java, the servlet API calls this HttpSession.

import jakarta.servlet.http.HttpSession;
import org.springframework.web.bind.annotation.*;

@RestController
public class CartController {

    @PostMapping("/cart/items/{sku}")
    public int add(@PathVariable String sku, HttpSession session) {
        Cart cart = (Cart) session.getAttribute("cart");
        if (cart == null) {
            cart = new Cart();                 // first request: no cart yet
            session.setAttribute("cart", cart);
        }
        cart.add(sku);
        return cart.size();
    }
}

The session object lives in server memory by default. Tomcat expires an idle session after 30 minutes unless you change it; in Spring Boot the property is server.servlet.session.timeout. The cookie flags can be set with server.servlet.session.cookie.http-only, .secure and .same-site. For several instances, Spring Session can keep sessions in Redis or a database instead of memory, so any instance can serve any request. The stored object (here Cart) must be serializable for this.

Session fixation, step by step

  1. The attacker visits the site, receives session ID X, and tricks the victim into using X (for example through a link or a vulnerable subdomain).
  2. The victim logs in. If the server keeps ID X, the session is now authenticated.
  3. The attacker sends X and is logged in as the victim.

The fix is to change the session ID at login (Spring Security does this by default) and to invalidate the session on logout. Never accept a session ID from the URL (the old ;jsessionid= style), because URLs leak through logs and the Referer header.

Convention: keep sessions small

Store an ID or a small object in the session, not whole database result lists. Big sessions use memory per user and slow down replication. Set a sensible timeout and call session.invalidate() on logout.

Mistake: thinking HttpOnly stops everything

HttpOnly only stops scripts from reading the cookie. An XSS bug can still make requests that carry it. You still need input escaping and a Content Security Policy. Likewise Secure does nothing if the site also answers on plain HTTP; redirect HTTP to HTTPS.

Cookie consent

Indian and EU sites often show cookie banners. Cookies needed for login or the cart are "strictly necessary"; analytics and advertising cookies normally need the user's consent. This is a legal topic, so ask your team's policy owner.

The browser returns it in the Cookie header on every request, and the server looks up the user. I set HttpOnly, Secure and SameSite, change the ID at login to stop fixation, and use Redis for sessions when running several instances. JWT is the stateless alternative."

HTTP/1.1 vs HTTP/2 vs HTTP/3

HTTP/1.1 sends one request at a time per connection in text; HTTP/2 multiplexes many streams over one TCP connection in a binary format with header compression; HTTP/3 runs the same ideas over QUIC (UDP) to remove TCP's head-of-line blocking and speed up connection setup.

HTTP/1.1 and its limits

HTTP/1.1 (1997) is text-based. Even with persistent connections, a connection handles one request-response at a time. If response 1 is slow, request 2 waits behind it: head-of-line (HOL) blocking at the HTTP level. Browsers worked around it by opening about six parallel TCP connections per host, and developers used tricks such as bundling files, image sprites and domain sharding. Headers like Cookie and User-Agent are repeated in full on every request.

HTTP/2

HTTP/2 (2015) keeps the same meaning (methods, status codes, headers) but changes how bytes travel.

  • Binary framing: messages are split into small binary frames; faster to parse than text.
  • Multiplexing: many streams (request/response pairs) share one TCP connection, their frames interleaved. A slow response no longer blocks others. One connection per host is enough.
  • Header compression (HPACK): repeated headers are sent as short indexes.
  • Stream prioritisation and flow control per stream.
  • Server push: the server could send resources before they were asked for. It was little used and has been removed from major browsers.

Browsers use HTTP/2 only over TLS in practice (negotiated with ALPN during the TLS handshake). The remaining problem: HTTP/2 still sits on one TCP connection. If one TCP segment is lost, TCP holds back all streams until it is retransmitted: HOL blocking at the transport level.

HTTP/3

HTTP/3 (2022) keeps HTTP/2's model but replaces TCP with QUIC over UDP. Streams are independent inside QUIC, so a lost packet delays only its own stream. TLS 1.3 is built into QUIC, so connection setup takes one RTT (or zero on resumption) instead of TCP plus TLS in two or three. Headers use QPACK compression. Connection migration keeps sessions alive when your phone changes networks. A browser discovers HTTP/3 support from the Alt-Svc header (or DNS) and falls back to HTTP/2 if UDP is blocked.

Real projects

You seldom code against these versions: Nginx, a CDN or a load balancer typically terminates HTTP/2 or HTTP/3 from browsers and talks plain HTTP/1.1 to your Spring Boot app. Spring Boot supports HTTP/2 with server.http2.enabled=true (it needs TLS on Tomcat for browsers). Java's built-in java.net.http.HttpClient speaks HTTP/1.1 and HTTP/2. Because multiplexing removes the connection-per-request penalty, old tricks like file bundling matter less on HTTP/2 and later.

HTTP/2 internals

HTTP/2 splits every message into frames. Each frame has a 9-byte header: a 3-byte length, a 1-byte type (for example HEADERS, DATA, SETTINGS), 1 byte of flags and a stream identifier. Frames from different streams are mixed on the one connection, and the receiver sorts them by stream ID. Streams started by the client use odd numbers. Flow control works per stream and per connection, so a slow consumer cannot make the sender flood the memory.

HPACK compresses headers with two tables. A static table lists common headers such as :method GET or :status 200. A dynamic table remembers headers this connection has sent, such as your long Cookie or User-Agent, so the next request sends only a small index. Values that do not match a table entry are compressed with Huffman coding. The pseudo-headers (:method, :path, :scheme, :authority) replace the old request line and the Host header.

The browser and the server agree on HTTP/2 inside the TLS handshake through ALPN (Application-Layer Protocol Negotiation): the client offers h2 and http/1.1, and the server picks one. Because the semantics are unchanged, your controllers, status codes and JSON bodies work the same on any version.

QUIC and HTTP/3 internals

QUIC is a transport protocol built on UDP. It does what TCP and TLS did together: reliability, ordering inside each stream, congestion control and encryption. Key points:

  • Independent streams. Loss recovery is per stream, so a missing packet blocks only the streams whose data it carried.
  • Faster start. TLS 1.3 is part of the QUIC handshake, so the first request can go after one round trip. A client that has talked to the server before may send data in the very first flight: 0-RTT.
  • Connection IDs. A connection is identified by an ID, not by the IP and port pair. When your phone moves from Wi-Fi to mobile data, the connection survives (connection migration).
  • QPACK. A header compression like HPACK, redesigned so that streams arriving out of order do not block each other; it uses separate streams for table updates.
  • Runs in user space. QUIC is implemented in the application or library, not in the OS kernel, so it can improve quickly, but it often uses more CPU than TCP.

Edge case: 0-RTT can be replayed

Data sent in the first flight can be captured and sent again by an attacker. Servers therefore accept 0-RTT only for safe, idempotent requests such as GET, never for a payment POST.

Round trips before the first request

SetupHandshake round trips
HTTP/1.1 or HTTP/2 over TCP + TLS 1.21 (TCP) + 2 (TLS) = 3
TCP + TLS 1.31 + 1 = 2
HTTP/3 over QUIC (first visit)1
HTTP/3 with 0-RTT resumption0 (data in the first flight)

On a mobile network with a 100 ms round trip, saving two round trips means 200 ms less before the first byte is requested. The gain is largest on slow, lossy networks and smallest on a fast office LAN.

How a client finds out which version to use

A first visit usually goes over TCP. The server answers with an Alt-Svc header such as Alt-Svc: h3=":443"; ma=86400, which says "HTTP/3 is available on UDP port 443 for the next 24 hours". The browser tries QUIC next time and falls back to HTTP/2 if UDP is blocked. Newer DNS records (HTTPS records) can also announce this. You can check the version a server speaks with curl.

$ curl -s -o /dev/null -w "%{http_version}\n" https://example.com
2
$ curl -sI https://example.com | grep -i alt-svc
alt-svc: h3=":443"; ma=86400

The exact output depends on the site. Testing HTTP/3 with curl --http3 works only if your curl build supports it. In browser DevTools, the Network tab can show a Protocol column with h2 or h3.

Wrong: HTTP/1.1 habits on HTTP/2

cdn1.shop.com, cdn2.shop.com, cdn3.shop.com   (domain sharding)
one 4 MB bundle.js changed on every release
# extra connections, extra TLS handshakes, no cache reuse

Right: one host, sensible split files

vendor.js (rarely changes) + app.js (changes often)
# multiplexing handles many files; caching works per file

Rule: HTTP semantics do not change

Methods, status codes, headers and cookies mean the same on all three versions. Only the encoding and transport change. Your API design (see HTTP basics) does not depend on the version.

Convention: terminate at the edge

Enable HTTP/2 (and HTTP/3 where offered) on the CDN or reverse proxy that faces browsers, and keep a simple HTTP/1.1 link to your Spring Boot instances inside the private network. Keep-alive connections to the backend are enough.

Mistake: "HTTP/3 is always faster"

On a clean, fast network the difference is small. HTTP/3 helps most with packet loss, long distances and changing networks. Some corporate firewalls block UDP 443, which is why HTTP/2 stays as the fallback. Also, HTTP/2 over TCP can be slower than several HTTP/1.1 connections on a very lossy link, because one lost segment stalls every stream.

Interview: "What problem did HTTP/2 solve? And HTTP/3?"

  • HTTP/2: multiplexing over one connection, HPACK, binary framing; fixes HTTP-level HOL.
  • Still TCP-level HOL on packet loss; HTTP/3 uses QUIC over UDP to fix that.
  • HTTP/3 also gives a faster handshake and connection migration.

20-second answer: "HTTP/1.1 handles one request at a time per connection, so slow responses block the ones behind them. HTTP/2 uses binary frames, multiplexes many streams on one TCP connection and compresses headers with HPACK, but one lost TCP segment still stalls all streams. HTTP/3 runs over QUIC on UDP, so streams are independent, the handshake needs one round trip or zero, and connections survive network changes."

HTTPS and TLS: encryption, certificates and the TLS 1.3 handshake

HTTPS is HTTP inside a TLS-encrypted connection: TLS uses a certificate signed by a trusted authority to prove the server's identity, uses asymmetric cryptography to agree on a key, and then uses fast symmetric encryption for the data, giving confidentiality, integrity and authentication.

Why HTTPS

Plain HTTP travels as readable text. Anyone on the path (Wi-Fi owner, ISP, a hacked router) can read passwords, change the page (inject ads or malware) or pretend to be the site. TLS (Transport Layer Security; the successor of SSL) fixes this. HTTPS = HTTP + TLS, on port 443. TLS gives three guarantees:

  • Confidentiality: data is encrypted; eavesdroppers see noise.
  • Integrity: any change in transit is detected.
  • Authentication: you are talking to the real example.com, not an impostor.

Symmetric vs asymmetric encryption

PointSymmetricAsymmetric (public-key)
KeysOne shared secret keyA key pair: public + private
SpeedVery fastSlow (100–1000× slower)
ProblemHow to share the key safely?Expensive for bulk data
ExamplesAES-GCM, ChaCha20RSA, ECDSA, ECDH (key exchange)

TLS combines both: asymmetric cryptography (or a key-agreement protocol) to agree on a shared secret over an open network, then symmetric encryption for all data. With asymmetric keys, what the public key encrypts only the private key can decrypt, and what the private key signs anyone can verify with the public key. A hash (SHA-256) and a MAC/AEAD tag give the integrity check.

Certificates and certificate authorities

How do you know a public key really belongs to shop.example.com? Through a digital certificate (X.509): a document saying "this public key belongs to this domain", with an expiry date, signed by a Certificate Authority (CA) such as Let's Encrypt, DigiCert or Google Trust Services. Your OS and browser ship a list of trusted root CAs. Servers usually send a chain: their own certificate, signed by an intermediate CA, which is signed by a root in your trust store. The browser checks the chain's signatures, that the certificate is not expired or revoked, and that the hostname matches the certificate's Subject Alternative Name list. A mismatch gives the browser's red warning.

Free automated certificates (Let's Encrypt, ACME, as in the DevOps module's Nginx section at DevOps · Module 2) are why HTTPS is now the default.

The TLS 1.3 handshake (simplified)

  1. ClientHello: the client lists the TLS versions and cipher suites it supports, sends its half of a key exchange (an ephemeral Diffie-Hellman key share) and the SNI (the hostname wanted, so a server with many sites picks the right certificate).
  2. ServerHello: the server picks a cipher suite and sends its key share. Now both sides can compute the same shared secret without ever sending it. From here, the handshake messages are already encrypted.
  3. Certificate + proof: the server sends its certificate chain and a signature over the handshake made with its private key (CertificateVerify), proving it owns the certificate, then a Finished message.
  4. Client checks and finishes: the client validates the chain, hostname and signature, then sends its own Finished. Traffic keys are derived; the application data (HTTP) flows under symmetric encryption (AES-GCM or ChaCha20-Poly1305).

TLS 1.3 needs one round trip (1-RTT) after the TCP handshake. TLS 1.2 needed two. A client that has connected before can use session resumption and even send data in the first flight (0-RTT, with replay risks, so only for safe requests). TLS 1.3 also removed old weak options (RSA key transport, RC4, SHA-1), and uses forward secrecy: the key is ephemeral, so stealing the server's private key later does not decrypt recorded traffic.

What HTTPS protects, and what it does not

Protected

  • URL path, query, headers, cookies and body from eavesdroppers
  • Tampering with the page in transit
  • Impersonation of the domain (if CAs and the browser behave)

Not protected

  • The destination IP and, usually, the hostname (SNI, DNS lookups) are visible
  • Traffic size and timing
  • The server itself: SQL injection, XSS, and a hacked server still work over HTTPS
  • A phishing site can have a valid certificate for its own domain
  • Your own device: malware or a trusted rogue CA on your machine

HTTPS secures the road, not the destination. The padlock means "encrypted to whoever owns this domain", not "trustworthy".

HSTS and mutual TLS

HSTS (Strict-Transport-Security header) tells the browser "for the next N seconds, use only HTTPS for this site", blocking downgrade attacks where an attacker strips the first plain-HTTP redirect. In mutual TLS (mTLS) the client also presents a certificate, common for service-to-service calls inside a service mesh.

HTTPS in Java

Java keeps trusted CA certificates in a truststore (the default cacerts file) and your server's own key and certificate in a keystore. Typical Spring Boot properties:

server.port=8443
server.ssl.enabled=true
server.ssl.key-store=classpath:keystore.p12
server.ssl.key-store-password=${KEYSTORE_PASSWORD}
server.ssl.key-store-type=PKCS12

In production most teams terminate TLS at Nginx, a cloud load balancer or an ingress, not in the Spring Boot app.

Errors you will see

  • javax.net.ssl.SSLHandshakeException: PKIX path building failed: your JVM does not trust the server's CA (often a corporate proxy or a self-signed certificate); import the CA into the truststore.
  • Browser NET::ERR_CERT_DATE_INVALID / hostname mismatch: expired certificate or the certificate is for a different name.
  • Never "fix" it by disabling certificate validation in code; that removes the protection entirely.

Interview: "How does HTTPS work?"

  • TCP handshake, then TLS: hello messages, key exchange, certificate check, then symmetric encryption.
  • Why both kinds of crypto: asymmetric for trust and key agreement, symmetric for speed.
  • Role of the CA and the chain of trust; TLS 1.3 is 1-RTT with forward secrecy.
  • State plainly what HTTPS does not protect.

DNS: hierarchy, resolution, caching and record types

DNS is the internet's distributed phone book: it translates a domain name into an IP address by asking a recursive resolver, which walks down the hierarchy (root, TLD, authoritative server) and caches answers for their TTL.

Why DNS

Humans remember flipkart.com; routers need an IP address. In the early internet a single hosts file mapped names to addresses; that did not scale. The Domain Name System is a global, hierarchical, distributed database, so no single machine holds everything and the load is spread out. It is an application-layer service that mostly uses UDP port 53, and TCP port 53 for large responses and zone transfers.

The hierarchy

A domain name is read right to left. In www.shop.example.com. the final dot is the invisible root; com is the top-level domain; example is the second-level domain; shop is a subdomain; www a host name.

Root servers
Know which servers handle each TLD. There are 13 root server identities (named A to M), each served by many machines worldwide via anycast.
TLD servers
Run .com, .org, .in and so on; know which name servers are authoritative for each domain under them.
Authoritative name server
Holds the actual records for a domain, set by the domain owner (via a provider like Route 53 or Cloudflare). Gives the final answer.
Recursive resolver
The server that does the work for you, run by your ISP or a public service (8.8.8.8, 1.1.1.1). It caches answers.
Stub resolver
The small client in your OS that just asks the recursive resolver.

Resolution step by step

Recursive vs iterative: your device makes a recursive query ("get me the final answer, I will wait"). The recursive resolver then makes iterative queries: each server it asks does not chase the answer but replies with the best help it has, a referral to the next server down, until the authoritative server gives the real answer.

Caching and TTL

Every record has a TTL (time to live, in seconds) set by the domain owner. Caches may keep the answer until the TTL expires. Caching happens at every level, which is why most lookups never reach the root: browser cache → OS cache (and the hosts file) → router cache → resolver cache → authoritative server. Resolvers also cache the TLD servers' addresses, so root and TLD servers are contacted rarely. Java caches DNS lookups too (networkaddress.cache.ttl security property); long-running apps that never refresh can keep calling an old IP after a failover.

The cost of caching is slow propagation: if you change an IP with TTL 86,400 (a day), some users will keep reaching the old one for up to a day. Teams lower the TTL before a planned migration.

A CNAME cannot coexist with other records on the same name, so it cannot be placed on the bare domain (the "zone apex"); providers offer ALIAS or ANAME records for that.

$ dig example.com A +noall +answer
example.com.    300    IN    A    203.0.113.10
$ nslookup example.com
Name:    example.com
Address: 203.0.113.10

The number 300 is the remaining TTL. The sample uses a documentation address.

Edge cases and failures

  • Negative caching: "this name does not exist" (NXDOMAIN) is cached too.
  • java.net.UnknownHostException: the name could not be resolved: typo, no DNS access, or a missing record. Different from a connection error: no IP was even found.
  • DNS load balancing: one name can return several A records, rotated (round robin), or different answers by location (GeoDNS).
  • DNS is mostly unencrypted and unauthenticated; DNSSEC adds signatures, and DNS over HTTPS or TLS encrypts the query.

Interview: "How does DNS resolution work?"

  • Caches first (browser, OS), then the recursive resolver; if it misses: root → TLD → authoritative.
  • Recursive (client to resolver) vs iterative (resolver to servers); UDP 53.
  • TTL and caching; record types A, AAAA, CNAME, MX, NS, TXT.

Other application protocols in one line each

Besides HTTP and DNS, a handful of application protocols come up in interviews: FTP for files, SMTP/IMAP/POP3 for email, SSH for secure remote shells, Telnet (insecure), WebSocket for two-way web messages, and DHCP for address assignment.

Email in short

Sending mail from Alice at one company to Bob at another follows: Alice's mail app → her server over SMTP → the server finds Bob's server through the domain's MX record in DNS → delivers over SMTP → Bob's app fetches it from his server using IMAP or POP3. SMTP only pushes; IMAP and POP3 only fetch. Spring Boot sends mail with JavaMailSender over SMTP.

HTTP vs WebSocket

HTTP is request-response: the server cannot speak first. For chat, live scores or trading tickers you want the server to push updates. Options: polling (ask repeatedly, wasteful), Server-Sent Events (one-way stream over HTTP), or WebSocket: the browser sends an HTTP request with Upgrade: websocket, the server answers 101 Switching Protocols, and the same TCP connection then carries small two-way messages with little overhead. Spring supports WebSocket and STOMP messaging; see Spring Boot · Module 7.

Tip: encrypted versions end in S or sit on a different port

HTTP → HTTPS, FTP → FTPS/SFTP, IMAP → IMAPS (993), Telnet → SSH, WebSocket → wss://. If a protocol sends passwords in plain text, replace it with its secure variant.

Interview: "Name the protocols for email" and "WebSocket vs HTTP"

  • SMTP sends, IMAP/POP3 receive; IMAP syncs and keeps mail on server, POP3 downloads.
  • SSH vs Telnet: encrypted vs plain text. FTP uses two connections (control and data).
  • WebSocket: upgrade from HTTP, then persistent full-duplex messages.

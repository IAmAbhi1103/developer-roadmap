An operating system (OS) is the software that sits between your programs and the hardware. Every Java program you run, every Spring Boot server and every Docker container depends on it for CPU time, memory, files and network. What an operating system does: kernel, modes and system calls

An OS is a resource manager and an abstraction layer: its kernel runs in privileged mode, shares the CPU, memory and devices among programs safely, and offers system calls as the only door through which user programs ask for those services.

The three jobs of an OS

A bare computer is a CPU, some RAM and devices. Writing every program against raw hardware would be painful and unsafe. The OS does three jobs:

  • Resource manager. The CPU, memory, disk and network card are limited, and many programs want them at once. The OS decides who gets what, and when (scheduling, memory allocation, disk and network queues).
  • Abstraction. It hides ugly hardware details behind clean ideas: a process instead of "CPU registers and memory areas", a file instead of "disk sectors", a socket instead of "network card registers". Your FileInputStream works the same on any disk.
  • Protection. One buggy or malicious program must not read another program's memory, corrupt the disk or hog the CPU forever. The OS, with help from the hardware, enforces this.

Types of operating systems

TypeIdea in one line

Windows, Linux, macOS and Android are all multitasking, multiprocessor systems. Servers that run your Spring Boot app are almost always Linux.

The kernel and the two modes

The kernel is the core of the OS: the part that is always in memory and has full control of the hardware. It contains the scheduler, memory manager, file system, device drivers and network stack. Everything else (your shell, browser, JVM) is a user program.

The CPU has at least two privilege levels, selected by a mode bit:

  • Kernel mode (supervisor mode): can run every instruction, touch any memory, talk to devices, change the page tables.
  • User mode: can run only safe instructions and touch only its own memory. A privileged instruction (such as "disable interrupts" or "write to an I/O port") raises a trap, and the kernel typically kills the program.

This split is the foundation of protection. A crash in user mode kills one program; a crash in kernel mode (a driver bug) can bring down the whole machine (a "blue screen" or "kernel panic").

System calls: the only door into the kernel

A user program cannot read a file itself. It asks the kernel through a system call (syscall). Libraries such as the C library, and the JVM on top of it, wrap syscalls so you rarely see them directly.

  1. The program puts the syscall number and arguments in registers and executes a special trap instruction (a software interrupt; syscall on modern x86-64).
  2. The CPU switches to kernel mode and jumps to a fixed kernel entry point.
  3. The kernel checks the arguments and permissions, does the work (possibly blocking the process while the disk works), and stores the result.
  4. The CPU switches back to user mode and the program continues after the call.

You can watch the syscalls of any program on Linux with strace:

Rule: user programs never run privileged code directly

Every request that touches hardware or another process goes through a system call, and the kernel validates it. This is what makes isolation possible.

Edge cases

  • A system call is not a normal function call: it costs a mode switch (and often a copy of data between user and kernel memory), so many tiny read/write calls are slow. That is why Java wraps streams in BufferedInputStream.
  • An interrupt (from hardware, such as a timer or a network packet) and a trap (from software, such as a syscall or a divide-by-zero) both move the CPU into kernel mode; they differ in who raised them.
  • "Operating system" and "kernel" are not the same thing: Linux is a kernel; Ubuntu is an OS built around it with tools and libraries.

Interview: "What is a system call? What happens when a program calls read()?"

  • It is the controlled entry point to the kernel; the user program traps into kernel mode, the kernel does the work and returns.
  • Mention the mode bit, the trap instruction, argument checking and the return to user mode.
  • Say why: protection, since user code cannot touch devices or other processes' memory directly.
  • Give examples: fork, exec, open, read, write, mmap.

Processes: memory layout, PCB, states and context switching

A process is a program in execution with its own address space and resources; the OS tracks each one in a Process Control Block, moves it through the states new, ready, running, waiting and terminated, and saves and restores its CPU state on every context switch.

Program vs process

A program is a passive file on disk (your app.jar or the java binary). A process is a running instance of it: code plus data plus the current position in the code plus the resources it holds. Start the same program twice and you get two processes, each with its own PID (process id).

Memory layout of a process

  • Text: the compiled instructions. Read-only and shareable between processes running the same program.
  • Data: global and static variables.
  • Heap: memory requested at run time. Forgetting to free it in C is a leak; in Java the garbage collector does it (see JVM memory).
  • Stack: one frame per active function call. A runaway recursion fills the stack and ends in a stack overflow (StackOverflowError in Java).

Process Control Block (PCB)

The kernel keeps one PCB (also called the task control block) per process. It is the OS's record card for that process:

PCB fieldHolds
PID, parent PIDIdentity and family tree

Memory-management informationPage-table pointer, segment limits

In Linux the PCB is a structure called task_struct. The ready queue and device wait queues are lists of PCBs.

Process states

StateMeaning
NewBeing created; the PCB is being set up.
ReadyHas everything except the CPU; waiting in the ready queue.
RunningExecuting on a CPU. At most one process per core.
Waiting (blocked)Cannot continue until an event happens, such as a disk read finishing or a lock being released.
TerminatedFinished; resources are being reclaimed.

Notice what is not allowed: a waiting process never goes straight to running (it must become ready and wait for the scheduler), and a ready process never goes to waiting by itself. Real systems add suspended states for processes swapped out of memory. Do not confuse the OS "waiting" state with Java's Thread.State names (BLOCKED, WAITING, TIMED_WAITING), which describe the same idea at JVM level.

Context switching

A context switch is when the CPU stops running one process and starts another. The kernel saves the old process's context (program counter, registers, stack pointer, and memory-mapping information) into its PCB, picks the next process, and loads that process's saved context.

  1. A timer interrupt, a blocking syscall or a higher-priority arrival enters the kernel.
  2. The kernel saves the running process's registers and program counter into its PCB and sets its state (ready or waiting).
  3. The scheduler picks the next ready process.
  4. The kernel switches the address space (page-table pointer) and loads the new process's registers from its PCB.
  5. The CPU returns to user mode and continues the new process exactly where it stopped.

Switching is pure overhead: no user work is done while it happens. The direct cost is the saving and loading of state. The bigger, hidden cost is that the new process finds the CPU caches and the TLB (the address-translation cache, see TLB) full of the old process's data, so it runs slowly at first. Switching between threads of the same process is cheaper because the address space stays the same.

Creating processes: fork() and exec()

On Unix, fork() creates a child that is a copy of the parent. It returns 0 in the child, the child's PID in the parent, and -1 on failure. Modern kernels use copy-on-write: parent and child share the same physical pages until one of them writes, and only then is that page copied. Then the child usually calls exec(), which replaces its memory with a new program. The parent can call wait() to collect the child's exit status.

pid = fork();
if (pid == 0) {
    execlp("ls", "ls", "-l", NULL);   /* child: become the ls program */
} else if (pid > 0) {
    wait(NULL);                         /* parent: wait for the child */
} else {
    perror("fork failed");
}

Shells work exactly like this: type ls and the shell forks, the child execs ls, and the shell waits. In Java you do the same thing with ProcessBuilder, which hides the fork/exec.

Zombie and orphan processes

KindWhat happenedHow it ends
ZombieThe child has finished, but the parent has not called wait(). The kernel keeps its PCB entry (PID and exit status) so the parent can still read it. It uses no CPU or memory except that entry. ps shows state Z.The parent calls wait(), or the parent dies and the zombie is adopted and reaped by init.
OrphanThe parent finished first while the child is still running.The child is adopted by the init process (PID 1, such as systemd), which reaps it when it ends.

A zombie cannot be killed with kill -9 because it is already dead; only its parent can clear it. Thousands of zombies can exhaust the PID table.

Rule: a running process belongs to exactly one state at a time

Only the scheduler moves a process from ready to running. A process moves to waiting only by its own action (a blocking call). Remember: ready → running → (ready | waiting | terminated), and waiting → ready.

Mistake: "a process waiting for I/O is using the CPU"

A waiting process uses no CPU at all; it sits in a wait queue until the device raises an interrupt. This is exactly why multiprogramming raises CPU utilisation: the CPU runs someone else meanwhile.

Real projects

A Docker container is, to the kernel, just a group of ordinary processes with isolated views of the system. If your container's main process (PID 1) does not reap children, zombies pile up; tools like tini (or docker run --init) exist for this reason. See DevOps · Docker.

Interview: "Explain process states and what a context switch does"

  • Draw the five states and label every arrow (admitted, dispatch, preempt, wait, wake-up, exit).
  • Context switch: save registers and PC into the old PCB, load them from the new PCB, switch address space. Overhead, no useful work.
  • Add the hidden cost: cold cache and TLB.
  • Zombie = finished, not yet reaped; orphan = parent gone, adopted by init.

Inter-process communication (IPC)

Because processes have separate address spaces, they need OS-provided channels to exchange data: pipes, shared memory, message queues, sockets and signals, each with its own trade-off between speed, ease and how far apart the processes may be.

Why IPC is needed

Process isolation means process A cannot read process B's variables. Yet real systems need cooperation: a shell connects cat to grep, a web server talks to a database, a browser talks to its renderer processes. IPC is the set of mechanisms the kernel offers for this. They fall into two models:

  • Shared memory: the kernel maps one region into both address spaces. Processes read and write it like normal memory. Very fast (no copying), but you must synchronise access yourself.
  • Message passing: processes send and receive messages through the kernel. Slower (data is copied and every message costs a syscall), but simpler and safe, and it extends naturally to different machines.

The common mechanisms

MechanismModelKey points
Unnamed pipeMessage passing (byte stream)One-way, between related processes (parent and child). The shell's a | b. Created with pipe().
Named pipe (FIFO)Message passingA pipe with a name in the file system, so unrelated processes can use it. mkfifo.
Message queueMessage passingThe kernel stores discrete, often typed, messages until the receiver reads them. Survives short sender-receiver timing gaps.

SocketMessage passingTwo-way; works on one machine (Unix domain socket) or across the network (TCP/UDP). The basis of all client-server software. See Computer networks.
SignalNotification onlyA tiny asynchronous event with no data, such as SIGTERM (please stop), SIGKILL (cannot be caught), SIGINT (Ctrl+C).
 
$ cat access.log | grep " 500 " | wc -l
37

Here the shell creates two pipes and three processes. cat writes into the first pipe, grep reads from it and writes into the second, and wc reads that. The kernel buffers the bytes; if the pipe is full the writer blocks, and if it is empty the reader blocks (a built-in producer–consumer, see classic problems).

Signals in practice

When Kubernetes or docker stop stops your Spring Boot app, it first sends SIGTERM. The JVM runs its shutdown hooks (Spring closes the context, finishes in-flight requests, closes pools) and exits. If the app is still alive after a grace period, SIGKILL ends it instantly with no cleanup. Handling SIGTERM properly is called graceful shutdown.

Choosing a mechanism

  • Parent and child streaming bytes: pipe.
  • Very large data on one machine, speed matters: shared memory plus a semaphore.
  • Separate services, possibly on different machines: sockets (HTTP, gRPC and database drivers all run over them).
  • Just "wake up" or "stop": signal.

Rule: shared memory needs synchronization, message passing does not

With shared memory two processes can write the same bytes at once, which is a race condition (see critical section). A pipe or queue is synchronised by the kernel.

Edge cases

  • Writing to a pipe whose read end is closed raises SIGPIPE (or an EPIPE error); a read from a pipe whose write end is closed returns end-of-file.
  • SIGKILL and SIGSTOP can never be caught, blocked or ignored.
  • Pipes have a limited buffer; a writer faster than the reader will block.

Real projects

Between your microservices the IPC is sockets (HTTP/gRPC) or a broker such as Kafka. Inside one machine, PostgreSQL's backend processes coordinate through shared memory. Java itself has no direct pipe-between-processes API beyond Process streams, but java.nio offers MappedByteBuffer (memory-mapped files, which can be shared).

Interview: "What are the ways processes communicate?"

  • Two models: shared memory (fast, needs synchronization) and message passing (simpler, copies data).
  • Name pipes, named pipes, message queues, shared memory, sockets, signals, and when each fits.
  • Pipes are one-way byte streams between related processes; sockets work across machines.

Threads and process vs thread

A thread is a unit of execution inside a process; threads of one process share code, data, heap and open files but each has its own stack and registers, which makes them cheap to create and switch but easy to corrupt through shared data.

What a thread is

A thread is a single path of execution. A classic process has one thread. A multithreaded process has several, all running inside the same address space. Think of a Swiggy server process handling 200 customers: one process, many threads, each thread serving one request at a time.

The address space and page tableThread-local storage (ThreadLocal in Java)

This matches the JVM: all threads share the heap (objects), but each has its own stack for local variables. See JVM memory.

Benefits and problems of multithreading

Benefits

  • Responsiveness: a UI or server keeps working while one thread waits for I/O.
  • Resource sharing: no IPC needed for shared data.
  • Economy: cheaper to create and switch than processes.
  • Scalability: threads run in parallel on multiple cores.

Problems

  • Race conditions on shared data, needing locks (synchronization).
  • Deadlock and starvation (deadlock).
  • One buggy thread can crash or corrupt the entire process.
  • Hard to debug: bugs depend on timing.

User threads vs kernel threads

Kernel threads are known to and scheduled by the OS kernel; the kernel can run different threads of one process on different cores, and when one blocks the others keep running. User threads are managed by a library in user space; creating and switching them needs no system call and is very fast, but the kernel sees only one thread, so one blocking syscall can stall them all, and they cannot use several cores by themselves.

ModelMappingNote
Many-to-oneMany user threads → one kernel threadCheap, but no parallelism; a blocking call blocks all.
One-to-oneEach user thread → one kernel threadTrue parallelism, blocking is isolated; costs one kernel thread each. Linux and Windows use this.
Many-to-manyMany user threads → a smaller pool of kernel threadsFlexible, more complex to build.

Java threads and virtual threads

A normal Java Thread (a platform thread) is one-to-one with an OS kernel thread, so each one costs a kernel thread plus a stack (the default is typically about 1 MB of reserved stack space on 64-bit Linux, set with -Xss). A few thousand are fine; hundreds of thousands are not. Since Java 21 you can use virtual threads: lightweight threads scheduled by the JVM on top of a small pool of carrier OS threads, which is an M:N, many-to-many idea. When a virtual thread blocks on I/O, the JVM parks it and the carrier thread runs another virtual thread. They let a "one thread per request" server handle very many concurrent blocking requests. Thread creation, states, synchronized and pools are in Core Java · Module 6.

public class ThreadModels {
    public static void main(String[] args) throws InterruptedException {
        Thread platform = new Thread(() -> System.out.println("platform thread"));
        Thread virtual = Thread.ofVirtual().start(() -> System.out.println("virtual thread"));
        platform.start();
        platform.join();
        virtual.join();
    }
}

Rule: threads share memory, so shared mutable state needs protection

Every variable on the heap that more than one thread writes must be guarded by a lock, an atomic or a concurrent class. Local variables on a thread's own stack are safe by default.

Edge cases

  • After fork() in a multithreaded process, only the calling thread exists in the child; locks held by other threads stay locked forever. This is why fork in threaded programs is risky.
  • More threads than CPU cores does not mean more speed for CPU-bound work: the extra threads only add context switches.
  • A process ends when its last non-daemon thread ends (in Java) or when any thread calls exit() (in C).

Mistake: "threads are always faster than processes"

They are cheaper to create and share data easily, but a single lock that every thread fights for makes a threaded program slower than a single thread. Separate processes can be the better design when isolation matters (a plugin crashing must not kill the server).

Interview: "Process vs thread" (the most asked OS question)

  • Process: own address space and resources, heavy, isolated. Thread: execution unit inside a process, shares code, data, heap and files, owns stack and registers.
  • Thread creation and context switching are cheaper; communication is easier but unsafe without synchronization.
  • A thread crash can kill the process; a process crash does not affect other processes.
  • Close with a Java link: platform threads map 1:1 to OS threads; virtual threads (Java 21) are scheduled by the JVM.

Functional dependencies, attribute closure and finding candidate keys

A functional dependency X → Y says that X determines Y; the closure X+ is everything X determines, and a set is a key exactly when its closure is all attributes and no smaller subset works.

Functional dependency (FD)

A functional dependency X → Y holds in a relation when any two tuples that agree on X also agree on Y. In words: "X determines Y", "Y is functionally dependent on X". X is the determinant. An FD is a rule about the meaning of the data, not about the rows you happen to see — you can disprove an FD with one counter-example, but you can never prove it from a sample.

Example: R(A, B, C) with rows (1, x, p), (2, x, q), (3, y, p).

  • A → B and A → C hold (every A value is different).
  • B → A fails: rows 1 and 2 have B = x but A = 1 and 2.
  • C → B fails: rows 1 and 3 have C = p but B = x and y.

Kinds of FD:

  • Trivial: Y ⊆ X (for example AB → A). Always true.
  • Non-trivial: Y ⊄ X. Completely non-trivial: X ∩ Y = ∅.
  • Full dependency: Y depends on all of X, not on any proper subset of X.
  • Partial dependency: Y depends on a proper subset of a (candidate) key.
  • Transitive dependency: X → Y and Y → Z (with Y not a key and Y not determining X) so X → Z only through Y.

Armstrong's axioms

Armstrong's axioms let you derive every FD that must hold. They are sound (they derive only true FDs) and complete (they derive all of them).

  1. Reflexivity: if Y ⊆ X then X → Y.
  2. Augmentation: if X → Y then XZ → YZ for any Z.
  3. Transitivity: if X → Y and Y → Z then X → Z.

Derived rules you can use freely: union (X → Y and X → Z give X → YZ), decomposition (X → YZ gives X → Y and X → Z) and pseudo-transitivity (X → Y and WY → Z give WX → Z). Warning: you can split the right side (A → BC means A → B and A → C) but you cannot split the left side (AB → C does not mean A → C).

The set of all FDs implied by F is the closure of F, written F+. Two FD sets are equivalent if they have the same closure. A minimal cover is a smallest equivalent set: single attributes on every right side, no extra attribute on any left side, no redundant FD. It is the starting point of 3NF synthesis.

Attribute closure X+

The closure of an attribute set X under F is the set of all attributes that X functionally determines. Algorithm:

  1. Start with result = X.
  2. Look for any FD L → R in F where L ⊆ result. If R adds new attributes, add them to result.
  3. Repeat until nothing changes.

Uses: (1) X is a super key iff X+ contains all attributes of R; (2) X is a candidate key if, in addition, no proper subset of X is a super key; (3) the FD X → Y is implied by F iff Y ⊆ X+.

Worked example 1: closure

R(A, B, C, D, E), F = { A → B, BC → D, D → E, E → A }.

A+  : start {A}  -> A->B gives {A,B}.  BC->D needs C: no.   A+ = {A,B}
AC+ : {A,C} -> A->B: {A,B,C} -> BC->D: {A,B,C,D} -> D->E: {A,B,C,D,E}
      AC+ = {A,B,C,D,E} = all attributes, so AC is a super key
CD+ : {C,D} -> D->E: {C,D,E} -> E->A: {A,C,D,E} -> A->B: all
BC+ : {B,C} -> BC->D: {B,C,D} -> D->E: {B,C,D,E} -> E->A: all
CE+ : {C,E} -> E->A: {A,C,E} -> A->B: {A,B,C,E} -> BC->D: all

Finding all candidate keys

The shortcut that saves minutes in an exam or interview:

  1. List attributes that appear only on the left of FDs, or on neither side. They must be in every candidate key, because nothing can derive them.
  2. List attributes that appear only on the right. Something else always determines them, so they are in no candidate key. Leave them out of your starting set.
  3. Compute the closure of the must-have set. If it is all of R, that set is the only candidate key.
  4. Otherwise, add the remaining attributes one at a time (then in pairs...) to the must-have set and test closures; keep only the minimal successes.

Back to example 1: which attributes appear only on the left? C never appears on a right side, so C is in every key. C+ = {C}, not enough. Add one attribute at a time: AC, BC, CD, CE all give the full set (computed above). No single attribute besides C works, and each of those pairs is minimal. So the candidate keys are AC, BC, CD, CE. Every attribute is part of some key, so every attribute is prime and there are no non-prime attributes.

Worked example 2: a unique key

R(A, B, C, D, E), F = { AB → C, C → D, D → E }. A and B never appear on a right side, so both are in every key. Compute:

AB+ : {A,B} -> AB->C: {A,B,C} -> C->D: {A,B,C,D} -> D->E: {A,B,C,D,E}

AB determines everything and is already the must-have set, so AB is the only candidate key. Prime attributes: A, B. Non-prime: C, D, E.

Worked example 3: a cyclic set

R(A, B, C, D), F = { AB → C, C → D, D → A }. B never appears on a right side, so B is in every key; B+ = {B}. Try one more attribute:

AB+ : {A,B} -> AB->C: {A,B,C} -> C->D: {A,B,C,D}   all, key
BC+ : {B,C} -> C->D: {B,C,D} -> D->A: {A,B,C,D}     all, key
BD+ : {B,D} -> D->A: {A,B,D} -> AB->C: {A,B,C,D}    all, key

Candidate keys: AB, BC, BD. All of A, B, C, D are prime.

Mistake: stopping at the first key

A relation can have several candidate keys, and interviewers often ask "how many". After you find one, check the other attributes that sit in a cycle of FDs (C → D → A above): each can replace another.

Tip: check an FD quickly

To test whether F implies A → E, compute A+ and see whether E is in it. Never try to rebuild the derivation with the axioms by hand unless asked.

Interview angle

"Find the candidate keys of R(A,B,C,D) with F = ..." is a classic. A strong answer states the "must be in every key" trick, shows each closure on one line, lists all keys, then names the prime and non-prime attributes — because the next question is "which normal form is it in?"

Normalization: 1NF, 2NF, 3NF and BCNF on one running example

Normalization removes redundancy and update anomalies by splitting a table until every non-key fact depends on the key, the whole key and nothing but the key.

Why normalize: the anomalies

Normalization is the step-by-step process of decomposing tables using functional dependencies so that each fact is stored once. A badly designed table suffers from three anomalies:

  • Insertion anomaly — you cannot store a fact without storing an unrelated one (a new customer cannot be added until they place an order).
  • Update anomaly — one fact lives in many rows; a partial update leaves the data inconsistent (a customer moves city but only two of three rows change).
  • Deletion anomaly — deleting one fact deletes another (deleting the only order of a customer also deletes the customer).

The running example: orders

A shop stores everything in one sheet:

OrderIDCustIDCustNameCityItems
O1C1AshaPuneP1 Pen x2, P2 Book x1
O2C1AshaPuneP1 Pen x5
O3C2RaviDelhiP2 Book x3

First normal form (1NF)

Definition: a relation is in 1NF if every attribute holds only atomic (indivisible, single) values — no lists, no repeating groups, no nested tables — and each row can be identified. The Items column above breaks this. Flatten it, one row per order line:

OrderIDProdIDCustIDCustNameCity ProdNameQty
O1P1C1AshaPunePen2
O1P2C1AshaPuneBook1
O2P1C1AshaPunePen5
O3P2C2RaviDelhiBook3

Candidate key: (OrderID, ProdID). The functional dependencies:

OrderID            -> CustID
CustID             -> CustName, City
ProdID             -> ProdName
OrderID, ProdID    -> Qty

Prime attributes: OrderID, ProdID. Non-prime: CustID, CustName, City, ProdName, Qty.

Second normal form (2NF)

Definition: 1NF, and no partial dependency — every non-prime attribute depends on the whole of every candidate key, not on a part of it. Partial dependencies are possible only when a key is composite; if every candidate key is a single attribute, a 1NF table is already in 2NF.

Here OrderID → CustID and ProdID → ProdName are partial (a part of the key determines the attribute). Fix: move each partial dependency to its own table.

Product   (ProdID, ProdName)                      key: ProdID
Orders    (OrderID, CustID, CustName, City)        key: OrderID
OrderItem (OrderID, ProdID, Qty)                   key: (OrderID, ProdID)

The Pen name is now stored once. But Orders still repeats Asha's name and city for every order she places.

Third normal form (3NF)

Definition: 2NF, and no transitive dependency of a non-prime attribute on a key. Formal version: for every non-trivial FD X → A, either X is a super key, or A is a prime attribute.

In Orders: OrderID → CustID → CustName, City. The city depends on the key only through CustID. Fix:

Customer  (CustID, CustName, City)       key: CustID
Orders    (OrderID, CustID)              key: OrderID, FK CustID -> Customer
Product   (ProdID, ProdName)             key: ProdID
OrderItem (OrderID, ProdID, Qty)         key: (OrderID, ProdID)

Now Asha moving to Mumbai is a one-row update; a customer can exist without orders; deleting order O3 does not delete Ravi. This is the design you would put in PostgreSQL. A common memory line: every attribute depends on the key (1NF), the whole key (2NF) and nothing but the key (3NF), "so help me Codd" (BCNF).

Boyce–Codd normal form (BCNF)

Definition: for every non-trivial FD X → Y, X is a super key. BCNF is stricter than 3NF: 3NF lets X → A pass if A is prime; BCNF does not. The difference shows only when a relation has several overlapping composite candidate keys.

Example. A college allocates each student one instructor per course; each instructor teaches only one course (but a course can have several instructors):

StudentIDCourseIDInstructorID
S1DBMSI1
S2DBMSI1
S3DBMSI3
S1OSI2
 
StudentID, CourseID  -> InstructorID
InstructorID         -> CourseID
Candidate keys: (StudentID, CourseID) and (StudentID, InstructorID)
Prime attributes: StudentID, CourseID, InstructorID  (all of them)

3NF check: InstructorID → CourseID: InstructorID is not a super key, but CourseID is prime, so 3NF allows it. BCNF check: the left side InstructorID is not a super key, so it violates BCNF. The redundancy is real: the fact "I1 teaches DBMS" repeats for every student of I1. Decompose on the violating FD:

InstructorCourse (InstructorID, CourseID)     key: InstructorID
Allocation       (StudentID, InstructorID)    key: (StudentID, InstructorID)

The decomposition is lossless (the common attribute InstructorID is a key of InstructorCourse), but the dependency StudentID, CourseID → InstructorID is no longer visible in a single table. Nothing stops a student being allocated two instructors for DBMS (I1 and I3). That is the price of BCNF here (see the next article).

Summary table

Normal formRequiresRemoves

Hierarchy: BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF. Every BCNF relation is in 3NF, not the other way round.

How to find the highest normal form of a relation

  1. Find all candidate keys (closure method) and the prime attributes.
  2. For each FD X → Y check: is X a super key? If every FD passes, it is in BCNF.
  3. Else, for each failing FD, is Y prime (every attribute of Y)? If all are, it is in 3NF.
  4. Else, does any non-prime attribute depend on a part of a candidate key? If none, it is in 2NF; otherwise it is in 1NF.

Using this on the closure example from the previous article (keys AC, BC, CD, CE; FDs A → B, BC → D, D → E, E → A): A → B fails BCNF (A is not a super key) but B is prime. Every other FD also has a prime right side, so the relation is in 3NF but not BCNF. In example 3 of that article (FDs AB → C, C → D, D → A; keys AB, BC, BD): C → D has a non-super-key left side, D is prime; D → A the same; so again 3NF, not BCNF.

Mistake: calling every table "3NF" by looking at it

Normal forms are properties of the functional dependencies, not of how the rows look. Without the FDs (the business rules), you cannot decide the normal form.

In real projects

Most teams design to 3NF (a good ER model gives it for free), apply BCNF where a real overlap shows up, and rarely think about 4NF or 5NF. For practical design steps and examples see SQL · Module 4.

Interview angle

Expect "explain 1NF to BCNF with an example", "difference between 3NF and BCNF", "is every 3NF table BCNF?" (no) and "what are the anomalies?". A strong answer defines each form in one line, shows one table moving through all of them and gives the BCNF-but-lost-dependency trade-off.

Lossless join, dependency preservation, 4NF, 5NF and denormalization

A good decomposition must be lossless (joining the parts returns exactly the original rows) and ideally dependency-preserving; BCNF always gives the first but not always the second, and denormalization deliberately breaks normal forms for read speed.

Lossless-join decomposition

Splitting R into R1 and R2 is lossless (non-additive) if R1 ⋈ R2 = R — you get back exactly the original rows. A lossy decomposition returns extra, spurious rows and so loses information.

Test for two relations: the decomposition of R into R1, R2 is lossless iff R1 ∩ R2 → R1 or R1 ∩ R2 → R2 holds. In plain words: the shared attributes must be a key of at least one of the parts.

Lossy example. R(A, B, C) has rows (a1, b1, c1) and (a2, b1, c2). Split into R1(A, B) and R2(B, C):

R1 = {(a1,b1), (a2,b1)}      R2 = {(b1,c1), (b1,c2)}
R1 join R2 on B = (a1,b1,c1) (a1,b1,c2) (a2,b1,c1) (a2,b1,c2)    4 rows
Original R had 2 rows. Two spurious rows appeared.

The common attribute B is not a key of R1 or R2 (b1 repeats in both), so the split is lossy. Our orders example is safe: splitting Orders(OrderID, CustID, CustName, City) into Customer(CustID, CustName, City) and Orders(OrderID, CustID) shares CustID, which is the key of Customer.

Dependency preservation

A decomposition preserves dependencies if every FD of the original relation can be checked inside one of the parts (or follows from the FDs that can). Otherwise, enforcing an FD means joining tables on every insert, which is slow and often skipped.

  • Always possible with 3NF: the 3NF synthesis algorithm (build a table per FD of the minimal cover, add a key table if needed) gives a decomposition that is both lossless and dependency-preserving.
  • For BCNF: lossless is always possible, dependency preservation is not always. The student–course–instructor example from the previous article loses StudentID, CourseID → InstructorID.

The BCNF decomposition step: take a violating FD X → Y and split R into R1 = X ∪ Y and R2 = R − (Y − X). Repeat on each part until none violates. This is why textbooks say "BCNF: lossless, maybe not dependency preserving; 3NF: lossless and dependency preserving".

4NF and 5NF in one line each

Fourth normal form (4NF): BCNF, and no non-trivial multivalued dependency (MVD) X →→ Y unless X is a super key. An MVD arises when two independent multivalued facts sit in one table. Example: Person(Name, Phone, Hobby) where phones and hobbies are independent: Asha with two phones and two hobbies needs 2 × 2 = 4 rows. Split into PersonPhone(Name, Phone) and PersonHobby(Name, Hobby).

Fifth normal form (5NF, also PJNF): 4NF, and every join dependency is implied by the candidate keys — a table cannot be split into smaller tables that rejoin to it unless the keys already allow it. It matters for rare three-way relationships (supplier–part–project) and is almost never discussed in projects.

Denormalization

Denormalization deliberately adds redundancy to a normalized design to make reads faster: store customer_name inside orders, keep a precomputed order_total, or copy a count into a parent row.

Gains

  • Fewer joins, faster reads and reports
  • Simpler queries for dashboards
  • Natural fit for read-heavy systems and data warehouses

Costs

  • Redundant data can become inconsistent
  • Writes get slower and more complex (update every copy)
  • More storage; anomalies come back

Rule of thumb: normalize first, measure, then denormalize a specific hot path and keep the copy in sync with a trigger, a transaction, or a periodic job. Materialized views and caching are often better than editing the schema. In NoSQL (document stores) embedding is denormalization by design; see SQL · Module 6.

Interview angle

"What is a lossless join?" Give the key test and a spurious-rows example. "Is BCNF always dependency preserving?" No — and 3NF is. "When would you denormalize?" Read-heavy, proven slow joins, with a plan to keep copies consistent.

Relational algebra and its SQL equivalents

Relational algebra is the set of operators (select σ, project π, union, difference, product ×, rename ρ, join ⋈) that SQL queries are built on; each operator takes relations and returns a relation.

Why it matters

Relational algebra is the procedural query language behind SQL: it says how to build the answer step by step. The DBMS parses your SQL into an algebra tree, optimizes the tree (for example, pushes selections down before joins) and runs it. Relational calculus is the declarative cousin; SQL is closer to calculus in style. One subtle point: algebra works on sets (no duplicate rows), but SQL works on bags (duplicates allowed) — that is why SQL needs DISTINCT.

The operators

Sample tables: Employee(emp_id, name, salary, dept_id) and Department(dept_id, dname).

The five fundamental operators are selection, projection, union, set difference and Cartesian product (rename is a helper). Join, intersection and division can be written using them, so they are derived. Union, difference and intersection need union-compatible relations: the same number of attributes with matching domains.

Composing operators

Names of employees in the "Sales" department earning above 50000:

π name ( σ dname = 'Sales' AND salary > 50000 ( Employee ⋈ Department ) )
SELECT e.name
FROM   employee e
JOIN   department d ON d.dept_id = e.dept_id
WHERE  d.dname = 'Sales' AND e.salary > 50000;

Read the algebra from the inside out: join first, then select rows, then project the column. An optimizer will rewrite this to select Department on dname first, so the join sees fewer rows.

Division: "for all" queries

Find students enrolled in all courses. Algebra: π student_id, course_id (Enrollment) ÷ π course_id (Course). SQL by counting:

SELECT student_id
FROM   enrollment
GROUP  BY student_id
HAVING COUNT(DISTINCT course_id) = (SELECT COUNT(*) FROM course);

This works when every enrollment.course_id is a valid course.

Extended operators

Real SQL adds: aggregation (GROUP BY with SUM, AVG, COUNT, MIN, MAX, written 𝒢 in algebra), sorting (ORDER BY), assignment (←) for temporary results, and outer joins.

Edge case: NULL and duplicates

Pure algebra has no NULLs and no duplicate rows. SQL has both. UNION removes duplicates, UNION ALL keeps them, and a comparison with NULL is "unknown", which a WHERE clause treats as not true.

Interview angle

"Which operators are fundamental?" The five above. "Difference between σ and π?" Rows versus columns. "Natural join vs inner join?" Natural join matches on all same-named columns automatically. Also expect: "convert this SQL to relational algebra".

Object relationships, composition over inheritance, coupling and cohesion

Objects relate through association, aggregation, composition (has-a) and dependency (uses), or through inheritance (is-a); prefer composition to inheritance, aim for loose coupling and high cohesion.

Is-a vs has-a

Is-a is inheritance: a Car is a Vehicle. Has-a is containment: a Car has an Engine. A quick test: if "B is an A" sounds right in every situation, use extends; if "A has a B" sounds right, use a field.

The four relationships

RelationshipStrengthMeaningLifetime
Dependency (uses)WeakestOne class uses another temporarily, as a method parameter, local variable or return value Only during the call
AssociationWeakA general link: one object holds a reference to or knows about another (1:1, 1:N, M:N)Independent
AggregationMedium"Has-a" whole–part where the part can live without the wholePart survives the whole
CompositionStrong"Part-of" where the whole owns the partPart dies with the whole
 
import java.util.ArrayList;
import java.util.List;

// Dependency: EmailSender is only used inside a method
class OrderService {
    void confirm(Order order, EmailSender sender) {      // parameter = dependency
        sender.send(order.customerEmail(), "Order confirmed");
    }
}

// Aggregation: teachers exist independently of the department
class Department {
    private final List<Teacher> teachers = new ArrayList<>();
    void add(Teacher t) { teachers.add(t); }             // Teacher created elsewhere
}

// Composition: rooms are created and owned by the house
class House {
    private final List<Room> rooms = new ArrayList<>();
    House(int roomCount) {
        for (int i = 0; i < roomCount; i++) {
            rooms.add(new Room());                       // created inside; dies with House
        }
    }
}

// Association: a teacher knows her students, both live independently
class Teacher {
    private final List<Student> students = new ArrayList<>();
}

How to tell aggregation from composition in code: in composition the whole usually creates the parts, keeps them private, never hands out the reference for others to keep, and nothing else can hold them; in aggregation the parts are passed in from outside. In real life examples: order and order lines (composition), course and enrolled students (aggregation/association). The difference is about design intent and lifetime, so state your assumption when you answer.

Composition over inheritance

A well-known design rule: prefer composition to inheritance. Reuse behaviour by holding another object and delegating to it, rather than extending its class.

Inheritance for reuse only

class Stack<E> extends ArrayList<E> {
    void push(E e) { add(e); }
    E pop() { return remove(size() - 1); }
}
// Stack also exposes add(0, x), remove(i), ... that break stack rules

Composition: hide the parts you do not want

class Stack<E> {
    private final List<E> items = new ArrayList<>();
    void push(E e) { items.add(e); }
    E pop() { return items.remove(items.size() - 1); }
}

Why composition wins

  • Looser coupling: you depend on a small interface, not a whole parent class
  • Behaviour can change at runtime by swapping the held object (Strategy pattern)
  • No fragile-base-class surprises when the parent changes
  • Works around the single-inheritance limit

When inheritance is still right

  • A genuine, stable is-a relationship
  • You want polymorphism through a common supertype (then use an interface)
  • The parent is designed for extension (documented template methods)

Coupling

Coupling is how strongly one class depends on another. Tight coupling: class A creates new B(), knows B's internals, uses its fields, so a change in B breaks A. Loose coupling: A depends on an interface and receives its collaborator from outside, so B can be replaced. Aim for low coupling.

// Tight: OrderService is stuck with one gateway
class OrderService {
    private final UpiGateway gateway = new UpiGateway();
}

// Loose: any PaymentGateway can be supplied (constructor injection)
class OrderService {
    private final PaymentGateway gateway;
    OrderService(PaymentGateway gateway) { this.gateway = gateway; }
}

This is the idea behind dependency injection in Spring; see Spring Boot · Module 1.

Cohesion

Cohesion is how closely the members of one class belong together. High cohesion: a class does one well-defined job (InvoiceCalculator only calculates). Low cohesion: a "Utils" or "Manager" class with unrelated methods (calculate tax, send email, parse dates). Aim for high cohesion.

AspectCouplingCohesion
ConcernsRelationship between classesFocus inside one class

How to improveInterfaces, dependency injection, hide internals Split classes by responsibility

"Low coupling, high cohesion" is the shortest summary of good OOP design, and it connects directly to SOLID (next article).

Interview angle

"Aggregation vs composition?" — both are has-a; in composition the part cannot exist without the whole (house and rooms), in aggregation it can (department and teachers). "Why prefer composition to inheritance?" — looser coupling, runtime flexibility, no fragile base class. "What is tight coupling and how do you reduce it?" — interfaces plus dependency injection.

SOLID principles in one line each

SOLID is five design rules — single responsibility, open/closed, Liskov substitution, interface segregation, dependency inversion — that keep classes small, replaceable and easy to change.

SOLID was popularised by Robert C. Martin. These are guidelines, not laws. Each below has the one-line statement and a tiny Java example; the long version with refactoring walk-throughs is in System Design · Module 1.

S — Single Responsibility Principle (SRP)

A class should have only one reason to change. One class, one job.

Wrong: three jobs in one class

class Invoice {
    double total() { /* maths */ return 0; }
    void print()   { /* formatting and printing */ }
    void save()    { /* SQL insert */ }
}

Right: one job each

class Invoice { double total() { return 0; } }
class InvoicePrinter { void print(Invoice i) { /* ... */ } }
class InvoiceRepository { void save(Invoice i) { /* ... */ } }

O — Open/Closed Principle (OCP)

Software entities should be open for extension but closed for modification. Add new behaviour by adding code, not by editing tested code.

interface DiscountPolicy { double apply(double amount); }
class FestivalDiscount implements DiscountPolicy {
    public double apply(double amount) { return amount * 0.90; }
}
class Cart {
    double total(double amount, DiscountPolicy policy) { return policy.apply(amount); }
}
// A new discount = a new class. Cart never changes (no if/else chain on type).

L — Liskov Substitution Principle (LSP)

Objects of a subclass must be usable wherever the parent is expected, without breaking correctness. A subclass must keep the parent's promises.

Wrong: Penguin breaks Bird's promise

class Bird { void fly() { /* flies */ } }
class Penguin extends Bird {
    @Override void fly() {
        throw new UnsupportedOperationException();
    }
}

Right: model the real hierarchy

class Bird { }
class FlyingBird extends Bird { void fly() { } }
class Penguin extends Bird { }          // no fly() to break

Another classic: Square extends Rectangle fails because setting the width of a square silently changes its height, so code written for rectangles breaks.

I — Interface Segregation Principle (ISP)

Clients should not be forced to depend on methods they do not use. Prefer several small, focused interfaces to one fat one.

// Fat: a Robot must implement eat()
interface Worker { void work(); void eat(); }

// Segregated:
interface Workable { void work(); }
interface Feedable { void eat(); }
class Human implements Workable, Feedable { public void work() { } public void eat() { } }
class Robot implements Workable { public void work() { } }

D — Dependency Inversion Principle (DIP)

High-level modules should not depend on low-level modules; both should depend on abstractions. The business class owns an interface; the details implement it.

interface MessageSender { void send(String to, String text); }

class OrderService {                                  // high-level
    private final MessageSender sender;               // depends on abstraction
    OrderService(MessageSender sender) { this.sender = sender; }
    void confirm(String phone) { sender.send(phone, "Order confirmed"); }
}
class SmsSender implements MessageSender {            // low-level detail
    public void send(String to, String text) { /* call SMS provider */ }
}

Quick summary

LetterPrincipleSmell it fixes
SSingle Responsibility"God" classes that change for many reasons
OOpen/ClosedLong if/else or switch on type that grows with each feature
LLiskov SubstitutionSubclasses that throw "not supported" or break callers
IInterface SegregationFat interfaces with empty or throwing methods
DDependency InversionHigh-level code that calls new on concrete details

DIP vs DI vs IoC

DIP is the principle (depend on abstractions). Dependency injection is a technique that supplies the dependency from outside (constructor, setter). IoC (inversion of control) is the wider idea that a framework, not your code, controls object creation and flow; a Spring container does DI as one form of IoC.

Interview angle

Be ready to name all five, say each in one line, and give one example for at least two of them (SRP and DIP are easiest; LSP with Penguin or Square/Rectangle shows depth). Likely follow-up: "how do you follow OCP in Spring?" — program to interfaces, inject strategies, add beans instead of editing if/else.

Cloning, immutable classes, marker interfaces and final/finally/finalize

Object.clone() makes a shallow copy, immutable classes cannot change after creation, marker interfaces tag classes without methods, and final, finally and finalize are three unrelated things.

Object cloning: shallow vs deep copy

Cloning creates a copy of an object. Object.clone() is protected and native; a class must implement the marker interface Cloneable and override clone(), otherwise it throws CloneNotSupportedException.

  • Shallow copy: copies the object's fields as they are. Primitive fields are copied by value, but a reference field is copied as a reference, so the original and the clone share the same inner object.
  • Deep copy: also copies the objects that the fields refer to, recursively, so the two objects are fully independent.
class Address {
    String city;
    Address(String city) { this.city = city; }
}

class Person implements Cloneable {
    String name;
    Address address;
    Person(String name, Address address) { this.name = name; this.address = address; }

    @Override
    public Person clone() throws CloneNotSupportedException {
        return (Person) super.clone();               // shallow copy
    }
}

public class CloneDemo {
    public static void main(String[] args) throws CloneNotSupportedException {
        Person p1 = new Person("Asha", new Address("Pune"));
        Person p2 = p1.clone();
        p2.address.city = "Delhi";                  // changes the SHARED Address
        System.out.println(p1.address.city);
        System.out.println(p1 == p2);
    }
}
Delhi
false

The two Person objects are different, but both point to the same Address. For a deep copy, clone the inner object too, or better, use a copy constructor:

Person(Person other) {                           // copy constructor, deep
    this.name = other.name;                      // String is immutable: sharing is safe
    this.address = new Address(other.address.city);
}

Prefer a copy constructor or copy factory over clone()

clone() is widely considered flawed: it bypasses constructors, needs the marker interface, is shallow by default, and has awkward checked exceptions. A copy constructor (new Person(other)) or a static factory is clearer. Other ways to deep copy: serialize and deserialize, or copy via a library or mapper. Arrays have a public clone(), which is shallow for arrays of objects.

Immutable classes

An immutable object cannot change after it is created. String, the wrapper classes (Integer), BigDecimal and java.time classes are immutable. Recipe for your own class:

  1. Declare the class final (so nobody can subclass and add mutability).
  2. Make all fields private final.
  3. Provide no setters or other mutators.
  4. Initialise every field in the constructor.
  5. For mutable fields (a list, a Date) make a defensive copy on the way in and return a copy or an unmodifiable view on the way out.
import java.util.List;

public final class Course {
    private final String title;
    private final List<String> topics;

    public Course(String title, List<String> topics) {
        this.title = title;
        this.topics = List.copyOf(topics);        // defensive copy, unmodifiable
    }

    public String getTitle() { return title; }
    public List<String> getTopics() { return topics; }   // cannot be changed by callers
}

A record (Java 16+) gives you most of this in one line: record Course(String title, List<String> topics) { }. A record is only shallowly immutable: the list inside is still mutable unless you copy it in the compact constructor.

Why immutable

  • Thread-safe with no locking
  • Safe as HashMap keys and set elements (hash never changes)
  • Easy to reason about, cache and share
  • Used for value objects: money, dates, IDs

Costs

  • Every "change" allocates a new object
  • Building large objects step by step needs a builder

Marker interfaces

A marker (tag) interface has no methods; it only marks a class as having some capability that the JVM or a library checks with instanceof. Examples: Serializable (can be turned into bytes), Cloneable (allows Object.clone()), RandomAccess (fast index access, used by Collections algorithms). Today annotations usually do the same job (@Entity), but a marker interface still has one edge: it defines a type, so a method can demand Serializable in its signature and the compiler checks it.

Details: a final reference cannot be reassigned, but the object it points to can still change (final List can still receive add). A finally block does not run only if the JVM exits (System.exit) or crashes, or the thread is killed. Use try-with-resources instead of finalize for cleanup.

equals() and hashCode() contract

If you override equals, override hashCode too. The contract:

  • equals is reflexive, symmetric, transitive and consistent, and x.equals(null) is false.
  • If a.equals(b) then a.hashCode() == b.hashCode().
  • Unequal objects may share a hash code (a collision), but fewer collisions mean faster hash-based collections.
import java.util.Objects;

public final class Point {
    private final int x, y;
    public Point(int x, int y) { this.x = x; this.y = y; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point p)) return false;
        return x == p.x && y == p.y;
    }
    @Override public int hashCode() { return Objects.hash(x, y); }
}

If you forget hashCode, a HashSet may hold "duplicates" because equal points land in different buckets. Full treatment (with HashMap internals) is in Core Java · Module 7.

More frequent OOP questions: main, static, chaining, singleton, inner classes

Why main is static, why static and private methods are hidden rather than overridden, how constructors chain, how a singleton is built safely, and the four kinds of inner class.

Why is main static?

The JVM must call public static void main(String[] args) to start the program before any object exists. If main were an instance method, the JVM would first have to create an object of your class and decide which constructor to call. static means "callable on the class itself". public lets the JVM reach it from outside, void because the JVM uses no return value (use System.exit(code) for an exit code), and String[] args carries the command-line arguments.

Newer Java

Recent Java releases simplify this for beginners with "instance main" methods and compact source files (finalized in Java 25 by JEP 512). The classic public static void main still works everywhere and is what interviews expect.

Can we override static and private methods?

  • Static methods: no — they are hidden. A subclass can declare a static method with the same signature, but the call is resolved by the reference type at compile time (Parent p = new Child(); p.greet(); runs the parent's). This is method hiding. Using @Override on it is a compile error.
  • Private methods: no. They are not visible to the subclass, so a same-named method in the child is a brand-new, unrelated method.
  • Final methods: no (compile error).

Static vs dynamic dispatch: Java chooses which overload to call by the declared types of the arguments (static dispatch), and chooses which override to run by the actual class of the receiver object (dynamic dispatch). So Java is single-dispatch: only the receiver is looked up at runtime. This explains question 5 in the polymorphism article. Static methods, fields and private methods are always resolved statically.

Constructor chaining

Constructor chaining is calling one constructor from another, to avoid repeating initialisation code. Within a class use this(...); to the parent use super(...). Up to Java 24 the call must be the first statement (Java 25 relaxes this, see the rules below).

class Employee {
    private final String name;
    private final double salary;
    private final String dept;

    Employee(String name, double salary, String dept) {   // the "master" constructor
        this.name = name;
        this.salary = salary;
        this.dept = dept;
    }
    Employee(String name, double salary) { this(name, salary, "General"); }
    Employee(String name)                 { this(name, 0); }
}

class Manager extends Employee {
    Manager(String name) { super(name, 90000, "Management"); }
}

Rules: you cannot call both this(...) and super(...) in one constructor; recursive chains (A() calls B(), B() calls A()) are a compile error; instance initialiser blocks and field initialisers run after super(...) and before the rest of the constructor body. Java 25 finalized flexible constructor bodies (JEP 513): statements that do not use the object being built, such as argument validation, may now come before this(...) or super(...). Most codebases and interviews still assume the classic "first statement" rule, so know both.

Singleton class

A singleton has exactly one instance, accessible globally. Recipe: private constructor, a private static instance, a public static accessor. Thread-safe, lazy version using the initialization-on-demand holder idiom (the JVM guarantees class initialisation is thread-safe):

public final class AppConfig {
    private AppConfig() { }                                   // nobody else can call new

    private static class Holder {
        static final AppConfig INSTANCE = new AppConfig();    // created when first used
    }

    public static AppConfig getInstance() { return Holder.INSTANCE; }
}

// Simplest and safest in Java: an enum
enum Registry {
    INSTANCE;
    void register(String name) { /* ... */ }
}
  • Eager (static final field): simple, created at class load.
  • Double-checked locking needs a volatile field; otherwise a thread may see a half-built object.
  • Singletons can be broken by reflection (calling the private constructor), serialization (a new object on deserialize) and clone(). An enum singleton resists all three.
  • In Spring, beans are singleton-scoped by default, so you rarely write this by hand.

Inner classes

A class declared inside another class is a nested class.

KindDeclaredNeeds outer instance?Typical use
Static nestedstatic class inside a classNo Helper tied to the outer class (Map.Entry, builders)
Member inner (non-static)Inside a class, no static Yes; can use outer's fields, even private onesIterators, event handlers
LocalInside a methodYes, in an instance method Small helper used once
AnonymousUnnamed, created with new Type() { ... } Yes, in an instance methodOne-off implementation (often replaced by a lambda)
 
public class Outer {
    private int value = 10;

    class Inner {                                  // member inner class
        int doubled() { return value * 2; }        // can read Outer's private field
    }
    static class Nested {                          // static nested class
        String hello() { return "hi"; }
    }

    public static void main(String[] args) {
        Outer outer = new Outer();
        Outer.Inner in = outer.new Inner();        // needs an Outer object
        Outer.Nested n = new Outer.Nested();       // does not
        System.out.println(in.doubled() + " " + n.hello());

        Runnable r = new Runnable() {              // anonymous class
            @Override public void run() { System.out.println("run"); }
        };
        r.run();
    }
}

run

Local and anonymous classes (and lambdas) can use only final or effectively final local variables. A member inner class holds a hidden reference to its outer object, which can keep the outer object alive and cause a memory leak; use a static nested class when you do not need the outer instance.

Other quick facts

  • Object class methods: toString, equals, hashCode, getClass, clone, finalize, wait, notify, notifyAll.
  • Can a class be both abstract and final? No: contradictory.
  • Can we create an object of an abstract class? Not directly; an anonymous subclass can implement it (new Bird("x") { String sound() { return "tweet"; } }).
  • Can the constructor be inherited? No, but a child constructor must call one.
  • Method overloading with null: the most specific type wins, or the call is ambiguous.

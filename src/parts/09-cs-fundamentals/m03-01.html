DBMS theory is the part of databases that interviewers ask without a laptop in front of you: keys, normalization, ACID, transactions, isolation levels and indexing. You can write SQL, but the interview wants the textbook words behind it — what a candidate key is, why a table is in 3NF but not BCNF, why two schedules are or are not serializable, and why a database uses a B+ tree.

This module is revision-style. The practical side lives on the SQL page: schema design in SQL · Module 4, internals (indexes, transactions, locking) in SQL · Module 5, and NoSQL in SQL · Module 6. Here you get crisp definitions, worked theory examples that you can redo on paper, and the most-asked questions.

DBMS vs file system, data models and SQL sub-languages

A DBMS is software that stores, protects and serves shared data through a query language, solving the redundancy, inconsistency, concurrency and security problems of plain files.

Database, DBMS and database system

A database is an organised collection of related data. A DBMS (Database Management System) is the software that creates, stores, queries and protects that data — PostgreSQL, MySQL, Oracle, SQL Server, MongoDB. A database system is the whole thing: the data, the DBMS and the applications that use them. Your Spring Boot app talks to a DBMS; it never reads the data files itself.

The problems of a file-based system

Imagine a college that keeps students in students.csv, fees in fees.csv and results in results.csv, each read by a different program. Soon you hit these problems:

Problem in filesWhat it meansHow a DBMS solves it
Data redundancy and inconsistencyThe same address is stored in three files; one is updated, two are notOne copy of each fact; normalization; constraints
Difficult data accessEvery new question needs a new program A declarative query language (SQL)
Data isolationDifferent formats in different files One schema, one format
Integrity problemsNothing stops a negative fee or a result for a missing studentIntegrity constraints (NOT NULL, CHECK, FOREIGN KEY)
Atomicity problemsThe program crashes after debiting one account but before crediting the otherTransactions with rollback and recovery
Concurrent access anomaliesTwo users update the same balance together; one update is lostLocking / MVCC and isolation levels
Security problemsAnyone who can open the file sees everything Users, roles, GRANT / REVOKE

A DBMS also gives data independence (next article), backup and recovery, and tuned storage with indexes. The price: more cost and complexity, and a DBMS can be overkill for a tiny single-user tool.

Data models

A data model is a way to describe the structure of data, the operations on it and its constraints. One line each:

  • Relational model — data in tables (relations) of rows and columns; the basis of SQL databases.
  • ER (entity–relationship) model — a design-time picture of entities and their relationships; converted to tables afterwards.
  • Document model — self-contained JSON-like documents (MongoDB).
  • Key-value model — a value looked up by a key (Redis).
  • Graph model — nodes and edges, built for relationships (Neo4j).
  • Hierarchical and network models — older tree and graph-like models; now of historical interest.

Schema vs instance

The schema is the design: table names, columns, types and constraints. It changes rarely. The instance (or state, snapshot) is the data stored at one moment. It changes with every insert, update and delete. Analogy: the schema is the empty form; the instance is all the forms filled in so far.

SQL sub-languages

GroupFull nameCommandsPurpose
DDLData Definition LanguageCREATE, ALTER, DROP, TRUNCATEDefine and change the schema

Some books put SELECT in its own group, DQL. TRUNCATE is DDL in most books because it removes all rows by deallocating storage and is usually not rolled back the way DML is (in PostgreSQL it can be rolled back inside a transaction; in MySQL it cannot).

Database users

  • DBA (database administrator) — installs, tunes, backs up, secures.
  • Database designer — decides tables and constraints.
  • Application programmer — you; writes code that uses the DBMS.
  • End user — uses the application (casual or naive users).

Interview angle: "Why DBMS over a file system?"

Name five problems with examples — redundancy, inconsistency, no concurrency control, no atomicity, weak security — and say how a DBMS fixes each. Add data independence and the query language to finish.

Three-schema architecture and data independence

The three-schema architecture separates what users see (external), what the database logically contains (conceptual) and how it is stored (internal), so each level can change without breaking the one above.

The three levels

  • External schema (view level): many of them, one per user group. The accounts team sees fees; the library sees books issued. SQL views implement this level.
  • Conceptual schema (logical level): exactly one. It describes entities, attributes, relationships and constraints for the whole organisation, hiding storage details. Your CREATE TABLE statements are the conceptual schema.
  • Internal schema (physical level): how data is stored — file organisation, indexes, page layout, compression.

The DBMS keeps mappings between the levels: external ↔ conceptual and conceptual ↔ internal. A query on a view is translated down through these mappings.

Data independence

Data independence is the ability to change the schema at one level without changing the schema at the next higher level.

TypeYou changeWithout changingExample
Physical data independenceInternal schemaConceptual schema and applicationsAdd an index, move a table to another disk, change page size — queries stay the same
Logical data independenceConceptual schemaExternal schemas and applicationsAdd a column to a table; existing views and programs keep working

Physical independence is easy to get and every real DBMS has it. Logical independence is harder: removing or renaming a column that a view uses will still break that view. Adding columns is the safe case.

Real-life link

When you run CREATE INDEX on a production table, no query text changes — only speed changes. That is physical data independence in action. When you create a database view for the reporting team, you are using the external level.

Two-tier and three-tier architecture (application view)

Do not confuse this with the application architecture. In a two-tier setup, the client application talks directly to the DBMS server. In a three-tier setup (browser → Spring Boot server → database), the middle tier holds business logic and the client never touches the database. Modern web apps are three-tier.

Interview angle

"What is data independence?" Give the definition, then both types with one example each. "Which level do views belong to?" The external level. "Which is the one level that exists only once?" The conceptual level.

The ER model: entities, attributes, relationships

An ER diagram models a system as entities with attributes connected by relationships, with cardinality and participation constraints, before anyone writes a table.

Building blocks

Entity
A real-world thing that can be told apart from others: a student, a course, an order.
Entity set
A collection of entities of the same type (all students). It becomes one table; each entity becomes one row.
Attribute
A property of an entity (name, email). Each attribute has a domain.
Relationship
An association between entities: a student enrolls in a course.
Relationship set
A collection of relationships of the same type.
Degree of a relationship
The number of entity sets involved: unary (recursive, employee manages employee), binary (most common), ternary.

Types of attributes

Cardinality and participation

Cardinality ratio says how many entities on one side can relate to how many on the other:

  • One-to-one (1:1) — one person has one passport.
  • One-to-many (1:N) — one department has many employees; each employee has one department.
  • Many-to-one (N:1) — the same relationship read from the employee side.
  • Many-to-many (M:N) — students and courses.

Participation constraint says whether every entity must take part. Total participation (double line): every entity participates — every order must belong to a customer. Partial participation (single line): some may not — a customer may have no orders yet.

Strong and weak entities

A strong entity has its own key. A weak entity has no key of its own; it exists only in relation to an owner (identifying) entity and is identified by the owner's key plus its own partial key (discriminator). The link is an identifying relationship, and the weak entity has total participation in it. Example: a Dependent (child of an employee) has only a first name; two employees can both have a child named "Riya", so the key is (employee id, dependent name).

Generalization and specialization

Specialization is the top-down step: split an entity into more specific sub-entities (Employee → Manager, Engineer). Generalization is bottom-up: combine similar entities into a higher-level one (Car and Truck → Vehicle). Subclasses inherit the attributes and relationships of the superclass (an "is-a" relationship). Constraints: the sub-classes can be disjoint or overlapping, and the specialization can be total (every employee is a manager or an engineer) or partial. Aggregation in ER means treating a relationship as an entity so it can take part in another relationship.

Mistake: foreign keys inside the ER diagram

An ER diagram shows relationships, not foreign-key columns. Foreign keys appear only when you convert the diagram to tables (next article). Also, do not store a derived attribute such as age; compute it.

Interview angle

"Entity vs attribute?", "What is a weak entity? Give an example", "How do you represent an M:N relationship?" and "Total vs partial participation" are the usual questions. Always attach a concrete example.

Converting an ER diagram to tables

Each entity becomes a table; a 1:N relationship becomes a foreign key on the N side; an M:N relationship becomes its own junction table; weak entities and multivalued attributes get tables that carry the owner's key.

The rules

  1. Strong entity → a table. Simple attributes become columns; the key attribute becomes the primary key. A composite attribute is flattened into its simple parts (street, city, pincode). A derived attribute is not stored.
  2. Weak entity → a table with its own attributes plus the owner's primary key as a foreign key. The primary key is (owner key, partial key). Use ON DELETE CASCADE because a dependent cannot outlive its owner.
  3. Multivalued attribute → a separate table with the entity's key (foreign key) and one column for the value. Primary key = both columns.
  4. 1:1 relationship → put the foreign key on either side, ideally on the side with total participation; make it UNIQUE. If both sides are total, you may merge into one table.
  5. 1:N relationship → put the foreign key (the key of the "one" side) in the table on the "many" side. No new table.
  6. M:N relationship → a new junction (associative) table containing both keys as foreign keys, plus any attributes of the relationship. Primary key = both keys together.
  7. Ternary relationship → a junction table with three foreign keys.
  8. Unary (recursive) relationship → a foreign key to the same table (manager_id in employee); M:N recursive needs a junction table.
  9. Generalization → one of three layouts: one table for the whole hierarchy with a type column; one table for the superclass plus one per subclass (subclass key = foreign key to superclass); or one table per concrete class with the inherited columns repeated. See SQL · Module 4 for the trade-offs.

Worked example

The diagram from the previous article has DEPARTMENT, EMPLOYEE, PROJECT, DEPENDENT, a 1:N relationship (employs), an M:N relationship (works on, with an attribute hours), and a weak entity.

CREATE TABLE department (
    dept_id   INT PRIMARY KEY,
    dept_name VARCHAR(50) NOT NULL
);

CREATE TABLE employee (                -- 1:N: FK on the many side
    emp_id   INT PRIMARY KEY,
    name     VARCHAR(80) NOT NULL,
    dept_id  INT NOT NULL REFERENCES department(dept_id)
);

CREATE TABLE project (
    proj_id  INT PRIMARY KEY,
    title    VARCHAR(80) NOT NULL
);

CREATE TABLE works_on (                -- M:N: junction table
    emp_id   INT REFERENCES employee(emp_id),
    proj_id  INT REFERENCES project(proj_id),
    hours    INT,                      -- attribute of the relationship
    PRIMARY KEY (emp_id, proj_id)
);

CREATE TABLE dependent (               -- weak entity
    emp_id   INT REFERENCES employee(emp_id) ON DELETE CASCADE,
    dep_name VARCHAR(50),              -- partial key
    birth    DATE,
    PRIMARY KEY (emp_id, dep_name)
);

CREATE TABLE employee_phone (          -- multivalued attribute
    emp_id   INT REFERENCES employee(emp_id),
    phone    VARCHAR(15),
    PRIMARY KEY (emp_id, phone)
);

Count: five entity-like tables plus one junction table = six tables from three entity sets, one weak entity, one multivalued attribute and one M:N relationship.

Tip: a quick way to remember where the foreign key goes

Ask "which side has one of the other?" Each employee has one department, so the employee row stores the department id. A department has many employees, so you cannot store them in one column. M:N: neither side can hold the key, so use a third table.

Interview angle

"How many tables for an M:N relationship between A and B?" Three: A, B and the junction. "Where does the foreign key go in 1:N?" On the N side. "How is a weak entity converted?" Owner's key plus the partial key form the primary key.

Relational model: terms and integrity constraints

The relational model stores data as relations (tables) of tuples (rows) over attributes (columns), and protects it with domain, entity and referential integrity constraints.

Properties of a relation in theory: tuples are unordered, attributes are unordered, values are atomic, no two tuples are identical (a relation is a set). SQL tables relax the last one: without a primary key a table can hold duplicate rows. Do not confuse cardinality of a relation (number of rows) with cardinality of a relationship (1:1, 1:N, M:N).

Integrity constraints

An integrity constraint is a rule that every valid database state must satisfy. The DBMS rejects any change that breaks it.

Domain constraint
Each value must belong to its attribute's domain: right data type, range, format. Implemented with types, CHECK, NOT NULL, DEFAULT.
Key constraint
No two tuples may have the same value for a key (UNIQUE).
Entity integrity
The primary key of a relation can never be NULL (and must be unique), because NULL means "unknown" and a row must be identifiable.
Referential integrity
A foreign key value must either be NULL or match an existing primary-key value in the referenced table. No orphan rows.
CREATE TABLE student (
    roll_no  INT PRIMARY KEY,                       -- entity integrity
    name     VARCHAR(80) NOT NULL,
    email    VARCHAR(120) UNIQUE,                   -- key constraint
    marks    INT CHECK (marks BETWEEN 0 AND 100),   -- domain constraint
    dept_id  VARCHAR(5) REFERENCES department(dept_id) -- referential integrity
);

What happens on delete or update of a referenced row

If you delete a department that students still reference, the DBMS must choose an action. These are the referential actions you declare on the foreign key:

ActionEffect
RESTRICT / NO ACTIONReject the delete or update (the default)
CASCADEDelete or update the child rows too
SET NULLSet the child foreign key to NULL
SET DEFAULTSet the child foreign key to its default value

Two practical differences: NO ACTION checks at the end of the statement (and can be deferred in PostgreSQL), while RESTRICT checks immediately. MySQL InnoDB treats the two the same.

Edge cases

  • A foreign key may be NULL (unless declared NOT NULL) — NULL means "no reference". A primary key may not.
  • A foreign key may reference a UNIQUE column, not only a primary key.
  • A foreign key may reference its own table (employee → manager).
  • Foreign key columns do not need to have the same name as the referenced column, only a compatible type.

Interview angle

"What is referential integrity?" Foreign key values must exist in the parent table. "Can a foreign key be NULL?" Yes. "Difference between degree and cardinality?" Columns vs rows. "Which integrity constraint does a primary key enforce?" Entity integrity (plus uniqueness).

Keys: super, candidate, primary, alternate, foreign, composite, surrogate

A key is a set of attributes that identifies rows; every candidate key is a minimal super key, one candidate is chosen as the primary key, and a foreign key links one table to another.

One table, every key

We use this table for all the definitions:

student_idroll_noemailnamedept_id
1CS101asha@x.inAshaCS
2CS102ravi@x.inRaviCS
3EC101meera@x.inMeeraEC

Assume roll number and email are each unique, but names and departments repeat in general. student_id is a system-generated number.

Super key
Any set of attributes that uniquely identifies every row. It may contain extra attributes. {roll_no}, {roll_no, name}, {email, dept_id} and {student_id, name, email} are all super keys. If a table has n attributes and exactly one candidate key of a single attribute, it has 2n−1 super keys.
Candidate key
A minimal super key: remove any attribute and it stops being unique. Here: {student_id}, {roll_no}, {email}. A table can have several. {roll_no, name} is not a candidate key, because roll_no alone already works.
Primary key
The one candidate key chosen to identify rows. Not NULL, unique, one per table. Say we choose student_id.
Alternate key
The candidate keys that were not chosen: roll_no and email. Declare them UNIQUE NOT NULL.
Unique key
A column (or set) with a UNIQUE constraint. It may allow NULL (most databases allow several NULLs; SQL Server allows only one). A table can have many unique keys, but one primary key.
Foreign key
An attribute (set) in one table that references the primary key (or a unique key) of another table: dept_id references department(dept_id). It enforces referential integrity and can repeat and be NULL.
Composite key
A key made of two or more attributes. In enrollment(student_id, course_id, grade), the pair (student_id, course_id) is the key; neither column alone is unique.
Surrogate key
An artificial key with no business meaning, such as an auto-increment number or UUID (student_id here). Opposite of a natural key (roll number, email, PAN) that has real-world meaning.
Secondary key
An attribute (set) used for look-up, not necessarily unique — usually one with an index (for example name).

Surrogate vs natural key

Surrogate key

  • Never changes, so foreign keys stay valid
  • Small and fast to join (one integer)
  • Hides business rules that may change (an email can change)

Natural key

  • Meaningful, and no extra column
  • May change or be reused (phone, email)
  • Often long or composite, so foreign keys get bulky
  • Still needs a UNIQUE constraint if you also add a surrogate

Professional practice: use a surrogate primary key and put a UNIQUE constraint on the natural key. For ID choices (identity vs UUID) see SQL · Module 4.

Mistake: "primary key = unique + not null, so a unique column is a primary key"

A table has only one primary key, and a unique column that allows NULL is not a primary key. Also, a candidate key must be minimal: a set with a redundant attribute is only a super key.

Interview angle

"Super key vs candidate key" — minimal vs not. "Primary key vs unique key" — one vs many, NULL rules. "Can a table have no primary key?" SQL allows it, but the relational model does not, and you lose a unique row identity. "Can a primary key be a foreign key?" Yes (a 1:1 sub-table, or a junction table's columns).

Class, object, constructor, this, super and access modifiers

A class is a blueprint that defines fields and methods; an object is one instance of it created with new; constructors initialise objects, and access modifiers decide who can see each member.

OOP is a style, not a magic wand: a long program in either style can be bad. OOP helps when many things share behaviour and the code keeps changing. Note that Java is not purely object-oriented: it has primitive types (int, boolean) that are not objects.

Class and object: the crisp definitions

Class
A blueprint or template that defines the state (fields) and behaviour (methods) common to a kind of object. It is a logical definition; it takes no per-object memory until you create objects. Example: a Student class.
Object
An instance of a class: a real entity with its own values for the fields (state), the class's methods (behaviour) and a unique identity. Example: the student Asha, roll number 101. Objects live on the heap; a reference variable points to them.
ClassObject

public class Student {
    private final int rollNo;       // state
    private String name;

    public Student(int rollNo, String name) {   // constructor
        this.rollNo = rollNo;
        this.name = name;
    }

    public String describe() {                  // behaviour
        return rollNo + " - " + name;
    }

    public static void main(String[] args) {
        Student a = new Student(101, "Asha");   // object 1
        Student b = new Student(102, "Ravi");   // object 2
        System.out.println(a.describe());
        System.out.println(b.describe());
    }
}

Four ways to create an object: new, clone(), deserialization and reflection (Constructor.newInstance()). A reference is not an object: Student s; creates no object, and Student t = a; makes a second reference to the same object.

Constructors

A constructor is a special block that has the same name as the class and no return type. The JVM calls it automatically during new to initialise the new object.

Constructor rules

  • Same name as the class; no return type (not even void).
  • Can be overloaded. Cannot be static, final, abstract or synchronized, and cannot be inherited or overridden.
  • Can be private (singleton, utility class, factory methods).
  • If you write any constructor, the compiler does not add the default one. A class with only Student(int, String) cannot be created with new Student().
  • The first statement is this(...) or super(...); if you write neither, the compiler inserts super(). If the parent has no no-argument constructor, you get a compile error.

Constructor vs method: a constructor has no return type, is called by new and runs once per object; a method has a return type, is called on an object and can run many times.

Destructor: why Java has none

In C++ a destructor runs when an object dies, to free memory and resources, and the programmer must manage that. Java has a garbage collector that frees unreachable objects automatically, so there is no destructor. The old finalize() hook was unreliable (no guarantee when or whether it runs), is deprecated, and has been marked for removal since Java 18. For non-memory resources (files, sockets, connections) implement AutoCloseable and use try-with-resources.

The four pillars: encapsulation, abstraction, inheritance, polymorphism

Encapsulation hides data behind methods, abstraction shows only what matters, inheritance reuses a parent's features in a child, and polymorphism lets one call behave differently depending on the actual object.

The four pillars are the principles that define object-oriented design. For each: a textbook definition, what it means in plain words, an analogy, a short Java example, and a 20-second answer you can say aloud. The Java language details are in Core Java · Module 2.

1. Encapsulation

Definition: encapsulation is the bundling of data (fields) and the methods that operate on it into one unit (a class), and restricting direct access to the data so that it can be changed only through the class's own methods.

Plain words: make fields private, give controlled access through public methods, and let the class protect its own rules (no negative balance). The outside world sees what you can do, not how it is stored.

Analogy: a medicine capsule — the contents are sealed inside one unit; you take it as a whole. Or an ATM: you press buttons, you never touch the cash vault.

public class BankAccount {
    private long balanceInPaise;                 // hidden state

    public void deposit(long paise) {
        if (paise <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
        balanceInPaise += paise;
    }

    public void withdraw(long paise) {
        if (paise > balanceInPaise) {
            throw new IllegalStateException("Insufficient balance");
        }
        balanceInPaise -= paise;
    }

    public long getBalanceInPaise() {            // read-only access
        return balanceInPaise;
    }
}

Nobody can set the balance to -500 directly. If tomorrow you store the balance as BigDecimal, callers do not change.

  • Benefits: data hiding and security, validation in one place, freedom to change internals, easier testing.
  • How in Java: private fields, public getters and setters (only where needed), package-private or private helpers. A class with private fields and getters/setters is also called a JavaBean.
  • Common trap: generating a getter and setter for every field with no validation is only pretending to encapsulate; exposing a mutable list through a getter leaks the internals. Return a copy or an unmodifiable view.

20-second answer: encapsulation

"Encapsulation means keeping data and the code that works on it together in one class and hiding the data with private fields. Other code can use it only through public methods, so the class can validate input and change its internals safely. For example, a BankAccount keeps the balance private and exposes deposit and withdraw with checks."

2. Abstraction

Definition: abstraction is the process of hiding implementation details and showing only the essential features of an object or operation, focusing on what it does rather than how.

Plain words: define a simple contract (an interface or abstract class) and hide the messy details behind it. Callers depend on the contract, so implementations can change.

Analogy: driving a car: you use the steering wheel, pedals and gear; you do not need to know how fuel injection works. A TV remote: buttons, not circuits.

interface PaymentMethod {
    void pay(long paise);                 // WHAT: the contract
}

class UpiPayment implements PaymentMethod {
    public void pay(long paise) {         // HOW: hidden from the caller
        System.out.println("Paid " + paise + " paise via UPI");
    }
}

class CardPayment implements PaymentMethod {
    public void pay(long paise) {
        System.out.println("Paid " + paise + " paise by card");
    }
}

class Checkout {
    void complete(PaymentMethod method, long paise) {
        method.pay(paise);                // works with any implementation
    }
}
  • How in Java: interfaces (100% abstraction in the classic view) and abstract classes (partial abstraction, 0–100%).
  • Benefits: less complexity for the user, loose coupling, easier to swap implementations and to test with fakes.

20-second answer: abstraction

"Abstraction means showing only what an object does and hiding how it does it. In Java I define it with an interface or an abstract class. For example, Checkout calls pay() on a PaymentMethod and does not care whether it is UPI or card, so I can add a new payment type without changing Checkout."

3. Inheritance

Definition: inheritance is a mechanism by which one class (the subclass, child or derived class) acquires the fields and methods of another (the superclass, parent or base class), modelling an is-a relationship.

Plain words: put common code in a parent once; children get it for free and add or change what they need. In Java you write extends.

Analogy: a child inherits traits from parents and adds their own; a "Car" is a "Vehicle" and gets wheels and start() automatically.

class Vehicle {
    protected String brand;
    Vehicle(String brand) { this.brand = brand; }
    void start() { System.out.println(brand + " starting"); }
}

class Car extends Vehicle {
    Car(String brand) { super(brand); }          // call the parent constructor
    void openBoot() { System.out.println(brand + " boot open"); }
}

public class Demo {
    public static void main(String[] args) {
        Car car = new Car("Swift");
        car.start();       // inherited
        car.openBoot();    // own
    }
}
Swift starting
Swift boot open
  • Benefits: code reuse, a natural hierarchy, and it enables runtime polymorphism.
  • Costs: tight coupling to the parent (the "fragile base class" problem); a change in the parent can break all children. Prefer composition when the relationship is not truly is-a (see the relationships article).
  • Java facts: single inheritance for classes (one extends), every class implicitly extends Object, private members are not inherited, constructors are not inherited, final classes cannot be extended.

20-second answer: inheritance

"Inheritance lets a class reuse and extend another class using extends, modelling an is-a relationship. The child gets the parent's non-private fields and methods and can override methods. Java supports single inheritance for classes and multiple inheritance of type through interfaces. I use it when there is a real is-a relationship and otherwise prefer composition."

4. Polymorphism

Definition: polymorphism ("many forms") is the ability of one interface, method name or reference to take many forms: the same call produces different behaviour depending on the actual object or arguments.

Plain words: a parent-type variable can hold any child object, and calling an overridden method runs the child's version. Two kinds: compile-time (method overloading) and runtime (method overriding).

Analogy: the word "play" — you play cricket, play the guitar, play a video: one verb, different action by context. A single "pay" button on Swiggy: UPI, card or wallet decides what happens.

abstract class Shape {
    abstract double area();
}

class Circle extends Shape {
    private final double r;
    Circle(double r) { this.r = r; }
    double area() { return Math.PI * r * r; }
}

class Rectangle extends Shape {
    private final double w, h;
    Rectangle(double w, double h) { this.w = w; this.h = h; }
    double area() { return w * h; }
}

public class Shapes {
    public static void main(String[] args) {
        Shape[] shapes = { new Circle(1), new Rectangle(2, 3) };
        for (Shape s : shapes) {
            System.out.println(s.area());    // which area()? decided at runtime
        }
    }
}

The loop code never changes when you add Triangle. That is the practical power of polymorphism: new behaviour without editing old code. The next articles cover overloading vs overriding and binding in detail.

20-second answer: polymorphism

"Polymorphism means one name, many behaviours. At compile time it is method overloading: same name, different parameters. At runtime it is method overriding: a parent reference points to a child object and the child's method runs. For example, a Shape reference calling area() runs Circle's or Rectangle's version depending on the object."

Mistake: saying "polymorphism is method overloading" only

Overloading is one kind (compile-time). Interviewers want the runtime kind, with a parent reference and a child object, as the main answer. Likewise, do not claim that Java supports "multiple inheritance" without adding "only through interfaces".

Abstraction vs encapsulation

Abstraction is a design-level idea of exposing only essential behaviour (what), while encapsulation is an implementation-level technique of hiding data inside a class (how it is protected).

Why they are confused

Both involve "hiding", so they sound the same. The difference is what is hidden and why. Abstraction hides complexity to simplify the user's view; encapsulation hides data to protect it and keep control over changes.

One example showing both

interface Notifier {                     // ABSTRACTION: what we can do
    void send(String to, String message);
}

class EmailNotifier implements Notifier {
    private final String smtpHost;           // ENCAPSULATION: hidden state
    private int sentCount;

    EmailNotifier(String smtpHost) { this.smtpHost = smtpHost; }

    @Override
    public void send(String to, String message) {
        // connect to smtpHost, build mail ... (details hidden)
        sentCount++;
    }

    public int getSentCount() { return sentCount; }   // read-only access
}

The interface Notifier is abstraction: callers know only send. The private smtpHost and sentCount are encapsulation: no one can reset the counter from outside.

A one-line way to remember

Abstraction answers "what can I do with this?" Encapsulation answers "who may touch the insides?" You can have one without the other: a fully public class with an interface is abstract but not encapsulated; a class with private fields but no interface is encapsulated but not abstract.

Abstraction in depth

Abstraction means choosing which details matter to the user of a piece of code and leaving the rest out. You build it by deciding on a contract: a small set of operations with clear meaning. Java gives you interface and abstract class for this (the pillar itself is explained in the four pillars). Abstraction exists on many levels, not only in classes.

  • List hides whether the data sits in an array or in linked nodes.
  • JDBC's Connection hides the network protocol of PostgreSQL or MySQL.
  • A Spring @Service method placeOrder() hides ten database calls behind one business action.
  • Even a method name is an abstraction: you call Collections.sort(list) without knowing the algorithm.

A good abstraction lets you swap the implementation without changing the callers. Replace EmailNotifier with SmsNotifier and the code that calls Notifier.send() stays the same.

Encapsulation in depth

Encapsulation bundles the data with the methods that work on it and controls access, so the object can protect its own invariants (rules that must always be true, such as "balance never below zero"). The class becomes the only gatekeeper of its state. Java's tools are the access modifiers private, package-private (no keyword), protected and public, plus final and immutable classes. At a larger scale, the Java module system (module-info.java with exports) hides whole packages.

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class Wallet {
    private long balanceInPaise;                           // hidden state
    private final List<String> history = new ArrayList<>();

    public void deposit(long paise) {
        if (paise <= 0) throw new IllegalArgumentException("Amount must be positive");
        balanceInPaise += paise;
        history.add("DEPOSIT " + paise);
    }

    public void withdraw(long paise) {
        if (paise > balanceInPaise) throw new IllegalStateException("Insufficient funds");
        balanceInPaise -= paise;
        history.add("WITHDRAW " + paise);
    }

    public long getBalanceInPaise() { return balanceInPaise; }

    public List<String> getHistory() {
        return Collections.unmodifiableList(history);      // do not leak the real list
    }
}

Nobody can set the balance to a negative number, because the only ways to change it are deposit and withdraw, and both check the rule. If the field were public, any line of code in the project could break the rule.

Analogies that stick

  • ATM. The screen offers "Withdraw cash", "Check balance", "Change PIN". That list is the abstraction. The locked vault, the cash cassettes and the bank's database are encapsulated: you cannot reach them, and you do not need to.
  • TV remote. Buttons such as volume and channel are the abstraction. The sealed circuit inside is encapsulated.
  • Capsule tablet. The word encapsulation comes from this picture: the medicine (data) is sealed inside a shell, and you take it only in the form it is meant to be used.

How they work together

Encapsulation is closely related to information hiding: the design rule that a module should hide the decisions that are likely to change. Abstraction decides what to show; encapsulation makes sure the rest cannot be reached. A well-designed class does both.

Where each one goes wrong

Wrong: getters and setters for everything

public class Account {
    private long balance;
    public long getBalance() { return balance; }
    public void setBalance(long b) { balance = b; }
}
// anyone can call setBalance(-500)

Right: behaviour with rules

public class Account {
    private long balance;
    public void deposit(long amount) {
        if (amount <= 0) throw new IllegalArgumentException();
        balance += amount;
    }
    public long getBalance() { return balance; }
}

Wrong: a leaky abstraction

interface Cache {
    void put(String key, String value);
    void flushRedisPipeline();       // exposes one implementation
}

Right: the contract fits any implementation

interface Cache {
    void put(String key, String value);
    Optional<String> get(String key);
    void evict(String key);
}

Quick comparison: where Java's tools fit

Rule: expose behaviour, not raw state

Make fields private by default. Add a method only when a caller truly needs it, and prefer a method named after the action (deposit, cancel) over a bare setter. Return copies or unmodifiable views of internal collections.

Convention: program to the interface

Declare variables and parameters as List, Map, Notifier, not ArrayList or EmailNotifier. Your code then depends on the abstraction and not on one implementation.

Edge cases

  • Private is not absolute: reflection with setAccessible(true) can read private fields, which is how frameworks such as Hibernate and Jackson work. Since Java 16/17, the JDK blocks this for its own internal classes.
  • A getter that returns a mutable object (a List, a Date) breaks encapsulation even though the field is private.
  • Abstraction without encapsulation and encapsulation without abstraction are both possible, as the tip above shows.

Interview angle

This is among the most-asked pairs. Give the one-line difference, the table's three or four rows (what is hidden, level, Java tools), and a single example with both. Many candidates say "encapsulation is data hiding" and "abstraction is hiding implementation" — correct, but add "abstraction is about the design and the contract; encapsulation is about protecting state inside a class".

20-second answer: "Abstraction is a design idea: show only what a user needs, the contract, and hide how it works. I use interfaces and abstract classes for it. Encapsulation is an implementation technique: keep the data private inside the class and allow changes only through methods that enforce rules. Abstraction gives a simple view from outside; encapsulation protects the state inside. A List reference is abstraction; the private array inside ArrayList is encapsulation."

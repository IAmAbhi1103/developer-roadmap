Transactions, ACID and transaction states

A transaction is a group of operations treated as one logical unit; ACID — atomicity, consistency, isolation, durability — is the set of guarantees that makes it safe.

What a transaction is

A transaction is a sequence of database operations (reads and writes) that performs one logical task and must be executed as a whole. The classic example is a UPI transfer of ₹500 from account A to account B:

BEGIN;
UPDATE account SET balance = balance - 500 WHERE id = 'A';   -- step 1
UPDATE account SET balance = balance + 500 WHERE id = 'B';   -- step 2
COMMIT;                          -- or ROLLBACK to cancel both steps

If the system crashed between step 1 and step 2, ₹500 would vanish. A transaction makes the two steps all-or-nothing. In a normal client library, each single statement is its own transaction (autocommit) until you start one explicitly. The commands are BEGIN (or START TRANSACTION), COMMIT, ROLLBACK and SAVEPOINT (a point you can roll back to without cancelling everything).

Plain-words view of each property

  • Atomicity — "all or nothing". The responsibility of the recovery manager.
  • Consistency — "rules always hold". Partly the DBMS (it enforces declared constraints) and partly you: if you write a transfer that debits ₹500 but credits ₹400, the database cannot know it is wrong. Consistency is the one letter that is not purely a DBMS feature.
  • Isolation — "each transaction behaves as if it were alone". The responsibility of the concurrency-control manager. Full isolation costs speed, so databases offer levels (see the isolation-levels article).
  • Durability — "committed means permanent". The responsibility of the recovery manager; commit is acknowledged only after the log record reaches stable storage.

Memory hook: Atomicity and Durability belong to recovery; Isolation to concurrency control; Consistency to constraints and the programmer.

ACID "C" is not the CAP "C"

ACID consistency means "constraints and invariants hold". CAP consistency means "every read sees the latest write across replicas". Same word, different meaning. See the CAP section in the SQL vs NoSQL article.

Transaction states

Active
The initial state; the transaction is executing its reads and writes.
Partially committed
The last statement has run, but results may still be only in memory. The system now writes the log and checks that nothing violates constraints.
Committed
Success: the log is safely on disk. The effects are permanent. The only way to "undo" is a new compensating transaction.
Failed
The transaction can no longer proceed (constraint violation, deadlock victim, crash, user abort).
Aborted
The transaction was rolled back and the database restored to its state before the transaction. The system can then restart the transaction (if the failure was not a logic error) or kill it.
Terminated
The transaction has left the system (after commit or abort).

Commit and rollback in application code

@Transactional   // Spring starts a transaction, commits on success, rolls back on RuntimeException
public void transfer(long from, long to, long paise) {
    accounts.debit(from, paise);
    accounts.credit(to, paise);   // if this throws, the debit is rolled back too
}

Spring's rule: roll back on unchecked exceptions by default; checked exceptions commit unless you configure rollbackFor. For the Spring side see Spring Boot · Module 3; for how a database does this inside see SQL · Module 5.

Mistake: assuming DDL is always transactional

PostgreSQL lets you roll back most DDL (CREATE TABLE, ALTER TABLE). MySQL and Oracle commit implicitly on DDL, so a rollback cannot undo it.

Interview angle

Define each letter in one line, give the bank-transfer example, and say which component enforces it (log / constraints / locks / WAL). "Which ACID property is violated if the server crashes after commit and data is lost?" Durability. "If two users book the last seat at the same time?" Isolation.

Schedules, conflict serializability and recoverability

A schedule is an interleaving of transactions' operations; it is correct if it is equivalent to some serial order, which you can test by drawing a precedence graph and looking for a cycle.

Schedules

A schedule is the order in which operations of several transactions run. Write R1(A) for "transaction T1 reads A" and W1(A) for "T1 writes A". Within one transaction the order never changes.

  • Serial schedule: one transaction runs completely, then the next. Always correct, but slow — nothing runs in parallel. With n transactions there are n! serial schedules.
  • Concurrent (non-serial) schedule: operations of different transactions interleave. Fast, but only correct if equivalent to some serial schedule.
  • A concurrent schedule is serializable if its result equals that of some serial schedule.

Conflicting operations

Two operations conflict if all three hold: they belong to different transactions, they access the same data item, and at least one is a write.

PairConflict?Problem if reordered
R(A) – R(A)No—
R(A) – W(A)Yes (RW)Unrepeatable read
W(A) – R(A)Yes (WR)Dirty read
W(A) – W(A)Yes (WW)Lost update / overwritten write

Two schedules are conflict equivalent if one can be turned into the other by swapping adjacent non-conflicting operations. A schedule is conflict serializable if it is conflict equivalent to a serial schedule.

The precedence graph test

  1. Make one node per transaction.
  2. For each pair of conflicting operations where Ti's operation comes first and Tj's comes later, draw a directed edge Ti → Tj.
  3. If the graph has a cycle, the schedule is not conflict serializable. If it is acyclic, it is, and any topological order of the nodes is an equivalent serial order.

Worked example 1: acyclic

T1 works on A and B, T2 only on A. Schedule S1:

Order:  R1(A)  W1(A)  R2(A)  W2(A)  R1(B)  W1(B)

On A: R1(A) before W2(A)  -> T1 -> T2
      W1(A) before R2(A)  -> T1 -> T2
      W1(A) before W2(A)  -> T1 -> T2
On B: only T1, no conflict.
Graph: T1 -> T2   (no cycle)

S1 is conflict serializable, equivalent to the serial schedule T1 then T2. Check by swapping: R1(B) W1(B) do not conflict with T2's operations, so you can move them left past R2(A) W2(A), giving R1(A) W1(A) R1(B) W1(B) R2(A) W2(A) — the serial order T1; T2.

Worked example 2: a cycle (the lost update)

Both transactions read A, then both write A (each adds 100 to the value they read):

Order:  R1(A)  R2(A)  W1(A)  W2(A)

R1(A) before W2(A)  -> T1 -> T2
R2(A) before W1(A)  -> T2 -> T1
Graph: T1 -> T2 -> T1   (cycle)

S2 is not conflict serializable. With A = 1000 both read 1000, T1 writes 1100, T2 writes 1100 — one ₹100 update is lost. Any serial order would give 1200. The cycle in the graph is exactly the anomaly.

Worked example 3: three transactions

T1 writes A; T2 reads A and writes B; T3 reads B. Schedule S3: W1(A) R2(A) W2(B) R3(B). Edges: W1(A) → R2(A) gives T1 → T2; W2(B) → R3(B) gives T2 → T3. Acyclic. The topological order is T1, T2, T3, so S3 is equivalent to the serial schedule T1; T2; T3.

View serializability (brief)

Two schedules are view equivalent if (1) each transaction reads the same initial values, (2) each read sees the value written by the same transaction (same "read-from" relationships), and (3) the final write of each item is by the same transaction. A schedule is view serializable if it is view equivalent to a serial schedule.

  • Every conflict serializable schedule is view serializable, but not the other way round.
  • The difference comes from blind writes (writes without a prior read). Example: R1(A) W2(A) W1(A) W3(A) has a cycle T1 ⇄ T2, so it is not conflict serializable, yet it is view equivalent to the serial order T1, T2, T3 (T1 reads the initial A; the last write is T3's in both).
  • Testing view serializability is NP-complete, so databases use conflict serializability.

Recoverable, cascadeless and strict schedules

Serializability ignores failures. Recoverability asks: what if a transaction aborts?

  • Irrecoverable: T2 reads data written by T1 and commits before T1. Example: W1(A) R2(A) C2 A1 — T1 aborts after T2 has already committed a result based on a value that never existed. It cannot be fixed.
  • Recoverable: if T2 reads from T1, T1 commits before T2 commits.
  • Cascading rollback: W1(A) R2(A) W2(A) A1 — T1 aborts, so T2 (which read the dirty value) must abort too, and so on down a chain.
  • Cascadeless (ACA): a transaction reads only values written by committed transactions. No cascading rollbacks.
  • Strict: no transaction reads or overwrites an item written by an uncommitted transaction. Recovery by restoring "before images" is then simple.

Relation: strict ⊂ cascadeless ⊂ recoverable. Strict two-phase locking (next article) produces strict, conflict-serializable schedules.

Mistake: mixing up the edge direction

An edge Ti → Tj means "Ti must come before Tj in the equivalent serial order". The edge goes from the transaction whose conflicting operation comes first. A wrong direction on one edge can hide a cycle.

Interview angle

"How do you check if a schedule is serializable?" Precedence graph, cycle means no. Draw it live for a small schedule. Also: "conflict vs view serializable", "what is a cascading rollback", "recoverable vs cascadeless".

Concurrency control: locks, 2PL, timestamps, MVCC and deadlocks

Databases keep concurrent transactions correct with locks (two-phase locking), timestamps or multiple row versions (MVCC); locking can deadlock, which the DBMS detects with a wait-for graph and breaks by aborting a victim.

Lock-based protocols

A lock controls access to a data item. The two basic modes:

  • Shared lock (S): for reading; many transactions can hold it together.
  • Exclusive lock (X): for writing; only one holder, and no readers.
Held \ RequestedSX
SGrantedWait
XWaitWait

"Readers share, writers are alone." A transaction asks for a lock before using an item and releases it later; a lock upgrade turns S into X. Locking only for the duration of one operation is not enough: it still allows non-serializable schedules, so we need a protocol.

Two-phase locking (2PL)

Each transaction has two phases:

  1. Growing phase: it may acquire locks but not release any.
  2. Shrinking phase: it may release locks but not acquire any new one.

The moment of the last lock acquired is the lock point. Theorem: every schedule produced by 2PL is conflict serializable, and the transactions are equivalent to a serial order sorted by lock point. Limits of basic 2PL:

  • It does not prevent deadlocks.
  • It does not prevent cascading rollbacks: T1 may release an X lock in the shrinking phase, T2 reads the uncommitted value, then T1 aborts.
VariantRuleEffect
Basic 2PLGrowing then shrinkingConflict serializable; deadlocks and cascading rollback possible
Strict 2PLHold all exclusive locks until commit or abort Strict schedules: no cascading rollback; most databases behave like this
Rigorous 2PLHold all locks until commit or abort Serial order = commit order
Conservative 2PLAcquire all locks before starting Deadlock-free, but you must know the lock set in advance

Lock granularity and intention locks

Locks can be on a row, a page or a whole table. Fine granularity allows more concurrency but costs more lock memory. To let a table-level request find out quickly that some row inside is locked, databases use intention locks on the parent: IS (intend to take shared locks below) and IX (intend to take exclusive locks below). That is also why SELECT ... FOR UPDATE on a row blocks a table-level ALTER.

Deadlocks

A deadlock is a cycle of transactions each waiting for a lock the next one holds. T1 holds a lock on row A and wants B; T2 holds B and wants A. Neither can move.

Ways to handle it:

  • Detection: the DBMS builds the wait-for graph periodically (or on each wait), finds cycles and aborts one victim (usually the cheapest to roll back). The application sees an error (PostgreSQL: "deadlock detected", SQLSTATE 40P01; MySQL error 1213) and should retry the transaction.
  • Prevention with timestamps: each transaction gets a timestamp when it starts. Suppose Ti requests an item held by Tj.
    • Wait–die (non-preemptive): if Ti is older, it waits; if younger, it "dies" (aborts and restarts with the same timestamp).
    • Wound–wait (preemptive): if Ti is older, it "wounds" Tj (Tj aborts); if younger, it waits.
    In both schemes the older transaction is never starved, because restarted transactions keep their original timestamp.
  • Timeouts: abort a transaction that waits too long (simple, can be wrong).

Avoiding deadlocks in your code

Always lock rows in the same order (for example, lower account id first in a transfer), keep transactions short, and retry on a deadlock error. Details in SQL · Module 5.

Timestamp ordering (brief)

Instead of locks, give each transaction T a unique timestamp TS(T) at start. Each item Q keeps R-TS(Q) (the largest timestamp that read Q) and W-TS(Q) (the largest that wrote it). The schedule must act as the serial order of timestamps.

  • Read(Q) by T: if TS(T) < W-TS(Q), T would read a value "from the future" — reject and roll T back. Otherwise run it and set R-TS(Q) = max(R-TS(Q), TS(T)).
  • Write(Q) by T: if TS(T) < R-TS(Q), a younger transaction has already read the old value — roll T back. If TS(T) < W-TS(Q), an obsolete write — roll back (the Thomas write rule instead just ignores the write). Otherwise run it and set W-TS(Q) = TS(T).

Timestamp ordering is deadlock-free (nobody waits), but can roll back often and may cause starvation. Optimistic concurrency control (validation-based) is related: transactions run without locks on private copies, then validate at commit that no conflict occurred, and restart if one did. It suits workloads with few conflicts.

MVCC (multi-version concurrency control)

MVCC keeps several versions of a row. A write creates a new version instead of overwriting; every transaction reads from a consistent snapshot — the versions that were committed when it (or its statement) started.

  • Readers never block writers, and writers never block readers. Only writer–writer conflicts on the same row wait or fail.
  • Old versions are cleaned up later (PostgreSQL: VACUUM; InnoDB: purge of undo logs).
  • Used by PostgreSQL, Oracle and MySQL InnoDB, among others.
  • Plain MVCC gives snapshot isolation, which is not fully serializable: it allows write skew. Example: two doctors on call each check "at least one other doctor is on call" and both go off call. PostgreSQL's SERIALIZABLE level adds detection (SSI) to prevent this; the application must be ready to retry on a serialization failure (SQLSTATE 40001).

Interview angle

"What is 2PL and what does it guarantee?" Two phases; conflict serializability. "Does 2PL avoid deadlock?" No. "Strict 2PL?" Hold X locks to commit, so no cascading aborts. "How does a database detect a deadlock?" Wait-for graph cycle, then abort a victim. "What is MVCC and what is its benefit?" Versions and snapshots, readers do not block writers.

Isolation levels and the anomalies they allow

The four SQL isolation levels trade correctness for speed by allowing or forbidding dirty reads, non-repeatable reads and phantom reads; Read Committed is the common default, and Serializable is the only level with no anomalies.

The anomalies

All examples use an account(id, balance) table. T1 and T2 run at the same time.

Dirty read
T1 reads a value that T2 has written but not yet committed. If T2 rolls back, T1 used data that never existed. Example: T2 sets balance to 0 (uncommitted); T1 reads 0 and declines a loan; T2 rolls back.
Non-repeatable read
T1 reads the same row twice and gets different values because T2 updated and committed in between. Example: T1 reads balance 1000, T2 deducts 200 and commits, T1 reads 800.
Phantom read
T1 runs the same range query twice and gets different sets of rows because T2 inserted or deleted matching rows and committed. Example: T1 counts accounts with balance > 5000 and gets 10; T2 inserts one; T1 counts 11. (A non-repeatable read concerns a row that exists; a phantom concerns rows that appear or disappear.)
Lost update
Two transactions read the same value, both compute a new value and write it; the second write silently overwrites the first (schedule S2 from the schedules article).
Write skew
Two transactions read overlapping data, then update different rows based on what they read, breaking an invariant (both doctors go off call).

Isolation levels vs anomalies (SQL standard)

LevelDirty readNon-repeatable readPhantom read

REPEATABLE READPreventedPreventedPossible
SERIALIZABLEPreventedPreventedPrevented

This is the table the standard defines, and the one interviewers expect. Higher level means fewer anomalies, more blocking or retries, and lower throughput.

  • Read Uncommitted: no read locks; you can see uncommitted data. Rarely useful.
  • Read Committed: each statement sees only data committed before that statement began (MVCC), or takes short read locks (lock-based). The usual default.
  • Repeatable Read: rows you have read stay the same for the whole transaction (snapshot taken at the first statement, or read locks held to the end).
  • Serializable: the result equals some serial order. Implemented with range locks, or with SSI that aborts conflicting transactions.

Lost updates are not part of the standard's table. In practice, avoid them in any level with an atomic statement (SET balance = balance - 500), a row lock (SELECT ... FOR UPDATE), or a version column (optimistic locking). PostgreSQL's REPEATABLE READ aborts the second writer with an error; do not rely on that elsewhere.

Setting the level

-- one transaction
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM account WHERE id = 1;
-- ... other work ...
COMMIT;

-- lock the row you are about to change
SELECT balance FROM account WHERE id = 1 FOR UPDATE;
@Transactional(isolation = Isolation.REPEATABLE_READ)
public void report() { /* ... */ }

Mistake: using SERIALIZABLE everywhere "to be safe"

It reduces throughput and causes serialization failures that your code must retry. Use the default for most work, and raise the level (or use explicit row locks) only for the few places that need it, such as booking the last seat or a balance check followed by a write.

Recovery: logs, write-ahead logging and checkpoints

A DBMS survives crashes by writing every change to a log on disk before the data page (write-ahead logging), then after a crash redoing committed work and undoing unfinished work, starting from the last checkpoint.

Failures the DBMS must handle

  • Transaction failure: a logic error, constraint violation or deadlock victim — roll back that one transaction.
  • System crash: power loss or OS crash; memory is lost, disk survives.
  • Media failure: the disk is damaged — restore from backup and replay logs.

The log

The log (journal) is an append-only file of records describing every change. A typical record is <T, X, old, new>: transaction T changed item X from old (the before image) to new (the after image). Other records mark <T start>, <T commit> and <T abort>. Appending sequentially to a log is cheap; updating scattered data pages is not, which is why the log is written first.

Write-ahead logging (WAL)

The WAL rule has two parts:

  1. Before a modified data page is written to disk, the log records describing the change must already be on disk (this makes undo possible).
  2. A transaction is committed only when all its log records, including the commit record, are on disk (this makes redo possible and gives durability).

So at commit time the DBMS flushes only the log, not the data pages. The data pages can reach disk later, in the background. PostgreSQL's WAL and InnoDB's redo log are exactly this.

Buffer policies: steal and force

PolicyMeaningConsequence
STEALUncommitted changes may be written to diskNeeds UNDO after a crash
NO-STEALUncommitted pages stay in memoryNo undo, but a big transaction needs big memory
FORCEAll changed pages written at commitNo redo, but slow commits
NO-FORCEPages need not be written at commitNeeds REDO after a crash

Real systems use STEAL + NO-FORCE for performance, so they need both undo and redo, driven by WAL.

Recovery rules

After a crash, scan the log. For each transaction:

  • start and commit both in the log: REDO — apply the after images again (the data pages may not have reached disk).
  • start but no commit (or an abort): UNDO — restore the before images (some of its changes may have reached disk).
<T1 start>
<T1, A, 1000, 500>
<T1, B, 2000, 2500>
<T1 commit>
<T2 start>
<T2, C, 300, 400>
   --- crash ---

T1 committed: redo, so A = 500 and B = 2500. T2 never committed: undo, so C goes back to 300. The outcome is exactly as if T1 ran alone and T2 never started — atomicity and durability.

Checkpoints

Without help, recovery would scan the whole log since the database was created. A checkpoint periodically flushes dirty pages to disk and writes a checkpoint record listing the transactions active at that moment. After a crash, recovery starts from the last checkpoint:

TransactionPositionAction
T1Started and committed before the checkpointNothing; already on disk
T2Started before, committed after the checkpointREDO
T3Started after the checkpoint, committed before the crashREDO
T4Started before or after, no commit at the crashUNDO

ARIES, shadow paging and other ideas

  • ARIES is the standard recovery algorithm in many commercial databases. It runs three passes after a crash: analysis (find dirty pages and active transactions), redo (repeat history from the log, including the work of transactions that will later be undone) and undo (roll back the losers). It uses log sequence numbers (LSNs) on pages.
  • Deferred update writes to the database only after commit (no undo needed). Immediate update writes as the transaction proceeds (needs undo).
  • Shadow paging keeps a copy of the page table and switches to the new one at commit; no log needed, but fragmentation and poor concurrency make it uncommon.
  • Backups (full plus incremental) and point-in-time recovery (restore a backup, then replay archived logs to a chosen moment) protect against media failure and human error.

How this appears in real projects

You see WAL when you configure PostgreSQL replication (replicas replay the WAL stream) and point-in-time recovery. InnoDB's equivalent is the redo log plus undo logs, which also feed MVCC. Settings that trade durability for speed (like not flushing the log on each commit) risk losing the last few commits in a crash.

Interview angle

"What is WAL and why is it needed?" Log first, data later; enables undo and redo and cheap commits. "Redo or undo?" Committed — redo; uncommitted — undo. "What is a checkpoint?" A marker that bounds how much log recovery must read.

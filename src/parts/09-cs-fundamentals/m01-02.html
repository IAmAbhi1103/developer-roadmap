CPU scheduling: goals, criteria and preemption

The CPU scheduler picks which ready process runs next; it is judged by CPU utilisation, throughput, turnaround time, waiting time and response time, and it can be preemptive (the OS may take the CPU away) or non-preemptive (a process keeps it until it blocks or ends).

What the scheduler does

With many processes ready and few CPU cores, something must decide who runs. The short-term scheduler (the CPU scheduler) does this every time the CPU becomes free. The code that then hands the CPU over (switch context, switch to user mode, jump to the right instruction) is called the dispatcher, and the time it takes is the dispatch latency.

A process alternates between a CPU burst (computing) and an I/O burst (waiting for disk or network). A CPU-bound process has long CPU bursts (video encoding); an I/O-bound process has many short bursts (a web server handler). A good scheduler favours short bursts, because that keeps the I/O devices busy and the system responsive.

Scheduling decisions happen when a process (1) goes from running to waiting, (2) goes from running to ready (timer interrupt), (3) goes from waiting to ready (I/O finished), or (4) terminates. If the scheduler acts only in cases 1 and 4, scheduling is non-preemptive. If it also acts in cases 2 and 3, it is preemptive.

Scheduling criteria and formulas

Arrival time (AT)
The time the process enters the ready queue.
Burst time (BT)
The CPU time the process needs in total.
Completion time (CT)
The clock time at which the process finishes.
Turnaround time (TAT)
Total time from arrival to completion: TAT = CT − AT.
Waiting time (WT)
Time spent sitting in the ready queue: WT = TAT − BT.
Response time (RT)
Time from arrival to the first time on the CPU: RT = first run − AT.
CPU utilisation
The percentage of time the CPU is busy. Goal: keep it high.
Throughput
Number of processes completed per unit time. Goal: maximise.

The goals are to maximise utilisation and throughput and to minimise turnaround, waiting and response time. They conflict: a scheduler tuned for the best throughput may give poor response time. Interactive systems care about response time and fairness; batch systems care about throughput.

How to solve a scheduling problem

  1. Make a table of arrival and burst times.
  2. Advance a clock. Whenever the CPU is free (or a preemption point arrives), pick a process by the algorithm's rule from those that have already arrived.
  3. Draw the Gantt chart and read off each process's completion time.
  4. Compute TAT = CT − AT and WT = TAT − BT, then take averages.

If the CPU is idle because no process has arrived, the clock simply jumps to the next arrival. In the next articles every algorithm is solved on the same four processes so you can compare results:

Rule: waiting time excludes the time a process spends running or in I/O

Waiting time counts only the time in the ready queue. With no I/O in the problem, WT = TAT − BT is exact. Mixing up turnaround and waiting time is the most common exam error.

Edge cases

  • When two processes arrive at the same time, or tie on the rule, the tie is broken by lower process number (FCFS order). State your tie-break in an interview.
  • In Round Robin, if a new arrival and a preempted process enter the queue at the same instant, the usual convention is that the new arrival goes first. Textbooks differ; say which one you use.
  • Context-switch time is normally ignored in textbook problems but is real overhead.

Real projects

Linux's default scheduler for normal tasks is the Completely Fair Scheduler (CFS), which gives each task a fair share of CPU time using virtual runtime. Recent kernels (6.6 onwards) replaced it with the EEVDF scheduler. You rarely tune it directly, but nice values and container CPU limits (--cpus, Kubernetes CPU requests and limits) influence it. Details of both schedulers are beyond interview level.

FCFS, SJF and SRTF scheduling

FCFS runs processes in arrival order and suffers from the convoy effect; SJF runs the shortest next burst first and gives the lowest average waiting time among non-preemptive algorithms but can starve long jobs; SRTF is its preemptive form and does even better.

First-Come, First-Served (FCFS)

FCFS is non-preemptive and uses a simple FIFO queue: the process that arrives first runs to completion first. It is easy to implement and fair in the sense of order, but its average waiting time can be very long.

The convoy effect

The convoy effect happens when many short processes queue behind one long CPU-bound process, like many small cars stuck behind one slow truck. Take three processes arriving at time 0 in the order P1 (burst 24), P2 (3), P3 (3):

FCFS order: waiting times are 0, 24 and 27, average = 51 / 3 = 17. Shortest-first order: waiting times are P2 = 0, P3 = 3, P1 = 6, average = 9 / 3 = 3. Same work, same finish time (30), but the average wait fell from 17 to 3. The convoy also keeps I/O devices idle, since the I/O-bound processes are stuck waiting for the CPU. This motivates SJF.

Shortest Job First (SJF, non-preemptive)

SJF picks, among the processes that have arrived, the one with the smallest CPU burst. When the CPU is free it decides; once running, a process is never interrupted. It is provably optimal for minimum average waiting time among non-preemptive algorithms.

  1. t = 0: only P1 has arrived, so P1 runs 0–8 (non-preemptive, it cannot be stopped).
  2. t = 8: P2 (4), P3 (9), P4 (5) are waiting. Shortest is P2: runs 8–12.
  3. t = 12: P3 (9) and P4 (5) wait. P4 is shorter: runs 12–17.
  4. t = 17: only P3 is left: runs 17–26.

Shortest Remaining Time First (SRTF, preemptive SJF)

SRTF re-decides every time a process arrives: if the newcomer's burst is shorter than the remaining time of the running process, the running one is preempted.

  1. t = 0: P1 starts (remaining 8).
  2. t = 1: P2 arrives with 4. P1 has 7 left, so P2 preempts P1.
  3. t = 2: P3 (9) arrives; P2 has 3 left, so P2 continues. t = 3: P4 (5) arrives; P2 has 2 left, so P2 continues.
  4. t = 5: P2 finishes. Remaining times: P1 = 7, P3 = 9, P4 = 5. P4 is shortest: runs 5–10.
  5. t = 10: P1 (7) beats P3 (9): runs 10–17. Then P3 runs 17–26.

The catches of SJF and SRTF

  • The next burst length is unknown. The OS cannot see the future, so it predicts it from the past with an exponential average: next = α × last_burst + (1 − α) × previous_prediction, with α usually 0.5. That is why SJF is mostly a theory benchmark.
  • Starvation: if short jobs keep arriving, a long job may wait forever.
  • SRTF adds context-switch overhead.

Rule: SJF chooses only among processes that have already arrived

A very common error is picking the globally shortest job even though it arrives later. In the example above, P2 (burst 4) cannot start at t = 0, because it arrives at t = 1.

Mistake: forgetting that waiting time uses arrival time

For P2 in FCFS, completion is 12 but waiting time is 12 − 1 − 4 = 7, not 8. Always subtract arrival time before burst time.

Interview: "Why is SJF optimal but not used in practice?"

  • It minimises average waiting time, since running short jobs first reduces the time everyone else waits.
  • But burst lengths are not known in advance (only estimated), and long jobs can starve.
  • Explain the convoy effect as the reason FCFS performs poorly, with the 24/3/3 example (17 vs 3).

Priority scheduling and Round Robin

Priority scheduling runs the highest-priority process first and fixes starvation with aging; Round Robin gives every process a fixed time quantum in turn, which gives good response time for interactive systems if the quantum is chosen well.

Priority scheduling

Each process gets a priority number, and the CPU goes to the highest priority. In these notes a lower number means higher priority (as in Unix nice values, where -20 is the highest priority and 19 the lowest; some books use the opposite, so always state the convention). Priority can be set internally by the OS (memory needs, I/O-to-CPU ratio, SJF itself is priority = burst time) or externally (importance, user, payment). It can be non-preemptive or preemptive.

Example (non-preemptive), same arrivals and bursts as before, with priorities P1 = 2, P2 = 4, P3 = 1, P4 = 3:

  3. t = 17: P4 (3) beats P2 (4): runs 17–22. Then P2 runs 22–26.

Starvation and aging

Starvation (indefinite blocking) means a low-priority process may wait forever while higher-priority ones keep arriving. A famous story says that when the IBM 7094 at MIT was shut down in 1973, a low-priority process submitted in 1967 had still not run. Treat that as a legend rather than a hard fact.

The fix is aging: the longer a process waits, the more its priority is raised, for example by one level every few minutes. Eventually even the lowest-priority process becomes the highest and runs.

Priority inversion

A low-priority process holds a lock that a high-priority process needs, and a medium-priority process keeps preempting the low one, so the high-priority process waits behind the medium one. The usual fix is priority inheritance: the lock holder temporarily gets the priority of the waiter. This bug famously caused repeated resets of the Mars Pathfinder lander in 1997.

Round Robin (RR)

Round Robin is the preemptive scheduler designed for time-sharing. The ready queue is a circular FIFO queue. Each process gets the CPU for at most one time quantum (time slice) q. If it needs more, a timer interrupt preempts it and it goes to the back of the queue. If it finishes earlier, the CPU is released at once.

Same four processes, quantum q = 4 (tie rule: a process that arrives during a slice enters the queue before the preempted process):

  1. 0–4: P1 runs (4 left). During this time P2, P3 and P4 arrive. Queue: P2, P3, P4, P1.
  2. 4–8: P2 runs and finishes (burst 4). 8–12: P3 runs (5 left). 12–16: P4 runs (1 left).
  3. 16–20: P1 runs its last 4 and finishes.
  4. 20–24: P3 runs (1 left). 24–25: P4 runs its last unit and finishes. 25–26: P3 finishes.

Choosing the time quantum

  • q very large → RR behaves like FCFS (a process finishes within its quantum).
  • q very small → many context switches; useful work shrinks. If q is comparable to the context-switch time, a large share of the CPU goes to switching.
  • Rule of thumb: q should be larger than the context-switch time by a wide margin, and roughly 80% of CPU bursts should finish within one quantum. Typical values are 10–100 ms.

With n processes and quantum q, no process waits more than (n − 1) × q before its next turn. That bound is why RR has no starvation.

Rule: RR is preemptive by design; a process leaves the CPU for one of three reasons

It finishes, it blocks for I/O, or its quantum expires (then it goes to the tail of the ready queue).

Mistake: restarting the quantum on a process that has not used it

If a process blocks after 1 unit of its 4-unit quantum, it does not get the rest later: when it returns it joins the queue and gets a fresh quantum. Also never put the preempted process in the queue before the new arrivals unless your stated convention says so.

Interview: "How does the time quantum affect Round Robin? What is starvation and aging?"

  • Large quantum → FCFS. Tiny quantum → context-switch overhead dominates.
  • RR gives good response time, poor average turnaround time; it is fair and has no starvation.
  • Priority scheduling can starve low-priority processes; aging raises the priority of waiting processes over time.
  • Bonus: priority inversion and priority inheritance.

Multilevel queues, MLFQ and comparing the algorithms

A multilevel queue splits processes into fixed classes with their own queues, while a multilevel feedback queue moves processes between queues based on observed behaviour, so short and interactive jobs finish fast without knowing burst lengths in advance.

Multilevel Queue (MLQ)

Processes are permanently assigned to one of several queues by type, for example: system processes, interactive (foreground) processes, batch (background) processes. Each queue has its own algorithm (say RR for foreground, FCFS for background). Between queues there are two usual designs:

  • Fixed priority: a lower queue runs only when all higher queues are empty. Simple, but can starve the lower queues.
  • Time slicing between queues: for example 80% of CPU time to the foreground queue (RR) and 20% to the background queue (FCFS).

Worked example (fixed priority between queues). Queue 1 (foreground) uses RR with q = 2; Queue 2 (background) uses FCFS. All processes arrive at t = 0: F1 (foreground, burst 3), F2 (foreground, burst 2), B1 (background, burst 4).

Multilevel Feedback Queue (MLFQ)

MLFQ lets a process move between queues. It is the idea behind the schedulers of many real systems. The common rules:

  1. There are several queues; higher queues have higher priority and smaller quanta.
  2. A new process enters the top queue.
  3. If it uses up its whole quantum, it is demoted to the next queue (it looks CPU-bound).
  4. If it gives up the CPU early (for I/O), it stays at its level (it looks interactive).
  5. The bottom queue is usually FCFS. To prevent starvation, a process that waits too long is promoted (aging), or all processes are periodically boosted to the top.

The key benefit: the scheduler learns job lengths from behaviour. Short and interactive jobs finish in the top queues; long CPU hogs sink to the bottom, without the OS ever being told burst times.

Worked example. Three queues: Q0 uses RR with q = 2, Q1 uses RR with q = 4, Q2 uses FCFS. All three processes arrive at t = 0 in order A (burst 10), B (3), C (6). A higher queue always runs before a lower one.

  1. Q0 (q = 2): A runs 0–2 (8 left, demoted), B runs 2–4 (1 left, demoted), C runs 4–6 (4 left, demoted).
  2. Q1 (q = 4): A runs 6–10 (uses all 4, 4 left, demoted to Q2). B runs 10–11 and finishes. C runs 11–15 and finishes (its last 4 units fit in the quantum).
  3. Q2 (FCFS): A runs 15–19 and finishes.

Edge cases

  • In a real MLFQ, a clever process can game the scheduler by doing a tiny I/O just before its quantum ends to stay at the top level. Modern designs count the total CPU time used at a level, not just one burst.
  • Multi-core systems usually keep one run queue per core with load balancing between them, plus a preference to keep a process on the same core to keep its cache warm (processor affinity).
  • Real-time systems use specialised algorithms such as Rate Monotonic and Earliest Deadline First; you only need to know they exist.

How to present a scheduling answer in an exam or interview

  • Write the table, the tie-break rule, the Gantt chart, then the formulas with numbers substituted. Interviewers want to see the method.
  • Check that CT of the last process equals the sum of all bursts when there is no idle gap.
  • Check that the sum of all waiting times plus the sum of all bursts equals the sum of all turnaround times.

Interview: "Which scheduling algorithm is best?" and "Explain MLFQ"

  • No single best: SRTF gives the lowest average waiting time but needs the future and starves long jobs; RR gives the best response time for interactive systems.
  • MLFQ approximates SJF without knowing burst times: new jobs start at the top, those that use their full quantum are demoted, and aging or periodic boosts prevent starvation.
  • Always mention the trade-offs: throughput, fairness, response time and overhead.

Memory management: addresses, contiguous allocation and fragmentation

The MMU translates the logical addresses a program uses into physical RAM addresses; with contiguous allocation each process gets one unbroken block (placed by first, best or worst fit), which leads to internal and external fragmentation that compaction or paging must repair.

Why memory management?

RAM is shared by the kernel and many processes. The memory manager must (1) track which parts are free or used, (2) give memory to processes and take it back, (3) protect each process from touching another's memory, and (4) let programs be bigger than RAM (virtual memory, the next articles). Remember the layout of a process from the process article: text, data, heap and stack. Here we look at how the OS places them in RAM.

Logical vs physical addresses and the MMU

  • A logical (virtual) address is what the CPU generates while running a program. The program thinks its memory starts at address 0 and is its own.
  • A physical address is the actual location in RAM.
  • The Memory Management Unit (MMU) is hardware between the CPU and RAM that converts logical to physical addresses on every memory access.

The simplest MMU scheme uses two registers per process: a base (relocation) register and a limit register. Physical address = logical address + base, and the access is allowed only if logical address < limit; otherwise the hardware raises a trap (the OS then ends the process: on Linux, "segmentation fault"). Only the kernel can change these registers when it does a context switch.

Because of this translation, a process can be loaded anywhere in RAM and even moved later. The OS can also swap a whole process out to disk when RAM is short and bring it back later (swapping).

Contiguous allocation

In the oldest scheme each process occupies one contiguous block of RAM. Memory is divided into partitions: fixed-size partitions (simple, but a process wastes the unused part of its partition) or variable-size partitions (the OS carves out exactly what a process needs). Free blocks are called holes. To place a process of size n, the OS chooses a hole of at least n by one of three strategies:

StrategyRuleNotes
First fitFirst hole that is big enough, scanning from the startFast; leaves small holes near the start
Best fitSmallest hole that is big enoughMust search all holes (unless sorted); leaves many tiny, useless holes
Worst fitLargest holeLeaves big leftover holes; in practice performs poorly

Worked example: first, best and worst fit

Memory has five holes in this order: 100 KB, 500 KB, 200 KB, 300 KB, 600 KB. Processes arrive in the order 212 KB, 417 KB, 112 KB, 426 KB.

First fit.

  • 212 → the 500 KB hole (first big enough; 100 is too small). The hole becomes 288.
  • 417 → 500 is now 288 (too small), 200 and 300 too small, so the 600 KB hole. It becomes 183.
  • 112 → holes are now 100, 288, 200, 300, 183. First big enough is 288 → 176 left.
  • 426 → holes: 100, 176, 200, 300, 183. None is large enough, so the process must wait.

Best fit.

  • 212 → smallest hole ≥ 212 is 300 → 88 left.
  • 417 → smallest ≥ 417 is 500 → 83 left.
  • 112 → holes 100, 83, 200, 88, 600; smallest ≥ 112 is 200 → 88 left.
  • 426 → only 600 fits → 174 left. All four processes are placed.

Worst fit.

  • 212 → largest hole is 600 → 388 left.
  • 417 → largest is 500 → 83 left.
  • 112 → holes 100, 83, 200, 300, 388; largest is 388 → 276 left.
  • 426 → holes 100, 83, 200, 300, 276: none fits, so it must wait.

So in this example best fit gave the best result, but that is not guaranteed in general: first fit and best fit are about equally good in studies, and both beat worst fit on average.

Fragmentation

PointInternal fragmentationExternal fragmentation
What is wastedSpace inside an allocated block that the process does not useFree space between allocated blocks, in scattered small holes
CauseFixed-size units (fixed partitions, pages): the block is larger than the requestVariable-size contiguous allocation: processes come and go, leaving holes
ExampleA 10 KB process in a 12 KB partition wastes 2 KB; the last page of a processHoles of 50 KB + 60 KB + 40 KB = 150 KB free in total, but a 100 KB process cannot be placed
RemedySmaller allocation units; variable partitionsCompaction; paging or segmentation (non-contiguous allocation)

Compaction slides all processes to one end of memory so that the holes merge into one large block. It is possible only if relocation is dynamic (the base register can be changed), and it is expensive because a lot of memory must be copied. The better cure is to stop requiring contiguous memory, which is what paging does.

Rule: every memory access passes through the MMU, and the OS alone controls its registers

That is the basis of process isolation: a process can only form addresses inside its own mapping.

Edge cases

  • A 50-percent rule from studies of first fit says that with N allocated blocks about N/2 blocks are lost to fragmentation (one third of memory unusable); treat it as a rule of thumb, not a guarantee.
  • Internal and external fragmentation cannot both be eliminated by the same fix; paging removes the external kind but brings back a little internal waste.
  • A "segmentation fault" is the OS reacting to an access that the hardware rejected, such as a null pointer dereference in C. In Java the same mistake becomes NullPointerException because the JVM checks first.

Mistake: mixing up the two kinds of fragmentation

Internal = wasted inside a block you were given. External = free memory that exists but is split into pieces too small to use. A quick memory aid: external is "outside any process".

Paging and address translation

Paging cuts a process's logical address space into fixed-size pages and RAM into frames of the same size, so pages can sit in any free frames; a per-process page table maps page numbers to frame numbers, and an address is split into page number and offset.

The idea

Paging removes the need for contiguous memory. Logical memory is divided into pages; physical memory is divided into frames of exactly the same size (a power of two, commonly 4 KB). Any page can go into any free frame, so external fragmentation disappears. The OS keeps a free-frame list. To run a program of n pages it finds n free frames and loads the pages there, then fills in the page table.

Splitting the address

Every logical address the CPU generates is split in two by simple bit slicing:

  • Page number (p): the high bits; used as an index into the page table.
  • Page offset (d): the low bits; the position inside the page, unchanged by translation.

If the logical address space is 2m bytes and the page size is 2n bytes, then the offset takes n bits and the page number takes m − n bits. The physical address is frame number × page size + offset (or: frame number bits followed by the offset bits).

Worked example

Logical address space 64 KB (16-bit addresses), page size 4 KB (212), physical memory 32 KB.

  • Offset = 12 bits. Page number = 16 − 12 = 4 bits, so there are 16 pages.
  • Physical memory has 32 KB / 4 KB = 8 frames, so a frame number needs 3 bits and a physical address has 15 bits.

Part of the page table (page 5 is not in memory):

Page012345
Frame52703invalid

Translate logical address 9000:

  1. Page number = 9000 div 4096 = 2 (2 × 4096 = 8192). Offset = 9000 − 8192 = 808.
  2. Page table: page 2 → frame 7.
  3. Physical address = 7 × 4096 + 808 = 28672 + 808 = 29480.

Check in binary: 9000 = 0010 0011 0010 1000. The top 4 bits 0010 are page 2; the low 12 bits 0011 0010 1000 (hex 328 = 808) are the offset. Frame 7 is 111, so the physical address is 111 0011 0010 1000 = hex 7328 = 29480. ✓

public class Translate {
    static final int PAGE_BITS = 12;                  // 4 KB pages
    static final int[] FRAME = {5, 2, 7, 0, 3, -1};   // -1 = page not in memory

    public static void main(String[] args) {
        int[] logicalAddresses = {9000, 4100, 12345, 21000};
        for (int addr : logicalAddresses) {
            int page = addr >> PAGE_BITS;               // high bits
            int offset = addr & 0xFFF;                  // low 12 bits
            if (FRAME[page] < 0) {
                System.out.println(addr + " -> page " + page + ", offset " + offset
                        + " -> PAGE FAULT");
                continue;
            }
            int physical = (FRAME[page] << PAGE_BITS) | offset;
            System.out.println(addr + " -> page " + page + ", offset " + offset
                    + " -> frame " + FRAME[page] + " -> physical " + physical);
        }
    }
}
9000 -> page 2, offset 808 -> frame 7 -> physical 29480
4100 -> page 1, offset 4 -> frame 2 -> physical 8196
12345 -> page 3, offset 57 -> frame 0 -> physical 57
21000 -> page 5, offset 520 -> PAGE FAULT

Check the second line by hand: 4100 = 4096 + 4, so page 1, offset 4; frame 2 gives 2 × 4096 + 4 = 8196. Third: 12345 − 3 × 4096 (12288) = 57; frame 0 gives 57. Fourth: 21000 − 5 × 4096 (20480) = 520; page 5 is invalid, so the hardware traps to the OS (a page fault, see virtual memory).

Page table entries (PTE)

A page-table entry holds the frame number plus control bits:

BitPurpose
Valid / presentIs the page in a frame (1) or not (0)? An access to a 0 page causes a page fault.
ProtectionRead, write, execute permissions; writing to a read-only page traps.
Dirty (modified)Set when the page has been written; a dirty page must be saved to disk before its frame is reused.
Referenced (accessed)Set on any use; helps page replacement decide what is old.

The code page of two processes running the same program can point to the same frame (sharing), saving RAM. This is how shared libraries work, and also how fork() with copy-on-write starts.

Page-table size and internal fragmentation

On a 32-bit system with 4 KB pages, the page number has 32 − 12 = 20 bits, so a single-level page table has 220 = 1,048,576 entries. At 4 bytes per entry that is 4 MB per process just for the table, and 64-bit systems make a flat table impossible. The remedies, multi-level tables and others, are in the next article.

Paging has no external fragmentation but has internal fragmentation in the last page of every process. Example: with a page size of 2,048 bytes, a process of 72,766 bytes needs 35 full pages (71,680 bytes) plus 1,086 bytes, so 36 pages; the last page wastes 2,048 − 1,086 = 962 bytes. On average a process wastes about half a page. A smaller page size wastes less but needs larger page tables and more disk transfers, so common sizes are 4 KB, with "huge pages" of 2 MB for big-memory servers.

Rule: page size = frame size = a power of two

That is what makes the split of an address into page number and offset a simple cut in the bits, with no division needed.

Edge cases

  • The page table must be in memory, so without a cache every access would cost two memory accesses (one for the table, one for the data). The TLB solves this.
  • A context switch must switch the page-table pointer, which is why it is part of the saved context.
  • Programmers see contiguous memory; only the OS sees the scattered frames. So a Java int[] that is contiguous in the JVM's virtual addresses can sit in many unrelated physical frames.

Mistake: translating the offset

The offset is copied unchanged from the logical to the physical address. Only the page number is replaced by the frame number.

TLB, multi-level page tables and segmentation

A TLB caches recent page-to-frame translations so most accesses need no page-table lookup, multi-level page tables keep the table small for sparse address spaces, and segmentation divides memory by logical parts (code, stack, heap) instead of fixed-size pages.

The Translation Lookaside Buffer (TLB)

Without help, each memory access needs two RAM accesses: one to read the page-table entry, one for the actual data. The TLB is a small, very fast hardware cache inside the MMU that stores recent (page → frame) pairs, usually tens to a few thousand entries.

  1. The CPU generates a logical address; the MMU takes the page number.
  2. It looks the page up in the TLB (in parallel across all entries).
  3. TLB hit: the frame number is available at once; access RAM once.
  4. TLB miss: read the page table in RAM (an extra access), then load that entry into the TLB (evicting another) and access the data.

On a context switch the old process's translations are wrong for the new one, so the TLB is flushed, or its entries are tagged with an address-space id (ASID) so both can coexist. This flush is part of the hidden cost of switching processes (context switching). Locality of reference (programs reuse nearby addresses) gives hit ratios of 98 percent or more in practice.

Effective Access Time (EAT)

Let the TLB lookup take ε, a memory access take m, and the TLB hit ratio be h. With a single-level page table:

EAT = h × (ε + m) + (1 − h) × (ε + m + m)

Example. TLB lookup = 10 ns, memory access = 100 ns.

  • Hit ratio 80%: EAT = 0.80 × (10 + 100) + 0.20 × (10 + 100 + 100) = 0.80 × 110 + 0.20 × 210 = 88 + 42 = 130 ns. That is 30% slower than the ideal 100 ns.
  • Hit ratio 98%: EAT = 0.98 × 110 + 0.02 × 210 = 107.8 + 4.2 = 112 ns (only 12% slower).

With a two-level page table a miss costs two table reads plus the data: at 98% hits, EAT = 0.98 × 110 + 0.02 × (10 + 100 + 100 + 100) = 107.8 + 0.02 × 310 = 107.8 + 6.2 = 114 ns. The TLB makes deep page tables affordable. (Some textbooks ignore the TLB lookup time ε; if so, use 100 and 200 in the formula instead. State your assumption.)

Multi-level (hierarchical) page tables

A flat table for a 32-bit space needs 220 entries (4 MB) per process, even if the process uses a few pages. The fix is to page the page table itself. In a two-level scheme with 4 KB pages and 4-byte entries, the 32-bit address splits as 10 + 10 + 12 bits:

An inner table is allocated only if some page in its 4 MB range is used (1024 pages × 4 KB). A small process needs the outer table plus a few inner tables, a few KB instead of 4 MB. 64-bit CPUs use four or five levels (x86-64 uses four, with an optional fifth). The price is more memory accesses per TLB miss, which the TLB hides.

Two other designs exist: hashed page tables (hash the page number) and inverted page tables (one entry per physical frame for the whole system, searched by process id and page number; small, but lookup is slow without a hash and sharing is hard). Know the names.

Segmentation

Segmentation divides a program by its logical parts: main code, functions, global data, heap, stack, each a segment of different length. A logical address is a pair (segment number, offset). A segment table has, for each segment, a base (start in RAM) and a limit (length). The translation is: if offset < limit, physical = base + offset; otherwise trap.

  • Address (2, 53): 53 < 400, so physical = 4300 + 53 = 4353.
  • Address (3, 852): 852 < 1100, so physical = 3200 + 852 = 4052.
  • Address (0, 1222): 1222 ≥ 1000, so the hardware traps: the offset is beyond the segment.

Segmentation matches how programmers think and makes sharing and protection natural (a code segment is read-only; a stack segment is read-write). But segments have different sizes, so it suffers from external fragmentation again. Real systems either use paging alone (modern Linux, with a flat address space) or paged segmentation, where each segment is itself divided into pages (the old x86 and others).

Rule: translation hardware sits on the critical path, so it must be cached

The TLB is not optional; without it paging would halve memory speed. Hit ratio drives performance, and a context switch that flushes the TLB hurts.

Edge cases

  • A TLB miss is not a page fault. A miss only means the translation was not cached; the page may well be in RAM. A page fault means the page is not in RAM at all.
  • Huge pages (2 MB or 1 GB) cover much more memory per TLB entry and so reduce TLB misses for large heaps; the JVM can use them with -XX:+UseLargePages or transparent huge pages.
  • Segmentation in a segmented system can give two different errors from the same bad address range: a limit violation (trap) versus a not-present segment (fault).

Real projects

For a big Java heap or a database with a huge buffer cache, TLB misses show up as slower memory access; operations teams then enable huge pages. In everyday backend work you only meet the idea indirectly: a large, randomly accessed data structure is slower than a compact, sequentially accessed one partly because of cache and TLB behaviour (see backend work).

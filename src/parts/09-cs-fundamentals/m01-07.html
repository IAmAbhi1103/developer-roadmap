File systems: files, directories, inodes and allocation

A file system turns raw disk blocks into named files and directories; on Unix a file's metadata and block pointers live in an inode, directories map names to inode numbers, and allocation methods (contiguous, linked, indexed) decide how a file's blocks are placed on disk.

Files and directories

A file is a named collection of related bytes stored persistently. The OS hides disk sectors and presents a file as a stream of bytes. Its attributes include name, type, size, location, owner, permissions and timestamps. The main operations are create, open, read, write, seek, truncate, close and delete; the matching Java classes are in java.io and java.nio.file (see Core Java · Module 3).

A directory is a special file that maps names to files. Directory structures: single-level (one flat list, name clashes), two-level (one directory per user), tree-structured (directories inside directories, with absolute and relative paths; what you use daily) and acyclic graph (a file can appear under two names through links, but no loops).

When a program calls open(), the kernel returns a small integer, the file descriptor, an index into the process's table of open files. 0, 1 and 2 are standard input, output and error. Sockets and pipes also use descriptors, so "everything is a file" on Unix. Each process may open only a limited number of descriptors.

The inode

On Unix-style file systems (ext4, XFS and others) each file has an inode (index node), a fixed-size structure holding everything about the file except its name: type, owner, permissions, size, timestamps, link count and the pointers to the data blocks. The inode is identified by an inode number. A directory entry is simply (name → inode number). That separation makes links possible:

A file's data is freed only when its link count reaches zero and no process still has it open. That is why a deleted log file still takes disk space while a process holds it open (a classic surprise in production; df shows full but du does not).

$ ls -i report.txt
524301 report.txt
$ ln report.txt backup.txt && ls -li report.txt backup.txt
524301 -rw-r--r-- 2 asha asha 1204 Nov 11 10:00 backup.txt
524301 -rw-r--r-- 2 asha asha 1204 Nov 11 10:00 report.txt

Both names show the same inode number and a link count of 2. The numbers here are examples.

File allocation methods

How are a file's blocks placed on the disk?

MethodHowProsCons
ContiguousFile occupies consecutive blocks (start, length)Fast sequential and direct access; simpleExternal fragmentation; file size must be known or hard to grow
LinkedEach block holds a pointer to the next blockNo external fragmentation; grows easilySlow random access (follow the chain); one broken pointer loses the rest; pointer space per block
IndexedAn index block lists all the file's block addressesDirect access; no external fragmentationIndex block overhead, even for tiny files

FAT (the file allocation table, used on USB sticks and SD cards) is the linked method with the chain pointers moved into one table. Unix inodes use a clever indexed scheme: the inode holds some direct pointers to data blocks, plus a single indirect pointer (to a block of pointers), a double indirect and a triple indirect pointer. Small files stay fast; huge files are still possible.

Worked example (the classic ext2-style layout): block size 4 KB, block pointer 4 bytes, 12 direct pointers.

  • Pointers per indirect block = 4096 / 4 = 1,024.
  • Direct: 12 × 4 KB = 48 KB.
  • Single indirect: 1,024 × 4 KB = 4 MB.
  • Double indirect: 1,024 × 1,024 × 4 KB = 4 GB.
  • Triple indirect: 1,0243 × 4 KB = 4 TB.

Modern file systems such as ext4 use extents (a start block plus a length) instead of long pointer lists, but the indirect-block scheme remains the standard teaching example.

Free-space management and reliability

  • Bitmap: one bit per block (1 = free, or the reverse). Easy to find runs of free blocks.
  • Linked list of free blocks, or a list of free runs (grouping and counting).
  • Journaling: before changing the file system's structures, the OS writes the intended change to a log (the journal). After a crash it replays or discards the log instead of scanning the whole disk, which keeps the file system consistent. ext4, NTFS and XFS journal their metadata.
  • Buffer (page) cache: recently used blocks stay in RAM, so most reads never touch the disk. Writes are normally buffered too, so a program must call fsync (Java: FileChannel.force) when it needs data on the disk before continuing; this is what databases do at commit.

For Unix permissions (read, write, execute for owner, group and others, written like rwxr-xr--) and the shell commands around files, see DevOps · Linux and the command line.

Rule: the name lives in the directory, not in the inode

Rename and move within a file system change only directory entries; the inode and data stay put. That is why a rename is instant.

Edge cases

  • A file system can run out of inodes before it runs out of space (millions of tiny files); df -i shows it, and the error message is still "No space left on device".
  • Deleting a file does not erase its data; the blocks are only marked free.
  • On Windows the path separator and case rules differ; Java's Path hides most of that.

Interview: "What is an inode? Hard link vs soft link? File allocation methods?"

  • Inode: per-file metadata and block pointers (not the name); directory entries map names to inode numbers.
  • Hard link shares the inode and survives deletion of the other name; soft link stores a path.
  • Contiguous / linked / indexed with one pro and con each; inode direct and indirect pointers.

Disk scheduling and I/O: polling, interrupts and DMA

Disk scheduling orders pending requests to cut head movement (SSTF, SCAN, C-SCAN, LOOK beat FCFS), and the OS talks to devices with polling, interrupts or DMA, the last letting the device copy data to memory without the CPU.

How a hard disk takes time

A magnetic disk has spinning platters divided into circular tracks, each split into sectors; the same track on all platters forms a cylinder. A read or write costs:

  • Seek time: moving the head to the right track (usually the largest part).
  • Rotational latency: waiting for the sector to rotate under the head.
  • Transfer time: reading the data.

Seek time dominates, so the OS reorders requests to reduce total head movement. SSDs have no moving parts, so seek time and rotational latency disappear and disk-scheduling algorithms matter much less (SSDs have their own issues, such as write wear and erase blocks). The algorithms below are still asked in interviews.

Disk-scheduling algorithms: one worked example

Disk with cylinders 0 to 199. The head is at cylinder 53. The request queue (in arrival order) is: 98, 183, 37, 122, 14, 124, 65, 67. We count total head movement in cylinders.

Calculations.

  • FCFS: |53−98| + |98−183| + |183−37| + |37−122| + |122−14| + |14−124| + |124−65| + |65−67| = 45 + 85 + 146 + 85 + 108 + 110 + 59 + 2 = 640.
  • SSTF: 12 (to 65) + 2 (67) + 30 (37) + 23 (14) + 84 (98) + 24 (122) + 2 (124) + 59 (183) = 236.
  • SCAN toward 0: 53→37 is 16, →14 is 23, →0 is 14, then 0→65 is 65, →67 is 2, →98 is 31, →122 is 24, →124 is 2, →183 is 59. Sum = 16 + 23 + 14 + 65 + 2 + 31 + 24 + 2 + 59 = 236.
  • C-SCAN toward 199: 53→65 is 12, →67 is 2, →98 is 31, →122 is 24, →124 is 2, →183 is 59, →199 is 16; that is 146. Return jump 199→0 is 199; then 0→14 is 14 and 14→37 is 23. Sum = 146 + 199 + 14 + 23 = 382. Books differ on whether the return jump counts; without it the figure is 183.
  • LOOK toward 0: 16 + 23 (to 14) + 51 (14→65) + 2 + 31 + 24 + 2 + 59 = 208.

FCFS is fair but wasteful (640). SSTF is greedy and can starve far-away requests when new nearby ones keep arriving. SCAN gives a bounded wait and is fairer; C-SCAN gives more uniform wait times because requests at both ends are treated alike (it only services in one direction). LOOK and C-LOOK save the useless trip to the physical end. Linux's modern I/O schedulers are more complex (and for SSDs often "none" or simple deadline-style schedulers).

How the CPU talks to I/O devices

Every device has a controller with registers (status, command, data). A device driver (kernel code) knows how to operate one kind of device and offers the OS a uniform interface. Three ways to transfer data:

MethodHowCPU costGood for
Polling (programmed I/O)CPU repeatedly checks the device's status register until it is readyHigh: busy waitingVery fast devices, very short waits
Interrupt-driven I/OCPU starts the operation and does other work; the device raises an interrupt when done and the CPU runs an interrupt handlerMedium: one interrupt per byte or blockKeyboards, network packets, mouse
DMA (direct memory access)CPU programs the DMA controller with source, destination and count; the controller moves the whole block between device and RAM; one interrupt at the endLowDisks, network cards, bulk transfers

An interrupt makes the CPU save its state, jump to the handler found through the interrupt vector table, and then resume. The timer interrupt that drives preemptive scheduling is the most important one.

Blocking, non-blocking and asynchronous I/O

  • Blocking: the call does not return until the data is ready; the process sleeps in the waiting state. Java's InputStream.read() and classic Socket work this way, so a thread is tied up per connection.
  • Non-blocking: the call returns at once, perhaps with "no data yet". The program asks again later, or uses a readiness API (select, poll, epoll on Linux) to wait on many descriptors with one thread. Java NIO's Selector and Netty (under Spring WebFlux) are built on this.
  • Asynchronous: the call returns at once and the OS notifies you when the operation has completed (Linux io_uring, Windows I/O completion ports; Java's AsynchronousChannel).

Kernel I/O support also includes buffering (hold data in memory to smooth the speed difference between device and process), caching (keep a copy of data in fast memory) and spooling (queue output for a device that serves one job at a time, such as a printer).

Rule: an interrupt handler must be short

It runs with some interrupts masked, so it only acknowledges the device and schedules the longer work for later (the "bottom half" in Linux).

Edge cases

  • Polling can be better than interrupts when the device is extremely fast and busy, since the cost of each interrupt exceeds the cost of a short spin. High-speed network stacks use a mix.
  • SSTF and SCAN assume the head position is known; modern disks and SSDs hide their geometry (logical block addresses), so the OS only approximates.
  • DMA competes with the CPU for the memory bus ("cycle stealing"), slowing the CPU slightly during transfers.

Interview: "Disk scheduling algorithms? Polling vs interrupts vs DMA?"

  • Do the 53-head example if asked: FCFS 640, SSTF 236, SCAN 236, LOOK 208. Name SSTF's starvation and why SCAN is the elevator.
  • Polling = CPU asks repeatedly; interrupt = device tells the CPU; DMA = device moves data to RAM by itself and interrupts once.
  • Blocking vs non-blocking vs async I/O, with the Java link (NIO Selector, virtual threads).

How operating-system ideas show up in backend work

Thread pools, connection pools, memory limits in containers, the OOM killer and context-switch cost are the OS concepts you meet daily as a backend developer; knowing the theory tells you what to measure and how to size things.

Thread pools and the cost of threads

Every platform thread is a kernel thread with its own stack and scheduling cost (see threads). Creating one per request wastes time and memory, and thousands of runnable threads mean constant context switching (context switch) with cold caches. So servers use a thread pool: a fixed set of reusable worker threads that take tasks from a queue, which is the producer–consumer pattern from classic problems. Embedded Tomcat in Spring Boot uses up to 200 request threads by default (property server.tomcat.threads.max), and Java's ExecutorService is the general tool (Core Java · Module 6).

How big should a pool be?

  • CPU-bound work (calculation): about the number of cores (or cores + 1). More threads only add context switches.
  • I/O-bound work (database, HTTP calls): threads spend most of their time in the waiting state, so you can have many more. A rule of thumb from Java Concurrency in Practice: threads = cores × target utilisation × (1 + wait time / compute time). For 4 cores, full utilisation and a task that waits 90 ms for every 10 ms of compute (ratio 9): 4 × 1 × (1 + 9) = 40 threads. Treat this as a starting point and measure.
  • Virtual threads (Java 21) make the one-thread-per-request style cheap for I/O-bound work, because the OS no longer pays for each waiting thread.

Connection pools and semaphores

A database connection is expensive to open and the database can serve only so many at once. A connection pool (HikariCP in Spring Boot, default maximum size 10) hands out a limited number of connections; further requests wait for one to be returned. It is exactly a counting semaphore with N permits (semaphores). Two consequences:

  • If a request holds a connection while it calls a slow service, the pool drains and all other requests block: this looks like a deadlock but is really resource starvation. Hold connections briefly.
  • A pool can deadlock if a task holding a connection needs a second connection from the same pool, and every thread does the same. Keep one connection per unit of work.

Memory limits in containers

A container does not get its own kernel; Linux cgroups limit how much memory and CPU its processes may use. If the processes in a container try to use more memory than the limit, the kernel kills one of them. Kubernetes reports this as OOMKilled, and the exit code is 137 (128 + signal 9, SIGKILL).

  • The JVM's memory is more than the heap: it also holds metaspace, thread stacks (each thread has its own stack), code cache, direct buffers and garbage-collector structures. A container limit of 512 MB with -Xmx512m will be killed, because the total exceeds the limit.
  • Modern JVMs read the container limit (container support is on by default). Setting -XX:MaxRAMPercentage (for example 75.0) sizes the heap as a fraction of the limit and leaves room for the rest. More in Core Java · Module 7.
  • CPU limits work through scheduling: a container limited to half a CPU gets throttled (it is not given time slices) when it uses more, which shows up as latency spikes under load.

The OOM killer, swap and monitoring

On a plain server, if RAM and swap run out, the kernel's OOM killer picks a process with a high score (mainly big memory users) and kills it. Typical sign: the database or your Java service vanishes with no stack trace; the kernel log (dmesg) says "Out of memory: Killed process". Do not confuse this with Java's own OutOfMemoryError, which the JVM throws when its heap is full while the OS still has memory.

Sockets also use file descriptors, so a service with a connection leak ends with "Too many open files". Leaked connections, unclosed streams and forgotten try-with-resources are the usual causes.

Other everyday connections

  • Page cache: a file read the second time is fast because the kernel cached it in RAM. "Free memory" is therefore a poor health metric; look at "available".
  • Graceful shutdown: Kubernetes sends SIGTERM; Spring Boot can finish in-flight requests (server.shutdown=graceful) before exiting (signals).
  • Race conditions in singletons: a Spring @Service is shared by all request threads, so mutable fields need the tools from the synchronization article.
  • Locks in the database: row locks and deadlock detection behave as in the deadlock articles; see DBMS theory.

Rule: bound every resource

Queues, pools, memory and open files must have limits, and callers must have timeouts. Unbounded resources fail suddenly (OOM, descriptor exhaustion); bounded ones fail early and visibly (rejected tasks, timeouts), which you can handle.

Mistake: "just add more threads"

More threads on a CPU-bound or lock-bound service increases context switches and contention without adding capacity; on a memory-limited container, each thread's stack adds to the footprint. Measure first.

Interview: "A service is slow and its CPU is only 10% - what could be wrong?"

  • Threads blocked on I/O, a slow downstream call, an exhausted connection pool, lock contention or a deadlock, or heavy swapping/GC pauses.
  • Take thread dumps, check pool metrics, vmstat for I/O wait and swap, and the GC log.
  • Tie the answer to OS ideas: waiting state, semaphores (pools), context switches, thrashing.

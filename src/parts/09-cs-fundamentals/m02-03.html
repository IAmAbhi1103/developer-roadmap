Ports and sockets

An IP address finds the machine, a port number finds the process on it, and a socket is one endpoint of a conversation, identified by IP address, port and protocol; a TCP connection is identified by the full 4-tuple of both endpoints.

Why ports exist

One computer runs many network programs at once: a browser with twenty tabs, an SSH session, a database, your Spring Boot app. The IP address gets a packet to the machine, but the OS must decide which process receives it. The port number (16 bits, 0 to 65,535) solves this. Ports belong to the transport layer: TCP and UDP each have their own separate set of 65,536 ports, so TCP port 53 and UDP port 53 are different things.

Sockets

A socket is the programming interface to the network: an endpoint that your program reads from and writes to, like a file. The OS identifies a socket by IP address + port + protocol, e.g. 203.0.113.10:443 over TCP. A server socket in the LISTEN state waits for connections. When a client connects, the OS creates a new connected socket for that client; the listening socket keeps listening.

A TCP connection is identified by the 4-tuple: (source IP, source port, destination IP, destination port). That is why 10,000 browsers can all connect to port 443 on your server at once: each connection has a different source IP or port, so the 4-tuples differ. The server uses one port, not 10,000.

Sockets in Java

Java exposes this in java.net. A minimal echo server and client (TCP):

import java.io.*;
import java.net.*;

public class EchoServer {
    public static void main(String[] args) throws IOException {
        try (ServerSocket server = new ServerSocket(5000)) {   // bind + listen
            System.out.println("Listening on 5000");
            try (Socket client = server.accept();              // blocks until connect
                 BufferedReader in = new BufferedReader(
                         new InputStreamReader(client.getInputStream()));
                 PrintWriter out = new PrintWriter(client.getOutputStream(), true)) {
                String line = in.readLine();
                out.println("echo: " + line);
            }
        }
    }
}
import java.io.*;
import java.net.*;

public class EchoClient {
    public static void main(String[] args) throws IOException {
        try (Socket socket = new Socket("localhost", 5000);    // TCP handshake here
             PrintWriter out = new PrintWriter(socket.getOutputStream(), true);
             BufferedReader in = new BufferedReader(
                     new InputStreamReader(socket.getInputStream()))) {
            out.println("hello");
            System.out.println(in.readLine());
        }
    }
}
echo: hello

The client never chooses its own port: the OS picks an ephemeral port. Spring Boot's embedded Tomcat or Netty does the same ServerSocket-style listening, with a thread pool or event loop on top.

Errors you will meet

  • java.net.BindException: Address already in use: another process (or an old instance of your app) owns that port. Find it with netstat -ano (Windows) or ss -ltnp (Linux), or change server.port.
  • java.net.ConnectException: Connection refused: the host answered, but nothing listens on that port (the OS sent a TCP RST).
  • java.net.SocketTimeoutException / "connect timed out": no answer at all, usually a firewall silently dropping packets or a wrong IP.

Mistake: "a server uses one port per client"

All clients connect to the same listening port. The server distinguishes them by the client's IP and port, and the OS creates one connected socket per client. The real limit is open file descriptors and memory, not ports.

Interview: "What is a socket? What is a port?"

TCP: handshake, teardown, sequence numbers and states

TCP is a connection-oriented, reliable, ordered byte-stream protocol; it opens a connection with a three-way handshake (SYN, SYN-ACK, ACK), numbers every byte so the receiver can acknowledge and reorder, and closes each direction separately with FIN and ACK.

What TCP gives you

TCP (Transmission Control Protocol) runs on top of unreliable IP and builds a dependable pipe for two programs. Its features:

  • Connection-oriented: a connection is set up before data moves and torn down afterwards; both sides keep state.
  • Reliable: every byte is acknowledged; lost data is retransmitted.
  • Ordered: bytes reach the application in the order sent, even if packets arrive jumbled.
  • Byte stream: no message boundaries. Two 100-byte writes may arrive as one 200-byte read; applications must frame messages (HTTP uses headers and Content-Length).
  • Flow control: the sender never overruns the receiver's buffer.
  • Congestion control: the sender slows down when the network is overloaded.
  • Full duplex: data flows both ways at once.
  • Error detection: a checksum in every segment.

The TCP header

The fixed header is 20 bytes. Fields you should know: source port and destination port (16 bits each), sequence number (32 bits), acknowledgment number (32 bits), header length, the flags (SYN, ACK, FIN, RST, PSH, URG), the window size (16 bits), checksum, and urgent pointer. Options such as MSS, window scaling and selective acknowledgments follow.

SYN
Synchronise: starts a connection and carries the initial sequence number.
ACK
The acknowledgment number field is valid; set on almost every segment after the first.
FIN
The sender has finished sending data (graceful close).
RST
Reset: abort the connection immediately (for example, port closed).
PSH
Push the data to the application now, do not wait to fill a buffer.

Sequence and acknowledgment numbers

TCP numbers bytes, not segments. Each side picks a random initial sequence number (ISN) in the handshake. The sequence number of a segment is the number of its first data byte. The acknowledgment number is the next byte the receiver expects: "I have everything before this." ACKs are cumulative.

Example: the client's data starts at sequence 1,000 and it sends 500 bytes (1,000 to 1,499). The server acknowledges with ack = 1,500. If the next segment, bytes 1,500 to 1,999, is lost but the one after it arrives, the server keeps answering ack = 1,500: duplicate ACKs that signal a gap.

The three-way handshake

  1. SYN: the client sends a segment with SYN set and its ISN x.
  2. SYN-ACK: the server replies with SYN and ACK set, its own ISN y, and ack = x + 1 (the SYN consumes one sequence number).
  3. ACK: the client acknowledges with ack = y + 1. The client may already put data in this third segment.

Why three and not two? Each side must tell the other its starting number and hear it acknowledged. That is four messages, but the server's ACK and SYN travel together, so three. Two messages would not let the server know the client received its ISN, and old duplicate SYNs from a previous connection could open a false connection. The handshake costs one RTT before data flows, which is why far-away servers feel slow on first connect and why keep-alive matters.

The four-way teardown

TCP is full duplex, so each direction is closed on its own: each side sends a FIN and gets an ACK. Usually the ACK and the second FIN are separate messages, giving four steps.

After the first FIN, the other side may keep sending (a half-close) until it is done. If the server has no more data, its ACK and FIN can be combined into one segment, which makes it look like a three-step close.

Connection states

TIME_WAIT

The side that closes first (the active closer) stays in TIME_WAIT for twice the Maximum Segment Lifetime (2 × MSL; Linux uses a fixed 60 seconds). Two reasons: (1) the last ACK might be lost, so if the peer resends its FIN the closer can ACK it again; (2) delayed packets of the old connection must die out so they are not mistaken for data of a new connection that reuses the same 4-tuple. A server making thousands of short outgoing connections can pile up TIME_WAIT sockets and run out of ephemeral ports; the usual fix is connection pooling and keep-alive, not deleting the wait.

RST and SYN queues

If a SYN arrives for a port with no listener, the OS answers with RST, and the client sees "Connection refused". A server keeps half-open connections in a SYN queue and completed ones in an accept queue until the application calls accept(). When these overflow, new clients wait or time out. A flood of fake SYNs that fills the queue is the SYN flood attack (see the security article).

Edge cases

  • Simultaneous open (both sides send SYN) and simultaneous close are legal and rare.
  • Many CLOSE_WAIT sockets on a server mean your application is not closing its sockets: a leak in your code, not a network problem.
  • A host crash leaves the peer thinking the connection is fine until it tries to send; TCP keep-alive probes or application heartbeats detect dead peers.

Interview: "Explain the TCP three-way handshake"

  • SYN, SYN-ACK, ACK with sequence and ack numbers; ISNs exchanged; one RTT cost.
  • Why not two: confirm both directions, avoid stale connections.
  • Teardown is four steps because each direction closes separately; mention TIME_WAIT.

TCP reliability, flow control and congestion control

TCP detects loss by missing ACKs (timeout or three duplicate ACKs) and retransmits; the receiver's advertised window limits how much the sender may have in flight (flow control), and the sender's congestion window grows by slow start and AIMD and shrinks on loss (congestion control).

Retransmission

The sender keeps every unacknowledged segment and starts a timer, the RTO (retransmission timeout), calculated from measured RTTs. It resends a segment in two cases:

  • Timeout: no ACK arrived before the RTO fired. This is the slow, heavy signal.
  • Fast retransmit: three duplicate ACKs for the same number arrive. Three duplicates mean later segments got through while one is missing, so the sender resends at once without waiting for the timer.

Modern TCP also uses SACK (selective acknowledgment): the receiver tells exactly which ranges it has, so the sender resends only the holes, not everything after the loss. Because of cumulative ACKs and sequence numbers, duplicates are discarded and out-of-order segments are held and reordered before delivery.

Flow control and the sliding window

A fast sender can overwhelm a slow receiver. In every ACK the receiver advertises its receive window (rwnd): how many more bytes its buffer can hold. The sender may have at most rwnd bytes sent but not yet acknowledged. This region is the sliding window; it slides right as ACKs arrive.

Worked example: receiver window 4,000 bytes, MSS 1,000. The sender sends segments 1 to 4 without waiting. The receiver ACKs segment 2 (ack = 2,001) and says window = 4,000 again, so the window slides and segments 5 and 6 may go out. If the receiving application is slow and the buffer fills, the receiver advertises window = 0; the sender stops and sends small window probes until space opens. The window field is 16 bits (at most 65,535 bytes), so the window scale option, negotiated in the handshake, allows much larger windows on fast long-distance links.

Compare with stop-and-wait, where only one segment is in flight: on a link with a 100 ms RTT that is one segment per 100 ms. A sliding window keeps the pipe full.

Congestion control

Flow control protects the receiver; congestion control protects the network. If every sender blasted at full speed, router queues would overflow, packets would be dropped, retransmissions would add more load, and throughput would collapse. TCP infers congestion from loss (and, in some variants, delay) and keeps a second limit, the congestion window (cwnd). The sender may have min(cwnd, rwnd) bytes in flight.

  1. Slow start: begin with a small cwnd (modern stacks start with 10 segments) and increase it by one segment per ACK, which doubles cwnd every RTT. Despite the name, growth is exponential. It continues until cwnd reaches the slow-start threshold (ssthresh) or a loss happens.
  2. Congestion avoidance: above ssthresh, grow by about one segment per RTT (linear). This is the additive increase.
  3. On loss: set ssthresh = cwnd / 2. After a fast retransmit (three dup ACKs), set cwnd to the new ssthresh and continue in avoidance (fast recovery). After a timeout, which signals worse trouble, set cwnd back to 1 segment and slow-start again.

Increase by one, cut by half on loss: AIMD (Additive Increase, Multiplicative Decrease). It makes competing flows converge to a fair share. The cwnd graph looks like a sawtooth.

Numerical example (units of MSS, ssthresh = 8): RTT 1: cwnd 1, RTT 2: 2, RTT 3: 4, RTT 4: 8. Now at ssthresh, RTT 5: 9, RTT 6: 10, RTT 7: 11. Three duplicate ACKs arrive at cwnd = 11: ssthresh = 11 / 2 = 5 (rounded down), cwnd = 5 and growth continues linearly. Had it been a timeout, cwnd would drop to 1 with ssthresh = 5, then slow-start up to 5.

Named algorithms: Tahoe and Reno are the classics (Reno adds fast recovery), CUBIC is the default on Linux, and BBR (from Google) estimates bandwidth and RTT rather than reacting to loss alone.

Mistake: mixing flow control with congestion control

Flow control is between the two end hosts (receiver says "slow down, my buffer is full"). Congestion control is about the routers in the middle (sender guesses "the network is full"). Interviewers ask for exactly this difference.

Real projects

You rarely tune TCP, but you feel it. A new connection starts slow, so a cold HTTPS call to a far region is slower than a warm one: reuse connections (HTTP keep-alive, JDBC and RestClient/WebClient pools). Lossy mobile networks reduce TCP throughput sharply, one reason HTTP/3 moved to QUIC.

Interview: "How does TCP ensure reliability, and what is congestion control?"

  • Sequence numbers, ACKs, checksum, retransmission (timeout and fast retransmit), ordering.
  • Flow control = receiver window; congestion control = cwnd, slow start, AIMD.
  • State the loss reactions: 3 duplicate ACKs → halve; timeout → back to 1.

UDP, TCP vs UDP and QUIC

UDP is a thin, connectionless, unreliable datagram service with an 8-byte header and no handshake; choose TCP when every byte must arrive in order, UDP when speed or low latency matter more, and QUIC when you want TCP-like reliability on top of UDP with faster setup.

UDP

UDP (User Datagram Protocol) adds almost nothing to IP: source and destination ports, a length and a checksum. That is the whole 8-byte header. Each datagram is sent independently. There is no handshake, no connection state, no acknowledgment, no retransmission, no ordering, no flow or congestion control. If a datagram is lost, UDP does not know or care. Message boundaries are preserved: one send is one datagram, one receive.

That bareness is the point. UDP has no setup delay, no head-of-line blocking from a lost packet, and the application decides what to do about loss. Typical uses:

  • DNS queries: one small question, one small answer.
  • DHCP, NTP, SNMP: short exchanges.
  • Live voice and video, online games: a late packet is useless; skipping it is better than waiting for a resend.
  • Streaming and telemetry where occasional loss is acceptable.
  • QUIC / HTTP/3: reliability rebuilt in user space on top of UDP.

The same sockets idea applies in Java: DatagramSocket and DatagramPacket send and receive UDP datagrams without any connection.

A good one-liner: TCP is a phone call (set up, confirmed, ordered); UDP is posting letters without tracking. UDP is not "bad": it hands control to the application.

QUIC and HTTP/3

QUIC is a transport protocol built on UDP, standardised in 2021 (RFC 9000), and it carries HTTP/3. It implements in user space what TCP and TLS did in the kernel: reliability, ordering, congestion control, and TLS 1.3 encryption built in. Benefits: (1) faster setup, because the transport and TLS handshakes are combined (one RTT for a new connection, and zero-RTT for a repeat one); (2) independent streams, so a lost packet only stalls the stream it belongs to, not the whole connection (fixes TCP's head-of-line blocking); (3) connection migration, since a connection ID rather than the IP/port 4-tuple identifies it, so a phone switching from Wi-Fi to mobile data keeps the session. It runs over UDP because new IP protocols would be dropped by middleboxes, and because user-space code can evolve faster than OS kernels.

Exceptions and edge cases

  • DNS normally uses UDP port 53 but switches to TCP for large responses and zone transfers.
  • UDP can be reliable if the application adds its own ACKs and retries (QUIC, many game protocols). "UDP is unreliable" means UDP itself does not provide it.
  • Some corporate firewalls block UDP 443, so HTTP/3 clients fall back to HTTP/2 over TCP.

Mistake: "TCP is always better because it is reliable"

For a video call, retransmitting a lost packet makes it arrive too late and adds delay for the packets behind it. Choose by requirement: correctness → TCP, timeliness → UDP.

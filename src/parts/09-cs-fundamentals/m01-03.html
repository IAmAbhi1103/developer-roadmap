Race conditions and the critical-section problem

When two threads or processes update shared data without coordination, the result depends on timing (a race condition); the critical-section problem asks for a protocol that gives mutual exclusion, progress and bounded waiting, implemented with help from atomic hardware instructions.

The race condition

A race condition exists when the result of a computation depends on the order in which concurrent threads run. The classic example is counter++. It looks like one step, but the CPU does three: load the value into a register, add one, store it back. If two threads interleave those steps, one update is lost.

The Java version of this bug, with a program that prints less than 2,000,000, and the fixes (synchronized, AtomicInteger) are in Core Java · Module 6. This article gives the OS theory behind those fixes.

The critical-section problem

The part of the code that accesses shared data is the critical section. A correct design wraps it like this:

do {
    entry section        // ask permission to enter
        critical section // use the shared data
    exit section         // announce that we are done
    remainder section    // everything else
} while (true);

A solution must satisfy three requirements:

  1. Mutual exclusion: if one process is in its critical section, no other can be.
  2. Progress: if no process is in its critical section and some want to enter, only the processes that are not in their remainder sections take part in deciding who goes next, and the decision cannot be postponed forever. (Nobody outside the contest may block it.)
  3. Bounded waiting: once a process has asked to enter, there is a limit on how many times others may enter before it does. This prevents starvation.

On top of these, a solution must not assume anything about the CPU speed or the number of CPUs.

Software solution: Peterson's algorithm

Peterson's solution works for exactly two processes, 0 and 1, using two shared variables: flag[2] (who wants to enter) and turn (whose turn it is if both want to). Process i treats the other process as j:

// shared: boolean flag[2] = {false, false};  int turn;
flag[i] = true;                     // I want to enter
turn = j;                           // but you go first, if you also want to
while (flag[j] && turn == j) {
    /* busy wait */
}
    /* critical section */
flag[i] = false;                    // I am done

If both set their flags at the same moment, whichever writes turn last loses and waits, so the other enters. Mutual exclusion, progress and bounded waiting all hold. The catch: modern CPUs and compilers reorder memory operations, so on real hardware it fails without memory barriers. That is why you learn it for the idea, not for production use.

Hardware support: atomic instructions

Real systems rely on instructions that execute atomically (as one indivisible step, even with other cores running):

  • Disabling interrupts works on a single CPU (nobody can preempt you) but not on multicore machines, and user programs must not be allowed to do it. The kernel uses it for very short sections.
  • Test-and-set: reads a flag, sets it to true, and returns the old value, all atomically.
  • Compare-and-swap (CAS): sets a variable to a new value only if it currently equals the expected value, and reports whether it did.
// test_and_set(x) atomically does: old = x; x = true; return old;
boolean lock = false;               // shared

// entry:
while (test_and_set(&lock)) {
    /* spin: the lock was already true */
}
    /* critical section */
// exit:
lock = false;
// executed atomically
int compare_and_swap(int *value, int expected, int new_value) {
    int old = *value;
    if (old == expected) *value = new_value;
    return old;                     // caller checks: old == expected ?
}

CAS is the building block of lock-free code. Java's AtomicInteger and the other atomic classes are built on it; the retry loop is explained in Core Java · Module 6.

The simple test-and-set lock gives mutual exclusion and progress but not bounded waiting: an unlucky process can lose the race every time. Textbook versions add a waiting array to fix that.

Spinlocks: busy waiting

A lock where a process loops until it is free is a spinlock (the waiting is called busy waiting). It wastes CPU cycles while spinning, but it avoids the cost of a context switch. That makes it a good choice only when the critical section is very short and there are several cores, as inside the kernel. On a single core a spinning process just burns its time slice while the lock holder cannot run. For longer waits, use a lock that puts the waiter to sleep (a mutex or semaphore, next article).

Rule: all three requirements must hold

A lock that gives mutual exclusion but can deadlock or starve a process is not a solution. When asked "what are the requirements of the critical-section problem", name all three: mutual exclusion, progress, bounded waiting.

Edge cases

  • A race needs sharing and mutation. Read-only shared data and thread-private data need no lock.
  • Visibility problems are separate from atomicity: without synchronization, a thread may not see another thread's write for a long time (the Java memory model topic in Module 6).
  • Peterson's algorithm is correct on an idealised machine but incorrect on real CPUs that reorder instructions.

Mistake: "a single statement is atomic"

One line of high-level code (count++, balance += x, if (!map.containsKey(k)) map.put(k, v)) is usually several machine steps. Never assume atomicity without a guarantee from the language, the library or a lock.

Interview: "What is a race condition? What is the critical-section problem?"

  • Race: outcome depends on interleaving of unsynchronised access to shared data; give the count++ load-add-store example.
  • Critical section: code touching shared data; needs mutual exclusion, progress and bounded waiting.
  • Solutions: Peterson (software, two processes), atomic hardware instructions (test-and-set, CAS), then locks, semaphores and monitors built on them.

Mutex, semaphore and monitor

A mutex is a lock owned by one thread for mutual exclusion; a semaphore is a counter used for signalling and for limiting access to a pool of identical resources; a monitor bundles a lock with condition variables, and Java's synchronized and wait/notify are exactly that.

Semaphores

A semaphore (invented by Dijkstra) is an integer variable that can be changed only through two atomic operations:

  • wait(S) (also called P, down or acquire): decrement S; if the result is negative, block the caller.
  • signal(S) (also V, up, release): increment S; if there are blocked processes, wake one up.
typedef struct { int value; list of processes waiting; } semaphore;

wait(S) {
    S.value--;
    if (S.value < 0) {
        add this process to S.waiting;
        block();                        // process goes to the waiting state
    }
}

signal(S) {
    S.value++;
    if (S.value <= 0) {
        remove a process P from S.waiting;
        wakeup(P);                      // P goes to the ready state
    }
}

When the value is negative, its magnitude is the number of waiting processes. The kernel must make wait and signal atomic themselves, typically with a short spinlock inside.

Two kinds:

  • Binary semaphore: value is 0 or 1. Used for mutual exclusion (initial value 1) or for signalling between two threads (initial value 0).
  • Counting semaphore: value 0 to N. Initialised to the number of available units of a resource, for example 10 free database connections. Each user does wait before using one and signal after.

Another use is ordering: to make B run after A, start a semaphore at 0; B does wait(s) and A does signal(s) when it is done.

import java.util.concurrent.Semaphore;

public class PoolLimit {
    // at most 3 threads may call the payment gateway at the same time
    private static final Semaphore permits = new Semaphore(3);

    static void callGateway(int id) throws InterruptedException {
        permits.acquire();                       // wait(S)
        try {
            System.out.println("request " + id + " is calling the gateway");
            Thread.sleep(100);                   // pretend work
        } finally {
            permits.release();                   // signal(S)
        }
    }

    public static void main(String[] args) {
        for (int i = 1; i <= 6; i++) {
            int id = i;
            new Thread(() -> {
                try { callGateway(id); } catch (InterruptedException e) { }
            }).start();
        }
    }
}

Only three requests are inside callGateway at any moment; the other three wait for a permit. This is also how a connection pool limits its users.

Mutex

A mutex (mutual exclusion lock) has two states, locked and unlocked, and an owner: only the thread that locked it may unlock it. It protects a critical section: lock(), work, unlock(). In Java the equivalents are synchronized and ReentrantLock.

A binary semaphore can be used as a lock, but it is not the same thing, because it has no owner. If a buggy thread calls signal without having called wait, a semaphore silently allows two threads into the critical section, while a mutex would reject the unlock. Use a mutex to protect data, a semaphore to coordinate events and counts. That sentence is the best short answer to "mutex vs semaphore".

Monitors

Semaphores are powerful but easy to misuse: swap two wait calls and you deadlock, forget a signal and everyone hangs. A monitor is a higher-level language construct that makes the common case safe. It is a module with:

  • private shared data,
  • procedures (methods) that access the data, only one thread allowed inside the monitor at a time (mutual exclusion is automatic),
  • condition variables with wait() (give up the monitor and sleep until the condition is signalled) and signal() (wake one waiting thread).

Java's synchronized is a monitor. Every object has one hidden monitor lock; synchronized methods and blocks enter it, and wait(), notify(), notifyAll() are the condition operations. One difference: a Java object has a single wait set, while a general monitor can have several condition variables (ReentrantLock with Condition provides several). Full details and code are in Core Java · Module 6.

Rule: always release what you acquire, on every path

Pair every wait/lock/acquire with exactly one signal/unlock/release, in finally in Java. A missed release means every other thread blocks forever.

Edge cases

  • Priority inversion arises with locks: a high-priority thread waits for a lock held by a low-priority one (see priority scheduling). Mutexes with priority inheritance fix it.
  • A recursive (reentrant) mutex lets the owner lock again without deadlocking itself. Java's intrinsic locks and ReentrantLock are reentrant; a plain POSIX mutex is not by default.
  • Java's Semaphore is not reentrant and has no owner: calling acquire() twice in one thread uses two permits.
  • A mutex unlocked by a non-owner is an error; a semaphore does not care who signals.

Mistake: using a semaphore as a lock and forgetting the "binary" part

A counting semaphore initialised to 2 for a "mutex" lets two threads into the critical section. Initialise to 1 only for mutual exclusion, and prefer a real lock object.

Interview: "Mutex vs semaphore" (very frequent)

  • Mutex: ownership, locking mechanism, one thread at a time, released by the owner. Semaphore: signalling mechanism with a counter, no ownership.
  • Binary semaphore (0/1) vs counting semaphore (0..N, N identical resources).
  • Give examples: mutex around a bank balance update; counting semaphore for a pool of 10 connections; semaphore starting at 0 to make thread B wait for thread A.
  • Monitor: lock plus condition variables built into the language; Java synchronized with wait/notify.

Classic synchronization problems

Producer–consumer (bounded buffer), readers–writers and dining philosophers are three standard tests of any synchronization tool; each shows a typical hazard (lost items, writer starvation, deadlock) and its standard fix.

1. Producer–consumer (bounded buffer)

A producer creates items and puts them into a fixed-size buffer; a consumer takes them out. Three rules: the producer must wait if the buffer is full, the consumer must wait if it is empty, and only one of them may change the buffer at a time. Think of Swiggy orders (produced by customers) waiting in a queue for the kitchen (consumer).

Three semaphores solve it: empty counts free slots (starts at N), full counts filled slots (starts at 0), and mutex protects the buffer (starts at 1).

semaphore mutex = 1, empty = N, full = 0;

producer() {                       consumer() {
    while (true) {                     while (true) {
        item = produce();                  wait(full);     // any item?
        wait(empty);   // free slot?       wait(mutex);
        wait(mutex);                       item = remove();
        insert(item);                      signal(mutex);
        signal(mutex);                     signal(empty);  // one more free slot
        signal(full);  // one more item     consume(item);
    }                                  }
}                                  }

Order matters: wait on empty/full before mutex. If the producer took mutex first and then found the buffer full, it would sleep while holding the lock, the consumer could never get in to remove an item, and both would be stuck forever: a deadlock.

import java.util.ArrayDeque;
import java.util.Queue;
import java.util.concurrent.Semaphore;

public class BoundedBuffer {
    private final Queue<Integer> items = new ArrayDeque<>();
    private final Semaphore empty;                       // free slots
    private final Semaphore full = new Semaphore(0);     // filled slots
    private final Semaphore mutex = new Semaphore(1);    // protects the queue

    BoundedBuffer(int capacity) { this.empty = new Semaphore(capacity); }

    void put(int item) throws InterruptedException {
        empty.acquire();
        mutex.acquire();
        try { items.add(item); } finally { mutex.release(); }
        full.release();
    }

    int take() throws InterruptedException {
        full.acquire();
        mutex.acquire();
        int item;
        try { item = items.remove(); } finally { mutex.release(); }
        empty.release();
        return item;
    }

    public static void main(String[] args) throws InterruptedException {
        BoundedBuffer buf = new BoundedBuffer(2);
        Thread producer = new Thread(() -> {
            try { for (int i = 1; i <= 5; i++) buf.put(i); }
            catch (InterruptedException e) { }
        });
        producer.start();
        for (int i = 0; i < 5; i++) {
            System.out.println("Consumed " + buf.take());
        }
    }
}

2. Readers–writers

Many threads share a data set (a product catalogue). Readers only read, so many can read together. Writers modify, so a writer needs exclusive access (no readers, no other writer). The "first readers–writers" solution gives readers priority:

semaphore rw_mutex = 1;   // exclusive access to the data
semaphore mutex = 1;      // protects read_count
int read_count = 0;

writer() {                         reader() {
    wait(rw_mutex);                    wait(mutex);
    write();                           read_count++;
    signal(rw_mutex);                  if (read_count == 1) wait(rw_mutex);
}                                      signal(mutex);
                                       read();
                                       wait(mutex);
                                       read_count--;
                                       if (read_count == 0) signal(rw_mutex);
                                       signal(mutex);
                                   }

The first reader locks writers out and the last reader lets them back in. The weakness: while readers keep arriving, writers starve. The "second" variant gives writers priority and may starve readers instead. In Java use ReentrantReadWriteLock or a concurrent collection (see Core Java · Module 6), and databases offer the same idea as shared and exclusive locks (DBMS theory).

3. Dining philosophers

Five philosophers sit round a table with a bowl of rice and one chopstick between each pair (5 chopsticks). A philosopher alternates between thinking and eating, and needs both neighbouring chopsticks to eat. The problem is a model for a process needing several resources at once.

The naive solution picks the left chopstick, then the right:

semaphore chopstick[5] = {1, 1, 1, 1, 1};

philosopher(i) {
    while (true) {
        think();
        wait(chopstick[i]);               // pick left
        wait(chopstick[(i + 1) % 5]);     // pick right
        eat();
        signal(chopstick[i]);
        signal(chopstick[(i + 1) % 5]);
    }
}

If all five pick up their left chopstick at the same time, each holds one and waits for the next one forever: a circular wait, which is a deadlock. Fixes:

  • Allow at most 4 philosophers at the table (a counting semaphore of 4): at least one can always get both chopsticks.
  • Pick up both or neither (check both under a lock or monitor). No hold-and-wait.
  • Asymmetric order: odd-numbered philosophers pick left first, even-numbered pick right first.
  • Resource ordering: number the chopsticks and always pick the lower number first. This breaks the circular wait.
import java.util.concurrent.locks.ReentrantLock;

public class Philosopher implements Runnable {
    private final int id;
    private final ReentrantLock[] chopsticks;

    Philosopher(int id, ReentrantLock[] chopsticks) {
        this.id = id;
        this.chopsticks = chopsticks;
    }

    @Override
    public void run() {
        int n = chopsticks.length;
        int first = Math.min(id, (id + 1) % n);    // always lower number first
        int second = Math.max(id, (id + 1) % n);
        for (int meal = 0; meal < 3; meal++) {
            chopsticks[first].lock();
            try {
                chopsticks[second].lock();
                try {
                    System.out.println("Philosopher " + id + " eats meal " + meal);
                } finally {
                    chopsticks[second].unlock();
                }
            } finally {
                chopsticks[first].unlock();
            }
        }
    }

    public static void main(String[] args) {
        ReentrantLock[] sticks = new ReentrantLock[5];
        for (int i = 0; i < 5; i++) sticks[i] = new ReentrantLock();
        for (int i = 0; i < 5; i++) new Thread(new Philosopher(i, sticks)).start();
    }
}

Philosopher 4 needs chopsticks 4 and 0, and picks 0 first, so the cycle of "everyone holds the left one" cannot form. The output order differs on every run, but all 15 meals complete.

Deadlock-freedom alone is not enough: a scheme can still starve a philosopher whose neighbours keep eating in turn. Fairness needs extra care.

Rule: acquire multiple locks in one global order

Whenever code needs several locks or resources, acquire them in the same order everywhere. This is the practical lesson of dining philosophers and the most useful deadlock-avoidance habit in real code.

Edge cases

  • With a buffer of size 1, producer and consumer simply alternate.
  • Readers–writers: a reader cannot upgrade to a writer while other readers are active without risking deadlock, if two readers both try to upgrade.
  • Semaphore signal counts are remembered, but monitor/condition signals are not. Mixing them up produces "lost wake-up" bugs.

Real projects

Producer–consumer is everywhere: a thread pool's task queue, a Kafka consumer, log appenders, and the HTTP server accept queue. Readers–writers appears as database shared/exclusive locks and read-write locks on caches. Dining philosophers is the model for the "transfer money from account A to B" deadlock: lock the accounts in order of account id.

Interview: "Solve producer–consumer / dining philosophers"

  • Producer–consumer: semaphores empty (N), full (0), mutex (1); wait on the counting semaphore before the mutex. In Java, say BlockingQueue.
  • Readers–writers: reader count guarded by a mutex; first reader blocks writers; mention writer starvation.
  • Philosophers: show the circular-wait deadlock, then give two fixes (limit to 4 / ordered pick-up).

Interview questions — DBMS theory

1. What is a DBMS and why use one instead of files?

A DBMS is software that stores, retrieves and protects shared data. Files give redundancy and inconsistency, no query language, no integrity rules, no atomic multi-step updates, no safe concurrent access and weak security. A DBMS solves these with one schema, constraints, SQL, transactions, locking and access control, and adds data independence.

2. Explain the three-schema architecture and data independence.

Three levels: external (user views), conceptual (the whole logical schema) and internal (physical storage). Data independence means changing one level without breaking the one above. Physical independence: change storage or add an index; the conceptual schema and programs are untouched. Logical independence: change the conceptual schema (add a column); views and programs still work. Physical is easier to achieve.

3. What are DDL, DML, DCL and TCL? Difference between DELETE, TRUNCATE and DROP?

DDL defines structure (CREATE, ALTER, DROP, TRUNCATE); DML changes data (INSERT, UPDATE, DELETE); DCL controls access (GRANT, REVOKE); TCL controls transactions (COMMIT, ROLLBACK, SAVEPOINT). DELETE removes chosen rows (with WHERE), is logged row by row and can be rolled back. TRUNCATE removes all rows quickly, keeps the table, resets identity counters and usually cannot be rolled back (PostgreSQL can). DROP removes the table itself with its data and indexes.

4. Super key vs candidate key vs primary key vs alternate key?

A super key is any attribute set that identifies rows uniquely. A candidate key is a minimal super key. The primary key is the one candidate key you choose; the other candidate keys are alternate keys. So: primary and alternate keys are candidate keys; candidate keys are super keys with nothing extra.

5. Primary key vs unique key?

Both enforce uniqueness. A table has one primary key but can have many unique keys. A primary key cannot be NULL; a unique key usually can (several NULLs in PostgreSQL and MySQL; one in SQL Server). The primary key is the row's identity and the default target of foreign keys. In InnoDB it is also the clustered index.

6. What is a foreign key? Can it be NULL or duplicate?

A foreign key is a column (set) that references the primary or a unique key of another (or the same) table to enforce referential integrity. It can be NULL (no reference) and can repeat (many children per parent). You choose the action on parent delete or update: RESTRICT / NO ACTION, CASCADE, SET NULL, SET DEFAULT.

7. Surrogate key vs natural key?

A natural key has real-world meaning (email, PAN); a surrogate key is generated and meaningless (identity number, UUID). Surrogates never change and keep joins small; natural keys can change or be reused. Common practice: surrogate primary key plus a UNIQUE constraint on the natural key.

8. What is a weak entity? How do you convert it to a table?

A weak entity has no key of its own and depends on an owner entity through an identifying relationship (a dependent of an employee). Its table includes the owner's primary key as a foreign key (usually with ON DELETE CASCADE); the primary key is the owner's key plus the weak entity's partial key.

9. How do you convert 1:1, 1:N and M:N relationships to tables?

1:1: a foreign key (UNIQUE) on either side, preferably the side with total participation. 1:N: the foreign key goes in the N side's table. M:N: a new junction table with both keys as foreign keys and a composite primary key, plus any relationship attributes. A multivalued attribute also gets its own table.

10. What is normalization and what anomalies does it remove?

Normalization decomposes tables using functional dependencies so that each fact is stored once. It removes insertion anomalies (cannot add a fact alone), update anomalies (a repeated fact is changed in some places only) and deletion anomalies (deleting one fact loses another).

11. Define 1NF, 2NF and 3NF.

1NF: atomic values, no repeating groups. 2NF: 1NF and no partial dependency (no non-prime attribute depends on part of a candidate key). 3NF: 2NF and no transitive dependency; formally, for each non-trivial X → A, X is a super key or A is prime. Short line: the key, the whole key and nothing but the key.

12. What is the difference between 3NF and BCNF?

BCNF requires every determinant of a non-trivial FD to be a super key. 3NF also allows a determinant that is not a super key if the right side is a prime attribute. The two differ only when a relation has overlapping composite candidate keys. Every BCNF relation is in 3NF, not the reverse. BCNF is always lossless but may lose dependency preservation; 3NF can be both.

13. What is a functional dependency? State Armstrong's axioms.

X → Y means equal X values force equal Y values. Axioms: reflexivity (Y ⊆ X gives X → Y), augmentation (X → Y gives XZ → YZ) and transitivity (X → Y and Y → Z give X → Z). They are sound and complete. Derived: union, decomposition (right side only), pseudo-transitivity.

14. Find the candidate keys of R(A,B,C,D) with F = { A → B, B → C }.

A and D never appear on a right side, so both are in every key. Closure of AD: A → B gives ABD; B → C gives ABCD — all attributes. So the only candidate key is AD. B and C are non-prime; A → B is a partial dependency, so the relation is only in 1NF.

15. What is a lossless-join decomposition? How do you test it?

Joining the parts returns exactly the original rows, with no spurious ones. For R split into R1 and R2 it is lossless iff R1 ∩ R2 → R1 or R1 ∩ R2 → R2, i.e. the common attributes are a key of one of the parts.

16. What is denormalization and when do you use it?

Deliberately adding redundancy (copied columns, precomputed totals) to avoid costly joins. Use it for proven read-heavy hot paths and reporting, after normalizing first, and keep the copies consistent with transactions, triggers or jobs. The cost is more complex writes and risk of inconsistency.

17. Name the relational algebra operators and their SQL equivalents.

σ (selection) = WHERE; π (projection) = SELECT columns; ∪ = UNION; − = EXCEPT; × = CROSS JOIN; ρ = AS (alias); ⋈ = JOIN; ∩ = INTERSECT; ÷ = "for all" queries. The five fundamental ones are σ, π, ∪, −, ×. Algebra uses sets; SQL uses bags, hence DISTINCT.

18. Explain ACID with an example.

In a ₹500 transfer: atomicity — debit and credit both happen or neither; consistency — constraints hold and the total stays the same; isolation — a concurrent reader never sees the half-done transfer; durability — after commit, a crash does not undo it. Atomicity and durability come from logging and recovery, isolation from locks or MVCC, consistency from constraints plus correct application logic.

19. What are the states of a transaction?

Active, partially committed, committed, failed, aborted (and terminated). Active moves to partially committed when the last statement runs, then to committed when the log is safely written. Any error sends it to failed, then aborted after rollback. An aborted transaction can be restarted or killed.

20. How do you check whether a schedule is conflict serializable?

Build a precedence graph: a node per transaction, and an edge Ti → Tj when an operation of Ti conflicts with a later operation of Tj (same item, different transactions, at least one write). A cycle means not conflict serializable; if acyclic, a topological order gives the equivalent serial schedule. Example: R1(A) R2(A) W1(A) W2(A) gives T1 → T2 and T2 → T1, a cycle.

21. Conflict serializability vs view serializability?

Conflict serializable schedules are a subset of view serializable ones. View serializability only needs the same initial reads, read-from relationships and final writes as a serial schedule, so it also accepts some schedules with blind writes that have a cycle. It is NP-complete to test, so databases enforce conflict serializability.

22. Recoverable, cascadeless and strict schedules?

Recoverable: if T2 reads from T1, T1 commits first. Cascadeless: transactions read only committed data, so no cascading rollbacks. Strict: no read or overwrite of uncommitted data. Strict ⊂ cascadeless ⊂ recoverable. Strict 2PL gives strict schedules.

23. What is two-phase locking? Strict 2PL? Does it prevent deadlock?

2PL has a growing phase (acquire locks only) and a shrinking phase (release only) and guarantees conflict serializability. Strict 2PL keeps all exclusive locks until commit or abort, so there are no cascading rollbacks. Neither prevents deadlocks; conservative 2PL (all locks up front) does but is rarely practical.

24. What is a deadlock and how is it handled?

A cycle of transactions each waiting for a lock the next holds. Handling: detection with a wait-for graph and aborting a victim (the application must retry); prevention with wait–die or wound–wait using timestamps; or lock timeouts. Reduce deadlocks by locking in a consistent order and keeping transactions short.

25. Dirty read vs non-repeatable read vs phantom read?

Dirty read: reading uncommitted data. Non-repeatable read: the same row read twice returns different values because another transaction committed an update. Phantom read: the same range query returns a different set of rows because another transaction inserted or deleted matching rows.

26. Which anomalies does each isolation level allow?

READ UNCOMMITTED: all three. READ COMMITTED: non-repeatable and phantom. REPEATABLE READ: phantom only (in the standard). SERIALIZABLE: none. PostgreSQL defaults to READ COMMITTED and MySQL InnoDB to REPEATABLE READ. Real engines differ from the table: PostgreSQL's REPEATABLE READ also prevents phantoms.

27. What is a lost update and how do you prevent it?

Two transactions read the same value and both write back a result, so the second overwrites the first. Prevent it with an atomic statement (SET qty = qty - 1), a row lock (SELECT ... FOR UPDATE), optimistic locking with a version column, or a higher isolation level that aborts the second writer.

28. What is MVCC? What is its advantage?

Multi-version concurrency control keeps several versions of each row; each transaction reads a consistent snapshot. Readers do not block writers and writers do not block readers. Old versions are removed later (VACUUM in PostgreSQL, purge in InnoDB). Snapshot isolation can still allow write skew.

29. What is write-ahead logging and how does recovery work?

WAL: log records describing a change reach disk before the changed data page, and a transaction commits once its log is flushed. After a crash, the DBMS starts from the last checkpoint: transactions with a commit record are redone (after images), those without are undone (before images). ARIES does this in analysis, redo and undo passes.

30. Clustered vs non-clustered index?

A clustered index decides the physical order of the rows (the leaf level is the table), so there is only one per table; in InnoDB it is the primary key. A non-clustered index is a separate structure with key and a pointer to the row; a table can have many. Range scans on the clustered key are fastest; non-clustered lookups need an extra hop unless the index covers the query.

31. Why do databases use B+ trees for indexes?

Nodes match disk pages and internal nodes hold only keys, so fan-out is huge and the tree is only about 3–4 levels deep even for hundreds of millions of rows. All data sits in leaves at the same depth, and linked leaves make range queries and ordering sequential. Lookups, inserts and deletes are O(log n).

32. When can an index hurt or not be used?

It hurts write-heavy tables (every index is updated), tiny tables, and low-selectivity columns. It is skipped for WHERE UPPER(col) = ..., LIKE '%x', type mismatches, and for composite indexes when the leftmost column is missing. Check with EXPLAIN.

33. SQL vs NoSQL, and what is the CAP theorem?

SQL: fixed schema, joins, strong ACID transactions, mostly vertical scaling. NoSQL: flexible schema, several models (document, key-value, wide-column, graph), built-in horizontal scaling, often weaker or tunable consistency. CAP: during a network partition a distributed store must choose consistency or availability. Pick per access pattern, not by fashion. See SQL · Module 6.

34. SQL: find the second-highest salary. 
-- portable: highest salary below the maximum
SELECT MAX(salary) FROM employee
WHERE  salary < (SELECT MAX(salary) FROM employee);

-- PostgreSQL / MySQL: skip one distinct value
SELECT DISTINCT salary FROM employee
ORDER BY salary DESC
LIMIT 1 OFFSET 1;

The first returns NULL if there is no second value; DISTINCT in the second makes ties count once. Window-function versions (DENSE_RANK) are in SQL · Module 3.

35. SQL: find and delete duplicate rows by email. 
-- find
SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1;

-- delete, keeping the row with the smallest id (PostgreSQL, SQL Server, Oracle)
DELETE FROM users
WHERE  id NOT IN (SELECT MIN(id) FROM users GROUP BY email);

MySQL rejects a subquery on the table being deleted from; wrap it in a derived table or use a self join. Afterwards add a UNIQUE constraint on email so it cannot happen again.

Cheat sheet — DBMS theory

  • DBMS over files removes redundancy, inconsistency, concurrency anomalies, integrity and security problems; gives data independence.
  • Three schemas external (views), conceptual (logical), internal (physical).
  • Physical independence change storage, nothing above breaks; logical change tables, views survive.
  • DDL / DML / DCL / TCL define / change / permit / control transactions.
  • ER to tables 1:N foreign key on the N side; M:N junction table; weak entity owner key plus partial key; multivalued attribute own table.
  • Integrity domain, entity (PK not NULL), referential (FK matches a parent or is NULL).
  • Keys super ⊃ candidate (minimal) ⊃ primary + alternate; foreign key references another table.
  • Degree number of columns; cardinality number of rows.
  • Closure X+ add right sides of FDs whose left side is inside the result until nothing changes; key if X+ is all attributes and X is minimal.
  • Key shortcut attributes never on a right side are in every key; attributes only on right sides are in none.
  • 1NF atomic; 2NF no partial dependency; 3NF no transitive dependency (X is super key or A prime); BCNF every determinant is a super key.
  • Lossless test R1 ∩ R2 is a key of R1 or R2. BCNF may lose dependencies; 3NF does not.
  • 4NF no non-trivial multivalued dependency; 5NF no join dependency beyond keys.
  • Relational algebra σ rows, π columns, ∪ − × ρ, ⋈; ÷ for "for all".
  • ACID atomic, consistent, isolated, durable; recovery handles A and D, concurrency control handles I.
  • States active → partially committed → committed; failed → aborted.
  • Conflict different transactions, same item, at least one write; precedence graph cycle means not serializable.
  • Schedules strict ⊂ cascadeless ⊂ recoverable; conflict ⊂ view serializable.
  • 2PL grow then shrink; strict 2PL holds X locks to commit; deadlock still possible.
  • Deadlock wait-for graph cycle; wait–die and wound–wait prevent; retry the victim.
  • MVCC versions and snapshots; readers do not block writers.
  • Isolation RU: all anomalies; RC: no dirty; RR: no dirty/non-repeatable; SER: none.
  • WAL log before data; commit = log flushed; redo committed, undo uncommitted; checkpoint bounds recovery.
  • Indexes clustered (one, rows ordered) vs non-clustered (many); dense per row, sparse per block; B+ tree for ranges, hash for equality only.
  • B+ tree data only in linked leaves, high fan-out, 3–4 levels for millions of rows.
  • CAP during a partition choose consistency or availability.

Practice — DBMS theory

  1. ER design (easy). Draw an ER diagram for a library: Member, Book, Loan, with cardinalities, a weak entity (Copy of a Book) and one multivalued attribute (member phone numbers). Convert it to SQL tables using the rules. Done when you have a junction table or foreign key for every relationship and composite primary keys where needed.
  2. Keys (easy). For Employee(emp_id, pan, email, name, dept_id) list two super keys that are not candidate keys, all candidate keys, the primary key you would choose, the alternate keys, and the foreign key. Done when you can justify each in one line.
  3. Closure and keys. For R(A,B,C,D,E) with F = { A → B, C → D, B → E }, find all candidate keys and the highest normal form. Done when you get key AC (A and C are never on a right side; AC+ = ABCDE) and conclude 1NF only, because A → B is a partial dependency.
  4. Normalize. Take a flat invoice(invoice_no, date, customer_id, customer_phone, product_id, product_name, unit_price, qty) where a customer has one phone and a product one name and price. Write the FDs, find the key, and decompose to 3NF. Done when each decomposed table has a key and no table repeats a customer or product fact.
  5. BCNF vs 3NF. Show that R(Student, Course, Instructor) with Instructor → Course is in 3NF but not BCNF, decompose it, and name the dependency that is lost. Done when you list the keys, check lossless join by the key test and state the lost FD.
  6. Precedence graph. Is R1(A) W1(A) R2(A) W2(A) R2(B) W2(B) R1(B) W1(B) conflict serializable? Done when you list the conflicts, draw the graph and find the cycle: edges T1 → T2 (on A) and T2 → T1 (on B), so it is not.
  7. Isolation lab. In PostgreSQL, open two psql sessions. Reproduce a non-repeatable read at READ COMMITTED and show that REPEATABLE READ prevents it. Then try to cause a dirty read at READ UNCOMMITTED and explain what you see (PostgreSQL treats it as READ COMMITTED). Done when you can narrate each step with the values seen by both sessions.
  8. Recovery by hand. A log reads: T1 start; T1 A 10→20; T1 commit; T2 start; T2 B 5→7; checkpoint with T2 active; T3 start; T3 C 1→2; T3 commit; crash. State what recovery does. Done when you say: T1 nothing (before the checkpoint), T2 undo (B back to 5), T3 redo (C = 2).
  9. Index experiment (hard). Create a table with a million rows, run a query with EXPLAIN ANALYZE before and after a B+ tree index on the filter column, then a query using LIKE '%x' and one with UPPER(col). Done when you can explain each plan using this module and SQL · Module 5.
  10. Algebra to SQL. Translate π name ( σ salary > 50000 ( Employee ⋈ Department ) ) and the "students enrolled in all courses" division to SQL. Done when both queries run and return the expected rows on sample data.

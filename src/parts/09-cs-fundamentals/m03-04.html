Indexing theory: primary, secondary, clustered, dense, sparse and hash

An index is a separate sorted (or hashed) structure that maps search-key values to row locations, turning a full scan into a few page reads at the cost of extra storage and slower writes.

The problem an index solves

Data is stored on disk in fixed-size blocks (pages). The cost of a query is mostly the number of blocks it reads. Without an index, finding one student by roll number means reading every block (a full table scan). Say a table has 1,000,000 rows and 100 rows fit in a block: that is 10,000 block reads. An index is like the index at the back of a book: a small, sorted list of (search key, pointer) entries, so you jump straight to the right page.

Classification of indexes

Textbook "primary index" means "index on the ordering key". In everyday SQL talk, "primary key index" is just the index that backs the primary key. Interviewers usually mean the textbook version when asking "primary vs secondary index".

Typical examplePrimary key in InnoDB and SQL Server Index on email
  • MySQL InnoDB: the primary key is always the clustered index. A secondary index stores the primary-key value as its pointer, so a lookup goes secondary index → primary key → row. A long primary key therefore makes every secondary index bigger.
  • PostgreSQL: tables are heaps (unordered); all indexes are non-clustered and point to a physical tuple location. The CLUSTER command rewrites a table once in index order but does not keep it that way.
  • SQL Server: you choose; the clustered index is the table.

Dense vs sparse

  • Dense index: one entry for every search-key value (every row). Works on unsorted files, so secondary indexes are always dense. Fast, but large.
  • Sparse index: one entry per block (the first key of each block). Works only when the data file is sorted by the key. Smaller; you find the right block, then search inside it.

Numbers for 1,000,000 rows, 100 rows per block, 500 index entries per index block:

No index           : up to 10,000 block reads (scan)
Sparse index       : 10,000 entries -> 20 index blocks
                     binary search 20 blocks (about 5 reads) + 1 data block = about 6 reads
Dense index        : 1,000,000 entries -> 2,000 index blocks
                     binary search (about 11 reads) + 1 data block = about 12 reads
B+ tree (multilevel): 3 levels deep -> about 3 index reads + 1 data read

A multilevel index builds an index on the index until the top fits in one block; that idea, made dynamic, is the B+ tree (next article).

Other index kinds

  • Composite (multi-column) index: on (a, b, c). It helps queries that filter on a, or a and b, or a, b and c — the leftmost prefix rule — but not on b alone.
  • Unique index: also enforces uniqueness (primary and unique constraints create one).
  • Covering index: contains every column the query needs, so the table is never touched (an "index-only scan").
  • Hash index: stores hash(key) → bucket. Finds an exact match in about one step. It cannot do ranges (>, BETWEEN), ordering or prefix matches, because hashing destroys order.
  • Bitmap index: a bit-vector per value; good for low-cardinality columns in analytics (Oracle). Full-text, spatial and partial indexes exist for special needs.

When indexes hurt

Indexes help when

  • Columns appear in WHERE, JOIN ON, ORDER BY, GROUP BY
  • The column is selective (few rows match)
  • Tables are large and read-heavy

Indexes hurt when

  • Writes dominate: every insert, update and delete must update each index
  • The table is tiny (a scan is as cheap)
  • The column has very low selectivity (a boolean flag: half the table matches)
  • You index everything: wasted storage and a confused optimizer

Mistake: writing queries that cannot use the index

  • A function on the column: WHERE UPPER(name) = 'ASHA' (use a functional index or store normalized data).
  • A leading wildcard: LIKE '%sha'.
  • An implicit type conversion, such as comparing a number column to a string.
  • Skipping the leftmost column of a composite index.

Use EXPLAIN to see whether the optimizer picks the index. Practical index design is in SQL · Module 5.

Interview angle

"What is an index and what does it cost?" Faster reads; slower writes and more storage. "Clustered vs non-clustered?" Rows ordered by index vs separate pointers; one vs many. "Dense vs sparse?" Entry per row vs entry per block. "Why can't a hash index do range queries?" Hash order is unrelated to key order.

B-tree vs B+ tree and why databases use B+ trees

A B+ tree is a balanced, wide, shallow search tree whose internal nodes only route searches and whose linked leaves hold all entries, so any lookup takes a few page reads and range scans are sequential.

Why a binary tree is wrong for disks

A binary search tree over 1,000,000 keys is about 20 levels deep; each level would be a separate disk read. Disks read whole pages (often 8 KB or 16 KB), so a tree should make each node as big as a page and hold hundreds of keys. That gives a tree with a very large fan-out (number of children), so very few levels.

B-tree

A B-tree of order m is a self-balancing tree where:

  • Every node has at most m children and (except the root) at least ⌈m/2⌉ children.
  • All leaves are at the same depth.
  • A node with k children holds k−1 keys in sorted order.
  • Keys and their data pointers are stored in all nodes, internal ones too, so a search can finish at an internal node.

B+ tree

A B+ tree is a B-tree variant:

  • Internal nodes hold only keys (signposts) and child pointers; no data.
  • Leaf nodes hold all the keys with their records (or record pointers). Every key appears in a leaf; some keys are also copied into internal nodes as routing values.
  • Leaves are linked in a list in key order.
  • All leaves are at the same depth, so every lookup costs the same number of page reads.

Search for 50: at the root, 50 is at least 30 and below 60, so go to the middle child, then find 50 in that leaf. Range BETWEEN 20 AND 60: find 20 in the first leaf, then follow the leaf links to the right until you pass 60; no need to climb back up.

Insert and split

Suppose a leaf holds at most 3 keys. Insert 10, 20, 30: one leaf [10 20 30] (also the root). Insert 40: the leaf is full, so it splits into [10 20] and [30 40], and the key 30 is copied up into a new root [30]. If a parent overflows, it splits too, and the middle key is moved up; splits can reach the root, which is the only way the tree grows taller — so it always stays balanced. Delete is the reverse: if a node falls below half full, it borrows from a sibling or merges with one.

Why databases use B+ trees

  1. Higher fan-out, shallower tree. Internal nodes carry no data, so more keys fit in a page. With 8 KB pages and about 16 bytes per (key, pointer), a node has roughly 500 children; a root with 500 children gives 250,000 leaf pages at level 3, each holding about 500 entries — roughly 125 million entries in three levels (an estimate, not an exact figure). So finding one row takes about 3–4 page reads. The top levels stay cached in memory.
  2. Predictable cost. Every search ends at a leaf at the same depth.
  3. Fast range scans and ordering. Leaves are linked, so BETWEEN, ORDER BY and "next 20 rows" are sequential reads.
  4. Full scans of the index read only the leaf list.
  5. Efficient updates. Inserts and deletes cost O(log n) page changes, with occasional splits.

Interview angle

"Why B+ tree and not a binary tree or hash?" Disk pages, high fan-out, few reads, ranges. "B tree vs B+ tree?" Data only in leaves, linked leaves. "What is the complexity of a lookup?" O(log n) with a huge base, effectively 3–4 reads.

SQL vs NoSQL quick revision and the CAP theorem

SQL databases give structured tables, joins and strong ACID guarantees; NoSQL databases trade some of that for flexible schemas and easy horizontal scaling; CAP says a partitioned distributed system must choose between consistency and availability.

The comparison

AspectSQL (relational)NoSQL
Data modelTables, rows, columnsDocument, key-value, wide-column, graph
SchemaFixed, defined up frontFlexible or schema-less
Query languageSQL (standard)Database-specific APIs or query languages
Relationships and joinsFirst-class, with foreign keys Usually embedded or handled in the application
TransactionsFull ACID multi-row, multi-tableVaries: often single-document or key; some support multi-document
ScalingMostly vertical; read replicas; sharding is harder Designed for horizontal scaling (sharding built in)
Consistency modelStrongTunable; often eventual
Best forOrders, payments, anything with strong relations Catalogues, sessions, events, feeds, caches, graphs
ExamplesPostgreSQL, MySQL, Oracle MongoDB, Redis, Cassandra, Neo4j

The lines are blurring: PostgreSQL stores JSON, MongoDB offers multi-document transactions, and many "NewSQL" systems scale SQL horizontally. "SQL vs NoSQL" is a trade-off per workload, not a war.

The four NoSQL families

  • Key-value (Redis, DynamoDB): value by key; fastest, simplest.
  • Document (MongoDB): JSON documents; nested data in one read.
  • Wide-column (Cassandra, HBase): rows with flexible columns grouped in families; huge write volume.
  • Graph (Neo4j): nodes and edges; relationship-heavy queries such as "friends of friends".

ACID vs BASE

Many NoSQL systems follow BASE: Basically Available (the system answers, even during partial failures), Soft state (state may change over time without input, as replicas sync) and Eventual consistency (if writes stop, all replicas converge). ACID gives correctness first; BASE gives availability and scale first.

CAP theorem (one-liner)

A distributed data store can provide at most two of: Consistency (every read sees the latest write), Availability (every request gets a non-error answer) and Partition tolerance (the system keeps working when the network splits). Network partitions will happen, so in practice when a partition occurs you choose C or A. A CP store (commonly said of MongoDB and HBase) refuses some requests to stay consistent; an AP store (Cassandra, DynamoDB with eventual consistency) keeps answering and may return stale data. When there is no partition you can have both; the PACELC extension adds the latency-versus-consistency trade-off that exists even then.

Interview angle

Never say "NoSQL is faster" or "SQL doesn't scale". Say: pick SQL when data is structured, relationships and transactions matter; pick a NoSQL type when the access pattern fits it (flexible documents, key lookups, huge write volume) and you can live with weaker consistency or no joins. For CAP, state "during a partition choose consistency or availability" with one example each.

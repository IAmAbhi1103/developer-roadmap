Deadlock: conditions, resource allocation graphs and prevention

A deadlock is a state where a set of processes each hold a resource and wait for one held by another in the set, so none can ever proceed; it needs four conditions together (mutual exclusion, hold and wait, no preemption, circular wait), and prevention works by making at least one of them impossible.

What is a deadlock?

A deadlock is a permanent blocking of a set of processes or threads, each waiting for a resource that another member of the set holds. Nobody can release anything, so nobody ever moves. A resource can be physical (a printer, a disk) or logical (a mutex, a file lock, a database row lock).

The everyday picture: a narrow bridge where two cars meet in the middle and neither will reverse. The software picture: thread 1 holds lock A and wants B, while thread 2 holds lock B and wants A. In banking code this is "transfer from account X to Y" running at the same time as "transfer from Y to X".

A process uses a resource in three steps: request (wait if not free), use, release.

The four necessary (Coffman) conditions

A deadlock can occur only if all four hold at the same time:

ConditionMeaningExample
Mutual exclusionAt least one resource can be used by only one process at a time.A lock, a printer
Hold and waitA process holding some resources is waiting to get more.Holds lock A, asks for lock B
No preemptionA resource can be released only voluntarily by its holder; the OS cannot take it away.You cannot yank a mutex away from a thread
Circular waitThere is a cycle P1 → P2 → ... → Pn → P1 where each waits for a resource held by the next.T1 waits for T2, T2 waits for T1

The conditions are necessary, not by themselves sufficient: with all four present a deadlock is possible; the circular wait actually closes the loop. Break any one and deadlock cannot happen. This is the key to prevention.

Resource allocation graph (RAG)

A resource allocation graph shows the state precisely. It has two kinds of nodes: processes (circles) and resources (rectangles; dots inside a rectangle are the instances of that resource). Two kinds of edges: a request edge P → R (P is waiting for R) and an assignment edge R → P (an instance of R is held by P).

Reading the graph here: P1 holds R1 and wants R2; P2 holds R2 and wants R1. The cycle P1 → R2 → P2 → R1 → P1 is a deadlock. The rules for reading any RAG:

  • No cycle → no deadlock.
  • Cycle, and every resource has a single instance → deadlock for sure.
  • Cycle, but some resources have several instances → deadlock is only possible. Example: a cycle through R1 (two instances), where the second instance is held by P3 outside the cycle. When P3 releases it, a waiting process gets it and the cycle breaks. So with multiple instances, a cycle is necessary but not sufficient.

Deadlock in Java

public class DeadlockDemo {
    private static final Object lockA = new Object();
    private static final Object lockB = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (lockA) {
                System.out.println("T1 holds A, wants B");
                pause();
                synchronized (lockB) { System.out.println("T1 got both"); }
            }
        }, "T1");
        Thread t2 = new Thread(() -> {
            synchronized (lockB) {                  // opposite order: the bug
                System.out.println("T2 holds B, wants A");
                pause();
                synchronized (lockA) { System.out.println("T2 got both"); }
            }
        }, "T2");
        t1.start();
        t2.start();
    }

    private static void pause() {
        try { Thread.sleep(200); } catch (InterruptedException e) { }
    }
}
T1 holds A, wants B
T2 holds B, wants A

All four conditions are present: the locks are exclusive, each thread holds one while waiting for the other, a synchronized lock cannot be taken away, and the wait is circular. Run jstack <pid> (or jcmd <pid> Thread.print) and it prints "Found one Java-level deadlock" with the two threads and their locks. Code can also detect it with ThreadMXBean.findDeadlockedThreads(). More Java detail and the fix are in Core Java · Module 6.

Deadlock vs starvation vs livelock

ProblemWhat happensCPU useExample / fix
DeadlockA group of processes wait for each other foreverNone: all blockedTwo locks in opposite orders. Fix: lock ordering, timeouts
StarvationOne process waits indefinitely while others progressSystem is busy; the victim never runsLow priority never scheduled; writer behind endless readers. Fix: aging, fair locks
LivelockProcesses keep changing state in response to each other but make no progressHigh: they are activeTwo people in a corridor both step aside again and again; retry loops that collide forever. Fix: random back-off

Four ways to handle deadlock

  1. Prevention: design the system so one Coffman condition can never hold.
  2. Avoidance: let all four be possible, but never enter an unsafe state (needs advance knowledge; Banker's algorithm).
  3. Detection and recovery: allow deadlocks, find them, then break them (detection and recovery).
  4. Ignore it (the ostrich algorithm, head in the sand): assume deadlocks are rare and reboot or kill when it happens. Windows and Unix general-purpose kernels largely take this approach for application-level deadlocks because the cost of prevention is higher than the damage of a rare deadlock.

Prevention: break one condition

Break thisHowDrawback
Mutual exclusionMake resources sharable (read-only files, lock-free structures)Impossible for inherently exclusive resources like a printer or a write lock
Hold and waitRequest all resources at once before starting, or release everything before asking for moreLow resource utilisation; starvation of processes needing popular resources; may not know needs in advance
No preemptionIf a request cannot be granted, the process releases what it holds and retries later; or the OS preempts the holderWorks for CPU state and memory, not for printers or half-finished updates
Circular waitGive all resources a global number; processes must request in increasing orderAwkward to impose; unnatural order for the application

Breaking circular wait by lock ordering is the most practical, and it is what you do in real code. The deadlock above disappears if both threads take lockA before lockB. A transfer between two accounts can lock the account with the smaller id first. Another practical technique is ReentrantLock.tryLock(timeout): if the second lock cannot be had in time, release the first and retry. That breaks no-preemption/hold-and-wait voluntarily. Beware that retry loops with identical timing can cause livelock, so add a random delay.

Rule: all four conditions must hold at once

If an interview question asks "which condition would you remove?", the answer in practice is circular wait (lock ordering), because the other three are usually part of the problem definition.

Edge cases

  • A single thread can deadlock with itself on a non-reentrant lock (locking twice). Java's intrinsic locks are reentrant, so this does not happen there.
  • Deadlock is not only about locks: a full pipe plus a waiting parent, a thread pool whose tasks wait for other tasks in the same pool (thread starvation deadlock), and database row locks can all deadlock.
  • Databases detect deadlocks themselves and abort one transaction (see DBMS theory).

Mistake: confusing a cycle with a certain deadlock

A cycle in a resource allocation graph with multi-instance resources does not prove deadlock. Check whether a process outside the cycle can free an instance.

Interview: "What is deadlock? What are the necessary conditions? How do you prevent it?"

  • Define it with a two-lock example. List the four Coffman conditions by name and meaning.
  • Give the four strategies: prevention, avoidance, detection and recovery, ignore. For each prevention row, name the drawback.
  • Show you know the practical fix: global lock ordering and tryLock with timeout.
  • Distinguish deadlock, starvation and livelock.

Deadlock avoidance and the Banker's algorithm

The Banker's algorithm grants a request only if the system stays in a safe state, meaning there is an order in which every process can still finish; it needs each process's maximum demand declared in advance and is checked with the safety algorithm.

Safe and unsafe states

Avoidance needs extra information: before running, each process declares the maximum number of instances of each resource it may ever need. The OS then checks every request against the current state.

  • A state is safe if there is at least one safe sequence <Pa, Pb, ...> such that each process can get its remaining need from what is free plus what the earlier processes in the sequence will give back when they finish.
  • A state is unsafe if no safe sequence exists. Unsafe does not mean deadlocked yet; it means deadlock is possible, depending on future requests.
  • A deadlocked state is always unsafe. The OS keeps the system out of unsafe states.

The banker analogy: a bank never lends cash in a way that leaves it unable to satisfy all its customers' maximum credit lines one after another.

The data structures

For n processes and m resource types:

StructureSizeMeaning
Availablevector of mFree instances of each resource type right now
Maxn × mMaximum demand of each process
Allocationn × mInstances each process currently holds
Needn × mRemaining need: Need = Max − Allocation

The safety algorithm

  1. Set Work = Available and mark every process unfinished.
  2. Find an unfinished process Pi with Need[i] ≤ Work (every resource type). If none exists, go to step 4.
  3. Pretend Pi runs to completion and returns its resources: Work = Work + Allocation[i]; mark Pi finished. Go back to step 2.
  4. If every process is finished, the state is safe (the order you picked is a safe sequence). Otherwise it is unsafe.

Worked example: is the state safe?

The system has three resource types A, B, C with 10, 5 and 7 instances in total, and five processes. Current snapshot:

ProcessAllocation (A B C)Max (A B C)Need = Max − Allocation
P00 1 07 5 37 4 3
P12 0 03 2 21 2 2
P23 0 29 0 26 0 0
P32 1 12 2 20 1 1
P40 0 24 3 34 3 1

Available. Allocated totals: A = 0 + 2 + 3 + 2 + 0 = 7, B = 1 + 0 + 0 + 1 + 0 = 2, C = 0 + 0 + 2 + 1 + 2 = 5. So Available = (10 − 7, 5 − 2, 7 − 5) = (3, 3, 2).

Safety check. Start with Work = (3, 3, 2).

StepChooseNeed ≤ Work?Work after releasing Allocation

All five finish and the final Work (10, 5, 7) equals the total resources, a good sanity check. The state is safe with safe sequence <P1, P3, P4, P0, P2>. Other safe sequences exist; one is enough. (At the start P0, P2 and P4 cannot go first, because their needs exceed (3,3,2).)

The resource-request algorithm

When process Pi asks for Request[i]:

  1. If Request ≤ Need[i] is false, raise an error: the process exceeded its declared maximum.
  2. If Request ≤ Available is false, Pi must wait: the resources are not free.
  3. Otherwise pretend to grant it: Available −= Request; Allocation[i] += Request; Need[i] −= Request.
  4. Run the safety algorithm on the pretend state. If safe, make the grant permanent. If unsafe, undo the pretend change and make Pi wait.

Request 1: P1 asks for (1, 0, 2). Check: (1,0,2) ≤ Need (1,2,2) yes; (1,0,2) ≤ Available (3,3,2) yes. Pretend: Available = (2,3,0), P1 Allocation = (3,0,2), P1 Need = (0,2,0). Safety with Work = (2,3,0): P1 can go (needs (0,2,0)) → Work (5,3,2); P3 (0,1,1) → (7,4,3); P4 (4,3,1) → (7,4,5); P0 (7,4,3) → (7,5,5); P2 (6,0,0) → (10,5,7). Safe, sequence <P1, P3, P4, P0, P2>. The request is granted.

Request 2 (from the new state): P0 asks for (0, 2, 0). Check: (0,2,0) ≤ Need (7,4,3) yes; (0,2,0) ≤ Available (2,3,0) yes. Pretend: Available = (2,1,0), P0 Allocation = (0,3,0), P0 Need = (7,2,3). Safety with Work = (2,1,0): P0 needs (7,2,3) no; P1 needs (0,2,0), B: 2 > 1 no; P2 needs (6,0,0) no; P3 needs (0,1,1), C: 1 > 0 no; P4 needs (4,3,1) no. Nobody can finish: unsafe, so the request is denied and P0 waits, even though the resources are physically free.

That last point is the cost of avoidance: it can delay a process that, in hindsight, would not have deadlocked.

Cost and limits

  • Running the safety check takes roughly O(m × n²) operations per request.
  • It needs the maximum demand known up front, a fixed number of processes and resources, and processes that always release what they hold. Real systems rarely satisfy these, so general-purpose OSes do not use the Banker's algorithm. It is mainly an exam and design-thinking tool, though the idea (check safety before granting) is used in some resource managers.

Rule: Banker's algorithm checks, in order, Request ≤ Need, Request ≤ Available, then safety

Do all three. Skipping the first check lets a process exceed its declared maximum; skipping the last is simply prevention by guesswork.

Edge cases

  • Unsafe is not deadlock: an unsafe state may never actually deadlock if processes happen to release resources early. Avoidance is conservative.
  • Several different safe sequences may exist; any of them proves safety. Do not lose marks for finding a different one.
  • For a single-instance resource, avoidance can use a claim edge in the resource allocation graph instead: grant a request only if converting the claim edge to an assignment edge creates no cycle.

Mistake: using Max instead of Need in the safety check

Compare Need (what the process still wants) with Work, never Max. Also remember to add the process's Allocation (not Need) back to Work when it finishes.

Interview: "Explain the Banker's algorithm"

  • Avoidance: grant a request only if the resulting state is safe. Safe = a sequence exists in which every process can finish.
  • Four structures: Available, Max, Allocation, Need = Max − Allocation.
  • Walk through the safety algorithm with Work and the Need ≤ Work test; then the request algorithm.
  • Limits: needs maximum demands in advance; overhead; unsafe does not mean deadlocked.

Deadlock detection and recovery

Instead of preventing deadlock, the system lets it happen, periodically searches for it (a cycle in a wait-for graph, or a Banker-style check for multi-instance resources) and then breaks it by terminating processes or preempting resources.

Detection with single-instance resources: the wait-for graph

When every resource has one instance, simplify the allocation graph by removing the resource nodes. Draw an edge Pi → Pj if Pi is waiting for a resource held by Pj. This is the wait-for graph. The system runs a cycle-detection algorithm on it from time to time (depth-first search, O(n²) in the number of processes in the worst case). A cycle means a deadlock, and the processes on the cycle are the deadlocked ones.

Database engines work this way: the lock manager keeps a graph of which transaction waits for which, finds a cycle and aborts one transaction (the "victim"), and your application sees a deadlock error and must retry. See DBMS theory for transactions and locking.

Detection with multiple instances

With several instances of a resource, a cycle is not enough, so a variant of the Banker's safety algorithm is used. It has Available, Allocation and a Request matrix (what each process is currently waiting for). It optimistically assumes a process that can be satisfied now will finish and release everything, which is a way of asking "is there any order in which everyone can finish?"

  1. Set Work = Available. For each process, mark it finished if its Allocation is all zero, else unfinished.
  2. Find an unfinished Pi with Request[i] ≤ Work. If none, go to step 4.
  3. Work = Work + Allocation[i]; mark Pi finished; go to step 2.
  4. Any process still unfinished is deadlocked.

Worked example. Resources A, B, C with 7, 2, 6 instances; five processes:

ProcessAllocation (A B C)Request (A B C)
P00 1 00 0 0
P12 0 02 0 2
P23 0 30 0 0
P32 1 11 0 0
P40 0 20 0 2

Allocated totals: A = 0 + 2 + 3 + 2 + 0 = 7, B = 1 + 0 + 0 + 1 + 0 = 2, C = 0 + 0 + 3 + 1 + 2 = 6. So Available = (0, 0, 0). Work = (0,0,0):

  • P0: Request (0,0,0) ≤ Work: yes → Work = (0,1,0).
  • P2: Request (0,0,0) ≤ (0,1,0): yes → Work = (3,1,3).
  • P3: Request (1,0,0) ≤ (3,1,3): yes → Work = (5,2,4).
  • P1: Request (2,0,2) ≤ (5,2,4): yes → Work = (7,2,4).
  • P4: Request (0,0,2) ≤ (7,2,4): yes → Work = (7,2,6).

Everyone can finish (for example in the order P0, P2, P3, P1, P4), so there is no deadlock. Now suppose P2 makes one extra request for (0, 0, 1). Work starts at (0,0,0): only P0 can finish (Work becomes (0,1,0)). P1 needs (2,0,2), P2 needs (0,0,1), P3 needs (1,0,0), P4 needs (0,0,2): none fits within (0,1,0). So P1, P2, P3 and P4 are deadlocked.

When to run detection

  • On every request that cannot be granted immediately: finds deadlock as early as possible and identifies the process that caused it, but costs a lot of CPU.
  • At fixed intervals (say every hour) or when CPU utilisation drops below a threshold (a deadlock stops useful work): cheaper, but you may not know which process closed the cycle.

Recovery

Once a deadlock is found, there are two families of recovery.

1. Process termination

  • Abort all deadlocked processes: certain to break it, but throws away all their work.
  • Abort one at a time until the cycle disappears: less waste, but the detection algorithm runs after every abort.

Choosing the victim: lowest priority, least CPU time used so far, fewest resources held, closest to finishing, number of other processes that must be aborted too, and whether it is interactive or batch.

2. Resource preemption

  • Select a victim (minimise cost, as above).
  • Rollback: return the victim to a safe earlier state (a checkpoint) from which it can restart; databases roll back the aborted transaction.
  • Avoid starvation: if the same process is always chosen as the victim, it never finishes. Include the number of rollbacks in the cost, so a process already rolled back often is not picked again.

Detection in Java and in practice

import java.lang.management.ManagementFactory;
import java.lang.management.ThreadInfo;
import java.lang.management.ThreadMXBean;

public class DetectDeadlock {
    // call this from a monitoring thread, for example once every few seconds
    static void check() {
        ThreadMXBean bean = ManagementFactory.getThreadMXBean();
        long[] ids = bean.findDeadlockedThreads();      // null if none
        if (ids != null) {
            for (ThreadInfo info : bean.getThreadInfo(ids)) {
                System.out.println("Deadlocked: " + info.getThreadName()
                        + " waits for " + info.getLockName()
                        + " held by " + info.getLockOwnerName());
            }
        }
    }
}

Java can detect a deadlock but cannot recover automatically; you cannot safely kill a thread, so the usual recovery is to restart the service. That is why the best strategy for application code is prevention through lock ordering and timeouts, with a thread dump (jstack) taken when a service hangs. Spring Boot Actuator can expose thread dumps; see Spring Boot · Module 6.

Rule: the wait-for graph is valid only for single-instance resources

For multi-instance resources use the Banker-style detection with the Request matrix. A cycle alone is not a proof there.

Edge cases

  • Processes that do not hold anything (Allocation all zero) cannot be part of a deadlock, which is why step 1 marks them finished.
  • A thread waiting on I/O or a sleep is not deadlocked even if it has been waiting a long time; deadlock needs a circular wait among the processes themselves.
  • Rolling back a process that has already produced external effects (sent an email, charged a card) is not always possible; only systems with transactions or idempotent operations recover cleanly.

Real projects

You meet deadlock recovery in databases: PostgreSQL reports "deadlock detected" and aborts one transaction; the application should catch the error and retry the whole transaction. In services, a hung request thread pool is often a deadlock or a stuck downstream call: take two thread dumps a few seconds apart and compare. Timeouts on every lock, query and HTTP call turn a permanent deadlock into a failed request.

Interview: "How do you detect and recover from deadlock?"

  • Detection: cycle in the wait-for graph (single instances) or the Banker-style algorithm with a Request matrix (multiple instances).
  • Recovery: abort all deadlocked processes or one at a time; or preempt resources with rollback. Mention victim selection and starvation of the victim.
  • State the trade-off against prevention and avoidance, and the ostrich approach used by most general-purpose systems.

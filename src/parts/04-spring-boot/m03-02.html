Spring Data repositories and derived queries

You declare an interface that extends JpaRepository; Spring Data creates the implementation, gives you CRUD and paging for free, and turns method names such as findByEmail into queries.

The repository hierarchy

InterfaceAdds
Repository<T, ID>Nothing: a marker. Extend it to expose only the methods you choose.
CrudRepositorysave, saveAll, findById, existsById, findAll, count, deleteById, delete, deleteAll
ListCrudRepositorySame as above but returns List instead of Iterable
PagingAndSortingRepositoryfindAll(Sort), findAll(Pageable)
JpaRepositoryJPA extras: flush, saveAndFlush, deleteInBatch-style methods, getReferenceById

In Spring Data 3.x, PagingAndSortingRepository no longer extends CrudRepository, which is why ListCrudRepository and ListPagingAndSortingRepository exist; JpaRepository combines them so you get everything.

Using it

public interface UserRepository extends JpaRepository<User, Long> {

    Optional<User> findByEmail(String email);

    boolean existsByEmail(String email);
}

No @Repository annotation is needed; Boot's auto-configuration scans for interfaces that extend a Spring Data repository (starting at the package of your @SpringBootApplication class). At startup Spring creates a proxy that implements the interface, backed by SimpleJpaRepository. Exceptions are translated into Spring's DataAccessException hierarchy.

User saved = repo.save(user);                 // insert or update
Optional<User> one = repo.findById(5L);        // SELECT ... where id=?
List<User> all = repo.findAll();              // SELECT all (careful on big tables)
Page<User> page = repo.findAll(PageRequest.of(0, 20, Sort.by("name")));
long n = repo.count();
boolean has = repo.existsById(5L);
repo.deleteById(5L);                          // loads the entity, then DELETE
repo.saveAll(users);                          // one persist/merge per element

deleteById loads the entity first (so cascades and lifecycle callbacks work). deleteAllInBatch() and deleteAllByIdInBatch(ids) issue a single bulk DELETE and skip callbacks and cascades. Paging was introduced in module 2; the same Pageable works on every repository method below.

Derived queries: the method name is the query

Spring Data parses the method name. The prefix says what to do (find…By, read…By, get…By, query…By, count…By, exists…By, delete…By), and the part after By is a list of conditions on entity properties, joined by And / Or. A wrong property name fails at startup, not at runtime, which is a big advantage.

Return types

Return typeMeaning

List<T>, Set<T>All results, loaded in memory

Use Slice for "load more" or infinite scroll when the total count is not shown; the count query on a big table can be slower than the page itself.

Limits of derived queries

Names are checked at startup and are great for one to three conditions. After that they become unreadable: findByStatusAndCityAndExperienceLessThanEqualAndSalaryMaxGreaterThanEqualOrderByPostedAtDesc. Switch to @Query (next article) for long or join-heavy queries, and to Specifications for optional filters. Derived queries also cannot do joins with conditions on collections, aggregations, or group by.

Rules

  • Property names in the method must match entity field names (postedAt, not posted_at).
  • Parameters are bound by position, in the order of the conditions in the name.
  • deleteBy… and modifying queries need a transaction; put @Transactional on the service method.
  • A repository for an aggregate root only. Do not create one repository per table (e.g. no ApplicationItemRepository if items are only reached through their parent).

Mistakes

  • Using List<T> findAll() on a table with millions of rows. Always page.
  • Returning T (not Optional) for a "find one" and then getting null or an exception when it is missing.
  • Using deleteByStatus for a mass delete: it loads every entity and deletes row by row (N+1 deletes). Use a @Modifying @Query instead.
  • Expecting Like to add wildcards. Like uses your string as is; Containing adds them.

Exceptions

  • PropertyReferenceException: No property 'x' found for type 'Job' — typo in a derived method; the app fails to start.
  • IncorrectResultSizeDataAccessException — a single-result method found two rows.
  • InvalidDataAccessApiUsageException: no transaction — deleteBy… or a modifying query outside a transaction (TransactionRequiredException inside).
  • DataIntegrityViolationException — unique or foreign-key violation on save; map it to HTTP 409 (module 2).

Interview angle

"How does Spring Data create a repository with no implementation?" At startup it builds a JDK proxy for the interface, backed by SimpleJpaRepository; method names are parsed into queries (PartTree) and validated against the entity. "Page vs Slice?" Page runs an extra count query; Slice does not. "findAll vs findAll(Pageable)?" Memory and speed on large tables.

@Query, projections, Specifications and Query by Example

When a method name is too long, write the query with @Query (JPQL or native SQL); return small DTO projections for reads; use Specifications to build dynamic filters from optional parameters.

JPQL with @Query

JPQL (Jakarta Persistence Query Language) looks like SQL but works on entities and fields, not tables and columns. You write from Job j where j.city = :city, and Hibernate translates it into SQL for your database. That is why JPQL is portable.

public interface JobRepository extends JpaRepository<Job, Long> {

    @Query("""
           select j from Job j
           where j.status = :status
             and (:city is null or lower(j.city) = lower(:city))
             and j.salary.max >= :minSalary
           order by j.postedAt desc
           """)
    List<Job> search(@Param("status") JobStatus status,
                     @Param("city") String city,
                     @Param("minSalary") BigDecimal minSalary);

    @Query("select j from Job j join j.company c where c.name = :company")
    List<Job> findByCompanyName(@Param("company") String company);
}
  • Use the entity name (Job) and field names (j.postedAt), not job and posted_at.
  • Use named parameters :status with @Param("status"). Positional ?1 works but breaks silently when you reorder arguments. (With -parameters compiler flag, which Boot's Maven/Gradle plugins enable, @Param is optional; keeping it is safer.)
  • JPQL is validated at startup, so a typo fails fast.
  • The (:city is null or ...) trick works for a few optional filters; it can hurt index use. For many filters use Specifications.

Native SQL

@Query(value = """
        select * from job
        where to_tsvector('english', title || ' ' || description)
              @@ plainto_tsquery('english', :text)
        """, nativeQuery = true)
List<Job> fullTextSearch(@Param("text") String text);

@Query(value = "select * from job where status = :s",
       countQuery = "select count(*) from job where status = :s",
       nativeQuery = true)
Page<Job> findPageNative(@Param("s") String status, Pageable pageable);

Native queries use table and column names and database-specific features, and are not checked at startup. They do not apply Sort from a Pageable reliably; give a countQuery and write the order by yourself. Use them for window functions, full-text search, jsonb and tuned reports.

Sorting and paging with @Query

@Query("select j from Job j where j.company.id = :companyId")
Page<Job> findByCompany(@Param("companyId") Long companyId, Pageable pageable);

// call:
jobRepository.findByCompany(7L,
        PageRequest.of(0, 10, Sort.by(Sort.Direction.DESC, "postedAt")));

Spring Data appends order by from the Sort and builds the count query from your query. If the query is complex (joins, distinct, group by), pass your own countQuery. Sort property names are entity fields in JPQL. Never concatenate user input into the query string; sort fields from the client must be checked against an allow-list.

@Modifying: UPDATE and DELETE queries

@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("update Job j set j.status = 'CLOSED' where j.closingDate < :today")
int closeExpired(@Param("today") LocalDate today);     // returns rows changed

Call it from a @Transactional service method. A bulk statement runs directly in the database and bypasses the persistence context: entities already loaded in memory still show the old values. clearAutomatically = true clears the context after the update so the next read hits the database; flushAutomatically = true flushes pending changes first. Bulk statements also skip @Version, lifecycle callbacks and auditing, unless you handle them yourself. One UPDATE for 100,000 rows beats loading and changing 100,000 entities.

Projections: read only what you need

Loading an entire Job (with description text and relationships) to show a list of titles wastes memory and time. A projection returns only chosen fields.

// 1. Interface-based (closed projection): getters named like entity fields
public interface JobSummary {
    Long getId();
    String getTitle();
    String getCity();
}
List<JobSummary> findByStatus(JobStatus status);   // derived query, selects 3 columns

// 2. Record / DTO-based
public record JobCard(Long id, String title, String companyName) {}

List<JobCard> findCardsByStatus(JobStatus status);   // derived queries can return DTOs too

@Query("""
       select new com.example.jobs.job.JobCard(j.id, j.title, c.name)
       from Job j join j.company c
       where j.status = :status
       """)
List<JobCard> cards(@Param("status") JobStatus status);   // constructor expression
select j.id, j.title, c.name
from job j join company c on c.id = j.company_id
where j.status = ?

Projections are also a way to dodge the N+1 problem (next module topics): a DTO query with an explicit join reads exactly what the response needs in one SQL statement.

Specifications: dynamic filters

The "search jobs" screen has optional filters: city, minimum salary, keyword, status. Writing one method per combination is impossible. A Specification is a small reusable predicate; you combine the ones you need. Make the repository also extend JpaSpecificationExecutor<Job>.

public interface JobRepository
        extends JpaRepository<Job, Long>, JpaSpecificationExecutor<Job> { }

public final class JobSpecs {
    private JobSpecs() { }

    public static Specification<Job> hasStatus(JobStatus status) {
        return (root, query, cb) -> cb.equal(root.get("status"), status);
    }
    public static Specification<Job> inCity(String city) {
        return (root, query, cb) ->
                cb.equal(cb.lower(root.get("city")), city.toLowerCase());
    }
    public static Specification<Job> titleContains(String text) {
        return (root, query, cb) ->
                cb.like(cb.lower(root.get("title")), "%" + text.toLowerCase() + "%");
    }
    public static Specification<Job> minSalary(BigDecimal min) {
        return (root, query, cb) ->
                cb.greaterThanOrEqualTo(root.get("salary").get("max"), min);
    }
}

// in the service
Specification<Job> spec = Specification.where(JobSpecs.hasStatus(JobStatus.OPEN));
if (city != null && !city.isBlank()) spec = spec.and(JobSpecs.inCity(city));
if (text != null && !text.isBlank()) spec = spec.and(JobSpecs.titleContains(text));
if (min != null) spec = spec.and(JobSpecs.minSalary(min));

Pageable pageable = PageRequest.of(0, 20, Sort.by("postedAt").descending());
Page<Job> page = jobRepository.findAll(spec, pageable);

Each lambda gets root (the entity, like from Job j), query and the CriteriaBuilder cb. The builder produces a type-aware, injection-safe query: user text goes in as a bound parameter. The attribute names are strings, so a typo fails at runtime; the JPA static metamodel (Job_.status) gives compile-time safety if you generate it. Combining with and/or/not reads well.

Query by Example (QBE), briefly

Job probe = new Job();
probe.setCity("Pune");
ExampleMatcher matcher = ExampleMatcher.matching()
        .withIgnoreCase()
        .withStringMatcher(ExampleMatcher.StringMatcher.CONTAINING);

QBE builds a query from a filled-in "probe" object. It is quick for simple equality and string matching on non-null fields, but it cannot express ranges, or or nested collections. Most real projects choose Specifications (or QueryDSL / jOOQ for heavy reporting).

Mistakes

  • Table names in JPQL: from job works only if it happens to match the entity name. Think entities.
  • Forgetting @Modifying on an update query: an InvalidDataAccessApiUsageException at runtime (the query is run as a SELECT and the DML is rejected).
  • Concatenating user input into a JPQL or native string: SQL/JPQL injection. Always bind parameters.
  • Reading entities after a bulk update without clearAutomatically: you see stale values.
  • Projection getter names that do not match fields: null values, or startup errors for constructor expressions with the wrong signature.

Interview angle

"JPQL vs native?" JPQL is portable and entity-based, validated at startup; native is raw SQL, not portable, for special features. "Why use projections?" Fewer columns, less memory, no lazy loading, avoids N+1. "How do you build a search with optional filters?" Specifications (or Criteria API) combined with and, with paging. "After a bulk update, why are my entities stale?" The persistence context was bypassed; clear it.

Relationships: owning side, mappedBy, cascade and orphanRemoval

A relationship is stored as a foreign key; the entity whose table holds that column is the owning side, mappedBy marks the inverse side, and cascade and orphanRemoval decide what happens to children when the parent changes.

The four relationship types

AnnotationMeaningDatabase shapeExample
@ManyToOneMany rows point to oneFK column on the "many" tableJob → Company
@OneToManyOne row has many childrenFK on the child table (mirror of ManyToOne)Company → Jobs
@ManyToManyMany to manyA join table with two FKsJob ↔ Tag
@OneToOneOne to oneFK (unique) on one side, or shared primary keyUser → Profile

Every relationship can be unidirectional (only one entity has a field) or bidirectional (both have one). The database has just one foreign key either way. In bidirectional relations, two Java fields describe one FK, so JPA needs to know which field is "the real one".

The owning side and mappedBy

The owning side is the one that controls the foreign key column: when you change it, Hibernate writes the FK. It is always the side whose table contains the foreign key: the @ManyToOne side. The other side is the inverse side, marked with mappedBy = "fieldNameOnTheOwner"; changes made only on the inverse side are ignored when saving.

@Entity
public class Company {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;

    @OneToMany(mappedBy = "company", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Job> jobs = new ArrayList<>();    // inverse side

    public void addJob(Job job) {                       // keep both sides in sync
        jobs.add(job);
        job.setCompany(this);
    }
    public void removeJob(Job job) {
        jobs.remove(job);
        job.setCompany(null);
    }
}

@Entity
public class Job {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String title;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "company_id", nullable = false)  // owning side: the FK
    private Company company;
}

@JoinColumn names the FK column (the default would be company_id anyway). Without mappedBy, a @OneToMany becomes its own owning side and Hibernate creates a hidden join table (company_jobs) or, with @JoinColumn on the many side, extra UPDATE statements. Both are usually unwanted.

Helper methods keep both sides in sync

In memory, Java does not update the other side for you. If you only call company.getJobs().add(job), job.getCompany() stays null, and since Job is the owner, the FK is saved as NULL (or the insert fails). Always change both sides in one place, with addJob/removeJob methods, and avoid exposing the raw list for modification (return Collections.unmodifiableList(jobs)).

Unidirectional vs bidirectional

  • Prefer unidirectional @ManyToOne only: Job.company exists, Company.jobs does not. You can still ask jobRepository.findByCompanyId(id) with paging. It is simpler, avoids sync bugs and JSON loops, and avoids loading big collections.
  • Add the @OneToMany side only when the parent really owns a small child list and cascading is useful (an Order with its OrderItems). A company with 50,000 jobs should never be loaded through company.getJobs().
  • Avoid a unidirectional @OneToMany without mappedBy: it generates inefficient SQL.

Cascade types

Cascade says "when I do this to the parent, do it to the children too".

CascadeTypeEffect
PERSISTSaving the parent (persist) saves new children
MERGEMerging the parent merges the children
REMOVEDeleting the parent deletes the children
REFRESH, DETACHPassed to children on refresh / detach
ALLAll of the above

Cascade is for composition: children that cannot exist without the parent and are not shared (an order and its items; a job and its screening questions). Do not cascade across independent aggregates: deleting a Company must not silently delete Users, and an Application must not cascade REMOVE to its Job.

orphanRemoval = true deletes a child when it is removed from the parent's collection (company.getJobs().remove(job) → DELETE), even if the parent itself stays. Use it only for true compositions. Do not replace the collection object (setJobs(newList)) on an orphanRemoval collection: Hibernate throws HibernateException: A collection with cascade="all-delete-orphan" was no longer referenced. Clear and addAll instead.

Never CascadeType.REMOVE (or ALL) on @ManyToMany

Deleting one Job would delete every Tag it links to, although other jobs use those tags. The same for REMOVE on a @ManyToOne: deleting a job would delete its company. Rule: cascade flows from parent to owned children only.

@ManyToMany and the join table

@Entity
public class Job {
    // ...
    @ManyToMany
    @JoinTable(name = "job_tag",
            joinColumns = @JoinColumn(name = "job_id"),
            inverseJoinColumns = @JoinColumn(name = "tag_id"))
    private Set<Tag> tags = new HashSet<>();

    public void addTag(Tag tag)    { tags.add(tag);    tag.getJobs().add(this); }
    public void removeTag(Tag tag) { tags.remove(tag); tag.getJobs().remove(this); }
}

@Entity
public class Tag {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;

    @ManyToMany(mappedBy = "tags")          // inverse side
    private Set<Job> jobs = new HashSet<>();
}
create table job_tag (
    job_id bigint not null references job(id),
    tag_id bigint not null references tag(id),
    primary key (job_id, tag_id)
);

Use Set for @ManyToMany: removing from a List makes Hibernate delete all join rows of that owner and re-insert the remaining ones; a Set deletes just one row. For @OneToMany a List without @OrderColumn is a "bag" (unordered, duplicates allowed); a Set avoids the MultipleBagFetchException trap (see fetching pitfalls), but then equals/hashCode must be correct (entities).

Many-to-many with extra columns: an explicit join entity

The moment the link needs data of its own (when did the user apply, with which status, which cover letter), the join table has columns beyond the two FKs. @ManyToMany cannot hold them. Model the link as an entity with two @ManyToOnes. In the job portal, Application is exactly this: User ↔ Job many-to-many, made explicit (see the full example).

Wrong: no place for status

@ManyToMany
@JoinTable(name = "application", ...)
private Set<Job> appliedJobs;       // where do appliedAt and status go?

Right: explicit entity

@Entity
class Application {
    @ManyToOne(fetch = LAZY) private User applicant;
    @ManyToOne(fetch = LAZY) private Job job;
    private Instant appliedAt;
    @Enumerated(EnumType.STRING) private ApplicationStatus status;
}

@OneToOne and @MapsId

A one-to-one is a foreign key with a unique constraint. The owning side holds the FK (@JoinColumn); the other uses mappedBy. Because Hibernate cannot make the inverse side lazy without extra work (it must query to know whether the row exists), the inverse side of a bidirectional @OneToOne is often loaded eagerly anyway. Prefer unidirectional from the side with the FK.

@MapsId shares the primary key: the child's id is the parent's id, so no separate FK or index is needed.

@Entity
public class UserProfile {
    @Id
    private Long id;                         // same value as user.id

    @OneToOne(fetch = FetchType.LAZY, optional = false)
    @MapsId                                  // copies user's id into this id
    @JoinColumn(name = "id")
    private User user;

    private String headline;
    private String resumeUrl;
}

@JoinColumn and defaults

  • @JoinColumn(name = "company_id", nullable = false) sets the FK column name and NOT NULL.
  • foreignKey = @ForeignKey(name = "fk_job_company") names the constraint (useful if Hibernate generates the DDL).
  • optional = false on @ManyToOne tells Hibernate the FK is never null, so it can use inner joins.

Rules

  • The side with the foreign key (@ManyToOne) is the owner; mappedBy goes on the other side and names the owner's field.
  • Only the owning side writes the FK. Update both sides in memory with helper methods.
  • Cascade and orphanRemoval only for owned children (composition).
  • Use Set for @ManyToMany; use an explicit entity when the link has its own data.
  • Do not use entities with bidirectional links in JSON responses; use DTOs (module 2).

Exceptions and edge cases

  • TransientPropertyValueException: object references an unsaved transient instance — you linked to an entity that was never persisted and has no cascade.
  • DataIntegrityViolationException (null value in column "company_id") — set only the inverse side.
  • ConstraintViolationException on delete — a child row still references the parent; delete children first or cascade.
  • StackOverflowError in toString/hashCode/Jackson — bidirectional loop (entities).

Interview angle

"What is the owning side?" The side with the foreign key; the other has mappedBy. "What does mappedBy do?" Tells JPA this side only mirrors a mapping defined on the other entity, so no extra table or column. "Cascade vs orphanRemoval?" Cascade propagates operations; orphanRemoval deletes children that leave the collection. "How to model many-to-many with extra columns?" A join entity with two ManyToOne. "Why Set for ManyToMany?" Efficient removal and no duplicates.

Project 2 model: User, Company, Job, Application

A full set of entities for the job portal: Company 1-n Job, User 1-n Application n-1 Job, with lazy ManyToOne everywhere, a Set-based tag link, the matching Flyway SQL, and the repository methods that read it.

The job portal has recruiters who post jobs for a company, and candidates who apply. The relationships are:

  • Company → Job: one-to-many; Job.company is the owner.
  • Company → User: a recruiter works for one company (User.company, nullable for candidates).
  • User ↔ Job through Application: an explicit join entity with status and date. A candidate may apply to a job only once: a unique constraint on (job_id, user_id).

Base class with the shared id

@MappedSuperclass
public abstract class BaseEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    public Long getId() { return id; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || Hibernate.getClass(this) != Hibernate.getClass(o)) return false;
        BaseEntity other = (BaseEntity) o;
        return id != null && id.equals(other.getId());
    }

    @Override
    public int hashCode() { return Hibernate.getClass(this).hashCode(); }
}

A @MappedSuperclass is not an entity itself; its fields become columns in each subclass's table. Audit fields are added to it in the auditing article.

       uniqueConstraints = @UniqueConstraint(
               name = "uk_application_job_user", columnNames = {"job_id", "user_id"}))
public class Application extends BaseEntity {

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "job_id", nullable = false)
    private Job job;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "user_id", nullable = false)
    private User applicant;

    @Enumerated(EnumType.STRING) @Column(nullable = false, length = 20)
    private ApplicationStatus status = ApplicationStatus.SUBMITTED;

    @Column(name = "cover_letter", columnDefinition = "text")
    private String coverLetter;

    @Column(name = "applied_at", nullable = false, updatable = false)
    private Instant appliedAt = Instant.now();

    protected Application() { }
    public Application(Job job, User applicant, String coverLetter) {
        this.job = job; this.applicant = applicant; this.coverLetter = coverLetter;
    }
    public void shortlist() { this.status = ApplicationStatus.SHORTLISTED; }
}

Notice the decisions: every @ManyToOne is LAZY; nobody has a List that could grow without limit; the one collection (tags) is a Set and small; Application has behaviour (shortlist()) instead of a public setter.

PostgreSQL does not index foreign key columns automatically, so add indexes on job.company_id and application.user_id yourself (the unique index on (job_id, user_id) already covers lookups by job_id). See SQL · Module 5 on indexes.

Repositories and a service

public interface ApplicationRepository extends JpaRepository<Application, Long> {

    boolean existsByJobIdAndApplicantId(Long jobId, Long userId);

    Page<Application> findByApplicantId(Long userId, Pageable pageable);

    @Query("select a from Application a join fetch a.applicant where a.job.id = :jobId")
    List<Application> findForJob(@Param("jobId") Long jobId);
}

@Service
public class ApplicationService {
    // constructor injection of repositories omitted

    @Transactional
    public Long apply(Long jobId, Long userId, String coverLetter) {
        if (applicationRepository.existsByJobIdAndApplicantId(jobId, userId)) {
            throw new DuplicateResourceException("Already applied");
        }
        Job job = jobRepository.findById(jobId)
                .orElseThrow(() -> new ResourceNotFoundException("Job", jobId));
        if (job.getStatus() != JobStatus.OPEN) {
            throw new IllegalStateException("Job is closed");
        }
        User applicant = userRepository.getReferenceById(userId);   // no SELECT
        return applicationRepository.save(
                new Application(job, applicant, coverLetter)).getId();
    }
}

Design notes

  • The database UNIQUE (job_id, user_id) is the real guarantee; the existsBy check only gives a friendly message. Catch DataIntegrityViolationException for the race.
  • Give constraints and indexes explicit names. They appear in error messages and make migrations easier to read.
  • Aggregate boundaries: Application has its own repository because it is queried by user and by job, not only through a parent.

In real projects

Teams often skip bidirectional collections entirely and read children through repositories with paging, which avoids both huge collections and the N+1 traps discussed next. Cascading is used rarely: for an Order with its OrderItems, yes; for anything shared between aggregates, no.

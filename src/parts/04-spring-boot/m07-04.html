RabbitMQ with Spring AMQP, and Kafka vs RabbitMQ

RabbitMQ routes messages from producers through exchanges to queues using bindings and routing keys; Spring AMQP gives you RabbitTemplate to publish and @RabbitListener to consume, with acknowledgements, retries and dead-letter exchanges for failures.

The RabbitMQ model

RabbitMQ is a traditional message broker that implements the AMQP protocol. Its main difference from Kafka: the producer never writes to a queue directly. It publishes to an exchange, and the exchange routes the message to zero or more queues according to bindings and a routing key. Consumers read from queues, and a message is removed from the queue once it is acknowledged.

Exchange typeRouting ruleTypical use
directRouting key must equal the binding key exactlyTask queues, one destination per key
topicBinding patterns with * (one word) and # (zero or more words), e.g. application.*Event routing by category
fanoutCopies the message to every bound queue, ignoring the keyBroadcast: cache invalidation, notifications to many
headersMatches on message headersRare
  • Acknowledgements: the consumer acks after processing; if it dies or rejects (nack), the broker re-queues or dead-letters the message. This gives at-least-once delivery.
  • Durability: mark queues durable and messages persistent so they survive a broker restart.
  • Competing consumers: several consumers on one queue share its messages round-robin (prefetch controls how many unacknowledged messages each holds).
  • Dead-letter exchange (DLX): rejected or expired messages are re-routed to another exchange for inspection.

Spring AMQP setup

    <groupId>org.springframework.boot</groupId>

    listener:
      simple:
        acknowledge-mode: auto              # ack when the method returns, nack on exception
        prefetch: 10
        retry:
          enabled: true                     # local retries before giving up
          max-attempts: 3
          initial-interval: 1s
          multiplier: 2.0
        default-requeue-rejected: false     # after retries: reject, do not loop (goes to DLX)

Declaring exchange, queue and bindings

Spring declares these on the broker at startup when you create them as beans:

@Configuration
public class RabbitConfig {

    public static final String EXCHANGE = "jobs.events";
    public static final String QUEUE = "notification.application-submitted";
    public static final String DLX = "jobs.events.dlx";
    public static final String DLQ = "notification.application-submitted.dlq";

    @Bean TopicExchange eventsExchange() { return new TopicExchange(EXCHANGE, true, false); }
    @Bean DirectExchange deadLetterExchange() { return new DirectExchange(DLX); }

    @Bean
    Queue notificationQueue() {
        return QueueBuilder.durable(QUEUE)
                .deadLetterExchange(DLX)                    // rejected messages go here
                .deadLetterRoutingKey(DLQ)
                .build();
    }

    @Bean Queue deadLetterQueue() { return QueueBuilder.durable(DLQ).build(); }

    @Bean
    Binding notificationBinding() {
        return BindingBuilder.bind(notificationQueue()).to(eventsExchange())
                .with("application.submitted");             // routing key pattern
    }

    @Bean
    Binding deadLetterBinding() {
        return BindingBuilder.bind(deadLetterQueue()).to(deadLetterExchange()).with(DLQ);
    }

    @Bean
    MessageConverter jsonMessageConverter() {
        return new Jackson2JsonMessageConverter();         // JSON instead of Java serialization
    }
}

Version note

Jackson2JsonMessageConverter uses Jackson 2. Boot 4 moves to Jackson 3, and Spring AMQP offers a Jackson 3 converter with a different class name; check the Spring AMQP reference for your version. Define one MessageConverter bean and Boot wires it into RabbitTemplate and the listener containers.

Producer and consumer

@Component
public class ApplicationEventsPublisher {

    private final RabbitTemplate rabbitTemplate;
    public ApplicationEventsPublisher(RabbitTemplate rabbitTemplate) { this.rabbitTemplate = rabbitTemplate; }

    public void publish(ApplicationSubmitted event) {
        rabbitTemplate.convertAndSend(RabbitConfig.EXCHANGE, "application.submitted", event);
    }
}

@Component
public class NotificationListener {

    private static final Logger log = LoggerFactory.getLogger(NotificationListener.class);

    @RabbitListener(queues = RabbitConfig.QUEUE)
    public void onSubmitted(ApplicationSubmitted event) {
        log.info("Notifying recruiter for application {}", event.applicationId());
        // throw an exception -> retry -> after max attempts the message goes to the DLQ
    }
}

If the listener method returns normally, the message is acknowledged. If it throws, Spring retries locally (the retry settings above), and when retries are exhausted the message is rejected without requeue and RabbitMQ routes it to the dead-letter exchange. Throw AmqpRejectAndDontRequeueException to reject at once for unrecoverable data. Publisher-side reliability uses publisher confirms (spring.rabbitmq.publisher-confirm-type=correlated) and returns for unroutable messages.

Kafka vs RabbitMQ

KafkaRabbitMQ
ModelDistributed commit log; consumers pull and track offsetsSmart broker: exchanges, queues, routing; broker pushes to consumers
After consumptionMessages stay until retention expires; replay is possibleMessage is removed after ack
RoutingBy topic and key onlyFlexible: direct, topic, fanout, headers
OrderingPer partitionPer queue (lost with competing consumers and redelivery)
ThroughputVery high (millions of records per second per cluster)High (tens of thousands per second per node)
Best forEvent streaming, event sourcing, analytics, data pipelines, many independent readersTask queues, request routing, per-message TTL, priorities, delayed retries
OperationsHeavier cluster; partitions to planSimpler to start

Rule of thumb: work to be done once (send this email, resize this image) fits RabbitMQ; facts that many parties read and may replay (a stream of order events) fit Kafka. For a small project either works; choose what your team can run. Cloud alternatives exist too: AWS SQS/SNS, Google Pub/Sub, Azure Service Bus.

Common mistakes

  • Non-durable queues, so messages vanish on a broker restart.
  • Requeueing a poison message for ever (default-requeue-rejected: true with a permanent error).
  • A huge prefetch with slow consumers: one consumer holds many messages while others idle.
  • Using the default guest account in production.
  • Expecting Kafka-style replay from RabbitMQ.

Interview angle

"Explain exchange, queue, binding and routing key." Producer to exchange, bindings route to queues. "Exchange types?" Direct, topic, fanout, headers. "How does RabbitMQ avoid message loss?" Durable queues, persistent messages, publisher confirms, consumer acks. "Kafka or RabbitMQ?" Streaming and replay and scale versus routing flexibility and task queues.

Delivery semantics, idempotent consumers and the outbox pattern

Networks make exactly-once delivery impossible in general, so build for at-least-once delivery with idempotent consumers, and use the outbox pattern to publish events atomically with your database change.

Delivery guarantees

GuaranteeMeaningHow it happensRisk
At-most-once0 or 1 timesSend and forget; commit the offset before processingLost messages
At-least-once1 or more timesRetry until acknowledged; commit the offset after processingDuplicates
Exactly-onceExactly 1 effectIdempotent processing, or transactions inside one system (Kafka transactions)Complex; works only within defined boundaries

Why duplicates? A consumer processes a message, then crashes before acknowledging. The broker redelivers. Or a producer sends, the broker stores it, but the acknowledgement is lost, so the producer retries. You cannot tell "lost request" from "lost response". The practical industry answer: at-least-once delivery + idempotent handling = effectively-once. Kafka's "exactly-once semantics" (idempotent producer plus transactions) is real, but it covers reading from Kafka and writing to Kafka; once you touch an email server or your database, you need your own idempotency.

Idempotent consumers

An operation is idempotent if doing it twice has the same effect as doing it once. "Set status to SHORTLISTED" is idempotent; "add 100 to the balance" and "send an email" are not. Make a handler idempotent by recording the ids of events already processed, in the same transaction as the effect:

CREATE TABLE processed_event (
    event_id     UUID PRIMARY KEY,
    consumer     VARCHAR(100) NOT NULL,
    processed_at TIMESTAMP NOT NULL DEFAULT now()
);
@Transactional
public void handle(ApplicationSubmitted event) {
    try {
        processedEventRepository.saveAndFlush(
                new ProcessedEvent(event.eventId(), "notification-service"));   // unique key
    } catch (DataIntegrityViolationException duplicate) {
        log.info("Event {} already processed, skipping", event.eventId());
        return;
    }
    notificationRepository.save(Notification.forRecruiter(event));   // same transaction
}

If the handler fails, the transaction rolls back including the "processed" row, and a retry works. Natural idempotence is even better: INSERT ... ON CONFLICT DO NOTHING, an upsert, "set" instead of "increment", or a unique constraint on (application_id, type). For external side effects (an email), store a "mail sent" flag, or pass an idempotency key to the provider. Producers should include a unique eventId in every event.

The dual-write problem

The application service must (1) save the application in its database and (2) publish an event. These are two systems, and there is no transaction across both:

  • Save, then publish: if the app crashes between, the data exists but no event was sent; the recruiter is never told.
  • Publish, then save: if the save fails, an event describes something that never happened.
  • Publish inside the transaction: the commit may still fail after the event left.

The outbox pattern

Write the event to an outbox table in the same local database transaction as the business data. Because both rows are in one ACID transaction, either both exist or neither. A separate process then reads the outbox and publishes to the broker, marking rows as sent.

@Transactional
public ApplicationResponse apply(Long jobId, Long userId) {
    Application saved = applicationRepository.save(new Application(jobId, userId));

    outboxRepository.save(new OutboxEvent(
            UUID.randomUUID(),
            "application-events",                       // topic
            String.valueOf(jobId),                      // key
            objectMapper.writeValueAsString(ApplicationSubmitted.from(saved)),   // JSON payload
            Instant.now()));
    return mapper.toResponse(saved);                    // one commit covers both rows
}
@Component
public class OutboxRelay {

    @Scheduled(fixedDelay = 1000)
    @SchedulerLock(name = "outboxRelay", lockAtMostFor = "PT30S")      // one relay at a time
    public void publishPending() {
        List<OutboxEvent> batch = outboxRepository.findTop100BySentAtIsNullOrderByCreatedAtAsc();
        for (OutboxEvent e : batch) {
            try {
                kafkaTemplate.send(e.getTopic(), e.getKey(), e.getPayload()).get(5, TimeUnit.SECONDS);
                e.markSent(Instant.now());
                outboxRepository.save(e);
            } catch (Exception ex) {
                log.warn("Outbox publish failed for {}, will retry", e.getId(), ex);
                break;                                   // keep order; try again next tick
            }
        }
    }
}

The relay itself is at-least-once (it may publish and crash before marking), which is why consumers must be idempotent. Variants: a polling relay as above (simple, adds a second or so of delay), or change data capture (CDC) with a tool such as Debezium that reads the database's transaction log and publishes outbox rows to Kafka (low latency, no polling, more infrastructure). Delete or archive sent rows regularly. The Spring Modulith project has built-in support for an event publication log with similar goals. Pattern background: System Design · Module 6.

Ordering, retries and sagas in one paragraph

Ordering holds only per partition (Kafka) or per queue (RabbitMQ without competing consumers), so key by the entity id and design handlers that tolerate late or reordered events (include a version or timestamp and ignore older ones). A saga coordinates a multi-service workflow as a chain of local transactions plus compensations, either choreographed (each service reacts to events) or orchestrated (a coordinator tells each service what to do).

A worked event flow: OrderPlaced to payment to notification

Food-delivery example, with three services and one broker:

  1. The order service stores the order as PENDING and an OrderPlaced row in its outbox, in one transaction.
  2. The relay publishes OrderPlaced keyed by order id.
  3. The payment service charges the customer; a duplicate delivery finds the payment for this order id already exists and does nothing. It publishes PaymentCompleted or PaymentFailed.
  4. The order service consumes the result and moves the order to CONFIRMED (or CANCELLED, the compensation).
  5. The notification service sends the SMS and email; it deduplicates by event id.

Notice what the user sees: the order API returns "accepted" immediately; confirmation arrives a moment later. The system is eventually consistent, and the UI must reflect that ("processing payment...").

Rules

  • Assume every message can arrive twice, late or out of order.
  • Give every event a unique id, and every consumer a way to ignore a repeat.
  • Never do "save to DB and publish to broker" as two independent steps; use an outbox or an after-commit mechanism with a recovery path.
  • Check duplicates in the same transaction as the side effect.

Common mistakes

  • Believing a broker setting makes the whole flow "exactly-once".
  • Idempotency check outside the transaction, leaving a window where a crash marks an event processed without its effect (or the reverse).
  • Deleting outbox rows before the broker confirmed.
  • Retrying a non-idempotent step (charging) without a key.

Interview angle

"What delivery guarantees exist?" At-most, at-least, exactly-once; explain why at-least-once plus idempotence is the practical choice. "What is the dual-write problem and how do you solve it?" Outbox with a relay or CDC. "How do you make a consumer idempotent?" Event id table or natural idempotence, in the same transaction. "Orchestration vs choreography?" Central coordinator versus event reactions.

Distributed tracing with Micrometer Tracing

A trace follows one request across all services using a trace id that travels in the traceparent header; Micrometer Tracing creates spans automatically, propagates the context over HTTP and messaging, exports them to Zipkin, Jaeger or Tempo, and puts the trace id in your logs.

The problem and the vocabulary

A user clicks "Apply". The request passes the gateway, the application service, the job service, the payment service and a Kafka consumer. It is slow. Which hop is slow? Logs from five services do not tell the story unless something links them. Distributed tracing records the path and timing of a request across services.

Trace
The whole journey of one request; identified by a trace id (128-bit, 32 hex characters).
Span
One unit of work inside a trace (an incoming HTTP request, a database query, an outgoing call, a Kafka send); has a span id, a parent span id, a start time and a duration, and tags.
Context propagation
Passing the trace id and current span id to the next service, so it continues the same trace. Over HTTP it travels in headers; over messaging in message headers.

The W3C traceparent header

The standard format for HTTP propagation is the W3C Trace Context header:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

The fields are: version (00), the 32-hex trace id, the 16-hex parent span id, and flags (01 means "sampled"). The receiving service creates a new child span under that parent. Older Zipkin systems used the B3 headers; Micrometer Tracing can be configured for either.

Micrometer Tracing

Micrometer Tracing is the tracing facade in Spring Boot 3 and later (the successor of Spring Cloud Sleuth, which is not used any more). It is built on the Micrometer Observation API: one instrumented operation produces both a metric and a span. You choose a bridge to a tracer implementation, and an exporter to a backend:

PieceChoices
Bridge (tracer)OpenTelemetry (micrometer-tracing-bridge-otel) or Brave (micrometer-tracing-bridge-brave)
ExporterOTLP (opentelemetry-exporter-otlp) to any OpenTelemetry-compatible backend; or Zipkin reporter for Brave
Backend (UI)Zipkin, Jaeger, Grafana Tempo, commercial APM tools

Version note

The dependencies and management.tracing.* settings above are for Boot 3.x. Spring Boot 4 adds a dedicated OpenTelemetry starter and its own configuration for OTLP; the concepts (traces, spans, sampling, propagation) are identical. Check the Boot 4 reference for the exact starter name before copying the dependencies.

What is traced automatically

  • Incoming HTTP requests (Spring MVC and WebFlux).
  • Outgoing calls made with the Boot-provided RestClient.Builder, RestTemplateBuilder or WebClient.Builder: they add the traceparent header. You must build clients from the injected builders (RestClient.create() or new RestTemplate() are not instrumented).
  • Messaging: set spring.kafka.template.observation-enabled=true and spring.kafka.listener.observation-enabled=true for Kafka; Spring AMQP has similar observation settings. The trace id then travels in message headers and the consumer continues the trace.
  • JDBC and others, with extra libraries (datasource-micrometer, OpenTelemetry instrumentation).
  • Your own code: annotate with @Observed (needs ObservedAspect bean) or create a span by hand:
@Service
public class ResumeScoringService {

    private final ObservationRegistry observationRegistry;
    public ResumeScoringService(ObservationRegistry observationRegistry) {
        this.observationRegistry = observationRegistry;
    }

    public int score(Long applicationId) {
        return Observation.createNotStarted("resume.score", observationRegistry)
                .lowCardinalityKeyValue("type", "pdf")
                .observe(() -> doScore(applicationId));        // a timer metric AND a span
    }
}

Trace ids in your logs

When tracing is on, Spring Boot 3.2 and later add the trace and span ids to the log lines automatically (the application name, trace id and span id appear in the default pattern), and they are fields in the JSON log formats. Then the loop closes: find a slow trace in Tempo or Zipkin, copy the trace id, and search the central log system for every log line of that request across all services. If you write your own pattern, use %X{traceId:-} and %X{spanId:-}, or the property logging.pattern.correlation. Return the trace id to clients in an error response or header, so a bug report can include it. This replaces the hand-made request id from module 6.

Sampling and cost

Tracing every request in a busy system produces a lot of data. Sampling keeps a percentage: management.tracing.sampling.probability: 0.1 keeps 10%. The decision is made at the start of the trace and respected by all services (the "sampled" flag). Production systems often sample 1 to 10%, or use tail-based sampling in a collector (keep all slow or failed traces). Errors you care about may be missed at low rates, which is the trade-off.

The three pillars of observability

PillarQuestion it answersSpring tool
LogsWhat happened, exactly, in this component?SLF4J + Logback (JSON)
MetricsIs the system healthy, and how is it trending?Micrometer + Prometheus
TracesWhere did this one request spend its time, across services?Micrometer Tracing + OTLP/Zipkin

The usual workflow: an alert on a metric (error rate up) leads to traces of failing requests, which lead to the logs of the failing span, joined by the trace id. Setting up Prometheus, Grafana, Loki and Tempo is covered in DevOps · Module 6.

Common mistakes

  • Creating new RestTemplate() or RestClient.create() by hand: no propagation, broken traces.
  • Leaving the default 10% sampling and wondering why the trace for a failing request is missing during a test.
  • Forgetting spring.application.name: every service shows as unknown_service.
  • Tracing everything at 100% in production without a plan for the storage cost.
  • Putting personal data (emails, tokens) into span tags.

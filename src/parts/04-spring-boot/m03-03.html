Lazy vs eager loading, proxies and LazyInitializationException

Fetch type decides when a related entity is loaded; make every association LAZY, load what you need explicitly in the service, and turn off Open Session in View so lazy loading cannot leak into the web layer.

Lazy and eager

  • EAGER: the related data is loaded together with the owner, always, whether you need it or not.
  • LAZY: the related data is loaded only when you first touch it (job.getCompany().getName()), with a second query.
AnnotationDefault fetchMeaning of the default
@ManyToOneEAGERLoading a Job also loads its Company
@OneToOneEAGERSame
@OneToManyLAZYChildren loaded on first access
@ManyToManyLAZYJoin rows loaded on first access
@Basic fieldsEAGERColumn loaded with the row (LAZY on a basic field needs bytecode enhancement)

The defaults are historical and dangerous: an eager @ManyToOne on Application.job means "load 20 applications" also loads 20 jobs, and each job eagerly loads its company. With JPQL/derived queries this becomes extra queries per row; with findById it becomes joins you did not ask for. Also, fetch = EAGER cannot be switched off for a single query. LAZY can be switched on per query (join fetch, entity graph), so LAZY is the flexible default.

Rule: make every association LAZY

Write @ManyToOne(fetch = FetchType.LAZY) and @OneToOne(fetch = FetchType.LAZY) everywhere. Then decide per use case what to load: JOIN FETCH, @EntityGraph, batch fetching, or a DTO projection (see the N+1 article).

How lazy loading works: proxies

For a lazy @ManyToOne, Hibernate puts a proxy in the field: a generated subclass of Company that holds only the id. Calling job.getCompany().getId() does not hit the database. The first call to any other method (getName()) makes the proxy run select ... from company where id=? through the open session and fill itself. For a lazy collection, Hibernate puts its own collection class (PersistentBag/PersistentSet) that loads on first iteration or size().

@Transactional(readOnly = true)
public String companyOfJob(Long jobId) {
    Job job = jobRepository.findById(jobId).orElseThrow();   // select from job where id=?
    Company c = job.getCompany();                             // proxy, no SQL yet
    return c.getName();                                       // select from company where id=?
}

Consequences of proxies: c.getClass() is not Company but Company$HibernateProxy$...; instanceof and equals need care (Hibernate.getClass, entities); final classes and methods cannot be proxied.

LazyInitializationException

The proxy can only load data while its session is open, that is, inside the transaction. If you touch it after the service method returned, there is no session and you get:

org.hibernate.LazyInitializationException: could not initialize proxy
[com.example.jobs.company.Company#7] - no Session
// service
@Transactional(readOnly = true)
public Job getJob(Long id) { return jobRepository.findById(id).orElseThrow(); }

// controller (no transaction)
Job job = jobService.getJob(5L);
return job.getCompany().getName();       // BOOM: session already closed

Wrong fixes people copy from the internet: make the association EAGER (slow everywhere), add @Transactional to the controller (wrong layer), or keep Open Session in View. Right fixes, in order of preference:

  1. Map to a DTO inside the service (inside the transaction) and return the DTO. This is the standard in module 2.
  2. Load what you need with the query: join fetch, @EntityGraph, or a DTO/projection query that selects the fields directly.
  3. Initialise explicitly in the service (Hibernate.initialize(job.getTags())) only for rare cases.

Open Session in View (OSIV)

Open Session in View keeps the Hibernate session open for the whole HTTP request, until the response is written. Lazy loading then works in the controller and in JSON serialization. Spring Boot enables it by default (spring.jpa.open-in-view=true) and prints a warning at startup: "spring.jpa.open-in-view is enabled by default... Explicitly configure spring.jpa.open-in-view to disable this warning".

Why it exists

  • No LazyInitializationException in controllers or views.
  • Convenient for quick demos.

Why to switch it off

  • Hides N+1 queries: every row serialised can fire a query, outside any transaction boundary.
  • Holds a database connection for the whole request, including slow JSON writing and calls to other services, so the pool runs out under load.
  • Lets the web layer depend on entity internals; the service stops being the data boundary.
spring.jpa.open-in-view=false

With it off, your code must fetch everything the response needs inside the service. That is the discipline you want, and the exceptions will tell you early where a fetch is missing.

Eager loading when you do need it

Do not mark the mapping EAGER. Ask for it in the query instead, so only that screen pays:

@Query("select j from Job j join fetch j.company where j.id = :id")
Optional<Job> findWithCompany(@Param("id") Long id);

@EntityGraph(attributePaths = "company")
Optional<Job> findDetailedById(Long id);          // derived query + graph
select j.*, c.* from job j join company c on c.id = j.company_id where j.id = ?

Other lazy-related details

  • getReferenceById gives a proxy on purpose (persistence context).
  • Lazy basic fields and @Lob: to avoid loading a big text column, move it to its own entity or use a projection; true attribute laziness needs Hibernate bytecode enhancement.
  • optional = false helps Hibernate use an inner join instead of a left join for fetches.
  • Serialising entities with Jackson triggers lazy loads on every getter, one more reason for DTOs.

Exceptions

  • LazyInitializationException — lazy association touched with no open session (above).
  • EntityNotFoundException — a proxy tries to load a row that was deleted.
  • HibernateException: Unable to find ... with id — same cause, older style message, from stale foreign keys.

Mistakes

  • Making associations EAGER to silence LazyInitializationException. You trade one error for hidden slowness.
  • Leaving OSIV on because the app "works", then discovering 300 queries per page in production.
  • Calling a lazy getter in a toString() (Lombok) or in logging.

Interview angle

"What is LazyInitializationException and how do you fix it?" Explain proxy + closed session, then give the DTO-in-service and fetch-in-query fixes, and say why not EAGER or OSIV. "What are the default fetch types?" ToOne = EAGER, ToMany = LAZY. "What is Open Session in View and should you use it?" Describe it and its connection and N+1 downsides; recommend false.

The N+1 problem: detect and fix with JOIN FETCH, EntityGraph and batching

N+1 means one query loads N parents and then N more queries load each parent's relation; find it in the SQL log, and fix it with JOIN FETCH, @EntityGraph, batch fetching or a DTO query.

What it is

You load a list of Applications (1 query) and then, for each one, print app.getApplicant().getName(). Because applicant is lazy, Hibernate loads each user separately: N more queries. For 50 applications, that is 51 queries instead of 1 or 2. It looks fine with 5 rows in development and kills the database with 5,000 rows in production.

@Transactional(readOnly = true)
public List<ApplicantRow> applicantsOfJob(Long jobId) {
    List<Application> apps = applicationRepository.findByJobId(jobId);   // 1 query
    return apps.stream()
            .map(a -> new ApplicantRow(a.getId(), a.getApplicant().getName()))  // N queries
            .toList();
}
select a.* from application a where a.job_id=?          -- 1 query, 3 rows
select u.* from app_user u where u.id=?                 -- user 11
select u.* from app_user u where u.id=?                 -- user 12
select u.* from app_user u where u.id=?                 -- user 13

The same happens with a lazy collection: companies.forEach(c -> c.getJobs().size()) runs one extra query per company. And with EAGER associations on a JPQL query: Hibernate loads the parents with your query, then loads each eager relation with separate queries. Eager is not a fix; it is another source of N+1.

Detecting it

  1. Read the SQL log. Turn on logging.level.org.hibernate.SQL=debug in development and look for the same statement repeating with different ids (SQL logging).
  2. Hibernate statistics. spring.jpa.properties.hibernate.generate_statistics=true plus logging.level.org.hibernate.stat=debug prints, per session, how many statements were prepared. A list page with 100+ statements is a red flag.
  3. Tests that count queries. Libraries such as datasource-proxy or Hypersistence Utils assert "this method runs at most 2 queries". It stops regressions.
  4. APM / slow query logs in production show hundreds of identical short queries per request.

Fix 1: JOIN FETCH

join fetch tells JPQL to load the association in the same SQL statement with a join.

@Query("""
       select a from Application a
       join fetch a.applicant
       where a.job.id = :jobId
       """)
List<Application> findByJobIdWithApplicant(@Param("jobId") Long jobId);
select a.*, u.*
from application a join app_user u on u.id = a.user_id
where a.job_id = ?

Use left join fetch when the association may be null or empty (a company with no jobs). distinct removes duplicate parents when you fetch a collection: select distinct c from Company c left join fetch c.jobs (Hibernate 6 removes duplicate entities automatically, but keeping distinct is harmless and clearer).

Fix 2: @EntityGraph

An entity graph says "load these attributes eagerly for this call", without writing JPQL. It works on derived queries and findAll overrides.

public interface ApplicationRepository extends JpaRepository<Application, Long> {

    @EntityGraph(attributePaths = {"applicant", "job"})
    List<Application> findByJobId(Long jobId);              // derived query + graph

    @EntityGraph(attributePaths = {"job", "job.company"})   // nested path
    Page<Application> findByApplicantId(Long userId, Pageable pageable);
}

An entity graph is a fetch hint, by default of type "fetch" (the listed attributes are eager, others keep their mapping). It is convenient and keeps method names clean; join fetch gives you more control (filters on the joined rows, aliases).

Fix 3: batch fetching

Instead of one query per parent, Hibernate can load many at once: ... where id in (?, ?, ?, ...). This is configured globally, and it makes lazy loading cheap without changing any query.

spring.jpa.properties.hibernate.default_batch_fetch_size=16
select a.* from application a where a.job_id=?
select u.* from app_user u where u.id in (?,?,?, ... up to 16 ids)

Per association you can use Hibernate's @BatchSize(size = 16) on the field or class. A value between 10 and 50 is common. It is a good safety net: set it once and many accidental N+1s become 1+1.

Fix 4: DTO projection

If the screen needs only a few fields, do not load entities at all (projections):

public record ApplicantRow(Long applicationId, String name, String email,
                           ApplicationStatus status) {}

@Query("""
       select new com.example.jobs.application.ApplicantRow(
              a.id, u.name, u.email, a.status)
       from Application a join a.applicant u
       where a.job.id = :jobId
       """)
List<ApplicantRow> findApplicantRows(@Param("jobId") Long jobId);

This is the fastest option for read-only lists: no entities, no persistence-context tracking, no lazy loading.

FixBest whenWatch out for
JOIN FETCHYou need the entities and the relation, one-to-one or many-to-oneCollections + pagination; duplicates
@EntityGraphSame, with derived queries or findAllSame limits as join fetch
Batch fetchingMany places; collections; paginationStill extra queries (but few)
DTO projectionRead-only list or report screensNo entity behaviour; one DTO per screen

Pitfall 1: JOIN FETCH of a collection with pagination

SQL pages by rows, but a join with a collection multiplies parent rows (a company with 3 jobs appears 3 times). If you ask for page 0 of size 10 on select c from Company c join fetch c.jobs, Hibernate cannot use limit on the SQL safely. It loads all rows, applies the limit in memory and logs a warning (it mentions applying pagination in memory). On a big table this is an outage waiting to happen.

Wrong: fetch join on a collection + Pageable

@Query("select c from Company c left join fetch c.jobs")
Page<Company> findAllWithJobs(Pageable p);   // pagination in memory

Right: page the parents, then fetch children

Page<Company> page = companyRepository.findAll(pageable);   // limit in SQL
// children: default_batch_fetch_size loads jobs for the page with 1 "in" query
// or: select c from Company c left join fetch c.jobs where c in :companies

Fetch joins on to-one associations (join fetch a.applicant) are safe with pagination because they do not multiply rows.

Pitfall 2: MultipleBagFetchException

Fetching two List (bag) collections in one query, such as join fetch j.tags join fetch j.questions, would produce a Cartesian product and Hibernate refuses: org.hibernate.loader.MultipleBagFetchException: cannot simultaneously fetch multiple bags. Fixes: change the collections to Set, or fetch one collection per query (the second query hits the persistence context and fills the other collection), or use batch fetching. Do not "fix" it with FetchType.EAGER.

Pitfall 3: the Cartesian product

Fetching two collections even as Sets multiplies rows (3 tags × 4 questions = 12 rows per job). Prefer one collection per query plus batch fetching.

A practical routine

  1. Keep everything LAZY.
  2. Set default_batch_fetch_size to a modest number as a net.
  3. For each list endpoint, look at the SQL; use DTO projections or join fetch on to-one relations.
  4. Add a query-count assertion in the integration test of the heavy endpoints.

Edge cases

  • LazyInitializationException remains if you add the relation to the DTO but forget to fetch it and map outside the transaction (fetching).
  • Batch fetching applies to lazy loads by id and to collections; it does not rewrite your JPQL.
  • Two queries are not "bad": fetching the parents then one batch query for the children is often better than one huge join.

Interview angle

One of the most common JPA questions. Strong answer: define it with a number ("1 + N queries"), give the lazy-loop example, say how you detect it (SQL log, statistics, query-count tests), list four fixes (join fetch, entity graph, batch size, DTO projection), and mention the two pitfalls: join fetch of a collection with pagination (in-memory) and MultipleBagFetchException. Add why EAGER does not fix it.

@Transactional in depth: proxies, propagation and rollback

@Transactional wraps your bean in a proxy that begins a transaction before the method and commits or rolls back after it; know the self-invocation trap, the rollback rules for checked exceptions and what each propagation value does.

A transaction is an all-or-nothing group of database operations (ACID; see SQL · Module 5). In Spring you do not write begin/commit; you annotate a method and Spring does it. This works because of the AOP proxies from module 1.

How it works: the proxy

When Spring finds @Transactional, it does not give other beans your object; it gives a proxy (a generated subclass with CGLIB, or a JDK interface proxy) with a TransactionInterceptor. The interceptor asks the PlatformTransactionManager (for JPA, JpaTransactionManager) to start a transaction, binds the connection and the EntityManager to the current thread, calls your method, and then commits or rolls back. Hibernate flushes right before the commit, so most SQL runs at the end of the method (flush). Repository methods are already transactional by themselves (SimpleJpaRepository has @Transactional(readOnly = true) on reads and @Transactional on writes), but each call is its own transaction; the service method joins them into one.

@Service
public class ApplicationService {

    @Transactional
    public void withdraw(Long applicationId, Long userId) {
        Application app = applicationRepository.findById(applicationId).orElseThrow();
        if (!app.getApplicant().getId().equals(userId)) {
            throw new AccessDeniedException("Not your application");  // rolls back
        }
        app.withdraw();                                  // dirty checking: UPDATE
        notificationRepository.save(Notification.of(app));   // INSERT, same transaction
    }                                  // both statements commit, or neither
}

The self-invocation pitfall

Only calls that go through the proxy start a transaction. When a method of the same class calls another method of that class, the call is this.method(), which skips the proxy, so the annotation on the second method is ignored.

Wrong: self-invocation

@Service
public class ReportService {
    public void run() {
        saveAudit();                   // this.saveAudit(): NO new transaction
    }
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveAudit() { ... }
}

Right: call through another bean

@Service
public class ReportService {
    private final AuditService auditService;     // separate bean
    public void run() {
        auditService.saveAudit();                // goes through the proxy
    }
}
@Service
public class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveAudit() { ... }
}

Alternatives: inject the bean into itself (ugly), use TransactionTemplate for programmatic control, or use AspectJ weaving (rare). Splitting into two beans is the usual fix. The same trap affects @Async, @Cacheable and other proxy-based annotations.

Where it works

  • On public methods of Spring beans called from other beans. Spring 6 also supports protected and package-visible methods with class-based proxies, but public is the safe, portable habit.
  • Not on private methods, final methods (CGLIB cannot override them) or objects created with new.
  • Prefer the service layer: a service method is the business unit of work. Not on controllers (web concerns, longer than needed) and not on every repository call.
  • Class-level @Transactional applies to all public methods; method-level overrides it. Put @Transactional(readOnly = true) on the class and @Transactional on the writing methods.

Rollback rules

By default a transaction rolls back only for unchecked exceptions (RuntimeException and subclasses) and Error. A checked exception (IOException, your own extends Exception) does not roll back: the transaction commits whatever was already flushed.

@Transactional                                   // checked exception: COMMITS
public void importJobs(MultipartFile file) throws IOException { ... }

@Transactional(rollbackFor = Exception.class)    // rolls back on any exception
public void importJobs(MultipartFile file) throws IOException { ... }

@Transactional(noRollbackFor = DuplicateResourceException.class)
public void tolerateDuplicates() { ... }

Many teams make their domain exceptions unchecked (as in module 2) to avoid this. A catch that swallows the exception also prevents rollback: try { ... } catch (Exception e) { log.error(...); } inside a transactional method means Spring never sees the failure. Rethrow it, or call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly().

Propagation

Propagation answers: "if a transaction already exists when this method is called, what do I do?"

REQUIRED means inner calls share one transaction, so one failure rolls back everything. REQUIRES_NEW uses a second database connection while the first waits, so overuse can exhaust the pool (a deadlock risk with a pool of 1). With REQUIRES_NEW, the inner transaction cannot see uncommitted data of the outer one.

The "silently rolled back" surprise

With REQUIRED, inner and outer share one transaction. If the inner method throws a runtime exception, Spring marks the whole transaction rollback-only. If the outer method catches that exception and carries on, then at commit Spring throws:

org.springframework.transaction.UnexpectedRollbackException:
Transaction silently rolled back because it has been marked as rollback-only
@Transactional
public void outer() {
    try {
        inner.doWork();             // REQUIRED, throws RuntimeException: marks rollback-only
    } catch (RuntimeException e) {
        log.warn("ignored", e);     // you swallowed it, but the mark stays
    }
    repo.save(x);                   // commit fails: UnexpectedRollbackException
}
// Fix: make inner REQUIRES_NEW or NESTED if its failure is acceptable,
// or let the exception propagate.

readOnly, isolation and timeout

@Transactional(readOnly = true)                              // reads
@Transactional(isolation = Isolation.READ_COMMITTED)         // see the SQL notes
@Transactional(timeout = 5)                                  // seconds
@Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRED)
  • readOnly = true is a hint. With Hibernate it sets the flush mode to MANUAL (no dirty checking, less memory and CPU), and with some drivers/databases it marks the connection read-only so a replica can be used. It does not stop you from running a write query on every database. Use it on every query-only service method.
  • isolation: default DEFAULT = the database default (PostgreSQL READ COMMITTED, MySQL InnoDB REPEATABLE READ). Raise it only when you understand the anomalies (SQL · Module 5).
  • timeout: seconds before the transaction is marked for rollback; it is checked at statement boundaries.

@Transactional in tests

In a Spring test (@SpringBootTest or @DataJpaTest), a test method annotated with @Transactional runs inside a transaction that is rolled back at the end by default, so tests leave no data behind. @DataJpaTest is already transactional. Beware: because nothing commits, flush-time errors (constraint violations) may never appear; call flush() in the test. A real test client (MockMvc in same thread is fine; an HTTP call from another thread is a different transaction) will not see uncommitted data.

Rules

  • Transactions belong on service methods (public, called from another bean).
  • Checked exceptions do not roll back unless you add rollbackFor.
  • Keep transactions short: no HTTP calls, file uploads or Thread.sleep inside; they hold a connection and locks.
  • Do your lazy loading and DTO mapping inside the transaction.

Mistakes

  • Self-invocation: a @Transactional method called from the same class.
  • @Transactional on a private method or on a class that is not a Spring bean: silently ignored.
  • Catching and swallowing the exception, so nothing rolls back.
  • Sending an email or a Kafka message inside the transaction, then the commit fails: the message is already out. Use the outbox pattern or send after commit (@TransactionalEventListener(phase = AFTER_COMMIT)).
  • Starting an async thread inside a transaction: the new thread has no transaction (transactions are thread-bound).

Interview angle

"How does @Transactional work?" Proxy + interceptor + transaction manager + thread-bound connection; commit or rollback after the call. "Why did my transaction not start?" Self-invocation, private method, not a bean. "What does it roll back on by default?" Unchecked exceptions and Errors only. "Explain REQUIRED vs REQUIRES_NEW." Join vs suspend-and-new; give the audit-log example. "What is UnexpectedRollbackException?" Rollback-only mark set by an inner participating transaction. "Why readOnly = true?" Skips dirty checking, signals intent, may route to a replica.

Optimistic and pessimistic locking

Use @Version for optimistic locking, which detects lost updates and fails the second writer; use pessimistic locks (SELECT ... FOR UPDATE) only for hot rows where conflicts are frequent and retries are not acceptable.

The problem: lost updates

Two recruiters open the same job. Both read vacancies = 5. One saves 4, the other saves 3 a moment later, based on the stale 5. The first change is silently overwritten: a lost update. Transactions alone do not prevent this at the default isolation level because each user reads and writes in separate requests. Background on isolation and row locks: SQL · Module 5.

Optimistic locking with @Version

Optimistic locking assumes conflicts are rare. It does not lock rows; it checks at write time that nobody changed the row since you read it. Add a version field:

@Entity
public class Job extends BaseEntity {

    @Version
    private Long version;          // wrapper type; managed by Hibernate, no setter

    private int vacancies;
}
update job set vacancies=?, version=?, ... where id=? and version=?
-- version in the WHERE is the value you read. If another transaction
-- already changed the row, 0 rows match.

Hibernate increments version on every update. If the UPDATE affects 0 rows, someone else got there first, and Hibernate throws OptimisticLockException, which Spring translates to ObjectOptimisticLockingFailureException (a subclass of OptimisticLockingFailureException). Supported version types: Long, Integer, Short or timestamp types. Add the column in the migration: version BIGINT NOT NULL DEFAULT 0.

Handling the conflict

  • In a REST API, return 409 Conflict (or 412 Precondition Failed with ETag / If-Match) so the client reloads and retries. Map it in your @RestControllerAdvice (module 2).
  • Expose the version to the client. The sequence above only helps if the version read when the form was opened travels with the update. Put version in the response DTO and in the update request, then compare in the service (if (!request.version().equals(job.getVersion())) throw ...) or set it on the entity before merging. If the DTO does not carry the version, only conflicts within a single request are caught.
  • Server-side retry for automatic operations (a counter): catch the exception outside the transaction and re-run the whole transaction a few times (Spring Retry's @Retryable, or a loop).
@ExceptionHandler(ObjectOptimisticLockingFailureException.class)
ProblemDetail conflict(ObjectOptimisticLockingFailureException ex) {
    return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT,
            "The record was changed by someone else. Reload and try again.");
}

Important: a bulk @Modifying query does not touch version unless you write set j.version = j.version + 1 (or use update versioned Job in HQL).

Pessimistic locking

Pessimistic locking assumes conflicts are likely: it locks the row in the database while you work, and others wait. In SQL that is SELECT ... FOR UPDATE.

public interface JobRepository extends JpaRepository<Job, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select j from Job j where j.id = :id")
    Optional<Job> findByIdForUpdate(@Param("id") Long id);

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
    Optional<Job> findWithLockById(Long id);          // waits at most 3 seconds
}

@Transactional
public void reserveVacancy(Long jobId) {
    Job job = jobRepository.findByIdForUpdate(jobId).orElseThrow();   // row locked
    job.decreaseVacancies();
}                                                                      // lock released at commit
select j.* from job j where j.id = ? for update
Lock modeMeaning
PESSIMISTIC_WRITEExclusive lock (FOR UPDATE): others can neither read-for-update nor write until commit
PESSIMISTIC_READShared lock (FOR SHARE where supported): others can read, not write
OPTIMISTIC, OPTIMISTIC_FORCE_INCREMENTVersion check at commit / force a version bump even without changes

The lock exists only inside a transaction, so @Transactional is required. Possible failures: PessimisticLockingFailureException (including CannotAcquireLockException when the timeout expires) and deadlocks (DeadlockLoserDataAccessException) if two transactions lock rows in opposite orders; always lock in a consistent order.

Sometimes neither is needed: an atomic SQL update such as update job set vacancies = vacancies - 1 where id = ? and vacancies > 0 (a @Modifying query) is the simplest and fastest guard for counters.

Mistakes

  • Adding @Version but never sending the version to the client, so the form-edit race is not caught.
  • Making version a primitive long with a manually set id: save may treat the entity as old (isNew).
  • Holding a pessimistic lock while calling an external service.
  • Retrying only the failing line instead of the whole transaction: after the exception the transaction is rollback-only.

Interview angle

"How do you prevent lost updates?" Optimistic locking with @Version: describe the where version=? update, the exception and a 409 response. "When would you choose pessimistic locking?" High contention on the same rows, such as stock or seat booking, plus a lock timeout. Mention the atomic-update alternative for counters.

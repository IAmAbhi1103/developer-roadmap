JWT way 2 (recommended): OAuth2 Resource Server with JwtEncoder and JwtDecoder

Add spring-boot-starter-oauth2-resource-server, define a JwtDecoder and JwtEncoder from your key, and Spring Security's BearerTokenAuthenticationFilter does the parsing, validation and Authentication for you; you only write the token issuing and a role converter.

Why this way

Spring Security ships a complete, well-tested Bearer-token implementation called the OAuth2 Resource Server support. A resource server is simply an API that accepts access tokens. It reads Authorization: Bearer, validates the JWT with a JwtDecoder (built on the Nimbus library, a dependency of the starter), maps claims to authorities, and produces the standard 401 responses. You do not write a filter, you do not catch parser exceptions, and moving later to RS256 keys or to an external identity provider (Keycloak, Auth0, Okta) is a configuration change. Use it for new code; it is the approach Spring Security's documentation recommends.

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-oauth2-resource-server</artifactId>
</dependency>

Keep spring-boot-starter-security too. Remove the jjwt dependencies and the custom filter, or leave them unused while you compare.

Step 1: the key, encoder and decoder

The decoder verifies tokens; the encoder creates them (the encoder is only needed because this application also issues tokens at login). Both use the same HS256 secret from app.jwt.secret (same properties as before).

import com.nimbusds.jose.jwk.source.ImmutableSecret;
import javax.crypto.SecretKey;
import javax.crypto.spec.SecretKeySpec;
import org.springframework.security.oauth2.jose.jws.MacAlgorithm;
import org.springframework.security.oauth2.jwt.*;

@Configuration
@EnableConfigurationProperties(JwtProperties.class)
public class JwtConfig {

    @Bean
    SecretKey jwtSecretKey(JwtProperties props) {
        byte[] bytes = Base64.getDecoder().decode(props.secret());
        return new SecretKeySpec(bytes, "HmacSHA256");
    }

    @Bean
    JwtEncoder jwtEncoder(SecretKey key) {
        return new NimbusJwtEncoder(new ImmutableSecret<>(key));
    }

    @Bean
    JwtDecoder jwtDecoder(SecretKey key, JwtProperties props) {
        NimbusJwtDecoder decoder = NimbusJwtDecoder.withSecretKey(key)
                .macAlgorithm(MacAlgorithm.HS256)
                .build();
        // default validators (exp, nbf) + the issuer must match
        decoder.setJwtValidator(JwtValidators.createDefaultWithIssuer(props.issuer()));
        return decoder;
    }
}

Step 2: issue the token at login

@Service
public class NimbusTokenService implements TokenService {

    private final JwtEncoder encoder;
    private final JwtProperties props;

    public NimbusTokenService(JwtEncoder encoder, JwtProperties props) {
        this.encoder = encoder;
        this.props = props;
    }

    @Override
    public String issueAccessToken(AppUserDetails user) {
        Instant now = Instant.now();
        JwtClaimsSet claims = JwtClaimsSet.builder()
                .issuer(props.issuer())
                .issuedAt(now)
                .expiresAt(now.plus(Duration.ofMinutes(props.accessTtlMinutes())))
                .subject(String.valueOf(user.getId()))
                .claim("email", user.getUsername())
                .claim("roles", List.of(user.getRole().name()))
                .build();
        JwsHeader header = JwsHeader.with(MacAlgorithm.HS256).build();   // see below
        return encoder.encode(JwtEncoderParameters.from(header, claims)).getTokenValue();
    }
}

Edge case: set the header algorithm yourself

If you call JwtEncoderParameters.from(claims) without a header, the encoder defaults to RS256 and fails with a "Failed to select a JWK signing key" error when your key is an HMAC secret. Pass JwsHeader.with(MacAlgorithm.HS256).build() as shown. Also keep only one TokenService bean: delete @Service from JjwtService (or the class itself) when you switch.

The login controller from the previous article is unchanged: it authenticates with the AuthenticationManager and calls tokenService.issueAccessToken(user).

Step 3: turn on the resource server and map roles

By default the converter looks at the scope or scp claim and prefixes each value with SCOPE_. Our tokens carry a roles claim, so we tell the converter to read that claim and prefix ROLE_, which makes hasRole("RECRUITER") work.

@Configuration
@EnableWebSecurity
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http, JsonSecurityHandlers handlers)
            throws Exception {
        http
            .csrf(csrf -> csrf.disable())
            .cors(Customizer.withDefaults())
            .sessionManagement(s ->
                    s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers("/api/auth/**").permitAll()
                    .requestMatchers(HttpMethod.GET, "/api/jobs/**").permitAll()
                    .requestMatchers("/api/admin/**").hasRole("ADMIN")
                    .anyRequest().authenticated())
            .oauth2ResourceServer(oauth -> oauth
                    .jwt(jwt -> jwt.jwtAuthenticationConverter(jwtConverter()))
                    .authenticationEntryPoint(handlers)     // 401 JSON
                    .accessDeniedHandler(handlers));        // 403 JSON
        return http.build();
    }

    @Bean
    JwtAuthenticationConverter jwtConverter() {
        JwtGrantedAuthoritiesConverter authorities = new JwtGrantedAuthoritiesConverter();
        authorities.setAuthoritiesClaimName("roles");
        authorities.setAuthorityPrefix("ROLE_");
        JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(authorities);
        return converter;
    }

    @Bean
    AuthenticationManager authenticationManager(AuthenticationConfiguration cfg)
            throws Exception {
        return cfg.getAuthenticationManager();
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }
}

What you get for free: BearerTokenAuthenticationFilter in the chain; for each request the token goes to the JwtDecoder, then the converter builds a JwtAuthenticationToken whose principal is a Jwt object (claims accessible by jwt.getClaim("email")) and whose getName() is the sub claim, the user id. In a controller:

@GetMapping("/api/me")
public Map<String, Object> me(@AuthenticationPrincipal Jwt jwt) {
    return Map.of(
            "id", jwt.getSubject(),
            "email", jwt.getClaimAsString("email"),
            "roles", jwt.getClaimAsStringList("roles"));
}

Expired and invalid tokens

If the token is missing the entry point answers 401. If it is present but bad, BearerTokenAuthenticationFilter catches the failure and calls the entry point with an InvalidBearerTokenException. The default entry point returns an empty body with:

HTTP/1.1 401
WWW-Authenticate: Bearer error="invalid_token", error_description="Jwt expired at 2026-11-10T10:15:00Z"

That follows the OAuth2 standard (RFC 6750). Our JsonSecurityHandlers replaces it with a JSON body but can keep the header. Note the difference from the custom filter: here a bad token on a public URL is rejected with 401 too, not ignored.

Asymmetric keys and external providers

With RS256 the application that issues tokens keeps the private key; other services only need the public key. With the resource server you can configure that with properties alone:

spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://login.example.com/realms/jobs    # discovers the JWKS
          # or: jwk-set-uri: https://login.example.com/.well-known/jwks.json
          # or: public-key-location: classpath:app.pub

When Boot sees one of these properties it builds the JwtDecoder for you, and you do not define the decoder bean. This is how a microservice trusts tokens from Keycloak without any security code of its own (module 7).

Common mistakes

  • Roles never work: the default converter uses scope and SCOPE_, so hasRole fails with 403 until you add the converter above.
  • A secret shorter than 32 bytes: the HS256 key is rejected or insecure.
  • Forgetting the HS256 header when encoding (see the edge case).
  • Defining both your own JwtDecoder bean and the issuer-uri property and expecting both to work: your bean wins.

Interview angle

"How would you secure a Spring Boot API with JWT today?" Resource Server with a JwtDecoder and a converter for roles; mention Nimbus, BearerTokenAuthenticationFilter, and that issuing tokens uses JwtEncoder (or an external identity provider). Contrast with the hand-written filter and say why the framework version is safer.

JSON error responses for 401 and 403: AuthenticationEntryPoint and AccessDeniedHandler

Security filters run before Spring MVC, so @RestControllerAdvice cannot handle their errors; implement AuthenticationEntryPoint for 401 and AccessDeniedHandler for 403 and write the JSON yourself.

Why a separate mechanism

Your @RestControllerAdvice from module 2 only sees exceptions thrown inside DispatcherServlet. Security filters run before it. When AuthorizationFilter denies a request, or the token is bad, the exception is caught by ExceptionTranslationFilter which delegates to two strategies:

InterfaceCalled whenStatusDefault behaviour
AuthenticationEntryPointAnonymous user hits a protected URL, or authentication failed401Empty body (and a WWW-Authenticate header)
AccessDeniedHandlerAuthenticated user lacks permission403Empty 403

A client that gets an empty body cannot show a good message. We write one handler class that implements both interfaces and returns a ProblemDetail-style JSON (the same shape as the rest of the API, module 2).

The handlers

@Component
public class JsonSecurityHandlers implements AuthenticationEntryPoint, AccessDeniedHandler {

    @Override   // 401
    public void commence(HttpServletRequest request, HttpServletResponse response,
                         AuthenticationException ex) throws IOException {
        String detail = "Authentication is required or the token is invalid.";
        if (ex instanceof InvalidBearerTokenException) {
            detail = "The access token is invalid or has expired.";
        }
        response.setHeader(HttpHeaders.WWW_AUTHENTICATE, "Bearer");
        write(response, 401, "Unauthorized", detail, request.getRequestURI());
    }

    @Override   // 403
    public void handle(HttpServletRequest request, HttpServletResponse response,
                       AccessDeniedException ex) throws IOException {
        write(response, 403, "Forbidden",
                "You do not have permission to do this.", request.getRequestURI());
    }

    private void write(HttpServletResponse response, int status, String title,
                       String detail, String path) throws IOException {
        response.setStatus(status);
        response.setContentType("application/problem+json");
        response.setCharacterEncoding("UTF-8");
        response.getWriter().write("""
                {"type":"about:blank","title":"%s","status":%d,\
                "detail":"%s","instance":"%s"}"""
                .formatted(title, status, detail, path.replace("\"", "")));
    }
}
HTTP/1.1 401
WWW-Authenticate: Bearer
Content-Type: application/problem+json

{"type":"about:blank","title":"Unauthorized","status":401,
 "detail":"Authentication is required or the token is invalid.",
 "instance":"/api/jobs/mine"}

The detail texts are fixed strings, so no user input reaches the JSON except the path, whose quotes we remove. If you build bigger bodies, use your JSON mapper (JsonMapper/ObjectMapper) instead of string formatting; its package differs between Jackson 2 in Boot 3 and Jackson 3 in Boot 4, which is why this example avoids it.

Register the handlers as shown in the earlier configurations: exceptionHandling(e -> e.authenticationEntryPoint(h).accessDeniedHandler(h)) for the custom filter, or the same two calls inside oauth2ResourceServer(...) for the resource server.

Method-security exceptions inside controllers

An AccessDeniedException thrown by @PreAuthorize or by your service code is raised inside MVC. If you have a catch-all @ExceptionHandler(Exception.class) returning 500, it swallows it and the user gets a wrong status. Handle it explicitly in the advice (or rethrow it):

@ExceptionHandler(AccessDeniedException.class)
ProblemDetail denied(AccessDeniedException ex) {
    return ProblemDetail.forStatusAndDetail(HttpStatus.FORBIDDEN,
            "You do not have permission to do this.");
}

Common mistakes

  • Expecting @RestControllerAdvice to format the 401/403 for URL rules.
  • A catch-all handler that turns AccessDeniedException into 500.
  • Putting stack traces or "user not found" details into the 401 body.
  • Forgetting the WWW-Authenticate header (it is part of the 401 contract, and clients and tools use it).

Interview angle

"Where do you customise the 401 and 403 responses?" AuthenticationEntryPoint and AccessDeniedHandler, set in exceptionHandling (or in the resource-server DSL). Explain why controller advice does not apply: the filters run before the DispatcherServlet.

Authorization: roles, hasRole, @PreAuthorize and owner-only checks

Use URL rules for coarse role checks, @PreAuthorize for method-level rules, and an ownership check in the service layer for "only the owner can edit"; roles need the ROLE_ prefix and the current user comes from the Authentication.

Roles vs authorities and the ROLE_ prefix

Spring Security has one concept: a GrantedAuthority, a string. A role is just an authority whose name starts with ROLE_. A finer-grained authority (also called permission) has any other name, e.g. job:write.

ExpressionChecks for
hasRole("ADMIN")Authority ROLE_ADMIN (prefix added for you)
hasAnyRole("ADMIN", "RECRUITER")Either role
hasAuthority("ROLE_ADMIN")The exact string, same result as hasRole("ADMIN")
hasAuthority("job:write")A permission name, exactly as stored
authenticated(), permitAll(), denyAll()Any user / everyone / nobody

The classic bug: the database stores RECRUITER, the authority list contains RECRUITER, and hasRole("RECRUITER") returns 403 because it looks for ROLE_RECRUITER. Add the prefix when you build authorities (we did in both implementations).

Roles suit a small fixed set (CANDIDATE, RECRUITER, ADMIN). If you need "can edit jobs but not delete" across many roles, use permissions and map roles to permission sets.

URL rules vs method security

URL rules (authorizeHttpRequests)Method security (@PreAuthorize)
WhereCentral, in SecurityConfigOn controller or service methods
SeesPath, HTTP method, rolesMethod arguments, return value, the Authentication
Good forCoarse rules: public vs login vs admin areaFine rules: "owner only", argument-based checks
RiskPath patterns that miss a URL variantSelf-invocation skips the proxy (as with @Transactional)

Use both: URL rules as the outer wall, method security next to the business code.

@EnableMethodSecurity and @PreAuthorize

@RestController
@RequestMapping("/api/jobs")
public class JobController {

    @PostMapping
    @PreAuthorize("hasRole('RECRUITER')")
    public JobResponse create(@Valid @RequestBody CreateJobRequest req,
                              Authentication auth) { ... }

    @DeleteMapping("/{id}")
    @PreAuthorize("hasRole('ADMIN')")
    public void delete(@PathVariable Long id) { ... }

    @GetMapping("/admin/stats")
    @PreAuthorize("hasAnyRole('ADMIN', 'RECRUITER')")
    public Stats stats() { ... }
}

The annotation holds a SpEL expression (Spring Expression Language). The useful pieces: authentication (the Authentication), principal, method arguments with #name (needs the -parameters compiler flag, which Spring Boot's Maven parent sets), and bean calls with @beanName. Related annotations: @PostAuthorize (checks the returned object), @PreFilter / @PostFilter (filter collections; avoid on big lists, filter in the query instead).

// Principal is a UserDetails with getId() (session / custom-filter style)
@PreAuthorize("#id == authentication.principal.id or hasRole('ADMIN')")
public UserResponse getProfile(Long id) { ... }

// Resource server style: authentication.name is the "sub" claim
@PreAuthorize("#id.toString() == authentication.name or hasRole('ADMIN')")
public UserResponse getProfile(Long id) { ... }

// Call a bean for anything that needs the database
@PreAuthorize("@jobSecurity.isOwner(#jobId, authentication)")
public JobResponse update(Long jobId, UpdateJobRequest req) { ... }
@Component("jobSecurity")
public class JobSecurity {

    private final JobRepository jobRepository;

    public JobSecurity(JobRepository jobRepository) {
        this.jobRepository = jobRepository;
    }

    public boolean isOwner(Long jobId, Authentication auth) {
        Long userId = Long.valueOf(auth.getName());
        return jobRepository.existsByIdAndPostedById(jobId, userId);
    }
}

If a rule fails, AuthorizationDeniedException (a subclass of AccessDeniedException) is thrown and becomes 403 through the handler above.

Ownership: "recruiters edit only their own jobs"

Roles answer "may a recruiter edit jobs?". Ownership answers "may this recruiter edit this job?". No role expression can know that, so a check against the data is needed. Do it in the service layer, where the entity is already loaded, so it works for every caller (controllers, scheduled jobs, other services) and cannot be forgotten by a new controller.

@Service
public class JobService {

    @Transactional
    public JobResponse update(Long jobId, UpdateJobRequest req, CurrentUser me) {
        Job job = jobRepository.findById(jobId)
                .orElseThrow(() -> new ResourceNotFoundException("Job " + jobId));

        boolean owner = job.getPostedBy().getId().equals(me.id());
        if (!owner && !me.isAdmin()) {
            throw new AccessDeniedException("You can only edit your own jobs");
        }
        job.update(req.title(), req.description(), req.salaryMin(), req.salaryMax());
        return JobResponse.from(job);                    // dirty checking saves it
    }
}

Notes: the first lookup returns 404 for an unknown job, then 403 for someone else's. Some APIs return 404 in both cases so outsiders cannot discover ids; pick one. In list queries, filter by owner in the query itself: findByPostedById(userId, pageable) for "my jobs"; never load all and filter in Java. For candidates, "only owners can edit their data" means applications: application.getApplicant().getId() must equal the current user, and a recruiter may see applications only for jobs they posted.

Getting the current user

// 1. Parameter of the controller method (simplest and testable)
@GetMapping("/me")
UserResponse me(Authentication authentication) { ... }

// 2. The principal itself
@GetMapping("/me")
Object me(@AuthenticationPrincipal Jwt jwt) { ... }                 // resource server
Object me(@AuthenticationPrincipal AppUserDetails user) { ... }     // UserDetails style

// 3. Static access (anywhere, but hidden dependency)
Authentication a = SecurityContextHolder.getContext().getAuthentication();

// 4. A small value object used by services
public record CurrentUser(Long id, Set<String> roles) {
    public static CurrentUser from(Authentication a) {
        Set<String> roles = a.getAuthorities().stream()
                .map(GrantedAuthority::getAuthority)
                .collect(Collectors.toSet());
        return new CurrentUser(Long.valueOf(a.getName()), roles);
    }
    public boolean isAdmin() { return roles.contains("ROLE_ADMIN"); }
}

Resolving CurrentUser once in the controller and passing it to the service keeps services free of SecurityContextHolder and easy to unit test (module 5). Do not accept the user id from the request body or URL for "my data" endpoints: POST /api/applications with {"userId": 5} lets anyone apply as someone else.

Rule: authorize on the server, with data, every time

Hiding a button in React is not security. Every endpoint must check role and ownership on the server. Missing ownership checks are called IDOR (insecure direct object reference, also "broken object-level authorization") and top the OWASP API list.

Common mistakes

  • hasRole("ROLE_ADMIN") double prefix, or authorities stored without prefix and hasRole used.
  • Forgetting @EnableMethodSecurity: the annotations silently do nothing.
  • Calling a @PreAuthorize method from another method of the same class (no proxy, no check).
  • Checking the role but not the owner: any recruiter edits any job.
  • Using the old @EnableGlobalMethodSecurity(prePostEnabled = true); it is replaced by @EnableMethodSecurity.

Interview angle

"Role vs authority?" Role is an authority with the ROLE_ prefix. "hasRole vs hasAuthority?" Prefix handling. "How do you stop one user editing another's data?" Ownership check against the loaded entity in the service (or @PreAuthorize calling a bean), plus query filtering; mention IDOR. "Where do you put authorization: controller or service?" URL/role rules at the edge, ownership in the service.

Monolith, modular monolith and microservices

Start with a well-structured modular monolith and split into microservices only when team size, scaling needs or release independence justify the cost of a distributed system.

The three architectures

A monolith is one deployable application: one JAR, one process, usually one database. Everything you built in Project 2 is a monolith. A microservice architecture splits the system into many small, independently deployable services, each owning its data and talking to the others over the network. A modular monolith is a middle path: one deployable, but inside it the code is divided into strongly separated modules with clear interfaces, so it could be split later.

MonolithModular monolithMicroservices
DeploymentOne unitOne unitMany units, each its own pipeline
ScalingWhole app togetherWhole app togetherEach service by itself
DataOne shared schemaOne database, schema or tables per moduleDatabase per service
Calls between partsMethod callsMethod calls through module APIsNetwork calls and events
TransactionsACID across everythingACID (use sparingly across modules)No distributed ACID; sagas and eventual consistency
ComplexityLow at first, grows into a "big ball of mud"MediumHigh: networking, observability, DevOps
Team size that fits1 to 15 people5 to 40 peopleMany teams that must ship independently

What microservices really buy you

  • Independent deployment: a team ships its service without coordinating a release of everything.
  • Independent scaling: the search service needs 20 instances, the admin service needs 1.
  • Fault isolation and technology freedom: a crash in the recommendation service need not take down checkout; a service may use another language or database.
  • Organisation: small teams own services end to end (Conway's law: system structure mirrors the communication structure of the organisation).

What they cost

  • Network instead of method calls. A call that took nanoseconds now takes milliseconds and can fail, time out or arrive twice. You need timeouts, retries and circuit breakers (Resilience4j).
  • Distributed data. No joins across services and no single transaction. Consistency becomes eventual, and you need patterns like events, sagas and the outbox (delivery semantics).
  • Observability. One user request touches six services; you need central logs, metrics and distributed tracing (tracing).
  • DevOps load. Many pipelines, containers, configs, secrets, versions and environments (Docker, Kubernetes).
  • Testing gets harder: contracts between services, end-to-end environments.
  • Latency and duplication: more hops per request, and the same code (auth, DTOs) repeated.

The distributed monolith anti-pattern

The worst result is a distributed monolith: services that must be deployed together, share one database, call each other in long synchronous chains, or break whenever another service changes. You pay all the costs of microservices and get none of the benefits. Warning signs: a change always touches three services; services cannot start without each other; two services read each other's tables; a release needs a "deployment order".

Why a modular monolith is often the better start

  1. You do not yet know the right boundaries. Wrong boundaries in a monolith cost a refactor; wrong boundaries across services cost API versions, data migration and meetings.
  2. You keep simple transactions, simple debugging, one deployment and fast local development.
  3. If you structure it well (packages by business capability, no cross-module repository access, events between modules), extracting a module into a service later is a mechanical job.

Many well-known companies run a monolith or a few large services successfully. Move to microservices when you have a concrete reason: several teams blocked on each other's releases, a part of the system with very different scaling or availability needs, or regulatory isolation.

Spring Modulith (brief)

Spring Modulith is a Spring project that helps you build and keep a modular monolith. Each top-level package under your application class is an application module; other modules may use only its public API (the types in the module's base package), and a test verifies this:

// com.example.jobs.job          -> module "job"   (public API: JobApi, events)
// com.example.jobs.job.internal -> hidden implementation
// com.example.jobs.application  -> module "application"
// com.example.jobs.notification -> module "notification"

class ModularityTests {
    @Test
    void verifyModularity() {
        ApplicationModules.of(JobsApplication.class).verify();   // fails on illegal dependencies
    }
}

Modules communicate with application events (and Modulith can persist events so they are not lost), which is the same style you would use between microservices. It also generates documentation diagrams of the modules. Add the Spring Modulith starter and test dependencies from the Spring Modulith documentation.

In real projects

A common path: monolith, then modular monolith, then extract one or two services that really need it (notifications, search, payments, report generation), often because they scale differently or are owned by a separate team. Companies "go back" from microservices to a monolith more often than people admit. Project 4 in this roadmap lets you practise the split on a small scale.

Common mistakes

  • Choosing microservices because it looks good on a CV, with a team of three and no users.
  • Splitting by technical layer (a "database service", a "validation service") instead of business capability.
  • Sharing one database between services.
  • Making every call synchronous, building a chain: A calls B calls C calls D.

Interview angle

"Monolith vs microservices?" Give a balanced table (deployment, scaling, data, transactions, complexity), not "microservices are modern". "When would you not use microservices?" Small team, unclear domain, no DevOps maturity. "What is a distributed monolith?" Coupled services that deploy together. "How would you migrate?" Modular monolith first, then the strangler pattern: extract one capability at a time behind a gateway.

Microservice basics: boundaries, data ownership and communication

Draw service boundaries around business capabilities, give each service its own database, talk synchronously only where the caller needs the answer now, and use events for everything else.

Service boundaries: business capabilities

A good boundary groups things that change together and have one owner. Look at the business, not the code layers. For a food-delivery product the capabilities are: restaurants and menus, orders, payments, delivery tracking, notifications, users and authentication. Each becomes a candidate service with its own team, API and data. For the job portal of Project 2: identity (users), jobs (companies and jobs), applications, notifications (email) and search.

  • A service should be small enough for one team to understand, large enough to do something useful alone. "Micro" does not mean one class.
  • Domain-driven design helps: a bounded context is an area where the words have one meaning ("customer" in billing differs from "customer" in support). Boundaries often follow bounded contexts.
  • If two services must always change together or call each other on every request, they are probably one service.

Database per service

Each service owns its data and is the only one allowed to access it. Others use its API or listen to its events. This keeps services independently changeable: the jobs service can rename a column without breaking applications. The consequences:

  • No SQL joins across services. If the applications service needs a job title, it calls the jobs service, or stores a copy of the fields it needs (updated by events).
  • No single ACID transaction across services. "Place order, charge payment, reserve stock" becomes a saga: a series of local transactions with compensating actions (refund) if a later step fails.
  • Data is eventually consistent: a copy may lag behind for milliseconds or seconds.

"Database per service" may be separate servers or just separate schemas with separate credentials; what matters is that nobody reads another service's tables.

Synchronous vs asynchronous communication

Synchronous (REST, gRPC)Asynchronous (events, messages)
StyleRequest and wait for the responseSend a message and continue; consumers react later
CouplingCaller needs the callee up nowLoose: the producer does not know the consumers
Latency of the callerAdds the callee's time (and failures)Only the time to publish
Good forQueries that need an answer now: "get job details", "validate the token"Notifications, workflows, data replication, spikes
Failure handlingTimeouts, retries, circuit breaker, fallbackBroker buffers; retries, dead-letter queue, idempotent consumers
DebuggingSimpler, a call stack across servicesHarder: need tracing and correlation ids

REST with JSON is the default for synchronous calls (you know it from module 2; call it with RestClient or HTTP service clients, module 6). gRPC uses Protocol Buffers over HTTP/2: smaller, faster, strongly typed contracts, popular for internal calls between services, less friendly for browsers. Rule of thumb: commands that need an immediate answer go synchronous; facts that happened ("ApplicationSubmitted") are published as events. Details of communication styles: System Design · Module 6.

API composition

When a screen needs data from several services (an application page: job from the jobs service, candidate from identity, status from applications), someone must assemble it, since there is no join. Options:

  • API composition: a gateway, a backend-for-frontend or one service calls the others (in parallel) and merges the answers. Simple, but latency is the slowest call and one failure affects the page; use timeouts and partial results.
  • Data replication / CQRS-style read model: a service keeps its own read-optimised copy built from events, so the page needs one query. More work, much faster reads.

Service-to-service contracts

  • Treat each API as a public contract: add fields, do not remove or rename them; version when you must (/v2). The consumers deploy on their own schedule.
  • Be liberal in what you accept: ignore unknown JSON fields (spring.jackson.deserialization.fail-on-unknown-properties=false is Boot's default).
  • Consider consumer-driven contract tests (Spring Cloud Contract, Pact) so a provider cannot break a consumer unnoticed.
  • Security: services trust the gateway or validate JWTs themselves (module 4); never expose internal services directly to the internet.

Rules

  • One service, one owner, one database. Never share tables.
  • Never design a long synchronous call chain; keep depth to one or two hops.
  • Every network call has a timeout; every message handler is idempotent.
  • Automate: one command to build, test and deploy each service.

Common mistakes

  • Splitting too early into "nano-services" that cannot do anything alone.
  • Replicating whole tables by hand with a cron job instead of events.
  • Distributed transaction attempts (two-phase commit) instead of sagas and idempotency.
  • Putting business logic in the gateway.

Interview angle

"How do you decide service boundaries?" Business capabilities and bounded contexts, data ownership, team ownership. "How do you handle a transaction across services?" Saga with compensation, idempotent steps, eventual consistency. "REST vs messaging between services?" Need-the-answer-now vs facts and decoupling. "How do you get data owned by another service?" API call, composition, or a local copy fed by events.

API gateway with Spring Cloud Gateway

An API gateway is the single entry point that routes client requests to the right service and handles cross-cutting concerns such as authentication, rate limiting, CORS and path rewriting; Spring Cloud Gateway configures this with routes made of predicates and filters.

What and why

Without a gateway, the React frontend would need to know the address of every service, handle each one's CORS and authentication, and the services would be exposed to the internet. An API gateway is one server in front of all of them. Clients call https://api.jobs.example.com/...; the gateway decides where each request goes.

Typical responsibilities:

  • Routing by path, host, method or header, plus path rewriting.
  • Authentication: validate the JWT once at the edge and pass user information on (services may still validate again for defence in depth).
  • Rate limiting and request size limits (rate limiting).
  • CORS and security headers in one place; TLS termination.
  • Load balancing to several instances (with discovery), retries, circuit breaking.
  • Aggregation of several calls into one response, logging, correlation ids.

Keep it thin: routing and cross-cutting rules only, no business logic. A fat gateway becomes a new monolith and a bottleneck owned by nobody.

Spring Cloud Gateway: the model

Spring Cloud Gateway is a gateway built on Spring WebFlux (reactive, non-blocking, on Netty), so it handles many concurrent connections cheaply. It is a separate Spring Boot application, not a library inside your services. Its three core ideas:

Route
The basic building block: an id, a destination URI, a list of predicates and a list of filters.
Predicate
A condition that decides whether a route matches the incoming request (Path, Method, Host, Header, Query, After...).
Filter
A step that changes the request before it is sent on, or the response on its way back (StripPrefix, AddRequestHeader, RequestRateLimiter...).

A route configuration

server:
  port: 8080

spring:
  application:
    name: api-gateway
  cloud:
    gateway:
      routes:
        - id: job-service
          uri: http://job-service:8081            # or lb://job-service with service discovery
          predicates:
            - Path=/api/jobs/**, /api/companies/**
          filters:
            - AddRequestHeader=X-Gateway, api-gateway
            - name: CircuitBreaker
              args:
                name: jobsCb
                fallbackUri: forward:/fallback/jobs

        - id: application-service
          uri: http://application-service:8082
          predicates:
            - Path=/api/applications/**
            - Method=GET,POST,PUT,DELETE
          filters:
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 10     # tokens per second
                redis-rate-limiter.burstCapacity: 20
                key-resolver: "#{@ipKeyResolver}"        # a KeyResolver bean

        - id: identity-service
          uri: http://identity-service:8083
          predicates:
            - Path=/auth/**
          filters:
            - StripPrefix=0
            - RewritePath=/auth/(?<segment>.*), /api/auth/${segment}

      globalcors:
        cors-configurations:
          '[/**]':
            allowedOrigins: "https://app.jobs.example.com"
            allowedMethods: [GET, POST, PUT, DELETE, OPTIONS]
            allowedHeaders: "*"
      default-filters:
        - DedupeResponseHeader=Access-Control-Allow-Origin Access-Control-Allow-Credentials
  • Path=/api/jobs/** matches every URL under that path. Multiple predicates in one route are combined with AND.
  • StripPrefix=1 removes the first path segment before forwarding: /job-api/jobs becomes /jobs. RewritePath uses a regex for arbitrary changes.
  • RequestRateLimiter uses Redis (the reactive Redis starter) with a token bucket and a KeyResolver bean that picks the key (IP, user, API key).
  • A CircuitBreaker filter needs the Resilience4j reactive circuit-breaker starter on the gateway's classpath (Resilience4j), and a fallback endpoint.
  • You can also define routes in Java with RouteLocatorBuilder when you need logic:
@Bean
RouteLocator routes(RouteLocatorBuilder builder) {
    return builder.routes()
            .route("job-service", r -> r.path("/api/jobs/**")
                    .filters(f -> f.addRequestHeader("X-Gateway", "api-gateway"))
                    .uri("http://job-service:8081"))
            .build();
}

@Bean
KeyResolver ipKeyResolver() {
    return exchange -> Mono.just(exchange.getRequest().getRemoteAddress()
            .getAddress().getHostAddress());
}

A global filter (a GlobalFilter bean) applies to every route; it is the place for a correlation id, request logging, or JWT validation (with Spring Security's resource server support for WebFlux, module 4).

Version note

Dependency and property names of Spring Cloud Gateway changed in the Spring Cloud 2025.0 release train: the classic starter spring-cloud-starter-gateway is renamed spring-cloud-starter-gateway-server-webflux, and the configuration prefix becomes spring.cloud.gateway.server.webflux.* (there is also a separate servlet-based gateway-server-webmvc variant). The concepts (routes, predicates, filters) and the route syntax are the same. Always use the Spring Cloud release train that matches your Spring Boot version (the spring-cloud-dependencies BOM) and check its documentation for the property prefix.

Backend for Frontend (BFF)

A Backend for Frontend is a gateway-like service built for one kind of client: a mobile app needs small payloads and fewer calls, a web admin needs big tables. Each BFF aggregates and shapes data for its client. It is useful when clients differ a lot; do not create one until you feel the pain.

Gateway alternatives

Nginx, Kong, Traefik, Envoy, cloud gateways (AWS API Gateway, Azure API Management) and Kubernetes Ingress controllers all do routing and rate limiting. Spring Cloud Gateway is attractive when your team knows Spring and wants route logic in Java; a plain Nginx or ingress is often enough for pure routing (DevOps · Module 2).

Common mistakes

  • Putting blocking code (JDBC, RestTemplate) in a reactive gateway filter: it blocks the Netty event loop and stalls all traffic.
  • CORS configured both in the gateway and in the services, giving duplicate Access-Control-Allow-Origin headers (hence DedupeResponseHeader).
  • Trusting a user-id header from clients: the gateway must remove incoming X-User-Id headers and set its own.
  • Leaving the services publicly reachable, so attackers bypass the gateway.

Interview angle

"What does an API gateway do?" Routing, auth, rate limiting, CORS, aggregation, one entry point. "Route, predicate, filter?" Define each. "Why is Spring Cloud Gateway not a normal Spring MVC app?" It is reactive (WebFlux/Netty). "Gateway vs load balancer?" A load balancer spreads traffic across identical instances; a gateway routes to different services and applies policies.

@SpringBootTest: full integration tests, profiles, test data and context caching

@SpringBootTest starts the whole application context so you can test real flows end to end through the layers; keep these tests few, share one context between them, and give each test its own clean data.

What it does

@SpringBootTest searches upwards for your @SpringBootApplication class and starts the full application context: all beans, security, JPA, Flyway, everything. Use it to prove the parts work together: controller to service to repository to database, with real security and real transactions. It is slower (seconds to start), so you write fewer of these.

webEnvironmentWhat happensCall the app with
MOCK (default)Full context, but a mock servlet environment; no port is openedMockMvc with @AutoConfigureMockMvc
RANDOM_PORTReal embedded server on a random free port@LocalServerPort + an HTTP client (RestClient, TestRestTemplate, WebTestClient)
DEFINED_PORTReal server on the configured port (can clash)Rarely used
NONEContext without any web environmentTest services or batch jobs directly

Prefer MOCK + MockMvc for most API flows: it is faster, runs in the same thread, and works with @Transactional rollback. Choose RANDOM_PORT when you need the real servlet container, real HTTP (filters at container level, cookies, serialisation over the wire) or to simulate a client.

An integration test through MockMvc

@SpringBootTest
@AutoConfigureMockMvc
@ActiveProfiles("test")
@Import(TestcontainersConfig.class)             // real PostgreSQL, see next article
class JobFlowIT {

    @Autowired MockMvc mvc;

    @Test
    void recruiterPostsJob_candidateApplies() throws Exception {
        register("asha@example.com", "S3cret#2026", "RECRUITER");
        register("ravi@example.com", "S3cret#2026", "CANDIDATE");
        String recruiterToken = login("asha@example.com", "S3cret#2026");
        String candidateToken = login("ravi@example.com", "S3cret#2026");

        String jobBody = mvc.perform(post("/api/jobs")
                        .header("Authorization", "Bearer " + recruiterToken)
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                                {"title":"Java Developer","description":"Spring Boot"}"""))
                .andExpect(status().isCreated())
                .andReturn().getResponse().getContentAsString();
        int jobId = JsonPath.read(jobBody, "$.id");

        mvc.perform(post("/api/jobs/{id}/applications", jobId)
                        .header("Authorization", "Bearer " + candidateToken))
                .andExpect(status().isCreated());

        // the candidate may not edit the job
        mvc.perform(put("/api/jobs/{id}", jobId)
                        .header("Authorization", "Bearer " + candidateToken)
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                                {"title":"Hacked","description":"x"}"""))
                .andExpect(status().isForbidden());
    }

    private void register(String email, String password, String role) throws Exception {
        mvc.perform(post("/api/auth/register")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                                {"name":"Test","email":"%s","password":"%s","role":"%s"}"""
                                .formatted(email, password, role)))
                .andExpect(status().isCreated());
    }

    private String login(String email, String password) throws Exception {
        String body = mvc.perform(post("/api/auth/login")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                                {"email":"%s","password":"%s"}""".formatted(email, password)))
                .andExpect(status().isOk())
                .andReturn().getResponse().getContentAsString();
        return JsonPath.read(body, "$.accessToken");
    }
}

This one test exercises registration, BCrypt, JWT, role rules, ownership and the database, using the real security chain instead of mocks. That is its value: the wiring that unit tests cannot see.

Calling a real server

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Import(TestcontainersConfig.class)
class HealthIT {

    @LocalServerPort int port;

    @Test
    void healthEndpoint_isUp() {
        RestClient client = RestClient.create("http://localhost:" + port);

        String body = client.get().uri("/actuator/health")
                .retrieve().body(String.class);

        assertThat(body).contains("UP");
    }
}

RestClient (Spring 6.1+) works the same in Boot 3 and 4. TestRestTemplate and WebTestClient also work with a random port, but how they are provided (extra dependencies or annotations) differs between Boot lines, so check your version's documentation; the idea is identical. Remember that a test method annotated @Transactional does not roll back the server's work with RANDOM_PORT: the server handles the request in another thread and its own transaction.

Profiles and test configuration

  • @ActiveProfiles("test") activates the test profile, so src/test/resources/application-test.yml overrides the main settings: a short JWT secret for tests, lower BCrypt cost, a fixed clock, disabled mail sending. Files in src/test/resources shadow those of the same name in src/main/resources.
  • @TestPropertySource(properties = "app.jwt.access-ttl-minutes=1") or @SpringBootTest(properties = "...") set single properties for one class.
  • @TestConfiguration adds or replaces beans for tests only, for example a fixed Clock. A static nested @TestConfiguration class is picked up automatically; a top-level one must be imported with @Import. (A normal @Configuration in src/test would be found by component scanning of every test, which is usually not what you want.)
@SpringBootTest
@Import(FixedClockConfig.class)
class DeadlineIT { ... }

@TestConfiguration
class FixedClockConfig {
    @Bean
    @Primary
    Clock clock() {
        return Clock.fixed(Instant.parse("2026-11-10T10:00:00Z"), ZoneOffset.UTC);
    }
}

values (10, 'Java Developer', 'Spring Boot', 1);

Three ways to keep tests independent in integration tests: (1) @Transactional on the test class with MockMvc (same thread, rolled back after each test), (2) @Sql cleanup scripts or repository.deleteAll() in @AfterEach, (3) unique data per test (random emails), so no cleanup is needed and tests can even run in parallel.

Context caching

Starting a Spring context takes seconds. The test framework therefore caches contexts and reuses one for all test classes with the same configuration. The cache key includes the configuration classes, active profiles, properties, @MockitoBean definitions, @TestConfiguration imports, and webEnvironment. Any difference creates and caches another context, and every cached context keeps its beans and connection pool alive.

Started JobFlowIT in 4.1 seconds
Started ApplicationFlowIT in 3.8 seconds     (different mocks: new context)
Started AuthIT in 3.9 seconds                (another property: new context)
  • Use one shared base class for integration tests with the same annotations, so most of them share a context.
  • Avoid scattering @MockitoBean and @TestPropertySource across many classes; each variant costs one more startup.
  • @DirtiesContext marks the context as dirty and discards it after the test or class. It is a last resort: it throws away the cache and makes the suite slow. Reset state explicitly instead.

Rules

  • Use @SpringBootTest for flows across layers; use slices and unit tests for everything else.
  • Integration tests need a real database of the production type (Testcontainers), not H2.
  • Each test creates the data it needs and must not rely on another test.

Exceptions and edge cases

  • Unable to find a @SpringBootConfiguration: the test class is in a package that is not under your application class. Move it or give classes = ....
  • ApplicationContext failure threshold exceeded / Failed to load ApplicationContext: the real cause is in the first "Caused by" lines, often a missing property or bean in the test profile.
  • @Transactional + RANDOM_PORT: no rollback of the server side (see above).
  • Port conflicts with DEFINED_PORT; prefer RANDOM_PORT.

Common mistakes

  • Using @SpringBootTest for a test that only needs one service and two mocks. Use a plain unit test.
  • Sharing mutable data between tests, then seeing tests pass alone and fail together.
  • A different set of @MockitoBean in every class, giving ten contexts and a ten-minute build.
  • Reaching for @DirtiesContext to clean the database.

Interview angle

"@SpringBootTest vs slice tests?" Full context vs one layer; mention speed and when you need each. "MOCK vs RANDOM_PORT?" No server, MockMvc vs real server and HTTP client. "Why are my tests slow?" Too many contexts: different mocks/properties break the cache; @DirtiesContext; Testcontainers started per class. Good answer: base class, shared container, fewer integration tests.

Testcontainers: tests against a real PostgreSQL in Docker

Testcontainers starts a throwaway Docker container (PostgreSQL, Redis, Kafka) for your tests; with @ServiceConnection Spring Boot wires it in automatically, and a shared configuration or base class starts it once for the whole suite.

Why

H2 is not PostgreSQL, and a database installed on your laptop differs from your colleague's and from CI. Testcontainers is a Java library that starts a real database in a Docker container, from an exact image tag (postgres:16-alpine), for the duration of the tests, and removes it afterwards. Every developer and every CI run gets the same database, with your real Flyway migrations, real SQL features and real locking. You trade a few seconds of startup for tests that mean something.

Requirement: Docker must be running. On Windows start Docker Desktop (with the WSL 2 backend) before running the tests; on Linux the Docker daemon. Without it you get IllegalStateException: Could not find a valid Docker environment. CI runners such as GitHub-hosted Ubuntu already have Docker.

Dependencies

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-testcontainers</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>junit-jupiter</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>postgresql</artifactId>
    <scope>test</scope>
</dependency>

Spring Boot's dependency management supplies the versions. Your normal PostgreSQL JDBC driver must be on the classpath too.

Versions

Testcontainers 2.x (used by newer Boot lines) renamed its modules with a testcontainers- prefix (for example testcontainers-postgresql, testcontainers-junit-jupiter) and moved PostgreSQLContainer to the package org.testcontainers.postgresql without the generic type parameter. The ideas and the Spring annotations stay the same. Use the artifact names and imports that match the Testcontainers version your Boot version manages; the code below uses the 1.x style.

Way 1: @Testcontainers, @Container and @ServiceConnection

import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;

@SpringBootTest
@Testcontainers
class JobRepositoryIT {

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired JobRepository jobRepository;

    @Test
    void connectsToRealPostgres() {
        assertThat(postgres.isRunning()).isTrue();
        assertThat(jobRepository.count()).isZero();     // Flyway ran on a clean database
    }
}
  • @Testcontainers adds the JUnit extension that manages containers.
  • @Container on a static field: started once before the first test of the class and stopped after the last. On a non-static field: a new container per test method (slow).
  • @ServiceConnection (Spring Boot 3.1+) tells Boot to create the connection details from the container (JDBC URL, user, password) and use them instead of spring.datasource.*. No manual property mapping.

Way 2: @DynamicPropertySource (before 3.1, or when @ServiceConnection does not fit)

@DynamicPropertySource
static void dbProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.datasource.url", postgres::getJdbcUrl);
    registry.add("spring.datasource.username", postgres::getUsername);
    registry.add("spring.datasource.password", postgres::getPassword);
}

The values are suppliers because the container's mapped port is known only after it starts. This also works for containers that @ServiceConnection does not support.

A reusable setup for the whole suite

Starting one PostgreSQL per test class wastes time (about 2 to 5 seconds each) and gives each class its own Spring context. Share one container. The cleanest way in modern Boot is a test configuration that defines the container as a bean:

@TestConfiguration(proxyBeanMethods = false)
public class TestcontainersConfig {

    @Bean
    @ServiceConnection
    PostgreSQLContainer<?> postgres() {
        return new PostgreSQLContainer<>(DockerImageName.parse("postgres:16-alpine"));
    }
}
@SpringBootTest
@AutoConfigureMockMvc
@ActiveProfiles("test")
@Import(TestcontainersConfig.class)
public abstract class AbstractIntegrationTest {

    @Autowired protected MockMvc mvc;
}

class JobFlowIT extends AbstractIntegrationTest { ... }
class ApplicationFlowIT extends AbstractIntegrationTest { ... }

All subclasses have identical annotations, so Spring caches one context, which holds one container for the entire test run. Flyway runs its migrations once on startup. Isolate tests by unique data or cleanup.

The older, widely seen alternative is the singleton container pattern, which does not need the Spring bean approach:

public abstract class AbstractPgTest {

    static final PostgreSQLContainer<?> POSTGRES =
            new PostgreSQLContainer<>("postgres:16-alpine");

    static { POSTGRES.start(); }                 // started once per JVM, no @Container

    @DynamicPropertySource
    static void props(DynamicPropertyRegistry r) {
        r.add("spring.datasource.url", POSTGRES::getJdbcUrl);
        r.add("spring.datasource.username", POSTGRES::getUsername);
        r.add("spring.datasource.password", POSTGRES::getPassword);
    }
}

Testcontainers starts a helper container (called Ryuk) that removes your containers when the JVM exits, even if the test run crashes, so you do not stop the singleton yourself.

Container reuse, other containers, dev time

  • Reuse between runs (local development only): call .withReuse(true) on the container and set testcontainers.reuse.enable=true in ~/.testcontainers.properties. The container then stays running after the tests and the next mvn test starts in a second. Data persists, so such tests must clean up after themselves. Do not enable it in CI.
  • Other services: the same pattern works for Redis (new GenericContainer<>("redis:7").withExposedPorts(6379) with @ServiceConnection(name = "redis")), Kafka (KafkaContainer), RabbitMQ, MongoDB, Elasticsearch, and a mock HTTP server. See module 7 for messaging.
  • Dev-time Testcontainers (Boot 3.1+): a class in src/test with SpringApplication.from(Application::main).with(TestcontainersConfig.class).run(args) starts your real application with a containerised database, no local PostgreSQL install needed. Combined with @RestartScope it survives DevTools restarts. It reuses the same configuration class as your tests.

Speed tips

  • One container per suite (above); pin a small image (postgres:16-alpine) so CI caches it.
  • Use a tmpfs for the data directory only if tests are I/O heavy: .withTmpFs(Map.of("/var/lib/postgresql/data", "rw")).
  • Keep the number of distinct Spring contexts low (context caching).
  • Use @DataJpaTest with Replace.NONE for query tests: it starts less than the full application but shares the same container class.

Exceptions and edge cases

  • IllegalStateException: Could not find a valid Docker environment: Docker is not running or not reachable. Start Docker Desktop; check docker ps.
  • ContainerLaunchException: Container startup failed: image could not be pulled (no network, proxy), or the database crashed on start. Read the container logs printed above the exception.
  • Connection refused to localhost:5432: the test connects to a fixed port instead of the container's mapped port. Always read the port from the container (getJdbcUrl()).
  • Tests pass locally and fail in CI: CI has no Docker (for example Docker-in-Docker not enabled) or lacks permissions.
  • Flyway fails with "Found non-empty schema" or checksum errors when a reused container holds old data.

Common mistakes

  • A non-static @Container field: a fresh database for every test method.
  • Using the latest image tag: a surprise upgrade breaks CI. Pin the major version to match production.
  • Hard-coding jdbc:postgresql://localhost:5432/... in application-test.yml, which overrides the container wiring.
  • Forgetting that @DataJpaTest replaces the database unless Replace.NONE is set.

Interview angle

"How do you test repositories against a real database?" Testcontainers with @ServiceConnection; Docker required; one shared container per suite; Flyway migrations run for real. "Why not H2?" Behaviour and SQL dialect differ. "What is @ServiceConnection?" Boot 3.1+ feature that derives connection details from the container, replacing @DynamicPropertySource boilerplate.

Coverage with JaCoCo, Surefire vs Failsafe, and tests in CI

JaCoCo measures which lines and branches your tests execute; read the HTML report to find untested code, aim for sensible targets, never treat the percentage as proof of quality, and run unit tests with mvn test and integration tests (*IT) with mvn verify.

What coverage tells you

Code coverage is the share of your code that ran while the tests ran. JaCoCo is the standard Java tool: it attaches an agent to the test JVM and records executed instructions.

Line coverage
Percentage of source lines executed at least once.
Branch coverage
Percentage of decision outcomes taken: for if (a && b) both the true and false path of each condition. More honest than line coverage, because one line can hide several paths.
Other counters
Instruction, method, class and cyclomatic complexity.
return job.isOpen() ? apply(job) : reject(job);   // a test with an open job gives 100% line,
                                                  // but only 50% branch coverage

Setting up the JaCoCo Maven plugin

<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.12</version>
    <executions>
        <execution>
            <id>prepare-agent</id>
            <goals><goal>prepare-agent</goal></goals>
        </execution>
        <execution>
            <id>report</id>
            <phase>verify</phase>
            <goals><goal>report</goal></goals>
        </execution>
    </executions>
</plugin>

prepare-agent adds the JaCoCo agent to the JVM arguments of the test runs (Surefire and Failsafe). report turns the recorded data into HTML after the tests. Use the latest 0.8.x release that supports your JDK; an old JaCoCo fails on classes compiled by a newer Java ("Unsupported class file major version").

$ mvn clean verify
...
[INFO] Loading execution data file target/jacoco.exec
[INFO] Analyzed bundle 'jobs' with 48 classes
$ start target/site/jacoco/index.html          # Windows (macOS: open, Linux: xdg-open)

Reading the report

The first page lists packages with bars for instruction and branch coverage, plus missed/total counts. Click a package, then a class, then a method: the source view colours each line green (fully covered), yellow (some branches missed, with a diamond marker) and red (never executed). Start with red lines in service classes that hold business rules; ignore generated code, DTOs and the main method. The right questions are "which rules are untested?" and "which branches did I forget (404, 403, validation, empty list)?", not "how do I reach 100%?".

Exclude classes that add noise (configuration, generated mappers, entities with only getters) in the plugin <configuration><excludes>. To fail the build under a threshold add a check goal:

<execution>
    <id>check</id>
    <phase>verify</phase>
    <goals><goal>check</goal></goals>
    <configuration>
        <rules>
            <rule>
                <element>BUNDLE</element>
                <limits>
                    <limit>
                        <counter>LINE</counter>
                        <value>COVEREDRATIO</value>
                        <minimum>0.70</minimum>
                    </limit>
                </limits>
            </rule>
        </rules>
    </configuration>
</execution>

Sensible targets, and why coverage is not quality

  • Many teams ask for roughly 70 to 80 percent line coverage on new code and watch the trend; 100 percent is rarely worth the cost. Services and domain logic deserve more than configuration or DTOs.
  • A test with no assertions gives coverage and no protection. service.update(...) called without checking anything is "covered".
  • Coverage tells you what is definitely untested; it cannot tell you what is well tested. Review assertions in pull requests, not just the percentage.
  • Mutation testing (PIT) goes further by changing your code and checking that tests fail; use it to learn, not necessarily in every build.

A common layout: name pure unit and slice tests *Test and Docker-based ones *IT. Developers run mvn test constantly (no Docker needed, seconds); CI runs mvn verify (everything). If your whole project uses only Surefire and you name Testcontainers tests *Test, that also works; the split is about speed and feedback. To meet the goal "Project 2 passes all its tests with mvn test", either keep all tests under Surefire naming, or decide that the full check is mvn verify and say so in the README.

Common mistakes

  • Chasing a percentage with tests that have no assertions.
  • Naming an integration test MyFlowTest and wondering why it runs on every mvn test (or naming it MyFlowIT and wondering why mvn test skips it).
  • Checking JaCoCo only on unit tests and concluding that controllers are "untested" when integration tests cover them: aggregate both runs (verify).
  • A JaCoCo version too old for your Java version.

Interview angle

"What coverage is enough?" There is no number; useful targets are around 70 to 80 percent on business code, with branch coverage and good assertions. "Line vs branch coverage?" One line can have several branches. "Surefire vs Failsafe?" Unit vs integration, test vs verify phases, *Test vs *IT names.

Good tests: FIRST, test data builders and avoiding flaky tests

A good test is fast, independent, repeatable, self-validating and written at the right time; it checks behaviour not implementation, builds its data with readable helpers, and never depends on time, order or luck.

The FIRST principles

Fast
Unit tests run in milliseconds, the whole unit suite in seconds. Slow tests are not run, so they do not protect you.
Independent
No test depends on another or on their order. Each creates its own data and cleans up. You can run one test alone or all in parallel.
Repeatable
Same result in every environment and on every run: no dependence on the clock, random numbers, network, the machine's time zone or leftover files.
Self-validating
The test says pass or fail by itself, through assertions. No reading console output to decide.
Timely
Written together with the code (or before it, TDD), when you still remember the rules. Not "after the release".

Test behaviour, not implementation

A test should fail when behaviour breaks and keep passing when you refactor. Tests that mirror the code line by line (verify that private helper A called B twice) break on every refactoring and teach nothing. Ask: "what would a caller notice?" Test the public result, the stored state, the response, and the side effects that matter.

Wrong: tests how, not what

verify(jobRepository).findById(7L);
verify(jobRepository).save(job);
verify(mapper).toResponse(job);
verifyNoMoreInteractions(jobRepository, mapper);

Right: tests the outcome

JobResponse r = service.close(7L, owner);
assertThat(r.open()).isFalse();
assertThat(job.getClosedAt()).isNotNull();

Test data builders

Creating a Job needs a user, a title and more fields; repeating a ten-line set-up in every test hides what matters. A test data builder creates a valid object with defaults and lets the test override only what it cares about.

public final class TestData {

    private TestData() {}

    public static User user(Long id, String email, Role role) {
        User u = new User("Test " + email, email, "{bcrypt}hash", role);
        ReflectionTestUtils.setField(u, "id", id);
        return u;
    }

    public static User newUser(String email, Role role) {      // no id: for persist
        return new User("Test " + email, email, "{bcrypt}hash", role);
    }

    public static Job job(Long id, String title, User owner) {
        Job j = new Job(title, "Description of " + title, owner);
        ReflectionTestUtils.setField(j, "id", id);
        return j;
    }

    public static Job newJob(String title, User owner) {
        return new Job(title, "Description of " + title, owner);
    }
}

// A builder with fluent overrides, when objects have many fields:
public class JobBuilder {
    private String title = "Java Developer";
    private boolean open = true;
    private User owner = TestData.newUser("owner@example.com", Role.RECRUITER);

    public static JobBuilder aJob() { return new JobBuilder(); }
    public JobBuilder withTitle(String t) { this.title = t; return this; }
    public JobBuilder closed() { this.open = false; return this; }
    public Job build() {
        Job j = new Job(title, "Some description", owner);
        if (!open) j.close();
        return j;
    }
}
// usage: Job closed = aJob().withTitle("QA").closed().build();

Test data should be minimal and meaningful: names like asha@example.com help readers; magic numbers do not. Avoid giant shared fixtures loaded for all tests (changing one row breaks twenty tests).

Flaky tests

A flaky test sometimes passes and sometimes fails with no code change. It destroys trust: people re-run the pipeline "until green" and real failures get ignored. Typical causes and fixes:

CauseExampleFix
Time and datesLocalDate.now(); a test fails at midnight or on month endInject Clock; use a fixed instant
RandomnessRandom emails that sometimes collideSeeded random or UUIDs; assert on properties, not values
Test order and shared stateOne test leaves a row that another countsOwn data per test, cleanup, rollback
Unordered resultsAsserting list order from a query with no ORDER BYAdd ordering or containsExactlyInAnyOrder
Async and threadsThread.sleep(500) then assertAwaitility: await().atMost(5, SECONDS).untilAsserted(...)
External systemsCalling a real payment or mail APIMock, WireMock/MockWebServer, or a container
EnvironmentFixed ports, time zone, locale, file paths, Windows vs Linux newlineRandom ports, explicit time zone and locale, Path APIs
ResourcesDocker not ready, CI under load, timeouts too tightWait strategies, generous timeouts, retry only the infrastructure step

Never "fix" a flaky test by adding a retry or @Disabled without finding the cause. Reproduce it by running the test in a loop, read the failure, fix the cause.

Habits of strong teams

  • Test the unhappy paths: not found, validation failure, duplicate, forbidden, empty list, boundary values (0, 1, max).
  • When you fix a bug, first write a test that fails because of it (regression test).
  • Keep tests readable: a new teammate should understand a test without opening the production code. Prefer clear duplication over clever shared helpers that hide the scenario.
  • Treat test code like production code: review it, refactor it, delete obsolete tests.
  • Do not assert on log output or private methods. Do not test third-party libraries.

Real projects

A typical Spring Boot pull request contains: unit tests for new service logic, a @WebMvcTest for a new endpoint (success plus 400/401/403/404), a repository test for any new query, and the existing integration flows still green. Reviewers reject changes that lower coverage on business code or that add Thread.sleep.

Interview angle

"What makes a good unit test?" FIRST, one behaviour, Arrange-Act-Assert, descriptive name, no logic, no real I/O. "What is a flaky test and how do you handle it?" Name causes (time, order, async, shared state) and fixes (Clock, isolation, Awaitility), and say you never ignore it. "TDD in one minute?" Red (failing test), green (smallest code), refactor.

Interview questions — Testing

Explain the testing pyramid and what you test at each level in a Spring Boot app.

Many fast unit tests at the base (services with Mockito), fewer slice tests (@WebMvcTest for controllers, @DataJpaTest for repositories), a few @SpringBootTest integration flows with a real database, and very few end-to-end tests. Each check goes to the lowest level that can prove it, because upper levels are slower and fail for more reasons.

What is the difference between @Mock, @InjectMocks, @MockBean/@MockitoBean and @Spy?

@Mock creates a Mockito fake (plain unit tests with MockitoExtension). @InjectMocks creates the real object under test and injects those fakes. @MockitoBean (earlier @MockBean) puts a Mockito mock into the Spring context, replacing the bean, for slice and integration tests. @Spy wraps a real object so that only the stubbed methods are faked.

What is UnnecessaryStubbingException?

With MockitoExtension stubs are strict: a when(...) that the test never triggers fails the test. It points to dead set-up or a wrong assumption about what the code calls. Remove the stub, or use lenient() for shared set-up in @BeforeEach.

Why can't you write when(mock.voidMethod()) and what do you use instead?

A void method has no value to pass to when, so it does not compile. Use the action-first forms doThrow(...).when(mock).voidMethod() or doNothing(). The same style, doReturn(x).when(spy).method(), is needed with spies so the real method is not called while stubbing.

What is the rule for argument matchers?

If any argument of a call uses a matcher (any(), anyString()), all arguments must use matchers; wrap literals in eq(). Mixing them throws InvalidUseOfMatchersException.

When do you use verify, and when does it hurt?

Use verify for side effects that are the point of the behaviour: an e-mail was sent, a save happened, nothing was deleted. Over-verifying every interaction (or verifyNoMoreInteractions everywhere) couples tests to the implementation, so refactoring breaks them. When a result is returned, assert the result instead.

What does @WebMvcTest load, and how do you test a secured endpoint?

Only the web layer: controllers, advice, filters, converters and security auto-configuration; services need @MockitoBean. Import your SecurityConfig. With spring-security-test use @WithMockUser(roles = ...) or .with(jwt().authorities(...)), add csrf() when CSRF is enabled, and test both 401 (no auth) and 403 (wrong role).

How do you test validation errors and error responses for a POST endpoint?

Post invalid JSON with MockMvc (content type JSON), expect status().isBadRequest(), assert the ProblemDetail fields with jsonPath, and verifyNoInteractions(service) to show the service was never reached. Likewise, make the mocked service throw ResourceNotFoundException and expect 404.

What does @DataJpaTest do and why not use H2 for it?

It starts only JPA: entities, repositories, TestEntityManager, a transaction rolled back after each test. By default it swaps your database for an embedded one. H2 differs from PostgreSQL in SQL dialect, functions, case rules, locking and migrations, so tests can pass while production fails. Use Testcontainers with @AutoConfigureTestDatabase(replace = NONE). Call flush() and clear() so SQL really runs.

@SpringBootTest MOCK vs RANDOM_PORT?

MOCK (default) loads the full context with a mock servlet environment and no port; you call it with MockMvc, in the same thread, so @Transactional rollback works. RANDOM_PORT starts a real embedded server on a free port, injected with @LocalServerPort, and you use an HTTP client; the server handles requests on its own threads and transactions.

Why is my Spring test suite slow, and what is context caching?

Spring caches each distinct application context and reuses it across test classes. Different @MockitoBean sets, properties, profiles or @DirtiesContext create new contexts (seconds each), and starting a Testcontainers database per class adds more. Fix with one shared base class, a shared container, fewer integration tests and no @DirtiesContext.

How does Testcontainers work with Spring Boot, and what does @ServiceConnection do?

Testcontainers starts a real PostgreSQL in Docker for the tests. A static @Container field (or a container bean in a @TestConfiguration) annotated with @ServiceConnection (Boot 3.1+) makes Boot derive the datasource URL, user and password from the container; before that you used @DynamicPropertySource. Docker must be running, and a shared container keeps the suite fast.

Line coverage vs branch coverage, and is 100% coverage the goal?

Line coverage counts executed lines; branch coverage counts the outcomes of decisions (both sides of an if), so it is stricter. 100 percent is not the goal: coverage shows what is untested, not whether tests assert anything. Use it to find missing scenarios, set a modest threshold on business code, and review assertion quality.

What is a flaky test and how do you fix one?

One that passes and fails without code changes. Causes: time (now()), randomness, test order or shared data, unordered results, Thread.sleep with async code, external services, environment differences. Fix the cause: inject a Clock, isolate data, containsExactlyInAnyOrder or ORDER BY, Awaitility, mocks or containers. Do not just retry or disable it.

Cheat sheet — Testing

  • Pyramid unit (many, ms) then slice then integration then end-to-end (few).
  • AAA Arrange, Act, Assert (= Given, When, Then); one behaviour per test.
  • Naming method_condition_expected or shouldXWhenY; test tree mirrors main.
  • Starter spring-boot-starter-test: JUnit 5, Mockito, AssertJ, Spring Test, JsonPath; add spring-security-test.
  • JUnit @Test, @BeforeEach, @AfterEach, static @BeforeAll, @Nested, @DisplayName, @Disabled, @Tag.
  • Parameterized @ParameterizedTest with @ValueSource, @CsvSource, @MethodSource, @EnumSource.
  • Mockito setup @ExtendWith(MockitoExtension.class), @Mock, @InjectMocks, @Spy, @Captor.
  • Stubbing when(x).thenReturn/thenThrow/thenAnswer; void or spy: doThrow/doNothing/doReturn(...).when(m).
  • Matchers any(), eq(); all-or-none rule.
  • Verify verify(m), times(n), never(), verifyNoInteractions; use sparingly.
  • Strict stubs unused stub gives UnnecessaryStubbingException; lenient() as exception.
  • Do not mock the SUT, value objects, collections; prefer a Clock to static mocks.
  • AssertJ assertThat, extracting, containsExactly, hasSize, assertThatThrownBy, SoftAssertions.
  • @WebMvcTest controller + advice + security only; MockMvc, @MockitoBean for services, @Import your config.
  • MockMvc perform(post(...).contentType(JSON).content(...)), status(), jsonPath(), andDo(print()).
  • Security tests @WithMockUser, jwt(), csrf(); always test 401 and 403.
  • @MockitoBean replaces @MockBean (Boot 3.4+, only one in Boot 4).
  • @DataJpaTest JPA slice, rollback per test, TestEntityManager, flush() + clear(), Replace.NONE for real DB.
  • @SpringBootTest full context; MOCK + MockMvc or RANDOM_PORT + client; few of them.
  • Test config @ActiveProfiles("test"), application-test.yml, @TestConfiguration, @Sql, avoid @DirtiesContext.
  • Context cache same config gives same context; vary mocks or properties and you pay a new startup.
  • Testcontainers Docker running; static @Container + @ServiceConnection; shared container via config/base class.
  • Surefire / Failsafe *Test with mvn test; *IT with mvn verify.
  • JaCoCo prepare-agent + report; HTML in target/site/jacoco; branch coverage is stricter; coverage is not quality.
  • FIRST Fast, Independent, Repeatable, Self-validating, Timely; fix flaky tests at the cause.

Practice — Testing

  1. Warm-up unit tests. Write SalaryRangeTest or a similar pure-Java test with JUnit 5 and AssertJ: a normal case, a boundary, and a @ParameterizedTest with @CsvSource for invalid input. Done when mvn test -Dtest=SalaryRangeTest is green and each test name states the expected result.
  2. Unit-test the services of Project 2. Write JobServiceTest and ApplicationServiceTest with Mockito: create, update by owner, update by another recruiter (forbidden), admin override, not found, duplicate application, apply to a closed job. Use ArgumentCaptor once and verify(..., never()) once. Done when every branch of the services' public methods is covered and no test starts Spring.
  3. Break it on purpose. Add an unused stub and a mixed-matcher call, read the two Mockito exceptions, and fix them. Done when you can explain both messages.
  4. MockMvc tests for controllers. For JobController and AuthController write @WebMvcTest tests: 200 and 201 responses, 400 for invalid JSON, 404 via a mocked ResourceNotFoundException, 401 without token, 403 for a CANDIDATE posting a job. Done when each endpoint has a success test and at least two failure tests, and $.password never appears in any response.
  5. Repository tests. Write a @DataJpaTest for every custom query (for example jobs by recruiter, search by title ignoring case, applications by job). Use flush() and clear(). Done when a deliberately broken query (wrong field) makes a test fail.
  6. One Testcontainers integration test. Add TestcontainersConfig and AbstractIntegrationTest with PostgreSQL and your Flyway migrations. Write JobFlowIT: register a recruiter and a candidate, log in, post a job, apply, and check that the candidate cannot edit the job and the other recruiter gets 403. Done when it passes with Docker Desktop running and your Flyway migrations are applied on startup.
  7. Switch repository tests to PostgreSQL. Run the @DataJpaTest tests with Replace.NONE and the shared container. Add a native query using a PostgreSQL feature (such as ilike) and show it would fail on H2. Done when all repository tests run against the container.
  8. Measure coverage. Add JaCoCo and run mvn clean verify. Open target/site/jacoco/index.html, find the three least-covered service methods, and add tests for the missed branches. Done when business packages are above 70 percent line coverage, with a short note on one thing the percentage cannot tell you.
  9. Make the suite green and fast. Check the log for how many Spring contexts start; reduce them with a common base class. Split names into *Test and *IT, enable Failsafe, and run both mvn test and mvn verify. Done when Project 2 passes all its tests with mvn test (and mvn verify if you keep ITs separate) with no @Disabled and no sleeps.
  10. CI. Add the GitHub Actions workflow from this module and push a deliberately failing test to a branch. Done when the pull request shows a red check and turns green after the fix (DevOps · Module 4).

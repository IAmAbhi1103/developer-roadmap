Loading users from the database: User, UserDetailsService and registration

Store users with a hashed password and a role, implement UserDetailsService to load them by email, wrap them in a UserDetails with the account-status flags, and offer a registration endpoint that hashes the password before saving.

Spring Security does not know your User table. You teach it in two small steps: a class that describes a user in Security's terms (UserDetails), and a service that fetches that class from your database (UserDetailsService). Registration is the other half: how users get into the table with a safe password hash.

The User entity and roles

Project 2 already has a User entity from module 3. For security it needs three things: a unique login name (we use the email), a password hash (never the password), and a role. Roles are an enum stored as text.

public enum Role {
    CANDIDATE, RECRUITER, ADMIN
}
@Entity
@Table(name = "app_user")
public class User extends BaseEntity {

    @Column(nullable = false)
    private String name;

    @Column(nullable = false, unique = true)
    private String email;

    @Column(name = "password_hash", nullable = false)
    private String passwordHash;           // BCrypt hash, 60 characters

    @Enumerated(EnumType.STRING)           // never ORDINAL: reordering would break data
    @Column(nullable = false, length = 20)
    private Role role;

    private boolean enabled = true;
    private boolean locked = false;

    // constructor, getters; no setter for passwordHash except changePassword(hash)
}

One role or many?

One role per user keeps Project 2 simple and covers most apps. If a user can hold several, map Set<Role> with @ElementCollection and @Enumerated(EnumType.STRING); the rest of this module (authorities as a list) works unchanged. Load the roles together with the user (@EntityGraph), because login happens outside any long transaction.

UserDetails and UserDetailsService

UserDetails is Spring Security's view of a user: name, password hash, authorities, and four status flags. UserDetailsService has one method, loadUserByUsername(String), and is how DaoAuthenticationProvider finds the user. "Username" is just the login identifier; here it is the email.

public class AppUserDetails implements UserDetails {

    private final Long id;
    private final String email;
    private final String passwordHash;
    private final Role role;
    private final boolean enabled;
    private final boolean accountNonLocked;

    public AppUserDetails(User u) {
        this.id = u.getId();
        this.email = u.getEmail();
        this.passwordHash = u.getPasswordHash();
        this.role = u.getRole();
        this.enabled = u.isEnabled();
        this.accountNonLocked = !u.isLocked();
    }

    public Long getId() { return id; }
    public Role getRole() { return role; }

    @Override public Collection<? extends GrantedAuthority> getAuthorities() {
        return List.of(new SimpleGrantedAuthority("ROLE_" + role.name()));
    }
    @Override public String getPassword() { return passwordHash; }
    @Override public String getUsername() { return email; }
    @Override public boolean isAccountNonExpired() { return true; }
    @Override public boolean isAccountNonLocked() { return accountNonLocked; }
    @Override public boolean isCredentialsNonExpired() { return true; }
    @Override public boolean isEnabled() { return enabled; }
}
@Service
public class DbUserDetailsService implements UserDetailsService {

    private final UserRepository userRepository;

    public DbUserDetailsService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @Override
    @Transactional(readOnly = true)
    public UserDetails loadUserByUsername(String email) {
        return userRepository.findByEmailIgnoreCase(email)
                .map(AppUserDetails::new)
                .orElseThrow(() -> new UsernameNotFoundException("User not found"));
    }
}

The repository method is a derived query: Optional<User> findByEmailIgnoreCase(String email);. With a UserDetailsService bean and a PasswordEncoder bean in the context, Spring Boot wires DaoAuthenticationProvider for you, and the generated default user disappears.

For a small app you can skip the custom UserDetails class and return Spring's own builder instead. The catch is that you then lose extra fields like the user id, and you must use the full class name because it clashes with your entity:

return org.springframework.security.core.userdetails.User
        .withUsername(u.getEmail())
        .password(u.getPasswordHash())
        .roles(u.getRole().name())          // adds the ROLE_ prefix itself
        .disabled(!u.isEnabled())
        .accountLocked(u.isLocked())
        .build();

How DaoAuthenticationProvider uses them

When a login request reaches the AuthenticationManager, it delegates to DaoAuthenticationProvider. This is the exact order of work, and it explains every exception you will see:

  1. It receives a UsernamePasswordAuthenticationToken holding the email and the raw password the user typed.
  2. It calls userDetailsService.loadUserByUsername(email). If your service throws UsernameNotFoundException, the provider by default converts it into BadCredentialsException ("Bad credentials") so the caller cannot tell a wrong email from a wrong password. When the user is not found it still runs one password hash comparison against a dummy hash, so the response time does not reveal which emails exist (a protection against timing attacks).
  3. Pre-checks: it rejects a locked, disabled or expired account (LockedException, DisabledException, AccountExpiredException) before checking the password.
  4. It calls passwordEncoder.matches(rawPassword, user.getPassword()). A mismatch is a BadCredentialsException.
  5. Post-check: expired credentials give CredentialsExpiredException.
  6. On success it builds a new, authenticated Authentication with the UserDetails as principal and its authorities. The raw password is not kept.

Your login endpoint calls the manager directly. The result is an authenticated principal whose id and role you put into the JWT (JWT basics). The matching of the hash itself is explained in password hashing.

public AppUserDetails login(String email, String password) {
    Authentication auth = authenticationManager.authenticate(
            new UsernamePasswordAuthenticationToken(email, password));
    return (AppUserDetails) auth.getPrincipal();     // then create the token from it
}

The AuthenticationManager bean is not created by default. Expose it from the configuration:

@Bean
AuthenticationManager authenticationManager(AuthenticationConfiguration config)
        throws Exception {
    return config.getAuthenticationManager();
}

The account-status flags

FlagMeaningException on failure
isEnabled()Account is active (email verified, not deleted)DisabledException
isAccountNonLocked()Not locked, e.g. after too many failed loginsLockedException
isAccountNonExpired()Account validity not over (trial accounts)AccountExpiredException
isCredentialsNonExpired()Password not too oldCredentialsExpiredException

All of them extend AccountStatusException or AuthenticationException, so a login failure becomes a 401. Returning one generic message ("Invalid email or password") for all of them is safer than telling an attacker which accounts exist. One caution: DisabledException and LockedException are thrown only after the user was found, so a different message for them does reveal that the email exists. Map all of them to the same public message in your error handler.

Registration endpoint

Registration creates a user and hashes the password. The caller may choose CANDIDATE or RECRUITER; ADMIN accounts are created by seed data or by another admin, never by the public endpoint. Otherwise anyone could register as ADMIN, a classic privilege-escalation bug.

public record RegisterRequest(
        @NotBlank @Size(max = 100) String name,
        @NotBlank @Email String email,
        @NotBlank @Size(min = 8, max = 72) String password,
        @NotNull Role role) {}
@Service
public class AuthService {

    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;

    public AuthService(UserRepository userRepository, PasswordEncoder passwordEncoder) {
        this.userRepository = userRepository;
        this.passwordEncoder = passwordEncoder;
    }

    @Transactional
    public UserResponse register(RegisterRequest req) {
        if (req.role() == Role.ADMIN) {
            throw new AccessDeniedException("Cannot self-register as ADMIN");
        }
        if (userRepository.existsByEmailIgnoreCase(req.email())) {
            throw new DuplicateResourceException("Email already registered");
        }
        User user = new User(req.name(), req.email().toLowerCase(),
                passwordEncoder.encode(req.password()), req.role());
        return UserResponse.from(userRepository.save(user));
    }
}
@RestController
@RequestMapping("/api/auth")
public class AuthController {
    // fields + constructor omitted

    @PostMapping("/register")
    @ResponseStatus(HttpStatus.CREATED)
    public UserResponse register(@Valid @RequestBody RegisterRequest req) {
        return authService.register(req);
    }
}

Seeding the first ADMIN

Because the public endpoint refuses ADMIN, the first admin comes from a one-time seed. A runner that reads the password from the environment is a simple option (never hard-code it):

@Component
class AdminSeeder implements CommandLineRunner {

    private final UserRepository users;
    private final PasswordEncoder encoder;
    private final String adminPassword;

    AdminSeeder(UserRepository users, PasswordEncoder encoder,
                @Value("${app.admin.password:}") String adminPassword) {
        this.users = users;
        this.encoder = encoder;
        this.adminPassword = adminPassword;
    }

    @Override
    public void run(String... args) {
        if (!adminPassword.isBlank() && !users.existsByEmailIgnoreCase("admin@example.com")) {
            users.save(new User("Admin", "admin@example.com",
                    encoder.encode(adminPassword), Role.ADMIN));
        }
    }
}

Rules

  • Store only a hash made by a PasswordEncoder; the same encoder bean must be used for registration and for login.
  • loadUserByUsername must never return null; throw UsernameNotFoundException when the user is missing.
  • The role stored in the database is the plain name (RECRUITER); the authority is ROLE_RECRUITER.
  • The public registration endpoint must not accept ADMIN.

Conventions

  • Keep the entity free of Spring Security types; wrap it in a separate UserDetails class, as above.
  • Normalise the email (lower case, trimmed) once, in the service, and query case-insensitively.
  • Add a unique index on the normalised email; it is the real protection against duplicates.
  • Put registration and login in an AuthService, not in the controller.

Common mistakes

  • Letting the request body set the role without a whitelist (mass assignment).
  • Case-sensitive email lookup: Asha@x.com and asha@x.com become two accounts. Normalise to lower case.
  • Returning the User entity from a controller: the hash leaks into JSON.
  • Throwing a different message for "unknown email" and "wrong password" (user enumeration).

Wrong: plain password saved, role from the client

User u = new User(req.name(), req.email(), req.password(), req.role());
userRepository.save(u);        // plain text; ADMIN accepted

Right: hash it, restrict the role

if (req.role() == Role.ADMIN) throw new AccessDeniedException("no");
String hash = passwordEncoder.encode(req.password());
userRepository.save(new User(req.name(), email, hash, req.role()));

Edge cases and exceptions

  • UsernameNotFoundException is hidden as BadCredentialsException by default. If you set hideUserNotFoundExceptions to false yourself, the real reason leaks.
  • LazyInitializationException in getAuthorities(): you read a lazy role collection outside a transaction. Copy the data in the constructor of AppUserDetails, inside the transactional loadUserByUsername, as above.
  • IllegalArgumentException: There is no PasswordEncoder mapped for the id "null" means the stored value has no {bcrypt} prefix while you use a delegating encoder. Use a plain BCryptPasswordEncoder bean (as in the config article) or store the prefix.
  • DataIntegrityViolationException on save: duplicate email under a race; return 409.
  • A user who is deleted or disabled after receiving a JWT keeps a valid token until it expires, because stateless checks do not call the database. Keep access tokens short (refresh tokens).

Real projects

Real systems add email verification (the user starts with enabled = false and a verification link flips it), a failed-login counter that sets locked for 15 minutes, password reset by a one-time token mailed to the user, and a rule that the first ADMIN comes from a deployment seed or a migration script. Many teams also record createdAt and lastLoginAt (auditing).

Interview angle

"How does Spring Security load a user?" DaoAuthenticationProvider calls your UserDetailsService.loadUserByUsername, gets a UserDetails, checks the flags, then compares the password with PasswordEncoder.matches. Follow-up: "What does UsernameNotFoundException become?" By default BadCredentialsException, to hide which part was wrong. Another favourite: "How do you stop a user registering as ADMIN?" Whitelist the role in the service; admins are created by seed or by another admin. And: "Why store a hash, not the password?" See password hashing.

Password hashing with BCrypt

Never store passwords or encrypt them; store a salted, deliberately slow hash such as BCrypt, check logins with PasswordEncoder.matches, and use DelegatingPasswordEncoder so the algorithm can change later.

Why hash, and why not encrypt

If your database leaks (it happens to big companies), the attacker must not get passwords. Plain text is the worst choice. Encryption is reversible: whoever has the key (and the key is usually on the same server) gets every password back. A hash is a one-way function: you can turn a password into a hash, but not a hash back into the password. At login you hash the typed password and compare hashes.

Encryption (AES)Fast hash (SHA-256)Password hash (BCrypt)
ReversibleYes, with keyNoNo
Saltedn/aOnly if you add oneYes, automatically
SpeedFastBillions per second on a GPUDeliberately slow, tunable
Use for passwordsNoNoYes

Two problems remain with a plain hash. First, equal passwords give equal hashes, and attackers keep huge tables of common passwords and their hashes (rainbow tables). A salt fixes this: a random value added to each password before hashing, so two users with password123 get different hashes and precomputed tables are useless. Second, SHA-256 is designed to be fast, so an attacker can try billions of guesses per second. A password hash must be slow on purpose: a work factor makes each guess expensive, and you can raise it as computers get faster.

BCrypt

BCrypt generates its own random 16-byte salt, applies a slow key-derivation, and writes everything into one 60-character string:

$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
 |  |  |                     |
 |  |  |                     +-- 31 characters of hash
 |  |  +-- 22 characters of salt
 |  +-- cost factor (work factor): 2^10 rounds
 +-- algorithm version

Because salt and cost are inside the string, you store just this one column and need no separate salt column. The cost factor is the exponent: strength 10 means 210 = 1,024 rounds; every +1 doubles the time. The default of BCryptPasswordEncoder is 10 (allowed 4 to 31). Choose a value so that one hash takes roughly 100–300 ms on your production hardware; raising it to 12 is common today. Too high and a login burst becomes a denial-of-service on your own CPU.

  • encode(raw) returns a new hash every time, so you can never compare hashes with equals.
  • matches(raw, stored) reads the salt and cost from stored, hashes raw the same way and compares in constant time.
  • upgradeEncoding(stored) says whether the hash should be recomputed with a newer setting (used by DaoAuthenticationProvider to upgrade hashes at login).

DelegatingPasswordEncoder and the {bcrypt} prefix

Algorithms age. PasswordEncoderFactories.createDelegatingPasswordEncoder() returns an encoder that writes an id in front of the hash and uses that id to pick the algorithm at check time:

{bcrypt}$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
{argon2@SpringSecurity_v5_8}...   (another algorithm; different prefix)
@Bean
PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}

New passwords use the current default (bcrypt); old rows with another prefix still work; you migrate users gradually. If a stored value has no prefix you get IllegalArgumentException: There is no PasswordEncoder mapped for the id "null". Either add the prefix to old data, or use a plain BCryptPasswordEncoder bean. For a new app that will never change algorithm, a plain BCryptPasswordEncoder is fine; the delegating form is the framework default and the safer long-term choice. Spring also provides Argon2PasswordEncoder (needs the Bouncy Castle library), SCryptPasswordEncoder and Pbkdf2PasswordEncoder.

Limits and good habits

  • 72-byte limit. BCrypt only uses the first 72 bytes of the password, so the rest is ignored (some library versions reject longer input with an exception instead). Limit the password length in validation (@Size(max = 72), as in the DTO above). Do not pre-hash with SHA-256 unless you know exactly why.
  • Never log or return a password or a hash. Check toString() of request records (a record prints all its fields), Lombok @Data classes, and request-logging filters.
  • Do not invent your own scheme ("MD5 twice with a pepper"). Use the framework.
  • Password rules: minimum length matters more than odd character rules; check against a list of leaked passwords if you can.
  • Hashing is slow. That is the point, but it means the login endpoint needs rate limiting (checklist).

Rule: compare with matches, never equals

A salted hash differs every time. Always call passwordEncoder.matches(raw, stored).

Common mistakes

  • Saving request.password() directly, so the database holds plain text.
  • Hashing the password twice: once in the controller and once in the service, so login can never match.
  • Using MD5 or SHA-1 because "it is hashing too".
  • Seeding test users with a plain password in SQL, then wondering why login fails (generate the BCrypt hash first).

Interview angle

"How do you store passwords?" Salted adaptive hash (BCrypt/Argon2), one-way, work factor tunable; never encryption, never plain SHA. "What is a salt?" Random per-user value stored with the hash, defeats rainbow tables and makes equal passwords differ. "Why is BCrypt slow on purpose?" To make brute force expensive. "What is the {bcrypt} prefix?" DelegatingPasswordEncoder id, used to support several algorithms and migrate.

JWT in depth: structure, claims, signing and the login flow

A JWT is a signed JSON document (header.payload.signature) that proves who the user is without server-side storage; anyone can read it but nobody can change it without the key, and it is valid until it expires.

What and why

A JSON Web Token (JWT, pronounced "jot") is a compact string that carries claims about a user and a signature that proves the server issued it. After login the server gives one to the client; the client sends it with each request; the server verifies the signature and trusts the claims inside, with no database or session lookup. That is what makes the API stateless (see sessions vs tokens).

Structure

A JWT has three parts separated by dots, each encoded with base64url (base64 with - and _ instead of + and /, no padding):

eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsInJvbGVzIjpbIlJFQ1JVSVRFUiJdfQ.Sx3...k9A
{
  "alg": "HS256",
  "typ": "JWT"
}
{
  "iss": "jobportal-api",
  "sub": "42",
  "roles": ["RECRUITER"],
  "iat": 1790000000,
  "exp": 1790003600
}

The signature (part 3) is computed over base64url(header) + "." + base64url(payload) with the secret key (or private key). If anybody changes one character of the payload, the signature no longer matches and verification fails.

Rule: the payload is readable by everyone

Base64url is encoding, not encryption. Paste any JWT into a decoder and you see the claims. Never put passwords, card numbers, or secrets in a JWT. Put identifiers and roles only. (An encrypted token format, JWE, exists but is rarely needed.)

Claims

ClaimNameMeaning
subSubjectWho the token is about: the user id (or email)
issIssuerWho created it, e.g. jobportal-api; check it on validation
audAudienceWho it is meant for (which API); check it when several services exist
iatIssued atCreation time (seconds since 1970)
expExpirationAfter this time the token is invalid
nbfNot beforeNot valid before this time
jtiJWT IDUnique id, useful for revocation lists
roles, scopeCustomYour own claims (keep them small)

Times are numbers in seconds, not milliseconds, a frequent source of "token expired in 1970" bugs when you mix them up.

Signing: HS256 vs RS256

HS256 (HMAC-SHA256)RS256 (RSA + SHA-256)
Key typeOne shared secretKey pair: private signs, public verifies
Who can create tokensAnyone who has the secret (every verifier)Only the holder of the private key
Who can verifyAnyone who has the secretAnyone with the public key (can be published, e.g. JWKS)
SpeedVery fastSlower signing
UseOne application issuing and verifying its own tokensSeparate auth server and many resource servers; microservices; third-party login

Project 2 has one application, so HS256 is enough. The HS256 secret must be long and random (at least 256 bits = 32 bytes) and come from an environment variable or secret store, never from the Git repository. Moving to RS256 later is a configuration change when you use the Spring support.

The login flow

  1. The client sends the email and password once to the public login endpoint (over HTTPS).
  2. The controller calls AuthenticationManager.authenticate, which runs the DaoAuthenticationProvider path from the architecture article. A wrong password throws and becomes 401.
  3. On success the server builds a JWT with the user id, roles and an expiry (for example 15–60 minutes) and signs it.
  4. The client keeps the token and sends Authorization: Bearer <token> on each call.
  5. A filter verifies signature, expiry (and issuer), creates an Authentication from the claims, and stores it in the SecurityContext for this request.
  6. URL rules, method security and your controller now see the current user.

Expiry and what JWT cannot do

The server holds no record of issued tokens, so it cannot "log out" a token: until exp passes, any holder is accepted. That is why access tokens are short-lived and paired with a refresh token (refresh tokens). Roles inside the token are also a snapshot: if an admin removes a user's role, the old token still carries it until it expires. Keep the lifetime short, or look the user up on each request when you need immediate effect.

Common mistakes

  • A weak or hard-coded secret ("secret", "mykey") committed to GitHub. Anyone can then forge an ADMIN token.
  • Putting personal or sensitive data in the payload.
  • Accepting tokens without checking expiry, or setting a lifetime of months.
  • Trusting the alg header from the token (the old "alg: none" attack). Libraries today reject it; always configure the expected algorithm yourself.
  • Treating JWT as a replacement for authorization: the token says who the user is, your code must still check ownership.

Interview angle

"What is a JWT and how is it verified?" Three base64url parts; the server recomputes the signature with the key and checks exp/iss. "Is the payload secret?" No, only tamper-proof. "HS256 vs RS256?" Shared secret vs key pair. "How do you invalidate a JWT?" You mostly cannot; use short expiry, refresh-token rotation, or a deny list keyed by jti.

The TokenService contract

The login controller depends on a small interface, so you can swap the implementation (this one, or the Nimbus one) without touching the controller.

public interface TokenService {
    String issueAccessToken(AppUserDetails user);
}

JjwtService: create and parse tokens

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.io.Decoders;
import io.jsonwebtoken.security.Keys;
import javax.crypto.SecretKey;

@Service
public class JjwtService implements TokenService {

    private final SecretKey key;
    private final String issuer;
    private final Duration ttl;

    public JjwtService(JwtProperties props) {
        this.key = Keys.hmacShaKeyFor(Decoders.BASE64.decode(props.secret()));
        this.issuer = props.issuer();
        this.ttl = Duration.ofMinutes(props.accessTtlMinutes());
    }

    @Override
    public String issueAccessToken(AppUserDetails user) {
        Instant now = Instant.now();
        return Jwts.builder()
                .issuer(issuer)
                .subject(String.valueOf(user.getId()))
                .claim("email", user.getUsername())
                .claim("roles", List.of(user.getRole().name()))
                .issuedAt(Date.from(now))
                .expiration(Date.from(now.plus(ttl)))
                .signWith(key)                 // HS256 chosen from the key size
                .compact();
    }

    /** Verifies signature, expiry and issuer. Throws JwtException if invalid. */
    public Claims parse(String token) {
        return Jwts.parser()
                .verifyWith(key)
                .requireIssuer(issuer)
                .build()
                .parseSignedClaims(token)
                .getPayload();
    }
}

Keys.hmacShaKeyFor throws WeakKeyException if the key is shorter than 256 bits for HS256, which is a useful safety net. parseSignedClaims only accepts a signed token (an unsigned or "alg: none" token fails). The parser checks exp and nbf itself.

What the parser can throw

ExceptionMeaning
ExpiredJwtExceptionexp is in the past
SignatureExceptionSignature does not match (tampered or wrong key)
MalformedJwtExceptionNot a valid JWT structure
UnsupportedJwtExceptionUnexpected token type (e.g. unsigned)

The filter

OncePerRequestFilter guarantees one execution per request. The filter's job: read the header, validate the token, and store an Authentication. It does not write error responses itself; if the token is missing or bad it simply leaves the context empty and lets the rest of the chain decide (a protected URL then triggers the authentication entry point, which returns 401).

public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private static final String PREFIX = "Bearer ";
    private final JjwtService jwtService;

    public JwtAuthenticationFilter(JjwtService jwtService) {
        this.jwtService = jwtService;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain)
            throws ServletException, IOException {

        String header = request.getHeader(HttpHeaders.AUTHORIZATION);
        if (header == null || !header.startsWith(PREFIX)) {
            chain.doFilter(request, response);          // anonymous request
            return;
        }
        try {
            Claims claims = jwtService.parse(header.substring(PREFIX.length()));
            List<?> roles = claims.get("roles", List.class);
            List<SimpleGrantedAuthority> authorities = roles.stream()
                    .map(r -> new SimpleGrantedAuthority("ROLE_" + r))
                    .toList();

            var auth = new UsernamePasswordAuthenticationToken(
                    claims.getSubject(), null, authorities);   // principal = user id
            auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
            SecurityContextHolder.getContext().setAuthentication(auth);
        } catch (JwtException | IllegalArgumentException e) {
            SecurityContextHolder.clearContext();       // bad token: stay anonymous
            request.setAttribute("auth.error", e.getClass().getSimpleName());
        }
        chain.doFilter(request, response);
    }
}

The three-argument UsernamePasswordAuthenticationToken constructor creates an authenticated token (the two-argument one is "not yet authenticated"). The principal here is the user id as a string, so authentication.getName() returns "42". We read the roles from the token and trust the signature; there is no database call per request. If you need fresh account status (disabled users blocked immediately), load the user inside the filter instead, at the cost of one query per request (or a short cache).

Registering the filter and exposing the AuthenticationManager

@Configuration
@EnableWebSecurity
@EnableMethodSecurity
@EnableConfigurationProperties(JwtProperties.class)
public class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http, JjwtService jwtService,
                            JsonSecurityHandlers handlers) throws Exception {
        http
            .csrf(csrf -> csrf.disable())
            .cors(Customizer.withDefaults())
            .sessionManagement(s ->
                    s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .httpBasic(b -> b.disable())
            .formLogin(f -> f.disable())
            .exceptionHandling(e -> e
                    .authenticationEntryPoint(handlers)      // 401 JSON
                    .accessDeniedHandler(handlers))          // 403 JSON
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers("/api/auth/**").permitAll()
                    .requestMatchers(HttpMethod.GET, "/api/jobs/**").permitAll()
                    .anyRequest().authenticated())
            .addFilterBefore(new JwtAuthenticationFilter(jwtService),
                    UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }

    @Bean
    AuthenticationManager authenticationManager(AuthenticationConfiguration cfg)
            throws Exception {
        return cfg.getAuthenticationManager();
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }
}

JsonSecurityHandlers is defined in the error-response article. Note that the filter is created with new inside the configuration and is not annotated with @Component: Spring Boot registers every Filter bean in the servlet container too, so a @Component filter would run twice (once outside and once inside the security chain). If you prefer a bean, add a FilterRegistrationBean with setEnabled(false).

The login controller

public record LoginRequest(@NotBlank @Email String email, @NotBlank String password) {}

public record TokenResponse(String accessToken, String tokenType, long expiresIn) {}
@PostMapping("/login")
public TokenResponse login(@Valid @RequestBody LoginRequest req) {
    Authentication auth = authenticationManager.authenticate(
            UsernamePasswordAuthenticationToken.unauthenticated(
                    req.email().toLowerCase(), req.password()));
    AppUserDetails user = (AppUserDetails) auth.getPrincipal();
    String token = tokenService.issueAccessToken(user);
    return new TokenResponse(token, "Bearer", 1800);
}

A wrong password makes authenticate throw BadCredentialsException. Because this happens inside a controller (after the filter chain), ExceptionTranslationFilter is not involved; handle AuthenticationException in your @RestControllerAdvice and return 401 with the same generic message for every cause.

@ExceptionHandler(AuthenticationException.class)
ProblemDetail loginFailed(AuthenticationException ex) {
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(
            HttpStatus.UNAUTHORIZED, "Invalid email or password");
    pd.setTitle("Authentication failed");
    return pd;
}

Expired and invalid tokens

With this design an expired token makes the filter catch ExpiredJwtException, leave the request anonymous, and the protected URL returns 401. The client reads 401, uses its refresh token (or sends the user to the login screen) and retries. To tell the client why, read the auth.error request attribute in your entry point and put "token_expired" or "token_invalid" in the JSON body.

Common mistakes

  • Annotating the filter with @Component (double registration) or forgetting addFilterBefore, so the filter never runs.
  • Catching the exception and writing a 500 or a stack trace, or swallowing it and still authenticating.
  • Mixing seconds and milliseconds in exp, or using the 0.11 API names with the 0.12 jar.
  • Reading the secret with getBytes() when it is stored as Base64 (or the other way round); both ends must agree.
  • Forgetting permitAll() on the login URL, so nobody can ever log in.

Interview angle

"Walk me through JWT authentication in Spring Boot." Login controller authenticates through the AuthenticationManager and returns a signed token; a OncePerRequestFilter placed before UsernamePasswordAuthenticationFilter reads the Bearer header, validates it, sets the SecurityContext; the stateless session policy means every request repeats this. Mention failure behaviour: invalid token leaves the request anonymous, so the entry point returns 401.

@Async, thread pools and virtual threads

@Async runs a method on another thread through a proxy so the caller does not wait; configure your own ThreadPoolTaskExecutor, handle exceptions explicitly, remember that transactions, security context and MDC do not follow the new thread, and consider virtual threads for blocking work.

What and why

When a candidate applies for a job, the API must save the application and then email the recruiter. Sending email takes 300 ms to 3 seconds and can fail. The candidate should not wait for it. Asynchronous execution means: start the work on another thread and return immediately. Spring does this with @Async. (Threads, executors and CompletableFuture themselves are explained in Core Java · Module 6.)

Setup and basic use

@Configuration
@EnableAsync
class AsyncConfig { }

@Service
public class NotificationService {

    private static final Logger log = LoggerFactory.getLogger(NotificationService.class);

    @Async                                          // fire and forget
    public void sendNewApplicationMail(Long applicationId) {
        log.info("Sending mail on thread {}", Thread.currentThread().getName());
        // ... load data, build and send the mail
    }

    @Async
    public CompletableFuture<Integer> countInactiveUsers() {     // caller can wait for the result
        int n = userRepository.countInactive();
        return CompletableFuture.completedFuture(n);
    }
}
  • A method may return void or Future/CompletableFuture<T> (wrap the value with completedFuture). Any other return type gives null to the caller.
  • With CompletableFuture the caller can combine results: CompletableFuture.allOf(a, b).join().
  • The call returns at once; the work runs on a pool thread (task-1 in the log).

How it works: the same proxy trap

@Async is another proxy feature (module 1): the proxy does not run your method but submits it as a task to an Executor and returns. Therefore:

  • Self-invocation does not work. this.sendMail() from the same class runs synchronously on the caller's thread. Call it from another bean.
  • The method must be public and not final/private.
  • The caller must be another bean holding the proxy.

Configuring the executor

Boot auto-configures an applicationTaskExecutor (a ThreadPoolTaskExecutor) that @Async uses. Tune it with properties:

spring:
  task:
    execution:
      thread-name-prefix: app-async-
      pool:
        core-size: 4
        max-size: 16
        queue-capacity: 200
        keep-alive: 60s
      shutdown:
        await-termination: true
        await-termination-period: 30s       # finish queued work on shutdown

How the pool behaves is a classic interview point: threads up to core-size are created first; further tasks go into the queue; only when the queue is full does the pool grow up to max-size; when both are full, the executor rejects the task (TaskRejectedException). A queue of "unbounded" capacity (the old default) means max-size is never used and memory can grow without limit.

For different kinds of work, define named executors, so slow email sending cannot starve report generation (the bulkhead idea):

@Configuration
@EnableAsync
public class AsyncConfig {

    @Bean("mailExecutor")
    public ThreadPoolTaskExecutor mailExecutor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(2);
        ex.setMaxPoolSize(5);
        ex.setQueueCapacity(100);
        ex.setThreadNamePrefix("mail-");
        ex.setTaskDecorator(new MdcTaskDecorator());          // copy request id (below)
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        ex.setWaitForTasksToCompleteOnShutdown(true);
        ex.setAwaitTerminationSeconds(30);
        return ex;                       // Spring initialises it as a bean
    }
}

@Async("mailExecutor")                    // choose the executor by bean name
public void sendNewApplicationMail(Long applicationId) { ... }

CallerRunsPolicy makes the caller run the task when the pool is full, which slows the producer down (back-pressure) instead of losing work or throwing.

Exception handling

  • For methods returning CompletableFuture, the exception is stored in the future: handle it with .exceptionally(...) or .handle(...), or you get it at get()/join().
  • For void methods the caller is already gone, so nobody can catch the exception. Spring passes it to an AsyncUncaughtExceptionHandler; the default only logs it.
@Configuration
@EnableAsync
public class AsyncErrorConfig implements AsyncConfigurer {

    private static final Logger log = LoggerFactory.getLogger(AsyncErrorConfig.class);

    @Override
    public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (ex, method, params) ->
                log.error("Async method {} failed with params {}", method.getName(),
                        java.util.Arrays.toString(params), ex);
    }
}

A failed email is lost unless you record it. For important work, catch inside the method, save a "FAILED" status, and let a scheduled job retry (scheduling), or use a message queue (messaging) which gives you retries and durability.

Transactions, security and MDC do not follow the thread

Transactions, the Spring Security context and the MDC are all stored in thread-locals (per-thread storage), so a new thread starts with none of them:

  • Transaction: the async method does not run in the caller's transaction. If the caller has not committed yet, the async method may not see the new row (it can fail with "not found"). Pass ids, not entities, and load again in the async method with its own @Transactional. Better, trigger it after commit:
public record ApplicationSubmitted(Long applicationId) { }

@Service
public class ApplicationService {
    private final ApplicationEventPublisher events;
    // ...
    @Transactional
    public ApplicationResponse apply(Long jobId, Long userId) {
        Application saved = applicationRepository.save(new Application(jobId, userId));
        events.publishEvent(new ApplicationSubmitted(saved.getId()));   // nothing sent yet
        return mapper.toResponse(saved);
    }
}

@Component
public class ApplicationMailListener {
    private final NotificationService notifications;
    // ...
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onSubmitted(ApplicationSubmitted event) {
        notifications.sendNewApplicationMail(event.applicationId());    // @Async method
    }
}

If the transaction rolls back, the event is dropped and no email is sent. That is exactly what you want, and it is the in-process cousin of the outbox pattern (delivery semantics).

  • Security context: SecurityContextHolder is empty in the async thread. Wrap the executor with DelegatingSecurityContextAsyncTaskExecutor, or pass the user id explicitly. Passing explicit values is simplest (module 4).
  • MDC: use a TaskDecorator to copy the map:
import java.util.Map;
import org.slf4j.MDC;
import org.springframework.core.task.TaskDecorator;

public class MdcTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable task) {
        Map<String, String> context = MDC.getCopyOfContextMap();   // captured on the caller
        return () -> {
            try {
                if (context != null) MDC.setContextMap(context);
                task.run();
            } finally {
                MDC.clear();
            }
        };
    }
}

Virtual threads in Spring Boot

A normal (platform) thread maps to an operating-system thread and costs about a megabyte of stack, so pools hold tens or hundreds of them. A virtual thread (Java 21+) is a cheap thread managed by the JVM: you can have hundreds of thousands, and a virtual thread that blocks (waiting for a database or HTTP response) frees the underlying carrier thread. Blocking code scales without becoming reactive. Details: Core Java · Module 6.

spring.threads.virtual.enabled=true

One property (Spring Boot 3.2+, Java 21+) makes Boot use virtual threads for: Tomcat/Jetty request handling (one virtual thread per request), the @Async executor, @Scheduled tasks, and several other places (Kafka and RabbitMQ listeners among them). In effect, core-size/max-size pool settings no longer limit these.

Platform thread poolVirtual threads
Best forCPU-heavy workBlocking I/O: database, HTTP, files
CountSmall, bounded poolOne per task, no pool needed
Limiting concurrencyPool size does itYou must limit yourself (a Semaphore, a connection pool)
Thread-localsReused threads need clean-upWork, but are not shared: each task has its own

Things to know about virtual threads

  • They do not make CPU-bound code faster, and they do not remove the bottleneck of your database: 10,000 concurrent requests still share a Hikari pool of 10 connections. The pool becomes the limit (and requests wait for a connection), so size it consciously.
  • Pinning: on Java 21 a virtual thread blocked inside a synchronized block holds its carrier thread. Java 24 and later fixed most of this. Prefer ReentrantLock in your own code, and keep your libraries current.
  • Do not pool virtual threads, and do not put unbounded ThreadLocal caches on them.

Common mistakes

  • Forgetting @EnableAsync, or calling the async method from the same class: it runs synchronously and nobody notices.
  • An unbounded queue or pool: memory grows or threads explode.
  • Passing a JPA entity into the async method; its session is closed (LazyInitializationException). Pass an id.
  • Sending the async message inside the transaction, then rolling back: the email says "application received" for an application that does not exist.
  • Blocking on future.get() immediately, which removes all the benefit.

Interview angle

"How does @Async work and when does it fail?" Proxy submits to an executor; fails on self-invocation, missing @EnableAsync, private methods. "Which thread runs it?" The applicationTaskExecutor or the named one. "Is the async method in the caller's transaction?" No. "How do you handle exceptions?" Future, or AsyncUncaughtExceptionHandler. "What do virtual threads change?" Cheap blocking, one property to enable; not for CPU-bound work.

File upload and download: MultipartFile, storage and safe file names

Receive files as MultipartFile, limit their size, check type and content yourself, never trust the original file name, store the file under a generated name (on disk or S3) with metadata in the database, and send it back with ResponseEntity<Resource> and a Content-Disposition header.

What and why

In Project 2 a candidate uploads a resume (PDF) when applying. Browsers send files using the multipart/form-data encoding: one HTTP request with several parts (text fields and files), each part with its own headers. Spring parses it for you and gives each file as a MultipartFile.

Limits first

spring:
  servlet:
    multipart:
      enabled: true
      max-file-size: 5MB          # one file (default is 1MB)
      max-request-size: 6MB       # whole request: all files + fields (default is 10MB)
      file-size-threshold: 1MB    # above this size Spring writes to a temp file instead of memory
app:
  upload-dir: ${UPLOAD_DIR:./uploads}

If a client sends more, Spring throws MaxUploadSizeExceededException before your controller runs. Map it to 413 Payload Too Large in your @RestControllerAdvice (module 2). Also set limits at the proxy (Nginx client_max_body_size) so huge bodies are rejected before they reach Java.

The controller

@RestController
@RequestMapping("/api/applications")
public class ResumeController {

    private final ResumeService resumeService;

    public ResumeController(ResumeService resumeService) { this.resumeService = resumeService; }

    @PostMapping(path = "/{applicationId}/resume", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
    public ResponseEntity<ResumeResponse> upload(@PathVariable Long applicationId,
                                                 @RequestParam("file") MultipartFile file,
                                                 @AuthenticationPrincipal UserPrincipal user) {
        ResumeResponse saved = resumeService.store(applicationId, user.getId(), file);
        return ResponseEntity.status(HttpStatus.CREATED).body(saved);
    }
}
$ curl -X POST http://localhost:8080/api/applications/12/resume \
       -H "Authorization: Bearer $TOKEN" \
       -F "file=@./asha-resume.pdf;type=application/pdf"
{"id":5,"originalName":"asha-resume.pdf","size":184320,"contentType":"application/pdf"}

Useful MultipartFile methods:

MethodReturnsTrust it?
getOriginalFilename()Name chosen by the clientNo (may contain ../)
getContentType()Type the client claimsNo (client controlled)
getSize()Size in bytesYes (counted by the server)
isEmpty()No file chosen or zero bytesYes
getInputStream()Stream of the contentYes, read from this
transferTo(Path)Moves the content to a destinationYes

Security: validate everything about the file

  • Size: check getSize() again in the service, with a business limit (a resume: 2 MB) even if the global limit is 5 MB.
  • Type by content, not by name: the extension and Content-Type are written by the client; an attacker uploads shell.jsp labelled image/png. Check the first bytes (a PDF starts with %PDF-) or use a detection library such as Apache Tika. Keep an allow-list (pdf, docx), never a block-list.
  • The file name: getOriginalFilename() can be ../../etc/cron.d/job or contain a null byte. This is a path traversal attack: writing outside your upload folder. Defence: do not use the client name for the path at all. Generate your own stored name, and keep the original only as a display name in the database (after cleaning it with StringUtils.cleanPath and taking only the last segment).
  • Where to store: never inside the web root or a folder served as static files, so an uploaded HTML or script file can never be fetched and run. Serve downloads only through your controller.
  • Authorisation: check that the logged-in user may upload to / download this application's resume. Using a guessable id (/files/5) without checking ownership is an IDOR bug (module 4).
  • Malware and image bombs: for public uploads, scan with an antivirus service and limit image dimensions.

Storing: generated name, safe path, metadata in the DB

@Service
public class ResumeService {

    private static final long MAX_SIZE = 2L * 1024 * 1024;           // 2 MB
    private static final byte[] PDF_MAGIC = "%PDF-".getBytes(StandardCharsets.US_ASCII);

    private final Path root;
    private final ResumeRepository resumeRepository;
    private final ApplicationRepository applicationRepository;

    public ResumeService(@Value("${app.upload-dir}") Path root,
                         ResumeRepository resumeRepository,
                         ApplicationRepository applicationRepository) throws IOException {
        this.root = root.toAbsolutePath().normalize();
        this.resumeRepository = resumeRepository;
        this.applicationRepository = applicationRepository;
        Files.createDirectories(this.root);
    }

    @Transactional
    public ResumeResponse store(Long applicationId, Long userId, MultipartFile file) {
        Application app = applicationRepository.findById(applicationId)
                .filter(a -> a.getApplicant().getId().equals(userId))     // ownership
                .orElseThrow(() -> new ResourceNotFoundException("Application " + applicationId));

        if (file.isEmpty() || file.getSize() > MAX_SIZE) {
            throw new BadRequestException("File must be between 1 byte and 2 MB");
        }
        try (InputStream in = file.getInputStream()) {
            byte[] head = in.readNBytes(PDF_MAGIC.length);
            if (!Arrays.equals(head, PDF_MAGIC)) {
                throw new BadRequestException("Only PDF files are accepted");
            }
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }

        String storedName = UUID.randomUUID() + ".pdf";                   // our name, our extension
        Path target = root.resolve(storedName).normalize();
        if (!target.startsWith(root)) {                                    // belt and braces
            throw new BadRequestException("Invalid path");
        }
        try (InputStream in = file.getInputStream()) {
            Files.copy(in, target, StandardCopyOption.REPLACE_EXISTING);
        } catch (IOException e) {
            throw new UncheckedIOException("Could not store file", e);
        }

        String display = StringUtils.getFilename(StringUtils.cleanPath(
                file.getOriginalFilename() == null ? "resume.pdf" : file.getOriginalFilename()));
        Resume resume = resumeRepository.save(
                new Resume(app, storedName, display, "application/pdf", file.getSize()));
        return new ResumeResponse(resume.getId(), display, resume.getSize(), "application/pdf");
    }
}

The table behind it keeps what the database should know: id, application_id, stored_name, original_name, content_type, size_bytes, uploaded_at. The file system holds only bytes; the database holds meaning and permissions. Add a Flyway migration for the table (module 3). If the database save fails after the file was written, delete the file in a catch block (or run a clean-up job for orphan files), because a file system is not part of the transaction.

Downloading

@GetMapping("/{applicationId}/resume")
public ResponseEntity<Resource> download(@PathVariable Long applicationId,
                                         @AuthenticationPrincipal UserPrincipal user) {
    DownloadableFile f = resumeService.load(applicationId, user);   // checks permission
    Resource resource = new FileSystemResource(f.path());

    ContentDisposition disposition = ContentDisposition.attachment()
            .filename(f.displayName(), StandardCharsets.UTF_8)      // safe encoding of the name
            .build();

    return ResponseEntity.ok()
            .contentType(MediaType.APPLICATION_PDF)
            .contentLength(f.size())
            .header(HttpHeaders.CONTENT_DISPOSITION, disposition.toString())
            .header("X-Content-Type-Options", "nosniff")
            .body(resource);
}
  • Content-Disposition: attachment makes the browser download the file; inline shows it in the browser (fine for PDFs and images that you trust).
  • Return Resource (a FileSystemResource, UrlResource or InputStreamResource). Spring streams it to the response in chunks; it does not load the whole file into memory.
  • Set contentType from your stored value, not from a guess, and add nosniff so a browser does not reinterpret it.
  • Return 404 when the row or the file is missing, and 403/404 when the user is not allowed.

Streaming large files

For big downloads (exports, videos) use StreamingResponseBody, which lets you write to the output stream from your own code on a separate thread, without buffering. For huge uploads, avoid byte[] getBytes(); use getInputStream() and copy in chunks. For data exports (CSV of 1 million rows), stream from a database cursor and write rows as you read them.

@GetMapping("/export/jobs.csv")
public ResponseEntity<StreamingResponseBody> export() {
    StreamingResponseBody body = out -> {
        var writer = new BufferedWriter(new OutputStreamWriter(out, StandardCharsets.UTF_8));
        writer.write("id,title,city\n");
        jobService.streamAll(job -> {                         // iterates, no full list in memory
            try { writer.write(job.id() + "," + job.title() + "," + job.city() + "\n"); }
            catch (IOException e) { throw new UncheckedIOException(e); }
        });
        writer.flush();
    };
    return ResponseEntity.ok()
            .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=\"jobs.csv\"")
            .contentType(MediaType.parseMediaType("text/csv"))
            .body(body);
}

Escape CSV fields properly in real code (commas and quotes inside titles) or use a CSV library, and beware of CSV injection (cells starting with =).

Disk vs object storage

Local diskObject storage (S3 and similar)
SetupNoneBucket, credentials, SDK
Several app instancesEach has its own disk: file not found on another instance (needs a shared volume)All instances see the same bucket
ContainersLost when the container is replaced unless a volume is mountedIndependent of the container
Durability, backupYour jobBuilt in (replication, versioning)
Large downloadsGo through your appCan use a time-limited pre-signed URL: the browser downloads directly from S3

Local disk is fine for development and a single server. In production on several instances or containers, use object storage (see DevOps · Module 5). Hide the choice behind an interface (FileStorage with save, load, delete) with a disk implementation and an S3 implementation, selected by a property; the controller and service never know. For large uploads to S3, many systems let the browser upload directly with a pre-signed URL, and the API only records the metadata.

Common mistakes

  • Saving with the client's file name ("uploads/" + file.getOriginalFilename()): path traversal and overwrites.
  • Trusting Content-Type or the extension.
  • Storing uploads inside src/main/resources/static or any served folder.
  • Reading the whole file into memory with getBytes().
  • No ownership check on download; sequential ids let users read each other's resumes.
  • Not handling MaxUploadSizeExceededException: the client gets a confusing 500 or 413 HTML page.

Exceptions and edge cases

  • MissingServletRequestPartException (400): the part name is not file, or the request is not multipart.
  • MultipartException / "Current request is not a multipart request": missing Content-Type: multipart/form-data, often caused by setting the header manually in a client (the boundary is then missing; let the HTTP client set it).
  • Temporary files: Spring writes large parts to a temp folder and deletes them after the request; on small disks watch the temp space.
  • Names with non-ASCII characters (हिंदी.pdf) need the RFC 5987 encoding that ContentDisposition.filename(name, UTF_8) produces.

Interview angle

"How do you handle file upload securely?" Size limits, content-based type check with an allow-list, generated storage names, path normalisation, storage outside the web root, authorisation, metadata in the DB. "What is path traversal?" ../ in a file name writes outside the folder. "How do you send a file?" ResponseEntity<Resource> with Content-Disposition. "Disk or S3?" S3 for multiple instances and containers.

Sending email with JavaMailSender, HTML, attachments and local testing

Add spring-boot-starter-mail, set the SMTP properties from environment variables, send plain mail with SimpleMailMessage and HTML or attachments with MimeMessageHelper, render bodies with Thymeleaf, send asynchronously after commit, and test locally with Mailpit.

What and why

Email is the oldest notification channel: welcome mails, password reset, "a candidate applied to your job". Mail travels with SMTP (Simple Mail Transfer Protocol). Your application is an SMTP client: it connects to a mail server (a provider such as SES, SendGrid, Brevo, or Gmail) with a host, port, username and password, and hands over the message. The server delivers it. Your code never talks to the recipient's server.

Setup

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-mail</artifactId>
</dependency>
spring:
  mail:
    host: ${MAIL_HOST:smtp.gmail.com}
    port: ${MAIL_PORT:587}
    username: ${MAIL_USERNAME}
    password: ${MAIL_PASSWORD}           # never commit this; use an environment variable
    properties:
      mail:
        smtp:
          auth: true
          starttls:
            enable: true                 # upgrade the connection to TLS on port 587
          connectiontimeout: 5000        # ms: do not wait for ever
          timeout: 5000
          writetimeout: 5000
app:
  mail:
    from: "Jobs Portal <no-reply@jobs.example.com>"

With these properties set, Boot creates a JavaMailSender bean. Provider notes: Gmail needs 2-step verification on the account and an app password (a 16-character password made for apps; your normal password does not work). It is fine for learning but limited (about 500 mails a day) and unsuitable for production. Real systems use a transactional email provider (SES, SendGrid, Mailgun, Brevo) with their SMTP credentials or HTTP API, and set up SPF/DKIM/DMARC DNS records for your sending domain, otherwise your mail lands in spam. Port 587 with STARTTLS is the usual choice; port 465 uses implicit TLS (spring.mail.properties.mail.smtp.ssl.enable=true).

Plain text mail

@Service
public class MailService {

    private final JavaMailSender mailSender;
    private final String from;

    public MailService(JavaMailSender mailSender, @Value("${app.mail.from}") String from) {
        this.mailSender = mailSender;
        this.from = from;
    }

    public void sendPlain(String to, String subject, String text) {
        SimpleMailMessage msg = new SimpleMailMessage();
        msg.setFrom(from);
        msg.setTo(to);
        msg.setSubject(subject);
        msg.setText(text);
        mailSender.send(msg);              // throws MailException (unchecked) on failure
    }
}

HTML mail and attachments

For HTML, an attachment, an inline image or a non-ASCII text, use a MimeMessage (MIME is the format of structured email) with the helper class:

public void sendNewApplication(String to, String subject, String html,
                               String attachmentName, Path attachment) {
    try {
        MimeMessage message = mailSender.createMimeMessage();
        MimeMessageHelper helper = new MimeMessageHelper(message, true, "UTF-8");   // true = multipart
        helper.setFrom(from);
        helper.setTo(to);
        helper.setSubject(subject);
        helper.setText(html, true);                                   // true = this is HTML
        helper.addAttachment(attachmentName, new FileSystemResource(attachment));
        mailSender.send(message);
    } catch (MessagingException e) {
        throw new MailPreparationException("Could not build mail", e);
    }
}

Pass true for multipart whenever you add attachments or inline images. Always send a plain-text alternative for important mail with helper.setText(plain, html). Attach only when needed: many providers cap messages at 10 to 25 MB, and sending a link is often better.

Templates with Thymeleaf (brief)

Do not build HTML with string concatenation. Use a template engine; Thymeleaf is the common choice with Spring (spring-boot-starter-thymeleaf). Put src/main/resources/templates/mail/new-application.html in place:

<!DOCTYPE html>
<html xmlns:th="http://www.thymeleaf.org">
  <body>
    <p>Hello <span th:text="${recruiterName}">Recruiter</span>,</p>
    <p><strong th:text="${candidateName}">Candidate</strong> applied for
       <em th:text="${jobTitle}">Job</em>.</p>
    <p><a th:href="${link}">Open the application</a></p>
  </body>
</html>
@Service
public class ApplicationMailService {

    private final TemplateEngine templateEngine;      // org.thymeleaf.TemplateEngine
    private final MailService mailService;
    // constructor omitted

    public void notifyRecruiter(RecruiterMailData d) {
        Context ctx = new Context();                  // org.thymeleaf.context.Context
        ctx.setVariable("recruiterName", d.recruiterName());
        ctx.setVariable("candidateName", d.candidateName());
        ctx.setVariable("jobTitle", d.jobTitle());
        ctx.setVariable("link", d.link());
        String html = templateEngine.process("mail/new-application", ctx);   // th:text escapes HTML
        mailService.sendHtml(d.recruiterEmail(), "New application: " + d.jobTitle(), html);
    }
}

th:text escapes HTML, which protects you from a candidate whose name contains a script tag. Never use th:utext with user input.

Send asynchronously and after commit

SMTP is slow and flaky. If send() runs inside the request, a slow mail server makes the API slow, and a mail failure can roll back (or fail) the business operation. The standard design for Project 2 combines three pieces from earlier in this module:

  1. The service saves the application and publishes an ApplicationSubmitted event.
  2. A @TransactionalEventListener(phase = AFTER_COMMIT) receives it only if the transaction committed.
  3. It calls an @Async("mailExecutor") method that loads the data, renders the template and sends, with a try/catch that logs failures and records them (Async).
@Async("mailExecutor")
public void sendNewApplicationMail(Long applicationId) {
    try {
        RecruiterMailData data = loader.load(applicationId);        // own @Transactional(readOnly)
        applicationMailService.notifyRecruiter(data);
        log.info("Recruiter mail sent for application {}", applicationId);
    } catch (MailException | RuntimeException ex) {
        log.error("Recruiter mail failed for application {}", applicationId, ex);
        // optionally: save a FAILED row so a scheduled job can retry
    }
}

This is "good enough" for a small system. Its weakness: if the app crashes between commit and sending, the mail is lost. A table of pending mails (an outbox) plus a scheduler, or a message queue, solves it; see the outbox idea.

Testing email locally

Never test with real recipients. Run a fake SMTP server that catches all mail and shows it in a web page. Mailpit (successor of MailHog) is a small Docker image:

services:
  mailpit:
    image: axllent/mailpit
    ports:
      - "1025:1025"      # SMTP: the application sends here
      - "8025:8025"      # web UI: open http://localhost:8025 to read the mails
spring:
  mail:
    host: localhost
    port: 1025
    properties:
      mail.smtp.auth: false
      mail.smtp.starttls.enable: false

MailHog (mailhog/mailhog) works the same way with the same ports. In automated tests, either use Testcontainers with Mailpit and call its HTTP API, or mock JavaMailSender and capture the MimeMessage (module 5); GreenMail is a popular in-process test SMTP server.

Common mistakes

  • Committing the SMTP password to Git. Use environment variables or a secret manager.
  • Sending email inside the database transaction: a mail goes out for data that is later rolled back.
  • No timeouts: a stuck SMTP server hangs the thread for minutes.
  • Sending to a user-supplied address without limit: your "forgot password" form becomes a spam cannon (rate-limit it, next topics).
  • Putting user-controlled text in the subject or headers without removing line breaks (header injection). MimeMessageHelper checks this for you; do not build headers by hand.

Exceptions

  • MailAuthenticationException: wrong username/password (Gmail without an app password).
  • MailSendException: delivery to some recipients failed; it contains the failed messages.
  • MailParseException / MailPreparationException: bad address or content.
  • All extend the unchecked MailException, so no throws clause; MessagingException (checked) comes from the Jakarta Mail API when you build a MimeMessage.
  • The health indicator mail (Actuator) connects to the SMTP server; it can mark the app DOWN when the mail server is unreachable. Disable it with management.health.mail.enabled=false if mail is not critical.

Interview angle

"How do you send email in Spring Boot?" Starter, SMTP properties, JavaMailSender, SimpleMailMessage vs MimeMessageHelper. "Why asynchronous?" Slow, unreliable external call; do not block the request or the transaction. "How do you make sure it is sent only if the data was saved?" After-commit listener or outbox. "How do you test it?" Mailpit/MailHog or GreenMail.

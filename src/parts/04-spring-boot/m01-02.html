@Configuration and @Bean: defining beans in Java code

A @Configuration class holds @Bean methods; each method's return value becomes a bean, which is how you register third-party classes and objects that need custom set-up.

Stereotypes only work on classes you own. You cannot put @Component on ObjectMapper, RestClient or BCryptPasswordEncoder, because you do not edit their source. For those, and for any object that needs set-up code, you write a method that builds the object and tell Spring to treat the result as a bean.

import java.time.Clock;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

@Configuration
public class AppConfig {

    @Bean
    public Clock clock() {                         // bean name: "clock"
        return Clock.systemUTC();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {     // bean name: "passwordEncoder"
        return new BCryptPasswordEncoder(12);
    }
}

Now any class can ask for a Clock or a PasswordEncoder in its constructor. Putting a Clock in the container is also a good testing habit: tests inject a fixed clock instead of calling LocalDateTime.now() directly.

Beans that depend on other beans

A @Bean method can take parameters; Spring resolves them as beans, exactly like a constructor.

@Configuration
public class PaymentConfig {

    @Bean
    public PaymentClient paymentClient(RestClient.Builder builder,
                                       PaymentProperties props) {
        RestClient client = builder.baseUrl(props.baseUrl()).build();
        return new PaymentClient(client, props.apiKey());
    }
}

Here RestClient.Builder is provided by Boot's auto-configuration and PaymentProperties by your own configuration properties.

Bean names and customising

  • The name is the method name. Change it with @Bean("fastEncoder") or @Bean(name = {"a", "b"}) for aliases.
  • Several methods can return the same type with different names; choose between them with @Qualifier or @Primary.
  • Other attributes: initMethod and destroyMethod (lifecycle callbacks on a third-party class), and @Scope, @Lazy, @Profile, @ConditionalOnProperty next to @Bean.
@Configuration
public class HttpConfig {

    @Bean
    @Primary                        // chosen when nobody says which
    public RestClient paymentRestClient() {
        return RestClient.create("https://pay.example.com");
    }

    @Bean
    public RestClient shippingRestClient() {
        return RestClient.create("https://ship.example.com");
    }
}

@Service
class ShippingService {
    ShippingService(@Qualifier("shippingRestClient") RestClient client) { /* ... */ }
}

@Configuration, proxyBeanMethods and "full" vs "lite" mode

A @Configuration class is itself a bean, and by default Spring wraps it in a CGLIB subclass (proxyBeanMethods = true). The proxy makes one promise: if one @Bean method calls another, the call goes through the container, so you still get the singleton and not a new object.

@Configuration
public class ServiceConfig {

    @Bean
    public AuditLog auditLog() {
        return new AuditLog();
    }

    @Bean
    public OrderService orderService() {
        return new OrderService(auditLog());   // same AuditLog singleton
    }
}

With @Configuration(proxyBeanMethods = false) (called lite mode) the proxy is skipped: startup is slightly faster, but auditLog() inside orderService() is a plain method call and creates a second object. Boot's own auto-configuration classes use proxyBeanMethods = false and take dependencies as method parameters instead. Your rule: keep the default, or use false and always pass dependencies as parameters.

@Component with @Bean ("lite" beans)

@Bean methods also work inside any @Component class. They follow the lite rules: inter-method calls are plain Java calls. Use @Configuration for classes whose job is to define beans.

When to use which

SituationUse
Your own classA stereotype annotation (@Service, @Component)
A class from a library@Bean method
An object needing builder code, parameters or a condition@Bean method
Several differently configured instances of one classSeveral @Bean methods with distinct names
Swap a Boot default (your own ObjectMapper, security chain)@Bean; Boot's version backs off (auto-configuration)

Rules

  • @Bean methods must not be private or final inside a @Configuration class that is proxied (CGLIB must override them).
  • The @Configuration class itself must not be final when proxyBeanMethods is true.
  • Return the interface or the most useful type; the declared return type is what Spring uses for type matching before the bean is created.

Conventions

  • Split configuration by concern: SecurityConfig, JacksonConfig, HttpClientConfig. Do not make one giant AppConfig.
  • Prefer parameters over calling other @Bean methods.
  • Name beans for what they are, not how they are built (paymentRestClient, not bean1).

Mistake: creating a bean with new in business code

Writing PasswordEncoder encoder = new BCryptPasswordEncoder() inside every service gives each one its own object and hard-wires the choice. Define it once as a @Bean and inject it.

Interview: "@Component vs @Bean? What does proxyBeanMethods do?"

  • @Component is class-level and found by scanning; @Bean is method-level and used inside configuration classes, so you control construction and can register third-party classes.
  • With proxyBeanMethods = true (default) calls between @Bean methods return the same singleton; with false they are plain calls, which is faster to start.

Injection types: constructor, setter, field, and choosing between beans

Prefer constructor injection: it makes dependencies required, lets fields be final and lets you test with plain new; use @Qualifier and @Primary when several beans match.

Spring can hand a bean its dependencies in three ways. They differ in what they guarantee, not in what they can reach.

Constructor injection (preferred)

@Service
public class OrderService {

    private final OrderRepository repository;
    private final NotificationSender sender;

    // Only one constructor: @Autowired is not needed (Spring 4.3+)
    public OrderService(OrderRepository repository, NotificationSender sender) {
        this.repository = repository;
        this.sender = sender;
    }
}

If a class has one constructor, Spring uses it automatically. With several constructors, mark the one to use with @Autowired. With Lombok you can drop the boilerplate:

@Service
@RequiredArgsConstructor      // generates a constructor for all final fields
public class OrderService {
    private final OrderRepository repository;
    private final NotificationSender sender;
}

Records and Java 21 make this even lighter for small cases, but Lombok's @RequiredArgsConstructor is what you will see in most projects.

Setter injection

@Service
public class ReportService {
    private AuditLog auditLog;   // optional: the app works without it

    @Autowired(required = false)
    public void setAuditLog(AuditLog auditLog) {
        this.auditLog = auditLog;
    }
}

Use it for dependencies that are truly optional or that must be changeable after creation. The object can exist without them, which is both the benefit and the risk.

Field injection (avoid)

@Service
public class OrderService {
    @Autowired
    private OrderRepository repository;     // set by reflection
    @Autowired
    private NotificationSender sender;
}

Several beans of the same type

Suppose two classes implement NotificationSender. A constructor parameter of that type matches both, and Spring cannot choose. Three tools solve it.

@Component
@Primary
public class EmailSender implements NotificationSender { /* ... */ }

@Component
public class SmsSender implements NotificationSender { /* ... */ }
@Service
public class OtpService {
    private final NotificationSender sender;

    public OtpService(@Qualifier("smsSender") NotificationSender sender) {
        this.sender = sender;      // bean name: class SmsSender -> "smsSender"
    }
}

A third way: name the parameter like the bean (NotificationSender smsSender); Spring falls back to the parameter name when several beans match. It works but breaks silently when someone renames the parameter, so prefer @Qualifier. An explicit @Qualifier always wins over @Primary.

Injecting all implementations: the strategy pattern

Ask for a List or a Map and Spring injects every bean of the type. This gives you the strategy pattern with no if chains.

public interface PaymentService {
    void pay(long amountInPaise);
}

@Service("upi")  public class UpiPayment  implements PaymentService { /* ... */ }
@Service("card") public class CardPayment implements PaymentService { /* ... */ }

@Service
public class PaymentRouter {
    private final Map<String, PaymentService> byName;   // key = bean name
    private final List<PaymentService> all;

    public PaymentRouter(Map<String, PaymentService> byName,
                         List<PaymentService> all) {
        this.byName = byName;
        this.all = all;
    }

    public void pay(String method, long amountInPaise) {
        PaymentService service = byName.get(method);    // "upi" or "card"
        if (service == null) {
            throw new IllegalArgumentException("Unknown method: " + method);
        }
        service.pay(amountInPaise);
    }
}

Adding a new payment method means adding one new class; PaymentRouter does not change (open/closed principle). The order inside the List follows @Order or the Ordered interface when present.

Optional dependencies

@Service
public class FeatureService {
    private final Optional<MetricsClient> metrics;
    private final ObjectProvider<AuditLog> audit;

    public FeatureService(Optional<MetricsClient> metrics,
                          ObjectProvider<AuditLog> audit,
                          @Autowired(required = false) Cache cache) {
        this.metrics = metrics;
        this.audit = audit;
    }

    public void run() {
        metrics.ifPresent(m -> m.count("feature.run"));
        audit.ifAvailable(a -> a.record("run"));
    }
}

ObjectProvider<T> is the most flexible: getIfAvailable(), ifAvailable(...), getObject(), stream(), and it also resolves late, which is how you get a new prototype bean each time (see scopes).

@Resource and @Inject

@Autowired is Spring's own annotation (match by type, then name). @Inject (jakarta.inject) behaves almost the same. @Resource matches by name first. In new code use constructor injection and skip all three.

Rules

  • A single constructor is autowired without any annotation; with two or more, annotate exactly one with @Autowired.
  • A required dependency with no matching bean stops startup (NoSuchBeanDefinitionException).
  • Two matching beans with no @Primary or @Qualifier stop startup (NoUniqueBeanDefinitionException).
  • @Autowired works only on beans managed by Spring, never on objects you create with new.

Conventions

  • Constructor injection, private final fields, interface types.
  • Use @Primary for "the usual one" and @Qualifier for the exceptions.
  • If a constructor has more than about five parameters, split the class.

Edge cases

  • A Map<String, T> uses bean names as keys, so keep names meaningful ("upi", not "upiPaymentServiceImpl") when the key matters.
  • An injected List is empty (not an error) when no bean of the type exists, unlike a single required bean.
  • Constructor injection with @Lazy on a parameter injects a lazy proxy; useful to break a cycle, not as a habit.

Mistake: field injection and then new

A class with @Autowired private Repo repo; cannot be unit-tested with new OrderService(): repo stays null and you get a NullPointerException. Constructor injection makes that mistake impossible.

Wrong: field injection

@Service
class OrderService {
    @Autowired OrderRepository repo;
}
// new OrderService().place()  -> NullPointerException

Right: constructor injection

@Service
class OrderService {
    private final OrderRepository repo;
    OrderService(OrderRepository repo) { this.repo = repo; }
}
// new OrderService(fakeRepo) works in a plain unit test

Interview: "Constructor vs field injection? How do you pick between two beans?"

  • Constructor injection: immutability, required dependencies, easy testing, no reflection, visible class size. Field injection hides all of that.
  • Setter injection for optional dependencies only.
  • Two candidates: @Primary on one, or @Qualifier("name") at the injection point, or inject a Map/List of all.
  • Single constructor needs no @Autowired since Spring 4.3.

Common bean errors and how to read the startup failure report

Most Spring startup failures are a missing bean, two matching beans or a circular dependency; the failure report at the end of the log names the class, the parameter and usually the fix.

When the container cannot build the object graph, the application refuses to start. Do not scroll through the 200-line stack trace. Look for the box that Boot prints at the bottom.

***************************
APPLICATION FAILED TO START
***************************

Description:

Parameter 0 of constructor in com.example.shop.order.OrderService
required a bean of type 'com.example.shop.order.OrderRepository'
that could not be found.

Action:

Consider defining a bean of type 'com.example.shop.order.OrderRepository'
in your configuration.

The Description says what went wrong and where; the Action suggests a fix. Read those two first. If you see only a long stack trace, scroll to the last Caused by:: the deepest cause is the real problem; the BeanCreationException lines above are wrappers.

1. NoSuchBeanDefinitionException (the bean is missing)

Cause: nothing in the container matches the required type or name.

CheckFix
Class has no stereotype annotationAdd @Service, @Component or a @Bean method
Class is outside the scanned packagesMove it under the main class's package (scanning)
You asked for the implementation, but the bean is a proxy of the interfaceInject the interface type
The bean is excluded by @Profile or a conditionActivate the profile or fix the condition
A starter is missing (no DataSource bean)Add the dependency; check with the conditions report
Test with a slice (@WebMvcTest)Mock the missing collaborator or @Import it

2. NoUniqueBeanDefinitionException (too many beans)

Parameter 0 of constructor in com.example.shop.OtpService required a
single bean, but 2 were found:
    - emailSender: defined in file [.../EmailSender.class]
    - smsSender: defined in file [.../SmsSender.class]

Action: Consider marking one of the beans as @Primary, updating the
consumer to accept multiple beans, or using @Qualifier to identify the
bean that should be consumed

Fix by one of: @Primary on the usual bean; @Qualifier("smsSender") at the injection point; accept List/Map of all; or a bean-name-matching parameter name. Another cause is two @Bean methods that both return the same type.

3. UnsatisfiedDependencyException

This is a wrapper. Spring says "I could not satisfy a dependency of bean X" and the reason is in the nested exception: usually one of the two above, or an exception thrown by another bean's constructor. Always read the last Caused by.

4. Circular dependencies

A needs B and B needs A. With constructors neither can be created first.

@Service
class OrderService {
    OrderService(CustomerService customers) { }
}

@Service
class CustomerService {
    CustomerService(OrderService orders) { }
}
The dependencies of some of the beans in the application context
form a cycle:

┌─────┐
|  orderService defined in file [.../OrderService.class]
↑     ↓
|  customerService defined in file [.../CustomerService.class]
└─────┘

Action: Despite circular references being allowed by default in Spring
Framework, they are prohibited by Spring Boot by default...

Since Spring Boot 2.6 cycles are prohibited by default (spring.main.allow-circular-references is false). Treat a cycle as a design smell and fix the design, in this order of preference:

  1. Extract the shared logic into a third class that both use. Often A and B both really need "customer lookup", which belongs in its own service.
  2. Move one direction to events: A publishes an event, B listens (events).
  3. Pass data, not services: give the method the values it needs instead of the whole bean.
  4. Last resort: @Lazy on one constructor parameter, which injects a lazy proxy that resolves on first call. It hides the problem; document why.

Setting spring.main.allow-circular-references=true brings the old behaviour back for setter and field injection. Do not do that; it only postpones the design fix.

A debugging routine

  1. Read the "Description" and "Action" of the failure report.
  2. Find the last Caused by: in the stack trace if no report was printed.
  3. Check the three basics: annotation present, package scanned, profile active.
  4. Run with --debug to print the conditions report, and list beans with ctx.getBeanDefinitionNames() if needed.
  5. Fix the root cause, never by switching injection style or allowing cycles.

Rule: fail fast is good

These errors appear at startup, because singletons are created eagerly. That is the container protecting you; never hide them with lazy tricks unless you understand why.

Edge cases

  • Field-injected cycles used to "work" before Boot 2.6 because Spring injected a half-built object. Upgrading old projects shows these cycles suddenly.
  • A @Lazy constructor parameter breaks a startup cycle but not a cycle in real method calls: infinite recursion causes a StackOverflowError at runtime.
  • An exception inside a @PostConstruct method also aborts startup, reported as BeanCreationException: Invocation of init method failed.

Mistake: fixing a cycle with allow-circular-references

It silences the error and leaves two classes that know too much about each other. Extract a third class or use an event instead.

Interview: "What is a circular dependency and how do you fix it?"

  • A needs B and B needs A; constructor injection cannot create either first. Since Boot 2.6 it fails at startup by default.
  • Fix by redesign: extract a third class, use events, pass data instead of beans. @Lazy on one parameter or setter injection are last resorts.
  • Also be able to name NoSuchBeanDefinitionException (missing bean) and NoUniqueBeanDefinitionException (several candidates) with causes and fixes.

Bean scopes: singleton, prototype and web scopes

The scope decides how many instances of a bean exist and how long they live; the default singleton scope gives one shared instance per container, so singleton beans must be stateless or thread-safe.

A scope answers: "when someone asks the container for this bean, does it give the same object or a new one?"

ScopeInstancesLives forUse for
singleton (default)One per containerWhole applicationServices, repositories, controllers, clients
prototypeA new one for every injection or getBeanUntil garbage collected; Spring does not destroy itStateful helper objects
requestOne per HTTP requestThe requestPer-request data (a request id, tenant)
sessionOne per HTTP sessionThe user sessionShopping cart in a server-side session
applicationOne per ServletContextWhole web applicationRare; usually a singleton does the same

The web scopes (request, session, application) exist only in a web application. There is also websocket, which is rare.

Singleton: shared, so keep it stateless

"Singleton" here means one instance per container, not the classic Gang-of-Four pattern with a private constructor. Because every request thread uses the same instance at the same time, a singleton bean must hold no per-request mutable state.

Wrong: per-user state in a singleton

@Service
public class CartService {
    private List<Item> items = new ArrayList<>();   // shared by ALL users!

    public void add(Item item) { items.add(item); }
}

Right: state passed in or stored per user

@Service
public class CartService {
    private final CartRepository carts;           // stateless; state lives in the DB
    public CartService(CartRepository carts) { this.carts = carts; }

    public void add(long userId, Item item) { carts.addItem(userId, item); }
}

Fields that are final collaborators are fine. Mutable counters, caches and lists are not, unless you use thread-safe types (AtomicLong, ConcurrentHashMap); see Core Java · Module 6.

Prototype

@Component
@Scope("prototype")          // or ConfigurableBeanFactory.SCOPE_PROTOTYPE
public class ReportBuilder {
    private final List<String> lines = new ArrayList<>();
    public void add(String line) { lines.add(line); }
}

Spring creates and injects a prototype, then forgets it: destroy callbacks like @PreDestroy are not called. Releasing resources is your job.

The classic trap: a prototype inside a singleton

A singleton is built once, so its dependencies are injected once. If one of them is a prototype, the singleton keeps that single instance forever, and the "new instance every time" behaviour is lost.

@Service
public class ReportService {
    private final ReportBuilder builder;          // injected ONCE

    public ReportService(ReportBuilder builder) { this.builder = builder; }

    public String build() { return builder.toString(); }   // shared, grows forever
}

Ask the container for a fresh one each time, with ObjectProvider:

@Service
public class ReportService {
    private final ObjectProvider<ReportBuilder> builders;

    public ReportService(ObjectProvider<ReportBuilder> builders) {
        this.builders = builders;
    }

    public String build() {
        ReportBuilder builder = builders.getObject();    // a NEW instance
        builder.add("Total: 1500");
        return builder.toString();
    }
}

Alternatives: @Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS) (a proxy that gets a new target per call), or a @Lookup method. ObjectProvider is the clearest. Often the best answer is simpler still: create the helper with new inside the method, since it is not really a bean.

Web scopes

@Component
@RequestScope                       // = @Scope(value = "request", proxyMode = TARGET_CLASS)
public class RequestContext {
    private String requestId;
    // getters and setters
}

@Service
public class AuditService {
    private final RequestContext context;     // a proxy, safe to inject here
    public AuditService(RequestContext context) { this.context = context; }

    public void log(String action) {
        System.out.println(context.getRequestId() + " " + action);
    }
}

The singleton AuditService is created at startup, when there is no request. So Spring injects a scoped proxy instead of the real bean. On each call the proxy finds the real RequestContext of the current request and forwards the call. @RequestScope and @SessionScope set up that proxy for you; with plain @Scope("request") you must add proxyMode yourself. Using the bean outside a request (a scheduled job, a new thread) throws IllegalStateException: No thread-bound request found.

Server-side sessions fit badly with REST APIs, which should be stateless (Module 2). So in API projects request scope is the only web scope you may use, and rarely.

Rules

  • Default is singleton; keep singleton beans free of mutable per-request state.
  • Spring calls @PreDestroy for singletons (and other long-lived scopes), not for prototypes.
  • A longer-lived bean (singleton) that needs a shorter-lived one (prototype, request) must get it through a provider or a scoped proxy.

Conventions

  • Over 95 percent of beans are singletons; do not add @Scope without a clear reason.
  • Put request data (the user, a tenant, a trace id) in method parameters, a ThreadLocal-backed context, or the security context, not in a mutable singleton field.

Edge cases

  • Singleton beans are shared across threads, but created eagerly in one thread at startup; that does not make their later use thread-safe.
  • A prototype injected into a prototype is a new instance each time; the trap exists only when a longer-lived bean holds it.
  • Two @Bean methods returning the same class give two different singletons, because the scope is per bean definition, not per class.

Interview: "What are bean scopes? Is a singleton bean thread-safe?"

  • Singleton (default), prototype, request, session, application (and websocket). Singleton is one per container, not per JVM and not the GoF pattern.
  • A singleton is not automatically thread-safe: keep it stateless or use thread-safe state.
  • Prototype into singleton: injected once; fix with ObjectProvider, a scoped proxy, or @Lookup. Prototype beans are not destroyed by Spring.

The bean lifecycle: from construction to destruction

The container creates a bean, injects its dependencies, calls the Aware and post-processor callbacks, runs your init methods, keeps it in use, and calls destroy methods at shutdown; AOP proxies are created right after initialization.

Knowing the order helps you decide where code belongs: dependencies are not available in the constructor of a field-injected bean, a proxy appears only after init, and cleanup runs at shutdown. This is a favourite interview topic.

The steps, in order

  1. Instantiate — the constructor runs. With constructor injection all dependencies are already passed in.
  2. Populate properties — setter and field injection happen now (and @Value fields are set).
  3. Aware callbacks — if the bean implements BeanNameAware, BeanFactoryAware or ApplicationContextAware, Spring passes in the name, factory or context.
  4. BeanPostProcessor, before init — every registered postProcessBeforeInitialization runs. This is where the handling of @PostConstruct itself happens.
  5. @PostConstruct — your method runs; everything is injected.
  6. InitializingBean.afterPropertiesSet() — the interface-based alternative.
  7. Custom init method — @Bean(initMethod = "start").
  8. BeanPostProcessor, after init — postProcessAfterInitialization may return a replacement. This is where Spring wraps the bean in an AOP proxy for @Transactional, @Cacheable and @Async. What other beans receive may be the proxy, not your object.
  9. In use — the bean serves calls until the context closes.
  10. @PreDestroy, then DisposableBean.destroy(), then a custom destroyMethod — cleanup at shutdown. Singletons only.

Watching the order yourself

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.beans.factory.BeanNameAware;
import org.springframework.beans.factory.InitializingBean;
import org.springframework.stereotype.Component;

@Component
public class LifecycleDemo implements BeanNameAware, InitializingBean {

    public LifecycleDemo() {
        System.out.println("1 constructor");
    }

    @Override
    public void setBeanName(String name) {
        System.out.println("3 BeanNameAware: " + name);
    }

    @PostConstruct
    public void init() {
        System.out.println("5 @PostConstruct");
    }

    @Override
    public void afterPropertiesSet() {
        System.out.println("6 afterPropertiesSet");
    }

    @PreDestroy
    public void cleanup() {
        System.out.println("10 @PreDestroy");
    }
}

3 BeanNameAware: lifecycleDemo
5 @PostConstruct
6 afterPropertiesSet
... application runs ...
10 @PreDestroy

The package is jakarta.annotation in Boot 3 and 4 (it was javax.annotation in Boot 2). The annotations come from the Jakarta Annotations API, which Boot's starters already include.

@PostConstruct: what to use it for

  • Validating configuration: fail startup if a required value is blank.
  • Warming up: loading a small lookup table or opening a connection once.
  • Setting derived fields that need injected dependencies.

Keep it short and fast. Do not call slow remote services there; a slow @PostConstruct delays application startup, and a failure aborts it. For work that should run once the app is up, use a runner.

CommandLineRunner and ApplicationRunner

These run after the context is fully built, just before SpringApplication.run returns. They are good for seeding data or one-off start-up tasks.

@Component
@Order(1)
public class SeedData implements CommandLineRunner {

    private final ProductRepository products;
    public SeedData(ProductRepository products) { this.products = products; }

    @Override
    public void run(String... args) {          // raw command-line arguments
        if (products.count() == 0) {
            products.save(new Product("MSE-1001", "Wireless Mouse"));
        }
    }
}

@Component
class Warmup implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {        // parsed: --mode=fast
        System.out.println("fast? " + args.containsOption("mode"));
    }
}

ApplicationRunner gives parsed options (--name=value) and non-option arguments; CommandLineRunner gives the raw string array. Order several runners with @Order. An exception in a runner fails startup.

@Lazy and @DependsOn

  • @Lazy on a bean (or class) delays creation until the first request for it. It speeds startup but moves errors to runtime. You can enable it for all beans with spring.main.lazy-initialization=true, a trade-off to use knowingly.
  • @DependsOn("databaseMigrator") forces that bean to be created first even if there is no injection link between them (for example a bean that must exist before this one, as a side effect). Use it sparingly; normally injection already orders things.

Defining callbacks for third-party beans

@Bean(initMethod = "connect", destroyMethod = "disconnect")
public LegacyQueueClient queueClient() {
    return new LegacyQueueClient("amqp://localhost");
}

For @Bean methods Spring also guesses a destroy method named close or shutdown if the class has one (this is called inference). Set destroyMethod = "" to turn that off.

Why the order matters in practice

  • Do not use an injected field in a constructor of a field-injected bean: it is still null. This is another reason to prefer constructor injection.
  • Calling a @Transactional method of the same bean from @PostConstruct does not start a transaction, because the proxy is created in step 8, after the method runs.
  • Cleaning up resources (thread pools, files) belongs in @PreDestroy or a close() method; Spring Boot's graceful shutdown calls it when the JVM gets a stop signal.

Rules

  • @PostConstruct and @PreDestroy methods take no arguments and should return void.
  • Destroy callbacks run for singletons at context close, not for prototypes, and not if the JVM is killed with kill -9.
  • Prefer the annotations over the interfaces InitializingBean and DisposableBean, which tie your class to Spring.

Conventions

  • Constructor: assign fields only. @PostConstruct: light set-up. Runner: start-up tasks that need the running app.
  • Keep seed data and migrations out of production profiles (use profiles).

Edge cases

  • Both @PostConstruct and afterPropertiesSet exist: the annotation runs first. If the same method name is also declared as an init method, Spring runs it once.
  • If the constructor throws, you see BeanInstantiationException; if @PostConstruct throws, BeanCreationException: Invocation of init method failed.
  • A BeanPostProcessor is itself a bean; make its @Bean method static so it is created early and does not force its configuration class to load too soon.

Interview: "Explain the bean lifecycle"

  • Instantiate → populate dependencies → Aware callbacks → post-processor before → @PostConstruct → afterPropertiesSet → init-method → post-processor after (proxies) → ready → @PreDestroy → destroy → destroy-method.
  • Name one use for each hook: @PostConstruct to validate config; BeanPostProcessor to wrap beans (AOP); @PreDestroy to release resources.
  • Say prototype beans are not destroyed by Spring, and runners run after the context is ready.

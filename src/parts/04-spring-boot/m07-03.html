Messaging concepts: queues, topics and the Kafka model

A message broker lets services communicate asynchronously: producers send messages, the broker stores them, and consumers process them later; a queue gives each message to one worker, a topic gives it to every subscriber, and Kafka stores topics as partitioned, replicated logs that consumer groups read at their own pace.

Why messaging

Take "a candidate applies for a job". After saving the application you want to email the recruiter, update search, add to analytics and notify the candidate. If the application service calls all four synchronously, the user waits for the slowest, and any failure breaks the request. With a message broker in the middle, the service publishes one message, "ApplicationSubmitted", and returns. Other services consume it in their own time.

  • Decoupling: the producer does not know who consumes, or how many.
  • Buffering: a spike (10,000 applications in a minute) is stored in the broker and processed at the consumers' speed.
  • Resilience: if the notification service is down for an hour, messages wait and are processed on recovery.
  • Scalability: add consumer instances to share the work.

The costs: more infrastructure, eventual consistency, harder debugging, and the need to deal with duplicates and ordering (delivery semantics).

Queue vs topic

Queue (point-to-point)
Each message is delivered to one consumer among those listening. Several consumers on one queue are competing consumers: they share the load. Example: a queue of "send this email" tasks.
Topic (publish/subscribe)
Each message is delivered to every subscriber group. Example: "ApplicationSubmitted" is read independently by notifications, analytics and search.

RabbitMQ models both through exchanges and queues; Kafka models everything as topics, and gets queue behaviour with consumer groups.

Kafka: the model

Apache Kafka is a distributed, durable commit log. Unlike a classic queue, a consumed message is not deleted: Kafka keeps messages for a retention period (days or weeks, or by size), and consumers remember how far they have read. That makes replay possible and lets many independent consumers read the same data.

Broker
A Kafka server. A cluster has several brokers.
Topic
A named stream of records, such as application-events.
Partition
A topic is split into partitions; each partition is an ordered, append-only log. Partitions let a topic scale over many brokers and many consumers.
Offset
The position number of a record inside a partition (0, 1, 2...). A consumer commits the offset it has processed.
Key
An optional value on each record. Records with the same key always go to the same partition (hash of the key), which gives ordering per key.
Producer / Consumer
Clients that write to and read from topics.
Consumer group
Consumers with the same group.id share a topic: each partition is read by exactly one consumer in the group. Different groups each get all records.
Replication
Each partition has copies on several brokers (replication factor, commonly 3): one leader serves reads and writes, followers replicate. If the leader dies, a follower takes over.
  • Ordering is guaranteed only inside a partition. Use the entity id as key (job id, order id) so all events of one entity stay in order.
  • Parallelism of a group is limited by the number of partitions: 3 partitions can keep at most 3 consumers busy; a fourth consumer sits idle. Choose the partition count with future growth in mind (it can be increased later but then key-to-partition mapping changes).
  • When consumers join or leave a group, Kafka rebalances: partitions are reassigned, with a short pause.
  • Modern Kafka runs without ZooKeeper, in KRaft mode: brokers (some acting as controllers) manage the metadata themselves. Single-node KRaft is easy for development (see Compose).

When to use messaging, and when not

  • Good: notifications, workflows across services, replicating data to other services or search indexes, activity/analytics streams, smoothing spikes, background jobs that must survive restarts.
  • Not good: a user waiting for a result right now (use a synchronous call); tiny apps where @Async plus an after-commit event (module 6) is enough.

Event types you will hear: event notification (a small message "job 7 was updated", consumers call back for details), event-carried state transfer (the message contains the data, so consumers keep their own copy), and commands ("send this email", directed at one service). Name events in the past tense (ApplicationSubmitted); commands in the imperative (SendEmail).

Broker theory (log-structured storage, consensus) appears in System Design · Module 5.

Interview angle

"Why a message broker?" Decoupling, buffering, resilience. "Queue vs topic?" One consumer vs every subscriber. "Explain partitions, offsets and consumer groups." Define each; partition = ordering and parallelism unit; group = load sharing; offset = progress. "How do you keep events of one order in order?" Use the order id as the record key. "What if there are more consumers than partitions?" Extra consumers idle.

Kafka with Spring: KafkaTemplate, @KafkaListener, JSON and dead-letter topics

Add spring-kafka, configure serializers and a consumer group in YAML, publish with KafkaTemplate using a business key, consume with @KafkaListener, and handle failures with retries and a dead-letter topic through DefaultErrorHandler.

Setup

<dependency>
    <groupId>org.springframework.kafka</groupId>
    <artifactId>spring-kafka</artifactId>
</dependency>
spring:
  kafka:
    bootstrap-servers: ${KAFKA_BOOTSTRAP:localhost:9092}
    producer:
      acks: all                                  # wait for all in-sync replicas
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
      properties:
        enable.idempotence: true                 # no duplicates from producer retries
        spring.json.add.type.headers: false      # do not tie consumers to our class names
    consumer:
      group-id: notification-service             # consumer group
      auto-offset-reset: earliest                # new group starts from the beginning
      enable-auto-commit: false
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      properties:
        spring.deserializer.value.delegate.class: >-
          org.springframework.kafka.support.serializer.JsonDeserializer
        spring.json.trusted.packages: com.example.events
        spring.json.value.default.type: com.example.events.ApplicationSubmitted
    listener:
      ack-mode: record                           # commit the offset after each record
      concurrency: 3                             # 3 consumer threads in this instance
    template:
      observation-enabled: true                  # tracing for sends (see tracing article)
  • acks: all with enable.idempotence: true is the safe producer setting: a message is acknowledged only when all in-sync replicas have it, and a retry cannot create a duplicate in the partition.
  • auto-offset-reset matters only when the group has no committed offset: earliest reads history, latest reads only new records.
  • ErrorHandlingDeserializer wraps the real deserializer so a malformed message does not crash the consumer in an endless loop (a "poison pill"); the error is delivered to the error handler.
  • spring.json.trusted.packages is a security setting: JSON deserialization may only create classes from these packages. Do not use * in production.

Version note

The class names JsonSerializer and JsonDeserializer come from Spring for Apache Kafka and use Jackson 2. Spring Boot 4 moves to Jackson 3, and Spring for Apache Kafka 4 provides matching Jackson 3 serializers; names and packages differ, so use the ones in the reference for your version. The Kafka concepts and the property structure (spring.kafka.*) are unchanged.

The event class

A shared contract. Keep events small, immutable and versionable. Records are perfect:

package com.example.events;

import java.time.Instant;
import java.util.UUID;

public record ApplicationSubmitted(
        UUID eventId,              // unique id: lets consumers detect duplicates
        Long applicationId,
        Long jobId,
        Long candidateId,
        String recruiterEmail,
        Instant occurredAt) { }

Creating the topic

@Configuration
public class KafkaTopicConfig {

    public static final String APPLICATION_EVENTS = "application-events";

    @Bean
    NewTopic applicationEventsTopic() {
        return TopicBuilder.name(APPLICATION_EVENTS)
                .partitions(3)
                .replicas(1)                   // 3 in a real cluster
                .build();                      // created at startup if it does not exist
    }
}

Producer: KafkaTemplate

@Component
public class ApplicationEventsProducer {

    private static final Logger log = LoggerFactory.getLogger(ApplicationEventsProducer.class);
    private final KafkaTemplate<String, ApplicationSubmitted> kafkaTemplate;

    public ApplicationEventsProducer(KafkaTemplate<String, ApplicationSubmitted> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    public void publish(ApplicationSubmitted event) {
        String key = String.valueOf(event.jobId());              // same job -> same partition
        kafkaTemplate.send(KafkaTopicConfig.APPLICATION_EVENTS, key, event)
                .whenComplete((result, ex) -> {                  // send() is asynchronous
                    if (ex != null) {
                        log.error("Publish failed for application {}", event.applicationId(), ex);
                    } else {
                        var md = result.getRecordMetadata();
                        log.info("Published to {}-{} offset {}", md.topic(), md.partition(), md.offset());
                    }
                });
    }
}
  • send() returns a CompletableFuture<SendResult> in current Spring Kafka versions (older versions returned a ListenableFuture). It is non-blocking; a failure appears only in the callback, so always handle it.
  • Choose the key deliberately. No key means records are spread without ordering. A skewed key (one huge customer) overloads one partition.
  • Do not publish inside the database transaction and hope: if the transaction rolls back, the event is already out; if the app crashes after commit and before publishing, the event is lost. See the outbox pattern in the next articles.

Consumer: @KafkaListener

@Component
public class ApplicationEventsListener {

    private static final Logger log = LoggerFactory.getLogger(ApplicationEventsListener.class);
    private final NotificationService notificationService;
    private final ProcessedEventRepository processedEvents;

    // constructor omitted

    @KafkaListener(topics = "application-events", groupId = "notification-service")
    @Transactional
    public void onApplicationSubmitted(ApplicationSubmitted event,
                                       @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
                                       @Header(KafkaHeaders.OFFSET) long offset) {
        log.info("Received {} from partition {} offset {}", event.eventId(), partition, offset);

        if (!processedEvents.markProcessed(event.eventId())) {     // idempotency: seen already?
            log.info("Duplicate event {} ignored", event.eventId());
            return;
        }
        notificationService.notifyRecruiter(event);                 // do the real work
    }
}
  • The method parameter type is the payload; add @Header parameters for metadata, or take a whole ConsumerRecord<String, ApplicationSubmitted>.
  • Instances with the same groupId share the partitions. A second group (analytics) with its own listener gets every event too.
  • concurrency starts several consumer threads in one instance; the total across all instances cannot usefully exceed the partition count.
  • Listener threads are not request threads: no SecurityContext, no web request. Wrap work in its own transaction.
  • Process quickly. If one poll's processing takes longer than max.poll.interval.ms (5 minutes by default), Kafka thinks the consumer died and rebalances.

Commit behaviour: with ack-mode: record the offset is committed after the listener method returns normally; if it throws, the error handler decides (retry, skip, dead-letter). With MANUAL ack mode you inject an Acknowledgment and call acknowledge() yourself, useful when work finishes asynchronously.

Error handling: retries and a dead-letter topic

A listener will meet bad data or temporary failures (database down). Without a plan, a failing record is retried again and again and blocks its partition. Spring Kafka's DefaultErrorHandler retries with a back-off, then hands the record to a recoverer. The standard recoverer publishes it to a dead-letter topic (DLT), a parking place for messages that could not be processed, where humans or tools inspect them.

@Configuration
public class KafkaErrorConfig {

    @Bean
    DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
        // after retries are used up, publish to "<topic>.DLT" (same partition number)
        var recoverer = new DeadLetterPublishingRecoverer(template);

        var backOff = new ExponentialBackOffWithMaxRetries(4);   // up to 4 retries
        backOff.setInitialInterval(1_000);
        backOff.setMultiplier(2.0);
        backOff.setMaxInterval(10_000);

        var handler = new DefaultErrorHandler(recoverer, backOff);
        handler.addNotRetryableExceptions(IllegalArgumentException.class);   // bad data: no retry
        return handler;
    }
}

Boot picks up a single CommonErrorHandler bean for its listener container factory. A dead-letter record carries headers with the original topic, partition, offset and the exception message, so you can diagnose and, after a fix, re-publish it. Alternatively, @RetryableTopic creates retry topics (-retry-0, -retry-1) and a DLT for you, so retries do not block the main partition, at the cost of more topics and weaker ordering.

Monitor the DLT (alert when it is not empty) and the consumer lag, the difference between the latest offset and the group's committed offset, which shows whether consumers keep up.

Testing

Use Testcontainers with a Kafka container (@ServiceConnection sets the bootstrap address, module 5) and Awaitility to wait for the asynchronous result: publish, then await().atMost(10, SECONDS).untilAsserted(...). @EmbeddedKafka from spring-kafka-test is faster to start but less like the real broker.

Common mistakes

  • Ignoring the future returned by send(): failures vanish.
  • No key, then wondering why events of one job are processed out of order.
  • Unlimited retries on a poison message: the partition is blocked for ever.
  • Sharing a Java class between services through a "common" library so every change forces all services to redeploy; prefer a stable, versioned schema (JSON schema, Avro with a schema registry).
  • Using the same group.id for two different services: they steal each other's messages.
  • Doing slow, blocking work in the listener until the poll timeout expires and a rebalance storm begins.

Exceptions and edge cases

  • SerializationException or DeserializationException: bad payload or a missing trusted package; wrapped by the ErrorHandlingDeserializer.
  • TimeoutException: Topic ... not present in metadata: wrong bootstrap server, topic missing, or auto-creation disabled.
  • org.apache.kafka.common.errors.RecordTooLargeException: message above the broker limit (about 1 MB by default); send a reference to the data instead of the data.
  • CommitFailedException / rebalance: processing took too long between polls.

Interview angle

"How do you produce and consume in Spring?" KafkaTemplate.send(topic, key, value) and @KafkaListener(topics, groupId). "How do you handle a failing message?" Retry with back-off, then dead-letter topic; no-retry for bad data; alert on DLT. "How do you avoid duplicates?" Idempotent producer plus idempotent consumer with an event id. "Why a key?" Ordering per entity. "What is consumer lag?" Distance between the log end and the group's committed offset.

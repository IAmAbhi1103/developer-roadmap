CORS: same-origin policy, preflight and Spring Security configuration

Browsers block JavaScript from reading responses of another origin unless that server allows it with CORS headers; configure one CorsConfigurationSource bean with your exact frontend origins, connect it with cors(withDefaults()), and never combine * with credentials.

The same-origin policy and what an origin is

A browser lets a page talk freely to its own server, but a page from one site must not read data from another site (otherwise any web page could call your bank in the background). This rule is the same-origin policy. An origin is the triple scheme + host + port.

Page at http://localhost:5173 callsSame origin?Why
http://localhost:5173/api/jobsYesSame scheme, host, port
http://localhost:8080/api/jobsNoDifferent port: React dev server vs Spring Boot
https://localhost:5173/xNoDifferent scheme
http://api.jobportal.in/xNoDifferent host

CORS (Cross-Origin Resource Sharing) is the standard way for a server to say "this other origin may read my responses". It is a browser rule: Postman and curl ignore it, and the server still receives the request. The classic symptom is a React console error: "Access to fetch at 'http://localhost:8080/api/jobs' from origin 'http://localhost:5173' has been blocked by CORS policy". The fix is on the server (or a dev proxy), not in React.

Simple requests and the preflight

For simple requests (GET, or POST with a form content type, no custom headers) the browser sends the request and then checks the response header Access-Control-Allow-Origin. For anything else, for example PUT, DELETE, Content-Type: application/json or an Authorization header, the browser first sends a preflight: an OPTIONS request asking permission, without credentials.

OPTIONS /api/jobs HTTP/1.1
Origin: http://localhost:5173
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization,content-type

HTTP/1.1 200
Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Methods: GET,POST,PUT,PATCH,DELETE,OPTIONS
Access-Control-Allow-Headers: authorization,content-type
Access-Control-Max-Age: 3600

Max-Age lets the browser cache the preflight answer, so it does not repeat before every call.

Configuring CORS with Spring Security

Define a CorsConfigurationSource bean and enable it with http.cors(withDefaults()). This puts CorsFilter early in the security chain, so a preflight (which carries no token) is answered before authentication rejects it with 401.

@Configuration
public class CorsConfig {

    @Bean
    CorsConfigurationSource corsConfigurationSource(
            @Value("${app.cors.allowed-origins}") List<String> origins) {
        CorsConfiguration cfg = new CorsConfiguration();
        cfg.setAllowedOrigins(origins);                    // exact origins, no wildcard
        cfg.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"));
        cfg.setAllowedHeaders(List.of("Authorization", "Content-Type"));
        cfg.setExposedHeaders(List.of("Location"));        // headers JS may read
        cfg.setAllowCredentials(false);                    // true only for cookie auth
        cfg.setMaxAge(3600L);

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/api/**", cfg);
        return source;
    }
}
app:
  cors:
    allowed-origins: http://localhost:5173,https://jobportal.example.com

Then .cors(Customizer.withDefaults()) in the SecurityFilterChain picks up the bean named corsConfigurationSource. Origins come from properties so development and production differ without code changes.

@CrossOrigin and WebMvcConfigurer

@CrossOrigin(origins = "http://localhost:5173")      // one controller or method
@RestController
class JobController { ... }

@Configuration
class WebConfig implements WebMvcConfigurer {         // MVC-level global config
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**").allowedOrigins("http://localhost:5173");
    }
}

These work for plain Spring MVC, but with Spring Security present the CorsConfigurationSource bean above is the better single place: one list of allowed origins for the whole app and it also covers requests that security rejects (401/403 responses still carry CORS headers, so the browser can show the real error instead of a confusing CORS failure). Scattered @CrossOrigin annotations are easy to forget on new controllers.

Credentials and wildcards

When the frontend sends cookies (fetch(..., { credentials: "include" })), the server must answer with Access-Control-Allow-Credentials: true and a specific origin. The wildcard * is forbidden together with credentials; Spring throws IllegalArgumentException: When allowCredentials is true, allowedOrigins cannot contain the special value "*". If you need patterns (all subdomains), use setAllowedOriginPatterns(List.of("https://*.jobportal.in")). For a Bearer-token API, allowCredentials can stay false, because the token travels in a header the JavaScript sets itself.

Avoiding CORS in development

Vite's dev server can proxy /api to localhost:8080, so the browser sees one origin and no preflight is needed. Production behind one domain with a reverse proxy (Nginx) has the same effect. Keep the CORS config anyway for separate frontend domains. See Frontend · Module 6.

Common mistakes

  • Allowing * for every origin on an API that uses cookies. Any website can then call it as the logged-in user.
  • Fixing the error by disabling CORS in the browser or by adding @CrossOrigin("*") everywhere "to make it work".
  • Forgetting cors(withDefaults()): the MVC mapping exists, but security answers the preflight with 401 first.
  • Allowing the origin but not the Authorization header in allowedHeaders.
  • Trailing slash or wrong port in the origin: http://localhost:5173/ does not match http://localhost:5173.
  • Believing CORS protects the API. It only restricts browsers; authentication does the protecting.

Interview angle

"What is CORS and why does the preflight exist?" Same-origin policy, origin = scheme+host+port, browser enforced; preflight asks permission before non-simple requests so a foreign page cannot trigger a state-changing call that the server never agreed to. "Why can't I use * with credentials?" Spec forbids it, because it would let any site act as the user. "Does CORS stop curl?" No.

CSRF: the attack, and when protection can be off

CSRF tricks a logged-in browser into sending a request the user never intended, which works only when the browser attaches credentials automatically (cookies); stateless APIs that need an Authorization header set by your own code can turn CSRF protection off, but tokens kept in cookies bring it back.

The attack, as a story

Ravi is logged in to jobportal.com; his browser holds the session cookie. In another tab he opens a harmless-looking page, cute-cats.example. That page contains a hidden form:

<form action="https://jobportal.com/api/account/email" method="POST" id="f">
  <input name="email" value="attacker@evil.example">
</form>
<script>document.getElementById("f").submit();</script>

The browser sends the POST to jobportal.com and, because that is the cookie's site, attaches Ravi's session cookie automatically. The server sees a valid session and changes the account email to the attacker's. The attacker then resets the password. Ravi clicked nothing. This is Cross-Site Request Forgery. The attacker cannot read the response (the same-origin policy and CORS prevent that), but a state-changing request is enough.

The requirement: the credential is attached automatically by the browser. Cookies and HTTP Basic credentials both behave this way.

How Spring Security defends: the CSRF token

The defence is a secret value that the attacker's page cannot know. The server gives the legitimate page a random CSRF token; for every unsafe request (POST, PUT, PATCH, DELETE) the page must send it back in a header (X-CSRF-TOKEN) or a hidden form field (_csrf). CsrfFilter compares it to the expected value and answers 403 when it is missing or wrong. GET, HEAD, OPTIONS and TRACE are exempt because they must not change data. Spring Security has this on by default, which is why your first POST after adding the starter returned 403.

  • Thymeleaf forms add the hidden field automatically.
  • For a JavaScript SPA with cookie sessions, store the token in a cookie that JavaScript can read and echo it back in the header: .csrf(c -> c.csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())) (the token cookie must be readable by JS, so it is not HttpOnly).
  • Defence in depth: SameSite=Lax or Strict on the session cookie. Modern browsers default to Lax, which already blocks the cross-site POST above; it still does not replace the token for all cases.

Why a stateless Bearer-token API can disable it

In our JWT design, the JavaScript code reads the token from memory and writes Authorization: Bearer ... on each request. A page on cute-cats.example cannot do that: it cannot read your token (different origin), and a browser never adds an Authorization header to a cross-site form post on its own. There is nothing automatic for the attacker to ride on. So the CSRF filter protects against an attack that cannot happen, and Spring's documentation says it is fine to disable it for such APIs:

http.csrf(csrf -> csrf.disable())
    .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
// 1. no session cookie  2. credentials only in the Authorization header
// 3. no HTTP Basic or form login left enabled

When tokens in cookies bring CSRF back

Some teams keep the JWT (or refresh token) in an HttpOnly cookie, so JavaScript cannot steal it with XSS. That is a good idea for XSS, but now the browser attaches the credential automatically, and the whole CSRF argument above applies again. If you store the access token in a cookie, you must keep CSRF protection (or rely strictly on SameSite=Strict plus a custom-header check), and CORS with credentials becomes relevant. A refresh-token cookie scoped to /api/auth/refresh is a smaller risk, because the worst the attacker can do is force a token refresh whose result they cannot read, but protect that endpoint too.

SetupCredential sentCSRF protection
Server-rendered site, session cookieCookie, automaticallyOn (default)
SPA + session cookieCookie, automaticallyOn, token in cookie + header
SPA + Bearer token in memory or localStorageHeader, by your codeCan be off
SPA + JWT stored in a cookieCookie, automaticallyOn (or SameSite=Strict + checks)

Rule: CSRF is about automatic credentials, not about "REST"

Do not disable CSRF just because "it is an API". Disable it because nothing in your design is attached to the request automatically. If a session cookie or Basic auth is anywhere in play, leave it on.

Common mistakes

  • Calling csrf.disable() on an app that still uses JSESSIONID sessions or httpBasic().
  • Making state-changing endpoints with GET (GET /api/jobs/5/delete); GET is not CSRF-protected.
  • Confusing CSRF with XSS. CSRF abuses the browser's automatic credentials; XSS runs the attacker's JavaScript inside your page and can read tokens in localStorage.
  • Confusing CSRF with CORS. CORS controls who may read responses; it does not stop the sending of a form post.

Interview angle

"What is CSRF and how is it prevented?" Give the forged-form story, the automatic cookie, then the synchronizer token and SameSite cookies. "Why do you disable CSRF in your JWT API?" Bearer header is not sent automatically by the browser; stateless; no session cookie. "When would you re-enable it?" When the token lives in a cookie.

Refresh tokens: short-lived access tokens, rotation and logout

Keep the access JWT short (minutes), give the client a long-lived random refresh token stored hashed in your database, rotate it on every use, and revoke it on logout or when reuse is detected.

The problem

An access JWT cannot be revoked, so the longer it lives, the longer a stolen one works. But a 15-minute token means the user would log in every 15 minutes. The answer is two tokens:

  • Access token: a JWT valid for 5–30 minutes, sent with every API call.
  • Refresh token: a long-lived (days to weeks) opaque random string, sent only to one endpoint (/api/auth/refresh) to get a new access token.

The refresh token is not a JWT: it is stored on the server, so it can be checked, rotated and deleted. That gives you the revocation that pure JWTs lack.

Rotation and reuse detection

Rotation means every refresh call returns a new refresh token and invalidates the old one. A stolen token then works at most once before the real user's next refresh fails. Reuse detection goes further: if an already-used refresh token is presented again, somebody has a copy (either the thief or the user, after the thief rotated it). The server cannot tell which, so it revokes the whole family (all tokens that descend from that login), forcing a fresh login on every device of that session chain.

Storing refresh tokens

create table refresh_token (
    id          bigserial primary key,
    user_id     bigint not null references app_user(id) on delete cascade,
    family_id   uuid not null,
    token_hash  varchar(64) not null unique,   -- SHA-256 hex of the token
    expires_at  timestamp not null,
    used        boolean not null default false,
    revoked     boolean not null default false,
    created_at  timestamp not null default now()
);

Store a hash of the token, never the token. If the table leaks, the attacker still cannot use the values. A fast hash (SHA-256) is fine here, unlike passwords, because the token is 256 bits of randomness, not a guessable password.

@Service
public class RefreshTokenService {

    private static final SecureRandom RANDOM = new SecureRandom();
    private final RefreshTokenRepository repo;

    public RefreshTokenService(RefreshTokenRepository repo) { this.repo = repo; }

    /** Create a token for a fresh login: new family. */
    @Transactional
    public String create(Long userId) {
        return store(userId, UUID.randomUUID());
    }

    /** Validate, rotate and return the new raw token plus the user id. */
    @Transactional(noRollbackFor = InvalidRefreshTokenException.class)
    public Rotation rotate(String rawToken) {
        RefreshToken stored = repo.findByTokenHash(sha256(rawToken))
                .orElseThrow(() -> new InvalidRefreshTokenException("Unknown token"));

        if (stored.isUsed() || stored.isRevoked()) {
            repo.revokeFamily(stored.getFamilyId());         // reuse detected
            throw new InvalidRefreshTokenException("Token reuse detected");
        }
        if (stored.getExpiresAt().isBefore(Instant.now())) {
            throw new InvalidRefreshTokenException("Expired");
        }
        stored.markUsed();
        String next = store(stored.getUserId(), stored.getFamilyId());
        return new Rotation(stored.getUserId(), next);
    }

    private String store(Long userId, UUID family) {
        byte[] bytes = new byte[32];
        RANDOM.nextBytes(bytes);
        String raw = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
        repo.save(new RefreshToken(userId, family, sha256(raw),
                Instant.now().plus(Duration.ofDays(7))));
        return raw;
    }

    private static String sha256(String s) {
        try {
            byte[] d = MessageDigest.getInstance("SHA-256")
                    .digest(s.getBytes(StandardCharsets.UTF_8));
            return HexFormat.of().formatHex(d);
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }

    public record Rotation(Long userId, String newRefreshToken) {}
}

Notes: noRollbackFor matters. The reuse branch revokes the family and then throws; with the default rule the exception would roll the revocation back (@Transactional rollback rules) if the exception were unchecked. The refresh controller calls rotate, loads the user (check that the account is still enabled!) and issues a new access token with the TokenService. Delete expired rows with a scheduled job (module 6).

A widely used compromise: keep the access token in memory and the refresh token in an HttpOnly, Secure, SameSite cookie restricted to the refresh path. On page load, React calls /api/auth/refresh to get a new access token silently. Setting such a cookie in Spring:

ResponseCookie cookie = ResponseCookie.from("refresh_token", rawToken)
        .httpOnly(true)
        .secure(true)                  // HTTPS only
        .sameSite("Strict")
        .path("/api/auth")             // sent only to auth endpoints
        .maxAge(Duration.ofDays(7))
        .build();
response.addHeader(HttpHeaders.SET_COOKIE, cookie.toString());

How the React side wires this up (an Axios interceptor that refreshes on 401 and retries) is in Frontend · Module 6.

Logout and revocation

  • Logout: revoke the user's current refresh token (or family) in the database, clear the cookie, and have the client forget the access token. The access token stays valid until it expires (minutes).
  • Logout everywhere / password change / account disabled: revoke all refresh tokens of the user.
  • Immediate access-token revocation (rarely needed): keep a deny list of jti values in Redis with a TTL equal to the token lifetime, and check it in the filter; or add a per-user "token version" claim and compare it with the database. This gives back some statefulness; use only if the short expiry is not enough.

Common mistakes

  • Making the refresh token another long-lived JWT that is never stored: nothing can be revoked.
  • Storing raw refresh tokens in the database.
  • No rotation: a stolen refresh token works for weeks.
  • Sending the refresh token with every API call, which defeats the purpose.
  • Not re-checking that the user is still enabled when refreshing.

Interview angle

"How do you log out with JWT?" Short access token plus revocable refresh tokens in the database; optionally a jti deny list. "What is refresh-token rotation?" New refresh token on each use, old one invalid; reuse of an old one revokes the family. "Where do you store tokens in the browser?" Memory for access, HttpOnly cookie for refresh; explain the XSS vs CSRF trade-off against localStorage.

OAuth2, OpenID Connect and "Login with Google/GitHub"

OAuth2 lets an app act with a user's permission without seeing their password, and OpenID Connect adds identity on top; with spring-boot-starter-oauth2-client a few properties give you social login, after which you may still issue your own JWT.

OAuth2 vocabulary

OAuth 2.0 is a standard for delegated authorization: "let this app access my data at that service, without giving the app my password". OpenID Connect (OIDC) is a thin layer on top that adds authentication: it returns an ID token (a JWT) saying who the user is. "Login with Google" is OIDC.

Resource owner
The user who owns the data.
Client
The application that wants access (your Spring Boot app or your React app).
Authorization server
Authenticates the user and issues tokens (Google, GitHub, Keycloak, Okta).
Resource server
The API that accepts access tokens (Google's APIs; your own API from the earlier articles).
Scope
What the client asks for, e.g. openid profile email.

Authorization code flow with PKCE

The recommended flow for web apps and SPAs is the authorization code flow. The user is sent to the provider to log in (the client never sees the password), the provider returns a short-lived code through the browser, and the client exchanges that code for tokens on a direct, back-channel call. PKCE (Proof Key for Code Exchange, "pixy") adds a random secret created at the start (code_verifier, sent as a hash called code_challenge) and proved at the end, so a stolen code is useless. It is required for public clients (SPAs, mobile) and recommended for all.

The state parameter is a random value the client checks on return; it prevents CSRF on the login redirect.

Opening a protected URL now redirects to a generated page with "Google" and "GitHub" links; after login the principal is an OidcUser (Google) or OAuth2User (GitHub, which does not support OIDC). On your database you map the provider's email to a local User row (create it on first login) so that roles and ownership still work.

Common mistakes

  • Redirect URI mismatch: the value in the provider console differs from {baseUrl}/login/oauth2/code/google in scheme, host, port or path. The provider shows a redirect_uri_mismatch error.
  • Committing the client secret. Use environment variables.
  • Treating an OAuth2 access token as proof of identity. Use the OIDC ID token for "who is this".
  • Trusting the provider's email without checking that it is verified, then linking to an existing local account (account takeover).
  • Using the old implicit flow or putting tokens in the URL fragment of an SPA; use code + PKCE.

Interview angle

"OAuth2 vs OpenID Connect?" OAuth2 = authorization (access tokens); OIDC = authentication on top (ID token). Security best practices checklist and the OWASP Top 10

Most real breaches come from missing basics: plain HTTP, leaked secrets, no rate limit, missing ownership checks, verbose errors and outdated libraries; walk this checklist before every release.

Checklist for a Spring Boot API

  1. HTTPS only. Terminate TLS at the load balancer or reverse proxy and redirect HTTP to HTTPS. Without it, passwords and tokens travel in clear text. Add HSTS (Spring Security adds the header on HTTPS requests).
  2. Secrets in environment variables or a secret manager (JWT key, database password, OAuth2 client secret). Never in Git, never in the Docker image. Rotate them when someone leaves (DevOps · Module 5).
  3. Hash passwords with BCrypt/Argon2; enforce minimum length; never log them.
  4. Short access tokens, rotating refresh tokens, an explicit issuer check.
  5. Rate-limit login, register and password reset (per IP and per account), using a gateway, Bucket4j, or a small Redis counter. Lock an account (or add delays) after repeated failures, and notify the user.
  6. Authorize on the server for every endpoint: role plus ownership. Deny by default with anyRequest().authenticated().
  7. Validate all input (@Valid, size limits); use parameterised queries (Spring Data does) so there is no SQL injection; never build SQL by string concatenation.
  8. Do not leak details. One message for "wrong email or password"; no stack traces, SQL or class names in error JSON; server.error.include-stacktrace=never; return DTOs, never entities.
  9. Security headers. Spring Security sets X-Content-Type-Options and cache headers; add Content-Security-Policy and Referrer-Policy if you serve HTML.
  10. CORS with exact origins; CSRF on whenever cookies carry credentials.
  11. Protect operational endpoints. Expose only health (and what you need) from Actuator, and secure the rest (module 6). Disable the H2 console outside development.
  12. Keep dependencies updated. Run OWASP Dependency-Check or Dependabot/Renovate; a vulnerable library (the Log4Shell case) is a vulnerability in your app.
  13. Log security events (logins, failures, denials, role changes) without secrets, and monitor them.
  14. Least privilege. The application's database user should not be a superuser; containers run as non-root.
  15. Test security: 401/403 and ownership cases belong in your suite (module 5).

Interview questions — Security

What is the difference between authentication and authorization?

Authentication proves who you are (password, token); authorization decides what you may do once identified (roles, ownership). Authentication comes first. Failures map to HTTP 401 and 403. In Spring Security: AuthenticationManager for the first, AuthorizationFilter and @PreAuthorize for the second.

What happens when you add spring-boot-starter-security to a project?

Every endpoint becomes authenticated. A default user named user with a random password printed in the log is created, form login and HTTP Basic are enabled, CSRF protection is on (POST without a token gets 403), a session is used, and default security headers are added. You take control by defining a SecurityFilterChain, a UserDetailsService and a PasswordEncoder.

Explain the Spring Security filter chain.

Security is a list of servlet filters before DispatcherServlet. DelegatingFilterProxy hands the request to FilterChainProxy, which selects the first matching SecurityFilterChain. Important filters: CORS, CSRF, an authentication filter (Bearer token, form login), ExceptionTranslationFilter (turns exceptions into 401/403), and AuthorizationFilter (URL rules). Authentication results are stored in the thread-local SecurityContextHolder.

How does Spring check a username and password?

AuthenticationManager (ProviderManager) delegates to DaoAuthenticationProvider. It calls UserDetailsService.loadUserByUsername, checks account flags (enabled, locked, expired) and then PasswordEncoder.matches(raw, hash). A mismatch gives BadCredentialsException, which becomes 401.

Why hash passwords with BCrypt instead of encrypting or using SHA-256?

Encryption is reversible (the key can leak). SHA-256 is fast, so attackers test billions of guesses per second and use rainbow tables. BCrypt is one-way, adds a random salt automatically (equal passwords give different hashes) and has a tunable cost factor that makes each guess slow. Verify with matches, never equals.

What is a JWT, and is its payload secret?

A JSON Web Token has three base64url parts: header, payload (claims such as sub, iat, exp, roles) and signature. The signature proves integrity; the payload is only encoded, so anyone can read it. Never put secrets in it. The server verifies the signature and expiry on every request and needs no session storage.

HS256 vs RS256?

HS256 uses one shared secret for both signing and verifying: simple and fast, but every verifier can also forge tokens. RS256 uses a private key to sign and a public key to verify, so many services can verify without being able to issue tokens; it fits microservices and external identity providers (JWKS).

How do you implement JWT login in Spring Boot?

A login endpoint authenticates through the AuthenticationManager and returns a signed token. On later requests either a custom OncePerRequestFilter (placed before UsernamePasswordAuthenticationFilter) parses the Bearer header and sets the SecurityContext, or, preferably, the OAuth2 Resource Server support with a JwtDecoder does it. The session policy is STATELESS and CSRF is disabled for header-based tokens.

What is the difference between 401 and 403?

401 means unauthenticated: no or invalid credentials, so the client should log in or refresh. 403 means authenticated but not permitted; logging in again does not help. In Spring, AuthenticationEntryPoint produces 401 and AccessDeniedHandler produces 403; customise both to return JSON.

What is the difference between hasRole and hasAuthority?

Both check GrantedAuthority strings. hasRole("ADMIN") adds the ROLE_ prefix and checks ROLE_ADMIN; hasAuthority("ROLE_ADMIN") checks the exact text. A frequent bug is storing roles without the prefix and getting 403 from hasRole.

How do you make sure a recruiter can edit only their own jobs?

The role check says recruiters may edit jobs; ownership needs data. Load the job in the service, compare job.getPostedBy().getId() with the current user's id (from the Authentication), and throw AccessDeniedException (403) otherwise; admins may bypass. Alternatively use @PreAuthorize("@jobSecurity.isOwner(#id, authentication)"). Filter list queries by owner. Never trust a user id from the request body.

What is CORS and why is there a preflight request?

Browsers apply the same-origin policy (origin = scheme + host + port); CORS is the server's way to allow other origins to read its responses. For non-simple requests (JSON content type, Authorization header, PUT/DELETE) the browser first sends an OPTIONS preflight asking whether the real request is allowed. In Spring Security register a CorsConfigurationSource bean and call cors(withDefaults()); do not use * together with credentials.

What is CSRF? Can you disable it for a JWT API?

CSRF makes a victim's browser send a state-changing request to a site where they are logged in, using credentials the browser attaches automatically (cookies). Defence: CSRF tokens and SameSite cookies. For a stateless API where the token goes in the Authorization header set by your JavaScript, there is nothing automatic to abuse, so you can disable it. If the token lives in a cookie, keep CSRF protection.

How do refresh tokens work, and how do you log out a JWT user?

The access JWT lives minutes; a random refresh token (stored hashed in the database) lives days and only buys new access tokens. Rotate it on each use and revoke the whole family if an old one is reused. Logout revokes the refresh tokens (and clears the cookie); the access token stays valid until it expires, unless you keep a jti deny list.

Explain the OAuth2 authorization code flow and PKCE.

The client redirects the user to the authorization server, the user logs in there and consents, the server redirects back with a short-lived code (plus state), and the client exchanges the code on the back channel for tokens. PKCE adds a one-time secret (verifier and its hash, the challenge) so a stolen code cannot be redeemed; it is mandatory for SPAs and mobile apps. OIDC adds an ID token for identity.

Cheat sheet — Security

  • AuthN vs AuthZ who are you (401 on failure) vs what may you do (403 on failure).
  • Starter default everything secured, user user + generated password, form login, Basic, CSRF on.
  • Filter chain DelegatingFilterProxy to FilterChainProxy to SecurityFilterChain; ExceptionTranslationFilter then AuthorizationFilter at the end.
  • SecurityContextHolder thread-local; holds the Authentication (principal, credentials, authorities).
  • Password check AuthenticationManager to DaoAuthenticationProvider to UserDetailsService + PasswordEncoder.
  • Config a SecurityFilterChain bean with the lambda DSL; WebSecurityConfigurerAdapter is removed.
  • Rule order first match wins; end with anyRequest().authenticated().
  • API chain csrf.disable(), cors(withDefaults()), STATELESS, Basic and form login off.
  • Passwords BCrypt (salted, cost 10 default), matches not equals, never log, max 72 bytes.
  • DelegatingPasswordEncoder stores {bcrypt}...; supports migration between algorithms.
  • JWT header.payload.signature, base64url; payload readable; claims sub iat exp iss aud.
  • HS256 / RS256 shared secret (at least 32 bytes) / key pair.
  • Custom filter OncePerRequestFilter + jjwt, addFilterBefore(..., UsernamePasswordAuthenticationFilter.class), do not make it a @Component.
  • Resource server spring-boot-starter-oauth2-resource-server, JwtDecoder (NimbusJwtDecoder.withSecretKey), JwtEncoder, set the HS256 header.
  • Roles from JWT JwtGrantedAuthoritiesConverter: claim name roles, prefix ROLE_.
  • 401 / 403 JSON AuthenticationEntryPoint / AccessDeniedHandler (advice cannot see filter errors).
  • hasRole adds ROLE_; hasAuthority is exact text.
  • Method security @EnableMethodSecurity + @PreAuthorize; proxy-based, so no self-invocation.
  • Ownership check in the service against the loaded entity; filter queries by owner; admin bypass explicit.
  • Current user Authentication parameter, @AuthenticationPrincipal, never the id from the body.
  • CORS exact origins in a CorsConfigurationSource bean; preflight is OPTIONS; no * with credentials.
  • CSRF needed when credentials are sent automatically (cookies); off for Bearer-header APIs.
  • Refresh token random, hashed in DB, rotated, family revoked on reuse; access token in memory.
  • OAuth2 roles: owner, client, authorization server, resource server; code flow + PKCE; OIDC adds ID token.
  • Checklist HTTPS, secrets in env, rate-limit login, validate input, generic errors, update dependencies.

Practice — Security

  1. Meet the defaults. Add spring-boot-starter-security to Project 2. Find the generated password in the log, call GET /api/jobs with curl (expect 401), then with -u user:password (200). Then POST without a CSRF token and note the 403. Done when you can explain each of the three results.
  2. Register with BCrypt. Add role, passwordHash, enabled to the User entity and migration; build POST /api/auth/register (CANDIDATE or RECRUITER only; duplicate email gives 409). Done when the database column holds a 60-character hash starting with $2a$ and two users with the same password have different hashes.
  3. Load users from the database. Implement AppUserDetails and DbUserDetailsService; expose the AuthenticationManager. Done when a wrong password returns 401 with a generic message and a disabled user cannot log in.
  4. JWT login, way 1. Implement JjwtService, the filter and POST /api/auth/login. Done when a token from login opens GET /api/me, a tampered token or a token with a past exp returns 401 JSON, and no endpoint besides login/register and public GETs works without a token.
  5. JWT login, way 2. Switch to the OAuth2 Resource Server with JwtEncoder/JwtDecoder and the role converter, removing the custom filter. Done when the same requests behave identically and you can write down three differences between the two versions.
  6. Roles for Project 2. Enforce the access matrix: only RECRUITER posts jobs, only CANDIDATE applies, ADMIN manages users. Use URL rules for the broad cases and @PreAuthorize for at least two methods. Done when each cell of the matrix is verified by a curl call.
  7. Owner-only edits. Make recruiters edit and close only their own jobs and see applications only for their jobs, candidates see only their own applications. Done when recruiter B gets 403 on recruiter A's job, "my jobs" returns only own rows, and a client-supplied user id is ignored.
  8. CORS and CSRF decisions. Run the React app from localhost:5173, watch the CORS error, add the CorsConfigurationSource bean, and verify the preflight with curl -X OPTIONS and the three Access-Control-Request-* headers. Write two sentences on why CSRF is disabled in your design.
  9. Refresh tokens (stretch). Add the refresh_token table, /refresh and /logout, rotation and reuse detection. Done when reusing an old refresh token returns 401 and the newest one stops working as well.
  10. Social login (stretch). Add Google or GitHub login to a small sandbox project with oauth2Login and print the logged-in email at /profile. Then write the security tests for all of the above in module 5.

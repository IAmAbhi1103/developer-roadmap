Almost every real API has users, and almost every user-facing bug that hurts a company is a security bug: a recruiter editing another recruiter's job, a candidate reading all applications, a leaked password table. Spring Security is the standard framework that protects Spring Boot applications. It is big, and the old tutorials are mostly out of date, so this module teaches the current style (the lambda DSL, no WebSecurityConfigurerAdapter) from first principles.

You will first understand what happens when you add the security starter, how the filter chain works and where the Authentication object lives. Then you build the full login system for Project 2: users in the database, BCrypt password hashing, stateless JWT tokens (two ways: a custom filter and the OAuth2 Resource Server support), roles CANDIDATE, RECRUITER and ADMIN, owner-only edits, clean JSON error responses, CORS and CSRF. It builds on the REST layer from module 2 and the entities from module 3. How to test all of this is in module 5, and how a React app uses the token is in Frontend · Module 6.

After this module you will be able to:

  • Explain authentication vs authorization, 401 vs 403, and sessions vs tokens.
  • Describe the Spring Security filter chain and write a modern SecurityFilterChain bean.
  • Load users from a database and hash passwords with BCrypt.
  • Issue and validate JWTs with a custom filter or with the OAuth2 Resource Server support.
  • Protect URLs and methods by role, and enforce "only the owner can edit".
  • Configure CORS correctly, and decide when CSRF protection can be off.
  • Design refresh tokens, understand OAuth2 login, and apply a security checklist.

Authentication vs authorization, 401 vs 403, sessions vs tokens

Authentication asks "who are you?", authorization asks "what may you do?"; a failed login is 401, a known user without permission is 403, and a stateless API proves identity on every request with a signed token instead of a server-side session.

Two different questions

Authentication (AuthN) is proving who you are: a username and password, a fingerprint, a one-time code, a signed token. Authorization (AuthZ) is deciding what an already-identified user is allowed to do: "a RECRUITER may post a job, a CANDIDATE may not". Authentication always comes first; you cannot authorize someone you cannot identify. Think of an airport: the passport check is authentication, the boarding pass that lets you into the business lounge is authorization.

AuthenticationAuthorization
QuestionWho are you?What are you allowed to do?
InputCredentials (password, token, certificate)The identity plus roles, permissions, resource owner
Failure status401 Unauthorized403 Forbidden
Spring Security typeAuthenticationManager, AuthenticationAuthorizationManager, @PreAuthorize
ExampleLogin with email and passwordOnly ADMIN can delete users

In practice authorization has two levels. Role-based rules look only at the user ("RECRUITER may post jobs"). Ownership (resource-level) rules also look at the data ("a recruiter may edit only their own jobs"). Roles are checked by Spring Security rules; ownership is usually checked in the service layer (authorization).

How Spring Security models "who you are"

Spring Security represents the current user as an Authentication object. It holds the principal (who: usually your UserDetails), the credentials (the password or token, erased after login), and the authorities (what: a list of strings such as ROLE_RECRUITER). A flag says whether it is authenticated. A filter puts it into the SecurityContext, stored in SecurityContextHolder, which keeps it in a thread-local for the length of the request. Your code reads it from there, or gets it as a controller parameter:

@GetMapping("/api/me")
public Map<String, Object> me(Authentication auth) {
    return Map.of(
            "name", auth.getName(),
            "authorities", auth.getAuthorities().toString());
}
{"name":"asha@example.com","authorities":"[ROLE_RECRUITER]"}

A request with no login is not "empty": Spring Security fills the context with an anonymous authentication (principal anonymousUser, role ROLE_ANONYMOUS). That lets rules like permitAll() and authenticated() work with one uniform check. How the filters build this object is shown in the filter chain article.

401 vs 403

The name of status 401 is misleading: it means "unauthenticated". The server does not know who you are, or your credentials are missing, wrong or expired. Status 403 means "I know who you are, and you may not do this".

  • 401: no token, bad password, expired or tampered JWT. The client should log in (or refresh the token) and retry.
  • 403: a valid CANDIDATE token calls POST /api/jobs. Logging in again changes nothing.
  • 404 instead of 403: sometimes you hide that a resource exists at all (a candidate asking for another candidate's application). Both are acceptable; choose one rule and keep it.
POST /api/jobs                               (no Authorization header)
HTTP/1.1 401

POST /api/jobs   Authorization: Bearer eyJ... (valid token, role CANDIDATE)
HTTP/1.1 403

POST /api/jobs   Authorization: Bearer eyJ... (valid token, role RECRUITER)
HTTP/1.1 201

Inside Spring Security, one filter decides between the two. ExceptionTranslationFilter catches the exceptions thrown further down the chain. If it catches an AuthenticationException, or an AccessDeniedException for an anonymous user, it calls the AuthenticationEntryPoint (response 401, or a redirect to a login page for browsers). If it catches an AccessDeniedException for a logged-in user, it calls the AccessDeniedHandler (response 403). Both can be replaced to return your JSON (JSON error responses).

Strictly, a 401 response should carry a WWW-Authenticate header that names the scheme (Bearer or Basic). The resource server support in Spring Security adds it; hand-written entry points often forget it.

Sessions (stateful) vs tokens (stateless)

HTTP has no memory: each request stands alone. After login the server must recognise you again on the next request. There are two classic ways.

Server-side session. The server stores your login state in memory (or Redis) under a random session id and sends the id in a JSESSIONID cookie. The browser returns the cookie automatically on every request; the server looks the session up. Spring Security can store the SecurityContext in that session. Token-based (stateless). The server stores nothing. After login it gives the client a signed token (usually a JWT, see the JWT article) containing the user id and roles. The client sends it in the Authorization: Bearer ... header, and the server only verifies the signature.

Session + cookieStateless token (JWT)
Server storesSession data for each userNothing (only the signing key)
ScalingNeeds sticky sessions or shared store (Redis)Any instance can verify; easy to scale
Logout / revokeEasy: delete the sessionHard: token is valid until it expires (see refresh tokens)
Sent byCookie, automaticallyHeader, by your JavaScript code
CSRF riskYes, must protectNo, if not kept in a cookie (CSRF)
FitsServer-rendered web appsREST APIs, SPAs, mobile apps, microservices

Neither is "better". A server-rendered site with Thymeleaf is happy with sessions. A React app plus a Spring Boot REST API, plus a future mobile app and several services, is usually happier with tokens. Project 2 uses tokens.

Security details that decide which one is safer

  • Session cookies should be HttpOnly (JavaScript cannot read them, which limits XSS theft), Secure (HTTPS only) and SameSite (limits CSRF). Spring Security also changes the session id at login (session fixation protection), so an attacker cannot plant a known id before the victim logs in.
  • Tokens in localStorage are easy to use but any XSS bug can read them. A token in an HttpOnly cookie is safer against XSS but brings back CSRF protection duties. Many apps keep a short-lived access token in memory and a refresh token in an HttpOnly cookie (refresh tokens).
  • Sessions can scale too: with Spring Session the session data lives in Redis and every instance reads it. Stateless is simpler, not the only way.
  • A JWT cannot be "logged out" by the server alone. Keep access tokens short (minutes), or keep a deny list of revoked token ids.

Rules

  • Check authentication first, then authorization; never decide permissions for an anonymous user.
  • Return 401 for "who are you?" problems and 403 for "not allowed". Do not mix them.
  • Do the authorization check on the server for every request. Hiding a button in React is not security.
  • Never trust a role or user id sent by the client in a body or query string; take it from the verified token or session.

Conventions

  • Roles are named in upper case; Spring stores them as authorities with the prefix ROLE_ (ROLE_ADMIN), and hasRole("ADMIN") adds the prefix for you. Fine-grained permissions (job:write) are authorities without the prefix.
  • Use one generic message for failed logins ("Invalid email or password"), so attackers cannot tell which emails exist.

Common mistakes

Wrong: wrong status for the wrong problem

// token missing:
return ResponseEntity.status(403).build();
// logged-in CANDIDATE calling a RECRUITER endpoint:
return ResponseEntity.status(401).build();

Right: 401 = identity, 403 = permission

// token missing or invalid:
return ResponseEntity.status(401).build();
// logged-in CANDIDATE calling a RECRUITER endpoint:
return ResponseEntity.status(403).build();
  • Putting secrets (a password, a card number) inside a JWT payload. A JWT is signed, not encrypted; anyone can read it.
  • Trusting the front end: checking the role only in React.
  • Treating "logged in" as "allowed": forgetting the ownership check, so any user can read another user's order by changing the id (broken access control, the top item of the OWASP list, best practices).

Edge cases and exceptions

  • BadCredentialsException (wrong password), DisabledException, LockedException and UsernameNotFoundException are all AuthenticationExceptions: they lead to 401.
  • AccessDeniedException comes from failed authorization: it leads to 403 (or to 401 if the user is anonymous).
  • With default settings and no custom entry point, an API that disables form login and Basic may answer anonymous requests with 403 instead of 401 (see security configuration).
  • A browser-oriented app redirects (302) to /login instead of returning 401. Fine for HTML pages, wrong for a JSON API.
  • With @PreAuthorize on a service method, the denial happens inside the call and is translated in the same way, but an unhandled AccessDeniedException thrown after the security filters ran is caught by your @ExceptionHandler if you have one for Exception, and may turn into a 500. Handle it explicitly or rethrow.

Real projects

A React + Spring Boot job portal usually works like this: POST /api/auth/login returns an access token (about 15 minutes) and sets a refresh token cookie; React sends the access token as a Bearer header; the API has stateless security with role rules for RECRUITER and CANDIDATE, plus ownership checks in services. An admin web UI built with Thymeleaf in the same company may still use sessions.

Interview angle

"Difference between authentication and authorization?" Give the one-line definitions plus the airport or login-vs-role example. "401 vs 403?" 401 = not authenticated (who are you?), 403 = authenticated but not allowed. "Why JWT instead of sessions?" Stateless, scales across instances, works for SPAs and mobile; the price is that revocation is harder. Strong answers also mention where the token is stored (memory or HttpOnly cookie versus localStorage), that sessions can scale with Redis, and that authorization must be checked on the server.

What happens when you add spring-boot-starter-security

Adding the starter secures every endpoint at once with a generated password and a default login page; you take control by defining your own SecurityFilterChain bean.

Add one dependency and nothing else:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

Restart the application. Spring Boot's auto-configuration now does the following without any code from you:

  1. Every endpoint requires authentication, including your existing REST controllers, static files and the error page. GET /api/jobs now returns 401.
  2. A default user named user is created with a random password printed in the log at startup.
  3. Form login and HTTP Basic are enabled. A browser is redirected to a generated /login page; a client such as Postman can send Basic credentials.
  4. CSRF protection is on: POST, PUT, PATCH and DELETE without a CSRF token get 403.
  5. A session is created after login, and the browser keeps the JSESSIONID cookie.
  6. Default security headers are added (X-Content-Type-Options, Cache-Control: no-cache for secured responses, X-Frame-Options and others).

configuration must be updated before running your application in production.

Taking control

This default is a safe starting point, not a design. You change it in three steps: (1) define your own SecurityFilterChain bean (once Spring Boot sees one, it backs off its default chain, see the configuration article), (2) define a UserDetailsService bean that loads real users, and (3) define a PasswordEncoder bean.

For quick experiments you can set the default user in application.properties:

spring.security.user.name=admin
spring.security.user.password=admin123
spring.security.user.roles=ADMIN

Common mistakes

  • Adding the starter late and thinking "my controllers broke". They did not; the whole app is now secured. Read the 401/403 as a feature.
  • Disabling security with http.csrf(c -> c.disable()) and permitAll() on everything "to make Postman work". Fix the configuration instead.
  • Following a tutorial that extends WebSecurityConfigurerAdapter. That class was removed in Spring Security 6 (Spring Boot 3), so the code will not compile.

Versions

Spring Boot 3.x uses Spring Security 6.x; Spring Boot 4.x uses Spring Security 7.x. The lambda DSL shown in this module works in both. In Security 7 the old non-lambda style (http.csrf().disable(), chained .and()) is gone, so always write http.csrf(csrf -> csrf.disable()).

The Spring Security architecture: the filter chain and the Authentication object

Spring Security is a chain of servlet filters in front of your controllers; filters authenticate the request, store an Authentication in the SecurityContext, and the last filters decide whether the request may continue.

Why filters

Spring MVC's DispatcherServlet and your controllers sit at the end of the request path. A servlet filter is code that runs before the servlet and can read the request, change it, or stop it and write a response itself. Security must run before any controller, so Spring Security is built from filters.

DelegatingFilterProxy
A normal servlet filter registered with the container. It does no security itself; it hands over to a Spring bean. (Spring Boot registers an equivalent for you.)
FilterChainProxy
The bean it delegates to. It holds a list of SecurityFilterChains and picks the first one whose request matcher matches the URL.
SecurityFilterChain
An ordered list of security filters for a group of URLs. This is what you configure with HttpSecurity.

The important filters, in order

FilterWhat it does
SecurityContextHolderFilterLoads the SecurityContext for the request (from the session, if any) and clears it at the end
CorsFilterAnswers CORS preflight requests and adds CORS headers (CORS)
CsrfFilterRejects state-changing requests without a valid CSRF token (CSRF)
UsernamePasswordAuthenticationFilterHandles form login (POST /login); not used by a JWT API
BasicAuthenticationFilterReads the Authorization: Basic header
BearerTokenAuthenticationFilterReads Authorization: Bearer ... and validates the JWT (added by the OAuth2 Resource Server support)
AnonymousAuthenticationFilterIf nobody logged in, sets an "anonymous" Authentication so later code never sees null
ExceptionTranslationFilterCatches AuthenticationException and AccessDeniedException thrown below it and turns them into 401 / 403 responses
AuthorizationFilterThe last one: checks the URL rules (authorizeHttpRequests) and throws if the user may not continue

Order matters: your own filter must be placed relative to these (for JWT, before UsernamePasswordAuthenticationFilter). To see the real chain of your app, set logging.level.org.springframework.security=DEBUG; at the first request it prints "Will secure any request with [filter1, filter2, ...]".

What is stored: SecurityContext and Authentication

After a successful authentication a filter puts an Authentication object into the SecurityContext, which is kept in the SecurityContextHolder, a thread-local holder (one value per request thread). Any code on that thread can read it.

Authentication
The "who" object. Before authentication it carries credentials (isAuthenticated() == false); after, it carries the principal and authorities.
Principal
The identity. Often a UserDetails (form login / Basic) or a Jwt (resource server). getName() returns the username.
Credentials
The proof (password or token). Erased after a successful login.
GrantedAuthority
One permission as a string, e.g. ROLE_RECRUITER or jobs:write.
Authentication auth = SecurityContextHolder.getContext().getAuthentication();
String name = auth.getName();                              // e.g. "asha@example.com"
Collection<? extends GrantedAuthority> roles = auth.getAuthorities();
boolean loggedIn = auth.isAuthenticated()
        && !(auth instanceof AnonymousAuthenticationToken);

How a username and password is checked

When some filter or your login controller has credentials, it calls the AuthenticationManager. The standard implementation, ProviderManager, asks a list of AuthenticationProviders whether one supports this kind of credential. For username and password the provider is DaoAuthenticationProvider, which uses two collaborators you supply.

  1. DaoAuthenticationProvider calls userDetailsService.loadUserByUsername(name) and receives a UserDetails (name, hashed password, authorities, status flags).
  2. It checks the account flags (enabled, not locked, not expired). A bad flag throws DisabledException, LockedException and so on.
  3. It calls passwordEncoder.matches(rawPassword, storedHash). A mismatch throws BadCredentialsException.
  4. On success it returns a fully authenticated Authentication with authorities.

All exceptions here extend AuthenticationException, and ExceptionTranslationFilter turns them into 401. A missing user also gives BadCredentialsException by default (so attackers cannot tell "unknown email" from "wrong password").

Rule: the SecurityContext is per thread and per request

The context lives in a thread-local. In a stateless app it is empty at the start of every request and filled again by your token filter. Code that starts another thread (@Async, a manual executor) does not automatically see it; Spring offers DelegatingSecurityContextExecutor and MODE_INHERITABLETHREADLOCAL for those rare cases.

Interview angle

"Explain the Spring Security architecture." Filters in front of the DispatcherServlet; FilterChainProxy picks a SecurityFilterChain; an authentication filter builds an Authentication and stores it in the SecurityContextHolder; AuthorizationFilter checks the rules; ExceptionTranslationFilter maps failures to 401/403. Then draw the AuthenticationManager to DaoAuthenticationProvider to UserDetailsService and PasswordEncoder path.

Writing a SecurityFilterChain with the lambda DSL

Declare a SecurityFilterChain bean that sets the URL rules, switches off form login and Basic for an API, makes sessions stateless, and plugs in your authentication; matcher order matters, the first match wins.

In the architecture article you saw that Spring Security is a list of servlet filters. The SecurityFilterChain bean is how you choose and configure those filters. You describe what you want with HttpSecurity, a builder, and call http.build(); the result is the list of filters for one group of URLs.

A complete configuration for a stateless REST API

import static org.springframework.security.config.Customizer.withDefaults;

@Configuration
@EnableWebSecurity
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())
            .cors(withDefaults())
            .sessionManagement(s ->
                    s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .httpBasic(basic -> basic.disable())
            .formLogin(form -> form.disable())
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/jobs/**", "/api/companies/**")
                        .permitAll()
                .requestMatchers("/actuator/health").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .requestMatchers(HttpMethod.POST, "/api/jobs").hasRole("RECRUITER")
                .anyRequest().authenticated());
        return http.build();
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

(Authentication of tokens is added later: one more line in the chain, shown in the JWT articles.) Line by line:

@EnableWebSecurity
Switches on web security. Optional in Spring Boot (auto-configured), but it states the intent.
@EnableMethodSecurity
Allows @PreAuthorize on methods (authorization).
csrf(csrf -> csrf.disable())
Turns off CSRF checks. Correct only for token-in-header APIs (CSRF).
cors(withDefaults())
Uses your CorsConfigurationSource bean (CORS).
sessionCreationPolicy(STATELESS)
Spring Security never creates or uses an HTTP session to store the SecurityContext. Every request must carry its own token.
httpBasic / formLogin disabled
An API has no HTML login page and does not use Basic. Disabling them removes the default login page and the redirect-to-login behaviour (you get a clean 401).
authorizeHttpRequests
The URL rules, evaluated by AuthorizationFilter.
permitAll()
Anyone, including anonymous users.
authenticated()
Any logged-in user.
hasRole("ADMIN")
Needs authority ROLE_ADMIN.
anyRequest().authenticated()
The safety net: everything not listed above needs a login. Always end with it (deny by default).

What the DSL does inside

The "lambda DSL" is the style where every feature gets its own lambda: .csrf(csrf -> ...). Each call configures one configurer, and each configurer adds one or more filters to the chain. So .csrf(...) adds CsrfFilter, .cors(...) adds CorsFilter, .sessionManagement(...) adds session-related filters, and .authorizeHttpRequests(...) adds AuthorizationFilter near the end. A configurer you disable (or never call) adds nothing. When you call http.build(), Spring Security sorts the filters into their fixed order, so the order of your DSL calls does not change the filter order.

At runtime Boot registers one servlet filter, FilterChainProxy (under the name springSecurityFilterChain), which holds all your SecurityFilterChain beans. For each request it picks the first chain whose request matcher matches, and runs only that chain's filters. A simplified view of a typical API chain:

Two other defaults come with the chain. First, HeaderWriterFilter adds security response headers such as X-Content-Type-Options: nosniff and X-Frame-Options: DENY; change them with .headers(h -> ...). Second, the chain needs an AuthenticationManager; Boot builds one from your UserDetailsService and PasswordEncoder beans, or from the JWT decoder when you use the resource server (users from the database).

Plugging in your own authentication filter

A custom filter is placed relative to a known one with addFilterBefore or addFilterAfter. This is the "one more line" used by the custom JWT approach (JWT custom filter).

http.addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);

// or, for the resource server approach, a single line:
http.oauth2ResourceServer(oauth -> oauth.jwt(withDefaults()));

Matcher order matters

Rules are checked from top to bottom and the first matching rule wins. Put specific rules first, general ones last.

Wrong: the general rule hides the specific one

.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/**").authenticated()          // matches everything
    .requestMatchers("/api/auth/**").permitAll()         // never reached
    .anyRequest().denyAll())

Right: specific first

.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/auth/**").permitAll()
    .requestMatchers("/api/**").authenticated()
    .anyRequest().denyAll())

Spring Security even throws an error at startup if a rule after anyRequest() is added (IllegalStateException: Can't configure requestMatchers after anyRequest), because it could never match.

Request matchers

  • requestMatchers("/api/jobs/**"): Ant-style paths. * = one segment, ** = any depth.
  • requestMatchers(HttpMethod.GET, "/api/jobs/**"): path plus HTTP method. Use methods to make reads public and writes protected.
  • requestMatchers("/h2-console/**") and similar for tools. In the old API this was antMatchers / mvcMatchers; both were replaced by requestMatchers in Spring Security 6.

More than one filter chain

You may define several SecurityFilterChain beans for different URL groups, each with @Order and a securityMatcher, for example one stateless chain for /api/** and one session-based chain for an admin web UI. The first chain whose matcher matches the request handles it.

@Bean
@Order(1)
SecurityFilterChain apiChain(HttpSecurity http) throws Exception {
    http.securityMatcher("/api/**")
        .authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .csrf(c -> c.disable());
    return http.build();
}

@Bean
@Order(2)
SecurityFilterChain webChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .formLogin(withDefaults());
    return http.build();
}

The last chain has no securityMatcher, so it matches everything and must come last. If a chain that matches every request comes before another one, the later chain can never run; Spring Security 6 detects this and fails at startup with an UnreachableFilterChainException.

Ignoring static resources

Do not use web.ignoring() for URLs that need security headers; use permitAll() instead, so the filters (and headers) still run. Common Spring Boot static locations are already handled by PathRequest.toStaticResources() if you serve a UI from the same app.

Try it: what the client sees

$ curl -i localhost:8080/api/jobs                     # GET, public
HTTP/1.1 200
$ curl -i -X POST localhost:8080/api/jobs -d '{}'     # needs login
HTTP/1.1 401
$ curl -i -X POST localhost:8080/api/jobs -H "Authorization: Bearer $CANDIDATE" ...
HTTP/1.1 403
$ curl -i localhost:8080/api/unknown-thing            # anyRequest().authenticated()
HTTP/1.1 401

Rule: deny by default

End every authorizeHttpRequests block with anyRequest().authenticated() (or denyAll()), and list public URLs explicitly. A forgotten endpoint is then protected, not exposed.

Conventions

  • Keep the chain in one SecurityConfig class; keep filters and handlers as separate classes and inject them.
  • Expose PasswordEncoder as its own bean; services (registration) need it too.
  • Write one test per rule with MockMvc and @WithMockUser (controller tests). A rule nobody tests breaks silently when someone reorders the lines.

Common mistakes

  • Putting permitAll() for /api/auth/** after a broader rule (see the Wrong example).
  • Using hasRole("ROLE_ADMIN"). Spring adds the prefix itself, so use hasRole("ADMIN") (or hasAuthority("ROLE_ADMIN")).
  • Returning the HttpSecurity without calling http.build().
  • Forgetting that the servlet context-path or a trailing slash can change matching; test your rules (module 5).
  • Disabling CSRF on an app that uses session cookies. That is only right for token-in-header APIs.
  • Calling permitAll() on /actuator/** in production. Expose only health, or secure the rest (Actuator).

Edge case: 403 instead of 401 for missing credentials

If you disable httpBasic and formLogin and add no other authentication mechanism, there is no AuthenticationEntryPoint to say "401, please log in", and Spring Security falls back to a plain 403 for anonymous requests. Fix it by configuring an entry point (JSON errors), or by using the resource server support, which sets one.

More edge cases and startup errors

  • The /error trap. When a controller throws an exception, the servlet container forwards to /error, and in Spring Security 6 the authorization rules also apply to that forward. A real 404 or 500 can then appear as 401 or 403. Add .requestMatchers("/error").permitAll() if you see this.
  • IllegalArgumentException: This method cannot decide whether these patterns are Spring MVC patterns or not appears when a second servlet is registered (for example the H2 console) and you pass a string to requestMatchers. Use PathRequest.toH2Console() for that one.
  • Defining your own SecurityFilterChain makes Boot back off from its default chain (starter defaults): the generated password and default form login are gone.
  • A path with a different case or a trailing slash (/API/jobs) is not matched by /api/jobs; with deny-by-default it is still protected.

Spring Security 6 and 7

Spring Boot 3.x uses Spring Security 6; Boot 4.x uses Spring Security 7. The lambda style shown here is the supported style in both. The older chained style (http.csrf().disable().and()...) was deprecated in 6.x and is removed in 7, and WebSecurityConfigurerAdapter was already removed in Security 6. Write every new configuration in lambda style.

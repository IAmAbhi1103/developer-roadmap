Starters and dependency management (the Boot parent and BOM)

A starter is one dependency that pulls in a whole feature with tested, compatible library versions; the Boot parent POM (a BOM) fixes those versions so you never write them yourself.

Without starters you would list Spring MVC, Jackson, Tomcat, validation and logging separately, and pick versions that work together. A starter is an empty-ish JAR whose only job is to depend on the right libraries. Add spring-boot-starter-web and you get a working web stack in one line.

Starters follow the pattern spring-boot-starter-* for official ones; third-party starters name the other way round (mybatis-spring-boot-starter). Starters are the input; auto-configuration is what turns them into beans (previous article).

Version note: starter names can change between 3.x and 4.x

Boot 4 reorganised some starters and modules. The names above are the long-standing ones; check the names Initializr generates for your Boot version rather than copying from older articles.

No version numbers: the parent and the BOM

Look at the dependency list in a Boot pom.xml: starters have no <version>. The version comes from the parent.

<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.5.0</version>
</parent>

<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-data-jpa</artifactId>   <!-- no version -->
    </dependency>
    <dependency>
        <groupId>org.postgresql</groupId>
        <artifactId>postgresql</artifactId>      <!-- no version: managed too -->
        <scope>runtime</scope>
    </dependency>
</dependencies>

A BOM (bill of materials) is a POM that only lists recommended versions of many libraries (dependencyManagement). spring-boot-starter-parent inherits from spring-boot-dependencies, which is that BOM: it fixes hundreds of versions (Hibernate, Jackson, Tomcat, JUnit, the PostgreSQL driver and more) that were tested together. Upgrading Boot upgrades all of them in one step.

The parent also sets Java compiler defaults, UTF-8 encoding, resource filtering and plugin versions for the Boot Maven plugin.

If your company has its own parent POM

You can only extend one parent. Import the Boot BOM instead:

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-dependencies</artifactId>
            <version>3.5.0</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

In Gradle the Spring Boot plugin plus the io.spring.dependency-management plugin does the same. The Maven build part is in Core Java · Module 8.

Overriding a managed version

Sometimes you need a different version (for example a security fix in a library). Set the property the BOM uses:

<properties>
    <jackson-bom.version>2.18.2</jackson-bom.version>   <!-- illustration only -->
</properties>

Property names are listed in the Boot reference documentation (Dependency Versions appendix). Override only with a reason, because you leave the combination that Boot tested. See what is really on the classpath with ./mvnw dependency:tree.

Removing or swapping a transitive dependency

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <exclusions>
        <exclusion>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-tomcat</artifactId>
        </exclusion>
    </exclusions>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-jetty</artifactId>
</dependency>

Rules

  • Do not mix Boot versions: all spring-boot-* and spring-* artifacts must come from one BOM.
  • Do not write versions for libraries the BOM already manages.
  • Database drivers use runtime scope; test libraries use test.

Conventions

  • Add only the starters you need; every starter adds startup time and auto-configuration.
  • Upgrade Boot by changing one version number, then read the release notes and run the tests.
  • Keep the Initializr link in your README so a new teammate can regenerate a similar project.

Edge cases

  • Two starters can bring two JSON or logging libraries; Boot's exclusions handle the common cases. A Multiple SLF4J bindings warning means one of your own dependencies adds a second logging backend.
  • spring-boot-starter-web and spring-boot-starter-webflux together: Boot chooses Spring MVC. Reactive stack is a different style, rarely needed at the beginning.

Interview: "What is a starter? Why no versions in the pom?"

  • A starter is a dependency descriptor that brings a feature's libraries together. Auto-configuration then configures them.
  • The parent spring-boot-starter-parent (via spring-boot-dependencies) is a BOM that manages tested versions.
  • Override a version with a property; exclude a transitive library with <exclusions>.

The embedded server, executable JAR and DevTools

Boot runs Tomcat inside your application, so one executable JAR starts the whole server with java -jar; change it with server.* properties and use DevTools for automatic restarts while you develop.

Before Boot, you built a WAR and deployed it into a separately installed Tomcat. With an embedded server the server is just a library: SpringApplication.run starts it from main. The application owns its server version and settings, which fits Docker and cloud deployment perfectly: the artifact is the whole runtime.

Tomcat by default, Jetty and Undertow as options

spring-boot-starter-web includes spring-boot-starter-tomcat. You can exchange it, as shown in the starters article. Tomcat is the default choice and what almost all companies use; there is rarely a reason to change it.

Server properties you will use

server:
  port: 8081                       # 0 = pick a random free port (useful in tests)
  servlet:
    context-path: /shop            # all URLs start with /shop
  shutdown: graceful               # finish running requests before stopping
  compression:
    enabled: true                  # gzip JSON responses
  error:
    include-message: never         # do not leak exception text to clients
  tomcat:
    threads:
      max: 200                     # request-handling threads (the default)
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s
PropertyPurpose
server.portThe HTTP port (default 8080)
server.servlet.context-pathA URL prefix for the whole app
server.shutdown=gracefulOn stop signal, refuse new requests and let running ones finish
server.tomcat.threads.maxMaximum worker threads; one thread serves one request at a time
server.ssl.*HTTPS directly in the app (usually a proxy does TLS instead)
server.http2.enabledHTTP/2 (needs HTTPS in browsers)

Each incoming request is handled by one thread from Tomcat's pool; this is why singleton beans must be thread-safe (scopes). Since Java 21 you can switch on virtual threads with spring.threads.virtual.enabled=true in Boot 3.2 and later; read more in Core Java · Module 6.

The executable (fat) JAR

The spring-boot-maven-plugin repackages the normal JAR into one that contains everything:

A plain Java java -jar cannot read JARs inside a JAR, so Boot adds a small launcher that sets up a class loader for BOOT-INF/lib, and then calls your main. You never see this. For Docker, the layered layout (layers.idx) lets an image keep dependencies in one layer and your code in another, so rebuilds are small (DevOps · Module 3).

Spring Boot DevTools

DevTools makes development faster. Add it as an optional development-only dependency:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-devtools</artifactId>
    <scope>runtime</scope>
    <optional>true</optional>
</dependency>
  • Automatic restart: when a class on the classpath changes, DevTools restarts the application. It uses two class loaders (one for unchanging libraries, one for your code), so a restart is much faster than a cold start.
  • LiveReload: a browser extension can refresh the page after a restart (mostly for server-rendered pages).
  • Development defaults: template caching is switched off, and more debug information is shown.
  • Remote restart: possible, but not recommended.

In IntelliJ you must trigger a compile (Ctrl+F9, or enable "build project automatically") for the restart to start, because DevTools reacts to changed class files, not to saved sources. DevTools is automatically disabled when the app runs from a packaged JAR (java -jar), and it is excluded from repackaged JARs by default, so it does not reach production.

Rules

  • Never run DevTools in production; mark it optional or runtime as shown.
  • The embedded server's context-path and port come only from properties of the app; an external server's WAR deployment ignores server.port.
  • Secure real deployments with HTTPS, normally terminated by a reverse proxy or load balancer in front of the app.

Conventions

  • Package as a JAR; use the same JAR in every environment, configured by profile and environment variables.
  • Enable graceful shutdown so a deployment does not cut requests in half.
  • Turn on compression only if no proxy already does it.

Edge cases

  • Port 0 chooses a random port; read it from the local.server.port property in tests (@LocalServerPort).
  • Behind a proxy, set server.forward-headers-strategy=framework or native so redirects and links use the public scheme and host.
  • A WAR build for an external Tomcat is still possible (extend SpringBootServletInitializer, mark Tomcat provided), but it is the legacy route.

Interview: "What is an embedded server? How is a Boot app packaged?"

  • The server (Tomcat) is a library started by main; no separate installation, easier containers, per-app server versions.
  • The Boot Maven plugin builds a fat JAR with BOOT-INF/classes, nested BOOT-INF/lib and a launcher; start it with java -jar.
  • Change the port with server.port; swap the server with exclusions; DevTools gives restart for development only.

Spring AOP and proxies: how @Transactional works, and the self-invocation pitfall

Spring wraps beans in proxy objects that run extra code (transactions, caching, security, your aspects) before and after the real method; calling a method on this bypasses the proxy, so the extra behaviour silently does not happen.

Some concerns cut across many classes: open a transaction, log timing, check a role, cache a result. Writing that in every method is repetitive and hides the business logic. Aspect-oriented programming (AOP) moves such code into one place and applies it to many methods without changing them.

Vocabulary in simple words

Aspect
A class holding the cross-cutting code, for example "log how long a service method takes".
Advice
The code itself, plus when it runs: @Before the method, @After it, @AfterReturning, @AfterThrowing, or @Around (wraps the call and decides whether to proceed).
Join point
A point where advice can run. In Spring AOP it is always a method execution on a bean.
Pointcut
An expression that selects which methods get the advice, such as execution(* com.example.shop.service..*(..)).
Proxy
A stand-in object created by Spring that holds the advice and forwards calls to the real bean (the target).

A small aspect

import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.stereotype.Component;

@Aspect
@Component
public class TimingAspect {

    // every public method of every class in a package named "service"
    @Around("execution(public * com.example.shop..service..*(..))")
    public Object time(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.nanoTime();
        try {
            return pjp.proceed();                     // call the real method
        } finally {
            long ms = (System.nanoTime() - start) / 1_000_000;
            System.out.println(pjp.getSignature().toShortString() + " took " + ms + " ms");
        }
    }
}
OrderService.placeOrder(..) took 12 ms

OrderService has no logging code. Spring noticed that the pointcut matches it, and when the bean was created it gave out a proxy instead of the original object.

How the proxy works

The proxy is created in the "after initialization" step of the bean lifecycle (lifecycle). Everything that injects OrderService receives the proxy. Annotations that work through proxies include @Transactional (Module 3), @Cacheable, @Async, @Retryable and method security such as @PreAuthorize (Module 4).

JDK dynamic proxy vs CGLIB

JDK dynamic proxyCGLIB proxy

Spring Framework itself uses a JDK proxy when the class has an interface; Spring Boot changes the default to CGLIB so injecting the concrete class works. In both cases the proxy sits in front of the real object.

The self-invocation pitfall

A call from outside goes through the proxy. A call from inside the same object goes straight to this, which is the real object, so no advice runs.

@Service
public class OrderService {

    public void checkout(Cart cart) {
        // ... some work ...
        saveOrder(cart);            // really this.saveOrder(cart): NOT via proxy
    }

    @Transactional
    public void saveOrder(Cart cart) {
        // runs WITHOUT a transaction when called from checkout()
    }
}

The same applies to @Cacheable, @Async and @PreAuthorize: they silently do nothing. There is no error, which makes this a famous bug and a favourite interview question. Fixes, best first:

  1. Move the method to another bean, and inject that bean. This is clean and obvious.
  2. Put the annotation on the entry method (checkout) so the whole operation is covered.
  3. Inject the bean into itself (self-injection with @Lazy) or use AopContext.currentProxy() with exposeProxy; these work but are ugly.
  4. Use AspectJ weaving (compile-time or load-time), which changes the bytecode and works for internal calls. Heavy; rarely used.
@Service
public class OrderService {
    private final OrderPersister persister;
    public OrderService(OrderPersister persister) { this.persister = persister; }

    public void checkout(Cart cart) {
        persister.saveOrder(cart);      // goes through persister's proxy
    }
}

@Service
public class OrderPersister {
    @Transactional
    public void saveOrder(Cart cart) { /* in a transaction */ }
}

Other proxy limits

  • Only public methods are advised in the default proxy setup for @Transactional; annotating a private or package-private method has no effect (a protected one may work on newer versions, but do not rely on it).
  • CGLIB cannot override final methods or subclass a final class: advice on them is skipped, or startup fails.
  • Objects you create with new have no proxy. @Transactional on such an object does nothing.
  • With a JDK proxy, a field of the concrete type fails with BeanNotOfRequiredTypeException. Inject interfaces.
  • An exception inside the advice or a proxy that hides the target changes stack traces; the real method appears deeper in the trace.

Rules

  • Proxy-based annotations work only when the call comes from another bean through the container.
  • Only methods of Spring beans can be advised; only method execution, not field access or constructors.
  • You need spring-boot-starter-aop for your own @Aspect classes (annotations from AspectJ).

Conventions

  • Put @Transactional on service methods, not on controllers or repositories' internals.
  • Use aspects for real cross-cutting needs: audit, timing, rate limiting. Do not hide business rules in aspects.
  • Keep pointcuts narrow. A broad one such as execution(* *(..)) slows startup and surprises people.

Mistake: trusting an annotation that is silently skipped

If a "transactional" method does not roll back, or a cache never hits, check the call path first: is it called through another bean, and is the method public? Turn on logging.level.org.springframework.transaction=DEBUG to see transactions begin and end.

Interview: "How does @Transactional work? Why can it fail on a method called from the same class?"

  • Spring creates a proxy (CGLIB by default in Boot, or JDK when an interface is used) around the bean; the proxy begins and commits or rolls back the transaction around the call.
  • Self-invocation uses this, bypassing the proxy, so no transaction (same for @Cacheable, @Async).
  • Fix by moving the method to another bean, restructuring, or AspectJ weaving. Mention public-method and final-class limits.
  • Define aspect, advice, pointcut and join point in one line each.

Application events: publishing and listening inside the app

With ApplicationEventPublisher a bean announces that something happened and any number of @EventListener methods react, so the publisher does not need to know who is listening.

Placing an order should save it, send a confirmation, update stock and write an audit record. If OrderService calls all of these directly, it knows too many classes. With events, OrderService says "an order was placed" and the other parts subscribe independently. This reduces coupling (and helps break the circular dependencies from the errors article).

Publishing and listening

public record OrderPlacedEvent(long orderId, String customerEmail, long amountInPaise) { }
@Service
public class OrderService {

    private final ApplicationEventPublisher publisher;

    public OrderService(ApplicationEventPublisher publisher) {
        this.publisher = publisher;
    }

    public void placeOrder(String email, long amountInPaise) {
        long id = 101;                               // ... save the order ...
        System.out.println("Order saved: " + id);
        publisher.publishEvent(new OrderPlacedEvent(id, email, amountInPaise));
        System.out.println("placeOrder finished");
    }
}
@Component
public class EmailListener {
    @EventListener
    public void onOrderPlaced(OrderPlacedEvent event) {
        System.out.println("Email to " + event.customerEmail());
    }
}

@Component
public class AuditListener {
    @EventListener
    public void onOrderPlaced(OrderPlacedEvent event) {
        System.out.println("Audit: order " + event.orderId());
    }
}
Order saved: 101
Email to ravi@example.com
Audit: order 101
placeOrder finished

Since Spring 4.2 an event can be any object; you do not need to extend ApplicationEvent. Listeners are chosen by the parameter type, so a listener for a parent class also receives subclasses.

Key behaviours

  • Synchronous by default. publishEvent calls every listener in the same thread, one after another, before it returns (as the output above shows). An exception in a listener goes back to the publisher, and a slow listener slows the caller.
  • Same transaction. Because it is the same thread, listeners run inside the publisher's transaction, if one is active.
  • Order. Control it with @Order(1) on the listener method.
  • Conditions. @EventListener(condition = "#event.amountInPaise > 100000") filters with SpEL.
  • Chaining. A listener may return a new event object, which Spring then publishes.

Asynchronous listeners

@SpringBootApplication
@EnableAsync
public class ShopApplication { /* ... */ }

@Component
public class EmailListener {
    @Async
    @EventListener
    public void onOrderPlaced(OrderPlacedEvent event) {
        // runs on a task-executor thread; the caller does not wait
    }
}

An async listener cannot roll back the publisher's transaction, and exceptions do not reach the publisher; handle them inside the listener. @Async is proxy-based, so the self-invocation rule applies (AOP article).

Publishing only after a successful commit

A frequent bug: you publish an "order placed" event inside a transaction, a listener sends the email, and then the transaction rolls back. The customer gets an email for an order that does not exist. Use @TransactionalEventListener, which waits for the transaction phase (the default is AFTER_COMMIT).

@Component
public class EmailListener {
    @TransactionalEventListener              // phase = AFTER_COMMIT by default
    public void onOrderPlaced(OrderPlacedEvent event) {
        // safe to send the email now
    }
}

Without an active transaction this listener is skipped (unless you set fallbackExecution = true). For work that must never be lost even if the app crashes, use a message broker and the outbox pattern from Module 7 instead of in-memory events.

Rules

  • The listener must be a Spring bean; an object created with new receives nothing.
  • A listener method takes one parameter (the event) or none when the type is named in the annotation.
  • Events are in-memory and in one application only; they do not cross services or survive a restart.

Conventions

  • Name events in the past tense: OrderPlacedEvent, UserRegisteredEvent. Make them immutable (records).
  • Use events for side effects (notification, audit, cache refresh), not for the main flow whose result you need.
  • Do not overuse them; a plain method call is easier to read and trace when only one class reacts.

Edge cases

  • An event published while the context is still starting may arrive before some listeners are registered. Use ApplicationReadyEvent for start-up work.
  • Listeners run in a synchronous chain: if the first throws, the later ones never run for that event.
  • If no listener exists, publishEvent does nothing and is not an error.

Interview: "How do Spring events work? Sync or async?"

  • A publisher calls ApplicationEventPublisher.publishEvent; @EventListener methods that match the type receive it.
  • Synchronous in the same thread and transaction by default; add @Async (with @EnableAsync) for async.
  • Use @TransactionalEventListener to run after commit. For cross-service or durable messaging use a broker, not in-app events.

Interview questions — Spring fundamentals

What is the difference between Spring and Spring Boot?

Spring Framework is the core: the IoC container, AOP, MVC, transactions. Spring Boot is a layer on top that removes setup. It adds starters (feature bundles), auto-configuration, an embedded server, an executable JAR, Actuator and sensible defaults. Boot does not replace Spring; the beans are the same, only created for you.

What are IoC and DI, and what problem do they solve?

Without them a class creates its dependencies with new, which makes it tightly coupled and hard to test. With dependency injection the object receives its dependencies (best via the constructor). Inversion of Control means the framework, not your code, creates and wires objects and controls their life. The result is loose coupling, easy mocking and one place to configure and add proxies.

BeanFactory vs ApplicationContext?

BeanFactory is the basic container and creates beans lazily. ApplicationContext extends it with events, Environment/property handling, i18n, resource loading and eager singleton creation, so wiring mistakes fail at startup. Applications always use the ApplicationContext.

@Component vs @Service vs @Repository vs @Controller?

All register a bean through component scanning. @Service and @Repository are specialisations of @Component that mark the layer; @Repository also translates persistence exceptions into DataAccessException. @Controller marks a web handler, and @RestController adds @ResponseBody so return values become JSON.

@Component vs @Bean?

@Component is placed on your own class and found by scanning. @Bean is placed on a method in a @Configuration class and its return value is registered, so it works for third-party classes and for objects needing custom construction logic. With proxyBeanMethods = true a call from one @Bean method to another returns the same singleton.

Why is constructor injection preferred over field injection?

Fields can be final, the object is never half-built, dependencies are visibly required, it needs no reflection, and a unit test can just call new with fakes. A very long constructor also warns you that a class has too many responsibilities. A single constructor needs no @Autowired. Setter injection is for optional dependencies.

Two beans of the same type exist. What happens and how do you fix it?

Startup fails with NoUniqueBeanDefinitionException. Mark the usual bean @Primary, name the wanted bean with @Qualifier("name") at the injection point (it beats @Primary), or inject List<T> / Map<String, T> to receive all of them, as in the strategy pattern.

What is a circular dependency, and how do you handle it?

A needs B and B needs A. With constructor injection neither can be built first, and since Boot 2.6 cycles are rejected by default. Fix the design: extract the shared logic into a third bean, publish an event instead of calling directly, or pass values instead of beans. @Lazy on one parameter or enabling spring.main.allow-circular-references are last resorts that hide the problem.

What are the bean scopes? Is a singleton thread-safe?

Singleton (default, one per container), prototype (new each time), and the web scopes request, session and application. A singleton bean is shared by all request threads, so it is not automatically thread-safe: keep it stateless or use thread-safe state. A prototype injected into a singleton is injected once only; use ObjectProvider to get a fresh one each time.

Explain the bean lifecycle.

Instantiate (constructor), inject dependencies, Aware callbacks, BeanPostProcessor before-init, @PostConstruct, afterPropertiesSet, custom init method, BeanPostProcessor after-init (where AOP proxies are made), then the bean is in use. At shutdown: @PreDestroy, destroy(), custom destroy method. Spring does not call destroy callbacks for prototype beans.

How does externalised configuration work, and what is the precedence?

Boot merges settings from files, environment variables, system properties and command-line arguments. From highest to lowest: command line, environment, profile-specific files, application.yml, defaults. Relaxed binding maps SPRING_DATASOURCE_URL to spring.datasource.url. Secrets come from the environment, not from Git.

@Value vs @ConfigurationProperties?

@Value("${key:default}") injects one value and supports SpEL. @ConfigurationProperties(prefix = "...") binds a group into a typed object (a record is ideal), with relaxed binding, nested structures, type conversion and validation through @Validated. Use it for anything beyond a single flag, so a typo or blank value fails at startup.

What does @SpringBootApplication do, and how does auto-configuration work?

It is @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan. Auto-configuration reads META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports from all JARs; each listed class has conditions (@ConditionalOnClass, @ConditionalOnProperty, @ConditionalOnMissingBean) and only matching classes create beans. If you define your own bean, Boot's default backs off. Debug with --debug; disable with exclude.

Why does @Transactional not work when a method calls another method of the same class?

Spring applies transactions through a proxy around the bean. A call from another bean goes through the proxy; a call on this goes straight to the target and skips the advice. The same happens with @Cacheable and @Async. Fix it by moving the method into another bean, annotating the entry method, or using AspectJ weaving. Also remember that the method must be public and the class non-final for CGLIB.

Cheat sheet — Spring fundamentals

  • Spring vs Boot Spring = container + features; Boot = starters, auto-configuration, embedded server, fat JAR, Actuator
  • Initializr start.spring.io: Maven, Java, latest stable Boot, group/artifact, Jar, Java 21, add starters

  • Scan rule main class package and sub-packages only; a bean outside gives NoSuchBeanDefinitionException
  • Stereotypes @Component generic, @Service logic, @Repository data + exception translation, @RestController JSON

  • Injection constructor (preferred, final fields); setter for optional; avoid field injection
  • Single constructor no @Autowired needed; Lombok @RequiredArgsConstructor writes it

  • Lifecycle constructor → inject → Aware → post-processor → @PostConstruct → init → proxy → use → @PreDestroy

  • Precedence command line > environment > profile files > application.yml > defaults

Practice — Spring fundamentals

  1. First project. Generate a Maven project at start.spring.io with Spring Web and DevTools. Run it with ./mvnw spring-boot:run, then build the JAR and start it with java -jar. Done when: the log shows Tomcat started on 8080 and you can start the JAR with --server.port=9090.
  2. DI by hand, then Spring. In plain Java write NotificationSender, EmailSender, SmsSender and an OrderService that takes the sender in its constructor; wire it in main. Then convert it to Spring beans. Done when: both versions print the same message and you can name which line the container replaced.
  3. Break and fix. Move a @Service to a sibling package and read the failure report; then add a second NotificationSender and cause NoUniqueBeanDefinitionException. Fix with @Primary and then with @Qualifier. Done when: you can explain each report's "Description" and "Action".
  4. Notification app (roadmap exercise). Build an app with NotificationSender, EmailSender, SmsSender, ConsoleSender, and an OrderService. Select the sender by profile (dev → console, prod → SMS) using @Profile, with the activation done through spring.profiles.active. Done when: running with each profile prints from a different sender and a CommandLineRunner places a sample order at startup.
  5. Strategy map. Add three PaymentService beans named upi, card and netbanking, and a router that injects Map<String, PaymentService>. Done when: adding a fourth class needs no change to the router.
  6. Typed configuration. Create app.notification.* settings (sender name, retries, timeout, allowed channels) as a @ConfigurationProperties record with @Validated. Supply the secret API key from an environment variable. Done when: a blank key stops startup with a clear binding error, and --app.notification.max-retries=5 on the command line overrides the file.
  7. Scopes and lifecycle. Create a singleton service with a prototype dependency; show the bug, then fix it with ObjectProvider. Add a bean printing each lifecycle step. Done when: the console shows the exact order from the lifecycle diagram, with @PreDestroy at shutdown.
  8. See auto-configuration. Run with --debug and find one positive and one negative match. Define your own ObjectMapper bean (or Clock) and prove Boot's default backs off by listing bean names. Then exclude DataSourceAutoConfiguration in an app that has a JDBC starter but no database. Done when: the app starts and you can explain each condition that decided the result.
  9. Self-invocation. Write a timing aspect (add spring-boot-starter-aop) on a service. Call the advised method from outside and from another method of the same class, and compare the output. Fix it with a second bean. Done when: you can show, with logs, that the internal call skips the aspect, and that the fixed version runs it.
  10. Events. Replace the direct email and audit calls in OrderService by an OrderPlacedEvent with two listeners. Make one async and one @TransactionalEventListener. Done when: you can show which listener runs in which thread and that a rolled-back order sends no email.

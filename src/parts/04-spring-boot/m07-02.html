Service discovery and centralized configuration

Services find each other by name instead of fixed addresses (client-side discovery with Eureka, or DNS in Kubernetes), and shared configuration comes from a config server, environment variables, ConfigMaps or Vault instead of files inside each JAR.

The problem: addresses change

In the monolith you called a method. Between services you need a URL. But service instances start and stop all the time (autoscaling, deployments, crashes), and their IP addresses change. Hard-coding http://10.0.4.17:8081 breaks within a day. Service discovery solves it: services register under a logical name (job-service), and callers look the name up to get the current healthy instances.

Client-side discovery: Eureka

Eureka (from Netflix, wrapped by Spring Cloud) is a registry server. Each service instance registers itself at startup, sends heartbeats, and unregisters on shutdown. A caller asks Eureka for the instances of job-service, picks one (client-side load balancing), and calls it directly.

@SpringBootApplication
@EnableEurekaServer
public class DiscoveryServerApplication {
    public static void main(String[] args) { SpringApplication.run(DiscoveryServerApplication.class, args); }
}
server:
  port: 8761
eureka:
  client:
    register-with-eureka: false        # the registry itself does not register
    fetch-registry: false
spring:
  application:
    name: job-service                  # the logical name in the registry
eureka:
  client:
    service-url:
      defaultZone: http://discovery:8761/eureka
  instance:
    prefer-ip-address: true

With Spring Cloud LoadBalancer on the classpath, a client built from a @LoadBalanced builder understands logical names:

@Configuration
class ClientConfig {
    @Bean
    @LoadBalanced                                   // resolve "job-service" via discovery
    RestClient.Builder loadBalancedBuilder() {
        return RestClient.builder();
    }
}

@Service
class JobLookup {
    private final RestClient client;
    JobLookup(@LoadBalanced RestClient.Builder builder) {
        this.client = builder.baseUrl("http://job-service").build();   // not a real DNS name
    }
    JobDto get(Long id) {
        return client.get().uri("/api/jobs/{id}", id).retrieve().body(JobDto.class);
    }
}

Gateway routes use the same idea: uri: lb://job-service. Eureka tolerates failures by design (it favours availability): the registry may briefly list a dead instance until its lease expires, so callers still need timeouts and retries. Remember to run more than one registry in production.

Server-side discovery: Kubernetes and Docker DNS

On Kubernetes (or Docker Compose) the platform does discovery for you. A Kubernetes Service gets a stable DNS name (job-service, or job-service.default.svc.cluster.local) and a virtual IP; the platform spreads traffic across the healthy pods behind it. Your code simply calls http://job-service:8081. There is no registry to run and no client library, which is why many teams skip Eureka on Kubernetes (DevOps · Module 5). Docker Compose gives the same by service name on a shared network (Compose).

Client-side (Eureka)Server-side / platform DNS

Centralized configuration

With 20 services and 3 environments, copying application.yml files around is a mess; changing a database password means rebuilding images. Principles: keep the build the same everywhere and inject configuration from outside (12-factor). Choices:

  • Environment variables: the simplest. Boot's relaxed binding reads SPRING_DATASOURCE_URL. Works with Docker, Compose and Kubernetes. Hard to manage for hundreds of values.
  • Kubernetes ConfigMaps and Secrets: mounted as environment variables or files. ConfigMaps for plain settings, Secrets for passwords (base64-encoded, so also protect them with RBAC and consider encryption at rest or an external secrets operator).
  • Spring Cloud Config Server: a Spring Boot app that serves configuration files stored in a Git repository over HTTP; clients fetch at startup. Gives history and review (Git), per-service and per-profile files, and optional refresh.
  • HashiCorp Vault / cloud secret managers (AWS Secrets Manager, Azure Key Vault) for secrets: access control, auditing, rotation.
@SpringBootApplication
@EnableConfigServer
public class ConfigServerApplication {
    public static void main(String[] args) { SpringApplication.run(ConfigServerApplication.class, args); }
}
server:
  port: 8888
spring:
  cloud:
    config:
      server:
        git:
          uri: https://github.com/example-org/jobs-config    # files: job-service.yml, job-service-prod.yml
          default-label: main
spring:
  application:
    name: job-service                                  # selects job-service*.yml in the repo
  config:
    import: "optional:configserver:http://config-server:8888"
  profiles:
    active: prod

The client merges the fetched properties with its own, with the usual precedence rules (environment variables and command-line arguments still win). Changing a value at runtime without restart is possible with @RefreshScope and the Actuator refresh endpoint (or Spring Cloud Bus), but many teams prefer to redeploy, which is simpler to reason about. Never store plain-text secrets in the config repository; use encryption support or a vault.

Practical advice

For Project 4 and for most real teams on Kubernetes: environment variables + ConfigMaps + Secrets, no Eureka, no Config Server. Learn Eureka and Config Server so you can explain them and maintain older Spring Cloud systems, but do not add them just because the tutorial does.

OpenFeign vs HTTP service clients

OpenFeign (spring-cloud-starter-openfeign) is a declarative HTTP client from Spring Cloud: you write an interface with @FeignClient(name = "job-service") and Spring Cloud-style mapping annotations, and it creates the client, integrated with discovery and load balancing. It is common in existing microservice code. The newer Spring-native alternative is the @HttpExchange interface from module 6, which needs no extra Spring Cloud library and works with a @LoadBalanced builder as well.

@FeignClient(name = "job-service")                  // logical name, resolved by discovery
public interface JobClient {
    @GetMapping("/api/jobs/{id}")
    JobDto byId(@PathVariable("id") Long id);
}
// @EnableFeignClients on a configuration class turns this on

Common mistakes

  • Hard-coded localhost URLs that work on a laptop and fail in Docker (each container has its own localhost).
  • A config server as a single point of failure with no optional: import or retry.
  • Secrets in the config Git repository, or in an image layer.
  • Starting services in an order that requires the registry to be up, instead of retrying.

Interview angle

"What is service discovery and why?" Dynamic addresses; registry plus load balancing. "Client-side vs server-side discovery?" Eureka vs Kubernetes Service. "How do you manage configuration and secrets across environments?" Same artifact, external config, ConfigMaps/Secrets/Vault or a Config Server backed by Git. "Feign vs RestClient?" Declarative Spring Cloud client vs Spring's own client and HTTP interfaces.

Resilience4j: timeouts, retries, circuit breaker, bulkhead and rate limiter

In a distributed system, calls fail; protect each remote call with a timeout first, then a retry (for idempotent calls only, with exponential backoff and jitter), a circuit breaker that stops calling a failing service, and a bulkhead that limits concurrency, all with a sensible fallback.

Why: failures spread

Suppose the application service calls the payment service for every request, and payments become slow (10 seconds per call). Each request now holds a thread for 10 seconds; soon all of the application service's threads are stuck waiting; it stops answering; services that call it start to hang. One slow dependency has taken down the whole system. This is a cascading failure. Resilience patterns stop it by failing fast, limiting damage and giving the failing service room to recover.

Resilience4j is the standard lightweight Java library for these patterns (it replaced Netflix Hystrix, which is retired). It integrates with Spring Boot through annotations and YAML configuration.

The patterns

PatternWhat it doesAnnotation
Time limiter / timeoutStops waiting after a set time@TimeLimiter
RetryTries again after a failure, with waiting between attempts@Retry
Circuit breakerAfter too many failures, rejects calls immediately for a while@CircuitBreaker
BulkheadLimits concurrent calls to one dependency (like watertight ship compartments)@Bulkhead
Rate limiterLimits calls per time period to a dependency@RateLimiter
FallbackA substitute result when the call failsfallbackMethod

Setup

</dependency>

Add the version of Resilience4j that matches your Boot version (use the project's BOM or the version in its release notes). The annotations are AOP proxies like @Transactional, so the same rules apply: public methods, called from another bean, no self-invocation (module 1).

Version note

The artifact resilience4j-spring-boot3 targets Boot 3.x. For Boot 4, check the Resilience4j release notes for the artifact and version that support it. Spring Framework 7 also ships basic resilience features in core (@Retryable and @ConcurrencyLimit, switched on with @EnableResilientMethods), which cover simple retry and concurrency limiting without an extra library; circuit breakers, bulkheads and time limiters still come from Resilience4j.

Why timeouts come first

Every other pattern needs the call to end. A retry cannot happen and a circuit breaker cannot count a failure while the call waits for ever. So always set the client's connect and read timeouts (module 6), and keep them shorter than the caller's own timeout: if your API promises an answer in 3 seconds, the sum of timeouts and retries inside it must fit in 3 seconds. @TimeLimiter adds a time limit for an asynchronous call, but it works on CompletableFuture return types, which is why a client-level timeout is usually the first line of defence.

Circuit breaker

It works like the electrical one in your house. In normal state calls go through. If too many calls fail, the breaker "trips" and further calls fail instantly without touching the broken service. After a pause it lets a few test calls through; if they succeed, it closes again.

  • CLOSED: calls pass; the breaker records successes and failures in a sliding window (last N calls, or last N seconds).
  • OPEN: calls are rejected at once with CallNotPermittedException (and your fallback runs). The failing service gets time to recover, and your threads are free.
  • HALF_OPEN: after waitDurationInOpenState, a limited number of probe calls are allowed. Enough successes close the breaker; failures reopen it.

A call counts as failed when it throws an exception (configurable which ones) or when it is slow (above slowCallDurationThreshold). Business exceptions such as "payment declined" or a 404 should usually not count; list them in ignoreExceptions.

Configuration in YAML

resilience4j:
  circuitbreaker:
    instances:
      paymentService:
        slidingWindowType: COUNT_BASED
        slidingWindowSize: 20                    # judge the last 20 calls
        minimumNumberOfCalls: 10                 # do not decide before 10 calls
        failureRateThreshold: 50                 # open at 50% failures
        slowCallDurationThreshold: 2s
        slowCallRateThreshold: 80
        waitDurationInOpenState: 15s
        permittedNumberOfCallsInHalfOpenState: 3
        automaticTransitionFromOpenToHalfOpenEnabled: true
        registerHealthIndicator: true
        ignoreExceptions:
          - com.example.jobs.payment.PaymentDeclinedException
  retry:
    instances:
      paymentService:
        maxAttempts: 3                           # first call + 2 retries
        waitDuration: 500ms
        enableExponentialBackoff: true
        exponentialBackoffMultiplier: 2          # 500 ms, 1 s, 2 s ...
        enableRandomizedWait: true               # jitter

          - java.io.IOException

          - com.example.jobs.payment.PaymentDeclinedException

Using the annotations with a fallback

@Service
public class PaymentGateway {

    private static final Logger log = LoggerFactory.getLogger(PaymentGateway.class);
    private final RestClient client;

    public PaymentGateway(@Qualifier("paymentRestClient") RestClient client) { this.client = client; }

    @CircuitBreaker(name = "paymentService", fallbackMethod = "chargeFallback")
    @Retry(name = "paymentService")
    @Bulkhead(name = "paymentService")
    public PaymentResult charge(PaymentRequest request) {
        return client.post().uri("/payments")
                .header("Idempotency-Key", request.idempotencyKey())     // makes retry safe
                .body(request).retrieve().body(PaymentResult.class);
    }

    // same parameters + a Throwable (or a specific exception type) as the last one
    private PaymentResult chargeFallback(PaymentRequest request, Throwable cause) {
        log.warn("Payment service unavailable for order {}: {}", request.orderId(),
                cause.toString());
        return PaymentResult.pending(request.orderId());     // accept the order, charge later
    }
}
  • The fallback method must be in the same class, with the same parameters plus an exception parameter, and the same return type. You can have several fallbacks, one per exception type; the most specific wins.
  • Order of the aspects (outermost first): Retry, CircuitBreaker, RateLimiter, TimeLimiter, Bulkhead. So a retry wraps the circuit breaker: each retry attempt is recorded by the breaker, and when the breaker is open, the retry sees CallNotPermittedException, which you should list in ignoreExceptions of the retry to avoid hammering.

Retries: only when safe

  • Retry only idempotent operations (GET, PUT, DELETE, or a POST with an idempotency key). Retrying "charge 500 rupees" without protection can charge twice, because the first request may have succeeded and only the response got lost.
  • Retry only transient errors: timeouts, connection refused, 502/503/504. Never retry 400, 401, 403, 404 or a validation error; they will fail again.
  • Exponential backoff (wait 0.5 s, 1 s, 2 s...) gives the service room to recover. Jitter (random variation) stops all clients retrying at the same instant, which would create a retry storm.
  • Keep maxAttempts small (2 or 3). Retries multiply load: 3 attempts across 3 layers of services is 27 calls.
  • Use a total time budget; a retry loop that takes longer than the user waits is useless.

Fallbacks that make sense

  • Cached or default data: show the last known company logo, or an empty recommendation list.
  • Degraded mode: accept the order as "payment pending", queue it, charge later.
  • A clear error (503 with a message and Retry-After) is also a valid fallback. For money, security and consistency-critical operations, a wrong guess is worse than failing: do not invent "payment succeeded".
  • Do not hide failures: log and count fallbacks.

Bulkhead and rate limiter

A bulkhead reserves a limited capacity for each dependency: with maxConcurrentCalls: 10 for payments, at most ten threads can be busy with payments, so a slow payment service cannot use all your Tomcat threads, and image resizing still works. It throws BulkheadFullException when full. The semaphore type (the default) limits concurrent calls on the caller's thread; a thread-pool type isolates calls on a separate pool (for CompletableFuture methods). A rate limiter here protects a dependency with a quota (for example an SMS provider that allows 50 requests per second); it is the outgoing cousin of the incoming rate limits from module 6.

Observing it

With Actuator, /actuator/circuitbreakers lists breakers and their states, /actuator/circuitbreakerevents shows the recent events (success, error, state transition), and with registerHealthIndicator the health endpoint reports breakers. Resilience4j publishes Micrometer metrics (resilience4j_circuitbreaker_state, resilience4j_circuitbreaker_calls and others) for Prometheus. Alert on "breaker open for more than a few minutes" (Micrometer).

Rules

  • Timeout on every remote call. Always.
  • Retry only idempotent, transient failures, with backoff and jitter and a small limit.
  • Do not count business errors as circuit-breaker failures.
  • The total time of all attempts must fit within your own deadline.

Common mistakes

  • Annotations that do nothing: self-invocation, a missing AOP starter, a private method.
  • Retry on a POST that is not idempotent.
  • Fixed-delay retries with no jitter from hundreds of clients.
  • A fallback that returns fake success, hiding a real outage.
  • No minimumNumberOfCalls: one failure out of one call is "100% failure rate" and opens the breaker.

Exceptions you will see

  • CallNotPermittedException: breaker is OPEN.
  • BulkheadFullException: too many concurrent calls.
  • RequestNotPermitted: rate limiter quota used.
  • TimeoutException: from the time limiter.
  • NoFallbackAvailableException: no matching fallback method signature.

Interview angle

"Explain the circuit breaker." Three states, failure-rate threshold, wait duration, half-open probes, fail fast and recover. "Retry and circuit breaker together?" Order, idempotency, backoff with jitter, ignore CallNotPermittedException. "What is a cascading failure and how do you prevent it?" Timeouts, bulkheads, circuit breakers, fallbacks. "What is a good fallback?" A degraded but honest answer. "Why timeouts first?" Nothing else works while calls hang.

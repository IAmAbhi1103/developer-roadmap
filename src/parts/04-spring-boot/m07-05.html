Running several services together with Docker Compose

Docker Compose describes all your containers (services, databases, broker, cache) in one compose.yaml; use healthchecks with depends_on conditions so services start in a working order, a shared network so they reach each other by service name, and environment variables for configuration.

What and why

A microservice system is many processes. Starting PostgreSQL, Kafka, Redis and three Spring Boot applications by hand with long docker run commands is slow and error-prone. Docker Compose lets you write the whole setup once in compose.yaml and start it with docker compose up. It is the standard tool for local development and for simple single-host deployments. (Docker basics, images and Dockerfiles: DevOps · Module 3; Kubernetes replaces Compose for large production systems.)

Compose creates a private network for the project. Containers reach each other by service name as hostname: from application-service, the database is simply jobs-db:5432 and Kafka is kafka:9092. localhost inside a container means that container itself, a very common mistake.

A complete compose.yaml

Two Spring Boot services (jobs and notifications), each with its own PostgreSQL (database per service), plus Kafka and Redis:

name: jobs-platform

services:
  jobs-db:
    image: postgres:17
    environment:
      POSTGRES_DB: jobs
      POSTGRES_USER: jobs
      POSTGRES_PASSWORD: ${JOBS_DB_PASSWORD:?set JOBS_DB_PASSWORD in .env}
    volumes:
      - jobs-db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U jobs -d jobs"]
      interval: 5s
      timeout: 3s
      retries: 10
    networks: [backend]

  notify-db:
    image: postgres:17
    environment:
      POSTGRES_DB: notify
      POSTGRES_USER: notify
      POSTGRES_PASSWORD: ${NOTIFY_DB_PASSWORD:?set NOTIFY_DB_PASSWORD in .env}
    volumes:
      - notify-db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U notify -d notify"]
      interval: 5s
      timeout: 3s
      retries: 10
    networks: [backend]

  redis:
    image: redis:7
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10
    networks: [backend]

  kafka:
    image: apache/kafka:3.9.0
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
      KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS: 0
    healthcheck:
      test: ["CMD-SHELL", "/opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list"]
      interval: 10s
      timeout: 10s
      retries: 10
      start_period: 20s
    networks: [backend]

  jobs-service:
    build: ./jobs-service                       # folder with its Dockerfile
    ports:
      - "8081:8080"                             # host:container
    environment:
      SPRING_PROFILES_ACTIVE: docker
      SPRING_DATASOURCE_URL: jdbc:postgresql://jobs-db:5432/jobs
      SPRING_DATASOURCE_USERNAME: jobs
      SPRING_DATASOURCE_PASSWORD: ${JOBS_DB_PASSWORD}
      SPRING_DATA_REDIS_HOST: redis
      SPRING_KAFKA_BOOTSTRAP_SERVERS: kafka:9092
      MANAGEMENT_TRACING_SAMPLING_PROBABILITY: "1.0"
    depends_on:
      jobs-db:
        condition: service_healthy
      redis:
        condition: service_healthy
      kafka:
        condition: service_healthy
    healthcheck:
      # needs curl inside the image; or use a tiny Java/wget check
      test: ["CMD-SHELL", "curl -fs http://localhost:8080/actuator/health/readiness || exit 1"]
      interval: 10s
      timeout: 3s
      retries: 10
      start_period: 40s
    restart: unless-stopped
    networks: [backend]

  notification-service:
    build: ./notification-service
    ports:
      - "8082:8080"
    environment:
      SPRING_PROFILES_ACTIVE: docker
      SPRING_DATASOURCE_URL: jdbc:postgresql://notify-db:5432/notify
      SPRING_DATASOURCE_USERNAME: notify
      SPRING_DATASOURCE_PASSWORD: ${NOTIFY_DB_PASSWORD}
      SPRING_KAFKA_BOOTSTRAP_SERVERS: kafka:9092
      SPRING_MAIL_HOST: mailpit
      SPRING_MAIL_PORT: "1025"
    depends_on:
      notify-db:
        condition: service_healthy
      kafka:
        condition: service_healthy
    restart: unless-stopped
    networks: [backend]

  mailpit:
    image: axllent/mailpit
    ports:
      - "8025:8025"                             # open the mail UI on the host
    networks: [backend]

volumes:
  jobs-db-data:
  notify-db-data:

networks:
  backend:

Reading the file

  • depends_on with condition: service_healthy makes Compose wait until the dependency's healthcheck passes. A plain depends_on: [kafka] only waits until the container has started, which is not the same as "ready to accept connections", the usual reason for startup crashes.
  • Healthchecks are commands that Docker runs repeatedly; the container becomes healthy after one succeeds. start_period gives slow starters (Spring Boot, Kafka) time before failures count. Your services can reuse the Actuator readiness endpoint (Actuator); the image needs a tool such as curl to call it.
  • Environment variables override application.yml via relaxed binding: SPRING_DATASOURCE_URL becomes spring.datasource.url, SPRING_KAFKA_BOOTSTRAP_SERVERS becomes spring.kafka.bootstrap-servers. Hostnames are service names (jobs-db, kafka, redis).
  • ${VAR} and .env: Compose reads a .env file next to compose.yaml for substitutions. ${VAR:?message} stops with an error if the variable is missing. Add .env to .gitignore; commit a .env.example instead.
  • volumes (named volumes) keep database files when containers are recreated. docker compose down -v deletes them.
  • networks: by default all services share one network anyway; naming networks lets you separate, for example, a frontend network (gateway, UI) from a backend network (databases not reachable from outside).
  • ports publish a container port to the host. Do not publish databases and Kafka in anything but local development; services on the network reach them without publishing.
  • Kafka needs an advertised listener that clients can reach: kafka:9092 works for other containers. For an application running on your host (outside Docker), you would add a second listener on a host-visible address such as localhost:9094.

A Dockerfile for a Spring Boot service

FROM eclipse-temurin:21-jdk AS build
WORKDIR /workspace
COPY . .
RUN ./mvnw -q -DskipTests package

FROM eclipse-temurin:21-jre
RUN useradd --system --create-home app
USER app
WORKDIR /app
COPY --from=build /workspace/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

The multi-stage build keeps the build tools out of the final image, and the non-root user is a basic security measure. Spring Boot can also build an image without a Dockerfile (./mvnw spring-boot:build-image, using buildpacks).

Everyday commands

$ docker compose up -d --build        # build images and start everything in the background
$ docker compose ps                   # status and health of each service
$ docker compose logs -f jobs-service # follow one service's logs
$ docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
      --bootstrap-server localhost:9092 --list
$ docker compose stop notification-service   # simulate an outage: do events queue up?
$ docker compose up -d notification-service  # bring it back: does it catch up?
$ docker compose down                 # stop and remove containers (keeps volumes)
$ docker compose down -v              # also delete volumes (all data!)

The "stop a service and restart it" experiment is the best way to see the value of Kafka buffering and of timeouts and circuit breakers in the other services.

Spring Boot's Docker Compose support for development

While developing, you usually run the application from your IDE and only want the infrastructure (databases, Kafka, Redis) in Docker. Spring Boot 3.1+ can manage this for you. Add the dependency:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-docker-compose</artifactId>
    <scope>runtime</scope>
    <optional>true</optional>
</dependency>

Put a compose.yaml with only the infrastructure services in the project root. When you start the application, Boot runs docker compose up, waits for the containers, and configures the connections automatically (datasource URL, Redis host, Kafka bootstrap server, the mapped random ports), so you write no connection properties for local development. On shutdown it stops the containers. You control it with spring.docker.compose.lifecycle-management (start-and-stop, start-only, none) and spring.docker.compose.file. The same idea with Testcontainers and @ServiceConnection is used for tests (module 5). Keep the full multi-service file above for running the whole system.

Common mistakes

  • localhost in SPRING_DATASOURCE_URL inside a container: connection refused. Use the service name.
  • Plain depends_on and a race condition: the app starts before the database accepts connections (or before Kafka is ready) and exits.
  • Committing secrets in compose.yaml or .env.
  • Publishing database and broker ports on a server.
  • Forgetting that docker compose down -v deletes the data volume.
  • One shared database for all services: it works, but it breaks the main microservice rule.

Tip

Add Prometheus, Grafana and Zipkin (or Grafana's all-in-one grafana/otel-lgtm image) as extra Compose services, point your services at them with environment variables, and your laptop becomes a complete observability lab (DevOps · Module 6).

Interview angle

"What is Docker Compose for?" Define and run multi-container applications locally. "How do containers find each other?" Service-name DNS on the Compose network. "How do you make a service wait for the database?" Healthcheck plus depends_on: condition: service_healthy, and application-level retries. "Compose vs Kubernetes?" Single host and development versus orchestration, scaling and self-healing across a cluster.

Interview questions — Microservices and messaging

Monolith vs modular monolith vs microservices: how do you choose?

A monolith deploys as one unit and is simplest; a modular monolith is the same deployment with strict module boundaries; microservices are independently deployable services with their own data. Microservices give independent deployment and scaling for many teams, but cost network failures, distributed data, observability and DevOps effort. Start with a (modular) monolith, and extract services when there is a concrete need such as team independence or different scaling.

What is a distributed monolith?

A system split into services that are still tightly coupled: they share a database, must be deployed together, or call each other in long synchronous chains. It has all the costs of microservices and none of the benefits. Avoid it with clear business boundaries, database per service, and asynchronous events between services.

How do you decide service boundaries, and what does "database per service" mean for queries and transactions?

Use business capabilities and bounded contexts, with one team owning each service. Each service is the only owner of its data, so there are no cross-service joins: you use API composition or a local copy fed by events. Cross-service transactions become sagas with compensating actions and eventual consistency.

What does an API gateway do, and what is a route in Spring Cloud Gateway?

It is the single entry point that routes requests to services and handles authentication, rate limiting, CORS and similar cross-cutting concerns. A route has an id, a destination URI, predicates that decide whether it matches (Path, Method, Header...) and filters that modify the request or response (StripPrefix, RewritePath, RequestRateLimiter, CircuitBreaker). The gateway is reactive (WebFlux/Netty), so avoid blocking calls in it.

How do services find each other, and how is configuration managed across environments?

With client-side discovery (Eureka registry plus load balancing, lb://service-name) or, more commonly today, platform DNS such as Kubernetes Services or Compose service names. Configuration is kept outside the artifact: environment variables, ConfigMaps and Secrets, a Spring Cloud Config Server backed by Git, and a vault for secrets. The same image runs in every environment.

Explain the circuit breaker pattern and its states.

It protects a caller from a failing dependency. In CLOSED state calls pass and failures are counted in a sliding window. When the failure (or slow-call) rate exceeds the threshold, it moves to OPEN and rejects calls immediately, so threads are not blocked and the dependency can recover. After a wait time it becomes HALF_OPEN and allows a few probe calls; success closes it, failure reopens it. Business errors should not count as failures.

How do you configure retries safely?

Retry only idempotent operations and transient errors (timeouts, 503), never 4xx or validation errors. Use few attempts with exponential backoff and jitter, and keep the total time inside your own deadline. For non-idempotent calls like payments, pass an idempotency key. Put timeouts first, since a retry needs the earlier call to end.

Why must every remote call have a timeout, and what is a cascading failure?

Without a timeout, a slow dependency makes threads wait indefinitely; the thread pool fills, the service stops responding, and its callers start hanging too. That chain reaction is a cascading failure. Timeouts, bulkheads (limiting concurrency per dependency), circuit breakers and fallbacks contain the damage.

Kafka: what are topics, partitions, offsets and consumer groups?

A topic is a named stream split into partitions; each partition is an ordered append-only log, and each record has an offset. Records with the same key go to the same partition, so order is guaranteed per key only. A consumer group shares a topic: each partition is read by one consumer in the group, so parallelism is limited by the partition count, while different groups each receive all records. Messages are retained for a set period, so consumers can replay.

Kafka vs RabbitMQ: when would you pick each?

Kafka is a distributed log with high throughput, retention and replay, good for event streaming, many independent consumers and data pipelines. RabbitMQ is a broker with flexible routing (direct, topic, fanout exchanges), per-message acknowledgement and dead-letter exchanges, good for task queues and work distribution. RabbitMQ deletes a message after the ack; Kafka keeps it until retention ends.

What delivery guarantees exist, and how do you achieve effectively-once processing?

At-most-once can lose messages, at-least-once can duplicate them, and true exactly-once is only achievable inside controlled boundaries. In practice you use at-least-once delivery (acks after processing, producer retries with idempotence) together with idempotent consumers that record processed event ids in the same transaction as their side effect, or use naturally idempotent operations.

What is the outbox pattern and what problem does it solve?

It solves the dual-write problem: you cannot atomically update your database and publish to a broker. The service writes the event into an outbox table in the same database transaction as the business change. A relay (a polling job or change data capture such as Debezium) publishes outbox rows to the broker and marks them sent. Delivery is at-least-once, so consumers must be idempotent.

How do you handle a message that keeps failing in a Kafka listener?

Configure a DefaultErrorHandler with a back-off (for example exponential, 4 attempts) and a DeadLetterPublishingRecoverer that sends the record to a dead-letter topic. Mark non-retryable exceptions (bad data) so they go straight to the DLT, wrap the deserializer in ErrorHandlingDeserializer to survive poison pills, and alert on the DLT and consumer lag. Alternatively use @RetryableTopic for non-blocking retries.

How does distributed tracing work in a Spring Boot system?

Each request gets a trace id; each operation is a span with its own id and a parent. The trace context travels to the next service in the W3C traceparent header (or message headers). Micrometer Tracing with an OpenTelemetry or Brave bridge creates spans for HTTP and messaging automatically, an exporter sends them to Zipkin, Jaeger or Tempo, and sampling controls the volume. The trace id is also added to the logs so you can jump from a trace to all log lines of the request.

How would you run a multi-service system locally, and how do containers wait for each other?

Docker Compose: one compose.yaml with the services, databases, Kafka and Redis on a shared network where service names are hostnames. Each infrastructure container has a healthcheck, and application services use depends_on with condition: service_healthy. Configuration is passed through environment variables. For development, Boot's spring-boot-docker-compose module can start the infrastructure for you and configure connections.

Cheat sheet — Microservices and messaging

  • Modular monolith first one deployable, strict module boundaries; extract services when team or scaling needs prove it
  • Distributed monolith services that share a DB or must deploy together: worst of both worlds
  • Boundaries business capabilities / bounded contexts; one owner, one database per service; no cross-service joins
  • Sync vs async REST/gRPC when you need the answer now; events for facts that happened; keep call chains short
  • Sagas local transactions + compensations instead of distributed ACID; eventual consistency
  • API gateway routing, auth, rate limit, CORS; Spring Cloud Gateway = routes (id, uri, predicates, filters), reactive, no business logic
  • Gateway YAML predicates: - Path=/api/jobs/**, filters: - StripPrefix=1, uri: lb://job-service
  • Discovery Eureka (client-side, @EnableEurekaServer, @LoadBalanced) or Kubernetes / Compose DNS by service name
  • Config env vars, ConfigMaps/Secrets, Spring Cloud Config Server (spring.config.import=configserver:), Vault for secrets
  • Feign vs HTTP interfaces @FeignClient (Spring Cloud) vs @HttpExchange (Spring native)
  • Timeouts first connect + read timeouts on every call; nothing else works without them
  • Retry idempotent + transient only; exponential backoff + jitter; 2 to 3 attempts
  • Circuit breaker CLOSED, OPEN (fail fast), HALF_OPEN (probes); @CircuitBreaker(name, fallbackMethod); ignore business exceptions
  • Bulkhead / rate limiter / time limiter limit concurrency / calls per period / wait time per dependency
  • Resilience4j order Retry, CircuitBreaker, RateLimiter, TimeLimiter, Bulkhead (outermost first); needs AOP starter; see /actuator/circuitbreakers
  • Queue vs topic one consumer gets each message vs every subscriber group gets it
  • Kafka topic, partitions (ordering + parallelism unit), offset, key, consumer group, replication, retention, KRaft
  • Spring Kafka KafkaTemplate.send(topic, key, value) (async), @KafkaListener(topics, groupId), ErrorHandlingDeserializer, spring.json.trusted.packages
  • Kafka errors DefaultErrorHandler + back-off + DeadLetterPublishingRecoverer (topic.DLT); watch consumer lag
  • RabbitMQ producer to exchange (direct/topic/fanout) to queues via bindings + routing key; ack/nack; DLX; RabbitTemplate, @RabbitListener
  • Kafka vs RabbitMQ log with replay and huge throughput vs smart routing and task queues
  • Delivery at-most-once (loss), at-least-once (duplicates), exactly-once (only within boundaries); use at-least-once + idempotent consumer
  • Idempotent consumer unique event id stored in the same transaction as the effect; or upsert / set semantics
  • Outbox event row saved in the same DB transaction, relay or CDC publishes later; fixes the dual-write problem
  • Tracing trace id + span id, W3C traceparent, Micrometer Tracing bridge (OTel/Brave) + exporter; management.tracing.sampling.probability; build clients from injected builders
  • Compose healthcheck + depends_on: condition: service_healthy; service names as hosts; env vars override Spring properties; down -v deletes data

Practice — Microservices and messaging

  1. Draw the boundaries (easy). For the job portal, write down the services you would extract, what data each owns, and which calls are synchronous and which are events. Compare it with a modular-monolith package layout. Done when you can justify each boundary in one sentence and have no shared tables.
  2. Gateway (easy). Create a Spring Cloud Gateway project that routes /api/jobs/** and /api/applications/** to two local services, strips a prefix, adds a header and handles CORS. Done when the frontend calls only the gateway port and both routes work.
  3. HTTP client with timeouts (easy). In the application service, call the job service with an @HttpExchange client with a 2 s connect and 3 s read timeout. Done when stopping the job service makes the call fail fast with a clear exception, not a hang.
  4. Resilience4j (medium). Add a circuit breaker, retry (exponential backoff with jitter) and a fallback to that call; expose the breaker via Actuator. Done when you can watch it go CLOSED, OPEN and HALF_OPEN by stopping and restarting the dependency, and POST calls are not retried without a key.
  5. Kafka producer and consumer (medium). Publish ApplicationSubmitted (JSON, keyed by job id) from the application service and consume it in a notification service. Done when two instances of the consumer in one group split the partitions and a second group receives every event.
  6. Dead-letter topic (medium). Make the listener throw for a specific bad record, configure retries with back-off and a DLT. Done when the bad record lands in the DLT with the exception headers after the retries, and the good records behind it are still processed.
  7. Idempotency and outbox (hard). Replace direct publishing with an outbox table and a scheduled relay; add a processed-event table to the consumer. Done when killing the application between commit and publish does not lose the event, and replaying the same event twice sends only one email.
  8. RabbitMQ variant (medium). Re-implement the notification flow with a topic exchange, durable queue, DLX and @RabbitListener. Done when a rejected message appears in the dead-letter queue, and you can explain in two sentences when you would pick RabbitMQ over Kafka.
  9. Tracing (medium). Add Micrometer Tracing with OTLP or Zipkin export to the gateway and two services, enable Kafka observation, and show the trace id in the logs. Done when one browser request shows up as one trace with spans from the gateway, both services and the Kafka consumer.
  10. Project 4 (hard). Build either a URL shortener with analytics (a redirect service that serves from Redis and publishes a click event, plus an analytics service that consumes events and exposes statistics) or a food-delivery backend split into services (orders, payments, notifications) using Redis, Kafka or RabbitMQ. Run everything with one compose.yaml with healthchecks and depends_on: condition: service_healthy, add a README with an architecture diagram, and add timeouts, a circuit breaker and tracing. Done when docker compose up starts the whole system, a simulated outage of one service does not lose events, and you can walk an interviewer through the event flow.

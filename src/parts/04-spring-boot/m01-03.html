Configuration: application.properties, application.yml and property precedence

Boot reads settings from application.properties or application.yml, and from many other sources; when the same key appears twice, the higher-priority source (command-line arguments, then environment variables, then files) wins.

Code should not contain a database URL, a port or an API key. Those change between your laptop, the test server and production. Externalised configuration means keeping them outside the compiled code, so the same JAR runs everywhere with different settings.

properties vs YAML: the same keys

Boot reads src/main/resources/application.properties or application.yml (or .yaml). Pick one format per project. The keys are identical; YAML nests them by indentation.

server.port=8081
spring.application.name=order-service
spring.datasource.url=jdbc:postgresql://localhost:5432/shop
spring.datasource.username=shop_user
spring.jpa.hibernate.ddl-auto=validate
logging.level.com.example.shop=DEBUG
server:
  port: 8081
spring:
  application:
    name: order-service
  datasource:
    url: jdbc:postgresql://localhost:5432/shop
    username: shop_user
  jpa:
    hibernate:
      ddl-auto: validate
logging:
  level:
    com.example.shop: DEBUG

If both application.properties and application.yml exist, the .properties values win. Do not mix them.

Where Boot looks

In order of increasing priority: the classpath root, then a /config folder on the classpath, then the current directory, then ./config/ and its sub-folders. A file next to the JAR can therefore override the one packed inside it, which is handy on servers. Change the name or the location with spring.config.name and spring.config.location.

Property source precedence (highest first)

Boot gathers settings from many places and merges them. For a given key, the first source in this list that has it wins:

  1. Command-line arguments: java -jar app.jar --server.port=9090
  2. Java system properties: -Dserver.port=9090 (SPRING_APPLICATION_JSON sits near here too)
  3. Operating-system environment variables: SERVER_PORT=9090
  4. Profile-specific files: application-prod.yml (outside the JAR beats inside)
  5. application.yml / application.properties: outside the JAR beats inside
  6. @PropertySource files and default properties: the lowest priority, including defaults in your @Value("${x:default}")

The simplified rule to remember: command line > environment > profile files > application.yml > defaults. This gives a clean design: put safe defaults in application.yml, specific values in a profile file, and secrets or per-server overrides in environment variables.

$ java -jar app.jar                               # 8081 from application.yml
$ SERVER_PORT=9000 java -jar app.jar              # environment variable wins
$ java -jar app.jar --server.port=9100            # command line wins over all

Relaxed binding: one setting, many spellings

Boot matches names loosely, so the same setting can be written in different ways depending on where it lives.

WhereFormExample for property app.max-retries
.properties / .ymlkebab-case (recommended)app.max-retries=3
.properties / .ymlcamelCase and underscore also acceptedapp.maxRetries=3
Environment variableUPPER_CASE with underscoresAPP_MAXRETRIES=3 or APP_MAX_RETRIES=3

That is why SPRING_DATASOURCE_PASSWORD sets spring.datasource.password. Write keys in kebab-case in files.

Secrets

Never commit passwords, API keys or JWT secrets. Use environment variables, a secrets manager, or a file that is not in Git. Reference them with a placeholder so the file stays safe to commit:

spring:
  datasource:
    url: ${DB_URL:jdbc:postgresql://localhost:5432/shop}
    username: ${DB_USER:shop_user}
    password: ${DB_PASSWORD}              # no default: must be provided
app:
  jwt-secret: ${JWT_SECRET}

${NAME:default} reads the environment (or any property) and falls back to the default after the colon. With no default and no value, startup fails with Could not resolve placeholder, which is what you want for a missing secret.

spring.config.import and the Environment

Pull in extra files with spring.config.import. The prefix optional: means "do not fail if it is missing".

spring:
  config:
    import: optional:file:./local-secrets.properties

Inside code, the Environment bean gives programmatic access: env.getProperty("app.name"), env.getActiveProfiles(). Prefer @Value or @ConfigurationProperties in normal code (next articles).

Seeing which value won

With Actuator, /actuator/env lists each property source and each value (expose it only in dev; it can reveal secrets, so Boot masks values by default). In the log, The following 1 profile is active: "dev" tells you the profile.

Rules

  • YAML uses spaces only, a consistent indent (2 spaces), and key: value with a space after the colon.
  • A key set in a higher-priority source completely overrides lower ones; lists are replaced as a whole, not merged.
  • Changing a property file needs a restart (DevTools restarts for you in development).

Conventions

  • Use kebab-case keys, a common prefix for your own settings (app.* or the company name), and YAML for nested data.
  • Defaults for local development live in application.yml; production differences arrive through profile files and environment variables.
  • Secrets only through environment variables or a secret store; never in Git.

Edge cases

  • A password containing # or : in YAML or properties needs quotes in YAML ("p#ss"); in .properties, # inside a value is fine but a leading # starts a comment.
  • A YAML key spring.datasource.url written as one dotted key works, but mixing dotted and nested forms in the same file is confusing.
  • Unknown keys are silently ignored for @Value; @ConfigurationProperties can be told to fail on unknown fields, which catches typos.

Mistake: committing the production password

A password in a file in Git stays in the history forever, even after you delete it. Rotate the secret and move it to an environment variable.

Interview: "How do you externalise configuration? What is the precedence?"

  • Properties/YAML files, environment variables, system properties and command-line arguments; the same JAR works in every environment.
  • Order, highest first: command line, environment, profile-specific files, application.yml, defaults.
  • Relaxed binding maps SPRING_DATASOURCE_URL to spring.datasource.url. Secrets come from the environment, never from Git.

Profiles: dev, test and prod settings

A profile is a named set of configuration and beans that is switched on with spring.profiles.active, so the same code uses an H2 database and debug logs in dev and PostgreSQL and quiet logs in prod.

You rarely run an application with the same settings everywhere. On your laptop you want a local database and detailed logs; in production a managed database, small logs and real payment keys. Profiles let you describe each environment once and pick one when starting. The build artifact stays the same (one JAR); only the profile changes. This idea is called build once, configure per environment, and it is the base of every Docker or Kubernetes deployment.

Activating a profile

$ java -jar app.jar --spring.profiles.active=prod
$ java -Dspring.profiles.active=prod -jar app.jar
$ SPRING_PROFILES_ACTIVE=prod java -jar app.jar          # typical in Docker
$ ./mvnw spring-boot:run -Dspring-boot.run.profiles=dev

You can also set spring.profiles.active=dev in application.yml as a local default, but do not commit a hard-coded prod there. Several profiles are separated by commas (dev,debug). In tests, use @ActiveProfiles("test") (Module 5). If no profile is set, the profile named default is active. IntelliJ users set the same value in the run configuration under "Active profiles".

Boot tells you what it chose in the first lines of the log. Always look at this line when something behaves strangely:

The following 1 profile is active: "prod"
# or, when nothing was set:
No active profile set, falling back to 1 default profile: "default"

Profile-specific files

Boot loads application.yml first, then application-{profile}.yml for every active profile, which overrides the base values. The same naming works for .properties files.

How Boot decides which value wins

When the same key appears in several places, the more specific source wins. From weakest to strongest, the order that matters in daily work is:

  1. application.yml inside the JAR (the shared defaults).
  2. application-{profile}.yml inside the JAR.
  3. An application.yml and application-{profile}.yml placed outside the JAR (next to it, or in a config/ folder).
  4. Operating-system environment variables (SPRING_DATASOURCE_URL).
  5. Command-line arguments (--server.port=9090).

So a base file gives defaults, the profile file overrides them for one environment, and the deployment can still override a single value without rebuilding. When two profiles are active (dev,debug), the profile listed later overrides the earlier one. The full list of sources is in the configuration files article.

Multi-document YAML in one file

A YAML file can hold several documents separated by ---. Each can be tied to a profile with spring.config.activate.on-profile.

app:
  notification:
    channel: email
---
spring:
  config:
    activate:
      on-profile: dev
app:
  notification:
    channel: console
---
spring:
  config:
    activate:
      on-profile: prod
app:
  notification:
    channel: sms

In .properties files use the separate-file naming instead (the multi-document form exists with #--- but is rare). Older tutorials use spring.profiles: dev for this; that key was removed in Boot 2.4, so use spring.config.activate.on-profile.

@Profile: beans that depend on the environment

Put @Profile on a bean or configuration class and it is registered only when the profile is active. Internally it is a condition checked while the container reads bean definitions, so a bean in an inactive profile is never even created (see the container). This is how the notification app chooses its sender.

public interface NotificationSender {
    void send(String to, String text);
}

@Component
@Profile("dev")
public class ConsoleSender implements NotificationSender {
    public void send(String to, String text) {
        System.out.println("[DEV] to " + to + ": " + text);
    }
}

@Component
@Profile("prod")
public class SmsSender implements NotificationSender {
    public void send(String to, String text) { /* call the SMS gateway */ }
}

@Component
@Profile("!dev & !prod")       // every other profile, including 'default'
public class NoOpSender implements NotificationSender {
    public void send(String to, String text) { }
}

Expressions use ! (not), & (and) and | (or); mixing & and | needs parentheses. Without a matching sender the app fails to start with NoSuchBeanDefinitionException, so make sure every profile has exactly one implementation, or add a catch-all like the last one. The opposite problem, two matching senders, gives NoUniqueBeanDefinitionException (bean errors).

@Profile also works on a @Bean method and on a whole @Configuration class. You can read the profiles in code when you really need to:

@Component
class ProfileInfo {
    ProfileInfo(Environment env) {
        String[] active = env.getActiveProfiles();           // e.g. ["prod"]
        boolean prod = env.acceptsProfiles(Profiles.of("prod"));
    }
}

Other profile features

  • spring.profiles.include adds profiles unconditionally (for example dev always includes local-db).
  • spring.profiles.group.prod: prod-db,prod-logging activates a group with one name. Starting with prod then activates all three.
  • Environment.getActiveProfiles() returns the active profiles at runtime; the Actuator /actuator/env endpoint shows them too, if you expose it (Actuator).
  • spring.profiles.default changes the name of the fallback profile, which is rarely needed.

Rules

  • Profile-specific files override application.yml, and the active profile list order matters: later profiles override earlier ones.
  • @Profile without a value is invalid; a bean without it exists in every profile.
  • An unknown profile name is not an error: it only means no file matches.
  • spring.profiles.active and spring.profiles.include cannot be set inside a profile-specific file or a document with on-profile. Boot refuses to start with an InvalidConfigDataPropertyException, because the profile would depend on itself. Set them in the base file, an environment variable or an argument.

Conventions

  • Keep profile names few and standard: dev, test, prod (and maybe staging).
  • Do not branch on "prod" inside business code; use properties and let configuration differ.
  • Keep real production values out of application-prod.yml; read them from the environment.
  • Make dev work with one command on a fresh laptop (Docker Compose for the database, Compose), so new team members start without a setup document.

Mistake: secrets and environment checks in the code

Wrong: password in Git, profile test in code

spring:

A password in Git stays in the history even after you delete it. Branching on the profile name makes the production path impossible to test on your laptop.

Edge cases and errors

  • With no active profile, application-default.yml is loaded if present. Do not rely on this; it confuses people.
  • Too many profiles combine in unexpected ways (dev,debug,local). If you need more than three, use properties.
  • A list in a profile file replaces the whole list from the base file; it is not merged. If application.yml has three app.allowed-origins and the profile file has one, only that one remains. Scalar keys are overridden one by one, maps are merged key by key.
  • A typo in a profile name (SPRING_PROFILES_ACTIVE=prd) is silent: the app starts with base settings, often connecting to the dev database. Check the startup log line.
  • A ${DB_URL} placeholder with no value fails at startup with IllegalArgumentException: Could not resolve placeholder 'DB_URL'. That is good: it stops a misconfigured prod start.
  • On Windows PowerShell set an environment variable with $env:SPRING_PROFILES_ACTIVE="dev"; cmd uses set SPRING_PROFILES_ACTIVE=dev.
  • Profile-specific files are loaded only for active profiles, so a test that forgets @ActiveProfiles("test") silently uses the base settings.

Real projects

A typical setup: application.yml with local defaults, application-test.yml pointing to Testcontainers or H2, and production values injected by the deployment (Kubernetes or Docker env vars, DevOps · Module 3) with SPRING_PROFILES_ACTIVE=prod. Some teams add a staging profile that equals prod but with a smaller database and test payment keys. Secrets come from a secret store (Kubernetes Secrets, Vault, AWS Secrets Manager), never from Git.

Interview: "What are Spring profiles? How do you use them?"

  • Profiles group configuration and beans per environment. Activate with spring.profiles.active (property, argument or env var).
  • Config: application-{profile}.yml or multi-document YAML with spring.config.activate.on-profile. Beans: @Profile, with expressions like !prod.
  • Precedence: command line and environment beat profile files, which beat application.yml; later profiles beat earlier ones.
  • Add that you keep secrets in environment variables, and prefer properties over profile checks for feature choices. A follow-up is often "how do you run tests with a different database?" (@ActiveProfiles("test") and application-test.yml).

@Value and @ConfigurationProperties: reading settings in code

Use @Value("${key:default}") for one simple setting; use @ConfigurationProperties with a record and @Validated for a group of related settings, because it is type-safe, validated and easy to test.

Once a value is in application.yml, your classes need to read it. Spring offers two main ways, and a quick look at the third.

@Value: one value at a time

@Service
public class OrderService {

    private final String appName;
    private final int maxItems;
    private final boolean giftWrapEnabled;

    public OrderService(@Value("${spring.application.name}") String appName,
                        @Value("${app.order.max-items:20}") int maxItems,
                        @Value("${app.order.gift-wrap:false}") boolean giftWrapEnabled) {
        this.appName = appName;
        this.maxItems = maxItems;               // 20 if the key is missing
        this.giftWrapEnabled = giftWrapEnabled;
    }
}
  • ${key} reads a property; ${key:default} uses the default after the colon if the key is missing; without a default a missing key fails startup.
  • Spring converts the string to int, boolean, Duration, List and more. A list: @Value("${app.hosts}") List<String> with a,b,c.
  • #{...} is a SpEL expression (Spring Expression Language): @Value("#{2 * 60}"), @Value("#{systemProperties['user.home']}"). Use it rarely.

It is perfect for one value. Its limits show up quickly: the keys are strings spread across many classes (a typo is found only at runtime), there is no grouping, no validation, no IDE help, and testing needs every key set. Relaxed binding is also weaker: @Value wants the exact kebab-case key.

@ConfigurationProperties: a typed group

Bind a whole prefix to an object. With a record the settings become immutable and the object is created through its constructor (constructor binding).

app:
  payment:
    base-url: https://pay.example.com
    api-key: ${PAYMENT_API_KEY}
    timeout: 5s
    max-retries: 3
    allowed-methods:
      - upi
      - card
import java.time.Duration;
import java.util.List;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotEmpty;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.context.properties.bind.DefaultValue;
import org.springframework.validation.annotation.Validated;

@ConfigurationProperties(prefix = "app.payment")
@Validated
public record PaymentProperties(
        @NotBlank String baseUrl,
        @NotBlank String apiKey,
        @DefaultValue("5s") Duration timeout,
        @DefaultValue("3") @Min(0) @Max(10) int maxRetries,
        @NotEmpty List<String> allowedMethods) {
}

Register it. The easiest is to scan for such classes on the main class:

@SpringBootApplication
@ConfigurationPropertiesScan          // finds all @ConfigurationProperties classes
public class ShopApplication { /* ... */ }

// or, one by one:
@Configuration
@EnableConfigurationProperties(PaymentProperties.class)
class PaymentConfig { }

Then inject it like any bean:

@Service
public class PaymentService {
    private final PaymentProperties props;

    public PaymentService(PaymentProperties props) {
        this.props = props;
    }

    public void pay(long paise) {
        System.out.println("POST " + props.baseUrl() + " timeout " + props.timeout());
        // retry up to props.maxRetries() times ...
    }
}

What you gain:

  • Type conversion — 5s becomes a Duration, 10MB a DataSize, true a boolean, nested objects and lists work.
  • Validation at startup — a blank api-key stops the app with a clear message:
Binding to target PaymentProperties[...] failed:

    Property: app.payment.apiKey
    Value: ""
    Reason: must not be blank

Action: Update your application's configuration
  • Relaxed binding — base-url, baseUrl and BASE_URL all match the field baseUrl.
  • One place — easy to find, easy to construct in a test with new PaymentProperties(...).

Validation needs the spring-boot-starter-validation dependency. You can also generate IDE auto-complete and documentation for your keys by adding the spring-boot-configuration-processor dependency (optional, annotation-processor only).

Nested records and the class-style alternative

@ConfigurationProperties(prefix = "app.mail")
public record MailProperties(String from, Smtp smtp) {
    public record Smtp(String host, int port, boolean tls) { }
}
// app.mail.from, app.mail.smtp.host, app.mail.smtp.port, app.mail.smtp.tls

Before records, properties were a class with getters and setters (JavaBean binding). That still works and is common in older code. A class with a single constructor and no setters also uses constructor binding. If a class has several constructors, mark the one for binding with @ConstructorBinding.

Rules

  • A @ConfigurationProperties class is a bean only when registered (@ConfigurationPropertiesScan, @EnableConfigurationProperties, or @Component on a mutable class).
  • Validation annotations are checked only when the class also has @Validated.
  • For a prefix use kebab-case lowercase (app.payment), not camelCase.

Conventions

  • Default to @ConfigurationProperties records for anything beyond a single flag; keep @Value for one-off values.
  • Give optional settings sensible defaults and mark required ones with @NotBlank, @NotNull.
  • Never log a properties object that contains secrets; override toString or avoid printing it.

Edge cases

  • @Value is not applied to static fields. And a @Value field is still null in the constructor if you use field injection (use constructor parameters).
  • Unknown keys: by default @ConfigurationProperties ignores unknown properties. Set ignoreUnknownFields = false to make typos fail.
  • Changing a property file does not change a running application; a restart (or Spring Cloud refresh) is needed.
  • @Value("${a.b}") with an empty value gives an empty string, not null; @Value("${a.b:}") gives an empty string when missing.

Mistake: 15 @Value fields scattered everywhere

The same key typed in five classes, with different defaults, is a bug waiting to happen. Group them in one properties record.

Interview: "@Value vs @ConfigurationProperties?"

  • @Value injects a single property with optional default and SpEL support. @ConfigurationProperties binds a whole prefix into a typed object.
  • The latter gives relaxed binding, type conversion, nested objects, validation (@Validated) and IDE metadata; it is the recommended style.
  • Constructor binding with records keeps settings immutable.

What @SpringBootApplication does

@SpringBootApplication is three annotations in one: @SpringBootConfiguration (this class is a configuration), @EnableAutoConfiguration (turn on Boot's auto-configuration) and @ComponentScan (scan this package and below).

The annotation on your main class is short but carries the whole Boot idea. It is a meta-annotation: an annotation built from other annotations, so one line on your class has the effect of several. Here is what it contains.

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan(excludeFilters = { /* skip some test configurations */ })
public @interface SpringBootApplication {
    // attributes: exclude, excludeName, scanBasePackages, scanBasePackageClasses ...
}

And this is the typical main class it sits on:

package com.example.shop;                 // the ROOT package

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class ShopApplication {
    public static void main(String[] args) {
        SpringApplication.run(ShopApplication.class, args);
    }
}

The three annotations, one by one

@SpringBootConfiguration
A specialised @Configuration. It marks the class as a source of bean definitions, so you can put @Bean methods directly in the main class. It exists as a separate annotation so that tests can find your main class: @SpringBootTest and the slice tests search upwards from the test package until they find a class with this annotation, and use it as the configuration (Module 5).
@EnableAutoConfiguration
Tells Boot to load all matching auto-configuration classes: beans created for you because of what is on your classpath and in your properties (next article).
@ComponentScan
Scans the main class's package and sub-packages for stereotype annotations (scanning).

You could write the three annotations yourself and get the same behaviour. The combined annotation is just convenient.

Inside @EnableAutoConfiguration

This is the most interesting of the three. It is itself made of two parts:

  • @AutoConfigurationPackage records the package of your main class. Later, JPA auto-configuration uses it as the default place to look for @Entity classes and Spring Data repositories. That is why entities in a package outside your root package are "not found" even though you never configured scanning.
  • @Import(AutoConfigurationImportSelector.class) runs while the context reads configuration. The selector reads the list of auto-configuration class names from the file META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports inside each JAR on the classpath, removes the ones you excluded, and imports the rest. Each of those classes carries @Conditional... rules, so only those that fit your classpath and properties actually create beans.

The same trick is how any library can plug into Boot: it ships a configuration class and lists it in that .imports file. Your own code is never touched.

Inside @ComponentScan on this annotation

The @ComponentScan on @SpringBootApplication has two exclude filters. One (TypeExcludeFilter) lets test slices such as @WebMvcTest remove beans they do not need. The other (AutoConfigurationExcludeFilter) stops the scan from picking up auto-configuration classes as ordinary configuration, because they must go through the conditional import route described above. You normally never think about these filters, but they explain why a sliced test loads only part of your app.

What SpringApplication.run does

The annotation is a description; SpringApplication.run does the work. In simplified order:

  1. Decide the application type from the classpath: servlet web (Spring MVC), reactive web, or none.
  2. Load configuration: application.yml, environment variables, command-line arguments, and set the active profiles (profiles).
  3. Print the banner and create the right ApplicationContext.
  4. Register bean definitions from your classes (component scan, @Bean) and from auto-configuration.
  5. Refresh the context: create all singleton beans; the web context starts the embedded server (embedded server).
  6. Call all CommandLineRunner and ApplicationRunner beans, then return.

Boot publishes events along the way (ApplicationStartedEvent, ApplicationReadyEvent and more); you can listen to them (events). If anything fails, Boot catches the exception, prints a readable failure analysis ("APPLICATION FAILED TO START", with a Description and an Action) and exits with a non-zero code (bean errors). The run method returns the ConfigurableApplicationContext, which is useful in plain programs and tests; in a web app the JVM stays alive because the server threads keep running.

Running code at startup

A runner is a bean that executes once after the context is ready. Use it for small start-up tasks such as seeding demo data. It is not a place for heavy business logic.

@Component
@Order(1)                                   // lower number runs first
class DemoDataLoader implements CommandLineRunner {

    private static final Logger log = LoggerFactory.getLogger(DemoDataLoader.class);

    @Override
    public void run(String... args) {
        log.info("Seeding demo data, args = {}", List.of(args));
    }
}

ApplicationRunner is the same but receives parsed ApplicationArguments (so you can ask args.containsOption("seed") for --seed). A runner that throws an exception stops the application with a failure exit.

Customising startup

public static void main(String[] args) {
    SpringApplication app = new SpringApplication(ShopApplication.class);
    app.setBannerMode(Banner.Mode.OFF);
    app.setAdditionalProfiles("local");
    app.run(args);
}

// or the fluent builder:
new SpringApplicationBuilder(ShopApplication.class)
        .profiles("local")
        .run(args);

Most of these switches also exist as properties (spring.main.banner-mode=off, spring.main.web-application-type=none), which is usually better because you do not touch the code. For a command-line tool without a web server, set spring.main.web-application-type=none or leave out the web starter.

Rules

  • Use exactly one @SpringBootApplication per application, in the root package.
  • Keep the main class small: main, annotations, maybe a few shared beans. Put real configuration in separate @Configuration classes.
  • Do not add @EnableAutoConfiguration a second time; it is already there.
  • All your code (controllers, services, entities, repositories) must live in the root package or below, unless you list the extra package in scanBasePackages.

Conventions

  • Name the class after the application, ending in Application (ShopApplication), in the top package of the group id and artifact (com.example.shop).
  • Prefer properties (spring.autoconfigure.exclude) or the exclude attribute over deleting dependencies just to silence one auto-configuration.

Mistake: sprinkling extra annotations on the main class

Adding @EnableJpaRepositories, @EntityScan or @EnableScheduling to the main class changes more than you expect: @EnableJpaRepositories switches off Boot's own repository scanning defaults. This also affects sliced tests, which load the main class. Put such annotations on dedicated configuration classes.

Wrong: main class in a sub-package

com.example.shop.web.ShopApplication   (scans only ...shop.web)
com.example.shop.service.OrderService  (never found)

Right: main class in the root package

com.example.shop.ShopApplication       (scans all of ...shop)
com.example.shop.service.OrderService  (found)

Edge cases and errors

  • In a multi-module project, beans in another module's package are not scanned unless that package is under yours or you list it in scanBasePackages. Libraries should expose their beans through auto-configuration instead.
  • Running a Boot app inside an external Tomcat (WAR) needs a SpringBootServletInitializer; this is the legacy deployment style.
  • Excluding a class that is not an auto-configuration (for example your own @Configuration) fails with IllegalStateException: The following classes could not be excluded because they are not auto-configuration classes. To remove your own bean, use a profile or a condition instead.
  • A class in the default package (no package line) makes the scan cover the whole classpath; Boot warns that the context is unlikely to start. Always declare a package.
  • Two classes with @SpringBootApplication in one module give IllegalStateException: Found multiple @SpringBootConfiguration annotated classes in tests, because the search finds more than one.
  • The main method is not a bean: you cannot inject anything into it. Use a runner or an event listener.

Boot 3 and Boot 4

The annotation and its three parts work the same in both lines. Before Boot 2.7 the auto-configuration list lived in META-INF/spring.factories; modern versions use the .imports file shown above. Boot 4 also splits its large auto-configuration JAR into smaller per-technology modules, which changes dependency names but not how you write your main class.

Interview: "What does @SpringBootApplication do?"

  • It combines @SpringBootConfiguration, @EnableAutoConfiguration and @ComponentScan.
  • Scan covers the main class's package and below; auto-configuration creates beans from the classpath and properties, using the imports file and @Conditional rules.
  • SpringApplication.run creates the context, starts the embedded server and calls runners.
  • A strong answer adds why the main class belongs in the root package and how you would exclude one auto-configuration. A common follow-up: "how do you run code at startup?" (CommandLineRunner or ApplicationRunner).

How auto-configuration works

Boot ships hundreds of ordinary @Configuration classes, listed in an .imports file; each is guarded by conditions (is this class on the classpath? is this property set? is a bean of this type already defined?), so only the ones that fit your app apply.

You add spring-boot-starter-web and, with no setup, a DispatcherServlet, a Tomcat server and a JSON converter exist. You add a PostgreSQL driver and a datasource properties, and a pooled DataSource appears. This is auto-configuration: Boot decides what beans you probably want, then creates them, unless you say otherwise.

The mechanism, step by step

  1. @EnableAutoConfiguration triggers an import selector.
  2. The selector reads the file META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports from every JAR on the classpath. It is a plain text file with one fully qualified class name per line. (Before Boot 2.7/3.0 the list lived in spring.factories; that is the old way.)
  3. Each listed class is a normal @AutoConfiguration (a variant of @Configuration) with @Bean methods and conditions.
  4. Conditions are evaluated: a class whose conditions fail contributes nothing.
  5. The surviving classes are processed after your own configuration, so your beans are already known and can win.

A real example, simplified

@AutoConfiguration
@ConditionalOnClass(DataSource.class)                 // JDBC classes are present
@EnableConfigurationProperties(DataSourceProperties.class)
public class DataSourceAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(DataSource.class)       // you did not define one
    public DataSource dataSource(DataSourceProperties props) {
        return props.initializeDataSourceBuilder().build();   // Hikari pool
    }
}

Read it as: "If JDBC is on the classpath and the user has not made their own DataSource, create one from the spring.datasource.* properties." Spring's actual classes are bigger, but the idea is exactly this.

The conditions

ConditionTrue whenExample use
@ConditionalOnClassA class is on the classpathSet up MVC only if DispatcherServlet is present
@ConditionalOnMissingClassA class is absentFallbacks
@ConditionalOnBeanA bean of that type existsAdd a metrics binder if a registry exists
@ConditionalOnMissingBeanNo bean of that type is defined yetBack-off: use my default unless the user made their own
@ConditionalOnPropertyA property has a valueFeature toggles: app.cache.enabled=true
@ConditionalOnWebApplicationThe app is a web appServlet-only beans
@ConditionalOnResourceA file existsOptional config files

You can use the same annotations in your own configuration, for example to create a bean only when a flag is set:

@Configuration
public class SmsConfig {

    @Bean
    @ConditionalOnProperty(name = "app.sms.enabled", havingValue = "true")
    public SmsSender smsSender() {
        return new SmsSender();
    }
}

Back-off: how you override a default

Because Boot's beans are guarded by @ConditionalOnMissingBean, defining your own bean replaces the default:

@Configuration
public class JacksonConfig {

    @Bean
    public ObjectMapper objectMapper() {         // Boot's ObjectMapper backs off
        return new ObjectMapper()
                .findAndRegisterModules()
                .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);
    }
}

Note the trade-off: when you replace a Boot bean, you lose Boot's other customisations of it (for example properties like spring.jackson.*). Often a smaller tool is better: a Jackson2ObjectMapperBuilderCustomizer bean, or just a property. Check the reference docs for the right extension point before replacing a whole bean.

Excluding an auto-configuration

@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)
public class ShopApplication { }
spring:
  autoconfigure:
    exclude:
      - org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration

Typical reason: you added a starter transitively but have no database in this module, and startup fails with Failed to configure a DataSource.

Writing your own auto-configuration (the idea)

Company teams package a shared logging or client library as a starter. The recipe: a @AutoConfiguration class with conditions, a properties class, and one line in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. Not needed for day-to-day work, but it shows there is no magic.

Rules

  • Auto-configuration never overrides a bean you defined (for beans guarded by @ConditionalOnMissingBean); your configuration is always processed first.
  • Conditions are about the state at startup. They do not react to later changes.
  • Auto-configuration classes must not be found by component scanning; they are loaded only through the imports file.

Conventions

  • Prefer changing a property over replacing a bean, and a customizer over a full replacement.
  • Define your own bean with the same type to take control; do not edit or copy Boot's classes.
  • Use --debug before guessing why a bean does or does not exist.

Edge cases

  • A transitive dependency can trigger an unwanted auto-configuration (a JDBC jar brings DataSource requirements). Exclude it or remove the jar.
  • Defining a bean of the type Boot expects with a different bean name still makes Boot back off, because the condition checks the type.
  • In sliced tests (@WebMvcTest, @DataJpaTest) only a chosen subset of auto-configurations is imported.
  • Boot 4 splits its auto-configuration into smaller modules; the mechanism (conditions, back-off, the .imports file) is unchanged.

Version note: spring.factories vs the imports file

Old tutorials say auto-configurations are listed under EnableAutoConfiguration in META-INF/spring.factories. That was Boot 2.x. From Boot 3.0 the only supported place is the AutoConfiguration.imports file shown above.

Interview: "How does Spring Boot auto-configuration work?"

  • @EnableAutoConfiguration loads class names from META-INF/spring/...AutoConfiguration.imports in every JAR.
  • Each class has conditions such as @ConditionalOnClass, @ConditionalOnProperty and @ConditionalOnMissingBean; only matching ones register beans.
  • "Back-off": if you define your own bean, Boot's default is skipped.
  • Debug with --debug or /actuator/conditions; disable with exclude or spring.autoconfigure.exclude.

JSON and Jackson basics

JSON is the text format APIs speak; Jackson converts Java objects to JSON (serialization) and JSON back to Java objects (deserialization), and Spring Boot configures it for you.

JSON (JavaScript Object Notation) is the body format of almost every REST API: easy to read, light, and understood by every language. In a Spring Boot app, a library called Jackson does the conversion between Java objects and JSON. You rarely call Jackson yourself — Spring's message converters call it for @RequestBody parameters and for return values — but every surprise about dates, nulls and field names comes from Jackson's rules, so you need to know them.

JSON in one minute

{
  "id": 42,
  "name": "Wireless Mouse",
  "price": 799.00,
  "inStock": true,
  "tags": ["wireless", "usb"],
  "dimensions": { "widthMm": 60, "heightMm": 35 },
  "discount": null
}

JSON has only six kinds of value: object ({…} with named members), array ([…]), string, number, boolean and null. The rules are strict: keys and strings use double quotes only, there are no comments, no trailing commas, and the text is UTF-8. A single misplaced comma makes the whole document invalid.

JSON valueUsually maps to this Java type
objecta record, a class, or Map<String, Object>
arrayList<T>, Set<T>, T[]
stringString, an enum, LocalDate, UUID, …
numberint, long, double, BigDecimal
booleanboolean / Boolean
nullnull

Serialization and deserialization

Serialization
Java object → JSON text. It happens when your controller returns an object. Jackson reads the object through its getters (or the accessors of a record).
Deserialization
JSON text → Java object. It happens for @RequestBody. Jackson creates the object through a constructor, or through the no-argument constructor plus setters.

Returning a record from a controller is all you need; Spring Boot's auto-configured ObjectMapper does the rest.

public record ProductResponse(
        Long id,
        String name,
        BigDecimal price,
        boolean inStock,
        List<String> tags,
        LocalDate launchDate) {}
{
  "id": 42,
  "name": "Wireless Mouse",
  "price": 799.00,
  "inStock": true,
  "tags": ["wireless", "usb"],
  "launchDate": "2026-08-15"
}

You can also use the mapper by hand, for example in a test, in a Kafka consumer, or when you store JSON in a column:

// objectMapper is the auto-configured bean; inject it through the constructor
String json = objectMapper.writeValueAsString(response);                 // Java → JSON
ProductResponse back = objectMapper.readValue(json, ProductResponse.class);  // JSON → Java

// Generic types need a TypeReference because of type erasure
List<ProductResponse> list = objectMapper.readValue(
        listJson, new TypeReference<List<ProductResponse>>() {});

// No class available? Read a tree
JsonNode tree = objectMapper.readTree(json);
String name = tree.get("name").asText();

Dates and times

Java typeJSON valueUse it for
LocalDate"2026-10-21"A calendar date with no time or zone: birthday, due date
LocalDateTime"2026-10-21T10:15:30"Wall-clock time with no zone (ambiguous; avoid for events)
Instant"2026-10-21T04:45:30Z"A precise moment in time: createdAt, updatedAt
OffsetDateTime"2026-10-21T10:15:30+05:30"A moment plus the offset the user saw (+05:30 is India)

The professional habit: send timestamps as UTC Instant values (they end with Z), store them in UTC, and convert to the user's time zone only when you display them, in the React app. Do not use java.util.Date in new code. A LocalDateTime without a zone is the usual source of "the time is off by 5½ hours" bugs.

Nulls and missing fields

  • Writing: nulls are written as null. Omit them per class with @JsonInclude(NON_NULL) or for the whole app with spring.jackson.default-property-inclusion=non_null. Omitting shrinks the payload; always writing keys gives a stable shape that is easier to type in TypeScript. Choose one policy for the whole API.
  • Reading: a missing field becomes null for objects, but 0 or false for primitives. You cannot tell "missing" from "zero". Use wrapper types (Integer, Boolean) together with @NotNull for required numbers.
  • A plain DTO also cannot tell "field absent" from "field explicitly null". That matters for PATCH; see the partial-update section of the DTO article.

Unknown properties

Because Boot ignores unknown properties, a client that sends "prcie": 500 (a typo) gets no error — the field is silently dropped. That is friendly to clients that add fields later, but it hides mistakes. To be strict, set spring.jackson.deserialization.fail-on-unknown-properties=true; unknown fields then produce a 400. Public APIs usually stay tolerant; internal APIs often go strict.

Enums, money and big numbers

  • Enums are written by name ("status": "ACTIVE"). An unknown name on input fails with a 400. If the API value must differ from the constant name, use @JsonValue and @JsonCreator.
  • Money: never double (0.1 + 0.2 is not 0.3). Use BigDecimal, which becomes a JSON number like 799.00. Some teams send an integer in paise (79900) or a string to avoid any rounding in JavaScript.
  • Big numbers: JavaScript reads JSON numbers as 64-bit floating point, which is exact only up to 9,007,199,254,740,991 (253 − 1). A Long id larger than that loses digits in the browser; send such ids as strings.

Records, classes and constructors

Records work without any annotations (Jackson 2.12 and newer). For a normal class, Jackson needs either a no-argument constructor plus setters, or a constructor whose parameter names it can see (Spring Boot compiles with -parameters and registers the right module), or an explicit @JsonCreator. If none exists you get InvalidDefinitionException: Cannot construct instance of … (no Creators, like default constructor, exist). Spring reports this as a 500, not a 400, because the fault is in your class definition and not in the client's JSON.

Spring Boot 3.x uses Jackson 2; Spring Boot 4 uses Jackson 3

Boot 3.x ships Jackson 2 (com.fasterxml.jackson.databind.ObjectMapper). Spring Boot 4 uses Jackson 3 by default. Jackson 3 moved its core and databind classes to a new package, tools.jackson (for example tools.jackson.databind.ObjectMapper), and its exceptions are unchecked. The annotations in this article (@JsonProperty, @JsonIgnore, @JsonInclude, @JsonFormat and the rest) still live in com.fasterxml.jackson.annotation. Everything above about annotations, dates and null policy applies to both versions; only the imports and the direct ObjectMapper calls differ. If you upgrade an existing app, read the Boot 4 migration guide for its Jackson section.

Rules

  • JSON must be valid: double quotes, no comments, no trailing commas.
  • Jackson derives property names from getters: getName() gives name, and isActive() on a boolean gives active (not isActive).
  • For reading, Jackson needs a way to create the object: a record, a no-arg constructor with setters, or a constructor it can map.
  • Generic collections read by hand need a TypeReference.

Conventions

  • Use camelCase keys, ISO-8601 dates, UTC Instant for timestamps, and one consistent null policy.
  • Serialize DTOs, not JPA entities (DTO article).
  • Do not hand-write JSON with string concatenation. Build objects and let Jackson write them.

Edge cases and the exceptions you will see

  • Infinite recursion: an entity graph where Order points to OrderItem and back fails with JsonMappingException: Infinite recursion (StackOverflowError); Spring wraps it in HttpMessageNotWritableException and the client gets a 500.
  • Hibernate proxies: serializing a lazy entity can fail with No serializer found for class org.hibernate.proxy.pojo.bytebuddy.ByteBuddyInterceptor. Another reason to use DTOs.
  • Input errors (bad JSON syntax, wrong type, unknown enum name) arrive as HttpMessageNotReadableException and become a 400.
  • @JsonIgnore on a field also blocks reading it. A write-only password field needs @JsonProperty(access = JsonProperty.Access.WRITE_ONLY) instead.

Mistake: hiding a password with @JsonIgnore on a two-way class

The client must be able to send the password when registering but must never receive it back. @JsonIgnore blocks both directions, so registration silently stores a null password.

Wrong: the password can no longer be read from the request

public class UserDto {
    private String email;
    @JsonIgnore
    private String password;
    // getters and setters
}

Right: accepted on input, never written to output

public class UserDto {
    private String email;
    @JsonProperty(access = JsonProperty.Access.WRITE_ONLY)
    private String password;
    // getters and setters
}

Interview: "How does Spring convert JSON to objects? How do you handle dates and nulls?"

  • An HttpMessageConverter backed by Jackson's ObjectMapper reads the body for @RequestBody and writes return values, chosen by Content-Type and Accept.
  • Serialization = object to JSON (getters); deserialization = JSON to object (constructor or setters).
  • Dates: ISO-8601 strings, Instant in UTC for timestamps, @JsonFormat only when a contract demands another pattern.
  • Nulls: @JsonInclude(NON_NULL) or spring.jackson.default-property-inclusion; use wrapper types and @NotNull to detect missing input.
  • Common annotations: @JsonProperty, @JsonIgnore, @JsonIgnoreProperties, @JsonInclude, @JsonFormat, @JsonCreator.

What makes an API RESTful

REST is an architectural style in which resources are identified by URLs and handled through representations with standard HTTP methods, one stateless request at a time; most real-world "REST APIs" follow it only partly, at level 2 of the Richardson model.

REST stands for Representational State Transfer. Roy Fielding described it in his 2000 PhD dissertation as a set of design rules for networked systems, taken from how the web itself works. REST is a style, not a protocol, a library or a standard. An API that follows the rules is called RESTful. In daily work, "REST API" usually means "JSON over HTTP with sensible URLs, methods and status codes".

The key ideas

Resource
Anything the API can name: a product, an order, a user, "the cart of user 7". A resource is a noun with a URL. It is not a database table and not a Java class; one resource may combine data from several tables.
Representation
A snapshot of a resource's state in some format, usually JSON. The same resource could have a JSON and an XML representation. The client never touches the database row; it exchanges representations.
Statelessness
Every request contains everything the server needs (token, parameters, body). The server keeps no conversation memory between requests.
Uniform interface
Every resource is handled the same way: identified by a URL, changed through representations, with standard methods and status codes, in self-descriptive messages (the method, status and Content-Type tell you what is going on).
Client–server
The UI and the data store are separate. The React app can change without touching the backend, and the other way round.
Cacheable
Responses say whether they may be reused (Cache-Control, ETag), so repeated reads can be cheap.
Layered system
A client cannot tell whether it talks to your server or to a proxy, CDN or load balancer in front of it.

Fielding also lists "code on demand" (the server sends executable code, like JavaScript) as an optional constraint. The uniform interface includes one more rule, HATEOAS, which is explained below.

Statelessness: why it matters

Imagine an e-commerce site on three server instances behind a load balancer. If server A kept your login in its own memory, your next request could land on server B, which would not know you. With a stateless design, you send a token every time and any instance can check it. The benefits are real:

  • Scaling: add or remove instances freely.
  • Reliability: if one instance dies, nothing is lost with it.
  • Simplicity: a request can be understood on its own, logged, replayed and retried.

The cost is that the token travels with every request and the server must verify it every time. This is why JWT-based security (Module 4) is configured as stateless in Spring Security. The client's UI state (which page you are on) may still be remembered by the client — "stateless" is about the server.

Richardson Maturity Model

Leonard Richardson's model grades how much of REST an API uses. It is a favourite interview topic.

LevelIdeaLooks like
0One URL, one method; HTTP is only a tunnel (RPC style)POST /api with {"action":"getProduct","id":42}
1Separate resources, each with its own URLPOST /products/42 for everything
2Proper HTTP methods and status codesGET /products/42 → 200 or 404
3Hypermedia: responses contain links to the next possible actions (HATEOAS)An order with cancel and pay links

Most production APIs, including the ones you will write, sit at level 2. That is a good, practical target.

HATEOAS in one paragraph

HATEOAS (Hypermedia As The Engine Of Application State) means a response tells the client what it can do next by including links, the way a web page has links. The client follows links instead of building URLs from documentation. For an order that can still be cancelled, the response could carry a cancel link; once the order ships, that link disappears. Spring has a library for this (spring-boot-starter-hateoas) and a common format called HAL. In practice, JSON APIs for single-page apps rarely go to level 3, because the front-end developers already know the URLs. Know the idea for interviews; do not feel bad about not using it.

{
  "id": 5,
  "status": "PLACED",
  "total": 1598.00,
  "_links": {
    "self":   { "href": "/api/v1/orders/5" },
    "cancel": { "href": "/api/v1/orders/5/cancel" }
  }
}

REST compared with other API styles

StyleFormatBest forWatch out for

GraphQLOne endpoint, client writes the queryApps that need flexible data shapesCaching and rate limiting are harder

Rules of a RESTful API

  • Identify things with nouns in URLs (/orders/5), and let the HTTP method be the verb.
  • Keep requests self-contained: no server-side session needed to understand them.
  • Use standard status codes and media types so that clients and proxies understand the messages.
  • Do not let a read change data: GET must be safe.

Conventions: a practical checklist

  • Plural nouns, lowercase, consistent naming (URL design).
  • JSON in and out; camelCase keys; ISO-8601 dates.
  • Correct status codes and one error format everywhere.
  • Pagination for every list; a version in the URL when you must break clients.
  • Token-based authentication in the Authorization header.

Edge cases: where pure REST bends

  • Some operations do not map to CRUD: "cancel an order", "send an OTP", "transfer money". Model them as sub-resources or action URLs and use POST (see URL design).
  • A "session" or "cart" is state, but you can store it on the server as a resource (/carts/{id}) that the client refers to by id. That is still stateless communication.
  • Long-running work does not fit request–response; answer 202 Accepted and give a status resource to poll.

Mistake: RPC in disguise

Endpoints named after methods (/getUser, /createOrder, /deleteProduct) with everything sent as POST are level 0 or 1. Caches, monitoring and developers lose all the meaning that HTTP already provides.

Wrong: verbs in URLs, POST for everything

POST /api/getUser        {"id": 7}
POST /api/createOrder    {"userId": 7, "items": [...]}
POST /api/deleteProduct  {"id": 42}

Right: resources and methods

GET    /api/v1/users/7
POST   /api/v1/orders          {"items": [...]}
DELETE /api/v1/products/42

Interview: "What is REST? What are its constraints? What does stateless mean?"

  • An architectural style from Fielding's dissertation: client–server, stateless, cacheable, uniform interface, layered system, optional code on demand.
  • Resources are named by URLs; clients exchange representations (JSON) using standard methods and status codes.
  • Stateless: each request is complete on its own, so any server instance can serve it; this makes horizontal scaling easy.
  • Richardson levels 0–3: single endpoint, resources, HTTP verbs and codes, then HATEOAS. Say that most APIs are level 2.
  • Be ready for "REST vs GraphQL vs gRPC": REST is simple and cacheable, GraphQL gives flexible queries, gRPC is binary and fast for internal calls.

Designing resource URLs

Name resources with plural lowercase nouns, let the HTTP method be the verb, nest at most one or two levels, and use query parameters for filtering, sorting and paging.

URLs are the user interface of your API. A consistent scheme means a developer who has seen /products can guess /orders without reading any documentation. The rules below are the common agreement of the industry; follow them unless your team has a written reason not to.

The standard shape for one resource

OperationMethod and URLSuccessNotes
ListGET /products200Filter, sort and page with query parameters
Read oneGET /products/{id}200404 if missing
CreatePOST /products201Location header with the new URL
ReplacePUT /products/{id}200 / 204Whole representation in the body
Update partPATCH /products/{id}200Only changed fields in the body
DeleteDELETE /products/{id}204404 if missing

The rules

  1. Use nouns, not verbs. The method already says what to do. POST /products, not /createProduct.
  2. Use plural for collections. /products and /products/42, always plural, even for the single item. A mix of /product and /products is confusing.
  3. Lowercase letters with hyphens. Paths are case-sensitive, so /Products and /products would be different URLs. Hyphens are readable: /order-items, not /order_items or /orderItems.
  4. No trailing slash, no file extension. Not /products/ and not /products.json; the format is chosen by the Accept header. (Spring 6 and later already treats /products/ as a different, unmapped URL.)
  5. Identity goes in the path; options go in the query. /products/42 says which product; ?sort=price says how to show the list.
  6. Nest only when a resource belongs to another. /orders/9/items is fine, because an item cannot exist without its order. Go at most two levels deep. For anything deeper, expose the child directly: /order-items/3/reviews.
  7. Start with a stable prefix and a version. /api/v1/... separates the API from the React app's own routes and leaves room to evolve.
  8. Use ids that you can keep stable. Do not use names or database internals. Sequential numeric ids are easy to guess, so never rely on "nobody knows the id" for security; always check permissions. UUIDs make guessing harder but are not a security control either.

Actions that are not CRUD

Some things are not "create, read, update, delete": cancel an order, send an OTP, transfer money, log in. You have three honest choices, in order of preference.

  1. Model the result as a noun: POST /orders/5/cancellation, POST /payments/9/refunds, POST /accounts/3/transfers. Each call creates something (a cancellation, a refund, a transfer) that you can later read with GET.
  2. Use an action sub-path with POST: POST /orders/5/cancel. This is pragmatic, very common, and acceptable. It breaks the "nouns only" rule on purpose, because there is no good noun.
  3. Top-level action endpoints for things that are not tied to a resource: POST /auth/login, POST /auth/logout, POST /search.

Whichever you choose, use POST, never GET, and say in the docs whether it is idempotent.

@PostMapping("/{id}/cancel")
public OrderResponse cancel(@PathVariable Long id) {
    return orderService.cancel(id);   // 200 with the updated order, or 409 if already shipped
}

Query parameters: what belongs there

PurposeExample
Filtering/products?category=books&inStock=true&maxPrice=500
Free-text search/products?q=wireless+mouse
Sorting/products?sort=price,desc
Paging/products?page=0&size=20
Choosing fields/products?fields=id,name,price
Including related data/products/42?expand=category

All of these are optional and never change which resource you mean. A list URL such as /products?name=mouse always answers with a list (possibly empty); /products/mouse would claim there is one resource named "mouse".

A worked example: a job portal API

The Project 2 job portal fits the rules directly:

RequestPurpose
GET /api/v1/jobs?title=java&location=pune&minSalary=800000&page=0&size=10Search jobs
POST /api/v1/jobsA recruiter posts a job
GET /api/v1/jobs/{id}Job details

Rules for responses that go with the URLs

  • A list endpoint always returns a JSON object or array of the same item shape every time; an empty result is [] or an empty content, not an error.
  • Wrap paged lists in an object ({"content": [...], "page": 0, ...}). A bare array has no room for paging metadata, so adding it later would break every client.
  • Keep the same field names for the same concept across endpoints (id, createdAt).

Conventions

  • One controller class per resource, with the base path on the class (@RequestMapping("/api/v1/products")).
  • Query parameter names are camelCase (minPrice) and match the JSON field names.
  • Boolean fields read as adjectives: active, inStock, not isActive (Jackson turns isActive() into active anyway).
  • Irregular plurals are fine (/people); just be consistent.

Edge cases

  • A path variable cannot contain a slash. An encoded slash (%2F) is rejected by Tomcat by default. Use a query parameter for values such as file paths.
  • Words with special characters in the path must be URL-encoded (/search/c%2B%2B); clients' HTTP libraries usually do it for you.
  • Verbs are acceptable for real actions: /login, /logout, /orders/{id}/cancel, /search.
  • Bulk operations (create 100 items) do not have a standard URL. POST /products/bulk or a POST of an array to the collection are both used; document which one you choose.

Mistake: using the query string to identify a resource

GET /products?id=42 works, but it reads like a filter and returns a list in the minds of most developers. If the URL points to exactly one thing, put the id in the path.

Wrong: id and verb in the query

@GetMapping("/getProduct")
public ProductResponse get(@RequestParam Long id) {
    return service.findById(id);
}

Right: id in the path

@GetMapping("/{id}")
public ProductResponse get(@PathVariable Long id) {
    return service.findById(id);
}

Interview: "Design the URLs for a library / e-commerce system" and "Path variable or query parameter?"

  • Name the resources first (books, members, loans), then give each the collection and item URLs with the standard methods.
  • Show nesting for owned data (/members/{id}/loans), keep it shallow, and put filters, sorting and paging in the query string.
  • Path = identifies a resource; query = refines the view. Query parameters are optional; path variables are not.
  • For actions, explain the trade-off: a noun sub-resource if you can (/loans/{id}/return or /returns), otherwise a clearly named action with POST.

API versioning strategies

Version an API so existing clients keep working while you make breaking changes; the most common way is a version in the URL path (/api/v1/…), with header, media-type and query-parameter versioning as alternatives.

Once other people depend on your API, you cannot change it freely. A mobile app installed on a million phones cannot be updated the day you rename a JSON field. Versioning lets you publish a new, incompatible shape (v2) while the old one (v1) keeps working until its clients have moved.

Breaking and non-breaking changes

You only need a new version for a breaking change. Everything else you can add to the current version.

Breaking — needs a new versionNon-breaking — safe in the same version
Removing or renaming a fieldAdding a new optional response field
Changing a field's type or meaning (price from number to object)Adding a new endpoint
Making an optional request field requiredAdding an optional request field or query parameter
Changing a URL, a status code or the error formatMaking a validation rule more lenient
Tightening validation so that old requests failFixing a bug so the API matches its documentation

This works only if clients are tolerant readers: they ignore response fields they do not know. Tell your API consumers this in the docs. Adding a new value to an enum is a grey area: clients that switch over the values may break, so announce it.

The four strategies

StrategyExampleGoodBad
URI pathGET /api/v2/products/42Visible, easy to test in a browser, easy to route and cache, simple docsPurists say a URL should identify a resource, not a version; every client URL changes
Custom headerX-API-Version: 2Clean URLs; one URL per resourceHidden; harder to try in a browser; caches need Vary; easy to forget
Media typeAccept: application/vnd.shop.v2+jsonMost "pure" REST; versions each representationComplex; weaker tool support; hard to explore
Query parameterGET /products/42?version=2Easy to try; easy to defaultClutters URLs and cache keys; optional parameter that is easy to omit

Some public APIs, such as Stripe's, use date-based versions sent in a header, so each client stays on the behaviour of the day it integrated. For most teams, the URI path is the right default: it is boring, visible and works with every tool.

Implementing path versioning in Spring MVC

Keep one service layer and version only the web layer: the controller and its DTOs. Suppose v2 changes price from a plain number into an object with a currency.

public record ProductResponseV1(Long id, String name, BigDecimal price) {}

public record Money(BigDecimal amount, String currency) {}

public record ProductResponseV2(Long id, String name, Money price, Instant createdAt) {}
@RestController
@RequestMapping("/api/v1/products")
public class ProductControllerV1 {
    private final ProductService service;

    public ProductControllerV1(ProductService service) {
        this.service = service;
    }

    @GetMapping("/{id}")
    public ProductResponseV1 get(@PathVariable Long id) {
        ProductDetails d = service.getDetails(id);          // shared business logic
        return new ProductResponseV1(d.id(), d.name(), d.price());
    }
}

@RestController
@RequestMapping("/api/v2/products")
public class ProductControllerV2 {
    private final ProductService service;

    public ProductControllerV2(ProductService service) {
        this.service = service;
    }

    @GetMapping("/{id}")
    public ProductResponseV2 get(@PathVariable Long id) {
        ProductDetails d = service.getDetails(id);          // the same service call
        return new ProductResponseV2(d.id(), d.name(),
                new Money(d.price(), "INR"), d.createdAt());
    }
}

The other strategies are variations on the mapping attributes you will meet in the mapping annotations article:

// Header versioning: the request must contain "X-API-Version: 2"
@GetMapping(value = "/{id}", headers = "X-API-Version=2")

// Media-type versioning: the request must send Accept: application/vnd.shop.v2+json
@GetMapping(value = "/{id}", produces = "application/vnd.shop.v2+json")

// Query-parameter versioning: the request must end with ?version=2
@GetMapping(value = "/{id}", params = "version=2")

Spring Framework 7 / Spring Boot 4: built-in API versioning

Spring Framework 7, the base of Spring Boot 4, adds first-class support for API versioning. The mapping annotations get a version attribute (for example @GetMapping(path = "/{id}", version = "2")), and you configure once, in the MVC configuration, where the version is read from: a request header, a path segment, a query parameter or a media-type parameter. That replaces the hand-written headers, params and produces tricks above. The configuration API is new, so follow the Spring Framework 7 reference for your exact release. The strategies and trade-offs in this article stay the same, and on Boot 3.x you still use the manual approach.

The lifecycle of a version

  1. Release v2 with documentation of what changed and why.
  2. Keep v1 stable. Fix bugs and security problems only; add nothing new.
  3. Announce deprecation with a date, in the docs and by email. You can also send the Sunset response header (RFC 8594) with the planned end date.
  4. Measure usage per version (a metric tagged with the version). When nobody calls v1 any more, remove it.
  5. Return 410 Gone or a clear error from the removed version for a while instead of a mysterious 404.

Rules

  • Never change an existing version's behaviour in a breaking way. That is the whole point of a version.
  • Version the whole API together (/api/v1/...), not one resource at a time. Mixed versions per resource are painful to document and use.
  • Use whole-number major versions (v1, v2). Minor versions in URLs (v1.1) only multiply the paths.

Conventions

  • Start with /api/v1 from day one, even if v2 never comes; adding a prefix later is itself a breaking change.
  • Support at most two versions at a time. Each live version doubles testing and support.
  • Share services and the database; version controllers and DTOs only.
  • Publish one OpenAPI group per version (OpenAPI article).

Edge cases

  • Missing version with header or parameter versioning: decide the default. Serving the oldest stable version protects old clients; requiring an explicit version avoids guessing.
  • Evolve without versioning where you can: add optional fields, deprecate old ones, and migrate in the "expand then contract" way (add the new field, let clients move, remove the old one later).
  • Internal APIs that you control end to end (one team owns client and server, deployed together) often need no versioning at all.

Mistake: copying the whole stack for every version

Duplicating services and repositories for v2 doubles every bug fix. Put business rules in one service; let each controller only translate between that service and its own DTOs.

Interview: "How do you version a REST API? What counts as a breaking change?"

  • Four options: URI path (most common), custom header, media type (vnd.…+json) and query parameter. Give one pro and one con of each.
  • Breaking: removing or renaming fields, changing types or status codes, adding required inputs. Non-breaking: adding optional fields or endpoints.
  • Version only the web layer; keep one service layer. Deprecate with a timeline, a Sunset header, and usage metrics.
  • Mention that clients should be tolerant readers, and that Spring Framework 7 adds built-in versioning support.

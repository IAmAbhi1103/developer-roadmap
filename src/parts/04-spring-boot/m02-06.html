Pagination, sorting and filtering

Never return a whole table: accept page, size and sort parameters through Spring's Pageable, cap the page size, filter with optional query parameters, and return your own page DTO instead of the raw Page.

A findAll() that works with 20 rows in development will freeze the server and the browser with 2 million rows in production. Pagination returns one slice of the data at a time. Sorting decides the order of rows, which a page needs to be stable. Filtering narrows the rows. Together they make every list endpoint safe and fast. Spring Data and Spring MVC support all three with very little code.

The Pageable parameter

Declare a Pageable parameter on a controller method. Spring MVC fills it from the query string.

@GetMapping
public PageResponse<ProductResponse> list(
        @PageableDefault(size = 20, sort = "name") Pageable pageable) {
    return service.findAll(pageable);
}

curl "http://localhost:8080/api/v1/products?page=2&size=10&sort=price,desc"
curl "http://localhost:8080/api/v1/products?sort=category,asc&sort=name,desc"

Return a page DTO, not the raw Page

If you return Spring Data's Page from a controller, Jackson serializes the implementation class PageImpl with many internal fields (pageable, sort, numberOfElements, …). Spring Data logs a warning that serializing PageImpl as-is gives no guarantee about the stability of the JSON structure: a library upgrade can change what your clients receive. It also exposes entities if you forgot to map. Define your own small record:

public record PageResponse<T>(
        List<T> content,
        int page,
        int size,
        long totalElements,
        int totalPages,
        boolean last) {

    public static <E, T> PageResponse<T> from(Page<E> page, Function<E, T> mapper) {
        return new PageResponse<>(
                page.getContent().stream().map(mapper).toList(),
                page.getNumber(), page.getSize(),
                page.getTotalElements(), page.getTotalPages(), page.isLast());
    }
}

// service
@Transactional(readOnly = true)
public PageResponse<ProductResponse> findAll(Pageable pageable) {
    return PageResponse.from(repository.findAll(pageable), mapper::toResponse);
}

Spring Data's own DTO mode

Since Spring Data 3.3 you can opt in to a stable, documented JSON shape (PagedModel) with @EnableSpringDataWebSupport(pageSerializationMode = EnableSpringDataWebSupport.PageSerializationMode.VIA_DTO). It outputs content and a page object with size, number, totalElements and totalPages. It is a fine choice if you want less code; a hand-written record gives you full control over the names, so many teams keep their own. Both exist in Boot 3.3+ and 4.x.

Sorting safely

Sort names from the URL go straight to the query. An unknown property (sort=salary on Product) throws PropertyReferenceException, which becomes a 500 unless you handle it. A property that is not indexed makes the query slow. Two protections:

  • Whitelist the allowed fields and map public names to entity fields:
private static final Set<String> SORTABLE = Set.of("name", "price", "createdAt");

private Pageable safe(Pageable in) {
    for (Sort.Order o : in.getSort()) {
        if (!SORTABLE.contains(o.getProperty())) {
            throw new BadRequestException("Cannot sort by " + o.getProperty());
        }
    }
    return in;
}
  • Always add a stable tiebreaker such as id. If you sort by price and many rows have the same price, rows can jump between pages. @PageableDefault(sort = {"createdAt", "id"}) or Sort.by("price").and(Sort.by("id")) fixes it.

Filtering with optional query parameters

curl "http://localhost:8080/api/v1/products?category=mouse&maxPrice=1000&q=wire&page=0&size=10"

For one or two fixed filters, derived query methods are enough (findByCategory, findByPriceBetween). When filters are optional and combine freely, use the Specification API: each filter is a small reusable object, and you add only those that were sent. The repository must extend JpaSpecificationExecutor.

public interface ProductRepository
        extends JpaRepository<Product, Long>, JpaSpecificationExecutor<Product> { }

public final class ProductSpecs {
    public static Specification<Product> categoryIs(String category) {
        return (root, query, cb) -> cb.equal(root.get("category"), category);
    }
    public static Specification<Product> priceAtMost(BigDecimal max) {
        return (root, query, cb) -> cb.lessThanOrEqualTo(root.get("price"), max);
    }
    public static Specification<Product> nameContains(String text) {
        return (root, query, cb) ->
                cb.like(cb.lower(root.get("name")), "%" + text.toLowerCase() + "%");
    }
}

// service: combine only the filters that were provided
Specification<Product> spec = Specification.where(null);
if (filter.category() != null) spec = spec.and(ProductSpecs.categoryIs(filter.category()));
if (filter.maxPrice() != null) spec = spec.and(ProductSpecs.priceAtMost(filter.maxPrice()));
if (filter.q() != null)        spec = spec.and(ProductSpecs.nameContains(filter.q()));
Page<Product> page = repository.findAll(spec, pageable);

Specifications, JPQL and the Criteria API are explained in module 3. In the controller, bind filters with a plain record (mapping annotations) plus the Pageable:

@GetMapping
public PageResponse<ProductResponse> search(
        ProductFilter filter,
        @PageableDefault(size = 20, sort = {"name", "id"}) Pageable pageable) {
    return service.search(filter, pageable);
}

Offset paging and its limits; keyset (cursor) paging

The page/size style is offset pagination: SQL LIMIT 20 OFFSET 40000. The database must walk past the first 40,000 rows before returning 20, so deep pages get slower. Also, if rows are inserted while the user browses, items shift and the user sees duplicates or misses some.

Keyset (cursor) pagination asks for "the 20 rows after the last one I saw", using an indexed column:

SELECT * FROM product
WHERE (created_at, id) < (:lastCreatedAt, :lastId)     -- the cursor from the previous page
ORDER BY created_at DESC, id DESC
LIMIT 20;

The API returns a nextCursor token (often a Base64 string with the last created_at and id) and the client sends it back as ?cursor=…. It stays fast on any depth and is stable under inserts, but you cannot jump to "page 37". It suits feeds, logs and infinite scroll. Spring Data has a Scroll API for this (Window and ScrollPosition, Spring Data 3.1+). Offset paging is correct for most business apps; mention keyset when the interviewer asks about millions of rows.

Rules

  • Every list endpoint that can grow is paged, with a maximum page size.
  • Pages are zero-based in Spring: page=0 is the first.
  • Sorting must be deterministic: add a unique tiebreaker.
  • Return your own page DTO, map entities to response DTOs inside the transaction (Page.map).

Mistakes

  • Returning List<Product> from findAll() with no limit.
  • Returning Page<Product> (entities) directly: JSON instability and entity exposure.
  • Letting the client sort by any column, or using LIKE '%text%' on a huge table and wondering about speed (a leading wildcard cannot use a normal index).
  • A Page query with a heavy join fetch: the count query repeats it, or Hibernate pages in memory (warning HHH90003004). Page the parent ids first; see module 3.

Interview angle

"How do you implement pagination in Spring Boot?" Pageable in the controller, Page from the repository, map to a page DTO, cap the size. Then: "Page vs Slice" (count query), "problem with large offsets" (use keyset), and "how do you filter?" (derived queries for simple cases, Specifications for optional combinations).

API documentation with springdoc-openapi and Swagger UI

Add the springdoc starter and your controllers produce an OpenAPI document at /v3/api-docs and an interactive Swagger UI page where anyone can read and try every endpoint.

An API without documentation is a guessing game for the React developer, the mobile team and your future self. OpenAPI (formerly "Swagger spec") is the standard, machine-readable description of a REST API: paths, parameters, request and response schemas, status codes and security. Swagger UI turns that description into a web page with a "Try it out" button. springdoc-openapi is the library that builds the OpenAPI document from your Spring annotations at runtime, so the docs match the code.

Setup

<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>${springdoc.version}</version>
</dependency>

Match springdoc to your Spring Boot version

springdoc releases follow Spring Boot: the 2.x line is for Spring Boot 3.x, and Spring Boot 4 needs the newer springdoc line built for it. Check the version table in the springdoc documentation (springdoc.org) before choosing springdoc.version; a mismatched version fails at startup with confusing NoSuchMethodError or ClassNotFoundException errors. Use springdoc-openapi-starter-webmvc-ui for Spring MVC (the webflux variant is for WebFlux).

Documenting JWT authentication

Once the API is secured with a JWT (module 4), Swagger needs an "Authorize" button that sends the Authorization: Bearer … header. Declare a security scheme and require it:

import io.swagger.v3.oas.annotations.security.SecurityScheme;
import io.swagger.v3.oas.annotations.enums.SecuritySchemeType;

@Configuration
@SecurityScheme(
        name = "bearerAuth",
        type = SecuritySchemeType.HTTP,
        scheme = "bearer",
        bearerFormat = "JWT")
public class OpenApiConfig { /* the OpenAPI bean from above */ }

// on a controller or method that needs a token
@SecurityRequirement(name = "bearerAuth")
@RestController
public class OrderController { ... }

In the UI, click Authorize, paste the token (without the word "Bearer"), and "Try it out" sends it. Remember to allow the docs URLs in your Spring Security configuration (/swagger-ui.html, /swagger-ui/**, /v3/api-docs/**) or Swagger itself gets a 401.

Grouping and versions

For larger APIs, split the documentation by path or package: one group per API version or per audience (public vs admin).

@Bean
GroupedOpenApi publicApi() {
    return GroupedOpenApi.builder().group("public").pathsToMatch("/api/v1/**").build();
}

@Bean
GroupedOpenApi adminApi() {
    return GroupedOpenApi.builder().group("admin").pathsToMatch("/api/admin/**").build();
}

Swagger UI then shows a dropdown with the groups; each has its own /v3/api-docs/{group}.

Rules

  • The starter version must match your Spring Boot line.
  • Documentation must describe DTOs, not entities (another reason for DTOs).

Common problems

  • Swagger page shows "Failed to load API definition" or a 401: security rules block /v3/api-docs.

Interview angle

"How do you document a REST API?" OpenAPI with springdoc: one dependency, /swagger-ui.html and /v3/api-docs, annotate with @Operation, @ApiResponse, @Schema, add the bearer security scheme for JWT, disable it in production. Mention contract-first as the alternative.

Postman

Postman is a GUI client with collections, environments and scripts. The concepts you need:

Request
Method + URL + headers + body, saved with a name.
Collection
A folder of requests, for example "Shop API", grouped into folders (Auth, Products, Orders). One collection per project.
Environment
A named set of variables: local, staging, prod. Each has its own values for the same names.
Variable
Written {{name}} in URLs, headers and bodies. Example: {{baseUrl}}/api/v1/products. Keep secrets in "current value" fields, which are not shared when you export.

JavaScript that runs before a request (pre-request) or after the response (tests).

The usual setup: environment local with baseUrl = http://localhost:8080 and an empty token. The login request has a test script that saves the token. Every other request uses Authorization: Bearer {{token}} (or the collection's Authorization tab, type Bearer Token, value {{token}}, inherited by all requests).

Lombok basics

Lombok is a compile-time tool whose annotations generate getters, setters, constructors, equals, hashCode, toString, builders and loggers, so you write less boilerplate; use it carefully, and not with @Data on JPA entities.

Java classes carry a lot of repeated code: fields, getters, setters, constructors, toString. Lombok is an annotation processor: while javac compiles your class, Lombok adds the methods to the compiled .class file. The source stays short. Many Spring Boot projects use it, so you must be able to read it, even if you prefer records.

Setup

<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <optional>true</optional>
</dependency>

Spring Boot manages the Lombok version, and its Maven plugin keeps Lombok out of the final jar. In the IDE, enable annotation processing (IntelliJ: Settings → Build, Execution, Deployment → Compiler → Annotation Processors → Enable). Current IntelliJ versions include Lombok support; in Eclipse or VS Code install the Lombok plugin or agent. If the code compiles with Maven but the IDE shows "cannot find symbol getName()", annotation processing or the plugin is the cause.

@Data and JPA entities: avoid

Do not put @Data (or @EqualsAndHashCode / @ToString) on JPA entities

  • equals/hashCode on all fields: the generated version includes the id (null until saved) and mutable fields. An entity put in a HashSet and then saved is "lost", because its hash code changed. Hibernate proxies and lazy collections break comparison too.
  • toString touching relationships: it calls getOrders() on a lazy collection (extra queries or LazyInitializationException), and two entities that point to each other cause infinite recursion and StackOverflowError.
  • Setters everywhere let any code put an entity in an invalid state.

Instead use @Getter with a protected no-args constructor (@NoArgsConstructor(access = AccessLevel.PROTECTED)), write equals/hashCode on the id (or a business key) by hand as described in module 3, and exclude relationships from toString.

Lombok vs records

Java recordLombok
Part ofThe language (Java 16+)A library plus compiler plugin

A practical split: records for DTOs, Lombok for the repetitive bits of services and entities (and some teams skip Lombok entirely, which is also fine). Since the modern IDE can generate constructors and getters in a click, Lombok's value is mostly in keeping files short and diffs small.

Conventions

  • Check the team's rules: some codebases ban Lombok or limit it to a few annotations.
  • Prefer specific annotations (@Getter, @RequiredArgsConstructor) over @Data.
  • With MapStruct, add the lombok-mapstruct-binding processor and list Lombok first (DTOs).
  • Use delombok if you ever need to see the generated source.

Interview angle

"What is Lombok and how does it work?" An annotation processor that modifies the compiled classes to add methods; no runtime cost. "Why is @Data dangerous on entities?" Equals/hashCode on mutable or lazy state, toString loops on relationships. Show you know @RequiredArgsConstructor for constructor injection.

Content negotiation, CORS and file uploads (pointers)

Content negotiation lets the client ask for a format through the Accept header; CORS is a browser rule that you configure on the server so a React app on another origin may call your API; file uploads arrive as multipart requests.

Content negotiation

The same resource can have several representations: JSON, XML, CSV. The client states what it can read in the Accept header, and says what it sends in Content-Type. Spring MVC picks an HttpMessageConverter that fits both (request flow). Spring Boot REST apps normally have only the JSON converter, so the result is always JSON.

  • Accept: application/json → JSON. Accept: */* → the default (JSON).
  • Accept: application/xml with no XML converter on the classpath → 406 Not Acceptable (HttpMediaTypeNotAcceptableException).
  • Body sent as text/plain to a JSON-only @RequestBody → 415 Unsupported Media Type.
  • To offer XML too, add jackson-dataformat-xml to the classpath; the converter is registered and clients can ask for either.
  • You can pin a method to one format with produces and consumes (mapping annotations), or give one URL two methods that differ only in produces.
  • Do not use file extensions (/products.json) or a ?format= parameter for negotiation in new APIs; use the headers. Recent Spring versions have removed suffix matching.
curl -i http://localhost:8080/api/v1/products/1 -H "Accept: application/xml"
HTTP/1.1 406

See the header tables in HTTP headers and the versioning-by-media-type idea in API versioning.

CORS in one paragraph

A browser lets a page call another origin (scheme + host + port) only if that server says so. Your React dev server runs on http://localhost:5173 and your API on http://localhost:8080: different ports, so different origins, and the browser blocks the response unless your API sends CORS headers (Access-Control-Allow-Origin and friends), after a preflight OPTIONS request for non-simple calls. CORS is enforced by browsers only; curl and Postman never see it. Configure it on the server, and list exact origins, never * together with credentials. The quick way is @CrossOrigin(origins = "http://localhost:5173") on a controller; the right way for a whole API is one global configuration, and with Spring Security it must be wired into the security filter chain so the preflight is not rejected with 401. The full explanation, the Java configuration and the React side are in Frontend · Module 6; the security wiring is in module 4.

File upload pointer

A file arrives as a multipart/form-data request, and a controller reads it with @RequestPart or a MultipartFile parameter:

@PostMapping(value = "/{id}/image", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public ResponseEntity<Void> uploadImage(@PathVariable Long id,
                                        @RequestPart("file") MultipartFile file) {
    // check size and content type, store the file, save its URL or key
    return ResponseEntity.noContent().build();
}
spring.servlet.multipart.max-file-size=5MB
spring.servlet.multipart.max-request-size=10MB
curl -i -X POST http://localhost:8080/api/v1/products/1/image -F "file=@mouse.png"

Rules for real uploads: limit the size, check the content type and extension against an allow-list, never trust the original file name (path traversal), and store files in object storage such as S3 instead of the app server's disk. Storage choices are covered in module 6. Too-large files give MaxUploadSizeExceededException (a 413 response with a handler).

Auditing fields: createdAt, updatedAt, createdBy

Spring Data JPA auditing fills createdAt, updatedAt and createdBy automatically through an entity listener; put the fields in a @MappedSuperclass so every entity gets them.

Auditing means recording when a row was created or changed and by whom. Writing entity.setCreatedAt(Instant.now()) in every service is repetitive and easy to forget. Two options exist: Spring Data's auditing (portable, supports "who") and Hibernate's own annotations (simpler, time only).

Spring Data JPA auditing

  1. Enable it once with @EnableJpaAuditing on a configuration class.
  2. Add @EntityListeners(AuditingEntityListener.class) to the entity (or to a base class).
  3. Annotate fields with @CreatedDate, @LastModifiedDate, @CreatedBy, @LastModifiedBy.
  4. For the "by" fields, provide an AuditorAware bean that returns the current user.
import org.springframework.data.annotation.*;
import org.springframework.data.jpa.domain.support.AuditingEntityListener;

@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class AuditableEntity extends BaseEntity {

    @CreatedDate
    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    @LastModifiedDate
    @Column(name = "updated_at", nullable = false)
    private Instant updatedAt;

    @CreatedBy
    @Column(name = "created_by", updatable = false)
    private Long createdBy;                        // user id

    @LastModifiedBy
    @Column(name = "updated_by")
    private Long updatedBy;

    public Instant getCreatedAt() { return createdAt; }
    public Instant getUpdatedAt() { return updatedAt; }
}
@Configuration
@EnableJpaAuditing(auditorAwareRef = "auditorProvider")
public class AuditConfig {

    @Bean
    AuditorAware<Long> auditorProvider() {
        return () -> {
            Authentication auth = SecurityContextHolder.getContext().getAuthentication();
            if (auth == null || !auth.isAuthenticated()
                    || auth instanceof AnonymousAuthenticationToken) {
                return Optional.empty();                // system job or anonymous
            }
            return Optional.of(((AppUserDetails) auth.getPrincipal()).getId());
        };
    }
}

The AuditorAware body above assumes Spring Security (module 4) and a principal class that carries the user id. Until security exists, return a fixed id or Optional.empty(). Now Job extends AuditableEntity, and jobRepository.save(job) sets both timestamps on insert, and only updatedAt/updatedBy on update.

insert into job (created_at, created_by, updated_at, updated_by, title, ...) values (?,?,?,?,?,...)
update job set updated_at=?, updated_by=?, vacancies=?, ... where id=?

Notes: the listener runs on persist and on flush when the entity is dirty. Entities modified through bulk @Modifying queries are not audited. Add updated_at = now() to those queries by hand. @EnableJpaAuditing must not be on the main application class if you use @WebMvcTest slices (it would need the JPA metamodel); put it in a separate configuration class as shown.

Conventions

  • Use Instant (UTC) and TIMESTAMPTZ; convert to a zone only for display.
  • Mark createdAt and createdBy as updatable = false.
  • Put the columns in the migration with NOT NULL; set a default for old rows in the migration that adds them.
  • Never expose audit fields as writable in request DTOs.

Mistakes

  • Forgetting @EnableJpaAuditing or @EntityListeners: the fields stay null and the insert fails on NOT NULL.
  • Expecting history. These columns hold only the latest state. For full history use Hibernate Envers or an audit table.
  • An AuditorAware that throws for system jobs; return Optional.empty() instead.

Schema migrations with Flyway in Spring Boot

Flyway runs versioned SQL files (V1__init.sql, V2__...) in order at application startup, records them in flyway_schema_history, and refuses to change a migration that was already applied.

A database schema changes over time: new columns, new tables, new indexes. A migration tool keeps the schema in version control like code, so every environment (your laptop, test, production) reaches the same state by running the same ordered scripts. Without it, teams run SQL by hand and drift apart. Flyway is the simplest and most common choice with Spring Boot (Liquibase is the other popular one). Basics of schema design are in SQL · Module 4.

Setup

<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>   <!-- PostgreSQL support module -->
</dependency>

Recent Flyway versions put database support in separate modules: flyway-database-postgresql for PostgreSQL, flyway-mysql for MySQL and MariaDB. Without it you get an error such as "Unsupported Database: PostgreSQL 17".

Boot 3.x vs 4.x

In Boot 3.x, having flyway-core on the classpath is enough to turn on the auto-configuration. Boot 4 split its auto-configuration into smaller modules; the supported way there is the spring-boot-starter-flyway starter (plus the database module above). Check the Boot 4 migration notes for your exact version.

What happens at startup

  1. Boot creates the DataSource; the Flyway auto-configuration runs before JPA's EntityManagerFactory is created (Boot orders this for you).
  2. Flyway creates the table flyway_schema_history if it does not exist.
  3. It scans classpath:db/migration, compares file names and checksums with the history table.
  4. It validates already applied migrations (checksum unchanged) and runs the pending ones in order, each in a transaction where the database supports transactional DDL (PostgreSQL does; MySQL does not roll back DDL).
  5. Hibernate starts; with ddl-auto=validate it checks that entities match the schema Flyway built.

Baseline: adding Flyway to an existing database

If the database already has tables created by hand or by Hibernate, V1__init.sql would fail with "table already exists". A baseline tells Flyway "treat the current state as version N; only run migrations above N". Dump the current schema into V1__init.sql (for new environments), then on the existing database set spring.flyway.baseline-on-migrate=true and spring.flyway.baseline-version=1. Flyway records version 1 as already applied and runs V2 onwards. Turn the baseline option off afterwards, because on an empty database it would skip V1.

The golden rule: never edit an applied migration

Rule: applied migrations are immutable

Flyway stores a checksum of every applied script. If you edit it later, the next startup fails with FlywayValidateException: Migration checksum mismatch for migration version 2 (the app refuses to start). To change the schema, add a new migration (V4__fix_...sql). Fix a migration freely only while it exists on your branch and has never run anywhere shared. On a dev database you may delete the database and start again. flyway repair fixes checksums but should be a conscious choice, not a habit.

Migrations that are safe in production

  • Add, do not rename. To rename a column on a running system: add the new column, deploy code that writes both, backfill, switch reads, then drop the old column in a later release (expand and contract).
  • Adding a NOT NULL column to a big table needs a default or a backfill first; check lock time.
  • Build large indexes with CREATE INDEX CONCURRENTLY in PostgreSQL (it cannot run inside a transaction; use the per-script non-transactional setting) to avoid blocking writes.
  • Keep one logical change per file, and give constraints and indexes explicit names.
  • Run the whole migration chain on an empty database in CI so mistakes surface before release.

Flyway + ddl-auto=validate

The pairing means: Flyway owns the schema, Hibernate only checks it. If a developer adds a field to an entity and forgets the migration, the app fails at startup with Schema-validation: missing column in dev and CI instead of failing in production on the first query. For tests with Testcontainers PostgreSQL, run the same migrations; avoid H2 with different SQL.

Mistakes

  • Single underscore in V1_init.sql (needs two): the file is ignored or rejected.
  • Putting migrations outside the scanned folder, or in src/test/resources only.
  • Keeping ddl-auto=update next to Flyway: two tools changing the schema.
  • Merging two branches that both created V5__...; rename one before merging.
  • Using application credentials with DDL rights in production; use a separate migration user via spring.flyway.user.

Exceptions

  • FlywayValidateException — checksum mismatch, or a migration missing from the folder that is in the history.
  • FlywayException: Found non-empty schema ... without schema history table — existing database, no baseline.
  • FlywayException: Detected resolved migration not applied to database — an older version appeared after a newer one ran (out-of-order).
  • SQLException in a script — the migration is marked failed. On PostgreSQL it rolls back; on MySQL part of it may remain, requiring manual cleanup.

Interview angle

"How do you manage database changes?" Versioned migrations in source control, run automatically at startup (or in the CI/CD pipeline), history table, checksums, never edit applied scripts, validate in Hibernate. Follow-up: "How to rename a column with zero downtime?" Expand and contract over two releases.

HikariCP: the connection pool

Opening a database connection costs milliseconds (TCP, authentication). A connection pool opens a fixed set once and lends them to requests. Spring Boot uses HikariCP by default. A request borrows a connection when its transaction starts and returns it at the end, so the transaction length decides how long the connection is busy.

Sizing. A database can only do so much in parallel; a small pool (often 10–20 per application instance) usually gives better throughput than a huge one, because extra connections just queue inside the database. Remember the total: instances × pool size must stay below the database's max_connections (PostgreSQL default 100). Many teams tune from monitoring: pool wait time and active connections (see module 1 and the actuator metrics in module 6).

Symptoms of pool problems: HikariPool-1 - Connection is not available, request timed out after 30000ms means all connections are busy, usually because of long transactions, OSIV, a leak, or a slow query, not a pool that is "too small". Fix the cause first.

Batch inserts and updates

Saving 1,000 jobs normally sends 1,000 INSERT statements, each a network round trip. With JDBC batching Hibernate groups them into a few batches.

spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true
  • jdbc.batch_size is the number of statements per batch.
  • order_inserts / order_updates sort statements by entity type so identical statements sit together; without them, saving a parent and its children alternately breaks the batch.
  • The id strategy must allow it: IDENTITY disables insert batching (ID strategies). Use SEQUENCE on PostgreSQL.
  • For PostgreSQL you can add the driver option reWriteBatchedInserts=true to the JDBC URL (multi-row inserts); for MySQL, rewriteBatchedStatements=true.
@Transactional
public void importJobs(List<Job> jobs) {
    int i = 0;
    for (Job job : jobs) {
        em.persist(job);
        if (++i % 50 == 0) {
            em.flush();        // send the batch
            em.clear();        // free memory, stop dirty checking old entities
        }
    }
}

Without clear() the persistence context keeps every entity and the job slows down and may run out of memory. For millions of rows, think about JdbcClient batch updates or the database's bulk loader (COPY) instead.

Interview questions — Data access with Spring Data JPA

What are JPA, Hibernate and Spring Data JPA, and how do they relate?

JPA is a specification: annotations, the EntityManager interface and JPQL. Hibernate is an implementation of that specification; it tracks entities and generates SQL. Spring Data JPA is a layer on top that creates repository implementations from interfaces and calls the EntityManager underneath. You code against Spring Data and JPA; Hibernate does the work.

What is the persistence context, and what are the entity states?

It is the per-transaction first-level cache and identity map that tracks managed entities. States: transient (new, unknown to JPA), managed (tracked; changes saved at flush), detached (has an id, but the context is closed), removed (scheduled for deletion). Within one context a given row is always the same Java object.

What is dirty checking? Why does my update work without calling save()?

Hibernate keeps a snapshot of each managed entity. At flush (before commit) it compares the entity with the snapshot and issues an UPDATE for changes. So inside @Transactional, loading an entity and calling a setter is enough. Without a transaction the entity is detached and the change is lost.

How does save() decide between INSERT and UPDATE?

It calls isNew: a null id (or a null wrapper @Version) means new, so persist; otherwise merge, which first runs a SELECT. With ids that you assign yourself, the id is never null, so every save does a needless SELECT; add a @Version field or implement Persistable.

IDENTITY vs SEQUENCE vs UUID?

IDENTITY lets the database auto-increment; Hibernate must INSERT immediately to learn the id, which disables batching. SEQUENCE asks a database sequence in blocks (allocationSize, default 50), so inserts can be delayed and batched; MySQL lacks sequences. UUID is generated in Java, needs no round trip and is not guessable, but it is larger and random, which hurts index locality.

What does ddl-auto do and what should production use?

It controls schema generation at startup: none, validate, update, create, create-drop. Production uses validate (or none) with Flyway migrations. update cannot rename or drop and leaves no history; create drops all data.

Explain the owning side and mappedBy.

In a bidirectional relationship the owning side is the entity whose table holds the foreign key (the @ManyToOne side). Only changes on the owning side write the FK. The inverse side uses mappedBy = "fieldOnOwner" and is a read-only mirror. So you must set both sides in memory; use helper methods like addJob.

What are the default fetch types and what do you recommend?

ToOne (@ManyToOne, @OneToOne) is EAGER; ToMany is LAZY. Recommendation: make everything LAZY, and load needed data per use case with JOIN FETCH, @EntityGraph, batch fetching or DTO projections. Eager mappings cannot be turned off per query and cause hidden extra queries.

What is the N+1 problem and how do you fix it?

One query loads N parents, then lazy loading fires one query for each parent's relation: 1 + N queries. Detect it with the SQL log, Hibernate statistics or query-count tests. Fix with JOIN FETCH, @EntityGraph, hibernate.default_batch_fetch_size (turns N into N/size), or a DTO projection. Beware of join-fetching a collection with pagination (done in memory) and MultipleBagFetchException.

What causes LazyInitializationException and how do you solve it properly?

A lazy association is read after the session closed, usually in the controller or during JSON serialization. Solve it by mapping to a DTO inside the service transaction, or by fetching the data in the query. Do not make it EAGER and do not rely on Open Session in View; set spring.jpa.open-in-view=false.

How does @Transactional work, and why might it not apply?

Spring wraps the bean in a proxy; the interceptor starts a transaction through the transaction manager, binds the connection to the thread, calls the method and commits or rolls back. It does nothing on self-invocation (this.method() skips the proxy), on private or final methods, or on objects not managed by Spring. It rolls back only for unchecked exceptions and errors unless rollbackFor says otherwise.

REQUIRED vs REQUIRES_NEW vs NESTED?

REQUIRED joins the existing transaction or creates one; a failure anywhere marks the whole thing rollback-only. REQUIRES_NEW suspends the outer transaction and runs independently on another connection (use it for an audit record that must persist even if the caller rolls back). NESTED runs in a savepoint inside the outer transaction, so only the inner part rolls back.

What is UnexpectedRollbackException?

An inner method taking part in the outer transaction threw a runtime exception, which marked the transaction rollback-only. The outer code caught the exception and continued, then tried to commit; Spring throws because the transaction can only roll back. Let the exception propagate, or run the inner call in REQUIRES_NEW or NESTED.

Optimistic vs pessimistic locking?

Optimistic: add a @Version column; the UPDATE includes where version=?, and the loser gets ObjectOptimisticLockingFailureException (return 409, reload, retry). No locks are held. Pessimistic: @Lock(PESSIMISTIC_WRITE) issues SELECT ... FOR UPDATE and others wait; use for heavy contention like stock or seats, with a timeout. For simple counters an atomic update ... set n = n - 1 where n > 0 is enough.

How do you manage schema changes in a Spring Boot project?

Flyway migrations in db/migration (V1__init.sql, V2__...), applied at startup and recorded in flyway_schema_history with checksums. Applied files are never edited; a change is a new file. Hibernate runs with ddl-auto=validate so a missing migration fails fast. Existing databases are adopted with a baseline.

Practice — Data access with Spring Data JPA

  1. Local database (easy). Start PostgreSQL in Docker, connect the Product API from module 2 with environment-variable credentials, and set ddl-auto=validate. Done when the app starts and the Product endpoints still work against the Docker database.
  2. First migration (easy). Write V1__init.sql for company, app_user, job and application (use the SQL in the relationships example as a starting point), add Flyway, and start the app. Done when flyway_schema_history has one row. Then edit V1 on purpose, restart, and read the checksum error.

Caching with @Cacheable, @CachePut and @CacheEvict

Spring's cache abstraction puts a proxy in front of a method so that repeated calls with the same arguments return a stored result; you choose the cache provider separately (a simple map, Caffeine or Redis) and must plan how entries are invalidated.

What and why

A cache keeps the result of expensive work (a slow query, a call to another service) so the next request gets it from memory. The job list page of Project 2 is read thousands of times and changes a few times a day: running the same SQL on every request wastes the database. Caching trades freshness for speed; the hard part is not storing, it is knowing when the stored value is wrong (invalidation). The general theory (cache-aside, write-through, eviction policies) is in System Design · Module 5.

How it works

Like @Transactional, caching is an AOP proxy feature (module 1). Spring wraps your bean; when you call a cached method from another bean, the proxy computes a key from the arguments, looks in the named cache, and calls your method only on a miss.

Setup

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-cache</artifactId>
</dependency>
@SpringBootApplication
@EnableCaching                       // without this, the annotations do nothing
public class JobsApplication {
    public static void main(String[] args) { SpringApplication.run(JobsApplication.class, args); }
}

With no provider on the classpath, Boot uses a simple ConcurrentHashMap cache: good for learning and tests, but it never expires and has no size limit.

The annotations

AnnotationWhat it doesTypical use
@CacheableReturn the cached value if present; otherwise call the method and store the resultReads: findById, search
@CachePutAlways call the method and store the result (no skip)Update: refresh the entry after a change
@CacheEvictRemove one entry (or all with allEntries = true)Delete, or any change that makes entries stale
@CachingCombine several of the above on one methodUpdate that evicts a list and puts an item
@CacheConfigClass-level defaults (cacheNames)Avoid repeating the cache name
 
@Service
@CacheConfig(cacheNames = "jobs")
public class JobService {

    private final JobRepository jobRepository;
    private final JobMapper mapper;

    public JobService(JobRepository jobRepository, JobMapper mapper) {
        this.jobRepository = jobRepository;
        this.mapper = mapper;
    }

    @Cacheable(key = "#id")                              // key = the argument
    @Transactional(readOnly = true)
    public JobResponse getJob(Long id) {
        return mapper.toResponse(jobRepository.findById(id).orElseThrow(
                () -> new ResourceNotFoundException("Job " + id)));
    }

    @CachePut(key = "#id")                               // runs always, refreshes the entry
    @Transactional
    public JobResponse updateJob(Long id, JobRequest request) {
        Job job = jobRepository.findById(id).orElseThrow();
        mapper.update(job, request);
        return mapper.toResponse(job);
    }

    @CacheEvict(key = "#id")
    @Transactional
    public void deleteJob(Long id) {
        jobRepository.deleteById(id);
    }

    @CacheEvict(allEntries = true)                       // clear the whole "jobs" cache
    public void clearAll() { }
}

Keys and SpEL

The default key is built from all method arguments (a single argument is the key itself; several become a SimpleKey; no arguments use a constant). You almost always want to write the key explicitly with SpEL (Spring Expression Language):

@Cacheable(key = "#id")                                   // a parameter by name
@Cacheable(key = "#filter.city + ':' + #filter.page")     // property of a parameter
@Cacheable(key = "T(java.util.Objects).hash(#city, #type)")
@Cacheable(key = "#root.methodName + ':' + #id")          // method name in the key
@Cacheable(key = "#user.id")                              // per-user cache

Parameter names work only if the code is compiled with -parameters (Spring Boot's Maven and Gradle plugins do this) or you use #p0, #a0 for positions. Two arguments that mean the same thing must produce the same key, and different things must never collide: a per-user result with a key that ignores the user would leak one user's data to another.

condition and unless

  • condition is checked before the call and decides whether caching applies at all: @Cacheable(condition = "#id > 0"). If false, the method runs and nothing is read or stored.
  • unless is checked after the call and can veto storing the result; it can use #result: @Cacheable(unless = "#result == null || #result.isEmpty()").

Use unless to avoid caching empty results or errors you do not want to remember. @Cacheable on a method that returns Optional caches the unwrapped value.

@CacheEvict options and @Caching

@Caching(
    put   = { @CachePut(cacheNames = "jobs", key = "#result.id()") },
    evict = { @CacheEvict(cacheNames = "jobList", allEntries = true) }
)
@Transactional
public JobResponse createJob(JobRequest request) { ... }

@CacheEvict(cacheNames = "jobs", key = "#id", beforeInvocation = true)
public void forceReload(Long id) { ... }      // evict even if the method throws

By default eviction happens after a successful call, so a method that throws leaves the cache intact. beforeInvocation = true evicts first. allEntries = true clears the cache; with Redis it can be slow on large caches because it scans keys.

The two cache names pattern: items and lists

A single-item cache (jobs::7) is easy to keep correct. A list or search cache (jobList::Pune:page0) is hard: any new job makes every list stale. Options: keep list caches short-lived (TTL of a minute), evict the whole list cache on any write (allEntries = true), or do not cache lists and cache only single items and expensive aggregates.

Concurrency: sync = true

When a popular entry expires, many requests may miss at once and all hit the database (a cache stampede). @Cacheable(sync = true) makes one thread compute the value while the others wait. It works only with one cache name and is not supported with unless. For Redis it locks per JVM, not across servers.

The self-invocation pitfall

Exactly the same as @Transactional: the call must go through the proxy.

Wrong: same-class call skips the cache

@Service
public class JobService {
    public JobResponse view(Long id) {
        return getJob(id);               // this.getJob(): proxy bypassed, NOT cached
    }
    @Cacheable("jobs")
    public JobResponse getJob(Long id) { ... }
}

Right: call from another bean

@RestController
public class JobController {
    private final JobService jobService;
    @GetMapping("/api/jobs/{id}")
    JobResponse get(@PathVariable Long id) {
        return jobService.getJob(id);    // goes through the proxy: cached
    }
}

Also: only public methods, and the bean must be created by Spring (not new).

Providers: simple, Caffeine, Redis

Caffeine is a high-performance local cache library. Add com.github.ben-manes.caffeine:caffeine next to the cache starter and Boot configures it:

spring:
  cache:
    type: caffeine
    cache-names: jobs, companies                       # fixed set of caches
    caffeine:
      spec: maximumSize=1000,expireAfterWrite=10m      # size limit + TTL

With several application instances, a local cache means each instance has its own copy: after an update on instance A, instance B still serves the old value until its TTL ends. That is acceptable for slowly changing data with a short TTL; for anything stricter use Redis (next article).

What to cache, what not to cache

  • Good candidates: read-heavy data that changes rarely (job categories, company profiles, config), results of expensive calculations, responses of slow third-party APIs.
  • Bad candidates: data that must be exactly current (account balance, stock count), per-user data without the user in the key, huge results, anything cheap to compute, and entities with lazy associations (cache DTOs instead; module 3).
  • Cache DTOs/records, not JPA entities. A cached entity is detached, may have uninitialised lazy fields, and cannot be serialised cleanly.
  • Always set a TTL. It is your safety net if an eviction is missed.

Invalidation strategy

  1. Time-based: every entry expires after a TTL (60 seconds to a few hours). Simple and always works; data may be a little stale.
  2. Event-based: evict or update on every write (@CacheEvict, @CachePut). Fresher, but you must cover every write path (also bulk updates, SQL scripts, other services).
  3. Combine both: evict on writes and keep a TTL as a backstop.

Transactions and caches

Eviction runs when the method returns, which is before the transaction commits if the cache annotation and @Transactional sit on the same method. Another thread can then reload the old row and put the stale value back. For strictness, evict after commit (a @TransactionalEventListener(phase = AFTER_COMMIT)) or accept the short TTL.

Common mistakes

  • Forgetting @EnableCaching and wondering why nothing is cached.
  • Caching without a TTL, so wrong data lives for ever.
  • A key that ignores a parameter (the second page returns the first page).
  • Caching a method that returns a mutable object, then modifying the object (with a local cache you modify the cached instance itself).
  • Caching exceptions or null by accident; use unless.

Edge cases

  • NoSuchCacheException or "Cannot find cache named 'x'": the name is not in spring.cache.cache-names when the list is fixed.
  • @Cacheable on a method with void return caches nothing useful.
  • A key of null (null argument) throws IllegalArgumentException: Null key returned for cache operation.
  • Caches that store null: Caffeine does not by default; Redis can (cache-null-values, default true).

Interview angle

"How does @Cacheable work?" Proxy, key, cache lookup, call on miss. "Why does it not work when I call the method from the same class?" Proxy bypass. "@CachePut vs @Cacheable?" Always run and store vs skip on hit. "How do you avoid stale data?" TTL plus eviction on writes. "Local vs distributed cache?" Caffeine vs Redis trade-offs in the table above.

Redis as a cache: setup, TTL, JSON serialization and RedisTemplate

Add the Redis and cache starters, set spring.cache.type=redis with a TTL, configure JSON serialization so cached values are readable and safe to change, and use StringRedisTemplate directly for counters, locks and other non-cache uses.

What Redis gives you

Redis is an in-memory key-value server. All your application instances talk to the same Redis, so a value cached by one is visible to all, and an eviction on one removes it for all. It is fast (sub-millisecond on a local network), supports TTL on every key, and also offers counters, sets, sorted sets, pub/sub and atomic operations. Keep it for data you can lose: a cache is a copy, the database stays the source of truth. More on Redis internals in SQL · Module 6.

Setup

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-cache</artifactId>
</dependency>
spring:
  data:
    redis:
      host: localhost                  # the service name in Docker Compose, e.g. redis
      port: 6379
      password: ${REDIS_PASSWORD:}     # empty for local development
      timeout: 2s
  cache:
    type: redis
    redis:
      time-to-live: 10m                # default TTL for every cache
      key-prefix: "jobs-api::"
      use-key-prefix: true
      cache-null-values: false
$ docker run -d --name redis -p 6379:6379 redis:7
$ docker exec -it redis redis-cli
127.0.0.1:6379> KEYS *
1) "jobs-api::jobs::7"
127.0.0.1:6379> TTL "jobs-api::jobs::7"
(integer) 583

Use the property spring.data.redis.* on Boot 3.x and 4.x (older Boot 2 used spring.redis.*). The default client is Lettuce, which is thread-safe and works with the connection pooling Boot sets up.

Serialization: the important detail

Redis stores bytes. By default the Spring cache uses JDK serialization, which has three problems: your cached classes must implement Serializable; the stored bytes are unreadable in redis-cli; and a change to the class (a new field) can make old entries fail to deserialize after a deployment. Most projects switch to JSON.

import java.time.Duration;
import org.springframework.cache.annotation.EnableCaching;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.cache.RedisCacheConfiguration;
import org.springframework.data.redis.cache.RedisCacheManager;
import org.springframework.data.redis.connection.RedisConnectionFactory;
import org.springframework.data.redis.serializer.GenericJackson2JsonRedisSerializer;
import org.springframework.data.redis.serializer.RedisSerializationContext.SerializationPair;
import org.springframework.data.redis.serializer.StringRedisSerializer;

@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    RedisCacheConfiguration defaultCacheConfig() {
        return RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofMinutes(10))
                .disableCachingNullValues()
                .serializeKeysWith(SerializationPair.fromSerializer(new StringRedisSerializer()))
                .serializeValuesWith(SerializationPair.fromSerializer(
                        new GenericJackson2JsonRedisSerializer()));
    }

    @Bean
    RedisCacheManager cacheManager(RedisConnectionFactory factory,
                                   RedisCacheConfiguration defaults) {
        return RedisCacheManager.builder(factory)
                .cacheDefaults(defaults)
                .withCacheConfiguration("jobs", defaults.entryTtl(Duration.ofHours(1)))
                .withCacheConfiguration("jobList", defaults.entryTtl(Duration.ofMinutes(1)))
                .build();
    }
}

The per-cache TTL is the main reason to define the manager yourself: categories can live for hours, search results for a minute. GenericJackson2JsonRedisSerializer writes the class name into the JSON (@class) so it can rebuild the right type. Records and immutable DTOs work with Jackson, but they must be deserializable (a record is fine). The stored JSON is readable:

{"@class":"com.example.jobs.job.JobResponse","id":7,"title":"Java Developer",
 "company":"Acme","city":"Pune"}

Version note

Spring Boot 4 moves to Jackson 3, and Spring Data Redis 4 adds serializers for it next to the Jackson 2 ones. The idea above is the same on every version (key serializer = string, value serializer = JSON), but the exact serializer class name differs; check the Spring Data Redis reference for your version before you copy the code. Properties under spring.cache.redis.* do not change.

Rule: cached data is a contract between deployments

During a rolling deploy, old and new application versions share one Redis. If the new version changes a cached class, old entries may not deserialize and every request throws SerializationException. Include a version in the key prefix (jobs-v2::) when you change a cached class, or flush the cache on deployment. Also treat a Redis failure as a cache miss, not an error (below).

If Redis is down

By default a cache error becomes an exception and the request fails, although the database is healthy. For a cache that is only an optimisation, you can register a CacheErrorHandler that logs and continues:

@Configuration
public class CacheErrorConfig implements CachingConfigurer {

    private static final Logger log = LoggerFactory.getLogger(CacheErrorConfig.class);

    @Override
    public CacheErrorHandler errorHandler() {
        return new SimpleCacheErrorHandler() {
            @Override
            public void handleCacheGetError(RuntimeException ex, Cache cache, Object key) {
                log.warn("Cache get failed: {} {}", cache.getName(), key, ex);   // act as a miss
            }
            @Override
            public void handleCachePutError(RuntimeException ex, Cache cache, Object key,
                                            Object value) {
                log.warn("Cache put failed: {} {}", cache.getName(), key, ex);
            }
        };
    }
}

Combine it with a short connection timeout (spring.data.redis.timeout) so a dead Redis does not hang every request for 60 seconds. Circuit breakers for this kind of problem appear in Resilience4j.

RedisTemplate and StringRedisTemplate

The cache abstraction hides Redis. When you want Redis features directly, inject a template. StringRedisTemplate (keys and values are plain strings) is the simplest and the one you will use most; RedisTemplate<K, V> is generic and needs serializers configured.

@Service
public class OtpService {

    private final StringRedisTemplate redis;

    public OtpService(StringRedisTemplate redis) { this.redis = redis; }

    public void store(String email, String otp) {
        redis.opsForValue().set("otp:" + email, otp, Duration.ofMinutes(5));   // SET with TTL
    }

    public boolean verify(String email, String otp) {
        String key = "otp:" + email;
        String saved = redis.opsForValue().get(key);
        if (saved != null && saved.equals(otp)) {
            redis.delete(key);                  // one-time use
            return true;
        }
        return false;
    }

    public long viewCount(Long jobId) {
        Long n = redis.opsForValue().increment("views:job:" + jobId);   // atomic INCR
        return n == null ? 0 : n;
    }
}
Operations objectRedis typeTypical use
opsForValue()StringCache entries, counters, OTP, tokens
opsForHash()HashSmall objects, sessions
opsForList()ListSimple queues, recent items
opsForSet()SetUnique members, "already seen" checks
opsForZSet()Sorted setLeaderboards, sliding-window rate limits

Typical real uses beyond caching: login/OTP tokens with expiry, rate-limit counters (rate limiting), distributed locks, a blacklist of revoked JWTs (module 4), and Spring Session to share HTTP sessions between instances.

Testing with Redis

In tests, run a real Redis with Testcontainers (@ServiceConnection with GenericContainer for Redis, see module 5) instead of mocking it; serialization bugs only show against the real thing. For unit tests that do not care, set spring.cache.type=none.

Common mistakes

  • Leaving JDK serialization on: unreadable values and NotSerializableException for DTOs.
  • No TTL at all: Redis memory grows until it evicts keys or runs out.
  • Running KEYS * on a production Redis (it blocks the single-threaded server); use SCAN.
  • Keeping the only copy of important data in Redis without persistence.
  • Hard-coded host localhost in a container; use the service name from Compose (Compose).

Edge cases

  • RedisConnectionFailureException: Unable to connect to Redis when the server is down or the host is wrong.
  • SerializationException when the stored JSON no longer matches the class.
  • A key with a prefix: allEntries = true deletes only keys that match the cache name prefix, so one cache does not clear another.
  • Redis eviction policy (maxmemory-policy) can drop keys even before their TTL when memory is full.

Interview angle

"How do you set up Redis caching in Spring Boot?" Two starters, spring.cache.type=redis, @EnableCaching, TTL, JSON serializer. "Why not default serialization?" Needs Serializable, unreadable, brittle. "Redis down: what happens?" Add a CacheErrorHandler and timeouts. "Local vs distributed cache?" Consistency across instances. "What else is Redis used for?" OTP, counters, locks, sessions, rate limits.

Scheduled jobs with @Scheduled

Enable scheduling, annotate a no-argument method with fixedRate, fixedDelay or a six-field cron expression, remember that the default scheduler uses one thread, and use a lock such as ShedLock when several instances must run the job only once.

What and why

Some work is not triggered by a user: close expired jobs every night, send a daily digest at 9 am, clear old uploads, retry failed emails. A scheduled job is a method that Spring calls repeatedly on a timetable, inside your application, with no extra tool.

@Configuration
@EnableScheduling                       // switches the feature on
class SchedulingConfig { }

@Component
public class JobExpiryTask {

    private static final Logger log = LoggerFactory.getLogger(JobExpiryTask.class);
    private final JobService jobService;

    public JobExpiryTask(JobService jobService) { this.jobService = jobService; }

    @Scheduled(cron = "0 30 0 * * *", zone = "Asia/Kolkata")     // 00:30 IST every day
    public void closeExpiredJobs() {
        int closed = jobService.closeJobsPastDeadline();
        log.info("Closed {} expired jobs", closed);
    }
}

The annotated method must return void (a returned value is ignored) and take no parameters. The bean can be any Spring component.

Timing options

AttributeMeaningExample
fixedRateStart every N ms, measured from the start of the previous runfixedRate = 60000
fixedDelayWait N ms after the previous run finishedfixedDelay = 30000
initialDelayWait before the first run (with fixedRate/fixedDelay)initialDelay = 10000
cronA calendar expressioncron = "0 0 9 * * MON-FRI"
zoneTime zone for cronzone = "Asia/Kolkata"

Use fixedDelay when runs must never overlap and you want a rest between them (polling a table). Use fixedRate for a steady rhythm, but note that if a run takes longer than the period, the next run starts as soon as the previous ends, because by default runs of the same task never overlap on one scheduler thread. Both accept string forms that read properties or use Duration text: @Scheduled(fixedDelayString = "${app.poll-delay:PT30S}").

@Scheduled(fixedRate = 60_000, initialDelay = 10_000)    // every minute, first after 10 s
void heartbeat() { ... }

@Scheduled(fixedDelayString = "${app.mail.retry-delay:PT5M}")   // 5 minutes after finishing
void retryFailedEmails() { ... }

@Scheduled(cron = "${app.digest.cron}", zone = "Asia/Kolkata")  // cron from configuration
void dailyDigest() { ... }

Spring cron vs Unix cron

Spring's cron has six fields, with seconds first; classic Unix cron has five.

┌──────── second (0-59)
│ ┌────── minute (0-59)
│ │ ┌──── hour (0-23)
│ │ │ ┌── day of month (1-31)
│ │ │ │ ┌ month (1-12 or JAN-DEC)
│ │ │ │ │ ┌ day of week (MON-SUN, or 0-7)
0 0 9 * * MON-FRI        weekdays at 09:00
0 */15 * * * *           every 15 minutes
0 0 2 1 * *              1st of every month at 02:00
0 0 0 * * *              midnight; also written with the macro  @daily  /  "@midnight"

Common surprises: a Unix expression like 0 9 * * 1-5 has five fields and Spring rejects it (IllegalStateException: Encountered invalid @Scheduled method ... cron expression must consist of 6 fields). Without zone, the time zone is the server's, which in a Docker container is usually UTC, so "9 am" silently means 2:30 pm in India. Always set zone. Spring also supports L (last day), # (nth weekday) and macros such as @hourly, @daily.

The single-thread default and a thread pool

By default all @Scheduled methods in the application share one thread (Boot's auto-configured ThreadPoolTaskScheduler has pool size 1). If one job takes ten minutes, every other job waits. Give the scheduler more threads:

spring:
  task:
    scheduling:
      thread-name-prefix: sched-
      pool:
        size: 5                          # default is 1

Even with a pool, one task still does not run concurrently with itself. For truly parallel work, hand the job to an executor (@Async, next article) and keep the scheduled method short. Exceptions: if a scheduled method throws, Spring logs it and the schedule continues (for fixedRate/cron the next run still happens). Catch exceptions yourself to log with context and to avoid half-finished batches.

Running the job only once in a cluster

If you run three instances of the application, every instance runs the scheduled job, so every candidate gets three digest emails. Options:

  • A lock in the database or Redis: ShedLock. A small library; before the job runs, an instance tries to write a lock row. Only the winner runs the job.
  • One dedicated instance (a "worker" profile) runs scheduling; others disable it with a property or profile.
  • An external scheduler (Kubernetes CronJob, Quartz cluster, a cloud scheduler) that triggers an HTTP endpoint or runs a container.
// Table: shedlock(name varchar(64) primary key, lock_until timestamp,
//                 locked_at timestamp, locked_by varchar(255))

@Configuration
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "PT10M")
class SchedulingConfig {
    @Bean
    LockProvider lockProvider(DataSource dataSource) {
        return new JdbcTemplateLockProvider(dataSource);
    }
}

@Scheduled(cron = "0 0 9 * * *", zone = "Asia/Kolkata")
@SchedulerLock(name = "dailyDigest", lockAtMostFor = "PT5M", lockAtLeastFor = "PT1M")
public void dailyDigest() { ... }

lockAtMostFor releases the lock even if the instance crashes; set it longer than the longest normal run. lockAtLeastFor stops a fast job from running again on another instance with a slightly different clock. ShedLock needs a lock provider (JDBC, Redis, Mongo and others) from its own dependencies; check its README for the current artifact names.

Designing good scheduled jobs

  • Idempotent: running twice must not do harm (the job may run twice after a crash or on two instances). Mark processed rows, or select rows with status = 'PENDING'.
  • Batch size: process 100 rows at a time, not a million in one transaction.
  • Log start, end and count, and add a counter or timer metric (Micrometer) so you notice when it stops.
  • Transactions: the scheduled method has no transaction; call a @Transactional service method (from another bean, not this).
  • Make it testable: put the logic in a service and test the service; test the schedule by calling the method directly.
  • Virtual threads: with spring.threads.virtual.enabled=true Boot runs scheduled tasks on virtual threads too (Async).

Programmatic scheduling is possible with TaskScheduler.schedule(runnable, trigger), useful when the schedule comes from the database.

Common mistakes

  • Forgetting @EnableScheduling (nothing runs, no error).
  • A five-field cron, or no time zone.
  • Long job blocking a pool of one, so other jobs are late.
  • Three instances sending three emails.
  • Annotating a method that takes parameters.
  • Calling a @Transactional method of the same class (self-invocation).

Interview angle

"fixedRate vs fixedDelay?" Start-to-start vs end-to-start. "What if the app runs on three servers?" Every instance runs it; use ShedLock, a single worker, or an external scheduler. "Why did my 9 am job run at the wrong time?" Missing zone, server in UTC. "Default number of scheduler threads?" One.

A project that "works on my laptop" is not yet a project that runs well in production. This module is about everything around your business code that makes an application operable: you can see what it is doing (logs, health, metrics), it is fast enough (caching), it does work in the background (scheduling, async), it handles files and email, it calls other APIs safely, and it protects itself from abuse (rate limiting).

Most of these features are a starter dependency plus a few properties, and most are built on the proxy mechanism from module 1, so the same traps repeat (self-invocation, wrong thread, wrong transaction). We use the Project 2 job portal (User, Company, Job, Application) for examples: a resume upload, an email to the recruiter when someone applies, a cached job list and a health endpoint for Docker.

The next module, Microservices and messaging, builds on these: Actuator and Micrometer feed tracing, and RestClient meets Resilience4j.

  • Configure logging with levels, files, JSON output and a correlation id, and know what never to log.
  • Expose health, info and metrics with Actuator, secure it, and write a custom health check and custom metrics.
  • Cache with @Cacheable using Caffeine or Redis, and invalidate correctly.
  • Run scheduled and asynchronous jobs safely, with virtual threads where they help.
  • Upload and download files and send email (HTML, attachments) without security holes.
  • Call other services with RestClient and declarative HTTP clients, with timeouts.
  • Add rate limiting and walk through a production-readiness checklist.

Logging with SLF4J and Logback: levels, files, JSON and MDC

Log through the SLF4J API, let Spring Boot's default Logback do the work, control it with logging.level.* and a few properties, switch to JSON in production, tag every line with a request id using MDC, and never log secrets.

What and why

System.out.println is not logging. A log is a stream of timestamped, levelled events that you can filter, search, ship to a central system and turn up or down without redeploying. When a user says "my application did not go through at 3 pm", the log is often your only evidence.

Java has many logging libraries, so Spring Boot uses a facade. SLF4J is the API you write against (Logger, LoggerFactory); Logback is the implementation that actually writes lines. spring-boot-starter-logging is included by every starter, so logging works with zero setup. Basic Java logging ideas are in Core Java · Module 8.

Writing log statements

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

@Service
public class ApplicationService {

    private static final Logger log = LoggerFactory.getLogger(ApplicationService.class);

    public ApplicationResponse apply(Long jobId, Long userId) {
        log.info("User {} applying to job {}", userId, jobId);   // placeholders, no concatenation
        try {
            // ... save the application
            log.debug("Application saved, id={}", saved.getId());
            return mapper.toResponse(saved);
        } catch (DuplicateResourceException ex) {
            log.warn("Duplicate application: user={}, job={}", userId, jobId);
            throw ex;
        } catch (RuntimeException ex) {
            log.error("Could not save application for user {} job {}", userId, jobId, ex);
            throw ex;                    // the last argument, an exception, prints the stack trace
        }
    }
}

With Lombok you can write @Slf4j on the class and use log directly. Rules for the statements themselves:

  • Use {} placeholders. The message is built only if the level is enabled, so log.debug("x " + big) (which builds the string always) is a small performance bug.
  • Pass the exception as the last argument, without a placeholder, to get the stack trace. log.error("failed: " + ex.getMessage()) throws the stack trace away.
  • Do not log and rethrow the same exception at every layer; you get the same stack trace five times. Log it once, where you handle it (usually the @RestControllerAdvice from module 2).

Log levels

LevelUse it forExample
ERRORThe operation failed and someone should lookDatabase down, unexpected exception
WARNSomething odd, but the app handled itRetry succeeded, deprecated API used, rate limit hit
INFOImportant business events, few per request"Application submitted", startup, job finished
DEBUGDetails for developers, off in productionMethod arguments, decisions taken
TRACEVery fine detailEvery loop iteration, raw payloads

Levels are ordered: setting a logger to INFO prints INFO, WARN and ERROR. Spring Boot's default is INFO for everything. A bad request from a client (validation failure, 404) is not an ERROR in your system; log it at INFO or DEBUG, or not at all. Reserve ERROR for things you would wake up for.

Configuring Logback through properties

Boot's defaults need no XML. Everything below goes in application.yml (or .properties):

logging:
  level:
    root: INFO
    com.example.jobs: DEBUG              # your packages
    org.springframework.web: WARN
    org.hibernate.SQL: DEBUG             # print SQL (see the JPA module)
  file:
    name: logs/jobs-api.log              # also write to a file (path relative to working dir)
  logback:
    rollingpolicy:
      max-file-size: 10MB                # roll over when the file reaches this size
      max-history: 14                    # keep 14 days of archives
      total-size-cap: 1GB
  pattern:
    console: "%d{HH:mm:ss.SSS} %-5level [%X{requestId:-}] %logger{36} - %msg%n"
  group:
    persistence: org.hibernate.SQL, org.springframework.orm.jpa   # one name for many loggers
  • logging.level.<logger> sets the level for a package or class. Loggers form a tree: com.example.jobs also controls com.example.jobs.job.JobService unless that has its own level.
  • logging.file.name (or logging.file.path, which writes spring.log inside that folder) adds a file. Boot rolls files by size and date once you set the logging.logback.rollingpolicy.* properties.
  • logging.pattern.console and logging.pattern.file change the line format. %X{requestId:-} prints a value from the MDC (below), or nothing.
  • logging.group.<name> lets you write logging.level.persistence: DEBUG for several loggers at once.
  • Quick debugging: start with --debug (or debug=true) to see Boot's auto-configuration report. This is not the same as DEBUG for your own code.

You can also change a level of a running application without a restart through the Actuator loggers endpoint (see Actuator).

logback-spring.xml: profiles and rolling files

When properties are not enough, add src/main/resources/logback-spring.xml. Use the name logback-spring.xml, not logback.xml: the "-spring" version is loaded by Spring Boot, so you can use <springProfile> and <springProperty>.

<configuration>
  <include resource="org/springframework/boot/logging/logback/defaults.xml"/>
  <include resource="org/springframework/boot/logging/logback/console-appender.xml"/>

  <springProperty scope="context" name="APP" source="spring.application.name"
                  defaultValue="jobs-api"/>

  <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>logs/${APP}.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
      <fileNamePattern>logs/${APP}-%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
      <maxFileSize>10MB</maxFileSize>
      <maxHistory>14</maxHistory>
      <totalSizeCap>1GB</totalSizeCap>
    </rollingPolicy>
    <encoder>
      <pattern>%d %-5level [%thread] [%X{requestId:-}] %logger{36} - %msg%n</pattern>
    </encoder>
  </appender>

  <springProfile name="dev">
    <root level="INFO"><appender-ref ref="CONSOLE"/></root>
    <logger name="com.example.jobs" level="DEBUG"/>
  </springProfile>

  <springProfile name="prod">
    <root level="INFO">
      <appender-ref ref="CONSOLE"/>
      <appender-ref ref="FILE"/>
    </root>
  </springProfile>
</configuration>

Think about whether you need files at all. In Docker and Kubernetes the standard is: write to the console (stdout) and let the platform collect it. Files and rotation are for plain VM deployments (DevOps · Module 6).

Structured (JSON) logging

Plain text lines are easy for humans but hard for log tools: to search "all errors for user 42" you must parse text. Structured logging writes each event as one JSON object with fields (@timestamp, level, message, traceId, your MDC values), so tools like Loki, Elasticsearch or CloudWatch can filter by field.

logging:
  structured:
    format:
      console: ecs          # also: logstash, gelf
      # file: ecs           # same for the log file
{
  "@timestamp": "2026-11-10T09:15:03.412Z",
  "log.level": "INFO",
  "message": "User 42 applying to job 7",
  "service.name": "jobs-api",
  "log.logger": "com.example.jobs.application.ApplicationService"
}

Version note

Built-in structured logging (logging.structured.format.console) arrived in Spring Boot 3.4 and works the same in 4.x. On older versions you would add a JSON encoder library such as logstash-logback-encoder in logback-spring.xml. The exact field names depend on the format you pick (ECS, Logstash, GELF).

MDC: a request id on every line

The MDC (Mapped Diagnostic Context) is a per-thread map that Logback can print on every line. Put a correlation id (request id) in it at the start of each request, and every log line from that request, from any class, carries the same id. When a user reports a problem, you search for one id and see the whole story.

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.util.UUID;
import org.slf4j.MDC;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class RequestIdFilter extends OncePerRequestFilter {

    private static final String HEADER = "X-Request-Id";

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        String id = request.getHeader(HEADER);
        if (id == null || id.isBlank() || id.length() > 64) {
            id = UUID.randomUUID().toString();
        }
        MDC.put("requestId", id);
        response.setHeader(HEADER, id);          // the client can quote it in a bug report
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.remove("requestId");             // threads are reused: always clean up
        }
    }
}
09:15:03.412 INFO  [a1b2c3d4-...] c.e.jobs.application.ApplicationService - User 42 applying to job 7
09:15:03.430 WARN  [a1b2c3d4-...] c.e.jobs.application.ApplicationService - Duplicate application

Two details matter. First, the MDC is bound to the thread; a new thread (@Async, an executor, a Kafka listener) starts with an empty MDC. Copy it with a TaskDecorator (see Async). Second, if you add Micrometer Tracing later (tracing), it puts traceId and spanId in the MDC for you, and the request id becomes less necessary.

What to log, and what never to log

  • Log: business events with ids (application submitted, job closed), calls to other systems with duration and status, scheduled job start/end with counts, security events (login failed, access denied), and the exception at the place you handle it.
  • Never log: passwords, JWTs, API keys, OTPs, card numbers, Aadhaar/PAN, full email bodies, full request bodies of sensitive endpoints. This is both a security and a legal problem (privacy laws, PCI rules). Log ids, not personal data: userId=42, not the user's phone number.
  • Watch out for: toString() of entities (lazy loading and sensitive fields), Lombok @Data printing a password field, and logging.level.org.springframework.web=DEBUG in production, which can print request details.

Logging in tests

Keep a src/test/resources/application-test.yml with quieter levels so test output is readable. To assert on log output, use the OutputCaptureExtension from Spring Boot (@ExtendWith(OutputCaptureExtension.class), then take a CapturedOutput parameter and check output.getOut()). Prefer asserting on behaviour, and only check logs for things like "secret is not printed". See module 5 for test setup.

Common mistakes

  • String concatenation in log calls, or ex.printStackTrace() (goes to stderr, outside the log).
  • Logging a whole request DTO that contains a password.
  • DEBUG left on in production: slow, huge disk use, and leaks data.
  • Forgetting MDC.remove in finally, so the next request on that thread shows the old id.
  • Logging inside a tight loop (a million lines for one batch). Log a summary.

Edge cases

  • Both logging.file.name and logging.file.path set: name wins.
  • If a second logging library is on the classpath (log4j-slf4j and Logback together), SLF4J prints "multiple bindings" and may pick the wrong one. Exclude one in the build.
  • A logback.xml (without "-spring") is read before Boot starts, so <springProfile> will not work there.
  • Logging cannot fail the request: Logback swallows its own I/O errors (a full disk loses logs, but requests continue).

Interview angle

"SLF4J vs Logback?" Facade vs implementation. "Why placeholders?" No string building when disabled. "How do you trace one request across many log lines?" MDC correlation id in a filter, or tracing ids. "How do you change the log level without restart?" Actuator loggers. "What do you never log?" Secrets and personal data. Mention JSON logs for log platforms.

Spring Boot Actuator: health, info, endpoints and securing them

Add spring-boot-starter-actuator to get ready-made endpoints (health, info, metrics, loggers and more); expose only what you need, secure the rest, and use the liveness and readiness probes for Docker and Kubernetes.

What and why

Actuator adds production endpoints to your application with no code: "is it up?", "what is its version?", "how many requests failed?", "what is the log level?". Load balancers, Docker, Kubernetes and monitoring tools call these endpoints. Without a health endpoint, your platform can only guess whether the application works.

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

With the starter alone, only /actuator/health is exposed over HTTP (and it shows just {"status":"UP"}). The other endpoints exist but are hidden for safety, because some of them (env, heapdump) reveal sensitive data.

The main endpoints

EndpointWhat it shows or doesRisk
healthUP/DOWN of the app and its parts (database, disk, Redis...)Low (details can leak)
infoApp name, version, git commit, build timeLow
metricsMicrometer metric names and values (JVM, HTTP, pool)Medium
prometheusAll metrics in Prometheus text format (needs the Prometheus registry)Medium
loggersList and change log levels at runtimeMedium (writeable)
envProperties and environment (values of secrets are masked by default, not always)High
mappingsAll URL mappingsMedium
beansAll Spring beansMedium
conditionsWhy each auto-configuration did or did not applyLow
threaddumpStack of every thread (find deadlocks and stuck requests)High
heapdumpDownloads a JVM heap dump, which contains everything in memoryVery high

Exposure settings

Every endpoint has two switches: enabled and exposed (over HTTP or JMX). You choose what is exposed:

management:
  endpoints:
    web:
      exposure:
        include: health, info, metrics, prometheus, loggers   # list what you need
        # exclude: heapdump, env
        # include: "*"                                         # everything: dev only
      base-path: /actuator                                     # default
  endpoint:
    health:
      show-details: when-authorized      # never | when-authorized | always
      probes:
        enabled: true                    # adds /actuator/health/liveness and /readiness
  server:
    port: 9090                           # optional: serve actuator on a separate port

A separate management port (management.server.port) is a strong, simple protection: do not publish port 9090 to the internet, only to your monitoring network. Your gateway or Nginx only forwards the API port.

Securing Actuator

If Spring Security is on the classpath, actuator endpoints are protected by your filter chain like any URL. The rule is: health (and the probes) open or limited to the platform, everything else for an admin role.

@Bean
SecurityFilterChain actuatorChain(HttpSecurity http) throws Exception {
    http.securityMatcher(EndpointRequest.toAnyEndpoint())          // only actuator URLs
        .authorizeHttpRequests(auth -> auth
            .requestMatchers(EndpointRequest.to("health", "info")).permitAll()
            .anyRequest().hasRole("ADMIN"))
        .httpBasic(Customizer.withDefaults());
    return http.build();
}

Put this chain before your main API chain with @Order(1), or merge the rules into your existing chain. Prometheus scrapers usually use a separate port or a basic-auth user. Rule of thumb: health may be public; env, heapdump, threaddump, loggers must never be.

Health in depth

The health endpoint combines many health indicators. Boot adds them automatically when the related library is present: db (runs a validation query on your DataSource), diskSpace, redis, mail, rabbit, and so on. The overall status is the worst one: if the database is DOWN, the app is DOWN (HTTP 503).

{
  "status": "UP",
  "components": {
    "db":        { "status": "UP", "details": { "database": "PostgreSQL" } },
    "diskSpace": { "status": "UP", "details": { "free": 91234816000, "threshold": 10485760 } },
    "ping":      { "status": "UP" }
  }
}

Liveness and readiness probes

Orchestrators ask two different questions, and Boot answers both when management.endpoint.health.probes.enabled=true (it is on automatically when Boot detects Kubernetes):

  • Liveness (/actuator/health/liveness): "Is the process broken beyond repair?" If it fails, the platform restarts the container. Keep it simple: it should not check the database, or a database outage would restart every pod and make things worse.
  • Readiness (/actuator/health/readiness): "Can it accept traffic now?" If it fails, the platform stops sending requests but does not restart. It goes OUT_OF_SERVICE during startup and during graceful shutdown.

You can define your own health groups that pick specific indicators, for example a group the Docker healthcheck uses:

management:
  endpoint:
    health:
      group:
        readiness:
          include: readinessState, db, redis       # DB and Redis needed to serve traffic
        liveness:
          include: livenessState

A custom HealthIndicator

Add your own check by implementing HealthIndicator; the bean name (minus "HealthIndicator") becomes the component name. Example: is the resume storage folder writeable?

import java.nio.file.Files;
import java.nio.file.Path;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.actuate.health.Health;
import org.springframework.boot.actuate.health.HealthIndicator;
import org.springframework.stereotype.Component;

@Component("storage")                         // shows as components.storage
public class StorageHealthIndicator implements HealthIndicator {

    private final Path root;

    public StorageHealthIndicator(@Value("${app.upload-dir}") Path root) {
        this.root = root;
    }

    @Override
    public Health health() {
        if (Files.isWritable(root)) {
            return Health.up().withDetail("path", root.toString()).build();
        }
        return Health.down().withDetail("path", root.toString())
                .withDetail("reason", "not writable").build();
    }
}

Keep indicators fast (they run on each call, and the platform may call every few seconds). Do not call a slow external API from one; if you must, cache the result.

The info endpoint: build and git information

The info endpoint answers "which version is running?" You can feed it from properties, the build, and git:

<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <executions>
        <execution>
            <goals><goal>build-info</goal></goals>   <!-- creates META-INF/build-info.properties -->
        </execution>
    </executions>
</plugin>
management:
  info:
    env:
      enabled: true          # show properties that start with "info."
    git:
      mode: simple           # needs git.properties (git-commit-id plugin)
info:
  app:
    name: Jobs API
    owner: platform-team

With the git-commit-id Maven plugin generating git.properties, info shows the commit id and branch, which is gold when you ask "is the fix deployed?".

Changing log levels at runtime

The loggers endpoint lets you raise one logger to DEBUG on a live system, find the problem, then put it back, with no restart:

$ curl -s localhost:8080/actuator/loggers/com.example.jobs.application
{"configuredLevel":null,"effectiveLevel":"INFO"}

$ curl -X POST localhost:8080/actuator/loggers/com.example.jobs.application \
       -H 'Content-Type: application/json' -d '{"configuredLevel":"DEBUG"}'

$ curl -X POST localhost:8080/actuator/loggers/com.example.jobs.application \
       -H 'Content-Type: application/json' -d '{"configuredLevel":null}'     # reset

The change is in memory only; it is lost on restart. This is why loggers must be admin-only.

Rules

  • Expose only the endpoints you use. Never expose env, heapdump or threaddump publicly.
  • Liveness must not depend on external systems; readiness may.
  • Do not put secrets into info or health details.

Common mistakes

  • include: "*" copied from a tutorial into production.
  • Using /actuator/health (with the DB check) as the liveness probe, so a short database outage restarts all pods.
  • A Docker healthcheck that calls an endpoint behind authentication, so the container is "unhealthy" forever.
  • Forgetting that show-details: always leaks database names and paths on a public URL.

Exceptions and edge cases

  • A DOWN health returns HTTP 503, not 200 with a body saying DOWN. Docker or Kubernetes probes use the status code.
  • With a separate management port, Spring Security rules for the main port do not apply to it; protect it by the network.
  • Boot 3 and 4 both read management.endpoints.web.exposure.*; JMX exposure has different defaults (JMX is off unless enabled).

Interview angle

"What is Actuator?" Production-ready endpoints. "Liveness vs readiness?" Restart vs stop sending traffic. "How do you secure it?" Expose few endpoints, separate port, role-based access. "How do you add a custom check?" Implement HealthIndicator. "How do you find which version is deployed?" The info endpoint with build and git info.

Metrics with Micrometer and the Prometheus endpoint

Micrometer is the metrics facade inside Spring Boot: it records JVM, HTTP and pool metrics automatically, you add your own counters, timers and gauges through MeterRegistry, and Prometheus scrapes them from /actuator/prometheus.

What and why

Logs tell you what happened in one request. Metrics are numbers over time: requests per second, error rate, 95th percentile latency, heap used, database connections in use. They answer "is the system healthy right now, and is it getting worse?" and they drive alerts and dashboards.

Micrometer is to metrics what SLF4J is to logging: a facade. You write code against Micrometer, and a registry for your monitoring system (Prometheus, Datadog, CloudWatch...) turns it into that system's format. With Actuator you already get many metrics:

  • jvm.memory.used, jvm.gc.pause, jvm.threads.live
  • http.server.requests (count, total time and max, tagged by method, URI, status, outcome)
  • hikaricp.connections.active, hikaricp.connections.pending
  • system.cpu.usage, process.uptime, logback.events, cache metrics for caches that expose stats
$ curl -s localhost:8080/actuator/metrics | head -c 120
{"names":["application.ready.time","hikaricp.connections.active", ...

$ curl -s "localhost:8080/actuator/metrics/http.server.requests?tag=status:500"
{"name":"http.server.requests","baseUnit":"seconds","measurements":[
 {"statistic":"COUNT","value":3.0},{"statistic":"TOTAL_TIME","value":0.41}, ...

Meter types

TypeMeaningExample
CounterA value that only goes upApplications submitted, emails sent, errors
GaugeA value that goes up and down; read when scrapedQueue size, open jobs, cache size
TimerCount and duration of short events, with percentilesTime to send an email, time of a job run
DistributionSummaryDistribution of non-time valuesUploaded file size

Custom metrics with MeterRegistry

Inject MeterRegistry (Boot provides it) and create meters. Names use dots (jobs.applications.submitted); each registry converts them to its own style (Prometheus: jobs_applications_submitted_total).

import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;
import org.springframework.stereotype.Component;

@Component
public class ApplicationMetrics {

    private final Counter submitted;
    private final Timer emailTimer;

    public ApplicationMetrics(MeterRegistry registry, JobRepository jobRepository) {
        this.submitted = Counter.builder("jobs.applications.submitted")
                .description("Applications submitted by candidates")
                .tag("source", "web")
                .register(registry);

        this.emailTimer = Timer.builder("jobs.email.send")
                .description("Time to send one email")
                .publishPercentileHistogram()          // allows percentiles in Prometheus
                .register(registry);

        Gauge.builder("jobs.open", jobRepository, repo -> repo.countByStatus(JobStatus.OPEN))
                .description("Jobs currently open")
                .register(registry);                   // read on every scrape: keep it cheap
    }

    public void applicationSubmitted() { submitted.increment(); }

    public <T> T timeEmail(java.util.function.Supplier<T> work) {
        return emailTimer.record(work);                // records duration, returns the result
    }
}

Use it from a service: metrics.applicationSubmitted();. A gauge keeps only a weak reference to the object it observes, so keep a reference (a bean, as here) or the gauge may report NaN after garbage collection.

Rule: keep tag values low-cardinality

Every unique combination of tag values creates a new time series in memory and in Prometheus. Tags like status, method, outcome are fine. A tag with a user id, an email or a full URL with ids creates millions of series and can bring the monitoring system down. For ids, use logs or traces, not metric tags.

@Timed and @Observed (brief)

To time a method without writing the Timer code, use @Timed("jobs.search"). For controllers Boot already times every request, but for ordinary beans you must register the aspect once (it needs spring-boot-starter-aop or the AOP libraries on the classpath):

@Configuration
public class MetricsConfig {
    @Bean
    TimedAspect timedAspect(MeterRegistry registry) {
        return new TimedAspect(registry);
    }
}

@Service
public class JobSearchService {
    @Timed(value = "jobs.search", description = "Job search time", histogram = true)
    public Page<JobResponse> search(JobFilter filter, Pageable pageable) { ... }
}

Like all proxy-based annotations, it does not work on self-invocation (module 1). Micrometer's Observation API (@Observed) goes one step further: one annotation produces both a timer and a trace span, which we use in distributed tracing.

The Prometheus endpoint

Prometheus is a monitoring system that pulls: every few seconds it calls /actuator/prometheus on each application, stores the numbers, and Grafana draws graphs from it. To enable it, add the registry and expose the endpoint:

<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
    <scope>runtime</scope>
</dependency>
management:
  endpoints:
    web:
      exposure:
        include: health, info, prometheus
  metrics:
    tags:
      application: ${spring.application.name}      # added to every metric: filter by app
    distribution:
      percentiles-histogram:
        http.server.requests: true                 # latency histogram for p95/p99 in Grafana
# HELP jobs_applications_submitted_total Applications submitted by candidates
# TYPE jobs_applications_submitted_total counter
jobs_applications_submitted_total{application="jobs-api",source="web"} 17.0
http_server_requests_seconds_count{method="GET",status="200",uri="/api/jobs"} 412.0
jvm_memory_used_bytes{area="heap",id="G1 Eden Space"} 5.2428800E7

The Prometheus side is one scrape config (job name, metrics_path: /actuator/prometheus, target host:port). Setting up Prometheus, Grafana and alert rules belongs to DevOps · Module 6.

The four golden signals

A useful first dashboard has four graphs, all available from the metrics above: latency (p95 of http.server.requests), traffic (requests per second), errors (share of status 5xx), and saturation (CPU, heap, Hikari connections pending, thread pool queue). Alert on symptoms users feel (errors, latency), not on every internal number.

Common mistakes

  • High-cardinality tags (user id, raw URL) that explode the number of series.
  • Creating a new Counter on every call without caching it; building meters is cheap but not free. Create once, increment many times (or use registry.counter(name) which looks it up).
  • Exposing /actuator/prometheus publicly. It reveals internals; put it on the management port or behind auth.
  • Heavy database queries inside a gauge supplier; it runs on every scrape.

Tip

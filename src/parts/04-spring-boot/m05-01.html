Code that is not tested is code you are afraid to change. In a real job you do not get to say "it works on my machine": a pull request is merged only when the tests pass, and reviewers expect tests next to every new service and endpoint. Testing is also one of the most common interview topics for Spring Boot developers, and one of the first things that separates a job-ready developer from a tutorial follower.

This module teaches testing the way Spring Boot projects do it: fast unit tests with JUnit 5, Mockito and AssertJ; slice tests that load only one layer (@WebMvcTest, @DataJpaTest); full @SpringBootTest integration tests; and Testcontainers, which runs a real PostgreSQL in Docker so tests behave like production. It also covers coverage with JaCoCo and what makes a test good. The examples test Project 2 (REST, JPA, Security) and finish with the goal "Project 2 passes all its tests with mvn test".

After this module you will be able to:

  • Choose the right kind of test (unit, slice, integration) for each layer and name and structure tests clearly.
  • Write unit tests with JUnit 5, Mockito (@Mock, @InjectMocks, when, verify, ArgumentCaptor) and AssertJ.
  • Test controllers with @WebMvcTest and MockMvc, including validation errors and secured endpoints.
  • Test repositories with @DataJpaTest and integration flows with @SpringBootTest.
  • Run tests against a real PostgreSQL with Testcontainers and @ServiceConnection.
  • Measure coverage, run tests in Maven and CI, and avoid flaky tests.

Why test: the testing pyramid, structure and naming

Tests give you the confidence to change code; write many fast unit tests, fewer slice tests, a few integration tests and very few end-to-end tests, and keep every test in Arrange-Act-Assert shape with a name that says what is expected.

Why write tests

  • Catch bugs early. A failing test on your laptop costs minutes; the same bug in production costs a night.
  • Refactor safely. With tests you can restructure a service and know within seconds whether behaviour changed.
  • Documentation that runs. A test named apply_whenJobClosed_throwsConflict states a business rule and never goes out of date.
  • Design pressure. Code that is hard to test (static calls, new everywhere, huge methods) is usually badly designed. Constructor injection from module 1 makes testing easy.
  • CI gate. The pipeline runs the tests on every push (DevOps · Module 4).

The testing pyramid

LevelWhat is loadedSpeedTest in a Spring Boot app
UnitOne class, collaborators mocked, no SpringMillisecondsServices (business rules), mappers, validators, utilities
SlicePart of the context: web layer or JPA layer onlyUnder a second to a few secondsControllers (status, JSON, validation, security) and repositories (queries)
IntegrationWhole context, real database (Testcontainers)SecondsKey flows: register, login, post job, apply; Flyway migrations; transactions
End-to-endDeployed app, real browser or API clientSlowestA handful of critical user journeys (Playwright, Cypress); not in this module

The shape matters because tests higher up are slower, need more setup, and fail for more reasons. A pyramid turned upside down (hundreds of end-to-end tests, few unit tests) gives a suite that takes an hour and fails randomly. Put each check at the lowest level that can prove it: a price calculation is a unit test; "an unauthenticated call returns 401" is a slice test; "this query works on PostgreSQL" needs a real database.

Arrange-Act-Assert (Given-When-Then)

Every test has three parts: Arrange (prepare data and mocks), Act (call the one thing under test), Assert (check the result). BDD people call it Given-When-Then; it is the same idea. Separate the parts with a blank line or a comment.

@Test
void applyFee_forPremiumJob_addsTwoPercent() {
    // Arrange (given)
    var calculator = new FeeCalculator();
    var job = JobTestData.premiumJob(100_000);

    // Act (when)
    long fee = calculator.feeFor(job);

    // Assert (then)
    assertThat(fee).isEqualTo(2_000);
}

Rules: one behaviour per test; at most one "Act" call; no if or loops in the test body (a test with logic needs its own test).

Naming

The test name should tell what failed without opening the file. Two common styles:

  • methodName_condition_expectedResult: update_whenNotOwner_throwsAccessDenied
  • shouldDoXWhenY: shouldRejectApplicationWhenJobIsClosed

Pick one per project. Add @DisplayName("...") if the team prefers sentences in reports. Name classes JobServiceTest (unit), JobControllerTest (web slice), JobRepositoryTest (JPA slice) and JobFlowIT (integration, see the Failsafe note in the Maven article).

Folder structure

The test tree mirrors the main tree, so a class and its test are in the same package (this also lets tests use package-private members):

Versions

Each Spring Boot release manages the versions of JUnit, Mockito and AssertJ, so you normally never write their version numbers. Newer Boot lines ship newer JUnit Jupiter releases, but the annotations in this module stay the same. Boot 4 also reorganised the test support into smaller modules and moved some test annotations to new packages (for example @WebMvcTest and @DataJpaTest); the annotation names are unchanged, so let the IDE fix imports and check the release notes of your version.

Common mistakes

  • Making every test a @SpringBootTest. The suite becomes slow, and nobody runs it.
  • Testing getters and setters, or the framework itself, for coverage numbers.
  • Tests that depend on the order of other tests or on leftover data.
  • A test named test1, or one test that checks ten things.

JUnit 5 essentials for Spring developers

JUnit 5 gives you @Test, lifecycle hooks, @DisplayName, @Nested groups, parameterized tests and assertThrows; Spring Boot projects need just these plus AssertJ.

JUnit 5 (also called JUnit Jupiter) is the test framework behind spring-boot-starter-test. A test method is any method annotated @Test. Test classes and methods need no public modifier; package-private is the convention. For core Java background on JUnit see Core Java · Module 8.

    }

What is inside "JUnit 5"

JUnit 5 is not one library but three parts. Knowing them explains many dependency questions.

JUnit Platform
The launcher that finds and runs tests. Maven Surefire, Gradle and IDEs talk to the Platform, not to your tests directly.
JUnit Jupiter
The new programming model (@Test, @BeforeEach, assertions, extensions in the package org.junit.jupiter.api) and its test engine.
JUnit Vintage
An engine that runs old JUnit 3 and 4 tests on the Platform. Boot's starter no longer includes it by default, so an old org.junit.Test is simply not found.

spring-boot-starter-test bundles Jupiter, AssertJ, Mockito, Hamcrest, JsonPath and the Spring test support, so you add one dependency with test scope and nothing else (testing overview).

Lifecycle annotations

AnnotationRunsTypical use
@BeforeEachBefore every test methodCreate the object under test, reset data
@AfterEachAfter every test methodClean up files or static state
@BeforeAllOnce before all tests; method must be staticStart an expensive shared resource
@AfterAllOnce after all tests; staticStop it

JUnit creates a new instance of the test class for every test method, so instance fields are never shared between tests: that is what keeps tests independent. (@TestInstance(Lifecycle.PER_CLASS) changes this and lets @BeforeAll be non-static; avoid it unless needed.) The order for one test is: @BeforeAll once, then for each test @BeforeEach, the test, @AfterEach, and finally @AfterAll once.

class LifecycleDemoTest {
    @BeforeAll static void beforeAll() { System.out.println("beforeAll"); }
    @BeforeEach void beforeEach()      { System.out.println("  beforeEach"); }
    @Test void a()                     { System.out.println("    test a"); }
    @Test void b()                     { System.out.println("    test b"); }
    @AfterEach void afterEach()        { System.out.println("  afterEach"); }
    @AfterAll static void afterAll()   { System.out.println("afterAll"); }
}

JUnit runs test methods in a deterministic but intentionally not obvious order. Never depend on it. If you really need an order (rare, mostly for slow end-to-end flows), add @TestMethodOrder(MethodOrderer.OrderAnnotation.class) and @Order(1) on the methods.

@DisplayName, @Nested, @Disabled, @Tag

@DisplayName("ApplicationService")
class ApplicationServiceTest {

    @Nested
    @DisplayName("apply()")
    class Apply {

        @Test
        @DisplayName("saves an application for an open job")
        void openJob_savesApplication() { ... }

        @Test
        @DisplayName("rejects a second application to the same job")
        void duplicate_throwsConflict() { ... }
    }

    @Nested
    class Withdraw {
        @Test void byOwner_marksWithdrawn() { ... }

        @Disabled("fails until JIRA-123 is fixed")
        @Test void byOtherUser_isForbidden() { ... }
    }
}
  • @Nested inner classes group tests per method or per scenario; the reports show the tree. An outer @BeforeEach runs before each nested test.
  • @Disabled("reason") skips a test; always give a reason and a ticket. A disabled test is a debt.
  • @Tag("slow") labels tests; run only some with Maven: mvn test -Dgroups=fast or exclude with -DexcludedGroups=slow.
  • @Timeout(2) fails a test that takes longer than 2 seconds.
  • @DisplayNameGeneration(DisplayNameGenerator.ReplaceUnderscores.class) on the class turns saves_application into "saves application" in reports, so you can skip @DisplayName on every method.

Parameterized tests

One test body, many inputs. Needs the junit-jupiter-params module, already included in the starter.

@ParameterizedTest
@ValueSource(strings = {"", " ", "ab", "not-an-email"})
void isValidEmail_forBadInput_returnsFalse(String input) {
    assertThat(EmailValidator.isValid(input)).isFalse();
}

@ParameterizedTest(name = "{0} years -> {1}")
@CsvSource({
        "0, JUNIOR",
        "2, JUNIOR",
        "3, MID",
        "8, SENIOR"
})
void levelFor_experience(int years, Level expected) {
    assertThat(Level.forYears(years)).isEqualTo(expected);
}

@ParameterizedTest
@MethodSource("invalidSalaryRanges")
void create_withInvalidRange_isRejected(int min, int max) {
    assertThatThrownBy(() -> new SalaryRange(min, max))
            .isInstanceOf(IllegalArgumentException.class);
}

static Stream<Arguments> invalidSalaryRanges() {
    return Stream.of(
            Arguments.of(100, 50),
            Arguments.of(-1, 10),
            Arguments.of(0, 0));
}

@ParameterizedTest
@EnumSource(value = Role.class, names = {"CANDIDATE", "RECRUITER"})
void selfRegistration_isAllowedFor(Role role) { ... }

The test name template {0}, {1} shows the arguments in the report. The factory method for @MethodSource is static (unless PER_CLASS). Also available: @NullSource, @EmptySource, @CsvFileSource. For a factory in another class, give the full name: @MethodSource("com.example.Data#cases"). Each row runs as its own test, so one bad row does not hide the others.

Testing exceptions and grouping assertions

import static org.junit.jupiter.api.Assertions.*;

@Test
void divide_byZero_throws() {
    ArithmeticException ex = assertThrows(ArithmeticException.class,
            () -> calculator.divide(1, 0));
    assertEquals("/ by zero", ex.getMessage());      // expected FIRST, then actual
}

@Test
void response_hasAllFields() {
    var r = service.getJob(7L);
    assertAll("job response",                        // all failures are reported
            () -> assertEquals(7L, r.id()),
            () -> assertEquals("Java Developer", r.title()),
            () -> assertTrue(r.open()));
}

JUnit's assertEquals(expected, actual) takes the expected value first; swapping them gives confusing failure messages. AssertJ (next articles) reads better and is the usual choice in Spring projects. assertThrows passes only if the thrown exception is the given type or a subtype, and it returns the exception so you can check the message.

JUnit assertionUseFailure
assertEquals, assertNotEqualsValues equal or notAssertionFailedError with expected and actual
assertTrue, assertFalseA boolean conditionAssertionFailedError
assertNull, assertNotNullNull checksAssertionFailedError
assertThrowsAn exception is thrownFails if nothing, or another type, is thrown
assertAllSeveral checks togetherMultipleFailuresError lists every failing check
assertTimeoutCode finishes in timeFails if too slow

JUnit with Spring: extensions

JUnit 5 replaced the single "runner" of JUnit 4 with extensions; you can use several at once. Two matter in Spring work:

  • @ExtendWith(MockitoExtension.class) creates @Mock and @InjectMocks fields for a plain unit test, with no Spring at all (Mockito). This is the fastest kind of test.
  • SpringExtension loads the Spring context and injects beans into the test. You normally do not write it: @SpringBootTest, @WebMvcTest and @DataJpaTest already include it (SpringBootTest).
@ExtendWith(MockitoExtension.class)
class JobServiceTest {
    @Mock JobRepository jobRepository;
    @InjectMocks JobService jobService;
    @Test void find_missing_throws() { ... }
}

@SpringBootTest
class JobRepositoryIT {
    @Autowired JobRepository jobRepository;     // injected by SpringExtension
    @Test void contextLoads() { assertThat(jobRepository).isNotNull(); }
}

JUnit 5 also lets a test constructor or method take parameters. Spring supplies beans for them, and JUnit supplies built-in ones such as @TempDir Path dir (a temporary folder deleted after the test), TestInfo and RepetitionInfo. A parameter nobody can resolve fails with ParameterResolutionException.

Rules

  • Test methods must not be private or static, and must return void.
  • @BeforeAll / @AfterAll must be static in the default lifecycle.
  • Do not mix JUnit 4 (org.junit.Test, @RunWith) and JUnit 5 (org.junit.jupiter.api.Test) imports; a test with the wrong @Test is silently not run. Use @ExtendWith instead of @RunWith.
  • Name test classes so the build finds them: Surefire runs *Test, Test* and *Tests; integration tests named *IT go to Failsafe (Maven setup).

Conventions

  • Name the test class after the class under test (OrderServiceTest) and methods as method_condition_result or with @DisplayName (naming).
  • One logical behaviour per test, and the arrange-act-assert shape with blank lines between the parts.
  • Prefer parameterized tests over copy-pasted tests that differ only in the data.
  • Put the test in the same package as the class, so package-private code is reachable.

Common mistakes

  • Relying on test order or on state left by another test. Each test must set up its own data.
  • Catching an exception with try/catch and forgetting fail(), so the test passes when nothing is thrown. Use assertThrows.
  • @Disabled without a reason, left for months.

Wrong: passes even if nothing is thrown

@Test
void withdraw_tooMuch() {
    try {
        account.withdraw(10_000);
    } catch (InsufficientFundsException e) {
        assertEquals("Not enough balance", e.getMessage());
    }
}

Right: fails unless it is thrown

@Test
void withdraw_tooMuch() {
    var ex = assertThrows(InsufficientFundsException.class,
            () -> account.withdraw(10_000));
    assertEquals("Not enough balance", ex.getMessage());
}

Exceptions and edge cases

  • PreconditionViolationException: @BeforeAll method must be static unless the test class is annotated with @TestInstance(Lifecycle.PER_CLASS): you forgot static. The same rule applies to a @MethodSource factory.
  • ParameterResolutionException: No ParameterResolver registered for parameter: a test method takes a parameter that JUnit and your extensions cannot supply. Often a missing @ParameterizedTest or @Autowired.
  • AssertionFailedError: expected: <5> but was: <4>: a normal failed assertion. MultipleFailuresError comes from assertAll and lists every failure; assertThrows reports "Unexpected exception type thrown" when the type differs.
  • If a test run reports "No tests found" or runs zero tests, the usual reasons are a JUnit 4 @Test import, a name that Surefire does not match, or a missing junit-platform provider on an old Surefire version.
  • An exception in @BeforeEach marks every test of the class as failed, and an exception in @AfterEach fails the test that already passed. Keep hooks simple.
  • A static field shared between tests is shared state again: the new-instance rule does not protect static data or Spring singletons.

Tip: run one test quickly

From the command line: ./mvnw test -Dtest=JobServiceTest runs one class, and -Dtest=JobServiceTest#find_missing_throws runs one method. In IntelliJ, click the green arrow beside the method.

Mockito in depth: mocks, stubbing, verification and a full service test

Mockito replaces a class's collaborators with fakes you control: @Mock creates them, @InjectMocks wires them into the class under test, when(...).thenReturn(...) scripts answers, and verify(...) and ArgumentCaptor check what the class did.

Why mocks

A unit test of JobService should test the service's logic, not the database and not the e-mail sender. A mock is a fake object that has the same type as the real collaborator (JobRepository), returns whatever you script, and records how it was called. The test stays fast and is only about the class under test (the SUT, system under test).

Setup

import static org.assertj.core.api.Assertions.*;
import static org.mockito.ArgumentMatchers.*;
import static org.mockito.Mockito.*;

@ExtendWith(MockitoExtension.class)         // JUnit 5 integration; no Spring context
class JobServiceTest {

    @Mock JobRepository jobRepository;
    @Mock UserRepository userRepository;

    @InjectMocks JobService jobService;     // gets the mocks through its constructor
    ...
}
@ExtendWith(MockitoExtension.class)
Creates the mocks before each test, injects them, and checks strictness after each test.
@Mock
A mock of the field's type. Every method returns a default: null, 0, false, an empty List/Optional.
@InjectMocks
Creates the real object under test and injects the mocks. It tries the biggest constructor first, then setters, then fields. If a constructor argument has no matching mock it passes null, so a missing @Mock shows up as a NullPointerException in your service.
@Spy
A real object whose methods run for real unless you stub them; used rarely (partial mocking).

Without the extension you can create mocks by hand: JobRepository repo = mock(JobRepository.class);. The annotations are shorter.

Stubbing: when ... then

when(jobRepository.findById(7L)).thenReturn(Optional.of(job));
when(jobRepository.findById(99L)).thenReturn(Optional.empty());
when(userRepository.findById(any())).thenThrow(new IllegalStateException("db down"));

// consecutive calls: first returns a, then b
when(jobRepository.count()).thenReturn(1L, 2L);

// compute the answer from the arguments
when(jobRepository.save(any(Job.class))).thenAnswer(inv -> {
    Job j = inv.getArgument(0);
    ReflectionTestUtils.setField(j, "id", 7L);       // simulate the generated id
    return j;
});

For methods that return void, and for spies, when(...) does not work (the call would run for real or does not compile). Use the other form, action first:

doThrow(new MailException("smtp down")).when(mailSender).send(any());
doNothing().when(auditLog).record(anyString());
doReturn(42).when(spyCalculator).slowCompute();       // on a @Spy, avoids calling the real method

Argument matchers: the all-or-none rule

Matchers (any(), anyLong(), anyString(), eq(x), argThat(...), isNull()) say "any value of this kind". If one argument uses a matcher, all arguments of that call must use matchers; wrap plain values in eq().

Wrong: mixing a matcher and a raw value

when(repo.findByTitleAndCity(anyString(), "Pune")).thenReturn(list);
// InvalidUseOfMatchersException: 2 matchers expected, 1 recorded

Right: matchers for all arguments

when(repo.findByTitleAndCity(anyString(), eq("Pune"))).thenReturn(list);

With Mockito 5 (used by current Boot), any(Job.class) matches only a non-null instance of that type; any() matches anything including null.

Verification

Stubbing controls what the mock returns; verify checks what the SUT did to it.

verify(jobRepository).save(any(Job.class));                // exactly once (default)
verify(jobRepository, times(2)).findById(anyLong());
verify(jobRepository, never()).deleteById(anyLong());
verify(jobRepository, atLeastOnce()).findById(7L);
verifyNoInteractions(mailSender);                          // never touched
verifyNoMoreInteractions(jobRepository);                   // nothing else was called

Use verify for side effects that matter (an e-mail was sent, a row was saved, nothing was deleted). Do not verify every call of every mock: verifyNoMoreInteractions in every test makes tests break whenever you refactor, which is the "testing implementation details" trap (good tests). If the method returns a value, assert the value instead of verifying the call that produced it.

ArgumentCaptor

Sometimes the SUT builds an object internally and passes it to a collaborator. A captor lets you grab it and assert on it.

ArgumentCaptor<Job> captor = ArgumentCaptor.forClass(Job.class);
verify(jobRepository).save(captor.capture());
Job saved = captor.getValue();
assertThat(saved.getTitle()).isEqualTo("Java Developer");
assertThat(saved.getPostedBy().getId()).isEqualTo(5L);

You can also declare @Captor ArgumentCaptor<Job> captor; as a field with the extension.

BDDMockito: given / then

The same API with names that match Given-When-Then, in org.mockito.BDDMockito:

import static org.mockito.BDDMockito.*;

given(jobRepository.findById(7L)).willReturn(Optional.of(job));        // given
JobResponse r = jobService.getJob(7L);                                 // when
then(jobRepository).should().findById(7L);                             // then
then(mailSender).shouldHaveNoInteractions();

Strict stubs and UnnecessaryStubbingException

With MockitoExtension the default is strict stubs: if you stub something the test never uses, the test fails with org.mockito.exceptions.misusing.UnnecessaryStubbingException. This is useful: it finds dead set-up code and wrong assumptions about what the SUT calls. Also, strict stubs report a PotentialStubbingProblem if the SUT calls a stubbed method with different arguments than you stubbed. Fix by removing the stub or correcting the arguments. Use lenient().when(...) only for set-up shared by many tests in @BeforeEach.

Mocking static methods (brief)

Since Mockito 5 (Mockito 3.4+ with the inline mock maker) you can mock a static method. It is limited to a block and thread, via try-with-resources:

Instant fixed = Instant.parse("2026-11-10T10:00:00Z");
try (MockedStatic<Instant> mocked = mockStatic(Instant.class, CALLS_REAL_METHODS)) {
    mocked.when(Instant::now).thenReturn(fixed);
    assertThat(service.isExpired(job)).isFalse();
}   // the static mock is closed here

A static mock is a design smell more often than a solution. Inject a java.time.Clock into the service (clock.instant()) and pass Clock.fixed(...) in the test; that is simpler and thread-safe.

What not to mock

  • The class under test. A test that mocks the SUT tests the mock.
  • Value objects and records (JobResponse, Money, LocalDate, String): just create them.
  • Collections and simple data holders: use List.of(...).
  • Types you do not own (the JDBC driver, RestTemplate, EntityManager) in deep chains: wrap them in your own class and mock that, or test with a real thing (Testcontainers, MockWebServer).
  • Everything. If a test has six mocks and eleven stubs, it is probably re-implementing the code. Test that logic at a higher level instead.

A complete service test: JobServiceTest

The service under test (simplified from the earlier modules):

@Service
public class JobService {

    private final JobRepository jobRepository;
    private final UserRepository userRepository;

    public JobService(JobRepository jobRepository, UserRepository userRepository) {
        this.jobRepository = jobRepository;
        this.userRepository = userRepository;
    }

    @Transactional
    public JobResponse create(CreateJobRequest req, CurrentUser me) {
        User recruiter = userRepository.findById(me.id())
                .orElseThrow(() -> new ResourceNotFoundException("User " + me.id()));
        Job saved = jobRepository.save(new Job(req.title(), req.description(), recruiter));
        return JobResponse.from(saved);
    }

    @Transactional
    public JobResponse update(Long jobId, UpdateJobRequest req, CurrentUser me) {
        Job job = jobRepository.findById(jobId)
                .orElseThrow(() -> new ResourceNotFoundException("Job " + jobId));
        if (!job.getPostedBy().getId().equals(me.id()) && !me.isAdmin()) {
            throw new AccessDeniedException("You can only edit your own jobs");
        }
        job.update(req.title(), req.description());
        return JobResponse.from(job);
    }
}
@ExtendWith(MockitoExtension.class)
class JobServiceTest {

    @Mock JobRepository jobRepository;
    @Mock UserRepository userRepository;
    @InjectMocks JobService jobService;

    private User recruiter;
    private final CurrentUser asRecruiter = new CurrentUser(5L, Set.of("ROLE_RECRUITER"));

    @BeforeEach
    void setUp() {
        recruiter = TestData.user(5L, "asha@example.com", Role.RECRUITER);
    }

    @Nested
    class Create {

        @Test
        void create_savesJobPostedByCurrentUser() {
            when(userRepository.findById(5L)).thenReturn(Optional.of(recruiter));
            when(jobRepository.save(any(Job.class))).thenAnswer(inv -> {
                Job j = inv.getArgument(0);
                ReflectionTestUtils.setField(j, "id", 7L);
                return j;
            });

            JobResponse response = jobService.create(
                    new CreateJobRequest("Java Developer", "Spring Boot, SQL"), asRecruiter);

            assertThat(response.id()).isEqualTo(7L);
            ArgumentCaptor<Job> captor = ArgumentCaptor.forClass(Job.class);
            verify(jobRepository).save(captor.capture());
            assertThat(captor.getValue().getPostedBy()).isSameAs(recruiter);
        }

        @Test
        void create_whenUserMissing_throwsNotFound() {
            when(userRepository.findById(5L)).thenReturn(Optional.empty());

            assertThatThrownBy(() -> jobService.create(
                    new CreateJobRequest("x", "y"), asRecruiter))
                    .isInstanceOf(ResourceNotFoundException.class)
                    .hasMessageContaining("User 5");

            verify(jobRepository, never()).save(any());
        }
    }

    @Nested
    class Update {

        @Test
        void update_byOwner_changesFields() {
            Job job = TestData.job(7L, "Old title", recruiter);
            when(jobRepository.findById(7L)).thenReturn(Optional.of(job));

            JobResponse r = jobService.update(7L,
                    new UpdateJobRequest("New title", "New text"), asRecruiter);

            assertThat(r.title()).isEqualTo("New title");
        }

        @Test
        void update_byAnotherRecruiter_isForbidden() {
            Job job = TestData.job(7L, "Old title", recruiter);
            when(jobRepository.findById(7L)).thenReturn(Optional.of(job));
            var other = new CurrentUser(6L, Set.of("ROLE_RECRUITER"));

            assertThatThrownBy(() -> jobService.update(7L,
                    new UpdateJobRequest("Hacked", "x"), other))
                    .isInstanceOf(AccessDeniedException.class);

            assertThat(job.getTitle()).isEqualTo("Old title");     // unchanged
        }

        @Test
        void update_byAdmin_isAllowed() {
            Job job = TestData.job(7L, "Old title", recruiter);
            when(jobRepository.findById(7L)).thenReturn(Optional.of(job));
            var admin = new CurrentUser(1L, Set.of("ROLE_ADMIN"));

            jobService.update(7L, new UpdateJobRequest("By admin", "x"), admin);

            assertThat(job.getTitle()).isEqualTo("By admin");
        }

        @Test
        void update_whenJobMissing_throwsNotFound() {
            when(jobRepository.findById(99L)).thenReturn(Optional.empty());

            assertThatThrownBy(() -> jobService.update(99L,
                    new UpdateJobRequest("t", "d"), asRecruiter))
                    .isInstanceOf(ResourceNotFoundException.class);
        }
    }
}

TestData is a small helper class in src/test that builds entities (see test data builders); it uses reflection to set generated ids. Notice what the tests check: returned values and state for the main behaviour, verify only for the important side effect ("nothing saved" when the user is missing), and no real database. No save call is verified in update because the service relies on dirty checking (module 3); in a unit test we assert the entity changed.

Exceptions and edge cases

  • NullPointerException inside the SUT: a dependency has no @Mock (it was injected as null), or an unstubbed mock returned null from a method returning a non-collection object.
  • InvalidUseOfMatchersException: mixed matchers and raw values, or a matcher used outside a stubbing/verification call.
  • UnnecessaryStubbingException: a stub was never used (strict stubs).
  • WantedButNotInvoked / TooManyActualInvocations: verify failed; the message lists the actual calls.
  • MockitoException: Cannot mock/spy class ... final: very old Mockito versions could not mock final classes; Mockito 5 can.
  • Stubbing when(mock.voidMethod()) does not compile; use doThrow/doNothing.

Common mistakes

  • Testing the mock: stub repo.findById to return X and then assert the service returned X, with no logic in between.
  • Mocking User, Job or other entities; create real objects.
  • Using @Mock with @SpringBootTest: that is @MockitoBean (see the MockMvc article); @Mock is for pure unit tests.
  • Over-verifying every call, so every refactor breaks tests.

Interview angle

"@Mock vs @InjectMocks?" Mock creates a fake; InjectMocks builds the real SUT and injects the fakes. "Mock vs spy?" Mock is a full fake, spy wraps a real object. "When do you use doReturn?" Void methods and spies. "What is ArgumentCaptor for?" Inspecting arguments passed to a collaborator. "What does UnnecessaryStubbingException mean?" Strict stubs found a stub that was not used. Also expect: "What would you not mock?"

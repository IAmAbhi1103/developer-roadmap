Layers: controller, service, repository

A Spring Boot API is split into three layers: the controller handles HTTP, the service holds business rules and transactions, and the repository talks to the database; each layer calls only the one below it.

A layered architecture gives every class one reason to change. If the JSON format changes, only the controller changes. If a business rule changes (for example "an order over ₹50,000 needs approval"), only the service changes. If you switch from PostgreSQL to MongoDB, only the repository changes. It also makes testing easy: you can test the service without HTTP and the controller without a database.

What each layer does

LayerAnnotationResponsible forMust not
Controller@RestControllerPaths, binding, validation trigger, status codes, calling one service methodContain business logic, call repositories, open transactions
Service@ServiceBusiness rules, orchestration, @Transactional, mapping entity ↔ DTOKnow about HTTP (ResponseEntity, HttpServletRequest, status codes)
Repository@Repository / Spring Data interfaceQueries and persistence of entitiesContain business rules; return DTOs of the web layer

Next to the three layers sit two kinds of classes that cross them: the entity (the database row as an object, used by service and repository) and the DTO (the shape of the JSON, used by controller and service). See DTOs.

What goes where: a worked example

Requirement: "Create a product. The SKU must be unique. Price must be positive. Save it and return it."

  • Controller: receives the JSON, triggers format checks (@Valid: price not null, name not blank), calls service.create(request), returns 201 and Location.
  • Service: checks the business rule "SKU is not already used" (existsBySku), throws DuplicateResourceException if it is, builds the entity, calls save, maps the result to a response DTO.
  • Repository: save(entity) and existsBySku(sku). Nothing else.

Note the split in validation: format rules (not blank, positive, an email shape) belong to Bean Validation at the edge; business rules that need data (unique SKU, enough stock, user may cancel only own order) belong to the service.

Transactions live in the service

A transaction groups several database operations into one all-or-nothing unit. One business action usually touches several repositories (reduce stock, create order, create payment record), so the service method is the unit of work. Put @Transactional there, not on controllers or repositories. Use @Transactional(readOnly = true) on read methods. Full details are in module 3.

Dependency direction and wiring

@RestController
@RequestMapping("/api/v1/products")
public class ProductController {

    private final ProductService productService;       // depends on the service only

    public ProductController(ProductService productService) {
        this.productService = productService;
    }
}

@Service
public class ProductService {

    private final ProductRepository productRepository; // depends on the repository only

    public ProductService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }
}

Depending on an interface for the service (ProductService + ProductServiceImpl) is optional. With one implementation it adds files and no value. Introduce an interface when you truly have two implementations or need a clean seam for a test double; Mockito can mock concrete classes anyway.

Package structure

StyleLayoutGood for
By layercontroller/, service/, repository/, dto/, entity/Small apps, learning
By featureproduct/ (controller, service, repository, dto…), order/, user/Growing apps; microservice splits later

Package-by-feature keeps everything about one resource together, lets you make classes package-private, and is what most teams move to after the first few months. Both work; pick one and keep it.

Rules of the layers

  • Controller → service → repository. Never skip a layer (a controller calling a repository), never call upwards.
  • No HTTP types in services: no ResponseEntity, HttpStatus, HttpServletRequest. A service throws domain exceptions; the web layer maps them to status codes.
  • No entities in controller signatures. Controllers speak DTOs.
  • No business logic in controllers or repositories.
  • Do not put @Transactional on a controller; do not call a @Transactional method from another method of the same class and expect a new transaction (self-invocation bypasses the proxy; see module 3).

Mistake: the fat controller

Wrong: logic and database in the controller

@PostMapping
public Product create(@RequestBody Product p) {
    if (repo.existsBySku(p.getSku())) {
        throw new RuntimeException("dup");
    }
    p.setCreatedAt(Instant.now());
    return repo.save(p);
}

Right: controller delegates

@PostMapping
public ResponseEntity<ProductResponse> create(
        @Valid @RequestBody CreateProductRequest r) {
    ProductResponse created = service.create(r);
    return ResponseEntity.created(location(created)).body(created);
}

The wrong version cannot be tested without a database, repeats its rules in every controller that needs them, and exposes the entity.

Exception: simple lookups

For a trivial read-only app, a service that only forwards to the repository is "pass-through" code. Some teams still keep it so there is one place to add rules and transactions later. Pick the discipline early; moving it into a project later is harder than starting with it.

Interview angle

"Why not call the repository from the controller?" Strong points: separation of concerns, one place for business rules and transactions, easier unit tests (mock the repository, no HTTP needed), reuse of the service from other entry points (scheduled jobs, message listeners), and the controller stays a thin translation layer between HTTP and your domain. Also name @Component, @Service, @Repository as stereotypes of the same idea (module 1).

Complete CRUD example: Product API

One resource through every layer: entity, repository, DTO records, mapper, service, controller and exception handler, with curl requests and the JSON they return.

This is the pattern you will repeat for every resource in a job project. Pieces that need a later topic are marked: validation details are in Bean Validation, the full error handler in error handling, and JPA in module 3. The example uses PostgreSQL and Spring Data JPA.

1. Entity

package com.example.shop.product;

import jakarta.persistence.*;
import java.math.BigDecimal;
import java.time.Instant;

@Entity
@Table(name = "product")
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 120)
    private String name;

    @Column(nullable = false, unique = true, length = 40)
    private String sku;

    @Column(nullable = false, precision = 10, scale = 2)
    private BigDecimal price;

    @Column(nullable = false)
    private int stock;

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    protected Product() { }                       // required by JPA

    public Product(String name, String sku, BigDecimal price, int stock) {
        this.name = name;
        this.sku = sku;
        this.price = price;
        this.stock = stock;
    }

    @PrePersist
    void onCreate() { this.createdAt = Instant.now(); }

    public Long getId() { return id; }
    public String getName() { return name; }
    public String getSku() { return sku; }
    public BigDecimal getPrice() { return price; }
    public int getStock() { return stock; }
    public Instant getCreatedAt() { return createdAt; }

    public void update(String name, BigDecimal price, int stock) {
        this.name = name;
        this.price = price;
        this.stock = stock;
    }
}

2. Repository

package com.example.shop.product;

import org.springframework.data.jpa.repository.JpaRepository;

public interface ProductRepository extends JpaRepository<Product, Long> {

    boolean existsBySku(String sku);
}

Spring Data creates the implementation at startup; existsBySku becomes SQL from the method name.

3. DTOs (records)

public record CreateProductRequest(
        @NotBlank @Size(max = 120) String name,
        @NotBlank @Size(max = 40) String sku,
        @NotNull @Positive @Digits(integer = 8, fraction = 2) BigDecimal price,
        @PositiveOrZero int stock) {}

public record UpdateProductRequest(
        @NotBlank @Size(max = 120) String name,
        @NotNull @Positive @Digits(integer = 8, fraction = 2) BigDecimal price,
        @PositiveOrZero int stock) {}

public record ProductResponse(
        Long id, String name, String sku, BigDecimal price, int stock, Instant createdAt) {}

The update request has no sku: the SKU cannot change, so the API does not accept it.

4. Mapper (by hand)

@Component
public class ProductMapper {

    public Product toEntity(CreateProductRequest r) {
        return new Product(r.name(), r.sku(), r.price(), r.stock());
    }

    public ProductResponse toResponse(Product p) {
        return new ProductResponse(p.getId(), p.getName(), p.getSku(),
                p.getPrice(), p.getStock(), p.getCreatedAt());
    }
}

5. Exceptions

public class ResourceNotFoundException extends RuntimeException {
    public ResourceNotFoundException(String resource, Object id) {
        super(resource + " with id " + id + " not found");
    }
}

public class DuplicateResourceException extends RuntimeException {
    public DuplicateResourceException(String message) { super(message); }
}

6. Service

@Service
public class ProductService {

    private final ProductRepository repository;
    private final ProductMapper mapper;

    public ProductService(ProductRepository repository, ProductMapper mapper) {
        this.repository = repository;
        this.mapper = mapper;
    }

    @Transactional(readOnly = true)
    public List<ProductResponse> findAll() {
        return repository.findAll().stream().map(mapper::toResponse).toList();
    }

    @Transactional(readOnly = true)
    public ProductResponse findById(Long id) {
        return mapper.toResponse(getOrThrow(id));
    }

    @Transactional
    public ProductResponse create(CreateProductRequest request) {
        if (repository.existsBySku(request.sku())) {
            throw new DuplicateResourceException(
                    "Product with SKU " + request.sku() + " already exists");
        }
        Product saved = repository.save(mapper.toEntity(request));
        return mapper.toResponse(saved);
    }

    @Transactional
    public ProductResponse update(Long id, UpdateProductRequest request) {
        Product product = getOrThrow(id);
        product.update(request.name(), request.price(), request.stock());
        return mapper.toResponse(product);          // dirty checking saves it at commit
    }

    @Transactional
    public void delete(Long id) {
        Product product = getOrThrow(id);
        repository.delete(product);
    }

    private Product getOrThrow(Long id) {
        return repository.findById(id)
                .orElseThrow(() -> new ResourceNotFoundException("Product", id));
    }
}

7. Controller

@RestController
@RequestMapping("/api/v1/products")
public class ProductController {

    private final ProductService service;

    public ProductController(ProductService service) { this.service = service; }

    @GetMapping
    public List<ProductResponse> list() {
        return service.findAll();
    }

    @GetMapping("/{id}")
    public ProductResponse get(@PathVariable Long id) {
        return service.findById(id);
    }

    @PostMapping
    public ResponseEntity<ProductResponse> create(
            @Valid @RequestBody CreateProductRequest request) {
        ProductResponse created = service.create(request);
        URI location = ServletUriComponentsBuilder.fromCurrentRequest()
                .path("/{id}").buildAndExpand(created.id()).toUri();
        return ResponseEntity.created(location).body(created);
    }

    @PutMapping("/{id}")
    public ProductResponse update(@PathVariable Long id,
            @Valid @RequestBody UpdateProductRequest request) {
        return service.update(id, request);
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void delete(@PathVariable Long id) {
        service.delete(id);
    }
}

8. Exception handler (minimal)

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    ProblemDetail notFound(ResourceNotFoundException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    }

    @ExceptionHandler(DuplicateResourceException.class)
    ProblemDetail conflict(DuplicateResourceException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, ex.getMessage());
    }
}

Without a handler for MethodArgumentNotValidException you only get a generic 400 body. The validation and error-handling articles turn it into a clean list of field errors.

What to notice

  • The entity never leaves the service. The controller sees only records.
  • The service has no ResponseEntity; it throws domain exceptions that the advice maps to 404 and 409.
  • update loads the entity and changes it inside a transaction; Hibernate's dirty checking writes the UPDATE. No save call is needed.
  • The check existsBySku is not race-proof: two concurrent requests can both pass it. The database UNIQUE constraint is the real guard; handle DataIntegrityViolationException as 409 too (see error handling).
  • PUT replaces the writable fields; that is why UpdateProductRequest requires all of them. For a partial update, use PATCH with an optional-field DTO.

Edge cases you should think about

  • Delete of an already deleted product: this code returns 404 the second time. Some APIs return 204 again to make DELETE strictly idempotent in outcome; both are accepted, be consistent.
  • findAll() on a big table is a performance bug. Real list endpoints are paged: pagination.
  • Concurrent updates overwrite each other (lost update). Add a @Version field for optimistic locking (module 3).

In real projects

Reviewers check this checklist on every endpoint: correct verb and status, DTO in and out, @Valid on bodies, no logic in the controller, transaction on the service, domain exceptions mapped centrally, a test for the happy path and for 400/404/409, and documentation in Swagger. You will use this same skeleton for the job-portal project in the practice article.

DTOs and mapping (manual, MapStruct)

A DTO is a small class or record that defines exactly what goes into and out of your API; you map entities to DTOs in the service so internal fields and database details never leak, either by hand or with MapStruct.

A DTO (Data Transfer Object) carries data across a boundary. On the web edge, your API contract is the set of request and response DTOs. Your entity is a different thing: it describes a database table and may hold lazy relationships, password hashes, audit columns and internal flags. Mixing the two is the most common beginner mistake in Spring Boot APIs.

Why you should never expose entities

  1. Leaking data. Return a User entity and the JSON includes passwordHash, roles, deleted, internal ids. Adding a column to the table silently adds it to the public API.
  2. Over-posting (mass assignment). If @RequestBody is an entity, a client can send {"id": 1, "role": "ADMIN", "price": 1} and set fields you never meant to expose. A request DTO has only the fields a client may set.
  3. Lazy-loading errors. A JPA relationship such as order.getItems() is loaded on demand. Jackson touches it after the transaction is closed and you get LazyInitializationException; with open-session-in-view it silently fires extra queries per row (the N+1 problem).
  4. Infinite recursion. A bidirectional relationship (Order ↔ OrderItem) makes Jackson loop until StackOverflowError or a "Document nesting depth" failure.
  5. Tight coupling. A database refactoring (rename a column, split a table) breaks every client. With DTOs the API stays the same and only the mapper changes.
  6. Different shapes for different needs. A list view needs three fields, a detail view fifteen, a create request needs no id and no timestamps. One entity cannot be all of these.
  7. Validation fits the request. Constraints like @NotBlank on a create request differ from the update request; the entity should hold database rules.

Wrong: entity as the API

@PostMapping
public User register(@RequestBody User user) {   // client can set role, id, ...
    return userRepository.save(user);            // response includes passwordHash
}

Right: DTOs in and out

@PostMapping
public UserResponse register(@Valid @RequestBody RegisterRequest request) {
    return userService.register(request);        // service hashes the password
}

Request DTO vs response DTO

Use separate types for input and output and often one per operation. Java records are ideal: immutable, no boilerplate, and Jackson supports them.

public record RegisterRequest(
        @NotBlank @Size(max = 80) String name,
        @NotBlank @Email String email,
        @NotBlank @Size(min = 8, max = 72) String password) {}

public record UserResponse(Long id, String name, String email, Instant createdAt) {}
// no password, no roles, no internal flags

public record UserSummary(Long id, String name) {}   // for lists and nested use

Mapping by hand

Hand-written mapping is plain Java: no magic, easy to debug, the compiler tells you when you add a field and forget it somewhere. Keep it in a mapper class or as a static factory on the DTO.

// Style 1: a static factory method on the response record
public record ProductResponse(Long id, String name, BigDecimal price) {
    public static ProductResponse from(Product p) {
        return new ProductResponse(p.getId(), p.getName(), p.getPrice());
    }
}
List<ProductResponse> list = products.stream().map(ProductResponse::from).toList();

// Style 2: a @Component mapper (see the CRUD article)
@Component
public class ProductMapper {
    public ProductResponse toResponse(Product p) { ... }
    public Product toEntity(CreateProductRequest r) { ... }
}

It is boring code, and that is fine for apps with up to a few dozen DTOs. When you have hundreds of mappings, a generator saves time and typos.

MapStruct

MapStruct is an annotation processor: at compile time it generates a plain Java implementation of your mapper interface. There is no reflection at runtime, so it is fast, and the generated source is readable in target/generated-sources. If a target property has no source, the compiler warns you (set unmappedTargetPolicy = ReportingPolicy.ERROR to fail the build).

<dependency>
    <groupId>org.mapstruct</groupId>
    <artifactId>mapstruct</artifactId>
    <version>${mapstruct.version}</version>
</dependency>

<!-- inside maven-compiler-plugin configuration -->
<annotationProcessorPaths>
    <path>
        <groupId>org.mapstruct</groupId>
        <artifactId>mapstruct-processor</artifactId>
        <version>${mapstruct.version}</version>
    </path>
</annotationProcessorPaths>

Use the current stable MapStruct version from its website for mapstruct.version. If you also use Lombok, add Lombok and the lombok-mapstruct-binding artifact to the same processor-path list, with Lombok listed first, or mappers will not see Lombok-generated getters.

import org.mapstruct.*;

@Mapper(componentModel = "spring")          // generated class is a Spring bean
public interface ProductMapper {

    ProductResponse toResponse(Product product);       // same names: automatic

    List<ProductResponse> toResponses(List<Product> products);

    @Mapping(target = "id", ignore = true)
    @Mapping(target = "createdAt", ignore = true)
    Product toEntity(CreateProductRequest request);

    // different names and a small conversion
    @Mapping(source = "title", target = "name")
    @Mapping(target = "slug", expression = "java(request.title().toLowerCase())")
    Product fromLegacy(LegacyRequest request);

    // update an existing entity in place
    @Mapping(target = "id", ignore = true)
    @Mapping(target = "sku", ignore = true)
    void updateEntity(UpdateProductRequest request, @MappingTarget Product product);
}

With a mapper bean, the service is the same as before: ProductResponse r = mapper.toResponse(entity). MapStruct works with records and with classes.

ModelMapper and other reflection mappers

Libraries like ModelMapper map by guessing at runtime: modelMapper.map(entity, ProductResponse.class). It saves typing but has real costs: errors show up at runtime (or silently as nulls) instead of compile time, a rename in one class quietly breaks a mapping, reflection is slower, and refactoring tools cannot follow it. Most teams, and most interviewers, prefer MapStruct or hand-written mapping.

Nested DTOs and partial updates

  • Nested objects: map a relationship to a small summary record, not the full entity: OrderResponse(Long id, UserSummary customer, List<OrderItemResponse> items). Load the data you need in the service (a fetch join or an entity graph, module 3) so no lazy load happens outside the transaction.
  • Partial update (PATCH): use a request record with wrapper types, where null means "do not change": PatchProductRequest(String name, BigDecimal price). A plain DTO cannot tell "not sent" from "sent as null". If you must support "set to null", use JSON Merge Patch or JsonNullable-style wrappers; for most APIs "null means unchanged" is enough.
  • Projections: for read-heavy lists, Spring Data can return interface or record projections straight from the query, skipping the entity (module 3).

Rules

  • No entity in a controller method signature, as parameter or return type, not even inside List or ResponseEntity.
  • Map inside the service transaction, before lazy data is out of reach.
  • Response DTOs never hold secrets; request DTOs never hold server-controlled fields (id, role, createdAt).

Naming

Common names: CreateProductRequest, UpdateProductRequest, ProductResponse, ProductSummary. The suffix Dto alone (ProductDto) is also widely used, but it hides whether the type is for input or output. Nest the records inside a single ProductDtos class only for tiny projects.

Mistakes

  • One ProductDto used for create, update and response, so the client must send an id and the response has null fields.
  • Using @JsonIgnore on entity fields to "hide" them. It is easy to forget and couples the database model to the API. Separate types are safer.
  • A mapper that calls entity.getItems() outside a transaction, giving LazyInitializationException.
  • Putting JPA annotations on DTOs, or validation annotations only on the entity.

Interview angle

"Why use DTOs instead of returning entities?" Give at least four reasons: security (hide fields, stop over-posting), stability (API independent of the schema), lazy loading and recursion problems, and different shapes per use case. Then "How do you map?" Hand-written or MapStruct (compile-time, generated, fast); explain why you avoid reflection-based mappers.

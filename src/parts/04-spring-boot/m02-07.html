Interview questions — REST APIs with Spring Boot

What is REST, and what makes an API RESTful?

REST is an architectural style for APIs over HTTP. Resources (products, orders) are identified by URLs, the client works with representations of them (usually JSON), and the HTTP method says what to do with them. Key constraints: client-server, stateless requests (each request carries everything the server needs, such as the token), a uniform interface (standard methods and status codes), cacheable responses and a layered system. In practice a good REST API uses nouns in plural URLs, the right verb for each action, and correct status codes.

PUT vs PATCH vs POST: what is the difference, and which are idempotent?

POST creates a resource (or runs an action); sending it twice creates two resources, so it is not idempotent. PUT replaces the whole resource at a known URL; repeating it leaves the same state, so it is idempotent. PATCH changes some fields; whether it is idempotent depends on the change ("set price to 500" is, "increase price by 10" is not). GET, PUT, DELETE are idempotent; GET and HEAD are also safe (no state change).

Which status codes do you return for create, update, delete, validation error, missing resource and duplicate?

Create: 201 Created with a Location header. Read/update: 200 OK. Delete: 204 No Content. Invalid input: 400 Bad Request (some teams use 422 for business-rule failures). Not found: 404. Duplicate or version conflict: 409 Conflict. Not logged in: 401; logged in but not allowed: 403. Unexpected server error: 500, with no stack trace in the body.

Explain what happens when a request reaches a Spring Boot application.

Embedded Tomcat accepts the connection and builds a servlet request. It passes through the filter chain (CORS, security, logging). The DispatcherServlet, the front controller, asks HandlerMapping which controller method matches the method, path and media types. The HandlerAdapter resolves the arguments: path variables, query parameters, and the body through an HttpMessageConverter (Jackson), running @Valid validation. Your method runs; its return value is written by a message converter as JSON. If an exception is thrown, @RestControllerAdvice turns it into an error response.

What is the difference between @Controller and @RestController?

@RestController is @Controller plus @ResponseBody. With @Controller the returned String is a view name for a template engine; with @RestController every return value is serialized into the response body, normally as JSON. Use @RestController for APIs.

@PathVariable vs @RequestParam: when do you use each?

A path variable identifies a resource (/products/42) and is always required. A request parameter is a query-string value for filtering, sorting and paging (?category=mouse&page=1) and can be optional with required = false, defaultValue or Optional. A path variable that cannot be converted (/products/abc for a Long) causes a 400 through MethodArgumentTypeMismatchException.

How do you return 201 with the URL of the new resource?

Return a ResponseEntity:

URI location = ServletUriComponentsBuilder.fromCurrentRequest()
        .path("/{id}").buildAndExpand(created.id()).toUri();
return ResponseEntity.created(location).body(created);

The URI is built from the current request, so it is right in every environment. The client can follow Location to fetch the new resource.

Why should you never return JPA entities from a controller?

Because it leaks fields (password hash, internal flags), lets clients over-post fields you did not intend to expose, ties the API to the database schema, and causes LazyInitializationException and infinite recursion on bidirectional relationships. Use request and response DTOs (records) and map in the service, by hand or with MapStruct.

MapStruct vs ModelMapper: which do you choose and why?

MapStruct generates plain mapping code at compile time. It is fast, errors appear at build time, and the generated code can be read and debugged. ModelMapper maps by reflection at runtime: slower, and a renamed field can silently map to nothing. Hand-written mapping is also fine for small projects. Configure MapStruct with @Mapper(componentModel = "spring") so the mapper is injectable.

Explain @NotNull, @NotEmpty and @NotBlank. What do @Valid and @Validated do?

@NotNull rejects null only. @NotEmpty also rejects empty strings and collections. @NotBlank (strings only) also rejects text made of spaces. The other constraints (@Size, @Email, @Positive) accept null, so combine them with a Not-annotation for required fields.

@Valid (Jakarta) triggers validation of a @RequestBody and cascades into nested objects. @Validated (Spring) supports validation groups and enables method-level validation on a class. A failed @Valid @RequestBody throws MethodArgumentNotValidException and the method is never called.

How do you handle exceptions globally and return a consistent error body?

Services throw domain exceptions (ResourceNotFoundException, DuplicateResourceException). One @RestControllerAdvice class has @ExceptionHandler methods mapping them to 404, 409 and so on, and returns a ProblemDetail (RFC 9457) with type, title, status, detail, instance and extra properties such as the list of field errors. Extending ResponseEntityExceptionHandler covers the framework's own exceptions. A catch-all Exception handler logs the stack trace and returns a generic 500. Errors raised in security filters are not seen by the advice and are handled in the security configuration.

How do you implement pagination and sorting? What is the difference between Page and Slice?

Add a Pageable parameter to the controller (?page=0&size=20&sort=name,asc), pass it to a repository method returning Page<T>, map to a page DTO and cap the size with spring.data.web.pageable.max-page-size. Page runs an extra count query to know the total elements and pages; Slice skips it and only knows whether a next page exists, which is cheaper for infinite scroll. Return your own page record instead of the raw PageImpl, because its JSON shape is not guaranteed to be stable. For huge tables, offset paging gets slow; use keyset (cursor) pagination.

How do you version a REST API? What are the options?

Options: URI (/api/v1/products, the simplest and most common), a custom request header, a media type (Accept: application/vnd.shop.v2+json), or a query parameter. URI versioning is easy to see, cache and test; header and media-type versioning keep URLs clean but are harder to use from a browser. Whatever you choose, avoid breaking changes inside a version: adding fields is safe; removing or renaming fields needs a new version.

What is the difference between 401 and 403? Between 400, 404 and 422?

401 Unauthorized really means "unauthenticated": no valid credentials. 403 Forbidden means the user is known but not allowed. 400 means the request is malformed or fails validation, 404 means the resource does not exist, and 422 (used by some APIs) means the request is well-formed but breaks a business rule.

How do you document an API, and how do you test an endpoint manually?

Add springdoc-openapi-starter-webmvc-ui (a version matching your Boot line). It exposes /v3/api-docs and Swagger UI at /swagger-ui.html; annotate with @Tag, @Operation, @ApiResponse and @Schema, declare a bearer security scheme for JWT, and disable it in production. For manual testing use curl for quick checks and Postman or Bruno for collections with environments ({{baseUrl}}, {{token}}) and test scripts.

Cheat sheet — REST APIs with Spring Boot

  • GET / POST / PUT / PATCH / DELETE read / create or action / replace / partial change / remove; GET, PUT, DELETE are idempotent; GET and HEAD are safe.
  • Status codes 200 OK, 201 Created (+ Location), 204 No Content, 400 bad input, 401 not logged in, 403 not allowed, 404 missing, 409 conflict, 422 rule broken, 500 server bug.
  • @RestController = @Controller + @ResponseBody; return values become JSON.
  • Request path Tomcat → filters → DispatcherServlet → HandlerMapping → HandlerAdapter → controller → message converter.
  • @RequestMapping("/api/v1/products") on the class; @GetMapping, @PostMapping, @PutMapping, @PatchMapping, @DeleteMapping on methods.
  • @PathVariable identifies a resource (/{id}); @RequestParam filters, sorts and pages (?q=).
  • @RequestParam options required, defaultValue, Optional<T>; never a primitive for an optional value.
  • @RequestBody JSON → object; invalid JSON gives HttpMessageNotReadableException → 400; wrong Content-Type gives 415.
  • ResponseEntity status + headers + body: ok, created(uri), noContent, notFound, status(...).
  • Location URI ServletUriComponentsBuilder.fromCurrentRequest().path("/{id}").buildAndExpand(id).toUri().
  • @ResponseStatus fixed status on a method or exception class (e.g. NO_CONTENT for delete).
  • Layers controller (HTTP) → service (rules, @Transactional, mapping) → repository (data); no HTTP types in services.
  • DTOs records for request and response; never expose entities (leaks, over-posting, lazy loading, recursion).
  • MapStruct @Mapper(componentModel = "spring"), @Mapping, @MappingTarget; avoid reflection mappers.
  • Validation @NotBlank (text), @NotEmpty (lists), @NotNull (everything else), @Size, @Positive, @Email, @Pattern; @Valid on bodies and nested fields.
  • Validation exceptions MethodArgumentNotValidException (body), HandlerMethodValidationException (parameters, Spring 6.1+), ConstraintViolationException (class-level @Validated).
  • Error handling @RestControllerAdvice + @ExceptionHandler; return ProblemDetail (application/problem+json); catch-all logs and returns a generic 500.
  • Exception to status not found → 404, duplicate or DataIntegrityViolationException → 409, business rule → 422, validation → 400.
  • Paging Pageable (page from 0, size, sort=field,dir); cap spring.data.web.pageable.max-page-size; return your own page record.
  • Page vs Slice Page runs a count query; Slice only knows if there is a next page.
  • Filtering optional query parameters bound to a record; Specifications for combinable filters; keyset paging for deep pages.
  • springdoc springdoc-openapi-starter-webmvc-ui; /swagger-ui.html, /v3/api-docs; turn off in prod.
  • Lombok @RequiredArgsConstructor, @Slf4j, @Getter, @Builder; no @Data on JPA entities.
  • Tools curl for quick checks; Postman or Bruno with {{baseUrl}} and {{token}} variables for collections.

Practice — REST APIs with Spring Boot

  1. Hello API (easy). Create a project on start.spring.io (Web, Validation). Add GET /api/v1/hello?name=Asha returning {"message":"Hello, Asha"} from a record. Use defaultValue = "world". Done when curl returns the JSON and the response header Content-Type is application/json.
  2. Status code drill (easy). Build an in-memory Map based CRUD for a Note resource (no database). Return 201 + Location on create, 200 on read and update, 204 on delete, and 404 for an unknown id. Done when all five curl calls show the right status and the Location header opens the new note.
  3. Product CRUD with layers (medium). Copy the Product API from the CRUD article with PostgreSQL and Spring Data JPA. Write it yourself without looking, then compare. Done when create, list, get, update and delete all work, and the entity never appears in a controller signature.
  4. Validation and global errors (medium). Add Bean Validation to the request records (@NotBlank, @Positive, @Size, a custom @ValidSku). Write a @RestControllerAdvice returning ProblemDetail with a field-error list for 400, plus 404, 409 and a safe 500. Done when invalid input, an unknown id, a duplicate SKU and a forced RuntimeException each return the same JSON shape and no stack trace.
  5. Validate parameters (medium). Add @Positive on the {id} path variable and @Min(1) @Max(100) on a size query parameter. Handle HandlerMethodValidationException. Done when /products/-1 returns a 400 with the parameter name in errors.
  6. Search, paging and sorting (medium). Add GET /api/v1/products?q=&category=&maxPrice=&page=&size=&sort= using a filter record, a Pageable, a Specification, and a PageResponse record. Cap the size at 50 and whitelist the sort fields. Done when 30 seeded products page correctly and sort=salary gives a clean 400, not a 500.
  7. Project 2 — job-portal API (hard). Follow the roadmap's Project 2 steps for this module:
    • Create a new project from Spring Initializr with Web, JPA, Validation, the PostgreSQL driver and Security (you will use Security properly in module 4).
    • Build CRUD endpoints for jobs (and companies) with request and response DTOs and Bean Validation.
    • Add a global error handler that returns consistent JSON errors (ProblemDetail with a field-error list).
    • Add job search by title, location and salary with pagination and sorting.
    • Document every endpoint in Swagger UI with springdoc: tags, summaries, example values and the 400/404 responses.
    Done when a stranger can open Swagger UI, try every endpoint, and get sensible errors for bad input.
  8. Collection and README (hard). Create a Postman or Bruno collection with a local environment (baseUrl, token) and test scripts that check the status code and the Location header. Export it into docs/ and add the curl equivalent of three requests to the README. Done when a teammate can clone the repo, import the collection, and run it end to end.

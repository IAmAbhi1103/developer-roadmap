Almost every backend job means reading and writing a relational database. In Spring Boot you do this with Spring Data JPA, which sits on top of JPA and Hibernate. This module explains the layers from the bottom up: what JDBC does, what an ORM adds, how Hibernate tracks your objects, how entities and relationships are mapped, and how to stop the classic performance traps (the N+1 problem, lazy-loading errors, wrong transaction boundaries).

It builds on module 1 (beans, proxies, AOP — @Transactional is a proxy) and module 2 (the layered Product CRUD API, DTOs, pagination). The SQL itself — indexes, isolation levels, locking, how a database works inside — is in SQL · Module 4, Module 5 and Module 6. Here we use that knowledge from Java. The running example is the job-portal project: User, Company, Job and Application.

ORM, JPA, Hibernate and Spring Data: how they relate

An ORM maps Java objects to database rows; JPA is the standard API for that, Hibernate is the engine that implements it, and Spring Data JPA is a thin layer on top that writes repository code for you.

The problem: the object–relational mismatch

Java stores data as objects: nested, linked by references, with inheritance and collections. A relational database stores rows in tables: flat, linked by foreign keys, with no inheritance and no collections inside a row. Moving data between the two is tedious and full of small differences. This gap is called the object–relational impedance mismatch.

Object worldRelational worldWhat goes wrong by hand
Reference to another objectForeign key columnYou write joins and rebuild the graph yourself
A List<Job> inside CompanyRows in job with company_idOne-to-many is not a column
InheritanceNo such thingYou must choose a table layout
Identity: == / equalsPrimary keyTwo objects, one row
camelCase, Instant, enumssnake_case, timestamptz, text/intConversion code in every query

The layers, from bottom to top

JDBC
The low-level Java API: open a Connection, prepare a statement, set parameters, loop over a ResultSet, map columns to fields, close everything. Reliable, but 20 lines for one query.
JdbcTemplate / JdbcClient
Spring helpers over JDBC. They manage connections, close resources and convert exceptions; you still write the SQL and the row mapping.
ORM (Object-Relational Mapping)
A technique and a kind of library that maps classes to tables and objects to rows, and generates SQL for you.
JPA (Jakarta Persistence API)
A specification: the annotations (@Entity, @Id, @OneToMany), the EntityManager interface and the JPQL query language. It is only interfaces and rules, no code that runs. Packages start with jakarta.persistence (older code uses javax.persistence).
Hibernate
The most-used JPA implementation (also called a provider). It does the real work: tracks changes, generates SQL, caches, lazy-loads. Spring Boot uses it by default. It also has features beyond JPA (@BatchSize, @CreationTimestamp, statistics).
Spring Data JPA
A Spring module that generates repository implementations from interfaces, so findByEmail(String email) becomes a query. It does not replace Hibernate; it calls the EntityManager for you.

Analogy: JPA is like the JDBC idea of "a standard"; Hibernate is like the PostgreSQL driver — one of several implementations (EclipseLink is another). You write to the standard, and run on the implementation.

One query at three levels

// 1. Plain JDBC (about 20 lines in real code)
try (Connection c = dataSource.getConnection();
     PreparedStatement ps = c.prepareStatement(
             "SELECT id, name, email FROM app_user WHERE email = ?")) {
    ps.setString(1, email);
    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) {
            return Optional.of(new User(rs.getLong("id"),
                    rs.getString("name"), rs.getString("email")));
        }
        return Optional.empty();
    }
}

// 2. Spring JdbcClient (Spring Framework 6.1+): SQL stays, plumbing goes
Optional<User> user = jdbcClient
        .sql("SELECT id, name, email FROM app_user WHERE email = :email")
        .param("email", email)
        .query(User.class)
        .optional();

// 3. Spring Data JPA: no SQL, no mapping
public interface UserRepository extends JpaRepository<User, Long> {
    Optional<User> findByEmail(String email);
}

When JdbcTemplate / JdbcClient is the better tool

JPA is excellent for loading and saving object graphs with business rules. It is a poor fit for some jobs. Use JdbcTemplate or JdbcClient (they live in spring-boot-starter-jdbc, which JPA already pulls in) when:

  • You run reports and analytics with window functions, CTEs, many joins and aggregations. Plain SQL is clearer than JPQL.
  • You do bulk operations on millions of rows (INSERT ... SELECT, big updates).
  • The data has no useful object model: a read-only dashboard row, an export file.
  • You need database-specific features (PostgreSQL jsonb operators, full-text search) and want full control.

Mixing is normal: JPA for the write model, JdbcClient for a few heavy read queries. Both can join the same @Transactional transaction because they share one DataSource connection.

WeaknessBoilerplate, no object graphHidden SQL, N+1, learning curve

What the starter gives you

Add spring-boot-starter-data-jpa and a database driver. Boot then auto-configures a DataSource (with HikariCP), a JPA EntityManagerFactory built by Hibernate, a transaction manager, and repository scanning. You write no XML and no persistence.xml. Setup details are in datasource and HikariCP.

Boot 3.x vs 4.x

Spring Boot 3.x uses Hibernate ORM 6.x and Jakarta Persistence 3.1; Spring Boot 4.x moves to Hibernate ORM 7.x. The annotations in these notes (@Entity, @ManyToOne, @Version, @Transactional) and the Spring Data repository style are the same in both. Where something differs, a version note says so. Always keep jakarta.persistence.* imports; javax.persistence stops working from Boot 3.

Mistake: thinking JPA hides the database

JPA hides the syntax, not the database. Every repository call becomes SQL, and bad mappings give slow SQL. Learn to read the SQL log (SQL logging) from day one, and keep your SQL skills sharp (SQL · Module 4).

Interview angle

"What is the difference between JPA, Hibernate and Spring Data JPA?" Strong answer: JPA is the specification (interfaces and annotations); Hibernate is an implementation that generates SQL and manages entities; Spring Data JPA is an abstraction on top that creates repository implementations from interfaces and uses JPA underneath. Persistence context, entity states and dirty checking

The persistence context is Hibernate's per-transaction workspace that tracks every loaded entity; entities in it are "managed", and any change to them is written to the database at flush time without a save() call.

Hibernate does not run SQL the moment you call a setter or persist. It keeps a persistence context (also called the first-level cache or session): a map from (entity type, id) to the entity object, plus a snapshot of the data as it was loaded. Within one transaction there is one EntityManager and one persistence context. In a Spring Boot app, this context lives as long as the transaction (see @Transactional).

The four entity states

Transient (new)
Created with new, not known to any persistence context, no row in the database (yet).
Managed (persistent)
Attached to the persistence context. Hibernate watches it. Entities returned by find or by a query are managed. Anything you change is saved at flush.
Detached
Has an id and may have a row, but the persistence context that loaded it is closed or cleared. Changes are not tracked. This is the state of an entity after the service method returns.
Removed
Managed entity scheduled for deletion; the DELETE is sent at flush.

Dirty checking: no save() needed

When Hibernate loads an entity, it keeps a copy of the loaded values. At flush it compares each managed entity with its snapshot. If a field differs, the entity is dirty and Hibernate issues an UPDATE. This is automatic dirty checking.

@Transactional
public void changeSalary(Long jobId, BigDecimal newMax) {
    Job job = jobRepository.findById(jobId).orElseThrow();   // managed
    job.setSalaryMax(newMax);                                // just a setter
    // no save() call. At commit Hibernate sees the difference and runs:
    // update job set salary_max=?, ... where id=?
}

Calling save() here is harmless (the entity is already managed) but useless. The same code without @Transactional does nothing: findById returns a detached entity once the repository's own tiny transaction ends, and no one flushes the change.

Flush: when SQL is really sent

Flush means "synchronise the persistence context with the database": send the pending INSERT, UPDATE and DELETE statements. It does not commit. With the default FlushModeType.AUTO, a flush happens:

  • before the transaction commits;
  • before a query that could be affected by pending changes (so the query sees them);
  • when you call flush() / saveAndFlush() yourself.

So SQL runs late. A constraint violation (duplicate email) often appears at commit, outside the line that caused it. Call saveAndFlush or flush() when you need the error right there. Exception: with GenerationType.IDENTITY, persist runs the INSERT immediately, because the database must generate the id (see ID strategies).

The first-level cache

@Transactional
public void demo() {
    Job a = jobRepository.findById(1L).get();   // SELECT ... where id=1
    Job b = jobRepository.findById(1L).get();   // no SQL: served from the context
    System.out.println(a == b);                 // true: the very same object
}

Within one persistence context, one row is one object. This guarantees identity (a == b) and saves queries, but only for lookups by id. A JPQL or derived query always goes to the database (it then returns the already-managed instance for rows it has seen). The cache lives and dies with the transaction; it is not shared between requests.

EntityManager basics

The EntityManager is the JPA API behind every repository. You rarely use it directly, but you should know its methods, and you can inject it with @PersistenceContext (or constructor injection) for custom code.

MethodWhat it does
persist(e)Makes a new entity managed; INSERT at flush (or now for IDENTITY). Returns void; e itself becomes managed.
find(Class, id)Loads by id (SELECT unless cached); null if missing.
getReference(Class, id)Returns a lazy proxy with the id, no SELECT; fails later if the row is missing.
merge(e)Copies state of a detached/new object onto a managed copy and returns that copy.
remove(e)Schedules DELETE of a managed entity.
flush()Sends pending SQL now.
detach(e) / clear()Stops tracking one entity / all entities.
refresh(e)Reloads the entity from the database, discarding in-memory changes.

persist vs merge, and how save() chooses

InputA transient entityA detached or transient entity

repository.save(entity) in SimpleJpaRepository is basically:

@Transactional
public <S extends T> S save(S entity) {
    if (entityInformation.isNew(entity)) {
        em.persist(entity);
        return entity;
    } else {
        return em.merge(entity);      // extra SELECT, returns a different object
    }
}

isNew is true when the entity has a @Version attribute of a wrapper type that is null, otherwise when the @Id is null (or 0 for a primitive id). Consequences:

  • With a generated id, new Job() has id null → persist → one INSERT. Good.
  • With an id you assign (a UUID you made, a business code), the id is never null, so save thinks the entity is old and calls merge: a useless SELECT before every insert. Fix: add a @Version Long version field, or implement Persistable<ID> with an isNew() method.
  • Always use the return value of save: job = repo.save(job). After a merge, your original object is not the managed one.

findById vs getReferenceById

@Transactional
public void apply(Long jobId, Long userId, String coverLetter) {
    Application app = new Application();
    app.setJob(jobRepository.getReferenceById(jobId));    // proxy, no SELECT
    app.setApplicant(userRepository.getReferenceById(userId));
    app.setCoverLetter(coverLetter);
    applicationRepository.save(app);   // insert into application (job_id, user_id, ...)
}

findById returns Optional and runs a SELECT (unless cached). getReferenceById (the new name for the old getById) returns a proxy holding only the id, so you can set a foreign key without loading the whole row. If the row does not exist you get an EntityNotFoundException later, when the proxy is first used, or a foreign-key error at flush. Use it when you only need the id; use findById when you must validate existence or read data.

Rules

  • Changes to a managed entity are saved at flush; changes to a detached entity are lost unless you merge/save it.
  • Entity state is only tracked inside a transaction (an open persistence context). Put @Transactional on the service method that changes entities.
  • Use the object returned by save/merge, not the one you passed in.

Exceptions and edge cases

  • PersistentObjectException: detached entity passed to persist — you called persist on an object that already has an id. Use merge (or let save decide).
  • EntityNotFoundException — a getReference proxy points to a missing row.
  • TransientObjectException / TransientPropertyValueException — a managed entity references a transient one that is not persisted and has no cascade.
  • A big loop that loads thousands of entities grows the persistence context (memory + slow dirty checking). For batch jobs, process in chunks and call flush() then clear().
  • Setting a managed field and then throwing a checked exception: the change is still flushed on commit if the transaction does not roll back (see rollback rules).

Mistake: expecting an update without a transaction

Wrong: entity is detached, change is lost

public void rename(Long id, String name) {      // no @Transactional
    Company c = companyRepository.findById(id).orElseThrow();
    c.setName(name);                             // nothing saves this
}

Right: transaction + dirty checking

@Transactional
public void rename(Long id, String name) {
    Company c = companyRepository.findById(id).orElseThrow();
    c.setName(name);                             // UPDATE at commit
}

Interview angle

"What is dirty checking?" At flush Hibernate compares each managed entity with the snapshot taken at load time and issues UPDATEs for changed ones. Follow-ups: "Why does my change not save?" (not in a transaction, entity detached), "When does Hibernate send SQL?" (flush: commit, before queries, explicit flush), "What is the first-level cache?" (per-transaction identity map, only for lookups by id), "persist vs merge?" (see the table).

Entities and mappings: @Entity, @Id, @Column and friends

An entity is a plain Java class marked @Entity with an @Id and a protected no-arg constructor; annotations such as @Table, @Column, @Enumerated and @Embedded describe how fields map to columns.

The rules for an entity class

Rules for entities (JPA spec)

  • Annotate the class with @Entity (jakarta.persistence.Entity).
  • It needs an @Id field (or @EmbeddedId/@IdClass for composite keys).
  • It needs a no-argument constructor, public or protected. protected is the professional choice: Hibernate can use it, your code cannot create half-built objects.
  • The class must not be final, and persistent methods must not be final, because Hibernate creates proxy subclasses for lazy loading.
  • Fields (or getters) must not be final/static to be persisted. Java records cannot be entities (they are final and immutable); records are good as DTOs and embeddables.

A first complete entity

package com.example.jobs.user;

import jakarta.persistence.*;
import java.time.Instant;

@Entity
@Table(name = "app_user",                       // "user" is a reserved word in PostgreSQL
       uniqueConstraints = @UniqueConstraint(name = "uk_user_email", columnNames = "email"))
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 80)
    private String name;

    @Column(nullable = false, length = 150)
    private String email;

    @Column(name = "password_hash", nullable = false, length = 100)
    private String passwordHash;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private Role role;                           // enum Role { CANDIDATE, RECRUITER, ADMIN }

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    protected User() { }                         // for JPA only

    public User(String name, String email, String passwordHash, Role role) {
        this.name = name;
        this.email = email;
        this.passwordHash = passwordHash;
        this.role = role;
    }

    // getters; setters only where the business needs to change the field
}

Naming. Spring Boot's default naming strategy turns createdAt into created_at and JobPosting into job_posting, so @Column(name = "created_at") is optional. Writing it explicitly is still common because it makes the mapping obvious and independent of the strategy.

Length and precision. @Column(length = 80) only affects the DDL that Hibernate generates and gives you no runtime validation. Use Bean Validation (@Size) for the check and keep both in sync with the migration. Money must be BigDecimal with precision and scale, for example @Column(precision = 12, scale = 2); never double.

Enums: STRING, never ORDINAL

Wrong: ORDINAL (the default!)

@Enumerated            // same as EnumType.ORDINAL
private Role role;     // stores 0, 1, 2
// Insert a new constant in the middle of the enum
// and every stored number now means a different role.

Right: STRING

@Enumerated(EnumType.STRING)
@Column(nullable = false, length = 20)
private Role role;     // stores 'CANDIDATE', 'RECRUITER'

Renaming a constant still breaks stored data, so treat enum names as part of your schema. A database CHECK constraint or native enum type can protect the values.

Embedded value objects

A value object has no identity of its own, only values (an address, a money amount, a salary range). Mark the class @Embeddable and use it with @Embedded: its fields become columns of the owner's table.

@Embeddable
public class SalaryRange {
    @Column(name = "salary_min", precision = 12, scale = 2)
    private BigDecimal min;
    @Column(name = "salary_max", precision = 12, scale = 2)
    private BigDecimal max;

    protected SalaryRange() { }
    public SalaryRange(BigDecimal min, BigDecimal max) { this.min = min; this.max = max; }
    // getters; equals/hashCode on both fields
}

@Entity
public class Job {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Embedded
    private SalaryRange salary;          // columns salary_min, salary_max in table job
}

If you embed the same type twice (home and office address), rename columns with @AttributeOverride. If all embedded columns are null, Hibernate loads the embedded field as null, so guard for that.

equals and hashCode for entities

Entities go into Sets and maps, and Hibernate compares them, so equals/hashCode matter. The three obvious choices all have a catch:

ChoiceProblem
Do not override (identity)Fine inside one persistence context. Breaks when the same row is loaded in two contexts, or compared with a detached copy.
All fields (Lombok @Data)Hash changes when a field changes; touches lazy collections; can loop forever on bidirectional links.
Generated idThe id is null before the first save, so the hash changes when the entity is persisted. An entity inside a HashSet gets "lost".
Business key (email, ISBN)Best when you have a stable unique natural key; not always available.

A safe, widely used pattern: equal only when both ids are non-null and equal; hash code constant per class. A constant hash code is fine because it only costs performance in huge sets of entities, which you rarely keep.

import org.hibernate.Hibernate;

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || Hibernate.getClass(this) != Hibernate.getClass(o)) return false;
    Job other = (Job) o;
    return id != null && id.equals(other.id);   // two new objects are never equal
}

@Override
public int hashCode() {
    return Hibernate.getClass(this).hashCode();     // same for all Job instances
}

Hibernate.getClass unwraps a lazy proxy, so proxy.equals(real) works. Never use getClass() != o.getClass() with proxies, and never read fields directly on the other object (other.id on a proxy is null; use other.getId() when the other side may be a proxy). If your entity has a real business key, use it in both methods instead.

Lombok and entities

Lombok is popular but dangerous on entities. @Data generates equals/hashCode/toString over all fields, which causes the problems above plus StackOverflowError when Company.toString() prints its jobs and each Job.toString() prints its company. Use @Getter (and selective @Setter), @NoArgsConstructor(access = AccessLevel.PROTECTED), and if you want toString, exclude relationships: @ToString(exclude = {"jobs"}) or write it by hand with only basic fields.

Design habits that pay off

  • Keep setters out where a method with a business name is clearer: job.close(), user.changeEmail(...).
  • Use Instant (UTC) for timestamps, LocalDate for dates, BigDecimal for money.
  • Keep entities separate from DTOs (module 2).
  • Table names: avoid reserved words (user, order, group); use app_user, orders, etc.

Exceptions and edge cases

  • InstantiationException: No default constructor for entity / HibernateException — the entity has no no-arg constructor.
  • org.hibernate.AnnotationException or MappingException at startup — missing @Id, bad mappedBy, unknown column type.
  • A field holding a lazy proxy compares unequal with ==; use equals as above.
  • Inheritance (@Inheritance, @MappedSuperclass) exists; for a shared base with id and audit columns use @MappedSuperclass (see auditing).

Interview angle

"Why does an entity need a no-arg constructor and why can't it be final?" Hibernate instantiates entities by reflection and creates subclass proxies for lazy loading. "Why EnumType.STRING?" Ordinal values shift when the enum changes. "How do you write equals/hashCode for an entity?" ID generation strategies and ddl-auto

IDENTITY, SEQUENCE and UUID decide who creates primary keys and whether JDBC batching works; spring.jpa.hibernate.ddl-auto decides whether Hibernate touches your schema, and in production it should be validate or none.

@GeneratedValue strategies

@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "job_seq")
@SequenceGenerator(name = "job_seq", sequenceName = "job_seq", allocationSize = 50)
private Long id;
IDENTITY
Uses an auto-increment column (BIGSERIAL / GENERATED ... AS IDENTITY in PostgreSQL, AUTO_INCREMENT in MySQL). The database creates the id during INSERT, so Hibernate must run the INSERT immediately on persist to learn the id. Result: simple, but JDBC insert batching is disabled.
SEQUENCE
Uses a database sequence object. Hibernate asks the sequence for a number before the INSERT, so it can delay and batch inserts. Supported by PostgreSQL, Oracle, H2, SQL Server and MariaDB; not by MySQL, where Hibernate falls back to a table-like emulation or you use IDENTITY.
UUID
GenerationType.UUID (JPA 3.1) generates a random UUID in Java; the field type is java.util.UUID. No database round trip, ids are globally unique and safe to expose, but they are 16 bytes and random, so B-tree indexes fragment and are bigger than a bigint.
AUTO
Lets the provider choose. In Hibernate 6+ it picks SEQUENCE for numeric ids on databases that support sequences, UUID for UUID fields, and IDENTITY or a table emulation elsewhere. Convenient for demos, but explicit is better in real code.
TABLE
Keeps ids in a helper table. Slow because of locking; almost never used.

allocationSize: why SEQUENCE is faster

With allocationSize = 50 (the default for sequence generators), Hibernate calls the sequence once, gets a value like 1000, and hands out the next 50 ids (951–1000 or 1000–1049, depending on the optimizer) from memory. One sequence call per 50 inserts. The database sequence must use the same increment (INCREMENT BY 50); if they differ, Hibernate warns or generates duplicates. A Flyway migration should create it:

CREATE SEQUENCE job_seq START WITH 1 INCREMENT BY 50;

Side effect: ids have gaps after restarts (unused ids of a block are lost). That is normal; never rely on gap-free ids.

Practical guidance: PostgreSQL + heavy inserts → SEQUENCE; MySQL → IDENTITY; distributed or public ids → UUID (or a time-ordered UUID/ULID if index locality matters). For small CRUD apps like the Product example in module 2, IDENTITY is perfectly fine.

spring.jpa.hibernate.ddl-auto

Hibernate can read your entities and create or change tables. The property spring.jpa.hibernate.ddl-auto controls it:

ValueWhat Hibernate does at startupUse
noneNothingProduction (schema from Flyway)
validateCompares entities with the schema; fails startup on a mismatch (missing table/column, wrong type). Changes nothing.Production, staging, CI

Boot's default is create-drop for an embedded database (H2) with no schema manager, and none for a real database. Do not rely on defaults: set the value explicitly in each profile.

spring.jpa.hibernate.ddl-auto=validate
spring.flyway.enabled=true

Mistake: update (or create) in production

  • update cannot rename a column (it adds a new empty one), cannot change a type safely, never removes anything, and gives you no history or review of what changed.
  • create or create-drop on a production URL deletes every row at startup. This has happened to real companies.
  • Use versioned migrations instead (Flyway) and let Hibernate only validate. Hibernate-generated DDL is also not tuned: no indexes beyond keys and uniques you declared, default varchar(255).

Tip: see the DDL without running it

For a first draft of a migration, run once with ddl-auto=create on a throwaway local database and copy the SQL from the log, or use Hibernate's schema generation properties. Then review it by hand, add indexes and constraint names, and commit it as V1__init.sql.

Exceptions and edge cases

  • SchemaManagementException: Schema-validation: missing column [x] in table [y] — validate found an entity field with no column.
  • Schema-validation: wrong column type — for example entity String versus text, or Long versus integer. Fix the migration or the mapping.
  • IDENTITY inserts with hibernate.jdbc.batch_size set: Hibernate silently does not batch them.
  • Sequence increment mismatch: duplicate-key errors or a warning about allocationSize.

Interview angle

"IDENTITY vs SEQUENCE?" Mention who generates the id, the early INSERT, and that only SEQUENCE allows batch inserts; mention allocationSize and gaps. "What ddl-auto do you use in production?" validate or none with Flyway, and explain why update is unsafe.

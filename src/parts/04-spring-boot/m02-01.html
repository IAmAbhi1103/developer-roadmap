Almost every Spring Boot job is about one thing: building REST APIs — HTTP endpoints that a React app, a mobile app or another service calls to read and change data, usually as JSON. This module takes you from the raw text of an HTTP request all the way to a layered, validated, documented CRUD API with clean error responses and pagination.

It builds on Spring fundamentals (Module 1: beans, dependency injection, configuration). The repository layer uses Spring Data JPA, which Module 3 explains in depth; Module 4 secures the API and Module 5 tests it. The React app in Frontend · Module 6 is the client that consumes what you build here. Examples work on Spring Boot 3.x and 4.x; where the two differ, a version note says so.

After this module you will be able to:

  • read and write raw HTTP requests and responses, and choose the right method, status code and headers;
  • design resource URLs, version an API, and explain what makes an API RESTful;
  • build controllers with the mapping annotations and explain how a request travels through Spring MVC;
  • split an application into controller, service and repository layers, and map entities to DTOs by hand or with MapStruct;
  • validate input with Bean Validation and return consistent error JSON with ProblemDetail;
  • add pagination, sorting and filtering, document the API with Swagger UI, and test it with curl, Postman or Bruno.

HTTP basics: how a request and a response look

HTTP is a text-based request–response protocol: the client sends a method, a URL, headers and an optional body, and the server answers with a status code, headers and an optional body.

Every REST API runs on HTTP (HyperText Transfer Protocol). Your React app, Postman, curl and a mobile app all do the same thing: open a connection, send one request, and read one response. Spring annotations only make sense when you can read the raw messages, because that is what your controller methods really work with.

The five words you need first

Client
The program that sends the request: a browser, a React app, a mobile app, curl, or another service.
Server
The program that listens and answers. For you, that is your Spring Boot application running inside an embedded Tomcat.
Resource
A "thing" the API exposes, named by a URL: a product, an order, a user.
Request
One message from client to server that says "do this method on that URL".
Response
The server's single reply to a request: a status code, headers and, usually, a body.

A request, line by line

This is exactly what travels over the network when a client creates a product. Nothing is hidden: it is plain text.

POST /api/v1/products HTTP/1.1
Host: localhost:8080
Content-Type: application/json
Accept: application/json
Content-Length: 68

{"sku":"MSE-1001","name":"Wireless Mouse","price":799.00,"stock":25}
  1. Request line — three parts: the method (POST), the request target (path plus query string: /api/v1/products) and the protocol version (HTTP/1.1).
  2. Headers — one Name: value pair per line. They describe the request: which host, what format the body is in, what format the client wants back, how long the body is.
  3. An empty line — this blank line is the signal "headers are over".
  4. Body (optional) — the data. A GET normally has none; a POST or PUT usually carries JSON.

A response, line by line

HTTP/1.1 201 Created
Content-Type: application/json
Location: http://localhost:8080/api/v1/products/1
Content-Length: 75
Date: Wed, 21 Oct 2026 04:45:30 GMT

{"id":1,"sku":"MSE-1001","name":"Wireless Mouse","price":799.00,"stock":25}

The first line is the status line: protocol version, a three-digit status code (201) and a short reason phrase (Created). The reason phrase is optional and clients ignore it — Spring Boot's Tomcat usually sends just HTTP/1.1 201. Then come the response headers, a blank line and the body. Code decides everything; the phrase is only for humans.

A URL tells the client where the resource lives. Take this one:

HTTP is stateless

The server treats every request as a brand-new conversation. It does not remember that you called it a second ago. That is called being stateless. To stay "logged in", the client must send proof with every request: either a session cookie (Cookie: JSESSIONID=…) or a token (Authorization: Bearer …). REST APIs prefer tokens, because any server instance can verify a token without shared memory — you will build this in Module 4.

HTTP/1.1, HTTP/2 and HTTP/3

VersionHow it travelsWhat changes for you
HTTP/1.1Plain text messages; one request at a time per connection (the connection can be reused)This is what you see in curl. It is the default for Tomcat.
HTTP/2Binary frames; many requests in parallel on one connection; compressed headersSame methods, status codes and headers. Spring Boot can enable it with server.http2.enabled=true; browsers use it only over HTTPS.
HTTP/3Same meaning as HTTP/2, but over QUIC (UDP) instead of TCPUsually handled by a CDN or load balancer, not by your Spring app.

The important point: the meaning (methods, status codes, headers, bodies) is the same in all versions. Learn the semantics once.

Rules of the message format

  • A message is: start line, headers, an empty line, optional body — in that order.
  • Header names are case-insensitive (content-type equals Content-Type). Header values and URL paths are normally case-sensitive.
  • HTTP/1.1 requires a Host header.
  • If there is a body, the sender says how long it is (Content-Length) or sends it in chunks (Transfer-Encoding: chunked).

Edge cases

  • A GET request can carry a body, but its meaning is undefined and many proxies and servers drop it. Do not design APIs that depend on it.
  • Some responses never have a body: replies to HEAD, 204 No Content and 304 Not Modified.
  • Very long URLs get rejected. Servers usually limit the request line plus headers to a few KB (Tomcat's default is 8 KB), so never pack big data into the query string.
  • Local development uses plain http://localhost:8080. In production, HTTPS is mandatory; it is usually terminated by a reverse proxy or load balancer in front of your app (see DevOps · Module 2).

Mistake: putting secrets in the URL

Everything in the URL ends up in server logs, browser history, proxy logs and the Referer header. Passwords and tokens belong in the body or in the Authorization header, and always over HTTPS.

Wrong: credentials in the query string

GET /login?user=ravi&password=Secret@123 HTTP/1.1
Host: shop.example.com

Right: credentials in the body, over HTTPS

POST /api/v1/auth/login HTTP/1.1
Host: shop.example.com
Content-Type: application/json

{"email":"ravi@example.com","password":"Secret@123"}

Interview: "What is HTTP? What does stateless mean?"

  • HTTP is an application-layer request–response protocol over TCP (or QUIC for HTTP/3). The client always starts; the server only replies.
  • A request has a method, a target, headers and an optional body. A response has a status code, headers and an optional body.
  • Stateless means the server keeps no memory of earlier requests; each request carries everything needed, such as a token. This lets you run many identical server instances behind a load balancer.
  • HTTPS is HTTP over TLS: it encrypts the traffic and proves the server's identity with a certificate. The HTTP messages themselves are unchanged.

HTTP methods: purpose, safe and idempotent

The method says what you want to do with a resource; safe methods never change server state, and idempotent methods leave the server in the same state whether you call them once or ten times.

An HTTP method (also called a verb) is the first word of a request. It tells the server the intent: read, create, replace, change, delete. The URL names the resource, and the method says what to do with it. If you pick methods correctly, clients, proxies, caches and browsers all behave correctly without extra work.

The methods at a glance

MethodPurposeRequest bodySafeIdempotent

POSTCreate a resource, or trigger an actionYesNoNo
PUTReplace a resource completelyYesNoYes
PATCHChange part of a resourceYesNoNot guaranteed

Safe and idempotent — two different ideas

Safe
The method only reads. It must not change anything the user cares about on the server. Because GET is safe, browsers can prefetch it, search-engine crawlers can follow it, and caches can store its response.
Idempotent
Sending the same request many times has the same effect on the server as sending it once. This is what makes a request safe to retry after a network timeout, when the client does not know whether the first attempt worked.

Every safe method is idempotent, but not the other way round: DELETE changes state, yet deleting the same product twice leaves the same final state — the product is gone. The response may differ (first call 204, second call 404); idempotency is about server state, not about identical responses.

Idempotency is a promise that you keep in your code. HTTP does not enforce it. If you write a PUT handler that appends to a list each time, it is no longer idempotent, and clients that retry will create damage.

POST vs PUT vs PATCH

These three cause the most confusion. Use the same product to compare them.

Content-Type: application/json

{"sku":"MSE-1001","name":"Wireless Mouse","price":799.00,"stock":25}
PUT /api/v1/products/1 HTTP/1.1
Content-Type: application/json

{"name":"Wireless Mouse","description":"Silent click","price":749.00,"stock":25}
PATCH /api/v1/products/1 HTTP/1.1
Content-Type: application/json

{"price":749.00}

Target URLA collection (/products)One resource (/products/1)One resource (/products/1)

Why PATCH is "not guaranteed" idempotent: it depends on what the patch says. {"status":"SHIPPED"} sets a value, so repeating it changes nothing — idempotent. {"stockDelta":-1} subtracts one each time — not idempotent. The method itself does not decide; your design does.

PUT can also create. If the client chooses the id and the resource does not exist yet, PUT /users/ravi may create it (return 201); if it exists, replace it (return 200 or 204). Most Spring APIs use PUT only for replacing an existing resource and generate ids on the server with POST.

Making a POST safe to retry: the Idempotency-Key pattern

Creating a payment with POST is the classic danger: the client times out, retries, and the customer is charged twice. Payment APIs such as Stripe solve this with an idempotency key: the client generates a unique value (a UUID) and sends it in a header. Spring has no built-in feature for this; you implement it in a filter or in the service.

  1. The client sends POST /payments with Idempotency-Key: 7c9e6679-….
  2. The server looks the key up in a table. If the key is new, it processes the payment and stores the key together with the response it produced.
  3. If the client retries with the same key, the server does not process again. It returns the stored response.
  4. Keys expire after some time (for example 24 hours), and the same key with a different body is rejected with 422 or 409.

What Spring does for you

In Spring MVC each method has a mapping annotation (@GetMapping, @PostMapping, @PutMapping, @PatchMapping, @DeleteMapping; see the mapping annotations article). Two things happen automatically: a GET mapping also answers HEAD (the body is dropped), and OPTIONS on a mapped path returns an Allow header that lists the supported methods.

$ curl -i -X OPTIONS http://localhost:8080/api/v1/products
HTTP/1.1 200
Allow: GET,HEAD,POST,OPTIONS
Content-Length: 0

Rules

  • GET, HEAD and OPTIONS must never change data. No "delete" or "cancel" behind a GET.
  • PUT and DELETE must be idempotent. Design them so that a retry is harmless.
  • Only GET and HEAD responses are normally cached.
  • A wrong method on a known URL must give 405 Method Not Allowed with an Allow header. Spring does this for you (HttpRequestMethodNotSupportedException).

Conventions

  • One URL, several methods: /products supports GET and POST; /products/{id} supports GET, PUT, PATCH and DELETE.
  • Prefer PATCH for partial updates and keep PUT for full replacement. If you only offer one update endpoint, PUT with the full body is the simplest and safest.
  • Return the updated resource (200) or nothing (204) from PUT/PATCH — pick one style for the whole API.

Edge cases

  • The second DELETE of the same id: return 404 (honest) or 204 (idempotent outcome). Both are valid; stay consistent.
  • DELETE with a body is allowed but unreliable; some proxies strip it. Put the identifier in the URL.
  • Plain HTML forms can only send GET and POST. That limit does not apply to fetch/axios in a React app.
  • Firewalls and old proxies sometimes block PUT, PATCH and DELETE. If a client behind such a network fails, this is the first thing to check.
  • TRACE and CONNECT exist but are not used for APIs; TRACE is normally disabled.

Mistake: using GET for actions

A link, a browser prefetch or a crawler can call any GET URL. If that URL deletes data, the data disappears without anyone clicking "delete".

Wrong: a state change behind GET

@GetMapping("/products/{id}/delete")
public void delete(@PathVariable Long id) {
    service.delete(id);
}

Right: DELETE on the resource

@DeleteMapping("/products/{id}")
@ResponseStatus(HttpStatus.NO_CONTENT)
public void delete(@PathVariable Long id) {
    service.delete(id);
}

Interview: "PUT vs PATCH vs POST?" and "Is DELETE idempotent?"

  • POST creates under a collection and is not idempotent. PUT replaces a whole resource at a known URL and is idempotent. PATCH changes part of a resource and is idempotent only if the change itself is.
  • Safe = read-only (GET, HEAD, OPTIONS). Idempotent = same server state after one or many identical calls (safe methods plus PUT and DELETE).
  • DELETE is idempotent because the end state is the same ("not there") even though the second call may answer 404.
  • Mention retries: idempotency is why clients and gateways can retry PUT and DELETE automatically, and why POST needs an idempotency key for payments.

HTTP status codes and which one to return

The first digit of a status code tells the class — 2xx success, 3xx redirect, 4xx client error, 5xx server error — and a good API returns the most specific code so clients can react without reading the body.

A status code is the three-digit number at the start of every response. Clients, browsers, load balancers and monitoring dashboards all make decisions from it alone: retry or not, show an error or not, count it as a failure or not. Returning 200 for everything and hiding the real outcome in the body breaks all of that.

The five classes

1xxInformational (for example 100 Continue)Handled by the HTTP stack; you rarely see them.
2xxSuccess — the request workedNobody; carry on.
3xxRedirection — look somewhere else, or use your cached copyThe client follows the Location header.
4xxClient error — the request is wrongThe caller must fix the request. Retrying the same request will not help (exceptions: 408, 429).
5xxServer error — the server failedYou must fix it. The client may retry later.

Choosing a code: a quick decision path

In Spring the order is slightly different in one place: the request body is validated before your method runs. So a bad body sent to a missing id gives 400, not 404.

401 vs 403

400 vs 422 for validation errors

Both are used in real APIs. 400 means "I cannot understand or accept this request" and is what Spring returns by default for malformed JSON and failed @Valid checks. 422 means "I understood the JSON, but the values break rules". Pick one for validation, document it, and use it everywhere. These notes use 400 because it is Spring's default.

In your own code, pick codes with the HttpStatus enum (HttpStatus.CREATED) or by number (ResponseEntity.status(409)). Spring 6 also has the HttpStatusCode interface, which covers any number, including codes that are not in the enum.

Rules

  • A 201 response should carry a Location header; a 204 response must not have a body.
  • A 401 response should carry WWW-Authenticate; a 405 response must carry Allow.
  • The error body must match the status. Never send 200 with {"error": ...}.
  • 4xx means "the caller can fix it"; 5xx means "we have a bug or an outage". Use them honestly so monitoring works.

Conventions

  • An empty collection is 200 with [], not 404. The collection exists; it is just empty.
  • To hide that something exists (another user's order), answer 404 instead of 403.
  • Use 409 for business-rule clashes (duplicate SKU, insufficient stock), and put the explanation in the error body.
  • Return a consistent error body for every 4xx and 5xx (the ProblemDetail articles in this module).

Edge cases

  • A search with no matches is 200 and [], but GET /products/9999 for a missing id is 404.
  • Redirects (301, 302) may change a POST into a GET in some clients. 307 and 308 keep the method and body.
  • Behind a gateway, 502, 503 and 504 usually come from the gateway, not from your Spring app. Check the gateway logs first.
  • If an exception is thrown after the response has started streaming, the status is already sent and cannot change.

Mistake: success status with an error inside

Clients, caches and dashboards read the status code first. A 200 that contains "success": false looks like a success everywhere except in your own front-end code.

Wrong: HTTP 200 for a missing product

@GetMapping("/{id}")
public Map<String, Object> get(@PathVariable Long id) {
    Optional<Product> product = repository.findById(id);
    if (product.isEmpty()) {
        return Map.of("success", false, "message", "Product not found");
    }
    return Map.of("success", true, "data", product.get());
}

Right: throw, and let the handler answer 404

@GetMapping("/{id}")
public ProductResponse get(@PathVariable Long id) {
    // throws ResourceNotFoundException, which the global
    // handler turns into a 404 response
    return service.findById(id);
}

Interview: "401 vs 403? 200 vs 201 vs 204? When 409?"

  • 401 = not authenticated (no or bad credentials). 403 = authenticated but not authorised.
  • 200 = success with a body, 201 = something was created (with Location), 204 = success with no body.
  • 409 = the request conflicts with the current state: a duplicate email, an optimistic-locking version clash, deleting a record that others still use.
  • 400 = malformed or invalid input; 422 = well-formed but semantically invalid; 404 = no such resource; 405 = wrong method; 415 = wrong Content-Type.
  • 502, 503 and 504 are gateway-side failures: bad reply, unavailable, and timeout. 500 is an unexpected bug in the service itself.

HTTP headers that matter for APIs

Headers are name–value metadata on a request or response; Content-Type, Accept, Authorization, Location, Cache-Control and ETag do most of the work in a REST API.

A header is one line of the form Name: value placed before the body. Headers carry information about the message: what format the body is in, who is calling, how long the answer may be cached. Your JSON stays clean because this extra information travels beside it.

Content-Type vs Accept

These two are confused all the time. Content-Type describes the data I am sending. Accept describes the data I want back.

HeaderDirectionIf it is wrong, Spring answers…
Content-Type on the requestDescribes the request body415 Unsupported Media Type when no converter can read that type
Accept on the requestAsks for a response format406 Not Acceptable when no converter can produce it

A very common surprise: curl -d '{"name":"x"}' sends Content-Type: application/x-www-form-urlencoded by default, so your JSON endpoint answers 415. Always add -H "Content-Type: application/json", or use curl --json '…' (curl 7.82 and newer), which sets both Content-Type and Accept for you.

Authorization

The caller proves who it is with Authorization: <scheme> <credentials>. Two schemes matter. Basic sends username:password encoded in Base64 — encoded, not encrypted, so it is only acceptable over HTTPS. Bearer sends a token, usually a JWT: Authorization: Bearer eyJhbGciOi…. "Bearer" means whoever holds the token is let in, so treat tokens like passwords. Module 4 builds the JWT flow. Never send credentials in the URL.

Caching with Cache-Control

Cache-Control tells browsers and proxies whether and how long they may reuse a response.

  • max-age=60 — the response is fresh for 60 seconds; reuse it without asking the server.
  • no-cache — you may store it, but you must revalidate with the server before every reuse.
  • no-store — do not store it at all. Use it for sensitive data such as account details.
  • public / private — shared caches (CDNs) may store it / only the user's own browser may.

ETag and conditional requests

An ETag is a label for one version of a representation, such as a hash or a version number. The client stores it and sends it back, and the server can reply "nothing changed" instead of resending the body.

@GetMapping("/{id}")
public ResponseEntity<ProductResponse> get(@PathVariable Long id) {
    ProductResponse product = service.findById(id);
    return ResponseEntity.ok()
            .eTag(String.valueOf(product.version()))   // quotes are added for you
            .cacheControl(CacheControl.maxAge(Duration.ofSeconds(60)).cachePublic())
            .body(product);
}
GET /api/v1/products/1 HTTP/1.1
Host: localhost:8080
If-None-Match: "3"

HTTP/1.1 304
ETag: "3"
Cache-Control: max-age=60, public

When a ResponseEntity carries an ETag and the request has a matching If-None-Match, Spring turns the reply into 304 for you. If you do not want to compute ETags yourself, register Spring's ShallowEtagHeaderFilter: it hashes each response body and adds the ETag. It saves bandwidth, not server work, because the handler still runs.

If-Match solves a different problem: the lost update. Two users load product 1 (ETag "3"). User A saves; the ETag becomes "4". User B then sends PUT with If-Match: "3", the server sees the mismatch and answers 412 Precondition Failed instead of silently overwriting A's change. In a JPA application the ETag is usually the @Version column (Module 3).

Reading and setting headers in Spring

  • Read a header with @RequestHeader (details in the request body and headers article).
  • Set response headers with ResponseEntity builders (the ResponseEntity article), with HttpHeaders, or on the HttpServletResponse parameter.
  • CORS headers (Origin, Access-Control-Allow-Origin, …) are covered in the CORS article; Spring Security also adds protective headers such as X-Content-Type-Options (Module 4).

Rules

  • Send Content-Type: application/json whenever the request has a JSON body.
  • Every 201 Created response needs a Location header; every 405 needs Allow.
  • Never put tokens or passwords in URLs; use Authorization.
  • Weak validators, W/"abc", mean "semantically the same"; strong ones mean "byte-for-byte the same". If-Match needs strong ETags.

Edge cases

  • Some headers repeat or hold a comma-separated list (Accept: application/json, text/plain;q=0.5). The q value is a preference weight from 0 to 1.
  • Oversized headers (huge cookies or tokens) can be rejected by Tomcat or a proxy with a 400 or 431 before your code runs.
  • Behind a reverse proxy, the original client IP and scheme arrive in X-Forwarded-For and X-Forwarded-Proto. Without server.forward-headers-strategy set, Spring may build wrong absolute URLs (for example in Location).
  • Browsers hide most response headers from JavaScript on cross-origin calls unless the server lists them in Access-Control-Expose-Headers.

Mistake: forgetting Content-Type on a JSON POST

Without Content-Type: application/json your @RequestBody endpoint cannot choose a converter and returns 415. Testing tools set the header for you only if you pick "JSON" as the body type.

Wrong: curl sends a form content type

$ curl -i -X POST http://localhost:8080/api/v1/products \
    -d '{"name":"Mouse"}'
HTTP/1.1 415

Right: declare the body as JSON

$ curl -i -X POST http://localhost:8080/api/v1/products \
    -H "Content-Type: application/json" \
    -d '{"name":"Mouse"}'

Real projects

In a typical service you read Authorization in Spring Security (not by hand), add a X-Request-Id or traceparent header in a filter so logs from several services line up, set Cache-Control: no-store on anything personal, and add ETags only to read-heavy endpoints that really benefit, such as product details or reference data.

Interview: "Content-Type vs Accept? How does ETag caching work? no-cache vs no-store?"

  • Content-Type labels the body you send; Accept lists the formats you want back. Wrong values give 415 and 406.
  • ETag: the server labels a version; the client sends it back in If-None-Match; if unchanged, the server returns 304 with no body. With If-Match the same label protects updates from lost writes (412).
  • no-cache means "revalidate before reuse"; no-store means "never keep a copy".
  • Tokens go in Authorization: Bearer …, never in the URL. Basic auth is only Base64, not encryption.

Calling other APIs: RestClient, HTTP service clients, WebClient and RestTemplate

Use RestClient (Spring 6.1+, Boot 3.2+) for synchronous HTTP calls with a fluent API, wrap it in an @HttpExchange interface for a declarative client, always set timeouts, and map error statuses deliberately.

What and why

Your backend often calls other services: a payment gateway, a resume parser, an email API, another microservice. This is an outgoing HTTP call, the mirror image of a controller. It is where production systems fail most: the other side is slow, down or returns something unexpected. So the three rules are: set timeouts, handle errors explicitly, and decide what to do when the call fails (retry, fallback, circuit breaker; see Resilience4j).

The four clients: which one?

ClientStyleStatusUse it for
RestClientSynchronous, fluentCurrent (since Spring 6.1 / Boot 3.2)New code in a servlet (blocking) application
HTTP service client (@HttpExchange)Declarative interface on top of RestClient or WebClientCurrentA typed client for one remote API; the least code
WebClientReactive (Mono/Flux), also works blockingCurrent, part of WebFluxReactive apps, streaming, parallel calls
RestTemplateSynchronous, template methodsMaintenance mode; will not get new featuresExisting code; do not start new code with it

You will meet RestTemplate in most older codebases and interviews, so know its methods (getForObject, postForEntity, exchange). RestClient was created to give the same blocking model with the modern fluent style of WebClient, without needing the reactive stack.

RestClient basics

Boot provides a RestClient.Builder bean already configured (message converters, observability). Inject it, set a base URL and defaults once, and keep the built client in a bean:

@Configuration
public class PaymentClientConfig {

    @Bean
    RestClient paymentRestClient(RestClient.Builder builder,
                                 @Value("${payments.base-url}") String baseUrl,
                                 @Value("${payments.api-key}") String apiKey) {

        SimpleClientHttpRequestFactory factory = new SimpleClientHttpRequestFactory();
        factory.setConnectTimeout(2000);        // ms to open the connection
        factory.setReadTimeout(5000);           // ms to wait for the response

        return builder
                .baseUrl(baseUrl)
                .defaultHeader(HttpHeaders.AUTHORIZATION, "Bearer " + apiKey)
                .defaultHeader(HttpHeaders.ACCEPT, MediaType.APPLICATION_JSON_VALUE)
                .requestFactory(factory)
                .build();
    }
}
@Service
public class PaymentGateway {

    private final RestClient client;
    public PaymentGateway(@Qualifier("paymentRestClient") RestClient client) { this.client = client; }

    public PaymentStatus status(String paymentId) {
        return client.get()
                .uri("/payments/{id}", paymentId)               // URI template: encoded safely
                .retrieve()
                .body(PaymentStatus.class);                     // deserialises JSON into a record
    }

    public ResponseEntity<PaymentResponse> pay(PaymentRequest request) {
        return client.post()
                .uri("/payments")
                .contentType(MediaType.APPLICATION_JSON)
                .body(request)                                  // serialised to JSON
                .retrieve()
                .toEntity(PaymentResponse.class);               // status, headers and body
    }

    public List<PaymentStatus> recent(int days) {
        return client.get()
                .uri(b -> b.path("/payments").queryParam("days", days).build())
                .retrieve()
                .body(new ParameterizedTypeReference<List<PaymentStatus>>() { });  // generics
    }
}
  • retrieve() is the simple path: send, check status, give the body. exchange() gives full control of the raw response when you need it.
  • body(Class) returns the object; toEntity(Class) keeps headers and status; toBodilessEntity() ignores the body; .body(new ParameterizedTypeReference<...>(){}) keeps generic types.
  • Use URI templates ("/payments/{id}") instead of string concatenation, so values are encoded and you do not get injection into the URL.

Error handling with onStatus

By default, retrieve() throws HttpClientErrorException (4xx) or HttpServerErrorException (5xx), both subclasses of RestClientResponseException. Turn these into your own domain exceptions, so the rest of your code does not depend on HTTP:

public PaymentStatus status(String paymentId) {
    return client.get()
            .uri("/payments/{id}", paymentId)
            .retrieve()
            .onStatus(status -> status.value() == 404, (request, response) -> {
                throw new PaymentNotFoundException(paymentId);
            })
            .onStatus(HttpStatusCode::is5xxServerError, (request, response) -> {
                throw new PaymentProviderException("Provider error " + response.getStatusCode());
            })
            .body(PaymentStatus.class);
}

Other failures: a connection refused or a timeout surfaces as ResourceAccessException (wrapping ConnectException or SocketTimeoutException). Catch it where you decide to retry or fall back. Never log the full request when it holds API keys or personal data.

Timeouts: always

The default of many HTTP clients is "wait for ever". One slow dependency then occupies all your threads and your whole application stops answering: a cascading failure. Always set a connect timeout (1 to 3 s) and a read timeout (based on the remote service's normal speed, for example 3 to 10 s). Three ways, from simplest:

  • Boot properties (Boot 3.4+): spring.http.client.connect-timeout and spring.http.client.read-timeout apply to clients built from the auto-configured builder.
  • A request factory in code, as above (SimpleClientHttpRequestFactory, JdkClientHttpRequestFactory, or the Apache / Jetty factories when those libraries are present).
  • Resilience4j @TimeLimiter as an outer deadline for the whole operation.

Retries are the next layer; they belong with circuit breakers and backoff in module 7. Retry only idempotent calls (GET, PUT, DELETE), not a payment POST unless the API supports idempotency keys.

HTTP service clients: a declarative interface

Instead of writing a class full of client.get().uri(...), describe the remote API as an interface. Spring creates the implementation (a proxy) at runtime; the style is like Feign or Retrofit.

import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.service.annotation.GetExchange;
import org.springframework.web.service.annotation.HttpExchange;
import org.springframework.web.service.annotation.PostExchange;

@HttpExchange("/api/companies")
public interface CompanyDirectoryApi {

    @GetExchange("/{id}")
    CompanyDto byId(@PathVariable("id") Long id);

    @GetExchange
    List<CompanyDto> search(@RequestParam("q") String query);

    @PostExchange
    CompanyDto create(@RequestBody CompanyDto company);
}
@Configuration
public class DirectoryClientConfig {

    @Bean
    CompanyDirectoryApi companyDirectoryApi(RestClient.Builder builder,
                                            @Value("${directory.base-url}") String baseUrl) {
        RestClient restClient = builder.baseUrl(baseUrl).build();
        RestClientAdapter adapter = RestClientAdapter.create(restClient);
        HttpServiceProxyFactory factory = HttpServiceProxyFactory.builderFor(adapter).build();
        return factory.createClient(CompanyDirectoryApi.class);
    }
}

Now other beans just inject CompanyDirectoryApi and call api.byId(5L). The same interface with a WebClientAdapter works on WebClient. Methods can return the body type, ResponseEntity<T>, or void. It uses the Spring MVC annotations for parameters (@PathVariable, @RequestParam, @RequestBody, @RequestHeader) and its own @HttpExchange family for the verb and path (@GetExchange, @PostExchange, @PutExchange, @DeleteExchange, @PatchExchange).

Version note

HttpServiceProxyFactory is available from Spring Framework 6.0, and RestClient support from 6.1. Spring Framework 7 / Boot 4 adds simpler registration of such clients (annotations and properties so you do not write the factory bean yourself); the interface you write stays the same, only the bean wiring becomes shorter. Check the Spring reference for your version if you use 7 or later.

WebClient and RestTemplate in short

WebClient webClient = WebClient.builder().baseUrl("https://api.example.com").build();

Mono<PaymentStatus> mono = webClient.get().uri("/payments/{id}", id)
        .retrieve().bodyToMono(PaymentStatus.class);          // reactive: nothing happens until subscribed

PaymentStatus blocking = mono.block(Duration.ofSeconds(5));   // blocking style, with a timeout
RestTemplate rest = new RestTemplateBuilder()
        .rootUri("https://api.example.com")
        .connectTimeout(Duration.ofSeconds(2))        // method names differ between Boot versions
        .readTimeout(Duration.ofSeconds(5))
        .build();

PaymentStatus s = rest.getForObject("/payments/{id}", PaymentStatus.class, id);
ResponseEntity<PaymentResponse> r = rest.postForEntity("/payments", request, PaymentResponse.class);

Do not add the WebFlux starter to a servlet app just for WebClient; use RestClient. Choose WebClient when your whole stack is reactive or you must call many services in parallel without blocking threads.

Testing outgoing calls

Test your client against a fake server: MockRestServiceServer (bind it to the RestClient.Builder with MockRestServiceServer.bindTo(builder)), or WireMock / MockWebServer for real HTTP. Test the error cases too: 404, 500, a slow response, an invalid JSON. See module 5.

Common mistakes

  • No timeouts, so one slow dependency freezes the application.
  • Creating a new client (RestClient.create()) for each call: lose pooling and configuration. Build once, reuse.
  • Calling a remote API inside a database transaction, holding a connection while waiting.
  • Catching Exception and returning an empty object: the failure becomes invisible.
  • Retrying non-idempotent POSTs and charging a customer twice.
  • Building URLs with string concatenation of user input.

Interview angle

"RestTemplate vs RestClient vs WebClient?" Legacy blocking, modern blocking, reactive. "What is an HTTP service client?" A proxy generated from an @HttpExchange interface. "What happens if the remote service is slow?" Timeouts, then circuit breaker and fallback. "How do you handle 4xx and 5xx?" onStatus, map to domain exceptions.

Rate limiting: algorithms, Bucket4j, 429 responses and distributed limits

Rate limiting caps how many requests a client may make in a time window; implement a token bucket per user or IP (Bucket4j) in a filter, return 429 with Retry-After, store counters in Redis when you run several instances, and prefer doing coarse limiting at the gateway or Nginx.

What and why

Rate limiting restricts how often a client may call your API. Reasons:

  • Abuse and attacks: brute-force logins, OTP guessing, scraping, a denial-of-service attempt.
  • Cost: every request that sends an email or calls a paid API costs money.
  • Fairness and stability: one noisy client must not slow the service for everyone.
  • Protecting downstream systems (database, third-party APIs with their own limits).

Algorithms in brief

AlgorithmHow it worksGoodWeak
Fixed windowCount requests per clock window (per minute); reset at the boundarySimplest; one Redis keyBurst at the boundary: 100 at 10:00:59 and 100 at 10:01:00
Sliding windowCount the last N seconds continuously (log of timestamps, or weighted two windows)Smooth, accurateMore memory and work
Token bucketBucket holds up to N tokens; each request takes one; tokens refill at a steady rateAllows short bursts, enforces the average rate; cheapTwo parameters to tune
Leaky bucketRequests enter a queue that drains at a fixed rateVery smooth outputAdds delay; queue can fill

Token bucket is the most common. Example: capacity 20, refill 10 tokens per minute: a client can burst 20 requests at once, then is held to one every 6 seconds. Design notes for the algorithms are in System Design · Module 5.

In-app implementation with Bucket4j

Bucket4j is a Java library that implements the token bucket correctly and thread-safely. Add the bucket4j-core dependency (check the Bucket4j site for the current group and artifact name for your Java version). We keep one bucket per client key and consult it in a servlet filter:

import com.github.benmanes.caffeine.cache.Cache;
import com.github.benmanes.caffeine.cache.Caffeine;
import io.bucket4j.Bucket;
import io.bucket4j.ConsumptionProbe;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.time.Duration;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

@Component
public class RateLimitFilter extends OncePerRequestFilter {

    // one bucket per client; entries unused for 10 minutes are dropped (no memory leak)
    private final Cache<String, Bucket> buckets = Caffeine.newBuilder()
            .expireAfterAccess(Duration.ofMinutes(10))
            .maximumSize(100_000)
            .build();

    private Bucket newBucket() {
        return Bucket.builder()
                .addLimit(limit -> limit.capacity(20).refillGreedy(10, Duration.ofMinutes(1)))
                .build();
    }

    @Override
    protected boolean shouldNotFilter(HttpServletRequest request) {
        return !request.getRequestURI().startsWith("/api/");     // limit the API only
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        String key = clientKey(request);
        Bucket bucket = buckets.get(key, k -> newBucket());
        ConsumptionProbe probe = bucket.tryConsumeAndReturnRemaining(1);

        if (probe.isConsumed()) {
            response.setHeader("X-RateLimit-Remaining", String.valueOf(probe.getRemainingTokens()));
            chain.doFilter(request, response);
        } else {
            long waitSeconds = Math.max(1, probe.getNanosToWaitForRefill() / 1_000_000_000L);
            response.setStatus(HttpStatus.TOO_MANY_REQUESTS.value());          // 429
            response.setHeader("Retry-After", String.valueOf(waitSeconds));
            response.setContentType("application/problem+json");
            response.getWriter().write("{\"title\":\"Too many requests\",\"status\":429,"
                    + "\"detail\":\"Try again in " + waitSeconds + " seconds\"}");
        }
    }

    private String clientKey(HttpServletRequest request) {
        var auth = org.springframework.security.core.context.SecurityContextHolder
                .getContext().getAuthentication();
        if (auth != null && auth.isAuthenticated() && !"anonymousUser".equals(auth.getPrincipal())) {
            return "user:" + auth.getName();                 // logged in: limit per user
        }
        return "ip:" + request.getRemoteAddr();              // anonymous: limit per IP
    }
}
  • The filter needs a Caffeine dependency here; a plain ConcurrentHashMap works too but never forgets old clients.
  • If you want to limit authenticated users, register the filter after the security filter that sets the authentication; for login and OTP endpoints (anonymous) use the IP.
  • You can give different endpoints different limits: strict for /api/auth/login (5 per minute) and loose for reads. Select the bucket configuration by path.

Returning 429 properly

Status 429 Too Many Requests is the standard answer. Add a Retry-After header (seconds to wait) so well-behaved clients back off, and optionally informal headers such as X-RateLimit-Limit and X-RateLimit-Remaining. Use the same error body format as the rest of your API (ProblemDetail, module 2). Log rejections at WARN with the key, and count them with a Micrometer counter so you can see attacks.

Which client key? Be careful with proxies

Behind Nginx, a load balancer or a gateway, request.getRemoteAddr() is the proxy's address, so everyone shares one bucket and gets blocked together. Set server.forward-headers-strategy=framework (or native for Tomcat) so Spring reads the X-Forwarded-For header, and make sure only your trusted proxy can set it; otherwise an attacker sends a fake header with a new value on each request and escapes the limit. Authenticated user id or an API key is a better key than IP, because many people share one IP (a college or an office network behind NAT).

Distributed rate limiting with Redis

With three instances of the app, each with its own in-memory buckets, a client effectively gets three times the limit. Counters must live in a shared store, and Redis is the usual choice because it is fast and has atomic operations. Two ways:

  • Bucket4j with a Redis backend (extension modules for Lettuce, Redisson, Jedis and others): the same bucket API, with the state kept in Redis.
  • A simple fixed-window counter with StringRedisTemplate:
public boolean allow(String clientKey, int limit, Duration window) {
    long slot = System.currentTimeMillis() / window.toMillis();          // current window number
    String key = "rl:" + clientKey + ":" + slot;
    Long count = redis.opsForValue().increment(key);                     // atomic
    if (count != null && count == 1L) {
        redis.expire(key, window);                                       // first hit sets the TTL
    }
    return count != null && count <= limit;
}

This has a tiny race (the app can crash between INCR and EXPIRE, leaving a key with no TTL); production code puts both steps in a Lua script that Redis runs atomically. It also has the fixed-window boundary burst. For a sliding window use a sorted set (opsForZSet()): add the timestamp, remove entries older than the window, count the rest, all in one script. Decide what happens if Redis is down: fail open (allow requests, accept the risk) or fail closed (reject). Most public APIs fail open, with an alert.

Limit at the edge instead

The cheapest request to handle is the one that never reaches Java. Put coarse limits in front of the application:

http {
    limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;     # 10 requests per second per IP

    server {
        location /api/ {
            limit_req zone=api burst=20 nodelay;                     # allow short bursts
            limit_req_status 429;
            proxy_pass http://backend;
        }
    }
}

Spring Cloud Gateway has a built-in RequestRateLimiter filter backed by Redis (gateway article), and cloud API gateways and CDNs offer limits too. A good layering: Nginx or gateway for coarse per-IP limits and DDoS protection; the application for business limits (5 resume uploads per hour per user, 3 password-reset mails per hour per address) that need to know who the user is.

PlaceStrengthWeakness
Nginx / CDN / WAFBlocks before Java; very cheapKnows IP and URL, not your users
API gatewayOne place for all services; can use user or API keyAnother component to run
Application filterBusiness rules, per-user, per-planUses app resources; needs Redis for several instances
Resilience4j @RateLimiterLimits your calls to another serviceOutgoing, not for protecting your API from clients

Common mistakes

  • An unbounded HashMap of buckets: one attacker with a million fake IPs fills memory.
  • Rate limiting by getRemoteAddr() behind a proxy (everybody is "the proxy").
  • Trusting X-Forwarded-For from anyone.
  • Same limit for login and for reading job lists.
  • Returning 500 or 403 instead of 429, with no Retry-After.
  • In-memory limits on several instances (limit multiplied by the instance count).

Interview angle

"How would you rate-limit an API?" Pick key (user/IP/API key), algorithm (token bucket for bursts), shared store (Redis) for several instances, answer 429 + Retry-After, and do coarse limiting at the edge. "Token bucket vs fixed window?" Bursts allowed with a steady average vs boundary double-burst. "What if Redis fails?" Fail open or closed, a stated decision.

Production-readiness checklist

Before you deploy, check that configuration comes from the environment, health checks and logs work, shutdown is graceful, every external call has a timeout, pools are sized, the schema is migrated by a tool, and the API is documented.

"It works" is not "it is ready". This checklist collects the lessons of the whole module and ties them to Project 2. Go through it before the first real deployment, and again when a service misbehaves.

1. Configuration and secrets

  • 12-factor style: the same JAR runs everywhere; only environment variables change. Spring's relaxed binding maps SPRING_DATASOURCE_URL to spring.datasource.url.
  • No passwords, API keys or JWT secrets in Git, in application.yml defaults, or in logs. Use environment variables, Docker/Kubernetes secrets or a vault.
  • Profiles (dev, test, prod) for differences; prod must not fall back to development defaults silently.
  • Fail fast: validate required properties at startup with @ConfigurationProperties and @Validated.
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USER}
    password: ${DB_PASSWORD}
  jpa:
    open-in-view: false
    hibernate:
      ddl-auto: validate           # Flyway owns the schema; Hibernate only checks it
  flyway:
    enabled: true
server:
  shutdown: graceful
  forward-headers-strategy: framework
  tomcat:
    threads:
      max: 200
spring.lifecycle.timeout-per-shutdown-phase: 30s
management:
  endpoints:
    web:
      exposure:
        include: health, info, prometheus
  endpoint:
    health:
      probes:
        enabled: true
logging:
  structured:
    format:
      console: ecs

2. Database

  • Migrations with Flyway or Liquibase, never ddl-auto=update in production (module 3). Migrations run on startup before traffic is served.
  • Connection pool sizing: HikariCP maximum-pool-size defaults to 10. More is not better: a pool larger than the database can serve only moves the queue into the database. Start at about 10 to 20 per instance and make sure (instances x pool size) stays below the database's max_connections. Watch hikaricp.connections.pending.
  • Set spring.datasource.hikari.connection-timeout (default 30 s) lower, so overloaded requests fail fast.
  • Indexes for your real queries, slow-query log on, open-in-view=false, N+1 checked.

3. Health, shutdown and timeouts

  • Actuator health with liveness and readiness probes; the container or Kubernetes uses them (Actuator).
  • Graceful shutdown: server.shutdown=graceful makes Tomcat stop accepting new requests, finish in-flight ones, then exit; spring.lifecycle.timeout-per-shutdown-phase=30s sets how long it waits. Without it, a deployment cuts requests in half (HTTP 502 for users). Match it with the platform's termination grace period.
  • Timeouts everywhere: outgoing HTTP (clients), database (spring.jpa.properties.jakarta.persistence.query.timeout or per-transaction timeout), Redis, SMTP. A missing timeout is a future outage.
  • Executors have bounded queues; scheduled jobs are idempotent and single-run in a cluster.

4. Observability

  • Structured logs to stdout with a request or trace id; correct levels; no secrets (Logging).
  • Metrics scraped by Prometheus; dashboards for latency, traffic, errors and saturation; alerts on error rate and latency (Micrometer).
  • Version in /actuator/info (build and git info), so you know what is running.
  • Later: tracing across services (module 7).

5. Performance and protection

  • Caching for hot read paths with TTL and invalidation (Caching); pagination on every list endpoint; compression (server.compression.enabled=true) if not handled by Nginx.
  • Rate limiting on login, OTP, upload, email-sending endpoints (Rate limiting).
  • Request size limits (max-file-size, Tomcat max-http-form-post-size where relevant).
  • Security: HTTPS at the edge, CORS limited to your frontend origin, security headers, actuator locked, dependencies updated (module 4).

6. API quality

  • API documentation with springdoc-openapi (Swagger UI) from your controllers and DTOs (module 2). Disable or protect Swagger UI in production if the API is not public.
  • Consistent error responses (ProblemDetail), correct status codes, validation, idempotency for payments.
  • Versioning strategy (/api/v1) and a deprecation policy before you have many clients.

7. Build and deploy

  • A multi-stage Dockerfile, non-root user, small base image, JVM that respects container memory limits (DevOps · Module 3). Layered JARs make rebuilds faster.
  • CI runs tests and builds the image on every push (DevOps · Module 4).
  • A rollback plan; migrations that are backward-compatible for one release (add a column first, remove it later).
  • Backups of the database and a tested restore.

In real projects

Teams turn this list into a template: a company "service starter" with logging, Actuator, metrics, Dockerfile and CI already configured, so every new service is production-ready on day one. The same list is also a good outline for the "how do you take a Spring Boot app to production?" interview question.

Common mistakes

  • Treating production as "dev with a bigger server": same ddl-auto=update, same passwords, debug logs.
  • Health check that returns UP while the database is unreachable (or the opposite: liveness depending on the database).
  • A 200-connection pool times ten instances, killing PostgreSQL.
  • No graceful shutdown, so every deploy shows errors to users.

Interview questions — Production features

What is the difference between SLF4J and Logback, and why use placeholders in log calls?

SLF4J is the logging API (a facade) that your code uses; Logback is the implementation that formats and writes the lines, and it is Spring Boot's default. The facade lets you change the implementation without touching code. Placeholders (log.info("user {}", id)) build the message only when the level is enabled, and they keep the exception as a separate last argument so the stack trace is printed.

How do you follow one request through many log lines, including across threads?

Put a correlation id into the MDC in a servlet filter at the start of the request, print %X{requestId} in the log pattern, and clear the MDC in finally. The MDC is thread-local, so for @Async or executors you copy it with a TaskDecorator. With Micrometer Tracing the trace and span ids are put in the MDC for you and propagated between services.

What is Spring Boot Actuator, and how do you secure it?

It adds production endpoints (health, info, metrics, loggers, env, threaddump and others). Only health is exposed over HTTP by default. You choose exposure with management.endpoints.web.exposure.include, restrict sensitive endpoints to an admin role with Spring Security, and/or serve them on a separate management.server.port that is not reachable from the internet. Never expose heapdump or env publicly.

Liveness vs readiness probe?

Liveness answers "is the process broken?"; failure makes the platform restart the container, so it should not depend on external systems. Readiness answers "can it serve traffic now?"; failure removes the instance from the load balancer but does not restart it, and it may include the database. Boot exposes /actuator/health/liveness and /readiness when probes are enabled.

What are counters, gauges and timers in Micrometer, and why is tag cardinality dangerous?

A counter only increases (requests, errors); a gauge reports a current value that can rise and fall (queue size); a timer records count and duration of events. Each unique combination of tag values becomes a separate time series, so a tag such as user id or a raw URL creates millions of series and overloads Prometheus and your application's memory. Use low-cardinality tags only.

How does @Cacheable work, and why might it not work?

A proxy intercepts the call, builds a key from the arguments, looks it up in the named cache and calls the method only on a miss. It fails silently when @EnableCaching is missing, when the method is called from the same class (self-invocation bypasses the proxy), when the method is private or final, or when the bean is not created by Spring. The key can also be wrong, for example when it ignores a parameter.

@Cacheable vs @CachePut vs @CacheEvict?

@Cacheable skips the method if the value is cached. @CachePut always runs the method and updates the cache with the result (use on updates). @CacheEvict removes an entry, or all entries with allEntries = true (use on deletes and on changes that make other cached results stale). @Caching combines several on one method.

Caffeine or Redis for a cache? What serialization would you use with Redis?

Caffeine is in-process memory: fastest, no network, but every instance has its own copy, so entries can differ between instances. Redis is shared and survives restarts of the application, at the cost of a network hop. With Redis, replace the default JDK serialization by JSON (and string keys) so values are readable, need not be Serializable, and are less fragile to class changes; always set a TTL.

What is the difference between fixedRate, fixedDelay and cron? What problems appear in a cluster?

fixedRate measures the period from the start of one run to the start of the next; fixedDelay from the end of one run to the start of the next; cron uses a calendar expression (six fields in Spring, with seconds) and a time zone. In a cluster each instance runs the job, so use ShedLock, a dedicated worker instance, or an external scheduler. The default scheduler also has one thread, so a long job delays the others.

Why can an @Async method run synchronously, and what does not propagate to the async thread?

It runs synchronously when @EnableAsync is missing or when it is called from within the same class, because the proxy is bypassed. Thread-local state does not propagate: the caller's transaction, the Spring Security context and the MDC are not available in the new thread. Pass ids instead of entities, start async work after commit, and copy context with a decorator if needed.

What do virtual threads change in Spring Boot?

With Java 21+ and Boot 3.2+, spring.threads.virtual.enabled=true runs request handling, @Async and scheduled tasks on cheap virtual threads. Blocking calls (JDBC, HTTP) no longer hold an OS thread, so a blocking-style application scales to many concurrent requests. They do not speed up CPU-bound work, and your connection pool and downstream services still limit the throughput. Older Java versions could pin carrier threads in synchronized blocks.

How do you implement a secure file upload?

Limit sizes (spring.servlet.multipart.max-file-size and a business limit), check the content type by looking at the bytes with an allow-list, never use the client's file name for the path (path traversal), generate a UUID name, normalise and verify that the path stays inside the upload folder, store outside the web root, keep metadata and ownership in the database, authorise downloads and send them with Content-Disposition. In production use object storage such as S3.

RestTemplate, RestClient and WebClient: which one do you use, and what must you configure?

For new blocking code use RestClient (Spring 6.1+); RestTemplate is in maintenance mode but common in old code; WebClient is for reactive stacks. Whatever the client, set connect and read timeouts, map 4xx/5xx errors to domain exceptions (onStatus), reuse the client bean, and add retry and circuit breaking for unreliable dependencies. An @HttpExchange interface gives a declarative client.

How would you rate-limit the login endpoint across three instances of a service?

Use a shared counter store, normally Redis, with a token bucket or sliding window keyed by IP (and username for login). Local in-memory buckets would give each instance its own allowance. Respond with 429 and Retry-After, decide fail-open or fail-closed if Redis is down, make sure the real client IP is read correctly behind the proxy, and add coarse limits at Nginx or the gateway as well.

What would you check before putting a Spring Boot service in production?

Config and secrets from the environment, Flyway migrations with ddl-auto=validate, open-in-view=false, sized connection pool, timeouts on every external call, health and readiness probes, graceful shutdown, structured logs without secrets, metrics and alerts, rate limits on sensitive endpoints, locked-down Actuator, API docs, a multi-stage Docker image and a rollback plan.

Cheat sheet — Production features

  • Logger LoggerFactory.getLogger(X.class) or Lombok @Slf4j; use {} placeholders; exception as the last argument
  • Levels ERROR > WARN > INFO > DEBUG > TRACE; Boot default is INFO; set with logging.level.com.example=DEBUG
  • Log files logging.file.name, logging.logback.rollingpolicy.max-file-size, max-history; in containers log to stdout
  • JSON logs logging.structured.format.console=ecs (Boot 3.4+); MDC filter puts requestId, clear in finally
  • Never log passwords, tokens, OTPs, card or ID numbers, full bodies
  • Actuator spring-boot-starter-actuator; expose with management.endpoints.web.exposure.include; separate management.server.port
  • Probes /actuator/health/liveness (restart) and /readiness (traffic); custom check = HealthIndicator
  • Runtime log level POST /actuator/loggers/<logger> with {"configuredLevel":"DEBUG"}
  • Micrometer Counter (up), Gauge (current), Timer (duration); low-cardinality tags; /actuator/prometheus needs micrometer-registry-prometheus
  • Caching @EnableCaching; @Cacheable(key, condition, unless), @CachePut, @CacheEvict(allEntries), @Caching
  • Cache pitfalls self-invocation, no TTL, wrong key, cached entities; cache DTOs
  • Redis cache spring.cache.type=redis, spring.cache.redis.time-to-live, JSON value serializer, string keys; StringRedisTemplate for direct use
  • Caffeine local, spring.cache.caffeine.spec=maximumSize=1000,expireAfterWrite=10m
  • @Scheduled @EnableScheduling; fixedRate (start to start), fixedDelay (end to start), 6-field cron + zone="Asia/Kolkata"
  • Scheduler pool default 1 thread: spring.task.scheduling.pool.size; cluster: ShedLock
  • @Async @EnableAsync; returns void or CompletableFuture; named executor @Async("mailExecutor"); bounded queue
  • Async limits no caller transaction, no security context, no MDC; start after commit with @TransactionalEventListener(AFTER_COMMIT)
  • Virtual threads spring.threads.virtual.enabled=true (Boot 3.2+, Java 21+); for blocking I/O, not CPU work
  • Upload MultipartFile; spring.servlet.multipart.max-file-size/max-request-size; check bytes, UUID name, normalised path, outside web root
  • Download ResponseEntity<Resource> + ContentDisposition.attachment().filename(n, UTF_8); big data: StreamingResponseBody
  • Email spring-boot-starter-mail, spring.mail.*; SimpleMailMessage vs MimeMessageHelper (HTML, attachments); test with Mailpit (SMTP 1025, UI 8025)
  • RestClient builder.baseUrl().build(); .get().uri(..).retrieve().body(T.class); onStatus; always timeouts
  • HTTP service client @HttpExchange interface + HttpServiceProxyFactory
  • Rate limiting token bucket (Bucket4j) per user/IP; 429 + Retry-After; Redis for several instances; coarse limits in Nginx/gateway
  • Production env-var config, Flyway + ddl-auto=validate, open-in-view=false, server.shutdown=graceful, timeouts, pool sizing, probes

Practice — Production features

  1. Logging (easy). In your Project 2 API, add an SLF4J logger to the application service, log "application submitted" at INFO with ids, and set logging.level.com.example to DEBUG in a dev profile. Done when the console shows the line with the right level and no secret appears.
  2. Correlation id (easy). Write the RequestIdFilter, print %X{requestId} in the pattern, and return the id in an X-Request-Id response header. Done when two requests show different ids across several log lines each, and the id does not leak into the next request.
  3. Actuator health and info (easy). Add Actuator, expose health,info,metrics,prometheus, enable probes, add build info, and write a custom HealthIndicator for the upload folder. Done when /actuator/health shows your component, turns DOWN (503) if the folder is removed, and the other endpoints need the ADMIN role.
  4. Custom metric (medium). Add a counter for submitted applications and a timer for the mail sending, then scrape /actuator/prometheus. Done when the counter increases after each application and the timer appears in the output.
  5. Caching (medium). Cache getJob(id) and the company list with Caffeine (TTL 10 minutes), evict on update and delete, and prove it with a test that counts repository calls. Then switch to Redis with JSON values and a per-cache TTL, and inspect keys with redis-cli. Done when the second call does not hit the database and an update makes the next read fresh.
  6. Project 2: resume upload (medium). Add POST /api/applications/{id}/resume (PDF only, 2 MB, UUID name, metadata table through a Flyway migration) and an owner-only download endpoint. Done when a renamed .exe is rejected, a file called ../../x.pdf cannot escape the folder, and another user gets 404/403.
  7. Project 2: email to the recruiter (medium). When someone applies, send an HTML mail to the job's recruiter (Thymeleaf template, resume attached) asynchronously after commit using a dedicated executor, tested against Mailpit in Docker. Done when the API answers quickly, the mail appears in Mailpit, and no mail is sent if the transaction rolls back.
  8. Scheduled job (medium). Close jobs whose deadline passed every night at 00:30 IST, idempotently and in batches, with a log line and a counter. Done when running it twice changes nothing the second time; bonus: protect it with ShedLock and start two instances.
  9. Rate limiting (hard). Limit /api/auth/login to 5 requests per minute per IP using Bucket4j, returning 429 with Retry-After. Then move the counter into Redis and verify with two instances. Done when the sixth call in a minute fails on both instances.
  10. Project 2 finishing steps (hard). Complete the production side of the job portal: Swagger/OpenAPI docs for all endpoints, Flyway migrations for the whole schema with ddl-auto=validate, an Actuator health endpoint with probes, proper logging (levels, request id, JSON in the prod profile), graceful shutdown, and a README that lists the endpoints and contains the ER diagram of User, Company, Job and Application. Done when a new developer can clone the repository, start it with one command and find every endpoint and the data model in the README, and the checklist in this module is ticked.

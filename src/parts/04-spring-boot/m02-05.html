Bean Validation: @Valid, @NotBlank, @Email, @Size and custom constraints

Bean Validation lets you declare rules with annotations on DTO fields; adding @Valid to a @RequestBody makes Spring check them before your method runs and throw an exception, which you turn into a clean 400.

Never trust data from outside. A client can send an empty name, a negative price, an email without @ or a 10 MB string. Bean Validation (the Jakarta Validation standard; Hibernate Validator is the implementation Spring Boot uses) lets you write these rules once, as annotations, next to the fields. Add the starter and you are ready:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

The annotations live in the package jakarta.validation.constraints (older Boot 2 projects used javax.validation).

The first example

import jakarta.validation.constraints.*;

public record CreateProductRequest(

        @NotBlank(message = "name is required")
        @Size(max = 120, message = "name must be at most 120 characters")
        String name,

        @NotBlank @Pattern(regexp = "[A-Z]{2}-\\d{3,6}", message = "sku looks like MS-100")
        String sku,

        @NotNull @Positive @Digits(integer = 8, fraction = 2)
        BigDecimal price,

        @PositiveOrZero
        int stock) {}
@PostMapping
public ResponseEntity<ProductResponse> create(
        @Valid @RequestBody CreateProductRequest request) {   // @Valid starts the check
    ...
}

With @Valid, Spring validates the object right after Jackson builds it. If any rule fails, the method is not called; a MethodArgumentNotValidException is thrown and the response is 400. Without @Valid the annotations are simply ignored. That is the number-one "my validation does nothing" cause.

Use @NotBlank for text, @NotEmpty for lists that must have an element, @NotNull for numbers, dates and objects.

Most annotations treat null as valid

Only the three Not… annotations (and @AssertTrue in some cases) reject null. @Size(min = 3), @Email, @Pattern and @Positive all pass a null value, because "absent" and "invalid" are different questions. So a required email is @NotBlank @Email, and a required price is @NotNull @Positive. A primitive int can never be null: a missing JSON field becomes 0, which @Positive would reject. Use Integer with @NotNull if you must tell "missing" from "zero".

Custom messages

Every annotation has a message. Write messages a user can read: not "must not be blank" but "name is required". You can use placeholders from the annotation: @Size(max = 120, message = "at most {max} characters"). For many messages or for translation, put keys in messages.properties (or ValidationMessages.properties) and write message = "{product.name.required}".

Nested objects and lists

Validation does not go into nested objects automatically. Mark the field with @Valid to cascade.

public record PlaceOrderRequest(
        @NotNull @Valid Address shippingAddress,           // cascade into Address

        @NotEmpty @Size(max = 50)
        List<@Valid OrderLine> lines) {}                    // each element is checked

public record Address(
        @NotBlank String line1,
        @NotBlank @Pattern(regexp = "\\d{6}", message = "PIN code must have 6 digits")
        String pin) {}

public record OrderLine(@NotNull Long productId, @Positive int quantity) {}

Errors from nested objects get a path such as lines[1].quantity or shippingAddress.pin, so the client can show the message at the right input.

Validation groups

Sometimes one DTO is used in two situations with different rules: id must be null on create but required on update. Groups are marker interfaces that select a subset of rules. Often separate request records (create vs update) are simpler, but you should know groups for interviews and legacy code.

public interface OnCreate {}
public interface OnUpdate {}

public record ProductRequest(
        @Null(groups = OnCreate.class) @NotNull(groups = OnUpdate.class) Long id,
        @NotBlank(groups = {OnCreate.class, OnUpdate.class}) String name) {}

@PostMapping
public ... create(@Validated(OnCreate.class) @RequestBody ProductRequest r) { ... }

@PutMapping("/{id}")
public ... update(@Validated(OnUpdate.class) @RequestBody ProductRequest r) { ... }

A constraint without groups belongs to the Default group. Once you use @Validated(OnCreate.class), only that group runs, not Default, unless OnCreate extends Default.

Validating @PathVariable and @RequestParam

Constraints can sit directly on controller method parameters. This is method validation.

@GetMapping("/{id}")
public ProductResponse get(@PathVariable @Positive Long id) { ... }

@GetMapping
public Page<ProductResponse> search(
        @RequestParam @Size(min = 2, max = 50) String q,
        @RequestParam(defaultValue = "20") @Min(1) @Max(100) int size) { ... }
  • Since Spring Framework 6.1 (Boot 3.2+) the framework validates these parameters itself and throws HandlerMethodValidationException (a 400). You do not need @Validated on the class.
  • If the controller class has @Validated (older style, a proxy-based check), a failure throws jakarta.validation.ConstraintViolationException instead, which you must handle yourself or you get a 500. Do not mix: pick the built-in 6.1+ approach and leave @Validated off controller classes.
  • On services, @Validated on the class still enables validation of method arguments (ConstraintViolationException) for non-web callers.

A custom constraint

When the built-in set is not enough, write your own annotation plus a validator. Example: a SKU must match the company's format and must not be a reserved word.

import jakarta.validation.*;
import java.lang.annotation.*;

@Documented
@Constraint(validatedBy = SkuValidator.class)       // which class does the check
@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.RECORD_COMPONENT})
@Retention(RetentionPolicy.RUNTIME)
public @interface ValidSku {
    String message() default "invalid SKU";          // the three required attributes
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
public class SkuValidator implements ConstraintValidator<ValidSku, String> {

    private static final Pattern FORMAT = Pattern.compile("[A-Z]{2}-\\d{3,6}");
    private static final Set<String> RESERVED = Set.of("XX-000");

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        if (value == null) {
            return true;                  // convention: null is handled by @NotNull
        }
        return FORMAT.matcher(value).matches() && !RESERVED.contains(value);
    }
}

// usage
public record CreateProductRequest(@NotBlank @ValidSku String sku, ...) {}

Validators are created as Spring-aware objects, so a validator can have injected dependencies (for example a repository for a "unique email" check). Be careful: a uniqueness check in a validator is a convenience for good error messages only. The database unique constraint is still the real guard (two requests can race).

For a rule across several fields (startDate before endDate), either put the custom constraint on the class (@Target(TYPE)), or add a boolean helper to the record with @AssertTrue:

public record DateRange(@NotNull LocalDate start, @NotNull LocalDate end) {
    @AssertTrue(message = "end must not be before start")
    public boolean isValidRange() {
        return start == null || end == null || !end.isBefore(start);
    }
}

  "type": "about:blank",
  "title": "Validation failed",
  "status": 400,

  "instance": "/api/v1/products",

    { "field": "price", "message": "must be greater than 0" }

}

Rules

  • No @Valid, no validation. Put it on every @RequestBody that has constraints, and on nested fields to cascade.
  • Most constraints accept null; combine with @NotNull/@NotBlank for required fields.
  • Constraints on a record go on the components (the parameters in the header); they are copied to the right places.
  • The server must validate even if the React form already did. Client-side checks are only for convenience.

Conventions

  • Validate format (shape, range, size) at the edge with annotations; validate business rules that need data in the service.
  • Always limit sizes (@Size(max=…)) on strings and lists. Unbounded input is a denial-of-service risk and may overflow your column.
  • Keep messages short, specific and user-readable.
  • Put the same limits in the database schema (VARCHAR(120), NOT NULL). Two lines of defence.

Mistakes

  • Forgetting @Valid (the rules never run) or forgetting the starter dependency (the annotations compile but nothing is enforced on some setups, or the classes are missing).
  • Using @NotNull on a string and expecting blank strings to be rejected.
  • Using @Size on an Integer (it is for length); use @Min/@Max.
  • Adding @Valid on a nested object field without validating the outer object, or the reverse.
  • Validating the JPA entity instead of the request DTO, then getting a 500 at save time.

Boot 3.x and 4.x

Everything here works the same in Spring Boot 3.x and 4.x (Jakarta Validation, Hibernate Validator, built-in method validation since Spring 6.1). The thing to remember from older tutorials: the package is jakarta.validation, not javax.validation.

Global error handling: @RestControllerAdvice and ProblemDetail

Throw domain exceptions from your services and map them in one @RestControllerAdvice class to a consistent error JSON (ProblemDetail, RFC 9457) with the right status code, never a stack trace.

When something goes wrong, the client needs three things: the right status code, a machine-readable shape it can parse the same way for every error, and a human message. It must never get a Java stack trace, a SQL error or a framework page. Spring lets you do this in one central place instead of try/catch in every controller.

What Spring Boot does by default

An uncaught exception ends at Boot's /error endpoint and produces this body:

{
  "timestamp": "2026-11-10T08:15:30.123+00:00",
  "status": 500,
  "error": "Internal Server Error",
  "path": "/api/v1/products/7"
}

Messages and stack traces are hidden by default (server.error.include-message and include-stacktrace are never). Do not turn them on in production. The default is safe but not helpful, and it is a different shape from your own errors. Fix both with an advice class.

Step 1: domain exceptions

Services throw exceptions that describe what went wrong in business terms, not HTTP. Make them unchecked (RuntimeException) so they pass through without throws clutter and, with @Transactional, roll back by default.

public class ResourceNotFoundException extends RuntimeException {
    public ResourceNotFoundException(String resource, Object id) {
        super(resource + " with id " + id + " not found");
    }
}

public class DuplicateResourceException extends RuntimeException {
    public DuplicateResourceException(String message) { super(message); }
}

public class BusinessRuleException extends RuntimeException {   // 422
    public BusinessRuleException(String message) { super(message); }
}

Step 2: @RestControllerAdvice and @ExceptionHandler

@RestControllerAdvice = @ControllerAdvice + @ResponseBody: a bean whose @ExceptionHandler methods apply to all controllers. Each handler names the exception type it handles; Spring picks the closest match in the class hierarchy. You can narrow an advice to some controllers with @RestControllerAdvice(basePackages = "...").

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ProblemDetail handleNotFound(ResourceNotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(
                HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setTitle("Resource not found");
        return pd;
    }
}

ProblemDetail (RFC 9457)

Instead of inventing an error format for each project, use the standard Problem Details format (RFC 9457, which replaced RFC 7807). Spring has the class ProblemDetail and serves it as Content-Type: application/problem+json. Frontend developers and API tools understand it.

        "Product with SKU MS-100 already exists");

When a handler returns a ProblemDetail, the HTTP status of the response is taken from its status field.

Step 3: the complete advice class

Extending ResponseEntityExceptionHandler gives you handlers for all the standard Spring MVC exceptions (400 malformed JSON, 405, 406, 415, 404 for no handler, missing parameter, type mismatch …) already in ProblemDetail format. You override only what you want to customise and add your own exceptions.

@RestControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    // --- your domain exceptions ---------------------------------------------

    @ExceptionHandler(ResourceNotFoundException.class)
    ProblemDetail handleNotFound(ResourceNotFoundException ex) {
        return problem(HttpStatus.NOT_FOUND, "Resource not found", ex.getMessage());
    }

    @ExceptionHandler(DuplicateResourceException.class)
    ProblemDetail handleDuplicate(DuplicateResourceException ex) {
        return problem(HttpStatus.CONFLICT, "Duplicate resource", ex.getMessage());
    }

    @ExceptionHandler(BusinessRuleException.class)
    ProblemDetail handleRule(BusinessRuleException ex) {
        return problem(HttpStatus.UNPROCESSABLE_ENTITY, "Business rule violated",
                ex.getMessage());
    }

    // --- database constraint that slipped past the service check ------------

    @ExceptionHandler(DataIntegrityViolationException.class)
    ProblemDetail handleIntegrity(DataIntegrityViolationException ex) {
        log.warn("Data integrity violation", ex);                  // details only in the log
        return problem(HttpStatus.CONFLICT, "Data conflict",
                "The request conflicts with existing data");
    }

    // --- validation: @Valid @RequestBody -------------------------------------

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders headers,
            HttpStatusCode status, WebRequest request) {

        List<Map<String, String>> errors = ex.getBindingResult().getFieldErrors().stream()
                .map(fe -> Map.of("field", fe.getField(),
                        "message", String.valueOf(fe.getDefaultMessage())))
                .toList();

        ProblemDetail pd = problem(HttpStatus.BAD_REQUEST, "Validation failed",
                "One or more fields are invalid");
        pd.setProperty("errors", errors);
        return ResponseEntity.badRequest().body(pd);
    }

    // --- validation: constraints on path / query parameters (Spring 6.1+) ----

    @Override
    protected ResponseEntity<Object> handleHandlerMethodValidationException(
            HandlerMethodValidationException ex, HttpHeaders headers,
            HttpStatusCode status, WebRequest request) {

        List<Map<String, String>> errors = new ArrayList<>();
        ex.getParameterValidationResults().forEach(result ->
                result.getResolvableErrors().forEach(error ->
                        errors.add(Map.of(
                                "field", String.valueOf(
                                        result.getMethodParameter().getParameterName()),
                                "message", String.valueOf(error.getDefaultMessage())))));

        ProblemDetail pd = problem(HttpStatus.BAD_REQUEST, "Validation failed",
                "One or more parameters are invalid");
        pd.setProperty("errors", errors);
        return ResponseEntity.badRequest().body(pd);
    }

    // --- validation: class-level @Validated on service or controller ---------

    @ExceptionHandler(ConstraintViolationException.class)
    ProblemDetail handleConstraintViolation(ConstraintViolationException ex) {
        List<Map<String, String>> errors = ex.getConstraintViolations().stream()
                .map(v -> Map.of("field", v.getPropertyPath().toString(),
                        "message", v.getMessage()))
                .toList();
        ProblemDetail pd = problem(HttpStatus.BAD_REQUEST, "Validation failed",
                "One or more values are invalid");
        pd.setProperty("errors", errors);
        return pd;
    }

    // --- last resort: never leak internals -----------------------------------

    @ExceptionHandler(Exception.class)
    ProblemDetail handleUnexpected(Exception ex) {
        String errorId = UUID.randomUUID().toString();
        log.error("Unexpected error, id={}", errorId, ex);          // full stack trace here
        ProblemDetail pd = problem(HttpStatus.INTERNAL_SERVER_ERROR, "Internal error",
                "Something went wrong. Quote this id to support: " + errorId);
        pd.setProperty("errorId", errorId);
        return pd;
    }

    private static ProblemDetail problem(HttpStatus status, String title, String detail) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(status, detail);
        pd.setTitle(title);
        return pd;
    }
}
  • The imports you need: org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler, org.springframework.web.method.annotation.HandlerMethodValidationException, org.springframework.web.bind.MethodArgumentNotValidException, org.springframework.dao.DataIntegrityViolationException and jakarta.validation.ConstraintViolationException.
  • The catch-all Exception handler is safe because Spring chooses the most specific matching handler. The standard MVC exceptions are caught by the parent class handler first, so a malformed JSON stays a 400.
  • Log the stack trace on the server (with an id the client can quote); return only a generic message.
  • The catch-all should not swallow Spring Security's AccessDeniedException or AuthenticationException in a way that turns 403 into 500. See module 4 for the Security handlers; a common pattern is to rethrow them or add specific handlers.

The built-in alternative: spring.mvc.problemdetails.enabled

If you do not want to extend ResponseEntityExceptionHandler, one property gives you ProblemDetail output for the standard MVC exceptions:

spring.mvc.problemdetails.enabled=true

Boot then registers a built-in advice that extends ResponseEntityExceptionHandler. Do not turn it on and define your own advice that extends the same class: you would have two such beans and an ambiguity. Either use the property and add a plain advice with only your own @ExceptionHandler methods, or extend the class yourself (as above) and leave the property off.

Custom exceptions that carry their status: ErrorResponseException

ErrorResponseException is an exception that already contains a status and a ProblemDetail. Spring handles it automatically without any @ExceptionHandler (with the standard handler class active). Handy for exceptions that need their own title and type.

public class ProductNotFoundException extends ErrorResponseException {
    public ProductNotFoundException(Long id) {
        super(HttpStatus.NOT_FOUND,
              ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND,
                      "Product " + id + " not found"),
              null);
        getBody().setTitle("Product not found");
    }
}

The trade-off: the exception now knows about HTTP, which goes against the "no HTTP in services" rule. Many teams accept it for convenience; stricter teams keep plain exceptions and map them in the advice.

ResponseStatusException: when it is fine

return repository.findById(id).orElseThrow(() ->
        new ResponseStatusException(HttpStatus.NOT_FOUND, "Product " + id + " not found"));

It is a one-liner that needs no custom class. It is fine for prototypes and for small, one-off cases in the controller. For anything reused, a named domain exception is better: it is searchable, testable and keeps HTTP out of the service.

A consistent error shape for the frontend

The goal: React reads status, shows detail, and puts each item of errors next to its field, for every error in the API. Decide the shape once, put it in this one class, and test it. With ProblemDetail you already have it:

{
  "type": "about:blank",
  "title": "Validation failed",
  "status": 400,
  "detail": "One or more fields are invalid",
  "instance": "/api/v1/products",
  "errors": [ { "field": "price", "message": "must be greater than 0" } ]
}

If your team already has its own error class (ApiError(timestamp, status, error, message, path, fieldErrors)), that works as well; what matters is that it is the same everywhere. Authentication and authorization errors from Spring Security filters should use the same shape (module 4).

Rules

  • Never return a stack trace, SQL text, class names or file paths to a client. Log them.
  • The status code must match the error: not 200 with an error body, not 500 for client mistakes.
  • Handlers should be as specific as possible; the catch-all Exception is the last resort only.
  • The advice must be in a package covered by component scanning (the same or a sub-package of your @SpringBootApplication class).

Edge cases

  • Controller-local handlers win: an @ExceptionHandler inside a controller overrides the global one for that controller only.
  • Errors in filters (such as Spring Security) happen before the DispatcherServlet, so @RestControllerAdvice never sees them. Handle those in the security configuration.
  • A rolled-back transaction: a @Transactional method rolls back on unchecked exceptions, so throwing your domain exception also undoes the database changes. Checked exceptions do not roll back by default (module 3).
  • A 404 for an unknown URL comes from the framework (NoResourceFoundException in recent versions), not from your code. With the standard handler active it becomes a ProblemDetail as well.

Mistakes

  • try { ... } catch (Exception e) { return null; } in controllers. It hides errors and returns 200.
  • e.printStackTrace() instead of a logger, or returning e.getMessage() from a catch-all (it may include SQL or paths).
  • Using @ControllerAdvice without @ResponseBody semantics and getting a view-name lookup. @RestControllerAdvice avoids this.
  • Handling Exception in a controller class and accidentally hiding the validation 400s.

Spring versions

ProblemDetail, ErrorResponseException and the spring.mvc.problemdetails.enabled property arrived with Spring Framework 6 / Boot 3.0 and work the same in Boot 4. HandlerMethodValidationException needs 6.1+ (Boot 3.2+). If you target an older Boot 2.x codebase, none of these exist; teams there use their own ApiError class.

Interview angle

"How do you handle exceptions in a Spring Boot REST API?" Strong answer: domain exceptions thrown by services; one @RestControllerAdvice with @ExceptionHandler methods that map them to status codes; a consistent body using ProblemDetail (RFC 9457); validation errors as a field list; a catch-all that logs and returns a generic 500; and no stack traces to clients. Bonus: the difference between @ControllerAdvice and @RestControllerAdvice, and why filter-level errors are not caught.

AssertJ: fluent assertions for objects, collections and exceptions

AssertJ's assertThat(actual) starts a chain of readable checks with helpful failure messages; it is the default assertion library in Spring Boot tests and clearly better than JUnit's assertEquals for collections and exceptions.

AssertJ comes with spring-boot-starter-test. Import one static method and let the IDE's auto-complete show what you can check, because the available methods depend on the type of the value:

import static org.assertj.core.api.Assertions.*;

Objects, numbers, strings, booleans

assertThat(job.getTitle()).isEqualTo("Java Developer");
assertThat(job.getSalaryMax()).isGreaterThan(job.getSalaryMin());
assertThat(rate).isBetween(0.0, 1.0);
assertThat(0.1 + 0.2).isCloseTo(0.3, within(0.0001));          // floating point
assertThat(job.isOpen()).isTrue();
assertThat(job.getDescription()).isNotBlank();

assertThat(email)
        .startsWith("asha")
        .contains("@")
        .endsWith(".com")
        .doesNotContain(" ");
assertThat("JAVA").isEqualToIgnoringCase("java");

assertThat(user).isNotNull();
assertThat(a).isSameAs(b);                      // same reference (==)
assertThat(response.status()).isEqualTo(ApplicationStatus.SUBMITTED);
assertThat(maybeJob).isPresent().hasValueSatisfying(j -> assertThat(j.getId()).isEqualTo(7L));
assertThat(Optional.empty()).isEmpty();

Chaining makes one statement check several things. Add a description with .as("job title") before the check to get a clearer failure message.

Collections

List<JobResponse> jobs = service.findOpenJobs();

assertThat(jobs).hasSize(3);
assertThat(jobs).isNotEmpty();
assertThat(jobs).extracting(JobResponse::title)
        .containsExactly("Java Developer", "QA Engineer", "DevOps Engineer");   // order matters
assertThat(jobs).extracting(JobResponse::title)
        .containsExactlyInAnyOrder("QA Engineer", "Java Developer", "DevOps Engineer");
assertThat(jobs).extracting(JobResponse::title).contains("QA Engineer");        // at least
assertThat(jobs).extracting(JobResponse::title).doesNotContain("Cook");

assertThat(jobs).filteredOn(j -> j.salaryMax() > 1_000_000)
        .extracting(JobResponse::title)
        .containsExactly("DevOps Engineer");
assertThat(jobs).allMatch(JobResponse::open);
assertThat(jobs).anySatisfy(j -> assertThat(j.title()).startsWith("Java"));

assertThat(map).containsEntry("city", "Pune").containsKey("country");
assertThat(page.getContent()).isSortedAccordingTo(Comparator.comparing(JobResponse::id));
contains
Contains these elements (and maybe others), any order.
containsOnly
Only these elements, duplicates and order ignored.
containsExactly
Exactly these elements in exactly this order.
containsExactlyInAnyOrder
Exactly these elements, any order. The usual choice when SQL order is not specified.
extracting
Maps each element to a field first; check the field values instead of whole objects.

To compare two objects by their fields (when equals is not implemented or is by id only), use assertThat(actual).usingRecursiveComparison().isEqualTo(expected), optionally with .ignoringFields("id", "createdAt").

Exceptions

assertThatThrownBy(() -> service.update(99L, request, me))
        .isInstanceOf(ResourceNotFoundException.class)
        .hasMessage("Job 99")
        .hasMessageContaining("99");

assertThatExceptionOfType(AccessDeniedException.class)
        .isThrownBy(() -> service.update(7L, request, stranger))
        .withMessageContaining("own jobs");

assertThatNoException().isThrownBy(() -> service.update(7L, request, owner));

// the cause chain
assertThatThrownBy(() -> service.importJobs(file))
        .hasRootCauseInstanceOf(IOException.class);

Put only the one call that should throw inside the lambda. If you put the whole arrange block in it, an exception from the set-up code makes the test pass for the wrong reason.

Soft assertions

Normal assertions stop at the first failure. Soft assertions collect all failures and report them together, which is nice when checking many fields of one response:

SoftAssertions.assertSoftly(softly -> {
    softly.assertThat(response.id()).isEqualTo(7L);
    softly.assertThat(response.title()).isEqualTo("Java Developer");
    softly.assertThat(response.open()).isTrue();
});

AssertJ vs JUnit assertions

JUnit (Assertions.*)AssertJ
StyleassertEquals(expected, actual)assertThat(actual).isEqualTo(expected)
Argument orderEasy to swap, wrong failure textActual first, no confusion
CollectionsBasic (assertIterableEquals)Rich: extracting, filteredOn, containsExactly
ExceptionsassertThrows (returns the exception)assertThatThrownBy with chained checks
Failure messagesShortDetailed, shows both values and the difference
DiscoverabilityFew methodsIDE shows only methods valid for the type

Using AssertJ everywhere is a good habit; just do not mix both styles inside one test. Hamcrest matchers (assertThat(x, is(5))) still appear in old MockMvc examples; use AssertJ or jsonPath there.

Common mistakes

  • Writing assertThat(x) and forgetting the check: assertThat(list.size() == 3); compiles but verifies nothing. Always end with a method such as isTrue() or use hasSize(3).
  • Using isEqualTo on arrays of entities without a useful equals.
  • Asserting the order of a result that SQL does not order (use containsExactlyInAnyOrder or add ORDER BY).
  • Comparing floating-point numbers with isEqualTo instead of isCloseTo.

Interview angle

"Why AssertJ over JUnit assertions?" Fluent, type-aware, better messages, strong collection and exception support. Be ready to write a collection assertion with extracting(...).containsExactly(...) and an exception assertion from memory.

@WebMvcTest and MockMvc: testing controllers, validation and security

@WebMvcTest loads only the web layer (controllers, advice, filters, JSON, security) so you can test status codes, JSON, validation and 401/403 with MockMvc while the service is replaced by @MockitoBean.

What it loads, and what it does not

A test slice starts a small part of the Spring context. @WebMvcTest starts only the MVC infrastructure:

LoadedNot loaded
@Controller / @RestController (the ones you name), @ControllerAdvice, @JsonComponent, converters, Filter beans, WebMvcConfigurer, Jackson, validation, MockMvc, Spring Security auto-configuration@Service, @Repository, @Component beans, DataSource, JPA, Flyway, your @Configuration classes (import what you need)

Because services are not loaded, a controller that needs JobService fails to start the context with "No qualifying bean of type JobService". You supply a mock with @MockitoBean. This keeps the test fast (typically about a second) and focused on HTTP behaviour: URL mapping, request parsing, validation, status codes, JSON shape, error handling and security rules.

A first controller test

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.*;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@WebMvcTest(JobController.class)
@Import({SecurityConfig.class, JsonSecurityHandlers.class})
class JobControllerTest {

    @Autowired MockMvc mvc;

    @MockitoBean JobService jobService;
    @MockitoBean JwtDecoder jwtDecoder;      // required by the resource server config

    @Test
    void getJob_returnsJson() throws Exception {
        when(jobService.getJob(7L)).thenReturn(new JobResponse(7L, "Java Developer", true));

        mvc.perform(get("/api/jobs/{id}", 7L))                    // public endpoint
                .andExpect(status().isOk())
                .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_JSON))
                .andExpect(jsonPath("$.id").value(7))
                .andExpect(jsonPath("$.title").value("Java Developer"))
                .andExpect(jsonPath("$.open").value(true));
    }

    @Test
    void getJob_whenMissing_returns404Problem() throws Exception {
        when(jobService.getJob(99L)).thenThrow(new ResourceNotFoundException("Job 99"));

        mvc.perform(get("/api/jobs/{id}", 99L))
                .andExpect(status().isNotFound())
                .andExpect(jsonPath("$.status").value(404))
                .andExpect(jsonPath("$.detail").value("Job 99"));
    }
}
MockMvc
Sends fake HTTP requests straight into DispatcherServlet without opening a network port. Fast and in the same thread.
perform(request)
Executes the request built with get, post, put, delete, patch.
andExpect(matcher)
Checks the response: status(), content(), jsonPath(), header(), cookie().
andDo(print())
Prints the request and response; the fastest way to debug a failing test (MockMvcResultHandlers.print).
@Import(...)
Adds beans the slice does not scan. Your SecurityConfig is a @Configuration, so import it explicitly (with its handlers), otherwise default security rules apply.

The @ControllerAdvice from module 2 is picked up automatically, so error responses (ProblemDetail) are tested here too.

@MockitoBean and @MockBean

@MockitoBean (package org.springframework.test.context.bean.override.mockito) puts a Mockito mock into the Spring test context in place of the real bean of that type, and resets it after each test. It exists since Spring Framework 6.2 (Spring Boot 3.4) and replaces @MockBean, which Boot deprecated in 3.4 and removed in Boot 4. On Boot 3.0 to 3.3 you still use @MockBean (package org.springframework.boot.test.mock.mockito). Inside test slices and @SpringBootTest use @MockitoBean; @Mock is only for plain unit tests with MockitoExtension. Similarly @MockitoSpyBean replaces @SpyBean.

Posting JSON and testing validation

private static final String VALID_JSON = """
        {"title": "Java Developer", "description": "Spring Boot, SQL"}""";

@Test
void createJob_asRecruiter_returns201() throws Exception {
    when(jobService.create(any(), any())).thenReturn(new JobResponse(7L, "Java Developer", true));

    mvc.perform(post("/api/jobs")
                    .with(jwt().authorities(new SimpleGrantedAuthority("ROLE_RECRUITER"))
                            .jwt(j -> j.subject("5")))
                    .contentType(MediaType.APPLICATION_JSON)
                    .content(VALID_JSON))
            .andExpect(status().isCreated())
            .andExpect(jsonPath("$.id").value(7));
}

@Test
void createJob_withBlankTitle_returns400() throws Exception {
    mvc.perform(post("/api/jobs")
                    .with(jwt().authorities(new SimpleGrantedAuthority("ROLE_RECRUITER")))
                    .contentType(MediaType.APPLICATION_JSON)
                    .content("""
                            {"title": "", "description": "x"}"""))
            .andExpect(status().isBadRequest())
            .andExpect(jsonPath("$.status").value(400));

    verifyNoInteractions(jobService);                 // service was never called
}

@Test
void createJob_withoutToken_returns401() throws Exception {
    mvc.perform(post("/api/jobs")
                    .contentType(MediaType.APPLICATION_JSON)
                    .content(VALID_JSON))
            .andExpect(status().isUnauthorized());
}

@Test
void createJob_asCandidate_returns403() throws Exception {
    mvc.perform(post("/api/jobs")
                    .with(jwt().authorities(new SimpleGrantedAuthority("ROLE_CANDIDATE")))
                    .contentType(MediaType.APPLICATION_JSON)
                    .content(VALID_JSON))
            .andExpect(status().isForbidden());

    verifyNoInteractions(jobService);
}

Text blocks (""") keep JSON readable. For bigger bodies serialize a record with the ObjectMapper (autowire JsonMapper/ObjectMapper, which differs by Boot line), but hand-written JSON also checks the real field names that clients use. The 400/401/403 tests are cheap and protect your security rules from accidental change.

Testing secured endpoints

Add spring-security-test (scope test). With it, MockMvc can pretend a user is logged in without a real token:

<dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-test</artifactId>
    <scope>test</scope>
</dependency>
ToolUse when
@WithMockUser(roles = "RECRUITER")Session/Basic style or when the principal type does not matter. Annotation on the test; creates a user with ROLE_RECRUITER. Does not apply to JWT resource-server authentication tokens, but method security and URL rules see its authorities.
.with(jwt())Resource server. Replaces the JwtDecoder: no real token is needed. Customise with .authorities(...), .jwt(j -> j.subject("5").claim("email", "...")).
.with(user("asha").roles("ADMIN"))Per-request user for form/Basic setups.
.with(csrf())When CSRF protection is enabled (cookie/session apps): adds a valid token to POST/PUT/DELETE. Without it you get 403. Not needed in our stateless API.
httpBasic("user", "pw")Basic authentication in the request.
 
@Test
@WithMockUser(username = "5", roles = "ADMIN")
void adminEndpoint_asAdmin_returns200() throws Exception {
    mvc.perform(get("/api/admin/users")).andExpect(status().isOk());
}

@Test
@WithMockUser(roles = "CANDIDATE")
void adminEndpoint_asCandidate_returns403() throws Exception {
    mvc.perform(get("/api/admin/users")).andExpect(status().isForbidden());
}

Note that roles = "ADMIN" already adds the ROLE_ prefix, while authorities in jwt().authorities(...) are used as written. If your controller reads jwt.getSubject() (for example through @AuthenticationPrincipal Jwt), use jwt() with a subject; @WithMockUser does not provide a Jwt principal.

Useful matchers

.andExpect(status().isCreated())                              // 201
.andExpect(header().string("Location", "/api/jobs/7"))
.andExpect(jsonPath("$.items", hasSize(3)))                    // Hamcrest matcher from jsonPath
.andExpect(jsonPath("$.items[0].title").value("Java Developer"))
.andExpect(jsonPath("$.items[*].open", everyItem(is(true))))
.andExpect(jsonPath("$.password").doesNotExist())              // never leak a hash
.andExpect(content().json("{\"id\":7}"))                       // lenient JSON compare
.andExpect(content().string(containsString("Java")))

Read a value from the response for a later step with MvcResult result = mvc.perform(...).andReturn(); and result.getResponse().getContentAsString(). To test pagination parameters use .param("page", "0").param("size", "10").

MockMvcTester (brief)

Spring Framework 6.2 added MockMvcTester, an AssertJ-style wrapper around MockMvc, auto-configured for MVC tests in recent Boot versions. It avoids the throws Exception and the matcher imports:

@Autowired MockMvcTester mvc;

@Test
void getJob_returnsJson() {
    when(jobService.getJob(7L)).thenReturn(new JobResponse(7L, "Java Developer", true));

    assertThat(mvc.get().uri("/api/jobs/{id}", 7L))
            .hasStatusOk()
            .bodyJson()
            .extractingPath("$.title").isEqualTo("Java Developer");
}

It is optional; many codebases still use classic MockMvc, which you must be able to read. Check the API of your Spring version before using it.

Rules

  • A @WebMvcTest never touches a database. If the test needs one, it is the wrong kind of test.
  • Name the controller in @WebMvcTest(JobController.class) so only it is loaded; a bare @WebMvcTest loads all controllers and needs mocks for all their services.
  • Mock the layer below (the service), assert the HTTP contract. Business rules belong to the service unit test.

Exceptions and edge cases

  • NoSuchBeanDefinitionException: No qualifying bean of type JobService: add @MockitoBean for every dependency of the controller (and of imported filters/config).
  • 401/403 in a test where you expected 200: security is active; add jwt()/@WithMockUser, or csrf() when CSRF is on. If the real security config is missing, you get the default (everything secured, CSRF on).
  • Missing JwtDecoder: UnsatisfiedDependencyException when the imported config uses oauth2ResourceServer; mock it.
  • HttpMessageNotReadableException (400): malformed JSON in the test body or a missing Content-Type.
  • Empty body with jsonPath: the status was an error; use andDo(print()).

Common mistakes

  • Using @SpringBootTest + @AutoConfigureMockMvc for every controller test: slower, and loads the database you wanted to avoid.
  • Forgetting contentType(APPLICATION_JSON) on POST (you get 415 Unsupported Media Type).
  • Disabling security in tests (addFilters = false) so the 401/403 behaviour is never tested.
  • Putting business logic assertions here instead of in the service test.

Interview angle

"What does @WebMvcTest load?" Only web-layer beans; services are mocked with @MockitoBean. "How do you test a secured endpoint?" spring-security-test: @WithMockUser or jwt() post-processor; csrf() when needed; test 401 (no auth) and 403 (wrong role). "@MockBean vs @MockitoBean?" Same purpose; the latter is the replacement from Spring 6.2, while @MockBean was removed in Boot 4.

@DataJpaTest: testing repositories and queries

@DataJpaTest loads only JPA entities and repositories with a transaction that rolls back after each test; use it for derived and custom queries, and run it against the real database type (Testcontainers) instead of the default embedded H2.

What it loads

@DataJpaTest starts the persistence slice: entity scanning, Spring Data repositories, the DataSource, Hibernate, EntityManager, Flyway/Liquibase migrations when present, and a TestEntityManager. It does not load services, controllers or web configuration. By default it also replaces your configured database with an embedded one (H2 or HSQLDB, if on the classpath) and runs each test in a transaction that is rolled back at the end, so tests do not leave data behind (@Transactional in tests).

@DataJpaTest
class JobRepositoryTest {

    @Autowired JobRepository jobRepository;
    @Autowired UserRepository userRepository;
    @Autowired TestEntityManager em;

    @Test
    void findByPostedById_returnsOnlyThatRecruitersJobs() {
        User asha = em.persist(TestData.newUser("asha@example.com", Role.RECRUITER));
        User ravi = em.persist(TestData.newUser("ravi@example.com", Role.RECRUITER));
        em.persist(TestData.newJob("Java Developer", asha));
        em.persist(TestData.newJob("QA Engineer", asha));
        em.persist(TestData.newJob("DevOps Engineer", ravi));
        em.flush();           // send INSERTs to the database
        em.clear();           // forget loaded entities, so the query really hits the DB

        List<Job> jobs = jobRepository.findByPostedById(asha.getId());

        assertThat(jobs).extracting(Job::getTitle)
                .containsExactlyInAnyOrder("Java Developer", "QA Engineer");
    }

    @Test
    void existsByEmailIgnoreCase_isCaseInsensitive() {
        em.persist(TestData.newUser("Asha@Example.com", Role.CANDIDATE));
        em.flush();

        assertThat(userRepository.existsByEmailIgnoreCase("asha@example.com")).isTrue();
    }
}
TestEntityManager
A test helper around EntityManager with persist, persistAndFlush, find, flush, clear. Use it to arrange data without going through the repository you test.
flush()
Writes pending SQL to the database. Hibernate delays INSERTs until flush or commit, and the test transaction never commits, so without it your query may not see the data (or constraint violations never appear).
clear()
Empties the persistence context. Without it, findById returns the cached Java object and the test does not prove the SQL works.

What to test with it

  • Derived query methods with tricky names (findTop5ByCityAndOpenTrueOrderBySalaryMaxDesc).
  • Custom @Query JPQL and native SQL (joins, join fetch, projections, paging).
  • Constraints and mappings: unique email gives DataIntegrityViolationException on flush; @Enumerated(STRING) columns; cascade and orphanRemoval.
  • Pagination and sorting with PageRequest.of(0, 10, Sort.by("id")).
@Test
void saveTwoUsersWithSameEmail_violatesUniqueConstraint() {
    em.persist(TestData.newUser("asha@example.com", Role.CANDIDATE));
    em.flush();

    assertThatThrownBy(() -> {
        em.persist(TestData.newUser("asha@example.com", Role.RECRUITER));
        em.flush();                                   // the exception happens here
    }).isInstanceOf(PersistenceException.class);
}

Do not test Spring Data's built-in methods (save, findById); they are already tested. Test your own queries and mappings.

The H2 trap, and the fix

An embedded H2 database is fast and needs no setup, but it is not PostgreSQL. It can hide bugs and cause false failures:

  • PostgreSQL-only SQL in native queries (ILIKE, jsonb, array types, DISTINCT ON, RETURNING, window-function details) fails on H2.
  • Different rules for case sensitivity, null ordering, GROUP BY strictness and function-based indexes (lower(email)), so a test passes on H2 and fails in production, or the reverse.
  • Your Flyway migrations (written for PostgreSQL) may not run on H2 at all.
  • Different locking and transaction isolation behaviour.

The fix: test against the same database type you run in production. Tell @DataJpaTest not to replace the database, and supply a real PostgreSQL with Testcontainers (next articles):

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Testcontainers
class JobRepositoryPgTest {

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired JobRepository jobRepository;
    // tests as before
}

With Replace.NONE Spring Boot keeps the DataSource that @ServiceConnection created from the container. Put the container in a shared base class so it starts once, as shown in the Testcontainers article.

Versions

In Boot 4 the packages of @DataJpaTest and @AutoConfigureTestDatabase changed with the new modular test support; the names and behaviour are the same. Let the IDE import them. With Flyway on the classpath its migrations run in the slice, which is a good thing: the tests then also check your schema scripts.

Exceptions and edge cases

  • A test passes but production fails: the SQL ran on H2, or the entity came from the first-level cache. Use flush() + clear() and a real database.
  • DataIntegrityViolationException/PersistenceException only appears at flush(), not at save().
  • LazyInitializationException does not appear in a @DataJpaTest because the test transaction keeps the session open; you can miss this bug. Test the service with a real transaction boundary in an integration test, or map to DTOs.
  • Auditing fields (@CreatedDate) need @Import(JpaAuditingConfig.class) because your configuration classes are not scanned.
  • Hibernate sequence/identity ids: do not hard-code expected ids; read them from the saved entity.

Common mistakes

  • Asserting on an entity returned by findById without clear(): you are testing the cache.
  • Test data written with SQL files in H2 syntax and never run on PostgreSQL.
  • Marking the test @Transactional(propagation = NOT_SUPPORTED) or @Commit to "see data", then leaking rows into other tests.

Interview angle

"What does @DataJpaTest do?" Slice with entities and repositories, embedded DB by default, rollback per test, TestEntityManager. "Why not just use H2?" Dialect and feature differences hide real bugs; use Testcontainers PostgreSQL with Replace.NONE. "Why flush and clear?" Force SQL and bypass the first-level cache.

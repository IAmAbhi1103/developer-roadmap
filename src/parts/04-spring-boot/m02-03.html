How a request flows through Spring MVC

Every HTTP request enters the embedded Tomcat, passes the filters, reaches the single DispatcherServlet, which finds your controller method, calls it, and turns the return value into a response through an HttpMessageConverter such as Jackson.

When you write @GetMapping("/products/{id}") you never write code that opens a socket, parses text or sets headers. Spring Web MVC does all of that around your method. If you understand the path a request takes, errors like "404 for a URL that exists", "415 Unsupported Media Type" or "my filter runs but my interceptor does not" stop being mysteries. This article is the map for the rest of module 2.

The big picture

Step by step

  1. Embedded Tomcat. Spring Boot starts Tomcat inside your JAR (default port 8080). Tomcat accepts the TCP connection, parses the HTTP text and builds an HttpServletRequest and an empty HttpServletResponse. One thread from Tomcat's pool handles the request from start to end (the classic "thread per request" model).
  2. Servlet filters. The request passes through a chain of jakarta.servlet.Filter objects: character encoding, CORS, request logging, and later Spring Security's filter chain. Filters see raw requests and responses and know nothing about controllers. A filter can stop the request, for example by returning 401.
  3. DispatcherServlet. This is the front controller: the one servlet mapped to /, so every URL that no other servlet handles comes to it. It does no business work; it coordinates the other pieces below.
  4. HandlerMapping. The dispatcher asks "which handler matches this method, path, Content-Type and Accept?". For annotated controllers the answer comes from RequestMappingHandlerMapping, which built a lookup table at startup from every @RequestMapping-style annotation. The result is a handler execution chain: your controller method plus any interceptors. If nothing matches you get 404 (or 405 if the path matches but the method does not).
  5. HandlerInterceptor.preHandle. Interceptors are Spring MVC's own, lighter hooks. They know the matched handler, so they suit things like auditing or per-endpoint timing. preHandle can return false to stop.
  6. HandlerAdapter. The adapter (RequestMappingHandlerAdapter) knows how to call your method. It resolves every parameter: path variables, query parameters, headers and the body. For @RequestBody it picks an HttpMessageConverter using the request's Content-Type; Jackson reads the JSON into your DTO. If the parameter has @Valid, Bean Validation runs here, before your method starts.
  7. Your controller method runs. It calls a service and returns an object, a ResponseEntity, or nothing.
  8. Return value handling. The adapter chooses a converter using the Accept header and the return type, writes the body (JSON by Jackson, String as text) and sets the status and headers.
  9. Back out. Interceptor postHandle / afterCompletion run, the response travels back through the filters in reverse order, and Tomcat sends it to the client.
  10. Exceptions. If anything throws, the dispatcher hands the exception to HandlerExceptionResolver beans. Your @RestControllerAdvice is one of them; see global error handling.

Where the common errors come from

  • 404: HandlerMapping found nothing for the path. Check the class-level and method-level paths together and the context path.
  • 405 Method Not Allowed: the path matches but not the HTTP method (HttpRequestMethodNotSupportedException).
  • 415 Unsupported Media Type: no converter can read the request's Content-Type, or your method's consumes does not allow it (HttpMediaTypeNotSupportedException).
  • 406 Not Acceptable: no converter can produce what Accept asks for (HttpMediaTypeNotAcceptableException).
  • 400 Bad Request: broken JSON (HttpMessageNotReadableException), a missing required parameter, or a path variable that cannot be converted (MethodArgumentTypeMismatchException), or a validation failure.
  • A 401/403 before your controller: a security filter answered; the DispatcherServlet never ran.

Servlet stack vs reactive stack

This flow is Spring MVC (servlet stack, blocking, Tomcat by default), which this module uses. Spring WebFlux is a separate reactive stack with DispatcherHandler instead of DispatcherServlet. Since Java 21 you can also run MVC on virtual threads (spring.threads.virtual.enabled=true) and keep the same simple code. The flow above stays the same in Spring Boot 3.x and 4.x.

Interview angle

"Explain what happens when a request hits a Spring Boot application." Strong answer: Tomcat → filter chain → DispatcherServlet (front controller) → HandlerMapping finds the controller method → HandlerAdapter resolves arguments (message converter reads the JSON, validation runs) → controller → return value written by a message converter → response back through the filters. Add one failure case (exception resolver and @RestControllerAdvice) and the filter vs interceptor difference.

@Controller vs @RestController

@RestController is @Controller plus @ResponseBody: every method's return value is written straight into the HTTP response body (as JSON), instead of being treated as the name of a view to render.

Spring MVC supports two styles of web app. In the older server-rendered style, a controller returns the name of an HTML template (Thymeleaf, JSP) and a view resolver renders it. In the REST style, the controller returns data and a message converter writes it as JSON. The annotation you choose on the class selects the style.

The two annotations

@Controller
public class PageController {

    @GetMapping("/welcome")
    public String welcome(Model model) {
        model.addAttribute("user", "Asha");
        return "welcome";          // a VIEW name: templates/welcome.html
    }
}
@RestController
@RequestMapping("/api/v1/products")
public class ProductController {

    private final ProductService productService;

    public ProductController(ProductService productService) {
        this.productService = productService;
    }

    @GetMapping("/{id}")
    public ProductResponse get(@PathVariable Long id) {
        return productService.findById(id);   // written as JSON
    }
}

@RestController is a composed annotation: its source is just @Controller + @ResponseBody. @Controller itself is a @Component stereotype, so component scanning registers the class as a bean (see scanning). @ResponseBody tells Spring: "do not look up a view; hand the return value to an HttpMessageConverter".

How it works inside

After DispatcherServlet finds your method (request flow), the RequestMappingHandlerAdapter calls it and then hands the return value to the first return value handler that supports it. This choice is the real difference between the two annotations:

  • For a @Controller method returning String, a view-name handler takes the value, and the ViewResolver turns it into a template.
  • For a method with @ResponseBody (or any method of a @RestController), a body handler (RequestResponseBodyMethodProcessor) takes the value. It looks at the request's Accept header, goes through the registered HttpMessageConverter list, and uses the first converter that can write that Java type as an acceptable media type.
  • For a ResponseEntity return type, another handler writes the status and headers first and then the body in the same way (ResponseEntity).

Boot registers the usual converters for you. A String is written as-is by the string converter. A byte[] or Resource is written as raw bytes. Records, classes, lists and maps are written by Jackson as JSON (Jackson basics). The same list also reads request bodies for @RequestBody (next article).

What the return value becomes

Method returnsResponse
A record or classJSON object, status 200

A small trap with String: return "ok" sends the three characters ok, not "ok" with quotes. A client that parses the response as JSON then fails. If the client expects JSON, return a record such as new StatusResponse("ok").

Mixing both styles

You can have both kinds in one app: a @Controller serving an HTML landing page and several @RestController classes serving /api/**. You can also keep @Controller and put @ResponseBody on single methods, but when everything in the class is an API method, @RestController is cleaner. In a React plus Spring Boot project, nearly every controller is a @RestController, because React is a separate app that only asks for data (Frontend · Module 6). The same split exists for global error handlers: @ControllerAdvice versus @RestControllerAdvice (error handling).

@Controller
public class MixedController {

    @GetMapping("/")
    public String home() {
        return "index";                       // view name
    }

    @GetMapping("/ping")
    @ResponseBody                              // this one method is an API method
    public Map<String, String> ping() {
        return Map.of("status", "up");
    }
}

Rules for controllers

Rules

  • Controllers are singletons shared by all threads: keep them stateless. No mutable instance fields.
  • Use constructor injection for the service (one constructor needs no @Autowired).
  • Put the common path prefix on the class with @RequestMapping; put method and sub-path on each method.
  • Keep controllers thin: bind the request, call one service method, shape the response. See layers.
  • Return DTOs (records), never JPA entities. Lazy relations can break serialization and you may leak fields (DTOs).

Convention: one controller per resource

Name it after the resource: ProductController, OrderController, in a web or controller package. One class handles one noun and its sub-resources. A class with forty endpoints is a design smell. Version the prefix (/api/v1/..., see versioning) and use plural nouns (URL design).

Mistake: @Controller on an API class

With @Controller and no @ResponseBody, a method that returns a String or object is treated as a view name. With no view found you see a Whitelabel error page or an error like Circular view path, and the JSON never appears. If your API "returns a 404 HTML page" for a URL that exists, check the class annotation first.

Wrong: view lookup for a DTO

@Controller
@RequestMapping("/api/v1/products")
public class ProductController {
    @GetMapping("/{id}")
    public ProductResponse get(@PathVariable Long id) { ... }
}

Right: body is written as JSON

@RestController
@RequestMapping("/api/v1/products")
public class ProductController {
    @GetMapping("/{id}")
    public ProductResponse get(@PathVariable Long id) { ... }
}

Edge cases and errors you can meet

  • HttpMediaTypeNotAcceptableException (406): the client's Accept header asks for a type no converter can produce, for example Accept: application/xml with no XML library.
  • HttpMessageNotWritableException (500): Jackson cannot write the object, for example a lazy JPA relation closed after the transaction, or a bean with no properties.
  • A @Controller whose URL equals the returned view name gives Circular view path [welcome]: would dispatch back to the current handler URL (common with JSP). With Thymeleaf a missing template gives TemplateInputException and a 500 page.
  • Two methods with the same path and HTTP method give IllegalStateException: Ambiguous mapping at startup.
  • A controller bean that is not scanned (outside the root package) simply produces 404 for its URLs, with no error at startup.

Boot 3 and Boot 4

The controller annotations are unchanged. What does change is the JSON library behind the converter: Boot 3 uses Jackson 2, while Boot 4 moves to Jackson 3 by default (different package names for custom modules and serializers). If you only write controllers and records, you do not notice. Check the Boot 4 release notes before porting custom serializers.

Interview angle

Question: "Difference between @Controller and @RestController?" Answer in three points: @RestController = @Controller + @ResponseBody; the return value goes through HttpMessageConverter instead of the view resolver; use @Controller for server-rendered HTML and @RestController for APIs. Then show depth: the converter is chosen by Accept and the Java type, and Jackson is the JSON one. A follow-up: "How do you return 201 or set a header?" → ResponseEntity (below). Another: "Is a controller thread-safe?" It is a singleton, so it is safe only while it holds no mutable state.

Mapping annotations: @RequestMapping, @PathVariable, @RequestParam

@RequestMapping and its shortcuts (@GetMapping, @PostMapping and so on) connect an HTTP method and path to a Java method; @PathVariable reads values from the path and @RequestParam reads them from the query string or form.

Mapping annotations answer two questions: which requests reach this method, and how do the parts of the request become Java parameters. This article covers the routing side and the two parameter styles you use most. The body, headers and status come next in the following article.

@RequestMapping and the shortcuts

@RequestMapping is the general annotation. On a class it sets a shared prefix; on a method it can set the HTTP method, the path, and conditions on headers and media types. Because writing method = RequestMethod.GET everywhere is noisy, Spring gives one shortcut per method.

@RestController
@RequestMapping("/api/v1/products")            // prefix for every method
public class ProductController {

    @GetMapping                                // GET    /api/v1/products
    public List<ProductResponse> list() { ... }

    @GetMapping("/{id}")                       // GET    /api/v1/products/42

    @PostMapping                               // POST   /api/v1/products
    public ResponseEntity<ProductResponse> create(...) { ... }

    @PutMapping("/{id}")                       // PUT    /api/v1/products/42
    public ProductResponse replace(@PathVariable Long id, ...) { ... }

    @DeleteMapping("/{id}")                    // DELETE /api/v1/products/42
    public void delete(@PathVariable Long id) { ... }
}

consumes and produces

Besides method and path, a mapping can be narrowed by media type. consumes matches the request's Content-Type; produces matches the request's Accept and sets the response Content-Type. A mismatch gives 415 or 406.

@PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE,
             produces = MediaType.APPLICATION_JSON_VALUE)
public ProductResponse create(@RequestBody CreateProductRequest request) { ... }

// same endpoint path, two representations
@GetMapping(value = "/{id}", produces = "application/json")
public ProductResponse json(@PathVariable Long id) { ... }

@GetMapping(value = "/{id}", produces = "text/csv")
public String csv(@PathVariable Long id) { ... }

Most of the time you do not set them: JSON in and out is the default for REST controllers. Set them when one URL really serves two formats, or when you want a clear 415 for anything but JSON. More in content negotiation.

Path patterns

  • /products/{id} — one segment, captured as a variable.
  • /products/{id:[0-9]+} — a regex after the colon; only digits match. Anything else falls through to 404.
  • /files/* — one segment of anything; /files/** — any number of segments (only as the last part of the pattern).
  • Static paths win over variables: with both /products/featured and /products/{id}, the request /products/featured goes to the first, because the more specific pattern wins.
  • Two methods with the identical method + path + media types cause an IllegalStateException: Ambiguous mapping at startup, so the error shows up early.

@PathVariable

A path variable is part of the URL path that identifies a resource. Use it for ids: /products/42.

// Name matches the placeholder: works when compiled with -parameters (Boot default)
@GetMapping("/{id}")
public ProductResponse get(@PathVariable Long id) { ... }

// Different name: say it explicitly
@GetMapping("/{productId}")
public ProductResponse get(@PathVariable("productId") Long id) { ... }

// Several variables (nested resource)
@GetMapping("/{productId}/reviews/{reviewId}")
public ReviewResponse review(@PathVariable Long productId,
                             @PathVariable Long reviewId) { ... }

// Regex limits the match
@GetMapping("/{code:[A-Z]{3}-\\d{4}}")
public ProductResponse byCode(@PathVariable String code) { ... }
  • A path variable is required by nature. @PathVariable(required = false) exists but is awkward; define two methods instead.
  • Spring converts the text to your parameter type (Long, UUID, LocalDate, an enum). If conversion fails — /products/abc for a Long — you get MethodArgumentTypeMismatchException and a 400.
  • A dot in the last variable (/files/report.pdf) is safe in current Spring versions; suffix-based content negotiation was removed.

@RequestParam

A request parameter is a key in the query string (?category=mouse&page=2) or in a form body. Use it for filtering, sorting and paging, not for identifying a resource.

// GET /api/v1/products?category=mouse
@GetMapping
public List<ProductResponse> list(
        @RequestParam String category) { ... }                  // required: 400 if missing

// optional, with a default
@RequestParam(defaultValue = "20") int size                     // ?size absent → 20
@RequestParam(required = false) String category                 // absent → null
@RequestParam Optional<BigDecimal> maxPrice                    // absent → Optional.empty()

// different name in the URL
@RequestParam("q") String searchText

// repeated or comma-separated values: ?tag=usb&tag=wireless  or  ?tag=usb,wireless
@RequestParam List<String> tag

// every parameter as a map (rarely a good idea)
@RequestParam Map<String, String> all

Binding many parameters to one object

When the list of filters grows, group them in a plain object without any annotation. Spring binds query parameters to its properties (a record works too).

public record ProductFilter(String category, BigDecimal minPrice, BigDecimal maxPrice) {}

// GET /api/v1/products?category=mouse&minPrice=500
@GetMapping
public List<ProductResponse> list(ProductFilter filter) { ... }

Do not add @RequestBody here: a GET request should not carry a body.

Mistake: primitive types for optional parameters

@RequestParam(required = false) int size fails with IllegalStateException when the parameter is absent, because null cannot become an int. Use Integer, Optional<Integer> or defaultValue.

Conventions

  • Version the prefix on the class: /api/v1/... (see API versioning).
  • Use the shortcut annotations, never bare @RequestMapping for a method.
  • Name query parameters in camelCase or lowercase and keep the style the same across the API (minPrice).
  • Do not trust path or query values: validate them (Bean Validation) and put a maximum on size.

@RequestBody, @RequestHeader and @ResponseStatus

@RequestBody turns the JSON body into a Java object, @RequestHeader reads a header, and @ResponseStatus sets a fixed status code for a method or an exception class.

@RequestBody

@RequestBody asks Spring to read the whole request body and convert it into the parameter type. The converter is chosen by the request's Content-Type; for application/json it is Jackson. Use it with POST, PUT and PATCH.

public record CreateProductRequest(
        String name,
        String sku,
        BigDecimal price,
        int stock) {}
@PostMapping
public ResponseEntity<ProductResponse> create(
        @Valid @RequestBody CreateProductRequest request) {
    ProductResponse created = productService.create(request);
    ...
}
POST /api/v1/products HTTP/1.1
Content-Type: application/json

{ "name": "Wireless Mouse", "sku": "MS-100", "price": 799.00, "stock": 25 }

How the body is converted

Spring keeps a list of HttpMessageConverter objects. For a parameter with @RequestBody, it asks them in order: "can you read this Java type from this Content-Type?" The first one that says yes does the work. Boot's list contains converters for byte[], String, form data, and Jackson for JSON.

  1. The request arrives with Content-Type: application/json and a body.
  2. The argument resolver for @RequestBody picks the Jackson converter, because it can read JSON into your type.
  3. Jackson builds the record or class from the JSON. A record uses its constructor; a class needs a default constructor and setters or a suitable constructor.
  4. If the parameter has @Valid, the validator then checks the constraints (validation).
  5. The object is passed into your method. If any step fails, your method is never called.

Because the converter works from the declared type, you can also bind to a List<CreateProductRequest> (a JSON array), a Map<String, Object> (any JSON object), a plain String (the raw text), a byte[], or a record with nested records. Prefer a specific record: the contract is then visible in code and in the OpenAPI document (OpenAPI).

@PostMapping("/bulk")
public List<ProductResponse> bulk(@RequestBody List<CreateProductRequest> items) { ... }

@PostMapping("/webhook")
public void webhook(@RequestBody String rawJson) { ... }   // needed to verify a signature

@PutMapping("/{id}/note")
public void note(@PathVariable Long id,
        @RequestBody(required = false) NoteRequest note) { ... }  // body may be absent

@RequestHeader

Reads one HTTP header. Header names are case-insensitive. Use it for things that describe the request rather than the resource: a correlation id, a client version, an idempotency key, a conditional-request If-Match.

// required: missing header → 400 (MissingRequestHeaderException)
@GetMapping("/{id}")
public ProductResponse get(@PathVariable Long id,
        @RequestHeader("X-Request-Id") String requestId) { ... }

// optional with a default
@RequestHeader(value = "Accept-Language", defaultValue = "en") String lang

// all headers
@RequestHeader HttpHeaders headers

// idempotency key for a safe retry of POST
@PostMapping("/orders")
public ResponseEntity<OrderResponse> place(
        @RequestHeader(value = "Idempotency-Key", required = false) String key,
        @Valid @RequestBody PlaceOrderRequest request) { ... }

Spring converts the header text to the parameter type: @RequestHeader("X-Page-Size") int size works, and a value like abc gives MethodArgumentTypeMismatchException (400). A header that is sent several times can be bound to a List<String>. For the standard headers in more detail, see HTTP headers.

Do not read Authorization by hand

You can write @RequestHeader("Authorization"), but once Spring Security is in place the filter already parsed the token. Take the user from @AuthenticationPrincipal or Authentication instead (module 4). The same applies to cookies: @CookieValue("name") reads one.

@ResponseStatus

The default status for a successful response is 200. @ResponseStatus changes it to a fixed value, on a controller method or on an exception class.

@DeleteMapping("/{id}")
@ResponseStatus(HttpStatus.NO_CONTENT)       // 204, empty body
public void delete(@PathVariable Long id) {
    productService.delete(id);
}

@PostMapping("/{id}/archive")
@ResponseStatus(HttpStatus.ACCEPTED)         // 202
public void archive(@PathVariable Long id) { ... }
@ResponseStatus(HttpStatus.NOT_FOUND)
public class ProductNotFoundException extends RuntimeException {
    public ProductNotFoundException(Long id) {
        super("Product " + id + " not found");
    }
}
// throwing it anywhere in a request gives a 404 response

Inside, the status on an exception is applied by ResponseStatusExceptionResolver, one of the resolvers that DispatcherServlet asks when a controller throws. It calls response.sendError(404), and Boot's /error endpoint then builds the JSON error body. Note that by default Boot does not put the exception message into that body (the property server.error.include-message defaults to never), so the client sees status 404 and a generic body unless you set the property or write your own handler.

The limits of @ResponseStatus: the status is fixed at compile time (no choice by data), it cannot add headers such as Location, and on an exception it gives you no control over the JSON shape. For those cases use ResponseEntity and @RestControllerAdvice. Also, if a method with @ResponseStatus throws an exception, the exception's own status wins.

Rules

  • Add @Valid next to @RequestBody; without it, constraint annotations on the record are not checked.
  • The client must send Content-Type: application/json for a JSON body, or it gets 415.
  • A 204 response has no body, so a @ResponseStatus(NO_CONTENT) method must return void.

Mistake: using the entity or reading the body twice

Wrong: entity as body, two bodies

@PostMapping
public Product create(@RequestBody Product entity,
                      @RequestBody Audit audit) { ... }

Right: one request DTO

@PostMapping
public ProductResponse create(
        @Valid @RequestBody CreateProductRequest request) { ... }

An entity as the body lets a client set fields like id or role (mass assignment). Reading the stream twice, for example in a filter and again in the controller, gives an empty body the second time.

Conventions

  • Name request bodies CreateXRequest and UpdateXRequest, and make them records.
  • Use custom headers sparingly; if a value belongs to the resource, put it in the body or the path. Older code prefixes custom headers with X-; newer standards do not require it.
  • Prefer one global error handler over @ResponseStatus on many exceptions once the API grows.

In real projects

Teams give every request a correlation id: a filter reads X-Request-Id (or makes one), puts it in the logging context (MDC), and echoes it back in the response so a user's bug report can be traced across services. Payment-style POST endpoints take an Idempotency-Key header so a client can retry after a timeout without charging twice. Webhook endpoints (a payment gateway calling you) bind the body as a String first, because the signature in a header is calculated over the exact raw bytes.

Interview angle

"How does @RequestBody work?" It reads the body through an HttpMessageConverter selected by Content-Type (Jackson for JSON) and passes the object to the method; errors are 400 or 415. "What if the JSON has extra fields?" Boot ignores them. "@ResponseStatus vs ResponseEntity?" The first is a fixed status, the second can vary status and add headers. A strong answer also names MethodArgumentNotValidException for @Valid failures and says why you never bind entities.

ResponseEntity and the Location header

ResponseEntity lets a method choose the status code, headers and body of a response, which you need for 201 Created with a Location header, 204 No Content, conditional 404s and cache headers.

Returning a plain object always means status 200. A real API needs more: 201 after creating, 204 after deleting, 404 when nothing exists, Location pointing to the new resource, ETag for caching. ResponseEntity<T> is the whole HTTP response as a Java object: status + headers + body. T is the body type, written by the message converter.

How it works inside

ResponseEntity extends HttpEntity, a small class that holds headers and a body, and adds a status. When a controller method returns it, a dedicated return value handler (HttpEntityMethodProcessor) does three things in order: it copies the status to the response, copies your headers, and then writes the body through the same HttpMessageConverter chain used for a plain @ResponseBody (controller article). A null body is allowed and produces an empty body. Because the handler is chosen by the return type, ResponseEntity works in a @RestController and also in a plain @Controller, with no @ResponseBody needed.

The builders you use

BuilderStatusUse for
ResponseEntity.ok(body)200Successful read or update
ResponseEntity.created(uri).body(body)201 + LocationPOST that created a resource
ResponseEntity.accepted().build()202Work queued, not finished
ResponseEntity.noContent().build()204Delete, or update without a body
ResponseEntity.badRequest().body(e)400Rarely by hand; use the exception handler
ResponseEntity.notFound().build()404Missing resource (body-less)
ResponseEntity.status(HttpStatus.CONFLICT).body(e)anyAny other status
ResponseEntity.of(optional)200 or 404Optional present → 200, empty → 404

All builders end with .build() (no body) or .body(x). Between them you can chain .header(name, value), .headers(...), .contentType(...), .eTag(...), .lastModified(...) and .cacheControl(...). You can also call the constructor new ResponseEntity<>(body, headers, status), which older code uses; the builder style is easier to read. For the meaning of each status, see status codes.

Create with 201 and Location

After POST creates something, the correct answer is 201 Created, a Location header with the URL of the new resource, and normally the created resource in the body. Build the URL from the current request so it is right on every host, port and context path. Never hard-code http://localhost:8080.

import org.springframework.web.servlet.support.ServletUriComponentsBuilder;

@PostMapping
public ResponseEntity<ProductResponse> create(
        @Valid @RequestBody CreateProductRequest request) {

    ProductResponse created = productService.create(request);

    URI location = ServletUriComponentsBuilder
            .fromCurrentRequest()          // http://host/api/v1/products
            .path("/{id}")                 // .../products/{id}
            .buildAndExpand(created.id())  // .../products/42
            .toUri();

    return ResponseEntity.created(location).body(created);
}
HTTP/1.1 201
Location: http://localhost:8080/api/v1/products/42
Content-Type: application/json

{"id":42,"name":"Wireless Mouse","sku":"MS-100","price":799.00,"stock":25}

A shorter alternative is MvcUriComponentsBuilder.fromMethodName(...), but fromCurrentRequest() is the simplest and works well for the create-then-fetch pattern. You can also let Spring inject a UriComponentsBuilder as a method parameter; it is already initialised from the current request:

@PostMapping
public ResponseEntity<ProductResponse> create(
        @Valid @RequestBody CreateProductRequest request,
        UriComponentsBuilder uriBuilder) {

    ProductResponse created = productService.create(request);
    URI location = uriBuilder.path("/api/v1/products/{id}")
            .buildAndExpand(created.id()).toUri();
    return ResponseEntity.created(location).body(created);
}

Behind a reverse proxy, make sure Boot honours X-Forwarded-* headers (server.forward-headers-strategy=framework), or the host in Location will be the internal one.

Why bother? A client that gets Location can fetch the new resource without guessing its id, and a browser-based client can follow it. It is also a REST rule that a response to a create should point to the new resource (REST principles).

Read: 200 or 404

// 1. Throw. The exception handler produces a 404 body. (Preferred in services.)
@GetMapping("/{id}")
public ProductResponse get(@PathVariable Long id) {
    return productService.findById(id);          // throws ProductNotFoundException
}

// 2. Decide in the controller with ResponseEntity
@GetMapping("/{id}")
public ResponseEntity<ProductResponse> get(@PathVariable Long id) {
    return productService.findOptional(id)       // Optional<ProductResponse>
            .map(ResponseEntity::ok)
            .orElseGet(() -> ResponseEntity.notFound().build());
}

The first style keeps controllers short and gives every 404 the same JSON error body from the global handler (error handling). The second gives a 404 with no body. In a big project choose the first.

Delete, headers and caching

// 204 No Content
@DeleteMapping("/{id}")
public ResponseEntity<Void> delete(@PathVariable Long id) {
    productService.delete(id);
    return ResponseEntity.noContent().build();
}

// Custom headers and cache control
@GetMapping("/{id}/image-meta")
public ResponseEntity<ImageMeta> meta(@PathVariable Long id) {
    ImageMeta meta = productService.imageMeta(id);
    return ResponseEntity.ok()
            .cacheControl(CacheControl.maxAge(Duration.ofMinutes(10)).cachePublic())
            .eTag("\"" + meta.version() + "\"")
            .header("X-Total-Images", String.valueOf(meta.count()))
            .body(meta);
}

// Download a file
@GetMapping("/export")
public ResponseEntity<byte[]> export() {
    byte[] csv = productService.exportCsv();
    return ResponseEntity.ok()
            .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=\"products.csv\"")
            .contentType(MediaType.parseMediaType("text/csv"))
            .body(csv);
}

For large files, do not load everything into a byte[]. Return a ResponseEntity<Resource> (for example an InputStreamResource) or use a streaming body, so memory stays small (file download).

Conditional requests with ETag

An ETag is a version label for a response. The client sends it back in If-None-Match; if nothing changed, the server answers 304 Not Modified with no body, saving bandwidth. Spring can do this check for you with WebRequest.checkNotModified:

@GetMapping("/{id}")
public ResponseEntity<ProductResponse> get(@PathVariable Long id, WebRequest request) {
    ProductResponse p = productService.findById(id);
    String etag = "\"" + p.version() + "\"";
    if (request.checkNotModified(etag)) {
        return null;                     // Spring already wrote 304
    }
    return ResponseEntity.ok().eTag(etag).body(p);
}

Returning null here is the documented pattern, because checkNotModified has already written the 304 response. This is the one case where null from a controller is correct. The same ETag idea is reused for optimistic updates with If-Match (locking).

Rules

  • The status code must match the result: 201 only for a created resource, 204 only with no body, 4xx for client errors.
  • ResponseEntity.created(uri) needs a non-null URI; it sets the Location header for you.
  • Set the status and headers before the body is written; with ResponseEntity this is automatic because the whole response is built first.

Convention

Return the DTO directly for plain reads and updates. Use ResponseEntity only where you need to control status or headers: create (201 + Location), delete (204), caching and downloads. Always use a specific generic type (ResponseEntity<ProductResponse>), not ResponseEntity<?> or a raw type, so tools like springdoc can read the schema.

Mistakes

  • Returning 200 with {"error": "not found"} in the body. Clients and monitoring tools rely on the status code.
  • Returning ResponseEntity.created(...) with no Location, or hard-coding the host in the URI.
  • Returning 204 with a body. A 204 must have no body.
  • Returning null from a controller for "not found" (gives 200 and an empty body).

Wrong: success status with an error body

@GetMapping("/{id}")
public ResponseEntity<?> get(@PathVariable Long id) {
    var p = productService.findOptional(id);
    if (p.isEmpty()) {
        return ResponseEntity.ok(Map.of("error", "not found"));
    }
    return ResponseEntity.ok(p.get());
}

Right: real 404 and a typed result

@GetMapping("/{id}")
public ResponseEntity<ProductResponse> get(@PathVariable Long id) {
    return ResponseEntity.of(productService.findOptional(id));
}

Edge cases and errors

  • Using ResponseEntity.ok(null) or .build() on a method declared ResponseEntity<ProductResponse> is fine: the body is just empty.
  • If the body cannot be written (for example Jackson fails on a lazy collection), you get HttpMessageNotWritableException and a 500, after the status was chosen but before it was sent.
  • If the client's Accept header cannot be satisfied, the result is 406 (HttpMediaTypeNotAcceptableException) even though you built a 200 entity.
  • A HEAD request to a GET method returns the headers of your ResponseEntity without the body.
  • A relative Location such as /api/v1/products/42 is allowed by HTTP, but absolute URLs are safer for simple clients.

In real projects

Most teams use ResponseEntity in three places only: create endpoints (201 + Location), file downloads (Content-Disposition), and cache-friendly reads (ETag, Cache-Control). Everything else returns a record, and errors go through one @RestControllerAdvice. Integration tests then assert the status and the Location header with MockMvc (controller tests).

Interview angle

"How do you return 201 with the URL of the new object?" Use ResponseEntity.created(uri).body(dto) with the URI built by ServletUriComponentsBuilder.fromCurrentRequest().path("/{id}").buildAndExpand(id).toUri(). Then explain why Location matters (the client can fetch the new resource), and when you prefer throwing an exception for 404 (one consistent error format). Be ready for "difference between ResponseEntity and @ResponseBody": the first carries status, headers and body; the second only marks the return value as the body.

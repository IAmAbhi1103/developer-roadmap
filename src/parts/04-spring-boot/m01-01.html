Spring Boot is how most Java back-ends are built today. Behind it sits the Spring Framework, whose core idea is simple: instead of your classes creating their own collaborators with new, a container creates the objects, wires them together and manages their life. Once you understand that one idea (Inversion of Control and dependency injection), the rest of Spring — configuration, auto-configuration, transactions, security, data access — becomes a set of small, learnable parts.

This module is the foundation for everything else in the page. Module 2 builds REST controllers on top of beans, Module 3 uses injected repositories, Module 4 and Module 5 rely on profiles, proxies and test slices, and Module 6 and Module 7 deploy what you build. The plain Java behind it (interfaces, polymorphism, reflection, annotations) is in Core Java · Module 2. Examples work on Spring Boot 3.x and 4.x; where they differ, a version note says so.

After this module you will be able to:

  • explain Spring vs Spring Boot, and create and run a project from Spring Initializr;
  • explain Inversion of Control and dependency injection, first in plain Java and then with the ApplicationContext;
  • define beans with stereotype annotations and @Configuration / @Bean, and use constructor injection with @Qualifier and @Primary;
  • read and fix the common bean errors from the startup failure report;
  • choose bean scopes and describe the bean lifecycle step by step;
  • configure an app with application.yml, profiles, @Value and @ConfigurationProperties;
  • explain how @SpringBootApplication, auto-configuration, starters and the embedded server work, and why @Transactional fails on self-invocation.

What Spring and Spring Boot are

Spring is a framework whose container creates and wires your objects; Spring Boot sits on top of it and adds starters, auto-configuration, an embedded server and sensible defaults so an app runs with almost no setup.

Java was designed for large business applications, but writing them with plain Java means a lot of repeated work: creating objects, connecting them, opening database connections, handling transactions, reading config files. The Spring Framework (first released in 2003) took over that repeated work. You write business classes; Spring creates them, connects them and adds features such as transactions around them. A class managed this way is called a bean.

Early Spring needed pages of XML and a separate server (Tomcat) to run. Spring Boot (2014) removed that pain. You add one dependency, write one class with a main method, and you get a running web server with JSON support, logging and database connection pooling already configured. Boot does not replace Spring: it is Spring, with the setup done for you.

Version note: which Spring Boot should you learn?

Spring Boot 4.x (released November 2025) is built on Spring Framework 7 and Jakarta EE 11 and needs Java 17 or newer. Spring Boot 3.x (Spring Framework 6, Jakarta EE 10, Java 17+) is still on most company servers. Since Boot 3, all enterprise packages are jakarta.*, not javax.* (for example jakarta.persistence.Entity, jakarta.validation.Valid); old tutorials with javax.* are Boot 2 and will not compile. Everything in this module works on both. Learn on the latest stable Boot, use Java 21 or 25, and read the official migration guide when a project upgrades. Boot 4 also reorganised some starters and modules, so always copy dependency names from Initializr instead of from an old blog.

Rule: Boot never replaces Spring knowledge

Auto-configuration is just Spring beans created for you. When something goes wrong (a missing bean, a wrong config value, a transaction that does not roll back), you debug it with Spring Framework concepts: beans, scopes, proxies, properties. The rest of this module teaches exactly those.

Mistake: thinking Spring Boot is a different framework

"Boot is faster than Spring" or "Boot replaces Spring MVC" is wrong. Boot configures Spring MVC for you. If someone asks "Spring vs Spring Boot" in an interview, the answer is "Boot is an opinionated layer on top of Spring that removes configuration".

Interview: "What is Spring Boot and why use it?"

  • Spring is a container-based framework for building enterprise apps; Boot is a layer on top that gives starters, auto-configuration, an embedded server, an executable JAR and Actuator.
  • Benefits: faster start, less configuration, tested dependency versions, production-ready features, easy deployment (one JAR, Docker friendly).
  • Mention that you can still override any default, and that Boot is still plain Spring underneath.

Creating a project: Spring Initializr and project structure

start.spring.io generates a ready-to-run Maven or Gradle project from a few choices; its main class calls SpringApplication.run, and everything else lives in the standard src/main and src/test folders.

Spring Initializr is a web tool at start.spring.io. IntelliJ IDEA, VS Code and Spring Tools for Eclipse have the same tool built in (New Project → Spring Initializr). It writes a pom.xml (or build.gradle), a main class and a test class, so you start from a working build.

Press Generate, unzip the download and open the folder in your IDE. You can add dependencies later by editing pom.xml; nothing is locked in.

The generated structure

  • src/main/java — your code. src/main/resources — non-code files that go onto the classpath.
  • application.properties — starts empty except for spring.application.name. Rename it to application.yml if you prefer YAML (see the configuration article).
  • static/ and templates/ matter only for web pages. A pure REST API leaves them empty.
  • src/test/java — tests, mirroring the package of the code they test.
  • mvnw — the Maven Wrapper downloads the right Maven version on first use, so every developer and the CI server build the same way.

The main class

package com.example.orderservice;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class OrderserviceApplication {

    public static void main(String[] args) {
        SpringApplication.run(OrderserviceApplication.class, args);

}

SpringApplication.run does the whole startup: it reads the configuration, creates the ApplicationContext (the container), scans for beans, applies auto-configuration, starts the embedded Tomcat and keeps the JVM alive. What @SpringBootApplication means is explained in its own article.

Package by layer or by feature

Where do your own classes go under com.example.orderservice? There are two common styles.

By layerBy feature
Layoutcontroller/, service/, repository/, model/order/, customer/, payment/, each holding its own controller, service, repository
Good forSmall apps, learning, quick scanning of "all controllers"Bigger apps; a feature's code sits together; easy to extract into a microservice later
WeaknessOne feature is spread over four folders; everything tends to be publicNeeds discipline about what one feature may call in another

Start with layers while learning; move to features when the project grows past a handful of entities. Both work with component scanning as long as the sub-packages sit under the main class's package.

Rule: keep the main class in the root package

The main class must sit in a package above all your other code (com.example.orderservice), because scanning starts there. Never leave it in the default (empty) package: Spring would scan the whole classpath and Boot logs a warning.

Conventions

  • Commit pom.xml, mvnw, .mvn/ and the sources. Add target/ to .gitignore.
  • Use the wrapper (./mvnw) in README and CI so nobody needs a local Maven.
  • Name the application class XxxApplication.

Edge cases

  • Port 8080 already in use: the app fails with Web server failed to start. Port 8080 was already in use. Stop the other program or set server.port.
  • Unsupported class file major version or a compile error about the release version: your installed JDK is older than the java.version in the pom.
  • On Windows PowerShell use .\mvnw.cmd spring-boot:run; in Git Bash ./mvnw works.

Interview: "Walk me through a Spring Boot project and its startup"

  • Main class annotated @SpringBootApplication calls SpringApplication.run; the resources folder holds application.yml; the pom inherits from the Boot parent and uses starters.
  • Startup creates the context, scans for beans, applies auto-configuration, starts Tomcat, then runs any CommandLineRunner beans.
  • Packaging is a fat JAR run with java -jar.

Inversion of Control and dependency injection, in plain Java first

Dependency injection means a class receives the objects it needs instead of creating them; Inversion of Control means something else (the Spring container) decides which objects to create and hand over.

Before any annotation, understand the problem with plain Java. A dependency is any object your class needs to do its work. An OrderService that sends a confirmation needs something that can send messages; that "something" is its dependency.

Step 1: tight coupling with new

public class EmailSender {
    public void send(String to, String text) {
        System.out.println("EMAIL to " + to + ": " + text);
    }
}

public class OrderService {
    private final EmailSender sender = new EmailSender();   // hard-wired

    public void placeOrder(String customerEmail) {
        // ... save the order ...
        sender.send(customerEmail, "Your order is confirmed");
    }
}

This works, but it hurts in four ways. (1) OrderService is welded to EmailSender: to switch to SMS you must edit OrderService. (2) You cannot unit-test it without really sending an email, because you cannot replace the sender. (3) If EmailSender itself needs an SMTP host and a password, OrderService must know how to build it. (4) You cannot share one instance across classes. This is called tight coupling.

Step 2: program to an interface, receive it through the constructor

public interface NotificationSender {
    void send(String to, String text);
}

public class EmailSender implements NotificationSender {
    public void send(String to, String text) {
        System.out.println("EMAIL to " + to + ": " + text);
    }
}

public class SmsSender implements NotificationSender {
    public void send(String to, String text) {
        System.out.println("SMS to " + to + ": " + text);
    }
}

public class OrderService {
    private final NotificationSender sender;           // only the interface

    public OrderService(NotificationSender sender) {   // given from outside
        this.sender = sender;
    }

    public void placeOrder(String customer) {
        sender.send(customer, "Your order is confirmed");
    }
}

public class Main {
    public static void main(String[] args) {
        NotificationSender sender = new EmailSender();      // you wire it
        OrderService service = new OrderService(sender);    // by hand
        service.placeOrder("ravi@example.com");
    }
}
EMAIL to ravi@example.com: Your order is confirmed

This is dependency injection (DI): OrderService no longer creates its sender, it is given one. Now switching to SMS needs no change inside OrderService, and a unit test can pass a fake sender. DI is only a technique — a constructor that takes its collaborators. You can do it with no framework at all.

Step 3: the wiring grows, so let a container do it

In a real app you have 50 or 200 classes, each with dependencies, which have their own dependencies. Writing that wiring by hand in main becomes a long, fragile list: you must create objects in the right order and share singletons correctly.

DataSource ds = new HikariDataSource(config);
OrderRepository repo = new OrderRepository(ds);
PaymentClient payment = new PaymentClient(httpClient, apiKey);
NotificationSender sender = new EmailSender(smtpHost, user, pass);
OrderService service = new OrderService(repo, payment, sender);
OrderController controller = new OrderController(service);
// ... 40 more lines, in the right order ...

Inversion of Control (IoC) means you hand this job to a framework. Normally your code is in control: you decide what to create and when. With IoC the framework is in control: it creates the objects, finds each one's dependencies, builds them in the right order and gives them out. You only declare what is a bean and what each class needs. The container that does this is Spring's ApplicationContext.

@Service
public class OrderService {
    private final NotificationSender sender;

    public OrderService(NotificationSender sender) {   // Spring passes it in
        this.sender = sender;
    }
    // ...
}

@Component
public class EmailSender implements NotificationSender { /* ... */ }

The classes did not change much. What disappeared is the new calls and the main wiring. Spring sees that OrderService needs a NotificationSender, finds the EmailSender bean, creates it first, then creates OrderService with it.

IoC vs DI

Inversion of ControlDependency Injection
What it isA design principle: the framework calls your code and controls object creation ("Hollywood principle: don't call us, we call you")A technique that implements IoC for object dependencies
ScopeWider: also covers callbacks, event listeners, the servlet container calling your controllerNarrower: how an object gets its collaborators
In SpringThe container manages the life of beansConstructor, setter or field injection

Why this is worth it

  • Easy testing. Pass a fake NotificationSender into the constructor; no Spring needed for a unit test (Module 5).
  • Swappable parts. Change the implementation by changing configuration, not business code (the demo project uses this with profiles).
  • One place for lifecycle. Singletons, creation order, startup and shutdown callbacks are the container's job.
  • Cross-cutting features. Because the container creates your objects, it can wrap them in proxies to add transactions, caching and security (the AOP article).

Rule: depend on interfaces, not on concrete classes

Declare the field and constructor parameter as the interface (NotificationSender), not EmailSender. The container supplies whichever implementation is configured. If you write the concrete class, you lose the swapping and testing benefit.

Convention: do not use new for your own beans

Inside a Spring app, never write new OrderService(...) for a class that is a bean. The object you create is not managed: it gets no injection, no proxy and no transactions. Ask for it as a dependency instead. Plain value objects (DTOs, records, entities) are fine to create with new.

Edge cases

  • Not every class should be a bean. Beans are services and components with behaviour and shared state-free logic; data holders are not beans.
  • You can still use DI without Spring (Guice, Dagger, Jakarta CDI, or by hand). Spring just also bundles lifecycle, AOP and configuration.
  • Too many constructor parameters (more than about five) is a design smell: the class probably does too much. Split it.

Interview: "What is IoC? What is DI? What problem do they solve?"

  • Without DI, classes create their dependencies with new — tight coupling, hard to test, hard to change.
  • DI gives the object its dependencies from outside (best through the constructor). IoC means the framework controls creation and wiring.
  • Spring's IoC container reads bean definitions (annotations or Java config), builds the object graph in dependency order and manages scope and lifecycle.
  • Benefits: loose coupling, testability, one place for configuration, ability to add proxies for transactions and security.

The container: ApplicationContext, BeanFactory and bean definitions

The ApplicationContext is the Spring container: it reads bean definitions, creates the beans in dependency order, injects them into each other and manages their life until shutdown.

When SpringApplication.run returns, it hands you back a ConfigurableApplicationContext. That object is the container. It holds every bean in a registry (a map from bean name to bean), knows how each was built and keeps singleton beans alive until the application stops.

BeanFactory vs ApplicationContext

BeanFactoryApplicationContext
RoleThe basic container: create beans, look them up, inject dependenciesA BeanFactory plus enterprise features
Singleton creationLazy: when first requestedEager: all singletons are created at startup
ExtrasNoneEvents, Environment and properties, message sources (i18n), resource loading, annotation processing, BeanPostProcessor registration

Eager creation is a feature: a wrong configuration makes the application fail at startup, not hours later when a user hits that code path.

Bean definitions: the recipe

Before the container builds any object, it collects bean definitions. A definition is a recipe: the class, the scope, the init and destroy methods, the dependencies. Definitions come from three places:

  • Stereotype annotations found by component scanning (@Component and friends).
  • @Bean methods inside @Configuration classes.
  • Auto-configuration classes from Boot libraries (they are ordinary @Configuration classes, just loaded conditionally).

Every bean has a name (id) and a type. For a scanned class the default name is the simple class name with a lowercase first letter: OrderService becomes orderService. For a @Bean method the name is the method name.

Using the context directly

In application code you almost never call the container; you declare dependencies. But it helps to see it once, for example to understand what Boot does or in a quick experiment:

@SpringBootApplication
public class OrderserviceApplication {

    public static void main(String[] args) {
        ConfigurableApplicationContext ctx =
                SpringApplication.run(OrderserviceApplication.class, args);

        OrderService byType = ctx.getBean(OrderService.class);
        OrderService byName = (OrderService) ctx.getBean("orderService");
        boolean same = byType == byName;
        System.out.println("Same singleton? " + same);
        System.out.println("Bean count: " + ctx.getBeanDefinitionCount());
    }
}
Same singleton? true
Bean count: 164

Calling getBean yourself is the service locator style and is an anti-pattern in normal code: it hides dependencies and brings back the testing problems DI solved. Use it only in framework-style glue code.

The ApplicationContext in a plain Spring program (no Boot)

@Configuration
@ComponentScan("com.example.shop")
class AppConfig { }

public class Main {
    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(AppConfig.class)) {
            ctx.getBean(OrderService.class).placeOrder("ravi@example.com");
        }   // close() destroys singleton beans and runs @PreDestroy
    }
}

Boot does the same thing with SpringApplication.run, plus auto-configuration and an embedded server. You can even list all beans with ctx.getBeanDefinitionNames() to see what auto-configuration created for you.

Rule: beans are found by type first, then by name

Injection matches the type of the parameter. If several beans have that type, Spring falls back to matching the parameter name against bean names, and then you need @Primary or @Qualifier (see the injection article).

Convention: let Boot own the context

Do not create a second ApplicationContext inside a Boot app. Tests use @SpringBootTest or slice annotations, which create one for you (Module 5).

Edge cases

  • Only singleton beans are created eagerly. Prototype and request-scoped beans are created on demand, and @Lazy singletons wait until first use.
  • A web app uses a web-aware context (AnnotationConfigServletWebServerApplicationContext) that also starts the embedded server. You do not need to remember the class name.
  • Contexts form hierarchies (parent and child), used in older Spring MVC setups and in some Spring Cloud setups. Boot apps normally have one.

Interview: "BeanFactory vs ApplicationContext? What happens at startup?"

  • BeanFactory is the basic lazy container; ApplicationContext adds events, property/environment handling, i18n, resource loading and eager singleton creation. Use the latter.
  • Startup: collect bean definitions, run post-processors, create singletons in dependency order, inject, run init callbacks, then the context is ready.
  • Eager singleton creation makes wiring errors fail fast at startup.

Component scanning and the stereotype annotations

Component scanning finds classes marked @Component (or @Service, @Repository, @Controller) in the main class's package and its sub-packages and registers each as a bean.

You do not list your beans anywhere. Instead you put an annotation on the class, and at startup Spring walks the packages looking for those annotations. This is component scanning. It is switched on by @ComponentScan, which is part of @SpringBootApplication.

The scanning rule

@SpringBootApplication scans the package of the class it is on, and all sub-packages — nothing else.

Mistake: a bean outside the base package

The most common beginner failure: a class is annotated @Service but lives in a sibling package, so nobody finds it. The app fails with "required a bean of type … that could not be found".

Wrong: service outside the scanned tree

// main class: com.example.shop.ShopApplication
package com.example.common;     // sibling of com.example.shop

@Service
public class AuditService { }

Right: move it under the base package, or widen the scan

package com.example.shop.common;     // under the main class

// or, if it must stay where it is:
@SpringBootApplication(scanBasePackages = {"com.example.shop", "com.example.common"})
public class ShopApplication { }

Moving the class is nearly always better than widening the scan. Use scanBasePackages (or @ComponentScan with basePackages) only for shared libraries from other modules.

The stereotype annotations

A stereotype annotation marks a class as a bean and also tells readers its role. @Component is the generic one; the others are specialisations of it (they are meta-annotated with @Component).

AnnotationLayerExtra behaviour
@ComponentAny class that fits no other role (a mapper, a helper, a client)None. Just a bean.
@ServiceBusiness logicNone today; documents intent and is a good pointcut target.
@RepositoryData accessTranslates persistence exceptions (such as SQLException or Hibernate errors) into Spring's unchecked DataAccessException hierarchy.
@ControllerWeb layer returning HTML viewsHandler methods are found by Spring MVC; return values are view names.
@RestControllerWeb layer returning JSON@Controller + @ResponseBody: return values are written to the response body.
 
@RestController
@RequestMapping("/api/v1/orders")
public class OrderController {
    private final OrderService service;
    public OrderController(OrderService service) { this.service = service; }
}

@Service
public class OrderService {
    private final OrderRepository repository;
    public OrderService(OrderRepository repository) { this.repository = repository; }
}

@Repository
public class JdbcOrderRepository implements OrderRepository { /* ... */ }

With Spring Data (Module 3) you will not annotate repository interfaces yourself; Spring Data creates and registers them. You still use @Repository on hand-written data-access classes.

Exception translation in @Repository

Each persistence technology throws its own exceptions. A @Repository bean is wrapped by a post-processor (PersistenceExceptionTranslationPostProcessor, which Boot registers for you when data access is present) so those exceptions turn into DataAccessException subclasses, such as DuplicateKeyException or DataIntegrityViolationException. Your service code then does not depend on JPA or JDBC exception types.

Bean names and conflicts

  • Default name: class name, first letter lowercase (OrderService → orderService). An exception: names like URLService keep their case, because the first two letters are capitals.
  • Custom name: @Service("orders").
  • Two scanned classes with the same simple name in different packages produce the same default name and fail with ConflictingBeanDefinitionException. Give one an explicit name.

Customising what is scanned

  • @ComponentScan(basePackages = "...") sets other packages (this replaces the default, so list the original one as well).
  • Include/exclude filters (@ComponentScan.Filter) can drop classes by annotation or pattern.
  • @Profile("dev") on a class keeps it out of the context unless that profile is active (profiles).

Rules

  • A scanned class must be concrete (not an interface or abstract class) and needs a constructor Spring can call.
  • Use the most specific stereotype: @Service for services, @Repository for data access, @RestController for JSON endpoints.
  • Scanning only finds classes you annotate; third-party classes cannot be annotated, so use @Bean for them (next article).

Conventions

  • Do not put @Component on everything. Entities, DTOs and records are data, not beans.
  • Keep the dependency direction one-way: controller → service → repository. A repository must never call a controller.
  • Use @Component (not @Service) for technical helpers such as a JSON mapper or a filter.

Edge cases

  • @Service and @Component behave the same; using the wrong one never breaks the app, but it misleads readers and can break AOP pointcuts written for a stereotype.
  • In tests with @WebMvcTest or @DataJpaTest, only a slice of beans is loaded; a scanned @Service is missing unless you add it with @Import or @MockitoBean (Module 5).
  • A class with two constructors and no @Autowired on one makes Spring look for a no-argument constructor and fail (see injection).

Interview: "@Component vs @Service vs @Repository? What does @ComponentScan do?"

  • All three register a bean. @Service and @Repository are specialisations of @Component that express the layer; @Repository also enables exception translation.
  • @Controller adds web handling; @RestController = @Controller + @ResponseBody.
  • Component scanning looks in the main class's package and sub-packages; a bean outside gives NoSuchBeanDefinitionException.
  • For classes you cannot annotate (third-party), declare a @Bean method.

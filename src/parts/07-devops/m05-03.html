RDS: managed PostgreSQL, private access and the cheap Docker alternative

RDS runs PostgreSQL for you (installation, patching, backups, failover); you keep it private by allowing port 5432 only from your EC2 security group, pass the endpoint to Spring Boot through environment variables, and delete it when a lab ends.

Why a managed database

Running PostgreSQL yourself means installing it, tuning it, patching it, taking backups, testing restores and planning for a failed disk. Amazon RDS (Relational Database Service) does the heavy parts:

  • Backups: automatic daily backups plus transaction logs, so you can restore to a point in time within the retention period you set.
  • Patching: minor engine updates and OS patches in a maintenance window you choose.
  • Multi-AZ: a standby copy in another availability zone with automatic failover.
  • Monitoring and storage growth: metrics in CloudWatch and storage that can scale.

You still own the schema, the users, the queries, the indexes and the network rules. RDS is the right default for a real application; the cost is higher than running the database yourself, and the exact price changes, so check the current RDS pricing page and any free-tier offer before you create one.

Create an instance (console steps)

  1. RDS → Create database → Standard create → engine PostgreSQL.
  2. Pick a template for your purpose (the console offers dev/test or free-tier style templates; read the current descriptions) and a small instance class. Use the same region as your EC2 instance.
  3. DB instance identifier shop-db; master username and a long random password (or let RDS keep the password in Secrets Manager).
  4. Storage: small is enough; understand whether storage autoscaling is on.
  5. Connectivity: the same VPC as your EC2 instance; Public access: No; create a new security group shop-db-sg.
  6. Additional configuration: initial database name shop; backup retention; Multi-AZ only if you need it (it roughly doubles the cost).
  7. Create. After a few minutes, copy the endpoint, a DNS name such as shop-db.abc123.ap-south-1.rds.amazonaws.com.

Let only your server in

A security group rule can name another security group as its source. Edit shop-db-sg and add an inbound rule: type PostgreSQL, port 5432, source = the security group of your EC2 instance (for example shop-ec2-sg). Now any instance in that group can connect, whatever its IP, and nobody else can, including you from your laptop.

Connect and create an application user

$ sudo apt install -y postgresql-client
$ psql -h shop-db.abc123.ap-south-1.rds.amazonaws.com -U postgres -d shop
Password for user postgres:
shop=>
CREATE USER shop_app WITH PASSWORD 'change-me-long-random';
ALTER DATABASE shop OWNER TO shop_app;   -- simple for a small app; Flyway needs DDL rights

Do not run the application as the master user. A dedicated user limits the damage of a bug or a leaked password. If you need to reach the database from your laptop (for a one-time import), use an SSH tunnel through the EC2 server instead of opening 5432 to the world:

$ ssh -i shop-key.pem -N -L 5433:shop-db.abc123.ap-south-1.rds.amazonaws.com:5432 ubuntu@203.0.113.25
# in another terminal:
$ psql -h localhost -p 5433 -U shop_app -d shop

Connect from Spring Boot

Spring Boot reads the standard properties, and any property can be set by an environment variable (dots become underscores, uppercase). Put the values in the server's .env file:

SPRING_DATASOURCE_URL=jdbc:postgresql://shop-db.abc123.ap-south-1.rds.amazonaws.com:5432/shop?sslmode=require
SPRING_DATASOURCE_USERNAME=shop_app
SPRING_DATASOURCE_PASSWORD=change-me-long-random
SPRING_JPA_HIBERNATE_DDL_AUTO=validate
SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=10

sslmode=require asks the PostgreSQL JDBC driver to encrypt the connection (it does not verify the server certificate; stricter modes need the RDS CA bundle). ddl-auto=validate means Hibernate only checks the schema; create tables with Flyway or Liquibase migrations, never with update in production (see Spring Boot · Module 3). Limit the Hikari pool: a small RDS instance allows only a limited number of connections, and several app instances each hold a pool.

Backups, snapshots and restore

  • Automated backups are on by default with a retention period you set; they enable point-in-time restore.
  • Manual snapshots are kept until you delete them. Take one before a risky migration. Snapshots use (billed) storage.
  • A restore creates a new instance with a new endpoint; it does not rewind the old one. You then update SPRING_DATASOURCE_URL. Practise a restore once while nothing depends on it; a backup you have never restored is only a hope.
  • When you delete an instance, the console offers a final snapshot. Automated backups are removed with the instance unless you choose otherwise.

Multi-AZ and read replicas

Multi-AZ keeps a synchronous standby in another AZ. If the primary fails, RDS flips the endpoint's DNS to the standby, usually within a minute or two. It improves availability, not read speed. A read replica is a separate copy used to spread read queries and has its own endpoint; it is for scaling, not failover. Do not confuse the two (a common interview question).

The cheap option: PostgreSQL in Docker on the same EC2

For a learning project you can run PostgreSQL as another Compose service and skip the RDS cost:

  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: shop
      POSTGRES_USER: shop_app
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    restart: unless-stopped
    # no 'ports:' section: only the api container can reach it

volumes:
  pgdata:

The app then uses jdbc:postgresql://postgres:5432/shop (the service name, see Docker networks). The risks are real:

Pros

  • No extra service cost; simple to start.
  • Fast: same machine, no network hop.

Cons

  • One disk and one machine: if the instance dies, the data may die with it.
  • No automatic backups, failover or patching; you must do them.
  • The database and the app fight over a small amount of RAM.
  • docker compose down -v deletes the data volume.
$ docker compose exec -T postgres pg_dump -U shop_app shop | gzip > /opt/backups/shop-$(date +%F).sql.gz
$ aws s3 cp /opt/backups/shop-$(date +%F).sql.gz s3://shop-backups-asha/

Also take regular EBS snapshots. For anything with real users, use RDS.

Mistakes

  • Turning on "Public access" and opening 5432 to 0.0.0.0/0 to "make it work". Bots find it in minutes.
  • Leaving a test RDS instance running for weeks.
  • Using the master user and ddl-auto=create in production.

Errors and what they mean

  • Connection timed out or PSQLException: The connection attempt failed — security group rule missing or wrong source, wrong endpoint, or EC2 in a different VPC.
  • password authentication failed for user — wrong password or user; special characters in a password inside a URL need escaping (put credentials in separate variables as above).
  • too many connections — pool sizes times app instances exceed the database limit.
  • After the instance was stopped: RDS can be stopped for a limited time and then restarts by itself, so a "stopped" database may begin billing again.

Interview: "Why use RDS instead of installing PostgreSQL on EC2?"

  • Managed backups with point-in-time restore, patching, Multi-AZ failover, monitoring; less operational risk. Cost: higher price and less OS-level control.
  • Security: private subnet or no public access, access only from the app's security group.

S3: buckets, objects, safe access and presigned URLs

S3 stores files as objects in buckets; keep buckets private with Block Public Access, let your app reach them through an IAM role, and let browsers upload or download directly using short-lived presigned URLs.

Buckets and objects

S3 (Simple Storage Service) is object storage: you put whole files in and get whole files out over HTTP. A bucket is a top-level container, and its name is unique across all AWS accounts (lowercase letters, digits, hyphens). An object is a file plus metadata, found by its key, for example products/42/photo.jpg. S3 has no real folders; the slashes are just part of the key, and the console shows them as folders using the prefix. S3 is very durable and scales without limit, but it is not a file system: you cannot append to an object or edit part of it, only replace it. Typical uses: user uploads, invoices and PDFs, images, backups, static websites and build artefacts.

Storage classes (brief)

ClassMeant for
StandardFrequently accessed data (the default)
Intelligent-TieringUnknown or changing access patterns; S3 moves objects automatically
Standard-IA / One Zone-IARarely accessed but needs quick access; cheaper storage, retrieval fee
Glacier classesArchives and compliance data; retrieval takes minutes to hours

A lifecycle rule moves or deletes objects automatically, for example "delete temp uploads after 7 days" or "move logs to an archive class after 30 days". Costs depend on class, requests and data transfer; check current pricing.

Keep it private

  • Block Public Access is on by default for new buckets. Leave it on. Public buckets are behind many data leaks.
  • Access is decided by IAM policies (what a user or role may do) and optionally a bucket policy. Your app gets access through an instance role, not through keys in the code.
  • Enable default encryption (new buckets already encrypt objects at rest) and consider versioning to recover from accidental overwrites.

Uploading from Spring Boot (AWS SDK for Java v2)

Add the SDK's BOM (bill of materials, which keeps module versions aligned) and the s3 module. Use the latest 2.x version shown on the SDK's documentation page for the property below.

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>software.amazon.awssdk</groupId>
      <artifactId>bom</artifactId>
      <version>${aws.sdk.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <dependency>
    <groupId>software.amazon.awssdk</groupId>
    <artifactId>s3</artifactId>
  </dependency>
</dependencies>
@Configuration
public class AwsConfig {

    @Bean
    S3Client s3Client(@Value("${app.aws.region}") String region) {
        // No keys here: the SDK finds credentials by itself (env, profile, or the EC2 role)
        return S3Client.builder().region(Region.of(region)).build();
    }

    @Bean
    S3Presigner s3Presigner(@Value("${app.aws.region}") String region) {
        return S3Presigner.builder().region(Region.of(region)).build();
    }
}
@Service
public class FileStorageService {

    public record UploadTicket(String key, String url) { }

    private final S3Client s3;
    private final S3Presigner presigner;
    private final String bucket;

    public FileStorageService(S3Client s3, S3Presigner presigner,
                              @Value("${app.aws.bucket}") String bucket) {
        this.s3 = s3;
        this.presigner = presigner;
        this.bucket = bucket;
    }

    /** Server-side upload: the file passes through your app. Fine for small files. */
    public String upload(MultipartFile file) throws IOException {
        String key = "uploads/" + UUID.randomUUID();      // never trust the user's file name
        PutObjectRequest request = PutObjectRequest.builder()
                .bucket(bucket).key(key).contentType(file.getContentType()).build();
        s3.putObject(request, RequestBody.fromInputStream(file.getInputStream(), file.getSize()));
        return key;
    }

    /** A link the browser can use to download one private object for 10 minutes. */
    public String downloadUrl(String key) {
        GetObjectRequest get = GetObjectRequest.builder().bucket(bucket).key(key).build();
        GetObjectPresignRequest presign = GetObjectPresignRequest.builder()
                .signatureDuration(Duration.ofMinutes(10)).getObjectRequest(get).build();
        return presigner.presignGetObject(presign).url().toString();
    }

    /** A link the browser can use to upload one object directly to S3. */
    public UploadTicket uploadTicket(String contentType) {
        String key = "uploads/" + UUID.randomUUID();
        PutObjectRequest put = PutObjectRequest.builder()
                .bucket(bucket).key(key).contentType(contentType).build();
        PutObjectPresignRequest presign = PutObjectPresignRequest.builder()
                .signatureDuration(Duration.ofMinutes(10)).putObjectRequest(put).build();
        return new UploadTicket(key, presigner.presignPutObject(presign).url().toString());
    }
}

Presigned URLs

A presigned URL is a normal S3 URL with a signature in its query string, created by your server using its credentials. Whoever holds the URL can perform that one operation on that one object until it expires, with no AWS account. This lets the browser talk to S3 directly, so a 200 MB video does not pass through your Spring Boot server.

async function uploadFile(file) {
  const res = await fetch("/api/files/upload-url", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ contentType: file.type }),
  });
  const { key, url } = await res.json();

  // The Content-Type here must match the one that was signed
  const put = await fetch(url, {
    method: "PUT",
    headers: { "Content-Type": file.type },
    body: file,
  });
  if (!put.ok) throw new Error("Upload failed: " + put.status);
  return key;
}

The browser calls S3 from your site's origin, so the bucket needs a CORS configuration (Bucket → Permissions → Cross-origin resource sharing). Restrict it to your real origins:

[
  {
    "AllowedOrigins": ["https://shop.example.com", "http://localhost:5173"],
    "AllowedMethods": ["GET", "PUT"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3000
  }
]

Serving a React build from S3 and CloudFront (brief)

S3 can hold the static files of a React app, and CloudFront (AWS's CDN) serves them over HTTPS from locations near the user. Keep the bucket private and give CloudFront access with an Origin Access Control.

  1. Build: npm run build creates dist/.
  2. Upload: aws s3 sync dist/ s3://shop-web-asha --delete.
  3. Create a CloudFront distribution with the bucket as origin, default root object index.html.
  4. For client-side routing, add custom error responses that return /index.html with status 200 for 403 and 404.
  5. For a custom domain, request a certificate in AWS Certificate Manager (CloudFront needs it in us-east-1) and add the domain to the distribution.
  6. After each deploy: aws cloudfront create-invalidation --distribution-id EXXXX --paths "/*" so users do not see old files.

This is fine, but Vercel or Netlify do the same with far less setup (see Vercel and Netlify).

Mistakes

  • Making the bucket public so "the images load". Use presigned GET URLs, or CloudFront.
  • Putting AWS keys in the React code to upload directly. Everything in the browser is public; use a presigned URL.
  • Using the original file name as the key (path tricks, clashes, personal data). Generate the key.
  • Very long expiry times on presigned URLs. Use minutes.

Exceptions and errors

  • A presigned URL made with temporary role credentials stops working when those credentials expire, even if you asked for a longer time.
  • SignatureDoesNotMatch on a PUT — the browser sent a different Content-Type (or signed header) than the one signed.
  • S3Exception with status 403 AccessDenied — the role lacks the permission, or the bucket policy denies it; 404 NoSuchKeyException — wrong key; NoSuchBucket — wrong name or region.
  • SdkClientException: Unable to load credentials — no role, profile or environment credentials on this machine.
  • CORS errors appear in the browser console, not in your Java logs.

Interview: "How would you let users upload a large file securely?"

  • The API authenticates the user and returns a short-lived presigned PUT URL for a generated key; the browser uploads directly to a private bucket (with CORS); the API then stores the key in the database. Limit type and size, and scan if needed.

IAM: users, roles, policies, least privilege and instance roles

IAM decides who may do what in AWS: policies (JSON documents) grant actions on resources to users, groups or roles; give every person and application the minimum, and give EC2 a role so no access keys are stored on the server.

The building blocks

User
An identity for one person or program, with a password and/or access keys. Long-lived credentials, so use them sparingly.
Group
A set of users that share permissions ("developers"). Permissions attach to the group, not to each user.
Role
An identity with no permanent password or key that a trusted entity can assume to receive temporary credentials: an EC2 instance, a Lambda function, another AWS account, or a person signing in through Identity Center.
Policy
A JSON document listing allowed or denied actions on resources. Attached to users, groups and roles (identity policies), or to a resource such as a bucket (resource policy).

IAM is global, not tied to a region. By default everything is denied. A request succeeds only when some policy allows it and no policy explicitly denies it (an explicit Deny always wins).

Anatomy of a policy

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadWriteObjects",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::shop-uploads-asha/*"
    },
    {
      "Sid": "ListTheBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::shop-uploads-asha"
    }
  ]
}
Version
The policy language version. Always 2012-10-17.
Statement
One or more rules.
Effect
Allow or Deny.
Action
The API operation, written service:Operation. Wildcards such as s3:* are allowed but broad.
Resource
What the action applies to, as an ARN (Amazon Resource Name), in the form arn:aws:service:region:account-id:resource. S3 ARNs have no region or account.
Condition
Optional extra checks, for example the region or source IP.

Notice the two ARNs. Object actions apply to bucket/* (the objects), while s3:ListBucket applies to the bucket itself, without /*. Mixing them up is the most common S3 policy bug. A condition example, which allows an action only in the Mumbai region:

{
  "Effect": "Allow",
  "Action": "ec2:*",
  "Resource": "*",
  "Condition": {
    "StringEquals": { "aws:RequestedRegion": "ap-south-1" }
  }
}

Policies are either AWS managed (ready-made, for example AmazonS3ReadOnlyAccess, easy but often broader than needed) or customer managed (yours, like the one above), plus inline policies embedded in one identity. Prefer customer managed policies for anything real.

Least privilege in practice

  1. Start with no permissions. Add what the task needs.
  2. Name exact resources (one bucket) instead of "Resource": "*".
  3. Name exact actions instead of "Action": "*".
  4. When a call fails with AccessDenied, read the message. It names the action and resource, such as "not authorized to perform: s3:PutObject on resource: arn:aws:s3:::shop-uploads-asha/uploads/x", and tells you exactly what to add.
  5. Later, use IAM's "last accessed" information and Access Analyzer to remove unused permissions.

Instance roles: no keys on the server

Your Spring Boot app on EC2 needs to reach S3. The wrong way is to create an access key and paste it into .env. The right way is an IAM role for EC2. AWS gives the instance temporary credentials that rotate automatically, and the SDK finds them by itself through the instance metadata service.

  1. IAM → Roles → Create role → trusted entity: AWS service → EC2.
  2. Attach your customer-managed policy (the JSON above). Name the role shop-api-role.
  3. EC2 → select the instance → Actions → Security → Modify IAM role → choose shop-api-role. (Behind the scenes the role sits in an "instance profile".)
  4. Run the app with no AWS_ACCESS_KEY_ID variables. The SDK's default credentials provider chain tries environment variables, then profile files, and finally the instance role.

The role also has a trust policy, saying who may assume it. The console writes it for you when you pick EC2:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "ec2.amazonaws.com" },
      "Action": "sts:AssumeRole"
    }
  ]
}

Two policies, two questions: the trust policy answers "who can become this role?" and the permissions policy answers "what can the role do?".

Edge case: the role does not work inside a Docker container

Recent instances require IMDSv2 with a hop limit of 1, and a request from a container on the default bridge network takes one more hop, so the SDK inside the container may fail with "Unable to load credentials". Raise the hop limit to 2 for the instance:

$ aws ec2 modify-instance-metadata-options \
    --instance-id i-0abc123def456789 \
    --http-tokens required \
    --http-put-response-hop-limit 2

Check which identity the server uses (install the AWS CLI first, or read the app's startup log):

{
    "UserId": "AROAEXAMPLEROLEID:i-0abc123def456789",
    "Account": "123456789012",
    "Arn": "arn:aws:sts::123456789012:assumed-role/shop-api-role/i-0abc123def456789"
}

Other tools worth knowing

  • MFA for every human user. Password policy for IAM users.
  • Permission boundaries and Service Control Policies (organisation-wide limits) set the maximum permissions; companies with many accounts use them.
  • IAM Identity Center for staff sign-in with temporary credentials.
  • CloudTrail records who called which API, which is essential for audits and for investigating incidents.

Mistakes

  • Attaching AdministratorAccess to the application, "just to make it work".
  • Keys in .env on the server, in the image, or in Git, when a role would do.
  • Sharing one IAM user among several people.
  • Writing s3:ListBucket on bucket/*; it needs the bucket ARN.

In real projects

Each service has its own role with a small policy; developers sign in through SSO with roles that expire; production access is limited and audited; policies are written as Terraform (Module 6) and reviewed like code.

Interview: "How does an application on EC2 access S3 securely?"

  • An IAM role with a least-privilege policy, attached to the instance (instance profile); the SDK uses temporary credentials from the metadata service; nothing is stored on disk.
  • Explain user vs role, trust policy vs permissions policy, default deny and explicit deny.

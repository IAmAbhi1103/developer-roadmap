HTTP versus HTTPS, TLS certificates and Let's Encrypt

HTTPS is HTTP inside a TLS tunnel: TLS encrypts the traffic, detects tampering and proves the server's identity with a certificate signed by a trusted authority; Let's Encrypt and certbot give you that certificate for free and renew it automatically.

HTTP is plain text

HTTP is the request/response protocol of the web. Over plain HTTP (port 80) every router between the browser and the server can read and change the data: passwords, cookies, JWTs, card details. Public Wi-Fi makes this easy. HTTPS (port 443) wraps HTTP in TLS (Transport Layer Security; the old name was SSL, and people still say "SSL certificate"). Today every real site should use HTTPS only, and browsers mark plain HTTP as "Not secure".

What TLS gives you

Encryption (confidentiality)
Only the two ends can read the data. A listener on the path sees random bytes.
Integrity
Any change in transit is detected, so nobody can silently alter a response or inject a script.
Authentication
The browser verifies that the server really owns the domain, using a certificate. This stops someone from impersonating yourbank.com.

Certificates and certificate authorities

A certificate is a signed document that says "this public key belongs to shop.example.com, valid from date A to date B". It is signed by a Certificate Authority (CA). Your operating system and browser ship with a list of CAs they trust (root certificates). Servers usually send a chain: the server certificate, signed by an intermediate CA, signed by a root the browser already trusts. The browser checks that the chain leads to a trusted root, that the name matches, that the dates are valid and that the certificate was not revoked.

The TLS handshake, simplified

  1. The client says which TLS versions and ciphers it supports and, through SNI (Server Name Indication), the host name it wants. SNI lets one IP serve many HTTPS sites.
  2. The server chooses the settings and sends its certificate chain.
  3. The client verifies the chain and the name.
  4. Both sides use a key-exchange algorithm to agree on a fresh session key without ever sending it. The slow public-key maths is used only here.
  5. The rest of the connection uses fast symmetric encryption with the session key.

Where the TLS ends matters. Most setups use TLS termination at Nginx or a load balancer: the proxy handles HTTPS, and passes plain HTTP to your Spring Boot app on localhost or a private network (Nginx config).

Let's Encrypt and certbot

Let's Encrypt is a free, automated CA. It proves you control a domain by asking for a file at http://yourdomain/.well-known/acme-challenge/... (the HTTP-01 challenge), so the domain must already point to your server and port 80 must be open. Its certificates last 90 days by design, so renewal must be automatic. certbot is the usual client.

$ sudo apt install -y certbot python3-certbot-nginx

The --nginx plugin edits your Nginx config to add the certificate and (if you choose) an HTTP-to-HTTPS redirect. Certbot installs a systemd timer (or cron job) that renews certificates before they expire; --dry-run proves the renewal path works. The two files you care about: fullchain.pem (your certificate plus the intermediates) and privkey.pem (the private key: keep it secret, readable by root only). Certbot's exact prompts and the way it is installed (apt or snap) vary by version; check certbot.eff.org for current instructions. An email address, a domain pointing at the server and open ports 80 and 443 are what you need.

Besides HTTP-01, there is a DNS-01 challenge (a TXT record) which allows wildcard certificates such as *.example.com and works for servers that are not reachable from the internet. AWS offers a different route: AWS Certificate Manager (ACM) gives free certificates for use with load balancers and CloudFront, so you may not need certbot at all (Module 5).

HSTS, HTTP/2 and HTTP/3

  • HSTS (HTTP Strict Transport Security): the header Strict-Transport-Security: max-age=31536000 tells browsers to use only HTTPS for that domain for the given seconds. It prevents downgrade attacks. Enable it only when HTTPS works everywhere, because a mistake is cached by browsers for a long time.
  • HTTP/2 keeps one connection and sends many requests in parallel (multiplexing), compresses headers, and is used over TLS by browsers. HTTP/3 runs the same ideas over QUIC (UDP), which avoids head-of-line blocking at the TCP level and connects faster. You rarely change code for this: enable it in Nginx or your CDN, and Spring Boot behind the proxy still sees HTTP/1.1.

Rule: HTTPS everywhere, redirect HTTP, keep the private key private

Serve production only over HTTPS, redirect port 80 to 443, mark session cookies Secure, and never commit privkey.pem or put it in a Docker image. Use a normal (non-root) process to run the app, and let Nginx read the key.

Mistake: turning off certificate checks to "fix" an error

curl -k, verify=False in Python or a trust-all TrustManager in Java makes the error go away by removing the security. Fix the cause: wrong name, expired certificate, missing intermediate in fullchain.pem, or an unknown (self-signed) CA that must be added to the truststore.

Edge cases and errors

  • NET::ERR_CERT_DATE_INVALID / "certificate has expired" — renewal failed. Check certbot renew and that port 80 is reachable.
  • NET::ERR_CERT_COMMON_NAME_INVALID — the certificate does not cover the name you typed (for example you got a certificate for shop.example.com but visit www.shop.example.com).
  • Java: javax.net.ssl.SSLHandshakeException: PKIX path building failed — your JVM does not trust the issuer, typical with internal or self-signed CAs. Import the CA into the truststore (keytool -importcert).
  • Let's Encrypt has rate limits; test with --dry-run or the staging environment before you request many certificates.
  • Mixed content: an HTTPS page that loads http:// scripts or APIs is blocked by browsers.

Interview: "How does HTTPS work? What does a certificate prove?"

  • TLS handshake: negotiate, server sends certificate, client validates the chain, both derive a session key, then symmetric encryption.
  • You get confidentiality, integrity and authentication. A certificate binds a public key to a domain name and is signed by a trusted CA.
  • Practical: Let's Encrypt, certbot, auto-renewal every 60 days or so, TLS termination at Nginx.

Firewalls and security groups: open only the ports you need

A firewall allows or blocks traffic by port, protocol and source address; on a server you use ufw, in AWS you use security groups, and the rule is to open only what is needed (22 from your IP, 80 and 443 from anywhere, never the database).

Why a firewall

A running program that listens on a port is a door. Databases, debug ports and admin tools you forgot about are doors too. A firewall decides which doors are reachable from where. The core idea is default deny: block everything, then allow exactly what you need. Bots scan the whole internet for open 22, 3306, 5432, 6379 and 27017 all day, and databases left open with a weak or no password are a leading cause of data leaks.

ufw: the simple Ubuntu firewall

ufw (Uncomplicated Firewall) is a friendly front end for the Linux packet filter. It is installed on Ubuntu but disabled until you turn it on.

$ sudo ufw default deny incoming
$ sudo ufw default allow outgoing
$ sudo ufw allow 22/tcp
$ sudo ufw allow 80,443/tcp
$ sudo ufw enable

The order matters: allow SSH before you enable the firewall, or you lock yourself out of a remote machine. ufw allow OpenSSH also works, using an application profile.

AWS security groups

On EC2 the main firewall is the security group, attached to the instance's network interface. It lives outside the machine, so it protects even if the OS firewall is off. Key ideas:

  • Allow rules only. You cannot write a deny rule; anything not allowed is dropped.
  • Inbound and outbound rules. Each rule has a protocol, a port (or range), and a source (inbound) or destination (outbound): a CIDR, or another security group. By default all outbound traffic is allowed and no inbound traffic is.
  • Stateful. If an inbound request is allowed, the reply is allowed automatically, and the same for outbound requests and their replies. You do not need a rule for the response.
  • Reference groups. A rule can use another security group as the source: "allow 5432 from the web servers' group". It keeps working when instance IPs change.

Security groups are one layer. A network ACL is a second, stateless filter at the subnet level (rarely needed at first). Put databases in private subnets without a public IP. Module 5 covers VPCs in detail.

Rule: never open a database to 0.0.0.0/0

Ports 3306 (MySQL), 5432 (PostgreSQL), 6379 (Redis), 27017 (MongoDB) and 9092 (Kafka) must not be reachable from the whole internet. Allow them only from the app's security group or private subnet; for admin work use an SSH tunnel (Module 1). Allow SSH only from your own IP.

Mistake: "All traffic from anywhere" while testing

Opening everything to find a connection problem usually stays in place for months. Open one port to the smallest source that works. If your home IP changes (most ISPs rotate it), update the rule instead of widening it to 0.0.0.0/0; the AWS console offers a "My IP" source for this.

Edge cases

  • Two firewalls can stack: the security group and ufw. A request must pass both. On Amazon Linux/Ubuntu AMIs the OS firewall is usually off by default, but check.
  • Docker publishes ports by writing its own packet-filter rules and can bypass ufw. A container started with -p 5432:5432 may be reachable even if ufw says "deny". Bind to localhost (-p 127.0.0.1:5432:5432) or rely on the security group.
  • Symptom: a blocked port by a firewall that drops packets gives a timeout; a closed port with no listener gives connection refused.

Interview: "How do you secure an EC2 instance's network access?"

  • Security group with default deny: 22 only from my IP, 80 and 443 from anywhere, database only from the app group; stateful rules; no public IP for private resources.
  • Add OS-level ufw, key-only SSH, regular updates and least privilege.

Network debugging tools and the "my app is not reachable" checklist

Test one hop at a time: is the app running, on which address and port, can the machine reach it locally, then check the firewall, the security group, DNS and HTTPS — with ss, curl -v, nc, ping and dig.

The tools

ToolQuestion it answers
ip a (Windows ipconfig)What IP addresses does this machine have?
ping hostIs the host reachable at all, and how fast? (ICMP echo; may be blocked by a firewall, so no reply does not always mean down)
traceroute host (Windows tracert)Which routers does the path pass; where does it stop?
dig / nslookupWhat IP does this name resolve to?
nc -zv host portIs this TCP port open from here? (nc = netcat; telnet host port also works)
curl -v URLWhat does the HTTP(S) conversation look like: DNS, connect, TLS, status, headers?
ss -tulpnWhich process listens on which address and port on this machine?

The checklist

Work from the server outward. Do not skip steps; each one removes a whole class of causes.

  1. Is the app running? systemctl status billing and journalctl -u billing -n 50 (crashes, "port in use", database errors). In Docker: docker ps and docker logs.
  2. On which address and port is it listening? sudo ss -tulpn | grep 8080. 127.0.0.1:8080 is local only; *:8080 or 0.0.0.0:8080 accepts outside connections. Is the port the one you expect (server.port)?
  3. Does it answer locally? curl -i http://localhost:8080/actuator/health on the server. If this fails, the problem is the app, not the network.
  4. Is the reverse proxy fine? sudo nginx -t, systemctl status nginx, tail /var/log/nginx/error.log. Does curl -i http://localhost reach the app through Nginx?
  5. OS firewall? sudo ufw status. Are 80/443 (or the port you use) allowed?
  6. Cloud firewall? The security group's inbound rules: right port, right protocol (TCP), right source (is your IP still the same?). Is the instance in a subnet with an Internet Gateway route, and does it have a public IP?
  7. Reachable from outside? From your laptop: nc -zv IP 443 and curl -v http://IP/. Use the IP to skip DNS.
  8. DNS? dig +short shop.example.com returns the right IP? Wait for the TTL after a change, or test with dig @8.8.8.8.
  9. HTTPS? curl -vI https://shop.example.com: valid certificate, right name, not expired? Does port 443 listen in Nginx (ss -tlnp | grep 443)?
  10. The application layer. If a response comes back, read the status code and headers: CORS, wrong context path, authentication, or a 4xx from Spring Security. That is no longer a network problem.

Tip: bisect the path

Test from inside out: app on localhost:8080, then Nginx on localhost:80, then the public IP from another machine, then the domain name, then HTTPS. The first step that fails is where the fault is.

Mistake: trusting ping

Many cloud networks block ICMP, so ping can fail while the website works, and it can succeed while the app is down (the machine is up, the app is not). Test the real thing: the TCP port with nc or the HTTP response with curl.

Edge cases

  • It works over the IP but not by name — DNS. It works by name from one network but not another — a stale cache, or an IPv6 (AAAA) record that points nowhere.
  • The app answers on the private IP from inside the VPC but not from the internet — a security group, route table or missing public IP.
  • Everything works from your laptop but a colleague in the office fails — a corporate proxy or firewall blocking unusual ports (use 80/443).
  • Intermittent failures with a load balancer — one of several backends is down; check health checks.

Interview: "Users say the site is down. How do you troubleshoot?"

  • Reproduce with curl -v, read the failure (DNS, timeout, refused, TLS, 5xx), then follow the checklist from the server outward: process, listening address, local curl, proxy, firewall, security group, DNS, HTTPS.
  • Say what you read in the logs and that you change one thing at a time.

Deployment strategies: recreate, rolling, blue-green, canary and rollback

A deployment strategy decides how the new version replaces the old one: recreate (stop, then start), rolling (replace one by one), blue-green (switch between two full copies) or canary (send a small share of traffic first); whatever you pick, keep the previous image tag so you can go back fast.

The four strategies

StrategyHow it worksDowntimeExtra capacity
RecreateStop the old version, start the new oneYes, seconds to minutesNone
RollingReplace instances a few at a time; old and new run together brieflyNone if done rightA little
Blue-greenRun the new version (green) beside the old (blue), test it, then switch all trafficNoneA full second copy
CanarySend a small percentage of users to the new version, watch metrics, then increaseNoneA little
  • Recreate is what docker compose up -d does on a single server. It is simple and fine for a small app where a few seconds of downtime at a quiet hour is acceptable. It is also the only option when two versions cannot run at the same time (for example an incompatible schema change).
  • Rolling is the default in Kubernetes Deployments, ECS services and Elastic Beanstalk. With a load balancer in front, each instance is taken out of rotation, updated, health-checked and put back. During the update both versions serve users, so they must be compatible with each other and with the database.
  • Blue-green gives instant rollback: if green misbehaves, switch the load balancer or the Nginx upstream back to blue. It costs double capacity during the switch and needs care with shared databases.
  • Canary limits the damage of a bad release to a few users and gives real traffic evidence. It needs a router that can split traffic and good metrics (Module 6). A related tool is a feature flag: code ships dark and is switched on for chosen users without a new deployment.

Zero downtime on one server (a blue-green sketch)

With one EC2 server you can still avoid downtime by starting the new container on a second port, checking it, and switching Nginx. Assume Nginx proxies to an upstream defined in a small file:

upstream shop_backend {
    server 127.0.0.1:8080;      # blue is live; green would be 8081
}
$ docker run -d --name shop-green --env-file /opt/shop/.env \
    -p 127.0.0.1:8081:8080 ghcr.io/asha/shop-api:sha-9b1d4e7
$ curl -fsS http://127.0.0.1:8081/actuator/health          # wait until UP
$ sudo sed -i 's/127.0.0.1:8080/127.0.0.1:8081/' /etc/nginx/conf.d/shop-upstream.conf
$ sudo nginx -t && sudo systemctl reload nginx          # reload does not drop connections
$ docker stop shop-blue                                     # keep it for a while for rollback

In the site config use proxy_pass http://shop_backend;. This is a manual teaching example; in a real team a load balancer with target groups, or Kubernetes, automates the same idea.

Zero-downtime basics in Spring Boot

  • Readiness: traffic should reach an instance only after it started (health checks and probes, Module 6).
  • Graceful shutdown: when the old instance is told to stop, finish in-flight requests first. Spring Boot supports this:
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s
  • Connection draining: the load balancer stops sending new requests to an instance being removed and lets existing ones finish (a "deregistration delay").
  • Backward-compatible database changes (the expand and contract pattern): release 1 adds a nullable column; release 2 starts using it; a later release removes the old column. Then old and new code both work against the same schema, which makes rolling updates and rollbacks safe. Renaming or dropping a column in a single step breaks the version that is still running.

Rollback

Rollback should be boring and fast. Rules that make it so:

  1. Tag images immutably (sha-9b1d4e7, 1.4.2); never deploy latest.
  2. Record the previously running tag on every deployment (the runbook's .previous_tag file).
  3. Keep several old images in the registry and on the server (careful with docker image prune -a).
  4. Make the rollback a command or a button (a script, a workflow_dispatch run, a platform "redeploy previous").
  5. Keep database migrations backward compatible. If a release changed data irreversibly, an image rollback alone will not help; that is why the migration discipline matters.
  6. Practise it before you need it.

Mistakes

  • Dropping or renaming a column in the same release that stops using it.
  • Calling a deployment successful because the container started, without a health check.
  • No graceful shutdown: users see errors for requests that were in progress.
  • Deploying a big release on Friday evening with no rollback plan.

In real projects

Most teams use rolling updates by default, blue-green for risky releases, and canary or feature flags for large user bases. A deployment typically has a health-check gate, a smoke test, and dashboards watched for the first minutes after release.

Interview: "Blue-green vs canary vs rolling?"

  • Rolling: gradual replacement, cheap, mixed versions for a while. Blue-green: two full environments, instant switch and rollback, double cost. Canary: small traffic slice with metrics before full rollout.
  • Mention database compatibility and health checks.

Production deployment checklist

Before you call a deployment production-ready, check security, configuration, data, runtime, networking, observability, release process and cost, using this list as a final pass.

How to use it

Go through the list once before the first launch and again before a major change. Every line is a small failure that has hurt someone. A "no" is not always wrong; it should be a decision you can explain.

Security

  • Root account has MFA, and no root access keys exist. Daily work uses a non-root identity.
  • SSH is limited to your IP (or replaced by Session Manager); password login is off; keys are not shared.
  • Only ports 80 and 443 are public. The app port and the database port are private.
  • The database is not publicly accessible. The app uses its own limited database user.
  • No secrets in Git, images or frontend code. The .env file has mode 600.
  • AWS access uses roles; policies name exact resources; S3 buckets block public access.
  • The OS gets security updates (unattended-upgrades or a patch routine). Images are rebuilt on newer base images regularly.
  • Swagger UI, H2 console and sensitive Actuator endpoints are off or protected in production.

Configuration

  • All environment-specific values come from environment variables or a config service, per environment.
  • The production profile is active (SPRING_PROFILES_ACTIVE=prod); ddl-auto is validate or none; migrations run through Flyway or Liquibase.
  • CORS allows exactly the real frontend origins, not * with credentials.
  • Time zone, character set and locale are set on purpose (store timestamps in UTC).

Data

  • Automated backups are on, and you have tested a restore.
  • The database has enough connections for the pool sizes times the number of instances.
  • Uploaded files live in S3 or a durable volume, not in the container's temporary disk.

Runtime

  • Memory is sized: MaxRAMPercentage is set, container limits match, and swap exists on tiny machines.
  • Restart policy is set; the app and Docker start on boot; you tested a reboot.
  • Graceful shutdown is on. Health endpoints (liveness and readiness) exist.
  • Logs go to stdout, are rotated (max-size, max-file), and the disk cannot fill silently.

Networking and domain

  • DNS records are correct; HTTPS works; HTTP redirects to HTTPS; the certificate renewal was tested with certbot renew --dry-run.
  • Nginx forwards the right headers; upload size and timeouts match your needs.
  • The Elastic IP is attached (the address survives restarts).

Observability

  • An external uptime monitor checks the public health URL and alerts you by email, Slack or Telegram.
  • You can read logs quickly; important errors are noticed without a user complaint.
  • Basic metrics (CPU, memory, disk, request errors, latency) are visible (Module 6).

Release process

  • CI runs tests on every pull request; deployment comes only from the main branch after tests pass.
  • Images carry immutable tags. The previous tag is known and rollback is rehearsed.
  • A smoke test runs after each deployment.
  • The runbook (how to deploy, roll back, and who to call) is written down and stored in the repository.

Cost

  • A budget alert exists and goes to an email you read.
  • You know what each resource costs per month (from the current pricing pages), and unused resources are deleted: stopped servers with disks, old snapshots, unattached Elastic IPs, forgotten databases.

Tip: keep the checklist in the repository

Put a DEPLOYMENT.md file next to the code with the checklist and the runbook commands. Reviewers can then check it, and a new team member can deploy on day one.

Interview: "What do you check before releasing to production?"

  • Tests and migrations are green and backward compatible; config and secrets are correct for the environment; health checks and monitoring are in place; there is a rollback plan; the deployment is done at a quiet time with a smoke test afterwards.

Interview questions — Cloud and deployment

What are IaaS, PaaS and SaaS? Give one example of each.

IaaS rents virtual infrastructure (servers, disks, networks): you manage the OS and everything above it; example EC2. PaaS rents a platform to run your code: you manage the app and its settings; examples Render, Railway, Elastic Beanstalk. SaaS is finished software you just use: Gmail, Jira, Slack. The further toward SaaS, the less you manage and the less you can change.

What is the shared-responsibility model?

The provider secures the cloud itself (buildings, hardware, virtualisation). You secure what you put in it: data, accounts and permissions, network rules, and, on EC2, the OS and application. The split changes with the service: for RDS, AWS patches the engine; for EC2, you patch the OS. Typical customer errors are public buckets, open security groups and leaked keys.

What is the difference between a region and an availability zone? How do you get high availability?

A region is a geographic area (Mumbai, ap-south-1); an availability zone is an isolated group of data centres inside it. Spread instances over at least two AZs behind a load balancer and enable Multi-AZ on the database, so a failure of one zone does not stop the app. Regions are independent, so cross-region designs cost more and are used only when needed.

What do you do first in a new AWS account?

Enable MFA on the root user and stop using it, create an IAM Identity Center or IAM user (with MFA) for daily work, grant least privilege, avoid access keys, set a budget with email alerts, and enable CloudTrail. Check the current free-tier terms instead of assuming. These steps prevent the most common incidents: leaked keys and surprise bills.

Name common surprise costs on AWS and how to avoid them.

Instances left running, EBS volumes and snapshots that remain after termination, Elastic IPs and public IPv4 addresses, NAT gateways, load balancers, data transfer, and RDS instances left on. Avoid them with budgets and alerts, tags, a cleanup routine after labs, a weekly look at the bill by service and region, and infrastructure as code so terraform destroy removes everything.

What is the difference between stopping and terminating an EC2 instance?

Stopping shuts the instance down but keeps it and its EBS volumes; you stop paying for compute but still pay for storage, and the automatic public IP changes on the next start. Terminating deletes the instance and, by default, its root volume; it cannot be undone. Data on instance-store disks is lost on stop.

How do you let only your application reach the RDS database?

Create the database with Public access off, in the same VPC as the app. In its security group add an inbound rule for port 5432 whose source is the application's security group, not an IP range. Then only instances in that group can connect. Use a dedicated database user and pass the credentials through environment variables or a secrets service.

RDS Multi-AZ vs read replica?

Multi-AZ keeps a synchronous standby in another AZ for automatic failover; it is for availability and you cannot read from the standby. A read replica is an asynchronously updated copy with its own endpoint that serves read queries to scale reads; it can lag behind. They solve different problems and can be used together.

How does an app on EC2 call S3 without storing access keys?

Create an IAM role with a least-privilege policy and attach it to the instance (through an instance profile). The AWS SDK's default credentials chain gets temporary, automatically rotated credentials from the instance metadata service. Nothing is written to disk or Git. Inside Docker you may need the metadata hop limit set to 2.

What is a presigned URL and why use it?

It is an S3 URL signed with your server's credentials that allows one operation (GET or PUT) on one object until it expires. The browser uploads or downloads directly to and from a private bucket, so large files do not pass through your server, and you do not expose credentials or make the bucket public. Keep the expiry short and generate the object key on the server.

Walk me through putting a Spring Boot app on a fresh EC2 server with HTTPS.

Launch Ubuntu with a security group (SSH from my IP, 80 and 443 open), attach an Elastic IP, SSH in, install Docker, log in to the registry and pull the tagged image, run it with Compose using an env file and a port bound to 127.0.0.1:8080, install Nginx as a reverse proxy, create a DNS A record to the Elastic IP, run certbot --nginx -d api.example.com, verify renewal with a dry run, and enable restart policies. Finish with logs, a health check, and a deploy and rollback script.

Why put Nginx in front of Spring Boot?

It terminates TLS, serves on ports 80/443 without running Java as a privileged user, redirects HTTP to HTTPS, can add compression, request size limits, caching and rate limiting, and hides the app port. It also lets you switch between app versions without changing the public address. The app then trusts the X-Forwarded-* headers (server.forward-headers-strategy).

Why does a React app on Vercel or Netlify return 404 on refresh, and how do you fix it?

Client-side routes such as /orders/42 do not exist as files; the server finds nothing and returns 404. Add a rewrite sending all unknown paths to index.html (vercel.json rewrites, or a Netlify redirect with status 200), and React Router renders the right page. Also remember that VITE_ variables are fixed at build time.

Compare recreate, rolling, blue-green and canary deployments. How do you roll back?

Recreate: stop old, start new, with downtime. Rolling: replace instances gradually behind a load balancer. Blue-green: run a full new copy and switch traffic, with instant rollback and double capacity. Canary: send a small share of traffic to the new version first. Rollback is easy when images have immutable tags, the previous tag is known, the switch is scripted, and database changes are backward compatible.

Your site works on its Elastic IP but not on the domain. What do you check?

Run dig +short name to see what DNS returns. Check the record type and host field (only api, not the full name), that it points to the Elastic IP, the TTL and cached answers, and that Nginx has a matching server_name. For HTTPS, check certbot succeeded, port 443 is open, and the certificate covers that name. If the domain is proxied by Cloudflare, check the SSL mode.

Practice — Cloud and deployment

  1. Secure the account (easy). Turn on MFA for root, create a daily-use user or Identity Center user with MFA, and create a monthly budget with email alerts. Done when: you can sign in as the new user, aws sts get-caller-identity shows it, and a test alert email arrives.
  2. Read the bill (easy). Open Bills and Cost Explorer; list the services and regions you used this week. Done when: you can say what each line is and what you will delete.
  3. First server (easy). Launch an Ubuntu EC2 instance with a security group that allows SSH only from your IP, SSH in, install Nginx, and open the default page in a browser. Done when: you can explain each security group rule, and you then terminate the instance and check it is gone in all regions.
  4. Run your container (medium). On a new instance, install Docker, pull your Spring Boot image from GHCR, and run it with Compose on 127.0.0.1:8080. Done when: curl localhost:8080/actuator/health on the server returns UP, and port 8080 is unreachable from your laptop.
  5. Proxy, DNS and HTTPS (medium). Attach an Elastic IP, configure Nginx, create an A record for api.yourdomain, and run certbot. Done when: the browser shows a valid padlock and certbot renew --dry-run passes.
  6. Managed database (medium). Create an RDS PostgreSQL instance that is not public, allow 5432 only from the EC2 security group, create a shop_app user, and connect the app through environment variables. Done when: the app starts, Flyway runs, and a connection attempt from your laptop times out.
  7. S3 uploads (medium). Create a private bucket, an IAM policy limited to it, and an instance role. Add presigned PUT and GET endpoints to Spring Boot and a small React upload form with the bucket CORS rules. Done when: you upload from the browser and view the file through a presigned link, and the object URL without a signature returns AccessDenied.
  8. Update and roll back (medium to hard). Write the deploy.sh from the runbook, deploy a new tag, then deploy a deliberately broken one (for example a missing environment variable). Done when: the script detects the unhealthy app and returns to the previous tag by itself.
  9. Deploy Project 3 (hard). Deploy the React frontend on Vercel or Netlify and Spring Boot with PostgreSQL on EC2 (or Render), under your own domain with HTTPS, with CI/CD from Module 4. Done when: Project 3 is live on a public HTTPS address, and you can explain everything that happens between git push and the new version going live (CI, tests, image build, registry, deploy, health check, DNS and TLS in the request path, and how to roll back).

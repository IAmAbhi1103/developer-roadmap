Secrets and variables in GitHub Actions, and OIDC instead of long-lived keys

Store passwords, tokens and keys as GitHub secrets (repository, environment or organization level) and read them as ${{ secrets.NAME }}; GitHub masks them in logs, but you must never echo them, forks do not receive them, and for AWS you should use OIDC to get short-lived credentials instead of stored access keys.

Secrets versus variables

A secret is encrypted configuration you must not reveal: tokens, SSH keys, passwords. A variable is plain configuration that is fine to see: a URL, a region, a Java version. Add them at Settings → Secrets and variables → Actions, or with the GitHub CLI (gh secret set SSH_HOST, gh variable set APP_URL).

LevelAvailable toUse for
RepositoryAll workflows in this repoRegistry tokens, shared test settings
EnvironmentOnly jobs that name that environment (and pass its rules)Production database URL, deploy key
OrganizationChosen repos in the organizationA token every project uses

The value is read in the workflow as ${{ secrets.NAME }} or ${{ vars.NAME }}. Environment-level values override repository-level ones with the same name, which lets staging and production use the same workflow with different credentials.

      - name: Call the API
        env:
          API_TOKEN: ${{ secrets.API_TOKEN }}     # pass through env ...
        run: curl -fsS -H "Authorization: Bearer $API_TOKEN" "${{ vars.APP_URL }}/ping"

Rules for handling secrets

  1. Never print them. GitHub masks exact secret values in logs, but masking is not perfect: if you transform a value (base64, split, URL-encode) the result is not masked. Do not echo secrets, do not run with set -x around them, and do not print environment dumps (env, printenv).
  2. Pass secrets through env and refer to $NAME in the shell, instead of pasting ${{ secrets.X }} into the script text. This avoids quoting bugs and script injection.
  3. Least privilege. Create tokens with the minimum scope (a deploy key that can only SSH as the deploy user; a registry token that can only push one repository). Prefer environment secrets for production so a feature branch cannot use them.
  4. Rotate. If a secret appears in a log, a commit or a screenshot, treat it as stolen: revoke it and create a new one.
  5. Do not commit secrets. Enable GitHub secret scanning and push protection; keep .env in .gitignore.
  6. Be careful with third-party actions. An action runs with access to the secrets you give it. Pin trusted actions to a version or commit SHA, and prefer official or well-known ones.

Pull requests from forks

For a pull request from a fork (someone else's copy of your repository), GitHub does not give the workflow your secrets and gives GITHUB_TOKEN read-only access. Otherwise any stranger could open a PR whose workflow prints your secrets. Consequences: tests that need a secret fail on fork PRs, and deploy or push steps must be restricted to pushes on your own branches (for example if: github.event_name == 'push'). Keep CI independent of secrets whenever you can; use Testcontainers and fake values for tests.

OIDC to AWS (brief)

Storing an AWS access key in GitHub secrets is a long-lived credential: if it leaks, it works until someone notices. OpenID Connect (OIDC) removes it. GitHub issues each workflow run a short-lived signed identity token; AWS is configured to trust tokens from GitHub for a specific repository (and branch or environment), and exchanges the token for temporary AWS credentials that expire in about an hour. Nothing secret is stored in GitHub.

permissions:
  id-token: write                 # lets the job request the OIDC token
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-deploy
          aws-region: ap-south-1
      - run: aws sts get-caller-identity       # shows the assumed role

On the AWS side you create an IAM identity provider for token.actions.githubusercontent.com and an IAM role whose trust policy allows only your repository (and, better, only the main branch or the production environment). Follow the current instructions in the GitHub docs ("Configuring OpenID Connect in Amazon Web Services") and the README of the AWS action for the exact trust policy. The same idea works for Google Cloud and Azure.

Mistakes with secrets

  • A multi-line secret (SSH key) pasted with lost line breaks, or missing the final newline: the key fails with invalid format. Paste the whole file including the BEGIN and END lines.
  • Using a secret in a step's if: condition: secrets are not available there; copy it to an env variable first.
  • Giving the whole organisation's admin token to a workflow "to make it work".
  • Checking in a workflow that echoes ${{ secrets.X }} "just to debug".

Edge cases

  • Secrets are limited in size (a few tens of KB) and cannot be read back in the UI after saving; you can only overwrite them.
  • Dependabot-triggered runs use a separate set of secrets (Dependabot secrets), not the Actions ones.
  • Workflows triggered by pull_request_target run with secrets even for forks; combined with checking out the PR's code this is a known attack path. Avoid it unless you follow GitHub's hardening guide.

Interview: "How do you manage secrets in CI/CD?"

  • GitHub secrets at the right level (environment for production), passed via env, never echoed; masked in logs; not available to fork PRs.
  • Prefer OIDC and short-lived credentials over stored cloud keys; rotate on leak; scan for secrets.

Branch protection, required checks and the status badge

A branch protection rule (or ruleset) on main requires a pull request, passing status checks and reviews before merging and blocks force pushes — so broken code cannot reach main; add a workflow status badge to the README to show the build state.

Why protect main

CI is only useful if its result matters. Without protection, anyone can push straight to main, skip the tests, or force-push and rewrite history. A branch protection rule makes the rules enforceable by GitHub itself, for the whole team (including admins if you choose).

Setting it up

  1. Open the repository → Settings → Branches → Add branch protection rule (or Rules → Rulesets → new branch ruleset). Target the branch main.
  2. Tick Require a pull request before merging; set Required approvals to 1 or more. Optionally dismiss stale approvals when new commits arrive and require review from code owners (a CODEOWNERS file).
  3. Tick Require status checks to pass before merging and choose the checks by their job name (for example Backend (Maven) and Frontend (React)). A check appears in the list only after it has run at least once in the repository.
  4. Tick Require branches to be up to date before merging, so the checks ran against the latest main, not an old base.
  5. Tick Require conversation resolution, Require linear history if the team uses squash or rebase merges, and keep Do not allow force pushes and Do not allow deletions on.
  6. Consider Do not allow bypassing the above settings so admins follow the rules too.
SettingWhat it prevents

Branch protection rules are the classic feature; rulesets are the newer, more flexible system (several rulesets can apply, they can target many branches or tags by pattern, and they can be tested in "evaluate" mode first). The checkboxes are similar in both. Some features, such as protection on private repositories, depend on your GitHub plan.

What the developer sees

On a pull request, the merge button stays grey with messages like Required statuses must pass before merging until the CI jobs are green and the review is approved. If CI fails, the author pushes a fix to the same branch and the checks run again. Typical flow: branch → PR → CI runs → review → merge. See Git · Module 3 for the pull-request workflow.

The CI status badge

A badge is a small image in the README that shows whether the latest run on a branch passed. GitHub generates it for each workflow: Actions tab → the workflow → ⋯ → Create status badge, or build the URL yourself:

# Shop API

[badge]: https://github.com/asha/shop-api/actions/workflows/ci.yml/badge.svg?branch=main

The pattern is https://github.com/OWNER/REPO/actions/workflows/FILE.yml/badge.svg?branch=main, wrapped in a link to the workflow page. Replace OWNER, REPO and FILE.yml with your own. A green badge in a project README tells recruiters at a glance that your code builds and tests run; a red one tells them to fix it.

Convention: protect main from day one, even on solo projects

Working through pull requests on your own repositories builds the habit, produces a visible history of checks, and lets you show the workflow to interviewers. Set the rule once CI has run.

Mistakes

  • Requiring a check by a name that is never reported (renamed job, or path-filtered workflow that did not run): the PR waits forever. Select the check from the list and keep job names stable.
  • Leaving admins able to bypass the rule, then bypassing it "just this once" before a demo.
  • Requiring approvals on a one-person repository: you can never merge. Use 0 approvals and keep the status checks.

Edge cases

  • A required check that is skipped (because of an if condition) counts as passed for a job, but a workflow that never starts leaves the check pending.
  • Merge queues (a GitHub feature for busy repositories) re-run checks on the combined result before merging; the workflow then also needs the merge_group trigger.
  • Rules apply to merges done in the UI and to pushes from Git; the deployment workflow's own commits (like version bumps) must go through a PR or be allowed explicitly.

Interview: "How do you make sure broken code never reaches main?"

  • Branch protection or rulesets: PR required, required status checks (the CI jobs), up-to-date branch, at least one review, no force pushes.
  • Developers work on feature branches; CI runs on the PR; merging is blocked until green.

Jenkins, the Jenkinsfile, and other CI/CD tools

Jenkins is a self-hosted automation server (controller plus agents, extended with plugins) whose pipelines are written in a Jenkinsfile; many Indian companies still run it, so you should be able to read a declarative Jenkinsfile even if you use GitHub Actions yourself.

What Jenkins is

Jenkins is an open-source automation server written in Java, first released in 2011 (it grew out of the Hudson project). You install and run it yourself — on a VM, in Docker or on Kubernetes — and connect it to your Git repository. It was the standard CI server of the 2010s, so large enterprises, banks and service companies have years of Jenkins jobs and pipelines in place. That is why interviews in India still ask about it.

Controller
The main Jenkins server: web UI, configuration, job scheduling, plugin management. (Older docs call it the "master".)
Agent
A machine (or container) that actually runs build steps; the controller sends work to agents (also called nodes). It lets one Jenkins serve many projects and platforms.
Plugin
Extension that adds features: Git, Pipeline, Docker, credentials, SonarQube, Slack. Jenkins has a very large plugin ecosystem — a strength, and a maintenance burden, because plugins need updates.
Job / pipeline
A unit of automation. A Pipeline job is defined as code.
Jenkinsfile
A text file in the repository root that defines the pipeline (Pipeline as Code).
Credentials
Jenkins' encrypted store for passwords, tokens and SSH keys, referenced by id.

A declarative Jenkinsfile

Jenkins pipelines are written in Groovy, in two styles: declarative (structured, recommended) and scripted (free-form Groovy). Here is a declarative pipeline with the stages you know: checkout, build, test, Docker build and push, deploy.

pipeline {
    agent any                               // run on any available agent

    tools {
        maven 'Maven-3.9'                   // names configured in Jenkins -> Tools
        jdk   'JDK-21'
    }

    environment {
        IMAGE = "registry.example.com/shop-api"
        TAG   = "${env.GIT_COMMIT.take(7)}"
    }

    options {
        timeout(time: 20, unit: 'MINUTES')
        buildDiscarder(logRotator(numToKeepStr: '20'))
    }

    stages {
        stage('Checkout') {
            steps {
                checkout scm                // the repository that holds this Jenkinsfile
            }
        }
        stage('Build') {
            steps {
                sh 'mvn -B -ntp clean package -DskipTests'
            }
        }
        stage('Test') {
            steps {
                sh 'mvn -B -ntp test'
            }
            post {
                always {
                    junit 'target/surefire-reports/*.xml'   // test results in the UI
                }
            }
        }
        stage('Docker build and push') {
            when { branch 'main' }
            steps {
                withCredentials([usernamePassword(credentialsId: 'registry-creds',
                        usernameVariable: 'REG_USER', passwordVariable: 'REG_PASS')]) {
                    sh '''
                        docker build -t $IMAGE:$TAG .
                        echo "$REG_PASS" | docker login registry.example.com \
                          -u "$REG_USER" --password-stdin
                        docker push $IMAGE:$TAG
                    '''
                }
            }
        }
        stage('Deploy') {
            when { branch 'main' }
            steps {
                sshagent(credentials: ['deploy-server-key']) {
                    sh '''
                        ssh -o StrictHostKeyChecking=yes deploy@server \
                          "cd /opt/shop && IMAGE_TAG=$TAG docker compose up -d api"
                    '''
                }
            }
        }
    }

    post {
        success { echo 'Build and deploy finished' }
        failure { echo 'Pipeline failed - notify the team' }   // mail or Slack step in real life
    }
}
pipeline, agent, stages, stage, steps
The fixed skeleton of the declarative syntax.
tools / environment
Select configured JDK and Maven; define variables for all stages.
when { branch 'main' }
Run a stage only for some branches (needs a multibranch pipeline).
post { always / success / failure }
Actions after the pipeline or a stage, like cleanup, reports and notifications.
withCredentials / sshagent
Inject stored credentials for a block of steps; the values are masked in the console log.
sh
Run a shell command on the agent; the same mvn and docker commands you already know.

Jenkins creates the pipeline job from the repository: a Multibranch Pipeline scans the repository, and builds every branch and pull request that has a Jenkinsfile. A GitHub webhook calls Jenkins on each push so the build starts immediately instead of polling.

In real projects

At a service company you may inherit a Jenkins server with dozens of pipelines: read the Jenkinsfile, open the console output of a failed build, check the credentials and agents. Many of these teams are slowly migrating to GitHub Actions or GitLab CI because Jenkins needs ongoing care (plugin updates, security patches, agent capacity).

Edge cases and problems

  • An outdated plugin or an exposed Jenkins UI is a frequent security problem; keep Jenkins updated, put it behind HTTPS and authentication, and restrict who can configure jobs.
  • A build that works on one agent and fails on another usually depends on tools installed only on that machine; use Docker agents or the tools block to make it reproducible.
  • "Scripted" pipelines use node { ... } blocks and plain Groovy; they look different from the declarative form but do the same job.

Interview: "What is Jenkins? Jenkins versus GitHub Actions?"

  • A self-hosted automation server: controller schedules, agents execute, plugins extend; pipelines as code in a declarative Jenkinsfile with stages and steps.
  • Jenkins: maximum control, more maintenance. Actions: hosted, YAML, tight GitHub integration, minimal setup. The concepts are the same.

CI/CD best practices

Keep pipelines fast, fail early, cache dependencies, keep main green, make small pull requests, build reproducibly, and use the same commands locally and in CI.

The practices

  1. Fast feedback. Aim for CI under about 10 minutes. Slow pipelines make people stop waiting, batch their changes and ignore failures. Measure the run time and attack the slowest step.
  2. Fail fast. Put the cheapest, most likely-to-fail checks first (compile, lint, unit tests) and the slow ones (integration tests, image build, scans) after them or in parallel jobs. Use needs so expensive jobs do not run when cheap ones failed.
  3. Cache dependencies and layers. cache: maven or cache: npm, and Docker layer cache with type=gha. Order the Dockerfile so dependency layers are reused.
  4. Keep main green. Protect the branch; require passing checks; fix or revert a broken main immediately; do not merge on red.
  5. Small pull requests. A 100-line PR is reviewed in minutes and rarely breaks the build; a 3,000-line PR hides bugs and conflicts. Merge often.
  6. Reproducible builds. Pin tool versions (Maven wrapper, Java 21, locked package-lock.json with npm ci, tagged base images), avoid "latest", and build the artifact once and promote the same one through environments.
  7. Same commands locally and in CI. The workflow should call ./mvnw verify, npm ci && npm run build or a script in the repository. Developers can then reproduce any CI failure on their laptop.
  8. Test reliably. Remove flaky tests or fix their root cause (time, ordering, shared state, sleeps). Prefer Testcontainers to a shared test database.
  9. Least privilege and safe secrets. Minimal permissions, environment secrets for production, OIDC instead of stored keys, scanning for leaked secrets.
  10. Make failures easy to read. Upload test reports, name jobs and steps clearly, set timeouts, and notify the team (GitHub emails the PR author; add Slack if the team uses it).
  11. Deploy small and often, with a way back. Immutable image tags, health checks and smoke tests after deploy, a manual rollback workflow, and backward-compatible database migrations.
  12. Keep workflows maintainable. Reuse with reusable workflows or composite actions, let Dependabot update action versions, and delete old branches and artifacts.

Mistake: ignoring a flaky red build

"Just re-run it" teaches the team that red does not mean broken. Then a real failure is merged. Track flaky tests, fix them, or move them out of the required path.

Tip: pin actions and let Dependabot update them

Add .github/dependabot.yml with the github-actions ecosystem (and maven, npm, docker) so version bumps arrive as pull requests that your CI checks. Look at each action's README for the latest major when you write a workflow by hand.

Interview: "How would you improve a slow, unreliable pipeline?"

  • Measure; cache Maven/npm and Docker layers; parallelise jobs; run cheap checks first; trim the build context; use path filters carefully.
  • Fix flaky tests, pin versions, add timeouts and good reports, keep main protected and green.

Interview questions — CI/CD with GitHub Actions

What is CI/CD? Explain CI, continuous delivery and continuous deployment.

CI builds and tests every change automatically on a clean machine so the main branch always works. Continuous delivery also produces a release-ready artifact and deploys it to staging; production release is a manual approval. Continuous deployment sends every green change to production with no manual step. Together they give fast feedback, small releases and repeatable deployments.

Describe the structure of a GitHub Actions workflow.

A YAML file in .github/workflows. on lists the triggering events; jobs contains named jobs, each with runs-on (the runner) and steps. A step is either run (a shell command) or uses (a reusable action with with inputs). Jobs run in parallel unless ordered with needs; each runs on its own fresh runner.

GitHub-hosted versus self-hosted runners?

Hosted runners are fresh VMs managed by GitHub (ubuntu-latest): no maintenance, clean every time, but limited resources and no access to your private network. Self-hosted runners are your own machines running the runner agent: custom hardware, private network access and no per-minute fee, but you must secure, update and clean them, and never use them for untrusted fork PRs on public repositories.

How do jobs share data, and how do you control their order?

needs orders jobs and skips a job if a dependency failed. Because each job has its own machine, files are shared with artifacts (upload-artifact, download-artifact), small values with job outputs, and built images through a registry.

What triggers can you use? How do you run CI only for pull requests and main?

on: push: branches: [main] and pull_request: branches: [main]. Other events: workflow_dispatch (manual), schedule (cron in UTC), tag pushes and releases, workflow_call for reusable workflows. Filters paths, branches and tags narrow when it runs.

How do you speed up a Maven build in GitHub Actions?

Use cache: maven in actions/setup-java (keyed on the POMs), run with -B -ntp, run unit and integration tests in parallel jobs, cancel outdated runs with a concurrency group, and avoid building twice. Docker layer caching with type=gha speeds up the image build.

How do you handle secrets in GitHub Actions? What about pull requests from forks?

Store them as repository, environment or organization secrets and read ${{ secrets.NAME }}, passing them through env. They are masked in logs but never echoed. Forks get no secrets and a read-only token, so deploy and push steps must not run for them. Use environment secrets with required reviewers for production, and OIDC for cloud access.

What is OIDC in GitHub Actions and why is it better than stored AWS keys?

GitHub issues each run a short-lived signed token (needs permissions: id-token: write). AWS trusts GitHub as an identity provider and, for a role limited to your repository or branch, exchanges the token for temporary credentials. No long-lived access key sits in GitHub, so there is nothing to leak or rotate.

How do you build and push a Docker image from a workflow?

After tests: docker/setup-buildx-action, docker/login-action (GHCR using GITHUB_TOKEN with packages: write, or Docker Hub with a token secret), docker/metadata-action for tags (git SHA, semver), and docker/build-push-action with push: true and the GHA cache. Deploy by the SHA tag, not latest.

How do you deploy automatically to your own server?

A deploy job (after tests and image push, on main only) connects over SSH with a dedicated key stored as a secret and a pinned known_hosts, then runs IMAGE_TAG=… docker compose pull && docker compose up -d on the server and finishes with a health check. Alternatively call a platform deploy hook URL (Render) or its CLI.

What are GitHub environments and how do they help?

Named deployment targets (staging, production) with their own secrets and protection rules: required reviewers, wait timers, and allowed branches. A job with environment: production pauses for approval and is the only one that can read the production secrets. They also record deployment history.

How do you roll back a bad deployment?

Because every image has an immutable tag, redeploy the previous tag using a manual workflow_dispatch workflow that takes the tag as input, or revert the commit and let the pipeline redeploy. Keep database migrations backward-compatible so the old version still works with the new schema.

How do you stop broken code from being merged into main?

Branch protection rules or rulesets on main: require a pull request, required status checks (the CI jobs), up-to-date branches and at least one review; disallow force pushes and deletion. The merge button stays disabled until checks pass. Add a CI badge to the README for visibility.

What is Jenkins, and how does it differ from GitHub Actions?

Jenkins is a self-hosted automation server: a controller schedules builds on agents and plugins add features; pipelines are Groovy Jenkinsfiles with stages and steps. You maintain the server, plugins and security. GitHub Actions is hosted, YAML-based and integrated with GitHub, with almost no setup. Concepts (trigger, stages, credentials, artifacts) are the same.

Tests pass on your laptop but fail in CI. What do you check?

Java version and OS differences (Linux is case-sensitive), time zone (runner is UTC), missing services or environment variables, tests depending on order or on files that exist only locally, line endings, and flaky timing. Download the test report artifact, read the first failure, and reproduce with the exact CI command and Java version.

Practice — CI/CD with GitHub Actions

  1. Hello workflow. In a test repository add .github/workflows/hello.yml that prints the commit SHA, branch name and the Java version. Push and read the run in the Actions tab. Done when you can point to the event, job, step and runner in the log.
  2. CI on every push and PR. In Project 2 add ci.yml that runs on push to main and on pull requests: checkout, Temurin 21 with Maven cache, ./mvnw -B verify (this runs mvn test and more), and upload the surefire reports as an artifact. Done when a pull request shows a green check, and a deliberately broken test makes it red with a downloadable report.
  3. Make it faster. Compare the run time of the first and second runs to see the Maven cache work. Add a concurrency group and timeout-minutes. Done when a push cancels the older run on the same branch.
  4. Test on two Java versions and add the frontend. Add a matrix for Java 17 and 21 (if your code supports both), and a separate frontend job with npm ci and npm run build. Done when both jobs run in parallel.
  5. Protect main and add the badge. Create a branch protection rule (or ruleset) that requires a pull request and your CI checks and blocks force pushes. Add the CI status badge to the top of the README. Done when you cannot push to main directly, a failing PR cannot be merged, and the badge shows the state.
  6. Dockerize and publish. Add the multi-stage Dockerfile (Module 3) and a job that builds and pushes the image to GHCR on pushes to main, tagged with the short SHA. Done when the package appears under your repository's Packages and docker pull ghcr.io/you/app:sha-… works.
  7. CD on merge to main. Prepare a server (an EC2 instance from Module 1/5 or any VPS) with Docker and the production compose.yaml. Create a dedicated SSH key, store the secrets, add a deploy job in the production environment that pulls the new tag, runs docker compose up -d, and ends with a smoke test. Done when merging a pull request deploys the new version without you touching the server.
  8. Approval and rollback. Add a required reviewer to the production environment, and write a workflow_dispatch workflow that deploys a given image tag. Deploy a "bad" change, then roll back to the previous tag. Done when you can restore the previous version in under five minutes.
  9. Document it. In the README add the CI badge and a "Deployment" section: how the pipeline works (a small diagram or list), the secrets and variables it needs (names only), how to roll back, and how to run the same steps locally. Done when a stranger could set up the pipeline from your README.
  10. Read a Jenkinsfile (roadmap goal). Translate your GitHub Actions pipeline into a declarative Jenkinsfile on paper (stages: checkout, build, test, docker build, deploy). Optionally run Jenkins in Docker and execute it. Done when you can explain every GitHub Actions concept's Jenkins equivalent, and a push to main in your own project runs your tests and deploys automatically.

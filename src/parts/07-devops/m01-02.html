Processes: ps, top, signals, kill and background jobs

A process is a running program with a PID; list them with ps aux or top, stop them politely with kill (signal 15) and only use kill -9 as a last resort.

What a process is

When you run java -jar app.jar, Linux starts a process: your program loaded in memory, with its own PID (process id), an owner, and a parent process. Your shell is a process too, and it is the parent of every command you run from it. The very first process is systemd (PID 1), which starts the services of the machine. For the theory (scheduling, memory, threads) see CS Fundamentals · Module 1.

$ ps aux | head -3

$ ps aux | grep billing
billing 4120  3.1 12.5 3456788 502340 ?  Sl   10:00  1:12 /usr/bin/java -jar billing.jar
ubuntu  4388  0.0  0.0   9032   720 pts/0 S+  10:20  0:00 grep --color=auto billing

Columns: USER owner; PID; %CPU and %MEM; RSS real memory in KB (here about 490 MB); STAT state (S sleeping, R running, Z zombie, l multi-threaded); COMMAND. Note that the grep itself shows up in its own result. Use pgrep -f to avoid this, or ps aux | grep [b]illing. ps aux uses BSD-style options (no dash) and shows all users' processes.

Signals: asking a process to stop

A signal is a small message the kernel delivers to a process. kill does not necessarily "kill": it sends a signal, and by default it sends SIGTERM.

SignalNumberMeaningCan the app handle it?
SIGTERM15"Please shut down" (default)Yes: cleanup, close connections
SIGINT2Interrupt; what Ctrl+C sendsYes
SIGKILL9"Die now"; the kernel ends itNo: cannot be caught
SIGHUP1Terminal closed; some daemons reload configYes
 
$ kill 4120
$ ps -p 4120
    PID TTY          TIME CMD
$ kill -9 4120
$ pkill -f billing.jar
$ killall nginx

Always try kill -15 (same as plain kill) first. A Spring Boot app handles SIGTERM by running its shutdown hooks: it stops accepting requests, finishes work in progress and closes its database pool. kill -9 skips all of that and can leave half-written files or open transactions. Use it only when the process ignores SIGTERM for a long time. A process that exited after SIGTERM reports exit code 143 (128 + 15); after SIGKILL, 137 (128 + 9). Both numbers show up in Docker and Kubernetes too.

pkill -f pattern matches the full command line; killall name matches the program name. Check with pgrep -af pattern first so you do not kill the wrong thing.

Background jobs

A command normally owns the terminal until it ends. You can move work to the background:

$ java -jar billing.jar &
[1] 4120
$ jobs
[1]+  Running                 java -jar billing.jar &
$ fg %1
java -jar billing.jar
^Z
[1]+  Stopped                 java -jar billing.jar
$ bg %1
[1]+ java -jar billing.jar &
$ nohup java -jar billing.jar > app.log 2>&1 &
[1] 4150
  • cmd & starts in the background. jobs lists this shell's jobs.
  • Ctrl+Z pauses the foreground job; bg resumes it in the background, fg brings it back.
  • When you close the terminal or the SSH session, the shell sends SIGHUP to its jobs and they die. nohup ("no hang up") makes the command ignore SIGHUP so it survives logout. Output goes to nohup.out unless you redirect it as shown.

Convention: nohup is for quick tests, systemd is for real services

A nohup process does not restart after a crash or a reboot, has no standard log handling and is hard to manage. For anything that must stay up, write a service unit (next article). tmux is another useful tool: a session that keeps running after you disconnect.

Mistake: kill -9 as the first move

Reaching for kill -9 every time means your app never runs its shutdown hooks. You may see lost messages, locked rows or corrupted files. Try kill, wait 10-30 seconds, check with ps, and only then escalate.

Edge cases

  • kill: (4120) - Operation not permitted — the process belongs to another user. Use sudo kill.
  • A zombie (Z) process has already exited but its parent has not collected its status. You cannot kill it; fix or restart the parent.
  • A process in state D (uninterruptible sleep, usually stuck on disk or NFS) ignores even kill -9 until the I/O returns.
  • The JVM may be killed by the kernel's OOM killer when the machine runs out of memory. The process just disappears; look for "Out of memory: Killed process" with dmesg or journalctl -k.

Interview: "Difference between kill -15 and kill -9?"

  • 15 (SIGTERM) asks the process to stop and lets it clean up; 9 (SIGKILL) cannot be caught or ignored, the kernel removes the process immediately.
  • Use 15 first; 9 only for a hung process. Exit codes 143 and 137.
  • Bonus: how nohup and systemd keep a process alive after logout.

systemd: running a Spring Boot JAR as a service

systemd starts services at boot, restarts them when they crash and collects their logs; you describe your app in a small unit file and control it with systemctl and journalctl.

What systemd does

systemd is the service manager on Ubuntu, Debian, Amazon Linux and RHEL. It is PID 1. A unit is something it manages; the most common is a service (a long-running program). For your Spring Boot JAR, systemd gives you what nohup cannot:

  • Start at boot, and start after the network is up.
  • Restart automatically after a crash.
  • Run as a limited user, with environment variables and a working directory.
  • Capture everything the app prints (stdout and stderr) in the journal.
  • A single, standard interface: start, stop, status.

systemctl commands

CommandWhat it does
sudo systemctl start billingStart now
sudo systemctl stop billingStop now (sends SIGTERM)
sudo systemctl restart billingStop then start
systemctl status billingState, PID, last log lines
sudo systemctl enable billingStart automatically at boot
sudo systemctl enable --now billingEnable and start in one step
sudo systemctl disable billingDo not start at boot
sudo systemctl daemon-reloadRe-read unit files after you edit them
systemctl is-active billingPrints active or inactive

start and enable are different: start affects the current boot, enable affects future boots. You usually want both.

A complete unit file for a Spring Boot JAR

First prepare a user, a folder and the files:

$ sudo adduser --system --group --no-create-home billing
$ sudo mkdir -p /opt/billing /etc/billing
$ sudo cp target/billing-1.0.0.jar /opt/billing/billing.jar
$ sudo chown -R billing:billing /opt/billing
$ sudo nano /etc/billing/billing.env
$ sudo chown root:billing /etc/billing/billing.env
$ sudo chmod 640 /etc/billing/billing.env

The environment file holds secrets, one KEY=value per line, no export:

SPRING_PROFILES_ACTIVE=prod
SERVER_PORT=8080
SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/billing
SPRING_DATASOURCE_USERNAME=billing
SPRING_DATASOURCE_PASSWORD=change-me

Now the unit file, created with sudo nano /etc/systemd/system/billing.service:

[Unit]
Description=Billing service (Spring Boot)
After=network.target

[Service]
Type=simple
User=billing
Group=billing
WorkingDirectory=/opt/billing
EnvironmentFile=/etc/billing/billing.env
ExecStart=/usr/bin/java -Xms256m -Xmx512m -jar /opt/billing/billing.jar
SuccessExitStatus=143
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
SyslogIdentifier=billing

[Install]
WantedBy=multi-user.target
After=network.target
Start this service after basic networking is up.
User / Group
Run as the unprivileged billing account, not root.
WorkingDirectory
The folder the process starts in; relative paths like ./config are resolved here.
EnvironmentFile
Loads variables from a file, so passwords stay out of the unit file and out of Git.
ExecStart
The command. Use full paths: systemd does not use your shell's PATH. Check with which java. Heap options go before -jar.
SuccessExitStatus=143
A JVM stopped by SIGTERM exits with 143. This tells systemd that is a normal stop, not a failure.
Restart=on-failure, RestartSec=5
Restart after a crash or non-success exit, waiting five seconds. Restart=always also restarts after a clean exit.
WantedBy=multi-user.target
What enable hooks into: start in normal multi-user boot.
$ sudo systemctl daemon-reload
$ sudo systemctl enable --now billing

$ systemctl status billing

Reading logs with journalctl

Anything your app writes to the console goes to the journal. Read it with journalctl:

$ journalctl -u billing -f
$ journalctl -u billing -n 100 --no-pager
$ journalctl -u billing --since "1 hour ago"
$ journalctl -u billing --since "2026-11-11 10:00" --until "2026-11-11 10:30"
$ journalctl -u billing -p err
$ journalctl -u billing -b
OptionMeaning
-u NAMEOnly this unit
-fFollow: show new lines live (Ctrl+C to stop)
-n 100The last 100 lines
--since / --untilTime window
-p errOnly priority err and worse
-bOnly the current boot

Pipe it for analysis: journalctl -u billing --since today --no-pager | grep ERROR.

Deploying a new version

$ sudo cp billing-1.0.1.jar /opt/billing/billing.jar
$ sudo chown billing:billing /opt/billing/billing.jar
$ sudo systemctl restart billing
$ systemctl is-active billing
active

If you edit the unit file itself, run sudo systemctl daemon-reload first; changing only the JAR or the env file needs just a restart.

Mistake: forgetting daemon-reload, or using relative paths

After editing billing.service, systemd warns: The unit file changed on disk. Run 'systemctl daemon-reload'. And ExecStart=java -jar billing.jar fails with Executable path is not absolute. Use /usr/bin/java and a full JAR path.

Why a service fails: status codes you will see

  • status=203/EXEC — systemd could not run ExecStart: wrong path to java or the JAR, or the file is not readable by the service user.
  • status=217/USER — the User= account does not exist.
  • status=1/FAILURE — the app started and exited; read journalctl -u billing -n 100 (often a database connection or "port already in use").
  • Restart loop: Active: activating (auto-restart). After too many quick restarts systemd gives up with start-limit-hit; fix the cause, then systemctl reset-failed billing.
  • Spring Boot also supports building an "executable" JAR; the explicit java -jar in ExecStart is clearer and works with all versions.

In real projects

On a single VM, many teams run the app exactly like this behind Nginx (Nginx config). With containers, Docker or Kubernetes replaces systemd (Module 3), but the ideas are the same: a restart policy, a non-root user, config from environment variables, logs to stdout.

Interview: "How do you keep your Spring Boot app running after you close SSH?"

  • Create a systemd unit, enable --now it; it survives logout and reboots and restarts on crash with Restart=on-failure.
  • Mention a dedicated user, EnvironmentFile for secrets and journalctl -u for logs. nohup or & are only quick tricks.

Ports on a server: ss, lsof and "address already in use"

A program listens on a port to accept connections; ss -tulpn shows who listens where, and "address already in use" means another process already owns that port.

What listening means

An IP address finds a machine; a port (0-65535) finds a program on it. A server program listens on one address and port, such as 0.0.0.0:8080. When a client connects, the kernel hands the connection to that program. Only one process can listen on a given address and port at a time. Ports below 1024 are "privileged": only root (or a process given special rights) may bind to them, which is why apps listen on 8080 and Nginx on 80 and 443. Full networking ideas are in Module 2.

ss -tulpn

$ sudo ss -tulpn
Netid State  Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
tcp   LISTEN 0      4096   0.0.0.0:22          0.0.0.0:*         users:(("sshd",pid=801,fd=3))
tcp   LISTEN 0      511    0.0.0.0:80          0.0.0.0:*         users:(("nginx",pid=1100,fd=6))
tcp   LISTEN 0      200    127.0.0.1:5432      0.0.0.0:*         users:(("postgres",pid=950,fd=5))
tcp   LISTEN 0      100    *:8080              *:*               users:(("java",pid=5201,fd=9))
udp   UNCONN 0      0      127.0.0.53%lo:53    0.0.0.0:*         users:(("systemd-resolve",pid=620,fd=13))
FlagMeaning
-t / -uTCP / UDP sockets
-lOnly listening sockets
-pShow the process (needs sudo to see other users' processes)
-nNumbers, do not translate names (faster, clearer)

Read the Local Address column carefully:

  • 0.0.0.0:80 or *:8080 — listens on all network interfaces. Reachable from other machines (if the firewall allows).
  • 127.0.0.1:5432 — listens on localhost only. Only programs on the same machine can connect. This is the right setting for a database that only your app uses.

Many "my app is not reachable" problems are exactly this: the app listens on 127.0.0.1 only (see the checklist).

lsof and other ways to check a port

$ sudo lsof -i :8080
COMMAND  PID    USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
java    5201 billing    9u  IPv6  45678      0t0  TCP *:8080 (LISTEN)
$ sudo ss -tulpn | grep :8080
tcp LISTEN 0 100 *:8080 *:* users:(("java",pid=5201,fd=9))
$ curl -I http://localhost:8080/actuator/health
HTTP/1.1 200
$ nc -zv localhost 8080
Connection to localhost (127.0.0.1) 8080 port [tcp/http-alt] succeeded!

lsof ("list open files") works because in Linux a network socket is a file. lsof -i :PORT is the shortest way to answer "who is using this port?". netstat is the older tool; ss replaces it and is installed by default.

Fixing "address already in use"

When you start a second copy of your app, or an old one is still running, Spring Boot fails at startup:

***************************
APPLICATION FAILED TO START
***************************

Description:

Web server failed to start. Port 8080 was already in use.

Action:

Identify and stop the process that's listening on port 8080 or configure this
application to listen on another port.
  1. Find the owner: sudo lsof -i :8080 or sudo ss -tulpn | grep :8080.
  2. Decide: is it your old app, a leftover from a crash, or something else important?
  3. Stop it politely: kill PID, or sudo systemctl stop billing if it is a service. Escalate to kill -9 PID only if needed.
  4. Start your app again. Or choose another port: java -jar app.jar --server.port=8081 (or the environment variable SERVER_PORT=8081).

On Windows the same job is netstat -ano | findstr :8080 then taskkill /PID 1234 /F.

Tip: a quick one-liner

Free a port you know is a stuck dev process: kill $(lsof -t -i :8080). lsof -t prints only the PIDs. Make sure the port really is yours before you run it.

Edge cases

  • Permission denied when binding port 80 or 443 as a normal user — ports below 1024 need root. Run the app on 8080 and let Nginx (running as a service) listen on 80/443.
  • After a crash, a port can stay in TIME_WAIT for about a minute; most servers set the socket option so a restart still works.
  • The same port may be used for TCP and UDP by two different programs: they are separate.
  • Inside Docker, ss shows the container's own network, not the host's.

Interview: "Your app says port 8080 is in use. What do you do?"

  • Find the PID with lsof -i :8080 or ss -tulpn; check it is safe; stop it with kill; restart. Or change server.port.

Text tools: pipes, redirection, grep and tail -f

Linux tools each do one small job on text; pipes (|) connect them and redirection (>, >>, 2>&1) sends output to files, so a one-line pipeline can answer questions about gigabytes of logs.

Standard streams

Every process has three channels: stdin (0, input), stdout (1, normal output) and stderr (2, error messages). By default stdin is your keyboard and both outputs go to your screen. Redirection and pipes change where they go.

Redirection and pipes

SyntaxMeaning
cmd > fileWrite stdout to the file, replacing it
cmd >> fileAppend stdout to the file
cmd < fileRead stdin from the file
cmd 2> err.txtWrite only stderr to a file
cmd > out.txt 2>&1Send stderr to the same place as stdout (both into out.txt)
cmd > /dev/null 2>&1Throw away all output
cmd1 | cmd2Pipe: stdout of cmd1 becomes stdin of cmd2
cmd | tee fileShow on screen and save to a file
cmd1 && cmd2 / cmd1 || cmd2Run cmd2 only if cmd1 succeeded / failed

Order matters: 2>&1 means "make 2 point where 1 points now", so it must come after > file.

$ echo "build started" > build.log
$ echo "step 2 done" >> build.log
$ cat build.log
build started
step 2 done
$ ls /nonexistent 2> errors.txt
$ cat errors.txt
ls: cannot access '/nonexistent': No such file or directory
$ mvn package > build.log 2>&1
$ sort < names.txt | head -3
$ mkdir release && cp app.jar release/ || echo "failed"

-A/-B are very useful for Java logs: the line with ERROR is followed by a stack trace, so grep -A 15 "ERROR" prints the exception under each error. Quote patterns so the shell does not interpret *, | or $.

Watching logs live

$ tail -f /opt/billing/logs/app.log
$ tail -n 200 -f app.log
$ tail -f app.log | grep --line-buffered ERROR
$ tail -F app.log
$ less +F app.log
  • tail -f follows the file. -F also follows through log rotation, when the file is renamed and recreated; prefer it on production logs.
  • When you pipe tail -f into grep, add --line-buffered or the output may appear late.
  • less +F starts in follow mode; press Ctrl+C to stop following and scroll or search (/), then F to follow again. It is better than tail -f when you need to go back and look.
  • For a systemd service use journalctl -u NAME -f.

Mistake: truncating a file by redirecting onto itself

sort data.txt > data.txt empties the file before sort reads it. Write to a new file, then mv it back, or use sort -o data.txt data.txt. A single > overwrites; when in doubt use >>.

Mistake: uniq without sort

uniq only merges neighbours. uniq -c on unsorted input gives many partial counts. The standard idiom is sort | uniq -c | sort -rn.

Edge cases

  • grep exit code: 0 if something matched, 1 if nothing matched, 2 on error. In a script with set -e, a "no match" stops the script.
  • Binary file: Binary file x matches. Use grep -a to treat it as text.
  • Compressed rotated logs: zgrep ERROR app.log.2.gz searches without unzipping.
  • Basic grep treats +, | and () literally; add -E for regex features.

Interview: "How do you debug a production issue from logs?"

  • tail -f or journalctl -f to watch live; grep -n ERROR with -A context to see stack traces; narrow to the time window.
  • Summarise with sort | uniq -c | sort -rn (next article).

Docker packages your application together with everything it needs to run — the JRE, libraries, config files — into one unit called an image. You start that image as a container, and it behaves the same on your laptop, on a teammate's Windows machine, on the CI server and on a cloud VM. This ends the old "it works on my machine" problem, and it is why almost every Java job today expects you to read and write a Dockerfile.

This module builds on Linux (containers are Linux processes) and Networking (ports, DNS, localhost). It feeds directly into CI/CD, where the pipeline builds and pushes your image, and into Cloud and deployment, where platforms run it for you. The Spring Boot side (profiles, configuration, Actuator health) is in Spring Boot · Module 6.

After this module you will be able to:

  • Run, inspect, debug and clean up containers with the core docker commands.
  • Write a multi-stage Dockerfile for Spring Boot and explain every line, including layer caching.

  • Run Spring Boot, PostgreSQL and Redis with one docker compose up, with healthchecks.
  • Handle configuration and secrets safely, push images to a registry, and fix common failures.

Why containers: containers vs virtual machines, and Docker's architecture

A container is an ordinary Linux process that the kernel isolates (namespaces) and limits (cgroups), started from an image that holds the app and all its dependencies — so it runs the same everywhere, starts in seconds and uses far less memory than a virtual machine.

The "works on my machine" problem

You build a Spring Boot app on Windows with Java 21. The server has Java 17, a different PATH, an older PostgreSQL client, and no one remembers which environment variables were set. The app crashes in production but runs fine on your laptop. Every difference between environments — OS, Java version, libraries, config — is a possible bug.

A container fixes this by shipping the environment with the app. The unit you deploy is no longer "a JAR, plus instructions for the server"; it is "an image that already contains the JRE, the JAR and the settings". Anyone who runs that image gets the same result. Other benefits:

  • Consistency. Dev, test and production run the same image.
  • Isolation. Two apps that need Java 17 and Java 21 live side by side on one machine.
  • Fast start. A container starts in about a second plus your app's own start-up time.
  • Easy setup. A new teammate runs docker compose up and has PostgreSQL, Redis and your app — no installers.
  • Easy deployment. Every cloud platform (AWS ECS, Kubernetes, Render, Railway, Cloud Run) runs containers. Image in, running service out.

Containers versus virtual machines

A virtual machine (VM) emulates a whole computer. A hypervisor (VMware, VirtualBox, Hyper-V, KVM) splits the physical machine into several VMs, and each VM runs its own full operating system with its own kernel. Containers skip that: all containers on a host share one kernel, and the kernel keeps them apart.

Virtual machineContainer

They are not enemies. In the cloud, containers usually run inside VMs: an EC2 instance is a VM, and you run Docker on it.

What a container really is

A container is not a tiny VM; it is a normal Linux process with two kernel features applied. Namespaces give the process its own view of the system: its own process IDs (it thinks it is PID 1), its own network interfaces and ports, its own hostname, its own mounted filesystem. cgroups (control groups) limit how much CPU, memory and I/O the process may use. Add a layered filesystem built from the image, and you have a container. That is why you can see a container's Java process in ps on the host, and why a container needs a Linux kernel.

Docker Desktop on Windows (WSL2 backend)

Containers need a Linux kernel, and Windows does not have one. Docker Desktop solves this by running a small Linux environment through WSL2 (Windows Subsystem for Linux 2) and placing the daemon inside it. You type docker in PowerShell or a WSL terminal and it works as on Linux. Install Docker Desktop, keep "Use the WSL 2 based engine" ticked in Settings → General, and check with docker version and docker run hello-world.

  • Files inside the WSL2 filesystem (\\wsl$\Ubuntu\home\...) are much faster for bind mounts than files on C:\. Keep big projects there if builds feel slow.
  • WSL2 can take a lot of RAM. Limit it in %UserProfile%\.wslconfig ( [wsl2] section, memory=6GB).
  • Docker Desktop has licensing terms for larger companies; on a Linux server you install the free Docker Engine only. Podman is a compatible alternative.

Edge cases: containers are not a security boundary like a VM

  • A Windows or macOS "container" is a Linux container running in a hidden Linux VM.
  • Because the kernel is shared, an image built for ARM (Apple M-series, AWS Graviton) will not run on an x86 server unless it is built for both. Check the architecture if you see exec format error.
  • Running as root inside a container is risky; see the Dockerfile article.

Interview: "What is the difference between a container and a VM?"

  • A VM virtualises hardware and runs a full guest OS with its own kernel; a container virtualises the OS: processes share the host kernel and are isolated with namespaces and limited with cgroups.
  • Containers are lighter, start faster and pack denser; VMs isolate more strongly. In practice containers run on VMs.

Images, layers, tags and the container lifecycle

An image is a stack of read-only layers plus start-up metadata; a container is that stack with one thin writable layer on top. Use specific tags (never latest in production), and pick a small, official base image such as eclipse-temurin for Java.

Image, container, registry

Think of an image as a class and a container as an object created from it. You can start ten containers from one image. The image never changes; each container gets its own writable layer, which is thrown away when the container is removed. That is why data written inside a container disappears — unless you use a volume.

A registry stores images so other machines can download them. Docker Hub (hub.docker.com) is the default public registry. An image name has the form registry/namespace/repository:tag, and most parts have defaults:

Written asMeans

ghcr.io/asha/shop-api:1.2.0GitHub Container Registry

Layers and the build cache

Each instruction in a Dockerfile that changes the filesystem (RUN, COPY, ADD) creates a layer: a set of file changes. An image is a stack of layers. Layers are identified by a hash of their content, so they are shared: ten images built on the same eclipse-temurin:21-jre store that base only once on disk and download it once.

When you build, Docker reuses a cached layer if the instruction and its inputs are identical. The moment one layer changes, every layer after it is rebuilt. This is the most important performance rule in Docker: put things that change rarely (dependencies) before things that change often (your source code). The Dockerfile article shows how.

Tags and digests

A tag is a movable label on an image: postgres:16, eclipse-temurin:21-jre. If you do not write a tag, Docker uses latest, which is just a name, not "the newest safe version". Tags can be moved: postgres:16 points to 16.x today and a newer 16.y next month. A digest is the immutable SHA-256 of the image content: postgres@sha256:…. It always means exactly the same bytes.

Official images and choosing a Java base image

Official images (no username, such as postgres, redis, nginx, eclipse-temurin) are curated, documented and regularly updated. Prefer them over random user images. For Java use eclipse-temurin, the Eclipse Adoptium build of OpenJDK. Its tags are named by version and type:

  • eclipse-temurin:21-jdk — full JDK, for compiling. Large.
  • eclipse-temurin:21-jre — runtime only. Right for running a built JAR. The same pattern exists for 25 (the newest LTS) and 17.
  • Variants such as 21-jre-alpine (Alpine Linux base) or 21-jre-jammy (a named Ubuntu release). Check the image's page on Docker Hub for the exact tag list.
BaseProsCons
Debian/Ubuntu (default tags)Uses glibc, most compatible, easy debugging toolsBigger

A sensible default for a Spring Boot service: eclipse-temurin:21-jre. Choose Alpine only when image size really matters and you have tested the app on it.

The container lifecycle

A container lives only as long as its main process (PID 1). When your Java process exits, the container exits. A stopped container still exists, with its writable layer and logs, until you remove it with docker rm.

Rule: pin a version; never rely on latest in production

With FROM eclipse-temurin:latest your next build may silently switch to a new Java major version. Use a version tag in Dockerfiles and compose files, and tag your own images with a version or git SHA.

Mistake: storing data in the container's writable layer

Uploads, database files or logs written inside a container vanish on docker rm and on redeploys. Use volumes, an external database, or object storage.

Interview: "Image versus container? What are layers?"

  • Image: read-only template; container: a running instance with a writable layer.
  • Layers: each filesystem-changing instruction creates one; they are cached and shared. Order instructions so rarely changing ones come first.

Docker commands: run, ps, logs, exec, stop, rm and friends

Learn docker run and its flags, then ps, logs -f, exec -it, stop, rm, images and system prune; these ten commands cover nearly all daily Docker work.

Your first container

$ docker run -d --name pg -p 5432:5432 \
    -e POSTGRES_PASSWORD=devpass -e POSTGRES_DB=shop \
    postgres:16

Port mapping reads left to right as host:container. In -p 8081:8080 a browser uses localhost:8081 and the app inside still listens on 8080. Bind only to your own machine with -p 127.0.0.1:5432:5432; plain -p 5432:5432 listens on all interfaces, which is risky on a public server.

Inspecting and debugging

$ docker ps -a                       # all containers, also stopped ones
$ docker logs pg                     # print the logs
$ docker logs -f --tail 100 pg       # follow, starting from the last 100 lines
$ docker exec -it pg psql -U postgres -d shop     # open psql inside the container
$ docker exec -it pg sh              # a shell inside it (bash if the image has it)
$ docker inspect pg                  # full JSON: IP address, mounts, env, state
$ docker inspect -f '{{.State.ExitCode}}' pg      # one field
$ docker stats                       # live CPU and memory per container
$ docker top pg                      # processes inside
$ docker cp pg:/etc/hostname ./      # copy a file out of a container

exec starts a new process inside a running container; it is how you "log in". docker run -it starts a new container. Do not confuse them.

A Spring Boot app handles SIGTERM by finishing in-flight requests if you enable server.shutdown=graceful. This works only if the Java process is PID 1 or receives the signal (see ENTRYPOINT exec form in the next article).

Images and cleanup

$ docker images                      # list local images
$ docker pull eclipse-temurin:21-jre # download without running
$ docker rmi postgres:16             # delete an image (no container may use it)
$ docker tag shop-api:1.0 asha/shop-api:1.0
$ docker push asha/shop-api:1.0
$ docker system df                   # how much space Docker uses
$ docker system prune                # remove stopped containers, dangling images, unused networks
$ docker system prune -a --volumes   # also unused images AND unused volumes (dangerous)

Disks fill up with old images and containers quickly, especially on CI servers and laptops. docker system prune is safe for most work; the --volumes flag deletes volumes that no container uses, which can include your database data.

Restart policies

By default a container that crashes stays down. --restart on-failure restarts it when it exits with an error; unless-stopped restarts it also after a server reboot unless you stopped it by hand; always is similar but also restarts a container you stopped, after the daemon restarts. For a server, unless-stopped is the usual choice.

Tip: name things and clean as you go

Use --name so commands are readable, and --rm for throwaway containers (docker run --rm -it eclipse-temurin:21-jdk jshell gives you a JShell with no installation).

Mistake: "port is already allocated" and "name already in use"

  • Bind for 0.0.0.0:5432 failed: port is already allocated — a local PostgreSQL or another container already uses that host port. Use -p 5433:5432 or stop the other one.
  • The container name "/pg" is already in use — remove the old container (docker rm pg) or choose another name.

Edge cases

  • -e POSTGRES_PASSWORD=... on the command line is stored in your shell history and visible in docker inspect; use --env-file for anything real.
  • The official PostgreSQL image only reads POSTGRES_PASSWORD and POSTGRES_DB when the data directory is empty. Changing them later has no effect on an existing volume.
  • On Windows PowerShell, line continuation is the backtick (`), not \; Git Bash and WSL use \.

Interview: "docker stop versus docker kill? exec versus run?"

  • stop sends SIGTERM, waits (10 s default), then SIGKILL; kill sends SIGKILL at once.
  • run creates and starts a new container from an image; exec runs an extra process inside an existing running container.

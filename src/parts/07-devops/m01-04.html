Editing in the terminal: nano and vim survival

On a server you edit files in the terminal: nano is simple and shows its keys at the bottom; vim is on every server and has modes, so learn the few keys to open, edit, save and quit without panic.

A server has no VS Code. When a config file needs a one-line change at 2 a.m., you open it with an editor that is already installed. You do not need to be fast; you need to be safe and sure.

nano: the easy editor

Run nano file (use sudo nano for files you do not own, such as those in /etc). You type directly; commands are shown at the bottom. ^ means Ctrl.

KeysAction

Ctrl+XExit (asks to save if there are changes)
Ctrl+WSearch
Ctrl+K / Ctrl+UCut the current line / paste it
Ctrl+_Go to a line number
Alt+UUndo
 
$ sudo nano /etc/billing/billing.env
# change a value, then Ctrl+O, Enter, Ctrl+X
$ sudo systemctl restart billing

vim: why bother?

vim (or its older form vi) is installed on almost every Linux machine, including minimal containers and recovery shells. git commit may open it, and crontab -e may open it. You must be able to leave it. People get "stuck in vim" because it starts in normal mode, where keys are commands, not text.

The modes

  • Normal mode (default): move, delete, copy, search, undo.
  • Insert mode: type text like any editor. Enter with i; leave with Esc.
  • Command mode: start with :, then type a command and press Enter (save, quit, replace).

Lost? Press Esc two or three times. You are then in normal mode.

  1. Open: vim application.properties. You are in normal mode.
  2. Search for the setting: type /server.port and press Enter.
  3. Move to the right place and press i to start editing. Change the value.
  4. Press Esc.
  5. Type :wq and press Enter. Changed your mind? :q!.

Tip: choose your default editor

If a tool opens an editor you do not like, set it: export EDITOR=nano in ~/.bashrc, or run sudo update-alternatives --config editor. Git has git config --global core.editor nano. For bigger work, edit locally and copy the file with scp, or use the VS Code Remote-SSH extension.

Mistake: typing text in normal mode, or editing a root file without sudo

Typing letters in normal mode runs commands and can wreck the file (undo with u). And if you open /etc/... without sudo, vim lets you edit but :w fails with E45: 'readonly' option is set or Can't open file for writing. Quit with :q! and reopen with sudo vim.

Edge cases

  • A leftover file .file.swp means vim was closed badly or another session has the file open. Vim offers to recover; delete the swap file only when you are sure.
  • Pasting into a terminal editor can mangle indentation (auto-indent). In vim use :set paste first; in YAML, spaces matter, so check the result.
  • YAML and Makefiles are indentation sensitive; tabs can break them (YAML forbids tabs).

Interview: "How do you exit vim?"

  • Press Esc, then :wq to save and quit, or :q! to quit without saving.
  • Show you know the three modes; that earns the point more than the keys do.

Bash scripting: variables, conditions, loops, functions and exit codes

A bash script is a text file of commands with a shebang line; add variables, if, loops and functions, check exit codes ($?), and start every serious script with set -euo pipefail.

Your first script

Any series of commands you type twice deserves a script. Create a file, add the shebang (the first line, which tells Linux which interpreter runs the file), make it executable and run it.

#!/usr/bin/env bash
echo "Hello from $(hostname) on $(date +%F)"
$ chmod +x hello.sh
$ ./hello.sh
Hello from web-1 on 2026-11-11
$ bash hello.sh
Hello from web-1 on 2026-11-11

$(command) is command substitution: it runs the command and inserts its output. #!/usr/bin/env bash finds bash on the PATH (portable); #!/bin/bash is also common.

Variables and quoting

#!/usr/bin/env bash
APP_NAME="billing"
VERSION=1.0.1
JAR="${APP_NAME}-${VERSION}.jar"
echo "Deploying $JAR"
echo 'Single quotes: no $expansion here'
FILES=$(ls | wc -l)
echo "There are $FILES entries"
echo "Home is ${HOME}, user is ${USER:-unknown}"
  • No spaces around =. Read a variable with $NAME; use ${NAME} when letters follow it.
  • Double quotes expand variables; single quotes do not. Always quote variables: "$FILE". Unquoted, a value with spaces splits into several words.
  • ${VAR:-default} uses a default when VAR is unset or empty; ${VAR:?message} stops with an error if it is unset.

Arguments

>&2 sends the message to stderr, which is the right place for errors.

Exit codes

Every command ends with an exit code: 0 means success, any other number means failure. $? holds the last one. Conditions, &&, || and CI pipelines all use it.

$ ls /tmp > /dev/null; echo $?
0
$ ls /nonexistent 2> /dev/null; echo $?
2
$ grep -q ERROR app.log && echo "errors found" || echo "clean"
clean

In your own scripts end with exit 0 for success and exit 1 (or another small number) for failure; CI (Module 4) marks a step as failed when the script exits non-zero.

if, test and [[ ]]

if [[ -f "$JAR" ]]; then
    echo "jar exists"
elif [[ -d "$JAR" ]]; then
    echo "it is a directory"
else
    echo "missing"
fi

if [[ "$ENV" == "prod" && $COUNT -gt 3 ]]; then echo "big prod run"; fi
if grep -q "ERROR" app.log; then echo "has errors"; fi
if ! command -v java > /dev/null; then echo "java not installed"; fi
TestTrue when
-f path / -d path / -e pathRegular file / directory / anything exists

[[ ]] is the modern bash form (safer with spaces, supports && and || inside). [ ] and test are the older POSIX forms that work in plain sh too. Needs spaces inside the brackets: [[ -f $x ]], not [[-f $x]]. if can also test any command directly, as with grep -q.

Loops

for f in *.log; do
    echo "$f has $(wc -l < "$f") lines"
done

for i in {1..5}; do echo "attempt $i"; done

count=0
while [[ $count -lt 3 ]]; do
    echo "count=$count"
    count=$((count + 1))
done

while read -r line; do
    echo "host: $line"
done < hosts.txt

$(( ... )) is arithmetic. The while read -r form reads a file line by line. break and continue work as in Java.

Functions

log() {
    echo "[$(date +%T)] $*"
}

check_port() {
    local port="$1"
    if ss -tln | grep -q ":${port} "; then
        return 0
    fi
    return 1
}

log "Checking the app"
if check_port 8080; then log "8080 is listening"; else log "8080 is down"; fi

Functions take arguments as $1, $2; return sets the exit status (0-255), and printed text is the "return value". Use local for variables, or they become global.

Read input and make scripts safe

#!/usr/bin/env bash
set -euo pipefail

read -r -p "Deploy to which environment (staging/prod)? " ENV
case "$ENV" in
    staging|prod) echo "Deploying to $ENV" ;;
    *) echo "Unknown environment: $ENV" >&2; exit 1 ;;
esac

cleanup() { rm -f /tmp/deploy.lock; }
trap cleanup EXIT
set -e
Exit immediately when a command fails (non-zero exit).
set -u
Treat an unset variable as an error. It protects rm -rf "$DIR/" from running with an empty DIR.
set -o pipefail
A pipeline fails if any stage fails, not only the last. Without it, false | true counts as success.
trap cleanup EXIT
Run a function when the script ends, even on error: delete temp files, release locks.
case
Match a value against patterns; like switch in Java.

Rule: start scripts with a shebang and set -euo pipefail

Without them, bash keeps going after an error. A failed cd followed by rm -rf * deletes the wrong folder. Add them to every script that changes anything.

Mistake: unquoted variables and spaces around =

Wrong: breaks on spaces, wrong assignment

NAME = "my app"
rm -rf $DIR/*
if [ $ENV == prod ]; then echo ok; fi

Right: quoted, no spaces around =

NAME="my app"
rm -rf "${DIR:?}"/*
if [[ "$ENV" == "prod" ]]; then echo ok; fi

${DIR:?} aborts the script when DIR is empty or unset — a cheap safety net.

Edge cases

  • With set -e, a grep that finds nothing (exit 1) stops the script. Guard it: grep -q x file || true or put it in an if.
  • Commands in an if condition or before || are exempt from set -e.
  • A script run as sh script.sh uses a smaller shell on Ubuntu (dash), so [[ ]] and arrays fail. Run it with bash or ./script.sh.
  • A script run through cron or systemd has a small PATH and no ~/.bashrc; use absolute paths.
  • CRLF line endings break the shebang (see Linux basics).

Interview: "What does set -euo pipefail do?"

  • -e stop on error, -u error on unset variables, pipefail fail if any command in a pipe fails.
  • Together they make a script fail fast instead of continuing in a broken state. Mention trap for cleanup and quoting variables.

A real deploy and backup script, with cron

A deploy script copies the new JAR, restarts the service, checks the health endpoint and rolls back if it fails; cron runs scheduled jobs such as a nightly database backup.

Deploy script

This script runs on the server. You upload the JAR to /tmp first, then run it. It keeps the previous JAR, restarts the systemd service from the earlier article, waits for Spring Boot Actuator's health endpoint and rolls back if the new version does not become healthy.

#!/usr/bin/env bash
# Usage: ./deploy.sh /tmp/billing-1.0.1.jar
set -euo pipefail

APP_DIR="/opt/billing"
SERVICE="billing"
HEALTH_URL="http://localhost:8080/actuator/health"
NEW_JAR="${1:?Usage: $0 path-to-new-jar}"

log() { echo "[$(date '+%F %T')] $*"; }

[[ -f "$NEW_JAR" ]] || { log "File not found: $NEW_JAR" >&2; exit 1; }

log "Backing up current jar"
if [[ -f "$APP_DIR/billing.jar" ]]; then
    cp "$APP_DIR/billing.jar" "$APP_DIR/billing.jar.previous"
fi

log "Installing new jar"
cp "$NEW_JAR" "$APP_DIR/billing.jar"
chown billing:billing "$APP_DIR/billing.jar"

log "Restarting $SERVICE"
systemctl restart "$SERVICE"

log "Waiting for health check"
for attempt in {1..30}; do
    if curl -fsS "$HEALTH_URL" 2>/dev/null | grep -q '"status":"UP"'; then
        log "Healthy after $attempt checks. Deploy OK."
        exit 0
    fi
    sleep 2
done

log "Health check failed, rolling back" >&2
if [[ -f "$APP_DIR/billing.jar.previous" ]]; then
    cp "$APP_DIR/billing.jar.previous" "$APP_DIR/billing.jar"
    systemctl restart "$SERVICE"
fi
journalctl -u "$SERVICE" -n 30 --no-pager >&2
exit 1

Walk through it:

  1. set -euo pipefail and ${1:?...} make the script stop if a step fails or the JAR argument is missing.
  2. It checks the new file exists before touching anything.
  3. It keeps billing.jar.previous as the rollback copy.
  4. curl -fsS: -f fails on HTTP errors, -s is silent, -S still shows errors. The loop tries for about a minute (30 times, 2 seconds apart), long enough for Spring Boot to start.
  5. On failure it restores the old JAR, restarts, prints the last log lines and exits with 1 so whoever called the script (a person or CI) sees the failure.
$ mvn -q package -DskipTests
$ scp target/billing-1.0.1.jar billing:/tmp/
$ ssh billing "sudo /opt/billing/deploy.sh /tmp/billing-1.0.1.jar"
[2026-11-11 10:55:01] Backing up current jar
[2026-11-11 10:55:01] Installing new jar
[2026-11-11 10:55:01] Restarting billing
[2026-11-11 10:55:02] Waiting for health check
[2026-11-11 10:55:12] Healthy after 5 checks. Deploy OK.

The health endpoint needs spring-boot-starter-actuator in the project; the exact JSON your app returns can differ, so adjust the grep. Module 5 and Module 4 automate this exact flow in a GitHub Actions pipeline.

Backup script

#!/usr/bin/env bash
set -euo pipefail

BACKUP_DIR="/var/backups/billing"
DB_NAME="billing"
KEEP_DAYS=7
STAMP="$(date +%F_%H%M)"
FILE="$BACKUP_DIR/${DB_NAME}_${STAMP}.sql.gz"

mkdir -p "$BACKUP_DIR"
pg_dump "$DB_NAME" | gzip > "$FILE"
echo "Backup written: $FILE ($(du -h "$FILE" | cut -f1))"

find "$BACKUP_DIR" -name "${DB_NAME}_*.sql.gz" -mtime +"$KEEP_DAYS" -delete
echo "Old backups removed"

pg_dump writes the database as SQL; gzip compresses it. The find -mtime +7 -delete line removes files older than seven days so the disk does not fill up. For PostgreSQL the script runs as a user that may connect to the database (for example postgres through its own crontab, or credentials from a ~/.pgpass file). A backup you have never restored is not a backup; test a restore.

cron: scheduled jobs

cron runs commands on a schedule. Each user has a crontab:

$ crontab -e
$ crontab -l
0 2 * * * /opt/scripts/backup-db.sh >> /var/log/backup.log 2>&1
*/15 * * * * curl -fsS http://localhost:8080/actuator/health > /dev/null || echo "down"
ScheduleMeaning
0 2 * * *Every day at 02:00
*/15 * * * *Every 15 minutes
30 9 * * 1-509:30 on weekdays (Mon-Fri)
0 0 1 * *Midnight on the first day of each month
@rebootOnce, at boot (a shortcut instead of five fields)

Mistake: cron jobs that work in the terminal but not in cron

  • cron runs with a minimal PATH and no .bashrc. Use absolute paths (/usr/bin/pg_dump) and set variables in the script.
  • Without redirection you will not see errors. Always append >> file.log 2>&1.
  • In a crontab, a % character means a newline; escape it as \% (for example in date +%F). Putting the logic into a script avoids this.
  • The server's time zone decides when "02:00" is; check with timedatectl. EC2 machines are usually UTC.

Edge cases

  • If the script is still running when the next run starts, you get two at once. Use flock -n /tmp/backup.lock command to skip a run while the lock is held.
  • cron does not catch up on missed runs if the server was off. For that, look at systemd timers (OnCalendar= with Persistent=true).
  • A rollback copy is not a database rollback: if the new version changed the schema, restoring the old JAR may not be enough. Use migrations carefully (Flyway/Liquibase, Spring Boot Module 6).

In real projects

Small teams run exactly this: CI builds the JAR, scps it, and calls the deploy script over SSH. Larger teams replace it with Docker images and rolling updates, but the checks (health endpoint, rollback, log tail on failure) remain.

Interview: "How would you deploy a Spring Boot app to a Linux server, without Docker?"

  • Build the JAR, copy it with scp, run it under systemd as a non-root user with env vars from a file, restart, check the health endpoint, keep the previous JAR for rollback.
  • Put Nginx in front for TLS (Module 2).

wget is simpler for downloads: wget https://example.com/file.zip, with -c to resume and -O name to rename. Piping a download straight into a shell (curl ... | bash) runs unseen code; download, read, then run.

Tip: a one-screen "server check" you can paste in any ticket

uptime; free -h | head -2; df -h / | tail -1; systemctl is-active billing; \
ss -tln | grep -E ':(80|443|8080) '

Mistake: tar with the wrong flag order, and curl quoting

  • tar -cfz backup.tar.gz dir makes a file named z, because -f takes the next word as the file name. Write -czf.
  • Wrap JSON for curl -d in single quotes in bash; on Windows cmd or PowerShell the quoting differs, which is another reason to practise in WSL.

Edge cases

  • A deleted file that a running process still holds open keeps using disk space. df stays full while du shows less. Restart the process (or find it with lsof | grep deleted).
  • curl prints nothing for an empty 204 response; check the status with -i or -w "%{http_code}".
  • tar -xzf overwrites existing files silently; extract into a new folder with -C.
  • curl: (7) Failed to connect = nothing listening or blocked; (6) Could not resolve host = DNS; (60) = certificate problem (see TLS).

Interview: "The server is slow. What do you check first?"

  • uptime and top for load and the busy process; free -h for memory (is it swapping or OOM-killed?); df -h for a full disk; logs.
  • Then the network side: ss, curl -v, and the app's own metrics.

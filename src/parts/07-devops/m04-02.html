A complete CI workflow for a Spring Boot Maven project

The CI workflow checks out the code, installs Temurin Java with the Maven cache, runs ./mvnw -B verify, and uploads the test reports; add a PostgreSQL service container or Testcontainers for integration tests, and a separate job for the React frontend.

The goal

On every pull request to main and every push to main: compile the project, run all tests, and keep the test reports so a failure can be diagnosed without re-running. The build must be quick (dependencies cached) and reproducible (same Java version as production).

The workflow

name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read                      # least privilege for GITHUB_TOKEN

concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true            # a newer push cancels the older run

jobs:
  backend:
    name: Backend (Maven)
    runs-on: ubuntu-latest
    timeout-minutes: 15               # never let a stuck build run for hours

    steps:
      - name: Check out the code
        uses: actions/checkout@v4

      - name: Set up Java 21 (Temurin) with Maven cache
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"
          cache: maven                # caches ~/.m2, keyed on pom.xml files

      - name: Build and test
        run: ./mvnw -B -ntp verify

      - name: Upload test reports
        if: always()                  # also when tests failed
        uses: actions/upload-artifact@v4
        with:
          name: surefire-reports
          path: |
            target/surefire-reports/
            target/failsafe-reports/
          if-no-files-found: ignore
          retention-days: 7

      - name: Upload the JAR
        uses: actions/upload-artifact@v4
        with:
          name: app-jar
          path: target/*.jar
          retention-days: 7

Line by line

on: push / pull_request
Run on merges to main and on every PR aimed at it.
permissions: contents: read
The token can only read the repository. Nothing in CI needs more.
concurrency
One run per branch; cancels outdated runs. The group includes the workflow name so different workflows do not cancel each other.
runs-on: ubuntu-latest
A fresh GitHub-hosted Ubuntu VM for this job. It already contains Docker, Git, Node, several JDKs and Maven; we still install our own Java to control the version.
timeout-minutes
Fails the job if it runs longer than this (the default is 360 minutes, which wastes your free minutes on a hang).
actions/checkout@v4
Clones your repository into the runner. Without this step the runner has no code. By default it fetches only the commit being built (shallow); add fetch-depth: 0 if a tool needs the full history.
actions/setup-java@v4
Installs the JDK. distribution: temurin is the Eclipse Temurin build; java-version is quoted so YAML keeps it a string. cache: maven restores and saves Maven's local repository, so dependency downloads happen only when a pom.xml changes.
./mvnw -B -ntp verify
The Maven wrapper pins the Maven version for the project. -B is batch mode, -ntp hides the noisy "downloading…" lines. verify runs the lifecycle through compile, unit tests (Surefire), packaging, and integration tests (Failsafe, if used), so it checks more than test. Use mvn test if you only want unit tests.
if: always()
The upload step runs even if the build step failed, which is exactly when you need the reports.
upload-artifact
Stores files with the run; download them from the run's summary page. Set a short retention-days to save storage.

Mistake: mvnw: Permission denied

If the wrapper was committed from Windows, its executable bit may be missing and Linux refuses to run it. Fix once on your machine and commit: git update-index --chmod=+x mvnw && git commit -m "Make mvnw executable". Or run sh ./mvnw …, or call mvn directly (Maven is preinstalled on the runner).

Integration tests that need PostgreSQL

Two good options exist.

Option 1: Testcontainers (recommended). Your tests start a real PostgreSQL container themselves (see Spring Boot · Module 5). GitHub-hosted Ubuntu runners have Docker installed, so it works with no extra workflow lines, and the test behaves the same locally and in CI. This is the preferred approach.

Option 2: a service container. The workflow starts a database next to the job, and your tests connect to it through environment variables.

  integration:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_DB: shop_test
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U test -d shop_test"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 10
    env:
      SPRING_DATASOURCE_URL: jdbc:postgresql://localhost:5432/shop_test
      SPRING_DATASOURCE_USERNAME: test
      SPRING_DATASOURCE_PASSWORD: test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"
          cache: maven
      - run: ./mvnw -B -ntp verify

Here the job runs directly on the runner, so the database is reached at localhost:5432 (the published port). If the job itself ran in a container (container: key), you would use the service name postgres instead — the same localhost rule as in Docker networks. The options health check makes GitHub wait until the database is ready before the steps start.

A frontend job (React with Vite)

The React app is built and tested in its own job, in parallel with the backend. If the frontend sits in a frontend/ folder of the same repository, set the working directory.

  frontend:
    name: Frontend (React)
    runs-on: ubuntu-latest
    timeout-minutes: 10
    defaults:
      run:
        working-directory: frontend
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "22"
          cache: npm
          cache-dependency-path: frontend/package-lock.json
      - run: npm ci                  # clean, exact install from package-lock.json
      - run: npm run lint --if-present
      - run: npm test --if-present
      - run: npm run build           # fails the job on TypeScript/Vite errors

npm ci installs exactly what package-lock.json says and fails if the lock file and package.json disagree — which is what you want in CI (npm install may modify the lock file). Choose the Node version your project uses. See Frontend · Module 5 for the React side.

Showing results

On each pull request the checks appear at the bottom: a green tick or a red cross per job, with a link to the log. Open a failed step, read the last lines of output (Maven prints the failing test name and the assertion), and download the surefire-reports artifact for the full stack traces. Always try to reproduce locally with the same command: ./mvnw -B verify.

Convention: one command that CI and developers both run

Keep logic in Maven (or a script in the repository), not in long YAML. The workflow becomes "checkout, install tools, run the command". Then "it fails in CI" can be reproduced on a laptop.

Edge cases and errors

  • Tests pass locally but fail in CI — usually time zones (the runner is UTC), file name case (Linux is case-sensitive), line endings, a service that exists only on your laptop, or tests that depend on order.
  • Flaky tests — fix or quarantine them; do not just re-run until green.
  • Cache never hits — the key is based on pom.xml; editing it changes the key and rebuilds the cache once. Caches are scoped per branch (a PR can read the default branch's cache).
  • Out of disk or memory on a hosted runner — a standard runner has limited RAM and disk; keep Testcontainers and test data modest.

Interview: "Write a CI pipeline for a Spring Boot app."

  • Trigger on PR and push to main; checkout, setup-java (Temurin 21, cache: maven), ./mvnw -B verify, upload reports with if: always().
  • Integration tests with Testcontainers or a Postgres service container; parallel frontend job with npm ci; least-privilege permissions and concurrency.

Building and pushing a Docker image to GHCR or Docker Hub

After tests pass, log in to the registry with docker/login-action, let docker/metadata-action compute the tags (git SHA, branch, semver), and build and push with docker/build-push-action using the GitHub Actions cache — to GHCR with the built-in GITHUB_TOKEN.

The pieces

  • docker/setup-buildx-action — sets up Buildx, the modern builder (enables caching and multi-platform builds).
  • docker/login-action — logs the runner in to a registry.
  • docker/metadata-action — turns the git context into image tags and labels, so you do not assemble strings by hand.
  • docker/build-push-action — runs docker build (using your Dockerfile) and optionally pushes.

Your multi-stage Dockerfile from Module 3 already builds the JAR inside the image, so this job needs no Maven step.

Publishing to GitHub Container Registry

name: Docker image

on:
  push:
    branches: [main]
    tags: ["v*.*.*"]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}      # owner/repo

jobs:
  image:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write                       # needed to push to GHCR
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Compute tags and labels
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha
            type=semver,pattern={{version}}
            type=raw,value=latest,enable={{is_default_branch}}

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

What each part does

permissions: packages: write
Allows the GITHUB_TOKEN to publish packages. Without it you get denied: permission_denied: write_package.
login-action with GITHUB_TOKEN
No password to store: the automatic token of the run logs in to ghcr.io as the triggering user.
images: ghcr.io/owner/repo
The image name. GHCR names must be lowercase; the metadata action lowercases the repository name for you. If you build the name by hand with a mixed-case owner, convert it first.
tags: type=sha
Adds a tag from the commit SHA, in the short form sha-3f9c2ab (the prefix sha- is the default). Every build gets a unique tag.
type=semver,pattern={{version}}
On a tag push such as v1.2.0, adds the tag 1.2.0 (without the v).
type=raw,value=latest,enable=…
Also tags latest on the default branch, for convenience. Do not deploy from it.
cache-from / cache-to: type=gha
Stores Docker layer cache in the GitHub Actions cache, so unchanged layers (the dependency layer!) are not rebuilt in the next run. mode=max also caches intermediate stages, which matters for multi-stage builds.
steps.meta.outputs.tags
A step with an id exposes outputs that later steps read as ${{ steps.<id>.outputs.<name> }}.

For pull requests you usually want to build the image (to make sure the Dockerfile works) but not push it. Use push: ${{ github.event_name != 'pull_request' }} and run the workflow on PRs too.

Where it fits

Common layouts: one workflow with jobs test → image → deploy chained by needs (shown in the CD article), or separate workflows. Having the image job depend on the test job means a broken build is never published.

Rule: build once, deploy that exact image

The image you tested is the image you deploy: reference it by the SHA tag. Do not rebuild on the server or build a second time for production.

Mistake: denied errors when pushing

  • denied: permission_denied: write_package — the job lacks packages: write, or the package already exists and is linked to another repository, or the organisation restricts token permissions (Settings → Actions → General → Workflow permissions).
  • invalid reference format — uppercase letters in the image name, or an empty tag from a mistyped metadata step.
  • Docker Hub login failing — you used your account password instead of an access token, or the secret name is misspelled.

Edge cases

  • Pull requests from forks cannot push (no secrets, read-only token); build without pushing.
  • The runner is x86-64. To run on ARM servers (AWS Graviton) add docker/setup-qemu-action and platforms: linux/amd64,linux/arm64; the ARM build under emulation is slow.
  • A newly created GHCR package may be private; make it public or give your server a token with read:packages.

Interview: "How does your pipeline build and publish a Docker image?"

  • After tests: buildx, login (GHCR with GITHUB_TOKEN and packages: write), metadata for tags (SHA, semver), build-push with the GHA layer cache.
  • Immutable SHA tags; deploy by tag; never push from untrusted PRs.

Continuous deployment: SSH to a server, deploy hooks, environments and rollback

After the image is pushed, a deploy job logs in to your server over SSH and runs docker compose pull && docker compose up -d with the new tag — or calls your platform's deploy hook; an environment adds approvals, and rollback is just deploying the previous tag.

Option A: deploy over SSH to your own server

The server (for example an EC2 instance from Module 1) has Docker, a folder /opt/shop with the production compose.yaml and a .env file with real secrets. The compose file references the image through a variable:

services:
  api:
    image: ghcr.io/asha/shop-api:${IMAGE_TAG:-latest}
    env_file: .env
    ports:
      - "127.0.0.1:8080:8080"          # Nginx on the host proxies to this
    restart: unless-stopped
  # postgres, redis ... as in the Compose article

One-time setup on the server: create a deploy user, add the CI's public SSH key to ~/.ssh/authorized_keys, and log Docker in to GHCR with a token that can read packages (docker login ghcr.io) if the image is private. Generate a dedicated key pair on your laptop (ssh-keygen -t ed25519 -f deploy_key -C "github-actions") and put the private key into a GitHub secret. Never reuse your personal key.

Add these repository (or environment) secrets: SSH_HOST, SSH_USER, SSH_PRIVATE_KEY, and SSH_KNOWN_HOSTS (the output of ssh-keyscan -t ed25519 your.server.ip, which pins the server's identity so a man-in-the-middle cannot impersonate it).

The full CI → image → deploy workflow

This is the workflow for your Project 3: tests on every push and PR; on main only, push the image and deploy.

name: CI/CD

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

env:
  REGISTRY: ghcr.io

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"
          cache: maven
      - run: ./mvnw -B -ntp verify

  image:
    needs: test
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    outputs:
      tag: ${{ steps.vars.outputs.tag }}
    steps:
      - uses: actions/checkout@v4
      - id: vars
        run: echo "tag=sha-${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ github.repository }}
          tags: |
            type=sha
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy:
    needs: image
    runs-on: ubuntu-latest
    environment:
      name: production                  # approvals and environment secrets apply here
      url: https://shop.example.com
    concurrency:
      group: deploy-production
      cancel-in-progress: false         # never cancel a deployment half way
    steps:
      - name: Prepare SSH
        env:
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          SSH_KNOWN_HOSTS: ${{ secrets.SSH_KNOWN_HOSTS }}
        run: |
          mkdir -p ~/.ssh
          printf '%s\n' "$SSH_PRIVATE_KEY" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          printf '%s\n' "$SSH_KNOWN_HOSTS" > ~/.ssh/known_hosts

      - name: Deploy the new image
        env:
          TAG: ${{ needs.image.outputs.tag }}
          TARGET: ${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}
        run: |
          ssh "$TARGET" "cd /opt/shop && \
            IMAGE_TAG=$TAG docker compose pull api && \
            IMAGE_TAG=$TAG docker compose up -d api && \
            docker image prune -f"

      - name: Smoke test
        run: |
          for i in 1 2 3 4 5 6; do
            if curl -fsS https://shop.example.com/actuator/health; then exit 0; fi
            sleep 10
          done
          echo "Health check failed" && exit 1

How it works

  • Job chain. test runs on PRs and pushes. image and deploy run only for pushes to main (the if on the image job skips it for PRs, and deploy is skipped because its need was skipped).
  • The tag handoff. The image job exposes tag as a job output (sha- plus the first seven characters of the commit). The metadata action's type=sha produces the same short form, so the deploy job pulls exactly the image just built.
  • SSH. The private key is written to a file with permission 600 (SSH refuses looser permissions). Secrets are passed in through env and used as shell variables, not pasted into the script text with ${{ }}, which keeps them out of the script source and avoids shell injection. known_hosts holds the server's pinned key, so we do not need StrictHostKeyChecking=no.
  • The remote command. docker compose pull api downloads the new image; up -d api recreates only the API container with it; databases keep running. docker image prune -f removes dangling old layers.
  • Smoke test. After deployment, call the health URL a few times. A failing smoke test marks the run red so someone notices, instead of "deployed" meaning "started".
  • You can use a ready-made action such as appleboy/ssh-action instead of raw ssh, but any third-party action that receives your key is part of your trusted code; read its README and pin a version.

Option B: deploy hooks and platform integrations

Platforms such as Render give each service a deploy hook: a secret URL that, when called with POST, starts a deploy. Store the URL as a secret and call it after the tests pass:

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - name: Trigger deploy
        env:
          HOOK: ${{ secrets.RENDER_DEPLOY_HOOK_URL }}
        run: curl -fsS -X POST "$HOOK"

Railway, Fly.io, Heroku and others have a CLI or API token you call from a step, or can deploy straight from your GitHub repository on every push to main. If the platform builds from GitHub itself, make sure it waits for your CI checks (most have a "wait for CI" setting) so a failing build is not deployed. Read the platform's current documentation for exact commands; they change often. More on these platforms in Module 5.

Environments, approvals and rollback

A GitHub environment (repository Settings → Environments) such as staging or production can have protection rules: required reviewers (the job pauses until someone approves), a wait timer, and branch restrictions (only main may deploy). It also has its own secrets, so production credentials are available only to jobs that target the production environment. Required reviewers turn continuous deployment into continuous delivery for production: staging deploys automatically, production waits for a click.

Rollback. Because every image has an immutable tag, rolling back means deploying an older one. Add a manual workflow that takes the tag as input (workflow_dispatch with image_tag, see Triggers) and runs the same SSH step with IMAGE_TAG=${{ inputs.image_tag }}. Or revert the bad commit on main and let the pipeline deploy the revert. Database migrations make rollback harder: write backward-compatible migrations (add a column first, remove the old one in a later release).

Mistakes in deployment pipelines

  • Deploying from latest, so you cannot tell or roll back what is running.
  • Using StrictHostKeyChecking=no and a personal SSH key with full access.
  • Printing secrets with echo or set -x in the deploy script.
  • Deploying without a health check, or two deployments overlapping (use the concurrency group).
  • Putting production secrets at repository level where any workflow or branch can use them.

Edge cases

  • Replacing a container causes a few seconds of downtime. For zero downtime you need two instances behind a load balancer, or an orchestrator (Kubernetes, ECS) doing rolling updates.
  • If the server's firewall only allows SSH from your IP, GitHub-hosted runners (many changing IPs) cannot connect. Options: a self-hosted runner, a deploy hook/pull-based deploy, or SSM instead of SSH on AWS.
  • If the image on GHCR is private, the server needs credentials; a failed pull shows as unauthorized in the deploy log.

In real projects

Small teams use exactly this: test, build image, push, SSH or platform deploy, smoke test. Larger teams separate "build" from "deploy": CI publishes a versioned image, and a deployment tool (Argo CD, Spinnaker, AWS CodeDeploy) rolls it out. The idea — immutable artifact, promote the same artifact through environments — stays the same.

Interview: "How does your code get from a merge to production?"

  • Merge to main triggers: tests, Docker build and push (SHA tag), deploy job in the production environment (approval optional), SSH compose pull/up or deploy hook, then a smoke test.
  • Rollback: redeploy the previous tag via workflow_dispatch or revert the commit.

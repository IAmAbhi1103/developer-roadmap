Environment variables and secrets: never put passwords inside images

Configuration and secrets enter a container at run time — through environment variables, an untracked .env file, or Docker/Compose secrets — never through the Dockerfile, because every layer of an image can be read by anyone who can pull it.

Why secrets must stay out of images

An image is a stack of layers, and each layer keeps its files forever. If a Dockerfile does COPY .env . and a later step runs rm .env, the file is still inside the earlier layer. docker history shows every ENV and ARG value. Once the image is pushed to a registry (or shared with a friend), the password is out. Rotating the secret is the only fix. The twelve-factor rule applies: the same image runs in every environment; only the configuration changes.

Wrong: password baked into the image

ENV SPRING_DATASOURCE_PASSWORD=SuperSecret123
ARG GITHUB_TOKEN
RUN git clone https://${GITHUB_TOKEN}@github.com/org/private.git

Right: supplied when the container starts

$ docker run -d --env-file .env shop-api:1.0
# or in compose: env_file / environment / secrets

A .env file is plain text. Keep it in .gitignore and commit an .env.example with fake values so teammates know which variables exist.

# .gitignore
.env
.env.*
!.env.example

# .env.example (safe to commit)
POSTGRES_DB=shop
POSTGRES_USER=shop
POSTGRES_PASSWORD=replace-me
APP_PORT=8080

Docker and Compose secrets (brief)

A secret in Compose is a file that Docker mounts read-only into the container at /run/secrets/<name>. It does not appear in docker inspect or docker history. Many official images accept *_FILE variables so they read the value from such a file.

services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt   # keep this folder out of Git

For Spring Boot, either set spring.config.import=configtree:/run/secrets/ (every file in the folder becomes a property named after the file) or read the file in a small start-up script. Check the Spring Boot reference for "Config Tree" to confirm the property naming for your version.

Build args are not secret

ARG values appear in docker history and in image metadata. For a secret needed only during the build (a token for a private Maven repository), use a BuildKit secret mount, which is never written into a layer:

RUN --mount=type=secret,id=maven_settings,target=/root/.m2/settings.xml \
    mvn -B -q package -DskipTests
$ docker build --secret id=maven_settings,src=$HOME/.m2/settings.xml -t shop-api:1.0 .

Finding leaked secrets

  • Run a scanner such as gitleaks or trufflehog on the repository (and in CI). GitHub's secret scanning and push protection catch many token formats automatically.
  • Check an image: docker history --no-trunc shop-api:1.0 and docker run --rm -it --entrypoint sh shop-api:1.0, then look for .env, key files and passwords.
  • If a secret was ever committed or pushed in an image: rotate it. Deleting the file in a later commit does not remove it from history.

Rule: one image, many environments

Do not build a "production image" with production settings inside. Build once, tag, and deploy the same image to test and production with different environment variables and secrets.

Mistake: committing .env, or a fallback password in application.yml

A line like spring.datasource.password=${DB_PASSWORD:admin123} silently ships a default password. Prefer failing at start-up when the variable is missing: ${DB_PASSWORD} with no default in production profiles.

Edge cases

  • Environment variables are visible to anyone who can run docker inspect or read /proc/<pid>/environ, and Spring's Actuator /env endpoint (mask values and never expose it publicly).
  • Do not log the full environment or configuration on start-up.
  • A .env file used by Compose does not pass every variable into the container; only the ones you list under environment (or load with env_file) reach it.

Interview: "How do you handle secrets with Docker?"

  • Never in the Dockerfile, image or Git. Inject at runtime via env vars, env files, Docker secrets or a secret manager.
  • ARG/ENV are visible in docker history; use BuildKit secret mounts for build-time secrets; rotate anything that leaked.

Registries: Docker Hub, GHCR, tagging, pushing and image scanning

A registry stores images; log in with docker login, tag the image with the registry path and a version or git SHA, then docker push and docker pull — Docker Hub is the public default, GitHub Container Registry (ghcr.io) fits projects hosted on GitHub.

Other registries you will meet: AWS ECR (see Cloud), Google Artifact Registry, Azure Container Registry, and self-hosted ones like Harbor or Nexus. They all speak the same protocol, so the commands are identical.

Tagging strategy

Give each build an immutable, traceable tag and optionally move a friendly tag:

  • shop-api:3f9c2ab — the short git commit SHA. Unique per commit; tells you exactly which code runs. Best for CI deploys.
  • shop-api:1.2.0 — a semantic version for releases. Never overwrite it.
  • shop-api:1.2, shop-api:1 — movable convenience tags for "latest patch".
  • shop-api:latest — optional alias for the newest build; do not deploy production from it.

Login, tag, push, pull

$ docker login                        # asks for username and an access token (not your password)
$ docker build -t shop-api:1.2.0 .
$ docker tag shop-api:1.2.0 asha/shop-api:1.2.0
$ docker tag shop-api:1.2.0 asha/shop-api:latest
$ docker push asha/shop-api:1.2.0
The push refers to repository [docker.io/asha/shop-api]
1.2.0: digest: sha256:4f2a... size: 1789
$ docker pull asha/shop-api:1.2.0    # on the server
$ echo "$GHCR_TOKEN" | docker login ghcr.io -u asha --password-stdin
$ docker tag shop-api:1.2.0 ghcr.io/asha/shop-api:1.2.0
$ docker push ghcr.io/asha/shop-api:1.2.0

docker tag does not copy anything; it adds another name to the same image id. --password-stdin keeps the token out of your shell history and process list. Always use an access token (revocable, limited scope) instead of your account password. In CI the workflow logs in with secrets (next module).

Image scanning (brief)

Images include an OS and libraries, which may contain known vulnerabilities (CVEs). Scanners compare the image contents with vulnerability databases. Docker Scout is built into Docker Desktop and the CLI; Trivy and Grype are popular open-source scanners.

$ docker scout quickview shop-api:1.2.0     # summary of CVEs by severity
$ docker scout cves shop-api:1.2.0          # detailed list
$ trivy image shop-api:1.2.0                # if Trivy is installed

Fix findings by updating the base image tag (rebuild regularly to get patched layers), upgrading dependencies and using smaller bases. Run a scan in CI and fail the build on critical issues that have a fix available.

Convention: tag by SHA in CI, by version on release

Pipelines push :<git-sha> on every merge to main; a release tag (v1.2.0) also pushes :1.2.0. Deployments reference the exact tag, which makes rollback a matter of deploying the previous tag.

Mistake: denied: requested access to the resource is denied

Pushing shop-api:1.0 without your namespace tries to write to docker.io/library/shop-api. Tag it as youruser/shop-api:1.0. Also check that you are logged in to the right registry and that the token has write access.

Edge cases

  • Anonymous pulls from Docker Hub are rate-limited; you may see toomanyrequests on shared CI runners. Log in before pulling, or mirror base images to your own registry.
  • Pushing a tag that already exists silently moves it; the old image becomes untagged ("dangling").
  • A GHCR package that you push from a workflow may be private by default; link it to the repository and set visibility in the package settings.
  • exec format error on a server usually means the image was built for another CPU architecture. Build multi-platform with docker buildx build --platform linux/amd64,linux/arm64.

Interview: "How do you version and publish Docker images?"

  • Build once in CI, tag with the git SHA (and semver on release), push to a registry (GHCR/ECR/Hub), deploy by tag; never deploy latest.
  • Log in with a token; scan for CVEs; use digests for strict reproducibility.

Troubleshooting Docker: the usual problems and how to fix them

Most Docker problems fall into a few patterns: read the logs first (docker logs), then the exit code and the state (docker inspect), then check ports, names and permissions.

A debugging routine

  1. docker ps -a — is the container running, or did it exit? Note the status and exit code.
  2. docker logs --tail 100 name — the app's stack trace is usually here.
  3. docker inspect name — State.ExitCode, State.OOMKilled, the environment, mounts and network.
  4. docker exec -it name sh — look around inside (if it is still running); try curl to the other service by name.
  5. If it will not start: docker run --rm -it --entrypoint sh image to get a shell in a fresh container and run the start command by hand.
  6. Compose: docker compose ps, docker compose logs -f, docker compose config.

Tip: keep a throw-away debug container on the network

docker run --rm -it --network shop-net nicolaka/netshoot (or a plain alpine with apk add curl bind-tools) lets you test DNS and ports from inside the same network: nslookup postgres, nc -zv postgres 5432. Production images often have no such tools, which is why this helps.

Mistake: fixing the symptom with --privileged or root

Running containers with --privileged, as root, or mounting the Docker socket (/var/run/docker.sock) "to make it work" gives the container control of the host. Find the real cause (usually file ownership or a missing option).

Interview: "A container exits immediately after starting. How do you debug it?"

  • docker ps -a and docker logs for the error; docker inspect for exit code (137 = killed/OOM, 1 = app error).
  • Run the image with a shell entrypoint to start the app manually; check the JAR path, env vars and the Java version.

Interview questions — Docker

What is Docker and why do we use containers?

Docker packages an application with its runtime and dependencies into an image that runs the same everywhere as a container. It solves "works on my machine", gives isolation between apps, starts in seconds, and is the standard deployment unit for cloud platforms and Kubernetes.

Container versus virtual machine?

A VM runs a full guest OS with its own kernel on a hypervisor; a container is an isolated process sharing the host kernel. Containers are smaller (MBs), start in about a second and pack more density; VMs isolate more strongly. In the cloud, containers usually run inside VMs.

What is a container really, at the kernel level?

A normal Linux process with namespaces (own process IDs, network, hostname, mounts) and cgroups (limits for CPU, memory, I/O), running on a layered filesystem created from an image. Docker is a tool that sets these features up.

Image versus container? What are layers and why do they matter?

An image is a read-only template; a container is a running instance with a thin writable layer. Each filesystem-changing Dockerfile instruction creates a layer. Layers are cached and shared, so ordering instructions from least to most frequently changing makes rebuilds fast and downloads small.

Explain ENTRYPOINT versus CMD, and shell form versus exec form.

ENTRYPOINT is the fixed executable; CMD supplies default arguments that docker run image args replaces. Exec form (JSON array) runs the program directly as PID 1 so it gets SIGTERM and can shut down gracefully; shell form wraps it in sh -c, and signals may not reach the app.

How do you make a Docker image for a Spring Boot app small and fast to build?

Use a multi-stage build: Maven/JDK stage builds the JAR (copy pom.xml and resolve dependencies first so they are cached), runtime stage uses a JRE image and copies only the JAR. Add .dockerignore, run as a non-root user and consider layered JARs. Final images are a few hundred MB instead of 700 MB+.

What is the difference between COPY and ADD, ARG and ENV, EXPOSE and -p?

ADD also extracts local archives and fetches URLs; prefer COPY. ARG exists only at build time; ENV persists into the running container. EXPOSE only documents a port; -p host:container (or compose ports) actually publishes it.

Data in a container disappears when it is removed. How do you persist it?

Mount a named volume at the data directory (-v pgdata:/var/lib/postgresql/data). A bind mount maps a host folder and suits development. tmpfs is memory only. Volumes survive docker rm and docker compose down, but not down -v.

Your Spring Boot container throws "Connection refused" for localhost:5432. Why?

localhost inside a container is the container itself, not the host or the database container. Put both on the same user-defined network (Compose does this) and connect to the service name: jdbc:postgresql://postgres:5432/shop. Also make sure the database is healthy before the app starts.

What does depends_on do in Compose? How do you wait for the database?

By default only start order: the dependency container has started, not that it accepts connections. Add a healthcheck (pg_isready) to the database and depends_on: postgres: condition: service_healthy to the app so it starts when the database is truly ready.

How do you handle secrets in Docker?

Never bake them into images or commit .env. Inject at runtime with environment variables, an untracked env file, Docker/Compose secrets (files under /run/secrets) or a secret manager. ENV and ARG are visible in docker history. Use BuildKit secret mounts for build-time secrets and rotate anything that leaked.

How does the JVM behave in a container? What is MaxRAMPercentage?

Modern JVMs read cgroup limits for memory and CPUs. The default max heap is 25% of the container memory. -XX:MaxRAMPercentage=75 sets it as a share of the limit, leaving room for metaspace, stacks and native memory. Always set a container memory limit; exit code 137 with OOMKilled means the total exceeded it.

docker stop versus docker kill, and docker run versus docker exec?

stop sends SIGTERM, waits 10 seconds by default, then SIGKILL; kill sends SIGKILL immediately. run creates a new container from an image; exec runs an additional process inside an already running container.

Why not use the latest tag in production? How do you tag images?

latest is a movable label; a rebuild can change the Java version or dependencies without notice, and you cannot tell what is deployed or roll back. Tag with the git SHA and a semantic version, deploy by explicit tag (or digest), and roll back by redeploying the previous tag.

Your image is 1.2 GB. How do you find out why and reduce it?

Run docker history image to see layer sizes. Typical causes: JDK and Maven in the final image, a big base, build output and caches, or a missing .dockerignore. Fix with a multi-stage build, a JRE-only base (or slim/Alpine after testing), cleaning in the same RUN and excluding files from the context.

Cheat sheet — Docker

  • Container vs VM shared kernel + namespaces and cgroups vs full guest OS on a hypervisor
  • Image / container / registry template / running instance + writable layer / image store
  • Layers one per RUN, COPY, ADD; cached by content; a changed layer rebuilds all after it
  • Tags name:tag; pin versions, tag with git SHA or semver, avoid latest in prod
  • Java base eclipse-temurin:21-jre to run, maven:3.9-eclipse-temurin-21 to build
  • docker run -d -p 8081:8080 --name n -e K=v --env-file f -v vol:/path --rm --network net --restart unless-stopped
  • Look docker ps -a, logs -f --tail 100, inspect, stats
  • Get inside docker exec -it name sh; new container: docker run --rm -it --entrypoint sh image
  • Stop / remove stop (SIGTERM, 10 s) vs kill (SIGKILL); rm, rmi
  • Clean up docker system df, system prune; --volumes deletes data
  • Build docker build -t name:tag .; --no-cache to ignore the cache
  • Dockerfile order FROM, WORKDIR, COPY pom.xml, RUN deps, COPY src, RUN package, then runtime stage
  • Exec form ENTRYPOINT ["java","-jar","app.jar"] so Java is PID 1 and gets SIGTERM
  • ENTRYPOINT vs CMD fixed executable vs overridable default arguments
  • Best practice multi-stage, .dockerignore, non-root USER, one process, no secrets, pinned versions
  • JVM -XX:MaxRAMPercentage=75, always set a memory limit; exit 137 + OOMKilled = over limit
  • Volumes named volume for data, bind mount for dev files, tmpfs for RAM; down -v deletes volumes
  • Networks user-defined bridge gives DNS by name; compose creates one automatically
  • localhost trap inside a container localhost is itself; use postgres:5432, not localhost
  • Ports host:container; containers talk internally without published ports
  • Compose up -d --build, ps, logs -f, exec, down, config
  • Wait for DB healthcheck (pg_isready) + depends_on: condition: service_healthy
  • Spring env vars SPRING_DATASOURCE_URL = spring.datasource.url; SPRING_DATA_REDIS_HOST
  • Secrets never in image or Git; env file (untracked), Docker secrets, secret manager; ARG is not secret
  • Registry docker login, tag, push, pull; GHCR: ghcr.io/owner/app

Practice — Docker

  1. First containers. Install Docker Desktop (WSL2 backend), run hello-world, then docker run --rm -it eclipse-temurin:21-jdk jshell. Run nginx with -p 8081:80 and open it in the browser; view its logs, enter it with exec, stop and remove it. Done when you can list, stop and remove containers without looking anything up.
  2. Persist a database. Start PostgreSQL with a named volume, create a table, remove the container, start a new one with the same volume and check that the data is still there. Then run down -v style cleanup and watch it disappear. Done when you can explain which commands delete data.
  3. Dockerize Project 2 (single stage first). Write a simple Dockerfile (JDK image, copy the JAR, ENTRYPOINT) and run it. Note the image size with docker images. Done when the app answers on localhost:8080.
  4. Multi-stage build. Rewrite it as the multi-stage Dockerfile from this module (Maven stage, JRE stage, non-root user, healthcheck) and add a .dockerignore. Compare image size with step 3 and time a second build after changing one line of code to see the cache work. Done when the final image is clearly smaller and the second build skips the dependency download.
  5. Break the localhost trap. Run PostgreSQL and your app in two containers with the datasource URL set to localhost; read the error. Create a network, use the container name, and fix it. Done when you can explain the error to someone in two sentences.
  6. Compose the stack. Write a compose.yaml with the API, PostgreSQL and Redis, a .env file (git-ignored) and .env.example, named volumes and healthchecks with service_healthy. Run docker compose up -d --build and check docker compose ps shows all healthy. Done when a fresh clone plus one command starts the whole app.
  7. JVM limits. Run the container with -m 512m and -XX:MaxRAMPercentage=75, watch docker stats, then try a very low limit (-m 128m) and find the exit code and the OOMKilled flag. Done when you can explain exit code 137.
  8. Secrets audit. Run docker history --no-trunc on your image and look for anything sensitive; scan the repository with gitleaks and the image with docker scout cves. Move any secret to an env file or Compose secret. Done when no password exists in the Dockerfile, the compose file or the image.
  9. Publish the image. Create a Docker Hub (or GHCR) access token, log in with --password-stdin, tag the image with a version and the git SHA, push it, then pull and run it from a different folder or machine. Done when the pulled image runs with only environment variables supplied.
  10. Final check (roadmap goal). Without notes, write a Dockerfile and a docker-compose.yml from scratch for Spring Boot + PostgreSQL, bring it up, and fix one deliberately introduced fault (wrong host name, missing healthcheck or wrong port). Done when you can do this in under 30 minutes.

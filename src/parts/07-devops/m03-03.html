Volumes, bind mounts and keeping data safe

A container's own filesystem disappears with the container; use a named volume for data that must survive (database files), a bind mount to share a host folder (source code, config), and remember that docker compose down -v deletes volumes.

The problem: containers are disposable

Remove a PostgreSQL container and all its tables are gone, because they lived in the container's writable layer. Containers should be disposable — you replace them on every release — so data that matters must live outside the container's own filesystem. Docker offers three ways to mount storage:

Persisting PostgreSQL data

$ docker volume create pgdata
$ docker run -d --name pg -e POSTGRES_PASSWORD=devpass \
    -v pgdata:/var/lib/postgresql/data postgres:16
$ docker exec -it pg psql -U postgres -c "CREATE TABLE t(id int); INSERT INTO t VALUES (1);"
$ docker rm -f pg                        # container gone ...
$ docker run -d --name pg2 -e POSTGRES_PASSWORD=devpass \
    -v pgdata:/var/lib/postgresql/data postgres:16
$ docker exec -it pg2 psql -U postgres -c "SELECT * FROM t;"
 id
----
  1
(1 row)

The data survived because the volume pgdata was mounted at the directory where PostgreSQL stores its files. If you mount a volume with a name that does not exist, Docker creates it. If you use a volume for a database, use the data directory documented on the image's Docker Hub page (/var/lib/postgresql/data for the official PostgreSQL image; MySQL uses /var/lib/mysql).

PostgreSQL 18 image path change

Check the image page for newer major versions: some recent PostgreSQL images changed the recommended mount point (for example to /var/lib/postgresql for 18+). Always read the "PGDATA" notes for the exact tag you use, otherwise your data may not land in the volume. For postgres:16 the path above is correct.

Bind mounts for development

$ docker run -d --name shop-api -p 8080:8080 \
    -v "$(pwd)/config/application-prod.yml:/app/config/application-prod.yml:ro" \
    -v "$(pwd)/uploads:/app/uploads" \
    shop-api:1.0

The suffix :ro makes the mount read-only inside the container. Spring Boot automatically reads ./config/application*.yml relative to its working directory, so a mounted /app/config folder overrides settings without rebuilding the image. In compose files use relative paths such as ./config:/app/config.

Managing volumes

$ docker volume ls
$ docker volume inspect pgdata        # shows the Mountpoint on the host
$ docker volume rm pgdata             # fails if a container still uses it
$ docker volume prune                 # remove volumes no container uses (data loss!)

Backing up a volume (brief)

For databases, prefer a logical backup that the database understands. For any volume, you can archive it with a throw-away container that mounts both the volume and a host folder:

$ docker exec pg pg_dump -U postgres shop > shop-backup.sql          # logical dump
$ docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine \
    tar czf /backup/pgdata.tar.gz -C /data .                         # raw copy (stop the DB first)
$ docker exec -i pg psql -U postgres shop < shop-backup.sql          # restore a dump

A raw copy of a running database's files may be inconsistent; stop the database first or use pg_dump. Real production databases normally run outside Docker, as managed services (Amazon RDS) with automated backups.

Mistake: docker compose down -v wipes your database

docker compose down removes containers and networks but keeps named volumes. docker compose down -v also deletes the volumes. People run it to "clean up" and lose the local database; on a server it would be a disaster. Likewise docker system prune --volumes and docker volume prune. Use -v deliberately, only when you want a fresh database.

Edge cases

  • An anonymous volume (-v /var/lib/data with no name) is created on each run with a random name, and silently piles up. Always name volumes.
  • A bind mount hides whatever the image had at that path. Mounting an empty host folder over /app hides your JAR.
  • Permission denied on a mounted folder: the container user's UID (a non-root spring user) must have rights to the host folder. On Linux fix with chown or --user; Docker Desktop on Windows/Mac usually hides this problem, which then appears on the Linux server.
  • The first start of the PostgreSQL image runs *.sql and *.sh files from /docker-entrypoint-initdb.d, but only when the data directory is empty.

Interview: "How do you persist database data in Docker?"

  • Mount a named volume at the database's data directory; the volume outlives the container.
  • Volume versus bind mount: Docker-managed and portable versus a host path for dev.
  • Know down -v deletes volumes; back up with pg_dump.

Docker networks and the localhost trap

Containers on the same user-defined network reach each other by name (Docker's built-in DNS); inside a container localhost means that container itself, so a Spring Boot container must connect to the database at postgres:5432, not localhost:5432.

Network drivers in practice

Docker gives every container a virtual network interface. The default and most common driver is bridge: a private virtual switch inside the host, with its own subnet (for example 172.17.0.0/16). Containers on it get private IPs and reach the internet through NAT (see Networking).

NetworkBehaviour
Default bridgeEvery container joins it if you say nothing. Containers can reach each other by IP only, no names.
User-defined bridgeYou create it (docker network create shop-net). Adds DNS by container name and better isolation. Compose creates one for you.
hostContainer shares the host's network stack; no port mapping. Linux only in practice.
noneNo networking.

Name resolution on a user-defined network

$ docker network create shop-net
$ docker run -d --name postgres --network shop-net \
    -e POSTGRES_PASSWORD=devpass -e POSTGRES_DB=shop postgres:16
$ docker run -d --name shop-api --network shop-net -p 8080:8080 \
    -e SPRING_DATASOURCE_URL=jdbc:postgresql://postgres:5432/shop \
    -e SPRING_DATASOURCE_USERNAME=postgres \
    -e SPRING_DATASOURCE_PASSWORD=devpass \
    shop-api:1.0
$ docker exec shop-api getent hosts postgres      # (if the image has getent)
172.18.0.2      postgres

Docker runs an embedded DNS server (at 127.0.0.11 inside the container) that resolves a container's name, and in compose also its service name, to its IP on that network. The IP changes when the container is recreated, but the name does not, so always use names.

The localhost trap

Each container has its own network namespace, so localhost (127.0.0.1) inside the Spring Boot container is the Spring Boot container. If your datasource URL is jdbc:postgresql://localhost:5432/shop, the app looks for PostgreSQL inside its own container, finds nothing, and fails:

org.postgresql.util.PSQLException: Connection to localhost:5432 refused.
Check that the hostname and port are correct and that the postmaster is accepting TCP/IP connections.
Caused by: java.net.ConnectException: Connection refused

Wrong: localhost points at the app's own container

SPRING_DATASOURCE_URL: jdbc:postgresql://localhost:5432/shop

Right: use the service name on the shared network

SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/shop

It works on your laptop when you run the app from the IDE because there localhost is the host, where the database port is published. The same value fails inside a container. The fix is not "publish more ports" but "use the service name". This is the number one Docker bug in Spring Boot projects: whenever you see connection refused between containers, check the host name first.

Publishing ports versus internal communication

  • -p 8080:8080 (or compose ports) opens a port on the host for people and tools outside Docker: the browser, curl, an IDE database client.
  • Containers on the same network need no published ports to talk. The app reaches postgres:5432 directly. Do not publish the database port on a server unless you need it; leaving it unpublished means the internet cannot reach it at all.
  • The port on the right of host:container is the container's port, the one used inside the network. Mapping 5433:5432 changes only what the host sees; containers still use 5432.

Reaching the host from a container

Sometimes the app in a container must call something running on your machine (a database you installed locally). Docker Desktop provides the special name host.docker.internal that resolves to the host. On Linux Engine you add it yourself: docker run --add-host=host.docker.internal:host-gateway … (in compose: extra_hosts: ["host.docker.internal:host-gateway"]). Use it only for development; production services should be containers or managed services on a real network.

Network commands

$ docker network ls
$ docker network inspect shop-net      # subnet, attached containers and their IPs
$ docker network connect shop-net pg   # attach a running container
$ docker network rm shop-net

Rule: the app inside Docker must bind to 0.0.0.0, and call others by service name

Spring Boot listens on all interfaces by default, so published ports work. If you set server.address=127.0.0.1 (as on a bare-metal server behind Nginx), a published port in Docker will not reach the app; leave it unset in containers.

Edge cases

  • On the default bridge there is no name resolution; --link is legacy. Use a user-defined network (compose does this automatically).
  • Two compose projects get separate networks, so their services cannot see each other unless you attach both to an external network.
  • Publishing -p 5432:5432 on a cloud server exposes PostgreSQL to the internet. Docker writes its own firewall rules, so ufw rules may not block published ports.

Interview: "Spring Boot in Docker cannot connect to PostgreSQL. Why?"

  • Usually the URL uses localhost, which is the container itself; use the service name (postgres) on a shared network.
  • Also check: same network, database healthy before the app starts, correct credentials, and the container's port (5432), not the host-mapped one.

Docker Compose: Spring Boot, PostgreSQL and Redis with one command

A compose.yaml file describes all your containers, networks and volumes; docker compose up -d --build builds and starts the whole stack, and depends_on with condition: service_healthy makes the app wait until the database is really ready.

What Compose is for

A real app is several containers: the API, a database, a cache, maybe Nginx. Starting them with long docker run commands is error-prone. Docker Compose lets you declare them once in YAML and manage them together. The file is named compose.yaml (older name docker-compose.yml also works), and the command is docker compose (a space; the old standalone tool was docker-compose with a hyphen). A top-level version: key is obsolete in current Compose and can be left out.

File structure

KeyPurpose
servicesThe containers; each key is a service name (also its DNS name)
image / buildUse a ready image, or build from a Dockerfile (build: .)
portsPublish "host:container" ports
environment / env_fileVariables, inline or from a file
volumesMount named volumes or host paths
networksAttach to networks (default one is created automatically)
depends_onStart order; with condition also wait for health
healthcheckCommand that tells Docker if the service is ready
restartRestart policy: no, on-failure, always, unless-stopped
volumes / networks (top level)Declare the named volumes and networks used above

A complete stack: Spring Boot + PostgreSQL + Redis

Project layout:

shop-api/
  Dockerfile
  compose.yaml
  .env              (not committed)
  .env.example      (committed: names only, fake values)
  pom.xml
  src/
POSTGRES_DB=shop
POSTGRES_USER=shop
POSTGRES_PASSWORD=change-me-locally
APP_PORT=8080
services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped

  redis:
    image: redis:7
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped

  api:
    build: .
    image: shop-api:dev
    ports:
      - "${APP_PORT}:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/${POSTGRES_DB}
      SPRING_DATASOURCE_USERNAME: ${POSTGRES_USER}
      SPRING_DATASOURCE_PASSWORD: ${POSTGRES_PASSWORD}
      SPRING_DATA_REDIS_HOST: redis
      SPRING_DATA_REDIS_PORT: "6379"
      SPRING_PROFILES_ACTIVE: prod
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    restart: unless-stopped

volumes:
  pgdata:
  redisdata:

What each part does

Service names
postgres, redis, api are also the host names on the automatic default network. That is why the datasource URL uses postgres.
${POSTGRES_DB}
Compose reads a .env file in the same folder and substitutes ${VAR} in the YAML. You can set a default with ${VAR:-value} or require a value with ${VAR:?error message}.
image: postgres:16
A pinned version, not latest.
volumes: pgdata:/var/lib/postgresql/data
The named volume holds the database. It is declared in the top-level volumes: block.
healthcheck (postgres)
pg_isready exits 0 once PostgreSQL accepts connections. Compose runs it every 5 s; after enough passes the service state becomes healthy.
healthcheck (redis)
redis-cli ping returns PONG when Redis is ready.
build: .
Builds the API image from the Dockerfile in this folder (the multi-stage one from before). image: shop-api:dev names the result.
ports: "${APP_PORT}:8080"
Only the API is published. PostgreSQL and Redis are reachable from the API through the network but not from outside.
SPRING_DATASOURCE_URL …
Spring Boot's relaxed binding maps the environment variable SPRING_DATASOURCE_URL to the property spring.datasource.url (upper case, dots become underscores). No code change needed.
SPRING_DATA_REDIS_HOST
Property spring.data.redis.host.
depends_on … service_healthy
Start the API only after PostgreSQL and Redis report healthy. Plain depends_on: [postgres] waits only until the container has started, which is long before the database accepts connections.
restart: unless-stopped
Containers come back after a crash or a server reboot.

Spring Boot version differences

Spring Boot 3.x and 4.x use spring.data.redis.*. Boot 2.x used spring.redis.* (so SPRING_REDIS_HOST). Schema changes: set SPRING_JPA_HIBERNATE_DDL_AUTO=validate and use Flyway or Liquibase in production.

Compose commands

$ docker compose up -d --build        # build images if needed, start everything in the background
$ docker compose ps                   # status, ports and health of each service
NAME            SERVICE    STATUS                  PORTS
shop-api-api-1  api        Up 25 seconds           0.0.0.0:8080->8080/tcp
shop-api-postgres-1  postgres   Up 40 seconds (healthy)   5432/tcp
shop-api-redis-1     redis      Up 40 seconds (healthy)   6379/tcp
$ docker compose logs -f api          # follow one service's logs
$ docker compose exec postgres psql -U shop -d shop
$ docker compose up -d --build api    # rebuild and recreate only the API
$ docker compose restart api
$ docker compose down                 # stop and remove containers and the network; keep volumes
$ docker compose down -v              # ALSO delete volumes (database data!)
$ docker compose config               # print the final file with variables substituted

docker compose config is the quickest way to check that variables from .env were substituted as you expected. Compose names containers <project>-<service>-<number>; the project name defaults to the folder name (override with -p or a top-level name:).

Overriding files and profiles (brief)

  • Override files. Compose automatically merges compose.yaml with compose.override.yaml if it exists — handy for developer-only settings (publishing the DB port, bind-mounting code). For production use explicit files: docker compose -f compose.yaml -f compose.prod.yaml up -d. Later files override earlier ones.
  • Profiles. Add profiles: ["tools"] to a service (for example pgAdmin); it starts only with docker compose --profile tools up.
services:
  postgres:
    ports:
      - "127.0.0.1:5432:5432"     # let my IDE reach the database
  pgadmin:
    image: dpage/pgadmin4:latest
    profiles: ["tools"]
    environment:
      PGADMIN_DEFAULT_EMAIL: dev@example.com
      PGADMIN_DEFAULT_PASSWORD: devonly
    ports:
      - "5050:80"

Mistake: the app starts before the database is ready

Without a healthcheck and condition: service_healthy, the API starts at the same time as PostgreSQL, tries to connect for the first time during DB initialisation and crashes with Connection refused. restart: unless-stopped may hide it by retrying, but the proper fix is the healthcheck. Spring's own retries (for example spring.datasource.hikari initialisation) are not a substitute.

Mistake: YAML indentation and quoting

  • Use spaces, never tabs; two spaces per level; list items start with - .
  • Quote port mappings ("8080:8080"): YAML can read unquoted xx:yy numbers below 60 as base-60 numbers.
  • In environment: map form write KEY: value; in list form - KEY=value. Do not mix.

Edge cases

  • depends_on only controls start order at up; if PostgreSQL restarts later, the API is not restarted. The app must handle reconnects (HikariCP does).
  • Changing a .env value does not recreate containers by itself; run docker compose up -d again.
  • Changing POSTGRES_PASSWORD after the volume exists has no effect: the database was initialised with the old one. Remove the volume (down -v) in dev, or change the password inside the database.

In real projects

The same compose.yaml is used on a developer laptop and on a small single-server production (an EC2 instance that runs docker compose pull && docker compose up -d; see CD over SSH). Larger systems move to Kubernetes or ECS, but the concepts — services, networks, volumes, health — carry over.

Interview: "How do you run Spring Boot with PostgreSQL in Docker?"

  • Compose file with three services, a named volume for the DB, and env vars with service names.
  • Healthcheck + condition: service_healthy so the app waits; publish only the API port.
  • up -d --build, logs -f, down (not down -v).

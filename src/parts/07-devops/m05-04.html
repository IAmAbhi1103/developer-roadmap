AWS services glossary: what the other names mean

AWS has hundreds of services, but a Java backend developer meets about twenty; this glossary gives one line for each and shows how they fit into a typical production setup.

Networking

VPC
Virtual Private Cloud: your own isolated network inside a region, with an IP range you choose. Every EC2 and RDS instance lives in one. New accounts get a default VPC.
Subnet
A slice of the VPC's IP range that lives in one availability zone. A public subnet has a route to the internet gateway; a private subnet does not (databases go here).
Internet gateway / NAT gateway
The internet gateway connects a VPC to the internet. A NAT gateway lets private machines make outbound calls only; it is billed per hour and per GB, a famous surprise cost.
Security group
The stateful firewall around an instance, as in the EC2 article.
ELB / ALB
Elastic Load Balancing. The Application Load Balancer spreads HTTP(S) traffic across several servers in different zones, checks their health, and can terminate TLS.
Route 53
AWS's DNS service (and domain registrar). It can send users to a load balancer, CloudFront or an IP.
CloudFront
The CDN: caches content at edge locations close to users and serves it over HTTPS.

Compute and containers

ECR
Elastic Container Registry: AWS's private Docker image registry (like GHCR).
ECS
Elastic Container Service: AWS's own container orchestrator. You describe tasks and services; it runs and replaces containers.
Fargate
A mode where ECS (or EKS) runs your containers without you managing any EC2 servers.
EKS
Elastic Kubernetes Service: managed Kubernetes (see Module 6).
Elastic Beanstalk
A PaaS on AWS: upload a JAR or container, and it creates the servers, load balancer and scaling for you. Quick, but less flexible and less modern than ECS.
Lambda
Serverless functions: upload code, AWS runs it on demand, billed by calls and duration. Good for events and small tasks; Spring Boot cold starts need care.

Data and messaging

EBS / EFS
EBS is a block disk for one instance; EFS is a shared network file system.
DynamoDB
A managed NoSQL key-value and document database with very fast, predictable access.
SQS
Simple Queue Service: a managed message queue for decoupling services.
SNS
Simple Notification Service: publish a message and fan it out to emails, SMS, queues or HTTP endpoints. Budget alerts use it.
SES
Simple Email Service: send application emails (OTP, invoices). New accounts start in a sandbox with limits; you request production access.

Security, secrets and operations

IAM
Users, roles and policies (IAM article).
Secrets Manager
Stores secrets (database passwords, API keys), encrypts them, controls access with IAM, and can rotate some automatically. It is a paid service.
Systems Manager Parameter Store
Stores configuration values and secrets (as SecureString), simpler than Secrets Manager. Spring Cloud AWS can load them as properties.
ACM
AWS Certificate Manager: free public TLS certificates for load balancers and CloudFront.
CloudWatch
Logs, metrics, dashboards and alarms for AWS resources and your app. Set a retention period on log groups, or they grow forever.
CloudTrail
The audit log of API calls: who did what, when.

How they fit together

In a production layout the app servers (EC2 or Fargate containers) sit in private subnets behind the load balancer in public subnets; CloudWatch collects logs and alarms; ECR holds the images; Secrets Manager holds the database password; IAM roles tie it together. You do not need all of this for Project 3, but you should be able to draw it and say what each box does.

What to learn first

PriorityServices
MustEC2, security groups, EBS, IAM, S3, RDS, Route 53 basics, CloudWatch basics
Good to knowVPC and subnets, ALB, CloudFront, ECR, Secrets Manager / Parameter Store, SES

Tip: learn the shape, not the console

The console changes layout often and every service has dozens of settings. Learn what each service is for and what a typical architecture looks like. Look up the exact buttons in the current documentation when you need them.

Interview: "Draw the AWS architecture for a Spring Boot web app."

  • Route 53 → (CloudFront for static) → ALB in public subnets → app servers/containers in private subnets across two AZs → RDS Multi-AZ in private subnets; S3 for files; IAM roles; CloudWatch; ECR for images; Secrets Manager.
  • Explain which parts are public and which are private, and why.

Render and Railway: deploying Spring Boot without managing servers

Render and Railway build your repository (from a Dockerfile) on every push, run it behind HTTPS with a public URL, inject environment variables, and offer managed PostgreSQL, so you deploy a backend in minutes with no SSH or Nginx.

What these platforms do for you

A PaaS such as Render or Railway replaces most of the runbook you just read. You connect a GitHub repository; the platform builds the image, runs the container, gives it an https://… URL with a certificate, restarts it if it crashes, keeps logs, and lets you attach a database. The price of the convenience is less control, platform-specific settings, and cost that grows faster than a self-managed server at scale. They are excellent for portfolio projects, demos and small startups.

Plans, free tiers, credits, sleep behaviour and prices change often. Read each platform's current pricing and docs before choosing, and do not assume a free plan fits a Spring Boot app, which needs more memory than a small Node service.

Deploy on Render

  1. Push your project (with the multi-stage Dockerfile from Module 3) to GitHub.
  2. In Render choose New → Web Service → connect the repository. For a Java project the safest choice is the Docker runtime so Render uses your Dockerfile (check the docs for any native Java build option).
  3. Pick the region nearest your users and an instance type. If your repository holds several projects, set the root directory.
  4. Add environment variables (see below).
  5. Set the health check path to /actuator/health, so Render only sends traffic to a started app.
  6. Create the service; watch the build and deploy logs. Later pushes to the branch redeploy automatically.

Create a PostgreSQL database in the same region from the dashboard. It shows an internal connection address (for services in the same region and account) and an external one (for your laptop). Use the internal address from your service.

Deploy on Railway

  1. New project → Deploy from GitHub repo. Railway looks for a Dockerfile; without one, it tries to detect a Maven or Gradle project and build it automatically. A Dockerfile gives the most predictable result.
  2. Add a PostgreSQL service to the project from the dashboard.
  3. In your service's Variables tab, set variables. Railway lets one service reference another's variables (for the database host, port and password), so you do not copy secrets by hand; read its docs for the exact reference syntax.
  4. Generate a public domain for the service in its Networking settings.

Spring Boot settings that platforms need

Two things trip up most first deployments.

1. The port. The platform tells the app which port to listen on through the PORT environment variable. Make Spring Boot use it, with 8080 as the default for local runs:

server.port=${PORT:8080}
server.forward-headers-strategy=framework

spring.datasource.url=jdbc:postgresql://${DB_HOST}:${DB_PORT:5432}/${DB_NAME}
spring.datasource.username=${DB_USER}
spring.datasource.password=${DB_PASSWORD}
spring.jpa.hibernate.ddl-auto=validate

management.endpoints.web.exposure.include=health,info
management.endpoint.health.probes.enabled=true

2. The database URL. Platforms often give a URL like postgres://user:password@host:5432/dbname. The JDBC driver does not understand that form: it needs jdbc:postgresql://host:5432/dbname with user and password given separately. So copy the host, port, name, user and password into separate variables as above (many platforms show them separately, or you can split the URL yourself). If the platform offers a ready-made JDBC URL, use it.

Free plans, sleeping and cold starts

Some platforms put free services to sleep after a period without traffic, and wake them on the next request. A Spring Boot app takes many seconds to start, so the first visitor waits a long time (and a browser or proxy may time out). Free databases may also expire or have strict limits. These terms change, so read the current plan details. Acceptable for a demo, not for a real customer. Workarounds such as pinging the app every few minutes may break the platform's rules or use up your quota; paid plans remove sleeping. For job interviews, tell the interviewer the first load may be slow and why.

Auto-deploy, CI and rollback

By default the platform deploys on every push to the chosen branch, even if your tests fail. Fix that by turning on "wait for CI to pass" if the platform offers it, or by turning auto-deploy off and calling the platform's deploy hook from your pipeline after tests succeed (see the Render example in the CD article). Both platforms keep earlier deployments and let you roll back to one from the dashboard.

Mistakes

  • Hard-coding server.port=8080: the platform's health check never reaches the app, and the deploy is marked failed.
  • Using localhost or the external database address instead of the internal one.
  • Forgetting CORS for the frontend's new HTTPS origin (Frontend · Module 6).
  • Committing application-prod.properties with real passwords.

Edge cases

  • An app killed with exit code 137 on a small instance usually ran out of memory; reduce the heap with MaxRAMPercentage or choose a bigger instance.
  • Local disk on these platforms is usually ephemeral: files saved to the container's disk disappear on redeploy. Use S3 or a platform disk.
  • Build timeouts: a Maven build that downloads the world each time is slow; keep the Dockerfile's dependency layer cached.

Interview: "When would you choose Render or Railway over EC2?"

  • Small team, MVP, demo or low traffic: faster to ship, no server upkeep, built-in HTTPS and deploys.
  • Choose EC2/ECS when you need control, private networking, compliance, or cost optimisation at scale.

Vercel and Netlify: deploying a React (Vite) app

Connect the GitHub repository, set the build command (npm run build) and output directory (dist), add VITE_ environment variables, add a rewrite so React Router works, and every pull request gets its own preview URL.

What they do

Vercel and Netlify host static sites and frontend apps. A React app built with Vite is just HTML, JavaScript and CSS files after npm run build; these platforms build it for you on every push, upload the files to a global CDN, give you HTTPS and a URL, and keep every older version. They are the easiest place for a React frontend, and both have free plans for personal projects (check current terms; commercial use may need a paid plan).

Deploy steps

  1. Push the React project to GitHub. Sign in to Vercel or Netlify with GitHub.
  2. Add New Project / Add new site → import the repository.
  3. Settings (usually detected for Vite, but check): framework Vite; install command npm install (or npm ci); build command npm run build; output directory dist. If the React app is in a subfolder (for example frontend/), set the root directory to it.
  4. Add environment variables, for example VITE_API_BASE_URL=https://api.example.com.
  5. Deploy. The first build gives a URL like your-project.vercel.app or your-site.netlify.app.

Environment variables in Vite

Vite exposes only variables that start with VITE_ to the browser code, read as import.meta.env.VITE_API_BASE_URL. The value is baked into the JavaScript at build time, so after changing a variable you must redeploy, and every visitor can read the value in the bundle. Therefore never put secrets (API secrets, database passwords) in VITE_ variables; only public settings such as the API URL.

const API = import.meta.env.VITE_API_BASE_URL ?? "http://localhost:8080";

export async function getProducts() {
  const res = await fetch(`${API}/api/products`);
  if (!res.ok) throw new Error("Request failed: " + res.status);
  return res.json();
}

Single-page app rewrites

A React Router app has one real file, index.html. If a user opens /orders/42 directly or refreshes there, the server looks for a file at that path, finds none, and returns 404. The fix is a rewrite: serve index.html for unknown paths while keeping the URL, and let React Router draw the page.

{
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}
[build]
  command = "npm run build"
  publish = "dist"

[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200

Netlify also accepts a file named _redirects in the public/ folder containing /* /index.html 200. Static files (JS, CSS, images) that exist are served first, so the catch-all does not break them. Netlify's rule is status 200 (a rewrite), not 301.

Talking to your backend

Two ways to connect the deployed frontend and the API:

  • Direct calls with CORS. The browser calls https://api.example.com directly; the Spring Boot app must allow the frontend's origin in its CORS configuration (see Spring Boot · Module 2).
  • Proxy rewrite. The platform forwards /api/* to the backend, so the browser sees one origin and CORS is not needed. On Vercel:
{
  "rewrites": [
    { "source": "/api/:path*", "destination": "https://api.example.com/api/:path*" },
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}

Netlify has the same idea with a redirect to a full URL and status 200. Whichever you pick, the backend must be served over HTTPS: a page loaded over HTTPS cannot call an http:// API (the browser blocks this "mixed content").

Preview deployments and rollback

Every pull request or branch gets its own build and URL (a preview deployment), so you and your reviewer can click the real result before merging. The production URL updates only when you merge into the production branch (usually main). Note that previews have different origins, so your backend CORS list must allow them if previews call a real API (or you point previews to a staging backend). Both platforms keep every deployment: rolling back means promoting an earlier one, which takes seconds and needs no rebuild.

Custom domain

In the project's Domains settings add shop.example.com (or your apex domain). The platform shows the DNS record to create, normally a CNAME for a subdomain and A or ALIAS records for the apex, and issues the HTTPS certificate itself. Details in Domains and DNS.

Mistakes

  • Refresh gives 404 on a nested route: the rewrite is missing.
  • API calls go to localhost:8080 in production: the VITE_ variable was not set for the production environment, or it was set after the build and not rebuilt.
  • Wrong output directory (build is Create React App's name; Vite uses dist): the site shows 404 for everything.
  • Variable without the VITE_ prefix: it is undefined in the browser.

Edge cases

  • Case-sensitive file names: import Header from "./header" works on Windows and fails on the Linux build server when the file is Header.jsx.
  • Node version mismatch can break the build; set the Node version in the project settings or an engines field if needed.
  • Warnings treated as errors: some platforms set CI=true, and lint warnings may fail the build in some toolchains.

Interview: "How do you deploy a React app and handle client-side routing?"

  • Build to static files, host on a CDN platform (Vercel, Netlify, S3 + CloudFront); add a rewrite of all unknown paths to index.html; build-time VITE_ variables; HTTPS; CORS or a proxy to the API.

Where to deploy: choosing between the options

Use Vercel or Netlify for the React frontend, Render or Railway for a quick backend, EC2 with Docker to learn real operations, and ECS, Kubernetes or Lambda when the team and scale need them.

The comparison table

Effort means the work you do after the code is ready; control means how much of the stack you can change. Prices change, so compare current pricing yourself.

How to decide

  1. Who runs it? No operations person: prefer a PaaS. A team with DevOps skills: ECS, Kubernetes, or EC2 with automation.
  2. How important is uptime? A demo may sleep. A paying customer's system needs two instances in two zones behind a load balancer, a Multi-AZ database and monitoring.
  3. What does it cost over time? A PaaS saves your time at a higher price per unit; a server saves money and costs time. At small scale, time is usually the more expensive part.
  4. What must you learn? For a job, EC2 plus Docker plus Nginx teaches the most; a PaaS teaches the least about operations but gets you live fastest.

A good plan for Project 3

  • Frontend: Vercel or Netlify, with your own domain.
  • Backend: EC2 with Docker, Nginx and HTTPS (this is the impressive, learnable path), or Render if you only need it live quickly. You can do both: Render first, EC2 second.
  • Database: RDS, or the platform's PostgreSQL; a container database only for practice.
  • Pipeline: the GitHub Actions workflow from Module 4 that builds, tests, pushes the image and deploys.

Convention: keep the choice reversible

A Docker image, environment-variable configuration and a managed Postgres (a standard database) let you move from Render to EC2 to ECS with small changes. Avoid features that lock you to one platform unless they give a clear benefit.

Mistake: choosing the most complex option to look impressive

Kubernetes for one small app is a poor choice, and interviewers know it. It is better to deploy something simple well (HTTPS, health checks, backups, rollback) and explain the trade-offs.

Interview: "How would you deploy this application?"

  • Ask about traffic, uptime needs, team skills and budget first. Then propose: static frontend on a CDN platform; backend as a container on ECS or EC2 behind a load balancer; managed Postgres; CI/CD with immutable image tags; monitoring and rollback.

Domains and DNS: pointing your own name at the app

Buy a domain from a registrar, then create DNS records: an A record from api to your Elastic IP and a CNAME from shop (or www) to Vercel or Netlify; changes appear after caches expire, and you check them with dig.

Buying a domain

A domain name (such as example.com) is rented yearly from a registrar (GoDaddy, Namecheap, Hostinger, BigRock, Route 53, Cloudflare Registrar and many others; .com, .in and .dev are examples of top-level domains). Prices differ between registrars and between the first year and renewals, so compare the renewal price and check that WHOIS privacy (hiding your personal details from the public record) is included. Use a strong password and MFA on the registrar account: whoever controls the domain controls your email and website. Turn on auto-renew, or you may lose the name.

How DNS works (resolvers, name servers, root and TLD servers) is explained in Module 2. Here we only manage records.

The records you need

TypeMapsExample

CNAMEA name to another name (an alias)www → your-site.netlify.app

NSWhich name servers are in charge of the zoneSet at the registrar

Each record has a TTL (time to live, in seconds): how long resolvers may cache the answer. The apex (or root) is the bare domain example.com; a subdomain is api.example.com. A CNAME is not allowed at the apex, because the apex must carry other records (NS, MX). Providers solve this with special alias-style records (ALIAS, ANAME or "CNAME flattening", and Route 53 "alias records"), or you can send the apex to an address given by the platform.

Add the domain in the Vercel or Netlify project first; it shows the exact records and checks them. Then open your DNS provider's panel and create the records. Do not copy values from a blog: use the ones the platform shows today.

Using Cloudflare DNS (brief)

You can host your DNS at Cloudflare: add the site, then change the name servers at the registrar to the two Cloudflare gives you. Cloudflare has a free plan (check current terms) and a fast DNS panel. Each record has a proxy switch:

  • DNS only (grey cloud): the record answers with your real IP. The simplest option while learning, and what certbot expects.
  • Proxied (orange cloud): traffic passes through Cloudflare, which hides your IP and adds caching and protection. Then use SSL mode "Full (strict)" so Cloudflare-to-origin traffic is encrypted and validated. "Flexible" mode leaves the last hop unencrypted and often causes redirect loops.

Records for Vercel/Netlify are usually best left DNS-only, so those platforms can manage certificates themselves.

Propagation and checking

There is no global switch that "propagates". Each resolver caches an old answer until its TTL ends, so a change can appear in seconds for you and take hours for someone else. If you plan a move, lower the TTL a day before. Check what the world sees:

$ dig +short api.example.com
203.0.113.25
$ dig +short shop.example.com CNAME
cname.vercel-dns.com.
$ dig api.example.com @1.1.1.1 +short      # ask a specific public resolver
$ dig +short NS example.com
$ nslookup api.example.com                  # works on Windows too

Your own machine may also cache a failed lookup; if it still shows the old answer, wait a little or flush the local DNS cache (ipconfig /flushdns on Windows).

Mistakes

  • Typing the full name in the host field (api.example.com.example.com). Many panels want only api.
  • Pointing the A record at the instance's temporary public IP instead of the Elastic IP; it changes at the next stop and start.
  • Leaving an old A record next to a new CNAME for the same name (a name cannot be both).
  • Running certbot before the record exists.

Edge cases

  • NXDOMAIN means the name does not exist in DNS: a typo, a missing record, or the name servers are not changed yet.
  • A CAA record, if present, lists the authorities allowed to issue certificates; it must allow letsencrypt.org or issuance fails.
  • www and the apex are different names; set up both and redirect one to the other.

Interview: "Difference between A and CNAME records? Why not CNAME at the root?"

  • A maps a name to an IP; CNAME maps a name to another name. A CNAME cannot coexist with other records for the same name, and the apex needs NS/SOA/MX, so use ALIAS/ANAME/flattening there.
  • TTL and caching explain "propagation".

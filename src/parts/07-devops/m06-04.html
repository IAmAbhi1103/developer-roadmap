What to learn after month 12 for DevOps-leaning backend developers

After the basics in this page, deepen in this order: cloud networking and security, one cloud certification, Kubernetes and Terraform in practice, observability with OpenTelemetry, safer pipelines (scanning, GitOps), and reliability habits such as SLOs, load tests and incident reviews.

Where you stand after this page

By now you can containerise a Spring Boot app, build a pipeline, deploy it to a server or a PaaS under your own HTTPS domain, read logs, add health checks and know what Prometheus, Kubernetes and Terraform are. That is already more than many fresh graduates know. The next steps depend on the kind of job you want, but they all follow the same rule: learn each tool by deploying one real thing with it, then write down what broke.

Three directions you can take

  • Backend developer who ships well (most Java full-stack roles). You do not need to become an infrastructure specialist. Be excellent at Docker, CI/CD, one cloud's core services, logs, metrics and debugging production. Add tracing and load testing next.
  • DevOps or platform engineer. Go deeper into Linux, networking, Kubernetes, Terraform, GitOps and security. Study how to build "paved roads" (templates and pipelines) that let other developers deploy safely without learning everything.
  • Site reliability engineer (SRE). Add SLOs, capacity planning, incident management, chaos testing, and performance analysis. This path rewards strong software skills as well as operations.

Habits that matter more than tools

  1. Automate what you do twice. A script today, a pipeline later.
  2. Write things down. A README with the deploy and rollback steps, and a short post-mortem after every failure.
  3. Prefer boring technology. A simple setup that you understand beats a fashionable stack that you copied.
  4. Read documentation and release notes. Cloud services change often; the official documentation (docs.aws.amazon.com, kubernetes.io, docs.docker.com) is the final reference.
  5. Break things on purpose in a safe place. Kill a container, fill a disk, remove a permission, and watch what your monitoring shows.
  6. Keep a cost eye on everything. It is a professional skill, not a limitation.

How to talk about this in interviews

Do not claim to be a Kubernetes expert after one tutorial. Say what you did: "I deployed a Spring Boot and React project with a GitHub Actions pipeline, Docker images in GHCR, EC2 behind Nginx with HTTPS, RDS, S3 presigned uploads, health checks and uptime alerts. I have run it on a local Kubernetes cluster and described the AWS setup in Terraform." Honest, specific stories with the problems you hit and how you fixed them are far more convincing than a long list of tool names.

Tip: pick one project and keep upgrading it

Project 3 is the best learning vehicle you have. Each new tool (Kubernetes, Terraform, tracing, scanning) becomes one more branch and one more README section on a project that already works. This is easier to remember and to explain than ten separate tutorials.

Interview: "What would you improve in your deployment setup next?"

  • Good answers are concrete: Terraform for repeatability, a second instance behind a load balancer for availability, tracing and centralised logs for debugging, image scanning and secrets management for security, SLO-based alerts, load tests before launch.

Interview questions — Monitoring and later topics

The container keeps restarting. How do you find out why?

Check docker compose ps -a for the exit code and docker inspect for OOMKilled. Read the last log lines (docker compose logs --tail 200), looking for the first error and any "APPLICATION FAILED TO START" block. Then check memory and disk (free -h, df -h, dmesg). Common causes are exit 137 (out of memory), a port in use, a refused database connection, and a missing environment variable.

What does exit code 137 mean?

It is 128 plus 9: the process got SIGKILL. In containers this is usually the kernel's out-of-memory killer, confirmed by OOMKilled=true and a line in dmesg. The Java log simply stops, with no stack trace. Fix by lowering the heap (MaxRAMPercentage), raising the memory limit, or finding a leak.

How do you stop logs from filling the disk?

For Docker set max-size and max-file for the json-file log driver (per service in Compose or in daemon.json). For files use logrotate or Logback's rolling policy with a history limit. Cap the journal with SystemMaxUse. Monitor disk space with an alert, and log at INFO rather than DEBUG in production.

What are the three pillars of observability?

Logs (events with detail), metrics (numbers over time, good for dashboards and alerts) and traces (the path and timing of one request across services). They are linked by IDs such as a trace ID in each log line. Metrics tell you that something is wrong, traces show where, logs show what exactly happened.

What are the four golden signals?

Latency (use percentiles such as p95), traffic (requests per second), errors (rate of failed requests) and saturation (how full CPU, memory, disk, thread or connection pools are). RED (rate, errors, duration) suits services and USE (utilisation, saturation, errors) suits resources.

Liveness vs readiness probes: what is the difference and why does it matter?

A failing liveness probe makes Kubernetes restart the container; a failing readiness probe only removes the pod from the Service so it gets no traffic. Keep external dependencies like the database out of liveness; otherwise a database outage restarts all pods in a loop. Spring Boot provides /actuator/health/liveness and /readiness.

Why do you need an external uptime monitor if you have Prometheus?

Prometheus and its alerts normally run on your own infrastructure, so they may be down with it, and they usually scrape from inside the network. An external monitor tests the full public path (DNS, TLS, Nginx, the app) from outside, and tells you when everything is down, including the monitoring itself.

How does Prometheus collect metrics from a Spring Boot app?

The app uses Actuator and Micrometer with the Prometheus registry to publish text metrics at /actuator/prometheus. Prometheus pulls ("scrapes") this URL at the interval set in prometheus.yml for each target, stores the samples, and answers PromQL queries. Grafana reads from Prometheus to draw dashboards. A failed scrape sets up to 0.

Write a PromQL query for the error percentage and for p95 latency. 
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
/ sum(rate(http_server_requests_seconds_count[5m]))

histogram_quantile(0.95,
  sum by (le) (rate(http_server_requests_seconds_bucket[5m])))

Counters need rate(); p95 needs the histogram buckets enabled and the le label kept in the sum.

Counter vs gauge vs histogram in metrics?

A counter only increases (requests served), so you look at its rate. A gauge moves up and down (heap used, active connections). A histogram records observations in buckets plus a sum and count, which lets you estimate percentiles and averages of values such as latency.

Why Kubernetes? What are Pod, Deployment, ReplicaSet and Service?

It schedules containers across machines, heals failures, scales, and does rolling updates. A Pod runs containers; a ReplicaSet keeps N identical pods alive; a Deployment manages ReplicaSets to give rolling updates and rollback; a Service gives a stable address and load balancing over pods selected by labels. Ingress adds HTTP routing from outside.

How do you roll out a new version in Kubernetes and undo it?

Change the image tag (for example kubectl set image or kubectl apply with the new tag). The Deployment performs a rolling update, starting new pods and waiting for readiness before stopping old ones. Watch with kubectl rollout status; undo with kubectl rollout undo deployment/NAME. Using immutable tags makes this reliable.

Docker Compose vs Kubernetes: when would you pick each?

Compose describes containers on one host: ideal for local development and small single-server deployments, with low complexity. Kubernetes manages a cluster with scheduling, self-healing, autoscaling and rolling updates, suited to many services and teams, at the cost of complexity and operations work. A small app does not need Kubernetes.

What is Terraform? What are plan, apply and state?

Terraform is a declarative infrastructure-as-code tool. You describe resources in .tf files; terraform plan shows what would change, apply makes it so, and destroy removes it. The state file maps your code to real resources and must be stored safely (remote, locked, encrypted) and never committed to Git. It gives repeatable, reviewable environments.

Practice — Monitoring and later topics

  1. Read logs like an operator (easy). On a server or your laptop with Compose, follow your app's logs, find the first ERROR after you send a bad request, and count the WARN lines with grep -c. Done when: you can show the exact log line, with its timestamp, for one failing request.
  2. Limit the log size (easy). Add max-size and max-file to your Compose file and recreate the container. Done when: docker inspect shows the log options and you can explain why recreating was needed.
  3. Break it on purpose (medium). Cause each failure once: remove a required environment variable, start a second app on port 8080, stop the database, set a very small memory limit. Done when: for each one you can name the log line, the exit code, and the fix, in under two minutes.
  4. Health checks (medium). Add Actuator, enable liveness and readiness, add a custom health indicator, and add a Compose healthcheck. Done when: docker ps shows (healthy), and stopping the database turns readiness DOWN while liveness stays UP.
  5. Uptime alert (easy). Create an external monitor for your public health URL with a keyword check and a Telegram or email alert. Done when: you stop the app and the alert arrives on your phone within a few minutes.
  6. Prometheus and Grafana (medium). Add the Micrometer registry, run Prometheus and Grafana from Compose, import a JVM dashboard, and build a panel for requests per second, error percentage and p95 latency. Done when: you generate load with a small loop of curl calls and see all three panels move.
  7. An alert rule (medium). Write alerts.yml with ApiDown and HighErrorRate, check it with promtool check rules, and trigger the alert on purpose. Done when: the alert appears as firing in the Prometheus Alerts page.
  8. Kubernetes locally (hard). Start a kind or minikube cluster, load your image, apply the Deployment and Service from this module, port-forward, then update the image tag and roll it back. Done when: kubectl rollout status shows a clean update, rollout undo returns to the old tag, and you can explain each probe.
  9. Terraform the server (hard). Recreate the EC2 instance, security group and Elastic IP from Module 5 with the Terraform example, then run terraform destroy. Done when: the plan shows five resources to add, everything is created and removed by commands only, and the AWS console shows nothing left over.
  10. Project 3, live and watched (capstone). Deploy Project 3 (React on Vercel or Netlify, Spring Boot and PostgreSQL on EC2 or Render, your own domain with HTTPS) as in the Module 5 practice, then add health checks, an uptime alert and a dashboard. Done when: Project 3 is live on a public HTTPS address, you get a phone alert when you stop it, and you can explain everything that happens between git push and the new version going live, and how you would find out and recover if it broke.

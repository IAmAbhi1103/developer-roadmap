Dockerfile instructions, ENTRYPOINT vs CMD and best practices

A Dockerfile is a recipe of instructions that builds an image layer by layer; order the instructions so dependencies are cached, run as a non-root user, keep images small, and never put secrets inside.

What a Dockerfile is

A Dockerfile is a text file (named exactly Dockerfile) with one instruction per step. docker build -t shop-api:1.0 . reads it, runs the steps in order, and stores the result as an image. The final . is the build context: the folder whose files COPY may use. Docker sends the whole context to the daemon, so keep it small with a .dockerignore.

The instructions

Lines starting with # are comments. RUN, ENTRYPOINT and CMD each have two forms:

  • Exec form ["java", "-jar", "app.jar"] (JSON array). Runs the program directly as PID 1, so it receives SIGTERM from docker stop. Use this for ENTRYPOINT and CMD.
  • Shell form java -jar app.jar. Docker wraps it in /bin/sh -c, the shell becomes PID 1, and signals may never reach Java, so shutdown is not graceful.

ENTRYPOINT versus CMD

ENTRYPOINT is "what this container is" and CMD is "default arguments". When both exist, Docker runs ENTRYPOINT followed by CMD. docker run image extra args replaces CMD but not ENTRYPOINT (override it with --entrypoint).

Dockerfiledocker run imageRuns
CMD ["java","-jar","app.jar"](nothing)java -jar app.jar
CMD ["java","-jar","app.jar"]shsh (CMD replaced; the app is gone)
ENTRYPOINT ["java","-jar","app.jar"](nothing)java -jar app.jar
ENTRYPOINT ["java","-jar","app.jar"]--server.port=9000java -jar app.jar --server.port=9000

For a Spring Boot service use ENTRYPOINT in exec form; that way extra arguments become Spring command-line arguments, and nobody starts a shell by accident.

Best practices

  1. Order layers for the cache. Copy pom.xml and download dependencies before copying src. Dependencies change rarely, source changes on every commit; so the slow download layer stays cached.
  2. Use multi-stage builds. Compile with the JDK and Maven in one stage; ship only the JRE and the JAR in the final stage (next article).
  3. Run as a non-root user. If an attacker breaks into the app, they are not root inside the container.
  4. One main process per container. The app in one, the database in another, a cache in a third. Compose joins them.
  5. Keep images small. A JRE base, no build tools, no caches; fewer packages mean less to patch and faster pulls.
  6. Pin versions. eclipse-temurin:21-jre, not latest; pin Maven and Node versions too.
  7. No secrets in the image. Every layer is readable by anyone who can pull the image, even if a later step deletes the file.
  8. Combine related RUN steps with && and clean up in the same step (for example apt-get install … && rm -rf /var/lib/apt/lists/*). Deleting in a later layer does not shrink the image.
  9. Use exec form for ENTRYPOINT/CMD, and add a healthcheck where the platform uses it.

Wrong: source copied first, cache never helps

FROM maven:3.9-eclipse-temurin-21
WORKDIR /build
COPY . .
RUN mvn -B package
ENTRYPOINT java -jar target/app.jar

Right: dependencies cached, exec form

FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /build
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src src
RUN mvn -B package -DskipTests
# ...runtime stage copies only the JAR

In the wrong version any edit to any file invalidates the COPY . . layer, so Maven downloads all dependencies again on every build, and the final image carries Maven, the JDK and the source.

Rule: ARG and ENV values are not secrets

Build args and environment variables baked into an image can be read with docker history and docker inspect. Pass real secrets at runtime (see Environment variables and secrets) or use BuildKit secret mounts for build-time needs.

Edge cases

  • EXPOSE changes nothing at runtime. Without -p (or compose ports) the host cannot reach the port.
  • CMD or ENTRYPOINT given twice: only the last counts.
  • ARG declared before FROM is usable only in FROM lines; redeclare it inside the stage to use it there.
  • ADD auto-extracts local archives and downloads URLs, which surprises people; it is the reason to prefer COPY.

Interview: "How do you make Docker builds fast and images small?"

  • Order instructions by change frequency so the build cache works; copy the dependency manifest first.
  • Multi-stage build, JRE base image, .dockerignore, combine and clean RUN steps.
  • Non-root user, pinned tags, no secrets.

A complete multi-stage Dockerfile for Spring Boot, line by line

Stage one uses a Maven + JDK image to download dependencies and build the JAR; stage two starts from a small JRE image, copies only the JAR, switches to a non-root user and starts the app with an exec-form ENTRYPOINT — typically a few hundred MB smaller than a single-stage image.

Why two stages

Building needs Maven, the JDK, your source and about 200 MB of downloaded dependencies. Running needs only a JRE and one JAR. A multi-stage build uses several FROM lines in one Dockerfile; each starts a fresh stage, and COPY --from= takes chosen files from an earlier stage. Everything else in the earlier stage is dropped from the final image.

The Dockerfile

Project layout: pom.xml, src/, and optionally the Maven wrapper (mvnw, .mvn/). This version uses the Maven image, so it does not need the wrapper.

# syntax=docker/dockerfile:1

# ---------- Stage 1: build ----------
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /build

# Copy only the dependency manifest first, so this layer is cached
COPY pom.xml .
RUN mvn -B -q dependency:go-offline

# Now copy the source and build the JAR
COPY src ./src
RUN mvn -B -q package -DskipTests

# ---------- Stage 2: runtime ----------
FROM eclipse-temurin:21-jre
WORKDIR /app

# Create a non-root user and group
RUN groupadd --system spring && useradd --system --gid spring --no-create-home spring

# Take only the built JAR from stage 1
COPY --from=build /build/target/*.jar app.jar

USER spring
EXPOSE 8080

# Tune the JVM for containers (see the JVM article)
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75.0"

HEALTHCHECK --interval=30s --timeout=3s --start-period=40s --retries=3 \
  CMD curl -fs http://localhost:8080/actuator/health || exit 1

ENTRYPOINT ["java", "-jar", "app.jar"]

Every line explained

# syntax=docker/dockerfile:1
Optional first line that selects the current stable Dockerfile syntax for BuildKit (the default builder). It enables newer features such as RUN --mount.
FROM maven:3.9-eclipse-temurin-21 AS build
The base for stage 1: Maven 3.9 on Temurin JDK 21. AS build names the stage so we can copy from it later.
WORKDIR /build
Creates /build and makes it the current folder. All following relative paths start here.
COPY pom.xml .
Copies just the POM. If the POM has not changed, this layer and the next stay cached.
RUN mvn -B -q dependency:go-offline
Downloads dependencies and plugins into the image's ~/.m2 as its own layer. -B is batch mode (no colours or progress bars) and -q is quiet. Some plugins are only resolved when they run, so a rare "missing artifact" can still appear later; it only costs speed, not correctness.
COPY src ./src
Brings in your code. From here down, layers are rebuilt on every code change.
RUN mvn -B -q package -DskipTests
Compiles and builds the executable Spring Boot JAR into target/. Tests are skipped here because CI runs them in an earlier step; running them inside the image build would need a database.
FROM eclipse-temurin:21-jre
Starts stage 2 from a JRE-only image. Nothing from stage 1 comes along automatically.
RUN groupadd … && useradd …
Creates a system user spring. These are the Debian/Ubuntu commands; on Alpine you would use addgroup/adduser.
COPY --from=build /build/target/*.jar app.jar
Copies the JAR from the build stage and renames it app.jar. Keep exactly one JAR in target/ (the glob fails or misbehaves if a -plain.jar is also produced, e.g. by the Gradle jar task; Maven's Boot plugin produces one executable JAR).
USER spring
From now on, and at runtime, the process runs as spring, not root.
EXPOSE 8080
Documentation: the app listens on 8080.
ENV JAVA_TOOL_OPTIONS=…
The JVM reads this variable at start-up and applies the flags.
HEALTHCHECK …
Docker runs the command inside the container every 30 s. start-period gives Spring time to boot. It needs curl and the Actuator health endpoint; the Temurin Ubuntu-based images include curl, but Alpine and distroless images do not.
ENTRYPOINT ["java", "-jar", "app.jar"]
Exec form: Java is PID 1 and gets SIGTERM on docker stop.

Build and run

$ docker build -t shop-api:1.0 .

$ docker images shop-api

shop-api     1.0   5a1b2c3d4e5f   10 seconds ago   310MB

{"status":"UP"}
$ docker build -t shop-api:1.0 .       # second build after a code change
[+] Building 12.8s (13/13) FINISHED     # dependency layer came from the cache

The sizes and times above are examples; yours will differ. The point to notice is the second build: the dependency layer is cached, so only the compile and copy steps run.

Optional: layered JARs for faster pulls

A Spring Boot JAR is mostly third-party libraries that rarely change, plus a small part that is your code. Spring Boot can split the JAR into layers (dependencies, application classes) that Docker caches separately, so a code change re-pushes only a few KB instead of the whole fat JAR. You extract the layers in the build stage with java -Djarmode=tools -jar app.jar extract --layers (Spring Boot 3.3 and later; older versions use -Djarmode=layertools with extract) and copy each folder with its own COPY. This is an optimisation; start with the simple version above and see the Spring Boot reference ("Efficient container images") before you add it.

Java versions

Replace 21 with 17 or 25 to match your project's java.version. The build and runtime stages must use the same major version (or the runtime must be newer), otherwise you get UnsupportedClassVersionError.

Mistake: building the JAR on the host and forgetting to rebuild

A Dockerfile that does COPY target/app.jar uses whatever is in target/ on your machine, possibly an old build, and breaks in CI where target/ does not exist. The multi-stage version builds inside Docker, so the result does not depend on your laptop.

Errors you will see

  • Error: Unable to access jarfile app.jar — the JAR was not copied to the path the ENTRYPOINT expects, or the glob matched nothing.
  • no main manifest attribute — a plain (non-Boot) JAR was copied; build with the spring-boot-maven-plugin repackage goal.
  • UnsupportedClassVersionError — compiled with a newer JDK than the runtime image.
  • Container becomes "unhealthy" — curl missing, Actuator not on the classpath, or the app needs more than start-period to start.

Interview: "Walk me through a Dockerfile for a Spring Boot app."

  • Two stages: Maven/JDK builds the JAR (POM and dependencies first for caching); a JRE image runs it.
  • COPY --from=build, non-root USER, exec-form ENTRYPOINT, EXPOSE 8080, healthcheck; secrets come from the environment at runtime.

The JVM in containers, Buildpacks and Jib

Modern JVMs read the container's memory and CPU limits; set the heap as a percentage with -XX:MaxRAMPercentage, always set a container memory limit, and consider Spring Boot's Buildpacks or Jib when you want an image without writing a Dockerfile.

Container-aware JVM

A container limit (for example -m 512m) is enforced by the kernel through cgroups. Old JVMs (Java 8 before update 191) looked at the host memory and sized the heap for 16 GB while the container had 512 MB, and the kernel killed the container. Modern JVMs (Java 10+, and 8u191+) are container-aware by default (-XX:+UseContainerSupport is on): they read the cgroup limits for memory and CPU count.

By default the maximum heap is about 25% of the container memory — safe but often too low. Control it with a percentage so the setting follows the limit:

FlagMeaning
-XX:MaxRAMPercentage=75.0Max heap as a percentage of container memory (default 25)
-XX:InitialRAMPercentage=50.0Initial heap size as a percentage
-Xmx512mFixed maximum heap; does not follow the container limit
-XX:ActiveProcessorCount=2Override the CPU count the JVM believes it has
-XX:+ExitOnOutOfMemoryErrorExit on OOM so the platform restarts the container

Why not 100%? The JVM also needs memory outside the heap: metaspace, thread stacks, the code cache, direct buffers and garbage collector structures. A container with a 1 GB limit and MaxRAMPercentage=75 gets a heap up to 768 MB, leaving about 256 MB for everything else. For very small containers (under 512 MB) use a lower percentage, around 50–60.

$ docker run -d --name shop-api -m 1g --cpus 2 -p 8080:8080 \
    -e JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75.0 -XX:+ExitOnOutOfMemoryError" \
    shop-api:1.0
$ docker logs shop-api | head -3
Picked up JAVA_TOOL_OPTIONS: -XX:MaxRAMPercentage=75.0 -XX:+ExitOnOutOfMemoryError
$ docker stats --no-stream shop-api
CONTAINER ID   NAME       CPU %   MEM USAGE / LIMIT   MEM %
8c1d2e3f4a5b   shop-api   0.6%    412MiB / 1GiB       40.23%

JAVA_TOOL_OPTIONS is read by every JVM start, so it also affects tools like jcmd that run in the same container (they print the "Picked up" line). That is harmless.

Other container tips for the JVM

  • Always set a memory limit (-m, or deploy.resources.limits / mem_limit in compose, or the platform setting). Without one, the JVM sees the whole host.
  • CPU limits change the GC and thread pools. With under 2 CPUs the JVM may choose the Serial GC. If start-up is slow, give it more than one CPU while it boots.
  • Start-up time. A Spring Boot app often needs 5–20 s to start; set the healthcheck start-period and the platform's readiness delay accordingly.
  • Heap dumps and logs. Write logs to stdout (the default), not to files inside the container; Docker and platforms collect stdout.
  • See Core Java · Module 7 for heap, GC and memory in detail.

Mistake: container killed with exit code 137, no Java stack trace

Exit code 137 = 128 + 9 (SIGKILL). When the whole container exceeds its memory limit the kernel's OOM killer kills it silently; Java never prints an OutOfMemoryError. Check docker inspect -f '{{.State.OOMKilled}}' name. Fix: lower MaxRAMPercentage to leave room for non-heap memory, raise the limit, or find the leak.

Alternative 1: Spring Boot Buildpacks (no Dockerfile)

Cloud Native Buildpacks inspect your project and build an optimised, layered image for you. Spring Boot wraps them in the Maven and Gradle plugins:

$ ./mvnw -DskipTests spring-boot:build-image \
    -Dspring-boot.build-image.imageName=shop-api:1.0
...
Successfully built image 'docker.io/library/shop-api:1.0'
$ docker run --rm -p 8080:8080 shop-api:1.0

It needs a running Docker daemon, downloads builder images on the first run (slow), and configures the JVM memory settings automatically at start-up. Good for quick builds and teams that want standard images; less control than a Dockerfile.

Alternative 2: Jib

Jib (a Google plugin for Maven and Gradle) builds a layered image directly from your compiled classes and dependencies without a Docker daemon and without a Dockerfile. It can push straight to a registry, which suits CI servers where Docker is not available.

<plugin>
    <groupId>com.google.cloud.tools</groupId>
    <artifactId>jib-maven-plugin</artifactId>
    <!-- use the latest version from the plugin's README -->
    <configuration>
        <to><image>ghcr.io/asha/shop-api:1.0</image></to>
    </configuration>
</plugin>
$ ./mvnw compile jib:dockerBuild    # build into the local Docker daemon
$ ./mvnw compile jib:build          # build and push straight to the registry

Convention: know the Dockerfile first

Interviews and most existing projects use Dockerfiles. Learn that well; reach for Buildpacks or Jib when a project already uses them or when you need to avoid a Docker daemon.

Interview: "Your Java container keeps getting killed. Why?"

  • Exit 137 and OOMKilled=true: total memory (heap plus non-heap) exceeded the limit.
  • Set an explicit limit, use MaxRAMPercentage (60–75), leave room for metaspace and threads, and look for leaks.

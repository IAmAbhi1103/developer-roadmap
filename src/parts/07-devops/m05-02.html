EC2: virtual servers, instance types, keys, security groups and disks

EC2 rents you a Linux virtual machine: you choose an AMI (the OS image), an instance type (CPU and RAM), a key pair for SSH, a security group (the firewall) and an EBS disk, then pay while it runs.

What EC2 is

EC2 (Elastic Compute Cloud) is AWS's virtual-server service, the main IaaS product. An instance is one virtual machine. You get a normal Linux server with SSH access, exactly like the machine you practised on in Module 1: install Docker, run containers, configure Nginx. When you launch an instance you choose these things:

AMI
Amazon Machine Image: the template of the operating system and preinstalled software. For this course use Ubuntu Server LTS (the login user is ubuntu). Amazon Linux is AWS's own distribution (login user ec2-user) and also works.
Instance type
The CPU and memory size, for example t3.micro.
Key pair
The SSH key used to log in. AWS stores the public half; you download the private half (.pem file) once.
Security group
A virtual firewall around the instance.
EBS volume
The virtual disk (Elastic Block Store).

Instance types and names

A name like t3.micro has three parts: the family (t), the generation (3) and the size (micro). Sizes go nano, micro, small, medium, large, xlarge, 2xlarge and so on, doubling each step.

FamilyMeaningUse for
t (t3, t4g)Burstable: a low baseline CPU with credits for burstsLearning, small apps, dev servers
mGeneral purpose, balanced CPU and memoryTypical application servers
cCompute-optimisedCPU-heavy work
rMemory-optimisedCaches, big in-memory data

Burstable (t-family) instances run at a baseline and earn credits while idle, which they spend when busy. If you run at full CPU for long, credits run out and the instance slows (or, in "unlimited" mode, bills extra), so they suit apps that are mostly idle. A letter g in the name (t4g, m7g) means Graviton, AWS's ARM processor. Graviton is often cheaper for the same power, but it needs ARM builds of your software. Java runs fine on ARM, and Docker images must be built for linux/arm64 (see the multi-platform note in the GHCR article). Which types qualify for any free offer changes, so check the current free-tier page before choosing.

Size for memory, not only CPU. A Spring Boot app plus Nginx plus Docker needs roughly a gigabyte to run comfortably; on a 1 GiB instance with a database too, memory is tight. Options: a bigger type, a swap file (shown in the runbook), or a managed database so the instance only runs the app.

Key pairs and SSH

When you create a key pair, AWS lets you download the private key only once. Keep it safe, and restrict its permissions, or SSH refuses it:

$ chmod 400 shop-key.pem
$ ssh -i shop-key.pem ubuntu@203.0.113.25
Welcome to Ubuntu 24.04 LTS (GNU/Linux 6.8.0-1012-aws x86_64)
ubuntu@ip-172-31-5-20:~$
PS> icacls .\shop-key.pem /inheritance:r
PS> icacls .\shop-key.pem /grant:r "$($env:USERNAME):(R)"
PS> ssh -i .\shop-key.pem ubuntu@203.0.113.25

If you lose the private key, you cannot recover it; you would create a new key pair and launch a new instance (or use AWS Systems Manager Session Manager or EC2 Instance Connect to get in and add a new key).

Security groups

A security group is a stateful firewall attached to the instance. Inbound traffic is denied unless a rule allows it; outbound is allowed by default. "Stateful" means that a reply to an allowed request is allowed automatically. For one web server:

TypePortSourceWhy
SSH22My IP onlyAdmin login
HTTP800.0.0.0/0 (anywhere)Nginx, and the Let's Encrypt check
HTTPS4430.0.0.0/0Public traffic

Do not open port 8080 (the Spring Boot container) to the world; only Nginx on the same machine talks to it. Never leave SSH open to 0.0.0.0/0: bots try passwords on port 22 all day. A rule's source can also be another security group, which is how the database lets in only your server (see RDS). Your home IP may change; if SSH suddenly times out, update the rule.

Disks, IP addresses and user data

  • EBS volumes are network disks. The root volume holds the OS. A volume survives a stop; whether it is deleted at termination is the "delete on termination" setting. Common type: gp3 (general-purpose SSD). Snapshots are backups of a volume. A volume lives in one AZ.
  • Public IP: the automatic public address of an instance changes when you stop and start it. An Elastic IP is a static public IPv4 address that you own until you release it; associate it with the instance so your DNS record stays valid. AWS now charges for public IPv4 addresses, and an unused Elastic IP is a classic waste, so check current pricing and release what you do not need.
  • User data: a script that runs once as root at first boot (through cloud-init). Good for installing packages automatically. Its output goes to /var/log/cloud-init-output.log.
#!/bin/bash
apt-get update -y
apt-get install -y nginx
systemctl enable --now nginx

Stop vs terminate

ActionWhat happensBilling
RebootRestart of the OS; same host, same IPsContinues
StopShut down; the instance and disks remain; the public IP changesNo compute charge, but EBS storage (and any Elastic IP) still bills
TerminateInstance deleted forever; root volume deleted if "delete on termination" is onStops, except volumes that were kept

Mistake: SSH errors and what they mean

  • Connection timed out — the security group does not allow your IP on port 22, you used the wrong IP, or the instance has no public address.
  • Permission denied (publickey) — wrong user (ubuntu vs ec2-user), wrong key file, or the instance was launched with another key pair.
  • UNPROTECTED PRIVATE KEY FILE — the .pem permissions are too open; chmod 400 it.

Tip: enable termination protection and IMDSv2

Turn on termination protection for the one server you care about. Prefer IMDSv2 (token-based instance metadata, the default on recent AMIs); it blocks a class of attacks where a bug in your app is tricked into reading the server's credentials.

Interview: "What happens to data when you stop vs terminate an instance?"

  • Stop: EBS data stays, the public IP changes (unless Elastic IP). Terminate: the instance is gone, and the root volume is deleted by default. Instance-store data is lost on stop.
  • Mention security group statefulness and the t-family credit model.

Runbook: deploy Spring Boot on EC2 with Docker, Nginx and HTTPS

Launch an Ubuntu instance, attach an Elastic IP, install Docker, run your container from GHCR with Compose, put Nginx in front, point an A record at the IP, get a certificate with certbot, and keep two small scripts for updating and rolling back.

What we are building

Your Spring Boot image (from Module 3), published to GHCR by your pipeline (Module 4), runs on one EC2 server. Nginx listens on ports 80 and 443 and forwards to the container on 127.0.0.1:8080. The database is RDS (or a container for a cheap experiment). We use the example name api.example.com and image ghcr.io/asha/shop-api; replace them with yours.

Step 1: launch the instance

  1. In the console, select your region (for example Mumbai), open EC2 → Launch instance.
  2. Name: shop-api. AMI: Ubuntu Server LTS. Instance type: pick a small one that fits your plan (check the current free-tier page; for a Spring Boot app 2 GiB of RAM is more comfortable than 1 GiB).
  3. Key pair: create shop-key (ED25519 or RSA, .pem), and save the download.
  4. Network settings: create a security group allowing SSH from My IP, and HTTP and HTTPS from anywhere. Do not open 8080.
  5. Storage: the default root volume (gp3) is enough; leave "delete on termination" on.
  6. Launch. Wait for "Running" and 2/2 status checks.
  7. EC2 → Elastic IPs → Allocate, then Associate it with your instance. This is the address for DNS.

Step 2: connect and prepare the server

$ ssh -i shop-key.pem ubuntu@203.0.113.25
$ sudo apt update && sudo apt -y upgrade
$ sudo timedatectl set-timezone Asia/Kolkata     # optional, logs in IST
$ free -h                                         # check the RAM you actually have

On a small instance, add a swap file so a short memory spike does not kill the app (swap is slow, so it is a safety net, not a substitute for RAM):

$ sudo fallocate -l 1G /swapfile
$ sudo chmod 600 /swapfile
$ sudo mkswap /swapfile
$ sudo swapon /swapfile
$ echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
$ swapon --show

Step 3: install Docker

Docker's documentation (docs.docker.com) has the official apt-repository steps for Ubuntu. For a learning server, Docker's convenience script is a short alternative, but read a script before you run it as root and avoid it for production machines.

$ curl -fsSL https://get.docker.com -o get-docker.sh
$ less get-docker.sh                 # read it first
$ sudo sh get-docker.sh
$ sudo usermod -aG docker $USER      # allow 'docker' without sudo
$ exit                               # log out and back in for the group to apply
$ ssh -i shop-key.pem ubuntu@203.0.113.25
$ docker run --rm hello-world
$ docker compose version
$ sudo systemctl enable docker       # start Docker at boot (usually already on)

Members of the docker group effectively have root on the machine, so add only yourself.

Step 4: configuration, secrets and the Compose file

Create a folder that holds only configuration, never source code. The .env file holds secrets, so its permissions are strict.

$ sudo mkdir -p /opt/shop && sudo chown $USER:$USER /opt/shop
$ cd /opt/shop
$ nano .env
$ chmod 600 .env
IMAGE_TAG=sha-3f9c2ab
SPRING_PROFILES_ACTIVE=prod
SPRING_DATASOURCE_URL=jdbc:postgresql://shop-db.abc123.ap-south-1.rds.amazonaws.com:5432/shop
SPRING_DATASOURCE_USERNAME=shop_app
SPRING_DATASOURCE_PASSWORD=change-me-long-random
JWT_SECRET=change-me-another-long-random-value
JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75
services:
  api:
    image: ghcr.io/asha/shop-api:${IMAGE_TAG}
    env_file: .env
    ports:
      - "127.0.0.1:8080:8080"        # reachable only from this machine (Nginx)
    restart: unless-stopped          # comes back after a crash or a reboot
    logging:
      driver: json-file
      options:
        max-size: "10m"              # rotate logs so the disk never fills
        max-file: "3"

The binding 127.0.0.1:8080:8080 is the important line: Docker publishes the port on the loopback interface only. A plain 8080:8080 would open it on every interface, and Docker bypasses some host firewall rules, so the security group is your real protection too. In production a HEALTHCHECK is also useful (Module 6). The Spring property server.forward-headers-strategy=framework makes the app trust Nginx's X-Forwarded-* headers, so generated links and redirects use https.

Step 5: pull and run

If your image is private on GHCR, log in with a personal access token that has the read:packages scope. Type the token without leaving it in your shell history:

$ read -rs GHCR_TOKEN                 # paste the token, press Enter (nothing is echoed)
$ echo "$GHCR_TOKEN" | docker login ghcr.io -u asha --password-stdin
$ unset GHCR_TOKEN
$ cd /opt/shop
$ docker compose pull
$ docker compose up -d
$ docker compose ps
$ docker compose logs -f api          # Ctrl+C to leave; look for "Started ShopApplication"
$ curl -s http://127.0.0.1:8080/actuator/health
{"status":"UP"}

Step 6: Nginx as a reverse proxy

Nginx accepts public connections and forwards them to the app. The full configuration with TLS settings is in Module 2; here is the minimum.

$ sudo apt install -y nginx
$ sudo nano /etc/nginx/sites-available/shop
server {
    listen 80;
    listen [::]:80;
    server_name api.example.com;

    client_max_body_size 10m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }
}
$ sudo ln -s /etc/nginx/sites-available/shop /etc/nginx/sites-enabled/shop
$ sudo rm -f /etc/nginx/sites-enabled/default
$ sudo nginx -t                      # always test the syntax first
$ sudo systemctl reload nginx
$ curl -i -H "Host: api.example.com" http://127.0.0.1/actuator/health

Step 7: point the domain (A record)

At your DNS provider, add an A record: name api, value your Elastic IP. Details are in Domains and DNS. Check it from your laptop:

$ dig +short api.example.com
203.0.113.25
$ curl -i http://api.example.com/actuator/health

Wait until dig returns your IP. Do not run certbot before DNS works; the certificate check needs to reach your server by that name.

Step 8: HTTPS with Let's Encrypt

Let's Encrypt issues free certificates, and certbot is the tool that obtains them and edits Nginx for you. (The certbot website also documents a snap-based install, which gives newer versions; the apt packages below are simplest on Ubuntu.)

$ sudo apt install -y certbot python3-certbot-nginx
$ sudo certbot --nginx -d api.example.com
# It asks for an email address and for you to accept the terms of service,
# then offers to redirect HTTP to HTTPS: choose the redirect.
$ curl -I https://api.example.com/actuator/health
HTTP/2 200
$ sudo certbot renew --dry-run         # prove that automatic renewal works
$ systemctl list-timers | grep certbot # the renewal timer

Certificates last a short time (90 days), so renewal must be automatic. The package installs a timer that runs twice a day; the dry run proves it works. Port 80 must stay open for renewals.

Step 9: survive crashes and reboots

Three layers keep the app alive: restart: unless-stopped restarts the container if it exits; Docker itself starts at boot (systemctl enable docker); Nginx is a systemd service and starts at boot (systemctl enable nginx, already done by the package). Test it once:

$ sudo reboot
# wait a minute, ssh in again
$ docker compose -f /opt/shop/compose.yaml ps
$ curl -s https://api.example.com/actuator/health

If you run a plain JAR without Docker, use a systemd unit instead (see Module 1 for how units work):

[Unit]
Description=Shop API
After=network.target

[Service]
User=shop
EnvironmentFile=/etc/shop/shop.env
ExecStart=/usr/bin/java -jar /opt/shop/app.jar
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

Step 10: logs

$ docker compose logs --tail 100 -f api
$ sudo tail -f /var/log/nginx/access.log /var/log/nginx/error.log

More methods are in Module 6.

Step 11: update to a new version, and roll back

Each build in your pipeline has an immutable tag (sha-xxxxxxx). A small script on the server changes the tag, pulls, restarts, checks health, and goes back automatically if the new version does not become healthy.

#!/usr/bin/env bash
# Usage: ./deploy.sh sha-3f9c2ab
set -euo pipefail
cd /opt/shop

NEW_TAG="${1:?usage: deploy.sh <image-tag>}"
OLD_TAG="$(grep '^IMAGE_TAG=' .env | cut -d= -f2)"

sed -i "s/^IMAGE_TAG=.*/IMAGE_TAG=${NEW_TAG}/" .env
echo "${OLD_TAG}" > .previous_tag

docker compose pull api
docker compose up -d api

for i in $(seq 1 40); do
  if curl -fsS http://127.0.0.1:8080/actuator/health > /dev/null; then
    echo "Healthy on ${NEW_TAG}"
    docker image prune -f > /dev/null
    exit 0
  fi
  sleep 3
done

echo "New version is not healthy, going back to ${OLD_TAG}"
sed -i "s/^IMAGE_TAG=.*/IMAGE_TAG=${OLD_TAG}/" .env
docker compose up -d api
exit 1
$ chmod +x /opt/shop/deploy.sh
$ /opt/shop/deploy.sh sha-9b1d4e7          # deploy a new version
$ /opt/shop/deploy.sh "$(cat /opt/shop/.previous_tag)"   # manual rollback

Module 4's CD workflow runs these same commands over SSH after the image is pushed. A rollback works only because old images still exist (so prune carefully) and because database changes are backward compatible.

Rule: only 80, 443 (and SSH from your IP) are public

The app port and the database port must never be reachable from the internet. From your laptop, curl http://203.0.113.25:8080 should time out.

Mistakes

  • Putting secrets in the Compose file or the image instead of an env file with mode 600.
  • Deploying latest, so you cannot name or roll back what runs.
  • Running certbot before the DNS record exists.
  • Editing files only on the server and not keeping the Compose file and Nginx config in Git.
  • Forgetting that stopping the instance changes the public IP when no Elastic IP is attached.

Edge cases

  • Let's Encrypt applies rate limits; use --dry-run or its staging server while testing.
  • If the app runs on Cloudflare's proxy (orange cloud), certificate and redirect settings behave differently; see Domains and DNS.
  • docker compose up -d recreates the container, causing a few seconds of downtime. See deployment strategies.

Interview: "Walk me through deploying a Spring Boot app to a server."

  • Provision (EC2, Elastic IP, security group), install Docker, pull the tagged image, run with env vars, Nginx reverse proxy, DNS A record, certbot HTTPS, restart policy, logs, scripted update with health check and rollback.
  • Add: secrets never in the image, only 80/443 public, database private.

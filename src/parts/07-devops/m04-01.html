CI/CD means a robot does the boring, risky work for you on every change: build the code, run the tests, package the app, and (if all is green) deploy it. GitHub Actions is the CI/CD service built into GitHub; you describe the steps in a YAML file inside your repository and GitHub runs them on its servers. Teams that do this ship smaller changes, more often, with fewer production surprises — and it is a standard expectation in a developer's first week at a company.

This module uses what you already know: Git branches and pull requests (Git · Module 3), Maven and tests (Core Java · Module 8, Spring Boot · Module 5), Docker images (Module 3) and SSH deployment to a Linux server (Module 1). Cloud-specific deployment targets follow in Module 5.

CI, continuous delivery and continuous deployment

Continuous Integration builds and tests every change automatically so the main branch always works; continuous delivery keeps every green build ready to release with one click; continuous deployment releases every green build to production automatically.

The problem CI solves

Without automation, a team of five works for two weeks on separate branches, merges everything on the last day, and finds that the pieces do not fit together. One person's change breaks another's, the tests were never run on the merged code, and a release needs a weekend. This is called integration hell. The cure is to integrate small changes often and let a machine check each one.

Three terms that sound alike

Continuous Integration (CI)
Every push and pull request triggers an automatic build and test run on a clean machine. Developers merge to the shared branch at least daily. The goal: main is always working.
Continuous Delivery (CD)
After CI passes, the pipeline also produces a release-ready artifact (a JAR or Docker image) and deploys it to a test/staging environment. Releasing to production is possible at any time, but a human clicks the button.
Continuous Deployment (CD)
Every change that passes all automated checks goes to production automatically, with no manual approval. It needs strong tests, monitoring and a fast rollback.

"CD" is used for both delivery and deployment; ask which one people mean. In your Project 3 you will build continuous deployment on a small scale: a merge to main deploys itself.

A pipeline as a picture

A pipeline is the whole chain from commit to running software. Each stage is a gate. If tests fail, nothing is packaged and nothing is deployed; the author gets an email or a red cross on the pull request.

Why CI matters for a team

  • Fast feedback. You learn within minutes that your change breaks a test — while you still remember the code.
  • A neutral build machine. "Works on my machine" is replaced by "works on the CI machine", which starts clean every time (right Java version, no leftover files).
  • A safe main branch. Combined with branch protection, broken code cannot be merged.
  • Repeatable releases. The same scripted steps run every time; no one forgets a step or deploys from a laptop.
  • Small, frequent releases. Small changes are easy to review and to roll back.
  • Quality gates. Style checks, test coverage, security scans and dependency checks run automatically on every pull request.

What CI/CD needs from you

Automation is only as good as what it runs. You need tests that are fast and reliable (a flaky test that fails randomly teaches everyone to ignore red builds), a build that works from a clean checkout with one command (./mvnw verify), configuration kept out of the code (environment variables, secrets), and a deployment you can repeat by script. Everything the pipeline does should also be doable by hand on your laptop.

Rule: a red main branch is the team's top priority

If the build on main fails, stop merging and fix or revert at once. Everyone else's pull requests will otherwise fail for reasons they did not cause.

Edge cases

  • CI proves only what your tests cover. A green build with weak tests gives false confidence.
  • Some changes (database migrations, breaking API changes) cannot simply be deployed and reverted; they need careful steps even with a perfect pipeline.
  • Continuous deployment is not "no testing"; it is "all the testing is automatic".

Interview: "What is the difference between CI, continuous delivery and continuous deployment?"

  • CI: automatic build and test on every change. Delivery: always releasable, production deploy is a manual decision. Deployment: every green change reaches production automatically.
  • Benefits: fast feedback, fewer integration problems, repeatable releases, smaller changes.

GitHub Actions concepts: workflows, jobs, steps, runners and expressions

A workflow is a YAML file in .github/workflows that runs when an event happens; it contains jobs (run on runners, in parallel unless you use needs), and each job is a list of steps that either run a shell command (run) or use a ready-made action (uses).

The building blocks

Workflow
One YAML file in .github/workflows/. A repository can have many (ci.yml, deploy.yml).
Event
What starts a workflow: a push, a pull request, a schedule, a manual click, a release.
Job
A group of steps that runs on one fresh runner machine. Jobs run in parallel by default.
Step
One task inside a job. Steps run in order and share the job's filesystem.
Action
A reusable, versioned unit of work (uses: actions/checkout@v4) written by GitHub or the community, found in the Marketplace.
Runner
The machine that runs a job. GitHub-hosted runners (ubuntu-latest, windows-latest, macos-latest) are fresh virtual machines that GitHub provides; self-hosted runners are machines you install the runner agent on (your own server, inside your network).

A first workflow

name: Hello

on: push

jobs:
  greet:
    runs-on: ubuntu-latest
    steps:
      - name: Say hello
        run: echo "Hello from commit ${{ github.sha }} on ${{ github.ref_name }}"
      - name: Show the runner
        run: |
          uname -a
          java -version

Push this file and open the repository's Actions tab: you see the run, each job and the log of every step. The file must be on the repository's default branch (or the branch you push) to run.

Run versus uses

A multi-line command uses | (each line is run in order; the step fails if a line fails). The version after @ is a tag, such as v4 (a major version that receives compatible updates), a full tag, or a commit SHA (the safest, immutable choice).

Check each action's README for the latest major version

Official actions release new majors regularly (for example to move to a newer Node.js runtime). The versions in these notes (actions/checkout@v4, actions/setup-java@v4, actions/upload-artifact@v4, docker/build-push-action@v6 and so on) were current when written. Before you copy a workflow, open each action's page on GitHub and use the latest major shown in its README. Dependabot can also open pull requests that update action versions for you.

needs, if, env and outputs

env:
  JAVA_VERSION: "21"             # workflow-level variable

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: echo "testing with Java $JAVA_VERSION"

  package:
    needs: test                  # waits for 'test'; skipped if 'test' fails
    runs-on: ubuntu-latest
    steps:
      - run: echo "packaging"

  deploy:
    needs: [test, package]
    if: github.ref == 'refs/heads/main'   # only on main
    runs-on: ubuntu-latest
    steps:
      - name: Only when a previous step failed
        if: failure()
        run: echo "something earlier failed"
      - run: echo "deploying"
  • needs creates the order between jobs. Without it, jobs start at the same time.
  • if decides whether a job or step runs. Status functions: success() (default), failure(), always(), cancelled().
  • env can be set at workflow, job or step level; inner levels override outer ones.
  • Jobs run on different machines, so files from one job are not available in another. Pass files with artifacts and small values with outputs.

Contexts and expressions

Inside ${{ ... }} you write an expression that reads a context (an object with information) or calls a function. GitHub evaluates it before the step runs.

ExpressionGives
${{ github.sha }}The full commit SHA being built
${{ github.ref_name }}Branch or tag name (main, v1.2.0)
${{ github.actor }}The user who triggered the run
${{ github.repository }}owner/repo
${{ github.event_name }}push, pull_request, ...
${{ secrets.DEPLOY_KEY }}A secret value (masked in logs)
${{ vars.APP_URL }}A non-secret configuration variable
${{ runner.os }}Linux, Windows, macOS
${{ matrix.java }}Current value in a matrix build
${{ hashFiles('**/pom.xml') }}A hash of matching files (cache keys)

Matrix builds

A matrix runs the same job several times with different values — for example tests on Java 17 and 21, or on Linux and Windows. GitHub creates one job per combination.

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false            # let other combinations finish if one fails
      matrix:
        java: [17, 21]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: ${{ matrix.java }}
      - run: ./mvnw -B verify

Permissions, GITHUB_TOKEN and concurrency

Every run gets a temporary GITHUB_TOKEN, valid only for that run and that repository. What it may do is set by the permissions key. Follow least privilege: give read access by default and add more only to jobs that need it.

permissions:
  contents: read                 # default for all jobs

concurrency:
  group: ci-${{ github.ref }}    # one run per branch at a time
  cancel-in-progress: true       # a new push cancels the older run

jobs:
  publish:
    permissions:
      contents: read
      packages: write            # this job may push to GHCR
    runs-on: ubuntu-latest
    steps:
      - run: echo "pushing"

A concurrency group makes sure only one run of that group is active. For CI, cancelling older runs on the same branch saves time and minutes. For deployments, use cancel-in-progress: false so a deploy is never cut in half.

Artifacts and caching in one line each

  • Artifact — a file produced by a run (test reports, a JAR) that you can download or pass to a later job: actions/upload-artifact and actions/download-artifact.
  • Cache — files reused between runs (Maven's ~/.m2) to make builds faster: actions/cache, or built into setup-java and setup-node.

YAML basics and indentation pitfalls

  • Indentation is meaning. Use spaces (two per level), never tabs. A step must be indented under steps:, and with: keys under their step.
  • A list item starts with - . In steps, each item is one step.
  • Quote strings that could be read as something else: java-version: "21" is fine either way, but "1.10" must be quoted or it becomes the number 1.1. Quote values starting with ${{ or containing : or # when in doubt.
  • on: and jobs: are top-level keys; a missing or misplaced space is the usual cause of "Invalid workflow file" errors.
  • A comment starts with #. The editor on github.com shows YAML errors before you commit; VS Code with the GitHub Actions extension validates too.

Mistake: the workflow file is in the wrong place or has the wrong extension

It must be at .github/workflows/name.yml (or .yaml) in the repository root. .github/workflow/ (missing s) or a file in a sub-folder never runs, and no error is shown.

Mistake: expecting files to exist in another job

Each job starts on a clean runner. A JAR built in build does not exist in deploy unless you upload and download it as an artifact, or rebuild, or push an image to a registry and pull it.

Interview: "Explain GitHub Actions: workflow, job, step, runner."

  • A workflow (YAML) is triggered by an event; it has jobs that run in parallel on separate runners (needs orders them); each job has sequential steps that are run commands or reusable uses actions.
  • Contexts such as github.sha and secrets.X; matrix for variations; permissions for the token; concurrency to avoid overlapping runs.

Workflow triggers: push, pull_request, manual, schedule and tags

The on: key decides when a workflow runs — typically push and pull_request with branch and path filters for CI, workflow_dispatch for a manual button, schedule for cron jobs and tag or release events for versioned releases.

push and pull_request

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

With this, a push to main (including a merge) triggers the workflow, and so does any pull request that targets main — on creation and on each new commit pushed to it.

  • push runs on the pushed commit of that branch.
  • pull_request runs on a merge preview of the PR branch into the target branch, so you test what main would look like after the merge. This is the check that branch protection uses.
  • Feature branches without a pull request do not run, because of the filter. If you want CI on every branch push, use on: push without branches; but then a PR commit runs twice (once for push, once for the PR). Limiting push to main avoids this.

Filters: branches, paths and tags

on:
  push:
    branches: [main, "release/**"]      # patterns: * and ** wildcards
    paths:
      - "src/**"
      - "pom.xml"
  pull_request:
    branches: [main]
    paths-ignore:                       # use paths OR paths-ignore for one event, not both
      - "**.md"
    types: [opened, synchronize, reopened]   # default types; shown explicitly
FilterEffect
branches / branches-ignoreRun only for (or never for) matching branch names
paths / paths-ignoreRun only when changed files match (e.g. do not run a backend build for a README edit)
tagsRun on pushes of matching tags, e.g. v*
typesWhich activity of the event: PR opened, synchronize (new commits), reopened, ...

Careful with path filters and required checks: if a workflow is skipped because of its path filter, a required status check from it stays "pending" and the PR cannot be merged. Either do not use path filters on workflows that branch protection requires, or add a small always-running job that reports status.

workflow_dispatch: a manual button

on:
  workflow_dispatch:
    inputs:
      image_tag:
        description: "Image tag to deploy (e.g. a git SHA)"
        required: true
        type: string

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying tag ${{ inputs.image_tag }}"

The workflow appears with a Run workflow button in the Actions tab (the file must be on the default branch). It is perfect for "deploy this tag" and rollbacks, or for jobs you want to test without pushing commits. You can also trigger it with the GitHub CLI: gh workflow run deploy.yml -f image_tag=3f9c2ab.

schedule: cron

on:
  schedule:
    - cron: "0 2 * * *"      # minute hour day-of-month month day-of-week

The cron time is always UTC. India Standard Time is UTC+5:30, so 02:00 UTC is 07:30 IST. Scheduled runs happen on the default branch, may start a few minutes late when GitHub is busy, and GitHub may disable schedules on repositories with no activity for a long time. Use them for nightly full test suites, dependency checks or clean-up jobs.

Tags and releases

on:
  push:
    tags:
      - "v*.*.*"             # v1.2.0, v2.0.1 ...
  release:
    types: [published]

Create a tag with git tag v1.2.0 && git push origin v1.2.0. The workflow can then build the image with the tag name (${{ github.ref_name }}) and publish a GitHub Release. This is the usual way to produce versioned releases.

A few more events

  • workflow_call — lets one workflow call another (reusable workflows), so many repositories share one CI definition.
  • workflow_run — start a workflow after another one finishes (for example deploy after CI).
  • pull_request_target — runs with the base repository's permissions and secrets even for forks; powerful and easy to misuse. Avoid it until you understand the security notes in the GitHub docs.
  • issues, issue_comment, repository_dispatch — automation around issues and external triggers.

Documentation of every event and filter: docs.github.com/en/actions.

Mistake: workflow triggers itself, or runs twice per PR commit

  • A workflow that pushes a commit with the default GITHUB_TOKEN does not trigger other workflows (GitHub prevents loops), which surprises people who expect it to.
  • on: [push, pull_request] without filters runs twice for a PR branch commit. Filter push to main.

Edge cases

  • Pull requests from forks run with a read-only token and no secrets, so steps that need secrets (deploy, push image) must not run for them.
  • A workflow with on: pull_request uses the workflow file from the merge commit, so you can test a changed workflow inside its own PR.
  • Commits whose message contains [skip ci] skip push and pull_request workflows (useful for docs-only changes; check the GitHub docs for the exact supported phrases).

Interview: "When does your CI run, and how do you stop it running when only the README changed?"

  • On pull requests to main and on pushes to main; manual workflow_dispatch; optionally a nightly cron.
  • Use paths/paths-ignore filters, mindful of required status checks.

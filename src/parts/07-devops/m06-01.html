Reading your app's logs on a server

Run docker compose logs -f --tail 100 api (or journalctl -u shop -f for a systemd service) to follow the application log, search it with grep and less, and rotate logs so they cannot fill the disk.

Where logs live

A log is a time-ordered text record of what the application did and what went wrong. Where you find it depends on how the app runs:

How it runsWhere the log isCommand
Docker containerCaptured from stdout/stderr by Dockerdocker logs
Docker ComposeSame, grouped by servicedocker compose logs
systemd service (a JAR)The journaljournalctl -u shop
Plain process with file loggingA file such as /var/log/shop/app.logtail, less
Nginx/var/log/nginx/access.log and error.logtail, grep
PaaS (Render, Railway)The platform's log viewerDashboard or CLI

Spring Boot writes to the console (stdout) by default. In containers that is exactly right: the platform collects stdout, and the app does not manage files. This is one of the twelve-factor ideas: treat logs as an event stream.

Docker and Compose

$ docker logs shop-api                      # everything since the container started
$ docker logs --tail 100 shop-api           # the last 100 lines
$ docker logs -f --tail 100 shop-api        # follow new lines (Ctrl+C to stop)
$ docker logs --since 10m shop-api          # the last 10 minutes
$ docker logs -t shop-api | tail            # add Docker's timestamps

$ cd /opt/shop
$ docker compose logs -f --tail 100 api     # one service
$ docker compose logs -f                    # all services, interleaved
$ docker compose logs --no-color --since 1h api > api.log   # save for sharing

Note that docker logs shows logs of a container that still exists, even if stopped. When a container is removed (for example by docker compose down or a recreate), its json log file is removed with it. After a crash, look first, then restart.

systemd and the journal

$ journalctl -u shop -f                         # follow
$ journalctl -u shop -n 200 --no-pager          # last 200 lines
$ journalctl -u shop --since "1 hour ago"
$ journalctl -u shop --since "2026-11-11 09:00" --until "2026-11-11 09:30"
$ journalctl -u shop -p err                     # only errors and worse
$ journalctl -b -1                              # the previous boot, useful after a crash/reboot
$ journalctl -u docker --since today            # logs of the Docker service itself

Add sudo if your user is not in the systemd-journal group. The journal's size can be capped with SystemMaxUse=500M in /etc/systemd/journald.conf.

Searching logs: grep, less, awk

$ docker compose logs api | grep -i error                  # case-insensitive
$ docker compose logs api | grep -C 5 "NullPointerException"  # 5 lines around each match
$ docker compose logs api | grep -c "WARN"                 # count matches
$ grep -r "OrderService" /var/log/shop/ | tail             # search several files
$ zgrep "ERROR" /var/log/shop/app.log.*.gz                 # search rotated, compressed logs
$ less +F /var/log/shop/app.log                            # follow inside less; Ctrl+C to stop following

# Nginx access log: count responses per status code
$ awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
# the busiest client IPs
$ awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head

Inside less: / then a word searches forward, n jumps to the next match, G goes to the end, g to the start, q quits. In the default Nginx log format the status code is the 9th space-separated field, which is why the awk line works; if you change the log format, adjust it.

Log levels and Spring Boot settings

Levels from quiet to loud are ERROR, WARN, INFO, DEBUG, TRACE. Production usually runs at INFO for your code and WARN for libraries. Set levels in properties or environment variables:

logging.level.root=WARN
logging.level.com.shop=INFO
# only if you must log to a file (not needed in containers):
logging.file.name=/var/log/shop/app.log
logging.logback.rollingpolicy.max-file-size=20MB
logging.logback.rollingpolicy.max-history=14

With Actuator's loggers endpoint exposed (and protected!), you can change a level on a running app without restarting, which is handy for a short debugging session:

$ curl -X POST -H "Content-Type: application/json" \
    -d '{"configuredLevel":"DEBUG"}' http://127.0.0.1:8080/actuator/loggers/com.shop.orders
$ curl -X POST -H "Content-Type: application/json" \
    -d '{"configuredLevel":null}' http://127.0.0.1:8080/actuator/loggers/com.shop.orders

Version note: structured logging

Spring Boot 3.4 and later (including 4.x) can write logs as JSON for log tools using properties such as logging.structured.format.console=ecs (other formats include logstash). On older 3.x versions use a Logback encoder library. JSON logs are far easier to search in a central system.

Stop logs from filling the disk

A full disk kills a server: the database cannot write, the app crashes, even SSH can misbehave. Docker's default json-file driver keeps logs forever unless you limit them. Set limits per service in Compose (as in the runbook), or for all containers in /etc/docker/daemon.json:

{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}

Restart Docker after editing (sudo systemctl restart docker); the new default applies only to containers created afterwards. For plain log files, logrotate renames, compresses and deletes old files on a schedule:

/var/log/shop/*.log {
    daily
    rotate 14
    compress
    missingok
    notifempty
    copytruncate
}

copytruncate copies the file and empties the original, so a running app that keeps the file open continues to write without a restart. Check space regularly with df -h, du -sh /var/log/* and docker system df.

Centralised logging, in one paragraph

With one server, SSH and grep are enough. With many servers or containers, logs vanish when a container is replaced and searching ten machines by hand is painful. A centralised logging system ships every log line to one searchable place. Two popular stacks are ELK (Elasticsearch stores and indexes, Logstash or Beats ship, Kibana searches and charts) and Loki with Grafana (an agent such as Promtail or Grafana Alloy ships logs; Loki indexes only labels, so it is lighter; you search in Grafana). On AWS, CloudWatch Logs does this for you. Use structured JSON logs and a correlation (request) ID in every line so one request can be followed across services.

Rule: never log secrets or personal data

Do not log passwords, JWTs, API keys, full card numbers or whole request bodies. Logs are copied, shared and kept for months, and many people can read them.

Mistakes

  • Running at DEBUG in production: huge logs, slower app, leaked data.
  • Restarting or recreating the container before reading the log of the crash.
  • Using System.out.println or e.printStackTrace() instead of a logger with levels and timestamps.
  • No limit on Docker log size, then "No space left on device" months later.

Interview: "How do you debug a production problem using logs?"

  • Find the time window, follow or filter the logs (--since, grep -C), find the first error (not the last), use a request ID to follow one request, check the stack trace's "Caused by".
  • Mention log levels, rotation, structured logs and centralised logging for many servers.

Why did my app crash? A step-by-step walkthrough

Check whether the container or service is running and how it exited, read the lines just before the death, then match the symptom to one of the usual causes: killed for memory (exit 137), port already in use, database refused, missing environment variable, or a full disk.

The method

Do not guess and do not restart blindly. Follow the same order every time:

$ docker compose ps -a                        # status and exit code (Exited (137) ...)
$ docker inspect -f '{{.State.ExitCode}} oom={{.State.OOMKilled}}' shop-api-1
137 oom=true
$ docker compose logs --tail 200 api          # the end of the log
$ df -h / ; free -h                           # disk and memory right now

Exit codes tell a lot. 0 means a clean exit. 1 means the application failed (an exception during startup). 137 means the process received SIGKILL (128 + 9), most often from the out-of-memory killer. 143 means SIGTERM (128 + 15): a normal stop request from docker stop or a deploy.

Cause 1: the process was killed for memory (exit 137)

Symptom: the container restarts at random times, exit code 137, OOMKilled is true, and the app log simply stops with no stack trace, because the kernel killed the process instantly.

$ sudo dmesg -T | grep -i -E "out of memory|killed process"
[Tue Nov 11 09:14:02 2026] Out of memory: Killed process 4218 (java) total-vm:3482112kB ...

Why: the JVM uses more than heap (metaspace, thread stacks, buffers), and the machine or container limit is smaller than the total. Fix: give the JVM less than the limit with -XX:MaxRAMPercentage=75 (in JAVA_TOOL_OPTIONS), move to a bigger instance, add swap as a safety net, stop other memory eaters, and look for a leak.

Do not confuse this with a Java-level java.lang.OutOfMemoryError: Java heap space, which is in the log with a stack trace: the heap itself was too small or leaking. To study it, run with -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp and open the dump in a tool such as Eclipse MAT or VisualVM (see Core Java · Module 7).

Cause 2: the port is already in use

***************************
APPLICATION FAILED TO START
***************************

Description:

Web server failed to start. Port 8080 was already in use.

Action:

Identify and stop the process that's listening on port 8080 or configure
this application to listen on another port.

Find the owner:

$ sudo ss -ltnp | grep ':8080'
LISTEN 0 100 *:8080 *:* users:(("java",pid=2311,fd=9))
$ docker ps --format '{{.Names}} {{.Ports}}' | grep 8080

Typical reasons: an old copy of the app (a forgotten manual java -jar), two containers publishing the same host port, or a new container started before the old one released the port. Stop the other process, or map a different host port.

Cause 3: the database refuses the connection

HikariPool-1 - Exception during pool initialization.
org.postgresql.util.PSQLException: Connection to localhost:5432 refused.
Check that the hostname and port are correct and that the postmaster is accepting TCP/IP connections.
Caused by: java.net.ConnectException: Connection refused

Read the host in the message. Check, in this order:

  1. Wrong host. localhost inside a container means the container itself. Use the Compose service name (postgres) or the RDS endpoint (see Docker networks).
  2. Database not ready or not running. docker compose ps; use a healthcheck and depends_on: condition: service_healthy.
  3. Network rule. For RDS, a timeout (not "refused") usually means the security group does not allow the app's group on 5432.
  4. Credentials. password authentication failed for user means the host is reachable but the user or password is wrong. database "shop" does not exist means a wrong name.
  5. Too many connections. Pool size times instances is above the server limit.
$ docker compose exec api sh -c 'getent hosts postgres'
$ docker run --rm --network shop_default postgres:16 \
    psql -h postgres -U shop_app -d shop -c 'select 1'

Cause 4: a missing or wrong environment variable

Caused by: java.lang.IllegalArgumentException:
Could not resolve placeholder 'JWT_SECRET' in value "${JWT_SECRET}"

The code expects a variable that the container does not have. See what the container actually got, and what Compose resolved:

$ docker compose config | grep -A 12 environment     # after variable substitution
$ docker compose exec api env | grep -E "SPRING|JWT|DB_"

Common reasons: the variable is missing from .env, a typo in the name, a value with a space or special character that needs quotes, an env_file path that is wrong, or the container was not recreated after the file changed (docker compose up -d recreates only when the configuration differs, so run it again after editing, and check).

Cause 5: the disk is full

java.io.IOException: No space left on device
ERROR: could not write to file "pg_wal/xlogtemp.123": No space left on device
$ df -h
$ sudo du -xh / --max-depth=2 2>/dev/null | sort -rh | head -15
$ docker system df
$ docker system prune -f              # removes stopped containers, dangling images, unused networks
$ sudo journalctl --vacuum-size=200M  # shrink the journal

Typical culprits: unlimited container logs, old images, a growing upload folder, a database dump left in place. Fix by cleaning, then add log rotation and a disk alert so it does not return.

More causes worth a quick check

  • Wrong Java version: UnsupportedClassVersionError means the JAR was compiled for a newer Java than the runtime image provides.
  • Migration failed: Flyway reports a checksum mismatch or a failed script; the app refuses to start. Read the migration name in the log.
  • The health check kills a slow starter: an orchestrator restarts the app before it finished starting; add a startup probe or a longer initial delay.
  • Permissions: the app cannot write to a mounted folder owned by root.
  • Certificates or DNS: UnknownHostException for an external API, or SSL handshake errors, point to network or trust problems.

Tip: write a post-mortem note

After fixing, write three lines: what happened, the cause, what you changed so it will not repeat (a memory limit, an alert, a test). This habit is what turns incidents into experience, and interviewers like to hear one real story.

Edge cases

  • With restart: unless-stopped, a crash loop can restart the app every few seconds and fill the log. Use docker compose ps to see the restart count, and stop the loop to investigate.
  • The first error in a log is usually the real cause. Later errors are often side effects.
  • A Java OutOfMemoryError for "unable to create native thread" is about the OS thread or memory limit, not the heap.

Interview: "The app keeps restarting in production. What do you do?"

  • Check status and exit code, read the log before the exit, check memory and disk, then match the cause (137 OOM, port conflict, DB connection, missing config). Fix, redeploy, verify the health endpoint, and add monitoring so you hear about it first next time.

Observability: logs, metrics, traces and the golden signals

Observability means you can understand what a running system is doing from its outputs: logs say what happened, metrics say how much and how fast, traces show the path of one request; watch the four golden signals (latency, traffic, errors, saturation) to know whether users are happy.

Monitoring vs observability

Monitoring watches known things: "is the site up, is CPU above 90%?". It answers the questions you thought of in advance. Observability is the ability to ask new questions about a live system ("why are orders from one city slow since 3 pm?") using the data it emits, without shipping new code first. You need both: monitoring tells you something is wrong, observability helps you find out why.

The three pillars

PillarWhat it isGood forTypical tools
LogsTimestamped events with details"What exactly happened in this request?"Docker logs, ELK, Loki, CloudWatch
MetricsNumbers sampled over time (counters, gauges, histograms)Trends, dashboards, alertsPrometheus, Grafana, CloudWatch
TracesThe timeline of one request across services, as nested spans"Which service made this slow?"OpenTelemetry, Zipkin, Jaeger, Tempo

Metrics are cheap and compact, so they power alerts. Logs are rich but heavy. Traces matter most in microservices, where one user click touches many services; see Spring Boot · Module 7 for Micrometer Tracing and distributed tracing. The three connect through shared identifiers: a trace ID printed in each log line lets you jump from a slow trace to its logs.

The four golden signals

Google's Site Reliability Engineering book names four signals that describe the health of almost any service. If you can watch only four things, watch these.

Latency
How long requests take. Look at percentiles (p50, p95, p99), not the average, because the slowest 1% of users matter. Separate the latency of failed requests from successful ones.
Traffic
How much demand: requests per second, messages per minute.
Errors
The rate of failing requests: HTTP 5xx, exceptions, timeouts, and wrong results.
Saturation
How full the system is: CPU, memory, disk, thread pool, database connection pool, queue length. Latency rises sharply as saturation nears 100%.

Two shortcuts help you choose metrics: the RED method for request-driven services (Rate, Errors, Duration), and the USE method for resources like CPU, disk and network (Utilisation, Saturation, Errors). RED tells you how users feel; USE tells you which machine part is the bottleneck.

Golden signalSpring Boot / JVM example
Latencyhttp.server.requests timer (p95), database query time
TrafficRequest count per second per endpoint
ErrorsCount of responses with status 5xx; exceptions per minute
SaturationJVM heap used vs max, GC pause time, Hikari active connections vs max, Tomcat threads busy, CPU, disk

What to alert on

Alert on symptoms users feel, not on every cause. "Error rate above 5% for 5 minutes" and "p95 latency above one second for 10 minutes" are good alerts. "CPU above 80% for a minute" often is not: it may be fine, and it wakes you for nothing. Too many alerts cause alert fatigue, and people begin to ignore them. Every alert should be actionable, and link to a runbook that says what to check first. Terms you will hear: SLI (service level indicator: a measured number such as the percentage of successful requests), SLO (the target for it, such as 99.9% over 30 days) and the error budget (how much failure the SLO still allows, used to decide between shipping features and fixing reliability).

Mistakes

  • Looking at average latency only; a few very slow requests hide inside it.
  • Metrics with unbounded labels (a user ID or full URL as a label): the number of time series explodes and memory runs out (high cardinality). Use the URI template /orders/{id}, not /orders/42.
  • Dashboards nobody looks at, and alerts nobody acts on.

Interview: "What is observability? What are the golden signals?"

  • Logs, metrics and traces help you explain system behaviour from outside. The golden signals are latency, traffic, errors and saturation. Use percentiles; alert on user-visible symptoms; link alerts to runbooks.
  • Mention RED for services, USE for resources, and OpenTelemetry as the vendor-neutral standard.

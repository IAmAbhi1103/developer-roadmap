Health checks: Actuator, liveness vs readiness, Docker and load balancers

Spring Boot Actuator exposes /actuator/health (UP returns 200, DOWN returns 503); use it for Docker HEALTHCHECK, load-balancer target checks and uptime monitors, and split it into liveness ("restart me?") and readiness ("send me traffic?") for orchestrators.

Why health checks

A running process is not always a working application. The JVM can be alive while the database pool is exhausted or startup is not finished. A health check is a cheap URL or command that answers "is this instance OK?". Docker, load balancers, Kubernetes and monitoring tools call it on a schedule and act: stop sending traffic, restart the container, or alert you.

Actuator basics

Add spring-boot-starter-actuator to the project. The health endpoint combines many health indicators (database connectivity, disk space, Redis and so on) into one status.

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
management.endpoints.web.exposure.include=health,info
management.endpoint.health.show-details=when-authorized
management.endpoint.health.probes.enabled=true
GET /actuator/health HTTP/1.1

HTTP/1.1 200 OK
Content-Type: application/vnd.spring-boot.actuator.v3+json

{"status":"UP"}

HTTP/1.1 503 Service Unavailable

{"status":"DOWN"}

Without extra properties only the overall status is shown, which is what you want on the public internet. show-details=when-authorized shows which component failed only to authenticated users; never expose details publicly because they reveal your internals. Only the endpoints listed in exposure.include are reachable over the web, so list the minimum.

A custom health indicator

Add checks for things your app really depends on, such as a payment gateway. Keep them fast and time-limited: a slow health check can itself cause outages.

@Component
public class PaymentGatewayHealthIndicator implements HealthIndicator {

    private final PaymentClient client;

    public PaymentGatewayHealthIndicator(PaymentClient client) {
        this.client = client;
    }

    @Override
    public Health health() {
        try {
            client.ping();                      // must be quick, with a short timeout
            return Health.up().withDetail("gateway", "reachable").build();
        } catch (Exception e) {
            return Health.down(e).build();
        }
    }
}

Version note: Actuator packages in Spring Boot 4

Spring Boot 4 split Actuator into smaller modules, and some health classes moved to new packages. The idea (implement HealthIndicator, return Health) is the same, but check the Boot 4 migration notes for the exact imports if you upgrade.

Liveness vs readiness

Two different questions, and mixing them causes outages.

LivenessReadiness
QuestionIs the process stuck or broken beyond repair?Can it serve requests right now?
If it failsThe orchestrator restarts the containerThe instance is removed from the load balancer; no restart
Should includeOnly the app's own state (not external services)Dependencies the app needs to work, such as the database
Spring URL/actuator/health/liveness/actuator/health/readiness

If liveness included the database and the database had a short outage, an orchestrator would restart every app instance in a loop and make the incident worse. Readiness is the right place for the database: the instance stops receiving traffic until the database returns, then rejoins. Spring Boot enables these two groups automatically when it detects Kubernetes; elsewhere turn them on with management.endpoint.health.probes.enabled=true. Choose what the readiness group contains:

management.endpoint.health.group.readiness.include=readinessState,db
management.endpoint.health.group.liveness.include=livenessState

Spring also publishes the state during shutdown: when the app is stopping, readiness turns REFUSING_TRAFFIC first, so a load balancer stops sending new requests (pair this with server.shutdown=graceful).

Docker HEALTHCHECK and Compose

Docker can run a command inside the container and mark it healthy or unhealthy. The image needs the tool you call; slim images may lack curl, so install it or use another tool that exists there.

HEALTHCHECK --interval=30s --timeout=3s --start-period=60s --retries=3 \
  CMD curl -fsS http://localhost:8080/actuator/health || exit 1
services:
  api:
    image: ghcr.io/asha/shop-api:${IMAGE_TAG}
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost:8080/actuator/health"]
      interval: 30s
      timeout: 3s
      retries: 3
      start_period: 60s        # failures during startup do not count
  worker:
    image: ghcr.io/asha/shop-worker:${IMAGE_TAG}
    depends_on:
      api:
        condition: service_healthy   # start only after api is healthy

Plain Docker marks a container unhealthy but does not restart it by itself (Docker Swarm and orchestrators do). Use docker ps to see (healthy), and combine with an uptime monitor.

Load balancers and platforms

  • AWS ALB: each target group has a health check path (/actuator/health or the readiness URL), an interval, and thresholds. Instances failing the check are taken out of rotation.
  • Render, Railway and others: set the health check path in service settings; a new deployment receives traffic only after it passes, which gives zero-downtime deploys.
  • Kubernetes: liveness, readiness and startup probes (next articles).

Security of health endpoints

  • If you use Spring Security, permit /actuator/health/** without login, and protect other Actuator endpoints with a role. See Spring Boot · Module 4.
  • Better still, put Actuator on a separate port that is never published: management.server.port=8081. Then probes and Prometheus use the internal network, and nothing sensitive is reachable through Nginx. (If you move the port, point your Docker or Kubernetes checks to it.)
  • For the uptime monitor, expose only a simple public health URL, or a separate small endpoint.

Mistakes

  • Health checks that call slow external services, so one slow partner marks every instance DOWN.
  • Putting the database in liveness (restart storms).
  • Exposing * endpoints or full health details publicly.
  • A start period that is shorter than your app's startup time, so it gets killed while starting.
  • Health only checks "process is up" (a static 200) and hides a broken database.

Interview: "Liveness vs readiness probe?"

  • Liveness decides if the container should be restarted; readiness decides if it receives traffic. Keep external dependencies out of liveness. Spring Boot provides both through Actuator health groups.

Uptime monitoring and alerts to email, Slack and Telegram

An external service calls your public health URL every few minutes from outside your infrastructure and alerts you by email, Slack or Telegram when it fails, so you hear about an outage before your users tell you.

Why monitor from outside

If your monitoring runs on the same server as the app, it dies with it. An uptime monitor is a service on someone else's infrastructure that requests your URL from outside, through the same path as a real user: DNS, the internet, TLS, Nginx, and the app. If any link breaks, it notices. Popular services are UptimeRobot and Better Stack (formerly Better Uptime); both have free plans at the time of writing, with limits on check interval and number of monitors that change, so check the current terms. Healthchecks.io works the other way round for scheduled jobs: your cron job pings it after each run, and it alerts if a ping is missing (a "dead man's switch", good for nightly backups).

Set up a monitor, step by step

  1. Choose the URL: https://api.example.com/actuator/health through your real domain, over HTTPS. Add a second monitor for the frontend URL.
  2. Choose type "HTTP(s)". Better still, use a keyword check that expects "status":"UP" in the body: a custom error page with status 200 would otherwise look healthy.
  3. Set the interval as short as your plan allows (often one to five minutes).
  4. Add alert contacts: email first, then a chat tool. Test them with the service's test button.
  5. Require two failed checks in a row before alerting, so one network blip does not wake you.
  6. Add monitors for the TLS certificate expiry and, if available, the domain expiry.
  7. Optionally publish a public status page.

Alert channels

  • Email: the baseline. Put the address on your phone with push notifications.
  • Slack or Discord: create an incoming webhook for a channel; most monitoring tools already have a ready integration.
  • Telegram: create a bot with BotFather (it gives you a token), start a chat with the bot, find your chat ID, and paste both into the tool's Telegram integration. It is free and reaches your phone quickly, which suits solo developers.

You can also send your own alerts from scripts, for example at the end of a failed deployment. Treat the webhook URL and the bot token as secrets: keep them in environment variables or CI secrets.

# Slack incoming webhook
$ curl -fsS -X POST -H 'Content-type: application/json' \
    --data '{"text":"Deploy of sha-9b1d4e7 failed on production"}' "$SLACK_WEBHOOK_URL"

# Telegram bot
$ curl -fsS "https://api.telegram.org/bot${BOT_TOKEN}/sendMessage" \
    -d chat_id="${CHAT_ID}" -d text="Deploy of sha-9b1d4e7 failed on production"

Add this to the failure branch of your deploy workflow (Module 4), so the pipeline tells you when it breaks.

Good alerting habits

  • Alert on user-visible failure, not on every internal blip.
  • Make each alert say what failed, since when, and where to look first (link to the runbook).
  • Do not alert your whole team on a learning project, and do not mute alerts permanently because they are noisy; fix the noise.
  • Test the whole path by stopping the app once and checking that your phone receives the alert.

Mistakes

  • Monitoring only the home page of the frontend and never the API.
  • Alerts going to an email address nobody reads (compare the billing alert advice in Module 5).
  • Pinging a free, sleeping service every few minutes to keep it awake: it can break the platform's rules or use up its allowance. Read the platform terms.
  • Checking the root URL / that serves a cached or static page and stays 200 when the API is dead.

Interview: "How do you know your service is down before customers do?"

  • External uptime checks on a real health URL with keyword assertion, alert routing to chat or phone, metrics-based alerts on error rate and latency, and an on-call or at least a runbook.

Prometheus and Grafana: metrics from Spring Boot with Docker Compose

Spring Boot (Actuator plus Micrometer) exposes metrics at /actuator/prometheus; Prometheus pulls and stores them on a schedule defined in prometheus.yml, and Grafana draws dashboards from Prometheus.

The pull model

Prometheus is a time-series database and monitoring system. It uses a pull model: instead of your app sending data, Prometheus visits each target's metrics URL every few seconds ("scrapes" it) and stores the numbers with timestamps. The advantages are simple targets (they only expose text), and Prometheus itself notices a dead target, because the scrape fails (the metric up becomes 0). Grafana is the dashboard tool; it reads from Prometheus (and from Loki, PostgreSQL, CloudWatch and others) and draws graphs.

Expose metrics from Spring Boot

Micrometer is the metrics facade inside Spring Boot (like SLF4J for logging). The Prometheus registry turns its metrics into Prometheus text format. Add the dependency (the version is managed by Boot):

<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
management.endpoints.web.exposure.include=health,info,prometheus
management.metrics.tags.application=shop-api
management.metrics.distribution.percentiles-histogram.http.server.requests=true
# optional: serve Actuator on a private port that is never published
management.server.port=8081
  • management.metrics.tags.application adds a label to every metric so you can tell apps apart in one Prometheus.
  • percentiles-histogram…http.server.requests=true publishes histogram buckets for request time. Without them you cannot calculate p95 with histogram_quantile (see the PromQL article).
  • management.server.port keeps metrics off the public port. Prometheus reaches api:8081 inside the Docker network; Nginx does not proxy to it.

Open the endpoint to see the format: lines of name{labels} value.

# HELP http_server_requests_seconds Duration of HTTP server request handling
# TYPE http_server_requests_seconds histogram
http_server_requests_seconds_count{method="GET",status="200",uri="/api/products"} 1542
http_server_requests_seconds_sum{method="GET",status="200",uri="/api/products"} 61.4
http_server_requests_seconds_bucket{le="0.1",method="GET",status="200",uri="/api/products"} 1390
jvm_memory_used_bytes{area="heap",id="G1 Eden Space"} 5.2428800E7
process_cpu_usage 0.031
hikaricp_connections_active{pool="HikariPool-1"} 2.0

Metric types

Counter
A number that only goes up (requests served). You almost always look at its rate of change, with rate().
Gauge
A value that goes up and down (heap used, active connections).
Histogram / timer
Counts observations in buckets (_bucket), plus a total (_sum) and a count (_count). Used for latency.

The scrape configuration

global:
  scrape_interval: 15s            # how often to scrape
  evaluation_interval: 15s        # how often to evaluate alert rules

rule_files:
  - /etc/prometheus/alerts.yml

scrape_configs:
  - job_name: shop-api
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ["api:8081"]     # service name and management port on the Compose network

  - job_name: prometheus          # Prometheus monitors itself too
    static_configs:
      - targets: ["localhost:9090"]

A job is a group of targets with the same purpose; every sample gets the labels job and instance (the address). Spring Boot's default path is not Prometheus's default path, so metrics_path is essential. Use static_configs for fixed hosts; on Kubernetes or AWS Prometheus finds targets through service discovery.

Run Prometheus and Grafana with Docker Compose

services:
  prometheus:
    image: prom/prometheus
    volumes:
      - ./prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - ./prometheus/alerts.yml:/etc/prometheus/alerts.yml:ro
      - prometheus-data:/prometheus
    ports:
      - "127.0.0.1:9090:9090"       # only reachable from the server itself
    restart: unless-stopped

  grafana:
    image: grafana/grafana
    environment:
      GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_PASSWORD}
    volumes:
      - grafana-data:/var/lib/grafana
    ports:
      - "127.0.0.1:3000:3000"
    depends_on:
      - prometheus
    restart: unless-stopped

volumes:
  prometheus-data:
  grafana-data:
$ docker compose -f compose.yaml -f compose.monitoring.yaml up -d
$ ssh -i shop-key.pem -L 3000:127.0.0.1:3000 -L 9090:127.0.0.1:9090 ubuntu@203.0.113.25
# then open http://localhost:3000 (Grafana) and http://localhost:9090 (Prometheus)

Use the pinned image versions you have tested rather than the default latest tag in real setups. Both ports are bound to the loopback address and reached through an SSH tunnel, so no extra security-group rules are needed. If you want Grafana on a public domain later, put it behind Nginx with HTTPS and a strong admin password.

  1. In Prometheus open Status → Targets: the shop-api target should be UP. If it is DOWN, read the error message (wrong port, wrong path, network name).
  2. In Grafana log in as admin with the password you set (Grafana asks you to change a default password if you never set one).
  3. Connections → Data sources → Add data source → Prometheus, URL http://prometheus:9090 (the Compose service name, not localhost). Save and test.
  4. Dashboards → New → Import. Search grafana.com/grafana/dashboards for a "JVM (Micrometer)" or "Spring Boot" dashboard, enter its ID or JSON, pick the Prometheus data source and import. Community dashboards expect specific label names, such as the application tag set above, so adjust the dashboard variables if panels are empty.
  5. Build your own panel for the golden signals using the queries in the next article.

For machine-level metrics (CPU, memory, disk of the server) add node_exporter as another scrape target; for per-container metrics, cAdvisor. Together with application metrics, they cover saturation.

Rule: metrics endpoints are not public

Metrics reveal your endpoints, versions and load. Expose /actuator/prometheus only on an internal port or protect it. Never publish Prometheus or Grafana with default passwords.

Mistakes

  • Target DOWN because Prometheus uses localhost:8081 inside its own container; use the service name.
  • Forgetting metrics_path and getting 404.
  • Not persisting data (prometheus-data volume), so history disappears on recreate.
  • Labels with unbounded values (user IDs), which explode memory.

Edge cases

  • Prometheus stores data locally for a limited time (the retention setting); it is not a long-term archive. Long-term storage needs remote write to another system.
  • Short-lived jobs may finish between scrapes; for those a Pushgateway exists.
  • A scrape interval of 15s with rate(...[5m]) works well; the range should hold several samples.

Interview: "How do you monitor a Spring Boot app with Prometheus and Grafana?"

  • Actuator plus the Micrometer Prometheus registry expose /actuator/prometheus; Prometheus scrapes it (pull model) per prometheus.yml; Grafana queries Prometheus; alert rules go through Alertmanager.
  • Mention metric types, the application tag, and keeping the endpoint private.

PromQL basics: rate, error rate, p95 latency and alert rules

PromQL selects time series by name and labels; use rate(counter[5m]) for per-second speed, divide two sums for an error ratio, and histogram_quantile(0.95, …) over buckets for p95 latency; alert rules turn a query into a notification.

Selectors and ranges

PromQL is Prometheus's query language. A name alone returns the latest value of every series with that name; braces filter by labels.

http_server_requests_seconds_count
http_server_requests_seconds_count{uri="/api/products"}
http_server_requests_seconds_count{status=~"5.."}        # regex match: any 5xx
http_server_requests_seconds_count{status!="200"}        # not equal
http_server_requests_seconds_count[5m]                   # a range: the last 5 minutes of samples

The operators are =, !=, =~ (regex) and !~. A selector with [5m] is a range vector and can only be passed to functions such as rate; one without a range is an instant vector.

The golden signals as queries

Rate (traffic)
rate(x[5m]) gives the per-second increase of a counter averaged over 5 minutes. It handles counter resets after restarts. Never graph a raw counter; it only climbs.
sum / sum by
Adds series together, optionally keeping some labels: sum by (uri) (...).
increase
increase(x[1h]) gives the total increase over the range (requests in the last hour).
histogram_quantile
Estimates a percentile from histogram buckets.
sum(rate(http_server_requests_seconds_count[5m]))

# per endpoint, busiest first
topk(5, sum by (uri) (rate(http_server_requests_seconds_count[5m])))
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
/
sum(rate(http_server_requests_seconds_count[5m]))
# average response time
sum(rate(http_server_requests_seconds_sum[5m]))
/
sum(rate(http_server_requests_seconds_count[5m]))

# 95th percentile (needs the histogram buckets enabled in Spring Boot)
histogram_quantile(0.95,
  sum by (le) (rate(http_server_requests_seconds_bucket[5m])))

For p95, you must keep the le label ("less or equal", the bucket bound) while summing; that is what sum by (le) does. If you group also by uri, add it: sum by (le, uri). The result is an estimate based on bucket sizes, not an exact number.

# heap usage as a fraction
sum(jvm_memory_used_bytes{area="heap"}) / sum(jvm_memory_max_bytes{area="heap"})

# database connection pool: busy connections vs the maximum
hikaricp_connections_active / hikaricp_connections_max

# process CPU usage (0 to 1 of the CPU available to the process)
process_cpu_usage

# is every target up? (1 = scrape succeeded)
up{job="shop-api"}

Alert rules

An alert rule is a query plus a condition and a duration. When the condition holds for the whole for period, the alert fires. Prometheus then sends it to Alertmanager, which groups, de-duplicates and routes alerts to email, Slack, Telegram (via a webhook receiver) or paging tools. Grafana also has its own alerting if you prefer to manage everything there.

groups:
  - name: shop-api
    rules:
      - alert: ApiDown
        expr: up{job="shop-api"} == 0
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "shop-api is not reachable by Prometheus"

      - alert: HighErrorRate
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
          / sum(rate(http_server_requests_seconds_count[5m])) > 0.05
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "More than 5% of requests fail"

      - alert: SlowRequests
        expr: |
          histogram_quantile(0.95,
            sum by (le) (rate(http_server_requests_seconds_bucket[5m]))) > 1
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "p95 latency is above one second"

The file is loaded through rule_files in prometheus.yml. Check rule syntax with promtool check rules alerts.yml (the tool ships with Prometheus) before you restart. In the Prometheus UI, the Alerts page shows pending and firing alerts. Remember a catch: an alert that depends on the app's own metrics cannot fire if the whole server is down, which is why the external uptime monitor from the previous article remains necessary.

Reading and building a dashboard

  • Make one row per golden signal: traffic (requests per second), errors (percentage), latency (p50 and p95 lines), saturation (heap, CPU, pool usage).
  • Show the same time range for all panels and annotate deployments, so a spike can be linked to a release.
  • Use the panel's unit settings (seconds, percent 0.0–1.0, bytes) to make numbers readable.

Mistakes

  • Graphing a counter without rate(): a line that only goes up.
  • Using rate() on a gauge, or a range shorter than twice the scrape interval (no data).
  • Dividing two queries without sum, so the labels do not match and the result is empty.
  • Averaging percentiles across instances. Sum the buckets first and then use histogram_quantile.
  • p95 returns "no data": the histogram buckets were never enabled in Spring Boot.

Tip: build queries step by step in the Prometheus UI

Start with the plain metric name, add a label filter, wrap it in rate, then in sum. Open the Graph tab at each step and check that the result makes sense.

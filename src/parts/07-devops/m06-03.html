Kubernetes basics: why, architecture and the main objects

Kubernetes runs and manages many containers across many machines: you declare the state you want (three copies of this image, exposed on this port), and the control plane keeps reality equal to it by scheduling, restarting, scaling and rolling out updates.

The problem it solves

Docker Compose runs containers on one machine. Real systems need more: place containers on whichever machine has room, replace a container that crashed, start more copies when load rises, update without downtime, and survive the loss of a whole machine. Doing that by hand with scripts does not scale. Kubernetes (also written K8s) is an open-source container orchestrator, originally from Google, that does these jobs. Its core ideas:

  • Scheduling: it chooses a node with enough CPU and memory for each container.
  • Self-healing: failed containers are restarted; containers that fail health checks are replaced; work moves away from a dead node.
  • Scaling: change the number of replicas by hand or automatically by load (the Horizontal Pod Autoscaler).
  • Rolling updates and rollback: new versions replace old ones gradually; one command returns to the previous version.
  • Service discovery and load balancing: stable names and addresses for changing containers.

The model is declarative: you write YAML describing the desired state and submit it. A controller compares the actual state with the desired state in a loop and fixes any difference. You do not say "start a container"; you say "there should be three".

Architecture

Control plane
The brain. The API server is the front door for every command; etcd stores the cluster state; the scheduler assigns new pods to nodes; the controller manager runs the loops that match actual state to desired state.
Node
A worker machine (a VM or physical server) that runs pods.
kubelet
The agent on each node. It talks to the API server, starts the containers for pods assigned to the node, and runs the health probes.
Container runtime
The software that actually runs containers on a node (containerd, for example). kube-proxy handles Service networking on each node.

The main objects

ObjectWhat it is
PodThe smallest unit: one or more containers sharing a network address and storage. Pods are temporary; you rarely create them directly.
ReplicaSetKeeps a stated number of identical pods running. Created and managed by a Deployment.
DeploymentDeclares an app: image, replicas, update strategy. Manages ReplicaSets so updates are rolling and reversible.
ServiceA stable name and virtual IP in front of a changing set of pods, chosen by labels. Load-balances between them.
IngressHTTP(S) routing from outside by host and path to Services; needs an ingress controller (for example Nginx).
ConfigMapNon-secret configuration (environment values, files).
SecretSensitive values (passwords, tokens). Stored base64-encoded, which is not encryption; restrict access and consider encryption at rest and external secret stores.
NamespaceA named partition of the cluster (dev, staging, shop) for organising and limiting resources.

Others you will meet: StatefulSet (pods with stable identity and disks, for databases), Job and CronJob (run to completion, scheduled), PersistentVolumeClaim (a request for storage), HorizontalPodAutoscaler and DaemonSet (one pod per node).

Labels and selectors: how objects find each other

Objects carry labels, simple key/value tags such as app: shop-api. A Deployment's selector says which pods it owns; a Service's selector says which pods it sends traffic to. If the labels do not match, the Service has no backends: the most common beginner problem.

Service types

TypeReachable fromUse for
ClusterIP (default)Inside the cluster onlyBackends, databases, anything behind an Ingress
NodePortEach node's IP on a high port (30000–32767)Quick tests, local clusters
LoadBalancerA cloud load balancer with a public addressExposing one service on a cloud cluster

On a cloud cluster, one Ingress with a single load balancer usually fronts many Services, which is cheaper than a LoadBalancer Service per app.

Where Kubernetes fits

Kubernetes shines with many services, several teams and the need for automated scaling and updates. It brings real complexity: networking, storage, security, upgrades and YAML. For one Spring Boot app, a single server with Compose, or a PaaS, is simpler and cheaper. Learn Kubernetes to read and operate it, because many companies run it; do not use it to run your first project.

Mistakes

  • Running a database as a plain Deployment with no persistent storage plan. Use managed databases, or StatefulSets with care.
  • Believing a Secret is encrypted. It is only base64 by default.
  • Using the latest image tag, so a pod restart can pull a different version.
  • Setting no resource requests or limits; one greedy pod starves the others.

Interview: "Explain Pod, Deployment and Service."

  • Pod: the unit that runs containers, temporary. Deployment: declares replicas and image, handles rolling updates and rollback through ReplicaSets. Service: stable address and load balancing across matching pods by labels.
  • Add the control loop idea: desired state versus actual state.

Deploying Spring Boot to Kubernetes: YAML, probes, kubectl and local clusters

A Deployment (image, replicas, resources, probes pointing at Actuator's liveness and readiness URLs) plus a Service gives you a self-healing, rolling-updating Spring Boot app; apply it with kubectl apply -f and manage it with get, describe, logs and rollout.

The complete manifest

A manifest is a YAML file describing objects; --- separates several in one file. This one creates a namespace, configuration, a Deployment with two replicas, and a Service. The names and image are examples.

apiVersion: v1
kind: Namespace
metadata:
  name: shop
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: shop-config
  namespace: shop
data:
  SPRING_PROFILES_ACTIVE: "prod"
  JAVA_TOOL_OPTIONS: "-XX:MaxRAMPercentage=75"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-api
  namespace: shop
  labels:
    app: shop-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: shop-api                  # which pods this Deployment owns
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                    # at most one extra pod during an update
      maxUnavailable: 0              # never go below the desired count
  template:
    metadata:
      labels:
        app: shop-api                # must match the selector above
    spec:
      terminationGracePeriodSeconds: 40
      imagePullSecrets:
        - name: ghcr-pull            # only needed for a private registry
      containers:
        - name: api
          image: ghcr.io/asha/shop-api:sha-3f9c2ab   # always a specific tag
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: shop-config
            - secretRef:
                name: shop-secrets   # DB password, JWT secret (created with kubectl)
          resources:
            requests:                # what the scheduler reserves
              cpu: "250m"
              memory: "512Mi"
            limits:                  # the hard ceiling
              memory: "768Mi"
          startupProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            periodSeconds: 5
            failureThreshold: 30     # up to 150 seconds to start
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
---
apiVersion: v1
kind: Service
metadata:
  name: shop-api
  namespace: shop
spec:
  type: ClusterIP
  selector:
    app: shop-api                    # sends traffic to pods with this label
  ports:
    - port: 80                       # the Service's port
      targetPort: 8080               # the container's port

Create the sensitive objects from the command line, not from files in Git:

$ kubectl create secret generic shop-secrets -n shop \
    --from-literal=SPRING_DATASOURCE_URL='jdbc:postgresql://db.example.internal:5432/shop' \
    --from-literal=SPRING_DATASOURCE_USERNAME='shop_app' \
    --from-literal=SPRING_DATASOURCE_PASSWORD='change-me' \
    --from-literal=JWT_SECRET='change-me-too'

$ kubectl create secret docker-registry ghcr-pull -n shop \
    --docker-server=ghcr.io --docker-username=asha --docker-password="$GHCR_TOKEN"

The pieces explained

replicas: 2
Run two identical pods. If one dies, the ReplicaSet creates another.
selector and labels
matchLabels must equal the pod template's labels. The Service selects the same label.
RollingUpdate
With maxSurge: 1 and maxUnavailable: 0, Kubernetes starts one new pod, waits until it is Ready, then stops an old one. This is zero-downtime when readiness is correct.
envFrom
Turns every key in a ConfigMap or Secret into an environment variable. Spring Boot reads SPRING_DATASOURCE_URL by relaxed binding, as in the earlier modules.
requests and limits
Requests are what the scheduler reserves for the pod; limits are the ceiling. Exceeding the memory limit gets the container killed (OOMKilled). CPU over its limit is only throttled. Set the JVM heap below the memory limit (MaxRAMPercentage=75).
terminationGracePeriodSeconds
How long Kubernetes waits after SIGTERM before killing. Match it to spring.lifecycle.timeout-per-shutdown-phase with server.shutdown=graceful.

Probes mapped to Actuator

ProbeFailing meansSpring Boot URL
startupProbeStill starting; the other probes wait. If it never passes, the container is restarted./actuator/health/liveness
readinessProbeNot ready; removed from the Service endpoints, not restarted/actuator/health/readiness
livenessProbeBroken; the container is restarted/actuator/health/liveness

Spring Boot turns on these probe endpoints automatically when it detects it runs in Kubernetes; if you deploy elsewhere, set management.endpoint.health.probes.enabled=true. The startup probe protects a slow-starting JVM from being killed by the liveness probe. If you moved Actuator to its own port (management.server.port=8081), point the probes at that port. The reasons for keeping the database out of liveness are in Health checks.

An Ingress for HTTP from outside

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop-api
  namespace: shop
spec:
  ingressClassName: nginx
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: shop-api
                port:
                  number: 80

TLS certificates in Kubernetes are commonly handled by cert-manager, which obtains Let's Encrypt certificates for Ingress hosts, the cluster version of certbot.

Where to run a cluster

  • Local learning: minikube (minikube start), kind (Kubernetes in Docker: kind create cluster; load a local image with kind load docker-image NAME:TAG), or the Kubernetes option in Docker Desktop.
  • Managed in the cloud: EKS (AWS), GKE (Google) and AKS (Azure) run the control plane for you; you pay for it and for the worker nodes. Learn locally first; a managed cluster left running is a surprise cost.
  • Helm: a package manager for Kubernetes. A chart is a templated bundle of manifests, installed with helm install and configured through a values file.

Docker Compose vs Kubernetes

Docker ComposeKubernetes
MachinesOne hostA cluster of nodes
Self-healing and schedulingRestart policy onlyFull: reschedules on other nodes
Rolling updatesRecreate (brief downtime)Built in, with rollback
ScalingManual, single hostManual or automatic
Learning costLowHigh
Best forLocal development, small single-server appsMany services, teams, high availability

Rule: every container gets probes, requests and a pinned image tag

Without readiness probes, rolling updates can send traffic to a pod that is still starting. Without requests and limits, scheduling and memory behaviour are unpredictable. Without a pinned tag, you cannot say what is running.

Mistakes

  • Selector and template labels that do not match (the apply is rejected), or a Service selector that matches nothing (no endpoints; check with kubectl get endpoints).
  • Liveness probe with a short delay on a slow JVM: pods are killed while starting. Use a startup probe.
  • Memory limit equal to the heap size: the JVM also needs non-heap memory, so it gets OOMKilled.
  • Committing Secrets with real values to Git.

Interview: "How do you deploy a Spring Boot app on Kubernetes and do a zero-downtime release?"

  • Image with a SHA tag; Deployment with replicas, resources and probes on Actuator readiness and liveness; Service and Ingress; rolling update with maxUnavailable: 0 and graceful shutdown; kubectl rollout status and rollout undo.

Terraform basics: infrastructure as code

Terraform lets you describe cloud resources in code, preview the changes with terraform plan, create them with apply, and remove them with destroy, keeping a state file that records what exists, so environments are repeatable and reviewable like source code.

Why infrastructure as code

Clicking in the console is fine for learning, but it cannot be reviewed, repeated or undone cleanly. If your production server was clicked together by hand, nobody can say exactly how, and a second copy for testing is guesswork. Infrastructure as code (IaC) keeps the description of servers, networks and databases in text files in Git. You get history, code review, repeatable environments, and a one-command cleanup (a real help against surprise bills, see Module 5).

Terraform (by HashiCorp; a community fork named OpenTofu also exists) is the most widely used IaC tool. It is declarative: you state the desired end result, and Terraform works out what to create, change or delete. It works with any platform that has a provider.

Core concepts

Provider
A plugin that talks to a platform's API: aws, google, azurerm, kubernetes, github. Downloaded by terraform init.
Resource
A thing to create: aws_instance, aws_security_group, aws_s3_bucket. Written as resource "type" "local_name" { ... }.
Data source
Read-only information looked up from outside, such as the latest Ubuntu AMI.
Variable
An input (region, instance type) so code can be reused. Set with defaults, -var, or a .tfvars file.
Output
A value printed after apply (the server's public IP).
State
A file (terraform.tfstate) mapping your code to the real resources. Terraform compares code, state and reality to produce a plan.
Module
A reusable folder of Terraform code, called with inputs.

A tiny example: an EC2 instance, a security group and an Elastic IP

This creates the web server from the Module 5 runbook. Put it in a folder as main.tf. It uses the default VPC of the region. Pin the provider version range you have tested; the range below is only a starting point.

terraform {
  required_version = ">= 1.5"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = ">= 5.0"
    }
  }
}

provider "aws" {
  region = var.region
}

variable "region" {
  type    = string
  default = "ap-south-1"
}

variable "instance_type" {
  type    = string
  default = "t3.micro"            # check the current free-tier rules before choosing
}

variable "my_ip_cidr" {
  type        = string
  description = "Your public IP with /32, for SSH, for example 203.0.113.7/32"
}

variable "public_key_path" {
  type    = string
  default = "~/.ssh/shop-key.pub"
}

# Latest Ubuntu 24.04 image published by Canonical
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"]
  }
}

resource "aws_key_pair" "shop" {
  key_name   = "shop-key"
  public_key = file(pathexpand(var.public_key_path))
}

resource "aws_security_group" "web" {
  name        = "shop-web-sg"
  description = "SSH from my IP; HTTP and HTTPS from anywhere"

  ingress {
    description = "SSH"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = [var.my_ip_cidr]
  }
  ingress {
    description = "HTTP"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
  ingress {
    description = "HTTPS"
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_instance" "web" {
  ami                    = data.aws_ami.ubuntu.id
  instance_type          = var.instance_type
  key_name               = aws_key_pair.shop.key_name
  vpc_security_group_ids = [aws_security_group.web.id]

  root_block_device {
    volume_size = 20
    volume_type = "gp3"
  }

  tags = {
    Name    = "shop-api"
    project = "shop"
  }
}

resource "aws_eip" "web" {
  domain = "vpc"
}

resource "aws_eip_association" "web" {
  instance_id   = aws_instance.web.id
  allocation_id = aws_eip.web.id
}

output "public_ip" {
  value = aws_eip.web.public_ip
}

output "ssh_command" {
  value = "ssh -i shop-key.pem ubuntu@${aws_eip.web.public_ip}"
}

Notice the references like aws_key_pair.shop.key_name and aws_security_group.web.id. Terraform builds a dependency graph from them: it creates the key pair and security group first, then the instance, then the address, automatically and in parallel where possible.

The workflow

$ terraform init                  # download the provider; run once per folder
$ terraform fmt                   # format the code
$ terraform validate              # check syntax
$ terraform plan -var="my_ip_cidr=203.0.113.7/32"
  # + aws_instance.web will be created
  # + aws_security_group.web will be created
  ...
Plan: 5 to add, 0 to change, 0 to destroy.

$ terraform apply -var="my_ip_cidr=203.0.113.7/32"     # shows the plan, asks "yes"
Apply complete! Resources: 5 added, 0 changed, 0 destroyed.
Outputs:
public_ip = "203.0.113.25"

$ terraform output public_ip
$ terraform destroy -var="my_ip_cidr=203.0.113.7/32"   # delete everything it created

In a plan, + means create, ~ means change in place, - means destroy, and -/+ means replace (destroy and create). Always read the plan. A replaced database or server in the plan is a data-loss warning. Terraform authenticates the way the AWS CLI does: your profile, environment variables or Identity Center login; never write keys into .tf files.

State, and remote state

The state file records what Terraform created, including resource IDs and sometimes secrets. Rules:

  • Never commit terraform.tfstate or the .terraform/ folder to Git. Do commit .terraform.lock.hcl (it pins provider versions) and your .tf files.
  • On a team, store state remotely so everyone shares one truth, with locking so two people do not apply at once. A common AWS choice is an S3 bucket, with versioning and encryption. Locking was traditionally done with a DynamoDB table; newer Terraform versions can lock in S3 itself, so check the current documentation.
terraform {
  backend "s3" {
    bucket  = "shop-terraform-state-asha"
    key     = "prod/terraform.tfstate"
    region  = "ap-south-1"
    encrypt = true
  }
}

Changes made outside Terraform (someone edits a security group in the console) cause drift; the next plan shows the difference. Treat the code as the source of truth and avoid manual edits.

Mistakes

  • Running apply without reading the plan.
  • Committing state files or .tfvars that hold secrets.
  • Editing resources by hand in the console after Terraform created them.
  • Forgetting terraform destroy after a lab and paying for it.

Edge cases

  • Importing existing resources into state is possible (terraform import, or import blocks in newer versions) when you adopt IaC for something already created.
  • Changing an immutable property (such as an instance's AMI) usually replaces the resource.
  • Provider and Terraform versions change; keep them pinned and upgrade deliberately.

Interview: "What is Terraform and what is the state file?"

  • A declarative IaC tool: providers, resources, variables, outputs; init, plan, apply, destroy. State maps code to real resources; store it remotely with locking, and never in Git.
  • Compare with CloudFormation (AWS-only, managed state) and with Ansible (configuration).

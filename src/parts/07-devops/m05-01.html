Cloud basics: IaaS, PaaS, SaaS and pay-as-you-go

The cloud means renting computing (servers, storage, databases, networks) from a provider over the internet and paying only for what you use; IaaS rents raw machines, PaaS rents a ready platform for your code, SaaS rents finished software.

What the cloud is

Before the cloud, a company that wanted to run a website bought servers, put them in a room, hired people to look after them, and paid for the peak load all year. In the cloud, a provider such as Amazon, Microsoft or Google owns huge data centres. You rent a slice of them through a web console or an API, in minutes, and stop paying when you delete the slice.

Every provider sells the same building blocks:

Compute
Machines that run your code: virtual servers (EC2), containers (ECS, Kubernetes) or functions (Lambda).
Storage
Object storage for files (S3), block disks attached to a server (EBS), file shares.
Managed databases
A database the provider installs, backs up and patches for you (RDS for PostgreSQL/MySQL, DynamoDB).
Networking
Private networks (VPC), load balancers, DNS, firewalls (security groups).
Identity
Users, roles and permissions: who may do what (IAM).

IaaS vs PaaS vs SaaS

The three service models differ in how much the provider manages for you. Think of getting a pizza: IaaS is buying the flour and using their oven, PaaS is ordering the base and adding your own toppings, SaaS is eating the finished pizza.

ModelYou manageProvider managesExamples
IaaS (Infrastructure as a Service)OS, runtime, patches, app, data, firewall rulesHardware, network, virtualisationAWS EC2, Azure Virtual Machines, Google Compute Engine
PaaS (Platform as a Service)Your code (or container) and its settingsOS, runtime, scaling, TLS, deploysRender, Railway, Heroku, Elastic Beanstalk, Vercel, Netlify
SaaS (Software as a Service)Your data and usersEverything elseGmail, Slack, Jira, Zoho, Salesforce, GitHub

There is also FaaS (Function as a Service, "serverless"): you upload a function and pay per call, for example AWS Lambda. As a backend developer you mostly choose between IaaS and PaaS for your own apps, and use SaaS tools (GitHub, Jira, Slack) every day.

The trade-off is always control versus effort. On IaaS you can install anything and tune everything, but you must patch Linux, configure Nginx and renew certificates. On PaaS you push code and get a URL, but you accept the platform's rules, and costs can be higher at scale. This module teaches both, because interviews ask about EC2 and real jobs use both.

Pay-as-you-go

Cloud billing is pay-as-you-go: there is no purchase, you are metered. Servers are billed for the time they run, storage for the gigabytes kept, data leaving the provider for the gigabytes sent out, and many services per request. Good effects: no big upfront cost, you can try an idea for a few hours, and you can scale up for a sale and back down after. Bad effect: a mistake costs money immediately. A server you forget about keeps billing, and a loop that calls a paid API can bill fast. That is why the next two articles are about account safety and billing alerts.

Providers also offer cheaper long-term options, for example committing to steady usage for one or three years (Savings Plans, Reserved Instances) or using spare capacity that can be taken back (Spot). You do not need them while learning; just know the names. Never trust a price you read in an old blog post: always check the provider's current pricing page.

The shared-responsibility model

Security in the cloud is split. The provider is responsible for the security of the cloud: buildings, hardware, network, and the virtualisation layer. You are responsible for security in the cloud: your data, your accounts and permissions, your firewall rules, and, depending on the service, your operating system and application.

ServiceProvider handlesYou handle
EC2 (IaaS)Hardware, hypervisorOS patches, Nginx/Docker, app, security groups, SSH keys, backups
RDS (managed)OS and database patching, backups, failoverDatabase users and passwords, network access, schema, queries
S3Durability, hardwareBucket policies, public-access settings, what you upload
Render / Vercel (PaaS)OS, runtime, TLS, scalingYour code, secrets, dependencies, access to your account

The practical meaning: when a company's S3 bucket leaks customer data, it is almost always because the customer made it public, not because AWS was hacked.

The big three, in one line each

  • AWS (Amazon Web Services): the oldest and largest, the widest range of services and the most job listings; this module uses it.
  • Microsoft Azure: strong in enterprises that already use Microsoft products (Windows, Active Directory, .NET), also popular for Java.
  • Google Cloud (GCP): strong in data, machine learning and Kubernetes, which Google created.

The ideas (virtual machine, object storage, managed database, IAM, load balancer) are the same everywhere, with different names. Learn them on AWS and the others become a vocabulary exercise.

Mistake: "the cloud is secure by default, so I need not worry"

Providers secure the data centre, not your configuration. A public bucket, an SSH port open to the whole internet, or an access key in a public GitHub repository are your mistakes, and bots find them within minutes.

Interview: "Explain IaaS, PaaS and SaaS with examples."

  • IaaS: raw machines (EC2); you manage OS upwards. PaaS: you bring code (Render, Elastic Beanstalk). SaaS: finished software (Gmail, Jira).
  • Add the trade-off (control versus effort) and the shared-responsibility model.

Regions and availability zones (Mumbai and Hyderabad)

A region is a geographic area with several isolated availability zones; you pick the region nearest your users (Mumbai ap-south-1 or Hyderabad ap-south-2 for India) and spread across zones to survive a data-centre failure.

Regions

An AWS region is a physical area of the world where AWS runs a cluster of data centres, such as Mumbai or Frankfurt. Each region has a name and a code. For India you will use:

RegionCodeNotes
Asia Pacific (Mumbai)ap-south-1The older, most complete Indian region
Asia Pacific (Hyderabad)ap-south-2Newer; may need to be enabled in your account, and some services may be missing, so check
US East (N. Virginia)us-east-1The oldest and largest; several global features are managed from here

Regions are independent. A server, a database or a bucket you create lives in one region. Switching the region in the top-right menu of the console shows a different, empty set of resources. This causes the classic panic "my server has disappeared": you simply looked at the wrong region. Some services are global (IAM users and roles, Route 53 DNS, CloudFront), so they do not belong to a region.

How to choose a region

  • Latency. Data travels at finite speed; a user in Pune is faster served from Mumbai than from Virginia. Choose the region closest to most users.
  • Rules about data. Some companies and sectors (banking, health, government) require data to stay in India. Check the rules that apply to you.
  • Service availability. New services and instance types arrive first in a few big regions. Check that the services you need exist in your region.
  • Price. The same service can cost differently in different regions. Check the current pricing page.
  • Keep related things together. Your EC2 server, RDS database and S3 bucket should be in the same region. Cross-region traffic is slower and is billed as data transfer.

Availability zones

A region is split into several availability zones (AZs), normally three or more in the bigger regions. An AZ is one or more data centres with its own power, cooling and network, close enough to others in the region for very low latency, but separate enough that a fire or power cut in one does not take down the others. Zone names look like ap-south-1a, ap-south-1b, ap-south-1c. (AWS maps these letters to physical zones differently per account, so your "1a" may be someone else's "1b"; the zone ID such as aps1-az1 is the stable name.)

Why zones matter for your design

One server in one zone is a single point of failure: if that zone has a problem, your app is down. The standard fix is to run at least two copies in different zones behind a load balancer (ELB/ALB), and to turn on Multi-AZ for the database (RDS keeps a standby copy in another zone and fails over automatically). Subnets (slices of your private network) are tied to one AZ, so "use two AZs" means "create subnets in two zones".

For learning and for small apps, one EC2 instance in one zone is fine, and it is cheaper. For a business system that must stay up, use at least two zones. Even then, a whole-region outage is rare but possible; multi-region designs exist and cost much more, so they are used only when the business needs them.

Rule: create all related resources in one region

Pick the region first, keep the console on it, and set the same region in the AWS CLI (aws configure) and in your code (for example Region.AP_SOUTH_1). A mismatch gives errors such as "bucket not found" or an empty list.

Edge cases

  • An EBS disk can only be attached to a server in the same AZ.
  • An S3 bucket name is global across all of AWS, but the bucket's data lives in one region.
  • Some regions are "opt-in": you must enable them in your account settings before use. If Hyderabad is not in your region list, this is why.

Interview: "What is the difference between a region and an availability zone?"

  • Region = a geographic area; AZ = an isolated group of data centres inside it. Zones in a region are connected by fast links.
  • Use multiple AZs for high availability (load balancer + Multi-AZ database); use the region closest to users and legal needs.

AWS account safety first: root MFA, daily-use users, least privilege and keys

Protect the root user with MFA and never use it daily; do your work as an IAM Identity Center or IAM user with only the permissions you need, and never put access keys in code, Git or an image.

Why this comes before any server

Bots scan GitHub for AWS keys all day. A leaked key can be used within minutes to start expensive servers for crypto-mining, and you receive the bill. Spending an hour on the steps below prevents that.

Step 1: secure the root user

When you create an AWS account, you sign up with an email and password. That identity is the root user. It can do everything, including closing the account and changing billing, and its permissions cannot be limited. So:

  1. Use a strong, unique password from a password manager, and a mailbox you control.
  2. Turn on MFA (multi-factor authentication) for the root user: in the console, open your account menu → Security credentials → Assign MFA device. Use an authenticator app or a passkey/security key. Save recovery details safely.
  3. Do not create access keys for the root user. If any exist, delete them.
  4. Use the root user only for the few tasks that need it (changing the account email, closing the account, some billing settings). Sign out afterwards.

Step 2: create an identity for daily work

You have two good options. Check the current AWS "Getting started" guidance, because the console changes.

  • IAM Identity Center (AWS's recommended way for people): you create a user, assign a permission set, and sign in through a portal URL. It gives temporary credentials, so there are no long-lived keys on your laptop. Best choice when you can use it.
  • An IAM user (simpler, fine for learning): create a user such as asha-admin, tick console access, enable MFA for it too, and attach permissions through a group. For a personal account you may attach the managed policy AdministratorAccess to a group, but prefer narrower policies as soon as you know what you need. See IAM.

From now on, sign in with this identity, not root. The sign-in URL for IAM users contains your account ID or alias; bookmark it.

Step 3: least privilege

The principle of least privilege means each user, application and server gets only the permissions it needs for its job. An app that uploads photos needs s3:PutObject on one bucket, not AdministratorAccess. If the app is ever compromised, the damage is limited to that bucket.

Step 4: handle access keys carefully

An access key is a pair (access key ID plus secret access key) that lets a program or the AWS CLI act as a user. It is a password in another form.

Rules for access keys

  • Never commit keys to Git, even in a private repository, and never put them in a Dockerfile, an image, a React app (everything in frontend code is public), a screenshot or a chat message.
  • Prefer no keys at all: use IAM Identity Center on your laptop and an instance role on EC2.
  • If you must use keys, store them with aws configure (it writes ~/.aws/credentials outside any repository), give the user minimal permissions, and rotate or delete unused keys.
  • Add .env and credential files to .gitignore before the first commit.

Check which identity the CLI is using at any time:

$ aws sts get-caller-identity
{
    "UserId": "AIDAEXAMPLEUSERID",
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/asha-admin"
}

If a key leaks

  1. Deactivate and then delete the key immediately (IAM → Users → Security credentials).
  2. Look for anything you did not create: instances in every region, new IAM users, new keys. CloudTrail (the audit log) shows what the key did.
  3. Delete unknown resources, then check the billing page. AWS often emails you about exposed keys; follow its instructions and contact AWS Support if you see charges you did not make.
  4. Remove the secret from Git history (rotating the key matters more than rewriting history, because anyone may already have copied it).

The free tier

AWS has offered a free tier for new accounts: some services free up to a limit for a period, some free always, and some as trials. The terms, limits, durations and even the structure of the programme have changed over the years, and they differ by account creation date. So do not rely on a number from a blog or this page. Open the current "AWS Free Tier" page, read the exact terms for your account, and note which services and instance types qualify. "Free tier" never means "unlimited": going over the limit, using a non-eligible instance type, or running in a way the tier does not cover creates a normal bill.

Convention: one account for learning, tags on everything

Use a separate account for experiments. Give resources a tag such as project=shop so you can find and delete them later. Real companies use separate accounts for development and production.

Interview: "How do you secure a new AWS account?"

  • MFA on root, no root keys, root unused; IAM Identity Center or IAM users with groups and least privilege; roles instead of keys for servers; billing alerts; CloudTrail on.

Billing alerts, AWS Budgets and the surprise-cost list

Create a monthly budget with email alerts on day one, learn to read the bill by service and region, and know the usual surprise costs: running instances, forgotten disks, public IPs, NAT gateways, data transfer and idle databases.

Create a budget, step by step

AWS Budgets watches your spending (actual and forecast) against a number you choose and emails you at thresholds. The console layout changes now and then, so treat the labels below as a guide.

  1. Sign in as the root user (or an admin). By default, IAM users cannot see billing pages. As root, open Account → "IAM user and role access to Billing information" and activate it if you want your admin user to see billing.
  2. Open Billing and Cost Management → Billing preferences and turn on the email alerts offered there, for example free-tier usage alerts, and set the email addresses.
  3. Open Budgets → Create budget. For a first budget choose a template such as "Zero spend budget" (alerts as soon as you spend anything) or "Monthly cost budget" (you enter an amount).
  4. Enter a name, the monthly amount you are comfortable with, and your email address. Create the budget.
  5. Optionally, make a second, customised cost budget with several alerts: for example at 50% and 80% of the amount on actual spend, and at 100% on forecasted spend (the forecast warns you before you cross the line).
  6. Confirm the email subscription if AWS sends a confirmation message, then check that alert emails do not go to spam.
  7. Open Cost Explorer and enable it (it may take a day to fill). It shows cost by service, by region and over time.

Limits of budget alerts

  • A budget alerts, it does not stop spending. (Advanced "budget actions" can apply a restrictive policy automatically, but they need setup and care.)
  • Billing data lags by hours, so an alert can arrive after the cost happened. Alerts are a smoke detector, not a fire brigade; the real protection is cleaning up when you finish.
  • Look into Cost Anomaly Detection as well; it flags unusual spikes by service.

Reading the bill

Open Billing → Bills to see the current month, grouped by service, with a view by region. The region view quickly shows the mistake "I created a server in a region I forgot". Make it a weekly habit for the first months: two minutes, once a week.

The usual surprise costs

SurpriseWhy it happensWhat to do

Do not memorise prices. Memorise the habit: everything that exists in the console may be billed, so when a lab ends, delete what you created.

A cleanup routine after every lab

  1. Terminate EC2 instances you do not need (stopping keeps the disk, which is still billed).
  2. Delete the leftover EBS volumes and snapshots; release Elastic IPs.
  3. Delete RDS instances, load balancers, NAT gateways.
  4. Empty and delete S3 buckets used for tests.
  5. Look at Bills → by region next day to confirm nothing is still running.

Tip: use tags and a "delete me" day

Tag lab resources with purpose=learning. When you search resources by tag, you can delete them all together. For repeatable labs, write them as Terraform (Module 6) and run terraform destroy.

Mistake: setting up alerts to an email you never read

An alert nobody sees is useless. Use an address you check daily, add a second recipient, and test by creating a tiny "zero spend" budget.

Interview: "How do you keep cloud costs under control?"

  • Budgets and alerts, Cost Explorer, tags, right-sizing, shutting down non-production at night, deleting unused resources, committing to Savings Plans for steady load, and reviewing the bill regularly.

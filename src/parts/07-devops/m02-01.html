Your Spring Boot app is useful only when someone else can reach it. Between a user's browser and your code sit IP addresses, DNS, TCP, TLS, firewalls and usually a reverse proxy such as Nginx. When something breaks, the error is rarely "your code is wrong"; it is "the request never arrived". This module gives you the small, practical mental model of that path, and the tools to test each hop.

It builds on Module 1 (you will use ss, curl and SSH constantly) and prepares Docker networking and cloud deployment. The deeper theory (OSI model, TCP internals, congestion) is in CS Fundamentals · Module 2; web basics from the browser side are in Frontend · Module 1.

IP addresses, ports, CIDR, NAT and localhost versus 0.0.0.0

An IP address finds a machine and a port finds a program on it; private ranges are used inside networks, NAT lets them reach the internet, and a server app must listen on 0.0.0.0, not just 127.0.0.1, to accept outside connections.

IP addresses

Every device on a network has an IP address, the number that packets are routed to. IPv4 addresses are 32 bits, written as four numbers from 0 to 255: 203.0.113.10. That gives about 4.3 billion addresses, which ran short. IPv6 addresses are 128 bits, written in hexadecimal groups such as 2001:db8::1, with an effectively unlimited supply. Both are in use today; most examples in these notes use IPv4 because that is what you will configure first. Your cloud VM has at least a private IP and usually a public IP as well.

Public and private addresses

Three IPv4 blocks are reserved for private networks. They are never routed on the public internet, so your home, office and every AWS VPC can reuse them.

RangeSizeWhere you see it
10.0.0.0/816.7 million addressesCompanies, cloud VPCs
172.16.0.0/121 million addressesDocker's default bridge uses 172.17.0.0/16; AWS default VPC uses 172.31.0.0/16
192.168.0.0/1665 thousand addressesHome Wi-Fi routers

Anything else is a public address (for example 203.0.113.10, a documentation range we use in examples). Also special: 127.0.0.0/8 is loopback, and 169.254.x.x is link-local (self-assigned when DHCP fails).

CIDR in simple words

CIDR notation writes a block of addresses as address/prefix. The prefix is how many of the 32 bits are fixed (the network part); the rest can change (the host part).

CIDRFixed bitsAddressesExample
/32All 321 (one host)203.0.113.10/32 = just my IP
/24First 3 numbers256192.168.1.0/24 = 192.168.1.0 to .255
/16First 2 numbers65,53610.0.0.0/16 = 10.0.0.0 to 10.0.255.255
/8First number16.7 million10.0.0.0/8
/0NoneEverything0.0.0.0/0 = the whole internet

Rule of thumb: a bigger prefix number is a smaller block. You meet CIDR in AWS security groups and VPC subnets: "allow port 22 from 203.0.113.10/32" means only your IP; "from 0.0.0.0/0" means anyone. A cloud provider reserves a few addresses in each subnet, so a /24 gives slightly fewer than 256 usable ones.

NAT: how private machines reach the internet

Your laptop at 192.168.1.20 cannot be routed to from the internet. Your home router does NAT (Network Address Translation): it rewrites outgoing packets to use the router's one public IP and remembers the connection, so replies come back to the right device. In AWS the same idea appears as an Internet Gateway (for instances with public IPs) and a NAT Gateway (so private instances can go out but nobody can come in). Consequence: devices behind NAT cannot accept incoming connections unless you forward a port.

Ports

A port is a 16-bit number (0-65535) that picks the program on a machine. A connection is identified by source IP and port plus destination IP and port. Servers use fixed, well-known ports; clients get a random high port (ephemeral) for each connection.

localhost, 127.0.0.1 and 0.0.0.0

localhost is a hostname that resolves to 127.0.0.1, the loopback address: traffic never leaves the machine. When a program starts a server it chooses which address to bind to:

Bind addressWho can connectUse for
127.0.0.1Only programs on the same machineA database used only by the local app; an app behind Nginx on the same host
A specific private IP, e.g. 10.0.1.5Clients that can reach that network interfaceServices that talk only inside a VPC
0.0.0.0Any interface: loopback, private and publicAnything that must accept outside traffic; apps in Docker

0.0.0.0 is not a destination you connect to; it means "all my addresses" when listening. Spring Boot's embedded Tomcat listens on all interfaces by default, and you can restrict it with server.address:

# default: all interfaces (0.0.0.0). Uncomment to allow only local connections.
# server.address=127.0.0.1
server.port=8080

Inside a Docker container, localhost is the container itself. If your app binds only to 127.0.0.1 inside the container, published ports do not work. Bind 0.0.0.0 (Module 3).

$ ip a
1: lo: <LOOPBACK,UP,LOWER_UP> ...
    inet 127.0.0.1/8 scope host lo
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> ...
    inet 172.31.5.20/20 brd 172.31.15.255 scope global eth0
$ curl -s https://checkip.amazonaws.com
203.0.113.10

ip a shows the private address(es) assigned to the machine, here 172.31.5.20. The public IP of an EC2 instance is not on the interface at all: AWS translates it (1:1 NAT), so ask an external service (or the EC2 console) for it. On Windows use ipconfig.

Mistake: "it works on localhost, so it works"

curl localhost:8080 on the server only proves the app listens on the loopback. It says nothing about the firewall, the security group, DNS or the bind address as seen from outside. Test from another machine too, or with the server's private/public IP.

Edge cases

  • Overlapping private ranges break VPNs and VPC peering: two networks both using 10.0.0.0/16 cannot be joined. Plan address ranges early.
  • A public IP on an EC2 instance changes after a stop/start unless it is an Elastic IP.
  • localhost can resolve to ::1 (IPv6) first. If the app listens only on IPv4, some clients fail; use 127.0.0.1 to be explicit.
  • Ports below 1024 need root to bind; use 8080 for the app and let Nginx take 80/443.

Interview: "Difference between 127.0.0.1 and 0.0.0.0? What is a private IP?"

  • 127.0.0.1 is loopback (same machine only). 0.0.0.0 as a bind address means all interfaces.
  • Private ranges: 10/8, 172.16/12, 192.168/16; not routable on the internet; NAT gives them outbound access.
  • Explain CIDR with an example such as /24 = 256 addresses, and "/32 = my one IP" for SSH rules.

DNS: how a domain becomes an IP address

DNS is the internet's phone book: your computer asks a resolver, which asks the root, TLD and authoritative servers, and gets back the IP for a name; you control the answer with records such as A and CNAME at your domain provider.

The problem DNS solves

Computers connect with IP addresses, but people remember names like shop.example.com. The Domain Name System (DNS) is a distributed database that maps names to IPs (and other data). It also lets you move a service to a new server by changing one record, without telling users. A name is read from right to left: shop (subdomain) . example (domain you bought) . com (top-level domain, TLD) . and an invisible root dot.

Resolution step by step

  1. Local caches. The browser and operating system check their own cache and the hosts file first (/etc/hosts, or C:\Windows\System32\drivers\etc\hosts).
  2. Recursive resolver. If not found, the OS asks the configured resolver (your ISP, your router, or a public one like 8.8.8.8). It does the hard work and caches answers.
  3. Root servers point to the servers for the TLD (.com, .in).
  4. TLD servers point to the domain's name servers (set at your registrar).
  5. Authoritative server holds the real records and returns the answer.
  6. The resolver caches the answer for the record's TTL and returns it. The browser then opens a TCP connection to that IP.

Record types

TypeMapsExample
AName to an IPv4 addressshop.example.com A 203.0.113.10
AAAAName to an IPv6 addressshop AAAA 2001:db8::10
CNAMEName to another name (alias)www CNAME shop.example.com.
MXMail servers for the domainexample.com MX 10 mail.example.com.
TXTFree text: domain verification, SPF, DKIM"v=spf1 include:..."
NSThe name servers of the domainexample.com NS ns1.example-dns.net.

A versus CNAME. An A record points to an IP. A CNAME says "this name is an alias of that name; look that one up instead". Use A for a server with a fixed IP (an Elastic IP). Use CNAME for hosted services that give you a hostname, such as an AWS load balancer (my-lb-123.ap-south-1.elb.amazonaws.com) or a CDN, because their IPs change. A CNAME cannot be placed at the root of the domain (example.com itself) under the standard rules; many DNS providers offer an "ALIAS" or "ANAME" feature for that case, and AWS Route 53 has alias records.

TTL and propagation

TTL (time to live) is how many seconds a resolver may cache a record. With TTL 300, a change can take up to five minutes to reach users who looked it up just before; with 86400 it can take a day. "Propagation" is not a push through the internet: it is the old cached answers expiring. Before a planned move, lower the TTL a day ahead (to 300), switch the record, then raise it again.

Tools: dig, nslookup, the hosts file

$ dig +short shop.example.com
203.0.113.10
$ dig shop.example.com A

;; ANSWER SECTION:
shop.example.com.   300   IN   A   203.0.113.10

;; Query time: 24 msec
;; SERVER: 127.0.0.53#53(127.0.0.53)
$ dig www.example.com CNAME +short
shop.example.com.
$ dig NS example.com +short
ns1.example-dns.net.
ns2.example-dns.net.
$ dig @8.8.8.8 shop.example.com +short
203.0.113.10
$ nslookup shop.example.com
Server:         127.0.0.53
Address:        127.0.0.53#53

Non-authoritative answer:
Name:   shop.example.com
Address: 203.0.113.10

Read the answer line: name, TTL (300), class IN (Internet), type, value. "Non-authoritative" means the answer came from a cache, not the domain's own server. dig @8.8.8.8 asks a specific resolver, which is a quick way to see whether a change has reached the public. On Windows, nslookup works out of the box; dig is in the dnsutils package (sudo apt install dnsutils) on Ubuntu.

The hosts file overrides DNS on one machine. It is handy for testing before a DNS change, or for blocking a site:

127.0.0.1   localhost
203.0.113.10   shop.example.com

Connecting a domain to your server

  1. Buy a domain from a registrar (GoDaddy, Namecheap, Route 53, ...).
  2. Give your server a stable public IP: on AWS, allocate an Elastic IP and attach it to the instance.
  3. In the DNS settings (at the registrar, or a DNS host such as Route 53 or Cloudflare), add an A record: name @ (the root) or shop, value the IP, TTL 300.
  4. Add www as a CNAME to the root name, if you want both.
  5. Check: dig +short shop.example.com returns your IP (it may take a few minutes).
  6. Make sure the web server (Nginx) has a server_name for the domain, then get a certificate (HTTPS).

Mistake: changing DNS and testing in the browser straight away

Browsers and the OS cache answers, and the old IP may still be cached for the old TTL. Test with dig @8.8.8.8 name +short to see what public resolvers return, and clear the local cache if needed (Windows: ipconfig /flushdns). Also, a "negative" answer (name not found) is cached too.

Edge cases and errors

  • NXDOMAIN — the name does not exist (typo, or the record is missing).
  • curl: (6) Could not resolve host or UnknownHostException in Java — DNS failed. Check the name, /etc/resolv.conf and network access.
  • The JVM caches successful DNS lookups; if a service's IP changes (a load balancer behind a CNAME), a long-running app may keep using the old IP until the cache expires. The JVM's cache time is controlled by the networkaddress.cache.ttl security property.
  • You cannot put a CNAME at the same name as other records (such as MX) — the root domain needs A or ALIAS records.

Interview: "What happens when you type a URL in the browser? (DNS part)"

  • Cache and hosts file, then the recursive resolver, root, TLD, authoritative server; the answer is an A record with a TTL; then TCP, TLS and HTTP follow.
  • Know A, CNAME, MX, TXT, NS, and why TTL makes changes take time.

TCP versus UDP, and the three-way handshake

TCP gives reliable, ordered delivery after a handshake and is used by HTTP, SSH and databases; UDP just sends packets with no guarantees and is used for DNS queries, video calls and games.

Both are transport layer protocols that carry data between ports on two hosts. IP only delivers packets to a machine and may lose, duplicate or reorder them. TCP and UDP sit above IP and decide how much help the application gets.

TCP: reliable stream

Before any data moves, TCP sets up a connection with a three-way handshake:

After that, TCP numbers every byte, the receiver acknowledges what arrived, lost segments are sent again, data is delivered in order, and the sender slows down if the network or receiver is overloaded (flow and congestion control). Closing uses a FIN exchange. Details of windows and congestion are in CS Fundamentals · Module 2. The practical meaning: a TCP connection costs one round trip to set up, which is why servers keep connections open (HTTP keep-alive, connection pools).

UDP: fire and forget

UDP has no connection, no retransmission and no ordering. Each message (datagram) is sent independently; some may be lost. In exchange it is lightweight and fast to start, and the application decides what to do about loss. It suits traffic where a late packet is worse than a lost one.

Seeing TCP and UDP on your machine

$ ss -tn state established

$ ss -tn state established | wc -l

$ ss -s

Each established line is one TCP connection: your SSH session on port 22 and a proxy connection to the app on 8080. A server's connection count includes states such as TIME-WAIT (recently closed, waiting a short time to catch stray packets). A very high count of SYN-RECV can point to a SYN flood attack.

Mistake: testing a UDP service with TCP tools

nc -zv host 53 tests TCP only. For UDP use nc -zvu host 53 and remember that a silent UDP port can mean "open" or "filtered", because no reply is expected.

Edge cases and errors

  • Connection refused — the host answered with a reset: nothing listens on that port.
  • Connection timed out — no answer at all: a firewall dropped the packets, or the host is unreachable.
  • Connection reset by peer — the other side closed abruptly (app crash, a proxy timeout, an idle connection dropped).
  • In Java you meet these as java.net.ConnectException, java.net.SocketTimeoutException and java.net.SocketException.

Interview: "TCP versus UDP; explain the three-way handshake."

  • TCP: connection, reliable, ordered, flow and congestion control. UDP: connectionless, no guarantees, low latency.
  • SYN, SYN-ACK, ACK agree on sequence numbers; examples: HTTP and SSH on TCP; DNS queries, video calls and QUIC on UDP.
  • Add that refused versus timed out tells you whether the host or the firewall is the problem.

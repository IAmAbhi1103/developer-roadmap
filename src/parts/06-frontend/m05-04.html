Forms: controlled inputs and validation

In a controlled form, React state is the single source of truth for every input (value + onChange); you validate on submit, show errors next to fields, and disable the button while the request is running.

Controlled inputs

A controlled input gets its value from state and reports every change through onChange. The DOM input never holds its own truth; React does. That makes it easy to validate, format, clear or pre-fill the field. An uncontrolled input keeps its own value in the DOM and you read it later with a ref or FormData; it is simpler for tiny forms and is what libraries like React Hook Form use internally.

const [name, setName] = useState('');
const [role, setRole] = useState('DEVELOPER');
const [active, setActive] = useState(true);
const [shift, setShift] = useState('day');

// Text, number, email, password, textarea: value + onChange
<input value={name} onChange={(e) => setName(e.target.value)} />

// Select: value on the select, not "selected" on options
<select value={role} onChange={(e) => setRole(e.target.value)}>
  <option value="DEVELOPER">Developer</option>
  <option value="TESTER">Tester</option>
</select>

// Checkbox: checked + e.target.checked
<input type="checkbox" checked={active} onChange={(e) => setActive(e.target.checked)} />

// Radio group: checked is "does this one match the state?"
<input type="radio" name="shift" value="day"
       checked={shift === 'day'} onChange={(e) => setShift(e.target.value)} />
<input type="radio" name="shift" value="night"
       checked={shift === 'night'} onChange={(e) => setShift(e.target.value)} />

One state object and one handleChange

For forms with many fields, keep one object in state and give every input a name matching the key. One handler updates the right field using a computed property name [name].

import { useState } from 'react';

const empty = { name: '', email: '', salary: '', department: 'ENGINEERING', active: true };

function validate(values) {
  const errors = {};
  if (!values.name.trim()) errors.name = 'Name is required';
  if (!/^\S+@\S+\.\S+$/.test(values.email)) errors.email = 'Enter a valid email';
  const salary = Number(values.salary);
  if (!Number.isFinite(salary) || salary <= 0) errors.salary = 'Salary must be greater than 0';
  return errors;
}

function EmployeeForm({ initialValues = empty, onSubmit }) {
  const [values, setValues] = useState(initialValues);
  const [errors, setErrors] = useState({});
  const [submitting, setSubmitting] = useState(false);
  const [submitError, setSubmitError] = useState(null);

  function handleChange(e) {
    const { name, type, value, checked } = e.target;
    setValues((prev) => ({ ...prev, [name]: type === 'checkbox' ? checked : value }));
  }

  async function handleSubmit(e) {
    e.preventDefault();                       // stop the page reload
    const found = validate(values);
    setErrors(found);
    if (Object.keys(found).length > 0) return;   // do not send invalid data

    setSubmitting(true);
    setSubmitError(null);
    try {
      await onSubmit({ ...values, salary: Number(values.salary) });
    } catch (err) {
      setSubmitError(err.message);
    } finally {
      setSubmitting(false);
    }
  }

  return (
    <form onSubmit={handleSubmit} noValidate>
      <label htmlFor="name">Name</label>
      <input id="name" name="name" value={values.name} onChange={handleChange}
             aria-invalid={Boolean(errors.name)} aria-describedby="name-error" />
      {errors.name && <p id="name-error" className="error">{errors.name}</p>}

      <label htmlFor="email">Email</label>
      <input id="email" name="email" type="email" value={values.email}
             onChange={handleChange} />
      {errors.email && <p className="error">{errors.email}</p>}

      <label htmlFor="salary">Salary (₹ per month)</label>
      <input id="salary" name="salary" type="number" value={values.salary}
             onChange={handleChange} />
      {errors.salary && <p className="error">{errors.salary}</p>}

      <label>
        <input type="checkbox" name="active" checked={values.active} onChange={handleChange} />
        Active
      </label>

      {submitError && <p role="alert" className="error">{submitError}</p>}
      <button type="submit" disabled={submitting}>
        {submitting ? 'Saving…' : 'Save employee'}
      </button>
    </form>
  );
}

export default EmployeeForm;

Validation: when and where

  • On submit is the simplest and least annoying: validate all fields, show all errors.
  • On blur (when the user leaves a field) gives early feedback; track a touched object so you do not show errors on fields the user has not visited.
  • On every change suits password strength or availability hints, but shouting "invalid email" while the user is still typing is bad UX.
  • HTML attributes (required, minLength, pattern, type="email") give free browser validation. Use noValidate on the form when you show your own messages.
  • The server decides. Client validation is for convenience. Spring Boot's @Valid must check everything again, and the UI must display the server's field errors (see Module 6).

Edge cases that surprise people

  • value must never be undefined or null. React then treats the input as uncontrolled and later warns "A component is changing an uncontrolled input to be controlled." Start with ''.
  • value without onChange makes a read-only input and a warning. Use readOnly or add the handler.
  • Number inputs return strings. Convert with Number() before sending JSON, or Spring will complain it cannot parse "85000" into a BigDecimal in some configurations (it usually coerces, but do not rely on it).
  • Date inputs return yyyy-MM-dd strings, which Jackson maps to LocalDate directly.
  • For file uploads use <input type="file" /> (always uncontrolled) and send FormData.
  • Every input needs a <label htmlFor> matching its id (or wrap the input in the label) for accessibility.

React Hook Form + Zod (the common library choice)

Hand-written forms get long. Most teams use React Hook Form (RHF), which tracks inputs without re-rendering on every keystroke, together with Zod, a schema library that defines the rules once and also gives you TypeScript types. The bridge is the @hookform/resolvers package. Install with npm install react-hook-form zod @hookform/resolvers.

import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import { z } from 'zod';

const schema = z.object({
  name: z.string().min(1, 'Name is required'),
  email: z.string().email('Enter a valid email'),
  salary: z.coerce.number().positive('Salary must be greater than 0'),
});

function EmployeeFormRhf({ onSubmit }) {
  const {
    register,
    handleSubmit,
    setError,
    formState: { errors, isSubmitting },
  } = useForm({ resolver: zodResolver(schema) });

  async function submit(values) {
    try {
      await onSubmit(values);
    } catch (err) {
      setError('email', { message: 'This email is already registered' });  // server error
    }
  }

  return (
    <form onSubmit={handleSubmit(submit)} noValidate>
      <input {...register('name')} placeholder="Name" />
      {errors.name && <p className="error">{errors.name.message}</p>}

      <input {...register('email')} placeholder="Email" />
      {errors.email && <p className="error">{errors.email.message}</p>}

      <input type="number" {...register('salary')} placeholder="Salary" />
      {errors.salary && <p className="error">{errors.salary.message}</p>}

      <button disabled={isSubmitting}>Save</button>
    </form>
  );
}

The API names above (register, handleSubmit, formState, setError, zodResolver) are stable across recent versions, but check the library docs for current details. Zod's Java parallel is Bean Validation: the schema is your @NotBlank, @Email and @Positive in one place.

Rules for forms

  • Always e.preventDefault() in onSubmit (or let RHF's handleSubmit do it).
  • Use a real <form> with a type="submit" button so Enter works. Buttons that are not submit buttons should say type="button".
  • Never trust client validation; the backend validates again.
  • Disable the submit button (or ignore clicks) while a request is running to prevent double submits.

Common mistakes

  • Forgetting preventDefault: the page reloads and all state vanishes.
  • Writing onChange={setName(e.target.value)} (calling instead of passing).
  • Mutating the state object in handleChange (values[name] = value).
  • A button inside the form that should not submit but has no type="button".
  • Using defaultValue and value on the same input.

Interview: "Controlled vs uncontrolled components?"

  • Controlled: value lives in React state, changes come through onChange; easy validation and dependent fields, more re-renders.
  • Uncontrolled: DOM keeps the value, read through a ref or FormData; less code, fewer renders. File inputs are always uncontrolled.
  • Libraries such as React Hook Form use uncontrolled inputs with refs for speed.

Routing with React Router

React Router maps URL paths to components inside a single page: declare Routes, navigate with Link and useNavigate, read URL data with useParams and useSearchParams, and nest routes with Outlet.

Why a router?

A single-page app has one HTML file, but users expect different URLs for different screens: /employees, /employees/42, /login. They also expect the back button, bookmarks and shareable links to work. A client-side router watches the URL (using the browser History API), renders the matching component, and changes the address without a page reload. Install it with npm install react-router.

Version note: React Router v7

React Router v7 is the current major version. In v7 the package is react-router; the DOM pieces (BrowserRouter, Link, NavLink, …) are imported from react-router, and react-router-dom remains as a package that re-exports them for older projects. Older v6 code imports from react-router-dom. v7 can be used in two ways: the classic declarative mode shown here (BrowserRouter + Routes), a data mode with createBrowserRouter and loaders, and a framework mode (Remix merged into it). This module uses the declarative API because it is the same in v6 and v7. If your project's package.json says react-router-dom, use that import path.

Setup

import { StrictMode } from 'react';

  </StrictMode>,

function App() {
  return (
    <Routes>
      <Route path="/login" element={<LoginPage />} />

      {/* Layout route: renders the shared header, then the child route in its Outlet */}
      <Route element={<Layout />}>
        <Route index element={<HomePage />} />
        <Route path="employees" element={<EmployeeListPage />} />
        <Route path="employees/:id" element={<EmployeeDetailPage />} />

}

Nested routes and the path rules

  • A route with no path but an element is a layout route: it wraps its children and shows them in <Outlet />.
  • index marks the default child of a parent path (the page at exactly / or /employees).
  • Child paths are relative to the parent: path="employees" then path=":id" gives /employees/:id. Do not start child paths with / unless you want an absolute path.
  • path="*" matches anything not matched elsewhere — your 404 page.
  • Router v6+ ranks routes by specificity, so the order you write them in does not matter.
  • <NavLink to="/" end> needs end so "Home" is not active on every page.

Rule: the server must also serve index.html for every path

Routing happens in the browser. If a user refreshes on /employees/42, the browser asks the web server for that path, and a plain static server returns 404. Vite's dev server already falls back to index.html. In production you must configure the same fallback (Netlify/Vercel rewrites, Nginx try_files, a Spring Boot forward controller) — see deployment in Module 6.

Conventions

  • Keep one component per route in src/pages/, named XxxPage; they fetch data and compose smaller components.
  • Put list filters, sort order and page numbers in search params so links are shareable.
  • Use replace when a redirect should not add a history entry (login redirect).
  • Link to routes with a helper or constants if paths repeat a lot.

Edge cases

  • useParams values are always strings ("42"), so id === 42 is false. This breaks strict comparisons with numeric ids.
  • The same page component rendered for /employees/1 and /employees/2 is not remounted when the id changes; state is kept, and your fetch effect must list id as a dependency.
  • Using <a href="/employees"> inside the app causes a full page reload and loses all state.
  • useNavigate must be called inside a component under the Router; calling it outside gives an error "useNavigate() may be used only in the context of a <Router> component".
  • Hash router (HashRouter, URLs like /#/employees) works without server rewrites but looks old; prefer BrowserRouter.

Interview: "How does client-side routing work?"

  • The router listens to URL changes via the History API (pushState, popstate), matches the path to a route, and renders its component without a page reload.
  • Dynamic segments (:id) come from useParams; query data from useSearchParams; layouts use nested routes with Outlet.
  • On refresh, the server must return index.html for all app paths (SPA fallback).

Sharing state: lifting state up and the Context API

When two components need the same state, move it to their closest common parent and pass it down; when many distant components need it, put it in a Context provider and read it with useContext.

Lifting state up

Each piece of state has one owner. If a sibling needs it too, you lift it up: the parent owns the state and passes the value (down) and a setter or handler (so children can ask for changes) as props. There is one source of truth, so the siblings can never disagree.

function EmployeesPage() {
  const [search, setSearch] = useState('');           // owned by the parent
  const [employees] = useState(initialEmployees);

  const visible = employees.filter((e) =>
    e.name.toLowerCase().includes(search.toLowerCase()),
  );

  return (
    <>
      <SearchBar value={search} onChange={setSearch} />     {/* writes the state */}
      <ResultCount count={visible.length} />               {/* reads derived data */}
      <EmployeeList employees={visible} />
    </>
  );
}

function SearchBar({ value, onChange }) {          // a controlled component
  return <input value={value} onChange={(e) => onChange(e.target.value)} />;
}

How far up should you lift? To the closest common parent, and no further. Lifting too high makes that parent re-render (and re-render all its children) on every change, and passes props through components that do not care. A good habit: keep state as low as possible, and lift it only when a second component needs it. The opposite move also exists: if only one child uses a piece of state, push it down into that child.

Props, children and composition

Before reaching for Context, try composition. A component can accept children (or JSX in other props) so the page that owns the data builds the middle layers' content itself, and the middle layers never see the props.

// The Layout does not know about user at all
function Layout({ sidebar, children }) {
  return (
    <div className="layout">
      <aside>{sidebar}</aside>
      <main>{children}</main>
    </div>
  );
}

function DashboardPage({ user }) {
  return (
    <Layout sidebar={<UserCard user={user} />}>
      <Orders userId={user.id} />
    </Layout>
  );
}

The Context API

Lifting works until the value must pass through many layers (prop drilling). Context lets a component make a value available to everything below it without passing props. It has three steps: create the context, provide a value high in the tree, and read it anywhere below. Think of it like a Spring bean in the application context: you declare it once at the top and any component below "injects" it with useContext, though it only lives in the component tree, not globally.

import { createContext, useCallback, useContext, useMemo, useState } from 'react';

// 1. Create. The default is used only when there is no provider above.
const AuthContext = createContext(null);

// 2. Provide
export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);       // { id, name, roles } or null

  const login = useCallback((userData) => setUser(userData), []);
  const logout = useCallback(() => setUser(null), []);

  // Memoise so consumers re-render only when something really changed
  const value = useMemo(() => ({ user, login, logout }), [user, login, logout]);

  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

// 3. Read, wrapped in a custom hook with a helpful error
export function useAuth() {
  const ctx = useContext(AuthContext);
  if (ctx === null) throw new Error('useAuth must be used inside an AuthProvider');
  return ctx;
}
// main.jsx: wrap the app once
<AuthProvider>
  <App />
</AuthProvider>

// Any component, any depth
function Header() {
  const { user, logout } = useAuth();
  return user ? <button onClick={logout}>Logout {user.name}</button> : null;
}

A realistic AuthProvider: restoring the session

A real provider also has to answer "is someone already logged in?" when the page loads. With a cookie-based session or a stored token you ask the backend (for example GET /api/auth/me in Spring Boot), and until the answer arrives the app does not know. That is why the context exposes an isLoading flag; protected routes use it so they do not redirect too early. The token flow itself is in JWT login end to end.

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  const [isLoading, setIsLoading] = useState(true);     // true until /me answers

  useEffect(() => {
    const controller = new AbortController();
    fetch('/api/auth/me', { signal: controller.signal, credentials: 'include' })
      .then((res) => (res.ok ? res.json() : null))      // 401 = not logged in
      .then((me) => setUser(me))
      .catch(() => {})                                   // aborted or network error
      .finally(() => {
        if (!controller.signal.aborted) setIsLoading(false);
      });
    return () => controller.abort();
  }, []);

  const login = useCallback((me) => setUser(me), []);
  const logout = useCallback(() => setUser(null), []);

  const value = useMemo(
    () => ({ user, isLoading, login, logout }),
    [user, isLoading, login, logout],
  );
  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

Version note: React 19 and Context

In React 19 you can render the context itself as the provider: <AuthContext value={value}>…</AuthContext>. The <AuthContext.Provider> form still works and is what most existing code uses. The use(AuthContext) API can read a context too, but useContext is still the everyday choice.

What Context is good and bad at

When the provider's value changes, every component that reads that context re-renders, even if it only uses one field. Context has no selector mechanism. So it suits values that change rarely and are needed widely: the current user, theme, language, feature flags, the router. It is a poor fit for fast-changing data (mouse position, a form on every keystroke, large lists) or for server data (use TanStack Query). For big client state with frequent updates, look at Redux Toolkit or Zustand in Module 7.

How context re-renders work

Two different things can cause a re-render, and they are easy to mix up.

  • The provider's parent re-renders. If the provider component gets new props or its own state changes, it renders again. Its children prop is the same element objects as before (they were created by the component above), so React skips re-rendering those children. That is why wrapping children inside the provider is cheap, as in AuthProvider above.
  • The context value changes. React compares the new value with the old one using Object.is. If different, every component that called useContext for that context re-renders, skipping any memo in between.

This is why the object literal matters. value={{ user, login }} creates a new object each render of the provider, so the comparison always says "changed", and all consumers re-render even if user is the same. useMemo keeps the same object until a dependency changes.

Wrong: new value object every render

function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

Right: memoised value

function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('light');
  const value = useMemo(() => ({ theme, setTheme }), [theme]);
  return (
    <ThemeContext.Provider value={value}>
      {children}
    </ThemeContext.Provider>
  );
}

setTheme from useState is stable (same function every render), so it does not need to be in the dependency list. Functions you define yourself (like login) need useCallback to stay stable; see useMemo and useCallback.

Splitting a context

If some components only need to change a value (a "Logout" button) and others only read it, use two contexts so the writers do not re-render when the data changes. This is a common pattern for larger state.

const CartStateContext = createContext(null);
const CartActionsContext = createContext(null);

export function CartProvider({ children }) {
  const [items, setItems] = useState([]);

  const actions = useMemo(() => ({
    add: (item) => setItems((prev) => [...prev, item]),
    remove: (id) => setItems((prev) => prev.filter((i) => i.id !== id)),
    clear: () => setItems([]),
  }), []);                                  // setItems is stable, so never changes

  return (
    <CartActionsContext.Provider value={actions}>
      <CartStateContext.Provider value={items}>{children}</CartStateContext.Provider>
    </CartActionsContext.Provider>
  );
}

Rule: a consumer must be below its provider

useContext reads the value of the nearest provider above the component in the tree. If there is none, it returns the default passed to createContext. Putting null as the default and throwing in your useXxx hook turns a silent bug into a clear error message. Providers can be nested; the inner one overrides the outer one for its subtree.

Conventions

  • One context per concern (AuthContext, ThemeContext); do not make one giant "AppContext".
  • Export a Provider component and a useXxx hook; do not export the raw context object.
  • Memoise the provider value (useMemo) when it is an object.
  • Split state and dispatch into two contexts if consumers mostly need only one.
  • Keep providers near the top (main.jsx), but put feature-specific ones around only that feature's routes.

Common mistakes

  • Passing a fresh object literal as value={{ user, login }} without memoising — every parent render re-renders all consumers.
  • Reading the context outside its provider and getting null or the default.
  • Putting all server data into context and hand-rolling cache invalidation.
  • Lifting state far higher than needed "just in case".
  • Keeping a copy of context data in local state (useState(user)); the copy goes stale when the context changes. Read it directly.
  • Storing a rapidly changing value (a text field's draft, the scroll position) in a global context, so half the app re-renders on every keystroke.

Edge cases

  • Context values are compared with Object.is; mutating an object in place and keeping the same reference will not notify consumers. Always create a new object or array.
  • Context does not cross separate React roots, and in tests you must wrap the component in the provider (a small renderWithProviders helper is normal).
  • React.memo on a consumer does not stop context-driven re-renders; the context update bypasses it.

In real projects

A typical Spring Boot + React app has an AuthProvider (current user and roles), maybe a ThemeProvider and a toast/notification provider. Everything that comes from your REST API (employees, orders) goes through TanStack Query instead, and form drafts stay local. That keeps the contexts small and rarely changing.

Interview: "Prop drilling, and how do you avoid it?"

  • Passing props through components that do not use them. Fix with composition, Context, or a state library.
  • Context re-renders all consumers when its value changes, so it is for low-frequency global values; use selectors (Zustand/Redux) for hot state.
  • Lifting state up: the closest common parent owns the state; children receive value and callbacks.
  • Why memoise the provider value? A new object each render makes Object.is see a change and re-renders every consumer.
  • Is Context a replacement for Redux? Not for frequent updates or complex logic; it only transports a value, it does not manage state by itself.

Custom hooks

A custom hook is a function whose name starts with use and that calls other hooks, so you can share stateful logic between components without sharing state.

Why and how

When two components need the same combination of useState, useEffect and helpers, extract it into a function. The hook must start with use (so React and the linter know the rules of hooks apply) and can call any hook. Each component that calls the hook gets its own copy of the state; hooks share logic, not data. Return what the component needs: a value, an array, or an object.

If you know Java, a custom hook is closest to a small reusable service class that you create per use, not a singleton: every new gives separate fields. The "fields" are the state and effects inside the hook, and the component that calls it owns them. Nothing is magic: when the hook's state changes, the component that called it re-renders, exactly as if you had written that useState directly in the component.

Extracting a hook step by step

  1. Spot repeated code: the same useState plus useEffect pair in two components.
  2. Cut it into a function named useSomething in src/hooks/.
  3. Turn the values that differ (a URL, a key, a delay) into parameters.
  4. Return the values and functions the component needs, and replace the old code with one call.

A first, tiny hook: useToggle

import { useCallback, useState } from 'react';

export function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn((v) => !v), []);   // stable function identity
  return [on, toggle, setOn];
}

// Use: const [open, toggleOpen] = useToggle();
//      <button onClick={toggleOpen}>{open ? 'Hide' : 'Show'} details</button>

useLocalStorage

import { useEffect, useState } from 'react';

export function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    try {
      const stored = localStorage.getItem(key);
      return stored !== null ? JSON.parse(stored) : initialValue;
    } catch {
      return initialValue;       // blocked storage or invalid JSON
    }
  });

  useEffect(() => {
    try {
      localStorage.setItem(key, JSON.stringify(value));
    } catch {
      // storage full or disabled: ignore
    }
  }, [key, value]);

  return [value, setValue];      // same shape as useState
}

// Use: const [theme, setTheme] = useLocalStorage('theme', 'light');

Because it returns the real setValue from useState, the functional form also works: setTheme((t) => (t === 'light' ? 'dark' : 'light')). The initial value is read once, using a function passed to useState (a lazy initialiser), so localStorage is not read on every render. Do not store tokens or secrets here; see the storage trade-offs in JWT login end to end.

useDebounce

Debouncing waits until the user stops typing before using the value, which avoids one API call per keystroke.

import { useEffect, useState } from 'react';

export function useDebounce(value, delayMs = 400) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delayMs);
    return () => clearTimeout(id);       // typing again cancels the pending update
  }, [value, delayMs]);

  return debounced;
}
function EmployeeSearch() {
  const [text, setText] = useState('');
  const query = useDebounce(text, 400);

  useEffect(() => {
    if (!query) return;
    const controller = new AbortController();
    fetch(`/api/employees?q=${encodeURIComponent(query)}`, { signal: controller.signal })
      .then((r) => r.json())
      .then(console.log)
      .catch(() => {});
    return () => controller.abort();
  }, [query]);          // runs when the debounced value changes, not on each keystroke

  return <input value={text} onChange={(e) => setText(e.target.value)} />;
}

The input stays instant because text updates on every keystroke; only the debounced copy is delayed. A debounce hook returns a delayed value; a "debounced function" is a different tool. The server side matters too: your Spring Boot endpoint should still be efficient (an index on the searched column), because debouncing only reduces the number of calls.

useFetch

This hook bundles the loading / error / data pattern from fetching data, including the cleanup.

import { useEffect, useState } from 'react';

export function useFetch(url) {
  const [state, setState] = useState({ data: null, error: null, loading: true });

  useEffect(() => {
    const controller = new AbortController();
    setState({ data: null, error: null, loading: true });

    fetch(url, { signal: controller.signal })
      .then((res) => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json();
      })
      .then((data) => setState({ data, error: null, loading: false }))
      .catch((error) => {
        if (error.name !== 'AbortError') setState({ data: null, error, loading: false });
      });

    return () => controller.abort();
  }, [url]);

  return state;
}

// Use:
// const { data: employees, error, loading } = useFetch('/api/employees');

When url changes (a new page number, a different employee id) the cleanup aborts the old request, so a slow earlier response can never overwrite a newer one: this is the race condition from the fetching article, solved once inside the hook. Components that use it stay short:

function EmployeePage({ id }) {
  const { data: employee, error, loading } = useFetch(`/api/employees/${id}`);

  if (loading) return <p>Loading…</p>;
  if (error) return <p role="alert">Could not load: {error.message}</p>;
  return <h2>{employee.name}</h2>;
}

A production-grade version needs caching, retries, deduplication and refetching — exactly what TanStack Query provides. Write useFetch once to understand the pattern, then prefer the library.

Hooks that wrap your domain

The most useful custom hooks in real projects are domain hooks like useEmployees(), useAuth() or useCart(). They hide where data comes from, so components stay small and you can change the implementation (hand-written fetch → TanStack Query) without touching them. This is the same idea as a Spring service interface: callers depend on the contract, not the implementation.

import { useCallback } from 'react';
import { useFetch } from './useFetch.js';

export function useEmployees(department) {
  const url = department
    ? `/api/employees?department=${encodeURIComponent(department)}`
    : '/api/employees';
  const { data, error, loading } = useFetch(url);

  const hasData = data !== null;
  return { employees: data ?? [], error, loading, hasData };
}

Rules for custom hooks

  • The name starts with use. Without it the linter cannot enforce the rules of hooks inside.
  • Call it only at the top level of a component or another hook: not inside loops, conditions, nested functions, or after an early return. React tracks hooks by call order, so the order must be the same on every render.
  • Call hooks only from React function components or other hooks, never from plain functions or class components.
  • Hooks share logic, not state: two components calling useFetch make two requests.
  • Do not create a hook that does nothing hook-like (no hook calls inside): a normal function is enough.

Conventions

  • One hook per file in src/hooks/, file name equals hook name (useDebounce.js).
  • Return an array for one or two values that callers will rename (like useState), and an object for three or more.
  • Accept simple parameters; for many options take one options object with defaults.
  • Keep a hook focused: "fetch", "debounce", "toggle". Compose small hooks into bigger domain hooks instead of writing one that does everything.

Mistakes

  • Expecting two components to share data just because they call the same hook. Each call has its own state; for shared state use Context, lifting, or a data library.
  • Passing an object or function created inline into the dependency array of the effect inside the hook (useFetch(url, { headers }) with a new headers object each render): the effect re-runs on every render and may loop. Memoise it, depend on its primitive fields, or accept primitives.
  • Forgetting the cleanup (abort, clearTimeout, remove listener) so a stale result or leaked timer arrives after the component has changed.
  • Calling the hook conditionally: if (id) { useFetch(...) } breaks the call order. Call it always and make the hook skip the work (for example, accept an enabled option or a null URL).

Edge cases

  • In development, Strict Mode runs effects twice, so useFetch may send two requests on mount. This is expected and only happens in development; the abort in the cleanup makes it harmless.
  • useLocalStorage reads the browser's storage, so it fails during server-side rendering where localStorage does not exist. In a Vite single-page app this does not matter, and the try / catch covers blocked storage.
  • Updates made in one browser tab do not reach useLocalStorage in another tab unless you also listen to the storage event.

Tip: test them too

Hooks can be tested with renderHook from React Testing Library (see Module 7). Keep logic in hooks and plain functions, and components become thin and easy to test.

Interview: "What is a custom hook and why use one?"

  • A function starting with use that composes built-in hooks to reuse stateful logic (fetching, forms, debouncing, local storage).
  • Each call has isolated state; hooks share logic only.
  • Benefits: no duplicated code, smaller components, testable logic, swap implementations behind a stable interface.
  • Be ready to write useDebounce or useLocalStorage on a whiteboard, and to state the two rules of hooks (top level only; only from components or hooks).
  • Follow-up: "Does a custom hook make two components share state?" No; use Context or lift the state.

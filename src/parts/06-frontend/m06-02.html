JWT login end to end: storing the token and handling 401

The login form POSTs credentials, Spring Boot returns a JWT, the app keeps it (best: in memory, with a refresh token in an httpOnly cookie), attaches it as Authorization: Bearer to every request, and reacts to 401 by refreshing or logging out.

The flow

The backend side (generating and verifying the JWT, the security filter) is covered in Spring Boot · Module 4. Here is the frontend's half of the same conversation.

  1. Login request. Send { email, password } over HTTPS to a public endpoint such as POST /api/auth/login.
  2. Token response. The backend returns the JWT (and user info: id, name, roles). A JWT is a signed string of three base64 parts: header, payload (claims such as sub, roles, exp) and signature. The payload is readable by anyone, so never put secrets in it.
  3. Store. Keep the token somewhere the next requests can read it (see the trade-offs below).
  4. Attach. A request interceptor adds Authorization: Bearer <token> to each call.
  5. Verify. Spring's JWT filter checks the signature and expiry on each request (the server stays stateless).
  6. Expiry. When exp passes, the API answers 401. The client either gets a new token with a refresh token, or sends the user back to the login page.

Where to store the token

This is a security decision, and a favourite interview question. The two attacks to know: XSS (cross-site scripting: attacker JavaScript runs on your page and can read anything JavaScript can read) and CSRF (cross-site request forgery: another site makes the browser send a request that carries your cookies automatically).

StorageXSS riskCSRF riskSurvives reload?
localStorageHigh: any script can read the tokenNone (not sent automatically)Yes
sessionStorageHigh, same as aboveNonePer tab only
JavaScript memory (a variable)Lower: the token is not in a place scripts can scrape later, but running malicious code can still use itNoneNo; needs a refresh to restore
httpOnly cookieJavaScript cannot read it, so it cannot be stolen by XSS (it can still be used by injected code to make requests)Yes: you need SameSite and/or CSRF tokensYes

The recommended pattern

  • Keep the short-lived access token (say 15 minutes) in memory.
  • Keep a long-lived refresh token in an httpOnly, Secure, SameSite cookie, scoped to the refresh endpoint (POST /api/auth/refresh).
  • On page load, call the refresh endpoint: if the cookie is valid you get a new access token and the session is restored. A reload therefore does not log the user out.
  • Use CSRF protection on the refresh endpoint (SameSite=Strict/Lax plus a check) since it relies on a cookie.

localStorage is simple and very common in tutorials and small projects, and many employers accept it, but you should be able to explain its XSS weakness. For learning projects it is acceptable; say so honestly in an interview.

AuthContext: login, logout and the current user

The Context pattern fits auth well: the user changes rarely and many components need it. The provider exposes user, isLoading, login and logout, and restores the session when the app starts.

import { createContext, useCallback, useContext, useEffect, useMemo, useState } from 'react';
import { api } from '../lib/axios.js';
import { tokenStore } from '../lib/tokenStore.js';

const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  const [isLoading, setIsLoading] = useState(true);    // true until we know if a session exists

  // Restore the session on page load: the refresh cookie gives us a new access token
  useEffect(() => {
    let ignore = false;
    api.post('/auth/refresh', null, { withCredentials: true })
      .then(({ data }) => {
        if (ignore) return;
        tokenStore.set(data.accessToken);
        setUser(data.user);
      })
      .catch(() => { /* no valid session: user stays null */ })
      .finally(() => { if (!ignore) setIsLoading(false); });
    return () => { ignore = true; };
  }, []);

  // The 401 interceptor fires this event when the token is rejected
  useEffect(() => {
    const onForcedLogout = () => setUser(null);
    window.addEventListener('auth:logout', onForcedLogout);
    return () => window.removeEventListener('auth:logout', onForcedLogout);
  }, []);

  const login = useCallback(async (email, password) => {
    const { data } = await api.post('/auth/login', { email, password }, { withCredentials: true });
    tokenStore.set(data.accessToken);
    setUser(data.user);
    return data.user;
  }, []);

  const logout = useCallback(async () => {
    try {
      await api.post('/auth/logout', null, { withCredentials: true });
    } finally {
      tokenStore.clear();
      setUser(null);
    }
  }, []);

  const value = useMemo(
    () => ({ user, isLoading, isAuthenticated: user !== null, login, logout }),
    [user, isLoading, login, logout],
  );
  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth must be used inside AuthProvider');
  return ctx;
}

The login page

import { useState } from 'react';
import { Navigate, useLocation, useNavigate } from 'react-router';
import { useAuth } from '../context/AuthContext.jsx';
import { describeError } from '../lib/errors.js';

function LoginPage() {
  const { login, isAuthenticated } = useAuth();
  const navigate = useNavigate();
  const location = useLocation();
  const from = location.state?.from?.pathname ?? '/employees';   // where the user wanted to go

  const [form, setForm] = useState({ email: '', password: '' });
  const [error, setError] = useState(null);
  const [submitting, setSubmitting] = useState(false);

  if (isAuthenticated) return <Navigate to={from} replace />;

  async function handleSubmit(e) {
    e.preventDefault();
    setSubmitting(true);
    setError(null);
    try {
      await login(form.email, form.password);
      navigate(from, { replace: true });             // do not leave /login in history
    } catch (err) {
      setError(err.response?.status === 401 ? 'Wrong email or password' : describeError(err));
    } finally {
      setSubmitting(false);
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <h1>Login</h1>
      <label htmlFor="email">Email</label>
      <input id="email" type="email" autoComplete="username" required value={form.email}
             onChange={(e) => setForm({ ...form, email: e.target.value })} />
      <label htmlFor="password">Password</label>
      <input id="password" type="password" autoComplete="current-password" required
             value={form.password}
             onChange={(e) => setForm({ ...form, password: e.target.value })} />
      {error && <p role="alert" className="error">{error}</p>}
      <button disabled={submitting}>{submitting ? 'Signing in…' : 'Login'}</button>
    </form>
  );
}

export default LoginPage;

Handling 401 and 403

StatusMeaningFrontend reaction
401 UnauthorizedNot authenticated: no token, bad token, expired tokenRefresh the token once and retry; if that fails, clear the session and go to /login
403 ForbiddenAuthenticated but not allowedShow "You do not have access"; do not log out

To refresh and retry transparently, extend the response interceptor. Share one refresh promise so that ten simultaneous 401 responses trigger only one refresh call.

let refreshPromise = null;

api.interceptors.response.use(
  (res) => res,
  async (error) => {
    const original = error.config;
    const isAuthCall = original?.url?.includes('/auth/');

    if (error.response?.status === 401 && !original._retry && !isAuthCall) {
      original._retry = true;                           // retry each request only once
      try {
        refreshPromise ??= api.post('/auth/refresh', null, { withCredentials: true })
          .then(({ data }) => { tokenStore.set(data.accessToken); return data.accessToken; })
          .finally(() => { refreshPromise = null; });
        const newToken = await refreshPromise;
        original.headers.Authorization = `Bearer ${newToken}`;
        return api(original);                           // repeat the failed request
      } catch {
        tokenStore.clear();
        window.dispatchEvent(new Event('auth:logout'));
      }
    }
    return Promise.reject(error);
  },
);

Rules

  • Use HTTPS in production; a JWT sent over HTTP can be stolen on the network.
  • Keep access tokens short-lived. A JWT cannot be revoked before exp unless the server keeps a deny list.
  • Never put passwords, personal data or secrets in the JWT payload; it is only encoded, not encrypted.
  • Never trust client-side checks of the JWT (decoding exp or roles) for security; they are for convenience. The server verifies every request.
  • Do not log tokens. Never commit real tokens to Git.

Common mistakes

  • Sending the token as Authorization: token or Bearer: token. The format is Authorization: Bearer <token> with a space.
  • Calling the app logged out after refresh because the token lived only in a variable and there is no refresh step.
  • Handling 401 on the login request itself (redirect loop or lost message).
  • A refresh interceptor that retries forever; use a _retry flag and exclude auth endpoints.
  • Forgetting withCredentials / CORS credentials settings when using cookies, so the browser silently drops the cookie.

Interview: "Explain the JWT login flow and where you store the token"

  • Login POST → server verifies the password → returns signed JWT → client sends it as a Bearer header → server verifies the signature and expiry on every request (stateless).
  • localStorage: easy but XSS-readable. httpOnly cookie: safe from XSS theft but needs CSRF defence. Best practice: access token in memory plus refresh token in an httpOnly cookie.
  • 401 means not authenticated (refresh or re-login); 403 means authenticated but forbidden.
  • On reload, restore the session by calling refresh (or /me with a stored token).

Protected routes and role-based UI

A RequireAuth route wrapper redirects anonymous users to /login and remembers where they wanted to go; role checks hide UI and pages from the wrong users, but only the backend can truly enforce access.

The idea: three layers of access control

"Who can see what" is decided in three places, and each has a different job. The browser layers exist for a good user experience; only the last one is security.

LayerExamplePurposeTrusted?
Route guardRequireAuth around /employeesSend anonymous users to loginNo (UX only)
UI hidingHasRole around a Delete buttonDo not show actions that will failNo (UX only)
API authorisation@PreAuthorize, 401/403Actually protect data and actionsYes

RequireAuth

A protected route renders its page only for a logged-in user. The component checks the auth context (see the AuthContext); while the session is still being restored on page load it shows a loading state (otherwise a logged-in user would be bounced to the login page on every refresh); if there is no user it redirects with <Navigate>, saving the current location in route state so that the login page can send the user back afterwards.

import { Navigate, Outlet, useLocation } from 'react-router';
import { useAuth } from '../context/AuthContext.jsx';

function RequireAuth({ roles }) {
  const { user, isLoading } = useAuth();
  const location = useLocation();

  if (isLoading) return <p>Checking your session…</p>;          // do not redirect too early

  if (!user) {
    // Remember the page they wanted; replace so Back does not return to a blocked page
    return <Navigate to="/login" replace state={{ from: location }} />;
  }

  if (roles && !roles.some((r) => user.roles.includes(r))) {
    return <Navigate to="/forbidden" replace />;                // logged in, wrong role
  }

  return <Outlet />;                                            // render the child routes
}

export default RequireAuth;
function App() {
  return (
    <Routes>
      <Route path="/login" element={<LoginPage />} />
      <Route path="/forbidden" element={<ForbiddenPage />} />

      {/* Every route inside needs a logged-in user */}
      <Route element={<RequireAuth />}>
        <Route element={<Layout />}>
          <Route index element={<DashboardPage />} />
          <Route path="employees" element={<EmployeeListPage />} />
          <Route path="employees/:id" element={<EmployeeDetailPage />} />
        </Route>
      </Route>

      {/* Only ADMIN users */}
      <Route element={<RequireAuth roles={['ADMIN']} />}>
        <Route element={<Layout />}>
          <Route path="admin/users" element={<UserAdminPage />} />
        </Route>
      </Route>

      <Route path="*" element={<NotFoundPage />} />
    </Routes>
  );
}

Because RequireAuth renders an <Outlet />, it works as a layout route (a route with no path): one guard protects a whole group of pages. This is cleaner than wrapping each page in its own guard component. The guard is also a normal component, so it re-renders whenever the auth context changes; when the user logs out, it redirects by itself, with no extra code.

Sending the user back after login

The guard saved state.from. The login page reads it with useLocation, and after a successful login navigates to that path instead of always going to the dashboard. It also redirects away if the user is already signed in.

import { Navigate, useLocation, useNavigate } from 'react-router';
import { useAuth } from '../context/AuthContext.jsx';

function LoginPage() {
  const { user, login } = useAuth();
  const navigate = useNavigate();
  const location = useLocation();

  // Same-app path only; fall back to the home page
  const from = location.state?.from?.pathname ?? '/';

  if (user) return <Navigate to={from} replace />;       // already signed in

  async function handleSubmit(e) {
    e.preventDefault();
    const form = new FormData(e.currentTarget);
    const res = await fetch('/api/auth/login', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(Object.fromEntries(form)),
      credentials: 'include',
    });
    if (res.ok) {
      login(await res.json());                 // sets the user in AuthContext
      navigate(from, { replace: true });       // back to /employees/7
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <input name="email" type="email" required />
      <input name="password" type="password" required />
      <button>Login</button>
    </form>
  );
}

Roles in the UI

Hide buttons and menu items the user cannot use. A small helper keeps the check readable:

import { useAuth } from '../context/AuthContext.jsx';

export function useHasRole(...roles) {
  const { user } = useAuth();
  return Boolean(user) && roles.some((r) => user.roles.includes(r));
}

export function HasRole({ roles, children, fallback = null }) {
  const allowed = useHasRole(...roles);
  return allowed ? children : fallback;
}

// Use
// <HasRole roles={['ADMIN', 'HR']}><button onClick={onDelete}>Delete</button></HasRole>

The same hook can build a menu from a list, so the sidebar and the route table never disagree:

const NAV = [
  { to: '/employees', label: 'Employees', roles: ['USER', 'HR', 'ADMIN'] },
  { to: '/payroll', label: 'Payroll', roles: ['HR', 'ADMIN'] },
  { to: '/admin/users', label: 'Users', roles: ['ADMIN'] },
];

function Sidebar() {
  const { user } = useAuth();
  const items = NAV.filter((n) => n.roles.some((r) => user.roles.includes(r)));
  return (
    <nav>
      {items.map((n) => (
        <NavLink key={n.to} to={n.to}>{n.label}</NavLink>
      ))}
    </nav>
  );
}

Rule: frontend checks are for experience, the backend enforces security

Everything in the browser can be changed by the user: they can edit JavaScript, flip user.roles in DevTools, or call your API with curl. A hidden delete button does not stop DELETE /api/employees/7. Every endpoint must check authentication and authorisation itself — @PreAuthorize("hasRole('ADMIN')") or requestMatchers rules in Spring Security (Spring Boot · Module 4). The server must answer 403 for a forbidden call, and the UI should handle that 403 gracefully.

Wrong: the role check exists only in React

@DeleteMapping("/api/employees/{id}")
public void delete(@PathVariable Long id) {
    employeeService.delete(id);      // any logged-in user, or anyone with curl, can call this
}

Right: the server checks the role too

@PreAuthorize("hasRole('ADMIN')")
@DeleteMapping("/api/employees/{id}")
public void delete(@PathVariable Long id) {
    employeeService.delete(id);      // others get 403 Forbidden
}

Handling 401 and 403 in the UI

The two status codes mean different things, and your Axios interceptor or fetch wrapper (see Calling your API) should treat them differently.

StatusMeaningUI reaction
401 UnauthorizedNot logged in, or the token expiredClear the user in context; the guard redirects to login
403 ForbiddenLogged in, but not allowedShow "You do not have access" or a toast; keep the user logged in

Mistake: trusting a role stored in the browser

Reading the role from localStorage (localStorage.getItem('role')) and deciding access from it is the most common beginner error. The user can type localStorage.setItem('role', 'ADMIN') and see the admin pages. Take the roles from the server response (/me or the decoded token), and remember that even those only change what is shown. Another version: decoding the JWT in the browser and trusting its roles claim for anything beyond display. The backend verifies the signature; the browser cannot.

Role names must match the backend

Spring's hasRole('ADMIN') checks for the authority ROLE_ADMIN. Decide whether your /me response sends ADMIN or ROLE_ADMIN and be consistent in the frontend comparisons. A typo here causes "I am admin but see nothing". Keep the role names in one constants file (roles.js) instead of repeating string literals.

Conventions

  • Use a layout route with <Outlet /> for guards instead of wrapping every page.
  • Keep user, isLoading, login, logout in one AuthContext and expose it through a useAuth hook.
  • Check permissions rather than raw roles when the rules grow (can('employee:delete') instead of roles.includes('ADMIN')), so changing which role may do what touches one place.
  • Always give a 403 page and a 404 page their own routes.

Edge cases

  • Flash of login: skipping the isLoading branch redirects logged-in users to the login page for a moment (or permanently) on every refresh.
  • Deep links: a user opening /employees/7 while logged out should land on login, then come back to /employees/7; that is what state.from does. Only use same-app paths from the state, never a full URL from a query string, to avoid open-redirect bugs.
  • When the token expires while the user is on a page, the interceptor fires logout, the context sets user to null, and RequireAuth re-renders into the redirect — you get this for free with the event pattern.
  • Multiple tabs: logging out in one tab does not update the others unless you listen to the storage event or use BroadcastChannel.
  • Redirecting an already logged-in user away from /login (as in the login page above) avoids showing the form to signed-in users.
  • Roles can change on the server while the user is logged in. Re-fetch /me after important actions or on a timer; a stale role in the UI is harmless for security (the API still decides) but confusing.
  • A route guard hides a page only after the JavaScript bundle is downloaded. The code of an admin page is still visible to anyone who opens the files, so never put secrets or hidden endpoints' keys in it.

In real projects

A common setup: Spring Security issues a JWT or session cookie at login; /api/auth/me returns { id, name, roles }; AuthProvider calls it once on load; a single RequireAuth layout wraps all private pages and another with roles wraps admin pages; buttons use HasRole. Tests then check the important part separately: that the API returns 401 and 403 correctly without any React in front of it.

Interview: "How do you implement protected routes? Is hiding a button enough?"

  • A wrapper/layout route reads auth state; shows a loader while restoring the session; redirects with <Navigate to="/login" replace state={{ from }} /> if anonymous; renders <Outlet /> otherwise. Role checks add an allowed-roles prop.
  • Not enough: the client is untrusted. The API must enforce authentication and roles on every endpoint (401/403), and the UI only mirrors that for usability.
  • Explain 401 vs 403, and why the loading state avoids a redirect flash.
  • Where does the role come from, and can the user fake it? It comes from the server; the user can fake what the browser shows, never what the server allows.

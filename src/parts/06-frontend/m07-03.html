Testing the frontend: Vitest, React Testing Library, MSW and Playwright

Test what the user sees and does, not how the component is built: Vitest runs the tests, React Testing Library renders components and finds elements by role and label, MSW fakes the API at the network level, and a few Playwright tests check the whole app in a real browser.

What to test, and what not to

Frontend tests have a cost: they must be written and kept up to date. Spend that effort where bugs hurt. Think of a pyramid with many fast tests at the bottom and few slow ones at the top:

LevelToolTestsHow many
UnitVitestPure functions: formatters, validators, classifyErrorMany
Component / integrationVitest + React Testing Library (+ MSW)A form shows errors; a list shows loading, data, error; a button click calls the APIModerate: the sweet spot
End-to-end (E2E)PlaywrightLogin, create an employee, log out, in a real browser against a real or test backendFew: the critical journeys
  • Test behaviour: "when I submit an empty form, I see 'Name is required' and no request is sent". The user does not care that you used useState.
  • Do not test React itself, library internals, CSS details, or private state. A test that breaks when you refactor without changing behaviour is a bad test.
  • Backend rules (validation, security, transactions) are tested in Spring Boot (Spring Boot · Module 5). The frontend tests check that the UI reacts correctly to the responses.

Vitest: setup

Vitest is a test runner made for Vite projects. It reuses your Vite configuration, so imports, TypeScript and JSX just work, and it is fast. Its API (describe, it, expect) is almost the same as Jest, with vi instead of jest for mocks. React Testing Library (RTL) renders components into a simulated browser (jsdom, a Node.js implementation of the DOM) and gives you queries that find elements the way a user would.

$ npm install -D vitest jsdom @testing-library/react @testing-library/jest-dom \
    @testing-library/user-event msw
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',
    setupFiles: './src/test/setup.ts',
  },
});
import '@testing-library/jest-dom/vitest';   // adds toBeInTheDocument(), toBeDisabled(), ...
import { afterEach } from 'vitest';
import { cleanup } from '@testing-library/react';

afterEach(() => cleanup());                   // unmount rendered components after each test
{
  "scripts": {
    "test": "vitest",
    "test:run": "vitest run"
  }
}

npm test starts watch mode (re-runs affected tests when you save); vitest run runs once, which is what a CI pipeline uses (DevOps · Module 4). Vite loads .env.test in test mode, so put VITE_API_URL=http://localhost:8080/api there.

A first test: a pure function

import { describe, expect, it } from 'vitest';
import { classifyError } from './errors';

describe('classifyError', () => {
  it('treats a missing response as a retryable network error', () => {
    const info = classifyError({ code: 'ERR_NETWORK' });       // no "response" property
    expect(info.kind).toBe('network');
    expect(info.retryable).toBe(true);
  });

  it('does not retry a 404', () => {
    const info = classifyError({ response: { status: 404, data: {} } });
    expect(info.kind).toBe('not-found');
    expect(info.retryable).toBe(false);
  });
});

Component tests with React Testing Library

The pattern is arrange, act, assert: render the component, act like a user (click, type), and check what is on the screen.

import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { describe, expect, it, vi } from 'vitest';
import { EmployeeForm } from './EmployeeForm';

describe('EmployeeForm', () => {
  it('shows client errors and does not submit an empty form', async () => {
    const user = userEvent.setup();
    const onSubmit = vi.fn();                       // a spy function
    render(<EmployeeForm onSubmit={onSubmit} />);

    await user.click(screen.getByRole('button', { name: /save/i }));

    expect(screen.getByText('Name is required')).toBeInTheDocument();
    expect(onSubmit).not.toHaveBeenCalled();
  });

  it('submits the typed values', async () => {
    const user = userEvent.setup();
    const onSubmit = vi.fn().mockResolvedValue(undefined);
    render(<EmployeeForm onSubmit={onSubmit} />);

    await user.type(screen.getByLabelText('Name'), 'Asha Rao');
    await user.type(screen.getByLabelText('Email'), 'asha@acme.in');
    await user.type(screen.getByLabelText('Department'), 'IT');
    await user.type(screen.getByLabelText('Salary'), '50000');
    await user.click(screen.getByRole('button', { name: /save/i }));

    expect(onSubmit).toHaveBeenCalledWith({
      name: 'Asha Rao', email: 'asha@acme.in', department: 'IT', salary: 50000,
    });
  });
});

Which query to use: the priority order

RTL queries are ordered by how close they are to what a real user and assistive technology perceive. Use the first one that works. Choosing queries this way also pushes you to write accessible markup.

  1. getByRole('button', { name: /save/i }): the best default. Works for buttons, links, headings, textboxes, checkboxes.
  2. getByLabelText('Email'): form fields with a label.
  3. getByPlaceholderText, then getByText('Employee created'): visible text.
  4. getByDisplayValue, getByAltText, getByTitle.
  5. getByTestId('row-7'): the last resort, using a data-testid attribute that users cannot see.
Query familyNot foundUse it for
getBy…Throws an error at onceSomething that must be there now
queryBy…Returns nullAsserting that something is not there: expect(screen.queryByText('Error')).not.toBeInTheDocument()
findBy…Waits (default about one second), then throwsSomething that appears after an async step (API data)

Add All (getAllByRole) when several elements match. Always await userEvent calls; they are asynchronous.

Mocking the API with MSW

MSW (Mock Service Worker) intercepts HTTP requests at the network layer, so your real Axios code, interceptors and error handling run unchanged and only the server is fake. This is better than mocking Axios with vi.mock, which skips half of the code you want to test. In Node tests you use setupServer.

import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

export const handlers = [
  http.get('http://localhost:8080/api/employees', () =>
    HttpResponse.json({
      content: [{ id: 1, name: 'Asha Rao', email: 'asha@acme.in', department: 'IT', salary: 50000 }],
      page: 0, size: 10, totalElements: 1, totalPages: 1,
    }),
  ),
];

export const server = setupServer(...handlers);
import { afterAll, afterEach, beforeAll } from 'vitest';
import { server } from './server';

beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));  // fail on unexpected calls
afterEach(() => server.resetHandlers());                          // undo per-test overrides
afterAll(() => server.close());
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';
import { render, screen } from '@testing-library/react';
import { http, HttpResponse } from 'msw';
import { MemoryRouter } from 'react-router';
import { expect, it } from 'vitest';
import { server } from '../test/server';
import EmployeeListPage from './EmployeeListPage';

function renderPage() {
  const client = new QueryClient({ defaultOptions: { queries: { retry: false } } }); // no retries
  return render(
    <QueryClientProvider client={client}>
      <MemoryRouter>
        <EmployeeListPage />
      </MemoryRouter>
    </QueryClientProvider>,
  );   // components that call useAuth also need a test AuthProvider around them
}

it('shows employees from the API', async () => {
  renderPage();
  expect(await screen.findByText('Asha Rao')).toBeInTheDocument();   // waits for the data
});

it('shows a friendly message when the server fails', async () => {
  server.use(   // override the default handler for this test only
    http.get('http://localhost:8080/api/employees', () =>
      HttpResponse.json({ title: 'Internal Server Error' }, { status: 500 })),
  );
  renderPage();
  expect(await screen.findByRole('alert')).toHaveTextContent('Something went wrong on our side');
});

Notes: a fresh QueryClient per test avoids cached data leaking between tests; retry: false makes the error case fast; MemoryRouter provides routing without a browser URL.

Mocking modules with vi.mock

For things you do not want to run, use vi.mock('./employeeApi') to replace a module with mocks, and vi.fn() for spies. Use it for browser APIs, timers (vi.useFakeTimers()) and third-party modules, but prefer MSW for HTTP so that Axios, interceptors and error mapping are part of the test.

End-to-end tests with Playwright

Playwright drives a real browser (Chromium, Firefox, WebKit) through your running app, as a user would. It catches what component tests cannot: CORS problems, wrong routing after deploy, a broken login against the real backend. Because E2E tests are slow and can be flaky, write few of them, for the journeys that must never break: login, the main create flow, checkout.

import { expect, test } from '@playwright/test';

test('a logged-out visitor is sent to login, then sees the employee list', async ({ page }) => {
  await page.goto('http://localhost:5173/employees');
  await expect(page).toHaveURL(/\/login/);              // the route guard worked

  await page.getByLabel('Email').fill('admin@acme.in');
  await page.getByLabel('Password').fill(process.env.E2E_PASSWORD ?? '');
  await page.getByRole('button', { name: 'Login' }).click();

  await expect(page.getByRole('heading', { name: 'Employees' })).toBeVisible();
});

Create the project with npm init playwright@latest and run tests with npx playwright test. Playwright's locators (getByRole, getByLabel) follow the same ideas as RTL. Use a dedicated test user and test database, and keep the password in an environment variable, not in the file.

Rules for good frontend tests

  • Each test is independent: no shared state, any order, can run alone.
  • Find elements by role or label before text, and by test id last.
  • Wait with findBy or waitFor, never with setTimeout or fixed sleeps.
  • No real network in unit and component tests. MSW answers; unknown requests fail the test.
  • Tests run in CI on every push.

Common mistakes

  • Testing implementation details (calling an internal function, checking state values) so tests break on every refactor.
  • Forgetting await on user.click or findBy: the assertion runs too early, or you see "not wrapped in act(...)" warnings.
  • Using getBy for data that loads later (throws immediately). Use findBy.
  • Asserting absence with getBy (it throws). Use queryBy.
  • Large snapshot tests that everybody updates without reading.
  • Not wrapping a component in the providers it needs (QueryClient, Router, Auth): "No QueryClient set" errors.
  • Reusing one QueryClient across tests, so cached results leak.

Interview: "How do you test a React component that calls an API?"

  • Vitest + React Testing Library; render inside the needed providers with a fresh QueryClient with retries off.
  • Fake the network with MSW (not by mocking Axios), so interceptors and error handling run.
  • Interact with userEvent, find elements by role/label, assert with findBy for async results, and test loading, success, empty and error states.
  • Add a few Playwright E2E tests for the critical journeys; leave rules and security to backend tests.

Interview questions — TypeScript, Next.js, state and testing

Why use TypeScript instead of JavaScript?

Static types catch typos, wrong argument types and missing null checks before the code runs. They give accurate autocomplete, safe refactoring across a large codebase, and living documentation for data shapes such as API DTOs. The cost is a build step and some extra writing. Types are erased, so they add no run-time overhead and also give no run-time protection.

What is the difference between any and unknown?

Both accept any value. any turns off type checking for it, so you can call anything on it and errors are hidden. unknown forces you to narrow the type (typeof, instanceof, a type guard) before you use it. Use unknown for external data and catch variables.

interface or type?

For object shapes they are nearly interchangeable. type can also name unions, tuples and primitives; interface supports extends and declaration merging. A common convention: interface for object shapes and props, type for unions and combinations. Consistency inside the project matters more.

What does this print or fail on? const [rows, setRows] = useState([]); setRows(data);

It runs, but with strict TypeScript the state type is inferred as never[], so setRows(data) is a compile error ("not assignable to never[]"). Fix it by giving the type: useState<Employee[]>([]).

How do you type an API response, and why is it not a guarantee?

Write an interface that mirrors the backend DTO and pass it as a generic: api.get<Page<Employee>>('/employees'). The compiler then checks your usage. It is a promise, not a check: TypeScript types do not exist at run time, so if the server sends another shape, the code still compiles. Close the gap with types generated from the OpenAPI document, schema validation such as Zod at the boundary, and API tests.

What does "strict": true do?

It enables a group of strict checks: strictNullChecks (null and undefined are separate types), noImplicitAny, strictFunctionTypes, strictPropertyInitialization, useUnknownInCatchVariables and others. It catches the largest class of run-time errors ("cannot read property of undefined") at compile time. New projects should always start with it.

What is narrowing? Give two ways to do it.

Narrowing is the compiler refining a union type inside a branch after a check. Examples: typeof x === 'string', x instanceof Error, 'name' in x, an equality check against null, a discriminated-union switch (state.status), or a custom type guard function returning x is Employee.

How does TypeScript's type system differ from Java's?

TypeScript is structural: an object fits a type if it has the required properties, with no implements. Java is nominal. TypeScript types are erased and unavailable at run time; Java keeps class information for reflection. TypeScript has first-class unions and literal types, and heavy inference; null-safety comes from strictNullChecks.

Server-side rendering vs client-side rendering: what are the trade-offs?

With CSR (a Vite SPA) the browser downloads JavaScript, runs it and then fetches data, so the first content is late and crawlers or link previews may see an empty page. With SSR or static generation the server sends ready HTML, so content appears quickly and is indexable, then React hydrates it. SSR needs a server to run and adds the server/client boundary to think about. CSR is simpler and fine behind a login.

When would you choose Next.js over Vite and React Router with a Spring Boot backend?

Choose Next.js for public pages that need SEO, social previews and fast first load (catalogues, blogs, marketing), or when you want a backend-for-frontend layer that keeps tokens in httpOnly cookies. Choose a Vite SPA for internal dashboards and apps behind a login, for static hosting, and for the smallest number of moving parts. In both cases Spring Boot remains the API and owns the business rules.

What is the difference between a Server Component and a Client Component?

In the Next.js App Router, components are Server Components by default: they run on the server, can be async and read data directly, and send no component JavaScript to the browser. A file with 'use client' is a Client Component: it also runs in the browser and can use state, effects and event handlers. Keep the client part small and pass data down as props.

When do you need Redux or Zustand, given Context and TanStack Query exist?

Server data belongs to TanStack Query; URL state to the URL; local state to useState; stable app-wide values (user, theme) to Context. A store is for shared client state that is complex or changes often and is used by many distant components, such as a cart, a wizard or editor state. Context re-renders every consumer on any change, while stores let components select a slice. Redux Toolkit fits large teams and strict structure; Zustand fits small, simple global state.

How do you test a React component that fetches data?

Render it with Vitest and React Testing Library inside the required providers (a new QueryClient with retry off, a MemoryRouter). Fake the server with MSW so the real Axios code and interceptors run. Use await screen.findByText(...) for async results, userEvent for interaction, and test the loading, success, empty and error states. Override an MSW handler per test to simulate a 500.

Which RTL query should you reach for first, and what is the difference between getBy, queryBy and findBy?

getByRole first, then getByLabelText, then text, with getByTestId as the last resort. getBy throws immediately if nothing matches; queryBy returns null (use it to assert absence); findBy waits and retries until the element appears (use it for async UI).

What do you test with Playwright instead of component tests?

Whole journeys in a real browser against a running app and backend: login and redirect, creating a record, permissions. It finds integration problems such as CORS, routing and deployment settings. These tests are slower and more fragile, so keep them few and focused on critical paths.

Cheat sheet — TypeScript, Next.js, state and testing

  • TypeScript JavaScript plus static types; checked by tsc/editor, erased at build.
  • Vite + TS npm create vite@latest app -- --template react-ts; Vite strips types, tsc checks.
  • Basic types string, number, boolean, null, undefined, bigint, T[], [A, B].
  • Union / literal 'ADMIN' | 'USER', string | null; replaces most enums.
  • Discriminated union shared tag property (status) + switch for exact narrowing.
  • interface vs type objects: either; type for unions/tuples; interface merges and extends.
  • Optional / readonly phone?: string, readonly id: number (compile-time only).
  • Generics Page<T>, function f<T extends HasId>(x: T).
  • Narrowing typeof, instanceof, in, equality, type guards (x is T).
  • any / unknown / never unchecked / must narrow / impossible. Prefer unknown.
  • Utility types Partial, Pick, Omit, Record, Readonly, Required.
  • React typing props interface; ReactNode for children; useState<User | null>(null); ChangeEvent<HTMLInputElement>.
  • DTO mapping record → interface; LocalDate → string; enum → union; nullable → T | null.
  • Types are not checks validate with Zod or generate from OpenAPI.
  • tsconfig "strict": true always; noEmit; jsx: "react-jsx".
  • Structural typing shape decides compatibility; Java is nominal.
  • Next.js React framework: file routing, SSR/SSG/ISR, Server Components, route handlers, Server Actions.
  • Server vs Client Component default server; 'use client' for state/effects/events.
  • Choose Next.js for SEO and public pages; Vite SPA for logged-in dashboards.
  • Env vars (Next) only NEXT_PUBLIC_* reaches the browser.
  • State kinds local → useState; server → TanStack Query; URL → search params; shared → Context/Zustand/Redux.
  • Redux Toolkit createSlice + configureStore + Provider + useSelector/useDispatch; Immer inside.
  • Zustand create((set) => ({...})), no provider, select slices.
  • Vitest + RTL render, screen.getByRole, await userEvent, findBy for async.
  • Query order role → label → placeholder/text → display value → test id.
  • MSW http.get(url, () => HttpResponse.json(...)) + setupServer; fresh QueryClient, retry: false.
  • Playwright few E2E tests of critical journeys in a real browser.

Practice — TypeScript, Next.js, state and testing

  1. TypeScript warm-up (easy). In a scratch .ts file write: a union of string literals for roles, a discriminated union for a load state with an exhaustive switch, a generic Page<T> and a type guard isApiError. Done when the compiler flags a missing case after you add a new status.
  2. Type the DTOs (easy). Write TypeScript interfaces for every record your Spring Boot API returns, using Omit for request types. Done when api.get<Page<Employee>> autocompletes every field.
  3. Migrate Project 3's frontend to TypeScript (medium). Rename components to .tsx one at a time with strict on. Type props, state, events, context and the API module. Done when npm run build passes with no any except documented ones, and renaming a DTO field in one place shows errors everywhere it is used.
  4. Validate at the boundary (medium). Add a Zod schema for one response and parse it in the API function. Make the backend return a wrong field and watch the app fail with a clear error. Done when the type is derived with z.infer and you can explain why.
  5. Unit and component tests (medium). Set up Vitest, jsdom and React Testing Library. Test classifyError, then EmployeeForm (empty submit shows errors and does not call onSubmit; valid input calls it with the right values). Done when npm run test:run is green and all queries use role or label.
  6. Mock the API with MSW (medium). Test the list page for data, empty list, 500 and network error. Done when no test touches the real backend and unexpected requests fail the test.
  7. One E2E test (medium). Write a Playwright test for login and creating an employee against a local backend with a test user. Done when it passes headless and the password comes from an environment variable.
  8. A shared store (medium). Add a cart or notification feature with Zustand, then re-implement it with Redux Toolkit. Done when you can state which you would use for this app and why, and the cart badge re-renders only when its count changes.
  9. Next.js comparison (hard). Build a public, read-only "company directory" page in Next.js that renders the employee list on the server from your Spring Boot API, with a client-side search box. Done when "View page source" shows the names in the HTML, and you can write five lines on when you would not use Next.js.
  10. Plan your next quarter (easy). Choose ten job posts, list their required skills, and write a four-week plan from the "What to learn next" article. Done when each week has a concrete output (a deployed app, a pipeline, a test suite).

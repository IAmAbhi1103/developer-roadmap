Next.js: what it adds and when to choose it over a Vite SPA

Next.js is a React framework that adds file-based routing, rendering on the server (SSR, static generation, Server Components), API routes and a production server; choose it when SEO, first-load speed or a backend-for-frontend layer matter, and stay with a Vite SPA plus Spring Boot for logged-in dashboards and internal tools.

React is a library, Next.js is a framework

React alone draws components. It does not give you routing, a way to render on the server, a build setup or a deployment story; with Vite you add React Router and the rest yourself. Next.js (made by Vercel) is a framework built on React that includes those pieces and makes the choices for you. The React team itself recommends using a framework for new full-stack React apps.

The problem with a pure SPA

A Vite single-page app sends an almost empty index.html and a large JavaScript bundle. The browser downloads the JavaScript, runs React, calls your API, and only then shows content. This is client-side rendering (CSR). Consequences:

  • The first meaningful content appears late, especially on slow phones and networks.
  • Search engines and link previews (WhatsApp, LinkedIn) see an empty page unless they run JavaScript. Big search engines do run it, but less reliably and more slowly, and social-preview bots usually do not.
  • Every page waits for a second round trip (the API call after the JavaScript loads).

For an employee dashboard behind a login, none of this matters: nobody indexes it and users wait once. For a public product catalogue, a blog or a marketing site, it matters a lot.

Rendering modes

ModeWhere and when HTML is madeGood for
CSR (Vite SPA)In the browser, after JavaScript loadsDashboards, admin tools, apps behind login
SSR (server-side rendering)On the server for every requestPersonalised or frequently changing public pages
SSG (static generation)Once at build timeBlogs, docs, marketing pages
ISR (incremental static regeneration)Static pages that are re-generated in the background after a set timeProduct pages that change now and then

With SSR or SSG the browser receives ready-made HTML, so content shows quickly and crawlers see it. React then hydrates the page: it attaches event handlers to the existing HTML so it becomes interactive.

What Next.js gives you

File-based routing
Folders under app/ are URLs. app/employees/page.tsx is /employees. A folder named [id] is a dynamic segment.
Layouts
layout.tsx wraps all pages in a folder (navigation bar, footer) and is not re-created when you move between those pages. loading.tsx and error.tsx give loading and error screens by naming convention.
Server Components
In the App Router, components run on the server by default. They can be async, fetch data directly, and send no JavaScript for themselves to the browser.
Client Components
Files that start with 'use client' run in the browser too and can use state, effects and event handlers.
Route handlers
A route.ts file defines an HTTP endpoint (GET, POST…) inside the Next.js app, a small backend-for-frontend.
Server Actions
Functions marked to run on the server and called from forms or components.
Built-ins
next/link (client navigation with prefetching), next/image (image optimisation), font loading, metadata for SEO tags.

Next.js changes between major versions

Next.js moves fast. Details such as how fetch results are cached by default, whether route params are passed as a promise, and which file name is used for request interception ("middleware") differ between major versions. The ideas on this page (App Router, Server and Client Components, route handlers) are stable, but check the current documentation at nextjs.org/docs before copying code from an older tutorial. React 19 and the App Router are the basis of current versions.

Next.js with a Spring Boot backend

Next.js does not replace Spring Boot. It replaces the Vite-and-React-Router part. Your Java API still owns the business rules, database and security. Two common ways to connect them:

  • Browser calls Spring Boot directly (as in Module 6) from Client Components, with CORS and JWT handling as before. Server Components can also call Spring Boot during rendering.
  • Next.js as a backend-for-frontend (BFF). The browser talks only to Next.js; Next.js server code (route handlers, Server Components) calls Spring Boot. The access token can then live in an httpOnly cookie set by Next.js and never be visible to browser JavaScript, which removes the XSS token-theft risk discussed in the JWT article. The price is one more server to run.

Do not put the business logic in Next.js "API routes"

It is tempting to write database access and rules in route handlers because it is quick. If you have a Spring Boot service, keep rules and data access there. Next.js route handlers should be thin: forward, attach cookies, shape data for the UI. Two places with business logic drift apart.

Pros of Next.js

  • SEO and fast first load through server rendering and static pages.
  • Routing, layouts, image and font handling included.
  • Large ecosystem, many jobs; easy deployment on Vercel.

Cons

  • More concepts: server vs client boundary, caching rules, hydration errors.
  • You must run a Node.js server (or use a platform that does), unless you export static files.
  • Fast-changing APIs; older tutorials mislead.
  • For a pure internal SPA it is extra complexity with no payoff.

Basics you should know

  • npx create-next-app@latest creates a project (with TypeScript if you choose it). next dev runs the dev server, next build builds, next start runs the production server.
  • Environment variables: only names starting with NEXT_PUBLIC_ are sent to the browser; everything else stays on the server. The same warning as for VITE_: public means public. Compare with Vite env variables.
  • To deploy in Docker, Next.js can produce a smaller server bundle with the option output: 'standalone' in next.config (DevOps · Module 3).
  • A hydration error means the HTML rendered on the server differs from what React rendered in the browser (for example you print Date.now() or read localStorage during render). Move such code into an effect.

Common mistakes

  • Using useState or onClick in a Server Component. Add 'use client' to a small component, not to the whole page.
  • Marking a layout 'use client' and losing the benefits of server rendering for everything under it.
  • Reading browser-only things (window, localStorage) during server rendering.
  • Importing a server-only module (with secrets) into a Client Component.
  • Choosing Next.js because it is popular, for an app that needs none of its features.

Interview: "Would you use Next.js or a Vite SPA for this project?"

  • Ask whether the pages are public and need SEO or fast first paint. If yes: Next.js with SSR/SSG. If it is an authenticated dashboard: a Vite SPA is simpler and cheaper to host.
  • Explain the rendering modes (CSR, SSR, SSG, ISR) and the Server vs Client Component split.
  • Say that Spring Boot remains the API in both; Next.js may act as a BFF.

State management: Context, TanStack Query, Redux Toolkit and Zustand

Most "state" in a CRUD app is server data, which TanStack Query handles; keep UI state local, and reach for Redux Toolkit or Zustand only when many distant components share client-side state that changes often.

Five kinds of state

The first step in choosing a tool is to name the kind of state you have. Most confusion comes from putting everything in one global store.

KindExampleBest home
Local UI stateIs this dropdown open? Text in one inputuseState in the component
Form stateValues and errors while typinguseState or React Hook Form
URL stateCurrent page, filters, selected tabThe URL (useSearchParams)
Server stateEmployees from the API, with loading, caching, refetchingTanStack Query
Shared client stateShopping cart, theme, sidebar, multi-step wizard, notificationsContext for simple cases; Redux Toolkit or Zustand when it grows

If you use TanStack Query for server data and the URL for filters, the amount of leftover global state is small. Many apps never need Redux.

Why Context stops being enough

Context (Module 5) is built into React and perfect for values that change rarely: the logged-in user, the theme, the language. Its limit: when the value in a context changes, every component that calls useContext for it re-renders, even if it uses a part of the value that did not change. A context holding { items, total, coupon } re-renders the whole tree that reads it whenever the coupon changes. There is also no built-in way to select a slice, no dev tools and no middleware. That is where a state library helps.

Redux Toolkit

Redux keeps all shared state in one store. Components read it with a selector and change it by dispatching an action; a pure function called a reducer computes the next state. Redux Toolkit (RTK) is the official, modern way to write Redux: it removes the boilerplate, and its createSlice lets you write "mutating" code that it turns into immutable updates (using a library called Immer).

import { createSlice, type PayloadAction } from '@reduxjs/toolkit';

export interface CartItem { productId: number; name: string; price: number; qty: number }
interface CartState { items: CartItem[] }

const initialState: CartState = { items: [] };

const cartSlice = createSlice({
  name: 'cart',
  initialState,
  reducers: {
    added(state, action: PayloadAction<Omit<CartItem, 'qty'>>) {
      const existing = state.items.find((i) => i.productId === action.payload.productId);
      if (existing) existing.qty += 1;               // looks like mutation; Immer makes it safe
      else state.items.push({ ...action.payload, qty: 1 });
    },
    removed(state, action: PayloadAction<number>) {
      state.items = state.items.filter((i) => i.productId !== action.payload);
    },
    cleared(state) {
      state.items = [];
    },
  },
});

export const { added, removed, cleared } = cartSlice.actions;
export default cartSlice.reducer;
import { configureStore } from '@reduxjs/toolkit';
import { useDispatch, useSelector, type TypedUseSelectorHook } from 'react-redux';
import cartReducer from './cartSlice';

export const store = configureStore({
  reducer: { cart: cartReducer },        // add more slices here
});

export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;

// Typed hooks: use these instead of the plain ones
export const useAppDispatch = () => useDispatch<AppDispatch>();
export const useAppSelector: TypedUseSelectorHook<RootState> = useSelector;
// main.tsx: make the store available
import { Provider } from 'react-redux';
// <Provider store={store}><App /></Provider>

// CartBadge.tsx
function CartBadge() {
  const count = useAppSelector((s) => s.cart.items.reduce((n, i) => n + i.qty, 0));
  return <span>Cart ({count})</span>;          // re-renders only when the count changes
}

// ProductCard.tsx
function AddButton({ product }: { product: Product }) {
  const dispatch = useAppDispatch();
  return <button onClick={() => dispatch(added(product))}>Add to cart</button>;
}

RTK also ships RTK Query, a data-fetching and caching tool (like TanStack Query but integrated with the store). If a team is already on Redux, they often use RTK Query for server state. Redux DevTools lets you see every action and travel back in time, which is a real help in large apps.

Zustand

Zustand (German for "state") is a very small library. You create a store with create; the store is a hook. There is no provider, no actions, no reducers: you write state and the functions that change it side by side.

import { create } from 'zustand';

export interface CartItem { productId: number; name: string; price: number; qty: number }

interface CartState {
  items: CartItem[];
  add: (item: Omit<CartItem, 'qty'>) => void;
  remove: (productId: number) => void;
  clear: () => void;
}

export const useCartStore = create<CartState>()((set) => ({
  items: [],
  add: (item) =>
    set((state) => {
      const existing = state.items.find((i) => i.productId === item.productId);
      return existing
        ? { items: state.items.map((i) =>
            i.productId === item.productId ? { ...i, qty: i.qty + 1 } : i) }
        : { items: [...state.items, { ...item, qty: 1 }] };
    }),
  remove: (productId) =>
    set((state) => ({ items: state.items.filter((i) => i.productId !== productId) })),
  clear: () => set({ items: [] }),
}));
function CartBadge() {
  // Select only what you need: re-renders only when this value changes
  const count = useCartStore((s) => s.items.reduce((n, i) => n + i.qty, 0));
  return <span>Cart ({count})</span>;
}

function AddButton({ product }: { product: Product }) {
  const add = useCartStore((s) => s.add);
  return <button onClick={() => add(product)}>Add to cart</button>;
}

Zustand has optional middleware, for example persist (save the store to localStorage) and a Redux DevTools connector. As with any localStorage use, never persist tokens or secrets.

A sensible decision path

  1. Keep state as local as possible (useState); lift it only when siblings need it.
  2. Data from the API: TanStack Query. Do not copy it into a store.
  3. Filters, paging, selected tab: the URL.
  4. A few app-wide values that rarely change: Context.
  5. Complex client state used by many distant components, or frequent updates: Zustand (simple) or Redux Toolkit (large team, strict structure, great tooling).

Common mistakes

  • Copying API data into Redux or Zustand, then writing code to keep it in sync. Let TanStack Query own server data.
  • Putting everything in one global store "because we have Redux". Local state belongs in components.
  • Subscribing to the whole store (useStore() without a selector) so every change re-renders the component.
  • Returning a new object or array from a selector on every call, which causes needless re-renders. Select primitives, or select the stable reference and derive outside.
  • Mutating state outside createSlice in Redux (plain Redux requires immutability; only Immer inside slices allows "mutating" syntax). Also, non-serialisable values (Date, class instances, functions) in the store.

Interview: "When would you use Redux, and when not?"

  • Separate server state (TanStack Query / RTK Query) from client state. Most apps have little truly global client state.
  • Redux Toolkit when many components share complex state, you need predictable updates, time-travel debugging, middleware, or a strict structure for a big team.
  • Zustand when you want a small global store with almost no boilerplate. Context for stable values.
  • Explain the Redux flow: dispatch an action, the reducer returns new state, subscribers re-render. Mention that Redux Toolkit uses Immer so reducers can be written in a mutating style safely.

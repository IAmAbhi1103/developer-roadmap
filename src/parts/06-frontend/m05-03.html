useEffect: side effects and the dependency array

useEffect runs code after React has updated the screen, to synchronise your component with something outside React; the dependency array decides when it re-runs and the cleanup function undoes the previous run.

What an effect is for

Rendering must be pure, but real apps need to do things that are not pure: call an API, start a timer, subscribe to a WebSocket, change document.title, read the size of a DOM node. These are side effects. useEffect is the place for effects that happen because the component appeared or changed. Effects that happen because the user did something (clicked Save) belong in the event handler instead.

Think of an effect as: "after rendering, synchronise the outside world with the current props and state". It is not a lifecycle method like componentDidMount, even if it can imitate one.

import { useEffect } from 'react';

useEffect(() => {
  // setup: runs after the render is on screen
  return () => {
    // cleanup (optional): runs before the next setup and when the component unmounts
  };
}, [dep1, dep2]);   // dependency array

When does it run?

React renders your component, commits the changes to the DOM, lets the browser paint, and then runs effects. The dependency array controls re-runs:

Dependency arrayRunsTypical use
OmittedAfter every renderRare; almost always a mistake
[]Once after the first render (twice in dev StrictMode)Connect once, load initial data, add a global listener
[a, b]After the first render and whenever a or b changed (compared with Object.is)Fetch data for an id, re-subscribe to a room
 
function EmployeePage({ employee }) {
  useEffect(() => {
    document.title = `${employee.name} | HR Portal`;
  }, [employee.name]);                      // re-run only when the name changes

  return <h1>{employee.name}</h1>;
}

The dependency rule

Every reactive value the effect reads — props, state, and variables or functions declared inside the component — must be listed in the array. Do not lie to React to silence a warning. The react-hooks/exhaustive-deps ESLint rule (already in the Vite template) checks this. A missing dependency gives a stale closure: the effect keeps using old values from the render in which it was created (the closure idea from Module 4).

function Ticker() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count);            // always logs 0: closure from the first render
      setCount(count + 1);           // always sets 1
    }, 1000);
    return () => clearInterval(id);
  }, []);                            // count is missing

  return <p>{count}</p>;
}

Fix it by removing the dependency on count with a functional update (setCount(c => c + 1)), which makes the empty array correct, or by listing [count] (the interval is then recreated every second, which works but is wasteful).

Cleanup

The function you return is the cleanup. React calls it before running the effect again (with new values) and when the component unmounts. Use it for everything the effect started: timers, event listeners, subscriptions, WebSocket connections, in-flight requests.

function useWindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    function onResize() {
      setWidth(window.innerWidth);
    }
    window.addEventListener('resize', onResize);
    return () => window.removeEventListener('resize', onResize);   // no leak
  }, []);

  return width;
}

Order for a change of [roomId]: render with the new value → cleanup of the previous effect (with the old values) → setup with the new values. In StrictMode development, React adds one extra setup → cleanup → setup on mount. If that breaks your component, your cleanup is incomplete; fix the effect.

Objects and functions as dependencies

React compares dependencies by reference. An object, array or function created inside the component is a new one on every render, so an effect depending on it runs after every render — and if that effect sets state, you get an infinite loop.

function Bad({ userId }) {
  const [user, setUser] = useState(null);
  const options = { headers: { 'X-User': userId } };   // new object each render

  useEffect(() => {
    fetch('/api/me', options).then((r) => r.json()).then(setUser);
  }, [options]);     // changes every render -> fetch -> setUser -> render -> fetch ...
  return <p>{user?.name}</p>;
}

Fixes: depend on primitives (userId), move the object inside the effect, move constants outside the component, or memoise with useMemo / useCallback. The other classic infinite loop is an effect with no dependency array that sets state.

Rules for useEffect

  • List every reactive value the effect uses; never suppress the lint rule to "fix" a loop.
  • Return a cleanup for anything that needs one.
  • The effect function itself cannot be async (it would return a Promise instead of a cleanup function). Define an inner async function and call it.
  • Effects must be safe to run twice in development.
  • Do not use effects to respond to user actions; use event handlers.

Edge cases

  • Effects do not run during server rendering; they run only in the browser.
  • useLayoutEffect runs before the browser paints. Use it only to measure the DOM and adjust before the user sees a flicker; it blocks painting.
  • Refs and setters from useState/useReducer are stable and need not be listed (the linter knows), though listing them is harmless.
  • React 19.2 added useEffectEvent for reading the latest value inside an effect without making it a dependency (a chat room that logs the current theme but reconnects only when the room changes). It is new; many codebases do not use it yet.

Common mistakes

  • Empty array [] while the effect uses props or state (stale data, wrong request).
  • No array at all, plus setState in the effect: endless re-render loop.
  • Passing an async function directly to useEffect.
  • No cleanup for setInterval or addEventListener: duplicates pile up, and you see memory leaks and multiple handlers.
  • Putting state-changing logic in an effect that just reacts to another state change (see you might not need an effect).

Interview: "Explain useEffect and its dependency array"

  • It runs after render to synchronise with external systems; setup returns an optional cleanup.
  • No array: after every render. []: after mount only. [a]: when a changes.
  • Cleanup runs before the next effect and on unmount; use it for timers, listeners, subscriptions, aborting requests.
  • Missing dependencies cause stale closures; unstable object dependencies cause loops.
  • Runs twice on mount in StrictMode development to verify cleanup.

Fetching data with useEffect: loading, error and race conditions

A fetch in an effect needs three states (loading, error, data), a cleanup that aborts or ignores outdated responses, and a dependency array containing every input of the request.

The basic pattern

Fetching is the most common reason to write an effect. You need three pieces of state, because a request is not a single value: it starts, then ends with data or with an error. This uses the apiClient style from Module 4: check response.ok, because fetch only rejects on network failure, not on HTTP 404 or 500.

import { useEffect, useState } from 'react';

function EmployeeList() {
  const [employees, setEmployees] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    const controller = new AbortController();

    async function load() {
      try {
        setLoading(true);
        setError(null);
        const res = await fetch('http://localhost:8080/api/employees', {
          signal: controller.signal,
        });
        if (!res.ok) throw new Error(`Server returned ${res.status}`);
        setEmployees(await res.json());
      } catch (err) {
        if (err.name === 'AbortError') return;   // cleanup aborted it: not a real error
        setError(err);
      } finally {
        if (!controller.signal.aborted) setLoading(false);
      }
    }
    load();

    return () => controller.abort();   // cancel the request on unmount / re-run
  }, []);

  if (loading) return <p>Loading employees…</p>;
  if (error) return <p role="alert">Something went wrong: {error.message}</p>;
  if (employees.length === 0) return <p>No employees yet.</p>;

  return (
    <ul>
      {employees.map((e) => <li key={e.id}>{e.name}</li>)}
    </ul>
  );
}

The race condition

Suppose a page shows employee details for an id from the URL. The user clicks employee 1, then quickly employee 2. Two requests are in flight. Network responses can arrive in any order. If the response for 1 arrives after the response for 2, the screen shows employee 1's data under employee 2's URL. This is a race condition, and it happens in real apps on slow mobile networks.

The cleanup function solves it. When id changes, React runs the cleanup of the old effect before starting the new one. Two options:

  • AbortController cancels the old request, so its promise rejects with an AbortError and never reaches setState. This also saves bandwidth.
  • An ignore flag lets the request finish but throws its result away. Use it when the library does not support abort.
function EmployeeDetails({ id }) {
  const [employee, setEmployee] = useState(null);
  const [status, setStatus] = useState('loading');   // 'loading' | 'error' | 'success'

  useEffect(() => {
    let ignore = false;                 // belongs to THIS run of the effect
    setStatus('loading');

    fetch(`http://localhost:8080/api/employees/${id}`)
      .then((res) => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json();
      })
      .then((data) => {
        if (!ignore) {                  // only the latest effect run may set state
          setEmployee(data);
          setStatus('success');
        }
      })
      .catch(() => {
        if (!ignore) setStatus('error');
      });

    return () => {
      ignore = true;                    // this run is now outdated
    };
  }, [id]);                             // re-fetch when the id changes

  if (status === 'loading') return <p>Loading…</p>;
  if (status === 'error') return <p role="alert">Could not load employee {id}.</p>;
  return <h2>{employee.name}</h2>;
}

Why this also fixes StrictMode's double effect in development: the first run's cleanup marks it as ignored (or aborts it), so only the second request updates the state. You may still see two requests in the Network tab; that is expected.

A status state instead of three booleans

Several separate booleans (loading, error, success) can contradict each other. One status string, or one state object, makes impossible combinations impossible. The same thinking leads to useReducer (see hooks toolbox) and to TanStack Query, which gives you exactly this.

Fetching on user action vs on mount

Use an effect to load data a screen needs to show. For data loaded because the user clicked something (search, refresh, submit), call the API directly in the event handler — no effect. And to keep UI responsive while typing in a search box, combine the effect with a debounce hook so you do not call the API on every keystroke.

SituationWhere to fetch
Screen opens and needs a list or detailsEffect (or better, TanStack Query)
Route param or filter changesEffect with that value in the dependency array
User clicks Save, Delete, SearchEvent handler
Many components need the same data, with cachingTanStack Query

Rule: every fetching effect needs a cleanup

Abort the request or set an ignore flag in the cleanup. Without it, fast navigation shows wrong data, and responses arriving after unmount waste work. Always check response.ok and always handle the error branch; an unhandled rejection leaves the user on a spinner forever.

Common mistakes

  • Forgetting to reset loading to true when the id changes, so the old employee shows while the new one loads.
  • Setting loading to false only on success; on an error the spinner stays.
  • Using async directly: useEffect(async () => {…}).
  • Reading data.name before data arrives: "Cannot read properties of null". Render the loading branch first, or use optional chaining.
  • Treating AbortError as a real error and showing it to the user.

In real projects

Hand-written fetch effects are fine for learning and for one or two small screens. In real codebases they are repeated in dozens of components, and each copy handles loading, errors, caching and refetching slightly differently. Teams usually switch to TanStack Query or at least a custom useFetch hook. In Module 6 the same calls go through an Axios instance with the JWT attached.

Interview: "How do you fetch data in React and avoid race conditions?"

  • Fetch in useEffect with the request inputs as dependencies; keep loading, error and data state.
  • Check res.ok since fetch does not reject on HTTP errors.
  • Return a cleanup that calls controller.abort() or sets an ignore flag, so an older response cannot overwrite a newer one.
  • Mention StrictMode's double effect and that libraries like TanStack Query handle caching, deduplication and cancellation for you.

You might not need an effect

Most "state that follows other state" bugs come from effects used where a plain calculation during render or an event handler is the right tool.

Why this matters

Effects are an escape hatch for talking to things outside React. When you use one only to move data between your own state variables, you add an extra render, risk showing stale values for a frame, and write code that is harder to follow. The React docs have a whole page on this (react.dev, "You Might Not Need an Effect"). Learn these patterns.

What an effect really costs

Remember the order of work from useEffect: React renders your component, commits the result to the DOM, the browser paints, and only then your effect runs. If the effect calls setState, React must render and commit again. So an effect that copies state costs two renders for every change, and for one frame the screen shows the old, inconsistent value (a "flicker"). With a chain of effects, each setting state for the next, you pay one extra render per link and the logic becomes very hard to follow. In development, Strict Mode also runs every effect twice (set up, clean up, set up) to expose missing cleanup, so careless effects show bugs earlier.

An easy test: is there an outside system involved? A WebSocket, a timer, the DOM, a browser API, a network request: yes, an effect may be right. Only your own props and state: probably not.

1. Derived state: calculate it during render

Wrong: effect copies data into state

const [employees, setEmployees] = useState([]);
const [search, setSearch] = useState('');
const [visible, setVisible] = useState([]);

useEffect(() => {
  setVisible(
    employees.filter((e) => e.name.includes(search)),
  );
}, [employees, search]);   // extra render, extra state

Right: derive while rendering

const [employees, setEmployees] = useState([]);
const [search, setSearch] = useState('');

const visible = employees.filter((e) =>
  e.name.includes(search),
);

If the calculation is truly expensive, wrap it in useMemo, not an effect.

The same applies to anything you can compute: a full name from first and last name, a cart total from the items, an "is the form valid" flag from the field values. Store the minimum (the raw fields); compute the rest. Storing both creates two sources of truth that can disagree.

function Cart({ items }) {
  // items: [{ id, name, priceInPaise, qty }] from your API
  const totalInPaise = items.reduce((sum, i) => sum + i.priceInPaise * i.qty, 0);
  const itemCount = items.reduce((n, i) => n + i.qty, 0);

  return <p>{itemCount} items — ₹{(totalInPaise / 100).toFixed(2)}</p>;
}

2. Responding to user actions: use the event handler

If something should happen because the user clicked, do it in the click handler. An effect cannot tell why state changed; it only sees that it did.

// Wrong: effect watches "submitted" and then posts
useEffect(() => {
  if (submitted) postEmployee(form);
}, [submitted]);

// Right: do the work where the event happens
async function handleSubmit(e) {
  e.preventDefault();
  await postEmployee(form);
  showToast('Employee saved');
}

The effect version has a nasty extra problem: if form is in the dependency array, a later edit re-posts; if it is left out, the linter complains and you may post stale data. The handler has none of this, because it runs exactly once per click with the current values.

3. Resetting state when a prop changes: use a key

// Wrong: effect resets the form when the employee changes
useEffect(() => { setDraft(employee); }, [employee]);

// Right: a new key = a new component instance with fresh state
<EmployeeForm key={employee.id} employee={employee} />

With the effect, the form first renders with the old user's draft for one frame and then jumps to the new one. With the key, React throws the old instance away and mounts a new one, so the first render is already correct. See keys.

4. Notifying a parent: do it in the handler

Do not call onChange(value) from an effect after setting local state. Call both the local setter and the parent's callback in the same event handler, or lift the state up so there is a single source of truth (see Sharing state).

// Wrong: parent is told one render late, by an effect
function Toggle({ onChange }) {
  const [on, setOn] = useState(false);
  useEffect(() => { onChange(on); }, [on, onChange]);
  return <button onClick={() => setOn(!on)}>{on ? 'ON' : 'OFF'}</button>;
}

// Right: update both in the handler (or make the parent own the state)
function Toggle({ onChange }) {
  const [on, setOn] = useState(false);
  function handleClick() {
    const next = !on;
    setOn(next);
    onChange(next);
  }
  return <button onClick={handleClick}>{on ? 'ON' : 'OFF'}</button>;
}

5. Adjusting some state when a prop changes

Sometimes only part of the state should reset when a prop changes (for example, clear the selected row when the list is replaced). The first choice is still to calculate it: store the selected id and derive the selected row with list.find(...); if the id is no longer in the list, you get undefined and no reset is needed. If you truly must store something from the previous render, React allows calling the component's own setState during render behind a condition (if (prevList !== list) { setPrevList(list); setSelected(null); }). It re-renders immediately without painting the stale value. Use it rarely; derive or use a key first.

6. Chains of effects

Avoid effects whose only job is to set state that triggers another effect (country → state → city dropdowns). Compute what you can, and put the real logic in the event handler that started the chain (handleCountryChange sets country and clears state and city together). Each hop in a chain is an extra render and a place for the values to go out of sync.

When an effect IS right

  • Synchronising with an external system: browser APIs, timers, WebSockets, a non-React widget.
  • Fetching data that a screen needs because it is displayed (ideally through a library).
  • Sending an analytics event because a page was shown.
  • Subscribing to an external store. For this, React provides useSyncExternalStore, which is safer than writing the subscription by hand; libraries such as Redux and Zustand use it.

Mistake: an effect that updates its own dependency

useEffect(() => { setCount(count + 1); }, [count]); loops forever: the effect changes count, which re-runs the effect. Similar loops happen when the effect sets an object or array that is also in its dependencies, because a new object is never equal to the old one. If you find yourself adding // eslint-disable-line react-hooks/exhaustive-deps to stop a loop, the effect is probably unnecessary.

Rule: every effect needs a clear external reason and a cleanup if it subscribes

Before writing useEffect, you should be able to name the outside system it synchronises with. If it starts something (listener, timer, connection, request), return a cleanup function that stops it. Dependencies must list every reactive value the effect reads.

Convention: a code-review question

Whenever you see useEffect(() => { setSomething(...) }, [other]), ask: "can something be calculated during render instead?" Usually it can.

Edge cases

  • Data fetching on mount is a legitimate effect, but it has traps (race conditions, double calls in Strict Mode); see fetching data, or avoid the problem with TanStack Query.
  • Do not use an effect to run code "once when the app starts" if the code is not about the component; module-level code (outside the component) or main.jsx is the place.
  • Initialising state from a prop is fine (useState(props.initial)) but later prop changes are ignored; that is why the key pattern exists.

Interview: "When should you NOT use useEffect?"

  • For derived data, for reacting to user events, for resetting state, for chains of effects that set state to trigger other effects.
  • Effects are for syncing with external systems; each unnecessary effect adds a render and a place for bugs.
  • Give one concrete example: filtering a list by search text is a variable in render, not useEffect plus a second state.
  • Mention the alternatives by name: render-time calculation, useMemo, event handlers, key, and a data library for server state.

useRef, useMemo, useCallback, useReducer and the rules of hooks

useRef holds a value or DOM node without re-rendering, useMemo and useCallback cache a value or function between renders, useReducer organises complex state, and all hooks follow two strict rules.

useRef: a box that does not trigger renders

useRef(initial) returns an object { current: initial } that stays the same object for the whole life of the component. Changing ref.current does not cause a re-render. It has two uses.

1. Reaching a DOM element (focus an input, scroll to a row, measure size). Pass the ref to the element's ref prop; after the commit, ref.current is the DOM node.

import { useEffect, useRef } from 'react';

function SearchBox() {
  const inputRef = useRef(null);

  useEffect(() => {
    inputRef.current.focus();          // DOM node is available after mount
  }, []);

  return <input ref={inputRef} placeholder="Search employees" />;
}

2. Keeping a mutable value between renders that is not part of the UI: a timer id, the previous value of a prop, a "has this run already" flag, the latest callback.

function Stopwatch() {
  const [seconds, setSeconds] = useState(0);
  const timerId = useRef(null);

  function start() {
    if (timerId.current) return;       // already running
    timerId.current = setInterval(() => setSeconds((s) => s + 1), 1000);
  }
  function stop() {
    clearInterval(timerId.current);
    timerId.current = null;
  }
  useEffect(() => stop, []);           // cleanup on unmount

  return (
    <div>
      <p>{seconds}s</p>
      <button onClick={start}>Start</button>
      <button onClick={stop}>Stop</button>
    </div>
  );
}

Rule: do not read or write ref.current during render

Refs are an escape hatch. Read and write them in event handlers and effects. If a value should appear on screen, it is state, not a ref. In React 19, ref is a normal prop for function components; in 18 you needed forwardRef to pass a ref to a child.

useMemo and useCallback: caching between renders

useMemo(() => compute(a, b), [a, b]) remembers a calculated value and recalculates only when a dependency changes. useCallback(fn, [deps]) remembers a function (it is shorthand for useMemo(() => fn, [deps])). Because every render creates new objects and functions, these hooks give you stable references.

import { memo, useCallback, useMemo, useState } from 'react';

const EmployeeRow = memo(function EmployeeRow({ employee, onSelect }) {
  console.log('render row', employee.id);
  return <li onClick={() => onSelect(employee.id)}>{employee.name}</li>;
});

function EmployeeTable({ employees }) {
  const [query, setQuery] = useState('');
  const [selectedId, setSelectedId] = useState(null);

  const visible = useMemo(
    () => employees.filter((e) => e.name.toLowerCase().includes(query.toLowerCase())),
    [employees, query],
  );
  const handleSelect = useCallback((id) => setSelectedId(id), []);

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <p>Selected: {selectedId}</p>
      <ul>
        {visible.map((e) => (
          <EmployeeRow key={e.id} employee={e} onSelect={handleSelect} />
        ))}
      </ul>
    </>
  );
}

React.memo(Component) makes a component skip re-rendering when its props are shallow-equal to last time. It only helps if the props are stable: without useCallback, onSelect would be a new function each render and memo would never skip. The three tools work as a team: memo + useCallback + useMemo.

When are they worth it?

  • A calculation is genuinely expensive (sorting or filtering thousands of rows, heavy maths) — measure first with the React DevTools Profiler.
  • A value is a dependency of an effect or another hook and must stay stable.
  • A function or object is passed to a memo-wrapped child, or into Context value.

Otherwise skip them. They cost memory and make code harder to read, and re-rendering is cheap. Do not wrap everything "just in case". The React Compiler (a build plugin that has reached a stable release) can add this memoisation automatically, which is one more reason not to hand-optimise early. Check the React docs before adopting it in a project.

useReducer: state with many transitions

When state has several related fields and many ways to change, or the next state depends on complex rules, useReducer puts all transitions in one pure function: (state, action) => newState. You dispatch actions such as { type: 'added', item }. Java developers: it is a small state machine, and the same idea as Redux (Module 7).

function cartReducer(state, action) {
  switch (action.type) {
    case 'added': {
      const found = state.find((i) => i.id === action.item.id);
      if (found) {
        return state.map((i) => (i.id === found.id ? { ...i, qty: i.qty + 1 } : i));
      }
      return [...state, { ...action.item, qty: 1 }];
    }
    case 'removed':
      return state.filter((i) => i.id !== action.id);
    case 'cleared':
      return [];
    default:
      throw new Error(`Unknown action: ${action.type}`);
  }
}

function Cart() {
  const [cart, dispatch] = useReducer(cartReducer, []);
  return (
    <>
      <button onClick={() => dispatch({ type: 'added', item: { id: 1, name: 'Dosa' } })}>
        Add dosa
      </button>
      <button onClick={() => dispatch({ type: 'cleared' })}>Clear</button>
      <p>{cart.length} different items</p>
    </>
  );
}

The rules of hooks

Rule: two rules for every hook (anything named useSomething)

  1. Call hooks only at the top level. Not inside if, loops, nested functions, event handlers, or after an early return.
  2. Call hooks only from React function components or from other (custom) hooks, never from plain JavaScript functions.

Why? React does not know hook names. It remembers each component's hooks as an ordered list: "first useState, second useEffect…". On every render it expects the same calls in the same order. A conditional hook shifts the order and React hands back the wrong state. The ESLint plugin eslint-plugin-react-hooks catches both rules and is installed in the Vite template.

Wrong: hook after an early return

function Profile({ user }) {
  if (!user) return null;
  const [open, setOpen] = useState(false);   // skipped sometimes
  return <p>{user.name}</p>;
}

Right: hooks first, then conditions

function Profile({ user }) {
  const [open, setOpen] = useState(false);
  if (!user) return null;
  return <p>{user.name}</p>;
}

The error you see: "Rendered more hooks than during the previous render" or "React has detected a change in the order of Hooks".

Other hooks you will meet

  • useContext (see Context), useId (stable unique ids for labels), useTransition and useDeferredValue (keep typing responsive while a heavy list updates), useSyncExternalStore (for library authors), useImperativeHandle (rare).
  • React 19: use, useActionState, useOptimistic, useFormStatus. use is not bound by the "no conditions" rule in the same way as other hooks; read the docs before using it.

Common mistakes

  • Wrapping everything in useMemo/useCallback with no measurement.
  • Using useMemo to guarantee something runs once; it is a performance hint, React may recompute.
  • Putting values that should render in a ref (the UI never updates).
  • Wrong dependency arrays in useCallback giving stale values.

Interview: "useMemo vs useCallback? Why the rules of hooks?"

  • useMemo caches a computed value; useCallback caches a function reference. Both depend on a dependency array and only help when stability matters (memo children, effect dependencies) or the work is expensive.
  • useRef persists a mutable value without re-rendering and holds DOM nodes.
  • Hooks are stored by call order, so they must run unconditionally at the top level, in components or custom hooks.
  • useReducer centralises complex transitions in a pure reducer.

Operators, type coercion and truthy/falsy values

Always compare with ===; JavaScript silently converts types in ==, + and conditions, so know the six falsy values, use ?? for "missing" defaults, ?. for safe access, and convert input explicitly with Number().

Most operators look like Java's: + - * / %, ** (power), ++ --, && || !, ? :, and the compound forms like +=. The big difference is that JavaScript is happy to apply them to values of different types. It first converts ("coerces") the values and then continues, without any compile error. Type coercion means the automatic conversion of a value from one type to another. If you do not know the rules, you get bugs such as "5" + 3 giving "53". If you know the rules, you simply avoid the cases that confuse.

== vs ===

=== is strict equality: it returns true only when type and value are both the same, and it never converts anything. == is loose equality: if the types differ, it converts one or both sides first. In Java you never meet this, because the compiler stops you from comparing a String with an int. The rule for JavaScript is easy: use === and !== always. ESLint's eqeqeq rule enforces it.

Truthy and falsy

In an if, a while, a ?: or with !, JavaScript does not need a boolean. Java would reject if (name); JavaScript converts the value to a boolean. A value that becomes false is falsy; every other value is truthy. There are exactly these falsy values:

+ with strings, and other conversions

The + operator does two jobs: addition and string joining. If either side is a string, the other side is converted to a string and the result is joined text. All other arithmetic operators (- * / %) convert both sides to numbers.

console.log("5" + 3);        // "53"   — string wins with +
console.log("5" - 3);        // 2      — "-" always means numbers
console.log("5" * "2");      // 10
console.log(1 + 2 + "3");    // "33"   — (1 + 2) first, then + "3"
console.log("1" + 2 + 3);    // "123"
console.log(true + 1);       // 2
console.log(null + 1);       // 1      — null becomes 0
console.log(undefined + 1);  // NaN    — undefined becomes NaN
console.log([] + {});        // "[object Object]"
console.log("abc" * 2);      // NaN
console.log(+"42");          // 42     — unary plus converts to number
console.log(`${5}${3}`);     // "53"   — template literal, explicit about joining

Logical operators return values, not booleans

&& and || short-circuit as in Java, but they return one of their operands, not true/false. a || b gives a if a is truthy, otherwise b. a && b gives a if a is falsy, otherwise b. That is why you see name || "Guest" for defaults.

?? (nullish coalescing) vs ||

The || default has a bug: it replaces every falsy value, including valid ones like 0, "" and false. The nullish coalescing operator ?? replaces only null and undefined.

const settings = { quantity: 0, coupon: "", notify: false };

console.log(settings.quantity || 1);     // 1     — wrong, 0 was a real value
console.log(settings.quantity ?? 1);     // 0     — right
console.log(settings.coupon ?? "NONE");  // ""
console.log(settings.notify ?? true);    // false
console.log(settings.missing ?? "n/a");  // "n/a"

Optional chaining ?. and logical assignment

Reading a property of undefined throws TypeError: Cannot read properties of undefined (reading 'city') — the JavaScript NullPointerException. The optional chaining operator ?. stops and returns undefined if the thing before it is null or undefined. Java's Optional.map(...) chain becomes one line.

const user = { name: "Asha", address: null, orders: [{ id: 1 }] };

console.log(user.address?.city);        // undefined (no TypeError)
console.log(user.orders?.[0]?.id);      // 1       — ?.[ ] for index access
console.log(user.sendEmail?.());        // undefined — ?.( ) calls only if it exists
console.log(user.address?.city ?? "Unknown city"); // "Unknown city"

// Logical assignment (ES2021)
let theme;
theme ??= "light";   // assign only if null/undefined
let retries = 0;
retries ||= 3;       // assign if falsy -> 3
let ready = true;
ready &&= false;     // assign only if truthy -> false

Rule: ?. guards the missing value, not a missing variable

a?.b is safe when a exists but is null/undefined. If a was never declared, you still get ReferenceError. Do not sprinkle ?. everywhere: it can hide a real bug that should have failed loudly.

Other operators worth knowing

  • typeof, instanceof, in ("id" in order tests a property), delete obj.key, and the comma-free void (rare).
  • Comparison < > <= >=: two strings are compared alphabetically by code unit ("10" < "9" is true); if one side is a number, the other becomes a number.
  • Bitwise operators exist (& | ^ ~ << >> >>>) and convert to 32-bit integers; you rarely need them.
  • Increment/decrement work as in Java; i++ on a string gives a number or NaN.

Edge cases

  • a ?? b || c without brackets is a SyntaxError: you cannot mix ?? with && or || unless you add parentheses.
  • Number(null) is 0 but Number(undefined) is NaN; Number(" 12 ") is 12 (spaces trimmed); Number("1,000") is NaN.
  • parseInt(0.0000005) is 5, because the number is first turned into the string "5e-7". Use Math.trunc() for numbers, parseInt only for strings.
  • ["1","2","3"].map(parseInt) gives [1, NaN, NaN], because map passes the index as the radix. Write .map(Number) or .map(s => parseInt(s, 10)).

Common mistake: using || for defaults and forgetting form values are strings

Wrong: drops 0, joins strings

const qty = input.value || 1;   // "0" is truthy, 0 is not
const total = input.value + 10; // "3" + 10 = "310"

Right: convert, then default

const qty = Number(input.value) ?? 1;
const total = Number(input.value) + 10; // 13

Interview angle

  • "== vs ===": strict compares type and value; loose converts first. Always use strict; the exception is x == null.
  • "List the falsy values." false, 0, -0, 0n, "", null, undefined, NaN. Empty arrays and objects are truthy.
  • "What is [] + [], 1 + "2", "3" - 1?" "", "12", 2.
  • "?? vs ||?" || replaces all falsy values, ?? only null and undefined.

Functions: declarations, expressions, arrows, defaults and rest

A function in JavaScript is a value you can store, pass and return; you can write it as a declaration, an expression or an arrow function, give parameters defaults, gather extra arguments with rest, and build behaviour by passing functions to higher-order functions.

In Java, code lives in methods inside classes, and passing behaviour needs a functional interface plus a lambda. In JavaScript, a function is an ordinary value, just like a number or a string. This is called having first-class functions. It is the idea behind map, filter, event handlers, promises and React hooks, so it deserves your full attention.

Three ways to write a function

// 1. Function declaration
function addGst(price) {
  return price * 1.18;
}

// 2. Function expression — a function value stored in a variable
const addGst2 = function (price) {
  return price * 1.18;
};

// 3. Arrow function (ES2015)
const addGst3 = (price) => price * 1.18;          // one expression: implicit return
const total = (price, qty) => {                   // block body: write "return"
  return price * qty;
};
const getUser = () => ({ id: 7, name: "Asha" });   // wrap an object literal in ( )

console.log(addGst(100));   // 118
console.log(total(499, 3)); // 1497
console.log(getUser());     // { id: 7, name: 'Asha' }

Hoisting means a function declaration can be called above the line where it is written, but an arrow function stored in a const cannot: calling it early throws ReferenceError: Cannot access 'total' before initialization. See scope and hoisting. The differences in this are explained in this.

Parameters are loose

JavaScript does not check the number of arguments. Missing parameters become undefined, extra arguments are ignored (but available through rest or arguments). There is no overloading: the second declaration of a name replaces the first. Use default and rest parameters instead.

function greet(name, greeting = "Hello") {   // default parameter
  return `${greeting}, ${name}!`;
}
console.log(greet("Asha"));           // "Hello, Asha!"
console.log(greet("Asha", "Namaste")); // "Namaste, Asha!"
console.log(greet("Asha", undefined)); // "Hello, Asha!" — undefined triggers the default
console.log(greet("Asha", null));      // "null, Asha!"  — null does not

// Rest parameter: collects the remaining arguments into a real array
function sum(...numbers) {
  return numbers.reduce((acc, n) => acc + n, 0);
}
console.log(sum());           // 0
console.log(sum(10, 20, 30)); // 60

// Defaults can use earlier parameters and expressions
function createOrder(items, createdAt = new Date(), total = items.length * 100) {
  return { items, createdAt: createdAt.getFullYear(), total };
}
console.log(createOrder(["a", "b"])); // { items: [ 'a', 'b' ], createdAt: 2026, total: 200 }

A rest parameter (...numbers) must be last and is a real array, like Java's varargs int... numbers. The old arguments object (available in non-arrow functions) is array-like but has no map; prefer rest. To pass an array as separate arguments, use spread: Math.max(...prices) (see spread and rest).

A function with no return, or a bare return;, gives undefined. It returns one value only; to return several, return an object or array and destructure it.

Functions as values and higher-order functions

A callback is a function you pass to another function so that it is called later. A higher-order function is a function that takes functions as arguments or returns a function. map, filter, setTimeout and addEventListener are all higher-order functions.

const prices = [499, 1299, 250];

// A function that takes a function
function applyToAll(list, fn) {
  const result = [];
  for (const item of list) result.push(fn(item));
  return result;
}
console.log(applyToAll(prices, (p) => p * 0.9)); // [ 449.1, 1169.1, 225 ]

// A function that returns a function (a "function factory")
function discount(percent) {
  return (price) => price - (price * percent) / 100;
}
const diwali = discount(20);
console.log(diwali(1000)); // 800
console.log(typeof diwali); // "function"

// Functions have properties too
console.log(diwali.name, diwali.length); // "diwali" 1  (name, number of params)

Pass the function itself, not the result of calling it. setTimeout(sayHi, 1000) schedules a call; setTimeout(sayHi(), 1000) calls sayHi now and passes its return value (usually undefined). Brackets after the name mean "call now".

Pure functions and side effects

A pure function returns a result that depends only on its arguments and changes nothing outside itself (no changing a global, an argument, the DOM or the network). Pure functions are easy to test and to reason about, and React expects components to be pure. Prefer returning a new value over modifying the input.

// Impure: changes its argument
function addItemBad(cart, item) { cart.push(item); return cart; }

// Pure: returns a new array
const addItem = (cart, item) => [...cart, item];

const c1 = ["Rice"];
const c2 = addItem(c1, "Dal");
console.log(c1, c2); // [ 'Rice' ] [ 'Rice', 'Dal' ]

IIFE (briefly)

An IIFE (immediately invoked function expression) is a function that runs the moment it is defined: (function () { … })(); or (() => { … })();. It was the old way to make a private scope before modules and let existed. Today you meet it in old libraries and in one modern spot: an async IIFE, (async () => { await main(); })();, where top-level await is not available.

Other useful facts

  • Recursion works as in Java. Very deep recursion throws RangeError: Maximum call stack size exceeded (the JavaScript StackOverflowError).
  • Methods are just function-valued properties. The shorthand { total() { … } } is covered in objects.
  • Each function can have inner functions that remember the variables around them: a closure.
  • Naming: camelCase verbs for functions (calculateTotal), PascalCase for classes and React components.

Convention: when to use which form

  • Top-level, named, reusable functions: declaration (function formatPrice(p) {…}) or a const arrow — pick one style per project.
  • Callbacks and one-liners: arrow functions.
  • Object methods and class methods: method shorthand, not arrows (arrows have no own this).
  • Keep functions short and do one thing; limit parameters to three, then pass an options object: createUser({ name, role }).

Edge cases

  • Arrow function returning an object: () => { id: 1 } is a block with a label, so it returns undefined. Write () => ({ id: 1 }).
  • Default parameters are evaluated each call, so function f(list = []) gives a fresh array every time (unlike Python).
  • fn.length does not count parameters with defaults or rest.
  • Function declarations inside if blocks behave inconsistently in sloppy mode. Use a const arrow there.

Common mistake: calling instead of passing, and arrow methods

Wrong: calls the handler immediately

button.addEventListener("click", handleClick());
// handleClick runs now; its return value (undefined)
// is registered as the listener

Right: pass the function

button.addEventListener("click", handleClick);
button.addEventListener("click", () => handleClick(7));

Interview angle

  • "Declaration vs expression vs arrow?" Hoisting, own this and arguments, new-ability, and syntax.
  • "What is a higher-order function / callback?" Takes or returns a function; give map as an example.
  • "What are first-class functions?" Functions are values: assignable, passable, returnable.
  • "What is a pure function?" Same input, same output, no side effects.
  • "Does JavaScript support overloading?" No; the last definition wins. Use defaults, rest or an options object.

Scope, the scope chain and hoisting

Scope decides where a name is visible: global, function and block scopes are nested, a name is looked up from the inside outwards (the scope chain), and hoisting means declarations are registered before the code runs — var as undefined, functions fully, let/const in the temporal dead zone.

Scope is the region of code where a variable can be seen. Lexical scoping means the scope is decided by where you write the code, not by where you call it. You already know this from Java: a local variable is visible inside its block. JavaScript has the same idea with a few extra twists.

The three kinds of scope

  • Global scope — names declared at the top of a classic script (or on window). In an ES module the top level is the module scope, private to that file.
  • Function scope — parameters and everything declared inside a function. var belongs to this scope.
  • Block scope — a { } block, if, for, try. let, const and class belong to the block.

Scopes nest. When code uses a name, the engine looks in the current scope, then in the scope that contains it, and so on up to the global scope. This path is the scope chain. If the name is nowhere, you get ReferenceError: x is not defined. An inner variable with the same name shadows the outer one.

const platform = "web";             // module/global scope

function placeOrder() {
  const orderId = 1042;             // function scope
  if (orderId > 0) {
    const status = "PLACED";        // block scope
    console.log(platform, orderId, status); // found by walking up the chain
  }
  // console.log(status);           // ReferenceError — the block is gone
}

placeOrder(); // web 1042 PLACED

let x = "global";
function show() {
  let x = "local";                  // shadows the outer x
  console.log(x);
}
show();                // "local"
console.log(x);        // "global"

Lexical, not dynamic

A function sees the variables of the place where it was written, not the place where it is called. This is what makes closures work. Do not confuse it with this, which is decided at call time.

Hoisting

Hoisting is the behaviour that all declarations are processed before any code in the scope runs. It does not move your code; the engine simply knows the names in advance. What differs is the initial value:

Global scope and window

In a classic script, a top-level var or function declaration becomes a property of window; let and const do not. Assigning to an undeclared name in sloppy mode creates an accidental global. Too many globals cause name clashes between scripts, one more reason to use modules and "use strict".

var oldStyle = 1;
let newStyle = 2;
console.log(window.oldStyle); // 1
console.log(window.newStyle); // undefined

function leak() {
  leaked = "oops";   // no declaration: sloppy mode creates window.leaked
}
leak();
console.log(leaked); // "oops" (in strict mode: ReferenceError inside leak)

Scope compared with Java

  • Java has block scope for locals, and a local cannot shadow another local in the same method. JavaScript lets an inner block shadow an outer variable of the same name.
  • Java has no hoisting of locals: using a variable before its declaration is a compile error. JavaScript catches it only at runtime (or silently gives undefined for var).
  • Java has no free-standing functions; JavaScript functions can be nested and capture variables from the enclosing function. Java lambdas can do the same only for effectively final variables — JavaScript functions can also change the captured variable.

Rule: declare at the top of the scope, use const/let

Declare variables before using them, in the smallest scope that works. Turn on ESLint's no-undef, no-use-before-define and no-var rules so the editor warns you about hoisting traps.

Edge cases

  • If a function declaration and a var share a name, the function wins until the var assignment runs.
  • Function parameters and the function's body var variables share a scope; let with the same name as a parameter is a SyntaxError.
  • catch (e) creates a block scope for e.
  • A switch has one shared block: let x in two cases clashes. Wrap each case body in { }.

Interview angle

  • "What is hoisting?" Declarations are registered before execution; var is undefined, functions are usable, let/const/class sit in the TDZ.
  • "What is the scope chain / lexical scope?" Name lookup walks outward through enclosing scopes as written in the source.
  • "What does Puzzle 5 print and why?" undefined, because var city is hoisted inside the function.
  • "What is an accidental global?" Assigning to an undeclared name in sloppy mode; strict mode throws.

Closures

A closure is a function together with the variables of the scope where it was created — the function keeps access to those variables even after the outer function has finished, which gives you private state, factories, memoization and the classic loop bug.

Take this small example. The function makeCounter finishes running, so you would expect its local variable count to be gone. It is not.

function makeCounter() {
  let count = 0;                 // local to makeCounter
  return function () {           // inner function "closes over" count
    count++;
    return count;
  };
}

const counterA = makeCounter();
const counterB = makeCounter();   // a separate count

console.log(counterA()); // 1
console.log(counterA()); // 2
console.log(counterA()); // 3
console.log(counterB()); // 1  — its own private count
console.log(typeof count); // "undefined" — nobody outside can reach it

A closure is created every time a function is created. It consists of the function plus a hidden link to the lexical environment (the variables) where it was defined. The inner function does not copy count; it keeps a live reference to the variable itself. As long as the function can be reached, the variable stays in memory. Because every call to makeCounter() creates a new environment, counterA and counterB have separate counts.

Closure vs Java lambda

A Java lambda can capture only effectively final variables, so it can read a value but never change it. A JavaScript closure captures the variable itself and can update it. That is why the counter works in JavaScript, while in Java you would need an AtomicInteger or a one-element array.

Use 1: private state (encapsulation)

JavaScript objects have no private keyword outside classes (see classes for #private). Closures give you real privacy: nothing outside the function can touch the variable except through the functions you return.

function createWallet(initialPaise) {
  let balance = initialPaise;            // private

  return {
    deposit(amount) {
      if (amount <= 0) throw new Error("Amount must be positive");
      balance += amount;
    },
    withdraw(amount) {
      if (amount > balance) throw new Error("Insufficient balance");
      balance -= amount;
    },
    getBalance: () => balance,
  };
}

const wallet = createWallet(50_000);
wallet.deposit(10_000);
wallet.withdraw(5_000);
console.log(wallet.getBalance()); // 55000
console.log(wallet.balance);      // undefined — cannot be read or changed directly
wallet.withdraw(1_000_000);       // Error: Insufficient balance

Use 2: function factories

The discount(percent) example in functions is a closure: the returned function remembers percent. The same pattern gives you configured helpers such as makeLogger("orders") or createFormatter("en-IN").

Use 3: memoization (caching results)

Memoization stores the results of a slow pure function so that the same input is not computed twice. The cache lives in the closure.

function memoize(fn) {
  const cache = new Map();                 // private cache, one per memoized function
  return function (arg) {
    if (cache.has(arg)) {
      console.log("cache hit for", arg);
      return cache.get(arg);
    }
    const result = fn(arg);
    cache.set(arg, result);
    return result;
  };
}

const slowSquare = (n) => n * n;           // pretend this is expensive
const fastSquare = memoize(slowSquare);
console.log(fastSquare(12)); // 144
console.log(fastSquare(12)); // cache hit for 12, then 144

The same trick is behind useMemo and useCallback in React, and behind debouncing a search box (the timer id lives in a closure).

The classic loop bug: var vs let

A very common interview question. Three timers are created in a loop, each should print its own index.

for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log("var:", i), 0);
}
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log("let:", j), 0);
}
var: 3
var: 3
var: 3
let: 0
let: 1
let: 2

With var there is only one i for the whole function. The three callbacks all close over the same variable, and they run later, after the loop has ended and i is 3. With let, every iteration gets its own fresh j, so each callback closes over a different variable. The old fix was an IIFE that copied i into a parameter; today you simply use let.

Closures in React hooks

Every render of a React component is a new function call, and the event handlers inside it close over the state values of that render. A handler that logs count after a delay shows the value from the moment the handler was created: this is the "stale closure" problem. It is a closure rule, not a React bug. You will meet it in Module 5.

Memory and closures

A closure keeps its whole environment reachable as long as the function is reachable. A long-lived function (for example an event listener on window) that closes over a huge array keeps the array in memory. Remove listeners you no longer need and do not capture big objects without a reason.

Edge cases

  • Closures capture variables, not values. If the variable changes before the function runs, the function sees the new value.
  • Two closures made in the same call share the same variables (deposit and getBalance above see one balance).
  • Every function in JavaScript is a closure; it only becomes noticeable when it outlives its outer function.

Common mistake: a shared variable captured in a loop

Wrong: every button alerts 3

for (var i = 0; i < 3; i++) {
  buttons[i].onclick = () => alert(i);
}

Right: let makes one i per iteration

for (let i = 0; i < 3; i++) {
  buttons[i].onclick = () => alert(i);
}

Interview angle

  • "What is a closure?" A function plus its lexical environment; it remembers outer variables after the outer function returns. Give the counter example.
  • "Why does the var loop print 3 three times?" One shared i, callbacks run after the loop. let creates one per iteration.
  • "Where do you use closures?" Private state, factories, memoization, debounce, event handlers, React hooks.
  • "Can closures cause memory leaks?" Yes, when long-lived functions hold large objects. Release references and listeners.

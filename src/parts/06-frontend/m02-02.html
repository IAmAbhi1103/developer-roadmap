Forms: form, labels, inputs and buttons

A form collects user input and sends it as name=value pairs to a server; every control needs a name (so it is sent), a label (so people know what it is) and the right type (so the browser helps).

Forms are how users log in, register, search and check out, so they are the most important HTML you will write. The browser's built-in form support does a lot: keyboards, mobile keyboards, autofill, validation hints and submission. Your Spring Boot controller is the other half of the story: it receives what the form sends.

The form element

<form action="/register" method="post">
  <label for="fullName">Full name</label>
  <input type="text" id="fullName" name="fullName" autocomplete="name" required>

  <label for="email">Email</label>
  <input type="email" id="email" name="email" autocomplete="email" required>

  <button type="submit">Create account</button>
</form>
  • action: the URL that receives the data. Left out, the form posts to the current page.
  • method: get (the default) puts the data in the query string — right for searches and filters, so the URL can be shared. post sends it in the request body — right for anything that changes data or is private. (The HTML method attribute accepts only get and post; there is no HTML form that sends PUT or DELETE. Spring's hidden _method filter and JavaScript fetch() cover those.)
  • enctype: how the body is encoded. Default application/x-www-form-urlencoded; use multipart/form-data when the form has a file input.

When the user clicks submit, the browser collects every named control and sends name=value pairs. The form above produces this request:

POST /register HTTP/1.1
Host: localhost:8080
Content-Type: application/x-www-form-urlencoded

fullName=Asha+Rao&email=asha%40example.com

Spring MVC binds these to a controller method:

@Controller
public class RegisterController {

    // fullName and email come from the form's name attributes
    @PostMapping("/register")
    public String register(@RequestParam String fullName,
                           @RequestParam String email) {
        // validate again on the server, then save
        return "redirect:/welcome";
    }
}

The name attribute is what is sent

The name attribute becomes the key. A control without name is not submitted at all. id is a different thing: it links a label to a control and gives CSS and JavaScript a handle. Normally you set both, with the same text. In a React app that sends JSON, the names are less important but the field-to-DTO mapping logic is the same.

Labels

Every control needs a visible <label>. Connect it in one of two ways:

<!-- 1. for + id (the usual way) -->
<label for="city">City</label>
<input id="city" name="city" type="text">

<!-- 2. wrap the control -->
<label>
  City
  <input name="city" type="text">
</label>

A connected label gives the control its accessible name, so a screen reader says "City, edit text". It also makes the label clickable: clicking the text focuses the input, or ticks a checkbox — a big help for small touch targets. In React the attribute is written htmlFor, because for is a reserved word in JavaScript.

Mistake: placeholder as a label

placeholder is a hint inside the empty field (placeholder="e.g. 9876543210"). It disappears as soon as you type, often has low contrast, and is not a reliable accessible name. Always add a real label; use the placeholder only for an example format.

Input types

The type attribute picks the control. The right type brings a suitable mobile keyboard, built-in validation and sometimes a native picker, at zero cost.

Other controls

<label for="role">Role</label>
<select id="role" name="role" required>
  <option value="">Choose one</option>
  <option value="dev">Developer</option>
  <option value="qa">Tester</option>
  <option value="ops" selected>DevOps</option>
</select>

<label for="bio">About you</label>
<textarea id="bio" name="bio" rows="4" cols="40" maxlength="500"></textarea>

<label>
  <input type="checkbox" name="newsletter" value="yes">
  Send me the newsletter
</label>

<fieldset>
  <legend>Preferred contact method</legend>
  <label><input type="radio" name="contact" value="email" checked> Email</label>
  <label><input type="radio" name="contact" value="phone"> Phone</label>
</fieldset>
  • <select> sends the chosen option's value, not its visible text. If an option has no value, the text is sent. Use multiple for multi-select, <optgroup label> to group options.
  • <textarea> holds multi-line text. The initial text goes between the tags (it has no value attribute). Resize it with CSS.
  • Radio buttons share a name: that is what makes them mutually exclusive. Each radio needs a different value. Wrap related radios or checkboxes in <fieldset> with a <legend> naming the question; screen readers then announce "Preferred contact method, Email, radio button".
  • <datalist> gives suggestions to a text input: <input list="cities"><datalist id="cities"><option value="Pune">…</datalist>.
  • <output>, <progress> and <meter> display results and values.

Buttons

ButtonWhat it does
<button type="submit">Submits the form. This is the default type for a button inside a form.
<button type="button">Does nothing by itself; for JavaScript-driven actions
<button type="reset">Resets fields to their initial values (rarely wanted)

The classic bug: a button that submits the form by accident

A button inside a form without a type is a submit button. So a "Show password", "Add another phone number" or "Cancel" button reloads the page or posts incomplete data. Write type="button" on every button that is not meant to submit.

<!-- Wrong: submits the form when clicked -->
<button onclick="togglePassword()">Show</button>

<!-- Right -->
<button type="button" onclick="togglePassword()">Show</button>

Use <button> rather than <input type="submit">: a button can contain text, icons and markup, and it is easier to style. A disabled button (disabled) cannot be focused or clicked, and its value is not submitted. To tell the server which button was pressed, give it a name and value.

Useful attributes on controls

autocomplete
Helps the browser autofill: name, email, tel, street-address, postal-code, username, current-password, new-password, one-time-code. Autofill saves users time and works better with correct values; do not set autocomplete="off" on login fields.
autofocus
Focuses a field on load. Use rarely; it can disorient screen-reader users.
readonly vs disabled
readonly can be focused and is submitted but cannot be edited; disabled cannot be focused and is not submitted.
inputmode
Chooses the mobile keyboard: inputmode="numeric" gives digits without the number-input quirks (good for OTP and PIN codes).
form
Associates a control placed outside the <form> with it, by form id.

A realistic form: login-style signup

<form action="/api/signup" method="post" novalidate>
  <fieldset>
    <legend>Create your account</legend>

    <p>
      <label for="su-email">Email</label>
      <input id="su-email" name="email" type="email" autocomplete="email"
             required aria-describedby="su-email-hint">
      <small id="su-email-hint">We never share your email.</small>
    </p>

    <p>
      <label for="su-pw">Password (at least 8 characters)</label>
      <input id="su-pw" name="password" type="password" minlength="8"
             autocomplete="new-password" required>
    </p>

    <p>
      <label>
        <input type="checkbox" name="terms" required>
        I accept the terms and conditions
      </label>
    </p>

    <button type="submit">Sign up</button>
  </fieldset>
</form>

aria-describedby links the hint text to the field, so a screen reader reads the hint after the label. (novalidate here switches off the browser's built-in checks so that your own JavaScript can show custom messages; leave it out if you want the defaults — see Form validation.)

Rules

  • Every control has a visible label connected with for/id or by wrapping.
  • Every control you want sent has a name.
  • Radio buttons in a group share a name; group them with fieldset and legend.
  • Any button inside a form that is not meant to submit has type="button".
  • A file upload form needs method="post" and enctype="multipart/form-data".

Conventions

  • One field per row and labels above fields (easier on mobile); mark required fields clearly in the label text, not by colour alone.
  • Choose input types for the data: email, tel, date; set autocomplete values.
  • Use method="get" for search forms, post for everything else; never put passwords in a GET query string.

Edge cases

  • An unticked checkbox is absent from the request, not sent as false. Spring binds a missing boolean parameter to false only if you declare @RequestParam(defaultValue = "false"); otherwise a missing required parameter gives MissingServletRequestParameterException (400).
  • Number inputs return strings. An empty number field is sent as an empty string, which binding turns into a conversion error for int (MethodArgumentTypeMismatchException), so use Integer with required = false when a field is optional.
  • Pressing Enter in a text field submits the form via its first submit button. A form with no submit button but one text field also submits.
  • Nested forms are not allowed.

In real projects

In React you rarely use the browser's default submit. You keep the field values in state, call event.preventDefault(), and send JSON with fetch() (Module 5 and Module 6). All the HTML rules above still apply — labels, types, autocomplete, button types — because React renders the same elements.

Interview angle

  • "GET vs POST in a form?" — query string vs body; GET for idempotent searches, POST for changes and secrets.
  • "Why does a button inside a form submit it?" — default type is submit.
  • "Which attribute decides the key sent to the server?" — name, not id.
  • "How do you group radio buttons?" — same name, fieldset/legend for accessibility.

Form validation: attributes, the constraint API and the server

HTML validation attributes (required, min, max, minlength, maxlength, pattern, type) give instant feedback in the browser, but they are only for user experience — the server must validate every request again.

Validation checks whether input is acceptable before it is processed. Browsers can do much of it declaratively, with no JavaScript. When the user submits, the browser checks every control; if one fails, it blocks the submission, focuses the first invalid field and shows a message.

<label for="mobile">Mobile number</label>
<input id="mobile" name="mobile" type="tel" inputmode="numeric"
       pattern="[6-9][0-9]{9}" maxlength="10" required
       title="10 digits, starting with 6, 7, 8 or 9">

<label for="age">Age</label>
<input id="age" name="age" type="number" min="18" max="60" required>

<label for="pin">PIN code</label>
<input id="pin" name="pin" type="text" inputmode="numeric" pattern="[0-9]{6}"
       required>

The pattern is anchored automatically (as if wrapped in ^(?:…)$), unlike Java's find(); it is similar to String.matches(). The title attribute text is appended to the browser's error message to explain the format. Keep patterns simple: strict email or phone regexes reject real people.

CSS hooks: :valid, :invalid and :user-invalid

input:user-invalid {
  border-color: #b00020;     /* only after the user has interacted */
}
input:user-valid {
  border-color: #1b7f3b;
}

:invalid matches an empty required field the moment the page loads, so the form looks full of errors before the user types anything. :user-invalid and :user-valid apply only after interaction, and are supported in current browsers; for older ones, add the :focus or a class from JavaScript. Never signal an error by colour alone — add text.

The constraint validation API (brief)

JavaScript can read and customise the browser's validation. Every control has validity (an object of flags), validationMessage, checkValidity() and setCustomValidity().

const form = document.querySelector("#signup");
const email = document.querySelector("#su-email");

email.addEventListener("input", () => {
  if (email.validity.typeMismatch) {
    email.setCustomValidity("Please enter a valid email, like asha@example.com");
  } else {
    email.setCustomValidity("");   // empty string = valid again
  }
});

form.addEventListener("submit", (event) => {
  if (!form.checkValidity()) {
    event.preventDefault();        // stop the submit
    form.reportValidity();         // show the browser's error bubbles
  }
});

Useful validity flags: valueMissing (required), typeMismatch (email/url), patternMismatch, tooShort, tooLong, rangeUnderflow, rangeOverflow, stepMismatch and valid. A form with novalidate skips the automatic check but you can still call these functions. Forgetting to clear a custom message with setCustomValidity("") leaves the field permanently invalid — a very common bug.

Client-side validation is not security

Everything in the browser can be bypassed. A user can delete the required attribute in DevTools, disable JavaScript, or skip the browser entirely and send the request with curl or Postman. So:

  • Client-side validation exists for user experience: quick, friendly feedback without a network round trip.
  • Server-side validation exists for correctness and security: it is the only validation you can trust. The server must re-check everything — required fields, lengths, formats, ranges, business rules (is this email already registered? is the stock available?) — and never assume the browser did it.

In Spring Boot you do this with Bean Validation annotations and @Valid (covered in Spring Boot · Module 2). Keep the same rules on both sides so the user does not get surprised.

import jakarta.validation.constraints.*;

public record SignupRequest(
        @NotBlank @Email String email,
        @NotBlank @Size(min = 8, max = 72) String password,
        @AssertTrue(message = "You must accept the terms") boolean terms) {
}

// In the controller:  public ResponseEntity<?> signup(@Valid @RequestBody SignupRequest req)
// A failed rule returns 400 Bad Request with details of the field errors.

Also show the server's errors on the page. When the API returns 400 with field errors, your front-end code should display each message next to the matching field (Module 6).

Showing helpful errors

  • Say what is wrong and how to fix it: "Password must be at least 8 characters", not "Invalid input".
  • Put the message next to the field and connect it with aria-describedby; set aria-invalid="true" on the bad field.
  • Do not clear what the user typed. Do not validate on every keystroke before the user finishes; validate on blur or submit.

Rule: the server is the only validator you can trust

Treat all input as hostile: validate type, length, range and format on the server, encode output, and use parameterised queries. HTML attributes are conveniences.

Edge cases

  • type="number" accepts e (as in 1e5) and allows a minus sign; minlength/pattern do not apply to it. For a PIN, use text with inputmode="numeric" and pattern.
  • minlength and required are checked only when the user edits the value — a pre-filled value shorter than minlength passes until edited.
  • disabled controls are never validated; readonly ones are skipped for the "required" check too.
  • The look and wording of the browser's error bubble differs between browsers and cannot be fully styled; custom designs use novalidate with JavaScript.

Mistake: "the form already checks it, so the API does not need to"

This is how invalid or malicious data reaches the database. Add @Valid and constraints on every request body and parameter, even for forms that look strict.

Interview angle

  • "Client-side vs server-side validation?" — UX versus security; do both; server is mandatory.
  • "Name HTML5 validation attributes." — required, min, max, minlength, maxlength, pattern, type.
  • "How can the client-side check be bypassed?" — DevTools, curl/Postman, disabled JavaScript.

Tables for tabular data

Use table, thead, tbody, tfoot, caption and th with scope for data that has rows and columns — never for page layout.

A table presents data that has a natural grid: an invoice, a marks sheet, a train timetable, an employee list. If you would put it in a spreadsheet, it is a table. If you only want things side by side, it is not — use CSS Flexbox or Grid.

Structure

<table>
  <caption>Employees by department, October 2026</caption>
  <thead>
    <tr>
      <th scope="col">Name</th>
      <th scope="col">Department</th>
      <th scope="col">Salary (₹)</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">Asha Rao</th>
      <td>Engineering</td>
      <td>1,200,000</td>
    </tr>
    <tr>
      <th scope="row">Ravi Kumar</th>
      <td>Finance</td>
      <td>950,000</td>
    </tr>
  </tbody>
  <tfoot>
    <tr>
      <th scope="row" colspan="2">Total</th>
      <td>2,150,000</td>
    </tr>
  </tfoot>
</table>
ElementJob
<table>The whole table
<caption>The table's title; first child; announced by screen readers
<thead>, <tbody>, <tfoot>Header rows, body rows, summary rows. They let you style sections and keep headers when printing
<tr>A row
<th>A header cell (bold and centred by default)
<td>A data cell

The browser adds a <tbody> automatically if you leave it out. In your Java code you often generate such tables from a list: Thymeleaf's th:each, or in React orders.map(o => <tr key={o.id}>…</tr>).

Accessibility: th and scope

A screen reader announces a cell together with its headers ("Salary, 1,200,000"), and it needs to know which headers apply. Use <th> for every header cell and add scope="col" (this header applies to the column below) or scope="row" (applies to the row). For complex tables with several header levels, headers and id link cells to headers explicitly. Always give the table a <caption> that says what it shows.

Merging cells: colspan and rowspan

<tr>
  <th colspan="2">Name (first and last)</th>   <!-- spans 2 columns -->
  <th rowspan="2">Marks</th>                  <!-- spans 2 rows -->
</tr>

colspan="n" stretches a cell across n columns; rowspan="n" across n rows. Cells that are covered must not be written again, or the grid shifts. Merged cells make tables harder for assistive technology, so use them only when they truly help.

Styling and responsive tables

Browsers draw tables with small gaps and no lines. CSS adds the polish:

table {
  border-collapse: collapse;       /* one line between cells, not double */
  width: 100%;
}
th, td {
  padding: 0.6rem 0.8rem;
  border-bottom: 1px solid #ddd;
  text-align: left;
}
td.number { text-align: right; }   /* align numbers to the right */
tbody tr:nth-child(even) { background: #f6f6f6; }   /* zebra stripes */

.table-scroll { overflow-x: auto; }  /* wrapper: scroll sideways on a phone */

Wide tables overflow small screens. The usual fix is a wrapper element with overflow-x: auto (as in the book you are reading right now, where tables become cards on phones). Do not shrink the font to unreadable sizes.

Rule: tables are for data, never for layout

Layout tables (a 1990s trick) break on small screens, confuse screen readers and mix structure with presentation. Use Flexbox or Grid (Flexbox, Grid).

Conventions

  • Always: caption, thead with th scope="col", tbody.
  • Right-align numbers (and use consistent decimals); left-align text.
  • Keep tables simple: a long table with sorting, paging and filtering is built with JavaScript (or a library) on top of this markup.

Edge cases

  • Text directly inside a <table> or <tr> is moved out by the browser (to above the table). Only tr, th, td and the section elements belong there. In React, whitespace or a stray string inside <tbody> gives a "validateDOMNesting" warning.
  • A row with fewer cells than the others does not fail; it leaves a blank area.
  • An empty list should show a message row such as "No orders yet", with <td colspan="3">, not an empty table.

Mistake: using td for headers, or tables to place a form and a picture side by side

A bold <td> is not a header; use <th> so assistive tools can relate the cells. Side-by-side layout belongs to CSS.

Interview angle

  • "When should you use a table?" — only for tabular data; layout with CSS.
  • "What do th scope, caption, colspan do?" — accessibility association, the title, and merging columns.

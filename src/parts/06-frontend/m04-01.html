JavaScript is the programming language of the browser. Every button that reacts, every form that checks your input before sending it, every list that updates without a page reload — that is JavaScript. React (Module 5) is a JavaScript library, and when your React app calls your Spring Boot API (Module 6) it does so with the JavaScript you learn here. This is the core module of the frontend page, so take your time with it.

As a Java developer you will find the syntax familiar: curly braces, if, for, class, try/catch. That familiarity is the trap. Under the same-looking syntax, JavaScript works very differently: values have types but variables do not, there is only one number type, functions are values, this changes with how you call a function, and all your code runs on one thread with an event loop. Every article in this module points out where JavaScript differs from Java.

  • Explain how JavaScript differs from Java and avoid the classic traps (==, coercion, this, floating-point numbers).
  • Write modern JavaScript: const/let, arrow functions, destructuring, spread, template literals and modules.
  • Transform data with map, filter, reduce and find instead of hand-written loops.
  • Build small apps with the DOM and events, without any framework.
  • Understand scope, closures, this, prototypes and the event loop well enough to answer "what does this print?" questions.
  • Call a REST API with fetch, handle every kind of error and send a JWT.
  • Use ES modules, npm and local storage the way real projects do.

Where JavaScript runs and how to add it to a page

JavaScript runs inside a JavaScript engine — built into every browser and into Node.js on servers; on a web page you load it with a <script> tag, normally with defer or type="module", and you watch it work in the browser console.

The language, the engine and the host

People use the word "JavaScript" for three different things. Keep them apart and many confusing errors start to make sense.

ECMAScript
The official language specification (ECMA-262), maintained by a committee called TC39. A new edition is published every year. ES2015 (also called ES6) was the big modern update — let, const, arrow functions, classes, modules, promises. Later editions are named by year (ES2016, ES2017 … ES2025 …). "Modern JavaScript" means ES2015 and later.
Engine
The program that executes JavaScript: V8 (Chrome, Edge, Node.js), SpiderMonkey (Firefox) and JavaScriptCore (Safari). An engine parses your source code, turns it into bytecode, interprets it, and compiles frequently used ("hot") functions to machine code with a JIT (just-in-time) compiler — the same idea as the JVM's HotSpot JIT.
Host environment
The program that embeds the engine and adds its own APIs. The browser adds the DOM (document), fetch, setTimeout, localStorage and many more. Node.js adds files, HTTP servers and process, but has no DOM.

This split explains real errors. document.querySelector() is not part of the JavaScript language; it is a browser API. Run it in Node.js and you get ReferenceError: document is not defined. In the same way, Node's require("fs") fails in a browser with ReferenceError: require is not defined. The language is the same; the host decides which extra objects exist.

One more fact clears up a common confusion: JavaScript has nothing to do with Java. It was created at Netscape in 1995, and the name was a marketing decision made while Java was popular. The two languages share C-style syntax and nothing else.

Is JavaScript compiled or interpreted?

Both, inside the engine. You never run a separate compile step like javac: the browser downloads your source code and the engine parses, interprets and JIT-compiles it on the spot. A syntax error is therefore found only when the file is loaded, and it stops that whole file from running. In real projects, tools such as Vite and TypeScript transform your code before it ships (bundling, minifying, removing types), but what the browser finally receives is still plain JavaScript source.

Adding JavaScript to a page

You attach JavaScript to an HTML page with the <script> element. You can write code inside the tag (an inline script) or point to a file with src (an external script). External files are the professional choice: the browser can cache them, and your HTML stays clean.

<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Order status</title>
  <!-- downloads in parallel, runs after the HTML is parsed -->
  <script src="app.js" defer></script>
</head>
<body>
  <h1 id="status">Loading…</h1>
</body>
</html>
const heading = document.getElementById("status");
heading.textContent = "Order #1042 is out for delivery";
console.log("app.js ran after the HTML was parsed");

The attribute on the <script> tag decides when the code runs. This is one of the most common interview questions on the frontend.

Strict mode

Strict mode is a safer variant of JavaScript that turns several silent mistakes into real errors. You switch it on with the string "use strict"; as the very first statement of a script or a function. ES modules and class bodies are always strict, so in a Vite or React project you are in strict mode without writing anything.

"use strict";

function applyCoupon() {
  totl = 450; // typo for "total"
}
applyCoupon(); // ReferenceError: totl is not defined
// Without strict mode the typo silently creates a global variable "totl".

What strict mode changes:

  • Assigning to an undeclared variable throws ReferenceError instead of creating a global variable.
  • In a plain function call, this is undefined instead of the global object (window). See this.
  • Writing to a read-only property (a frozen object, a getter-only property) throws TypeError instead of failing silently.
  • Duplicate parameter names, the with statement and old octal literals like 010 become a SyntaxError.

The console: your first tool

Every browser has DevTools. In Chrome or Edge on Windows press F12 or Ctrl+Shift+J (on a Mac, Cmd+Option+J) to open the Console tab. The console does three jobs: it shows the output of console.log() (the JavaScript version of System.out.println), it shows errors in red with a link to the file and line, and it is a REPL — type any expression and press Enter to see the result. In Chrome, $0 in the console means "the element I selected in the Elements panel", which is handy for quick experiments.

Node.js gives you the same REPL in a terminal, and runs files with node:

Rule: a script can only touch elements that already exist

A plain <script> in the <head> runs before the browser has parsed the <body>, so getElementById returns null. Use defer or type="module" (or put the script at the end of <body>, the old approach).

Wrong: runs before the body exists

<head>
  <script src="app.js"></script>
</head>
<!-- TypeError: Cannot set properties of null
     (setting 'textContent') -->

Right: waits until parsing is done

<head>
  <script src="app.js" defer></script>
</head>
<!-- app.js runs after the whole
     document is parsed -->

Edge cases

  • defer and async only work on external scripts (with src). On an inline classic script they are ignored. Inline module scripts are deferred anyway.
  • Module scripts are fetched with CORS rules. If you open the HTML file by double-clicking it (a file:// URL), Chrome blocks the module with an error like "Access to script at 'file:///…/main.js' from origin 'null' has been blocked by CORS policy". Serve the folder with a local web server instead — the VS Code Live Server extension, npx serve ., or Vite.
  • Two async scripts can run in any order. Never use async for a script that depends on another script.

In real projects

In a React + Vite project you almost never write script tags yourself. The generated index.html contains one line — <script type="module" src="/src/main.jsx"></script> — and everything else is imported from that entry file. Vite then bundles the modules for production (see Node.js and npm).

Interview angle

  • "defer vs async?" Both download in parallel. defer runs after parsing, in document order; async runs as soon as the file arrives, in any order.
  • "Is JavaScript interpreted or compiled?" Engines like V8 interpret bytecode and JIT-compile hot code to machine code — no separate compile step.
  • "What is strict mode?" An opt-in safer mode (automatic in modules and classes): no accidental globals, this is undefined in plain calls, silent failures become errors.
  • "Can JavaScript run outside the browser?" Yes — Node.js runs it on servers and in build tools, but it has no DOM.

What stays the same

Plenty works exactly as you expect: if/else, for, while, do…while, break, continue, the ternary operator, ++ and +=, try/catch/finally, Math.max(), Math.floor(), Math.random(). Strings are immutable, objects live on a heap and are reached through references, and a garbage collector frees memory for you. switch works like Java's classic switch (with fall-through when you forget break), but it compares with ===, and there are no arrow-style case -> switch expressions.

Edge case: automatic semicolon insertion (ASI)

JavaScript inserts missing semicolons at line ends. Usually that is harmless, but a line break straight after return ends the statement:

function getUser() {
  return          // ASI inserts ";" here
  {
    name: "Asha"
  };
}
console.log(getUser()); // undefined

Always start the returned value on the same line as return: return {.

Common mistake: comparing arrays or objects with ===

Java developers expect value comparison, but === on objects compares references, and you cannot override it with an equals() method.

Wrong: compares references

const a = [1, 2, 3];
const b = [1, 2, 3];
console.log(a === b); // false
console.log(a == b);  // false

Right: compares the contents

const same = a.length === b.length &&
  a.every((x, i) => x === b[i]);
console.log(same); // true

Where TypeScript fits

TypeScript is JavaScript plus static types. You write .ts/.tsx files, the compiler checks types and removes them, and the browser runs the resulting JavaScript. Many React teams use it and it will feel closer to Java. Learn JavaScript first: TypeScript does not change how JavaScript runs — coercion, this and the event loop behave exactly as described in this module.

Interview angle: "How is JavaScript different from Java?"

  • Dynamically typed (variables have no fixed type) vs statically typed.
  • Prototype-based objects (classes are syntax on top) vs class-based.
  • Functions are first-class values; closures are everywhere.
  • Single-threaded with an event loop and non-blocking I/O vs multi-threaded.
  • One floating-point number type; null and undefined; type coercion with ==.
  • Runs in browsers (and Node.js), interpreted and JIT-compiled from source.

Values and types: primitives, objects and typeof

JavaScript has seven primitive types — string, number, bigint, boolean, undefined, null, symbol — and everything else is an object; variables have no type, only values do, and typeof tells you a value's type (with a few famous surprises).

A primitive is a simple, immutable value that is copied when you assign it. An object is a collection of properties that lives on the heap and is reached through a reference. Arrays, functions, dates, maps and plain { } objects are all objects. So the language has eight types in total: seven primitives plus object.

number: one floating-point type for everything

Every JavaScript number is an IEEE 754 double-precision value — the same format as Java's double. There is no separate integer type. Integers are exact up to 253 − 1, and fractions behave like Java doubles, rounding errors included.

console.log(0.1 + 0.2);               // 0.30000000000000004
console.log(0.1 + 0.2 === 0.3);       // false
console.log(Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON); // true

console.log(7 / 2);                   // 3.5 — "/" never does integer division
console.log(Math.trunc(7 / 2));       // 3
console.log(-7 % 3);                  // -1 (sign follows the left side, as in Java)
console.log(2 ** 10);                 // 1024

console.log(1 / 0);                   // Infinity  (no ArithmeticException)
console.log(-1 / 0);                  // -Infinity
console.log(0 / 0);                   // NaN
console.log(Number("abc"));           // NaN
console.log(typeof NaN);              // "number"
console.log(NaN === NaN);             // false — NaN equals nothing, not even itself
console.log(Number.isNaN(0 / 0));     // true  — the correct way to test for NaN

console.log(Number.MAX_SAFE_INTEGER); // 9007199254740991 (2^53 - 1)
console.log(9007199254740993);        // 9007199254740992 — precision lost!
console.log(Number.isSafeInteger(2 ** 53)); // false

NaN ("Not a Number") is a special number value that means "this calculation failed". It spreads: any arithmetic with NaN gives NaN. Infinity appears when a result is too large or you divide by zero. Java throws ArithmeticException for integer division by zero; JavaScript just returns Infinity and carries on, so check your inputs.

Number literals can be written as 1_000_000 (underscores for readability), 0xff (hex), 0b1010 (binary), 0o17 (octal) or 1e6 (exponent).

In real projects: money and big IDs

  • Money. Never add rupees as fractions (0.1 + 0.2 problem). Keep amounts as integer paise, do integer maths, and format only for display. This is the JavaScript version of using BigDecimal or long paise in Java.
  • Big IDs from Java. A Java long can exceed 253. When Spring Boot sends {"id": 9007199254740993}, JSON.parse turns it into 9007199254740992 — a different ID. Send such IDs as strings (for example with Jackson's @JsonFormat(shape = JsonFormat.Shape.STRING) on the field).
const pricePaise = 49_900;          // ₹499.00 stored as an integer
const quantity = 3;
const totalPaise = pricePaise * quantity;   // 149700 — exact

const inr = new Intl.NumberFormat("en-IN", { style: "currency", currency: "INR" });
console.log(inr.format(totalPaise / 100)); // ₹1,497.00
console.log(inr.format(12345678.5));       // ₹1,23,45,678.50 (lakh/crore grouping)

bigint: integers of any size

A bigint holds a whole number of any size, like Java's BigInteger — but with normal operators. Write it with an n suffix or create it with BigInt("…").

const big = 9007199254740993n;
console.log(big + 2n);               // 9007199254740995n
console.log(typeof big);             // "bigint"
console.log(7n / 2n);                // 3n — bigint division drops the fraction
console.log(BigInt("9007199254740993")); // 9007199254740993n — exact
console.log(BigInt(9007199254740993));   // 9007199254740992n — the number was already rounded
console.log(big + BigInt(1));        // 9007199254740994n
// big + 1  -> TypeError: Cannot mix BigInt and other types, use explicit conversions

You cannot mix bigint and number in arithmetic, Math functions do not accept bigints, and JSON.stringify throws TypeError: Do not know how to serialize a BigInt. Use bigint only when you really need integers above 253.

string: immutable text

Strings can use single quotes, double quotes or backticks (template literals, see template literals). They are primitives, so === compares their content — no equals() needed. They are immutable: methods return new strings. length is a property, not a method, and counts UTF-16 code units, so an emoji like "😀" has length 2.

undefined and null

JavaScript has two "no value" values. undefined means "nothing was ever put here": a declared variable without a value, a missing object property, a missing function argument, or the result of a function without return. null means "empty on purpose" — you, the programmer, assign it.

Spring Boot (Jackson) sends a missing Java value as null in JSON, so data from your API contains null; values you forgot to set in JavaScript are undefined. The check value == null (with two equals signs) is true for both — the one place where == is commonly accepted.

symbol

A symbol is a unique value: Symbol("id") === Symbol("id") is false. Symbols serve as object keys that can never clash with other keys. You will rarely create them yourself, but the language uses "well-known symbols" internally — for example Symbol.iterator is what makes arrays work with for…of.

typeof and its surprises

console.log(typeof "hi");            // "string"
console.log(typeof 42);              // "number"
console.log(typeof 42n);             // "bigint"
console.log(typeof true);            // "boolean"
console.log(typeof undefined);       // "undefined"

console.log(typeof null);            // "object"   ← surprise 1
console.log(typeof [1, 2]);          // "object"   ← surprise 2
console.log(typeof function () {});  // "function" ← surprise 3 (functions are objects)
console.log(typeof class {});        // "function"
console.log(typeof notDeclaredAnywhere); // "undefined" — no ReferenceError

typeof null === "object" is a bug from the first JavaScript engine (values carried a type tag, and null's tag matched objects). Fixing it would break old websites, so it stays. Use the right tool for each check:

  • Is it null? → value === null
  • Is it null or undefined? → value == null or value ?? fallback
  • Is it an array? → Array.isArray(value)
  • Is it NaN? → Number.isNaN(value)
  • Is it a date, a map, an instance of your class? → value instanceof Date

Primitives are copied, objects are shared

Assignment copies a primitive's value. For objects, the variable holds a reference, and assignment copies the reference — exactly like Java. JavaScript is "pass by value" in the same sense as Java: for objects, the value passed is the reference.

Edge cases

  • Wrapper objects. "hi".toUpperCase() works because the engine briefly wraps the primitive in a String object, like Java autoboxing. Never write new String("hi") or new Number(5): they create objects, typeof says "object", and new String("a") === new String("a") is false.
  • Immutable strings. s[0] = "H" does nothing in sloppy mode and throws TypeError in strict mode. Build a new string instead: "H" + s.slice(1).
  • Negative zero. -0 exists. 0 === -0 is true, but Object.is(0, -0) is false and 1 / -0 is -Infinity.
  • typeof in the temporal dead zone. typeof x is safe for undeclared names, but throws ReferenceError if x is a let/const used before its declaration line (see let, const and var).

Common mistakes

Wrong: these checks never work

if (typeof items === "array") { }  // never true
if (result === NaN) { }            // never true
const total = 0.1 + 0.2;           // ₹0.30000000000000004

Right: the reliable checks

if (Array.isArray(items)) { }
if (Number.isNaN(result)) { }
const totalPaise = 10 + 20;        // 30 paise, exact

Interview angle

  • "Name the data types." Seven primitives (string, number, bigint, boolean, undefined, null, symbol) plus object. Arrays and functions are objects.
  • "Why is 0.1 + 0.2 !== 0.3?" Numbers are binary floating point; 0.1 has no exact binary form — Java's double behaves the same. Compare with a tolerance or use integers.
  • "null vs undefined?" undefined = not set (engine default); null = intentionally empty (set by code). typeof null is "object" because of an old bug.
  • "What is NaN? How do you check it?" A number value for failed maths; it is not equal to itself, so use Number.isNaN().
  • "What is the largest safe integer?" Number.MAX_SAFE_INTEGER = 253 − 1 = 9007199254740991; beyond it use bigint or strings.

let, const and var: declaring variables

Use const by default, let when the variable must be reassigned, and never var: let and const are block-scoped and protected by the temporal dead zone, while var is function-scoped, can be re-declared and is silently hoisted as undefined.

JavaScript has three keywords for declaring variables. var is the original from 1995. let and const arrived in ES2015 to fix its problems. Modern code uses only let and const, but you must understand var because old code and interview questions are full of it.

Block scope vs function scope

A block is any pair of curly braces: an if, a loop body, a try, or a bare { }. let and const live only inside the block where you declare them — the same rule as local variables in Java. var ignores blocks and belongs to the whole enclosing function.

function checkout(items) {
  if (items.length > 0) {
    var viaVar = "visible in the whole function";
    let viaLet = "visible only inside this if block";
  }
  console.log(viaVar);  // "visible in the whole function"
  console.log(viaLet);  // ReferenceError: viaLet is not defined
}
checkout(["Paneer Tikka"]);

The temporal dead zone (TDZ)

All three declarations are hoisted: before a scope runs, the engine registers every name declared in it. The difference is the starting value. A var starts as undefined. A let or const starts uninitialised, and touching it before its declaration line throws a ReferenceError. The stretch of code between the start of the scope and the declaration is called the temporal dead zone. It exists to catch bugs: reading a variable before it has a value is almost always a mistake.

console.log(orderId);      // undefined — var is hoisted with the value undefined
var orderId = 1042;

console.log(orderStatus);  // ReferenceError: Cannot access 'orderStatus' before initialization
let orderStatus = "PLACED";

Hoisting has its own article with output-prediction exercises: scope and hoisting.

Re-declaration

var count = 1;
var count = 2;    // allowed — silently replaces the first one (a classic source of bugs)

let total = 1;
let total = 2;    // SyntaxError: Identifier 'total' has already been declared

A SyntaxError is reported when the file is parsed, so none of the file runs — not even the lines above the error. Re-assigning (total = 2) is fine with let; only declaring the same name twice in one scope is an error. Declaring the same name in an inner block is allowed and shadows the outer variable.

const does not freeze objects

const means the binding cannot change: the name always points to the same value. If that value is an object or array, the object itself can still change. It is exactly Java's final on a reference variable.

const GST_RATE = 0.18;
// GST_RATE = 0.12;          // TypeError: Assignment to constant variable.

const cart = { items: [] };
cart.items.push("Vada Pav"); // fine — the object changes, the binding does not
cart.total = 40;             // fine
// cart = { items: [] };     // TypeError: Assignment to constant variable.

const city = Object.freeze({ name: "Pune" });
city.name = "Goa";           // TypeError in strict mode (modules); ignored otherwise
console.log(city.name);      // "Pune"

Object.freeze() makes an object's own properties read-only, but only one level deep: a frozen object's nested objects can still change. See objects for details.

Loops: let gives each iteration its own variable

In for (let i = 0; …), each iteration gets a fresh copy of i. This fixes the famous closure-in-a-loop bug (explained in closures). In a for…of loop you can use const, because each iteration creates a new binding: for (const item of items). A classic counting loop cannot use const: for (const i = 0; i < 3; i++) runs the body once and then throws TypeError: Assignment to constant variable. at i++.

Naming rules and conventions

Rules: a name starts with a letter, _ or $, continues with letters, digits, _ or $, is case-sensitive, and cannot be a reserved word (class, const, function, new, this, default, delete …). The conventions are close to Java's:

Not every const is UPPER_CASE. Use capitals only for true constants that are known before the program runs (const MAX_RETRIES = 3). A const that holds a computed value is still camelCase: const total = calculateTotal(cart).

Convention: const first, let when needed, var never

Start every declaration with const. Change it to let only when you really reassign it (a counter, a value built in a loop). Seeing let then tells the reader "this changes later". ESLint enforces this with the rules prefer-const and no-var.

Java's var is not JavaScript's var

Java 10's var is local type inference: var list = new ArrayList<String>() still has a fixed, static type, and it follows normal block scope. JavaScript's var is the old function-scoped declaration with none of those guarantees. The closest JavaScript match for Java's var is let (or const for a final var).

Edge cases

  • No declaration at all. total = 10 without let/const creates a global variable in sloppy mode and throws ReferenceError: total is not defined in strict mode.
  • Globals in classic scripts. All classic <script> files on a page share one global scope, so two files declaring let user at the top level clash with a SyntaxError. Modules have their own scope and avoid this.
  • window properties. A top-level var name in a classic script overwrites window.name, which is a real browser property. Another reason to avoid var.

Common mistake: thinking const makes data immutable

Wrong: "it's const, so nobody can change it"

const ADMIN_ROLES = ["ADMIN", "OWNER"];
// some other code, far away:
ADMIN_ROLES.push("GUEST"); // works! security bug

Right: freeze shared constant data

const ADMIN_ROLES = Object.freeze(["ADMIN", "OWNER"]);
ADMIN_ROLES.push("GUEST");
// TypeError: Cannot add property 2,
// object is not extensible

Interview angle

  • "var vs let vs const?" Scope (function vs block), hoisting (undefined vs TDZ), re-declaration (allowed vs SyntaxError), re-assignment (const forbids it).
  • "What is the temporal dead zone?" The part of a scope before a let/const declaration runs; accessing the variable there throws ReferenceError.
  • "Does const make an object immutable?" No — it fixes the binding only. Use Object.freeze() (shallow) for the object.
  • "Are let and const hoisted?" Yes, they are hoisted but not initialised — that is exactly what creates the TDZ.

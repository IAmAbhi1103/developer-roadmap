What HTML, CSS and JavaScript each do

HTML describes what is on the page (structure and meaning), CSS describes how it looks (presentation), and JavaScript describes what it does (behaviour) — three languages, three jobs, one page.

Every web page, from a plain blog to a Flipkart product page, is built from the same three technologies. The browser understands only these three, so every framework you will meet later (React, Tailwind, Bootstrap) is just a smarter way of producing HTML, CSS and JavaScript in the end.

The three jobs

HTML (HyperText Markup Language)
A markup language: you wrap content in tags that say what it is — a heading, a paragraph, a link, a form field. HTML gives the page its structure and meaning. It is not a programming language: no variables, no loops, no logic.
CSS (Cascading Style Sheets)
A style language: rules that say "all headings are dark blue, cards have rounded corners, on phones show one column". CSS controls presentation — colours, fonts, spacing, layout, animation. It is declarative too: you describe the result, the browser works out how.
JavaScript (JS)
A real programming language that runs inside the browser. It reacts to clicks, validates input, changes the page, calls your Spring Boot API with fetch() and updates the screen with the answer. It controls behaviour.

A Java developer's mapping

If you think in layers, the browser side has its own layering:

ConcernFrontendSomething similar in your Java world
Structure and contentHTMLThe data model / the view template (Thymeleaf, JSP)
PresentationCSSFormatting and layout rules, kept separate from logic
BehaviourJavaScriptThe controller and service code
DataJSON from fetch()The DTOs returned by your REST controllers

The golden rule is separation of concerns: keep the three in separate files (index.html, styles.css, app.js), so each can change without breaking the others. React later blends HTML-like markup and JavaScript in one file, but it still produces the same three things for the browser.

The same button, three ways

Start with HTML only. This is a page with a heading and a button. It works, but it looks like a 1995 page and the button does nothing:

<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Chai counter</title>
</head>
<body>
  <h1>Chai counter</h1>
  <p>Cups today: <span id="count">0</span></p>
  <button id="add">Add a cup</button>
</body>
</html>

Add CSS in a separate file and link it from the <head> with <link rel="stylesheet" href="styles.css">:

body {
  font-family: system-ui, sans-serif;
  max-width: 24rem;
  margin: 2rem auto;
  text-align: center;
}

h1 { color: #7a3e00; }

button {
  padding: 0.6rem 1.2rem;
  border: 0;
  border-radius: 0.5rem;
  background: #c76b00;
  color: white;
  font-size: 1rem;
  cursor: pointer;
}

button:hover { background: #a85a00; }

Add JavaScript in a third file and load it at the end of the page (or with defer, see How the browser renders a page):

const countEl = document.getElementById("count");
const button = document.getElementById("add");
let cups = 0;

button.addEventListener("click", () => {
  cups++;
  countEl.textContent = cups;   // changes the page without any server call
});

Now each file has one job. Change the colours and you only touch styles.css. Change the counting logic and you only touch app.js. The browser connects them through the DOM: JavaScript finds elements with document.getElementById and changes them; the id in the HTML is the shared name.

What each language cannot do

  • HTML cannot compute anything or react to events. The only "behaviour" it has is built in: links navigate, forms submit, <details> opens.
  • CSS cannot read data or make decisions beyond selectors, media queries and a few functions like calc(). It can animate and respond to hover and screen size, but not call an API.
  • JavaScript can do everything, but doing it with JavaScript is often slower and more fragile than using HTML or CSS. A rule of thumb: use HTML if it can, CSS if it can, JavaScript only when you must. A dropdown built with <details>, or a smooth hover with a CSS transition, needs no script.

JavaScript is not Java

The names are a marketing accident from 1995. The two languages are unrelated. JavaScript is dynamically typed, uses prototypes and functions as first-class values, has a single-threaded event loop, and runs in the browser (and on servers through Node.js). Module 4 teaches it properly, with Java comparisons at each step. TypeScript, a typed superset of JavaScript that compiles to plain JavaScript, is covered in Module 7.

Rule: the browser only runs HTML, CSS and JavaScript

Whatever tool you use — React, Vite, Tailwind, Sass, TypeScript — its output for the browser is those three file types (plus images, fonts and WebAssembly). Build tools exist to turn friendly source code into that output.

Convention: no inline styles, no inline handlers

Avoid style="color:red" and onclick="..." inside HTML. They mix the concerns, are hard to override and make a strict Content-Security-Policy impossible. Use classes in CSS and addEventListener in JavaScript.

Mistake: using JavaScript to do layout or styling work

Beginners write scripts that compute widths and set pixel positions. CSS Flexbox, Grid and media queries do this faster, survive window resizing and need no code. Reach for script only for behaviour.

Interview angle: "What do HTML, CSS and JavaScript do?"

  • HTML = structure and meaning, CSS = presentation, JavaScript = behaviour; all three are loaded by the browser from separate files.
  • HTML and CSS are declarative; JavaScript is a programming language.
  • Mention that JavaScript changes the page through the DOM, and that frameworks still output these three.

What happens when you open a page

Typing a URL triggers a chain: parse the URL, find the IP through DNS, open a TCP and TLS connection, send an HTTP request, receive HTML, then fetch every linked file and render the page.

"What happens when you type a URL and press Enter?" is one of the most common interview questions, for freshers and for experienced developers. A good answer is a clear sequence of steps, with one or two details at each step. The full network story belongs to CS Fundamentals · Module 2; here is the version a full-stack developer should be able to tell.

The sequence

  1. Parse the input. The browser decides whether you typed a URL or a search term. For https://shop.example.com/products/42 it splits scheme, host, port and path (see URL anatomy).
  2. Check the caches. HSTS list (a site that must use HTTPS), service worker, HTTP cache. A fresh cached copy skips the network completely.
  3. DNS lookup. The browser turns shop.example.com into an IP address (see DNS in short).
  4. TCP connection. The browser opens a reliable connection to that IP on port 443 with the three-way handshake (SYN, SYN-ACK, ACK). HTTP/3 uses QUIC over UDP instead.
  5. TLS handshake. For HTTPS, the server sends its certificate, the browser verifies it against trusted authorities, and both sides agree on session keys. From now on, everything is encrypted.
  6. HTTP request. The browser sends GET /products/42 with headers, plus cookies stored for that site.
  7. Server work. Often a load balancer or Nginx receives it first and forwards it to one of your app instances. Your controller calls the service and repository, the database answers, and the server builds the response.
  8. HTTP response. Status line, headers and the body — usually HTML. The browser starts working on the first bytes while the rest is still arriving (streaming parse).
  9. Render and load sub-resources. While parsing, the browser finds <link>, <script> and <img> tags and sends more requests — each reusing the same connection where possible. Then it builds the DOM, applies styles, calculates layout and paints (see How the browser renders a page).
  10. JavaScript runs. Scripts may change the page and make fetch() calls to your API. The page is "interactive" once the main script has run.

Where the time goes

On a first visit to a site, DNS, TCP and TLS each cost at least one round trip before a single byte of your page is requested. This is why a server far away feels slow even when your code is fast, and why CDNs (servers close to users) and connection reuse matter. On the second request to the same host, the browser reuses the open connection and skips steps 3–5. The DevTools Network panel shows the split for each request: DNS lookup, initial connection, SSL, waiting (the server's time) and content download.

A tiny trace you can run

The -w option of curl prints the timing of each phase. Run this in a terminal (use curl.exe in PowerShell):

$ curl -s -o /dev/null https://example.com \
    -w "dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} \
first_byte=%{time_starttransfer} total=%{time_total}\n"
dns=0.012 connect=0.045 tls=0.110 first_byte=0.180 total=0.185

The numbers are in seconds and cumulative; yours will differ. Subtract neighbours to see each phase: here DNS took 12 ms, TCP 33 ms, TLS 65 ms, and the server about 70 ms. On Windows PowerShell write NUL instead of /dev/null.

What changes for a React + Spring Boot app

The first HTML response is tiny — an almost empty page with a <div id="root"> and a script tag. The browser then downloads the JavaScript bundle, runs React, and React calls your API (GET /api/products/42) to fetch JSON and draw the page. So there are two rounds: one for the app shell, one for the data. Static, dynamic, MPA, SPA and SSR explains the trade-offs.

Edge cases

  • A cached page may be shown without contacting the server at all (Cache-Control: max-age), which is why you sometimes do not see a change you just deployed. Hard reload with Ctrl+Shift+R bypasses the cache.
  • A redirect (301/302) adds a whole extra round trip, and http:// to https:// redirects are common. HSTS lets the browser skip that redirect next time.
  • If the TLS certificate is expired or does not match the host name, the browser shows a full-page warning (NET::ERR_CERT_DATE_INVALID or similar) instead of your site.
  • If the server is down, you see ERR_CONNECTION_REFUSED; if it never answers, ERR_CONNECTION_TIMED_OUT.

Tip: answer in layers, not in a list of acronyms

Interviewers want to see that you understand the order and the purpose of each step. Say what each step achieves ("DNS gets the IP", "TLS makes the connection private"), then ask whether they want more depth on any layer.

Interview angle: "What happens when you type a URL and press Enter?"

  • URL parse → cache check → DNS → TCP → TLS → HTTP request → server processing → response → parse HTML, fetch CSS/JS/images → render → run JS.
  • Add one Java-flavoured detail: the request reaches Tomcat, then DispatcherServlet, your controller, the service and the database.
  • Mention connection reuse, caching and CDNs as ways to make it faster.

How the browser renders a page

The browser parses HTML into the DOM and CSS into the CSSOM, combines them into a render tree, calculates the size and position of every box (layout), draws them (paint) and layers the result on screen (composite) — and a plain script tag stops the parser until the script has run.

The browser does not show HTML as it arrives. It runs a pipeline — the critical rendering path — every time it shows a page. Knowing the pipeline explains three things a full-stack developer meets constantly: why a page can flash unstyled content, why script placement matters, and why some CSS changes are cheap while others make the page janky.

1. HTML becomes the DOM

The parser reads HTML bytes, turns them into characters, then into tokens (start tag, end tag, text) and then into nodes that form a tree: the DOM (Document Object Model). The DOM is a live, in-memory object tree — each element is an object with properties and methods that JavaScript can read and change. Think of it as the parsed object graph of the document, like the object graph Jackson builds from JSON.

<body>
  <h1>Menu</h1>
  <ul>
    <li>Dosa</li>
    <li>Idli</li>
  </ul>
</body>

The parser is forgiving: if your HTML has a missing end tag, the browser repairs the tree instead of failing. That is convenient but hides mistakes, so validate your HTML (Validating HTML). Parsing is also incremental: the browser starts building the DOM from the first bytes while the rest of the file downloads.

2. CSS becomes the CSSOM

The browser parses every stylesheet into the CSSOM (CSS Object Model), a tree of rules with their final values. Unlike HTML, CSS cannot be used piece by piece: a rule at the bottom of the file can override one at the top, so the browser needs all the CSS before it can safely draw. That makes CSS render-blocking: the browser will not paint anything until the stylesheets in the head have loaded. This is why you put the stylesheet link in the head and keep CSS files small.

3. The render tree

The browser combines DOM and CSSOM into the render tree: only what will actually be displayed, with computed styles attached. Elements with display: none and everything in the <head> are left out. Elements with visibility: hidden are in the tree (they take space) but not drawn. Pseudo-elements such as ::before are in the render tree although they are not in the DOM.

4. Layout (reflow)

Layout works out the exact size and position of every box, in pixels, for the current window size. Percentages and rem units become real numbers here, and boxes are placed according to flow, Flexbox, Grid and positioning rules. One change high up the tree (a bigger image, a font that finishes loading) can change the position of everything below it, so layout is expensive. A second layout caused by a later change is called a reflow.

5. Paint

Paint turns boxes into pixels: backgrounds, borders, text, shadows, images. The browser records the draw commands for each layer. A change that only affects colour, such as a hover background, needs paint but not layout.

6. Composite

The page is split into layers (elements with transform, opacity animations, position: fixed, video and so on). The GPU draws the layers in the right order and combines them — compositing. A change to transform or opacity on its own layer only needs this last step, which is why animations should use them (Transitions and animations).

You change…Stages that re-runCost
width, margin, font-size, adding elementsLayout, paint, compositeHighest
background-color, box-shadowPaint, compositeMedium
transform, opacityComposite onlyLowest

Scripts block the parser

JavaScript can change the DOM while it is being built (document.write can even add HTML). So when the parser meets a plain <script src="app.js">, it stops, downloads the script, waits for pending stylesheets (the script may read styles), runs it, and only then continues. A big script in the head therefore leaves the user looking at a blank page.

Two attributes fix this. Both download the script in parallel with the HTML parsing; they differ in when it runs.

TagDownloadRuns whenOrder kept?Use for
<script src>Blocks the parserImmediatelyYesAlmost never in the head
<script defer>In parallelAfter the HTML is fully parsed, before DOMContentLoadedYes, in document orderYour app code; scripts that touch the DOM
<script async>In parallelThe moment it arrives (may interrupt parsing)NoIndependent scripts such as analytics
<script type="module">In parallelDeferred by defaultYesModern ES modules (Vite uses this)
 
<head>
  <link rel="stylesheet" href="styles.css">
  <!-- runs after parsing, in order: first vendor.js, then app.js -->
  <script src="vendor.js" defer></script>
  <script src="app.js" defer></script>
  <!-- independent; runs whenever it loads -->
  <script src="analytics.js" async></script>
</head>

The older advice was "put scripts just before </body>". defer in the head is better: the download starts earlier and the order is still guaranteed. A Vite-built React app has exactly this shape:

<body>
  <div id="root"></div>
  <script type="module" src="/src/main.jsx"></script>
</body>

Page load events and metrics

  • DOMContentLoaded fires when the HTML is parsed and deferred scripts have run (images may still be loading).
  • load fires when everything, including images and stylesheets, has finished.
  • First Contentful Paint (FCP) is when the first text or image appears. Largest Contentful Paint (LCP) is when the biggest visible element appears; good is under 2.5 seconds. Cumulative Layout Shift (CLS) measures unexpected jumps of the layout; Interaction to Next Paint (INP) measures how quickly the page reacts to clicks. Lighthouse and the Performance panel report them.

Watching it happen

You can see the DOM change live. Open DevTools on any page, go to the Console and run:

const p = document.createElement("p");
p.textContent = "Added by JavaScript";
document.body.append(p);      // DOM changes -> layout and paint run again
document.body.children.length; // how many direct children body has now

The new line appears at once, and you can find it in the Elements panel. The DOM is the truth the browser draws; the HTML file you downloaded is only where it started.

Rule: CSS in the head, scripts with defer

Link stylesheets in the <head> so the first paint is already styled. Load your own scripts with defer (or type="module") so they never block parsing and always see a complete DOM.

Edge cases and errors

  • An async or defer attribute on an inline script (no src) does nothing; defer is ignored there. Only type="module" inline scripts are deferred.
  • A script that runs too early gets null from getElementById and fails with TypeError: Cannot read properties of null. The element does not exist yet. Use defer.
  • Images without width and height have no size until downloaded; the layout then jumps (bad CLS). Set the size in HTML (Images).
  • Web fonts can make text invisible or swap suddenly while loading; font-display: swap shows a fallback font first.

Mistake: reading layout values in a loop while changing styles

Reading element.offsetHeight forces the browser to run layout right away. Alternating "write style, read size, write style, read size" in a loop causes a reflow every iteration (layout thrashing). Batch all reads first, then all writes. React does much of this batching for you.

Interview angle: "How does the browser render a page?"

  • HTML → DOM; CSS → CSSOM; both → render tree → layout → paint → composite.
  • CSS blocks rendering; a normal script blocks parsing; defer keeps order and runs after parsing; async runs as soon as it loads, in no fixed order.
  • Layout is the costly stage; animate transform and opacity to skip it.
  • Reflow = layout again; repaint = paint again.

Static vs dynamic sites, MPA vs SPA, CSR vs SSR

A static site serves ready-made files, a dynamic site builds pages per request; a multi-page app loads a new HTML page per click, a single-page app loads one page and swaps content with JavaScript; and the HTML can be built in the browser (CSR) or on the server (SSR).

These terms are mixed up constantly, because they answer different questions. Keep three questions apart: (1) is the content fixed or generated? (2) does a click load a new page or update the current one? (3) where is the HTML produced? Your full-stack project will be: dynamic data, single-page app, client-side rendering.

Static vs dynamic

A static site is a folder of finished files — HTML, CSS, JS, images. The server just hands them over; nothing is computed per user. A dynamic site runs code on the server for each request, usually reading a database, so two users can see different content.

StaticDynamic
ExamplesPortfolio, docs, a company landing pageFlipkart, IRCTC, a banking dashboard
Server workRead a file, send itRun code, query the database, build the response
SpeedVery fast; served from a CDNDepends on your code and database
HostingFree or cheap: GitHub Pages, Netlify, S3 + CDNNeeds a running server, e.g. Spring Boot
Security surfaceTinyLarge: login, input, database

The line is blurry, because a static page can call a dynamic API after it loads. The React build is static files; the data it shows is dynamic. Static site generators (Hugo, Jekyll, Astro, Next.js in export mode) build HTML files ahead of time from templates and data.

Multi-page apps (MPA)

In a multi-page application every link click or form submit makes the browser request a new HTML document. The server (Spring MVC with Thymeleaf or JSP, PHP, Django, Rails) returns the complete page. The browser throws the old page away, including its JavaScript state, and renders the new one.

@Controller
public class OrderPageController {

    private final OrderService orderService;

    public OrderPageController(OrderService orderService) {
        this.orderService = orderService;
    }

    @GetMapping("/orders/{id}")
    public String show(@PathVariable long id, Model model) {
        model.addAttribute("order", orderService.find(id));
        return "order";   // Thymeleaf template order.html -> full HTML page
    }
}

MPAs are simple, work without much JavaScript, and are good for SEO since each URL returns finished content. The cost: every navigation reloads the whole page, even the header and sidebar.

Single-page apps (SPA)

A single-page application loads one HTML page and one JavaScript bundle once. After that, clicking a link does not reload anything: JavaScript changes the URL with the History API, calls fetch() for JSON, and rewrites parts of the DOM. React with React Router, Angular and Vue work this way. It feels like a desktop app — fast transitions, state preserved — and the server becomes a pure JSON API.

SPA strengths

  • Smooth, app-like navigation; no full reloads
  • Clean split: one team builds the UI, another the REST API
  • The same API can serve a mobile app
  • The static build is cheap to host on a CDN

SPA weaknesses

  • Larger first download; blank screen until JavaScript runs
  • SEO and link previews are harder, since the first HTML is nearly empty
  • More moving parts: routing, state, auth tokens, CORS
  • Deep links need server configuration (see below)

Client-side vs server-side rendering

Rendering here means producing the HTML for the page content. Client-side rendering (CSR): the server sends an empty shell; the browser's JavaScript builds the content. Server-side rendering (SSR): the server sends HTML that already has the content; the browser shows it at once. Thymeleaf, JSP and PHP are server-side rendering in the classic sense. Frameworks like Next.js render React components on the server, then hydrate the page: React attaches event handlers to the already-present HTML so it becomes interactive.

CSR (plain React + Vite)SSR (Thymeleaf, Next.js)
First HTMLEmpty shellFull content
Time to first contentSlower (download, run JS, call API)Faster
SEO and link previewsWeaker (crawlers must run JS)Strong
Server costLow (static files + API)Higher (renders on every request)
After first loadVery fast navigationDepends on the framework

A related idea is static site generation (SSG): render the pages once at build time and serve them as static files — the best of both for content that rarely changes.

Where a React + Spring Boot app fits

The standard architecture in this course: a CSR single-page app in React, talking to a REST API in Spring Boot over JSON. In development, two servers run (Vite on 5173, Spring Boot on 8080). In production, there are two common layouts:

  • Separate hosting. The React build lives on a CDN or Nginx; the API lives on its own domain or under /api behind the same proxy. Teams can deploy independently.
  • One jar. Copy the Vite dist folder into Spring Boot's src/main/resources/static; Boot serves both files and API. Simple to deploy, but UI and API now ship together.
import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;

@Controller
public class SpaForwardController {

    // The browser URL /orders/7 is a React route, not a server resource.
    // On a hard refresh the server must return index.html;
    // React Router then decides what to show.
    @GetMapping({"/orders/{id}", "/profile"})
    public String forward() {
        return "forward:/index.html";
    }
}

That last point catches many beginners: with a SPA, a refresh on /orders/7 sends that path to the server, which has no such file and answers 404. The fix is to return index.html for every non-API path (this is the try_files line in Nginx, or a fallback rule on static hosts).

Rule: in a SPA the server must never return an HTML error page to the API

Your React code calls response.json(). If the API answers with the SPA's index.html or a Whitelabel HTML error page, parsing fails with SyntaxError: Unexpected token '<'. Keep /api/** separate and make it always return JSON.

Convention: prefix all API routes with /api

A clear prefix lets Nginx or Spring route /api/** to controllers and everything else to the React app, and keeps SPA routes and API routes from clashing.

Edge case: SEO for a SPA

Google can run JavaScript, but other crawlers and social-media link previews (WhatsApp, LinkedIn) often read only the raw HTML. For public pages that need search ranking or good previews, use SSR/SSG (Next.js, Thymeleaf) or pre-render. For apps behind a login — dashboards, admin tools, CRMs — SEO does not matter and a SPA is perfectly fine.

Mistake: choosing a SPA for every project

A five-page company website or a blog is better as a static site or server-rendered pages. Pick the architecture from the need: public content → static/SSR; interactive app → SPA.

In real projects

Many service-company projects still use Spring MVC + Thymeleaf or JSP (MPA, SSR). Most product-company and startup teams build React + REST API. Large public sites such as e-commerce increasingly use Next.js for SSR with a Java backend behind it.

Interview angle

  • SPA vs MPA: one HTML page + JSON calls versus a full HTML page per navigation. Mention routing without reload, SEO and initial load.
  • CSR vs SSR: who builds the HTML — browser or server — and the effect on first paint and SEO.
  • Where does your project fit? React SPA (CSR) + Spring Boot REST API, JWT or session auth, Nginx serving the build.

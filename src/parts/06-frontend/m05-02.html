Components and props

A component is a function that takes one object of props and returns JSX; props flow from parent to child, are read-only, and you build screens by composing small components.

Function components

A component is a JavaScript function whose name starts with a capital letter and that returns JSX (or null to show nothing). You use it like an HTML tag: <EmployeeCard />. React treats lowercase tags (<div>) as built-in HTML elements and capitalised tags as your components. That is why <employeeCard /> fails: React looks for an HTML element called "employeecard".

Old code uses class components (class X extends React.Component). They still work but nobody writes them in new code. Everything in these notes uses function components and hooks.

function EmployeeCard({ name, role, salary, active = true }) {
  return (
    <article className="card">
      <h3>{name}</h3>
      <p>{role}</p>
      <p>₹{salary.toLocaleString('en-IN')} per month</p>
      {!active && <span className="badge">Inactive</span>}
    </article>
  );
}

export default EmployeeCard;
import EmployeeCard from './components/EmployeeCard.jsx';

function App() {
  return (
    <main>
      <EmployeeCard name="Asha Rao" role="Java Developer" salary={85000} />
      <EmployeeCard name="Vikram Nair" role="QA Engineer" salary={62000} active={false} />
    </main>
  );
}

export default App;

Props: the inputs of a component

Props (short for properties) are the attributes you write on the tag. React collects them into one object and passes it as the first argument of the function. Destructuring in the parameter list, as above, is the normal style.

  • Text can be passed with quotes: name="Asha". Everything else goes in braces: salary={85000}, active={false}, tags={['java', 'sql']}, onSave={handleSave}, user={user}.
  • A prop with no value, such as <Button disabled />, means true.
  • You can spread an object into props: <EmployeeCard {...employee} />. It is handy but hides which props a component needs, so use it sparingly.
  • Default values are normal JavaScript default parameters (active = true). The old Component.defaultProps is removed for function components in React 19.
  • Props can be anything: strings, numbers, objects, arrays, functions and even JSX.

Props are read-only

A component must never change its own props. Treat the props object like a Java record: it is a snapshot owned by the parent. If a child needs to change something, the parent passes a function as a prop, and the child calls it (the lifting state up pattern). This keeps data flowing in one direction — down — and events flowing up.

function DeleteButton({ onDelete }) {
  return <button onClick={onDelete}>Delete</button>;
}

function EmployeeRow({ employee, onRemove }) {
  return (
    <li>
      {employee.name}
      {/* The child calls back; the parent owns the data and decides what happens */}
      <DeleteButton onDelete={() => onRemove(employee.id)} />
    </li>
  );
}

Pure components

React expects a component to be pure while rendering: the same props and state in should give the same JSX out, and rendering must not change anything outside the component (no editing a global variable, no fetch, no Math.random() that changes the output, no writing to the DOM). Side effects belong in event handlers or in useEffect. StrictMode renders twice in development precisely to catch impure components.

children and composition

Whatever you put between the opening and closing tags arrives as the special prop children. This lets you build generic wrappers (cards, modals, layouts) that do not know what they contain.

function Card({ title, children, footer }) {
  return (
    <section className="card">
      <h2>{title}</h2>
      <div className="card-body">{children}</div>
      {footer && <div className="card-footer">{footer}</div>}
    </section>
  );
}

function Dashboard() {
  return (
    <Card title="Today's orders" footer={<a href="/orders">See all</a>}>
      <p>42 orders, ₹1,86,400 revenue</p>
    </Card>
  );
}

React prefers composition over inheritance. You never make SpecialCard extends Card. Instead you wrap, pass children, or pass JSX in props (as footer above). If you used the Decorator pattern in Java, this will feel familiar.

Prop drilling

Prop drilling means passing a prop through several layers of components that do not use it, only to deliver it to a deep child. One or two levels is fine. When the same value (the logged-in user, the theme) travels through five layers, use Context, or restructure with children so the middle layers never see the prop.

Folder structure that scales

Rules for components

  • Component names are PascalCase; the file has the same name; one main component per file, exported as default (or by name — be consistent).
  • Never define a component inside another component. Each render would create a new function, so React sees a "different type", destroys the subtree and loses its state.
  • Never modify props (props.items.push(x), props.user.name = 'x').
  • Components must be pure during render.

Conventions

  • Keep components small. If you cannot name what a component does in one phrase, or the file passes about 150 lines, split it.
  • Props that hold functions are named onSomething (onSave, onClose); the handler inside the parent is handleSomething.
  • Booleans read like questions: isOpen, hasError, disabled.
  • Pass the data a component needs, not a whole big object it barely uses, unless the object is the natural unit (an employee for an EmployeeCard).

Edge cases

  • key and ref are special. key is never delivered to your component as a prop. In React 19, ref is an ordinary prop on function components; in React 18 you needed forwardRef.
  • Destructuring undefined throws: function Row({ user }) then user.name gives "Cannot read properties of undefined" if the parent forgot to pass user. This is the most common error when data has not loaded yet — render a loading state first.
  • Passing a new object or array literal as a prop (style={{…}}, options={[1, 2]}) creates a new reference every render. That is harmless unless the child is wrapped in memo (see memo and useCallback).

Mistake: copying a prop into state

const [name, setName] = useState(props.name) reads the prop only on the first render. When the parent sends a new name, the child keeps showing the old one. Use the prop directly, or, if the component truly needs an editable copy, reset it by giving the component a key that changes when the source item changes.

Interview: "Props vs state?"

  • Props are inputs passed down by the parent and are read-only for the receiver. State is private memory owned by the component, changed through a setter, and it triggers a re-render.
  • When a parent re-renders, children get new props; state survives re-renders.
  • Data flows down as props; changes flow up by calling functions passed as props.
  • Avoid prop drilling with composition (children) or Context.

State with useState

useState gives a component memory: it returns the current value and a setter, state is a snapshot for each render, and you must replace objects and arrays instead of changing them.

Why a plain variable does not work

Local variables are thrown away every time the function runs, and changing one does not tell React to re-render. State fixes both problems: React stores the value outside your function, and calling the setter schedules a new render.

import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);   // [current value, setter]; 0 is the initial value

  return (
    <div>
      <p>You clicked {count} times</p>
      <button onClick={() => setCount(count + 1)}>Click me</button>
    </div>
  );
}

The syntax const [count, setCount] = useState(0) is array destructuring (from Module 4). The first item is the value in this render; the second is the setter. Name them x and setX. The initial value is used only on the first render. If computing it is expensive, pass a function and React calls it once: useState(() => readFromLocalStorage()) (a "lazy initial state").

State is a snapshot

This is the idea that causes the most confusion. In each render, count is a constant with one fixed value. Calling setCount(count + 1) does not change the variable in the running function; it asks React for a new render in which count has the new value.

function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);   // asks for count = 1
    setCount(count + 1);   // still count is 0 in this snapshot: asks for count = 1 again
    setCount(count + 1);   // same
    console.log(count);    // prints 0, not 1
  }
  return <button onClick={handleClick}>Count: {count}</button>;
}
Console: 0
Button:  Count: 1   (not 3)

Functional updates

When the new value depends on the previous one, pass a function. React calls it with the latest pending value ("updater function"), so several updates in a row stack correctly.

function handleClick() {
  setCount((c) => c + 1);   // 0 -> 1
  setCount((c) => c + 1);   // 1 -> 2
  setCount((c) => c + 1);   // 2 -> 3
}   // one re-render, count is 3

Use the functional form whenever the next state is calculated from the old state — counters, toggles (setOpen(o => !o)), appending to a list — and always inside timers, async callbacks and effects, where the captured value may be stale.

Batching and when re-renders happen

React batches state updates: all set… calls inside one event handler are collected, then React renders once at the end. Since React 18 this also applies inside setTimeout, promises and native event handlers. Setting state to the same value (compared with Object.is) normally causes no visible work.

A component re-renders when its own state changes, when its parent re-renders (even if the props are the same, unless you use memo), or when a context it reads changes.

Updating objects and arrays immutably

React decides whether state changed by comparing references. If you mutate an object or array and pass the same reference to the setter, React sees "no change" and may skip the update. Always create a new object or array. You know the tools from Module 4: spread, map, filter.

    setTodos((prev) => prev.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));

    setTodos((prev) => prev.filter((t) => t.id !== id));

        </li>

    </ul>

Spread makes a shallow copy: nested objects are still shared, so copy each level you change. For deeply nested state, flatten the shape or use the Immer library, which lets you write mutating-looking code that produces immutable updates (Redux Toolkit uses it too, see Module 7).

Derive values instead of storing them

If a value can be calculated from props or other state, calculate it during render. Do not store it in a second useState and sync the two — they will get out of step.

function Cart({ items }) {
  // No state for these: they are computed from items on every render
  const total = items.reduce((sum, i) => sum + i.price * i.qty, 0);
  const count = items.length;
  const isEmpty = count === 0;
  return <p>{isEmpty ? 'Cart is empty' : `${count} items, ₹${total}`}</p>;
}

Where should state live?

  • Keep state in the lowest component that needs it (a modal's open flag lives in the modal's parent, not in App).
  • If two siblings need the same state, move it to their closest common parent (lifting state up).
  • If many distant components need it (current user, theme), use Context.
  • Data that comes from the server is a different kind of state — see TanStack Query.
  • Filters and page numbers that should survive a refresh or be shareable belong in the URL (search params).

Resetting state

State belongs to a component's position in the tree. Same type in the same place keeps its state; a different type, or a different key, resets it. So <EmployeeForm key={employee.id} employee={employee} /> gives each employee a fresh form without any reset code.

Rules for state

  • Never change state directly. Always use the setter, and give it a new object or array.
  • Call useState at the top level of the component (rules of hooks), never in loops, conditions or event handlers.
  • Do not call a setter during render (outside special patterns): it causes "Too many re-renders".
  • Keep state minimal and avoid duplicate sources of truth.

Edge cases

  • setX(fn) treats a function argument as an updater. To store a function in state, wrap it: setHandler(() => myFunction).
  • Setting state right after await in a component that has already unmounted does nothing harmful in React 18+ (the old warning is gone), but the request is still wasted work.
  • State is lost when the component unmounts, and on a full page refresh. Persist what matters (token, theme) to localStorage, a cookie or the server.
  • Reading state right after setting it gives the old value; use the next render, or compute the new value in a local variable first and use that for both the setter and the follow-up work.

Interview: "Why is my state not updating immediately? Why not mutate state?"

  • State is a snapshot per render; the setter schedules a re-render with the new value, it does not change the variable in the running function.
  • Updates are batched; use the functional form when the new value depends on the old one.
  • React detects change by reference comparison, so mutated objects look unchanged and the UI does not update. Immutability also keeps history, memoisation and DevTools reliable.
  • Derive what you can; store the minimum.

Events and conditional rendering

Pass a function (not its result) to onClick, use &&, a ternary or an early return to show or hide UI, and beware the 0 && gotcha.

Handling events

React events are written in camelCase and take a function: onClick, onChange, onSubmit, onKeyDown, onMouseEnter, onFocus, onBlur. Under the hood React attaches one listener at the root and gives your handler a synthetic event: a wrapper with the same API as the browser event (target, preventDefault(), stopPropagation()) that works the same in every browser.

function SaveBar({ onSave }) {
  function handleClick(event) {          // named handler, receives the event
    console.log(event.type, event.target);
    onSave();
  }
  return (
    <>
      <button onClick={handleClick}>Save</button>
      <button onClick={() => onSave('draft')}>Save draft</button>   {/* inline arrow */}
    </>
  );
}

Wrong: calls the function during render

<button onClick={handleDelete(id)}>Delete</button>
<button onClick={handleClick()}>Go</button>

Right: pass a function to call later

<button onClick={() => handleDelete(id)}>Delete</button>
<button onClick={handleClick}>Go</button>

handleClick() runs the function while rendering and passes its return value (usually undefined) as the handler. If that function sets state, you get an infinite loop and "Too many re-renders". To pass an argument, wrap the call in an arrow function.

Rendering vs handling: when does your code run?

React separates two moments. Rendering is when React calls your component function to find out what the screen should look like; it must be pure and must not change anything. Event handling is when the user does something; this is where you are allowed to change things: set state, call an API, navigate. Most "why does my component loop?" bugs come from putting handler work into the render body. Think of the component function like a Java toString(): it describes, it does not act. Handlers are like controller methods: they act.

Two details about handlers and state, both covered in State with useState: a handler sees the state values from the render that created it (a snapshot), and React batches all setState calls inside one event into a single re-render. So setCount(count + 1) called three times adds only 1; use setCount((c) => c + 1) when the next value depends on the previous one.

How an event travels

A browser event goes through three phases: capture (from the root down to the target), target, and bubble (from the target back up to the root). React's onClick runs in the bubble phase; onClickCapture runs in the capture phase. Since React 17 the single listener is attached to the root container you passed to createRoot, not to document. React then calls the handlers of the clicked element and each of its parents, in order.

Common event patterns

  • preventDefault() stops the browser's default action: a form submit reloading the page, a link navigating. Always call it in onSubmit for React-controlled forms.
  • stopPropagation() stops the event bubbling to parent handlers — for example a delete button inside a clickable row.
  • event.target.value is the text of an input; event.target.checked is the state of a checkbox.
  • Events bubble: a click on a child also fires onClick on its parents. To handle the capture phase, use onClickCapture.
  • Prefer a real <button> or <a> over a clickable <div>; they work with the keyboard and screen readers.
function EmployeeRow({ employee, onOpen, onDelete }) {
  return (
    <li onClick={() => onOpen(employee.id)}>
      {employee.name}
      <button
        onClick={(e) => {
          e.stopPropagation();       // do not also fire the row's onClick
          onDelete(employee.id);
        }}
      >
        Delete
      </button>
    </li>
  );
}

A realistic form handler

A login form shows the usual pieces together: a controlled input, preventDefault, an async call, and state for the "submitting" and error cases. Forms are covered fully in Forms; here the point is where the work happens, which is in the handler.

function LoginForm({ onLoggedIn }) {
  const [email, setEmail] = useState('');
  const [password, setPassword] = useState('');
  const [submitting, setSubmitting] = useState(false);
  const [error, setError] = useState(null);

  async function handleSubmit(e) {
    e.preventDefault();                    // no full page reload
    setSubmitting(true);
    setError(null);
    try {
      const res = await fetch('/api/auth/login', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ email, password }),
      });
      if (!res.ok) {
        throw new Error(res.status === 401 ? 'Wrong email or password' : 'Server error');
      }
      onLoggedIn(await res.json());
    } catch (err) {
      setError(err.message);
    } finally {
      setSubmitting(false);
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <input type="email" value={email} onChange={(e) => setEmail(e.target.value)} />
      <input type="password" value={password} onChange={(e) => setPassword(e.target.value)} />
      {error && <p role="alert">{error}</p>}
      <button disabled={submitting}>{submitting ? 'Signing in…' : 'Login'}</button>
    </form>
  );
}

Conditional rendering

JSX has no if inside the markup, so you use ordinary JavaScript: an if before the return, the ternary operator, or logical &&. A component can also return null to render nothing. Inside JSX, null, undefined, true and false all render nothing, which is exactly why cond && <X /> works.

function OrderStatus({ order, isLoading, error }) {
  // 1. Early return: best for loading / error / empty screens
  if (isLoading) return <p>Loading…</p>;
  if (error) return <p role="alert">Could not load: {error.message}</p>;
  if (!order) return null;               // render nothing

  // 2. Variable holding JSX
  let badge = null;
  if (order.status === 'DELIVERED') badge = <span>Delivered</span>;

  return (
    <div>
      {/* 3. Ternary: one thing or the other */}
      <p>{order.paid ? 'Paid' : 'Payment pending'}</p>
      {/* 4. &&: show something or nothing */}
      {order.items.length > 0 && <p>{order.items.length} items</p>}
      {badge}
    </div>
  );
}

Mistake: the 0 && gotcha

{items.length && <List />} prints a literal 0 when the array is empty, because 0 && x evaluates to 0, and React renders numbers. Make the left side a real boolean: items.length > 0 && … or Boolean(items.length) && …. Strings are similar: an empty string renders nothing, but a number never does.

Rule: an early return must come after every hook

React identifies hooks by call order (see the rules of hooks). If you write if (!user) return null; and then call useState below it, the number of hooks changes between renders and React throws an error. Call all hooks first, then return early.

Hiding vs not rendering

When a condition is false, the element is not rendered, and any state inside that component is destroyed. To keep state while hiding (a half-filled tab), render it always and hide with CSS (hidden attribute or a class) or lift the state up (see Sharing state).

The reverse also matters. React keeps state for a component that stays at the same position in the tree with the same type. In {isAdmin ? <Form /> : <Form />} the two branches are the same component in the same place, so typed text survives the switch. If that is not what you want, give them different keys (see keys). Swapping <Form /> for <Other /> always resets the state.

Showing one of several states

A screen that loads data has at least four states: loading, error, empty and data. Handle them explicitly, in that order, with early returns. Missing the empty state is a very common review comment. Data from a Spring Boot endpoint that returns [] is a valid success, not an error; show a friendly "No employees yet" message with a button to add one.

const STATUS_LABEL = {
  PLACED: 'Order placed',
  SHIPPED: 'On the way',
  DELIVERED: 'Delivered',
  CANCELLED: 'Cancelled',
};

function StatusBadge({ status }) {
  const label = STATUS_LABEL[status] ?? 'Unknown status';   // safe default
  return <span className={`badge badge-${status.toLowerCase()}`}>{label}</span>;
}

A lookup object replaces a long if / else if chain, much like a Java switch on an enum or an EnumMap. The ?? fallback covers a value your backend adds later that the frontend does not know yet.

Conventions

  • Handler names: handleX inside the component, onX as a prop.
  • Keep inline arrows short. Move longer logic to a named function above the return.
  • Avoid nested ternaries in JSX; use early returns or small components instead.
  • Use a real <form> with onSubmit instead of an onClick on a button, so the Enter key works.
  • Disable the submit button while a request is in flight to stop double submits.

Edge cases

  • React 17+ attaches events at the root container, not document, so mixing React and native listeners behaves predictably. A native stopPropagation on document can no longer hide events from React; a native listener on a parent element that stops propagation can.
  • onChange in React fires on every keystroke (like the native input event), unlike the native change event that waits for blur.
  • Passing onClick={undefined} or null is fine: no handler is attached.
  • Since React 17 the synthetic event is no longer pooled, so reading event inside an await or setTimeout works. You may still prefer to copy the value first: const value = e.target.value;.
  • A disabled <button> does not fire onClick; a clickable <div> with aria-disabled still does, so check inside the handler.

In real projects

Delete flows use both ideas together: the button's handler calls DELETE /api/employees/{id}, and the row is rendered conditionally from the list in state, with a confirm step (window.confirm or a modal) before the call. Role-based buttons use the same && pattern; see Protected routes.

Interview: "What is the difference between onClick={fn} and onClick={fn()}?"

  • fn passes the function; React calls it on click. fn() calls it immediately during render and passes the result.
  • Use () => fn(arg) to pass arguments.
  • React wraps the browser event in a synthetic event, delegating at the root.
  • Follow-ups: why does count && <X /> show 0? (numbers are rendered), what is the difference between stopPropagation and preventDefault? (bubbling vs the browser's default action).

Rendering lists and keys

Turn an array into elements with map, and give each item a stable, unique key (usually the database id) so React can match items between renders.

map() in JSX

You render a list by mapping data to elements. filter and sort before map give you search and ordering; do them on a copy during render, not in state. This works like a Java stream pipeline: filter → sorted → map produces a new collection and leaves the source list alone. That is why you use toSorted (or [...list].sort()), because plain sort() changes the original array, which you must never do with props or state.

function EmployeeList({ employees, search }) {
  const visible = employees
    .filter((e) => e.name.toLowerCase().includes(search.toLowerCase()))
    .toSorted((a, b) => a.name.localeCompare(b.name));   // toSorted does not mutate

  if (visible.length === 0) return <p>No employees found.</p>;

  return (
    <ul>
      {visible.map((e) => (
        <li key={e.id}>
          {e.name} — {e.department}
        </li>
      ))}
    </ul>
  );
}

Version note: toSorted

toSorted, toReversed and with are newer array methods (ES2023) that return a copy. They exist in current browsers and in Node 20+. If you must support very old browsers, use [...employees].sort(compareFn).

A list from a Spring Boot API

The usual real case: load a list from your backend, keep it in state, and render it. A Spring Data Page response wraps the rows in content next to paging fields, so you map over page.content, not over the page object (see Pagination).

function EmployeeTable() {
  const [rows, setRows] = useState([]);

  useEffect(() => {
    fetch('/api/employees?page=0&size=20')
      .then((r) => r.json())
      .then((page) => setRows(page.content));      // Spring Data Page: { content: [...] }
  }, []);

  function handleDelete(id) {
    setRows((prev) => prev.filter((e) => e.id !== id));   // new array, never splice
  }

  return (
    <table>
      <tbody>
        {rows.map((e) => (
          <EmployeeRow key={e.id} employee={e} onDelete={handleDelete} />
        ))}
      </tbody>
    </table>
  );
}

function EmployeeRow({ employee, onDelete }) {
  return (
    <tr>
      <td>{employee.name}</td>
      <td>{employee.department}</td>
      <td><button onClick={() => onDelete(employee.id)}>Delete</button></td>
    </tr>
  );
}

Notice the key is on <EmployeeRow> in the map, the outermost element of each item, not on the <tr> inside the row component.

What the key is for

A key is a string or number that identifies an item among its siblings. When the list changes, React uses keys to decide which old element matches which new one: same key → same item (keep the DOM node and any component state, just update it); new key → new item; missing key → removed. Without keys React can only compare by position.

How reconciliation uses keys

Every render produces a new tree of elements. Reconciliation is the step where React compares the new tree with the previous one and works out the smallest set of DOM changes. It compares children one level at a time. For a list, it looks up each new child's key in the old children: if found and the type is the same, it reuses the existing instance (with its state and DOM node) and only updates changed props; if not found, it creates one; old keys that are no longer present are unmounted.

Rule: keys must be stable, unique among siblings, and not random

  • Use the record's id from your database (employee.id).
  • Uniqueness is only needed among siblings, not across the whole app.
  • The key goes on the outermost element returned by map, not on a child inside a component. In a fragment use <Fragment key={…}>.
  • Never use Math.random() or crypto.randomUUID() during render as a key; each render gives new keys, so every item is destroyed and rebuilt (inputs lose focus, state is lost). Generate ids once, when you create the item.

Why index keys break

key={index} removes the warning but ties identity to position. If an item is added at the top, removed from the middle, or the list is sorted, the index of each item changes. React then matches the wrong data to the wrong DOM node and component state.

// A list of rows, each with an uncontrolled input holding the user's typing
{todos.map((t, index) => (
  <li key={index}>                      {/* wrong */}
    {t.text} <input placeholder="note" />
  </li>
))}
// Type "urgent" in the first row's input, then delete the first todo.
// The input text "urgent" now sits in the row that used to be second:
// React kept DOM node 0 and just changed its label.

Wrong: index as key in a changing list

{todos.map((t, i) => (
  <TodoItem key={i} todo={t} />
))}

Right: the item's own id

{todos.map((t) => (
  <TodoItem key={t.id} todo={t} />
))}

Index keys are acceptable only when the list is static: never reordered, filtered, inserted into or deleted from, and items have no state. Even then, an id is better. If your data has no id (a list of plain strings that are unique), the string itself can be the key.

// Good: id from the API
employees.map((e) => <EmployeeCard key={e.id} {...e} />);

// Good: unique natural value
tags.map((tag) => <span key={tag}>{tag}</span>);

// Good: id assigned once when the item is created (not during render)
setTodos((prev) => [...prev, { id: crypto.randomUUID(), text }]);

// Avoid: index, unless the list is static
// Never: key={Math.random()}

Nested lists and fragments

Keys only need to be unique among siblings, so an inner list can reuse ids used elsewhere. When one item must return several elements without a wrapper (two table rows, a term and its description), use the long form of the fragment, because the short <> cannot take a key.

import { Fragment } from 'react';

function DepartmentList({ departments }) {
  return (
    <dl>
      {departments.map((d) => (
        <Fragment key={d.id}>
          <dt>{d.name}</dt>
          {d.employees.map((e) => (
            <dd key={e.id}>{e.name}</dd>      {/* ids only need to be unique here */}
          ))}
        </Fragment>
      ))}
    </dl>
  );
}

Keys also reset state

A key is not only for lists. Changing the key of any component makes React treat it as a brand-new instance: old state is discarded. <Profile key={userId} /> is the clean way to reset a form when the user changes (see You might not need an effect).

The warning: "Each child in a list should have a unique key prop"

You rendered an array without keys, or the keys are duplicated, or you put the key on the wrong element (inside the child component instead of on the map result). Duplicate keys, such as two employees with the same id in test data, cause items to be duplicated or dropped on update. Check your data first.

Conventions

  • Extract the row into its own component (EmployeeRow) once it has more than a few lines; the map then stays one line.
  • Keep the list in state as an array of objects with ids; do not store an index.
  • Filter and sort in render (derived data) instead of keeping a second "visible" state.
  • Always handle the empty list, the loading state and the error state.

Edge cases

  • Keys are not passed as props. If the child needs the id, pass it separately (id={e.id}).
  • Ids from Spring Boot are numbers (Long) or strings (UUID); both work as keys. Be careful with composite data: if the id is not unique, combine fields (`${e.orderId}-${e.lineNo}`).
  • Rendering thousands of rows slows the page however good your keys are. Use pagination (see Module 6) or a virtualised list library such as TanStack Virtual.
  • A Java Long above 2^53 loses precision when parsed as a JavaScript number, so two different ids can become one key. Very large ids (for example snowflake ids) should be sent as strings from the API.
  • Keys of 0 and "0" are the same key (keys are compared as strings), so do not mix numbers and strings that look alike in one list.

In real projects

New records created in the browser before the server answers (optimistic add) have no database id yet. Give them a temporary client id (crypto.randomUUID() at creation), use it as the key, and replace the item with the saved one when the response arrives. If you swap the key at that moment, React remounts the row; keeping a separate stable clientId field avoids that flicker.

Interview: "Why do we need keys? Is index a good key?"

  • Keys identify items between renders so reconciliation can reuse, move or remove the right element and keep its state.
  • Use a stable unique id. Index keys are fine only for static lists; with reorder, insert or delete they mismatch state and DOM nodes and cause subtle bugs.
  • A random key every render forces a full remount of every item.
  • Changing the key of a component deliberately resets its state.
  • Follow-up: why is sort() on state a bug? It mutates the array that React compares by reference, so copy first.

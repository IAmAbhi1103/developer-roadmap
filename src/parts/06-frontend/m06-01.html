A React app on its own only shows data you typed into it. A real full-stack app talks to a backend: the browser loads your React files, then your JavaScript calls a Spring Boot REST API, which reads and writes PostgreSQL. This module is the glue between Module 5 and the Spring Boot work in Spring Boot · Module 4. Most real-world bugs for a new full-stack developer live here: a CORS error, a 401 on every request, a token that disappears on refresh, a validation message that never shows up.

You will build the whole path: an API client with the JWT attached, the CORS configuration on both sides, login and protected routes, forms that show backend errors, environment variables per environment, and a production build. Then you will put it all into one small project.

  • Draw the request path from browser to database and back.
  • Call your API with a configured Axios instance or a small fetch wrapper.
  • Explain CORS and preflight, read a CORS error, and fix it in Spring Boot or with the Vite proxy.
  • Implement JWT login with an AuthContext, restore the session on reload and handle expired tokens (401).
  • Build protected and role-based routes, and explain why the backend must still check roles.
  • Show loading, error, empty and paginated data, and map Spring's field errors onto form fields.
  • Use environment variables, build for production and deploy the static files.

The full-stack architecture and the request cycle

The browser downloads static React files once, then your JavaScript sends JSON requests to the Spring Boot API, which talks to PostgreSQL; the React app and the API are two separate programs, often on two different origins.

The pieces

  1. The page load. The user opens https://crm.example.com. A static host (Nginx, Vercel, Netlify, S3 + CDN) returns index.html and the JS and CSS files that npm run build produced. No Java runs here.
  2. React starts. The JavaScript runs in the browser, renders the first screen, and the router shows the page for the URL.
  3. API call. A component (or a query) calls https://api.example.com/api/employees with fetch or Axios, adding Authorization: Bearer <jwt>.
  4. Spring Boot. Security filters check the token, the controller calls the service, the repository runs SQL on PostgreSQL, and the result is serialised to JSON by Jackson.
  5. Response. The browser receives JSON, your code calls setState (or the query cache updates) and React re-renders.

Two origins, two deployments

In development you run two servers: Vite on http://localhost:5173 and Spring Boot on http://localhost:8080. These are different origins (different ports), and browsers apply the same-origin policy to scripts that call other origins. That is why CORS (next article) is the first thing that goes wrong. In production you choose between three layouts:

LayoutHowCORS needed?
Separate hostsUI on Vercel/Netlify/S3, API on its own domain or cloud serverYes
Reverse proxy, one domainNginx serves / from dist/ and forwards /api to Spring BootNo (same origin)
Bundled in the JARCopy dist/ into Spring Boot's static folderNo, but UI and API deploy together

The contract between the two sides

The frontend and backend agree on a contract: URLs, methods, JSON field names, status codes and the error format. Keep a short list of it (or an OpenAPI document from springdoc) and let the Java record DTOs drive the JavaScript object shapes. Typical mapping:

public record EmployeeResponse(Long id, String name, String email,
                               String department, BigDecimal salary, LocalDate joinedOn) {}
{
  "id": 7,
  "name": "Asha Rao",
  "email": "asha@corp.in",
  "department": "ENGINEERING",
  "salary": 85000.00,
  "joinedOn": "2024-06-03"
}

Things that trip people up in the JSON contract

  • Dates arrive as strings ("2024-06-03"). Convert with new Date(...) only when you need date maths or formatting.
  • Long ids above 253 lose precision in JavaScript numbers. Normal auto-increment ids are fine; send very large ids as strings.
  • BigDecimal becomes a JSON number; use integer paise or a string for money you calculate with.
  • Spring's default pagination response (Page) has content, totalElements, totalPages, number and size fields, plus flags such as first and last; the exact shape depends on your Spring Data version and whether you wrap it in your own DTO. Check the real response in the Network tab.

Conventions

  • Prefix all API routes with /api so a proxy or Nginx can tell them apart from frontend routes.
  • The frontend stores the API base URL in one place (an environment variable), never repeated in components.
  • All API calls go through one module (src/lib/apiClient.js). Components do not call fetch with full URLs.

Interview: "Walk me through what happens when a user opens the page and clicks Login"

  • Static files load from the host; React boots in the browser (SPA).
  • The login form POSTs credentials as JSON to the API (a cross-origin request, so CORS applies).
  • Spring Security authenticates, returns a JWT; the app stores it and attaches it to later requests.
  • Each API response is JSON that updates React state; the backend remains the authority for security and validation.

Calling your API: an Axios instance or a fetch wrapper

Create one configured HTTP client (base URL from an env variable, JSON headers, a request interceptor that adds the JWT, a response interceptor that handles 401) and use it everywhere; Axios gives this almost for free, and a 40-line fetch wrapper does the same.

Why a single client

Without one, every component repeats the base URL, the headers, the token, the res.ok check and the error parsing. One mistake or change then needs fifty edits. A central client makes four things happen automatically: the right base URL, the Authorization header, a consistent error shape, and one place to react to "401, token expired".

Axios

Axios is a popular HTTP client library. Install it with npm install axios. Compared with fetch, it parses JSON for you, throws on 4xx and 5xx responses, supports timeouts, and has interceptors: functions that run on every request or response.

import axios from 'axios';
import { tokenStore } from './tokenStore.js';

export const api = axios.create({
  baseURL: import.meta.env.VITE_API_URL,       // e.g. http://localhost:8080/api
  timeout: 10_000,                              // fail after 10 s instead of hanging
  headers: { 'Content-Type': 'application/json' },
});

// Request interceptor: runs before every request
api.interceptors.request.use((config) => {
  const token = tokenStore.get();
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// Response interceptor: runs for every response
api.interceptors.response.use(
  (response) => response,                      // 2xx: pass through
  (error) => {
    if (error.response?.status === 401 && !error.config.url.includes('/auth/')) {
      tokenStore.clear();                       // token invalid or expired
      window.dispatchEvent(new Event('auth:logout'));   // AuthContext listens for this
    }
    return Promise.reject(error);               // let the caller handle other errors
  },
);
import { api } from '../../lib/axios.js';

export const employeeApi = {
  list: (params) => api.get('/employees', { params }).then((r) => r.data),
  get: (id) => api.get(`/employees/${id}`).then((r) => r.data),
  create: (body) => api.post('/employees', body).then((r) => r.data),
  update: (id, body) => api.put(`/employees/${id}`, body).then((r) => r.data),
  remove: (id) => api.delete(`/employees/${id}`),
};

// employeeApi.list({ page: 0, size: 10, sort: 'name,asc' })
// -> GET /api/employees?page=0&size=10&sort=name%2Casc

Telling error kinds apart

An Axios error has different fields depending on what failed. This distinction decides what you show the user.

export function describeError(error) {
  if (error.response) {
    // The server answered with 4xx or 5xx
    const { status, data } = error.response;
    if (status === 401) return 'Your session has expired. Please log in again.';
    if (status === 403) return 'You do not have permission to do this.';
    if (status === 404) return 'Not found.';
    if (status >= 500) return 'Server error. Please try again later.';
    return data?.detail ?? data?.message ?? `Request failed (${status}).`;
  }
  if (error.request) {
    // The request was sent but no response arrived: server down, offline, or CORS blocked
    return 'Cannot reach the server. Check your connection.';
  }
  return error.message;                          // something broke before sending
}

The same with fetch

fetch needs no library. The cost is that you write the wrapper yourself: it does not throw on HTTP errors, does not parse JSON automatically, has no built-in timeout, and has no interceptors. This wrapper adds all of them (this is the apiClient idea from Module 4, grown up).

import { tokenStore } from './tokenStore.js';

const BASE_URL = import.meta.env.VITE_API_URL;

export class ApiError extends Error {
  constructor(status, body) {
    super(body?.detail ?? body?.message ?? `HTTP ${status}`);
    this.status = status;
    this.body = body;            // keep the whole Spring ProblemDetail for field errors
  }
}

async function request(path, { method = 'GET', body, params, signal } = {}) {
  const url = new URL(BASE_URL + path, window.location.origin);
  if (params) Object.entries(params).forEach(([k, v]) => url.searchParams.set(k, v));

  const headers = { Accept: 'application/json' };
  if (body !== undefined) headers['Content-Type'] = 'application/json';
  const token = tokenStore.get();
  if (token) headers.Authorization = `Bearer ${token}`;

  const timeout = AbortSignal.timeout(10_000);   // built-in timeout signal
  const res = await fetch(url, {
    method,
    headers,
    body: body !== undefined ? JSON.stringify(body) : undefined,
    signal: signal ? AbortSignal.any([signal, timeout]) : timeout,
  });

  if (res.status === 204) return null;           // No Content (typical for DELETE)
  const data = await res.json().catch(() => null);

  if (!res.ok) {
    if (res.status === 401 && !path.startsWith('/auth/')) {
      tokenStore.clear();
      window.dispatchEvent(new Event('auth:logout'));
    }
    throw new ApiError(res.status, data);
  }
  return data;
}

export const apiClient = {
  get: (path, opts) => request(path, opts),
  post: (path, body, opts) => request(path, { ...opts, method: 'POST', body }),
  put: (path, body, opts) => request(path, { ...opts, method: 'PUT', body }),
  delete: (path, opts) => request(path, { ...opts, method: 'DELETE' }),
};

Both versions expect a tiny token helper, shown here with an in-memory store. The JWT article explains where the token should live.

let accessToken = null;               // lives in memory only

export const tokenStore = {
  get: () => accessToken,
  set: (token) => { accessToken = token; },
  clear: () => { accessToken = null; },
};

Which one should you pick?

Either is fine; consistency matters more. Many Spring Boot teams use Axios because interceptors make JWT handling short. If you use TanStack Query, both work as the queryFn. Do not mix them in the same project. The rest of this module uses Axios (api) in most examples and shows the fetch equivalent where it differs.

Common mistakes

  • Hard-coding http://localhost:8080 in components; it breaks in staging and production.
  • Treating fetch 404/500 as success because the promise resolved.
  • Redirecting to login on every 401, including the 401 of a wrong password on the login request, which clears the error message. Skip the interceptor for auth endpoints.
  • Logging the Authorization header or token to the console or an error tracker.
  • Sending Content-Type: application/json with a FormData body; leave the header off and let the browser set the multipart boundary.

Interview: "Axios vs fetch? What are interceptors?"

  • Both use promises. Axios adds automatic JSON, rejection on non-2xx, timeouts and interceptors; fetch is native and needs a wrapper for the same behaviour.
  • Interceptors are hooks on every request/response: add the bearer token on the way out; handle 401 (logout or refresh) on the way back.
  • Keep one configured client so base URL, auth and error handling live in one place.

CORS end to end: why the browser blocks your request and how to fix it

CORS is a browser rule: a page may read a response from another origin only if that server's headers allow it; fix it by allowing your frontend's origin in Spring Boot (or avoid it in development with the Vite proxy), and remember CORS does not protect your API.

The error you will meet first

You call http://localhost:8080/api/employees from a React app on http://localhost:5173. The API works in Postman, but the browser Console shows:

Access to XMLHttpRequest at 'http://localhost:8080/api/employees' from origin
'http://localhost:5173' has been blocked by CORS policy: No
'Access-Control-Allow-Origin' header is present on the requested resource.

Postman works because CORS is enforced by browsers, not by servers. Your Spring Boot code probably ran fine and returned data; the browser then refused to hand the response to your JavaScript.

What an origin is

An origin is the combination of scheme + host + port. Two URLs are the same origin only if all three match.

URL compared with http://localhost:5173Same origin?Why
http://localhost:5173/employeesYesOnly the path differs
http://localhost:8080/apiNoDifferent port
https://localhost:5173NoDifferent scheme
http://127.0.0.1:5173NoDifferent host name
https://api.crm.in vs https://app.crm.inNoDifferent host (subdomain)

The same-origin policy stops a script on one origin from reading data from another, so that a malicious page you visit cannot read your bank's pages using your logged-in session. CORS (Cross-Origin Resource Sharing) is the controlled loophole: the server tells the browser, using response headers, which other origins may read its responses.

Simple requests and preflight

For some requests the browser just sends them with an Origin header and checks the response headers. For others, it first sends an OPTIONS "preflight" request to ask permission. A request needs preflight when it is not "simple": a method other than GET, HEAD or POST; or a Content-Type such as application/json; or a custom header such as Authorization. A JSON POST with a JWT therefore always triggers a preflight.

The fix in Spring Boot

Option 1, without Spring Security: register CORS mappings in a WebMvcConfigurer.

import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.CorsRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
public class WebConfig implements WebMvcConfigurer {

    private final String[] allowedOrigins;

    public WebConfig(@Value("${app.cors.allowed-origins}") String[] allowedOrigins) {
        this.allowedOrigins = allowedOrigins;
    }

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins(allowedOrigins)
                .allowedMethods("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS")
                .allowedHeaders("Authorization", "Content-Type")
                .exposedHeaders("Location")
                .maxAge(3600);
    }
}
# application.properties (development)
app.cors.allowed-origins=http://localhost:5173

# application-prod.properties (override per environment)
app.cors.allowed-origins=https://crm.example.com

Option 2, with Spring Security (the case for any JWT API). The Security filter chain runs before Spring MVC, so a preflight request with no Authorization header would be rejected with 401 before MVC's CORS mapping is ever consulted. You must configure CORS in the security chain, using a CorsConfigurationSource bean.

import java.util.List;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.web.cors.CorsConfiguration;
import org.springframework.web.cors.CorsConfigurationSource;
import org.springframework.web.cors.UrlBasedCorsConfigurationSource;

@Configuration
public class SecurityConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .cors(Customizer.withDefaults())          // uses the CorsConfigurationSource bean
            .csrf(csrf -> csrf.disable())             // OK for a stateless Bearer-token API
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()   // preflight
                .requestMatchers("/api/auth/**").permitAll()
                .anyRequest().authenticated());
        // ... JWT filter, session policy STATELESS, etc. (see the Spring Boot page)
        return http.build();
    }

    @Bean
    CorsConfigurationSource corsConfigurationSource(
            @Value("${app.cors.allowed-origins}") List<String> origins) {
        CorsConfiguration config = new CorsConfiguration();
        config.setAllowedOrigins(origins);
        config.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"));
        config.setAllowedHeaders(List.of("Authorization", "Content-Type"));
        config.setExposedHeaders(List.of("Location"));
        config.setAllowCredentials(true);            // needed only for cookie-based auth
        config.setMaxAge(3600L);

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/api/**", config);
        return source;
    }
}

Rules of thumb for the Java side:

  • List the exact origins (scheme + host + port, no trailing slash). The origin http://localhost:5173/ with a trailing slash never matches.
  • allowedOrigins("*") together with allowCredentials(true) is rejected by Spring (and by browsers). With credentials you must name origins explicitly, or use allowedOriginPatterns.
  • Read origins from properties, so development, staging and production differ without code changes.
  • If Spring Security is present and you only added addCorsMappings, preflights fail with 401/403. Always use .cors(...) in the security chain.
  • A controller-level @CrossOrigin(origins = "...") exists for quick tests, but a central configuration is cleaner.

The Vite dev proxy: avoiding CORS in development

Instead of allowing another origin, make the browser think the API is on the same origin. Vite's dev server can forward requests: the browser calls http://localhost:5173/api/... (same origin, so no CORS), and Vite passes them on to Spring Boot on port 8080 server-to-server, where CORS does not apply.

import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,        // sets the Host header to the target
      },
    },
  },
});
# With the proxy, use a relative base URL
VITE_API_URL=/api

The proxy works only with npm run dev; npm run build output has no proxy. In production use Nginx to proxy /api the same way (see deployment), or set the full API URL and configure CORS properly. Many teams do both: proxy in development, CORS or Nginx in production.

Reading a CORS problem in DevTools

  1. Open the Network tab. Find the failed request; a preflight shows as a separate OPTIONS line.
  2. If the OPTIONS response is 401/403/404, the server rejected the preflight (Spring Security not configured for CORS, or the path is not permitted).
  3. If it is 200 but the Console still complains, compare the response headers with the message: "origin not allowed" means a wrong or missing Allow-Origin; "header not allowed" means Allow-Headers misses Authorization or Content-Type; "method not allowed" means Allow-Methods misses PUT or DELETE.
  4. Test the API without the browser (Postman, curl). If it works there, the problem is CORS, not your controller.

Edge cases

  • A 500 error from the controller can also look like a CORS error: error responses created before the CORS filter applies may lack the headers, and the browser reports only "CORS". Check the server log and the Network tab response.
  • A wrong URL or the server not running also gives "Failed to fetch" / ERR_NETWORK, with no HTTP status. Do not assume CORS every time.
  • Cookies across origins need withCredentials: true (Axios) or credentials: 'include' (fetch) on the client and Allow-Credentials: true plus an explicit origin on the server, and SameSite/Secure cookie settings that allow cross-site use.
  • Multiple CORS configurations (a @CrossOrigin, a gateway, and Nginx all adding headers) can produce duplicate Access-Control-Allow-Origin values, which browsers reject. Configure CORS in exactly one layer.

CORS is not security for your API

CORS only tells browsers what scripts may read. curl, Postman, scripts and other servers ignore it completely, so anyone can still call your API. Real protection is authentication, authorisation and validation on the server (Spring Security). Allow your real frontend origins only, and never reflect any origin back automatically.

Interview: "What is CORS? What is a preflight? How did you fix it?"

  • Origin = scheme + host + port. Browsers block scripts from reading cross-origin responses unless the server sends Access-Control-Allow-Origin (same-origin policy plus CORS).
  • Non-simple requests (JSON, Authorization, PUT/DELETE) trigger an OPTIONS preflight asking for allowed methods and headers.
  • Spring fix: CorsConfigurationSource bean plus .cors() in the security chain (or addCorsMappings without Security); origins from properties.
  • In dev, the Vite proxy removes the need. CORS is browser-only and is not an API security mechanism.

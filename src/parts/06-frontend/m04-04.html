The DOM: selecting and changing elements

The DOM is the live tree of objects the browser builds from your HTML; with querySelector you find elements, with textContent, attributes, classList and createElement you change them, and you must never put user text into innerHTML (XSS).

When the browser loads HTML, it builds a tree of objects in memory: the DOM (Document Object Model). The <html> element is the root, <body> is a child, and so on. JavaScript gets this tree through the global document object. When your code changes a DOM object, the browser immediately updates what the user sees. The DOM is not part of the JavaScript language but a browser API (see where JavaScript runs). The HTML you wrote in Module 1 is the starting point; the DOM is what it becomes at runtime, and it can differ from the source after your script has changed it.

Selecting elements

Use querySelector with any CSS selector (the same selectors from Module 2). It returns the first match or null. querySelectorAll returns a NodeList of all matches (empty if none), which supports forEach and for…of; use [...list] or Array.from(list) to get map/filter.

const title = document.querySelector("h1");              // first h1
const form = document.querySelector("#login-form");      // by id
const cards = document.querySelectorAll(".card");        // all with class "card"
const firstItem = document.querySelector("ul.menu li:first-child");
const byId = document.getElementById("login-form");      // faster, id only, no "#"

console.log(cards.length);                 // 3
const names = [...cards].map(c => c.dataset.name);
console.log(document.querySelector(".nothing")); // null — check before using it

// Searching inside one element only
const firstCard = cards[0];
const price = firstCard.querySelector(".price");

// Walking the tree
console.log(price.parentElement === firstCard);   // true
console.log(firstCard.children.length, firstCard.nextElementSibling);
console.log(price.closest(".card") === firstCard); // closest ancestor matching a selector

The older getElementsByClassName and getElementsByTagName return live collections that update when the page changes; querySelectorAll returns a fixed snapshot. Prefer querySelector(All) for everything.

Danger: innerHTML with user data is an XSS hole

XSS (cross-site scripting) happens when an attacker's text is run as code in other users' browsers. Comments, names, search terms, URL parameters and API data can all contain it. The script can read localStorage, call your API with the user's token and more. See Module 6 for the security side.

Wrong: user text becomes HTML

list.innerHTML += `<li>${userText}</li>`;

Right: build elements, set textContent

const li = document.createElement("li");
li.textContent = userText;
list.append(li);

If you must show rich HTML from users, sanitise it with a library such as DOMPurify. React escapes text by default, which is a major reason people use it.

const frag = document.createDocumentFragment();

Changing the DOM many times in a loop is slow, because the browser may recalculate the layout each time. Batch the changes (fragment, or build one string of trusted markup). Frameworks like React exist partly to do this batching for you.

DOMContentLoaded and script placement

Your script can touch only elements that already exist. With defer or type="module" the DOM is ready when the script runs. If you cannot use those, wait for the event:

document.addEventListener("DOMContentLoaded", () => {
  console.log("HTML parsed; images may still be loading");
});
window.addEventListener("load", () => console.log("everything loaded, images too"));

Edge cases and errors

  • TypeError: Cannot set properties of null (setting 'textContent'): the selector matched nothing (typo, wrong id, or script ran too early).
  • querySelector("#my id") or an id starting with a digit throws SyntaxError: '…' is not a valid selector; use getElementById or CSS.escape.
  • innerHTML += re-creates all existing children, which destroys their event listeners and input values.
  • NodeList has no map/filter; convert with spread first.
  • Each element is the same object everywhere: two querySelector calls for one element give === references.

In real projects

In React you almost never call querySelector: you describe the UI from state and React updates the DOM. Direct DOM code remains in small scripts, in non-React pages, in browser extensions and in the rare React escape hatch (useRef). Learning the DOM first shows you what React does for you.

Interview angle

  • "What is the DOM?" A tree of objects representing the page; the browser API through which JavaScript reads and changes it.
  • "textContent vs innerHTML?" Plain text (safe) vs parsed HTML (XSS risk with user data).
  • "querySelector vs getElementById?" Any CSS selector, first match or null; id only, slightly faster.
  • "NodeList vs array / live vs static?" Convert with spread; querySelectorAll is static.
  • "DOMContentLoaded vs load?" HTML parsed vs all resources loaded.

Events: listeners, bubbling, delegation and forms

An event is something that happens (click, input, submit); you react with addEventListener(type, handler), the event object describes it, events bubble up the tree so one listener on a parent can serve many children (delegation), and preventDefault() stops the browser default such as a form reload.

Browser programs are event-driven: you do not run top to bottom and finish; you register small functions and the browser calls them when the user clicks, types, scrolls, or when a timer or network response fires. A listener (or handler) is such a function. It is the same idea as a Swing ActionListener, without the interface.

const button = document.querySelector("#pay");

function handleClick(event) {
  console.log("clicked:", event.type, event.target.id);
}
button.addEventListener("click", handleClick);       // register
button.addEventListener("click", () => console.log("second listener")); // many allowed

button.removeEventListener("click", handleClick);    // needs the SAME function reference
button.addEventListener("click", () => {}, { once: true });  // run once, then auto-remove

Avoid the old styles button.onclick = fn (only one handler per event) and the HTML attribute onclick="…" (mixes code into markup).

The event object

The browser passes an event object to your handler. The useful parts:

  • event.type — the event name, e.g. "click".
  • event.target — the element that was actually clicked (maybe a child of what you listened on).
  • event.currentTarget — the element the listener is attached to (always the same as the element you called addEventListener on).
  • event.key, event.shiftKey — for keyboard events; event.clientX/Y for the mouse.
  • event.preventDefault() — cancel the browser's default action (following a link, submitting a form).
  • event.stopPropagation() — stop the event from travelling to parent elements.

Bubbling and capturing

An event does not stay on the element where it happened. It travels in three phases: first capturing (from window down to the target), then the target itself, then bubbling (from the target back up to window). Listeners run in the bubbling phase by default, so a click on a button also triggers the click listeners on its parent div, then body, and so on. Pass { capture: true } as the third argument to listen during the capturing phase (rare).

// HTML: <div id="card"><button id="buy">Buy</button></div>
document.querySelector("#card").addEventListener("click", () => console.log("card"));
document.querySelector("#buy").addEventListener("click", (e) => {
  console.log("button");
  // e.stopPropagation();   // would hide the click from "card"
});
// Click the button:  button, then card

Use stopPropagation() sparingly: it breaks code (analytics, dropdowns that close on an outside click) which relies on seeing the event.

Event delegation

Event delegation means putting one listener on a parent and using event.target to find which child was clicked. It has three benefits: fewer listeners (one instead of a hundred), items added later work automatically, and removing items leaves no stale listeners. It is the standard pattern for lists and tables.

const list = document.querySelector("#cart");

list.addEventListener("click", (event) => {
  const removeBtn = event.target.closest("button.remove");
  if (!removeBtn || !list.contains(removeBtn)) return;     // click was elsewhere

  const item = removeBtn.closest("li");
  console.log("removing", item.dataset.id);
  item.remove();
});

// Items added later also work — no new listener needed
const li = document.createElement("li");
li.dataset.id = "99";
li.innerHTML = '<span>Tea</span> <button class="remove">x</button>';   // fixed markup, no user data
list.append(li);

closest() matters: if the button contains an icon, event.target may be the icon, not the button. closest("button.remove") walks up from the target and finds the right element.

Forms

A form's default action on submit is to send a request and reload the page. A JavaScript app handles submit itself, calls event.preventDefault() and then works with the data. FormData reads all named fields at once.

// HTML:
// <form id="signup">
//   <input name="email" type="email" required>
//   <input name="age" type="number">
//   <p id="error"></p> <button>Join</button>
// </form>
const form = document.querySelector("#signup");
const error = document.querySelector("#error");

form.addEventListener("submit", (event) => {
  event.preventDefault();                       // stop the page reload
  const data = Object.fromEntries(new FormData(form));
  console.log(data);                            // { email: 'a@b.in', age: '21' } — strings!

  const age = Number(data.age);
  if (!data.email.includes("@") || Number.isNaN(age) || age < 18) {
    error.textContent = "Enter a valid email and an age of 18 or more.";
    return;
  }
  error.textContent = "";
  console.log("send to server", { email: data.email, age });
  form.reset();
});

document.querySelector('input[name="email"]').addEventListener("input", (e) => {
  console.log("typing:", e.target.value);       // live
});

HTML5 validation attributes (required, type="email", min, pattern) run before the submit event; see Module 1. Always validate again on the server (Bean Validation in Spring Boot): browser checks are for user comfort only, not security.

Keyboard and debouncing

Typing into a live-search box fires input on every key. Sending one API call per key is wasteful. A debounce waits until the user pauses. It uses a closure for the timer id (see closures).

function debounce(fn, delayMs) {
  let timerId;
  return (...args) => {
    clearTimeout(timerId);
    timerId = setTimeout(() => fn(...args), delayMs);
  };
}
const search = debounce((text) => console.log("searching for", text), 300);
document.querySelector("#q").addEventListener("input", (e) => search(e.target.value));

document.addEventListener("keydown", (e) => {
  if (e.key === "Escape") console.log("close the dialog");
  if (e.ctrlKey && e.key === "k") { e.preventDefault(); console.log("open search"); }
});

Rule: remove listeners you add to long-lived targets

A listener on window or document lives until you remove it, and keeps everything its closure uses in memory. Add it in setup and remove it in cleanup. In React, useEffect returns a cleanup function for exactly this.

Edge cases

  • this inside a normal-function handler is the element (currentTarget); inside an arrow function it is not. See this.
  • focus, blur and scroll do not bubble to parents (use focusin/focusout for delegation).
  • A <button> inside a form defaults to type="submit"; use type="button" for non-submit buttons.
  • Passive listeners: for touchstart/wheel the browser may ignore preventDefault() unless you say { passive: false }.
  • A checkbox's state is checked (boolean), not value.

Common mistake: forgetting preventDefault, and the wrong listener type

Wrong: page reloads, state lost

form.addEventListener("submit", () => {
  saveOrder();            // runs, then the page reloads
});
btn.addEventListener("click", save());  // called immediately

Right

form.addEventListener("submit", (e) => {
  e.preventDefault();
  saveOrder();
});
btn.addEventListener("click", save);

Interview angle

  • "What is event bubbling? Capturing?" Events travel down then up the tree; listeners default to the bubbling phase.
  • "What is event delegation and why use it?" One parent listener + event.target/closest; fewer listeners, works for dynamic items.
  • "target vs currentTarget?" The element clicked vs the element the listener is on.
  • "preventDefault vs stopPropagation?" Cancel the default action vs stop the event travelling.
  • "Debounce vs throttle?" Run after a pause vs at most once per interval.

A complete example: a to-do list with the DOM

One page ties the DOM and events together: a form adds tasks, a delegated listener toggles and deletes them, and a single render() function draws the whole list from an array — the same "state in, UI out" idea that React uses.

This example uses no libraries. The important design choice is to keep the data in an array (the state) and to have one function that redraws the list from that array. Handlers change the array and call render(); they never patch the DOM by hand. That keeps data and screen from drifting apart. Saving the tasks to localStorage is added in Storage and in the practice exercises.

let tasks = [

let nextId = 3;

const list = document.querySelector("#task-list");

// ---- Render: draw the list from the state ----
function render() {
  list.replaceChildren();                       // clear the old list

  for (const task of tasks) {
    const li = document.createElement("li");
    li.dataset.id = task.id;
    li.classList.toggle("done", task.done);

    const checkbox = document.createElement("input");
    checkbox.type = "checkbox";
    checkbox.checked = task.done;
    checkbox.setAttribute("aria-label", `Mark "${task.text}" as done`);

    const label = document.createElement("span");
    label.textContent = task.text;              // textContent: safe against XSS

    const remove = document.createElement("button");
    remove.type = "button";
    remove.className = "remove";
    remove.textContent = "Delete";

    li.append(checkbox, label, remove);
    list.append(li);
  }

  const left = tasks.filter(t => !t.done).length;
  summary.textContent = `${left} of ${tasks.length} tasks left`;
}

// ---- Actions: change the state, then render ----
function addTask(text) {
  tasks = [...tasks, { id: nextId++, text, done: false }];
  render();
}
function toggleTask(id) {
  tasks = tasks.map(t => (t.id === id ? { ...t, done: !t.done } : t));
  render();
}
function deleteTask(id) {
  tasks = tasks.filter(t => t.id !== id);
  render();
}

// ---- Events ----
form.addEventListener("submit", (event) => {
  event.preventDefault();
  const text = input.value.trim();
  if (text === "") return;                      // ignore blank tasks
  addTask(text);
  input.value = "";
  input.focus();
});

// One delegated listener for every checkbox and delete button
list.addEventListener("click", (event) => {
  const li = event.target.closest("li");
  if (!li) return;
  const id = Number(li.dataset.id);             // dataset values are strings

  if (event.target.matches("input[type=checkbox]")) toggleTask(id);
  if (event.target.matches("button.remove")) deleteTask(id);
});

How it works, step by step

  1. The script is loaded with defer, so the form and list exist when the code runs.
  2. render() clears the list and creates one li per task. Text is set with textContent, so a task named <script> is shown as text and not run.
  3. Submitting the form calls preventDefault(), trims the text, adds a new task object to a new array, and redraws.
  4. The list has one click listener. event.target.closest("li") finds the row, dataset.id tells us which task, and matches() decides whether it was the checkbox or the Delete button.
  5. toggleTask and deleteTask create new arrays with map and filter instead of editing items in place.

From this to React

Look at what React will remove: the manual createElement code, the clearing and redrawing, and the element lookups. In React you write the tasks.map(...) part as JSX and call setTasks(...); React updates only the changed DOM nodes. The state array, the map/filter updates and the immutable style stay exactly the same. See Module 5.

Limits of this version

  • render() destroys and rebuilds every row; a text field being edited in a row would lose focus. Fine for a small list.
  • Ids come from a counter that restarts when the page reloads. With stored tasks, compute nextId from the maximum stored id.
  • Editing a task, filters (all/active/done) and drag-and-drop are good extensions: add them as exercises.

Interview angle

  • "Build a to-do list live." State array + render() + delegation + preventDefault; mention textContent for safety and immutability for easy testing.
  • "Why delegate?" New rows get handlers for free; one listener instead of many.
  • "Why does the id from dataset need Number()?" Dataset values are always strings, so "2" === 2 would fail.

The this keyword and how it is decided

In JavaScript this is not fixed to an object like in Java; it is decided by how a function is called — as a method (the object before the dot), as a plain function (undefined in strict mode), with new, with call/apply/bind — and arrow functions simply use the this of the code around them.

In Java, this always means the current instance, and you cannot lose it. In JavaScript a function does not belong to an object. Passing it somewhere else, or calling it differently, gives it a different this. This is the most common source of confusing bugs for Java developers, and a favourite interview topic. The good news: there are only a few rules. To find this, look at the call site, not at where the function was written (except for arrow functions).

The rules, in order of priority

  1. new call: new Cart() — this is the new object being created.
  2. Explicit binding: fn.call(obj), fn.apply(obj), fn.bind(obj)() — this is obj.
  3. Method call: obj.method() — this is obj, the thing left of the dot at call time.
  4. Plain call: fn() — this is undefined in strict mode (modules, classes) and window in sloppy mode.
  5. Arrow function: has no this of its own; it uses the this of the surrounding code where it was written, and none of the rules above can change it.
"use strict";
const cart = {
  owner: "Asha",
  show() { return this?.owner; },          // normal method
  showArrow: () => this?.owner,            // arrow: "this" of the module top level
};

console.log(cart.show());        // "Asha"       — method call, this = cart
console.log(cart.showArrow());   // undefined    — arrow ignores cart

const loose = cart.show;         // copy the function out of the object
console.log(loose());            // undefined    — plain call, this = undefined (strict)

function who() { return this?.name; }
console.log(who.call({ name: "Ravi" }));     // "Ravi"
console.log(who.apply({ name: "Meera" }));   // "Meera"
const bound = who.bind({ name: "Kabir" });
console.log(bound());                         // "Kabir"
console.log(bound.call({ name: "Other" }));   // "Kabir" — bind cannot be overridden
MethodWhen it runsArguments
fn.call(thisArg, a, b)ImmediatelyListed one by one
fn.apply(thisArg, [a, b])ImmediatelyIn an array
fn.bind(thisArg, a)Later — returns a new function with this fixedCan pre-fill the first arguments

Losing this: the classic bug

Passing a method as a callback passes only the function; the object before the dot is left behind. The caller (for example setTimeout) then makes a plain call.

"use strict";
class Timer {
  constructor() { this.seconds = 0; }
  tick() { this.seconds++; console.log(this.seconds); }
}
const t = new Timer();

setTimeout(t.tick, 0);                 // TypeError: Cannot read properties of undefined
                                       // (reading 'seconds')   — this is undefined
setTimeout(() => t.tick(), 0);         // 1 — arrow calls it as a method
setTimeout(t.tick.bind(t), 0);         // 2 — bind fixes this

Three fixes: wrap the call in an arrow function (most common), use bind, or define the method as an arrow function class field, tick = () => { … }, so each instance keeps its own bound version (this is common in older React class components).

Arrow functions fix this inside callbacks

A normal function inside a method has its own this, which is not the method's. An arrow function inside the method uses the method's this.

"use strict";
const team = {
  name: "Backend",
  members: ["Asha", "Ravi"],
  listBad() {
    this.members.forEach(function (m) {
      console.log(this?.name, m);        // this is undefined here
    });
  },
  listGood() {
    this.members.forEach((m) => {
      console.log(this.name, m);         // arrow keeps the method's this
    });
  },
};
team.listBad();    // undefined Asha / undefined Ravi
team.listGood();   // Backend Asha / Backend Ravi

That is why the rule of thumb is: object and class methods are normal methods; callbacks inside them are arrows. Do not write an object method as an arrow (showArrow above), because it cannot see the object.

this in event handlers

For a normal-function handler, the browser calls it with this set to the element (same as event.currentTarget). In an arrow handler, this is the outer this (usually undefined in a module). Use event.currentTarget instead and the question disappears.

button.addEventListener("click", function () {
  console.log(this === button);              // true
});
button.addEventListener("click", () => {
  console.log(this === button);              // false
});
button.addEventListener("click", (e) => console.log(e.currentTarget === button)); // true

this at the top level and in functions called with new

At the top level of a module this is undefined; in a classic script it is window; in Node's CommonJS files it is module.exports. A function called with new acts as a constructor (see classes and prototypes); forgetting new then runs it as a plain call, where this is undefined in strict mode, and this.name = … throws TypeError.

Rule: ask "how was it called?"

Do not look at where a regular function is written; look at the call. a.b.fn() has this = a.b. fn() has no object. For arrow functions only, look at where they are written.

Edge cases

  • (obj.method)() keeps this; (0, obj.method)() and const f = obj.method; f() lose it.
  • call/apply/bind have no effect on the this of an arrow function.
  • In sloppy mode, call(null) makes this the global object; in strict mode it stays null.
  • Class bodies are always strict, so extracting a class method and calling it gives undefined, not window.

Common mistake: arrow function as an object or class method

Wrong: no access to the object

const counter = {
  count: 0,
  inc: () => { this.count++; }   // this is not counter
};

Right: method shorthand

const counter = {
  count: 0,
  inc() { this.count++; }
};

Interview angle

  • "What is this in JavaScript?" A value decided at call time: new > call/apply/bind > method call > plain call; arrows take it lexically.
  • "call vs apply vs bind?" Run now with listed args / run now with an array / return a new bound function.
  • "Why does setTimeout(obj.method, 0) fail?" The method is detached and called plainly; wrap in an arrow or bind.
  • "How are arrow functions different?" No own this, arguments or new.

Classes, prototypes and inheritance

The class keyword gives JavaScript a Java-like syntax (constructor, methods, static, getters, #private, extends/super), but underneath, objects inherit from other objects through the prototype chain — classes are just a cleaner way to set that up.

Since ES2015, JavaScript has a class syntax that looks very much like Java. It is popular in Node.js back ends and in custom error types. In modern React you write function components and rarely use classes, but interviews ask about them, and libraries use them. Remember one fact above all: a JavaScript class is not a blueprint that is copied into every object like in Java. It is a function that creates objects linked to a shared prototype object.

Classes

class BankAccount {
  #balance = 0;                       // private field (real privacy, # is part of the name)
  static bankName = "Desi Bank";      // static field: belongs to the class
  owner;                              // public field

  constructor(owner, openingPaise = 0) {
    this.owner = owner;
    this.#balance = openingPaise;
  }

  deposit(paise) {
    if (paise <= 0) throw new RangeError("Deposit must be positive");
    this.#balance += paise;
    return this;                      // allows chaining
  }

  get balance() { return this.#balance; }          // getter: used like a property
  set balance(v) { throw new Error("Use deposit()"); }

  static compare(a, b) { return a.balance - b.balance; }   // static method

  toString() { return `${this.owner}: ₹${this.#balance / 100}`; }
}

const acc = new BankAccount("Asha", 50_000);
acc.deposit(10_000).deposit(500);
console.log(acc.balance);             // 60500   (getter, no brackets)
console.log(`${acc}`);                // Asha: ₹605
console.log(BankAccount.bankName);    // "Desi Bank"
console.log(acc.#balance);            // SyntaxError — private outside the class
console.log(typeof BankAccount);      // "function" — a class is a function

Inheritance with extends and super

class Employee {
  constructor(name, salary) {
    this.name = name;
    this.salary = salary;
  }
  describe() { return `${this.name} earns ${this.salary}`; }
}

class Manager extends Employee {
  constructor(name, salary, reports) {
    super(name, salary);              // must come before using "this"
    this.reports = reports;
  }
  describe() {                        // overrides the parent method
    return `${super.describe()} and manages ${this.reports.length} people`;
  }
}

const m = new Manager("Meera", 150000, ["Asha", "Ravi"]);
console.log(m.describe());            // Meera earns 150000 and manages 2 people
console.log(m instanceof Manager, m instanceof Employee); // true true

If a subclass has a constructor, it must call super(...) before it touches this, otherwise: ReferenceError: Must call super constructor in derived class before accessing 'this'. Custom errors extend Error the same way (see error handling).

Prototypes: what is really happening

Every object has a hidden link to another object, its prototype (readable with Object.getPrototypeOf(obj); the old name is __proto__). When you read obj.prop, the engine looks at the object itself; if the property is missing, it follows the link to the prototype, then that object's prototype, and so on until null. This path is the prototype chain. It is how [1,2].map works: the array itself has no map, but Array.prototype has it.

// Before 2015: constructor function + prototype (what "class" compiles to conceptually)
function Animal(name) { this.name = name; }
Animal.prototype.speak = function () { return `${this.name} makes a sound`; };

const dog = new Animal("Tommy");
console.log(dog.speak());                                   // Tommy makes a sound
console.log(Object.getPrototypeOf(dog) === Animal.prototype); // true
console.log(dog.hasOwnProperty("speak"));                   // false — it lives on the prototype
console.log("speak" in dog);                                // true

// Object.create: make an object with a chosen prototype
const base = { greet() { return "hi " + this.name; } };
const child = Object.create(base);
child.name = "Asha";
console.log(child.greet());                                 // "hi Asha"

// Methods are shared: one copy for all instances
const d2 = new Animal("Bruno");
console.log(dog.speak === d2.speak);                        // true

Methods defined in a class body are placed on the prototype once and shared by all instances (memory efficient), while fields and this.x = … assignments are per instance. Arrow-function class fields (tick = () => …) are per instance, so each object gets its own copy.

Prototype vs Java classes

  • Java copies nothing at runtime: the class is fixed. In JavaScript you can add a method to a prototype at any time, and every existing object sees it. Do not modify built-in prototypes (Array.prototype.myMethod = …): it can break libraries.
  • Java has multiple interface inheritance; JavaScript has single prototype inheritance. For shared behaviour, use composition: call helper functions or put objects inside objects. Many JavaScript teams prefer composition over deep class hierarchies.
  • Plain objects need no class at all: { name: "Asha" } is the normal way to hold data.

Convention

  • Class names in PascalCase, one class per file, export default class or a named export.
  • Use #private for internals instead of an underscore name.
  • Prefer simple objects and functions; reach for a class when you need many instances with shared behaviour or custom Error types.

Edge cases

  • Classes are not hoisted like functions: using a class before its declaration gives ReferenceError (temporal dead zone).
  • A getter without a setter ignores writes in sloppy mode and throws TypeError in strict mode (class code is strict).
  • Methods are not bound: const f = acc.deposit; f(5) loses this (see this).
  • Private fields do not appear in Object.keys or JSON.stringify; getters on the prototype are not serialised either.
  • Instance fields are created before the constructor body in a base class but after super() in a subclass.

Common mistake: forgetting new, forgetting super

Wrong

const e = Employee("A", 100);   // TypeError: Class
                                // constructor cannot be
                                // invoked without 'new'
class M extends Employee {
  constructor() { this.x = 1; } // ReferenceError: super
}                               // must be called first

Right

const e = new Employee("A", 100);
class M extends Employee {
  constructor(n, s) {
    super(n, s);
    this.x = 1;
  }
}

Interview angle

  • "What is the prototype chain?" Each object links to a prototype; lookups walk the links up to null.
  • "Are JavaScript classes real classes?" They are syntax over constructor functions and prototypes; typeof Class is "function".
  • "What does new do?" Creates an empty object linked to the constructor's prototype, runs the constructor with this as that object, returns it.
  • "How do you make a private field?" #name in a class; closures for plain objects.
  • "hasOwnProperty vs in?" Own property only vs including the prototype chain.

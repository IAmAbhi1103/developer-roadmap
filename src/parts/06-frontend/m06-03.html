Loading and error states: network vs 4xx vs 5xx, spinners, toasts

Every API call can be loading, succeeded, empty or failed; a good UI shows a clear face for each, tells a network failure apart from a 4xx (your request was wrong) and a 5xx (the server broke), and never leaves the user staring at a spinner or a blank page.

The states of one request

When a component asks the Spring Boot API for data, the screen is in one of four situations. Beginners code only the happy one. Real apps handle all four:

  • Loading: the request is in flight. Show a spinner or a skeleton.
  • Error: the request failed. Say what happened and offer a way forward (retry, go back, log in again).
  • Empty: the request worked but the list has zero items. This is not an error. Show "No employees yet" and a button to add one.
  • Data: the normal screen.

Not all errors are the same

The first question is: did the server answer at all? With Axios, a failed call throws an error. If the server answered with a status such as 404 or 500, error.response exists. If the request never got an answer (server down, no internet, CORS block, timeout), error.response is undefined. That single check splits "network problem" from "server answered with a problem".

Why the difference matters: retrying a 404 or a 400 is pointless because the same request will fail the same way. Retrying a network blip or a 503 often works. Showing "Server error" when the user simply lost Wi-Fi sends them to the wrong place.

One place to classify errors

Do not scatter err.response?.status === 404 checks across components. Write one helper that turns any thrown value into a small object the UI understands.

import axios from 'axios';

const fail = (kind, status, message, retryable) => ({ kind, status, message, retryable });

export function classifyError(err) {
  if (axios.isCancel(err)) {
    return { kind: 'canceled', status: null, message: '', retryable: false };
  }
  if (!err.response) {                       // the server never answered
    const timeout = err.code === 'ECONNABORTED' || err.code === 'ETIMEDOUT';
    return {
      kind: timeout ? 'timeout' : 'network',
      status: null,
      message: timeout
        ? 'The server took too long to respond. Please try again.'
        : 'Cannot reach the server. Check your internet connection.',
      retryable: true,
    };
  }

  const { status, data } = err.response;
  // Spring Boot ProblemDetail has "detail"; fall back to "message"
  const serverText = typeof data?.detail === 'string' ? data.detail : data?.message;

  if (status === 401) return fail('auth', status, 'Please log in again.', false);
  if (status === 403) return fail('forbidden', status, 'You do not have access to this.', false);
  if (status === 404) return fail('not-found', status, serverText ?? 'Not found.', false);
  if (status === 429) return fail('rate-limit', status, 'Too many requests. Try again soon.', true);
  if (status >= 500) {
    return fail('server', status, 'Something went wrong on our side. Please try again.', true);
  }
  return fail('client', status, serverText ?? 'The request was not accepted.', false);
}

// Short text for banners and toasts
export function describeError(err) {
  return classifyError(err).message;
}

Rule: never show raw server internals

For 5xx responses show your own friendly sentence, not err.message or the response body. Raw text such as "Request failed with status code 500" is meaningless to users, and a leaked stack trace or SQL message helps attackers. Log the details to the console (or an error-tracking tool) instead. Spring Boot should not send stack traces in production responses either.

The loading state, by hand

This is the pattern from the useEffect articles in Module 5, now with a real API call. Three pieces of state and a finally that always clears the loading flag.

import { useEffect, useState } from 'react';
import { api } from '../lib/axios.js';
import { classifyError } from '../lib/errors.js';

function EmployeeListSimple() {
  const [employees, setEmployees] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);
  const [attempt, setAttempt] = useState(0);            // bump to retry

  useEffect(() => {
    const controller = new AbortController();
    setLoading(true);
    setError(null);
    api.get('/employees', { signal: controller.signal })
      .then(({ data }) => setEmployees(data.content))
      .catch((err) => {
        const info = classifyError(err);
        if (info.kind !== 'canceled') setError(info);
      })
      .finally(() => {
        if (!controller.signal.aborted) setLoading(false);
      });
    return () => controller.abort();                   // cleanup: cancel the old request
  }, [attempt]);

  if (loading) return <p>Loading employees…</p>;
  if (error) {
    return (
      <div role="alert">
        <p>{error.message}</p>
        {error.retryable && <button onClick={() => setAttempt((n) => n + 1)}>Try again</button>}
      </div>
    );
  }
  if (employees.length === 0) return <p>No employees yet.</p>;
  return <ul>{employees.map((e) => <li key={e.id}>{e.name}</li>)}</ul>;
}

export default EmployeeListSimple;

This works, but you need the same 25 lines on every page. That is why most teams use TanStack Query (Module 5), which keeps these states for you.

The same with TanStack Query

import { useQuery } from '@tanstack/react-query';

function EmployeeListQuery() {
  const query = useQuery({
    queryKey: ['employees'],
    queryFn: async () => (await api.get('/employees')).data,
  });

  return (
    <QueryState query={query} isEmpty={query.data?.content.length === 0}>

    </QueryState>

}
import { classifyError } from '../lib/errors.js';
import { Spinner } from './Spinner.jsx';

export function QueryState({ query, isEmpty, emptyMessage = 'Nothing here yet.', skeleton, children }) {
  if (query.isPending) return skeleton ?? <Spinner />;
  if (query.isError) {
    const info = classifyError(query.error);
    return (
      <div role="alert" className="error-box">
        <p>{info.message}</p>
        {info.retryable && <button onClick={() => query.refetch()}>Try again</button>}
      </div>
    );
  }
  if (isEmpty) return <p className="empty">{emptyMessage}</p>;
  return children;
}

Two flags to tell apart: isPending is true only when there is no data yet (first load), while isFetching is true whenever a request runs, including a background refresh. Use isPending for the big spinner and isFetching for a small "refreshing…" indicator, otherwise the screen flashes every time the user returns to the tab.

TanStack Query version names

In TanStack Query v5 the first-load flag is isPending and mutations use isPending too. Older v4 code and many older tutorials use isLoading for this. If a tutorial's code behaves differently, check which major version it targets.

Retries: do not retry what cannot succeed

TanStack Query retries a failed query a few times by default, which is good for network blips and bad for a 404 (the user waits several seconds for a result that will never change). Give it a function that retries only when it makes sense:

import { QueryCache, QueryClient } from '@tanstack/react-query';
import toast from 'react-hot-toast';
import { classifyError } from './lib/errors.js';

export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30_000,
      retry: (failureCount, error) => classifyError(error).retryable && failureCount < 2,
    },
  },
  queryCache: new QueryCache({
    // Runs once per failed query. Only toast for background refreshes: when data is on screen
    // already, the user would otherwise never learn the refresh failed.
    onError: (error, query) => {
      if (query.state.data !== undefined) toast.error(classifyError(error).message);
    },
  }),
});

Toasts

A toast is a small message that appears for a few seconds in a corner and then goes away. Use toasts for results of actions that do not have a natural place on the page: "Employee deleted", "Saved", "Could not delete: server error". Do not use them for form validation (errors belong next to the field) or for failures the user must act on (use a visible banner). react-hot-toast and sonner are two popular small libraries; the example below uses react-hot-toast.

// main.jsx: render the container once
import { Toaster } from 'react-hot-toast';
// <Toaster position="top-right" /> next to <App />

// anywhere:
import toast from 'react-hot-toast';

  mutationFn: (id) => api.delete(`/employees/${id}`),
  onSuccess: () => {
    toast.success('Employee deleted');
    queryClient.invalidateQueries({ queryKey: ['employees'] });
  },
  onError: (err) => toast.error(describeError(err)),
});

Error boundaries: a different kind of error

A bug in a component, such as reading user.name when user is null, throws during rendering and, left alone, blanks the whole page. An error boundary is a component that catches errors thrown while its children render and shows a fallback instead. It does not catch errors in event handlers, async code or fetch/Axios failures; those you handle with try/catch and the patterns above. React supports boundaries only as class components, so most projects use the small react-error-boundary package and wrap the app (or each route) once.

Common mistakes

  • Swallowing errors: .catch(() => {}) or only console.log(err). The user sees an empty list and thinks there is no data.
  • Forgetting finally: setLoading(false) only in .then, so a failed call leaves the spinner forever.
  • Treating empty as error (or the reverse): an empty array is a success.
  • Rendering error.message directly (Axios text like "Network Error").
  • Trusting a 200 status for everything: some APIs return 200 with an error body. Your own Spring Boot API should use proper status codes, and the frontend should rely on them.
  • Toast spam: a toast for every failed refetch plus a banner plus a log. Pick one place per error.

Edge cases

  • A 204 No Content response (typical for DELETE) has no body; data is empty. Do not call data.id on it.
  • A CORS block looks like a network error in JavaScript (no response). Open the Network tab and the console to tell them apart: see CORS.
  • A request cancelled by AbortController throws too; classify it as canceled and show nothing.
  • If the API gateway or Nginx answers with an HTML error page (502, 504), data is a string, not JSON. Read data?.detail safely, as above.

Interview: "How do you handle errors from an API call in React?"

  • Model the states: loading, error, empty, data. Use try/catch/finally or a query library so loading always ends.
  • Separate network errors (no response), 4xx (client; show message or field errors) and 5xx (server; friendly message, retry). Do not retry 4xx.
  • Centralise: an Axios interceptor for 401, one error classifier, a shared QueryState component, toasts for action results, an error boundary for render crashes.

Showing backend validation errors on form fields (ProblemDetail)

When Spring Boot rejects a form with 400, send back a ProblemDetail that includes a field-to-message map; the React form reads that map and shows each message under the right input, so the server stays the single source of truth for rules.

Why the server's validation must reach the screen

Client-side checks (required, a regex, "password at least 8 characters") give instant feedback, but they are only a convenience: anyone can bypass the browser and call your API with curl. The backend therefore validates again with Bean Validation (@NotBlank, @Email, @Positive and so on; see Spring Boot · Module 2). Some rules also exist only on the server, such as "this email is already registered". The frontend must show those messages properly instead of a vague "Request failed".

What Spring Boot sends back

ProblemDetail is Spring's class for the standard error format of RFC 7807 (later RFC 9457), sent with the media type application/problem+json. The standard members are type, title, status, detail and instance. You can add your own members; Spring writes them at the top level of the JSON. The code below returns the field errors in an errors member.

import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.util.LinkedHashMap;
import java.util.Map;

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail handleValidation(MethodArgumentNotValidException ex) {
        Map<String, String> errors = new LinkedHashMap<>();
        ex.getBindingResult().getFieldErrors().forEach(fe ->
                errors.putIfAbsent(fe.getField(), fe.getDefaultMessage()));

        ProblemDetail pd = ProblemDetail.forStatusAndDetail(
                HttpStatus.BAD_REQUEST, "One or more fields are invalid");
        pd.setTitle("Validation failed");
        pd.setProperty("errors", errors);
        return pd;
    }

    @ExceptionHandler(DuplicateEmailException.class)
    public ProblemDetail handleDuplicate(DuplicateEmailException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, ex.getMessage());
        pd.setTitle("Duplicate email");
        pd.setProperty("errors", Map.of("email", "This email is already registered"));
        return pd;
    }
}
{
  "type": "about:blank",
  "title": "Validation failed",
  "status": 400,
  "detail": "One or more fields are invalid",
  "instance": "/api/employees",
  "errors": {
    "email": "must be a well-formed email address",
    "salary": "must be greater than 0"

ProblemDetail in Spring Boot 3.x and 4.x

ProblemDetail arrived with Spring Framework 6 (Boot 3) and is the same idea in Framework 7 (Boot 4). Extending ResponseEntityExceptionHandler makes Spring's own MVC exceptions (bad JSON, wrong method, missing parameter) come back as problem details; if you extend it, override handleMethodArgumentNotValid instead of adding a second @ExceptionHandler for the same exception (two handlers for the same exception cause an ambiguity error at startup). Boot also has a property to switch problem details on for the default handling; check the reference for your exact version. The errors member is a convention of this project, not part of the standard, so agree on it with the backend developer (probably you).

Reading the response in React

Add a helper next to classifyError that returns a plain object from field name to message. It returns an empty object when the error is not a field error, so callers can fall back to a general message.

// { email: 'must be a well-formed email address', salary: '...' }
export function getFieldErrors(err) {
  const errors = err?.response?.data?.errors;
  if (errors && typeof errors === 'object' && !Array.isArray(errors)) return errors;
  return {};
}

export function hasFieldErrors(err) {
  return Object.keys(getFieldErrors(err)).length > 0;
}

A reusable field component

Put the label, the input and the error message in one component so every form shows errors the same, accessible way. aria-invalid and aria-describedby let screen readers announce the message with the field.

import { useId } from 'react';

export function TextField({ label, name, error, ...inputProps }) {
  const id = useId();

  return (

      <input

        {...inputProps}
      />
      {error && <p id={errorId} className="field-error">{error}</p>}
    </div>
  );
}

The form: client rules, then server rules

import { useState } from 'react';
import { TextField } from './TextField.jsx';
import { describeError, getFieldErrors, hasFieldErrors } from '../lib/errors.js';

const EMPTY = { name: '', email: '', department: '', salary: '' };

function validateClient(values) {
  const errors = {};
  if (!values.name.trim()) errors.name = 'Name is required';
  if (!/^\S+@\S+\.\S+$/.test(values.email)) errors.email = 'Enter a valid email';
  if (!(Number(values.salary) > 0)) errors.salary = 'Salary must be greater than 0';
  return errors;
}

export function EmployeeForm({ initial = EMPTY, onSubmit, submitLabel = 'Save' }) {
  const [values, setValues] = useState(initial);
  const [errors, setErrors] = useState({});          // field name -> message
  const [formError, setFormError] = useState(null);  // message not tied to a field
  const [submitting, setSubmitting] = useState(false);

  function handleChange(e) {
    const { name, value } = e.target;
    setValues((v) => ({ ...v, [name]: value }));
    setErrors((prev) => ({ ...prev, [name]: undefined }));  // clear this field's error on typing
  }

  async function handleSubmit(e) {
    e.preventDefault();
    const clientErrors = validateClient(values);
    setErrors(clientErrors);
    setFormError(null);
    if (Object.keys(clientErrors).length > 0) return;     // do not call the API

    setSubmitting(true);
    try {
      await onSubmit({ ...values, salary: Number(values.salary) });
    } catch (err) {
      if (hasFieldErrors(err)) setErrors(getFieldErrors(err));  // server said which fields
      else setFormError(describeError(err));                    // network, 5xx, ...
    } finally {
      setSubmitting(false);
    }
  }

  return (
    <form onSubmit={handleSubmit} noValidate>
      {formError && <p role="alert" className="form-error">{formError}</p>}
      <TextField label="Name" name="name" value={values.name}
                 onChange={handleChange} error={errors.name} />
      <TextField label="Email" name="email" type="email" value={values.email}
                 onChange={handleChange} error={errors.email} />
      <TextField label="Department" name="department" value={values.department}
                 onChange={handleChange} error={errors.department} />
      <TextField label="Salary" name="salary" type="number" value={values.salary}
                 onChange={handleChange} error={errors.salary} />
      <button type="submit" disabled={submitting}>
        {submitting ? 'Saving…' : submitLabel}
      </button>
    </form>
  );
}

Notes on the choices: noValidate switches off the browser's own bubbles so that your messages are the only ones; the field name must be exactly the Java record component name (email, not emailAddress), because the server's keys come from fe.getField(); and the submit handler throws errors up to onSubmit's caller so the form decides how to show them.

The same with React Hook Form

If you use React Hook Form (Module 5), server errors are pushed into the form with setError. The field then behaves exactly like one that failed client validation.

const { register, handleSubmit, setError, formState: { errors, isSubmitting } } = useForm();

const onSubmit = async (values) => {
  try {
    await createEmployee(values);
  } catch (err) {
    const fieldErrors = getFieldErrors(err);
    Object.entries(fieldErrors).forEach(([field, message]) => {
      setError(field, { type: 'server', message });
    });
    if (Object.keys(fieldErrors).length === 0) {
      setError('root.server', { message: describeError(err) });
    }
  }
};

Conventions

  • Show client-side errors on submit (and on blur), then clear each field's error as soon as the user edits it.
  • Keep the user's input. Never reset the form after a failed submit.
  • Move focus to the first invalid field or to the error summary so keyboard and screen-reader users find it.
  • Duplicate rules (client and server) only for fast feedback. The server is the authority.
  • Use the status code to decide the kind of error: 400 or 409 with errors means "show on fields"; anything else means "show a general message".

Edge cases

  • Nested and list fields: Spring reports address.city or items[0].quantity as the field path. Your form must use the same keys, or map them.
  • Class-level rules (for example "end date after start date") produce object errors, not field errors. Put them under a key such as global or return them in detail and show them as the form error.
  • Several rules fail on one field (blank and too short): the handler above keeps the first with putIfAbsent. Return a list per field if you want to show all.
  • Malformed JSON or wrong types (a string in a number field) make Spring throw HttpMessageNotReadableException, a 400 without field errors. Your form falls back to the general message.
  • Messages are English by default. For other languages use message bundles on the server or map error codes to text on the client.

Common mistakes

  • Showing only err.message ("Request failed with status code 400") and losing the server's field errors.
  • Form field names that differ from the DTO property names, so messages never match an input.
  • Not clearing old server errors when the user retypes, so a stale red message stays.
  • Returning 200 with { success: false } instead of 400. Use real status codes.
  • Validating only in the browser and assuming it is safe.

Interview: "How do you display backend validation errors?"

  • Backend: @Valid on the request body, a @RestControllerAdvice turns MethodArgumentNotValidException into a 400 ProblemDetail with a field-to-message map.
  • Frontend: in the catch block, read error.response.data.errors, store it in state keyed by field name and render each message beside its input; fall back to a general message for other failures.
  • Both sides validate: the client for speed, the server for safety.

Pagination UI and optimistic updates

Ask Spring Data for one page at a time with page and size parameters, keep the current page in the URL, render controls from the response's totals, and use optimistic updates only for quick, low-risk actions you can roll back.

Why paginate

A table with 50,000 rows must not be sent to the browser in one response. It is slow to download, heavy to render and wasteful in the database. Pagination returns a small slice (a page) per request. Spring Data supports this directly with Pageable (see Spring Boot · Module 3).

The backend contract

Spring MVC turns the query string ?page=0&size=10&sort=name,asc into a Pageable. Page numbers start at 0. The repository returns a Page<T>, which knows the content and the totals.

public record PageResponse<T>(List<T> content, int page, int size,
                              long totalElements, int totalPages) {
    public static <T> PageResponse<T> from(Page<T> p) {
        return new PageResponse<>(p.getContent(), p.getNumber(), p.getSize(),
                p.getTotalElements(), p.getTotalPages());
    }
}

@GetMapping("/api/employees")
public PageResponse<EmployeeDto> list(@RequestParam(defaultValue = "") String q,
                                      @PageableDefault(size = 10, sort = "name") Pageable pageable) {
    return PageResponse.from(employeeService.search(q, pageable).map(EmployeeDto::from));
}

Serialising Page directly

If a controller returns a Spring Data Page object itself, the JSON contains many fields (pageable, sort, first, last, numberOfElements…). Newer Spring Data versions warn about serialising the default implementation directly and offer a DTO-style output with the totals nested under a page object. Because the shape can differ between versions and settings, a small PageResponse record of your own, as above, gives the frontend a stable contract. Always look at the real JSON in the Network tab before writing the TypeScript or JavaScript that reads it.

Page state belongs in the URL

If the current page lives only in useState, a refresh sends the user back to page 1, the Back button leaves the list, and nobody can share "page 3 of the IT department". Store page, size and search text in the query string with useSearchParams from React Router. The URL becomes the single source of truth, and the query key follows from it.

import { keepPreviousData, useQuery } from '@tanstack/react-query';
import { useSearchParams } from 'react-router';
import { api } from '../lib/axios.js';

export function useEmployeeParams() {
  const [searchParams, setSearchParams] = useSearchParams();
  const page = Math.max(0, Number(searchParams.get('page') ?? 0) || 0);
  const q = searchParams.get('q') ?? '';

  function update(changes) {
    const next = new URLSearchParams(searchParams);
    Object.entries(changes).forEach(([key, value]) => {
      if (value === '' || value === null || value === undefined) next.delete(key);
      else next.set(key, String(value));
    });
    setSearchParams(next);
  }
  return { page, q, update };
}

export function useEmployees({ page, q, size = 10 }) {
  return useQuery({
    queryKey: ['employees', { page, q, size }],        // a new key per page = cached per page
    queryFn: async ({ signal }) => {
      const { data } = await api.get('/employees', { params: { page, size, q }, signal });
      return data;
    },
    placeholderData: keepPreviousData,                  // keep showing the old page while loading
  });
}

Because the page is part of the query key, going to page 2 and back to page 1 shows page 1 instantly from the cache. keepPreviousData keeps the old rows on screen while the next page loads, so the table does not flash empty. While that happens query.isPlaceholderData is true; use it to dim the table and disable the "Next" button.

The pagination component

Build it from page (0-based) and totalPages only. Show the user a 1-based number, because people do not read "page 0".

export function Pagination({ page, totalPages, onChange, disabled = false }) {
  if (totalPages <= 1) return null;                      // nothing to page through
  const isFirst = page === 0;
  const isLast = page >= totalPages - 1;

  return (
    <nav aria-label="Pagination" className="pagination">
      <button onClick={() => onChange(page - 1)} disabled={disabled || isFirst}>
        Previous
      </button>
      <span>Page {page + 1} of {totalPages}</span>
      <button onClick={() => onChange(page + 1)} disabled={disabled || isLast}>
        Next
      </button>

Edge cases in pagination

  • Off-by-one: the API is 0-based, the UI is 1-based. Convert in exactly one place.
  • Search resets the page: when the search text changes, set page back to 0, or you may ask for page 7 of a result that has only 2 pages.
  • Last item deleted: after deleting the only row on the last page, the page you are on no longer exists (an empty content with totalPages smaller than page + 1). Move to totalPages - 1.
  • Sorting: send sort=field,direction. Whitelist sortable fields on the server; Spring Data throws PropertyReferenceException for an unknown property, which becomes a 500 unless you handle it.
  • Zero results: totalPages is 0. Show the empty state, not "Page 1 of 0".
  • Data changes between pages: with offset paging, if someone adds a row while you read, an item can appear twice or be skipped. Large, fast-changing feeds use cursor (keyset) paging instead.

Optimistic updates (briefly)

Normally a UI action waits for the server: click "Done", wait 300 ms, the checkbox changes. An optimistic update changes the screen immediately, as if the request already succeeded, sends the request in the background, and rolls back if it fails. It makes quick actions feel instant. With TanStack Query the recipe is: stop in-flight refetches, save the old data, write the new data into the cache, undo on error, and always refetch at the end so the cache matches the server.

const queryClient = useQueryClient();

const remove = useMutation({
  mutationFn: (id) => api.delete(`/employees/${id}`),

  onMutate: async (id) => {
    await queryClient.cancelQueries({ queryKey: ['employees'] });   // avoid overwrite by a refetch
    const snapshots = queryClient.getQueriesData({ queryKey: ['employees'] });
    queryClient.setQueriesData({ queryKey: ['employees'] }, (old) =>
      old ? { ...old, content: old.content.filter((e) => e.id !== id) } : old);
    return { snapshots };                                          // passed to onError as context
  },

  onError: (err, id, context) => {
    context?.snapshots.forEach(([key, data]) => queryClient.setQueryData(key, data));
    toast.error('Could not delete. The employee is back in the list.');
  },

  onSettled: () => queryClient.invalidateQueries({ queryKey: ['employees'] }),
});

When optimistic updates are a bad idea

  • When the server decides the result: new rows need a server-generated id, prices are recalculated, stock may be insufficient.
  • For money, bookings and anything irreversible. A UPI payment must show "processing", then the real outcome; never "success" first.
  • When failures are common. Constant rollbacks feel worse than a short wait.

Good candidates: toggling a favourite, marking a task done, reordering, deleting a draft.

Common mistakes

  • Keeping the page number in state only, so refresh and Back break.
  • Putting the page outside the query key, so every page shows the cached first page.
  • Optimistic updates without rollback, leaving the UI lying after a failure.
  • Forgetting invalidateQueries in onSettled, so the cache drifts from the server.
  • Fetching all rows and paging in JavaScript. That defeats the purpose.

Interview: "How would you build a paginated table against a Spring Boot API?"

  • Backend takes Pageable (0-based page, size, sort) and returns content plus totalElements and totalPages.
  • Frontend keeps page and search in the URL, uses them in the query key, keeps the previous page visible while the next loads, and builds controls from the totals.
  • Mention the edge cases: reset page on search, page beyond the end after deletes, sort whitelist, and offset vs cursor paging for huge or live data.

Interview questions — Connecting React to your Spring Boot API

Why does the browser block my React app's request to the Spring Boot API, and how do you fix it?

The browser enforces the same-origin policy. An origin is scheme + host + port, so http://localhost:5173 (React) and http://localhost:8080 (Spring) are different origins. The browser lets the page send the request but hides the response unless the server answers with Access-Control-Allow-Origin for that origin. This is CORS.

Fix it on the server: configure allowed origins, methods and headers in Spring Boot (a CorsConfigurationSource bean with Spring Security, or addCorsMappings without). In development you can also use the Vite proxy (server.proxy) so the browser sees one origin. The fix is never in React code.

What is a preflight request?

For "non-simple" requests (methods like PUT or DELETE, a JSON Content-Type, or an Authorization header) the browser first sends an OPTIONS request asking "may I send this?", with headers such as Access-Control-Request-Method and Access-Control-Request-Headers. The server must answer with matching Access-Control-Allow-Methods and -Headers. Only then does the browser send the real request. A common bug: Spring Security rejects the OPTIONS request with 401 because CORS is not enabled in the security filter chain.

Is CORS a security feature of your API?

No. CORS protects the user's browser from other sites reading responses with the user's credentials. It does not stop curl, Postman or a script on a server from calling your API. Your API still needs authentication, authorisation and validation on every endpoint.

fetch or Axios: which would you use and why?

Both work. fetch is built into the browser and needs no dependency, but it does not reject on 4xx/5xx (you check response.ok), you call response.json() yourself, and there are no interceptors or default timeout. Axios adds a base URL, automatic JSON, rejection on non-2xx, interceptors (perfect for adding the token and handling 401), cancellation and timeouts. Many teams choose Axios for apps with auth; a small fetch wrapper gives the same features if you want zero dependencies.

Explain the JWT login flow in a React and Spring Boot app.

The login form POSTs email and password to /api/auth/login. Spring verifies the password hash and returns a signed JWT (and user info). The app keeps the token and an Axios request interceptor adds Authorization: Bearer <token> to every call. Spring's filter verifies signature and expiry on each request, so the server stays stateless. When the token expires the API returns 401; the app uses a refresh token to get a new access token and retries, or logs the user out and redirects to /login. On page reload the session is restored by the refresh call (or by reading the stored token and calling /me).

Where should the token be stored: localStorage, sessionStorage, memory or a cookie?

localStorage and sessionStorage are readable by any JavaScript on the page, so an XSS bug lets an attacker steal the token. An httpOnly cookie cannot be read by JavaScript, but it is sent automatically, so you must defend against CSRF (SameSite, CSRF token). A common best practice: the short-lived access token in memory, the long-lived refresh token in an httpOnly, Secure, SameSite cookie. localStorage is acceptable for learning projects if you can explain the risk.

What is the difference between 401 and 403, and how does the frontend react to each?

401 means "not authenticated": no, invalid or expired credentials. The client refreshes the token or sends the user to login. 403 means "authenticated but not allowed". The client shows an "access denied" message and keeps the session. Redirecting to login on a 403 is a bug that loops the user.

How do you implement protected routes? Is hiding a button enough?

A layout route (RequireAuth) reads the auth context. While the session is being restored it shows a loader; if there is no user it returns <Navigate to="/login" replace state={{ from: location }} /> so login can send the user back; otherwise it renders <Outlet />. Roles are an extra check. Hiding buttons is not security: users can edit the client or call the API directly, so every endpoint must enforce authentication and roles (@PreAuthorize, request matchers).

How do you handle loading and error states for an API call?

Model four states: loading, error, empty and data. With useEffect that means three pieces of state and finally to end loading; with TanStack Query you get isPending, isError and data. Classify errors: no response (network or timeout; retry), 4xx (user or request problem; no retry, show field errors or a message), 5xx (server problem; friendly message and retry). Disable submit buttons while a request runs, use skeletons for first loads, and use toasts for action results.

The backend returns validation errors. How do they get onto the form fields?

Spring throws MethodArgumentNotValidException for an invalid @Valid body. A @RestControllerAdvice converts it to a 400 ProblemDetail that includes an errors map of field name to message. In the React catch block you read error.response.data.errors, store it in state and render each message under the input with the same name. With React Hook Form you call setError(field, …). Field names must match the DTO property names.

How do you build pagination in the UI with Spring Data?

The API accepts page (0-based), size and sort and returns the content plus totalElements and totalPages. The UI keeps the page in the URL (useSearchParams), puts it in the TanStack Query key, uses keepPreviousData so the table does not flash, and draws Previous/Next from totalPages. Reset to page 0 when the search changes and move back a page if the last row of the last page is deleted.

What happens to environment variables in a Vite build? Can you store an API key there?

Only variables prefixed with VITE_ are exposed, through import.meta.env, and their values are copied into the JavaScript at build time. So the bundle contains them in plain text and anyone can read them. Use them for the API URL and other public configuration, never for secrets such as database passwords, JWT secrets or secret API keys. Changing a value needs a rebuild.

After deploying, refreshing /employees/7 shows 404. Why, and what is the fix?

React Router changes the URL in the browser only. On refresh the server is asked for the path /employees/7 and has no file for it. Configure a fallback that returns index.html with status 200 for unknown paths: try_files $uri $uri/ /index.html in Nginx, a rewrite in vercel.json, a /* /index.html 200 line in Netlify's _redirects, or a resource resolver in Spring Boot.

Separate hosting (Vercel) or Spring Boot's static folder: how do you decide?

Separate hosting deploys the UI independently, gives CDN speed and preview URLs, but is cross-origin, so you need CORS, HTTPS and careful cookie settings. Bundling the build into Spring Boot's static folder gives one artefact and one origin (no CORS), which is simple for small internal tools, but couples frontend and backend releases and serves static files less efficiently. Nginx in front of both gives one origin and separate deployables.

How would you debug "the request fails only from the browser, but works in Postman"?

That points to something browser-specific. Open the Network tab and look at the failing request and its OPTIONS preflight, and the Console for a CORS message. Check the origin allowed on the server (exact scheme, host, port, no trailing slash), that Authorization is in the allowed headers, and that Spring Security lets OPTIONS through. If cookies are involved, check withCredentials, Access-Control-Allow-Credentials, a specific (not *) origin and the cookie's SameSite and Secure flags.

Cheat sheet — Connecting React to your Spring Boot API

  • Architecture browser → React (static files) → Spring Boot REST API → PostgreSQL; JSON over HTTP.
  • Origin scheme + host + port; :5173 and :8080 are different origins.
  • CORS server-side permission for cross-origin reads; send Access-Control-Allow-Origin; not API security.
  • Preflight automatic OPTIONS before PUT/DELETE/JSON/Authorization requests.
  • Spring CORS CorsConfigurationSource bean + http.cors(...) with Security; addCorsMappings without.
  • Vite proxy server.proxy forwards /api to :8080 in dev, so no CORS locally.
  • Axios instance baseURL: import.meta.env.VITE_API_URL, timeout, JSON by default.
  • Request interceptor adds Authorization: Bearer <token>.
  • Response interceptor on 401 refresh once (_retry, shared promise) or log out.
  • fetch does not reject on 4xx/5xx; check response.ok, call .json().
  • JWT storage memory + httpOnly refresh cookie (best); localStorage (simple, XSS-readable).
  • 401 vs 403 not authenticated (refresh/login) vs not allowed (show message, stay logged in).
  • RequireAuth loader while restoring, Navigate to="/login" replace state={{ from }}, else Outlet.
  • Frontend roles cosmetic only; the backend enforces with @PreAuthorize.
  • Four UI states loading, error, empty, data. isPending vs isFetching.
  • Error kinds no response = network/timeout; 4xx = fix request; 5xx = retry later.
  • ProblemDetail RFC 7807 JSON: type, title, status, detail, instance + your extras (errors).
  • Field errors errors[name] under the input with the same name; clear on change.
  • Pagination ?page=0&size=10&sort=name,asc; 0-based; page in the URL and the query key.
  • Optimistic update change cache at once, roll back on error, refetch in onSettled; not for payments.
  • Vite env .env, .env.development, .env.production; only VITE_*; strings; build-time.
  • No secrets everything in the bundle is public.
  • Build npm run build → dist/ (static, hashed files); npm run preview to check it.
  • SPA fallback unknown path → index.html with 200 (Nginx, Vercel, Netlify, Spring resolver).
  • Debugging Network tab: status, request headers, payload, response body, OPTIONS; copy as cURL.

Practice — Connecting React to your Spring Boot API

  1. Break and fix CORS (easy). Run a Vite app and a Spring Boot endpoint without any CORS settings and call it with fetch. Read the console error and the failed request in the Network tab. Then fix it with a CORS configuration, and again with the Vite proxy. Done when you can say which header was missing and which approach you used.
  2. Axios instance (easy). Create lib/axios.js with a baseURL from VITE_API_URL, a request interceptor that adds the Bearer token and a response interceptor that clears the session on 401. Done when a wrong token sends you to the login page.
  3. Rebuild a DOM/async app in React (easy to medium). Take the movie search or expense tracker you built with plain JavaScript in Module 4 and rebuild it in React with routing (list page, detail page), Context for shared state (favourites or theme) and loading and error states. Done when it has no manual DOM code and a refresh on the detail URL works in npm run preview.
  4. Login and protected routes (medium). Add AuthContext, LoginPage and RequireAuth with return-to-original-page. Done when opening a protected URL logged out redirects to login and back, and a page reload keeps you logged in.
  5. CRUD with backend validation (medium). Build list, create, edit and delete for one resource of your own (books, expenses, students). Show server validation errors beside the fields, including a 409 for a duplicate. Done when a bad submit never shows a generic error and a double-click creates one record.
  6. Pagination and search (medium). Add page, size and search to the list, stored in the URL, with keepPreviousData. Done when Back/refresh/share keep the same page and deleting the last row of the last page moves you back one page.
  7. Project 3 frontend (hard). Build a React UI for your Spring Boot API from Project 3: JWT login, protected pages, role-based buttons, forms that show backend validation errors, and pagination. Done when you can log in to your own API, see protected data, and a normal user cannot delete (hidden button and 403 from the API).
  8. Error handling pass (medium). Test the four states on every page: stop the backend, return 500 from a controller, return 404 for a bad id, return an empty list. Done when each case shows the right message, and 4xx errors are not retried.
  9. Deploy it (hard). Set production env variables, run npm run build, and deploy the UI to Vercel or Netlify (with the SPA rewrite) and the API somewhere reachable over HTTPS, or serve the build from an Nginx container with a proxy to the API. Done when a deployed deep link survives refresh and login works with the production CORS settings.
  10. Debug drill (medium). Ask a friend (or yourself with a git stash) to introduce three bugs: a wrong allowed origin, a missing VITE_ prefix, and a mismatched form field name. Find each using only the Network tab and console. Done when you can name the symptom, the tab and the fix for each in under five minutes.

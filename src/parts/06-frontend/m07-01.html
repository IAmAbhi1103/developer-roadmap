TypeScript basics: types, unions, interfaces, generics, narrowing

TypeScript is JavaScript plus a static type system that is checked before the code runs and then erased; learn the basic types, unions, interface vs type, generics and narrowing, and you can read and write most TypeScript in React projects.

What it is and why teams use it

JavaScript decides types while the program runs. If you write employee.nmae (a typo), nothing warns you; the user sees undefined or a crash. TypeScript (TS) adds type annotations to JavaScript. A tool called the type checker (tsc, or your editor) reads your code, reports mistakes at once, and then the types are erased: the browser runs plain JavaScript. Every valid JavaScript program is also valid TypeScript, so you can adopt it gradually.

What you get: autocomplete for every property, safe renaming and refactoring, errors for typos and wrong argument types, null-safety, and types that document your API data. For a Java developer, this is the feeling of working with an IDE and a compiler again.

Vite does not type-check

When you create a project with npm create vite@latest my-app -- --template react-ts, Vite only strips the types (fast), it does not check them. Type errors appear in your editor and when you run the check script; the template's build script runs tsc first so that a build fails on type errors. Files are named .ts and .tsx (TSX = TypeScript with JSX).

Basic types and inference

const name: string = 'Asha';
const age: number = 29;               // one number type: no int/long/double
const active: boolean = true;
const nothing: null = null;
let maybe: undefined = undefined;
const big: bigint = 9007199254740993n; // for integers beyond 2^53

// Inference: the compiler works out the type, so you usually do NOT annotate
const city = 'Pune';                  // type is the literal 'Pune' (const)
let count = 0;                        // type is number
count = 'five';                       // Error: Type 'string' is not assignable to type 'number'

// Arrays
const ids: number[] = [1, 2, 3];
const names: Array<string> = ['Asha', 'Ravi'];   // same thing; number[] is more common

// Tuple: fixed length, known type at each position
const point: [number, number] = [18.52, 73.85];
const entry: [string, number] = ['salary', 50000];

// Objects
const employee: { id: number; name: string; email?: string } = { id: 1, name: 'Asha' };

Annotate the places the compiler cannot infer: function parameters, function return types of public functions, and empty initial values (const items: Employee[] = []). Let it infer the rest.

Union and literal types

A union type says "this or that": string | null. A literal type is one exact value. Together they replace most uses of Java enums and make states precise. Java has no direct equivalent of a union (sealed interfaces come closest).

type Role = 'ADMIN' | 'HR' | 'USER';           // a union of string literals
type Id = number | string;
let selected: Employee | null = null;           // "maybe an employee"

function canDelete(role: Role): boolean {
  return role === 'ADMIN';
}
canDelete('ADMIN');
canDelete('admin');    // Error: Argument of type '"admin"' is not assignable to type 'Role'

// A discriminated union: each case has a common "tag" property
type LoadState =
  | { status: 'loading' }
  | { status: 'error'; message: string }
  | { status: 'success'; data: Employee[] };

interface vs type

Both describe the shape of an object. Pick one style per project; both are fine.

interface Employee {
  readonly id: number;        // cannot be reassigned after creation
  name: string;
  email: string;
  phone?: string;             // optional: string | undefined
}

interface Manager extends Employee {   // inheritance
  reports: Employee[];
}

type EmployeeDraft = Omit<Employee, 'id'>;       // a type alias built from another type
type Status = 'active' | 'on-leave' | 'resigned';   // aliases can name unions; interfaces cannot

const e: Employee = { id: 1, name: 'Asha', email: 'asha@acme.in' };

Generics

Generics let you write one type or function that works for many types, exactly as in Java. The syntax is the same: angle brackets. Your API already returns a generic page.

function first<T>(items: T[]): T | undefined {
  return items[0];
}
const a = first([1, 2, 3]);          // a: number | undefined (T inferred as number)
const b = first(['x', 'y']);         // b: string | undefined

// Generic interface: the same shape for Page<Employee>, Page<Department>, ...
interface Page<T> {
  content: T[];
  page: number;
  size: number;
  totalElements: number;
  totalPages: number;
}

// Constraint: T must have an id (like <T extends HasId> in Java)
interface HasId { id: number }
function indexById<T extends HasId>(items: T[]): Record<number, T> {
  const result: Record<number, T> = {};
  for (const item of items) result[item.id] = item;
  return result;
}

// Default type parameter
interface ApiResult<T = unknown> { data: T; status: number }

Narrowing

Narrowing means the compiler follows your checks and gives a more precise type inside each branch. This is how you safely use a union.

function show(value: string | number | null): string {
  if (value === null) return 'none';                // value: string | number
  if (typeof value === 'string') return value.toUpperCase();   // value: string
  return value.toFixed(2);                          // value: number
}

// 'in' and instanceof
function describe(x: Employee | Error): string {
  if (x instanceof Error) return x.message;         // narrowed to Error
  return x.name;                                    // narrowed to Employee
}

// Discriminated union + exhaustive check
function render(state: LoadState): string {
  switch (state.status) {
    case 'loading': return 'Loading…';
    case 'error': return state.message;                       // state has message here
    case 'success': return `${state.data.length} employees`;  // state has data here
    default: {
      const unreachable: never = state;   // compile error if a new status is added and not handled
      return unreachable;
    }
  }
}

// Your own check: a type guard (the return type "x is ..." tells the compiler)
function isApiError(x: unknown): x is { message: string } {
  return typeof x === 'object' && x !== null && 'message' in x;
}

any vs unknown vs never

TypeMeaningSafe?
any"Turn off checking for this value." Anything goes in, anything can be done with it.No. It spreads: one any silently removes safety from everything it touches.

function parse(json: string): unknown {
  return JSON.parse(json);                 // JSON.parse returns any; we hide that behind unknown
}

const value = parse('{"name":"Asha"}');
value.name;                                // Error: 'value' is of type 'unknown'
if (typeof value === 'object' && value !== null && 'name' in value) {
  console.log(value.name);                 // OK after narrowing
}

try {
  riskyCall();
} catch (err) {                            // err is unknown in strict mode
  if (err instanceof Error) console.log(err.message);
}

Two escape hatches you will see: a type assertion (value as Employee) tells the compiler "trust me", and the non-null assertion (user!.name) says "this is not null". Neither checks anything at run time. Use them rarely, and only when you know something the compiler cannot.

Rules

  • Types exist only at compile time. They are erased, so you cannot use a type in a value position (if (x instanceof Employee) fails when Employee is an interface) and the compiler cannot check data that arrives at run time, such as an API response.
  • Optional phone?: string means the property may be missing, and its type includes undefined. Java's null maps to string | null.
  • A readonly property is only enforced by the compiler; it does not freeze the object at run time.

Conventions

  • Types and interfaces in PascalCase without an I prefix (Employee, not IEmployee).
  • Prefer string-literal unions over TypeScript's enum keyword: simpler, and they match the JSON strings your Java enums produce.
  • Let inference work; annotate function boundaries (parameters, exported return types).
  • Prefer unknown to any; if you must use any, leave a comment saying why.
  • Prefer discriminated unions to several optional fields that are "only set in some cases".

Common mistakes

  • Sprinkling any or as to make red lines go away. The error was telling you something.
  • Believing the types describe the real API response. If the backend sends a different shape, your code compiles and still crashes. Validate at the boundary when it matters (next article).
  • Comparing against types at run time (typeof x === 'Employee' is never true; the typeof results are only 'string', 'number', 'object' and a few more).
  • Forgetting that arrays and objects are still mutable even when typed as constants (const only stops reassignment).

Interview: "Why TypeScript, and what is the difference between any and unknown?"

  • Static types catch typos and wrong calls before run time, give autocomplete and safe refactoring, and document data shapes. Types are erased, so there is no run-time cost and no run-time checking.
  • any disables checking; unknown accepts any value but forces you to narrow before using it.
  • interface vs type: both describe objects; type also names unions and tuples, interface supports declaration merging and extends.
  • Narrowing with typeof, instanceof, in, equality and discriminated unions.

TypeScript with React and your API: props, state, events and DTO types

Type props with an interface, give useState a type when the initial value does not say it, use React's event types for handlers, and write TypeScript interfaces that mirror your Java records so a renamed backend field becomes a compile error in the frontend.

Props, children and callbacks

A component is a function; its props are its parameter. Describe them with an interface. Use ReactNode for anything React can render (text, elements, arrays, null) and plain function types for callbacks.

import type { ReactNode } from 'react';
import type { Employee } from '../types/employee';

interface EmployeeCardProps {
  employee: Employee;
  highlight?: boolean;                       // optional prop
  onDelete: (id: number) => void;            // callback prop
  children?: ReactNode;                      // anything nested inside the component
}

export function EmployeeCard({ employee, highlight = false, onDelete, children }: EmployeeCardProps) {
  return (
    <article className={highlight ? 'card highlight' : 'card'}>
      <h3>{employee.name}</h3>
      <p>{employee.email}</p>
      {children}
      <button onClick={() => onDelete(employee.id)}>Delete</button>
    </article>
  );
}

// Usage: a missing or wrongly typed prop is a compile error
// <EmployeeCard employee={e} onDelete={(id) => remove(id)} />
// <EmployeeCard employee={e} />              // Error: Property 'onDelete' is missing

Most projects type props like this and let the return type be inferred. You will also see React.FC<Props>; it is not needed and many style guides avoid it. import type imports a name that exists only as a type; it is erased and makes that fact clear.

State

// Inferred from the initial value
const [count, setCount] = useState(0);              // number

// When the initial value does not tell the whole story, pass the type

const [rows, setRows] = useState<Employee[]>([]);       // without it: never[]

Events

React wraps browser events. Its types take the element as a generic argument: ChangeEvent<HTMLInputElement>, FormEvent<HTMLFormElement>, MouseEvent<HTMLButtonElement>. When you write the handler inline the compiler infers the type for you; annotate only when the handler is a separate function.

import type { ChangeEvent, FormEvent } from 'react';

interface FormValues { name: string; email: string; department: string }

function EmployeeFormTs({ onSave }: { onSave: (values: FormValues) => Promise<void> }) {
  const [values, setValues] = useState<FormValues>({ name: '', email: '', department: '' });

  function handleChange(e: ChangeEvent<HTMLInputElement | HTMLSelectElement>) {
    const { name, value } = e.target;
    setValues((prev) => ({ ...prev, [name]: value }));
  }

  async function handleSubmit(e: FormEvent<HTMLFormElement>) {
    e.preventDefault();
    await onSave(values);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input name="name" value={values.name} onChange={handleChange} />
      <input name="email" value={values.email} onChange={handleChange} />
      <select name="department" value={values.department} onChange={handleChange}>
        <option value="">Choose…</option>
        <option value="IT">IT</option>
      </select>
      <button type="submit">Save</button>
    </form>
  );
}

Context with types

import { createContext, useContext } from 'react';

export type Role = 'ADMIN' | 'HR' | 'USER';

export interface User {
  id: number;
  name: string;
  email: string;
  roles: Role[];
}

interface AuthContextValue {
  user: User | null;
  isLoading: boolean;
  login: (email: string, password: string) => Promise<User>;
  logout: () => Promise<void>;
}

const AuthContext = createContext<AuthContextValue | null>(null);   // null = "no provider"

export function useAuth(): AuthContextValue {
  const ctx = useContext(AuthContext);
  if (ctx === null) throw new Error('useAuth must be used inside AuthProvider');
  return ctx;               // narrowed: no null checks needed in every component
}

Typed API calls and hooks

import { api } from './axios';
import type { Employee, EmployeeRequest, Page } from '../types/employee';

export const employeeApi = {
  async list(params: { page: number; size: number; q?: string },
             signal?: AbortSignal): Promise<Page<Employee>> {
    const { data } = await api.get<Page<Employee>>('/employees', { params, signal });
    return data;                                   // typed as Page<Employee>
  },
  async create(body: EmployeeRequest): Promise<Employee> {
    const { data } = await api.post<Employee>('/employees', body);
    return data;
  },
};

// src/hooks/employeeHooks.ts: the generics are inferred from the queryFn
export function useEmployees(page: number, q: string) {
  return useQuery({
    queryKey: ['employees', { page, q }],
    queryFn: ({ signal }) => employeeApi.list({ page, size: 10, q }, signal),
  });
}
// const { data } = useEmployees(0, '');   data: Page<Employee> | undefined
// data.content[0].nmae                    Error: Property 'nmae' does not exist

Errors from Axios are unknown in a catch block. Narrow them with isAxiosError:

import { isAxiosError } from 'axios';

export function getFieldErrors(err: unknown): Record<string, string> {
  if (isAxiosError(err)) {
    const errors = err.response?.data?.errors;     // data is any here: narrow before trusting it
    if (errors && typeof errors === 'object') return errors as Record<string, string>;
  }
  return {};
}

Types are not run-time checks

api.get<Employee> does not verify anything. It tells the compiler "believe me". If the backend renames department to dept, your code still compiles and employee.department is undefined at run time. Three ways to close the gap:

  • Generate the types from the backend. Add the springdoc OpenAPI documentation to Spring Boot and generate the TypeScript types from it with a tool such as openapi-typescript. A backend change then shows up as a frontend compile error.
  • Validate at the boundary with Zod. A schema checks the data when it arrives and the type is derived from the schema.
  • Contract tests and integration tests on the API (Spring Boot · Module 5).
import { z } from 'zod';

export const employeeSchema = z.object({
  id: z.number(),
  name: z.string(),
  email: z.string(),
  department: z.string(),
  salary: z.number(),
});

export type Employee = z.infer<typeof employeeSchema>;

// In the API function:
const { data } = await api.get('/employees/1');
const employee = employeeSchema.parse(data);   // throws if the shape is wrong

Common mistakes

  • useState([]) without a type: the state is never[] and every setRows(data) is an error. Write useState<Employee[]>([]).
  • Typing an event as any or React.ChangeEvent without the element (e.target.value then is not found). Use ChangeEvent<HTMLInputElement>.
  • Using the DTO type for form state: forms hold strings (a salary input is a string until you convert it), so the form values often need their own type.
  • Using Date in the interface for a LocalDate: JSON gives you a string.
  • Copying the whole Java entity (with lazy relations and passwords) instead of the DTO your controller actually returns.

Edge cases

  • useParams() values are string | undefined. Convert and check: const id = Number(params.id) and handle Number.isNaN(id).
  • The type of document.getElementById('root') is HTMLElement | null; the Vite template uses ! because index.html always has it.
  • An index access such as rows[0] is typed as Employee although the array may be empty. The option noUncheckedIndexedAccess (not part of strict) makes it Employee | undefined.

Interview: "How do you type API responses in a React and Spring Boot project?"

  • Interfaces that mirror the DTO records; generics such as Page<T>; api.get<Page<Employee>>; separate request and response types (Omit<Employee, 'id'>).
  • Say honestly that types are erased: use generated types from OpenAPI and/or Zod validation so the types match the real JSON.
  • Map Java types: LocalDate to string, enums to string unions, BigDecimal to number (watch precision), nullable to T | null.

tsconfig strict mode, common errors, and TypeScript vs Java

Keep "strict": true in tsconfig, learn to read the five or six error messages you will see every day, and use your Java experience: TypeScript's types are structural and erased, while Java's are nominal and present at run time.

Migrating a JavaScript project step by step

  1. Add TypeScript and a tsconfig; allow JavaScript (allowJs) so old files keep working.
  2. Rename files one at a time from .jsx to .tsx, starting with the leaves (utilities, small components).
  3. Add the DTO interfaces first; they give the biggest benefit.
  4. Keep strict on for new files. Fix, do not suppress.

The similarities help you learn quickly; the differences are where interview questions and bugs come from.

interface Named { name: string }

function hello(x: Named): string { return `Hi ${x.name}`; }

const employee = { id: 1, name: 'Asha', email: 'asha@acme.in' };
hello(employee);              // OK: it has a name; no "implements Named" needed

class Dog { constructor(public name: string) {} }
hello(new Dog('Tommy'));      // also OK, unrelated class, same shape

Edge case: excess property checks

A fresh object literal with an extra property is rejected (hello({ name: 'A', age: 3 }) errors: "Object literal may only specify known properties"), but the same object stored in a variable first is accepted. The first check catches typos; the second follows structural rules.

Interview: "How is TypeScript's type system different from Java's?"

  • Structural vs nominal; erased at compile time vs available through reflection.
  • Unions, literal types, narrowing and inference are central in TS. Java has sealed types and pattern matching for similar ideas.
  • strict mode, and in particular strictNullChecks, gives null-safety that Java does not have by default.
  • No run-time guarantees: validate external data (Zod, generated types).

The event loop: how single-threaded JavaScript does many things

JavaScript runs your code on one thread, one piece at a time; slow work (timers, network, clicks) is handed to the browser, and when it finishes the event loop moves its callback into a queue and runs it once the call stack is empty — microtasks (promises) always before the next macrotask (timers, events).

Java handles waiting with threads: one thread per request, or a thread pool. JavaScript has one main thread that runs all your code, and no synchronized, no race conditions between two lines of your code. Yet a page can wait for a 2-second API call and still respond to clicks. The trick is that your code never waits; it starts the job, gives the browser a callback, and moves on. This model is called non-blocking I/O, and it is the same idea Node.js uses on servers.

The parts

Call stack
The list of functions currently running, last in first out (same as the JVM stack). One function runs at a time; it must finish before the next starts.
Web APIs (the host)
Features supplied by the browser (or Node.js), not by the language: setTimeout, fetch, DOM events. They do their work outside the JavaScript thread, using the browser's own threads.
Task queue (macrotask queue)
Callbacks that are ready to run: a timer fired, a click happened, a message arrived. First in, first out.
Microtask queue
A higher-priority queue for promise callbacks (.then, catch, finally, code after await) and queueMicrotask().
Event loop
The loop that watches: when the call stack is empty, run all microtasks, then take one task from the task queue, run it, and repeat. The browser may redraw the screen between tasks.

The ordering puzzle

This is the most famous JavaScript interview question. Predict the output first.

console.log("1: script start");

setTimeout(() => console.log("2: setTimeout 0"), 0);

Promise.resolve()
  .then(() => console.log("3: promise 1"))
  .then(() => console.log("4: promise 2"));

queueMicrotask(() => console.log("5: microtask"));

(async () => {
  console.log("6: async function start");
  await null;
  console.log("7: after await");
})();

console.log("8: script end");
1: script start
6: async function start
8: script end
3: promise 1
5: microtask
7: after await
4: promise 2
2: setTimeout 0

Step by step:

  1. The script itself is one task. Synchronous lines run first, in order: 1, then the timer is handed to the browser, then the promise callback and the microtask are queued. The async function runs synchronously until its first await, so 6 prints, and the rest of the function is queued as a microtask. Finally 8 prints.
  2. The stack is empty. The loop now empties the microtask queue, in the order the callbacks were queued: 3: promise 1, 5: microtask, 7: after await. Running "promise 1" queues "promise 2" at the end of the same queue, so it runs next (4) before the loop leaves the microtask phase.
  3. Only now does the loop take the next macrotask: the timer callback, 2: setTimeout 0.

The rule to remember: synchronous code → all microtasks → next macrotask. setTimeout(fn, 0) does not mean "now": it means "after the current script and all promise work are done, and at least 0 ms later".

Blocking the loop

Because there is one thread, a long-running synchronous function freezes everything: no clicks, no scrolling, no timers. It also makes a timer late.

setTimeout(() => console.log("timer"), 100);

const start = Date.now();
while (Date.now() - start < 2000) { /* busy wait for 2 seconds */ }
console.log("loop finished");
// Output: "loop finished" after 2 s, then "timer" — about 2 s late.
// During those 2 seconds the page cannot be clicked.

Never run heavy loops, huge JSON.parse calls or big sorts on the main thread of a UI. Options: split the work into chunks with setTimeout, move it to a Web Worker (a real second thread with its own event loop; communication only by messages), or do it on the server. In Node.js, CPU-heavy work uses worker threads or a separate service.

"Run to completion" means a function that has started cannot be interrupted by another of your functions. But two async operations can interleave at await points, so logical race conditions still exist: two clicks may start two requests whose responses arrive in reverse order.

Rule: keep every task short

A task should finish in a few milliseconds. Anything that takes more than about 50 ms may be felt as a lag by the user. Start slow work with an async API and use its callback or promise.

Edge cases

  • An endless microtask chain (a promise callback that always queues another) starves the task queue: timers and clicks never run, and the page hangs.
  • Timers are not exact. setTimeout(fn, 100) means "no earlier than 100 ms"; browsers also slow timers in background tabs and clamp nested timers to at least about 4 ms.
  • Node.js has its own phases and also process.nextTick and setImmediate; the microtask-before-macrotask idea is the same, but details of the order differ from the browser.
  • alert(), confirm() and synchronous XHR block the thread. Avoid them.

Interview angle

  • "Explain the event loop." Single thread + call stack; async work goes to Web APIs; finished callbacks wait in queues; the loop runs microtasks, then one macrotask, when the stack is empty.
  • "Output of the script above?" Sync logs, then promise/microtask callbacks, then the timer. Explain microtask priority.
  • "Is JavaScript multi-threaded?" The language runs on one thread; the host uses threads underneath; Web Workers give extra threads.
  • "What happens if you run a 5-second loop?" The page freezes, no events or timers run until it finishes.

Callbacks and promises

A callback is a function you hand over to be called later, which leads to nested "callback hell"; a promise is an object that stands for a future value (pending, fulfilled or rejected) and lets you chain then, catch and finally in a flat line, or combine many with Promise.all.

Callbacks and callback hell

The first way to handle async work was the callback: pass a function that runs when the job is done. The convention in Node.js was "error first": callback(error, result).

function getUser(id, callback) {
  setTimeout(() => callback(null, { id, name: "Asha" }), 100);   // fake network
}
function getOrders(userId, callback) {
  setTimeout(() => callback(null, [{ no: 1, amount: 499 }]), 100);
}
function getPayment(orderNo, callback) {
  setTimeout(() => callback(null, { status: "PAID" }), 100);
}

// Each step needs the previous result, so the code drifts to the right
getUser(7, (err, user) => {
  if (err) return console.error(err);
  getOrders(user.id, (err, orders) => {
    if (err) return console.error(err);
    getPayment(orders[0].no, (err, payment) => {
      if (err) return console.error(err);
      console.log(user.name, orders[0].amount, payment.status); // Asha 499 PAID
    });
  });
});

This staircase is called callback hell (or the pyramid of doom). Errors must be handled at every level, try/catch cannot catch an error thrown later in a callback, and the order of steps is hard to follow. Promises solve this.

What is a promise?

A promise is an object that represents the eventual result of an async operation. It is like a Java CompletableFuture, or a receipt for an order you placed: you do not have the food yet, but you can say what to do when it arrives. A promise is in exactly one of three states:

  • pending — the work is still running;
  • fulfilled — it finished with a value;
  • rejected — it failed with a reason (usually an Error).

Fulfilled and rejected together are called settled; a settled promise never changes again. Callbacks attached with then always run later, as microtasks (see the event loop), even if the promise is already settled.

Creating and using promises

// Creating one: wrap callback-style code (you rarely need this; fetch already returns promises)
function wait(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}
function payUpi(amount) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (amount > 1000) reject(new Error("Daily limit exceeded"));
      else resolve({ txnId: "TX123", amount });
    }, 100);
  });
}

payUpi(500)
  .then((receipt) => console.log("Paid", receipt.txnId))   // Paid TX123
  .catch((err) => console.log("Failed:", err.message))
  .finally(() => console.log("done, hide the spinner"));

payUpi(5000)
  .then((receipt) => console.log("Paid", receipt.txnId))
  .catch((err) => console.log("Failed:", err.message))     // Failed: Daily limit exceeded
  .finally(() => console.log("done, hide the spinner"));

Chaining: the flat version

Every then returns a new promise. If your callback returns a plain value, the next then receives it. If it returns a promise, the chain waits for that promise and passes on its result. That is how the callback staircase becomes a straight line. An error thrown, or a rejected promise, skips ahead to the next catch.

const wait = (ms, value) => new Promise(res => setTimeout(() => res(value), ms));

const getUser = (id) => wait(100, { id, name: "Asha" });
const getOrders = (userId) => wait(100, [{ no: 1, amount: 499 }]);
const getPayment = (orderNo) => wait(100, { status: "PAID" });

getUser(7)
  .then((user) => getOrders(user.id))               // return a promise
  .then((orders) => getPayment(orders[0].no))
  .then((payment) => console.log(payment.status))    // PAID
  .catch((err) => console.error("Something failed", err))   // one handler for all steps
  .finally(() => console.log("end"));

Promise.resolve(1)
  .then((n) => n + 1)                 // returns a plain value
  .then((n) => { throw new Error("boom " + n); })
  .then(() => console.log("skipped"))   // skipped because of the throw
  .catch((e) => { console.log(e.message); return "recovered"; })   // boom 2
  .then((v) => console.log(v));        // recovered — catch returned a value, chain continues

// All three run at the same time: total about 300 ms, not 600

  .then((results) => console.log(results));          // [ 'user', 'orders', 'offers' ]

Promise.allSettled([wait(100, "ok"), wait(100, "bad", true)])
  .then((r) => console.log(r));
// [ { status: 'fulfilled', value: 'ok' },
//   { status: 'rejected', reason: Error: bad } ]

Promise.race([wait(500, "slow API"), wait(100, "timeout!", true)])
  .catch((e) => console.log(e.message));             // timeout!

Promise.any([wait(300, "mirror A"), wait(100, "mirror B")])
  .then((v) => console.log(v));                      // mirror B

Rule: return the promise inside then, and always end with a catch

If you forget to return the inner promise, the next step runs immediately with undefined. A rejection that nobody handles triggers an "unhandled rejection": the browser logs Uncaught (in promise) in the console, and in Node.js the process exits with an error in recent versions. End chains with .catch, or use try/catch with await.

Edge cases

  • Exceptions thrown inside new Promise((resolve, reject) => …) or inside then become rejections; but an error thrown inside a setTimeout callback within the executor is not caught (call reject there).
  • resolve and reject work only once; later calls are ignored.
  • .then(a).catch(b) is not .then(a, b): with the second form, b does not see errors thrown in a.
  • A promise starts running when created, not when you call then. Creating the promises first and then Promise.all is how you get parallelism.

Common mistake: nesting promises like callbacks

Wrong: callback hell again

getUser(7).then((user) => {
  getOrders(user.id).then((orders) => {
    console.log(orders);
  });
});   // errors in the inner promise are lost

Right: return and flatten

getUser(7)
  .then((user) => getOrders(user.id))
  .then((orders) => console.log(orders))
  .catch(console.error);

Interview angle

  • "What is a promise? Its states?" Object for a future value: pending, fulfilled, rejected; settles once.
  • "What is callback hell and how do promises fix it?" Deep nesting with scattered error handling; chaining flattens it with a single catch.
  • "Promise.all vs allSettled vs race vs any?" Use the table above; mention fail-fast behaviour.
  • "What does then return?" A new promise, which allows chaining.
  • "Why do promise callbacks run before setTimeout?" Microtasks have priority over macrotasks.

async and await, timers and common mistakes

An async function always returns a promise, and await pauses it until a promise settles so asynchronous code reads like normal top-to-bottom code with try/catch; await sequentially when steps depend on each other, use Promise.all when they do not, and never await inside forEach.

async/await (ES2017) is syntax on top of promises. It removes the then chains and makes asynchronous code look synchronous, much like writing blocking Java code — but only the async function pauses; the rest of the program keeps running (see the event loop).

The two keywords

  • async function f() {} (or async () => {}) — always returns a promise. A returned value becomes the fulfilled value; a thrown error becomes a rejection.
  • await promise — only inside an async function (or at the top level of an ES module). It pauses the function, lets the event loop do other work, and resumes with the fulfilled value, or throws the rejection reason.
const wait = (ms, value) => new Promise(res => setTimeout(() => res(value), ms));
const getUser = (id) => wait(100, { id, name: "Asha" });
const getOrders = (userId) => wait(100, [{ no: 1, amount: 499 }]);
const getPayment = (orderNo) => wait(100, { status: "PAID" });

async function showOrderStatus(userId) {
  try {
    const user = await getUser(userId);            // pauses here, UI stays responsive
    const orders = await getOrders(user.id);
    const payment = await getPayment(orders[0].no);
    console.log(user.name, orders[0].amount, payment.status);
    return payment.status;                          // the returned promise fulfils with this
  } catch (err) {
    console.error("Could not load order:", err.message);
    throw err;                                      // rethrow if the caller should know
  } finally {
    console.log("hide spinner");
  }
}

showOrderStatus(7).then((s) => console.log("result:", s));
console.log("this prints first, the function is still waiting");
this prints first, the function is still waiting
Asha 499 PAID
hide spinner
result: PAID

Compare this with the callback pyramid and the then chain in callbacks and promises: the logic is the same, but now it is a straight line, and a single try/catch/finally covers every step like in Java. Note the difference: an await does not block the thread. Code after the call to showOrderStatus(7) ran first.

Sequential vs parallel

Each await waits for its promise before the next line starts. If the calls do not depend on each other, that wastes time.

async function sequential() {
  const t = Date.now();
  const user = await wait(300, "user");        // 300 ms
  const offers = await wait(300, "offers");    // another 300 ms
  console.log("sequential", Date.now() - t);   // ~600
}

async function parallel() {
  const t = Date.now();
  const [user, offers] = await Promise.all([wait(300, "user"), wait(300, "offers")]);
  console.log("parallel", Date.now() - t);     // ~300
}

async function parallelManually() {
  const userPromise = wait(300, "user");       // start both first
  const offersPromise = wait(300, "offers");
  const user = await userPromise;              // then wait
  const offers = await offersPromise;
}

Rule of thumb: depends on the previous result → sequential await; independent → Promise.all. A product page that loads details, reviews and recommendations should start all three at once.

Looping with await

const ids = [1, 2, 3];
const fetchOne = (id) => wait(100, `item ${id}`);

// One after another: ~300 ms (use when order or rate limits matter)
for (const id of ids) {
  const item = await fetchOne(id);
  console.log(item);
}

// All at once: ~100 ms
const items = await Promise.all(ids.map(fetchOne));
console.log(items);   // [ 'item 1', 'item 2', 'item 3' ]

// WRONG: forEach ignores the promises returned by its async callback
ids.forEach(async (id) => {
  const item = await fetchOne(id);
  console.log(item);
});
console.log("forEach finished");   // prints BEFORE any item is logged

forEach, map and filter do not wait for async callbacks. Use for…of with await to go one by one, or Promise.all(array.map(async …)) to go in parallel.

Timers: setTimeout and setInterval

Timers are Web APIs (also in Node.js). Both return an id that you pass to the matching clear… function. The delay is a minimum, not a promise (see the event loop).

const id = setTimeout(() => console.log("runs once after 1 s"), 1000);
clearTimeout(id);                     // cancelled — never runs

setTimeout((name) => console.log("hello", name), 500, "Asha");  // extra args are passed on

let seconds = 0;
const clock = setInterval(() => {
  seconds++;
  console.log("tick", seconds);
  if (seconds === 3) clearInterval(clock);   // stop it, or it runs forever
}, 1000);

// A promise-based sleep makes async code readable
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
async function retry(task, times = 3) {
  for (let i = 1; i <= times; i++) {
    try { return await task(); }
    catch (e) { console.log(`attempt ${i} failed`); await sleep(500 * i); }
  }
  throw new Error("All attempts failed");
}
  • setInterval does not wait for the previous run to finish; a slow callback can pile up. For polling, a setTimeout that re-schedules itself at the end of each run is safer.
  • Always clear intervals when the screen closes (in React, in the useEffect cleanup), or they keep running and leak memory.
  • requestAnimationFrame(fn) runs before the next screen repaint; use it for animations rather than a timer.

Common mistakes

Mistake 1: forgetting await

Wrong: user is a pending Promise

async function show() {
  const user = getUser(7);          // no await
  console.log(user.name);           // undefined
  console.log(user);                // Promise { <pending> }
}

Right

async function show() {
  const user = await getUser(7);
  console.log(user.name);           // "Asha"
}

Mistake 2: unhandled rejection, and awaiting without try/catch

Wrong: nobody catches the failure

button.addEventListener("click", async () => {
  const data = await loadData();   // may reject
  render(data);
});
// Console: Uncaught (in promise) Error: ...

Right: handle it where the UI can react

button.addEventListener("click", async () => {
  try {
    render(await loadData());
  } catch (err) {
    showError(err.message);
  }
});
  • Mistake 3: await inside forEach (shown above).
  • Mistake 4: awaiting in a loop when Promise.all would do — slow pages.
  • Mistake 5: await in a non-async function: SyntaxError: await is only valid in async functions and the top level bodies of modules.
  • Mistake 6: return somePromise inside try without await: the catch will not catch its rejection. Write return await somePromise there.
  • Mistake 7: making the executor of new Promise async, or wrapping an existing promise in new Promise needlessly.

Top-level await and async in React

In an ES module (type="module", Vite) you may write const config = await loadConfig(); at the top level. In React, the function you pass to useEffect must not be async; define an async function inside and call it. You will see this in Module 5.

Edge cases

  • An async function that throws before its first await still returns a rejected promise; it never throws synchronously to the caller.
  • await on a non-promise just wraps it: await 5 gives 5 (after a microtask delay).
  • With Promise.all, if one promise rejects the others still run to the end, but their results are dropped. Use allSettled to collect everything.
  • You cannot cancel a promise. To stop work such as a network request, use an AbortController (see fetch).

Interview angle

  • "What does an async function return?" Always a promise.
  • "Does await block the thread?" No; it suspends only that function and lets the event loop continue.
  • "How do you run two calls in parallel with await?" Start both, then await Promise.all([…]).
  • "Why doesn't await work in forEach?" forEach ignores the callback's returned promise; use for…of or Promise.all(map).
  • "setTimeout(fn, 0) vs a promise callback?" The promise runs first (microtask).
  • "setTimeout vs setInterval, and how do you stop them?" Once vs repeatedly; clearTimeout/clearInterval with the returned id.

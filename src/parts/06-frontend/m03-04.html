Transitions, transforms and animations

A transition smoothly animates a property between two states (like normal and hover), transform moves, scales or rotates without disturbing layout, and @keyframes build multi-step animations — animate transform and opacity for smooth performance, and respect prefers-reduced-motion.

Small amounts of motion make an interface feel alive and explain changes (a menu sliding in, a button reacting). Too much is distracting and slow. CSS gives you three tools: transitions (from state A to state B), transforms (change shape or position visually) and keyframe animations (many steps, loops, no trigger needed).

Transitions

Put the transition on the element's base rule. When a listed property changes — because of :hover, :focus, a class toggled by JavaScript — the browser animates between the old and new values instead of jumping.

.button {
  background: #1a56db;
  transform: translateY(0);
  transition: background-color 200ms ease, transform 200ms ease;
}
.button:hover,
.button:focus-visible {
  background: #1e429f;
  transform: translateY(-2px);
}

Good durations: 100–300ms for small UI feedback, up to 500ms for larger movements. ease-out (fast start, slow end) feels natural for things entering; ease-in for leaving. Not every property can animate: those with numeric or colour values can (width, opacity, color, transform), but display (none to block) cannot, and a transition from height: auto does not work. Fade with opacity and visibility, or animate max-height, or use the newer features if you need them.

Transforms

transform changes how an element is drawn without affecting the layout: neighbours do not move, and the element keeps its original space.

.a { transform: translate(20px, -10px); }  /* move x, y (% = of its own size) */
.b { transform: scale(1.1); }              /* grow 10%; scale(1, 0.5) squashes */
.c { transform: rotate(45deg); }           /* clockwise */
.d { transform: translateY(-4px) scale(1.05) rotate(2deg); }  /* combine, in order */
.e { transform-origin: top left; }         /* the pivot point (default: centre) */

Order matters when combining: transforms apply right to left in terms of the coordinate system, so translate(100px) rotate(45deg) and rotate(45deg) translate(100px) end up in different places. The separate properties translate, scale and rotate also exist in current browsers and can be transitioned independently. Percentages in translate refer to the element's own size, which is why translate(-50%, -50%) centres an absolute element.

Keyframe animations

For motion that has several steps, loops or starts on its own (a loading spinner, a fade-in on page load), define the steps with @keyframes and attach them with animation.

@keyframes fade-in-up {
  from { opacity: 0; transform: translateY(16px); }
  to   { opacity: 1; transform: translateY(0); }
}

.card {
  animation: fade-in-up 400ms ease-out both;
}

@keyframes spin {
  to { transform: rotate(360deg); }
}
.spinner {
  width: 2rem;
  height: 2rem;
  border: 3px solid #e5e7eb;
  border-top-color: #1a56db;
  border-radius: 50%;
  animation: spin 800ms linear infinite;
}

@keyframes pulse {
  0%, 100% { opacity: 1; }
  50%      { opacity: 0.4; }
}
.skeleton { animation: pulse 1.5s ease-in-out infinite; background: #e5e7eb; }

Triggering by JavaScript is simple: add or remove a class (el.classList.add("is-open")) and let CSS do the animation. Listen to transitionend or animationend events if you must run code when it finishes.

Performance: animate transform and opacity

Remember the rendering pipeline (How the browser renders a page). Animating width, height, top, left or margin forces layout on every frame, which janks on cheap phones. Animating transform and opacity can be done on the GPU compositor with no layout and no repaint, and stays at 60 frames per second. So:

  • Move with transform: translate(), not left/top.
  • Resize with transform: scale() where possible, not width/height.
  • Fade with opacity.
  • Do not use transition: all; name the properties. It animates things you did not intend and can trigger layout.
  • The will-change: transform hint prepares the browser for an upcoming animation. Use it rarely and remove it afterwards; overuse wastes memory.

Check animation smoothness in DevTools → Performance, and the Rendering panel's "Paint flashing" option.

Respect reduced motion

Some people feel dizzy or ill from parallax, zooming and large movement (vestibular disorders), and some simply turn off animations in their operating system. The media query prefers-reduced-motion detects it. This is an accessibility requirement under WCAG.

@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}

This blunt reset is one of the rare acceptable uses of !important. A subtler approach removes only large movement and keeps gentle fades. Also avoid anything that flashes more than three times per second.

Rule: put the transition on the base state, not only on :hover

If transition is only in :hover, the element animates when you enter but jumps back instantly when you leave, since the leaving state has no transition. Declare it in the normal rule so both directions animate.

Conventions

  • Keep UI motion short (150–300ms) and subtle; use one or two easing curves across the product.
  • Animate transform and opacity; list properties explicitly.
  • Always include a prefers-reduced-motion block; never convey information by motion alone.
  • Do the state change in CSS (classes), the logic in JavaScript.

Edge cases

  • Transitions do not run when an element is first inserted (no previous state) or when it goes from display: none; use a keyframe animation for entering elements, or the newer @starting-style and transition-behavior: allow-discrete where supported.
  • An element with a transform becomes a containing block for fixed descendants and a new stacking context (Positioning).
  • Hover-based transitions do not help on touch screens; also support :focus-visible.
  • Frameworks like React need the element to exist at both states to animate; libraries such as Framer Motion or React Transition Group help with enter and exit.

Interview angle

  • "Transition vs animation?" — transitions go between two states when a property changes; animations use keyframes, can loop and need no trigger.
  • "Which properties should you animate and why?" — transform, opacity: composited, no layout or paint.
  • "How do you handle users who dislike motion?" — prefers-reduced-motion.

Tailwind CSS and Bootstrap

Tailwind is a utility-first framework where you style by combining small single-purpose classes in the HTML (flex, p-4, md:grid-cols-3, hover:bg-blue-700), while Bootstrap supplies ready-made components and a 12-column grid — learn plain CSS first, then use whichever your team chose.

Writing every rule by hand is flexible but slow, and large teams need consistency. CSS frameworks give you a ready design system. You must know the CSS basics from this module first: Tailwind classes are nothing but short names for the properties you have just learned, and you cannot debug them without that knowledge. Two frameworks dominate: Tailwind (very common with React in startups and product companies) and Bootstrap (very common in service-company and older enterprise projects).

The utility-first idea

In traditional CSS you invent a class name (.card), then write its rules in another file. In Tailwind you compose the look directly from tiny classes, each doing one thing:

<div class="product-card">
  <h3 class="product-title">Masala Dosa Mix</h3>
  <button class="buy-button">Add to cart</button>
</div>
<div class="rounded-xl border border-gray-200 bg-white p-4 shadow-sm">
  <h3 class="text-lg font-semibold text-gray-900">Masala Dosa Mix</h3>
  <button class="mt-3 rounded-md bg-blue-600 px-4 py-2 text-white
                 hover:bg-blue-700 focus-visible:outline-2">
    Add to cart
  </button>
</div>

No separate CSS file, no naming, no worry that changing .card breaks another page. The build tool scans your files and generates CSS only for the classes you used, so the final stylesheet is small. The cost: long class lists in the markup. In React you solve this by making a component (<ProductCard />) once and reusing it, so the long list appears in one place.

Tailwind v4 vs v3

The setup above is Tailwind v4's CSS-first approach: one @import "tailwindcss" line and the Vite plugin, with no tailwind.config.js needed by default; customisation (colours, fonts) goes in CSS with @theme. Tailwind v3 projects, still common, use tailwind.config.js with a content list and the three @tailwind base/components/utilities directives, plus PostCSS. The utility class names are mostly the same, so what you learn here applies to both. Always follow the official installation guide at tailwindcss.com for your version.

Then import index.css in main.jsx and use classes in JSX with className. Install the "Tailwind CSS IntelliSense" extension in VS Code for autocomplete and hover previews.

Tailwind pros and cons

Pros

  • Fast to build: no switching between files and no naming
  • Consistent spacing, colours and sizes from one design scale
  • Small production CSS, since unused classes are never generated
  • Changes are local: editing one element cannot break another
  • Responsive, state and dark variants are one prefix away

Cons

  • Long class strings; HTML is harder to scan
  • You must know CSS anyway; the learning curve is the class names
  • Needs a build step and tooling
  • Component reuse needs discipline (React components)
  • Different feel from "semantic" CSS; some teams dislike it

Bootstrap in brief

Bootstrap is a component library with a design: buttons, navbars, cards, modals, forms and a responsive 12-column grid, all styled out of the box. Add it with a CDN link or npm install bootstrap.

<div class="container">
  <div class="row g-3">
    <div class="col-12 col-md-6 col-lg-4">
      <div class="card">
        <div class="card-body">
          <h5 class="card-title">Masala Dosa Mix</h5>
          <a href="#" class="btn btn-primary">Add to cart</a>
        </div>
      </div>
    </div>
  </div>
</div>
  • Grid: .container centres and limits width; .row is a flex row of 12 columns; .col-12 .col-md-6 .col-lg-4 mean full width on phones, half from 768px, a third from 992px. It is mobile-first like Tailwind.
  • Components: .btn .btn-primary, .navbar, .card, .modal, .alert, .form-control. Some need Bootstrap's JavaScript (modals, dropdowns, collapse) — in React use the React-Bootstrap library instead of the jQuery-era scripts.
  • Utilities exist too: d-flex, justify-content-between, mt-3, text-center, p-4.
  • Customise with Sass variables or CSS variables. Without that, every Bootstrap site looks like Bootstrap.

There are also component libraries built on these ideas — shadcn/ui and Headless UI (Tailwind based), Material UI and Ant Design (own styling) — that you will meet in React projects.

Rule: learn the CSS first

You cannot read items-center, col-span-2 or .row without knowing Flexbox and Grid. When a framework "does not work", the fix is almost always CSS knowledge: specificity, the box model, positioning contexts.

Conventions

  • With Tailwind: extract repeated class lists into React components (not into @apply), keep class order consistent (the official Prettier plugin sorts them), and use your theme's colours, not random hex values.
  • Never build class names by string concatenation like "bg-" + color + "-500": Tailwind scans the source as text and will not generate classes it cannot see written in full. Map to complete class names instead.
  • With Bootstrap: use its grid and components as documented; add your own CSS in a separate file loaded after Bootstrap rather than editing Bootstrap's files.

Edge cases

  • Tailwind's preflight (a CSS reset) removes default heading sizes, list bullets and margins — an h1 looks like plain text until you add classes.
  • Utility classes on the same element conflict by their order in the generated CSS, not in your class attribute: class="p-2 p-4" does not mean "p-4 wins" by position. Do not add both; compute one.
  • Bootstrap's old versions needed jQuery; Bootstrap 5 does not.

Interview angle

  • "What is utility-first CSS?" — style by composing small single-purpose classes in markup; consistent scale, small output.
  • "Tailwind vs Bootstrap?" — utilities versus prebuilt components; design freedom versus speed of a default look.
  • "How do you do responsive in Tailwind?" — mobile-first prefixes like md: and lg:.

Organising CSS and debugging it

Keep CSS maintainable with a small reset, a flat naming scheme such as BEM, low-specificity single-class selectors, variables for design tokens and one file per component — and debug problems in DevTools by checking the Styles, Computed and layout overlays.

CSS has no compiler, no types and no private scope. Everything is global, and the cascade connects it all. A stylesheet that grows without rules turns into a "append-only" mess that nobody dares to change. A few habits prevent that — much like the package structure and naming rules that keep a Java codebase healthy.

A small reset

Browsers apply their own default styles, differently from each other. A reset gives a consistent base. You do not need a heavy one; a few lines are enough:

*, *::before, *::after { box-sizing: border-box; }

body {
  margin: 0;
  font-family: system-ui, sans-serif;
  line-height: 1.6;
  color: var(--color-text, #1f2937);
}
img, video, svg { max-width: 100%; height: auto; display: block; }
button, input, select, textarea { font: inherit; }   /* forms use the page font */
h1, h2, h3, p { margin-block: 0 0.75em; }
a { color: inherit; }
:focus-visible { outline: 3px solid #1a56db; outline-offset: 2px; }

Well-known ready-made options are normalize.css (fixes browser differences but keeps the defaults), and "modern resets" such as Josh Comeau's or Andy Bell's. Tailwind ships its own (preflight); Bootstrap uses "Reboot".

Naming: BEM in brief

BEM (Block, Element, Modifier) is a naming convention that keeps selectors flat and self-explanatory.

  • Block: a standalone component — .card, .nav, .search-form.
  • Element: a part of the block — .card__title, .card__image (two underscores).
  • Modifier: a variant or state — .card--featured, .button--large (two hyphens).
<article class="card card--featured">
  <img class="card__image" src="dosa.jpg" alt="Masala dosa" width="400" height="300">
  <h3 class="card__title">Masala Dosa</h3>
  <a class="card__link button button--large" href="/menu/dosa">Order</a>
</article>
.card { border: 1px solid #e5e7eb; border-radius: 12px; padding: 1rem; }
.card--featured { border-color: #f59e0b; }
.card__title { font-size: 1.25rem; margin: 0 0 0.5rem; }
.card__image { border-radius: 8px; }

Every selector is a single class (specificity 0-1-0), so nothing fights anything else and any later rule can override. The name tells you where it is used. You do not need strict BEM; the lesson is: one class per thing, flat selectors, meaningful names. In React with CSS Modules (Card.module.css), class names are made unique automatically, so you can write short names like .title per component.

Avoid deep selectors and over-qualification

Wrong: tied to the HTML structure

#sidebar div.widget ul li a.link { color: red; }
div.card h3 { margin: 0; }

Right: a class where you need it

.widget__link { color: red; }
.card__title { margin: 0; }

The long selector breaks the moment someone adds a wrapper div, is hard to override (high specificity) and slower to read. Rules of thumb: no IDs, no more than two or three parts, and do not qualify a class with a tag (div.card).

Structure of a project

css/
  base.css          reset, :root variables, body, typography

  components/
    button.css

    navbar.css

  styles.css        imports the above (or the build tool bundles them)

Order matters: base first, then layout, components, utilities last (so helpers win). In React projects you usually keep one CSS file (or module) beside each component, and a global file for the reset and variables. Use CSS custom properties for design tokens (Colours, typography and variables). Sass/SCSS adds nesting, partials and variables; native CSS now has nesting and variables too (& .child { } inside a rule), so you can often skip Sass in new projects.

Debugging CSS in DevTools

  1. Find it. Right-click → Inspect. Is the right element selected (maybe a child is covering it)?
  2. Read Styles. Your rule present? Struck through (lost the cascade)? A warning icon (invalid)? A greyed property (no effect in this context)?
  3. Check Computed. Final value and the winning rule. Filter by property name.
  4. Check the box model diagram for unexpected margin, padding or width, and the layout overlays for Flexbox and Grid (click the badge in the Elements tree).
  5. Toggle and edit live. Untick declarations to find the one causing the issue; change values; use :hov to force hover/focus states.
  6. Find overflow. Run in the Console: [...document.querySelectorAll("*")].filter(e => e.scrollWidth > document.documentElement.clientWidth) — it lists the elements that are wider than the page.
  7. Outline everything. Temporarily add * { outline: 1px solid red; } to see every box. (Outline takes no space, unlike border.)
  8. Isolate. Copy the HTML and CSS into a small file and remove things until the bug disappears.

Tooling worth adding

  • Prettier formats CSS automatically; Stylelint catches invalid properties, duplicates and overly specific selectors.
  • VS Code's built-in CSS validation and the CSS Peek / IntelliSense extensions.
  • The DevTools Coverage tab (Command menu → "Show Coverage") shows how much of your CSS is unused.

Rule: one component, one block of CSS, no reaching into others

A component's styles should not rely on its parent's class names or style other components' internals. When one block needs to change another, add a modifier class instead.

Conventions

  • Single-class selectors, kebab-case names, BEM or CSS Modules, no IDs, no !important.
  • Design tokens in variables; magic numbers explained with a comment.
  • Delete dead CSS (check Coverage) instead of piling overrides on top.

Edge cases

  • CSS Modules and CSS-in-JS rename classes at build time; in DevTools you will see names like Card_title__x7Gq2. That is normal.
  • Global resets and third-party library CSS can change your elements; check the order of the imports.
  • Native CSS nesting is supported in current browsers; check your target browsers before relying on it without a build step.

Mistake: adding more and more overrides instead of fixing the original rule

Each override raises the specificity bar; finally someone adds !important. Refactor the base rule so one clear rule applies, and delete the old ones.

Interview angle

  • "How do you keep CSS maintainable?" — flat single-class selectors, a naming scheme like BEM, variables, component files, no !important, a reset.
  • "How do you debug a CSS issue?" — DevTools Styles/Computed, box model, layout overlays, toggle declarations, isolate.

Interview questions — CSS

How does CSS decide which rule wins? How do you calculate specificity?

First importance and origin (!important, author over browser styles), then specificity, then source order — later wins a tie. Specificity is compared as ID count, then class/attribute/pseudo-class count, then type/pseudo-element count; inline styles beat all selectors. For example #nav .item a is 1-1-1 and beats .nav .item a.link at 0-3-1.

What is inheritance? Which properties inherit?

Some properties pass from parent to child automatically — mostly text ones such as color, font-family, font-size, line-height and text-align. Box properties such as margin, padding, border, background and width do not. inherit, initial, unset and revert control this explicitly.

Explain the box model and box-sizing.

Every element is a box of content, padding, border and margin. With content-box (the default) width is only the content, so padding and border add to the total. With border-box the width includes padding and border, which is predictable, so we reset it globally with *, *::before, *::after { box-sizing: border-box; }.

What is margin collapsing?

Adjacent vertical margins of block elements merge into one, with the size of the larger, rather than adding up. It also happens between a parent and its first or last child when nothing separates them. It does not happen in flex or grid containers or with padding/border/overflow on the parent. Using gap or margin in a single direction avoids surprises.

em vs rem vs px vs %?

px is fixed; rem is relative to the root font size (16px by default) and respects the user's browser setting; em is relative to the element's own (or parent's, for font-size) font size and compounds when nested; % depends on the property, usually the parent's size. Use rem for fonts and spacing, px for borders and shadows.

How do you centre a div horizontally and vertically?

Make the parent a flex container with justify-content: center; align-items: center; and give it a height (for example min-height: 100dvh). Or use display: grid; place-items: center. For horizontal-only, give a block a width and margin-inline: auto. An absolute alternative is top: 50%; left: 50%; transform: translate(-50%, -50%) inside a positioned parent.

Explain Flexbox: main axis, cross axis and flex: 1.

Flexbox lays out items in one dimension. The main axis follows flex-direction; the cross axis is perpendicular. justify-content distributes items along the main axis and align-items along the cross axis. flex: 1 is 1 1 0: the item may grow and shrink and starts from a zero basis, so items with flex: 1 share the space equally.

Flexbox vs Grid — when do you use which?

Flexbox is one-dimensional and content-driven: navbars, toolbars, rows of buttons, centring. Grid is two-dimensional and layout-driven: page structures, galleries and dashboards where rows and columns must align. Real pages use Grid for the overall layout and Flexbox inside components.

What does grid-template-columns: repeat(auto-fit, minmax(250px, 1fr)) do?

It creates as many columns as fit in the container, each at least 250px and sharing the remaining space equally, so the grid adapts from one column on phones to several on desktops without media queries. auto-fit collapses empty tracks so existing items stretch; auto-fill keeps them.

Explain the position values.

static is the default flow. relative offsets from the normal position and is the anchor for absolute children. absolute leaves the flow and positions against the nearest positioned ancestor. fixed positions against the viewport. sticky behaves as relative until a scroll threshold (top), then sticks within its scroll container.

My z-index: 9999 does not work. Why?

Either the element is not positioned (static), or it sits inside a stacking context created by an ancestor (positioned with a z-index, or opacity below 1, transform, filter…). Z-index values only compete within the same stacking context, so the whole ancestor is stacked at its own level. Fix the ancestor, or move the element (a portal for modals).

Why might position: sticky not work?

No top (or other offset) is set; an ancestor has overflow hidden/auto/scroll, which becomes the scroll container; the parent is no taller than the element; or a flex/grid parent stretches the element. Fix the cause, for instance align-self: flex-start in a flex layout.

What is mobile-first design and how do you implement it?

You write the base CSS for small screens and add @media (min-width: …) blocks that enhance the layout for larger ones. It needs the viewport meta tag, fluid layouts (Flexbox, Grid, max-width), images with max-width: 100%, and relative units. It keeps the base CSS small and simple, and avoids undoing desktop styles on phones.

Transition vs animation? Which properties should you animate?

A transition animates between two states when a property changes; an animation uses @keyframes, can have many steps, loop and start without a trigger. Animate transform and opacity, which the browser can composite without layout or paint; avoid animating width, height, top or left. Respect prefers-reduced-motion.

Why use Tailwind (or not)? How does it differ from Bootstrap?

Tailwind provides small utility classes composed in markup — fast, consistent, small output, but long class lists and a build step. Bootstrap provides prebuilt styled components and a grid — fastest start, but sites look alike unless customised. Both need solid CSS knowledge and both are mobile-first.

Cheat sheet — CSS

  • Add CSS external <link rel="stylesheet"> in head (preferred); never rely on inline styles
  • Rule selector { property: value; } — end every line with a semicolon; invalid lines are ignored silently
  • Selectors p, .class, #id, [attr], a b, a > b, a + b, a ~ b, a, b
  • Pseudo :hover, :focus-visible, :nth-child(), :not(); ::before, ::after, ::placeholder
  • Specificity inline > ID > class/attribute/pseudo-class > tag; equal → later wins; avoid !important
  • Inherited color, font, line-height, text-align; not margin, padding, border, background, width
  • Variables --brand: #1a56db; on :root; use var(--brand, fallback)
  • Box model content + padding + border + margin; reset box-sizing: border-box
  • Margin collapse adjacent vertical margins merge; not in flex or grid
  • Units rem for type and space, px for borders, %/fr for fluid, dvh for mobile full height, ch for line length
  • Math calc(), min(), max(), clamp(min, preferred, max)
  • Flex container display:flex, flex-direction, justify-content (main), align-items (cross), flex-wrap, gap
  • Flex item flex: grow shrink basis; flex:1 equal shares; flex:none fixed; align-self; order
  • Flex gotchas container needs height to centre vertically; min-width: 0 to let items shrink
  • Centre flex: justify-content + align-items: center; grid: place-items: center
  • Grid grid-template-columns: repeat(3, 1fr), gap, grid-column: span 2, grid-template-areas
  • Responsive grid repeat(auto-fit, minmax(250px, 1fr))
  • Flex vs Grid one dimension vs two; Grid for the page, Flexbox for the parts
  • Position relative (anchor), absolute (nearest positioned ancestor), fixed (viewport), sticky (needs top)
  • z-index works on positioned or flex/grid items; compared only within a stacking context
  • Responsive viewport meta + mobile-first min-width queries + max-width: 100% images
  • Breakpoints about 640 / 768 / 1024 / 1280px; choose them from the content
  • Motion animate transform and opacity; transition on the base rule; honour prefers-reduced-motion
  • Tailwind utility classes, md: responsive and hover: state prefixes, dark:; never build class names dynamically
  • Organise reset, single-class BEM names, tokens as variables, no IDs, shallow selectors

Practice — CSS

  1. Specificity quiz. Write five conflicting rules for one paragraph (a tag, a class, a tag with a class, an id, an inline style). Predict the colour, then check in DevTools (Styles shows what lost). Done when all five predictions are right and you can explain each score.
  2. Box model by hand. Make a 300px wide box with padding, border and margin, first with content-box, then border-box. Measure the box in DevTools and note the totals. Done when the numbers match your calculation (344px and 300px).
  3. Flexbox Froggy. Complete all levels of Flexbox Froggy (flexboxfroggy.com). Done when you can explain justify-content, align-items, flex-direction, order and align-self without notes.
  4. CSS Grid Garden. Complete all levels of Grid Garden (cssgridgarden.com). Done when you can write grid-column, grid-row and grid-area placements from memory.
  5. Five Flexbox layouts. Build from scratch, without copying: a navbar (logo left, links right), a centred login card on a full screen, a wrapping card row, a sticky footer, and a sidebar with content that stacks on phones. Done when each works at 320px and 1440px.
  6. Style the profile page (roadmap build). Take your semantic profile page from the HTML practice and style it with plain CSS only: reset, variables for colours and spacing, system font stack, a flex navbar, a sticky header, a hero section, a project cards grid with auto-fit, hover and focus states with transitions, a footer and a dark-mode variant with prefers-color-scheme. Done when Lighthouse gives 90+ for accessibility and the page works at 320px with no horizontal scroll.
  7. Responsive landing page (roadmap build). Pick a free design from Frontend Mentor (frontendmentor.io), a "newbie" or "junior" landing page challenge. Build it mobile-first with Flexbox and Grid: a header with a collapsing menu, hero, feature cards, testimonial and footer. Compare against the mobile and desktop previews at the specified widths. Done when it matches both previews and passes the keyboard-only test.
  8. Positioning lab. Build a product card with an absolutely positioned "Sale" badge, a sticky table header inside a scrolling container, and a modal overlay with a centred dialog using position: fixed. Then deliberately break it: remove position: relative from the card and put overflow: hidden on a parent of the sticky header; fix each in DevTools.
  9. Animate safely. Add a button hover transition, a card fade-in-up animation and a loading spinner. Then add the prefers-reduced-motion block and test it by turning on "reduce motion" in your operating system or in DevTools (Rendering panel). Done when the Performance panel shows no layout work during the animations.
  10. Rebuild with Tailwind. Create a Vite + React project, install Tailwind, and rebuild the product card and the navbar with utility classes only, including md: and hover: variants and dark mode. Done when the Tailwind version looks identical to your plain-CSS one and you can point to the CSS each class generates.

HTML is the skeleton of every web page. A React component, a Thymeleaf template and a hand-written file all end up as HTML in the browser, so you must know it well even if you never write a raw .html file at work. Good HTML gives you accessibility, search ranking, working forms and a layout that CSS can style easily. Bad HTML (a page made of <div> soup) fails all four.

This module teaches HTML the way professionals use it: the right element for the job. Module 3 styles what you build here, Module 4 and Module 5 make it interactive, and the forms you learn here are what your Spring Boot controllers receive and validate (Spring Boot · Module 2). You will finish by building a personal profile page.

  • Write a valid HTML5 page and explain every line of the boilerplate.
  • Choose the correct element for text, links, images, lists and tables.
  • Structure a page with semantic elements such as header, nav, main, article and footer.
  • Build accessible forms with labels, the right input types and validation attributes, and explain why the server must validate again.
  • Make a page usable with a keyboard and a screen reader, and check it with Lighthouse.
  • Add meta tags for SEO and link previews, and validate your HTML.

HTML basics and the page boilerplate, line by line

An HTML document is a tree of elements written as tags with attributes; every page starts from the same small boilerplate — doctype, html with lang, head with charset, viewport and title, and a body.

HTML is text. A browser reads it and builds the DOM (see How the browser renders a page). You can write it in any editor — VS Code is the usual choice — save it as index.html and double-click the file to open it. For live reload while you edit, use the Live Server extension or the Vite dev server.

The boilerplate

<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>Asha Rao - Java Developer</title>
    <link rel="stylesheet" href="styles.css">
    <script src="app.js" defer></script>
  </head>
  <body>
    <h1>Hello, world</h1>
  </body>
</html>
<!doctype html>
Tells the browser to use modern standards mode. Without it, browsers fall back to quirks mode, which imitates 1990s behaviour and breaks CSS layouts in odd ways. Always the first line. It is not a tag, and it is case-insensitive.
<html lang="en">
The root element; everything else lives inside it. lang declares the page language so screen readers pick the right pronunciation, translation tools know what to translate and search engines classify the page. Use hi for Hindi, en-IN for Indian English.
<head>
Information about the page — nothing inside it is displayed (except the title in the tab).
<meta charset="utf-8">
The character encoding. Without it, "₹" or "नमस्ते" may appear as garbage like â‚¹. Keep it within the first 1,024 bytes, so put it first in the head. Also make your server send Content-Type: text/html; charset=UTF-8 (Spring does by default).
<meta name="viewport" ...>
Tells mobile browsers to use the real device width instead of pretending to be a 980-pixel-wide desktop. Without it, your responsive CSS does not work on phones (see Responsive design). Do not add user-scalable=no; zooming is an accessibility need.
<title>
The text of the browser tab, bookmarks and search results. Required, unique per page, ideally 50–60 characters.
<link rel="stylesheet" href="...">
Loads a CSS file. Put it in the head so the page is styled on first paint.
<script src="..." defer></script>
Loads JavaScript without blocking the parser (see defer and async).
<body>
Everything the user sees.

In VS Code, type ! and press Tab (Emmet) to generate this skeleton.

Elements, tags and attributes

An element is a start tag, content and an end tag. Attributes are extra settings in the start tag, written as name="value".

<a href="https://developer.mozilla.org" target="_blank">MDN Web Docs</a>
<!--   ^ tag name   ^ attribute      ^ attribute         ^ content   ^ end tag -->
  • Void elements have no content and no end tag: <br>, <hr>, <img>, <input>, <meta>, <link>. In HTML you write <img ...>, not <img ... /> (the slash is allowed and ignored; JSX in React requires it).
  • Boolean attributes are on when present: <input required disabled>. disabled="false" is still disabled — remove the attribute to turn it off.
  • Always quote values with double quotes. Tag and attribute names are case-insensitive but lowercase is the convention.
  • Global attributes work on any element: id (unique in the page), class (one or more names, for CSS), title (tooltip), hidden, tabindex, lang, data-* (your own data, e.g. data-product-id="42", read in JavaScript as el.dataset.productId).

Nesting rules

Elements nest like brackets in Java: the last one opened is the first one closed. <p><strong>text</strong></p> is right; <p><strong>text</p></strong> is wrong. Some elements restrict their children: <ul> may contain only <li>; a <p> cannot contain a <div> or another <p> (the browser closes the paragraph early); an <a> cannot contain another <a> or a <button>; a <table> expects rows, not random elements.

Block vs inline

Block elementsInline elements
LayoutStart on a new line, fill the full widthSit inside a line of text, only as wide as their content
Width and heightCan be setIgnored for width/height; vertical margin has no effect
Examplesdiv, p, h1–h6, ul, section, form, tablespan, a, strong, em, img, code, label

Block or inline is just the default display value; CSS can change it (The box model and display). In the HTML spec the stricter idea is the content model: flow content, phrasing content and so on — an inline element should hold only phrasing content.

Comments and whitespace

<!-- This is a comment. The browser ignores it, but it is visible in View Source. -->
<p>Many     spaces   and
new lines collapse    into single spaces.</p>

HTML collapses runs of spaces and line breaks into one space. To force a line break use <br> (for addresses and poems only, not for spacing; use CSS margin), and for preformatted text use <pre>. Never put secrets in comments — users see them.

HTML entities

Characters that mean something to HTML must be written as entities when you want them as text. Entities start with & and end with ;.

You wantWriteNotes
<&lt;Otherwise it starts a tag
>&gt;Optional but tidy
&&amp;Also in URLs inside attributes: ?a=1&amp;b=2
"&quot;Needed inside a double-quoted attribute
Non-breaking space&nbsp;Keeps two words together; do not use for layout
©&copy;Or just type ©, since the file is UTF-8
₹&#8377;Numeric code; or type ₹ directly

With charset="utf-8" you can type most characters directly; entities are essential only for <, & and quotes in attributes. To show HTML code on a page, escape it: <code>&lt;p&gt;</code> displays as <p>. This is also how XSS attacks work in reverse: a framework escapes user text for you (React does); Thymeleaf's th:text escapes, th:utext does not.

Rules

  • Start every page with <!doctype html>, set lang, declare charset and the viewport meta, and give a <title>.
  • id values must be unique per page and contain no spaces.
  • Close every element that needs closing, and nest properly.

Conventions

  • Lowercase tags and attributes, double quotes, two-space indentation.
  • Name files in lowercase with hyphens: contact-us.html. The home page is index.html, which servers return for /.
  • Class names describe meaning (product-card), not looks (red-big).

Edge cases

  • The browser never rejects bad HTML; it repairs it silently. A missing </div> may break the layout far below the actual mistake, and the result differs between nested cases. Validate (see Validating HTML).
  • Omitting <html>, <head> and <body> tags is legal — the parser adds them — but always write them.
  • Duplicate ids do not raise an error; getElementById just returns the first one.

Mistake: using <br> and &nbsp; to create space

Stacks of <br><br><br> or non-breaking spaces make spacing that cannot be controlled or made responsive. Use margin and padding in CSS.

Interview angle

  • "What does <!doctype html> do?" — triggers standards mode instead of quirks mode.
  • "Why the viewport meta tag?" — so mobile browsers use the device width; required for responsive design.
  • "What are void elements? Block vs inline?" — give examples and the layout difference.

Headings, text, links and generic containers

Use headings for outline (one h1, no skipped levels), p for paragraphs, strong and em for meaning, a for links with correct URLs and rel attributes, and div or span only when no meaningful element fits.

Headings

<h1> to <h6> form the outline of the page, like chapter and section titles in a book. Screen-reader users jump from heading to heading to scan a page, and search engines use them to understand it. So choose levels by structure, never by size — change the size with CSS.

  • One <h1> per page: the main topic ("Asha Rao — Java Developer").
  • Do not skip levels: an h2 is followed by h3, never directly by h4.
  • Do not use a heading just to make text big or bold.
<h1>Asha Rao</h1>
  <h2>Projects</h2>
    <h3>Library Management System</h3>
    <h3>Expense Tracker API</h3>
  <h2>Skills</h2>

Paragraphs and text-level elements

<p> is a paragraph. Inside text, choose the element by meaning:

ElementMeaningLooks like (default)
<strong>Strong importance or warningBold
<em>Stress emphasis (changes the sentence meaning when read aloud)Italic
<b>Draw attention, no extra importance (a keyword)Bold
<i>Alternate voice: a foreign word, a technical term, a thoughtItalic
<mark>Highlighted for reference (a search hit)Yellow background
<code>, <kbd>Code; keyboard inputMonospace
<blockquote>, <q>Long quotation; short inline quotationIndented; with quote marks
<abbr title="...">Abbreviation with expansionDotted underline
<sub>, <sup>, <small>Subscript; superscript; side commentsSmaller text

The rule: strong and em carry meaning (a screen reader changes its voice); b and i are only styling-like hints. If you want bold looks without meaning, use CSS font-weight. Also useful: <hr> (a thematic break between topics), <br> and <pre> (keeps whitespace, used with <code> for code blocks).

Links

The anchor element <a href="..."> is what makes the web a web. The href can be a lot of things.

<!-- Absolute URL: another site -->
<a href="https://developer.mozilla.org/en-US/docs/Web/HTML">MDN HTML guide</a>

<!-- Relative URL: another file in your site -->
<a href="projects.html">Projects</a>           <!-- same folder -->
<a href="blog/first-post.html">First post</a>  <!-- sub-folder -->
<a href="../index.html">Home</a>               <!-- one folder up -->
<a href="/about">About</a>                    <!-- root-relative: from the site root -->

<!-- In-page anchor: jumps to the element with id="contact" -->
<a href="#contact">Contact me</a>
<h2 id="contact">Contact</h2>

<!-- Other schemes -->
<a href="mailto:asha@example.com?subject=Hello">Email me</a>
<a href="tel:+919876543210">Call +91 98765 43210</a>

<!-- Download a file -->
<a href="files/asha-rao-cv.pdf" download>Download my CV (PDF)</a>

Absolute vs relative: an absolute URL has the scheme and host; a relative one is resolved against the current page's URL. Use relative links inside your own site so it works on localhost, staging and production alike. Be careful with a leading slash: /about starts from the host root, so it breaks when the site is deployed in a sub-path like /myapp/ (for example on GitHub Pages).

Opening in a new tab

<a href="https://github.com/asharao" target="_blank" rel="noopener noreferrer">
  My GitHub (opens in a new tab)
</a>

target="_blank" opens a new tab. Modern browsers already treat it as noopener, but writing rel="noopener noreferrer" is still the standard habit and protects older browsers: noopener stops the new page from controlling yours through window.opener (a phishing trick), and noreferrer hides your page's URL from the target. Warn users when a link opens a new tab, and do not do it for ordinary internal links — users can choose that themselves.

Writing good link text

Screen-reader users often list all links on a page without the surrounding text. So the link text must make sense alone: "Download my CV" is good; "click here" and "read more" are bad. Do not use a bare long URL as the text either.

div and span: the last resort

<div> (block) and <span> (inline) have no meaning. They are neutral boxes for grouping elements so CSS or JavaScript can target them. Use them only when no semantic element fits — a wrapper for a layout, a styled word inside text. Overusing div is called "div soup", and is the most common beginner problem (see Semantic HTML).

Wrong: headings for looks, links without meaning

<h4>Welcome</h4>       <!-- chosen for its size -->
<h1>Menu</h1><h1>Cart</h1> <!-- two h1 -->
<a href="/docs">click here</a>

Right: structure first, style with CSS

<h1 class="page-title">Welcome</h1>
<h2>Menu</h2>
<a href="/docs">Read the documentation</a>

Rule: links go somewhere, buttons do something

Use <a href> to navigate to a URL and <button> to perform an action (open a menu, save). An <a> without href is not keyboard-focusable, and a button used as a link cannot be opened in a new tab.

Edge cases

  • A link to an id that does not exist does nothing (no error). Anchors are case-sensitive.
  • mailto: and tel: open the user's mail or phone app, which may not exist on a desktop.
  • The download attribute works only for same-origin URLs.
  • In a SPA with React Router you use a router <Link>, which renders an <a> but prevents a full page load.

Interview angle

  • <strong> vs <b>, <em> vs <i> — meaning versus appearance.
  • "Why rel="noopener noreferrer"?" — stop window.opener access and hide the referrer.
  • "Absolute vs relative URL?" — with or without the origin; relative links stay portable between environments.

Images, figures and lists

An image needs a useful alt text and explicit width and height; lists use ul, ol or dl depending on whether order or name–value pairs matter; figure and figcaption attach a caption to content.

Images

<img src="images/asha.jpg" alt="Asha Rao smiling at her desk" width="400" height="300">

<!-- Below the fold: load only when near the screen -->
<img src="images/project-1.png" alt="Dashboard showing monthly expenses as a bar chart"
     width="800" height="450" loading="lazy">

<!-- Decorative image: empty alt -->
<img src="images/divider.svg" alt="" width="200" height="10">
src
The image URL (relative or absolute). A wrong path shows a broken-image icon and a 404 in the Network panel.
alt
Text replacement: read by screen readers, shown when the image fails to load, and used by search engines. Always present.
width and height
The image's intrinsic size in pixels (numbers only, no px). The browser uses them to reserve space before the image downloads, which prevents the page jumping (layout shift). CSS such as max-width: 100%; height: auto; still makes it responsive.
loading="lazy"
Downloads the image only when it comes near the viewport. Use it for images below the fold, never for the main hero image at the top.
srcset and sizes
Offer several sizes so the browser picks the best for the screen. A brief example is below.
<img src="hero-800.jpg"
     srcset="hero-400.jpg 400w, hero-800.jpg 800w, hero-1600.jpg 1600w"
     sizes="(min-width: 800px) 800px, 100vw"
     alt="Mumbai skyline at sunset" width="800" height="450">

The w numbers are the file widths. sizes says how wide the image will be displayed, and the browser chooses the smallest file that fits the screen's pixel density. A phone on mobile data then downloads 400 pixels, not 1,600.

Writing alt text

  • Describe the purpose, not just the picture: for a photo in an article, say what it shows; for a logo that links home, say "Company name – home".
  • Decorative images (borders, background flourishes) get alt="" so screen readers skip them. Omitting alt entirely is worse, because the reader may read out the file name.
  • Do not start with "image of" or "picture of"; the screen reader already announces it as an image.
  • If the text is in the image (a banner saying "50% off"), repeat that text in the alt.
  • Keep it short, about one sentence. A complex chart needs a nearby text description.

Image formats

FormatBest for

figure and figcaption

<figure>
  <img src="images/er-diagram.png" alt="ER diagram of customers, orders and products"
       width="600" height="400">
  <figcaption>Figure 1: Database design of the shop project</figcaption>
</figure>

<figure> wraps self-contained content referenced from the text — an image, a diagram, a code listing — and <figcaption> is its caption. Do not use it for every image; use it when a caption makes sense.

Lists

Lists tell assistive technology "these items belong together" and announce "list, 3 items".

<!-- Unordered: order does not matter -->
<ul>
  <li>Java</li>
  <li>Spring Boot</li>
  <li>PostgreSQL</li>
</ul>

<!-- Ordered: order matters -->
<ol>
  <li>Clone the repository</li>
  <li>Run the build</li>
  <li>Start the app</li>
</ol>

<!-- Description list: terms and their descriptions -->
<dl>
  <dt>Email</dt>
  <dd>asha@example.com</dd>
  <dt>City</dt>
  <dd>Pune</dd>
</dl>
  • <ol> accepts start="5", reversed and type="a" (letters). <li value="10"> sets one item's number.
  • Lists nest: put the inner <ul> inside an <li>, not beside it.
  • Navigation menus are lists of links: <nav><ul><li><a>…</a></li></ul></nav>. CSS then removes the bullets and lays the items out in a row.
  • <dl> fits key–value data such as a profile summary, glossary or product specifications.

Audio, video and embeds (brief)

<video controls src="demo.mp4" width="640"></video> and <audio controls src="song.mp3"></audio> need no plugin. Always provide controls; avoid autoplay with sound. <iframe> embeds another page (YouTube, Google Maps) — give it a title for accessibility, and remember that you are loading a third party's code.

Rule: every img has an alt attribute; informative images have meaningful text

Missing alt is the most common accessibility failure on the web, and Lighthouse reports it. Decorative images use alt="".

Convention: set dimensions and lazy-load below the fold

Always write width and height. Add loading="lazy" to images further down the page, but never to the largest image above the fold, or the page appears to load slower.

Edge cases

  • A relative src works when you open the file from disk, but breaks if the folder structure changes on the server. Check case: Photo.JPG and photo.jpg are different files on Linux servers, though Windows ignores case, so a page that works on your laptop can fail in production.
  • An image inside a link needs alt text that describes the link target, since the image is the link's only text.

Mistake: building a list with line breaks

Typing "- Java<br>- Spring" is not a list; screen readers do not announce it and CSS cannot style the items individually. Use ul and li.

Interview angle

  • "Why set width and height on images?" — to reserve space and avoid layout shift (CLS).
  • "What is alt for and when is it empty?" — screen readers, broken images and SEO; empty for decorative images.
  • "ul vs ol vs dl?" — unordered, ordered, name–value pairs.

Semantic HTML and page layout

Semantic elements such as header, nav, main, article, section, aside and footer say what each part of the page is, which gives screen readers landmarks, search engines context and you maintainable markup — a div says nothing.

A semantic element describes its meaning, not its looks. <nav> means "navigation links"; <div> means nothing. Compare the Java equivalent: naming a class OrderService instead of Class1. The page may look identical, but the meaning is available to tools.

Why semantics matter

  • Accessibility. Browsers build an accessibility tree from your HTML. Screen readers offer shortcuts to jump to landmarks like "main" or "navigation". With only divs, a blind user must read the whole page linearly.
  • SEO. Search engines weigh content in main and headings higher than repeated navigation.
  • Maintainability. <footer> tells the next developer more than <div class="f2">.
  • Built-in behaviour. Native elements bring keyboard support, default styles and features for free (button, details, dialog).
  • Reader mode and browser features find the article content only if it is marked up.

When in doubt, ask: "does this have a heading, and is it part of the page outline?" If yes, section. "Could I move it to another site and it still makes sense?" article. Otherwise div. Using div is fine; it is overusing it that hurts.

A full semantic page skeleton

<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Asha Rao - Java Full-Stack Developer</title>
</head>
<body>
  <a class="skip-link" href="#main">Skip to main content</a>

  <header>
    <p class="logo">Asha Rao</p>
    <nav aria-label="Main">
      <ul>
        <li><a href="#about">About</a></li>
        <li><a href="#projects">Projects</a></li>
        <li><a href="#contact">Contact</a></li>
      </ul>
    </nav>
  </header>

  <main id="main">
    <h1>Asha Rao - Java Full-Stack Developer</h1>

    <section id="about">
      <h2>About me</h2>
      <p>I build REST APIs with Spring Boot and interfaces with React.</p>
    </section>

    <section id="projects">
      <h2>Projects</h2>
      <article>
        <h3>Expense Tracker API</h3>
        <p>Posted <time datetime="2026-08-02">2 August 2026</time></p>
        <p>A Spring Boot and PostgreSQL service for personal budgets.</p>
      </article>
    </section>

    <aside>
      <h2>Currently learning</h2>
      <p>React and Docker.</p>
    </aside>
  </main>

  <footer id="contact">
    <address>
      <a href="mailto:asha@example.com">asha@example.com</a>
    </address>
    <p>&copy; 2026 Asha Rao</p>
  </footer>
</body>
</html>

A div version of the same page would look the same after styling, but the screen reader would report no landmarks at all. With the semantic version, header becomes the "banner" landmark, nav "navigation", main "main", aside "complementary" and footer "contentinfo" (header and footer map to these only when they are direct children of the body).

Rule: one main, one h1, landmarks not nested wrongly

A page has exactly one visible <main>, and it is not inside header, footer, nav, aside or article. Give each nav a label if there is more than one.

Convention: choose the element first, add classes second

Write <nav class="site-nav">, not <div class="nav">. Semantic element for meaning, class for styling hooks. Add a "skip to main content" link as the first focusable element so keyboard users can bypass the menu.

Exceptions

  • Semantic tags carry almost no default styling (section, nav and main are just blocks), so the visual result is unchanged. The benefit is for tools.
  • Do not wrap everything in a section. A group made only for layout is a div.
  • <header> inside an <article> is the article's header, and is not a page-level banner landmark.

In real projects

React components should return semantic markup too: a <Navbar> renders a <nav>, a <ProductCard> renders an <article>. A component library that renders only divs makes your whole app inaccessible — check what it outputs in Elements.

Interview angle: "What is semantic HTML and why use it?"

  • Elements named by meaning; benefits: accessibility landmarks, SEO, readable code, native behaviour.
  • List header, nav, main, section, article, aside, footer and explain section vs article vs div.
  • Say "only one main per page".

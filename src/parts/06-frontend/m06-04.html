Environment variables in Vite and the production build

Vite reads .env files and exposes only variables that start with VITE_ as import.meta.env.VITE_…, baked into the JavaScript at build time; npm run build produces a static dist folder, and nothing in it can be secret.

Why the API URL must not be hard-coded

On your laptop the API is at http://localhost:8080/api. In production it is https://api.acme.in/api, and on a staging server it is something else again. If you type the URL into your code, you must edit code for every environment and you will one day ship localhost to production. An environment variable is a named setting that lives outside the code and changes per environment. The code only says "use whatever VITE_API_URL is".

The .env files

Vite loads these files from the project root (the folder with package.json):

FileLoaded whenCommit to Git?
.envAlwaysYes, if it holds only harmless defaults
.env.localAlways; your personal overridesNo (git-ignored)
.env.developmentMode development (npm run dev)Yes
.env.productionMode production (npm run build)Yes
.env.[mode].localThat mode only; local overridesNo (git-ignored)

A mode is a name for the situation. vite (dev server) runs in development, vite build runs in production, and you can invent your own: vite build --mode staging loads .env.staging. When the same variable is in several files, the more specific file wins (.env.production.local beats .env.production, which beats .env.local, which beats .env), and a variable already set in the shell or by the hosting platform beats all files. The Vite project template already puts *.local in .gitignore.

VITE_API_URL=http://localhost:8080/api
VITE_APP_NAME=Employee Manager (dev)
VITE_API_URL=https://api.acme.in/api
VITE_APP_NAME=Employee Manager

Using them in code

Vite does not use Node's process.env in browser code. It gives you import.meta.env:

const apiUrl = import.meta.env.VITE_API_URL;     // 'http://localhost:8080/api' in dev
const appName = import.meta.env.VITE_APP_NAME;

// Built-in values, always present:
import.meta.env.MODE;        // 'development' | 'production' | your custom mode
import.meta.env.DEV;         // true when running npm run dev
import.meta.env.PROD;        // true in the production build
import.meta.env.BASE_URL;    // the base path the app is served from ('/' by default)

if (import.meta.env.DEV) {
  console.log('Calling API at', apiUrl);        // dev-only logging
}

Rules

  • Only variables starting with VITE_ are exposed to your code. A variable called API_URL is undefined in the browser. The prefix is a safety net so that a stray server variable is not leaked by accident.
  • Values are always strings. VITE_ENABLE_X=false gives the string "false", which is truthy. Compare explicitly: import.meta.env.VITE_ENABLE_X === 'true'.
  • Values are replaced at build time. Vite copies the text into the bundle. Changing the variable on the server later does nothing until you build again.
  • Restart npm run dev after editing a .env file; the dev server reads them at start-up.

Never put secrets in frontend environment variables

A VITE_ variable ends up as plain text inside dist/assets/*.js. Anyone can open DevTools, search the bundle and read it. The prefix does not hide anything; it only decides what is included.

  • Fine in the frontend: the API base URL, an app name, a feature flag, a publishable key that is designed to be public (Stripe publishable key, a Google Maps key restricted to your domain).
  • Never: database passwords, the JWT signing secret, a Stripe secret key, cloud access keys, anything that grants power. Those live only in the Spring Boot backend (environment variables or a secrets manager), and the frontend asks the backend to act for it.

If you ever committed a secret, treat it as leaked and rotate it. Removing it from Git history is not enough.

Typing the variables (TypeScript projects)

/// <reference types="vite/client" />

interface ImportMetaEnv {
  readonly VITE_API_URL: string;
  readonly VITE_APP_NAME: string;
}

interface ImportMeta {
  readonly env: ImportMetaEnv;
}

Fail early when a variable is missing

A missing VITE_API_URL produces confusing errors later ("requests go to undefined/employees"). Check once at start-up:

function required(name) {
  const value = import.meta.env[name];
  if (!value) throw new Error(`Missing environment variable ${name}. Check your .env files.`);
  return value;
}

export const config = {
  apiUrl: required('VITE_API_URL'),
  appName: import.meta.env.VITE_APP_NAME ?? 'Employee Manager',
};

npm run build and the dist folder

The Vite template's package.json has these scripts:

CommandWhat it does
npm run devStarts the dev server with hot module replacement. Not optimised; for development only.
npm run buildCreates the production bundle in dist/ (runs vite build; the TypeScript template runs the type check first).
npm run previewServes the built dist/ locally to check it. Not a production server.
npm run lintRuns ESLint, if the template includes it. The build does not run it for you.

During the build, Vite starts at index.html and follows every import to produce optimised files. The browser cannot run your JSX or your hundreds of small modules efficiently, so the build does these jobs:

  • Compiles JSX (and TypeScript) to plain JavaScript.
  • Bundles modules into a few files and tree-shakes unused exports.
  • Minifies JavaScript and CSS (short names, no spaces).
  • Splits code where you use dynamic import() (for example lazy-loaded routes), so users download a page's code only when they visit it.
  • Hashes file names (index-3f9a2c1b.js) so that a new release has new names and browsers never use a stale cached file.
  • Replaces import.meta.env.VITE_* with the real values.

Other settings you will meet

  • base in vite.config.js: set it (for example base: '/hr/') when the app lives under a sub-path such as https://acme.in/hr/. React Router then needs the same value as basename. Most apps use the default /.
  • Source maps (build.sourcemap) are off by default. They map minified code back to your source for debugging; upload them to an error tracker rather than serving them publicly if your code is sensitive.
  • One build per environment. Because values are baked in, a staging build and a production build are different artefacts. If you need one image for all environments, load a /config.json at start-up instead (a runtime config) and keep the build generic.

Check the production build before deploying

Run npm run build and npm run preview, then click through the app. Some bugs only appear in production: wrong environment variable, a missing SPA fallback, a case-sensitive import that worked on Windows but breaks on Linux (./Header.jsx vs ./header.jsx). Also open the Network tab and confirm that requests go to the production API URL, not localhost.

Edge cases

  • If you set a variable in the hosting dashboard after the first deploy, you must trigger a new build for it to take effect.
  • An absolute http:// API URL called from an https:// page is blocked by the browser as mixed content. Production APIs must use HTTPS.
  • A blank white page after deploy with a console error about a .js file usually means the server returned index.html for a missing asset or the base path is wrong.

Interview: "How do you configure a React app for different environments?"

  • .env.development and .env.production, variables prefixed with VITE_, read with import.meta.env; set in the host's dashboard or CI for real deployments.
  • They are compiled into the bundle, so they are public: only non-secret configuration belongs there. Secrets stay on the backend.
  • Changing a value needs a rebuild; for run-time changes use a config file fetched at start-up.

Deploying the React app: Vercel, Netlify, Nginx or Spring Boot

A built React app is a folder of static files, so any static host can serve it; the one thing to configure is the SPA fallback (unknown paths return index.html), and the choice between a separate host or Spring Boot's own static folder is a trade-off between convenience and simplicity.

What you are deploying

After npm run build the dist folder contains one HTML page and some hashed JavaScript and CSS (see the previous article). All the "pages" of your app, such as /login and /employees/7, are drawn by JavaScript in the browser using the History API. To the web server, they do not exist as files.

The SPA fallback problem

Open https://app.acme.in/, click around to /employees/7: works, because React Router changes the URL without asking the server. Now press F5. The browser asks the server for the path /employees/7. There is no such file, so a plain static server answers 404. The same happens when a user opens a bookmark or a shared link.

The fix is a fallback rule (also called a rewrite): for any path that is not a real file, return index.html with status 200. React then starts, reads the URL and shows the right page. Every hosting option below needs this rule in its own syntax.

Option 1: Vercel

  1. Push the React project to GitHub (Git · Module 2).
  2. In Vercel, import the repository. It detects Vite; the build command is npm run build and the output directory is dist.
  3. Under the project's environment-variable settings add VITE_API_URL with your production API URL.
  4. Add the SPA rewrite below, commit, and push. Every push deploys; every pull request gets its own preview URL.
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}

Files that exist (such as the JavaScript assets) are served first; the rewrite applies to paths that do not match a file.

Option 2: Netlify

The flow is the same: connect the repository, build command npm run build, publish directory dist, set VITE_API_URL. For the fallback, put a _redirects file in the public/ folder (Vite copies it into dist/), or use netlify.toml:

/*    /index.html   200
[build]
  command = "npm run build"
  publish = "dist"

[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200

The status 200 matters: it means "serve this content, keep the URL". A 301/302 would change the URL in the address bar.

Cross-origin deployment: what changes

On Vercel or Netlify the app is at https://employee-app.vercel.app while the API is elsewhere, so every call is cross-origin. Three things follow:

  • CORS: add the exact deployed origin to your Spring Boot allowed origins, with no trailing slash and the right scheme (CORS in Spring Boot). Use an environment variable on the backend, not a hard-coded list.
  • HTTPS on both sides, or the browser blocks the calls as mixed content.
  • Cookies: if the refresh token is an httpOnly cookie (JWT flow), a cookie set by api.acme.in for a page on another site is a third-party cookie. It needs SameSite=None; Secure, and browsers increasingly restrict such cookies. The robust design is to serve the app and the API under the same parent domain (app.acme.in and api.acme.in count as the same site) or behind one origin, as in the next options.

Option 3: Nginx

Nginx is a fast web server and reverse proxy (DevOps · Module 2). One Nginx can serve the React files and forward /api to Spring Boot. The browser sees one origin, so there is no CORS at all, and the app can call the relative URL /api.

server {
    listen 80;
    server_name app.acme.in;

    root /usr/share/nginx/html;
    index index.html;

    gzip on;
    gzip_types text/css application/javascript application/json image/svg+xml;

    # Hashed assets never change: cache for a year
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # The HTML entry point must always be revalidated, or users keep an old app
    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    # Forward API calls to Spring Boot
    location /api/ {
        proxy_pass http://backend:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # SPA fallback: real file, real folder, otherwise index.html
    location / {
        try_files $uri $uri/ /index.html;
    }
}

In Docker, a two-stage build compiles with Node and ships only the static files in a small Nginx image (DevOps · Module 3):

FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
ARG VITE_API_URL=/api
ENV VITE_API_URL=$VITE_API_URL
RUN npm run build

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80

The build argument is how the variable reaches Vite, because it is read at build time, not when the container starts.

Option 4: Spring Boot's static folder

Spring Boot serves files from src/main/resources/static (on the classpath at /static) without any configuration. Copy the contents of dist there, build the JAR, and one process serves both the API and the UI. Use VITE_API_URL=/api.

employee-api/
├── pom.xml
└── src/main/
    ├── java/in/acme/employee/...
    └── resources/
        ├── application.yml
        └── static/            ← contents of the React dist/ folder
            ├── index.html
            └── assets/...

Spring only returns files that exist, so a refresh on /employees/7 gives 404 here too. Add the fallback by teaching the resource handler to return index.html for unknown paths. Controllers are matched first, so real /api/** endpoints keep working.

import java.io.IOException;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.io.ClassPathResource;
import org.springframework.core.io.Resource;
import org.springframework.web.servlet.config.annotation.ResourceHandlerRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;
import org.springframework.web.servlet.resource.PathResourceResolver;

@Configuration
public class SpaWebConfig implements WebMvcConfigurer {

    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        registry.addResourceHandler("/**")
                .addResourceLocations("classpath:/static/")
                .resourceChain(true)
                .addResolver(new PathResourceResolver() {
                    @Override
                    protected Resource getResource(String resourcePath, Resource location)
                            throws IOException {
                        Resource requested = location.createRelative(resourcePath);
                        return requested.exists() && requested.isReadable()
                                ? requested
                                : new ClassPathResource("/static/index.html");
                    }
                });
    }
}

If Spring Security is on, permit the static files and the SPA paths (permitAll for /, /index.html, /assets/** and the frontend routes), while /api/** stays protected; the frontend's own RequireAuth handles the login redirect. Many teams automate "build React, copy into the JAR" in the Maven or Gradle build with a frontend plugin, or in the CI pipeline (DevOps · Module 4).

Pros of serving from Spring Boot

  • One artefact, one server, one URL. Easy to demo and to run on a single VM.
  • Same origin: no CORS configuration, simple cookies.
  • No extra hosting account or cost.

Cons

  • A frontend-only change needs a rebuild and redeploy of the whole backend.
  • The Java server serves static files less efficiently than a CDN or Nginx; no global edge caching.
  • Frontend and backend release together, and you cannot scale or cache them separately.
  • Unknown paths (including mistyped /api/... URLs) can fall through to index.html unless you restrict the fallback.

Which should you choose?

  • Learning, portfolio, interview demo: Vercel or Netlify for the UI and any Java host for the API. It shows you can handle CORS and environment variables.
  • Company with Docker/Kubernetes: Nginx image (or a CDN) for the UI, a separate Spring Boot container, a reverse proxy in front of both.
  • Small internal tool, one team: Spring Boot static is the least moving parts.

Pre-deploy checklist

  • VITE_API_URL set for production; build run after setting it.
  • API reachable over HTTPS; allowed origins on the backend include the deployed UI origin.
  • SPA fallback configured and tested by refreshing a deep link.
  • A route for path="*" (404 page) exists in the app.
  • Hashed assets cached for long, index.html not cached (or revalidated).
  • No secrets or .env.local committed.

Common mistakes

  • Refresh gives 404 on any non-root page: the fallback rule is missing.
  • The deployed app calls http://localhost:8080: the variable was not set before the build.
  • CORS error only in production: the allowed origin has a trailing slash, uses http instead of https, or is the old preview URL.
  • Redirect rule with status 301 instead of 200 (Netlify) so the URL changes.
  • Serving npm run dev or npm run preview as the production server.
  • Case-sensitive file name errors that only break on a Linux build server.

Interview: "Your React app shows 404 when you refresh /employees/7 in production. Why?"

  • The route exists only in client-side JavaScript. On refresh the browser asks the server for that path; the server has no such file.
  • Configure a fallback to index.html with status 200: try_files in Nginx, a rewrite on Vercel, _redirects on Netlify, a resource resolver in Spring Boot.
  • Add the trade-offs: separate hosting needs CORS and HTTPS but deploys the UI independently; bundling in Spring Boot is simplest but couples releases.

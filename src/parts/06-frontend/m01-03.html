Browser DevTools: opening them, Elements and Console

DevTools is the debugger built into your browser: the Elements panel shows and edits the live DOM and CSS, and the Console shows errors and runs JavaScript — together they answer "what is the page doing, and why?".

For a frontend developer, DevTools is what the IDE debugger and log files are for a Java developer. These notes use Chrome (Edge is identical, Firefox is very similar). You will keep DevTools open for most of your working day, so learn it early.

You can also right-click anything on a page and choose Inspect. DevTools can dock to the bottom, the right or a separate window (the three-dots menu); the right side suits wide monitors. The command menu is a quick way to find features by name — type "screenshot" to capture a full-page screenshot, or "dark" to switch themes.

The Elements panel

The Elements panel shows the live DOM — not the HTML file you downloaded, but the tree as it is right now, including everything JavaScript added. This is why "View Source" (Ctrl+U) of a React app shows an empty <div id="root"> while Elements shows the whole page.

  • Select and expand nodes in the tree on the left; the page highlights the matching element, and hovering a node shows its size.
  • Edit HTML live. Double-click text or a tag, change it, press Enter. Right-click a node for Edit as HTML, Delete element, Copy → selector, Break on → attribute modifications, and Force state → :hover (to style a hover state without keeping the mouse there).
  • Drag nodes to reorder them and see the effect immediately.
  • Search the DOM with Ctrl+F — by text, CSS selector or XPath.

Changes are made only in your browser's memory. Refresh the page and they are gone; nothing is saved to the server. That is perfect for experiments — and a reminder to copy a working change into your source files.

Styles, Computed and the box model

Select an element and look at the right-hand side.

Styles
Every CSS rule that applies to the element, from most to least specific. A rule that lost the fight is shown with a line through it (strikethrough). Each rule shows the file and line number (click it to jump to Sources). Edit a value, or tick and untick the checkbox beside a declaration to switch it on and off. Click + to add a new rule. Colour swatches open a colour picker; arrow keys change numbers (Shift+arrow changes by 10).
Computed
The final value of every property after the cascade — for example 1rem becomes 16px, and an inherited colour is shown. Expand a property to see which rule supplied the value. Use it when you ask "why is this 24px?".
Box model diagram
A nested picture of the element's content, padding, border and margin with the numbers. Hover a layer to highlight it on the page. It makes spacing bugs obvious (see The box model).
Layout (Flexbox, Grid)
Elements with display: flex or grid get a small badge in the tree. Click it to draw overlays that show the flex items or grid lines and track sizes. Essential for learning Flexbox and Grid.
Event Listeners / Accessibility
Lists the JavaScript listeners attached to the element, and its accessibility tree entry (role, name) — handy for checking forms and buttons.

Tip: the fastest CSS debugging loop

Inspect the element, look in Styles for a struck-through rule (it lost), look in Computed for the winning rule, untick declarations until the page looks right, then copy the change into your CSS file. Do not guess and re-save repeatedly.

The Console panel

The Console does two jobs: it prints messages from the browser and your code, and it is a JavaScript REPL (read–eval–print loop) where you can run code in the context of the current page — much like jshell for Java, but connected to the live page.

Reading messages
  • Errors (red): an uncaught exception such as Uncaught TypeError: Cannot read properties of undefined (reading 'name'), a failed request (Failed to load resource: 404), or a CORS block. The right-hand link shows the file and line; the arrow expands the stack trace.
  • Warnings (yellow): deprecations and framework warnings such as React's "Each child in a list should have a unique key".
  • Info and logs: output of your console.log() calls. Use the level filter and the text filter box to cut the noise.
Logging helpers
console.log("order", order);          // object is expandable
console.table(orders);                // array of objects as a table
console.error("Payment failed", err); // red, with a stack trace
console.warn("Cart is empty");        // yellow
console.group("Checkout");            // indent related logs
console.log("step 1");
console.groupEnd();
console.time("load");                 // start a timer ...
// ... code to measure ...
console.timeEnd("load");              // ... prints: load: 12.3 ms
console.dir(document.body);           // inspect as an object, not as HTML
Using it as a REPL
document.title                           // "Chai counter"
document.querySelectorAll("a").length    // 14
$$("img").filter(i => !i.alt).length    // images missing alt text
$0                                       // the element selected in Elements
$_                                       // the result of the last expression
$("h1").textContent = "Hello"            // $ is a shortcut for querySelector
localStorage.getItem("token")            // read saved data
fetch("/api/hello").then(r => r.json()).then(console.log)
await (await fetch("/api/hello")).json() // top-level await works in the Console

$, $$, $0 and $_ exist only in the Console, not in your source files. Press Up for earlier commands, and use the Preserve log setting so messages survive a page reload. Multi-line code: Shift+Enter adds a new line.

Convention: remove debug logging before you commit

A stray console.log(user) can leak personal data in production, where anyone can open the Console. Keep logs temporary, or use a logging helper that is switched off in production builds. ESLint's no-console rule catches them.

Edge cases

  • console.log(obj) shows a live reference: if the object changes later and you expand it afterwards, you see the new values, not the values at the time of logging. Use console.log(JSON.parse(JSON.stringify(obj))) or structuredClone(obj) for a snapshot.
  • Browser extensions add their own errors to the Console. Test in an Incognito window (extensions are off by default) when an error looks unrelated to your code.
  • An error in the Console only says what failed in the browser. A 500 from your API shows up as a red network line, but the real cause is in the Spring Boot log.

Interview angle

  • "How do you debug a UI problem?" — inspect the element, read Styles/Computed for CSS, read Console errors, check Network for failed calls, then set breakpoints in Sources.
  • "View Source vs Elements?" — Source is the original response; Elements is the live DOM after JavaScript ran.

DevTools Network panel: reading every request

The Network panel lists every request the page makes with its status, size and timing, and shows the headers, payload and response of each — it is where you find out whether a bug is in React or in your Spring Boot API.

Open the panel before loading the page: open DevTools, click Network, then reload. Requests that happened earlier are not recorded. As a full-stack developer, this is the panel you will use most when connecting React to Spring Boot (Module 6).

The request list

Each row is one request. Useful default columns: Name (file or last path segment), Status, Type (document, script, stylesheet, fetch, xhr, image…), Initiator (which file or line made the request), Size (transferred over the network, versus the unpacked size below it), Time and Waterfall. Right-click the column header to add more, for example Protocol (h2, h3), Method and Domain.

The summary bar at the bottom shows the request count, total transferred data and the timings of DOMContentLoaded (blue line) and load (red line) on the waterfall.

Filtering to find your API calls

  • The type buttons — All, Fetch/XHR, JS, CSS, Img, Media, Font, Doc, WS, Wasm, Manifest, Other. Click Fetch/XHR to see only calls your JavaScript made with fetch() or XMLHttpRequest: this is your API traffic with the static files removed.
  • The filter box accepts text and special filters: /api/ matches URLs, method:POST, status-code:500, -domain:google.com to exclude, larger-than:100k.
  • The search icon (Ctrl+F) searches inside headers and response bodies of all requests.

Settings that save hours

  • Preserve log: keep the list when the page navigates or reloads. Without it, a redirect after a form submit wipes the evidence — tick it when debugging a login.
  • Disable cache: skips the browser cache while DevTools is open. Always on during development, so you never debug stale files.
  • Throttling: the dropdown that reads "No throttling" lets you pick Fast 4G, Slow 4G, 3G or Offline. Indians on mobile data do not get your office Wi-Fi speed, so test your loading states and spinners with it. Offline shows how your app handles a lost connection.
  • Block request URL (right-click a row): pretend a file or API fails to test your error handling.
  • Record (red circle) and Clear (the stop icon) control capture.
  • Export HAR (download arrow): saves everything as a HAR file to share with a teammate.

Copy as cURL: replay a request outside the browser

Right-click a request → Copy → Copy as cURL (bash or cmd). You get a complete command, including cookies and tokens. Paste it into a terminal to reproduce the call without the UI, edit it, or import it into Postman (File → Import → paste raw text). If the curl call works but the browser fails, the problem is browser-only: CORS, cookies or caching. If both fail, the problem is on the server.

curl 'http://localhost:8080/api/orders' \
  -H 'Accept: application/json' \
  -H 'Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...' \
  -H 'Content-Type: application/json' \
  --data-raw '{"productId":42,"quantity":2}'

Mind the secrets: the copied command contains your real token. Do not paste it into chat groups or tickets.

A worked debugging example

The orders page is blank. Steps: open DevTools → Network → tick Preserve log and Disable cache → reload → click Fetch/XHR. You see GET /api/orders in red with status 401. In Headers, the request has no Authorization line, so the token was not attached — the bug is in the React code that builds the request, not in Spring Boot. Had the status been 500, you would read the Response tab (Spring Boot's error JSON) and then the server log. Two minutes, no guessing.

Rule: look at the Network panel before you read any code

Decide first which side is wrong: was the request correct? what status came back? what was in the body? Only then open source files. This one habit separates efficient full-stack developers from frustrated ones.

Mistake: trusting the Console message for a failed CORS call

For a CORS failure the Network panel may show the request as (failed) or with a status that JavaScript cannot read, while the Console explains "blocked by CORS policy". The server might actually have processed the request. Check the Spring Boot log to see if it arrived.

Edge cases

  • With "Disable cache" off, you may see (disk cache) or (memory cache) in the Size column — no network request happened.
  • Responses larger than a limit may show as "Failed to load response data" in Preview; use "Open in new tab" or curl.
  • WebSocket traffic appears under the WS filter; click the row and use the Messages tab.

Interview angle

  • "How do you debug a failing API call from React?" — Network tab, Fetch/XHR filter, check status, request headers and payload, response body, then Spring Boot logs; replay with Copy as cURL or Postman.
  • "What is TTFB?" — time to first byte; mostly your server's processing time plus network latency.

DevTools: Application, Sources, Lighthouse and device mode

Application shows what the browser stores (localStorage, cookies), Sources lets you pause running JavaScript at breakpoints, Lighthouse audits performance, accessibility and SEO, and device mode tests phone screens.

Application panel: what the browser stores

The Application panel lists the data your site keeps in the browser. On the left, open the Storage section.

Local storage
Key–value strings (about 5 MB per origin) that stay until deleted. Read in JavaScript with localStorage.getItem("theme"). You can double-click a value to edit it, or click the delete icons. Many apps store a JWT here (a security trade-off covered in Spring Boot · Module 4).
Session storage
Same API, but cleared when the tab closes and separate per tab.
Cookies
Name, value, domain, path, expiry and the flags HttpOnly, Secure, SameSite. A JSESSIONID from Spring Security appears here. HttpOnly cookies are visible in DevTools but not to JavaScript.
IndexedDB, Cache storage, Service workers
Bigger structured storage and offline-app features, used by PWAs. Know they exist.

Clear site data (Application → Storage → Clear site data) resets everything for the site — the quickest way to test "first-time visitor" and to log out cleanly when a stale token causes strange behaviour.

localStorage.setItem("theme", "dark");
localStorage.getItem("theme");     // "dark"
localStorage.removeItem("theme");
localStorage.clear();              // everything for this origin
document.cookie;                   // readable cookies only (not HttpOnly ones)

Sources panel: breakpoints and stepping

console.log debugging works, but a debugger lets you pause the program and look at every variable — exactly like IntelliJ's debugger. In Sources, open a file (Ctrl+P), and click a line number to set a breakpoint. Trigger the code (click the button) and execution freezes on that line.

  • The Scope pane shows local and closure variables; the Call Stack pane shows how you got here; Watch evaluates expressions you add.
  • Controls: resume F8, step over F10, step into F11, step out Shift+F11.
  • Conditional breakpoint: right-click a line number → Add conditional breakpoint → order.id === 1042. It stops only when true.
  • Logpoint: like a breakpoint, but prints a message without stopping and without editing code.
  • The right-hand lists include XHR/fetch breakpoints (pause when a URL matches), DOM breakpoints (pause when an element changes) and Event listener breakpoints (pause on any click).
  • Writing debugger; in your code pauses it whenever DevTools is open. Remove it before committing.
  • Also tick Pause on exceptions to stop at the line where an error is thrown.

Vite and other tools bundle and compile your code. Source maps let DevTools show your original files (OrderList.jsx) instead of the bundled output, so breakpoints land on the lines you wrote. They are on by default in development.

Lighthouse: an automatic audit

The Lighthouse panel runs an audit and scores four areas from 0 to 100: Performance, Accessibility, Best Practices and SEO. Choose Mobile or Desktop, tick the categories, click Analyze page load. The report lists problems with advice, such as "Image elements do not have explicit width and height", "Buttons do not have an accessible name" or "Document does not have a meta description". Run it in an Incognito window with extensions off, so results are consistent. Scores vary a little from run to run, and a local dev server is slower than a production build, so audit the production build (npm run build then npm run preview) for real numbers.

Device mode: test phones without a phone

Press Ctrl+Shift+M. The page appears in a resizable frame. Pick a device (iPhone, Pixel, iPad) or choose Responsive and drag the handles; the width in pixels is shown at the top. It simulates screen size, device pixel ratio, touch events and the mobile user agent, and the three-dots menu adds a media-query ruler and network throttling. It is not a real phone — fonts, scrolling and performance differ — so test on a real device before release. See Responsive design.

Other panels in one line each

  • Performance: record a timeline of CPU, rendering and scripting to find slow frames and long tasks.
  • Memory: heap snapshots to find memory leaks in the browser.
  • Security / Privacy and security: certificate and mixed-content information.
  • React Developer Tools (a browser extension): adds Components and Profiler panels that show the React component tree, props and state. Install it before Module 5.

Tip: a debugging workflow for "it works on my machine"

  1. Console: any red error?
  2. Network: failed or wrong request?
  3. Elements: is the element present, what are its computed styles?
  4. Application: stale token or cached data? Clear site data.
  5. Sources: breakpoint where the data goes wrong.

Mistake: storing secrets in localStorage or in front-end code

Anything in the browser — localStorage, the JavaScript bundle, environment variables compiled into it — can be read by the user in seconds with DevTools. API secret keys and database passwords belong on the server only. Vite exposes only variables prefixed VITE_ to the browser, and those are public.

Edge cases

  • Local storage is per origin: localhost:5173 and localhost:3000 have separate storage.
  • localStorage can throw (QuotaExceededError, or a security error in some private modes). Wrap calls in try/catch in production code.
  • Breakpoints in minified production code are hard to read unless source maps are published; many teams do not publish them publicly.

Interview angle

  • "localStorage vs sessionStorage vs cookies?" — size, lifetime, and whether it is sent to the server automatically (only cookies are).
  • "How do you debug JavaScript?" — console logging, then breakpoints and stepping in Sources; mention conditional breakpoints and source maps.

Interview questions — How the web works

Explain the client–server model and the request–response cycle.

A client (usually a browser) sends an HTTP request to a server; the server runs code, such as a Spring controller and a database query, and returns one response with a status code, headers and a body. The client always starts the conversation, and HTTP is stateless, so each request is independent.

What happens when you type a URL in the browser and press Enter?

The browser parses the URL and checks its caches. DNS resolves the host to an IP; the browser opens a TCP connection and, for HTTPS, a TLS handshake. It sends the HTTP request; the server (often behind a load balancer) processes it and responds with HTML. The browser parses the HTML, fetches CSS, JS and images, builds the DOM and CSSOM, lays out, paints and runs the JavaScript.

Name the parts of a URL. Which part never reaches the server?

Scheme, host, port, path, query and fragment. The fragment (after #) stays in the browser; it is used for in-page jumps and, in older SPAs, routing.

How does DNS resolution work?

The browser checks its cache, then the OS cache and hosts file, then asks a recursive resolver. If the resolver has no cached answer, it asks a root server, then the TLD server (.com), then the domain's authoritative name server, which returns the IP and a TTL. Every layer caches the answer until the TTL expires. DNS returns only an address, never a port.

GET vs POST — what is the difference?

GET reads data; it is safe and idempotent, sends parameters in the URL, can be cached and bookmarked, and has no body. POST sends data in the body to create a resource or trigger an action; it is neither safe nor idempotent, so repeating it can create duplicates. Never use GET for operations that change data.

PUT vs PATCH? What does idempotent mean?

PUT replaces the whole resource; PATCH changes only the fields you send. An idempotent method has the same effect on the server whether called once or many times. GET, PUT and DELETE are idempotent; POST is not; PATCH is not guaranteed to be.

401 vs 403?

401 means the server does not know who you are — missing or invalid credentials. 403 means it knows you but you are not allowed to do this. In Spring Security, a missing token gives 401 and a failed hasRole check gives 403.

HTTP is stateless. How do logins and carts work then?

The client sends proof of identity with every request. With sessions, the server sets a JSESSIONID cookie and looks up the session by id. With tokens, the client stores a JWT and sends it in the Authorization: Bearer header. The state lives in the server session store, a database, or the signed token itself.

How does the browser render a page?

HTML is parsed into the DOM and CSS into the CSSOM. They combine into the render tree (only visible elements with computed styles). Layout computes sizes and positions, paint draws the pixels, and compositing assembles the layers on the GPU. CSS blocks rendering, and a normal script blocks the HTML parser.

What is the difference between defer and async on a script tag?

Both download in parallel with HTML parsing. defer runs the script after the document is parsed and keeps document order, so it suits app code that needs the DOM. async runs the script as soon as it is downloaded, in any order, and may interrupt parsing, so it suits independent scripts like analytics. Module scripts are deferred by default.

What is the difference between reflow and repaint? Which CSS changes are cheap?

Reflow (layout) recalculates sizes and positions and is the expensive step; repaint redraws pixels without changing geometry. Changing width or margin triggers layout; changing a background colour triggers paint only; changing transform or opacity usually triggers only compositing, so animations should use these two.

SPA vs MPA? CSR vs SSR?

An MPA requests a new HTML page for each navigation; a SPA loads one page and updates it with JavaScript and JSON calls. CSR builds the HTML in the browser from an empty shell; SSR sends ready HTML from the server, which gives a faster first paint and better SEO. A React + Spring Boot app is normally a CSR SPA talking to a REST API.

What is an origin, and why does React on port 5173 fail to call Spring Boot on 8080?

An origin is scheme + host + port. The ports differ, so the origins differ, and the browser's same-origin policy blocks the response unless the server sends CORS headers (Access-Control-Allow-Origin). The fix is CORS configuration in Spring Boot, or a Vite dev proxy so the browser sees one origin.

An API call from your React app fails. How do you debug it with DevTools?

Open Network with Preserve log, filter Fetch/XHR and find the request. Check the status code, the request URL, headers (Authorization, Content-Type) and the Payload, then the Response body. A 4xx points to the request, a 5xx to the server log, and (failed) to CORS or a down server. Use Copy as cURL to replay it outside the browser.

Why can you not trust the browser to enforce security?

Everything in the browser can be changed by the user, and any script or tool can send the same HTTP requests. Hidden buttons and client-side validation are for user experience only. The server must authenticate, authorise and validate every request.

Cheat sheet — How the web works

  • Client–server the client sends a request; the server sends one response; HTTP is stateless
  • URL scheme://host:port/path?query#fragment — the fragment never reaches the server
  • Default ports http 80, https 443; Vite 5173, Spring Boot 8080, PostgreSQL 5432
  • Origin scheme + host + port; different origins need CORS
  • DNS name → IP; cache → OS/hosts → resolver → root → TLD → authoritative; TTL controls caching
  • Request method + path + headers + optional body; response status + headers + body
  • Safe/idempotent GET safe + idempotent; PUT, DELETE idempotent; POST neither
  • Status classes 2xx ok, 3xx redirect, 4xx client error, 5xx server error
  • Key codes 200, 201 + Location, 204, 304, 400, 401, 403, 404, 409, 500, 503
  • Headers Content-Type, Accept, Authorization, Cookie / Set-Cookie, Cache-Control, Location
  • HTTPS HTTP over TLS; certificate proves identity; keys are agreed in the handshake
  • HTTP/2, HTTP/3 multiplexing on one connection; HTTP/3 runs on QUIC over UDP
  • HTML / CSS / JS structure / presentation / behaviour
  • Rendering HTML → DOM, CSS → CSSOM → render tree → layout → paint → composite
  • Scripts plain blocks parsing; defer after parsing, in order; async when ready, any order
  • Cheap animation animate transform and opacity, not width or top
  • Static / dynamic ready files versus pages built per request
  • MPA / SPA page per click versus one page + JSON; SPA needs an index.html fallback for deep links
  • CSR / SSR HTML built in the browser versus on the server; SSR is better for SEO
  • Network tab Fetch/XHR filter, Preserve log, Disable cache, Throttling, Copy as cURL
  • Elements live DOM; Styles shows strikethrough losers; Computed shows final values
  • Console console.log/table/error, $0, $$(), errors with file and line
  • Sources breakpoints, F10 over, F11 into, conditional breakpoints, source maps
  • Shortcuts F12 open, Ctrl+Shift+C inspect, Ctrl+Shift+M device mode, Ctrl+Shift+R hard reload
  • Never trust the client validate and authorise on the server for every request

Practice — How the web works

  1. Split URLs. Write down scheme, host, port, path, query and fragment for five URLs of your choice (include one with a port and one with repeated query keys). Then verify with new URL(...) in the Console. Done when all parts match the browser's answer.
  2. Trace DNS. Run nslookup (or dig) for three sites. Find the A record and, for one site, a CNAME. Done when you can explain each line of the output.
  3. Read raw HTTP. Run curl -i https://example.com and label the status line, each header and the body. Then run your Spring Boot /api/hello endpoint with curl -v and find the request and response headers.
  4. Status code lab. In a Spring Boot app, write endpoints that return 200, 201 with Location, 204, 400, 404 and 500. Call each with curl and the browser. Done when you can predict each status before calling.
  5. Network panel tour. Open a big website. Filter Fetch/XHR, find a JSON response, copy it as cURL, and run it in a terminal. Write down the page's total requests, transferred size and DOMContentLoaded time with and without "Disable cache".
  6. Throttle it. Reload a heavy page with Slow 4G. Note which resource is the slowest and what appears first. Done when you can explain the waterfall.
  7. Edit a live page. On any site, use Elements to change a heading's text, hide an element with a Styles checkbox, force :hover on a button and change a colour. Refresh and notice that everything resets.
  8. Break the order. Make a small page with a script in the head that does document.getElementById("x").textContent = "hi". See the TypeError in the Console. Fix it with defer, then explain why it works.
  9. Storage tour. In the Application panel, add a localStorage key, find a cookie set by a site and read its flags, then use "Clear site data". Done when you can say which of the three is sent to the server automatically.
  10. Lighthouse run. Audit one of your own pages (a later module's profile page works), write down the four scores and fix the first three issues it reports.

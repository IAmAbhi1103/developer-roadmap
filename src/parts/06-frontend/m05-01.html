React is a JavaScript library for building user interfaces out of small, reusable pieces called components. In Module 4 you changed the page by hand: find an element, set its text, add a class, remove a node. React turns that around. You describe what the screen should look like for the current data, and React works out which DOM changes are needed. When a Java full-stack job in India mentions a frontend, it almost always means React (often with TypeScript) talking to a Spring Boot REST API.

This module uses React 19 with Vite. It takes you from an empty folder to a multi-page app with forms, routing, shared state and server data. Module 6 then connects that app to your Spring Boot API, and Module 7 adds TypeScript, Next.js, state libraries and tests.

What React is and why it exists

React is a library for building user interfaces from components: you describe what the UI should look like for the current data, and React updates the real DOM to match every time that data changes.

The problem: keeping the DOM in sync by hand

In Module 4 you wrote imperative code: step-by-step instructions that change the page. That works for small pages. But every piece of data on screen now has two copies — one in your JavaScript variables and one in the DOM — and you must update both, every time, in every code path. Look at a tiny cart:

const items = [];
const list = document.querySelector('#cart-list');
const badge = document.querySelector('#cart-count');
const emptyMsg = document.querySelector('#empty');

function addItem(name) {
  items.push(name);
  const li = document.createElement('li');
  li.textContent = name;
  list.appendChild(li);
  badge.textContent = items.length;   // forget this line and the badge is wrong
  emptyMsg.hidden = items.length > 0; // forget this one and "Cart is empty" stays
}

// removeItem(), clearCart(), applyCoupon() ... each must repeat the same DOM updates

Add "remove", "change quantity" and "apply coupon" and you have many functions that must all remember to update the badge, the list, the empty message and the total. Miss one, and the screen shows "3 items" while the list has 4. This class of bug is exactly what React removes.

The React way: describe the result

React is declarative: you write what the UI should look like for a given state, not how to change it. When the state changes, React calls your component again and updates only the parts of the DOM that are different.

import { useState } from 'react';

function Cart() {
  const [items, setItems] = useState([]);

  function addItem(name) {
    // Change the data. React re-renders and updates the DOM for you.
    setItems([...items, { id: crypto.randomUUID(), name }]);
  }

  return (
    <section>
      <h2>Cart ({items.length})</h2>
      {items.length === 0 ? <p>Cart is empty</p> : null}
      <ul>
        {items.map((item) => <li key={item.id}>{item.name}</li>)}
      </ul>
      <button onClick={() => addItem('Masala Dosa')}>Add dosa</button>
    </section>
  );
}

export default Cart;

There is no code that touches the badge or the empty message. The count, the list and the message are all calculated from items on every render, so they can never disagree.

The core ideas

Component
A JavaScript function that returns a description of UI (written in JSX). You build pages by putting components inside components: App → Header, ProductList → ProductCard.
Props
The inputs a parent passes to a child component, like arguments to a function. Read-only.
State
Data a component remembers between renders, such as the text in a search box or the items in a cart. Changing state makes React re-render the component.
Render
React calling your component function to get the latest UI description. Rendering is not the same as touching the DOM.
One-way data flow
Data flows down the tree through props. A child never changes its parent's data directly; it calls a function the parent passed down (an event "flows up").
Reconciliation
React's process of comparing the new UI description with the previous one to find the minimum set of DOM changes.

How it works: render, reconcile, commit

  1. Trigger. Something calls a state setter (for example setItems). React schedules a render of that component.
  2. Render. React calls your component function again. It returns a new tree of React elements — plain JavaScript objects such as { type: 'h2', props: { children: ['Cart (', 2, ')'] } }.
  3. Reconcile (diff). React compares the new tree with the previous one and works out what changed.
  4. Commit. React applies only those differences to the real DOM — here, it changes one text node and appends one <li>.
  5. Paint and effects. The browser paints the screen, then React runs your effects (useEffect).

The virtual DOM in simple words

The tree of React elements is often called the virtual DOM: a lightweight copy of the UI made of plain objects. Creating objects is cheap; changing the real DOM is slower because the browser may have to recalculate layout and repaint. So React builds the cheap copy first, compares it with the last one, and then makes a small number of real DOM changes.

A perfect comparison of two arbitrary trees is expensive (the general algorithms are around O(n³)). React uses two simple assumptions to do it in roughly O(n):

  • Different type → new subtree. If a <div> becomes a <section>, or <LoginForm /> becomes <Dashboard /> at the same position, React throws away the old subtree (and its state) and builds a new one.
  • Same type → update in place. React keeps the DOM node or component instance and only updates the changed attributes or props. A component keeps its state.
  • Lists use keys. For children rendered from an array, the key prop tells React which item is which between renders (see Lists and keys).

Since React 16 the engine that does this work is called Fiber. It splits rendering into small units so React can pause, prioritise urgent updates (typing in an input) over less urgent ones (re-rendering a long list), and then continue. React 18 and 19 build their concurrent features, such as useTransition, on top of it.

Mistake: thinking "re-render" means "redraw the whole page"

A re-render is just React calling your function and comparing objects. If the output is the same, the DOM is not touched at all. Re-renders are normal and usually fast. Do not start adding optimisations (memo, useMemo) until you have measured a real slowdown.

A library, not a framework

React itself only handles the view: components, state and rendering. Routing, data fetching, form handling and global state are separate libraries you choose — this module uses React Router, TanStack Query and React Hook Form. Frameworks built on React, like Next.js (Module 7), make those choices for you and add server rendering.

Version note: React 19

React 19 has been the current major version since December 2024. Things you will meet in newer code: Actions for forms with useActionState and useFormStatus, useOptimistic, the use API for reading a promise or context, ref as a normal prop on function components (no forwardRef needed), rendering <MyContext value={…}> directly as a provider, and <title> / <meta> tags placed inside components. React 19 removed old APIs: ReactDOM.render (use createRoot), propTypes checks and defaultProps on function components, and string refs. React 19.2 (October 2025) added <Activity> and useEffectEvent.

Server Components and Server Functions are part of React 19, but they need a framework that supports them, such as Next.js. In a Vite single-page app, every component is a client component that runs in the browser.

In real projects

The common Java-shop setup is a React single-page application (SPA): Vite builds it into static files, a CDN or Nginx serves them, and the app calls a Spring Boot REST API with JSON and a JWT. Admin panels, internal dashboards, CRMs and banking back-office tools are mostly built this way. That is the setup this page teaches.

A Java way to think about it

A component is like a pure method View render(Props props, State state). Think of a Thymeleaf template that re-renders itself in the browser whenever its model changes — except React patches only the changed parts instead of reloading the page.

Interview: "What is the virtual DOM and how does React update the UI?"

  • Components return React elements — plain objects describing the UI (the virtual DOM).
  • On a state change, React re-renders the component and diffs the new tree with the old one (reconciliation), using element type and key as heuristics, which makes it about O(n).
  • It then commits only the differences to the real DOM; several state updates are batched into one render.
  • The virtual DOM is not "faster than the DOM". Its value is that you write simple declarative code and still get efficient, targeted updates.
  • Fiber (React 16+) lets React split and prioritise rendering work.

Create a React project with Vite

npm create vite@latest creates a React project in seconds, npm run dev starts a fast development server with instant updates, and npm run build produces optimised static files in dist/.

What Vite is

Vite (French for "quick", said "veet") is a build tool and development server. In development it serves your source files to the browser as native ES modules and transforms each file only when the browser asks for it, so the server starts almost instantly even for big apps. When you edit a file, Hot Module Replacement (HMR) swaps just that module in the running page; for React components this is called Fast Refresh and usually keeps the component's state. For production, Vite bundles, minifies and splits your code into a few optimised files.

You need Node.js (which includes npm, the package manager). Install a current LTS release from nodejs.org. Vite 7 needs Node.js 20.19+ or 22.12+; newer Vite versions may need a newer Node, so check the Vite docs if the tool complains.

Create and run the project

  1. Open a terminal in the folder where you keep projects and run npm create vite@latest.
  2. Answer the prompts: a project name (for example employee-ui), the framework React, and the variant JavaScript (or TypeScript once you have read Module 7).
  3. Go into the folder and install dependencies: cd employee-ui, then npm install.
  4. Start the dev server with npm run dev and open http://localhost:5173.
  5. Edit src/App.jsx, save, and watch the browser update without a reload.

The project structure

index.html sits at the project root, not inside public/. Vite treats it as the entry point of your app. It contains one empty div and one script tag:

<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <link rel="icon" type="image/svg+xml" href="/vite.svg" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>employee-ui</title>
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/src/main.jsx"></script>
  </body>
</html>

src/main.jsx is the JavaScript entry. It finds the #root element and tells React to render your App component inside it. Everything inside #root is now managed by React. Later you will wrap <App /> with providers here: the router, the TanStack Query client and the auth context.

import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import './index.css';
import App from './App.jsx';

// Find <div id="root"> and let React manage everything inside it
createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>,
);

src/App.jsx is your root component. Replace the template's demo with something small of your own:

import { useState } from 'react';
import './App.css';

function App() {
  const [count, setCount] = useState(0);

  return (
    <main>
      <h1>Employee UI</h1>
      <button onClick={() => setCount((c) => c + 1)}>
        Clicked {count} times
      </button>
    </main>
  );
}

export default App;

StrictMode, and why things run twice in development

<StrictMode> in main.jsx turns on extra checks in development only. It renders nothing visible. It deliberately does some work twice to expose bugs early:

  • It calls each component function twice per render, to catch components that are not pure (for example, ones that change a global variable while rendering).
  • On mount, it runs every effect, then its cleanup, then the effect again (setup → cleanup → setup). If your effect has no proper cleanup, you will see the problem straight away instead of in production.
  • In React 19 it also runs ref callbacks twice on mount, and it warns about deprecated APIs.
useEffect(() => {
  console.log('connect');
  return () => console.log('disconnect');
}, []);
connect
disconnect
connect

This is why a fetch in an effect shows up twice in the Network tab during development. That is expected. The fix is never "remove StrictMode"; write the effect so that running it twice is harmless (a cleanup that aborts or ignores the first request — see Fetching data) or use TanStack Query. A production build runs everything once.

Rule: commit the lock file, never node_modules

Commit package.json and package-lock.json so every developer and the CI server install the same versions. Never commit node_modules/ or dist/; the template's .gitignore already excludes them.

Conventions

  • Files that contain JSX use the .jsx extension (.tsx in TypeScript). Vite's React setup expects that.
  • Component files are named in PascalCase, like the component: EmployeeList.jsx.
  • Keep main.jsx tiny: it only mounts the app and wraps it in providers.
  • Put your own code under src/; use public/ only for files that must keep their exact name and URL, such as robots.txt.

Edge cases

  • If port 5173 is busy, Vite picks the next free port (5174, 5175 …) and prints it. Set server.strictPort: true in vite.config.js if you would rather fail.
  • To open the dev server from your phone on the same Wi-Fi, run npm run dev -- --host and use the "Network" URL Vite prints.
  • Fast Refresh keeps state only when a file exports React components. Edit a file that also exports plain functions or constants and the page may fully reload instead.

Common mistakes

  • Double-clicking index.html to open it from disk (file://). You get a blank page. Always run npm run dev (or npm run preview for a build).
  • Running npm commands outside the project folder. npm complains that it cannot find package.json — cd into the project first.
  • Forgetting npm install after cloning a repository, then seeing "vite: not found" or "'vite' is not recognized".

Version note: Create React App is deprecated

Older tutorials use npx create-react-app and react-scripts start. The React team officially deprecated Create React App in February 2025. Do not start new projects with it; use Vite for a single-page app, or a framework such as Next.js when you need server rendering. Older environment variables like process.env.REACT_APP_API_URL become import.meta.env.VITE_API_URL in Vite (see Module 6).

Interview: "Why Vite? And why does my effect run twice?"

  • Vite serves native ES modules in development and transforms files on demand, so start-up and HMR stay fast as the app grows; for production it bundles, minifies and splits the code.
  • npm run build outputs static files in dist/ that any web server or CDN can serve.
  • Effects running twice is StrictMode in development: setup → cleanup → setup, to prove your cleanup works. It does not happen in production.

JSX: HTML-like markup inside JavaScript

JSX lets you write HTML-like markup in JavaScript files; it compiles to plain function calls that create React elements, so it follows JavaScript rules — className, camelCase attributes, one root element and {} for expressions.

What JSX really is

JSX is a syntax extension for JavaScript. Browsers cannot run it, so Vite's React plugin compiles it into ordinary function calls before the code reaches the browser. Knowing this explains almost every JSX rule.

const greeting = <h1 className="title">Namaste, {user.name}!</h1>;
// Classic form (still valid, and what older code and interviews show)
const greeting = React.createElement('h1', { className: 'title' }, 'Namaste, ', user.name, '!');

// Modern "automatic runtime" (React 17+): same idea, a different helper,
// imported for you by the compiler
import { jsxs as _jsxs } from 'react/jsx-runtime';
const greeting2 = _jsxs('h1', { className: 'title', children: ['Namaste, ', user.name, '!'] });

The result is a React element: a plain object that describes what to show. It is not a DOM node.

{
  type: 'h1',
  props: { className: 'title', children: ['Namaste, ', 'Asha', '!'] },
  key: null,
  // ...a few internal fields
}

Because JSX becomes createElement(type, props, ...children), it must produce one value (hence one root), attributes are object keys (hence JavaScript property names like className), and anything inside {} must be an expression that produces a value.

Curly braces: JavaScript inside markup

Inside {} you can put any JavaScript expression — something that produces a value: a variable, a calculation, a function call, a ternary, array.map(…), a template literal, or more JSX. You cannot put a statement there: no if, for, switch or variable declarations. Do that work above the return.

function ProfileCard({ user }) {
  const initials = user.name
    .split(' ')
    .map((part) => part[0])
    .join('');
  const joined = new Date(user.joinedOn).toLocaleDateString('en-IN');

  return (
    <div className="card" data-user-id={user.id}>
      {/* Attribute values: quotes for fixed strings, braces for expressions */}
      <img src={user.avatarUrl} alt={`Photo of ${user.name}`} width={64} />
      <span className="avatar-fallback">{initials}</span>
      <h2>{user.name.toUpperCase()}</h2>
      <p>Joined on {joined}</p>
      <p>Experience: {user.years > 1 ? `${user.years} years` : 'Fresher'}</p>
      <label htmlFor="bio">Bio</label>
      <textarea id="bio" defaultValue={user.bio} maxLength={300} />
    </div>
  );
}

export default ProfileCard;

Fragments: one root without an extra div

A component must return one element. When an extra <div> would break your layout (for example inside a table or a flex container), use a fragment. It groups children without adding a DOM node. The short form <>…</> cannot take attributes; when you need a key (in lists), write <Fragment key={…}>, imported from react.

function EmployeeCells({ employee }) {
  return (
    <>
      <td>{employee.name}</td>
      <td>{employee.department}</td>
    </>
  );
}

Style objects

The style prop takes a JavaScript object with camelCase property names. The double braces are not special syntax: the outer pair means "JavaScript expression", the inner pair is the object literal. A number becomes pixels for length properties (fontSize: 18 → 18px); unitless properties such as opacity, zIndex, flexGrow and lineHeight keep the plain number.

function ProgressBar({ percent }) {
  // Inline styles are best for values that change at runtime, like this width
  return (
    <div className="progress">
      <div
        className="progress-fill"
        style={{ width: `${percent}%`, backgroundColor: percent < 30 ? 'crimson' : 'seagreen' }}
      />
    </div>
  );
}

Multi-line JSX and the return trap

Wrap multi-line JSX in parentheses after return. If you put a line break right after return, JavaScript's automatic semicolon insertion ends the statement there and the function returns undefined — the component renders nothing.

Wrong: HTML habits and the return trap

function Badge() {
  return
    <span class="badge" style="color: green" onclick="alert('hi')">
      New
    </span>
}

Right: valid JSX

function Badge() {
  return (
    <span
      className="badge"
      style={{ color: 'green' }}
      onClick={() => alert('hi')}
    >
      New
    </span>
  );
}

Rules that break the build or the page

  • Return a single root (an element or a fragment).
  • Close every tag, including void ones: <input />, <img />, <br />. An unclosed tag is a compile error.
  • Only expressions inside {}. An if inside JSX is a syntax error.
  • style must be an object. A string gives the error "The style prop expects a mapping from style properties to values, not a string."

Edge cases and warnings

  • class= and onclick= still work in some cases but React warns: "Invalid DOM property class. Did you mean className?" and "Invalid event handler property onclick. Did you mean onClick?" Fix them.
  • Boolean attributes: <button disabled> means disabled={true}; disabled={false} removes the attribute. Writing disabled="false" passes a non-empty string, so React warns that this will not work as expected — use disabled={false}.
  • Dates and objects must be turned into strings first: {order.placedAt.toLocaleString()}, not {order.placedAt}.
  • Text in JSX is escaped, so {userComment} cannot inject HTML. That is built-in XSS protection. The escape hatch dangerouslySetInnerHTML={{ __html: html }} turns it off — only use it with HTML you have sanitised (for example with the DOMPurify library).

Tip: converting existing HTML

When you paste HTML from a design or an old page, fix it in this order: class → className, for → htmlFor, close void tags, convert style strings to objects, turn onclick strings into functions, and replace HTML comments. Your editor and the React warnings in the console point to anything you missed.

Interview: "What is JSX? Can you write React without it?"

  • JSX is syntax sugar that compiles to React.createElement (or the modern jsx() helper) calls, which return plain objects called React elements.
  • Yes, React works without JSX — you would call createElement yourself — but JSX is far easier to read.
  • className and htmlFor exist because JSX attributes map to JavaScript DOM properties (element.className) and class / for are reserved words in JavaScript.
  • JSX escapes embedded values, which protects against XSS unless you use dangerouslySetInnerHTML.

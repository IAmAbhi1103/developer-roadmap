Accessibility basics

Accessibility means everyone can use your page — with a keyboard, a screen reader, low vision or a slow hand — and most of it comes free if you use the right native elements, alt text, labels, visible focus and enough colour contrast.

Accessibility (often written a11y, "a", 11 letters, "y") is designing so that people with disabilities can use your site. That includes blind users with screen readers, people with low vision or colour blindness, people who cannot use a mouse, deaf users, and people with temporary limits (a broken arm, bright sunlight). It also helps everyone: keyboard shortcuts, captions in a noisy bus, large tap targets. In India alone, millions rely on assistive technology, and in many countries (and for many government and enterprise clients) accessibility is a legal or contractual requirement, usually measured against WCAG, the Web Content Accessibility Guidelines. Interviewers increasingly ask about it.

How assistive technology reads your page

The browser turns the DOM into an accessibility tree: each node has a role (button, link, heading, checkbox), a name (its text or label), a state (checked, expanded, disabled) and a value. A screen reader reads this tree aloud. You can see it in DevTools: Elements → Accessibility pane. Native HTML elements fill in role, name, state and keyboard behaviour automatically; divs give nothing.

1. Use the right element — the foundation

Wrong: a clickable div

<div class="btn" onclick="save()">Save</div>

Right: a real button

<button type="button" onclick="save()">Save</button>

The div version cannot be reached with Tab, does not react to Enter or Space, and is announced as plain text. To fix it you would need role="button", tabindex="0" and key handlers — everything a <button> already does. The same goes for links (<a href>), checkboxes, <select> and <details>.

2. Text alternatives

Images need meaningful alt (decorative: alt=""); icon-only buttons need a name; videos need captions; links need descriptive text (see Images). An icon button:

<button type="button" aria-label="Close dialog">
  <svg aria-hidden="true" width="16" height="16">…</svg>
</button>

3. Labels and instructions

Every form control has a connected label (Forms). Errors are text, placed next to the field and linked with aria-describedby. Do not rely on placeholder text, colour or position alone.

4. Keyboard access and focus order

Many users never touch a mouse. Everything you can do with a pointer must work with the keyboard:

  • Tab moves to the next focusable element, Shift+Tab back, Enter activates links and buttons, Space activates buttons and ticks checkboxes, arrow keys move between radio buttons and inside menus, Esc closes dialogs.
  • Focus order follows the DOM order. So write the HTML in a logical reading order, and do not use CSS (order, positioning) to reorder things visually in a way that makes the Tab sequence jump around.
  • Avoid positive tabindex values (tabindex="3"); they create a confusing custom order. Use tabindex="0" (join the natural order) or tabindex="-1" (focusable by script only, e.g. to move focus to a dialog heading) when you must.
  • Add a skip link ("Skip to main content") as the first focusable element, so keyboard users do not have to tab through the whole menu on every page.
  • Visible focus. The outline that shows where you are must stay. Never write outline: none without a replacement. Use :focus-visible, which shows the ring for keyboard users but not for mouse clicks:
:focus-visible {
  outline: 3px solid #1a56db;
  outline-offset: 2px;
}

.skip-link {
  position: absolute;
  left: -999px;               /* off screen until focused */
}
.skip-link:focus {
  left: 1rem;
  top: 1rem;
  background: white;
  padding: 0.5rem 1rem;
}

5. Landmarks and headings

Use header, nav, main, aside and footer (Semantic HTML) and a logical heading hierarchy. Screen-reader users navigate by them, much as sighted users scan visually.

6. Colour and contrast

  • WCAG AA asks for a contrast ratio of at least 4.5:1 for normal text and 3:1 for large text (about 24px, or 19px bold) and for UI parts such as input borders and icons.
  • Light grey text on white is the most common failure. Check colours with the DevTools colour picker (it shows the ratio) or Lighthouse.
  • Do not convey meaning with colour alone — a red border should come with an error message and perhaps an icon. About 1 in 12 men has some colour-vision deficiency.
  • Support zoom and text resize: use relative units (rem) so text enlarges to 200% without breaking the layout, and do not disable pinch zoom.
  • Respect prefers-reduced-motion for animations (Transitions and animations). Touch targets should be at least about 44 by 44 pixels.

7. ARIA — the last resort

ARIA (Accessible Rich Internet Applications) is a set of attributes (role, aria-*) that add semantics when HTML has none. The first rule of ARIA: do not use ARIA if a native HTML element or attribute can do the job. Wrong ARIA is worse than none, because it makes false promises to the screen reader. A few safe, common attributes:

AttributeUse
aria-label="Search"Gives a name when there is no visible text (icon buttons, a second nav)
aria-labelledby="id"Names an element from other visible text, e.g. a dialog from its heading
aria-describedby="id"Adds extra description such as a hint or error message
aria-hidden="true"Hides decorative content from assistive technology. Never on focusable elements
aria-expanded="true|false"State of a toggle button that shows or hides something
aria-live="polite"Announces changes inside a region, e.g. "3 items in cart" or a form error
aria-current="page"Marks the current link in a navigation
role="alert"An important, time-sensitive message announced at once

ARIA changes only what is announced. It adds no keyboard behaviour: a div role="button" still needs tabindex="0" and key handlers. This is why native elements win.

<button type="button" aria-expanded="false" aria-controls="menu">Menu</button>
<ul id="menu" hidden>
  <li><a href="/profile">Profile</a></li>
</ul>

Your script flips aria-expanded and removes hidden together, keeping the visual state and the announced state in sync.

Testing

  1. Unplug the mouse. Tab through the whole page: can you reach everything, in a sensible order, always seeing where you are? Can you open and close menus and dialogs?
  2. Zoom to 200% and check the layout and reading order.
  3. Run Lighthouse (Accessibility category) and fix every item. Also try the browser extension axe DevTools.
  4. Inspect the Accessibility pane in DevTools to verify role and name.
  5. Listen once. Turn on a screen reader (NVDA is free on Windows; VoiceOver is built into macOS and iOS; TalkBack on Android) and navigate your own page for five minutes. It will teach you more than any checklist.

Automated tools find only about a third of real problems, such as missing alt text or low contrast. They cannot tell if your alt text is meaningful. Manual testing is part of the job.

Rules

  • Everything that can be clicked can also be reached and operated with the keyboard.
  • Focus is always visible; never remove the outline without a better one.
  • Text contrast is at least 4.5:1 (3:1 for large text).
  • First rule of ARIA: use a native element first.

Edge cases

  • display: none and visibility: hidden hide content from screen readers too; to hide something visually but keep it for them, use a "visually hidden" utility class (clip the box to 1px). aria-hidden does the opposite: visible but not announced.
  • Placeholder-only inputs, auto-playing carousels and time-limited pop-ups all fail users; give a way to pause or extend.
  • In a SPA the page does not reload on navigation, so screen readers do not announce the new page. Move focus to the new page's heading and update the document title.

Mistakes

  • outline: none with no replacement.
  • A div or span with a click handler instead of a button or link.
  • "Click here" links, missing alt text, heading levels chosen for size.
  • Putting aria-label on everything; it overrides visible text and can contradict it.

Interview angle: "How do you make a site accessible?"

  • Semantic HTML first; alt text; labels for forms; keyboard operable with visible focus; sufficient contrast; ARIA only when needed.
  • Mention testing: keyboard-only, Lighthouse or axe, a screen reader, zoom.
  • Quote WCAG AA contrast: 4.5:1 for normal text.

Meta tags and SEO basics

Meta tags in the head describe your page to browsers, search engines and social sites — title, description, Open Graph for link previews, favicon, robots and canonical — and good SEO is mostly semantic HTML, useful content and fast pages.

SEO (search engine optimisation) is making pages easy for search engines to find, understand and rank. Meta tags are the head-level part of it. They also control how your link looks when someone pastes it into WhatsApp, LinkedIn or Slack.

The essential tags

<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">

  <title>Asha Rao - Java Full-Stack Developer in Pune</title>
  <meta name="description"
        content="Portfolio of Asha Rao: Spring Boot, React and PostgreSQL projects.">

  <link rel="canonical" href="https://asharao.dev/">
  <link rel="icon" href="/favicon.ico" sizes="32x32">
  <link rel="icon" href="/favicon.svg" type="image/svg+xml">
  <link rel="apple-touch-icon" href="/apple-touch-icon.png">
  <meta name="theme-color" content="#1a56db">

  <!-- Open Graph: link previews -->
  <meta property="og:type" content="website">
  <meta property="og:title" content="Asha Rao - Java Full-Stack Developer">
  <meta property="og:description" content="Spring Boot, React and PostgreSQL projects.">
  <meta property="og:image" content="https://asharao.dev/images/og-card.png">
  <meta property="og:url" content="https://asharao.dev/">

  <!-- X (Twitter) card -->
  <meta name="twitter:card" content="summary_large_image">
</head>
<title>
The blue headline in search results and the browser tab. Make it unique per page, descriptive, with the main keywords first, about 50–60 characters (longer titles get cut).
meta name="description"
The grey summary under the title in search results. Search engines may rewrite it, and it is not a ranking factor by itself, but a clear 120–160 character summary gets more clicks. Unique per page.
Open Graph (og:*)
A protocol created by Facebook and used by WhatsApp, LinkedIn, Slack, Telegram and others to build link preview cards. Without it they guess, often badly. og:image should be an absolute URL, around 1200 × 630 pixels. The twitter:card tag controls the card on X; other twitter:* tags fall back to Open Graph.
Favicon
The small icon in the tab and bookmarks. Browsers also request /favicon.ico automatically, and a 404 here shows in your server log — add one.
link rel="canonical"
Tells search engines the preferred URL when the same content is reachable at several (with and without www, with tracking parameters), so ranking is not split.
meta name="robots"
content="noindex" asks search engines not to list the page (use on admin, thank-you and login pages); nofollow asks them not to follow its links. Default is index and follow. A separate robots.txt file at the site root tells crawlers which paths not to fetch — it is public and is not security.
meta name="theme-color"
Colours the browser toolbar on mobile.

SEO basics that matter more than tags

  • Useful content that answers what people search for. No amount of markup rescues empty pages.
  • Semantic HTML: a single descriptive h1, logical h2/h3, main, lists, alt text (images also appear in image search). Meaningful link text rather than "click here".
  • Clean URLs: /blog/spring-boot-jwt, not /post?id=8372; lowercase, hyphens, stable (use 301 redirects when you must change one).
  • Speed and mobile friendliness: Google ranks on mobile experience and Core Web Vitals (LCP, INP, CLS). Compress images, use loading="lazy", set image sizes, defer scripts.
  • HTTPS everywhere.
  • A sitemap.xml listing your pages helps crawlers discover them.
  • Structured data (JSON-LD, schema.org) can add rich results like star ratings; mention it if asked, and learn it when you need it.

The SPA caveat

A plain React + Vite app sends an almost empty HTML file, and fills in content with JavaScript. Google can execute JavaScript but does it later and less reliably; many other crawlers and every link-preview bot (WhatsApp, LinkedIn) read only the raw HTML. In a SPA, the <title>, description and Open Graph tags in index.html are the same for every route, so every shared link looks identical. Options:

  • For logged-in apps, ignore SEO — crawlers cannot log in anyway.
  • Update the title per route with JavaScript (React Helmet or React 19's built-in support for rendering <title> and <meta> inside components) — helps tabs and Google, not link-preview bots.
  • For public content, use server-side rendering or static generation (Next.js, or Thymeleaf pages from Spring Boot), or a pre-rendering service. See CSR vs SSR.

Check your tags

View the page source (Ctrl+U) to see what a crawler sees without JavaScript. Run Lighthouse's SEO category. Platforms such as the LinkedIn Post Inspector and Facebook Sharing Debugger show your link preview; they cache results, so re-scrape after changes.

Rule: every page has a unique title and description

Identical titles across a site ("My App") hurt both users with many tabs open and search engines. Generate them from the page data.

Convention: put the page name before the site name

"Order 1042 - My Shop" is better than "My Shop - Order 1042", since the tab and the result snippet show the start first.

Edge cases

  • robots.txt blocks crawling, not indexing: a blocked URL can still appear in results if others link to it. To keep a page out, allow crawling and use noindex.
  • Never put private data in robots.txt or meta tags — they are public. Protect secrets with authentication.
  • Relative og:image URLs often fail; use absolute https URLs.
  • The keywords meta tag is ignored by Google; do not bother.

Interview angle

  • "What meta tags do you add?" — charset, viewport, title, description, Open Graph, canonical, robots as needed, favicon.
  • "SEO problem with a React SPA?" — empty initial HTML; fix with SSR/SSG or pre-rendering for public pages.

Validating HTML and the most common mistakes

Browsers silently repair broken HTML, so you must check it yourself with the W3C validator and an editor linter — most problems are unclosed tags, bad nesting, duplicate ids, missing alt and labels, and div soup.

Why validate

A Java compiler refuses to compile broken code; a browser never refuses broken HTML. It guesses what you meant, and different browsers can guess differently. A missing end tag may only show up as a strange layout far from the real mistake. Validation is the "compiler error" step for HTML.

Tools

  • W3C Markup Validation Service (validator.w3.org): paste your HTML, upload a file or give a URL. It lists errors and warnings with line numbers. Warnings about a missing lang or an empty heading matter; for the fragment you paste, ignore "missing doctype" if you only pasted a part.
  • Editor feedback. VS Code highlights some problems; the extension "HTMLHint" or ESLint with HTML plugins add rules. Prettier formats your markup and makes nesting mistakes visible through indentation.
  • DevTools Elements panel. Compare it with your source: if the tree is not what you wrote, the parser repaired something.
  • Lighthouse for accessibility and SEO issues, and the axe extension for accessibility rules.

Wrong: five problems

The problems fixed: a visual "title" div instead of a heading; a block div inside a p; a duplicate id; a missing alt and image size; a "click here" link.

A good habit for the daily workflow

  1. Write semantic markup first, without any CSS.
  2. Open the page and read it as plain text. Does it make sense in order? That is what a screen reader and a crawler see.
  3. Run the validator and Lighthouse.
  4. Only then add CSS and JavaScript.

Tip: turn CSS off to test your structure

In DevTools, or with an extension, disable all styles. A well-built page is still readable and in the right order — headings, lists, links and forms all make sense. A page that collapses into chaos was built on divs.

Edge case: React and JSX

React uses JSX, which looks like HTML but is stricter and differs: className instead of class, htmlFor instead of for, every tag must be closed (<img />, <br />), and attributes are camelCase (tabIndex, maxLength). All the HTML rules in this module still apply to what JSX produces. See Module 5.

Interview angle

  • "Does a browser show errors for invalid HTML?" — no, it repairs it silently; use the validator.
  • "What are common HTML mistakes?" — pick four from the table: nesting, missing alt/labels, duplicate ids, div soup, button without type.

Interview questions — HTML

What does <!doctype html> do, and what is quirks mode?

It tells the browser to render the page in standards mode following the HTML5 rules. Without it, the browser enters quirks mode, which imitates old browser behaviour (for example different box sizing and table inheritance) and breaks modern CSS layouts. It must be the first line.

Why do we need the viewport meta tag?

Mobile browsers pretend to be about 980px wide so old desktop sites fit, then scale down. width=device-width, initial-scale=1 makes the layout viewport equal to the real device width, so media queries and responsive CSS work. Without it, your mobile layout shows as a shrunken desktop page.

What is semantic HTML? Why does it matter?

Using elements that describe meaning (header, nav, main, article, section, footer, button) instead of generic divs. It gives screen readers landmarks, helps search engines understand content, brings built-in behaviour such as keyboard support, and makes code easier to read.

section vs article vs div?

article is self-contained content that could stand alone (a blog post, a product card). section is a themed group of content with a heading. div has no meaning and is only a wrapper for styling or scripting. Use div only when nothing semantic fits.

What is the difference between block and inline elements?

Block elements start on a new line and take the full available width; their width, height and vertical margins work. Inline elements flow within a line of text, are as wide as their content and ignore width and height. CSS display can change either default; inline-block mixes both.

<strong> vs <b> and <em> vs <i>?

strong and em carry meaning (importance, stress) and change how a screen reader speaks. b and i only draw attention or mark another voice, with no extra importance. For purely visual bold or italic, use CSS.

What does target="_blank" need, and why?

Add rel="noopener noreferrer". noopener prevents the new page from controlling the original through window.opener, and noreferrer hides the referrer. Modern browsers imply noopener, but the explicit attribute is still the habit.

How do you write good alt text? When is it empty?

Describe what the image conveys in its context in a short sentence, without "image of". Decorative images get alt="" so screen readers skip them. Images that are links describe the link's target. The attribute must always be present.

How do labels work, and why is placeholder not a label?

A label connected with for and the control's id (or wrapping the control) provides the accessible name and enlarges the click target. A placeholder disappears when typing, often has poor contrast and is not reliably announced, so it can only be an example hint.

A button inside a form reloads the page when clicked. Why?

The default type of a button is submit. Set type="button" for buttons that are not meant to submit, or call event.preventDefault() in the handler.

Which attribute decides what the server receives for a field? What if it is missing?

The name attribute is the key in the request. A control without name is not submitted. id is for labels, CSS and JavaScript. Unchecked checkboxes and disabled controls are also not sent.

GET vs POST for a form?

GET adds the fields to the URL as a query string; it is visible, bookmarkable and cached, so it is right for searches and filters. POST sends them in the body; use it for changes and sensitive data such as passwords. HTML forms support only these two methods; PUT and DELETE need JavaScript.

Is HTML5 form validation enough? Why validate on the server too?

No. Client-side validation (required, pattern, min, type=email) improves user experience but can be removed in DevTools or skipped entirely by calling the API with curl or Postman. The server must validate every request, for example with @Valid and Bean Validation in Spring Boot.

How do you make a page accessible? What is the first rule of ARIA?

Use semantic elements, meaningful alt text and labels, make everything keyboard operable with visible focus, keep contrast at 4.5:1 or better, and test with a keyboard, Lighthouse and a screen reader. The first rule of ARIA is not to use ARIA when a native HTML element does the job, since ARIA adds announcements but no behaviour.

Which meta tags matter for SEO and sharing?

A unique title and description, the canonical link, the robots meta (for noindex), a favicon, and Open Graph tags (og:title, og:description, og:image) for link previews. Page speed, headings and semantic HTML matter even more than tags.

Cheat sheet — HTML

  • Boilerplate doctype, html lang, meta charset, viewport, title, CSS link, script defer
  • Void elements br, hr, img, input, meta, link — no end tag
  • Entities &lt; &gt; &amp; &quot; &copy;
  • Headings one h1, no skipped levels, chosen for structure not size
  • Meaning strong/em carry meaning; b/i do not
  • Links href absolute or relative; #id anchors; mailto:, tel:; new tab needs rel="noopener noreferrer"
  • Images always alt (empty if decorative), width + height, loading="lazy" below the fold
  • Lists ul unordered, ol ordered, dl name–value
  • Landmarks header, nav, main (one only), aside, footer
  • section / article / div themed with heading / stand-alone / no meaning
  • Forms action, method; only controls with name are sent
  • Labels label for = control id; placeholder is not a label
  • Input types text, email, password, number, tel, url, search, date, checkbox, radio, file, hidden
  • Radios same name; group in fieldset + legend
  • Buttons default type is submit; use type="button" for others
  • Files need method="post" + enctype="multipart/form-data"
  • Validation required, min, max, minlength, maxlength, pattern, type
  • Server validates again client validation is for UX only
  • Tables caption, thead/tbody/tfoot, th scope, colspan/rowspan; never for layout
  • Accessibility native elements, keyboard + visible focus, contrast 4.5:1, labels, alt, skip link
  • ARIA last resort; aria-label, aria-describedby, aria-expanded, aria-hidden
  • SEO / meta unique title + description, Open Graph, canonical, robots, favicon
  • SPA caveat empty first HTML hurts SEO and link previews; use SSR or SSG for public pages
  • Validate W3C validator, Lighthouse, axe; browsers silently repair broken HTML

Practice — HTML

  1. Boilerplate from memory. Create index.html without copying: doctype, lang, charset, viewport and title. Done when the tab shows your title and Lighthouse reports no meta issues.
  2. Document outline. Write a page about yourself with one h1, three h2 sections and a few h3s, using only text. Done when it reads sensibly with no CSS at all.
  3. Links lab. Add an absolute link, a relative link to a second page, an in-page anchor to a section, a mailto:, a tel: and a downloadable file. Done when every link works from a different folder structure.
  4. Images and figures. Add a profile photo and one project screenshot with correct alt, width, height and loading, and wrap the screenshot in figure and figcaption. Done when the Elements panel shows no layout shift when the image loads on Slow 4G.
  5. Build the personal profile page (roadmap build). Semantic HTML only, no CSS: skip link, header with nav, main with h1, "About", "Skills" (a list), "Projects" (an article per project with links to GitHub opened safely in a new tab), "Experience or education" (a table with caption and th scope), an aside for "Currently learning", and a footer with address. Done when the validator reports 0 errors.
  6. Contact form. Add a contact form to the profile page: name, email, mobile (tel with a pattern), preferred contact method (radio group in a fieldset), topic (select), message (textarea with maxlength), a consent checkbox, and a submit button. Done when every field has a label, name and autocomplete, and invalid input is blocked with clear messages.
  7. Break the form on purpose. Remove required in DevTools and submit the empty form. Then send the same request with curl to a Spring Boot endpoint that uses @Valid. Done when you can explain why the server still returns 400.
  8. Keyboard-only test. Navigate the whole profile page with Tab, Shift+Tab, Enter and Space. Fix the order or the focus if anything is skipped or invisible. Done when you never lose track of the focus.
  9. Audit and fix. Add title, description, favicon and Open Graph tags. Run Lighthouse (Accessibility, SEO, Best Practices) and the W3C validator. Done when all scores are 90+ and the validator is clean.
  10. Table from data. Write a table of 6 employees (name, department, salary) with a total in tfoot. Then write a small Spring Boot endpoint that returns the same data as JSON, and compare the two. Done when you can explain why one is presentation and the other is data.

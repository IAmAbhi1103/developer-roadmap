fetch: calling a REST API from JavaScript

fetch(url, options) sends an HTTP request and returns a promise of a Response; it rejects only on network failure, so you must check response.ok yourself, then read the body with response.json() — wrap this in one reusable apiClient that adds the JWT header, a timeout and clear errors.

fetch is the browser's built-in way to make HTTP calls (also available in Node.js 18 and later). It is how your frontend talks to the Spring Boot REST API you built, so every call is one request/response from the HTTP you learned in Module 1. Fetch is promise-based, so you use it with async/await (see async and await). The older XMLHttpRequest is not used in new code; libraries like Axios wrap fetch-like behaviour, but plain fetch is enough for most projects.

A GET request

async function loadProducts() {
  const response = await fetch("http://localhost:8080/api/products");

  console.log(response.status);       // 200
  console.log(response.ok);           // true for status 200–299
  console.log(response.headers.get("Content-Type")); // "application/json"

  const products = await response.json();   // reads the body and parses the JSON — also a promise
  console.log(products);   // [ { id: 1, name: 'Mouse', price: 499 }, ... ]
  return products;
}
loadProducts();

Two awaits are needed: the first resolves when the headers arrive (the response object), the second when the body has been read and parsed. The body can be read only once; calling response.json() twice throws TypeError: body stream already read. Use response.clone() if you need two reads. Other readers: response.text(), response.blob() (files, images), response.formData().

fetch does NOT reject on 404 or 500

The promise rejects only when the request itself could not be completed: no network, DNS failure, CORS block, request aborted. An HTTP error such as 404, 401 or 500 is a successful fetch with response.ok === false. Java developers used to RestTemplate or WebClient throwing on 4xx/5xx are caught by this often. Always check response.ok.

Wrong: error body parsed as data

const res = await fetch("/api/products/999");
const product = await res.json();   // 404 JSON error
render(product);                    // renders "Not found" as a product

Right: check ok first

const res = await fetch("/api/products/999");
if (!res.ok) throw new Error(`HTTP ${res.status}`);
render(await res.json());

POST, PUT, PATCH, DELETE with a JSON body

The second argument is an options object. For JSON you must set the method, the Content-Type header and a string body made with JSON.stringify. Without the header, Spring's @RequestBody answers 415 Unsupported Media Type.

const BASE = "http://localhost:8080/api";

async function createProduct(product) {
  const res = await fetch(`${BASE}/products`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(product),            // must be a string (or FormData, Blob)
  });
  if (!res.ok) throw new Error(`Create failed: ${res.status}`);
  return res.json();                           // 201 Created with the saved product
}

async function updateProduct(id, changes) {
  const res = await fetch(`${BASE}/products/${id}`, {
    method: "PUT",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(changes),
  });
  if (!res.ok) throw new Error(`Update failed: ${res.status}`);
  return res.json();
}

async function deleteProduct(id) {
  const res = await fetch(`${BASE}/products/${id}`, { method: "DELETE" });
  if (!res.ok) throw new Error(`Delete failed: ${res.status}`);
  // a 204 No Content response has NO body: do not call res.json() here
}

await createProduct({ name: "Keyboard", price: 899 });

Query strings and URLs

Do not join query strings by hand: special characters (&, spaces, ₹) must be encoded. URLSearchParams does it for you.

const params = new URLSearchParams({ q: "mobile & cover", page: 2, size: 10 });
console.log(params.toString());   // q=mobile+%26+cover&page=2&size=10

const res = await fetch(`${BASE}/products?${params}`);

const url = new URL("/api/products", "http://localhost:8080");
url.searchParams.set("category", "phones");
console.log(url.href);            // http://localhost:8080/api/products?category=phones

Sending a JWT

After login, Spring Boot returns a JWT (JSON Web Token). Protected endpoints expect it in the Authorization header with the word Bearer and a space. A 401 means "not logged in or token expired"; a 403 means "logged in but not allowed". The backend side is explained on the Spring Boot page.

async function login(email, password) {
  const res = await fetch(`${BASE}/auth/login`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ email, password }),
  });
  if (!res.ok) throw new Error("Invalid email or password");
  const { token } = await res.json();
  return token;                           // keep it in memory or storage; see "Storage"
}

async function loadMyOrders(token) {
  const res = await fetch(`${BASE}/orders/mine`, {
    headers: { Authorization: `Bearer ${token}` },
  });
  if (res.status === 401) throw new Error("Session expired, please log in again");
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}

Timeouts and cancelling with AbortController

Fetch has no built-in timeout; a hung server would keep the request open for a very long time. An AbortController gives you a signal to pass to fetch; calling controller.abort() cancels the request, and the promise rejects with an error named AbortError. The same tool cancels outdated requests, for example when the user keeps typing in a search box or leaves a React screen.

async function fetchWithTimeout(url, options = {}, timeoutMs = 8000) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeoutMs);
  try {
    return await fetch(url, { ...options, signal: controller.signal });
  } catch (err) {
    if (err.name === "AbortError") throw new Error("Request timed out");
    throw err;
  } finally {
    clearTimeout(timer);                      // always clean up the timer
  }
}

// Shorter, in newer browsers and Node 18+/20+: AbortSignal.timeout(8000)
const res = await fetch(`${BASE}/products`, { signal: AbortSignal.timeout(8000) });

CORS errors

If your React app runs on http://localhost:5173 and calls http://localhost:8080, the browser treats these as different origins and blocks the response unless the server allows it. The console shows "Access to fetch at '…' from origin '…' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header". The fix is on the server (Spring's @CrossOrigin or a global CORS configuration), or a Vite dev proxy. The request often reaches the server; the browser only refuses to let your code read the answer. JavaScript cannot "turn off" CORS. Full explanation in Module 6.

A reusable apiClient

Repeating headers, ok checks and JSON parsing in every call leads to bugs. Put them in one small module. This version adds the base URL, the JWT, JSON handling, a timeout and a custom error that carries the status code and the server's message.

const BASE_URL = "http://localhost:8080/api";

export class ApiError extends Error {
  constructor(status, message, body) {
    super(message);
    this.name = "ApiError";
    this.status = status;     // e.g. 404
    this.body = body;         // parsed error body from Spring, if any
  }
}

function getToken() {
  return localStorage.getItem("token");
}

async function request(path, { method = "GET", body, params, timeoutMs = 8000 } = {}) {
  const url = new URL(`${BASE_URL}${path}`);
  if (params) Object.entries(params).forEach(([k, v]) => url.searchParams.set(k, v));

  const headers = { Accept: "application/json" };
  const token = getToken();
  if (token) headers.Authorization = `Bearer ${token}`;
  if (body !== undefined) headers["Content-Type"] = "application/json";

  let response;
  try {
    response = await fetch(url, {
      method,
      headers,
      body: body !== undefined ? JSON.stringify(body) : undefined,
      signal: AbortSignal.timeout(timeoutMs),
    });
  } catch (err) {
    // network failure, CORS, timeout
    const msg = err.name === "TimeoutError" ? "The server took too long" : "Cannot reach the server";
    throw new ApiError(0, msg);
  }

  // 204 No Content, or any empty body
  const text = await response.text();
  const data = text ? safeJson(text) : null;

  if (!response.ok) {
    const message = data?.message ?? data?.error ?? `Request failed (${response.status})`;
    throw new ApiError(response.status, message, data);
  }
  return data;
}

function safeJson(text) {
  try { return JSON.parse(text); } catch { return text; }
}

export const api = {
  get: (path, params) => request(path, { params }),
  post: (path, body) => request(path, { method: "POST", body }),
  put: (path, body) => request(path, { method: "PUT", body }),
  del: (path) => request(path, { method: "DELETE" }),
};
import { api, ApiError } from "./apiClient.js";

try {
  const page = await api.get("/products", { category: "phones", page: 0 });
  console.log(page.length, "products");
  await api.post("/cart/items", { productId: 3, quantity: 2 });
} catch (err) {
  if (err instanceof ApiError && err.status === 401) {
    console.log("Please log in again");
  } else if (err instanceof ApiError) {
    console.log(`Error ${err.status}: ${err.message}`);
  } else {
    throw err;                              // a bug in our code: do not hide it
  }
}

In real projects

  • One apiClient (or an Axios instance with interceptors) is shared by all screens; on a 401 it clears the token and redirects to login.
  • React data libraries such as TanStack Query call your fetch functions and add caching, retries and loading states (Module 5).
  • Spring Boot returns errors as JSON (a message or ProblemDetail detail field), which the client turns into a readable message. Agree the shape with the backend team.
  • The base URL comes from an environment variable (in Vite, import.meta.env.VITE_API_URL), not hard-coded.

Edge cases

  • Do not set Content-Type yourself when the body is FormData: the browser adds the boundary.
  • Do not JSON.stringify a FormData or file; upload it as the body directly.
  • Sending cookies to another origin needs credentials: "include" and a matching server CORS setting.
  • Redirects are followed automatically; a login redirect may return an HTML page with status 200 — a reason json() sometimes fails.
  • A request with a custom header such as Authorization triggers a CORS preflight (an automatic OPTIONS request first). Your Spring Security config must allow it.

Interview angle

  • "Does fetch reject on a 404?" No. Only on network-level failures; check response.ok.
  • "How do you send JSON with fetch?" method, Content-Type: application/json header, JSON.stringify body.
  • "How do you send a JWT?" Authorization: Bearer <token>.
  • "How do you time out or cancel a request?" AbortController / AbortSignal.timeout().
  • "fetch vs Axios?" Axios rejects on HTTP errors, parses JSON automatically, has interceptors; fetch is built in with no dependency.
  • "What is CORS and where do you fix it?" Browser same-origin protection; fix with server headers.

ES modules: import and export

An ES module is a JavaScript file with its own private scope that shares only what it exports and takes what it needs with import; use named exports by default, one default export per file at most, and load the entry file with type="module".

Before modules, every script shared one global scope, and files depended on the order of the script tags. ES modules (ES2015) solve this and are the standard in browsers, in Vite and React projects, and in modern Node.js. The idea is like Java packages and imports, but at the file level: one file is one module; there is no package declaration and no class-per-file rule.

Named exports

export const GST_RATE = 0.18;

export function addGst(amount) {
  return amount * (1 + GST_RATE);
}

export const formatInr = (amount) =>
  new Intl.NumberFormat("en-IN", { style: "currency", currency: "INR" }).format(amount);

const secret = "not exported";      // private to this file
import { addGst, formatInr } from "./utils/price.js";   // names must match; braces required
import { GST_RATE as TAX } from "./utils/price.js";       // rename on import
import * as price from "./utils/price.js";                // everything in one namespace object

console.log(formatInr(addGst(1000)));   // ₹1,180.00
console.log(TAX);                       // 0.18
console.log(price.addGst(100));         // 118
console.log(Object.keys(price));        // [ 'GST_RATE', 'addGst', 'formatInr' ]

Default export

A module can have one default export. The importer chooses any name, with no braces. React components are usually exported by default.

// CartItem.js
export default function CartItem(props) { /* ... */ }

// elsewhere
import CartItem from "./CartItem.js";        // any local name works
import Item, { helper } from "./CartItem.js"; // default + named together

Rules of modules

  • Module scope. Top-level variables are private to the file; no globals, no clash between files. Modules are always in strict mode and top-level this is undefined.
  • Run once. A module is executed the first time it is imported and then cached; all importers share the same instance (like a Spring singleton). A module-level let counter is therefore shared state.
  • Imports are live, read-only bindings, not copies. The importing file cannot assign to an imported name (TypeError: Assignment to constant variable), but sees later changes made inside the exporting module.
  • Static and hoisted. import lines must be at the top level (not inside if or functions), and run before the rest of the file. This lets tools do "tree shaking": removing unused exports from the final bundle.
  • The path. In the browser and in Node.js you write the file extension and a relative path starting with ./ or ../: "./price.js". Bundlers such as Vite let you leave the extension off for .js/.jsx files, but a bare name like "react" means a package from node_modules.
<script type="module" src="main.js"></script>
<!-- main.js can import others; they load automatically, in parallel -->

Dynamic import

import("./chart.js") loads a module on demand and returns a promise. Use it for code splitting: load a heavy page only when the user opens it. In React this is React.lazy(() => import("./Reports")).

button.addEventListener("click", async () => {
  const { drawChart } = await import("./chart.js");   // downloaded only now
  drawChart(data);
});

CommonJS vs ES modules

Node.js started with its own system, CommonJS: const fs = require("fs") and module.exports = …. You will still see it in older code and config files. Modern Node.js runs ES modules when the file ends in .mjs or package.json contains "type": "module". Do not mix both styles in a file: require is not defined in ES module scope and Cannot use import statement outside a module are the two classic errors.

Edge cases

  • Circular imports (a imports b, b imports a) work only if the values are used later, not while the modules are loading; otherwise you see ReferenceError: Cannot access 'x' before initialization.
  • Wrong braces are silent surprises: import { CartItem } for a default export gives SyntaxError: The requested module does not provide an export named 'CartItem'.
  • Opening a module page from file:// fails because of CORS; use a dev server (see where JavaScript runs).
  • Forgetting ./ in the path makes the browser treat it as a package name: Failed to resolve module specifier "utils/price.js".

Conventions

  • Prefer named exports for helpers; one default export per React component file, with the file name equal to the component name.
  • Keep one purpose per module; group by feature (cart/, orders/), not only by type.
  • Order imports: libraries first, then your own modules, then CSS.

Interview angle

  • "Named vs default export?" Many vs one; braces vs none; name fixed vs free.
  • "ES modules vs CommonJS?" Static import/export (tree-shakeable, async loading) vs dynamic require/module.exports (synchronous, Node).
  • "What is module scope?" Variables are private to the file unless exported.
  • "What is tree shaking / dynamic import?" Removing unused exports at build time; loading code on demand with import().

Node.js, npm and Vite basics

Node.js runs JavaScript outside the browser and npm is its package manager (like Maven for Java): package.json lists your dependencies and scripts, npm install downloads them into node_modules, package-lock.json pins exact versions, and a bundler like Vite prepares your modules for the browser.

Real frontend projects use hundreds of libraries and build tools. They are all JavaScript packages, installed and run with npm (Node Package Manager), which comes with Node.js. Node uses the same V8 engine as Chrome (see where JavaScript runs). Install the LTS version from nodejs.org, then check:

Semantic versions: ^ and ~

Versions look like MAJOR.MINOR.PATCH (for example 19.1.2): a major change may break your code, a minor adds features, a patch fixes bugs. Symbols in package.json say which updates are allowed:

package-lock.json records the exact version of every package, including those that your packages depend on (transitive dependencies). Commit it to Git so every developer and the build server get identical code. Never commit node_modules: add it to .gitignore, and anyone can recreate it with npm ci.

What a bundler like Vite does

Browsers can load ES modules directly, but a real app has hundreds of files, JSX that browsers cannot read, and packages in node_modules. A bundler reads your entry file, follows every import, transforms JSX and TypeScript to plain JavaScript, removes unused code (tree shaking), minifies, splits the result into chunks and writes a few optimised files to dist/ that any web server (or the static folder of Spring Boot) can serve.

  • npm run dev starts the dev server (usually http://localhost:5173) with instant reload when you save a file.
  • npm run build creates the production files in dist/.
  • Environment variables for the browser must start with VITE_ in Vite (import.meta.env.VITE_API_URL), and are public: never put secrets in them.

Vite, JSX and React come together in Module 5.

Rule: every dependency is code you run

An npm package can run scripts at install time and a compromised or look-alike package (typosquatting) is a real attack path. Install packages you recognise, check download counts and maintainers, commit the lock file, run npm audit and use npm ci in pipelines.

Edge cases and common errors

  • npm ERR! code ERESOLVE: two packages need incompatible versions of a third (often React). Fix the versions rather than forcing with --force or --legacy-peer-deps.
  • 'vite' is not recognized / command not found: dependencies were not installed. Run npm install.
  • Error: Cannot find module 'x': package missing from package.json or node_modules deleted.
  • A global install (npm i -g) is for tools only; project dependencies stay local so every developer uses the same version.
  • Other managers (yarn, pnpm) use the same package.json with a different lock file. Use whatever the project already uses and never mix two in one repo.

Interview angle

  • "dependencies vs devDependencies?" Runtime libraries vs build/test tools.
  • "npm install vs npm ci?" Resolves and may update the lock file vs exact reproducible install from it.
  • "What does ^ mean?" Allow minor and patch updates, not major.
  • "Why commit package-lock.json but not node_modules?" Lock gives reproducible versions; node_modules is generated and huge.
  • "What does a bundler do?" Combines, transforms, tree-shakes and minifies modules into files for the browser.

Browser storage: localStorage, sessionStorage and cookies

localStorage keeps strings in the browser until you delete them, sessionStorage until the tab closes, and cookies travel to the server with every request; store objects with JSON.stringify/JSON.parse, and never keep secrets in storage because any script on the page (XSS) can read it.

The browser can keep small amounts of data on the user's device. The data belongs to one origin (scheme + host + port): http://localhost:5173 cannot read what http://localhost:3000 stored. This is client-side only; the Spring Boot server does not see it unless you send it. Typical uses: a theme choice, a half-written form, the items of a to-do list, a cart for a guest, a login token (with caution, below).

The Storage API

Both storages have the same five methods. Keys and values are always strings: if you store a number or an object without converting it, you get text back.

localStorage.setItem("theme", "dark");
console.log(localStorage.getItem("theme"));       // "dark"
console.log(localStorage.getItem("nothing"));     // null — missing key
localStorage.removeItem("theme");
localStorage.clear();                              // delete everything for this origin
console.log(localStorage.length);                  // number of keys

localStorage.setItem("visits", 5);
console.log(typeof localStorage.getItem("visits")); // "string"
console.log(localStorage.getItem("visits") + 1);    // "51"  — not 6!
console.log(Number(localStorage.getItem("visits")) + 1); // 6

localStorage.setItem("user", { name: "Asha" });
console.log(localStorage.getItem("user"));          // "[object Object]" — data lost

sessionStorage.setItem("draft", "Dear team...");    // same methods, gone when the tab closes

Storing objects with JSON

Convert with JSON.stringify on the way in and JSON.parse on the way out (what survives is explained in objects and JSON). A small wrapper makes this safe: reading can return null, the stored text can be broken, and storage can be unavailable.

export const store = {
  get(key, fallback = null) {
    try {
      const raw = localStorage.getItem(key);
      return raw === null ? fallback : JSON.parse(raw);
    } catch {
      return fallback;           // corrupt JSON, or storage blocked
    }
  },
  set(key, value) {
    try {
      localStorage.setItem(key, JSON.stringify(value));
      return true;
    } catch (err) {
      console.warn("Could not save", key, err.name);   // e.g. QuotaExceededError
      return false;
    }
  },
  remove(key) { localStorage.removeItem(key); },
};

store.set("cart", [{ id: 1, qty: 2 }]);
console.log(store.get("cart"));         // [ { id: 1, qty: 2 } ]
console.log(store.get("missing", []));  // []

// To-do app: load on start, save after every change
let tasks = store.get("tasks", []);
function saveTasks() { store.set("tasks", tasks); }

Other useful bits: the storage event (window.addEventListener("storage", e => …)) fires in other tabs when localStorage changes, which is handy for "logged out in one tab" behaviour. Object.keys(localStorage) lists the keys. Storage is synchronous, so do not store megabytes of data; for large data use IndexedDB.

Cookies in short

A cookie is a small piece of text the server sets with a Set-Cookie header; the browser sends it back automatically with every request to that site. Important flags the server sets: HttpOnly (JavaScript cannot read it, which blocks theft through XSS), Secure (HTTPS only), SameSite=Lax|Strict|None (limits sending on cross-site requests, a defence against CSRF), Max-Age/Expires. Session logins in Spring Security use a cookie named JSESSIONID.

Security: what to store and what not

Never store secrets or sensitive personal data in web storage

Any script running on your page can read localStorage: an XSS bug, or a compromised npm package (see npm), can steal everything in it and send it to an attacker. Storage is not encrypted, and it is visible to the user in DevTools. Passwords, card numbers, Aadhaar or PAN numbers and API secrets do not belong there.

  • Safe: UI preferences, a draft, a cart of product ids, non-sensitive cached lists.
  • Debated: JWTs. Many tutorials store the access token in localStorage because it is easy; it is exposed to XSS. A more secure option is an HttpOnly, Secure, SameSite cookie set by the server, or a short-lived access token kept only in memory. Which one fits depends on the architecture; the trade-offs (XSS vs CSRF) are covered in Module 6. If you do use localStorage, keep tokens short-lived and prevent XSS (use textContent, escape output, set a Content-Security-Policy).
  • Always validate what you read back: the user can edit localStorage in DevTools. Never trust a stored role: "admin"; the server must check permissions on every request.

Edge cases

  • QuotaExceededError when the ~5 MB limit is hit; catch it in setItem.
  • In some private browsing modes or when the user blocks site data, access throws SecurityError; always wrap in try/catch if the feature is optional.
  • localStorage does not exist in Node.js (older versions) and in server-side rendering: guard with typeof window !== "undefined".
  • Values with a Date come back as strings; Map/Set come back as {}.
  • Because the data is shared across tabs, two tabs can overwrite each other's saved state.

Interview angle

  • "localStorage vs sessionStorage vs cookies?" Use the table: lifetime, size, sent to server, who sets it.
  • "Can you store an object in localStorage?" Only as a string: JSON.stringify and JSON.parse.
  • "Is it safe to store a JWT in localStorage?" It is readable by any script (XSS); an HttpOnly cookie is safer against XSS but needs CSRF protection. Explain the trade-off.
  • "What does HttpOnly do?" Hides the cookie from JavaScript.

Error handling and debugging

Use try/catch/finally and throw new Error() as in Java (but there are no checked exceptions, and you can throw anything), create custom errors by extending Error, and find bugs with the browser's console, breakpoints and the debugger statement.

try, catch, finally and throw

function parseQuantity(text) {
  const qty = Number(text);
  if (Number.isNaN(qty)) {
    throw new Error(`"${text}" is not a number`);      // like throw new IllegalArgumentException
  }
  if (qty <= 0) throw new RangeError("Quantity must be positive");
  return qty;
}

try {
  console.log(parseQuantity("3"));        // 3
  console.log(parseQuantity("abc"));      // throws
  console.log("never printed");
} catch (err) {
  console.log(err.name, "-", err.message);   // Error - "abc" is not a number
  console.log(err instanceof Error);          // true
  console.log(err.stack.split("\n")[0]);      // the stack trace text (non-standard but everywhere)
} finally {
  console.log("always runs, even after return or throw");
}

try { null.name; } catch { console.log("catch without a variable is allowed"); }

The semantics match Java: a thrown error unwinds the stack until a catch handles it; finally always runs. The differences:

  • There is one catch block per try; to react to different kinds, use instanceof or check err.name inside it.
  • All errors are unchecked; nothing forces you to catch. There is no throws clause.
  • You can throw any value (throw "oops"), but then you get no stack trace. Always throw Error objects.
  • try/catch catches only errors from code that runs inside it while it is running. It does not catch errors in a later callback (setTimeout) or an un-awaited promise; use await inside the try, or .catch() (see async and await).

It means the value before the dot is undefined: an API response with a different shape, a missing array item, an element not found. Custom errors

Extend Error to give your errors a name and extra data. This is the JavaScript version of your own exception classes, and it is how the ApiError in fetch works.

class ValidationError extends Error {
  constructor(field, message) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}

class PaymentError extends Error {
  constructor(message, { cause, code } = {}) {
    super(message, { cause });      // "cause" chains the original error (ES2022)
    this.name = "PaymentError";
    this.code = code;
  }
}

function validateEmail(email) {
  if (!email.includes("@")) throw new ValidationError("email", "Enter a valid email");
}

try {
  validateEmail("asha.example.com");
} catch (err) {
  if (err instanceof ValidationError) {
    console.log(`Fix the ${err.field} field: ${err.message}`);   // Fix the email field: Enter a valid email
  } else {
    throw err;                      // unknown problem: rethrow, do not swallow
  }
}

try {
  try { JSON.parse("{bad"); }
  catch (e) { throw new PaymentError("Could not read gateway reply", { cause: e, code: "GW_PARSE" }); }
} catch (e) {
  console.log(e.name, e.code, e.cause.name);    // PaymentError GW_PARSE SyntaxError
}

Where to catch

  • Catch where you can do something useful: show a message, retry, use a fallback value. Otherwise let it travel up.
  • Do not leave an empty catch {}: it hides bugs. At least log it with console.error(err).
  • Global safety nets log unexpected errors to a monitoring service (Sentry or similar): window.addEventListener("error", …) for runtime errors and window.addEventListener("unhandledrejection", …) for forgotten promise rejections. In React, error boundaries catch errors while rendering (see Module 5).
  • Show the user a friendly message; log the technical details. Never display raw stack traces on the page.
window.addEventListener("unhandledrejection", (event) => {
  console.error("Unhandled promise rejection:", event.reason);
  // sendToMonitoring(event.reason);
});

Breakpoints and the debugger statement

A breakpoint pauses the program on a line so you can look at the values, like in IntelliJ. In Chrome or Edge DevTools open Sources, find your file, and click the line number. Then:

  1. Trigger the code (click the button). Execution stops on that line.
  2. Read the Scope panel for local, closure and global variables, and the Call Stack panel to see who called this function.
  3. Step with Step over (F10), Step into (F11), Step out (Shift+F11) or Resume (F8).
  4. Add Watch expressions, or a conditional breakpoint (right-click the line number, "Add conditional breakpoint") to stop only when, for example, order.id === 7.

Writing the statement debugger; in your code does the same thing: if DevTools is open, execution pauses there. Remove it before committing. In VS Code you can debug Node.js scripts, and with a launch configuration also your browser app, using the same step buttons.

Other DevTools panels you will use daily: Elements (live DOM and CSS), Network (every fetch call with status, headers, payload and timing; the first place to look when an API call fails), Application (localStorage, cookies), and Performance. The React Developer Tools extension adds component inspection for Module 5.

A debugging routine that works

  1. Read the error message and the first line of the stack that is in your file.
  2. Check the Network tab: was the request sent, which status, what response body?
  3. Log or break just before the failing line and inspect real values (console.log({ user })).
  4. Reduce the problem: remove code until it works, then add it back.
  5. Fix the cause, not the symptom; add a test or a check so it cannot come back.

Edge cases

  • finally with return overrides a return/throw in try/catch, as in Java; avoid it.
  • A SyntaxError in a script file is not catchable inside that file: the file never runs. Only eval/JSON.parse can throw it at runtime.
  • A cross-origin script error is reported only as Script error. without details unless CORS headers are set.
  • Minified production code gives unreadable stack traces; build tools emit source maps that DevTools and monitoring tools use to map back to your source.
  • console.log(obj) shows the object as it is when you expand it, not when it was logged. To freeze a snapshot, log JSON.stringify(obj) or structuredClone(obj).

Common mistake: swallowing errors and throwing strings

Wrong: hides the bug, no stack

try {
  saveOrder(order);
} catch (e) {
  // nothing
}
throw "Payment failed";

Right: handle or rethrow an Error

try {
  saveOrder(order);
} catch (e) {
  console.error("saveOrder failed", e);
  showToast("Could not save the order");
}
throw new Error("Payment failed");

Interview angle

  • "How is error handling different from Java?" One catch, no checked exceptions, can throw any value, and async errors need promises or await.
  • "Will try/catch catch an error inside setTimeout?" No; the callback runs later outside the try. Put the try inside the callback.
  • "Name the error types." ReferenceError, TypeError, SyntaxError, RangeError.
  • "How do you debug a failing API call?" Network tab for status/response, console error, breakpoints in the handler.
  • "How do you create a custom error?" class X extends Error and set name.

Mini project: Employee Manager UI — contract, folders and app shell

The project is a React app with JWT login, protected routes and a paginated list/create/edit/delete screen for one resource (employees) against your Spring Boot API; this article fixes the API contract, the folder structure and the wiring files, and the next article builds the pages.

What you build and why this project

Almost every business application is "log in, see a table, add a row, change it, delete it". If you can build this one resource cleanly, you can build most screens of a real project. The project uses everything from Modules 5 and 6: routing, forms, Context, TanStack Query, Axios with interceptors, CORS, JWT, error handling and environment variables. It is also the frontend of Project 3 in the roadmap (see Practice).

Folder structure

Files marked "built earlier" were written in the previous articles; this article does not repeat them. The rule behind the layout: a page is one route; a component is reused by several pages; a hook wraps server data; lib has no React in it (except Context). For bigger projects, group by feature instead (features/employees/…); the idea is the same.

The only file that knows the URLs: employeeApi.js

Components never call api.get('/employees') directly. A small module owns every URL and returns plain data, so a changed endpoint is a one-file edit and tests can mock one module.

import { api } from './axios.js';

export const employeeApi = {
  async list({ page = 0, size = 10, q = '' }, signal) {
    const { data } = await api.get('/employees', {
      params: { page, size, q: q || undefined },         // undefined params are not sent
      signal,
    });
    return data;                                          // PageResponse
  },

  async get(id, signal) {
    const { data } = await api.get(`/employees/${id}`, { signal });
    return data;
  },

  async create(body) {
    const { data } = await api.post('/employees', body);
    return data;
  },

  async update(id, body) {
    const { data } = await api.put(`/employees/${id}`, body);
    return data;
  },

  async remove(id) {
    await api.delete(`/employees/${id}`);                 // 204: no body to return
  },
};

The useEmployees hook from the pagination article now calls employeeApi.list({ page, q, size }, signal) inside its queryFn instead of api.get. Keep it in the same file as the hooks below.

The query hooks

import {
  keepPreviousData, useMutation, useQuery, useQueryClient,
} from '@tanstack/react-query';
import { employeeApi } from '../lib/employeeApi.js';

// Query keys in one place: a typo in a key is a classic cache bug
export const keys = {
  list: (params) => ['employees', params],
  all: ['employees'],
  one: (id) => ['employee', String(id)],
};

export function useEmployees({ page, q, size = 10 }) {
  return useQuery({
    queryKey: keys.list({ page, q, size }),
    queryFn: ({ signal }) => employeeApi.list({ page, q, size }, signal),
    placeholderData: keepPreviousData,
  });
}

export function useEmployee(id) {
  return useQuery({
    queryKey: keys.one(id),
    queryFn: ({ signal }) => employeeApi.get(id, signal),
  });
}

export function useCreateEmployee() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: employeeApi.create,
    onSuccess: () => queryClient.invalidateQueries({ queryKey: keys.all }),
  });
}

export function useUpdateEmployee() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: ({ id, body }) => employeeApi.update(id, body),
    onSuccess: (saved, { id }) => {
      queryClient.setQueryData(keys.one(id), saved);             // detail page is fresh at once
      queryClient.invalidateQueries({ queryKey: keys.all });     // lists refetch
    },
  });
}

export function useDeleteEmployee() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: employeeApi.remove,
    onSuccess: () => queryClient.invalidateQueries({ queryKey: keys.all }),
  });
}

Why invalidateQueries: after a write, the cached lists are out of date. Invalidating the ['employees'] prefix marks every cached page of the list stale and refetches the ones on screen. The single-employee key is ['employee', id] (singular), so it is not matched by that prefix; the update hook sets it directly.

src/lib/queryClient.js is the QueryClient with the retry rule and the global QueryCache error toast from the error-states article, moved into its own file and exported. The order matters: AuthProvider may call the API, so it sits inside the places that provide what it needs; RequireAuth uses router hooks, so BrowserRouter must be above App.

Conventions used in this project

  • One module owns the API URLs; pages never build URLs.
  • Server data lives in TanStack Query, not in useState or Context. Context holds only the logged-in user.
  • Every list page has the four states: loading, error, empty, data.
  • URL is state: page and search text are in the query string; the edit page's id is in the path.
  • Roles are shown as the backend sends them (ADMIN); routes and buttons use the same strings.

Common mistakes when wiring the app

  • Two nested BrowserRouter components, or AuthProvider above the router when it needs router hooks.
  • Placing /employees/new after /employees/:id logic that would treat new as an id. React Router ranks static segments higher, but the habit of checking the order is still useful.
  • Fetching in components with useEffect and also in hooks, so the same data loads twice.
  • Forgetting that useParams() returns strings: id is "7", not 7.

Mini project: list, create, edit and delete pages — and debugging it

The list page combines search, pagination, role-based buttons and delete; the create and edit pages reuse one form that shows server validation errors; a short debugging table maps common symptoms to causes, and a checklist tells you when the project is done.

The list page

This page uses almost everything: URL state for page and search, the query hook, the QueryState wrapper, the pagination control, a role-aware delete button and a mutation with a toast.

import { useState } from 'react';
import { Link } from 'react-router';
import toast from 'react-hot-toast';
import { useEmployeeParams } from '../hooks/useEmployeeParams.js';
import { useDeleteEmployee, useEmployees } from '../hooks/employeeHooks.js';
import { QueryState } from '../components/QueryState.jsx';
import { Pagination } from '../components/Pagination.jsx';
import { SkeletonRows } from '../components/SkeletonRows.jsx';
import { HasRole } from '../components/HasRole.jsx';
import { describeError } from '../lib/errors.js';

export default function EmployeeListPage() {
  const { page, q, update } = useEmployeeParams();
  const query = useEmployees({ page, q });
  const remove = useDeleteEmployee();
  const [search, setSearch] = useState(q);

  function handleSearch(e) {
    e.preventDefault();
    update({ q: search.trim(), page: 0 });               // a new search starts at page 0
  }

  function handleDelete(employee) {
    if (!window.confirm(`Delete ${employee.name}?`)) return;
    remove.mutate(employee.id, {
      onSuccess: () => {
        toast.success(`${employee.name} deleted`);
        const onlyRowOnPage = query.data.content.length === 1;
        if (onlyRowOnPage && page > 0) update({ page: page - 1 });
      },
      onError: (err) => toast.error(describeError(err)),
    });
  }

  const rows = query.data?.content ?? [];

  return (
    <section>
      <div className="toolbar">
        <h1>Employees</h1>
        <form onSubmit={handleSearch} role="search">
          <input value={search} onChange={(e) => setSearch(e.target.value)}
                 placeholder="Search name or email" aria-label="Search employees" />
          <button>Search</button>
        </form>
        <HasRole roles={['ADMIN', 'HR']}>
          <Link to="/employees/new" className="button">Add employee</Link>
        </HasRole>
      </div>

      <QueryState query={query} isEmpty={rows.length === 0}
                  skeleton={<SkeletonRows />}
                  emptyMessage={q ? `No employees match "${q}".` : 'No employees yet.'}>
        <table className={query.isPlaceholderData ? 'dim' : undefined}>
          <thead>
            <tr>
              <th>Name</th><th>Email</th><th>Department</th>
              <th>Salary</th><th></th>
            </tr>
          </thead>
          <tbody>
            {rows.map((e) => (
              <tr key={e.id}>
                <td>{e.name}</td>
                <td>{e.email}</td>
                <td>{e.department}</td>
                <td>₹{Number(e.salary).toLocaleString('en-IN')}</td>
                <td>
                  <HasRole roles={['ADMIN', 'HR']}>
                    <Link to={`/employees/${e.id}/edit`}>Edit</Link>
                  </HasRole>
                  <HasRole roles={['ADMIN']}>
                    <button onClick={() => handleDelete(e)}
                            disabled={remove.isPending && remove.variables === e.id}>
                      Delete
                    </button>
                  </HasRole>
                </td>
              </tr>
            ))}
          </tbody>
        </table>
        <Pagination page={query.data?.page ?? 0} totalPages={query.data?.totalPages ?? 0}
                    disabled={query.isPlaceholderData}
                    onChange={(p) => update({ page: p })} />
      </QueryState>
    </section>
  );
}

Two small files complete it: useEmployeeParams is the URL-state hook from the pagination article saved as src/hooks/useEmployeeParams.js, and SkeletonRows is the skeleton component from the error-states article. A salary shown with toLocaleString('en-IN') gives Indian digit grouping (for example 1,25,000).

Create and edit pages share one form

EmployeeForm takes initial values and an async onSubmit. It already handles client rules, server field errors and the disabled button. The two pages only decide what to call.

import { useNavigate } from 'react-router';
import toast from 'react-hot-toast';
import { EmployeeForm } from '../components/EmployeeForm.jsx';
import { useCreateEmployee } from '../hooks/employeeHooks.js';

export default function EmployeeCreatePage() {
  const navigate = useNavigate();
  const create = useCreateEmployee();

  async function handleSubmit(values) {
    await create.mutateAsync(values);          // throws on 400/409: the form shows the errors
    toast.success('Employee created');
    navigate('/employees');
  }

  return (
    <section>
      <h1>Add employee</h1>
      <EmployeeForm onSubmit={handleSubmit} submitLabel="Create" />
    </section>
  );
}
import { Link, useNavigate, useParams } from 'react-router';
import toast from 'react-hot-toast';
import { EmployeeForm } from '../components/EmployeeForm.jsx';
import { QueryState } from '../components/QueryState.jsx';
import { useEmployee, useUpdateEmployee } from '../hooks/employeeHooks.js';

export default function EmployeeEditPage() {
  const { id } = useParams();                   // a string such as "7"
  const navigate = useNavigate();
  const query = useEmployee(id);
  const update = useUpdateEmployee();

  async function handleSubmit(values) {
    await update.mutateAsync({ id, body: values });
    toast.success('Employee updated');
    navigate('/employees');
  }

  const employee = query.data;

  return (
    <section>
      <h1>Edit employee</h1>
      <QueryState query={query}>
        {employee && (
          <EmployeeForm
            key={employee.id}                   // new employee loaded = fresh form state
            initial={{
              name: employee.name,
              email: employee.email,
              department: employee.department,
              salary: String(employee.salary),
            }}
            onSubmit={handleSubmit}
            submitLabel="Save changes"
          />
        )}
      </QueryState>
      <Link to="/employees">Back to the list</Link>
    </section>
  );
}

The form copies initial into its own state once, when it first renders. That is why the edit page renders the form only after the data has loaded (inside QueryState), and why it passes a key: with the key, loading a different employee mounts a fresh form. If you rendered the form first with empty values and passed the data later, the inputs would stay empty, which is a very common bug.

Try the whole flow

  1. Start PostgreSQL and the Spring Boot API (port 8080), then npm run dev (port 5173).
  2. Open /employees while logged out. You must land on /login.
  3. Log in with a wrong password: a clear message, no redirect loop. Log in correctly: you return to /employees.
  4. Add an employee with an empty name and a bad email: client messages appear without a request. Fix them and submit an email that already exists: the server's 409 message appears under the email field.
  5. Create a valid employee, see the toast and the new row. Edit it. Delete it as ADMIN; log in as a normal user and check that the Delete button is hidden and that DELETE from curl gives 403.
  6. Stop the Spring Boot app and reload: you see the "cannot reach the server" message with a retry button, not a white page.
  7. Wait for the token to expire (or shorten it to one minute in application.yml) and click around: the interceptor refreshes, or sends you to the login page.
  8. Run npm run build and npm run preview; repeat steps 2 to 5 against the built app.

Debugging with the Network tab

Open DevTools (F12) and the Network tab, filter by Fetch/XHR. Click a request and read four things: the status code, the request headers (is there Authorization: Bearer …?), the request payload (are the field names right?) and the response body (what did Spring say?). The Console tab shows CORS errors in red.

Reproduce an API problem outside React

If something fails, copy the request from the Network tab (right-click, Copy as cURL) and run it in a terminal or Postman. If curl works but the browser fails, the problem is browser-specific: CORS, cookies or headers. If curl fails too, the bug is in the backend. This one habit saves hours.

Edge cases to test

  • Open /employees/9999/edit (a missing id): the page shows the 404 message and a link back; it does not crash.
  • Double-click Create quickly: the button disables and only one employee is created.
  • Delete the last row on the last page: the list moves to the previous page.
  • Change the search while on page 3: the page resets to 0.
  • Salary of 0, negative, or letters: client and server both reject.
  • A normal user opens /employees/new by typing the URL: redirected to /forbidden by the route, and a direct API call is also rejected.

How a real team would extend this

  • Replace hand-written forms with React Hook Form and Zod schemas; keep the server-error mapping.
  • Add TypeScript (Module 7) so a renamed DTO field breaks the build, not the user.
  • Add tests for the form and the list with Vitest and MSW (testing).
  • Deploy: the UI on Vercel or in an Nginx container, the API in Docker (deployment), a pipeline on every push (DevOps · Module 4).

Interview: "Walk me through the React app you built against your Spring Boot API"

  • Architecture: Vite SPA, Axios instance with interceptors, JWT in memory plus refresh cookie (or localStorage in a simple version), React Router with a guard, TanStack Query for server state.
  • Features: login, protected routes, CRUD, pagination in the URL, role-based UI, backend validation errors on fields, loading/error/empty states, toasts.
  • Hard parts you solved: CORS and preflight, 401 refresh with a single shared promise, cache invalidation after writes, the SPA fallback on deploy.
  • Honest limits: client roles are cosmetic; the backend enforces security.

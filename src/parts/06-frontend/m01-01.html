As a Java developer you already know one side of the web: a Spring Boot controller receives a request and returns a response. This module shows you the other side — what the browser does before, during and after that request. You will learn how a URL is split into parts, how DNS finds your server, what an HTTP request and response really contain, and how the browser turns HTML, CSS and JavaScript into pixels on the screen.

Everything in the later modules builds on this. HTML (Module 2) and CSS (Module 3) are files the browser downloads and renders. JavaScript (Module 4) and React (Module 5) run inside the browser and call your API (Module 6). When something breaks between React and Spring Boot, the browser DevTools covered at the end of this module are how you find out which side is at fault.

Browser, server and the request–response cycle

The browser (the client) always starts the conversation by sending an HTTP request; the server answers with exactly one response — an HTML page, a CSS or JavaScript file, an image or JSON data.

The web is built on the client–server model. A client is a program that asks for something. A server is a program that waits for requests and answers them. On the web, the usual client is a browser — Chrome, Edge, Firefox or Safari. The server is a program listening on a network port (a numbered "door" on a machine), for example the embedded Tomcat inside your Spring Boot app on port 8080, or Nginx on port 443.

The word "server" means two things: the machine (a cloud VM, a container) and the program running on it. When someone says "the server is down", they may mean either. In these notes, "server" means the program unless stated otherwise.

The request–response cycle

Every interaction on the web follows the same pattern:

  1. The client opens a connection to the server and sends a request, for example "GET me /products/42".
  2. The server runs some code — it reads a file from disk, or calls your controller, service and repository, which query the database.
  3. The server sends back exactly one response: a status code (200, 404, 500…), some headers and usually a body.
  4. The client uses the response — the browser renders HTML, applies CSS, runs JavaScript, or hands JSON to your React code.

For a Java developer, a useful picture is a method call over the network. The request is like the method name plus its arguments; the response is like the return value. The differences matter, though: a network call is slow (milliseconds, not nanoseconds), it can fail halfway, and the server does not remember you between calls.

What a server can send back

The server tells the browser what kind of data the body contains using the Content-Type header. The browser decides what to do with the body based on it.

BodyContent-TypeWhat the browser does with it
HTML documenttext/htmlParses it and builds the page
Stylesheettext/cssApplies the styles to the page
Scripttext/javascriptRuns it in the JavaScript engine
Image, font, videoimage/png, font/woff2, video/mp4Displays it, or uses it to draw text
Dataapplication/jsonHands it to your JavaScript (for example a React component)

One page is never one request. The browser first downloads the HTML, then discovers the stylesheets, scripts, images and fonts it references and requests each of them. A React app then makes further requests for JSON data. A busy shopping page easily makes dozens of requests — you will see every one of them in the Network panel.

Try it: your own server and client

The smallest possible "server" is a Spring Boot controller. The browser is the client.

import java.util.Map;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {

    @GetMapping("/api/hello")
    public Map<String, String> hello() {
        // Spring converts the Map to JSON and sets Content-Type: application/json
        return Map.of("message", "Namaste from Spring Boot");
    }
}

Start the app and open http://localhost:8080/api/hello in the browser. The browser sends a GET request; Tomcat hands it to Spring's DispatcherServlet, which calls your method; the return value goes back as the response body.

{"message":"Namaste from Spring Boot"}

In production you often see two kinds of server, one in front of the other.

A reverse proxy is a server that receives requests from browsers and forwards them to another server behind it. A common setup: Nginx serves the React files directly and forwards every request that starts with /api to Spring Boot.

localhost is the name for your own machine; it resolves to 127.0.0.1 (IPv4) or ::1 (IPv6). During development the browser, the Vite server and Spring Boot all run on localhost, just on different ports.

Rule: the client always speaks first

In plain HTTP the server cannot send anything to a browser that did not ask. For live updates — order tracking, chat, stock prices — applications use WebSockets (a two-way connection) or Server-Sent Events (a one-way stream from server to browser), or the browser simply asks again every few seconds (polling).

Rule: HTTP is stateless

Each request is independent. The server does not automatically remember that the same user sent the previous request. Logins, carts and preferences work only because the client sends something with every request — a cookie with a session id, or an Authorization header with a token. You will see how in HTTP requests and responses.

Edge case: the browser is not the only client

curl, Postman, a mobile app, another microservice or an attacker's script can all send the same requests your React app sends. Anything only the browser enforces — a hidden Delete button, a disabled field, HTML form validation — can be bypassed in seconds. The server must validate and authorise every single request.

Mistake: "the admin API is safe because normal users never see the button"

Hiding a button is a user-interface decision, not security. Protect the endpoint itself on the server, for example with Spring Security rules or @PreAuthorize (see Spring Boot · Module 4).

In real projects

A common production layout: the React build sits on a CDN or behind Nginx, the Spring Boot API runs as several instances behind a load balancer, and all instances share one PostgreSQL database. Because HTTP is stateless and the instances share nothing in memory, any instance can serve any request — that is what makes scaling out easy.

Interview angle: "Explain the client–server model"

  • The client (browser, app) sends a request; the server processes it and returns one response.
  • The client always initiates; HTTP is stateless, so state travels in cookies or tokens.
  • Mention the layers: browser → load balancer or Nginx → Spring Boot → database.
  • Close with the security point: never trust the client; validate and authorise on the server.

URL anatomy: scheme, host, port, path, query, fragment

A URL tells the browser which protocol to use (scheme), which server to contact (host and port), which resource to ask for (path), extra parameters (query) and a position inside the page (fragment) — and the fragment never reaches the server.

A URL (Uniform Resource Locator) is the address of a resource on the web. You type URLs, put them in links, and call them from fetch(). Spring Boot reads parts of them with @PathVariable and @RequestParam. Knowing each part precisely saves you from many small bugs.

PartIn the exampleMeaningSent to the server?
SchemehttpsThe protocol. https = HTTP over an encrypted TLS connection.Decides how to connect
Hostshop.example.comDomain name (or IP address) of the server. DNS turns it into an IP.Yes, in the Host header
Port8443Which port on that machine. Omitted = default (80 for http, 443 for https).Used to connect
Path/products/42Which resource. Maps to @GetMapping("/products/{id}").Yes
Query?color=red&size=mKey–value parameters after ?, separated by &. Maps to @RequestParam.Yes
Fragment#reviewsA position inside the page — usually the element with id="reviews".No — browser only

Scheme

Besides http and https you will meet mailto: (open an email client), tel: (dial a number), ws: and wss: (WebSockets), file: (a local file — opening an HTML file by double-clicking gives you a file:///C:/... URL) and data: (data embedded in the URL itself). Modern browsers mark plain http sites as "Not secure"; production sites use https.

Host and port

The host can be a domain (shop.example.com), an IPv4 address (192.168.1.20) or an IPv6 address in square brackets ([::1]). shop is a subdomain of example.com. Host names are case-insensitive: SHOP.Example.com is the same server.

The port is written after a colon. You rarely see it in production because sites use the defaults, but in development it is everywhere: http://localhost:5173 (Vite) and http://localhost:8080 (Spring Boot).

Path

The path identifies a resource on the server. Unlike the host, the path is usually case-sensitive — Spring MVC treats /Products/42 and /products/42 as different paths. REST APIs use the path to name resources: /api/orders/1042, /api/customers/7/orders.

Query string

The query string starts with ? and holds key=value pairs joined with &. Use it for optional inputs: filters, sorting, paging and search terms. A key can repeat: ?tag=veg&tag=spicy binds to List<String> tag in Spring.

// GET /api/products?category=snacks&page=2&sort=price
@GetMapping("/api/products")
public Page<ProductDto> list(@RequestParam String category,
                             @RequestParam(defaultValue = "0") int page,
                             @RequestParam(defaultValue = "name") String sort) {
    // ...
}

// GET /api/products/42  -> id = 42
@GetMapping("/api/products/{id}")
public ProductDto one(@PathVariable long id) {
    // ...
}

Fragment

The fragment (also called the hash) starts with #. The browser keeps it to itself: it scrolls to the element whose id matches, and JavaScript can read it with location.hash. It is never sent in the HTTP request, so your Spring Boot logs never show it. Older single-page apps used it for routing (/#/orders/42) precisely because changing the fragment does not reload the page.

Percent-encoding

Only a limited set of characters may appear in a URL as-is. Others — spaces, &, ?, #, non-English text — must be percent-encoded: each byte becomes % plus two hex digits. A space becomes %20, @ becomes %40, & becomes %26. In HTML form submissions (and in Java's URLEncoder) a space in the query string becomes + instead.

encodeURIComponent("Asha & Co");   // "Asha%20%26%20Co"
encodeURIComponent("मसाला");        // "%E0%A4%AE%E0%A4%B8%E0%A4%BE%E0%A4%B2%E0%A4%BE"
decodeURIComponent("Asha%20%26%20Co"); // "Asha & Co"
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;

String q = URLEncoder.encode("Asha & Co", StandardCharsets.UTF_8);
System.out.println(q);
Asha+%26+Co

Reading a URL in code

Never split URLs by hand with string methods. Both languages have a parser. Paste this into the browser console:

const url = new URL("https://shop.example.com:8443/products/42?color=red&size=m#reviews");
console.log(url.protocol);               // "https:"
console.log(url.hostname);               // "shop.example.com"
console.log(url.port);                   // "8443"
console.log(url.pathname);               // "/products/42"
console.log(url.search);                 // "?color=red&size=m"
console.log(url.searchParams.get("size")); // "m"
console.log(url.hash);                   // "#reviews"
console.log(url.origin);                 // "https://shop.example.com:8443"

const api = new URL("https://shop.example.com/api/products");
api.searchParams.set("q", "dosa mix & chutney"); // encodes for you
console.log(api.toString());
// "https://shop.example.com/api/products?q=dosa+mix+%26+chutney"
import java.net.URI;

URI uri = URI.create("https://shop.example.com:8443/products/42?color=red&size=m#reviews");
System.out.println(uri.getScheme());   // https
System.out.println(uri.getHost());     // shop.example.com
System.out.println(uri.getPort());     // 8443
System.out.println(uri.getPath());     // /products/42
System.out.println(uri.getQuery());    // color=red&size=m
System.out.println(uri.getFragment()); // reviews

Origin: the part that matters for security

An origin is the combination scheme + host + port. https://shop.example.com and https://shop.example.com:443 are the same origin (443 is the default). http://localhost:5173 and http://localhost:8080 are different origins because the ports differ. Browsers isolate data per origin (cookies work a little differently, by domain), and a page from one origin calling an API on another origin triggers CORS checks — the reason your first React-to-Spring call fails in development. Module 6 explains the fix.

Rule: encode every value you put into a URL

Build query strings with URLSearchParams / url.searchParams in JavaScript and UriComponentsBuilder or URLEncoder in Java. A raw & or # inside a value silently cuts it short or starts a new parameter.

Convention: path for identity, query for options

Use the path to identify a resource (/api/orders/1042) and the query for filtering, sorting and paging (/api/orders?status=SHIPPED&page=0). Use lowercase, hyphen-separated path segments: /order-items, not /OrderItems.

Edge cases

  • url.port returns an empty string when the port is the default — new URL("https://a.com:443/").port is "". Java's URI.getPort() returns -1 when no port is written.
  • URLs have practical length limits. Spring Boot's embedded Tomcat limits the request line plus headers to 8 KB by default (server.max-http-request-header-size); a longer URL gets an error response before your controller runs. Send large data in a POST body.
  • A trailing slash can matter: since Spring Framework 6 (Boot 3), /api/orders/ no longer matches a mapping for /api/orders by default.

Mistake: putting secrets or personal data in the URL

URLs end up in browser history, server and proxy logs, analytics tools and the Referer header sent to other sites. Never put passwords, tokens, Aadhaar or PAN numbers in a query string. Send them in a request body or header over HTTPS.

Interview angle

  • "Name the parts of a URL" — scheme, host, port, path, query, fragment; give default ports.
  • "Is the fragment sent to the server?" — No; the browser uses it for in-page navigation and JavaScript reads it via location.hash.
  • "What is an origin?" — scheme + host + port; different ports mean different origins, which is why CORS appears between Vite (5173) and Spring Boot (8080).
  • "Path variable or request param?" — path identifies the resource, query refines the result.

DNS in short: from a name to an IP address

DNS is the internet's phone book: it turns a name like shop.example.com into the IP address the browser connects to, and every step caches the answer for a time called the TTL.

Computers connect to IP addresses — 203.0.113.10 (IPv4) or 2001:db8::10 (IPv6). Humans remember names. The Domain Name System (DNS) is the distributed database that maps names to addresses. Before the browser can send a single byte of HTTP, it needs the IP address of the host in the URL.

How a lookup works

  1. Browser cache. The browser remembers recent answers. If it looked up the name a minute ago, it is done.
  2. Operating system. The OS checks its own cache and the hosts file — a local text file that maps names to IPs and wins over real DNS.
  3. Recursive resolver. The OS asks a resolver — usually your ISP's, your company's, or a public one such as Google (8.8.8.8) or Cloudflare (1.1.1.1). The resolver does the hard work and caches results for everyone who uses it.
  4. Root servers. If the resolver has nothing cached, it asks a root server, which answers "I don't know, but here are the servers for .com".
  5. TLD servers. The top-level domain servers for .com (or .in, .org) answer "ask the name servers of example.com".
  6. Authoritative server. The domain's own name server (often run by the DNS provider, such as Route 53 or Cloudflare) gives the final answer: the IP address and a TTL (time to live, in seconds).
  7. The resolver returns the IP to your machine; everyone on the way caches it until the TTL runs out.

RecordHoldsExample use

Look it up yourself

nslookup works on Windows, macOS and Linux; dig is common on Linux and macOS; PowerShell has Resolve-DnsName. The output below is illustrative — real addresses and the exact layout differ.

$ nslookup shop.example.com

Address:  192.168.1.1

Non-authoritative answer:
Name:     shop.example.com
Address:  203.0.113.10

$ dig +short shop.example.com

"Non-authoritative" means the answer came from a resolver's cache, not directly from the domain's own name server. That is normal.

Java does the same lookup when you open a connection. You can trigger it directly:

import java.net.InetAddress;

public class DnsDemo {
    public static void main(String[] args) throws Exception {
        for (InetAddress address : InetAddress.getAllByName("localhost")) {
            System.out.println(address);
        }
    }
}

The hosts file: DNS on your own machine

The hosts file lets you map a name to an IP without any DNS server. Developers use it to test with a realistic name. Editing it needs administrator rights.

# Windows: C:\Windows\System32\drivers\etc\hosts
# Linux and macOS: /etc/hosts
127.0.0.1   shop.test

Now http://shop.test:8080 reaches the Spring Boot app on your machine. Use the reserved .test ending for such names; it will never clash with a real domain.

Rule: DNS gives an IP address, never a port

A and AAAA records hold only an address. The port comes from the URL — written explicitly, or the default for the scheme. If your app listens on 8080 and the URL has no port, the browser tries 80 or 443 and fails, however correct the DNS is.

Edge cases and the errors you will see

  • Chrome shows DNS_PROBE_FINISHED_NXDOMAIN when a name does not exist (a typo, or a record not created yet).
  • In Java, a failed lookup throws java.net.UnknownHostException — common when a microservice's host name is misspelt in application.yml.
  • Changes are not instant. Old answers live in caches until their TTL expires, so a server migration can look "half done" for a while. Lower the TTL a day before a planned change.
  • The JVM caches lookups too (controlled by the networkaddress.cache.ttl security property), so a long-running Java process can keep using an old IP.

Mistake: forgetting an entry in the hosts file

You add 127.0.0.1 api.myapp.com for a test, forget it, and weeks later the "production" site on your laptop is really your local server. When a site behaves strangely only on your machine, check the hosts file first.

Going deeper

DNS normally runs over UDP port 53. Browsers can also use DNS over HTTPS (DoH) for privacy. Caching layers, resolvers and DNS-based load balancing are covered in CS Fundamentals · Module 2 and DevOps · Module 2.

Interview angle: "How does DNS resolution work?"

Answer in order: browser cache → OS cache and hosts file → recursive resolver → root → TLD → authoritative server → answer cached for the TTL. Name the A, AAAA and CNAME records, and mention that DNS returns only an IP, never a port.

HTTP requests and responses

HTTP is the request–response protocol of the web: a request carries a method, a path, headers and an optional body; a response carries a status code, headers and an optional body — and every request stands alone.

HTTP (HyperText Transfer Protocol) defines the messages a client and server exchange. HTTPS is exactly the same protocol, sent through an encrypted TLS connection. Every API you build in Spring Boot and every fetch() call you write in React is HTTP, so this is one of the most important topics in the whole page.

Anatomy of a request

In HTTP/1.1 a message is plain text. This is what the browser sends when your React app loads an order:

GET /api/orders/1042 HTTP/1.1
Host: shop.example.com
Accept: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI3In0.signature
Cookie: lang=en
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...
  1. Request line: the method (GET), the request target (path + query: /api/orders/1042) and the protocol version.
  2. Headers: Name: value lines with extra information — which site (Host), which formats the client accepts, credentials, cookies.
  3. An empty line marks the end of the headers.
  4. An optional body — empty for GET, JSON or form data for POST, PUT and PATCH.

Anatomy of a response

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 55
Cache-Control: no-store
Date: Sun, 18 Oct 2026 10:15:00 GMT

{"id":1042,"status":"DELIVERED","total":1499,"items":2}

The status line has the version, a three-digit status code and an optional reason phrase. Then come headers, an empty line and the body. Content-Length is the body size in bytes (55 here).

A request that creates something usually carries a JSON body and gets 201 Created back:

POST /api/orders HTTP/1.1
Host: shop.example.com
Content-Type: application/json
Content-Length: 29

{"productId":42,"quantity":2}
HTTP/1.1 201 Created
Location: /api/orders/1043
Content-Type: application/json

{"id":1043,"status":"PLACED"}

The same thing in Spring Boot

import java.net.URI;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService orderService; // your own service class

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @GetMapping("/{id}")
    public OrderDto get(@PathVariable long id) {
        return orderService.find(id);                 // 200 OK + JSON body
    }

    @PostMapping
    public ResponseEntity<OrderDto> create(@RequestBody CreateOrderRequest req) {
        OrderDto saved = orderService.place(req);
        URI location = URI.create("/api/orders/" + saved.id());
        return ResponseEntity.created(location).body(saved); // 201 + Location
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> cancel(@PathVariable long id) {
        orderService.cancel(id);
        return ResponseEntity.noContent().build();    // 204, no body
    }
}

Methods

The method (also called the verb) says what the client wants to do. Two properties matter in interviews. A safe method does not change anything on the server. An idempotent method has the same effect on the server whether you send it once or ten times — important because networks retry requests.

MethodUse it toBodySafeIdempotent
GETRead a resource or a listNoYesYes
POSTCreate a resource or trigger an action (place order, pay)YesNoNo
PUTReplace a resource completelyYesNoYes
PATCHChange part of a resourceYesNoNot guaranteed
DELETERemove a resourceUsually noneNoYes
HEADLike GET, but only the headersNoYesYes
OPTIONSAsk which methods are allowed; used by the CORS preflightNoYesYes

Idempotent is about the effect, not the response. Deleting order 1042 twice leaves the server in the same state as deleting it once, even though the second call may return 404. Sending "POST /api/orders" twice creates two orders — which is why payment APIs ask for an idempotency key header so they can detect a retried POST.

State on top of a stateless protocol: cookies and tokens

Because HTTP is stateless, a login must be proven again on every request. Two common ways:

  • Session cookie. After login the server responds with Set-Cookie: JSESSIONID=8F2A…; Path=/; HttpOnly. The browser stores it and automatically adds Cookie: JSESSIONID=8F2A… to every later request to that site. The server looks up the session by id.
  • Token. After login the server returns a token (often a JWT). Your JavaScript stores it and adds Authorization: Bearer <token> to each API call. The browser does not do this automatically.

Cookie flags matter: HttpOnly (JavaScript cannot read it), Secure (sent only over HTTPS) and SameSite (limits sending on cross-site requests). The JWT flow is covered in Spring Boot · Module 4 and the browser side in Module 6.

Caching in one paragraph

The browser keeps copies of responses according to Cache-Control. max-age=31536000, immutable suits Vite's hashed build files (index-a1b2c3.js): the name changes whenever the content changes. no-store means "never store" — right for personal data. With an ETag header the browser can ask "has it changed?" and get a cheap 304 Not Modified with no body.

HTTPS

HTTPS wraps HTTP in TLS. Before any HTTP is sent, the browser and server perform a TLS handshake: the server presents a certificate proving it owns the domain, and both sides agree on encryption keys. After that, nobody in between — public Wi-Fi, an ISP — can read or change the messages. The default port is 443. A page loaded over HTTPS that tries to load a script over plain HTTP is blocked by the browser as mixed content.

HTTP versions

VersionRuns overKey idea
HTTP/1.1 (1997)TCPText messages; connections are reused (keep-alive), but each carries one request at a time, so browsers open several connections per host (Chrome allows six)
HTTP/2 (2015)TCPBinary frames; many requests in parallel on one connection (multiplexing); compressed headers; header names always lowercase
HTTP/3 (2022)QUIC over UDPFaster connection setup; one lost packet no longer stalls every request; good on mobile networks

The meaning — methods, status codes, headers — is the same in all three versions. Only the way bytes travel changes. DevTools shows the version in the Network panel's Protocol column (http/1.1, h2, h3).

Notice HTTP/1.1 200 with no "OK": Tomcat leaves out the optional reason phrase. Clients only use the number. Transfer-Encoding: chunked means the body was streamed in pieces instead of declaring a Content-Length up front.

Tip: curl on Windows

In Windows PowerShell 5.1, curl is an alias for Invoke-WebRequest, which takes different options. Type curl.exe to run real curl (it ships with Windows 10 and 11), or use Git Bash.

Rules

  • GET must not change server state. Links, prefetchers and crawlers follow GET URLs freely.
  • A 204 response and a 304 response have no body.
  • Send Content-Type: application/json with a JSON body, or Spring rejects @RequestBody with 415.
  • Header names are case-insensitive (content-type = Content-Type); values often are not.

Conventions for REST APIs

  • Nouns in paths, methods for actions: POST /api/orders, not POST /api/createOrder.
  • Return the most specific status code: 201 + Location on create, 204 on delete, 404 for a missing id, 400 with field errors for bad input.
  • Return errors as JSON with a consistent shape. Spring supports the standard Problem Details format (application/problem+json).

Edge cases

  • A GET request with a body has no defined meaning; many servers and proxies drop it, and fetch() refuses it with TypeError: Request with GET/HEAD method cannot have body.
  • Cache-Control: no-cache does not mean "do not cache" — it means "store it, but check with the server before every use". Use no-store to forbid storing.
  • With 301 and 302, browsers may change a redirected POST into a GET. 307 and 308 keep the method and body.
  • Browsers and fetch() follow redirects automatically, so your code sees the final response, not the 302.

Wrong: 200 for everything

HTTP/1.1 200 OK
Content-Type: application/json

{"success":false,"error":"Order not found"}

Right: the status code tells the truth

HTTP/1.1 404 Not Found
Content-Type: application/problem+json

{"title":"Not Found","status":404,"detail":"Order 1042 not found"}

More common mistakes

  • Using 401 when the user is logged in but lacks permission — that is 403.
  • Making "Delete" a GET link (/orders/1042/delete); a browser prefetch or crawler can trigger it.
  • Forgetting that fetch() does not throw on 404 or 500 — you must check response.ok (see Module 6).

Interview angle

  • GET vs POST: GET reads, is safe and idempotent, sends data in the URL and can be cached and bookmarked; POST creates or acts, sends data in the body and is not idempotent.
  • PUT vs PATCH: PUT replaces the whole resource and is idempotent; PATCH changes some fields and is not guaranteed idempotent.
  • 401 vs 403: 401 = who are you? (authenticate); 403 = I know you, and the answer is no.
  • Stateless: each request carries everything needed; sessions and JWTs add state on top.
  • HTTP/2: multiplexing many requests over one connection; HTTP/3 moves to QUIC over UDP.

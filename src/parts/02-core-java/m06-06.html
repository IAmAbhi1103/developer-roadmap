Interview questions — Multithreading and concurrency

Process vs thread? What is the difference between concurrency and parallelism?

A process is a running program with its own memory space; a thread is a unit of execution inside a process, and threads of one process share its heap but each has its own stack. Threads are cheaper to create and communicate through shared memory, which also makes them risky. Concurrency means managing many tasks that overlap in time (possibly on one core, by switching); parallelism means actually running tasks at the same instant on several cores.

start() vs run()? Can you start a thread twice?

start() asks the JVM to create a new thread, which then calls run(). Calling run() directly just executes the method in the current thread like any normal call, so no concurrency happens. Calling start() a second time throws IllegalThreadStateException, because a thread that has been started (even if finished) cannot be restarted.

Name the thread states and what moves a thread between them.

NEW (created, not started), RUNNABLE (running or ready to run), BLOCKED (waiting to enter a synchronized block), WAITING (wait(), join(), LockSupport.park() with no timeout), TIMED_WAITING (sleep, wait(ms), join(ms)) and TERMINATED (finished). start() moves NEW to RUNNABLE; lock contention gives BLOCKED; notify, a timeout or an interrupt brings a thread back.

Why is count++ not thread-safe?

It is three steps: read the value, add one, write it back. Two threads can both read 5, both compute 6 and both write 6, so one increment is lost. This is a read-modify-write race. Fix with synchronized, AtomicInteger.incrementAndGet() (uses CAS) or LongAdder for heavy contention. volatile does not help because it gives visibility but not atomicity.

synchronized vs volatile?

synchronized gives mutual exclusion (one thread in the block at a time, on the same lock) plus visibility: changes made before leaving the block are seen by the next thread that enters. volatile gives only visibility and ordering for one variable: a write is seen by later reads in other threads. Use volatile for simple flags (volatile boolean running) and safe publication; use synchronized or atomics when the action is a compound one like increment.

Which object does a synchronized method lock?

An instance method locks this; a static synchronized method locks the Class object (MyClass.class). A synchronized block locks the object you name. Threads using different locks do not block each other, so instance and static synchronized methods do not exclude one another. The lock is reentrant: a thread that already holds it can enter another synchronized block on the same object.

Explain ThreadPoolExecutor and what happens when the queue is full.

Parameters: core size, maximum size, keep-alive time, work queue, thread factory and rejection handler. A new task starts a core thread if fewer than core are running; otherwise it goes into the queue; if the queue is full a thread up to the maximum is created; if that is also full the rejection policy runs (default AbortPolicy throws RejectedExecutionException). With an unbounded queue the maximum is never used and memory can run out.

Runnable vs Callable; execute vs submit; what does Future.get() throw?

Callable returns a value and may throw checked exceptions. execute takes a Runnable and returns nothing, and an uncaught exception goes to the thread's handler. submit returns a Future and captures any exception inside it. get() throws ExecutionException (the real error is the cause), InterruptedException, and TimeoutException in the timed version, or CancellationException if cancelled.

thenApply vs thenCompose in CompletableFuture. How do you run three calls in parallel?

thenApply maps the result with a normal function (like map); thenCompose is for a function that itself returns a CompletableFuture (like flatMap), avoiding a nested future. For three parallel calls, start each with supplyAsync(..., executor), combine with CompletableFuture.allOf(a, b, c), then read each with join(). Use your own executor for blocking calls, because the default common pool is small.

How does ConcurrentHashMap achieve thread safety? How does it differ from synchronizedMap?

In Java 8 and later it uses CAS to insert into an empty bin and a synchronized lock on the first node of a bin otherwise, so threads that touch different bins run in parallel; reads take no lock. It forbids null keys and values and has weakly consistent iterators. Methods such as merge and computeIfAbsent are atomic. Collections.synchronizedMap guards every method with one lock, and iteration needs manual locking.

What is a deadlock? Give an example and how to prevent it.

Thread 1 holds lock A and waits for B; thread 2 holds B and waits for A; both wait forever. It needs mutual exclusion, hold-and-wait, no preemption and circular wait (the four Coffman conditions). Prevent by taking locks in a fixed global order, using tryLock with a timeout, holding fewer locks and not calling foreign code under a lock. Detect with jstack or jcmd <pid> Thread.print, which prints "Found one Java-level deadlock".

CountDownLatch vs CyclicBarrier vs Semaphore?

A latch lets threads wait until a count of events reaches zero and cannot be reset. A barrier makes a fixed group of threads wait for each other at a point and then resets for the next round. A semaphore holds permits and limits how many threads can use a resource at once, for example 3 concurrent calls to a partner API.

What is ThreadLocal and what goes wrong with thread pools?

It stores a separate value for each thread, used for request context such as the logged-in user or a trace id. Pool threads are reused, so a value set by one task stays visible to the next task on that thread unless you call remove(). That leaks data between requests and keeps objects alive. Always remove in finally. Values also do not carry over to tasks run on other threads.

What are virtual threads and how do they differ from platform threads?

Virtual threads (final in Java 21) are lightweight threads scheduled by the JVM onto a few carrier platform threads. When they block on I/O they unmount, so the carrier serves other virtual threads. Creating a million of them is feasible, so you use one per task and do not pool them. They help with blocking, I/O-heavy work and do nothing for CPU-bound work. Pinning (blocked inside native code, or inside synchronized before Java 24) is the known limitation. Spring Boot enables them with spring.threads.virtual.enabled=true.

How do you stop a thread properly?

Java has no safe forced stop (Thread.stop() was removed from use). You ask the thread to stop cooperatively: call interrupt(), and the task checks Thread.currentThread().isInterrupted() or handles InterruptedException from blocking calls. When you catch InterruptedException and cannot rethrow it, restore the flag with Thread.currentThread().interrupt(). A volatile boolean flag also works for loops that do not block.

Cheat sheet — Multithreading and concurrency

  • Process vs thread process = own memory; threads share the heap, each has its own stack.
  • Create new Thread(runnable).start(), a lambda, or an executor. start() runs in a new thread; run() is a plain call.
  • States NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.
  • Interrupt cooperative; on InterruptedException rethrow or call Thread.currentThread().interrupt().
  • Race condition count++ is read, add, write; lost updates without protection.
  • Memory model atomicity, visibility, ordering; happens-before links a write to later reads (lock release/acquire, volatile, start/join).
  • synchronized mutual exclusion plus visibility; instance method locks this, static locks the Class; reentrant; keep it small.
  • volatile visibility only, no atomicity; good for flags and double-checked locking.
  • Atomics AtomicInteger.incrementAndGet(), compareAndSet (CAS); LongAdder under heavy contention.
  • Locks ReentrantLock: lock() then unlock() in finally; tryLock(time); fairness optional.
  • wait/notify legacy; hold the lock, loop on the condition; prefer BlockingQueue.
  • ThreadPoolExecutor core, max, keep-alive, queue, factory, rejection; order: core, queue, max, reject.
  • Pools newFixedThreadPool, newCachedThreadPool, newSingleThreadExecutor, newScheduledThreadPool; prefer bounded queues.
  • Shutdown shutdown() + awaitTermination; shutdownNow() interrupts; Java 19+ try-with-resources.
  • Sizing CPU-bound about cores; I/O-bound more, or virtual threads.
  • Callable/Future submit returns a Future; get throws ExecutionException; get(timeout) may throw TimeoutException.
  • CompletableFuture supplyAsync, thenApply (map), thenCompose (flatMap), thenCombine, allOf, exceptionally, handle; own executor for blocking I/O.
  • ConcurrentHashMap no nulls; atomic merge/compute/putIfAbsent; lock-free reads; weakly consistent iterators.
  • CopyOnWriteArrayList snapshot iteration, writes copy the array; for read-heavy lists.
  • BlockingQueue put/take block; ArrayBlockingQueue (bounded), LinkedBlockingQueue (set a bound), PriorityBlockingQueue, SynchronousQueue.
  • Synchronizers CountDownLatch one-shot; CyclicBarrier reusable; Semaphore permits (release in finally).
  • Deadlock four conditions: mutual exclusion, hold and wait, no preemption, circular wait. Fix: lock order, tryLock, fewer locks. Detect: jstack / jcmd Thread.print.
  • ThreadLocal per-thread value; remove() in finally with pools; scoped values are final in Java 25.
  • Virtual threads Java 21; one per task, never pooled; limit with a Semaphore; not for CPU-bound work; pinning fixed for synchronized in Java 24; Spring: spring.threads.virtual.enabled=true.
  • Thread safety order do not share, do not mutate, use concurrent classes and atomics, then lock. Spring singleton beans must be stateless.

Practice — Multithreading and concurrency

  1. Start vs run. Print Thread.currentThread().getName() from a task, first by calling run() and then start(). Done when you can explain why the two names differ and what happens if you call start() twice.
  2. The counter race, fixed two ways. Two threads each add 1 to a shared counter 1,000,000 times. First show the wrong result, then fix it with synchronized, then with AtomicInteger. Done when the broken version prints less than 2,000,000 on most runs and both fixed versions always print exactly 2,000,000. 
    import java.util.concurrent.atomic.AtomicInteger;

public class CounterRace {
    static int unsafeCount = 0;
    static int syncCount = 0;
    static final AtomicInteger atomicCount = new AtomicInteger();
    static final Object lock = new Object();

    static void runTwoThreads(Runnable task) throws InterruptedException {
        Thread a = new Thread(task);
        Thread b = new Thread(task);
        a.start(); b.start();
        a.join(); b.join();                       // wait for both to finish
    }

    public static void main(String[] args) throws InterruptedException {
        final int N = 1_000_000;

        runTwoThreads(() -> { for (int i = 0; i < N; i++) unsafeCount++; });

        runTwoThreads(() -> {
            for (int i = 0; i < N; i++) {
                synchronized (lock) { syncCount++; }
            }
        });

        runTwoThreads(() -> { for (int i = 0; i < N; i++) atomicCount.incrementAndGet(); });

        System.out.println("unsafe      : " + unsafeCount);
        System.out.println("synchronized: " + syncCount);
        System.out.println("atomic      : " + atomicCount.get());
    }
}
    unsafe      : 1374920
synchronized: 2000000
atomic      : 2000000
    Then time each version with System.nanoTime() and note which one is faster on your machine, and why a single lock of this size is cheap here.
  3. Visibility with volatile. Write a worker with a boolean running = true flag looped on by a thread, and stop it from main after one second. Run it with and without volatile (it may hang without). Done when you can explain visibility and why volatile does not fix count++.
  4. Thread pool and Future. Create a fixed pool of 4 threads, submit 10 Callables that each sleep 200 ms and return their square, collect the results through Future.get(), and shut down the pool. Done when the total time is about 600 ms (three rounds) and one task that throws shows up as an ExecutionException.
  5. Parallel calls with CompletableFuture. Simulate three services (price, stock, reviews) that each sleep 300 ms. Combine them with allOf into one result, add a timeout and a fallback for reviews. Done when the whole page takes about 300 ms and the fallback appears if you raise the review delay to 2 s.
  6. Concurrent word count. Split a text into four parts, count words in four threads into one ConcurrentHashMap with merge, then repeat with a plain HashMap and compare totals. Done when the concurrent map always matches the single-threaded count.
  7. Producer-consumer. Use an ArrayBlockingQueue of size 5 with one producer and two consumers; the producer ends with "poison pill" values. Done when all items are consumed exactly once and the program exits cleanly.
  8. Make it deadlock, then fix it. Reproduce the two-lock deadlock, take a thread dump with jstack, find the "Found one Java-level deadlock" section, and then fix it with lock ordering. Done when the fixed version finishes 1,000 opposite transfers without hanging.
  9. Virtual threads. Run 10,000 tasks that sleep one second using newVirtualThreadPerTaskExecutor and compare the time with a fixed pool of 200 threads. Add a Semaphore(100) to cap concurrency. Done when you can explain the difference in time and why you would still keep a limit.

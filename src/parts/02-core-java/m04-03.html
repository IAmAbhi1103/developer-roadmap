Iteration: Iterator, ListIterator and ConcurrentModificationException

An Iterator walks a collection one element at a time and is the only safe way to remove elements during a loop; changing a collection behind a running loop's back throws ConcurrentModificationException.

To visit every element of a collection you have four tools: an index loop (lists only), the enhanced for loop, an explicit Iterator, and forEach with a lambda. Behind the second, third and fourth sits the same idea: the Iterator.

Iterator

An Iterator<E> is a cursor that moves through a collection. Every Collection has an iterator() method (it comes from Iterable).

MethodMeaning
boolean hasNext()Is there another element?
E next()Return the next element and move forward; NoSuchElementException if none is left
void remove()Remove the element last returned by next(); IllegalStateException if next() was not called first, or if you call it twice in a row
void forEachRemaining(action)Apply a lambda to all remaining elements

The enhanced for loop is syntax sugar. The compiler rewrites it into an iterator loop, which is exactly why the same exceptions appear:

for (String name : names) {
    System.out.println(name);
}

// is compiled to roughly:
for (Iterator<String> it = names.iterator(); it.hasNext(); ) {
    String name = it.next();
    System.out.println(name);
}

Any class that implements Iterable<T> can be used in a for-each loop. You only write iterator():

import java.util.Iterator;

public class Range implements Iterable<Integer> {
    private final int from, to;                 // from inclusive, to exclusive

    public Range(int from, int to) {
        this.from = from;
        this.to = to;
    }

    @Override
    public Iterator<Integer> iterator() {
        return new Iterator<>() {
            private int next = from;
            @Override public boolean hasNext() { return next < to; }
            @Override public Integer next() { return next++; }
        };
    }

    public static void main(String[] args) {
        for (int n : new Range(1, 5)) {
            System.out.print(n + " ");
        }
    }
}
1 2 3 4

An array cannot be used as an Iterable directly, but it works in for-each because the compiler treats arrays specially.

ListIterator — both directions, with set and add

list.listIterator() returns a ListIterator, available only for lists. It can move backwards (hasPrevious, previous), report positions (nextIndex, previousIndex), and change the list while walking: set(e) replaces the last returned element and add(e) inserts at the cursor. list.listIterator(list.size()) starts at the end.

List<String> list = new ArrayList<>(List.of("a", "b", "c"));

ListIterator<String> it = list.listIterator();
while (it.hasNext()) {
    String s = it.next();
    if (s.equals("b")) {
        it.set("B");           // replace the element just returned
        it.add("b2");          // insert after it
    }
}
System.out.println(list);

ListIterator<String> back = list.listIterator(list.size());
while (back.hasPrevious()) {
    System.out.print(back.previous() + " ");     // walk backwards
}
[a, B, b2, c]
c b2 B a

Fail-fast iterators and ConcurrentModificationException

Collections such as ArrayList, HashMap and HashSet keep a counter named modCount that goes up on every structural modification (add, remove, clear — anything that changes the size; set(i, e) and changing a map value do not count). When an iterator is created it remembers the counter. On every next() it compares the two values. If they differ, someone changed the collection behind the iterator's back, and it throws ConcurrentModificationException (CME) immediately — it fails fast instead of returning garbage later.

  1. iterator() stores expectedModCount = modCount.
  2. Your loop body calls list.remove(…), so modCount increases.
  3. The next call to it.next() sees modCount != expectedModCount and throws.
  4. it.remove() removes and then updates expectedModCount, so it never triggers the exception.
List<String> names = new ArrayList<>(List.of("Asha", "Ravi", "Meera", "Kiran"));
try {
    for (String n : names) {
        if (n.equals("Ravi")) {
            names.remove(n);               // structural change inside the loop
        }
    }
} catch (ConcurrentModificationException e) {
    System.out.println("CME thrown");
}

// A surprise: remove the SECOND-TO-LAST element and nothing is thrown
List<String> three = new ArrayList<>(List.of("Asha", "Ravi", "Meera"));
for (String n : three) {
    System.out.println("visiting " + n);
    if (n.equals("Ravi")) {
        three.remove(n);
    }
}
System.out.println(three);
CME thrown
visiting Asha
visiting Ravi
[Asha, Meera]

In the second loop, after removing "Ravi" the size drops to 2 and the cursor is also 2, so hasNext() says "finished" and the check in next() never runs — "Meera" is silently skipped. This is why fail-fast is only best effort: it helps find bugs, but you must never write code that depends on the exception being thrown.

The right ways to remove while iterating

List<String> base = List.of("Asha", "Ravi", "Meera", "Kiran");

// 1. Iterator.remove() — works for every Collection
List<String> a = new ArrayList<>(base);
Iterator<String> it = a.iterator();
while (it.hasNext()) {
    if (it.next().startsWith("R")) {
        it.remove();
    }
}

// 2. removeIf(predicate) — the shortest and best (Java 8+)
List<String> b = new ArrayList<>(base);
b.removeIf(n -> n.startsWith("R"));

// 3. Build a new list with a stream
List<String> c = base.stream().filter(n -> !n.startsWith("R")).toList();

// 4. Map: remove through a view
Map<String, Integer> stock = new HashMap<>(Map.of("pen", 0, "book", 4));
stock.entrySet().removeIf(e -> e.getValue() == 0);

System.out.println(a + " " + b + " " + c + " " + stock);
[Asha, Meera, Kiran] [Asha, Meera, Kiran] [Asha, Meera, Kiran] {book=4}

A fifth way for lists only: loop by index from the end to the start, removing as you go (removing from the end never shifts the indexes you have not visited). It works but removeIf is cleaner.

Fail-safe and weakly consistent iterators

The collections in java.util.concurrent never throw CME. They work in two styles (the name "fail-safe" is common in interviews, but the Javadoc does not use it):

  • CopyOnWriteArrayList — every write copies the whole array, and an iterator walks a snapshot taken at the time the iterator was created. It never sees later changes. Good for lists that are read a lot and written rarely, such as listener lists. Its iterator does not support remove().
  • ConcurrentHashMap, ConcurrentLinkedQueue — weakly consistent iterators. They work on the live structure, may or may not show changes made after creation, and never throw CME.
PointFail-fast (ArrayList, HashMap)Snapshot / weakly consistent (concurrent classes)
Change during iterationThrows CME (best effort)No exception
Sees changes made after creationNot applicable — it throwsSnapshot: never. Weak: maybe
iterator.remove()SupportedSnapshot: not supported. Concurrent map: supported
CostNoneCopy cost on every write (CopyOnWriteArrayList)

CME is not only about threads. The example above fails with a single thread. With several threads, a plain ArrayList needs real synchronisation or a concurrent collection (Module 6).

Rule: never structurally modify a collection while iterating it, except through the iterator

Use Iterator.remove() (or ListIterator.add/set/remove), removeIf, or build a new collection. Calling list.add/list.remove/map.put/map.remove inside a for-each over the same collection is a bug even when it happens to run.

Exceptions and edge cases

  • ConcurrentModificationException — structural change during iteration, including from subList views whose parent changed, and a get inside a loop over an access-order LinkedHashMap.
  • NoSuchElementException — next() after hasNext() returned false.
  • IllegalStateException — remove() before the first next(), or twice after one next().
  • UnsupportedOperationException — remove() on the iterator of an immutable collection.
  • Changing the value of an existing map entry (entry.setValue, or map.put for an existing key) during iteration is allowed; adding or removing keys is not.

Mistake: counting on the CME

Do not write try { for … remove } catch (CME) as flow control. The "second-to-last" case shows the exception is not guaranteed. Fix the loop instead.

Tip: which loop to use

  • Just reading: for-each. Need the index or going backwards: index loop or ListIterator.
  • Removing: removeIf. Transforming into another collection: streams (Module 5).
  • Map: loop over entrySet() or use map.forEach((k, v) -> …).

Interview: "What is ConcurrentModificationException? How do you avoid it?"

  • Thrown by fail-fast iterators when the collection's modCount changes during iteration, by anything other than the iterator itself.
  • Avoid with Iterator.remove(), removeIf, a new filtered list, or a concurrent collection (CopyOnWriteArrayList, ConcurrentHashMap).
  • Fail-fast is best effort, not a guarantee (the second-to-last example); the for-each loop is an iterator in disguise.
  • Fail-fast vs fail-safe: concurrent collections give snapshot or weakly consistent iterators.

Comparable vs Comparator: sorting objects

Comparable defines the one natural order inside the class itself; Comparator defines any number of orders outside it, and the comparing/thenComparing helpers make sorting by several fields a one-liner.

Sorting needs a rule for "which of these two comes first". Java gives you two ways to supply the rule.

Comparable — the natural order

A class implements Comparable<T> and its single method int compareTo(T other). The result is negative if this comes before other, zero if they are equal in order, and positive if this comes after. String, all number wrappers, LocalDate, BigDecimal and enums already implement it, so Collections.sort(listOfStrings) just works. Sorted collections (TreeSet, TreeMap, PriorityQueue) and Arrays.sort(Object[]) use it when you give no comparator.

The compareTo contract:

  • Antisymmetry — sign(x.compareTo(y)) == -sign(y.compareTo(x)).
  • Transitivity — if x > y and y > z, then x > z.
  • Consistency — if x.compareTo(y) == 0, then x and y sort the same against every other element.
  • Recommended: consistent with equals — x.compareTo(y) == 0 exactly when x.equals(y). If not, say so in the Javadoc; BigDecimal is the known exception.
  • x.compareTo(null) must throw NullPointerException.

Comparator — any order you like, outside the class

A Comparator<T> has one abstract method, int compare(T a, T b), with the same negative/zero/positive meaning. Because it is a functional interface, you write it as a lambda. You pass it to list.sort(cmp), Collections.sort(list, cmp), Arrays.sort(array, cmp), stream.sorted(cmp), or the constructors of TreeSet, TreeMap and PriorityQueue. Use it when the class has no natural order, you cannot change the class, or you need several orders.

Sorting a list of employees

import java.util.*;

public class SortingDemo {
    record Employee(int id, String name, String dept, double salary)
            implements Comparable<Employee> {

        @Override
        public int compareTo(Employee other) {           // natural order: by id
            return Integer.compare(this.id, other.id);
        }
    }

    static String names(List<Employee> list) {
        return list.stream().map(Employee::name).toList().toString();
    }

    public static void main(String[] args) {
        List<Employee> staff = new ArrayList<>(List.of(
                new Employee(3, "Ravi", "IT", 90000),
                new Employee(1, "Asha", "HR", 65000),
                new Employee(2, "Meera", "IT", 90000),
                new Employee(4, "Kiran", "HR", 72000)));

        Collections.sort(staff);                            // uses compareTo
        System.out.println("By id:          " + names(staff));

        staff.sort(Comparator.comparing(Employee::name));
        System.out.println("By name:        " + names(staff));

        staff.sort(Comparator.comparingDouble(Employee::salary).reversed()
                .thenComparing(Employee::name));
        System.out.println("Salary desc, name: " + names(staff));

        staff.sort(Comparator.comparing(Employee::dept)
                .thenComparing(Employee::salary, Comparator.reverseOrder())
                .thenComparing(Employee::name));
        System.out.println("Dept, salary desc: " + names(staff));

        List<String> withNull = new ArrayList<>(Arrays.asList("Ravi", null, "Asha"));
        withNull.sort(Comparator.nullsFirst(Comparator.naturalOrder()));
        System.out.println(withNull);
        withNull.sort(Comparator.nullsLast(Comparator.naturalOrder()));
        System.out.println(withNull);
    }
}

The subtraction bug

A very common comparator is (a, b) -> a - b. It is wrong for large values because integer subtraction can overflow and flip the sign.

Comparator<Integer> bad = (a, b) -> a - b;
System.out.println(bad.compare(Integer.MAX_VALUE, -1));          // MAX − (−1) overflows
System.out.println(Integer.compare(Integer.MAX_VALUE, -1));      // correct

Comparator<Double> alsoBad = (a, b) -> (int) (a - b);
System.out.println(alsoBad.compare(1.2, 1.0));                   // (int) 0.2 = 0 → "equal"
-2147483648
1
0

The first comparator claims MAX_VALUE is smaller than −1. Always use Integer.compare, Double.compare, Long.compare or Comparator.comparingInt(…).

Other details worth knowing

  • Stability. List.sort, Collections.sort and Arrays.sort(Object[], cmp) use TimSort, which is stable: elements that compare equal keep their original relative order. That is why sorting by salary and then by dept is not the same as one chained sort — chaining is the safe way. Arrays.sort(int[]) uses dual-pivot quicksort; stability does not matter for primitives.
  • Lambda type inference with reversed(). Comparator.comparing(Employee::salary).reversed() compiles, but Comparator.comparing(e -> e.salary()).reversed() does not: with a lambda the compiler cannot infer the type of e through the chained call. Use a method reference, write (Employee e) -> …, or use comparing(Employee::salary, Comparator.reverseOrder()).
  • Records can share one comparator. Keep a static final Comparator<Employee> and call it from compareTo so the rule is written once.
  • Comparison is a total order. A comparator that is inconsistent (says A < B, B < C, C < A) can make TimSort throw IllegalArgumentException: Comparison method violates its general contract!.

Rule: compare must be antisymmetric, transitive and null-safe by design

Handle ties with thenComparing. If you sort by one field and put objects in a TreeSet or use them as TreeMap keys, objects that tie are treated as duplicates. Include a unique field such as the id as the last tie-breaker.

Conventions

  • Implement Comparable only when the order is obvious and unique (ids, dates, versions, money). Otherwise write Comparators.
  • Keep reusable comparators as named static final constants: BY_SALARY_DESC.
  • Prefer comparingInt/comparingDouble for primitive fields and Integer.compare over subtraction.
  • Keep compareTo consistent with equals and document it when it is not.

Exceptions and edge cases

  • ClassCastException: class X cannot be cast to class java.lang.Comparable — sorting or adding to a TreeSet objects of a class that does not implement Comparable with no comparator supplied.
  • NullPointerException — a null element or a null key (for example a null name in comparing(Employee::name)). Wrap the key comparator with nullsFirst or nullsLast.
  • String.compareTo is case-sensitive: uppercase letters sort before lowercase. Use String.CASE_INSENSITIVE_ORDER or a Collator for language-aware sorting.
  • Double.compare treats NaN as greater than everything and -0.0 as less than 0.0, unlike the < operator.

Mistake: a comparator that cannot handle ties or overflow

Returning only -1 or 1 (never 0) for equal items, or using subtraction, breaks the contract. Delegate to Integer.compare or the Comparator factory methods.

Real projects

Most sorting in a Spring Boot app is done by the database (ORDER BY, Spring Data Sort). Java comparators are used for in-memory lists, stream pipelines (sorted(Comparator.comparing(Order::createdAt).reversed())) and priority queues in schedulers.

Interview: "Comparable vs Comparator"

  • Comparable: one natural order, compareTo(T), inside the class, java.lang. Comparator: many orders, compare(T, T), outside the class, java.util.
  • Show chaining: Comparator.comparing(Employee::dept).thenComparing(Employee::salary).reversed() — and mention nullsFirst.
  • Mention the subtraction overflow bug and stable sorting (TimSort).
  • "What does a TreeSet do with two objects whose comparator returns 0?" Keeps only one — consistency with equals.

Collections and Arrays hold ready-made static algorithms, and Java gives you five different "read-only-ish" list factories whose differences — view or copy, nulls, fixed size or immutable — are a favourite source of bugs and interview questions.

All immutable collections are only shallowly immutable: if the elements are mutable objects (say StringBuilder or your own class with setters), their fields can still change. Set.of and Map.of follow the same rules as List.of (no nulls, immutable, iteration order unspecified).

Synchronized wrappers

Collections.synchronizedList(list) returns a wrapper where every method is guarded by one lock. Single calls are safe, but a loop over it is not: you must hold the lock yourself.

List<String> safe = Collections.synchronizedList(new ArrayList<>());
// ... other threads add to it ...
synchronized (safe) {                  // required while iterating
    for (String s : safe) {
        System.out.println(s);
    }
}

In new code prefer CopyOnWriteArrayList, ConcurrentHashMap and the other classes from Module 6.

Rule: know whether you hold a view or a copy

A view (unmodifiableList, subList, Arrays.asList, keySet) shares data with its source. A copy (List.copyOf, new ArrayList<>(…), stream.toList()) does not. If you return a collection from a getter, return a copy or an unmodifiable view, never your internal list.

Conventions

  • Constants and small fixed data: List.of(…), Set.of(…), Map.of(…).
  • Defensive copy in constructors and getters: this.items = List.copyOf(items);.
  • Return List.of() or Collections.emptyList(), not null, for "no results".
  • Need a mutable list from a factory: wrap it — new ArrayList<>(List.of(1, 2, 3)).

Exceptions and edge cases

  • UnsupportedOperationException — any mutating call on List.of, List.copyOf, unmodifiableList, stream.toList(), Collections.emptyList(), nCopies, or add/remove on Arrays.asList.
  • NullPointerException — List.of / Set.of / Map.of with null; also list.contains(null) on them.
  • IllegalArgumentException — duplicate elements in Set.of or duplicate keys in Map.of.
  • Collections.unmodifiableList(list) does not protect you if someone else still holds the original and changes it.
  • binarySearch on an unsorted list returns a meaningless result without any error.

Mistake: sorting or modifying a List.of

List<String> names = List.of("b", "a"); Collections.sort(names); throws UnsupportedOperationException. Copy first: new ArrayList<>(names), or use names.stream().sorted().toList().

Interview: "Arrays.asList vs List.of vs Collections.unmodifiableList"

  • Arrays.asList: fixed size, set allowed, backed by the array. List.of: truly immutable, no nulls. unmodifiableList: read-only view, still changes when the source changes. List.copyOf: immutable snapshot.
  • "How do you make a class immutable if it has a list field?" Copy in the constructor with List.copyOf and return an unmodifiable list from the getter.
  • Collections vs Collection vs Arrays; Arrays.asList(int[]) pitfall.

Choosing the right collection

Ask three questions — key-value or single values, duplicates allowed, and what order or access pattern — and the answer is almost always ArrayList, HashMap, HashSet or ArrayDeque.

Picking a collection is a design decision, not a habit. The wrong one still compiles, but it can make a loop O(n²) or lose entries silently. Use the flowchart, then check the table of everyday scenarios.

Rules of thumb

  • Default to ArrayList, HashMap, HashSet, ArrayDeque. Change only for a clear reason: order, sorting, thread safety or a measured bottleneck.
  • Repeated list.contains(x) on a big list is a red flag. It is O(n) each time; keep a HashSet next to it, or switch to one.
  • Sorted data needed once? Sort an ArrayList. Sorted data with constant inserts and queries? TreeMap/TreeSet.
  • Need both order and fast lookup? LinkedHashMap, or a list plus a map.
  • Collections of millions of primitive numbers: consider int[] — boxing makes List<Integer> about four times larger.
  • Expose the interface in public signatures (List, Map) and keep the concrete class inside.

Mistake: a List used as a lookup table

Searching a List<Customer> for an id inside a loop over orders is O(n × m). Build a Map<Long, Customer> once (Collectors.toMap) and look up in O(1).

"Average" for hash classes assumes a decent hashCode. A bad one pushes many keys into one bucket, and the cost drifts toward O(n) (O(log n) once Java turns a long bucket into a tree).

Three worked decisions

1. Duplicate emails in an uploaded file. You need to know if you have seen a value already, and the order of first appearance for the report. Answer: a LinkedHashSet, or a HashSet for the check plus an ArrayList for the order.

List<String> emails = List.of("a@x.in", "b@x.in", "a@x.in", "c@x.in", "b@x.in");
Set<String> seen = new HashSet<>();
Set<String> duplicates = new LinkedHashSet<>();
for (String e : emails) {
    if (!seen.add(e)) {              // add returns false when already present
        duplicates.add(e);
    }
}
System.out.println(duplicates);      // [a@x.in, b@x.in]

2. Orders per customer. Key-value with a list per key: Map<Long, List<Order>>, built with computeIfAbsent(id, k -> new ArrayList<>()).add(order) or Collectors.groupingBy. If the report must list customers in id order, use a TreeMap instead of a HashMap.

3. "Next ticket to serve" with priorities (VIP first). You always want the smallest or largest element next, not a full sort. That is a PriorityQueue with a comparator. A sorted list re-sorted after every insert would cost O(n log n) per ticket.

Wrong: LinkedList "because inserts are O(1)"

List<Integer> list = new LinkedList<>();
for (int i = 0; i < 100_000; i++) list.add(i);
long sum = 0;
for (int i = 0; i < list.size(); i++) {
    sum += list.get(i);          // each get walks the chain: O(n)
}

Right: ArrayList, or iterate with for-each

List<Integer> list = new ArrayList<>();
for (int i = 0; i < 100_000; i++) list.add(i);
long sum = 0;
for (int x : list) {
    sum += x;                    // O(1) per step
}

In practice ArrayList beats LinkedList in nearly every real workload, because its elements sit next to each other in memory and the CPU cache likes that. Reach for ArrayDeque when you want queue behaviour at both ends.

Runtime exceptions that point at a wrong choice

  • UnsupportedOperationException — you called add or remove on List.of(...), Collections.unmodifiableList or the fixed-size list from Arrays.asList.
  • NullPointerException — a null put into List.of, ConcurrentHashMap, ArrayDeque, PriorityQueue or a TreeMap key.
  • ConcurrentModificationException — a plain collection changed during iteration or shared across threads without protection. Switch to a concurrent class or fix the loop.
  • ClassCastException — elements put into a TreeSet or PriorityQueue that are not Comparable and no comparator was given.

Conventions

  • Return List.copyOf(list) or an unmodifiable view from a method that exposes internal state, so callers cannot damage it.
  • Size big collections when you know the size: new ArrayList<>(n). For a HashMap of n entries, HashMap.newHashMap(n) (Java 19+) picks a table size that avoids resizing.
  • If the key type is an enum, always prefer EnumMap; if the set has a few fixed flags, EnumSet.
  • Choose by the operation you repeat most, then measure only if it is truly the bottleneck.

In real projects

A Spring service typically holds a Map<Long, Customer> cache (often ConcurrentHashMap), returns List<OrderDto> from repositories, and uses a Set<String> for allowed roles. Anything heavier, such as caching with expiry or distributed queues, moves to a library (Caffeine, Redis) rather than a hand-made collection.

Interview: "Which collection would you use for…?"

  • Answer with the question you ask yourself: key-value? duplicates? order? thread-safety? Then name the class and its complexity.
  • Typical prompts: unique sorted names (TreeSet), first non-repeating character (LinkedHashMap), top-K (min-heap PriorityQueue), LRU cache (LinkedHashMap), undo stack (ArrayDeque).

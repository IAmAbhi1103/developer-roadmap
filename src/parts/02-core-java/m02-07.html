The Object class: toString, getClass and friends

Every class in Java extends java.lang.Object, so every object has toString, equals, hashCode, getClass and a few more methods; override toString in almost every class so that printing and logging show useful data.

If you write class Account { } and do not extend anything, the compiler silently adds extends Object. This is the root of the class tree (inheritance), and it is why a variable of type Object can hold anything, and why List<Object> accepts any element. The methods of Object are the minimum that all objects can do.

toString(): the text form

The default toString() returns the class name, an @ and the hash code in hexadecimal, for example Account@1b6d3586. That is useless in a log. Whenever you print an object with println, concatenate it with a string, or the debugger or a logger shows it, Java calls toString() for you.

import java.util.List;

class Plain { }

class Account {
    private final String number;
    private final String holder;
    private long balanceInPaise;

    Account(String number, String holder, long balanceInPaise) {
        this.number = number;
        this.holder = holder;
        this.balanceInPaise = balanceInPaise;
    }

    @Override
    public String toString() {
        return "Account{number=" + number + ", holder=" + holder
             + ", balance=" + balanceInPaise / 100.0 + "}";
    }
}

public class ToStringDemo {
    public static void main(String[] args) {
        System.out.println(new Plain());                       // default: Class@hash
        Account a = new Account("SB1001", "Asha", 150000);
        System.out.println(a);                                 // println calls toString()
        System.out.println("Created " + a);                    // so does concatenation
        System.out.println(List.of(a, new Account("SB1002", "Ravi", 5000)));
    }
}

The hex number after @ changes from run to run, so do not copy it into tests. Collections call toString() on each element, which is why the list prints properly.

A good toString()

  • Include the class name and the fields that identify the object: Account{number=…}. Your IDE generates this; records and Lombok's @ToString do it for you.
  • Never include secrets: passwords, tokens, card numbers, Aadhaar. toString() ends up in logs.
  • Avoid fields that point back to a parent (a bidirectional JPA relationship). Two objects printing each other end in StackOverflowError. Avoid lazy-loaded collections for the same reason (extra queries).
  • Do not use toString() for program logic or parsing. It is for humans.
  • Keep it cheap; it may be called inside a log statement.

getClass(): the exact runtime class

obj.getClass() returns a Class object that describes the real class of obj, never its declared type. It is final. You can ask it for getName(), getSimpleName(), getSuperclass() and, through reflection, its methods and fields (the basis of Spring and Hibernate). A class literal Account.class gives the same kind of object without an instance.

Object o = "text";
System.out.println(o.getClass().getName());          // java.lang.String
System.out.println(o.getClass().getSimpleName());    // String
Number n = Integer.valueOf(5);
System.out.println(n.getClass() == Integer.class);   // true: exact class
System.out.println(n instanceof Number);             // true: any subtype counts
System.out.println(new int[0].getClass().getSimpleName());   // int[]

The difference between getClass() == X.class (exact) and instanceof (any subtype) is the key to writing a correct equals() (see the table in casting and instanceof).

Edge cases

  • String.valueOf(obj) and "" + obj print "null" for a null reference, but obj.toString() throws NullPointerException. Objects.toString(obj) is the null-safe call.
  • On an interface-typed variable you can always call Object's methods, because every interface type is also an Object.
  • An array's toString() is the default ([I@6d06d69c); use Arrays.toString(arr) or Arrays.deepToString.
  • getClass() of a Spring or Hibernate proxy returns the generated proxy class, not your class. This breaks getClass()-based equality on JPA entities.

Interview: Object class questions

  • Which class is the parent of all classes? java.lang.Object, even if you write no extends. An interface type has none, but its objects do.
  • Name the methods of Object. toString, equals, hashCode, getClass, clone, finalize, wait, notify, notifyAll.
  • What does the default toString() print? ClassName@hexHashCode.
  • What does getClass() return, and can you override it? The exact runtime Class; no, it is final.

equals() and hashCode(): the contracts and a correct implementation

Override equals when two objects with the same data should count as equal, follow its five rules, and always override hashCode too so that equal objects return the same number; otherwise HashMap and HashSet silently misbehave.

The default Object.equals() is the same as ==: two references are equal only if they point to the very same object. That is right for a Thread or a database connection, but wrong for a value such as money, a PAN number or an email address. Two Money(100, "INR") objects should be equal. So value classes override equals. The collections framework then relies on that (Module 4; internals in Module 7).

== versus equals()

String a = new String("hi");
String b = new String("hi");
System.out.println(a == b);          // false: two different objects
System.out.println(a.equals(b));     // true: same characters

Integer x = 127, y = 127;
System.out.println(x == y);          // true: small values come from a cache
Integer p = 1000, q = 1000;
System.out.println(p == q);          // false: two objects
System.out.println(p.equals(q));     // true

For objects, == compares identity (the reference), and equals() compares meaning, if the class defines it. For primitives only == exists. Use equals() for objects, always.

The equals contract

The documentation of Object.equals lists five rules for non-null references:

  1. Reflexive: x.equals(x) is true.
  2. Symmetric: x.equals(y) is true exactly when y.equals(x) is.
  3. Transitive: if x.equals(y) and y.equals(z), then x.equals(z).
  4. Consistent: repeated calls give the same answer while the objects are unchanged.
  5. Non-null: x.equals(null) is false (and never throws).

The hashCode contract

  • Called twice on an unchanged object in one run, it returns the same int.
  • If a.equals(b) is true, then a.hashCode() == b.hashCode() must be true. This is the rule that matters.
  • Unequal objects may share a hash code (a collision), but fewer collisions mean a faster map.

Rule: override equals and hashCode together

A HashMap first uses hashCode() to pick a bucket, then equals() to find the right key inside it. If equal objects have different hash codes, they land in different buckets and the map never even compares them.

What goes wrong without hashCode

import java.util.*;

class Pan {
    final String number;
    Pan(String number) { this.number = number; }
    @Override public boolean equals(Object o) {          // equals overridden...
        return o instanceof Pan p && number.equals(p.number);
    }
    // ...but no hashCode(): the identity hash from Object is used
}

public class Broken {
    public static void main(String[] args) {
        Set<Pan> set = new HashSet<>();
        set.add(new Pan("ABCDE1234F"));
        set.add(new Pan("ABCDE1234F"));

        System.out.println(set.contains(new Pan("ABCDE1234F")));      // expected true

Each Pan gets its own identity-based hash code, so the two equal objects usually go to different buckets. "Usually" is the danger: sometimes they land in the same bucket and the bug disappears, which makes it hard to find.

A correct implementation

Use the same fields in both methods. Compare primitives with == (use Double.compare for double), objects with Objects.equals (null-safe), and build the hash with Objects.hash.

import java.util.*;

public final class Customer {
    private final long id;
    private final String email;                  // part of equality
    private String nickname;                     // NOT part of equality

    public Customer(long id, String email, String nickname) {
        this.id = id;
        this.email = email;
        this.nickname = nickname;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                              // fast path, reflexive
        if (o == null || getClass() != o.getClass()) return false;   // null and type check
        Customer other = (Customer) o;
        return id == other.id && Objects.equals(email, other.email);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, email);                          // same fields as equals
    }

    @Override public String toString() { return "Customer{id=" + id + ", email=" + email + "}"; }

    public static void main(String[] args) {
        Customer a = new Customer(1, "asha@example.com", "A");
        Customer b = new Customer(1, "asha@example.com", "Ash");
        Set<Customer> set = new HashSet<>(List.of(a));
        System.out.println(a.equals(b) + " " + (a.hashCode() == b.hashCode()));
        System.out.println(set.contains(b));
    }
}
true true
true

The five-step recipe is: same reference, then null and class check, then cast, then compare the significant fields. Java 16+ lets you shorten the check with pattern matching: return o instanceof Customer c && id == c.id && Objects.equals(email, c.email);. A record generates all three methods for you (records).

instanceof or getClass() inside equals?

With getClass() a subclass instance never equals a parent instance, so symmetry and transitivity always hold. With instanceof a ColorPoint and a Point can be "equal" one way and not the other, which breaks symmetry. The safe choices are: use getClass(), or make the class final and use instanceof. Use instanceof with a non-final class only when the parent class defines equality for the whole hierarchy (as AbstractList does for all lists). Know that Hibernate proxies can make the getClass() approach fail for JPA entities, and a common choice there is equality on the id with a constant hashCode; the pitfalls are covered in the Spring Data JPA notes.

Mutable keys

Customer c = new Customer(1, "asha@example.com", "A");
Set<List<String>> sets = new HashSet<>();
List<String> key = new ArrayList<>(List.of("a"));
sets.add(key);
key.add("b");                                  // hash code changes after insertion
System.out.println(sets.contains(key));        // false: wrong bucket now
System.out.println(sets.size());               // 1, the entry is stuck in the old bucket

If a field used in hashCode changes while the object sits in a HashSet or is a HashMap key, the object is lost. Use immutable keys: String, Integer, records, or your own immutable classes (immutability).

Edge cases

  • Float and double fields. Compare with Double.compare(a, b) == 0, not ==, to handle NaN and -0.0. Objects.hash boxes the primitive, which is fine.
  • Arrays in fields. Use Arrays.equals and Arrays.hashCode; Objects.equals on arrays compares references.
  • Constant hashCode. return 42; is legal but turns a map into a linked list or tree. Never do it for performance-sensitive types.
  • Consistency with compareTo. For sorted sets and maps, compareTo should return 0 exactly when equals is true, or TreeSet and HashSet will disagree.
  • Overload instead of override. boolean equals(Customer c) is an overload; collections call equals(Object) and ignore it. @Override catches this at compile time.
  • hashCode() values are not stable between JVM runs for objects with identity hashes; never store them in files or databases.

Mistakes to avoid

Wrong: overload, and compare floats with ==

public boolean equals(Customer c) {        // overload, not override
    return this.id == c.id;                // also NPE on null
}

Right

@Override
public boolean equals(Object o) {
    return o instanceof Customer c && id == c.id;
}
@Override public int hashCode() { return Long.hashCode(id); }
  • Different fields in equals and hashCode (the hash uses a field that equals ignores).
  • Using a mutable or generated field (a database id that is null before saving) as the only equality basis.
  • Throwing an exception from equals on null or on a different type.

Tip: let tools write it

Use the IDE generator (it uses Objects.equals and Objects.hash), a record, or Lombok's @EqualsAndHashCode. Then write one test that adds two equal objects to a HashSet and expects size 1. For tests there is also the EqualsVerifier library.

Interview: the favourites

  • What is the contract between equals and hashCode? Equal objects must have equal hash codes. The reverse need not hold.
  • What if you override equals but not hashCode? Hash collections fail to find equal objects. Show the HashSet duplicate example.
  • What if two different objects have the same hash code? A collision. The map falls back to equals() to tell them apart; correctness is kept, only speed suffers.
  • == vs equals? Identity vs logical equality; strings, wrappers and the Integer cache as examples.
  • Can a key change inside a HashMap? Not safely; make keys immutable.

clone(), shallow vs deep copy, and copy constructors

A copy can be shallow (the new object shares the inner objects with the original) or deep (everything is duplicated); Object.clone() is awkward and easy to get wrong, so use a copy constructor, a static factory or an immutable design instead.

Assigning b = a copies only the reference; both variables then point at one object. To get an independent object, you need a real copy. The question is how deep the copy goes.

Shallow versus deep copy

A shallow copy makes a new outer object, but its fields still point to the same inner objects as the original. A deep copy also duplicates the inner objects, recursively. Immutable inner objects (String, Integer, LocalDate) need no duplication.

clone() and the Cloneable interface

Object.clone() is protected and makes a field-by-field (shallow) copy, without calling any constructor. To use it you must: implement the marker interface Cloneable (otherwise CloneNotSupportedException is thrown), override clone() as public and call super.clone(). You may narrow the return type (covariant return, overriding).

import java.util.*;

class Playlist implements Cloneable {
    String name;
    List<String> songs = new ArrayList<>();

    Playlist(String name) { this.name = name; }

    @Override
    public Playlist clone() {
        try {
            Playlist copy = (Playlist) super.clone();      // shallow: songs is shared
            copy.songs = new ArrayList<>(this.songs);      // fix it by hand: deep-ish copy
            return copy;
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);                   // cannot happen: we are Cloneable
        }
    }
}

public class CloneDemo {
    public static void main(String[] args) {
        Playlist a = new Playlist("Morning");
        a.songs.add("Kun Faya Kun");
        Playlist b = a.clone();
        b.songs.add("Tum Hi Ho");
        b.name = "Evening";
        System.out.println(a.name + " " + a.songs);
        System.out.println(b.name + " " + b.songs);
    }
}
Morning [Kun Faya Kun]
Evening [Kun Faya Kun, Tum Hi Ho]

If you delete the line that copies songs, adding to b also changes a. And that is only one level; if the songs were mutable objects, you would have to clone them too.

Why clone() is disliked

  • The Cloneable interface has no clone() method; it just flips a switch inside Object.clone(). This is a design mistake that Java keeps for compatibility.
  • It creates objects without running a constructor, so invariants set by constructors are bypassed.
  • It is shallow by default and every mutable field needs manual care.
  • It throws a checked exception you can never really get, and it does not work with final fields that need a new value.
  • Subclasses must also remember to call super.clone() correctly.

One accepted use: array.clone() is a fast, correct shallow copy of an array (int[] copy = arr.clone();). For arrays of mutable objects remember it is shallow.

Better: copy constructor and static factory

A copy constructor takes an object of the same class and builds a new one. It is plain Java: it runs your validation, works with final fields, and makes it obvious what is copied deeply. A static factory such as Playlist.copyOf(other) does the same with a clearer name, like List.copyOf.

import java.util.*;

class Address {
    private String city;
    Address(String city) { this.city = city; }
    Address(Address other) { this.city = other.city; }        // copy constructor
    void setCity(String c) { this.city = c; }
    @Override public String toString() { return city; }
}

class Person {
    private final String name;
    private final Address address;                            // mutable inner object
    private final List<String> phones;

    Person(String name, Address address, List<String> phones) {
        this.name = name;
        this.address = new Address(address);                  // defensive copy in
        this.phones = new ArrayList<>(phones);
    }

    Person(Person other) {                                    // deep copy constructor
        this(other.name, other.address, other.phones);        // reuses the defensive copies
    }

    Address getAddress() { return new Address(address); }    // defensive copy out
    @Override public String toString() { return name + " " + address + " " + phones; }
}

public class Copying {
    public static void main(String[] args) {
        Address home = new Address("Pune");
        Person asha = new Person("Asha", home, List.of("98100"));
        Person copy = new Person(asha);
        home.setCity("Delhi");                 // does not affect either person
        asha.getAddress().setCity("Goa");      // nor this
        System.out.println(asha);
        System.out.println(copy);
    }
}
Asha Pune [98100]
Asha Pune [98100]

The same defensive-copy habit protects encapsulation (encapsulation). Besides these, other copy routes exist: serialization (slow and fragile), JSON mapping through Jackson (convenient for tests), the new ArrayList<>(other) constructors of collections, List.copyOf (an unmodifiable copy; the elements are not copied), and libraries such as MapStruct for DTO copies. Best of all is to share immutable objects so that no copy is needed (immutability).

Edge cases

  • Collection copy constructors and List.copyOf are shallow: the new list holds the same element objects.
  • Arrays.copyOf and array.clone() are shallow for object arrays; a 2D array needs a loop (or clone per row).
  • A cloned HashMap or ArrayList (they implement clone()) is also a shallow copy.
  • Records cannot be cloned in the usual sense, but they are immutable; copy a record by building a new one, for example new Point(p.x(), 5).
  • Calling clone() on a class that is not Cloneable gives CloneNotSupportedException at run time.

Convention

Prefer: immutable class, then copy constructor or static factory, then clone() only for arrays or when a library demands it. This is the advice of Effective Java and of most style guides.

Interview: copy questions

  • Shallow vs deep copy? Shared inner objects vs fully duplicated ones. Draw the two diagrams.
  • Why is clone() considered broken? Marker interface without the method, bypasses constructors, shallow by default, checked exception.
  • What do you use instead? Copy constructor, static factory, or immutable objects.
  • What does Cloneable do? It only allows Object.clone() to work; without it you get CloneNotSupportedException.

Composition vs inheritance: has-a, is-a and delegation

Inheritance models "is-a" and binds a child tightly to its parent's internals; composition models "has-a" by holding another object and forwarding calls to it, and is usually the safer, more flexible way to reuse code.

Beginners often use extends whenever two classes share code. That couples the child to every detail of the parent: when the parent changes, children can break. The other tool is composition: a class keeps a field that refers to another object and uses it. The classic advice from Effective Java and the Gang of Four book is "favor composition over inheritance".

Association, aggregation and composition

"Has-a" relationships come in three strengths. UML (the common diagram language) names them like this:

Association
One object knows or uses another: a Customer places Orders; a Teacher teaches Students. Both live on their own. Drawn as a plain line or arrow.
Aggregation
A weak "whole-part": a Department has Employees, but an employee exists without the department and may move to another. Hollow diamond.
Composition
A strong "whole-part": a House has Rooms; the rooms are created by and die with the house, and belong to no other. Filled diamond.

In code the difference is about lifetime and ownership. In composition the whole creates the parts and does not hand them out. In aggregation the parts are passed in and may live on.

import java.util.*;

class Room {
    final String name;
    Room(String name) { this.name = name; }
}

class House {                                           // composition
    private final List<Room> rooms = new ArrayList<>();
    House(String... roomNames) {
        for (String n : roomNames) rooms.add(new Room(n));   // House creates and owns the rooms
    }
    int roomCount() { return rooms.size(); }
}

class Employee { final String name; Employee(String n) { name = n; } }

class Department {                                      // aggregation
    private final List<Employee> staff = new ArrayList<>();
    void add(Employee e) { staff.add(e); }              // employees come from outside
    int size() { return staff.size(); }
}

public class Relations {
    public static void main(String[] args) {
        System.out.println(new House("Hall", "Kitchen").roomCount());
        Employee asha = new Employee("Asha");
        Department hr = new Department(), it = new Department();
        hr.add(asha);
        it.add(asha);                                   // the same employee in two departments
        System.out.println(hr.size() + " " + it.size());
    }
}

The fragile base class problem

Inheritance breaks encapsulation: a subclass depends on how the parent works, not only on what it promises. Here is the well-known example. We want a HashSet that counts how many elements were ever added.

import java.util.*;

class CountingSet<E> extends HashSet<E> {          // inheritance
    private int added = 0;

    @Override public boolean add(E e) { added++; return super.add(e); }

    @Override public boolean addAll(Collection<? extends E> c) {
        added += c.size();
        return super.addAll(c);          // HashSet.addAll calls add() for each element!
    }
    int getAdded() { return added; }
}

public class CountingDemo {
    public static void main(String[] args) {
        CountingSet<String> s = new CountingSet<>();
        s.addAll(List.of("a", "b", "c"));
        System.out.println(s.getAdded());     // we expect 3
    }
}
6

The parent's addAll internally calls add for each element, which the subclass has also overridden, so each element is counted twice. If a future JDK changed addAll not to call add, the answer would change again. The child is at the mercy of the parent's private implementation. That is the fragile base class problem. Other costs of inheritance: the child exposes the parent's whole API (a CountingSet also offers remove and clear); the relation is fixed at compile time; and Java allows one parent only.

The fix: composition and delegation

Hold a set as a private field and delegate (forward) the calls to it. You decide which methods to expose, and the wrapped set can be any Set.

import java.util.*;

class CountingSet2<E> {
    private final Set<E> inner;                     // has-a, typed by the interface
    private int added = 0;

    CountingSet2(Set<E> inner) { this.inner = inner; }

    boolean add(E e) { added++; return inner.add(e); }

    boolean addAll(Collection<? extends E> c) {
        boolean changed = false;
        for (E e : c) changed |= add(e);              // our own loop: no hidden double count
        return changed;
    }
    int getAdded() { return added; }
    int size() { return inner.size(); }
}

public class CountingDemo2 {
    public static void main(String[] args) {
        CountingSet2<String> s = new CountingSet2<>(new TreeSet<>());   // swap to LinkedHashSet freely
        s.addAll(List.of("a", "b", "c"));
        System.out.println(s.getAdded() + " " + s.size());
    }
}

A second refactoring: behaviour as a component

Suppose you model vehicles and start with Car extends Engine because a car "uses" an engine. A car is not an engine. Worse, an electric car now inherits petrol-engine methods. Make the engine a component:

Wrong: inheritance for reuse

class Engine { void start() { /* ... */ } }
class Car extends Engine { }          // "a car is an engine"?

Right: composition and an interface

interface Engine { void start(); }
class PetrolEngine implements Engine { public void start() { /* ... */ } }
class ElectricMotor implements Engine { public void start() { /* ... */ } }

class Car {
    private final Engine engine;       // chosen at construction time
    Car(Engine engine) { this.engine = engine; }
    void start() { engine.start(); }   // delegation
}

Now you can build a new Car(new ElectricMotor()) or swap the engine in a test. This is the idea behind the Strategy pattern and behind dependency injection in Spring: an OrderService is composed of a repository and a payment client, it does not extend them (abstraction, Design patterns).

When inheritance is still the right tool

  • There is a true is-a relation that passes the Liskov test: a child can be used wherever the parent is expected, without surprises (a Square that extends a mutable Rectangle fails this).
  • The parent was designed and documented for extension (AbstractList, abstract classes with Template Methods).
  • Both classes are in the same package or project, so you control both.
  • Otherwise, make classes final or use interfaces plus composition. "Design and document for inheritance, or else prohibit it."

Mistakes to avoid

  • Extending a class only to reuse one method (Stack extends Vector in the JDK is the famous regret: a stack that lets you insert in the middle).
  • Making a domain object extend a utility or framework class, such as class Order extends ArrayList<Item>. Keep a List<Item> field instead.
  • Deep hierarchies of more than two or three levels. They are hard to follow and to change.
  • Aggregation where a part is shared and mutated by many owners without clear ownership.

  • Explain the three has-a levels (association, aggregation, composition) with ownership and lifetime.
  • Show the fragile base class with the HashSet.addAll counter.
  • Name patterns that use composition: Strategy, Decorator, Adapter; and Spring DI.

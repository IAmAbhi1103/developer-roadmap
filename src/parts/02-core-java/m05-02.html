Method references: the four kinds

A method reference such as String::toUpperCase is a shorter way to write a lambda that does nothing except call one existing method; there are four kinds — static, bound instance, unbound instance and constructor.

Many lambdas only forward their arguments to a method that already exists: s -> s.toUpperCase(), x -> System.out.println(x), () -> new ArrayList<>(). A method reference names that method directly with the :: operator. It compiles to the same thing as the lambda, but it is shorter and says what is being called instead of how the arguments are passed.

The four kinds

KindSyntaxExampleSame as the lambda
1. Static methodClassName::staticMethodInteger::parseInts -> Integer.parseInt(s)
2. Bound instance method (a specific object)object::methodSystem.out::printlnx -> System.out.println(x)
3. Unbound instance method (any object of a type)ClassName::methodString::toUpperCases -> s.toUpperCase()
4. ConstructorClassName::newArrayList::new() -> new ArrayList<>()

Bound vs unbound — the one that confuses people

In a bound reference, the object is fixed when you write the reference: System.out::println always prints to that one PrintStream. All lambda parameters become method arguments.

In an unbound reference, you name a type, not an object. The first lambda parameter becomes the object the method is called on, and the remaining parameters become arguments:

  • String::toUpperCase as a Function<String, String> → s -> s.toUpperCase()
  • String::compareToIgnoreCase as a Comparator<String> → (a, b) -> a.compareToIgnoreCase(b)
  • String::startsWith as a BiFunction<String, String, Boolean> → (s, p) -> s.startsWith(p)

All four in one program

import java.util.*;
import java.util.function.*;
import java.util.stream.*;

public class MethodRefs {
    record Employee(String name, String dept) {
        Employee(String name) {            // second constructor
            this(name, "UNASSIGNED");
        }
    }

    public static void main(String[] args) {
        // 1. Static method
        Function<String, Integer> parse = Integer::parseInt;
        System.out.println(parse.apply("42") + 1);

        // 2. Bound instance method: the receiver (System.out) is fixed
        Consumer<String> printer = System.out::println;
        printer.accept("bound to System.out");

        // 3. Unbound instance method: the first argument is the receiver
        Function<String, String> upper = String::toUpperCase;
        System.out.println(upper.apply("upi"));

        List<String> cities = new ArrayList<>(List.of("pune", "Agra", "delhi", "Bhopal"));
        // same as (a, b) -> a.compareToIgnoreCase(b)
        cities.sort(String::compareToIgnoreCase);
        System.out.println(cities);

        // 4. Constructor: the target type picks the constructor
        Supplier<List<String>> listMaker = ArrayList::new;             // no-arg
        Function<String, Employee> newEmp = Employee::new;             // (String)
        BiFunction<String, String, Employee> newEmp2 = Employee::new;  // (String, String)
        IntFunction<int[]> newArray = int[]::new;                      // new int[n]
        System.out.println(listMaker.get().size() + " " + newEmp.apply("Ravi") + " "
                + newEmp2.apply("Asha", "HR") + " " + newArray.apply(3).length);

        // Typical stream usage
        String[] arr = Stream.of("a", "b").toArray(String[]::new);
        List<Employee> emps = Stream.of("Kiran", "Meera").map(Employee::new).toList();
        TreeSet<String> set = Stream.of("b", "a", "b")
                .collect(Collectors.toCollection(TreeSet::new));
        List<String> noNulls = Stream.of("x", null, "y")
                .filter(Objects::nonNull)
                .toList();

        System.out.println(arr.length + " " + emps + " " + set + " " + noNulls);
    }
}

How the compiler matches a method reference

  1. It looks at the target functional interface and its one method — for Function<String, Integer> that is Integer apply(String).
  2. For ClassName::name it searches for a static method name(String) and for an instance method name() called on the first parameter.
  3. Overloads are resolved by the parameter types, exactly like a normal call. System.out::println works for Consumer<String> and Consumer<Integer> because the right println overload is picked each time.
  4. If both a static and an instance method fit, the reference is ambiguous and does not compile.
Function<Integer, String> f = Integer::toString;   // toString(int) or toString()?
error: incompatible types: invalid method reference
    reference to toString is ambiguous
      both method toString(int) in Integer and method toString() in Integer match

Fix it with a lambda that says what you mean: i -> Integer.toString(i), or use String::valueOf.

this:: and super::

Inside an instance method you can reference your own methods with this::validate and the parent's version with super::describe. orders.forEach(this::process) is a common pattern in Spring services: the loop body lives in a named, testable method.

Edge case: a bound receiver is evaluated immediately

For object::method, Java evaluates object when the reference is created, not when it runs. Two visible effects:

  • If object is null, you get a NullPointerException at creation time. The equivalent lambda () -> object.method() fails only when it is called.
  • The variable does not need to be effectively final, because only its current value is captured. After String s = "abc"; Supplier<Integer> len = s::length; s = "abcdef";, len.get() returns 3.
Order order = null;
Runnable lambda = () -> order.confirm();   // created fine
Runnable ref = order::confirm;             // NullPointerException right here
lambda.run();                              // the lambda throws only now

Rule: the referenced method must fit the functional method

The number and types of parameters must match (for an unbound reference, counting the receiver as the first parameter), and the return type must be compatible. A method returning a value may be used where void is expected (the value is discarded), but not the other way round.

Conventions: when to use a method reference

  • Use one when the lambda only forwards its parameters: prefer map(Employee::name) over map(e -> e.name()).
  • Keep the lambda when it does more than one call or passes extra values: map(e -> e.salary() * 12) has no method-reference form.
  • For chains of getters, split them: .map(User::address).map(Address::city) reads better than one long lambda.
  • Do not force it. If Foo::bar hides which argument goes where, the lambda is clearer.

Mistake: calling a default method directly on a method reference

String::trim.andThen(...) does not compile ("method reference not expected here"), and var f = String::trim; fails with "method reference needs an explicit target-type". A method reference has no type until it is assigned or passed. Assign it to a typed variable first: Function<String, String> trim = String::trim;.

Interview: "What are the types of method references?"

  • Four kinds: static (Integer::parseInt), bound instance (System.out::println), unbound instance (String::length), constructor (ArrayList::new, int[]::new).
  • Give the lambda equivalent of each — interviewers often ask for it.
  • Unbound: the first parameter becomes the receiver, which is why String::compareToIgnoreCase works as a Comparator<String>.
  • The target type decides which overload or constructor is used.
  • Bonus point: a bound receiver is evaluated when the reference is created (null check happens then).

What a stream is: pipeline, laziness and sources

A stream is a one-time pipeline over a source of elements: a chain of lazy intermediate operations followed by one terminal operation, which triggers all the work and produces the result.

A stream (java.util.stream.Stream<T>) is a sequence of elements that you process with a chain of operations. It is not a data structure: it stores nothing. It pulls elements from a source — a collection, an array, a file, a generator — and pushes them through the operations one by one. It never modifies the source; a filter on a stream of a list leaves the list untouched.

The pipeline: source → intermediate → terminal

Source
Where elements come from: list.stream(), Arrays.stream(arr), Files.lines(path).
Intermediate operation
Returns a new Stream and does no work yet: filter, map, sorted, distinct, limit. You can chain any number of them.
Terminal operation
Produces a result or a side effect and ends the stream: collect, toList, forEach, count, reduce, findFirst. A pipeline has exactly one, at the end.

Laziness and short-circuiting — see it with peek

Lazy means intermediate operations only record what to do. The work starts when the terminal operation asks for elements. The stream then processes elements one at a time, through the whole chain ("vertically"), not one operation at a time over the whole list. Some operations are short-circuiting: they can finish without looking at every element (findFirst, anyMatch, limit). peek(action) lets you watch elements pass by.

List<String> names = List.of("Asha", "Bharat", "Chirag", "Deepa", "Esha");

Stream<String> pipeline = names.stream()
        .peek(n -> System.out.println("source: " + n))
        .filter(n -> n.length() > 4)
        .peek(n -> System.out.println("  passed filter: " + n))
        .map(String::toUpperCase);

System.out.println("Pipeline built, nothing processed yet");
Optional<String> first = pipeline.findFirst();       // terminal: work starts here
System.out.println("Result: " + first.get());
Pipeline built, nothing processed yet
source: Asha
source: Bharat
  passed filter: Bharat
Result: BHARAT

Three things to notice. Nothing printed before findFirst(). "Asha" failed the filter and went no further. And after "Bharat" produced a result, the stream stopped — "Chirag", "Deepa" and "Esha" were never read. With a million names, that saves a million checks.

Stateful operations break the one-at-a-time flow

Most intermediate operations are stateless: each element is handled on its own (filter, map). Stateful operations need to remember other elements. sorted() cannot emit the smallest element until it has seen all of them; distinct() must remember what it has already seen.

Stream.of("c", "a", "b")
        .peek(s -> System.out.println("before sorted: " + s))
        .sorted()
        .forEach(s -> System.out.println("after sorted:  " + s));
before sorted: c
before sorted: a
before sorted: b
after sorted:  a
after sorted:  b
after sorted:  c

This is why sorted() on an infinite stream never finishes, and why it uses memory proportional to the number of elements.

A stream can be used only once

Stream<String> once = names.stream();
System.out.println(once.count());   // 5
once.count();                       // throws
5
Exception in thread "main" java.lang.IllegalStateException: stream has already been operated upon or closed

A terminal operation consumes the stream. If you need the data twice, keep the source (the list) and call stream() again, or use a Supplier<Stream<T>>. Calling two intermediate operations on the same stream object (branching) fails the same way.

Kinds of streams and encounter order

There are four stream types: Stream<T> for objects, and IntStream, LongStream, DoubleStream for primitives (with extras like sum() and average()). A stream from a List, an array or a range has an encounter order, and operations keep it. A stream from a HashSet has no defined order, so findFirst() on it can return any element.

Rules

  • Exactly one terminal operation per stream; after it, the stream is closed.
  • Without a terminal operation, nothing runs — not even peek or map.
  • Do not modify the source while the stream runs (no list.add inside the pipeline).
  • Close streams backed by I/O (Files.lines, Files.list, Files.walk) with try-with-resources. Streams over collections do not need closing.

Conventions

  • Put each operation on its own line, aligned under .stream(). Diffs and stack traces become readable.
  • Return collections from methods, not streams, unless the caller clearly needs lazy processing. A returned stream can be consumed only once.
  • Use peek only for debugging; never for logic.

Edge cases

  • Stream.of(intArray) gives a stream with one element — the array itself (Stream<int[]>). Stream.of(new int[]{1, 2, 3}).count() is 1. Use Arrays.stream(intArray) or IntStream.of(1, 2, 3).
  • An infinite stream without limit, takeWhile or a short-circuiting terminal never ends; with sorted() or collect it eventually throws OutOfMemoryError.
  • Files.lines throws UncheckedIOException during processing if a line cannot be decoded (for example, wrong charset); the file-not-found IOException is thrown when you open it.

Mistake: keeping a stream to use it twice

Wrong: IllegalStateException on the second use

Stream<Order> paid = orders.stream()
        .filter(Order::isPaid);
long count = paid.count();
List<Order> list = paid.toList();   // throws

Right: collect once, then reuse the list

List<Order> paid = orders.stream()
        .filter(Order::isPaid)
        .toList();
long count = paid.size();

Interview: "What is a stream? Intermediate vs terminal? What is lazy evaluation?"

  • A stream is a pipeline over a source; it stores nothing and does not change the source.
  • Intermediate operations return a stream and are lazy; terminal operations produce a result and trigger processing.
  • Elements flow one at a time through the whole chain; short-circuiting operations stop early. Show the peek demo if you can.
  • Stateful operations (sorted, distinct) must see many or all elements.
  • Streams are single-use: reuse throws IllegalStateException.

Intermediate operations: filter, map, flatMap, sorted and friends

Intermediate operations turn one stream into another, lazily: filter keeps elements, map transforms them, flatMap flattens nested data, sorted and distinct reorder or deduplicate, and limit, skip, takeWhile and dropWhile cut the stream.

map vs flatMap

map is one-to-one: each element becomes exactly one new element. When each element holds a collection, map gives you a stream of collections. flatMap is one-to-many: the function returns a stream for each element, and flatMap joins ("flattens") all of them into a single stream.

List<List<String>> nested = orders.stream()
        .map(Order::items)                         // Stream<List<String>>
        .toList();
System.out.println(nested);

List<String> allItems = orders.stream()
        .flatMap(o -> o.items().stream())          // Stream<String>
        .toList();
System.out.println(allItems);

List<String> uniqueItems = orders.stream()
        .flatMap(o -> o.items().stream())
        .distinct()
        .sorted()
        .toList();
System.out.println(uniqueItems);

List<String> lines = List.of("upi is fast", "cards are common");
System.out.println(lines.stream()
        .flatMap(line -> Arrays.stream(line.split(" ")))   // sentences → words
        .toList());

List<Employee> emps = List.of(
        new Employee("Ravi", "IT", 90000, 31),
        new Employee("Asha", "HR", 60000, 28),
        new Employee("Kiran", "IT", 90000, 26),
        new Employee("Meera", "IT", 120000, 35),
        new Employee("John", "HR", 75000, 40));

// Salary high → low, then name A → Z for equal salaries
System.out.println(emps.stream()
        .sorted(Comparator.comparingInt(Employee::salary).reversed()
                .thenComparing(Employee::name))
        .map(e -> e.name() + ":" + e.salary())
        .toList());

// Department A → Z, and inside each department salary high → low
System.out.println(emps.stream()
        .sorted(Comparator.comparing(Employee::dept)
                .thenComparing(Employee::salary, Comparator.reverseOrder()))
        .map(e -> e.dept() + "/" + e.name())
        .toList());
[Meera:120000, Kiran:90000, Ravi:90000, John:75000, Asha:60000]
[HR/John, HR/Asha, IT/Meera, IT/Ravi, IT/Kiran]

In the second result, Ravi and Kiran both earn 90,000, and they stay in their original order. For ordered streams, sorted is stable: equal elements keep their encounter order.

limit and skip — pagination

int page = 1, size = 2;                   // page index starts at 0
System.out.println(emps.stream()
        .sorted(Comparator.comparing(Employee::name))   // Asha, John, Kiran, Meera, Ravi
        .skip((long) page * size)
        .limit(size)
        .map(Employee::name)
        .toList());                       // [Kiran, Meera]

Good for in-memory lists. For database data, paginate in SQL (LIMIT/OFFSET or Spring Data's Pageable) instead of loading everything and skipping in Java.

takeWhile and dropWhile vs filter

List<Integer> nums = List.of(1, 2, 3, 10, 4, 5);
System.out.println(nums.stream().takeWhile(n -> n < 5).toList());   // [1, 2, 3]
System.out.println(nums.stream().filter(n -> n < 5).toList());      // [1, 2, 3, 4]
System.out.println(nums.stream().dropWhile(n -> n < 5).toList());   // [10, 4, 5]

takeWhile stops at the first element that fails — 4 is never reached. filter checks every element. Use takeWhile on data that is already sorted or ordered by the condition (log lines by time, prices ascending), where stopping early is both correct and faster.

Primitive streams: mapToInt, boxed, mapToObj

int total = emps.stream().mapToInt(Employee::salary).sum();                 // 435000
double avg = emps.stream()
        .mapToDouble(Employee::salary)
        .average()
        .getAsDouble();                                                      // 87000.0

List<Integer> squares = IntStream.rangeClosed(1, 5)
        .map(n -> n * n)       // IntStream → IntStream
        .boxed()               // IntStream → Stream<Integer>
        .toList();             // [1, 4, 9, 16, 25]

List<String> seats = IntStream.range(0, 3)
        .mapToObj(i -> "Seat-" + i)
        .toList();             // [Seat-0, Seat-1, Seat-2]

Object streams have no sum(); convert with mapToInt first. Primitive streams cannot be collected with Collectors directly; convert back with boxed() or mapToObj.

Version note: mapMulti (Java 16)

mapMulti((element, sink) -> ...) is an alternative to flatMap: instead of returning a stream, you push zero or more results into sink. It avoids creating many small streams. orders.stream().<String>mapMulti((o, sink) -> o.items().forEach(sink)) gives the same 6 items as the flatMap example. flatMap remains the common, readable choice.

Rules

  • The function given to map must return a value. map(s -> System.out.println(s)) does not compile, because println returns void.
  • The function given to flatMap must return a Stream, not a List — write o.items().stream().
  • sorted() without a comparator requires Comparable elements.

Edge cases and runtime exceptions

  • sorted() on elements that are not Comparable compiles, but throws ClassCastException (… cannot be cast to class java.lang.Comparable) when the terminal operation runs.
  • distinct() relies on equals and hashCode. Records have them; a plain class without them is compared by identity, so "duplicates" stay.
  • If the function in flatMap returns null, that element contributes nothing (it is treated as an empty stream).
  • takeWhile/dropWhile on an unordered source (a HashSet) give unpredictable results.
  • Sorting with null keys throws NullPointerException; wrap the key comparator with Comparator.nullsLast(...).

Mistake: a lambda key extractor before reversed()

Comparator.comparing(e -> e.name()).reversed() fails with "cannot find symbol: method name(), location: variable e of type Object". With .reversed() chained on, the compiler cannot use the target type to infer e, so it falls back to Object. Use a method reference (Employee::name) or type the parameter: (Employee e) -> e.name().

Wrong: does not compile

emps.stream()
    .sorted(Comparator.comparing(e -> e.name()).reversed())
    .toList();

Right: method reference gives the type

emps.stream()
    .sorted(Comparator.comparing(Employee::name).reversed())
    .toList();

Tip: filter early, map late

Put filter before expensive map calls and before sorted. Sorting 100 filtered elements is far cheaper than sorting 100,000 and filtering afterwards. The result is the same; the work is not.

Interview: "Difference between map and flatMap?" and "What is a stateful operation?"

  • map: one input → one output. flatMap: one input → a stream of outputs, all joined into one stream. Example: orders → items.
  • Stateful operations (sorted, distinct, skip, limit) need information about other elements; stateless ones (filter, map) handle each element alone.
  • takeWhile stops at the first failure; filter checks every element.
  • reversed() reverses the whole comparator chain; use Comparator.reverseOrder() as a second argument to reverse one key.

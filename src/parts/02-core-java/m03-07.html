Interview questions — Exceptions and files

What is the difference between checked and unchecked exceptions?

Checked exceptions are subclasses of Exception that are not RuntimeException (for example IOException, SQLException). The compiler forces you to catch them or declare them with throws. Unchecked exceptions are RuntimeException and its subclasses (and Error); the compiler does not check them. Use checked exceptions for failures the caller can reasonably recover from, and unchecked for programming errors and for failures the caller cannot fix. Modern frameworks such as Spring prefer unchecked exceptions.

Draw the exception hierarchy. Why should you not catch Error?

Throwable has two children: Error and Exception. RuntimeException is a subclass of Exception. Errors such as OutOfMemoryError and StackOverflowError signal that the JVM itself is in trouble. Your code usually cannot repair that, and trying to continue can leave the application in a corrupt state. Let the error propagate, log it at the top level, and let the process or container restart.

Does finally always run? What does this code print? 
static int test() {
    try {
        return 1;
    } finally {
        System.out.println("finally");
    }
}

It prints finally and then returns 1. The return value is computed first, then finally runs, then the method returns. finally does not run if the JVM exits (System.exit(), a crash, power loss), if the thread is killed, or if the code loops forever before reaching it. If finally itself has a return, it overrides the earlier return and swallows any exception, so never write one.

What is the difference between throw and throws?

throw is a statement that throws one exception object at run time: throw new IllegalArgumentException("amount <= 0"). throws is part of a method signature and lists the checked exceptions the method may pass to its caller: void read() throws IOException. throw is used inside the body; throws is used in the declaration and can list several types.

Why must catch blocks go from specific to general?

Java checks catch blocks from top to bottom and uses the first one that matches. If you put catch (Exception e) before catch (IOException e), the second block can never run, and the compiler reports an error ("exception IOException has already been caught"). In a multi-catch (A | B) the two types must not be related by inheritance, for the same reason.

What is try-with-resources and what are suppressed exceptions?

It declares resources that implement AutoCloseable in the parentheses of try. Java closes them automatically in reverse order of declaration, whether the body succeeds or throws. If the body throws exception A and then close() throws exception B, A is thrown and B is attached to it as a suppressed exception, readable with a.getSuppressed(). In a hand-written finally, B would replace A and the real cause would be lost.

Can an overriding method throw a broader exception than the method it overrides?

No, not for checked exceptions. The overriding method may throw the same checked exception, a narrower one, or none. It may throw any unchecked exception. The reason: code that uses the parent type only prepared for the exceptions in the parent's throws clause. If the child method could throw something broader, that caller would be surprised. A constructor and a method that is overridden follow the same rule.

How do you create a custom exception? Checked or unchecked?

Extend Exception (checked) or RuntimeException (unchecked), name it ...Exception, and provide constructors for a message and for a message plus cause. Add fields when callers need data, such as an error code or the missing amount. Choose checked when the caller can and should recover (for example InsufficientBalanceException in a payment flow where the UI offers "add money"); choose unchecked for business-rule violations that a global handler converts to an HTTP response, which is the common choice in Spring applications.

What is exception chaining and why wrap exceptions?

Chaining means passing the original exception as the cause of a new one: throw new OrderException("Cannot place order " + id, e). The stack trace then shows "Caused by: ...", so nothing is lost. Wrapping lets a service layer hide low-level details (SQLException) behind its own exception type, and converts a checked exception into an unchecked one when the caller cannot handle it. Always pass the cause; throwing a new exception without it destroys the evidence.

Why is catching Exception or swallowing an exception bad?

A broad catch (Exception e) also catches bugs (NullPointerException, ClassCastException) and interruptions that you did not plan for. An empty catch block hides the failure completely, so the program continues in a wrong state and you debug it weeks later with no log. Catch the specific type you can handle. Either handle it or rethrow it. Do not both log and rethrow at every layer, because one failure then appears ten times in the logs.

How do you avoid NullPointerException?

Validate inputs early (Objects.requireNonNull(x, "x must not be null")), return empty collections instead of null, return Optional from methods that may have no result, use constant-first comparison ("PAID".equals(status)), and avoid long chains of calls on possibly-null values. Since Java 14 the NPE message names the null expression, such as Cannot invoke "String.length()" because "name" is null, which makes debugging faster.

How does Spring Boot turn exceptions into HTTP responses?

An exception that escapes a controller is passed to exception resolvers. You normally write a class annotated with @RestControllerAdvice containing @ExceptionHandler methods, each mapping an exception type to a status code and a JSON error body. Without one, Spring Boot returns a default error response with status 500 for unhandled exceptions. You can also annotate an exception with @ResponseStatus. See Spring Boot · Module 2.

Files.readAllLines vs Files.lines vs BufferedReader: which for a large file?

readAllLines loads every line into a List, so memory use grows with the file size. It is fine for small files. Files.lines returns a lazy Stream<String> that reads as you consume it; it must be closed, so use try-with-resources. Files.newBufferedReader with readLine() is the same lazy idea in a classic loop. For a multi-gigabyte log, use lines or the reader, not readAllLines or readString.

Byte streams vs character streams? What does BufferedReader add?

Byte streams (InputStream, OutputStream) move raw bytes and suit binary data. Character streams (Reader, Writer) decode bytes to characters with a charset and suit text. BufferedReader wraps another reader, reads big blocks into memory so there are fewer system calls, and adds readLine(). It is an example of the decorator pattern.

What does transient mean, and what is serialVersionUID for?

A transient field is skipped during Java serialization; after loading it has its default value. serialVersionUID is a version number stored in the stream. On deserialization Java compares it with the class's number and throws InvalidClassException if they differ. You declare it explicitly, otherwise the compiler generates one from the class structure and a small edit breaks old data.

Why is Java serialization considered dangerous?

Deserializing a stream creates objects and calls code in classes on your classpath before your code can check anything. An attacker who controls the bytes can chain existing classes ("gadgets") to run commands on your server. So never deserialize untrusted input. Use a serialization filter if you must, and prefer JSON or another data-only format for storage and APIs.

Cheat sheet — Exceptions and files

  • Hierarchy Throwable → Error (do not catch) / Exception → RuntimeException (unchecked).
  • Checked Exception minus RuntimeException: catch or declare. Examples: IOException, SQLException, InterruptedException.
  • Unchecked RuntimeException: NPE, IllegalArgumentException, IllegalStateException, ArithmeticException, ClassCastException.
  • Catch order most specific first; a parent before its child is a compile error.
  • Multi-catch catch (A | B e); types must be unrelated; e is effectively final.
  • finally runs on return and on exceptions; not after System.exit(), a crash or an endless loop. Never return in it.
  • try-with-resources AutoCloseable resources closed in reverse order; extra close errors go to getSuppressed().
  • throw statement that throws one object. throws signature clause listing checked types.
  • Chaining new MyException("msg", cause) keeps "Caused by:" in the trace.
  • Overriding may throw the same, narrower or no checked exceptions, never broader.
  • Custom exception name ends with Exception; constructors (msg) and (msg, cause); add an error code field if useful.
  • Do not swallow, catch Throwable, log and rethrow in every layer, or use exceptions for normal flow.
  • Fail fast validate arguments first; Objects.requireNonNull(x, "msg").
  • Stack trace read top frame first (where it was thrown), then down to your code, then each "Caused by:" from the bottom.
  • Files (small) Files.readString, readAllLines, writeString, write; name UTF-8.
  • Files (large) Files.lines (close it!), newBufferedReader, newBufferedWriter.
  • Options StandardOpenOption.APPEND and CREATE to add to a file; default write truncates.
  • Directories createDirectories, list (one level), walk (tree), copy, move, deleteIfExists.
  • io bytes: InputStream/OutputStream; text: Reader/Writer; wrap with Buffered* (decorator).
  • File vs Path File is legacy; Path + Files is modern; convert with toPath().
  • Serialization Serializable marker; transient and static skipped; declare serialVersionUID; constructor not called.
  • Serialization risk never read untrusted data with ObjectInputStream; use JSON.
  • Properties load(Reader), getProperty(key, default), store; all values are strings.
  • Classpath file Class.getResourceAsStream("/name") returns null if missing.

Done when good rows are printed with a total and bad rows are listed with line numbers.
  6. Bank model with InsufficientBalanceException. Build the model below. Done when withdrawing too much throws your exception with the missing amount, the exception has a cause-capable constructor, and a test shows the balance unchanged after the failure. 
    public class InsufficientBalanceException extends Exception {
    private final long shortfallInPaise;

    public InsufficientBalanceException(String message, long shortfallInPaise) {
        super(message);
        this.shortfallInPaise = shortfallInPaise;
    }
    public long getShortfallInPaise() { return shortfallInPaise; }
}
    public class Account {
    private final String id;
    private long balanceInPaise;

    public Account(String id, long balanceInPaise) {
        this.id = id;
        this.balanceInPaise = balanceInPaise;
    }

    public void withdraw(long amount) throws InsufficientBalanceException {
        if (amount <= 0) {
            throw new IllegalArgumentException("amount must be positive: " + amount);
        }
        if (amount > balanceInPaise) {
            throw new InsufficientBalanceException(
                "Account " + id + " has " + balanceInPaise + " but needs " + amount,
                amount - balanceInPaise);
        }
        balanceInPaise -= amount;      // change state only after all checks pass
    }

    public String getId() { return id; }
    public long getBalanceInPaise() { return balanceInPaise; }
}
  7. Save and load the bank model. Write the accounts to accounts.csv (id,balanceInPaise) with Files.write and read them back into a Map<String, Account>. Done when a program that saves two accounts, restarts and loads them shows the same balances, and a missing or corrupt file gives a clear message instead of a stack trace. 
    import java.io.IOException;
import java.nio.file.*;
import java.util.*;

public class AccountStore {
    public static void save(Path file, Collection<Account> accounts) throws IOException {
        List<String> lines = accounts.stream()
                .map(a -> a.getId() + "," + a.getBalanceInPaise())
                .toList();
        Files.write(file, lines);              // UTF-8, creates or truncates
    }

    public static Map<String, Account> load(Path file) throws IOException {
        Map<String, Account> result = new LinkedHashMap<>();
        if (Files.notExists(file)) {
            return result;                     // first run: nothing saved yet
        }
        int lineNo = 0;
        for (String line : Files.readAllLines(file)) {
            lineNo++;
            String[] p = line.split(",");
            if (p.length != 2) {
                throw new IOException("Bad line " + lineNo + ": " + line);
            }
            try {
                result.put(p[0], new Account(p[0], Long.parseLong(p[1].trim())));
            } catch (NumberFormatException e) {
                throw new IOException("Bad balance on line " + lineNo, e);
            }
        }
        return result;
    }
}

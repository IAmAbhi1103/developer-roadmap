ThreadLocal: per-thread data and its leaks

A ThreadLocal gives every thread its own private copy of a variable, which is handy for per-request context, but in thread pools the copy outlives the task, so you must remove it or you leak data between requests.

What it is

Normally a field is shared by all threads. A ThreadLocal<T> is a variable where each thread that calls get() or set() sees its own value, stored inside the Thread object itself. No locks are needed because the data is never shared; this is called thread confinement.

public class ThreadLocalDemo {
    // each thread starts with its own value from the supplier
    private static final ThreadLocal<Integer> counter = ThreadLocal.withInitial(() -> 0);

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 3; i++) {
                counter.set(counter.get() + 1);
            }
            System.out.println(Thread.currentThread().getName() + " counter=" + counter.get());
        };
        Thread a = new Thread(task, "worker-A");
        Thread b = new Thread(task, "worker-B");
        a.start(); b.start();
        a.join(); b.join();
        System.out.println("main counter=" + counter.get());
    }
}
worker-A counter=3
worker-B counter=3
main counter=0

Each thread counted to 3 on its own copy, and main still has 0. No race condition is possible because nothing is shared.

MethodPurpose
ThreadLocal.withInitial(supplier)Create with a per-thread default value
get()Value for the current thread (initial value if unset)
set(value)Set the current thread's value
remove()Delete the current thread's value; the next get() gives the initial value again

Common uses

  • Per-request context in a web server that uses one thread per request: the current user, a request id for logging (SLF4J's MDC is a ThreadLocal map), the tenant id. Spring's SecurityContextHolder, RequestContextHolder and transaction synchronization work this way, so deep service code can find "the current user" without passing it through every method.
  • Non-thread-safe helper objects that are costly to create, such as the old SimpleDateFormat or a MessageDigest. Each thread gets its own copy. (For dates, simply use the immutable DateTimeFormatter instead.)
  • Per-thread random generators or buffers to avoid contention (the JDK's ThreadLocalRandom is built on this idea).

The leak in thread pools

Threads in a pool are reused. A ThreadLocal value stays attached to the thread until it is removed or the thread dies. So when task 1 sets a value and finishes without cleaning up, task 2 running on the same thread sees task 1's data. That is a bug and a security problem (user B served with user A's identity).

import java.util.concurrent.*;

public class LeakDemo {
    static final ThreadLocal<String> currentUser = new ThreadLocal<>();

    public static void main(String[] args) throws Exception {
        try (ExecutorService pool = Executors.newSingleThreadExecutor()) {   // 1 thread reused
            pool.submit(() -> currentUser.set("asha")).get();               // request 1 forgets remove()
            pool.submit(() -> System.out.println(
                    "request 2 sees user = " + currentUser.get())).get();
        }
    }
}
request 2 sees user = asha

Request 2 never set a user, yet it sees "asha". The cure is always to clean up in finally:

static void handleRequest(String user, Runnable work) {
    currentUser.set(user);
    try {
        work.run();
    } finally {
        currentUser.remove();      // always, even when work throws
    }
}

A second form of leak is memory. The values are strongly referenced from the thread, and a pool thread lives as long as the application. A large object (a big buffer, a user session graph) left in a ThreadLocal stays in memory. In application servers where the web app can be redeployed, a ThreadLocal holding an object of the app's classes can keep the whole old class loader alive ("ClassLoader leak", the cause of OutOfMemoryError: Metaspace after several redeploys). Frameworks like Spring clean their own ThreadLocals; the leaks usually come from your own code.

Related: InheritableThreadLocal, virtual threads and scoped values

  • InheritableThreadLocal copies the parent thread's value to a new child thread at creation. It does not help with pools, because the pool threads were created earlier; frameworks use task decorators to copy context into tasks.
  • Virtual threads support ThreadLocal, but because you may create millions of virtual threads, per-thread caches become expensive. Do not put heavy objects in them.
  • Scoped values (ScopedValue) are a modern, safer alternative: immutable data bound for the duration of a block of code and automatically gone afterwards. They were a preview API in Java 21 to 24 and became a final feature in Java 25.

Rules

  • Declare ThreadLocal as private static final.
  • Call remove() in finally whenever a thread might be reused (pools, servlet containers).
  • Store small, preferably immutable values; never large caches.

Exceptions and edge cases

  • NullPointerException — get() returns null when no initial value was set, and unboxing it (int x = tl.get()) fails.
  • ThreadLocal values do not follow work onto another thread: CompletableFuture.supplyAsync, @Async and parallel streams run on different threads, so the "current user" is missing there unless you pass it explicitly.
  • A ThreadLocal is hidden global state: it makes code harder to test and to reason about. Prefer plain method parameters when the call chain is short.

Interview: "What is ThreadLocal? What problems can it cause?"

  • Per-thread variable; no locking needed; uses: request context, MDC, non-thread-safe helpers.
  • In pools, values survive between tasks: stale or leaked data and memory leaks; fix with remove() in finally.
  • Does not propagate to async tasks; scoped values (final in Java 25) are the modern alternative.

Virtual threads (Java 21)

Virtual threads are lightweight threads managed by the JVM that let you write simple blocking code and still handle hundreds of thousands of concurrent tasks, because a virtual thread that waits on I/O frees its carrier platform thread.

The problem they solve

The classic server model is thread-per-request: one thread handles one request from start to finish. It is easy to write and debug. The trouble: a platform thread maps one-to-one to an operating-system thread and costs memory (typically about 1 MB of stack is reserved) and scheduling time, so a machine can hold only a few thousand. Most of the time a request thread is not computing; it waits for the database or another service. A server with 200 threads and 200 ms of waiting per request tops out at about 1,000 requests per second, while the CPU is almost idle.

Developers escaped this with asynchronous, callback-based code (CompletableFuture, reactive libraries), which is efficient but harder to read, debug and profile. Virtual threads (Project Loom, final in Java 21) keep the simple style and remove the thread limit.

How they work

The JVM runs virtual threads on a small pool of platform threads called carrier threads (a ForkJoinPool with, by default, as many carriers as CPU cores). When a virtual thread runs, it is mounted on a carrier. When it hits a blocking operation that the JDK has made virtual-thread-aware (socket I/O, Thread.sleep, locks and queues from java.util.concurrent), the JVM saves its stack to the heap and unmounts it. The carrier is now free to run another virtual thread. When the I/O completes, the virtual thread is scheduled again, possibly on a different carrier.

Creating virtual threads

import java.time.Duration;
import java.util.concurrent.*;
import java.util.stream.IntStream;

public class VirtualDemo {
    public static void main(String[] args) throws Exception {
        // 1. Builder API
        Thread t1 = Thread.ofVirtual().name("vt-1").start(
                () -> System.out.println("virtual? " + Thread.currentThread().isVirtual()));
        t1.join();

        // 2. Shortcut
        Thread t2 = Thread.startVirtualThread(() -> System.out.println("hello from t2"));
        t2.join();

        // 3. Executor: a NEW virtual thread for every task (not a pool)
        long start = System.currentTimeMillis();
        try (ExecutorService exec = Executors.newVirtualThreadPerTaskExecutor()) {
            IntStream.range(0, 10_000).forEach(i -> exec.submit(() -> {
                Thread.sleep(Duration.ofSeconds(1));      // 10,000 tasks each waiting 1 s
                return i;
            }));
        }   // close() waits for all tasks
        System.out.println("10,000 tasks took ~"
                + (System.currentTimeMillis() - start) / 1000.0 + " s");
    }
}

hello from t2
10,000 tasks took ~1.4 s

Ten thousand tasks that each wait one second finish in about one second in total, on a handful of carrier threads. With a fixed pool of 200 platform threads the same job would need about 50 seconds. The code is plain blocking code.

When they help and when they do not

  • Help: high-concurrency servers whose requests mostly wait: REST APIs calling databases and other services, batch jobs that fetch thousands of URLs, message consumers doing I/O.
  • Do not help: CPU-bound work (image processing, encryption, big computations). Throughput is limited by the number of cores no matter how many threads you have. Use a pool sized to the cores.
  • They improve throughput under load, not the speed of one request.

Rules and good habits

  1. Do not pool virtual threads. They are cheap; pooling defeats the purpose. Create one per task.
  2. Limit concurrency with a Semaphore, not with pool size, when a downstream resource has limits (for example a database that allows 20 connections, or a partner API).
  3. Keep using ReentrantLock or synchronized for short critical sections, but avoid long blocking I/O inside them.
  4. Avoid heavy ThreadLocal data (see ThreadLocal); a million threads times a big cache is a lot of memory.
  5. Do not tune with thread priorities or rely on thread-count assumptions.

Pinning

A virtual thread is pinned when it cannot unmount while blocked: it stays stuck to its carrier thread and blocks it. Before Java 24 this happened when the thread blocked inside a synchronized block or method, and it still happens when blocked inside native code or a foreign function call. A few pinned threads are harmless; many pinned threads can starve the small carrier pool. Java 24 (JEP 491) removed the synchronized case, so in Java 24 and later (including 25) blocking inside synchronized no longer pins the carrier in most cases. On Java 21 you can switch to ReentrantLock in hot code that blocks, and use the JFR event jdk.VirtualThreadPinned to find pinning.

Spring Boot

With Spring Boot 3.2 and later (so also 4.x) on Java 21+, one property switches request handling to virtual threads:

spring.threads.virtual.enabled=true

Embedded Tomcat or Jetty then runs each request on a virtual thread, and Boot's task execution and scheduling beans also use virtual threads. Your controllers and JDBC code stay unchanged. Details are in Spring Boot · Module 6. Remember that the database connection pool (HikariCP, default 10 connections) remains the next bottleneck: ten thousand virtual threads will still wait for ten connections.

Versions and structured concurrency

Virtual threads were a preview in Java 19 and 20 and are final in Java 21. Structured concurrency (StructuredTaskScope), which treats a group of subtasks as one unit of work with clean cancellation, was still a preview API in Java 25, so treat it as "coming" and do not use it in production code yet. Observability: thread dumps from jcmd <pid> Thread.dump_to_file -format=json file include virtual threads; the classic jstack output does not list them all.

Edge cases

  • IllegalArgumentException — setting a priority on a virtual thread other than normal is ignored; setting it to be non-daemon with setDaemon(false) throws.
  • Code that assumes Thread.currentThread().getName() is unique or non-empty: virtual threads have an empty name unless you set one.
  • Unlimited creation can overwhelm the thing behind them (database, other APIs). Protect it with a semaphore or a bulkhead.

Mistake: using virtual threads for CPU-bound loops

A million virtual threads each crunching numbers will queue on the few carriers and give no speed-up. Pick a fixed pool of about availableProcessors() threads (or a parallel stream) for computation.

Interview: "What are virtual threads and when would you use them?"

  • JVM-managed lightweight threads, mounted on carrier threads, unmounted on blocking I/O; final in Java 21.
  • Thread-per-request code scales to very many concurrent waits; not helpful for CPU-bound tasks.
  • Do not pool them; limit with a semaphore; know pinning (fixed for synchronized in Java 24).
  • Spring Boot: spring.threads.virtual.enabled=true.

Thread-safety strategies: a decision summary

Make code thread-safe in this order of preference: share nothing, share only immutable data, use concurrent collections and atomics, and only then use locks.

What thread-safe means

A class is thread-safe if it behaves correctly when used by many threads at once, with no extra synchronization by the callers. The dangerous situation always has three ingredients: shared data, mutable data and unsynchronized access. Remove any one and the problem disappears. That gives the five strategies below.

The strategies

  1. Do not share (confinement). Keep data in local variables (each thread has its own stack), in method parameters, or in a ThreadLocal. Hand an object to exactly one thread at a time (for example through a BlockingQueue). Local variables are always safe.
  2. Do not mutate (immutability). Immutable objects can be shared freely: String, Integer, LocalDate, records with immutable components, List.of(...). To change, create a new object. Make fields private final, no setters, copy mutable inputs, and do not leak this from constructors.
  3. Use thread-safe building blocks. ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue, and atomic classes (AtomicInteger, LongAdder, AtomicReference) give atomic operations without you writing locks.
  4. Synchronize access. synchronized or ReentrantLock around every access to the shared state (reads too), using the same lock; keep the critical section small; use volatile only for a simple flag or safe publication.
  5. Use higher-level coordination. Executors, CompletableFuture, latches, semaphores and virtual threads so that tasks communicate by passing results instead of sharing variables.

Real-world application: Spring beans

Spring creates singleton beans (controllers, services, repositories) by default, and one instance serves all request threads. So a service must be stateless: no mutable instance fields that hold per-request data. This code is a classic bug:

Wrong: shared mutable state in a singleton

@Service
public class OrderService {
    private Order currentOrder;          // shared by all requests!
    public void process(Order o) {
        this.currentOrder = o;
        validate();
        save(currentOrder);              // may save another user's order
    }
}

Right: pass data through parameters

@Service
public class OrderService {
    public void process(Order o) {
        validate(o);
        save(o);                         // o is local to this call
    }
}

Other thread-safety hot spots in Spring apps: caches held in plain HashMap fields, SimpleDateFormat as a field, counters as int fields, lazy initialization of fields, and mutable static variables. Each has a fix from the table above.

Checking your class

  • List all shared mutable fields. For each, name the one thing that protects it: a lock, an atomic, a concurrent type or immutability.
  • Look for check-then-act (if (!map.containsKey), if (x == null) x = ...) and read-modify-write (count++) sequences. They need to be one atomic step.
  • Do not expose internal mutable collections; return copies or unmodifiable views.
  • Document thread-safety in the class comment (immutable, thread-safe, not thread-safe, guarded by lock X).

Rules

  • Every access to shared mutable data, reads and writes, needs the same protection.
  • Thread-safe parts do not make a thread-safe whole: two atomic operations in a row are not atomic together.
  • Prefer the simplest tool that works: immutability before atomics, atomics before locks.

Conventions

  • Make classes immutable by default; use records for data.
  • Prefer java.util.concurrent over hand-written wait/notify.
  • Test concurrency with many threads and many repetitions, and use tools such as thread dumps and, in bigger projects, stress-testing libraries. A passing single-thread test proves nothing.

Interview: "How do you make a class thread-safe?"

  • Say the three ingredients (shared, mutable, unsynchronized) and the five ways to remove one: confinement, immutability, concurrent collections/atomics, locks, higher-level coordination.
  • Give the Spring example: singleton services must be stateless.
  • Mention check-then-act and read-modify-write as the typical bugs.

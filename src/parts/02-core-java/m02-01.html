Object-oriented programming (OOP) is the way almost all Java code is organised. You model a problem as objects — things that hold data together with the code that works on that data — and you describe each kind of object with a class. Spring beans, JPA entities, DTOs, exceptions, collections: everything you touch in a Java project is a class.

This module starts with the basics (classes, objects, constructors, this, static), moves through the four pillars — encapsulation, inheritance, polymorphism and abstraction — and then covers the tools professionals use every day: final, the Object methods (equals, hashCode, toString), composition, nested classes, packages, enums and records. It ends with one worked example that ties everything together.

It is the base for much of what follows: Collections (Module 4) depend on equals and hashCode, modern Java (Module 5) builds on interfaces, records and sealed types, memory (Module 7) explains where objects live, and design principles and patterns (System Design · Module 1) assume you know all of this well.

Why OOP: classes, objects, state, behaviour and identity

OOP keeps data and the code that changes it together inside objects, so each object can protect its own rules; a class is the blueprint and an object is one thing built from it.

Before OOP became mainstream, most programs were written in a procedural style: data lives in variables, arrays or simple records, and separate functions read and change that data. This works for small programs. It becomes painful as the program grows, because nothing stops any function from changing any data, and the business rules ("a balance can never go below zero") get copied into many places.

The problem with procedural code

Here is a tiny bank written in a procedural style. The data (holders and balances) sits in arrays, and a function changes it.

public class BankProcedural {
    static String[] holders = {"Ravi", "Asha"};
    static long[] balances = {5_000, 12_000};

    static void withdraw(int index, long amount) {
        balances[index] -= amount;            // no rule is checked here...
    }

    public static void main(String[] args) {
        withdraw(0, 8_000);
        balances[1] = -999;                   // ...and any code can do this
        System.out.println(holders[0] + ": " + balances[0]);
        System.out.println(holders[1] + ": " + balances[1]);
    }
}
Ravi: -3000
Asha: -999

Three problems show up at once:

  • No protection. Any line of code can write balances[1] = -999. The rule "no negative balance" is not enforced anywhere.
  • Scattered rules. If ten functions change balances, each one must remember to check the rule. One forgets, and you have a production bug.
  • Hard to extend. Add a "current account with overdraft" and every function grows another if (type == CURRENT) branch.

The OOP answer: keep data and behaviour together

In OOP you create an Account class. The balance is private, so only the class's own methods can change it, and each method checks the rules once, in one place.

public class Account {
    private final String holder;
    private long balance;                       // hidden: only Account can touch it

    public Account(String holder, long openingBalance) {
        if (openingBalance < 0) {
            throw new IllegalArgumentException("Opening balance cannot be negative");
        }
        this.holder = holder;
        this.balance = openingBalance;
    }

    public void withdraw(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
        if (amount > balance) {
            throw new IllegalStateException("Insufficient balance for " + holder);
        }
        balance -= amount;
    }

    public long getBalance() {
        return balance;
    }
}
public class Main {
    public static void main(String[] args) {
        Account ravi = new Account("Ravi", 5_000);
        try {
            ravi.withdraw(8_000);
        } catch (IllegalStateException e) {
            System.out.println(e.getMessage());
        }
        ravi.withdraw(1_500);
        System.out.println("Ravi: " + ravi.getBalance());
        // ravi.balance = -999;   // compile error: balance has private access in Account
    }
}
Insufficient balance for Ravi
Ravi: 3500

The rule now lives in exactly one method, and the compiler itself blocks ravi.balance = -999. When you need a new account type, you add a new class instead of editing every function — that is what inheritance and polymorphism give you.

Class vs object

A class is a blueprint. It says what data every object of that kind holds and what those objects can do. An object (also called an instance) is one concrete thing built from the blueprint at run time with new. One class, many objects — like one house plan and many houses built from it, each with its own paint colour and its own residents.

State, behaviour and identity

Every object has three things. Interviewers like this definition because it separates "what an object knows", "what it does" and "which one it is".

State
The data the object holds right now — the current values of its fields. Ravi's account: holder "Ravi", balance 3,500.
Behaviour
What the object can do — its methods, such as withdraw() and getBalance(). Behaviour usually reads or changes state.
Identity
What makes this object itself and not another one. Two accounts can have the same holder and the same balance and still be two different objects. In Java, == on two references compares identity.

Keep identity and equality apart in your head: == asks "is this the very same object?", while equals() asks "do these two objects represent the same value?". You decide what "same value" means by overriding equals() — see equals() and hashCode().

The four pillars in one line each

  • Encapsulation — hide the data and expose safe methods that keep it valid.
  • Inheritance — build a new class from an existing one when the new one "is a" kind of the old one.
  • Polymorphism — one method call, different behaviour depending on the actual object.
  • Abstraction — show what an object does and hide how it does it.

Each pillar has its own articles below, and the four pillars summary pulls them together at the end of the module.

In a real Spring Boot project

You write entity classes (Order, Customer), DTO records (OrderResponse), service classes (OrderService) and controllers. Spring creates the service and controller objects for you (they are "beans"); you create entities and DTOs yourself with new, or JPA and Jackson create them for you from database rows and JSON.

Java is not "pure" OOP — and that is fine

Primitives such as int and double are not objects, and static methods belong to no object. Modern Java also mixes in a functional style (lambdas and streams, Module 5) and a data-oriented style (records, sealed types and pattern matching). Good Java uses the right tool for each job.

Mistake: one giant "manager" class

A BankManager class with fifty methods that all work on raw arrays and maps is procedural code wearing a class costume (often called a god class). Model the domain nouns instead — Account, Transaction, Customer — and let each class own its data and its rules.

Interview: "What is OOP and why do we use it?"

  • OOP models software as objects that combine state (fields) and behaviour (methods); a class is the blueprint, an object is an instance.
  • Benefits: encapsulation protects invariants, inheritance and composition give reuse, polymorphism lets you add new types without changing callers, abstraction hides complexity.
  • Give a 20-second example: an Account with a private balance and a withdraw() that checks the rule.
  • Bonus point: mention the trade-off — deep inheritance trees are a design smell; prefer composition (see favor composition).

Classes and objects in code: fields, methods and new

A class declares fields (state), constructors (setup) and methods (behaviour); new creates an object on the heap, runs its constructor and gives you a reference to it.

Anatomy of a class

Here is a realistic class from an e-commerce app. Notice the three main parts: fields, a constructor and methods. The price is stored in whole paise as a long, because double cannot represent money exactly.

public class Product {
    // 1. Fields: the state every Product object carries
    private final String sku;
    private String name;
    private long pricePaise;          // money as whole paise, never double
    private int stock;

    // 2. Constructor: builds a valid object
    public Product(String sku, String name, long pricePaise, int stock) {
        this.sku = sku;
        this.name = name;
        this.pricePaise = pricePaise;
        this.stock = stock;
    }

    // 3. Methods: the behaviour
    public boolean isInStock() {
        return stock > 0;
    }

    public void sell(int quantity) {
        if (quantity > stock) {
            throw new IllegalStateException("Only " + stock + " left for " + sku);
        }
        stock -= quantity;
    }

    public String getName() { return name; }
    public int getStock()   { return stock; }

    public static void main(String[] args) {
        Product mouse = new Product("SKU-101", "Wireless Mouse", 49_900, 3);
        Product keyboard = new Product("SKU-102", "Keyboard", 1_29_900, 0);

        mouse.sell(2);
        System.out.println(mouse.getName() + " stock: " + mouse.getStock());
        System.out.println(keyboard.getName() + " in stock? " + keyboard.isInStock());
        try {
            mouse.sell(5);
        } catch (IllegalStateException e) {
            System.out.println("Error: " + e.getMessage());
        }
    }
}
Wireless Mouse stock: 1
Keyboard in stock? false
Error: Only 1 left for SKU-101

Two objects, mouse and keyboard, came from one class. Each has its own stock: selling a mouse did not touch the keyboard. Underscores in numbers such as 1_29_900 are only for readability; the compiler ignores them.

Conventions for classes and members

  • Class names are nouns in PascalCase: OrderService, UpiPayment. Method names are verbs in camelCase: placeOrder(), isInStock(). Constants are UPPER_SNAKE_CASE: MAX_RETRIES.
  • A file holds at most one public top-level class, and the file must be named after it (Product.java). Otherwise javac reports class Product is public, should be declared in a file named Product.java.
  • Common member order: constants, static fields, instance fields, constructors, public methods, private helpers. Teams enforce it with formatters and Checkstyle.
  • Fields are private by default in professional code; you open access only on purpose (see encapsulation).

Creating an object with new

The line Product mouse = new Product("SKU-101", "Wireless Mouse", 49_900, 3); does three things. Product mouse declares a reference variable of type Product. new Product(…) creates the object. The = stores a reference to the new object in the variable. Since Java 10 you can also write var mouse = new Product(…); — the variable's type is still Product; var only saves typing.

What new does, step by step

  1. Load and initialize the class if this is its first use. Static fields and static blocks run once, here (see initialization order).
  2. Allocate memory on the heap — enough for an object header plus every instance field, including the fields inherited from parent classes.
  3. Set every field to its default value: 0, false, '\u0000' or null.
  4. Run the constructor chain: the parent constructor first (all the way up to Object), then this class's field initializers and instance blocks, then the constructor body.
  5. Return the reference. The assignment stores it in your variable.

The variable does not contain the object. It contains a reference — think of it as the object's address inside the JVM. Local variables live in the method's stack frame and disappear when the method returns. Objects live on the heap and stay there as long as something can still reach them. Module 7 covers the heap, the stack and garbage collection in depth.

The JIT may skip the heap — your mental model stays the same

The JIT compiler uses escape analysis: if an object never leaves a method, the JVM may avoid allocating it on the heap at all. This is an optimisation you cannot see in your program's behaviour, so "objects live on the heap, references point to them" remains the right way to reason about code.

Default values

Fields always start with a default value before any constructor code runs. Local variables do not.

Rule: a local variable must be assigned before it is read

Reading an unassigned local variable is a compile error: variable total might not have been initialized. The compiler checks every path through the method (this is called definite assignment). Fields never cause this error because they always have a default — which is exactly why a forgotten field assignment becomes a silent null or 0 bug instead.

References are values: assignment and method calls

Assigning one reference variable to another copies the reference, not the object. Passing an object to a method also copies the reference. The method can change the shared object, but it cannot make your variable point somewhere else.

public class Refs {
    static class Account {
        String holder;
        long balance;
        Account(String holder, long balance) { this.holder = holder; this.balance = balance; }
    }

    static void credit(Account acc, long amount) {
        acc.balance += amount;          // changes the shared object
    }

    static void replace(Account acc) {
        acc = new Account("Someone else", 0);   // changes only the local copy of the reference
    }

    public static void main(String[] args) {
        Account a = new Account("Ravi", 1000);
        Account b = a;                  // copies the reference, not the object
        b.balance = 5000;
        System.out.println(a.balance);  // 5000
        System.out.println(a == b);     // true: same object

        credit(a, 500);
        System.out.println(a.balance);  // 5500
        replace(a);
        System.out.println(a.holder);   // Ravi

        Account c = new Account("Ravi", 5500);
        System.out.println(a == c);     // false: different objects, same state
    }
}

5500
Ravi

Interview: "Is Java pass-by-value or pass-by-reference?"

Always pass-by-value. For primitives the value is the number itself; for objects the value is the reference. That is why credit() can change the account (both copies of the reference point to the same object) but replace() cannot change what a points to. A strong answer shows exactly this pair of methods.

null and NullPointerException

A reference can be null, meaning it points to no object. Calling a method or reading a field through null throws NullPointerException (NPE). Since Java 14 the JVM prints helpful NPE messages (on by default since Java 15) that name exactly what was null:

Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.length()" because "c.name" is null
	at Npe.main(Npe.java:8)

Variable names such as c.name appear when the class was compiled with debug information (Maven and Gradle do this by default); otherwise you see placeholders like <local1>.

Conventions that prevent most NPEs

  • Validate constructor arguments early: this.name = Objects.requireNonNull(name, "name"); fails fast with a clear message.
  • Return an empty list instead of null from methods that return collections.
  • Use Optional as the return type when "no value" is a normal outcome (Module 5).

When does an object die?

Java has no destructors and no manual free(). When no live reference can reach an object any more, it becomes eligible for garbage collection, and the garbage collector reclaims the memory at a time of its choosing. Setting a local variable to null "to help the GC" is almost never needed; the reference disappears when the method returns. The cases that really matter — objects kept alive by a static collection or a cache — are covered in Module 7.

Mistake: using == to compare objects by value

Wrong: compares identity

Account x = new Account("Ravi", 5500);
Account y = new Account("Ravi", 5500);
if (x == y) {               // false: two different objects
    System.out.println("Same account");
}

Right: compare by value with equals()

// after Account overrides equals() and hashCode()
if (x.equals(y)) {          // true when the fields match
    System.out.println("Same account");
}

Without an overridden equals(), the version inherited from Object also compares identity, so you must override it first (see equals() and hashCode()).

Constructors in depth: default, overloaded, chained and copy

A constructor puts a new object into a valid state; Java adds a no-arg default constructor only when you write none, and constructors reuse each other with this(…) and super(…).

A constructor is a special block of code that runs exactly once for each new object, as part of new. Its job is to make the object valid from its very first moment: required fields set, rules checked. If an object can exist in a half-built state, bugs follow.

A constructor has the same name as the class and no return type — not even void. It can be overloaded, it can have any access modifier, and it can throw exceptions. It is not a method and it is not inherited.

The default constructor

If a class declares no constructor at all, the compiler adds a default constructor: it takes no arguments, has the same access as the class (a public class gets a public one; a package-private class gets a package-private one), and its body simply calls super().

The moment you write any constructor yourself, the compiler stops adding the default one. Code that used new Customer() then breaks:

class Customer {
    private String name;
    Customer(String name) { this.name = name; }
}

public class E2 {
    public static void main(String[] args) {
        Customer c = new Customer();   // compile error
    }
}

Frameworks that need a no-arg constructor

JPA requires every entity class to have a public or protected no-arg constructor, because Hibernate creates entity objects by reflection and then fills the fields. If you add Order(String id) to an entity, also add protected Order() { }. Jackson, which turns JSON into objects in Spring Boot, needs either a no-arg constructor or a constructor it can bind to — such as a record's canonical constructor or one marked @JsonCreator.

Overloading and chaining with this(…)

A class can have several constructors with different parameter lists — constructor overloading. To avoid copying the validation into each one, let the short constructors delegate to the most complete one using this(…). This is constructor chaining.

public class Ct2 {
    static class Order {
        private final String id;
        private final int quantity;
        private final String note;

        Order(String id) {
            this(id, 1);                          // delegate
        }

        Order(String id, int quantity) {
            this(id, quantity, "");               // delegate
        }

        Order(String id, int quantity, String note) {   // the "main" constructor
            if (id == null || id.isBlank()) {
                throw new IllegalArgumentException("id is required");
            }
            if (quantity <= 0) {
                throw new IllegalArgumentException("quantity must be > 0");
            }
            this.id = id;
            this.quantity = quantity;
            this.note = note;
            System.out.println("Created " + this);
        }

        @Override public String toString() {
            return "Order[id=" + id + ", quantity=" + quantity + ", note='" + note + "']";
        }
    }

    public static void main(String[] args) {
        new Order("SW-1001");
        new Order("SW-1002", 3);
        new Order("SW-1003", 2, "Less spicy");
        try {
            new Order("SW-1004", 0);
        } catch (IllegalArgumentException e) {
            System.out.println("Rejected: " + e.getMessage());
        }
    }
}

Calling the parent with super(…)

Every constructor starts by running a constructor of its parent class. You either write super(…) yourself, or — if you write neither this(…) nor super(…) — the compiler inserts super() with no arguments. If the parent has no no-arg constructor, that hidden call fails:

class Vehicle {
    Vehicle(String regNo) { }
}

class Car extends Vehicle {
    Car() { }        // compiler inserts super() here, but Vehicle() does not exist
}
E3.java:5: error: constructor Vehicle in class Vehicle cannot be applied to given types;
    Car() { }
          ^
  required: String
  found:    no arguments
  reason: actual and formal argument lists differ in length

The fix is Car(String regNo) { super(regNo); }. More on parent constructors in inheritance.

Rules for this(…) and super(…)

  • Up to Java 24, this(…) or super(…) must be the very first statement of the constructor. Java 17 says call to super must be first statement in constructor.
  • A constructor can call only one of them — never both.
  • Constructors must not call each other in a loop: javac reports recursive constructor invocation.
  • The arguments you pass to this(…)/super(…) cannot use the object being built. super(makeId()) fails if makeId() is an instance method (cannot reference makeId() before supertype constructor has been called); a static helper is fine.

Java 25: flexible constructor bodies

Java 25 finalised flexible constructor bodies (JEP 513). Statements may now appear before super(…) or this(…) — for example to validate arguments before the expensive parent constructor runs — as long as they do not use the object under construction (no reading fields, no instance method calls). They may assign fields that have no initializer.

class SavingsAccount extends Account {
    private final double rate;

    SavingsAccount(String accountNo, double rate) {
        if (rate < 0 || rate > 0.15) {           // validate BEFORE calling super
            throw new IllegalArgumentException("Bad rate: " + rate);
        }
        this.rate = rate;                        // allowed: field has no initializer
        super(accountNo);
    }
}

On Java 17 or 21 this is a compile error. Most projects still target 17 or 21, so write the classic form (call super first, or validate inside a static helper used as an argument) unless your project is on 25.

Copy constructors

A copy constructor takes another object of the same class and builds a new, independent object with the same state. Copy immutable fields (like String) by reference; copy mutable fields (like a List) into a new object, or the two objects will share and change the same list.

import java.util.*;

public class CopyCtor {
    static class Policy {
        private final String holder;
        private final List<String> nominees;

        Policy(String holder, List<String> nominees) {
            this.holder = holder;
            this.nominees = new ArrayList<>(nominees);
        }

        // Copy constructor: a new, independent object with the same state
        Policy(Policy other) {
            this.holder = other.holder;                       // String is immutable: share it
            this.nominees = new ArrayList<>(other.nominees);  // List is mutable: copy it
        }

        void addNominee(String name) { nominees.add(name); }
        List<String> nominees() { return List.copyOf(nominees); }
    }

    public static void main(String[] args) {
        Policy original = new Policy("Meera", List.of("Arjun"));
        Policy copy = new Policy(original);
        copy.addNominee("Kavya");
        System.out.println("original: " + original.nominees());
        System.out.println("copy:     " + copy.nominees());
    }
}
original: [Arjun]
copy:     [Arjun, Kavya]

Notice that Policy(Policy other) reads other.nominees even though the field is private. Access in Java is per class, not per object, so code inside Policy may read the private fields of any Policy. The JDK uses copy constructors everywhere: new ArrayList<>(otherList), new HashMap<>(otherMap). They are preferred over clone() — see copying objects.

Private constructors and static factory methods

A private constructor stops other classes from calling new. You use it for:

  • Utility classes that only have static methods (Math, Collections) — see static.
  • Singletons, where exactly one instance must exist (System Design · Module 2).
  • Static factory methods — static methods that create objects for the caller: List.of(…), LocalDate.of(2026, 10, 18), Integer.valueOf(42).

Factories have advantages over constructors: they have names (Money.ofRupees(250) reads better than new Money(25000)), they can return a cached object instead of a new one (Integer.valueOf caches −128 to 127 by default), and they can return a subtype. Their downside is that they are less visible than constructors in the class's API.

Edge cases and surprises

  • A "constructor" with a return type is a method. void FakeCtor() { status = "ACTIVE"; } compiles as an ordinary method named like the class. new FakeCtor() uses the default constructor, the "constructor" never runs, and status stays null. javac does not even warn you.
  • Modifiers: final, static, abstract and synchronized are not allowed on a constructor (modifier final not allowed here).
  • Abstract classes have constructors too. You cannot call them with new, but subclasses call them through super(…).
  • A constructor that throws means new completes abruptly and no reference is assigned — the caller never gets the half-built object.
  • Enums and records follow special rules: enum constructors are always private, and records get a canonical constructor instead of a no-arg one (see enums and records).

Mistake: the parameter shadows the field

Wrong: assigns the parameter to itself

class Customer {
    private String name;
    Customer(String name) {
        name = name;        // field stays null
    }
}

Right: this.name is the field

class Customer {
    private final String name;
    Customer(String name) {
        this.name = name;   // field = parameter
    }
}

Making the field final turns this bug into a compile error, because a final field that is never assigned is reported (variable name might not have been initialized).

Tip: too many constructor parameters? Use a builder

A constructor with seven parameters (several of them optional) is hard to call correctly — new Pizza("L", true, false, true, null, 2, "thin"). This is the telescoping constructor problem. The usual fix is the Builder pattern (a static nested Builder class, see nested classes), or a record plus a few static factories.

Interview: constructor questions

  • Can a constructor be private? Yes — singletons, utility classes, static factories.
  • Can it be final, static or abstract? No. Constructors are not inherited, so final and abstract mean nothing; static makes no sense because a constructor works on a new instance.
  • Can you override a constructor? No (not inherited), but you can overload it.
  • What is constructor chaining? One constructor calling another with this(…) (same class) or super(…) (parent class), first statement, so setup logic is written once.
  • Does a constructor return anything? It has no return type; the new expression produces the reference.

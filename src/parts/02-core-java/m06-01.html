A thread is an independent path of execution inside your program. Multithreading lets one Java process do several things at once: a web server handles hundreds of requests together, a Swiggy-style backend calls the restaurant, payment and delivery services in parallel, and a background job sends emails while the user keeps browsing. Almost every Spring Boot application is multithreaded whether you write a single Thread or not — Tomcat runs each request on a pool thread, and your singleton beans are shared by all of them.

Concurrency is also where the hardest bugs live: wrong totals that appear once in a thousand runs, a service that hangs forever, a memory leak that only shows after a week. This module teaches the model (memory visibility, atomicity, locks), the tools (executors, CompletableFuture, concurrent collections, synchronizers) and the modern answer for I/O-heavy code (virtual threads, Java 21). It builds on collections (Module 4), lambdas (Module 5) and connects to the JVM memory model in Module 7. For the operating-system view of processes and threads, see CS Fundamentals · Module 1.

After this module you will be able to:

  • create, start, join and interrupt threads correctly, and explain start() vs run() and the six thread states;
  • explain atomicity, visibility and ordering, and why count++ is not thread-safe;
  • fix a race condition with synchronized, AtomicInteger or a lock, and know when volatile is enough;
  • run work on thread pools, use Future and chain async calls with CompletableFuture;
  • pick the right concurrent collection, latch, barrier or semaphore;
  • recognise, prevent and diagnose a deadlock;
  • use ThreadLocal safely and decide when virtual threads are the right tool;
  • choose a thread-safety strategy for any shared data.

Why concurrency: processes, threads, concurrency vs parallelism

A process is a running program with its own memory; a thread is a lightweight path of execution inside a process that shares that memory, which lets a program use all CPU cores and keep working while it waits for I/O.

Your laptop has several CPU cores, and each core runs one instruction stream at a time. A program with one thread uses at most one core. Worse, most real programs spend their time waiting: for a database reply, an HTTP response, a disk read. While one thread waits, the core sits idle. Multithreading fixes both problems.

Why use threads

  • Use all cores — split a CPU-heavy job (image resizing, report calculation) across cores to finish sooner.
  • Hide waiting — while thread A waits for the payment gateway, thread B serves another customer. This is the main reason servers use threads.
  • Stay responsive — a UI or a main loop hands slow work to a background thread so it does not freeze.
  • Model independent tasks naturally — one thread per request is easy to read and debug.

Process vs thread

A process is a program that the operating system is running: it owns its own virtual address space (memory), open files and security context. Running java MyApp starts one process, which contains one JVM. A thread lives inside a process. All threads of a process share the same heap (all your objects) but each thread has its own call stack and program counter.

PointProcessThread
MemorySeparate address space per processShares the heap with other threads; own stack
Creation costHeavy (new memory map, resources)Lighter, but a platform thread still reserves about 1 MB of stack by default on 64-bit systems
CommunicationNeeds IPC: pipes, sockets, files, shared memoryJust read and write shared objects (which is also the danger)
IsolationA crash in one process leaves others aliveAn uncaught OutOfMemoryError or a shared-data bug can hurt the whole JVM
Context switchExpensiveCheaper, still not free

This picture explains the whole module. Local variables (primitives and references on a stack) are private to a thread, so they are automatically safe. Objects on the heap and static fields are shared, and every bug in this module is about two threads touching the same shared object at the wrong time.

Concurrency vs parallelism

These words are often confused. Concurrency means several tasks are in progress during the same period — their execution is interleaved, even on a single core. Parallelism means several tasks are literally running at the same instant on different cores. Concurrency is about structuring a program to deal with many things; parallelism is about doing many things at once to go faster.

PointConcurrencyParallelism
IdeaMany tasks in progress, taking turnsMany tasks running at the same instant
Needs multiple coresNoYes
Main goalResponsiveness, handling many requestsThroughput on CPU-heavy work
ExampleA server juggling 500 requests on 8 coresSumming a huge array in 8 chunks on 8 cores

CPU-bound vs I/O-bound work

This distinction decides almost every design choice later (pool size, virtual threads). CPU-bound work keeps the core busy computing: sorting, encryption, image processing. More threads than cores will not make it faster. I/O-bound work mostly waits: database queries, REST calls, file and network reads. You can run many more threads than cores because most of them are sleeping at any moment.

A first look: two threads, one program

public class FirstThreads {
    public static void main(String[] args) throws InterruptedException {
        int cores = Runtime.getRuntime().availableProcessors();
        System.out.println("Cores available: " + cores);

        Thread t = new Thread(() -> System.out.println(
                "Hello from " + Thread.currentThread().getName()));
        t.start();
        t.join();   // wait for t to finish
        System.out.println("Hello from " + Thread.currentThread().getName());
    }
}

Rule: threads share the heap, not the stack

Local variables and method parameters are thread-confined and need no protection. Anything reachable from two threads — a field, a static, a collection, an object passed to a task — needs a thread-safety plan (see thread-safety strategies).

Edge cases and limits

  • More threads is not always faster. For CPU-bound work, threads beyond the core count only add context-switch cost. Every thread also uses memory for its stack, so a few thousand platform threads can cause OutOfMemoryError: unable to create native thread.
  • Not every task can be split. Amdahl's law says the part that must run in sequence limits the speed-up: if 20% of a job is sequential, even infinite cores give at most 5× speed-up.
  • The JVM itself runs extra threads (garbage collector, JIT compiler), so "one thread" programs are rarely truly single-threaded.

Interview: "Process vs thread? Concurrency vs parallelism?"

  • Process: own memory, heavy, isolated, talks via IPC. Thread: shares the process heap, own stack, light, talks through shared objects.
  • Concurrency is dealing with many tasks by interleaving; parallelism is running them simultaneously on multiple cores. You can have one without the other.
  • Threads help in two ways: use more cores for CPU work, and overlap waiting for I/O work.
  • Shared heap is the benefit and the danger — it is the root of race conditions.

Creating and controlling threads: Thread, Runnable, join, sleep, daemon, interrupt

You describe the work as a Runnable, hand it to a Thread, and call start(); join() waits for it, sleep() pauses it, and interrupt() politely asks it to stop.

There are three classic ways to give a thread its work. All end in the same place: the thread runs a run() method.

Three ways to create a thread

public class CreateThreads {

    // 1. Extend Thread (works, but ties the task to the thread type)
    static class Worker extends Thread {
        @Override
        public void run() {
            System.out.println("Extending Thread: " + getName());
        }
    }

    // 2. Implement Runnable (the task is a separate object; reusable with pools)
    static class EmailTask implements Runnable {
        @Override
        public void run() {
            System.out.println("Runnable class: " + Thread.currentThread().getName());
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Worker();
        Thread t2 = new Thread(new EmailTask(), "email-sender");
        // 3. Lambda (Runnable is a functional interface) - the usual choice today
        Thread t3 = new Thread(
                () -> System.out.println("Lambda: " + Thread.currentThread().getName()),
                "report-builder");

        t1.start();
        t2.start();
        t3.start();
        t1.join();
        t2.join();
        t3.join();
        System.out.println("All done");
    }
}

Runnable class: email-sender

Prefer Runnable (or a lambda) over extending Thread. Java has single inheritance, so extending Thread uses up your one superclass. A Runnable is just a task: it can later be handed to an executor, run by a virtual thread, or tested directly. Extending Thread mixes "what to do" with "how to run it".

start() vs run() — the classic question

start() asks the JVM to create a new thread of execution, which then calls run(). Calling run() yourself is just a normal method call on the current thread — no new thread exists.

Daemon threads

The JVM exits when all non-daemon (user) threads have finished. A daemon thread is a background helper that does not keep the JVM alive: when the last user thread ends, daemon threads are stopped abruptly, with no finally blocks guaranteed to run. Garbage collection and many timers are daemon threads. Use daemons for housekeeping that can safely vanish (cache cleaners, heartbeats), never for work that must finish, such as writing a file or a payment record. A new thread inherits the daemon status of the thread that created it.

Thread ticker = new Thread(() -> {
    while (true) {
        System.out.println("tick");
        try { Thread.sleep(300); } catch (InterruptedException e) { return; }
    }
});

Priorities — and why not to rely on them

setPriority(Thread.MAX_PRIORITY) (10) or MIN_PRIORITY (1) is only a hint. How it maps to the operating system differs between Linux, Windows and macOS, and some systems ignore it. Never use priorities for correctness. If task A must run before task B, use join(), a latch or a CompletableFuture chain.

Interruption done right

Java has no safe way to force-kill a thread (Thread.stop() was deprecated for removal and is disabled in modern Java). Instead Java uses cooperative cancellation: you call t.interrupt(), which sets the thread's interrupt flag. The thread must notice and stop on its own.

  • If the thread is blocked in sleep, wait, join or a blocking queue call, it wakes up and throws InterruptedException. Throwing it clears the flag.
  • If the thread is busy computing, nothing happens until it checks Thread.currentThread().isInterrupted() itself.
  • isInterrupted() reads the flag; the static Thread.interrupted() reads and clears it.
public class InterruptDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            int processed = 0;
            while (!Thread.currentThread().isInterrupted()) {   // check the flag
                try {
                    Thread.sleep(100);                           // simulate work
                    processed++;
                } catch (InterruptedException e) {
                    // sleep() cleared the flag. Restore it, then stop.
                    Thread.currentThread().interrupt();
                }
            }
            System.out.println("Stopping cleanly after " + processed + " items");
        }, "batch-worker");

        worker.start();
        Thread.sleep(350);
        worker.interrupt();   // ask politely
        worker.join();
    }
}
Stopping cleanly after 3 items

Wrong: swallows the interrupt

try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    // ignored: flag is lost, caller never
    // learns that a stop was requested
}

Right: restore the flag (or rethrow)

try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;   // stop what you were doing
}

Rule: never swallow InterruptedException

Either declare it (throws InterruptedException) and let the caller handle it, or catch it, call Thread.currentThread().interrupt() to restore the flag, and stop the work. A swallowed interrupt makes a pool or application impossible to shut down cleanly.

Exceptions and edge cases

  • IllegalThreadStateException — calling start() twice, or setDaemon() after start().
  • An exception thrown in run() kills only that thread; main never sees it. The default handler prints the stack trace to System.err. Install your own with t.setUncaughtExceptionHandler((th, ex) -> log.error(th.getName(), ex)). Tasks in executors behave differently (see Callable and Future).
  • join() on a thread that was never started returns at once.
  • sleep(ms) never releases locks; Object.wait() does.
  • Thread.sleep(ms) is not an exact timer — it sleeps at least roughly that long.

Mistake: calling run() and expecting parallel work

Code review classic: new Thread(task).run(); works, prints the right output and is completely sequential. Always start().

Real projects

You rarely write new Thread(...) in production. Raw threads are for demos, tests and rare background loops; business code uses executors (next articles), Spring's @Async, or virtual threads. But you must understand the primitives, because pools, frameworks and thread dumps are built from them.

Interview: "start() vs run()", "Runnable vs Thread", "How do you stop a thread?"

  • start() creates a new thread that calls run(); run() alone is a plain call. start() twice throws IllegalThreadStateException.
  • Prefer Runnable: separates task from thread, allows another superclass, works with executors.
  • Stop a thread with interruption: set a flag with interrupt(), check isInterrupted(), handle InterruptedException by restoring the flag and exiting. Never Thread.stop().
  • Daemon threads do not stop the JVM from exiting and may be killed mid-work.

Thread lifecycle and states

A Java thread is always in one of six states — NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING or TERMINATED — and specific method calls move it between them.

The enum Thread.State defines exactly six states, and thread.getState() returns the current one. This is a snapshot for monitoring; do not build logic on it because it can change right after you read it.

StateMeaningHow a thread gets there

BLOCKEDWaiting to enter a synchronized block because another thread holds the monitorEntering a locked synchronized block
WAITINGWaiting indefinitely for another thread's actionObject.wait(), t.join(), LockSupport.park() (used by locks and queues)
TIMED_WAITINGWaiting with a time limitsleep(ms), wait(ms), join(ms), tryLock(time), poll(time)
TERMINATEDFinishedrun() returned or threw

Watching the states

public class StatesDemo {
    public static void main(String[] args) throws Exception {
        Object lock = new Object();
        Thread t = new Thread(() -> {
            synchronized (lock) {                 // main holds the lock first
                try { Thread.sleep(300); } catch (InterruptedException e) { }
            }
        });
        System.out.println("1. " + t.getState());       // NEW

        synchronized (lock) {
            t.start();
            Thread.sleep(100);
            System.out.println("2. " + t.getState());   // BLOCKED: needs lock
        }                                                // main releases the lock

        Thread.sleep(100);
        System.out.println("3. " + t.getState());       // TIMED_WAITING in sleep

        t.join();
        System.out.println("4. " + t.getState());       // TERMINATED
    }
}

BLOCKED vs WAITING — the confusing pair

BLOCKED means "I want a synchronized lock and someone else has it." WAITING means "I gave up on running until another thread signals me." A thread that calls wait() goes to WAITING; after notify() it moves to BLOCKED (it must re-acquire the monitor) and then to RUNNABLE. Threads waiting on a ReentrantLock show as WAITING, not BLOCKED, because those locks use park(). In a thread dump, many threads BLOCKED on the same monitor means a hot lock; many threads WAITING in a pool means idle workers.

Rule: a thread ends once and cannot restart

After TERMINATED you cannot call start() again. Create a new Thread, or better, submit tasks to a pool that reuses threads.

Edge cases

  • A thread reading from a socket or file is RUNNABLE in Java terms even though it is really waiting inside the operating system.
  • Thread.sleep(0) and yield() keep the thread RUNNABLE.
  • interrupt() on a WAITING or TIMED_WAITING thread wakes it with InterruptedException. On a BLOCKED thread it only sets the flag; the thread keeps waiting for the lock.

start() vs run(), and what start() really does

Calling t.start() asks the JVM to create a new operating-system thread (for a platform thread), which then calls run(). Calling t.run() directly is just an ordinary method call: it runs in the caller's thread, no new thread exists, and the state stays NEW. This is a classic interview trap and a classic bug.

Thread t = new Thread(() -> System.out.println("in " + Thread.currentThread().getName()));
t.run();                        // prints "in main"      (no new thread)
t.start();                      // prints "in Thread-0"  (a real new thread)
t.join();
t.start();                      // IllegalThreadStateException: it already ran

Calling start() a second time throws IllegalThreadStateException whatever the state (even if the thread is still running). The only legal move out of NEW is one start().

Thread dumps: reading states in production

When an application hangs or is slow, take a thread dump with jstack <pid> or jcmd <pid> Thread.print (or press Ctrl+Break on Windows). Each thread prints its name, its state and its stack. The state line looks like this:

java.lang.Thread.State: RUNNABLE
java.lang.Thread.State: BLOCKED (on object monitor)
java.lang.Thread.State: WAITING (parking)
java.lang.Thread.State: TIMED_WAITING (sleeping)

How to read it: many threads BLOCKED on the same lock address means lock contention; threads WAITING (parking) inside a ThreadPoolExecutor are idle workers waiting for tasks; a thread RUNNABLE at 100% CPU in the same method across dumps points to a busy loop. Two threads BLOCKED on each other's locks form a deadlock, and the JVM prints "Found one Java-level deadlock" at the end of the dump.

Common mistakes

  • Calling run() instead of start() and wondering why there is no parallelism.
  • Calling start() twice, or trying to restart a finished thread.
  • Using getState() or isAlive() to decide what to do next. The answer is stale the moment you get it; coordinate with join(), a latch or a Future instead.
  • Treating sleep() as a way to wait for another thread to finish. Use join(); sleeping gives only a guess about timing.

More edge cases and exceptions

  • IllegalThreadStateException — start() on a thread that was started before.
  • IllegalMonitorStateException — wait/notify without owning the monitor.
  • InterruptedException — thrown inside sleep, wait or join when the thread is interrupted. The interrupt flag is cleared when this exception is thrown, so catch blocks that swallow it should restore it with Thread.currentThread().interrupt().
  • A thread can be TERMINATED because run() threw an uncaught exception. The thread dies, the stack trace goes to the thread's uncaught-exception handler (stderr by default), and other threads carry on.
  • Daemon threads (setDaemon(true), before start()) do not keep the JVM alive. When the last non-daemon thread ends, the JVM exits even if daemon threads are still RUNNABLE.
  • Thread pools reuse threads, so a worker moves between RUNNABLE and WAITING many times and reaches TERMINATED only when the pool shuts down. See executors.

In real projects

You rarely call getState() in business code. You read states in thread dumps, in monitoring tools (VisualVM, Java Flight Recorder, APM dashboards), and in post-mortems of hung services. Name your threads (new Thread(task, "invoice-sync") or a thread factory) so the dump is readable; the default names Thread-0, Thread-1 tell you nothing. Related: creating threads and synchronized.

Interview: "Explain the thread lifecycle"

  • Name all six states and draw NEW → RUNNABLE → (BLOCKED / WAITING / TIMED_WAITING) → RUNNABLE → TERMINATED.
  • Give the trigger for each: start(), monitor contention, wait()/join(), sleep(), end of run().
  • Say that Java has no separate "running" state; RUNNABLE covers running and ready.
  • Mention that sleep() keeps locks and wait() releases them.

The Java Memory Model: atomicity, visibility, ordering and happens-before

Threads can disagree about what memory contains, so correct concurrent code must guarantee atomicity (no half-finished updates), visibility (writes are seen by others) and ordering (steps are not reordered unsafely) — and the happens-before rules tell you when that is guaranteed.

It is easy to imagine memory as one board that all threads read and write instantly. Real hardware is different. Each core has fast private caches and registers, and the CPU and the JIT compiler are free to reorder instructions for speed as long as a single thread cannot tell the difference. With several threads, you can tell. The Java Memory Model (JMM) is the specification of what values a read may see when threads share data. It gives you three properties to think about.

Atomicity
An operation is atomic if it happens completely or not at all, with no other thread able to see it half-done. Reads and writes of references and of most primitives are atomic. Reads and writes of long and double are guaranteed atomic only if the variable is volatile, although current 64-bit JVMs do it atomically anyway. Compound actions such as count++ are not atomic.
Visibility
When thread A writes a value, when does thread B see it? Without a guarantee, B may keep reading a stale value from its cache or register, possibly forever.
Ordering
The compiler and CPU may reorder independent statements. Another thread can observe writes in a different order from the one in your source code.

Why count++ is not atomic

One line of Java becomes three steps: read the value, add one, write it back. This is a read-modify-write sequence. Two threads can interleave between the steps and one update is lost.

Visibility problem in real code

public class VisibilityBug {
    static boolean ready = false;      // not volatile

    public static void main(String[] args) throws InterruptedException {
        Thread reader = new Thread(() -> {
            while (!ready) { }          // may spin forever: never re-reads memory
            System.out.println("Reader saw ready = true");
        });
        reader.start();
        Thread.sleep(500);
        ready = true;                   // writer thread sets the flag
        System.out.println("Main set ready = true");
    }
}

The JIT compiler may hoist the read of ready out of the loop, because nothing in this thread changes it. Making ready volatile fixes it (see volatile and atomics).

Happens-before in simple words

The JMM defines a relation called happens-before. If action A happens-before action B, then everything A did (all writes) is guaranteed to be visible to B and ordered before it. If there is no happens-before relation between a write and a read of the same variable, the read may see old or new data — this is called a data race. You do not need to memorise the full specification; know these rules:

RuleMeaning in plain words
Program orderWithin one thread, each statement happens-before the next one (as that thread sees it)
Monitor lockAn unlock of a monitor happens-before every later lock of the same monitor. So everything written inside synchronized is visible to the next thread that enters it
volatileA write to a volatile variable happens-before every later read of that variable
Thread startEverything before t.start() happens-before the first action in t
Thread joinEverything in t happens-before another thread returns from t.join()
TransitivityIf A happens-before B and B happens-before C, then A happens-before C
Concurrent utilitiesSubmitting a task to an executor, a Future.get(), putting an element into a concurrent collection before another thread takes it, CountDownLatch.countDown() before await() returns — all create happens-before edges

Practical meaning: any time you use a lock, a volatile field, an atomic class, a concurrent collection or an executor correctly, the visibility and ordering problems are handled for you. Problems appear only when threads share plain fields with no such link.

Safe publication

Publishing an object means making it reachable by other threads. Safe publication means the publication creates a happens-before edge, so other threads see a fully constructed object. Safe ways: store it in a volatile or final field, store it in a field accessed under a lock, put it in a concurrent collection, or pass it to a task submitted to an executor. A reference stored in a plain field can show another thread a half-built object.

Rule: shared mutable data needs a happens-before edge

For every variable that one thread writes and another reads, ensure a lock, a volatile, an atomic, a concurrent collection or a thread-join/executor hand-off links the two. Otherwise your program has a data race, and its behaviour is not defined by "what the code looks like".

Edge cases

  • final fields get a special guarantee: once the constructor finishes normally, any thread that sees the object sees the correct values of its final fields, even if the object was published unsafely — provided this did not escape during construction. This is one reason immutable objects are thread-safe.
  • Escaping this: starting a thread or registering a listener inside a constructor lets another thread see the object before it is fully built.
  • Data races are timing-dependent. A test may pass a thousand times and fail in production on a machine with more cores, because the bug depended on the hardware and the JIT.

Interview: "What is the Java Memory Model? What is happens-before?"

  • The JMM specifies when one thread's writes are visible to another and what reorderings are allowed.
  • Three concerns: atomicity, visibility, ordering. Locks give all three; volatile gives visibility and ordering but not atomicity of compound actions; atomics give atomic single-variable updates.
  • Happens-before: if A happens-before B, A's effects are visible to B. Sources: unlock → lock, volatile write → read, start, join, executor hand-off.
  • count++ is read–modify–write, so concurrent increments can be lost.

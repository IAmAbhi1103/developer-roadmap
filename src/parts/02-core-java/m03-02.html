try, catch and finally: rules and flow

Put the code that can fail in try, handle specific failures in catch blocks ordered from most specific to most general, and put cleanup that must always happen in finally.

A try statement marks a region of code whose exceptions you want to deal with. A catch block (also called a handler) says which exception types you handle and how. A finally block holds code that must run whether the try block succeeded or failed — releasing a lock, closing a resource, clearing a thread-local value.

try {
    // code that may throw
} catch (NoSuchFileException e) {          // most specific first
    // handle a missing file
} catch (IOException e) {                  // then more general
    // handle any other I/O problem
} finally {
    // always runs: cleanup
}

Structure rules

  • A try needs at least one catch or a finally (or resource declarations — see try-with-resources). A bare try { } fails with 'try' without 'catch', 'finally' or resource declarations.
  • You may have any number of catch blocks and at most one finally block, which comes last.
  • At most one catch block runs: the first one, from top to bottom, whose type matches the exception (the exception is an instance of that type).
  • Variables declared inside the try block are not visible in catch or finally. If finally needs a variable, declare it before the try.
  • The catch parameter (e) exists only inside its own catch block.

The four possible paths

Example: all three main paths

public class TryCatchFlow {
    public static void main(String[] args) {
        System.out.println("Result: " + parseQuantity("3"));
        System.out.println("Result: " + parseQuantity("three"));
        try {
            System.out.println("Result: " + parseQuantity(null));
        } catch (NullPointerException e) {
            System.out.println("main caught: " + e.getClass().getSimpleName());
        }
    }

    static int parseQuantity(String input) {
        System.out.println("-- parsing " + input);
        try {
            int quantity = Integer.parseInt(input.trim());   // NPE if input is null
            System.out.println("try: parsed");
            return quantity;
        } catch (NumberFormatException e) {
            System.out.println("catch: not a number, using 1");
            return 1;
        } finally {
            System.out.println("finally: runs every time");
        }
    }
}

-- parsing three

Three things to notice. First, finally runs even though the try and catch blocks execute return — it runs before the method actually returns. Second, with "three" the line try: parsed is skipped, because the exception jumped straight to the catch. Third, with null the exception is a NullPointerException, which the catch block does not match, so finally runs and the exception travels on to main.

Catch order: specific before general

Because the first matching catch wins, a general type placed first would catch everything and the specific block below it could never run. Java treats that unreachable handler as a compile error.

Wrong: general first — does not compile

try {
    Files.readString(Path.of("a.txt"));
} catch (IOException e) {
    System.out.println("I/O problem");
} catch (NoSuchFileException e) {   // error: exception
    System.out.println("missing");  // NoSuchFileException has
}                                   // already been caught

Right: subclass first, superclass last

try {
    Files.readString(Path.of("a.txt"));
} catch (NoSuchFileException e) {
    System.out.println("missing");
} catch (IOException e) {
    System.out.println("I/O problem");
}

The order only matters between types that are related by inheritance. Unrelated types, such as NumberFormatException and IOException, can appear in any order.

Multi-catch (Java 7+)

When two exceptions need the same handling, list them in one catch with | instead of copying the block.

public class MultiOk {
    public static void main(String[] args) {
        for (String s : new String[] {"4", "zero", "0"}) {
            try {
                System.out.println("100 / " + s + " = " + 100 / Integer.parseInt(s));
            } catch (NumberFormatException | ArithmeticException e) {
                System.out.println("Cannot divide by '" + s + "': " + e);
            }
        }
    }
}
100 / 4 = 25
Cannot divide by 'zero': java.lang.NumberFormatException: For input string: "zero"
Cannot divide by '0': java.lang.ArithmeticException: / by zero

Rules of multi-catch

  • The parameter is implicitly final. Assigning to it fails with multi-catch parameter e may not be assigned.
  • The alternatives cannot be subclasses of each other. catch (IOException | NoSuchFileException e) fails with Alternatives in a multi-catch statement cannot be related by subclassing — just catch IOException.
  • Inside the block, you can only use methods of the closest common supertype of the alternatives (here RuntimeException), because e could be either type.

Nested try

A try statement can sit inside a try, catch or finally block. An exception that the inner statement does not catch moves outwards to the outer one.

static int readQuantity(Path file) {
    try {
        String text = Files.readString(file).strip();
        try {
            return Integer.parseInt(text);
        } catch (NumberFormatException e) {          // inner: bad content
            System.out.println("Not a number in " + file + ": " + text);
            return 0;
        }
    } catch (IOException e) {                        // outer: cannot read the file
        System.out.println("Cannot read " + file + ": " + e);
        return 0;
    }
}

Nested try blocks work, but they are hard to read. Usually it is cleaner to move the inner part into its own method, such as parseOrZero(String text), and call it from a single try statement.

finally: when it runs, and when it does not

The finally block runs when the try block completes normally, when it throws (caught or not), and when try or catch leave early with return, break or continue. That is why it is the place for cleanup. The classic example is releasing a lock:

private final ReentrantLock lock = new ReentrantLock();

public void transfer(Account from, Account to, BigDecimal amount) {
    lock.lock();              // acquire BEFORE the try
    try {
        from.withdraw(amount);
        to.deposit(amount);
    } finally {
        lock.unlock();        // released even if withdraw() throws
    }
}

Lock does not implement AutoCloseable, so try-with-resources cannot help here — this try/finally idiom is still the standard way.

Exceptions: when finally does NOT run

  • System.exit() (or Runtime.halt()) is called inside try or catch. The JVM starts shutting down and the rest of the thread's code, including finally, never runs.
  • The JVM process dies: a native crash, kill -9, a power cut, the container being killed.
  • The try block never finishes: an infinite loop or a thread stuck forever in a deadlock.
  • The code runs in a daemon thread and the JVM exits because all non-daemon threads have finished. Daemon threads are abandoned; their finally blocks do not run.
public class ExitFinally {
    public static void main(String[] args) {
        try {
            System.out.println("try");
            System.exit(0);
        } finally {
            System.out.println("finally");     // never printed
        }
    }
}
try

Shutdown hooks registered with Runtime.getRuntime().addShutdownHook(...) do run on System.exit(); finally blocks of the exiting thread do not.

Mistake: an exception thrown from finally hides the original

If the try block throws exception A and the finally block then throws exception B, the caller sees only B — A is lost completely. This happens easily when finally calls close() on a resource that also fails. Use try-with-resources, which keeps the close failure as a suppressed exception instead. A return in finally is even worse: it discards the exception silently (see the puzzles).

Conventions

  • Keep try blocks small: wrap only the statements that can throw what you catch, so it is clear what failed.
  • Catch the most specific type you can handle; let the rest propagate.
  • Use try-with-resources for anything closeable; use finally for other cleanup (locks, resetting state, clearing logging context).
  • Never leave a catch block empty. If ignoring really is correct, write a comment saying why and name the variable ignored (Java 22+ also lets you write catch (IOException _) with an unnamed variable).

Interview: quick-fire questions on try/catch/finally

  • Can we have try without catch? Yes: try-finally, or try-with-resources.
  • Can more than one catch block run? No — only the first matching one.
  • Why must subclasses be caught first? The superclass handler would catch them first, making the subclass handler unreachable — a compile error.
  • Does finally run if try has a return? Yes, before the method returns.
  • When does finally not run? System.exit(), JVM crash/kill, a try block that never ends, daemon threads at JVM exit.

finally and return: output-prediction puzzles

The return value is saved before finally runs, so finally can change a returned object's contents but not a returned primitive or the returned reference; and a return or throw inside finally overrides everything, including a pending exception.

Interviewers love finally puzzles because they test whether you really understand the order of execution. They all become easy once you know how the compiler implements finally.

How javac implements finally

There is no "finally" instruction in bytecode. The compiler copies the finally code into every exit path of the try and catch blocks: the normal exit, each return, and an extra hidden handler that catches any Throwable, runs the finally code, and rethrows. For a return expr; the compiler first evaluates expr and stores the result in a hidden local variable, then runs the finally code, then returns the stored value.

static int puzzle2() {
    int x = 10;
    try {
        return x;
    } finally {
        x = 20;
    }
}
 0: bipush 10
 2: istore_0      // x = 10
 3: iload_0
 4: istore_1      // hidden slot 1 = x   (the return value is saved here)
 5: bipush 20
 7: istore_0      // finally code: x = 20
 8: iload_1
 9: ireturn       // return the SAVED value: 10
10: astore_2      // hidden catch-any handler: save the exception
11: bipush 20
13: istore_0      // finally code copied again
14: aload_2
15: athrow        // rethrow the saved exception

With that picture in mind, each puzzle below is mechanical: evaluate the return expression, save it, run finally, then return the saved value — unless finally itself returns or throws. Try each one before opening the answer.

Puzzle 1: return inside try

static int puzzle1() {
    try {
        System.out.println("try");
        return 1;
    } finally {
        System.out.println("finally");
    }
}
// main: System.out.println("P1 -> " + puzzle1());
What does it print? 
try
finally
P1 -> 1

finally runs before the method returns, so "finally" is printed before main receives the value 1 and prints it.

Puzzle 2: changing a primitive in finally

static int puzzle2() {
    int x = 10;
    try {
        return x;
    } finally {
        x = 20;
    }
}
Does it return 10 or 20?

10. The value of x was copied into the hidden slot when return x ran. Changing x afterwards does not change the copy (see the bytecode above).

Puzzle 3: changing an object in finally

static StringBuilder puzzle3() {
    StringBuilder sb = new StringBuilder("Hello");
    try {
        return sb;
    } finally {
        sb.append(" World");
        sb = null;
    }
}
// main: System.out.println("P3 -> " + puzzle3());
Does it print "Hello", "Hello World" or "null"? 
P3 -> Hello World

The saved return value is a copy of the reference, which still points to the same StringBuilder object. append changes that object, so the caller sees "Hello World". sb = null changes only the local variable, not the saved copy, so the method does not return null. Same rule as Java's pass-by-value for references.

Puzzle 4: return in both try and finally

static int puzzle4() {
    try {
        return 1;
    } finally {
        return 2;
    }
}
What is returned?

2. The try block saves 1 and runs finally, but finally executes its own return 2, which completes the method. The saved 1 is thrown away. Compiling with javac -Xlint:finally warns: finally clause cannot complete normally.

Puzzle 5: an exception and a return in finally

static int puzzle5() {
    try {
        throw new IllegalStateException("boom");
    } finally {
        return 42;
    }
}
// main: System.out.println("P5 -> " + puzzle5());
Does main see the exception? 
P5 -> 42

No. The hidden catch-any handler saves the exception and runs the finally code — but that code returns, so the athrow that would rethrow the exception is never reached. The exception is silently swallowed: no log, no stack trace. This is the main reason for the rule "never return from finally".

Puzzle 6: three exceptions

static void puzzle6() {
    try {
        throw new IllegalStateException("from try");
    } catch (IllegalStateException e) {
        throw new IllegalArgumentException("from catch");
    } finally {
        throw new UnsupportedOperationException("from finally");
    }
}
// main: try { puzzle6(); } catch (RuntimeException e) { System.out.println("P6 -> " + e); }
Which exception reaches main? 
P6 -> java.lang.UnsupportedOperationException: from finally

The try exception is caught. The catch block throws a new exception, so finally runs before it can leave. finally throws a third exception, which replaces the pending one. Only the last one escapes; the other two are lost (not even attached as suppressed).

Puzzle 7: finally inside a loop

static void puzzle7() {
    for (int i = 1; i <= 3; i++) {
        try {
            if (i == 2) continue;
            if (i == 3) break;
            System.out.println("body " + i);
        } finally {
            System.out.println("finally " + i);
        }
    }
    System.out.println("after loop");
}
What does it print? 
body 1
finally 1
finally 2
finally 3
after loop

continue and break leave the try block, so finally runs on each exit: for i = 2 before continuing, for i = 3 before breaking out of the loop.

Puzzle 8: return from catch

static String puzzle8() {
    try {
        Integer.parseInt("x");
        return "try";
    } catch (NumberFormatException e) {
        return "catch";
    } finally {
        System.out.println("finally runs first");
    }
}
// main: System.out.println("P8 -> " + puzzle8());
What does it print? 
finally runs first
P8 -> catch

The exception skips return "try". The catch block saves "catch" as the return value, finally prints its line, and then the saved value is returned.

Puzzle 9: side effects on a field

static int counter = 0;

static int puzzle9() {
    try {
        return ++counter;
    } finally {
        counter += 10;
    }
}
// main: System.out.println("P9 -> " + puzzle9() + ", counter = " + counter);
What are the returned value and the final counter? 
P9 -> 1, counter = 11

++counter makes counter 1 and saves 1 as the return value. finally then adds 10 to the field, so the field is 11, but the saved return value is still 1. String concatenation evaluates left to right, so puzzle9() runs before counter is read.

Rule: never return, throw, break or continue out of a finally block

Any of these makes the finally block "complete abruptly", which discards the pending return value or exception. Code reviewers and static analysis tools flag it; javac -Xlint:finally warns about it. Keep finally blocks short and limited to cleanup. If cleanup can itself throw, catch that inside finally (and log it), or use try-with-resources.

Interview: how to answer any finally puzzle

  1. Find which block exits first and how: normal end, return, or an exception.
  2. For a return, evaluate the expression now and remember the value (a primitive value or a reference).
  3. Run finally. If it returns or throws, that wins and the remembered value or exception is lost.
  4. Otherwise, return the remembered value or rethrow the remembered exception. Mention that objects can be mutated through the remembered reference.

try-with-resources and AutoCloseable

try-with-resources closes every resource declared in its header automatically, in reverse order, even when an exception is thrown, and keeps failures from close() as suppressed exceptions instead of losing the original one.

A resource is an object that holds something outside the JVM's memory that must be given back: an open file handle, a database connection, a network socket. The garbage collector does not close these for you in any predictable way. Forget to close them and you get a resource leak: after a few thousand requests the operating system refuses to open more files ("Too many open files"), or the database connection pool runs dry and every request starts timing out.

The problem with the old way

Before Java 7, correct cleanup looked like this:

BufferedReader reader = null;
try {
    reader = new BufferedReader(new FileReader("orders.csv"));
    return reader.readLine();
} finally {
    if (reader != null) {
        try {
            reader.close();
        } catch (IOException e) {
            // ignore? log? -- and the original exception may already be lost
        }
    }
}

It is long, easy to get wrong, and it has a hidden bug: if the body throws and then close() also throws, the close exception replaces the original one. You can see the original error vanish:

public class OldStyleLost {
    static class FlakyConnection implements AutoCloseable {
        @Override
        public void close() {
            throw new IllegalStateException("close failed");
        }
    }

    public static void main(String[] args) {
        try {
            FlakyConnection c = new FlakyConnection();
            try {
                throw new RuntimeException("query failed");    // the real problem
            } finally {
                c.close();                                     // throws, replacing it
            }
        } catch (RuntimeException e) {
            System.out.println("Caught: " + e.getMessage());
            System.out.println("Suppressed count: " + e.getSuppressed().length);
        }
    }
}
Caught: close failed
Suppressed count: 0

The log would say "close failed" and nobody would ever learn that the query failed.

The syntax

Declare the resources in parentheses after try. When the block ends — normally or with an exception — Java calls close() on each one.

import java.io.BufferedReader;
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

public class ErrorCounter {
    static long countErrors(Path log) throws IOException {
        try (BufferedReader reader = Files.newBufferedReader(log)) {
            long count = 0;
            String line;
            while ((line = reader.readLine()) != null) {
                if (line.contains("ERROR")) {
                    count++;
                }
            }
            return count;
        }   // reader.close() runs here, even if readLine() throws
    }

    public static void main(String[] args) throws IOException {
        Path log = Path.of("app.log");
        Files.write(log, List.of(
                "10:00:01 INFO  Order 101 placed",
                "10:00:02 ERROR Payment gateway timeout",
                "10:00:05 INFO  Order 102 placed",
                "10:00:09 ERROR Inventory service down"));
        System.out.println("Errors: " + countErrors(log));
    }
}
Errors: 2

The resource variable is implicitly final, and its scope is the try block. A try-with-resources statement may still have catch and finally blocks.

AutoCloseable vs Closeable

A resource must implement java.lang.AutoCloseable. Its older cousin java.io.Closeable was retrofitted to extend it, so every Closeable works too.

When you implement close() yourself, narrow the signature: an override may throw fewer exceptions, so public void close() with no throws clause spares your callers a pointless catch block.

Multiple resources and closing order

Separate resources with semicolons. They are opened left to right and closed in reverse order — the last opened is closed first, which is right because later resources often depend on earlier ones (a statement depends on its connection).

public class TwrOrder {
    static class Resource implements AutoCloseable {
        private final String name;

        Resource(String name) {
            this.name = name;
            System.out.println("open " + name);
        }

        @Override
        public void close() {
            System.out.println("close " + name);
        }
    }

    public static void main(String[] args) {
        try (Resource a = new Resource("A");
             Resource b = new Resource("B")) {
            System.out.println("body");
            throw new IllegalStateException("body failed");
        } catch (IllegalStateException e) {
            System.out.println("catch: " + e.getMessage());
        } finally {
            System.out.println("finally");
        }
    }
}

Rule: resources are closed before catch and finally run

The order is: open resources → body → close resources (reverse order) → matching catch → finally. So inside catch and finally the resources are already closed — you cannot use them there.

If opening a resource fails, the ones already opened are still closed, and the failed one is not (it was never assigned):

close A
catch: cannot open B

Suppressed exceptions

When the body throws exception A and close() then throws exception B, try-with-resources keeps A as the main exception and attaches B to it with A.addSuppressed(B). Nothing is lost. You can read the attached exceptions with getSuppressed(), and the stack trace prints them under Suppressed:.

public class SuppressedDemo {
    static class FlakyConnection implements AutoCloseable {
        @Override
        public void close() {
            throw new IllegalStateException("close failed");
        }
    }

    public static void main(String[] args) {
        try (FlakyConnection c = new FlakyConnection()) {
            throw new RuntimeException("query failed");
        } catch (RuntimeException e) {
            System.out.println("Caught: " + e.getMessage());
            for (Throwable s : e.getSuppressed()) {
                System.out.println("Suppressed: " + s.getMessage());
            }
            e.printStackTrace();
        }
    }
}
Caught: query failed
Suppressed: close failed
java.lang.RuntimeException: query failed
    at SuppressedDemo.main(SuppressedDemo.java:11)
    Suppressed: java.lang.IllegalStateException: close failed
        at SuppressedDemo$FlakyConnection.close(SuppressedDemo.java:5)
        at SuppressedDemo.main(SuppressedDemo.java:10)

Compare with the old-style output above: the real problem ("query failed") is now the main exception. If only close() throws (the body succeeded), that close exception is simply thrown as the main exception.

Java 9: using an existing variable as a resource

Since Java 9 you can put an existing variable in the header, as long as it is final or effectively final (never reassigned). This is handy when the resource is a parameter.

static void copyLines(BufferedReader reader, BufferedWriter writer) throws IOException {
    try (reader; writer) {             // both closed at the end, writer first
        String line;
        while ((line = reader.readLine()) != null) {
            writer.write(line);
            writer.newLine();
        }
    }
}

If the variable is reassigned anywhere, compilation fails with variable reader used as a try-with-resources resource neither final nor effectively final.

Edge cases

  • A null resource is allowed. If the resource expression is null, the body runs and close() is simply skipped — no NullPointerException.
  • Only declared resources are closed. In try (var r = new BufferedReader(new FileReader(f))) only the outer reader is a resource; closing it closes the inner one too, because wrapper streams close what they wrap.
  • Not every cleanup is AutoCloseable. Lock is not; keep using try/finally with unlock().

What the compiler generates

The Java Language Specification defines try-with-resources as a translation into ordinary try/catch/finally. Simplified, for one resource:

final Resource r = open();
Throwable primary = null;
try {
    // body
} catch (Throwable t) {
    primary = t;
    throw t;
} finally {
    if (r != null) {
        if (primary != null) {
            try {
                r.close();
            } catch (Throwable closeFailure) {
                primary.addSuppressed(closeFailure);   // keep the original exception
            }
        } else {
            r.close();
        }
    }
}

Wrong: returning a resource that the try already closed

static Stream<String> lines(Path p) throws IOException {
    try (Stream<String> s = Files.lines(p)) {
        return s;          // closed on the way out
    }
}
// caller: lines(p).forEach(...) throws
// IllegalStateException: stream has already
// been operated upon or closed

Right: finish the work inside the try

static List<String> errorLines(Path p) throws IOException {
    try (Stream<String> s = Files.lines(p)) {
        return s.filter(l -> l.contains("ERROR"))
                .toList();   // fully read before close
    }
}

The same trap with a BufferedReader fails with java.io.IOException: Stream closed at the caller. If a method must hand an open resource to its caller, do not close it there — document that the caller owns it and must close it.

Real project: where you still write it by hand

  • Plain JDBC code: Connection, PreparedStatement and ResultSet in one header.
  • Files.lines, Files.list and Files.walk streams — they hold open file handles.
  • Spring Data repository methods that return Stream<T>: the stream keeps a database cursor open and must be closed (and used inside a transaction).
  • In typical Spring code you rarely close connections yourself — JdbcTemplate and JPA do it — but you still close the files, streams and clients you open.

Interview: "What is try-with-resources and what are suppressed exceptions?"

  • Java 7 feature: resources declared in the header are closed automatically in reverse order; the resource type must implement AutoCloseable.
  • If the body and close() both throw, the body's exception propagates and the close failure is attached as suppressed (getSuppressed()), unlike try/finally where the original was lost.
  • Resources are closed before catch/finally run. Java 9 allows effectively final variables in the header.
  • Closeable vs AutoCloseable: IOException vs Exception, and the idempotency requirement.

Terminal operations: collect, reduce, count, match and find

A terminal operation starts the pipeline and closes the stream: it returns a result (a collection, a number, an Optional, a boolean) or acts on every element, and the short-circuiting ones — findFirst, anyMatch and a few others — can stop before the end.

Intermediate operations only describe work. The terminal operation is the one that makes the stream run, and it decides what you get back: a list, a number, a yes/no answer, or nothing at all. A pipeline has exactly one, at the end. When it finishes, the stream is used up (see What a stream is).

forEach and forEachOrdered

forEach runs an action for each element and returns nothing. On a normal (sequential) stream it follows the encounter order. On a parallel stream it does not: elements can be handled in any order, by different threads. forEachOrdered keeps the encounter order even in parallel, but loses part of the speed-up.

emps.stream()
        .filter(e -> e.dept().equals("HR"))
        .forEach(e -> System.out.println(e.name() + " works in HR"));
Asha works in HR
John works in HR

Use forEach only for actions that leave the pipeline — printing, logging, sending an e-mail. Do not use it to build a result; that is the job of collect and toList(). If you already have a collection, list.forEach(...) works without .stream(), and map.forEach((key, value) -> ...) works on a map. Inside the lambda, return only leaves the lambda — it behaves like continue. You cannot break out of a forEach.

reduce: many values into one

reduce repeatedly combines two values into one. "Sum of a list" is the classic case: start at 0, add the first element, add the second, and so on. It has three forms:

FormReturnsUse it when
reduce(BinaryOperator<T> op)Optional<T>There is no natural starting value and the stream may be empty
reduce(T identity, BinaryOperator<T> op)TInput and result have the same type; the identity is the answer for an empty stream
reduce(U identity, BiFunction<U, T, U> accumulator, BinaryOperator<U> combiner)UThe result type differs from the element type; the combiner merges partial results of a parallel run

The identity is a value that changes nothing when combined with any element: 0 for addition, 1 for multiplication, "" for string concatenation. Form 1 has no identity, so it cannot answer for an empty stream — it returns an empty Optional instead.

List<Integer> nums = List.of(1, 2, 3, 4);

int sum = nums.stream().reduce(0, Integer::sum);                       // form 2
Optional<Integer> product = nums.stream().reduce((a, b) -> a * b);    // form 1
int totalLetters = List.of("java", "is", "fun").stream()               // form 3
        .reduce(0, (acc, word) -> acc + word.length(), Integer::sum);
System.out.println(sum + " " + product + " " + totalLetters);

// What happens step by step
int total = nums.stream().reduce(0, (acc, n) -> {
    System.out.println(acc + " + " + n);
    return acc + n;
});
System.out.println("total = " + total);
10 Optional[24] 9
0 + 1
1 + 2
3 + 3
6 + 4
total = 10

In the three-argument form the accumulator folds one element into the running result (a number plus a word's length). The combiner is only used when the stream runs in parallel: each thread reduces its own chunk, and the combiner joins the chunk results. Even if you never go parallel, supply a correct one.

Rule: a reduce function must be associative, stateless and consistent with the identity

  • Associative: (a op b) op c must equal a op (b op c). Addition, multiplication, max and string concatenation qualify. Subtraction and division do not, so reduce(0, (a, b) -> a - b) gives wrong answers in parallel.
  • Identity: op(identity, x) must equal x. Using 10 as the "starting value" of a sum is not an identity (see the next mistake).
  • Stateless: the function must not read or change outside variables.

Mistake: a starting value that is not an identity

nums.stream().reduce(10, Integer::sum) returns 20 on a sequential stream. On a parallel stream every chunk starts from 10. If the list splits into four one-element chunks, you get (10+1) + (10+2) + (10+3) + (10+4) = 50. Add the offset after the reduce: 10 + nums.stream().reduce(0, Integer::sum).

reduce vs collect

reduce builds one immutable value (a number, a maximum). collect uses a mutable container (a list, a map, a StringBuilder) that it fills in place. Building a container with reduce means creating a new one at every step — slow, and unsafe in parallel.

Wrong: string building with reduce

String s = emps.stream()
        .limit(2)
        .map(Employee::name)
        .reduce("", (a, b) -> a + ", " + b);
// ", Ravi, Asha"  (leading comma, and O(n²) copying)

Right: collect with joining

String s = emps.stream()
        .limit(2)
        .map(Employee::name)
        .collect(Collectors.joining(", "));
// "Ravi, Asha"

count, min and max

count() returns a long. min and max take a Comparator and return an Optional, because an empty stream has no smallest element.

long itCount = emps.stream().filter(e -> e.dept().equals("IT")).count();
String top = emps.stream()
        .max(Comparator.comparingInt(Employee::salary))
        .map(Employee::name).orElse("nobody");
String youngest = emps.stream()
        .min(Comparator.comparingInt(Employee::age))
        .map(Employee::name).orElse("nobody");

boolean anyAbove1Lakh = emps.stream().anyMatch(e -> e.salary() > 100000);
boolean allAdults = emps.stream().allMatch(e -> e.age() >= 18);
boolean noneInSales = emps.stream().noneMatch(e -> e.dept().equals("Sales"));
String firstHr = emps.stream()
        .filter(e -> e.dept().equals("HR"))
        .findFirst().map(Employee::name).orElse("nobody");

System.out.println(itCount + " " + top + " " + youngest);
System.out.println(anyAbove1Lakh + " " + allAdults + " " + noneInSales + " " + firstHr);

anyMatch, allMatch, noneMatch — and the empty stream

anyMatch(p)At least one element matchesfalseThe first match
allMatch(p)Every element matchestrueThe first non-match

On an empty stream, allMatch and noneMatch return true because nothing breaks the rule — logicians call this vacuous truth. It surprises people when a filter removes everything: orders.stream().filter(Order::isPaid).allMatch(Order::hasInvoice) is true even when there are no paid orders.

findFirst vs findAny

Both return an Optional with one element of the stream. findFirst() returns the first element in encounter order. findAny() may return any element: on a sequential stream it almost always returns the first, but on a parallel stream it is free to return whichever thread finishes first — and that is faster. Use findAny() when any match will do and the stream is parallel; otherwise use findFirst().

sum() of an empty stream is 0. max(), min() and average() return OptionalInt or OptionalDouble, because there is no sensible answer for no data. Read them with getAsInt(), orElse(...) or orElseThrow().

Edge cases

  • count() may skip your pipeline. Since Java 9, if the count can be worked out from the source alone (a List with no filter in between), the stream does not run — so peek and map never execute. A filter makes the size unknown, and then the pipeline runs. Do not put side effects in a stream that ends in count().
  • IntStream.sum() overflows silently. IntStream.of(Integer.MAX_VALUE, 1).sum() is -2147483648. Use mapToLong or asLongStream() when totals can be large: IntStream.of(Integer.MAX_VALUE, 1).asLongStream().sum() is 2147483648.
  • findFirst() and findAny() throw NullPointerException if the element they would return is null, because an Optional cannot hold null.
  • Optional.get() on an empty result throws NoSuchElementException: No value present.
  • A second terminal operation on the same stream throws IllegalStateException.
List<Integer> nums = List.of(1, 2, 3);
long a = nums.stream().peek(n -> System.out.println("peek " + n)).count();
System.out.println("count = " + a);
long b = nums.stream().filter(n -> n > 1)
        .peek(n -> System.out.println("peek " + n)).count();
System.out.println("count = " + b);
count = 3
peek 2
peek 3
count = 2

Mistakes: forEach to build a result, and get() without a check

Wrong: side effect on an outside list

List<String> names = new ArrayList<>();
emps.stream().forEach(e -> names.add(e.name()));
// breaks (lost updates) on a parallel stream

Right: let the stream build it

List<String> names = emps.stream()
        .map(Employee::name)
        .toList();

Wrong: NoSuchElementException

String n = emps.stream()
        .filter(e -> e.dept().equals("Sales"))
        .findFirst()
        .get().name();

Right: decide what "not found" means

String n = emps.stream()
        .filter(e -> e.dept().equals("Sales"))
        .findFirst()
        .map(Employee::name)
        .orElse("nobody");

Tip: prefer mapToInt(...).sum() over reduce(0, Integer::sum)

For sums, averages and maximums of numbers, map to a primitive stream first. It reads better, avoids boxing every number into an Integer, and gives you average() and summaryStatistics() for free: emps.stream().mapToInt(Employee::salary).sum().

Interview: "reduce vs collect?", "findFirst vs findAny?", "toList() vs Collectors.toList()?"

  • reduce combines elements into one immutable value; collect accumulates into a mutable container. Strings and collections belong to collect.
  • Three reduce forms: no identity (returns Optional), identity, and identity + accumulator + combiner. The function must be associative, and the identity a true identity, or parallel runs give wrong answers.
  • findFirst respects encounter order; findAny does not and is cheaper in parallel. Both return Optional.
  • toList() (Java 16) returns an unmodifiable list and allows nulls; Collectors.toList() returns a modifiable list in practice but promises nothing.
  • allMatch and noneMatch are true on an empty stream; anyMatch is false.
  • Short-circuiting terminals: anyMatch, allMatch, noneMatch, findFirst, findAny.

Collectors: toList, toSet, toMap, joining and summaries

A Collector is a ready-made recipe that turns the elements of a stream into one result — a list, a set, a map, a string, a count or a set of statistics — and you hand it to collect().

collect is the most important terminal operation. You give it a Collector, and the Collectors class (note the "s") offers dozens of ready-made ones. Under the hood a collector is made of four small functions:

Supplier
Creates an empty container, for example ArrayList::new.
Accumulator
Adds one element to the container, for example ArrayList::add.
Combiner
Merges two containers. Only a parallel stream needs it, because each thread fills its own container.
Finisher
An optional last step that converts the container into the final result, for example turning a StringJoiner into a String.

You can pass the first three directly to collect(supplier, accumulator, combiner). You will mostly use the ready-made collectors, but it helps to know that nothing magic is going on.

ArrayList<String> list = Stream.of("a", "b", "c")
        .collect(ArrayList::new, ArrayList::add, ArrayList::addAll);   // 3-argument form

// Writing a collector of your own is rare, but possible:
Collector<String, StringJoiner, String> csv = Collector.of(
        () -> new StringJoiner(","), StringJoiner::add,
        StringJoiner::merge, StringJoiner::toString);
System.out.println(list + " " + Stream.of("a", "b", "c").collect(csv));
[a, b, c] a,b,c

toMap: turning elements into key–value pairs

toMap needs two functions: one that computes the key from an element and one that computes the value. Function.identity() means "the element itself".

Map<String, Integer> salaryByName = emps.stream()
        .collect(Collectors.toMap(Employee::name, Employee::salary));
Map<String, Employee> byName = emps.stream()
        .collect(Collectors.toMap(Employee::name, Function.identity()));
System.out.println(salaryByName.get("Meera") + " " + byName.get("Asha").dept());
120000 HR

This works only because every name is unique. Use a key that repeats and toMap fails:

Map<String, String> bad = emps.stream()
        .collect(Collectors.toMap(Employee::dept, Employee::name));   // dept repeats
Exception in thread "main" java.lang.IllegalStateException:
    Duplicate key IT (attempted merging values Ravi and Kiran)

The fix is the three-argument form: a merge function that says what to do when two elements produce the same key. The four-argument form adds a map supplier so you choose the map type (TreeMap for sorted keys, LinkedHashMap for first-seen order).

// Total salary per department, keys sorted
Map<String, Integer> totalByDept = emps.stream()
        .collect(Collectors.toMap(Employee::dept, Employee::salary,
                Integer::sum, TreeMap::new));
System.out.println(totalByDept);

// Names per department as one string, in first-seen order
Map<String, String> namesByDept = emps.stream()
        .collect(Collectors.toMap(Employee::dept, Employee::name,
                (first, second) -> first + "," + second, LinkedHashMap::new));
System.out.println(namesByDept);

// Highest-paid employee per department
Map<String, Employee> topByDept = emps.stream()
        .collect(Collectors.toMap(Employee::dept, Function.identity(),
                BinaryOperator.maxBy(Comparator.comparingInt(Employee::salary)),
                TreeMap::new));
topByDept.forEach((dept, e) -> System.out.println(dept + " -> " + e.name()));

Rules for toMap

  • Two elements with the same key throw IllegalStateException unless you pass a merge function.
  • A null value throws NullPointerException, even though a plain HashMap allows null values. Replace nulls first or use Optional.
  • The two-argument and three-argument forms return a HashMap in practice, with no ordering. Use the four-argument form for TreeMap or LinkedHashMap.
  • The merge function receives (value already in the map, new value) and returns the value to keep.

Edge cases

  • Collectors.toList(), toSet() and toMap() give no guarantee about the exact type, mutability or thread-safety of what they return. Never cast the result to ArrayList or HashMap; ask for the type you need with toCollection or the map supplier.
  • counting() returns a Long, not an int. Compare it with > or == against a number literal (it unboxes), but never use == between two Long objects.
  • averagingInt on an empty stream returns 0.0, while IntStream.average() returns OptionalDouble.empty(). Pick the one that matches how you want to treat "no data".
  • toUnmodifiableList(), toUnmodifiableSet() and toUnmodifiableMap() (Java 10) throw NullPointerException for null elements.

Mistake: toMap on a key that can repeat

It works in a quick test with unique data and fails in production the day two rows share a key. Ask yourself "can two elements produce the same key?" Whenever the answer is yes or maybe, supply a merge function — or use groupingBy, which is built for repeating keys.

Wrong: fails on the second IT employee

Map<String, Integer> m = emps.stream()
        .collect(Collectors.toMap(
                Employee::dept, Employee::salary));

Right: merge duplicates explicitly

Map<String, Integer> m = emps.stream()
        .collect(Collectors.toMap(
                Employee::dept, Employee::salary, Integer::sum));

Conventions

  • For a list use .toList(); for everything else use collect(...).
  • When the order of a map or set matters (output, tests, JSON), pass TreeMap::new, LinkedHashMap::new or TreeSet::new explicitly.
  • Use method references and Function.identity() instead of e -> e.
  • Do not build maps by hand with forEach and map.put inside a pipeline; that is a side effect.

Tip: a static import shortens long pipelines

Many teams write import static java.util.stream.Collectors.*; so the code reads groupingBy(Employee::dept, counting()). It is fine in a file that uses collectors heavily. These notes keep the Collectors. prefix so you can see where each method comes from.

Interview: "How do you turn a list into a map? What if keys repeat?"

  • collect(Collectors.toMap(keyFn, valueFn)); duplicates throw IllegalStateException: Duplicate key ....
  • Fix with a merge function as the third argument; pick the map type with the fourth (LinkedHashMap::new keeps order, TreeMap::new sorts).
  • Null values throw NullPointerException.
  • "Join names with commas": map(...).collect(Collectors.joining(", ")).
  • "Get a sorted set": collect(Collectors.toCollection(TreeSet::new)).

groupingBy, partitioningBy and downstream collectors

groupingBy splits a stream into groups by a key (like SQL GROUP BY), partitioningBy splits it into exactly two groups (true and false), and a downstream collector decides what each group turns into: a list, a count, a sum, an average, a set of names.

Grouping is the stream version of SQL's GROUP BY. You give groupingBy a classifier — a function that returns the group key for each element — and it returns a Map from key to group. By default each group is a List. A downstream collector changes that: it receives all the elements of one group and turns them into the map's value.

This article uses the same eight employees as the terminal operations article: Ravi, Kiran, Meera and Anita in IT; Asha and John in HR; Kavya and Sanjay in Finance.

Nested grouping

Use another groupingBy as the downstream collector to group twice: first by department, then by an age band.

Map<String, Map<String, List<String>>> nested = emps.stream()
        .collect(Collectors.groupingBy(Employee::dept, TreeMap::new,
                Collectors.groupingBy(e -> e.age() >= 30 ? "30+" : "under 30",
                        TreeMap::new,
                        Collectors.mapping(Employee::name, Collectors.toList()))));
nested.forEach((dept, byAge) -> System.out.println(dept + " " + byAge));

HR {30+=[John], under 30=[Asha]}

partitioningBy: exactly two groups

partitioningBy(predicate) splits the stream into true and false. The map always has both keys, even if one group is empty — something groupingBy with a boolean classifier does not promise. It also accepts a downstream collector.

Map<Boolean, List<String>> split = emps.stream()
        .collect(Collectors.partitioningBy(e -> e.salary() >= 90000,
                Collectors.mapping(Employee::name, Collectors.toList())));
Map<Boolean, Long> counts = emps.stream()
        .collect(Collectors.partitioningBy(e -> e.salary() > 500000,
                Collectors.counting()));
System.out.println(split);
System.out.println(counts);
System.out.println(split.get(true).size());
{false=[Asha, John, Kavya, Anita], true=[Ravi, Kiran, Meera, Sanjay]}

filtering vs filter

Filtering before grouping removes elements, and a group with no survivors disappears. Collectors.filtering filters inside each group, so the group stays, with an empty result. Choose based on whether you want to see the empty groups.

Map<String, List<String>> before = emps.stream()
        .filter(e -> e.salary() > 85000)
        .collect(Collectors.groupingBy(Employee::dept, TreeMap::new,
                Collectors.mapping(Employee::name, Collectors.toList())));

Map<String, List<String>> inside = emps.stream()
        .collect(Collectors.groupingBy(Employee::dept, TreeMap::new,
                Collectors.filtering(e -> e.salary() > 85000,
                        Collectors.mapping(Employee::name, Collectors.toList()))));
System.out.println(before);
System.out.println(inside);
{Finance=[Sanjay], IT=[Ravi, Kiran, Meera]}
{Finance=[Sanjay], HR=[], IT=[Ravi, Kiran, Meera]}

flatMapping is the same idea for flatMap: each element contributes several values to its group. With orders that each contain items, groupingBy(Order::customer, flatMapping(o -> o.items().stream(), toSet())) gives every distinct item each customer ever bought.

collectingAndThen and teeing

collectingAndThen(downstream, finisher) runs a collector and then transforms its result — unwrap an Optional, or wrap a list as unmodifiable: collectingAndThen(Collectors.toList(), Collections::unmodifiableList).

teeing (Java 12) sends every element to two collectors in a single pass and then merges their two results. Use it when you need two answers from one stream.

double average = emps.stream().collect(Collectors.teeing(
        Collectors.summingInt(Employee::salary),
        Collectors.counting(),
        (sum, n) -> (double) sum / n));

record Range(int min, int max) {}
Range range = emps.stream().collect(Collectors.teeing(
        Collectors.minBy(Comparator.comparingInt(Employee::salary)),
        Collectors.maxBy(Comparator.comparingInt(Employee::salary)),
        (lo, hi) -> new Range(lo.get().salary(), hi.get().salary())));
System.out.println(average);
System.out.println(range);
85250.0

Rules

  • The classifier must never return null. It throws NullPointerException: element cannot be mapped to a null key. Return a placeholder such as "UNKNOWN" for missing values.
  • A group exists only if at least one element has that key; there are no empty groups (except with partitioningBy and filtering).
  • Inside one group the elements keep their encounter order.

Edge case: println and TreeMap::new do not mix

If you pass a whole collect(groupingBy(..., TreeMap::new, ...)) expression directly to System.out.println(...), javac can fail with error: method println in class PrintStream cannot be applied to given types ... inference variable R has incompatible bounds. println has many overloads, and the constructor reference leaves the compiler without enough type information to choose one. Assign the result to a typed variable first, as the examples here do.

Mistake: sorting a map you got from groupingBy

A HashMap has no order, so you cannot sort it in place. Choose the order when you build it (TreeMap::new sorts by key, LinkedHashMap::new keeps insertion order). To sort by value, stream the entries and sort them (see the interview recipes).

In real projects

Reports and dashboards: orders per status, revenue per day, errors per service, top product per category. When the data lives in a database, group in SQL (GROUP BY) — it is faster and uses less memory. Use stream grouping for data that is already in memory: results of several service calls, a CSV file, a cache.

Interview: "groupingBy vs partitioningBy?" and "What is a downstream collector?"

  • groupingBy: any number of groups by a key function; partitioningBy: exactly two groups by a predicate, both keys always present.
  • A downstream collector processes the elements of each group: counting(), summingInt, averagingInt, mapping, maxBy, another groupingBy.
  • Classic questions: "count per department" (counting), "average salary per department" (averagingInt), "names per department" (mapping), "highest paid per department" (maxBy + collectingAndThen, or toMap with BinaryOperator.maxBy).
  • Pass TreeMap::new as the map factory for sorted keys.
  • filtering inside a group keeps empty groups; filter before grouping drops them.
  • teeing (Java 12) gives two results from one pass.

Exception handling best practices

Handle an exception only where you can do something useful, keep the cause and the context, log it once, and never swallow it silently.

Knowing the syntax of try and catch is the easy part. What separates clean exception handling from the kind that wakes a team up at 3 a.m. is a set of habits. This article lists them in the order you will meet them in a real code review. Each one has a reason, and most have a wrong-and-right pair.

1. Never swallow an exception

An empty catch block makes the problem disappear while the program carries on in a broken state. The payment failed, but the code continues as if it had succeeded; the bug shows up three screens later and nobody can say why.

Wrong: the failure vanishes

try {
    inventory.reserve(orderId);
} catch (Exception e) {
    // TODO handle later
}

Right: decide something, or let it travel

try {
    inventory.reserve(orderId);
} catch (OutOfStockException e) {
    return OrderResult.rejected("Item is out of stock");   // a real decision
}
// every other failure propagates to the central handler

Printing is not handling either. e.printStackTrace() writes to System.err, outside your log format, level and files, and the code still continues as if all was well. If ignoring an exception is truly correct (best-effort cleanup, for example), say so in a comment and name the variable ignored.

2. Catch specific exceptions, not Exception or Throwable

catch (Exception e) also catches every RuntimeException: the NullPointerException or ClassCastException that is a bug you want to see, not hide. It catches InterruptedException, which you must not swallow (see item 10). catch (Throwable t) adds OutOfMemoryError and StackOverflowError. Name the exceptions you really know how to handle.

try {
    BigDecimal rate = rateClient.fetch(currency);
    return amount.multiply(rate);
} catch (RateServiceUnavailableException e) {      // I know how to handle this one:
    return amount.multiply(lastKnownRate(currency));   // fall back to the cached rate
}   // a NullPointerException here is a bug: let it surface

Exception: boundaries may catch everything

The outermost layer of a thread — a web request handler, a scheduled job, a message listener, a thread-pool task — must not die from one bad request. There, and only there, catch Exception (or even Throwable) to log it and move on to the next unit of work. In Spring Boot this is the @ExceptionHandler(Exception.class) method of your global handler.

3. Log or rethrow — not both

If every layer logs the exception and then rethrows it, one failure produces three or four log entries with the same stack trace. Searching the logs becomes a maze, and it looks as if three separate things failed.

Wrong: every layer logs and rethrows

// repository
catch (SQLException e) {
    log.error("DB error", e);
    throw new DataAccessFailureException("DB error", e);
}
// service
catch (DataAccessFailureException e) {
    log.error("Could not place order", e);
    throw new OrderFailedException("Could not place order", e);
}
// controller
catch (OrderFailedException e) {
    log.error("Request failed", e);
    return ResponseEntity.status(500).build();
}

Right: wrap with context, log once at the top

// repository: translate and keep the cause, no logging
catch (SQLException e) {
    throw new DataAccessFailureException("Could not save order " + id, e);
}
// service: no try/catch at all, the exception just flows
// controller advice: the one place that logs
log.error("Request failed", ex);

Rule of thumb: a catch block does one of three things — handle the exception completely, rethrow or wrap it, or log it because it is the final stop. Never two of them at once.

4. Log the exception itself, at the right level

Pass the exception object as the last argument to the logger so that the stack trace and all "Caused by" sections are printed — see the wrong-and-right pair in Reading a stack trace. Use ERROR for unexpected failures that need attention. An expected business outcome, such as "insufficient balance", is not an error of the system; log it at INFO or WARN, or not at all. Logging is covered in Module 8.

5. Write messages with context

The message is the first thing a person reads at 3 a.m. It should answer: what were we trying to do, with which values, and what was expected?

Poor messageUseful message
"Error""Could not save order 1042 for customer 77"
"Invalid input""Quantity must be between 1 and 10 but was 25"
"File not found""Config file not found: /etc/shop/app.properties"
"Null value""couponCode must not be null"

Never put secrets in a message: passwords, tokens, OTPs, full card numbers. Messages travel into logs, monitoring tools and sometimes API responses.

6. Fail fast: validate at the door

Check arguments at the top of a method and in constructors, so that a bad value is rejected where it enters instead of causing a confusing failure far away. An object should never exist in an invalid state.

import java.math.BigDecimal;
import java.util.Objects;

public record Money(BigDecimal amount, String currency) {
    public Money {                       // compact constructor: runs before the fields are set
        Objects.requireNonNull(amount, "amount must not be null");
        Objects.requireNonNull(currency, "currency must not be null");
        if (amount.signum() < 0) {
            throw new IllegalArgumentException("amount must not be negative: " + amount);
        }
    }
}

Note: assert is not validation

The assert statement is for internal invariants ("this can never be negative here"). It is switched off by default and only active with java -ea, so it must never validate arguments of public methods or user input. Use exceptions for that.

7. Use standard exceptions when they fit

Callers already understand the JDK's exceptions. Throw a standard one when it describes the situation exactly:

ExceptionThrow it whenExample
IllegalArgumentExceptionAn argument has a value the method cannot acceptage < 0, an unknown country code
IllegalStateExceptionThe object is in the wrong state for this callwithdrawing from a closed account; starting a job twice
NullPointerExceptionA required argument is null — via Objects.requireNonNulla constructor receiving a null name
UnsupportedOperationExceptionAn optional operation is not supported by this classadd on an immutable list
IndexOutOfBoundsExceptionAn index is outside the valid range Objects.checkIndex(i, size)
NoSuchElementExceptionThere is no (more) element to return iterator.next() at the end of the data

Do not throw RuntimeException, Exception or Throwable directly: they say nothing and cannot be caught selectively. Do not throw Error types such as OutOfMemoryError yourself either.

8. Do not use exceptions for normal control flow

An exception means "something unexpected happened". Using it as a normal way to leave a loop or to report an everyday outcome is slow (building the stack trace costs time), hard to read, and hides real bugs because the same catch block also swallows genuine errors.

Wrong: exceptions as flow

// finding the end of an array by crashing into it
try {
    int i = 0;
    while (true) {
        total += prices[i++];
    }
} catch (ArrayIndexOutOfBoundsException e) {
    // done
}

// "not found" is an everyday outcome, not an exception
try {
    return repository.getByEmail(email);
} catch (UserNotFoundException e) {
    return null;
}

Right: ordinary control flow

for (int price : prices) {
    total += price;
}

// the return type says "may be absent"
Optional<User> user = repository.findByEmail(email);

Catching a NumberFormatException to reject a bad input at the edge of the program is fine. Doing it millions of times in a loop just to test "is this a number?" is not — validate first, or write a small helper that returns an OptionalInt.

9. Clean up reliably

Close files, connections and streams with try-with-resources; release locks and reset shared state in finally. Never return or throw from a finally block (see the puzzles).

10. Respect InterruptedException

When another thread interrupts a thread that is sleeping or waiting, Java throws InterruptedException and clears the thread's interrupted flag. That flag is how executors and frameworks ask your code to stop. If you swallow the exception, the request is lost and the thread keeps running. Either let the exception propagate, or restore the flag:

try {
    Thread.sleep(500);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();       // restore the flag
    throw new IllegalStateException("Interrupted while waiting for the payment gateway", e);
}

Threads are covered in Module 6.

11. Throw early, catch late — at the right boundary

Detect problems as early as you can (item 6). But catch them as late as possible: at the level that has enough knowledge to decide — retry, show a message, return an error response. Deep inside a utility method nobody knows what the user should see. Real applications use a few fixed boundaries:

  • the web layer — one global handler turns exceptions into HTTP responses (see the Spring Boot article),
  • a job or message listener — catch, log, then continue with the next message,
  • a thread-pool task — an exception inside submit() is stored in the Future and lost if nobody calls get(), so catch and log inside the task,
  • a safety net for everything else, so that no thread dies without a trace:
Thread.setDefaultUncaughtExceptionHandler((thread, ex) ->
        log.error("Uncaught exception in thread {}", thread.getName(), ex));

12. Document what can be thrown

Describe the exceptions callers should expect with Javadoc @throws, including unchecked ones such as IllegalArgumentException. The method signature shows only the checked ones.

13. Prefer empty results and Optional to null

Do not return null to signal "nothing" or "failure". Return an empty collection or an Optional, and throw an exception for real errors. See NullPointerException, requireNonNull and Optional.

Real project: what a clean setup looks like

Input is validated at the edge of the API. Services throw unchecked domain exceptions with clear messages. Repositories translate technical exceptions (SQL, HTTP clients) and keep the cause. One @RestControllerAdvice maps each exception type to an HTTP status and a JSON error body, and logs unexpected ones once, with a request id, so a support engineer can find the single log entry for a failed request in seconds.

Interview: "How do you handle exceptions in a real project?"

  • Validate early and throw specific exceptions with good messages; use standard exceptions where they fit, custom ones for business failures.
  • Never swallow; catch only what you can handle; wrap with the cause when changing layers.
  • Handle centrally at the boundary (for example @RestControllerAdvice) and log once with the stack trace; do not leak internals to clients.
  • Use try-with-resources for cleanup, restore the interrupt flag, and keep exceptions out of normal control flow.

NullPointerException, requireNonNull and Optional

Most NullPointerExceptions come from a null that should have been rejected earlier: validate inputs with Objects.requireNonNull, return Optional or an empty collection instead of null, and read the helpful NPE message to find the exact null.

null means "no object". Calling a method on it has no meaning, so the JVM throws a NullPointerException (NPE). It is the most common exception in Java programs. The inventor of null references, Tony Hoare, called it his "billion-dollar mistake", and Java still has it, so you need to know where nulls come from and how to keep them out of your code.

Where NullPointerExceptions come from

  • Calling an instance method on null: email.trim().
  • Reading or writing a field of null: customer.address.city.
  • Using null as an array: scores[0] or scores.length.
  • Unboxing a null wrapper: int qty = map.get(key) when the key is missing.
  • A for-each loop over a null collection or array.
  • throw null, synchronized (null), and a switch on a null string or enum (unless it has a case null).
  • Library methods that reject null on purpose, such as List.of(...) and Optional.of(null) (table below).

The helpful NullPointerException message

Before Java 14 the message was empty and you had to guess which part of a.b().c.d() was null. Java 14 added helpful NullPointerExceptions (JEP 358); since Java 15 they are on by default. The JVM now describes the failed action and the null expression. The text is built only when something asks for the message, so it costs nothing until then.

import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class NpeMessages {

    static class Address {
        String city;
    }

    static class Customer {
        String name;
        Address address;

        String getName() {
            return name;
        }
    }

    public static void main(String[] args) {
        Customer customer = new Customer();
        String email = null;
        int[] scores = null;
        Map<String, Integer> stock = new HashMap<>();
        List<String> tags = null;

        List<Runnable> cases = List.of(
                () -> email.trim(),
                () -> customer.getName().length(),
                () -> System.out.println(customer.address.city),
                () -> System.out.println(scores[0]),
                () -> { int qty = stock.get("P-100"); },
                () -> { for (String t : tags) { System.out.println(t); } }
        );
        for (Runnable r : cases) {
            try {
                r.run();
            } catch (NullPointerException e) {
                System.out.println(e.getMessage());
            }
        }
    }
}
Cannot invoke "String.trim()" because "email" is null
Cannot invoke "String.length()" because the return value of "NpeMessages$Customer.getName()" is null
Cannot read field "city" because "customer.address" is null
Cannot load from int array because "scores" is null
Cannot invoke "java.lang.Integer.intValue()" because the return value of "java.util.Map.get(Object)" is null
Cannot invoke "java.util.List.iterator()" because "tags" is null

Each message has two halves. The first half says what the code tried (Cannot invoke "String.trim()", Cannot read field "city", Cannot load from int array). The because half names the null expression: a variable, a field path, or the return value of a method. The fifth line shows the classic hidden unboxing: you wrote int qty = stock.get(...) and the JVM calls Integer.intValue() on the null that get returned. The last line shows that a for-each loop calls iterator().

Edge case: local variable names need javac -g

The class file contains local variable names only when it was compiled with -g. Without it you see placeholders such as "<local4>" instead of "email". Maven, Gradle and IntelliJ compile with -g by default, so in normal projects you see the real names. Field names, method names and class names are always shown.

Fail fast with Objects.requireNonNull

The best NPE is the one thrown where the null enters, with a clear message, not 200 lines later where it is finally used. java.util.Objects has helpers for this and for null-safe code in general:

MethodWhat it does
requireNonNull(obj)Returns obj, or throws an NPE with no message
requireNonNull(obj, "message")The same, with your message — the usual form
requireNonNull(obj, supplier)The message is built only when needed
requireNonNullElse(obj, other)Returns obj, or other when obj is null
requireNonNullElseGet(obj, supplier)Same, but computes the default lazily
isNull(obj) / nonNull(obj)Predicates for method references, as in filter(Objects::nonNull)
toString(obj, "default")Text of obj, or the default when null
equals(a, b)Null-safe equality; two nulls are equal
 
import java.util.Objects;

public class Customer {
    private final String name;
    private final String email;

    public Customer(String name, String email) {
        this.name = Objects.requireNonNull(name, "name must not be null");
        this.email = Objects.requireNonNull(email, "email must not be null");
    }
}

// new Customer("Asha", null) throws immediately:
// java.lang.NullPointerException: email must not be null
//     at Customer.<init>(Customer.java:9)

By convention a null argument is reported with NullPointerException, not IllegalArgumentException, and requireNonNull does exactly that. The message shows which argument was wrong, and the stack trace points at the constructor, not at the code that eventually used the value.

Return empty collections and Optional, not null

A method that returns null forces every caller to remember a check. Two simple rules remove most of the problem:

  • Collections and arrays: return an empty one (List.of(), Collections.emptyList(), new String[0]), never null. Callers can then loop without a check.
  • A single value that may be absent: return Optional<T>. The type tells the caller that "no result" is possible, and the compiler makes them deal with it.
public Optional<Customer> findByEmail(String email) {
    // ... returns Optional.empty() when nobody has this email
}

// no null checks, no NPE
String city = findByEmail("asha@example.com")
        .map(Customer::getAddress)
        .map(Address::getCity)
        .orElse("unknown");

Use Optional as a return type. Do not use it for fields, method parameters or inside collections, and never call get() without checking. The full API, including orElse vs orElseGet and orElseThrow, is in Module 5.

Defensive habits that work

  • Put the known value first: "PAID".equals(status) never throws when status is null, but status.equals("PAID") does.
  • Use Objects.equals(a, b) when both sides may be null.
  • Use defaults for lookups: map.getOrDefault(key, 0) instead of unboxing a possible null.
  • Print safely: String.valueOf(obj) and string concatenation turn a null into the text "null" instead of throwing.
  • Initialize fields (private final List<Item> items = new ArrayList<>();) so they are never null.
  • Check where the null comes from — a missing map key, a database NULL, a JSON field that was absent — instead of adding != null everywhere.

Which classes accept null?

The surprising rows are the sorted, concurrent and immutable collections: they reject nulls that ArrayList and HashMap accept. See Module 4 for the collections themselves.

Mistakes with null

  • Catching NullPointerException to deal with a null. An NPE is a bug signal. Find out why the value is null and fix that, or check it explicitly.
  • Returning null from a method that returns a collection. Return an empty one.
  • Hidden unboxing: int stock = stockByItem.get(itemId); throws when the item is unknown. Use getOrDefault(itemId, 0).
  • Optional.of(value) with a possibly-null value throws immediately. Use Optional.ofNullable(value).
  • Passing null as a "not given" marker in a long parameter list. Use an overload, a builder, or Optional in the return of a getter instead.

Tip: let tools catch nulls before the JVM does

IntelliJ's inspections warn about possible NullPointerExceptions while you type. Null annotations (such as the JSpecify @Nullable) document intent and are checked by IDEs and static analysers like SpotBugs or NullAway. Kotlin builds the idea into the language. None of this changes the bytecode — it only finds mistakes earlier.

Interview: "How do you avoid NullPointerException?"

  • Do not create nulls: initialize fields, return empty collections, return Optional for "may be absent".
  • Reject them early: Objects.requireNonNull in constructors and public methods.
  • Write null-safe code: "literal".equals(x), Objects.equals, getOrDefault, Optional.map(...).orElse(...).
  • When it happens anyway, read the helpful NPE message (Java 14+, default since 15): it names the exact null expression.

From exception to HTTP response in Spring Boot

In a Spring Boot API, services throw domain exceptions and one @RestControllerAdvice class turns each type into an HTTP status and a JSON error body — no try/catch in controllers.

This is a first look; the Spring Boot page covers it fully in Spring Boot · Module 2. It belongs here because it is where everything in this module pays off: custom exceptions, unchecked exceptions, wrapping, and "handle at the boundary".

The idea

A web request passes through a controller, a service and a repository. Any of them can fail. If each controller method had its own try/catch, the code would be full of repeated error handling and every endpoint would answer errors a little differently. Spring lets you write the error handling once, in a class outside the controllers.

The code

The service throws a domain exception. The controller has no error handling at all.

public class OrderNotFoundException extends RuntimeException {
    private static final long serialVersionUID = 1L;

    public OrderNotFoundException(long id) {
        super("Order " + id + " not found");
    }
}
@Service
public class OrderService {
    // ... repository injected by the constructor ...

    public OrderDto findOrder(long id) {
        return repository.findById(id)
                .map(OrderDto::from)
                .orElseThrow(() -> new OrderNotFoundException(id));
    }
}

@RestController
@RequestMapping("/orders")
public class OrderController {
    // ... service injected by the constructor ...

    @GetMapping("/{id}")
    public OrderDto getOrder(@PathVariable long id) {
        return orderService.findOrder(id);     // no try/catch: failures flow to the advice
    }
}

The error body is a tiny record, and the handler class is the one place that maps exceptions to responses:

public record ApiError(String code, String message) { }
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice
public class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    @ExceptionHandler(OrderNotFoundException.class)
    public ResponseEntity<ApiError> handleNotFound(OrderNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ApiError("ORDER_NOT_FOUND", ex.getMessage()));
    }

    @ExceptionHandler(InsufficientBalanceException.class)
    public ResponseEntity<ApiError> handleInsufficientBalance(InsufficientBalanceException ex) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(new ApiError("INSUFFICIENT_BALANCE", ex.getMessage()));
    }

    @ExceptionHandler(Exception.class)          // the safety net: everything unexpected
    public ResponseEntity<ApiError> handleUnexpected(Exception ex) {
        log.error("Unexpected error", ex);       // logged once, with the stack trace
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(new ApiError("INTERNAL_ERROR", "Something went wrong. Please try again later."));
    }
}
HTTP/1.1 404 Not Found
Content-Type: application/json

{"code":"ORDER_NOT_FOUND","message":"Order 42 not found"}

Spring picks the most specific @ExceptionHandler for the exception that arrives, so the Exception.class handler only receives what no other handler wants. The unexpected case deliberately does not send ex.getMessage() to the client: it might contain SQL, file paths or other internals. The details go to the log; the client gets a generic message.

What happens without a handler

Spring MVC translates its own exceptions by default: a wrong HTTP method gives 405, an unsupported content type 415, an unreadable JSON body 400. Any other exception that nobody handles ends as 500 Internal Server Error through Boot's /error endpoint. The default JSON body has fields such as timestamp, status, error and path; Boot leaves out the exception message and the stack trace unless you switch them on with the server.error.include-* properties — do not do that in production.

Spring Security's 401 and 403 are produced in its filter chain, before MVC, so they are configured separately (Spring Boot · Module 4). Teams differ on edge cases: some map "insufficient balance" to 422 or 400. What matters is to choose a rule and apply it consistently.

Lighter alternatives

  • @ResponseStatus on the exception class — the status is fixed for that type, without any handler method: 
    @ResponseStatus(HttpStatus.NOT_FOUND)
public class OrderNotFoundException extends RuntimeException { /* ... */ }
  • ResponseStatusException — thrown directly, no custom class: throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Order 42 not found"). It is quick, but it ties service code to HTTP; domain exceptions plus an advice keep layers clean.
  • ProblemDetail — Spring Framework 6 and later can return the standard "problem details" JSON format (type, title, status, detail, instance) with content type application/problem+json, defined by RFC 9457 (which replaced RFC 7807). A handler method can return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage()) instead of a custom error class.

Boot 3.x and 4.x

The annotations on this page (@RestControllerAdvice, @ExceptionHandler, @ResponseStatus) work the same in Spring Boot 3.x and 4.x. Boot 4 is built on Spring Framework 7. Boot 3 and 4 use the jakarta.* packages for validation and servlet classes, not javax.*.

Rules for error responses

  • Never send stack traces, SQL text or internal class names to a client.
  • Use one error body shape for the whole API (for example code plus message, or ProblemDetail).
  • Log unexpected exceptions once, with the stack trace and a request or trace id.
  • Unchecked exceptions let @Transactional roll back by default; a checked exception commits unless you configure rollbackFor (see custom exceptions).

Interview: "How do you handle exceptions in a Spring Boot REST API?"

  • Throw domain exceptions (unchecked) from services; no try/catch in controllers.
  • One @RestControllerAdvice with @ExceptionHandler methods maps each exception to a status and a consistent JSON body; a last Exception.class handler returns 500 with a generic message and logs the details.
  • Mention @ResponseStatus, ResponseStatusException and ProblemDetail as alternatives, and that validation errors become 400.
  • Add: never leak internals; log once; unchecked exceptions and transaction rollback.

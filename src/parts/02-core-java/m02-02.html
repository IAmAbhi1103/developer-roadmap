The this keyword: what it is and where you use it

Inside an instance method or constructor, this is a reference to the object being worked on; you use it to separate a field from a parameter, call another constructor, pass the object to someone else, return it for chaining and reach an outer object.

When you write ravi.withdraw(500), the method withdraw runs on one particular object: ravi. Inside the method, the keyword this is a reference to that object. The compiler passes it as a hidden extra argument to every instance method call. Most of the time you do not write it, because Java adds it for you: balance -= amount means this.balance -= amount.

Three facts about this

  • It exists only in instance context: instance methods, constructors, instance initializer blocks and instance field initializers. A static method belongs to the class, not to an object, so it has no this (see static).
  • Its type is the class where the code is written, but at run time it can be an object of a subclass. In a method of Account, this may really be a SavingsAccount. This is what makes polymorphism work.
  • You cannot assign to it: this = other; is a compile error. It is also never null. If you call a method on a null reference, the NullPointerException happens at the call, before the method starts.

Use 1: separate a field from a parameter

When a parameter or local variable has the same name as a field, the parameter shadows (hides) the field. Inside that method, the plain name means the parameter. Write this.name to reach the field.

public class Customer {
    private String name;
    private int age;

    public Customer(String name, int age) {
        this.name = name;      // field = parameter
        this.age = age;
    }

    public void setName(String name) {
        this.name = name;      // same pattern in a setter
    }
}

This is the most common use of this. Using the same name for the parameter and the field is a normal Java style, because the name says exactly what the value is. The risk is forgetting the this. — see the mistake in constructors.

Use 2: call another constructor with this(…)

Inside a constructor, this(…) calls another constructor of the same class. You use it to write the setup and validation once and let the short constructors delegate to the full one. The rules (first statement, no loops, no instance members in the arguments) are in constructors in depth.

Use 3: pass the current object to someone else

Sometimes an object must hand itself to another object — to register as a listener, to add itself to a list, or to ask a helper to work on it. You pass this as the argument.

import java.util.*;

public class PriceDemo {
    static class PriceFeed {
        private final List<PriceAlert> subscribers = new ArrayList<>();
        void subscribe(PriceAlert alert) { subscribers.add(alert); }
        void publish(long paise) {
            for (PriceAlert a : subscribers) a.onPrice(paise);
        }
    }

    static class PriceAlert {
        private final String productId;
        private final long targetPaise;

        PriceAlert(String productId, long targetPaise) {
            this.productId = productId;
            this.targetPaise = targetPaise;
        }

        void watch(PriceFeed feed) {
            feed.subscribe(this);          // "here I am": passes the current object
        }

        void onPrice(long paise) {
            if (paise <= targetPaise) {
                System.out.println("Alert " + productId + ": price dropped to " + paise);
            }
        }
    }

    public static void main(String[] args) {
        PriceFeed feed = new PriceFeed();
        new PriceAlert("SKU-101", 45_000).watch(feed);
        feed.publish(49_900);
        feed.publish(44_900);
    }
}
Alert SKU-101: price dropped to 44900

Only the second price is at or below the target of 45,000 paise, so only one alert prints.

Mistake: letting this escape from a constructor

If a constructor passes this to other code before all fields are assigned, that code can see a half-built object. In multithreaded code another thread may even call it at that moment (Module 6).

Wrong: this escapes first

PriceAlert(String productId, long target, PriceFeed feed) {
    feed.subscribe(this);          // a callback now sees productId == null
    this.productId = productId;
    this.targetPaise = target;
}

Right: finish building, then publish

static PriceAlert createAndWatch(String productId, long target, PriceFeed feed) {
    PriceAlert alert = new PriceAlert(productId, target);   // fully built
    feed.subscribe(alert);                                  // then shared
    return alert;
}

Use 4: return this for method chaining

If a method changes the object and then returns this, callers can chain calls on one line. This is called a fluent style. StringBuilder.append() works this way, and builders use it heavily.

import java.util.*;

public class ThisDemo {
    static class Pizza {
        private String size = "M";
        private boolean extraCheese;
        private final List<String> toppings = new ArrayList<>();

        Pizza size(String size) { this.size = size; return this; }
        Pizza extraCheese()     { this.extraCheese = true; return this; }
        Pizza topping(String t) { toppings.add(t); return this; }

        @Override public String toString() {
            return "Pizza[size=" + size + ", extraCheese=" + extraCheese
                    + ", toppings=" + toppings + "]";
        }
    }

    public static void main(String[] args) {
        Pizza p = new Pizza().size("L").extraCheese().topping("onion").topping("capsicum");
        System.out.println(p);
    }
}
Pizza[size=L, extraCheese=true, toppings=[onion, capsicum]]

Notice that the methods are named after the property (size(…)), not setSize(…). That is the usual fluent-API naming, and it is different from the JavaBeans naming you will meet in encapsulation. Immutable classes cannot change themselves, so their "chain" methods return a new object instead of this.

Use 5: name the outer object with Outer.this

An inner class (a class declared inside another class, see nested classes) holds a hidden reference to an object of the outer class. If both classes have a field with the same name, Outer.this reaches the outer one.

public class OuterThis {
    private String name = "outer";

    class Inner {
        private String name = "inner";
        void show() {
            System.out.println(name);               // the closest one: inner
            System.out.println(this.name);          // inner
            System.out.println(OuterThis.this.name);// outer
        }
    }

    public static void main(String[] args) {
        new OuterThis().new Inner().show();
    }
}

Rules for this

  • It is allowed only in instance context. In a static method javac says non-static variable this cannot be referenced from a static context.
  • It cannot be reassigned.
  • this(…) and super(…) must be the first statement of a constructor, and a constructor can use only one of them (Java 25 relaxes the "first" part, see the version note in constructors).

Edge cases

  • Lambdas and anonymous classes differ. Inside a lambda, this means the enclosing object, because a lambda is not a new object. Inside an anonymous class, this is the anonymous object itself, and you write Outer.this for the enclosing one (Module 5).
  • Overridable calls through this. A call like describe() in a constructor really means this.describe(), and it runs the subclass version, even though the subclass is not ready yet (see initialization order).
  • Field initializers may use this, but only fields declared above them are guaranteed to be set at that point.

When to write this

  • Write this. when you must: shadowing, passing the object on, returning it, this(…). Leave it out elsewhere; extra this. everywhere is noise.
  • Some teams require this. on every field access to make fields stand out. Follow your team's style guide and stay consistent.

Interview: "What is this, and can you use it in a static method?"

  • this is a reference to the current object; it is passed implicitly to every instance method and constructor.
  • No, you cannot use it in a static method, because static code runs without any object.
  • Name the uses: disambiguate field vs parameter, this(…) chaining, passing the object, returning it for chaining, Outer.this.
  • Difference to remember: this is a reference to an object; this(…) is a constructor call. They are different things that share a word.

static: shared fields, methods, blocks and utility classes

A static member belongs to the class itself, not to any object: there is one shared copy, you use it without new, and because there is no this a static method cannot touch instance fields.

Normally every object has its own copy of each field. Two Account objects have two balances. Sometimes you need something that exists once for the whole class: a counter of created accounts, a constant, a helper like Math.max(). That is what static is for.

Static fields: one copy for the class

A static field is created once, when the class is first initialized, and every object (and every piece of code) sees the same value. Access it with the class name: Account.totalAccounts.

public class StaticDemo {
    static class Account {
        private static int totalAccounts = 0;   // one copy, shared by all accounts
        private final int id;                   // one copy per account

        Account() {
            id = ++totalAccounts;               // each new account takes the next number
        }

        static int getTotalAccounts() { return totalAccounts; }
        int getId() { return id; }
    }

    public static void main(String[] args) {
        Account a = new Account();
        Account b = new Account();
        System.out.println(a.getId() + " " + b.getId() + " total=" + Account.getTotalAccounts());
    }
}
1 2 total=2

Static fields are good for constants (static final), counters and caches. They are risky for anything that changes, because the one copy is shared by every thread and every user of the program. The line ++totalAccounts above is not safe when two threads create accounts at the same time; Module 6 shows AtomicInteger for that. A static field also lives as long as the class is loaded, which is normally the whole run of the application (Module 7).

Static methods: functions that need no object

A static method is called with the class name and works only on its parameters and on other static members. The JDK is full of them: Math.max(), Integer.parseInt(), Arrays.sort(), List.of(), String.valueOf(). The main method is static because the JVM must start your program before any object exists.

A static method has no this, so it cannot use instance fields or call instance methods directly. The compiler asks the right question: whose field? There may be a hundred Counter objects, and the static method is not running on any of them.

public class Counter {
    private int count = 0;

    static void reset() {
        count = 0;           // whose count?
        this.count = 0;      // there is no this
        increment();         // increment() needs an object too
    }

    void increment() { count++; }
}

You have three honest fixes. Make the field static if it really is shared state. Make the method an instance method if it works on one object. Or pass an object in: static void reset(Counter c) { c.count = 0; }. A static method can use instance members through an object reference; what it cannot do is use them without one.

Static blocks: one-time setup for the class

A static initializer block is code in static { … } that runs once, when the class is initialized. Use it when a static field needs more than one expression to set up.

import java.util.*;

public class CountryCodes {
    private static final Map<String, String> DIAL_CODES = new HashMap<>();

    static {                                  // runs once, when the class loads
        DIAL_CODES.put("IN", "+91");
        DIAL_CODES.put("US", "+1");
        DIAL_CODES.put("GB", "+44");
    }

    public static String dialCode(String iso) {
        return DIAL_CODES.get(iso);
    }
}

A class can have several static blocks; they run in the order they appear, mixed with static field initializers. For a small constant map, Map.of("IN", "+91", "US", "+1") is shorter and the result cannot be modified. The exact order of everything is in initialization order.

When a static initializer fails

If a static initializer throws, the class cannot be initialized. The first use gives ExceptionInInitializerError (with the real exception as its cause). Every later use gives NoClassDefFoundError: Could not initialize class …, which hides the original cause and confuses people. Look for the first error in the logs.

public class StaticInitFail {
    static class Config {
        static final int PORT = Integer.parseInt("80x");   // throws while loading Config
        static int port() { return PORT; }
    }

    public static void main(String[] args) {
        try { Config.port(); }
        catch (Throwable t) { System.out.println(t.getClass().getName() + " <- " + t.getCause()); }
        try { Config.port(); }
        catch (Throwable t) { System.out.println(t.getClass().getName() + ": " + t.getMessage()); }
    }
}

Utility classes

A utility class is a class that only holds static methods, with no state. Math, Arrays, Collections and Objects are examples. Nobody should create an object of such a class, so the convention is: a final class with a private constructor.

public final class RupeeFormat {
    private RupeeFormat() {
        throw new AssertionError("Utility class, do not instantiate");
    }

    // assumes paise >= 0
    public static String ofPaise(long paise) {
        return String.format("Rs. %d.%02d", paise / 100, paise % 100);
    }
}

// RupeeFormat.ofPaise(1_29_900)  returns  "Rs. 1299.00"

The private constructor stops new RupeeFormat() from outside, and the AssertionError stops accidental calls from inside the class. Use static helpers for pure functions (same input, same output, no hidden state). When logic needs state or must be replaced in a test, make it a normal class and let Spring inject it.

Static and inheritance

  • A static field is shared with subclasses: there is still only one copy. A subclass that declares a field with the same name creates a second, separate field (that is hiding, not overriding).
  • A static method is inherited by name, but redeclaring it in a subclass hides it. Which one runs depends on the declared type of the reference, not on the object (overriding rules).
  • Static members cannot be abstract, and an interface may have static methods that are not inherited by the classes that implement it (interfaces).

Edge cases and surprises

  • Calling a static method on a null reference works. Util u = null; u.hello(); prints the result with no NullPointerException, because the compiler uses the declared type Util and ignores the value. Never write code like this; call Util.hello().
  • No static local variables. Unlike C, static int x; inside a method is a compile error. If a value must survive between calls, make it a field.
  • Static fields are not serialized with the object, because they do not belong to it.
  • The main method can be overloaded, but the JVM starts the program only through public static void main(String[] args). Java 25 also allows simpler forms of main, for example without String[] args, mainly to make first programs easier to write (JEP 512); real projects still use the classic form.
  • Constants are inlined. A static final primitive or String with a constant value is copied into the code that uses it (more in final).

Mistake: using static for data that belongs to one user or one request

There is one copy of a static field per JVM. In a web application, one JVM serves all users at the same time, so a static "current user" is shared by everybody. Users see each other's data, and the bug shows up only under load.

Wrong: one value for all users

public class UserContext {
    private static String currentUser;     // shared by every request thread
    public static void set(String user) { currentUser = user; }
    public static String get() { return currentUser; }
}

Right: pass it, or keep it per request

public class OrderService {
    public Order place(String user, Cart cart) {   // pass the user as a parameter
        return new Order(user, cart);
    }
}
// Frameworks keep per-request data in ThreadLocal or request-scoped beans.

Conventions

  • Constants: public static final and UPPER_SNAKE_CASE, for example MAX_RETRIES.
  • Call static members through the class name (Account.getTotalAccounts()), never through an object. IDEs warn about the second form.
  • Keep static mutable state to a minimum. It makes code hard to test and unsafe across threads.
  • Utility class: final + private constructor + only static methods.

In a real Spring Boot project

You write exactly one important static method yourself: public static void main that calls SpringApplication.run(…). Everything else is usually an instance method on a Spring bean. You will still call many static methods from the JDK and libraries (LocalDate.now(), Objects.requireNonNull(), Collectors.toList()) and write a few small static helpers and constants.

Interview: static questions

  • Why is main static? The JVM calls it before any object exists, so it must not need one.
  • Can a static method use instance variables? Not directly — there is no this. It can through an object reference.
  • Can static methods be overridden? No. They are hidden; the declared type of the reference decides which runs.
  • Static block vs instance block? Static: once, at class initialization. Instance: every new, before the constructor body.
  • When does a static block run? When the class is first initialized (first new, static method call, or non-constant static field access).

Initialization order: static blocks, instance blocks and constructors

Static code runs once when the class is first used, parent before child; then for every new, the parent's field initializers, instance blocks and constructor run first, followed by the child's.

Output-prediction questions about "what prints first?" are among the most common Java interview puzzles. They are easy once you know the order and impossible if you guess. This article gives you the order, the reason behind it and the traps.

Two kinds of initialization

Class initialization
Happens once per class, the first time the class is really used. It runs static field initializers and static { } blocks, in the order they are written.
Instance initialization
Happens once per object, during new. It runs instance field initializers, instance blocks { } and the constructor.

An instance initializer block is a plain { … } in the class body. It runs for every object, before the constructor body. Constructor chaining (this(…)) is usually a better way to share code, but you will see instance blocks in puzzles and in anonymous classes, which cannot have constructors.

The order, step by step

Take class Child extends Parent and the statement new Child() executed for the first time:

StepWhat runsHow often
1Parent: static fields and static blocks, in textual orderOnce per class
2Child: static fields and static blocks, in textual orderOnce per class
3Memory for the object is allocated; every field gets its default value (0, false, null)Every new
4The Child constructor starts and first calls super(…) (written or implicit)Every new
5Parent: instance field initializers and instance blocks, in textual orderEvery new
6Parent constructor bodyEvery new
7Child: instance field initializers and instance blocks, in textual orderEvery new
8Child constructor bodyEvery new

The reason for "parent first" is simple: the child may depend on things the parent sets up, so the parent part of the object must be complete before the child part starts. This is also why the super(…) call must come first in a constructor.

A complete example

public class InitOrder {
    static class Parent {
        static { System.out.println("1. Parent static block"); }
        { System.out.println("3. Parent instance block"); }
        Parent() { System.out.println("4. Parent constructor"); }
    }

    static class Child extends Parent {
        static { System.out.println("2. Child static block"); }
        { System.out.println("5. Child instance block"); }
        Child() { System.out.println("6. Child constructor"); }
    }

    public static void main(String[] args) {
        System.out.println("main starts");
        new Child();
        System.out.println("--- second object ---");
        new Child();
    }
}

Field initializers run at the start of each class's part of construction (steps 5 and 7), before that class's constructor body, and the parent's part is complete before the child's part begins.

When is a class initialized?

Class initialization is lazy: it happens at the first active use of the class. These count as active use:

  • creating an object with new;
  • calling a static method of the class;
  • reading or writing a static field that is not a compile-time constant;
  • initializing a subclass (the superclass is initialized first);
  • starting the program with the class that has main, or calling Class.forName("…").

These do not trigger initialization: declaring a variable or an array of the type, and reading a constant (a static final primitive or String set from a constant expression), because javac copies the value into the caller. Also, reading a static field through a subclass initializes only the class that declares the field.

public class Trig {
    static class Parent { static int x = 10; static { System.out.println("Parent init"); } }
    static class Child extends Parent { static { System.out.println("Child init"); } }
    static class Consts {
        static final int MAX = 5;                    // constant
        static { System.out.println("Consts init"); }
    }

    public static void main(String[] args) {
        System.out.println(Child.x);                 // x is declared in Parent
        System.out.println(Consts.MAX);              // constant: no initialization
        System.out.println("now touching a non-constant");
        Object o = new Consts();                     // new: initialization happens here
    }
}

Textual order and forward references

Field initializers and blocks of the same kind run in the order they appear in the file. If one initializer uses a field that is declared later, the field still has its default value. javac rejects the simplest form of this, but a method call hides it:

public class Fwd {
    static int a = initA();      // runs first
    static int b = 5;            // runs second
    static int initA() { return b + 1; }   // b is still 0 here

    public static void main(String[] args) { System.out.println(a + " " + b); }
}
1 5

If you write static int a = b + 1; directly, javac stops with illegal forward reference. The method call is the loophole: it compiles, and a becomes 1, not 6.

The classic trap: calling an overridable method from a constructor

The parent constructor runs before the child's field initializers. If the parent constructor calls a method that the child overrides, the child's version runs on an object whose child fields are still at their default values.

public class Trap {
    static class Base {
        Base() { describe(); }                      // looks harmless...
        void describe() { System.out.println("Base"); }
    }

    static class Derived extends Base {
        private String name = "Derived";
        private final int size = 10;
        private int count = 5;

        Derived() { super(); }

        @Override void describe() {
            System.out.println("name=" + name + ", size=" + size + ", count=" + count);
        }
    }

    public static void main(String[] args) { new Derived(); }
}
name=null, size=10, count=0

The overridden describe() ran in step 4, while name and count were still null and 0 (step 3 defaults). The initializers "Derived" and 5 would run later, in step 7. The field size printed 10 only because private final int size = 10; is a compile-time constant: javac copies the 10 into describe().

Rule: never call an overridable method from a constructor or initializer

A method is overridable if it is not private, static or final. Either call only private or final methods there, or finish construction first and then call a normal method (for example from a static factory). The same advice applies to clone() and deserialization hooks.

Constructors that call this(…)

Instance initializers run as part of the constructor that calls super(…). A constructor that starts with this(…) does not run them again; they run once, in the constructor at the end of the chain.

public class Chain {
    { System.out.println("instance block"); }
    Chain() { this(1); System.out.println("Chain()"); }
    Chain(int x) { System.out.println("Chain(int)"); }

    public static void main(String[] args) { new Chain(); }
}

Edge cases

  • Exceptions. An exception in an instance block or constructor comes out of new, and you get no object. An exception in a static block becomes ExceptionInInitializerError (see static).
  • Interfaces. Initializing a class does not initialize the interfaces it implements, unless those interfaces declare default methods.
  • Singletons. The JVM runs class initialization under a lock, so private static final Service INSTANCE = new Service(); is created safely once, even with many threads (System Design · Module 2).
  • Enums create all their constants during class initialization, before any static block of the enum runs (enums).

Tip: how to answer an order puzzle

Write the numbers 1 to 8 from the table on paper. First mark which classes are being initialized for the first time (static work), then walk through each new from the top of the hierarchy down. Output puzzles stop being scary when you do it mechanically. Remember the short version: static before instance, parent before child, blocks and field initializers before the constructor body.

Interview: "In what order do static blocks, instance blocks and constructors run?"

  • Static blocks and static fields run once, when the class is first initialized, parent class first.
  • For each object: parent instance initializers, then parent constructor body, then child instance initializers, then child constructor body.
  • Add the trap: an overridden method called from the parent constructor sees default values in the child's fields.
  • Add one edge case: a constant (static final int X = 5) does not trigger class initialization.

Access modifiers: private, package-private, protected and public

Access modifiers decide which code may use a class, field, method or constructor: private means this class only, no modifier means the same package, protected adds subclasses, and public means everyone.

Access modifiers are the tool behind encapsulation. Every member you make visible becomes part of your class's public contract: other code can depend on it, and you cannot change it freely any more. So the rule is to show as little as possible.

The four levels

ModifierSame classSame packageSubclass in another packageEveryone else
private✓✗✗✗
(none) package-private✓✓✗✗
protected✓✓✓ (see below)✗
public✓✓✓✓
  • private — visible only inside the class that declares it (and inside its nested classes). Use it for fields and helper methods. It is the default choice.
  • package-private (also called default access) — you write nothing. Visible to every class in the same package. Use it for things that classes of one package share but the outside world must not see. There is no keyword for it: the word default is used only for interface default methods and switch.
  • protected — visible in the same package and to subclasses in other packages. Use it for deliberate extension points, such as a hook method that subclasses override.
  • public — visible everywhere. Use it only for the API you want other code to rely on.

The four levels across two packages

Access rules are about packages, so an example needs two. Account lives in com.bank; Savings extends it from com.bank.app.

package com.bank;

public class Account {
    private long secret = 1;
    long packageLevel = 2;                 // package-private
    protected long balance = 3;
    public long publicField = 4;

    protected void audit() { System.out.println("audit"); }
    protected Account() { }
    public static Account open() { return new Account(); }
}
package com.bank.app;

import com.bank.Account;

public class Savings extends Account {
    void test(Savings s, Account a) {
        this.balance = 1;                  // ok: inherited protected member
        s.balance = 2;                     // ok: the reference is a Savings
        a.balance = 3;                     // error
        a.audit();                         // error
        long x = secret;                   // error
        long y = packageLevel;             // error
        long z = publicField;              // ok
        Account fresh = new Account();     // error

The protected subtlety

Most people think protected means "my subclasses can use it". That is only half the rule. Outside the parent's package, subclass code can use a protected member only on objects of its own type (this, or any reference whose type is the subclass or below). It cannot use it on a plain parent-type reference. In the example, s.balance compiles because s is a Savings, but a.balance does not, because a is an Account and might really be some other subclass, such as a CurrentAccount, that Savings has no business changing.

Two more details follow from the same rule:

  • Inside the same package, protected is as open as package-private plus subclasses. It is wider than package-private, not narrower.
  • A protected constructor cannot be called with new from another package, even from a subclass (last error above). A subclass reaches it through super(…). An anonymous subclass such as new Account() { } is allowed, because it is itself a subclass.

Access rules for classes

A top-level class can only be public or package-private. private and protected do not make sense for it, because there is no enclosing class or subclass context to restrict to.

private class Hidden { }       // error
protected class Prot { }       // error
public class TopLevel { }      // ok

A nested class (declared inside another class) is a member, so it can use all four levels. A public top-level class must be in a file with the same name. A package-private class is invisible outside its package, which makes it a good way to hide helper classes (packages).

Access modifiers in other places

  • Interface members are public by default, so an implementing method must be declared public (interfaces).
  • Overriding may widen access but never narrow it (overriding rules).
  • Enum constructors are always private, and record fields are private and final (enums, records).
  • Access is per class, not per object. Code inside Account may read the private fields of another Account object, which is why equals() and copy constructors can touch other.balance.

Edge cases

  • private is not a security feature. Reflection with setAccessible(true) can read private fields; frameworks such as Hibernate and Jackson do exactly that. Since Java 17 the JDK's own internals are closed to this by default (JEP 403), but your own classes are not.
  • Nested classes and their outer class can see each other's private members. The compiler and JVM treat them as one unit.
  • Sub-packages are unrelated. com.bank and com.bank.app are two different packages; package-private access does not cross between them.
  • Modules (JPMS). If a library uses module-info.java, a public class in a package that the module does not exports is still not reachable from other modules. Most Spring Boot applications do not use modules.

Mistake: public fields

Wrong: anyone can break the rule

public class Account {
    public long balance;       // account.balance = -500; compiles and runs
}

Right: private field, safe methods

public class Account {
    private long balance;
    public void deposit(long amount) {
        if (amount <= 0) throw new IllegalArgumentException("amount must be positive");
        balance += amount;
    }
    public long getBalance() { return balance; }
}

Tip: package-private helps testing

A test class in the same package (same folder path under src/test/java) can call package-private methods. So you can keep a helper off the public API and still test it directly. You do not have to make it public only for the test's sake.

In real projects

JPA entities usually have a protected no-argument constructor: Hibernate can use it, but application code in other packages cannot create half-empty objects. Service classes keep their dependencies in private final fields. Most classes in a well-designed package are package-private; only the few that form the package's entry points are public.

Interview: access modifier questions

  • Draw the table. Rows private, default, protected, public; columns class, package, subclass, world.
  • Difference between default and protected? Both allow the same package; protected also allows subclasses in other packages (through a subclass-typed reference).
  • Can a top-level class be private or protected? No — only public or package-private.
  • Can an overriding method have weaker access? No; it can only keep or widen access.
  • Can an object read another object's private field? Yes, if both are of the same class: access is per class.

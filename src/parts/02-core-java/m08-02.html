JUnit 5: writing and running unit tests

A unit test is a small method that calls your code with known input and asserts the expected result; JUnit 5 finds methods marked @Test, runs them in isolation and reports which ones fail.

A unit test checks one small piece of behaviour (usually one method or class) automatically and quickly, without a database or network. Tests catch bugs when you write the code, and — more importantly — when someone changes it six months later. JUnit 5 is the standard Java test framework (the Spring Boot test starter includes it). It consists of the Platform (runs tests), Jupiter (the API and engine you write against: org.junit.jupiter.api) and Vintage (runs old JUnit 4 tests). Spring-specific testing (@SpringBootTest, mocks, MockMvc) is covered in Spring Boot · Module 5.

Setup

Add the dependency with test scope (as in the pom.xml above): org.junit.jupiter:junit-jupiter, which brings the API, the engine and parameterised tests. Use a recent Surefire plugin (2.22 or newer) so Maven can run JUnit 5. Test classes go in src/test/java, in the same package as the class under test.

A first test

package com.shop;

public class PriceCalculator {
    /** Price in paise after a percentage discount (0-100). */
    public long finalPrice(long amount, int discountPercent) {
        if (amount < 0) {
            throw new IllegalArgumentException("amount must not be negative");
        }
        if (discountPercent < 0 || discountPercent > 100) {
            throw new IllegalArgumentException("discount must be between 0 and 100");
        }
        return amount - amount * discountPercent / 100;
    }
}
package com.shop;

import static org.junit.jupiter.api.Assertions.*;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

class PriceCalculatorTest {

    private PriceCalculator calculator;

    @BeforeEach
    void setUp() {
        calculator = new PriceCalculator();       // fresh object for every test
    }

    @Test
    @DisplayName("10% discount on 1000 gives 900")
    void shouldApplyDiscount() {
        // Arrange
        long amount = 1000;
        // Act
        long result = calculator.finalPrice(amount, 10);
        // Assert
        assertEquals(900, result);
    }

    @Test
    void shouldReturnSameAmountWhenNoDiscount() {
        assertEquals(1000, calculator.finalPrice(1000, 0));
    }

    @Test
    void shouldRejectNegativeAmount() {
        IllegalArgumentException ex = assertThrows(
                IllegalArgumentException.class,
                () -> calculator.finalPrice(-1, 10));
        assertEquals("amount must not be negative", ex.getMessage());
    }
}

Test classes and methods need not be public in JUnit 5 (package-private is fine), but must not be private or static. JUnit creates a new instance of the test class for every test method, so fields set in one test never leak into another.

Run tests from IntelliJ by clicking the green arrow beside the class or method, or with Ctrl+Shift+F10 at the cursor. From Maven:

$ mvn test
[INFO] Running com.shop.PriceCalculatorTest
[ERROR] PriceCalculatorTest.shouldApplyDiscount:25 expected: <900> but was: <1000>
[ERROR] Tests run: 3, Failures: 1, Errors: 0, Skipped: 0
[INFO] BUILD FAILURE

A failure means an assertion was false. An error means an unexpected exception was thrown. Surefire writes reports to target/surefire-reports.

Parameterised tests

Instead of copying a test five times with different numbers, feed one test method a table of inputs.

import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import org.junit.jupiter.params.provider.ValueSource;

class PriceCalculatorParamTest {
    private final PriceCalculator calculator = new PriceCalculator();

    @ParameterizedTest(name = "{0} paise with {1}% off is {2}")
    @CsvSource({
            "1000, 10, 900",
            "1000, 0, 1000",
            "1000, 100, 0",
            "999, 50, 500"          // 999 * 50 / 100 = 499 (integer division), 999 - 499
    })
    void shouldCalculateFinalPrice(long amount, int percent, long expected) {
        assertEquals(expected, calculator.finalPrice(amount, percent));
    }

    @ParameterizedTest
    @ValueSource(ints = {-1, 101, 1000})
    void shouldRejectInvalidDiscount(int percent) {
        assertThrows(IllegalArgumentException.class,
                () -> calculator.finalPrice(100, percent));
    }
}

Other sources: @MethodSource("method") (a static method returning a stream of arguments — for objects), @EnumSource, @NullAndEmptySource, @CsvFileSource. Each row appears as a separate test in the report.

Arrange-Act-Assert and naming

  1. Arrange — create the object under test and its input.
  2. Act — call the one method you are testing.
  3. Assert — check the result or the state.

Keep the three parts visible (a blank line between them). A test checks one behaviour. Name tests after the behaviour: shouldRejectNegativeAmount, givenExpiredCoupon_whenApply_thenThrows, returnsEmptyListForUnknownCustomer — or use @DisplayName with a full sentence. A test name should tell you what broke without opening the file.

What makes a good unit test (FIRST)

  • Fast — milliseconds. Slow tests do not get run.
  • Isolated — no dependence on test order, shared state, the clock, or external systems. Replace collaborators with fakes or mocks (Mockito, see Module 5 of Spring Boot).
  • Repeatable — same result on every machine, every run (no randomness without a seed, no real dates).
  • Self-validating — pass or fail by itself; no reading of console output.
  • Timely — written with (or before) the code.

Test the edges: zero, one, many, null, empty string, boundary values (0, 100, 101), and error paths — not only the happy path. Aim for meaningful coverage of business logic rather than a 100% number.

Rules

  • Test methods are void, take no arguments (except in parameterised tests), and are not private or static.
  • Tests must not depend on execution order; JUnit does not guarantee one.
  • Surefire only picks classes named *Test, Test*, *Tests or *TestCase by default.
  • @BeforeAll/@AfterAll must be static in the default lifecycle.

Common mistakes

  • Swapping expected and actual, which makes failure messages misleading.
  • Tests with no assertion (they pass but prove nothing).
  • Catching the exception manually in a try/catch and forgetting fail(); use assertThrows.
  • Sharing mutable state through static fields between tests.
  • Testing implementation details (private methods, call order) instead of behaviour, so every refactor breaks tests.
  • Using assertEquals(double, double) without a delta.

Version note

The examples use JUnit 5 (Jupiter) with the packages org.junit.jupiter.api and org.junit.jupiter.params. A newer major version, JUnit 6, was released in late 2025 and keeps the same annotations and packages for everyday use; check the project's dependency version before copying build settings, because the minimum Java version is higher. Spring Boot 3.x and 4.x set the JUnit version for you through their BOM.

Interview: "How do you unit-test a method? JUnit 4 vs 5?"

  • Arrange-Act-Assert; one behaviour per test; cover happy path, edge cases and exceptions (assertThrows).
  • Isolation: fresh object per test via @BeforeEach; mock external dependencies.
  • JUnit 5 has modular architecture (Platform, Jupiter, Vintage), @BeforeEach instead of @Before, @ParameterizedTest, @Nested, assertAll, lambdas in assertions, and extensions instead of runners.
  • Unit test vs integration test: speed, scope, and what is real (database, Spring context).

JDBC basics: connecting, PreparedStatement and SQL injection

JDBC is Java's standard API for relational databases: a driver implements it, DriverManager gives you a Connection, and you run SQL through a PreparedStatement with ? placeholders — never by concatenating user input.

JDBC (Java Database Connectivity) is a set of interfaces in java.sql. Your code talks to the interfaces; a JDBC driver — a JAR provided by the database vendor — implements them for PostgreSQL, MySQL, Oracle and so on. Frameworks like Spring Data JPA, Hibernate and MyBatis all run on JDBC underneath, so understanding it explains what they do and why things go wrong.

The core types

CallableStatementCalls stored procedures and functions
ResultSetThe rows returned by a query; a cursor you move with next()
SQLExceptionAnything that goes wrong (checked exception)

Setting up

Add the driver as a runtime dependency (see the pom.xml): org.postgresql:postgresql, or for MySQL com.mysql:mysql-connector-j. Since JDBC 4 (Java 6) the driver on the classpath registers itself, so the old line Class.forName("org.postgresql.Driver") is unnecessary. Create the table once:

CREATE TABLE customers (
    id      BIGSERIAL PRIMARY KEY,          -- MySQL: BIGINT AUTO_INCREMENT PRIMARY KEY
    name    VARCHAR(100)  NOT NULL,
    email   VARCHAR(150)  NOT NULL UNIQUE,
    city    VARCHAR(60),
    balance NUMERIC(12,2) NOT NULL DEFAULT 0
);
DatabaseURL pattern
PostgreSQLjdbc:postgresql://localhost:5432/shop
MySQLjdbc:mysql://localhost:3306/shop

The URL has the shape jdbc:<vendor>://host:port/database?options. The default ports are 5432 (PostgreSQL) and 3306 (MySQL).

Connect and run a query

import java.sql.*;

public class FirstQuery {
    public static void main(String[] args) throws SQLException {
        String url = "jdbc:postgresql://localhost:5432/shop";
        String user = System.getenv("DB_USER");            // never hard-code secrets
        String password = System.getenv("DB_PASSWORD");

        String sql = "SELECT id, name, city FROM customers WHERE city = ?";

        try (Connection con = DriverManager.getConnection(url, user, password);
             PreparedStatement ps = con.prepareStatement(sql)) {

            ps.setString(1, "Pune");                        // parameter index starts at 1

            try (ResultSet rs = ps.executeQuery()) {
                while (rs.next()) {                         // move to the next row
                    long id = rs.getLong("id");
                    String name = rs.getString("name");
                    String city = rs.getString("city");
                    System.out.println(id + " " + name + " " + city);
                }
            }
        }                                                   // all three closed automatically
    }
}
1 Asha Rao Pune
4 Vikram Shah Pune

Three things to remember:

  • Use try-with-resources so ResultSet, PreparedStatement and Connection are always closed, even on exceptions. Closing the connection also closes its statements, but closing each one explicitly is good hygiene.
  • Parameter and column indexes start at 1, not 0. Prefer column names (rs.getString("name")) to numbers.
  • rs.next() returns false when there are no more rows; the cursor starts before the first row, so you must call next() before reading.

SQL injection: the attack

SQL injection happens when user input becomes part of the SQL text. The input can then change the meaning of the query. This code builds the query by concatenation:

static boolean login(Connection con, String email, String password) throws SQLException {
    String sql = "SELECT id FROM users WHERE email = '" + email
               + "' AND password_hash = '" + password + "'";
    try (Statement st = con.createStatement();
         ResultSet rs = st.executeQuery(sql)) {
        return rs.next();                     // any row found = logged in
    }
}

With a normal input the SQL is ... WHERE email = 'asha@mail.in' AND password_hash = 'x'. Now an attacker types ' OR '1'='1 as both fields:

SELECT id FROM users WHERE email = '' OR '1'='1' AND password_hash = '' OR '1'='1'

The condition is always true; the query returns rows and the attacker is "logged in" as the first user. Worse input like '; DROP TABLE users; -- can delete data on databases and drivers that accept several statements in one call. SQL injection has been in the OWASP Top 10 for years and remains a common cause of real data breaches.

The fix: PreparedStatement

static boolean login(Connection con, String email, String passwordHash) throws SQLException {
    String sql = "SELECT id FROM users WHERE email = ? AND password_hash = ?";
    try (PreparedStatement ps = con.prepareStatement(sql)) {
        ps.setString(1, email);               // the value can never become SQL
        ps.setString(2, passwordHash);
        try (ResultSet rs = ps.executeQuery()) {
            return rs.next();
        }
    }
}

With a prepared statement the SQL text (with its ? placeholders) and the values travel separately. The database parses the structure first; later, the value ' OR '1'='1 is treated as one harmless string to compare with, not as code. (In real systems you also never store plain passwords: you hash them with BCrypt, covered in Spring Security.)

  • Placeholders work only for values, not for table names, column names or keywords like ORDER BY direction. If you must choose them from user input, validate against a fixed whitelist (Set.of("name", "city")) and build the text from your own constants.
  • For LIKE, put the wildcards in the value: ps.setString(1, "%" + term + "%");.
  • For IN (...) create as many ? as there are values.
  • ORMs are safe when you use their parameter features (JPQL :name, Spring Data derived queries), but string-concatenated JPQL or native SQL is just as vulnerable.

Rule: never build SQL by concatenating or formatting user input

Not with +, not with String.format, not with text blocks. Always bind values with PreparedStatement placeholders.

Conventions

  • Read the URL, user and password from environment variables or configuration, not from source code.
  • Open a connection late, close it early (try-with-resources); in real services get connections from a pool (next article).
  • Select only the columns you need instead of SELECT *; map rows into small objects (records) immediately.
  • Use BigDecimal for money (NUMERIC in the database), never double.

Errors you will meet

  • No suitable driver found for jdbc:… — driver JAR missing from the classpath (wrong Maven scope), or a typo in the URL.
  • Connection refused / connection timed out — database not running, wrong host or port, firewall.
  • password authentication failed (PostgreSQL) / Access denied (MySQL) — wrong credentials.
  • relation "customers" does not exist — wrong database or schema, table not created.
  • The column name x was not found in this ResultSet — the column is not in the SELECT list or is misspelled.
  • Operation not allowed after ResultSet closed — you used the ResultSet after closing its statement or connection.

Interview: "What is JDBC? Statement vs PreparedStatement? How do you prevent SQL injection?"

  • JDBC is the standard API; the driver implements it; steps: connection, statement, execute, process ResultSet, close (try-with-resources).
  • PreparedStatement is precompiled, parameterised, reusable, faster for repeated calls and — most importantly — prevents SQL injection because values are sent separately from the SQL.
  • Demo the attack (' OR '1'='1) and the fix; mention whitelisting for identifiers and hashing passwords.
  • Index start at 1; executeQuery vs executeUpdate; CallableStatement for stored procedures.

JDBC in practice: CRUD DAO, transactions, batches and connection pools

A DAO class hides all JDBC code behind simple methods; use try-with-resources for every call, setAutoCommit(false) with commit/rollback for multi-step changes, batches for bulk inserts, and a connection pool such as HikariCP in real applications.

The DAO pattern

A DAO (Data Access Object) is a class whose only job is to read and write one kind of data. The rest of the application calls customerDao.findById(7) and never sees SQL or Connection. When the database changes, only the DAO changes; in tests you can replace it with a fake. Spring Data repositories are an automatic version of the same idea. Mapping each row to a record keeps the data object short and immutable.

A complete CRUD DAO

public record Customer(long id, String name, String email, String city) {}
import java.sql.*;
import java.util.ArrayList;
import java.util.List;
import java.util.Optional;

public class CustomerDao {
    private final String url;
    private final String user;
    private final String password;

    public CustomerDao(String url, String user, String password) {
        this.url = url;
        this.user = user;
        this.password = password;
    }

    private Connection connect() throws SQLException {
        return DriverManager.getConnection(url, user, password);
    }

    // Row -> object. The ResultSet is already positioned on a row.
    private Customer map(ResultSet rs) throws SQLException {
        return new Customer(
                rs.getLong("id"),
                rs.getString("name"),
                rs.getString("email"),
                rs.getString("city"));              // may be null
    }

    // CREATE
    public Customer insert(String name, String email, String city) throws SQLException {
        String sql = "INSERT INTO customers (name, email, city) VALUES (?, ?, ?)";
        try (Connection con = connect();
             PreparedStatement ps = con.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) {
            ps.setString(1, name);
            ps.setString(2, email);
            ps.setString(3, city);
            ps.executeUpdate();
            try (ResultSet keys = ps.getGeneratedKeys()) {
                keys.next();
                return new Customer(keys.getLong("id"), name, email, city);
            }
        }
    }

    // READ one
    public Optional<Customer> findById(long id) throws SQLException {
        String sql = "SELECT id, name, email, city FROM customers WHERE id = ?";
        try (Connection con = connect();
             PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setLong(1, id);
            try (ResultSet rs = ps.executeQuery()) {
                return rs.next() ? Optional.of(map(rs)) : Optional.empty();
            }
        }
    }

    // READ many
    public List<Customer> findByCity(String city) throws SQLException {
        String sql = "SELECT id, name, email, city FROM customers WHERE city = ? ORDER BY name";
        List<Customer> result = new ArrayList<>();
        try (Connection con = connect();
             PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setString(1, city);
            try (ResultSet rs = ps.executeQuery()) {
                while (rs.next()) {
                    result.add(map(rs));
                }
            }
        }
        return result;
    }

    // UPDATE
    public boolean updateCity(long id, String newCity) throws SQLException {
        String sql = "UPDATE customers SET city = ? WHERE id = ?";
        try (Connection con = connect();
             PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setString(1, newCity);
            ps.setLong(2, id);
            return ps.executeUpdate() == 1;           // rows affected
        }
    }

    // DELETE
    public boolean delete(long id) throws SQLException {
        try (Connection con = connect();
             PreparedStatement ps = con.prepareStatement("DELETE FROM customers WHERE id = ?")) {
            ps.setLong(1, id);
            return ps.executeUpdate() == 1;
        }
    }
}
public class Main {
    public static void main(String[] args) throws Exception {
        CustomerDao dao = new CustomerDao("jdbc:postgresql://localhost:5432/shop",
                System.getenv("DB_USER"), System.getenv("DB_PASSWORD"));

        Customer saved = dao.insert("Asha Rao", "asha@mail.in", "Pune");
        System.out.println(saved);
        System.out.println(dao.findById(saved.id()).isPresent());
        System.out.println(dao.findByCity("Pune"));
        System.out.println(dao.updateCity(saved.id(), "Mumbai"));
        System.out.println(dao.findById(saved.id()).orElseThrow().city());
        System.out.println(dao.delete(saved.id()));
        System.out.println(dao.findById(saved.id()));
    }
}

Notes: RETURN_GENERATED_KEYS asks the driver to return the database-generated id. In PostgreSQL you can also write INSERT ... RETURNING id and run it with executeQuery. This DAO opens a new connection per call, which is fine for learning but slow in real systems (see pools below).

Transactions

A transaction groups several statements so they either all succeed or none do (ACID, see SQL · Module 5). By default JDBC is in auto-commit mode: every statement is committed immediately. For a multi-step operation such as a money transfer, turn auto-commit off, then commit() on success and rollback() on failure.

public void transfer(long fromId, long toId, BigDecimal amount) throws SQLException {
    String debitSql = "UPDATE customers SET balance = balance - ? WHERE id = ? AND balance >= ?";
    String creditSql = "UPDATE customers SET balance = balance + ? WHERE id = ?";

    try (Connection con = connect()) {
        con.setAutoCommit(false);                              // start a transaction
        try (PreparedStatement debit = con.prepareStatement(debitSql);
             PreparedStatement credit = con.prepareStatement(creditSql)) {

            debit.setBigDecimal(1, amount);
            debit.setLong(2, fromId);
            debit.setBigDecimal(3, amount);
            if (debit.executeUpdate() != 1) {
                throw new SQLException("Insufficient balance or unknown account " + fromId);
            }

            credit.setBigDecimal(1, amount);
            credit.setLong(2, toId);
            if (credit.executeUpdate() != 1) {
                throw new SQLException("Unknown account " + toId);
            }

            con.commit();                                      // both changes become permanent
        } catch (SQLException e) {
            con.rollback();                                    // undo the debit if anything failed
            throw e;
        }
    }
}

If the credit fails after the debit succeeded, rollback() restores the sender's money. Without a transaction, the money would simply vanish. If the connection closes without commit(), uncommitted work is rolled back by most drivers, but do not rely on it. In Spring you replace all of this with @Transactional (Spring Boot · Module 3). Isolation levels can be set with con.setTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED).

Batch inserts

Sending 10,000 inserts one by one costs 10,000 network round trips. A batch queues the statements and sends them together:

public void insertAll(List<Customer> customers) throws SQLException {
    String sql = "INSERT INTO customers (name, email, city) VALUES (?, ?, ?)";
    try (Connection con = connect();
         PreparedStatement ps = con.prepareStatement(sql)) {
        con.setAutoCommit(false);
        int count = 0;
        for (Customer c : customers) {
            ps.setString(1, c.name());
            ps.setString(2, c.email());
            ps.setString(3, c.city());
            ps.addBatch();                       // queue, do not run yet
            if (++count % 500 == 0) {
                ps.executeBatch();               // send every 500 rows
            }
        }
        ps.executeBatch();                       // send the remainder
        con.commit();
    }
}

executeBatch() returns an int[] of update counts. Some drivers need an option to really rewrite batches into fewer statements (reWriteBatchedInserts=true for PostgreSQL, rewriteBatchedStatements=true for MySQL, both added to the JDBC URL). Keep batches to a few hundred or thousand rows to limit memory.

Handling SQLException

try {
    dao.insert("Asha Rao", "asha@mail.in", "Pune");
} catch (SQLException e) {
    System.err.println("Message : " + e.getMessage());
    System.err.println("SQLState: " + e.getSQLState());     // standard 5-char code
    System.err.println("Vendor  : " + e.getErrorCode());    // database-specific code
    if ("23505".equals(e.getSQLState())) {                   // PostgreSQL unique violation
        throw new IllegalStateException("Email already registered", e);
    }
    throw new RuntimeException("Database error", e);          // keep the cause
}
  • SQLException is a checked exception. Do not swallow it with an empty catch; either handle it meaningfully or wrap it in your own unchecked exception with the original as the cause.
  • The SQLState is a five-character standard code whose first two characters give the class: 23xxx is an integrity-constraint violation (23505 is a duplicate key in PostgreSQL; MySQL reports duplicates with state 23000 and error code 1062), 08xxx is a connection problem, 42xxx is a syntax or access error.
  • Never show raw SQL errors to end users: they expose table names and structure. Log them, return a safe message.

Why connection pools exist

Opening a database connection is expensive: a TCP connection, authentication, and session setup on the server — typically many milliseconds, which dwarfs a fast query. Databases also limit the number of simultaneous connections. A connection pool opens a fixed set of connections once and lends them out: getConnection() returns a pooled connection quickly, and close() does not really close it, it returns it to the pool.

HikariCP is the fast, standard pool and the default in Spring Boot. Spring Boot creates a pooled DataSource from spring.datasource.url, username and password; HikariCP's default maximum pool size is 10 (spring.datasource.hikari.maximum-pool-size). If all connections are busy, new requests wait and may time out. Pool configuration and tuning are in Spring Boot · Module 3. Your DAO code stays the same: replace DriverManager.getConnection(...) by dataSource.getConnection() and keep closing the connection in try-with-resources — that is what returns it to the pool.

Rules

  • Always close Connection, PreparedStatement and ResultSet (try-with-resources). A connection leak exhausts the pool and freezes the application.
  • In a transaction, rollback() on failure, and use one Connection for all steps — separate connections are separate transactions.
  • Never share a Connection between threads.

Common mistakes

  • Leaving auto-commit on for a multi-statement business operation.
  • Forgetting to commit() after setAutoCommit(false): data seems saved in your session but vanishes.
  • Returning a ResultSet from a method after its connection was closed; map to objects inside the method.
  • Running one query per row in a loop (the N+1 problem); use a JOIN or IN, or batch.
  • Reading a nullable INT column with getInt and treating the returned 0 as real.
  • Catching SQLException and only calling e.printStackTrace().

Real projects

Few teams write raw JDBC for every query today: Spring Data JPA or JdbcTemplate remove the boilerplate. But everything above still runs underneath: a pooled DataSource, prepared statements, transactions, batches and SQLException translation. Raw JDBC remains common for bulk loads, reports and tools. When a framework misbehaves, turning on SQL logging (Logging) shows the exact statements JDBC receives.

Interview: "How do you handle transactions in JDBC? Why use a connection pool?"

  • setAutoCommit(false), do the steps on one connection, commit(), rollback() in the catch block, then close.
  • Pool: connection creation is expensive and databases limit connections; the pool reuses them; close() returns to the pool; HikariCP is the default in Spring Boot.
  • Batch: addBatch/executeBatch reduce round trips.
  • DAO pattern separates persistence from business logic. Mention try-with-resources and checked SQLException with getSQLState().

Concurrent collections: ConcurrentHashMap and friends

The java.util.concurrent collections are built for many threads: ConcurrentHashMap gives fast thread-safe reads and atomic updates like merge and compute, CopyOnWriteArrayList suits read-heavy lists, and the BlockingQueue family passes work between threads.

Why ordinary collections break

HashMap and ArrayList are not thread-safe. Two threads calling put at the same time can lose entries, corrupt the internal structure, or (in old Java versions) even loop forever during a resize. Iterating while another thread modifies the collection throws ConcurrentModificationException. The old fix, Collections.synchronizedMap, makes every call take one lock, which is safe but slow under load. The concurrent collections solve this with smarter designs.

ConcurrentHashMap

ConcurrentHashMap is the default thread-safe map. It does not allow null keys or values: in a concurrent map, get(k) == null must unambiguously mean "absent", and a stored null would make that unclear (NullPointerException if you try).

How it is thread-safe (Java 8 and later)
  • The table is an array of bins (buckets), like HashMap.
  • Putting into an empty bin uses a lock-free CAS (compare-and-set: "set this slot to the new node only if it is still empty").
  • Putting into a bin that already has nodes takes a synchronized lock on that bin's first node only. Threads working on different bins never block each other. (Java 7 used a fixed number of segments; Java 8 replaced them with this per-bin locking.)
  • get takes no lock: node values and next-pointers are volatile, so reads see recent writes.
  • Long collision chains turn into trees, as in HashMap (when a bin has at least 8 nodes and the table has at least 64 slots).
  • The size is kept in counter cells (like LongAdder) so many threads can update it without fighting over one variable. size() is therefore an estimate while updates are running; mappingCount() returns a long.
  • Iterators are weakly consistent: they never throw ConcurrentModificationException, and they may or may not show changes made after the iterator was created.

Atomic compound operations

Each single call (get, put) is atomic, but two calls together are not. This is the classic check-then-act race:

Wrong: not atomic, two threads can both see null

Integer old = map.get(word);
if (old == null) {
    map.put(word, 1);
} else {
    map.put(word, old + 1);    // lost updates
}

Right: one atomic call

map.merge(word, 1, Integer::sum);

computeIfPresent(k, fn)Recompute only if present

import java.util.*;
import java.util.concurrent.*;

public class HitCounter {
    public static void main(String[] args) throws Exception {
        Map<String, Integer> safe = new ConcurrentHashMap<>();
        Map<String, Integer> unsafe = new HashMap<>();

        try (ExecutorService pool = Executors.newFixedThreadPool(4)) {
            for (int t = 0; t < 4; t++) {
                pool.execute(() -> {
                    for (int i = 0; i < 50_000; i++) {
                        safe.merge("/home", 1, Integer::sum);        // atomic
                        unsafe.merge("/home", 1, Integer::sum);      // data race!
                    }
                });
            }
        }
        System.out.println("ConcurrentHashMap: " + safe.get("/home"));
        System.out.println("HashMap          : " + unsafe.get("/home"));
    }
}

The HashMap result changes on every run and is usually below 200,000 (it can even throw an exception, or hang in some versions). The ConcurrentHashMap result is always exact.

Rule: keep the function passed to compute and merge short

The function runs while a bin is locked. It must be quick, must not block, and must not modify the same map (that can deadlock or throw IllegalStateException: Recursive update).

CopyOnWriteArrayList

Every write (add, set, remove) makes a fresh copy of the internal array. Readers use the old array, with no locks, and an iterator works on a snapshot: it never throws ConcurrentModificationException and never sees later changes.

import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;

public class Listeners {
    public static void main(String[] args) {
        List<String> listeners = new CopyOnWriteArrayList<>(List.of("email", "sms"));

        for (String l : listeners) {           // iterating a snapshot
            System.out.println("notify " + l);
            if (l.equals("email")) {
                listeners.add("push");         // fine: no exception
            }
        }
        System.out.println(listeners);
    }
}

notify sms
[email, sms, push]

Good for: lists that are read very often and changed rarely, such as event listeners or a list of feature flags. Bad for: large lists with frequent writes, since each write copies everything (O(n)). With an ordinary ArrayList the same loop would throw ConcurrentModificationException. A set version exists: CopyOnWriteArraySet.

BlockingQueue implementations

A BlockingQueue makes put wait when full and take wait when empty, so producers and consumers need no wait/notify. It extends Queue with timed versions (offer(e, time, unit), poll(time, unit)).

For the non-blocking world: ConcurrentLinkedQueue and ConcurrentLinkedDeque are unbounded, lock-free (CAS-based) queues. poll() returns null when empty; there is no waiting. Use them when you never want to block. Note that their size() walks the whole queue, so it is O(n).

Exceptions and edge cases

  • NullPointerException — ConcurrentHashMap.put(k, null) or a null key; also null elements in blocking queues.
  • IllegalStateException: Queue full — add() on a full bounded queue (offer returns false, put blocks).
  • UnsupportedOperationException — remove() on an iterator of CopyOnWriteArrayList, which works on a snapshot.
  • Thread-safe collections do not make your compound logic safe: if (!map.containsKey(k)) map.put(k, v) is still a race. Use putIfAbsent.
  • Values stored in the map are not protected: a ConcurrentHashMap<String, List<String>> with an ArrayList value still needs the inner list to be thread-safe.

Real projects

In-memory caches (computeIfAbsent to load once per key), counters and rate-limit buckets per user, registries of active sessions or WebSocket connections, and work queues between an HTTP thread and background workers. Careful: computeIfAbsent with a slow loader holds the bin lock; for real caching use Caffeine.

Interview: "How does ConcurrentHashMap work? synchronizedMap vs ConcurrentHashMap?"

  • Java 8+: CAS for empty bins, synchronized on the first node of a bin otherwise; lock-free reads; no nulls; weakly consistent iterators.
  • Atomic merge, compute, putIfAbsent prevent check-then-act races.
  • synchronizedMap uses one global lock and needs manual locking for iteration and compound actions.
  • Copy-on-write is for read-mostly lists; blocking queues for producer-consumer.

Synchronizers: CountDownLatch, CyclicBarrier and Semaphore

Synchronizers coordinate threads without you writing wait/notify: a CountDownLatch waits for a number of events once, a CyclicBarrier makes a group of threads wait for each other repeatedly, and a Semaphore limits how many threads use a resource at once.

CountDownLatch: wait until N things are done

A latch starts with a count. Worker threads call countDown() when they finish; another thread calls await() and blocks until the count reaches zero. It is one-shot: once at zero it stays open and cannot be reset. Typical use: wait for services to start, or start many threads at the same instant (a "starting gun" with count 1).

import java.util.concurrent.*;

public class StartupCheck {
    public static void main(String[] args) throws InterruptedException {
        CountDownLatch ready = new CountDownLatch(3);

        for (String svc : new String[] {"database", "cache", "queue"}) {
            Thread.ofPlatform().start(() -> {
                try {
                    Thread.sleep(200);                 // pretend to start up
                    System.out.println(svc + " started");
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    ready.countDown();                 // always count down
                }
            });
        }

        ready.await();                                 // main waits here
        System.out.println("All services up, accepting traffic");
    }
}

database started
queue started
All services up, accepting traffic

Put countDown() in a finally. If a worker fails and never counts down, await() waits forever; the overload await(timeout, unit) returns false on timeout and is safer.

CyclicBarrier: wait for each other, again and again

A barrier is created for N parties. Each thread calls await(); the first N-1 block, and when the Nth arrives they all continue together. Then the barrier resets and can be used again, which makes it suit phased algorithms ("everyone finish step 1 before anyone starts step 2"). An optional barrier action runs once per round, in the last thread to arrive.

import java.util.concurrent.*;

public class BarrierDemo {
    public static void main(String[] args) {
        CyclicBarrier barrier = new CyclicBarrier(3,
                () -> System.out.println("-- all three finished this round --"));

        for (int w = 1; w <= 3; w++) {
            int id = w;
            Thread.ofPlatform().start(() -> {
                try {
                    for (int round = 1; round <= 2; round++) {
                        System.out.println("worker " + id + " done round " + round);
                        barrier.await();               // wait for the others
                    }
                } catch (InterruptedException | BrokenBarrierException e) {
                    Thread.currentThread().interrupt();
                }
            });
        }
    }
}

Semaphore: limit concurrent access

A semaphore holds a number of permits. acquire() takes one (blocking when none are left); release() gives one back. With N permits at most N threads are inside the protected section. With 1 permit it works like a lock (but without an owner, so any thread can release). Use cases: limit calls to a rate-limited partner API, cap the number of open DB-heavy jobs, or limit concurrency when using virtual threads.

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class RateLimit {
    static final Semaphore permits = new Semaphore(3);       // max 3 calls at once
    static final AtomicInteger inside = new AtomicInteger();

    static void callPartnerApi(int id) throws InterruptedException {
        permits.acquire();
        try {
            int now = inside.incrementAndGet();
            System.out.println("request " + id + " running, concurrent=" + now);
            Thread.sleep(300);                                // the slow call
        } finally {
            inside.decrementAndGet();
            permits.release();                                // always release
        }
    }

    public static void main(String[] args) {
        try (ExecutorService pool = Executors.newFixedThreadPool(8)) {
            for (int i = 1; i <= 8; i++) {
                int id = i;
                pool.execute(() -> {
                    try { callPartnerApi(id); }
                    catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                });
            }
        }
    }
}

Eight threads exist but never more than three are in the section at once. Other useful methods: tryAcquire() (do not wait; return false), tryAcquire(time, unit), availablePermits() and the fair constructor new Semaphore(3, true) (longest waiter first).

Beyond these: Phaser (a flexible multi-phase barrier) and Exchanger (two threads swap objects) exist but are rare.

Exceptions and edge cases

  • BrokenBarrierException — another party timed out, was interrupted or the barrier was reset; every waiting thread gets the exception.
  • TimeoutException — timed CyclicBarrier.await ran out of time.
  • IllegalArgumentException — negative count for a latch, or fewer than 1 party for a barrier.
  • A permit leak: acquire() without a release() in finally slowly drains the semaphore until everything blocks.
  • Calling release() more often than acquire() increases the permits beyond the initial value; a Semaphore does not check the owner.

Mistake: latch count that never reaches zero

If three workers must count down but one throws before reaching countDown(), the waiting thread hangs forever. Count down in finally, and prefer await(timeout, unit) in production.

How they work, and why not wait/notify

All three keep a small counter of "permits" or "arrivals" and park threads that must wait. CountDownLatch and Semaphore are built on AbstractQueuedSynchronizer (AQS), the same queue-and-park machinery behind ReentrantLock; CyclicBarrier uses a ReentrantLock and a condition. You get correct blocking, fairness options, timeouts and interruption for free. Writing the same with wait() and notifyAll() is possible (see locks and waiting) but easy to get wrong: lost wake-ups, missing loops, wrong lock. Use the ready-made class whenever one fits.

Two latches in one test harness

Two latches together are a standard pattern for measuring or testing concurrent code: a start gate (count 1) so that all workers begin together, and a done gate (count N) so that the caller knows when all have finished.

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class StartGate {
    public static void main(String[] args) throws InterruptedException {
        int workers = 4;
        CountDownLatch start = new CountDownLatch(1);
        CountDownLatch done = new CountDownLatch(workers);
        AtomicInteger counter = new AtomicInteger();

        for (int i = 0; i < workers; i++) {
            Thread.ofPlatform().start(() -> {
                try {
                    start.await();                       // all workers wait here
                    for (int j = 0; j < 1000; j++) counter.incrementAndGet();
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    done.countDown();
                }
            });
        }
        start.countDown();                               // fire the starting gun
        done.await();                                    // wait for everybody
        System.out.println("Total = " + counter.get());
    }
}
Total = 4000

Semaphore as a mutex, and the permit-leak trap

With one permit a semaphore allows a single thread at a time, but unlike synchronized or ReentrantLock it is not reentrant (a thread that acquires twice blocks itself) and has no owner. That can be useful (acquire in one thread, release in another, as in a hand-off) and dangerous. Placing acquire() inside the try block creates a subtle bug:

Wrong: release runs even when acquire never succeeded

try {
    permits.acquire();            // interrupted here → no permit taken
    doWork();
} finally {
    permits.release();            // still releases: permits grow past the limit
}

Right: acquire before the try

permits.acquire();
try {
    doWork();
} finally {
    permits.release();
}

For "do not wait if the resource is busy" use tryAcquire(): it returns false at once, and you can return a "429 Too Many Requests" or skip the job.

Deadlock with a barrier and a small thread pool

A CyclicBarrier(4) needs four threads waiting at the same time. If you run the four parties on a fixed pool of only two threads, the first two block at the barrier and the other two tasks never start. Nothing fails; the program just hangs. Make the pool at least as large as the number of parties, or use plain threads. The same trap exists for a latch when the task that must count down is queued behind tasks that are blocked in await().

Phaser and Exchanger in one paragraph

Phaser is a barrier whose number of parties can change while it runs (register, arriveAndDeregister) and that has numbered phases. It suits tasks that join and leave a multi-step process. Exchanger lets exactly two threads swap objects at a meeting point, for example a producer handing a full buffer to a consumer and taking back an empty one. Both are rare in application code; know the names and the idea.

Rules

  • A latch cannot be reset. For a repeating event use CyclicBarrier or a new latch each round.
  • Release a semaphore in finally, and acquire before the try.
  • The number of parties in a barrier must match the number of threads that will call await() each round.
  • Do not hold a lock (synchronized) while waiting on a synchronizer unless you are sure the others can still make progress; it is a common way to build a deadlock.

Conventions

  • Use the timed await or tryAcquire forms in production and log what happened on timeout.
  • Restore the interrupt flag when you catch InterruptedException.
  • For ordinary "run these tasks and wait for all", prefer invokeAll or CompletableFuture.allOf (see Callable and Future); use a latch when the events come from different places.
  • Use a semaphore to cap concurrency; use a ThreadPoolExecutor with a bounded queue to cap threads. They solve different problems.

In real projects

Latches appear in integration tests (wait until the Kafka consumer has processed the message) and in startup code. Semaphores guard connections to a partner API with a "10 calls at a time" contract, and bound the number of concurrent downloads in a virtual-thread application, where thread count no longer limits you. Barriers are the least common: parallel simulations and phased batch processing.

Interview: "CountDownLatch vs CyclicBarrier", "What is a Semaphore?"

  • Latch: one-shot, waiting for events; barrier: reusable meeting point for the same threads.
  • Semaphore: counted permits; limit concurrent access; acquire / release in finally.
  • Give a real example for each: startup gate, phased computation, API rate limit.

Deadlock, livelock and starvation

A deadlock happens when threads wait for each other's locks forever; you prevent it by always taking locks in the same order, using timeouts, or holding fewer locks, and you find it with a thread dump.

What a deadlock is

Thread A holds lock 1 and waits for lock 2. Thread B holds lock 2 and waits for lock 1. Neither can continue, and nothing will release the locks, so the program hangs (while using no CPU). The classic business example is a bank transfer: transferring from account X to Y locks X then Y, while a simultaneous transfer from Y to X locks Y then X.

A minimal deadlock program

public class DeadlockDemo {
    static final Object lockA = new Object();
    static final Object lockB = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (lockA) {
                System.out.println("T1 holds A");
                pause();                                   // let T2 grab B
                synchronized (lockB) {
                    System.out.println("T1 holds A and B");
                }
            }
        }, "T1");

        Thread t2 = new Thread(() -> {
            synchronized (lockB) {
                System.out.println("T2 holds B");
                pause();
                synchronized (lockA) {
                    System.out.println("T2 holds B and A");
                }
            }
        }, "T2");

        t1.start();
        t2.start();
    }

    static void pause() {
        try { Thread.sleep(200); } catch (InterruptedException e) { }
    }
}
T1 holds A
T2 holds B

Neither "holds A and B" line is ever printed. The sleep makes the problem happen every time; in real code the timing is rare, which is why deadlocks pass testing and appear in production under load.

The four Coffman conditions

A deadlock needs all four of these at once. Remove any one and it cannot happen.

Mutual exclusion
A resource can be held by only one thread at a time (a lock).
Hold and wait
A thread keeps what it has while waiting for more.
No preemption
A lock cannot be taken away from its holder; only the holder releases it.
Circular wait
A cycle exists: A waits for B, B waits for ... waits for A.

Prevention

  1. Lock ordering (breaks circular wait): every thread takes locks in the same global order. For transfers, lock the account with the smaller id first.
  2. tryLock with timeout (breaks hold and wait / no preemption): use ReentrantLock.tryLock(time, unit); if you cannot get the second lock, release the first, wait a random short time and retry.
  3. Fewer locks, smaller critical sections: one lock for related data, no calls to unknown code ("alien methods", listeners, callbacks) while holding a lock.
  4. Prefer higher-level tools: concurrent collections, atomics and immutable objects need no locks at all.
public class Transfer {
    static class Account {
        final long id;
        long balance;
        Account(long id, long balance) { this.id = id; this.balance = balance; }
    }

    static void transfer(Account from, Account to, long amount) {
        // Always lock the account with the lower id first: same order for every thread
        Account first = from.id < to.id ? from : to;
        Account second = from.id < to.id ? to : from;

        synchronized (first) {
            synchronized (second) {
                if (from.balance < amount) {
                    throw new IllegalStateException("Insufficient balance");
                }
                from.balance -= amount;
                to.balance += amount;
            }
        }
    }
}

Now transfer(x, y, 100) and transfer(y, x, 50) both lock the same account first, so a cycle is impossible. And a version with tryLock:

import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

boolean transferWithTimeout(ReentrantLock a, ReentrantLock b) throws InterruptedException {
    if (a.tryLock(100, TimeUnit.MILLISECONDS)) {
        try {
            if (b.tryLock(100, TimeUnit.MILLISECONDS)) {
                try {
                    // ... move the money ...
                    return true;
                } finally {
                    b.unlock();
                }
            }
        } finally {
            a.unlock();
        }
    }
    return false;       // caller retries later or reports failure
}

Detecting a deadlock with a thread dump

A thread dump is a snapshot of every thread's state and stack. Find your process id with jps (or the task manager), then:

$ jps
12840 DeadlockDemo
$ jstack 12840
$ jcmd 12840 Thread.print      # same result

On Linux you can also send Ctrl+\ (SIGQUIT) to a program started in the terminal. In IntelliJ, use the "Get Thread Dump" camera button while debugging. The JVM analyses the lock graph and prints a section like this (shortened):

  waiting to lock monitor 0x... (object 0x..., a java.lang.Object),
  which is held by "T2"
"T2":
  waiting to lock monitor 0x... (object 0x..., a java.lang.Object),
  which is held by "T1"

Java stack information for the threads listed above:
"T1":

        - waiting to lock <0x...> (a java.lang.Object)
        - locked <0x...> (a java.lang.Object)

Read the stack lines to see which code line each thread is stuck on. Your own code can also check: ManagementFactory.getThreadMXBean().findDeadlockedThreads() returns the ids of deadlocked threads (or null). Monitoring tools use this. Thread dumps help for other hangs too: a thread state BLOCKED or WAITING everywhere points to a lock or pool problem.

Livelock and starvation

  • Livelock: threads are not blocked; they keep reacting to each other and make no progress, like two people in a corridor who both step aside in the same direction again and again. CPU is busy but nothing is done. A typical cause is a retry loop where both threads back off and retry at the same time. Fix: add a random delay (jitter) or a clear priority rule.
  • Starvation: a thread never gets the resource because others keep winning. Examples: low-priority threads that never get CPU time, an unfair lock where one thread always loses, or one long task that fills a small thread pool. Fix: fair locks (new ReentrantLock(true), with some throughput cost), separate pools, shorter critical sections.
ProblemThreads are...CPU useTypical fix
DeadlockBlocked forever, in a cycleNoneLock ordering, timeouts

Rules

  • If you need more than one lock, define and document the order in which they are taken.
  • Never call code you do not control (callbacks, overridable methods, other services) while holding a lock.
  • Always release locks in finally.

Edge cases

  • Deadlocks are not only about synchronized. They also happen with database row locks (two transactions updating the same two rows in opposite order; the database aborts one with a deadlock error), with a thread pool whose tasks wait for other tasks of the same pool, and with join() cycles.
  • synchronized blocks cannot be interrupted while waiting for the lock; ReentrantLock.lockInterruptibly() can.
  • A deadlock with synchronized leaves the JVM running; only restarting (or killing a thread through a different design) recovers.

Interview: "What is a deadlock? How do you prevent and detect it?"

  • Define it with a two-lock example and name the four Coffman conditions.
  • Prevent: consistent lock order, tryLock with timeout, fewer and smaller locks.
  • Detect: jstack/jcmd Thread.print, IntelliJ dump, ThreadMXBean.findDeadlockedThreads().
  • Differentiate livelock (busy but no progress) and starvation (never gets a turn).

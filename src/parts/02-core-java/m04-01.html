Almost every Java program keeps groups of things: the items in a Flipkart cart, the employees of a department, the orders waiting to be packed, a map from user id to profile. The Collections Framework (package java.util) is Java's ready-made toolbox for this. It gives you lists, sets, maps, queues and the algorithms (sorting, searching, shuffling) that work on them. Generics are the feature that lets these containers be type-safe: List<String> holds only strings, and the compiler checks it.

This is the most-asked module in Java interviews. "How does HashMap work internally?", "ArrayList vs LinkedList", "Comparable vs Comparator" and "what is ConcurrentModificationException?" appear in nearly every round. It builds on equals and hashCode from Module 2, and it leads straight into streams (Module 5) and thread-safe collections (Module 6). Spring Data, JPA and REST controllers return and accept collections all day.

After this module you will be able to:

  • draw the Collections hierarchy and pick the right interface and implementation for a job;
  • explain ArrayList, LinkedList, HashSet, TreeSet, LinkedHashMap, TreeMap, ArrayDeque and PriorityQueue with their time complexity;
  • explain step by step how HashMap stores and finds an entry — hashing, buckets, collisions, resizing and treeification;
  • iterate safely, remove while iterating, and explain ConcurrentModificationException;
  • sort objects with Comparable and Comparator, and avoid the classic comparator bugs;
  • use the Collections utility class and know exactly which lists are mutable, immutable, views or copies;
  • write generic classes and methods, use bounded types and wildcards (PECS), and explain type erasure and its limits.

The Collections Framework: hierarchy and choosing a type

The framework is a small set of interfaces (List, Set, Queue, Deque, Map) with several implementations each; you code against the interface and pick the implementation for the performance and ordering you need.

An array has a fixed size, no helper methods and no built-in "add" or "remove". A collection is an object that holds a group of other objects and grows and shrinks as needed. The Java Collections Framework (JCF) is the set of interfaces, implementation classes and algorithms in java.util that standardise this. Because every list has the same methods, you can swap an ArrayList for a LinkedList by changing one word.

The hierarchy

Iterable
The top interface. Anything that implements it can be used in an enhanced for loop. It has one key method, iterator().
Collection
A group of elements. Common methods: add, remove, contains, size, isEmpty, clear, addAll, removeAll, retainAll, stream, toArray.
List
An ordered sequence with positions (index 0, 1, 2…). Allows duplicates. Use it when order and position matter.
Set
No duplicates. "Duplicate" is decided by equals() (and hashCode() for hash sets). Use it for unique ids, tags, visited nodes.
Queue / Deque
A queue holds elements to be processed, normally first in, first out (FIFO). A deque (double-ended queue, said "deck") allows add and remove at both ends, so it also works as a stack.
Map
Key → value pairs with unique keys. It is not a Collection, because its elements are pairs, not single values. Views such as keySet(), values() and entrySet() give you collections.

Sequenced collections (Java 21)

Before Java 21, getting "the last element" was different for every type: list.get(list.size() - 1), deque.getLast(), sortedSet.last(), and for a LinkedHashSet you had to iterate everything. Java 21 added three interfaces for collections that have a defined encounter order: SequencedCollection, SequencedSet and SequencedMap. They add getFirst(), getLast(), addFirst(), addLast(), removeFirst(), removeLast() and reversed() (a reverse-order view). Maps get firstEntry(), lastEntry(), pollFirstEntry(), putFirst(), putLast() and reversed().

import java.util.*;

public class Sequenced {
    public static void main(String[] args) {
        List<String> steps = new ArrayList<>(List.of("Cart", "Address", "Payment"));
        System.out.println(steps.getFirst() + " / " + steps.getLast());   // Java 21
        System.out.println(steps.reversed());                             // a view

        LinkedHashSet<String> seen = new LinkedHashSet<>(List.of("A", "B", "C"));
        seen.addFirst("Z");                       // moves/adds at the front
        System.out.println(seen);

        LinkedHashMap<String, Integer> stock = new LinkedHashMap<>();
        stock.put("pen", 10);
        stock.put("book", 4);
        System.out.println(stock.firstEntry() + " " + stock.lastEntry());
    }
}

List, Deque, LinkedHashSet, LinkedHashMap, SortedSet and SortedMap all became sequenced. HashSet and HashMap did not, because they have no defined order.

Interface vs implementation — program to the interface

An interface (List) says what you can do. An implementation (ArrayList, LinkedList) decides how it is done and how fast. Declare variables, fields, parameters and return types with the interface; use the implementation name only after new.

Wrong: locked to one implementation

ArrayList<String> names = new ArrayList<>();

public ArrayList<String> findAll() { ... }

Right: depends on the behaviour only

List<String> names = new ArrayList<>();

public List<String> findAll() { ... }

Now you can change to new LinkedList<>() or return List.of(...) without touching callers. Use the concrete type only when you need a method the interface lacks, such as ArrayList.ensureCapacity or TreeMap's NavigableMap methods (then declare it as NavigableMap).

Three names that look alike

  • Collection (singular) is the interface.
  • Collections (plural) is a utility class full of static methods such as sort and unmodifiableList (see The Collections utility class).
  • Arrays is another utility class, for arrays: Arrays.sort, Arrays.asList, Arrays.toString.

Collections hold objects, not primitives

You cannot write List<int>. Use the wrapper class List<Integer>. Java converts automatically (autoboxing on the way in, unboxing on the way out). This costs memory — an Integer object is about 16 bytes versus 4 for an int — so for millions of numbers, prefer int[] or IntStream. Unboxing a null throws NullPointerException, and comparing two Integer objects with == works only for small cached values (−128 to 127); always use equals.

Rule: elements of hash-based and sorted collections must behave well

Elements of a HashSet and keys of a HashMap must have consistent equals() and hashCode(). Elements of a TreeSet and keys of a TreeMap must be Comparable or you must pass a Comparator. Otherwise you get missing elements or ClassCastException.

Conventions

  • Declare with the interface: List, Set, Map, Deque. Plural or descriptive names: orders, emailsByUser.
  • Default choices: ArrayList for lists, HashMap for maps, HashSet for sets, ArrayDeque for stacks and queues. Change only when you have a reason.
  • Return an empty collection, never null, from a method that finds nothing.

Edge cases and exceptions

  • NullPointerException — adding null to List.of, ArrayDeque, PriorityQueue, TreeSet or ConcurrentHashMap.
  • UnsupportedOperationException — modifying an immutable collection.
  • ConcurrentModificationException — structurally changing a collection while iterating it.
  • NoSuchElementException — getFirst(), element(), iterator().next() on an empty or finished collection.
  • ClassCastException — putting non-comparable objects into a sorted collection.

Interview: "Explain the Collections hierarchy"

  • Iterable → Collection → List, Set, Queue (→ Deque); Map is separate and does not extend Collection.
  • List = ordered with duplicates; Set = unique; Queue/Deque = processing order; Map = key to value.
  • Mention Java 21 sequenced collections: getFirst, getLast, reversed.
  • "Program to the interface" and why: swap implementations without changing callers.

List: ArrayList vs LinkedList

ArrayList is a resizable array with fast random access and is the right default; LinkedList is a doubly linked list that is almost never faster in practice.

A List is an ordered collection that allows duplicates and lets you read or change an element by its index. The two classic implementations store data very differently, and that difference is the whole interview question.

ArrayList internals

ArrayList keeps its elements in a plain Object[] called elementData and a counter called size. The capacity is the length of the array; the size is how many slots are in use.

  1. new ArrayList<>() starts with an empty shared array — no memory is allocated yet.
  2. The first add allocates an array of default capacity 10.
  3. add(e) writes to elementData[size] and does size++.
  4. When the array is full, ArrayList allocates a new array about 1.5 times bigger (newCapacity = old + old/2: 10 → 15 → 22 → 33 → 49) and copies the old elements across with Arrays.copyOf.
  5. add(index, e) and remove(index) shift every later element one place with System.arraycopy.

Growing by a fixed fraction instead of a fixed amount makes add amortized O(1): an occasional expensive copy is spread over many cheap adds, so the average cost per add stays constant. A single add that triggers a resize is O(n), but that happens rarely.

  • new ArrayList<>(1000) allocates 1,000 slots at once. Do this when you know the final size, to avoid repeated resizing.
  • ensureCapacity(n) grows the array up front before a big batch of adds.
  • trimToSize() shrinks the array to exactly size. remove and clear never shrink the array on their own, so a list that was once huge keeps its memory until you trim it or drop it.
  • ArrayList implements the marker interface RandomAccess, which tells algorithms that get(i) is cheap.

LinkedList internals

LinkedList is a doubly linked list: each element lives in its own Node object holding the item, a link to the next node and a link to the previous node. The list keeps references to the first and last node. It implements both List and Deque.

Adding or removing at either end only changes a couple of links: O(1). But get(i) must walk from the nearer end, one node at a time: O(n). Inserting in the middle is O(1) only if you are already standing at that node (for example with a ListIterator); finding the position first is O(n).

On paper LinkedList wins at the front and the middle. In real programs ArrayList still wins almost every time: array copying is done by fast native code and the CPU cache loves contiguous memory, while a linked list must chase a pointer to every node and allocate an object for every add. Even for a queue, ArrayDeque beats LinkedList. The advice from the author of the framework is simple: use ArrayList unless a measurement tells you otherwise.

Trap: remove(int) vs remove(Object) on List<Integer>

List has two overloads: remove(int index) and remove(Object o). With a List<Integer>, a plain int argument picks the index version, because no boxing is needed for an exact match.

List<Integer> nums = new ArrayList<>(List.of(10, 20, 30, 1));

nums.remove(1);                     // int  → removes the element at INDEX 1
System.out.println(nums);

nums.remove(Integer.valueOf(1));    // Object → removes the VALUE 1
System.out.println(nums);

subList is a view, not a copy

subList(from, to) returns a window onto the same data. Changes to the sublist write through to the original list, and vice versa. This is useful for clearing a range in one line, and dangerous if you forget it.

List<Integer> list = new ArrayList<>(List.of(1, 2, 3, 4, 5, 6));
List<Integer> middle = list.subList(1, 4);   // elements at index 1, 2, 3
System.out.println(middle);

middle.set(0, 99);                           // writes through to the original
System.out.println(list);

middle.clear();                              // removes the range from the original
System.out.println(list);

list.add(7);                                 // structural change to the PARENT
try {
    System.out.println(middle.size());       // the view is now invalid
} catch (ConcurrentModificationException e) {
    System.out.println("CME: view is stale");
}

List<Integer> copy = new ArrayList<>(list.subList(0, 2));   // a real, independent copy
[2, 3, 4]
[1, 99, 3, 4, 5, 6]

LinkedList as a Deque

Because LinkedList is also a Deque, it has addFirst, removeLast, push, pop, peek and friends. It works, but ArrayDeque is faster and lighter for these jobs, with one exception: LinkedList allows null elements and ArrayDeque does not (see Queues and deques).

Rule: indexes must be in range, and lists use equals()

Valid indexes are 0 to size() - 1. add(i, e) also accepts i == size(). Searching methods (contains, indexOf, remove(Object)) compare with equals(), so your element class needs a correct equals.

Exceptions and edge cases

  • IndexOutOfBoundsException (message like Index 5 out of bounds for length 2) — get, set, remove or add(i, e) with a bad index. On an array the exception is ArrayIndexOutOfBoundsException.
  • ConcurrentModificationException — changing the list while a for-each loop or an old subList is using it (see Iteration).
  • new ArrayList<>(-1) throws IllegalArgumentException; new ArrayList<>(0) is fine.
  • An empty list's getFirst() (Java 21) throws NoSuchElementException.
  • Removing from the middle of a huge ArrayList in a loop is O(n²). Use removeIf or build a new list.

Mistake: removing inside a for-each loop

for (String s : list) { if (...) list.remove(s); } usually throws ConcurrentModificationException. Use list.removeIf(...) or an Iterator.

Tips

  • Copy a list: new ArrayList<>(other). Make a read-only copy: List.copyOf(other).
  • Need to insert or remove at the front a lot? Use ArrayDeque, not LinkedList.
  • Pre-size with new ArrayList<>(expectedSize) when loading many rows from a database.

Real projects

Spring Data repositories return List<Entity> (an ArrayList underneath), and REST controllers return lists that Jackson turns into JSON arrays. In the whole of a typical codebase you will see ArrayList hundreds of times and LinkedList almost never.

Interview: "ArrayList vs LinkedList"

  • ArrayList: dynamic array, O(1) random access, amortized O(1) add at the end, O(n) insert/remove in the middle, default capacity 10, grows about 1.5×.
  • LinkedList: doubly linked nodes, O(n) access by index, O(1) at the ends, also a Deque, more memory per element.
  • Strong answer: "ArrayList in almost all cases, because of cache locality and cheap copying; LinkedList's O(1) insert is only real when you already hold the node."
  • Follow-ups: what is amortized O(1)? What does subList return? What does list.remove(1) do on a List<Integer>?

How HashMap works inside

HashMap turns each key into a bucket index with hashCode(), stores the entry in that bucket, and uses equals() to find the exact key inside the bucket; it doubles its table when 75% full and turns long buckets into red-black trees.

A HashMap<K, V> stores key → value pairs and finds a value by its key in O(1) on average — whether the map has ten entries or ten million. This is the most asked Java interview topic, so we will build it up step by step. The idea: do not search; calculate where the entry must be.

The data structure: a table of buckets

Inside a HashMap there is an array called table. Each slot of the array is a bucket. A bucket is either empty (null) or holds a chain of Node objects. Each Node stores four things: the hash of the key, the key, the value, and a next link to the next node in the same bucket.

The table is created lazily — new HashMap<>() allocates nothing; the first put creates a table of the default capacity 16. Capacity is always a power of two.

Step 1 to 3: from key to bucket index

  1. hashCode() — call key.hashCode(), which returns an int. (A null key gets hash 0.)
  2. Spread — HashMap mixes the high bits into the low bits: h ^ (h >>> 16). This is the method hash(key) inside HashMap.
  3. Index — index = (n - 1) & hash, where n is the table length.

Why the spread? The index uses only the low bits of the hash (for n = 16, only the lowest 4 bits). Many real hash codes differ mainly in their upper bits, so without mixing they would pile into the same buckets. h ^ (h >>> 16) XORs the upper 16 bits into the lower 16 — cheap, and it makes every bit of the hash count a little.

Why (n - 1) & hash and not hash % n? When n is a power of two, n - 1 is a mask of all ones (for 16: 0b1111), and hash & mask equals hash % n for non-negative numbers — but it is a single fast CPU instruction, and it also works for negative hashes (% can return a negative number). It also makes resizing simple, as you will see below. Because of this trick the capacity must be a power of two; new HashMap<>(20) is rounded up to 32.

public class IndexDemo {
    static int spread(int h) {
        return h ^ (h >>> 16);               // same formula as HashMap.hash()
    }

    public static void main(String[] args) {
        int n = 16;                              // table length
        for (int key : new int[] {1, 17, 33, 65553}) {
            int h = spread(Integer.hashCode(key));   // Integer.hashCode(k) is k itself
            System.out.println(key + " -> hash " + h + " -> index " + (h & (n - 1)));
        }
        System.out.println("Aa".hashCode() + " " + "BB".hashCode());
    }
}
1 -> hash 1 -> index 1
17 -> hash 17 -> index 1
33 -> hash 33 -> index 1
65553 -> hash 65552 -> index 0
2112 2112

Look at the first three lines: 1, 17 and 33 land in the same bucket — they differ only in bits above the lowest four. The key 65553 (binary 1 0000 0000 0001 0001) would have gone to bucket 1 without the spread; the XOR with its upper half moved it to bucket 0. The last line shows two different strings with the same hash code, 2112 — a hash collision in the strict sense.

put(key, value) step by step

How two keys are judged equal inside a bucket: first hash == otherHash (a cheap int comparison that rejects most non-matches), then key == otherKey (same reference), then key.equals(otherKey). This is why hashCode picks the bucket and equals picks the exact entry. Inserting a key that already exists replaces the value, keeps the old key object, and returns the old value (or null if there was none).

get(key) step by step

  1. Compute the hash and the bucket index, exactly as in put.
  2. If the bucket is empty, return null.
  3. If the first node matches (hash equal and key same or equals), return its value.
  4. Otherwise walk the rest of the chain (or search the tree) with the same comparison. Return the value on a match, null if you reach the end.

With a good hash function and a low load factor, chains are 0 to 2 nodes long, so get does a constant amount of work. That is the O(1).

Capacity, load factor, threshold and resizing

Capacity
The length of the table. Default 16, always a power of two.
Load factor
How full the table may get before it grows. Default 0.75 — a balance between wasted space (low factor) and long chains (high factor).
Threshold
capacity × load factor. With the defaults it is 16 × 0.75 = 12. When the number of entries goes above the threshold (the 13th put), the map resizes.
Resize (rehash)
Create a new table of double the capacity and move every node into it. Capacity 16 → 32 → 64 → 128; thresholds 12 → 24 → 48 → 96.

Resizing is O(n), but it is rare, so put is still O(1) amortized. The index depends on the table length, so entries must move. Because the new length is exactly double, the new index of a node is either its old index or old index + old capacity. The extra bit that decides is hash & oldCapacity: if it is 0 the node stays, if it is 1 the node moves up by oldCapacity. Java 8 uses this to split each bucket into a "low" and a "high" chain without recomputing indexes, and it keeps the relative order of the nodes (the old Java 7 code reversed chains, which could create infinite loops in racy multi-threaded code).

Tip: size the map when you know the data

To hold 1,000 entries without any resize, the table needs a threshold above 1,000, so capacity 2,048 (1,000 / 0.75 = 1,334, rounded up to a power of two). new HashMap<>(1000) is not enough: it rounds to 1,024, threshold 768. Use new HashMap<>((int) (1000 / 0.75f) + 1), or since Java 19 the clearer HashMap.newHashMap(1000). This matters only for big maps in hot code.

Collisions: chains, then trees

A collision happens when two different keys land in the same bucket. It cannot be avoided: there are about 4 billion possible hash codes, far more keys than buckets, and the table is much smaller than that. HashMap handles it by separate chaining: nodes in one bucket are linked in a list, and a lookup walks the list using equals.

If many keys share a bucket (a poor hashCode, or an attacker choosing keys on purpose), the chain becomes long and lookup degrades to O(n). Java 8 added a defence:

ConstantValueMeaning
TREEIFY_THRESHOLD8When a chain reaches 8 nodes and another is added (the bucket would hold 9), it is considered for conversion to a tree
MIN_TREEIFY_CAPACITY64The table must have at least 64 buckets; if smaller, the map resizes instead, hoping to spread the keys
UNTREEIFY_THRESHOLD6A tree bin that shrinks to 6 nodes or fewer (after removals or a resize split) turns back into a chain

A tree bin is a red-black tree (a self-balancing binary search tree). Nodes are ordered first by hash; if two hashes are equal, by compareTo when the key class implements Comparable of its own type, and otherwise by a tie-breaking identity hash. Lookup in a tree bin is O(log n) instead of O(n). So the worst case of get in Java 8+ is O(log n) when keys are Comparable, and the common case is O(1). The gap between 8 (treeify) and 6 (untreeify) prevents a bucket from flipping back and forth when entries are added and removed around one number.

Null key and null values

HashMap allows one null key (its hash is 0, so it lives in bucket 0) and any number of null values. Because get(k) returns null both for "absent" and for "present with a null value", use containsKey(k) to tell them apart. Hashtable and ConcurrentHashMap reject null keys and values with a NullPointerException.

Why equals() and hashCode() must agree

The lookup first jumps to a bucket using hashCode(), then confirms with equals(). The contract between them: if a.equals(b) is true, then a.hashCode() == b.hashCode(). The reverse is not required (collisions are allowed). If you override equals but not hashCode, two "equal" objects get different identity-based hash codes, so they usually point to different buckets and the map never compares them. See equals() and hashCode() in Module 2.

import java.util.*;

public class MissingHashCode {
    static class Pt {                       // overrides equals only
        final int x, y;
        Pt(int x, int y) { this.x = x; this.y = y; }
        @Override public boolean equals(Object o) {
            return o instanceof Pt p && p.x == x && p.y == y;
        }
    }

    record Pos(int x, int y) {}             // a record gets equals AND hashCode

    public static void main(String[] args) {
        Map<Pt, String> bad = new HashMap<>();
        bad.put(new Pt(1, 2), "home");
        System.out.println(bad.get(new Pt(1, 2)));      // equal object, different hash

        Map<Pos, String> good = new HashMap<>();
        good.put(new Pos(1, 2), "home");
        System.out.println(good.get(new Pos(1, 2)));
    }
}

Pitfall: mutable keys

If a field used in hashCode changes after the key is in the map, the node stays in the old bucket with the old stored hash, but a lookup now computes a new hash and looks in the wrong place. The entry is still counted in size(), yet get cannot find it. It is lost until the key is changed back.

import java.util.*;

public class MutableKey {
    static class Key {
        int id;
        Key(int id) { this.id = id; }
        @Override public boolean equals(Object o) {
            return o instanceof Key k && k.id == id;
        }
        @Override public int hashCode() { return Objects.hash(id); }   // 31 + id
    }

    public static void main(String[] args) {
        Map<Key, String> map = new HashMap<>();
        Key k = new Key(1);
        map.put(k, "order-1");

        k.id = 2;                                   // mutate a field used in hashCode
        System.out.println("size = " + map.size());
        System.out.println("get = " + map.get(k));
        System.out.println("containsKey = " + map.containsKey(k));

        k.id = 1;                                   // restore it
        System.out.println("get after restore = " + map.get(k));
    }
}
size = 1
get = null
containsKey = false
get after restore = order-1

The fix is to use immutable keys: String, Integer, Long, enums, UUID, records with immutable fields. That is why String is such a popular key. A good key class has final fields and a stable hashCode.

Iteration order is not defined

HashMap iterates bucket by bucket, from index 0 up, and each chain in order. That order depends on the hash codes, the table size and the insert history, and it can change after a resize or between Java versions. Small Integer keys often come out sorted by accident (the hash is the number, the index is the number), which fools beginners. Never rely on it: if you need an order, use LinkedHashMap (insertion order) or TreeMap (sorted), see Map implementations.

HashMap is not thread-safe

Two threads calling put on the same HashMap can overwrite each other's entries, lose updates, corrupt the structure during a resize, or throw ConcurrentModificationException in readers. The result is not "slightly wrong" but undefined. If several threads share a map, choose one of these:

Rules for map keys

  • Override equals and hashCode together, using the same fields.
  • Do not change fields used by hashCode while the object is a key.
  • Do not rely on iteration order. Do not share a plain HashMap between threads.

Edge cases and exceptions

  • Constructor arguments: negative capacity or a load factor ≤ 0 throws IllegalArgumentException. A very high load factor saves memory but lengthens chains; a low one wastes memory.
  • Maximum capacity is 230 (about 1.07 billion buckets). Past that the table stops growing and chains lengthen.
  • ConcurrentModificationException — adding or removing an entry while iterating keySet(), values() or entrySet(). Changing the value of an existing key does not count as a structural change.
  • A key with a constant hashCode() (like return 1;) is legal but makes the map behave like a list or tree: correct, but slow.
  • Keys that are float/double wrappers: Double.NaN equals itself in Double.equals, and 0.0 and -0.0 are different keys.

Mistake: a key class without hashCode, or with a mutable key

"I put the object in the map and now get returns null." Nine times out of ten the key class lacks hashCode, or a key field was changed after insertion. Use records or immutable keys.

Real projects

HashMap is used for lookups by id (Map<Long, Customer>), grouping (Collectors.groupingBy returns a HashMap), counting, and in-memory caches. Hibernate's first-level cache, Spring's bean registry and Jackson's field maps are all hash maps. For a cache shared across requests use ConcurrentHashMap (or a library such as Caffeine), never a plain HashMap.

Interview: "How does HashMap work internally?" — the model answer

  • An array of buckets (Node[] table), default capacity 16, load factor 0.75, threshold 12.
  • put: hashCode() → spread with h ^ (h >>> 16) → index (n - 1) & hash. Empty bucket: store the node. Otherwise compare hash then equals along the chain; replace the value on a match, else append.
  • get: same index, then walk the bucket comparing hash and equals.
  • Collisions use a linked list; at 8+ nodes (table ≥ 64) the bucket becomes a red-black tree, back to a list at 6.
  • When size exceeds the threshold the table doubles and nodes are redistributed (old index or old index + old capacity).
  • Allows one null key; not thread-safe; iteration order undefined; keys must have a consistent equals/hashCode and should be immutable.

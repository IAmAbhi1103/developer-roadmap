Encapsulation: private data, safe methods, getters and setters

Encapsulation means keeping an object's data private and letting other code change it only through methods that check the rules, so the class alone controls its own state.

Encapsulation is the first of the four pillars. The word comes from "capsule": the data and the code that works on it are packed together, and the outside world sees only a small, safe surface. Why OOP already showed the idea with an Account class; this article gives you the complete set of rules.

Two ideas in one pillar

  • Bundling — the fields and the methods that work on them live together in one class.
  • Information hiding — the fields are private; other code uses public methods only. The class decides what is visible (access modifiers).

Why bother? Four practical benefits:

  • Invariants stay true. An invariant is a rule that must always hold: "a price is positive", "a balance never goes below zero". If only the class can change the data, only the class has to enforce the rule.
  • You can change the inside. Today the price is a long in paise; next year it becomes a BigDecimal. Callers do not break, as long as the public methods stay the same.
  • One place for extra work. Logging, validation, caching and thread safety (synchronized, Module 6) go into the method, not into every caller.
  • A smaller surface. Less public code means less that other developers can misuse or depend on.

Private fields plus methods that guard them

The pattern has two steps: make every field private, then add methods that check the rules before changing anything. Rules that apply to construction go into the constructor, so an invalid object can never exist.

public class ProductDemo {
    static class Product {
        private final String sku;              // never changes: final, no setter
        private String name;
        private long pricePaise;

        Product(String sku, String name, long pricePaise) {
            this.sku = requireText(sku, "sku");
            this.name = requireText(name, "name");
            this.pricePaise = requirePositive(pricePaise, "pricePaise");
        }

        void rename(String newName) { this.name = requireText(newName, "name"); }
        void changePrice(long newPricePaise) {
            this.pricePaise = requirePositive(newPricePaise, "pricePaise");
        }
        String getName()     { return name; }
        long getPricePaise() { return pricePaise; }

        private static String requireText(String value, String field) {
            if (value == null || value.isBlank()) {
                throw new IllegalArgumentException(field + " must not be blank");
            }
            return value.strip();
        }

        private static long requirePositive(long value, String field) {
            if (value <= 0) {
                throw new IllegalArgumentException(field + " must be positive, got " + value);
            }
            return value;
        }
    }

    public static void main(String[] args) {
        Product p = new Product("SKU-1", "  Wireless Mouse ", 49_900);
        p.changePrice(44_900);
        System.out.println(p.getName() + " costs " + p.getPricePaise() + " paise");
        try { p.changePrice(-1); }
        catch (IllegalArgumentException e) { System.out.println("Rejected: " + e.getMessage()); }
        try { new Product(" ", "Cable", 100); }
        catch (IllegalArgumentException e) { System.out.println("Rejected: " + e.getMessage()); }
    }
}
Wireless Mouse costs 44900 paise
Rejected: pricePaise must be positive, got -1
Rejected: sku must not be blank

Look at the design choices. The checks live in two small private static helpers, so the constructor and the change methods share them. The constructor does not call the public methods rename() or changePrice(), because a subclass could override those, and calling an overridable method from a constructor is a trap (initialization order). And sku has no setter at all: it is final.

Getters and setters, and JavaBeans naming

A getter reads a field and a setter changes it. Java has a naming convention for them, called the JavaBeans convention. Frameworks depend on it: Jackson turns JSON into objects with it, Spring binds configuration properties with it, JPA can read entity state through it, and template engines use it.

FieldGetterSetter
private String namegetName()setName(String name)
private int stockgetStock()setStock(int stock)
private boolean activeisActive()setActive(boolean active)
private String firstNamegetFirstName()setFirstName(String firstName)
  • The property name is the method name without get, is or set, with the first letter in lower case: getFirstName() is the property firstName.
  • A getter has no parameters and returns the value. A setter has one parameter and normally returns void. Both are public.
  • For a primitive boolean, the getter is named isX().
  • A class that has a public no-argument constructor, private fields and getters and setters like this is called a JavaBean. A POJO ("plain old Java object") is looser: any ordinary class that does not depend on a framework.

Records do not follow this convention: a record component name gets an accessor called name(), not getName() (records). Modern Jackson versions know about records.

A setter is not a free pass

Beginners learn "make fields private and add a getter and a setter for each". Followed blindly, this gives you a public field with extra typing: setBalance(-500) breaks the rule just like balance = -500. The goal is not to hide the field; it is to protect the rule.

  • If a value never changes (an id, a creation time), make the field final and write no setter.
  • If a value changes for a business reason, write a method named after that reason: withdraw(), rename(), cancel(), changePrice().
  • If you must have a setter, put the validation in it. A setter that only does this.x = x protects nothing.

Wrong: ask, decide outside, push back

if (order.getStatus() == Status.PLACED) {
    order.setStatus(Status.CANCELLED);   // every caller repeats the rule
}

Right: tell the object what you want

order.cancel();    // Order knows which states may be cancelled
                   // and throws IllegalStateException otherwise

This habit has a name: tell, don't ask. Do not pull data out of an object, make a decision, and push a new value back. Tell the object what to do and let it decide. The business rule then lives in one class.

Do not leak mutable internals

Private fields are not enough if a getter hands out the internal object. A private List returned by a getter is a public list: the caller can add, remove or clear it, and your class never finds out.

import java.util.*;

public class CartDemo {
    static class ShoppingCart {
        private final List<String> items = new ArrayList<>();

        public void add(String item) { items.add(Objects.requireNonNull(item, "item")); }

        public List<String> leakyItems()    { return items; }                 // BAD
        public List<String> itemsView()     { return Collections.unmodifiableList(items); }
        public List<String> itemsSnapshot() { return List.copyOf(items); }
    }

    public static void main(String[] args) {
        ShoppingCart cart = new ShoppingCart();
        cart.add("Mouse");

        cart.leakyItems().add("Hacked");          // the cart never agreed to this
        System.out.println("after leak: " + cart.itemsSnapshot());

        List<String> view = cart.itemsView();
        List<String> snap = cart.itemsSnapshot();
        cart.add("Keyboard");
        System.out.println("view:     " + view);
        System.out.println("snapshot: " + snap);
        try { view.add("x"); }
        catch (UnsupportedOperationException e) { System.out.println("view is read-only"); }
    }
}

The same idea applies to arrays (return prices.clone()), to maps, and to any mutable object, such as java.util.Date. Copying data into the object is just as important; that is covered in immutable classes and defensive copies.

Rule: all fields private, all rules in one place

Declare fields private (constants excepted). Check every rule in the constructor and in the methods that change state, never in the caller. Never return or store a reference to a mutable object you want to protect without copying it.

Conventions

  • Fail fast: reject bad input at the door. Use IllegalArgumentException for a bad value, NullPointerException (through Objects.requireNonNull(x, "x")) for an unexpected null, and IllegalStateException when the object is in the wrong state for the call.
  • Follow the JavaBeans names (getX, isX, setX) for classes that frameworks will read. Avoid names that start with two capital letters, such as getURL(): different tools derive different property names from them.
  • Make fields final by default. Remove final only when the value must change.
  • Money is a long of paise or a BigDecimal, never a double.

Exceptions to "everything private"

  • Constants are public static final.
  • Plain data carriers such as records and DTOs (data transfer objects) have no rules to protect, so hiding gains little; a record's components are its public API.
  • A private nested class that only its outer class can see may have package-private fields (private static class Node { int value; Node next; }) because the class itself is hidden.
  • Runtime errors you will meet: UnsupportedOperationException when you modify a read-only view or List.of(…); NullPointerException from requireNonNull.

Mistakes to avoid

  • Getter and setter for every field (the "anemic" class). It adds ceremony and removes no risk. Think about behaviour first.
  • Returning internal collections or arrays directly, as shown above.
  • Validation only in the controller. Bean Validation on a request object checks the shape of input, but jobs, tests and imports create domain objects too. Keep the core rules in the domain class itself.
  • Calling a public setter from a constructor. A subclass may override it and run before its own fields are ready.

In a real Spring Boot project

JPA entities have private fields, a protected no-argument constructor, getters, and a few behaviour methods such as order.cancel(). Request and response DTOs are usually records. Lombok's @Getter and @Setter generate the boilerplate at compile time; they save typing, but a @Setter on every field brings back the problem of this article. Putting @Data on a JPA entity is widely discouraged, because the generated equals, hashCode and toString can trigger lazy loading and loops.

Interview: "What is encapsulation? Is it just getters and setters?"

  • Encapsulation = bundling data and methods together and hiding the data behind private fields, so that the object controls how its state changes.
  • Getters and setters are only the mechanism. The point is to protect invariants: validate in constructors and setters, expose behaviour (withdraw) rather than raw state, and never leak mutable internals.
  • Give the benefits: invariants, freedom to change internals, one place for logging and thread safety.
  • Be ready for "encapsulation vs abstraction": encapsulation protects state; abstraction hides complexity behind a contract (abstraction).

Immutable classes and defensive copies

An immutable object never changes after it is built; to make a class immutable use a final class, private final fields, no setters, and copy any mutable data that goes in or comes out.

An immutable object is one whose state cannot change after the constructor finishes. The JDK is full of them: String, the wrapper classes (Integer, Long), BigDecimal, LocalDate, Instant, Optional and the collections made by List.of(…). Records are immutable too, with one catch (see records).

Why immutability is worth the effort

  • Thread safety for free. Many threads can read the same object without locks, because nobody can change it (Module 6).
  • Safe to share and to cache. You can pass the object anywhere without copying it. Nobody can alter it behind your back.
  • Safe as a key. A HashMap key whose hash code changes gets lost in the map (equals() and hashCode()). An immutable key can never change its hash.
  • Simple to reason about. An object is either valid or it was never built. There is no "half-updated" state.

The cost is that every "change" creates a new object. For a few objects this is cheap. When you build a big value in many steps (a long string, a large report), use a mutable builder such as StringBuilder and make the final result immutable.

The recipe

  1. Declare the class final (or give it only private constructors), so that no subclass can add mutable state or override a getter.
  2. Make every field private final.
  3. Write no setters and no method that changes a field. To "change" something, return a new object. A method like that is often named withX (a wither).
  4. Copy mutable arguments in the constructor (a defensive copy), so the caller's own reference cannot change your state later.
  5. Never return a mutable field. Return an immutable value, a copy, or a read-only view.
import java.time.LocalDate;
import java.util.*;

public class ImmutableDemo {
    static final class Customer {                          // 1. final class
        private final String name;                         // 2. private final fields
        private final LocalDate dob;                       //    (LocalDate is immutable)
        private final List<String> phones;                 //    (List is not, so we copy it)

        Customer(String name, LocalDate dob, List<String> phones) {
            this.name = Objects.requireNonNull(name, "name");
            this.dob = Objects.requireNonNull(dob, "dob");
            this.phones = List.copyOf(phones);             // 4. defensive copy, immutable
        }

        String getName() { return name; }
        LocalDate getDob() { return dob; }
        List<String> getPhones() { return phones; }        // 5. safe: already immutable

        Customer withName(String newName) {                // 3. "change" = new object
            return new Customer(newName, dob, phones);
        }
    }

    public static void main(String[] args) {
        List<String> phones = new ArrayList<>(List.of("98100 00001"));
        Customer c = new Customer("Asha", LocalDate.of(1995, 4, 12), phones);

        phones.add("98100 00002");                         // caller changes its own list
        System.out.println(c.getPhones());                 // the customer did not change

        try { c.getPhones().add("x"); }
        catch (UnsupportedOperationException e) { System.out.println("cannot modify phones"); }

        Customer c2 = c.withName("Asha K");
        System.out.println(c.getName() + " / " + c2.getName());
    }
}

Defensive copies: copy in, copy out

A defensive copy is a private copy of a mutable object that you keep so that nobody else can change it. You need one at two points: when the object arrives (constructor or setter argument) and when it leaves (getter return value). The old java.util.Date class is a perfect example of the problem, because it is mutable:

Wrong: stores and returns the caller's Date

final class Event {
    private final Date start;                 // final reference, mutable object
    Event(Date start) { this.start = start; }
    Date getStart()   { return start; }
}

// in main():
Date d = new Date(1_000_000L);
Event e = new Event(d);
d.setTime(0);                                 // caller changes its own object
System.out.println(e.getStart().getTime());   // 0: the Event changed!
e.getStart().setTime(5);                      // a reader changes it via the getter
System.out.println(d.getTime());              // 5

Right: use an immutable type (or copy)

final class Event {
    private final Instant start;              // Instant is immutable
    Event(Instant start) {
        this.start = Objects.requireNonNull(start);
    }
    Instant getStart() { return start; }      // nothing to protect
}
// If you are stuck with Date: copy in and copy out
//   this.start = new Date(start.getTime());
//   return new Date(start.getTime());

The output of the wrong version is 0 and then 5. Modern code uses java.time (Instant, LocalDate, LocalDateTime), which is immutable, so the problem disappears.

Copy first, then validate the copy

When a constructor checks a mutable argument and then stores it, another thread could change the argument between the check and the copy. Copy first, and validate the copy:

final class DiscountSlabs {
    private final List<Integer> thresholdsPaise;

    DiscountSlabs(List<Integer> thresholdsPaise) {
        List<Integer> copy = List.copyOf(thresholdsPaise);  // 1. copy first
        if (copy.isEmpty()) {                               // 2. check the copy,
            throw new IllegalArgumentException("slabs required");   //    not the argument
        }
        this.thresholdsPaise = copy;
    }
}

List.copyOf throws NullPointerException if the list or any element is null, so you get null-checking for free.

Shallow and deep immutability

A final field only means the reference cannot change. An object is deeply immutable only if everything it can reach is immutable too. Ask this question for every field:

Field typeSafe to share?
int, long, boolean, String, BigDecimal, LocalDate, enumsYes: immutable
List.copyOf(…), Map.copyOf(…), List.of(…)Yes, if the elements are immutable too
ArrayList, HashMap, arrays, Date, StringBuilderNo: copy them in and out
Your own classOnly if that class is immutable

A List.copyOf of StringBuilder objects is an immutable list, but each builder inside can still change. That is why the second half of the table says "if the elements are immutable too".

Edge cases

  • Non-final classes break the guarantee. A subclass can add a mutable field or override a getter to return something changing. That is why step 1 matters.
  • String still has a non-final field. It caches its hash code in a private field after the first call. From the outside it is immutable, and this is fine. Immutability is about visible state.
  • Reflection can still change private final fields of ordinary classes (setAccessible(true)). That is abuse, not a design problem you must defend against.
  • Memory model. The Java memory model gives final fields a special guarantee: once the constructor ends, other threads see their correct values even without synchronization, as long as this did not escape during construction (Module 6).
  • Many fields? An immutable class with ten fields is awkward to construct. Use a builder (nested classes) or a record with static factories.

Mistake: thinking final makes the object immutable

Wrong: final reference, mutable list

private final List<String> tags = new ArrayList<>();
public List<String> getTags() { return tags; }   // callers can add and remove

Right: immutable inside, immutable outside

private final List<String> tags;
Product(List<String> tags) { this.tags = List.copyOf(tags); }
public List<String> getTags() { return tags; }

In real projects

Value objects such as Money, Email or OrderId, request and response DTOs, domain events, cache values and configuration objects are all good immutable classes. JPA entities are mutable by nature, so keep them out of caches and out of shared state; map them to immutable DTOs at the edges of your service.

Interview: "How do you make a class immutable? Why is String immutable?"

  • List the five steps: final class, private final fields, no setters, defensive copies in, no mutable internals out.
  • Add the trap: final alone is not enough — a final field can point to a mutable list.
  • Why String is immutable: the string pool can share one object safely; it is used for security-sensitive values (file paths, URLs, class names, credentials); it is thread safe; and its cached hash code makes it a fast HashMap key.
  • Cost: more objects. Mention StringBuilder as the usual escape for heavy changes.

Inheritance: extends, super and the is-a relationship

With extends, a subclass receives the accessible fields and methods of its parent and can add or change behaviour; use it only when the subclass really is a kind of the parent, because it ties the two classes together.

Inheritance lets one class build on another. The existing class is the superclass (also called parent or base class). The new class is the subclass (child or derived class). The subclass inherits the parent's accessible members, so you do not copy code, and an object of the subclass can be used wherever the parent type is expected. That second point is what makes polymorphism possible.

A first example

Every employee has a name and a salary. A manager is an employee who also gets a bonus and can approve leave.

public class Employee {
    private final String name;
    private final long baseSalary;            // rupees per month

    public Employee(String name, long baseSalary) {
        this.name = name;
        this.baseSalary = baseSalary;
    }

    public String getName() { return name; }
    public long monthlyPay() { return baseSalary; }

    @Override public String toString() { return name + " earns " + monthlyPay(); }
}
public class Manager extends Employee {
    private final long bonus;

    public Manager(String name, long baseSalary, long bonus) {
        super(name, baseSalary);               // build the Employee part first
        this.bonus = bonus;
    }

    @Override public long monthlyPay() {
        return super.monthlyPay() + bonus;     // reuse the parent's logic, then add
    }

    public void approveLeave(Employee e) {
        System.out.println(getName() + " approved leave for " + e.getName());
    }
}
public class Main {
    public static void main(String[] args) {
        Employee e = new Employee("Asha", 50_000);
        Manager m = new Manager("Ravi", 80_000, 15_000);
        System.out.println(e);
        System.out.println(m);                 // toString() is inherited from Employee
        m.approveLeave(e);

        Employee asEmployee = m;               // a Manager IS-A Employee
        System.out.println(asEmployee.monthlyPay());
    }
}
Asha earns 50000
Ravi earns 95000
Ravi approved leave for Asha
95000

Three things happened. Manager got getName() and toString() without writing them. Manager added a field and a method. And it changed a behaviour by overriding monthlyPay(). The last line shows that a Manager object works through an Employee variable, and still uses its own version of monthlyPay().

What is inherited and what is not

public and protected fields and methodsInherited and usable by name
Package-private membersInherited only if the subclass is in the same package
private membersNot accessible by name. The data is still inside every object, but only the parent's own methods can touch it
ConstructorsNot inherited. Each class has its own and calls the parent's with super(…)

Initializer blocksNot inherited, but the parent's blocks still run when a child object is built

The private rule surprises people. A Manager object does contain the baseSalary field; you can see its effect in monthlyPay(). But code written in Manager cannot name it: return baseSalary; there is a compile error (baseSalary has private access in Employee). The subclass must use the parent's public or protected methods. This keeps the parent in control of its own data.

Every constructor runs a parent constructor first. If you write neither this(…) nor super(…), the compiler adds super(). If the parent has no no-argument constructor, you must call a parent constructor yourself. The full story, including the order in which things run, is in constructors and initialization order.

Single inheritance, Object and the diamond problem

A Java class can extend only one class. Every class extends Object, either directly or through its parents, so even Manager has equals() and hashCode() (the Object class). Chains of any length are fine: Object → Employee → Manager → Director.

Why not two parents? Imagine class D extends B, C where B and C both extend A and both override the method work(). Which version does D inherit? This is the diamond problem. If the classes also hold fields, D would get two copies of A's state. Java's designers removed the whole problem by allowing one superclass.

class A { }
class B extends A { }
class C extends A { }
class D extends B, C { }     // javac: error: '{' expected

Java still gives you multiple inheritance of type through interfaces: a class can implement many interfaces. Interfaces carry no instance state, and the rule for conflicting default methods is explicit (interfaces).

The is-a test and substitutability

Before you write extends, say the sentence "a Manager is an Employee". If it sounds natural, inheritance may fit. If you would say "has a" (an Order has a list of items), use a field instead — that is composition (composition vs inheritance).

The sentence is not enough. The deeper test is substitutability, known as the Liskov substitution principle: code written for the parent must keep working when it receives any subclass object. A classic failure:

class Rectangle {
    protected int w, h;
    void setWidth(int w)   { this.w = w; }
    void setHeight(int h)  { this.h = h; }
    int area()             { return w * h; }
}

class Square extends Rectangle {          // "a square is a rectangle" in maths...
    @Override void setWidth(int w)  { this.w = w; this.h = w; }
    @Override void setHeight(int h) { this.w = h; this.h = h; }
}

// in main():
Rectangle r = new Square();
r.setWidth(4);
r.setHeight(5);
System.out.println(r.area());             // 25, but a Rectangle user expects 20

A mutable Square breaks the promise that Rectangle makes (width and height change independently). So here the subclass is a bad idea even though the sentence sounded right. The JDK has its own mistakes: Stack extends Vector and Properties extends Hashtable, so both expose methods that break their purpose. The documentation of Stack tells you to prefer Deque.

Keeping the parent in control: protected and final

  • Keep the parent's fields private. Offer protected methods as deliberate extension points (hooks), not protected fields. Fewer details leak to subclasses, and the parent can change its internals.
  • Mark a method final if no subclass should change it. Mark a class final if it is not designed for extension, which is true of most classes (final).
  • A sealed class lets you name exactly which subclasses are allowed (sealed classes).

Benefits

  • Shared code lives in one place
  • A natural type hierarchy for polymorphism
  • Easy to add a new variant by writing a subclass

Costs

  • The subclass depends on the parent's internals (tight coupling)
  • A change in the parent can break every child (fragile base class)
  • Only one parent class; deep trees are hard to read

Edge cases and compiler errors

  • class X extends SomeInterface → no interface expected here. Use implements. The reverse, class Y implements SomeClass, gives interface expected here.
  • class MyString extends String → cannot inherit from final String.
  • class Q extends Q2 and class Q2 extends Q → cyclic inheritance involving Q.
  • Interfaces can extend several interfaces with extends A, B. An interface cannot extend a class.
  • A subclass can add a method with the same name but different parameters. That is overloading, not overriding (overloading).
  • Constructors, static and instance initializers, and private members are never "overridden". Constructors are not inherited at all.

Mistake: extending a class just to reuse its methods

Wrong: an Order is not a list

class Order extends ArrayList<Item> {   // exposes add, remove, clear, sort...
    long total() { /* sum of the items */ }
}

Right: an Order has a list of items

class Order {
    private final List<Item> items = new ArrayList<>();
    void add(Item item) { items.add(item); }       // only what Order allows
    long total() { /* sum of the items */ }
}

In a real Spring Boot project

You use inheritance in a few predictable places: custom exceptions (class OrderNotFoundException extends RuntimeException), a JPA @MappedSuperclass base entity that carries id and audit fields, framework base classes such as OncePerRequestFilter, and test base classes. For sharing behaviour between your own services, composition (injecting another bean) is the norm.

Interview: inheritance questions

  • What is inherited? Accessible fields and methods. Not constructors, not private members (although a private field still exists inside the object).
  • Why no multiple inheritance of classes? The diamond problem: ambiguous methods and duplicated state. Interfaces give multiple inheritance of type safely.
  • Types of inheritance? Single, multilevel, hierarchical are supported; multiple and hybrid only through interfaces.
  • super vs this? this is the current object; super reaches the parent part of it.
  • Can a subclass access a parent's private field? Not directly; through public or protected methods.
  • Can you extend a final class? No: String, Integer, and records are final.

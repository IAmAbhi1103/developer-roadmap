Upcasting, downcasting, instanceof and ClassCastException

Upcasting (child to parent) is automatic and always safe; downcasting (parent to child) needs an explicit cast and throws ClassCastException at run time if the object is not really that type, so check with instanceof first.

Every object has a real type, fixed when it was created with new. Every variable has a declared type. In Animal a = new Dog(); the object is a Dog and the variable is an Animal (polymorphism). A cast changes the type you use to look at the object. It never changes the object itself.

Upcasting: always safe, always implicit

Treating a subclass object as its parent type is called upcasting (the arrow on a class diagram points up). It needs no cast, because a Dog is an Animal. You pay one price: through the parent variable you can only use the parent's members.

Animal a = new Dog();       // upcast: implicit
a.eat();                    // fine: Animal has eat()
a.bark();                   // compile error: bark() belongs to Dog, and a is declared Animal

Downcasting: explicit and checked twice

To get back the full Dog view, you downcast: Dog d = (Dog) a;. The compiler and the JVM both check it.

  • At compile time the cast must be possible: the two types must be related (one is a subtype of the other, or the target is an interface and the source class is not final). (Integer) "text" fails with incompatible types: String cannot be converted to Integer.
  • At run time the object must really be an instance of the target type. Otherwise the JVM throws ClassCastException.
class Animal { }
class Dog extends Animal {
    void bark() { System.out.println("Woof"); }
    boolean isTrained() { return true; }
}
class Cat extends Animal { }

public class Cast {
    public static void main(String[] args) {
        Animal a = new Cat();
        try {
            Dog d = (Dog) a;                       // compiles, fails at run time
        } catch (ClassCastException e) {
            System.out.println(e.getMessage());
        }

        Animal b = new Dog();
        if (b instanceof Dog d && d.isTrained()) {   // pattern matching instanceof
            d.bark();
        }
        System.out.println(a instanceof Dog);       // false: a is a Cat
        System.out.println(null instanceof Animal); // false: null is never an instance

        Animal n = null;
        Dog nd = (Dog) n;                           // casting null always works
        System.out.println(nd);

        Object[] objs = new String[2];              // arrays are covariant...
        try {
            objs[0] = Integer.valueOf(1);           // ...so this fails at run time
        } catch (ArrayStoreException e) {
            System.out.println(e);
        }

        Object s = "text";
        if (!(s instanceof String str)) {           // pattern variable in scope after the if
            return;
        }
        System.out.println(str.length());
    }
}

The exception message names both classes. The part in brackets says which module and class loader they came from (it looks different for JDK classes). Remember the three lines about null: instanceof is false for it, a cast of it succeeds, and calling a method on it would throw NullPointerException.

The instanceof operator

x instanceof T asks: "is the real object in x an instance of T?" It is true for the class itself, for any subclass, and for any interface the class implements. It is false for null. If the compiler can prove the answer is always no (unrelated classes), it refuses to compile.

The classic way to use it is the guard then cast pair. Since Java 16 you can combine both steps with pattern matching for instanceof: the test also declares a typed variable.

Classic: test, then cast

if (animal instanceof Dog) {
    Dog d = (Dog) animal;      // repeats the type, easy to get wrong
    d.bark();
}

Modern: test and bind in one step

if (animal instanceof Dog d) {
    d.bark();                  // d is already a Dog here
}

The variable d is a pattern variable. It exists only where the compiler knows the test was true: inside the if, on the right side of && (animal instanceof Dog d && d.isTrained()), or after an if (!(animal instanceof Dog d)) return;. Java 21 adds patterns in switch and record patterns; they are covered in Module 5.

Edge cases

  • Casting to an interface compiles for any non-final class, because a subclass might implement it. (Runnable) animal compiles and then fails at run time if the object does not implement Runnable.
  • Arrays are covariant. String[] is an Object[], so the compiler lets you store any object in it, and the JVM throws ArrayStoreException for the wrong type (shown above). Generic collections do not have this problem (Module 4).
  • Primitive casts are different. (int) 3.9 converts a number and gives 3; it is not an object cast and does not throw.
  • Generics. A cast to List<String> cannot be checked at run time because of type erasure, so you get an "unchecked" warning instead of an exception, and the failure comes later, in a different place.
  • Boxing in casts. Object o = 1; Long l = (Long) o; throws ClassCastException, because the object is an Integer.

Mistake: casting without checking

Wrong: crashes on the first cat

for (Animal a : animals) {
    ((Dog) a).bark();
}

Right: guard, or better, use polymorphism

for (Animal a : animals) {
    if (a instanceof Dog d) {
        d.bark();
    }
}
// Better: add makeSound() to Animal and call a.makeSound()

When casting is acceptable

  • Inside equals(Object), where the parameter type is fixed to Object.
  • In framework glue and when reading loosely typed data (a Map<String, Object> from JSON).
  • Everywhere else, a downcast is a hint that the design could use polymorphism instead. A chain of instanceof checks on a closed set of types is better as a sealed hierarchy with a switch (sealed classes).

Interview: casting questions

  • Upcasting vs downcasting? Upcasting goes to a parent type, implicit and safe. Downcasting goes to a child type, explicit, and can throw ClassCastException.
  • When does ClassCastException happen? When the real object is not an instance of the target type. The compiler cannot see it, because it only knows the declared type.
  • How do you avoid it? Check with instanceof (or a pattern), or redesign with polymorphism.
  • What does instanceof return for null? Always false.
  • Does a cast change the object? No, only how the compiler sees the reference.

Output-prediction puzzles: overloading, overriding and fields

Almost every "what does this print?" puzzle about methods is solved by one two-step rule: the compiler picks the signature from declared types, then the JVM runs the override found in the real object's class; fields, static and private methods skip the second step.

Interviewers love these puzzles because they test whether you understand the difference between compile time and run time. This article gives you the method first, then six puzzles. Try each one on paper before you open the answer.

The two-step rule

  1. Step 1, compile time. Look at the declared type of the variable you call the method on. Among the methods of that type, pick the best-matching signature, using the declared types of the arguments (overload resolution, overloading).
  2. Step 2, run time. If the chosen method is an overridable instance method, run the version that the real class of the object provides (overriding).
  3. Exceptions to step 2. Fields, static methods and private methods are decided in step 1 only. They use the declared type, never the object.

Puzzle 1: a field and a method with the same name in both classes

class A1 { String name = "A"; String who() { return "A.who"; } }
class B1 extends A1 { String name = "B"; @Override String who() { return "B.who"; } }

// in main():
A1 x = new B1();
System.out.println(x.name + " " + x.who());
What is printed? 
A B.who

x.name is a field, so the declared type A1 decides: "A". x.who() is an overridden instance method, so the real object decides: B.who. A B1 object holds two separate fields called name.

Puzzle 2: the same object, different declared types

static void show(Object o) { System.out.println("show(Object)"); }
static void show(String s) { System.out.println("show(String)"); }

// in main():
Object o = "hi";
show(o);
show("hi");
show((Object) "hi");
show(null);
What is printed? 
show(Object)
show(String)
show(Object)
show(String)

Only step 1 applies: these are overloads, not overrides, so the compiler decides from the declared types. The variable o is declared Object, although it holds a String. A cast changes the declared type. null fits both, and String is the more specific.

Puzzle 3: overloading and overriding together

class Animal {
    void eat(Animal a) { System.out.println("Animal eats Animal"); }
}

class Dog extends Animal {
    void eat(Dog d) { System.out.println("Dog eats Dog"); }              // new overload
    @Override void eat(Animal a) { System.out.println("Dog eats Animal"); }
}

// in main():
Animal a = new Dog();
Dog d = new Dog();
a.eat(a);
a.eat(d);
d.eat(a);
d.eat(d);
What is printed? 
Dog eats Animal
Dog eats Animal
Dog eats Animal
Dog eats Dog

Apply the two steps to each call.

  • a.eat(a) — step 1: the declared type Animal has only eat(Animal). Step 2: the real object is a Dog, which overrides it: Dog eats Animal.
  • a.eat(d) — the declared type is still Animal, so eat(Dog) is not even visible. eat(Animal) accepts a Dog. Same result as above.
  • d.eat(a) — the declared type is Dog, which has two methods. The argument is declared Animal, so eat(Dog) does not apply. eat(Animal) runs.
  • d.eat(d) — both methods apply, and eat(Dog) is more specific: Dog eats Dog.

Puzzle 4: a static method called inside an inherited method

class P4 {
    static String id() { return "P"; }
    String run() { return id(); }
}
class C4 extends P4 {
    static String id() { return "C"; }       // hides P4.id()
}

// in main():
System.out.println(new C4().run());
What is printed? 
P

run() is written in P4, where the call id() means P4.id(). Static methods are bound at compile time to the class in which the call is written. The object being a C4 does not matter. If id() were an instance method that C4 overrides, the answer would be C.

Puzzle 5: a private method in the parent

class A5 {
    private void hello() { System.out.println("A.hello"); }
    void call() { hello(); }
}
class B5 extends A5 {
    void hello() { System.out.println("B.hello"); }     // a new method, not an override
}

// in main():
new B5().call();
What is printed? 
A.hello

A private method is not inherited, so B5.hello() cannot override it. Inside A5.call(), the call hello() is bound to A5's own private method. If you remove private from A5.hello() (and keep both classes in one package), B5.hello() becomes an override and the answer changes to B.hello. Adding @Override to the version in B5 would make the original code fail to compile.

Puzzle 6: the parent calls a method the child overrides

class A6 {
    void m() { System.out.println("A.m"); n(); }
    void n() { System.out.println("A.n"); }
}
class B6 extends A6 {
    @Override void n() { System.out.println("B.n"); }
}

// in main():
new B6().m();
What is printed? 
A.m
B.n

m() is inherited and runs from A6, so "A.m" prints. Inside it, n() means this.n(), and this is a B6 object. n() is an overridable instance method, so step 2 picks B6.n(). This is exactly how the Template Method pattern lets a parent class call code that subclasses supply (abstract classes).

Tip: a checklist for any puzzle

  1. Underline every call and write down the declared type of the receiver and of each argument.
  2. Is the member a field, a static method or a private method? Then you are done: use the declared type.
  3. Otherwise pick the signature from the declared types (most specific wins), then switch to the real object and find the override.
  4. If constructors or blocks are involved, number the steps from initialization order.

Interview: how to talk through such a puzzle

Say the rule out loud before you give the answer: "Overloads are resolved at compile time from the declared types; overrides are resolved at run time from the object; fields and statics follow the declared type." Interviewers care about the reasoning more than the output, and the sentence shows you have one.

Abstraction: hide the how, show the what

Abstraction means showing only what a user of a type needs to know, its contract, and hiding how it works inside; in Java you build it with abstract classes, interfaces and well-chosen public methods.

Abstraction is the fourth pillar. Think of an ATM. You press "withdraw" and enter an amount. You do not know how the cash dispenser works, how the bank checks your balance or what happens when the network is down. The ATM shows you the what (a small set of operations) and hides the how. In code, the same idea lets you change a database, a payment provider or an algorithm without touching the code that uses it.

The idea in code

An order service needs to tell the customer that the order is confirmed. It does not care whether that happens by email, SMS or WhatsApp. So we describe the capability as an interface, and the service depends only on that description.

interface NotificationSender {
    void send(String to, String message);        // the "what": a contract
}

class EmailSender implements NotificationSender {
    @Override public void send(String to, String message) {
        System.out.println("EMAIL to " + to + ": " + message);     // the "how", hidden
    }
}

class SmsSender implements NotificationSender {
    @Override public void send(String to, String message) {
        System.out.println("SMS to " + to + ": " + message);
    }
}

class OrderService {
    private final NotificationSender sender;                     // depends on the contract only
    OrderService(NotificationSender sender) { this.sender = sender; }

    void placeOrder(String customer, String contact) {
        System.out.println("Order saved for " + customer);
        sender.send(contact, "Your order is confirmed");
    }
}

public class Abstraction {
    public static void main(String[] args) {
        new OrderService(new EmailSender()).placeOrder("Asha", "asha@example.com");
        new OrderService(new SmsSender()).placeOrder("Ravi", "98100 00001");
    }
}
Order saved for Asha
EMAIL to asha@example.com: Your order is confirmed
Order saved for Ravi
SMS to 98100 00001: Your order is confirmed

OrderService never mentions email or SMS. Adding WhatsApp means writing one new class. A test can pass a fake sender that records messages instead of sending them. This is exactly what Spring does when it injects an implementation into your service.

Levels of abstraction

Abstraction is not one feature; it appears at several levels, from small to large:

  • A method. Collections.sort(list) hides the sorting algorithm. You say what you want.
  • A class. ArrayList hides the array that grows. You use add and get, and the private fields and helper methods stay hidden (encapsulation is the tool).
  • A type. An interface or an abstract class describes a contract with no (or partial) implementation. Callers hold the abstract type.
  • A layer. A UserRepository interface hides whether the data is in PostgreSQL, in memory or in a cache.

Abstraction versus encapsulation

Interviewers ask this pair all the time, and the two ideas do work together, so the difference is easy to blur. A clear way to remember it: encapsulation is about protecting data, and abstraction is about simplifying the view.

One sentence for an interview: "Encapsulation hides how the data is stored and changed; abstraction hides how the work is done."

Program to an interface

  • Declare variables, fields and parameters with the most general type that offers what you need: List<String> names = new ArrayList<>();, not ArrayList<String> names.
  • Name methods by what they do, not how: sendReminder(), not sendReminderUsingSmtp().
  • Keep the contract small. Every method you put in an interface is a promise to every implementation.

Abstractions can leak, and can be overdone

  • A leaky abstraction exposes a detail it was meant to hide. If a method returns ArrayList instead of List, every caller now depends on that class. If a repository interface has a method findByPostgresJsonbField(), it is not abstract any more.
  • Abstraction has a cost: more types and more indirection. Creating an interface with exactly one implementation "just in case" often adds noise. A common approach is to start with a class and extract an interface when a second implementation or a test double really appears. In Spring projects, service interfaces are common by habit; judge by the value they bring.

In a real Spring Boot project

You write interface OrderRepository extends JpaRepository<Order, Long> and never write a class that implements it; Spring Data generates the implementation at start-up. Your OrderService depends on the interface. In tests you replace a payment or email bean with a fake, because the service only knows the contract.

Interview: "What is abstraction? How is it different from encapsulation?"

  • Abstraction = exposing what an object does (its contract) and hiding how. In Java: interfaces and abstract classes, plus small public APIs.
  • Real-life examples: ATM, car steering wheel, List interface.
  • Encapsulation hides data and protects invariants with private fields; abstraction hides complexity behind a contract. They are partners, not synonyms.
  • Add the benefit: implementations can change without changing callers, and tests can use fakes.

Abstract classes and abstract methods

An abstract class is a partly finished class that cannot be instantiated: it shares fields, constructors and ready-made methods with its subclasses and leaves the varying parts as abstract methods that each concrete subclass must implement.

Sometimes a group of classes shares a lot of code, but one step differs for each. You do not want to create an object of the shared "idea" itself: a plain Shape has no area. You want to say "every shape has a name and can describe itself, but each shape computes its own area". An abstract class does exactly that.

Syntax and a first example

Mark the class with abstract. Mark each method that has no body with abstract and end it with a semicolon.

abstract class Shape {
    private final String name;

    Shape(String name) {                   // abstract classes can have constructors
        this.name = name;
    }

    abstract double area();                // abstract method: no body, subclasses must supply it

    String describe() {                    // concrete method: shared code
        return name + " with area " + String.format("%.2f", area());
    }
}

class Circle extends Shape {
    private final double radius;
    Circle(double radius) { super("Circle"); this.radius = radius; }
    @Override double area() { return Math.PI * radius * radius; }
}

class Rectangle extends Shape {
    private final double w, h;
    Rectangle(double w, double h) { super("Rectangle"); this.w = w; this.h = h; }
    @Override double area() { return w * h; }
}

public class ShapeDemo {
    public static void main(String[] args) {
        Shape[] shapes = { new Circle(2), new Rectangle(3, 4) };
        for (Shape s : shapes) {
            System.out.println(s.describe());          // area() is resolved at run time
        }
        Shape custom = new Shape("Unit square") {      // anonymous subclass
            @Override double area() { return 1; }
        };
        System.out.println(custom.describe());
    }
}
Circle with area 12.57
Rectangle with area 12.00
Unit square with area 1.00

The method describe() is written once in Shape and calls area(). For each object, Java runs that object's own area() (dynamic dispatch). You can declare a variable or an array of type Shape; you just cannot create a plain Shape with new. The last example creates an object of an anonymous subclass (nested classes), which supplies the missing method on the spot.

The rules

Rules for abstract classes and methods

  • An abstract class cannot be instantiated: new Shape() gives Shape is abstract; cannot be instantiated.
  • A class that has an abstract method must itself be declared abstract. The reverse is not required: an abstract class may have no abstract methods at all.
  • An abstract method has no body. A body gives abstract methods cannot have a body, and a missing body on a normal method gives missing a method body, or should be declared abstract.
  • The first concrete subclass must implement every inherited abstract method, or it must be abstract too. Otherwise: Circle is not abstract and does not override abstract method area() in Shape.
  • An abstract class can have fields, constructors, static members, initializer blocks and concrete methods of any access level.
  • Illegal combinations: abstract with final (a final class cannot be extended, so it could never be completed), with private (a subclass could not see it) or with static (static methods are not overridden). javac says illegal combination of modifiers: abstract and final and so on.

Abstract classes can have constructors, even though you cannot call them with new. A subclass constructor calls one through super(…), and the abstract class uses it to set up the shared state, as Shape does with name.

The Template Method pattern

The most useful job of an abstract class is the Template Method pattern. The parent fixes the order of the steps in a final method. Some steps are ready-made hooks with defaults, and others are abstract. Subclasses fill in only the varying steps and cannot change the overall flow.

import java.util.*;

abstract class ReportExporter {
    public final String export(List<String> rows) {        // the template: fixed steps
        StringBuilder sb = new StringBuilder(header());
        for (String row : rows) {
            sb.append(formatRow(row));
        }
        return sb.append(footer()).toString();
    }

    protected String header() { return ""; }                // hook with a default
    protected String footer() { return ""; }                // hook with a default
    protected abstract String formatRow(String row);        // must be supplied
}

class CsvExporter extends ReportExporter {
    @Override protected String formatRow(String row) { return row + "\n"; }
}

class BulletExporter extends ReportExporter {
    @Override protected String header() { return "Items:\n"; }
    @Override protected String formatRow(String row) { return " - " + row + "\n"; }
    @Override protected String footer() { return "(end)\n"; }
}

public class Exporter {
    public static void main(String[] args) {
        List<String> rows = List.of("Mouse", "Keyboard");
        System.out.print(new CsvExporter().export(rows));
        System.out.print(new BulletExporter().export(rows));
    }
}

This pattern is everywhere. HttpServlet decides when to call doGet and doPost; you only fill them in. Spring's JdbcTemplate and test frameworks do the same with callbacks. Making the template method final protects the flow from being broken by a subclass.

Abstract classes in the JDK

  • java.lang.Number is abstract: Integer, Long and Double extend it and supply intValue(), doubleValue() and so on.
  • java.io.InputStream is abstract with one abstract method, read(); every other read method is built on it.
  • AbstractList, AbstractMap and AbstractCollection are skeletons that make writing your own collection easy (see abstract class vs interface).

Edge cases

  • The constructor still runs. Creating a concrete subclass runs the abstract parent's constructor first. If that constructor calls an abstract method, the subclass's version runs before the subclass's fields are set. This is the trap from initialization order.
  • An abstract class may implement an interface and leave some or all interface methods unimplemented. Concrete subclasses must finish the job.
  • An abstract class can have main and static factory methods that return concrete subclasses.
  • Abstract with no abstract methods is a valid way to say "this class is only a base, do not instantiate it".
  • Anonymous subclasses are allowed: new Shape("x") { … } must implement all abstract methods.

Mistakes to avoid

  • Using an abstract class as a pure contract. If it has no state and no shared code, it only uses up the subclass's single inheritance slot. An interface is better (which to use).
  • Forgetting to implement an abstract method in a concrete subclass (compile error), or forgetting to declare a class abstract when it keeps an unimplemented method.
  • Calling an abstract method from the constructor and reading subclass fields in it.
  • Making every method abstract "to be flexible". Share what really is shared.

Interview: abstract class questions

  • Can an abstract class have a constructor? Yes. It runs when a subclass object is built, through super(…).
  • Can it have no abstract methods? Yes, to prevent instantiation.
  • Can an abstract class be final? No: abstract needs subclasses, final forbids them.
  • Can we create an object of an abstract class? Not directly. You can use a reference of that type, or an anonymous subclass.
  • What is the Template Method pattern? A final method in the base class defines the algorithm's steps; subclasses override only the abstract or hook steps.

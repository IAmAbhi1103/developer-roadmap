Classic java.io: streams, readers and writers

The old java.io package moves data as streams: byte streams (InputStream/OutputStream) for any data, character streams (Reader/Writer) for text, and small wrapper classes that you stack on top of each other to add buffering and conversion.

Why you still need to know it

New code should prefer java.nio.file.Files (see reading and writing with Files). But java.io is everywhere: servlet request bodies, socket streams, System.in, ZipInputStream, JDBC Blob and Clob, multipart uploads in Spring (MultipartFile.getInputStream()) and a huge amount of older code. Interviews also like the "byte stream vs character stream" and "decorator" questions. Even the NIO helper Files.newBufferedReader hands you a java.io.BufferedReader.

A stream is a sequence of data that you read or write one piece after another, without jumping around. You do not hold the whole content in memory; you process it piece by piece. That is why streams work for a 5 GB log file as well as for a 5-byte one.

Byte streams vs character streams

A byte stream moves raw bytes (values 0 to 255). Use it for anything that is not text: images, PDFs, ZIP files, encrypted data, network packets. The base classes are the abstract InputStream and OutputStream.

A character stream moves characters. It converts between bytes and characters using a charset (a character encoding such as UTF-8). Use it for text files, CSV, JSON and logs. The base classes are the abstract Reader and Writer.

The bridge classes connect the two worlds: InputStreamReader wraps an InputStream and decodes bytes into characters with a charset you give; OutputStreamWriter does the reverse. This is how you read text from a socket or from System.in.

Copying a file with byte streams

Reading one byte at a time is slow because every call may go to the operating system. Read into a byte array (a buffer) instead. read(byte[]) returns how many bytes it actually filled, or -1 at the end of the stream; always use that count when you write.

import java.io.*;

public class CopyBytes {
    public static void main(String[] args) throws IOException {
        try (InputStream in = new FileInputStream("photo.jpg");
             OutputStream out = new FileOutputStream("photo-copy.jpg")) {

            byte[] buffer = new byte[8192];     // 8 KB at a time
            int count;
            long total = 0;
            while ((count = in.read(buffer)) != -1) {
                out.write(buffer, 0, count);    // write only 'count' bytes
                total += count;
            }
            System.out.println("Copied " + total + " bytes");
        }   // both streams closed here, out first, then in
    }
}
Copied 248113 bytes

Since Java 9 you can also write in.transferTo(out), which does the loop for you. And Files.copy(Path, Path) is simpler still. The loop above is what they do inside.

Reading and writing text

FileReader and FileWriter read and write characters. Wrap them in BufferedReader and BufferedWriter: the buffer cuts the number of disk calls, and BufferedReader adds readLine(), which returns one line without the line break, or null at the end.

import java.io.*;
import java.nio.charset.StandardCharsets;

public class TextIo {
    public static void main(String[] args) throws IOException {
        // Write three lines (UTF-8 chosen explicitly)
        try (BufferedWriter w = new BufferedWriter(
                new OutputStreamWriter(new FileOutputStream("orders.txt"),
                                       StandardCharsets.UTF_8))) {
            w.write("1001,Asha,499.50");
            w.newLine();                    // correct line separator for this OS
            w.write("1002,Ravi,1200.00");
            w.newLine();
            w.write("1003,Meera,89.99");
        }

        // Read them back
        try (BufferedReader r = new BufferedReader(
                new InputStreamReader(new FileInputStream("orders.txt"),
                                      StandardCharsets.UTF_8))) {
            String line;
            int n = 0;
            while ((line = r.readLine()) != null) {
                n++;
                System.out.println(n + ": " + line);
            }
        }
    }
}
1: 1001,Asha,499.50
2: 1002,Ravi,1200.00
3: 1003,Meera,89.99

In newer code you can shorten the setup: new FileReader("orders.txt", StandardCharsets.UTF_8) (constructor with charset since Java 11) or Files.newBufferedReader(path), which defaults to UTF-8.

Default charset changed in Java 18

Before Java 18, new FileReader("x.txt") used the operating system's default charset (often Windows-1252 on Windows, UTF-8 on Linux), so the same program could read the same file differently on two machines. Since Java 18 the default is UTF-8 almost everywhere (JEP 400). Even so, name the charset in your code. It costs one argument and removes a whole class of bugs.

The decorator idea

Notice how the example builds objects by wrapping: new BufferedReader(new InputStreamReader(new FileInputStream(...))). This is the decorator pattern: each class implements the same interface (Reader) and holds another object of that interface. It forwards the calls and adds behaviour. You choose the features you need and stack them, instead of having one giant class like BufferedCompressedEncryptedFileReader. More about the pattern in System Design · Module 2.

The decorators you will meet most: BufferedInputStream/OutputStream (buffering), DataInputStream/DataOutputStream (read and write primitives like int and double in binary form), ObjectOutputStream (see serialization), GZIPOutputStream (compression), PrintWriter and PrintStream (println, printf; System.out is a PrintStream).

When you close the outermost wrapper, close() passes down and closes the inner ones too. With try-with-resources, declaring only the outermost object is enough, but declaring each one is the safer habit (if a middle constructor throws, the earlier resource is still closed).

File vs Path

java.io.File is the old way to represent a file or directory path. java.nio.file.Path (Java 7) is the modern one. A File is just a path name in an object, even if nothing exists on disk.

System.in and Scanner

System.in is an InputStream for the keyboard. Scanner parses tokens from it (nextInt(), nextLine()); it is fine for small programs and coding-practice sites. For fast input in DSA problems people use new BufferedReader(new InputStreamReader(System.in)) because it is much faster than Scanner.

Rules

  • Always close streams: use try-with-resources. A leaked stream keeps a file handle open (on Windows it can lock the file).
  • Use byte streams for binary data and character streams for text. Never read a PDF or an image through a Reader; the decoding corrupts it.
  • When reading into a buffer, use the count returned by read. The buffer is often only partly filled.
  • Do not mix Scanner and BufferedReader on the same System.in; each buffers input and will "steal" data from the other.

Conventions

  • Wrap with a buffer whenever you read or write many small pieces.
  • Name the charset explicitly (StandardCharsets.UTF_8).
  • Prefer Files methods for whole-file or line-by-line work; use streams directly when the data comes from a network, a request body, a ZIP or a database.
  • Use transferTo or Files.copy instead of writing your own copy loop.

Exceptions and edge cases

  • FileNotFoundException — the FileInputStream / FileReader constructor cannot open the file: it does not exist, is a directory or you have no permission. FileOutputStream creates the file if it does not exist, but fails when the folder is missing.
  • new FileOutputStream("a.txt") and new FileWriter("a.txt") truncate the file. Pass true as the second argument to append.
  • IOException from close() in try-with-resources is added to the suppressed list if the body already threw.
  • BufferedWriter keeps data in memory. If the program ends without close() or flush(), the last part is lost.
  • read() on a closed stream throws IOException ("Stream closed").

Mistake: reading text with a stream and a cast

Wrong: breaks non-ASCII text

int b;
while ((b = in.read()) != -1) {
    sb.append((char) b);   // each byte treated as a char
}

Right: decode with a charset

try (var r = new BufferedReader(
        new InputStreamReader(in, StandardCharsets.UTF_8))) {
    r.lines().forEach(sb::append);
}

In UTF-8, a character like "₹" takes three bytes. Casting each byte to a char gives three wrong characters.

Interview: "Byte stream vs character stream", "Why BufferedReader?", "File vs Path"

  • Byte streams move raw bytes; character streams decode bytes to chars with a charset.
  • Buffering reduces expensive system calls and adds readLine().
  • Decorator pattern: wrappers share an interface and add behaviour; closing the outer one closes the inner.
  • Path/Files is the modern API with better errors and attributes.

Serialization: Serializable, transient and serialVersionUID

Java serialization turns an object graph into a byte stream and back using ObjectOutputStream and ObjectInputStream; it is fragile and has serious security risks, so use JSON for new work and treat serialization as legacy knowledge you must still understand.

What it is

Serialization converts an object (and everything it references) into a sequence of bytes that you can store in a file, send over a network or keep in a cache. Deserialization does the reverse and rebuilds an equivalent object. Java has built-in support: a class opts in by implementing the marker interface java.io.Serializable. A marker interface has no methods; it just tells the JVM "this class may be serialized".

import java.io.Serializable;

public class Customer implements Serializable {
    private static final long serialVersionUID = 1L;

    private final String name;
    private final String email;
    private transient String sessionToken;   // not saved
    private static int totalCustomers;       // belongs to the class, not saved

    public Customer(String name, String email, String sessionToken) {
        this.name = name;
        this.email = email;
        this.sessionToken = sessionToken;
        totalCustomers++;
    }

    @Override public String toString() {
        return "Customer[" + name + ", " + email + ", token=" + sessionToken + "]";
    }
}
import java.io.*;

public class SerializeDemo {
    public static void main(String[] args) throws Exception {
        Customer c = new Customer("Asha", "asha@mail.in", "abc123");

        try (ObjectOutputStream out = new ObjectOutputStream(
                new FileOutputStream("customer.bin"))) {
            out.writeObject(c);                       // serialize
        }

        try (ObjectInputStream in = new ObjectInputStream(
                new FileInputStream("customer.bin"))) {
            Customer copy = (Customer) in.readObject();   // deserialize
            System.out.println(copy);
            System.out.println(copy == c);                // a new object
        }
    }
}
Customer[Asha, asha@mail.in, token=null]
false

The token came back as null, because it is transient. The copy is a different object with the same data. Note that deserialization creates the object without calling the constructor of the serializable class.

Rules that decide what is saved

  • Every field must be serializable (a primitive, a String, or an object whose class is Serializable), or be marked transient. Otherwise writeObject throws NotSerializableException. Collections like ArrayList and HashMap are serializable, but only if their contents are.
  • transient fields are skipped. After deserialization they hold the default value (null, 0, false). Use it for passwords, tokens, caches, threads and anything derived or sensitive.
  • static fields are not part of an object's state and are not serialized.
  • The whole object graph is saved: if Order refers to Customer, both are written. Shared references stay shared, and cycles are handled.
  • If a parent class is not serializable, its fields are not saved, and on deserialization the parent's no-argument constructor runs to initialise them. If the parent has none, you get an InvalidClassException.
  • Subclasses of a serializable class are serializable automatically.

serialVersionUID

Every serializable class has a version number, serialVersionUID, a long. It is written into the byte stream. When you deserialize, Java compares the number in the stream with the number of the class currently loaded. If they differ, it throws InvalidClassException ("local class incompatible"). This protects you from loading old data into a class whose shape has changed.

If you do not declare the field, the compiler computes one from the class details (name, fields, methods). Then any small change, even adding a method, gives a new number and breaks old data. So you declare it yourself:

private static final long serialVersionUID = 1L;

Rules of thumb: keep the same number when your change is compatible (adding a field is compatible: the old data gives the new field its default value); change the number when the change is incompatible (removing a field, changing a field's type, changing the class hierarchy) and you want old data to be rejected. IDEs can generate the field for you.

Customising: readObject, writeObject, Externalizable

A class can define private methods writeObject(ObjectOutputStream) and readObject(ObjectInputStream) to add steps, for example to encrypt a field or to rebuild a transient cache after loading. Call defaultWriteObject() / defaultReadObject() inside to handle the normal fields. Externalizable goes further: you write all the state yourself and need a public no-argument constructor. In practice you will almost never write these.

private void readObject(ObjectInputStream in)
        throws IOException, ClassNotFoundException {
    in.defaultReadObject();        // restore normal fields
    this.sessionToken = null;      // or recompute a cache here
    if (email == null) {           // validate: the stream may be hostile
        throw new InvalidObjectException("email is required");
    }
}

Records and enums

Enums serialize by name, so the constants stay singletons. A record can implement Serializable; on deserialization Java calls the record's canonical constructor, so the validation in your constructor runs again. That makes records a safer choice than ordinary classes if you must serialize.

Spring Boot uses Jackson for REST bodies; it turns objects into JSON with ObjectMapper.writeValueAsString(obj) and back with readValue(json, Customer.class). For a bank-style "save to a file" task you would also use JSON or CSV. Java serialization still shows up in legacy code, in HttpSession replication between servers, and in some caches (Redis with JdkSerializationRedisSerializer, which is why many teams switch Redis to a JSON serializer).

The security risk

Deserialization runs code chosen by whoever produced the bytes. When your program calls readObject() on data from an untrusted source, an attacker can craft a stream that makes Java build objects from classes already on your classpath (a "gadget chain"), so that a harmless-looking readObject or hashCode call ends up running a system command. This has caused many real remote-code-execution vulnerabilities in widely used Java libraries and servers. The danger exists even if the class you cast to is safe, because the objects are created before the cast.

Rule: never deserialize untrusted data with ObjectInputStream

If you must read Java-serialized data, restrict it with a serialization filter (ObjectInputFilter, Java 9+; for example set with ObjectInputStream.setObjectInputFilter or the JVM-wide jdk.serialFilter property) that allows only the classes you expect. Better: do not accept Java serialization at all.

Exceptions and edge cases

  • NotSerializableException — a field (or an element inside a collection) is not Serializable. The message names the class.
  • InvalidClassException — serialVersionUID mismatch, or a non-serializable parent without a no-arg constructor.
  • ClassNotFoundException — the class is not on the classpath of the reader; it is a checked exception of readObject.
  • StreamCorruptedException — the file is not a serialization stream, or is damaged.
  • Singletons break: deserializing creates a second instance unless you add readResolve() (or use an enum).
  • Writing the same object twice to one stream writes a back-reference the second time, so changes made between two writeObject calls are not saved (use reset()).

Mistake: forgetting that the parent class matters

You make Manager implements Serializable but its parent Employee does not. The Employee fields (name, salary) silently come back as defaults, because they were never written. Make the parent serializable too.

Interview: "What is serialVersionUID?", "What does transient do?", "Why is serialization risky?"

  • Serializable is a marker interface; the object graph is written; the constructor is not called.
  • transient and static fields are skipped.
  • serialVersionUID is a version check; mismatch gives InvalidClassException; declare it yourself.
  • Risks: gadget chains and remote code execution on untrusted input; use filters or, better, JSON.

Properties files and the Properties class

A .properties file stores simple key=value settings; java.util.Properties loads it into a map-like object so your program can read configuration without hard-coding it.

What and why

Settings such as the database URL, a timeout or a feature flag should not live inside your code. A properties file is the simplest configuration format in Java: one key=value pair per line. You change the file, not the code, and no recompile is needed. Spring Boot's application.properties is exactly this format (see Spring Boot · Module 1), and resource bundles for translations (messages_hi.properties) use it too.

# Database settings
db.url=jdbc:postgresql://localhost:5432/shop
db.user=shop_app
# Values may contain spaces; leading spaces are removed
app.name = Order Service
app.retries=3
# Line continuation with a backslash
app.welcome=Welcome to \
            the shop
feature.newCheckout=true

File format rules

  • Lines starting with # or ! are comments.
  • The key ends at the first =, : or whitespace. Spaces around the separator are ignored.
  • A trailing \ continues the value on the next line.
  • Everything is a string. app.retries=3 gives you the text "3"; you convert it with Integer.parseInt.
  • Special characters (\n, \t, \\) use backslash escapes; non-ASCII characters can be written as ₹. If you read the file with a UTF-8 Reader, you can type them directly.
  • Quotes are not special: name="Asha" stores the quote characters.

The Properties class

Properties extends Hashtable<Object,Object> (an old design choice), but you should only use its String methods.

MethodPurpose
load(Reader) / load(InputStream)Read the pairs from a file or stream. Prefer Reader with UTF-8
getProperty(key)Value, or null if the key is missing
getProperty(key, default)Value, or the default if the key is missing
setProperty(key, value)Add or change a pair in memory
stringPropertyNames()All keys as a Set<String>
store(Writer, comments)Write the pairs to a file, with a header comment
 
import java.io.*;
import java.nio.charset.StandardCharsets;
import java.nio.file.*;
import java.util.Properties;

public class ConfigDemo {
    public static void main(String[] args) throws IOException {
        Properties props = new Properties();

        try (Reader reader = Files.newBufferedReader(
                Path.of("app.properties"), StandardCharsets.UTF_8)) {
            props.load(reader);
        }

        String url = props.getProperty("db.url");
        int retries = Integer.parseInt(props.getProperty("app.retries", "1"));
        boolean newCheckout =
                Boolean.parseBoolean(props.getProperty("feature.newCheckout"));
        String timeout = props.getProperty("db.timeout", "30");   // missing: default

        System.out.println("url        = " + url);
        System.out.println("retries    = " + retries);
        System.out.println("checkout   = " + newCheckout);
        System.out.println("timeout    = " + timeout);
        System.out.println("welcome    = " + props.getProperty("app.welcome"));

        // Change and save
        props.setProperty("app.retries", "5");
        try (Writer writer = Files.newBufferedWriter(
                Path.of("app-new.properties"), StandardCharsets.UTF_8)) {
            props.store(writer, "Updated settings");
        }
    }
}
url        = jdbc:postgresql://localhost:5432/shop
retries    = 3
checkout   = true
timeout    = 30
welcome    = Welcome to the shop

The saved file starts with the comment line, then a timestamp comment, then the pairs. The order of the pairs is not guaranteed because the class is hash-based.

Reading from the classpath

A file in src/main/resources is packaged inside the JAR, so you cannot open it with a file path in production. Load it from the classpath instead:

try (InputStream in = ConfigDemo.class.getResourceAsStream("/app.properties")) {
    if (in == null) {
        throw new IllegalStateException("app.properties not found on classpath");
    }
    props.load(new InputStreamReader(in, StandardCharsets.UTF_8));
}

The leading / means "from the root of the classpath". getResourceAsStream returns null (not an exception) when the resource is missing, so check it.

Layering: defaults, files and environment

Real applications combine several sources: defaults in code, a file in the JAR, an override file on the server, and environment variables or system properties (-Dapp.retries=5, read with System.getProperty; environment variables with System.getenv). new Properties(defaults) accepts another Properties object as fallback. Spring Boot does this layering for you with a clear order of precedence, and @Value or @ConfigurationProperties bind the values to typed fields.

Rules

  • Never commit secrets (passwords, API keys) in a properties file in Git. Read them from environment variables or a secrets manager.
  • Convert strings to the right type yourself, and fail with a clear message when a required key is missing.
  • Use getProperty, not get: get comes from Hashtable and returns an Object, and it does not use the defaults.

Exceptions and edge cases

  • NumberFormatException — the value is not a number (app.retries=three).
  • NullPointerException — you call Integer.parseInt(props.getProperty("missing")); use a default or check for null.
  • IllegalArgumentException — load finds a malformed \uXXXX escape.
  • load(InputStream) assumes ISO-8859-1. That garbles UTF-8 text; use the Reader version.
  • A key written twice: the last value wins, with no warning.
  • Trailing spaces at the end of a value are kept, a classic cause of "true " not parsing as expected with some libraries.

Real projects

You will rarely call Properties.load yourself in a Spring Boot app. You write application.properties (or YAML) and let the framework read it. You will meet Properties directly in plain-Java tools, JDBC driver settings (DriverManager.getConnection(url, props)), Kafka client configuration and test utilities.

Interview: "How do you externalise configuration in Java?"

  • Key=value file loaded with Properties.load; all values are strings.
  • Classpath resources via getResourceAsStream; overrides through system properties and environment variables.
  • In Spring Boot: application.properties/YAML, profiles, @Value and @ConfigurationProperties.
  • Keep secrets out of Git.

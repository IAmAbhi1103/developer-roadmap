Method overriding: the rules

A subclass overrides an inherited instance method by declaring one with the same signature; the access may not be narrower, the return type may be a subtype, checked exceptions may not be broader, and @Override makes the compiler check all of it.

Overriding means a subclass provides its own version of an instance method that it inherited. When you call the method on a subclass object, Java runs the subclass version, even if the variable's type is the parent. That is the engine behind polymorphism. You already used it when Manager replaced monthlyPay() in inheritance.

class Account {
    public long monthlyChargePaise() { return 0; }
}

class CurrentAccount extends Account {
    @Override
    public long monthlyChargePaise() { return 15_000; }   // replaces the parent's version
}

// in main():
Account a = new CurrentAccount();
System.out.println(a.monthlyChargePaise());               // 15000

The rules

Overriding is strict. If one rule is broken, the code either fails to compile or quietly does something else. The first column is the rule; the last shows what the compiler tells you when you break it.

RuleDetailIf you break it
Same name and parameter typesThat pair is the signature. A different parameter list makes a new overload, not an overrideWith @Override: method does not override or implement a method from a supertype
Return typeThe same, or a subtype of it for objects (covariant). Primitives and void must match exactlyreturn type long is not compatible with int
AccessThe same or wider: protected may become public, never the other wayattempting to assign weaker access privileges; was public
Checked exceptionsNone, the same, or narrower ones. Unchecked exceptions are always allowedoverridden method does not throw IOException
Not finalA final method cannot be overriddenoverridden method is final
Instance methods onlyStatic methods are hidden, not overridden. Static and instance cannot swap rolesoverridden method is static or overriding method is static
Must be inheritedprivate methods are not inherited. Package-private methods are inherited only inside the same packageNo error: you silently created a new, unrelated method

Rule: remember it as "same, wider, narrower, covariant"

The same signature; wider or equal access; narrower or equal checked exceptions; covariant (same or more specific) return type. The reason is substitutability: code that calls the parent method must still work with any subclass, so a subclass may not promise less (narrower access) or throw more.

Always write @Override

@Override is an annotation that tells the compiler: "I intend to override a method from a parent class or interface. Check it." It has no effect at run time. Its value is that it turns a silent mistake into a compile error. The most famous such mistake is equals:

Wrong: this is an overload, not an override

class Account {
    long id;
    Account(long id) { this.id = id; }

    public boolean equals(Account other) {    // parameter is Account, not Object
        return other != null && id == other.id;
    }
}

Right: @Override catches it for you

class Account {
    long id;
    Account(long id) { this.id = id; }

    @Override
    public boolean equals(Object other) {
        return other instanceof Account a && id == a.id;
    }
    @Override public int hashCode() { return Long.hashCode(id); }
}

With the wrong version, equals seems to work when you call it with an Account variable, and fails everywhere else:

Account a = new Account(1), b = new Account(1);
System.out.println(a.equals(b));              // true: calls equals(Account)
Object o = b;
System.out.println(a.equals(o));              // false: calls Object.equals, a different method
List<Account> list = List.of(a);
System.out.println(list.contains(b));         // false: collections call equals(Object)

Put @Override on every overriding method, including implementations of interface methods. With the annotation, the wrong version above does not compile. It also protects you later: if someone renames the parent method, every override fails to compile instead of silently becoming a dead method.

Covariant return types

An override may return a more specific type than the parent method. Callers who know they hold the subclass get the specific type without a cast.

class Animal {
    Animal reproduce() { return new Animal(); }
}

class Dog extends Animal {
    @Override
    Dog reproduce() { return new Dog(); }      // Dog is a subtype of Animal: allowed
}

// in main():
Dog puppy = new Dog().reproduce();              // no cast needed
Animal other = new Dog().reproduce();           // still fine through the parent type

Behind the scenes, javac adds a hidden bridge method with the parent's return type, so that the JVM can still dispatch the call correctly. You never write it. This is why clone() overrides can declare their own class as the return type.

Exceptions in overriding methods

import java.io.*;

class Importer {
    void load(String file) throws IOException { }
}

class CsvImporter extends Importer {
    @Override void load(String file) throws FileNotFoundException { }   // narrower: OK
}

class CachedImporter extends Importer {
    @Override void load(String file) { }                                // none: OK
}

class BadImporter extends Importer {
    @Override void load(String file) throws Exception { }   // error: broader than IOException
}

The reason is again substitutability. A caller holding an Importer catches only IOException. If a subclass could throw Exception, that caller would be surprised by a checked exception it never prepared for. Unchecked exceptions (RuntimeException and its children) are not checked by the compiler, so they are always allowed.

Calling the parent version with super

An override often wants to extend the parent behaviour, not discard it. Call super.method() and add to the result. Two common places: toString() (super.toString() + ", extra=" + extra) and methods that do setup and teardown work in a base class.

Static methods and fields: hidden, not overridden

If a subclass declares a static method with the same signature as a static method of its parent, it hides the parent's method. A field with the same name as a parent field hides that field. In both cases, Java picks by the declared type of the reference, not by the object. Only instance methods are chosen by the object.

public class Hiding {
    static class P {
        static String who() { return "P"; }
        String name() { return "P"; }
        String f = "P.f";
    }

    static class C extends P {
        static String who() { return "C"; }                  // hides P.who()
        @Override String name() { return "C"; }              // overrides P.name()
        String f = "C.f";                                    // hides P.f
    }

    public static void main(String[] args) {
        P p = new C();                    // declared type P, real object C
        System.out.println(p.who());      // static: decided by declared type
        System.out.println(p.name());     // instance method: decided by the object
        System.out.println(p.f);          // field: decided by declared type
        System.out.println(((C) p).f);    // after a cast the declared type is C
        System.out.println(C.who());
    }
}

Only p.name() printed the subclass value. That single line is polymorphism; the others are not. Do not redeclare a parent's field name in a subclass. If subclasses need different values, expose a method (for example protected String label()) because methods are chosen by the object.

The silent trap: private and package-private methods

A method that is not inherited cannot be overridden. A private method in the parent is invisible to the child, so a method with the same name in the child is a brand-new method. Package-private methods behave the same way when the child is in another package:

package pkg1;

public class Base {
    void hook() { System.out.println("Base hook"); }      // package-private
    public void run() { hook(); }
}
package pkg2;

public class Derived extends pkg1.Base {
    // NOT an override: Base.hook() is invisible in this package
    void hook() { System.out.println("Derived hook"); }
}

// new Derived().run() prints:  Base hook

Nothing warns you about this, except @Override: with the annotation on Derived.hook() the compiler reports method does not override or implement a method from a supertype. Yet another reason to always write it.

Edge cases

  • An override may be final (to stop further overriding). Modifiers such as synchronized are not part of the signature, so they may differ.
  • An abstract class can re-declare an inherited concrete method as abstract, forcing subclasses to implement it again.
  • An abstract method must be overridden by the first concrete subclass, or javac reports … is not abstract and does not override abstract method … (abstract classes).
  • The overriding method may rename parameters and add or drop annotations freely; only the types matter.
  • A call through super.method() is not dynamic: it always runs the parent version.
  • Interface default methods can be overridden too, by a class or by a sub-interface (interfaces).

Mistakes to avoid

  • Leaving out @Override and shipping an overload (the equals(Account) bug above).
  • Breaking the parent's promise. If withdraw() in the parent never throws for a valid amount, a subclass that throws for valid amounts violates substitutability even though it compiles.
  • Calling overridable methods from a constructor (initialization order).
  • Assuming a field behaves like a method. Fields are never overridden.

Tip: design for overriding on purpose

A class that allows overriding must document how (which other methods call this one, what must hold afterwards). If you did not plan for subclasses, mark the class or the key methods final. "Design and document for inheritance, or else prohibit it" is the advice of Effective Java.

Interview: overriding questions

  • What are the rules? Same signature, same or wider access, same or narrower checked exceptions, same or covariant return type, instance methods only, not final.
  • Can we override static or private methods? No. Static methods are hidden; private ones are not inherited.
  • What is a covariant return type? An override that returns a subtype of the parent's return type (since Java 5).
  • Why use @Override? The compiler checks that you really override; it catches typos and wrong parameter types.
  • Can an overriding method throw a broader exception? No for checked exceptions; unchecked exceptions are fine.

Method overloading and how Java picks the method

Overloading means several methods with the same name but different parameter lists; the compiler chooses one at compile time from the declared types of the arguments, trying exact and widening matches first, then boxing, then varargs.

Method overloading lets you reuse one name for related operations on different inputs. The JDK does this constantly: System.out.println has overloads for int, double, char, String, Object and more; Math.max works for int, long, float and double; String.valueOf and StringBuilder.append have a dozen overloads each. The caller writes the same name, and the compiler picks the right version.

public class Calculator {
    public int add(int a, int b)                { return a + b; }
    public double add(double a, double b)       { return a + b; }
    public int add(int a, int b, int c)         { return a + b + c; }
    public String add(String a, String b)       { return a + b; }
}

What counts as a different method

The signature of a method is its name plus the types of its parameters, in order. Two methods in the same class (or in a class and its subclass) may share a name only if their signatures differ.

Rules of overloading

  • The parameter lists must differ in the number, the types or the order of types: f(int, String) and f(String, int) are different methods.
  • These do not make methods different: the return type, the access modifier, the throws clause and the parameter names.
  • Two methods with the same signature and different return types do not compile: method f(int) is already defined in class X.
  • You can overload static methods, instance methods and constructors. A subclass can also add overloads of inherited methods.

Why can the return type not be used? Because the compiler chooses a method from the arguments. A statement like f(); ignores the result, so there would be nothing left to choose with.

How the compiler picks: three phases

When several overloads could accept a call, the compiler works in three phases and stops at the first phase that finds a match:

PhaseWhat is allowedExample conversion
1Exact match, primitive widening, and passing a subtype. No boxing, no varargsbyte → int → long, String → Object
2Phase 1 plus boxing and unboxingint → Integer, double → Double → Object
3Phase 2 plus variable-arity (varargs) methodsf(1, 2) to f(int... x)

Inside one phase, if more than one method applies, the most specific one wins (int is more specific than long; String is more specific than Object). If no single method is most specific, the call is ambiguous and does not compile.

public class OvRes {
    static void f(int x)     { System.out.println("f(int)"); }
    static void f(long x)    { System.out.println("f(long)"); }
    static void f(Integer x) { System.out.println("f(Integer)"); }
    static void f(Object x)  { System.out.println("f(Object)"); }
    static void f(int... x)  { System.out.println("f(int...)"); }

    public static void main(String[] args) {
        byte b = 1;
        f(5);                    // exact match
        f(b);                    // byte widens to int; int is more specific than long
        f(5L);                   // exact match
        f(Integer.valueOf(5));   // exact match
        f(5.0);                  // no widening fits; double boxes to Double, which is an Object
        f("hi");                 // String is an Object
        f();                     // only the varargs method can take zero arguments
        f(1, 2);                 // only the varargs method fits
    }
}

Two more rules fall out of the phases. Widening beats boxing, because widening is phase 1 and boxing is phase 2. Boxing beats varargs, because varargs is phase 3.

static void g(long x)    { System.out.println("g(long)"); }
static void g(Integer x) { System.out.println("g(Integer)"); }
static void h(Integer x) { System.out.println("h(Integer)"); }
static void h(int... x)  { System.out.println("h(int...)"); }

// in main():

h(5);    // h(Integer): boxing (phase 2) wins over varargs (phase 3)

The declared type decides, not the real object

Overloads are chosen at compile time, so only the declared types of the arguments count. The run-time type of the object is invisible to the compiler.

static void show(Object o) { System.out.println("show(Object)"); }
static void show(String s) { System.out.println("show(String)"); }

// in main():
Object o = "hi";
show(o);                  // show(Object): the declared type of o is Object
show("hi");               // show(String)
show((Object) "hi");      // show(Object): the cast changes the declared type
show(null);               // show(String): null fits both; String is more specific
show(Object)
show(String)
show(Object)
show(String)

This is the key difference from overriding, where the object decides at run time. The first output line surprises many people: the variable holds a String, yet show(Object) runs.

Overloads and null

A null argument fits every reference type, so the compiler picks the most specific overload. If two overloads are equally specific, the call is ambiguous:

static void print(String s) { }
static void print(StringBuilder sb) { }

// print(null);    // error: reference to print is ambiguous
//                 //   both method print(String) and method print(StringBuilder) match
print((String) null);   // fix: cast to the type you mean

The classic trap: List.remove(int) versus remove(Object)

List has two remove methods: remove(int index) and remove(Object o). For a List<Integer>, phase 1 finds an exact match for an int argument, so the index version wins and boxing is never tried.

List<Integer> nums = new ArrayList<>(List.of(10, 20, 30, 1));
nums.remove(1);                        // remove(int index): removes the element at index 1 (20)
System.out.println(nums);              // [10, 30, 1]
nums.remove(Integer.valueOf(1));       // remove(Object): removes the value 1
System.out.println(nums);              // [10, 30]

Edge cases

  • System.out.println('a') prints a, but System.out.println('a' + 1) prints 98: the sum is an int, so the int overload runs.
  • A varargs call with no extra argument prefers the fixed-arity method: log("x") picks log(String) over log(String, Object...).
  • Overloading works across inheritance. In a subclass, eat(Dog) next to an inherited eat(Animal) is an overload, not an override, because the parameter types differ (see the output-prediction puzzles).
  • A generic method and a non-generic method with the same erasure, such as f(List<String>) and f(List<Integer>), do not compile as a pair: name clash: … have the same erasure (Module 4).
  • main can be overloaded, but the JVM starts the program only through the classic one.

Conventions for overloading

  • Overload only when the methods do the same thing on different inputs. If the behaviour differs, use different names: DataOutputStream has writeInt and writeLong, not ten write overloads.
  • Avoid overloads with the same number of parameters whose types are related (Object and String, int and Integer). The caller can no longer predict which one runs.
  • Do not overload with different functional interfaces at the same position; lambda arguments become ambiguous (Module 5).
  • To keep the number of constructors small, use chaining with this(…) (constructors) or static factory methods with distinct names.

Interview: overloading questions

  • What is overloading? Same name, different parameter list, resolved at compile time. It is called compile-time or static polymorphism.
  • Can you overload by return type? No; the return type is not part of the signature.
  • Which method runs for f(null)? The most specific overload; ambiguity is a compile error.
  • Order of resolution? Exact or widening, then boxing, then varargs.
  • Overloading vs overriding? The comparison table is in polymorphism.

Polymorphism: compile-time vs runtime, dynamic method dispatch

Polymorphism ("many forms") lets one reference type stand for many real types, so the same call runs different code depending on the actual object: chosen at run time for overriding, at compile time for overloading.

Imagine the checkout page of a shopping app. The customer pays with UPI, a card or cash on delivery. The checkout code should not contain a branch for every payment type. It should say "pay this amount" and let each payment type know how. That is polymorphism, the third pillar of OOP: one interface, many implementations, and the right one runs automatically.

A first example

The type PaymentMethod below is an interface: a type that lists methods without bodies (see interfaces). Everything here works the same with a parent class and overriding.

import java.util.*;

interface PaymentMethod {
    String pay(long amountPaise);
}

class UpiPayment implements PaymentMethod {
    private final String upiId;
    UpiPayment(String upiId) { this.upiId = upiId; }

    @Override public String pay(long amountPaise) {
        return "Paid " + amountPaise + " paise via UPI " + upiId;
    }
    String scanQr() { return "scanning QR"; }              // only UpiPayment has this
}

class CardPayment implements PaymentMethod {
    private final String last4;
    CardPayment(String last4) { this.last4 = last4; }

    @Override public String pay(long amountPaise) {
        return "Paid " + amountPaise + " paise by card ending " + last4;
    }
}

class CashOnDelivery implements PaymentMethod {
    @Override public String pay(long amountPaise) {
        return "Will collect " + amountPaise + " paise at the door";
    }
}

public class Checkout {
    static void checkout(PaymentMethod method, long amountPaise) {   // knows only the interface
        System.out.println(method.pay(amountPaise));
    }

    public static void main(String[] args) {
        List<PaymentMethod> methods = List.of(
                new UpiPayment("asha@upi"), new CardPayment("4242"), new CashOnDelivery());
        for (PaymentMethod m : methods) {
            checkout(m, 49_900);                           // same call, three behaviours
        }
    }
}
Paid 49900 paise via UPI asha@upi
Paid 49900 paise by card ending 4242
Will collect 49900 paise at the door

The method checkout was written once. If the shop adds NetBanking next month, you write one new class, and checkout does not change. New behaviour arrives without editing old, tested code — this is the open/closed idea you will meet again in design principles (System Design · Module 1).

Compile-time and run-time polymorphism

Java has two mechanisms that people call polymorphism. They differ in when the method is chosen.

When an interviewer says "polymorphism" without more words, they usually mean the run-time kind. Details of overloading are in their own article.

Reference type and object type

In PaymentMethod m = new UpiPayment("asha@upi"); there are two types in play:

  • The reference type (also called the declared or compile-time type) is PaymentMethod. It decides which methods you are allowed to call. The compiler checks this.
  • The object type (the actual or run-time type) is UpiPayment. It decides which implementation runs. The JVM decides this while the program runs.

Assigning a subclass object to a parent-type variable is called upcasting. It is always safe and needs no cast. The price is that the variable only offers the parent's methods:

PaymentMethod p = new UpiPayment("ravi@upi");
p.pay(100);        // fine: pay() is in PaymentMethod
p.scanQr();        // compile error: scanQr() exists in UpiPayment, not in PaymentMethod
Checkout2.java:4: error: cannot find symbol
        p.scanQr();
         ^
  symbol:   method scanQr()
  location: variable p of type PaymentMethod

To call scanQr() you would need a downcast; see casting and instanceof. A good design usually avoids the need: put what callers need into the shared type.

How dynamic method dispatch works

Dynamic method dispatch is the run-time lookup that finds the right overriding method. It happens in two steps, one at each time:

In bytecode, a call on a class type is an invokevirtual instruction and a call on an interface type is invokeinterface. Conceptually, each class has a table of its methods (a virtual method table). A subclass starts with a copy of its parent's table and replaces the entries for the methods it overrides. A call looks up the method in the table of the object's real class. The JIT compiler (Module 7) often removes the cost: if a call site has only ever seen one class, it can inline the method directly. So polymorphism is not slow.

What is polymorphic and what is not

Only instance methods that can be overridden are chosen by the object. Everything else is fixed by the compiler. This is also the answer to the interview question "static binding versus dynamic binding": binding means linking a method call to the method body.

The proof for fields and static methods is the Hiding example in overriding: p.f gave P.f although the object was a C.

Replace conditionals with polymorphism

Polymorphism removes long if/switch chains on a "type" value. Every new type forces you to find and edit every such chain.

Wrong: branch on a type code

static String pay(String type, long paise) {
    if (type.equals("UPI"))  { return "UPI " + paise; }
    else if (type.equals("CARD")) { return "Card " + paise; }
    else if (type.equals("COD"))  { return "COD " + paise; }
    throw new IllegalArgumentException(type);   // edit here for every new type
}

Right: let each type know itself

static String pay(PaymentMethod method, long paise) {
    return method.pay(paise);         // new types need no change here
}

Polymorphism is everywhere in Java

  • List<String> names = new ArrayList<>(); — you code against List; the object may be an ArrayList or a LinkedList.
  • Comparator, Runnable and Iterator — you pass behaviour; the library calls it.
  • Spring injects a PaymentGateway bean, and your service calls gateway.charge(…) without knowing whether Razorpay or a test fake is behind it.
  • JDBC: your code calls Connection and PreparedStatement; the real classes come from the database driver.

Java also has a third kind, parametric polymorphism: generics let one class or method work for many types (List<T>, Module 4). The run-time and compile-time kinds above are the ones about methods.

Rules to remember

  • The reference type decides what you can call; the object type decides which override runs.
  • Only overridable instance methods are dynamic. Fields, static methods, private methods and overload choice are fixed at compile time.
  • Upcasting is implicit and safe; downcasting needs a cast and can fail at run time.

Edge cases

  • Calling a method on a null reference throws NullPointerException; there is no object to dispatch on.
  • A call to an overridden method from a parent's constructor runs the child's version, before the child's fields are ready (initialization order).
  • Inside a parent's method, calling another overridable method means this.other(), which is dispatched dynamically. This is the basis of the Template Method pattern (abstract classes).
  • Dispatch also works for interface default methods: the most specific implementation of the object's class wins.

Mistakes to avoid

  • Believing the reference type picks the override. It does not: Employee e = new Manager(…); e.monthlyPay() runs the Manager's version.
  • Long instanceof chains in the caller instead of a method in the types (see the Wrong example above).
  • Mixing up overloading and overriding in puzzles. Ask first: is the choice about arguments (compile time) or about the receiver object (run time)?

Interview: "Explain polymorphism with an example"

  • Definition: one type, many forms; the same method call behaves differently depending on the actual object.
  • Two kinds: compile-time (overloading, chosen by the compiler from argument types) and run-time (overriding, chosen by the JVM from the object's class).
  • Example: PaymentMethod with UPI, card and COD; checkout() is written once and works with any of them.
  • How it works: upcasting plus dynamic method dispatch (a virtual method table lookup).
  • What is not polymorphic: fields, static methods, private methods.
  • Benefit: add new types without changing existing code; remove if/else chains.

Java 8 (2014) was the biggest change in the language's history. It added lambdas, method references and the Stream API, so you can pass behaviour around as a value and describe what you want instead of writing every loop by hand. It also added Optional and the java.time API. Every release since then has added more: var, text blocks, switch expressions, records, pattern matching, sealed classes, sequenced collections and unnamed variables.

This is not optional syntax sugar. Spring Boot code, code reviews and interviews all assume you can read and write it fluently — "find the second highest salary using streams" is one of the most asked Java interview questions. This module builds on OOP (Module 2) and collections (Module 4). The functional interfaces you learn here come back in CompletableFuture (Module 6) and all over Spring.

After this module you will be able to:

  • write lambdas and method references, and explain target typing and the "effectively final" rule;
  • pick the right interface from java.util.function and compose small functions into bigger ones;
  • build stream pipelines that filter, map, sort, group and reduce — and solve the common stream interview questions;
  • use Optional the way it was designed and avoid NullPointerException;
  • handle dates, times, time zones and durations correctly with java.time;
  • use var, text blocks, switch expressions, pattern matching, record patterns, sealed classes and sequenced collections, and say which Java version brought each one.

Functional programming ideas in one page

Functional style means treating behaviour as a value you can pass around, preferring pure functions and immutable data, and describing what result you want instead of how to loop for it.

Java is an object-oriented language, and it stays one. Since Java 8, though, it has borrowed a few ideas from functional programming (FP) — a style where programs are built mainly from functions that take values and return new values. You do not need to learn Haskell. You need five ideas, because lambdas, streams and Optional are all built on them.

The five ideas

Behaviour as data
A piece of code can be stored in a variable, passed to a method and returned from a method, just like a number or a string. In "sort these orders by price", the "by price" part is behaviour that you hand to sort(). A method that accepts or returns behaviour is called a higher-order function; filter, map and Comparator.comparing are examples.
Pure functions
A pure function returns a result that depends only on its arguments and does nothing else. It does not change fields, modify its arguments, print, write to a database or read the clock. Call it twice with the same input and you always get the same output.
Side effects
A side effect is anything a function does besides returning a value: printing, saving a row, changing a shared list, sending an SMS. Real programs need side effects. The goal is to keep them few, obvious and at the edges of the program.
Immutability
An immutable object cannot change after it is created. String, Integer, records with immutable fields, List.of(...) and every java.time type are immutable. To "change" one, you create a new one.
Declarative style
Imperative code says how: create a list, loop, check, add, sort. Declarative code says what: "names of active customers in Mumbai, in upper case, sorted". Streams are Java's declarative tool.

Imperative vs declarative — the same task twice

import java.util.*;

public class FunctionalIdeas {
    record Customer(String name, String city, boolean active) {}

    public static void main(String[] args) {
        List<Customer> customers = List.of(
                new Customer("Ravi", "Mumbai", true),
                new Customer("Asha", "Pune", true),
                new Customer("Kiran", "Mumbai", false),
                new Customer("Meera", "Mumbai", true));

        // Imperative: say HOW, step by step, with a mutable result list
        List<String> result1 = new ArrayList<>();
        for (Customer c : customers) {
            if (c.active() && c.city().equals("Mumbai")) {
                result1.add(c.name().toUpperCase());
            }
        }
        Collections.sort(result1);

        // Declarative: say WHAT you want; each step is a small function
        List<String> result2 = customers.stream()
                .filter(Customer::active)
                .filter(c -> c.city().equals("Mumbai"))
                .map(c -> c.name().toUpperCase())
                .sorted()
                .toList();

        System.out.println(result1);
        System.out.println(result2);
    }
}
[MEERA, RAVI]
[MEERA, RAVI]

Both are correct. The second one reads like the requirement, has no temporary list to manage and no index to get wrong. Each step (filter, map) receives a small function — behaviour as data.

Behaviour as data in a real setting

Suppose each payment mode has its own fee rule. Instead of a long if-else chain, store the rules as values in a map:

Map<String, Function<Long, Long>> feeRules = Map.of(
        "UPI", amount -> 0L,                               // no fee
        "CARD", amount -> amount * 2 / 100,                // 2%
        "WALLET", amount -> Math.min(amount / 100, 50L));  // 1%, at most ₹50

System.out.println(feeRules.get("UPI").apply(1500L));      // 0
System.out.println(feeRules.get("CARD").apply(1500L));     // 30
System.out.println(feeRules.get("WALLET").apply(10000L));  // 50

Adding a new payment mode is now one new map entry, not a new branch in five places. This is the strategy pattern without writing a class per strategy.

Pure vs impure

public class GstCalculator {
    private int gstPercent = 18;   // anyone with a reference can change this
    private int callCount = 0;

    // Impure: reads mutable state, changes state and does I/O
    public long withGstImpure(long amount) {
        callCount++;                                   // side effect
        System.out.println("Calculating GST...");      // side effect
        return amount + amount * gstPercent / 100;     // depends on a field
    }

    // Pure: the result depends only on the arguments; nothing else happens
    public static long withGst(long amount, int gstPercent) {
        return amount + amount * gstPercent / 100;     // withGst(1000, 18) is always 1180
    }
}

Why prefer the pure version where you can:

  • Easy to test — no setup, no mocks: give an input, check the output.
  • Safe with threads — nothing shared is modified, so there is nothing to race on (see Module 6).
  • Easy to reason about — you can replace a call with its result in your head. This property is called referential transparency.
  • Cacheable — same input, same output, so a result can be stored and reused.

Rule: functions you pass to streams must not modify the stream's source

The Stream API requires the functions you give it to be non-interfering (they never modify the source collection) and, in most cases, stateless (the result does not depend on state that changes while the pipeline runs). Break this and you get wrong results or a ConcurrentModificationException. Details in Streams vs loops.

Edge cases: what "immutable" really means in Java

  • final makes the reference constant, not the object. final List<String> names = new ArrayList<>(); still allows names.add("x").
  • Collections.unmodifiableList(list) returns a read-only view. If someone changes the original list, the view shows the change.
  • List.of and List.copyOf are unmodifiable, but only shallowly: if the elements are mutable objects, those objects can still change.
  • Java is not a pure functional language. Lambdas can still change state, and there is no tail-call optimisation, so deep recursion still ends in StackOverflowError.

Mistake: leaking an internal mutable list

A getter that returns its private list lets any caller change your object's state behind your back.

Wrong: the caller can add to or clear the cart

public class Cart {
    private final List<String> items = new ArrayList<>();

    public List<String> getItems() {
        return items;
    }
}

Right: return an unmodifiable snapshot

public class Cart {
    private final List<String> items = new ArrayList<>();

    public List<String> getItems() {
        return List.copyOf(items);
    }
}

Real projects: functional core, imperative shell

In a Spring Boot service, keep calculations — pricing, discount rules, validation, entity-to-DTO mapping — as pure methods that take values and return values. Keep the side effects (repository calls, Kafka publishing, HTTP calls, logging) in the outer service and controller layer. The pure core is unit-tested in milliseconds without starting Spring; the shell is thin. Records with a compact constructor that calls List.copyOf(...) are a common way to make value objects truly immutable.

Interview: "Is Java a functional language? What is a pure function?"

  • Java is object-oriented with functional features since Java 8: lambdas, functional interfaces, method references, streams and Optional.
  • A function in Java is still an object — an instance of a functional interface — but you can pass it around like a value.
  • A pure function: same input → same output, no side effects. Benefits: easy testing, thread safety, caching, readable code.
  • Immutability removes a whole class of bugs (shared mutable state) and makes objects safe to share between threads.
  • Mention a trade-off: debugging long pipelines is harder, and not every loop should become a stream.

Lambda expressions: syntax, target typing and captured variables

A lambda is a short anonymous function — parameters, an arrow and a body — that the compiler turns into an object of the functional interface the surrounding code expects.

Before Java 8, passing behaviour meant writing an anonymous inner class: a class with no name, declared and instantiated in one expression. Sorting names by length looked like this:

List<String> names = new ArrayList<>(List.of("Priya", "Om", "Lakshmi"));

// Before Java 8: anonymous inner class — five lines of ceremony
Collections.sort(names, new Comparator<String>() {
    @Override
    public int compare(String a, String b) {
        return Integer.compare(a.length(), b.length());
    }
});

// Java 8+: a lambda keeps only the idea
names.sort((a, b) -> Integer.compare(a.length(), b.length()));

// Even shorter: a ready-made comparator plus a method reference
names.sort(Comparator.comparingInt(String::length));

System.out.println(names);   // [Om, Priya, Lakshmi]

A lambda expression is that idea written as (parameters) -> body. It has no name, no class declaration and no @Override. It can only be used where Java expects a functional interface — an interface with exactly one abstract method (next article). The lambda is the implementation of that one method.

import java.util.*;
import java.util.function.*;

public class LambdaSyntax {
    public static void main(String[] args) {
        Supplier<String> greeting = () -> "Namaste";
        UnaryOperator<Integer> square = n -> n * n;
        BinaryOperator<Integer> add = (a, b) -> a + b;
        BinaryOperator<Integer> addTyped = (Integer a, Integer b) -> a + b;
        BinaryOperator<Integer> addVar = (var a, var b) -> a + b;

        Consumer<String> printer = msg -> {          // block body, no return value
            String line = "[LOG] " + msg;
            System.out.println(line);
        };

        Function<Integer, String> grade = marks -> {  // block body with return
            if (marks >= 60) {
                return "First class";
            }
            return "Keep going";
        };

        System.out.println(greeting.get());
        System.out.println(square.apply(7));
        System.out.println(add.apply(2, 3) + " " + addTyped.apply(2, 3) + " "
                + addVar.apply(2, 3));
        printer.accept("Order placed");
        System.out.println(grade.apply(72));
    }
}

Target typing: a lambda takes its type from the context

A lambda has no type of its own. The compiler looks at where it appears — the target type — and checks that the lambda fits the single abstract method of that interface. Target typing works in assignments, method arguments, return statements and casts. The same lambda text can therefore become different types:

Predicate<String> isEmptyP = s -> s.isEmpty();         // boolean test(String)
Function<String, Boolean> isEmptyF = s -> s.isEmpty();  // Boolean apply(String)

System.out.println(isEmptyP.test("") + " " + isEmptyF.apply("UPI"));   // true false

Object o = () -> System.out.println("hi");                // compile error
Object ok = (Runnable) () -> System.out.println("hi");    // fine: the cast is the target
error: incompatible types: Object is not a functional interface

Because the parameter types come from the target, you rarely write them. In names.sort((a, b) -> ...), the compiler knows sort takes a Comparator<String>, so a and b are String.

What the compiler and JVM do with a lambda

  1. javac moves the lambda body into a private method of your class, with a generated name such as lambda$run$0.
  2. Where the lambda is created, javac emits an invokedynamic instruction instead of new SomeClass().
  3. The first time that instruction runs, the JVM (through LambdaMetafactory) generates a small class at runtime that implements the interface and calls the private method.
  4. After that, creating the lambda is cheap. A lambda that captures nothing is usually created once and reused — an implementation detail, so never compare lambdas with ==.

Capturing variables: the "effectively final" rule

A lambda can use local variables of the method it is written in. This is called capturing. The rule: a captured local variable must be final or effectively final — never assigned again after its first assignment, so adding final would not cause an error.

String city = "Pune";                         // effectively final
Runnable r = () -> System.out.println("Delivering in " + city);
r.run();                                      // Delivering in Pune

int count = 0;
orders.forEach(o -> count++);                 // compile error
error: local variables referenced from a lambda expression must be final or effectively final

Even a reassignment after the lambda (city = "Delhi"; on a later line) makes city not effectively final, and the lambda line fails to compile.

Why Java has this rule:

  1. A local variable lives in the method's stack frame, which disappears when the method returns. A lambda can live longer — it can be stored in a field or run later on another thread. So the lambda receives a copy of the value when it is created.
  2. If you could change the variable later, the copy and the original would disagree. Forbidding reassignment guarantees they are always equal, so "copy" and "same variable" behave identically.
  3. Local variables are private to one thread by design. If lambdas running on other threads could write to them, every local would become a possible data race.

What you can do:

  • Read and modify fields (instance and static). The lambda captures this — a reference — and reaches the field through the object on the heap. It compiles, but it is still a side effect, and it is unsafe in parallel streams.
  • Modify the object a final variable points to: audit.add(s) inside a lambda is fine when audit itself is never reassigned. Effectively final is about the variable, not the object.
  • Use a holder such as AtomicInteger when you truly need a counter — but first ask whether a stream operation (count(), sum()) gives the answer directly.

this in a lambda vs in an anonymous class

A lambda does not create a new scope. Inside it, this means the enclosing object, exactly as on the line before the lambda. Inside an anonymous class, this means the anonymous object itself.

public class ThisDemo {
    @Override
    public String toString() {
        return "ThisDemo object";
    }

    void run() {
        Runnable lambda = () -> System.out.println("lambda    -> this = " + this);

        Runnable anonymous = new Runnable() {
            @Override
            public void run() {
                System.out.println("anonymous -> this = " + this);
            }

            @Override
            public String toString() {
                return "anonymous Runnable object";
            }
        };

        lambda.run();
        anonymous.run();
    }

    public static void main(String[] args) {
        new ThisDemo().run();
    }
}

anonymous -> this = anonymous Runnable object

The same "no new scope" idea explains another rule: a lambda parameter cannot reuse the name of a local variable from the enclosing method. With String name = "Ravi"; in scope, name -> name.length() fails with variable name is already defined in method main(String[]). An anonymous class may shadow it.

Checked exceptions inside lambdas

The interfaces in java.util.function do not declare any checked exceptions. So a lambda passed to map cannot let an IOException escape:

List<String> texts = paths.stream()
        .map(p -> Files.readString(p))      // readString throws IOException
        .toList();
error: unreported exception IOException; must be caught or declared to be thrown

The clean fix is a small named method that converts the checked exception into an unchecked one. UncheckedIOException exists exactly for this.

static String readFile(Path path) {
    try {
        return Files.readString(path);
    } catch (IOException e) {
        throw new UncheckedIOException(e);   // keeps the original as the cause
    }
}

List<String> texts = paths.stream()
        .map(FileReport::readFile)            // method reference keeps the pipeline clean
        .toList();

Rules the compiler enforces

  • A lambda needs a functional interface as its target type.
  • Captured local variables must be final or effectively final.
  • Give types to all parameters or to none: (Integer a, b) -> a + b fails with cannot mix implicitly-typed and explicitly-typed parameters. Mixing var with explicit types fails too.
  • A lambda parameter or local cannot reuse a name already in scope in the enclosing method.
  • A block body that returns a value must return on every path.

Conventions

  • Keep a lambda to one expression or a few lines. If it grows, move the logic to a named private method and pass a method reference.
  • Prefer an expression body over { return ...; }, and leave out parameter types unless they make the code clearer.
  • Use meaningful parameter names in business code (order -> order.total()); single letters are fine in tiny lambdas like (a, b) -> a + b.
  • Do not use lambdas for side effects inside stream pipelines; return values instead.

Edge cases

  • return inside a lambda leaves only the lambda. In list.forEach(s -> { if (s.isEmpty()) return; print(s); }) it skips one element, like continue.
  • You cannot break out of forEach. Use a normal loop, or a short-circuiting stream operation such as anyMatch or takeWhile.
  • s -> audit.add(s) fits a Consumer<String> even though add returns boolean: when the body is a method call, the result may be discarded.
  • An exception thrown inside a lambda appears when the functional method runs — possibly much later, or on another thread. Stack traces show frames like lambda$main$0.

Mistake: counting with a local variable inside forEach

Wrong: does not compile (and is not functional style)

int emptyCount = 0;
items.forEach(s -> {
    if (s.isEmpty()) {
        emptyCount++;   // captured local is modified
    }
});

Right: let the stream compute the value

long emptyCount = items.stream()
        .filter(String::isEmpty)
        .count();

Interview: "Why must captured variables be effectively final?" and "Lambda vs anonymous class?"

  • The lambda gets a copy of a local's value, because locals live on the stack and the lambda may outlive the method or run on another thread. Forbidding reassignment keeps the copy and the original identical and avoids data races on locals.
  • Fields are not copied — they are reached through the captured this reference — so they can be modified (but should not be, in streams).
  • Lambda vs anonymous class: lambdas implement only functional interfaces, have no state, share the enclosing scope (this is the outer object), and compile to a private method plus invokedynamic instead of a separate class file.
  • Target typing: a lambda's type is decided by the context; the same lambda can be a Predicate or a Function.

Functional interfaces and the java.util.function package

A functional interface has exactly one abstract method; java.util.function gives you 43 ready-made ones, and Predicate, Function, Consumer and Supplier are the four you use every day.

A functional interface is an interface with exactly one abstract method — often called a SAM (single abstract method) type. Any lambda or method reference whose parameters and return type fit that method can be used as an instance of the interface. Interfaces you already know, such as Runnable (void run()), Callable<V> (V call()) and Comparator<T> (int compare(T, T)), are functional interfaces.

What counts as "one abstract method"

  • Default methods and static methods do not count. A functional interface can have many of them — Function has andThen, compose and identity.
  • Abstract methods that match public methods of Object (equals, hashCode, toString) do not count, because every implementing class already has them. That is why Comparator, which declares boolean equals(Object), is still functional.
  • An interface that inherits one abstract method and declares no new one is also functional.

The @FunctionalInterface annotation

@FunctionalInterface is optional. Any interface with one abstract method works with lambdas. The annotation does two things: it documents your intent, and it makes the compiler fail if someone later adds a second abstract method.

@FunctionalInterface
interface PaymentGateway {
    void pay(long amount);
    void refund(long amount);   // second abstract method
}
error: Unexpected @FunctionalInterface annotation
  PaymentGateway is not a functional interface

Primitive specializations — avoiding boxing

Generics work only with objects, so a Function<Integer, Integer> boxes every int into an Integer object and unboxes it again. In a loop over millions of numbers this creates garbage and costs time. Primitive specializations work on int, long and double directly. Their names follow a pattern:

Composing functions

Many functional interfaces have default methods that build a new function out of existing ones. This is composition: small, tested pieces snapped together.

import java.util.*;
import java.util.function.*;
import java.util.stream.*;

public class Compose {
    record User(String name, int age, String email) {}

    public static void main(String[] args) {
        // andThen vs compose: the order is the whole difference
        Function<Integer, Integer> times2 = x -> x * 2;
        Function<Integer, Integer> plus3 = x -> x + 3;
        System.out.println(times2.andThen(plus3).apply(5));   // (5 * 2) + 3
        System.out.println(times2.compose(plus3).apply(5));   // (5 + 3) * 2

        Function<String, String> clean = ((Function<String, String>) String::trim)
                .andThen(String::toLowerCase);
        System.out.println("[" + clean.apply("  Ravi@Example.COM ") + "]");

        // Predicate composition: build rules from small pieces
        Predicate<User> isAdult = u -> u.age() >= 18;
        Predicate<User> hasEmail = u -> u.email() != null && !u.email().isBlank();
        Predicate<User> canRegister = isAdult.and(hasEmail);

        List<User> users = List.of(
                new User("Asha", 25, "asha@mail.in"),
                new User("Rohan", 16, "rohan@mail.in"),
                new User("Kiran", 30, " "));
        System.out.println(users.stream().filter(canRegister).map(User::name).toList());
        System.out.println(users.stream().filter(canRegister.negate())
                .map(User::name).toList());
        System.out.println(users.stream().filter(isAdult.or(hasEmail))
                .map(User::name).toList());

        List<String> words = List.of("java", " ", "", "spring");
        System.out.println(words.stream()
                .filter(Predicate.not(String::isBlank)).toList());

        // identity(): "the element itself" as the map value
        Map<String, User> byName = users.stream()
                .collect(Collectors.toMap(User::name, Function.identity()));
        System.out.println(byName.get("Asha"));

        Consumer<String> log = s -> System.out.println("LOG: " + s);
        Consumer<String> audit = s -> System.out.println("AUDIT: " + s);
        log.andThen(audit).accept("payment 499");

        BiFunction<Integer, Integer, Integer> multiply = (a, b) -> a * b;
        System.out.println(multiply.andThen(r -> "Result = " + r).apply(6, 7));

        BinaryOperator<String> longer =
                BinaryOperator.maxBy(Comparator.comparingInt(String::length));
        System.out.println(longer.apply("UPI", "NEFT"));

        // Primitive specializations: no Integer objects created
        IntPredicate even = n -> n % 2 == 0;
        ToIntFunction<String> length = String::length;
        IntBinaryOperator max = Math::max;
        System.out.println(even.test(10) + " " + length.applyAsInt("Swiggy") + " "
                + max.applyAsInt(3, 9));
    }
}

Note the cast in the clean line: a method reference on its own has no type, so you cannot call .andThen on String::trim directly. Assign it to a typed variable first (Function<String, String> trim = String::trim;) or cast it, as shown.

Writing your own functional interface

Use the standard interfaces first. Write your own when you need a domain name that makes code clearer, more than two parameters, or a method that throws a checked exception. You can add default and static methods to make it composable:

@FunctionalInterface
public interface DiscountPolicy {
    long apply(long amount);                       // the single abstract method

    default DiscountPolicy then(DiscountPolicy next) {
        return amount -> next.apply(this.apply(amount));
    }

    static DiscountPolicy percent(int pct) {
        return amount -> amount - amount * pct / 100;
    }

    static DiscountPolicy flat(long off) {
        return amount -> Math.max(0, amount - off);
    }
}

// Usage
DiscountPolicy festive = DiscountPolicy.percent(10).then(DiscountPolicy.flat(100));
System.out.println(festive.apply(2000));                  // 2000 → 1800 → 1700
System.out.println(DiscountPolicy.flat(500).apply(300));  // never below 0 → 0
1700
0

Rule: exactly one abstract method

A lambda can target an interface only if it has exactly one abstract method after ignoring default methods, static methods and public Object methods. Abstract classes never work as lambda targets, even with one abstract method.

Conventions

  • Prefer the standard interfaces in method signatures; everyone knows what a Predicate<Order> is.
  • Put @FunctionalInterface on every interface you write to be used with lambdas.
  • Use primitive specializations (IntPredicate, ToLongFunction) in hot code paths and with primitive streams.
  • Name predicates as questions or adjectives (isAdult, hasEmail) so compositions read like sentences: isAdult.and(hasEmail).

Edge cases

  • Unboxing null throws NullPointerException: a Function<Integer, Integer> written as x -> x * 2 fails if it receives null.
  • p.and(q) short-circuits: q is not evaluated when p is false. Order cheap or null-guarding checks first.
  • Supplier has no composition methods; Runnable and Callable have none either.
  • Function<T, Boolean> and Predicate<T> are different types; you cannot pass one where the other is expected, even if the lambda text is the same.

Mistake: mixing up andThen and compose

f.andThen(g) reads left to right: f, then g. f.compose(g) runs g first — like maths notation f(g(x)). When in doubt, use andThen; it matches reading order and most people never need compose.

Interview: "What is a functional interface? Is @FunctionalInterface required?"

  • An interface with exactly one abstract method; default, static and Object-method declarations do not count.
  • The annotation is optional; it documents intent and makes the compiler reject a second abstract method.
  • Name the core four with their methods: Predicate.test, Function.apply, Consumer.accept, Supplier.get.
  • UnaryOperator/BinaryOperator are Function/BiFunction with all types the same.
  • Primitive specializations exist to avoid boxing cost and null-unboxing errors.
  • Older interfaces such as Runnable, Callable and Comparator are functional too, which is why lambdas work with threads and sorting.

Memory leaks, JVM flags and diagnostic tools

A Java memory leak means objects that are no longer needed are still reachable; find them with a heap dump, size the JVM with -Xmx and friends, and inspect running processes with jcmd, jstack, jmap, JFR and VisualVM.

What is a memory leak in a garbage-collected language?

The GC cannot free an object that is still reachable, even if your program will never use it again. A leak in Java is therefore "unintentional reachability": something keeps a reference to dead data. Memory use climbs over hours or days, GC runs more and more often, and finally you see OutOfMemoryError. The symptom on a graph is a saw-tooth whose baseline (heap after each full GC) keeps rising.

Common causes

Static collections
A static Map or List that is only ever added to lives as long as the class. Typical: a hand-made cache or a registry.
Caches without eviction
A HashMap used as a cache that grows with every new key (user IDs, request URLs). Use a bounded cache with expiry (Caffeine, Spring's cache abstraction) instead.
Listeners and callbacks never removed
Registering an object as an observer or event listener makes the publisher hold it. If you never call remove, the listener — and everything it references — stays.
ThreadLocal in thread pools
Pool threads live forever, so a value stored in a ThreadLocal and not remove()d lives forever too. In app servers it can also pin the whole web application's class loader.
Unclosed resources
Streams, Connections, ResultSets, HTTP clients and Scanners that are not closed leak native memory and OS handles (and sometimes heap). Use try-with-resources.
Wrong equals/hashCode or mutable keys
Entries put into a HashMap/HashSet that can never be found again can never be removed (next articles).
Inner-class references
A non-static inner class or an anonymous class silently holds a reference to its outer instance. A long-lived callback created in a short-lived object keeps the outer object alive.
Unbounded queues and sessions
A queue whose producers are faster than consumers, or HTTP sessions that never expire.

Wrong: unbounded static cache

public class PriceService {
    private static final Map<String, Price> CACHE = new HashMap<>();

    public Price get(String productId) {
        return CACHE.computeIfAbsent(productId, this::loadFromDb);
        // grows forever; also not thread-safe
    }
}

Right: bounded and expiring (Caffeine)

    private final Cache<String, Price> cache = Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(Duration.ofMinutes(10))
            .build();

    public Price get(String productId) {
        return cache.get(productId, this::loadFromDb);
    }
}

Finding a leak

  1. Confirm the pattern. Turn on GC logging (-Xlog:gc) or watch a monitoring dashboard. A rising post-GC heap and more frequent full GCs mean a leak (or simply a too-small heap).
  2. Capture a heap dump while memory is high. Automatically on failure with -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps, or on demand with jcmd <pid> GC.heap_dump /tmp/heap.hprof. Take two dumps some time apart to compare.
  3. Analyse it in Eclipse MAT (Memory Analyzer), VisualVM or IntelliJ's profiler. In MAT, run the Leak Suspects report and the Dominator Tree: it shows which objects keep the largest amount of memory alive.
  4. Follow the path to GC roots from the suspicious object ("Path to GC Roots, exclude weak references") to see which static field, thread or collection holds it.
  5. Fix and verify: bound or clear the structure, then watch the post-GC baseline stay flat.

A quick view without a full dump: jmap -histo <pid> (or jcmd <pid> GC.class_histogram) prints how many instances of each class exist. A class whose count only grows is your suspect.

Heap dumps contain all data in memory — passwords, tokens, personal data. Treat them as secrets: do not email them or upload them to public tools.

Common mistakes

  • Treating every OutOfMemoryError as "the heap is too small". Check the message: Metaspace, native threads and heap are different problems.
  • Setting -Xmx equal to the container limit and getting the process killed by the OS.
  • Adding a dozen old -XX flags from an article written for Java 8.
  • Profiling only in the IDE with tiny data: leaks and GC behaviour show up under production-like load.

Interview: "How do you find and fix a memory leak in production?"

  • Symptoms: rising heap after full GC, frequent GCs, eventually OOM.
  • Capture a heap dump (jcmd GC.heap_dump or dump on OOM), open it in Eclipse MAT, read the leak suspects and the dominator tree, follow the path to GC roots.
  • Typical culprits: static collections, unbounded caches, listeners, ThreadLocals, unclosed resources.
  • Fix by bounding or clearing, then confirm with monitoring. Mention JFR and jmap -histo as lighter tools.

Class loading: loaders, delegation and initialization

The JVM loads a class the first time it is needed, in three steps — loading, linking (verify, prepare, resolve) and initialization — using a chain of class loaders that always ask their parent first.

Java does not load all classes at start-up. A class is brought into memory lazily, the first time the program needs it. Each class is loaded by a class loader, and the pair (class name, loader) identifies the class: the same .class file loaded by two loaders gives two different classes in the JVM.

The three phases

  1. Loading. A class loader finds the bytes of the class (from a folder, a JAR, a module or the network) and creates its runtime representation in Metaspace, plus a java.lang.Class object on the heap.
  2. Linking, in three sub-steps:
    • Verification — the bytecode verifier checks the class file is well-formed and safe.
    • Preparation — memory for static fields is allocated and set to default values (0, false, null), not yet to your assigned values.
    • Resolution — symbolic references in the constant pool (names of other classes, methods, fields) are replaced by direct references. HotSpot often does this lazily.
  3. Initialization. The JVM runs the class's static initializers: static field assignments and static { } blocks, in the order they appear in the source. The superclass is initialized first. This happens at most once per class and is thread-safe.

Parent delegation

When a loader is asked for a class, it does not look itself first. It delegates to its parent, and the parent to its own parent, up to bootstrap. Only if no parent can load the class does the child try.

Why this design?

  • Security. You cannot replace a core class: if someone puts a fake java.lang.String on the classpath, the bootstrap loader finds the real one first and the fake is never used.
  • No duplicates. A class is loaded once by the loader that "owns" it, so everyone sees the same Object and String.
  • Consistency for shared types. (Web containers deliberately bend the rule so each webapp can have its own library versions.)

When is a class initialized?

Initialization runs on the first active use:

  • creating an instance with new;
  • calling a static method;
  • reading or writing a static field that is not a compile-time constant;
  • Class.forName("pkg.Name") (reflection) — this initializes the class;
  • initializing a subclass (the superclass is initialized first);
  • running the class that contains main.

These do not initialize it: reading a static final primitive or String constant (the compiler copies its value into the caller), using Config.class, and declaring an array Config[].

class Config {
    static final int MAX = 10;                 // compile-time constant
    static int counter = 0;
    static { System.out.println("Config initialized"); }
}

class Parent {
    static { System.out.println("Parent static block"); }
    Parent() { System.out.println("Parent constructor"); }
}

class Child extends Parent {
    static { System.out.println("Child static block"); }
    Child() { System.out.println("Child constructor"); }

public class InitDemo {

        System.out.println("start");
        int x = Config.MAX;                    // constant: Config NOT initialized

Why you should care

  • Start-up time: lazy loading and class verification are part of why a big Spring Boot app takes seconds to start.
  • Metaspace leaks: redeploying web apps repeatedly creates new class loaders; if anything (a ThreadLocal, a driver, a static) still references an old loader, all its classes stay in Metaspace.
  • JDBC drivers: older code used Class.forName("org.postgresql.Driver") to load and register the driver. Since JDBC 4 (Java 6) drivers on the classpath register themselves automatically, so this line is no longer needed.

Rule: loaders delegate to the parent first

A class with the same name on the classpath cannot override a core JDK class. Order inside the classpath matters for duplicates: the first JAR that contains the class wins.

Edge cases

  • A compile-time constant is inlined, so changing Config.MAX without recompiling the callers leaves them with the old value.
  • static final objects (static final List<String> X = new ArrayList<>()) are not constants and do trigger initialization.
  • With the module system (Java 9+), a class can be on the path but not readable from another module (IllegalAccessError, "module does not export").
  • Instance initializer blocks and constructors run on every new; static blocks run once per class per loader.

Interview: "Explain class loading" and "ClassNotFoundException vs NoClassDefFoundError"

  • Loading, linking (verify, prepare, resolve), initialization. Lazy: first active use.
  • Bootstrap, platform, application loaders; parent delegation for security and uniqueness.
  • Initialization triggers: new, static method or non-constant static field, Class.forName, subclass.
  • CNFE: checked exception from an explicit by-name load. NCDFE: error from implicit linking when a class that existed at compile time is missing or failed to initialize.
  • Output order for parent/child static blocks and constructors is a classic puzzle: statics (parent, child) first, then constructors (parent, child).

== vs equals, and why hashCode must agree with equals

== compares primitives by value and objects by reference; equals compares by meaning when a class overrides it, and whenever you override equals you must override hashCode so that equal objects land in the same hash bucket.

Module 2 introduced the basics (equals and hashCode in OOP). Here we go deeper: what each comparison really does, the formal contracts, how to write both methods correctly, and exactly what breaks when they disagree.

The equals contract

The Object.equals documentation requires, for non-null references:

  • Reflexive: x.equals(x) is true.
  • Symmetric: if x.equals(y) is true then y.equals(x) is true.
  • Transitive: if x.equals(y) and y.equals(z) then x.equals(z).
  • Consistent: repeated calls give the same answer while the objects are not modified.
  • Non-null: x.equals(null) is false (and never throws).

The usual way to break symmetry is comparing with a different kind of object. A class that "helpfully" lets itself equal a plain String: ci.equals("abc") is true, but "abc".equals(ci) is false. Transitivity breaks with subclasses that add a field: Point(1,2) equals ColorPoint(1,2,RED) if the check ignores colour, and equals ColorPoint(1,2,BLUE) too, yet the two colour points are not equal.

The hashCode contract

  • Consistent: during one run, if the fields used in equals do not change, hashCode() returns the same int every time. (It may differ between runs.)
  • Equal objects ⇒ equal hash codes: if x.equals(y), then x.hashCode() == y.hashCode(). This is the rule that gets broken.
  • Unequal objects may have the same hash code (a collision), but a good function spreads values evenly because collisions make hash tables slower.

The inverse is false: the same hash code does not imply equal objects. "Aa".hashCode() and "BB".hashCode() are both 2112. The default Object.hashCode() is derived from object identity (often loosely based on a memory address or a random number); it is why two "equal" objects have different hashes unless you override.

How a hash collection uses both methods

  1. hashCode() is called on the key; the result selects a bucket (array slot).
  2. Inside that bucket, entries are compared with equals() to find the exact key (see Module 4 for HashMap internals).
  3. If equals says two keys are equal but their hash codes differ, the lookup goes to a different bucket and never calls equals — the entry is "lost".

Demo: what breaks when you override only equals

import java.util.*;

public class BrokenKey {
    static class BadPoint {
        final int x, y;
        BadPoint(int x, int y) { this.x = x; this.y = y; }

        @Override
        public boolean equals(Object o) {                // overridden...
            if (this == o) return true;
            if (!(o instanceof BadPoint other)) return false;
            return x == other.x && y == other.y;
        }
        // ...but hashCode() is NOT overridden: Object's identity hash is used
    }

        @Override
        public boolean equals(Object o) {

            if (!(o instanceof GoodPoint other)) return false;
            return x == other.x && y == other.y;

        @Override
        public int hashCode() { return Objects.hash(x, y); }

        good.add(new GoodPoint(1, 2));

Writing equals and hashCode correctly

import java.util.Objects;

public final class Customer {
    private final String email;       // identity of a customer
    private final String name;

    public Customer(String email, String name) {
        this.email = email;
        this.name = name;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                          // 1. same reference: fast path
        if (!(o instanceof Customer other)) return false;    // 2. null or wrong type
        return Objects.equals(email, other.email)            // 3. compare significant fields
                && Objects.equals(name, other.name);         //    null-safe
    }

    @Override
    public int hashCode() {
        return Objects.hash(email, name);                    // same fields as equals
    }

    @Override
    public String toString() {
        return "Customer[" + email + ", " + name + "]";
    }
}
  • Use the same fields in both methods. A field used in equals but not in hashCode is fine for correctness (equal objects still hash equally); a field in hashCode but not in equals breaks the contract.
  • Objects.equals(a, b) is null-safe equality. Objects.hash(a, b, c) builds a hash from values using the formula result = 31 * result + hash(element) starting at 1, so Objects.hash(1, 2) is 994. It boxes primitives into an array; for hot code compute it by hand with Integer.hashCode, Double.hashCode, and so on.
  • Compare float/double fields with Double.compare(a, b) == 0, not ==, to treat NaN correctly. Compare arrays with Arrays.equals and hash them with Arrays.hashCode.
  • You can generate both methods in IntelliJ (Alt+Insert → equals() and hashCode()), with Lombok (@EqualsAndHashCode, or @Data), or with a record.

Pick one deliberately. getClass() breaks with runtime proxies (a Hibernate lazy proxy is a generated subclass of your entity, so getClass() differs from the real class), which is one reason many JPA codebases use instanceof (or compare only the id) in entity equality.

Mutable keys

If a field used by hashCode changes while the object is inside a HashSet or is a HashMap key, the stored position no longer matches the new hash. The entry is still there but unreachable:

class Key {
    int id;
    Key(int id) { this.id = id; }
    @Override public boolean equals(Object o) { return o instanceof Key k && k.id == id; }
    @Override public int hashCode() { return Integer.hashCode(id); }
}

Set<Key> set = new HashSet<>();
Key k = new Key(1);
set.add(k);
k.id = 2;                                   // mutated after insertion
System.out.println(set.contains(k));        // false: looks in the bucket for hash(2)
System.out.println(set.size());             // 1:     but the entry is still stored (a leak)

Use immutable keys (String, Integer, records of immutable fields, enums). That is also why String is a perfect key.

Records and enums

record Money(long paise, String currency) {}

Money m1 = new Money(49900, "INR");
Money m2 = new Money(49900, "INR");
System.out.println(m1.equals(m2));                    // true: generated, component-wise
System.out.println(m1.hashCode() == m2.hashCode());   // true: generated, consistent
System.out.println(m1);                               // Money[paise=49900, currency=INR]
System.out.println(m1 == m2);                         // false

A record gets equals, hashCode and toString generated from its components. The exact hash formula is unspecified, but it is consistent with equals. Caution: an array component is compared by identity (record Bag(int[] items)), so two records with equal-content arrays are not equal. Enums inherit identity-based equals/hashCode (final in Enum), which is correct since each constant is a singleton.

Related: Comparable and equals

Sorted collections (TreeSet, TreeMap) use compareTo/compare, not equals, to decide whether two elements are the same. It is strongly recommended that compareTo(x) == 0 agrees with equals(x). BigDecimal violates this: 2.0 and 2.00 are different for equals (a HashSet holds both) but equal for compareTo (a TreeSet holds one).

Rule: override equals and hashCode together, using the same fields

Equal objects must return the same hash code, or HashMap, HashSet, Hashtable and ConcurrentHashMap will not find them. If you only need identity, override neither.

Conventions

  • Annotate with @Override; a signature like equals(Customer c) (overload, not override) is silent and never used by collections.
  • Prefer immutable value classes or records; make fields final.
  • Use Objects.equals and Objects.hash unless profiling says otherwise.
  • For JPA entities, base equality on a business key or the id with care for unsaved (null id) objects; do not include lazy collections in equals/hashCode (they trigger database loads).
  • Never use == on strings or wrappers; use Objects.equals(a, b) when either may be null.

Edge cases

  • hashCode() may be any int, including negative; the collection maps it to an index internally.
  • A constant hashCode() (return 1;) is legal but turns a hash table into a list (O(n) lookups); modern HashMap converts long buckets into balanced trees if keys are Comparable, but do not rely on it.
  • Calling an overridable method or accessing lazy state inside equals can cause recursion or extra queries.
  • Cyclic references (A has B, B has A) in equals/hashCode/toString produce StackOverflowError.

Common mistakes

  • Overriding only one of the two.
  • Writing equals(MyClass other) instead of equals(Object other).
  • Using a mutable object (or an object whose hash depends on mutable fields) as a map key.
  • Throwing ClassCastException by casting without checking instanceof/getClass.
  • Comparing Integer values with == (cache trap).

Interview: "What is the contract between equals and hashCode? What if you override only equals?"

  • If a.equals(b) then a.hashCode() == b.hashCode(); hash codes must be stable while the object is unchanged; unequal objects may collide.
  • Only equals overridden: equal objects get different identity hashes, land in different buckets; HashSet allows duplicates and contains/get fail.
  • The five properties of equals: reflexive, symmetric, transitive, consistent, non-null.
  • How to write them: same fields, Objects.equals, Objects.hash, instanceof or getClass() with the trade-off.
  • Records generate both; keys should be immutable; Integer cache trap for ==.

Interview questions — JVM and memory

Explain the JVM architecture.

Three main parts. The class loader subsystem loads, links and initializes classes. The runtime data areas: heap and Metaspace shared by all threads, and per thread a JVM stack of frames, a PC register and a native method stack. The execution engine: interpreter, JIT compiler (C1 and C2, tiered) and garbage collector. JNI connects Java to native code.

What is stored in the stack and what in the heap?

The stack (one per thread) holds frames with local primitives, local references, parameters and the operand stack; frames disappear when the method returns. The heap (shared) holds all objects and arrays, including instance fields, boxed values and the String pool. A local variable Product p = new Product() keeps the reference on the stack and the object on the heap. Static fields live with the class data, and class metadata lives in Metaspace.

What is the difference between StackOverflowError and OutOfMemoryError?

StackOverflowError means one thread's stack is full, nearly always from runaway recursion; fix the base case or use a loop. OutOfMemoryError means the JVM cannot allocate more memory in the heap (Java heap space), Metaspace, or for a new native thread. It usually comes from a leak, too much data loaded at once, or a heap that is too small. Both are Errors, not exceptions you normally catch.

How does garbage collection decide what to remove?

The GC traces from GC roots (local variables on thread stacks, static fields, active threads, JNI references) and marks everything reachable. Unreachable objects are garbage, even when they reference each other in a cycle. Memory is reclaimed by sweeping, copying or compacting. Java does not use reference counting.

What are the young and old generations, and what is a minor vs a full GC?

Most objects die young, so the heap is split into a young generation (Eden plus two survivor spaces) and an old generation. New objects go to Eden. A minor GC copies the live objects of Eden and one survivor into the other survivor; each survival raises an object's age, and old-enough objects are promoted to the old generation. When the old generation fills, a major GC runs; a full GC collects the whole heap and causes the longest stop-the-world pause.

Which garbage collectors do you know and when would you use each?

Serial for tiny heaps and single-CPU containers; Parallel for throughput-oriented batch work; G1, the default since Java 9, for balanced pause times and throughput using heap regions and a pause goal; ZGC and Shenandoah for low-latency services and large heaps with mostly concurrent work. CMS was removed in Java 14. Start with the default, measure with GC logs, and change only for evidence.

Can you force garbage collection? What about finalize()?

No. System.gc() is only a request that the JVM may ignore, and calling it often triggers an expensive full GC. finalize() has no timing guarantee, is slow, and is deprecated for removal since Java 18. Release resources with try-with-resources (AutoCloseable), and use Cleaner as a safety net for native resources.

Can a Java program have memory leaks? Give examples and say how you would find one.

Yes, when unneeded objects stay reachable: static collections that only grow, caches without eviction, listeners never unregistered, ThreadLocal values in pooled threads, unclosed resources, and mutable keys in hash maps. To find one, watch the heap after GC, take heap dumps (jcmd <pid> GC.heap_dump or -XX:+HeapDumpOnOutOfMemoryError), open them in Eclipse MAT or VisualVM, and follow the path to GC roots from the largest retained objects.

What do strong, soft, weak and phantom references mean?

A strong reference is a normal variable and prevents collection. A SoftReference object is cleared only when memory is short, so it suits caches. A WeakReference is cleared at the next GC if no strong reference remains, as used by WeakHashMap. A PhantomReference is enqueued after the object is finalised and is used for cleanup actions; Cleaner builds on it.

Describe class loading and the parent delegation model.

A class is loaded lazily: loading (read bytes, create the class in Metaspace), linking (verify, prepare statics with defaults, resolve references) and initialization (run static initializers once). The loaders are bootstrap (core JDK), platform and application. A loader first delegates to its parent and only loads the class itself if the parent cannot. This prevents applications from replacing core classes like java.lang.String and avoids duplicate loading.

What is the difference between ClassNotFoundException and NoClassDefFoundError?

ClassNotFoundException is a checked exception thrown when code loads a class by name (Class.forName, loadClass) and it is not on the classpath. NoClassDefFoundError is an Error thrown when a class that was available at compile time is missing at runtime, or when its static initialization already failed. Typical fixes: add the dependency to the package, fix scopes, or find the earlier ExceptionInInitializerError.

What is the difference between == and equals()?

For primitives, == compares values. For objects, == compares references (are they the same object?), while equals() compares by meaning if the class overrides it; the default Object.equals is identical to ==. String, wrappers, BigDecimal and records override it. Use equals for content and == only for primitives, enums and identity checks.

Why must hashCode() be overridden when you override equals()?

The contract says equal objects must have equal hash codes. Hash collections use the hash code to choose a bucket before they call equals. If two equal objects hash differently, they go to different buckets, so a HashSet can hold "duplicates" and contains or HashMap.get cannot find an equal key. Use the same fields in both methods, via Objects.equals and Objects.hash, or a record.

What are the properties of a correct equals(), and instanceof vs getClass()?

Reflexive, symmetric, transitive, consistent and false for null. instanceof accepts subclasses and works well for final classes and records; getClass() requires exactly the same class and avoids symmetry problems when subclasses add significant state, but fails with runtime proxies such as Hibernate lazy proxies. Choose one on purpose and document it.

What are C1, C2 and escape analysis?

C1 and C2 are HotSpot's JIT compilers: C1 compiles quickly with light optimisation, C2 compiles hot code with deep optimisation (tiered compilation uses both). Escape analysis lets C2 prove that an object never leaves a method, so it can avoid heap allocation (scalar replacement) or remove locks (lock elision). It explains JVM warm-up and why micro-benchmarks need JMH.

Cheat sheet — JVM and memory

  • JVM parts class loader subsystem, runtime data areas, execution engine, JNI.
  • Per thread JVM stack (frames), PC register, native method stack.
  • Shared heap (objects, arrays, String pool, statics) and Metaspace (class metadata, native memory).
  • Metaspace replaced PermGen in Java 8; limit with -XX:MaxMetaspaceSize.
  • Stack frame local variables, operand stack, constant pool link; popped on return.
  • Reference vs object reference on stack (or in a field), object on heap; assignment copies the reference.
  • StackOverflowError too deep recursion; fix base case or loop; -Xss sets stack size.
  • OutOfMemoryError heap space, Metaspace, GC overhead limit, unable to create native thread.
  • GC roots stack locals, statics, active threads, JNI refs.
  • Generations Eden + S0/S1 (young), tenured (old); minor GC is cheap, full GC is expensive.
  • Generational hypothesis most objects die young.
  • Collectors Serial, Parallel (throughput), G1 (default), ZGC, Shenandoah (low pause); CMS removed in 14.
  • System.gc() only a hint; finalize() deprecated for removal; use try-with-resources and Cleaner.
  • References strong, SoftReference (cache), WeakReference (WeakHashMap), PhantomReference.
  • Leak causes static collections, no-eviction caches, listeners, ThreadLocal in pools, unclosed resources, mutable keys.
  • Find leaks -XX:+HeapDumpOnOutOfMemoryError, jcmd GC.heap_dump, Eclipse MAT, jmap -histo.
  • Flags -Xms -Xmx -Xss -XX:MaxRAMPercentage -Xlog:gc.
  • Tools jps, jcmd, jstack (deadlocks), jmap, jstat, JFR, VisualVM.
  • JIT interpreter → C1 → C2 (tiered); warm-up; escape analysis can remove allocations.
  • Class loading loading → linking (verify, prepare, resolve) → initialization.
  • Loaders bootstrap → platform → application; parent first.
  • Initialization triggers new, static method, non-constant static field, Class.forName, subclass.
  • CNFE vs NCDFE checked exception from by-name load vs error for a missing or failed class at runtime.
  • equals contract reflexive, symmetric, transitive, consistent, null → false.
  • hashCode contract equal objects ⇒ equal hash codes; stable while fields do not change.
  • Write both same fields, Objects.equals, Objects.hash; records do it for you; keys should be immutable.

Practice — JVM and memory

  1. Draw it (easy). For the Shop example in the stack-vs-heap article, change compute to also take a String and an int[]. Redraw the stack and heap at the deepest point. Done when each primitive, reference, object and array is in the right place.
  2. Recursion crash (easy). Write a recursive method without a base case, catch StackOverflowError, print the depth, then rerun with -Xss512k and -Xss4m. Done when you can explain the three depths you saw.
  3. Make an OutOfMemoryError (easy). Run the heap demo with -Xmx64m -XX:+HeapDumpOnOutOfMemoryError and find the .hprof file. Done when you have the dump file and the error message.
  4. Watch the GC (medium). Run a loop that creates many short-lived objects with -Xlog:gc and with -XX:+UseSerialGC, -XX:+UseParallelGC and -XX:+UseG1GC. Compare the number and length of pauses. Done when you can describe the difference in one paragraph.
  5. Plant and find a leak (medium). Write a service class with a static HashMap cache that grows on every call. Run it under load with -Xmx128m, watch it with jstat -gc or VisualVM, take a dump with jcmd, open it in Eclipse MAT, and find the map. Then fix it with a bounded cache. Done when the post-GC heap stays flat.
  6. Weak vs strong (medium). Reproduce the WeakReference, SoftReference and WeakHashMap demos. Then make the WeakHashMap value strongly refer to its key and observe that the entry never disappears. Done when you can explain why.
  7. Class loading experiments (medium). Print the class loader of String, java.sql.Connection and your own class. Create classes with static blocks and predict the output order for new Child(), for reading a static final int constant, and for Class.forName. Done when all predictions match.
  8. Break and fix a HashMap key (medium). Write the BadPoint class, show that a HashSet contains duplicates, then fix it with equals and hashCode. Add a mutable-key demo and a record version. Done when all four variants print what the article predicts.
  9. Contract test (harder). Write a small test helper assertEqualsContract(a, b, c) that checks reflexive, symmetric, transitive, consistent and null properties plus the hash code rule for three objects. Run it against a correct class, a class with only equals, and a subclass that adds a field with instanceof. Done when it catches both broken cases.
  10. Diagnose a crash (harder). Take any Spring Boot or plain Java app, start it with -Xmx64m, flood it with requests (a loop or a load tool), and write a short diagnosis: the error message, the area (heap, Metaspace, threads), the evidence from a heap dump or jstack, and the fix. Done when your note could be handed to a teammate.

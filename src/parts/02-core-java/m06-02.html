Race conditions and synchronized

A race condition happens when the result depends on how threads interleave; synchronized makes a block of code a critical section that only one thread at a time can enter, using the lock (monitor) of one chosen object.

A race condition is a bug where the outcome depends on the timing of threads. The most common form is check-then-act or read-modify-write on shared data without protection. The code that touches the shared data and must not be interleaved is called a critical section.

The roadmap exercise: two threads, one counter

Two threads each add 1 to a shared counter 1,000,000 times. The expected total is 2,000,000.

public class RaceCondition {
    static int counter = 0;

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 1_000_000; i++) {
                counter++;                 // read, add, write: NOT atomic
            }
        };
        Thread t1 = new Thread(task, "t1");
        Thread t2 = new Thread(task, "t2");
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Expected 2000000, got " + counter);
    }
}
Expected 2000000, got 1316742

Updates are lost whenever both threads read the same old value (the picture in the memory model article). The wrong answer is silent: no exception, no warning.

Fix 1: synchronized

public class SyncCounter {
    private int count = 0;

    public synchronized void increment() {   // lock = this
        count++;
    }

    public synchronized int get() {
        return count;
    }

    public static void main(String[] args) throws InterruptedException {
        SyncCounter c = new SyncCounter();
        Runnable task = () -> {
            for (int i = 0; i < 1_000_000; i++) {
                c.increment();
            }
        };
        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start(); t2.start();
        t1.join();  t2.join();
        System.out.println("Expected 2000000, got " + c.get());
    }
}
Expected 2000000, got 2000000

Fix 2: AtomicInteger

import java.util.concurrent.atomic.AtomicInteger;

public class AtomicCounter {
    public static void main(String[] args) throws InterruptedException {
        AtomicInteger counter = new AtomicInteger();
        Runnable task = () -> {
            for (int i = 0; i < 1_000_000; i++) {
                counter.incrementAndGet();   // one atomic operation, no lock
            }
        };
        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start(); t2.start();
        t1.join();  t2.join();
        System.out.println("Expected 2000000, got " + counter.get());
    }
}
Expected 2000000, got 2000000

Both are correct. AtomicInteger is simpler and faster for a single counter (details in the next article). synchronized is the general tool when several variables must change together.

How synchronized works: the monitor

Every Java object has a hidden intrinsic lock, also called its monitor. synchronized acquires that lock on entry and releases it on exit — even if an exception is thrown. While one thread holds the lock, any other thread that wants the same lock goes to the BLOCKED state and waits. Entering also gives a happens-before edge: the next thread to take the lock sees everything the previous holder wrote. So synchronized gives you both mutual exclusion (atomicity of the block) and visibility.

Two threads exclude each other only if they use the same lock object. A static synchronized method and an instance synchronized method use different locks (the class and the instance) and do not block each other. Two different instances of the same class have two different locks.

public class Account {
    private final Object lock = new Object();   // private: nobody else can lock on it
    private long balance;
    private int transactions;

    public void deposit(long amount) {
        validate(amount);                 // slow, thread-safe work outside the lock
        synchronized (lock) {             // keep the critical section small
            balance += amount;
            transactions++;               // both fields change together
        }
    }

    public long getBalance() {
        synchronized (lock) {             // reads need the same lock for visibility
            return balance;
        }
    }

    private void validate(long amount) {
        if (amount <= 0) throw new IllegalArgumentException("amount must be positive");
    }
}

Reentrancy

Intrinsic locks are reentrant: a thread that already holds a lock can enter another synchronized block on the same lock without blocking itself. The JVM keeps a hold count. Without this, a synchronized method calling another synchronized method of the same object would deadlock on itself.

class Printer {
    synchronized void printAll() {
        printOne();                       // same lock, same thread: allowed
    }
    synchronized void printOne() {
        System.out.println("printing by " + Thread.currentThread().getName());
    }
}

Keep critical sections small

While a thread is inside a lock, all others wait. Do only the shared-data work inside, and do slow things (network calls, file I/O, heavy computation, sleep) outside. Never call unknown code — a callback or overridable method — while holding a lock; it may take other locks and cause a deadlock.

Synchronized vs no synchronization at all

Wrong: check-then-act without a lock

if (!cache.containsKey(id)) {
    cache.put(id, load(id));   // two threads
}                              // may both load

Right: one atomic operation

cache.computeIfAbsent(id, this::load);
// cache is a ConcurrentHashMap

Rules for synchronized

  • Protect every access (read and write) to a shared variable with the same lock. A synchronized setter with an unsynchronized getter is still a bug.
  • Synchronize compound actions as a unit (check-then-act, read-modify-write, "update two fields together").
  • Constructors cannot be synchronized; the keyword is a compile error there.
  • synchronized cannot be put on fields or on a method in an interface.

Conventions

  • Prefer a private final lock object over synchronized(this) or a synchronized method: outside code can lock this and interfere with you.
  • Never lock on a String literal, a boxed Integer or a pooled/shared object: unrelated code may lock the same instance. Never lock on a value that changes (a non-final field).
  • Document which lock guards which field (Java Concurrency in Practice style: // guarded by lock).
  • Keep lock order consistent when taking more than one lock (see deadlock).

Edge cases

  • synchronized (null) throws NullPointerException.
  • If a synchronized block throws, the lock is still released.
  • Synchronization does not stop a thread from being interrupted or from being BLOCKED forever — there is no timeout. Use ReentrantLock.tryLock when you need one.
  • Locks are per object, so synchronized on a method protects instance data only per instance. For a shared static field you need a static lock.
  • Locking is not fair: the thread that waited longest is not guaranteed to get the lock next.

Mistake: locking on a different object each time

synchronized (new Object()) { … } locks a brand-new object that no other thread ever sees, so it protects nothing. Likewise synchronized (counter) where counter is an Integer that gets re-boxed on every counter++ locks a different object each time.

Real projects

Spring singletons (@Service, @Controller) are shared by all request threads. Avoid mutable instance fields in them; if you need one (a counter, a cache), make it a concurrent type or an atomic, rather than adding synchronized to every method. Heavy use of synchronized on hot paths causes lock contention: many threads in BLOCKED, low CPU, high latency.

Interview: "What does synchronized do? Which lock does a static synchronized method use?"

  • Mutual exclusion plus visibility, via the object's monitor. Release on exit even on exceptions.
  • Instance method → this; static method → the Class object; block → the object in parentheses.
  • Reentrant: the same thread can re-enter locks it holds.
  • Keep blocks small; do not lock on public or shared objects; same lock for every access.
  • Alternatives: atomics for one variable, concurrent collections, ReentrantLock for timeouts and fairness.

volatile and the atomic classes

volatile guarantees that every thread sees the latest write to a variable but does not make count++ atomic; atomic classes such as AtomicInteger make single-variable updates atomic without locks by using compare-and-set (CAS).

volatile: visibility and ordering, not atomicity

Marking a field volatile tells the JVM that reads and writes go to main memory in a way every thread can see. A write to a volatile variable happens-before every later read of it, and the compiler may not reorder surrounding code across it unsafely. It is a light-weight tool, but a narrow one.

Use case 1: a stop flag
public class StopFlag {
    private static volatile boolean running = true;   // fixes the visibility bug

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            long loops = 0;
            while (running) {
                loops++;
            }
            System.out.println("Worker stopped after looping");
        });
        worker.start();
        Thread.sleep(300);
        running = false;       // visible to the worker immediately
        worker.join();
    }
}
Worker stopped after looping

This works because one thread writes and the others only read. For stopping a thread, interrupt() is usually better (see interruption), since it also wakes a sleeping thread.

Why volatile does not fix count++
static volatile int counter = 0;
// two threads each run: for (int i = 0; i < 1_000_000; i++) counter++;
// Result: still less than 2,000,000
Expected 2000000, got 1543180

Each thread sees fresh values, but read–add–write is still three steps, and another thread can slip in between them. volatile fixes visibility only.

Use case 2: safe publication of an immutable snapshot

Swap a whole immutable object by writing one volatile reference. Readers always see either the old or the new complete object (a config reload is a typical case).

public class ConfigHolder {
    record Config(String region, int timeoutMs) { }

    private volatile Config current = new Config("ap-south-1", 3000);

    public Config get() { return current; }                  // lock-free read
    public void reload(Config fresh) { current = fresh; }    // one atomic reference write
}
Use case 3: double-checked locking needs volatile

A lazy singleton avoids locking on every call by checking twice. Without volatile, another thread can see a non-null reference to an object whose constructor has not finished, because the reference write may be reordered before the field writes.

public class Singleton {
    private static volatile Singleton instance;      // volatile is required

    private Singleton() { }

    public static Singleton getInstance() {
        if (instance == null) {                      // first check: no lock
            synchronized (Singleton.class) {
                if (instance == null) {              // second check: under the lock
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

Simpler alternatives: an enum singleton, or the initialization-on-demand holder idiom (a private static nested class that holds the instance, loaded lazily by the class loader). Prefer those, or let Spring manage the singleton.

Atomic classes and CAS

The package java.util.concurrent.atomic has AtomicInteger, AtomicLong, AtomicBoolean, AtomicReference<V>, array versions, and more. They are built on a CPU instruction called compare-and-swap (CAS): "set the value to new only if it is currently expected; tell me whether it worked." Code that uses CAS is lock-free: no thread is ever blocked; a thread whose CAS fails just retries.

import java.util.concurrent.atomic.*;

public class AtomicDemo {
    public static void main(String[] args) {
        AtomicInteger stock = new AtomicInteger(5);

        // Reserve one item safely: never goes below zero
        boolean reserved = false;
        while (true) {
            int current = stock.get();
            if (current == 0) break;                                  // sold out
            if (stock.compareAndSet(current, current - 1)) {          // CAS
                reserved = true;
                break;
            }
            // CAS failed: another thread changed stock; loop and try again
        }
        System.out.println("reserved=" + reserved + ", left=" + stock.get());

        AtomicLong visits = new AtomicLong();
        System.out.println(visits.incrementAndGet() + " " + visits.addAndGet(10));

        AtomicInteger maxSeen = new AtomicInteger(3);
        maxSeen.accumulateAndGet(9, Math::max);       // atomic "max so far"
        System.out.println(maxSeen.get());

        AtomicReference<String> status = new AtomicReference<>("PENDING");
        System.out.println(status.compareAndSet("PENDING", "PAID") + " "
                + status.compareAndSet("PENDING", "FAILED") + " " + status.get());
    }
}

LongAdder for high contention

With many threads hammering one AtomicLong, most CAS attempts fail and retry, wasting CPU. LongAdder (and LongAccumulator, DoubleAdder) spreads updates across several internal cells and adds them up when you read. It is much faster for write-heavy counters such as metrics and request counts. The trade-off: sum() is not an exact snapshot while updates are in flight, and you cannot do compare-and-set on it.

LongAdder hits = new LongAdder();
hits.increment();      // many threads, low contention cost
hits.add(5);
System.out.println(hits.sum());   // 6

The ABA problem (brief)

CAS only checks "is the value still equal to what I read?" If another thread changed A → B → A in between, CAS succeeds although things changed. For plain counters this is harmless. For linked structures it can corrupt data; AtomicStampedReference adds a version stamp to detect it.

Rule: atomic operations compose only within one variable

Two separate atomic calls are not atomic together. if (a.get() < 10) a.incrementAndGet(); has a gap between the check and the update. Use compareAndSet in a loop, updateAndGet, or a lock. Likewise, two atomics that must stay consistent with each other need a lock around both.

Edge cases

  • volatile on an array or object reference makes the reference volatile, not the elements or fields it points to.
  • AtomicReference.compareAndSet compares with == (reference identity), not equals(). For boxed numbers or strings that are not the same instance, CAS may fail unexpectedly.
  • The function passed to updateAndGet may be called several times under contention. Keep it pure.
  • A volatile long or double read/write is atomic; a plain one technically is not (in practice 64-bit JVMs do it).

Mistake: using volatile for a counter or a check-then-act

Reviewers see private volatile int count; count++; far too often. Use AtomicInteger or LongAdder.

Conventions

  • Reach for the highest-level tool first: concurrent collection, then atomic, then lock. Plain volatile is for flags and snapshot references.
  • Metrics counters: LongAdder (or Micrometer, which Spring Boot uses). Sequence numbers or IDs where you need the exact next value: AtomicLong.

Interview: "volatile vs synchronized vs AtomicInteger"

  • volatile: visibility + ordering for a single variable; no atomicity of read-modify-write; never blocks.
  • synchronized: mutual exclusion + visibility for any block; blocks other threads.
  • AtomicInteger: atomic read-modify-write on one value via CAS; lock-free; retries on contention.
  • Why does double-checked locking need volatile? Without it, publication can be reordered and a thread may see a half-constructed object.
  • High contention counters: LongAdder.

wait/notify, BlockingQueue and explicit locks

wait() and notify() let threads hand signals to each other inside synchronized code but are low-level and error-prone, so modern code uses BlockingQueue for producer-consumer and ReentrantLock, ReadWriteLock and Condition when synchronized is not flexible enough.

wait, notify, notifyAll (legacy, but asked in interviews)

Sometimes a thread must pause until a condition becomes true — a queue gets an item, a payment is confirmed. The old way uses three methods of Object:

  • wait() — release the monitor and sleep until another thread notifies (state WAITING).
  • notify() — wake one waiting thread of this monitor.
  • notifyAll() — wake all waiting threads (safer default).

Rules: you must hold the object's lock (be inside synchronized on that same object) when you call them, otherwise you get IllegalMonitorStateException. Always call wait() inside a while loop that re-checks the condition, because of spurious wake-ups (the thread may wake without any notify) and because another thread may have consumed the item first.

import java.util.LinkedList;
import java.util.Queue;

public class SimpleBuffer {
    private final Queue<Integer> queue = new LinkedList<>();
    private final int capacity = 2;

    public synchronized void put(int item) throws InterruptedException {
        while (queue.size() == capacity) {   // while, never if
            wait();                          // releases the lock while waiting
        }
        queue.add(item);
        notifyAll();                         // wake consumers waiting for items
    }

    public synchronized int take() throws InterruptedException {
        while (queue.isEmpty()) {
            wait();
        }
        int item = queue.remove();
        notifyAll();                         // wake producers waiting for space
        return item;
    }
}

This works, but note how easy it is to get wrong: wrong lock, if instead of while, missed notification, notify waking the wrong kind of thread. That is why you rarely write it by hand.

BlockingQueue: the modern producer–consumer

A BlockingQueue is a thread-safe queue where put() waits if the queue is full and take() waits if it is empty. All the wait/notify logic is inside. A producer adds work; a consumer processes it. This decouples the two speeds and gives you back-pressure (a full bounded queue slows producers down).

import java.util.concurrent.*;

public class ProducerConsumer {
    private static final int POISON = -1;   // signal "no more work"

    public static void main(String[] args) throws InterruptedException {
        BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(3);   // bounded

        Thread producer = new Thread(() -> {
            try {
                for (int orderId = 1; orderId <= 5; orderId++) {
                    queue.put(orderId);              // waits if the queue is full
                    System.out.println("Produced order " + orderId);
                }
                queue.put(POISON);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "producer");

        Thread consumer = new Thread(() -> {
            try {
                while (true) {
                    int orderId = queue.take();      // waits if the queue is empty
                    if (orderId == POISON) break;
                    System.out.println("  Processed order " + orderId);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "consumer");

        producer.start();
        consumer.start();
        producer.join();
        consumer.join();
    }
}

ReentrantLock

java.util.concurrent.locks.ReentrantLock is an explicit lock object with the same reentrant mutual exclusion as synchronized, plus features synchronized lacks: try to lock without waiting, lock with a timeout, interruptible waiting, optional fairness, and multiple conditions. The price: you must unlock manually, always in finally.

import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class Wallet {
    private final ReentrantLock lock = new ReentrantLock();   // fair=false by default
    private long balance;

    public void deposit(long amount) {
        lock.lock();
        try {
            balance += amount;
        } finally {
            lock.unlock();                  // runs even if an exception is thrown
        }
    }

    public boolean tryDeposit(long amount) throws InterruptedException {
        if (lock.tryLock(200, TimeUnit.MILLISECONDS)) {   // give up after 200 ms
            try {
                balance += amount;
                return true;
            } finally {
                lock.unlock();
            }
        }
        return false;                       // could not get the lock in time
    }
}

Use synchronized by default; reach for ReentrantLock only for the extra features. A fair lock gives the lock to the longest-waiting thread; this prevents starvation but lowers throughput. Calling unlock() when you do not hold the lock throws IllegalMonitorStateException.

ReadWriteLock

Many reads, few writes? ReentrantReadWriteLock lets any number of readers hold the read lock at once, but a writer needs the write lock exclusively.

import java.util.*;
import java.util.concurrent.locks.*;

public class PriceCache {
    private final ReadWriteLock rw = new ReentrantReadWriteLock();
    private final Map<String, Long> prices = new HashMap<>();

    public Long get(String sku) {
        rw.readLock().lock();                 // many readers at the same time
        try { return prices.get(sku); }
        finally { rw.readLock().unlock(); }
    }

    public void put(String sku, long price) {
        rw.writeLock().lock();                // exclusive
        try { prices.put(sku, price); }
        finally { rw.writeLock().unlock(); }
    }
}

A thread holding the read lock cannot upgrade to the write lock (it would deadlock); it can downgrade (take the read lock before releasing the write lock). For most cases a ConcurrentHashMap is simpler. Java 8 also added StampedLock with optimistic reads — an advanced tool; know it exists.

Condition

A Condition (from lock.newCondition()) is the wait/notify of explicit locks, but a lock can have several, e.g. notFull and notEmpty. Methods: await(), signal(), signalAll(). The same rules apply: hold the lock, and wait in a while loop.

class BoundedBuffer<T> {
    private final Object[] items = new Object[10];
    private int putIdx, takeIdx, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    void put(T x) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) notFull.await();   // wait for space
            items[putIdx] = x;
            putIdx = (putIdx + 1) % items.length;
            count++;
            notEmpty.signal();                               // wake one consumer
        } finally {
            lock.unlock();
        }
    }
    // take() is the mirror image: await notEmpty, then signal notFull
}

Rules

  • wait/notify require holding the monitor, or IllegalMonitorStateException.
  • Always wait()/await() in a while loop that re-checks the condition.
  • lock.lock() goes before the try; unlock() goes in finally.
  • Lock and unlock the same number of times (locks are reentrant with a hold count).

Mistake: lock() inside try, or no finally

If lock() is inside the try and fails, finally calls unlock() on a lock you do not hold. If you skip finally, one exception leaves the lock held forever and every other thread hangs.

Edge cases

  • notify() before any thread is waiting is lost — notifications are not remembered. That is why you check the condition in a loop first.
  • notify() can wake the wrong type of thread (a producer waking a producer) and leave the system stuck; notifyAll() avoids this.
  • BlockingQueue does not allow null elements (NullPointerException).
  • Starvation: with an unfair lock, a thread can wait very long under heavy contention.

Interview: "wait vs sleep", "How do you implement producer–consumer?"

  • wait() belongs to Object, needs the monitor, releases it, wakes on notify. sleep() belongs to Thread, holds locks, wakes on time.
  • Producer–consumer: best answer is BlockingQueue (put/take); second answer is wait/notify with a while loop.
  • Why a while loop? Spurious wake-ups and stolen conditions.
  • ReentrantLock vs synchronized: tryLock, timeout, fairness, multiple conditions; must unlock in finally.

Nested classes: static nested, inner, local and anonymous

A nested class is a class declared inside another class; there are four kinds (static nested, inner, local, anonymous), and the main difference is whether the nested object carries a hidden reference to an outer object.

Normally each class sits in its own file. When a small class exists only to serve one other class, you can declare it inside that class. This keeps related code together, hides helpers from the rest of the program (encapsulation) and gives the helper access to the outer class's private members. The class that holds the others is the outer (enclosing) class.

Static nested class

A static nested class behaves like a top-level class that happens to live inside another one, just for grouping. It has no link to an outer object. It can reach the outer class's static members, including private ones. You create it with new Outer.Nested(). It may have any access modifier, so a private static nested class is invisible outside.

public class Pizza {
    private final String size;
    private final boolean cheese;

    private Pizza(Builder b) {                         // can read the builder's private fields
        this.size = b.size;
        this.cheese = b.cheese;
    }

    public static class Builder {                     // static nested class
        private String size = "medium";
        private boolean cheese;

        public Builder size(String s) { this.size = s; return this; }
        public Builder cheese(boolean c) { this.cheese = c; return this; }
        public Pizza build() { return new Pizza(this); }
    }

    @Override public String toString() { return size + " pizza, cheese=" + cheese; }

    public static void main(String[] args) {
        Pizza p = new Pizza.Builder().size("large").cheese(true).build();
        System.out.println(p);
    }
}
large pizza, cheese=true

The JDK uses this style often: Map.Entry, AbstractMap.SimpleEntry, HttpRequest.Builder.

Inner (member) class

An inner class is a non-static member. Each inner object is tied to one outer object and can use all its fields and methods, even private ones, directly. The compiler stores a hidden reference to the outer instance. Inside the inner class, this is the inner object and Outer.this is the outer one.

import java.util.Iterator;
import java.util.NoSuchElementException;

public class Playlist implements Iterable<String> {
    private final String[] songs = {"Kun Faya Kun", "Tum Hi Ho", "Kesariya"};
    private final String owner = "Asha";

    @Override
    public Iterator<String> iterator() {
        return new SongIterator();                    // created inside an instance method
    }

    private class SongIterator implements Iterator<String> {   // inner class
        private int index = 0;

        @Override public boolean hasNext() { return index < songs.length; }   // outer field

        @Override public String next() {
            if (!hasNext()) throw new NoSuchElementException();
            return songs[index++] + " (" + Playlist.this.owner + ")";       // Outer.this
        }
    }

    public static void main(String[] args) {
        for (String s : new Playlist()) {
            System.out.println(s);
        }
        Playlist p = new Playlist();
        Playlist.SongIterator it = p.new SongIterator();   // outer.new Inner() from outside
        System.out.println(it.next());
    }
}

Tum Hi Ho (Asha)
Kesariya (Asha)
Kun Faya Kun (Asha)

From outside you need an outer object first: outer.new Inner(). Plain new Inner() works only inside an instance method of the outer class. This is how ArrayList implements its iterator.

Inner classes hold on to the outer object

Because an inner object keeps a reference to its outer object, it keeps that outer object alive for the garbage collector. If a long-living inner or anonymous object (a listener, a cache entry) is registered somewhere, it can leak a large outer object. If the inner class does not need the outer instance, make it static. IDEs warn about this, and it is the main reason to prefer static nested classes by default. Also, an inner class cannot declare static members in older Java; since Java 16 it can.

Local classes

A local class is declared in a method body, like a local variable. It is visible only in that block, and it can use the method's parameters and local variables if they are final or effectively final (final). Since Java 16, local records, enums and interfaces are allowed too; they are useful for small data holders inside a stream pipeline.

static void printTotals(double[] prices) {
    final double gst = 0.18;
    class Line {                                       // local class
        final double price;
        Line(double price) { this.price = price; }
        double withTax() { return price * (1 + gst); } // captures the effectively final gst
    }
    for (double p : prices) {
        System.out.printf("%.2f%n", new Line(p).withTax());
    }
}
// printTotals(new double[]{100, 250}) prints 118.00 and 295.00

Anonymous classes and lambdas

An anonymous class declares and instantiates a class in one expression: it extends a class or implements an interface, has no name and exists only here. It is useful for a one-off implementation, with state or several methods.

import java.util.*;

public class AnonDemo {
    public static void main(String[] args) {
        List<String> names = new ArrayList<>(List.of("Ravi", "Asha", "Meera"));

        names.sort(new Comparator<String>() {           // anonymous class
            @Override public int compare(String a, String b) {
                return a.length() - b.length();
            }
        });
        System.out.println(names);

        names.sort((a, b) -> a.compareTo(b));              // same idea as a lambda
        System.out.println(names);

        Runnable r = new Runnable() {
            private int runs = 0;                         // own state: a lambda cannot do this
            @Override public void run() { System.out.println("run " + (++runs)); }
        };
        r.run();
        r.run();
    }
}
[Ravi, Asha, Meera]
[Asha, Meera, Ravi]
run 1
run 2

Since Java 8, a lambda replaces an anonymous class when the type is a functional interface (one abstract method). Prefer the lambda; it is shorter (Module 5). The two are not identical:

Can implementAny interface, or extend a classOnly a functional interface

Access rules in short

  • A nested class can access all members of its outer class, including private ones, and the outer class can access the nested class's private members.
  • A static nested class sees only the outer class's static members directly; for instance members it needs an outer object.
  • Local and anonymous classes can capture only final or effectively final local variables.
  • An anonymous class has no constructor of its own; arguments go to the superclass constructor: new Shape("x") { … }. It cannot be static or abstract.
  • The compiled names are Outer$Nested.class, Outer$1.class and Outer$1Local.class.

Conventions: which kind to choose

  • Start with a static nested class. Use inner only when each instance really needs the outer object.
  • If the nested class is big or used by other classes, move it to its own file.
  • Use a lambda for functional interfaces, an anonymous class only when you need state or a non-functional type, and a local class or local record for a tiny helper inside one method.

Mistake: instantiating an inner class from a static method

Wrong

public static void main(String[] a) {
    Inner i = new Inner();     // error: non-static variable this cannot be referenced
                               // from a static context
}

Right: make it static, or create an outer object

static class Inner { }                    // option 1
// option 2: Outer o = new Outer(); Outer.Inner i = o.new Inner();

Interview: nested class questions

  • Static nested vs inner? Inner holds a reference to an outer instance and can use its instance members; static nested does not.
  • Why can a local or anonymous class use only final variables? It captures a copy of the value; see effectively final.
  • Anonymous class vs lambda? Show the table: this, state, class file, functional-interface limit.
  • Can an inner class be private? Yes; a top-level class cannot (access modifiers).

Packages and imports

A package is a named folder of related classes that prevents name clashes and controls package-private access; you declare it with package, name it with your reversed domain in lowercase, and bring other packages' classes into view with import.

Imagine a project with two classes called Date, one for the database and one for the UI. Without a way to separate them they would clash. A package is a namespace: java.util.Date and java.sql.Date are different classes because their packages differ. Packages also group classes by purpose, and they are the unit for the package-private access level (access modifiers).

Declaring a package and the folder rule

The first statement of a file (before imports and the class) is the package declaration. The folder structure must match it. For a Maven or Gradle project, source files live under src/main/java.

 src/main/java
 └── com
     └── acme
         └── shop
             ├── model
             │   └── Order.java          package com.acme.shop.model;
             ├── service
             │   └── OrderService.java   package com.acme.shop.service;
             └── ShopApp.java            package com.acme.shop;

package com.acme.shop.service;               // must be the first statement

import com.acme.shop.model.Order;            // single-type import
import java.util.List;
import java.util.ArrayList;

public class OrderService {
    private final List<Order> orders = new ArrayList<>();

    public void place(Order order) {
        orders.add(order);
        System.out.println("Placed " + order.id());
    }
}

The fully qualified name of this class is com.acme.shop.service.OrderService. You can always use it without an import: java.util.List<String> names = new java.util.ArrayList<>();. An import is only a shortcut so that you can write the short name. It does not copy or load anything, and unused imports cost nothing at run time.

To compile and run by hand from the project root:

$ javac -d out src/main/java/com/acme/shop/model/*.java src/main/java/com/acme/shop/service/*.java src/main/java/com/acme/shop/ShopApp.java
$ java -cp out com.acme.shop.ShopApp

The class is run by its fully qualified name; the -d out option creates the matching folders for you. Build tools do this automatically.

Naming conventions

  • All lowercase, no underscores or spaces: com.acme.shop.service.
  • Start with your organisation's domain name reversed: the company acme.com becomes com.acme. Add the project and then layers or features. Open source: org.springframework, com.fasterxml.jackson.
  • If you have no domain, use something unique such as io.github.yourname.
  • Do not start with java. or javax.; those belong to the JDK.
  • Layer-based (controller, service, repository) or feature-based (order, payment) layouts both work. Larger apps tend to prefer feature packages, because a feature's classes can stay package-private and change together.

Things you do not need to import: everything in java.lang (String, Math, Integer, System, Object, Exception, Thread…), and classes in the same package. Classes in other packages always need an import or the full name, even if the folders are next to each other.

Name clashes

If two imported packages contain the same simple name, the compiler cannot decide. With two single-type imports of the same name it is an error, with two wildcard imports it is an error only when you use the name ("reference to Date is ambiguous"). Import one and write the other fully qualified:

import java.util.Date;

public class Clash {
    java.util.Date utilDate = new Date();           // from the import
    java.sql.Date sqlDate = new java.sql.Date(0L);  // full name for the other one
}

A single-type import beats a wildcard import, and a class declared in the same package beats a wildcard import. A class in your own file shadows a same-named import (the compiler rejects a conflicting single-type import).

The default package

A file with no package line belongs to the unnamed default package. It is fine for a 20-line experiment. Do not use it in real projects: classes in named packages cannot import classes from the default package, and Spring Boot's component scan will not work properly. Always declare a package.

Packages, access and modules

  • Package-private (no modifier) members are visible to every class in the same package, and nowhere else. Sub-packages are not "inside": com.acme.shop and com.acme.shop.model are separate packages.
  • Package names are a naming scheme; there is no "parent can see child" rule.
  • Java 9 added modules (module-info.java) that group packages and decide which are exported. Most application projects, including typical Spring Boot ones, do not use them; libraries and the JDK itself do.

Version note: module imports in Java 25

Java 25 finalises module import declarations: import module java.base; imports every public class of the packages that module exports. It is meant for scripts and teaching; in team code, explicit single-type imports are still the style.

Rules

  • The package statement comes first; imports come next; then the type declarations. One public top-level class per file, named like the file.
  • A wildcard import does not include subpackages: import java.util.*; does not give you java.util.function.Function.
  • Static imports import members, not classes; a regular import does not make static members available by simple name.
  • Folder structure must match the package for the usual tools; otherwise: class not found errors at run time.

Mistakes to avoid

  • Running java OrderService for a packaged class. You need the full name and a class path: java -cp out com.acme.shop.service.OrderService (the error is Could not find or load main class).
  • Naming a package after a class or using capitals (com.acme.Shop); it confuses readers and file systems.
  • Wildcard imports of two big packages, then an ambiguous List (java.util.List vs java.awt.List).
  • Circular dependencies between packages (model imports service and the reverse). Keep the dependency direction one way.

In a Spring Boot project

The main class sits in the root package (com.acme.shop.ShopApplication), and @SpringBootApplication scans that package and everything below it. A controller placed in a sibling package outside it is silently not found. Your IDE organises imports for you (Ctrl+Alt+O in IntelliJ) and Maven/Gradle compile the folders as packages.

Interview: package questions

  • Why packages? Avoid name clashes, organise code, control access with package-private.
  • Does import java.util.* import subpackages? No.
  • Which package is imported automatically? java.lang.
  • Is importing a lot of classes slower? No; imports are resolved at compile time and leave no run-time cost.
  • What is a static import? It lets you use static members without the class name; use it sparingly.

Enums: type-safe constants with behaviour

An enum is a class with a fixed set of named instances; it replaces int and String constants with a type the compiler checks, and each constant can carry fields, methods and its own behaviour.

Without enums, people wrote static final int PENDING = 0, SHIPPED = 1;. Nothing stops setStatus(42) or mixing an order status with a payment status. An enum (short for enumeration) fixes this: OrderStatus is its own type with exactly the values you list, and the compiler rejects anything else. Use an enum whenever a value comes from a small, known, fixed set: days, order states, roles, payment modes, HTTP methods.

The basics

enum OrderStatus { PLACED, PACKED, SHIPPED, DELIVERED, CANCELLED }

public class EnumBasics {
    public static void main(String[] args) {
        OrderStatus s = OrderStatus.SHIPPED;
        System.out.println(s);                         // SHIPPED (name())
        System.out.println(s.ordinal());               // 2: position in the declaration
        System.out.println(s == OrderStatus.SHIPPED);  // true: == is the right comparison
        System.out.println(s.compareTo(OrderStatus.PLACED));  // 2: ordinal difference

        for (OrderStatus x : OrderStatus.values()) {   // all constants, in order
            System.out.print(x + " ");
        }
        System.out.println();

        OrderStatus y = OrderStatus.valueOf("PACKED"); // from a String; exact, case-sensitive
        System.out.println(y);

        String msg = switch (s) {                      // switch expression, no default needed
            case PLACED, PACKED -> "We are preparing it";
            case SHIPPED        -> "On the way";
            case DELIVERED      -> "Done";
            case CANCELLED      -> "Cancelled";
        };
        System.out.println(msg);
        OrderStatus.valueOf("shipped");                // throws IllegalArgumentException
    }
}

The compiler turns the enum into a class that extends java.lang.Enum. Each constant is a public static final instance, created once when the enum class loads. Because there is exactly one instance of each constant, == is correct and fast (and equals is the same thing). When a switch expression covers every constant, the compiler checks that none is missing, so adding a new constant later makes the build fail where you forgot to handle it. That is a good reason to avoid a default branch there.

Enums with fields, constructors and methods

An enum is a full class. Put data after the constants (note the semicolon), write a constructor and add methods. The constructor is always private (implicitly), because only the enum itself creates its constants.

import java.util.*;

enum PaymentMode {
    UPI("UPI", 0.0),                       // calls the constructor
    CREDIT_CARD("Credit card", 2.0),
    NET_BANKING("Net banking", 1.5),
    COD("Cash on delivery", 0.0);

    private final String label;
    private final double feePercent;

    PaymentMode(String label, double feePercent) {   // implicitly private
        this.label = label;
        this.feePercent = feePercent;
    }

    public String label() { return label; }

    public double fee(double amount) { return amount * feePercent / 100; }

    private static final Map<String, PaymentMode> BY_LABEL = new HashMap<>();
    static {
        for (PaymentMode m : values()) BY_LABEL.put(m.label, m);
    }
    public static Optional<PaymentMode> fromLabel(String label) {   // safe lookup
        return Optional.ofNullable(BY_LABEL.get(label));
    }

    public static void main(String[] args) {
        for (PaymentMode m : values()) {
            System.out.printf("%-12s fee on 1000 = %.1f%n", m.label(), m.fee(1000));
        }
        System.out.println(fromLabel("Net banking").orElseThrow());
        System.out.println(fromLabel("Bitcoin").isPresent());
    }
}

Fields of an enum should be final. A mutable enum is shared global state and a bug waiting to happen. The static lookup map is the standard answer to "convert a code or label from the database or a request to an enum without an exception".

Per-constant behaviour

Each constant can have its own body that overrides a method, or supply a missing abstract method. This replaces long if/switch chains (a form of the Strategy pattern, polymorphism).

enum Operation {
    ADD("+") { @Override double apply(double a, double b) { return a + b; } },
    SUBTRACT("-") { @Override double apply(double a, double b) { return a - b; } },
    MULTIPLY("*") { @Override double apply(double a, double b) { return a * b; } };

    private final String symbol;
    Operation(String symbol) { this.symbol = symbol; }

    abstract double apply(double a, double b);        // every constant must implement it

    @Override public String toString() { return symbol; }

    public static void main(String[] args) {
        for (Operation op : values()) {
            System.out.println("6 " + op + " 3 = " + op.apply(6, 3));
        }
    }
}
6 + 3 = 9.0
6 - 3 = 3.0
6 * 3 = 18.0

Enums can also implement interfaces (enum Plan implements Billable), which lets them plug into a type hierarchy. They cannot extend a class, because they already extend Enum, and they cannot be extended.

EnumMap and EnumSet

For enum keys, use EnumMap and EnumSet. They store data in a compact array or bit vector indexed by ordinal. They are faster and smaller than HashMap and HashSet, and they iterate in declaration order (more in Module 4).

import java.util.*;

enum Day { MON, TUE, WED, THU, FRI, SAT, SUN }

public class EnumCollections {
    public static void main(String[] args) {
        Map<Day, Integer> orders = new EnumMap<>(Day.class);
        orders.put(Day.WED, 40);
        orders.put(Day.MON, 25);
        System.out.println(orders);                       // ordered by declaration, not insertion

        Set<Day> weekend = EnumSet.of(Day.SAT, Day.SUN);
        Set<Day> weekdays = EnumSet.complementOf(weekend);
        System.out.println(weekdays);
        System.out.println(EnumSet.range(Day.TUE, Day.THU));
    }
}

[MON, TUE, WED, THU, FRI]
[TUE, WED, THU]

Enum singleton

A one-constant enum is the simplest safe singleton: the JVM guarantees one instance, it is thread-safe and it survives serialization and reflection attacks. See the Singleton pattern in Design patterns.

enum AppConfig {
    INSTANCE;
    private final String env = System.getenv().getOrDefault("APP_ENV", "dev");
    public String env() { return env; }
}
// usage: AppConfig.INSTANCE.env()

Rules

  • An enum constructor is private; calling new on an enum is a compile error ("enum classes may not be instantiated").
  • Constants come first in the body, separated by commas; a semicolon is needed only if members follow.
  • Enums cannot extend a class or be extended, but can implement interfaces. They are implicitly final unless a constant has a body (then implicitly sealed).
  • In a switch over an enum, case labels use the bare constant name (case SHIPPED), not OrderStatus.SHIPPED in old-style switches.

Edge cases and runtime exceptions

  • valueOf("shipped") throws IllegalArgumentException: No enum constant … (case matters). Catch it or use a lookup map when the input comes from outside.
  • switch on a null enum throws NullPointerException.
  • A static field of the enum cannot be used from its constructor (the constants are built first); use a static block after the constants, as the lookup map above does.
  • Enum constants are serialized by name, so renaming a constant breaks old data.

Mistake: persisting ordinal()

Wrong: stores the position

@Enumerated(EnumType.ORDINAL)      // JPA default! stores 0, 1, 2...
private OrderStatus status;
// Later someone inserts a constant in the middle: every old row now means something else.

Right: store the name

@Enumerated(EnumType.STRING)       // stores "SHIPPED"
private OrderStatus status;

Never use ordinal() in your own logic either (no "status + 1"). If you need a number in a database or an API, give the enum a field such as code and a lookup method.

Conventions

  • Enum type names are singular nouns in PascalCase (OrderStatus); constants in UPPER_SNAKE_CASE.
  • Use == for comparison. Put behaviour in the enum rather than scattering switch statements across the code base.
  • For a fixed set that has data rather than behaviour and is read from a database, weigh an enum (compile-time safe, needs a deploy to change) against a lookup table (changes at run time).

Interview: enum questions

  • Why enums over constants? Type safety, names in output, can hold data and behaviour, works in switch, EnumMap.
  • Can an enum have a constructor? Be public? Yes; always private, implicitly.
  • Can an enum extend a class or implement an interface? Not extend; implement, yes.
  • How do you get an enum from a String? valueOf, with IllegalArgumentException on failure.
  • How is an enum singleton safe? JVM-guaranteed single instance, serialization-safe, reflection cannot create more.

Map: the API, HashMap vs LinkedHashMap vs TreeMap

A Map stores unique keys with one value each; HashMap is the fast default, LinkedHashMap remembers order, TreeMap keeps keys sorted, and the Java 8 methods merge, computeIfAbsent and getOrDefault replace most if-else code.

A Map<K, V> maps a key to a value. Keys are unique (decided by equals, or by the comparator in a TreeMap); values can repeat. Putting a key that already exists replaces its value. Think of a phone book, a Redis cache, or "order id → order". The three everyday implementations differ only in order and speed:

import java.util.*;

public class MapMethods {
    public static void main(String[] args) {
        Map<String, Integer> stock = new TreeMap<>();   // TreeMap: stable printing

        stock.put("pen", 10);
        System.out.println(stock.putIfAbsent("pen", 99));    // 10, value unchanged
        System.out.println(stock.putIfAbsent("book", 5));    // null, inserted
        System.out.println(stock);
        System.out.println(stock.getOrDefault("bag", 0));    // 0, "bag" is NOT added

        stock.merge("pen", 5, Integer::sum);                 // 10 + 5
        stock.computeIfAbsent("cap", k -> 3);                // absent → 3
        stock.computeIfPresent("book", (k, v) -> v - 1);     // 5 → 4
        stock.compute("pen", (k, v) -> v == null ? 1 : v + 1);   // 15 → 16
        System.out.println(stock);

        stock.remove("cap");
        stock.replaceAll((k, v) -> v * 2);
        System.out.println(stock);

        for (Map.Entry<String, Integer> e : stock.entrySet()) {   // best way to loop
            System.out.println(e.getKey() + " = " + e.getValue());
        }
        stock.forEach((k, v) -> System.out.println(k + " -> " + v));
    }
}

Word frequency — the classic example

Counting is the most common map task. There are three styles; the second is the idiom to learn.

import java.util.*;
import java.util.stream.*;

public class WordCount {
    public static void main(String[] args) {
        String text = "to be or not to be that is the question";
        String[] words = text.split(" ");

        // 1. Classic: getOrDefault
        Map<String, Integer> counts1 = new TreeMap<>();
        for (String w : words) {
            counts1.put(w, counts1.getOrDefault(w, 0) + 1);
        }

        // 2. merge: shortest and safe — "if absent put 1, else add 1"
        Map<String, Integer> counts2 = new TreeMap<>();
        for (String w : words) {
            counts2.merge(w, 1, Integer::sum);
        }

        // 3. Streams
        Map<String, Long> counts3 = Arrays.stream(words)
                .collect(Collectors.groupingBy(w -> w, TreeMap::new,
                        Collectors.counting()));

        System.out.println(counts1);
        System.out.println(counts2.equals(counts1));
        System.out.println(counts3);
    }
}

Grouping with computeIfAbsent

To build a "multi-map" (one key → a list of values), computeIfAbsent creates the list the first time and returns it, so you can add in the same line:

record Employee(String name, String city) {}

List<Employee> staff = List.of(new Employee("Ravi", "Mumbai"),
        new Employee("Asha", "Pune"), new Employee("Meera", "Mumbai"));

Map<String, List<String>> byCity = new TreeMap<>();
for (Employee e : staff) {
    byCity.computeIfAbsent(e.city(), city -> new ArrayList<>()).add(e.name());
}
System.out.println(byCity);          // {Mumbai=[Ravi, Meera], Pune=[Asha]}

Sorting a map by value

A map has no order to sort, so you stream its entries, sort them, and collect into an order-preserving map such as LinkedHashMap.

Map<String, Integer> marks = Map.of("Asha", 82, "Ravi", 91, "Meera", 75);

List<Map.Entry<String, Integer>> ranked = marks.entrySet().stream()
        .sorted(Map.Entry.<String, Integer>comparingByValue().reversed())
        .toList();
System.out.println(ranked);          // [Ravi=91, Asha=82, Meera=75]

Immutable maps

Map.of(k1, v1, k2, v2, …) (up to 10 pairs), Map.ofEntries(Map.entry(…), …) and Map.copyOf(map) create immutable maps. They reject null keys and values, throw IllegalArgumentException for duplicate keys, and their iteration order is deliberately unspecified and can differ from one JVM run to the next. Never write a test that depends on it.

LinkedHashMap: order, and an LRU cache

LinkedHashMap is a HashMap in which every entry also sits in a doubly linked list. Lookups are as fast as HashMap, and iteration follows the list. The list order is insertion order by default (re-inserting an existing key does not move it). With the constructor new LinkedHashMap<>(16, 0.75f, true) the order becomes access order: every get or put of a key moves that entry to the end, so the first entry is always the least recently used.

The method protected boolean removeEldestEntry(Map.Entry<K, V> eldest) is called after each insert. If you return true, the eldest (first) entry is removed. Together these give an LRU cache (least recently used: when full, throw away the entry unused for the longest time) in a dozen lines:

import java.util.*;

public class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    public LruCache(int capacity) {
        super(16, 0.75f, true);              // true = access order
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;              // evict when over capacity
    }

    public static void main(String[] args) {
        LruCache<String, Integer> cache = new LruCache<>(3);
        cache.put("a", 1);
        cache.put("b", 2);
        cache.put("c", 3);
        cache.get("a");                      // "a" becomes most recently used
        cache.put("d", 4);                   // size 4 > 3 → evict eldest, which is "b"
        System.out.println(cache);
    }
}
{c=3, a=1, d=4}

Remember two things. In access-order mode even get changes the structure, so calling get inside a loop over the same map throws ConcurrentModificationException. And the class is not thread-safe; wrap it with Collections.synchronizedMap or use a cache library for shared use. "Design an LRU cache" is a popular interview question; the other answer is your own hash map plus a doubly linked list (see the DSA notes).

Rule: keys are unique and a Map is not a Collection

A second put with an equal key replaces the value. Map does not extend Collection, so you cannot use it in a for-each loop directly or call stream() on it; use entrySet(), keySet() or values().

Exceptions and edge cases

  • NullPointerException — unboxing a missing value: int n = map.get("x"); where the key is absent. Use getOrDefault.
  • NullPointerException — null key in TreeMap / Map.of / ConcurrentHashMap.
  • UnsupportedOperationException — put on Map.of(…), Map.copyOf or Collections.unmodifiableMap.
  • ConcurrentModificationException — map.put or map.remove inside a loop over its own views. Use entrySet().removeIf(…) or map.values().removeIf(…).
  • computeIfAbsent with a function that modifies the same map throws ConcurrentModificationException in HashMap (this is why recursive memoisation with it is risky).
  • putIfAbsent and computeIfAbsent treat a key mapped to null as absent.

Conventions

  • Name maps by what they hold: customerById, ordersByStatus (valueByKey reads naturally: customerById.get(id)).
  • Use merge for counting and summing, computeIfAbsent for grouping.
  • Use an EnumMap when keys are enum constants: it is a compact array internally and iterates in enum order. WeakHashMap and IdentityHashMap exist for special cases.

Mistake: check-then-act on a shared map

if (!map.containsKey(k)) map.put(k, v); is two steps. With a ConcurrentHashMap and several threads, another thread can insert between them. Use the single atomic call putIfAbsent or computeIfAbsent.

Interview: "HashMap vs LinkedHashMap vs TreeMap"

  • HashMap: no order, O(1), one null key. LinkedHashMap: insertion (or access) order, O(1), slightly more memory. TreeMap: sorted keys, O(log n), no null key, has NavigableMap methods.
  • "Build an LRU cache" → LinkedHashMap with access order and removeEldestEntry.
  • "Count word frequency" → map.merge(word, 1, Integer::sum).

TreeMap and NavigableMap: sorted keys and range queries

TreeMap keeps its keys sorted in a red-black tree, so every operation costs O(log n) but you gain first/last, floor/ceiling and range views that a HashMap cannot do.

A TreeMap stores entries in a red-black tree: a self-balancing binary search tree in which the left child is smaller and the right child is larger. The tree rebalances itself on insert and delete, so its height stays about log₂(n). Searching 1,000,000 keys takes about 20 comparisons. Keys are sorted by their natural order (Comparable) or by a Comparator you pass to the constructor.

The NavigableMap methods

TreeMap implements NavigableMap (which extends SortedMap). These methods answer questions like "what is the nearest key to this value?" in O(log n).

import java.util.*;

public class TreeMapDemo {
    public static void main(String[] args) {
        TreeMap<Integer, String> t = new TreeMap<>();
        for (int k : new int[] {30, 10, 50, 20, 40}) {
            t.put(k, "v" + k);                       // inserted in any order
        }
        System.out.println(t);                       // always sorted by key
        System.out.println(t.firstKey() + " " + t.lastKey());
        System.out.println(t.floorKey(25) + " " + t.ceilingKey(25));
        System.out.println(t.lowerKey(30) + " " + t.higherKey(30));
        System.out.println(t.floorKey(5));           // nothing at or below 5
        System.out.println(t.headMap(30));           // keys < 30
        System.out.println(t.headMap(30, true));     // keys <= 30
        System.out.println(t.tailMap(30));           // keys >= 30
        System.out.println(t.subMap(20, 40));        // 20 <= key < 40
        System.out.println(t.descendingMap());
        System.out.println(t.pollFirstEntry() + " -> " + t.firstKey());
    }
}

headMap, tailMap and subMap return views of the original map, like subList: changes write through. Putting a key outside a view's range into the view throws IllegalArgumentException.

A realistic use: slab lookup

Discounts by cart value ("₹500 and above: 5%", "₹1,000 and above: 10%") are a perfect fit for floorEntry: find the greatest slab start that is not above the amount.

TreeMap<Integer, Integer> slabs = new TreeMap<>();
slabs.put(0, 0);          // cart value from → discount percent
slabs.put(500, 5);
slabs.put(1000, 10);
slabs.put(5000, 15);

int[] carts = {120, 500, 1200, 9999};
for (int cart : carts) {
    System.out.println("Cart ₹" + cart + " → " + slabs.floorEntry(cart).getValue() + "%");
}

Other uses: time-series data keyed by timestamp (find the reading just before a time), leaderboards, interval and calendar problems, and "find the closest value" in interviews.

Custom ordering

TreeMap<String, Integer> byLength =
        new TreeMap<>(Comparator.comparingInt(String::length)
                .thenComparing(Comparator.naturalOrder()));
byLength.put("UPI", 1);
byLength.put("NEFT", 2);
byLength.put("IMPS", 3);
byLength.put("RTGS", 4);
System.out.println(byLength);       // {UPI=1, IMPS=3, NEFT=2, RTGS=4}

TreeMap<String, Integer> ci = new TreeMap<>(String.CASE_INSENSITIVE_ORDER);
ci.put("Mumbai", 1);
ci.put("MUMBAI", 2);                // "equal" according to the comparator → replaces
System.out.println(ci);             // {Mumbai=2}

Rule: a TreeMap decides key equality with compareTo, not equals

If compare(a, b) == 0 the keys are the same key, whatever equals says. That is why the second put above replaced the first. Make your ordering consistent with equals (compare equal exactly when equals is true), or the map will behave differently from a HashMap holding the same data.

Exceptions and edge cases

  • ClassCastException — keys that are not Comparable and no comparator given. It is thrown on the very first put.
  • NullPointerException — a null key with natural ordering (null values are fine).
  • firstKey() on an empty map throws NoSuchElementException; firstEntry() returns null.
  • Not thread-safe. The concurrent sorted map is ConcurrentSkipListMap.
  • Iteration over a TreeMap is O(n) in sorted order; there is no capacity or load factor to tune.

Tip: sort once with TreeMap, or build a HashMap and sort at the end?

If you only need sorted output once, collect into a HashMap and then copy: new TreeMap<>(map). If you keep inserting and also query by range or nearest key, use a TreeMap all along.

Why the tree stays balanced

A plain binary search tree can degrade into a linked list if you insert sorted keys (1, 2, 3, 4…), and then every search costs O(n). A red-black tree prevents that with colour rules: the root is black, a red node never has a red child, and every path from the root to an empty spot has the same number of black nodes. After each put or remove the tree fixes itself with colour flips and rotations (small local re-arrangements). These rules guarantee that the longest path is at most twice the shortest, so the height is at most about 2·log₂(n+1). You never see this work; you only get O(log n) for get, put, remove, containsKey, floorKey and the other navigation methods.

Entries, views and live changes

The entries returned by firstEntry(), floorEntry(k), pollFirstEntry() and the like are snapshots. Calling setValue on them throws UnsupportedOperationException; change the map with put instead. The entries you get while iterating entrySet() are the real ones and setValue works there.

TreeMap<Integer, String> t = new TreeMap<>(Map.of(10, "a", 20, "b", 30, "c", 40, "d"));
NavigableMap<Integer, String> mid = t.subMap(15, true, 35, true);   // 20 and 30
System.out.println(mid);                  // {20=b, 30=c}

t.put(25, "x");                           // change the original map...
System.out.println(mid);                  // {20=b, 25=x, 30=c}  ...the view sees it

mid.remove(20);                           // change the view...
System.out.println(t);                    // {10=a, 25=x, 30=c, 40=d}  ...the map changes

try {
    mid.put(99, "out");                   // outside 15..35
} catch (IllegalArgumentException e) {
    System.out.println("key out of range");
}

The four-argument subMap(from, fromInclusive, to, toInclusive) lets you choose either end. The same idea exists for sets: TreeSet is built on a TreeMap and offers floor, ceiling, headSet, tailSet and subSet (see Sets).

Another realistic use: the reading just before a time

Sensor readings, price history or audit entries keyed by a timestamp. "What was the price at 10:07?" is the entry with the greatest key not after 10:07.

TreeMap<LocalTime, Integer> price = new TreeMap<>();
price.put(LocalTime.of(9, 15), 2400);
price.put(LocalTime.of(10, 0), 2450);
price.put(LocalTime.of(11, 30), 2390);

var at = LocalTime.of(10, 7);
System.out.println("At 10:07 → " + price.floorEntry(at).getValue());        // 2450
System.out.println("Next change → " + price.higherKey(at));                  // 11:30
System.out.println("Before open → " + price.floorEntry(LocalTime.of(9, 0))); // null

Always check for null from floorEntry, ceilingEntry, lowerEntry and higherEntry: there may be no such key.

Mistake: BigDecimal keys and other "equal but not equals" keys

new BigDecimal("1.0") and new BigDecimal("1.00") are not equals, but compareTo returns 0. A HashMap keeps two entries; a TreeMap keeps one and overwrites the value. Neither is wrong, but you must know which one you have. The reverse also happens: a comparator that looks at only one field (say, the name) treats two different employees with the same name as one key, and the second silently replaces the first.

Wrong: changing a key's sort field after insertion

TreeMap<Employee, String> m = new TreeMap<>(
        Comparator.comparing(Employee::getSalary));
m.put(emp, "Pune");
emp.setSalary(900_000);        // the tree is now in the wrong order
m.get(emp);                    // may return null

Right: remove, change, re-insert

String city = m.remove(emp);
emp.setSalary(900_000);
m.put(emp, city);
// better: use an immutable key such as an id or a record

More edge cases

  • ConcurrentModificationException — you change the map (not through the iterator) while iterating it. Remove with iterator.remove() or entrySet().removeIf(...).
  • headMap(k) returns keys below k; tailMap(k) includes k. This asymmetry is a frequent off-by-one, so pass the inclusive flag explicitly.
  • Do not use size() on a sub-map in a hot loop: counting a view walks the entries, so it is O(n) rather than O(1).

Conventions

  • Declare the variable as NavigableMap<K, V> when you use navigation methods, or as Map when you only need sorted iteration.
  • Pass a comparator built with Comparator.comparing(...).thenComparing(...) and include a unique field (like an id) at the end so that different objects never compare as equal by accident.
  • Use immutable keys: String, numbers, LocalDate, records.

Interview: "When would you use TreeMap?"

  • When keys must stay sorted or you need range/nearest queries: floorKey, ceilingKey, headMap, tailMap.
  • Cost: O(log n) per operation, no null key, keys need an ordering consistent with equals.
  • Internals: red-black tree (a balanced BST); height stays O(log n).

Set: HashSet, LinkedHashSet and TreeSet

A Set holds no duplicates; HashSet is a HashMap in disguise and is the fast default, LinkedHashSet keeps insertion order, and TreeSet keeps elements sorted.

A Set<E> is a collection with no duplicate elements and no index. Use it for "have I seen this before?", unique tags, unique ids, and to remove duplicates. The main method is add(e), which returns true if the element was new and false if an equal element was already there.

import java.util.*;

public class SetBasics {
    public static void main(String[] args) {
        Set<String> emails = new HashSet<>();
        System.out.println(emails.add("a@x.in"));      // true  — new
        System.out.println(emails.add("a@x.in"));      // false — duplicate ignored
        System.out.println(emails.size());             // 1
        System.out.println(emails.contains("a@x.in")); // true, O(1)

        List<Integer> withDupes = List.of(3, 1, 3, 2, 1);
        System.out.println(new LinkedHashSet<>(withDupes));   // dedupe, keep order
    }
}

HashSet — a HashMap inside

HashSet is implemented with a HashMap. Your element is stored as the key, and every key points to the same dummy object (a private static constant named PRESENT). So add(e) is map.put(e, PRESENT) == null, and everything you learned in How HashMap works inside applies: buckets, load factor, collisions, resizing. Elements need correct equals and hashCode; do not mutate them while they are in the set; the iteration order is undefined; one null is allowed.

LinkedHashSet

A HashSet that also threads its elements on a linked list (it uses LinkedHashMap inside). It iterates in insertion order, costs a little more memory, and is still O(1). Re-adding an existing element does not change its position. Since Java 21 it is a SequencedSet with getFirst, getLast and reversed. The most common use: remove duplicates but keep the original order.

TreeSet — sorted

TreeSet uses a TreeMap inside, so it is a red-black tree: elements stay sorted, and add, remove and contains are O(log n). It implements NavigableSet, which gives first(), last(), floor(e), ceiling(e), lower(e), higher(e), headSet, tailSet, subSet, descendingSet(), pollFirst() and pollLast(). These work exactly like the TreeMap methods in the previous article.

TreeSet<Integer> marks = new TreeSet<>(List.of(72, 91, 55, 88, 91));
System.out.println(marks);                    // sorted, duplicate 91 dropped
System.out.println(marks.first() + " " + marks.last());
System.out.println(marks.floor(80) + " " + marks.ceiling(80));
System.out.println(marks.headSet(72));        // below 72
System.out.println(marks.tailSet(88));        // 88 and above
System.out.println(marks.descendingSet());

Comparator must be consistent with equals

A TreeSet never calls equals; two elements are "the same" when compareTo (or the comparator) returns 0. For well-behaved classes both agree. BigDecimal is the famous exception: new BigDecimal("1.0").equals(new BigDecimal("1.00")) is false (the scales differ) while compareTo returns 0.

import java.math.BigDecimal;
import java.util.*;

Set<BigDecimal> hash = new HashSet<>();
Set<BigDecimal> tree = new TreeSet<>();
for (String s : new String[] {"1.0", "1.00"}) {
    hash.add(new BigDecimal(s));
    tree.add(new BigDecimal(s));
}
System.out.println("HashSet size = " + hash.size());
System.out.println("TreeSet size = " + tree.size());
HashSet size = 2
TreeSet size = 1

For your own classes: if you sort by a single field (say salary) and put employees into a TreeSet, two different employees with the same salary will be treated as duplicates and one silently disappears. Always add a tie-breaker (thenComparing(Employee::id)).

Run time of removeAll depends on the argument: with a List argument it can be O(n·m), so pass a set.

Immutable sets and EnumSet

Set.of(a, b, c) and Set.copyOf(c) are immutable, reject null (even in contains(null), which throws), throw IllegalArgumentException on duplicate elements in Set.of, and have an unspecified iteration order. EnumSet is a very fast, compact set for enum values (internally a bit mask).

Rule: uniqueness comes from equals/hashCode (hash sets) or compare (tree sets)

A HashSet of objects whose class has no hashCode override accepts "duplicates". A TreeSet of objects that are not Comparable throws ClassCastException on the first add.

Exceptions and edge cases

  • TreeSet.add(null) throws NullPointerException; HashSet and LinkedHashSet allow one null.
  • Mutating an element after adding it (changing a field used by hashCode or the ordering) breaks contains and remove, as with map keys.
  • A set has no get(i). To read one element, iterate, or use a sorted/sequenced set method such as first().
  • NoSuchElementException — TreeSet.first() on an empty set; pollFirst() returns null instead.

Mistake: expecting a HashSet to keep the order you added

A HashSet of strings prints in an order that looks random. If the order matters, use LinkedHashSet; if the sort matters, use TreeSet.

Real projects

Sets hold roles and authorities (Set<String> roles in a user), visited ids in graph searches, permission checks, and many-to-many JPA associations (Set<Course> avoids duplicate rows and the "multiple bag fetch" problem). Always give JPA entities a sensible equals/hashCode before putting them in a Set.

Interview: "How does HashSet work?" and "HashSet vs TreeSet"

  • HashSet is backed by a HashMap: the element is the key, the value is a constant dummy object. add returns false for duplicates. O(1) average.
  • LinkedHashSet adds insertion order. TreeSet adds sorted order with O(log n) and NavigableSet methods.
  • Duplicate detection: hashCode + equals for hash sets; compareTo / comparator for TreeSet — and they should agree.

Queue and Deque: ArrayDeque, PriorityQueue and legacy classes

Use ArrayDeque for every stack and plain queue, PriorityQueue when you always need the smallest (or largest) element next, and avoid Stack, Vector and Hashtable.

A queue holds elements waiting to be processed — print jobs, Swiggy orders, tasks. A Queue normally works first in, first out (FIFO). A stack works last in, first out (LIFO): think of the browser's back button. A Deque (double-ended queue) can add and remove at both ends, so one class serves as a queue and as a stack.

The Queue methods: two versions of each

Every queue operation exists twice: one version throws an exception on failure, the other returns a special value.

OperationThrows an exceptionReturns null / false
Insert at the tailadd(e)offer(e)
Remove the headremove()poll()
Look at the head (no removal)element()peek()

remove() and element() throw NoSuchElementException on an empty queue; poll() and peek() return null. add throws IllegalStateException("Queue full") when a bounded queue has no room; offer returns false. Prefer offer/poll/peek in normal code.

The Deque interface repeats the set for both ends: addFirst/offerFirst, addLast/offerLast, removeFirst/pollFirst, removeLast/pollLast, getFirst/peekFirst, getLast/peekLast. For stack use it adds three names: push(e) = addFirst, pop() = removeFirst, and peek() = peekFirst.

ArrayDeque

ArrayDeque is a resizable circular array with a head and a tail index. Adding or removing at either end is O(1) amortized and needs no object allocation per element. It is faster than LinkedList as a queue and faster than Stack as a stack. It does not allow null elements (because poll() uses null to mean "empty") and is not thread-safe.

import java.util.*;

public class QueueAndStack {
    public static void main(String[] args) {
        // As a QUEUE (FIFO): offer at the tail, poll from the head
        Queue<String> orders = new ArrayDeque<>();
        orders.offer("order-1");
        orders.offer("order-2");
        orders.offer("order-3");
        System.out.println(orders.peek());     // order-1 (not removed)
        System.out.println(orders.poll());     // order-1 (removed)
        System.out.println(orders);

        // As a STACK (LIFO): push and pop at the head
        Deque<String> history = new ArrayDeque<>();
        history.push("home");
        history.push("search");
        history.push("product");
        System.out.println(history);           // top of the stack is on the left
        System.out.println(history.pop());     // product
        System.out.println(history.peek());    // search

        Queue<String> empty = new ArrayDeque<>();
        System.out.println(empty.poll());      // null
        try {
            empty.remove();
        } catch (NoSuchElementException e) {
            System.out.println("remove() on empty queue throws");
        }
    }
}

A classic stack use case — checking balanced brackets:

static boolean isBalanced(String s) {
    Deque<Character> stack = new ArrayDeque<>();
    for (char c : s.toCharArray()) {
        switch (c) {
            case '(', '[', '{' -> stack.push(c);
            case ')' -> { if (stack.isEmpty() || stack.pop() != '(') return false; }
            case ']' -> { if (stack.isEmpty() || stack.pop() != '[') return false; }
            case '}' -> { if (stack.isEmpty() || stack.pop() != '{') return false; }
            default -> { }
        }
    }
    return stack.isEmpty();
}

System.out.println(isBalanced("{[()]}"));   // true
System.out.println(isBalanced("{[(])}"));   // false

PriorityQueue — always the smallest next

A PriorityQueue is a queue ordered by priority, not by arrival. poll() always returns the smallest element according to natural order or a Comparator. Inside it is a binary min-heap stored in an array: a complete binary tree in which every parent is ≤ its children, so the smallest element is always at index 0. For index i, the parent is at (i - 1) / 2 and the children at 2i + 1 and 2i + 2.

  • offer and poll: O(log n) (the height of the tree). peek: O(1).
  • contains and remove(Object): O(n) — a heap is not searchable.
  • Default initial capacity 11; it grows automatically. No null elements. Not thread-safe (use PriorityBlockingQueue).
  • Elements must be Comparable, or you pass a Comparator; otherwise ClassCastException.
  • Iteration and toString() are not sorted. They show the array order. Only poll() gives sorted order.
  • Elements with equal priority come out in no guaranteed order (it is not a stable queue).
import java.util.*;

public class PriorityQueueDemo {
    record Task(String name, int priority) {}      // 1 = most urgent

    public static void main(String[] args) {
        PriorityQueue<Integer> minHeap = new PriorityQueue<>();
        for (int n : new int[] {5, 1, 4, 2, 3}) {
            minHeap.offer(n);
        }
        System.out.println(minHeap);               // heap array, NOT sorted
        StringBuilder sb = new StringBuilder();
        while (!minHeap.isEmpty()) {
            sb.append(minHeap.poll()).append(' ');
        }
        System.out.println(sb);

        // Max-heap: reverse the order
        PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder());
        maxHeap.addAll(List.of(5, 1, 4, 2, 3));
        System.out.println(maxHeap.poll() + " " + maxHeap.poll());

        // Objects with a comparator
        PriorityQueue<Task> tasks =
                new PriorityQueue<>(Comparator.comparingInt(Task::priority));
        tasks.offer(new Task("Pay bill", 2));
        tasks.offer(new Task("Send newsletter", 5));
        tasks.offer(new Task("Fix prod bug", 1));
        while (!tasks.isEmpty()) {
            System.out.println(tasks.poll());
        }

        // Top-3 largest numbers with a min-heap of size 3
        int[] data = {7, 2, 9, 4, 11, 5};
        PriorityQueue<Integer> top = new PriorityQueue<>();
        for (int x : data) {
            top.offer(x);
            if (top.size() > 3) {
                top.poll();                         // drop the smallest of the four
            }
        }
        List<Integer> result = new ArrayList<>();
        while (!top.isEmpty()) {
            result.add(top.poll());
        }
        System.out.println("Top 3: " + result);
    }
}

The top-K trick is a favourite in interviews: a min-heap of size K keeps the K largest items in O(n log K) time and O(K) memory, without sorting everything.

Legacy classes and why to avoid them

Legacy classProblemUse instead
VectorEvery method is synchronized: slow, and still not safe for compound actions like check-then-addArrayList (or CopyOnWriteArrayList if shared)
StackExtends Vector (so it is synchronized and exposes get(i), add(i, e), breaking the stack idea)ArrayDeque through the Deque interface
HashtableOne lock for the whole map; no null keys or valuesHashMap, or ConcurrentHashMap when shared
EnumerationOld iteration interfaceIterator

One visible difference: Stack iterates from bottom to top, while an ArrayDeque used with push iterates top to bottom. For thread-safe queues (ArrayBlockingQueue, LinkedBlockingQueue, ConcurrentLinkedQueue) see Module 6; they power producer-consumer designs.

Rule: choose by the operations you need

FIFO queue or LIFO stack → ArrayDeque. Always the smallest or largest next → PriorityQueue. Need null elements or List methods too → LinkedList (rare).

Exceptions and edge cases

  • NullPointerException — offer(null) or push(null) on ArrayDeque or PriorityQueue.
  • NoSuchElementException — remove(), element(), pop(), getFirst() on an empty queue or deque.
  • ClassCastException — a PriorityQueue of objects that are not Comparable and no comparator. It fails on the first offer.
  • ArrayDeque.push adds at the front; if you want stack order but then add at the end, you get a mix. Pick one set of method names and stick to it.

Mistake: printing or looping a PriorityQueue to see the order

The output [1, 2, 4, 5, 3] for the values 1 to 5 surprises many people. Sorted order exists only when you poll() repeatedly. If you need a sorted snapshot, copy to a list and sort it.

Mistake: a subtraction comparator in a PriorityQueue

(a, b) -> a - b overflows for large ints and silently breaks the heap order. Use Integer.compare(a, b) or Comparator.comparingInt (details in Comparable vs Comparator).

Interview: "Stack vs ArrayDeque", "How does PriorityQueue work?"

  • Do not use Stack: it is a synchronized Vector subclass. Deque<Integer> s = new ArrayDeque<>() with push/pop/peek is the standard.
  • PriorityQueue: binary min-heap in an array; offer/poll O(log n), peek O(1); max-heap with Comparator.reverseOrder(); iteration is not sorted.
  • Queue method pairs: add/offer, remove/poll, element/peek — exception vs special value.
  • Use cases: BFS (queue), DFS and undo (stack), Dijkstra, top-K, task scheduling (priority queue).

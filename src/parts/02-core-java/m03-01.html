What an exception is: throwing and stack unwinding

An exception is an object that describes an abnormal event. When it is thrown, Java stops the normal flow and unwinds the call stack, method by method, until a matching catch block handles it — if nothing does, the thread dies and prints a stack trace.

Before exceptions, languages like C reported errors with special return values: -1, null or an error code. That design has two big problems. First, callers forget to check the return value, and the program continues with garbage data. Second, the error checks mix with the business logic, so every line of real work is followed by three lines of "did that fail?".

Java's answer is the exception: an object of a class that extends Throwable. It carries four things:

  • its type — the class name already says a lot (FileNotFoundException, NumberFormatException);
  • a message — a human-readable detail such as "Insufficient wallet balance";
  • a stack trace — the chain of method calls that were active when the exception object was created;
  • an optional cause — another exception that led to this one.

To throw an exception means to hand this object to the JVM and say "I cannot continue normally". To catch it means to say "I know how to deal with this kind of problem". The code that throws and the code that catches can be many method calls apart — that is the whole point.

The call stack

Every time a method is called, the JVM pushes a stack frame onto the current thread's call stack. The frame holds the method's parameters, its local variables and the place to return to. When the method returns, its frame is popped. So at any moment the stack is a record of "who called whom", with the running method on top.

What happens when an exception is thrown

  1. Code creates an exception object, for example new IllegalStateException("Insufficient wallet balance"). The stack trace is recorded at this moment, inside the Throwable constructor — not at the throw statement.
  2. The throw statement hands the object to the JVM. The current block stops immediately; the next line does not run.
  3. The JVM looks for an enclosing try block in the current method that has a catch clause whose type matches. "Matches" means the exception is an instance of the catch type — the same class or a subclass.
  4. If there is no match, the method ends abruptly. Its finally blocks run, its frame is popped, and the exception reappears in the caller, at the line that made the call. This is stack unwinding.
  5. Steps 3 and 4 repeat frame by frame. The first matching catch handles the exception, and execution continues after that whole try statement.
  6. If the exception unwinds past the bottom frame (main for the main thread), it is uncaught. The thread's uncaught-exception handler runs — by default it prints Exception in thread "main" plus the stack trace to System.err — and the thread terminates.

Example: an uncaught exception

A small food-ordering flow: main calls placeOrder, which calls chargeWallet. The wallet has ₹100 and the order costs ₹250.

public class OrderFlow {
    public static void main(String[] args) {
        System.out.println("main: start");
        placeOrder(250);
        System.out.println("main: end");                 // never printed
    }

    static void placeOrder(int amount) {
        System.out.println("placeOrder: start");
        chargeWallet(amount);
        System.out.println("placeOrder: confirmed");     // never printed
    }

    static void chargeWallet(int amount) {
        int balance = 100;
        System.out.println("chargeWallet: balance " + balance + ", amount " + amount);
        if (amount > balance) {
            throw new IllegalStateException("Insufficient wallet balance");
        }
        System.out.println("chargeWallet: charged");     // never printed
    }
}

Nobody caught the exception, so the main thread died, the JVM printed the stack trace, and the process ended with exit code 1 instead of 0. A deployment script or CI job sees that non-zero code as a failure.

Example: the same exception, caught

public class OrderFlowCaught {
    public static void main(String[] args) {
        System.out.println("main: start");
        try {
            placeOrder(250);
        } catch (IllegalStateException e) {
            System.out.println("main: order failed -> " + e.getMessage());
        }
        System.out.println("main: end");
    }

    static void placeOrder(int amount) {
        System.out.println("placeOrder: start");
        chargeWallet(amount);
        System.out.println("placeOrder: confirmed");
    }

    static void chargeWallet(int amount) {
        int balance = 100;

        }
        System.out.println("chargeWallet: charged");

Now main catches the exception, prints a friendly message and carries on. Notice that placeOrder: confirmed is still not printed. Catching an exception does not resume the code after the throw point; execution continues after the try statement that caught it.

Rule: control never returns to the throw point

Java has no "resume". Once an exception is thrown, every statement between the throw and the matching catch is skipped (except finally blocks). If placeOrder had already reserved stock before calling chargeWallet, that reservation is not undone automatically — you must design for it (a finally block, a database transaction, or a compensating action).

Note: uncaught exceptions in other threads

Each thread has its own call stack, so an uncaught exception kills only the thread where it happened. The JVM keeps running while any non-daemon thread is alive. In a web server, the framework catches exceptions from your controllers, so one bad request does not stop the server. With an ExecutorService, an exception from a task started with submit() is stored inside the returned Future and appears only when you call get(), wrapped in an ExecutionException — a classic "silent failure" (see Module 6).

Interview: "What happens when an exception is thrown and nobody catches it?"

  • The JVM searches the current method for a matching catch; if there is none, it runs the method's finally blocks, pops the frame and repeats the search in the caller — this is stack unwinding.
  • If no frame catches it, the thread's uncaught-exception handler prints the stack trace and the thread terminates.
  • For the main thread, when no other non-daemon thread is running, the JVM exits; the java launcher returns exit code 1.
  • Bonus point: the stack trace is captured when the exception object is created, not when it is thrown.

Reading a stack trace

Read a stack trace from the top: the first line gives the exception type and message, the first "at" line shows where it was thrown, the first frame from your own package shows where your code was involved, and the last "Caused by" section usually holds the root cause.

A stack trace is the printed form of an exception: its type, its message and the list of stack frames that were active when it was created. It looks scary because it is long, but it has a fixed structure. Once you know the structure, most bugs take minutes instead of hours to find. Reading stack traces quickly is one of the most valuable debugging skills on a real job.

A chained example

The method below parses a price. Someone typed the letter O instead of the digit zero. The parsing error is caught and wrapped in a new exception that adds context — the original exception becomes the cause.

public class StackTraceDemo {
    public static void main(String[] args) {
        new StackTraceDemo().loadPrice("12O");   // letter O, not zero
    }

    void loadPrice(String raw) {
        try {
            int price = parsePrice(raw);
            System.out.println("Price: " + price);
        } catch (NumberFormatException e) {
            throw new IllegalArgumentException("Bad price in catalog: " + raw, e);
        }
    }

    int parsePrice(String raw) {
        return Integer.parseInt(raw);
    }
}

The frame loadPrice appears in both traces but with different line numbers (11 in the outer trace, where the new exception was created, and 8 in the cause, where parsePrice was called), so it is printed twice.

How to read one: four steps

  1. Read the first line. Type plus message is often enough: NumberFormatException: For input string: "12O" already tells you the input was bad.
  2. Jump to the last "Caused by". Outer exceptions are usually wrappers that add context; the deepest cause is the root cause — the thing that really failed.
  3. Find the first frame from your own code in that section. Skip JDK frames (java., jdk., sun.), framework frames (org.springframework., org.hibernate.) and generated proxy frames (names containing $$ or jdk.proxy). Here it is StackTraceDemo.parsePrice(StackTraceDemo.java:16).
  4. Open that line and ask two questions: which value was wrong, and where did that value come from? Then walk down the frames (towards the callers) to trace the value back to its source.

Wrong: logs only the message — type, trace and cause are lost

try {
    paymentClient.charge(order);
} catch (PaymentException e) {
    log.error("Payment failed: " + e.getMessage());
}

Right: pass the exception as the last argument

try {
    paymentClient.charge(order);
} catch (PaymentException e) {
    // SLF4J prints the full stack trace, including every "Caused by"
    log.error("Payment failed for order {}", order.id(), e);
}

With SLF4J (the logging API Spring Boot uses), a Throwable passed as the last argument, with no {} placeholder left for it, is printed as a full stack trace. Avoid e.printStackTrace() in real applications: it writes to System.err, which bypasses your log format, log levels and log files.

Mistake: wrapping an exception without its cause

throw new IllegalStateException("Could not load config"); inside a catch block throws away the original exception — the stack trace will no longer show why loading failed. Always pass the caught exception as the cause: throw new IllegalStateException("Could not load config", e);.

Note: an exception with no stack trace in production logs

Sometimes a production log shows java.lang.NullPointerException with no frames at all. The HotSpot JIT compiler can replace some built-in exceptions that are thrown very often from the same hot code (such as NullPointerException and ArithmeticException) with a preallocated exception that has no stack trace, to save time. The first occurrences in the log still have full traces, so search earlier lines — or start the JVM with -XX:-OmitStackTraceInFastThrow to switch the optimization off.

Tip: let the IDE do the clicking

In IntelliJ IDEA, a stack trace printed in the Run window is already clickable. For a trace copied from a log file or a ticket, use the IDE's "Analyze Stack Trace" action: paste the text and every frame becomes a link to the source line.

Interview: "A production API returns 500. How do you find the cause?"

  • Find the error in the logs (by time, request id or trace id) and read the full stack trace, not just the first line.
  • Go to the deepest "Caused by" — the root cause — and the first frame from your own package.
  • Explain the pieces: frames are listed most recent first, ... n more means shared frames were omitted, Suppressed: comes from try-with-resources.
  • Reproduce with the same input in a test, fix, and add the test so it cannot come back.

The exception hierarchy: Throwable, Error and Exception

Everything you can throw extends Throwable. Error means the JVM or the environment is in serious trouble (don't catch it), Exception means a condition your program can respond to, and RuntimeException marks the unchecked exceptions that usually signal bugs or bad input.

Exceptions are ordinary classes, so they form an inheritance tree. The tree matters for two reasons. First, a catch (IOException e) block also catches every subclass of IOException, such as FileNotFoundException. Second, the position of a class in the tree decides whether it is checked (the compiler forces you to handle it) or unchecked (it does not) — see the next article.

The four classes at the top

ClassMeaningChecked?Should you catch it?
ThrowableRoot of everything that can be thrown or caught. Holds the message, cause, stack trace and suppressed exceptionsYes (itself)Only in rare top-level code that must log everything
ErrorA serious problem in the JVM or environment: out of memory, stack overflow, a missing classNoNo — let it crash, then fix the root cause
ExceptionA condition a reasonable program may want to handle: I/O failure, database error, interruptionYesYes, where you can actually do something
RuntimeExceptionUsually a programming bug (null, bad index, bad cast) or an invalid argument or stateNoUsually fix the bug instead; catch at boundaries

Why you should not catch Errors

An Error says the environment is broken, not your business logic. When the heap is full (OutOfMemoryError), even the code inside your catch block may fail to allocate memory. When the stack overflows, the JVM's state is fine but your algorithm is wrong (usually a recursion without a base case). When a class is missing at runtime, the deployment is broken. None of these can be fixed by the method that happens to be running. The right reaction is to let the thread or the process fail, alert someone, and fix the root cause: a memory leak, a too-small -Xmx, infinite recursion, or a missing JAR.

ErrorWhen it happens
OutOfMemoryErrorThe heap is full and garbage collection cannot free enough space ("Java heap space"), or another memory area such as Metaspace runs out. Causes: a memory leak, loading a huge file into memory, a heap size that is too small

Exception to the rule: top-level code may catch Throwable

Framework and infrastructure code at the very top of a thread — a web server's request loop, a scheduler running jobs, a message consumer — often catches Throwable to log the failure and keep the process alive for the next request. Test frameworks catch AssertionError to report failed tests. Business code should never do this.

Interview: "Explain the exception hierarchy" / "Error vs Exception"

  • Error = problems a program should not try to handle (OOM, stack overflow, linkage errors). Exception = conditions a program can handle.

Checked vs unchecked exceptions

The compiler forces you to catch or declare checked exceptions (Exception and its subclasses outside RuntimeException); unchecked exceptions (RuntimeException, Error and their subclasses) can be thrown anywhere without any declaration.

Java is almost alone among popular languages in having checked exceptions. A checked exception is part of a method's contract: Files.readString(Path) declares throws IOException, which says "reading can fail, and you must decide what to do about it". An unchecked exception is not part of the contract the compiler checks: any method may throw a NullPointerException without saying so.

Which is which

  • Unchecked = RuntimeException and its subclasses, plus Error and its subclasses.
  • Checked = every other Throwable: Exception itself, IOException, SQLException, InterruptedException, ClassNotFoundException, your own classes that extend Exception, and even Throwable itself.

The compiler rule: catch or declare

If code inside a method can throw a checked exception, the method must either catch it or declare it in its throws clause. This is called the catch-or-declare rule (also "handle or declare").

import java.nio.file.Files;
import java.nio.file.Path;

public class Unreported {
    static String readConfig() {
        return Files.readString(Path.of("app.conf"));   // throws IOException
    }
}

Two ways to fix it — catch it where you can handle it, or declare it and let the caller decide:

// Fix 1: handle it here (for example, fall back to a default)
static String readConfigOrDefault() {
    try {
        return Files.readString(Path.of("app.conf"));
    } catch (IOException e) {
        return "mode=default";
    }
}

// Fix 2: declare it; now every caller must catch or declare it in turn
static String readConfig() throws IOException {
    return Files.readString(Path.of("app.conf"));
}

The second compiler rule: no catching what cannot be thrown

The compiler also rejects a catch block for a checked exception that the try block can never throw — it would be dead code.

static int parse(String s) {
    try {
        return Integer.parseInt(s);       // throws only unchecked exceptions
    } catch (IOException e) {             // compile error
        return -1;
    }
}

Exception: catch (Exception e) and catch (Throwable t) are always allowed

Even when the try block throws no checked exception, catching Exception or Throwable compiles, because those types also cover unchecked exceptions that any code can throw. Unchecked types like NumberFormatException can always be caught too.

Unchecked exceptions: no rule at all

You may throw IllegalArgumentException from any method without a throws clause, and callers need not catch it. You may list unchecked exceptions in throws, but it changes nothing for the compiler. The professional way to document them is the Javadoc @throws tag:

/**
 * Withdraws money from this account.
 *
 * @throws IllegalArgumentException if amount is zero or negative
 * @throws InsufficientBalanceException if the balance is lower than amount
 */
public void withdraw(BigDecimal amount) { ... }

Note: checked exceptions exist only in the compiler

The JVM does not know about checked exceptions. Bytecode may throw any Throwable from anywhere; the catch-or-declare rule is enforced by javac alone. That is why other JVM languages such as Kotlin and Scala have no checked exceptions, and why Lombok's @SneakyThrows can throw a checked exception without declaring it.

The design debate

For checked exceptions

  • The method signature tells you what can go wrong.
  • The compiler stops you from forgetting a failure that really happens in production (a file that is missing, a network that drops).
  • Good for recoverable situations the caller is expected to handle.

Against checked exceptions

  • Boilerplate: catch blocks that do nothing useful, or throws clauses copied up through every layer.
  • They tempt people into swallowing exceptions just to make the code compile.
  • They leak implementation details: a service method should not declare SQLException just because its repository uses JDBC.
  • They do not work with lambdas and streams — Function.apply declares no checked exceptions.
  • Adding a checked exception to a public method breaks every caller.

The modern Java ecosystem leans towards unchecked exceptions. Spring translates JDBC's checked SQLException into its unchecked DataAccessException family, JPA's PersistenceException is unchecked, and most libraries written in the last decade throw unchecked exceptions. Checked exceptions are still the right tool in some places, and the JDK itself uses them heavily for I/O.

Checked exceptions and lambdas

A stream pipeline takes functional interfaces like Function, whose method declares no checked exceptions. So a lambda that calls Files.readString does not compile:

List<String> contents = files.stream()
        .map(p -> Files.readString(p))     // unreported exception IOException
        .toList();

List<String> contents2 = files.stream()
        .map(Files::readString)            // incompatible thrown types IOException
        .toList();

The standard fix is to catch inside the lambda and wrap the checked exception in an unchecked one. The JDK has a ready-made wrapper for I/O, java.io.UncheckedIOException:

List<String> contents = files.stream()
        .map(p -> {
            try {
                return Files.readString(p);
            } catch (IOException e) {
                throw new UncheckedIOException(e);   // keeps the IOException as the cause
            }
        })
        .toList();

If you need this in many places, move the try/catch into a small helper method such as readOrThrow(Path) and use map(Util::readOrThrow).

When to use which

  • Unchecked when the problem is a bug in the caller (null argument, invalid value, wrong order of calls), or when the caller cannot reasonably recover. This is the default in most modern application code, including Spring Boot services.
  • Checked when the failure is expected in normal operation, the caller can really do something about it (retry, choose another file, ask the user), and you want the compiler to make sure they think about it.
  • When in doubt in a Spring Boot app, make business exceptions unchecked and handle them in one central place that maps them to HTTP responses (see best practices).

Convention: throws Exception is for demos only

public static void main(String[] args) throws Exception is legal and handy in quick experiments. In real code, declaring throws Exception hides which failures can actually happen and forces every caller to catch the broadest type. Declare the specific checked types, or wrap them.

Mistake: an empty catch block just to satisfy the compiler

catch (IOException e) { } makes the error disappear — the program continues as if the file had been read. If you cannot handle a checked exception, declare it or wrap it in an unchecked exception with the original as the cause.

Interview: "Checked vs unchecked — and which do you prefer?"

  • Define both by the hierarchy and state the catch-or-declare rule; mention it is a compile-time rule only.
  • Give examples: IOException, SQLException vs NullPointerException, IllegalArgumentException.
  • Guideline: checked for recoverable conditions the caller must handle, unchecked for programming errors.
  • Mention the trade-offs (lambdas, boilerplate, leaking details) and that Spring prefers unchecked exceptions, translating SQLException into DataAccessException.

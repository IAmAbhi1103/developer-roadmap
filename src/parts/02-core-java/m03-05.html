Paths: Path, Path.of and the working directory

A Path is an immutable object that names a location in the file system; build one with Path.of("data", "orders.csv"), combine paths with resolve, and remember that a relative path is looked up from the working directory of the running JVM.

Almost every program touches files: configuration, uploads, reports, logs. Java 7 added a modern file API in the package java.nio.file (called NIO.2), and it is what you should use in new code. It has three main parts:

  • Path — an object that describes where a file or folder is. It does not touch the disk.
  • Files — a class of static methods that do things: read, write, copy, move, delete, list. The next articles cover it.
  • Paths — an older helper with one method, Paths.get(...). Since Java 11 you can write Path.of(...) instead; both give the same result.

The older java.io.File class still exists; File vs Path compares the two.

Creating a Path

Path a = Path.of("data", "2026", "orders.csv");        // pieces: separators added for you
Path b = Path.of("data/2026/orders.csv");              // one string works too
Path c = Paths.get("data", "orders.csv");              // older style, same result
Path d = new java.io.File("data/orders.csv").toPath(); // from a legacy File
Path e = Path.of("/var/app/uploads");                  // absolute on Linux and macOS
Path f = Path.of("C:\\Users\\priya\\shop");            // absolute on Windows (escape the \)

Pass the pieces as separate arguments and let Java insert the right separator (/ on Linux and macOS, \ on Windows). Never build paths with string concatenation and a hard-coded separator. A Path is only a name: the file does not have to exist, and creating a Path never fails because of a missing file. Like String, a Path is immutable: every method that "changes" it returns a new Path.

Absolute, relative and the working directory

An absolute path starts at the root of the file system (/var/app, or C:\app on Windows) and means the same thing wherever the program runs. A relative path (data/orders.csv) has no root. Java resolves it against the working directory: the folder in which the JVM was started, stored in the system property user.dir.

The working directory depends on how you start the program, which is the root of many "works on my machine" problems. IntelliJ uses the project or module folder by default, Maven and Gradle tests use the module folder, a Docker container uses its WORKDIR, and a service started by systemd uses whatever the unit file says. When a file is "not found", print where Java really looks:

Path orders = Path.of("data", "orders.csv");
System.out.println(orders.toAbsolutePath());        // /home/priya/shop/data/orders.csv
System.out.println(System.getProperty("user.dir")); // /home/priya/shop
System.out.println(Path.of("").toAbsolutePath());   // the working directory itself

For anything that must not depend on the working directory — uploads, data, logs of a server — use an absolute base directory taken from configuration (an environment variable or application.properties), and build paths below it with resolve.

Combining paths: resolve, relativize, normalize

Path base = Path.of("uploads");
Path file = base.resolve("avatars/asha.png");
System.out.println(file);                                  // uploads/avatars/asha.png
System.out.println(file.resolveSibling("asha-small.png")); // uploads/avatars/asha-small.png
System.out.println(base.relativize(file));                 // avatars/asha.png

Path messy = Path.of("reports/./2026/../2025/summary.txt");
System.out.println(messy.normalize());                     // reports/2025/summary.txt

System.out.println(base.resolve("/etc/passwd"));           // /etc/passwd
  • resolve(other) appends other to this path. It is the right way to build "folder + file name". If other is absolute, it wins and is returned unchanged (the last line).
  • resolveSibling(name) replaces the last element: "the file next to this one".
  • relativize(other) is the opposite of resolve: the path that leads from this one to other. Both paths must be of the same kind (both relative or both absolute), or you get IllegalArgumentException: 'other' is different type of Path.
  • normalize() removes . and folds name/... It works on the text only; it does not look at the disk, so it cannot know about symbolic links.

Never trust a user-supplied file name

If a web application builds a path from a name the user sends, a name such as ../../etc/passwd climbs out of the upload folder. This attack is called path traversal and it is a classic security hole. The defence is to normalize and then check that the result is still inside the base folder.

Wrong: uses the name as it comes

Path target = uploadDir.resolve(userFileName);
Files.copy(in, target);          // userFileName = "../../etc/passwd" escapes uploadDir

Right: normalize, then check

static Path safeResolve(Path base, String userFileName) {
    Path target = base.resolve(userFileName).normalize();
    if (!target.startsWith(base)) {              // compares whole name elements
        throw new IllegalArgumentException("Illegal file name: " + userFileName);
    }
    return target;
}
// base = /var/app/uploads (absolute and normalized)
// safeResolve(base, "avatars/asha.png")  -> /var/app/uploads/avatars/asha.png
// safeResolve(base, "../../etc/passwd")  -> IllegalArgumentException

Even better, do not use the client's name at all: store the file under a generated name (a UUID) and keep the original name in the database.

Comparing paths and finding the real file

  • equals compares the text of the paths: Path.of("a/../b").equals(Path.of("b")) is false, but it is true after normalize().
  • Files.isSameFile(p1, p2) asks the file system whether both paths lead to the same file, following symbolic links. For two different paths, both files must exist.
  • toRealPath() returns the real, absolute, normalized path with symbolic links resolved. Unlike toAbsolutePath(), it touches the disk and throws NoSuchFileException when the file does not exist.

Edge cases and exceptions

  • InvalidPathException (unchecked) is thrown by Path.of for a string the operating system cannot accept as a path, such as a NUL character anywhere, or <, ? or | in a name on Windows.
  • Path.of("") is the empty path; operations treat it as the current directory.
  • Whether names are case-sensitive depends on the operating system and file system: Orders.csv and orders.csv are the same file on Windows and usually different files on Linux. Be exact with names so that code behaves the same everywhere.
  • A Path is Iterable<Path> over its name elements and Comparable, so you can sort paths (the order is lexicographic by name).

Conventions

  • Use Path (not String) as the parameter and field type for files, so callers cannot pass nonsense.
  • Build paths with resolve from a configured base directory; never concatenate strings.
  • Use forward slashes in string literals if you must write one; Java accepts them on Windows too. A single backslash in a Java string literal is an escape character ("C:\data" does not compile).

Interview: "Path vs File, relative vs absolute"

  • Path (Java 7, java.nio.file) describes a location and is used together with Files; File is the old class from Java 1.0 with weaker error reporting.
  • A relative path is resolved against the working directory (user.dir), which differs between IDE, Maven, Docker and servers — a common source of "file not found".
  • resolve, relativize and normalize are text operations; toRealPath and isSameFile use the real file system.
  • Mention path traversal and how to prevent it.

Reading and writing text files with Files

For small files use Files.readString, writeString and readAllLines; for big files stream with Files.lines or a buffered reader; always know your charset (UTF-8) and say with StandardOpenOption whether you create, overwrite or append.

The Files class turns most file work into one line. Before NIO.2 (Java 7) the same job needed a reader, a loop and a try/finally. Every method below throws the checked IOException, so they sit inside a method that declares throws IOException or inside a try block.

The methods you will use

MethodPurposeMemory

Files.readAllLines(path)Whole file as a List<String> Whole file
Files.readAllBytes(path)Whole file as byte[] (binary data) Whole file
Files.lines(path)A lazy Stream<String> of lines — must be closed One line at a time
Files.newBufferedReader(path)A BufferedReader for a manual loop One line at a time
Files.writeString(path, text, options...)Write a String (Java 11) Text in memory

Example: a to-do file and a log file

import java.io.BufferedWriter;
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.StandardOpenOption;
import java.util.List;
import java.util.stream.Stream;

public class FilesReadWrite {
    public static void main(String[] args) throws IOException {
        Path dir = Files.createTempDirectory("notes-");
        Path todo = dir.resolve("todo.txt");

        // 1. write a String: creates the file, or overwrites it
        Files.writeString(todo, "Buy milk\nCall the bank\n");

        // 2. read it all back
        System.out.print(Files.readString(todo));

        // 3. append lines (the file already exists, so CREATE is not needed)
        Files.write(todo, List.of("Pay electricity bill", "Book train ticket"),
                StandardOpenOption.APPEND);

        // 4. read as a list of lines
        List<String> lines = Files.readAllLines(todo);
        System.out.println(lines.size() + " lines: " + lines);

        // 5. a log file: create it if missing, otherwise append
        Path log = dir.resolve("app.log");
        for (String msg : List.of("INFO  Order 1042 placed", "ERROR Payment timeout",
                "INFO  Order 1043 placed")) {
            try (BufferedWriter writer = Files.newBufferedWriter(log, StandardCharsets.UTF_8,
                    StandardOpenOption.CREATE, StandardOpenOption.APPEND)) {
                writer.write(msg);
                writer.newLine();
            }
        }

        // 6. stream a file lazily and close it
        try (Stream<String> stream = Files.lines(log)) {
            stream.filter(l -> l.startsWith("ERROR")).forEach(System.out::println);
        }
    }
}

Call the bank
4 lines: [Buy milk, Call the bank, Pay electricity bill, Book train ticket]
ERROR Payment timeout

Step 5 opens and closes the log file on every message just to keep the example short. In a real program, open the writer once before the loop and close it after.

StandardOpenOption: create, overwrite or append

The write and writeString methods and the buffered-writer methods take a list of options. If you give none, the default is CREATE, TRUNCATE_EXISTING and WRITE: create the file if missing, and erase the old content if it exists. Once you give any option, only the ones you list apply.

OptionMeaning
CREATECreate the file if it does not exist (no error if it does)
CREATE_NEWCreate it; fail with FileAlreadyExistsException if it already exists. The check and the creation are one atomic step
TRUNCATE_EXISTINGEmpty an existing file before writing
APPENDWrite at the end of the file. The file must exist unless you also give CREATE
WRITE, READOpen for writing or reading (usually implied)
DELETE_ON_CLOSEDelete the file when the stream is closed (temporary files)
 
Files.writeString(p, text);                                   // create or overwrite
Files.writeString(p, text, CREATE, APPEND);                   // create or append (logs)
Files.writeString(p, text, CREATE_NEW);                       // only if it does not exist yet
Files.writeString(p, text, APPEND);                           // append; fails if the file is missing
// (with: import static java.nio.file.StandardOpenOption.*;)

Running the failure cases from the example program prints:

APPEND on a missing file -> NoSuchFileException
CREATE_NEW on an existing file -> FileAlreadyExistsException
missing parent directory -> NoSuchFileException

The last line is the third common one: Files never creates missing parent folders. Call Files.createDirectories(path.getParent()) first (see the next article). Two details about line endings: write(path, lines) ends each line with the platform's separator (\r\n on Windows), while writeString writes exactly the text you give it, so add "\n" yourself.

Charsets: always UTF-8

A text file is bytes; a charset (character encoding) says how bytes map to characters. UTF-8 is the standard for new files: it covers every language, and ₹ or é survive a round trip. The Files methods without a charset parameter always use UTF-8. Many other APIs use the default charset of the machine instead.

APICharset when you do not pass one
Files.readString, readAllLines, lines, writeString, newBufferedReader/WriterUTF-8, always
new FileReader(f), new FileWriter(f), new Scanner(file), new String(bytes), text.getBytes()The default charset: depended on the operating system before Java 18; UTF-8 from Java 18 on (JEP 400)

Because you may meet Java 8, 11 or 17 projects, and files from other tools, pass StandardCharsets.UTF_8 explicitly whenever the API accepts a charset.

Real-life trap: a CSV from Excel is not valid UTF-8

Windows tools often save "CSV" as windows-1252 (a single-byte encoding, close to ISO-8859-1). A name like café then contains the byte 0xE9, which is not valid UTF-8, and Files.readString throws java.nio.charset.MalformedInputException (Input length = ...). Files.lines throws an UncheckedIOException whose cause is the same exception. Fix it by reading with the charset the file really has:

List<String> lines = Files.readAllLines(path, Charset.forName("windows-1252"));
// [name, café]

The other classic is the BOM (byte order mark): Excel's "CSV UTF-8" starts the file with the three bytes EF BB BF. Java does not remove them, so the first header becomes "\uFEFFid" and header.equals("id") is false although it prints like id:

String header = lines.get(0);
if (header.startsWith("\uFEFF")) {      // strip the byte order mark
    header = header.substring(1);
}

Large files: do not load them whole

readString, readAllLines and readAllBytes put the entire file into memory — fine for a config file, an OutOfMemoryError for a 3 GB log. For big files use Files.lines or Files.newBufferedReader and process one line at a time. The CSV article after next builds on this.

Files.lines returns a lazy stream: the file is read as you consume the stream, and the stream holds an open file handle. Close it with try-with-resources, as in step 6 above. If you forget, the handle can stay open for a long time: on Windows you cannot delete the file, and on a busy server you eventually hit "Too many open files". If reading fails halfway, the stream throws UncheckedIOException instead of IOException, because stream lambdas cannot throw checked exceptions.

Common mistakes

Wrong: every call overwrites the file

for (String line : report) {
    Files.writeString(file, line + "\n");   // default option = TRUNCATE_EXISTING
}
// the file now contains only the LAST line

Right: append, or open the file once

try (BufferedWriter writer = Files.newBufferedWriter(file)) {
    for (String line : report) {
        writer.write(line);
        writer.newLine();
    }
}

More mistakes

  • Forgetting to close Files.lines, Files.list or Files.walk — use try-with-resources.
  • readAllLines on a huge file — stream it instead.
  • Relying on the default charset — pass UTF-8 or the file's real charset.
  • APPEND without CREATE on a file that may not exist yet.
  • A single backslash in a Windows path string — write "C:\\data\\a.txt" or use Path.of("C:", "data", "a.txt").
  • Swallowing the IOException with an empty catch. Report which file failed: the exception message already contains the path.

Interview: "How do you read a file in Java?"

  • Small text file: Files.readString or readAllLines. Large file: Files.lines (close it!) or newBufferedReader in a loop — constant memory.
  • Always state the charset; know that Files methods default to UTF-8 while FileReader depended on the platform before Java 18.
  • Writing: writeString / write with StandardOpenOption (CREATE, APPEND, TRUNCATE_EXISTING, CREATE_NEW); the default truncates.
  • Handle IOException (checked), and use try-with-resources for readers, writers and streams.

Files and directories: create, copy, move, delete, list, walk

Files has one-liners to check, create, copy, move, delete, list and walk files and folders; handle the specific failures (already exists, not empty, missing) and close every Stream that holds a directory open.

Reading and writing content is half of file work. The other half is managing the files themselves: does it exist, create a folder, move a processed file to an archive, clean up a temp folder. All of these are static methods of Files, and all of them throw IOException subclasses that tell you exactly what went wrong.

Checking: exists, size, type

MethodAnswers
Files.exists(p)Does something exist at this path? false also when the answer cannot be determined (no permission)
Files.notExists(p)Is it certain that nothing exists there? Not the same as !exists(p) in the "cannot tell" case
Files.isRegularFile(p), isDirectory(p)A normal file? A folder?
Files.isReadable(p), isWritable(p)Does the JVM have access?
Files.size(p)Size in bytes; NoSuchFileException if missing. Do not use it for folders
Files.getLastModifiedTime(p)A FileTime (.toInstant() converts it)
Files.readAttributes(p, BasicFileAttributes.class)Size, times and type in one call

Do not check first, then act

if (!Files.exists(p)) Files.createFile(p); has a gap: another thread or process can create the file between the two lines. Prefer the operation that does the check atomically and handle the exception: Files.createFile(p) throws FileAlreadyExistsException, and writeString(..., CREATE_NEW) does the same. This "check-then-act" race is called time-of-check to time-of-use (TOCTOU).

Creating

  • Files.createFile(p) — an empty file; fails if it exists.
  • Files.createDirectory(p) — one folder; the parent must exist; fails if it exists.
  • Files.createDirectories(p) — the folder and every missing parent, like mkdir -p. It does nothing if the folder already exists. It fails with FileAlreadyExistsException only if the path exists and is a file. This is the method you want before writing into a new folder.
  • Files.createTempFile("report-", ".csv") and createTempDirectory("work-") — a uniquely named file or folder in the system's temp location (/tmp on Linux).

Copy, move and delete

  • Files.copy(source, target, options...) fails with FileAlreadyExistsException when the target exists, unless you pass StandardCopyOption.REPLACE_EXISTING. File attributes such as times and permissions are only copied if you add COPY_ATTRIBUTES. Copying a folder creates only an empty folder; its contents are not copied. There are also copy(InputStream, Path) and copy(Path, OutputStream), which are handy for saving an upload or sending a file.
  • Files.move(source, target, options...) moves or renames. Moving inside one folder is a rename. Options: REPLACE_EXISTING and ATOMIC_MOVE (all or nothing, cannot leave a half-moved file).
  • Files.delete(p) throws NoSuchFileException if the path is missing and DirectoryNotEmptyException for a folder with content. Files.deleteIfExists(p) returns false instead of throwing for a missing path (but still throws for a non-empty folder).
Path temp = Files.createTempFile(target.getParent(), "settings-", ".tmp");
Files.writeString(temp, newContent);
Files.move(temp, target, StandardCopyOption.ATOMIC_MOVE);   // readers see the old or the new file, never half

With ATOMIC_MOVE all other options are ignored, and whether an existing target is replaced is up to the file system (on Linux and macOS it is). The temp file must be in the same folder (the same file store) as the target.

Listing and walking

MethodGives you
Files.list(dir)A Stream<Path> of the entries of one folder, not recursive (files and sub-folders)
Files.walk(start) / walk(start, maxDepth)All entries below start, depth-first, including start itself
Files.find(start, depth, matcher)Like walk, filtered by a (path, attributes) predicate
Files.newDirectoryStream(dir, "*.csv")An Iterable of one folder's entries that match a glob pattern
Files.walkFileTree(start, visitor)Full control with a FileVisitor: skip folders, act before and after each folder

Three rules apply to all of them. The order is not guaranteed, so call sorted() when the result must be predictable. The streams from list, walk and find keep the directory open, so close them with try-with-resources. And problems that occur while iterating (a folder you may not read) surface as UncheckedIOException. walk does not follow symbolic links unless you pass FileVisitOption.FOLLOW_LINKS.

Example: process an inbox and archive the files

import java.io.IOException;
import java.io.UncheckedIOException;
import java.nio.file.DirectoryNotEmptyException;
import java.nio.file.FileAlreadyExistsException;
import java.nio.file.Files;
import java.nio.file.NoSuchFileException;
import java.nio.file.Path;
import java.nio.file.StandardCopyOption;
import java.util.Comparator;
import java.util.stream.Stream;

public class FilesManage {

    static void tree(Path root) throws IOException {
        try (Stream<Path> walk = Files.walk(root)) {
            walk.sorted().skip(1).forEach(p ->
                    System.out.println("  " + root.relativize(p) + (Files.isDirectory(p) ? "/" : "")));
        }
    }

    static void deleteTree(Path root) throws IOException {
        try (Stream<Path> walk = Files.walk(root)) {
            walk.sorted(Comparator.reverseOrder()).forEach(p -> {   // children before parents
                try {
                    Files.delete(p);
                } catch (IOException e) {
                    throw new UncheckedIOException(e);
                }
            });
        }
    }

    public static void main(String[] args) throws IOException {
        Path root = Files.createTempDirectory("inbox-demo-");
        Path inbox = Files.createDirectories(root.resolve("inbox"));
        Path archive = root.resolve("archive");
        Files.createDirectories(archive.resolve("2026").resolve("10"));   // creates every missing level

        Files.writeString(inbox.resolve("order-1.csv"), "id,total\n1,250\n");
        Files.writeString(inbox.resolve("order-2.csv"), "id,total\n2,990\n");
        Files.writeString(inbox.resolve("notes.txt"), "ignore me");
        System.out.println("After setup:");
        tree(root);

        // list ONE level, only CSV files, sorted
        System.out.println("CSV files in inbox:");
        try (Stream<Path> files = Files.list(inbox)) {
            files.filter(p -> p.getFileName().toString().endsWith(".csv"))
                 .sorted()
                 .forEach(p -> System.out.println("  " + p.getFileName() + " (" + sizeOf(p) + " bytes)"));
        }

        // copy keeps the original; a second copy fails unless REPLACE_EXISTING is given
        Path backup = root.resolve("backup-order-1.csv");
        Files.copy(inbox.resolve("order-1.csv"), backup);
        try {
            Files.copy(inbox.resolve("order-1.csv"), backup);
        } catch (FileAlreadyExistsException e) {
            System.out.println("second copy -> FileAlreadyExistsException");
        }
        Files.copy(inbox.resolve("order-1.csv"), backup, StandardCopyOption.REPLACE_EXISTING);

        // move processed files into the archive folder
        try (Stream<Path> files = Files.list(inbox)) {
            for (Path p : files.filter(f -> f.toString().endsWith(".csv")).toList()) {
                Files.move(p, archive.resolve("2026").resolve("10").resolve(p.getFileName()));
            }
        }
        System.out.println("After moving:");
        tree(root);

        // delete variants
        try {
            Files.delete(inbox);
        } catch (DirectoryNotEmptyException e) {
            System.out.println("delete(inbox) -> DirectoryNotEmptyException (notes.txt is still inside)");
        }
        try {
            Files.delete(root.resolve("nothing.txt"));
        } catch (NoSuchFileException e) {
            System.out.println("delete(missing) -> NoSuchFileException");
        }
        System.out.println("deleteIfExists(missing) -> " + Files.deleteIfExists(root.resolve("nothing.txt")));

        deleteTree(root);
        System.out.println("root still exists after deleteTree? " + Files.exists(root));
    }

    static long sizeOf(Path p) {
        try {
            return Files.size(p);
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
    }
}

Three things are worth studying in this program. deleteTree deletes a whole folder tree. A folder must be empty before it can be deleted, so children must go first. A path always sorts after its own parent, so sorting in reverse order puts every child before its parent. The helper sizeOf exists because lambdas cannot throw IOException (see wrapping). And the move loop first collects the list with toList(), so the directory stream is not being read while files leave the folder.

The same cleanup with a FileVisitor needs no lambda wrapping, because the visitor methods may throw IOException:

Files.walkFileTree(root, new SimpleFileVisitor<>() {
    @Override
    public FileVisitResult visitFile(Path file, BasicFileAttributes attrs) throws IOException {
        Files.delete(file);                    // every file first
        return FileVisitResult.CONTINUE;
    }

    @Override
    public FileVisitResult postVisitDirectory(Path dir, IOException exc) throws IOException {
        Files.delete(dir);                     // then the now-empty folder
        return FileVisitResult.CONTINUE;
    }
});

Spring users also have FileSystemUtils.deleteRecursively(Path) for this.

The IOException family for files

The file exceptions live in java.nio.file. Most extend FileSystemException (itself an IOException), whose getFile() and getReason() methods describe the failure. Catch the specific one when you can react differently:

ExceptionTypical cause
NoSuchFileExceptionReading, deleting or appending to a path that does not exist, or writing into a missing folder
FileAlreadyExistsExceptioncreateFile, createDirectory, copy or move onto an existing path (without a replace option); CREATE_NEW
DirectoryNotEmptyExceptionDeleting a folder that still has content
NotDirectoryExceptionFiles.list or newDirectoryStream on something that is not a folder
AccessDeniedExceptionNo permission to read, write or list. (On Windows, deleting a file that is still open elsewhere, even by your own unclosed stream, gives a plain FileSystemException: "being used by another process")
MalformedInputExceptionThe bytes are not valid in the charset you read with (a CharacterCodingException)
UncheckedIOExceptionAn IOException that happened inside a stream pipeline

Real project: handling uploaded files

  • At startup call Files.createDirectories(uploadDir), so the folder always exists.
  • Save with a generated name (UUID.randomUUID() + ".png"), never the client's name: Files.copy(file.getInputStream(), target); see path traversal in Paths.
  • Keep uploads outside the application folder, because a container filesystem is thrown away with the container; mount a volume or use object storage (S3).
  • Use createTempFile for intermediate files and delete them in finally.

Mistakes

  • Using the old File.delete() or mkdir(), which only return false when they fail and say nothing about why.
  • Assuming Files.copy copies a folder's contents. It copies the folder entry only.
  • Forgetting that Files.walk includes the start folder itself (use skip(1), or filter it out) — especially in a recursive delete.
  • Not closing Files.list / walk streams.
  • Expecting a stable order from list or walk; the result differs between operating systems.

Interview: "How do you delete a directory with files in Java?"

  • Files.delete throws DirectoryNotEmptyException for a non-empty folder, so you delete the contents first.
  • Either walk the tree and delete in reverse order (Files.walk(root).sorted(Comparator.reverseOrder())), or use Files.walkFileTree with a visitor that deletes files in visitFile and folders in postVisitDirectory.
  • Close the walk stream, and wrap IOException in UncheckedIOException inside a lambda.

You can write Java for years without thinking about the JVM — until the day an app dies with OutOfMemoryError, a request freezes for two seconds during a GC pause, or a HashMap "loses" an object. This module explains what the JVM does with your code: where variables and objects live, how memory is reclaimed, how classes are loaded, and why equals and hashCode must agree. It is an interview module first (these questions appear in nearly every Java interview) and a production-debugging module second.

It builds on Module 1 (references, pass-by-value, strings) and Module 2 (objects and classes). It pairs with Module 4 (how HashMap uses hashCode) and Module 6 (each thread has its own stack).

After this module you will be able to:

  • draw the JVM architecture and say what the heap, the stacks, Metaspace and the execution engine do;
  • trace a small program and say exactly where each variable, object, static field and string lives;
  • explain generational garbage collection, GC roots and the main collectors (G1, ZGC and others), and choose between them;
  • recognise the common memory leaks and find them with a heap dump;
  • use the important JVM flags and tools (-Xmx, jcmd, jstack, JFR);
  • explain class loading, parent delegation and the difference between ClassNotFoundException and NoClassDefFoundError;
  • write correct equals and hashCode and show what breaks in a HashSet when you do not.

JVM architecture: class loader, memory areas and execution engine

The JVM has three main parts — a class loader subsystem that brings classes in, runtime data areas (heap, stacks, Metaspace) that hold data, and an execution engine (interpreter, JIT compiler, garbage collector) that runs the code.

The JVM is a program (written mostly in C++) that provides a complete environment for bytecode: memory, threads, security checks and an instruction executor. The Java language specification only defines what the JVM must do; vendors implement it. The most common implementation is HotSpot (used in Oracle JDK, OpenJDK, Temurin, Corretto and others), and everything here describes HotSpot.

1. Class loader subsystem

Finds .class files (in folders, JARs, modules, or from the network), loads them into memory when first needed, checks them and prepares them for use. Details are in Class loading.

2. Runtime data areas

Heap
One area shared by all threads. Every object and every array created with new lives here, as do the String pool and the static fields of classes (HotSpot keeps them inside each class's Class object). The garbage collector manages it. Size is set with -Xms (initial) and -Xmx (maximum).
Metaspace (method area)
Stores class metadata: the structure of each class, method bytecode, the runtime constant pool. Before Java 8 this was the fixed-size PermGen inside the heap; since Java 8 it is Metaspace in native (OS) memory and grows on demand. It can still run out (OutOfMemoryError: Metaspace), typically when an app keeps generating or reloading classes. Limit it with -XX:MaxMetaspaceSize.
JVM stack (one per thread)
A stack of frames. Each method call pushes a frame holding its local variables, an operand stack and a reference to the constant pool; returning pops it. Size per thread is set with -Xss.
PC register (one per thread)
Holds the address of the bytecode instruction that the thread is executing right now.
Native method stack (one per thread)
Used when the thread runs native (non-Java) code via JNI. In HotSpot it is part of the same thread stack.

Note which areas are shared (heap, Metaspace — so they need care with threads) and which are per thread (stack, PC register). This is why local variables are naturally thread-safe and objects on the heap are not.

3. Execution engine

  • Interpreter. Reads bytecode one instruction at a time and executes it. Starts instantly but is slow.
  • JIT compiler. Compiles frequently run bytecode into native machine code at runtime (see below).
  • Garbage collector. Finds objects that nothing can reach and frees their memory (Garbage collection).

4. JNI

The Java Native Interface lets Java call code written in C or C++ and lets native code call Java. The JDK itself uses it for file, network and OS operations. You rarely write JNI yourself, but native memory (outside the heap) is one reason a Java process can use more memory than -Xmx.

JIT compilation: C1, C2 and tiered compilation

The JVM counts how often each method is called and each loop runs. Methods that cross a threshold are hot and get compiled to machine code by the JIT (just-in-time) compiler. HotSpot has two JIT compilers:

  • C1 (client compiler) compiles quickly with light optimisation.
  • C2 (server compiler) compiles slowly but applies heavy optimisation, using profile data collected while the code ran.

Tiered compilation (the default) combines both: code starts in the interpreter, moves to C1 when warm, and to C2 when very hot. The result is a fast start-up and a high peak speed. Typical C2 optimisations are inlining (copying a small method's body into its caller), removing dead code, and unrolling loops. If an assumption turns out wrong (for example a new subclass is loaded), the JVM deoptimises: it throws away the compiled code and falls back to the interpreter.

Consequences you can see: the first requests to a freshly started service are slower (warm-up); micro-benchmarks written with a simple System.nanoTime() loop are misleading (use JMH); and short-lived command-line tools never reach peak speed. -XX:+PrintCompilation prints what gets compiled.

Escape analysis

When C2 compiles a method, escape analysis checks whether an object created inside it ever "escapes" — is stored in a field, returned or passed somewhere the JIT cannot see. If it does not escape, the JIT can skip the heap allocation and keep the object's fields in CPU registers (scalar replacement), or remove locks on it (lock elision). So a short-lived new Point(x, y) in a hot loop may cost nothing. Objects are not literally moved to the stack; they simply disappear. Do not write ugly code to "save allocations"; write clear code first and measure.

Rule: heap and Metaspace are shared; stack and registers are per thread

Anything on the heap can be reached by several threads and needs synchronisation or immutability. Local variables on a thread's stack are private to it.

Edge cases

  • "PermGen" appears in old tutorials and interview questions. It was removed in Java 8 (replaced by Metaspace); -XX:PermSize flags are ignored by modern JVMs.
  • The JVM spec describes a "method area"; HotSpot implements it as Metaspace. The String pool and static fields moved into the heap in Java 7 and 8.
  • Other JVMs exist (Eclipse OpenJ9, GraalVM) with different internals; the model above still holds.

Interview: "Explain the JVM architecture"

  • Three parts: class loader subsystem, runtime data areas, execution engine (plus JNI and native libraries).
  • Data areas: heap and Metaspace shared; stack, PC register and native stack per thread.
  • Execution engine: interpreter for fast start, JIT (C1 then C2, tiered) for hot code, garbage collector for memory.
  • Add the details that show depth: Metaspace replaced PermGen in Java 8; string pool is on the heap; escape analysis can remove allocations.

Stack vs heap: where variables and objects live

Local variables and method-call frames live on a thread's stack; objects, arrays and the String pool live on the shared heap; a local reference variable sits on the stack and points to its object on the heap.

A worked example

Follow this small program from main into compute:

public class Shop {
    static int orders = 0;                       // static field

    static class Product {
        String name;                             // instance fields live inside the object
        double price;
        Product(String name, double price) { this.name = name; this.price = price; }
    }

    public static void main(String[] args) {
        int qty = 3;                             // primitive local
        String label = "Pen";                    // reference to a pooled literal
        Product p = new Product("Pen", 12.5);    // reference local + object on heap
        int total = compute(p, qty);             // call: new frame
        orders++;
        System.out.println(total);
    }

    static int compute(Product item, int q) {
        double sum = item.price * q;             // 37.5
        return (int) sum;
    }
}

Read the picture like this:

  • qty, q and sum are primitives: the number itself is stored in the frame.
  • p, item and label are references: the stack holds only the reference. p and item hold copies of the same reference, so they point to one Product — this is exactly pass-by-value.
  • The Product object is on the heap. Its fields are inside the object: the primitive price by value, and name as a reference to the pooled "Pen".
  • When compute returns, its frame is popped and sum, q, item disappear. The Product survives because p still points to it.
  • When main ends, p goes away; the Product becomes unreachable and the GC can free it later.

Stack frames in more detail

Each frame has: an array of local variables (parameters first, with this as slot 0 in instance methods); an operand stack, a small work area where bytecode instructions push operands and pop results; and a link to the constant pool of the class. For a + b the bytecode is: load a onto the operand stack, load b, add (pops two, pushes the result), store into a local. You can see this with javap -c. A thread's stack is a chain of frames; the stack trace printed with an exception is a readout of that chain.

StackOverflowError

Each thread's stack has a fixed maximum size. Infinite or very deep recursion keeps pushing frames until it is full:

public class StackDemo {
    static int depth = 0;

    static void recurse() {
        depth++;
        recurse();                      // no base case
    }

    public static void main(String[] args) {
        try {
            recurse();
        } catch (StackOverflowError e) {
            System.out.println("Overflow after about " + depth + " calls");
        }
    }
}
Overflow after about 10000-20000 calls

(The exact depth depends on frame size, JVM and -Xss; typical values are in the thousands to tens of thousands.) StackOverflowError is an Error, not an Exception. Fixes: add or correct the base case, convert recursion to a loop, or (rarely) increase -Xss. Common real-world causes: mutual recursion between toString() methods of two objects that reference each other, bidirectional JPA entities serialised to JSON, and a getter that calls itself.

Rule: a reference is never the object

A variable of a class type holds a reference (or null). Assigning, passing and returning copies the reference, not the object. Two references to one object see each other's changes.

Edge cases

  • "Primitives live on the stack" is only true for local primitives. A primitive field of an object lives inside that object on the heap, and the elements of an int[] are on the heap.
  • Escape analysis can remove an allocation altogether (JVM architecture). The model above is what the language guarantees, not what the JIT physically does.
  • Catching OutOfMemoryError is almost never a good idea: the JVM may be in an inconsistent state. Let it crash and restart (-XX:+ExitOnOutOfMemoryError) after saving a heap dump.
  • Virtual threads (Java 21) have small stacks stored on the heap that grow and shrink; the stack-versus-heap picture changes slightly there (Module 6).

Common mistakes

  • Believing that objects can be created on the stack in Java as in C++ (Product p(...)). In Java, new always means heap (as far as the language is concerned).
  • Saying "the object is passed by reference". The reference is copied.
  • Treating StackOverflowError as a memory-size problem when it is a recursion bug.

Interview: "Stack vs heap" and "StackOverflowError vs OutOfMemoryError"

  • Stack: per thread, frames with locals, fast, freed on return. Heap: shared, objects, managed by GC.
  • Walk through Product p = new Product(...): reference p on the stack, object on the heap.
  • Static fields with the class data; string literals in the pool in the heap; Metaspace holds class metadata.
  • SOE = too deep call chain (fix recursion). OOM = too much live data (fix leak, size, or algorithm). Name two OOM messages.

Garbage collection: generations, roots, collectors and references

The garbage collector frees objects that can no longer be reached from a GC root; the heap is split into young and old generations because most objects die young, and modern collectors (G1, ZGC) do most of their work concurrently to keep pauses short.

In Java you create objects with new and never free them. The garbage collector (GC) does it. An object is garbage when no live part of the program can reach it any more. This removes whole classes of bugs (use-after-free, double free) but introduces GC pauses and tuning.

Reachability and GC roots

Java does not use reference counting (which fails on cycles). The GC starts from a set of GC roots and follows references; everything it can reach is live, everything else is garbage. The roots include:

  • local variables and parameters in every thread's stack frames;
  • static fields of loaded classes;
  • active threads and JNI references;
  • other internal JVM references (such as class loaders and monitor locks).

The basic algorithm is mark and sweep: mark every reachable object, then reclaim the rest. Most collectors also compact or copy the survivors so free memory is one contiguous block (no fragmentation).

The generational hypothesis

Studies of real programs show that most objects die young (a request object, a temporary string, an iterator) and a few live very long (caches, connection pools, Spring beans). So the heap is divided into generations and the young one is collected often and cheaply:

  1. New objects are allocated in Eden (allocation is just a pointer bump, very fast).
  2. When Eden is full, a minor GC runs. It copies the live objects from Eden and the current survivor space into the other survivor space and frees Eden completely. Cost depends on the number of live objects, not on the garbage, so it is quick.
  3. Each survivor object has an age, increased at every minor GC it survives. When the age passes a threshold (at most 15 by default, and the JVM adapts it), the object is promoted to the old generation. Very large objects may be placed in the old generation directly.
  4. When the old generation fills up, an old-generation collection (a major GC) is needed. A full GC collects the entire heap, including young and old generations and Metaspace, and is the slowest, with the longest pauses.

Stop-the-world pauses

Some GC steps need the application threads to stop so that the object graph does not change while the GC walks it. This is a stop-the-world (STW) pause. Users see it as a request that suddenly takes 800 ms. The aim of modern collectors is to keep pauses short by doing most work concurrently with your threads. Throughput (how much CPU goes to your code) and latency (pause length) pull in opposite directions; different collectors choose different balances.

System.gc(), finalize() and Cleaner

  • System.gc() is only a hint; the JVM may ignore it, and when it runs it often causes a full GC pause. Do not call it in application code. (Some libraries do; -XX:+DisableExplicitGC turns it off.)
  • finalize() was meant to clean up before an object is collected. It is unpredictable (no guarantee when or whether it runs), slow, and can resurrect objects. It has been deprecated for removal since Java 18. Never write it.
  • For resources (files, sockets, DB connections) use try-with-resources with AutoCloseable, so they are closed at a known point. For a safety net around native resources, use java.lang.ref.Cleaner:
import java.lang.ref.Cleaner;

public class NativeBuffer implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();

    // The cleanup action must NOT refer to the NativeBuffer, or it can never be collected
    private static class State implements Runnable {
        public void run() { System.out.println("native memory freed"); }
    }

    private final Cleaner.Cleanable cleanable;

    public NativeBuffer() {
        this.cleanable = CLEANER.register(this, new State());
    }

    @Override
    public void close() {
        cleanable.clean();               // runs the action once, now
    }
}

Reference types

A normal variable is a strong reference: while it exists, the object is kept. java.lang.ref offers weaker references that the GC may clear:

Strong (Object o = new Object())Never while reachableEverything normal

WeakReferenceAt the next GC, if only weakly reachableWeakHashMap, canonical-object maps, listeners

import java.lang.ref.WeakReference;
import java.util.Map;
import java.util.WeakHashMap;

public class WeakDemo {
    public static void main(String[] args) throws Exception {
        Object big = new Object();
        WeakReference<Object> weak = new WeakReference<>(big);
        System.out.println(weak.get() != null);      // true: big still strongly held

        big = null;                                  // drop the only strong reference
        System.gc();                                 // a hint, but works in practice here
        Thread.sleep(100);
        System.out.println(weak.get());              // null (normally)

        Map<Object, String> cache = new WeakHashMap<>();
        Object key = new Object();
        cache.put(key, "metadata");
        key = null;                                  // no strong reference to the key remains
        System.gc();
        Thread.sleep(100);
        System.out.println(cache.size());            // 0 (normally): the entry vanished
    }
}

A WeakHashMap removes an entry when its key is no longer strongly reachable. If the value refers to the key strongly, the entry never disappears — a common mistake.

Helping the GC (and not hurting it)

  • Keep objects' scopes small. Local variables disappear when the method returns; you do not need to write x = null (except for a long-lived field that you want to release, or an element removed from your own array-based structure).
  • Do not hold on to data you no longer need: clear caches, unregister listeners, cap collection sizes.
  • Avoid creating huge numbers of short-lived objects in hot loops (boxing, string concatenation) — they are cheap, but not free.
  • Stream large results and process in batches instead of loading millions of rows into a list.

Rule: reachability, not scope, decides what is collected

An object is collectable when no GC root can reach it, even if it was never explicitly dereferenced or if it points to other garbage. A static field holding a collection keeps everything in it alive for the life of the class.

Edge cases

  • Objects in a cycle (A points to B, B to A) are still collected if nothing reaches the cycle.
  • "Humongous" objects (very large arrays) are allocated specially in G1 and can cause extra GC work if you create many.
  • A thread that is still running keeps its Runnable, and everything that Runnable references, alive.
  • GC can run at any time between any two bytecode instructions; never rely on it for program correctness or timing.

Common mistakes

  • Calling System.gc() "to free memory". It rarely helps and often hurts.
  • Relying on finalize() to close files or connections.
  • Increasing -Xmx to hide a leak: the app just dies later, with a bigger heap dump.
  • Setting a huge young generation or many GC flags copied from a blog without measuring.

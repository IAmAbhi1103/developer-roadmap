Logging with SLF4J and Logback instead of System.out.println

Write log messages through the SLF4J interface, let Logback (or Log4j2) decide where and how they appear, choose the right level, use {} placeholders, pass the exception as the last argument, and never log secrets.

Why not System.out.println?

A println is fine for a ten-line practice program. In an application running on a server it is a problem:

  • No levels. You cannot turn off debug chatter in production or turn it on for one package.
  • No context. No timestamp, thread name or class name, which you need to follow one request among thousands.
  • No control over the destination. You cannot send output to rolling files, to a log server (ELK, Loki, CloudWatch) or in JSON.
  • Slow and unsynchronised. Console output is slow and lines from different threads can interleave.
  • No stack-trace handling. e.printStackTrace() writes to System.err, outside your logging setup.

SLF4J facade and implementations

SLF4J (Simple Logging Facade for Java) is only an API: Logger, LoggerFactory and MDC. The real work is done by an implementation found at runtime. This lets libraries log through SLF4J without forcing one logging library on you.

  • Logback — written by SLF4J's author; the default in Spring Boot (spring-boot-starter-logging). Add ch.qos.logback:logback-classic in a plain project; it brings slf4j-api with it.
  • Log4j2 — a powerful alternative (async loggers, many appenders). Keep it up to date: old 2.x versions had the serious Log4Shell vulnerability. In Spring Boot you can switch to it by excluding the logging starter and adding spring-boot-starter-log4j2.
  • If no implementation is on the classpath, SLF4J prints a warning that no providers were found and discards the messages. Having several implementations gives a warning about multiple providers.

Using a logger

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class OrderService {
    private static final Logger log = LoggerFactory.getLogger(OrderService.class);

    public void placeOrder(long orderId, long customerId) {
        log.debug("Placing order {} for customer {}", orderId, customerId);
        try {
            charge(orderId);
            log.info("Order {} created for customer {}", orderId, customerId);
        } catch (IllegalStateException e) {
            log.error("Payment failed for order {}", orderId, e);   // exception LAST
            throw e;
        }
    }

    private void charge(long orderId) {
        throw new IllegalStateException("Gateway timeout");
    }
}

java.lang.IllegalStateException: Gateway timeout

(Only lines at INFO and above show with the default configuration, so the debug line is hidden until you lower the level.) One example run shows either the first or the second path; both are shown here to illustrate the format.

  • One logger per class, declared private static final, named after the class. The logger name is how you filter later (com.shop.OrderService, or everything under com.shop).
  • With Lombok, @Slf4j on the class generates a field named log.

Log levels

LevelUse it forExample
ERRORAn operation failed and needs attention; the system could not do what was askedPayment gateway unreachable, unexpected exception in a request
WARNSomething unexpected or risky happened, but the system recovered or continuesRetry succeeded on 3rd attempt, deprecated API used, cache miss rate high
INFOImportant business and lifecycle events; the "story" of the applicationApplication started, order created, scheduled job finished
DEBUGDetails useful to developers while diagnosingRequest parameters, SQL timing, decision branches
TRACEVery fine-grained flowMethod entry/exit, every loop iteration

Levels are ordered TRACE < DEBUG < INFO < WARN < ERROR. Setting a logger to INFO shows INFO, WARN and ERROR. Production usually runs at INFO (or WARN for noisy libraries) and you temporarily lower one package to DEBUG when investigating. SLF4J has no FATAL level (Log4j2 does). Do not log expected, normal situations (like "user typed a wrong password") at ERROR, or the alerts become noise.

Parameterised messages

Wrong: concatenation

log.debug("Order " + order + " has " + items.size() + " items");
// builds the whole string even when DEBUG is off

Right: placeholders

log.debug("Order {} has {} items", order, items.size());
// string is built only if DEBUG is enabled

With {} the message is formatted only when the level is enabled, so disabled debug statements cost almost nothing. If computing an argument is itself expensive (for example serialising a big object to JSON), guard it: if (log.isDebugEnabled()) { log.debug("Payload: {}", toJson(payload)); }. SLF4J 2 also offers a fluent API (log.atDebug().setMessage(...).log()) with lambdas for lazy arguments.

Logging exceptions

Wrong: the stack trace is lost

catch (Exception e) {
    log.error("Failed: " + e.getMessage());
    // or: e.printStackTrace();
}

Right: pass the exception as the last argument

catch (Exception e) {
    log.error("Failed to place order {}", orderId, e);
}

When the last argument is a Throwable and there is no placeholder left for it, SLF4J prints its full stack trace and the chain of causes. Also:

  • Log an exception once. Either handle it (and log) or rethrow it; do not log.error and then throw at every layer, or one failure fills the log with the same stack trace five times. A common pattern: lower layers throw, and one place (a global exception handler in Spring, @ControllerAdvice) logs.
  • Include identifiers that make the message searchable (order id, user id, request id), not vague text like "error occurred".

Configuration basics

Logback reads logback.xml (or logback-test.xml for tests) from src/main/resources:

<configuration>
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <logger name="com.shop" level="DEBUG"/>       <!-- our code: verbose -->
    <logger name="org.hibernate.SQL" level="WARN"/>

    <root level="INFO">                           <!-- everything else -->
        <appender-ref ref="CONSOLE"/>
    </root>
</configuration>
Logger
A named source of messages, arranged in a hierarchy by dots: com.shop.OrderService inherits the level of com.shop, which inherits from root.
Appender
A destination: console, a file, a rolling file (new file per day or size, old ones deleted), syslog, a network socket.
Encoder / layout / pattern
The format of each line: %d date, %thread, %-5level, %logger{36} abbreviated class name, %msg message, %n newline. JSON encoders exist for log-aggregation systems.

In Spring Boot you rarely write XML; use properties (add a logback-spring.xml only when you need more):

logging.level.root=INFO
logging.level.com.shop=DEBUG
logging.level.org.springframework.web=WARN
logging.file.name=logs/app.log
logging.pattern.console=%d{HH:mm:ss.SSS} %-5level [%thread] %logger{20} - %msg%n

Setting logging.level.org.hibernate.SQL=DEBUG prints the SQL that Hibernate sends — handy when debugging JPA (Spring Boot · Module 3).

MDC — adding context to every line

The MDC (Mapped Diagnostic Context) is a per-thread map of key-value pairs that Logback can print on every line. A filter puts a request id or user id in at the start of a request; every log line from that request, in any class, then carries it, which is how you follow one request through the logs.

import org.slf4j.MDC;

MDC.put("requestId", "req-8f21");
try {
    service.handle(request);          // every log line inside can show %X{requestId}
} finally {
    MDC.clear();                      // threads are reused: always clean up
}
// pattern: %d [%thread] %-5level %X{requestId} %logger{20} - %msg%n

MDC values live in the current thread; they do not automatically move to other threads (executors, async code), so copy them when you hand work over.

What never to log

  • Passwords, OTPs, API keys, JWTs, session ids and other secrets.
  • Card numbers, CVV, bank account numbers, Aadhaar, PAN and other government or financial identifiers; mask them (XXXX-XXXX-XXXX-4242).
  • Full personal data (address, phone, e-mail, health data) beyond what you need; privacy law (such as India's DPDP Act, GDPR) applies to log files too.
  • Whole request or response bodies by default; they hide secrets and fill disks.
  • Anything inside a tight loop at INFO or above.

Logs are copied, shipped to third-party tools and read by many people. Treat them as semi-public. Beware of logging a whole object whose toString() includes a password field; exclude sensitive fields from toString.

Rules

  • Depend on the SLF4J API in your code; keep exactly one implementation on the classpath.
  • Use placeholders, not concatenation; pass the exception as the last argument.
  • Never log secrets or full card/ID numbers.

Conventions

  • Messages are short sentences with identifiers: "Order {} shipped to {}". Start with the event, not "Entering method".
  • Log business events at INFO at service boundaries (request received, job finished) and details at DEBUG.
  • Never use System.out or e.printStackTrace() in application code. Replace tutorial code with log.info.
  • Add a correlation/request id through the MDC in services that call other services.

Common mistakes

  • Logging and rethrowing at every layer (duplicate stack traces).
  • log.info("Result: " + result) in a hot path — string building and I/O cost.
  • Using ERROR for validation failures caused by users.
  • Creating a new logger per call or logging with the wrong class (copy-pasted getLogger(OtherClass.class)).
  • A DEBUG level left on in production for a whole day, filling the disk.

Interview: "Why use a logging framework? What are the log levels?"

  • Levels, formatting, destinations, rolling files, performance and per-package configuration, all changeable without code changes.
  • SLF4J is a facade; Logback or Log4j2 implement it; Spring Boot uses Logback by default.
  • Levels: TRACE, DEBUG, INFO, WARN, ERROR, with a one-line meaning each. Placeholders avoid string building; the exception goes last.
  • MDC for request ids; never log passwords, tokens or card numbers.

Javadoc and code style

Write Javadoc comments for public classes and methods (@param, @return, @throws), and follow one consistent style enforced by the IDE formatter and a style guide such as Google Java Style.

Javadoc

Javadoc is documentation written in special comments (/** ... */) directly above a class, method or field. The javadoc tool turns them into the HTML API pages you know from the JDK documentation, and IntelliJ shows them when you press Ctrl+Q over a name. The first sentence is the summary.

/**
 * A prepaid wallet that holds an amount in paise.
 *
 * <p>Instances are not thread-safe. Amounts are never negative.
 *
 * @author Asha Rao
 * @since 1.0
 */
public class Wallet {
    private long balancePaise;

    /**
     * Withdraws money from the wallet.
     *
     * @param amountPaise the amount to withdraw, in paise; must be positive
     * @return the balance after the withdrawal, in paise
     * @throws IllegalArgumentException if {@code amountPaise} is zero or negative
     * @throws InsufficientFundsException if the balance is lower than the amount
     * @see #deposit(long)
     */
    public long withdraw(long amountPaise) throws InsufficientFundsException {
        if (amountPaise <= 0) {
            throw new IllegalArgumentException("amount must be positive");
        }
        if (amountPaise > balancePaise) {
            throw new InsufficientFundsException(balancePaise, amountPaise);
        }
        balancePaise -= amountPaise;
        return balancePaise;
    }
}
TagMeaning
@param nameDescribes a parameter (what it means, units, allowed values)
@returnDescribes the returned value (not for void)
@throws TypeWhen the method throws that exception
@see, {@link Type#method}Cross-reference to another class or method
{@code text}Inline code, with HTML characters shown literally
@since, @author, @deprecatedVersion, author, and a note about the replacement for old API

Generate the HTML with the JDK tool or Maven: javadoc -d docs src/main/java/com/shop/*.java or mvn javadoc:javadoc (output in target/site/apidocs); IntelliJ has Tools → Generate JavaDoc. Use <p> for new paragraphs inside a comment.

  • Document the contract, not the implementation: what the caller must pass, what comes back, what can go wrong.
  • Public APIs of libraries and shared modules need Javadoc; internal one-line helpers rarely do. Do not write comments that repeat the code (// increments i).
  • A comment that explains why (a business rule, a workaround, a link to a ticket) is worth more than one that explains what. If you need a comment to explain what a block does, consider renaming or extracting a method.
  • Keep documentation true: a wrong comment is worse than none.

Code style

Consistent formatting makes code reviews about logic, not about spaces, and makes diffs in Git small. Rules professionals follow:

  • Follow the Java naming conventions (Module 1): PascalCase classes, camelCase methods and variables, UPPER_SNAKE_CASE constants.
  • One style per codebase, applied by tools, not by arguing. The two common choices are the Google Java Style (2-space indent, 100-column limit, braces always) and IntelliJ's defaults (4-space indent, 120-column limit). Both are fine; the repository's choice wins.
  • Always use braces for if/for/while, one statement per line, one variable per declaration, no wildcard imports, no unused imports.
  • Keep methods short, with one purpose, and avoid deep nesting (use guard clauses).
  • Use meaningful names; avoid abbreviations and magic numbers (static final int MAX_RETRIES = 3;).
  • Declare variables as close as possible to first use; prefer final for fields that never change.
  • Order members consistently: constants, fields, constructors, public methods, private helpers.

Tools that enforce it:

  • IntelliJ formatter: Ctrl+Alt+L reformats, Ctrl+Alt+O optimises imports. Turn on Reformat code and Optimize imports in the commit dialog or "on save" actions.
  • .editorconfig: a small file in the repository root (indent size, line endings, final newline) understood by IntelliJ, VS Code and Eclipse.
  • Formatter plugins: google-java-format or Spotless (Maven/Gradle) can format or check formatting in the build; Checkstyle checks rules; SonarLint/SonarQube and the IDE inspections warn about bugs and smells.

Convention: make style automatic

Add an .editorconfig, share the IDE formatter settings (or use Spotless), and let CI fail when formatting is off. Then nobody discusses braces in a pull request.

Common mistakes

  • Javadoc that only repeats the method name ("Gets the name").
  • Forgetting to update a comment when the code changes.
  • Reformatting a whole file in an unrelated commit, which makes the real change impossible to review.
  • Leaving commented-out code in the file; Git remembers it for you.

Interview: "How do you keep code readable?"

  • Good names, small methods, consistent formatting through tools, comments for the why, Javadoc for public APIs.
  • Code reviews, linters (Checkstyle, SonarLint), and tests as living documentation.

Interview questions — Tools every Java developer uses

How do you debug a Java application in IntelliJ? Name the stepping options.

Set a breakpoint, start in Debug mode, and inspect variables, the frames (call stack) and watches. Step Over (F8) runs a line, Step Into (F7) enters the method on the line, Step Out (Shift+F8) finishes the current method, Run to Cursor (Alt+F9) jumps ahead, and Resume (F9) goes to the next breakpoint. Conditional breakpoints stop only when an expression is true, exception breakpoints stop where an exception is thrown, and Evaluate Expression runs code against the paused state.

What is remote debugging and how do you enable it?

It attaches the IDE to a JVM running elsewhere. Start that JVM with -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005, then create a Remote JVM Debug configuration in IntelliJ with the host and port. Use it only on protected environments, because an open debug port allows arbitrary code execution.

What is Maven and what does mvn clean install do?

Maven is a build and dependency-management tool configured by pom.xml. clean deletes target/; install runs the default lifecycle up to the install phase: validate, compile, test, package, verify, install. The result is a JAR in target/ that is also copied to the local repository ~/.m2.

Explain Maven coordinates and dependency scopes.

Coordinates are groupId (organisation), artifactId (module name) and version. Scopes: compile (default, everywhere), provided (needed to compile, supplied by the runtime, e.g. servlet API), runtime (not needed to compile, needed to run, e.g. JDBC driver) and test (only for tests, e.g. JUnit).

What are transitive dependencies and how do you resolve a version conflict?

A transitive dependency is a library required by a library you declared. When two paths need different versions, Maven keeps the nearest one in the dependency tree, and the first declared on a tie. Inspect with mvn dependency:tree, then pin a version in dependencyManagement, add an exclusion, or use a BOM such as Spring Boot's. Symptoms of a conflict are NoSuchMethodError and NoClassDefFoundError at runtime.

Maven vs Gradle?

Both use Maven Central. Maven has declarative XML, a fixed lifecycle and strong conventions, which makes projects uniform. Gradle uses a Kotlin or Groovy script, a task graph, incremental builds and a build cache, and is more flexible and often faster on large builds. Scope test corresponds to testImplementation, provided to compileOnly, and runtime to runtimeOnly. Both provide a wrapper (mvnw, gradlew).

What is a SNAPSHOT version? Why shouldn't you abuse -DskipTests?

A SNAPSHOT is a moving, in-development version; Maven checks for newer builds, so the same version string can mean different code. A release version is immutable. -DskipTests compiles tests but does not run them; using it to get a green build hides failures and ships bugs, so keep tests on in CI and release builds.

How do you write a unit test with JUnit 5? What are the lifecycle annotations?

Create a class in src/test/java, annotate methods with @Test, follow Arrange-Act-Assert and use Assertions (assertEquals(expected, actual), assertThrows, assertAll). @BeforeEach/@AfterEach run around every test; @BeforeAll/@AfterAll run once and are static. JUnit makes a new test-class instance per method, so tests are independent.

What is a parameterised test and when do you use it?

It runs one test method several times with different arguments, using @ParameterizedTest and a source such as @ValueSource, @CsvSource or @MethodSource. Use it for the same behaviour over many inputs (boundary values, valid and invalid cases) instead of copy-pasting tests.

Describe the steps of a JDBC query and why try-with-resources matters.

Get a Connection (from DriverManager or a pooled DataSource), create a PreparedStatement, bind parameters (index starts at 1), call executeQuery or executeUpdate, iterate the ResultSet with next(), and close everything. Try-with-resources closes the ResultSet, statement and connection even when an exception occurs; unclosed connections leak and exhaust the pool.

Statement vs PreparedStatement vs CallableStatement; what is SQL injection?

Statement runs a complete SQL string; PreparedStatement uses ? placeholders, is precompiled and reusable; CallableStatement calls stored procedures. SQL injection is an attack where user input concatenated into SQL changes the query (' OR '1'='1 turns a login into always-true). Prepared statements send values separately from the SQL text, so input cannot become code. Identifiers such as column names cannot be parameters and must be whitelisted.

How do transactions work in JDBC?

Auto-commit is on by default. For several dependent statements call con.setAutoCommit(false), run them on the same connection, call commit() if all succeed, and rollback() in the catch block if any fails. In Spring this becomes @Transactional.

Why use a connection pool such as HikariCP?

Opening a database connection is slow and databases limit how many they accept. A pool creates connections once and lends them to threads; closing a pooled connection just returns it. This improves latency and caps the load on the database. HikariCP is the default in Spring Boot, with a maximum pool size of 10 unless configured.

Why use SLF4J and Logback instead of System.out.println? What are the log levels and how do you log an exception?

Logging frameworks add levels, timestamps, thread and class names, configurable outputs (files, rolling, JSON) and per-package control, with better performance. SLF4J is the API; Logback or Log4j2 implement it. Levels are TRACE, DEBUG, INFO, WARN, ERROR. Use placeholders (log.info("User {} created", id)) and pass the exception last (log.error("Failed for {}", id, e)) so the stack trace is printed. Never log passwords, tokens or card numbers.

What is MDC and why do teams use it?

The Mapped Diagnostic Context is a per-thread map whose entries (request id, user id) can be printed on every log line. It lets you follow one request through all classes and, with a correlation id passed between services, across a microservice system. Clear it in a finally block because threads are reused.

Practice — Tools every Java developer uses

  1. Debug the cart (easy). Copy the Cart program from the debugger article and use a breakpoint, the Variables panel and a watch on items.size() to find the off-by-one. Then add a conditional breakpoint that stops only when item.price() > 100. Done when you can find the bug without adding a single println.
  2. Exception breakpoint (easy). Write code that throws a NullPointerException three calls deep. Add a Java Exception Breakpoint for it and use the Frames panel to walk back to the line that passed the null. Done when you can state the cause from the debugger alone.
  3. Maven project from scratch (easy). Create a project with Spring Initializr or mvn archetype:generate, or hand-write the pom.xml from this module (Java 21, Logback, JUnit). Run mvn clean install and run the JAR with java -jar (set the mainClass in the manifest). Done when the build is green and the program prints a log line.
  4. Dependency conflicts (medium). Add two libraries that need different versions of one dependency, run mvn dependency:tree -Dverbose, identify the conflict, and fix it with dependencyManagement and an exclusion. Done when the tree shows only the version you chose.
  5. JUnit suite (medium). Test a PriceCalculator or your own class: at least one test per rule, edge cases, an assertThrows, one @ParameterizedTest with @CsvSource, and @BeforeEach. Done when a deliberately introduced bug makes exactly the right test fail, and the tests run with mvn test.
  6. JDBC DAO (medium). Create the customers table in PostgreSQL or MySQL and write a DAO with insert, findById, findAll, update and delete using records, try-with-resources and environment variables for credentials. Done when a main method exercises every method and the table matches what you expect.
  7. Break it, then fix it (medium). Write a login method using string concatenation, log in with ' OR '1'='1, then rewrite it with a PreparedStatement. Done when the attack succeeds on the first version and fails on the second.
  8. Transaction and batch (medium). Implement transfer(from, to, amount) with commit and rollback; prove that a failure after the debit leaves balances unchanged. Then insert 10,000 customers with a batch and compare the time with single inserts. Done when both results are shown with numbers.
  9. Replace println with logging (easy). Add SLF4J and Logback to an earlier practice program, write a logback.xml with a console appender, log at three levels, log an exception with its stack trace, and add a request id through MDC. Done when changing one level in the config shows or hides messages without code changes.
  10. Project 1 — Expense tracker or library manager (end of month 2). Build a console application with a menu. Requirements: OOP classes (for example Expense, Category, ExpenseService; or Book, Member, Loan), collections for in-memory work, data saved in MySQL or PostgreSQL through JDBC with a DAO layer and try-with-resources, custom exceptions (for example ExpenseNotFoundException, BookNotAvailableException), SLF4J logging, a few JUnit tests for the service layer, and a Maven build. Put it on GitHub with a README that has the description, setup steps (database script, environment variables, how to run), screenshots or sample output, and the features list. Done when someone else can clone it, follow the README and run it, and every commit message says what changed.

Executors and thread pools

A thread pool keeps a fixed set of reusable worker threads that take tasks from a queue, so you submit tasks instead of creating threads; ThreadPoolExecutor is the engine behind every factory method in Executors.

Why thread pools

Creating a platform thread is expensive (stack memory, operating-system work), and an unlimited number of threads can crash the JVM. A thread pool starts a limited number of worker threads once and reuses them. You submit tasks (Runnable or Callable) and the pool decides which worker runs each. Benefits: lower creation cost, a hard limit on resource use, a queue to absorb bursts, and one place to shut everything down. The Executor interface (one method, execute(Runnable)) separates what to run from how to run it; ExecutorService adds lifecycle and result handling.

import java.util.concurrent.*;

public class PoolBasics {
    public static void main(String[] args) {
        // Java 19+: ExecutorService is AutoCloseable; close() waits for tasks to finish
        try (ExecutorService pool = Executors.newFixedThreadPool(3)) {
            for (int i = 1; i <= 5; i++) {
                int orderId = i;
                pool.execute(() -> System.out.println(
                        "Order " + orderId + " on " + Thread.currentThread().getName()));
            }
        }   // close(): stops accepting new tasks, waits for the running ones
        System.out.println("All orders done");
    }
}

ThreadPoolExecutor: the real parameters

Every factory above builds a ThreadPoolExecutor. In production code you often create it directly to control all the knobs:

import java.util.concurrent.*;

ThreadPoolExecutor pool = new ThreadPoolExecutor(
        4,                                   // corePoolSize: threads kept alive
        8,                                   // maximumPoolSize: upper limit
        60, TimeUnit.SECONDS,                // keepAliveTime for threads above core
        new ArrayBlockingQueue<>(100),       // bounded work queue
        Thread.ofPlatform().name("invoice-", 1).factory(),   // names: invoice-1, ...
        new ThreadPoolExecutor.CallerRunsPolicy());          // rejection policy

Order of events when you submit a task:

  1. If fewer than corePoolSize workers are running, start a new worker for this task (even if others are idle).
  2. Otherwise try to put the task in the work queue.
  3. If the queue is full and fewer than maximumPoolSize workers exist, start an extra worker.
  4. If the queue is full and the pool is at maximum, the task is rejected: the rejection policy decides what happens.

Note the surprise: extra threads above the core size are created only when the queue is full. With an unbounded queue (the default for fixed and single pools) step 3 never happens, so maximumPoolSize is ignored and the pool never grows beyond core.

Rejection policyEffect
AbortPolicy (default)Throws RejectedExecutionException
CallerRunsPolicyThe submitting thread runs the task itself; this slows the producer down (natural back-pressure)
DiscardPolicySilently drops the new task
DiscardOldestPolicyDrops the oldest queued task and retries the new one

The same task is also rejected after you call shutdown().

Why unbounded queues are risky

A fixed pool of 10 threads with an unbounded queue never rejects anything. If tasks arrive faster than 10 threads can process them, the queue grows until the JVM dies with OutOfMemoryError, and users wait minutes for responses long before that. A bounded queue plus a rejection policy turns overload into a visible, controllable event: return HTTP 429/503, slow the caller, or drop low-value work. Likewise newCachedThreadPool bounds nothing on the thread side. Many style guides therefore say: build ThreadPoolExecutor yourself with a bounded queue.

Shutting down properly

Non-daemon pool threads keep the JVM alive, so a program that forgets to shut down its pool never exits.

  • shutdown() — stop accepting new tasks; already queued and running tasks finish. Returns at once.
  • shutdownNow() — stop accepting tasks, try to stop running ones by interrupting them, and return the list of tasks that never started.
  • awaitTermination(time, unit) — block until all tasks finish or the time passes; returns true if the pool terminated.
pool.shutdown();                                    // no new tasks
try {
    if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
        pool.shutdownNow();                         // interrupt stragglers
        if (!pool.awaitTermination(10, TimeUnit.SECONDS)) {
            System.err.println("Pool did not terminate");
        }
    }
} catch (InterruptedException e) {
    pool.shutdownNow();
    Thread.currentThread().interrupt();
}

Since Java 19, ExecutorService.close() does this "shutdown, then wait" for you, which is why try-with-resources works. If the waiting thread is interrupted, close() calls shutdownNow().

Scheduled tasks

ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);

scheduler.schedule(() -> System.out.println("Run once after 1s"), 1, TimeUnit.SECONDS);

// scheduleAtFixedRate: every 5 s measured from start to start
// scheduleWithFixedDelay: 5 s pause AFTER each run finishes
scheduler.scheduleWithFixedDelay(
        () -> System.out.println("Sync inventory"), 0, 5, TimeUnit.SECONDS);
// ... later: scheduler.shutdown();

If a repeating task throws an exception, later runs are cancelled silently. Wrap the body in try/catch and log. In Spring you use @Scheduled, which sits on the same idea.

How many threads? Sizing pools

Work typeRule of thumbWhy
CPU-boundAbout the number of cores (availableProcessors()) or cores + 1Threads are always busy; extra threads only add context switching
I/O-bound (blocking)cores × (1 + wait time / compute time)Threads mostly wait, so more can be productive; measure and tune. Or use virtual threads
MixedSeparate pools for CPU and I/O workA slow I/O task must not starve CPU tasks

Example: 8 cores, each task computes 10 ms and waits 90 ms for the database. Compute-to-wait ratio is 9, so about 8 × (1 + 9) = 80 threads could keep the cores busy. Treat this as a starting point; the database connection pool size is usually the real limit.

Rules

  • Always shut down pools you create (try-with-resources, or shutdown in a lifecycle hook). Pools managed by Spring are closed with the application context.
  • Never block a pool thread waiting for another task in the same pool — with all workers waiting, no one runs the tasks they wait for (pool-induced deadlock).
  • Do not create a new pool per request; create one and reuse it.

Conventions

  • Name your threads with a ThreadFactory, so logs and thread dumps are readable (invoice-1, not pool-3-thread-7).
  • Use a bounded queue and an explicit rejection policy for production pools; monitor queue size and active count.
  • Catch and log exceptions inside tasks, so failures are not lost.
  • In Spring Boot, configure a TaskExecutor (e.g. ThreadPoolTaskExecutor) bean rather than building raw pools.

Exceptions and edge cases

  • RejectedExecutionException — pool shut down, or queue and max threads full (with AbortPolicy).
  • IllegalArgumentException — e.g. corePoolSize > maximumPoolSize or a non-positive pool size.
  • Core threads are not removed when idle unless allowCoreThreadTimeOut(true).
  • shutdownNow() only interrupts; a task that ignores interrupts keeps running.
  • Thread-local data of a pool thread survives between tasks (see ThreadLocal).

Mistake: using Executors.newFixedThreadPool for unbounded traffic

"It never throws" is the problem, not the benefit. Under overload it hides the failure until memory runs out. Size the queue.

Interview: "Explain ThreadPoolExecutor parameters and what happens when a task is submitted"

  • Core size, max size, keep-alive, work queue, thread factory, rejection handler.
  • Order: core threads first, then the queue, then extra threads up to max, then rejection.
  • Unbounded queue means max size is never used and memory can run out.
  • execute vs submit; shutdown vs shutdownNow.
  • Sizing: CPU-bound ≈ cores; I/O-bound larger, or virtual threads.

Callable, Future and invokeAll

Callable is a task that returns a value and may throw a checked exception; submitting it to an executor gives you a Future, a handle you use to wait for the result, set a timeout or cancel.

Runnable.run() returns nothing and cannot throw checked exceptions. When a task must give back a result, such as a price lookup, use Callable<V>.

import java.util.concurrent.*;

public class FutureDemo {
    static int fetchPrice(String sku) throws InterruptedException {
        Thread.sleep(500);                  // pretend this is a remote call
        return sku.length() * 100;
    }

    public static void main(String[] args) throws Exception {
        try (ExecutorService pool = Executors.newFixedThreadPool(2)) {
            Future<Integer> f1 = pool.submit(() -> fetchPrice("PHONE"));
            Future<Integer> f2 = pool.submit(() -> fetchPrice("CASE"));

            System.out.println("Submitted; main is free to do other work");
            System.out.println("Phone: " + f1.get());   // blocks until ready
            System.out.println("Case : " + f2.get());

            Future<Integer> slow = pool.submit(() -> { Thread.sleep(5000); return 1; });
            try {
                slow.get(1, TimeUnit.SECONDS);
            } catch (TimeoutException e) {
                System.out.println("Too slow, cancelling");
                slow.cancel(true);          // interrupts the sleeping task
            }
            System.out.println("cancelled=" + slow.isCancelled());
        }
    }
}

Exceptions in tasks: ExecutionException

An exception thrown inside a submitted task is caught by the executor and stored in the Future. It reappears when you call get(), wrapped in ExecutionException; the real cause is e.getCause().

Future<Integer> f = pool.submit(() -> { throw new IllegalStateException("gateway down"); });
try {
    f.get();
} catch (ExecutionException e) {
    System.out.println("Task failed: " + e.getCause());   // the original exception
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}

invokeAll and invokeAny

  • invokeAll(tasks) runs a collection of Callables and waits for all to finish; it returns a list of Futures in the same order as the tasks.
  • invokeAny(tasks) returns the result of one task that completed successfully (usually the fastest) and cancels the rest. Use it for "ask three mirrors, use the first answer".
import java.util.*;
import java.util.concurrent.*;

public class InvokeAllDemo {
    public static void main(String[] args) throws Exception {
        List<Callable<String>> calls = List.of(
                () -> "inventory ok",
                () -> "payment ok",
                () -> "address ok");

        try (ExecutorService pool = Executors.newFixedThreadPool(3)) {
            for (Future<String> f : pool.invokeAll(calls)) {   // waits for all
                System.out.println(f.get());
            }
            System.out.println("First finisher: " + pool.invokeAny(calls));
        }
    }
}
inventory ok
payment ok
address ok
First finisher: inventory ok

Rules

  • Future.get() blocks the calling thread. Use the timeout version when the caller must stay responsive.
  • Always handle InterruptedException (restore the flag) and ExecutionException (look at the cause).
  • Cancelling a task with cancel(true) only works if the task responds to interruption.

Exceptions and edge cases

  • ExecutionException — the task threw. TimeoutException — get(time) ran out of time (the task keeps running unless cancelled). CancellationException — get() on a cancelled future (unchecked). InterruptedException — the waiting thread was interrupted.
  • A submitted Runnable that throws is silent unless somebody calls get() — a common source of "my background job never runs and nothing is logged".
  • Future cannot be chained or combined and cannot be completed by hand. That is why CompletableFuture exists.

Mistake: calling get() right after submit in a loop

Submitting a task and immediately calling get() makes the work sequential. First submit all tasks, collect the futures, then call get() on each (as in the example above), or use invokeAll.

The executor itself and its thread lifecycle are explained in Executors and thread pools; here we focus on the results.

How a Future works inside: FutureTask

When you submit a Callable, the executor wraps it in a FutureTask. A FutureTask is both a Runnable (the pool thread runs it) and a Future (you wait on it). It stores the outcome — a value or an exception — and wakes everyone blocked in get() when the task completes. You can use it without a pool too, which is the way to give a Callable to a plain Thread:

FutureTask<String> task = new FutureTask<>(() -> "report ready");
new Thread(task, "report-thread").start();
System.out.println(task.get());          // report ready  (blocks until done)
System.out.println(task.isDone());       // true

The life of a Future

A Future ends in exactly one of three ways, and since Java 19 you can ask which with future.state(), which returns Future.State: RUNNING, SUCCESS, FAILED or CANCELLED.

  • Completed normally: get() returns the value.
  • Failed: get() throws ExecutionException with the original exception as the cause.
  • Cancelled: get() throws CancellationException. isDone() is also true after a cancel.

cancel(false) only stops a task that has not started yet; a running task finishes normally. cancel(true) also interrupts the running thread, but the task must check for interruption (blocking calls like sleep do; a tight CPU loop does not unless it tests Thread.currentThread().isInterrupted()). cancel returns false if the task had already finished.

invokeAll with a failing task and a time limit

List<Callable<String>> calls = List.of(
        () -> "stock: 12",
        () -> { throw new IllegalStateException("price service down"); },
        () -> { Thread.sleep(3000); return "reviews: 4.5"; });

try (ExecutorService pool = Executors.newFixedThreadPool(3)) {
    List<Future<String>> results = pool.invokeAll(calls, 1, TimeUnit.SECONDS);
    for (Future<String> f : results) {
        try {
            System.out.println("OK    " + f.get());
        } catch (ExecutionException e) {
            System.out.println("FAIL  " + e.getCause().getMessage());
        } catch (CancellationException e) {
            System.out.println("LATE  cancelled after the time limit");
        }
    }
}
OK    stock: 12
FAIL  price service down
LATE  cancelled after the time limit

The timed invokeAll cancels every task that is not finished when the time is up. The returned futures are all in a done state, so get() never blocks here. Plain invokeAll never throws because a task failed; each failure waits in its own Future. invokeAny throws ExecutionException only if every task fails.

Java 21: one cheap thread per task

Because Callable tasks are mostly blocking calls (HTTP, database), they suit virtual threads. Executors.newVirtualThreadPerTaskExecutor() gives a new virtual thread per submitted task, so you can run thousands of blocking Callables with the same submit/get code and no pool-size tuning.

Wrong: sequential, because get() is called inside the loop

List<Integer> prices = new ArrayList<>();
for (String sku : skus) {
    prices.add(pool.submit(() -> fetchPrice(sku)).get());   // waits every time
}

Right: submit all first, then collect

List<Future<Integer>> futures = new ArrayList<>();
for (String sku : skus) {
    futures.add(pool.submit(() -> fetchPrice(sku)));
}
List<Integer> prices = new ArrayList<>();
for (Future<Integer> f : futures) {
    prices.add(f.get());
}

More mistakes

  • Catching Exception around get() and printing e.getMessage(). For an ExecutionException that message is just the wrapper's text; log e.getCause().
  • Using submit for fire-and-forget work and never calling get(). Errors vanish. Use execute with a handler, or log inside the task.
  • Swallowing InterruptedException around get() with an empty catch. Restore the flag with Thread.currentThread().interrupt().
  • Forgetting to shut the executor down (or to use try-with-resources on Java 19+), which keeps the JVM alive.

Conventions

  • Always call the timed get(timeout, unit) on calls that leave your process, and decide what a timeout means (default value, retry or error).
  • Keep tasks independent and side-effect free where you can; then invokeAll is easy to reason about.
  • Prefer CompletableFuture for pipelines (call A, then B, then combine); use plain Future for "run these N things and collect the answers".

In real projects

A typical use is a product page that needs price, stock and reviews from three internal services. Submit three Callables, wait with a 500 ms limit each, and show the page with a default for any part that failed. The same shape is used for fan-out searches, batch file parsing and report generation. Note that Spring's @Async methods return CompletableFuture, which implements Future too.

Interview: "Runnable vs Callable", "What is a Future? What does get() throw?"

  • Callable returns a value and may throw checked exceptions; Runnable does neither.
  • Future is a handle to an async result: get, get(timeout), cancel, isDone.
  • get() throws ExecutionException (wrap of the real error), InterruptedException, and TimeoutException in the timed version.
  • Limits of Future: blocking, no chaining, no callbacks — solved by CompletableFuture.

CompletableFuture: async pipelines

CompletableFuture lets you start async work, chain steps on its result without blocking, combine several futures, and handle errors in the same pipeline.

A plain Future makes you wait. CompletableFuture<T> (Java 8) implements Future and also CompletionStage: you attach callbacks that run when the result arrives, like a stream pipeline for asynchronous values. It can also be completed by hand with complete(value) or completeExceptionally(ex).

thenApply vs thenCompose: if your function returns a plain value, use thenApply. If it returns another CompletableFuture (it calls another async service), use thenCompose; thenApply would give you a nested CompletableFuture<CompletableFuture<U>>. It is the same difference as map vs flatMap in streams.

import java.util.concurrent.CompletableFuture;

public class ChainDemo {
    static CompletableFuture<String> findUserId(String email) {
        return CompletableFuture.supplyAsync(() -> "U-" + email.length());
    }
    static CompletableFuture<Integer> loadCartTotal(String userId) {
        return CompletableFuture.supplyAsync(() -> 1499);
    }

    public static void main(String[] args) {
        CompletableFuture<String> message =
                findUserId("asha@mail.in")                    // step 1: async
                .thenCompose(ChainDemo::loadCartTotal)        // step 2: async, needs step 1
                .thenApply(total -> total * 118 / 100)        // step 3: plain function (GST)
                .thenApply(total -> "Pay Rs " + total);       // step 4: format

        System.out.println(message.join());
    }
}
Pay Rs 1768

Combining many futures

  • thenCombine — two futures into one value.
  • CompletableFuture.allOf(f1, f2, f3) — returns CompletableFuture<Void> that completes when all are done; read each result with join() afterwards.
  • CompletableFuture.anyOf(f1, f2) — completes when the first one completes; returns CompletableFuture<Object>.

Realistic example: three services in parallel

A product page needs price, stock and reviews from three services, each taking about 300 ms. Sequential calls cost about 900 ms; in parallel about 300 ms.

import java.util.concurrent.*;

public class ProductPage {
    record Page(String price, String stock, String reviews) { }

    static String slow(String what, String value) {
        try { Thread.sleep(300); } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException("interrupted calling " + what);
        }
        return value;
    }

    public static void main(String[] args) {
        try (ExecutorService io = Executors.newFixedThreadPool(10)) {   // our own pool
            long start = System.currentTimeMillis();

            var price   = CompletableFuture.supplyAsync(() -> slow("price", "Rs 999"), io);
            var stock   = CompletableFuture.supplyAsync(() -> slow("stock", "In stock"), io);
            var reviews = CompletableFuture.supplyAsync(() -> slow("reviews", "4.3 stars"), io)
                    .orTimeout(1, TimeUnit.SECONDS)                    // Java 9+
                    .exceptionally(ex -> "reviews unavailable");       // fallback

            Page page = CompletableFuture.allOf(price, stock, reviews)
                    .thenApply(v -> new Page(price.join(), stock.join(), reviews.join()))
                    .join();

            System.out.println(page);
            System.out.println("took ~" + (System.currentTimeMillis() - start) / 100 * 100
                    + " ms");
        }
    }
}

took ~300 ms

Async variants and which thread runs what

Every step has an Async twin (thenApplyAsync). The plain version may run on the thread that completed the previous stage, or on the caller if it was already complete. The Async version always submits to an executor. Without an executor argument, supplyAsync and the Async methods use ForkJoinPool.commonPool() — a shared pool sized to about the number of cores minus one, whose threads are daemon threads.

Mistake: blocking I/O on the common pool

If you run slow blocking calls (database, HTTP) in supplyAsync(...) with no executor, they occupy the few common-pool threads. Parallel streams and other code share that pool and will slow down or stall. Pass your own executor, as in the example: supplyAsync(task, ioExecutor). Also, because those threads are daemons, a main method that does not wait can end before the work does.

Rules

  • Do not call join()/get() in the middle of a pipeline; chain with thenApply/thenCompose and block only once at the edge (or never, in a reactive/async controller).
  • An exception in any stage skips the following thenApply stages and flows to the first exceptionally/handle.
  • Use thenCompose when the function returns a CompletableFuture.

Edge cases

  • Cancelling a CompletableFuture does not interrupt the running thread; it only completes the future exceptionally. Plan for cooperative stop yourself.
  • An exception that nobody observes (no join, no handle) disappears silently.
  • allOf with zero arguments is already complete; one failing future makes the combined future fail, but the others keep running.
  • orTimeout/completeOnTimeout exist since Java 9 and complete the future only; they do not stop the underlying work.

Real projects

Spring's @Async methods can return CompletableFuture<T>; aggregator or "backend for frontend" services use allOf to fan out to several microservices. With virtual threads (Java 21), many teams go back to plain blocking code in parallel tasks because it is easier to read — but CompletableFuture is still everywhere in existing code and libraries.

Interview: "thenApply vs thenCompose", "How do you run three calls in parallel?", "Where does supplyAsync run?"

  • thenApply = map (function returns a value); thenCompose = flatMap (function returns a future); thenCombine merges two independent futures.
  • Parallel calls: start each with supplyAsync, then allOf(...).thenApply(...) and read with join().
  • Default executor is the common ForkJoinPool; for blocking I/O supply your own executor.
  • Errors: exceptionally (fallback), handle (both paths), whenComplete (side effect). join() throws CompletionException.

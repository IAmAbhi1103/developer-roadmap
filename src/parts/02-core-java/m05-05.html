Optional: avoiding NullPointerException the right way

Optional<T> is a small container that holds either one value or nothing; use it as a method's return type to say "there may be no result", so callers must handle the empty case instead of discovering it as a NullPointerException.

A NullPointerException (NPE) happens when you use null as if it were an object: calling a method on it, reading a field, unboxing a null Integer, taking the length of a null array. The inventor of null references, Tony Hoare, called them his "billion-dollar mistake", and every Java developer has met the stack trace. Nulls come from everyday places: Map.get for a missing key, a database lookup that finds no row, a JSON field that was not sent, a field nobody assigned.

The old defence is a staircase of if checks. It works, hides the real logic, and you forget one check:

record Address(String city) {}
record User(String name, Address address) {}

static String cityOf(User user) {
    String city = "UNKNOWN";
    if (user != null) {
        Address address = user.address();
        if (address != null && address.city() != null) {
            city = address.city().toUpperCase();
        }
    }
    return city;
}

java.util.Optional<T> (Java 8) makes "might be missing" part of the type. A method that returns Optional<User> tells every caller, in the signature, that there may be no user — and the caller cannot reach the User without deciding what to do about the empty case. The JDK designers meant it for return types, not as a replacement for every nullable variable. Remember that when you read the rules below.

orElse vs orElseGet: eager vs lazy

The argument of orElse is a normal argument, so Java evaluates it before the call, whether or not the Optional has a value. orElseGet takes a lambda and runs it only when needed. Watch it happen:

static String expensiveDefault(String label) {
    System.out.println("computing default for " + label);
    return "DEFAULT";
}

public static void main(String[] args) {
    Optional<String> present = Optional.of("Ravi");
    Optional<String> empty = Optional.empty();

    System.out.println(present.orElse(expensiveDefault("orElse, present")));
    System.out.println(present.orElseGet(() -> expensiveDefault("orElseGet, present")));
    System.out.println(empty.orElseGet(() -> expensiveDefault("orElseGet, empty")));
}

Even though the Optional held "Ravi", orElse still computed the default. For a constant (orElse("guest")) that costs nothing. When the default is a method call, an object creation, a database query or a log line, use orElseGet — or you pay for it on every call, and any side effect happens every time.

Transforming: map, flatMap and filter

This is where Optional replaces the staircase. map applies a function to the value if there is one and wraps the result; on an empty Optional it does nothing and stays empty. filter turns a value into "empty" if it fails a test.

static String cityOf(User user) {
    return Optional.ofNullable(user)
            .map(User::address)          // null address  -> empty
            .map(Address::city)          // null city     -> empty
            .map(String::toUpperCase)
            .orElse("UNKNOWN");
}

System.out.println(cityOf(new User("Asha", new Address("pune"))));
System.out.println(cityOf(new User("Ravi", null)));
System.out.println(cityOf(null));

Optional<String> name = Optional.of("  Ravi ");
System.out.println(name.map(String::trim).filter(s -> s.length() > 3));
System.out.println(name.map(String::trim).filter(s -> s.length() > 4));

Optional in Spring Data JPA

You meet Optional constantly in Spring: CrudRepository.findById(id) returns Optional<T>, and so can any derived query that returns at most one row. List queries return an empty list, never null. More about repositories in Spring Boot · Module 3.

public interface UserRepository extends JpaRepository<User, Long> {
    Optional<User> findByEmail(String email);     // at most one row
    boolean existsByEmail(String email);           // cheaper than findByEmail(...).isPresent()
}

@Service
public class UserService {
    private final UserRepository users;

    public UserService(UserRepository users) {
        this.users = users;
    }

    public User getById(Long id) {
        return users.findById(id)
                .orElseThrow(() -> new UserNotFoundException(id));   // becomes a 404 in the API
    }

    public String displayName(String email) {
        return users.findByEmail(email).map(User::getName).orElse("guest");
    }
}

The pattern is always the same: ask the repository, then decide at once what "not found" means — a default value (orElse), an exception (orElseThrow), or "do nothing" (ifPresent).

Using Optional correctly: the rules

Rules

  • Use Optional as a return type when "no result" is a normal outcome (a search, a lookup).
  • Do not use it for fields. It is not Serializable, adds an extra object per field, and JPA and JSON libraries expect plain fields. Keep the field nullable and return Optional from the getter if you like.
  • Do not use it for method parameters. Callers must wrap values for no benefit. Use an overloaded method, or accept a nullable parameter and document it.
  • Do not use it for collections. Return an empty list, set or map instead of Optional<List<T>>.
  • Never return null from a method whose return type is Optional. Return Optional.empty().
  • Never call get() without checking. Prefer orElseThrow(), which says clearly that you expect a value.
  • Do not use Optional.of(x) when x can be null. Use ofNullable.

Wrong: isPresent() then get()

Optional<User> user = repo.findByEmail(email);
if (user.isPresent()) {
    return user.get().getName();
} else {
    return "guest";
}

Right: one chain

return repo.findByEmail(email)
        .map(User::getName)
        .orElse("guest");

Wrong: Optional as field and parameter

class Order {
    private Optional<String> coupon;
    void apply(Optional<String> code) { ... }
}

Right: nullable field, Optional getter

class Order {
    private String coupon;           // may be null
    Optional<String> getCoupon() {
        return Optional.ofNullable(coupon);
    }
}

Other ways to avoid NullPointerException

Optional is one tool. Often a simpler habit removes the null altogether:

  • Return empty collections (List.of(), Collections.emptyList()) and empty strings where it makes sense, not null.
  • Fail fast on bad input: Objects.requireNonNull(name, "name must not be null") throws an NPE with a clear message at the point of the mistake, not three calls later.
  • Defaults: Objects.requireNonNullElse(value, "default") and requireNonNullElseGet (Java 9), map.getOrDefault(key, 0).
  • Compare safely: "PAID".equals(status) or Objects.equals(a, b) instead of status.equals("PAID").
  • Beware of unboxing: int x = map.get("k"); throws an NPE if the key is missing, because it unboxes null.
  • Nullability annotations (@Nullable, @NonNull) let your IDE and static-analysis tools find nulls before runtime.

Version note: helpful NullPointerException messages (Java 14; on by default since Java 15)

Modern Java tells you which expression was null. Instead of a bare NullPointerException on a long chain, you get a message like the one below. Read it first when you debug an NPE.

java.lang.NullPointerException: Cannot invoke "Address.city()" because the return value of "User.address()" is null

Exceptions and edge cases

  • Optional.of(null) throws NullPointerException; get() and orElseThrow() on an empty Optional throw NoSuchElementException: No value present.
  • flatMap with a function that returns null (instead of an Optional) throws NullPointerException.
  • Optional is a value-based class: compare with equals, never ==, and never synchronize on one. Two Optionals are equal when both are empty or both hold equal values.
  • A stream.findFirst() on a stream whose first element is null throws an NPE, because an Optional cannot hold null.
  • orElse(null) is legal and sometimes needed at the boundary with old code that expects null.

Mistake: wrapping a value only to unwrap it

Optional.ofNullable(name).orElse("guest") for a single null check just creates an object for nothing. For one variable, Objects.requireNonNullElse(name, "guest") or a plain name != null ? name : "guest" is clearer. Use Optional when you chain map/filter, or when you return it.

Conventions

  • Name Optional-returning methods so the absence is obvious: findByEmail, lookup. Methods named get... usually promise a value.
  • Prefer map/orElse/orElseThrow chains over isPresent() plus get().
  • Throw a specific, meaningful exception from orElseThrow (UserNotFoundException), not a generic RuntimeException.
  • For existence checks use existsById or existsByEmail; do not load the whole entity.

Interview: "What is Optional? Why not use it for fields? orElse vs orElseGet? map vs flatMap?"

  • A container for zero or one value, meant mainly for return types, so absence is visible in the signature and callers must handle it.
  • Not for fields, parameters or collections: not Serializable, extra allocation, awkward for callers; return empty collections instead.
  • orElse(x) evaluates x always; orElseGet(supplier) only when empty — use the lazy form for anything costly.
  • map wraps the result of a normal function; flatMap is for a function that already returns an Optional, avoiding Optional<Optional<T>>.
  • Never call get() blindly; use orElseThrow().
  • Spring Data: findById returns an Optional; typical code is .orElseThrow(() -> new NotFoundException(...)).
  • Other NPE defences: Objects.requireNonNull, empty collections, "literal".equals(x), helpful NPE messages (Java 14+).

Date and time API: LocalDate, LocalDateTime, Instant, Duration and Period

The java.time package (Java 8) replaces Date and Calendar with immutable, thread-safe types for exactly what you need — a date, a time, both, or a moment on the timeline — and every "change" returns a new object.

Why Date and Calendar had to go

  • java.util.Date is mutable (setTime), so a shared Date can change under your feet. It is really a moment, but it prints in the JVM's default time zone, which confuses everyone. Its old constructors count years from 1900 and months from 0.
  • Calendar is verbose and mutable, and its months start at 0 (Calendar.OCTOBER is 9), a classic off-by-one bug source.
  • SimpleDateFormat is not thread-safe. Share one instance in a web server and you get corrupted dates under load, with no exception.
  • No type for "just a date". People used Date with the time set to midnight, and time zones moved birthdays by a day.

The java.time package (JSR-310, inspired by the Joda-Time library) fixes all of this: immutable and therefore thread-safe, one type per idea, months numbered 1–12, a fluent API, and ISO-8601 text formats by default.

Because the types are immutable, d.plusDays(5); on its own line does nothing — the new date is thrown away. Assign it: d = d.plusDays(5);.

How much time between two points?

  • Duration.between(timeA, timeB) — hours, minutes, seconds, for times, date-times and instants.

Instant and Clock

Instant is a single point on the UTC timeline, counted from the Unix epoch (1970-01-01T00:00:00Z) with nanosecond precision. It has no time zone and no calendar, so it has no plusMonths — only exact amounts such as seconds, hours and days of 24 hours. It is the right type for "when did this happen".

Instant paidAt = Instant.parse("2026-10-21T13:00:00Z");
System.out.println(paidAt.plus(Duration.ofHours(36)));
System.out.println(paidAt.toEpochMilli());          // milliseconds since 1970

// A Clock lets tests control "now"
Clock fixed = Clock.fixed(paidAt, ZoneId.of("Asia/Kolkata"));
System.out.println(LocalDate.now(fixed) + " " + LocalDateTime.now(fixed) + " " + Instant.now(fixed));

In real projects: inject a Clock

Code that calls LocalDate.now() or Instant.now() directly is hard to test: the result changes every run. Declare a Clock bean (Clock.systemUTC() in production) and inject it into services; call LocalDate.now(clock). In unit tests, pass Clock.fixed(...) and check coupon expiry, late fees or "valid for 7 days" rules on exact dates.

Rules

  • All java.time value types are immutable and thread-safe. Share them freely, including as static final constants.
  • Months are numbered 1–12 and days of the week are an enum (DayOfWeek.MONDAY). There is no zero-based month any more.
  • LocalDate, LocalTime and LocalDateTime carry no time zone. They are not moments in time and cannot be compared across servers or users.
  • now() uses the system clock and the JVM's default time zone. On a cloud server that is often UTC; on your laptop it is IST. Code that depends on the default behaves differently in each place.

Exceptions and edge cases

  • LocalDate.of(2026, 2, 30) throws DateTimeException: Invalid date 'FEBRUARY 30'.
  • Asking a type for something it does not hold throws UnsupportedTemporalTypeException: LocalDate.plus(1, ChronoUnit.HOURS) → Unsupported unit: Hours; Duration.between(dateA, dateB) with two LocalDates → Unsupported unit: Seconds; Instant.plus(1, ChronoUnit.MONTHS) → Unsupported unit: Months.
  • plusMonths clamps to the last valid day of the month (31 January + 1 month = 28 February), and a month added in a leap year gives 29 February where valid.
  • Period.between with the later date first gives negative values.
  • LocalDateTime.of(...) has no idea of daylight saving: it never "skips" or repeats an hour. Zoned types do.

Mistake: using LocalDateTime as a timestamp

LocalDateTime.of(2026, 10, 21, 10, 0) is only "10:00 on the wall clock". Interpreted in Kolkata it is 04:30Z; in UTC it is 10:00Z — a gap of 5.5 hours. Save "when it happened" as an Instant (or an OffsetDateTime), and use LocalDateTime only for local readings such as "the shop opens at 10:00".

Interview: "Why java.time? LocalDate vs LocalDateTime vs ZonedDateTime vs Instant? Period vs Duration?"

  • Old API: mutable, zero-based months, no date-only type, thread-unsafe SimpleDateFormat. New API: immutable, thread-safe, clear types, fluent.
  • LocalDate date only; LocalDateTime date and time without a zone (not a moment); ZonedDateTime adds a region zone and daylight-saving rules; Instant is a UTC timeline point.
  • Period is calendar-based (years, months, days); Duration is time-based (seconds and nanoseconds).
  • plusDays returns a new object — immutability.
  • Testing: inject a Clock.

Time zones, formatting, parsing and legacy Date conversion

Keep moments as Instant (UTC) in your code and database, convert to a ZoneId only to show a time to a person, format and parse with the thread-safe DateTimeFormatter, and convert legacy Date objects through Instant.

Zones and offsets

A ZoneId is a region such as Asia/Kolkata or America/New_York. It carries the history and daylight-saving rules of that region. A ZoneOffset is only a fixed distance from UTC, such as +05:30. India has one zone, Asia/Kolkata (IST, UTC+05:30, no daylight saving).

ZoneId kolkata = ZoneId.of("Asia/Kolkata");
ZonedDateTime ist = ZonedDateTime.of(2026, 10, 21, 18, 30, 0, 0, kolkata);

System.out.println(ist);
System.out.println(ist.withZoneSameInstant(ZoneOffset.UTC));
System.out.println(ist.withZoneSameInstant(ZoneId.of("America/New_York")));
System.out.println(ist.withZoneSameLocal(ZoneId.of("America/New_York")));
System.out.println(ist.toInstant());
System.out.println(ist.toOffsetDateTime());

Look at the third and fourth lines. withZoneSameInstant keeps the moment and changes the clock reading (18:30 in Kolkata is 09:00 in New York). withZoneSameLocal keeps the clock reading and therefore changes the moment — a different moment, 9.5 hours later. You almost always want withZoneSameInstant.

Daylight saving: gaps and overlaps

When clocks jump forward, some local times never exist (a gap). When they fall back, some happen twice (an overlap). ZonedDateTime handles both, and LocalDateTime cannot.

ZoneId ny = ZoneId.of("America/New_York");

// 8 March 2026: clocks jump from 02:00 to 03:00, so 02:30 does not exist
System.out.println(ZonedDateTime.of(2026, 3, 8, 2, 30, 0, 0, ny));

// 1 November 2026: 01:30 happens twice; the earlier one is the default
ZonedDateTime overlap = ZonedDateTime.of(2026, 11, 1, 1, 30, 0, 0, ny);
System.out.println(overlap + " | " + overlap.withLaterOffsetAtOverlap());

// "One day later" vs "24 hours later" across the 8 March change
ZonedDateTime before = ZonedDateTime.of(2026, 3, 7, 12, 0, 0, 0, ny);
System.out.println(before.plus(Period.ofDays(1)) + " | " + before.plus(Duration.ofHours(24)));
2026-03-08T03:30-04:00[America/New_York]
2026-11-01T01:30-04:00[America/New_York] | 2026-11-01T01:30-05:00[America/New_York]
2026-03-08T12:00-04:00[America/New_York] | 2026-03-08T13:00-04:00[America/New_York]

The gap time moved forward to 03:30. Period.ofDays(1) keeps the same clock time (12:00 the next day), while Duration.ofHours(24) adds exact time (13:00, because that day had only 23 hours). Choose the one that matches the business rule: "same time tomorrow" or "24 hours from now".

Edge case: lenient (SMART) parsing silently repairs impossible dates

By default a formatter uses the SMART resolver. LocalDate.parse("31/04/2026", dmy) does not fail — April has 30 days, so you get 2026-04-30. For input validation, switch to strict mode, which needs uuuu for the year:

DateTimeFormatter strict = DateTimeFormatter.ofPattern("dd/MM/uuuu")
        .withResolverStyle(ResolverStyle.STRICT);
System.out.println(LocalDate.parse("30/04/2026", strict));
LocalDate.parse("31/04/2026", strict);
2026-04-30
Exception in thread "main" java.time.format.DateTimeParseException:
    Text '31/04/2026' could not be parsed: Invalid date 'APRIL 31'

With yyyy instead of uuuu, strict mode fails even for valid dates, because year-of-era needs an era. Use uuuu with STRICT.

Mistakes in patterns: YYYY, mm and shared formatters

  • YYYY is the week-based year, not the calendar year. LocalDate.of(2025, 12, 29) formatted with YYYY-MM-dd and Locale.US gives 2026-12-29, because that week belongs to 2026. It looks fine for 360 days a year and fails around New Year. Use yyyy (or uuuu).
  • mm is minutes, MM is months. dd/mm/yyyy on a LocalDateTime prints the minutes where the month should be, without any error.
  • Using SimpleDateFormat as a shared static field. It is not thread-safe. Replace it with a static final DateTimeFormatter.

Storing and exchanging timestamps: use UTC

The rule used by most backend teams: store and pass around moments in UTC (Instant), and convert to a user's zone only at the edge, when you display them. UTC has no daylight saving, so every value is unambiguous, sorting and comparing just work, and moving the server to another region cannot change your data. Bugs of the "works on my laptop" kind usually come from code that relies on the default zone: the laptop runs in IST, the cloud server in UTC. Set the zone explicitly (-Duser.timezone=UTC for the JVM, and with Hibernate spring.jpa.properties.hibernate.jdbc.time_zone=UTC) and never call a method that silently uses the default.

Why the zone id for future appointments? Governments change daylight-saving rules. "10:00 on 5 November in Kolkata" must stay 10:00 local, so you keep the local time and the zone, and compute the instant when you need it. A moment that has already happened never changes, so UTC is enough.

Database details

  • PostgreSQL timestamptz stores UTC internally and shows values in the session's time zone. Plain timestamp stores no zone information at all.
  • MySQL TIMESTAMP is stored as UTC and converted using the session time zone, with a range that ends in 2038. DATETIME stores exactly what you give it, with no conversion and no zone.
  • With Spring Data JPA and a current Hibernate, entity fields of type LocalDate, LocalDateTime, Instant, OffsetDateTime and ZonedDateTime all work. Prefer Instant for audit columns such as createdAt.
  • Spring MVC parses LocalDate request parameters in ISO format by default; use @DateTimeFormat(pattern = "dd-MM-yyyy") on the parameter for another format.

Edge cases

  • A zone is needed to turn an Instant into a date. new GregorianCalendar(2026, 9, 21) is midnight in the JVM's zone. On a machine in India, calendar.toInstant().atZone(ZoneId.of("UTC")).toLocalDate() gives 2026-10-20, because midnight in Kolkata is 18:30 UTC the day before. Use the zone the value was created in, usually ZoneId.systemDefault().
  • Do not use three-letter zone ids. ZoneId.of("IST") throws ZoneRulesException: Unknown time-zone ID: IST (IST could mean India, Israel or Ireland). Use region ids: Asia/Kolkata.
  • Instant, OffsetDateTime and ZonedDateTime that denote the same moment are not all equals: two ZonedDateTime values with different zones are unequal even if they are the same instant. Compare with toInstant().equals(...), or isEqual.

Conventions

  • Store moments as Instant / timestamptz in UTC; convert to a ZoneId only for display.
  • Exchange text in ISO-8601 (2026-10-21T13:00:00Z); let the front end format it for the user's locale.
  • Always give formatters an explicit Locale and keep them as static final constants.
  • Use region ids (Asia/Kolkata), never abbreviations (IST).
  • Do not use Date, Calendar or SimpleDateFormat in new code.

Interview: "How do you handle time zones in a backend? What do you store in the database?"

  • Store UTC (Instant, timestamptz); convert to the user's ZoneId at the edge; use ISO-8601 in APIs.
  • ZoneId (region with rules) vs ZoneOffset (fixed). withZoneSameInstant vs withZoneSameLocal.
  • Never depend on the server's default zone; set it explicitly and inject a Clock.
  • Parsing: DateTimeParseException; strict resolver for validation. Formatting: yyyy not YYYY; MM vs mm.
  • DateTimeFormatter is thread-safe; SimpleDateFormat is not.
  • Legacy: Date.toInstant() and Date.from(instant).

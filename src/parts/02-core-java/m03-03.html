throw vs throws

throw is a statement that raises one exception object right now; throws is a clause in a method signature that tells callers which checked exceptions the method may let escape.

The two keywords differ by one letter, and beginners mix them up all the time. Keep them apart with one idea: throw does something while the program runs, but throws only describes something — for the compiler and for the people who call your method.

throw: raising an exception

A throw statement takes one exception object and starts the unwinding process from What an exception is: the current method stops at once, and Java looks for a matching catch block in the callers. Usually you create the object on the same line: throw new IllegalArgumentException("message"). The expression after throw can also be a variable that holds an exception, for example one you caught a moment ago.

throws: declaring what can escape

A throws clause sits in a method or constructor declaration, after the parameter list. It lists the checked exception types that the method does not handle itself, so they may come out of it. The compiler uses the list at every call site: the caller must catch those types or declare them in its own throws clause (the catch-or-declare rule from Checked vs unchecked exceptions).

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class ThrowsDemo {

    // Unchecked exceptions need no throws clause
    static int parsePort(String text) {
        int port = Integer.parseInt(text.trim());
        if (port < 1 || port > 65535) {
            throw new IllegalArgumentException("Port must be 1-65535 but was " + port);
        }
        return port;
    }

    // IOException is checked: the method must declare it
    static int readPort(Path file) throws IOException {
        String text = Files.readString(file);
        return parsePort(text);
    }

    public static void main(String[] args) throws IOException {
        Path dir = Files.createTempDirectory("ports-");
        Path good = Files.writeString(dir.resolve("good.txt"), "8080");
        Path bad = Files.writeString(dir.resolve("bad.txt"), "70000");
        Path missing = dir.resolve("missing.txt");

        for (Path file : new Path[] {good, bad, missing}) {
            String name = file.getFileName().toString();
            try {
                System.out.println(name + " -> port " + readPort(file));
            } catch (IOException e) {
                System.out.println(name + " -> cannot read (" + e.getClass().getSimpleName() + ")");
            } catch (IllegalArgumentException e) {
                System.out.println(name + " -> invalid: " + e.getMessage());
            }
        }
    }
}
good.txt -> port 8080
bad.txt -> invalid: Port must be 1-65535 but was 70000
missing.txt -> cannot read (NoSuchFileException)

Read the example in two layers. parsePort contains a throw statement, but it needs no throws clause because IllegalArgumentException is unchecked. readPort contains no throw statement at all, yet it has a throws clause: the exception comes from inside Files.readString, and readPort chooses to pass it on instead of handling it. So throws is about what can come out of a method, no matter who threw it. main declares throws IOException as well, because createTempDirectory and writeString throw it outside the try block.

Catch it, declare it or wrap it?

Every time a checked exception can reach your code you have three choices. The flowchart gives the usual order of thinking.

Catch only when you can do something useful. Declare when the caller is the right place to decide — for a file-reading method, the caller knows whether a missing file is fatal or just means "use the defaults". Wrap (next article) when the exception type would leak an implementation detail upwards.

Rules for the throw statement

  • The expression must be a Throwable. throw "error"; does not compile.
  • A throw ends the normal flow, so a statement right after it is unreachable and fails with error: unreachable statement.
  • If you throw a checked exception, the method must catch it or declare it. Throwing new IOException("x") in a method without a throws clause gives unreported exception IOException; must be caught or declared to be thrown.
  • throw is a statement, not an expression, so you cannot use it in the middle of a ternary a ? b : throw ....

Edge cases of throw and throws

  • throw in a switch expression. An arrow arm may be a throw statement. This is the clean way to reject unknown values: 
    String label = switch (status) {
    case "PAID" -> "Paid";
    case "PENDING" -> "Pending";
    default -> throw new IllegalArgumentException("Unknown status: " + status);
};
  • throw null compiles, because null can be assigned to any reference type. At run time it throws a NullPointerException instead (message: Cannot throw exception because "null" is null).
  • A throws clause may name unchecked exceptions (throws IllegalStateException) and checked types the body never throws. The compiler accepts both. This is useful on interface and abstract methods, where implementations may need to throw something the interface method itself does not.
  • The opposite is an error: a catch for a checked exception that the try block cannot throw is a compile error (see the second compiler rule in Checked vs unchecked).
  • Constructors can have a throws clause too. Throwing from a constructor means the object is never created.

The stack trace shows where the exception was created

The trace is recorded when the exception object is constructed (inside the Throwable constructor), not when throw runs. Most of the time both happen on the same line, so you never notice. They differ when you build an exception in one place and throw it in another:

public class ThrowLocation {
    public static void main(String[] args) {
        RuntimeException saved = new IllegalStateException("created early");
        try {
            throwIt(saved);
        } catch (RuntimeException e) {
            System.out.println("trace starts at: " + e.getStackTrace()[0]);
            System.out.println("same object: " + (e == saved));
        }
    }

    static void throwIt(RuntimeException e) {
        throw e;
    }
}
trace starts at: ThrowLocation.main(ThrowLocation.java:3)
same object: true

The trace points at line 3, where the object was created, not at line 12, where it was thrown. Never keep an exception in a constant to throw it again later: every throw would show the same stale trace and mislead whoever reads the log. Always write throw new ... at the place where the problem is detected.

Common mistakes

Mistake: creating an exception and forgetting to throw it

new IllegalStateException("never thrown"); compiles, runs and does nothing: the object is created and immediately thrown away, and execution continues as if nothing was wrong. The method prints "finished normally" even though you meant to fail. Write throw new IllegalStateException(...). Most IDEs flag the unused result.

Mistake: writing throw where throws belongs

void save() throw IOException { ... } fails with '{' or ';' expected — the parser does not expect the keyword throw in a declaration. The reverse (throws new IOException() in a body) is a syntax error as well. Declarations take throws plus a class name; bodies take throw plus an object.

Wrong: throws Exception hides what can fail

public Order load(long id) throws Exception {
    // callers must now catch the broadest type
    // and cannot tell what can really go wrong
}

Right: declare the specific type

/**
 * @throws IOException if the order file cannot be read
 */
public Order load(long id) throws IOException {
    // callers see exactly what they must handle
}

Conventions

  • Declare the narrowest checked types in throws; never throws Exception in application code (it is fine in main of a quick demo).
  • Document every exception a caller might care about, checked or not, with Javadoc @throws.
  • Throw as early as you can detect the problem (validate arguments at the top of the method), and always create the exception at the throw site.
  • Prefer a standard exception when it says exactly what happened (IllegalArgumentException, IllegalStateException), and a custom one when callers need to react to it differently (see custom exceptions).

Interview: "What is the difference between throw and throws?"

  • throw is a statement that raises one exception object at run time; throws is a clause in a method signature that declares the checked exceptions it may pass to its caller — checked at compile time.
  • You can throw only one exception at a time but list many in throws.
  • Follow-ups: Can a method have throws without throw? Yes — it may just pass on what a called method throws. Can you throw a checked exception without throws? Only if you catch it in the same method.
  • Bonus point: the stack trace is captured when the exception is created, not when it is thrown.

Rethrowing, wrapping and exception chaining

When you cannot fully handle an exception, rethrow it unchanged or wrap it in a more suitable exception that keeps the original as its cause — the chain of causes is what you read as "Caused by" in a log.

A catch block does not have to be the end of the story. Often the right move is to do a little work and pass the failure on. There are three reasons to do that:

  • Undo or clean up first — release a reserved seat, roll back a half-finished change — and then let the caller know that the operation failed.
  • Translate the exception to the level of abstraction of the caller. An OrderService should not make its callers deal with SQLException: that tells them how the data is stored, which is none of their business.
  • Add context that the low-level exception cannot know: which order, which file, which user.

Plain rethrow: throw e

Throwing the caught exception again keeps the very same object, so the original type, message and stack trace stay intact. Use it when you only need to react to the failure.

void checkout(Order order) throws PaymentException {
    inventory.reserve(order);
    try {
        payments.charge(order);
    } catch (PaymentException e) {
        inventory.release(order);   // undo the partial work
        throw e;                    // the caller still sees the original failure
    }
}

Precise rethrow (Java 7)

Suppose you catch Exception to run some cleanup, and then rethrow it. Before Java 7 the method then had to declare throws Exception. Since Java 7 the compiler is smarter: if the catch parameter is never reassigned (effectively final), it knows the rethrown exception can only be what the try block can throw.

import java.io.IOException;

public class PreciseRethrow {

    static void risky(boolean io) throws IOException {
        if (io) {
            throw new IOException("disk problem");
        }
    }

    // Java 7+: only IOException can arrive in the catch block,
    // so the method may declare just "throws IOException"
    static void process() throws IOException {
        try {
            risky(true);
        } catch (Exception e) {
            System.out.println("cleaning up after: " + e.getMessage());
            throw e;           // precise rethrow
        }
    }

    public static void main(String[] args) {
        try {
            process();
        } catch (IOException e) {
            System.out.println("main got " + e);
        }
    }
}
cleaning up after: disk problem
main got java.io.IOException: disk problem

If you assign something else to e before the throw e, the precise analysis is switched off and the compiler asks for throws Exception again. Unchecked exceptions never need declaring, so they pass through any rethrow.

Wrapping with a cause: exception chaining

To wrap an exception, create a new one and pass the original as its cause. The result is an exception chain: the outer exception says what the operation could not do, and the cause says why. Most exception classes offer these constructors:

ConstructorMessageCause
X()nullnone
X(String message)your textnone
X(String message, Throwable cause)your textthe original
X(Throwable cause)cause.toString(), such as java.io.IOException: disk fullthe original

Prefer the (message, cause) form: your message adds the context, and the cause keeps the detail.

import java.sql.SQLException;

public class ChainDemo {

    static class OrderRepository {
        void save(int orderId) throws SQLException {
            // pretend the database rejected the insert
            throw new SQLException("duplicate key value violates unique constraint \"orders_pkey\"",
                    "23505");
        }
    }

    static class OrderService {
        private final OrderRepository repository = new OrderRepository();

        void placeOrder(int orderId) {
            try {
                repository.save(orderId);
            } catch (SQLException e) {
                // translate: the service layer should not leak SQLException
                throw new IllegalStateException("Could not save order " + orderId, e);
            }
        }
    }

    public static void main(String[] args) {
        try {
            new OrderService().placeOrder(101);
        } catch (IllegalStateException e) {
            // walk the chain from the outermost exception to the root cause
            for (Throwable t = e; t != null; t = t.getCause()) {
                System.out.println(t.getClass().getSimpleName() + ": " + t.getMessage());
            }
            e.printStackTrace(System.out);
        }
    }
}

The loop in main uses getCause(), which returns the wrapped exception or null at the end of the chain. The last exception it prints is the root cause. The stack trace prints the whole chain for you: the top part is the new IllegalStateException with its own frames, and the Caused by: part holds the original SQLException, including the line in save where it was created. If you had not passed e as the cause, that second part would be gone and nobody could tell what the database complained about. initCause: for exceptions without a cause constructor

Some old exception classes have no constructor that accepts a cause — NumberFormatException and IndexOutOfBoundsException are examples. For those, initCause(Throwable) sets it after creation. It works at most once, and not at all if a constructor already set the cause (even when that cause was null).

import java.io.IOException;

public class InitCauseDemo {
    public static void main(String[] args) {
        // NumberFormatException has no constructor that takes a cause
        NumberFormatException nfe = new NumberFormatException("Bad quantity in row 7");
        nfe.initCause(new IOException("stream closed"));
        System.out.println("cause = " + nfe.getCause());

        try {
            nfe.initCause(new IOException("again"));        // second call
        } catch (IllegalStateException e) {
            System.out.println("second initCause -> " + e.getMessage());
        }

        Exception e2 = new Exception("with cause", new IOException("x"));
        try {
            e2.initCause(new IOException("y"));             // constructor already set it
        } catch (IllegalStateException e) {
            System.out.println("after constructor -> " + e.getMessage());
        }

        Exception e3 = new Exception(new IOException("disk full"));
        System.out.println("message when only a cause is given: " + e3.getMessage());
    }
}
cause = java.io.IOException: stream closed
second initCause -> Can't overwrite cause with java.io.IOException: again
after constructor -> Can't overwrite cause with java.io.IOException: y
message when only a cause is given: java.io.IOException: disk full

Wrapping a checked exception in an unchecked one

When a method cannot declare a checked exception — because it overrides a method without a throws clause, because it is a lambda, or because you do not want the type to leak — wrap it in an unchecked exception. For I/O the JDK provides java.io.UncheckedIOException; its constructors accept only an IOException as the cause. For other checked exceptions use IllegalStateException or one of your own runtime exceptions.

import java.io.IOException;
import java.io.UncheckedIOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class WrapIo {

    static String loadConfig(String file) {
        try {
            return Files.readString(Path.of(file));
        } catch (IOException e) {
            throw new UncheckedIOException("Cannot load config " + file, e);
        }
    }

    static void startApp() {
        String config = loadConfig("missing.properties");
        System.out.println(config);
    }

    public static void main(String[] args) {
        startApp();
    }
}

Let your own exceptions pass through

A very common mistake is a catch-all wrapper that also swallows exceptions your callers need to recognise. If the controller layer wants to answer "insufficient balance" with a clear message, a generic wrapper in the service layer ruins it.

Wrong: wraps everything, even domain exceptions

public void transfer(String from, String to, BigDecimal amount) {
    try {
        ledger.move(from, to, amount);
    } catch (Exception e) {
        throw new RuntimeException("Transfer failed", e);
    }   // InsufficientBalanceException is now hidden inside a RuntimeException
}

Right: translate only the technical exception

public void transfer(String from, String to, BigDecimal amount) {
    try {
        ledger.move(from, to, amount);
    } catch (SQLException e) {
        throw new TransferFailedException("Transfer " + from + " -> " + to + " failed", e);
    }   // InsufficientBalanceException is unchecked and flows through untouched
}

Mistake: wrapping again and again without adding anything

If every layer catches an exception and wraps it with the same message, the log shows a ladder of six "Caused by" sections that all say "Operation failed". Wrap only when you change the abstraction (SQL to domain) or add useful information (an id, a file name). Otherwise let the exception travel up unchanged.

Conventions

  • Always keep the cause: new X("context", e), never new X(e.getMessage()).
  • Write the message for the new level (what you were trying to do and with which data); let the cause carry the technical detail.
  • Translate at layer boundaries: repository to service to controller. Inside one layer, let exceptions flow.
  • Do not log and rethrow at every layer. Log once, where the exception is finally handled (see best practices).
  • To find the root cause in code, loop on getCause(). Libraries such as Spring (NestedExceptionUtils.getRootCause) and Apache Commons Lang (ExceptionUtils.getRootCause) already provide helpers.

Interview: "What is exception chaining?" / "throw e vs throw new X(e)"

  • Chaining means attaching the original exception as the cause of a new one, via the (message, cause) constructor or initCause. getCause() reads it, and the stack trace prints it as "Caused by".
  • throw e rethrows the same object — same type, same trace. throw new X(msg, e) creates a new exception (new type, new message, new trace) and keeps the old one inside.
  • Why wrap: translate low-level exceptions to the caller's level, add context, turn a checked exception into an unchecked one — without losing the root cause.
  • Precise rethrow (Java 7): rethrowing a caught Exception that is effectively final lets the method declare only the checked types the try block can really throw.

Writing custom exceptions

A custom exception is a small class that extends Exception (checked) or RuntimeException (unchecked), has a specific name ending in Exception, and carries the data a caller needs to react.

The JDK exceptions describe technical problems. Your application has its own failures: an account has too little money, an order does not exist, a coupon has expired. You could report these with IllegalStateException("insufficient balance"), but then a caller can only tell them apart by reading the message text, which is fragile. A custom exception gives the failure a name, lets callers catch it separately, and can carry data such as the account id and the missing amount.

Create one only when a standard exception does not fit

If IllegalArgumentException, IllegalStateException or NoSuchElementException says exactly what went wrong, use it. Create a custom type when callers will handle that failure differently from others (show a specific message, retry, map it to an HTTP status) or when the failure carries data.

The smallest custom exception

public class OrderNotFoundException extends RuntimeException {

    public OrderNotFoundException(String message) {
        super(message);
    }
}

That is all it takes: extend a base class and pass the message to super. Use it with throw new OrderNotFoundException("Order 1042 not found"). The base class decides whether the compiler checks it, see below.

Constructors to provide

The JDK's own exceptions follow a pattern, and callers expect the same from yours. Provide the constructors that make sense:

ConstructorProvide it when
X(String message)Almost always — the basic case
X(String message, Throwable cause)The exception wraps another one (see chaining). Always provide it for wrapper exceptions
X(Throwable cause)Optional; handy for pure wrappers
X()Rarely: an exception without a message is hard to understand in a log
Custom, such as X(String accountId, BigDecimal balance, ...)The exception carries data: build the message from the data inside the constructor, so every throw site gets the same good message

Adding fields: InsufficientBalanceException

This is the roadmap example. The exception stores what a caller needs to react: which account, how much it has, how much was asked. A user interface can then say "You are short by ₹500" without parsing a message.

import java.math.BigDecimal;

public class InsufficientBalanceException extends RuntimeException {
    private static final long serialVersionUID = 1L;

    private final String accountId;
    private final BigDecimal balance;
    private final BigDecimal requested;

    public InsufficientBalanceException(String accountId, BigDecimal balance, BigDecimal requested) {
        super("Account " + accountId + " has " + balance + " but " + requested + " was requested");
        this.accountId = accountId;
        this.balance = balance;
        this.requested = requested;
    }

    public String getAccountId() {
        return accountId;
    }

    public BigDecimal getBalance() {
        return balance;
    }

    public BigDecimal getRequested() {
        return requested;
    }

    public BigDecimal getShortfall() {
        return requested.subtract(balance);
    }
}
import java.math.BigDecimal;
import java.util.Objects;

public class Account {
    private final String id;
    private BigDecimal balance;

    public Account(String id, BigDecimal openingBalance) {
        this.id = Objects.requireNonNull(id, "id must not be null");
        if (openingBalance.signum() < 0) {
            throw new IllegalArgumentException("Opening balance cannot be negative: " + openingBalance);
        }
        this.balance = openingBalance;
    }

    public void withdraw(BigDecimal amount) {
        if (amount.signum() <= 0) {
            throw new IllegalArgumentException("Amount must be positive: " + amount);
        }
        if (amount.compareTo(balance) > 0) {
            throw new InsufficientBalanceException(id, balance, amount);
        }
        balance = balance.subtract(amount);
    }

    public String getId() {
        return id;
    }

    public BigDecimal getBalance() {
        return balance;
    }
}
import java.math.BigDecimal;

public class BankApp {
    public static void main(String[] args) {
        Account account = new Account("ACC-1001", new BigDecimal("5000.00"));
        String[] requests = {"1500.00", "4000.00", "-10"};

        for (String text : requests) {
            BigDecimal amount = new BigDecimal(text);
            try {
                account.withdraw(amount);
                System.out.println("Withdrew " + amount + ", balance now " + account.getBalance());
            } catch (InsufficientBalanceException e) {
                System.out.println("Declined: short by " + e.getShortfall());
                System.out.println("  detail: " + e.getMessage());
            } catch (IllegalArgumentException e) {
                System.out.println("Invalid request: " + e.getMessage());
            }
        }
    }
}
Withdrew 1500.00, balance now 3500.00
Declined: short by 500.00
  detail: Account ACC-1001 has 3500.00 but 4000.00 was requested
Invalid request: Amount must be positive: -10

Notice the two different failures. A negative amount is a bug in the caller, so the standard IllegalArgumentException fits. Too little money is a business situation that the caller must handle, so it gets its own type, and main reacts to it differently from the other one. Also notice that the money values are BigDecimal, never double.

Checked or unchecked?

The choice is a single word after extends, but it changes how every caller works. Compare the two versions of the same exception:

public class InsufficientBalanceException extends Exception {        // checked
    // ... same fields and constructor ...
}

public void withdraw(BigDecimal amount) throws InsufficientBalanceException {
    // ...
}

// every caller must now catch it or declare it
try {
    account.withdraw(amount);
} catch (InsufficientBalanceException e) {
    // ...
}
Extend Exception (checked)Extend RuntimeException (unchecked)
CompilerForces callers to catch or declareNo forcing
SignaturesEvery method on the way up needs throwsUnchanged
Lambdas and streamsAwkward: cannot be thrown from a FunctionWorks everywhere
Spring @TransactionalDoes not roll back by defaultRolls back by default

Modern application code leans towards unchecked for business exceptions: the failure travels up to one central handler that turns it into a response, and no signature is polluted. Choose checked when you write a library or API where ignoring the failure would be a real bug and the caller can recover (retry, pick another option). When unsure, go unchecked.

Real project: why the transaction rule matters

In Spring, a method annotated with @Transactional rolls back the database changes when a RuntimeException or Error leaves it, but commits when a checked exception leaves it, unless you add rollbackFor. A checked InsufficientBalanceException thrown after the debit would silently commit half a transfer. This is one of the main reasons Spring projects use unchecked business exceptions.

A base exception and error codes

In a real application, give all exceptions of one area a common parent, and add a machine-readable error code. The API layer can then catch the parent once, and clients get a stable code instead of a message that may change.

public enum ErrorCode {
    INSUFFICIENT_BALANCE,
    ACCOUNT_NOT_FOUND,
    ACCOUNT_FROZEN
}
public abstract class BankException extends RuntimeException {
    private static final long serialVersionUID = 1L;

    private final ErrorCode code;

    protected BankException(ErrorCode code, String message) {
        super(message);
        this.code = code;
    }

    protected BankException(ErrorCode code, String message, Throwable cause) {
        super(message, cause);
        this.code = code;
    }

    public ErrorCode getCode() {
        return code;
    }
}
public class AccountNotFoundException extends BankException {
    private static final long serialVersionUID = 1L;

    public AccountNotFoundException(String accountId) {
        super(ErrorCode.ACCOUNT_NOT_FOUND, "No account with id " + accountId);
    }
}

InsufficientBalanceException would now extend BankException and pass ErrorCode.INSUFFICIENT_BALANCE to super. A single catch block at the edge of the application handles all of them:

try {
    transferService.transfer(from, to, amount);
} catch (BankException e) {
    System.out.println(e.getCode() + " -> " + e.getMessage());
}
ACCOUNT_NOT_FOUND -> No account with id ACC-9
INSUFFICIENT_BALANCE -> Account ACC-1 has 10 but 25 was requested

Naming, packages and structure

  • End the name with Exception (OrderNotFoundException). Never Error — that suggests a JVM Error.
  • Be specific. MyException, CustomException and AppException say nothing. Name the failure, not the layer.
  • Keep the hierarchy shallow: one base class per area at most. Deep trees of exception classes are hard to maintain.
  • Put them near the code that throws them (the same package as the domain class, or an exception sub-package) and make them public when callers use them.

Rules for custom exception classes

  • An exception class cannot be generic: class Failure<T> extends Exception fails with a generic class may not extend java.lang.Throwable. The runtime cannot tell Failure<String> from Failure<Integer> in a catch block (type erasure, Module 4).
  • A record cannot be an exception, because records cannot extend another class.
  • Throwable implements Serializable, so declare private static final long serialVersionUID = 1L;. Without it, javac -Xlint:serial warns: serializable class X has no definition of serialVersionUID. Keep fields serializable or mark them transient.

Edge case: exceptions without a stack trace

Creating an exception is relatively expensive, because the JVM walks the stack to fill in the trace. The protected constructor super(message, cause, false, false) turns off suppression and the writable stack trace. A few high-volume frameworks use this for exceptions that work as control signals. For normal business exceptions do not do this — the trace is what you read in the log when something goes wrong.

Mistakes with custom exceptions

  • Everything extends Exception. Every caller up the chain gets a throws clause, and people start writing throws Exception or empty catch blocks.
  • Dropping the cause in wrapper exceptions — give wrappers the (message, cause) constructor and use it.
  • Sensitive data in the message. Messages end up in logs and sometimes in API responses. Never put passwords, tokens, OTPs or full card numbers in them.
  • Heavy fields: storing a whole entity or a request object inside the exception keeps it alive and may not be serializable. Store ids and amounts.
  • Business logic inside the exception class. It should only describe the failure.

Interview: "How do you create a custom exception?"

  • Extend Exception for a checked exception or RuntimeException for an unchecked one; end the name with Exception; call super(message) or super(message, cause); add serialVersionUID.
  • Add fields (an id, an error code) so callers can react without parsing messages.
  • Explain checked vs unchecked and your default: unchecked for business rules in Spring apps (including the @Transactional rollback rule), checked for recoverable failures in libraries.
  • Mention a small hierarchy with a base class and error codes, and handling it centrally.

Overriding methods and exceptions

An overriding method may throw fewer or narrower checked exceptions than the method it overrides, but never new or broader ones; unchecked exceptions are always allowed.

When a subclass overrides a method, the compiler checks the throws clause too, not only the name and parameters. The reason is simple. Code that calls a method through the parent type has already decided how to handle the parent's checked exceptions. If a child could suddenly throw a new checked exception, that code would break at run time without any warning. This is the Liskov substitution principle: wherever the parent type is used, a child must be usable without surprises (see System Design · Module 1).

The rule

For every checked exception that the overriding method declares, the overridden method must declare the same type or a superclass of it. The child's list can be shorter or empty, never wider. Unchecked exceptions (RuntimeException, Error and their subclasses) are not part of this check.

The message is the same for an unrelated type such as SQLException and for any checked exception added to a method whose parent declares none. When a class implements an interface method, the wording changes only slightly. For example, public void run() throws Exception inside a class that implements Runnable gives run() in Task cannot implement run() in Runnable and the same last line. That is also why you cannot call Thread.sleep() in a Runnable lambda without a try/catch: Runnable.run() declares nothing. Callable.call(), in contrast, declares throws Exception, so a Callable lambda may throw any checked exception.

The reference type decides what the caller must handle

The compiler checks a call against the declared type of the variable, not the object behind it. So the same object can need a try/catch through one variable and none through another:

class Reader2 {
    void load() throws IOException { }
}

class CachedReader2 extends Reader2 {
    @Override
    void load() { }                   // declares nothing
}

// in main (which has no throws clause):
Reader2 viaParent = new CachedReader2();
viaParent.load();     // error: unreported exception IOException; must be caught or declared

Here Reader2.load() declares IOException, so the call through Reader2 must handle it, even though CachedReader2.load() throws nothing. With a variable of type CachedReader2 the same call compiles without any handling. This is why coding against interfaces (List, not ArrayList) means living with the interface's exception contract.

Constructors, static methods and overloading

  • Constructors are not overridden, but there is a related rule. If a superclass constructor declares a checked exception, every subclass constructor must declare it too — it cannot be caught, because super(...) must be the first statement. A subclass that relies on the implicit default constructor fails with unreported exception IOException in default constructor; write an explicit constructor with a throws clause.
  • Static methods are hidden, not overridden, but the compiler applies the same throws rule to them.
  • Overloaded methods (same name, different parameters) are different methods, so they may declare any exceptions. The rule is only for overriding and implementing.
  • Generic throws: a method can declare a type variable, as Optional.orElseThrow(Supplier<? extends X>) does with throws X. The caller decides the type, which keeps the checked-exception rules intact.

Rule: an override may only make the exception contract narrower

Same type, a subclass, nothing at all, or any unchecked exception. If you need to throw a broader checked exception from an override, catch it and wrap it in an unchecked exception (see rethrowing and chaining), or change the parent method's signature — which breaks all of its callers.

Design tip: implement close() without a throws clause

AutoCloseable.close() declares throws Exception. Your own class may override it as public void close() with no throws clause (or with something narrower), as the earlier try-with-resources article showed. Callers that use your class by its own type are then spared a useless catch block.

Interview: "Rules for overriding with exceptions"

  • The overriding method can throw the same checked exceptions, subclasses of them, or none. It cannot throw new or broader checked exceptions.
  • It can throw any unchecked exception, whatever the parent declares.
  • Give the reason: the caller compiled against the parent's contract (Liskov substitution).
  • Typical trick questions: Parent throws IOException; can the child throw FileNotFoundException? Yes. Can it throw Exception? No. Parent declares nothing; can the child throw ArithmeticException? Yes, it is unchecked.

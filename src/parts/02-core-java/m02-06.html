Interfaces: default, static and private methods

An interface is a pure contract: a list of methods a class promises to provide. A class can implement many interfaces, and since Java 8 an interface can also carry default, static and (Java 9) private methods with bodies.

An interface says what a type can do and nothing about how. A class that implements the interface signs the contract and must provide every abstract method. Interfaces are how Java gets "multiple inheritance of type": one class can implement many interfaces even though it can extend only one class. They are the backbone of abstraction in real projects: List, Map, Comparable, Runnable and every Spring Data repository are interfaces.

Syntax and a first example

interface PaymentMethod {
    int MAX_RETRIES = 3;                          // implicitly public static final

    boolean pay(long amountInPaise);              // implicitly public abstract

    default String receipt(long amountInPaise) {  // default method: has a body
        return "Paid Rs " + amountInPaise / 100.0 + " via " + name();
    }

    String name();

    static PaymentMethod upi(String vpa) {        // static method: called on the interface
        return new Upi(vpa);
    }
}

class Upi implements PaymentMethod {
    private final String vpa;
    Upi(String vpa) { this.vpa = vpa; }

    @Override public boolean pay(long amountInPaise) {   // must be public
        System.out.println("Debiting " + amountInPaise + " paise from " + vpa);
        return true;
    }
    @Override public String name() { return "UPI(" + vpa + ")"; }
}

public class PaymentDemo {
    public static void main(String[] args) {
        PaymentMethod m = PaymentMethod.upi("asha@bank");   // static call on the interface
        if (m.pay(49900)) {
            System.out.println(m.receipt(49900));           // inherited default method
        }
        System.out.println(PaymentMethod.MAX_RETRIES);
    }
}

Why default methods exist

Before Java 8, adding a method to an interface broke every class that implemented it. When the Java team wanted list.stream(), list.forEach(…) and map.getOrDefault(…), they could not touch thousands of implementations, including yours. A default method gave them a body to fall back on. So Collection.stream() and Iterable.forEach() are default methods. This is called interface evolution. Use default methods for the same reason: to add a method to a published interface without breaking implementers, or to give a convenient method built from the abstract ones, as receipt() does above.

Static and private methods

A static method belongs to the interface itself, so it is a natural home for factories and helpers: List.of(…), Comparator.comparing(…), Map.entry(…). It is not inherited: you call PaymentMethod.upi(…), never m.upi(…) or Upi.upi(…). A private method (Java 9) lets two default methods share code without making that helper part of the public contract.

interface AuditLog {
    void write(String line);

    default void info(String msg)  { write(format("INFO", msg)); }
    default void error(String msg) { write(format("ERROR", msg)); }

    private String format(String level, String msg) {   // hidden helper, Java 9+
        return "[" + level + "] " + msg;
    }
}

The diamond conflict with default methods

If a class implements two interfaces that both offer a default method with the same signature, which one should it inherit? Java uses three resolution rules, in this order:

  1. A class always wins. A method declared in the class or inherited from a superclass beats any interface default.
  2. The more specific interface wins. If interface B extends A and both define the default, B's version is used.
  3. Otherwise, you must decide. The compiler reports an error and the class has to override the method. Inside it you can pick one with InterfaceName.super.method().
interface Camera { default String start() { return "camera on"; } }
interface Phone  { default String start() { return "phone on"; } }

// Without the override: "types Camera and Phone are incompatible;
// class CameraPhone inherits unrelated defaults for start()"
class CameraPhone implements Camera, Phone {
    @Override public String start() {
        return Camera.super.start() + " + " + Phone.super.start();   // choose explicitly
    }
}

public class Diamond {
    public static void main(String[] args) {
        System.out.println(new CameraPhone().start());
    }
}
camera on + phone on

This is why Java allows multiple inheritance of type and behaviour from interfaces but not of state. Interfaces have no instance fields, so the classic "which copy of the field?" part of the diamond problem never appears (inheritance).

Interfaces extending interfaces

An interface can extend one or more interfaces: interface Savings extends Account, Interest { … }. A class that implements Savings must supply everything from all of them. Remember the vocabulary: a class extends a class, a class implements an interface, and an interface extends interfaces.

Functional interfaces

A functional interface has exactly one abstract method (default and static methods do not count, nor do abstract methods that repeat Object methods such as equals). It can be implemented with a lambda: Runnable r = () -> System.out.println("hi");. Add @FunctionalInterface to make the compiler check the rule. Examples: Runnable, Callable, Comparator, Comparable and the java.util.function types such as Function and Predicate. Lambdas and these types get their own module: Module 5.

Marker interfaces

A marker interface has no methods. Implementing it only tags the class, and some other code checks the tag. java.io.Serializable says "this object may be converted to bytes", Cloneable says "Object.clone() may copy me" (clone), and RandomAccess says "indexed access is fast". Today annotations do the same job in most new code (@Entity, @Service), but the JDK keeps its markers.

Rules to remember

  • Interface methods are public. Implementing one with weaker access (void pay() without public) is a compile error: "attempting to assign weaker access privileges".
  • Interface fields are constants. You cannot reassign MAX_RETRIES.
  • You cannot instantiate an interface with new (an anonymous class or a lambda is allowed), and interfaces have no constructors.
  • A default method cannot override equals, hashCode or toString of Object. The compiler rejects it, because a class always inherits those from Object and "the class wins".
  • An interface method cannot be protected or final.
  • A class that does not implement all abstract methods must be declared abstract.

Edge cases

  • Static interface methods are not inherited by implementing classes or sub-interfaces. Only Iface.method() works.
  • Same constant name in two interfaces makes an unqualified use ambiguous: write A.X or B.X.
  • Empty and sealed interfaces. An interface with no methods is legal (a marker). A sealed interface limits who may implement it (sealed classes).
  • Interface constants anti-pattern. Putting only constants in an interface and implementing it "to get the names" is considered bad design. Use a final class or an enum.

Conventions

  • Name interfaces after a capability or a role: Comparable, PaymentMethod, OrderRepository. Do not prefix with I (IPayment is a C# habit).
  • When the implementation is single, name it plainly (JpaOrderRepository), or avoid the Impl suffix if a better name exists.
  • Keep interfaces small and focused. Many small contracts are easier to implement and to fake in tests than one large one.
  • Use default methods sparingly: convenience built from abstract methods, or evolution of an old interface. Do not build a class hierarchy out of them.

Mistake: forgetting public on the implementation

Wrong: weaker access

class Upi implements PaymentMethod {
    boolean pay(long p) { return true; }   // error: weaker access privileges
}

Right

class Upi implements PaymentMethod {
    @Override public boolean pay(long p) { return true; }
}

In a real Spring Boot project

Controllers depend on service interfaces, services on repository interfaces, and Spring picks the implementation to inject. Spring Data repositories are interfaces with no implementing class that you write. Strategy-style code ("pick the right PaymentMethod for this request") is a map of interface implementations. Tests replace real implementations with Mockito mocks of the interface.

Interview: interface questions

  • Why default methods? To add methods to existing interfaces without breaking implementers; this enabled the Streams API on old collections.
  • What if two interfaces have the same default method? The class must override it; it may call A.super.m(). A class method beats any default.
  • Can an interface have a constructor or instance variable? No. Fields are always public static final.
  • Can an interface have a main method? Yes, as a static method; it can be run.
  • What is a functional interface? A marker interface? One abstract method (lambda target) / no methods (a tag).

Abstract class vs interface: which to choose

Use an interface to describe a capability that unrelated classes can share; use an abstract class when closely related classes share state and code. When in doubt, start with an interface, and combine both with a skeleton class if you need shared code.

Since Java 8 the two look more alike, because both can hold method bodies. The real differences are about state, constructors and inheritance count. This table is the one to learn for interviews.

When to use which

Choose an interface when

  • Unrelated classes should share a capability (Comparable, Serializable, Notifier).
  • You want callers to depend on a contract, with many possible or future implementations.
  • A class already has a superclass (frameworks often force it) and still needs the new type.
  • You want lambdas or easy mocks in tests.

Choose an abstract class when

  • Subclasses are closely related and share fields and real code (Shape keeps name).
  • You need a constructor, non-public members or protected helpers.
  • You want a Template Method with final steps (abstract classes).
  • You need to control how the state is initialised for all subclasses.

The best of both: interface plus skeleton class

A common design is to publish an interface and also offer an abstract skeleton implementation that does the boring part. The JDK does this with List and AbstractList, Map and AbstractMap. Users who just need a list-like class extend the skeleton and write two methods. Users who already have a superclass implement the interface directly. Both stay compatible, because callers only see the interface.

import java.util.AbstractList;

interface Greeter { String greet(String name); }

abstract class BaseGreeter implements Greeter {          // skeleton: shared code
    protected abstract String salutation();
    @Override public String greet(String name) { return salutation() + ", " + name + "!"; }
}

class HindiGreeter extends BaseGreeter {
    @Override protected String salutation() { return "Namaste"; }
}

public class SkeletonDemo {
    public static void main(String[] args) {
        Greeter g = new HindiGreeter();                  // callers see only the interface
        System.out.println(g.greet("Asha"));

        // AbstractList needs only get(int) and size() for a read-only list
        var squares = new AbstractList<Integer>() {
            @Override public Integer get(int i) { return i * i; }
            @Override public int size() { return 5; }
        };
        System.out.println(squares);
    }
}
Namaste, Asha!

Why not always use default methods in interfaces?

Default methods cannot touch fields, cannot be protected, cannot be final and cannot be a stable base for subclass state. They are for convenience and evolution. If you find yourself wanting state in an interface, you want an abstract class, or better, composition (composition over inheritance).

Overlap and exceptions

  • An abstract class with no state, no constructor logic and only abstract methods is just a worse interface. Convert it.
  • An interface with default methods can offer "mixin" behaviour (Comparator.reversed()), but still no state.
  • Both can have static methods and nested types.
  • If you must keep binary compatibility in a public library, adding an abstract method to either breaks implementers; adding a default method (or a concrete method in the class) does not.

Interview: "Abstract class vs interface?"

  • Lead with the decision rule: state and shared code in a family means abstract class; a capability across unrelated classes means interface.
  • Give three differences: multiple inheritance, instance state and constructors, access modifiers.
  • Mention Java 8 changes: default and static methods narrowed the gap, but interfaces still have no state.
  • Mention the skeleton pattern (List and AbstractList) to show depth.
  • Follow-up: "Why did Java add default methods?" Interface evolution, for stream() and forEach().

The final keyword; final vs finally vs finalize

final means "cannot be changed after this point": a final variable is assigned once, a final method cannot be overridden and a final class cannot be extended; it fixes the reference, not the contents of the object.

The word final appears in four places and means a slightly different "no more changes" in each. Learn the four, and the two look-alike words finally and finalize, which interviewers love to mix into one question.

final variables

A final variable can be assigned exactly once. After that, any assignment is a compile error: cannot assign a value to final variable.

  • Final local variable or parameter. final int tax = 18;. Many teams skip final on locals; it adds noise, though it is useful for a parameter you do not want reassigned.
  • Final instance field. Must be assigned once, either at the declaration, in an instance initializer, or in every constructor. A final field with no initial value is a blank final; the compiler checks that each constructor assigns it exactly once ("variable might not have been initialized").
  • Final static field. Assigned at declaration or in a static block. With a primitive or String constant value, it is a compile-time constant (static final int MAX = 10;), which the compiler copies into the code that uses it. Convention: UPPER_SNAKE_CASE.
import java.util.*;

public class FinalDemo {
    static final double GST_RATE = 0.18;           // constant
    private final String orderId;                  // blank final
    private final List<String> items = new ArrayList<>();

    FinalDemo(String orderId) {
        this.orderId = orderId;                    // assigned exactly once
    }

    public static void main(String[] args) {
        FinalDemo d = new FinalDemo("OD-1");
        d.items.add("Mouse");                      // OK: the list object is mutable
        d.items.add("Keyboard");
        System.out.println(d.items + " " + d.orderId);
        // d.items = new ArrayList<>();            // error: cannot assign a value to final variable items

        final int[] marks = {40, 50};
        marks[0] = 99;                             // OK: contents of a final array can change
        System.out.println(Arrays.toString(marks));
        // marks = new int[3];                     // error
    }
}
[Mouse, Keyboard] OD-1
[99, 50]

final reference is not an immutable object

final locks the variable, not the object it points to. A final List still lets you call add; a final array still lets you change its elements. To get an object that really cannot change, make its class immutable (immutability), or use List.of(…) for an unmodifiable list. This is the most common final interview trap.

Effectively final

A local variable or parameter that is never reassigned after its first assignment is effectively final, even without the keyword. Lambdas and anonymous or local classes may use outer local variables only if they are final or effectively final. The reason: the lambda gets a copy of the value, and the variable may live on a thread's stack that is gone by the time the lambda runs. Allowing changes would give confusing results, so Java forbids them.

int count = 0;
Runnable r = () -> System.out.println(count);   // OK only if count is never changed
count++;   // error at the lambda: local variables referenced from a lambda expression
           // must be final or effectively final

// Fix when you need a changing value: use an object or array holder, or AtomicInteger
var counter = new java.util.concurrent.atomic.AtomicInteger();
Runnable ok = () -> counter.incrementAndGet();

final methods

A final method cannot be overridden. Use it when the method's behaviour is part of a class's safety or algorithm, such as the Template Method in abstract classes. Object.getClass(), wait() and notify() are final. A private method is effectively final already. Static methods can be marked final too, but it has little meaning, since they are hidden, not overridden.

final classes

A final class cannot be extended: cannot inherit from final String. The JDK uses it for security and immutability: String, Integer and all wrapper classes, LocalDate, Math. Records are implicitly final, and so are enums without constant bodies. For your own classes, making the class final is a good default for value-like types and utility classes, because inheritance is a strong coupling (composition). A middle option is a sealed class, which allows only chosen subclasses (sealed classes). A frequent real-world catch: frameworks that create proxies by subclassing (Spring CGLIB proxies, Hibernate lazy entities) cannot proxy a final class or final method. Spring Boot projects written in Kotlin need the "allopen" plugin for this reason.

Rules

  • A final field must be definitely assigned by the end of every constructor, once and only once.
  • A final method cannot be overridden; a final class cannot be extended; abstract final is illegal.
  • A lambda or inner class may capture only final or effectively final locals.
  • The same value assigned in a loop to a final local is fine, if declared inside the loop: each iteration is a new variable.

Conventions: where professionals use final

  • On fields, by default. Make fields private final unless they must change. It makes classes simpler and thread-safe by construction.
  • On constants: public static final, upper snake case.
  • On utility and value classes. Not on every local variable, and not on classes meant to be extended.
  • Constructor injection in Spring uses private final fields; it makes the dependency required and unchangeable.

Mistake: thinking final means immutable

Wrong belief

private final List<String> roles;     // "nobody can change roles"
public List<String> getRoles() { return roles; }   // caller can still add and remove

Right: protect the contents too

private final List<String> roles;
public List<String> getRoles() { return List.copyOf(roles); }  // unmodifiable copy

Interview: final questions

  • Final vs finally vs finalize? Keyword / cleanup block / deprecated GC hook. Say what each is in one line.
  • Can a final object's state change? Yes. Only the reference is fixed.
  • Can we override a final method? Extend a final class? No to both.
  • What is a blank final? A final field without an initial value; each constructor must assign it once.
  • What does effectively final mean, and why for lambdas? Never reassigned; lambdas capture copies of local values.
  • Why is String final? Security, caching of hash codes, safe sharing in the string pool, thread safety.

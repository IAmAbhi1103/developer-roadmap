Records: compact immutable data classes

A record declares an immutable data carrier in one line: the compiler generates the private final fields, the constructor, the accessors, and equals, hashCode and toString; use it for DTOs, value objects and return types, not for JPA entities or mutable state.

A normal data class needs about 30 lines: fields, a constructor, getters, equals, hashCode, toString. Most of it is boilerplate. A record (a standard feature since Java 16) says it in one line, and the intent is clear: "this class is just its data".

record Point(int x, int y) { }                      // that's the whole class

public class RecordBasics {
    public static void main(String[] args) {
        Point p = new Point(3, 4);
        System.out.println(p.x() + ", " + p.y());   // accessor is x(), not getX()
        System.out.println(p);                      // generated toString
        System.out.println(p.equals(new Point(3, 4)));          // generated equals: by value
        System.out.println(p.hashCode() == new Point(3, 4).hashCode());
        // p.x = 5;       // error: cannot assign a value to final variable x
    }
}
3, 4
Point[x=3, y=4]
true
true

What the compiler generates

  • A private final field for each component (the names in the header).
  • A canonical constructor with all components in order: new Point(3, 4).
  • One public accessor per component, named like the component: x(), y(). There is no getX() and no setters.
  • equals() (all components equal), hashCode() (derived from all components) and toString() in the form Point[x=3, y=4].
  • The record is implicitly final and extends java.lang.Record, so it cannot extend another class. It can implement interfaces.

Compact constructor: validation and normalisation

To check or adjust values, write a compact canonical constructor: the record name with no parameter list. It runs first with the parameters in scope. Assign nothing to the fields yourself; the compiler does it at the end, with whatever the parameters now hold.

import java.util.*;

record Money(long paise, String currency) implements Comparable<Money> {

    static final Money ZERO_INR = new Money(0, "INR");   // static fields are allowed

    Money {                                              // compact constructor
        Objects.requireNonNull(currency, "currency");
        if (paise < 0) throw new IllegalArgumentException("paise must be >= 0: " + paise);
        currency = currency.toUpperCase();               // normalise the parameter
    }

    static Money inr(double rupees) {                    // static factory with a clear name
        return new Money(Math.round(rupees * 100), "INR");
    }

    Money plus(Money other) {                            // custom method
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("currency mismatch");
        return new Money(paise + other.paise, currency);
    }

    @Override public int compareTo(Money o) { return Long.compare(paise, o.paise); }

    @Override public String toString() {                 // you may override generated methods
        return String.format("%s %.2f", currency, paise / 100.0);
    }

    public static void main(String[] args) {
        System.out.println(inr(499.5).plus(new Money(250, "inr")));
        try {
            new Money(-1, "INR");
        } catch (IllegalArgumentException e) {
            System.out.println(e.getMessage());
        }
    }
}
INR 502.00
paise must be >= 0: -1

Besides the compact form, you can write the full canonical constructor yourself (then you assign the fields with this.x = x), or add extra constructors, which must start with this(…) and so end up in the canonical one. A record may also declare an accessor of its own, for example to return a copy.

Immutability is shallow

The fields of a record are final, but if a component is a mutable object, the object can still change. Copy mutable inputs in the compact constructor and return unmodifiable views.

import java.util.*;

record Team(String name, List<String> members) {
    Team {
        members = List.copyOf(members);          // defensive copy; unmodifiable
    }

    public static void main(String[] args) {
        List<String> list = new ArrayList<>(List.of("Asha", "Ravi"));
        Team t = new Team("Core", list);
        list.add("Meera");                       // does not affect the record
        System.out.println(t);
        try {
            t.members().add("X");                // UnsupportedOperationException
        } catch (UnsupportedOperationException e) {
            System.out.println("members are read-only");
        }
    }
}
Team[name=Core, members=[Asha, Ravi]]
members are read-only

Without that line, the caller still holds the list and can change the team's state from outside. This is the same defensive-copy rule as in immutability. For hash-based collections a record with a mutable component also breaks the "mutable keys" rule from equals and hashCode.

Other things records can do

  • Nested and local records. A record declared inside a method is handy for grouping temporary data in a stream pipeline: record Pair(String name, int score) {}.
  • Generics. record Pair<A, B>(A first, B second) {}.
  • Interfaces. record Circle(double r) implements Shape (see sealed classes).
  • Record patterns (Java 21). if (o instanceof Point(int x, int y)) { … } takes a record apart in a test or switch (Module 5).
  • Static members are allowed; instance fields other than the components are not.

Rules

  • A record cannot extend a class, cannot be abstract, and cannot declare instance fields beyond its components.
  • In a compact constructor you cannot write this.x = x; assign to the parameter.
  • An explicit canonical constructor cannot be less accessible than the record itself.
  • An overridden accessor must be public and return the component's type.

When not to use a record

  • JPA/Hibernate entities. They need a no-argument constructor, non-final classes (for lazy proxies), mutable fields and an identity that outlives its data. Use a normal class for the entity and a record for the DTO or projection that you return from the API.
  • Mutable state or builder-style construction with many optional parameters (a record with 12 components is hard to read; use a class with a builder).
  • Inheritance hierarchies. Records are final. Model a family with a sealed interface and several records instead.
  • Hiding data. A record is a transparent carrier; its components are its public API. If you need to hide the representation (encapsulation), use a normal class.

In real Spring Boot projects

Records are now the standard way to write request and response DTOs: record CreateOrderRequest(@NotBlank String customerId, @Min(1) int quantity) {} works with Jackson (JSON) and Bean Validation, and with Spring Data projections and @ConfigurationProperties. Also use them for map keys, for returning several values from a method, and for events and messages.

Interview: record questions

  • What is a record, and what does the compiler generate? A final, immutable data class: fields, canonical constructor, accessors, equals, hashCode, toString.
  • Are records fully immutable? Only shallowly; copy mutable components.
  • Can a record have a setter, extend a class or implement an interface? No / no / yes.
  • Why not use a record as a JPA entity? No no-arg constructor, final class and fields, no proxies.
  • Record vs Lombok? Language feature with no dependency, but no setters or inheritance.

Sealed classes and interfaces (a teaser)

A sealed class or interface lists exactly which classes may extend or implement it, so the compiler knows every possible subtype and can check that a switch over them is complete.

Normally anyone can extend your public class or implement your public interface. Sometimes you want a closed family: a payment is either UPI, a card or cash on delivery, and nothing else. Enums are closed families of constants; sealed types (final since Java 17) are closed families of types, each of which may carry different data.

sealed interface Payment permits Upi, Card, Cod { }      // the allowed implementations

record Upi(String vpa) implements Payment { }
record Card(String last4, boolean credit) implements Payment { }
record Cod() implements Payment { }

public class SealedDemo {
    static String describe(Payment p) {
        return switch (p) {                                // exhaustive: no default needed
            case Upi u  -> "UPI to " + u.vpa();
            case Card c -> (c.credit() ? "Credit" : "Debit") + " card ending " + c.last4();
            case Cod c  -> "Cash on delivery";
        };
    }

    public static void main(String[] args) {
        System.out.println(describe(new Upi("asha@bank")));
        System.out.println(describe(new Card("4242", true)));
        System.out.println(describe(new Cod()));
    }
}
UPI to asha@bank
Credit card ending 4242
Cash on delivery

If you later add a fourth permitted type, describe stops compiling until you handle it. That is the big gain: the compiler tells you every place a new case matters. It replaces long instanceof chains and the visitor pattern. Pattern-matching switch belongs to Module 5; this article only shows why sealing makes it safe.

The rules

  • Declare with sealed and a permits list. If the permitted classes are in the same file, permits may be omitted.
  • Each permitted subclass must say what happens next: final (no more subclasses), sealed (it restricts its own children) or non-sealed (it opens the hierarchy again).
  • Permitted subclasses must be in the same module, or in the same package when you do not use modules.
  • Records and enums are implicitly final, so they fit perfectly as permitted types.
sealed abstract class Shape permits Circle, Polygon { }
final class Circle extends Shape { }
sealed class Polygon extends Shape permits Triangle, Square { }
final class Triangle extends Polygon { }
non-sealed class Square extends Polygon { }      // anyone may extend Square

When to use sealed types

  • For domain models with a small, known set of variants: results (Success/Failure), payment types, commands, expression trees.
  • When you want exhaustive switch without a default.
  • Not for plugin points where third parties must extend your type. Use a normal interface there.

Interview: one-liner

"A sealed type restricts its direct subtypes with permits; each must be final, sealed or non-sealed. It gives closed hierarchies and compiler-checked exhaustive switches." Compare it with final (no subclasses at all) and with enums (closed, but constants of one type).

The four pillars together: a worked bank example, and SOLID

Encapsulation protects data, abstraction hides complexity behind a contract, inheritance shares code in an is-a family, and polymorphism lets one call behave differently per object; a small bank model shows all four working together.

The four pillars at a glance

Real-world picture: a UPI app. Your account details are not readable by other apps (encapsulation). You tap "Pay" without knowing banks' internal APIs (abstraction). Savings and current accounts share account rules but differ in details (inheritance). Paying through any bank behaves correctly for that bank (polymorphism).

The model

The code

import java.util.*;

interface InterestPolicy {                                // abstraction: a contract
    long interestFor(long balanceInPaise);
}

record Transaction(String type, long amountInPaise, long balanceAfter) { }  // immutable data

abstract class Account {
    private final String number;                          // encapsulation: private state
    private long balance;
    private final List<Transaction> history = new ArrayList<>();

    protected Account(String number) { this.number = number; }

    public final void deposit(long amount) {              // fixed rules: subclasses can't break them
        if (amount <= 0) throw new IllegalArgumentException("Amount must be positive");
        post("DEPOSIT", amount);
    }

    public final void withdraw(long amount) {
        if (amount <= 0) throw new IllegalArgumentException("Amount must be positive");
        if (balance - amount < minimumBalance()) {
            throw new IllegalStateException("Insufficient funds in " + number);
        }
        post("WITHDRAW", -amount);
    }

    protected abstract long minimumBalance();             // varies per account type
    public void monthEnd() { }                            // hook: default does nothing

    protected final void post(String type, long signedAmount) {
        balance += signedAmount;
        history.add(new Transaction(type, Math.abs(signedAmount), balance));
    }

    public long balance() { return balance; }
    public List<Transaction> history() { return List.copyOf(history); }   // defensive copy

    @Override public String toString() {
        return String.format("%s %s balance=Rs %.2f",
                getClass().getSimpleName(), number, balance / 100.0);
    }
}

class SavingsAccount extends Account {                    // inheritance: is-a Account
    private final InterestPolicy policy;                  // composition: has-a policy

    SavingsAccount(String number, InterestPolicy policy) {
        super(number);
        this.policy = policy;
    }
    @Override protected long minimumBalance() { return 0; }
    @Override public void monthEnd() {
        long interest = policy.interestFor(balance());
        if (interest > 0) post("INTEREST", interest);
    }
}

class CurrentAccount extends Account {
    private final long overdraftLimit;
    CurrentAccount(String number, long overdraftLimit) {
        super(number);
        this.overdraftLimit = overdraftLimit;
    }
    @Override protected long minimumBalance() { return -overdraftLimit; }   // may go negative
}

public class BankDemo {
    public static void main(String[] args) {
        InterestPolicy fourPercent = balance -> balance * 4 / 1200;   // lambda: monthly 4% p.a.
        Account s = new SavingsAccount("SB1001", fourPercent);
        Account c = new CurrentAccount("CA2001", 500_000);          // Rs 5,000 overdraft

        s.deposit(1_000_000);                                       // Rs 10,000
        c.deposit(200_000);
        c.withdraw(600_000);                                        // goes to -Rs 4,000: allowed
        try {
            s.withdraw(2_000_000);                                  // not allowed
        } catch (IllegalStateException e) {
            System.out.println(e.getMessage());
        }

        List<Account> accounts = List.of(s, c);                     // polymorphism
        accounts.forEach(Account::monthEnd);                        // each type does its own thing
        accounts.forEach(System.out::println);
        System.out.println(s.history());
    }
}

Where each pillar shows up

  • Encapsulation: balance and history are private; the only way to change the balance is through deposit, withdraw or post, which check the rules. history() returns a copy. Money is a long in paise, never a double.
  • Abstraction: InterestPolicy says what is needed, not how; the abstract minimumBalance() names a concept that each account type defines. Callers use Account only.
  • Inheritance: both account types reuse the number, balance, history and all the rules from Account. deposit and withdraw are final, so a subclass cannot weaken them.
  • Polymorphism: accounts.forEach(Account::monthEnd) runs interest for savings and nothing for current, chosen at run time.
  • Composition: interest is a separate strategy object, not a subclass of savings per interest rate (composition). The record Transaction is a simple value type (records).

In production you would add thread safety, BigDecimal or a money type, and persistence, but the structure stays the same. This is also the shape of a Spring service: a class that depends on interfaces and keeps its state private.

SOLID teaser

SOLID is a set of five design guidelines that grow out of the pillars: Single responsibility (a class has one reason to change), Open/closed (open for extension, closed for modification; our new account type needs no change in the loop), Liskov substitution (a subclass must work wherever its parent is expected), Interface segregation (many small interfaces beat one fat one) and Dependency inversion (depend on abstractions such as InterestPolicy, not on concrete classes). The full treatment with examples is in System Design · Module 1.

Mistakes that break the pillars

  • Public fields, or getters that return internal mutable lists (breaks encapsulation).
  • Using extends only to reuse code, or a subclass that cannot do what the parent promises (breaks inheritance and Liskov).
  • Adding instanceof chains instead of overriding methods (misses polymorphism).
  • One interface per class "just because" (abstraction without a reason).
  • Saying "polymorphism is overloading" in an interview. Overloading is the compile-time form; the main idea is runtime polymorphism.

Interview questions — Object-oriented programming

What are the four pillars of OOP? Give an example of each.

Encapsulation (private fields plus validating methods, e.g. a bank balance), abstraction (an interface such as PaymentGateway hides the provider), inheritance (SavingsAccount extends Account) and polymorphism (account.monthEnd() runs the right version per object). Add that composition and interfaces often replace deep inheritance.

What is the difference between a class and an object?

A class is a blueprint: it defines fields and methods. An object is an instance created from it with new, with its own field values (state), behaviour from the class and an identity. The reference variable lives on the stack, and the object lives on the heap.

Overloading vs overriding?

Overloading: same name, different parameter lists in one class (or its subclasses); chosen at compile time by the declared argument types. Overriding: a subclass gives a new body to an inherited instance method with the same signature; chosen at run time by the object's real class. Return type alone cannot distinguish overloads. Static, private and final methods cannot be overridden.

Abstract class vs interface: when do you use which?

An abstract class can hold state, constructors and any-access methods, but a class can extend only one. An interface has only constants, public methods (abstract, default, static, private), no state, and a class can implement many. Use an interface for a capability across unrelated classes and an abstract class for closely related classes sharing fields and code. A skeleton abstract class implementing an interface gives both.

Why does Java not support multiple inheritance of classes? How do interfaces help?

Two parents could both supply the same field or method, so the diamond problem makes it unclear which copy the child inherits. Java allows only one parent class. Interfaces carry no state, so a class may implement many; if two default methods clash, the class must override and pick with A.super.m().

What does this print? 
class A { String n = "A"; String who() { return "A"; } }
class B extends A { String n = "B"; String who() { return "B"; } }
A x = new B();
System.out.println(x.n + x.who());

It prints AB. The field is looked up by the declared type (A), the overridden method by the real object (B). Fields are not polymorphic.

What is the order of initialization when you create an object?

First the class is loaded: parent static blocks and fields, then child static blocks (once). Then for each new: parent instance initializers and fields, parent constructor, then child instance initializers and fields, child constructor. If a parent constructor calls an overridden method, it sees the child's fields still at default values.

What is the contract between equals() and hashCode()? What happens if you break it?

If a.equals(b) then a.hashCode() == b.hashCode(); the reverse need not hold. equals must be reflexive, symmetric, transitive, consistent and false for null. If you override equals only, equal objects get different hash codes, and a HashSet or HashMap stores duplicates or fails to find a key.

Does final make an object immutable?

No. final fixes the reference: you cannot reassign it. The object can still change (final List still allows add). An immutable class needs: final class, private final fields, no setters, defensive copies of mutable inputs and outputs. Compare final, finally (cleanup block) and finalize (deprecated GC hook).

Composition or inheritance? Why "favor composition"?

Inheritance couples the child to the parent's implementation (the fragile base class problem, e.g. a HashSet subclass counting addAll twice) and is fixed at compile time with one parent only. Composition holds a component behind an interface and delegates, which is flexible, testable and swappable at run time. Use inheritance for a true is-a with a parent designed for extension.

Static nested class vs inner class?

An inner class belongs to an outer instance and holds a hidden reference to it (usable with Outer.this, created with outer.new Inner()); this can keep the outer object alive. A static nested class has no such reference and is created with new Outer.Nested(). Prefer static nested unless you need the outer instance.

Why use enums instead of int or String constants? What are their pitfalls?

Type safety, readable names, ability to hold fields and per-constant behaviour, exhaustive switch, EnumMap and EnumSet. Pitfalls: valueOf throws IllegalArgumentException on unknown names, ordinal() changes when you reorder (store the name, e.g. EnumType.STRING in JPA), and a new constant must be handled in every switch.

What is a record and when should you not use one?

A record is a concise, final, shallowly immutable data class with generated constructor, accessors (x()), equals, hashCode and toString. Do not use it for JPA entities, for mutable state, or when you need inheritance or hidden representation. Copy mutable components in the compact constructor.

What is the difference between ClassCastException and instanceof? How do you avoid the exception?

instanceof is a test that returns true when the object is an instance of the type (false for null). ClassCastException is what a downcast throws when the test would have been false. Guard with if (a instanceof Dog d), or better, put the behaviour in the parent so no cast is needed.

What is a sealed class and why was it added?

A sealed type lists its permitted direct subtypes with permits, and each must be final, sealed or non-sealed. It models closed hierarchies and lets the compiler check a pattern-matching switch for completeness, without a default branch.

Cheat sheet — Object-oriented programming

  • Class vs object blueprint vs instance; new allocates on the heap, the variable holds a reference.
  • Constructor same name as class, no return type; the default one exists only if you write none; chain with this(...) or super(...) as the first statement.
  • Init order static (parent, child) once; per object: parent fields/blocks, parent constructor, child fields/blocks, child constructor.
  • static belongs to the class; no this, no instance members directly.
  • Access private (class) < package-private < protected (package + subclasses) < public.
  • Encapsulation private fields, validated setters or none, defensive copies; immutable = final class, final fields, no setters.
  • Inheritance extends, one parent; constructors and private members are not inherited; super.m() calls the parent version.
  • Overriding rules same signature, covariant return, access not narrower, no broader checked exceptions; always @Override.
  • Not overridable static (hidden), private, final; fields are hidden, not overridden.
  • Polymorphism overloading = compile time (declared types); overriding = run time (real object).
  • Casting upcast implicit and safe; downcast explicit and may throw ClassCastException; check with instanceof.
  • Abstract class cannot be instantiated; may have state, constructors, concrete and abstract methods; use for the Template Method.
  • Interface constants, abstract/default/static/private methods; no state; implement many; implementations must be public.
  • Default method clash class wins; more specific interface wins; else override and call A.super.m().
  • final variable assigned once; method not overridable; class not extendable; reference, not content.
  • final / finally / finalize keyword / cleanup block / deprecated GC hook.
  • equals + hashCode override together with the same fields; equal objects need equal hashes; use Objects.equals and Objects.hash.
  • toString override it; never include secrets; use Arrays.toString for arrays.
  • Copying shallow shares inner objects; deep duplicates them; prefer copy constructors or immutables over clone().
  • Composition has-a, delegate to a component behind an interface; inheritance only for true is-a.
  • Nested classes static nested (no outer ref), inner (outer ref), local, anonymous; lambdas replace anonymous functional interfaces.
  • Packages reverse-domain lowercase, folders match; java.lang is auto-imported; wildcard excludes subpackages.
  • Enum fixed constants with fields, private constructor, per-constant bodies; compare with ==; store names, not ordinals.
  • Record record P(int x, int y) {}; compact constructor validates; shallow immutable; not for entities.
  • Sealed sealed ... permits; subtypes are final, sealed or non-sealed; enables exhaustive switch.

Practice — Object-oriented programming

  1. Class basics (easy). Write Student with private fields id, name and marks, a constructor that rejects marks outside 0-100, getters, and a good toString. Done when invalid marks throw IllegalArgumentException and printing a list of students shows readable text.
  2. Output prediction: initialization order. Write a parent and a child class, each with a static block, an instance block and a constructor that print a line; add a parent constructor that calls an overridden method reading a child field. Predict the order on paper, then run it. Done when you can explain every line, including why the field is still 0 or null.
  3. Output prediction: overloading vs overriding. Create Animal and Dog with eat(Animal) in both and eat(Dog) in Dog, plus overloads show(Object) and show(String). Call them through Animal and Dog variables with null and cast arguments. Done when you can state the compile-time and run-time step for each call (puzzles).
  4. Library model. Model Book, Member and Loan: a loan links one member and one book with a due date; a member can hold at most 3 loans; Book has an ISBN. Use inheritance or an interface only where it fits (for example Member types with different limits through a LoanPolicy interface). Done when borrowing a 4th book fails with a clear exception and equals/hashCode of Book use the ISBN.
  5. Bank model. Re-create Account, SavingsAccount, CurrentAccount and Transaction from the worked example without looking. Then add a FixedDeposit account that blocks withdrawals until a maturity date, and a second InterestPolicy with tiered rates. Done when the loop over List<Account> needs no change for the new type.
  6. Parking lot. Model ParkingLot, Floor, Slot and vehicles (bike, car, truck) with an enum VehicleType and an enum SlotSize. Decide where inheritance, composition (a lot has floors) and an interface (PricingStrategy) belong, and use a record for Ticket. Done when parking returns a ticket for the nearest fitting free slot, and a full lot reports a clear error.
  7. equals/hashCode test. Write Email as a normal class with a correct equals and hashCode (case-insensitive). First leave out hashCode and show a HashSet holding a duplicate; then fix it and add the same logic as a record with a compact constructor that lowercases the value. Done when both versions keep the set at size 1.
  8. Refactor to composition. Start with class Stack<E> extends ArrayList<E> and show that callers can call add(0, x) and break the stack rule. Rewrite it with a private list field and only push, pop, peek and isEmpty. Done when the public API has just those methods.
  9. Enum and sealed. Create an enum OrderStatus with the legal next states per constant (a method canMoveTo), and a sealed interface PaymentResult with record cases Paid, Failed and Pending. Write a switch over each without a default. Done when removing one case makes the code fail to compile.

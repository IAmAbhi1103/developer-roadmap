Debugging in IntelliJ: breakpoints, stepping, watches and remote debug

A debugger pauses your program at a breakpoint so you can step line by line, inspect variables, evaluate expressions and even change values — far faster and more reliable than adding System.out.println everywhere.

Printing values to find a bug means edit, compile, run, read, repeat, and you only see what you thought to print. A debugger lets you stop the running program, look at everything, and move forward one step at a time. The ideas are the same in Eclipse, VS Code and IntelliJ IDEA; the keys below are IntelliJ's default keymap on Windows.

Starting a debug session

  1. Click in the gutter (the grey strip left of the line numbers) next to a line, or press Ctrl+F8. A red dot appears: a line breakpoint.
  2. Start the program with Debug (the bug icon, or Shift+F9) instead of Run. For a test, click the green arrow beside the test method and choose Debug.
  3. When execution reaches the line, the program suspends before running it, and the Debug window shows frames, variables and watches.
  4. Step, inspect, then press F9 (Resume) to run to the next breakpoint or the end.

A bug to practise on

import java.util.List;

public class Cart {
    record Item(String name, int price, int qty) {}

    static int total(List<Item> items) {
        int sum = 0;
        for (int i = 0; i < items.size() - 1; i++) {      // bug: skips the last item
            Item item = items.get(i);
            sum += item.price() * item.qty();
        }
        return sum;
    }

    public static void main(String[] args) {
        List<Item> items = List.of(
                new Item("Pen", 10, 5),
                new Item("Book", 120, 2),
                new Item("Bag", 800, 1));
        System.out.println("Total: " + total(items));      // expected 1090
    }
}
Total: 290

Set a breakpoint on sum += ..., debug, and press F9 repeatedly. The Variables panel shows i = 0, then 1, and then the loop ends without ever seeing i = 2. Add the watch items.size() and the off-by-one is obvious: the loop stops at size() - 1. This "stop and look" approach finds in a minute what takes ten minutes with prints.

Looking at data

  • Frames panel. The call stack of the paused thread (the same chain as a stack trace). Click an older frame to see its local variables and the line that made the call: invaluable for "how did we get here?"
  • Variables panel. All locals, parameters and this. Expand objects to see fields. Hover over a variable in the editor for a quick look. IntelliJ also shows values inline, in grey, next to your code.
  • Watches. Click + in the Watches area and enter any expression (items.size(), order.total() > 1000). It is re-evaluated at every stop.
  • Evaluate Expression (Alt+F8). A mini-console: type any Java, including method calls, and see the result. Example: items.stream().mapToInt(Item::price).sum(). Beware of methods with side effects (they really run).
  • Set Value (F2 on a variable). Change a variable at runtime — set i back to 0, or force a null to a real object — to test a fix without restarting.
  • Mark Object. Give an object a label (F11) so you can recognise the same instance across stops.
  • Debugging streams. On a line with a stream pipeline, click Trace Current Stream Chain in the debug toolbar. It shows the elements before and after every step (filter, map, …), which solves most "why is my stream empty?" questions.

Hot reload

If you edit a method body while paused, IntelliJ can reload the changed class (Build → Recompile, then confirm the reload prompt) so you can continue with the new code. It works for changes inside method bodies only; adding or removing methods or fields needs a restart.

Remote debugging

A remote debug attaches your IDE to a JVM running somewhere else (another process, a Docker container, a test server). The JVM must be started with the JDWP (Java Debug Wire Protocol) agent:

$ java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005 -jar app.jar
Listening for transport dt_socket at address: 5005
  • server=y — the JVM waits for a debugger to connect; suspend=n — start running at once (use suspend=y to pause until a debugger attaches, handy to debug start-up code).
  • address=*:5005 — listen on all network interfaces, port 5005. A bare address=5005 listens only on localhost in recent JDKs.
  • In IntelliJ: Run → Edit Configurations → + → Remote JVM Debug, enter the host and port 5005, click Debug. Breakpoints now work in the remote process. The source code must match the deployed code.
  • With Maven and Spring Boot you can pass the same flag as a JVM argument; in Docker, publish port 5005 (-p 5005:5005).

Rule: never leave the debug port open in production

Anyone who can reach a JDWP port can run arbitrary code inside your JVM. Use remote debugging only on local or protected test environments, and never expose port 5005 to the internet.

Tips

  • Put the breakpoint before the problem, not on it; you can always step forward but not back (except with Drop Frame).
  • For a loop that fails on iteration 5,000, use a conditional breakpoint or pass count rather than pressing F9 5,000 times.
  • If breakpoints show a crossed-out grey dot, the line has no executable code, the class is not loaded yet, or the source differs from the compiled class: rebuild.
  • Read the stack trace of an exception first: the line number of your own code at the top of the "at com.shop…" frames is the best place for the first breakpoint.

Edge cases

  • Pausing at a breakpoint in a web app suspends that thread; HTTP clients may time out while you think. Increase timeouts in debug runs.
  • Evaluating an expression that calls code with side effects (saving to a database, sending an email) executes it for real.
  • Optimised or generated code (Lombok, proxies, lambdas) may show unexpected frames; IntelliJ hides many of them by default.
  • A debugger changes timing, so race conditions can disappear while debugging (a "Heisenbug"). Use logs for concurrency problems.

Interview: "How do you debug a problem in a Java application?"

  • Reproduce, read the stack trace, set a breakpoint before the suspected line, step through, and inspect variables and the call stack.
  • Name the tools: conditional and exception breakpoints, watches, evaluate expression, step over/into/out, run to cursor, stream trace, remote debug with JDWP.
  • For production: logs, thread dumps (jstack), heap dumps, JFR — not a remote debugger on a live server.

Maven: pom.xml, dependencies, lifecycle and commands

Maven builds a Java project from one pom.xml: it downloads dependencies, compiles, tests, packages and installs, following a fixed lifecycle and a standard folder layout.

A build tool automates the repeatable work: downloading libraries, compiling, running tests, creating a JAR and publishing it. Without one, you would copy JAR files by hand and call javac yourself. Maven (Apache) is the most widely used in Java companies and the default in many Spring Boot tutorials. Its idea is convention over configuration: if you follow the standard layout, you need very little configuration.

Coordinates

Every artifact has unique coordinates (GAV):

groupId
The organisation or project group, usually a reversed domain: com.shop, org.postgresql.
artifactId
The name of the module: order-service, postgresql. It becomes the JAR file name.
version
For example 1.0.0 (a release) or 1.0.0-SNAPSHOT (a work in progress).
packaging
jar (default), war or pom (for parent projects).

Standard directory layout

order-service/
├── pom.xml
├── mvnw, mvnw.cmd, .mvn/        (Maven wrapper)
├── src/
│   ├── main/
│   │   ├── java/com/shop/        production code
│   │   └── resources/            application.properties, logback.xml, SQL files
│   └── test/
│       ├── java/com/shop/        test code (JUnit)
│       └── resources/            test-only resources
└── target/                       build output (never commit this)

A complete annotated pom.xml

Transitive dependencies and conflicts

When you add library A and A needs B, Maven downloads B too. That is a transitive dependency. Show the whole tree with:

$ mvn dependency:tree
[INFO] com.shop:order-service:jar:1.0.0-SNAPSHOT
[INFO] +- ch.qos.logback:logback-classic:jar:1.5.6:compile
[INFO] |  +- ch.qos.logback:logback-core:jar:1.5.6:compile
[INFO] |  \- org.slf4j:slf4j-api:jar:2.0.13:compile
[INFO] +- org.postgresql:postgresql:jar:42.7.3:runtime
[INFO] \- org.junit.jupiter:junit-jupiter:jar:5.10.2:test

Trouble starts when two libraries need different versions of the same artifact (a version conflict). Maven keeps only one, chosen by two rules: the nearest to your project in the tree wins, and if the distance is equal the first declared wins. The loser may lack a method the other library needs, causing NoSuchMethodError or NoClassDefFoundError at runtime. How to fix it:

  • Find it with mvn dependency:tree -Dverbose (shows omitted duplicates) and search for the artifact.
  • Pin one version in dependencyManagement (this overrides what transitive paths ask for).
  • Remove an unwanted transitive dependency with an <exclusions> block inside the dependency.
  • In Spring Boot, prefer the version managed by the Boot BOM and override only deliberately.
<dependency>
    <groupId>com.example</groupId>
    <artifactId>legacy-client</artifactId>
    <version>2.3.0</version>
    <exclusions>
        <exclusion>
            <groupId>commons-logging</groupId>
            <artifactId>commons-logging</artifactId>
        </exclusion>
    </exclusions>
</dependency>

The build lifecycle

A lifecycle is an ordered list of phases. When you run a phase, Maven runs every phase before it, in order. The default lifecycle's main phases:

PhaseWhat happensPlugin goal bound by default (jar projects)
validateChecks the project is correct and all information is available—
compileCompiles src/main/java into target/classescompiler:compile
testCompiles and runs unit tests (does not need the JAR)compiler:testCompile, surefire:test
packageCreates the JAR/WAR in target/jar:jar
verifyRuns checks on the package, such as integration testsfailsafe if configured
installCopies the artifact to your local repository ~/.m2 so other local projects can use itinstall:install
deployUploads to a remote repository (Nexus, Artifactory, GitHub Packages)deploy:deploy

There are two other lifecycles: clean (mvn clean deletes the target folder) and site (documentation). A plugin is the code that does the work, and a goal is one task of a plugin, written plugin:goal (for example dependency:tree). Phases are just slots; goals are bound to phases. Key plugins: compiler (javac), surefire (unit tests; picks classes named *Test, Test*, *Tests), failsafe (integration tests named *IT, run in integration-test/verify), jar, and for Spring Boot the spring-boot-maven-plugin that creates an executable "fat" JAR.

The local repository, SNAPSHOT vs release, and the wrapper

  • Local repository: ~/.m2/repository (on Windows C:\Users\you\.m2\repository). Downloaded dependencies are cached there; ~/.m2/settings.xml holds mirrors, proxy and repository credentials. The default remote is Maven Central.
  • Release (1.2.0) is immutable: once published, the same version always contains the same bytes. -SNAPSHOT (1.3.0-SNAPSHOT) means "work in progress"; Maven re-checks remote repositories for newer snapshot builds (daily by default). Never depend on a SNAPSHOT in a release.
  • Maven Wrapper: the files mvnw, mvnw.cmd and .mvn/ download and use a fixed Maven version, so every developer and the CI server build with the same one. Run ./mvnw clean install (Linux/macOS) or mvnw.cmd clean install (Windows). Spring Initializr adds it automatically; mvn wrapper:wrapper adds it to an existing project. Commit it to Git.

Multi-module projects (a glimpse)

Large systems split into modules (for example common, order-service, payment-service) under a parent POM with <packaging>pom</packaging> and a <modules> list. Children inherit the parent's properties, dependencyManagement and plugin settings. Build a single module and what it needs with mvn -pl order-service -am install.

Rules

  • The packaged artifact is target/<artifactId>-<version>.jar.
  • Running a phase runs all earlier phases; mvn install therefore runs the tests.
  • Do not commit target/ (add it to .gitignore); do commit pom.xml and the wrapper files.
  • Test dependencies must have <scope>test</scope>, or they end up in the shipped application.

Conventions

  • Define versions once in <properties> or dependencyManagement; never hard-code the same version in several places.
  • Set Java with maven.compiler.release (not only source/target), so the code is checked against that version's API.
  • Pin plugin versions for reproducible builds.
  • Keep dependencies minimal; remove unused ones. Every dependency is code you must keep updated and secure.

Common mistakes

  • Abusing -DskipTests. Skipping tests to "make the build pass" hides real failures and ships bugs. Use it only for a quick local packaging when you have just run the tests, never in the CI pipeline for release builds.
  • Wrong scope: a JDBC driver at test scope (the app fails at runtime with "No suitable driver"), or Lombok at compile in a WAR.
  • Putting JARs in the project folder instead of using dependencies.
  • IDE shows red code after editing pom.xml: reload the Maven project (the small "m" button or Ctrl+Shift+O in the Maven window).
  • A corrupt download in ~/.m2 (.lastUpdated files): delete the artifact's folder or run mvn -U.

Errors you will meet

  • Could not resolve dependencies — wrong coordinates, no network/proxy, or a private repository without credentials.
  • invalid target release: 21 or release version 21 not supported — Maven is running on an older JDK than the release you set. Check mvn -version and JAVA_HOME.
  • No tests were executed or tests silently not found — the class name does not match the Surefire pattern, or the JUnit version is wrong for the Surefire plugin.
  • Could not find or load main class — the manifest has no mainClass; plain jar packaging also does not include dependencies, which is why Spring Boot uses its own plugin.

Interview: "What is Maven? Explain the lifecycle and dependency scopes."

  • Build and dependency-management tool driven by pom.xml; coordinates groupId, artifactId, version; standard layout; central repository and ~/.m2 cache.
  • Lifecycle phases in order: validate, compile, test, package, verify, install, deploy; running one runs the earlier ones; plugin goals do the work.
  • Scopes: compile, provided, runtime, test. Transitive dependencies, nearest-wins conflict resolution, dependencyManagement and BOMs, exclusions.
  • install vs deploy: local repository vs remote repository. SNAPSHOT vs release.
  • Why the wrapper: same Maven version for everyone.

Gradle basics and Maven vs Gradle

Gradle is the other major JVM build tool: build files are code (Kotlin or Groovy), dependencies are declared by configuration such as implementation and testImplementation, and everything you run is a task.

Gradle is used by Android projects and by many Java and Kotlin teams. Spring Initializr offers both Maven and Gradle, so you should be able to read a Gradle build even if your team uses Maven. Instead of XML, Gradle uses a script, written in the Kotlin DSL (build.gradle.kts, the current default) or the Groovy DSL (build.gradle).

plugins {
    java                                   // adds compileJava, test, jar, build ...
    application                            // adds the run task
}

group = "com.shop"
version = "1.0.0"

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))   // build with Java 21
    }
}

repositories {
    mavenCentral()                         // same Maven Central, same artifacts
}

dependencies {
    implementation("ch.qos.logback:logback-classic:1.5.6")   // compile + runtime
    runtimeOnly("org.postgresql:postgresql:42.7.3")          // runtime only
    testImplementation(platform("org.junit:junit-bom:5.10.2"))
    testImplementation("org.junit.jupiter:junit-jupiter")    // tests only
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

application {
    mainClass.set("com.shop.App")
}

tasks.test {
    useJUnitPlatform()                     // run JUnit 5 tests
}

Tasks and the wrapper

Gradle's unit of work is a task. Plugins add tasks; tasks depend on one another, forming a graph, and Gradle runs only what is needed (and skips tasks whose inputs did not change: UP-TO-DATE). Always use the Gradle Wrapper (gradlew / gradlew.bat plus gradle/wrapper/), which fetches the right Gradle version, just like mvnw.

$ ./gradlew build              # compile, test, assemble the JAR (output in build/libs)
$ ./gradlew test               # run tests only
$ ./gradlew clean build        # delete build/ first
$ ./gradlew run                # run the application plugin's main class
$ ./gradlew tasks              # list available tasks
$ ./gradlew dependencies       # print the dependency tree
$ ./gradlew build -x test      # build but exclude the test task

On Windows use gradlew.bat (or .\gradlew in PowerShell). Gradle puts its output under build/ (Maven uses target/) and caches downloads in ~/.gradle. A project also has settings.gradle.kts that names the project and lists modules.

Common mistakes

  • Using a globally installed gradle instead of the wrapper, so teammates and CI use other versions.
  • Forgetting useJUnitPlatform(): Gradle then finds no JUnit 5 tests.
  • Using implementation where a JDBC driver should be runtimeOnly, or api everywhere, which leaks dependencies.

Interview: "Maven vs Gradle?"

  • Both manage dependencies and builds from Maven Central. Maven: XML, fixed lifecycle, convention. Gradle: script-based, task graph, incremental builds and caching, more flexible.
  • Map the vocabulary: scope test ↔ testImplementation, provided ↔ compileOnly, runtime ↔ runtimeOnly, phase ↔ task.
  • Say which you use and why; show you can read the other.

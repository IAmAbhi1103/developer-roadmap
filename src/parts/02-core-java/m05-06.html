var and text blocks

var (Java 10) lets the compiler infer the type of a local variable from its initializer, and text blocks (Java 15) let you write multi-line strings between triple quotes without escape noise.

var: local variable type inference

var tells the compiler: "work out the type from the right-hand side". The variable is still statically typed; the type is fixed at compile time and you cannot later put a different type into it. It is not dynamic typing like JavaScript.

import java.util.*;

public class VarDemo {
    public static void main(String[] args) {
        var name = "Asha";                       // String
        var count = 3;                           // int
        var prices = new ArrayList<Double>();   // ArrayList<Double>
        var byCity = new HashMap<String, List<String>>();

        prices.add(499.5);
        byCity.computeIfAbsent("Pune", k -> new ArrayList<>()).add("Asha");

        for (var p : prices) {                   // double -> Double
            System.out.println(p);
        }
        // count = "three";   // compile error: int cannot hold a String
        System.out.println(name + " " + count + " " + byCity);
    }
}
499.5
Asha 3 {Pune=[Asha]}

Readability guidance

var removes repetition when the type is obvious: var users = new ArrayList<User>() is better than ArrayList<User> users = new ArrayList<User>(). It hurts when the reader cannot see the type. Compare:

Wrong: the type is a mystery

var result = service.process(request);
var data = repo.load(id);
var x = compute() / 3;      // int? long? double?

Right: obvious from the right side

var users = new ArrayList<User>();
var path = Path.of("orders.csv");
Invoice result = service.process(request);

Good habits: use meaningful variable names (the name now carries more meaning), keep methods short so the declaration is near the use, and write the explicit type when the right-hand side is a method call whose return type is not obvious. Two traps: var list = new ArrayList<>() infers ArrayList<Object> because the diamond has no target type; and var n = 10 is an int, so use 10L if you want a long. Also, var is not a keyword but a "reserved type name": you can still have a variable called var, but you cannot name a class var.

Text blocks

Before Java 15, a JSON or SQL string in code was a mess of \", \n and +. A text block starts with """ followed by a line break and ends with """.

public class TextBlockDemo {
    public static void main(String[] args) {
        String json = """
                {
                  "orderId": 1001,
                  "customer": "Asha",
                  "items": ["pen", "notebook"]
                }
                """;
        System.out.print(json);

        String sql = """
                SELECT id, name
                FROM employees
                WHERE department = 'IT'
                ORDER BY name
                """;
        System.out.println(sql.lines().count() + " lines of SQL");
    }
}
{
  "orderId": 1001,
  "customer": "Asha",
  "items": ["pen", "notebook"]
}
4 lines of SQL

The SQL text block has four lines (SELECT, FROM, WHERE, ORDER BY). The closing """ on its own line adds a final line break to the string but no extra line for lines().

Indentation rules

  1. Java finds the least-indented line among all content lines and the line with the closing """, and removes that much leading white space from every line. This is called incidental white space.
  2. So the closing delimiter controls the indent. If you put """ on its own line at the left edge, nothing more is removed; if you put it at the end of the last content line, there is no final line break.
  3. Trailing spaces on each line are removed.
  4. Line breaks inside are normalized to \n, whatever the source file uses.

Escapes: \, \s and quotes

  • A backslash at the end of a line joins it with the next line (no line break is inserted). Good for long single-line text in your source.
  • \s is a single space and is not trimmed, so use it to keep trailing space.
  • Normal escapes (\n, \t, \", \\) work. A single " needs no escape. To write three quotes in a row, escape one: \""".
String msg = """
        Dear %s, your order %d has shipped. \
        It will arrive by %s.
        """.formatted("Asha", 1001, "Friday");
System.out.print(msg);
Dear Asha, your order 1001 has shipped. It will arrive by Friday.

String.formatted(...) (Java 15) is the same as String.format(this, ...), and it chains nicely after a text block. Related String methods you will use with them: stripIndent(), translateEscapes() and lines().

Rules

  • The opening """ must be followed by a line break; content on the same line is a compile error.
  • A text block is still a normal String: same type, immutable, works with equals.
  • var needs an initializer that tells the type; use it only for local variables.

Mistake: building SQL from user input in a text block

A text block makes SQL easier to read, but concatenating user values into it is still SQL injection. Use PreparedStatement parameters or named parameters in Spring.

Interview: "Is var dynamic typing?"

  • No. It is compile-time inference; the type is fixed.
  • Only for locals, loop variables and lambda parameters; not fields or method signatures.
  • Use it when the type is clear from the right side; avoid it when it hides the type.

Switch expressions, arrow labels and yield

Since Java 14 a switch can be an expression that produces a value, uses arrow labels with no fall-through, groups labels with commas, and must cover every possible input.

The old switch and its problems

The classic switch statement uses case X: with break. Forget one break and execution falls through into the next case, a famous source of bugs. You also needed a temporary variable to get a value out of it.

int days;
switch (month) {
    case "FEB":
        days = 28;
        break;
    case "APR": case "JUN": case "SEP": case "NOV":
        days = 30;
        break;
    default:
        days = 31;      // forgetting a break above would silently change results
}

The new switch expression

public class SwitchDemo {
    enum Day { MON, TUE, WED, THU, FRI, SAT, SUN }

    static String typeOf(Day d) {
        return switch (d) {                    // switch is an expression: it has a value
            case SAT, SUN -> "Weekend";        // several labels in one case
            case MON, TUE, WED, THU, FRI -> "Weekday";
        };                                     // no default needed: all enum values covered
    }

    static int days(String month, boolean leap) {
        return switch (month) {
            case "FEB" -> leap ? 29 : 28;
            case "APR", "JUN", "SEP", "NOV" -> 30;
            default -> 31;                     // required for String: values are unbounded
        };
    }

    public static void main(String[] args) {
        System.out.println(typeOf(Day.SUN));
        System.out.println(days("FEB", true));
        System.out.println(days("JAN", false));
    }
}
Weekend
29
31

Differences you must remember:

  • Arrow labels (->) do not fall through. Only the code to the right runs. No break is needed.
  • The right side of an arrow is an expression, a block { ... }, or a throw statement.
  • A switch expression must be exhaustive: every possible value needs a result. For an enum you can list all constants; for int, String and other open types you need default.
  • You can use the arrow form as a statement too (no value needed, and then exhaustiveness is not required for old-style types).

Blocks and yield

When a case needs several statements, use a block and give the value with yield.

static double shippingCost(String zone, double weightKg) {
    return switch (zone) {
        case "LOCAL" -> 40;
        case "METRO" -> {
            double base = 60;
            double extra = Math.max(0, weightKg - 1) * 20;
            yield base + extra;                      // value of this case
        }
        case "REMOTE" -> {
            if (weightKg > 20) {
                throw new IllegalArgumentException("Too heavy for remote delivery");
            }
            yield 150 + weightKg * 30;
        }
        default -> throw new IllegalArgumentException("Unknown zone: " + zone);
    };
}

yield works in the old colon style as well, for people who prefer it:

int code = switch (status) {
    case "OK":
        yield 200;
    case "NOT_FOUND":
        yield 404;
    default:
        yield 500;
};

Do not mix arrows and colons in one switch; that is a compile error.

What can you switch on?

int, char, short, byte (and their wrappers), String, enums, and, since Java 21, any reference type with patterns (see pattern matching). Not long, float, double or boolean.

Rules

  • A switch expression must produce a value on every path: either cover all cases or add default.
  • Inside a switch expression you cannot break, continue or return out of it. Use yield for a value or throw.
  • String case labels must be compile-time constants and unique; duplicate labels do not compile.

Exceptions and edge cases

  • NullPointerException — switching on a null String or enum (unless you use a pattern switch with case null).
  • MatchException (Java 21) — an exhaustive switch with no default meets an enum constant or subtype that was added after the switch was compiled (only possible when jars are compiled separately).
  • Omitting default on an enum is a feature: when you add a new constant, the compiler flags every switch expression that does not handle it.

Convention

Prefer arrow switch for new code. Skip default for enums and sealed types so the compiler checks exhaustiveness for you. Keep each case short; move long logic into a method and call it.

Result type, scope and statements

All arms of a switch expression must produce values that fit one type. If the arms give int and double, the result is double, just like a conditional ?:. If you assign the switch to a variable, every arm must be compatible with that variable. Each arm also has its own scope, so two cases can declare a local with the same name without clashing, which was a trap in the old form.

An arrow case can also be a plain statement when the switch is a statement. Then the right side is an expression statement, a block or a throw:

enum Event { PLACED, PACKED, SHIPPED, DELIVERED, CANCELLED }

static void notifyCustomer(Event e, String orderId) {
    switch (e) {                                       // a statement, arrow form
        case PLACED, PACKED -> System.out.println("Order " + orderId + " is being prepared");
        case SHIPPED -> System.out.println("Order " + orderId + " is on the way");
        case DELIVERED -> {
            System.out.println("Order " + orderId + " delivered");
            System.out.println("Please rate your experience");
        }
        case CANCELLED -> throw new IllegalStateException("No message for cancelled orders");
    }
}

As a rule: if you want a value, use an expression and make the compiler check coverage; if you only want a side effect, the statement form is fine.

HTTP status to message: a realistic example

static String describe(int status) {
    return switch (status / 100) {                    // group by the first digit
        case 2 -> status == 204 ? "No content" : "Success";
        case 3 -> "Redirect";
        case 4 -> switch (status) {                   // a switch inside a switch
            case 400 -> "Bad request";
            case 401, 403 -> "Not allowed";
            case 404 -> "Not found";
            default -> "Client error";
        };
        case 5 -> "Server error";
        default -> throw new IllegalArgumentException("Not an HTTP status: " + status);
    };
}

// describe(204) → No content    describe(403) → Not allowed    describe(503) → Server error

Old-style fall-through still has a place

A colon switch statement can fall through on purpose, for example to run steps from some point onward. The arrow form cannot do this; there you list the labels instead. Prefer the arrow form unless you truly want the cascade, and mark deliberate fall-through with a comment.

switch (stage) {
    case "ORDER":   validate();       // falls through
    case "PAYMENT": charge();         // falls through
    case "SHIP":    dispatch();       // ORDER runs all three; SHIP runs only this one
}

Wrong: leaving the expression with return or break

String label = switch (code) {
    case 1 -> "one";
    case 2 -> { return "two"; }   // compile error
    default -> { break; }          // compile error
};

Right: yield the value

String label = switch (code) {
    case 1 -> "one";
    case 2 -> { yield "two"; }
    default -> "many";
};

Common mistakes

  • Mixing -> and : in the same switch is a compile error.
  • Forgetting default on a String or int switch expression. The compiler reports that the switch expression does not cover all possible input values.
  • Adding default to an enum switch "to be safe". It hides the compile error that would tell you a new constant is unhandled. Leave it out unless unknown values are truly possible.
  • Using a non-constant as a label. case limit -> compiles only if limit is a final variable with a constant value.
  • Writing a method called yield and calling it unqualified. yield is a restricted identifier now; call Thread.yield() with the class name.

More edge cases

  • Switching on an enum in a separate module or jar: if a new constant is added later and the switch is not recompiled, an exhaustive switch expression without default throws MatchException (older versions threw IncompatibleClassChangeError).
  • A throw arm has no value, so it fits any result type. It is the usual way to reject unknown input in a default arm.
  • Since Java 21 you may also write the enum constant with its type name (case Day.SAT). Both forms work.
  • A switch statement over a String compares with equals internally (through the hash code first), so it is case-sensitive: "fri" does not match "FRI". Normalise with toUpperCase() first.

In real projects

Switch expressions are common for mapping an enum to a label, a fee, a Spring HttpStatus or an error code; for choosing a strategy by a request type; and for turning a database status string into a domain enum. When the same switch appears in many places, that is a hint to move the behaviour into the enum itself (an abstract method per constant) or into a sealed hierarchy with pattern matching.

Interview: "What is new in switch since Java 14?"

  • Switch as an expression with a value; arrow labels; comma-separated labels; no fall-through.
  • yield returns a value from a block; exhaustiveness is enforced.
  • Java 21 adds pattern matching, guards (when) and case null.

Pattern matching: instanceof, record patterns and switch

Pattern matching lets you test a value's type and pull it apart in one step: instanceof binds a typed variable (Java 16), record patterns deconstruct records, and switch can choose by type with guards and null handling (Java 21).

Pattern matching for instanceof (Java 16)

The old code tests the type and then casts, repeating the type name three times:

if (obj instanceof String) {
    String s = (String) obj;
    System.out.println(s.length());
}

With a type pattern you declare the variable in the test. If the test is true, the variable is already cast:

if (obj instanceof String s) {
    System.out.println(s.length());
}
// combined with a condition (s is in scope on the right of &&)
if (obj instanceof String s && s.length() > 5) {
    System.out.println(s.toUpperCase());
}

The binding variable s exists only where the compiler can prove the test was true. That is the "scope of a pattern variable":

if (!(obj instanceof String s)) {
    return;                    // leave early when it is NOT a String
}
System.out.println(s.length());   // s is in scope here: we only get here if it matched

// if (obj instanceof String s || s.isEmpty())   // compile error: s not definite in ||

A typical use is a clean equals method: return o instanceof Point p && x == p.x && y == p.y;. Note that instanceof is false for null, so no extra null check is needed.

Record patterns (Java 21)

A record (see Module 2) is a transparent holder of data, so Java can take it apart in a pattern. The pattern Point(int x, int y) checks the type and extracts the components.

record Point(int x, int y) { }
record Line(Point from, Point to) { }

static String describe(Object o) {
    if (o instanceof Point(int x, int y)) {
        return "Point at " + x + "," + y;
    }
    if (o instanceof Line(Point(var x1, var y1), Point(var x2, var y2))) {   // nested
        return "Line from " + x1 + "," + y1 + " to " + x2 + "," + y2;
    }
    return "Unknown";
}

Nested patterns remove chains of getter calls. Inside a record pattern you can use var to infer a component's type.

Pattern matching for switch (Java 21)

A switch can now have type patterns as labels. This replaces long if / else if (x instanceof ...) chains. Consider payments:

public class SwitchPatterns {
    sealed interface Payment permits Upi, Card, Cash { }
    record Upi(String vpa) implements Payment { }
    record Card(String last4, boolean credit) implements Payment { }
    record Cash(int amount) implements Payment { }

    static String fee(Payment p) {
        return switch (p) {
            case Upi u -> "No fee for " + u.vpa();
            case Card(String last4, boolean credit) when credit -> "2% fee on card " + last4;
            case Card c -> "Flat Rs 5 on debit card " + c.last4();
            case Cash(int amount) when amount > 50_000 -> "Cash limit exceeded";
            case Cash c -> "No fee";
        };
    }

    static String show(Object o) {
        return switch (o) {
            case null -> "null value";
            case Integer i when i > 100 -> "big int " + i;
            case Integer i -> "int " + i;
            case String s -> "text of length " + s.length();
            case int[] arr -> "int array of " + arr.length;
            default -> "something else: " + o;
        };
    }

    public static void main(String[] args) {
        System.out.println(fee(new Upi("asha@upi")));
        System.out.println(fee(new Card("4242", true)));
        System.out.println(fee(new Cash(60_000)));
        System.out.println(show(500));
        System.out.println(show(7));
        System.out.println(show(null));
    }
}

Guards, order and dominance

  • A guard is when condition after the pattern. The case matches only if the pattern matches and the condition is true.
  • Labels are tested top to bottom. A label that can never match because an earlier one covers it is a compile error: this is dominance. case Integer i placed before case Integer i when i > 100 does not compile. Put guarded and more specific cases first.
  • A switch with patterns must be exhaustive. Over a sealed type (see sealed classes) it is exhaustive when all permitted subtypes are covered; otherwise add default.

Handling null

The old rule stays: a switch throws NullPointerException for a null selector. To handle null, add case null (as above), or case null, default -> to treat null like the default. This is opt-in, so old code does not change behaviour.

Rules

  • A pattern variable is in scope only where the match is certain; you cannot use it in an || branch or after a failed test.
  • Pattern switches must be exhaustive and must not have dominated labels.
  • when guards can use pattern variables but should be simple, side-effect-free conditions.

Exceptions and edge cases

  • NullPointerException — a pattern switch with no case null receives null.
  • MatchException — thrown if an exhaustive switch (or a record pattern whose accessor throws) finds no match at run time, for example after a sealed hierarchy was extended without recompiling the switch.
  • An instanceof pattern that the compiler knows always matches (for example String s instanceof String t) is allowed in modern Java, but gives no benefit.
  • Generic types: obj instanceof List<String> l is an error unless the check is safe; use List<?>.

Versions

Pattern matching for instanceof: final in Java 16. Pattern matching for switch and record patterns: final in Java 21 (both were previews in Java 17 to 20). Java 25 has primitive types in patterns still as a preview feature; do not rely on it.

Real projects

Pattern switches over sealed types model domain results cleanly: Success / Failure results from a payment gateway, AST nodes in a parser, event types in an event-sourced system. They replace the visitor pattern in many places.

Interview: "What is pattern matching for instanceof / switch?"

  • Test and cast in one step with a scoped binding variable.
  • Record patterns deconstruct records, also nested.
  • Switch by type with when guards, case null, dominance rules and exhaustiveness.

Sealed classes and interfaces

A sealed class or interface lists exactly which classes may extend it, so the compiler knows every subtype and can check switch statements for completeness.

The problem

Normally any class can extend your class, and any class can implement your interface. With final nobody can extend; with a public class everybody can. Often you want something in between: "a Shape is a Circle, a Rectangle or a Triangle and nothing else". Before Java 17 you could only fake this with package-private constructors. A sealed type states the closed list of subtypes in the language itself.

Syntax

public sealed interface Shape permits Circle, Rectangle, Triangle { }

public record Circle(double radius) implements Shape { }
public record Rectangle(double width, double height) implements Shape { }
public final class Triangle implements Shape {
    final double base, height;
    public Triangle(double base, double height) { this.base = base; this.height = height; }
}

Each permitted subclass must choose exactly one modifier:

ModifierMeaning
finalNo more subclasses. Records and enums are implicitly final
sealedContinues the closed hierarchy with its own permits list
non-sealedOpens that branch again: anyone may extend it
 
public abstract sealed class Account permits Savings, Current, Loan { }
public final class Savings extends Account { }
public non-sealed class Current extends Account { }   // others may extend Current
public sealed class Loan extends Account permits HomeLoan, CarLoan { }
public final class HomeLoan extends Loan { }
public final class CarLoan extends Loan { }

If the subclasses are in the same source file as the sealed type, you can leave out permits and the compiler infers the list. Otherwise they must be in the same package (or the same named module) as the sealed class.

The big benefit: exhaustive switch

static double area(Shape s) {
    return switch (s) {
        case Circle c -> Math.PI * c.radius() * c.radius();
        case Rectangle r -> r.width() * r.height();
        case Triangle t -> 0.5 * t.base * t.height;
        // no default: the compiler knows these three are all the Shape subtypes
    };
}

Now somebody adds Pentagon to the permits list. Every switch that does not handle it fails to compile, so you find all the places that need updating. With an ordinary interface you would get a silent bug at run time. If you add a default, you lose this safety: avoid default when the type is sealed.

Sealed result types

A very common modern pattern is a sealed type for "one of several outcomes", which models success and failure without exceptions for expected cases:

sealed interface PaymentResult {
    record Success(String txnId) implements PaymentResult { }
    record Declined(String reason) implements PaymentResult { }
    record GatewayDown(int retryAfterSeconds) implements PaymentResult { }
}

static String message(PaymentResult r) {
    return switch (r) {
        case PaymentResult.Success s -> "Paid, ref " + s.txnId();
        case PaymentResult.Declined d -> "Declined: " + d.reason();
        case PaymentResult.GatewayDown g -> "Try again in " + g.retryAfterSeconds() + "s";
    };
}
Declined: low balance

Rules

  • Every permitted subclass must directly extend or implement the sealed type, and must be final, sealed or non-sealed.
  • Permitted subclasses must be accessible: same package, or same module, or same file.
  • A sealed class cannot be anonymous or a lambda target (a sealed interface is not a functional interface target).

Exceptions and edge cases

  • IncompatibleClassChangeError / MatchException — a class is loaded that is not in the permitted list, or a switch meets an unknown subtype at run time. This happens when jars are compiled separately.
  • Reflection: Class.isSealed() and getPermittedSubclasses() read the list at run time.
  • Sealed does not mean immutable; the subclasses can have mutable fields.

Versions

Sealed classes were a preview in Java 15 and 16 and became final in Java 17 (LTS). Exhaustive pattern switches over them are final in Java 21.

Sealed vs final vs package-private

The difference with the old trick is important: sealing is part of the type, so the compiler can use it, and the JVM enforces it at run time too. The sealed type can still be public and used everywhere; only extending it is restricted.

A recursive hierarchy: a small expression tree

Sealed types shine for data that is "one of these shapes", especially recursive data such as expressions, JSON values or UI events. With records and Java 21 record patterns the evaluator reads like the definition:

sealed interface Expr permits Num, Add, Mul { }
record Num(int value) implements Expr { }
record Add(Expr left, Expr right) implements Expr { }
record Mul(Expr left, Expr right) implements Expr { }

public class ExprDemo {
    static int eval(Expr e) {
        return switch (e) {
            case Num n -> n.value();
            case Add(Expr l, Expr r) -> eval(l) + eval(r);      // record pattern
            case Mul(Expr l, Expr r) -> eval(l) * eval(r);
        };
    }

    public static void main(String[] args) {
        Expr e = new Add(new Num(2), new Mul(new Num(3), new Num(4)));   // 2 + 3 * 4
        System.out.println(eval(e));
        System.out.println(e);
    }
}

Common mistakes

  • Adding default to a switch over a sealed type. It compiles, but then a new subtype is handled by the fallback silently and you lose the compile-time check.
  • Using non-sealed without thinking. It reopens that branch to every class, so exhaustive switches still work (the non-sealed class itself is a case) but you no longer know all the real subtypes.
  • Sealing a type that other teams need to extend. Sealing is a design decision: a library that wants plug-in subclasses should stay open.
  • Forgetting that a sealed interface lists direct subtypes only. A class that extends a permitted non-sealed class is allowed, but it is not in the permits list.

More edge cases

  • Compile errors you will meet: "class is not allowed to extend sealed class" (the class is not in permits), and "sealed, non-sealed or final modifiers expected". Both are caught at compile time.
  • A final class cannot also be sealed; local classes and anonymous classes cannot be sealed or extend a sealed class.
  • A sealed class needs at least one permitted subclass. An enum can implement a sealed interface; its constants count as one permitted type.
  • With permits omitted, the subclasses must be in the same source file. Subclasses spread over several files need an explicit permits.
  • Sealed types and serialization libraries: JSON libraries such as Jackson do not guess which subtype to build from JSON. You still declare the type information yourself (for example with @JsonTypeInfo and @JsonSubTypes).

Conventions

  • Prefer a sealed interface with records for data variants; use a sealed abstract class only when the variants share state or code.
  • Nest the variants inside the sealed interface when they belong together (as in PaymentResult); then permits can be left out.
  • Keep the hierarchy shallow. Two levels cover almost all domain models.
  • Do not add default to switches over sealed types.

In real projects

Typical uses: API or service results (Success / Failure / Retry), domain events (OrderPlaced, OrderShipped), parser and rule-engine syntax trees, state machines, and commands in a message handler. Adding a case then forces every handler to be reviewed. Remember that adding a subtype to a published library is a breaking change for callers who switch exhaustively on it.

Interview: "What is a sealed class and why use it?"

  • It restricts which classes can extend it (permits); subclasses are final, sealed or non-sealed.
  • Gives you closed hierarchies for domain modelling and exhaustive switches without default.
  • Works well with records.

Sequenced collections and unnamed variables

Java 21 adds getFirst, getLast and reversed to every collection that has a defined order, and Java 22 lets you write _ for variables you do not use.

The problem with "first" and "last"

Before Java 21, getting the first and last element looked different for every collection: list.get(0) and list.get(list.size() - 1) for a list; deque.getFirst() for a deque; sortedSet.first() for a SortedSet; linkedHashSet.iterator().next() for a LinkedHashSet, and no easy way at all for the last one. Reversing was just as inconsistent.

New interfaces

Three new interfaces describe collections with an encounter order (a defined first, second, ... last): SequencedCollection, SequencedSet and SequencedMap. List, Deque, LinkedHashSet, SortedSet/TreeSet, LinkedHashMap and SortedMap/TreeMap now implement them. HashSet and HashMap do not, because they have no order.

import java.util.*;

public class SequencedDemo {
    public static void main(String[] args) {
        List<String> steps = new ArrayList<>(List.of("Cart", "Address", "Payment"));
        System.out.println(steps.getFirst());          // Cart  (was steps.get(0))
        System.out.println(steps.getLast());           // Payment
        steps.addFirst("Login");
        System.out.println(steps.reversed());

        LinkedHashSet<String> seen = new LinkedHashSet<>(List.of("a", "b", "c"));
        System.out.println(seen.getLast());            // c  (impossible before 21)

        LinkedHashMap<String, Integer> stock = new LinkedHashMap<>();
        stock.put("pen", 10);
        stock.put("book", 4);
        System.out.println(stock.firstEntry());
        System.out.println(stock.reversed());
    }
}

Edge cases

  • NoSuchElementException — getFirst() or getLast() on an empty collection. Compare with list.get(0), which throws IndexOutOfBoundsException.
  • UnsupportedOperationException — addFirst on List.of(...), or on a TreeSet (its position is decided by the sort order).
  • A custom List implementation compiled against old versions gets default implementations of the new methods, so it keeps working.
  • The name clash risk: if your own interface already had getFirst() with a different return type, upgrading to 21 could break compilation. Rare, but it is a known migration note.

Unnamed variables and patterns: _ (Java 22)

Sometimes the language forces you to declare a variable that you never use. Java 22 allows the underscore _ as the name, which says clearly "I ignore this" and stops IDE warnings. (Using _ as an identifier was an error from Java 9 to 21.)

// 1. Unused catch parameter
try {
    Integer.parseInt(input);
} catch (NumberFormatException _) {
    System.out.println("Not a number");
}

// 2. Unused loop variable: just counting
int total = 0;
for (var _ : orders) {
    total++;
}

// 3. Unused lambda parameter
map.computeIfAbsent(city, _ -> new ArrayList<>()).add(name);

// 4. Unused part of a record pattern
if (shape instanceof Rectangle(var w, _)) {   // only width matters
    System.out.println("width " + w);
}

// 5. try-with-resources you only need to open
try (var _ = lock.acquire()) { /* ... */ }

// 6. In a switch pattern: ignore the binding
case Card _ -> "card payment";

Rules: _ cannot be read, and you can declare it many times in one scope (each is a separate unused variable). It cannot be used for fields or method parameters. A single _ as a pattern alone (an unnamed pattern) matches anything inside a record pattern.

Versions

Sequenced collections: final in Java 21. Unnamed variables and patterns: preview in Java 21, final in Java 22. If you are on Java 17, neither is available.

Interview: "What did Java 21 add to collections?"

  • SequencedCollection/Set/Map give uniform getFirst, getLast, addFirst, removeLast and reversed().
  • reversed() returns a view, not a copy.
  • Hash-based collections are not sequenced.

From Java 8 to Java 25: the LTS timeline

Java ships a new version every six months, but only the long-term support (LTS) releases 8, 11, 17, 21 and 25 are used for years in production; knowing the headline features of each lets you read old code and use new features safely.

Release model

Since Java 9, a feature release arrives every March and September. Most releases get support for only six months. An LTS (long-term support) release gets patches for years from vendors such as Oracle, Eclipse Temurin, Amazon Corretto and Microsoft. Companies upgrade from LTS to LTS. Today (late 2026) Java 25 is the newest LTS; Java 21 and 17 are both common; Java 8 and 11 remain in older systems. Spring Boot 3.x needs Java 17 or newer, and Spring Boot 4.x also has Java 17 as its baseline.

Structured concurrency, primitive patterns and a few other APIs were still previews in Java 25; do not use preview features in production code (they need --enable-preview).

What the move between LTS versions means for you

  • 8 to 11: mainly runtime and library changes. Old Java EE modules (JAXB, JAX-WS) and some internal APIs (sun.misc.*) were removed or locked, so old apps need dependency updates.
  • 11 to 17: the biggest language upgrade: records, text blocks, switch expressions, sealed classes, pattern matching for instanceof. Reflection into JDK internals is blocked by default.
  • 17 to 21: virtual threads, pattern matching for switch, record patterns, sequenced collections.
  • 21 to 25: mostly incremental. Fewer pinning problems for virtual threads, scoped values, simpler first programs, and performance improvements.

Practical guidance

  • New projects: start on Java 21 or 25, depending on what your cloud platform and libraries support.
  • Check your framework's baseline before using a feature (Spring Boot 3 and 4 require 17+; Java 21 is needed for virtual threads).
  • Set maven.compiler.release (or the Gradle toolchain) so the compiler rejects APIs newer than your target.

Interview: "Which Java version are you using and what is new?"

  • Name the LTS you used and 3 or 4 features you actually used: records, text blocks, switch expressions, var, streams.
  • Know the order: lambdas and streams (8), var (10), switch expressions (14), records (16), sealed classes (17), virtual threads and pattern switch (21).

Generics: generic classes, interfaces and methods

Generics let a class or method work with a type that you name later (List<String>), so the compiler checks the types for you and you never write a cast.

Before Java 5 (2004) a list held plain Objects. You could add anything, and you had to cast every value you read. A wrong cast failed only at runtime. Generics move that check to compile time: you write a type parameter in angle brackets, and the compiler makes sure only that type goes in and comes out.

Wrong (raw type): fails at runtime

List names = new ArrayList();
names.add("Asha");
names.add(42);                       // accepted
String s = (String) names.get(1);    // ClassCastException

Right (generic): fails at compile time

List<String> names = new ArrayList<>();
names.add("Asha");
names.add(42);   // error: incompatible types
String s = names.get(0);             // no cast

Generics give you three things: type safety (bugs caught by the compiler), no casts (cleaner code), and reuse (one Box class works for every type, instead of StringBox, IntBox, …).

A generic class

Put the type parameter after the class name. Inside the class, T is used like any other type.

public class Box<T> {
    private T value;

    public Box(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }

    public void set(T value) {
        this.value = value;
    }

    public static void main(String[] args) {
        Box<String> name = new Box<>("Asha");
        Box<Integer> age = new Box<>(30);
        String s = name.get();                 // no cast needed
        int a = age.get() + 1;                 // auto-unboxing
        System.out.println(s + " " + a);
        // name.set(5);                        // compile error: int cannot be converted to String
    }
}
Asha 31

A class can have more than one parameter. Records can be generic too:

public record Pair<A, B>(A first, B second) {
    public Pair<B, A> swap() {
        return new Pair<>(second, first);
    }
}

Pair<String, Integer> p = new Pair<>("Asha", 30);
System.out.println(p + " -> " + p.swap());

A generic interface

Generic interfaces describe a contract for any type. This Repository shape is exactly what Spring Data's CrudRepository<T, ID> looks like:

import java.util.*;

interface Repository<T, ID> {
    void save(T entity);
    Optional<T> findById(ID id);
    List<T> findAll();
}

record Customer(Long id, String name) {}

class InMemoryCustomerRepository implements Repository<Customer, Long> {
    private final Map<Long, Customer> store = new LinkedHashMap<>();

    @Override public void save(Customer c) { store.put(c.id(), c); }
    @Override public Optional<Customer> findById(Long id) {
        return Optional.ofNullable(store.get(id));
    }
    @Override public List<Customer> findAll() { return new ArrayList<>(store.values()); }
}

When you implement a generic interface you either fill in the types (Repository<Customer, Long>) or stay generic (class Cache<T> implements Repository<T, Long>).

A generic method

A generic method declares its own type parameter list before the return type. The method can live in a normal class, and the type parameter is valid only inside that method. Static methods cannot use the class's type parameter, so they must declare their own.

import java.util.*;

public class GenericMethods {
    // <T> before the return type declares the type parameter
    static <T> T firstOrDefault(List<T> list, T fallback) {
        return list.isEmpty() ? fallback : list.get(0);
    }

    static <T> void swap(T[] array, int i, int j) {
        T temp = array[i];
        array[i] = array[j];
        array[j] = temp;
    }

    static <K, V> Map<V, K> invert(Map<K, V> map) {
        Map<V, K> result = new HashMap<>();
        map.forEach((k, v) -> result.put(v, k));
        return result;
    }

    public static void main(String[] args) {
        System.out.println(firstOrDefault(List.of("UPI", "NEFT"), "none"));
        System.out.println(firstOrDefault(new ArrayList<Integer>(), -1));

        String[] cities = {"Pune", "Delhi", "Chennai"};
        swap(cities, 0, 2);
        System.out.println(Arrays.toString(cities));

        System.out.println(invert(Map.of("A", 1)));
        System.out.println(Collections.<String>emptyList());   // explicit type witness
    }
}

Type inference. You almost never write the type argument at the call: the compiler infers T from the arguments (firstOrDefault(List.of("UPI"), "none") gives T = String) and, if needed, from the target (the variable you assign the result to). You write it explicitly — Collections.<String>emptyList(), called a type witness — only when inference fails, which is rare in modern Java. Generic methods can also appear in constructors (<T> MyClass(T x)) and in non-generic classes.

The diamond operator and raw types

The diamond <> (Java 7) tells the compiler to infer the type arguments on the right side: Map<String, List<Order>> m = new HashMap<>();. Since Java 9 it also works with anonymous classes. With var you must put the type on the right: var list = new ArrayList<String>(); — writing var list = new ArrayList<>(); infers ArrayList<Object>.

A raw type is a generic class used without type arguments (List list). It exists only so that pre-Java-5 code still compiles. The compiler cannot check anything on a raw type, and it prints a warning such as Note: Foo.java uses unchecked or unsafe operations. Never use raw types in new code. When you must call old code, confine the cast and add @SuppressWarnings("unchecked") on the smallest possible scope, with a comment explaining why it is safe.

Generics are invariant

Although Integer is a Number, a List<Integer> is not a List<Number>. If it were, this would be legal and break type safety:

List<Integer> ints = new ArrayList<>();
List<Number> nums = ints;       // compile error — suppose it were allowed...
nums.add(3.14);                 // ...then a Double would land in a List<Integer>
int x = ints.get(0);            // ...and this would blow up

Arrays took the opposite choice: Integer[] is a Number[] (arrays are covariant), so the same mistake compiles and fails at runtime with ArrayStoreException. Wildcards (next article) give you safe flexibility when you need it.

Rules

  • Type arguments must be reference types: List<Integer>, never List<int>.
  • The type parameter of a class cannot be used in static members; a static generic method declares its own.
  • A generic method declares its parameters before the return type: public static <T> T pick(…).
  • List<Integer> is not a subtype of List<Number> (invariance), but ArrayList<Integer> is a subtype of List<Integer>.

Conventions

  • Use the standard letters (T, E, K, V, R). Use a longer descriptive name only when several parameters would be confusing.
  • Always use the diamond on the right: new ArrayList<>().
  • Do not write a generic class just because you can. If every use is String, write a normal class.

Exceptions and edge cases

  • ClassCastException at a place that has no cast in your source — the sign of a raw type or unchecked cast polluting a generic collection (see Type erasure).
  • ArrayStoreException — storing a wrong type into a covariant array (Object[] o = new String[1]; o[0] = 1;).
  • NullPointerException — auto-unboxing a null from Box<Integer> into an int.
  • You can specify nested generics: Map<String, List<Order>>; before Java 7 you had to write a space between the closing brackets.

Mistake: using the raw type "to keep it simple"

List list = new ArrayList(); turns off every compile-time check on that variable and throws away the reason generics exist. If you do not care about the element type, write List<?>; if you need Object, write List<Object>.

Real projects

You use generics every day without writing them: ResponseEntity<List<UserDto>>, JpaRepository<User, Long>, Optional<Order>, CompletableFuture<String>. You write your own generic code for shared building blocks: an ApiResponse<T> wrapper, a PageResult<T>, a base service or mapper Mapper<S, T>, a generic cache.

Interview: "Why generics? What is a generic method?"

  • Compile-time type safety, no explicit casts, code reuse.
  • Generic method: declares <T> before the return type; inference picks T from the arguments.
  • Invariance: List<Integer> is not a List<Number>; arrays are covariant and fail at runtime.
  • Raw types exist only for backward compatibility; they bypass checks.

Bounded types and wildcards: extends, super and PECS

Use "T extends X" to limit what a type parameter can be, use "? extends T" for collections you only read from, and "? super T" for collections you only write to — Producer Extends, Consumer Super.

Bounded type parameters

A bare T can be any type, so you can only call Object methods on it. A bound restricts T and in return lets you call the bound's methods. The keyword is extends for both classes and interfaces.

import java.util.*;

public class Bounds {
    // T must be a Number (Integer, Double, BigDecimal, ...)
    static <T extends Number> double sum(List<T> items) {
        double total = 0;
        for (T item : items) {
            total += item.doubleValue();         // allowed because T is a Number
        }
        return total;
    }

    // T must be comparable with itself
    static <T extends Comparable<T>> T max(List<T> items) {
        T best = items.get(0);
        for (T item : items) {
            if (item.compareTo(best) > 0) {
                best = item;
            }
        }
        return best;
    }

    // multiple bounds: ONE class (first) and any number of interfaces, joined by &
    static <T extends Number & Comparable<T>> T largest(T a, T b) {
        return a.compareTo(b) >= 0 ? a : b;
    }

    public static void main(String[] args) {
        System.out.println(sum(List.of(1, 2, 3)));
        System.out.println(sum(List.of(1.5, 2.5)));
        System.out.println(max(List.of("pune", "delhi", "mumbai")));
        System.out.println(largest(7, 12));
        // sum(List.of("a", "b"));    // compile error: String is not a Number
    }
}

Rules for bounds: the class bound must come first (<T extends Number & Comparable<T>>), you can have at most one class, and the same bound syntax is used for interfaces (extends, never implements). A type parameter may refer to itself, as in T extends Comparable<T>; this is called a recursive bound and means "T can compare itself to other Ts". The JDK's own signature is slightly more flexible: <T extends Comparable<? super T>>, which also accepts a class that inherited its compareTo from a parent (a java.sql.Timestamp compares as a Date).

Why wildcards exist

Because List<Integer> is not a List<Number>, this method is too narrow:

static double total(List<Number> nums) { ... }

total(List.of(1, 2, 3));        // compile error: List<Integer> is not List<Number>

The wildcard ? means "some unknown type". Combined with bounds it expresses a whole family of types.

FormMeansCan read asCan write
List<?>List of some unknown typeObjectOnly null
List<? extends Number>List of Number or any subtype (upper bound)NumberOnly null
List<? super Integer>List of Integer or any supertype (lower bound)ObjectInteger (and subtypes)
List<Number>Exactly List<Number>NumberNumber and subtypes

? extends T — read-only "producers"

List<? extends Number> accepts a List<Integer>, a List<Double> or a List<Number>. You can safely read every element as a Number. You cannot add: the real list might be a List<Integer>, and the compiler cannot prove that your Double fits.

static double total(List<? extends Number> nums) {
    double sum = 0;
    for (Number n : nums) {                    // reading is fine
        sum += n.doubleValue();
    }
    // nums.add(1);                            // compile error: cannot add to ? extends
    return sum;
}

System.out.println(total(List.of(1, 2, 3)));        // List<Integer>
System.out.println(total(List.of(1.5, 2.5)));       // List<Double>

? super T — write-only "consumers"

List<? super Integer> accepts a List<Integer>, a List<Number> or a List<Object>. You can safely add an Integer, because every one of those lists can hold it. When you read, you only get Object, since the list might hold anything above Integer.

static void fillWithSquares(List<? super Integer> sink, int count) {
    for (int i = 1; i <= count; i++) {
        sink.add(i * i);                       // writing an Integer is fine
    }
    // Integer first = sink.get(0);            // compile error: only Object comes out
}

List<Number> numbers = new ArrayList<>();
List<Object> objects = new ArrayList<>();
fillWithSquares(numbers, 3);
fillWithSquares(objects, 2);
System.out.println(numbers + " " + objects);

PECS — Producer Extends, Consumer Super

The memory rule from Effective Java: if a parameter produces values you read, use ? extends T. If it consumes values you write, use ? super T. If it does both, use an exact type (no wildcard). A copy method shows both sides: the source produces, the destination consumes.

import java.util.*;

public class Pecs {
    static <T> void copy(List<? super T> dest, List<? extends T> src) {
        for (T item : src) {                   // read from the producer
            dest.add(item);                    // write to the consumer
        }
    }

    public static void main(String[] args) {
        List<Integer> ints = List.of(1, 2, 3);
        List<Number> numbers = new ArrayList<>();
        copy(numbers, ints);                   // T = Integer
        System.out.println(numbers);

        List<Object> objects = new ArrayList<>();
        copy(objects, List.of("a", "b"));      // T = String
        System.out.println(objects);
    }
}

[a, b]

The JDK follows PECS everywhere, which is why signatures look scary but make sense:

MethodWhy the wildcard
Collection.addAll(Collection<? extends E> c)The argument produces Es you read
Collections.copy(List<? super T> dest, List<? extends T> src)Exactly the example above
List.sort(Comparator<? super E> c)A Comparator<Object> or Comparator<Number> can order Integers; the comparator consumes elements
Stream.map(Function<? super T, ? extends R> f)The function consumes Ts and produces Rs
Collectors.toMap(Function<? super T, ? extends K>, …)Same idea

The unbounded wildcard List<?>

Use ? when the code does not care about the element type and only uses Object methods or size().

static void printAll(Collection<?> items) {
    for (Object o : items) {
        System.out.println(o);
    }
}

printAll(List.of(1, 2));
printAll(Set.of("x"));
List<?> unknown = new ArrayList<String>();
// unknown.add("a");      // compile error — only null may be added

List<?> is not the same as List<Object>. A List<Object> accepts adds but only matches lists of exactly Object; a List<?> accepts any list but you cannot add to it.

Wildcard capture: a helper method

Sometimes you need to modify a List<?> and the compiler refuses, because it does not know the element type. The trick is a private generic helper: calling it makes the compiler "capture" the unknown type as a name.

static void swapFirstAndLast(List<?> list) {
    swapHelper(list);                          // the unknown type is captured as T
}

private static <T> void swapHelper(List<T> list) {
    T first = list.get(0);
    list.set(0, list.get(list.size() - 1));
    list.set(list.size() - 1, first);
}

Choosing between the three

  • Method only reads elements: List<? extends T>.
  • Method only adds elements: List<? super T>.
  • Method both reads and adds, or returns elements of the same type it was given: use a type parameter <T> … List<T>.
  • Does not care about the type: List<?>.
  • Do not use wildcards in return types — they force callers to deal with them. Return List<Integer>, not List<? extends Number>.

Rule: you cannot add to a "? extends" collection or read specific types from "? super"

With List<? extends Number> the only value you may add is null. With List<? super Integer> everything you read is typed as Object. Wildcards cannot be used when creating an object: new ArrayList<?>() is an error (use new ArrayList<Object>() or new ArrayList<>()).

Conventions

  • Apply PECS to method parameters, which gives callers flexibility; keep return types exact.
  • Prefer a wildcard over a type parameter when the type appears only once in the signature: double total(List<? extends Number> list) is clearer than <T extends Number> double total(List<T> list).
  • Use Comparable<? super T> and Comparator<? super T> in your own generic utilities, as the JDK does.

Exceptions and edge cases

  • The compile errors people see: incompatible types: String cannot be converted to CAP#1 (adding to ? extends) and incompatible types: CAP#1 cannot be converted to Integer (reading specific types from ? super). "CAP#1" is the compiler's name for the captured unknown type.
  • You can still call remove(Object), contains(Object), clear() and size() on a List<? extends X>; they do not take E.
  • ? extends does not apply to primitive arrays or primitives; use the wrapper type.

Mistake: using List<Number> as a parameter and being surprised

A method that takes List<Number> rejects List<Integer> and List<Double>. If it only reads, change it to List<? extends Number>.

Interview: "Explain ? extends vs ? super — what is PECS?"

  • ? extends T = some subtype of T: safe to read as T, not safe to write. ? super T = some supertype of T: safe to write T, reads give Object.
  • PECS: Producer Extends, Consumer Super. Give the copy(dest, src) example and say which side is which.
  • Why List<Integer> is not a List<Number> (invariance) and how wildcards fix it safely.
  • Name JDK examples: Collections.copy, List.sort(Comparator<? super E>), Stream.map.

Type erasure and the limits of generics

The compiler checks generic types and then erases them, so at runtime a List<String> is just a List — which is why you cannot do new T(), new T[], instanceof List<String> or use primitive type arguments.

Generics were added in Java 5 without changing the JVM, so old code and new code could work together. To make that possible, the compiler uses type erasure: after it has checked your generic code, it removes the type arguments and generates ordinary bytecode.

  1. Each type parameter is replaced by its bound, or by Object when there is no bound (T becomes Object; T extends Number becomes Number).
  2. The compiler inserts casts where a value of the generic type is used (String s = list.get(0) becomes (String) list.get(0)).
  3. For overridden generic methods it adds bridge methods to keep polymorphism working. For example, a class implementing Comparable<Employee> gets a synthetic compareTo(Object) that calls your compareTo(Employee).
// You write:
class Box<T> {
    private T value;
    T get() { return value; }
}
Box<String> b = new Box<>();
String s = b.get();

// After erasure it is roughly:
class Box {
    private Object value;
    Object get() { return value; }
}
Box b = new Box();
String s = (String) b.get();      // cast inserted by the compiler

Because the information is gone at runtime, ArrayList<String> and ArrayList<Integer> are the same class:

List<String> strings = new ArrayList<>();
List<Integer> ints = new ArrayList<>();
System.out.println(strings.getClass() == ints.getClass());
System.out.println(strings.getClass().getName());

Heap pollution: a ClassCastException far from the cause

Raw types and unchecked casts can put the wrong type into a generic collection. The compiler warned you ("unchecked"), but the JVM sees nothing wrong at the add. The failure appears later, at an innocent-looking line that reads the element. This is called heap pollution.

List<String> strings = new ArrayList<>();
List raw = strings;                  // raw alias: unchecked warning
raw.add(42);                         // compiles; erasure means no runtime check
System.out.println(strings.size());  // 1
String s = strings.get(0);           // ClassCastException here, at the READ
1
Exception in thread "main" java.lang.ClassCastException:
    class java.lang.Integer cannot be cast to class java.lang.String

@SafeVarargs is a related annotation. A varargs parameter of generic type (T...) is secretly a T[], which can cause pollution; if your static, final or private method only reads the array, mark it @SafeVarargs to silence the warning (the JDK does this for List.of, Arrays.asList).

Getting generic types at runtime (when you must)

The type argument of a class declaration is kept in the class file. Libraries use this: Jackson's new TypeReference<List<User>>() {} creates an anonymous subclass so that getGenericSuperclass() can read List<User>. Spring's ParameterizedTypeReference works the same way. You need this when deserialising JSON into List<User>, because List.class alone loses the element type.

Rule: generics exist only at compile time

Do not write code that depends on a generic argument at runtime (instanceof, .class, overloads that differ only by type argument). Pass a Class<T>, a Supplier<T> or a type-reference token when you need the type.

Conventions

  • Treat every "unchecked" warning as a bug until proven otherwise. Keep @SuppressWarnings("unchecked") on the smallest scope (one local variable or one method) and explain why in a comment.
  • Compile with -Xlint:unchecked to see the details.
  • Never expose raw types in public APIs.

Exceptions and edge cases

  • ClassCastException at a read of a generic value — heap pollution through a raw type.
  • ArrayStoreException — storing into a covariant array, including (T[]) new Object[n] being returned to code that expects a String[].
  • Reifiable types (known at runtime): primitives, non-generic classes, raw types, List<?> and arrays of those. instanceof and array creation work only with them.
  • Overloading by erasure: void print(Object) and <T> void print(T) in the same class clash.

Mistake: casting to T and thinking it checks anything

(T) obj compiles to no check at all (the cast erases to Object or the bound). The error shows up later, in the caller. Validate with a real Class<T>: type.cast(obj) throws ClassCastException immediately.

Interview: "What is type erasure? What are its consequences?"

  • The compiler checks generics, then replaces type parameters by their bounds (or Object), inserts casts and generates bridge methods. Done for backward compatibility with pre-Java-5 code.
  • Consequences: no new T(), no new T[], no primitives as type arguments, no instanceof List<String>, no static fields of type T, no overloads that differ only in type arguments, no generic exceptions.
  • Heap pollution with raw types shows up as a ClassCastException far from the bug.
  • Contrast with C++ templates and C# generics, which keep the type at runtime.

Interview questions — Collections and generics

What is the difference between ArrayList and LinkedList? Which do you use and why?

ArrayList is backed by a resizable array: get(i) is O(1), adding at the end is amortized O(1), inserting or removing in the middle is O(n) because elements shift. LinkedList is a doubly linked list: access by index is O(n), adding or removing at the ends is O(1), and each element costs a node object. I use ArrayList almost always: contiguous memory is cache-friendly and array copying is fast, so LinkedList rarely wins even where Big-O says it should. For a queue or stack I use ArrayDeque.

How does HashMap work internally?

It has an array of buckets (default 16). For put(k, v) it computes hashCode(), spreads it with h ^ (h >>> 16), and finds the bucket as (n - 1) & hash. An empty bucket gets a new node. Otherwise it walks the chain comparing the hash and then equals; a match replaces the value, no match appends a node. get follows the same path. When the size exceeds capacity × 0.75 the table doubles and entries are redistributed. A bucket with 8 or more nodes becomes a red-black tree if the table has at least 64 buckets (otherwise the table resizes instead), and turns back into a list at 6 nodes. Average cost is O(1); worst case O(log n) in Java 8+.

What is the contract between equals() and hashCode()? What happens if you break it?

If a.equals(b) is true then a.hashCode() == b.hashCode(). Unequal objects may share a hash code (a collision), but equal objects must not differ. If you override equals only, two equal objects hash to different buckets, so HashMap.get and HashSet.contains fail to find an entry you "just" added. The same happens if a field used in hashCode is mutated after the object becomes a key: the entry stays in the old bucket and is effectively lost. Use immutable keys or records.

Compare HashMap, Hashtable, ConcurrentHashMap and Collections.synchronizedMap.

HashMap is not thread-safe and allows one null key and null values. Hashtable is a legacy class that locks the whole map on every method and allows no nulls. Collections.synchronizedMap wraps any map with one lock, and you must still lock manually to iterate. ConcurrentHashMap allows no nulls, lets reads proceed without locking, locks only a bucket for writes, has weakly consistent iterators, and offers atomic putIfAbsent, computeIfAbsent and merge. Use HashMap in single-threaded code and ConcurrentHashMap when threads share a map.

How does HashSet avoid duplicates? Why is HashSet.add O(1)?

A HashSet wraps a HashMap; your element is the key and the value is a shared dummy object. add(e) calls map.put(e, PRESENT) and returns true only if the key was new. Duplicates are detected by hashCode and equals, so it is O(1) on average like HashMap. A TreeSet detects duplicates with compareTo instead and costs O(log n).

What is a fail-fast iterator? When do you get ConcurrentModificationException, and how do you avoid it?

Fail-fast iterators of ArrayList, HashMap and similar classes compare the collection's modCount with the value they saved at creation, and throw ConcurrentModificationException if the collection was structurally changed by anything other than the iterator itself. A for-each loop that calls list.remove(x) is the typical case, and it needs only one thread. Fix it with Iterator.remove(), removeIf, a filtered copy, or a concurrent collection such as CopyOnWriteArrayList. The check is best effort, not a guarantee.

Comparable vs Comparator: when do you use each?

Comparable (compareTo(T), in java.lang) gives a class one natural order and is used automatically by Collections.sort, TreeSet and TreeMap. Comparator (compare(T, T), in java.util) is an external rule, so you can have many orders and sort classes you cannot edit. Build them with Comparator.comparing(Employee::dept).thenComparing(Employee::salary).reversed(). Never write a - b; it can overflow. Use Integer.compare.

What is the difference between Arrays.asList, List.of and Collections.unmodifiableList?

Arrays.asList(array) is a fixed-size list backed by the array: set works and writes through, add and remove throw UnsupportedOperationException. List.of is fully immutable and rejects null. Collections.unmodifiableList(list) is a read-only view: it cannot be modified itself, but it shows changes made to the original list. List.copyOf makes an immutable copy. All of them are shallow: mutable elements can still change.

What does this print? 
List<Integer> list = new ArrayList<>(List.of(1, 2, 3, 4, 5));
list.remove(Integer.valueOf(3));
list.remove(0);
System.out.println(list);

[2, 4, 5]. remove(Integer.valueOf(3)) calls remove(Object) and removes the value 3, giving [1, 2, 4, 5]. remove(0) uses the int overload and removes the element at index 0, which is 1. With a plain list.remove(3) on the original list you would have removed the element at index 3 (the value 4) instead.

How does PriorityQueue work? How do you get a max-heap? Is iteration sorted?

It is a binary min-heap stored in an array. offer adds at the end and sifts up, poll removes the root and sifts down: both O(log n); peek is O(1); contains and remove(Object) are O(n). Pass Comparator.reverseOrder() (or any comparator) for a max-heap. Iteration and toString() show the heap array, which is not sorted; only repeated poll() returns sorted order. It rejects null and is not thread-safe.

Why should you not use Stack, Vector and Hashtable?

They are Java 1.0 classes with every method synchronized, which costs performance and still does not make compound actions safe. Stack extends Vector, so it exposes index methods that break the stack idea. Use ArrayList, ArrayDeque (via Deque) and HashMap, or the java.util.concurrent classes when threads share the data.

What is type erasure? What can you not do because of it?

The compiler checks generic types, then removes them: a type parameter becomes its bound or Object, casts are inserted, and bridge methods are generated. At runtime List<String> and List<Integer> are the same class. So you cannot write new T(), new T[n], List<int>, obj instanceof List<String>, a static field of type T, two overloads that differ only by type argument, or a generic exception class. Workarounds: pass a Supplier<T> or Class<T>, or use List<T> instead of T[].

Explain ? extends and ? super. What is PECS?

List<? extends Number> may be a list of any Number subtype: you can read elements as Number but cannot add (except null). List<? super Integer> may be a list of Integer or any supertype: you can add Integers but reads give only Object. PECS = Producer Extends, Consumer Super. In copy(List<? super T> dest, List<? extends T> src) the source produces and the destination consumes. This also explains why List<Integer> is not a List<Number> (invariance): wildcards add the safe flexibility.

Scenario: remove duplicates from a list but keep the first-seen order; then count how often each word appears.

For de-duplication: List<String> unique = new ArrayList<>(new LinkedHashSet<>(list)); — the set removes duplicates, and being linked, keeps insertion order. For counting: Map<String, Integer> counts = new HashMap<>(); for (String w : list) counts.merge(w, 1, Integer::sum);. With streams, list.stream().collect(Collectors.groupingBy(w -> w, Collectors.counting())). Both approaches are O(n); the naive if (!result.contains(x)) on a list would be O(n²).

How would you build an LRU cache in Java?

Extend LinkedHashMap with the constructor super(16, 0.75f, true) for access order, and override removeEldestEntry to return size() > capacity. Every get or put moves the entry to the end, so the eldest is the least recently used and is evicted automatically. All operations are O(1). It is not thread-safe, so wrap it with Collections.synchronizedMap or use a library such as Caffeine. The manual version is a HashMap from key to node plus a doubly linked list.

Cheat sheet — Collections and generics

  • Hierarchy Iterable → Collection → List / Set / Queue → Deque; Map is separate. Java 21 adds SequencedCollection with getFirst, getLast, reversed.
  • Program to the interface List<String> x = new ArrayList<>();
  • Defaults ArrayList, HashMap, HashSet, ArrayDeque.
  • ArrayList array-backed; default capacity 10 (lazy); grows ×1.5; get O(1); add end amortized O(1); insert/remove middle O(n); trimToSize, ensureCapacity.
  • LinkedList doubly linked, also a Deque; get(i) O(n); ends O(1); more memory; rarely the right choice.
  • HashMap index hash = h ^ (h >>> 16); index = (n - 1) & hash; capacity is always a power of two.
  • HashMap numbers default capacity 16; load factor 0.75; threshold 12; resize doubles; treeify at 8+ nodes if table ≥ 64; untreeify at 6.
  • HashMap rules one null key; not thread-safe; order undefined; keys immutable with matching equals/hashCode; O(1) average.
  • Thread-safe maps ConcurrentHashMap (no nulls, atomic merge/computeIfAbsent) over Hashtable and synchronizedMap.
  • Map idioms getOrDefault, putIfAbsent, merge(k, 1, Integer::sum), computeIfAbsent(k, x -> new ArrayList<>()).add(v), loop with entrySet().
  • LinkedHashMap insertion order; (16, 0.75f, true) = access order; override removeEldestEntry for an LRU cache.
  • TreeMap / TreeSet red-black tree, sorted, O(log n), no null key; floorKey, ceilingKey, lowerKey, higherKey, headMap, tailMap, subMap; equality by compareTo.
  • Set HashSet is backed by a HashMap; add returns false for duplicates; union addAll, intersection retainAll, difference removeAll.
  • Queue pairs add/offer, remove/poll, element/peek = throws vs returns null/false.
  • ArrayDeque stack: push/pop/peek; queue: offer/poll; no nulls; replaces Stack.
  • PriorityQueue binary min-heap; offer/poll O(log n); peek O(1); iteration not sorted; max-heap with Comparator.reverseOrder().
  • Fail-fast structural change during iteration → ConcurrentModificationException; remove with iterator.remove() or removeIf.
  • remove trap List<Integer>: remove(1) = by index, remove(Integer.valueOf(1)) = by value.
  • Sorting Comparable.compareTo (natural, inside class); Comparator.comparing(..).thenComparing(..).reversed(); never a - b; sort is stable.
  • Read-only lists Arrays.asList fixed size and write-through; List.of immutable, no nulls; unmodifiableList is a view; List.copyOf is a copy.
  • Views subList, keySet, headMap, unmodifiableX, Arrays.asList share data with their source.
  • Generics compile-time type safety; invariant (List<Integer> is not List<Number>); letters T, E, K, V, R; diamond <>.
  • Bounds <T extends Comparable<T>>; multiple: <T extends Number & Comparable<T>> (class first).
  • PECS Producer Extends, Consumer Super: copy(List<? super T> dest, List<? extends T> src).
  • Erasure limits no new T(), new T[], List<int>, instanceof List<String>, static T fields; raw types and unchecked casts cause heap pollution.

Practice — Collections and generics

  1. Word frequency (easy). Read a paragraph into words (lower-case, strip punctuation), count them with merge, and print the top 3 words with counts. Break ties alphabetically. Done when the output is the same on every run and you can say why a HashMap alone could not guarantee that order.
  2. Set operations (easy). Given two lists of student ids, print the ids in both lists, only in the first, and in exactly one (symmetric difference), all sorted. Then remove duplicates from a list while keeping the first-seen order. Done when you use retainAll, removeAll, TreeSet and LinkedHashSet and copy before each bulk call.
  3. Sorting employees (easy–medium). Create an Employee record (id, name, dept, salary, and a nullable manager name). Give it a natural order by id with Comparable, then sort by dept, salary descending, name; and by manager name with nulls last. Done when no comparator uses subtraction and a TreeSet of employees sorted by salary does not drop employees with equal salary.
  4. Break and fix a loop (medium). Write a loop that removes all even numbers from a list with list.remove inside a for-each and make it throw ConcurrentModificationException. Then fix it three ways: Iterator.remove(), removeIf, and a stream. Also reproduce the "second-to-last element" case that does not throw. Done when you can explain modCount in two sentences.
  5. LRU cache (medium). Build LruCache<K, V> on LinkedHashMap with capacity 3 and test eviction after a get. Stretch goal: rebuild it with your own HashMap plus a doubly linked list so get and put stay O(1). Done when the printed order matches a hand-traced sequence of 10 operations.
  6. Generic utilities (medium). Write <T extends Comparable<? super T>> T max(Collection<? extends T> c), <T> void copy(List<? super T> dest, List<? extends T> src), a generic Pair<A, B> with swap(), and static double sum(List<? extends Number> list). Done when each compiles with the "wrong" call commented out and you can explain the compiler error for it.
  7. Build MyArrayList<T> (roadmap exercise, medium). Implement a growable list from scratch, backed by an Object[]: 
    public class MyArrayList<T> implements Iterable<T> {
    private Object[] data = new Object[10];
    private int size;

    public void add(T item) { /* grow when full: new length = old + old / 2 */ }
    public void add(int index, T item) { /* shift right with System.arraycopy */ }
    public T get(int index) { /* check range, cast with @SuppressWarnings */ return null; }
    public T set(int index, T item) { return null; }
    public T remove(int index) { /* shift left, null the last slot */ return null; }
    public int size() { return size; }
    public boolean isEmpty() { return size == 0; }
    public Iterator<T> iterator() { return null; }   // hasNext/next, bonus: fail-fast
}
    Done when 1,000 adds work, a bad index throws IndexOutOfBoundsException with a clear message, removed slots are set to null (no memory leak), and a for-each loop over it works. Bonus: add trimToSize() and a modCount check.
  8. Build MyHashMap<K, V> (roadmap exercise, hard). Use an array of buckets, each a singly linked chain of nodes: 
    public class MyHashMap<K, V> {
    private static class Node<K, V> {
        final int hash; final K key; V value; Node<K, V> next;
        Node(int hash, K key, V value, Node<K, V> next) { /* assign */ }
    }

    private Node<K, V>[] table;            // create with (Node<K, V>[]) new Node[16]
    private int size;

    public V put(K key, V value) { return null; }   // replace value or add; resize at 0.75

  9. Top-K frequent words (stretch). Return the K most frequent words of a text using a HashMap for counts and a size-K min-heap PriorityQueue. Done when the time complexity is O(n log K) and you can justify why a min-heap, not a max-heap, keeps the K largest.
